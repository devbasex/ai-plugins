# #4285: cross-review: 修正担当が文書の直しで直訳の語を戻し、設計承認の前に差し戻しが続く

正は課題の本文（#4285）で、この文書はそのコピーである。本文から作り直す。手で直さない。

## 何が起きたか

2026-11-23、計画 p9 のレーン lz2-ci で #3959 の設計を進めていた。conductor は設計 PR https://github.com/devbasex/ai-plugins/pull/4280 の文書から直訳の語（英語の語を和語へ直訳した語と造語。`document-style` のルール 11 が使わないと定める）を 0 件にしてから、相手役の AI がレビューして修正担当の AI が直す仕組み（cross-review）を回した。修正担当の直しで直訳の語が 24 件戻り、conductor が直し直した後も、オーガナイザーの確かめで 2 か所が残っていた。

同じ理由の変更要求は続いている。2026-11-23〜24 に、設計承認ゲートの前では #4000 #3877 #3908 #4036 #3959 で計 6 回以上、リリース承認ゲートの前では PR https://github.com/devbasex/ai-plugins/pull/4325 で 2 回起きた。語を探す手段はオーガナイザーが手で打つ grep で、#4280 では `普及の段階` を取りこぼし、#4325 では前の回に指摘された語だけを数え直したため、ほかの語が 100 行以上残った。

## 種類

機能追加（語の決まりは `document-style` のルール 11 に既にあるが、修正担当へ渡すことと、足した行の廃止した語を push の前に機械で見つけることは、今のコントラクトにも手順書にも無い。新しい振る舞いを足す）

## 今の姿

- 直訳の語の決まりは [document-style の SKILL.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/document-style/SKILL.md) のルール 11 が持つ
- 使わないと決めた語（廃止した語）と置き換え先は、プロジェクトの用語集 [docs/glossary/glossary.json](https://github.com/devbasex/ai-plugins/blob/main/docs/glossary/glossary.json) が持つ。1 文字の語などは、前後が漢字の出現に当てない形（`deprecated_standalone`）で登録できる
- 修正担当への指示（`plugins/ndf/src/ndf/domains/crossreview/drive.py` の `_fix_prompt`）は、指摘の一覧・指摘の基準・結果の形だけを持ち、語の決まりを持たない
- 指摘の基準（`plugins/ndf/contracts/data/review-criteria.json` の `not_written`）は「字句や言い回し」を書かないとする。相手役は語の戻りを指摘しない
- 修正担当のコミットは、語を見ずに cross-review が push する（同じファイルの `_round` → `_push`）
- 廃止した語を見る機械の検査は次の 2 つで、設計文書・確定仕様・PR の題と本文・承認資料の語を見るものは無い

| 検査 | 見る範囲 |
| --- | --- |
| `ndf records glossary meanings` | 用語集自身の意味の説明だけ（`glossary_decide.py` の `deprecated_in_meanings`）。`ndf check` の中では動かず、CI の `glossary.yml` が単独で打つ |
| `ndf check` の `banned-word` | `plugins/ndf/` のファイルだけ（全行） |

2026-11-24 の `main`（c870db5f6）で確かめた結果: 2 つの検査はどちらも `ok` を返す。一方、同じ規則の正規表現（`ndf.checks.words`）を `issues/` の要求と設計の 370 ファイルに当てると 33,040 件、`docs/specifications/` の 211 ファイルに当てると 13,416 件に当たる。今ある文書の全行を落とす形は取れない。

登録を求められた語の今の状態（同じ `main`）:

| 語 | 用語集 | 備考 |
| --- | --- | --- |
| `段`・`枠`・`宣言` | 登録済み | `段` と `枠` は前後が漢字の出現に当てない形 |
| `席` | 生きた語（コンテキスト `ndf-cross-review`） | 生きた語と廃止した語を同じコンテキストで重ねられない |
| `約束`・`段階`・`普及の段階`・`届ける`・`届く`・`写し`・`置き場所`・`書き手`・`背景`・`照らす`・`束ねる`・`畳む`・`溶かす`・`事象` | 未登録 | `plugins/ndf/` の中に多く残る（部分一致で `段階` 223 件・`写し` 196 件・`照ら` 190 件・`書き手` 239 件・`事象` 334 件など）。`事象` と `書き手` は要求仕様のテンプレートの見出しと欄の名前でもある（#4258） |

## 何を足すか・変えるか

| | 今 | 足した後 |
| --- | --- | --- |
| 修正担当への指示 | 語の決まりが無い | 文書のファイルを直すときは `document-style` のルール 11 を読んで従う、が入る |
| 修正担当の直しが足した廃止した語 | 誰も見ずに push される | push の前に見つかり、修正担当が直すか、未解決の指摘として残る |
| 承認ゲートの前の語の確かめ | オーガナイザーが手で grep を打つ | 1 つのコマンドが、足した行・PR の題と本文・承認資料を用語集の全部の廃止した語で見る |
| 用語集 | 変更要求で挙がった語が未登録 | 2026-11-23〜24 の変更要求で挙がった語が登録され、語ごとに当てない形を持てる |

## 今の利用者への影響と互換

用語集の設定（`.ndf/glossary.json`）の無いプロジェクトでは、検査は何も見ず、cross-review の終わり方も変わらない。用語集を持つプロジェクトでは、修正担当が足した行に廃止した語があると cross-review が収束しなくなる。登録済みの語の当たり方は変わらない。

## なぜ困るか

直訳の語を理由にした承認の前の変更要求は、1 回ごとに、直す・push する・求め直すの往復になる。修正担当は会話のたびに新しい語を足し、手の grep は知っている語しか見ないため、次の語が次の変更要求になる。放置すると、承認する人が語を見つける役を続け、スプリントごとに数回の往復が続く。

## 目的

- 修正担当が直訳の語を文書へ足さず、足したときは承認ゲートへ着く前に機械が見つける
- 承認する人とオーガナイザーが、語を数える作業から離れる

## 対象範囲

含む:
- cross-review の修正担当への指示に、語の決まりの参照を足す
- 修正担当の直しが足した廃止した語を、cross-review が push の前に見つける
- 足した行・PR の題と本文・承認資料の廃止した語を見る検査と、承認ゲートの資料を出す前にそれを打つこと
- 変更要求で挙がった語（「今の姿」の表の語）の用語集への登録と、語ごとに当てない形
- 登録した語で既にある検査（`ndf check`・`meanings`）が落ちないようにすること。NDF が配るテンプレートの見出しと欄の名前（#4258 の `事象`・`書き手`）の言い換えと、`席` の生きた語を「シート」へ改めることを含む

含まない:
- 修正担当へ PR の範囲・設計文書を渡すこと（#4182）、修正担当の時間の上限と静的解析（#4183）、修正の後のテスト（#4294）。直す場所（`_fix_prompt`）が同じで、親の #4350 が起動の入力を 1 つの組み立てに集める
- 今ある文書（`issues/`・`docs/specifications/` など）に残る廃止した語の一括の言い換え、上の表に無い語の洗い出し（#3610）
- 廃止した語の判定に AI を使うこと
- cross-refactoring など、cross-review の外で文書を直す担当への指示

## 前提

- 前提 1: 検査が見つけるのは、用語集に登録した語だけである。登録の無い直訳の語は、修正担当への指示（受け入れ条件 1）と相手役・人のレビューで見つけ、見つけたら用語集へ足す
- 前提 2: 「文書のファイル」は、プロジェクトの設定（`.ndf/project.json` の `docs.files`）か、無ければ `**/*.md` と用語集の `source`・`document` である（`development-workflow` の SKILL.md の定義）
- 前提 3: 「足した行」は、ベースブランチとの分岐点からの差分で増えた行から、同じ差分の中で別の場所から消えた行と同じ内容の行（移しただけの行）を除いたものである。修正担当の直しを見るときは、修正担当を起動する前の HEAD からの差分で同じように数える
- 前提 4: 語の決まりの文は `document-style`、語の一覧と置き換え先は用語集が、それぞれ 1 か所で持つ。`document-style` の表と grep の例は、用語集の無いプロジェクトにも配る一般の例であり、検査は読まない

## 受け入れ条件

修正担当への指示:

- [ ] 1. cross-review が修正担当を起動する指示に、文書のファイルを直すときは `document-style` の SKILL.md のルール 11 を読んで従うという文と、導入先でその SKILL.md を開けるパスが入る
- [ ] 2. 修正担当への指示・`plugins/ndf/contracts/data/review-criteria.json`・cross-review のコードと手順書に、廃止した語の一覧と置き換えの表が無い（`document-style` と用語集への参照だけを持つ）

cross-review での検出:

- [ ] 3. 修正担当のコミットが足した行に廃止した語があるとき、そのラウンドの push の前に、ファイル・行・語・置き換え先を持つ記録が作られる
- [ ] 4. 条件 3 の語は、push の前に修正担当が直して 0 件になるか、未解決の指摘として残る。未解決の指摘として残った実行は `converged` で終わらない
- [ ] 5. 最後のラウンド（`max_rounds`）の修正が廃止した語を足して残ったときも、未解決の指摘に数えられ、記録のコメント（`ndf:cross-review-report`）の未解決の件数に入る
- [ ] 6. 修正担当を起動する前からある行の廃止した語は、条件 3 の当たりにならない
- [ ] 7. 用語集の設定が無いプロジェクトの cross-review は、条件 3 の検査をせず、終わり方と結果 JSON の `status` が変更の前と同じである

検査のコマンド:

- [ ] 8. ベースブランチを渡して 1 つのコマンドを打つと、足した行の廃止した語が、ファイル・行・語・置き換え先とともに並び、1 件以上あれば 0 でない終了コードになる。0 件なら `status: ok` になる
- [ ] 9. 条件 8 の対象は、プラグインの外の文書（`issues/` の要求・設計・詳細設計、`docs/specifications/`）と、コードの説明文（コメント・docstring）・テストの名前を含む
- [ ] 10. 移しただけの行（前提 3）に廃止した語があっても、条件 8 は当てない
- [ ] 11. コードブロック・インラインコード・引用（行頭の `>`。要求仕様の「リクエスト（原文）」など）の中の廃止した語は、条件 8 で当てない
- [ ] 12. 同じ検査を PR の題と本文、承認資料の文に当てられ、条件 8 と同じ形で当たりが並ぶ
- [ ] 13. 設計承認ゲートとリリース承認ゲートの資料を出す経路は、資料を出す前に条件 8 と条件 12 の検査を打つ。当たりが 1 件以上あれば、資料を出さずに当たりを返す
- [ ] 14. 条件 13 の検査は、前の回の指摘にかかわらず毎回、用語集の廃止した語の全部を見る
- [ ] 15. 用語集か用語集の設定が読めない（JSON の誤りなど）とき、条件 3・8・13 は「廃止した語は無い」と報告せず、読めないことを理由に止まる

語の登録と誤検知:

- [ ] 16. 「今の姿」の表の語（`約束`・`段`・`段階`・`普及の段階`・`届ける`・`届く`・`席`・`枠`・`写し`・`置き場所`・`書き手`・`背景`・`照らす`・`束ねる`・`畳む`・`溶かす`・`事象`・`宣言`）が、置き換え先とともに廃止した語として用語集に登録されている
- [ ] 17. 活用した形（`照らして`・`束ねた`・`畳んだ`・`溶かした`・`届けた` など）を足した行が、条件 8 で当たる
- [ ] 18. 語ごとに「当てない形」を用語集のデータだけで足せる。コードを変えずに 1 語を足すと、次の検査から当たらなくなる
- [ ] 19. `手段`・`段落`・`階段`・`レッドライン`・`背景色`・見出しの `背景` は、条件 8 で当たらない
- [ ] 20. 置き換え先の文が別の廃止した語を含む登録は、用語集の検査で当たる（置き換えが次の当たりを作らない）
- [ ] 21. 登録の後、`ndf check` と `ndf records glossary render --check` と `ndf records glossary meanings` が `ok` を返す
      前提の確認: 2026-11-24 の `main`（c870db5f6）で 3 つを打ち、どれも `ok`（`ndf check` は 1,335 ファイルに違反なし）
- [ ] 22. NDF が配る要求仕様・設計書・詳細設計書のテンプレートの見出しと欄の名前だけをコピーした文書は、条件 8 で 0 件になる

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 条件 3・8 の検査は LLM を起動しない。修正担当を起動し直すのは、廃止した語が残ったときだけである |
| 運用・保守性 | 当たりの記録は、人が読まずに直せる形（ファイル・行・語・置き換え先）で残る |
| 移行性 | 登録済みの `deprecated`・`deprecated_standalone` の形の用語集は、書き換えずにそのまま読める |

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。廃止した語を足した行で探すコマンドと、用語集の「当てない形」の欄が増える（追加だけで、既にある形と互換） |

> ## 現象
>
> cross-review の修正担当（claude）が指摘を直すときに、直訳の語を文書へ戻す。修正担当への指示に、`document-style` のルール 11（直訳の語と造語を使わない）が入っていないためと見られる。
>
> 実例（2026-11-23）: 計画 p9 のレーン lz2-ci の #3959 の設計 PR https://github.com/devbasex/ai-plugins/pull/4280 。conductor が直訳の語を 0 件にした後、cross-review の修正担当の直しで **24 件が戻った**。conductor が直し直し、オーガナイザーの確かめでさらに 2 か所（「届ける」「段階」）が残っていた。
>
> 同じ種類の戻りは、設計承認の前の確かめで毎回起きている（11-23 の lctx の #4000・p9 の lsplit の #3877 #3908 #4036 も、直訳の語を理由に 2 回ずつ差し戻した）。
>
> ## 期待する振る舞い
>
> - 修正担当は、文書のファイルを直すときに `document-style` の語の決まり（直訳の語と造語を使わない）に従う
> - 修正担当の直しが直訳の語を足したら、cross-review の中で見つかり、承認ゲートへ持ち越さない
>
> ## 受け入れ条件
>
> 1. 修正担当を起動する指示に、文書のファイルを直すときの語の決まり（`document-style` のルール 11 を読む）が入る
> 2. 修正担当の直しで直訳の語が増えたとき、cross-review がそれを未解決の指摘として残す（あるいは修正担当が直してから終える）
> 3. 文書の語の決まりは 1 か所（`document-style`）にだけ持ち、cross-review の側へ写さない
> 4. **直訳の語を機械の検査で落とす。** 設計承認の前に差し戻した直訳の語（2026-11-23〜24 の実例: 約束・段・段階・届ける・席・枠・普及の段階）を用語集の廃止した語（`.ndf/glossary.json`）へ登録し、既にある `ndf records glossary meanings`（`ndf check` の中）が push の前に落とす。オーガナイザーの手の grep に頼らない（11-24 の #4280 では手の grep が「普及の段階」を最初に取りこぼし、1 往復増えた）。誤検知を避けるため、語ごとに除く形（手段・段落・レッドラインなど）を持てるようにする
>
> ## 効果の見込み
>
> 2026-11-23〜24 に、直訳の語を理由にした設計承認の前の差し戻しが 6 回以上あった（lctx の #4000、lsplit の #3877 #3908 #4036、lz2-ci の #3959 が 2〜3 回ずつ）。1 回ごとに、直す・push・求め直すの往復が入る。検査が push の前に落とせば、この往復が無くなる。開発工程を速くする案の 1 つ（傘は #4069）
>
> ## 追加の実例（スプリント p9-lsplit-r2、2026-11-24）
>
> 設計承認ゲートの 2 回に続き、**リリース承認ゲートの前でも 2 回**差し戻した（PR https://github.com/devbasex/ai-plugins/pull/4325 ）。
>
> | 回 | 残っていた語 |
> | --- | --- |
> | 1 | 段階・写し・届く・置き場所・書き手 |
> | 2 | 背景 75 行・照らす 15 行・束ねた 10 行・畳む・溶かす など（1 回目の指摘に無かった語だけを数えたため残った） |
>
> - 数える対象は、`main` との差分で足した行（移しただけの行を除く）・PR の題と本文・承認資料・確定仕様の 4 つである。実装の worker が足したコードの説明文とテストの名前にも残っていた
> - 受け入れ条件 4 へ足す語: 届く・写し・置き場所・書き手・背景（バックグラウンドの意味）・照らす・束ねる・畳む・溶かす・事象・宣言
> - 置き換えが別の廃止語を足すことがある（「報告の写し」を「報告のコピー」へ直す時に用語の検査が落ち、直し直した）。語の一覧は用語集の 1 か所に置き、検査と置き換えの表が同じ一覧を読む
> - 検査は、承認ゲートの資料を出す前にも打つ（指摘された語だけの数え直しでは、次の語が次の差し戻しになる）
