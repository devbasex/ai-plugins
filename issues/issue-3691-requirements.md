## 今の利用者への影響と互換

- NDF の利用者には、依存のバージョンが変わる。外部 CLI か本体が NDF の定義した下限より古い環境では、NDF のコマンドが理由を出して止まるようになる（今は止まらずに進み、使えない引数で失敗する）
- このリポジトリの開発者には、依存の一覧の Issue の行が増え、脆弱性の Issue と Dependabot の SHA の更新の PR が届くようになる

## なぜ困るか

- 推移的な依存とほかの lock は遅れても誰も気づかない。根の lock は 86 本のうち 47 本が遅れ、playwright-kit の lock には既知の脆弱性が 7 件ある
- タグで参照した Action は、タグを付け替えられると中身が黙って変わる。公開から日の浅いバージョンも待たずに PR にする
- 外部 CLI の引数が変わっても気づかず、利用者の環境で初めて失敗する
- 固定の理由が自由文だと、相手が制約を外しても固定が残り続ける

## 目的

- このリポジトリの依存（推移的な依存・ほかの lock・コードの中の固定・外部 CLI・Actions）を、利用者の方針（できるだけ最新の安定版・公開から 7 日待つ）のとおりに、漏れなく・安全に保つ。上げた後に確かめる範囲が分かり、脆弱性と固定の解除の時機を週 1 回の知らせで知れる

## 受け入れ条件

起票した時点の 6 項目（#3388 の設計の案のまま）を見出しに残し、確かめられる形を下に足した（2026-11-21、要求と受け入れ条件の工程）。

- [ ] 1. 推移的な依存・ほかの lock・コードの中のバージョンの固定が、上げる対象の一覧に入る（3380-3）
  - 依存の一覧の Issue に、「今の姿」の表で対象とした lock ごとの推移的な依存を上げる行と、コードの中で固定した uv のバージョンの行が出る。設定の検査のテストが、対象の lock と固定の保存先の一覧を縛り、1 つを外すと落ちる
- [ ] 2. 上げた後の確かめが CI の合否に加えて、変わった依存の公開 API を使う箇所のテストの一覧を出す（3380-6）
  - lock を変えた PR に、変わったパッケージ（名前・前と後のバージョン）と、そのパッケージを import するモジュールと、そのモジュールを import するテストの一覧が 1 件のコメントで出る。lock を変えない PR には出ない。一覧を作る処理は記録した lock の差分の入力で単体テストが縛る
- [ ] 3. 外部 CLI（`gh`・`claude`・`codex`）と本体のバージョンの下限が定義にあり、下限より古いと理由を出して止まる。外部 CLI の `--help` の出力を見本と照らす（3380-8、分類 P）
  - 下限より古いバージョンを返す偽の CLI を `PATH` の先に置くと、その CLI を使う NDF のコマンドが、CLI の名前・見つけたバージョン・下限を出して 0 以外で終わる。下限と同じバージョンでは止まらない
  - 週 1 回の検査が、NDF が使う引数の見本と今の `--help` の出力を照らし、見本の引数が `--help` に無ければ失敗で終わる
- [ ] 4. Actions を SHA で固定し、Dependabot の cooldown を定義する（分類 P）
  - `.github/workflows/` の外部の Action の参照がすべて 40 桁の SHA で、後ろにバージョンの注記がある。タグで参照する行を足すと検査が落ちる。`.github/dependabot.yml` の Actions の項目に `cooldown` の 7 日がある
- [ ] 5. 上げる先の表が公開から 7 日の規則で直り、依存が公開から 7 日たった最新の安定版にそろう（3380-1・3347-10）
  - 対象のすべての uv のプロジェクトの `[tool.uv]` に `exclude-newer = "7 days"` があり、その lock に `exclude-newer-span = "P7D"` があり、`uv lock --check` が通る。DBOS と固定した依存を除く直接の依存と推移的な依存が、実装の時点の上げる先にある（`plugins/ndf` の直接の依存は #3370 の受け入れ条件 4）
- [ ] 6. 週 1 回の検査が脆弱性の知らせも拾い、バージョンを固定する理由が解除を判定できる欄で残る（3380-2・3380-4・3380-9）
  - 週 1 回（と手動）の検査が、対象の lock の既知の脆弱性を、遅れの知らせとは別の 1 件の Issue にまとめ、脆弱性があれば作るか書き直し、無くなれば閉じる。脆弱性の取得が 1 つでも失敗したら Issue を書き換えずに失敗で終わる
  - 固定する理由が種類・相手・制約・見直す日の欄を持ち、欄が欠けると設定の検査のテストが落ちる。相手が制約を外したか見直す日を過ぎた固定を、週 1 回の検査が知らせる
