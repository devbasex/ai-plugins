## 目的

- 利用者が CLI のセッションの前にいなくても、自分の GitHub のリポジトリで NDF のスプリントを Web から始め、複数を並列に進められる状態にする（#2168 の条件 4・5 の前半、条件 10 のうち ② と ③）
- 承認の依頼で実行ジョブを終え、答えで続けることで、人の答えを待つ間にコンテナの費用を払わない

## 前提

- 前提 1: GitHub App はサービスが 1 つ持ち、利用者はそれを自分のリポジトリ（個人か組織）へ導入する。App の秘密鍵は private リポジトリのインフラが Secrets Manager に置き、サービスのコードは ARN だけを受ける。App が求める権限の一覧（中身の読み書き・Pull Request・課題・チェックの読みなど）は設計で決め、承認ゲート 1 で人が見る（C2）
- 前提 2: 利用者がリポジトリを登録できるのは、そのリポジトリが App の導入の対象で、かつ利用者の GitHub の身元がその導入へ届くと GitHub の API で確かめられたときだけである。Google でログインした利用者は、登録の前に GitHub の身元を結び付ける。結び付けの形は設計で決める
- 前提 3: 「同時に動かせるスプリントの実行」の数は、終わりの状態（終わった・止まった・失敗・取り消した）に達していないスプリントの実行を数え、承認待ちも含める。承認の答えで続ける再開は、使える量の判定にかけない（数が増えないため）。誤っていれば数え方の関数 1 つを直せば済む
- 前提 4: チームのアカウントでは、リポジトリの登録・外し、キーの持ち込みの保存・消去は持ち主（`role` が `owner`）だけが行い、スプリントの開始・取り消しは席を持つ人が行う
- 前提 5: ランナーが使う CLI は `claude` だけにする。cross-review は、使えるランタイムが 1 つのとき 2 つの枠を `claude` と `claude-2` で埋める既存の振る舞い（`plugins/ndf/skills/cross-review/SKILL.md`）に任せ、ランナーは 2 つ目の CLI を入れない
- 前提 6: ランナーは GitHub App の秘密鍵を受け取らない。導入の token（GitHub の仕様で 1 時間で切れる）は、実行の制御が実行ジョブの token で認証して渡し直す
- 前提 7: 形態 ② の利用者の AWS のロールは、外部 ID（アカウントごとの値）つきで引き受ける。外部 ID の値の作り方は設計で決める
- 前提 8: NDF のチャネル（`NDF_CHANNEL`）は、サービスの設定 1 つで正式版を既定にする。アカウントごとの選択は持たない
- 前提 9: #2206 の hook が「AI が代わりに判断した問いと答え」を NDF の記録（`progress.jsonl` か作業の報告）へ残す形は #2206 が決める。#2206 が入るまで、ランナーはその記録を翻訳しないだけで、ほかの受け入れ条件は満たせる
- 前提 10: 承認の依頼の答えを読む経路（#2173）は、この課題の実装の時点で入っていない。`resume` の受け入れ条件は、#2173 の経路の形どおりに応える試験用の代役で確かめる
- 前提 11: 課題の候補を選ぶ AI は、登録したリポジトリの棚卸しの順位（`/ndf:backlog-refinement` がマイルストーンの説明へ書く順位の表）を読み、`claude` で理由を作る。順位の表が無いリポジトリでは、開いている課題を新しい順に候補として出す。選ぶ処理を実行ジョブとして動かすか、API の中で動かすかは設計で決める

## 対象範囲

含む:
- 取り込み: GitHub App の導入の案内・リポジトリの登録と外し・登録の一覧（`factory/api/`・`factory/web/`）
- キーの持ち込み: 形態 ② の Anthropic API キーかロールの ARN の保存・差し替え・消去（Secrets Manager。値は返さない）
- 実行の制御: スプリントの実行と実行ジョブの状態、使える量による開始の判定、実行ジョブの token の発行、ECS Fargate のタスクの起動と停止の知らせの受け取り、`appendControlEvent` による `job.finished`（`control`）の直書き、打ち切りの時間による停止、再開の要求の受け口（#2173 が使う）、実行ジョブを渡す口（#2189 が使う）、利用者による取り消し、導入の token の渡し直し
- ランナー（`factory/runner/`）: clone・NDF の導入と版の固定・conductor の起動・`sprint.json` と `progress.jsonl` と作業の報告から進捗の事象への翻訳と送信・`usage.recorded`・S3 への状態の保存と復元・`resume` での答えの読み出しと NDF への記録・形態 ② ③ での claude の呼び方
- 画面: リポジトリの登録・キーの持ち込み・スプリントを始める（AI が選んだ課題の候補と理由・外す・足す・選び直させる）
- #2216: `step.recorded` の Pull Request の参照の照合（確定仕様を直す変更を含む）
- #2206 から回ってきた、AI が代わりに判断した問いと答えの事象（契約を直す変更を含む）
- 契約で「#2186 が決める」とされた値: 実行ジョブの打ち切りの時間・token の期限・発行の鍵の変数の名前・`gate.reached` の切り詰めの形

含まない:
- `factory/contracts/` の既存の形の変更のうち、上の 2 点（#2216・#2206）以外（#2171）
- 進捗の受け口の既存の処理（#2171）。#2216 の照合を足す箇所だけを変える
- ECS・S3・Secrets Manager・DynamoDB・GitHub App の作成などインフラの定義（private リポジトリ）
- 手元のランナー（形態 ①）の登録・心拍・受け取り（#2189）。この課題は渡す口だけを持つ
- 一覧と詳細の画面（#2172）、承認の依頼の保存・通知・Web からの承認（#2173）、料金と台帳（#2174）
- 承認ゲートの外の問い合わせを止める hook そのもの（#2206）
- 取り込むリポジトリの起点・テスト・配布・進め方の入力欄（確定仕様の決定 8。ランナーの中の NDF が `.ndf/` から読む）
- 止まった・失敗したスプリントの実行を同じ実行のまま続け直すこと（新しいスプリントとして始める）

## 受け入れ条件

### 取り込み

- [ ] 1. 画面に GitHub App の導入への案内があり、導入を終えた利用者は、その導入の対象のリポジトリを登録の候補として一覧で見られる
- [ ] 2. 導入の対象でないリポジトリ、または利用者の GitHub の身元がその導入へ届かないリポジトリの登録は 403 で拒まれ、登録の行は増えない
- [ ] 3. 同じアカウントに同じリポジトリを 2 回登録すると 409 を返し、行は 1 つのまま
- [ ] 4. 持ち主は登録を外せる。終わりの状態に達していないスプリントの実行があるリポジトリを外そうとすると 409 で拒まれる
- [ ] 5. 他人のアカウントの登録の一覧・登録・外しは、#2170 の I18 と同じ 403 の本文を返し、有無を明かさない

### キーの持ち込み（形態 ②）

- [ ] 6. 持ち主は Anthropic API キーか AWS のロールの ARN のどちらか 1 つを保存・差し替え・消去でき、画面と API は「登録済みか」と「種類」と「更新の時刻」だけを返す
- [ ] 7. 保存したキーの値は、どの API の応答・サービスのログ・進捗の事象・実行ジョブの指示（環境変数）にも出ない。ランナーへ渡るのは置き場の ARN（`MODEL_CREDENTIAL_SECRET_ARN`）だけで、そのアカウントの実行ジョブにだけ渡る
- [ ] 8. ロールを引き受けるときは、アカウントごとの外部 ID を付ける。外部 ID が違うロールの信頼の設定では claude を呼べず、実行ジョブは `failed` で終わる

### スプリントを始める

- [ ] 9. スプリントを始める画面を開くと、AI が選んだ課題の候補が、課題ごとの理由つきで出る
- [ ] 10. 利用者は候補から課題を外す・登録したリポジトリの開いている課題を足す・「AI に選び直させる」を行え、確かめた並びで開始できる。開いていない番号・別のリポジトリの番号は 400 で拒まれる
- [ ] 11. 開始は `judgeLimits` の判定で許されたときだけ通る。上限ちょうどの数のスプリントの実行が終わりの状態でないとき、開始は 409 で拒まれ、本文に `reasons`（量・上限・今の値）が載る。形態 `managed` では月の token の上限も照らす
- [ ] 12. 形態 `byok` でキーが保存されていないアカウントの開始は 409 で拒まれる。形態 `local` のアカウントの開始は ECS を起動せず、実行ジョブを #2189 の渡す口へ積む
- [ ] 13. 開始の時点で GitHub App の導入がそのリポジトリへ届かなくなっていれば、開始は 409 で拒まれる
- [ ] 14. 開始が通ると、スプリントの実行と最初の実行ジョブ（`START=new`、`EXECUTION_MODE` はアカウントの値の写し）が作られ、ECS のタスクが起動する。起動に失敗したら実行ジョブとスプリントの実行はどちらも失敗になり、利用者は画面で失敗を見られる

### 実行の制御

- [ ] 15. 承認の依頼が出た実行ジョブは `job.finished`（`gate`）で終わり、スプリントの実行は承認待ちになる。#2173 からの再開の要求で、`START=resume` と `APPROVAL_REQUEST_ID` を持つ新しい実行ジョブが起動する。承認待ちでないスプリントの実行への再開の要求は 409 で拒まれる（I8）
- [ ] 16. 登録したリポジトリと違うリポジトリの Pull Request を申告した `step.recorded` は 403 を返し、`pr_ref` を登録しない（#2216）
- [ ] 17. 登録したリポジトリの Pull Request を申告した `step.recorded` は、今どおり 202 で残る（#2216）
- [ ] 18. #2206 の記録がある実行では、AI が代わりに判断した問いと答えが進捗の事象として残る（前提 9）
- [ ] 19. 1 つのスプリントの実行で、実行ジョブが動いている間の 2 つ目の起動（再開の要求の重複を含む）は拒まれ、同時に動く実行ジョブは常に 1 つ（I9）
- [ ] 20. ランナーが `job.finished` を送れずにタスクが止まると、実行の制御が `job.finished`（`failed`、`source` は `control`）を書く。ランナーの分が先にあれば書かず、進捗の記録に `job.finished` は 1 件だけ残る
- [ ] 21. 打ち切りの時間を超えた実行ジョブは実行の制御が止め、`failed` で終わる。打ち切りの時間の値は、設計で示す実測（同じ規模の NDF のスプリントの所要の秒）から決めて設定に置く
- [ ] 22. 実行ジョブの token は `signRunJobToken` で実行ジョブごとに発行され、`verifyRunJobToken` で確かめられ、期限は打ち切りの時間より長い。別の実行ジョブの `job_id`・`sprint_run_id` の事象は受け口が 403 で拒む
- [ ] 23. 利用者がスプリントの実行を取り消すと、動いている実行ジョブが止まり、スプリントの実行は終わりの状態になり、使える量の数から外れる
