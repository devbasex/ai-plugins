# #3518: ndf-next: .ndf/ の宣言をまとめた仕様書と全種の JSON Schema を置き、連携システムが設定ページを作れるようにする

正は課題の本文（#3518）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 目的

連携システム（NDF を外から呼ぶシステム。サービス Factory のランナーと、それを使って設定ページを作る側）が、11.0.0（ndf-next）の NDF について次の 2 つを 1 か所で引けるようにする。

1. リポジトリの `.ndf/` に置く**宣言**（人が決める設定のファイル）の、ファイルごとのキー・型・既定値・取りうる値。設定ページの入力欄をここから作る
2. NDF を外から呼ぶ面（コマンド・環境変数・受け渡しのファイル・hook）の**入出力の規約**。呼び方と結果の形をここから検証する（#3519 を取り込んだ）
3. NDF の中で Skill・エージェント・AI が呼ぶ面（配る Skill と、AI が打つ `bin/ndf` の副命令）の入出力。公開する面と同じ仕組みで載せ、各行に「公開（外の呼び手に約束する）」か「内部（予告なく変えてよい）」かを示す（#3519 の範囲の追加）

どちらも、機械が読む JSON Schema と、そこから生成する人が読む文書の 2 つで出す。今はこれらの事実が設定の一覧（`plugins/ndf/contracts/index.md`）・キーの一覧（`plugins/ndf/contracts/settings/*.json`）・5 種だけの JSON Schema・ndf-next の契約（`plugins/ndf-next/contracts/`）・主題ごとの確定仕様に分かれていて、ファイル・副命令ごとに 1 つの場所で読めない。

11.0.0 で `plugins/ndf/` は `plugins/ndf-next/` と入れ替わるため、対象は ndf-next だけにする（利用者の決定）。ndf-next は M7 #3302・S1a 後半 #3303 でまだ変わるため、生成と検査を CI に載せ、後の変更で文書が古くならない状態にする。

## 前提

- 前提 1: `.ndf/` の宣言の一覧の正本は、ndf-next の置き場の表（`plugins/ndf-next/contracts/domains/ndf-files.json`）のうち、置き場が `.ndf/` で種類が宣言の行である（2026-11-14 時点で 19 行。`project.json`・`supervise.json`・`release.json`・`worktree.json`・`worktree.local.json`・`glossary.json`・`instructions.json`・`mvv.json`・`mvv.md`・`pace.json`・`review.json`・`backlog.json`・`runtimes.json`・`ask.json`・`context.json`・`estimate.json`・`issue-items.json`・`projects.json`・`code-metrics.json`）。ndf-next が足した行・消した行は、この表の変更として扱う
- 前提 2: `mvv.md` は Markdown の宣言で、JSON Schema の対象にしない。文書には置き場・範囲・読む工程と、本文の形（節の並び）を載せる。JSON Schema を持つのは JSON の宣言（同時点で 18 種）である
- 前提 3: 副命令の一覧の正本は、ndf-next の副命令の表（`plugins/ndf-next/src/ndf/cli.py` の `COMMANDS`。2026-11-14 時点で 22 個）である。環境変数の正本は `contracts/domains/env.json`、hook の入出力の正本は `contracts/hooks/runtimes.json`、終了コードの正本は `contracts/facts/exit-codes.json`、止まった理由の正本は `contracts/causes.json`、結果の統一 JSON レポートの正本は `contracts/schemas/result.schema.json` である。新しいスキーマと文書はこれらと同じ事実を手で写さず、正本から生成するか正本を参照する
- 前提 4: 形まで規約に載せる受け渡しのファイルは、置き場の表で外の呼び手が読む行（列 `reader` を持つ行）と、エントリポイントの表（`contracts/domains/entrypoints.json`）の `files` が指す行である。そのほかの行（中継の内部のファイルなど）は内部の面として、規約では一覧の 1 行（置き場と「内部」）だけを持ち、形を約束しない。#3519 の範囲の追加が内部の面として名前を挙げたのは Skill と AI が打つ CLI であり、内部の受け渡しのファイルの形の文書化はこの課題に含めない
- 前提 5: 宣言を読む側の実行時の振る舞いは変えない。スキーマは CI の検査と連携システムの検証に使い、NDF の実行時に宣言をスキーマで検証して拒むことはしない（K #3367 の「実行時に `jsonschema` を読み毎回検証しない」に合わせる）
- 前提 6: 副命令の実際の出力をスキーマで確かめるテストは、K #3367 の「すべての副命令の標準出力と終了コードを確かめる 1 本のテスト」と同じテストにする。同じことを確かめるテストを 2 本にしない
- 前提 7: 文書とスキーマと検査の置き場は、ndf-next の中（`plugins/ndf-next/`）に置き、入れ替えの後は `plugins/ndf/` の同じ相対パスへ移る。置き場の確定は設計で行い、入れ替えの後の文書の行き先の表（`docs/ndf-swap-doc-destinations.md`）に行を足して記録する
- 前提 8: S #3390 の公開する面の表がこの課題の実装の時点でまだ無い場合は、エントリポイントの表と置き場の表の列 `reader`・`fields` を公開する面の表として扱い、そこへ行を足す。表の置き場が D2+ で別に決まれば、そこへ合わせる
- 前提 9: 配る Skill の一覧の正本は、ndf-next の配る Skill の表（`plugins/ndf-next/manifests/skills.json`。2026-11-14 時点で 49 行）である。#3519 が挙げた `manifests/claude-skills.txt`・`codex-skills.txt` は今の版（`plugins/ndf/`）のもので、ndf-next では配る Skill の表が置き換える。規約に載せるのは、表の行のうち `skills/<名前>/SKILL.md` の実体がある Skill（同時点で 11 個）である。実体の無い Skill は配らないため載せず、S1a #3303 で移った時点で検査が載っていないことを落とす
- 前提 10: Skill のうち公開する面は、エントリポイントの表（`contracts/domains/entrypoints.json`。同時点で 12 行）に載る Skill である。そのほかの Skill は内部の面とする
- 前提 11: 「AI が叩く CLI」は、ndf-next の利用者が打つ起動スクリプト（`plugins/ndf-next/bin/` の `ndf`・`ndf-claude`）である。`ndf` の副命令は規約の副命令の節が持ち、`ndf-claude` は引数をそのまま `claude` へ渡すため、規約には起動スクリプトの 1 行だけを載せる。`bin/start.py` と `hooks/` のスクリプトは起動スクリプトと hook の設定が起こす内部の部品で、AI が直接打たないため副命令としては載せない（hook の入出力は受け入れ条件 9 が持つ）
- 前提 12: 書かれた呼び出しの照合（受け入れ条件 17）の対象は、ndf-next の `skills/`（`SKILL.md` と references）と `agents/` の Markdown に書かれた `ndf <副命令>`・`bin/ndf <副命令>` の行である。2026-11-14 時点では `ndf hooks` の 1 件で、Skill の移行（S1a #3303）につれて増える

## 対象範囲

含む:
- ndf-next が読む `.ndf/` の宣言のすべて（前提 1）。ファイルごとに、置き場（worktree かメインディレクトリか）・範囲（チームか個人か）・キー・型・既定値・取りうる値・必須か・読む工程（どの工程・副命令がいつ読むか）・例
- JSON の宣言の全種の JSON Schema（`plugins/ndf-next/contracts/` の下）
- 外から呼ぶ 4 つの面の、ndf-next の 11.0.0 の全件
  - コマンド: 副命令ごとの引数、結果の統一 JSON レポート（1 行）の `metrics` と `items` の形、終了コードの意味、止まった理由（`causes`）
  - 環境変数: 呼び手が渡す値（`NDF_FACTORY_RUN` など）と NDF が読む値
  - 受け渡しのファイル: 前提 4 の行
  - hook: Claude Code・Codex から呼ばれる事象ごとの入力と出力
- 副命令ごとの引数と結果の JSON Schema
- 配る Skill（前提 9）ごとの、引数の形・`/goal` の終わりの条件・読む宣言と環境変数・結果（応答の末尾のブロックや区間の報告）と、公開か内部か（前提 10）
- Skill の本文・references・エージェント定義に書かれた `ndf <副命令>` の呼び出しと、規約の副命令・引数の形との照合（前提 12）
- 起動スクリプト（前提 11）の一覧
- 公開する面と内部の面の区別と、S #3390 の公開する面の表との整合
- スキーマから文書を生成する仕組みと、コードにあって文書に無いものを落とす検査を 1 つの仕組みとして作り、CI で打つ
- 入れ替えの後の文書の行き先の表への行の追加

含まない:
- 今の `plugins/ndf/`（10.27.x）の宣言と規約の文書化、今の版との差の表
- 設定ページそのもの（連携システムの側で作る）
- OpenAPI と HTTP の API の新設（連携システムが HTTP で包むなら、その OpenAPI からこのスキーマを参照する）
- NDF の実行時に宣言をスキーマで検証すること（前提 5）
- 宣言・副命令・環境変数の追加・改名・削除（ndf-next の各子の担当。この課題は今ある形を書き表す）
- Skill の ndf-next への移行と、Skill の本文の書き換え（S1a #3303 の担当。照合で落ちた呼び出しは、その Skill を移す子が直す）
- 内部の受け渡しのファイルの形の文書化（前提 4）
