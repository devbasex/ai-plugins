## 目的

並列の計画を続けるのに要る状態を、計画と同じ寿命で持つ。達成したい状態は次のとおりである。

耐久ワークフローの作り直し・耐久の記録の消失・セッションの交代・プラグインの更新のどれが起きても、受けたリリースの依頼・答えていない問い・送った答え・オーガナイザーの役割が失われず、オーガナイザーが `parallel.py start <計画名>` を 1 回打てば計画が続く。carul の計画 l20261104 では、この状態が失われて 2 時間あまりどのレーンも進まなかった（#2617）。

## 前提

- 前提 1: 計画の台帳の置き場は、メインディレクトリの `.ndf/parallel/<計画名>/` とする。ここは `plan.json`・`run.log` を既に置いている計画の置き場で、devbase では残る volume の上にある（#2606 の実測の表）。残らない環境の扱いは #2606 が受け持つ
- 前提 2: 耐久の記録の置き場（`~/.local/state/ndf/dbos`）は動かさない。コンテナの再起動で消えても、台帳から作り直す（受け入れ条件 2）
- 前提 3: 1 つの計画の `run` は同時に 1 本で、レーンとオーガナイザーは同じメインディレクトリを読み書きする。別のコンテナで同じ計画の `run` を同時に動かす形は扱わない
- 前提 4: 外のオーガナイザーのレーンと Factory のランナーでは計画の台帳を使わない（`parallel.py` の `run`・`start` は Factory の実行の中で動かない。状態はサーバー側の DB で持つ。#2608）
- 前提 5: #2583 の置き場が消えた原因の確定は求めない。別のコンテナの片付け・同じコンテナの片付けのどちらで消えても、受け入れ条件 17・18 が成り立てばよい
- 前提 6: #2584 の原因は確定できていない（carul の記録を読めない）。版の違いによる形の違いがあっても `wait` が件数と id を出せること（受け入れ条件 12）を求め、原因の確定は求めない

**今の振る舞いの確認（2026-11-07 JST、コミット 9f40de6a5）。**

| 確かめたこと | 手段 | 結果 |
| --- | --- | --- |
| ERROR の耐久ワークフローは `run_plan` の経路では続けられない | `durable.launch` → 例外を上げる耐久ワークフロー → `output_of` を 2 回、開き直して `status` | 2 回とも同じ `ModuleNotFoundError`。開き直しても `ERROR` のまま |
| ERROR の耐久ワークフローへの送信は成功する | 同じ記録へ `durable.send_to` | 例外なく返る。受け手が居なくても送り手には分からない |
| 途中の記録は新しいコードで続く | `pytest plugins/ndf/scripts/tests/test_parallel_run.py -k recorded_run_of_the_old_steps` | 通過（受け入れ条件 19 の前提） |
| 即時修正の 3 か所が動く | `pytest plugins/ndf/scripts/tests -k "unknown_id or start_on_a_running or inuse"` | 3 件通過 |

## 用語

| 用語 | 意味 |
| --- | --- |
| 計画の台帳 | 1 つの並列の計画を続けるのに要る状態（受けた依頼・問い・答え・リリースの連番と状態・レーンの起動の記録・オーガナイザーの役割・使う版）を、計画の置き場へ追記した記録 |

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | 耐久ワークフローが失われた計画の復旧の操作は `parallel.py start` の 1 回である。台帳と耐久の記録を手で編集しない |
| 性能・拡張性 | 依頼 1,000 行の台帳を読む `start` の復元が 1 秒以内に収まる（計測はテストで行う）。耐久ワークフローの観測の 1 回に足す秒は 1 秒以内 |
| 運用・保守性 | 作り直しの回数・戻した依頼と問いの件数・外した行数を `run.log` と `start` の結果に残す。認証情報を台帳へ書かない |
| 移行性 | 台帳の無い計画はそのまま動く。切り戻しは前の版へ戻すだけで、台帳は読まれなくなる。動いている計画を止める手順は要らない |
| システム環境 | レーンとオーガナイザーが同時に追記しても行が混ざらない。Linux の同じファイルシステムの上での動作を保証する |

## 束 A（軸 2）: 計画の状態が、計画より短命な入れ物にしか無い

**根本原因。** 並列の計画が続くために要る状態（受けた依頼・答えていない問い・送った答え・オーガナイザーの印・使う中継の版）が、
耐久ワークフローのメモリ（`_Run.pending`・`_Run.questions`）、コンテナの再起動で消える `~/.local/state/ndf/dbos/`、
ラッパーのプロセス（pid）、版ごとのラッパーの置き場に結び付いている。そのどれかが作り直される（ERROR からの作り直し・
セッションの交代・プラグインの更新・コンテナの再起動）と、計画は生きているのに状態だけが消える。

**場所。**

| 何が消える | 場所 |
| --- | --- |
| ERROR になった耐久ワークフローを続ける手段が無く、作り直すしかない（作り直すと依頼と問いを引き継がない） | `plugins/ndf/scripts/lib/parallel_run.py:757-765`（`run_plan`: status が None のときだけ start、ほかは `output_of`） |
| 依頼と問いは耐久ワークフローの中にしか無い | `plugins/ndf/scripts/lib/parallel_run.py:323-357`（`take`・`receive_question`） |
| 一覧に無い依頼への答えを黙って捨てる | `plugins/ndf/scripts/lib/parallel_run.py:359-363`（`reply` の `return`） |
| 送る側は受け手が生きて受け取ったかを確かめない（DBOSClient の send は終わった・別の記録の wid にも成功する） | `plugins/ndf/scripts/lib/durable.py:395-398`・`plugins/ndf/scripts/lib/parallel_lane.py:217-232,293-302` |
| 耐久の記録の置き場がコンテナの overlay | `plugins/ndf/scripts/lib/durable.py:19`（`~/.local/state/ndf/dbos`） |
| オーガナイザーの印は耐久ワークフローの最初のステップで 1 回だけ、起動したラッパーに付く | `plugins/ndf/scripts/lib/parallel_run.py:106-112`（`step_init`）・`plugins/ndf/scripts/parallel.py:170-180`（`cmd_start` は run が動いていれば何もせず返る） |
| 数えの除外が印に依る | `plugins/ndf/scripts/relay_lib/hub.py:244-254` |
| 版の置き場の「使用中」を pid だけで見る。置き場 `~/.claude/ndf/` は `/persistent/group` の共有の volume で、別のコンテナの pid は死んで見える | `plugins/ndf/scripts/relay_lib/version_dir.py:204-241`（`prune`・`_in_use`）・`:109-110`（`_alive`） |
| 統括役は自分の `sys.executable`（起動した版の venv の python）でレーンを起こす | `plugins/ndf/scripts/relay_lib/hub.py:434-449`（`launch`） |

#2583 の置き場が消えた理由は推定である（このコンテナには carul の tmux のセッションも統括役の登録も無く、
`/persistent/group/.claude/ndf/` には 10.27.24〜26 の置き場だけが残る。carul の統括役は別のコンテナで動き、
こちらのコンテナの更新の `prune` が pid の生死で carul の 10.27.16 を使っていないと読んだ形が最も合う）。

**束に入る課題。** #2617・#2584・#2583・#2637。関連: #2563（起動の確かめ）・#2595（オーガナイザーのセッションの交代）。

**直せば消える理由。** 計画の台帳（依頼・問い・答え・役割・使う版）を、計画の置き場（`.ndf/parallel/<計画>/`、残る volume）に
追記型で持ち、耐久ワークフローは始まるたびに台帳から組み直す（作り直し＝回復になる）。

- #2617: 作り直しても台帳から保留の依頼と問いが戻る。未知の id への答えは台帳に積まれ、後で当たる
- #2584: 送り手が台帳へ書いてから知らせるので、受け手の版や記録の作り直しに依らず `wait` が台帳の未答の行を出せる
- #2637: 役割を計画（台帳）が持ち、`start` を打ったセッションへ付け直す
- #2583: 使う版を台帳とラッパーの持ち主（ホストまたはコンテナの識別＋pid、#2342 の lease）で持てば、別のコンテナの片付けが消さない

**直しても残るもの。**
- #2563・#2583 の受け入れ条件 2（起動したセッションが残っているかを確かめて失敗を返す）は束 C の起動側の確かめ（`hub.py:434-449`）
- #2584 の原因は記録を読めず確定できていない。台帳化で症状は消えるが、版をまたぐ送り手と受け手の形の違いがあれば別に残る
- ERROR そのものを防ぐのは束 D（#2509 の環境の漏れ）

**既存の柱との重なり。** #2342（持ち主と後片付けを lease で。マイルストーン 30）・#2335 の S7（再開の手段を耐久の記録 1 つに）・
#2606（置き場を寿命で分け、残る volume に置く）・#2600（`.ndf/` の置き場と持ち主をスクリプトで固定）・#2594（コンテナの再起動で消える）・
#2608（Factory は状態をサーバー側の DB で）。**台帳を `.ndf/parallel/<計画>/` に置く決め方は #2606 の「実行の間」の寿命そのもの**で、
#2606 の設計の中で決めると二重にならない。
