## 目的

- 人が任せた AI のエージェントや連携するシステムが、画面と同じ操作を、画面と同じ認可と記録のもとで行える状態にする
- API の入出力を画面の 1 枚から切り離し、機能（エンティティと操作）単位の配列の形へそろえる。画面・API・MCP が同じユースケースを通る
- 承認ゲートの承認と、人の承認が要る操作の確定を、委任の経路から行えないことを仕組みで保証する
- だれの委任で、どのエージェントが、いつ何をしたかを後から確かめられる記録を残す

## 前提

- 前提 1: 「画面で行える操作」は、画面の API クライアント（`factory/web/src/api.ts` の `Api`）が呼ぶ操作の全体と、承認と通知（#2173）が足す Web からの承認の操作を指す。2026-11-04 の時点で `Api` は 31 の操作を持つ（`request(` の呼び出し 31 件）
- 前提 2: 配列の規則と MCP のツールの対象は、利用者（人か、人の委任を受けたエージェント）が呼ぶ操作である。ランナー向けの経路（`/run-jobs/*`・`/ingest/events`・`/ingest/api/events`）と GitHub の Webhook（`/ingest/github`）は対象に含めない（S7）
- 前提 3: 1 回の要求で受け渡す配列の要素は 100 個までとする。値は設計で実測を見て変えてよいが、上限を超えた要求は処理せずに 400 と上限値を返す、という振る舞いは変えない
- 前提 4: 委任の資格情報の期限は 1 時間以内とする。範囲は「読み取りだけ」と「読み書き」の少なくとも 2 つを選べる。値と範囲の分け方は設計で決める
- 前提 5: GitHub App の導入とリポジトリへの認可は、人がブラウザで GitHub の画面を操作する流れである。MCP からは導入と認可の URL を返すところまでを行い、GitHub の画面の操作は人が行う
- 前提 6: 委任の資格情報の発行と取り消しは、人が画面で行う。委任の資格情報で委任の資格情報を発行できない
- 前提 7: 既存の契約（`factory/contracts/openapi/` の 5 ファイル）の経路を配列の形へ変える。画面と API は同じリポジトリで同時に変わり、外部の利用者はまだいないため、旧い形との互換の経路は持たない
- 前提 8: 操作の記録を置く表の定義は、インフラ（private リポジトリ）が作る。このリポジトリは保存の契約（interface）と、メモリの実装・本物の実装を持つ

## 対象範囲

含む:

- 契約（`factory/contracts/openapi/`）の利用者向けの操作を、機能（エンティティと操作）単位の配列の入出力へ起こし直すこと
- 画面の API クライアントと、ダミーの API クライアントを新しい契約の形へ合わせること
- MCP のサーバー（API と同じユースケースを呼ぶ）と、契約の操作と MCP のツールの対応表
- 委任の資格情報の発行・検証・取り消しと、それを発行・取り消す画面
- 人だけが確定できる操作の印と、その印のある操作を委任の資格情報から断る共通の処理
- 操作の記録（追記だけ）の保存の契約・実装と、すべての利用者向けの操作からの書き込み
- 画面の操作・契約・MCP の対応と、単一のレコードの受け渡しが無いことを確かめる検査

含まない:

- ランナー向けの経路と GitHub の Webhook の形（前提 2）
- Web からの承認の操作そのもの（#2173 が作る）。この課題は、その操作に人だけが確定できる印が付き、委任の資格情報から断られる仕組みを用意する
- 操作の記録を読む画面と、記録の検索の機能
- 操作の記録の保存期間と、国ごとの法令（GDPR など）に応じた削除の手続き（未決 2）
- 外部の利用者向けの公開の手続き（MCP のサーバーの一覧への掲載など）
- インフラの定義（表・Lambda・API Gateway）

## 用語

| 用語 | 意味 |
| --- | --- |
| 委任の資格情報 | 人が画面で発行し、エージェントかクライアントに渡す、期限と範囲つきの資格情報。だれの委任か（利用者）と、どのクライアントか（人が付けた名前と識別子）を持つ。人が取り消せる |
| 人だけが確定できる操作 | 承認ゲートの承認・判断の依頼への答えと、共通原則の C1〜C8・プロジェクト MVV の P に当たる Factory の操作。契約に印を持ち、委任の資格情報からは断る |
| 操作の記録 | 利用者向けの操作 1 回ごとに 1 件追記する記録。書き換えと削除の経路を持たない |
| 呼び出し元の種類 | 操作の記録に残す、操作がどこから来たかの区分。画面・API・MCP の 3 つ |
| 機能から起こした契約 | 経路と入出力を、画面の 1 枚でなくエンティティと操作から決めた契約。取得・作成・更新・削除とも配列で受け渡す |

## 受け入れ条件

対応と形:

- [ ] 1. 画面の API クライアントが呼ぶ操作がすべて契約（`factory/contracts/openapi/`）の `operationId` に対応することを、検査（`npm run check` の一部）が確かめる。対応しない操作が 1 つでもあると検査が落ちる
- [ ] 2. 契約の利用者向けの操作がすべて MCP のツールに対応し、MCP のツールがすべて契約の操作に対応することを、検査が確かめる。片方にしか無い操作かツールが 1 つでもあると検査が落ちる
- [ ] 3. MCP のツールは、API の経路と同じユースケースの関数を呼ぶ。MCP のツールから、契約に無い保存の操作を呼べないことをテストで確かめる
- [ ] 4. 契約の利用者向けの操作で、要求の本文か応答の本文が配列でない操作が無いことを、検査が確かめる（1 件の取得・作成・更新・削除も要素 1 個の配列で受け渡す）
- [ ] 5. 経路の変数で単一のレコードを指す取得（`/sprint-runs/{sprintRunId}` の形）が、利用者向けの操作の契約に無いことを、検査が確かめる

配列の受け渡し:

- [ ] 6. 101 個の要素を送ると、どの要素も処理されずに 400 が返り、応答に上限の値 100 が入る
- [ ] 7. 3 個の要素のうち 1 個だけに認可が無いとき、応答は入力と同じ順に 3 個の結果を返し、認可の無い 1 個だけに理由（`forbidden`）が付き、残り 2 個は処理される
- [ ] 8. 0 個の要素を送ると、何も処理されずに 400 が返る
- [ ] 9. 作成の要素に同じ冪等の鍵を付けて 2 回送ると、レコードは 1 件だけでき、2 回目の応答は 1 回目と同じ識別子を返す

委任の認証:

- [ ] 10. 人のログインの token で呼んだ操作と、同じ人が発行した委任の資格情報で呼んだ同じ操作は、同じ認可の判定になる（人に許された操作は委任でも許され、人に断られる操作は委任でも断られる）
- [ ] 11. 期限を過ぎた委任の資格情報で呼ぶと 401 になり、操作は行われない
- [ ] 12. 取り消した委任の資格情報で、取り消しの後に呼んだ最初の要求が 401 になる
- [ ] 13. 「読み取りだけ」の範囲の委任の資格情報で作成・更新・削除の操作を呼ぶと 403 になり、操作は行われない
- [ ] 14. 委任の資格情報で委任の資格情報の発行を呼ぶと 403 になる（前提 6）
- [ ] 15. 認可は要素ごとに掛かる。他人のアカウントの要素を混ぜた配列で、他人の要素だけが断られ、応答に他人のデータが含まれない

人だけが確定できる操作:

- [ ] 16. 契約で、人だけが確定できる操作に印が付いている。ループの判断待ちへの答え（`answerLoopPending`）には印がある
- [ ] 17. 印のある操作を委任の資格情報で呼ぶと、範囲が「読み書き」でも 403 になり、答えも状態も保存されない。印のある操作をすべて委任の資格情報で呼ぶテストがある（S6 の操作を含む）
- [ ] 18. 委任の資格情報で、承認の依頼とその材料（スプリントの詳細・承認待ちの一覧）は読める

操作の記録:

- [ ] 19. 利用者向けの操作 1 回ごとに、操作の記録が 1 件増える。記録は、操作した利用者の ID・委任の資格情報の識別子（人の直の操作では空）・日時（UTC）・呼び出し元の種類（画面・API・MCP）・`operationId`・対象の ID の配列・結果（成功・一部失敗・断った理由）を持つ
- [ ] 20. 読み取りの操作と、401・403・400 で断った操作も記録に残る
- [ ] 21. 操作の記録の保存の契約に、書き換えと削除の関数が無い。テストが契約の関数の一覧を確かめる
- [ ] 22. モデルの認証情報（API キー・ロールの ARN）・ログインの token・委任の資格情報の値・GitHub の token を含む要求を送っても、記録にそれらの値が入らないことをテストで確かめる
- [ ] 23. 記録に、メールアドレス・氏名・チームの名前・課題の題と本文が入らない

退行しないこと:

- [ ] 24. 契約の形を変えた後も、画面の既存の画面テスト（`factory/web` の Vitest と Playwright）が通る
- [ ] 25. ランナー向けの経路（`/run-jobs/*`・`/ingest/*`）の入出力が変わらない（前提 2）
- [ ] 26. 委任の資格情報を使わない人の操作で、今と同じく 401（token の検証の失敗）と 403（アカウントの解決の失敗）が返る
      前提の確認: `factory/api/src/auth/verify.test.ts` と `factory/api/src/handlers/api.test.ts` が今の 401・403 を確かめている（実装の前に `npm run check` で通ることを確かめる）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 配列の要素は 1 回の要求で 100 個まで。超えたら 400 と上限値を返す（前提 3）。画面は今と同じ回数以下の要求で同じ画面を描ける（今は詳細を要素の数だけ別々に取っている。`factory/web/src/api.ts` の `sprintRunDetails`・`stepDetails`・`backlogs`） |
| 運用・保守性 | 1 つの操作を、操作の記録の 1 件と、その操作の要求の識別子でたどれる。秘密と個人情報の値は記録に書かない（受け入れ条件 22・23） |
| 移行性 | 旧い形の経路との並走は持たない（前提 7）。画面と API は同じ Pull Request の系列で同時に切り替える |
| セキュリティ | 委任の資格情報は期限 1 時間以内で、取り消しの後の最初の要求から断る。委任の資格情報の値は保存の時点でハッシュにし、平文で持たない。人だけが確定できる操作は委任から断る |
| システム環境 | MCP のサーバーは `factory/api/` と同じ Node 24 の上で動き、新しい実行基盤を足さない。足す場合は理由と代わりの案を設計に書く（スプリント Value 6） |

| 手動確認 | リリース後に、人が手元の Claude Code に Factory の MCP のサーバーを登録し、委任の資格情報でスプリントの一覧を読めることと、承認の依頼に答えようとすると断られることを見る |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | 変更は `factory/` の中に置く。`plugins/` と `.claude-plugin/marketplace.json` は `factory/` を参照しない（`python3 scripts/check-service-boundary.py`）。インフラの定義と秘密は private リポジトリに置く（`AGENTS.md` の「マーケットプレイスの構造」） |
| コーディング規約 | `factory/` の TypeScript の規約と `npm run check`（`docs/specifications/ndf-factory-accounts-and-plans.md` の「パッケージの管理」）。契約の正は OpenAPI で、型は生成する（`docs/specifications/ndf-factory-contracts-and-progress.md`） |
| テスト戦略 | 契約と対応の検査は `factory/contracts/tests/`、委任・認可・記録の振る舞いは `factory/api/` の Hono の `app.request()` を使うテスト、画面は既存の Vitest と Playwright |

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | `npm run check` の実行、契約からの型の生成、変更する経路のテストの追加 |
| 確認してから行う | 依存パッケージの追加（MCP の SDK など）、契約の経路の名前の変更、記録の項目の追加。いずれも承認ゲート 1・2 で人が見る |
| 行わない | ランナー向けの経路の形の変更、インフラの定義の追加、`plugins/` から `factory/` への参照、操作の記録への秘密と個人情報の値の書き込み |
