## 何が起きたか

#4059（エージェントが NDF を通さずに打つ `gh` の書き込みにもマシン全体の間隔を当てる）の詳細設計 [issue-4059-design-detail.md](./issue-4059-design-detail.md) を、PR #4170（#4110 の設計）の cross-review の相手役がラウンド 1 で読んだ。書かれたとおりに実装すると、普通の `gh` の呼び出しが壊れるか、共有の停止を誤って書く箇所が 4 つある（r1-1〜r1-4）。

設計の前に手元の `gh` 2.103.3 で 4 点を確かめた（設計の「外部の調査」の STD1〜STD4）。4 点とも起票のとおりで、うち 2 点は起票より広い範囲に当たる。

| # | 起票の場所 | 起票の事象 | 実測で分かった広がり |
| --- | --- | --- | --- |
| 1 | 詳細設計 86 行（`run_child` の副作用） | Python の `subprocess.Popen` は既定で標準入出力以外のファイル記述子を閉じる（`close_fds=True`）。Bash のプロセス置換 `<(…)` のパス（`/dev/fd/63`）を `--input`・`-F query=@…` に渡すと、本物の `gh` が開けない | `gh pr comment --body-file <(…)` も同じく `open /dev/fd/63: no such file or directory` で失敗する。`--input` と `-F` だけでなく、ファイルを読むすべてのフラグに当たる |
| 2 | 同 118 行（`--silent` を外す条件） | 条件がフラグの出現だけで決まるので、`--silent=false` や `--silent --silent=false` の呼び出しまで本文を隠す | 出現で読むブール値のフラグはほかにもある。`gh api … --help=false` は本物の `gh` では要求を送るが、詳細設計の (b) では読み取りに分けうる（書き込みが順番の外へ出る）。`gh release create --draft=false` は公開の更新を送るが、件数の式は `--draft` の出現で 1 件少なく数える |
| 3 | 同 133 行（`mutation_kind`） | GraphQL の最上位のフィールドは種類の判定にしか使われず、複数の mutation のフィールドを含む要求も 1 件と数える | 起票のとおり。GitHub は 1 つの要求の最上位の mutation のフィールドを 1 つずつ実行する |
| 4 | 同 75 行（`limit_seen`） | 終了コードが 0 なら照らさない契約だが、シグネチャに終了コードが無い | 起票のとおり。成功した `gh`（終了コード 0）も、`GH_DEBUG=api` を付ければ応答の本文を標準エラーへ出す |

## 種類

不具合（設計文書が、誤動作する実装を導く。コードは #4059 の実装の前で、壊れたものはまだ配られていない）

## 今の姿

#4059 の設計 PR（#4115）はマージ済みで、実装は #4016（`WriteGate`）の実装の後に同じレーンで行う。`bin/gh` と `gh_gate` はまだ無い。

## 何を変えるか

| | 前（#4059 の詳細設計） | 後 |
| --- | --- | --- |
| 本物の `gh` の起動 | 包みが受け継いだファイル記述子を、標準入出力以外は閉じて起動する | 包みが受け継いだ記述子を、`gh` を直に打ったときと同じく本物へ継ぐ |
| ブール値のフラグ | 出現したかで読む | pflag と同じく、最後の指定の値（`--x`・`--x=<真偽>`）で読む |
| 文字列のフラグ（`--jq`・`--template`） | 出現したかで読む | 最後の指定の値で読み、空の値は指定なしとする |
| GraphQL の書き込みの件数 | 1 件 | 実行される mutation の最上位のフィールドの数（同じ応答のキーは 1 件） |
| 二次レート制限の見分け | 終了コードを受け取らない | 終了コードを受け取り、0 なら照らさない |

## 今の利用者への影響と互換

利用者への影響は無い。`gh_gate` はまだ配られていない。直した後の振る舞いは「`gh` を直に打ったときと同じ」に近づくだけで、#4059 の要求（受け入れ条件 4「引数・標準入力・標準出力・標準エラー・終了コードは `gh` を直に打ったときと同じ」）を変えない。

## なぜ困るか

- 1 のまま実装すると、エージェントがプロセス置換で本文や GraphQL の文書を渡す `gh` の書き込みが、包みを通るときだけ失敗する
- 2 のまま実装すると、`--silent=false` を付けて JSON を後ろの処理へ渡す呼び出しの出力が消える。`--help=false` の書き込みは順番の外で送られ、`--draft=false` のリリースは間隔が 1 件分足りない
- 3 のまま実装すると、1 つの要求で複数の mutation を送る `gh api graphql` が 1 件分の間隔しか空けず、#4059 の決定 7（1 回の `gh` が出す書き込みの件数の分だけ間隔を空ける）を破る
- 4 のまま実装すると、成功した `gh` の標準エラーに二次レート制限の語があるだけで、全レーンの書き込みを止めうる

## 目的

- `gh_gate` が本物の `gh` を走らせるとき、引数・ファイル記述子・フラグの値を本物の `gh` と同じに扱う
- 1 回の `gh` が出す GraphQL の書き込みを、実行されるフィールドの数で数える
- 共有の停止は、失敗した `gh` の出力からだけ書く
- 誰に効くか: #4059 を実装する人と、NDF のリレーが起動したセッションで `gh` を打つエージェント
