# 計画の台帳の設計の決定（#2647）

設計文書 [issue-2647-design.md](issue-2647-design.md) の決定の記録である。要求の未決の 4 点は決定 1・3・4・11 が答える。

## 決定の記録

### 決定 1: どの変更点でも戻せるよう、受けた行の追記と耐久ワークフローのチェックポイントの 2 ファイルに分ける

外から届いた行は事象として追記し、耐久ワークフローが自分で導いた状態（答えた依頼・リリースの状態・起動したレーン・自分で立てた問い）はチェックポイントへ全体を書く。状態を変える箇所は `_Run` と `ReleaseRouting` に数十か所ある。箇所ごとに行を足す形は書き忘れがそのまま状態の欠けになるが、ループの 1 周の終わりに全体を書く形は箇所の数に依らない。戻す処理も、同じ `take` と `resume` を残りの行へ流すだけで済む。

チェックポイントは上書きである。過去を失ってよいのは、外から届いた事実が台帳に残り、失うのが導いた値の古い時点だけだからである。無くても全行から依頼・問い・答えが戻る。起票者の推定 S2（追記型で持つ）のうち、この点だけ追記にしない。

| 採らなかった形 | 理由 |
| --- | --- |
| チェックポイントを台帳の行として足す | 1 行が状態の全体になる。答えが増えるほど台帳が 2 乗で伸び、1,000 行の復元の条件に当たる |
| 種類ごとにファイルを分ける | 行の順序が状態の順序であり、分けると順序が失われる |
| SQLite | 受け入れ条件 8 の行の単位の扱いと合わない |

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1 / STD3 / PRD3 / LIB3 / LIB4 / LIB5

根拠: Value 7 / Value 2（MVV 版 6）

### 決定 2: 同時の追記で行が混ざらないよう、既存の `locks` の排他の中で追記する

排他の中で重複のキーと末尾の改行を確かめる処理が要るため、`O_APPEND` だけでは足りない。POSIX は `PIPE_BUF` を超える書き込みが割り込まれないかを定めておらず、行の長さには上限が無い。同じ部品が統括役の記録でも動いており、4 プロセスの実測で壊れた行は 0 だった。重複の確かめは全行の読み出しになるが、1,000 行で 0.0035 秒である。

- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB2 / STD2

根拠: Value 7（MVV 版 6）

### 決定 3: 入力の経路を 1 つにするため、耐久ワークフローは台帳の行だけを受け取り、トピック `inbox`・`resume` は起こす知らせとして残す

送り手は台帳へ書いてから知らせる。受け手は `recv` の後にループの 1 周ごとに台帳を読む。経路が 1 つなら、知らせの失敗も受け手の作り直しも同じ処理で済み、受け入れ条件 11 に特別な経路が要らない。

トピックのメッセージは本体を持ったまま残す。動いている古い版の耐久ワークフローが新しいレーンの依頼を受けるためである。逆向き（古い版のレーンのメッセージ）は、読むステップが台帳へ足してから読む。

| 採らなかった形 | 理由 |
| --- | --- |
| トピックを外して観測の間隔だけで読む | 既定の 60 秒の待ちが依頼のたびに入る |
| メッセージと台帳の両方を受けて id で重ねを除く | 受け取りの経路が 2 つ残り、片方にだけ当たる不具合が起きる |

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD4 / LIB1

根拠: Value 7（MVV 版 6）

### 決定 4: 読み手の固定の ID を変えないため、耐久の記録を退避して同じ ID で新しく始める

耐久ワークフローの ID は `workflow_id(name)` として 16 か所の呼び出しが使う。退避なら読み手は 1 行も変わらず、記録が消えた計画と同じ道を通る。作り直しの経路が 1 つになる。

退避は `launch` の排他の中で行い、2 つの `start` が重なっても 1 回で済む。`launch` に判定の引数 `retire_if` を足し、結果 `Launched` へ退避先を足す。退避したファイルは `<実行の鍵>.sqlite.retired-<時刻>` とし、`purge_old` が記録と同じ 30 日で消す。

| 採らなかった形 | 理由 |
| --- | --- |
| 実行の回を足す（`parallel-<計画名>-<回>`） | 読み手のすべてが今の回を解決する処理を持つことになり、回を持たない途中の記録との分岐も要る |
| DBOS の fork | 新しい ID を作るため、同じ理由で合わない |
| DBOS の resume | 実測で ERROR のままだった。例外がステップの結果として記録に残り、流し直しても同じ例外になる |

- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB1 / PRD1 / PRD2

根拠: Value 7 / Value 6（MVV 版 6）

### 決定 5: `wait --after` が知らせを取りこぼさないよう、作り直しの回数から `seq` の基準を決める

`seq` の基準は `rebuilt` の行の数 × 1,000,000 とする。チェックポイントの `seq` を読む形は採らない。ループの 1 周の途中で立てたイベントはチェックポイントより先へ進むことがあり、チェックポイントが無いときは基準が 0 に戻る。`seq` は問いと知らせを立てるたびに 1 増えるだけで、1 秒に 1 回立てても 100 万に届くまで 11 日かかる。

根拠: Value 7（MVV 版 6）

### 決定 6: 復元を 1 秒以内に収めるため、答えのイベントを立て直さず、読み手がチェックポイントを読む

`read_answer`・`answers_of`・`released_version` は耐久の記録を読み、無ければチェックポイントの `published` を読む。`set_event` は実測で 1 回 11 ms あまりで、1,000 件で 11.1 秒かかる。読み手の側なら件数に依らず、ERROR の間にも読める。

全件を立て直す形は採らない。非機能の条件を満たさない。古い版の読み手が作り直しの前の答えを読めない点は残る（未確認のまま残ること）。

根拠: Value 7（MVV 版 6）

### 決定 7: 動いている計画を止めないよう、耐久ワークフローの先頭の `patched` で途中の記録を今までの道へ通す

先頭で 1 度だけ判定し、結果を `_Run.ledgered` に持つ。途中の記録は台帳を読まず、チェックポイントも書かない。実測で、先頭の `patched` は途中の記録で False を返し、記録の順を崩さなかった。形式の版を上げる形は採らない。途中の耐久ワークフローを続けられなくなる。

- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB1

根拠: Value 1 / Value 7（MVV 版 6）

### 決定 8: ERROR の間も依頼と答えを失わないよう、失われた計画を受け付ける

要求の境界が設計承認ゲートで人が見るとした公開インタフェースの変更である。`accepts` は動いている計画と失われた計画を受ける。閉じた計画を区別するため、計画の終わりに `closed` の行を書く。受け付けを広げると放棄した計画もレーンを受けるため、`lane_of` は動いている計画を先に探し、放棄は `stop` で閉じる。

根拠: Value 2（MVV 版 6）

### 決定 9: 使い回された pid を動いていると読まないよう、起動の引数で `run` を確かめる

`live_run_pid` は `os.kill(pid, 0)` の後に `procs.cmdline_contains(pid, "parallel.py run <計画名>")` を見る。False なら動いていない。None（読めない）は今どおり動いていると読み、二重起動を避ける。二重に起動しても `launch` の排他が止める。持ち主の記録（#2342）を待たず、要求のとおり受け入れ条件 15 の範囲だけを直す。

根拠: Value 7（MVV 版 6）

### 決定 10: 統括役の置き場が消えてもレーンを起こすよう、起動の直前に python の有無を確かめて `relay.current` の仮想環境へ切り替える

`Hub.launch` の `sys.executable` だけが消える。`launcher_path()` はバージョンディレクトリの親の `relay.py` を指し、残る。起こす python を `version_dir` の関数が返し、切り替えたときは `hub-log.jsonl` へ `version-switched` の 1 行を足す。統括役の使う版を台帳へ移す形（起票者の推定 S6）は採らない。統括役は計画を知らない層であり、持ち主を増やす。起票者の推定 S12（統括役が今の版でレーンを起こす）のとおりである。

根拠: Value 7（MVV 版 6）

### 決定 11: 1 回のレビューで読み切れるよう、実装の Pull Request を 3 本に分ける

版の置き場（受け入れ条件 17・18）は `relay_lib` だけを触り、台帳に依らない。役割の引き継ぎ（15・16）も台帳の核に依らない。この 2 本を先に出すと、それぞれ単独で carul の症状を消し、単独で戻せる。要求の未決「2 条件を別の Pull Request に分けるか」（Value 2）への答えである。設計は 1 本のまま、実装の順だけを分ける。

根拠: Value 2 / Value 1（MVV 版 6）

### 決定 12: 行数の例外を増やさないよう、観測と CLI の本体を別のモジュールへ移す

`parallel_run.py` は例外の 721 行が上限で、`parallel.py` は 500 行ちょうどである。例外の項目が示す分け方に従い、観測の関数を `parallel_observe.py` へ移す。耐久ステップの名前は変えないため、途中の記録の流し直しに影響しない。`parallel.py` は `cmd_start`・`cmd_wait` の本体を `parallel_cli.py` へ移す。`build_parser` を移す形は採らない。`check-ndf-contracts.py` が引数を静的に読むため、契約の検査が `args-unparsed` で落ちる。

根拠: Value 5（MVV 版 6）
