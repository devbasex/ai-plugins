# #3119: ブランチ運用: スプリントブランチを main から切り、承認したスプリントだけをリリースブランチで main へ届ける

正は課題の本文（#3119）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 種類

運用

## 目的

- **今どうなっているか**: スプリントブランチ（`sprint/<名前>`）はベースブランチ（`develop`）から切り、検査の後にベースブランチへマージする。設計 PR・確定仕様化の PR・開発版の版上げもベースブランチへ入る。リリースはベースブランチを丸ごと本番チャネル（`main`）へ入れる（`release/v<版>` の先頭はベースブランチの祖先）
- **困っていること**: 並列の計画で複数のレーンが同時にベースブランチへ入れると、リリースにはベースブランチにあるものがすべて載る。承認したスプリントだけを出せない。2026-11-12 の計画 p5 では、リリース 9 に計画の外のスプリント aixrepo-1（#3074、PR #3078・#3094・#3095）が入った。範囲が提示の時点のベースブランチ全体で決まるため、開いたまま置いたリリース 10 は版と比べる元が組んだ時点のまま残り、差し戻した（#3085）
- **変えると何が成り立つか**: スプリントごとの変更だけを、承認した単位で本番チャネルへ届けられる。ベースブランチは開発版のデプロイと結合を試す場になり、本番へは流れない。あわせて、PR の種類ごとに何をレビューするかが 1 つの宣言で決まり、同じ差分を 2 度レビューすることも、どこでもレビューされない差分も生じない

## 方針（利用者の指示、2026-11-12）

- **この運用を ai-plugins のルールとする（決定）**
- **NDF の制約にはせず、このリポジトリのルールとして実現する。** ブランチルールはリポジトリの事情によって決まり、NDF はどんなルールでも対応できるように設計する。NDF の側の一般化（ブランチ運用をリポジトリの宣言で受ける）は #3121 が持ち、この Issue はその宣言の値と、リポジトリの側の決まりの文書を持つ
- **レビューをどの単位で行うかのルールも、この運用に含める**（利用者 2026-11-12 追記）。ブランチが「実装 PR → スプリントブランチ → ベースブランチ / リリースブランチ → 本番チャネル」と分かれるため、どの PR で何をレビューするかを決めないと、同じ差分を何度もレビューするか、どこでもレビューしない差分が出る
- **ブランチの流れとレビューの単位は 1 つの宣言（`branch_flow`）に書く**（利用者 2026-11-12）。#3163 を先に出し、その版でこの Issue がまとめて宣言する

### 未決 4 の案（レビューの単位）

| 案 | 実装 PR（→ スプリントブランチ） | スプリントブランチ（→ ベースブランチ） | リリースブランチ（→ 本番チャネル） | 得失 |
| --- | --- | --- | --- | --- |
| A（起票者の推奨） | cross-review（課題のまとまりごと。#3081 の手法） | まだ検査していない差分だけに cross-refactoring・振る舞いの確認・最後の検査（#3126 の範囲） | 差分を読み直さない。衝突の解消の差分だけを cross-review する。全体テストは通す（受け入れ条件 6） | レビューは差分ごとに 1 回で済む。集めたときにだけ生じる不具合は、衝突の解消の差分と全体テストで拾う |
| B | レビューしない | cross-review と cross-refactoring を 1 回 | 同上 | 回数は最も少ないが、課題のまとまりごとの指摘が 1 つの大きな差分に混ざる（#3081 の動機に反する） |
| C | cross-review | 同左 | リリースの範囲全体を cross-review し直す | 組み合わせの不具合を最も拾えるが、同じ差分を 2 度レビューし、リリースの差分が大きいほど費用が増える |

案 A を `reviews` の値で書くと次になる。`parse_flow` がこの値を指摘なしで読むことは確かめた（2026-11-13、`promotion: selected` と組み合わせて実行）。

```json
"reviews": {
  "impl": {"checks": ["cross-review"], "diff": "pr"},
  "sprint": {"checks": ["cross-refactoring", "behavior"], "diff": "unchecked"},
  "release": {"checks": ["cross-review"], "diff": "resolution"},
  "design": {"checks": ["cross-review"], "diff": "pr"},
  "spec": {"checks": [], "diff": "none"}
}
```

案 C は、リリースブランチの行に `cross-review / pr` を書き、実装 PR の行も cross-review を持つため、同じ差分を 2 度レビューする組になる。受け入れ条件 7 の I12 の指摘には当たらない（I12 は書いていない行の既定値との重なりだけを見る）ため、2 度のレビューを避けるかは値の選び方で決まる。

| 方式 | 中身 | ai-plugins との相性 |
| --- | --- | --- |
| git 本家の運用（gitworkflows(7)、 https://man7.org/linux/man-pages/man7/gitworkflows.7.html ） | トピックブランチを、最終的に取り込む中で一番古いブランチ（本番）から切る。結合を試すブランチ `next` へマージして試し、安定したものから 1 つずつ本番へ上げる。`next` は本番へ戻さず、リリース後に作り直してよい | 最も合う。今のベースブランチが `next` の役にあたる |
| Branch per feature（ https://caktusgroup.com/blog/2025/03/04/how-deploy-selectively-production ・ https://docs.acquia.com/acquia-cloud-platform/help/89311-pragmatic-guide-git-branching ） | 機能ブランチを本番の同じ点から切り、結合ブランチで試し、準備のできた機能だけでリリースを組む。同じ衝突の解き方は `git rerere` で再利用する | 合う |
| GitFlow の develop | develop を丸ごとリリースへ流す。未完成のものを外せない | 今の形で、この Issue の問題の原因 |
| リリーストレイン（ https://martinfowler.com/articles/branching-patterns.html ） | 決まった間隔のリリースに、完成した機能がどの便に乗るかを選ぶ | 「どのスプリントを乗せるか」の考え方として使う |
| トランクベース開発＋機能フラグ（ https://docs.getunleash.io/feature-flag-tutorials/use-cases/trunk-based-development ） | 全部を本流へ入れ、未完成のものはフラグで隠す | 合わない。NDF の変更の多くは Skill の本文と手順書で、フラグで隠せない |

## MVV との突き合わせ

反する疑いは無い。

- Value 1: 承認したスプリントだけを本番へ出せるようになり、承認資料の範囲が承認の単位と一致する
- Value 4: 運用はリポジトリの宣言の値で表し、NDF の制約にしない（利用者の方針）
- Value 2・Value 11: レビューの単位を 1 つの宣言に置き、同じ差分の 2 度のレビューを避ける
- P1・C7: 宣言と `AGENTS.md` の運用の節の書き換えは、リリース承認ゲートで人が見る
