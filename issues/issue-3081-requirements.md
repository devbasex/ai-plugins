## 目的

- **今どうなっているか**: 課題のマイルストーンは大まかなテーマ別に付いている。並列の計画は、利用者が示したいくつかのテーマで組まれ、レーンはテーマ別に起動し、スプリントはそのテーマの課題で構成される。スプリントの中の課題の Pull Request はレビューを通さずにスプリントブランチへ集まり、ベースブランチ（`develop`）へのスプリントの Pull Request 1 本で、リファクタリングと cross-review をスプリントの全差分に対して 1 回行う（`plugins/ndf/skills/pr/SKILL.md` の「スプリントブランチ宛てと develop 宛て」）
- **困っていること**:
  - 1 つのスプリントの課題が似たテーマで集まるため、触るファイルが同じか依存関係で近いことが多い。並行に開発できず、逐次の開発になる（例: lcost-1 では 7 課題が `loop.md`・`sprint_loop*.py` などを共有し、480 分のあいだ実装が 1 本しか動かなかった。#2997 の調べ）
  - スプリントの Pull Request で複数テーマを同時にレビューするため、見る範囲が増えて精度が落ち、長い繰り返しが起きる（lcost-1 のスプリントの Pull Request は 11 ラウンド回って上限で終わった。#3050）
  - 結果として、スプリントの完了に長い時間がかかる
- **変えると何が成り立つか**: 並列の計画を作る時点で似た課題が「課題のまとまり」へまとまり、レーンとスプリントは触るファイルが互いに離れたまとまりで組まれて並行に開発される。レビューは 1 つのまとまりの短い差分に限られ、スプリントが短い時間でマージされる

## 前提

- 前提 1: 課題をまとめる判断（どの課題が似ているか・親子か統合か）と、まとまりをレーンとスプリントへ割り当てる判断は、並列の計画を作る conductor（オーガナイザー）が行う。スクリプトは、まとまりの記録の形の検査と、触る場所の見込みの重なりの検査を持つ
- 前提 2: 触る場所の見込みの出し方と重なりの判定は、#2997 の実装（`plugins/ndf/scripts/lib/touch_estimate.py`、実装のキューと同じ重なりの判定 `overlap_of`）を使い、判定の関数をもう 1 つ作らない。見込みの出し方・判定の粒度（#1811・#2037）はこの課題で変えない
- 前提 3: 並列の計画そのものは、利用者が示したいくつかのテーマで組んでよい。テーマはどの課題を計画に入れるかを決め、レーンとスプリントの組み方は決めない
- 前提 4: 同じまとまりの課題どうしは、触る場所が重なってよい（似た課題をまとめるため）。疎であることを求めるのは、同じスプリントか同じ時間帯のレーンに入った、異なるまとまりの間だけである
- 前提 5: 開発ループのレーン（入力がループのレーン）のスプリントの中身は、ループの選定（#2997 の並べ替え）が決める。この課題は、ループの選定がまとまりの単位で課題を選ぶかを設計で決める（未決 5）
- 前提 6: 「同時に動く本数」の基準は 2 つ置く。#2997 の調べの 8 スプリントの平均 1.08 本と、同じ記録を実験版の模擬（`plugins/ndf/scripts/experimental/selection-replay.py`）で今の選び方で打った値である
- 前提 7: 似た課題の統合で課題を閉じる・親の課題を起こすのは GitHub Issues への書き込みであり、外部の課題管理（C8）に当たらない。閉じた課題は開き直せる（C4 に当たらない）。この変更は外部への公開・課金・認証・利用者のデータに触れない（C1〜C8・P1 に当たらない）

## 対象範囲

含む:
- 並列の計画を作る時点で、似た課題を課題のまとまりへまとめる手順と、まとめ方（親の課題を起こして親子にするか、課題自体を統合するか）の決め方
- まとまりと課題の対応を、並列の計画の記録に残すこと
- レーンとスプリントを、テーマによらず互いに疎なまとまりで構成すること（計画自体は指定されたテーマで構成してよい）
- 並列の計画の検査で、同じスプリントか同じ時間帯のレーンに入った異なるまとまりの見込みの重なりを見つけること
- レビュー（cross-review）をまとまりの単位で行うこと
- 疎なまとまりで組んだ計画で、同時に動く本数とレビューの規模を測って記録すること

含まない:
- 触る場所の見込みの出し方と、開発ループの選定・レーンの割り当ての重なりの検査（`I21`）の仕組みそのもの（#2997 が持つ。マージ済み）
- 重なりの判定の粒度（#1811・#2037）
- cross-review が収束しない原因の計測と直し方（#3050）
- 設計で分けた Pull Request の本数を実装のプランへ写すこと（#2539）
- 似ていると判定する規則の自動化（どの課題が似ているかを機械が決めること）
- マイルストーンの付け方そのものの変更（テーマ別のままでよいかは設計で決める。未決 3）

## 用語

| 用語 | 意味 |
| --- | --- |
| 課題のまとまり | 並列の計画を作る時点で、似た課題を 1 つのレビューの単位としてまとめたもの。1 件の課題だけのまとまりもある。依頼の「タスク」に当たる |
| 疎なまとまり | 触る場所の見込みが互いに重ならない、課題のまとまりの組 |
| まとまりの単位のレビュー | 1 つの課題のまとまりの課題が変えた差分だけを範囲にした cross-review |

## 受け入れ条件

- [ ] 1. 並列の計画を作る手順（`issue-plan-strategy` の `references/parallel-plan.md`）が、似た課題を課題のまとまりへまとめる手順と、親子か統合かを選ぶ条件を持つ。条件は、同じ課題の組に対して誰が読んでも同じまとめ方を選ぶ形で書かれている（設計承認ゲートで、手順の例の課題の組に当てて確かめる）
- [ ] 2. 並列の計画の記録に、まとまりごとの名前と課題の番号の一覧が残る。どの課題も 2 つ以上のまとまりに入っていない（入っていれば検査が誤りにする）
- [ ] 3. まとめない課題は、その 1 件だけのまとまりとして扱われ、検査とレビューが 1 件のまとまりでも動く
- [ ] 4. 並列の計画の検査で、同じスプリント（同じレーンの入力）か、`after` で順序の付かない同じリポジトリの 2 レーンに、触る場所の見込みが重なる異なるまとまりがあるとき、検査の出力に重なるまとまりの組と、組み替えの案（別のスプリントへ移す・`after` を足す）が載る
- [ ] 5. 受け入れ条件 4 の判定でも、同じまとまりに入った課題どうしの見込みの重なりは出力に載らない
- [ ] 6. 受け入れ条件 4 の重なりの判定は、#2997 の見込みの出し方と実装のキューと同じ重なりの判定の関数を使う（テストで、同じ入力に対して #2997 の `I21` と同じ組が重なりと判定される）
- [ ] 7. テーマ別でなく、疎なまとまりの組でレーンとスプリントを構成した並列の計画を 1 つ作って回し、実装のステージで同時に動く本数の平均を記録する。その平均が基準の 2 つ（1.08 本と、同じ記録を今の選び方で模擬した値）より大きい
- [ ] 8. cross-review が 1 つのまとまりの差分を範囲にして回る。1 回のレビューのレビュー範囲（base・head・ファイル数）が、そのまとまりの課題が変えたファイルだけを含む
- [ ] 9. 受け入れ条件 7 の計画のスプリントについて、まとまりの単位のレビューごとの差分の行数・ラウンド数・所要時間・費用を、スプリント単位で回した今の値（lcost-1 のスプリントの Pull Request の 11 ラウンドなど）と並べて、この課題に記録する
- [ ] 10. 退行しない: まとまりを書かない既存の並列の計画の記録（`plan.json`）を読んでも、検査と起動が止まらない。既存の検査の規則（`I4`・`I19`・`I21`）の出力の形は変わらない（追加だけ）
- [ ] 11. 退行しない: 並列の計画を経ない単独のスプリントと開発ループのスプリントでは、まとまりを書かなければ今と同じく、スプリントの Pull Request の全差分に対して cross-review が 1 回回る

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | レビューの回数が増えるため、受け入れ条件 9 の記録で、スプリントあたりのレビューの合計の所要時間と費用を今の値と並べる。合計の費用が今より増えたときは、増えた理由と代わりの案を記録に書く（Value 2） |
| 運用・保守性 | 重なりの判定の関数を新しく作らず、#2997 と実装のキューの関数を共有する。まとまりの記録の形は、並列の計画の記録の契約（`plugins/ndf/contracts/`）に置き、検査がその形を読む |
| 移行性 | まとまりの欄の無い計画の記録は、課題 1 件ずつのまとまりとして読む（受け入れ条件 10） |

>
> ## 課題
> * 1つのスプリント内のissueは似通ったテーマで構成されているため、触るファイルが同じか依存関係的に近いことが多い
> * この結果、並行で開発することができず、逐次開発になってしまう
> * また、複数テーマを同時にレビューするため、見る範囲が増え、精度が落ち、かつ長い繰り返しが発生する
> * 結果、スプリントの完了に長い時間が掛っている
>
> ## あるべき姿
> * スプリント内のissueは触るファイルが異なる領域で構成され、並行に開発される
> * レビューは単一内容(issueまたは同じissueをまとめたもの)の範囲に限定して、かつ短い差分に対して行われる
> * 結果、スプリントが短時間でマージされる状態となっている
>
> ## あるべき姿に向けた案(要検討)
> * 並行開発計画自体は指定されたいくつかのテーマで構成される
> * 似たissueは開発計画時に「タスク」としてまとめられる(新しいissueを起こして親子関係とするか、issue自体を統合する)
> * レーンはテーマに関係なく、互いが疎になるようなタスクで構成される
> * スプリントも同様に関係の薄いタスクで構成される
> * レビューはタスク単位でおこなわれる
>
