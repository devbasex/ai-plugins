> ## 何を見つけたか
>
> 本番への配布の承認は「承認した時点の `develop` の中身」を前提にしているが、`release` の手順は承認した中身を**コミットで控えず、`main` へ入れる直前に比べることも求めていない。** ndf 10.16.0 の配布では、承認（2026-09-22T14:36Z、中身は「開発版 10.16.0-dev.1 と同じ」）の 6 分後に、ミッションの外の PR #806（statusline）が `develop` へマージされた。仕上げのフェーズが配布物の差分（119 → 124 ファイル）の食い違いに気づいて止まり、再承認（15:0xZ）を経て配布したが、気づいたのは差分の数を数え直したからで、手順の上の確認ではない。
>
> ## どこで見つけたか
>
> - `plugins/ndf/skills/release/SKILL.md` の「公開前の提示と承認」と手順 4（公開する）
> - `plugins/ndf/skills/development-workflow/references/approval-request.md` の「配布（`release`）」の承認資料
> - 見つけた場面: ndf 10.16.0 の配布（PR #808 → #809 → #810）
>
> ## なぜこの変更の範囲外なのか
>
> マイルストーン 13 は `cross-review` / `cross-refactoring` の収束ループを扱い、配布の手順は範囲に無い。振り返りで決めた「次に変えること」である。
>
> ## 直さないと何が起きるか
>
> 承認と公開の間に開発版のチャネルへ別の変更が入ると、**承認していない変更が検証を経ずに本番へ届く。** 差分の数を数え直さない限り気づけない。## 直し方
>
> 承認資料に「承認するコミット（`develop` の先端の SHA）」を書き、`develop` → `main` の Pull Request をマージする直前に `develop` の先端と比べ、違えば承認ゲートへ戻る。
>
> **直す場所は `plugins/ndf/scripts/release-steps.py` である。**
>
> | 段 | 今の形 | 足すこと |
> | --- | --- | --- |
> | `approval-facts`（`cmd_approval_facts`） | `origin/develop` の SHA を読み、承認資料の対象の比較 URL（`compare/<前のタグ>...<SHA>`）と題（`develop（<SHA の先頭 8 桁>）`）に入れる | 承認する SHA を結果の `metrics` に出す |
> | `release --channel prod`（`cmd_release`） | `develop` → `main` の Pull Request を作ってマージする。承認した SHA を受け取らず、比べない | 承認した SHA を引数で受け、マージの直前に `origin/develop` の先端と比べ、違えば承認ゲート（終了コード 10）で止まる |
>
> ## 関連
>
> - `plugins/ndf/scripts/release-steps.py` — 配布の決まった手順（`approval-facts` / `release`）
>
> ## 由来
>
> PR #810 の振り返り（ndf 10.16.0、マイルストーン 13）

## 目的

- 本番への配布（ゲート 2）で人か MVV 判定が承認した中身と、`main` へ入る中身が食い違ったら、公開の前に必ず止まる状態にする
- 食い違いに気づくのを「差分の数を数え直した」偶然に頼らず、`release-steps.py` の手順の上の確認にする

## 前提

- 前提 1: 「承認したコミット」は `approval-facts` を打った時点の `origin/<ベースブランチ>` の先端の SHA（40 桁）とする。今の承認資料が比較の URL と題に使っている SHA と同じものである
- 前提 2: 本番のリリースプランは、承認の後に配布の PR（`release/v<版>` → ベースブランチ。開発版の接尾辞を外す bump・changelog・他のプラグインの bump を含む）をマージしてから、ベースブランチ → 本番チャネルの PR をマージする（`cmd_release` の今の順序）。このため、承認したコミットとマージの直前のベースブランチの先端は**正しく進めても一致しない**。比べるのは「承認したコミットからベースブランチの先端までに、この版の配布の PR が入れたコミットの外のコミットが無いか」である
- 前提 3: 配布の PR のマージの方法（merge / squash / rebase）はリポジトリごとに違う。どの方法でも判定が成り立つ形は設計が決める。判定できない方法のときは、通さずに承認ゲート（終了コード 10）で止まる側へ倒す
- 前提 4: 承認したコミットを本番のリリースプランへどう渡すか（承認資料から読む・状態ファイルに書く・プランの生成時に引数で渡す）は設計が決める。この要求は「渡されなければ公開しない」だけを決める
- 前提 5: `merged-steps.py promote`（`release` の形を持たないリポジトリの昇格の経路）にも同じ欠けがある。この課題では直さず、比べる関数は promote から後で使える共通の層に置く（Value 6）。promote を直すのは別の課題にする

## 対象範囲

含む:
- `release-steps.py approval-facts` が承認したコミットを結果の `metrics` と承認資料に書くこと
- `release-steps.py release --channel prod` が承認したコミットを引数で受け、本番チャネルの PR をマージする直前にベースブランチの先端と比べ、承認していないコミットがあれば止まること
- 本番のリリースプラン（`supervise.py new release --channel prod`。`--mvv` を付けた形を含む）が、その引数を渡すこと
- `release` の Skill 本文と `references/release-steps.md` の打ち方・`status` の読み方の更新

含まない:
- `merged-steps.py promote` の昇格の経路（前提 5）
- `--channel dev` の振る舞い（開発版はマージした変更がそのまま載るチャネルであり、承認を要しない）
- 承認資料のほかの欄・MVV 判定（`mvv-gate.py`）の判定の中身
- 食い違ったときに承認資料を自動で作り直して再承認を求める仕組み（止まって人へ戻すまでを扱う）

## 受け入れ条件

- [ ] 1. `approval-facts` の結果 JSON の `metrics.approved_sha` に、打った時点の `origin/<ベースブランチ>` の SHA（40 桁）が入る
- [ ] 2. `approval-facts` が書く承認資料に、承認したコミットの SHA（40 桁）が欄として載る（題の先頭 8 桁と比較の URL は今のまま残る）。`next` のコマンドに `--approved-sha <SHA>` が入る
- [ ] 3. 前提: 承認したコミット A の後にベースブランチへ入ったのが、この版の配布の PR のコミットだけである
      操作: `release --version <版> --channel prod --approved-sha A`
      結果: 今と同じく本番チャネルの PR をマージし、タグと GitHub Release を作って `ok`（0）で終わる。結果の `metrics.approved_sha` に A が入る
- [ ] 4. `--channel prod` で `--approved-sha` を渡さないと、配布の PR も本番チャネルの PR もマージせず、終了コード 2 か 3 で止まり、`summary` に `--approved-sha` が要ることが書かれる
- [ ] 5. 前提: 承認したコミット A の後に、この版の配布の PR の外の PR（例: #806 のような別の変更）がベースブランチへマージされた
      操作: `release --version <版> --channel prod --approved-sha A`
      結果: 本番チャネルの PR をマージせず、タグも GitHub Release も作らず、`status: gate`・終了コード 10 で止まる。`items[]` に承認していないコミット（SHA と、分かれば PR 番号）が並び、`summary` か `next` に承認資料を作り直して承認を取り直すことが書かれる
- [ ] 6. 比べた後、本番チャネルの PR の CI を待つ間にベースブランチの先端が進んだら、マージしない（マージするのは比べた先端のコミットだけである）
- [ ] 7. 承認したコミット A がベースブランチの先端の祖先でない（履歴の書き換え・別のブランチの SHA・存在しない SHA）とき、マージせずに終了コード 10 で止まる。A を読めない（形の誤り）ときは終了コード 2 で止まる
- [ ] 8. 本番のリリースプラン（`supervise.py new release --channel prod`、`--mvv` 付きを含む）が `release` のステップに承認したコミットを渡し、受け入れ条件 5・7 の終了コード 10 は今の承認ゲートの扱い（プランの結果が承認ゲートになり、人へ戻る）になる。MVV 判定の承認でこの承認ゲートを通さない
- [ ] 9. 退行しない: `--channel dev` の引数・振る舞い・結果 JSON が変わらない。`release --channel prod` の配布の PR がマージ済みで打ち直したとき（一致する場合）も、今と同じく続きから進む
- [ ] 10. `release` の `SKILL.md`（公開前の提示と承認・手順 4）と `references/release-steps.md` に、承認したコミットを渡すことと、終了コード 10 で止まったときの読み方が書かれ、書いたコマンドは実行して確かめてある

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 止まったときの結果 JSON だけで、承認していないコミットの SHA と、承認したコミット・比べた先端が読める（LLM が git を追加で照会しなくてよい） |
| セキュリティ | 承認していない変更が本番チャネル・タグ・GitHub Release へ届かない（ゲート 2 の承認の対象が守られる。共通原則の「利用者の承認」の優先順位） |
| システム環境 | ベースブランチ・本番チャネル・プラグイン名は今と同じく宣言（`.ndf/release.json` / `.ndf/worktree.json`）と引数から読み、`develop` / `main` を既定に埋め込まない（Value 5） |

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`release --channel prod` に `--approved-sha` が必須になる（手で打つ人は承認資料の `next` のコマンドをそのまま使う）。`approval-facts` の `metrics` と承認資料に欄が増える |
