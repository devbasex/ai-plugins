# #3600: エピック: 複数のスプリントにまたがる作業の土台（全体設計・契約・データ構造・設定）を先に置き、機械で守らせる（11.x）

正は課題の本文（#3600）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 目的

NDF の工程（`development-workflow`）は、スプリント（1 つの版として出す課題と Pull Request のまとまり）までしか扱わない。複数のスプリント・レーン・版にまたがる大きな作業（**エピック**）では、全体の設計・入出力の仕様・データ構造・設定と環境変数の仕様を、個別の Issue の設計と実装を走らせる前にまとめる手順も置き場も無い。

達成したい状態: エピックを始める時点で、全レーンが先に読む文書（**エピックの土台**）が 1 か所にあり、土台の必須の節がそろうまでレーンが起動せず、土台の契約と実装の食い違いを CI が落とす。AI の並列のレーンが同じ前提で作れる。

具体例: ndf-next 11.0（#1142）では、横断の仕様を走りながら後からまとめた。

| 時点（JST） | 起きたこと |
| --- | --- |
| 11-13 夜 | 実装の子 X0・X1・D1・C1 が始まり閉じた。契約（`contracts/*.json`）は D1 の実装の中で作った |
| 11-13 深夜〜11-14 | 設計レビュー 24 本・182 項目を起票。その時点で子 9 本が閉じていた。D（DBOS の置き方）の決着まで C2 を止めた |
| 11-14 未明 | Y #3395（行き先と範囲の決定）の承認まで新しい子の着手を止めた。分割 3・新設 7 |
| 11-15 | 入出力の規約の文書（環境変数・副命令・終了コード・hook・宣言）を初めて生成（#3518）。子 46 単位のうち 23 が閉じていた |
| 11-15 | 試走 T2 の 1 回目は 204 行中 7 行だけ通った（#3569、エントリポイントの `$SCRIPTS` が旧いプラグインを指した） |

手戻り: 閉じた子への追補 10 単位・マージ済みの不具合 12 件（#3394）・要求と設計の食い違い 16 か所・着手の停止 2 回・決定の改定 2 件。nd-factory（モデルの文書が #63 の決め直しを引き出した）と carmo-system-console の法人リース（全体設計を先に置いたが 10-27 の方針転換で 20 本以上を直した）にも同じ種類の費用がある。

## 決まったこと（2026-11-15、利用者）

- **NDF の「プロジェクト」は、主リポジトリ 1 つとサブリポジトリの集まり（Factory の定義、#2653）だけを指す。** 今の `.ndf/project.json`・プロジェクト MVV などの「リポジトリ 1 本」の意味は、そのうちリポジトリが 1 本の場合で、#2653 で広げる途中にある。GitHub Projects・Claude Code の project など他のサービスの名前はそのまま受け入れる
- **複数のスプリントにまたがる作業は「エピック」と呼ぶ**
- 既存の Skill に足す（新しい Skill を作らない）
- 実装は 11.x（ndf-next）。11.0 の範囲（#1142、「現行と同等」）には入れない
- **設計は先に進める（2026-11-15 23:1x）。詳細設計は 11.0（`plugins/ndf-next/`）の構造に対して書く。** 難しければ詳細設計を後回しにしてレビューと設計承認へ進んでよい。nd-factory の画面構成に影響が出そうなので、設計にその節を置く（並列の計画 p6 のレーン lepic）

## 前提

- 前提 1: 実装の置き場は 11.x の ndf-next（`plugins/ndf-next/`）である。今の `plugins/ndf/` へは足さない。11.0 の範囲（#1142）が閉じる前は、実装の Pull Request を出さない
- 前提 2: 承認ゲートは設計承認ゲートとリリース承認ゲートの 2 つのままで、エピックの土台は最初のスプリントの設計 PR に載せて設計承認ゲートで人が見る
- 前提 3: エピックのエントリポイントに入る規模の目安は「複数のレーンか複数のスプリントにまたがる」である。境界の値（何レーンから・何スプリントから）は設計で決め、1 スプリントで 1 レーンの依頼はエントリポイントへ回らない
- 前提 4: 起票者の推定 S1 の効果（#1142 の手戻りを防げたか）は、受け入れ条件 1 の比べ（足す前と後）で確かめ、手戻りの件数の減りは測らない（同じエピックを 2 回走らせられないため）
- 前提 5: 詳細設計（ファイルの置き場・副命令・契約の表・`plan.json` の欄・検査）は 11.0 の構造に対して書く。11.0 の構造が固まっておらず書けない部分は、設計文書に「詳細設計は後」と書いて未決に残し、設計承認ゲートへ進む
- 前提 6: 用語集（`docs/glossary.md`・`docs/glossary/glossary.json`）は他のレーンも触る。取り込みの衝突は、ベースブランチとの同期で解く
- 前提 7: Factory 側（nd-factory）の課題は起票しない。画面への影響は設計文書の節と申し送りで渡す

## 対象範囲

含む:
- エピックの規模の判定（工程のエントリポイントでエピックのエントリポイントへ回すか）
- エピックの土台の参照（書き方・必須の節・規模の目安）と雛形の生成
- 並列の計画（`plan.json`）の欄（土台のパス・エピックの完了条件）と、起動の前の検査
- 土台の契約の表と実装の照合を、Pull Request ごとに CI で行う検査
- エピックの完了条件による並列の計画の終わりの判定と、`status` の進み具合
- 土台の変更を、触る場所の重なるレーンへ知らせる仕組み
- 用語集への「エピック」の追加と「プロジェクト」の定義の書き直し
- 設計文書の、nd-factory の画面構成への影響の節（Factory のどのオブジェクト・画面に現れ、何を足すか・変えるか）

含まない:
- 「プロジェクト」を複数リポジトリへ広げる実装（#2653）
- 今の `plugins/ndf/` への実装
- 11.0 の範囲（#1142）の変更
- nd-factory のコードの変更と、Factory 側の課題の起票
- 新しい Skill と新しい承認ゲート
- ウォーキングスケルトン（Walking Skeleton。端から端まで動く最小の構成）の有無を機械で検査すること
- 既存のエピック（#1142 など）の土台を遡って書くこと

## 用語

| 用語 | 意味 |
| --- | --- |
| エピック | 複数のスプリント・レーン・版にまたがる作業のまとまり。並列の計画 1 つか、続く複数の計画で進める |
| エピックの土台 | エピックの全レーンが設計と実装の前に読む、1 か所に置く文書。用語・データ構造と状態の置き場・入出力の契約・設定と環境変数などの必須の節を持つ |
| エピックの完了条件 | エピックが終わったと判定する、観測できる条件の一覧。並列の計画に書き、`status` が進み具合を出す |
| プロジェクト | 主リポジトリ 1 つとサブリポジトリの集まり。リポジトリが 1 本だけのときもその場合として含む |

「土台」はこの文書では常に「エピックの土台」を指す（用語集の「git を使うテストの土台」とは別の物）。「計画」は常に「並列の計画」を指し、実装計画とは呼び分ける。

## 受け入れ条件

- [ ] 1. 3 レーン規模の依頼を `claude -p` で渡すと、エピックのエントリポイントへ回り土台を書く。1 スプリントで 1 レーンの依頼では回らない（足す前と後で比べ、PR のコメントに残す）
- [ ] 2. エピックの土台の必須の節が空の並列の計画は、起動の前の検査がレーンを起動せず、空の節の名前を出して 0 以外の終了コードで落ちる。必須の節がそろえば同じ計画が起動する
- [ ] 3. エピックの土台の契約の表と実装が食い違う Pull Request を CI が落とし、食い違う項目の名前を出す。食い違いの無い Pull Request は通る
- [ ] 4. エピックの完了条件を持つ並列の計画は、全レーンが止まっても完了条件が残っていれば終わりと判定されない。すべての完了条件が満たされたときに終わりと判定される
- [ ] 5. `status` の出力に、エピックの完了条件ごとの満たした・残りと、満たした件数 / 全件数が出る
- [ ] 6. エピックの土台を変更する Pull Request がマージされると、その変更の触る場所と重なる場所を触るレーンに知らせが届く（止まっているレーンには再開のときに読む記録として残る）。重ならないレーンには届かない
- [ ] 7. 規模の手がかりが無い依頼は 1 スプリントとして扱われ、判定の理由が記録に残る
- [ ] 8. 土台のパスと完了条件の欄を持たない並列の計画は、今と同じく検査を通り、全レーンの停止で終わりと判定される（退行しない）
- [ ] 9. 承認ゲートの数が増えない（設計承認ゲートとリリース承認ゲートの 2 つ）。新しい Skill が増えない（`plugins/ndf-next/manifests/` の行数が変わらない）
- [ ] 10. 用語集に「エピック」があり、「プロジェクト」が主リポジトリとサブリポジトリの集まりの意味だけで載る
- [ ] 11. Skill の本文の増分が全体で 10 行以内で、各 `SKILL.md` が 500 行の上限に収まる
- [ ] 12. 設計文書に nd-factory の画面構成への影響の節があり、エピックが現れる Factory のオブジェクトと画面ごとに、足すもの・変えるもの・変えないものが表で載る

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。並列の計画（`plan.json`）に任意の欄（土台のパス・エピックの完了条件）が足され、`status` の出力に進み具合が足される。欄は任意で、既存の計画はそのまま通る（互換あり） |

## 検証手段

| 項目 | 手段 |
