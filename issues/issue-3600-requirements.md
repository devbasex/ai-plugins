# #3600: エピック: 複数のスプリントにまたがる作業の土台（全体設計・契約・データ構造・設定）を先に置き、機械で守らせる（11.x）

正は課題の本文（#3600）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 目的

NDF の工程（`development-workflow`）は、スプリント（1 つのバージョンとしてリリースする Issue と Pull Request のまとまり）までしか扱わない。複数のスプリント・レーン・バージョンにまたがる大きな作業（**エピック**）では、全体の設計・入出力の仕様・データ構造・設定ファイルと環境変数の仕様を、個別の Issue の設計と実装を走らせる前にまとめる手順も配置先も無い。

達成したい状態: エピックを始める時点で、全レーンが先に読む文書（**エピックのアーキテクチャ設計書**）が 1 か所にあり、その必須セクションがそろうまでレーンが起動せず、アーキテクチャ設計書のコントラクト（スキーマ）と実装の食い違いを CI のコントラクトテストが落とす。AI の並列のレーンが同じ前提で作れる。

具体例: ndf-next 11.0（#1142）では、横断の仕様を走りながら後からまとめた。

| 時点（JST） | 起きたこと |
| --- | --- |
| 11-13 夜 | 実装のサブ Issue X0・X1・D1・C1 が始まり閉じた。コントラクト（`contracts/*.json`）は D1 の実装の中で作った |
| 11-13 深夜〜11-14 | 設計レビュー 24 本・182 項目を起票。その時点でサブ Issue 9 本が閉じていた。D（DBOS の置き方）の決着まで C2 を止めた |
| 11-14 未明 | Y #3395（行き先と範囲の決定）の承認まで新しいサブ Issue の着手を止めた。分割 3・新設 7 |
| 11-15 | 入出力の規約の文書（環境変数・サブコマンド・終了コード・hook・設定ファイル）を初めて生成（#3518）。サブ Issue 46 単位のうち 23 が閉じていた |
| 11-15 | E2E の試験実行 T2 の 1 回目は 204 行中 7 行だけ通った（#3569、エントリポイントの `$SCRIPTS` が古いプラグインを指した） |

手戻り: 閉じたサブ Issue への追補 10 単位・マージ済みの不具合 12 件（#3394）・要求と設計の食い違い 16 か所・着手の停止 2 回・ADR（設計判断の記録）の改定 2 件。nd-factory（モデルの文書が #63 の決め直しを引き出した）と carmo-system-console の法人リース（全体設計を先に置いたが 10-27 の方針転換で 20 本以上を直した）にも同じ種類の費用がある。

## 決まったこと（2026-11-15、利用者）

- **NDF の「プロジェクト」は、主リポジトリ 1 つとサブリポジトリの集まり（Factory の定義、#2653）だけを指す。** 今の `.ndf/project.json`・プロジェクト MVV などの「リポジトリ 1 本」の意味は、そのうちリポジトリが 1 本の場合で、#2653 で広げる途中にある。GitHub Projects・Claude Code の project など他のサービスの名前はそのまま受け入れる
- **複数のスプリントにまたがる作業は「エピック」と呼ぶ**
- 既存の Skill に足す（新しい Skill を作らない）
- 実装は 11.x（ndf-next）。11.0 の範囲（#1142、「現行と同等」）には入れない
- **設計は先に進める（2026-11-15 23:1x）。詳細設計は 11.0（`plugins/ndf-next/`）の構造に対して書く。** 難しければ詳細設計を後回しにしてレビューと設計承認へ進んでよい。nd-factory の画面構成に影響が出そうなので、設計にその節を置く（並列の計画 p6 のレーン lepic）
- **設計文書 4 本（要求・設計・詳細設計・ADR）と、この設計 PR で用語集に足す行は、エンジニアの業界で使われている語で書く（2026-11-15 23:5x）。** 1 語に 1 つの意味を保つ。英語のほうが通じる語（Definition of Done・Walking Skeleton など）はカタカナか英語のまま使う。NDF の既存の用語集にある語は、初出で括弧に添える。用語集の既存の行を業界の語へ改める作業は、この設計 PR の範囲の外とし #3610 で扱う

## 前提

- 前提 1: 実装の配置先は 11.x の ndf-next（`plugins/ndf-next/`）である。今の `plugins/ndf/` へは足さない。11.0 の範囲（#1142）が閉じる前は、実装の Pull Request を出さない
- 前提 2: 承認ゲートは設計承認ゲートとリリース承認ゲートの 2 つのままで、エピックのアーキテクチャ設計書は最初のスプリントの設計 PR に載せて設計承認ゲートで人が見る
- 前提 3: エピックのエントリポイントに入る規模の目安は「複数のレーンか複数のスプリントにまたがる」である。境界の値（何レーンから・何スプリントから）は設計で決め、1 スプリントで 1 レーンの作業はエントリポイントへ回らない
- 前提 4: 起票者の推定 S1 の効果（#1142 の手戻りを防げたか）は、受け入れ条件 1 の比較（足す前と後）で確かめ、手戻りの件数の減りは測らない（同じエピックを 2 回走らせられないため）
- 前提 5: 詳細設計（ファイルの配置先・サブコマンド・コントラクトの表・`plan.json` の欄・検査）は 11.0 の構造に対して書く。11.0 の構造が固まっておらず書けない部分は、設計文書に「詳細設計は後」と書いて未決に残し、設計承認ゲートへ進む
- 前提 6: 用語集（`docs/glossary.md`・`docs/glossary/glossary.json`）は他のレーンも触る。マージコンフリクトは、ベースブランチとの同期で解く
- 前提 7: Factory 側（nd-factory）の Issue は起票しない。画面への影響は設計文書の節と引き継ぎで渡す
- 前提 8: Issue の本文の節の見出し（`依頼（原文）`・`起票者の推定`・`進行` など）は、NDF の Issue のテンプレートとそれを読むスクリプトが決める名前なので変えない。見出しの語を改めるかは #3610 で扱う

## 対象範囲

含む:
- エピックの規模の判定（工程のエントリポイントでエピックのエントリポイントへ回すか）
- エピックのアーキテクチャ設計書の参照（書き方・必須セクション・規模の目安）とテンプレートの生成
- 並列の計画（`plan.json`）の欄（アーキテクチャ設計書のパス・エピックの DoD）と、レーンの起動前チェック
- アーキテクチャ設計書のコントラクトの表と実装を、Pull Request ごとに CI で突き合わせるコントラクトテスト
- エピックの DoD による並列の計画の終了判定と、`status` の進捗
- アーキテクチャ設計書の変更を、触るファイルの重なるレーンへ通知する仕組み
- 用語集への「エピック」の追加と「プロジェクト」の定義の書き直し
- 設計文書の、nd-factory の画面構成への影響の節（Factory のどのオブジェクト・画面に現れ、何を足すか・変えるか）

含まない:
- 「プロジェクト」を複数リポジトリへ広げる実装（#2653）
- 今の `plugins/ndf/` への実装
- 11.0 の範囲（#1142）の変更
- nd-factory のコードの変更と、Factory 側の Issue の起票
- 新しい Skill と新しい承認ゲート
- Walking Skeleton（端から端まで動く最小の構成）の有無を機械で検査すること
- 既存のエピック（#1142 など）のアーキテクチャ設計書を遡って書くこと
- 用語集の既存の行（バージョン・既読フラグ・ワークフロー状態などに当たる語）の改名（#3610）

## 用語

| 用語 | 意味 | 依頼（原文）での呼び名 |
| --- | --- | --- |
| エピック | 複数のスプリント・レーン・バージョンにまたがる作業のまとまり。並列の計画 1 つか、続く複数の並列の計画で進める | エピック |
| エピックのアーキテクチャ設計書 | エピックの全レーンが設計と実装の前に読む、1 か所に置く文書（Architecture Doc）。用語・データ構造と状態の保存先・入出力のコントラクト・設定ファイルと環境変数などの必須セクションを持つ。Issue ごとの設計文書とは別の文書 | 土台 |
| エピックの DoD | エピックが終わったと判定する、観測できる項目の一覧（Definition of Done）。定義はアーキテクチャ設計書の表に置き、並列の計画は番号で指す。`status` が進捗を出す | エピックの完了条件 |
| プロジェクト | 主リポジトリ 1 つとサブリポジトリの集まり。リポジトリが 1 本だけのときもその場合として含む | プロジェクト |

- 「アーキテクチャ設計書」はこの文書では常に「エピックのアーキテクチャ設計書」を指す。Issue ごとの設計（`issue-<番号>-design.md`）は「設計文書」と呼び分ける
- 「アーキテクチャ設計書」を選んだのは、arc42（アーキテクチャ文書のテンプレート）が目標・制約・用語・横断の概念・ADR を 1 つの文書に持ち、この文書の必須セクションと同じ範囲だからである。Kiro の steering はリポジトリに常に効く文脈で、エピックの単位で閉じないため採らない。選んだ理由の全文は ADR（`issue-3600-design-decisions.md`）に置く
- 「DoD」はエピックの単位の完了の判定にだけ使う。Issue ごとの条件は「受け入れ条件」と呼び分ける
- 「計画」は常に「並列の計画」を指し、実装計画とは呼び分ける
- 「通知」は常にアーキテクチャ設計書の変更通知を指す

## 受け入れ条件

- [ ] 1. 3 レーン規模の作業を指示するプロンプトを `claude -p` で渡すと、エピックのエントリポイントへ回りアーキテクチャ設計書を書く。1 スプリントで 1 レーンの作業のプロンプトでは回らない（足す前と後で比べ、PR のコメントに残す）
- [ ] 2. アーキテクチャ設計書の必須セクションが空の並列の計画は、起動前チェックがレーンを起動せず、空のセクションの名前を出して 0 以外の終了コードで落ちる。必須セクションがそろえば同じ計画が起動する
- [ ] 3. アーキテクチャ設計書のコントラクトの表と実装が食い違う Pull Request を CI のコントラクトテストが落とし、食い違う項目の名前を出す。食い違いの無い Pull Request は通る
- [ ] 4. エピックの DoD を持つ並列の計画は、全レーンが止まっても DoD の項目が残っていれば終了と判定されない。DoD の項目がすべて満たされたときに終了と判定される
- [ ] 5. `status` の出力に、エピックの DoD の項目ごとの満たした・残りと、満たした件数 / 全件数が出る
- [ ] 6. アーキテクチャ設計書を変更する Pull Request がマージされると、その変更の触るファイルと重なるファイルを触るレーンに通知が届く（止まっているレーンには再開のときに読む未読の通知として残る）。重ならないレーンには届かない
- [ ] 7. 規模の手がかりが無い Issue かプロンプトは 1 スプリントとして扱われ、判定の理由が記録に残る
- [ ] 8. アーキテクチャ設計書のパスと DoD の欄を持たない並列の計画は、今と同じく起動前チェックを通り、全レーンの停止で終了と判定される（退行しない）
- [ ] 9. 承認ゲートの数が増えない（設計承認ゲートとリリース承認ゲートの 2 つ）。新しい Skill が増えない（`plugins/ndf-next/manifests/` の行数が変わらない）
- [ ] 10. 用語集に「エピック」があり、「プロジェクト」が主リポジトリとサブリポジトリの集まりの意味だけで載る
- [ ] 11. Skill の本文の増分が全体で 10 行以内で、各 `SKILL.md` が 500 行の上限に収まる
- [ ] 12. 設計文書に nd-factory の画面構成への影響の節があり、エピックが現れる Factory のオブジェクトと画面ごとに、足すもの・変えるもの・変えないものが表で載る
- [ ] 13. 設計文書 4 本とこの設計 PR で用語集に足す行に、直訳の和語（土台・印・版・副命令・進行表・宣言・知らせ・雛形）が説明の語として残らない。NDF の既存の用語集の語は、初出で括弧に添える形でだけ現れる（`document-style` のセルフチェック（直訳の和語）と `grep` の結果を設計 PR のコメントに残す。原文の引用は除く）

## 非機能の条件

| 大項目 | 条件 |
