# #3618 の決定の記録

頭の設計文書は [issue-3618-design.md](issue-3618-design.md) にある。番号（`STD1`・`PRD1`・`LIB1`・不変条件 `I1` など）はその文書の表を指す。

## 決定の記録

### 決定 1: 製品の約束を NDF を作らないリポジトリの判定へ持ち込まないため、製品の約束を共通原則の隣へ移さず、ai-plugins の MVV の Value 4 に「受け付ける値を減らさない」を足す

共通原則は、NDF を使うすべてのリポジトリの MVV 判定に本文全体が入る（`lib/project_mvv.block`）。製品の約束（ai-plugins の MVV の Value 1〜14）をそこへ移すと、nd-factory のように自分の MVV を持つリポジトリの判定にも、NDF の振る舞いの基準（正規化・責務の分け方など）が上位の基準として入り、そのリポジトリの判定の結果を変える。製品の約束を読む必要があるのは NDF を変える設計だけで、それは ai-plugins の中でだけ起きる。

ai-plugins の MVV（版 7）は、製品の約束（「NDF が利用者に届ける価値」の Value 1〜14）と開発の基準（Value 15）をすでに節で分けている。#3596 で足りなかったのは、Value 4 が「設定か引数で受ける」までを書き、「今受け付けている値を減らさない」を書いていないことである（基準値: 助言の MVV 判定の `basis` に Value 4 が無い）。Value 4 に 1 行を足す（改訂の文 M1）。

製品の約束を ndf-next の中の文書へ移す形も採らない。置き場が変わっても、判定へ渡るのは ai-plugins の中の判定だけで、効き目が変わらないためである。

根拠: Value 4 / Value 2 / Value 11（MVV 版 7）

### 決定 2: 受け口を減らす設計を必ず人が見るため、レッドラインを ai-plugins の MVV の P2 として足し、共通原則には足さない

受け口を減らす操作は、NDF の設定のスキーマとリリース方式の表を変えるリポジトリ、つまり ai-plugins の中でだけ起きる。共通原則の C の表はすべてのリポジトリで外せない操作の一覧で、どのリポジトリでも起こりうる操作（秘密・認証・データ・戻せない操作など）を持つ。そこへ 1 つのリポジトリでしか起きない行を足すと、すべてのリポジトリの判定の材料が増え、効くのは ai-plugins だけである。ai-plugins の MVV には、同じ性質の P1（取得元・版の規則を変える）がすでにある。P2 をその隣に置く（改訂の文 M2）。

共通原則は改訂しない（受け入れ条件 2 の「改訂が無い理由」）。共通原則の「人と AI の対話」は、承認を求める前に影響を示すことをすでに求めている。#3596 で影響が示されなかった（要求の事実 7）のは、影響を書く欄が設計文書に無かったためで、それは決定 3 の表が埋める。

根拠: C7 / P1 / Value 2 / Value 4（MVV 版 7）

### 決定 3: 振る舞いの表を、作るものを使う側のリポジトリがあるときだけ求めるため、代表のリポジトリの設定（`.ndf/design.json`）を置いたリポジトリでだけ設計の検査が表を求める

代表のリポジトリでの振る舞いは、作るものを使う側のリポジトリがあるとき（プラグイン・ライブラリ・SDK）にだけ意味を持つ。nd-factory の Web の機能の設計に「代表のリポジトリ」の表を求めると、書くことの無い欄が全リポジトリの設計に増える。表を求めること自体が ai-plugins の事情であり、この Issue が防ぐ混入と同じ形になる。

そこで、代表のリポジトリの種類と名指す番号を設定に置き、設定があるときだけ規則 `repo_scope_missing` を働かせる（I1・I3）。設定はスキーマで形を確かめ、壊れていれば推して進めず終了コード 2 で止める（I4）。検査は既存の `design-survey.py` に規則として足し、表と節を読む既存の部品（LIB1）を使う。設計のプランは `survey-check` で終了コード 1 を直しの worker へ渡す既存の流れを持つため、新しいステップは足さない。

規則を当てるのは頭の設計文書（`issue-<番号>-design.md`）だけである。`light` と `operation` は頭の設計文書を書かないため当たらず、それらの設計は後方互換の観点（決定 6）と MVV 判定の P2（決定 2）が見る。

- 作り方: 自前で作る
- 比べた候補: LIB1 / LIB2 / PRD3

根拠: Value 4 / Value 3 / Value 11（MVV 版 7）

### 決定 4: 使えなくなるものを承認する人へ届けるため、振る舞いの表の「使えなくなるもの」が `無し` 以外の行を持つ設計は、人へ残す判断に設定の番号を持つ行が無いと通さない

#3596 では、develop を使うリポジトリへの影響が「未確認のまま残ること」の 1 行に回り、人へ残す判断の表に載らなかった（要求の事実 3）。言語モデルの判定（MVV 判定・レビュー）だけに頼ると、名指されない影響は実行ごとに拾われたり拾われなかったりする。表の列「使えなくなるもの」と人へ残す判断の番号を、決まった検査で結ぶ（規則 `repo_loss_unrouted`。I2）。番号は設定の `redline` から読み、ai-plugins では P2 になる。

これで、助言の MVV 判定が走らなかった設計承認（要求の未決 1、#3596 の事実 6）でも、使えなくなるものの行は人へ残す判断に載って承認資料に届く。判定が走ったかを承認ゲートの前に確かめる工程は足さない（I6）。

- 作り方: 自前で作る
- 比べた候補: LIB1 / STD1 / STD2

根拠: Value 1 / Value 13 / C7（MVV 版 7）

### 決定 5: 運用の方針を製品の仕様として書かないため、要求と起票のテンプレートに、方針を「このリポジトリの運用の決まり（設定の値）」と「作るものの振る舞い」に分ける節を該当時で足す

#3596 の起点は、利用者の「ai-plugins は GitHub flow にする」という運用の方針を、起票者が NDF の製品の仕様として書いたことである（要求の事実 1）。依頼に運用の方針が含まれるとき、要求の書き手がそれをどちらに置くかを 2 列の表で書く。方針の無い依頼では節を作らない（該当時）。起票の項目は `issue-items.json` に `policy_split` を足し、`need` は「運用」「機能」で該当時、ほかは不要とする。

表の列名は「NDF の振る舞い」ではなく「作るものの振る舞い」にする。nd-factory のような利用者のリポジトリでも、運用の決まり（`qa/dev` を起点にする）と作るもの（Factory の機能）を分ける同じ形で使えるためである。

根拠: Value 4 / Value 14（MVV 版 7）

### 決定 6: レビューで受け口の減少を問うため、cross-review の `design` の観点に後方互換の 1 行を足し、ラウンドと CLI の数は変えない

足す行は「この設計の後に、利用者が今の設定で選べている値・運用・リリースの形のうち、受け付けられなくなるもの・既定が変わるものがあるか。あれば設計文書の人へ残す判断に載っているか。代表のリポジトリの設定があるときは、種類ごとに確かめる」の 1 行である。後方互換はどのリポジトリの設計にも当たる一般の観点（STD1）で、設定に依らず働かせる。観点は既存の `DESIGN_REVIEW_TEMPLATE` の文に足すだけで、分類・ラウンド・起動する CLI は変わらない（要求の非機能の条件）。

観点の文を照合するテストは書かない（`AGENTS.md` の DON'T）。効き目は受け入れ条件 13 の記録（「受け入れ条件 7 の確かめ」の E）で確かめる。

根拠: Value 4 / Value 2（MVV 版 7）

### 決定 7: 検査を 2 か所で作らないため、受け口の減少を落とす CI の検査・許可リスト・CI のジョブは #3617 が持ち、この Issue は受け口の語と設計の側の欄を持つ

数える集合（リリース方式の表の行・`delivery` の種類・リリースの形）は #3617 の受け入れ条件 5〜7 が定める。この Issue はその集合を後方互換の観点の例として参照するだけで、写さない。設計の検査（この Issue）は設計文書を、#3617 の検査は実装の差分を見るため、同じ事実を 2 か所で判定しない。

根拠: Value 11（MVV 版 7）

### 決定 8: 試走の範囲の持ち主を 1 つにするため、代表のリポジトリでの試走の実行は #3411 が持ち、この Issue は加える種類と確かめる項目を決めてレーン lr-t2 へリクエストで渡す

#3411 は ndf-next だけで 1 スプリントを流す試走を持つ。試走に代表のリポジトリを加えるかは #3411 の本文の改訂で、#3411 の持ち主が決める（要求の前提 4）。この Issue は、加える種類（頭の設計文書の「代表のリポジトリでの振る舞い」の 4 行）と、そのリポジトリで確かめる 3 項目（設定を読んだ工程が止まらない・設定の値がリリース方式の表に合う・設計の検査が今と同じ結果になる）を、実装でリクエストに書いて送る。#3411 の答えは「未確認のまま残ること」に置く。

根拠: Value 11 / Value 15（MVV 版 7）

### 決定 9: 11.0 の入れ替えの時点で ndf-next に入っているため、今の NDF へ入れ、ndf-next の Skill のコピーにも同じ変更を入れ、スクリプトの分は直しの棚卸しで移す子へ渡す

ndf-next には、設計の検査（`design-survey.py`）と cross-review の観点（`review_focus.py`）の移った先がまだ無い（機能の対応表で行き先は M7・M5、`trial` は `failed`）。ndf-next だけに入れると、入れる先が無い。今の NDF に入れれば、ai-plugins で NDF を変える設計（この防ぎが要る場所）に今すぐ効く。

ndf-next への渡し方は、作り直しの間に旧いプラグインへ入った直しを持つ既存の表（`parity/fixes.json`）に行を足す形にする。行き先は設計の検査と設定のスキーマが M7、観点が M5、起票の項目が M6 である。実装の時点で行き先の子が閉じていれば、追補の単位（`M7+` など。#3395 の決定 110）を行き先にする。Skill の本文（テンプレート・分類の説明）は ndf-next にコピーがあるため、同じ変更を直に入れる。入れ替え（S2）は直しの棚卸しの全行が移ったことを確かめるため、11.0 の時点で ndf-next に入る。

#3411 の I2（`plugins/ndf/` を変えない）は試走の子 T2 の受け入れ条件で、この Issue には当たらない。作り直しの間の今の NDF への直しは `fixes.json` が受け付ける既存の経路である。

根拠: Value 5 / Value 11 / Value 15（MVV 版 7）

### 決定 10: 用語を 1 語 1 意味に保つため、要求の工程で用語集に足した「受け口」をそのまま使い、「代表のリポジトリ」の意味を設定に結んで一般化する

「受け口」は要求の工程で用語集に足した語で、意味に SemVer の後方互換を壊す変更（breaking change）の 1 つであることを足す。別の語へ言い換えると、要求と設計で 2 つの語が同じものを指す。「代表のリポジトリ」は要求の工程で「ai-plugins 以外のリポジトリ」と書いたが、設定で有効にする形（決定 3）では、どのリポジトリも自分の代表のリポジトリを持てる。意味を「設定に書く、このリポジトリの作るものを使う側のリポジトリの種類」へ変え、汎用の欄の名前「このリポジトリだけの事情」を足す。ai-plugins の設計では「ai-plugins だけの事情」と書く。

根拠: Value 14（MVV 版 7）

### 決定 11: 既存の設計文書と進行中の設計を落とさないため、規則は設定を置いた後に設計の検査を通る設計にだけ当て、移行の扱いを足さない

設計の検査は、設計のプランが書いている設計文書に対してだけ走る（ステップ `survey-check` の `--issue <番号>`）。マージ済みの設計文書を CI が検査し直す経路は無い。ai-plugins に設定を置くのは実装の Pull Request で、その後に設計の検査を通る設計だけが表を求められる。同じ時期に進む #3617 は、自分の受け入れ条件 24 で同じ表を持つ。設定を置かない利用者のリポジトリは、結果が今と同じである（I3）。

根拠: Value 4 / Value 5（MVV 版 7）

### 決定 12: 作り直しの子の表で順番と依存を照らせるため、この Issue を子 G1（順番 9・レーン lguard・`needs` は S1a と X3）として足し、S2 の `needs` に G1 を足す

この Issue は ndf-next の `src/` のモジュールを足さない（`packages` は空）。ndf-next で触るのは Skill のコピー（S1a が置いた）と直しの棚卸し（X3 が置いた）で、どちらも閉じた子が置いたものである。そのため `needs` は S1a と X3、順番は先に要る子の最大（S1a の 8）に 1 を足した 9 にする。レーンはこの Issue を流すレーン lguard で、同じレーン・同じ順番の閉じていない子は G1 だけである（IG2 の上限 2 本）。11.0 の入れ替えの前に入っていることを表で縛るため、S2 の `needs` に G1 を足す（S2 の順番 10 は G1 の 9 より大きい）。

記号は、既存の記号（X・D・C・T・AD・P・M・S）と、レッドラインの番号の頭文字（C・P・R）と重ならない G（汎用性の守り）にする。#1142 の本文の子の表と `children.json` への追加は実装で行い、`ndf check` の規則 `child-deps` で確かめる（受け入れ条件 14）。

根拠: Value 11 / Value 15（MVV 版 7）
