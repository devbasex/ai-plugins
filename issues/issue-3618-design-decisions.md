# #3618 の決定の記録

頭の設計文書は [issue-3618-design.md](issue-3618-design.md) にある。番号（`STD1`・`PRD1`・`LIB1`・不変条件 `I1` など）はその文書の表を指す。

## 決定の記録

### 決定 1: 製品の約束を NDF を作らないリポジトリの判定へ持ち込まないため、製品の約束を共通原則の隣へ移さず、ai-plugins の MVV の Value 4 に「代表のリポジトリの種類をどれも扱えることを保つ」を足す

共通原則は、NDF を使うすべてのリポジトリの MVV 判定に本文全体が入る（`lib/project_mvv.block`）。製品の約束（ai-plugins の MVV の Value 1〜14）をそこへ移すと、nd-factory のように自分の MVV を持つリポジトリの判定にも入る。NDF の振る舞いの基準（正規化・責務の分け方など）が上位の基準として入り、そのリポジトリの判定の結果を変える。製品の約束を読む必要があるのは NDF を変える設計だけで、それは ai-plugins の中でだけ起きる。

ai-plugins の MVV（版 7）は、製品の約束（「NDF が利用者に届ける価値」の Value 1〜14）と開発の基準（Value 15）をすでに節で分けている。#3596 で足りなかったのは Value 4 の文言である。Value 4 は「設定か引数で受ける」までを書き、「どの種類のリポジトリも扱えることを保つ」を書いていない（基準値: 助言の MVV 判定の `basis` に Value 4 が無い）。#3596 で失われかけたのは旧い値ではなく、develop を経て本番へ出す運用とプラグイン以外のリリースの形という、リポジトリの種類を扱う手段である。Value 4 に、種類をどれも扱えることを保つ 1 行と、普及のフェーズまで後方互換を求めない 1 行を足す（改訂の文 M1）。2 行目を足すのは、1 行目を「値を減らさない」と読み広げて、改名や作り直しを人へ戻す解釈を防ぐためである。

製品の約束を ndf-next の中の文書へ移す形も採らない。置き場が変わっても、判定へ渡るのは ai-plugins の中の判定だけで、効き目が変わらないためである。

根拠: Value 4 / Value 2 / Value 11（MVV 版 7）

### 決定 2: 代表のリポジトリの種類を扱えなくする設計を必ず人が見るため、レッドラインを ai-plugins の MVV の P2 として足し、共通原則には足さない

作るものを使う側のリポジトリの種類のどれかを扱えなくすることは、どのリポジトリでも起きうる。nd-factory なら Factory の利用の形、モバイルアプリならアプリのリリースの形である。ただしどの種類を扱えることを保ち、どれを人の承認に回すかはリポジトリごとに違い、共通原則の C の表の 1 行（どのリポジトリでも同じ意味を持つ操作。秘密・認証・データ・戻せない操作など）では名指せない。そこで、各リポジトリが自分のプロジェクト MVV の「このプロジェクトが足す操作」の表に番号を置き、代表のリポジトリの設定の `redline` でその番号を名指す（決定 3・10）。

ai-plugins では、NDF が扱えることを保つ種類は代表のリポジトリの 3 種（Web サービス・モバイルアプリ・業務文書だけ）で、それらを扱う手段は NDF のサポートする選択肢（設定のスキーマ・リリース方式の表・`delivery` の種類）にある。その選択肢を代わりの形なしに無くす変更は、NDF を作る ai-plugins の中でだけ起きる。ai-plugins の MVV には、利用者全員に効く同じ性質の P1（取得元・版の規則を変える）がすでにある。P2 をその隣に置く（改訂の文 M2）。

P2 の単位はリポジトリの種類で、値ではない。設定のキーと値の改名・作り直し・既定の変更・代わりの形のある値の削除は、同じ種類が別の形で扱えるため P2 に当たらない。普及のフェーズに入るまで NDF は後方互換を求めず（利用者の方針、2026-11-16）、これらを人へ戻すと、きれいな最終形へ移る変更のたびに承認が要り、Value 5（速く届く）を損なう。SemVer（STD1）と Kubernetes の非推奨ポリシー（STD2）の後方互換の規則は、普及のフェーズまで当てない。

共通原則は改訂しない（受け入れ条件 2 の「改訂が無い理由」）。共通原則の「人と AI の対話」は、承認を求める前に影響を示すことをすでに求めている。#3596 で影響が示されなかった（要求の事実 7）のは、影響を書く欄が設計文書に無かったためで、それは決定 3 の表が埋める。

根拠: C7 / P1 / Value 2 / Value 4（MVV 版 7）

### 決定 3: 振る舞いの表を、作るものを使う側のリポジトリがあるときだけ求めるため、代表のリポジトリの設定（`.ndf/design.json`）を置いたリポジトリでだけ設計の検査が表を求める

代表のリポジトリでの振る舞いは、作るものを使う側のリポジトリがあるとき（プラグイン・ライブラリ・SDK）にだけ意味を持つ。nd-factory の Web の機能の設計に「代表のリポジトリ」の表を求めると、書くことの無い欄が全リポジトリの設計に増える。表を求めること自体が ai-plugins の事情であり、この Issue が防ぐ混入と同じ形になる。

そこで、代表のリポジトリの種類と名指す番号を設定に置き、設定があるときだけ規則 `repo_scope_missing` を働かせる（I1・I3）。

設定を置いたリポジトリの中でも、使う側へ公開するインタフェースを持つのは一部のディレクトリだけのことがある。ai-plugins では NDF のサポートする選択肢は `plugins/ndf/`・`plugins/ndf-next/`・`.claude-plugin/marketplace.json` にある。`plugins/mcp/`・`plugins/playwright-kit/` の設計には書くことが無い。リポジトリ全体に当てると、決定の冒頭で避けた「書くことの無い欄が増える」形がリポジトリの中で起きる。そこで設定に `paths`（glob の配列）を持たせ、頭の設計文書の「設計の結果」の表の「触るファイル」のどれかが当たる設計だけに 2 規則を当てる。`paths` を省いたときはリポジトリ全体に当てる。触るファイルは設計を書いた時点で頭の設計文書にあり、決まった検査で読める。設定はスキーマで形を確かめ、壊れていれば推して進めず終了コード 2 で止める（I4）。種類が空の配列もスキーマに合わない設定として扱う。種類を求めないリポジトリは設定を置かなければよく、空の配列に「設定なし」の意味を重ねない。検査は既存の `design-survey.py` に規則として足し、表と節を読む既存の部品（LIB1）を使う。設計のプランは `survey-check` で終了コード 1 を直しの worker へ渡す既存の流れを持つため、新しいステップは足さない。

規則を当てるのは頭の設計文書（`issue-<番号>-design.md`）だけである。`light` と `operation` は頭の設計文書を書かないため当たらず、それらの設計は汎用性の観点（決定 6）と MVV 判定の P2（決定 2）が見る。

- 作り方: 自前で作る
- 比べた候補: LIB1 / LIB2 / PRD3

根拠: Value 4 / Value 3 / Value 11（MVV 版 7）

### 決定 4: 扱えなくなる種類を承認する人へ届けるため、振る舞いの表の「この種類で扱えなくなること」が `無し` 以外の行を持つ設計は、人へ残す判断に設定の番号を持つ行が無いと通さない

#3596 では、develop を使うリポジトリへの影響が「未確認のまま残ること」の 1 行に回り、人へ残す判断の表に載らなかった（要求の事実 3）。言語モデルの判定（MVV 判定・レビュー）だけに頼ると、名指されない影響は実行ごとに拾われたり拾われなかったりする。表の列「この種類で扱えなくなること」と人へ残す判断の番号を、決まった検査で結ぶ（規則 `repo_loss_unrouted`。I2）。番号は設定の `redline` から読み、ai-plugins では P2 になる。

列の判定の単位はリポジトリの種類である。値を改名・作り直しても、同じ種類が改名後の設定か別の選択肢で同じ運用・リリース・テストを続けられるなら `無し` と書く（例: `promotion: selected` を `release_strategy: release_branch` へ改名しても、承認したスプリントだけを出す運用は続けられる）。値の単位で書かせると、普及のフェーズまで求めない後方互換の崩れが人へ残す判断に毎回載り、汎用性の後退が埋もれる。代わりの形があるかは決まった検査では判定できないため、検査は書かれたセルが `無し` で始まるかだけを見て、判定の中身は cross-review（決定 6）と MVV 判定（決定 2）が見る。

これで、助言の MVV 判定が走らなかった設計承認（要求の未決 1、#3596 の事実 6）でも、扱えなくなる種類の行は人へ残す判断に載って承認資料に届く。判定が走ったかを承認ゲートの前に確かめる工程は足さない（I6）。

- 作り方: 自前で作る
- 比べた候補: LIB1 / PRD3

根拠: Value 1 / Value 5 / Value 13 / C7（MVV 版 7）

### 決定 5: 運用の方針を製品の仕様として書かないため、要求と起票のテンプレートに、方針を「このリポジトリの運用の決まり（設定の値）」と「作るものの振る舞い」に分ける節を該当時で足す

#3596 の起点は、利用者の「ai-plugins は GitHub flow にする」という運用の方針を、起票者が NDF の製品の仕様として書いたことである（要求の事実 1）。依頼に運用の方針が含まれるとき、要求の書き手がそれをどちらに置くかを 2 列の表で書く。方針の無い依頼では節を作らない（該当時）。起票の項目は `issue-items.json` に `policy_split` を足し、`need` は「運用」「機能」で該当時、ほかは不要とする。

表の列名は「NDF の振る舞い」ではなく「作るものの振る舞い」にする。nd-factory のような利用者のリポジトリでも、運用の決まり（`qa/dev` を起点にする）と作るもの（Factory の機能）を分ける同じ形で使えるためである。

根拠: Value 4 / Value 14（MVV 版 7）

### 決定 6: レビューで汎用性の後退を問うため、cross-review の `design` の観点に汎用性の 1 行を足し、ラウンドと CLI の数は変えない

足す行は「この設計の後に、代表のリポジトリの種類（作るものを使う側のリポジトリの種類）のうち、扱えなくなるもの（代わりの形の無い運用・リリースの形・ツール）があるか。あれば設計文書の人へ残す判断に載っているか。代表のリポジトリの設定があるときは、種類ごとに確かめる。設定のキーと値の改名・作り直し・既定の変更は、同じ種類が別の形で扱えるなら指摘しない」の 1 行である。汎用性はどのリポジトリの設計にも当たる一般の観点で、設定に依らず働かせる。NDF の設定だけを問う文にすると、nd-factory の利用の形やモバイルアプリのリリースの形を扱えなくする設計に観点が当たらず、どのリポジトリにも当たるという前提と食い違う。改名・作り直しを指摘しない一文は、普及のフェーズまで後方互換を求めない方針（決定 2）に合わせ、レビュー担当が値の減少を一律に指摘してラウンドを増やすことを防ぐ。観点は既存の `DESIGN_REVIEW_TEMPLATE` の文に足すだけで、分類・ラウンド・起動する CLI は変わらない（要求の非機能の条件）。

観点の文を照合するテストは書かない（`AGENTS.md` の DON'T）。効き目は受け入れ条件 13 の記録（「受け入れ条件 7 の確かめ」の E）で確かめる。

根拠: Value 4 / Value 2（MVV 版 7）

### 決定 7: 検査を 2 か所で作らないため、代表のリポジトリの種類に要る選択肢を代わりの形なしに無くす変更を落とす CI の検査・許可リスト・CI のジョブは #3617 が持ち、この Issue は汎用性の後退の語と設計の側の欄を持つ

数える集合（リリース方式の表の行・`delivery` の種類・リリースの形）は #3617 の受け入れ条件 5〜7 が定める。この Issue はその集合を汎用性の観点の例として参照するだけで、写さない。設計の検査（この Issue）は設計文書を、#3617 の検査は実装の差分を見るため、同じ事実を 2 か所で判定しない。

根拠: Value 11（MVV 版 7）

### 決定 8: 試走の範囲の持ち主を 1 つにするため、代表のリポジトリでの試走の実行は #3411 が持ち、この Issue は加える種類と確かめる項目を決めてレーン lr-t2 へリクエストで渡す

#3411 は ndf-next だけで 1 スプリントを流す試走を持つ。試走に代表のリポジトリを加えるかは #3411 の本文の改訂で、#3411 の持ち主が決める（要求の前提 4）。この Issue は、加える種類と、そのリポジトリで確かめる 3 項目を、実装でリクエストに書いて送る。加える種類は頭の設計文書の「代表のリポジトリでの振る舞い」の 4 行、3 項目は「設定を読んだ工程が止まらない」「設定の値がリリース方式の表に合う」「設計の検査が今と同じ結果になる」である。#3411 の答えは「未確認のまま残ること」に置く。

根拠: Value 11 / Value 15（MVV 版 7）

### 決定 9: 11.0 の入れ替えの時点で ndf-next に入っているため、今の NDF へ入れ、ndf-next の Skill のコピーにも同じ変更を入れ、スクリプトの分は直しの棚卸しで移す子へ渡す

ndf-next には、設計の検査（`design-survey.py`）と cross-review の観点（`review_focus.py`）の移った先がまだ無い。機能の対応表で行き先は M7・M5 で、`trial` は `failed` である。ndf-next だけに入れると、入れる先が無い。今の NDF に入れれば、ai-plugins で NDF を変える設計（この防ぎが要る場所）に今すぐ効く。

ndf-next への渡し方は、作り直しの間に旧いプラグインへ入った直しを持つ既存の表（`parity/fixes.json`）に行を足す形にする。行き先は設計の検査と設定のスキーマが M7、観点が M5、起票の項目が M6 である。実装の時点で行き先の子が閉じていれば、追補の単位（`M7+` など。#3395 の決定 110）を行き先にする。Skill の本文（テンプレート・分類の説明）は ndf-next にコピーがあるため、同じ変更を直に入れる。入れ替え（S2）は直しの棚卸しの全行が移ったことを確かめるため、11.0 の時点で ndf-next に入る。

#3411 の I2（`plugins/ndf/` を変えない）は試走の子 T2 の受け入れ条件で、この Issue には当たらない。作り直しの間の今の NDF への直しは `fixes.json` が受け付ける既存の経路である。

根拠: Value 5 / Value 11 / Value 15（MVV 版 7）

### 決定 10: 用語を 1 語 1 意味に保ち業界の語にそろえるため、要求の工程で足した直訳の和語を廃止し、「汎用性の後退」「サポートする選択肢」「代表のリポジトリの種類」を足し、「代表のリポジトリ」の意味を種類に結ぶ

要求の工程で用語集に足した、設定が受け付ける値の種類を指す語は直訳の和語で、業界の語ではない（`document-style` のルール 11）。さらに守る単位を値に置く語で、守る対象をリポジトリの種類とする決定 2・4 と食い違う。用語集から廃止し、設定で選べる値は業界の語「サポートする選択肢」（supported options）、守る対象は「汎用性の後退」で書く。どちらも要求の用語の表と同じ意味である。

「代表のリポジトリ」は要求の工程で「ai-plugins 以外のリポジトリ」と書いたが、設定で有効にする形（決定 3）では、どのリポジトリも自分の代表のリポジトリを持てる。種類（設定の `kinds` に書く名前）を「代表のリポジトリの種類」として分け、「代表のリポジトリ」はその種類ごとに選ぶ実物か仮のリポジトリを指す。汎用の欄の名前「このリポジトリだけの事情」はそのまま使い、ai-plugins の設計では「ai-plugins だけの事情」と書く。ai-plugins の外のリポジトリが設定を置くときは、名指す番号を自分のプロジェクト MVV の「このプロジェクトが足す操作」の表に足す（決定 2）。

#3613 の対応表（W3「設定」・W9「リリース方式」）の語と、設定のキーの改名（`promotion` → `release_strategy`）に合わせ、今のキーを書く箇所には新しい名前を添える。

根拠: Value 14（MVV 版 7）

### 決定 11: 進行中の設計のプランを止めないため、設定のマージの後に設計の検査を打ち直す進行中の設計は、既存の直しのラウンドで表を足して通し、検査から外す扱いは足さない

設計の検査は、設計のプランが書いている設計文書に対してだけ走る（ステップ `survey-check` の `--issue <番号>`）。マージ済みの設計文書を CI が検査し直す経路は無い。ai-plugins に設定を置くのは実装の Pull Request で、その後に設計の検査を通る設計が表を求められる。

並列の計画で設計を進めているレーンが、設定のマージの後に直しのラウンドで `survey-check` を打ち直すと、表が無ければ規則 `repo_scope_missing` で終了コード 1 になる。終了コード 1 は、設計のプランが直しの worker へ渡す既存の流れで、プランは止まらない（止まるのは終了コード 2 だけ）。直しの worker は直しの指示（`procedures.py` の `survey_steps`）に従って表を足し、次の検査で通る。要求の未決 2 が避けたい「進行中のスプリントの設計の検査が落ちる」状態は、プランが止まることと読み、この扱いで避ける。費用は直しのラウンドが 1 回増えることである。

進行中の設計を検査から外す扱い（設定に適用の開始時点を持たせる、設定のマージより前に書き始めた設計文書を除く など）は採らない。外した設計には、#3617 のように NDF のサポートする選択肢を変える並行の設計が含まれ、この Issue が防ぎたい設計がちょうど検査を通らずに設計承認へ届くためである。同じ時期に進む #3617 は、自分の受け入れ条件 24 で同じ表を持つ。設定を置かない利用者のリポジトリと、触るファイルが `paths` に当たらない設計は、結果が今と同じである（I3）。
