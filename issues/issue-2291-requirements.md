## 何が起きたか

## 目的

- テストを使う工程（リファクタリングの着手前のテスト・最終ゲート・完了判定）が、時間の枠のほとんどを全体テストに使わずに本来の作業へ時間を回せるようにする
- PR ごとの CI の待ちを縮め、1 回の配布までの待ちを減らす
- テストの数を、守る振る舞いに見合う数まで減らし、保守の費用を下げる

## 前提

- 前提 1: 手元で測るマシンは、この開発コンテナ（CPU 8 個・メモリ 30 GB）である。開始時の 1 分の load average が 8 以下のときに測り、その値を記録に添える。8 を超える負荷の下で測った値は参考として別に残し、受け入れ条件 1 の判定に使わない
- 前提 2: 並列の数は今の宣言の値のまま（pytest の `-n 4`）にする。並列の数を変えるのは受け入れ条件の手段に含めない
- 前提 3: 「3 分」は壁時計の 180 秒で、`.ndf/project.json` の `test.suites` の `command` を宣言の順に 1 本ずつ流し、最初の起動から最後の終了までを測る。`uv` の仮想環境は作成済みの状態から測る（作成の時間は数えない）。factory の suite のコマンドに含まれる `npm ci` の時間は数える
- 前提 4: https://github.com/devbasex/ai-plugins/issues/2285 の 1 項目目（打ち切りで止まったときに作業場所の持ち主の記録へ終わった時刻を書く）は、この課題では扱わず #2285 に残す。この課題が扱うのは #2285 の 2 項目目（子のプロセス）だけである
- 前提 5: https://github.com/devbasex/ai-plugins/issues/2287 （閉じた課題）の「工程の時間の枠の決め方」は、この課題では変えない。全体テストが縮むことで枠に収まるようにする

## 対象範囲

含む:
- 意味の薄いテストを削る基準を文書にし、基準に当たるテストを消す・まとめる（#2204）
- 遅いテストを速くする（待ちの短縮・重い準備の共有など。手段は設計で決める）
- PR の pytest の CI を 3 分以内にし、同じ PR への新しい push で古い実行を止める（#2154）
- 全体テストを上限で打ち切ったとき、テストが起こした子孫のプロセスを残さない（#2285 の 2 項目目）

含まない:
- 並列の数を上げて 3 分に入れること（前提 2）
- テストを既定の実行から外して 3 分に入れること（受け入れ条件 5）
- 作業場所の持ち主の記録に終わった時刻を書くこと（#2285 の 1 項目目。前提 4）
- リファクタリングの工程の時間の枠の決め方の変更（前提 5）
- テストの対象のコード（プラグインの振る舞い）の変更。テストを速くするためにテストの対象を変える必要が出たら、その変更は止めて設計で扱いを決める
