# #933: cross-refactoring を想定最大時間に収める 1 回の計画実行へ改める — 要求と受け入れ条件

設計は [issue-933-design.md](issue-933-design.md)、決定の理由は
[issue-933-design-decisions.md](issue-933-design-decisions.md) にある。この文書は「何を満たすか」だけを扱う。

マイルストーンは「17 トークン消費の削減」。版はマイルストーン 26 の 10.17.x（PATCH）で、版数は配布の工程が決める（`release`）。

## 例: PR #917 の構造改善を、変えた後の形で通すと

今（v10.17.5）の実測（2026-09-23、PR #917）:

1. テスト整備ラウンドを 2 回回す。参加者 3 者が網羅的にテストを提案し、毎回上限の 5 件を採って適用する。**ここまでで約 36 分**
2. 提案ラウンドを 3 回回す。毎回上限の 5 件を採り、群に分けて輪番の担当が適用・検証・修正する
3. 5 ラウンド・25 項目・**約 71 分**で、`--max-outer-rounds` の上限で止まる。見送り 18 件の理由はすべて上限である。**収束したのか時間が足りなかったのかを、利用者は時間の側から制御できない**

変えた後（`--budget-minutes 60`。既定と同じ）:

1. 参加者の全員が 1 度だけ、多面的に提案する（並列。数分）
2. 選ばれた 1 ランタイムが計画を立てる。提案を順位付けし、配分テーブルの 1 件あたりの見積りで「60 分 − ここまでの所要 − 検証・修正の見込み」に収まる件数だけを採る。どの項目にどのテストを足すかも、ここで決める
3. 同じランタイムが、採った項目に要るテストだけを足し、項目を 1 件ずつ適用する
4. 改修した箇所に限ったテストが通るまで直す。直らない項目は項目の単位で取り消す。全体のテストは、危険の印が立ったときに限って 1 度だけ走る
5. 実績で配分テーブルを更新して終わる。見送った提案の理由は「時間」か「順位」で残る

## 依頼（原文）

> cross-refactoring を「ラウンドを上限まで回す」形から、**想定最大時間に収まる計画を 1 回だけ実行する**形へ改める（2026-09-23 利用者の指示）。
>
> 1. 引数「想定最大時間」を受け取る（既定 60 分）。所要をこの時間に収めるように計画する
> 2. ラウンド制を廃止する。次の 5 フェーズを 1 回だけ実施する: 提案 → 計画 → テスト追加 → 実装 → 検証/修正ループ
> 3. 提案フェーズ: 参加可能なすべてのランタイムに提案させる。できるだけ多面的に出すように指示する
> 4. 計画フェーズ:（以下、計画・テスト追加・実装・検証/修正ループは選ばれた 1 ランタイムが通して実行する）提案をランキングし、「想定最大時間 − これまでの所要時間 − 想定検証/修正時間」以内で終わる数の改修計画を立てる。どのテストを追加するかもここで決める
> 4a. 提案ごとの時間の見積りは、過去 10 回の種類別の履歴を集計した配分テーブルで決める。配分テーブルは保持し続ける。初回の既定値は #917 の結果
> 5. テスト追加フェーズ: 計画で決めた、提案を検証するために必要なテストだけを追加する（今のテスト整備ラウンドのような網羅の提案はしない）
> 6. 実装フェーズ: 選ばれた 1 ランタイムが実装する。計画・テスト追加・検証/修正ループも同じ 1 ランタイムが実行する（提案フェーズだけが全ランタイム）
> 7. 検証/修正ループフェーズ: このリファクタリングで改修した箇所に限定してテストを実施し、すべて pass するまでループする。全体テストは原則実施しない。危険性を察知した場合に限り 1 度だけ実施してよい（何を危険性とするかは設計で決める）
> 8. 最後に配分テーブルを更新して終了する
> 9. Jev にアクセスできる場合は、提案のランキングなど Jev を適用できる箇所はできるだけ Jev を使う（#841。`typesafe-ai/jev`、Vercel AI Gateway、鍵は `AI_GATEWAY_API_KEY`）。アクセスできなければ今までどおり LLM（選ばれたランタイム）が判断する

（#933 の本文の「変えた後」の表。設計で決めることの一覧は #933 の本文にある）

## 目的

- **所要の上限を利用者が時間で指定できるようにする。** 上限で止まるのではなく、上限に収まる計画を最初に立てる
- **テストの整備に使う時間を、採った改善項目の検証に要る分だけにする。** #917 では全体の約半分がテスト整備だった
- **見積りを実績から学ぶ。** 種類ごとの所要を実行のたびに記録し、次の計画に使う
- **判断のうち機械的に下せるものを Jev へ寄せる。** 使えない環境では今と同じくランタイムが判断する

## 前提

- 前提 1: 時間の上限は**目安の上限**であって、厳密な締め切りではない。実行中の CLI を途中で殺さない。守るのは「次の作業を始める前に、残り時間に収まるかを確かめる」ことである
- 前提 2: 提案フェーズの所要は計画の対象にしない（計画はその後に立つ）。提案フェーズの上限は監視の上限の表（`lib/limits.py` の `propose`）が持つ
- 前提 3: `--round-test` と `assess`（v10.17.5 の #880 #494）はそのまま使う。`assess` が飛ばしてよいと判定した変更では、この Skill を起動しない
- 前提 4: 最終ゲート（単独起動なら `cross-review`、工程の 1 つなら全体のテストか継続的統合）は想定最大時間の外に置く。**最終ゲートで走らせる全体のテストは内に置く**（工程の 1 つとして起動したときの全体のテストと、取り消しの後の確かめ。設計の決定 15・16）
- 前提 5: #930（cross-review のラウンドの削減）が先にマージされる。理由は 2 つある。#930 は参加者の決め方（既定の母集合から agy を外し、母集合に無い者の除外を無視する）を変え、この変更の参加者はそれに合わせる。あわせて #930 は `setup.py` / `report.py` / `prompts/apply.md` を触り、この変更が変えるファイルと重なる

## 対象範囲

含む:

- 引数の追加（想定最大時間）と、ラウンド制の引数の廃止・互換の扱い
- 5 フェーズの 1 回の実行（提案 → 計画 → テスト追加 → 実装 → 検証/修正）と、終わりの配分テーブルの更新
- 提案の雛形を多面的な提案へ変えること。テスト整備の提案の雛形（`propose-tests.md`）を廃すること
- 計画フェーズの順位付け・時間の見積り・件数の決定・足すテストの決定
- 配分テーブルと履歴の置き場所・形・集計の規則。初期値（#917 の実測）
- 検証を改修した箇所に限る規則と、全体のテストを 1 度だけ走らせる「危険の印」の条件
- 直らない項目の取り消しの単位と、ループの歯止め
- 計画以降を担う 1 ランタイムの選び方
- Jev を使う箇所・問いの形・使えるかの判定・使えないときの経路
- 状態ファイルの形の変更と、旧い形の状態ファイルの扱い（再開）
- `SKILL.md`・`docs/`・`prompts/`・呼び出し元の文書（`development-workflow` の工程表・`CLAUDE.md` の cross-refactoring の節）の改訂（実装の持ち場で行う）
- ラウンド制を確定仕様として持つ `docs/specifications/cross-refactoring-participants.md`・`cross-refactoring-round-tests-and-assess.md`・`cross-refactoring-apply-intake.md` と `docs/specifications/README.md` の索引の改訂（確定仕様化の工程で行う）
- #754 #755（適用の並列化）の前提が変わることの記録と、課題の扱いの決定

含まない:

- 最終ゲートの `cross-review` の中身（ラウンドの削減は #930 と #542 #786 が扱う）
- cross-review / cross-refactoring の駆動の bash を `scripts/` へ移すこと（#560 #870）。ただし新しい駆動は短くなるよう設計する
- 版ごとの測定の仕組み（#893）。配分テーブルの履歴は、この Skill の中だけで持つ
- Jev そのものの導入・鍵の配布（#841）。鍵があれば使い、無ければ使わない
- 提案の語彙（兆候・手法・重要度）の追加と変更
- クラス図。`refactor_lib` は関数の集まりで型を定義せず、変更が触る型が無い（決定 19）

## 用語

| 用語 | 意味 |
| --- | --- |
| 想定最大時間 | 利用者が与える時間の上限（分）。`--budget-minutes`。計画はこの中に収まるように立てる |
| フェーズ | 提案・計画・テスト追加・実装・検証/修正の 5 つ。**それぞれ 1 回だけ**行う（検証/修正の中のループを除く） |
| 実装担当 | 計画以降の 4 フェーズを通して担う 1 ランタイム |
| 種類 | 配分テーブルの行の単位。改善項目の手法（`technique`）と、テストの追加 |
| 配分テーブル | 種類ごとの 1 件あたりの所要の見積り。履歴の過去 10 回から集計する |
| 履歴 | 1 回の実行ごとに、種類ごとの件数と所要を残した記録 |
| 改修した箇所に限ったテスト | 項目が触ったファイルに対応するテストだけ。計画で項目ごとに決める |
| 危険の印 | 限ったテストでは覆えない変更を示す条件。立ったら全体のテストを 1 度だけ走らせる |

## 受け入れ条件

### 引数と既定

- [ ] AC1: `--budget-minutes N` を受け取る。省くと 60 になる。0 以下・数でない値は `init` が終了コード 4 で止める
- [ ] AC2: `--max-test-rounds` / `--max-outer-rounds` / `--max-items-per-round` を渡すと、廃止を知らせる 1 行を標準エラーへ出し、値を使わずに続ける（終了コード 0）
- [ ] AC3: `--max-fix-rounds` は「1 項目あたりの修正の上限」として残る（既定 3）

### 5 フェーズの 1 回の実行

- [ ] AC4: 1 回の実行で、提案の CLI は参加者ごとに 1 回だけ起動される。テスト整備の提案（`propose-tests`）の CLI は起動されない
- [ ] AC5: 提案の雛形は、兆候の観点を複数（少なくとも「重複」「責務の混在」「分岐の表し方」「名前」「依存の向き」「テストの書きにくさ」）挙げて、観点ごとに探すよう指示する。合計の件数の上限を提案者に示さない
- [ ] AC6: 計画・テスト追加・実装・修正の CLI は、すべて同じ 1 ランタイム（実装担当）で起動される。状態ファイルの `implementer` に 1 つだけ記録される
- [ ] AC7: 計画は、採った項目それぞれに「順位」「見積りの分」「足すテスト（無ければ空）」「限ったテストのコマンド」を持つ。状態ファイルの `plan` に残る
- [ ] AC8: 採った項目の見積り（テストの追加・実装・検証）の合計は「想定最大時間 − 計画を取り込む時点までの所要 − 控え」以下である。控えは、危険の印の全体のテスト 1 回・最終ゲートの全体のテスト 1 回（`--ci-check` が無いときだけ）・修正の起動 1 回分の和である
- [ ] AC9: 採らなかった提案は、理由（`budget` / `rank` / `duplicate` / `vocabulary` / `threshold`）とともに見送りに残る
- [ ] AC10: テスト追加で足すのは、計画が「足すテスト」を持つ項目のテストだけである。項目に紐づかないテストのコミットがあれば、そのコミットを取り消して記録に残す
- [ ] AC11: 実装は項目を計画の順位の順に 1 件ずつ行い、履歴は 1 改善項目 = 1 コミット（足すテストがある項目は 2 コミット）になる
- [ ] AC12: 実装の雛形には、項目ごとの着手の締め切り（時刻）が渡る。実装の取り込みの時点でコミットの無い項目は `not_done` の理由で見送りに残り、検証/修正へ進む

### 検証と修正

- [ ] AC13: 項目の検証は、その項目の限ったテストだけを走らせる。全体のテスト（`--baseline-test`）は、検証/修正の中で最大 1 回である
- [ ] AC14: 全体のテストを走らせるのは、設計が定める危険の印のどれかが立ったときだけである。走らせた理由（どの印か）が状態ファイルと報告に残る
- [ ] AC15: 1 項目の修正が `--max-fix-rounds` に達するか、残り時間が尽きたら、その項目だけを取り消す。他の項目のコミットは残る。項目の単位で戻せないとき（隣接する変更）は、今と同じく全件の取り消しへ退避し、退避したことが残る
- [ ] AC16: 検証/修正を終えた時点で、残った項目の限ったテストはすべて通っている（通っていない項目は取り消されている）
- [ ] AC16b: 危険の印の全体のテストが落ちて項目を取り消したとき、`--ci-check` が無ければ、最終ゲートは起動のされ方によらず、取り消した後の HEAD で全体のテストを 1 度走らせる。落ちたら最終ゲートの修正へ進み、通らないまま Pull Request を完了にしない

### 配分テーブル

- [ ] AC17: 実行の終わりに、種類ごとの件数と所要が履歴へ 1 件追記される。中断（終了コード 4）した実行は追記しない
- [ ] AC18: 配分テーブルは、種類ごとに履歴の直近 10 回から集計される。10 回に満たない種類は、ある分だけで集計し、1 回も無い種類は初期値を使う
- [ ] AC19: 初期値は #917 の実測から作られ、プラグインに同梱される。値の出所（#917 の記録の URL）が同じファイルに残る
- [ ] AC20: 履歴が読めない（壊れている・無い）ときは初期値で計画し、そのことを 1 行知らせて続ける

### 実装担当と Jev

- [ ] AC21: 実装担当は `--implementer NAME` で名指しでき、名指しが無ければ設計が定める規則で 1 者に決まる。再開しても変わらない
- [ ] AC22: `AI_GATEWAY_API_KEY` があり、Jev の疎通の確認が通るとき、次の 3 つは Jev の答えで決まる（確信度が下限に満たない答えは除く）: 順位の段、2 件の提案が同じ変更かの判定（候補の統合）、危険の印の D5。状態ファイルの `judge.kind` が `"jev"` になる
- [ ] AC23: Jev が使えないとき（鍵が無い・`NDF_JEV=0` で無効にした・対象が非公開のリポジトリ・疎通が通らない）は、実装担当が同じ 3 つの判断を行い、`judge.kind` が `"runtime"`、`judge.reason` が使わなかった理由になる。使える実行の中で 1 回の呼び出しが失敗したときは、その問いだけを実装担当の答えで決め、`judge.failures` に数える（`judge.kind` は `"jev"` のまま）。どちらの場合も進行は止まらない

### 状態と再開・報告

- [ ] AC24: 状態ファイルは新しい版の形になり、途中で落ちても同じコマンド列を打ち直せば、終わったフェーズを繰り返さずに再開できる
- [ ] AC25: 旧い形（ラウンド制）の状態ファイルで再開しようとすると、終了コード 4 で止まり、旧い版で終えるか状態を消して始め直すかを案内する
- [ ] AC26: 完了報告は、フェーズごとの所要・想定最大時間との差・採った件数と見送りの件数（理由別）・全体のテストを走らせたかとその理由・判断に Jev を使ったかを持つ

### 退行しないこと

- [ ] AC27: 範囲（`--scope`）の関門・着手前のテスト・進行側だけが push すること・生成物の同期（`--sync-command`）・改修計画の記録・最終ゲートの振る舞いは変わらない
- [ ] AC28: `cross-refactoring` の既存のテストのうち、ラウンド制に依らないものは通り続ける。ラウンド制に依るテストは、新しい形のテストへ置き換えられる

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | #917 と同じ範囲・同じ参加者で `--budget-minutes 60` を渡すと、最終ゲートの前までの所要が 60 分に 10% の余裕（66 分）を足した内に収まる |
| 運用・保守性 | 所要の内訳（フェーズ別・種類別）が状態ファイルと報告から読める。配分テーブルの値の出所（どの実行の記録か）がたどれる |
| 移行性 | 旧い引数は 1 つの版の間、知らせて無視する。旧い状態ファイルは読み替えずに止める |
| セキュリティ | `AI_GATEWAY_API_KEY` の値を状態ファイル・報告・コミット・ログへ書かない。Jev へ送るのは提案のフィールド（`path` / `symbol` / `smell` / `technique` / `rationale` / `plan` / 賛同した者の数）と `git diff --stat` の行だけで、差分・ファイルの本文・テストの出力を送らない。Jev は公開リポジトリでだけ使う |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。引数が 1 つ増え、3 つが廃止（知らせて無視）、`--max-fix-rounds` の意味が「群あたり」から「項目あたり」へ変わる |
| データ | 状態ファイルの形が変わる（版を上げる）。新しく配分テーブルの初期値（同梱）と履歴（利用者の手元）を持つ |
| 既存の振る舞い | ラウンド制・テスト整備ラウンド・群・輪番がなくなる。検証は群の単位から項目の単位へ変わる |
