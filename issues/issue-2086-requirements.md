## 何をしたいか

`document-restructuring` を、文書の**形式**（Markdown・スライド・表計算・Google ドキュメント・Confluence など）と**目的**（決議依頼・議論・アジェンダ・小説・エッセイ・ブログ・作業レポート・論文など）に関わらず、AI が作った文書を人が読みやすく分かりやすい形へ組み直せる Skill にする。

- **Value**（作成時の条件）

  4. 文書の目的（決議依頼・議論・アジェンダ・小説・エッセイ・ブログ・作業レポート・論文など）に合った構成と文章量にする

## 目的

- AI が書き上げた文書を、文書形式（Markdown・スライド・表計算・文書・ページ）と文書の目的（決議依頼・議論・アジェンダ・小説・エッセイ・ブログ・作業レポート・論文など）に合った構成と文章量へ、1 つの Skill で組み直せるようにする
- 形式と目的に関わらず守る決まりを共通ルールとして 1 か所に定め、他の文書系 Skill の規約と二重にしない
- 組み直した文書を読む人が、問い直さずに内容を理解し、納得できる状態にする（Vision）

## 前提

- 前提 1: 文書形式の分け方は、既存の `release` の `form-*.md` と `design` の `layout-*.md` の 4 つ（文書・ページ・スライド・表計算）に、リポジトリの Markdown（`docs/`・課題・Pull Request の本文・設計文書）を足した 5 つを出発点にする。Confluence と Notion は形ではなく置き場（`document-systems` のシステム）で、形は「ページ」に当たる。分け方を変えるかは設計で決める
- 前提 2: 小説・エッセイ・ブログのように、NDF の工程（`documentation` モード）の外で書かれる文書も対象に含める。工程の中で呼ばれたときと、利用者が明示して呼んだときの両方で同じ手順が使える
- 前提 3: 文書の目的の一覧は利用者の挙げた 8 つを最低限とし、既存の文書タイプ（`development-workflow` の `references/document-types.md` の 6 つ）と「確定事項を伝える文書」（確定した設計・報告書。今の構成が当たるもの）を含める。目的と文書タイプの対応は設計で決める
- 前提 4: 目的ごとの文章量・形式ごとの目安で実測が無いものは、根拠を「未実測」と書いて目安を置く。実測のあるものだけを実測と書く（Value 3）
- 前提 5: 小説・エッセイ・論文などで、ビジネス文書の決まり（結論を先に置く・対比を表にする など）が目的に合わない場合は、目的の側の決まりが優先する。共通ルールはこの場合でも外さない決まりだけを持つ
- 前提 6: 組み直しは内容を足さないという今の決まりを保つ。目的に必要な章が欠けていると分かったら、控えて報告に残し、組み直しの中では書き足さない

## 対象範囲

含む:
- `document-restructuring` の手順・構成・測る指標と目安・他の Skill との境界の書き直し
- 文書形式ごと・文書の目的ごとの参照ファイル（`references/` の下。対象に当たるファイルだけを読む形）の追加
- 形式と目的に共通する決まり（共通ルール）の定義
- #2083・#2080・#469 の受け入れ条件（下の受け入れ条件 13〜21）
- 規約の二重を解くために、`markdown-writing`・`document-drafting`・`design/references/layout-slide.md`・`release/references/form-slide.md` などの該当する行を、正本を指す形へ書き換えること
- `development-workflow` の工程表の「ドキュメント再構成」の行の書き直し（#469 の掛け忘れ）
- 形式と目的の違う文書 3 本以上での試行（前後の値の表）

含まない:
- 文書形式への生成そのもの（pptx・Google ドキュメント・表計算の作成、Notion・Confluence への投稿）。`release` の `form-*`・`document-systems`・`notion-writing` の手順は変えない
- 版面の点検（`layout-review` の手順）を変えること
- 文書の内容の誤りを直すこと・内容を書き足すこと（組み直しの外の作業）
- 文書の規約の点検をスクリプトにすること（#873・#854 は「やらない」で閉じている）
- 既存の文書を新しい Skill で一括に組み直すこと
- `.md` の文言を照合するテストを書くこと（`AGENTS.md`）

## 用語

| 用語 | 意味 |
| --- | --- |
| 文書形式 | 文書を読ませる形。利用者の原文の「文書形式」に当たる。リポジトリの Markdown・文書・ページ・スライド・表計算。置き場（Notion・Confluence・Google Drive などのシステム）とは別の軸 |
| 文書の目的 | 読み手にその文書で何をしてもらうか・何を渡すかの種類。利用者の原文の「文章の目的」に当たる（決議依頼・議論・アジェンダ・小説・エッセイ・ブログ・作業レポート・論文など） |
| 共通ルール | 文書形式と文書の目的に関わらず、組み直した文書が満たす決まり |
| キーワード | 文書の題・見出しと、本文で繰り返し使い、読み手がその文書の主題として受け取る語 |
| 確定事項を伝える文書 | 確定した設計・報告書のように、結論が既に決まっている文書。今の「構成」が当たる |
| 議論用の文書 | 仕様案・提案書・論点の整理のように、まだ決まっていないことを読み手と決めるための文書（#2083） |

## 受け入れ条件

### 共通ルール（Value 5）

- [ ] 1. `document-restructuring` が、文書形式と文書の目的に関わらず守る決まりを「共通ルール」として 1 か所に一覧で持つ。各行に、その決まりの正本の場所（その Skill 自身か、他の Skill のファイルと節）を書く。利用者がこれまでに指摘した 5 つ（具体例から始める・直訳の和語を避け業界の語で 1 語 1 意味・判断を求める前に経緯と前提と材料を示す・内部用語を前提にしない・パス・URL を表示先でリンクとして認識される形で書く）について、共通ルールに採るか、形式か目的別ガイドへ置くか、採らないかと理由が設計文書の決定の記録にある

### 他の文書系 Skill の規約（Value 1）

- [ ] 2. `document-restructuring` が、文書系の Skill と参照（`markdown-writing`・`document-drafting` と `type-*.md`・`notion-writing`・`layout-review`・`decision-request`・`document-sources`・`document-systems`・`design/references/layout-*.md`・`release/references/form-slide.md`・`form-document.md`・`form-spreadsheet.md`・`form-page.md`・`development-workflow/references/document-types.md`）のそれぞれについて、何を求めるか・組み直しのどの手順で読むか（または読まない理由）を表で持つ。表に無い文書系 Skill が 0 件である
- [ ] 3. 組み直した後の文書が、当たる他の Skill の求める節と決まりを失わない。少なくとも次を手順が守る: `design` の設計文書の固定の章（今の決まり）、`document-drafting` の文書タイプの「必ず書く節」、`decision-request` の 5 項目（判断を求める文書のとき）、`document-sources` の出典の節
- [ ] 4. 文書形式を決める手順があり、手がかり（拡張子・置き場・呼び出し元の指定）で決まらないときは推測せずに呼び出し元へ確かめる

### 文書形式（Value 2・3）

- [ ] 5. 文書形式ごとに、1 つの参照ファイル（`references/` の下）がある。各ファイルは、文章量の単位と目安（スライドは 1 ページ、表計算は 1 シートと 1 セル、ページと文書は章、など）・題と見出しの付け方・その形式への適用を担う Skill（呼び出し先）を持つ。手順は対象の形のファイルだけを読む（`lang-*.md` と同じ形）。形式への適用そのもの（生成・投稿・版面）の手順は書かず、呼び出し先を指す
- [ ] 6. 測る指標と目安が文書形式ごとに分かれ、各目安に根拠（実測の出所か「未実測」）が添えられている。章あたりの行数・平均文長のように形に当たらない指標は、その形で測らないと明記されている
- [ ] 7. スライドの形式別ガイドが、`design/references/layout-slide.md` と `release/references/form-slide.md` の「ページの文言」「章立て」（1 ページ 1 メッセージ・台本の文を縮めて載せない・章扉・見出しはページの結論）と食い違わず、同じ決まりを書き写さずに正本を指す

### 文書の目的（Value 4）

- [ ] 8. 文書の目的を決める手順があり、手がかり（題・本文・Pull Request の語、確認待ちの問いの有無、承認欄の有無など）と、決まらないときに呼び出し元へ確かめることが書かれている
