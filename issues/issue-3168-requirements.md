## 事象

選んで集める取り込み方のリリースで、本番チャネルへ入れる前の承認との比べ方に 2 つの穴がある。承認していない変更が、再承認なしで本番へ届きうる。

1. **承認の後のマージでないコミットをすべて許す。** `plugins/ndf/scripts/release_lib/promotion.py` の `allowed_after` は、承認したコミットから origin の `release/v<版>` の先頭までの first-parent のうちマージでないものを、版上げ・変更履歴などとしてすべて許す。ソースや権限の設定を直接書き換えたコミット、別のスプリントを cherry-pick したコミットも通る
2. **承認の後に選んだスプリントの先頭が動いても比べない。** `_merge_approved` が比べるのはリリースブランチだけで、承認資料を組んだ時点の単位（`sprint/<名前>`）の先頭と本番チャネルの SHA を、承認の後に読み直さない。組み立ての結果（`units`・`production`）は `release-branch` の結果 JSON に返しているが、承認資料と結び付けて保持していない

## 期待する結果

1. 承認の後に release ブランチへ積んでよいコミットが、リリースの工程が生む変更（版上げ・変更履歴・説明文・消費の記録）に限られる。それ以外の変更を含むコミットがあれば、承認ゲートへ戻して組み直す
2. 承認資料を組んだ時点の単位の先頭と本番チャネルの SHA が承認と結び付けて残り、本番へマージする前に読み直して、変わっていれば組み直しと再承認へ戻る
3. 1・2 を合成した入力（直接編集のコミット・承認の後のスプリントへの push）で、本番へのマージが止まることをテストで確かめる

## 再現手順

1. `.ndf/worktree.json` の `branch_flow.promotion` を `selected` にしたリポジトリで、スプリントを選んでリリースの承認資料を組み、承認する
2. 事象 1: 承認の後、`release/v<版>` へソースを書き換えたマージでないコミットを push する → 本番のプランの release がそのまま本番チャネルへマージする
3. 事象 2: 承認の後、選んだ `sprint/<名前>` へコミットを push する → release は比べずに、承認の時点の単位のまま本番チャネルへマージする

## 環境

- ndf v10.27.60（`plugins/ndf/scripts/release_lib/promotion.py` の `allowed_after`・`_merge_approved`）
- 要求を書いた時点の確認: v10.27.61 の `promotion.py` も同じ実装である（`allowed_after` は `git rev-list --first-parent --no-merges <承認したコミット>..<先頭>` の全件を許すコミットとして返す）

## 影響

承認資料と本番に入る中身が食い違いうる。脅威はうっかりの操作と権限の無い人で、AI による本人のなりすましは含めない。事象 1 は手で直したコミットを release ブランチへうっかり積む場合、事象 2 は承認待ちの間に他のレーンがスプリントブランチへ push する場合に起きる。selected を使うリポジトリだけが対象で、既定の取り込み方（whole）は当たらない。

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる（互換あり）。`release-steps.py release --promotion selected` が止まる条件が増える。終了コードは既存の承認ゲート（10）を使い、新しい終了コードを足さない。`release-branch` の結果 JSON の欄は変えない |
| データ | 承認資料に、組んだ時点の先頭の記録が増える（形は設計で決める）。既存の承認資料の書き換えはしない |
| 既存の振る舞い | 選んで集める取り込み方の本番のリリースだけが変わる。既定の取り込み方（whole）と開発版のリリースは変わらない |

## 目的

- **今どうなっているか**: 選んで集める取り込み方の本番のリリースは、承認したコミットの後のマージでないコミットを中身を見ずに通し、承認の後に動いたリリースの単位と本番チャネルの先頭を見ない
- **変えると何が成り立つか**: 本番チャネルへ入る中身が、承認資料で人が承認した中身と、リリースの工程が機械で足した変更だけになる。食い違えば本番へ入れずに承認ゲートへ戻り、組み直しと再承認を促す
- **誰に効くか**: 選んで集める取り込み方を宣言したリポジトリで、リリース承認ゲートを承認する利用者

## 前提

- 前提 1: 脅威は、うっかりの操作と権限の無い人である。AI による承認者のなりすまし（承認資料の記録を書き換えるなど）は防ぐ対象に含めない
- 前提 2: 許すコミットの判定は、変更したパスだけでなく差分の中身でも行う。版数の記載を持つファイル（`plugin.json`・`marketplace.json`・README など、`bump` が書き換える箇所）は、差分が版数の置き換えだけであるときに限って許す。`plugin.json` は版数のほかに hook などの設定を持つため、パスだけで許すと事象 1 の「権限の設定を直接書き換えたコミット」が通る
- 前提 3: リリースの単位か本番チャネルの先頭が組んだ時点の先頭と違えば、増えたコミットの中身を問わず止める（確定仕様の「組み直す条件」と同じ）
- 前提 4: 承認の外のコミットの差分が `docs/`・`issues/` の下だけに収まるときに止めずに通す扱い（`release_lib/approval.py` の `UNGATED`。#2221）は、選んで集める取り込み方でも変えない
- 前提 5: 本番チャネルへのマージが済んだ後の打ち直し（再開）は、マージ済みとして比べ直さない（取り消せない操作の後のため。今の振る舞いのまま）
- 前提 6: 止めるときは、今の承認ゲート（終了コード 10）の結果の形と `next` を使う。組み直し（`release-branch` の打ち直し）と承認資料の作り直し・再承認は、今の手順のまま人が承認ゲートで行う

## 対象範囲

含む:
- 選んで集める取り込み方の本番のリリースで、承認の後のコミットを、リリースの工程が書く箇所に収まるものだけに限ること（事象 1）
- リリースブランチを組んだ時点の先頭（各リリースの単位と本番チャネル）を承認資料と結び付けて残し、本番へマージする前に origin の先頭と比べること（事象 2）
- 止めたときの承認ゲートの結果に、止めた理由（どのコミットか・どの先頭がどこからどこへ動いたか）を載せること
- 合成した入力で両方の事象が止まることを確かめるテスト
- 確定仕様 `docs/specifications/ndf-branch-flow-declaration.md` と `production-merge.md` の「選んで集める取り込み方のリリース」の、承認の後に許すコミットの記述を新しい条件に合わせること

含まない:
- 既定の取り込み方（whole）のリリースの比べ方（`release_pr_allowed`・`compare_approved` の whole の経路）
- 並列の計画のまとめたリリースの selected 対応（#3151）
- 承認の後に `develop` が進んだときの出し直し（#3070）
- 本番チャネル宛の Pull Request の CI の検査（`scripts/check-pr-base.sh`）の条件
- 止まった後に組み直しと再承認を自動で回すこと
