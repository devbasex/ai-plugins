## 目的

**残すかどうかをテストで決める。** git の衝突は「その項目をそのまま積めない」ことを示すだけで、外す相手を決める根拠にしない。直すものが無いと分かった項目に時間を使わない。テストを通る改善が、別の項目の失敗に巻き込まれて捨てられない状態にする。

達成の目安（実測の材料は下の「見つけたときの記録」）:

- takemi-ohama/novel PR 254 の 12 件: 今 採用 1 件 → 偽の失敗が起きないので 12 件すべてが残る（引き金を直した場合）。引き金が別の形で起きても、衝突しない 6 件以上が残る（手元で積み直して確認済み）
- devbasex/ai-plugins PR 1732（#1733）の 18 件: 今 採用 0 件・終了コード 4 → 構造検査で落ちた 8 件は最初の修正の後に外れ、残りの 10 件が範囲テストを通れば採用される

## 決め直した規則（最終形）

今の 4 つの規則と 2 つの引き金を、次の形へ揃える。**判断の軸は 1 つ: 項目を残すかは、その項目を積んだ HEAD での範囲テストで決める。**

| # | 規則 | 今 | 最終形 | なぜ |
| --- | --- | --- | --- | --- |
| R1 | 取り消しの単位 | 項目の単位で取り消す（v8.2.0・#1482 決定 2） | **維持。** 取り消すのは失敗した項目だけで、他の項目は R2 の場合にだけ外れる | 合意した項目を PR に残す前提は今も成り立つ。崩していたのは R2 と R3 |
| R2 | 積み直しが衝突したとき | 消す・戻すコミットが触った**ファイル**を触った生きている全項目へ 1 段広げ（`widened`）、範囲テストを掛け直さずに取り消す。広げても衝突したら HEAD を戻して終了コード 4 | **衝突したコミットを持つ項目だけを外して積み直しを続ける**（後でそれに依存して衝突した項目も同じく外す）。積み終えたら、残った項目を新しい HEAD の範囲テストで確かめ直してから採る。`widened`（ファイル単位で広げる規則）と「広げても積み直せない → 終了コード 4」は無くす | 衝突は「git が自動で解けない」ことしか示さない。ファイルが同じというだけで外すと、テストを通る改善を捨てる（PR 254 で 7 件、#1733 で 18 件）。意味の上の依存は、ファイルの一致ではなく範囲テストで見つける |
| R3 | 修正の打ち切り | 締め切り（時計）まで、落ちた項目のすべてを修正へ回し続ける（#933 決定 22・23）。修正担当の答えの中身は見ない | **締め切りの規則は維持し、加えて「修正の起動が結果を残して終わり、その項目のコミットを 1 つも作らなかった」項目は次の修正へ回さず、その回の検証で取り消す** | 修正担当がコミットしなかったことは git で観測できる（オーケストレーターは git だけを見る規則と同じ根拠）。同じ項目を同じ状態で再び渡しても結果は変わらず、時間だけを使って取り消しを締め切りの直前へ押し出す（PR 254 で 10 回・約 11 分、#1733 で 43 回） |
| R4 | コミットの形 | 1 項目 = 1 コミット、計画がテストを足す項目は 2 コミット（#933 決定 8・12） | **維持** | テストのコミットどうしの衝突も R2 の「衝突したコミットを持つ項目だけを外す」で扱える |
| R5 | 範囲テストへ渡す対象（引き金 1） | `test_targets` の `tests/x.py::Check`（ノード ID）を、範囲テストの雛形の `{paths}` へそのまま渡す。ランナーが拒むと終了コード 2 で、テストの失敗と数える | **範囲テストを組み立てるときは、`test_targets` の `::` より前のパスだけを渡す**（重なりは 1 つにまとめ、順は保つ）。どのランナーでも同じ | `{paths}` の約束は「パス」である。`::` を受け付けるかはランナーごとに違い、宣言の `runner` は自由な文字列なので見分けられない（Value 5）。落ちたテストを読む側はすでに `::` より前のパスで読んでいる（`cross-refactoring-round-tests-and-assess.md` の 165 行目） |
| R6 | 「直すものは無い」と答えた項目（引き金 2） | 締め切りまで修正へ回る | **R3 で扱う**（別の規則を足さない） | 答えの中身（結果ファイルの申告）は読まない規則を保つ |

**案 A（#1793 の本文の推奨）を採る。** 案 B（項目ごとに範囲テストを掛けてから次を積む）は、取り消しの巻き込みが原理的に無いが、実装担当の 1 回の起動で順に実装する形（#933 決定 12）を変え、範囲テストの回数が項目の数だけ増える。R5 で偽の失敗を断てば、PR 254 では案 A でも 12 件すべてが残り、案 B との差が無い。案 C（ハンクの重なりで広げる相手を絞る）は、行範囲の重なりが git の衝突と一致せず（文脈 3 行の差）、試しに積む案 A より正確でも単純でもない。

**引き金も同じ設計で直す。** R5 と R6 は、R2・R3 と同じ「失敗した項目の扱い」の経路の入口であり、分けると「偽の失敗で修正を回し、取り消しで巻き込む」組み合わせが残る。R5 は組み立ての 1 か所、R6 は R3 そのものなので、設計を分けるほどの大きさが無い。

## 前提

- 前提 1: 公開済みのコミットを戻す `git revert` が衝突したとき、と、どの項目にも属さないコミット（オーケストレーターのコミット）の積み直しが衝突したときは、今のとおり HEAD を取り消しの前へ戻して終了コード 4 で止まる。R2 が外すのは、項目に属するコミット（テスト・実装・修正）の積み直しの衝突だけである
- 前提 2: R3 の「結果を残して終わった」は、今の「結果を残さなかった担当」の判定（振り替え。#919）の逆である。結果を残さずに終わった起動は今のとおり振り替えへ回し、R3 では数えない
- 前提 3: R3 で取り消す項目の判定に、結果ファイルの申告（`fixed` / `not_fixed`）は使わない。修正の起点から HEAD までの、その項目の `Item-Id` のコミットの有無だけで決める
- 前提 4: R5 で `::` を落としたことで、範囲テストが 1 項目あたりに走らせるテストの数は増えうる（ノード ID でなくファイルの全体を走らせる）。範囲テストの所要の見積り（配分テーブル）は変えず、実測が記録に入って次回から反映される
- 前提 5: R2 の確かめ直しで走らせる範囲テストは、今の検証と同じ上限・同じ語の並びの共有（1 回だけ走らせる）で走る。確かめ直しで落ちた項目は、今の「範囲テストが落ちた項目」と同じ経路（修正・締め切り・取り消し）を通る

## 対象範囲

含む:

- R2: 取り消しの積み直しで衝突した項目だけを外す規則と、積み直した後の範囲テストの確かめ直し
- R3: 修正担当がコミットを作らなかった項目を次の修正へ回さず取り消す規則
- R5: 範囲テストの組み立てで `test_targets` の `::` 以降を落とす規則
- 状態ファイルの取り消しの記録（`drops`）と項目の `failure_reason` に、外した理由（どの項目の取り消しで、どのコミットが衝突したか）を残すこと
- 旧い状態ファイル（`drops[].mode` が `widened` の記録）を読めること
- 文書の一致: 確定仕様（`docs/specifications/cross-refactoring-verify-and-final-gate.md` の取り消しの行・終了コードの表・不変条件の表）・`references/design-principles.md` の「収束しない項目」・`SKILL.md`（終了コード 1 の一覧の「同じファイルまで広げても積み直せない」・流れ図）・`CLAUDE.md` の cross-refactoring の節・修正担当と計画のプロンプトの `test_targets` の説明

含まない:

- 案 B（逐次の採用）への移行。R2・R3・R5 の効果を実測してから判断する
- 行数の上限に近いファイルを、計画の時点で足す行数を見積もって見送ること（#1733 の 3 つ目の案）。構造検査の失敗を「計画で避ける」話で、失敗した項目の扱いではない
- 範囲テストのコマンドがテストを 1 件も走らせずに失敗したことを、`::` 以外の原因でも見分ける一般の検出（JUnit の 0 件など）。範囲テストのコマンドの不一致は #1630 が扱う
- 全体テスト・最終ゲートの取り消し（`culprit` の判定・打ち切りの後の取り消し）の順序。取り消しが呼ぶ積み直しの規則（R2）だけが変わり、誰をいつ取り消すかは変えない
- 公開済みのコミットの revert の衝突の扱い（前提 1）

## 用語

| 用語 | 意味 |
| --- | --- |
| 積み直し | 取り消しで、取り消しの起点から HEAD までの残すコミットを cherry-pick で積み直すこと（未公開のコミットだけ） |

## 受け入れ条件

### 取り消しと積み直し（R2。#1793・#1733）

- [ ] 同じファイルを触る項目 A・B・C（B は A の行の上に書かれ、C は同じファイルの離れた行を触る）と別のファイルの項目 D を実物の git で積み、A を取り消すと、B だけが外れ、C と D は残る（ファイルが同じというだけでは外さない）
- [ ] 外した項目の `failure_reason` に、どの項目の取り消しで、どのコミット（短い SHA）の積み直しが衝突したかが入る。取り消しの記録（`drops[]`）に、外した項目の ID の並びが入り、`mode` に `widened` は現れない
- [ ] 取り消しで積み直した後、残った各項目は新しい HEAD で範囲テストを走らせ、通ったものだけが検証済みになる。落ちた項目は「範囲テストが落ちた」として修正か取り消しへ進む（範囲テストを走らせずに検証済みにも取り消しにもならない）
- [ ] 項目に属するコミット（テスト・実装・修正）の積み直しが衝突しても、HEAD を取り消しの前へ戻して終了コード 4 で止まらない
- [ ] 公開済みのコミットの revert が衝突したとき、またはどの項目にも属さないコミットの積み直しが衝突したときは、今のとおり HEAD を取り消しの前へ戻して終了コード 4 で止まる（退行しない）
- [ ] 取り消しの途中で止まった実行を再開すると（`pending_drop`）、新しい規則で取り消しをやり直し、同じ結果（外す項目・残す項目）になる
- [ ] `drops[].mode` が `widened` の旧い状態ファイルを、報告（`report`）がエラーなく読める
- [ ] 手動確認: PR 254 の作業 worktree の 12 件のコミット（`dc3aee0` まで）から I-005・I-006 を新しい規則で取り消すと、衝突しない 6 件以上が残り、その範囲テストが通る

### 修正の打ち切り（R3。#1733 の受け入れ条件を含む）

- [ ] 修正の起動が結果を残して終わり、修正の対象の項目のうち `Item-Id` のコミットを 1 つも作らなかった項目は、次の修正の対象（`fix.items`）に入らず、その回の検証で取り消される。取り消しの理由は「修正担当が直さなかった」で、締め切りを待たない
- [ ] 同じ修正の起動で、コミットを作った項目は次の検証で範囲テストを走らせ、落ちれば今のとおり締め切りまで修正へ回る
- [ ] #1733 の形（18 件のうち 8 件が同じ構造検査で落ち、修正担当が 8 件ともコミットしない）を偽の修正担当で再現すると、8 件は 1 回目の修正の後に取り消され、修正の回数（`fix_rounds`）はその 8 件について 1 で、残った項目が範囲テストを通れば採用（`adopted`）が 1 以上になり、終了コード 4 で終わらない
- [ ] 結果を残さずに終わった修正の起動は、今のとおり振り替えへ回り、R3 の取り消しに数えない

### 範囲テストの組み立て（R5。#1793 の引き金）

- [ ] `test_targets` が `tests/test_a.py::Check` と `tests/test_a.py` と `tests/test_b.py::test_x` の項目の範囲テストのコマンドは、`{paths}` に `tests/test_a.py tests/test_b.py` を渡し、`::` を含まない
- [ ] 既知のランナー（`pytest` / `jest` / `vitest`）の対象の差し替えでも、`::` を含まないパスだけを渡す
- [ ] PR 254 の形（unittest の包みの `scope_command`、`test_targets` に `::`）で、範囲テストが `unittest cannot select` で終わらない

### 文書

- [ ] 確定仕様（`docs/specifications/cross-refactoring-verify-and-final-gate.md`）の「取り消しは起点から HEAD までを逆再生し…同じファイルを触った項目まで広げて」の行・終了コードの表の `widened` の行・`test_targets` の `::` の説明・`references/design-principles.md` の「収束しない項目」・`SKILL.md` の終了コード 1 の一覧・`CLAUDE.md` の cross-refactoring の節（「同じファイルを触った項目まで取り消しを広げる」）が、R2・R3・R5 と一致する
- [ ] 計画と修正担当のプロンプトが、`test_targets` に書く値をパスとして説明する

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 1 回の取り消しで増える範囲テストは、残った項目の語の並びの数まで（同じ語の並びは 1 回）。R5 で語の並びはファイル単位に揃うので、同じファイルの項目は 1 回にまとまる |
| 運用・保守性 | 外した理由・取り消した理由は状態ファイルとリファクタリング計画のコメントの項目の行で読める（今の `failure_reason` の経路） |

### 根本原因

**取り消しの規則が「git で積み直せるか」だけで決まり、「残す項目がテストを通るか」を見ない。** 4 つの規則が重なって、1 件の偽の失敗が同じファイルの全項目へ広がった。

### 直さないと何が起きるか

- 同じファイルに複数の項目が入る実行（小さいモジュールを対象にした検査では普通）で、1 件が落ちるたびに同じファイルの改善がまとめて捨てられる。提案・計画・実装に使った時間とトークンがそのまま無駄になる（PR 254 では 30 分の実行で残ったのは 1 件）
- 偽の失敗（コマンドの不一致・揺れ）でも同じ経路を通るため、1 件の誤判定が全体の採用 0 につながる
- 修正担当が「直すものは無い」と答えても締め切りまで回るため、取り消しの判断が予算の最後に押し出され、積み直し直す時間が残らない

### 考えられる直し方（判断は設計で）

| 案 | 中身 | 得 | 失 |
| --- | --- | --- | --- |
| A. 衝突したコミットだけを外して積み直し、範囲テストを掛け直す | 落ちた項目を除いて順に cherry-pick し、衝突した項目だけを外す（外した項目のコミットに依存して後で衝突したものも同じ）。積み終えたら残った項目の範囲テストを 1 回掛け直し、落ちたら今の 1 件ずつの取り消しへ戻る | 今の積み直しの仕組み（`ledger.plan_rebuild`・`worktree.replay_commits`）をそのまま使える。PR 254 では 6 件残る（手元で確認）。cherry-pick と範囲テストは数秒で、締め切りの内に収まる | 衝突しないが意味の上で依存する項目は、範囲テストに頼って見つける |
| B. 逐次の採用（項目ごとに範囲テストを掛けてから次を積む） | 実装担当が 1 件積むたびにオーケストレーターが範囲テストを掛け、通った項目だけを確定する。落ちた項目はその場で外し、次の項目は確定した HEAD の上に書かせる | 取り消しで後ろの項目を巻き込むことが原理的に無い。落ちた項目を早く見つける | 実装担当の起動を項目ごとに区切るか、実装の途中でオーケストレーターが割り込む形が要る（#933 決定 12「1 回の起動で順に実装」と衝突）。範囲テストの回数が項目の数だけ増える |
| C. 取り消しの前に依存を見て、広げる相手を「衝突したコミットとそれに依存する項目」に絞る | `_widen` をファイル単位からハンクの重なり（`git diff` の行範囲）と「衝突したコミット」の推移閉包に変える | 今の 2 段の流れを保ったまま、巻き込みが減る | 行範囲の重なりは git の衝突と一致しない（文脈 3 行の差）。結局は試しに積むのが一番正確で、A より複雑 |

**推奨は A。** 最終形として「残すかどうかはテストで決め、git の衝突は外す理由の 1 つでしかない」に一本化でき、`widened`（ファイル単位で広げる規則）を無くせる。B は最も綺麗だが実装の起動の形を変えるため、A の後に効果を見て判断する。

あわせて、引き金の側も直す（この課題に含めるか分けるかは設計で決める）。

- `scope_command` が受け付けない選択子を計画の時点で落とす（宣言の `runner` が `unittest` なら `::` を書かせない）か、終了コードと出力でテストを 1 件も走らせなかったことを見分けて、項目の失敗にせず起動の失敗として止める
- 修正担当が「コードに直すものは無い」と答えた項目は、次の修正へ回さない（#1733 の 1 つ目の案と同じ）
