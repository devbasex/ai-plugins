## 目的

- 工程の 1 つとして起動した cross-refactoring（`--workflow-step`。検査のプランの refactor のステップ）が、最終ゲート修正の打ち切りで止まっても、全体テストを落とすコミットをスプリントのブランチに残さずに終える
- プランが refactor を「完了（採用は残った項目だけ）」として review へ進み、conductor の手作業（原因の調査・`git revert`・全体テストの走らせ直し・`--from review` での流し直し。#1663 で約 15 分）が要らない状態にする
- 単独で起動したとき（人が Pull Request を読む）の振る舞いは変えない

設計文書は #1649 と同じ 1 本（`issues/issue-1649-design.md`）で扱う。案 A と案 B の比較と推奨は決定の記録（`issues/issue-1649-design-decisions.md` の決定 1）にある。

## 方針の変更

今の方針（`plugins/ndf/skills/cross-refactoring/docs/04-verify-and-report.md` の「最終ゲート修正は想定最大時間の終わりで打ち切る」の節）は「最終ゲートは push 済みの地点なので打ち切っても取り消さない。取り消しの判断は Pull Request の読み手が持つ」と定める。

**工程の 1 つとして起動したときに限り、これを「打ち切ったら取り消して、全体テストが通る状態で終える」に変える。** 読み手がプランと conductor で、判断の材料（どの項目が落ちたテストに関わるか）はスクリプトの手元にあるためである。単独で起動したときは今の方針のまま残す。

推奨（決定の記録の決定 1）: **案 A（未確認の項目を取り消して、落ちたテストが通った時点で止める）を主にし、A で通らないときだけ案 B（着手前の HEAD の木へ戻すコミットを 1 本積む）へ落とす。**

## 前提

- 前提 1: 取り消しはすべて `git revert`（か、着手前の木へ戻す新しいコミット）で行い、push 済みの履歴を書き換えない。強制 push はしない（共通原則 C4 に当たらない形に限る）
- 前提 2: 案 A で取り消す順は、#1649 が決める原因の項目を先にし、決まらなければ取り消されていない改善項目を新しい順にする。取り消すたびに落ちたテスト（変更起因のファイル）を手元で走らせ直し、通った時点で止める（検証の中の危険フラグの取り消しと同じ形）
- 前提 3: 案 B へ落とすのは次のどれかのとき: A の取り消しが積み直しの衝突で止まった / 候補を取り消し尽くしても落ちたテストが通らない / 取り消しに使える時間（前提 4）を使い切った
- 前提 4: 打ち切りの後の取り消しにかける時間の上限は `--budget-minutes` から算術で出し、計画の終わりまでに状態ファイルと計画へ書き出す（CLAUDE.md の cross-refactoring の節「時間に関わる数値はすべて `--budget-minutes` から算術で出す」）。値の式は設計で決める
- 前提 5: 取り消した後の HEAD を push し、次の最終ゲートが全体テスト（CI に任せる戦略なら CI）で確かめる。そこで通れば最終ゲートは通過として終える
- 前提 6: 案 B を積んだ後の最終ゲートでも落ちたら（着手前の HEAD でも落ちる = 変更起因ではない、または揺れ）、今の「判断が要る」（終了コード 4）で止まる。取り消しをそれ以上は重ねない
- 前提 7: プランの refactor のステップの定義（`on_fail: abort`）は変えない。cross-refactoring の側が「完了」で終えれば、プランは今のまま review へ進む

## 対象範囲

含む:
- `--workflow-step` で起動したとき、最終ゲート修正の打ち切り（終了コード 1 の経路）で、案 A → 案 B の順に取り消して push し、最終ゲートへ戻る
- 取り消した項目の状態（`reverted`）と理由（最終ゲートの打ち切りで取り消した）、案 B を使ったかを状態ファイルと報告に残す
- drive の結果で、採用（adopted）を最終ゲートを通った後に残った項目の数で出す
- `docs/04-verify-and-report.md`・`SKILL.md` の終了コードの表・CLAUDE.md の cross-refactoring の節の方針の記述を、起動のされ方で分けて書き直す

含まない:
- 単独で起動したときの打ち切りの振る舞い（取り消さずに報告する、のまま）
- 原因の項目の決め方そのもの（#1649）
- 構造検査を範囲テストへ入れること（#1668）
- 最終ゲート修正の締め切り（`開始 + B`、1 回目は時計で打ち切らない）の変更
- 失敗したときに記録が残らない件（#1648）
- プランの定義（`supervise_lib/templates.py` の refactor のステップ）の変更

## 用語

| 用語 | 意味 |
| --- | --- |
| 最終ゲート | cross-refactoring の最後の判定。工程の 1 つとして起動したときは全体テスト、単独では全体テストの後に cross-review |
| 想定最大時間 | `--budget-minutes` で渡す、1 回の cross-refactoring に許す最大の時間 |
| プラン | supervise が通すステップの並び。ここでは検査のプラン |
| ステップ | プランの 1 つの段。ここでは refactor のステップ |

## 受け入れ条件

- [ ] 1. `--workflow-step` で起動し、最終ゲートが変更起因で落ちて最終ゲート修正が打ち切られたとき、原因の項目（決まらなければ未確認の項目を新しい順）が 1 件ずつ取り消され、落ちたテストが通った時点で取り消しが止まる
- [ ] 2. 1 の後、取り消した後の HEAD が push され、次の最終ゲートが通り、`refactor.py final-gate` は通過（終了コード 0）で、drive は `stopped` でなく完了で終わる
- [ ] 3. 2 のとき、drive の結果の `adopted` は取り消されずに残った項目の数で、`unconfirmed` は出ない。取り消した項目は `reverted` に数えられ、理由に最終ゲートの打ち切りで取り消したことが残る
- [ ] 4. 案 A の取り消しが積み直しの衝突で止まったとき、候補を取り消し尽くしても落ちたテストが通らないとき、時間の上限を使い切ったときのいずれでも、着手前の HEAD の木へ戻すコミットが 1 本積まれ、push され、最終ゲートへ戻る。状態ファイルに案 B を使ったことと、その理由が残る
- [ ] 5. 案 B の後の最終ゲートでも落ちたときは、終了コード 4（判断が要る）で止まり、取り消しを重ねない
- [ ] 6. 打ち切りの後の取り消しにかける時間の上限が、計画の終わりまでに状態ファイルと計画に書き出されている
- [ ] 7. どの経路でも、push 済みの履歴は書き換えられない（`git push --force` を使わず、送るコミットは origin の head の子孫である）
- [ ] 8. #1663 と同じ形（危険フラグの無い項目が全体テストを落とし、最終ゲート修正が締め切りに間に合わない）を再現するテストで、drive が完了で終わり、原因の項目だけが取り消される
- [ ] 9. 退行しない: 単独で起動したとき（`--workflow-step` なし）、最終ゲート修正の打ち切りは今と同じく取り消さずに終了コード 1 で終わる
- [ ] 10. 退行しない: 検証を受けていない最終ゲート修正のコミットの取り消し（`merge-final-fix` の今の振る舞い）は変わらない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | 工程の 1 つとして起動した cross-refactoring は、打ち切りの経路でもスプリントのブランチを全体テストが通る状態で終えるか、終えられないときは「判断が要る」で止まる。壊れた状態のまま完了と報告しない |
| 性能・拡張性 | 打ち切りの後の取り消しは、時間の上限（前提 4）を超えない。案 B はコミット 1 本で、走らせ直しを伴わない |
| 運用・保守性 | 取り消しは既存の取り消しの実装（`undo.drop`）と、#1649 の原因の項目の決め方を使う。最終ゲート専用の取り消しを別に作らない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | `final-gate` の終了コード 1（打ち切り）は単独の起動でだけ返る。工程の 1 つとして起動したときは 0 か 4 になる |
| データ | 状態ファイルの最終ゲートの記録に、打ち切りの後の取り消しの記録（取り消した項目・案 B を使ったか・理由・時間の上限）が増える。旧い状態ファイルを読めるまま残す |
| 既存の振る舞い | 工程の 1 つとして起動したときの方針「打ち切っても取り消さない」が変わる。プランは refactor の失敗で止まらず review へ進む |
