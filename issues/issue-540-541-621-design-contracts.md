### 列の値

| 列 | 値 |
| --- | --- |
| 行 | `<束>-設計` / `<束>-実装<N>`。1 つの文書の中で一意 |
| 種類 | `設計` / `実装` |
| 触るファイルと節 | ファイルのパスと、節の見出し（「」で囲む）。関数を触るなら関数名 |
| 確度 | `見込み` / `確定`。設計のレビューが収束した見直しで、その束の行を `確定` にする |
| 設計の依存・実装の依存 | `なし`、または `<行>:収束` / `<行>:マージ` を読点で並べる。設計の行の「実装の依存」は `—` |
| 状態 | `待ち` / `着手できる` / `動いている` / `承認待ち` / `止まった` / `マージ済み` |
| 測った値の各列 | `parallel-measure.py capacity` の出力の値をそのまま写す。測れなかった行は空きの列に `測れない` と書く |
| 閉じたときの測定 | `parallel-measure.py concurrency` の出力と、`oom_kill` の最後の値 − 測った値の表の最初の行の `oom_kill`（起点は見直しで更新されるため、開始時の値から数える） |

### 見直しの手順

**契機は 5 つである。** 担当の報告を受け取った / Pull Request がマージされた / 担当が止まった /
測定で `oom_kill` が増えていた / 進行側が再起動して実行計画を読み直した。

| 順 | 行うこと |
| ---: | --- |
| 1 | 契機になった行の状態を更新する。設計のレビューが収束した束は、設計文書の分け方から実装の行を足し、確度を `確定` にする |
| 2 | `確定` になった行どうしの触るファイルと節を突き合わせ、重なりの表へ書く。区分が `書き換え` なら、後の行の実装の依存へ先の行の `:マージ` を足す |
| 3 | 依存がすべて済んだ `待ち` の行を `着手できる` にする |
| 4 | `parallel-measure.py capacity --running <動いている行の数> --oom-baseline <起点>` を実行し、測った値の表へ 1 行足す。終了コードが 3（測れない）なら、起動してよい本数を 1 として扱う |
| 5 | `起動してよい本数 − 動いている本数` の数だけ、`着手できる` の行を表の上から起動し、`動いている` にする。コンテナを起動する検査を持つ行は、既に 1 本動いていれば起動しない |
| 6 | 1〜5 で束・順序・依存を変えたら、見直しの表へ 1 行足す。状態の更新だけなら足さない |

**`oom_kill_increased=yes` のときは、その見直しの手順 5 で起動しない。** 同じ見直しで、実行計画の
「oom_kill の起点」を今の値へ更新し、見直しの表へ 1 行足す（契機: OOM Killer の回数が増えた、変えたこと:
起点を N へ更新、理由）。次の見直しからは新しい起点と比べるため、再び増えない限り起動を再開する。
起動してよい本数が下がった分は、動いている担当を止めずに、終わるのを待って減らす。

### 閉じる手順

**すべての行が `マージ済み` になったら閉じる。**

1. `parallel-measure.py concurrency <行の Pull Request の番号すべて>` を実行し、閉じたときの測定の表へ写す
2. 状態を `閉じた` にする
3. 全文を、まとまりで最後にマージした Pull Request へ `gh pr comment <番号> --body-file <実行計画>` で投稿する
4. 投稿の URL を確かめてから、ファイルを消す

見出しは `### 並列の組（見込み）` にする。既存の説明の文は変えない。

```markdown
| --- | --- | --- | --- |

| 2 | #540 #541 #621 | `development-workflow/references/parallel-work.md` / `issue-plan-strategy` | なし |
| 3 | #550 #657 | `development-workflow`（工程の窓） / `skill-stats` | 1（#561 の後） |
```

### 列の値

| 列 | 値 | 写す元 |
| --- | --- | --- |
| 組 | 1 から始まる連番。説明の中で一意 | — |
| 課題 | 同じ修正レイヤーを持つ課題の番号 | 段 2A の「修正レイヤー」 |

| 依存 | `なし`、または組の番号（括弧で課題の番号） | 段 2A の「依存する課題の番号」 |

### 書く時点

| 時点 | 行うこと |
| --- | --- |
| 課題をマイルストーンへ入れる（新しく作る・既存へ足す・直近へ移す） | その課題の修正レイヤーが既存の組と同じなら、その組の「課題」へ番号を足す。違えば組を 1 つ足す。表が無ければ見出しと表を作る |
| 課題を別のマイルストーンへ移す | 元の説明の表から番号を消す。課題が 0 件になった組は行を消し、組の番号は詰めない |
| 課題が閉じた | 何もしない。実行計画が状態を持つ |

**実行計画は、表の組を束の初期値として読む。** 表に無い課題は本文を読んで束を決め、どの組にも
足さない（書き戻さない。決定 10）。

## `parallel-measure.py`

呼び方は `python3 "$SCRIPTS/parallel-measure.py" <副コマンド> ...` である。標準ライブラリだけを使う。

### `capacity`

| 引数 | 既定 | 意味 |
| --- | --- | --- |
| `--running N` | `0` | いま動いている担当の数 |
| `--oom-baseline N` | なし | 実行計画に控えた `oom_kill` の起点。渡さなければ増えたかを判定しない |
| `--reserve-mib N` | `2048` | 予備 |
| `--per-lane-mib N` | `2048` | 1 本の見込み |
| `--max N` | `3` | 上限 |
| `--swap-free-min-pct N` | `25` | スワップの空きの閾値（%） |
| `--meminfo PATH` | `/proc/meminfo` | 空きとスワップを読む元 |
| `--memory-events PATH` | `/sys/fs/cgroup/memory.events`。無ければ `/proc/self/cgroup` の `0::<path>` から導いたパス | `oom_kill` を読む元 |

**既定値を持つのはこの表の実装（スクリプトの定数）だけである。** 文書は値を写さず、引数の名前だけを書く。

出力は標準出力に `キー=値` を 1 行ずつ、この順で出す。

| キー | 値 |
| --- | --- |
| `mem_available_mib` | `MemAvailable` ÷ 1024 の切り捨て |
| `swap_total_mib` / `swap_free_mib` | `SwapTotal` / `SwapFree` ÷ 1024 の切り捨て |
| `oom_kill` | `memory.events` の値。読めなければ `unknown` |
| `oom_kill_increased` | `yes` / `no` / `unknown`（起点が無い、または `oom_kill` が `unknown`） |
| `running` | `--running` の値 |
| `by_memory` | `⌊(mem_available_mib − reserve) ÷ per_lane⌋`。負なら 0 |
| `allowed` | 下の式の結果 |
| `limited_by` | `allowed` を決めた条件を `,` で並べる。`memory` / `max` / `swap_low` / `oom_kill_increased` / `floor` |

```text
allowed = min(max, by_memory)
swap_total > 0 かつ swap_free × 100 < swap_total × swap_free_min_pct なら allowed -= 1
oom_kill_increased = yes なら allowed = min(allowed, running - 1)
allowed = max(allowed, 1)
```

**`limited_by` には、次の条件を満たした値を表の順に `,` で並べる。** `memory` と `max` の少なくとも一方は必ず付く。

| 値 | 付ける条件 |
| --- | --- |
| `memory` | `by_memory ≤ max`（空きメモリが `min` を決めた。等しいときも付ける） |
| `max` | `max ≤ by_memory`（上限が `min` を決めた。等しいときも付ける） |
| `swap_low` | スワップの減算を行った |
| `oom_kill_increased` | `running - 1` を当てて値が下がった |
| `floor` | 最後の `max(allowed, 1)` で値が上がった |

**2026-09-17 のこのホストの値での出力（`--running 0`）:**

```text
mem_available_mib=9742
swap_total_mib=2047
swap_free_mib=310
oom_kill=1
oom_kill_increased=unknown
running=0
by_memory=3
allowed=2
limited_by=memory,max,swap_low
```

| 終了コード | いつ |
| ---: | --- |
| 0 | 測れた（`oom_kill` が `unknown` でも 0） |
| 2 | 引数の誤り（未知の引数・整数でない値・負の値） |
| 3 | `--meminfo` を読めない、または `MemAvailable` が無い。標準出力に何も出さず、標準エラーに理由を 1 行出す |

### `concurrency`

| 引数 | 既定 | 意味 |
| --- | --- | --- |
| `<PR番号>...` | 必須（`--input` のときは不要） | 対象の Pull Request |
| `--repo OWNER/REPO` | `gh` の既定 | 対象のリポジトリ |
| `--input PATH` | なし | `gh` を呼ばず、`[{"number", "createdAt", "mergedAt", "closedAt"}]` の JSON を読む |
| `--now ISO8601` | 現在時刻 | 開いたままの Pull Request の区間の終わり |

**区間は `createdAt` から、`mergedAt`・`closedAt`・`--now` のうち最初に値のあるものまでである。**
同じ時刻に閉じる区間と開く区間は重ならない（閉じるほうを先に数える）。

| キー | 値 |
| --- | --- |
| `prs` | 対象の本数 |
| `start` / `end` | 最も早い開始と最も遅い終わり（UTC、`Z` 付き） |
| `span_minutes` | `end − start` の秒 ÷ 60 の切り捨て |
| `overlap_minutes` | 2 本以上が同時に開いていた秒 ÷ 60 の切り捨て |
| `concurrency_pct` | 重なりの秒 ÷ 期間の秒 × 100 を小数 1 桁へ四捨五入（`ROUND_HALF_UP`）。分へ丸めた値からは求めない。`span` が 0 秒なら `0.0` |
| `max_open` | 同時に開いていた本数の最大 |

| 終了コード | いつ |
| ---: | --- |
| 0 | 測れた |
| 1 | `gh pr view` が失敗した。失敗した番号を標準エラーに出す |
| 2 | 引数の誤り（番号が無い・整数でない・`--input` が読めない） |

**`gh` へ渡すのは `pr view <番号> --json number,createdAt,mergedAt,closedAt`（と `--repo`）だけである。**

## `parallel-work.md` の文言

### 守る下限

**下限 1〜3 の行は変えない。** 4〜6 を次の文言にする。太字の部分をテストが写す。

| # | 下限 | なぜ |
| --- | --- | --- |
| 4 | **依存する工程が終わる前に、それを入力にする工程を始めない** | 依存は工程の対で決まる。B の設計が A の決定を読むなら A の設計の収束を、B の実装が A の実装を前提にするなら A の実装のマージを待つ。**実装の順序の依存は、B の設計を止めない** |

| 6 | **並行の本数は、測った本数と収束レビューが回る範囲の小さい方に抑える** | `cross-review` は 4 つの CLI を共有する。加えて、担当はそれぞれ CLI・テスト・コンテナを起動し、**ホストのメモリ**を使う。21GiB のホストで 5〜6 本のとき OOM Killer が本体を 2 回落とし、3 本では落ちなかった（#621）。コンテナを起動する検査を持つ担当は同時に 1 本にする |

| # | 下限 | 誰が見るか | どこで |
| --- | --- | --- | --- |

### 重なりの目安

**「守る下限」の後ろに新しい節として置く。**

| 区分 | 何が当たるか | 並行 | 待つもの |
| --- | --- | --- | --- |
| 別の節 | 別のファイル、または同じファイルの別の節（見出し）・別の関数 | してよい | なし |
| 足すだけ | 同じ節に行・項目・関数を足すだけで、既存の行を変えない | してよい | なし。競合は後からマージする側が両方を残して解く |
| 書き換え | 同じ節の既存の行を書き換える・移す・消す | **実装はしない** | 先の Pull Request のマージ |

**設計の工程どうしは、どの区分でも並行してよい。** 設計文書は束ごとに別のファイルへ書く。

**区分は設計の後に確定する。** 着手の時点の触る場所は見込みで、設計のレビューが収束した時点で
実行計画が確定の値に置き換える。
