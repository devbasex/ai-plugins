# #1426 の設計の決定

設計文書の本体は [issue-1426-design.md](issue-1426-design.md) にある。

## 決定の記録

### 決定 1: 利用者の承認なしに本番へ進まないよう、承認の証跡をスプリント状態ファイルの承認ゲートの記録にする

要求の未決 1 の答えである。承認ゲート 2 の証跡は、conductor が利用者の答えを受けた時点で打つ
`sprint-state.py gate <状態> "関門 2" --what <要約> --by user --outcome approved` の記録とする。本番のプランの先頭の
`approve` は、この記録が開発版の `facts` の出力より後に書かれているときだけ承認の記録を書く。承認ゲート 1 も同じ形で、
`"関門 1" --pr <N>` の記録があれば `design-approved` が承認ラベルを付けてからマージへ進む。

利用者の答えを記録する 1 回はプランの外に残る。プランが答えを作り出さないこと（要求の前提 4）を守るには、
答えを受けた者が書くほかない。この記録は `--state` を渡した `normal` で既に承認ゲート 1・2 の文が求めている
もの（覆しの記録。#1400 の AC6）で、新しいコマンドを足さない。SHA の読み取りは `facts` の出力からプランが行い、
conductor が SHA を書き写す手当てはなくなる。

今の `gate` は利用者の記録に `by` と `pr` を書かず、同じ関門の名の記録を置き換える。これでは承認ゲート 1 の記録を
PR ごとに照らせず、複数の設計 PR を承認してからキューを流すと先の PR の記録が消える。そこで `gate --by user
--outcome approved` は `by: user` と、`--pr` を渡したときの `pr` を書き、置き換えを関門の名と `pr` の組で行う。
`--pr` を渡さない呼び出し（承認ゲート 2 など）の置き換えは今のまま変えない。

`--state` を渡さないスプリントには状態のファイルが無い。そのときは承認ラベル（承認ゲート 1）と承認資料の承認の記録
（承認ゲート 2）をそのまま証跡に読み、conductor は今の `gh pr edit --add-label` と `release-steps.py approve` を打つ。
状態のファイルを `new sprint` が黙って作る形は採らない。`normal` で `--state` を渡すと助言の MVV 判定が入るため、
引数の意味が変わる（要求の非機能の移行性）。キューに本番のプランを入れたこと、`queue` の引数（`--approved-by` の
ような印）を証跡に数える形も採らない。プランを流す操作と承認の答えが 1 つの操作に混ざり、前提 4 が禁じる形になる。

根拠: Value 2 / C4（MVV 版 3）

### 決定 2: 止まったプランを写さずに続けるため、キューの続きを `queue --resume <done>` の 1 つの形にする

要求の未決 2 の答えである。`--resume` は前の起動が done の隣に残した一覧（`<done>.plans.json`）からステージの並びと
`--max` を読み、done の `items` の完了していないプランを、それぞれが終えたステップから続ける。後続のステージは
今の `queue` と同じ条件（前のステージがすべて完了）で流れる。conductor が知る必要があるのは done のパスだけで、
目録の `resume` にそのまま書ける。

開始のステップは、そのプランの `state.json` の最後のステップ（落ちたステップか、承認ゲートを返したステップ）とする。
`--from <プラン名>=<ステップ>` は、承認の後に別の入口から入るステップ（`merge-approved`・`promote-approved`）のための
上書きで、既定では要らない。結果が `関門` のプランも続ける対象に入れる。承認ゲート 1 の証跡が無くて `approved` で
止まったマージのプランも、手動確認の印を待った検査の `merge-gate` も、同じ 1 つの形で続けられる。

採らなかった形は 2 つある。`queue <プラン>... --from <プラン>=<ステップ>` だけを足す形は、conductor が止まったプランと
ステップを報告から読み取り、`--then` の並びを打ち直す必要が残る。目録の `resume` に止まったプランの続きを書き足す形は、
書き出しの時点では止まる場所が分からず書けない。

根拠: Value 4 / Value 5（MVV 版 3）

### 決定 3: 取り込みを設計の前に決められるよう、`new sprint --absorb <課題>:<取り込み先>` を足す

要求の未決 3 の答えである。左が取り込む課題、右が取り込み先で、設計の結果の表の列（課題・取り込み先）と同じ向きに
する。何度でも並べられる。取り込んだ課題が `--issue` に無ければ足し、スプリント PR の閉じる行に入るようにする
（設計の結果の表で取り込んだ課題と同じ扱い）。

取り込んだ課題の実装のプランは書いたうえで `実行の条件`（`absorbed_condition`）で飛ばす。受け入れ条件 14 の 2 つの
選び方のうち、承認ゲート 1 の後に設計の結果から取り込んだときと同じ形を選んだ。プランのファイルの並びが 2 つの経路で
揃い、`design-results` がどちらの取り込みも同じ形で扱える。プランを書かない形は、`design-results` が取り込み先の
プランを探す今の照合（`rewrite` の取り込み先の確かめ）と食い違う。

設計のプランを持たないのは、`--absorb` で設計の前に取り込んだ課題だけである。設計の結果の表で後から取り込んだ課題の
設計のプランは既に流れており、消さずに残す。取り込み先への反映は、取り込み先のプランのうち存在するものに限る
（`--design` の取り込み先は設計と実装のプラン、`--issue` の取り込み先は実装のプラン）。取り込み先に設計のプランを作らない。

取り込み先の課題は `--design` にあれば設計のプランへ、`--issue` にあれば実装のプランへ反映する。どちらにも無ければ
計画を書かない（I8）。取り込む課題を AI が選ぶ形は採らない（要求の対象範囲の「含まない」）。

根拠: Value 4 / Value 6（MVV 版 3）

### 決定 4: 設計 PR の番号を conductor が書き込まないよう、マージのプランが `{queue_pr:design-<N>}` で設計のプランの報告から読む

設計のプランは承認ゲート 1 の judge で終わるため、結果は `完了` でなく `関門` である。今の `{queue_pr:<名>}` は
`完了` のプランの Pull Request しか埋めないため、`完了` か `関門` で終えたプランの Pull Request を埋めるよう広げる。
`{queue_prs}`（前のすべてのステージの PR）は今のまま `完了` だけを集める。

マージのプランの名前は `design-merge-<N>` にする。`merge-design-<N>` は `named` の照合（名前の末尾の一致）で
`design-<N>` に当たり、自分自身を設計のプランと取り違える。マージは設計 PR ごとに別のプランにし、同じステージで
並べる。設計 PR の 1 本が CI の失敗で止まっても、ほかの設計 PR のマージは進み、止まった 1 本だけをキューの続きで
続けられる。

採らなかった形は、設計のプランの後ろへマージのステップを足す形（`pace: auto` の `plan_mvv_design` の形）である。
`normal` の設計のプランは承認ゲート 1 で終わる約束で、続きをプランの途中から始めると、承認ゲート 1 の前のステップの
耐久の記録と、承認の後の実行の回が 1 本のプランに混ざる。

根拠: Value 4（MVV 版 3）

### 決定 5: 承認ゲート 1 の後をキュー 1 回にするため、`normal` のマージから配布までを 1 本の `--then` の列にする

`normal` で `--design` があれば、承認ゲート 1 の後の最初のステージを「設計 PR のマージ」にし、設計の結果・
スプリントブランチ・実装・検査・配布をその `then_of` にする。`--design` が無ければ、最初のステージは設計の結果
（`--designed` があるとき）かスプリントブランチになる。並びは `pace: auto` の `auto_sprint_plans` と同じ形で、
`then_of` の連結（`write_stage_index`）と後続の条件（`fill_stage`）は今のものをそのまま使う。

承認ゲート 2 の後の本番は、今のまま別の `command` にする。承認ゲート 2 は本番系へ届く操作の前の承認で、利用者の
答えを受けるまで流してはならない。配布の後の承認ゲート 2 のステージと本番のステージの並びは変えない。

根拠: Value 2 / Value 4（MVV 版 3）

### 決定 6: 打つコマンドを目録だけから読めるよう、`command` に `--done` を書き、`resume` を `queue --resume` の形にそろえる

今の目録の `command` は `--done` を持たず、手順書が「`--done` を足して打つ」と書いている。`--resume` は done のパスで
前の起動を引くため、`new sprint` が `command` に `--done <出力先>/done-<番号>.json` を書き、同じパスの
`queue --resume <done>` を `resume` に書く。`then_of` のステージの `resume` は、つながる先の最初のステージの done を指す。

`pace: auto` の承認ゲート 1 の文（`AUTO_GATE_1`）も、`run <プラン> --from approve` と次のステージの `resume` を打つ
2 手から、`queue --resume <done> --from design-<N>=approve` の 1 手へ書き直す。プランの並びは変えない（要求の前提 3。
受け入れ条件 17）。止まったときの手順が進め方ごとに分かれると、受け入れ条件 8 の「1 つだけ示す」が崩れる。

根拠: Value 4 / Value 6（MVV 版 3）

### 決定 7: 提示した SHA を書き写さずに照らせるよう、`approve` が開発版の `facts` の出力から SHA を読む

`release-steps.py approve` に `--facts-from <開発版のプランの状態ディレクトリ>` を足し、その中の最後の `facts` の
ステップの出力（結果 JSON の `metrics.approved_sha`）を提示した SHA とする。承認資料を読み直した値を使わない
今の約束（`release_lib/approval.py` の `approve`）は保つ。状態ディレクトリはキューの置き場 `{queue_state:release}` で
埋め、`new release --channel prod` は `--dev-state` で受ける。

`--facts-from` の誤りと証跡の無さは、今の `approve` の失敗（終了コード 1〜3）でなく 10（承認ゲート）で返す。
本番のプランの先頭のステップが `gate_next: end` で承認ゲートとして終わり、キューの続きでそのステップから続けられる。
承認資料に一致する承認の記録が既にあれば書かずに 0 を返し、`--state` の無いスプリントで conductor が今の
`approve` を打った後も同じプランが通る（決定 1）。

根拠: Value 2 / Value 4 / C4（MVV 版 3）

### 決定 8: 進め方によって取り込みの扱いが分かれないよう、`--absorb` を書き出しの後の 1 か所で当てる

`--absorb` は、進め方ごとのステージの組み立て（`sprint_plans`・`fast_sprint_plans`・`auto_sprint_plans`）の中で
扱わず、組み立てた後のプランへ `absorb.py` が当てる。プランは名前（`design-<N>`・`impl-<N>`）で引く。
組み立ての関数ごとに分岐を足すと、同じ規則が 3 か所へ写る。

承認ゲート 1 の後の `design-results` は、プランの `取り込み先` を読み、書き出しで決めた取り込みを表の取り込みと
合わせる。表の内容だけで `課題` を作り直すと、書き出しの取り込みが消える。

根拠: Value 6（MVV 版 3）
