## 目的

- プランを作ってから流すまでの間に版・記録の PR・宣言・予算が変わっても、プランを作り直さずに流せる状態にする（今は #2164 の 2 回の再発のように、conductor がプランを作り直すか版を書き換えた）
- 参照を解決できないとき・承認ゲートで人が見た値と食い違うときに、推定の値や古い値で黙って進まず、理由を添えて止まる状態にする
- 参照を解決する手当てを 1 か所にまとめ、新しい種類の値を足しても同じ規則で解決・記録・照合される状態にする（今は版・記録の PR・前のプランの結果が、キューの中で別々の関数として解決している）

## 対象範囲

含む:
- 参照の部品と、実行の核の参照の段（E4〜E7）
- 前提 3 の 4 つの実装を参照の部品へ寄せること（キューに残る差し込みの関数を消す）
- 宣言の値（`.ndf/` の設定）と予算を、プランを作る時点の値でなく参照で持たせること。対象のキーは設計が契約の一覧（`plugins/ndf/contracts/settings/`）から一覧にする
- 実行条件を、`--from` で始めるときも含めてステップの直前に評価すること（#2349 の 1 つ目）
- 完了したプランの流し直しの判定を、解決の記録とプランの中身の照合で行うこと（#2349 の 2 つ目）
- 開発ループが組むスプリントの版を参照にすること（#2354）
- 子の課題 4 件の再現の手順を通し、閉じるか残すかを本文に記録すること

含まない:
- 子の課題を 1 件ずつ直す Pull Request（即時修正の 4 条件を満たすものと本番を止めているものは除く）
- 触るファイルを参照にすること（起票者の推定 S5）
- 差分の無い実装のプランで `pr` が終了コード 1 になること（#2349 の 3 つ目）。値の解決の時点の問題でなく、結果の契約（柱 P1 #2337）の問題である（受け入れ条件 12 で確かめて残す）
- 上限と再試行の値そのもの（柱 P4 #2343）と、持ち主の記録の取り方（柱 P3 #2342）
- 版の規則（次に空いている版の決め方・決め直しの条件）を変えること。#2164 の規則をそのまま使う
- `factory/` のプラン

## 用語

| 用語 | 意味 |
| --- | --- |
| プランの参照 | プランが値の代わりに持つ、値の取り先の名前（例: 次に空いている開発版・この課題のリリース記録を置いた PR・`.ndf/pace.json` の 1 つのキー・上限の宣言の 1 つの方針）。流す直前に実行の核が値へ解決する。この文書で単に「参照」と書くときはこの意味である |
| 解決の記録 | 1 回の実行が解決した参照ごとの値と出所。実行の記録（#2335 の P2）の行として残る |
| 承認時の値 | 承認ゲートで人（か MVV 判定）が承認資料で見た値。承認したコミットと版を含む |
| 版の差し込み | 配布のプランが具体的な版の代わりに持つ `{release_version}`・`{release_base}`。この柱で参照の 1 種類になる |
| 版の記録 | 配布のプランの状態ディレクトリの `version.json`。この柱で解決の記録の 1 種類になる |
| 記録の PR | リリース記録（`## 配布の記録`）を置いた Pull Request |
| 承認したコミット | 承認ゲート 2 の承認資料が対象にした、ベースブランチの先端のコミットの SHA |
| 実行条件 | プランを流す前に打つコマンド（プランの `実行の条件`）。`skip_code` を返せば完了とする |
| 実行の核 | 入口・ステップが必ず通る共通の実行の仕組み（#2335 の `lib/run_core.py`） |

## 受け入れ条件

- [ ] 1. `supervise.py new sprint`（版を明示しない）・`new close`・`sprint-state.py loop sprint` が組むプランのファイルは、版数・記録の PR の番号・宣言から読んだ値（設計が一覧にするキー）・予算の秒を値として持たず、参照で持つ。組んだプランのファイルを読むテストで確かめる
- [ ] 2. 参照は、ステップの直前（持ち主の記録を取った後）に実行の核が解決し、参照ごとの値と出所が実行の記録に残る。解決でプランのファイルは書き換わらない（流す前と後でファイルの sha256 が同じ）
- [ ] 3. 参照を解決できないとき（記録の PR が見つからない・origin の版かタグを読めない・宣言のキーが無い・前のプランの完了した結果が無い）は、ステップを流さず `stopped` で返り、結果 JSON に参照の名前と解決できなかった理由が出る。推定の値・空・`0`・`unknown` で埋めて流さない
- [ ] 4. 承認ゲート 2 の後に、承認したコミットの後へ許したもの以外のコミットが入った、または承認資料の版と解決した版が違うとき、本番のステップを流さず `gate` で返り、結果 JSON に承認時の値と実行時の値が並ぶ。承認したコミットの後に許したものだけが入ったときは流れる（前提 5）
- [ ] 5. 同じプランの同じステップを流し直すと、前の実行で解決した版を使う。ただし #2164 の版の決め直し（自分の配布のマージより前に別のスプリントがその版を出した）に当たるときは、#2164 の規則で決め直し、決め直した前の版と理由が解決の記録に残る
- [ ] 6. 実行条件を満たして飛ばすはずのプランを `--from <プラン>=<ステップ>` で始めても、そのプランは飛ばされ、結果に飛ばした旨が出る（#2349 の再現の手順で確かめる）
- [ ] 7. 完了したプランを含む done のファイルを `--resume` しても、完了したプランは流れない。完了の後にプランのファイルが変わっていたら、流さずに `gate` で返り、変わったことと流し直す手段を結果に出す（#2349 の再現の手順で確かめる）
- [ ] 8. `sprint-state.py loop sprint` は `--dev` を省いて起動でき、省いたとき組むスプリントのプランは版を参照で持つ。`--dev` を渡したときは今と同じく明示の版のプランになる（#2354 の再現の手順で確かめる）
- [ ] 9. #2164 の受け入れ条件 1〜10 と #2230 の受け入れ条件のテストが、参照の部品へ寄せた後も通る。前提 3 の差し込みを解決する関数が、キュー（`supervise_lib/queue_fill.py`・`supervise_lib/queue.py`）に残らない
- [ ] 10. 前提 6 の旧い形のプラン（値を書き込んだプラン）を流すと、書き込まれた値で流れ、実行の記録に出所「プランの値」が残る
- [ ] 11. 宣言の値のうち秘密と宣言された入力（#2335 の I9）は、解決の記録に値が書かれず、出所の名前だけが残る
- [ ] 12. 子の課題 4 件（下の「子の課題」の表）それぞれについて、再現の手順を 1 回通した結果（コマンドと出力の要点）と、閉じた（解消を確かめた）か残した（理由つき）かを、この課題の本文の表に記録する。閉じた課題には、確かめた結果へのリンクを添える
- [ ] 13. 参照を持たない入口とプランの振る舞いが変わらない。全体テストが柱のマージの前後で通る

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 参照を持たない入口の起動に足す時間は、#2335 の上限 150 ms（核全体）の内側に収まる。GitHub と origin を読む参照は、その参照を持つステップだけが読む（今と同じ） |
| 可用性 | 解決できないときと食い違うときは、待ち続けずに `stopped` か `gate` で返る（受け入れ条件 3・4） |
| 運用・保守性 | 解決した・解決できなかった・照合した・食い違ったを、実行の記録の行に実行の識別子つきで書く（受け入れ条件 2） |
| 移行性 | 移す対象: 前提 3 の差し込みと、プランを組む入口が書き込む値。並走: 旧い形のプランは値のまま流す（受け入れ条件 10）。版の記録（`version.json`）は解決の記録として読む。切り戻し: 参照の段の Pull Request と入口を移す Pull Request を、それぞれ revert すれば前の形へ戻る |
| セキュリティ | 受け入れ条件 11。認証・認可（C2）と秘密の扱い（C1）は変えない |
| システム環境 | 版の比較は今と同じ `versions`（optional extras）を使う。extras が無い環境では、核が `stopped`（終了コード 69）と足りない extras の名前を返す（#2335 の受け入れ条件 15） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`sprint-state.py loop sprint` の `--dev` が任意になる（渡せば今と同じ）。承認ゲートの後の食い違いは `gate` で返る。差し込みの書き方（`{queue_record}` など）は旧い形のプランを読むために次の正式版まで受ける |
| データ | 変わる。プランのファイルは解決で書き換わらなくなり、解決した値は実行の記録に残る。版の記録（`version.json`）の置き場と形は設計で決める（未決）。利用者の `.ndf/` は変えない |
| 既存の振る舞い | 変わる。完了の後に変わったプランを `--resume` すると流さずに止まる。`--from` でも実行条件を先に評価する |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | 参照の部品は `plugins/ndf/scripts/lib/` に置く。既定で働くため `experimental/` に置かない（`AGENTS.md` の「安定版と実験版」）。`factory/` を参照しない |
| コーディング規約 | `AGENTS.md` の「最小限のコード実装」と、外部コマンド（`git fetch`・`gh`）の挙動を書く前に実行して確かめる決まり |
| テスト戦略 | 参照の部品は単体テストで解決・失敗・照合を担保し、プランを組む入口はプランのファイルを読むテストで担保する。子の課題は再現の手順で確かめる。`.md` の文言を照合するテストは書かない |
