## 目的

- AI エージェントが実施する前提で、作業の大きさを近い条件の実績から見積もり、優先順位とスプリントの容量・ステップの上限を決められるようにする
- 見積もりの規約と実績の集計を 1 か所に置き、Skill ごとの別の材料・別の単位の見積もりをやめる
- ai-plugins 以外のプロジェクトでも、同じ見積もりを使い始められるようにする

## 前提

- 前提 1: 見積もりの判断（6 項目の判定・類似の実績の選び方の妥当さ）は AI が行い、記録の読み出し・集計・丸め・誤差の計算はスクリプトが行う
- 前提 2: H（人の作業時間）の実績を直接記録する仕組みは今のリポジトリに無い。部品は H の実績が無いとき、H を「材料なし」として返してよい。H の記録の取り方は設計で決める
- 前提 3: 実装のステップの `timeout` は、`--impl-timeout` の引数 → `.ndf/supervise.json` の `impl_timeout` → 実績からの見込み → 既定の 3600 秒 の順に決まる（引数と宣言は #1916 で入った今の振る舞いを保つ）
- 前提 4: 実行の構成（モデル・ハーネス・レビューの方式・テストの方式・並列の数）が違う実績は、同じ構成の実績と区別して扱う。どう区別するか（除外するか、別に示すか）は設計で決める
- 前提 5: 要求はこの課題の全体（本文「何をするか」1〜5）を 1 つのスプリントで扱う。実装の Pull Request を 3 つ（規約と一次資料・部品と接続・予測と実績の検証）に分けるかは実装の計画で決める
- 前提 6: 一次資料が読めない研究（有料・削除・リンク切れ）は、「確かめられなかった」と書いて、その数値を規約に使わない

## 対象範囲

含む:
- 研究の出典を一次資料で確かめ、採る知見・採らない知見を設計文書に残す
- 見積もりの規約（完了条件・実行の構成・6 項目・A・H・L・C・実績が足りないときの扱い・Size への換算の規則）を 1 か所に置く
- 材料（supervise の記録・配分の履歴・テストの所要・ステップの所要・使用量の帳簿・差分の行数）を読み、類似の実績から A・H・L・C の見込みを根拠付きで返す共通の部品
- `backlog-refinement` の Size と、`supervise.py new` の実装のステップの `timeout` を部品へつなぐ
- 失敗・中断・取り消し・再試行を含む実績の記録と、見積もりの時点の記録、誤差の集計
- 利用者が任意の作業の見積もりを求められる Skill の入り口
- 部品を使う Skill の手順に、人の工数の基準や AI の倍率で見積もらないことを書く

含まない:
- 研究の数値（倍率・係数・削減率）を見積もりの式へ借りること
- 「工数」として A・H・L・C を足した 1 つの値を出すこと
- `size_exponent`（順位の重み）の値を変えること。運用の方針で、校正とは別に扱う
- 実績の記録の 7 系統（使用量の帳簿・収束ループの要約ほか）を 1 つへ統合すること。部品は読む側をまとめる
- 機械学習による予測モデル
- 既存のマイルストーンや課題の Size の付け直し（棚卸しの工程で行う）

## 用語

| 用語 | 意味 |
| --- | --- |
| AI の実行量 | 作業の調査・設計・実装・検証・修正で、AI エージェントが動いた時間の合計。並列に動いた分は足す（A） |
| 人の作業時間 | 要件の判断・説明・レビュー・手動の確認・修正への介入に、人が手を動かした時間。判断を待つ時間は含まない（H） |
| 完了までの時間 | 着手から完了条件に届くまでの経過時間。並列・依存・CI・承認の待ちを含む（L） |
| 利用費用 | 作業に使った LLM と実行環境の費用（USD）。サブスクリプションの枠の消費は別に記録する（C） |
| 実行の構成 | 実績を比べる前提になる、モデル・ハーネス・レビューの方式・テストの方式・並列の数の組 |
| 類似の実績 | 完了条件・6 項目・実行の構成が近い、過去の作業の A・H・L・C の実測 |
| 未校正 | 類似の実績が無く、想定の手順と既知のテストの所要から出した暫定の見込みであることの印 |
| 見積もりの記録 | 見積もりの時点の 6 項目・実行の構成・予測した A・H・L・C を残したもの。後で実績と突き合わせる |

### 背景

AI エージェントに追加の指示なしで「このタスクの工数を算出して」と頼むと、AI エージェントが無かった時代の人の工数の基準で返ってくる。設計とコーディングの大半を AI エージェントが行うようになり、速さは大きく変わった。人が得意な作業と AI エージェントが得意な作業も違うため、算定の方式そのものを変える必要がある。

それでも「時間の掛かる仕事」と「すぐ終わる仕事」の差ははっきり残る。優先順位を決めるうえで、AI エージェントを使う前提の工数算出は今も重要である。

### 調査の出発点（外部の助言。出典は未確認）

2026-10-08 に利用者が受け取った ChatGPT の助言を、調査の出発点として写す。**研究の出典と数値は着手の時点で一次資料を読んで確かめる。** リポジトリに関する指摘（尺度・配分の履歴の採り方・下の 4 つのファイル）は、起票の時点で develop と一致することを確かめた。

**基準の要旨**: AI で何倍速くなるかを見積もらない。**同じ実行条件で、同じ完了品質に届くまでの工程・検証・手戻りを類似の実績から見積もり、人の作業・AI の実行量・経過時間・費用を分けて返す。**

| 研究・主張（助言による） | 知見 | 見積もりに使うときの限界 |
| --- | --- | --- |
| HIE（Hybrid Intelligence Effort、2026-07） | 22 人・110 タスク・3 モデルの実験。Story Points に加え、検証と修正の指標が作業時間の違いを説明する | 実行中に観測する指標を含む。着手前の予測精度は検証していない |
| ACEM（Agentic Cost Estimation Model、2026-08、arXiv 2608.02582） | 費用を LLM・人の監督・インフラに分け、再試行と文脈の増大を考える | 係数は実証されていない。数値は借りない |
| METR の生産性実験と 2026 年の更新 | 2025 年前半の実験では 19% 遅くなった。後の実験は加速を示すが、選択の偏りで効果量が不確か | ある時点の平均を一律に当てられない。time horizon は能力の指標で、AI の所要時間ではない |
| Microsoft などの企業の実験 | 4,867 人の集計で完了タスク数が 26.08% 増えた | コード補完が中心。自律エージェントの所要とは違う |
| E3（Estimate, Execute, Expand、2026-07） | 小さな変更でもコードを読みすぎて費用が膨らむ。必要最小限から始める方法を提案 | 削減率はシミュレーターの結果 |

#### 工数を 4 つの値に分ける

| 値 | 定義 | 用途 |
| --- | --- | --- |
| 人の実作業時間 H | 要件の判断・説明・レビュー・手動の確認・修正への介入 | 人員の計画 |
| AI の実行量 A | 調査・設計・実装・検証・修正でエージェントが動いた量 | 実行の容量の計画 |
| 完了までの時間 L | 並列・依存・CI・承認待ちを含む経過時間 | 納期・実行の順序 |
| 利用費用 C | LLM と実行環境の費用（サブスクの枠の消費は別に記録） | 予算・利用枠の管理 |

例: AI が 3 本並列で各 20 分動き、人が 5 分レビューしたなら、A は 60 分、L は約 20 分、H は 5 分である。**足して「65 分の工数」にしない。** 人の判断を**待つ**時間は L に、人が判断の**ために作業する**時間は H に入れる。

#### 着手前に見る 6 項目

| 項目 | 軽い側 | 重い側 |
| --- | --- | --- |
| 要件の確定度 | 期待する結果と受け入れ条件が明確 | 正解を関係者と決める必要がある |
| 必要な情報の取得 | 対象・仕様・類似の実装が見つかっている | 原因が不明、情報が散らばる、外部の情報が要る |
| 変更の波及 | 局所的で既存の契約を保つ | API・DB・複数のサービス・移行の順序にまたがる |
| 検証のしやすさ | 短い自動テストで合否が分かる | 実機・本番相当のデータ・目視・長い観測が要る |
| 環境の準備 | 起動・権限・データ・テストが揃っている | 環境の構築・権限の取得・外部との調整が要る |
| 手戻りの見込み | 同じ種類の変更が安定して通っている | 類似の実績で修正が多い、新しい方式、失敗したときに戻しにくい |

**加点して時間へ換算しない**（項目が重なり、重みが検証されていない）。6 項目は**類似の実績を選ぶため**と、見積もりが膨らむ**理由を説明するため**に使う。

#### 算定の手順

1. 完了条件を決める（コードができた・レビュー済み・CI 通過・本番へ反映済みのどこまでか）
2. 実行条件を記録する（モデル・ハーネス・レビューの方式・テストの方式・並列の数）
3. 工程（情報の取得 → 設計 → 実装 → 検証 → 修正と再検証 → 公開）から要るものだけを選ぶ
4. 6 項目と実行条件が近い完了の実績から、工程ごとの時間・費用・修正の回数を比べる。実績に含まれる手戻りを重ねて足さない
5. 標準の見込みと上振れを分ける。データが十分なら P50・P80、少ないうちは「通常 / 追加の調査が要る」の 2 つにし、確率を装わない
6. 原因や検証の方法が分からない部分は、短い調査の課題として切り出し、分かった時点で残りを見積もり直す

**実績が無いときも、人日から AI の倍率で換算しない。** 想定する手順と既知のテスト時間から暫定の範囲を出し、「実績で未校正」と書く。

#### 優先順位の Size が何を表すかを決める

所要時間・LLM の費用・変更量を、説明なしに 1 つの Size へ混ぜない。どの資源を節約する順位なのかが曖昧になる。

| 優先付けの目的 | Size の基礎 |
| --- | --- |
| AI の実行の容量に収める | A |
| 人のレビューの負担を減らす | H |
| 早く価値を届ける | 待ちの扱いを明示した L |
| 支出を抑える | C |

- このリポジトリでは**既定を A にし、H・L・C は別の列**にする案。変更の行数は、波及と検証の範囲を判断する補助に残す
- 尺度 `1, 2, 3, 5, 8, 13, 20` は保つ。代表的な小さい課題の実測を Size 1 の基準にし、予測した実行量をその基準との比で表して、宣言した境界で尺度へ丸める
- 20 を超えるものは 20 に潰さず「尺度を超える・分割を検討」とする
- スプリントの容量を厳密に計画するときは、丸めた Size の和でなく元の予測した実行量を使う
- `size_exponent`（0.3）は順位で大きさをどれだけ重く見るかの**運用の方針**で、AI の速さの係数ではない。校正と分けて扱う

### 何をするか

1. **一次資料で確かめる**: 上の研究の出典と数値を読み、採る知見と採らない知見を設計文書に残す
2. **共通の見積もりの規約を 1 か所に置く**: 完了条件・実行条件・6 項目・4 つの値（A・H・L・C）・実績が足りないときの扱い・Size への換算の規則
3. **共通の部品を作る**: 材料（supervise の記録・配分の履歴・テストの所要・ステップの所要・差分の行数）を 1 か所で読み、類似の実績から A・H・L・C の見込みを根拠（比べた実績）付きで返す。中央値・直近 N 件などの集計を Skill ごとに持たない
4. **既存の Skill から参照する**（規則を各 Skill へ写さない）
   - `backlog-refinement`: Size（既定は A）。H・L・C は別の列
   - `cross-refactoring`: 工程の予算
   - `issue-plan-strategy` の実行計画・`development-workflow` のスプリントの大きさ: 完了までの時間 L
   - `supervise.py new` が書く実装・検査のステップの `timeout`（今は固定値で、引継ぎ文書で毎回補っている）
5. **予測と実績の差を検証する**: 見積もりの時点の情報を保存し、後の課題で時間の誤差・費用の誤差・大きさの順位・上振れの範囲を測る。モデルやハーネスを変えたら校正し直す
   - 記録する最小の項目: 着手前の 6 項目・実行条件・予測値・工程ごとの実績・手戻り・待ち時間・完了の結果
   - 実行の後に分かった修正の回数や実際の差分を、着手前から分かっていた特徴として学習させない

### 起票時の受け入れ条件（受け入れ条件の節へ書き直した。対応は「起票者の推定」）

- 研究の出典を一次資料で確かめた結果（採る知見・採らない知見と理由）が設計文書に残る
- 見積もりの規約が 1 か所にあり、A・H・L・C を分けて定義している。足し合わせた「工数」を出さない
- 共通の部品が 1 つあり、上の既存の仕組みのうち 2 つ以上がそれを使う
- `backlog-refinement` の Size が A を基礎にし、部品が出した見込みと比べた実績を材料として示せる。20 を超える課題は「尺度を超える」と出る
- `supervise.py new` の実装のステップの `timeout` が実績から出た値になる（実績が無ければ今の既定値で、「未校正」と分かる）
- 失敗・中断・取り消し・再試行の実行も、費用の実績として記録される
- 見積もりの時点の値と実績が残り、誤差を後から集計できる
- 人の工数の基準や AI の倍率で見積もらないことが、部品を使う Skill の手順に書かれている
