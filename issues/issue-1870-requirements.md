## 目的

- 本番まで出たスプリントの課題が、プランの `close` ステップ（`sprint-close.py --with-verification`）で閉じる。3 つの現れ方（昇格の後にリリース記録が無い #837・版数を上げない配布で 2 つの記録の版が食い違う #1789・リリース後テストの記録をプランが置かない #1683）を、それぞれ既存の関数とステップを 1〜2 か所直して塞ぐ
- conductor がプランの外で課題を閉じる手当て（m1340・m1649・m815・m1847）を無くす（Value 4）。新しいスクリプト・記録の形・用語を足さない（利用者の指摘「1876はこんなに複雑にする必要ある？もっと素直にできそう」、2026-10-09 の承認ゲート 1）

## 前提

- 前提 1: 依頼の「読む側を緩めるのは補助にとどめる」より、利用者の 2026-10-09 の指摘（素直な形にする）を優先する。読む側と書く側のどちらを直すかは、直す箇所が少ない方を採る。#1789 は読む側の 1 関数（`_pick_verify_block`）を直す方が、2 つの Skill に値の規則を足すより少ない
- 前提 2: 記録の見出しと行の名前は、今すでに `lib/dist_record.py` の定数だけが定義している（`release_lib/record.py`・`sprint-close.py` はその関数を使う。2026-10-09 に grep で確認）。依頼の「1 か所で決める」は満たされているため、集約の作業は持たない
- 前提 3: 課題を閉じるステップは、今のまとめのプラン（`supervise_lib/sprint.py` の `close_plan`）の `close` を使う。本番のプランには足さない。閉じる場所を 1 つに保つためである
- 前提 4: 子 issue（#837・#1789・#1683）は閉じない（依頼の「子 issue」の節）

## 対象範囲

含む:
- 読む側: `_pick_verify_block` が、版の一致するリリース後テストの記録が無いとき、最後のリリース記録より後の最後のブロックを採る（#1789）
- 昇格のプラン（`plan_promote`）: 昇格の Pull Request のマージの後に、既存の `release-steps.py record` でリリース記録を書くステップを置く。まとめのプランは昇格の経路で記録の PR を `{queue_pr:promote}` にする（#837 のプランの経路）
- `release` の SKILL.md の手順: スクリプトで書かない形でも、配布を実施した後に `段階: 本番` のリリース記録を置く段（#837 の案 A）
- まとめのプラン: `close` の前に `/ndf:release-verification` の work ステップを置く（#1683 の残る論点 1）

含まない:
- 記録の形（見出し・行の名前・`版:` の値）の規則を変えること、`release-verification` に `対象の版:` の値の規則を足すこと。読む側の 1 か所で受けるため要らない
- 新しいスクリプト・新しい用語（旧設計の `dist-record.py` と「配布の識別子」）
- merge・manual の経路のまとめ（記録の PR を持たず `--record-pr 0` で閉じる）。範囲外の課題 #1875 にある
- 最終の検査で変更が無く、まとめの queue の本番（雛形の `release-prod`・昇格の `promote`）が飛ばされたときの `--record-pr 0`。雛形の経路も今この扱いで、変えると `fill_queue_pr` の落ち先を広げることになる
- 課題を閉じるとき、本文の受け入れ条件と工程表のチェックボックスを更新すること（#1683 の残る論点 2）
- コミットの件名の closing keywords（GitHub が課題を自動で閉じるキーワード。`Closes #N` など）で GitHub が先に閉じる経路を塞ぐこと（#1683 の残る論点 3）
- 既に閉じた過去のスプリントの記録を書き直すこと

## 用語

| 用語 | 意味 |
| --- | --- |
| リリース後テストの記録 | `release-verification` が Pull Request へ残す、見出し `## リリース後テスト` から `合否:` までのブロック。`対象の版:` の行と課題ごとの表を持つ |
| 版数を上げない配布 | 版数を変えず、既定ブランチへのマージかコミットの反映で本番へ届ける配布（devbasex/devbase の m7e） |

既存の語: リリース記録（`## 配布の記録` のブロック）・昇格のプラン・昇格の Pull Request・まとめのプランは用語集のとおりに使う。

## 受け入れ条件

- [ ] 1. 版数を上げない配布で、リリース記録の `版:` の右（例 `4.0.0`）とリリース後テストの記録の `対象の版:`（例 `main c427284`）が違っても、リリース記録より後に置いたリリース後テストの記録を `parse_record` の `verify_block` として選ぶ（#1789 の再現: devbase PR #432 の 2 つの記録の組）。版の一致するブロックがあれば、今と同じくそれを選ぶ
- [ ] 2. 昇格のプラン（`plan_promote` の normal と fast / auto の両方）が、昇格の Pull Request のマージの後に `release-steps.py record` のステップを持ち、そのステップが落ちたら `judge-record`（`record` か `stop`）へ進む。書いた記録を `sprint-close.py` は `段階: 本番` として読む（#837 のプランの経路の再現）
- [ ] 3. 昇格の経路のまとめの `close` ステップは `--record-pr {queue_pr:promote}` を打つ。merge・manual・none の経路は今と同じ `0` である
- [ ] 4. 本文に `段階: 検証（… 承認待ちのため未実施）` を置いた PR に、配布の後に `record` がコメントで記録を足すと、`sprint-close.py` は `段階: 本番` として読む（#837 の再現: devbase PR #212 の本文の形）
- [ ] 5. `release` の SKILL.md の手順が、配布の形によらず「配布を実施した後に、実施後の値でリリース記録を置く」段を持つ
- [ ] 6. 記録の PR が `0` に固まらない経路（雛形・昇格）のまとめのプランが、`close` の前に `/ndf:release-verification` の work ステップを持つ（#1683 の残る論点 1 の再現: `new close` が書いたプランの JSON に、その順で並ぶ）
- [ ] 7. 退行しない: 版数を上げる配布（`版: 10.17.67 → 10.17.68` と `対象の版: 10.17.68（…）`）で `parse_record` の結果が直す前と同じで、`plugins/ndf/scripts/tests` の全体テストが通る

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 移行性 | 直す前の版で書かれた記録を、直した後の `parse_record` も同じ結果で読む（版の一致するブロックがあれば今と同じものを選ぶ） |
| システム環境 | 本番チャネルのブランチとベースブランチは、`.ndf/` の宣言か引数から受け、ai-plugins の値（`main` / `develop`）を既定に埋め込まない（Value 5） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`release-steps.py record` が昇格の形の引数を受ける。`plan_promote` とまとめのプランのステップが増える。`sprint-close.py` の引数と結果 JSON の形は変えない |
| データ | 無し（PR のコメントに書く記録の形は変えない） |
| 既存の振る舞い | 版の一致しないリリース後テストの記録も、リリース記録より後に置かれていれば読む。昇格の経路で本番まで出たスプリントは「配布なし」で閉じず、記録を見て閉じる |
