# #2169 の決定の記録

設計文書は `issues/issue-2169-design.md` にある。

## 決定の記録

### 決定 1: ライセンスの境目を 1 か所に見せるため、サービスのディレクトリを根の `factory/` にする

根の直下の 1 ディレクトリなら、ライセンスの差し替えは `factory/LICENSE` の 1 ファイルで済み、どのプラグインの `source`（すべて `./plugins/` の下）とも重ならない。名前は「Neural Development Factory」の語から取り、プラグインの語（`ndf`）と区別する。

`services/factory/` のように 1 段深くする形は採らない。サービスは 1 つで、2 つ目の予定が無いのに階層を足すと、ライセンスの境目がどの階層にあるかが読みにくくなる。

根拠: Value 6 / Value 7（MVV 版 3）

### 決定 2: 画面と API とランナーを 1 つの言語で書けるよう、サービスのコードは TypeScript にする

画面は React の SPA（Vite で組む）、API は Node の Lambda、ランナーも TypeScript で書く。3 つで型の定義（`factory/contracts/` から生成）を共有でき、事象の形の食い違いを型の検査で拾える。ランナーのコンテナには NDF のスクリプトのために Python と uv を入れるが、ランナー自身のコードは TypeScript である。

Python で API とランナーを書く形は採らない。画面が TypeScript になる以上、契約の型を 2 つの言語で持つことになる。パッケージの管理の道具（npm・pnpm）は #2171 が最初のコードを置くときに決める。

根拠: Value 6（MVV 版 3）

### 決定 3: 人の答えを待つ間に費用を払わないよう、実行ジョブは承認の依頼で終え、答えで新しいジョブを起こす

実行の単位は ECS Fargate のタスク 1 つ（実行ジョブ）で、スプリントの開始か承認の答えで始まり、次の承認の依頼・止まった・終わったのどれかで終わる。コードの状態は GitHub のブランチと Pull Request に、NDF の状態（`sprint.json` と計画の状態ディレクトリ）は S3 に置くため、新しいジョブはそこから続けられる。並列は、スプリントの実行ごとに別のジョブと別の clone を持つことで成り立ち、worktreeを取り合わない。

承認を待つ間もコンテナを動かし続ける形は採らない。承認までの時間は人が決め、数日かかることもあり、その間のコンテナの費用と、居座ったコンテナの再起動の扱いが増える。基盤を AWS にするのは、認証（Cognito）と推論（Bedrock）が既に AWS に決まっているためである。

根拠: Value 10 / Value 2（MVV 版 3）

### 決定 4: プラグインの版と配布の規則をサービスにもそのまま当てるため、ランナーは NDF をマーケットプレイスから導入し、版をスプリントの開始で固定する

ランナーは `NDF_MARKETPLACE`（既定の値はインフラが渡す）から NDF を導入し、スプリントの最初の実行ジョブで導入した版を `NDF_VERSION` として記録する。以後の実行ジョブは同じ版を導入する。スプリントの途中で版が変わると、途中まで流れた計画と次の計画で NDF の手順が食い違う。チャネル（正式版・開発版）は `NDF_CHANNEL` で選ぶ。

`plugins/` をパスで読み込む形や、ランナーのイメージに NDF を焼き込む形は採らない。前者は前提 2 に反し、後者は版の上げ下げのたびにイメージの作り直しが要り、利用者が使う配布物と別の経路になる。

根拠: Value 5 / P1（MVV 版 3）

### 決定 5: 進捗の正本を 1 つにするため、ランナーの中の NDF が書くファイルを源にし、サービスは翻訳した進捗の事象を追記だけで持つ

一覧・詳細・通知・課金は、進捗の事象（スプリントの実行ごとの追記だけの列）から導く。事象の源は、ランナーの中の NDF が書く `sprint.json`・`progress.jsonl`・作業の報告と、GitHub の Webhook（Pull Request と CI）である。今のフェーズや承認待ちかの状態は事象から導く派生で、作り直せる。

課題の本文の `## 進行` とボードは読まない。取り込むリポジトリがボードを使うとは限らず（Value 5）、読むには GitHub の API の上限を使い、反映が遅れる。新しい状態の表を正にして上書きする形も採らない。いつ何が起きたかの順が詳細の画面と課金の両方で要り、上書きすると失われる。

根拠: Value 5 / Value 3（MVV 版 3）

### 決定 6: NDF のファイルの形の変化を画面や課金へ漏らさないため、翻訳はランナーだけが持つ（腐敗防止層）

`progress.jsonl` の `kind` と `sprint.json` の鍵は NDF の都合で増減する。翻訳をランナー 1 か所に置けば、NDF の版が変わったときに直すのはランナーだけで、受け口・画面・通知・課金は進捗の事象の形だけを知ればよい。

受け口や画面が NDF のファイルをそのまま読む形は採らない。NDF のファイルの形が変わるたびに、子課題の 4 つの要素を同時に直すことになる。

根拠: Value 6（MVV 版 3）

### 決定 7: 子課題が並列に進められるよう、構成要素の間は文書化した事象と指示の形でつなぎ、機械可読な定義を `factory/contracts/` に置く

形の正本は本書の「入出力の契約」で、#2171 がそれを JSON Schema と OpenAPI に起こして `factory/contracts/` に置く。#2172〜#2174 は事象の形だけに依存し、#2171 の実装の完了を待たずに仮の事象で作れる。形を変えるときは本書を先に直す。

子課題がそれぞれ受け口の API を直に呼び合う形は採らない。呼び合う相手の実装の完了が互いの前提になり、並列に進められない。

根拠: Value 7 / Value 1（MVV 版 3）

### 決定 8: どのリポジトリでも同じ工程が通るよう、サービスは取り込むリポジトリの起点・テスト・配布を持たず、そのリポジトリの `.ndf/` に任せる

リポジトリの登録が持つのは、GitHub のリポジトリの識別子と GitHub App の導入の識別子だけである。ベースブランチ（`.ndf/worktree.json`）・テストのコマンド・配布の手段・進め方（`.ndf/pace.json`）は、ランナーの中の NDF がそのリポジトリの `.ndf/` から読む。`.ndf/` の無いリポジトリでは NDF の既定（既定ブランチ）で動く。

サービスの画面にブランチやテストのコマンドの入力欄を持つ形は採らない。CLI で使うときと Web で使うときで設定の置き場が 2 つになり、食い違う。ai-plugins の形（`develop` 起点・`uv` のテスト）を既定に置く形も採らない。

根拠: Value 5（MVV 版 3）

### 決定 9: 手元と CI で同じ結果を得るため、境界の検査は git の追跡するファイルだけを見る標準ライブラリの Python 1 本にする

対象を `git ls-files` に限ると、手元の追跡していないファイル（`.env` の実ファイルを含む）で結果が変わらない。標準ライブラリだけにすると、CI のジョブで依存を入れずに打て、10 秒の条件に収まる。既存の `scripts/check-*.py` と同じく `--root` で根を受け、終了コードは 0 / 1 / 2 にする。

既存の秘密の検出の道具（gitleaks など）を入れる形は採らない。受け入れ条件 1・2・4 が求める検出のうち、サービスへの参照・配布物の木の重なり・インフラの定義はその道具の対象に無いため、結局スクリプトが要る。2 つを持つと、許可の一覧も 2 か所になる。

根拠: Value 4 / Value 10（MVV 版 3）

### 決定 10: 許可の一覧そのものが秘密らしい値として当たらないよう、許可はファイルと値の sha256 の組で持つ

一覧に値を直に書くと、一覧のファイルが秘密らしい値を持つことになり、一覧を許可するためにまた一覧が要る。sha256 なら値を書かずに照らせる。どこにも当たらない許可の行は「古い許可」として落とし、偽の値を消したのに許可だけ残る状態を作らない。許可はファイル 1 つ単位で、ディレクトリや glob を受けない（前提 5）。

許可をパスだけで持つ形は採らない。許可したファイルに本物の値を足しても通ってしまう。インフラの定義と参照には許可を設けない（受け入れ条件は例外を求めていない）。

根拠: Value 3 / C1（MVV 版 3）

### 決定 11: 境界の検査が落ちたらマージできないよう、新しい必須チェックのジョブとして足し、ruleset への追加はゲート 2 で利用者が行う

ジョブ `service-boundary-check` を `runtime-plugin-validate.yml`（Pull Request で絞り込まずに常に走る、リポジトリの検査をまとめたワークフロー）に足し、`scripts/required-checks-allow.json` の `awaiting` に置く。`check-required-checks.py` はこれを「追加待ち」として知らせるだけで失敗にしない。ruleset への追加は、追加待ちの既存の扱い（ゲート 2 で足す）に従う。push の `paths` に `factory/**` を足し、サービスの変更でも push の検査が走るようにする。

既存の必須のジョブ（`lint` など）の手順へ足す形は採らない。ruleset を変えずに済むが、落ちたときにチェックの名前から境界の違反だと読めず、ジョブの責務が混ざる。

根拠: Value 2 / Value 7（MVV 版 3）

### 決定 12: 文書でインフラの語に触れても落とさないため、インフラの定義はファイルの名前と宣言の形で見て、Markdown の本文は見ない

要求の文書（`issues/issue-2169-requirements.md`）自体が `aws-cdk-lib` の語を持つ。語の出現で落とすと、インフラについて書いた設計や仕様が置けなくなる。見るのは、ファイルの名前（`cdk.json`・`*.tf` など）、依存の宣言の中の `aws-cdk-lib`、構造化ファイルの CloudFormation の宣言に限る。秘密らしい値は形で決まるため、Markdown も含めてすべての追跡ファイルを見る。

根拠: Value 1（MVV 版 3）

### 決定 13: 秘密をこのリポジトリと環境変数の値に置かないため、サービスのコードは秘密の ARN だけを受け、実行ジョブごとの token で受け口へ書く

GitHub App の秘密鍵・Slack の Webhook の URL・決済の鍵は private リポジトリのインフラが Secrets Manager に置き、サービスのコードは `*_SECRET_ARN` の名前の環境変数で場所だけを受ける。ランナーが受け口へ書く token は実行ジョブごとに作り、そのジョブのスプリントの実行にだけ書ける。Bedrock の呼び出しはタスクの役割の権限で行い、アクセスキーを渡さない。

ランナーに長く使える API の鍵を渡す形は採らない。ランナーは利用者のリポジトリのコードを実行するため、漏れたときに他のスプリントへ書ける鍵は持たせない。

根拠: C1 / C2（MVV 版 3）

### 決定 14: 課金の手段を決めずに子課題を進められるよう、この課題が決める課金の境界は「ランナーが使用量の事象を出す」までにする

ランナーは claude の結果の使用量（モデル・token・費用）を `usage.recorded` で出す。料金の計算・台帳・決済の手段・Bedrock の請求との突き合わせは #2174 が決める。事象の形が決まっていれば、#2174 は #2171 の実装を待たずに台帳を作れる。

根拠: Value 10（MVV 版 3）

### 決定 15: 承認ゲートの数を増やさないため、サービスの承認は NDF の承認ゲートの答えを運ぶだけにする

承認の依頼の種類はゲート 1・ゲート 2・判断の 3 つで、承認を求めるのはゲート 1・2 だけである。判断は、NDF が「止めて人へ戻す」としたときの知らせで、承認の工程ではない。ランナーは Web からの答えを NDF の既存の記録（`sprint-state.py gate --by user`）として書き、MVV 判定で通す進め方は取り込んだリポジトリの `.ndf/pace.json` に従う。サービスの側で承認を足したり省いたりしない。

根拠: Vision / Value 2（MVV 版 3）
