## 依頼（原文）

## 目的

棚卸しのたびに、open の課題の着手の順序を **同じ入力から同じ順序が出る形** で決め直し、後ろのマイルストーンに埋もれた重要な課題を人の目の前へ出す。

達成したい状態: 棚卸しの報告に (1) マイルストーンの中の順位と次のスプリントへ切り出す候補の境界、(2) 後ろのマイルストーンから直近へ前倒しする候補と、対になる後ろ倒しの候補、(3) 前回の順位からの変化とその理由、が出る。マイルストーンの順序そのものは人が決める。

- 前提 3: 下の層（マイルストーンの中）は順位の値で並べる。遅延コスト（CoD）= 実害の大きさ（UBV）+ 時間的重要度（TC）+ リスク低減・他の課題を解放（RR/OE）、順位の値 = CoD ÷ 大きさ（Size）^α（α は大きさの指数。既定 0.3、α=1 で一般的な WSJF。決定 21）。大きさは AI エージェントが実施したときの費用で付ける（決定 22）。確信度は掛けず、「本文の書き足しが要る」の目印にだけ使う（決定 1）
- 前提 4: 依存は点数に混ぜず順序の制約にする（依存のトポロジカル順を守る範囲で順位の値の降順）。あわせて、前提になる課題の RR/OE を被依存の数から段階へ写す。取り元の優先順は サブイシュー API → 本文の記述（LLM が抽出した結果）→ マイルストーンの説明の「並列の組」の依存の列（決定 2）
- 前提 5: 層をまたいだ逆転は前倒しの規則で防ぐ（決定 0b = 論点 0b の案 B）。比べる量は CoD、比べる相手は直近のマイルストーンの切り出しの境界の課題の CoD、余白は尺度の 1 段階（境界の CoD より尺度の次の値以上に高いときだけ候補にする）、移す先は直近のマイルストーン

## 用語

| 用語 | 意味 |
| --- | --- |
| プロダクトバックログ | open の課題を着手の順に並べた全体。マイルストーンの順（上の層）→ マイルストーンの中の順位（下の層）の辞書順で読む |
| スプリントバックログの候補 | 1 つのマイルストーンの中の課題を順位で並べたもの。次のスプリントはその先頭から容量の分を切り出す |
| 遅延コスト | 課題の着手を遅らせると失う量の相対値。実害の大きさ・時間的重要度・リスク低減の 3 つの見積の段階の和。略して CoD |
| WSJF | 遅延コストを大きさの見積の段階で割った値。人が実施する前提の一般的な形で、順位の値の α=1 に当たる |
| 順位の値 | 遅延コストを大きさの見積の段階の α 乗で割った値（α は大きさの指数、既定 0.3）。マイルストーンの中の順位を決める |
| 大きい課題 | 大きさの見積の段階が宣言の閾値（既定は尺度の上から 2 番目）以上の課題 |
| 大きい課題の枠 | 容量のうち枠の割合（既定 0.5）の分を、マイルストーンの中で遅延コストが最大の大きい課題の 1 切れへ先に当てる取り決め |
| 見積の段階 | 遅延コストの 3 つの要素と大きさに付ける相対値。宣言の尺度（既定は 1, 2, 3, 5, 8, 13, 20）の中から選ぶ |
| 切り出しの境界 | マイルストーンの中の順位を先頭から大きさの見積の段階の和が容量に収まるまで取ったときの、最後の課題 |
| 前倒しの候補 | 後ろのマイルストーンか未設定にあり、遅延コストが直近のマイルストーンの切り出しの境界の課題より余白以上に高い課題 |
| 後ろ倒しの候補 | 直近のマイルストーンのうち、同じマイルストーンの課題が依存していない課題の中で遅延コストが最も低い 1 件。前倒しの候補の最小の遅延コスト以上のものと、順序で次のマイルストーンが無いときは出さない。前倒しの候補と対にして示す |

## 受け入れ条件

- [ ] AC1: `upkeep.py` に順位のサブコマンドがあり、課題ごとの段階（UBV・TC・RR/OE・Size）を JSON で受けて、遅延コストと WSJF を算出し、マイルストーンごとの順位を 1 行の JSON で返す。同じ入力を 2 回渡すと、出力の順位が 1 件も違わない。WSJF が同じ課題は、遅延コストの高い方、それも同じなら番号の小さい方が先になる
- [ ] AC2: 段階が宣言の尺度に無い値・根拠の 1 行が空の段階・4 列のどれかが欠けた課題は順位に入らず、番号と理由が出力に並ぶ
- [ ] AC3: 依存のある課題は、同じマイルストーンの中で必ず依存先より後の順位になる（依存先の WSJF が低くても）。依存が循環するときは順序を出さず、循環する課題の番号を返して 0 以外の終了コードで止まる
- [ ] AC4: 被依存の数が段階へ写され（写し方は宣言で変えられる）、LLM が付けた RR/OE と大きい方が採られる。どちらを採ったかが出力に出る
- [ ] AC5: 容量を渡すと、マイルストーンごとに切り出しの境界（課題の番号と、そこまでの大きさの段階の和）が出力に出る。容量が無いときは境界を出さず、`next` に容量の渡し方が出る
- [ ] AC6: 後ろのマイルストーンと未設定の課題のうち、遅延コストが直近のマイルストーンの切り出しの境界の課題より余白以上に高いものが前倒しの候補に出る。候補ごとに、境界との差と、境界の課題より段階の高い列の名前が出る。前倒しの候補が依存する課題が直近より後ろにあれば、同じ候補の組に並ぶ
- [ ] AC7: 前倒しの候補が 1 件以上あるとき、直近のマイルストーンで同じマイルストーンの課題が依存していない課題のうち遅延コストが最も低い 1 件が後ろ倒しの候補に出る。その遅延コストが前倒しの候補の最小以上のときと、順序で次のマイルストーンが無いときは出ない
- [ ] AC8: 前倒しの候補ごとに「自動」か「承認」かが出力に出る。「自動」は、段階の入力で実害の観測ありとされ、UBV か RR/OE が自動の閾値以上の候補だけである。後ろ倒しの候補はすべて「承認」である
- [ ] AC9: 「承認」の候補は `apply` が承認の記録なしに反映せず（今の「やらない」と同じ扱い）、棚卸しの提示に一括で並ぶ。`pace` の値によってこの扱いは変わらない
- [ ] AC10: マイルストーンの順序（名前の連番と説明の着手の順序）は、順位のサブコマンドと `apply` のどちらも書き換えない。マイルストーンの集計値（遅延コストの合計・最大・`priority: high` にあたる件数）は出力に出る
- [ ] AC11: `apply` がマイルストーンの説明の末尾の `### 順位` の表を書き、既存の説明の文と `### 並列の組（見込み）` の表を変えない。同じ順位で 2 回反映すると、2 回目は書き込まない
- [ ] AC12: 順位のサブコマンドは、前回の `### 順位` の表と比べて、順位が上がった課題・下がった課題・新しく入った課題・外れた課題を、変わった列と前後の段階（例: `TC 3→8`）付きで返す。`report` にこの変化が載る
- [ ] AC13: 尺度・余白・自動の閾値・容量・被依存の数の写し方・ラベルと UBV の下限の対応・大きさの指数・大きい課題の閾値と枠の割合・実害の目安は、宣言と引数のどちらでも変えられ、引数が宣言に勝つ。宣言も引数も無いときは前提 11 の一般的な値で動き、ラベルの下限は効かない。スクリプトに ai-plugins のラベルの名前・容量・課題番号が現れない
- [ ] AC14: `SKILL.md` の手順に、段階の材料を控える（2A）・列ごとに段階を付ける（2B）・順位を算出する・反映する（3）・報告する、が組み込まれている。段階の付け方（尺度・段階ごとの意味・アンカーの選び方・材料の取り場所）が `references/` の文書にある
- [ ] AC15: このリポジトリの open の課題で 1 回通し、マイルストーンごとの順位・切り出しの境界・前倒しと後ろ倒しの候補を承認資料に載せる
- [ ] AC16: 退行しないこと: 既存の `candidates` / `apply` / `report` の入出力と終了コード、8 つの区分と「やらない」の承認の扱い、マイルストーンを使わないリポジトリでの振る舞い（順位の算出と表の書き込みを飛ばす）が変わらない
- [ ] AC17: 順位の値は遅延コスト ÷ 大きさ^α で算出され、α は宣言と引数で変えられる（既定 0.3）。α=1 のときの順位は遅延コスト ÷ 大きさの降順と一致し、α=0 のときは遅延コストの降順と一致する
- [ ] AC18: 容量があるとき、容量 × 枠の割合（既定 0.5、切り捨て）の枠が、マイルストーンの中で遅延コストが最大の大きい課題（大きさが閾値以上、既定は尺度の上から 2 番目）の 1 切れ（枠に収まるサブイシューか課題そのもの）に先に当たり、切り出しの境界はそれを除いて算出される。枠に収まる切れが無い大きい課題は「分割が要る」として出力と報告に出て自動で分割されず、枠は順位の先頭からの切り出しへ戻る。容量が無いときは枠を出さない

- [ ] AC21: 段階の入力の UBV は実害の目安の区分を持ち、UBV の段階が区分の帯の外なら順位に入らず、番号と理由が出力に並ぶ。帯の下端を下回る UBV は、退避策が実際に止まるのを防いでいる（`防いでいる`）ときだけ受け付けられ、「部分的」「無い」では受け付けられない。区分と帯は宣言で変えられる

## 非機能の条件

| 性能・拡張性 | open 200 件・依存 400 本の入力で、順位のサブコマンドが GitHub への問い合わせを除いて 5 秒以内に終わる |
