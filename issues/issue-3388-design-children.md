各子の本文は、先頭の 1 行と「目的・対象範囲・受け入れ条件」の 3 節で起票する。先頭の 1 行は「11.x の子 `Z<数>`（[11.x の子の表](https://github.com/devbasex/ai-plugins/blob/develop/issues/issue-3388-design-children.md)）」である。「対象範囲」の対応表の行は、起票のときに要旨を添えて本文へ写す（行き先の事実は対応表が正本で、本文は起票した時点のコピー）。

### Z1

**題**: 契約と構造の検査: 契約の表を整理し、説明を契約から生成し、構造の規則とラチェットを CI で数える

- **目的**: 11.0.0 で作った契約の表（上限・止まった理由・事実）と構造の検査が、参照されない方針と手書きの説明を残したまま配られている。表を整理し、説明を契約から生成し、AI が陥りやすい作りを CI が数えて前の数より増やさない状態にする
- **対象範囲**:
  - 対応表の 3367-6・3367-9・3382-8・3395-2・3395-4、要求 306・324・325（ラチェット）・326・332・333
  - 結果 JSON の `items` に観点・分類・重さ・受け入れ条件の欄を足す契約（Z12 が使う）
- **受け入れ条件**:
  1. 上限の表の方針のうち参照されないものが 0 件になり、表を読む検査が参照の無い方針を落とす
  2. 契約の読み手は検証を 1 プロセスで 1 回だけ行う（同じ契約を 2 回読んでも検証の関数の呼び出しが 1 回）
  3. 契約の説明（`docs/` の表）は契約のファイルから生成され、手で直すと CI の差分の検査が落ちる
  4. 要求 306・324・326・333 の種類ごとに CI の規則があり、前の数を基準にしたラチェットが数を増やした PR を落とす
  5. 結果 JSON のスキーマの `items` が `lens`・`category`・`severity`・`acceptance` を任意の欄として持つ

### Z12

**題**: 多観点の設計レビュー: 設計 PR を観点ごとに独立したレビュー役で並列に見て、分類とあるべき姿を承認資料に載せてから起票する

- **目的**: 設計 PR の cross-review は文面を磨く場で、観点を変えたときに見つかる抜け（#1142 では 4 巡で約 200 件）を拾えない。設計承認ゲートの前に観点ごとの独立したレビューを並列に回し、範囲の外の指摘は分類とあるべき姿を人が読んでから起票する
- **対象範囲**:
  - #3388 の本文の「W: 多観点の設計レビューの工程化」のあるべき姿 1〜10 と指摘 10 件
  - 直す先（すべて入れ替えの後のもの）:
    - `design`・`cross-review` の Skill 本文
    - 工程の定義（`contracts/workflow/`）
    - 上限の表（`contracts/limits.json`）
    - 承認資料の組み立て
- **受け入れ条件**:
  1. 観点の一覧は、設計文書が触る領域（`design` の手順 1）と受け入れ条件から選ばれ、ファイルのパスでは選ばれない。設計の欠陥の種類（抜け・前提・規模・運用・移行・費用）が指摘の基準として渡り、「まず起きない条件」を理由に書かない側へ入れない
  2. 工程の定義で、多観点レビューを 1 つのアクティビティの中で観点の数だけ並列に広げられ、観点ごとに「見た・指摘なし」が結果 JSON に残る
  3. `standard` は必ず通り、`documentation` は文書の観点で、`legacy-refactor` は設計 PR を分けたときだけ通り、`light`・`operation` は通らない
  4. 1 巡の観点の数の上限・巡の上限（2 巡目は重さ critical の指摘が出た分類だけ）・1 巡の予算が `contracts/limits.json` にあり、上限に当たると手を広げずに止まる
  5. 前の巡のまとめと既存の Issue で重複が除かれ、同じ指摘を 2 回起票しない
  6. 範囲の外の指摘は分類ごとのあるべき姿と受け入れ条件の案にまとめられ、設計承認ゲートの承認資料の節「多観点レビューの分類」に載る。人がその承認ゲートで答えた後にだけ起票され、MVV 判定で通った承認ゲートでは起票せず、次に人が答える承認ゲートの承認資料へ持ち越す
  7. プロジェクトは `.ndf/` に観点（名前・選ぶ条件・指示）を足せ、既定の一覧に上乗せされる
  8. セキュリティの観点は OWASP Top 10:2025 に合わせ、A06 安全でない設計を設計の観点として使う

### Z5

**題**: 人への問いと工程の操作: 問い・status・介入・再開の契約と、信頼の境界の不変条件をそろえる

- **目的**: 問いの文・状態の取り出し・手で介入する操作・会話が切れた後の再開に契約が無く、AI が手順書から組み立てている。人が読む面と打つ面を契約にし、信頼の境界（部外者の文を指示にしない）を不変条件として 1 か所に書く
- **対象範囲**:
  - 対応表の 3365-2・3365-3・3365-5・3366-2・3366-5・3366-6、要求 311・312・313
  - 分類 H: 信頼の不変条件の全体、fork からの PR の扱い
  - 分類 I: 業務時間を見た問いの出し方、問いのまとめ方、問いの量の上限、`ndf trace`、識別子の統一、問いの文の避ける語の照合
- **受け入れ条件**:
  1. 問いの文・`status` の出力・介入の操作の一覧と答えの取り消しが契約のファイルにあり、契約の外の形を検査が落とす
  2. 要求とモード判定のエントリポイントがスクリプトの副命令になり、Skill 本文が判定の手順を持たない
  3. 会話が切れた後の再開のエントリポイントが 1 つの副命令で、結果 JSON に次に打つコマンドが入る
  4. 信頼の境界の不変条件が 1 か所の表にあり、fork からの PR の本文と差分を指示として渡さないことをテストが縛る
  5. 1 回の承認依頼にまとめる問いの数の上限が上限の表にあり、上限を超えた問いは次の依頼へ回る
  6. リリースプランがほかのプラグインの版も上げ、検査のフェーズレポートがラウンド数と指摘の数を返し、MVV の判定に設計 PR の設計文書が渡る（要求 311〜313）

### Z2

**題**: テストと CI と配る構成: 本物に当てる見本のジョブ、テストと CI の予算、配る構成の宣言をそろえる

- **目的**: テストの偽物と本物（GitHub など）の振る舞いの食い違いを見つける仕組みが無く、Python・uv の版・実験版の置き場の宣言が食い違っている。偽物の見本を本物で毎日確かめ、テストと CI の予算を置き、配る構成を 1 つの宣言にそろえる
- **対象範囲**:
  - 対応表の 3367-2・3379-2・3379-3・3380-7・3381-5・3395-9・3395-10
  - 分類 K: 本物に当てる毎日のジョブ、契約を 1 項目 1 ファイルにすること
- **受け入れ条件**:
  1. 偽物の見本を本物に当てる毎日のジョブがあり、食い違った見本の名前を出して落ちる
  2. 契約は 1 項目 1 ファイルで、1 項目を変えた PR の差分は 1 ファイルに収まる
  3. Python の下限が 1 か所の宣言にあり、ほかの置き場はそこから読む。CI の uv と Python の版が固定され、宣言と違うと検査が落ちる
  4. uv かネットワークが無いマシンで起動すると、無いものの名前と直し方を出して 0 以外で終わる
  5. テストの件数と CI のジョブの数に上限があり、超えた PR を検査が落とす。lock にあって使われない依存と、lock の部品で置き換えられる自作を検査が数える
  6. 実験版の置き場と呼び方が宣言にあり、既定で動くものから参照すると検査が落ちる

### Z3

**題**: 異常系と復旧: 障害の注入の定期演習、取り合い・共有の資源の障害・時計のずれで止まらない

- **目的**: 2 人のオーガナイザーが同じ Issue を取り合う、共有の資源（DB・GitHub）が落ちる、時計がずれる、といった異常で、工程が止まるか二重に動く。障害を定期的に注入して確かめ、縮退と再開の手順を持たせる
- **対象範囲**:
  - 対応表の 3377-3・3377-6・3377-7
  - 分類 M: 障害の注入の定期演習、時計のずれ、マシン全体の障害の印
- **受け入れ条件**:
  1. 同じ Issue を 2 つのオーガナイザーが取ろうとすると、片方だけが取れ、もう片方は理由を出して止まる
  2. 共有の資源の障害を注入すると、工程は止まった理由 `resource_unavailable` 相当を返して縮退し、資源が戻った後の打ち直しで落ちたステップから再開する
  3. 障害の注入のテスト（プロセスの kill・DB のロック・GitHub の 5xx・時計のずれ）が週 1 回のジョブで回り、注入した回数と復旧した回数が一致しないと落ちる
  4. マシン全体の障害の印（ディスクの残り・メモリの不足）が状態の取り出しに出る

### Z4

**題**: 費用・資源・規模: 予算の体系と、件数で確かめる規模の検査を置く

- **目的**: LLM の費用・GitHub API の枠・ディスクに予算が無く、規模の前提は 6 レーンのままで重なりの検査が O(n²) である。1 回・1 プラン・1 日の予算を置いて超えたら縮退し、規模の目標を件数で確かめる
- **対象範囲**:
  - 対応表の 3366-8・3368-4・3368-6・3393-1・3393-2
  - 分類 L: 予算の体系、`budget_exceeded`、超えたときの縮退、GitHub API の全体の枠
  - 分類 V:
    - 規模の目標、合成した規模の見本で回す性能の CI
    - `ndf check` の 1 回の走査とキャッシュ、起動の予算と重い依存の import の規則
    - 進行表の保持と索引、CI の履歴の取得とリンクの検査の差分への絞り込み
- **受け入れ条件**:
  1. 1 回・1 プラン・1 日の予算が上限の表にあり、超えると止まった理由 `budget_exceeded` を返して手を広げずに縮退する
  2. モデルの選び方とキャッシュの扱い、役割ごとに読む量の予算が宣言にあり、宣言の外のモデルを呼ぶと検査が落ちる
  3. ディスクの下限を下回ると、NDF が作ったものだけを片付けてから続け、片付けても足りなければ理由を出して止まる
  4. 合成した規模の見本は 50 レーン・150 プロセス・5 リポジトリ・Issue 1 万件である。この見本で、重なりの検査の比較の回数・GitHub API の呼び出しの回数・`ndf check` の走査の回数が宣言した上限以下であることを CI が回数で確かめる。一定時間流して合否を決める試験は置かない
  5. 計画の耐久ワークフローはループの 1 回ごとに実行を区切り、1 つの実行が積む記録の数が上限以下になる
  6. 副命令ごとの起動で読み込む重い依存の数を CI が数え、上限を超えた PR を落とす

### Z6

**題**: 汎用性: GitHub 以外のホスト・OS・言語・ランタイムの違いがあっても同じ工程で動く

- **目的**: 工程は GitHub.com・Linux・日本語・Python のリポジトリ・`gh` の認証済みを前提にしている。前提を宣言に出し、宣言で受けられない環境では理由を出して止まるようにする
- **対象範囲**:
  - 対応表の 3366-7・3378-8・3379-4・3379-5・3379-6
  - 分類 N: GitHub 以外のホスト、オフライン、shallow clone、submodule、LFS
  - 分類 O: GitHub Enterprise、英語、macOS の CI、Windows、Node のリポジトリでの試走
- **受け入れ条件**:
  1. `gh` の認証が無いと、最初の副命令が認証の手順を出して 0 以外で終わる
  2. GitHub Enterprise のホストを宣言で受ける。GitHub 以外のホスト・オフライン・shallow clone・submodule・LFS は、受けられるか、理由を出して止まるかのどちらかになる（黙って誤動作しない）
  3. 承認のラベルを利用先に作らず、利用先に無いラベルは理由を出して止まる
  4. 最初のスプリントまでの最小構成（宣言 1 つ）が文書とテンプレートにあり、Node のリポジトリで 1 スプリントを流した記録が Issue に残る
  5. macOS の CI のジョブがあり、英語の利用者向けの出力の切り替えが宣言で選べる
  6. Claude Code と Codex で同じ Skill 本文が通じない箇所の一覧があり、各箇所がランタイムごとの分岐か共通の書き方へ直っている。ai-plugins に固有の作り（パス・ブランチ名）が配る側の契約と依存に入っていないことを検査が確かめる

  - 分類 P: 外部 CLI の `--help` の照合、Actions の SHA での固定、Dependabot の cooldown

### Z11

### Z7

- **目的**: サービス（Factory）から NDF を呼ぶとき、共有の DB の名前空間・契約の版・事象の流れ・取り消しのエントリポイントが無く、1 人の開発者の端末の前提が残っている。外の呼び手が頼る面を表にし、表の外の参照を検査で落とす
- **対象範囲**:
  - 対応表の 3390-4・3390-7
