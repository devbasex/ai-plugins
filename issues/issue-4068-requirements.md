NDF の中継（`ndf relay`）の下で動く AI の会話は、裏で動く作業や監視の終わりを 1 時間以上待つことが多い。待つ間にプロンプトのキャッシュの寿命（1 時間）が切れると、待ちが終わった最初の応答で文脈の全体をキャッシュへ書き直し、入力の 2 倍の値段を払う。困るのは利用者で、定額のプランでは週の利用上限を早く使い切り、上限に当たると並行して進めている開発がすべて止まる。この課題では、キャッシュが切れる手前で NDF の hook が待っている会話を短く起こし、キャッシュを保つ。起こす費用の合計が書き直し 1 回分に届いたら、起こすのをやめる。起こす相手は、supervisor などの作業が裏に 1 件以上残っている会話だけである。監視（`ndf lanes wait` などの待つコマンド）だけを待つ会話は、そのコマンドが 540 秒か 600 秒で戻るたびに起きて張り直すので、今でもキャッシュの寿命の内に起きている。

**前に知っておくこと**（この課題の仕組みの要点）:

- **中継と子。** 中継（`ndf relay`）は、Claude Code の会話を包んで動かす NDF のプロセス（ラッパー）である。会話の出力と記録を見回り、引継ぎ・アカウントの切り替え・起動し直しを行う。中継が包んで動かす会話を「子」と呼ぶ。この課題が起こす相手は子である
- **オーガナイザー・レーン・conductor・supervisor。** NDF の並行開発では、作業の列（レーン）をいくつも並べて進める。1 つのレーンの工程を進める会話が conductor、レーン全体を見張る会話がオーガナイザーで、どちらも中継の下の子として動く。supervisor は、conductor が裏で（バックグラウンドで）起動して 1 つの工程を任せる別の AI の実行である
- **作業と監視。** 子が裏で待つものは 2 種類ある。分け方は #4049 が決めた
  - 監視: 決まった待つコマンド（`ndf lanes wait` など）だけを裏で動かし、状態の変化を知らせるもの
  - 作業: 監視でない裏の処理のすべて（supervisor の実行など）。終わると結果が子へ届き、子はそれを使って次へ進む

  作業が残る子を止めると、その作業を失う。作業は終わるまで子へ何も知らせないので、作業だけを待つ子は、作業が終わるまで起きない。監視の待つコマンドは、知らせが無くても決まった時間（`ndf lanes wait` は 540 秒、`ndf plan wait`・`ndf progress wait` は既定 600 秒）で戻り、子はその結果を見て張り直す。そのため、監視だけを待つ子はキャッシュの寿命（1 時間）の内に起きる
- **判断開始の値と運用上限。** #3995 が決めた、文脈の量の 2 つの目安である。判断開始の値（既定 250,000 token）以上では、切りのよい時点で新しい会話へ引き継ぐかを判断し始める。運用上限（既定 500,000 token）以上では、中継が子に引継ぎを求める。この課題は、どちらの値も使わず、変えない
- **起こす hook。** 子が 1 回の応答を終えるたびに（Stop）、NDF の hook が 1 つ裏で動く。hook はキャッシュが切れる手前まで眠り、その間に子が動かなければ、Claude Code の仕組み（`asyncRewake`）で子を起こす。子は Tool を呼ばずに 1 行だけ答えるので、文脈はキャッシュから安い値段（入力の 0.05 倍）で読まれ、寿命が延びる

> **注意（受け入れ条件 1 は変わり得る）**: この仕組みは、Claude Code の `asyncRewake` の振る舞いに頼る。頼る振る舞いは前提 2 に挙げた 11 項目で、Claude Code の版ごとに測る。起こす hook を働かせるのは、11 項目のすべてに通った版だけである。1 項目でも通らない版では働かせない。
>
> この課題は、2 つの Pull Request に分けて入れる（設計の決定 7 の「一覧に載せる手順」）。11 項目のうち 2 つは、マージした実装の hook の登録と会話の記録の読み取りを使わないと測れないためである。
>
> 1. 実装の Pull Request: 実装を、働かない状態（働かせてよい版の一覧が空）でマージする
> 2. 有効化の Pull Request: マージした実装で 11 項目を測り、通った版を一覧に載せて働かせる
>
> この課題が終わるのは、2 つ目の有効化の Pull Request を終えたときである。
>
> 11 項目のすべてに通る版が 1 つも無ければ、起こす hook はどの版でも働かず、今の振る舞い（何もしない）のまま残る。作業を失うことは無い。そのときは、通らなかった項目の測った結果（例えば、受け付けた `timeout` の長さ）に合わせて、受け入れ条件 1・起こす間隔の既定・費用の見積りを直す。直した受け入れ条件で承認を取り直す。

## 何が起きたか

2026-10-24〜11-22 の会話の記録（このマシンの `~/.claude/projects/` の全 810 本余りと、その下のサブエージェントの記録）を数えた。直前の文脈が 20,000 token 以上のメインの会話で、応答の間が 1 時間を超えたのは 276 回あった。そのうち 263 回は次の応答でキャッシュが当たらず、文脈を書き直した（書き直した合計は 44,641,212 token）。残りの 13 回は当たった（60〜65 分で 12 回、65 分〜2 時間で 1 回）。書き直した 263 回では、応答の間隔の中央値が 1.9 時間、直前の文脈の量の中央値が 172,812 token で、250,000 token 以上が 64 回あった。

| 応答の間 | キャッシュが当たった | 当たらなかった |
| --- | --- | --- |
| 5 分〜30 分 | 2,704 | 42 |
| 30 分〜55 分 | 493 | 28 |
| 55 分〜60 分 | 106 | 14 |
| 60 分〜65 分 | 12 | 15 |
| 65 分〜2 時間 | 1 | 144 |
| 2 時間超 | 0 | 104 |

モデルは主に Claude Opus 5.5 で、書き直しは入力の 2 倍、読み出しは 0.05 倍の値段である。172,812 token の文脈なら、書き直し 1 回は 345,624 token 相当、50 分ごとに起こして読み出す 1 回は約 8,600 token 相当になる（読み出しの分だけ。起こす文と 1 行の返事の費用は含まない）。

**起こしていたら費用はいくらだったか。** 起こす時点（最後の応答から 50 分）を越えた待ちは 435 回ある。上の 276 回（1 時間超）に、50〜60 分の 159 回を足した数である。そのうち 158 回は、起こさなくても自然に当たった。

| 応答の間 | 当たった | 当たらなかった | 計 |
| --- | ---: | ---: | ---: |
| 50 分〜55 分 | 39 | 0 | 39 |
| 55 分〜60 分 | 106 | 14 | 120 |
| 60 分〜65 分 | 12 | 15 | 27 |
| 65 分〜2 時間 | 1 | 144 | 145 |
| 2 時間超 | 0 | 104 | 104 |
| 計 | 158 | 277 | 435 |

この 435 回の全部を 50 分ごとに起こしていたとして見積もった。費用はどれも、入力の値段に直した token で数えた。

- 何もしない場合の費用: 116,007,698 token 相当。当たらなかった 277 回の、書き直しの追加の費用の和である。追加の費用は、書き直しの値段から読み出しの値段を引いた差で、キャッシュが当たっていれば払わずに済んだ分を指す
- 起こした場合の費用: 13,351,993 token 相当。次の 2 つの和で、自然に当たった 158 回にも掛かる起こす費用を含む
  - 起こした回ごとの読み出しと、起こす応答の費用（1 回 2,000 token 相当）
  - 起こす回数には上限がある（起こす費用の合計が書き直し 1 回分に届く回数。式は受け入れ条件 4）。待ちが上限より長く続くと結局書き直すので、その分
- 比: 13,351,993 ÷ 116,007,698 = 0.115。この規則で起こしていれば、何もしない場合の約 12% で済んだはずである（見積り）

式と内訳は設計の測った結果（[issue-4068-4199-design-measured.md](./issue-4068-4199-design-measured.md)）にある。

**この約 12% は、効果を多めに見た値である。** 435 回には、裏の作業を待っていたのではなく、質問の回答を待っていた・利用者が離れていただけの待ちも含む。この課題はそうした待ちを起こさない（「対象範囲」の「含まない」。#4071 が扱う）。2026-11-24 に、待ちの直前に裏で何が残っていたかで分けて数え直した。期間（2026-10-24〜11-22 の 30 日）と規則は同じだが、その後に記録が書き足されたため、合計は 445 回になった。表の費用は、どれも入力の値段に直した token（token 相当）の 30 日の合計である。

| 待ちの種類 | 回数 | 何もしない場合の費用 | 起こした場合の費用 | 比 |
| --- | ---: | ---: | ---: | ---: |
| 全部（数え直し） | 445 | 122,253,598 | 13,901,302 | 0.114 |
| 裏に作業が 1 件以上残る（この課題が起こす待ち） | 291 | 51,928,921 | 4,316,828 | 0.083 |
| 裏に監視だけが残る | 0 | — | — | — |
| 質問の表示中・何も残っていない（起こさない） | 154 | 70,324,677 | — | — |

監視だけを待つ子を起こす対象から外しても、見込みは変わらない。50 分を越えた待ちに、監視だけの待ちは 1 回も無かったからである。この課題が起こす待ちだけで数えると、起こした場合の費用は何もしない場合の約 8% になる。数え方は設計の測った結果（[issue-4068-4199-design-measured.md](./issue-4068-4199-design-measured.md) の「起こす対象を縮めた後の費用の見込み」）にある。

## なぜ困るか

#4049 で、裏の supervisor や `ndf plan queue` を待つ子は、止められずに待つようになった。待ちは supervisor の 1 工程・CI・承認の取り次ぎに及び、1 時間を越えることが多い（上で書き直した 263 回の、応答の間隔の中央値は 1.9 時間）。待ちが終わった最初の応答は、文脈の全体を入力の 2 倍の値段で書き直す。運用上限（500,000 token）近くの文脈では、その 1 回が約 1,000,000 token 相当になり、読み出し 1 回（約 25,000 token 相当）の 40 回分にあたる。定額のプランでは週の利用上限を早く使い、上限に当たると、並行して進めている開発の作業がすべて止まる（#4069 の配慮する事項 2「週の利用上限」）。

## 目的

- 中継の下で待つ子のプロンプトのキャッシュが、寿命の内に起こされて保たれ、待ちが終わった応答で文脈の全体を書き直さない状態にする
- 起こす費用が書き直し 1 回を上回る長さの待ちでは、起こし続けない状態にする
- 起こす間隔と起こす回数の上限を決める値が、設定ファイル（「上限の設定」と呼ぶファイルの集まり。上限でない値も置く。前提 8）の 1 か所にあり、記録から測った値で見直せる状態にする

## 対象範囲

含む:
- 中継の下で、裏に作業が 1 件以上残る子（作業を待つオーガナイザー・レーンの conductor）を、キャッシュの寿命の手前で起こすこと
- 起こすか起こすのをやめるかを、文脈の量・寿命・モデルの値段・起こした回数で決める式と閾値
- 子を起こす hook（Stop で裏に起動し、終了コード 2 で起こす）と、子がその後に動いた・起動が替わったときに古い hook が起こさない守り。hook を起動してよい Claude Code の版を中継が確かめて渡すこと
- 子の寿命・モデル・最後の応答の時刻を会話の記録から読むことと、記録の形が変わったときに起こさない側へ落ちること
- 起こす記録と、閾値を見直す集計
- 値の保存先（上限の設定）と手順書の直し（`relay.md` の hook の一覧・記録の種類）

含まない:
- 裏の作業が残る子を止めるかの判定（#4049）。この課題は作業の子を止めない
- 裏に監視だけが残る子。待つコマンドが 540 秒か 600 秒で戻るたびに子が起きて張り直すので、キャッシュの寿命の内に起きている。2026-11-18（11.0.0 のリリース）の後の中継の子で、監視だけを待って応答の間が 1 時間を越えた回は 0 回だった（2026-10-24〜11-22 と 11-15 以後を数えても 0 回で、2026-10-24〜11-22 の 50 分を越えた待ち 445 回にも監視だけの待ちは無かった。2026-11-15 以後に待つコマンドが戻った 1,022 回は、どれも 26 分以内だった）。起こしても当たる場面が無いので、監視だけの子を起こすことも、監視だけの大きな子を新しい会話へ引き継ぐことも、この課題では行わない。監視だけの大きな子が張り直すたびに払う読み出しの費用を抑えることも含まない（文脈の量で新しい会話へ切る判断は #3995 が持つ）
- 監視だけを待つ子のうち、待ちのコマンドの戻りが寿命（1 時間）を越え得る子。待ちのコマンドに長い待ち時間を指定すると、戻るのが 1 時間を越えることがあり、そうした子は起こさない。具体的には次の 2 つである。`ndf ci watch` で、渡した予算（`--budget`）に、予算に数えない CI のランナーの割り当て待ちを足した時間が 1 時間を越える子。`ndf plan wait`・`ndf progress wait` に 1 時間以上の `--timeout` を渡した子。寿命の内に戻らなければ書き直しを 1 回払う（今と同じ。実測で 0 回）。この課題の範囲の外とし、起こさない
- 待ちをオーガナイザーへ知らせて別のレーンを起動すること（#4070）
- 次の 3 つ（どれも #4071 で扱う）
  - 後の工程で再利用できる supervisor・conductor を待機させる条件と、待機を終える条件
  - 裏の作業の無い待ち（承認ゲートの回答待ち・利用者の入力待ち）
  - サブエージェントの supervisor のキャッシュ（寿命 5 分）
- 待ちが終わった後に、書き直しを済ませた子の引継ぎを早めること（文脈の量で切る判断は #3995 が持つ）
- 中継の外の会話と Codex（中継は Claude Code だけを包む）
- 文脈の量の閾値の値（#3995）と、利用上限でアカウントを替える判定（#3604・#3864。lracct）
- 確定仕様の書き換え（確定仕様化の工程で直す）

#4071 との関係: #4071 は、この課題で作る起こす回数の式（受け入れ条件 4）・値（受け入れ条件 13）・起こす記録（受け入れ条件 11・12）を使って、自分の受け入れ条件 2・3 を満たす。この課題が #4071 の受け入れ条件を満たす作業はしない。境界は設計の決定 12 にある。

## 前提

- 前提 1: キャッシュの寿命は、キャッシュを書くか読む要求の始まりから数え、読むたびに追加の費用なしで延びる（公式の文書）。子を起こして文脈を読ませれば、寿命はその時点から延びる
- 前提 2: 裏で動く hook（`asyncRewake`）は、終了コード 2 で終わると入力を待つ会話をすぐに起こし、標準エラーの文を system reminder としてモデルへ渡す。Claude Code は `asyncRewake` の hook にも `timeout` を課す（公式の文書と 2026-11-22 の実測）。この仕組みが頼る次の 11 項目は、無効のまま入れた実装を使って Claude Code の版ごとに測る（「注意」）。11 項目が確かめるのは、大まかに次の 4 つである。長く眠った後に会話を起こせるか（1〜3）。起こした文を利用者の入力や質問への答えと取り違えないか（4〜8）。どの応答の後の hook かを決められ、登録が意図した会話でだけ効くか（9・10）。足す負担が小さいか（11）。11 項目のすべてに通った版でだけ働かせる（番号は設計の決定 7 の「測る 11」と同じで、そこに測り方がある）
  1. 長い `timeout`（3,300 秒）を受け付け、50 分眠った hook が子を起こせる
  2. 起こす鎖（起きた応答の Stop が次の hook を起動し、それを繰り返すこと）を続けても、Claude Code の続行の回数の上限に掛からない
  3. 会話を終えると、眠っている hook も終わる
  4. 質問の表示中に起こしても、質問の答えにならない
  5. 起きた応答の前に発火する UserPromptSubmit の入力に、起こす文が頭（`【ndf-relay】`）のまま載る（受け入れ条件 10 の見分けに使う）
  6. Stop の時点で、会話の記録の最後の応答が、Stop の入力の応答と同じ文で載っている（受け入れ条件 7 の確かめに使う）
  7. 応答の始まりが利用者の入力・裏の作業の知らせ・起床のどれでも UserPromptSubmit が発火し、その時刻が前の応答の記録の時刻より後になる（受け入れ条件 2 の確かめ直しに使う）
  8. 起こす文が会話の記録に残る形を、利用者の入力と裏の作業の知らせと見分けられる。起こした直後に別の入力が先に応答を始めても、起こす文が後から別の応答として届かない（受け入れ条件 4・8 に使う）
  9. Stop と今回の応答を 1 つに結べる。2 つの hook が同じ応答を取り合う順が起きても、どちらも起こさない（受け入れ条件 2 に使う）
  10. 中継が `--settings` で渡した登録が、プラグインの登録と並んで動き、`--resume` で起動し直した子でも効く。子の中で起動した別の claude では起動しない
  11. 足す負担が、避けられない分に収まる。hook の登録は起こす対象の Stop だけに絞れないので、対象でない Stop でも hook のプロセスが 1 つ起動する。そのため、足す起動の数は今ある Stop の hook の起動の数とほぼ同じになり、合わせると約 2 倍になる。これは避けられないので、その上に増える分が小さいことを、次の 3 つですべて確かめる（測り方は設計の決定 7 の 11）
     - 1 回の処理の時間が、95 パーセンタイルで 500 ミリ秒以内である（応答の終わりを遅らせない）
     - 1 日に足す起動の数（Stop ごとの 1 回と、中継が版を確かめるための起動の和）が、今ある Stop の hook の 1 日の起動の数の 1.1 倍以内である（例: 今が 1 日 1,000 回なら、足す起動は 1,100 回までで、合わせて 2,100 回まで。1 割の余裕は版を確かめる起動だけに当てる）
     - 1 日に足す処理の時間（眠っている間を除く CPU 時間。経路ごとに測り、回数で重みを付ける）の合計が、今ある Stop の hook の 1 日の処理の時間の合計以内である

  11 項目のすべてに通る版が 1 つも無ければ、起こす hook は働かず今の振る舞いのまま残る。そのときは、通らなかった項目の測った結果に合わせて起こす間隔・費用の見積り・受け入れ条件 1 を直し、承認を取り直す（受け入れ条件の前の「注意」）
- 前提 3: 子を起こす応答は、子の会話へ目印つきの入力 1 件と 1 行の返事を足す（1 回に数百 token）。起こす回数の上限が子の文脈を運用上限まで押し上げることは無い
- 前提 4: 費用の比べは、API の従量課金の料金の比（入力に対する書き込みと読み出しの倍率）で行う。定額のプランが週の利用上限に書き込みと読み出しをどの比で数えるかは公開されておらず、同じ比で近似する（確かめ方は設計の「未確認のまま残ること」）
- 前提 5: 起きた応答の前に UserPromptSubmit が発火する（実測）。その入力を中継の入力として見分ける形（起こす文の頭か中継の目印）は、前提 2 の実測で決める
- 前提 6: この課題の実装は #3995 → lracct（#3604・#3864。中継が、利用上限に当たったアカウントから別のアカウントへ子を切り替えて続ける仕組み）→ #4049 の実装の後に行う（4 件の実装は 2026-11-24 までにリリース済み）。#4049 からは、裏の作業を作業と監視に分ける関数だけを使う。待つ子かどうかは、Stop の入力の裏の作業の一覧（`background_tasks`）をその関数で分けて決め、#4049 が書く記録のファイルは読まない
- 前提 7: NDF は普及のフェーズの前で、記録の行と上限の設定の形を変えても互換の経路を持たない（MVV Value 4。MVV は NDF の使命・目指す姿・価値を書いた正本 `.ndf/mvv.md` で、Value 4 は「どのプロジェクトでもそのまま使える」。普及の前は、その汎用性だけを守り、後方互換は持たない）
- 前提 8: 「上限の設定」は、NDF の調整できる値を置く設定ファイルの集まりの呼び名である。名前に「上限」とあるが、上限でない値（余白・倍率・版の一覧など）も置く。`plugins/ndf/contracts/limits/` に、方針 1 つにつき 1 ファイルで置く。2026-11-24 に 1 つの `limits.json` から分かれた（#3687）。原文と起票者の推定 S2 の `limits.json` は、この上限の設定を指す
- 前提 9: #4199（寿命の補い方と費用の数え方の直し）は、この課題へ統合し、同じ設計の Pull Request で一緒に設計する。寿命の補い方と費用の数え方は #4199 の受け入れ条件が決め、#4068 の設計書と詳細設計書はそれを含めて書く。実装も 1 つにまとめる
- 前提 10: 会話の記録を読む部品（今回の応答の確かめと文脈の量の読み取り。`adapters/transcript.py` の `read_tail`・`last_context`・`timestamp_seconds`）は、#4089 の設計にある。#4089 は 2026-11-24 の時点で未実装である。この課題を #4089 より先に実装するなら、この課題の実装の中で、#4089 の詳細設計のとおりにその部品を作る（#4089 の設計の「#4068 の実装」）。#4089 が先なら、それを使うだけにする

## 受け入れ条件

この節の語の意味は次のとおりである。

- 「待つ子」: 中継の下の子のうち、直前の応答を終えた時点（Stop）で、裏に作業が 1 件以上あり、回答待ちの質問が無い子。作業と一緒に監視があってもよい。件数は、Stop の hook が受け取る入力の裏の作業の一覧（`background_tasks`）を、#4049 の作業と監視の分け方の関数で数える。#4049 が書く記録のファイルは読まない（前提 6）。裏に監視だけが残る子は待つ子に入らない（「対象範囲」の「含まない」）
- 「最後の応答の時刻」: 子の会話の記録の最後の応答（`assistant` の行）の時刻
- 「起こす hook」: 子の Stop で裏に起動し（`asyncRewake`）、起こすときに終了コード 2 で終わる NDF の hook
- 「起こす状態」: 会話ごとに 1 つ置く、起こす hook どうしが共有する記録。寿命・今の待ち・起こした回数・世代などを持つ
- 「世代」: 起こす状態の項目の 1 つ。hook は応答のたびに 1 つずつ起動して裏で眠るので、眠っている hook が同時にいくつもあり得る。世代は、そのうち起こしてよい hook を 1 つに決める印で、最新の出来事（応答・利用者の入力・起床）の時刻と、それを書いた hook を持つ。新しい出来事で書き換わり、古い hook は起こさずに終わる
- 「子を止めるロック」: 中継が子を止めるときに取るファイルのロック。起こす hook と UserPromptSubmit の guard も、起こす状態を読み書きするときに同じロックを取る。同じ会話の状態を、同時に 1 つの処理だけが書き換えるようにするためである

- [ ] 1. 待つ子の最後の応答の時刻から起こす間隔（キャッシュの寿命 − 余白。1 時間の寿命の既定で 3,000 秒）が過ぎたとき、起こす hook は終了コード 2 で終わって子を 1 回起こす。起こす間隔の 1 秒手前では起こさない。寿命が 5 分の応答では、余白の値によらず起こさない（余白を 300 秒より短くしても起こさない）
- [ ] 2. **起こす直前に子の様子を確かめ直し、状況が変わっていれば起こさない。1 つの会話を同じ時点に起こす hook は 1 つだけになる。** 細目は次のとおり
  - 起こす hook は、その hook を起動した Stop の後、起こす直前の確かめ（子を止めるロックの中）までに次のどれかがあれば、起こさずに終了コード 0 で終わる
    - 同じ会話で新しい Stop があった
    - 同じ会話で利用者の入力（UserPromptSubmit）があった
    - 中継の今の起動が、その hook の起動と違う（起動し直した）
    - 回答待ちの質問がある
  - 遅れて動いた古い Stop の hook も起こさず、起こす状態と起こす記録を書き換えない
  - 例外（取り合い）: **2 つの hook が同じ応答を自分の Stop の応答として取りに来たら、どちらの hook も起こさない。** その待ちが寿命を越えれば、書き直しを 1 回払う（今の振る舞いと同じ）。取り合いは、古い Stop の hook の動き始めが次の応答の記録より遅れたときだけ起き、どちらが新しい Stop の hook かを決められない。確かめることは次の 5 つである（仕組みと理由は設計の決定 4）
    - 後から来た hook は、起こす状態の世代に取り合いの印（`contested`）を書く
    - 先に取った hook がその応答で待ちを始めていて、まだ起こしていなければ、後から来た hook がその待ちを取り消し、取り消したことを起こす記録に残す
    - 先に取った hook は、眠る間に世代が替わったのを見て、何も書かずに終わる
    - 集計は、取り消した待ちを数えない
    - 印と待ちの取り消しのほかは、起こす状態も起こす記録も書き換えない。続きは次の Stop の hook が今までどおり決める
  - 入力の `session_id` が中継の渡した会話の ID と違う会話（子の中で起動した別の claude）では、起こさず、起こす状態も変えない
  - 起こす直前の確かめの後に届いた入力は止められず、起こす文と競合する。その起床の当たりは判定しない（設計の決定 6）
- [ ] 3. 起こす hook は、中継が渡す環境変数（`asyncRewake` に対応すると確かめた Claude Code の版でだけ渡す）が無ければ、眠らずにすぐ終了コード 0 で終わる。中継の外の会話と、Stop が裏で動かない版では、応答の終わりを待たせない
- [ ] 4. **1 つの待ちで起こす回数には上限 `n_max` があり、上限に達したら、その待ちではそれ以上起こさない。** 細目は次のとおり
  - 上限は `n_max = floor((w − r) × S / (r × S + d))` である。`S` は待ちの始まりの文脈の量、`w` は寿命の書き込みの倍率、`r` はモデルの読み出しの倍率、`d` は起こす応答 1 回の費用を表す。Opus 5.5・1 時間の寿命・`S` = 400,000・`d` = 2,000 で 35 になり、値を差し替えると差し替えた値で決まる
  - 1 つの待ちは、待つ子の Stop で始まる。終わるのは、利用者の入力か裏の作業の知らせで始まったと確かめた応答の Stop である
  - 次の応答の Stop では、待ちは終わらない: 起こす文で始まった応答。始めた入力が利用者の入力・作業の知らせ・起こす文のどれかを、記録から見分けられない応答
  - ただし、**待ちの間に起こす文でない入力が届いたと分かっていれば、記録からその入力を読めなくても、待ちを終える。** 届いたことは、利用者の入力を受けたときに動く NDF の hook（UserPromptSubmit の guard）が起こす状態に残す（設計の `opened`）。記録から読めないのは、通常の入力の後に大きな Tool の結果が続き、hook が読む会話の記録の末尾の範囲から入力の行が外れたときである。このとき、終えた待ちでキャッシュが当たったかと読み出しの量は、証拠が無いので記録しない（null）
  - 次の待ちでは回数を 0 から数え、上限をその始まりの文脈の量で決め直す
- [ ] 5. （外した。2026-11-24）元は、監視だけを待つ大きな子に、費用の予算に収まる最後の起床で新しい会話へ引き継ぐよう求める条件だった。監視だけの子を起こす対象から外したので（「待つ子」の定義と「対象範囲」の「含まない」）、引き継ぎを求める場面が無い。後の条件の番号は、ほかの文書の参照を保つために詰めない
- [ ] 6. 寿命は、その子の最後の応答の `usage` の寿命別の書き込みで決める（1 時間の書き込みがあれば 1 時間、5 分だけなら 5 分）。2 つの書き込みの値が両方 0 の応答の寿命は、#4199 の受け入れ条件 1〜4 が決める（前に分かった寿命で補い、分からなければ起こさない）。読み出しの倍率は記録のモデルで決め、上限の設定に無いモデルは既定の倍率を使う
- [ ] 7. **会話の記録から今回の応答を確かめられないときは、起こさない。前の応答へさかのぼって代わりに使わない。** どの場合も終了コード 0 で終わり、理由ごとに、その会話で 1 度だけ記録に残す

  | 場合 | 扱い |
  | --- | --- |
  | 会話の記録が読めない | 起こさない。次の Stop で読み直す |
  | 今回の応答がまだ記録に無い（記録の最後の応答が、今回の Stop の応答（Stop の入力の `last_assistant_message`）と違う。1 つ前の応答だけが完全に残っているときも含む） | 起こさない。次の Stop で読み直す |
  | 記録の形が違う（最後の応答に `usage`・時刻・寿命別の書き込みの項目が無い、または項目の型が違う） | 起こさない。読み直さず、その会話では起こすのをやめる（「何を足すか・変えるか」の表） |

  寿命別の書き込みの項目がそろい、値が両方 0 の応答は、形の違いではない（受け入れ条件 6）
- [ ] 8. 起こす文から始まった応答の `usage` の読み出しが、起こす前の文脈の量の 9 割未満なら（キャッシュが当たらなかった）、その会話では起こすのをやめ、理由を記録に残す。起こした後に、起こす文より先に別の入力（利用者の入力など）が届き、子がそれに先に答えたときは、その先を探さずに当たりを判定しない
- [ ] 9. 待つ子でなく、待ちも起こしたフラグ（起こした直後に状態へ書く印）も持たない会話の Stop（中継の外を含む）では、起こす hook は会話の記録を読まずに終わる（読み取りの回数が 0 回）。待つ子でも、眠る間は会話の記録を読み直さない
- [ ] 10. 起きた応答（起こす文で始まった応答）で、#3995 の数え手（判断開始の値の知らせを、利用者の入力ごとに数え直すカウンター）が、利用者の入力として数え直さない
- [ ] 11. 待ちの始まり・起こした・起きた応答の結果・待ちの終わり（当たったか書き直したか）・やめた、のそれぞれで、起こす記録に 1 行を書く。行は待ちの ID でつながり、文脈の量・寿命・モデル・起こした回数・上限と、応答の行は読み出しと書き込みと出力の token を持つ
- [ ] 12. 集計のコマンドが起こす記録から、次の値を返す。集計の項目はここが持ち、#4199 の受け入れ条件はここの項目の数え方を決める
  - 待ちの数・起こした回数・当たりの率・待ちの長さの分布
  - 2 つの中央値。1 つは起こす応答 1 回の費用の中央値（値 `d` の見直しに使う。書き込みと出力の費用の和）。もう 1 つは起こした応答 1 回の実費の中央値（読み出しの費用も含む）。どちらも書き込みの費用は #4199 の受け入れ条件 5 で数える
  - 避けた書き直し。1 つの待ちで最大 1 回と数え、2 つの値を別の項目で返す。1 つは避けた書き直しの文脈の量（token）。もう 1 つは正味の節約で、書き直しの追加の費用（`(w − r) ×` その量）から、その待ちで起こした実費の合計を引いた値
  - 起こした応答の費用を記録から数えられず、避けた書き直しの集計から外した待ちの数（#4199 の受け入れ条件 8 の待ちを含む）
- [ ] 13. 次の値は上限の設定（前提 8）にだけ置き、起こす hook と中継がそこから読む。集計は、起こす hook が記録に書いた同じ値で費用を出す
  - 起こす間隔の余白
  - 寿命ごとの書き込みの倍率
  - モデルごとの読み出しの倍率
  - 起こす応答 1 回の費用
  - 出力の倍率（起こす応答の出力の費用を数える）
  - 確かめ直す間隔（眠っている hook が、起こしてよいかを確かめ直す間隔）
  - 起こす hook を働かせてよい Claude Code の版
- [ ] 14. 起こす文は、Tool を呼ばずに 1 行で答えて応答を終えるよう求める。子が Tool を呼んだときも、次の起こす時点は最後の応答の時刻から数え直す
- [ ] 15. 設計文書が、利用者の全体の設計方針（#4069）と MVV の Value 2（安く使える）に合っているかを突き合わせた結果を、決定の 1 つとして持つ（設計レビューで確かめる）
- [ ] 16. 1〜14 を、時刻を差し替えた時計と、文脈の量・起こした回数の境界の値（間隔 − 1 秒・間隔、上限 − 1・上限）で確かめるテストがある。時間で区切る試験にせず、.md の文言を照合するテストにしない

| 公開インタフェース（hook） | 中継が子の起動にだけ `--settings` で渡す hook の登録に、Stop の裏の hook が 1 つ増える。プラグインの hook の登録（`hooks/claude.json`）には足さないので、中継の外の会話は変わらない |
| 公開インタフェース（環境変数） | 中継が子へ渡す環境変数が 1 つ増える |
| 公開インタフェース（コマンド） | 集計のサブコマンドが 1 つ増える |
| データ | 中継の保存先に起こす記録が増える。ラッパーの記録と同じく手元に残り、同じ掃除の対象になる。リポジトリへはコミットしない |
| 既存の振る舞い | 待つ子は起こす間隔ごとに 1 回、短い応答をする。子の会話に起こす文と 1 行の返事が残る。中継の下の子の Stop ごとに、裏の hook のプロセスが 1 つ起動する（待つ子でなければすぐ終わる）。監視だけを待つ子を含め、待つ子でない子は今と同じ |

## 用語

| 用語 | 意味 |
| --- | --- |
| 中継・ラッパー | `ndf relay` が Claude Code の会話を包んで動かすプロセス。会話の出力と記録を見回り、引継ぎ・アカウントの切り替え・起動し直しを行う |
| 子 | 中継が包んで動かす Claude Code の会話 |
| オーガナイザー・レーン・conductor | 並行開発で、並べて進める作業の列がレーンである。1 つのレーンの工程を進める会話が conductor、レーン全体を見張る会話がオーガナイザーで、どちらも中継の下の子として動く（`docs/ndf-parallel-model.md`） |
| supervisor | conductor が裏で起動し、1 つの工程を任せる別の AI の実行 |
| 作業・監視 | 子が裏で待つものの 2 種類（#4049 の分け方）。監視は、決まった待つコマンド（`ndf lanes wait` など）だけを動かし、状態の変化を知らせるもの。作業は、監視でない裏の処理のすべてで、終わると結果が子へ届く |
| 判断開始の値・運用上限 | #3995 が決めた文脈の量の 2 つの目安。判断開始の値（`context.decide-from`。既定 250,000 token）以上では、切りのよい時点で引継ぎへ切るかを判断し始める。運用上限（`context.limit`。既定 500,000 token）以上では、中継が引継ぎを求める |
| 数え手 | #3995 の、判断開始の値の知らせを利用者の入力ごとに数え直すカウンター。中継が送る入力では数え直さない |
| キャッシュの寿命 | プロンプトのキャッシュが、書くか読む要求の始まりから保たれる時間。Claude Code のメインの会話は 1 時間、サブエージェントは主に 5 分（実測） |
| キャッシュを起こす | 寿命の内に待つ子を起こして短く応答させ、文脈を読み出しの値段で読ませてキャッシュの寿命を延ばすこと |
| 起こす hook | 子の Stop で裏に起動し（`asyncRewake`）、起こす時点に確かめ直して、起こすなら終了コード 2 で終わる NDF の hook |
| 起こす記録 | 起こす hook が中継の保存先に書く、起こした・やめた・書き直したの行の記録 |
| 起こす間隔 | 最後の応答の時刻から起こすまでの秒。寿命から余白を引いた値 |
| 確かめ直す間隔 | 眠っている起こす hook が、起こしてよいか（子がその後に動いていないか）を確かめ直す間隔 |
| 起こす回数の上限 | 起こした費用の合計が、書き直し 1 回の追加の費用 `(w − r) × S`（書き直しの値段 `w × S` から、起こして当たったときにも払う読み出しの値段 `r × S` を引いた差）を上回らない最大の回数。式は受け入れ条件 4 |
| 書き直し | キャッシュが切れた後の応答で、文脈の全体をキャッシュへ書き込むこと（キャッシュの再書き込み。入力の 1.25 倍か 2 倍の値段） |
| 守り 1 | 中継のアカウントの切り替えの 1 つ目の守り。利用上限の閾値の手前で、同じ会話を別のアカウントで `--resume` して続ける（確定仕様 `ndf-relay-account-switching.md`） |
| lracct | #3604・#3864 の、利用上限に当たったアカウントから別のアカウントへ子を切り替えて続ける中継の仕組み |
| MVV | NDF の使命・目指す姿・価値を書いた正本（`.ndf/mvv.md`）。Value 2 は「安く使える。待機する文脈は、プロンプトのキャッシュの寿命の内に使うか、必要ならキャッシュを起こす。起こす費用が見合わなければ待機を終える」 |
