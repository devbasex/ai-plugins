## 何が起きたか

2026-11-22 から 11-24 にかけて、実際には別のファイルしか変えない開発作業どうしが、順番待ちになった。

NDF は、複数の開発作業の列（レーン）を同時に進める。その一覧が「並列の計画」である。これまで、各レーンは変える予定の場所（`touches`。以下「宣言」）を先に申告し、NDF は宣言が重なるレーンを同時に進めなかった。宣言がフォルダ（ディレクトリ）の単位で書かれていたため、別のファイルしか変えないレーンも重なると扱われた。

この文書で使うほかの言葉は次のとおりである。

- **オーガナイザー**: 並列の計画のまとめ役の AI（conductor と呼ぶ役割の 1 つ）
- **行**: レーンの中の 1 件の作業（スプリント。1 回のリリースとして出す課題のまとまり）。1 つのレーンは行を順に進める
- **単位の PR**: 行の作業をレビューの単位（1 つの課題か、まとめて見る複数の課題）に分け、単位ごとに出す変更の申請（Pull Request）
- **`after`**: 前のレーンの終わりを待つ指定

実際に待ちが起きた例は次の 2 つである。

- 計画 p12 では、ある課題（ https://github.com/devbasex/ai-plugins/issues/3995 ）の作業が約 24 時間止まった。11-22 11:53 JST にこの課題の「計画」の工程を終えてから、実装の最初の単位の PR（ https://github.com/devbasex/ai-plugins/pull/4216 ）を出すまで、何もしていなかった。AI のアカウントの切り替えを直す別のレーン（ https://github.com/devbasex/ai-plugins/issues/3604 ）と、同じフォルダ `relay/` を宣言していたためである。実装そのものは約 5 時間で終わった
- 計画 p9 では、あるレーンが製品のプログラムの大部分が入るフォルダ `plugins/ndf/src/` 全体を宣言していた。2026-11-24 に別の不具合を直すレーン（ https://github.com/devbasex/ai-plugins/issues/4049 ・ https://github.com/devbasex/ai-plugins/issues/4068 ）を足したときも、変えるファイルが重ならないかを確かめる手段が無く、`after` で順序を付けるしかなかった

逆向きのことも起きた。宣言の外のファイルまで変えたレーンがあり、その変更が同じ時間帯に動いていたほかのレーンと重なったことは、だれにも知らされなかった。

利用者はこの日、宣言の外のファイルを変えることを禁じる方向では解かないと決めた（2026-11-24）。重複の排除・モジュール化・ライブラリ化（プログラムを整理して直しやすくする作業）のために変える範囲が広がるのは、より重要な方針に沿った動きだからである。

### エンジニア向けの補足

- p12 で `relay/` を宣言していた相手はレーン lracct である
- p9 で `plugins/ndf/src/` 全体を宣言していたのはレーン lz1-contract、後から足したのはレーン lrelay である
- p9 のレーン lsplit（ https://github.com/devbasex/ai-plugins/issues/3877 ・ https://github.com/devbasex/ai-plugins/issues/3908 ・ https://github.com/devbasex/ai-plugins/issues/4036 ）は `progress/`・`core/plan/`・`contracts/workflow/` などを宣言したが、マージした単位の PR は宣言の外の `domains/relay/hub.py`・`domains/hooks/guards/relay_mark.py`・`core/worker.py`・`contracts/worker/kinds.json` なども変えた。知らされなかった重なりの相手は、p12 の lctx の `hooks/` と、後から足した lrelay の `relay/` である

## 種類

機能追加。今の版（11 系）でも、仕組みがこれまでしてきたことは「宣言が重なる行を同時に動かさない」だけである。宣言を詳細設計から出すことと、実際に変えたファイルで重なりを知らせることは、これまで仕組みに無かった。

## 今の姿

今の版（11 系）でも、並列の計画はこれまで、宣言（`touches`）が重なるかどうかだけで、レーンを同時に進めるかを決めていた。実際に変えたファイルは見ていなかった。宣言の書き方は [parallel-plan.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/issue-plan-strategy/references/parallel-plan.md) にある。

- 計画を受け付けるときの検査は、別のレーンの行どうしで宣言が重なり、どちらを先にするかが決まっていなければ、計画を誤りとして断っていた。この検査を、以下「I13」と呼ぶ
- 別のレーンの行どうしの順番は、`after` で決める。1 つのレーンの中の行は並び順に進むので、`after` で指定した相手より前に並ぶ行も、先に終わるものとして扱う
- フォルダを宣言すると、その中のすべてのファイルと重なるとみなしていた
- 宣言はレーンごとに 1 つで、行ごとには持っていなかった
- 宣言を直すのはオーガナイザーで、コマンドを手で打っていた
- 設計の文書には、これまでも変えるファイルが書かれていた。1 つは設計書の「設計の結果」の欄の「触るファイル」である。もう 1 つは、詳細設計書を別のファイルにしたときの、ファイルの配置を示す一覧（以下「地図」）である。これまではどちらも宣言に使っていなかった

### エンジニア向けの補足

- I13 は、計画の検査（`ndf lanes init`・`start`・`set`・`lane add`）の規則の番号である（[parallel-checks.md の「レーンの間の重なり」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/parallel-checks.md)）
- これまでの重なりの判定は接頭辞か glob で行っていた。`relay/` と `relay/hub.py` は重なる（`plugins/ndf/src/ndf/progress/lane/rules.py` の `touch_hit`）
- `touches` はパスか glob の並びで、これまではレーンに付いていた（`plugins/ndf/src/ndf/progress/lane/types.py` の `LaneSpec`）
- 宣言を直すコマンドは `ndf lanes set <計画> <レーン> --touches ...` である
- 地図は、詳細設計書の「ファイル配置と依存の向き」を指す（[document-roles.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/requirements-design/references/document-roles.md) の「文書ごとの読み手と順序」）
- これまでの判定の振る舞いは `plugins/ndf/tests/progress/test_lane.py` の `test_touch_hit`・`test_touch_overlap_errors_as_they_are_now` が確かめている（2026-11-24、main `ea401b56a` で通過）

## 何を足すか・変えるか

| | 今 | 足した後 |
| --- | --- | --- |
| 宣言の出所 | オーガナイザーが計画を組むときにフォルダの単位で書き、手で直す | レーンの設計 Pull Request が承認されてマージされると、そのレーンの宣言は、設計で確定した変えるファイルの一覧に置き換わる。一覧の元は、設計書の「設計の結果」の触るファイルである。詳細設計書を別のファイルにしたときは、その地図に載ったファイルも合わせる |
| 実際に変えたファイル | 見ない。宣言の外の変更はだれにも知らされない | 単位の PR で実際に変えたファイルを、機械がレーンの行に記録する。この記録は重なりの知らせだけに使い、宣言には足さない。同じ時間帯に動くほかのレーンの宣言か記録と重なれば、オーガナイザーへ知らせる。I13 は記録を使わず、宣言だけを見る |
| 宣言の外の変更 | 禁じる決まりは無い | 禁じる決まりを足さない（今と同じ） |
| 設計の結果が無い・読めないとき | — | 今の宣言のまま動く。詳細設計書を別のファイルにしたのに、その地図を読めないときも同じ |

## 今の利用者への影響と互換

- 宣言が狭まるので、今は I13 で断られる組の一部が、同時に実装へ進めるようになる
- 宣言の外のファイルを変えて、ほかのレーンと重なったときは、知らせを受けたオーガナイザーが順序を決める。知らせを受けてもレーンは止まらない
- 計画の JSON の形（`touches` の並び）は変えない

## なぜ困るか

フォルダ単位の宣言のままでは、変えるファイルが重ならないレーンも、片方がまるごと待つ。p12 では、実装は約 5 時間なのに、24 時間を待ちに使った。並列開発の方針（処理待ちを作らない、 https://github.com/devbasex/ai-plugins/issues/4069 ）に反する。

一方、これまで宣言の外へ広がった変更は、ほかのレーンと重なっても知らされなかった。2 つの変更を取り込む（マージする）ときにぶつかって、初めて気づくことになった。

## 目的

- レーンの触る場所を、詳細設計で確定したファイルの単位で持ち、見かけの重なりでレーンを待たせない
- 実装の途中で触る範囲が広がっても止めず、広がった結果ほかのレーンと重なれば、オーガナイザーがすぐ知って順序を決められる

## 対象範囲

含む:
- 設計の承認（設計承認ゲート）の後に、設計で確定した変えるファイル（「設計の結果」と、別のファイルにした詳細設計書の地図）で、レーンの `touches` をファイル単位に置き換えること
- 単位の PR で実際に変えたファイルをレーンの行に記録し、ほかのレーンと重なればオーガナイザーへ知らせること（別の計画のレーンも含む）。記録は I13 の判定に入れない
- 設計の結果が無い・読めないとき、または別のファイルにした詳細設計書の地図を読めないときに、今の宣言のまま動くこと
- 行より細かく、レビューの単位ごとに宣言を持つかを設計で比べること（採るなら受け入れ条件 7 を満たす）
- 実装に入る前に宣言を確定させる方法を決めること（#4050 は、実装に入る前に宣言が確定していることを前提にする）
- 次の 2 つの形の得失を設計で比べること。先に宣言して、重なる作業を同時に進めない（排他）形と、ぶつかってから最新の本流を取り込んで直す手順（base-sync）と自動テスト（CI）で直す形

含まない:
- 設計をしている最中の作業どうしを待たせるかどうか。開発計画を 7 つのフェーズに分ける課題（ https://github.com/devbasex/ai-plugins/issues/4050 ）の設計で、設計のフェーズは宣言と I13 の対象外にすると決めている（#4050 の実装はまだである）
- 待ちの種類ごとの時間の計測（ https://github.com/devbasex/ai-plugins/issues/4293 ）
- 宣言の外のファイルを変えることを禁じる・失敗にする決まり
- 1 つのスプリントの中の実装の作業手順（プラン）どうしの重なりの判定（ https://github.com/devbasex/ai-plugins/issues/2037 が扱う）

## 前提

- 前提 1: 本当に重なる組の順序は残す。実際に、2 つのレーンが同じファイルを 14 個変える予定の組があり、後のレーンを先のレーンの後に置いた順序は正しい。ファイル単位にしても順序が要る組は残り、減るのは見かけの重なりだけである
- 前提 2: 知らせを受けたオーガナイザーは、`after` で順序を付け直すか、そのまま進めて base-sync で直すかを選ぶ。どちらを選ぶかはオーガナイザーが決め、仕組みは決めない

### エンジニア向けの補足

- 前提 1 の組は、レーン lsplit の単位の PR（ https://github.com/devbasex/ai-plugins/pull/4289 ・ https://github.com/devbasex/ai-plugins/pull/4291 ・ https://github.com/devbasex/ai-plugins/pull/4297 ）と、#4050 を扱うレーン lphase の詳細設計の地図である。重なる 14 ファイルは `progress/plan/run.py`・`progress/lane/launch.py` などで、lphase を lsplit の後に置いた

## 受け入れ条件

- [ ] 1. 設計 Pull Request がマージされたレーンの `touches` が、設計で確定した変えるファイルの一覧に置き換わる。オーガナイザーがコマンド（`ndf lanes set`）を打たなくても置き換わる
  - 一覧は、「設計の結果」の触るファイルと、詳細設計書を別のファイルにしたときの地図に載ったファイルを合わせたものである
  - 詳細設計を別の文書に分けず設計書の中に書いた（地図を別に作らない）場合は、「設計の結果」だけで置き換わる
- [ ] 2. 同じフォルダの別々のファイルだけを地図に載せた 2 本のレーンは、順番が `after` や並び順で決まっていなくても I13 に断られず、同時に実装へ進める
- [ ] 3. 2 本のレーンの地図に同じファイルがあり、どちらを先にするかが決まっていなければ、今と同じく I13 が断る（今できていることが壊れない。前提の確認: テスト `test_touch_overlap_errors_as_they_are_now` が通る、2026-11-24）
- [ ] 4. 設計の結果が無い・読めないレーンと、別のファイルにした詳細設計書の地図を読めないレーンは、今の宣言のまま動く。置き換えに失敗しても、レーンは止まらない
- [ ] 5. 単位の PR が地図や宣言の外のファイルを変えても、その単位の PR を失敗にせず、レーンを止めない
- [ ] 6. 単位の PR で実際に変えたファイルが記録され、ほかのレーンと重なれば知らされる
  - 実際に変えたファイルは、レーンの行に記録される
  - 同じリポジトリで同じ時間帯に動くほかのレーン（別の計画のレーンを含む）の `touches` か記録と重なれば、オーガナイザーへ、重なったレーンとファイルが知らされる
  - 記録したファイルを理由に、I13 が計画を断ることは無い
- [ ] 7. （行より細かく、レビューの単位ごとに宣言を持つ形を設計で採ったとき）重なるレビューの単位だけが待ち、重ならない単位は先に実装へ進む
- [ ] 8. 重複の排除・モジュール化・ライブラリ化のために変える範囲を広げることを、手順書・操作のたびに自動で割り込む検査（hook）・そのほかの検査のどれも禁じない（禁じる決まりを足さない）
