# #2344 の設計: 決定の記録

設計文書の本体は [issue-2344-design.md](issue-2344-design.md) にある。要求の未決のうち、参照の書き方は決定 1、流し直しの判定は決定 7、
版の記録の置き場は決定 3、参照へ移す設定のキーは決定 4 が受ける。

## 決定の記録

### 決定 1: 新しい種類の値を同じ規則で解決できるよう、参照はプランの型の `refs` 欄に名前つきで宣言し、ステップからは `{ref:<名前>}` で指す

今の差し込みは、種類ごとに次の 3 つを持つ。

- 書き方（`{release_version}`・`{queue_record}`・`{queue_pr:<名>}`・`QUEUE_PRS`）
- それを探す正規表現
- 埋める関数

種類を足すたびに 3 つを足すことになる。解決できないときの扱いも関数ごとに違った（`{queue_pr:<名>}` は PR が無ければ `0`、`{queue_prs:<名>}` は止める）。
宣言を 1 つの欄に集めれば、プランの型が宣言の形を確かめ、参照の部品は宣言の `kind` で種類のモジュールを引くだけになる。ステップの中の書き方は
文字列の中の `{ref:<名前>}` と数の欄の `{"ref": "<名前>"}` の 2 つだけにする。

文字列の差し込みを種類ごとに続ける形は採らない。上の 3 つが種類ごとに増え、新しい種類が既存の規則に乗らないためである。

根拠: Value 7 / Value 5（MVV 版 5）

### 決定 2: プランが変わったのが人の編集か解決かを区別できるよう、解決した値はプランのファイルへ書き戻さず、メモリ上のステップにだけ入れる

今のキューは差し込みを埋めたプランでファイルを上書きする。そのため #2349 では、完了の後にプランが変わったのか差し込みが埋まったのかを判定できなかった。
その結果、完了したプランを流し直した。書き戻さなければ、プランのファイルは組んだエントリポイントと人だけが書く。変わったことがそのまま人の編集を意味する。
解決した値は実行の記録の `ref` 行に残り、どの実行がどの値で流したかは記録から追える。

埋めたプランを書き戻し、別に差し込み前のコピー（`version-plan.json`）を持つ形は採らない。コピーとプランの 2 つが正になるためである。
決め直しの途中で落ちたときの戻し方（今の `ensure_filled`）も要る。

根拠: Value 7 / Value 8（MVV 版 5）

### 決定 3: 流し直しでも同じ版を使えるよう、版の解決は状態ディレクトリの解決の控え（`refs.json`）に残し、`version.json` は移行関数で読む

実行の記録は 1 回の起動ごとのファイルで、30 日で消える（#2335 の決定 6）。版はプランの寿命の間ずっと同じ値である必要がある（受け入れ条件 5）。
実行の記録だけでは、流し直しで前の版を引けない。そこでプランの状態ディレクトリに、流し直しでも同じ値を使う参照の控えを 1 つのファイルで置く。
今その性質を持つのは版だけである。控えは参照の名前ごとの行で持ち、種類を足しても置き場を増やさない。決め直しは前の値を `history` へ追記し、過去を失わない。

`version.json` をそのまま残す形は採らない。同じ性質の参照を足したときに種類ごとのファイルが増えるためである。
控えを持たず実行の記録だけに置く形は、上の寿命の理由で採らない。

根拠: Value 7 / Value 8（MVV 版 5）

### 決定 4: 古い設定の値で黙って進まないよう、設定は「ステップの中身に入る値」を参照にし、「プランの形を決めた値」は組んだ時点の値を控えて流す前に照らす

設定には 2 種類ある。

| 種類 | 例 | 流す時点で読み直すと |
| --- | --- | --- |
| ステップの中身に入るだけの値 | 導入の確認のコマンド・上限の秒 | 流す直前の値を使えばよい |
| どのステップを置くかを決めた値 | 配布のテンプレート・本番のブランチ | ステップは増減しない |

後者を流す時点の値で使うと、組んだ形と設定が食い違ったまま流れる。そこで後者は、組んだ時点の値の sha256 だけをプランに控える（形を決めた設定）。
最初のステップの前に今の値と照らし、違えば組み直すコマンドを添えて止まる。
どちらに当たるかは設定の契約のキーの行（`plan`）が持ち、設計の表は契約からコピーした一覧とする。

すべての設定を参照にする形は採らない。形を決めた値を流す時点で読み直しても、プランのステップは組み直さない限り変わらないためである。
形を決めた値を照らさない形は、目的の 2 つ目（古い値で黙って進まない）に反するため採らない。

根拠: Mission / Value 6 / Value 7（MVV 版 5）

### 決定 5: 利用者が明示した値を AI が置き換えないよう、引数で渡した上限・ブランチは参照にせず値のまま持ち、明示した版は版の参照の `explicit` に値のまま入れる

`--version` などで渡した値は、利用者か conductor がその値で流すと決めたものである。参照にして流す時点の値へ置き換えると、明示した決定を黙って上書きする。
上限とブランチは値のまま持ち、解決の記録には出所「プランの値（明示）」を残す。流した値の出所を追えるようにするためである。
版だけは、明示の値にも確かめることがある。#2164 でも明示の版は決め直さず、既出なら止める。承認ゲート 2 の後は承認した版とも照らす（決定 6）。
そこで `--version` の値は版の参照の宣言の `params.explicit` に入れ、参照の部品が値を置き換えずに既出の判定と承認した版との照合を通す。解決の記録の出所は `plan:explicit` である。

上限とブランチの明示の値も参照に寄せる形は採らない。上限とブランチでは明示の値に確かめることが無く、宣言が増えるだけのためである。
明示の版を参照にせずリテラルで持つ形は採らない。既出の判定と承認した版との照合を通る経路が無くなるためである。

根拠: Vision / Value 2（MVV 版 5）

### 決定 6: 承認ゲート 2 で人が見た版と流す版を照らせるよう、承認資料に「承認した版」の行を足し、本番のエントリポイントはエントリポイントの契約の `refs` で参照の部品を通る

今の承認資料は承認したコミットの行だけを持つ。版は、承認ゲート 2 の通過の後に系列の版の記録が変わったか（`series_changed`）でしか照らせない。
承認資料に「承認した版」を書けば、人が見た版と解決した版をそのまま比べられる。照合は承認したコミットと同じく `approved: gate-2` を付けた参照で行い、
食い違えば `gate` で人へ戻す。今の `series_changed` は `stopped` である。承認した値との食い違いは人が判断することなので `gate` にする（受け入れ条件 4）。
本番のエントリポイントはプランからも手動でも呼ばれる。そのため照合をエントリポイントの契約の `refs` に置き、核がエントリポイントごとに同じ参照の部品で照らす。照らす関数は `lib/approved_commit.py` の 1 か所にする。

照合をプランのステップの側だけに置く形は採らない。手動で本番のエントリポイントを呼んだときに照合が抜けるためである。
「承認した版」の行が無い旧い承認資料は、`series_changed` の照らし方で読む（次の正式版まで）。

根拠: Value 2 / Value 7（MVV 版 5）

### 決定 7: 完了したプランの流し直しを中身の変更だけで判定できるよう、プランの同一性はプランの型で読んだ中身を正規化した JSON の sha256 で測る

決定 2 でプランのファイルは解決で変わらなくなる。ただし `jq` などで整形し直すと、キーの並びと空白だけが変わる。
ファイルのバイト列の sha256 では、中身の同じプランを「変わった」と判定して人へ戻すことになる。型で読んだ値をキーを並べ替えた JSON にしてから取れば、意味の変わった編集だけを拾える。
ハッシュは実行の記録の `start` 行とキューの done の項目に持ち、再開とキューの `--resume` が今のハッシュと照らす。
前のハッシュが無い旧い done では、完了したプランを流さない（受け入れ条件 7 の前半）。

ファイルの sha256 は上の理由で採らない。流し直しを完了の結果だけで止め、変わっても知らせない形も採らない。#2349 の「流し直すかを知らせて止まる」に反するためである。

根拠: Value 3 / Value 8（MVV 版 5）

### 決定 8: 飛ばすはずのプランが開始のステップで流れないよう、実行条件は参照の段の最初に開始のステップによらず 1 回だけ評価する

実行条件は「このプランを流すか」の判定で、どのステップから始めるかと関係しない。今は開始のステップを渡すと評価を飛ばす（`engine.py:219`）。
そのため #2349 で取り込み済みのプランが流れた。参照より先に評価すれば、飛ぶプランは版を照会しない。キューが条件を先に打つ手当て（`_release_skipped_by_condition`）も要らなくなる。

開始のステップが実行条件の後ろにあるときだけ評価する形は採らない。実行条件はステップではなくプランに付くため、前後の判定に意味が無い。

根拠: Value 7 / Value 5（MVV 版 5）

### 決定 9: 前のプランの結果をキューの外からも同じに解決できるよう、前のプランの結果の参照は状態ディレクトリから読む

今の `{queue_pr:<名>}` などは、次の 2 つの経路を順に見る。

1. キューが持つ前のステージの結果
2. 無ければ、同じディレクトリのプランの状態ディレクトリ

2 つの経路は同じ報告（`report.md` と `work/`）を読むため、後者だけにしても値は変わらない。経路を 1 つにすると、参照の部品はキューに依らない。
単独で流すとき・再開するとき・キューで流すときに同じ値になる。
キューの前のステージ全体の PR（今の `QUEUE_PRS`）は、キューが done の隣に書く一覧から前のステージのプランを引く。

キューが結果を参照の部品へ渡す形は採らない。キューの外から流したときに別の経路が要り、2 つの経路が食い違いうるためである。

根拠: Value 7 / Value 6（MVV 版 5）

### 決定 10: 結果を読む側を壊さないよう、参照で止まったプランのキューの項目は `unfilled: true` を保つ

次の読む側は、`unfilled` で「差し込みを埋められずに流さなかった」プランを数える。

- 開発ループ（`lib/sprint_loop.py:481`・`lib/sprint_loop_gate2.py:243`）
- キューの要約（`queue.py:340`）

参照で止まったプランは結果が「止まった」になるが、`unfilled` を外すと読む側の数え方が変わる。結果 JSON のキーは足すだけで消さない（#2335 の移行の表）。
そのため、参照で止まった項目にも `unfilled: true` を付け、旧い版の `流さなかった` の項目も読む。

`unfilled` を外し、読む側を同じ Pull Request で `止まった` の判定に寄せる形は採らない。旧い版のキューが書いた done を新しい版の開発ループが読むと、数え方が食い違うためである。

根拠: Value 6 / Value 1（MVV 版 5）

### 決定 11: 開発ループのスプリントが版の取り合いで止まらないよう、`loop sprint` の `--dev` を任意にし、省いたら版を渡さない

#2164 で `new sprint` は `--version` を省けば配布の時点に版を決める。開発ループは `--dev` を必須にして `--version` を必ず渡すため、この経路を選べない（#2354）。
`--dev` を省いたときと渡したときの振る舞いは次のとおりである。

| `--dev` | 振る舞い |
| --- | --- |
| 省く | `new sprint` に `--version` を、`sprint-state.py init` に `--dev` / `--prod` を渡さない。周回の版は、配布の答えを書く `settle_release` が今と同じく `versions.prod` に入れる |
| 渡す | 今と同じ明示の版のプランになり、呼び方を変えた利用者の手を止めない |

`--dev` を廃止する形は採らない。明示の版で回したい利用者（決定 5）の手段が無くなるためである。

根拠: Vision / Value 2（MVV 版 5）
