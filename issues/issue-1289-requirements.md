## 例: 2 つの承認ゲート 1 で起きたこと

**v10.15.0（#772）。** 設計 PR #739 #740 #741 #742 を 1 回の承認に載せた承認ゲート 1 で、利用者への問いが 9 回になった（2026-09-17T05:29Z〜09-18T02:34Z）。差し戻しの理由は設計の中身ではなく、承認資料に無かった 3 点だった。

| 問われたもの | 何が起きたか |
| --- | --- |
| 用語 | 実行単位と最上位の層の呼び方が 4 回変わり、そのたびに 3 文書を書き直してクロスレビューを 11 + 9 ラウンド回した |
| 適用範囲 | #742 の検査が ai-plugins だけのものに読め、配布先のリポジトリで使う形かを問われた |
| あるべき姿の根拠 | #742 に「指示書はどうあるのが適切か」の考察が無く、外部の出典 23 件を足して 38 ラウンドで収束した |

**マイルストーン 13（#785）。** 設計 PR #781 #782 #783 が承認ゲートに揃った時点（2026-09-19）で、利用者から「titleからして何を言ってるか分かりません。それぞれ目的を明らかにして全部書き直し」と指示を受けた。#781 の題は次のとおりで、「利用上限で止まった担当が `error` で終わる」という現象が題にも最初の章にも出ていなかった。

> Docs: 担当 1 回の起動の結末を共通の語彙で読む設計（#729 #619 #584）

**今も同じ形が出る。** スプリントで流す設計 PR の題は `supervise_lib/sprint_waves.py` が `設計: #<番号>` で付ける（例: #1627「設計: #1340」）。設計文書の H1 は `# #1340: cross-review にラウンドを足す入口・振動検知の順序・hook の締め切りの設計` で、最初の段落は「要求と受け入れ条件は…にある」という管理上の注記である。

この課題が済むと、承認する人は承認資料の先頭で「何が壊れていて、マージすると何が成り立つか」を読み、続けて用語・適用範囲・あるべき姿の根拠を同じ資料の中で確かめられる。欠けている欄は「無し」と理由つきで出るため、問い直しで初めて欠けに気づくことが無くなる。

## 目的

- 承認ゲート 1 で、承認する人が問い直さずに 1 回で承認か差し戻しを決められる
- 設計 PR の題と設計文書の最初の章から、変更の目的（今起きている問題と直した後に成り立つこと）が読める

## 今の状態（2026-10-02 に調べた）

- `design/references/design-template.md` の H1 は `# {課題番号}: {何を作るか}`、最初の段落は管理上の注記で、「目的」「適用範囲」「あるべき姿の根拠」の節が無い。「用語」の表はドメインモデルの節の中にある（#1111）
- `development-workflow/references/approval-request.md` の「承認の判断に使うもの」は 決めたこと・作るもの・満たすこと・未確認・収束・本文との一致・MVV 判定 の 7 行で、目的・用語・適用範囲・あるべき姿の根拠の行が無い。タイトルは「そのまま」並べる
- `design/references/decisions.md` の決定の見出しは `### 決定 N: {結論を 1 文で}`。承認資料の「決めたこと」はこの見出しをそのまま並べる
- 仕様の雛形（`requirements-design/references/spec-template.md`）には「目的」の節が既にある
- 設計 PR の題は、スプリントでは `supervise_lib/sprint_waves.py` の `"title": f"設計: #{n}"`、単発では `/ndf:pr` を呼ぶ者が決める。`pr/SKILL.md` は題の形を定めていない
- 子 #785 が挙げた機械の検査（題の形・H1 の直後の章）の置き場 #854（doc-check）は閉じている。セルフチェックを doc-check の呼び出しにする #873 は開いている

## 前提

- 前提 1: 規約（題の形・目的の章・用語・適用範囲・あるべき姿の根拠の欄の書き方）の本文は `design/references/design-template.md` の 1 か所に置く。`approval-request.md`・`decisions.md`・`pr/SKILL.md`・`requirements-design`・`document-restructuring`・`agent-layers.md` は、規約を写さずにその節を指す 1 行だけを持つ
- 前提 2: 題の形は「<今起きている問題（利用者が見る現象）> → <直した後に成り立つこと>（#課題番号）」とする。先頭に対象（Skill 名か領域）と `:` を置いてよい。仕組みの語は本文へ回す。課題番号は末尾の括弧に置く。設計 PR の題と設計文書の H1 は同じ文にする
- 前提 3: スプリントで流す設計 PR の題は、設計文書の H1 から機械で作る（LLM が別に書かない）。H1 を読めないときは今の `設計: #<番号>` のまま出し、承認資料に「題: 規約の形でない」と出す。どこで読むかは設計が決める
- 前提 4: 欄が空でも承認ゲートは止めない。承認資料に「無し（理由）」と出し、承認する人が差し戻すかを決める。欄を埋めるのは設計の工程（supervisor か設計の作業）で、承認ゲートを返す前に埋められるものは埋める
- 前提 5: 用語の確定のために、設計より前に人へ問う別の問いは置かない。新しく足した語・意味を変えた語は、承認資料の「用語」の行で承認と同じ 1 回に載せる（人の手を止めるのは承認ゲートに寄せる）
- 前提 6: 「あるべき姿の根拠」は、変更後の形が適切だと言える根拠（外部の一次情報・実測・利用者の指示の原文）を指す。MVV の項目の番号（用語集の「根拠の項目」）とは別のものである。根拠が要らない変更（既存の形に揃えるだけのもの）は「無し（既存の形に揃える）」と書けば足りる
- 前提 7: 機械の検査（題に `→` があるか、H1 の直後の章が「目的」か）は、この課題では足さない。#873 の doc-check の検査へ回す
- 前提 8: 既に出た設計文書・設計 PR（#781 #782 #783 と、題が `設計: #<番号>` の PR）は書き直さない。#781 #782 #783 の書き直し後の題は、規約の実例として雛形へ写す

## 対象範囲

含む:
- 設計文書の雛形に、H1 の形と、最初の章「目的」と、「適用範囲」「あるべき姿の根拠」の節を置く。「用語」の表は今の場所のまま、承認資料から指す
- 決定の見出しを「何のために何を決めたか」と読める形にする規約（`decisions.md` から雛形の規約を指す）
- 承認資料の「承認の判断に使うもの」の先頭に、目的・用語・適用範囲・あるべき姿の根拠の 4 行を足す。出所は設計文書の該当の節で、空なら「無し（理由）」と出す
- 設計 PR の題を規約の形にする（スプリントの設計 PR は設計文書の H1 から作る）
- conductor → supervisor の起動の指示（`agent-layers.md`）と、`pr`・`requirements-design`・`document-restructuring` から規約の節を指す 1 行
- #781 #782 #783 の書き直し後の題を、規約の実例として雛形へ写す
- 新しい語（適用範囲・あるべき姿の根拠）を用語集へ足す

含まない:
- 題と章の形の機械の検査（#873 へ回す。前提 7）
- 承認ゲートの数・承認を求める手段（`AskUserQuestion`）・MVV 判定の手順の変更
- `documentation` モードの企画承認の承認資料（判断に使うものが別の形で、#772・#785 の現象の外）
- 承認ゲート 2（リリース・運用の実行・文書の提出）の承認資料
- 既に出た設計文書・設計 PR の書き直し（前提 8）
- 実装 PR の題の形
