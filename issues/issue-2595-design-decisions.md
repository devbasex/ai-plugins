# オーガナイザーの切り替えの決定の記録（#2595）

設計文書は [issue-2595-design.md](issue-2595-design.md) にある。

## 決定の記録

### 決定 1: ほかの conductor と同じ規則で止めるため、`wait` を起動のキーに足し、判定の関数を共有する

`_launch_key` に種を 1 つ足せば、方針の解決・上限・排他・止め続け・記録がそのまま効く。受け入れ条件の 5・6・9・10 は追加のコードなしで満たす。対象は `wait` だけとする。`answer` の途中で切ると、持ち主のレーンを起こす 1 行が残らない。別の判定の関数を作る形は採らない。規則が 2 つに分かれ、上限の見直しのたびに両方を直すことになるためである。

- 作り方: 自前で作る
- 比べた候補: STD1 / PRD1

根拠: Value 7 / Value 2（MVV 版 6）

### 決定 2: オーガナイザーの判定を記録で追えるよう、工程の列と作業の識別子を計画の単位にする

工程の列は `parallel:wait`、作業の識別子は `parallel:<計画名>` とする。課題番号を持たないオーガナイザーの行を 1 つの計画へまとめられ、`report --work parallel:p1` で読める。`last_denial` が同じ識別子で拒否の理由を引き継げるので、再起動の行の理由が正しくなる。識別子を空のままにする形は、拒否の理由を引き継げず、セッションをまたいで結べないため採らない。

根拠: Value 4 / Value 8（MVV 版 6）

### 決定 3: 工程の見込みを保つため、`parallel:wait` の行を費用の較正の工程の区切りから除く

`wait` は工程の起動でなく、間隔は依頼の届き方で決まる。区切りに入れると、他の conductor が使う全工程の見込みが動く。オーガナイザーの費用の判定は全工程の見込みで読む。引継ぎの区間の標本には入れる。実際の引継ぎだからである。

根拠: Value 4（MVV 版 6）

### 決定 4: 手順を消すため、オーガナイザーの引継ぎを `handoff.py cut-organizer` の 1 回にする

既存のコマンドの組み合わせでは、引継ぎ開始の印・文書・再開コマンド・検査・再起動の記録の 5 回の Bash を AI が組み立てる。オーガナイザーの状態は耐久の記録にあり、文書に書く現在地が無いので、決まった手順である。置き場は `handoff.py` とする。要求が `parallel.py` の引数を変えないと定めているためである。`sprint-state.py next` はスプリントの状態ファイルを読むので、状態ファイルを持たないオーガナイザーに当たらない。引継ぎ文書を書けなくても、再開の 1 行は計画名だけで決まるので切り替えを止めない。止めると `wait` が拒否され続け、オーガナイザーが動けなくなる。

- 作り方: 自前で作る
- 比べた候補: PRD1

根拠: Value 5 / Value 2（MVV 版 6）

### 決定 5: 済んだ起動の指示を流し直さないよう、耐久ワークフローが知らせを今の状態へ合わせる

`pause` は上書きされる値なので、起動の指示が済んだら空の `notice` で上書きし、`release` を添えるときは起動の 1 行を除く。済んだかを正確に知るのは、一時レーンの問いと `settle` を受ける耐久ワークフローだけである。`helper_task` の側で見る形は、ファイルの有無では「途中で止まった」と「済んだ」を分けられない。古い知らせのたびに一時レーンのセッションを 1 本起動することにもなる。読む時点を切り替え前の seq へ進める形は、受け入れ条件 12 の `--after 0` と矛盾する。

起動の 1 行を除くだけで指示そのものは残すのは、問いの答えの後に起こされた一時レーンが `helper_task` で同じ `phase` を読むためである。空の `notice` はすでにある形なので、`wait` の出力の形は変わらない。

耐久ワークフローの受信は非同期なので、一時レーンは起動の 1 行が消えたことを `parallel.py helper-sync` で確かめてから止まる。確かめの印には上書きされた `pause` をそのまま使い、新しいイベントを足さない。止まる前は `name-taken` が重ねての起動を断るため、受信を待つ最長約 60 秒の間も流し直しは起きない。

動いている一時レーンは今も `name-taken` で断られるため、この決定は止まった後の一時レーンの流し直しだけを防ぐ。`held` は `sprint-state.py loop pending` が `none` を返して終わるので、済みの印を足さない。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: PRD2 / LIB1

根拠: Value 7 / Value 1（MVV 版 6）

### 決定 6: 手順書どおりに切り替えられるよう、引継ぎ文書の名に `parallel-<計画名>` を足す

手順書と要求の受け入れ条件 8 が `.ndf/handoff/parallel-p1.md` を指している。計画の名は開発ループ・スプリントの名前と別の名前空間で、`loop-` などへ寄せると同じ名前のレーンと文書がぶつかる。

根拠: Value 7（MVV 版 6）

### 決定 7: 利用者の指示を引き継げるよう、再開の 1 行は変えずに文書を手順 0 で読み、計画の終わりに消す

再開の 1 行は起動と同じ形（受け入れ条件 8）なので、文書のパスを持たない。そこで `parallel.md` の手順の先頭で、`handoff.py path parallel-<計画名> --exists` が 0 なら文書を読み、`復元完了` を打つ。文書は計画が終わる `step_finish` が消す。同じ計画名を後で使っても、古い指示を読まないためである。手順書で conductor に消させる形では、`finished` の後は `/goal` を満たして応答を終えるため、消すコマンドが打たれずに文書が残る。

根拠: Value 5 / Value 8（MVV 版 6）
