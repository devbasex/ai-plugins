# #2228 の設計: 決定の記録

設計文書の本体は [issue-2228-design.md](issue-2228-design.md) にある。要求の未決 1〜4 は決定 1・4・5・6・8 で決める。

## 決定の記録

### 決定 1: 別の機械とセッションからも同じ判定になるよう、最終工程の記録は GitHub に残った記録から読む

判定の材料は、配布の記録（`段階:`）・リリース後テストの行・課題の本文の `振り返り: <コメントの URL>` の行の 3 つにする（要求の未決 1 の候補 (b)）。どれも GitHub にあり、conductor・supervisor・別の機械のどこから打っても同じものを読む。配布とリリース後テストは今の閉じる条件 1・2 がすでに読んでおり、足すのは振り返りの行だけになる。

振り返りの行は、`retrospective` の「辿る経路を作る」がすでに課題ごとに書いている（#2086・#2216・#2227・#2229 で確かめた）。記録の PR のコメントは読まない。#2086 の行は記録の PR（2109）と違う PR（2110）を指しており、記録の PR から探すと見落とす。

#2227 の結果 JSON（候補 (a)）は採らない。プランの状態ディレクトリは手元の一時の置き場で、conductor が手で打つ経路では存在しない。通過記録に「工程を出た」記録を足す案（候補 (c)）も採らない。通過記録はリポジトリの外の手元のファイルで、別の機械からは読めない。

根拠: Value 5 / Value 6 / Vision（MVV 版 3）

### 決定 2: 呼ぶ側の書き違いで閉じる条件が緩まないよう、最終工程は引数で受け、省けば振り返りにする

`sprint-close.py` に `--final-stage 配布|リリース後テスト|振り返り` を足し、省いたときは最も後ろの `振り返り` として判定する。s2086 のように conductor が手で打つ経路では、何も付けなければ振り返りの記録が要る。緩めるには、最終工程を担う Skill（`release`・`release-verification`）がその値を明示する必要がある。どの Skill がどの値を渡すかは `progress-tracking` の「スプリントを閉じる」の呼ぶ Skill の表が持つ。

課題の本文の `## 進行` の `モード:` から最終工程を導く案は採らない。実際の課題（#2086・#2172・#2216・#2227・#2229）ではどれも `—` で、導けない。工程表（`WF_STAGE_MATRIX`）を Python から読む部品を新しく作っても、`operation` は経路でリリース後テストと振り返りの有無が変わり、モードだけでは決まらない。

根拠: Value 2 / Value 4（MVV 版 3）

### 決定 3: 最終工程がリリース後テストの経路で条件 2 を見落とさないよう、その値は条件 2 を必ず見る

`--final-stage リリース後テスト` を渡したときは、`--with-verification` を付けなくても閉じる条件 2 を判定する。この経路の最終工程の記録はリリース後テストの行そのものであり、条件 2 を見ずに閉じると最終工程の記録を確かめないまま閉じる。

2 つの引数を別々に必須にする案は採らない。片方を付け忘れると、最終工程を確かめずに閉じる経路が残る。

根拠: Value 6（MVV 版 3）

### 決定 4: 前の版で工程を通った課題のために移行の手段を作らない

この版より前に振り返りを通った課題は、すでに本文に振り返りの行を持つ（決定 1）。行を持たずに開いている課題は `kept_open` で残り、`reason` と `next` が「振り返りを通すか、確かめて手で閉じる」を示す（要求の未決 2）。

古い課題を一度だけ閉じる引数（判定を飛ばす `--force` の類）は足さない。足すと、新しい経路でも判定を飛ばす手段として使える。手で `gh issue close` を打つ経路は要求の対象範囲の外にあり、すでにある。

根拠: Value 1 / Value 6（MVV 版 3）

### 決定 5: 無人の実行を止めずにマージで閉じなくするため、既定ブランチ宛の本文の closing keywords は止めずに置き換える

既定ブランチ宛の Pull Request の本文を NDF の手順（`pr-steps.py create` / `update` とプランの pr のステップ）で書くとき、closing keywords を閉じる予定の参照へ置き換えてから送る（要求の未決 3 の前半）。指し先の字面は変えないため、何を閉じる予定だったかは本文に残る。置き換えたことは `metrics.deferred_closing` と `items` に載る。

止める案は採らない。プランの pr のステップは本文を機械で組み、`## 閉じる課題` に `Closes #N` を並べる。止めると、既定ブランチを起点にするリポジトリではスプリントのたびに無人の実行が止まる。

根拠: Value 2 / Value 5（MVV 版 3）

### 決定 6: 閉じる課題を本文から集め続けるため、閉じる予定の参照は専用の形にし、読み手の共通の部品で読む

閉じる予定の参照の形は `最終工程の後に閉じる: <指し先>` にする（要求の未決 3 の後半）。GitHub の closing keywords を含まないため GitHub は閉じず、`lib/closing-issues.sh` と `lib/closing.py` が closing keywords と同じ指し先の規則で読む。`sprint-close.py`・`merged`・工程の飛ばしの検知の hook・リリースの材料は今の部品を通して読むため、読み手ごとの直しは要らない。

`Refs #N` は採らない。「参照」はすでに参照だけの課題（閉じる対象にしない課題）の意味で使っており、同じ形に 2 つの意味が付く。`NDF-Closes #N` のような英語の造語も採らない。語の境界の後に `Closes` が来るため、NDF の読み手（`lib/closing.py` の `CLOSING`）が closing keywords として一致させ、GitHub が閉じるかを読み手ごとに確かめ直すことになる。`--issues` だけで集める案も採らない。受け入れ条件 8 は `--prs` だけで課題が集まることを求め、手で打つ経路で `--issues` を付け忘れると閉じる課題が 0 件になる。

最終工程の判定（`final_stage_gap`）は `sprint-close.py` に置き、`lib` に置かない。読み手が 1 つで、`lib/README.md` の「2 つ以上の読み手が使う部品だけを置く」に当たらない。

根拠: Value 6 / Value 8（MVV 版 3）

### 決定 7: 判定の費用を増やさないため、振り返りの行は形だけを見て、指すコメントは読まない

条件 3 は課題の本文にある行の形（`振り返り: https://github.com/…#issuecomment-<識別子>`）だけで判定する。本文は条件 2 と同じ 1 回の読みで取る。行の URL のコメントを `gh api` で読めば実在を確かめられるが、課題ごとに `gh` の呼び出しが 1 回増える。行は `retrospective` が投稿の後にだけ書く。

根拠: Value 10（MVV 版 3）

### 決定 8: まとめのプランで閉じる時点を 1 つにするため、閉じるのは close のステップだけにし、Skill からの呼び出しは残す

まとめのプランは `merge →（release-verify）→ retro → close → refine` の順にし、`retro` の指示に `release-verify` と同じく「課題を閉じない（次の close が閉じる）」を足す。プランの外（conductor が Skill を直接通す経路）では、今と同じく最終工程を担う Skill が「スプリントを閉じる」を行う（要求の未決 4）。

Skill から呼び出しを外す案は採らない。プランを通らない実行で、閉じる担い手がいなくなる。`sprint-close.py` は判定を自分で行うため、Skill とプランの両方が打っても、早すぎる時点では閉じず、2 度目は `already_closed` になる。プランの中で `retro` に閉じさせない理由は、担当が `--with-verification` を省いて打つと条件 2 を見ずに閉じるためである。

モードで並びを分ける案も採らない。今のまとめのプランはどのモードでも `retro` を持ち、`close` を `retro` の後に置けば、受け入れ条件 6 の「最終工程の後、棚卸しの前」をどのモードでも満たす。

根拠: Value 4 / Value 6（MVV 版 3）

### 決定 9: 書き換えの要否を確実に決めるため、宛先が既定ブランチかで決め、既定ブランチを決められないときは置き換える

置き換えるかは Pull Request の宛先（新しく作るなら `--base` か起点、既存なら `baseRefName`）が既定ブランチ（`lib/repo.py` の `default_branch`）と一致するかで決める。既定ブランチを決められないときは置き換える。置き換えても閉じる予定の参照として NDF の手順で閉じられ、失うものが無い。置き換えずに既定ブランチ宛だったときは、マージで閉じる。

`.ndf/worktree.json` の `base_branch` と既定ブランチを比べる案は採らない。GitHub が閉じるかを決めるのは各 Pull Request の宛先であり、`sprint/<名前>` 宛の課題の Pull Request は起点の設定に関わらずマージで閉じない。

根拠: Value 5（MVV 版 3）
