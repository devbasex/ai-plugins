# 文書の種類ごとに備えるべき内容の調査（#3868）

設計書（[issue-3868-design.md](./issue-3868-design.md)）の「文書の役割の表」が、5 つの文書（要求仕様・設計書・詳細設計書・実装計画・開発計画）に置いた読み手・判断・セクションの根拠である。設計承認ゲートで「文書ごとに備えるべき内容の調査を盛り込む」と差し戻されたのを受けて書いた。

文書の種類ごとに、一次資料が共通して求めること（読み手・読み手が下す判断・備えるべき節・省いてよい条件・分量）と、このリポジトリの過去の文書の実例の数を並べ、最後に設計の表とどこが合い・どこを変えたかを書く。出典の取得日はすべて 2026-11-19 で、出典の一覧は末尾にある。確かめられなかった点は「未確認」と書く。

## 要求仕様

**一次資料の求めること**

- **読み手と判断**: IPA のガイドは、要求の内容に責任を持つのは業務部門などの利害関係者で、成果物ごとに「誰と合意したら完成か」を先に決めるとする（S19 の 6.2）。ユーザーストーリーでは顧客が順位を決め、受け入れテスト（Confirmation）で完了を確かめる（S21）
- **節**: 29148 の SRS（S1 の 9.6）・Volere（S20 の 1・2・6・8・9〜17・18・26）・IPA の要件定義ドキュメント（S19 の DD.1〜DD.3）は、どれも 目的 → 利害関係者 → 範囲 → 要求の一覧 → 未解決 の並びを持つ
- **個々の要求に試験できる尺度を付ける**: Volere の fit criterion、IPA の要求一覧の測定尺度と目標値、ユーザーストーリーの Confirmation と Given-When-Then の 3 つに共通する（S19・S20・S21）
- **採らなかった要求を残す**: IPA の要求一覧の「採否区分」と、Volere の Waiting Room（後の版へ回す要求）（S19・S20）
- **不具合の報告**: 起きたことと期待する結果を別の欄に分け、1 報告 1 件とする（S7）
- **省いてよい条件**: 記載項目を案件に合わせて変える（S19 の 7.3.4、S20）。ストーリーは詳細を持たず会話へ回す（S21）
- **分量**: 文書全体の長さを定める資料は無い。ストーリーは 1 イテレーションに収まる大きさ（S21）

**このリポジトリの実例**（最近の 8 件。数え方は「実例の数え方」）

- 節の数は中央値 16・最大 17。「無し」だけの節は 0 件。表のセルの「無し」「—」は中央値 4
- 8 件すべてが「起票者の推定」「前提」「対象範囲」「ドメインイベント」「用語」「受け入れ条件」「影響」「検証手段」を持つ。#3868 の本文は、#3856 の要求仕様が冒頭の「起票者の推定」と次の「事象」で説明なしに内部の語を使ったことを、読めなかった理由に挙げている

**設計の表との関係**: 合う。目的・場面（何が起きたか・誰が困るか）・対象範囲（含まない＝採らなかった要求）・受け入れ条件（試験できる尺度）・未決が、一次資料の共通の節に当たる。不具合の 事象 → 期待する結果 → 再現手順 は S7 と同じ切り方である。場面（何が起きたか）と今の姿を目的より前に置くのは、一次資料の並び（目的が先頭）と違う。理由は設計書の決定 4 の採らなかった案（初めて見る読み手には変える前の姿が要る）にあり、調査はこの判断を変えない

## 設計書

**一次資料の求めること**

- **読み手と判断**: Rust の RFC は担当の sub-team が merge・close・postpone を決め（S12）、PEP は中心の開発者と Steering Council が受け入れを決め（S13）、KEP は SIG の承認者が状態を `implementable`（実装してよい）にするかを決める（S11）
- **節**: 3 つの節の構成は同じではない。Rust RFC は Summary → Motivation → Guide-level explanation → Reference-level explanation → Drawbacks → Rationale and alternatives → Prior art → Unresolved questions → Future possibilities（S12）。PEP 1 は Abstract → Motivation → Rationale → Specification → Backwards Compatibility → … → Rejected Ideas → Open Issues を挙げ、独立した欠点の節を列挙しない（S13）。KEP はリリースの確認表（Release Signoff Checklist）の後に Summary → Motivation → Proposal → Design Details → … → Drawbacks → Alternatives を置き、未解決の事項は節でなく本文中の編集中の印（`<<[UNRESOLVED]>>`）で表す（S11）。Google の Design Doc は 文脈と範囲 → 目標と非目標 → 設計 → 検討した代替案 → 横断の関心事（S2）、ADR は 文脈 → 決定 → 結果（S3）
- **3 つに共通するのは、提案本文の早い位置に要約があることまで**: RFC は先頭に 1 段落（S12）、KEP は確認表の後に少なくとも 1 段落でリリースノートにも使う（S11）、PEP は前書き（Preamble）の後に約 200 語の Abstract（S13）。長さの決め方は 3 つで違い（段落の数と語の数）、見出しはどれも付ける（`Summary`・`Abstract`）。見出しを付けない 1 段落にするのは NDF の判断である（設計書の決定 11）
- **提案と詳細を分ける**: RFC は Guide-level と Reference-level、KEP は Proposal と Design Details に分け、Proposal には API の設計と実装を書かない（S11・S12）
- **要求を繰り返さない**: "This isn't a requirements doc."（S2）
- **省いてよい条件**: 小さな変更・不具合の修正・利用者に見えない変更には文書自体が要らない（S2・S11・S12・S13）。後方互換・セキュリティなどは当たるときだけの節（S13）。KEP は Optional の印を付け、最初は要約と動機だけでよい（S11）。arc42 は「全部を埋めない」（S4）
- **分量**: 大きな案件で 10〜20 ページ、小さい変更は 1〜3 ページ（S2）。1 文書 1 提案（S13）、1 件 1〜2 ページの決定の記録（S3）

**このリポジトリの実例**

- 節の数は中央値 35・最大 45、行数は中央値 495・最大 734（課題 1 つの設計書 8 件。#3866 の束ねた設計書 2 本は節 42 と 30・488 行と 310 行で、別に数えた。「実例の数え方」）。手順書は `standard` で成果物 15 を必須とする
- 「無し」だけの節は 3 件に現れ、最大 3。どれも手順書が残すよう求める節（人へ残す判断・外部の調査の `省く:`・このリポジトリだけの事情）だった。「代表のリポジトリでの振る舞い」の「この種類で扱えなくなること」の列は 16 セルすべてが「無し」
- 要求仕様と同じ主題の節を中央値 5.5 持つ（ドメインイベント・用語は 8 件すべて）。行のコピーは 0 件で、すべて言い直しである
- **8 件とも要約の段落を持たない**（#3866 の束ねた 2 本も持たない）。 #3866 の承認する人は「結局のところ何が課題で何をしようとしているのかさっぱりわからない」と書いた
- cross-review の行コメント 50 件は、ドメインモデル・処理の流れ・データ構造に集まり、目的・目指す姿・決定の記録を指したものは 0 件だった。承認する人がどの節で判断したかは未確認（5 本の設計 PR に承認する人のコメントが無い）

**設計の表との関係**: 文脈が設計の前・採らなかった案・代償（欠点）・未確認のまま残ること（未解決の問い）・当たらない節を消すことは合う（決定 3・4）。設計書と詳細設計書を分けるのは、提案と詳細を分ける形に合う（決定 6）。**提案本文の早い位置の要約が今の設計の表に無かったので、決定 11 で足した。** 見出しを付けず 1 段落・4 文以内にするのは出典に無い NDF の判断で、理由は決定 11 にある。 目標と非目標を設計書に置かないのは今のまま（要求仕様の目的と対象範囲が持つ。S2 の "This isn't a requirements doc" と、要求と同じ主題の節が中央値 5.5 ある実例による）

## 詳細設計書

**一次資料の求めること**

- **読み手と判断**: IEEE 1016 は Interface の観点の読み手を「設計者・プログラマ・テスト担当」、Algorithm の観点を「プログラマ」と単体テスト計画の作成とする（S8）。12207 の詳細設計は「追加の情報なしにコーディングできる」詳細さを求める（S9、二次資料）。CMS の SDD の 9 章は「実際に作って結合する開発チーム」に向け、詳細設計レビュー（DDR）の入力になる（S10）
- **節**: 範囲と参照 → コンポーネントへの分け方 → インターフェース → 内部の処理（アルゴリズム・状態・資源と並行）。CMS はコンポーネントごとに 14 項目（識別子・種類・責務・**満たす要求**・内部データ・制約（事前条件・事後条件・例外）・利用関係（副作用）・資源（競合とデッドロック）・処理・インターフェースなど）を挙げる（S10）
- **要求との追跡**: CMS の「満たす要求」（S10）、12207 の成果「要求と方式設計との一貫性と追跡性」（S9、二次資料）、IEEE 1016 の完全さの基準「特定した関心事がどれも少なくとも 1 つのビューで扱われている」（S8 の 4.4）
- **省いてよい条件**: IEEE 1016 の観点は「設計対象に当たるとき」だけ使う（S8 の 5.1）。CMS は詳細度を案件ごとに決め、多くはソースのヘッダとコメントに置いて参照で済ませてよいとする（S10 の 9.3）。C4 はコードの水準の図を長く保つ文書に描かない（S4）
- **分量**: 上限を定める資料は無い。CMS は「作るのも保守するのも負担になりすぎない範囲」（S10）

**このリポジトリの実例**

- 節の数は中央値 10.5（テンプレートの 10 節をすべて持つ）、行数は中央値 531・最大 618
- **「無し」は節でなく表のセルに残る。** 1 件あたり「無し」「—」のセルは中央値 80・最大 160。「関数の仕様」の「事前条件」の列は 319 セルのうち 156（49%）、「副作用」は 342 のうち 102 が「無し」か「—」だった
- 設計書の「テスト設計」と重なるのは「単体テストの観点」だけで、似ている度合いは 0.02〜0.25（言い直しは少ない）
- cross-review の行コメントは「関数の仕様」8・「処理の手順」7・「異常系の処理」5 に集まった
- 構成要素がどの決定・受け入れ条件を満たすかを書く欄は、テンプレートに無い

**設計の表との関係**: 地図 → 構成要素ごと、関数の仕様・異常系・単体テストの観点は合う。**2 つを変えた（決定 12）**: 構成要素ごとに満たす決定と受け入れ条件の番号を書く（追跡）。関数の仕様の表の列のうち事前条件・事後条件・副作用を当たる関数だけに書き、列ごと「無し」が並ぶ形をやめる

## 実装計画

**一次資料の求めること**

- **読み手と判断**: Small CLs ではコードレビュー担当が、変更の大きさと分け方で受け取れるかを決め、大きすぎれば分けるよう差し戻せる（S14）。KEP は承認者が実装へ進めてよいかと alpha・beta・GA を進めてよいかを決める（S11）。Shape Up のスコープは作るチーム自身が「どこまで終わったか」を話す語になる（S15）
- **タスクの単位**: Small CLs は「1 つの自己完結した変更」（機能の一部・そのテスト・理解に要る文脈を含み、提出後もシステムが動く）、Shape Up は「独立に作って終えられる数日以内のスコープ」。どちらも人でなく構造（依存）で分け、縦（全層を通した機能の断片）の分け方を挙げる（S14・S15）
- **節**: テスト計画（KEP。Small CLs は関係するテストを同じ変更に含める）・リスクと緩和策（KEP）・切り戻し（KEP の本番準備の質問票は有効化と切り戻しを必須にする）・完了の条件（KEP の Graduation Criteria、Shape Up のスコープの完了）・未解決の問いを決める時点で分ける（RFC。議論で決める・実装で決める・範囲外）（S11・S12・S14・S15）
- **省いてよい条件**: KEP は最初に要約と動機だけでよく、テスト計画と alpha・beta・GA へ進める条件は対象のリリースが決まってから足す。Shape Up はスコープを作り始めてから描き、あればよい作業に `~` を付けて先に削る（S11・S15）
- **分量**: 文書の上限を定める資料は無い。変更は 100 行前後がふつう、1000 行は大きすぎる（S14）。スコープは数日以内（S15）

**このリポジトリの実例**

- 節の数は中央値 16.5・最大 21。手順書の 15 節はすべて「当たるとき」で、そのうち 9 節が要求仕様・設計書と同じ主題（目的と非目的・前提・受け入れ条件・代替案と採否など）である
- 要求仕様・設計書と同じ主題の節を中央値 4 持つ。「受け入れ条件」の節 7 件のうち 6 件は中身を書かず、要求の文書を指す 1〜3 行だった
- **調べた `issues/` と `docs/specifications/` には、2026-10-15 の後の実装計画のファイルが無い**（見つかった 34 件すべてが `issues/old/` の下）。分かるのはこの 2 つのディレクトリに新しい計画のファイルが無いことまでで、PR の本文・課題のコメント・別の保存先で計画を作った可能性は調べていない。実装計画を書かずに実装へ進んでいるかと、その理由は未確認である

**設計の表との関係**: 合う。今の `implementation-plan` は「機能単位で分け、レイヤー単位で分けない。1 タスクが独立して検証できる大きさにする」とし、Small CLs と Shape Up の単位と同じである。テスト・リスクと対処・切り戻し・完了の定義も表にある。前の文書と重なる 9 節を消し受け入れ条件を番号で指す決定 5 は、実例の 6/7 がすでに要求を指すだけだったことと合う。変えない

## 開発計画

この課題でいう開発計画は、スプリント（複数の課題）を扱う実行計画（`issues/execution-plan-<キー>.md`）と、レーンを並べる並列の計画（JSON）の 2 つである。

**一次資料の求めること**

- **読み手と判断**: Scrum の Sprint Planning では開発者が Product Owner と話して、どの項目をスプリントに入れるかを決め、途中で想定と違えば Sprint Goal を変えずに範囲を交渉し直す（S16）。Shape Up の betting table は次の周期に何を・誰に割り当てるかを決める（S15）。IEEE 1058 は計画との違いを測り、是正するかを決める（S17）
- **目標を 1 つ置く**: "The Sprint Goal is the single objective for the Sprint."（S16）。Shape Up の Pitch は Problem と Appetite（かける時間）から始まる（S15）。1058・16326 の概要は目的・範囲・目標から始まる（S17・S18）
- **作業の順序と依存・並行**: 作業の時間順の制約と並行できる箇所を書くよう求めるのは 1058 だけである（S17 の 4.5.2.2）。Scrum と Shape Up の Pitch は依存を書く欄を持たず、Shape Up は依存をスコープの分け方の根拠として作業の後に見つかるものとする（S15・S16）
- **範囲の外**: Shape Up の No-gos、16326 の概要の「範囲や目標から外すもの」（S15・S18）
- **計画の更新**: 1058 は版ごとに次の更新の予定を持ち、16326 は「生きた文書」として常に更新する（S17・S18）
- **変更の重なり**（同じ箇所を複数の作業が変えること）を独立の項目に持つ資料は、調べた 4 件に無い（16326 の 2019 年版の本文は未確認）
- **省いてよい条件**: 計画の作り方は開発者に任される（S16）。節を他の計画書の参照で済ませてよい、小さな案件は形式を軽くしてよい（S17・S18）。採らなかった案を持ち越さない（S15）
- **分量**: 文書の長さを定める資料は無い。周期は 1 か月以下（S16）か 6 週間＋cool-down 2 週間（S15）

**このリポジトリの実例**

- 実行計画の今の形（行・変更重複・見直し）の実例は `issues/old/execution-plan-26.md` の 1 件だけで、もう 1 件（`issue-540-execution-plan.md`）は実装計画の形で書かれていた。手順書は閉じるときに最後の PR のコメントへ貼ると定めるが、貼ったコメントは見つからなかった
- 実行計画の形（手順書の `execution-plan.md`）は 状態 → 開始 → 行 → 変更重複 → 見直し で、**スプリントの目標を書く行が無い**
- 並列の計画（JSON）の実例 8 件のうち 7 件が、今のスキーマに無い `handoff` の欄を持つ（この課題の範囲外。報告に残す）

**設計の表との関係**: 依存（行の「設計の依存」「実装の依存」）・並行（同時に動かす本数）・計画の更新（見直しの表）は合う。変更重複は外部に前例が無いが、複数の AI のセッションが同じファイルを同時に変える NDF に固有の欄なので残す。**目標の行が無かったので、決定 13 で実行計画の頭に 1 行足す。** 並列の計画は JSON のスキーマが知らない欄を断る入力で、レーンごとの目標はレーンが流すスプリントの実行計画が持つため、変えない

## 実例の数え方

リポジトリ（HEAD `07b324752`）の `issues/` と `docs/specifications/` から、種類ごとにファイル名で選び、`git log -1 --format=%cs` の新しい順に最大 8 件を取った（#3868 自身は除く）。要求仕様は `issue-<番号>-requirements.md`、設計書は `issue-<番号>-design.md`（課題 1 つの設計書だけ。下の注を参照）、詳細設計は `*-design-detail.md`、実装計画は `*-plan.md` など（実行計画を除く）、実行計画は `execution-plan*.md`、並列の計画はメインディレクトリの `.ndf/parallel/<計画名>/plan.json`（コミットされないため更新日で選んだ）である。

- **設計書の数値（中央値・最大・「無し」・要求と同じ主題の節）は、課題 1 つの設計書 8 件に限る。** 選ぶ名前が `issue-<番号>-design.md` なので、課題を束ねた `issue-<番号1>-<番号2>-design.md` は 8 件に入らない。問題提起の中心の #3866 の設計書 2 本は束ねた形なので、同じ数え方で別に数えた（HEAD `07b324752`）: `issue-3851-3856-3854-design.md` は節 42・488 行、`issue-3852-3853-3855-3843-design.md` は節 30・310 行で、どちらも最初の行が `## 目的` で要約の段落を持たない。節の数は 8 件の中央値 35 をまたぎ、行数は中央値 495 以下で、束ねた設計書が単一課題の設計書より長いとは言えない。束ねた設計の長さや重複を論じる根拠には、この 2 本の数だけを使う。詳細設計は `*-design-detail.md` で選んだので、束ねた形も 8 件の候補に入っている
- 節はコードブロックの外の `^## ` と `^### ` で数えた。中身が 1〜2 行で、1 行目が「無し」「なし」「省く」「該当なし」「対象外」で始まる節を「無し」だけの節とした
- 表のセルは、中身が「無し」「なし」「省く」「該当なし」「対象外」「—」「-」だけのものを数えた。「—」は「依存が無い」の意味でも使われ、同じ数に入る
- 前の文書と重なる節は、課題番号が同じ前の文書と、見出しの語（目的・受け入れ条件・前提・代替案・用語など）で照らした。関係の薄い節も拾い、見出しの違う重なりは拾わない
- 承認する人が判断に使った節は、設計 PR 5 本（#3866・#3863・#3772・#3678・#3607）のコメントとレビューで探したが、承認する人のコメントは無かった（未確認）
