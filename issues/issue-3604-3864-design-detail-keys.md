# #3604 #3864 の詳細設計（キーの子）: 環境変数の宣言の API キー・キーの子の認証の失敗の停止・設定の変更での停止

詳細設計書 [issue-3604-3864-design-detail.md](./issue-3604-3864-design-detail.md) から、API キーで動く子の節を分けた文書である。設計文書は [issue-3604-3864-design.md](./issue-3604-3864-design.md) で、決定 1・6・12 と「#4018 の cross-review の設計の指摘」の表がこの文書の行を指す。パスは `plugins/ndf/` からの相対で書く。

**キーの子**は、API キーで動く次の 2 つの子をまとめた呼び方である。この文書と詳細設計書は、この 2 つを同じ規則で扱う。

| 子 | 子のアカウントの名前 | キーの出所 |
| --- | --- | --- |
| 登録簿の API キーの子 | `key:<名前>` | API キーの登録簿（`api-keys.json`） |
| API キーの宣言の従量の接続の子 | `metered` で、`account_registry.metered_kind(宣言)` が `API_KEY_KIND` | 環境変数の宣言（`NDF_SUPERVISE_CLAUDE_FALLBACK`）の `ANTHROPIC_API_KEY` |

クラウド事業者の従量の接続（Bedrock など）の子は、キーの子に入らない。

## 宣言の提供元の確定（`account_registry.metered_kind`・`API_KEY_KIND`・`API_KEY_WITH`）

| 名前 | 種類 | シグネチャ・値 | 責務 |
| --- | --- | --- | --- |
| `metered_kind` | 新設 | `(env: Mapping[str, str]) -> Optional[str]` | 従量の接続の宣言の提供元を 1 つに確定する。`PROVIDER_ENV` のうち `provider_on` が真のものがちょうど 1 つで、ほかの `PROVIDER_ENV` がどれも偽（None の値があれば外れる）で、`ANTHROPIC_API_KEY` を持たなければ、その変数の名前を返す。どれも真でなく、`ANTHROPIC_API_KEY` が空白でない値で入っていて、ほかの `METERED_CHECKED` の変数が `API_KEY_WITH` と偽の提供元の選択だけなら `API_KEY_KIND` を返す。それ以外は None |
| `API_KEY_KIND` | 新設 | 定数 `"api-key"` | API キーの宣言を表す値 |
| `API_KEY_WITH` | 新設 | 定数。`ANTHROPIC_API_KEY` と「提供元ごとの照合する変数」の接続先の組の変数 | API キーの宣言が併用できる照合の変数 |

API キーの宣言で None になる組み合わせ:

| 組み合わせ | 例 | None にする理由 |
| --- | --- | --- |
| 提供元の選択と API キーの混在 | `CLAUDE_CODE_USE_BEDROCK=1 ANTHROPIC_API_KEY=…`（キーが空でも） | 同じ宣言を Bedrock として起動するか、候補から外すかが分かれる |
| ほかの認証の値 | `ANTHROPIC_API_KEY=… ANTHROPIC_AUTH_TOKEN=…`・`CLAUDE_CODE_OAUTH_TOKEN` | 認証の優先順位（STD2）で、指紋で固定したキーと別の資格情報が使われる |
| 資格情報とアカウントの選択 | `ANTHROPIC_PROFILE`・`AWS_PROFILE` | 同上 |
| 要求に足すヘッダー | `ANTHROPIC_API_KEY=… ANTHROPIC_CUSTOM_HEADERS=…` | ヘッダーの `Authorization` で別の資格情報を送れる |

使う場所: `wrapper._metered` の検証の「提供元を 1 つに選べる」の行（`metered_kind` が None でない）・`metered_env` が親の値を外すか・`account_choice.build` が helper を足すか・「従量の実効値の照合」の提供元の数。どれもこの 1 つの結果で決め、キーの有無や提供元の変数を別々に見ない。保存した設定の `check_decl` は、`PROVIDER_ENV` の名前を返す宣言だけを通す（保存した設定は資格情報の変数を持てない）。

**API キーの経路で使えるゲートウェイの設定は、接続先の変数だけである。** 追加のヘッダーが要るゲートウェイは、API キーの経路（環境変数の宣言の API キーと登録簿の `key:<名前>`。後者は詳細設計書の「`verify`」の表でヘッダーを拒む）では使えない。そうした宣言では、`_tell_at_start` の理由の 1 行に `ANTHROPIC_CUSTOM_HEADERS` の名前と「API キーの宣言ではヘッダーを足せない。ヘッダーの要らない接続先にするか、宣言から外す」を出し、従量の接続を候補に入れない（退避先が知らせなしに消えない）。値は出さない。

## 環境変数の宣言の API キー（`session_env.metered_env`・`account_choice.build`・`cli_account._acc_key_helper`）

**宣言の `ANTHROPIC_API_KEY` は、子の環境へ入れず、登録簿の API キーの子と同じく起動引数の `--settings` の `apiKeyHelper` で渡す。** 環境の `ANTHROPIC_API_KEY` で対話の claude を起動すると、キーを使うかを問う画面（「Detected a custom API key in your environment」）が出る。未承認のキーでは、切り替えた子が利用者の回答待ちで止まる。`apiKeyHelper` では問いが出ない（どちらも設計文書の「未確認のまま残ること」の「API キーの渡し方」で確かめた）。

| 部品 | API キーの宣言での振る舞い |
| --- | --- |
| `metered_env` | `account-drop` に加え、`METERED_CHECKED` の変数をすべて親の環境から外してから宣言を重ねる。宣言の `ANTHROPIC_API_KEY`（`session_env.METERED_HELPER_KEY`）は重ねない。親だけにある `ANTHROPIC_BASE_URL`・`ANTHROPIC_CUSTOM_HEADERS` は子に残らない。宣言にある接続先の変数は入る |
| 照合の期待値 | `metered_env` の出力。`METERED_CHECKED` の期待値は宣言の値だけで、親だけにある接続先とヘッダーは期待値に無い。設定ファイルから入っても、親から残っても外れる |
| `account_choice.build` | `metered` で `metered_kind(宣言)` が `API_KEY_KIND` のとき、`key:<名前>` と同じ「`--settings` の合成」で helper を足す。helper の文字列は `shlex.join([<ndf の実行ファイルの絶対パス>, "relay", "account", "api-key-helper", "metered", <指紋>])` である。合成は、候補を選ぶ照合用の起動引数（`fallbacks`。子のパスと ID はまだ無い）と、`target_env` の起動引数の両方に同じ条件で入れる（照合と起動で helper の有無を違えない）。引数の付き方は下の「照合した設定への固定」の「起動引数の 2 つの形」の 1 通りだけである |
| `<指紋>` | ラッパーが起動の前に検証した宣言の `ANTHROPIC_API_KEY` の値の SHA-256 の 16 進（`hashlib.sha256(値.encode()).hexdigest()`）。値そのものは起動引数にも `--settings` のファイルにも入れない（キーは推測できない長さの乱数なので、指紋から値は戻せない） |
| `api-key-helper metered <指紋>` | 自分の環境（Claude Code が設定の `env` を重ねた後の子の環境）の `NDF_SUPERVISE_CLAUDE_FALLBACK` を `wrapper._metered` と同じ検証で解き、`metered_kind` が `API_KEY_KIND` で、キーの値の SHA-256 が `<指紋>` と同じで、下の「照合した設定への固定」の照合に通るときだけ値を出す。宣言が無い・解けない・API キーの宣言でない・指紋が違えば、何も出さずに終了コード 1（下の「キーの子の認証の失敗の停止」へ入る）。設定の `env` が宣言を別のキーに差し替えても、検証したキーと違うキーは出さない |
| 起動の前の照合 | 詳細設計書の「従量の実効値の照合」の表の、helper の行（値が上の helper の文字列で、出所が `--settings`）と `NDF_SUPERVISE_CLAUDE_FALLBACK` の行（実効値が `metered_env` の継いだ値と同じ）。起動の後の差し替えは、下の「設定の変更でキーの子を止める範囲」で検出する |

保存した設定は資格情報の変数を持てないので、この経路は環境変数の宣言だけにある。

## キーの子の認証の失敗の停止

キーの子が 401 を受けたときと、helper が終了コード 1 を返したときの規則である。**どちらも、替え先の有無によらず子を残さない（`stalled` にしない）。** 子を残すと Claude Code が helper を呼び直し続け、止まる時点が無い。止めた後に替え先が無ければ、直し方の 1 行を出して `Ended("account_unavailable")` で終える。登録済みアカウントとクラウド事業者の従量の接続の子は、今どおり替え先が無ければ `stalled` で残す。

| 規則 | 中身 |
| --- | --- |
| helper の記録 | `api-key-helper`（`metered` と登録簿の `<名前>` の両方）は、記録先と ID を起動引数の `--record <記録先> --id <helper の ID>` だけから決める。Claude Code が設定の `env` を重ねた後の `NDF_RELAY_DIR`・`NDF_RELAY_LAUNCH` は、設定で書き換えられるので使わない。登録簿の場所（`NDF_ACCOUNTS_DIR`・`CLAUDE_CONFIG_DIR`）は helper 自身の環境から決めるので設定の `env` で替えられるが、これは詳細設計書の「脅威の範囲」の外として手当てしない。ラッパーは `_launch_target` で `target_env` を打つ前に helper の ID（`Target.helper_id`。`secrets.token_hex(16)`）を作り、記録先を、ラッパーが確定した中継の保存先（`self.dir`）の `key-helper.jsonl` の絶対パスにして、`build`・`target_env` のキーワード引数 `record=(記録先, helper の ID)` で渡す。子を起動する前に、保存先が `lstat` で symlink でなく自分の所有の 0700 のディレクトリであることを確かめ、古い記録と失敗の印（同じディレクトリの `key-helper.fail`）を `unlink` してから `os.open(記録先, O_WRONLY \| O_CREAT \| O_EXCL \| O_NOFOLLOW, 0o600)` で空の記録を作り、`(st_ino, st_dev)` を控える。確かめか作成が落ちれば、その起動先を理由 `key_record` で飛ばす（記録の無いキーの子を起動しない） |
| helper の書き方 | 呼ばれるたびに記録を `os.open(記録先, O_RDWR \| O_APPEND \| O_NOFOLLOW \| O_CLOEXEC)` で開き（作らない）、`fstat` で通常のファイル・`st_nlink` が 1・所有が自分・権限が 0600 であることを確かめ、`fcntl.flock(LOCK_EX)` を取る。下の「照合した設定への固定」の照合と、払い出しの上限の照合と、1 行の追記を、同じ錠の中で済ませる。1 行は `{"id": <helper の ID>, "at": <時刻>, "out": <キーを出したか>}` で、キーの値も指紋も書かない。キーを標準出力へ出すのは、`out: true` の行を書いて錠を放した後だけである。開けない・確かめが外れる・錠が `relay.key-helper` の `lock`（0.5 秒）で取れない・追記が落ちるときは、キーを出さずに終了コード 1。このとき記録には行を足せないので、終える前に、錠を取らずに記録と同じディレクトリの失敗の印 `key-helper.fail` を `os.open(…, O_WRONLY \| O_CREAT \| O_APPEND \| O_NOFOLLOW \| O_CLOEXEC, 0o600)` で開き、`{"id": <helper の ID>, "by": "helper", "cause": "lock" か "append" か "record"}` の 1 行を足す（印を作れない・書けないときもそのまま終了コード 1）。記録が正常なまま行が増えない失敗も、ラッパーがこの印で観測する。`--record` と `--id` は両方あるか両方無いかで、片方だけなら終了コード 1。両方無い起動（`ndf plan`。下の「入れ子の `ndf plan`」）は記録も上限も持たない |
| 払い出しの上限 | 錠の中で記録を読み、同じ helper の ID の行について次の順に確かめる。(a) ラッパーが書いた拒否の印（`{"id", "deny": true}`）か、`out` が偽の行が 1 つでもあれば出さない。(b) `out` が真の行が直近の `relay.key-helper` の `seconds`（60 秒）の間に `attempts`（3 回）以上あれば出さない。出さないときは `out: false` の行を足して終了コード 1。照合と追記が 1 つの錠の中にあるので、helper が同時に何本起動しても、`out: true` の行はどの 60 秒の間でも 3 行を超えない。(a) により、一度拒んだ後と拒否の印の後は、60 秒を過ぎても同じ ID へ出さない。正常時は起動の時点の 1 回と 5 分ごとの 1 回なので当たらない。指紋が違う・宣言が無い・使い方が `off`・無い名前で終了コード 1 を返すときも `out: false` の行を足す。照合した設定への固定に外れて出さないときは、`out: false` に `"cause": "pin"` を添えた行を足す（`_key_auth` は認証の失敗でなく設定の当たりとして扱う。下の「同時の当たり」）。`relay.key-helper` は `contracts/limits.json` に新設し、`seconds`・`attempts`・`lock`・`gate`（`config-gate` の hook の `timeout`。5 秒）・`first`（下の「最初の払い出しまで送らない」の待ち。30 秒）の 5 つを持つ |
| 検出（helper の終了コード 1） | `_key_auth` は `key-helper.jsonl` を `lstat` し、印が変わったときだけ `O_NOFOLLOW` で開いて読む。今の helper の ID の `out: false` の行（`cause` が `pin` のものを除く）があれば、画面の引き金と会話の記録を待たずに認証の失敗を確かめたとみなす。記録の異常（無い・symlink になった・控えた `(st_ino, st_dev)` と違う・`st_nlink` が 1 でない・読めない・行が JSON でない）も同じく確かめたとみなす（払い出しを数えられない子を動かし続けない）。加えて、見回りのたびに失敗の印 `key-helper.fail` を `lstat` し、今の helper の ID の `"by": "helper"` の行があれば同じく確かめたとみなす（子の起動の前に消すので、在るのは今のセグメントの失敗）。錠の取得を打ち切った・追記が落ちた helper は記録に行を残さないので、記録の印だけでは観測できない。保存先のディレクトリ自体が消えた・symlink になった・所有か権限が変わったときも、記録の異常として確かめたとみなす（印を作れない失敗をここで拾う）。**設定の当たり**（認証の失敗とは別に扱う）: 記録の `gate` の行（下の「反映の前に拒む」）・`out: false` で `cause` が `pin` の行・失敗の印の `"by": "gate"` の行（`config-gate` が拒んだ後の記録の失敗）・失敗の印の出し手を読めない行（symlink・読めない・JSON でない・`by` が無い）。どれもキーが断られたのではなく、宛先・認証の項目が照合した内容から変わったことを表す |
| 検出（401） | 詳細設計書の「認証の失敗の確かめ」（画面の引き金と、会話の行の最後の `assistant` の記録）で確かめる。キーの子でこれを打つのは `_key_auth` で、`_auth_pick` ではない。確かめたら、旧子を止める前に、helper と同じ錠の中で記録へ拒否の印 `{"id": <helper の ID>, "deny": true}` を足す（錠が取れない・書けないときもそのまま止める） |
| 検出の順 | `_loop` の (2) の `_drift` の直後、(3) の停止の判定より前に、キーの子だけ `_key_auth(sec, screen)` を打つ（返りは無く、フラグだけを立てる）。認証の失敗を確かめたら、今の起動先を `tried` に入れ、`Section.end_cause` を `auth` にして `must_end`・`must_end_at`・`end_now` を立て、入力の転送を止める。設定の当たりを読んだら、`_drift` の「送信先や認証を変え得る不一致」（下の「設定の変更でキーの子を止める範囲」の表の 2 行目）と同じく扱う。`tried` に入れず（キーは有効なので、ほかの宛先の設定での替え先の候補から外さない）、`end_cause` がまだ無ければ `drift` にして、`must_end`・`must_end_at`・`end_now` を立て、入力の転送を止める。候補も `after_auth` も読まず、`hold` もしない。同じ見回りの (3) で `_end_point` が `end_now` で真になり、`_stop_revoked` が旧子を止める |
| 同時の当たり | `must_end` が既に `drift` で立っているとき、または同じ見回りの `_drift` がキーの削除・登録し直し・`off` だけを当てて `must_end` を立てた（`end_now` は偽）ときは、helper の `out: false`・記録の異常・401 のどれでも `end_now` を立てず、`end_cause` も `drift` のままにして、下の「止める時点」の待ちを続ける。削除・`off` の後の helper の失敗はキーを出さない結果で、401 は変更前の宛先がキーを断った結果であり、どちらも許していない宛先へ送る経路ではないためである。401 のときも拒否の印は足す。逆に、`_key_auth` が先に `end_now` を立てた後に `off`・削除を検出しても `end_now` は下ろさない。`_drift` が `end_now` の当たりを当てた見回りは、`_key_auth` の結果によらず `end_now` が立っている。**設定の当たりは、この抑えの外にある。** `must_end` が `off`・削除・登録し直しで既に立っていても、同じ見回りの `_drift` がそれだけを当てていても、設定の当たりを読んだ見回りで `end_now` を立てる（`end_cause` は先に書いた `drift` のまま）。照合と違う設定は、反映されれば許していない宛先へ送る経路である。拒んだ変更はファイルに残り、待ちの間の次の保存のたびに関所を通り直すので、最長 60 秒の待ちを関所の成否に頼らない |
| `_auth_pick` | キーの子では何もせずに None を返す（`hold` も `after_auth` も打たない）。`_state` はキーの子へ `auth_pick=None` を渡すので、キーの子に `stalled` の手は返らない |
| 止め方 | 旧子を止めるのは `_loop` の (3) の `_stop_revoked` だけで、下の「止める時点の表」の `_end_point` が真の行と同じ順である。止めた見回りの `_state` で `_revoked_pick` が初めて替え先を読み（起動の理由 `revoked`。今の起動先は `tried` にあるので除く）、`_revoked` が手を返す。替え先が無ければ、`_on_revoked` が、`end_cause` が `auth` のとき直し方の 1 行（`tried` の名前と名前ごとの直し方。詳細設計書の「試して失敗した接続先の規則」）を出してから `Ended("account_unavailable")` で終える。設定の当たりで止めた（`end_cause` が `drift`）ときは、キーが断られた前提の直し方の 1 行を出さず、`ndf-relay: API キーの子の宛先・認証の設定（<source>）が起動のときと変わったので止めた。設定を戻すか、ndf relay で起動し直す` の 1 行（`<source>` は `gate` の行の `source`。`pin` と出し手を読めない印では `設定ファイル`）を出す。値とパスは出さない |
| 終点 | 替え先の起動（`--resume`）か `Ended`（`account_unavailable`・`refused`・`spin`）のどれかで必ず終わり、子を残したまま待つ経路は無い |
| 時間の上限 | 確かめた見回り（401 を確かめた見回りか、`out: false` の行・記録の異常・失敗の印・設定の当たりを読んだ見回り）から旧子の終わりまで、`relay.child-exit` の 5 秒以内（検出と停止は同じ見回りの (2)〜(3)）。記録の印が変わってから読むまでの最大 `relay.tick` の 0.5 秒と合わせて 5.5 秒である |
| 払い出しの回数 | 1 つの helper の ID でキーを出すのは、どの 60 秒の間でも 3 回までで、拒んだ後と拒否の印の後は 0 回である。401 の打ち直しの間（実測で会話の記録の最後の `assistant` が書かれるまで約 256 秒）も、この上限で 4 回目の呼び出しが終了コード 1 になり、上の検出に入る |
| CLI の起動の回数 | 払い出しの上限が縛るのはキーを出す回数だけで、helper の CLI の起動（`ndf` の起動 1 回）の回数は縛らない。拒んでから旧子が止まるまでの起動の回数は Claude Code の呼び直しの間隔で決まり、最短の間隔は公開されていないので設計からは導けない。そのため U11a の PR で、手元の Claude Code の対話の子を使い、(i) helper が最初から終了コード 1（指紋の合わない宣言）、(ii) helper はキーを出し模擬の API が 401、の 2 通りで、子の起動から止まるまでの helper の起動の回数と間隔を測り、PR の本文に残す。受け入れ条件は、1 つのセグメントで (i) が計 4 回以下（拒んだ 1 回と、止まるまでの 3 回）、(ii) が計 6 回以下（払い出し 3 回と、止まるまでの 3 回）である。超えたら実装を止めて設計へ戻す（止めるまでの時間を縮めるか、拒んだ起動を軽くする） |
| 入れ子の `ndf plan` | relay の子の Claude Code の中で打った `ndf plan` の `call_claude` は、`build` を `record=None` で打つので、内側の helper は `--record`・`--id` を持たない。内側の helper は外側の記録を書かず、外側の ID の払い出しの枠を使わず、外側の子の停止を起こさない（外側の helper の文字列は外側の子の起動引数にだけあり、環境で継がれない）。内側の取り直しは `call_claude` の timeout で必ず終わる。`call_claude` の子の環境から `NDF_RELAY_DIR`・`NDF_RELAY_LAUNCH` を外すかは、この設計では変えない（設計文書の「人へ残す判断」の 11） |

### helper の呼び出しの回数と所要時間

正常時の追加のコストは、起動の時点の 1 回（`claude -p` の 1 回の実行ごとに 1 回）と、動いているセッションで Claude Code の既定の有効期間の 5 分ごとに最大 1 回（1 時間で最大 12 回）である。1 回は `ndf` の起動 1 回で、`api-key-helper` は登録簿の読みと宣言の解釈と記録の 1 行だけにし、ほかの部品を読み込まない（起動の時間を `ndf relay account --help` の水準より増やさない）。認証の失敗の間の回数は、上の表の「CLI の起動の回数」で縛る。

| 経路 | 初回の取得 | 再取得 | 認証の失敗の間 |
| --- | --- | --- | --- |
| 対話のセッション | 起動の時点で 1 回（入力の前） | 最初の取得から 5 分を過ぎた後の最初の要求で 1 回。空いている間は呼ばれない | 取り直しが続く |
| `claude -p`（`ndf plan` と同じ起動の形） | 1 回の応答で 1 回 | 同じ規則 | 同上。`call_claude` の timeout で終わる |

表の回数と、`ndf relay account --help` の 1 回が 0.65〜0.75 秒（最初の 1 回は 1.1 秒）という所要時間は、U1 の PR #4018 の修正担当が手元（2026-11-22 JST、Claude Code 2.1.330）で、キーを出すだけのスクリプトを `apiKeyHelper` にし、応答を返す模擬の API を `ANTHROPIC_BASE_URL` に向けて数えた値である（無効なキーでは 120 秒に 9 回、平均約 13 秒の間隔）。測った手順と出力は残っておらず、未確認として扱う。U11a の PR で、上の「CLI の起動の回数」の実測と一緒に測り直し、PR の本文に残す。

## 設定の変更でキーの子を止める範囲

詳細設計書の「起動の後の設定の変更」で印が変わり、打ち直しで当たったときの、キーの子の扱いである。キーの子は替え先の有無によらず `_revoked` の経路で止める（`stalled` にしない）。helper の指紋はキーの差し替えだけを止め、宛先・ヘッダー・別の資格情報の追加・変更・削除は止めないためである。

| 当たり | 止める時点 | 理由 |
| --- | --- | --- |
| 登録簿のキーの削除・同じ名前の登録し直し（`generation` が起動のときと違う）・使い方の `off`（`key:<名前>` だけ） | 下の「止める時点」の待ち（止めてよい時点か `relay.end-wait` の 60 秒の早い方） | キーは変更前の宛先にしか送られない。登録し直した新しいキーは、helper が起動のときの世代（`--generation`）と違うので出さず、動いているセグメントでは送られない |
| 上の 2 つのほかの、送信先や認証を変え得る不一致すべて | 検出した見回り（`end_now`） | 道具の実行の途中でも、その結果を使う次の要求は利用者の入力なしに出て、変更後の宛先や資格情報でキーと会話を送る |

2 行目に入るのは、宛先・ヘッダー・資格情報・提供元の選択の変数・`apiKeyHelper` の追加に加え、既存の値の変更と削除である。たとえば、宣言した `ANTHROPIC_BASE_URL` を設定ファイルの `env` が別の URL へ置き換える・消して既定の宛先へ戻す、管理の設定が `--settings` の helper より上に別の `apiKeyHelper` を置く、がどれも当たる。API キーの宣言の従量の子では、宣言との照合（「従量の実効値の照合」）の外れすべてが当たる。

### 照合した設定への固定（`Resolved.pins`・`--pin`）

`verify` が設定を読んでから Claude Code が起動の時点の設定を読むまでの間に保存が入ると、照合していない宛先が最初から使われる。`ConfigChange` は実行中の変更だけを扱うので、この間には効かない。Claude Code が読む初期の設定そのものを照合済みの内容に固定する起動引数は無い（`--setting-sources` で源を外すと利用者の許可・hooks・プラグインも失う。詳細設計書の「起動の後の設定の変更」）。そのため、**キーを出す側で、設定が照合した内容のままであることを確かめてからキーを出し、会話はその払い出しを見届けてから子へ渡す。** キーを出す側の確かめだけでは足りない。照合の後に設定へ別の資格情報（`ANTHROPIC_AUTH_TOKEN` など）や優先される別の `apiKeyHelper` が入ると、Claude Code は NDF の helper を呼ばずに、その資格情報で照合していない宛先へ最初の要求を送れる。そこで、Claude Code の起動の後に NDF の helper が照合に通ってキーを出したこと（＝Claude Code が照合した設定のとおり NDF の helper を認証に使っていること）を、最初の会話を子へ渡す条件にする。helper の照合は Claude Code が設定を読んだ後に動くので、照合に通った払い出しを見届けたら、Claude Code が読んだ設定は照合した内容と同じである（下の「固定できない場合」の 2 回の保存を除く）。見届けられない起動の形には、キーを渡さない。

| 規則 | 中身 |
| --- | --- |
| 比べる範囲（`account_dir.gate_view`。新設） | 設定ファイルの object から、`env` のうち `account_registry.GATED_ENV`（新設。`METERED_CHECKED`・詳細設計書の「`verify`」の表の「認証の値」の組・`NDF_SUPERVISE_CLAUDE_FALLBACK`・`CLAUDE_CODE_SIMPLE`・`CLAUDE_CODE_SAFE_MODE`）の名前の値と、`apiKeyHelper`・`disableAllHooks`・`allowManagedHooksOnly` だけを取り出した object。宛先・ヘッダー・資格情報・提供元の選択・helper の項目と、下の「起動の前の確かめ」が関所の有効性の判定に使う項目（hook の無効化・管理の hook だけの許可・簡易の起動・安全の起動）で、`permissions`・`hooks`・`model` などは入らない。無いファイルは空の object と同じに扱う。関所の有効性の判定に使う項目を足すときは、この組にも足す（照合の後に変わった設定で、関所の働かない子へキーを出さない） |
| 起動引数の 2 つの形 | helper と `config-gate` の文字列の末尾の引数は、次の 2 通りだけである。(a) 照合用の起動引数（`fallbacks`。候補を選ぶ時点で、子の固定のファイルと helper の ID はまだ無い）: `--pin`・`--record`・`--id` のどれも持たない。`fallbacks` の `verify` は、この形の文字列を期待値として実効値と比べる。(b) `target_env` が `verify` に渡す起動引数と子の実際の起動引数: 同じ 1 つの文字列で、`--pin <固定のファイル>` を必ず持ち、ラッパーの起動では続けて `--record <記録先> --id <helper の ID>` を持つ（`ndf plan` では `--pin` だけ）。`target_env` の `verify` は、この形の文字列を期待値として実効値と比べ、通った引数をそのまま子へ渡す（照合した文字列と起動する文字列を作り直さない）。(a) と (b) で違うのは、この末尾の引数だけである |
| 控え（`Resolved.pins`） | 設定ディレクトリは `verify` が子の作業ディレクトリから絶対パスに解いてから `effective_env` へ渡すので、控えの `files`・`dirs` のパスはどれも絶対パスである（相対の `CLAUDE_CONFIG_DIR` を NDF の作業ディレクトリから解かない。U12b の PR #4142。#4136）。`effective_env` は、読んだか探した設定ファイル（利用者・プロジェクト・ローカル・管理の設定のファイルと `managed-settings.d` の各ファイル・`--settings` のファイル）ごとに、`gate_view` を `json.dumps(sort_keys=True)` にした SHA-256 の 16 進を `Resolved.pins` に持つ（`managed-settings.d` はファイルの名前の一覧も控える）。照合と同じ 1 回の読みから作り、読み直さない |
| 固定のファイル | `target_env` は、`verify` を打つ前に `<状態の保存先>/settings/<stem>.pin.json`（`<stem>` は `<owner の pid>-<owner の開始時刻>-<secrets.token_hex(8)>`）のパスを決め、上の (b) の形の起動引数で `verify` を打つ。合成の一時ファイルを書く起動では、その一時ファイルを同じ `<stem>` の `<stem>.json` にする。通ったら、その `Resolved.pins` を固定のファイルへ `O_WRONLY \| O_CREAT \| O_EXCL \| O_NOFOLLOW`・0600 で書いてから子を起動する（書けなければ一時ファイルと一緒に消して `key_record`）。置き場・寿命・出さないものは、詳細設計書の「`--settings` の合成と引用」の一時ファイルと同じ規則で、`Built.settings_file` と並べて `Built.pin_file` が持つ。ラッパーと `ndf plan` のどちらの起動も書く。残骸の規則だけは下の行で別に決める |
| 固定のファイルの残骸 | 一時ファイルの残骸の規則（`/proc/<pid>/cmdline` の独立した要素にパスを持つプロセスを探す）は、固定のファイルには使わない。固定のファイルのパスは、起動引数の `--settings` の JSON の文字列の中か、合成の一時ファイルの中にあり、独立した要素にならないためである。`target_env` は、`<stem>.pin.json`（と同じ `<stem>` の `<stem>.pin.ok`）を次の 3 つをすべて満たすときだけ消す。(1) 名前の `owner` の pid と開始時刻のプロセスが生きていない。(2) どのプロセスの `/proc/<pid>/cmdline` の要素にも、固定のファイルの絶対パスを部分の文字列として含むものが無い（`--settings` に JSON の文字列を渡した子は、その要素の中に持つ。パスは乱数を含むので、含む要素を持つプロセスがそのファイルを使う子である）。(3) 同じ `<stem>` の合成の一時ファイル `<stem>.json` が無い（一時ファイルを使う子は、一時ファイルの残骸の規則で生きている間は残るので、その間は固定のファイルも残る）。一時ファイルの残骸を先に消し、その後に固定のファイルを判定する。`/proc` を読めないときは消さない |
| helper の照合 | `api-key-helper` は払い出しのたびに、錠の中で `--pin` のファイルを `O_NOFOLLOW` で開き、通常のファイル・所有が自分・0600 を確かめ、控えた各パスの今の `gate_view` の SHA-256 と比べる。1 つでも違う・読めない・解けない・`managed-settings.d` の名前の一覧が違う・`--pin` が無いか開けないときは出さない（ラッパーの起動では `out: false`・`cause: pin` の行。`ndf plan` では行を書かずに終了コード 1）。照合に通ってキーを出すときは、`ndf plan`（`--record` が無い）では、出す前に同じ `<stem>` の `<stem>.pin.ok` を `O_WRONLY \| O_CREAT \| O_NOFOLLOW`・0600 で作る（作れなければ出さずに終了コード 1）。起動の時点の 1 回は Claude Code が設定を読んだ後なので、照合の後・Claude Code の読みの前に入った変更も、読みの後・最初の払い出しの前に入った変更も、NDF の helper を使う限り最初の要求より前にここで当たる。NDF の helper を使わなくなる変更は、次の行で止める |
| 最初の払い出しまで送らない | Claude Code が NDF の helper を呼ばずに別の資格情報を使う起動（照合の後に入った `ANTHROPIC_AUTH_TOKEN`・優先される別の `apiKeyHelper` など）では、上の照合が動かない。そのため、子が今の起動の helper の照合に通った払い出しを見届けるまで、会話を子へ渡さない。ラッパー: 子を起動してから、記録に今の helper の ID の `out: true` の行が現れるまで、最初のプロンプト・利用者の入力・質問の回答を子の端末へ送らずに控える（「止める時点」の捨て方と違い、現れたら控えた順に送る）。子の起動から `relay.key-helper` の `first`（30 秒）を過ぎても現れなければ、`_key_auth` は設定の当たり（`end_cause` が `drift`・`end_now`。理由の 1 行の `<source>` は `設定ファイル`）として子を止め、控えた入力を捨てる。`out: false` の行や失敗の印が先に現れたときは、今までの規則で止める。`ndf plan`: `call_claude` は質問を標準入力で渡すので、`<stem>.pin.ok` ができるまで標準入力へ書かずに待ち、できたら質問を書いて閉じる。`first` を過ぎてもできなければ、組ごと止めて `key_gate` の失敗を返す（キーの子の起動を諦め、質問を送らない）。対話の起動で Claude Code が入力の前に helper を呼ぶこと、`claude -p` が標準入力の終わりを待たずに helper を呼ぶことは、下の「確かめ」の (5) で確かめる。外れた起動の形は「最初の払い出しを見届けられない形」として、キーの子を起動しない（ラッパーでは `key_gate` で外し、`ndf plan` ではその形に `call_claude` がキーを渡さない） |
| 固定できない場合 | 照合の後に設定を元へ戻す 2 回の保存が Claude Code の読みと helper の呼び出しの間に収まる場合は当たらない。これは数百ミリ秒の間に意図して書き換える操作で、脅威（うっかりの利用者と権限の無い人）の外にある（詳細設計書の「脅威の範囲」）。会話を渡す前に Claude Code が送る要求（起動の時点の確かめ `HEAD /api/hello` など）は会話を持たないが、別の資格情報へ切り替わった起動では照合していない宛先へ送られ得るので、設計文書の「レッドラインの表」の行に残す。Claude Code が helper の最初の呼び出しより後に設定ファイルを読み足す（helper の照合を後から抜ける）ことが下の「確かめ」で見つかったら、キーの子を起動しない（実装を止めて設計へ戻す） |

### 反映の前に拒む（`ConfigChange` の hook・`config-gate`）

**キーの子では、利用者・プロジェクト・ローカルの設定の変更のうち、上の「比べる範囲」が照合した内容から変わるものを、Claude Code が実行中のセッションへ反映する前に拒む。** 見回りで検出して止めるだけでは、保存の直後に道具の結果が返ると、次の見回り（最大 `relay.tick` の 0.5 秒後）より先に、キャッシュ済みのキーと会話が変更後の宛先へ送られる。`end_now` は検出した後の待ちを省くだけで、送信の前の制約にはならない。宛先に関わらない変更（許可の追加・`/config` の表示の設定・skills の編集など）は通し、子も止めない。同じセッションで「今後は確認しない」・`/permissions`・`/model` で保存した設定は、Claude Code が hook を打たずに反映する（公開の文書の `ConfigChange`）が、どれも比べる範囲の外である。

| 規則 | 中身 |
| --- | --- |
| hook の合成 | `build` は、キーの子の `--settings` の合成（詳細設計書の「`--settings` の合成と引用」の表）に、helper と並べて `hooks.ConfigChange`（matcher 無し）の command の hook を 1 つ足す。hook は `{"type": "command", "command": <文字列>, "timeout": <relay.key-helper の gate>, "onFailure": "block"}` である。`onFailure: "block"` により、`config-gate` が起動できない・終了コード 0 と 2 のほかで終わる・`timeout` を過ぎたときも、Claude Code は終了コード 2 と同じく変更を反映しない（[公開の文書](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails)）。文字列は `shlex.join([<ndf の実行ファイルの絶対パス>, "relay", "account", "config-gate", "--pin", <固定のファイル>])` を、上の「起動引数の 2 つの形」の (b) にしたもの（ラッパーの起動では helper と同じ `--record <記録先> --id <helper の ID>` が続く）。hook の有無は照合用の起動引数と子の実際の起動引数で同じにし、照合用の起動引数（`fallbacks`）の hook の文字列は (a) の形で `--pin` を持たない |

**`claude -p` は 4 つの形（`PRINT_JSON`・`PRINT_STREAM` の通常の起動と、`minimal_args` の json・stream）とも、標準入力の終わりを待たずに NDF の helper を呼ばなかった。** Claude Code 2.1.330 は、標準入力を読み終えるか 3 秒待ち切る（`no stdin data received in 3s`）まで helper を呼ばない。そのため `<stem>.pin.ok` を見届けてから質問を書く形は成り立たない。上の「最初の払い出しまで送らない」の規則どおり、4 つの形はどれも「最初の払い出しを見届けられない形」として記録し、`ndf plan` でキーを渡さない（`claude.KEY_FORMS` は空。`call_claude` は `key:`・API キーの宣言の `metered` の親で `key_gate` の `Failure.REFUSED` を返す）。形が使えるようになっても、`KEY_FORMS` に足すだけでは有効にしない。今の `_talk`（`adapters/claude.py`）は `<stem>.pin.ok` を待たずに `communicate(prompt)` で質問を書くため、この順序のままでは上の実測のとおり別の宛先・資格情報へ質問が渡り得る。形を `KEY_FORMS` に足す変更は、次の 3 つをそろえてから入れる: (1) キーの子では `_talk` が質問を書く前に `<stem>.pin.ok` の作成を `relay.key-helper` の `first`（30 秒）まで待つ（上の「最初の払い出しまで送らない」の `ndf plan` の規則）、(2) 期限までに印が無ければ質問を 1 文字も書かずに子を止め（`terminate` → `kill`）、`key_gate` の `Failure.REFUSED` を返す、(3) 印を待つ・期限切れで止める・止めた子へ質問が届いていないことを、その形の実際の起動で確かめるテストを足す。合成・`--pin`・親の接続の識別は `plan_claude.begin(…, keys=True)` のテストで通してある。スプリントの目的への影響は、設計文書の「未確認のまま残ること」の「`ndf plan` の `claude -p` へキーを渡す形」にある。

**helper が記録を書く前に落ちる経路は、ラッパーが helper の失敗として観測できない。** ホストで打った対話の子の約 30 回のうち 2 回、NDF の helper が記録にも失敗の印にも行を書く前に、import の失敗（`サブコマンドが捕まえない例外で止まった: relay`）で終了コード 1 を返した。版ごとの共有の venv を、根ごとに `uv.lock` の違う別の作業場所の `uv run --frozen` が入れ替える最中に落ちたと見ている（#4006）。このとき上の「検出（helper の終了コード 1）」の記録の印も失敗の印も変わらないので、`_key_auth` は止めない。Claude Code は空の `Authorization: Bearer` で会話を持ったまま元の宛先へ送り続けるが、キーは出ていないので漏れは無く、許していない宛先へも送らない。この経路を 401 の検出に任せるか、helper の起動を包んで記録の前の失敗も失敗の印に書くかは決めていない（#4139。設計文書の「未確認のまま残ること」の「helper が記録を書く前に落ちる経路」）。

### 止める時点

キーの子で `_drift` が当たるか、`_key_auth` が 401・helper の失敗・設定の当たりを確かめると、次の順に進める。上限・認証の失敗・再起動ループの検出・次のセグメントのマーカーのどれと重なっても、この順を先にする（決定 12・13）。
