# #2457 の設計: 決定の記録

[issue-2457-design.md](issue-2457-design.md) から分けた決定の記録である。外部の調査の番号（`STD1` など）は設計文書の「外部の調査」の表を指す。

## 決定の記録

### 決定 1: 選ぶ件数がテストと CI の所要で変わらないよう、見積りをテストの追加と実装の和にし、経過とバッファを引かない

選定は「実効の予算 ≥ 採った項目の見積りの和」だけで決める。見積りは配分テーブルの `test`（足すテストがあるときだけ）と `structure/<手法>` の和で、`verify` を入れない。今は `verify` と経過とバッファ（全体テスト・CI の待ち・修正 1 回分）を予算から引くため、30 分のうち実装に回る時間が 5 分前後になっていた（#2202）。テストと CI の所要はどの項目でもかかる固定の時間で、件数を決める材料にならない。

予算の中に検証の時間も含めて数える形は採らない。受け入れ条件 2 が、テストの所要だけを変えた 2 回の選定で件数が同じになることを求めている。順位（グレード・賛同数・重要度）と、入らない候補を飛ばして次を見る選び方（#933 決定 10）は変えない。

根拠: Value 4 / Value 7（MVV 版 6）

### 決定 2: 順位の高い候補が予算の境目で切れないよう、グレード high の見積りの和が予算と 2 倍の間にあるときだけ予算をその和まで延ばす

延ばすかは「グレード `high` の候補の見積りの和 S」だけで決める。S ≤ B なら high はすべて入るので延ばさない。B < S ≤ 2B なら実効の予算を `ceil(S)` 分にする。理由は `budget.extension` に `{from: B, to: ceil(S), reason: "high の候補の見積りの和 S 分が予算 B 分を超えた", high_minutes: S}` を残す。S > 2B なら延ばさず、境目より下を `budget` で見送る。延ばした後の選定は同じ `select` を実効の予算で 1 回走らせる。順位は high が先頭なので、延ばした分は high に先に使われ、余りは次の順位の候補が使う。

「境目で絞り切れない」を順位の 1 位の候補が入らないときに限る形は採らない。1 位が小さく 2 位以降の high が切れる場合に延びず、high の中で採否が分かれる。倍率は `limits.json` の `cross-refactoring.budget-extension` の `factor`（2）に置く。

根拠: Value 3 / Value 4（MVV 版 6）

### 決定 3: 成立しない項目だけを打ち切るため、成立の判定を実装担当と別のランタイムに行わせ、担い手はホスト → 参加者の順で実装担当以外から選ぶ

判定の担い手は、`init` が確かめた参加者のうち実装担当でない者を、ホスト（参加者にいれば）→ 参加者の並びの順で 1 者選ぶ。担い手は提案のときと同じ読み取り用の作業ディレクトリを HEAD へ同期して起動し、コミットさせない。答えは `{"item", "feasible": true|false, "reason", "evidence"}` で、`evidence` には根拠にした差分の行かテストの出力を引かせる。判定は変更起因の失敗が出た項目に 1 回、停滞か振動を検知したときにもう 1 回（判定し直し）行う。修正担当を替えるときは、担い手と同じ選び方で実装担当の次の者にする。

担い手が居ない（参加者が 1 者だけ）か答えを残さないとき、初回の判定は「判定できない」として成立と同じに扱い、修正を続ける。判定し直しで担い手が居ないときは、打ち切りも続行も決められないので止めて人へ渡す（`gate`）。実装担当自身に判定させる形は採らない。直している当人の判定は、成立しないと言う理由を持たない。

選び方の部品は共通ライブラリ `scripts/lib/assignment.py` の「ホスト → 先頭」（`choose_implementer`）を使い、実装担当を除いた参加者で呼ぶ。cross-refactoring の中に選び方を書かない。

根拠: Value 5 / Value 7（MVV 版 6）

### 決定 4: 回数の上限を置かずに修正の空回りを止めるため、落ちたテストの集合を履歴と比べて前進・停滞・振動を判定する

修正 1 回ごとに、その項目の落ちたテストの集合 F(n)（無関係な失敗とフレーキーを除いた ID の集合）を記録する。F(n) が空なら通過、F(n) = F(n−1) なら停滞、F(n) が F(0)〜F(n−2) のどれかと等しければ振動、それ以外（件数が減った・別のテストへ移った）は前進である。前進の間は回数の上限なく修正へ回す。停滞か振動を検知したら同じ修正を繰り返さず、判定し直しへ回す（決定 3）。修正担当を替えた後にもう一度停滞か振動したら打ち切る。原因の項目を決められない失敗（`undetermined`。どの項目にも結ばない修正で直す）も同じ判定を当てるが、打ち消す項目が無いため、替えた後の停滞か振動では打ち切らずに止めて人へ渡す（`gate`）。

既定は 2 つで、`limits.json` の `cross-refactoring.fix-progress` で変えられる。

| 判定 | 既定 | 設定 |
| --- | --- | --- |
| 停滞 | 同じ集合が 2 回続く | `stagnation_same_sets: 2` |
| 振動 | 前に見たすべての集合と比べる | `oscillation_lookback: 0` |

修正の回数や残り時間で止める形は採らない。前進している修正を時間で止めると、PR 2452 のように直せる項目が消える。止める判断を形に置く考え方は、エージェントの停滞を繰り返しと交互の形で検知する PRD1 と同じである。

- 作り方: 自前で作る
- 比べた候補: PRD1

根拠: Value 3 / Value 5（MVV 版 6）

### 決定 5: 時間の上限を異常の検知にだけ残すため、安全網はコーディングの起動の秒の累計に置き、当たったら取り消さずに `gate` で止める

安全網の上限は「実効の予算 × `cross-refactoring.safety-net` の `factor`（2）」分で、`--safety-net-minutes` で上書きできる。数えるのはコーディングの CLI（テストの追加・実装・修正・最終ゲート修正・フレーキーの直し）の起動ごとの秒（監視の開始から終わり）の累計である。提案・計画・判定・テストの実行・CI の待ちと止まっていた時間は数えない。コーディングの CLI の監視の上限は安全網の残りで切る。起動の前に残りが 0 以下なら起動せずに止まる。

止まったら項目を取り消さず、HEAD をそのまま残し、項目の行（決定 10）を書いてから結果 JSON を `gate`・終了コード 10 で返す。`next` に「安全網の上限 N 分に当たった。続けるなら `--safety-net-minutes` を大きくして同じコマンドを打ち直す。やめるなら項目のコミットを `git revert` して `plan-comment --scan-reverts` を打つ」を書く。止まった地点の材料（項目ごとの状態・落ちているテスト・修正の履歴）は `items[0].refactor_items[]` に載る。上限で取り消して `stopped` で返す形は採らない。原則 1 のとおり、上限は打ち切りの理由にしない。

根拠: Value 2 / Value 3（MVV 版 6）

### 決定 6: 取り込んだベースブランチの変更を消さないため、打ち消しを項目のコミットの `git revert` だけにし、衝突したら止める

成立しないと判定した項目の打ち消しは、その項目のコミット（テスト・実装・修正）を新しい順に `git revert` する。公開の前でも後でも同じ手順で、`reset --hard` で未公開のコミットを外して積み直す経路と、起点の木へ戻すコミットを積む経路を消す。今の積み直しは、どの記録にも無いコミット（取り込んだベースブランチのマージなど）を外すため、#2323 の形でベースブランチの変更が消えていた。STD1 の `git revert` は指定したコミットの変更だけを打ち消す。

打ち消しが衝突したら `git revert --abort` で打ち消しの前の HEAD へ戻し、衝突した項目を外さずに `gate` で止める（受け入れ条件 19）。衝突した項目を外して続ける今の形（`ejected`）は採らない。外す理由が「別の項目と隣り合っていた」で、その項目が成立しないわけではない。コミットの数は打ち消しの分だけ増えるが、前提 6 のとおり履歴の書き換えを使わない。

- 作り方: 標準に倣う
- 比べた候補: STD1

根拠: Value 7 / C4（MVV 版 6）

### 決定 7: ベースブランチ由来の失敗を変更起因と取り違えないため、無関係な失敗は比較の木で見分ける

落ちたテストのうち、走らせ直して通るものはフレーキー（今どおり）、残りを比較の木で走らせる。比較の木は、HEAD から取り消していない改善項目のコミットをすべて `git revert --no-commit` で外した一時の detach の worktree である。着手の後に取り込んだベースブランチの変更を含む。比較の木でも落ちれば無関係な失敗で、項目の合否と停滞の判定に数えない。今は着手前の HEAD（`init` の SHA）と比べるため、着手の後にベースブランチを取り込んで落ちたテストを変更起因と読む（PR 2452 の 1 番の形）。比較の木を作れない（打ち消しが衝突する）ときは、着手前の HEAD で走らせる今の比べ方へ戻し、`whole_test.fallback_reason` に理由を残す。

フレーキーの見分けを走らせ直しの回数を増やす形（PRD2）や pytest のプラグイン（LIB2）へ置き換える形は採らない。利用先のリポジトリのテストのランナーを問わない今の見分けで足り、ランナーごとの部品を増やす。

- 作り方: 自前で作る
- 比べた候補: PRD2 / LIB2

根拠: Value 6 / Value 7（MVV 版 6）

### 決定 8: 検査のプランで予算を超えた実行が打ち切られないよう、ステップの締め切りを駆動がステップの延長で延ばし、`drive` の終了コード 10 を承認ゲートとして扱う

雛形の `refactor` のステップの `timeout` は「実効の予算 ×（1 + 安全網の倍率）」分の秒に `with_margin` を足す。テストの実行・CI の待ちはこの外にある。そのため駆動は子プロセス（テスト・CI の待ち・CLI）を起動する前に、ステップの開始からの経過とその子プロセスの上限の和を書く。書く先はステップの延長のファイル（`drive_pause.write_extension`。#2047 決定 4）である。延長は締め切りを後ろへずらすだけで、前へずらさない（#2047 の I7）。

プランの実行（`supervise_lib/engine.py`）の承認ゲートの判定を `drive` のステップにも当てる。今は `run` のステップの 10〜19 だけを承認ゲートとして扱い、`drive` の 10 は `on_fail`（`abort`）へ進む。雛形に `on_exit: {"10": ...}` を足す形は採らない。承認ゲートの扱いは共通の契約（`lib/step_result.py` の `GATE_CODES`）が決めるもので、ステップごとに写すと契約と食い違う。

根拠: Value 5 / Value 6（MVV 版 6）

### 決定 9: フレーキーをその実行の中で直すため、見分けたテストの直しを実装担当へ 1 回依頼し、項目とは別のコミットで残す

仕分けでフレーキーと見分けたテストごとに、実装担当へ `prompts/flaky-fix.md` で直しを 1 回依頼する。直しはトレーラー `Flaky-Fix: <テストの ID>` を持つコミットで、オーケストレーターが残すコミットとして台帳（`ledger.orchestrator_commits` と同じ扱い）へ記録する。項目の合否・停滞の判定・項目の実装時間に数えず、安全網の累計には数える。直しのコミットが無い・テスト以外のファイルを変えたときは、差し戻しを 1 回だけ行い、それでも直らなければ直しのコミットを打ち消して報告へ残す（項目は触らない）。同じテストの直しは 1 回の実行で 1 回だけ依頼する。

規則と見分けの部品の正本は #2458 で、#2458 は同じスプリントに入っていない。cross-refactoring・cross-review・fix で共通の部品を作るのは #2458 の範囲として、この変更は cross-refactoring の中の依頼と記録だけを持つ。共通の部品ができたら `commands/flaky.py` をその部品へ寄せる。

根拠: Value 1 / Value 7（MVV 版 6）

### 決定 10: 次回の見積りの材料を失わないよう、項目ごとの実績を配分の履歴の同じファイルへ `kind: item` の行として、終わり方を問わず追記する

項目の行は配分の履歴（`<metrics>/<owner>--<repo>/cross-refactoring-allocation.jsonl`）へ追記する。最終ゲートを通った実行だけでなく、安全網・打ち消しの衝突・中断で止まった実行でも、採った項目ごとに 1 行書く（受け入れ条件 14・18）。実行の行（`kind: run`）は今どおり最終ゲートを通った実行だけが書く。配分テーブルの集計は実行の行だけを読み、項目の行を読まない。項目の行から見積りを作るのは #2022 の範囲である。

別のファイルに置く形は採らない。配分テーブルを読む部品が同じ置き場と同じ根（`NDF_METRICS_DIR` など）を使えば、#2022 と #2205 が置き場を探さずに読める。

根拠: Value 4 / Value 8（MVV 版 6）

### 決定 11: 予算に縛られない上限を 1 つの式に揃えるため、テストと CI の待ちの上限は共通ライブラリの予算なしの式を使う

`init` は共通ライブラリ `lib/test_strategy.py` の `limits` を `budget_minutes=None` で呼ぶ。上限は supervise と同じ表になる。

| 対象 | 上限 |
| --- | --- |
| テスト | `3·max(w, m)` |
| CI | `3·c` |
| 所要が無いとき | `UNKNOWN_DURATION_LIMITS` |

cross-refactoring 専用の係数（`INIT_TEST_SHARE`・`TEST_FLOOR_SHARE`・`CI_WAIT_SHARE`）は使われなくなる。予算の割合から下限を出す形は採らない。予算は選定にだけ使う（原則 1）。cross-refactoring だけが使う係数と、範囲テストの所要 s を着手前の上限に入れる分岐は、実装で消す。

根拠: Value 6 / Value 7（MVV 版 6）

### 決定 12: JUnit を読めないときも修正担当が失敗を再現できるよう、落ちたテストの材料をログから組む

落ちたテストの材料は、ID・ログの置き場・走らせ直すコマンドの 3 つで、`failure_material.build` が組む。ID は JUnit XML（手元の suite の `junit`、CI の成果物）から読む。読めなければ、手元のログか CI の失敗したジョブのログ（`gh run view --log-failed`）の要約の行（`FAILED` / `ERROR` の後のノード ID）から取る。走らせ直すコマンドは、ID が取れれば範囲テストのテンプレートに ID のファイルを入れたもの、取れなければ全体テストのコマンドである。材料は修正・最終ゲート修正・判定の担い手のプロンプトへ渡る。ID がどちらからも取れないときは、落ちたテストの集合を `{"<whole>"}` の 1 要素として前進の判定に使う。

JUnit の読み取りを LIB1 へ置き換える形は採らない。今の読み取り（`lib/test_triage.py`）は動いており、足りないのは JUnit が無いときの材料で、LIB1 は賄わない。

- 作り方: 自前で作る
- 比べた候補: LIB1

根拠: Value 7（MVV 版 6）

### 決定 13: 意味の変わった状態を旧い記録と混ぜないため、状態ファイルの版を 3 へ上げ、版 2 の実行の再開は今どおり止める

`budget` と `safety_net` の形、項目の `feasibility[]`・`fix_history[]` が加わり、締め切りの鍵が無くなる。版 2 の状態ファイルを版 3 へ読み替える移行は持たない。版 2 の実行は予算から締め切りを導いた前提で途中まで進んでおり、読み替えると締め切りの無い経路へ途中から入る。版 2 の状態ファイルは今の「旧い状態ファイル」の扱い（終了コード 1 で止まり、打ち直しは最初から）で止める。

根拠: Value 1（MVV 版 6）
