# #1323: リポジトリに formatter と静的解析（ruff・型検査・shellcheck）を入れ、CI で守る

正は課題の本文（#1323）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

**この節は「何を満たすか」だけを扱う。** どう作るか（規則の範囲・型検査の選択・CI の形）は設計が決める。
マイルストーンは「17 トークン消費の削減」。版は配布の工程が決める（`release`）。

## 例: 変えた後に、手元と CI で同じ検査が走る

今（ndf 10.17.32）:

1. `plugins/ndf/scripts/lib/` の Python を直して Pull Request を出す。整形・未使用の import・未定義名を見る仕組みが無い
2. 例えば `plugins/ndf/skills/cross-refactoring/tests/crossref_helpers.py:172` の戻り値の注釈は、
   関数の中でしか import していない `subprocess` を指している（ruff の F821）。テストでは落ちないので、誰も気づかない

変えた後:

1. 手元で 1 つのコマンドを打つと、CI と同じ版・同じ設定の formatter と静的解析が走り、F821 のような指摘が出る
2. 直さずに Pull Request を出すと、CI の検査が落ちる
3. 一括で整形し直したコミットは `.git-blame-ignore-revs` に載っており、`git blame` はその前の変更を指す

> - 整形し直したコミットが `git blame` の邪魔をしない

## 目的

- **機械で見つけられる誤りを、レビューと LLM の手に回さない。** 未定義名・未使用の import・危ない書き方（shell の引用の抜けなど）を、書いた時点と CI で決定論的に見つける（ミッションの Value 1）
- **整形の差分をレビューから消す。** 書き手ごとの整形の揺れが差分に混ざらないようにする
- **整形し直しても履歴をたどれるようにする。** 一括の整形が `git blame` の行の作者を上書きしない状態にする

## 解釈

| 依頼文の語 | 具体化 |
| --- | --- |
| formatter | Python は ruff の `format`。sh の整形は入れない（前提 5） |
| 静的解析 | Python は ruff の `check`（規則の範囲は設計が決める）。sh は shellcheck（掛けるか・どの重さからかは設計が決める）。型検査は設計が入れるかを決める |
| CI で守り | Pull Request の宛先にかかわらず、検査の結果を返すワークフローがあり、違反があれば失敗する |
| 手元でも同じ設定で | 手元のコマンドと CI が、同じファイルの設定と同じ版のツールを読む。版は 1 か所で固定する |
| コードをクリーニングする | 一括の整形と、選んだ規則の違反をなくす修正（自動の修正と手の修正）を入れる |

## 前提

- 前提 1: 対象は git が追跡する Python と sh である（`git ls-files` で決まる）。追跡していないファイル・仮想環境・生成物は対象にしない
- 前提 2: 対象はリポジトリ全体の追跡しているファイルである（`plugins/`・`scripts/` に加えて根の `conftest.py`・`tests/`・`docs/presentations/build.sh`）。置き場ごとに外すかは設計が決め、外すなら理由を設定のファイルに残す
- 前提 3: 設定はこのリポジトリ（ai-plugins）の開発のためのものである。NDF が利用者のプロジェクトへ配る Skill・hook・スクリプトの振る舞い（#1319 の指標の測定を含む）は変えない。#1319 は Ruff を `--isolated` で起動するので、リポジトリに置く設定の影響を受けない
- 前提 4: ツールの版は、手元と CI が同じものを読む 1 か所（`uv.lock` か、コマンドに書いた版）で固定する。版を上げるのは、その 1 か所を変える Pull Request だけで行う（根の `pyproject.toml` の方針に揃える）
- 前提 5: sh の整形（shfmt など）は入れない。依頼は formatter と静的解析であり、課題は sh について shellcheck だけを挙げている
- 前提 6: 一括の整形と違反の修正は、配布物の振る舞いを変えない。全体テスト（`uv run --frozen --project . --all-extras pytest . -q -n auto`）と `claude plugin validate .` が、整形の前後で同じ結果になる
- 前提 7: 一括の整形は、その時点で開いている Pull Request と作業中のブランチが無いことを確かめてから入れる（依頼の原文）。開いている Pull Request があれば、整形はそのマージを待つ
- 前提 8: リリースの時期は依頼の原文のとおり、#1319 の配布（済み）の後、`issues/check-backlog-milestone26.md` の未検査分の cross-review の前である。版は配布の工程が決める

## 対象範囲

含む:

- ruff の設定（整形と規則）をリポジトリへ置くこと
- shellcheck を sh に掛けるかの決定と、掛けるならその設定
- 型検査を入れるかの決定と、入れるならその設定
- 手元で検査を 1 つのコマンドで走らせる手段と、ツールの版の固定
- CI のワークフロー（検査の実行と失敗の返し方）
- 一括の整形と、選んだ規則の違反の修正
- `.git-blame-ignore-revs` と、その使い方の案内（`git config blame.ignoreRevsFile` の設定を含む）
- 開発の手順の文書（`CONTRIBUTING.md` か `docs/plugin-development-guide.md`）への検査の手順の記載

含まない:

- NDF の Skill・hook が利用者のプロジェクトで formatter や静的解析を走らせる仕組み（ミッションの Value 6。やるなら別の課題）
- #1319 の指標の測定の変更
- sh の整形（前提 5）
- Python と sh 以外（Markdown・YAML・JSON・JavaScript）の整形と静的解析
- 規則の違反を直すためのリファクタリング（違反を消す最小の修正か、理由を書いた抑止に限る）
- ruleset の必須のチェックへの追加（リポジトリ設定の変更。確認してから行う）

| E1 | 検査の設定と版の固定を置いた | 設計の Pull Request のマージ後の実装 | 手元と CI で版が違えば、同じファイルに違う結果が出る → AC2 で防ぐ | — |

| E3 | 開いている Pull Request が無いことを確かめた | 一括の整形の直前 | 開いているものがある → 整形を待つ（前提 7） | E1 |
| E4 | 一括で整形し直し、違反を直した | E3 の確認 | テストか validate が変わる → 整形を入れない（前提 6・AC6） | E3 |
| E5 | 整形のコミットを `.git-blame-ignore-revs` に載せた | E4 のコミットが確定した | ハッシュが変わる（rebase・squash）→ マージ後のハッシュで載せ直す（AC8） | E4。マージの方式でハッシュが変わるので、載せるのはマージ後のハッシュである |
| E6 | CI が検査を走らせ、違反で落とした | Pull Request の作成と更新 | 検査の仕組みそのものが落ちる → 失敗として返す（成功に倒さない。AC4） | E1。E4 より前に CI で全体を落とすと、既存の違反で全 Pull Request が落ちる → 全体を落とすのは E4 の後（AC5） |
| E7 | 進行中のブランチが整形の後の develop を取り込んだ | 整形の後に作業を再開した | 衝突 → 手順の文書に解き方を書く（AC9） | E4 |
| E8 | 配布した | ミッションのリリース | — | E4〜E6。`check-backlog-milestone26.md` の cross-review より前（前提 8） |

## 用語

| 用語 | 意味 |
| --- | --- |
| 一括の整形 | リポジトリの全対象へ formatter を掛け、結果を 1 つのコミットにしたもの。`.git-blame-ignore-revs` に載せる単位 |
| 検査のコマンド | 手元で formatter の確認・静的解析を CI と同じ版・同じ設定で走らせる 1 つのコマンド |

## 受け入れ条件

- [ ] AC1: formatter（ruff の `format`）と静的解析（ruff の `check`）の設定がリポジトリの設定ファイルにある。設計が採ると決めたなら shellcheck と型検査の設定もある
- [ ] AC2: 検査に使うツールの版は 1 か所で固定され、手元の検査のコマンドと CI が同じ所を読む。版を変えずに同じコミットで走らせると、手元と CI の結果（違反の件数と対象のファイル）が一致する
- [ ] AC3: 手元でリポジトリの根から 1 つのコマンドを打つと、CI と同じ検査のすべてが走る。違反が無ければ終了コード 0、あれば 0 以外で終わり、違反のファイルと行を出す。ツールが無い・取得できないときも 0 以外で終わり、何が無いかを出す
- [ ] AC4: CI のワークフローが Pull Request で検査を走らせ、違反があれば失敗する。検査の仕組みが途中で落ちたときも失敗として返す。変更の種類にかかわらず結果を返す（`pytest.yml` と同じく、Pull Request では絞り込まずに起動する）
- [ ] AC5: 一括の整形と違反の修正が入った後の develop で、AC3 のコマンドが終了コード 0 で終わり、CI の検査が通る。一括の整形より前に、全体の違反で既存の Pull Request を落とす状態を作らない
- [ ] AC6: 一括の整形と違反の修正の前後で、全体テスト（`uv run --frozen --project . --all-extras pytest . -q -n auto`）の成否と `claude plugin validate .` の終了コードが変わらない。`bash scripts/build-runtime-plugins.sh --check` と `python3 scripts/check-script-structure.py` も通る
- [ ] AC7: 一括の整形のコミットは、整形のツールが出した変更だけを持つ（手の修正と設定の変更は別のコミットにする）
- [ ] AC8: 一括の整形のコミット（develop へ入った後のハッシュ）が `.git-blame-ignore-revs` に載っている。`git blame --ignore-revs-file .git-blame-ignore-revs <整形したファイル>` が、整形の行について整形より前のコミットを指す。GitHub の blame の画面は、このファイルを根に置けば自動で読む
- [ ] AC9: 開発の手順の文書に、検査のコマンド・`blame.ignoreRevsFile` の設定の仕方・整形の前から続くブランチの取り込み方が書いてある。書いたコマンドは書く前に実行して確かめてある
- [ ] AC10: 抑止（`# noqa`・`# shellcheck disable=`・設定の除外）を置いた箇所には、それぞれ理由がある（行の抑止は同じ行か直前の行、設定の除外は設定ファイルのコメント）
- [ ] AC11: NDF が配る Skill・hook・スクリプトの振る舞いが変わらない。#1319 の指標の測定の結果が、リポジトリに置いた設定の有無で変わらない（`--isolated` のまま）
- [ ] AC12: 一括の整形の直前に、開いている Pull Request が無いことを `gh pr list --state open` の出力で確かめ、その結果を課題か Pull Request に残してある

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | CI の検査のジョブは、既存の `pytest` のジョブより先に終わる（検査で Pull Request の待ちを延ばさない）。実測の秒を設計か Pull Request に残す |
| 運用・保守性 | ツールの版を上げるのは、版を固定した 1 か所を変える Pull Request だけで行う。上げたときに出る新しい違反は、同じ Pull Request で直すか抑止する |
| 移行性 | 一括の整形の後に、整形の前から続くブランチを取り込む手順がある（AC9） |
| システム環境 | 手元の検査のコマンドは、`uv` がある環境で追加の導入なしに走る。shellcheck を採るなら、無い環境でどう扱うかを設計が決める（CI では入れる） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない（NDF の配布物の振る舞いは変えない。AC11） |
| データ | 無し |

| 進行中のブランチ | 一括の整形の後に取り込むと衝突する（前提 7・AC9） |

| AC2・AC3 | 手元で検査のコマンドを打ち、終了コードと出力を見る。わざと違反を 1 つ入れた一時のブランチでも打つ |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | 設定は根の `pyproject.toml`（か根の設定ファイル）に置く。`plugins/ndf/pyproject.toml` は NDF が配るスクリプトの依存の宣言なので、開発の検査のツールを足さない（その判断は設計が確かめる） |
| コーディング規約 | `AGENTS.md`（最小限の実装・日本語のコメント）。検査の規則そのものがこの変更で規約になる |
| テスト戦略 | 新しい振る舞いは検査のコマンドと CI だけで、単体テストは足さない（設定の読み込みはツールが持つ）。退行は全体テストが見る（AC6） |

## 境界

