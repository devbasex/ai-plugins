## 何が起きたか

2026-11-22 の PR #4096 の cross-review の終わりに、指摘のスレッドを書く 9 件の POST が GitHub に断られ、PR の記録が欠けた（[記録のコメント](https://github.com/devbasex/ai-plugins/pull/4096#issuecomment-7077633494) の「注意」）。断られた応答は 2 つの形だった。表の JSON は応答の本文の `errors[]` の要素の抜粋で、本文の全体は `{"message":"Validation Failed","errors":[<この要素>],"documentation_url":…,"status":"422"}` の形（全文は記録のコメントにある）。

| 要求 | 応答 |
| --- | --- |
| `POST /pulls/4096/comments/{id}/replies` | 422 `{"resource":"PullRequestReview","code":"abuse","field":"base"}` |
| `POST /pulls/4096/comments`（8 件） | 422 `{"resource":"PullRequestReviewComment","code":"custom","message":"was submitted too quickly"}` |

同じ時間に、同じ GitHub アカウントで並列のレーン（並列の計画で 1 つの作業の流れを受け持つ claude のセッション）が PR・Issue・コメントを書いている。#4016（PR #4058 の設計。未実装）は NDF のコードを通る書き込みをマシン全体の順番に並べるが、エージェントが Bash で打つ `gh` の書き込みはその順番の外で送られる。

## 種類

機能追加（エージェントが NDF を通さずに打つ `gh` の書き込みに間隔を当てる約束は、今の SSOT にも #4016 の設計にも無い。#4016 の設計は「含まない」に置いた）

## 今の姿

| 書き込みの経路 | 例 | 間隔 | 二次レート制限の後の待ち |
| --- | --- | --- | --- |
| NDF のコード（githubkit の `Client`） | cross-review のスレッド・起票・リリース | #4016 の実装の後は `WriteGate` がマシン全体の順番を取る（今は cross-review のスレッドだけプロセスの中で 1 秒） | #4016 の実装の後は待ちの終わりを順番の記録で共有する |
| エージェントが Bash で打つ `gh` | `gh pr create`・`gh pr comment`・`gh issue create`・`gh issue edit`・`gh api -X POST` | 無い | 無い。当たった直後も打ち直せる |

Claude Code は有効なプラグインの `bin/` を Bash の `PATH` の末尾に足す（NDF の `bin/ndf` はこの仕組みで見つかる）。NDF のリレー（NDF が tmux の中で claude を起動し、セッションの切り替えを受け持つ仕組み）が起動する claude では、リレーが起動先の NDF の `bin/` を `PATH` の先頭に置く（`domains/relay/session_env.py` の `with_launched_ndf`）。並列のレーンはリレーが起動する。

## 何を足すか・変えるか

| | 前 | 後 |
| --- | --- | --- |
| エージェントの `gh` の書き込み | 間を空けずに送る | 送る前に #4016 の書き込みの順番の記録で順番を取り、NDF の書き込みと同じ間隔を空ける |
| 二次レート制限の待ちの終わり | `gh` は知らずに送る | 待ちの終わりまで送らない |
| `gh` の書き込みが二次レート制限で断られたとき | 断られた本人だけが知る | 待ちの終わりを順番の記録へ書き、NDF とほかのエージェントの書き込みも待つ |
| `gh` の読み取り | そのまま | そのまま（待たない） |

## 今の利用者への影響と互換

- エージェントが打つ `gh` の書き込みが、ほかのレーンと NDF の書き込みの分だけ待つ。どの書き込みも前の書き込みから #4016 の `github.write-spacing`（1 秒）を空ける。内容を作る書き込み（PR・Issue・コメントの作成）は、NDF の書き込みと合わせて #4016 の `github.content-window.minute`（1 分 80 件）・`github.content-window.hour`（1 時間 500 件）のウィンドウで数え、どちらかが上限に達しているときだけウィンドウが空くまで待つ
- `gh` の引数・標準入力・標準出力・標準エラー・終了コードは変わらない。待つ間だけ、標準エラーへ待ちの 1 行が出る。ただし待ちが上限（設計で決める）を越えるときは、送らずに終了コード 1 と理由の 1 行で終わる（受け入れ条件 2）
- 利用者が端末で手で打つ `gh` と、リレーを通らない claude の `gh` は変わらない（下の「対象範囲」）

## なぜ困るか

二次レート制限に当たると、同じアカウントで動くすべてのレーンが PR・Issue・コメントを書けなくなる。ブロックが続く長さは公開されておらず、打ち続けると BAN されうる。NDF の書き込みだけを並べても、エージェントの `gh` が並びの外で打てば合計は抑えられず、当たった後の待ちも破られる。

## 目的

- エージェントが打つ `gh` の書き込みも、NDF の書き込みと同じマシン全体の順番に並べる
- 二次レート制限に当たった後は、どの経路の書き込みも待ちの終わりまで送らない
- 誰に効くか: 同じ GitHub アカウントで並列に動くすべてのレーンと、オーガナイザーの起票

## 対象範囲

含む:
- NDF のリレーが起動したセッションのエージェント（その claude の Bash・サブエージェントと、そのセッションが起動する子のプロセス（`codex exec` など））が打つ `gh` の書き込み（PR・Issue・コメント・レビューの作成、本文・ラベルの書き換え、マージ、`gh api` の POST・PATCH・PUT・DELETE と GraphQL の mutation）に、#4016 の書き込みの順番の記録で間隔を当てる
- `gh` の書き込みが二次レート制限で断られたら、待ちの終わりを順番の記録へ書く
- 二次レート制限の見分けに、422 の `was submitted too quickly` と `code: abuse` を含める（#4016 の見分けにも同じ規則を当てる）

含まない:
- NDF のコードを通る書き込みの順番の取り方そのもの（#4016 が扱う）
- 利用者が端末で手で打つ `gh` と、NDF のリレーを通らずに起動した claude・Codex（Claude Code はプラグインの `bin/` を `PATH` の末尾に足すので、`/usr/bin/gh` が先に引かれる）
- CI のジョブが打つ `gh`（別のマシンで、`GITHUB_TOKEN` の別の主体で書く。#4016 の前提 2 の「マシン全体」の外）
- 読み取りの削減

## 前提

- 前提 1: 二次レート制限の上限と待ち方は #4016 の要求の前提 1 のとおりとする（内容を作るリクエストはおおむね 1 分 80 件・1 時間 500 件、書き込みは順に送り間を 1 秒以上空ける）
- 前提 2: 「マシン全体」は #4016 の前提 2 のとおり、同じ OS のユーザーで動くプロセスすべてを指す
- 前提 3: #4016 の `WriteGate` と書き込みの順番の記録は、この課題より先か同じ PR で実装される。この課題はその記録を共有し、別の記録を持たない

## 受け入れ条件

- [ ] 1. NDF のリレーが起動したセッションのエージェントが続けて打つ 2 つの `gh` の書き込みの送る時刻の差が `github.write-spacing` の秒以上になる。内容を作る `gh` の書き込みは、1 回の `gh` が送る件数（設計の決定 7）を NDF のコードの書き込みと同じ時刻の一覧に数え、`github.content-window.minute`・`github.content-window.hour` のどちらかの上限を越える時刻には送られない。ただし件数がウィンドウの上限そのものを越える `gh`（81 個以上のラベルを作る `gh label clone` など。決定 7 の代償）は、そのウィンドウが空になるまで送られず、空になった時刻に 1 回でまとめて送られる。`gh` の書き込みと NDF のコードの書き込みが続いても同じ（テスト）
- [ ] 2. 書き込みの順番の記録の待ちの終わりより前に、エージェントの `gh` の書き込みが送られない（テスト）
- [ ] 3. エージェントの `gh` の書き込みが二次レート制限（403・429 の `secondary rate limit`、422 の `was submitted too quickly`・`code: abuse`）で断られると、待ちの終わりが順番の記録へ書かれる。`gh` の終了コードと出力はそのまま返る。端末につながる出力だけに出た断りは見分けの対象に含めない（Claude Code の Bash は端末を割り当てないので、エージェントの `gh` は対象になる）。`gh api -i --silent` の 422 の `abuse` は対象に含め、`--paginate` を併用したもの・口の出力が 128 KiB を越えて本文が欠けたものの本文だけにある 422 の `abuse` は含めない（テスト）
- [ ] 4. `gh` の読み取りは順番を取らず、待たない。引数・標準入力・標準出力・標準エラー・終了コードは `gh` を直に打ったときと同じ（テスト）
- [ ] 5. 順番の記録を読めない・ロックを取れないときも、`gh` は送られ、標準エラーへ 1 行が出る（テスト）
- [ ] 6. NDF のリレーが起動したレーンの Bash とそのサブエージェントで `gh` を引くと、順番を取る入口に当たる（手動確認。リリースの後の最初の並列の計画で 1 回確かめる）
