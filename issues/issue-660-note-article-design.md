## 決定の記録

### 決定 1: 記事の正本を `docs/articles/` に置く

note の記事は後から直すことがあり、正本がリポジトリにあれば Pull Request で差分を追える。`docs/presentations/` と同じく「公開日時点の記録で、以後の構成変更には追随しない」と README に書く。

`docs/presentations/` へ同居させる案は採らない。そちらはスライドとビルド手順の置き場所で、ビルドの対象に記事が混ざる。

### 決定 2: cross-review と ai-plugins の説明は既出記事へのリンクで済ませる

依頼文が「触れていたらリンクを張ってざっくり紹介だけ」と定めており、既出記事（出典 8）が両方を紹介している。記事の主題を工程の並びに集中させる。

### 決定 3: 5 モードは表で 1 行ずつ示し、詳しく書くのは standard と documentation の 2 つだけにする

依頼文の主題が standard と documentation であり、残りの 3 モードまで説明すると分量が受け入れ条件 8 を超える。モードが 5 つあることだけは示さないと、「全部の変更にフル工程を課す」と誤読される。

### 決定 4: 工程の流れは Mermaid ではなくコードブロックの矢印で書く

note は Mermaid を描画しない。画像にすると正本の Markdown と図が別物になり、直すときに片方だけが古くなる。

### 決定 5: 記事自体が documentation モードで書かれたことを節 4 に書く

documentation モードの説明が抽象になりやすく、実例として最も手元にあるのがこの記事である。読み手が「本当に使っているのか」を問う前に答えられる。

### 決定 6: `## 出典` の節を記事の末尾に置く

`document-sources` の規約（出典は生成物に載る場所に置く）に従う。大浜の既出記事にも末尾のリンクの節があり、読み手の違和感は小さい。
