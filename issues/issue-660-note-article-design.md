## 決定の記録

### 決定 1: 記事の正本を `docs/articles/` に置く

記事は後から直すことがあり、正本がリポジトリにあれば Pull Request で差分を追える。`docs/presentations/` と同じく「書いた日時点の記録で、以後の構成変更には追随しない」と README に書く。

`docs/presentations/` へ同居させる案は採らない。そちらはスライドとビルド手順の置き場所で、ビルドの対象に記事が混ざる。

### 決定 2: cross-review と ai-plugins の説明は前回の記事へのリンクで済ませる

依頼文が「触れていたらリンクを張ってざっくり紹介だけ」と定めており、前回の記事（素材 7）が両方を紹介している。

### 決定 3: 5 モードは表で 1 行ずつ示し、詳しく書くのは standard と documentation の 2 つだけにする

依頼文の主題が standard と documentation である。モードが 5 つあることだけは示さないと、「全部の変更にフル工程を課す」と誤読される。

### 決定 4: 工程の流れは Mermaid ではなくコードブロックの矢印で書く

note は Mermaid を描画しない。画像にすると正本の Markdown と図が別物になり、直すときに片方だけが古くなる。

### 決定 5: 記事自体が documentation モードで書かれたことを節 4 に書く

documentation モードの説明は抽象になりやすく、手元にある一番の実例がこの記事である。企画承認で差し戻された経緯も、節 6-2 の主張の裏付けになる。

### 決定 6: 記事に出典の節を置かない

利用者の指示であり、ライトな読み物に出典の表は合わない。`document-sources` の規約（出典は生成物に載る場所に置く）から外れる代わりに、数値は設計文書の「素材」の表に残し、同じ値へ戻れるようにする。

### 決定 7: 下書きは Notion の子ページとして作り、note への投稿は筆者が行う

利用者が提出先として Notion の親ページを指定した。親ページには筆者の過去の記事の下書きが並んでおり、同じ置き方に揃う。Notion の子ページは公開前の下書きであり、本番の提出（note への公開）には当たらないため、子ページの作成は制作物承認の関門に数えない。
