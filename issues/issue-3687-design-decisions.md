# #3687 の決定の記録: 設定を 1 か所にそろえ、検査と毎日のジョブで食い違いと量を止める

設計文書 [issue-3687-design.md](./issue-3687-design.md) から分けた決定である（1 ファイル 500 行の上限を超えたため）。
外部の調査の番号（`STD<数>`・`PRD<数>`・`LIB<数>`）は設計文書の末尾の「外部の調査」にある。

## 決定の記録

### 決定 1: 1 項目を変える Pull Request が衝突しないよう、設定に書いた表を 1 項目 1 ファイルへ分ける

- **質問**: 223 項目を 1 ファイルに持つ表を、並行で書き足しても衝突しない形にどう変えるか
- **選んだ案**: 分ける表の一覧（`contracts/domains/split-tables.json`）に挙げた表を、同じ名前のディレクトリへ移して 1 項目 1 ファイルにする。ファイル名が項目のキーになり、表そのものの値（`owner`）は `_meta.json` に置く。最初の対象は `limits`（223 項目）と `causes`（35 項目）
- 採らなかった案: 区分（キーの先頭の語）ごとに 20〜30 ファイルへ分ける（同じ区分の別の項目を触る Pull Request どうしは衝突が残る。受け入れ条件 2 の「1 項目を変えた差分が 1 ファイルに収まる」を満たさない）
- 採らなかった案: 1 ファイルのまま、項目を 1 行 1 項目の追記だけの形（JSON Lines）にする（差分は 1 行に収まるが、同じファイルの別の行を同時に足すと衝突する。towncrier が避けた形そのものである）
- 採らなかった案: 177 ファイルすべてを分ける（1 項目 1 ファイルのファイルが 600 を超える。並行で書き足す表に限れば足りる）
- **代償**: ファイルの数が 258 増える。1 つの表を通して読むには、ディレクトリの一覧を開くことになる
- 作り方: 自前で作る・主要な製品に倣う
- 比べた候補: PRD5 / PRD6
- 根拠: Value 5（MVV バージョン 1）。towncrier は 1 ファイルの同時編集が衝突を生むことを理由に断片の方式を採り（PRD6）、changesets は 1 変更 1 ファイルを置いて適用後に消す（PRD5）。どちらも「並行で書き足すものは項目ごとのファイルにする」形である

### 決定 2: 呼び出しを増やさずに本物と突き合わせるため、公開の記述を持つ相手はその記述と当てる

- **質問**: 見本を「本物」と当てるとき、相手の API を実際に呼ぶか、相手が公開している記述と当てるか
- **選んだ案**: 見本の定義に `source` を持たせる。本番がリクエストの検証に使う記述を公開している相手（GitHub の REST）はその記述（OpenAPI 3.1 の bundled 形式）と当てる。記述の無い相手（ランタイムの CLI）は、既にある毎日のジョブの `cli-help` がコマンドを打って `--help` と当てる仕事を持ち続け、`ndf samples verify` は同じ `--help` を打たない
- 採らなかった案: すべて実際の API の呼び出しで当てる（認証が要り、相手ごとの呼び出しの上限を毎日使い、固定のデータ（課題 1 件など）が消えると落ちる）
- 採らなかった案: すべて公開の記述と当てる（ランタイムの CLI は記述を公開していない。既にある `--help` の突き合わせも捨てることになる）
- **代償**: 本物と当てる仕組みが `ndf samples verify`（記述）と `cli-help`（コマンド）の 2 つに分かれたまま残る。同じ `--help` を両方で打つと毎日の CLI の起動がランタイムごとに 1 回増えるため、寄せるのは `cli-help` を作り直す別の課題で行う
- 作り方: 自前で作る・ライブラリやサービスを使う
- 比べた候補: STD1 / PRD1 / PRD2 / PRD3 / LIB1 / LIB2 / LIB4
- 根拠: Value 2（MVV バージョン 1）。GitHub の REST の記述は「本番が API のリクエストの検証に使う記述と自動で同期する」と公式が書く（PRD3）ため、呼び出しを使わずに本物と当てられる。コントラクトテストの標準（STD1）と Pact Broker（PRD1）は provider 側が検証を送り返す前提で、相手が GitHub では成り立たない。記録と再生のライブラリ（LIB1・LIB2）は録り直しの手段であって、食い違いを見つけて落とす仕組みを持たない

### 決定 3: 利用先のリポジトリへ ai-plugins の値を持ち込まないよう、設定を配るものと配らないものに分ける

- **質問**: Python と uv のバージョン・量の上限を、配るコントラクトとリポジトリの設定のどちらに置くか
- **選んだ案**: NDF 自身が動く条件は、Python の下限・hook の下限・uv のバージョンと照合値である。これらは配るコントラクト（`contracts/data/toolchain.json`）に置く。そのリポジトリの CI が回す Python のバージョン・見るワークフロー・量の上限はリポジトリの設定（`.ndf/project.json` の `toolchain`・`budget`）に置く。設定のキーが無い項目は検査が数えない
- 採らなかった案: すべて配るコントラクトに置く（利用先のリポジトリの CI が ai-plugins の値（テスト 4,400 件など）で落ちる）
- 採らなかった案: すべてリポジトリの設定に置く（NDF が動く Python の下限は配るコードの条件で、利用先が書き換えてよい値ではない）
- 採らなかった案: `.ndf/toolchain.json` を新しく作る（設定ファイルが 1 つ増える。既にある `.ndf/project.json` に `test`・`checks` と並ぶキーとして足せる）
- **代償**: 設定が 2 か所に分かれ、どちらに書くかを足すたびに決めることになる
- 根拠: Value 4（MVV バージョン 1）

### 決定 4: 例外の設定を二重に持たないよう、使われない依存を `ndf check` の中で数える

- **質問**: 定義に挙げて使っていない依存を、既存のツール（deptry）で検出するか、`ndf check` の規則として数えるか
- **選んだ案**: `ndf check` の規則 `budget` の中で数える。構文木は既存の仕組み（`checks/model.py` の `Source`）が 1 ファイル 1 回だけ作ったものを使う。数える対象は `toolchain.plugin_pyprojects` の各 `pyproject.toml` の直接の実行時の依存（開発用と推移的な依存は数えない）で、関数の中の import も構文木で拾う。import に現れない使い方（子プロセスとして起動する `ruff` など）の例外は、依存の名前 → 理由の表としてリポジトリの設定（`.ndf/project.json` の `budget.dep_exempt`）に 1 か所だけ持つ。依存の名前と import の名前が違うもの（`python-dotenv` → `dotenv`）は `budget.dep_modules` に持つ
- 採らなかった案: deptry を dev の依存に足し、ルール DEP002 の結果を読んで上限と比べる（別プロセス・別の設定ファイルになる。例外の設定が deptry 側と NDF 側の二重になる。最後のリリースから約 8 か月で、リポジトリの所有も移っている）
- **代償**: 使われない依存の判定を自分で持つ。deptry が後から足す判定（推移的な依存・開発用の混入）は自動では入らない
- 作り方: 自前で作る
- 比べた候補: LIB5 / STD5
- 根拠: Value 3（MVV バージョン 1）。使っていない依存の検出を定める標準は無く（STD5）、事実上の標準はツール側の実装である

### 決定 5: 依存を取れない場合も結果 JSON を返すため、`exec` の前に同期を 1 回挟む

- **質問**: uv はあるが依存を取れないときに、結果 JSON と `deps_missing`（69）をどう返すか
- **選んだ案**: `plugins/ndf/bin/ndf` が `exec uv run` の前に `uv sync --frozen --no-dev --inexact` を 1 回打つ。`--inexact` は、今の `uv run` と同じに lock に無い追加のパッケージを消さないために付ける（`uv sync` の既定は消す）。失敗したら既にある `stop_deps_missing` を通す。成功したら `exec uv run --no-sync` で渡す（同期済みの同じ環境を使い、`exec` の後に uv が同期し直さない）。呼び出し元が `UV_NO_SYNC` を真（uv と同じに 1・true・yes・y・on・t を大文字小文字を問わず）にしていれば、同期を飛ばしてそのまま `exec uv run --no-sync` へ進む（今の `uv run` と同じに環境を書き換えない。`uv sync` はこの変数を受けないのでランチャーが分ける）
- 採らなかった案: `exec` をやめて `uv run` の終了コードを見る（シグナルの伝わり方が変わり、Ctrl-C と `SIGTERM` が中の処理へ届かなくなる）
- 採らなかった案: venv が無いときだけ同期する（venv があっても lock と食い違えば `uv run --frozen` が取りに行き、同じ失敗が `exec` の後に起きる）
- 採らなかった案: 同期の後も `uv run --frozen` のまま渡す（`uv run` が環境を同期し直すため同期の経路を 1 起動に 2 回通り、後続の処理で依存の用意に失敗すると結果 JSON が出ない）
- **代償**: 起動のたびに同期が 1 回増える。同期済みなら 1 回 15 ミリ秒である（2026-11-23 の実測。`uv sync --frozen --no-dev --quiet --project plugins/ndf` を 3 回で 45 ミリ秒）。`uv run` 自体の 1 回 32 ミリ秒に対して 5 割弱の上乗せになる
- 根拠: Value 1（MVV バージョン 1）

### 決定 6: 保存先の表を増やさないよう、実験版の行を既にある保存先の表へ足す

- **質問**: 実験版の保存先と呼び方の設定を、新しい表に置くか既にある表に置くか
- **選んだ案**: 既にある保存先の表（`contracts/domains/locations.json`、23 行）へ `experimental/ndf/`（リポジトリの根。配布元の `plugins/ndf/` の外）の行を足す。呼び方は `python3 experimental/ndf/<名前>.py` で、`bin/` にエントリポイントを置かない（配る対象に入れないため）
- 採らなかった案: `plugins/ndf/experimental/` に置き、配布の経路で除外する（Claude Code も Codex も `plugins/ndf/` を丸ごと配るため、両ランタイムの配布経路に除外の仕組みと確かめを足すことになり、漏れれば正式版の利用者へ実験版が届く）
- 採らなかった案: 実験版だけの表を新しく作る（保存先の定義が 2 か所に分かれ、保存先を探す側がどちらを読むかを決めることになる）
- 採らなかった案: `bin/ndf-exp` のエントリポイントを置く（配る構成（`manifests/`）に入り、既定で動くものから実験版への参照ができてしまう）
- **代償**: 実験版だけが持つ欄（台帳の「行き先」など）は保存先の表に入らず、台帳（`docs/`）の側に残る
- 根拠: Value 6（MVV バージョン 1）

### 決定 7: 1 日のジョブを増やさないよう、毎日の検証を既にあるワークフローのジョブとして足す

- **質問**: 毎日の見本の検証を、新しいワークフローに置くか既にある毎日のワークフローに足すか
- **選んだ案**: 既にある `.github/workflows/runtime-plugin-smoke-latest.yml`（毎日 06:00 JST）へ、毎日走るジョブを 1 件足す。足すジョブは matrix を持たない `live-samples` である。権限を分けるため、課題を作るジョブ `report` も足すが、前のジョブが失敗した日だけ起動する。同じ Pull Request で、このワークフローが見るブランチの既定を `develop` から `main` へ替える
- 採らなかった案: 新しいワークフローを作る（ワークフローが 1 本増え、起動の時刻と落ちたときの課題の作り方を二重に持つ）
- 採らなかった案: 既にあるランタイムごとの matrix のジョブへ相乗りする（GitHub の見本はランタイムに依らないため、同じ検証が 2 回走る）
- 権限の境界: ワークフロー全体の権限を `contents: read` だけにし、`issues: write` は課題を作るジョブ `report` だけが持つ。`live-samples` のジョブは `contents: read` だけを持ち、入力の `ref` を使わず `main` を取り出して検証する。今のランタイムごとの matrix のジョブも、入力の `ref` のコード（`resolve` とスモーク）を動かすので書き込みの権限を持たせず、その課題の報告を `report` へ移す。`report` は `main` の `scripts/runtime-smoke-latest.py report` で成果物の JSON だけを読む（既存の `cli-help` の手順が検証器を `main` に固定しているのと同じ考え方。手動の実行で別の ref を渡した人が、書き込みの権限で定義のコードを動かせないようにする）
- 失敗の日の流れ: `ndf samples verify` は食い違いで必ず 1 を返すので、`live-samples` はその日に失敗で終わる。GitHub Actions は `needs` の先が失敗すると既定で後のジョブを飛ばすため、次の 3 つを定める。(1) 結果 JSON を成果物として上げる手順は `if: always()` で動かす。(2) `report` は `if: ${{ !cancelled() && contains(needs.*.result, 'failure') && (github.event_name == 'schedule' || ((inputs.ref || 'main') == 'main' && (inputs.floors_ref || 'main') == 'main')) }}` で動かし、成果物が無い場合（検証の前の失敗）はその分の報告をせずに終える。任意の `ref` か `floors_ref` を試した手の起動では、matrix のジョブがその `ref` のコードで成果物を書けるため `report` を起動せず、課題へ書かない（`main` の実行でも、成果物のランタイム名・バージョンの一覧は `main` のスクリプトの定数とバージョンの形と突き合わせたものだけをコピーする）。(3) `live-samples` が失敗で終わっても、成果物の結果 JSON の `kind: mismatch` から相手ごとに課題を作る
- 毎日のジョブの数: 毎日走るジョブは `live-samples` の 1 件だけ増える。`report` は前のジョブのどれかが失敗した日だけ起動し、すべて成功の日は起動しない（飛ばされたジョブはランナーを使わない）。失敗の日は 1 実行あたり 2 件増えるが、今まで matrix の各ジョブの中で打っていた報告の手順はそこから消える
- **代償**: ランタイムのスモークが落ちると、見本の検証も同じワークフローの実行の中で結果が読みにくくなる
- 根拠: Value 2（MVV バージョン 1）

### 決定 8: 見本がテストで使われる形を示すため、見本を読むテストダブルを 1 つ作る

- **質問**: 見本を本物と突き合わせるだけでは、テストが使う偽の相手が見本と無関係のまま残る。どこまでを この変更に含めるか
- **選んだ案**: GitHub の見本を読むテストダブルを 1 つ作り、そのテストダブルを使うテストを 1 本置く。既存の 10 か所の `FakeHub` をそこへ寄せ替えるのは別の課題にする
- 採らなかった案: 10 か所すべてを同じ Pull Request で寄せ替える（`FakeHub` は保存先ごとに応答の組み立て方が違い、寄せ替えだけで 1 単位の上限（1,000 行）を超える。この変更の受け入れ条件にも無い）
- 採らなかった案: テストダブルを変えずに見本だけを置く（見本がテストで一度も使われず、「テストダブルはこの見本だけから応答を組み立てる」という見本の定義が成り立たない。本物と当てても、テストの偽の相手が食い違ったままになる）
- **代償**: 10 か所の `FakeHub` は当面そのまま残り、そこが本物と食い違っても毎日のジョブは気づかない
- 根拠: Value 3（MVV バージョン 1）

### 決定 9: 落ちたときに Pull Request が止まるよう、足す 4 規則は既にある必須チェックの中で走らせる

- **質問**: 足す 4 規則と毎日のジョブを、`main` の必須チェックへ足すか（要求仕様が設計へ送った未決）
- **選んだ案**: 4 規則は既にある必須チェック `script-structure-check`（`ndf check` を打つジョブ）の中で走らせる。必須チェックの数は 15 件のまま増やさない。毎日のジョブ（`live-samples`）は Pull Request では走らないため、必須チェックに足さない
- 採らなかった案: 規則ごとに CI のジョブを足して必須チェックにする（ジョブが 4 件増え、`budget.ci_jobs` の上限に自分で当たる）
- 採らなかった案: 毎日のジョブを必須チェックに足す（Pull Request の時点では走らないチェックを必須にすると、どの Pull Request も待ち続ける）
- **代償**: 4 規則の違反は `script-structure-check` の失敗としてまとまって出るため、どの規則が落ちたかは結果 JSON の `items` を開いて読むことになる
- 根拠: Value 2（MVV バージョン 1）
