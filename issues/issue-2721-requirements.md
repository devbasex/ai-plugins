## 目的

- 設計承認ゲートで承認する人が、判断に要る資料（図・表・選定の理由・動作する画面モック）を、自分で文書を探さずに開ける状態にする
- 設計の段階で作るべき資料と承認の段階で見るべき資料を、1 つの一覧で過不足なく定め、どの資料が欠けているかを機械で見つけられるようにする

## 今の定義（2026-11-07 に確かめた）

| 項目 | 設計で書く定義 | 承認の提示の定義 |
| --- | --- | --- |
| 要求・受け入れ条件 | `requirements-design` | 「満たすこと」（件数だけ） |
| ドメインモデル・ドメインイベント | `design/references/domain-model.md`（`standard` は必須） | 「用語」だけ |
| ER 図 | `design/references/data-structure.md`・`deliverables.md`（該当時） | 無し |
| 画面 | `design/references/interface-ui.md`（該当時）。動作する画面モックの定義は無い | 無し |
| 技術の選定 | `design/references/external-survey.md`（標準・製品・ライブラリとサービス） | 無し |
| 非機能 | `design/references/nonfunctional.md`（該当時） | 無し |

確かめた手段（2026-11-08）:

- `grep -rn "モック" plugins/ndf/skills/design plugins/ndf/skills/development-workflow` → 0 件
- `grep -n "モック\|mock" plugins/ndf/skills/development-workflow/schemas/project.schema.json` → 0 件（プロジェクトの設定に画面モックの表現方法を書く欄が無い）
- Factory の承認待ちの一覧（起票時の観測。画面のコードは volareinc/nd-factory の `factory/web/src/pages/ApprovalsPage.tsx` にある）の列は、種類・ループ・ループの 1 回・リポジトリ・課題・待ち始めた日時の 6 つで、資料へのリンクを持たない

`approval-request.md` の設計 Pull Request の「判断に使うもの」は、目的・用語・適用範囲・根拠・起票者の推定・決めたこと・作るもの・満たすこと・未確認・収束の状態・本文との一致・MVV 判定である。設計で書く成果物の多く（ER 図・画面・技術の選定・非機能・構成図）が、承認の提示に現れない。

## 前提

- 前提 1: 対象は設計承認ゲート（設計 Pull Request のマージの前）の資料である。リリース承認ゲートの資料は変えない
- 前提 2: 外部調査は、設計の「外部の調査」の手順（`design/references/external-survey.md`）で行う。調べる対象は設計レビューの資料の慣行（ADR・C4 モデル・設計文書の書式・主要な製品の設計レビューの資料）とし、確定は設計者が行う
- 前提 3: 「MECE」は、一覧の行どうしが同じ判断の問いに答えない（重複しない）ことと、今ある設計の成果物と承認の提示の項目がすべて一覧のどれかの行に対応づく（漏れない）ことで判定する
- 前提 4: Factory の Web 画面での見せ方は、この課題では規定（画面の構成と、画面が受け取るデータの形）までを書く。画面の実装は volareinc/nd-factory の別の課題にする
- 前提 5: 動作する画面モックの表現方法（Claude の artifact・検証環境のモック置き場・Storybook など）はプロジェクトごとに違う。この課題が決めるのは、表現方法をプロジェクトの設定に宣言する欄と、宣言が無いときの扱いである。個々のプロジェクトの表現方法は決めない
- 前提 6: CLI の承認の提示は、今と同じく AI が承認を求める直前の応答に書く（`approval-request.md` の「止まる手段」）。端末に専用の画面は作らない

## 対象範囲

含む:

- 設計承認ゲートの資料の一覧（資料名・判断する問い・作る段階・水準・該当の判定・形式・書き方の参照先・根拠）を 1 か所に定める
- 依頼の 4 項目（データ構造の図・動作する画面モックとデザインイメージ・技術スタックの一覧と選定の理由・周辺機能や周辺システムとの関係）の書き方の参照を足す
- 画面モックの表現方法をプロジェクトの設定に宣言する欄と、宣言の欠けを見つける検査
- 該当するのに欠けた資料を名前で挙げる検査
- 画面モックの置き場の宣言に秘密の形の値が書かれていたとき、宣言を保存する際に値を残さず置き換え、置き換えたことを利用者へ知らせる
- CLI での承認の提示の形（リンク集）を `approval-request.md` に規定する
- Factory の Web 画面での見せ方（リンク集の画面構成と、画面が受け取るデータの形）を規定する

含まない:

- Factory の Web 画面の実装（前提 4。別の課題）
- リリース承認ゲートの資料（前提 1）
- 個々のプロジェクトの画面モックの表現方法の選定（前提 5）
- 既存の設計文書（`issues/` と `docs/specifications/` にあるもの）を新しい一覧に合わせて書き直すこと
- 承認ゲートの数と置き場所の変更（`development-workflow` の「人手の承認を求める承認ゲート」が持つ）

## 用語

| 用語 | 意味 |
| --- | --- |
| 承認資料 | 承認ゲートで承認する人へ示すもの。この課題では設計承認ゲートの承認資料を扱う |
| 承認資料の一覧 | 設計承認ゲートで示しうる資料を、資料名・判断する問い・水準・該当の判定とともに並べた正本の表 |
| 画面モック | 画面を変える変更で、承認する人が実際に操作して挙動を確かめられる試作の画面。見た目だけを示すデザインイメージとは別の資料として扱う |
| デザインイメージ | 画面の見た目を示す画像か、見た目の値（色・寸法・字面）の記述 |
| 技術スタックの一覧 | 変更が使うインフラ・外部サービス・ライブラリと、それぞれを採った理由（新規のものは比べた候補、自作するものは既存のライブラリを採らなかった理由）を並べた表 |
| 周辺システムとの関係 | 変更が接する既存の機能と外部の系（セキュリティ・データ分析・ログ出力とアラートを含む）と、その接し方 |
| リンク集 | 承認の提示の本体の形。資料 1 件につき 1 行で、資料名・要旨・開くリンクを並べる |

## 受け入れ条件

一覧の定義:

- [ ] 1. 承認資料の一覧が 1 つのファイルの 1 つの表にあり、`approval-request.md` の設計 Pull Request の「判断に使うもの」はその表を参照する（同じ行を 2 か所に書かない）
- [ ] 2. 一覧の各行は、資料名・判断する問い・作る段階（設計時 / 承認時）・水準・該当の判定・形式・書き方の詳細の参照先・根拠（外部の出典か今の定義）の 8 つを持つ
- [ ] 3. 一覧に、依頼の 4 項目に当たる行がある: データ構造の図（ER 図・データの流れの図）、動作する画面モックとデザインイメージ、技術スタックの一覧（新規のインフラ・サービスと選定の理由と競合の比較、使う既存のライブラリと自作するライブラリとその理由、ビジネスロジックを作るときの既存ライブラリの調査と自作の理由）、周辺システムとの関係（セキュリティ・データ分析・ログ出力とアラートを含む）
- [ ] 4. 一覧の行どうしに、同じ判断の問いに答える行が無い。今の設計の成果物（`deliverables.md` の要否表の 20 行）と承認の提示の項目（`approval-request.md` の「判断に使うもの」の 12 行）が、すべて一覧のどれかの行に対応づく対応表が設計文書にある
- [ ] 5. 一覧の各行の水準は、必須か該当時のどちらかである。該当時の行には、該当を判定する条件（例: 永続データの構造を変える、画面を変える）が書かれている
- [ ] 6. 一覧の根拠の列の外部の出典は、設計文書の「外部の調査」の節に URL つきで並び、取得できなかった出典はその節の「確かめられなかったこと」に載っている

検査:

- [ ] 7. 設計文書を入力に取る検査コマンドがあり、該当するのに節が無い資料を資料名で 1 件ずつ挙げて、終了コード 0 以外で終わる。欠けが無ければ終了コード 0 で終わる
- [ ] 8. プロジェクトの設定に画面モックの表現方法を書く欄がある。欄が空のプロジェクトで画面を変える設計を検査すると、受け入れ条件 7 の検査が「画面モックの表現方法が未宣言」を挙げて終了コード 0 以外で終わる
- [ ] 9. 画面を変えない設計では、欄が空でも受け入れ条件 8 の欠けを挙げない
- [ ] 9a. プロジェクトの設定の画面モックの欄に秘密の形の値（資格情報を含む URL など）が書かれた宣言を、宣言の保存のコマンド（`project-decl.py write`）で保存すると、保存後の欄は `{"unknown": "秘密の形"}` になる。コマンドの出力に、置き換えた欄の名前と置き換えた理由が 1 行出て、元の値は出力にも保存後の設定にも現れない

CLI での見せ方:

- [ ] 10. `approval-request.md` の設計 Pull Request の提示の形は、資料 1 件につき 1 行のリンク集（資料名・要旨 1 行・生の URL）である。URL は設計文書の該当の節か、宣言された置き場の画面モックを指す
- [ ] 11. 該当しない資料はリンク集に出さず、必須なのに対象が無い資料は「無し（<理由>）」の 1 行で出す

Factory での見せ方:

- [ ] 12. Factory の承認の画面の規定（画面の構成と、進捗の事象で受け取るリンク集のデータの形）が設計文書にあり、画面の本体は CLI と同じ行の並び（資料名・要旨・リンク）である
- [ ] 13. Factory の承認の画面の実装を受け持つ課題が起票され、この課題の設計文書から番号で指されている

退行しない:

- [ ] 14. `light` / `operation` / `documentation` の設計の要否表の列（`deliverables.md`）と、`documentation` の企画承認の提示が変わらない
- [ ] 15. 今の設計 Pull Request の提示の項目（目的・用語・適用範囲・あるべき姿の根拠・起票者の推定・決めたこと・作るもの・満たすこと・未確認・収束の状態・本文との一致・MVV 判定）が、リンク集の行か提示の見出しのどちらかに残る
- [ ] 16. 全体テスト（`uv run --frozen --project . --all-extras pytest . -q -n 4`）と Skill の frontmatter の検査（`python3 scripts/check-skill-frontmatter.py`）が通る

## 依頼（原文）

> 設計承認時に必要な資料を定義するissueを起こします。
>
> * 要求定義と受け入れ条件
> * DDDに基づくドメインモデルとドメインイベント
> などは既に定義済みのはずですが、
> * データ構造を作成、変更する場合のデータ構造関連の(ER図、データダイヤグラムなど)
> * 画面の変更を伴う場合の画面モック(動作するもの)、デザインイメージ
>   * 特に画面モックは、実際の挙動を確認できるものを。artifactや検証環境のモック置き場など、プロジェクトでの表現方法の定義を必須とする
> * 技術スタックのリスト
>   * 新たにインフラ、サービス等を追加する場合はそのリストと選定理由
>    * 競合分析の結果
>   * 利用する既存ライブラリと自作するライブラリ。とその選定理由
>   * 特にビジネスロジックを作成・追加する場合は利用可能な既存ライブラリの調査。自作に決定した場合はその理由
> * 周辺機能や周辺システムとの関係。特にセキュリティやデータ分析、ログ出力とアラートなど
>
> 等が足りていないように見受けられます。
> 設計時に必要なものと、承認時に確認すべきドキュメントや図表、といった観点から外部調査して過不足の無いMECEな承認時資料一覧を作成する
> また、それらがcli上（コンソール上）やfactoryのWeb画面上でどう表示されるかを規定する
>   * なお、コンソールWebともに、メインのコンソールやWeb画面はリンク集となり、各リンクをたどって見れるようにすることが望ましい
