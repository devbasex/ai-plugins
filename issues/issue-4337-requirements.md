## 何が起きたか

2026-11-24、NDF 11.0.26 のリリース後テストで、使い捨てのリポジトリの `standard` のスプリントを `ndf progress next` で進めた。18 工程のうち 16 工程はプランが始まったが、工程「設計」と「ドキュメント再構成」は始まらなかった。どちらも、書き上げた文書を章立てから組み直すコマンドを利用者の設定から読もうとし、設定に無いので止まった。NDF を導入しただけのリポジトリは、この設定を持たない。

そのため、設定を足していないリポジトリで `standard` のスプリントを回す人（と、その工程を流す conductor）は、設計の始めで毎回止まる。2 つの工程の作業を手で行ってから、工程を済んだとして閉じる（`ndf progress finish`）ことになる。

この文書で使う NDF の言葉は次のとおりである。

| 言葉 | 意味 |
| --- | --- |
| conductor | スプリントの工程を順に進める AI のセッション |
| supervisor | conductor から工程を 1 つ任され、作業を worker へ割り振る AI |
| worker | 作業を 1 つ受け持つ AI の実行主体 |
| プラン | 工程の中で打つコマンドの並び。工程ごとのテンプレートから組む |
| 差し込み | プランのテンプレートの空欄。`ndf progress next` が値を入れる |
| 読み手役 | 文書を書いていない AI に、想定した読み手の立場で読ませ、伝わるかを確かめる役 |
| スプリント | 1 つ以上の課題を、要求から本番へのリリースまで通す開発の単位 |
| 工程・ステップ | 工程はスプリントを区切った作業のまとまり（例: 設計）。ステップは、工程のプランの中の 1 つのコマンド |
| モード | 変更の種類ごとに決まる工程の並び。`standard`（本番の振る舞いを変える変更）、`documentation`（リポジトリの外の読み手へ渡す文書を作る）、`legacy-refactor`（テストの少ないコードの構造を変える）、`light`、`operation` がある |
| 作業場所 | 工程が作業する git の worktree |
| 承認ゲート | 人が承認するまで先へ進まない所。設計承認ゲートとリリース承認ゲートの 2 つがある |
| 起点 | 差分を測る基準のコミット。ベースブランチ（スプリントの PR のマージ先）の、リモートにある位置（リモート追跡ブランチ）を使う。取得していないときやリモートが 1 つも無いときは、手元の位置を使う |
| MVV | このリポジトリの判断の基準（`.ndf/mvv.md` の Mission・Vision・Value）。「リクエスト（原文）」の「MVV バージョン 11」は 2026-11-22 に利用者が承認した今の版、「Value 4」は Value の 4 番目「どのプロジェクトでもそのまま使える」である |
| p9-lsplit-r2 | 「リクエスト（原文）」に出るスプリントの名前。worker の報告の保存先や、工程のプランの worker の既定を直したスプリント（PR https://github.com/devbasex/ai-plugins/pull/4325 ） |

## 種類

不具合（`standard` のスプリントの工程を `ndf progress next` のプランで流すことは、`development-workflow` の手順書と `ndf progress` が既に約束している。設定の無いリポジトリでは 2 工程だけ約束どおりに動かないので、約束どおりに動くようにする）

## 今の姿

`ndf progress next` は、工程ごとに決まったプランのテンプレート（[plugins/ndf/contracts/templates/](https://github.com/devbasex/ai-plugins/tree/main/plugins/ndf/contracts/templates)）へ値を差し込み、組んだプランを流す。差し込む値が 1 つでも決まらなければ、工程を始めずに止まる（工程のプランが起動のたびに止まった不具合を直した #3908 の決まり）。

文書を組み直すコマンド（差し込み `rebuild`）を使う工程は 2 つある。

| 工程 | プランの中での順 | 組み直しの後に使うもの |
| --- | --- | --- |
| 設計 | 設計を書く → **組み直す** → push → PR → レビュー | レビューが、組み直しの結果ファイルの「足すべき内容」（組み直しの途中で見つかった、文書に足すべき不足の指摘）を 1 件ずつ直すか見送る |
| ドキュメント再構成 | **組み直す** → push | なし |

同じように設定から読むコマンドでも、レビュー（`review`）とリファクタリング（`refactor`）は、設定が無ければ NDF が既定のコマンドを組む。組み直しだけは既定が無く、出所は `.ndf/project.json` の `workflow.launch.rebuild` だけである（[invoke.py](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/src/ndf/progress/invoke.py) の `FILL_SOURCES`・`PROJECT_KEYS`）。組み直しの手順そのものは [document-rebuild の SKILL.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/document-rebuild/SKILL.md) が持っている。

このリポジトリ（ai-plugins）には、既定ができるまでの代わりとして、組み直しのスクリプト `scripts/launch-document-rebuild.sh` とそれを指す設定が PR #4379（組み直しの起動を設定に置いた変更）で入っている。

## 事象

設定の無いリポジトリで、2 つの工程のプランがどちらも組めない。

```text
stopped（precondition）: 工程 設計 のプラン design の差し込み rebuild を決められない
items: [{"key": "rebuild", "source": ".ndf/project.json の設定"}]
```

- 工程の記録（`started`・`failed`）は書かれない
- `items` の `source` は「.ndf/project.json の設定」だけで、設定のどのキーに何を書けばよいかが分からない

`main`（167ea3bbc、NDF 11.0.28）でも、プランの準備（`invoke.prepare_plan`）だけを 2 つの工程について打って確かめた。

| 設定 `workflow.launch.rebuild` | 設計 | ドキュメント再構成 |
| --- | --- | --- |
| 無し | `TemplateValuesMissing`（`rebuild`） | `TemplateValuesMissing`（`rebuild`） |
| あり | 組める | 組める |

代わりのスクリプトにも、コードを読んで見つけた問題が 3 つある。別の変更の PR #4367（コントラクトの値の検査）のレビューで出た指摘で、実行はしていない。

| 問題 | 起きること |
| --- | --- |
| 差分の起点が `origin/main` に固定 | スプリントブランチにマージ済みの、別の課題の設計書まで組み直す |
| `issues/*.md` をすべて worker へ渡す | 要求仕様のコピーを外すことは worker への指示任せで、実装計画は外れない |
| `issues/` の外を見ない | 原稿だけを変えたドキュメント再構成が、組み直さずに成功する |

## 期待する結果

ブランチ戦略の設定（`branch_strategy`）を持ち、組み直しの設定を持たないリポジトリで、組み直しの既定のコマンドが決まり、工程「設計」と「ドキュメント再構成」がプランで流れる。既定を決められないときは、始める前に止まり、設定のキーと値の形が結果で分かる。

## 再現手順

1. `workflow.launch.rebuild` の無いリポジトリで `ndf progress new <名前> --mode standard --issues <番号>` を打つ
2. 工程「要求と受け入れ条件」「作業場所の用意」の後に `ndf progress next <ID>` を打つ
3. 工程「設計」が、上の `stopped（precondition）` で始まらない

設定に組み直しのコマンドを置くと、同じスプリントで設計 → 組み直し → push → PR → レビューまで進む。

## 環境

NDF 11.0.26（取得元の `main` から隔離した設定ディレクトリへ導入）と `main` の 167ea3bbc（11.0.28）、Linux

## なぜ困るか

`standard` のスプリントは、設定の無いリポジトリでは必ず設計の始めで止まる。conductor は設計とドキュメント再構成を supervisor で回し、`ndf progress finish` で閉じる手間を毎回払う。設定で避けるには、利用者が組み直しのスクリプトを自分で書く必要があり、その手順書は無い。

## 目的

- ブランチ戦略の設定（`.ndf/project.json` の `branch_strategy`）を持ち、組み直しの設定を足していないリポジトリで、`standard` のスプリントの工程「設計」と「ドキュメント再構成」が、`ndf progress next` だけで流れる
    - `branch_strategy` は利用者が書く設定で、NDF を導入しただけでは書かれない。工程「設計」の前の工程「作業場所の用意」（`ndf worktree create`）がこの設定が無いと止まるので、工程「設計」まで進んだスプリントのリポジトリはこの設定を持つ
- 組み直しで、別の課題の設計書・要求仕様のコピー・実装計画を書き換えない
    - ただし、次の 2 つが組み直しの対象になることは許す（設計書の決定 4・決定 9 の代償）。1 つ目は、スプリントブランチにマージ済みの別の課題の原稿である。原稿（前提 4）は名前に課題の番号を持たないので、番号で外せない。2 つ目は、前のスプリントで書いた同じ課題の実装計画のうち、頭に設計書を省いたことを示す行（`省いた文書: 設計書`。条件 9）を持ったまま残っているものである

## 対象範囲

含む:

- 設定が無いときの、組み直しの既定のコマンド（工程「設計」「ドキュメント再構成」）
- 既定のコマンドが組み直す文書の選び方（差分の起点・外す文書・原稿のパス）
- 既定を決められないときに、止まった結果へ何を載せるか
- ai-plugins の代わりの設定（`.ndf/project.json` の `workflow.launch.rebuild`）と `scripts/launch-document-rebuild.sh` を消すこと

含まない:

- 設計 PR のマージ先の決め方。設定 `branch_strategy.sprint.doc_prs` は、設計 PR などの文書の PR をベースブランチとスプリントブランチのどちらへ出すかを決める値である。今の NDF はこの値を読まず、設計 PR をいつもベースブランチ（スプリントの PR のマージ先）へ出す。この課題でもそれを変えない
- 工程の外でテンプレートを使う経路（`ndf route render`・`run`）の既定。組み直しのコマンドは今のとおり引数で渡す
- `document-rebuild` の手順と、工程表の工程の増減
- レビュー・リファクタリングの既定のコマンド
- 工程を移った後も、スプリントの記録が片付けた作業場所を指したままになること（#4229）

## 前提

- 前提 1: 「設計書」は、`issues/issue-<番号の並び>-design` で始まる Markdown（設計書・決定の記録・詳細設計書）を指す。要求仕様のコピーは `issues/issue-<番号>-requirements.md`、実装計画は `issues/issue-<番号>-plan.md` である
- 前提 2: 要求仕様のコピーは、正が課題の本文で、コピーだけを手で直さない決まりなので、どの工程でも組み直さない
- 前提 3: 設計書を省いた変更では、工程「ドキュメント再構成」の対象は実装計画になる（`development-workflow` の「文書を省いたときの工程」）。工程「設計」では、この場合も実装計画を組み直さない
- 前提 4: 原稿（読み手へ渡す文書のソース）は、作業場所の差分にある、`issues/` の外の Markdown を指す。組み直しの対象にするのは `documentation` モードのときだけとする。ほかのモードの差分にある `README.md` や `docs/` は原稿ではない
- 前提 5: 「差分」は、起点（用語の表）と作業場所の `HEAD` の分岐点から `HEAD` までに足すか変えたファイルを指す。消したファイルは含まない
- 前提 6: 条件 3 の前提の `doc_prs: sprint` は、ai-plugins の設定の値である。今の NDF はこの値を読まないので、別の課題の設計書がスプリントブランチに入るのは、その課題の変更をスプリントブランチへマージしたときである。条件 3 は、この値によらず結果が同じであることを求める
- 前提 7: 目的と条件は `standard` のスプリントで書く。工程「設計」はほかのモードでも通り（`light` と `operation` は設計が要るときだけ）、工程「ドキュメント再構成」は `documentation` と、設計 PR を分けた `legacy-refactor` も通る（`development-workflow` の工程表）。既定のコマンドは、これらのモードの 2 つの工程にも同じく当たる

| 大項目 | 条件 |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`workflow.launch.rebuild` が無くてもプランが組める。新しいサブコマンド `ndf document-rebuild run` が増え、既定のコマンドはこれを打つ。工程「ドキュメント再構成」の入力に `mode`（スプリントのモード）が加わる。既定を決められないときの `ndf progress next` の結果に、設定のキーと値の形が加わる。設定のキーと値の形、結果 JSON の今のキーは変えない |
| 重さ | 設定の無いリポジトリの `standard` のスプリントが設計の始めで必ず止まる。回避の手段は、組み直しのコマンドを自作して設定に置くか、2 工程を手で済ませて `ndf progress finish` で閉じること |

| 既存の振る舞い | 設定の無いリポジトリで、2 つの工程の組み直すステップが、1 回打つごとに worker を 1 回起動するようになる（対象が 0 件なら起動しない）。worker が立てる読み手役は、この回数に数えない |

## 検証手段

| 項目 | 手段 |

>
> `.ndf/project.json` に `workflow.launch.rebuild` を持たないリポジトリ（ai-plugins もそう）では、工程「設計」と「ドキュメント再構成」のプランの差し込み `rebuild` が決まらず、`ndf progress next` が始める前に止まる。
>
> ```text
> stopped（precondition）: 工程 設計 のプラン design の差し込み rebuild を決められない
> items: [{"key": "rebuild", "source": ".ndf/project.json の設定"}]
> ```
>
> 行に `started` も `failed` も書かれない（#3908 の直しのとおり）。ほかの 16 工程は、導入した 11.0.26 でプランが組めて始まる。
>
> ## 期待する結果
>
> 設定を持たないリポジトリでも、`refactor` と同じように `rebuild` の既定の起動が決まり、工程「設計」と「ドキュメント再構成」がプランで流れる。既定を持てないなら、止まる結果の `items` に設定のキー（`workflow.launch.rebuild`）と値の形を載せる。
>
> ## 再現手順
>
> 1. `workflow.launch.rebuild` の無いリポジトリで `ndf progress new <名前> --mode standard --issues <番号>` を打つ
> 2. 「要求と受け入れ条件」「作業場所の用意」の後に `ndf progress next <ID>` を打つ
>
> 設定へ `rebuild` の起動の引数を置くと、同じステートマシンで「設計」の worker・組み直し・push・PR・レビューまで進んだ。
>
> ## 環境
>
> NDF 11.0.26（取得元の main から隔離した設定ディレクトリへ導入）、Linux
>
> ## 影響
>
> `standard` のスプリントは設計のフェーズの始めで毎回止まり、conductor は設計とドキュメント再構成を supervisor で回して `ndf progress finish` で閉じる（11.0.25 までと同じ手間が 2 工程に残る）。
>
> ## 起票者の推定
>
> - 既定は `refactor` の既定（`plugins/ndf/src/ndf/progress/refactor_values.py`）と同じ層で組むのがよい（推した出所: #3908 の決定 7）
> - 組み直しは `document-rebuild` の手順を worker へ出す形になる（推した出所: `contracts/templates/params.json` の `rebuild` の説明が `--out` と結果のファイルを受けると書くこと）
