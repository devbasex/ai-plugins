## 決定の記録

### 決定 1: 部品が値でなく名前で上限を引けるよう、上限の宣言を方針の名前 → 値の平らな表にする

方針の 1 行は `summary` と、上限の秒・間隔・倍率・間隔の上限・1 回の呼び出しの待ち・打つ回数・同じ原因の上限のうち使うものだけを持つ。
監視の工程 × 担当の表は、`monitor.phase.<工程>` と `monitor.stall.<担当>` の名前で同じ表に置く。`limits.py` が接頭辞で数え上げる。
1 つの部品が組で使う値（設計の結果の読み取りの間隔・1 回の待ち・合計）は 1 つの方針にまとめ、組の値を別々の名前に分けない。

工程と担当の 2 段の入れ子を宣言の形に持つ案は採らない。入れ子を持つのは監視の表だけで、ほかの 100 か所の上限に使われない形を読み手が受け持つことになる。

根拠: Value 6「どのプロジェクトでも使える形を保つ」 / Value 8「判断の理由を残し、語をそろえる」（MVV 版 5）

### 決定 2: hook の経路でも起動を遅くしないよう、読み手は標準ライブラリの `json` だけで 1 プロセスに 1 回読み、置き場をプラグインからの相対に固定する

hook は SessionStart が用意した仮想環境の python を直に起動する。hook からは `deps.require()` を呼べない（構造チェックの `hook-deps`）。
読み手が pydantic を要すると、hook が宣言を読めない。形の確かめ（I1）は読み手の数十行の判定と、CI の契約の検査の 2 か所で行う。置き場の上書きの環境変数は作らない。
テストは読み手の読み込み先を関数で差し替える。

宣言の置き場を環境変数で差し替えられるようにする案は採らない。上書きの経路を新しく作ることになり、要求の対象範囲（含まない）に当たる。

根拠: Value 6「どのプロジェクトでも使える形を保つ」 / Value 5「決まった手順はスクリプトに、判断と中身は AI に」（MVV 版 5）

### 決定 3: 宣言の誤りで実際の上限が宣言と食い違わないよう、読めないときは組み込みの値へ戻らず `LimitsError` で止める

組み込みの値へ戻ると、宣言を直したつもりの人の値が使われず、それが結果に出ない。`LimitsError` は理由に宣言のパスと方針の名前を持ち、
エントリポイントは終了コード 1 で止まる。宣言は配布物の一部で、利用者が書く設定ではないため、壊れるのは配布物の不具合である。CI の契約の検査が先に落とす。

今の `safe_int_env`（環境変数が数字でなければ警告して既定値を使う）は利用者の入力への扱いで、宣言の誤りとは別のため変えない。

根拠: Value 1「小さく出して使って確かめる」 / Value 7「根本原因の場所で直す」（MVV 版 5）

### 決定 4: 正規表現で見落とす上限の数字を落とせるよう、`limit-literal` を構文木で判定し、名前の規則とキーワードの表の 2 つで当てる

`timeout=[0-9]` の正規表現が当たるのは 20 か所である（0 と docstring の中を含む）。構文木で数えた 110 か所のうち、定数・関数の既定値・`.get` の既定値の 91 か所を
この正規表現では落とせない。構文木で、名前の規則に当たる定数・12 個のキーワード引数・同じ名前の引数の既定値・`.get("<キー>", <数字>)` の 4 つを見る。0 は「待たない・打ち直さない」の意味で上限の値でないため外す。
終了コードの定数（`EXIT_` で始まる・`_CODE` で終わる名前）は名前の規則で外す。割合と見直しの周期の 3 か所は例外リストに理由つきで載せる。

名前の規則を持たずに、数字のリテラルをすべて落とす案は採らない。行数・文字数・終了コードなど上限でない数字が数百か所当たり、例外リストが検査の意味を失う。

根拠: Value 6「どのプロジェクトでも使える形を保つ」 / Value 7「根本原因の場所で直す」（MVV 版 5）

### 決定 5: 再試行のループを書き戻せないよう、再試行と待ちを見分けずに、`lib/waits.py` の外の眠りのループをすべて落とす

構文木から「失敗した同じ呼び出しの打ち直し」と「条件が揃うまでの問い合わせ」を見分ける規則は、呼ぶ関数の意味に頼るため外れる。
眠りのループは両方を含み、構文で決まる。今ある 25 か所のうち、再試行の 1 か所（`supervise_lib/paths.py`）は `waits.retry_call` へ移す。
待ちの 24 か所は、例外リストに理由（何を待つか）つきで載せる。新しい眠りのループは、`lib/waits.py` を通すか、例外リストの行を差分に載せて
レビューを通すかのどちらかになる。行の増加を機械で落とす検査（`allow-grow`）は #2335 の P0 の受け持ちで、入れば同じ行に効く。

名前（`retry` を含む関数）で再試行を見分ける案は採らない。要求の前提 6 のとおり、名前に `retry` を含む関数 2 つは打ち直しのループを持たない。
名前で見分けると、`_add_worktree_with_retry` のほかに名前で当たらない打ち直しが残る。

根拠: Value 5「決まった手順はスクリプトに、判断と中身は AI に」 / Value 7「根本原因の場所で直す」（MVV 版 5）

### 決定 6: 同じ失敗を番号や時刻の違いで別の原因と数えないよう、原因の鍵は種類と伏せた理由の文から作り、鍵ごとに数える

#1983 の失敗の理由は「PR #1976 の CI が失敗: runtime-smoke (agy)（run 38353378585）」である。run の番号が変わっても同じ原因である。
日時・URL・パス・16 進の語・数字をこの順で伏せ、空白をまとめて先頭 200 字を残す。種類（例外の型か `exit=<終了コード>`）を前に付け、
同じ文でも終了コードが違えば別の原因にする。回数は鍵ごとに数え、続いたかどうかは見ない。A と B の原因が交互に起きても、
どちらかが上限に届けば止まり、合計は打つ回数と待ちの合計の上限が抑える。

続けて起きた回数だけを数える案は採らない。交互に起きる 2 つの原因で、上限に届かないまま待ちの合計まで回る。理由の文の数字を伏せない案は採らない。
番号つきの失敗が毎回別の原因になり、#1983 が再現する。

根拠: Value 7「根本原因の場所で直す」 / Value 3「やめる・縮めるを既定にする」（MVV 版 5）

### 決定 7: 新しく止める所だけ振る舞いを変えるため、ステップの打ち直しの同じ原因の上限は 2、呼び出しの再試行は方針ごとに今届く回数にする

ステップの打ち直しは、今は同じ原因で止まらない。#1983 の受け入れ条件 1 は「同じ失敗の要約で 2 回落ちたステップは 3 回目を流さない」を求める。
呼び出しの再試行は一時的な失敗（上限・lock・502）を待つためのもので、同じ原因が続くのが通常である。そこへ小さい上限を当てると、
今は回復している失敗で止まる。再試行の方針の `same_cause` は、今の間隔と合計から届く打つ回数と同じ値にし、移す前後で振る舞いを変えない（要求の「移行性」）。

全方針に共通の既定（例: 3）を読み手に持たせる案は採らない。読み手の中に上限の数字が残り、I3 と食い違う。

根拠: Value 3「やめる・縮めるを既定にする」 / Value 1「小さく出して使って確かめる」（MVV 版 5）

### 決定 8: 判定役の答えに頼らず決まった回数で止まるよう、ステップの打ち直しはプランの実行が判定の後に数えて止める

#1983 では、判定役は自分で「再び同じ所で落ちたら止める」と書いた。しかし前の打ち直しの結果を読まずに、7 回とも同じ答えを返した。
判定は言語モデルの答えで、同じ入力でも揃わない。プランの記録（`RunState.record`）が、ステップの失敗ごとに原因の鍵を数える。
判定役が失敗したステップを返したときは、プランの実行（`Engine._next_after_judge`）が回数を見て止める。判定役の入力は変えない。

判定役の入力に前の失敗と回数を足して判断させる案は採らない。止まるかが答えに左右され、受け入れ条件 5 の「宣言の回数で止まる」をテストで縛れない。

根拠: Value 5「決まった手順はスクリプトに、判断と中身は AI に」（MVV 版 5）

### 決定 9: 宣言した上限を使い切ってから止まるよう、待ちと再試行は次の眠りを残りの秒に縮め、上限の時刻に最後の 1 回を打つ

今の `_stop_by_idle` は「眠りの合計 + 次の眠り > 上限」で止まる。間隔が 120 秒まで伸びた待ちでは、最大 119 秒を残す（#2224）。
次の眠りを `min(間隔, 残りの秒)` にし、残りが 0 になった後の 1 回で止まる。同じ規則を `retry_call` にも当て、止まる規則を 1 つにする。
上限がちょうど間隔の倍数の方針（設計の結果の読み取りの 15 秒 × 2 = 30 秒など）は、今と同じ回数で止まる。

`wait_until` だけを直す案は採らない。2 つの関数で止まる規則が分かれ、同じ方針の値を渡しても打つ回数が関数で変わる。

根拠: Value 7「根本原因の場所で直す」（MVV 版 5）

### 決定 10: 表示のたびに動くシェルを遅くしないよう、シェルのスクリプトの数字は検査に入れない

`statusline.sh` は表示のたびに動き、宣言を読むには Python を起動することになる。ほかの 5 か所は、`${<環境変数>:-<数字>}` の既定値と `timeout 1` である。
これらも、シェルのエントリポイントが実行の核の上で動く（#2337 の `run-core.sh`）までは、Python の宣言を読む経路が無い。核の上で動いた後は、
核が宣言から引いた値を環境変数で渡せるため、そのときにシェルの数字を移す。

シェルから `limits.py` を毎回起動して読む案は採らない。表示と錠の待ちのたびに Python の起動（21 ms）が足される。

根拠: Value 6「どのプロジェクトでも使える形を保つ」 / Value 1「小さく出して使って確かめる」（MVV 版 5）

### 決定 11: 前提の柱を待たずに値の置き場と止め方をそろえるため、この柱は実行の核に依存しない形で作る

要求の前提 1 は、核のスケルトン（#2337）と持ち主・後片付け（#2342）の後にこの柱を作るとする。この設計の部品（宣言・読み手・原因の鍵・待ちの部品・
プランの実行）は、核の段を通らずに今のエントリポイントから呼ばれる。核が入った後に核がするのは、`LimitsError` を `stopped` に変えることと、実行の記録へ理由を書くことである。
どちらもこの設計の形を変えない。期限で打ち切った実行の持ち主の記録（#2335 の柱の順序で P4 が P3 を前提にした理由）は、要求の対象範囲（含まない）のとおり #2342 が受け持つ。

核が入るまで設計を待つ案は採らない。#1983 と #2224 の不具合は核と無関係に起きており、待つ間も同じ止まり方が続く。

根拠: Value 1「小さく出して使って確かめる」 / Value 4「外の利用で測って決める」（MVV 版 5）

### 決定 12: 1 回の承認で読み切れる差分に収めるため、実装を 3 本の Pull Request に分け、例外リストで 1 本目を通す

| Pull Request | 入れるもの |
| --- | --- |
| 1 本目 | 宣言・読み手・原因の鍵・待ちの部品・プランの実行・worktree の作成・構造チェックと契約の検査。まだ移していない上限の数字は、`limit-literal` の例外リストの行として載せる |
| 2 本目 | `scripts/lib/`・`scripts/supervise_lib/`・エントリポイントのスクリプトの数字を移す |
| 3 本目 | 残り（`relay_lib`・`hook_lib`・Skill の下・ほかの `*_lib`）を移す |

移した Pull Request が、同じ差分でその行を消す。3 本目の後に残る `limit-literal` の行は、上限でない 3 か所だけになる。子の課題の再現の手順は 3 本目の後に通す。

1 本の Pull Request で 104 か所を移す案は採らない。69 ファイルの差分になり、#2335 の決定 11 の「部品の Pull Request は 3 本まで」の単位を超える。

根拠: Value 2「人が判断できる量に収める」 / Value 1「小さく出して使って確かめる」（MVV 版 5）

### 決定 13: エントリポイントから上限をたどれるよう、方針の名前と宣言の対応の検査と、方針ごとに引く関数の表を契約の検査に置く

契約の検査（`check-ndf-contracts.py`）は、契約の一覧の形と逆引きの表（`plugins/ndf/contracts/index.md`）を持つ。方針の名前を引く呼び出し
（`limits.policy("<名前>")`・`limits.seconds("<名前>")`・`limits.value("<名前>", …)`）を、構文木で集める。
宣言に無い名前と、どこからも引かれない方針を落とす。方針ごとの値と引く関数は、「上限の宣言」の表として描く。名前の照合ができるよう、`lib/limits.py` の外では方針の名前を文字列のリテラルで書く。
`lib/limits.py` が接頭辞で数え上げる方針（`monitor.` で始まる名前）は、引かれたものとして数える。

構造チェックに名前の対応を足す案は採らない。構造チェックはコードの形を見る検査で、契約の一覧の逆引きの表を描く役割を持たない。

根拠: Value 8「判断の理由を残し、語をそろえる」 / Value 6「どのプロジェクトでも使える形を保つ」（MVV 版 5）
