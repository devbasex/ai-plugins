# #1337 の設計: 決定の記録・テスト設計・未確認のまま残ること

設計の本体は [issue-1337-design.md](issue-1337-design.md) にある。この文書はその続きである。

## 決定の記録

### 決定 1: 依存の用意の宣言は共有設定の新しい `deps` 節に置く

依存の用意は worktree を作るたびに走る、worktree の設定の一部である。`localenv` は「ローカル環境（`kind: compose`）の
コードの向け先」の節で、`kind` が `compose` でなければ `worktree-localenv.sh` 全体が何もしない。`localenv` を
`compose` 以外でも働かせるのは、要求の境界で「確認してから行う」に当たる。キーの名前と意味
（`copy_from_main`・`copy_as_real`）は `localenv` から引き継ぎ、手続きも同じ関数を使う（前提 2）。

`.ndf/project.json` には置かない。`project.json` は解析が書くファイルで、利用者が手で足した節は解析のやり直しと
突き合わせる必要が出る。`localenv.copy_from_main` を作成時に自動で走らせる案は、既存の共有設定の振る舞いが
書き換えなしで変わるため採らない（移行性）。

### 決定 2: 手段は複製・実体の複製・コマンドの 3 つにし、symlink は張らない

symlink にすると、worktree のコードではなくメインディレクトリのコードが読まれる言語がある。PHP の `__DIR__` は
symlink をたどった先を返し、Composer はそこからアプリの根を決める（carmo のコンテナで実測）。Python の `.venv` も
`pyvenv.cfg` と編集可能な導入の `.pth` がメインディレクトリの絶対パスを持つ。どちらも偽の green になる。
symlink は `git worktree remove` を `--force` なしで断らせる（`vendor/` の規則はディレクトリにしか当たらない。
2026-09-27 に git 2.53.0 で実測）。

ハードリンクの複製は、worktree の中で依存物をその場で書き換えるとメインディレクトリの同じファイルも変わる
（同じ実測で、複製先へ追記するとメインディレクトリのファイルにも現れた）。書き換えるパスは `copy_as_real` に置く、
と宣言の契約にし、`worktree` Skill に書く（I7）。書き換えるかどうかを複製の前に見分ける手は無いため、用意の中では
複製の後に書き換えられたものを探す: 複製の前に時刻の印を置き、`run` の後に `find <copy_from_main のパス> -type f -links +1
-newer <時刻の印>` を打つ。置き換え（消して作り直す）で書くパッケージマネージャはリンクが切れて当たらず、その場で書いた
ものだけが当たる。所要は、ハードリンクで複製した 54,000 ファイルで 0.08 秒だった（2026-09-28 にこの worktree の
コンテナで実測。キャッシュが温まった状態）。見つかれば用意を失敗にし、印を書かない。用意の後にテストがその場で書く経路は
この検査で捕まえず、宣言の契約で防ぐ。

### 決定 3: 共通の処理は `worktree-deps.sh` の 1 本に置き、Python は薄い包みにする

作成の 6 箇所はシェル（W1・W5）と Python（W2・W3・W4・W6）に分かれる。複製の手続きは既にシェル
（`worktree-localenv.sh`）にあり、書き込み先の検査（`destination_is_safe`）もそこにある。Python へ書き直すと、
同じ規則が 2 つの言語に分かれる。Python の包みは共有設定を読んで `deps` の有無を決めることと、終了コードの受け渡しだけを持つ。

### 決定 4: 使い回しの判定は、worktree ごとの git ディレクトリに置く用意の印で行う

「作ったときに 1 回」を作成の経路だけで守ると、失敗の後のやり直しと、この変更より前に作られた worktree の使い回しが
用意されないまま残る。印は worktree の中ではなく `git rev-parse --git-dir` の下に置くため、git の状態を変えず（I3）、
`git worktree remove` で一緒に消える。宣言や lock ファイルの変更を印に含めて自動でやり直す案は採らない。
前提 3 が「宣言が求めない限りやり直さない」とし、求める形の宣言を必要とする事例がまだ無い。

### 決定 5: 用意は git の状態を変えてはならない

依存物が git に無視されないパスにあると、3 つが壊れる。修正担当の `git add -A` が依存物を Pull Request へ混ぜる。
cross-review の `_sync_worktree` がラウンドごとに `git clean -fd` で消す（無視されるパスは消さない）。
`_is_synced` が「追跡されないファイルがある」と読み、毎ラウンド巻き戻す。用意の前後で `git status --porcelain` を
比べれば、原因（無視の設定が無い・`run` が lock ファイルを書き換えた）を用意の時点で名指しできる。

### 決定 6: 作成の対象を 6 箇所に広げる

要求の 4 箇所に、cross-refactoring の書き込み用（W4）と着手前の HEAD の一時の worktree（W6）を足す。要求が挙げた
`prepare-worktrees.sh` は読み取り用だけを作り、範囲テストと全体テストが走る `work/` は `setup.py` が作る。W6 は
依存物が無いと変更起因の失敗を既存失敗へ入れる。どちらも `git worktree add` を検索して見つけた。

### 決定 7: 到達の確認は、コンテナの中から worktree の印を読んで行う

マウントの一覧（`docker inspect` の `Mounts`）から判定する案は採らない。コンテナ実行系が別のホストにある構成
（devbase の DooD）では、`Source` は実行系の側のパスで、こちらのパスと比べられない（carmo のコンテナは `/work` を
名前付きの volume でマウントしていた）。印を読む方法は、テストのコマンドと同じ `exec` の経路を通るため、コマンドが
見るものをそのまま確かめる。要るのはコンテナの中の `cat` だけである。

### 決定 8: コンテナへ worktree を届ける手段は、テスト環境の割り当てを環境変数で指すことにする

`worktree-testenv.sh` は worktree ごとの compose のプロジェクト（`NDF_WORKTREE` をマウントする上書き）を既に組める。
`COMPOSE_PROJECT_NAME` と `COMPOSE_FILE` を渡せば、プロジェクトが書いた `docker compose exec -T app …` を書き換えずに
その環境へ向けられる（shell の値が `.env` より優先されることを実測した）。コマンドの `{workdir}` のような語を足す案は、
テストの走らせ方の宣言（#1334）を変えるため採らない（要求の「含まない」）。

**テスト環境を自動で起こさない。** 起動にはポートの割り当てと基準のボリュームの用意が伴い、数分かかることがある。
届かないときは起こし方（`worktree-testenv.sh up <worktree>`）を理由に添えて止まる。コマンドの中で `-p` や `-f` を
固定したプロジェクトは環境変数が効かず、到達の確認と実際の実行が別のコンテナを見る。これは `references/test-execution.md`
に「container の suite のコマンドでは `-p`・`-f` を書かない」と書き、検出はしない（コマンドの語を見ることになる）。

### 決定 9: NDF の手順は `EnterWorktree` と Agent の `isolation: "worktree"` を使わず、拒まれたときの手を `worktree` Skill に書く

拒むのは Claude Code 本体の、Bash を走らせる直前の検査である（2.1.283 の本体を読み、使い捨てのリポジトリで
`claude -p` を別プロセスで起こして 18 通り打った）。隔離の根（`EnterWorktree` の `worktreePath` か、Agent の
`isolation: "worktree"`）があるときだけ働き、コマンドの文面を構文木にして「git がメインディレクトリを触らない」と
示せないものを拒む。権限モードに関係なく働き、判定は版で変わる（2.1.252 で拒まれた `for` と `${PIPESTATUS[0]}` は
2.1.283 で通る）。**NDF のスクリプトを隔離に合わせて書き直すと、版が変わるたびに追うことになる。**

NDF の手順はもともと `cd` で worktree へ移り（`worktree` Skill の手順 2-3）、隔離の根を作らない。Skill には次の 3 つを書く。

| 状況 | どこで何を打つか |
| --- | --- |
| NDF の手順で worktree に入る | `worktree-setup.sh create` の後に `cd <worktree>`。`EnterWorktree` と `isolation: "worktree"` は使わない |
| 隔離の中で `bash "$CLOSING"` の形が拒まれた | worktree の中で、スクリプトを変数でなくリテラルの絶対パスで書き、複合コマンドを 1 つずつに割る（`… \| bash /abs/…/closing-issues.sh`）。実測で、同じ形のスクリプトが通った |
| それでも拒まれる（メインディレクトリで git を打つ手順・文面に `git` を含む制御構文） | `ExitWorktree` で隔離を外し、`cd <worktree>` してから同じコマンドを打つ。実測で、外した後は拒まれた行がそのまま通った |

`issue-plan-strategy` の「Agent tool の `isolation: "worktree"` も検討する」（`SKILL.md:254`）は、同じ検査が働くため
「`worktree-setup.sh create` で worktree を作り、そのパスを渡す」に書き換える。**受け入れ条件 8 の「1 度実際に打つ」は、
本物の `closing-issues.sh` で実装のときに行う**（設計の実測は同じ形のスタブまでである）。

隔離の中でも動く形へ NDF のスクリプトの呼び方を揃える案は採らない。拒む条件が文面の部分一致（`/git/i` が `digit` にも
当たる）を含み、手順の書き方の規則として維持できない。

### 決定 10: 解析（`project-decl.py`）は依存の用意とコンテナの案を出さない

手段はリポジトリのファイルからは決まらない。carmo は `composer.lock` を持つが、コンテナに `composer` が無く、
`composer install` は動かない。同じリポジトリでも、使う人の環境で正しい手段が変わる。推測で書いた宣言は、前提 4 の
「NDF が推測で足さない」にも当たる。コンテナの suite（`container`）も、テストのコマンドの語を見ずには決められない。
宣言の書き方は `references/declaration.md` の例で示す。

### 決定 11: 受け入れ条件 3 の「実行される外部コマンド」は、git のコマンドと書き込むプロセスで比べる

シェルの作成箇所（W1・W5）は、`deps` の有無を決めるために共有設定を `jq` で 1 回読む。W1 は今も起点の解決で
`jq` を何度も打っており、読むだけのコマンドの回数を固定すると、振る舞いではなく実装を縛る。比べるのは、git の
コマンドと引数・`sh -c` で走るコマンド・worktree と `.git` の下に作られるファイル・標準出力と標準エラーである。
Python の作成箇所は共有設定を自分で読むため、`deps` が無ければプロセスを 1 つも足さない。

### 決定 12: 複製元が無いパスは失敗にする

`localenv.setup` は複製元が無いパスを黙って飛ばす。`deps` では失敗にする（受け入れ条件 4）。宣言した依存物が無いまま
「済み」と出すと、依存物に頼る検査が黙って飛ぶ。carmo の pre-commit は `vendor/bin/pint` が無くても成功を表示して
0 で終わり、コミットが通っていた（記録 07-17 と 06-16）。`localenv.setup` の振る舞いは移行性のため変えない。

## 未確認のまま残ること

| 項目 | 内容 |
| --- | --- |
| ホストから打つ carmo の pre-commit | devcontainer の外（`REMOTE_CONTAINERS` が無い）では、pre-commit が `docker compose exec -T app ./vendor/bin/pint` を打つ。compose のプロジェクト名は作業ディレクトリの名前か `.env` から決まり、NDF はフックの環境に手を入れない。今の carmo の運用（devbase のコンテナの中で打つ）では通らない経路で、受け入れ条件 9 の確認も devcontainer の中で行う。確かめるのは実装の後の手動確認である |
| lock ファイルを変える Pull Request の使い回し | cross-review のレビュー worktree は、ラウンドの間に `composer.lock` などが変わっても用意をやり直さない（決定 4）。依存物が古いまま走ったテストが落ちる経路はあるが、偽の green にはならない（コードは worktree のものを読む）。事例が出たら宣言でやり直しを求める形を足す |
| ハードリンクの複製先の書き換え | 決定 2 のとおり、用意の中（`run`）でその場で書き換えたものは検査で失敗にする。用意の後にテストやツールがその場で書く経路は検出せず、`copy_from_main` に書き換えないパスだけを置く宣言の契約で防ぐ。受け入れ条件 6 は消した後の一致だけを見る |
| 到達の確認の所要 | `docker compose exec` を 1 プロセスで 1 回打つ。carmo の規模のコンテナでの所要は実装で測る |
