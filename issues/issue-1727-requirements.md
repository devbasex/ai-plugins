# #1727: relay: 既定のログイン・従量の接続で 401 を扱わず、refreshToken が空のアカウントを候補に残す

正は課題の本文（#1727）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

**2026-10-04 の追加調査で、当初の「relay は 401 を扱わない」は誤りだと分かった。** relay は、上限のシグナルファイルの `error` が `authentication_failed` のとき、上限（429）と同じ経路で次のアカウントへ切り替える（`plugins/ndf/scripts/relay_lib/switch.py:299-361` の `_tick_limit`。`reason` は認証、`ca.note_auth_failed` で記録する）。10-03 10:55 UTC には nyle-team → ohama-personal の切り替えが記録に残っている。

**残る穴は 2 つある。**

1. **既定のログイン（`~/.claude`、アカウント未指定）と従量の接続（metered）では、401 を扱わない。** `_tick_limit` の判定は `self.account not in (None, METERED)` のときだけ認証切れとして扱う。このとき子の `claude` は `Please run /login · API Error: 401 OAuth access token has been revoked.` を出したまま止まり、利用者が端末を見るまで進まない
2. **refreshToken が空になったアカウントが、切り替え先の候補に残る。** Claude Code は token の更新で `invalid_grant` を受けると、共有の認証ファイル（`.credentials.json`）の refreshToken を空にする。認証ファイルは 5 つのコンテナ（novel・ai-plugins・ideabase ×2・with-ai-dev）が同じボリューム（`~/.claude` → `/persistent/group/.claude`）で共有しているため、1 つのコンテナでの失敗が全コンテナへ広がる。2026-10-04 の nyle-team は refreshToken も expiresAt も無く、`Failed to authenticate: OAuth session expired and could not be refreshed` で失敗した

2026-10-04、novel コンテナ（`novel-dev-1`）で利用者が 1 の表示を見た。同じ日に各アカウントを `claude -p "reply OK" --model haiku` で試した結果:

| アカウント（`CLAUDE_CONFIG_DIR`） | 結果 |
| --- | --- |
| 既定（`~/.claude`） | 通る |
| `ndf/accounts/ohama-personal` | 通る |
| `ndf/accounts/nyle-personal` | 通る |
| `ndf/accounts/nyle-team` | 失敗（refreshToken が空）。その後、利用者が Nyle 組織でログインし直して復旧 |

## どこで見つけたか

- novel の relay の記録 `~/.local/state/ndf/relay/20261003T005359Z-5109-04847420/log.jsonl`（05:02 UTC に `reason: limited`・`from: ohama-personal`・`to: metered`）
- relay の判定: `plugins/ndf/scripts/relay_lib/switch.py:299-361`
- 既定（`~/.claude`）と `nyle-personal` は同じアカウントを別々のログイン（別の refresh token）で持つ

## なぜこの変更の範囲外なのか

スプリント m1385（#1385・#1555・#919・#1664・#1689）は cross-refactoring の時間の上限・担当の振り替え・CI 待ちの上限が対象で、relay のアカウントの扱いは受け入れ条件に含まれない。どう扱うかは relay の方針の判断で、即時修正の 4 条件の「既存の方針の範囲」を満たさない。根拠: Value 2「利用者の手を止めない」（MVV 版 2）。

## 直し方（2026-10-04 利用者の決定: 推奨 1・2 を採る）

1. **既定のログイン・従量の接続でも 401 を画面に出し、`/login` を案内する。** 起動時には、refreshToken が空のアカウントを 1 行で知らせる（`/login` の手順付き）。切り替え先の候補からも外す
2. **すべてのアカウントが認証できないときは、従量の接続へ退避する**（上限ですべてが使えないときと同じ扱い）

採らないもの: 認証ファイルのボリュームをコンテナごとに分けること（ログインの手間が増え、上限の切り替えの効果も落ちるため勧めない）。同じアカウントを 2 つの設定ディレクトリで別々にログインしない運用（1 アカウント = 1 ログイン）は、案内に留める。

## 目的

- relay の下で動く `claude` が認証の失敗（401）で止まったとき、どのログインの形（既定のログイン・登録済みアカウント・従量の接続）でも、利用者が端末を見たときに原因と直し方が 1 行で分かり、替えられる先があれば relay が替えて続ける状態にする
- 登録し直さないと使えないアカウントを、起動の時点で利用者が知り、切り替え先に選ばれない状態にする

## 前提

- 前提 1: 従量の接続（`metered`）で 401 が出たときの案内は `/login` ではなく、宣言を確かめるコマンド（`python3 ~/.claude/ndf/relay.py account check metered`）と宣言の置き場（環境変数 `NDF_SUPERVISE_CLAUDE_FALLBACK` か保存した宣言）を示す。従量の接続は最後の退避先なので、それ以上は替えずに子を残す
- 前提 2: 登録済みアカウントの再ログインの案内は `python3 ~/.claude/ndf/relay.py account add <名前>` とする（`/login` で認証ファイルを直しても、登録の記録の「再登録が要る」は消えず候補に戻らない）。既定のログインの案内は `/login` とする
- 前提 3: 認証ファイルの `refreshToken` が空（無い・空の文字列）のアカウントは、アクセストークンが期限内でも候補から外し、「再登録が要る」として扱う（期限が切れた時点で区間の途中で 401 になるため）。今の判定（#1576。リフレッシュトークンか期限内のアクセストークンがあれば使える）をこの 1 点だけ変える
- 前提 4: 既定のログイン（区間のアカウントが無い）の 401 では、上限のときと同じ順で替え先を選ぶ: 使える登録済みアカウント → 従量の接続の宣言 → どれも無ければ案内を出して子を残す。登録が 1 つ以下（切り替えを使わない起動）でも、従量の接続の宣言があれば退避する
- 前提 5: 401 の判定は、今と同じく StopFailure hook が書く上限シグナルファイル（`limit.json`）の `error` が `authentication_failed` であることで行う。子の画面の文字列は読まない
- 前提 6: 認証の失敗の扱いは今と同じく区間ごとに 1 度だけとする（同じ区間で何度 401 が出ても、案内と切り替えは 1 度）

## 対象範囲

含む:
- 既定のログインと従量の接続で 401 が出たときの、画面の案内・記録・替え先の選び直し
- 登録済みアカウントで 401 が出て替え先が無いときの画面の文（今は「すべて上限にある」と出る）
- 起動時の、再登録が要るアカウントの 1 行の知らせ
- `refreshToken` が空のアカウントを候補から外す判定

含まない:
- 認証ファイルのボリュームをコンテナごとに分けること（S5。利用者が採らないと決めた）
- relay が子の `claude` のトークンを更新・修復すること（#1576 の I8。動いている claude のトークンは claude が更新する）
- 既定のログイン（`~/.claude`）の `refreshToken` を起動時に調べること（既定のログインは登録の記録を持たず、401 の時点の案内で扱う）
- 上限（429）の扱いの変更

## 用語

| 用語 | 意味 |
| --- | --- |
| 既定のログイン | `CLAUDE_CONFIG_DIR` を指定しない `~/.claude` のログイン。relay の区間のアカウントが無い（None）状態 |
| 従量の接続 | API キーか Bedrock などの宣言で動く接続。relay では予約の名前 `metered` |
| 再登録が要る | 登録の記録の `needs_relogin` が真のアカウント。候補から外れ、`account add` で登録し直すまで戻らない |
| 上限シグナルファイル | StopFailure hook が書く `limit.json`。`error` に失敗の種類を持つ |
