# #1814: cross-refactoring: 項目が新しいファイルを作ると範囲の外として取り消され、ファイル分割・共通モデルの抽出ができない

正は課題の本文（#1814）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

**cross-refactoring は、項目が新しいファイルを作ることを範囲の外として拒むため、ファイル分割・共通モデルの抽出といったリファクタリングの基本の手法が使えない。**

- 検査のプランは `--scope` を `refactor-scope.py --pr N` で組む。範囲は **PR の差分のファイルそのもので、ディレクトリへ広げない**（#1484 の決定。`plugins/ndf/scripts/refactor-scope.py` の冒頭）
- 範囲の判定 `path_in_scope` は前方一致だけ（`plugins/ndf/skills/cross-refactoring/scripts/refactor_lib/verify.py:34`）。新しく作ったファイルは差分に無いので範囲の外になる
- 実装・修正・最終ゲート修正のプロンプトは「対象範囲の外にあるファイルを 1 つも変更しない」と指示し（`prompts/implement.md:73`・`fix.md:68`・`final-fix.md:92`）、範囲の外を触ったコミットは項目ごと取り消される

## どこで見つけたか

PR 1732 https://github.com/devbasex/ai-plugins/pull/1732 （#1733）: 18 件が `plugins/ndf/scripts/lib/assignment.py` を 491 → 603 行にし、構造検査（1 ファイル 500 行）で 8 件が落ちた。修正担当は 43 回とも「上限へ戻すには新しいモジュールへ分けるしかなく、新しいファイルは対象範囲の外」と `not_fixed` を返した。#1793 で直さなかった項目は早く取り消すようになったが、**直す道（分割）が塞がったままなので、改善は取り消されるだけである。**

## 利用者の判断（2026-10-07）

- ファイル分割はリファクタリングの基本であり、範囲で禁じるのは融通が利かなさすぎる
- **新しいファイルの置き場所を「範囲の中のファイルと同じディレクトリ」に限る制約も付けない。** 分割して共通モデルを別の場所へ抽出することもできなくなるため

## なぜこの変更の範囲外なのか

#1793 は失敗した項目の取り消しと積み直しの規則を直した。範囲の決め方（#1484）は対象に含まれず、方針の変更なので即時修正の条件「既存の方針の範囲」を満たさない。

## 目的

- 範囲の中のファイルを分割する・共通の部品を別のモジュールへ抜き出すリファクタリングを、cross-refactoring が取り消さずに採用まで通せるようにする
- 範囲（`--scope`）が持つ「提案の発散と変更の肥大を防ぐ」役目は、**既存のファイル**について今のまま保つ

## コードで確かめた事実

- 範囲の判定はコミットが触ったファイルの一覧（`git show --name-only`。`gitfacts.py` の `commit_files`）を `path_in_scope` に通す。追加・変更・削除を区別しない
- 実装・修正・最終ゲート修正の取り込みは同じ関数 `verify_commit_basics` で範囲を見る（`verify.py`）
- 危険フラグ D1（項目の `path` と `tests` 以外を触った）は、新しいファイルを作ったコミットで立つ（`danger.py` の `d1`）。立てば全体テストが 1 度走る
- 静的解析の範囲テストは、項目のコミットが変えたファイルのうち worktree に残るものを対象にする（`gitfacts.py` の `changed_files`）
- `test_targets` は `--scope` のテストの置き場所の中にあることを求める。リファクタリング計画の `tests` に挙げたものは、まだ実在しなくてよい（`targets.py` の `valid_targets`）

## 前提

- 前提 1: 「新しいファイル」は、**この実行の起点のコミットに無く、この実行のコミットが追加したファイル**を指す（git の `A`）。同じ実行の中で作った後に別のコミット（同じ項目の後のコミット・修正・最終ゲート修正・別の項目）が直すのも、新しいファイルへの変更として範囲の中に数える。作ったコミットだけを許すと、修正担当が分割したファイルを直した時点で取り消される
- 前提 2: 名前の変更（`R`）・コピーは新しいファイルに数えない。範囲の中のファイルを範囲の外のパスへ移すのは、今と同じく範囲の外への変更として扱う（範囲の外の既存のパスを上書きする道を開かない）
- 前提 3: 生成物・配布物の同期は今と同じくオーケストレーターの責務で、実装担当が生成物を新しいファイルとして作ってよいことにはしない（プロンプトの「同期をしない」は残す）
- 前提 4: 新しいファイルを作ってよい場所に制限を付けない（利用者の判断）。ただし作業ディレクトリ（リポジトリ）の外へは書かない
- 前提 5: 新しいテストのファイルは、`test_targets` に入れるなら今の `valid_targets` の条件（`--scope` のテストの置き場所の中）に従う。置き場所の外のテストを範囲テストへ入れる方法は設計で決める（未決 3）

## 対象範囲

含む:
- 実装・修正・最終ゲート修正の取り込みの範囲の判定で、この実行で作られたファイルを範囲の中として扱うこと
- 新しいファイルを範囲テスト・静的解析の範囲テスト・危険フラグ・最終ゲートの対象に含めること
- プロンプト（`implement.md` / `fix.md` / `final-fix.md`）の範囲の指示
- cross-refactoring の Skill 本文と確定仕様の範囲の説明

含まない:
- `refactor-scope.py` が組む範囲（PR の差分のファイルそのもの。#1484 の決定）の変更
- 範囲の外の**既存の**ファイルの改変を許すかどうかの方針の変更（設計で決める。未決 1）
- #622（範囲がファイル単位なので課題と関係の無い関数まで整理する）の解決
- 構造検査（1 ファイル 500 行）の上限の変更
- 差分予算の計算の変更（新しいファイルの行数の数え方は今のまま。分割は `EXTRACTION_TECHNIQUES` の倍率で受ける）

## 受け入れ条件

- [ ] 1: 実装の項目のコミットが、範囲の外のパス（範囲の中のファイルと別のディレクトリを含む）に新しいファイルを作り、範囲の中のファイルを変えたとき、取り込みは範囲の外として取り消さない。修正・最終ゲート修正のコミットでも同じになる
- [ ] 1a: 同じ実行の中で作られた新しいファイルを、後のコミット（同じ項目の後のコミット・修正・最終ゲート修正）が変えても、範囲の外として取り消さない
- [ ] 1b: 範囲の外の**既存の**ファイルを変えた・消したコミットは、今と同じく範囲の外として取り消す（退行しない）。範囲の中のファイルを範囲の外のパスへ名前を変えたコミットも同じ
- [ ] 2: PR 1732 の形（範囲の中の 1 ファイルが 500 行を超えて構造検査で落ち、修正担当がその一部を範囲の外の新しいモジュールへ移して 500 行以下に戻す）を再現するテストで、項目が取り消されずに採用まで進む
- [ ] 3: 新しいファイルを作った項目で、危険フラグ D1 が立ち、静的解析の範囲テストの対象に新しいファイルが入り、最終ゲートの全体テストが新しいファイルを含むworktreeで走る
- [ ] 3a: 項目のリファクタリング計画が新しいテストのファイルを `tests` に挙げ、`test_targets` に入れたとき、範囲テストがそのファイルを走らせる（置き場所の条件は前提 5・未決 3）
- [ ] 4: `implement.md` / `fix.md` / `final-fix.md` が、新しいファイルを作ってよいこと・置き場所を限らないこと・範囲の外の既存のファイルは変えないこと（未決 1 の結論に従う）・生成物を作らないことを書く
- [ ] 5: cross-refactoring の `SKILL.md` の範囲の説明と、範囲を扱う確定仕様（`docs/specifications/cross-refactoring-apply-intake.md` ほか範囲を書く文書）が、新しいファイルの扱いを受け入れ条件 1〜3 と同じ内容で書く。食い違う記述が残らない
