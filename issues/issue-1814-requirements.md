# #1814: cross-refactoring: リファクタリングの戦略（分割・抽出・移動・改名・インライン化・テストの共通化）を阻害する制約を外す

正は課題の本文（#1814）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

**cross-refactoring は、項目が新しいファイルを作ることを範囲の外として拒むため、ファイル分割・共通モデルの抽出といったリファクタリングの基本の手法が使えない。**

- 検査のプランは `--scope` を `refactor-scope.py --pr N` で組む。範囲は **PR の差分のファイルそのもので、ディレクトリへ広げない**（#1484 の決定。`plugins/ndf/scripts/refactor-scope.py` の冒頭）
- 範囲の判定 `path_in_scope` は前方一致だけ（`plugins/ndf/skills/cross-refactoring/scripts/refactor_lib/verify.py:34`）。新しく作ったファイルは差分に無いので範囲の外になる
- 実装・修正・最終ゲート修正のプロンプトは「対象範囲の外にあるファイルを 1 つも変更しない」と指示し（`prompts/implement.md:73`・`fix.md:68`・`final-fix.md:92`）、範囲の外を触ったコミットは項目ごと取り消される

## どこで見つけたか

PR 1732 https://github.com/devbasex/ai-plugins/pull/1732 （#1733）: 18 件が `plugins/ndf/scripts/lib/assignment.py` を 491 → 603 行にし、構造検査（1 ファイル 500 行）で 8 件が落ちた。修正担当は 43 回とも「上限へ戻すには新しいモジュールへ分けるしかなく、新しいファイルは対象範囲の外」と `not_fixed` を返した。#1793 で直さなかった項目は早く取り消すようになったが、**直す道（分割）が塞がったままなので、改善は取り消されるだけである。**

## 利用者の判断（2026-10-07）

- ファイル分割はリファクタリングの基本であり、範囲で禁じるのは融通が利かなさすぎる
- **新しいファイルの置き場所を「範囲の中のファイルと同じディレクトリ」に限る制約も付けない。** 分割して共通モデルを別の場所へ抽出することもできなくなるため

### 残す制約（安全に直結する）

## 目的

- リファクタリングの基本の戦略（ファイル・モジュールの分割、クラスの抽出、共通モデルの抽出、移動、改名、シグネチャの変更、インライン化、テストの共通化、不要コードの削除、改名と中身の変更を分けた複数コミット）の形の項目を、cross-refactoring が取り消さずに採用まで通せるようにする
- 安全に直結する制約（上の「残す制約」）は今のまま保つ。範囲（`--scope`）が持つ「提案の発散と変更の肥大を防ぐ」役目は、**戦略に伴わない既存のファイルの変更**について保つ

## コードで確かめた事実

- 範囲の判定はコミットが触ったファイルの一覧（`git show --name-only`。`gitfacts.py` の `commit_files`）を `path_in_scope` に通す。追加・変更・削除を区別しない
- 実装・修正・最終ゲート修正の取り込みは同じ関数 `verify_commit_basics` で範囲を見る（`verify.py`）
- 危険フラグ D1（項目の `path` と `tests` 以外を触った）は、新しいファイルを作ったコミットで立つ（`danger.py` の `d1`）。立てば全体テストが 1 度走る
- 静的解析の範囲テストは、項目のコミットが変えたファイルのうち worktree に残るものを対象にする（`gitfacts.py` の `changed_files`）
- `test_targets` は `--scope` のテストの置き場所の中にあることを求める。リファクタリング計画の `tests` に挙げたものは、まだ実在しなくてよい（`targets.py` の `valid_targets`）。入れられなければ `none` で、呼ぶ側が `no_target` で見送る（`targets.py:222`）
- 差分予算は見積の行数 × 倍率（2、`EXTRACTION_TECHNIQUES` は 3）で、超えたら取り消す（`verify.py` の `verify_diff_budget`）
- 期待値の一次判定は、テストのファイルごとに「前にあった値が後のファイルのどこにも無い」を `changed` とする（`verify.py` の `assertion_change` / `verify_test_changes`）。ファイルをまたいで値を探さない
- 実装の取り込みは 1 項目に 2 コミット以上あれば取り消す（`commands/implement.py:402`）。テストの追加のコミットにも同じ規則がある（`commands/implement.py:327`）
- 語彙の手法（`refactoring/references/vocabulary.md` の「手法」）に、クラスの抽出・モジュールの分割・インライン化・シグネチャの変更・テストの共通化の識別子が無い。観点の識別子（`vocabulary.py` の `VIEWPOINTS`。`mixed_responsibility`・`data_shape` ほか）は兆候の語彙に無い
- 「1 改善項目 = 1 コミット」は `CLAUDE.md` の cross-refactoring の節にも書かれている

## 前提

- 前提 1: 「新しいファイル」は、**この実行の起点のコミットに無く、この実行のコミットが追加したファイル**を指す（git の `A`）。同じ実行の中で作った後に別のコミット（同じ項目の後のコミット・修正・最終ゲート修正・別の項目）が直すのも、新しいファイルへの変更として範囲の中に数える。作ったコミットだけを許すと、修正担当が分割したファイルを直した時点で取り消される
- ~~前提 2: 名前の変更（`R`）・コピーは新しいファイルに数えない。範囲の中のファイルを範囲の外のパスへ移すのは、今と同じく範囲の外への変更として扱う~~ → 範囲の中のファイルを範囲の外の**まだ無いパス**へ移す（`R`）のは、移動の戦略として許す。移す先のパスは新しいファイルとして扱う。範囲の外の**既存の**パスを上書きする・消すのは、前提 6 の「既存のファイル」の扱いに従う（2026-10-07、対象の拡大）

- 前提 4: 新しいファイルを作ってよい場所に制限を付けない（利用者の判断）。ただし作業ディレクトリ（リポジトリ）の外へは書かない

- 前提 6（2026-10-07 追加）: 範囲の外の**既存の**ファイルへの変更は、項目の戦略に伴う呼び手の追従（項目が移動・改名・シグネチャの変更・インライン化・分割した名前の読み込みと呼び出しの書き換え）だけを許す。それ以外の変更は今と同じく取り消す。「伴う」の機械の判定は設計で決める（未決 1）

| E5a | 不要コードの削除の項目を、範囲テストの対象が無いので静的解析と全体テストで検証した | E5 で対象が `none` | 落ちれば修正へ回す | E3 |
| E6 | 修正担当が新しいファイルを直した、または新しいファイルへ分割した | 範囲テスト・構造検査の失敗 | 戦略に伴わない範囲の外の既存のファイルを触れば修正の範囲ごと取り消す | E5 |
| E7 | 項目を取り消し、その項目のすべてのコミットと、項目が作ったファイルが消えた | 直らない・衝突 | 取り消しの衝突は今と同じ扱い | E2, E2a |
| E8 | 最終ゲートが新しいファイルを含む全体で走った | 計画の終わり | 最終ゲート修正（E6 と同じ判定）へ | E5 |

E7 の順序の前提: 別の項目が、取り消す項目の作ったファイルを直していれば積み直しが衝突する。衝突の扱いは今の規則（衝突した項目だけを外す）に従う。
