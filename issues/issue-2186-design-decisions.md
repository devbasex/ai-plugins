# #2186 の設計: 決定の記録

頭の文書は [issue-2186-design.md](issue-2186-design.md) にある。根拠の行の MVV は ai-plugins のプロジェクト MVV（版 3）である。

## 決定の記録

### 決定 1: 他のリポジトリの Pull Request を自分の実行へ結び付けさせないため、token に `repo` を載せて受け口で照らす（#2216）

受け口は token を確かめた時点で、その実行のリポジトリを表を読まずに知れる。照合は `authorize.ts` の 1 か所で閉じ、受け口が実行の制御の集約（実行の表）を読まずに済む。受け口の仕様が token の期限より前の取り消しを「実行ジョブの状態（#2186 の集約）を読むことになる」として持たなかったのと同じ境目を保つ。リポジトリは実行の中で変わらない（I39 と同じく開始で決まる）ため、主張に載せても古くならない。

受け口がスプリントの実行からリポジトリを引く形は採らない。受け口が #2186 の表に依存し、事象 1 件ごとに読み出しが 1 回増える。

根拠: Value 6 / C2（MVV 版 3）

### 決定 2: 代わりの判断を一覧と詳細で見せ、通知を鳴らさないため、新しい種類 `decision.delegated` にする

#2206 の方針では、代わりの判断は人の答えを要らない。`attention` の `payload` に載せると、`attention` を受ける #2173 が知らせとして扱い、人の手を止める知らせが増える。新しい種類なら受け手は #2172 だけになり、既存の種類の形も変わらない（`schema_version` は 1 のまま）。各欄の上限を 4,000 字にするのは、3 欄が最大でも UTF-8 で 48 KB に収まり、256 KiB の上限で切り詰めが要らないためである。

`gate.reached` の種類「判断」に混ぜる形は採らない。判断は承認の依頼を作り、実行ジョブを終わらせる。

根拠: Value 2 / Mission（MVV 版 3）

### 決定 3: スプリントの途中で NDF の版が変わらないよう、正式版はタグ、開発版はコミットで固定する

全体の契約は「最初の実行ジョブで導入した版を `NDF_VERSION` として記録し、以後も同じ版を入れる」と決めた。正式版には版ごとのリリースタグ（`ndf--v<版数>`）があり、版数からタグが 1 つに決まる。開発版の `develop` は版数を上げずに進むため、版数だけでは同じ中身を入れ直せない。そこで開発版では `<版数>@<コミットの SHA>` を値にする。指示の形（1 字以上の文字列）は変わらない。版は実行の制御が開始の時点でマーケットプレイスの `plugin.json` を読んで決め、最初のジョブもその値を入れる。指示の `NDF_VERSION` が必須で、最初のジョブにも値が要るためである。

ランナーが入れた版を後から実行の制御へ知らせる形は採らない。指示の必須の項目を最初のジョブで空にできない。

根拠: Value 1 / P1（MVV 版 3）

### 決定 4: 費用の上限を実測で決めるため、打ち切りの時間を 8 時間、token の期限を 9 時間にする

実行ジョブ 1 本に当たる区間の実測は最大 18,031 秒で（頭の文書の「打ち切りの時間の実測」）、1.5 倍を時間へ切り上げて 28,800 秒にした。1.5 倍は、実測が 7 本しかなく、課題 4 件のスプリントが最大だったため、課題が多いスプリントの伸びを見込む幅である。token の期限はこれに 1 時間を足す。足す 1 時間は打ち切りの余白ではなく、`pending` の間（Fargate の起動）と、止めた後にランナーが送る時間に当てる別の時間で、打ち切りの時間を延ばさない。どちらも環境変数で変えられ、#2174 の台帳と見回りの止めた件数で見直す。

打ち切りを置かない形は採らない。止まった conductor のコンテナが費用を払い続け、I8 が守れない。

根拠: Value 3 / Value 10（MVV 版 3）

### 決定 5: 同時の 2 本の開始が上限を超えないよう、実行の枠を数の行で持ち、実行と同じトランザクションで増減する

上限の判定は「今の数」を `judgeLimits` へ渡す。GSI で数えてから書くと、同時の 2 本が同じ数を読んでどちらも通る。枠の行の `count` を読み、判定し、`count` が読んだ値と等しいことを条件に実行の行と一緒に書けば、2 本目は条件で失敗して読み直す（3 回まで、超えたら 503）。リポジトリごとの枠も同じトランザクションで増減し、登録を外す処理はその行を条件として確かめるだけで書かない。数え方は要求の前提 3 のとおり、終わりの状態でない実行を数え、承認待ちも含め、再開は数を変えない。

枠をアカウントの集約（#2170）の行に置く形は採らない。#2170 の表と持ち主が変わり、開始が 2 つの持ち主の表をまたぐ。

根拠: Value 6（MVV 版 3）

### 決定 6: NDF が今の工程で使う操作だけを許すため、GitHub App の権限を 6 つにする（C2）

| 権限 | 水準 | 何に使うか |
| --- | --- | --- |
| Metadata | 読む | 必須（GitHub の規則） |
| Contents | 読み書き | clone・ブランチの push |
| Pull requests | 読み書き | 設計と実装の Pull Request の作成・本文の更新・レビューの返信・マージ |
| Issues | 読み書き | 課題の本文の `## 進行`・コメント・ラベル・マイルストーン（棚卸しの順位の表を読む） |
| Checks | 読む | CI の結果を待つ |
| Actions | 読む | 失敗した CI のログを読む |

Webhook は `pull_request`・`check_run` を受ける（受け口の仕様のまま）。Workflows（`.github/workflows/` の変更の push）・Administration・組織の Projects は持たない。Workflows は CI を書き換えて秘密を持ち出せる権限で、取り込んだリポジトリのコードを動かすランナーに持たせると被害が大きい。ワークフローを変える課題では push が断られ、ジョブは `failed` で理由が残る。Projects が無いため、ランナーの中の NDF のボードの記録は失敗するが、NDF はボードの失敗で工程を止めない。権限の一覧は承認ゲート 1 で人が見る。

Workflows も含める形は採らない。ワークフローを変える課題は手元の NDF で進められる。

根拠: C2 / Value 2（MVV 版 3）

### 決定 7: 1 時間を超えるジョブでも push でき、App の秘密鍵をランナーへ渡さないため、導入の token をランナー向けの経路で渡し直す

導入の token は GitHub の仕様で 1 時間で切れ、実行ジョブは最大 8 時間動く。ランナーは実行ジョブの token で `POST /run-jobs/github-token` を呼び、その実行のリポジトリ 1 つに絞った token を 50 分ごとに取り直す。token は gh の設定ファイルへ書き、git は gh の資格の口を使う。gh は呼ばれるたびに設定ファイルを読むため、claude の子の環境を作り直さずに新しい token が効く。

起動のときに 8 時間ぶんの資格を渡す形は採らない。導入の token は 1 時間を超えて作れず、秘密鍵を渡せばランナーが任意の導入の token を作れる。

根拠: C1 / Value 4（MVV 版 3）

### 決定 8: ジョブ同士が互いの状態を読めないよう、状態の置き場は署名つき URL でだけ渡し、ランナー向けの経路は `INGEST_URL` と同じ origin に置く

ランナーは取り込んだリポジトリのコードを動かすため、タスクの役割に S3 の権限を持たせると、別の実行の鍵を推せば読める。実行の制御がジョブの token を確かめ、その実行の鍵だけの 15 分の URL を返せば、タスクの役割は S3 の権限を持たない。経路の場所は指示に新しい項目を足さずに決めるため、`INGEST_URL` の origin に `/run-jobs/*` を置く（全体の契約は API の入口を 1 つとしている）。#2173 の答えの経路も同じ origin を前提にする。

指示に `RUN_JOBS_URL` を足す形は採らない。契約の変更は #2216 と #2206 の 2 点に限る（要求の対象範囲）。

根拠: Value 6 / C1（MVV 版 3）

### 決定 9: どの実行の形態でも候補に理由を付けるため、課題の候補は API の中でサービスの Bedrock を呼び、使える量に数えない

候補はスプリントの実行より前に作るため、実行ジョブとして動かすと指示の `START` に新しい値が要り、契約が変わる。`local` のアカウントは Claude の資格をサービスに預けないため、利用者のキーで呼ぶ形では理由を作れない。入力は順位の表の行と課題の題だけにし、出力を 1,500 token までに絞る（1 回 1 セント前後）。この費用は利用者の月の token に数えず、ログに 1 行残す。Bedrock が失敗したら、順位の表の順のまま理由を `note` に「AI が理由を作れなかった」と出し、利用者は手で選べる。候補は棚卸しの順位の表を持つ、番号が最も小さい開いたマイルストーン（`<2 桁の連番> <主題>` の形）の行から作る。表が無ければ開いている課題を新しい順に 10 件にする。

候補の費用を `managed` の月の token に数える形は採らない。台帳は #2174 が持ち、実行の外の使用量を積む口が無い。

根拠: Value 10 / Mission（MVV 版 3）

### 決定 10: 別のアカウントが他人のロールを引き受けさせられないよう、外部 ID をサービスがアカウントごとに作る

外部 ID は `ndf-factory:<account_id>` にする。AWS の文書は、外部 ID を顧客が選ばずサービスが顧客ごとに一意に作ることを求め、秘密である必要は無いとする。アカウントの ID はサービスが UUID で作り、利用者が選べない。キーの置き場の値に `external_id` を一緒に書くため、ランナーは別の値を付けられない。画面は外部 ID と信頼の設定の例を出す。

利用者が外部 ID を入れる形は採らない。他人のロールの ARN と外部 ID を知る者が、そのロールを引き受けさせられる。

根拠: C1 / C2（MVV 版 3）

### 決定 11: `byok` のジョブがサービスの Bedrock を呼べないよう、タスク定義を形態ごとに 2 つにする

`managed` のタスクの役割は Bedrock を呼べる。同じ定義で `byok` を動かすと、取り込んだリポジトリのコードがサービスの Bedrock を呼べる。`byok` の定義の役割は Bedrock を持たず、`AssumeRole` とキーの置き場の読み出しだけを持つ。`managed` の役割はキーの置き場を読めない。名前は既存の `RUNNER_TASK_DEFINITION_ARN` を `managed` に当て、`RUNNER_BYOK_TASK_DEFINITION_ARN` を足す。

1 つの定義で両方を動かす形は採らない。最小の権限から外れ、費用の出所が利用者のキーかサービスかが権限で決まらない。

根拠: C1 / Value 10（MVV 版 3）

### 決定 12: Google でログインした利用者も登録できるよう、身元は登録のたびに GitHub App の利用者の認可で確かめ、結び付けを保存しない

利用者の認可の token で導入の一覧と、各導入で利用者が届くリポジトリを引けば、要求の前提 2 の 2 条件が 1 回で確かめられる。GitHub でログインした利用者の token は Cognito が持ち、サービスに無いため、どちらの IdP でも同じ流れになる。認可の token は換えた要求の中で使い捨て、候補は署名した 10 分の証明で画面へ返す。登録はその証明と、登録の直前の導入の token の作成（そのリポジトリに絞る）で確かめる。

GitHub の利用者の ID を利用者に結び付けて保存する形は採らない。保存した結び付けは利用者が GitHub 側で権限を外しても残り、登録の時点の確かめにならない。

根拠: C2 / C3（MVV 版 3）

### 決定 13: 承認待ちの間に動くジョブを残さないため、ジョブと実行の状態の移りはタスクの停止の後だけで行う

ランナーの `job.finished` を受けた時点では、コンテナはまだ動いている。停止の知らせで `job.finished` を読み（無ければ `control` で書き）、結果に従って移せば、移りの経路が 1 つになり、`awaiting_approval` の実行には動くジョブが無い（I8）。答えが停止の知らせより先に来たときの再開の要求は `sprint_run_busy` で断り、#2173 が呼び直す。

受け口の追記を引き金に状態を移す形は採らない。受け口が実行の制御を呼ぶことになり、#2171 の処理を変える。

根拠: Value 6（MVV 版 3）

### 決定 14: 利用者の消す意図どおりに働くよう、持ち込んだキーは復元の期間を置かずに消す

消去は持ち主が画面で選んだ操作で、取り消しの期間を置くと値が Secrets Manager に残る。動いている `byok` のジョブはキーを読めなくなり、次に読む時点で `failed` になる。
7 日の復元の期間を置く形は採らない。消したと思った値が残り、I38 の「値を返す経路を持たない」と食い違う。

根拠: C3 / C1（MVV 版 3）

### 決定 15: Size 13 の変更をレビューできる大きさにするため、実装は 1 つの課題のまま、依存の順に 3 本の Pull Request へ分けるよう計画へ渡す

| 順 | 中身 | 先に要るもの |
| --- | --- | --- |
| 1 | 契約の 2 点・受け口の照合・実行の制御・ランナー向けの経路・停止の知らせと見回り | 無し |
| 2 | ランナー（`factory/runner/`）とイメージ | 1 |
| 3 | 取り込み・キーの持ち込み・課題の候補・3 つの画面 | 1 |

2 と 3 は互いに依存しないため並べて進められる。設計の課題は 1 つのままにし、分けた子課題を起こさない。

課題を 4 つに分ける形は採らない。不変条件（I34・I9）が取り込みと実行の制御をまたぎ、受け入れ条件を課題ごとに閉じられない。

根拠: Value 1 / Value 10（MVV 版 3）
