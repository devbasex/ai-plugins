  - このうち、自然に当たった 158 回に余計に掛かる起こす費用は 1,513,249

  - 引継ぎの費用は含めない
  - 組の取り方はこの節の頭の段落のとおりで、`S` は組の前の応答の `usage` の 3 つの数の合計である
- 起こす費用の比 0.115 は 13,351,993 ÷ 116,007,698 である。自然に当たった 158 回に掛かる起こす費用を除くと、比は 0.102 になる。式は (13,351,993 − 1,513,249) ÷ 116,007,698 = 11,838,744 ÷ 116,007,698 = 0.102 である。分母は同じで、自然に当たった回は分母の何もしない費用に入っていない
- 余白の判断: 自然に当たる待ちの費用を足しても比は 0.102 から 0.115 に上がるだけで、余白 600 秒（50 分で起こす）を変えるほどではない。50〜55 分は 39 組のうち 39 組が当たりで、55〜60 分（120 組のうち 106 組）より外れが少ないので、余白を詰めずに 600 秒のままにする
- この 435 回には、バックグラウンドの作業を待たない待ち（利用者が離れていた・会話を後で再開した）も含む。会話の記録からは、その時点でバックグラウンドの作業か監視が残っていたかを決められない（Stop の入力の列は記録に残らない）。そのため、対象の待ちだけに絞った分布は、起こす記録が溜まってから集計で出す（決定 9）。起こすのはバックグラウンドの作業か監視を待つ子だけなので、実際に当たる待ちはこの一部である

### 起こす対象を縮めた後の費用の見込み（2026-11-24）

決定 16 で起こす対象を「作業が 1 件以上残る子」に縮めたので、「会話の記録の集計と `asyncRewake` の実測」の 435 回の見積りを、待ちの種類で分けて数え直した。期間・組の取り方・規則（Opus 5.5、`r` 0.05・`w` 2・起こす間隔 3,000 秒・`d` 2,000）は元の見積りと同じで、間の下限だけを 3,000 秒にした。待ちの種類の見分け方は上の「見分け方」と同じである。

各回の起こしたい回数を `n = floor(間 ÷ 3,000)`、実際に起こす回数を `m = min(n, n_max)` とする。式は次のとおりである。

- 何もしない費用: 自然に外れた回の `(w − r) × S` の和
- 起こす費用: 各回の `m × (r × S + d)` の和に、最後に保てた時点から待ちの終わりまでが 3,600 秒以上の回の `(w − r) × S` を足す
- 比: 起こす費用 ÷ 何もしない費用

| 待ちの種類（3,000 秒以上・2026-10-24〜11-22・全会話） | 回数 | 自然に当たった | 何もしない費用 | 起こす費用 | 比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 全部（元の見積りの数え直し） | 445 | 159 | 122,253,598 | 13,901,302 | 0.114 |
| 作業が 1 件以上残る（縮めた後に起こす待ち） | 291 | 142 | 51,928,921 | 4,316,828 | 0.083 |
| 監視だけ | 0 | 0 | 0 | 0 | — |
| 質問の表示中 | 127 | | | | 起こさない |
| 何も残っていない | 27 | | | | 起こさない |

- 元の 435 回との差の 10 回は、2026-11-22 の後に追記された記録の分である（1 時間超の 276 回が 282 回になったのと同じ）
- **縮めても見込みは変わらない。** 3,000 秒以上の待ちに、監視だけの待ちは 1 回も無かった。縮めて起こさなくなる待ちが無いので、節約の額も比も縮める前と同じである
- 元の約 12%（0.115）は、起こさない待ち（質問の表示中・何も残っていない）まで分母と分子に入れた値だった。起こす対象の待ちだけで数えると約 8%（4,316,828 ÷ 51,928,921 = 0.083）になる
- 11.0.0 の前の「作業」には、10 系の待ちのスクリプトを背景で打っていた待ちが混ざる（上の表の注と同じ）。それらが監視だったなら、作業の待ちの回数と額はこれより少ない

### 待ちの上限を 3,000 秒に上げた後の確かめ（2026-11-24）

11.0.33 の即時修正（#4463・PR #4464）で、待ちのコマンドが知らせの無いまま戻るまでの上限が 3,000 秒に上がった。上げる前は、`ndf lanes wait` が 540 秒、`ndf plan wait`・`ndf progress wait` の既定が 600 秒だった。決定 16 の判断が変わらないかを、上限より後に起きる 2 つの遅れで確かめた。3,000 秒の上限で動いた記録はまだ無いので、上限によらない遅れを 540 秒・600 秒の期間の記録から測った。

期間は 11.0.0 の後（2026-11-18 20:00 JST〜11-24）、対象は中継の子（上の「見分け方」の 326 件の会話）のメインの会話である。

- **張り直す応答の遅れ**: 背景で打った待ちのコマンドの完了の知らせの時刻から、次のモデル呼び出しの始まりまでの秒。知らせは `<task-notification>` の `tool-use-id` が起動と一致するものとする。始まりは会話の記録の `api-request` とし、無ければ次の応答の記録の早い方とする
- **戻りの超過**: 起動（`tool_use` の記録）から知らせまでのうち、上限を越えた秒。知らせまでが上限以上の回だけを数えた
- **起動から応答の終わりまで**: 待ちのコマンドの起動（`tool_result` の記録）から、その応答の最後の記録（Stop の前の `assistant`）までの秒。起こす hook の起こす時点は、この最後の記録から数える
