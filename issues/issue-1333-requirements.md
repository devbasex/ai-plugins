## 例: carmo-system-console で NDF を回し始めたとき

今（ndf 10.17.33）:

1. `/ndf:development-workflow` の手順 0 は `.ndf/worktree.json` があるか（中身は `version` だけ）を見て通る。ほかの宣言は作らない
2. `supervise.py new check` は、テストの実行器を ai-plugins の形（`uv run ... pytest`、全体テストを手元で走らせる、打ち切り 1800 秒）のまま雛形へ入れる
3. PHPUnit のテストはコンテナ越し（`docker compose exec app ...`）で、全体を直列に走らせると約 64 分かかる。NDF はこれを知らないまま進み、`init` か最初の全体テストで止まる

変えた後:

1. 手順 0 で宣言が無いと分かると、解析が走る。言語（PHP 8.3・Laravel）・実行器（PHPUnit）・コンテナ越しの実行・CI の JUnit から合計した全体テストの所要（約 3,827 秒）・起点（`main`）・配布（`main` へのマージで本番）・課題の正本（Redmine と GitHub Issues）を測る

## 目的

- **NDF が、使い始めたリポジトリの形で動く。** ai-plugins の形（pytest を uv で・`develop` 宛て・版数を持つプラグインの配布）を、宣言の無いリポジトリの既定にしない（MVV の Value 6）
- **プロジェクトごとの違いを、手で書かずに宣言へ残す。** 今は ai-plugins で課題ごとに手で書いた宣言を、解析で作る
- **後続の課題（#1334 のテストの戦略・G3 の配布・G5 のマージ・G7 の課題の正本）が読む 1 つの入力を用意する**

## 前提

- 前提 1: 解析の入り口は `development-workflow` の手順 0 である（課題の案）。4 ランタイムで同じに働かせるため、hook ではなく手順の本文から呼ぶ（手順 0 の「拒否しない」の理由と同じ）
- 前提 2: 解析は、NDF の工程を止めない。解析が失敗した・時間を超えたときは、その旨を出力に出し、宣言を書かずに（または測れた項目だけを書いて）手順 1 へ進む。手順 0 の exit=1 と同じ扱いにする
- 前提 3: 既存の宣言の値は上書きしない。手で書いた値を正とし、解析は欠けた項目だけを足す。解析の値と既存の値が食い違えば、食い違いを出力に出すだけにする（ai-plugins の宣言は手で書いた正本である）
- 前提 4: 宣言を書き出すときに利用者の承認を待たない（課題の元の記載: コミットは取り消せるので承認ゲートにしない）。書き出したファイルと差分を出力に出し、確認は差分のレビューで行う
- 前提 5: 解析は外部へ何も送らず、リポジトリにも GitHub にも書き込まない。読むのはworktreeのファイルと、`gh` で取れる CI の結果・ブランチ・ruleset だけである。`gh` が使えない・権限が無いときは、その項目を「不明」として記録する
- 前提 6: 宣言に秘密を書かない。`.env` などの値・トークン・接続文字列の中身は読まない（有無と置き場だけを記録してよい）
- 前提 7: サンプル 4 つへの宣言のコミットは、この課題では行わない。検証は、書き出し先を一時ディレクトリにするか、サンプルのworktreeへ書いて差分を見た後で消すかで行う（サンプルは別の組織のリポジトリである）
- 前提 8: 課題 2 は #1334 である。#1334 の側で宣言を読む実装をする。この課題が満たすのは、#1334 が戦略を選ぶのに要る項目（P2・P3・P4・P5）を宣言が持ち、その形が schema で公開されていることである
- 前提 9: 「古い」の判定は決定論で行い、LLM を呼ばない。判定に使う入力の一覧は設計が決める
- 前提 10: 課題の正本（P8）は記録するだけで、工程をその正本に合わせる変更は #479 が扱う。配布の形（P7）を使う雛形の変更は G3、マージの形は G5 が扱う

## 対象範囲

含む:

- 解析（決定論の測定と LLM の判断）と、宣言の書き出し
- 解析を走らせる時点（手順 0）と、「古い」の判定
- 宣言の置き場と形の決定、schema の用意（`supervise.json` を含め、schema の無い宣言に schema を付けるか、まとめたファイルの schema を作る）
- 既存の 10 種類の宣言の扱い（そのまま保つか、まとめたファイルへ移すか。移すなら移し方）
- 宣言が無いと ai-plugins の形で動く箇所のうち、調査が挙げたもの: `merged-steps.py:220` の `develop` の既定、`workflow-modes.md:202` と `cross-refactoring/SKILL.md:121` の `origin/develop` の直書き、doc-lint と `.md` の文言テストの拒否を宣言で切れるようにすること
- 指示書の状態（P10）を見つけて、出力で案内すること（古い `CLAUDE.ndf.md` の読み込み・指示書が無いこと）
- 4 つのサンプルと ai-plugins での解析の実測

含まない:

- #1334 のテストの戦略の選び方と、supervise・cross-refactoring の雛形の打ち切り時間・範囲テストの変更（G2）
- 配布の雛形の変更（G3）、worktreeの環境（`vendor/` など。G4）、マージと PR の運用（G5）、言語ごとの判定（G6）、課題の正本に合わせた工程の変更（#479 / G7）、cross-review の再開と hook（G8）
- 指示書（AGENTS.md / CLAUDE.md）を解析が書き換えること（案内だけにする）
- サンプル 4 つへの宣言のコミット（前提 7）
- 解析で決めた値を使って、既存の手で書いた宣言を直すこと（前提 3）

- [ ] AC12: with-ai-dev で解析を走らせると、古い NDF の案内（`CLAUDE.ndf.md`）の読み込みが出力で案内される。carmo-contractors-app では、指示書が無いことが案内される。どちらでも指示書のファイルは変わらない
- [ ] AC13: 宣言には、秘密の値（`.env` の中身・トークン・接続文字列）が入らない。サンプル 4 つの宣言を `grep` で見て、`.env` の値と一致する文字列が無い
- [ ] AC14: 宣言の形が schema で公開されており、#1334 の設計が P2〜P5 の項目をその schema で参照している
- [ ] AC15: 解析は、サンプルのリポジトリにも GitHub にも書き込まない（解析の前後で、サンプルの `git status` の差分が宣言のファイルだけである。GitHub の課題・PR・ブランチが増えない）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 宣言が新しいときの判定（AC4）は決定論だけで、4 つのサンプルと ai-plugins のどれでも 5 秒以内に終わる。解析の決定論の測定は、それぞれ 120 秒以内に終わる（超えた項目は「不明」にする） |
| 運用・保守性 | 解析の測定と判断の結果は、宣言とは別に出力（または記録）へ残り、どの値が測った値でどれが判断した値かが分かる |
| 移行性 | 既存の 10 種類の宣言を持つリポジトリ（ai-plugins）で、宣言を読む Skill とスクリプトの振る舞いが変わらない。移すなら、移す前の形を読む手段を残すか、移し方を文書に書く |
| セキュリティ | 前提 5・6 のとおり、外部へ送らず、秘密の値を読まない・書かない（AC13・AC15） |
| システム環境 | 4 ランタイム（Claude Code・Codex・Kiro・agy）の手順 0 から同じに呼べる。決定論の測定は Python 3 標準と `git`・`gh` だけで動く |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。手順 0 の出力の `宣言:` の行に解析の結果が加わる。宣言の置き場を変えるなら、宣言を読む全スクリプトの読み取りが変わる（互換の扱いは設計） |
| データ | `.ndf/` のファイルが増える（か、まとめたファイルへ移る）。既存の値は上書きしない |
| 既存の振る舞い | 宣言の無いリポジトリで、後片付けの起点が `develop` から origin の HEAD に変わる。doc-lint と `.md` の文言テストの拒否を宣言で切れる |

## 前提とする取り決め

## 境界

| 区分 | 内容 |
