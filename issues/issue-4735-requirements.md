# 要求仕様書: Issue 4735 要求仕様書を Issue のコピーにしない

元の Issue: https://github.com/devbasex/ai-plugins/issues/4735

このファイルが要求の正である。Issue 4735 の本文は起票時の報告のまま残し、本文からこのファイルを作り直さない。この Issue では、このファイルが本文と一致するかを確かめない。Issue の本文を要求仕様で書き換えないことは、この Issue が求める形そのものである。

## 何が起きたか

2026-11-28、Issue 4543（設計書と PR の概要で、今の状態とこれから変えることを書き分ける。 https://github.com/devbasex/ai-plugins/issues/4543 ）の実装の途中で、工程が止まった。レビュー役の AI が要求仕様のファイル（Issue の本文のコピー）に指摘を出し、直し役の AI が「Issue の本文を書き替えてよいか」を決められなかったためである。利用者はこの問いに対して、「要求仕様書が Issue のコピーであり続ける必要がそもそもないのでは？」と指摘した。

利用者の考え方は次のとおりである。Issue は、不具合や課題をいち早く報告して対応を求める文書である。要求仕様書は、その報告をもとに現状を調査・分析し、根本からの解決を求める文書である。

## 種類

機能追加（今の手順書 `requirements-design` は「仕様の正は課題の本文である」と約束しており、その約束自体を変えるため）

## 今の姿

- 要求仕様の正は GitHub の Issue の本文である。`standard` の変更では、本文の「進行」より前を仕様のコピー（`issues/issue-<番号>-requirements.md`）へ写し、設計 PR と一緒にコミットする（`plugins/ndf/skills/requirements-design/SKILL.md` の手順 7）
- コピーを置く理由は、設計と要求を同じ差分でレビューするためである
- コピーは手で直さない。直すときは本文を直してからコピーを作り直す。設計 PR を出す前に、コピーと本文が一致するかを確かめる（`plugins/ndf/skills/design/SKILL.md` の 216 行目付近）
- 要求と受け入れ条件の工程は、要求を `gh issue edit <番号> --body-file` で本文へ書く。そのため、起票した人の報告は要求仕様で置き換わる
- 本文から要求を読む処理がある。確かめたものは次の 2 つである
  - モードの判定の材料を集めるコマンド（`ndf materials`、`plugins/ndf/src/ndf/domains/materials/cli.py`）。本文の「種類」「影響」を読む
  - 受け入れ条件の確認の記録（`ndf loop acceptance`、`plugins/ndf/src/ndf/domains/loop/acceptance.py`）。受け入れ条件ごとに、いつ（マージの前かリリースの後か）どう確かめるかを残すコマンドである。本文の受け入れ条件を読み、確認の記録を本文へ書き戻す
- 本文には、工程が進み具合を書く「進行」のセクションも置かれる。Issue を閉じるときは、満たした受け入れ条件のチェックボックスに印（`[x]`。以下、受け入れ条件のマーカー）が付く

## 何を足すか・変えるか

| | 今 | 変えた後 |
| --- | --- | --- |
| 要求の正 | Issue の本文 | 要求仕様書のファイル |
| Issue の本文 | 要求と受け入れ条件で置き換わる | 起票した人の報告のまま残る |
| 要求仕様書の中身 | 本文のコピー | 報告をもとに調べた現状・根本原因・解決の要求・受け入れ条件。元の Issue へのリンクを持つ |
| 要求仕様への指摘の直し方 | 本文を書き替えて、コピーを作り直す | 要求仕様書のファイルを直す（差分でレビューできる） |
| 本文とコピーの一致の確かめ | 設計 PR の前に行う | 無くなる |
| 要求を読む処理 | 本文を読む | 要求仕様書を読む |
| Issue と要求仕様書の数の関係 | 1 対 1 | 複数の Issue が 1 つの根本原因を持つとき、1 つの要求仕様書にまとめてよい |

## 今の利用者への影響と互換

- NDF の工程を使うプロジェクトでは、要求と受け入れ条件の工程の後も Issue の本文が報告のまま残る。受け入れ条件を GitHub の Issue の画面で読んでいた人は、要求仕様書のファイルを開くことになる
- 今、本文に要求を持っている開いた Issue について、本文から要求を読み続ける互換は持たせない（NDF が広く使われる段階に入るまで後方互換は要らない、という方針による）

## なぜ困るか

- 本文と仕様のコピーの 2 か所を一致させる手順と確かめが要り、そこで指摘と停止が出る（Issue 4543 で実際に止まった）
- 要求仕様への指摘を直すには、GitHub 上の本文を書き替えるしかない。本文は差分でレビューできず、設計書などほかの文書と扱いが違う
- 起票した人の報告が要求仕様で置き換わり、何が報告されたのかが本文から消える

## 目的

Issue を報告のための文書に戻し、現状の調査・分析にもとづく要求を、要求仕様書だけに持たせる。

## 対象範囲

含む:
- 受け入れ条件のマーカーと確認の記録の扱いを決める。受け入れ条件が本文から要求仕様書へ移ると、今のままでは成り立たないためである
- 要求と受け入れ条件の工程（`requirements-design`）が、要求を要求仕様書のファイルに書き、Issue の本文を書き替えないようにする
- 本文と仕様のコピーを一致させる手順と確かめ（`design` の手順 7 など）をなくす
- 今、本文から要求（種類・影響・受け入れ条件）を読む処理を、要求仕様書から読むように変える
- 要求仕様書から元の Issue へのリンクを持たせる
- 複数の Issue を 1 つの要求仕様書にまとめる形を許す
- この変更に合わせて、手順書・用語集・コントラクトの説明を直す

含まない:
- 過去の Issue の本文を報告の形へ書き戻すこと
- 工程が本文に書く進行の記録（「進行」のセクション）の置き場所を変えること
- Issue の起票の形（報告の書き方）を変えること
- Issue 4543 の進め方を変えること（当面「AI は本文を書き替えず、利用者の判断が要る指摘として返す」のまま）

## 前提

- 前提 1: 要求仕様書は追跡するファイルとしてリポジトリに置き、設計 PR と同じ差分でレビューする（今の仕様のコピーの置き方を引き継ぐ）
- 前提 2: 普及の段階に入るまで、今の Issue の本文に要求があっても読めるようにする互換は持たせない

## 受け入れ条件

- [ ] 1. 標準の開発手順で要求仕様書を作る前と後で、Issue の報告の部分が同じ文章である。作業前に「進行」欄が無ければ、作業前の本文全体と、作業後の「進行」欄より前を比べる。欄があれば、前後とも「進行」欄より前を比べる
- [ ] 2. 同じ工程のあと、要求仕様書のファイルがあり、元の Issue の URL を持つ。複数の Issue をまとめた要求仕様書は、そのすべての URL を持つ
- [ ] 3. `requirements-design` の手順に、要求を Issue の本文へ書く手順（`gh issue edit --body-file` で要求を渡す手順）が無い
- [ ] 4. 設計 PR を出す前の「仕様のコピーと Issue の本文が一致するか」の確かめが、手順書にもコードにも無い
- [ ] 5. 要求仕様書への指摘を、直し役の AI が要求仕様書のファイルの差分として直せ、Issue の本文の書き替えを要しない
- [ ] 6. 設計承認ゲートの承認資料が、「種類」と「影響」を要求仕様書から読む。Issue の本文に「種類」「影響」が無くても承認資料ができる
- [ ] 7. 受け入れ条件の確認の記録（`ndf loop acceptance`）が、受け入れ条件を要求仕様書から読む。Issue の本文に受け入れ条件が無くても記録できる
- [ ] 8. 今、Issue の本文から要求（種類・影響・受け入れ条件）を読んでいるほかの処理も、要求仕様書から読む。どの処理が当たるかは設計で洗い出し、設計書に一覧を置く
- [ ] 9. 2 つの Issue を 1 つの要求仕様書にまとめたとき、承認資料と受け入れ条件の確認の記録が、両方の Issue について作れる
- [ ] 10. 工程が Issue の本文に書く「進行」のセクションの更新は、今までどおり動く（退行しない）
