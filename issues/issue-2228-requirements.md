## 目的

- 課題が閉じた時点で、その実行の最終工程（棚卸しの前に最後に通る工程）が終わっているようにする。閉じた課題は棚卸しの対象から外れ、不合格の条件や未通過の工程が見えなくなるためである（#2119 の s2086 の経緯）
- 閉じる時点の決まりを 1 か所に置き、スクリプト・まとめのプラン・Pull Request の本文の規則がそれに従うようにする。今は文書の決まりと雛形の並びが食い違い、決まりを守るのは呼ぶ側（conductor・引継ぎ文書）の手順の並びに頼っている

## 前提

- 前提 1: この要求が扱う「閉じる経路」は次の 3 つである。(a) GitHub が Pull Request のマージの時点に、本文の closing keywords で課題を閉じる（#2082）、(b) `sprint-close.py` を、まとめのプラン・conductor・Skill の手順のどれかが打つ（#2119）、(c) `sprint-close.py` がボードの `Status` を `Done` にしたことで、ボードの `Auto-close issue` が課題を閉じる（(b) の中の 1 手で、(b) の判定を通らないと起きない）
- 前提 2: 「最終工程」は、`progress-tracking` の「スプリントを閉じる」の定義（棚卸しの前にその実行で最後に通る工程）と、`development-workflow` の工程表（`workflow-common.sh` の `WF_STAGE_MATRIX`）のモードごとの必須・条件付きの区分で決まる。`light` は `配布`、`standard` と `legacy-refactor` と `documentation` は `振り返り`、`operation` はその実行で通る条件付きの工程による
- 前提 3: 親 A（#2227）の結果 JSON の共通形式が先に入る。工程の通過を判定する材料は、#2227 の形式の結果（`status` が `ok` のもの）か、それと同じ版に入る記録から取る。今の通過記録（`progress-record.sh` が積むファイル）と本文の `## 進行` は「工程に入った時点」の記録で、工程を終えたことを表さないため、それだけで通過とは読まない
- 前提 4: `--record-pr 0`（本番の記録なし）と `--record-pr unknown`（記録の置き場が分からない）の今の扱いは変えない。工程の通過の判定は、その上に足す閉じる条件である
- 前提 5: 子の 2 件（#2082・#2119）の受け入れ条件は、この課題の受け入れ条件に含める（受け入れ条件 10）。設計はこの課題で 2 件をまとめて行い、実装の Pull Request を子ごとに分けるかは計画で決める
- 前提 6: 振り返りの記録は、記録の Pull Request のコメントとして投稿される（`retrospective` の今の決まり）。この要求はその置き場を変えない

## 対象範囲

含む:
- `progress-tracking` の「スプリントを閉じる」を閉じる時点の正本として、「最終工程を終えてから閉じる」の判定の材料と順序を書く
- `sprint-close.py` の入口で、課題ごとに最終工程を終えたかを判定し、終えていない課題を閉じない
- まとめのプラン（`supervise_lib/sprint.py` の `close_plan` と `sprint_close_steps.py`）の並びを正本に合わせる
- `pr` の宛先の表と「closing keywords は本文だけに書く」を、既定ブランチ宛の Pull Request で closing keywords を残さない形にする。closing keywords を持たない Pull Request から閉じる課題を集める手段（`--issues` か、それに代わるもの）を `sprint-close.py` に持たせる
- 正本を写している文書（`retrospective`・`release-verification`・`release`・`development-workflow` の references）の参照の付け替え

含まない:
- 利用者が手で `gh issue close` や GitHub の画面で閉じること（NDF の経路ではない）
- 棚卸しが「やらない」と決めた課題を `not planned` で閉じること（`backlog-refinement` の `no-work.md`。工程を通らずに閉じるのが意図の経路で、最終工程の判定の対象にしない）
- `check-trigger.py` が Pull Request を閉じること（課題ではない）
- 親 A（#2227）の結果 JSON の形式そのものの変更
- 他のリポジトリ（例: volareinc/carmo-screening）の既存の課題・Pull Request の書き直し

2. - [ ] 最終工程を終えていない課題（例: 振り返りを通るモードで振り返りの記録が無い）を含めて `sprint-close.py --record-pr <記録のPR> --issues <番号>` を打つ → `--with-verification` の有無にかかわらず、その課題は閉じず、ボードも `Done` にならず、結果 JSON の `items` に `kept_open` と、終えていない工程の名前を含む `reason` で載る（マージ前: `gh` と判定の材料を差し替えたテスト）
