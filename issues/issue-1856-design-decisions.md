# #1856 の設計: 決定の記録

設計文書の本体は [issue-1856-design.md](issue-1856-design.md) にある。

## 決定の記録

### 決定 1: 利用者が「工数算出のための Skill」として他のプロジェクトから呼べるよう、入り口を新しい Skill `estimate` にする

利用者は見積もりを課題の棚卸しとは別の場面（ほかのプロジェクトで 1 件の作業を見積もる）で使う。`backlog-refinement` は課題の一覧を GitHub から読み、順位とマイルストーンを書き換える工程で、1 件を見積もるだけの呼び出しに棚卸しの手順と前提（課題の一覧・宣言）を背負わせることになる。新しい Skill は入り口と規約の置き場だけを持ち、算出は共通の部品に置く。

既存の Skill へ統合する案は採らなかった。統合先の候補の `backlog-refinement` は棚卸しの工程 Skill で、課題番号の無い「作業の説明」を見積もる入り口を持たせると、Skill の説明と起動の条件が 2 つの用途に割れる。

根拠: Mission / Value 5（MVV 版 2）

### 決定 2: 規約を写さず 1 か所に置くため、正本を `skills/estimate/references/rules.md` にする

A・H・L・C・完了条件・実行の構成・着手前の 6 項目・類似の実績の選び方・実績が足りないときの扱い・Size への換算の規則を、この 1 ファイルが持つ。`backlog-refinement` の `ranking.md` の「大きさは AI の実施の費用で付ける」と `no-work.md` の費用の見積もりは、この規約への参照と `estimate.py predict` の手順へ置き換える。規約は Skill の配布物の中にあるため、ほかのプロジェクトでも同じ版の規約が読める。

`docs/` に置く案は採らなかった。`docs/` は配布されず、ほかのプロジェクトの AI が読めない。

根拠: Value 7 / Value 5（MVV 版 2）

### 決定 3: 失敗・中断を含む実績を失わないため、実績を新しい追記だけの記録（事象の記録）に持つ

supervise の実行が、始まり・ステップの終わり・実行の終わりを `actuals.jsonl` へ 1 行ずつ追記する。中断は書き手が落ちても数えられるよう、行の種類にせず「終わりの行が無い実行」として読む側が導く。既存の記録はどれも実績の正本にできない。`state.json` と `report.md` は流し直すたびに上書きされ、`step-history.jsonl` は成功と承認ゲートで止まった実行だけ、配分の履歴は最終ゲートを通った実行だけを積み、`progress.jsonl` は実行の終わり方を持たず課題番号も無い。

`step-history.jsonl` に失敗の行を足す案は採らなかった。遅れの見張りの想定時間が変わり（受け入れ条件 12）、費用と課題番号も持たない。既存の記録から読むだけで済ませる案も採らなかった。終わり方（成功・失敗・取り消し）を持つ記録が無い。

根拠: Value 3 / Value 6（MVV 版 2）

### 決定 4: 集計を 1 か所に持つため、`lib/estimate_stats.py` を作り、既存の 3 系統は値を変えずにその関数を呼ぶ

`slow_step.expected_for`（直近 N 件の中央値）・`measure_ci.ndf_record`（直近 10 件の中央値）・`allocation._per_unit` と `scope_seconds`（直近 10 件の Σ秒÷Σ件数・最大）を、集計の関数へ置き換える。窓の既定 10 は集計のモジュールだけが持ち、3 系統は自分の設定（`SlowConfig.window` など）を引数で渡す。係数・下限・既定値（`factor`・`floor` など）は各系統の意味なので、そのまま各系統に残す。

計測と報告のスクリプト（`run_metrics.py`・`skill-stats.py`・`token-usage.py`・`structure-baseline.py`・実験版）は対象にしない。見積もりの材料を作らず、受け入れ条件 12 の対象にも入っていない。

根拠: Value 6（MVV 版 2）

### 決定 5: 類似の実績の妥当さの判断を AI に残すため、AI が選んだ課題（`--like`）を優先し、無ければ 6 項目の違いが 1 つ以下の実績を選ぶ（未決 4）

どの課題が近いかは課題の中身を読む判断で、前提 1 が AI に置いている。部品は AI の選んだ課題の実績を集計するだけにする。`--like` が無いときだけ、見積もりの記録が持つ 6 項目の違いの数で機械的に選ぶ（違いの少ない順・新しい順に最大 10 件）。件数が 5 以上なら中央値と 80 分位、1〜4 なら中央値（通常）と最大（追加の調査が要る）、0 なら未校正とし、少ない件数で確率を装わない。

6 項目を点数にして距離の重みを付ける案は採らなかった。重みは検証されておらず（要求の材料「加点して時間へ換算しない」）、6 項目は一致の数だけで使う。

根拠: Value 4 / Value 3（MVV 版 2）

### 決定 6: 構成の違いで見込みが黙って歪まないよう、構成の違う実績は値の算出から外し、別の欄に示す（前提 4）

モデル・ハーネス・レビューの方式・テストの方式・並列の数のどれかが違う実績は `other_config` に課題番号と違う鍵を出し、値には入れない。構成を変えた直後は未校正の見込みが増えるが、それは事実であり、別の欄に出すことで AI と利用者が参考にできる。不明（空）の鍵は比べない。

構成の違う実績を補正して使う案は採らなかった。補正の係数を持つことになり、倍率で見積もらない規約に反する。

根拠: Value 3（MVV 版 2）

### 決定 7: 判断を待つ時間を H に混ぜないため、H は人が記録した行（`estimate.py human`）だけから取る（未決 3）

承認ゲートの記録は答えた時刻しか持たず、会話の記録（transcript）の問いと答えの時刻の差は、人が考えて手を動かした時間と、席を外して待たせた時間を区別できない。後者は定義上 L に入り、H に入れると H を多く見積もる。記録の行が無い課題の H は「材料なし」と返す（前提 2）。

会話の記録から問いと答えの差を H として取る案は採らなかった。上の理由に加え、会話の記録はランタイムとアカウントごとに置き場が違い、ほかのプロジェクトで同じ手順で読めない。

根拠: Value 3 / Value 5（MVV 版 2）

### 決定 8: このスプリントの範囲を受け入れ条件に絞るため、cross-refactoring の工程の予算と、実行計画・スプリントの大きさの L は部品へつながない（未決 1）

受け入れ条件 5 が求める接続は `backlog-refinement` の Size と実装の上限の 2 つで、配分は受け入れ条件 12 のとおり集計の関数を共有するところまでにする。cross-refactoring の予算は配分の履歴（最終ゲートを通った実行の項目ごとの所要）という別の単位で回っており、つなぐと配分の値が変わる（受け入れ条件 12 に反する）。実行計画とスプリントの L は、実績の記録に完了までの時間がたまってから設計した方が、値の妥当さを実測で示せる。承認ゲート 1 の後に別の課題として起こす。

根拠: Value 1 / Value 3（MVV 版 2）

### 決定 9: Size が A を表し尺度の最大で潰れないよう、A を Size 1 の基準との比で丸め、境界を隣り合う段階の中点に置き、最大を超えたら「尺度を超える」とする

比 r = A ÷ 基準とし、尺度の段階 s₁ < s₂ < … の各段階は、前の段階との中点を超え次の段階との中点以下の r を受け持つ（既定の尺度では 1.5・2.5・4・6.5・10.5・16.5 が境界、20 を超えると「尺度を超える」）。基準は `.ndf/estimate.json` の `size_unit_seconds`、無ければ実績のある課題のうち A の小さい 4 分の 1 の中央値（4 課題以上のとき）、それも無ければ Size は未校正で、棚卸しは今の付け方（AI の付けた段階）に戻る。尺度を超える課題は順位の値を丸める前の比で計算し、切り出しの境界に入れない。

比の対数で境界を置く案は採らなかった。尺度そのものが大きい側で間隔を広げており、中点で足りる。基準を課題番号のアンカーで宣言させる案も採らなかった。宣言の無いプロジェクトで丸められず、宣言は秒の値 1 つで足りる。

根拠: Value 5 / Value 3（MVV 版 2）

### 決定 10: 実装の上限が実績より短く打ち切られないよう、同じ構成の直近 10 件の最大に既存の余裕を掛け、3 件未満は 3600 秒の未校正にする

上限は超えると作業を打ち切る値で、中央値や 80 分位では 2〜5 回に 1 回打ち切る。最大に `with_margin`（10%・最小 30 秒）を掛け、既存の上限の余裕と同じ形にする。件数の下限 3 は遅れの見張りの `min_samples` の既定と揃える。

80 分位を使う案は採らなかった。見積もりの「上振れ」と上限は役割が違い、打ち切りは取り直しの費用が大きい。

根拠: Value 3 / Value 6（MVV 版 2）

### 決定 11: 倍率で見積もらない規約を部品の側で守るため、未校正の暫定の範囲は AI が渡し、部品は既定の暫定値を持たない

実績が 0 件のとき、AI は想定の手順と既知のテストの所要（部品が `materials.test_seconds` として返す）から暫定の範囲を作り、`--provisional` で渡す。部品はその範囲を印 `未校正` で返すだけで、渡されなければ値を空にする。部品が既定の値を持つと、どの作業にも同じ暫定値が付き、根拠の無い数値が見積もりとして流通する。

部品が「テストの所要 × 回数」で暫定値を出す案は採らなかった。回数の係数を部品に持つことになる。

根拠: Value 4 / Value 3（MVV 版 2）

### 決定 12: 複数の課題を 1 本で流したプランの実績を捨てないため、課題の数で等分し、根拠に `shared` の印を付ける

スプリントの設計・検査・配布のプランは 2 つ以上の課題を指す。除外するとスプリントの実績の大半を失い、等分以外の配分（差分の行数で比べるなど）は材料が揃わない。等分した値であることを根拠に出し、AI と利用者が読み分けられるようにする。

根拠: Value 3（MVV 版 2）
