# #2616: 並列の計画: plugin.json の無いリポジトリでは配布の版を決められず、配布の依頼 1 つで計画全体が止まる

正は課題の本文（#2616）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何が起きたか

プラグインではないアプリのリポジトリ（volareinc/carul。`.ndf/supervise.json` を持たず、`plugin.json` も無い）で並列の計画 l20261104 を流した。レーン l20261104-ux が配布の依頼（`l20261104-ux-r807469755886`、PR #182）を送ると、耐久ワークフローの `parallel.build` が次の誤りを返した（10.27.21、2026-11-05 21:29 UTC）。

```text
{"error": "出す版を決められない（ベースブランチと .ndf/supervise.json の release.plugin の plugin.json の版を読めない）"}
```

`open_release` はこの誤りを受けて `run.stop = True` にする。このため、配布を 1 本も組まないまま `parallel.stop-lanes`（ux・api）と `parallel.finish` まで進み、計画全体が止まった。同じ時点で届いていた api のレーンの問い（`l20261104-api-q9d246b7f36fa`）にも答えられなくなった。

並列の計画を使わない 1 スプリントや開発ループでは、carul は同じ develop → main の昇格を流せている。前の周回（ux の周回 5）は、プランの `verify` → `prepare` → `mvv` → `promote` → `record` で main へ届いた。並列の計画の下でだけ配布が組めない。

## 原因

- `lib/parallel_run.py` の `step_build` が、出す版を `dev_version` だけから決めている
- `dev_version` は `.ndf/supervise.json` の `release.plugin` と、ベースブランチの `plugin.json` の版を読む。プラグインでないリポジトリには、このどちらも無い。このため常に空文字を返し、`step_build` が誤りになる
- 版を決められないことを「配布の失敗」ではなく「計画を止める」理由として扱っている（`open_release` の `self.stop = True`）

## 直し方の案

1. 配るものがプラグインでないリポジトリ（`release.plugin` が無い）では、まとめた配布を組まず、届いた配布の依頼へその場で `released` と答える（下の「CD があるときは配布の工程が要らない」）
2. 版を決められないなどで配布を組めないときは、計画を止めず、その配布の依頼に `failed` と理由を答える。あわせてオーガナイザーへ問いを立てる（「直してから組み直す」「止める」）
3. `parallel.py check`（計画の検査）が、配布の版を決められないリポジトリを起動の前に見つけて知らせる

## CD があるときは配布の工程が要らない

carul の配布は CI/CD が決めている。develop へのマージで検証環境へ、main へのマージで本番へ、環境ごとの CodePipeline が反映する（利用者の指摘、2026-11-05）。このようにマージで反映する CD を持つリポジトリでは、マージそのものが配布になる。オーガナイザーがまとめた配布（提示のプラン・本番のプラン・版上げ・タグ）を組む工程は要らない。

| リポジトリ | 配布の工程 | 届いた配布の依頼への答え |
| --- | --- | --- |
| プラグイン（`release.plugin` があり、版とタグで出す） | まとめた配布を組む（今の動き） | 配布の結果（`released`・`rejected`・`failed`） |
| CD がマージで反映する（`.ndf/project.json` の `delivery` が `kind: auto`） | 組まない | その場で `released` |

本番チャネルへの昇格のマージ（develop → main）は承認ゲート 2 のままで、この変更は承認の要否を変えない。

## 目的

並列の計画が、配る形の違うリポジトリでも止まらずに進む状態にする。

- リポジトリの配り方を、`.ndf/project.json` の `delivery` と `.ndf/supervise.json` の `release.form` の宣言から読む。プラグインの形を前提にしない
- 配布を組めないことを、計画全体を止める理由にしない。その配布の失敗として依頼へ答え、計画を止めるかは人が決める

## 調べたこと

調べた時点は develop の e7500d193 である。

### 1. CD のリポジトリのレーンは、今のコードでは配布の依頼を送らない

本番のステージを配布の依頼に置き換える `prod_plans` の呼び出しは `supervise_lib/sprint.py` の 4 か所（124・164・219・318 行）で、どれも `has_release_template` が真のときだけ通る。テンプレートで組まない経路は `route_waves` へ進み、昇格のプランをレーンが直接流す。

carul の実物も同じである。周回 6 の本番のステージ `7-promote.json` は、組まれた時点では「配布（昇格）」のプランだった（`7-promote.json.direct-promote.bak`）。オーガナイザーの作業の中で配布の依頼のプランへ手で置き換えられ、その依頼が `parallel.build` の誤りを起こした。

つまり、この課題の再現は手で置き換えたプランで起きた。**配布の依頼を受けたときの直しだけでは、CD のリポジトリのレーンが直接昇格する流れは変わらない**（未決 1）。

### 2. リポジトリの形ごとの経路

次の形をリリースの経路の判定（`lib/delivery.py` の `routes`）へ渡した結果である。

| 形 | 宣言 | `routes` の結果（経路, ステージ） |
| --- | --- | --- |
| carul | `delivery` の 2 行がどちらも `auto` | `merge, merged-by-check`・`merge, promote` |
| ai-plugins | `release.form: package-plugin` | `template, template` |
| 手動で反映 | `delivery` が `manual` だけ | `manual, manual` |
| 自動と手動の混在 | `auto` と `manual` | `merge, merged-by-check`・`manual, manual` |
| 配布しない | `delivery: []` | `none, none` |
| 宣言が無い | `delivery` が無い | `manual, manual` |
| 不明 | `delivery: {"unknown": ...}` | `manual, manual` |

判定に必要な宣言と関数は揃っており、並列の計画（`lib/parallel_run.py`）だけがこれを読んでいない。

### 3. `release.plugin` では判定できない

`.ndf/supervise.json` を持つのは ai-plugins だけである（#2624 の「根にある形」の 3。/work の下の 11 リポジトリで確認）。このため `release.plugin` が無いことは、CD があることを意味しない。手動で反映するリポジトリも同じ条件に当たり、届いていない変更へ `released` と答えることになる。

### 4. 配布を組めない経路は、版の読み取りのほかにもある

- 配布の連番が上限を超えたとき（`step_build` の 225 行）
- `build_plans` が例外を上げたとき（`parallel_run.py` の `step_build` は例外を受けない）
- 承認の答えの時点でベースブランチが進み、提示 2 を組むとき。`confirm`（`parallel_run.py` の 475〜476 行）は `step_build` の `error` を見ずに `built["dir"]` を読むため、誤りが返ると `KeyError` になる

### 5. レーンは `version` の無い `released` を受けられる

`settle_release` は `version` が無ければ版を書かずに進む（`sprint_loop_gate2.py` の 176〜178 行）。carul の周回 6 は、手元の手当てで届いた `version` の無い `released` を受けてまとめを流した（`.ndf/handoff/loop-l20261104-ux.md`）。`test_sprint_loop.py` で `released` の答えを渡す 3 件の `version` はどれも文字列で、`version` の無い答えを読むテストは無い（同じファイルを `"version": None` で検索して 0 件）。

### 6. 計画を止める今の振る舞いはテストが固定している

`test_parallel_run.py` の `test_char_build_error_fails_release_and_stops` が、誤りで計画が止まることを確かめている。この課題で意図して書き換える。

## 前提

- 前提 1: リリースの経路は、メインディレクトリの `.ndf/project.json` の `delivery` と `.ndf/supervise.json` の `release.form` から決まる。読み方は `lib/delivery.py` の `load_delivery` と `routes` に従う
- 前提 2: `released` の答えは「本番系へ届いた」を意味しない。CD の経路では「オーガナイザーが組む配布が要らない」ことを意味し、レーンはまとめへ進む。本番系へ届いたことはリリース後テストが確かめる
- 前提 3: 配布の依頼が届く Pull Request は、ベースブランチへマージ済みである。依頼を送るのは検査のステージの後である。答えを返す時点で読み直さない
- 前提 4: この課題は #2624 の違反 1（宣言を読まない経路）を、宣言を読む形で直す。その場の例外を足さないため、#2624 の根本原因を直す作業の一部として扱う
- 前提 5: 手動で反映する経路を持つリポジトリの配布は、この課題では自動にしない。`failed` と理由を答え、オーガナイザーが手で進める

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 配布を組まなかった理由と組めなかった理由が、配布の記録（耐久ワークフローの結果の `releases`）に 1 件ごとに残る。理由だけで、どの宣言を直せばよいかが分かる |
| 移行性 | 記録のある途中の耐久ワークフローを新しい版で続けても、耐久ステップの並びの食い違いで落ちない。続けられない形なら、頭から流すときに受け付け済みの依頼を失わない手順を設計で決める |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`parallel.py check` の警告が増える。`answer-<依頼>` の `version` が `null` を取る（契約 `parallel-request` の `result` の値は変わらない）。互換性は保つ |
| データ | スキーマの変更と移行は無い。配布の記録の行に理由が載る |
| 既存の振る舞い | 配布を組めないときに計画が止まらなくなる。CD のリポジトリで依頼を受けても `parallel.build` を呼ばなくなる |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| 起動 | `python3 plugins/ndf/scripts/parallel.py check <計画名>` |
| テスト | `uv run --frozen --project . --all-extras pytest plugins/ndf/scripts/tests/test_parallel_run.py plugins/ndf/scripts/tests/test_parallel_answer.py plugins/ndf/scripts/tests/test_sprint_loop.py -q -n 4` |
| 静的解析・型検査 | `ruff`（`pyproject.toml` の `[tool.ruff]`） |
| 手動確認 | carul の並列の計画で、配布の依頼を 1 回通して、依頼に配布済みの答えが返り計画が止まらずにレーンがまとめへ進むことを、リリース後テストで確かめる |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | 判定は `plugins/ndf/scripts/lib/delivery.py` の既存の関数を使い、同じ役割の判定を並列の計画の側に足さない。実験版の置き場を参照しない（`AGENTS.md`） |
| コーディング規約 | `AGENTS.md` の「最小限のコード実装」。`ruff` で確かめる |
| テスト戦略 | 耐久ワークフローの判定は `test_parallel_run.py`、レーンの読み取りは `test_sprint_loop.py`、検査は `parallel.py check` の統合テストで確かめる。`.md` の文言を照合するテストは書かない |

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | 既存テストの実行、`ruff` の適用、宣言の読み取りを `lib/delivery.py` に寄せること |
| 確認してから行う | 公開インタフェースの変更、耐久ステップの並びの変更。どちらも承認ゲート 1 の設計で人が見る |
| 行わない | `main` へのマージを伴う処理の追加、`release.plugin` を判定に使うこと、手動の経路を自動にすること |
