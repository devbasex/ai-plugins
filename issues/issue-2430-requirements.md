## なぜこの変更の範囲外なのか

リリース後テストは不合格を即時修正しない（`release-verification` の「合否を判定する」）。リリース後の修正は新しい変更で、モードの判定から始める。画面の側は、承認の一覧が #2173（承認ゲートの通知と Web からの承認）、スプリントの詳細が #2172（工程・PR・CI・承認ゲート）の持ち物で、どちらにも `base_conflict` とループの承認の依頼を並べる条件が書かれていない。根拠: スプリント Value 2（画面先行）・プロジェクト Value 1（不具合はモードの判定から直す）（MVV 版 4）。

## 直さないと何が起きるか

- 取り込みで解けない衝突で止まった実行が、Web の画面では理由の分からないまま待ちに見え、利用者が手元のログを見に行くまで気づかない

- #2347 が閉じられると、この 2 つの条件の残りを持つ課題が無くなる

## 目的

- 取り込みで解けない衝突で止まったスプリントの実行について、利用者が手元のログを見ずに、Web の画面だけで止まった理由を知れる状態にする
- 複数の開発ループと単発のスプリントの実行が人の答えを待っているとき、どのループの何周目の、どの種類の承認の依頼かを 1 つの画面で見られる状態にする（スプリント Vision「いま何が人を待っているかが分かる」）

## 前提

- 前提 1: #2347 の受け入れ条件 7・13 の画面の残りを、この課題 1 つで扱う
- 前提 2: ランナーの翻訳（取り込みのステップの `attention` を `base_conflict` へ写す）と、`gate.reached` の `loop`（名前と周回の番号）は実装済みで、この課題では変えない（`factory/runner/src/translate.ts`、`factory/contracts/src/generated/progress-event.ts` の `LoopRef`）
- 前提 3: 承認待ちの一覧は読むだけの画面で、承認・差し戻し・判断への答え・通知は #2173 が同じ画面へ足す。画面の地図の「承認」の行の作る課題を #2430 へ書き換え、#2173 は答える操作の課題として残る
- 前提 4: 承認待ちの一覧と `attention` の表示は、進捗の事象の列とスプリントの実行の状態だけから導く（#2172 の前提 1 と同じ）。課題の本文・ボード・GitHub の API は読まない
- 前提 5: 見せる範囲は `resolveAccount` で解決できたアカウントのスプリントの実行だけで、スプリントの一覧と同じ規則で読む（#2172 の前提 9）
- 前提 6: MCP のツールは契約の操作の一覧（`factory/contracts/src/operations.ts`）から作られるため、API の操作を 1 つ足せば MCP からも同じ読み出しができる（`factory/api/src/mcp/server.ts` が `OPERATIONS` を読む）
- 前提 7: 画面を開いている間は、スプリントの一覧と同じ設定（`FACTORY_POLL_INTERVAL_MS`、既定 30 秒）で読み直す。押し出しの通知は作らない

- スプリントの一覧の行に `attention` の有無を出すこと

## 用語

| 承認待ちの一覧 | アカウントのスプリントの実行のうち、答えの無い承認の依頼（ゲート 1・ゲート 2・判断）を、ループの名前と周回の番号とともに 1 つに並べた、読むだけの画面と API の読み出し |

## 受け入れ条件

スプリントの詳細の `attention`:

- [ ] 1. 前提: スプリントの実行に `attention`（`reason: base_conflict`、`summary: "src/a.ts で衝突"`）が 1 件ある。操作: スプリントの詳細を開く。結果: 詳細に `attention` の欄があり、理由「取り込みで解けない衝突」・要約 `src/a.ts で衝突`・日時（利用者の時刻帯）の 1 行が出る
- [ ] 2. 理由が `base_conflict` 以外の `attention`（例 `reason: "stopped"`）は、理由の値そのもの（`stopped`）と要約で出て、詳細の読み出しは 200 を返す
- [ ] 3. `attention` が 3 件ある実行は、記録された順（`order_key` の順）に 3 行出る。0 件の実行では、欄に「ありません」が出る
- [ ] 4. スプリントの詳細の読み出し（`getSprintRunDetail`）の応答に `attention` の並び（理由・要約・日時）が入り、画面はこの読み出しだけで欄を描く

承認待ちの一覧:

- [ ] 5. 前提: 1 つのアカウントに、(a) ループ `lfactory2` の周回 3 でゲート 1 を待つ実行、(b) ループ `lfactory3` の周回 1 でゲート 2 を待つ実行、(c) ループでない実行で判断を待つ実行、(d) ゲート 1 に答えの記録された実行がある。操作: 承認待ちの一覧を開く。結果: (a)(b)(c) の 3 行が、種類（ゲート 1・ゲート 2・判断）・ループの名前・周回の番号・リポジトリ・課題の番号・待ち始めた日時とともに出る。(c) のループの名前と周回の番号は「—」。(d) は出ない
- [ ] 6. 行は待ち始めた日時の古い順に並ぶ。同じ実行の同じ種類の `gate.reached` が 2 度届いた（材料を直して出し直した）とき、行は 1 つで、日時は後の `gate.reached` のもの
- [ ] 7. 行を押すと、その実行のスプリントの詳細へ移る
- [ ] 8. 答えの無い承認の依頼が 0 件のとき、一覧に「承認を待っているものはありません」が出る
- [ ] 9. 一覧の画面は画面の地図と `screens.ts` に経路つきの「あり」の行として載り（`docs.test.ts` が通る）、ナビゲーションの行き先に出る。幅 360 px でもメニューのボタンと行き先の 2 手で届く
- [ ] 10. 他人のアカウントの実行の承認の依頼は一覧に出ない。他人のアカウントの一覧を読むと 403 `forbidden` で、スプリントの一覧と同じ本文になる。チームのアカウントでは席を持つ人なら読める
- [ ] 11. 同じ一覧を API の操作と MCP のツールで読むと、画面と同じ行（配列）が返る。API と MCP にも承認を確定する操作は足されない
- [ ] 12. 一覧の読み出しが失敗しても前の表示を残し、「読み直せませんでした（<時刻>）」が出る（#2172 の見本の画面と同じ）

退行しないこと:

- [ ] 13. スプリントの詳細の承認ゲートの欄（ゲート 1・ゲート 2・判断の状態）の表示と、既存のテストの結果が変わらない
- [ ] 14. 新しい文言はすべて翻訳のファイルにあり、画面のコードに日本語の文字列を直接書いていない（`npm run check:source -w web` が通る）。ダミーで起動（`npm run dev:dummy -w web`）すると、`attention` の欄と承認待ちの一覧がダミーデータで出る
