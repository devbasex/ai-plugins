# #1752: release: 他のプラグインの版の上げ幅と移行の手順が配布のプランと承認ゲート 2 の承認資料に届かず、互換の無い変更が PATCH で出うる

正は課題の本文（#1752）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

#744 の要求文書は、配布の工程に 2 つを委ねていた。どちらも配布のプランと承認ゲート 2 の承認資料に届かず、承認ゲート 2 の直前に利用者が気付いて、修正 PR #1747 で手で足した。

| 要求文書の記述 | 何が起きたか |
| --- | --- |
| 前提 6「playwright-kit の `version` もこのスプリントで上げる。上げ幅は配布（`release`）で決める」 | 開発版のプラン（`7-release.json`）は `bump --plugin ndf` だけで、他のプラグインを見ない。承認ゲート 2 の承認資料（`approval-facts`）にも playwright-kit の版は載らない。本番のプランの `bump-others`（`release-steps.py changed-plugins`）は差分のある他のプラグインの **PATCH だけ**を上げる。Drive への保管と `--pwk-drive-folder` を外した変更は MAJOR（2.0.6 → 3.0.0）が要った |
| 非機能の条件「移行性: CHANGELOG に移行の手順を書く」・前提 5「`gws drive +upload` を手で使う案内を CHANGELOG に書く」 | CHANGELOG は PR 本文の `## 利用者向けの変化` から組まれる（`release-steps.py notes`）。実装 PR #1744 の本文はその節に「何が変わったか」の 2 行だけを書き、移行の手順が無かった。要求文書の移行の条件を PR 本文へ写す工程も、CHANGELOG へ写す工程も無い |

#1747 が入った後の本番のプランでは `bump-others` が `already: ["playwright-kit"]` を返した（`8-release-prod-state/02-bump-others.out`）。手当てが無ければ playwright-kit は 2.0.7 で出ていた。

## どこで見つけたか

- `~/.local/state/ndf/sv/sprint-m744/7-release.json`（開発版のプランのステップ）・`8-release-prod.json`（`bump-others`）
- `supervise_lib/release_templates.py` の `bump_others_cmd`（PATCH を 1 つ上げる）、`release-steps.py` の `changed-plugins`・`notes`・`approval-facts`
- issue #744 の本文の「前提」5・6 と「非機能の条件」の移行性、PR #1744 の本文、PR #1747
- スプリント m744 の振り返り（PR #1745）

## なぜこの変更の範囲外なのか

#744 の受け入れ条件は google-workspace への一本化と playwright-kit の Drive 連携の撤去で、配布の雛形と承認資料は対象に無い。根拠: Value 4（決まった手順はスクリプトが持つ）・P1（版の規則は利用者全員に効く）（MVV 版 2）。

## 直さないと何が起きるか

- 機能を外す・引数を消すなど互換の無い変更が、PATCH の版で配布される。利用者は版数から影響を判断できない（AGENTS.md の「セマンティックバージョニングに従う」に反する）
- 認証のし直しなど利用者の操作が要る変更で、CHANGELOG に手順が載らない
- 承認ゲート 2 で利用者が気付かない限り防げない（今回は人が気付いた）

## 直し方の案

- 開発版のプランにも `changed-plugins` を置き、承認ゲート 2 の承認資料（`approval-facts`）に「版を上げる他のプラグインと上げ幅」の欄を足す。上げ幅は PATCH に決め打たず、PR 本文か要求文書の「影響」の公開インタフェースの行（「変わる」「互換の経路は持たない」）から MAJOR の候補を示す
- PR 本文の雛形に `## 移行の手順`（無ければ「無し」）の節を足し、`notes` が CHANGELOG の版の節へ写す。要求文書の非機能の条件に移行性の行があれば、実装のプロンプトがその節を書かせる

## 由来

PR #1745（スプリント m744）・issue #744 の振り返りで拾った取りこぼし。関連: PR #1747、#1742（PR 本文の下書きが載らない）。

# 要求と受け入れ条件

## 依頼（原文）

> #1752。人へ問わずに進め、決められない点は前提か未決として課題の本文へ書く。

（課題の本文の上の節「何を見つけたか」〜「直し方の案」が、要求の出所である）

## 目的

- 互換の無い変更を含む版で、主のプラグイン以外のプラグイン（以下「他のプラグイン」。ai-plugins では playwright-kit・mcp-*）の版数が、PATCH に決め打たれずに互換の扱いに合った上げ幅で出る
- 利用者の操作が要る変更（引数の撤去・認証のし直し・導入し直し）の移行の手順が、人が手で足さなくても CHANGELOG の版の節へ載る
- 上の 2 つが、承認ゲート 2（本番への配布の承認）の承認資料にそろって載り、承認する人（または MVV 判定）が 1 回で判断できる

## 前提

- 前提 1: 「他のプラグイン」の範囲は、今の `release-steps.py changed-plugins` と同じ（前のタグからの差分に `plugins/<名前>/` か `plugins/mcp/<名前>/` のファイルがある、宣言の `release.plugin` 以外のプラグイン）。範囲の決め方は変えない
- 前提 2: 対象は配布の形が `package-plugin` のときだけである。他の配布の形（`changed-plugins` を持たない形）の振る舞いは変えない
- 前提 3: 主のプラグイン（宣言の `release.plugin`。ai-plugins では ndf）の版数は、今と同じく配布のプランの `--version` で決まる。主のプラグインの上げ幅の決め方はこの課題で変えない（マイルストーン 26 の版は 10.17.x の PATCH で出す決まりがある）
- 前提 4: 上げ幅の規則そのもの（セマンティックバージョニング。AGENTS.md）は変えない。変えるのは、規則に合った上げ幅を配布のプランが選べるようにし、選んだ上げ幅を承認資料に載せることである
- 前提 5: 上げ幅の**候補**は機械で出し、最終の上げ幅は承認ゲート 2 の承認（人か MVV 判定）で決まる。候補を出す材料は、版に含む PR の本文と、その PR が指す課題の要求の「影響」の表の「公開インタフェース」の行である。材料に互換の無い変更を示す記述が無ければ候補は PATCH である
- 前提 6: 移行の手順の正は実装 PR の本文の `## 移行の手順` の節とする。節が無い PR・「無し」だけの PR は、移行の手順を持たないものとして扱う（エラーにしない）
- 前提 7: 既にマージ済みの PR（本文に `## 移行の手順` の節が無い）を含む版でも配布は今と同じに通る
- 前提 8: 他のプラグインの CHANGELOG の節（`## [playwright-kit 3.0.0]` のような、他のプラグイン自身の版の節）と、他のプラグインの README の更新の節を作ることは、この課題に含めない（下の「含まない」と「未決」）

## 対象範囲

含む:
- 開発版の配布のプランで、他のプラグインとその上げ幅の候補を出すこと
- 承認ゲート 2 の承認資料に「版を上げる他のプラグインと上げ幅」の欄と、移行の手順の欄を足すこと
- 本番の配布のプランの `bump-others` が、PATCH に決め打たず、承認ゲート 2 で決まった上げ幅で他のプラグインの版を上げること
- PR 本文の雛形（`pr-steps.py template`・実装のプランの PR 本文を書く指示）に `## 移行の手順` の節を足すこと
- `release-steps.py notes` が PR 本文の `## 移行の手順` を CHANGELOG の主のプラグインの版の節（と主のプラグインの README の更新の節）へ写すこと
- 要求の非機能の条件に移行性の行がある課題の実装で、実装の指示が PR 本文の `## 移行の手順` を書かせること
- 上の振る舞いを確かめる自動テスト

含まない:
- 主のプラグイン（ndf）の上げ幅の決め方（前提 3）
- 他のプラグイン自身の CHANGELOG の版の節・README の更新の節の自動作成（前提 8）
- 上げ幅の規則（セマンティックバージョニング）・配布の取得元・既定ブランチの変更（P1 に当たる操作はしない）
- `package-plugin` 以外の配布の形（前提 2）
- 実装のプランの PR 本文に worker の下書きを載せる仕組み（#1742 の範囲）
- 既にマージ済みの PR の本文の書き直し

## 用語

| 用語 | 意味 |
| --- | --- |
| 他のプラグイン | 配布の宣言の `release.plugin` 以外で、前のタグからの差分にファイルがあるプラグイン（前提 1） |

## 受け入れ条件

- [ ] 1: `package-plugin` の開発版の配布のプランに、他のプラグインを列挙するステップがあり、その結果が承認ゲート 2 の承認資料に載る。他のプラグインが 0 件なら欄は「無し」と書かれる
- [ ] 2: 承認ゲート 2 の承認資料の「版を上げる他のプラグイン」の欄に、プラグインごとに名前・今の版・上げ幅の候補・上げた後の版・候補の根拠（どの PR かどの課題の何の行か）が並ぶ
- [ ] 3: 版に含む PR か、その PR が指す課題の要求の「影響」の「公開インタフェース」の行が互換の無い変更を示すとき、そのプラグインの上げ幅の候補は MAJOR になる。m744 を再現した入力（playwright-kit 2.0.6・PR #1744 と課題 #744 の本文）で、候補が MAJOR・上げた後の版が 3.0.0 になる
- [ ] 4: 互換の無い変更を示す記述が材料に無いプラグインの上げ幅の候補は PATCH で、上げた後の版は今の `changed-plugins` と同じ値になる（退行しない）
- [ ] 5: 本番の配布のプランの `bump-others` は、承認ゲート 2 で決まった上げ幅で他のプラグインの版を上げる。上げ幅が MAJOR と決まった playwright-kit 2.0.6 は 3.0.0 になり、2.0.7 にならない
- [ ] 6: 本番の `bump-others` が決まった上げ幅を読めないとき、PATCH に黙って倒さず、ステップが落ちて judge へ進む
- [ ] 7: 既に版を上げてあるプラグイン（`already`）は、今と同じく上げ直さない
- [ ] 8: `pr-steps.py template` が書く雛形と、実装のプランで PR 本文を書く指示（`PR_SYSTEM`）が `## 移行の手順` の節を持ち、移行の手順が無いときは「- 無し」と書くよう求める
- [ ] 9: 要求の非機能の条件に「移行性」の行がある課題の実装で、PR 本文を書く材料にその行が渡り、PR 本文の `## 移行の手順` が「無し」以外になる
- [ ] 10: `release-steps.py notes` は、版に含む PR の本文の `## 移行の手順` の箇条を、CHANGELOG の主のプラグインの版の節の中の移行の手順の見出しの下へ PR 番号つきで写す。移行の手順を持つ PR が 0 件なら、その見出しを作らない
- [ ] 11: `notes --approval` は、同じ箇条を承認ゲート 2 の承認資料の移行の手順の欄へ書く。0 件なら「無し」と書く
- [ ] 12: 本文に `## 移行の手順` の節が無い PR だけの版で、`notes`・`approval-facts`・`bump-others` の出力（CHANGELOG・承認資料の既存の欄・上げた版）が今と同じになる（前提 7）
- [ ] 13: 全体テスト（`uv run --frozen --project . --all-extras pytest . -q -n 4`）が通り、上の 1〜12 を確かめるテストが含まれる
