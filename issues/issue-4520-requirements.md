## 何が起きたか

2026-11-25、AI が NDF の開発の流れで [測定値の扱いを分ける課題（#4516）](https://github.com/devbasex/ai-plugins/issues/4516) を進めていた。

NDF は、まとまった開発（スプリント）の進み具合を **ステートマシン** という記録に残す。記録には工程（要求・設計・実装・デプロイなど）ごとの状態がある。工程のうち設計とデプロイには、人の承認を待つ **承認ゲート** がある。

1. 設計の工程は、AI の担当（supervisor）が自動の流れの外で進めた。統括する AI（conductor）は、手順どおりに工程を「終えた」と記録した（`ndf progress finish`）
2. 利用者が設計を見て、変更を求めた
3. 回答を記録するコマンド（`ndf answer`）は「回答を待っていない」として断った
4. 工程をやり直すコマンド（`ndf progress retry`）も「失敗した工程だけ」として断った

設計を直すという普通の作業を、記録に残せなかった。このスプリントの記録には、設計の工程が承認ゲートを持つのに、利用者の回答が 1 件も無い（設計の [Pull Request #4518](https://github.com/devbasex/ai-plugins/pull/4518)）。

利用者の指摘は「ステートマシンの設計が保守的過ぎる」である。

## 種類

不具合（「利用者が承認ゲートで回答したら、承認も変更要求も記録する」という今の手順書の約束を、記録の仕組みが満たせないため）

## 今の姿

ステートマシンは、工程の状態の変化を **追記だけ** で残す。過去の記録は消えない。今の状態は、記録を順に読んで求める。承認ゲートの回答は、利用者の承認も変更要求も記録する決まりである（[承認ゲートの回答を記録する手順](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/approval-answer.md)）。

状態を変える操作は、打てる場面が限られている。

| 操作 | 今打てる場面 | 打てないために起きること |
| --- | --- | --- |
| やり直す（`ndf progress retry`） | 失敗した工程だけ | 終えた工程を、変更要求・後で分かった誤り・要求の追加でやり直せない |
| 回答する（`ndf answer`） | 自動の流れが承認ゲートで回答を待っている工程だけ | 流れの外で終えた工程への回答や、回答した後で考えが変わったときの回答を記録できない |
| 手で終える（`ndf progress finish`） | 未着手・失敗・無効の工程。承認ゲートの有無は見ない | 承認が無いまま「終えた」になり、次の工程が始まる。承認ゲートが記録の上で素通りになる |

表の 3 行目だけを扱う課題が [#3957（手で終えると回答を待たずに次の工程が始まる）](https://github.com/devbasex/ai-plugins/issues/3957) にある。

## 事象

- 手で終えた設計の工程へ、変更要求の回答を打つ（`ndf answer <ステートマシン> --gate "設計 Pull Request のマージ" --result request_changes ...`）と、`stopped`（`refused`: 回答を待っていない（実行の前か、済んだ回答））で止まる
- 同じ工程の `ndf progress retry <ステートマシン> "設計" --reason ...` も `refused`（書けるのは失敗の工程）で止まる
- 承認ゲートを持つ工程を `ndf progress finish` で終えると、回答が無くても次の工程へ進める

## 期待する結果

- 変更要求・やり直し・後からの修正という実際の作業の動きを、理由を添えて記録でき、その工程から作業を続けられる
- 承認ゲートを持つ工程は、承認が記録されるまで次の工程へ進まない

## 再現手順

1. 設計の工程を持つステートマシンを作る（`standard` モード）
2. 設計の工程を、承認ゲートの回答を書かずに `ndf progress finish` で終える
3. `ndf progress next` を打つ。承認を求めずに次の工程へ進む
4. 設計の工程へ `ndf answer ... --result request_changes` を打つ。`refused` で断られる
5. `ndf progress retry <ステートマシン> "設計" --reason ...` を打つ。`refused` で断られる

手順 4 と 5 の結果は 2026-11-25 の実例で観測した。手順 3 は #3957 に実例がある。2026-11-27 には、状態の遷移の表と回答の処理のコードを読み、同じ制限が残ることを確かめた（実行はしていない）。

- 2026-11-25 の実例の NDF のバージョン、ランタイム、OS: 未確認

## なぜ困るか

- 変更要求や誤りの発見のたびに、記録と実際の作業が食い違う。後から「何が起き、誰が何を承認したか」を追えない
- 承認ゲートを素通りできるため、人が承認していない設計のまま実装が始まりうる
- 記録は追記だけで過去が消えないので、やり直しや後からの回答を断っても守れるものが少ない

## 目的

- 起きうる作業の動き（変更要求・やり直し・後からの修正・考え直し）を、ステートマシンへ記録できるようにする
- 承認ゲートを、どの経路で工程を終えても素通りできないようにする

## 対象範囲

含む:

- スプリントのステートマシンの、手で終える・回答する・やり直すの 3 つの操作
- 操作と工程の状態の組み合わせ全体の見直し（「実際の作業の動きを記録できる」を基準にする）
- 開き直した工程に合わせた、課題の本文の進み具合の表の更新
- 上の操作を説明する手順書の更新
- #3957 の内容（受け入れ条件 1〜3 が同じことを扱う）

含まない:

- レーン（並行開発の 1 本）と並行開発の計画のステートマシン
- 完了または中止したスプリントの記録を開き直すこと
- 変更要求の指摘を、やり直しの担当の AI へ届けること（[#4431](https://github.com/devbasex/ai-plugins/issues/4431)）。自動の流れの実行中の工程を手で閉じることも #4431 に残す
- 並行開発のレーンが変更要求の回答を読まずに進むこと（[#3880](https://github.com/devbasex/ai-plugins/issues/3880)）
- 承認ゲートを出す対象の Pull Request の誤り（[#3913](https://github.com/devbasex/ai-plugins/issues/3913)）
- やり直しの前に実行済みの外への操作（マージ・リリース）の取り消し

## 前提

- 前提 1: 承認ゲートの数、承認できる者、承認を MVV（プロジェクトの判断基準）による判定で省ける条件は変えない。以下の「承認」は、今の決まりで認める承認を指す
- 前提 2: 記録は追記だけのままにする。過去の記録を消したり書き換えたりしない

## 受け入れ条件

承認ゲートを持つ工程を手で終える:

- [ ] 1. 承認ゲートを持つ工程を `ndf progress finish` で終えた後、承認が記録されていない間は、`ndf progress next` が次の工程を始めない。結果は `gate` で、回答ごとに打つコマンドを返す
- [ ] 2. 条件 1 の状態で `approved` を記録すると、`next` が次の工程へ進む
- [ ] 3. 同じ対象の承認が既に記録されている工程を `finish` で終えた場合は、承認をもう一度求めない
- [ ] 4. 承認ゲートを持たない工程の `finish` と `next` は、今と同じ結果になる

回答する:

- [ ] 5. 承認ゲートを持つ工程には、未着手・実行中・失敗・終了のどの状態でも、`ndf answer` で承認と変更要求を記録できる
- [ ] 6. 終了した工程に変更要求を記録すると、その工程と後ろの工程が開き直され、`next` はその工程から流す。承認を記録した後に変更要求を記録した場合も同じになる
- [ ] 7. 回答が `approved` 以外の間は、`next` は後ろの工程を始めない
- [ ] 8. 承認ゲートを持たない工程への回答は、理由を示して断る
- [ ] 9. 後からの回答にも、今の回答の検査を同じように適用する。見た後に対象が変わった回答は断る。本番へ反映される承認は利用者本人の回答だけを認める。同じキーで打ち直しても記録は増えない

やり直す:

- [ ] 10. 終了した工程を `ndf progress retry` でやり直せる。理由が空なら断る
- [ ] 11. 終了した工程のやり直しでは、後ろの工程を「開き直す」か「そのまま残す」かを選べる
- [ ] 12. 「開き直す」を選ぶと、指定した工程と後ろの工程が未着手に戻る。`next` は順に流し直し、前の回の済んだ作業の結果を使い回さない。後ろの工程は、やり直しで書かれた新しい出力を読む。無効と中止の工程は変わらない
- [ ] 13. 「そのまま残す」を選ぶと、指定した工程だけが未着手に戻る。それを終えると、`next` は残した終了の工程を飛ばして先へ進む
- [ ] 14. 承認ゲートを持つ工程を開き直した場合は、前の承認を使わず、改めて承認を求める
- [ ] 15. 操作の結果には、開き直した工程の一覧が出る。デプロイのように外への操作を済ませた工程が含まれれば、その操作は取り消されないことも出る
- [ ] 16. 失敗した工程の `retry` は、今と同じ打ち方で同じ結果になる

記録と安全:

- [ ] 17. 開き直しと後からの回答の後も、それより前の記録は残る。`ndf progress show` で時刻と理由を、`ndf answer list` ですべての回答を古い順に読める
- [ ] 18. 開き直した工程は、課題の本文の進み具合の表から終了のマーカーが外れる
- [ ] 19. 工程の作業が流れている間の、工程を開き直す操作は断る
- [ ] 20. 完了または中止したスプリントへの操作は、今と同じく断る
- [ ] 21. 操作を断るときは、結果の文に理由と、代わりに打てる操作が出る
- [ ] 22. 2026-11-25 の実例を通しで記録できる。順は、設計を手で終える → 変更要求を記録する → 設計を直して手で終える → 承認を求められる → 承認する → 次の工程が始まる、である
- [ ] 23. 手順書（進み具合の記録、supervisor の経路、承認の回答の記録）の説明が、新しい振る舞いと一致する

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 移行性 | 変更の前に作ったステートマシンを、そのまま読んで操作できる。変更の前に手で終えた承認ゲートの工程は、変更の後に自動で回答待ちへ戻さない |
| セキュリティ | どの操作の順でも、承認の記録が無いまま承認ゲートの後の工程が始まらない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`retry` と `answer` を打てる場面が増える。承認ゲートを持つ工程を `finish` した後の `next` は、次の工程を始めずに承認を求める |
| 重さ | 変更要求のたびに記録が止まる。承認ゲートは素通りできる。回避の手段は、記録をせずに作業だけを直すことしか無い |
| データ | 記録の種類が増える可能性がある。過去の記録は書き換えない |
| 既存の振る舞い | 流れの外で進める設計とデプロイの工程は、承認を記録するまで次へ進まなくなる |

## エンジニア向けの補足

- 状態の遷移の SSOT は [progress.json](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/contracts/workflow/progress.json) である。`retry` は `from: ["failed"]`、`manual_finished` は `["pending", "failed", "disabled"]`、`answered` は `["running", "failed"]`
- `answered` は表では失敗の工程にも書けるが、`ndf answer` は回答を待つ質問が無いと断る（[gate/answering.py](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/src/ndf/progress/gate/answering.py)）
- 次の 1 手の判断（[run.py](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/src/ndf/progress/run.py) の `decide`）は、終了の工程を飛ばす
