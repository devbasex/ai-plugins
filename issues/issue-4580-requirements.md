## 何が起きたか

Web アプリケーション（`main` へ変更が入ると自動で本番へ反映する、バージョン番号を持たないサービス）のリポジトリで、NDF を使ってスプリント（1 回のリリースとして出す作業のまとまり）を数本流した。NDF の開発の流れは、このリポジトリに合わない手順をそのまま当てた。観測した例は次の 5 つである。

| # | 場面 | 起きたこと | 直す場所（2026-11-27 時点） |
| --- | --- | --- | --- |
| 1 | リリースの工程 | バージョンを持たないため、リリースの手順が求められた値を返せず、失敗を繰り返した。オーガナイザー（並列の作業をまとめる担当）が結果を手で作って工程を終えた | https://github.com/devbasex/ai-plugins/issues/4513 |
| 2 | マージの判定 | リリースの届け先の設定が実態とずれ、スプリントの Pull Request が承認なしで本番のブランチへマージされた | https://github.com/devbasex/ai-plugins/issues/4579 |
| 3 | 並列の作業 | 開発用コンテナの再起動の後に、作業を再開する手順が無かった | https://github.com/devbasex/ai-plugins/issues/4575 |
| 4 | 課題を閉じる条件 | 課題を閉じる条件が、決まった形のリリース後テストの記録と、課題の本文の「振り返り:」の行を求めた。このリポジトリでリリース後に確かめる対象は、配ったプログラムではなく、反映した環境である | この課題 |
| 5 | 設計とリファクタリングの工程 | リファクタリングの工程が、GitHub のコマンドの案内文を Pull Request の番号に混ぜて失敗した。設計を流し直すと、設計の Pull Request の番号が結果に欠けた | 前半は NDF 11.0.40 で直った（ https://github.com/devbasex/ai-plugins/pull/4552 ）。後半は https://github.com/devbasex/ai-plugins/issues/4455 |

## 種類

機能追加（開発の流れをプロジェクトが設定で選ぶ、という約束を今の NDF は持たず、新しく足すため）

## 今の姿

NDF は、開発を工程（要求、設計、実装、デプロイ、リリース後テスト、振り返りなど）に分けて順に進める。通す工程はモード（変更の中身で決める 5 つの区分）ごとに決まる。プロジェクトごとの違いは、リポジトリの中の設定ファイルで一部だけ指定できる。

| 項目 | 今できること | 今できないこと |
| --- | --- | --- |
| リポジトリの種類 | 初期設定で 5 つの代表のリポジトリの種類（Web サービス 2 通り、モバイルアプリ、業務文書、プラグイン）から選ぶと、ブランチの使い方とリリースの方法の初期値が入る。バージョンを持たないサービス向けの初期値もある | 選んだ種類は作成の記録として残るだけで、通す工程や課題を閉じる条件は種類で変わらない |
| 工程の要否 | 工程を「行わない」と理由つきで設定でき、すべてのスプリントに効く。承認が要る工程は無効にできない | モードを指定して無効にすることはできない。工程の名前を書き間違えても知らせが出ない（コードを読んで確認） |
| 課題を閉じる条件 | NDF の手順書に固定されている | 条件を設定で外すことはできない |
| 設定の確かめ | 設定の形が正しいか、解析した後にリポジトリが変わっていないかを確かめる | 種類と流れの設定が食い違っていても知らせない |

### エンジニア向けの補足

- 種類は `.ndf/project.json` の `branch_strategy.kind`（`web-develop`・`web-trunk`・`mobile`・`docs`・`plugin`・`custom`）。スキーマは「作成の記録」と定義している。`web-trunk` の初期値は `release.version_store.kind: none`・`approval.target: production_pr` である。初期値の一覧は [branch-strategy-presets.json](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/contracts/data/branch-strategy-presets.json)
- 工程の恒久の無効化は `workflow.stages.<工程>` の `{"enabled": false, "reason": "..."}`。優先順位は スプリントの `--disable` > この設定 > 工程の定義の条件（`plugins/ndf/src/ndf/progress/stages.py` の `resolve_enabled`）。`plugins/ndf/tests/progress/test_command.py` と `test_run.py` の 176 件が通ることを確認した（2026-11-27、コミット `ea401b56a`）
- 工程の並びは `plugins/ndf/contracts/workflow/modes/<モード>.json`。閉じる条件は [progress-tracking の手順書](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/progress-tracking/SKILL.md) の「閉じる条件」
- 設定の確かめは `ndf project check`

## 何を足すか・変えるか

| 変わる点 | 今 | 足した後 |
| --- | --- | --- |
| リポジトリの種類 | ブランチとリリースの初期値だけを決める | 種類ごとに、通す工程、課題を閉じる条件、リリースで求める結果の既定を持つ |
| 工程の要否 | すべてのモードにまとめて指定する | モードごとにも指定できる |
| 課題を閉じる条件 | 固定 | リリース後テストの記録と振り返りの行を、設定で条件から外せる |
| リリース後テストの対象 | 配ったプログラムを導入して確かめる前提の記録 | バージョンを持たないサービスでは、反映した環境を対象にできる |
| 設定の確かめ | 形と古さだけ | 種類と流れの設定の食い違いと、無い工程の名前も知らせる |
| 文書 | 流れの決まりが複数の手順書に分かれる | 種類ごとの流れの定義を 1 か所で読める |

## 今の利用者への影響と互換

流れの設定を何も足さないリポジトリは、今と同じに動く。工程の恒久の無効化を既に書いているリポジトリで、工程の名前に誤りがあれば、この変更の後は止まって知らせる。

## なぜ困るか

NDF を導入した Web アプリケーションの開発が、工程の途中で止まる。止まるたびに人が結果を手で作る回避が要り、手で作った記録は実際の作業と食い違うおそれがある。観測したプロジェクトは進行が妨げられており、利用者が急ぎの対応を指示した。

流れの形が NDF の中に固定されたままだと、プロジェクトの形が違うたびに個別の直しが要る。

## 目的

プロジェクトが自分のリポジトリの形に合う開発の流れを設定で選べるようにする。バージョンを持たないサービスのリポジトリでも、手作業の回避なしにスプリントを最後まで流せる状態にする。

## 対象範囲

含む:

- リポジトリの種類ごとの、工程の要否・課題を閉じる条件・リリースで求める結果の既定
- モードごとの工程の要否の設定
- 課題を閉じる条件のうち、リリース後テストの記録と振り返りの行を外す設定
- バージョンを持たないサービスで、反映した環境をリリース後テストの対象にすること
- 種類と流れの設定の食い違いを知らせる確かめ
- 種類ごとの流れの定義の文書

含まない:

- リリースの手順が結果を返せない不具合の直し（表の 1。 https://github.com/devbasex/ai-plugins/issues/4513 で別の作業として直す）
- 本番のブランチへのマージに承認が要るかの判定の直しと、リリースの届け先の設定が実態とずれたことの検知（表の 2。 https://github.com/devbasex/ai-plugins/issues/4579 で別の担当が直す。重ならないようにする）
- 再起動の後の再開（表の 3。 https://github.com/devbasex/ai-plugins/issues/4575 ）
- 設計の Pull Request の番号が結果に欠ける不具合（表の 5 の後半。 https://github.com/devbasex/ai-plugins/issues/4455 ）
- 自動テストの設定が無いリポジトリでリファクタリングの工程が動かないこと（ https://github.com/devbasex/ai-plugins/issues/4566 ）と、設定の無いリポジトリで設計の工程が始まらないこと（ https://github.com/devbasex/ai-plugins/issues/4337 ）
- 工程の順序の入れ替えと、NDF に無い閉じる条件を新しく足すこと（「起票者の推定」の S3・S4）

## 前提

- 前提 1: この要求の「サービス型」は、作業の変更を本番のブランチへ直接入れ、バージョンの保存先を持たないサービスを指す。今の初期設定の `web-trunk` がこれに当たる。名前を新しくするか、今の種類を使うかは設計で決める
- 前提 2: 受け入れ条件 2 の判定は、 https://github.com/devbasex/ai-plugins/issues/4513 の直しがリリースされた状態で行う

## 受け入れ条件

以下の「サービス型の設定」は、前提 1 のサービス型で、`main` へのマージが本番への反映になることを指定した設定を指す。

- [ ] 1. 流れの設定を何も足していないリポジトリでは、モードごとの工程の並びと要否、課題を閉じる条件、工程が求める結果が、変更の前と同じである
- [ ] 2. 前提: サービス型の設定をしたリポジトリがある。操作: モードが `standard` のスプリントを、要求の工程から棚卸しの工程まで流す。結果: バージョン番号・タグ・GitHub Release が無いことを理由に止まる工程が 1 つも無く、工程の結果を人が手で作らずに終わる
- [ ] 3. 設定でリポジトリの種類を指定してスプリントを作ると、その種類の既定で行わない工程が、理由つきで工程の一覧に表示される
- [ ] 4. 設定でモードを指定して工程を無効にすると、そのモードのスプリントではその工程が理由つきで飛ばされ、ほかのモードのスプリントでは実行される。理由の無い無効化は、理由を示して止まる
- [ ] 5. 承認が要る工程は、種類の指定でもモードごとの指定でも無効にできない。無効にする設定があると、スプリントを作らずに理由を示して止まる
- [ ] 6. 設定でリリース後テストの記録を閉じる条件から外すと、記録の無い課題も、ほかの条件を満たせば閉じられる。閉じた報告に、設定で外した条件が載る
- [ ] 7. 設定で振り返りの行を閉じる条件から外すと、本文に「振り返り:」の行が無い課題も、ほかの条件を満たせば閉じられる。閉じた報告に、設定で外した条件が載る
- [ ] 8. リリース後テストの記録に不合格の行がある課題は、どの設定でも閉じない
- [ ] 9. サービス型の設定では、反映した環境を対象にしたリリース後テストの結果を、バージョン番号を持たずに記録でき、課題を閉じる判定がその記録を読める
- [ ] 10. 設定の確かめ（`ndf project check`）は、次のそれぞれで食い違う箇所と理由を示す。食い違いの無い設定では示さない
    - (a) NDF が知らないリポジトリの種類を指定した
    - (b) 存在しないモードか工程の名前を指定した
    - (c) 工程を行わないと設定したのに、課題を閉じる条件がその工程の記録を求めている
    - (d) バージョンを持たない設定なのに、バージョンを求める流れを指定した
- [ ] 11. 受け入れ条件 10 の (a) か (b) に当たる設定では、誤った項目を無視して工程を流さず、スプリントを作る時点で理由を示して止まる
- [ ] 12. 利用者は、種類ごとの工程の並びと要否、課題を閉じる条件、本番への承認が要る場面、リリースで求める結果を、1 つの文書で読める
- [ ] 13. NDF は、利用者の流れの設定を、利用者の承認なしに書き換えない

## 起きたこと

NDF の開発フロー（工程・プラン・hook・承認ゲート）が、ai-plugins 自身の開発（プラグインの配布物をバージョンを付けてリリースする）を前提にした手順を、そのまま Web アプリケーション開発のリポジトリへ持ち込み、そのリポジトリに合わない自動の流れを作ることがある。Web アプリケーション（サービス型。`main` への push でパイプラインが自動で反映する）のリポジトリで、スプリントを数本流した間に、次の例が出た。

| 1 | リリースの工程 | バージョンを持たないサービスで、release のステップが outputs を返せず失敗を繰り返した。オーガナイザーが、規約に合う出力を手で作って `ndf progress finish` を打つ回避を使った（#4513） | リリースはバージョン・タグ・GitHub Release を持つ配布物である |
| 2 | マージの判定 | `release.deliveries` が実態とずれると、スプリントの PR が承認ゲートなしで本番チャネルへマージされた（#4579） | 反映は、承認を伴う手動のリリースである |
| 3 | 並列の計画 | コンテナの再起動の後の再開手順が無い（#4575） | 長く動く常駐の開発環境である |
| 4 | 完了の条件 | 課題を閉じる条件が、機械可読なリリース後テストの記録と、課題本文の「振り返り:」の行を求めた。Web アプリケーションのリポジトリでは、リリース後テストの対象が配布物ではなく、反映した環境である | 配布物の導入をリリース後に確かめる |
| 5 | リファクタリング工程 | `gh` の案内文が PR 番号に混ざって失敗した。設計を流し直すと、出力の `design_pr` が欠けた | 原因は未調査（ai-plugins の流れの形を前提にした読み取りの可能性がある） |

このうち 1〜4 に共通するのは、フローの形（どの工程を通すか・何を完了の条件とするか・マージとリリースの判定・出力の形）が、NDF の中に固定されていて、プロジェクトが設定で選べないことである。

## 求めること

プロジェクトごとのフローを、設定ファイル（たとえば `.ndf/flow.json`）で規定できるようにする。NDF の既定は今のとおり（ai-plugins 型）にして、設定で別の型を選べるようにする。

1. **開発の型（archetype）を選ぶ:** たとえば `plugin`（今の既定）と `web-service`（サービス型。バージョンを持たず、`main` へのマージが反映になる）。型ごとに、既定の工程・完了の条件・リリースの判定を持つ
2. **工程の要否と順序を、モードごとに上書きできる:** 今の `--disable <工程>=<理由>` を、設定で恒久にできる。たとえばリリース後テストの対象を「反映した環境」にする
3. **完了の条件を、プロジェクトが決められる:** 課題を閉じる条件（リリース後テストの記録・振り返りの行など）を、設定で外す・足す
4. **マージとリリースの判定を、設定で明示する:** `release.deliveries` が実態とずれたときに、気づける・危険側に倒れる（#4579）
5. **出力の形（outputs）を、型ごとに持つ:** バージョンを持たないサービスで、release のステップが失敗しない
6. **設定の検証:** `ndf project check` が、型と設定の食い違い（トランク型で自動の反映があるのに `deliveries` が `manual` など）を警告する

## 受け入れ条件（案）

- 設定が無いプロジェクトでは、今と同じに動く（互換）
- `web-service` の型を選んだリポジトリで、スプリントを 1 本流すと、バージョンの出力を求める工程で失敗しない
- 型ごとのフローの定義が文書にあり、`ndf project check` で型と設定の整合を確かめられる
- 上の表の 1〜5 の再現が、`web-service` の型で解消している
