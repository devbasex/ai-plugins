## 目的

環境ブランチへ一部のコミットだけを届ける手順（`/ndf:cherry-pick-pr`）が、選んだコミットだけを届けるようにする。

- いまは、短命ブランチへベースブランチ全体を merge するため、手順の名前と説明（「必要なコミットだけを対象ブランチに届ける」）と結果が食い違う。ブランチ全体を環境へ届ける用途は別の Skill（`/ndf:deploy`）が持つ
- 原則 3 が守ろうとしている「CI が最新の起点を求める」ことは、Pull Request の宛先である環境ブランチの最新を取り込めば満たせる。ベースブランチを取り込む必要は無い（前提 1）
- 原則 3 は方針であり、変えるかは人が決める（プロジェクト MVV の「上位の原則 > 利用者の承認」）。この要求は原則 3 の書き直しを含み、設計承認ゲートで人が確かめる


## 事象

`cherry-pick-pr` の手順 5「ベースブランチを取り込む（必須）」は、環境ブランチ（`qa/*`・`staging/*`・`release/*`）から切った短命ブランチへ、開発のベースブランチ全体を `git merge "origin/$dev_base"` で取り込む。手順 6 はその後に、選んだコミットだけを cherry-pick する。

一部のコミットだけを環境へ届けたいのに、手順 5 の merge で開発のベースブランチにある別の機能もすべて入る。対象の修正がすでに開発のベースブランチへマージ済みなら、手順 6 の cherry-pick は空になって止まる。

根拠は `ndf-policies` の「ブランチ運用の原則」3（短命ブランチを push する前に開発のベースブランチを取り込む。CI に最新の起点が必須の Workflow があるため）である。

## 期待する結果

環境ブランチへ届くのは、選んだコミットだけになる。CI が最新の起点を求めるリポジトリでも、環境に入っていない別の機能は入らない。

## 再現手順

1. 開発のベースブランチ `develop` に、機能 A と修正 B がマージ済みである。環境ブランチ `qa/staging` には、どちらもまだ入っていない
2. `/ndf:cherry-pick-pr` で、修正 B だけを `qa/staging` へ届ける
3. 手順 5 の `git merge origin/develop` で、機能 A と修正 B の両方が短命ブランチへ入る
4. 手順 6 の `git cherry-pick -x <B>` は差分が無く、空のコミットとして止まる

文面から読んだ手順で、手元では動かしていない。

## 前提

- 前提 1: 「最新の起点を求める CI」が求めるのは、Pull Request の宛先（環境ブランチ）の先端を含むことである。GitHub の「マージ前にブランチを最新にする」の保護も、宛先のブランチに対して働く。宛先と別のブランチ（ベースブランチ）の先端を含むことを求める Workflow を持つリポジトリは、この課題では扱わない（未決 1）
- 前提 2: 選んだコミットの差分は、環境ブランチの上で cherry-pick できる。衝突したときの扱いは今の手順 6（解消して続け、解消の内容を報告に書く）のまま変えない
- 前提 3: 利用者が選ぶ対象は、feature ブランチのコミットか、ベースブランチへマージ済みの修正のコミットである。どちらでも元のコミットのハッシュが分かる
- 前提 4: ai-plugins は環境ブランチ（`qa/*`・`staging/*`）を持たない。受け入れ条件の確かめは、手元に作った使い捨ての git リポジトリで再現手順の状態を作って行う

## 用語

| 用語 | 意味 |
| --- | --- |
| 環境ブランチ | 検証や本番の環境へ載せるブランチ（`qa/*`・`staging/*`・`release/*` など）。`/ndf:cherry-pick-pr` の引数で指し、短命ブランチの Pull Request の宛先になる |
| 短命ブランチ | 環境ブランチの先端から切り、選んだコミットだけを cherry-pick して環境ブランチ宛の Pull Request を出すためのブランチ（`<元のブランチ>-for-<環境ブランチのスラッシュ以降>`）。マージした後に消す |

## 受け入れ条件

- [ ] 1: 再現手順 1 の状態（`develop` に機能 A と修正 B がマージ済み、`qa/staging` にはどちらも無い）で修正 B だけを選ぶと、push する短命ブランチと `origin/qa/staging` の差分のコミット（`git log origin/qa/staging..<短命ブランチ>`）は、修正 B を cherry-pick したコミットだけになる。機能 A のコミットとベースブランチとの merge のコミットは含まれない
- [ ] 2: 同じ状態で、修正 B の cherry-pick は空にならない。できたコミットのメッセージに、`-x` が足す元のコミットのハッシュの行がある
- [ ] 3: 手順 3 は、選ぶ修正がすでにベースブランチへマージ済みで `git log origin/<ベースブランチ>..HEAD` が空になる状態でも、その修正のコミットを利用者が選べる候補として示すか、候補が 0 件であることを示して選ぶコミットのハッシュを求める。候補が 0 件のまま手順 4 へ進まない
- [ ] 4: push の直前に `origin/<環境ブランチ>` を取得し直し、短命ブランチがその先端を含む状態で push する。手順 4 の後に環境ブランチへ別のコミットが入った状態で実行しても、push した短命ブランチは `git merge-base --is-ancestor origin/<環境ブランチ> <短命ブランチ>` が終了コード 0 になる
- [ ] 5: 選んだコミットのうち、変更がすでに環境ブランチにあるもの（cherry-pick が空になるもの）は空のコミットを作らずに飛ばし、飛ばしたコミットのハッシュを報告に並べる。選んだコミットがすべて飛ばされたときは、push も Pull Request の作成もせずに、その旨を報告して元のブランチへ戻る

## 影響

環境ブランチへ一部の修正だけを届ける利用者が困る。まだ環境で確かめていない機能が、気づかないまま qa・staging・release へ入る。

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない。`/ndf:cherry-pick-pr <環境ブランチ>` の引数は同じ |
| データ | 無し |
| 既存の振る舞い | 短命ブランチへベースブランチを merge しなくなる。環境ブランチ宛の Pull Request に、選んでいないコミットが載らなくなる。ベースブランチの先端を含むことを CI で求めるリポジトリでは、その検査が落ちるようになる（前提 1・未決 1） |
