# 工程「実装」がレビューの単位ごとに流す設計の決定の記録（#4369）

[設計書](./issue-4369-design.md)の「決定の記録」を分けた文書である。「入出力のコントラクト」「処理の流れ」「`impl` のプランのステップ」と不変条件の番号（I1〜I5）は設計書にある。

各決定の「根拠」と、決定 14 の番号は、次の 2 つの文書の項目を指す。

- Value <番号>: このリポジトリの判断基準（[プロジェクト MVV](../.ndf/mvv.md) のバージョン 11）の「Value」の項目
- C<番号>・P<番号>: 必ず人の承認が要る操作の表の行。C は [NDF の共通原則](./ndf-common-principles.md#必ず人の承認が要る操作)、P は [プロジェクト MVV](../.ndf/mvv.md#必ず人の承認が要る操作) にある

## 決定の記録

### 決定 1: 実装が 1 本にまとまる事象を早く止めるため、#3702 の実装を待たずに、単位を順に流す部分を先に入れる

- **質問**: #3702 の実装でこの課題を満たして確かめだけにするか、先に別の変更として入れるか（要求の未決 1）
- **選んだ案**: 先に入れる。単位を読む処理と流す処理は分ける。次の名前は #3702 の詳細設計に合わせる。流す処理のファイル（`progress/units_invoke.py`）、差し込み（`unit_file`）、工程のメタデータ（`per_unit`）。#3702 の実装は読み手を単位のファイルへ差し替え、流す処理に、並列実行と、入力が承認したものと同じかの確認を足す
- **理由**: 単位の大きな変更を流すたびに起きる事象で、直すのに要るのは「読んで順に流す」部分だけである。#3702 の残り（設計の工程の並びと承認ゲートの移動）を待つ必要が無い
- 採らなかった案: #3702 の実装で満たす（9 タスク・見込み約 3,550 行が入るまで同じ事象が起きる。表を読んで流すという受け入れ条件 1 には別の実装も要る）
- 採らなかった案: #3702 の単位のファイルの形をこの課題で先に作る（実装計画の書式を変えることになり、対象範囲の外）
- **代償**: 表の読み手は #3702 の実装で置き換わる。流す処理は #3702 で並列を足すときに書き直す部分がある
- 根拠: Value 5 / Value 11（MVV バージョン 11）。項目は「速く届く」、「重複と冗長が無い」

### 決定 2: 分けた変更が気づかれずに 1 本にならないよう、この課題では表だけの実装計画を表の順に流し、#3702 への移行後は止める

- **質問**: #3702 の設計は単位のファイルを持たない旧い形の実装計画を課題 1 つの 1 単位にする。受け入れ条件 1 とどちらに合わせるか（要求の未決 2）
- **選んだ案**: 受け入れ条件 1 に合わせる。扱いは時期で分かれる

| 時期 | 単位の表があり、単位のファイルが無い実装計画の扱い |
| --- | --- |
| この課題の実装から、#3702 の実装が入るまで | 表の単位を流す。実装計画の中の順は表の下に示す |
| #3702 の実装が入った後 | 単位の見出しがあるのに単位のファイルが無ければ止まる。表は読まず、1 単位にもまとめない |

- **この課題で流す順**（実装計画の中。正本は[設計書の「順序」](./issue-4369-design.md#順序)）:
  - 「実行順」の列があれば、プレリファクタリングをするかに関わらず、列の値の順に流す
  - 列が無ければ、表の行の順に流す。ただしプレリファクタリングをする場合は、「タスク分解」の最初のタスクを含む単位を先頭にする
- **#3702 の設計との違い**: #3702 の設計は、単位のファイルが無く区間の印（単位の表を生成して差し込む場所の印）も無い実装計画が、スプリントの起点に既にあれば、課題 1 つの 1 単位（`single`）にする（[#3702 の詳細設計](./issue-3702-design-detail.md)の「単位のファイルの集め方」）。#3702 の実装はこの判定を次の順に改める
  1. 単位のファイルが無い実装計画は、起点にあったかを調べる前に「レビューの単位」の見出しを調べる
  2. 見出しがあれば、起点にあった実装計画でも止まる
  3. 見出しが無ければ、#3702 の設計のとおりに判定する
- **理由**: 利用者が求めたのは、実装計画に書いた分け方のとおりに流れることである。表があるのに 1 本にすると、分けた意図が黙って捨てられる
- 採らなかった案: #3702 の設計に合わせて 1 単位にする（この課題の事象がそのまま残る）
- 採らなかった案: #3702 の後も表の読み手を残して 2 通りを読む（同じ事実の読み手が 2 つになる）
- **代償**: #3702 の実装が入った時点で終わっていないスプリントは、単位のファイルを書き足すまで工程「実装」が止まる
- 根拠: Value 3 / Value 8 / Value 11（MVV バージョン 11）。項目は「同じ手順は毎回同じ結果になる」、「正しいデータ構造で作られる」、「重複と冗長が無い」

### 決定 3: 同じ仕組みを 2 回作らないため、#3905 をこの課題へ統合する

- **質問**: 自動の経路で単位を実行しマージしてから `gathered` を記録する #3905 を統合するか（要求の未決 3）
- **選んだ案**: 統合する。#3905 の受け入れ条件は、この課題の受け入れ条件 1〜5 に含まれる。#3905 の条件は、単位ごとに実行しマージの後に記録する、未マージなら記録せずに止まる、欄が無ければこれまでのとおりにする、である。「設計の結果」の表で #3905 の扱いを「マージする」とし、設計の承認で確定する
- **理由**: #3905 が足すものはこの課題の流れの一部である。別に残すと、同じ処理を 2 回設計して確かめることになる
- 採らなかった案: 別の課題として残す（この課題の後には、足すものが無くなる）
- **代償**: #3905 は自分の受け入れ条件を単独では確かめず、#4369 の確かめで閉じる
- 根拠: Value 11（MVV バージョン 11）。項目は「重複と冗長が無い」

### 決定 4: 単位の無いスプリントの振る舞いを変えないため、工程の定義のステップは変えず、プランを呼ぶ層で単位の経路へ分ける

- **質問**: 単位の繰り返しをどこに置くか
- **選んだ案**: 工程「実装」の定義に `per_unit` を足し、プランを呼ぶ層（`invoke.py`）が単位の見出しの有無で分ける。単位の表の確かめは、これまでの差し込みの確かめと同じ時点で行う。そのため読めない表は工程を始める前に止まる。単位の経路に入るのは、`per_unit` を足した後に `ndf progress new` で作ったスプリントだけである。`ndf progress new` は工程の定義の写し（スナップショット）を保存し、そのスプリントは終わりまで保存した定義で進むためである
- **理由**: 単位があるかは実装計画を読むまで分からない。分けるのをプランの呼び出しに置けば、今ある打ち直しと差し込みの確かめをそのまま使え、単位の無いスプリントの流れは変わらない
- 採らなかった案: ステップを単位を流すスクリプトに置き換える（単位の無いスプリントでも、プランの打ち直しと事前の確かめの作り直しが要る）
- 採らなかった案: 単位の数だけ工程の行やステップを足す（工程の行はモード（変更の進め方の区分）の定義が決める。単位の数は、実装計画を書いた後にしか分からない）
- **代償**: 工程の定義を読むだけでは、単位の繰り返しがあることが `per_unit` の 1 語でしか分からない。実装計画から単位の見出しをすべて消して打ち直すと、これまでの経路で流れる
- 根拠: Value 3 / Value 9（MVV バージョン 11）。項目は「同じ手順は毎回同じ結果になる」、「責務の分かれた設計で作られる」

### 決定 5: 順序の食い違いと取り込みの衝突を生まないため、単位は並列にせず 1 つずつ流す

- **質問**: 同じ実行順の単位や、プレリファクタリングの単位の後の残りの単位を並列に流すか
- **選んだ案**: 1 つずつ流し、前の単位のマージの後に次の作業場所を切る
- **理由**: 単位が触るファイルは実装計画の表に無く、重なりを前もって確かめられない。順に流せば、後の単位は前の単位の変更の上で作られる
- 採らなかった案: 並列に流す（重ならないことを機械で確かめられない。並列は触るファイルと承認を持つ #3702 が足す）
- **代償**: 単位が多いスプリントは、supervisor が並列に回すより遅い
- 根拠: Value 3 / Value 9（MVV バージョン 11）。項目は「同じ手順は毎回同じ結果になる」、「責務の分かれた設計で作られる」

### 決定 6: 打ち直しで済んだ単位をやり直さないため、スプリントブランチ宛ての単位の PR がマージ済みかで完了を見分ける

- **質問**: どの単位が済んだかを何で持つか
- **選んだ案**: 別の記録を作らない。単位のブランチを head、スプリントブランチを宛先とする PR にマージ済みのものがあれば、その単位を飛ばす。単位のブランチ名はスプリントブランチ・代表の課題・単位の名前から決まるので、別のマシンの打ち直しでも同じ名前になる
- **対象にする PR**: 対象のリポジトリのブランチから出た PR だけである。単位のブランチ名は公開の情報から決まるので、フォークが同じ名前のブランチから PR を出せる。単位の PR を探す次の 3 か所は、head・宛先・フォークでないことを同じ条件にする。`impl` の `conflict-check`・`ci`・レビューは自分では探さず、`pr` のステップが決めた番号を使う（設計書の「PR の番号」）
  - 完了の判定: `adapters/github.py` で head と宛先を絞り、マージ済みの PR をまとめて読み、フォークの PR を除く。今の `pulls_by_head` は head だけで直近 5 件を読むので、そのままでは使わない
  - `impl` の `pr` の、開いた PR があるかの確かめ（共有のステップの `probe`）
  - `ndf ci merge --pr` が番号の PR を確かめるとき
- **`impl` の `done-check`**: 単位の経路では外す。上の「完了の判定」の結果を使い、単位ごとに同じ照会を繰り返さないためである。残すと、head だけで探す今の `done-check` が別の宛先のマージ済み PR を完了と読み、レビューせずに終わることもある
- **理由**: この課題の目的は、自動の経路でも単位ごとに PR とレビューを通すことである。マージ済みの PR はその結果そのもので、GitHub が持っている。マージコミットに記録を持つ専用の仕組みは目的に要らない。この設計は 2026-11-26 に cross-review（AI による相互レビュー）で見直した。その回では指摘がその仕組みに集まり、指摘が出なくなる状態にならなかった。そこで利用者は 2026-11-26 に、単位の完了を記録する専用の仕組みを持たないと決めた
- 採らなかった案: マージコミットの本文に単位の記録を持ち、取り消しも判定する（専用のマージと、打ち消しの読み方と、履歴の照合が要る）
- 採らなかった案: 手元のファイルにだけ記録する（別のマシンの打ち直しで、済んだ単位を確かめられない）
- **代償**（利用者が受け入れた）: マージした単位の変更を後で打ち消しても気づかず、完了した単位として飛ばす。同じ理由で、マージ済みの単位のタスクや条件を後で直しても飛ばす。直した内容を流すには、新しい名前の単位に分ける。工程の外（GitHub の画面など）でマージした単位の PR も完了と読む
- **工程の外でのマージの扱い**: 受け入れ条件 4 と不変条件 I2 は、工程がするマージの条件である。工程の外でのマージは次のように扱う
  - 工程が完了の根拠にするのは、head と宛先が単位のもので、フォークでないマージ済みの PR があることだけである。レビューが収束したか、レビューした HEAD か、人の判断を待つ指摘（決定 14）が残っていないかは確かめない
  - 残っていた指摘は、解消されたとも承認されたとも扱わない。工程に分かるのは、PR がマージされた事実だけである。GitHub のマージの権限からは、誰がどの指摘を承認したかは分からない。工程は、指摘が残る単位を自分ではマージしない
  - 開始時にマージ済みと分かって飛ばした単位は、結果の状態を `already_merged` にし、PR の番号を示す。後の工程と利用者は、その単位の指摘の解消が未確認だと分かる。指摘の中身は、単位の PR の cross-review の記録にある。工程は読み直さない
  - 前の試行で工程自身がマージした単位も `already_merged` になる。単位の完了を記録する仕組みを持たないので、工程の外でのマージと見分けないためである
- 根拠: Value 3 / Value 11（MVV バージョン 11）。項目は「同じ手順は毎回同じ結果になる」、「重複と冗長が無い」

### 決定 7: 分けたはずの単位を落とさないため、表は決めた形だけを読み、読めなければ始めずに止まる

- **質問**: 実装計画を書く側の表記の揺れ（注記・範囲・番号の省略・「無し」）をどこまで受けるか
- **選んだ案**: 「入出力のコントラクト」の読み方の表の形を受ける。複数の課題の実装計画で、最初の要素に課題が無いセルは受けない。表のセルの分け方は、受け入れ条件の確認の表を読む既存の部品を使う
- **理由**: 読み違えた単位は、実装もレビューもされないまま `gathered` の後ろへ進む。始める前に止まれば、直すのは実装計画の 1 行で済む
- 採らなかった案: `<課題>:<番号>` だけを受ける（今ある実装計画の多くが範囲や番号の省略を使い、止まる）
- 採らなかった案: 読めない行を飛ばして残りを流す（落ちた単位に気づけない）
- **代償**: `5a` のような番号で条件を指す実装計画は、番号を直すまで止まる
- 根拠: Value 3 / Value 13（MVV バージョン 11）。項目は「同じ手順は毎回同じ結果になる」、「確かめたことだけが済んだとされる」

### 決定 8: 単位の外の変更が単位の PR に入らないよう、単位の指示のファイルを実装・修正・レビューのすべてに渡す

- **質問**: 単位の範囲を、実装する worker と、後からコミットする修正担当へどう伝えるか
- **選んだ案**: 単位を流す処理が指示のファイルを単位の保存先に書く。中身は、単位の名前・含むタスク・満たす条件・実装計画のパス・単位の外の扱いと、下の例外である。届け方は次のとおりである

| コミットする経路 | 届け方 |
| --- | --- |
| 実装（`impl`）、手元のテストが落ちたときの修正（`fix`）、CI の修正（`ci-fix`）、push の拒否の修正（`fix-push`）、衝突の解消（`fix-base`） | worker の起動指示の入力 `unit_file` |
| レビューの修正担当（単位のレビューと差分のレビュー） | 環境変数 `NDF_UNIT_FILE`。相手役の指示にも同じ範囲を載せ、後の単位が担う条件を未達の指摘にしない（下の例外を除く） |

- **単位の外の変更が要るとき**: 単位の外を変えてよいのは、今の単位の変更が原因でテスト・CI が失敗するか、レビューで指摘を受け、直すのに単位の外の変更が要る場合だけである。変更は最小にし、コミットメッセージに理由を書く
  - 今の単位の変更が原因でない失敗（変更の前からあるテストや CI の失敗など）は直さない。原因が今の単位の変更だと確かめられない場合も同じである
  - 後の単位のタスクは実装しない
  - 直さない失敗が残る場合と、後の単位のタスクを実装しないと通らない場合は、理由を返し、単位がそこで止まる
- **例外（担当の単位にかかわらず、今の PR で扱う指摘）**: 今の差分に含まれる、秘密・認証認可・利用者のデータ・戻せない操作の問題は、相手役（レビューする AI）が必ず指摘する。修正担当は、その指摘を後の単位を理由に見送らない
- **見送りの区分**: 修正担当が後の単位の範囲を理由に見送る指摘には、区分 `not_applicable` と担当の単位を書く
- **理由**: 単位の PR を読み切れる大きさに保つには、後からコミットする修正担当にも同じ範囲が要る。範囲を理由に危険な指摘が後回しにならないよう、例外を置く
- 例外の根拠: 秘密・利用者のデータ・戻せない操作に関わる指摘は直される（Value 7）
- 採らなかった案: 初回の `impl` にだけ渡す（テストや CI が落ちたときに、修正担当が後の単位のタスクまで実装できる）
- 採らなかった案: 受け入れ条件の指定だけで絞る（1 つの条件が複数の単位にまたがる表があり、条件を持たないプレリファクタリングの単位もある）
- 採らなかった案: 課題の本文のコピーへ範囲の指示を足す（同じファイルが PR の本文になり、課題の本文と食い違う）
- **代償**: 設定でレビューや worker の起動を差し替えたリポジトリは、`unit_file` と `NDF_UNIT_FILE` を読む側も合わせる必要がある。範囲を守るのは指示で、差分を機械では確かめない
- 根拠: Value 3 / Value 9（MVV バージョン 11）。項目は「同じ手順は毎回同じ結果になる」、「責務の分かれた設計で作られる」

### 決定 9: 条件を持たないプレリファクタリングの単位を流せるよう、突き合わせないことを引数で明示する

- **質問**: 「満たす受け入れ条件」が「無し」の単位の確かめをどうするか
- **選んだ案**: `ndf loop acceptance check` に `--no-criteria` を足し、条件の無い単位には `--issue <代表の課題> --no-criteria` を渡す
- **理由**: プレリファクタリングの単位は、突き合わせる受け入れ条件を持たない。条件の渡し忘れと区別するため、突き合わせないことは引数で書く
- 採らなかった案: `--issue` だけを渡す（課題のすべての条件を突き合わせ、プレリファクタリングの単位が必ず止まる）
- 採らなかった案: 条件の無い単位を読めない表にする（プレリファクタリングの単位を持つ実装計画が実際にある）
- **代償**: 条件の漏れはこの単位では見つからない。工程「完了判定」がすべての条件を確かめる
- 根拠: Value 11 / Value 13（MVV バージョン 11）。項目は「重複と冗長が無い」、「確かめたことだけが済んだとされる」

### 決定 10: 後の工程をこれまでの入力のまま流すため、すべてのマージの後に工程「実装」がスプリントの PR を開く

- **質問**: 単位の経路ではスプリントの PR を誰も作らない。リファクタリングとコードレビューはそれを読む
- **選んだ案**: 最後のマージの後に、これまでのテンプレート `pr` を push のステップ（`push`・`fix-push`）を外して流し、スプリントブランチからベースブランチ宛ての PR を開く。単位のレビューを経ないコミットを、最後の処理で作らないためである。開いた PR があれば作らない。マージはしない。テンプレートの `refs` にはスプリントのすべての課題を渡す。既存の PR の本文に `Refs` の欠けがあれば、テンプレートの今の振る舞いのまま `incomplete` で止まる
- **理由**: 単位の経路でスプリントの PR を作れるのは、最後のマージを知る工程「実装」である
- 採らなかった案: 後の工程の側で PR が無ければ作る（作る場所が 2 つ以上になる）
- 採らなかった案: スプリントの PR の前に、リモートの履歴がレビューを経た単位のマージ結果だけかを照合する。マージの方式（merge・squash・rebase）ごとにマージ結果を再現する照合が要り、実装のレビューで抜け道の指摘が続いた。単位のマージは `ndf ci merge --reviewed` がレビューした HEAD を確かめ、スプリントの PR の前はリモートの先端が作業場所の HEAD と同じかを確かめ、スプリントの PR 自体もコードレビューを通るので、それで足りる
- **代償**: 工程「実装」の仕事が 1 つ増える
- 根拠: Value 3 / Value 11（MVV バージョン 11）。項目は「同じ手順は毎回同じ結果になる」、「重複と冗長が無い」

### 決定 11: 安全さを今の supervisor の手順と同じにするため、`ndf ci merge --reviewed` でマージし、宛先と PR の番号の確認だけを足す

- **質問**: 単位の PR をどうマージするか
- **選んだ案**: `ndf ci merge --pr <番号> --branch <単位のブランチ> --base <スプリントブランチ> --reviewed <レビューした HEAD>` を使う。今のコマンドは、作業場所の HEAD か PR の HEAD がレビューした HEAD と違えばマージしない。足すのは `--base` と `--pr` である。`--pr` には `impl` がレビューと CI の確認に使った PR の番号を渡し、その PR がマージされないまま閉じられているか、head・宛先・head のリポジトリが違えば止める。同じブランチ・宛先・HEAD で作り直された PR を、レビューしないままマージしないためである。`--base` は、対象の PR の宛先が違えばマージの要求を送らない。今の `GitHub.merge` は CLI が指定した PR を読み直し、その時点の宛先でマージの方式を選ぶ。そのため期待する宛先を `GitHub.merge` へ渡し、読み直した PR の宛先が違えば、直接のマージもマージキューへの投入も送らない。マージの方式の選び方、マージキュー、本文の残リスクの確かめは今のままである
- **理由**: 目的は自動の経路でも単位ごとに PR とレビューを通すことで、supervisor が使っているマージで足りる。受け入れ条件 4 が求める宛先の確認は今のコマンドに無いので足す（利用者の決定、2026-11-26）。PR の番号の指定は、レビューと CI の確認をした PR だけをマージするために足す
- 採らなかった案: 工程が merge commit を作ってスプリントブランチへ直接 push する（保護の読み取り、完了の記録、PR の後処理まで要る。決定 6 に書いた 2026-11-26 の設計のレビューで、指摘がここに集まった）
- 採らなかった案: 工程の中で PR を読んで宛先を確かめ、コマンドは変えない（読む PR とマージする PR を 2 か所で選ぶことになる）
- **代償**（利用者が受け入れた）: マージ先を最後に確認してからマージの要求が届くまでの間に、PR の宛先が書き換えられても気づけない。PR をマージする GitHub の API は、宛先を条件にできないためである。サーバー側で拒否する条件（ブランチの保護など）を自動のマージの前提にはしない
- 根拠: Value 3 / Value 11（MVV バージョン 11）。項目は「同じ手順は毎回同じ結果になる」、「重複と冗長が無い」

### 決定 12: 単位の数で流れを変えないため、単位が 1 つでも単位の PR とスプリントの PR の 2 本にする

- **質問**: 単位が 1 つのときは、分ける効果が無いのに PR の作成とマージが 1 回ずつ増える。これまでの経路を使えるか
- **選んだ案**: 使わず、PR を 2 本にする
- **理由**: 受け入れ条件 1・4 は、表があれば単位の数に関わらず、次を求める。単位のブランチ、スプリントブランチ宛ての PR、単位の受け入れ条件の `--criteria`、レビューした HEAD だけのマージである。これまでの経路は単位の範囲の指示も単位の受け入れ条件も渡さない
- 採らなかった案: 全体で 1 単位ならこれまでの経路を使う（要求の受け入れ条件を変える必要がある）。分けるつもりが無い課題は、実装計画に単位の見出しを置かなければこれまでの経路になる
- **代償**: 1 単位のスプリントでは、PR の作成とマージが 1 回ずつ増える。両方の PR で CI が走る設定では、CI も 1 回増える
- 根拠: Value 3（MVV バージョン 11）。項目は「同じ手順は毎回同じ結果になる」

### 決定 13: スプリントブランチ宛てで起動しない CI があっても流せるよう、単位の PR で待つチェックを宣言で選べるようにする

- **質問**: 必須のチェックの宣言（`ci.required_checks`）は、ベースブランチ宛ての PR を前提にする。単位の PR にも同じものを待つか
- **選んだ案**: 設定に `workflow.unit_required_checks`（チェックの名前の並び）を足す。スプリントの PR で待つチェックは、これまでのとおり `ci.required_checks` である

| 値 | 単位の PR の CI の完了の確認 |
| --- | --- |
| 書かない | `ci.required_checks` を待つ |
| 名前の並び | その名前を待つ |
| 空の並び | 待たない |

- **実装前の確かめ**: 開始前の確かめは、単位の PR の宛先、待つチェックの名前、その名前を読んだ設定のキーを結果に出す（出す時点と項目は設計書の「開始前の確かめ」）。起動しないチェックを待って止まった場合の理由にも、このキーを書く
- **空の並び**: `impl` のプランからステップ `ci` を外す。`ndf ci watch` はチェックの名前が 1 つも無いと起動できないためである
  - 外すときは、手元のテストのステップを外すのと同じ関数（`route.without_steps`）を使う。`ci` を指すルート（`push-fixed` の `next` など）は、`ci` の次の `head-reviewed` へ付け替わる
  - `ci` の失敗からしか到達しないステップ（`repeat-check`・`ci-fix`・`ci-local`・`push-fixed`）も一緒に外す
  - `ci` と、一緒に外すステップだけが使う差し込み（`required` など）と作業の入力は求めない。外す前のプランで要る差し込みを数えると、`ci.required_checks` を持たない設定が値の不足で止まる
- **理由**: CI の起動の条件はリポジトリごとに違い、スプリントブランチ宛ての PR で起動しないチェックを待つと、最初の単位から進めない
- 採らなかった案: `ci.required_checks` をそのまま使う（ベースブランチ宛てでだけ CI が起動するリポジトリは進めない）
- 採らなかった案: `ci` の下にキーを足す（`ci` はプロジェクトの解析が書く値で、利用者が選ぶ値は `workflow` に置く）
- 採らなかった案: CI の定義を読んで起動を機械で判定する（起動の条件の書き方は CI の提供元ごとに違う）
- **代償**: 空の並びや少ない並びを宣言すると、その分の検査はスプリントの PR まで行われない
- 根拠: Value 4（MVV バージョン 11）。項目は「どのプロジェクトでもそのまま使える」

### 決定 14: 利用者の承認を設計と本番の 2 回に保つため、人の判断を待つ指摘が残る単位は、分類を問わずマージせずに止める

- **質問**: レビューで人の判断を待つ指摘が残った単位を、どう扱うか
- **選んだ案**: 1 件でも残れば、その単位で止める。単位の名前と理由（指摘）を示し、後の単位は始めず、`gathered` を書かない。単位の承認の仕組みは作らない
- **理由**: 利用者の承認は設計と本番の 2 回のままになる。指摘の分類で通すものと止めるものを分けないので、分類の漏れでマージされることが無い

「人の判断を待つ指摘」は次の 2 種類である。種類は用語集の「レビューの保留」と同じで、見るのはその回のレビューの結果だけである。

| 種類 | 中身 |
| --- | --- |
| 必ず人の承認が要る操作に当たる指摘 | 秘密に触れる操作（C1）や、リリースの経路の外で配布物を変える操作（P3）のように、必ず人の承認が要る操作の表の行（C<番号>・P<番号>）を相手役が付け、直した（`fixed`）と記録されていないもの。見送っても、区分を問わず残る |
| 利用者の判断を待つ見送り | 修正担当が見送り、区分が `needs_user`、区分が無い、知らない値のどれかのもの |

直していない通常の指摘が残る単位も、これまでの `impl` と同じく `incomplete` で止まる。

- **どう止まるか**: 単位の経路は、レビューの起動の後ろに `--stop-on-hold` を足す。渡したレビューは、人の判断を待つ指摘が残ると `incomplete` で終わる。このとき `impl` のプランは、未解決の指摘が残った場合の今の流れと同じく、CI まで進めてから止まる。初回のレビューで残った指摘は、後の差分のレビューが通っても消えない。理由には単位の名前と PR の番号を示し、結果に欠けがあれば並べる。指摘の全文は単位の PR の cross-review の記録にある
- **打ち直し**: 次の回の保存先で流し、レビューは最初からになる。修正をコミットするなどで HEAD が変わっていれば `test`（手元のテスト）のステップから、変わっていなければ `push` のステップから流す（条件は設計書の「打ち直し」、ステップの並びは「`impl` のプランのステップ」）。前の回の指摘をこの設計で持ち越すことはしない
- **利用者の直し方**: 指摘のとおりに直すか、指摘された変更を単位から取り除いてコミットし、`ndf progress next` を打ち直す。今の cross-review は、次の 2 つを次の回へ引き継ぐ（この変更では変えない）。1 つは、cross-review が PR に付けて resolve されていないスレッドである。もう 1 つは、スレッドを作れず、cross-review の記録の PR コメントにだけ残った未解決の指摘である。直した指摘のスレッドは打ち直す前に resolve する。スレッドの無い指摘が残る場合は、直した上で単位の PR を閉じると、次の回が新しい PR を作る
- 採らなかった案: 前の回の指摘をファイルに残し、次のレビューへ渡して解けるまで止める（持ち越しと解く条件の仕組みが要る。決定 6 に書いた 2026-11-26 の設計のレビューで、指摘がここに集まった。利用者の決定）
- 採らなかった案: 単位ごとに利用者の承認を受けて工程がマージする（承認の回数が単位の数だけ増える）
- 採らなかった案: 指摘を残したままマージし、本番の承認で見る（受け入れ条件 4 に反し、人が判断していない変更の上に後の単位が積まれる）
- **代償**（利用者が受け入れた）: 打ち直したレビューが前回と同じ指摘を挙げなければ、直していなくてもマージされる。また、利用者が直さなくてよいと判断しても、承認するだけで単位を進める手段は無い。指示書の書き換えのように必ず人の承認が要る操作を含む単位は、相手役がそれを指摘するかぎり自動の経路では通らない
- 根拠: Value 1 / Value 9（MVV バージョン 11）。項目は「人の判断を大事な所だけにする」、「責務の分かれた設計で作られる」

### 決定 15: この課題の目的に絞るため、単位の作業場所とブランチは自動で消さない

- **質問**: マージした単位の作業場所と、手元とリモートのブランチを工程が消すか
- **選んだ案**: 工程「実装」は消さない。今の工程「クリーンアップ」はスプリントブランチの PR だけを扱い、単位の作業場所とブランチは拾わない。単位の作業場所は `.worktrees/` の下に作るので、人が `ndf worktree cleanup` を打てば、PR がマージ済みで変更の残らない作業場所が外れる。git がマージ済みと認めないローカルブランチと、リモートのブランチは残る
- **理由**: 目的は自動の経路でも単位ごとに PR とレビューを通すことで、後片付けは目的に要らない。工程が作ったものだけを消すには作った記録と照合が要る。決定 6 に書いた 2026-11-26 の設計のレビューで、指摘がここに集まった（利用者の決定）
- 採らなかった案: 作った記録を持ち、一致するものだけを消す（同じ名前で作り直されたものを区別できない場合が残る）
- **代償**（利用者が受け入れた）: 単位の数だけ作業場所とブランチが残る
- 根拠: Value 11（MVV バージョン 11）。項目は「重複と冗長が無い」

### 決定 16: リモートで足された単位を見落とさないため、単位の見出しが無いスプリントでも、実装の開始時にブランチを取得する

- **質問**: 単位があるかの判定に、追加の取得が要るか。単位を使わない利用者にも、git の起動とリモートへの照会が 1 回ずつ増える
- **選んだ案**: `per_unit` の工程の開始時に、作業場所が今いるブランチを 1 回取得する
- **理由**: 別の作業場所で足された単位の表は、実装を始める時点のリモートの先端を読まないと分からない。見落とすと、分けるはずの変更が 1 本の PR になる。取得 1 回は、worker とレビューの起動に比べて費用が小さい
- **この案を選ぶ条件**: 実装を始める前に、同じブランチの先端と中身を取得する処理がほかに無いこと。2026-11-26 のコードで `ndf progress` がブランチを取得するのは、2 か所だけである。`gathered` の記録（実装の後）と、レビューしていない差分の判定（コードレビューの工程）である。実装の開始の直前に同じ取得をする処理ができたら、その結果を使い回して追加の取得をやめる
- 採らなかった案: 工程「計画」が実装計画のコミットを記録し、工程「実装」へ渡す（記録した後に別の作業場所で足された単位が分からない。工程「計画」を通らずに実装計画を書き足した場合も同じである）
- 採らなかった案: 既にある取得の結果（手元の `refs/remotes/`）を読む（いつ取得したものか分からず、古ければ見落とす）
- 採らなかった案: 先に `git ls-remote` で先端を調べ、手元と違うときだけ取得する（リモートへの照会は 1 回のままで減らず、違うときは 2 回になる）
- **代償**: 単位を使わないスプリントも、工程「実装」の開始のたびに取得の時間がかかる。リモートへ届かないときは、実装を始めずに止まる
- 根拠: Value 2 / Value 3（MVV バージョン 11）。項目は「安く使える」、「同じ手順は毎回同じ結果になる」

### 決定 17: CI の監視の手順を 1 か所に保ち、シェルの起動も増やさないため、PR の番号の取り方はテンプレートの展開の時点で共有のステップへ組み込む

- **質問**: 共有のステップ `ci` は PR の番号をブランチから引き、`impl` の `ci` は保存した番号を読む。違うのは番号の取り方だけである。残りの手順（`pipefail`、`ndf ci watch`、結果の保存、引数の組み立て）をどう共有するか
- **選んだ案**: 共有のステップは、番号の取り方をキー `pr_source` に持つ。`pr_source` は、番号を出力するコマンド（`command`）と、その引数（`arg`）の組である。テンプレートを展開する時点で、`command` を Bash のスクリプトの `@pr_command` へ、`arg` を引数の並びの `@pr_arg` へ差し込む。`impl` は `pr_source` だけを上書きする
- **理由**: 番号の取り方はテンプレートごとに決まり、実行時に選ぶものは無い。展開の時点で組み込めば、監視の起動と結果の保存は `parts/steps.json` の 1 か所に残り、シェルの起動は増えない。`arg`（ブランチ名や保存先のパス）は位置引数で渡すので、シェルのコードとして解釈されない
- 採らなかった案: `impl` が `ci` の `run` を丸ごと上書きする（監視の起動と結果の保存が 2 か所になり、変えるときに両方を直す）
- 採らなかった案: 番号を取るコマンドを引数で渡し、実行時に `sh -c` で打つ（`ci` のステップのたびにシェルの起動が 1 回増える）
- **代償**: テンプレートの展開に、差し込みの形がもう 1 つ増える。`parts/steps.json` の `ci` の `run` は、展開しないと実行できない
- 根拠: Value 2 / Value 11（MVV バージョン 11）。項目は「安く使える」、「重複と冗長が無い」
