# 工程「実装」がレビューの単位ごとに流す設計の決定の記録（#4369）

[設計書](./issue-4369-design.md)の「決定の記録」を分けた文書である。「入出力のコントラクト」「処理の流れ」と不変条件の番号（I1〜I6）は設計書にある。

## 決定の記録

### 決定 1: 実装が 1 本にまとまる事象を早く止めるため、#3702 の実装を待たずに、単位を順に流す部分を先に入れる

- **質問**: #3702 の実装でこの課題を満たして確かめだけにするか、先に別の変更として入れるか（要求の未決 1）
- **選んだ案**: 先に入れる。単位を読む処理と流す処理は分ける。次の名前は #3702 の詳細設計に合わせる。流す処理のファイル（`progress/units_invoke.py`）、差し込み（`unit_file`）、工程のメタデータ（`per_unit`）である。#3702 の実装は読み手を単位のファイルへ差し替え、流す処理に並列と承認した入力の照合を足す
- **理由**: 単位が 1 本にまとまる事象は、単位の大きな変更を流すたびに起きる。直すのに要るのは「読んで順に流す」部分だけで、#3702 の残り（設計の工程の並びと承認ゲートの移動）を待つ必要が無い
- 採らなかった案: #3702 の実装で満たす（#3702 は 9 タスク・見込み約 3,550 行である。設計のフェーズの工程の並びと承認ゲートの移動も含む。それが入るまで同じ事象が起きる。#3702 は単位のファイルだけを読むので、表を読んで流す（受け入れ条件 1）には別の実装が要る）
- 採らなかった案: #3702 の単位のファイルの形をこの課題で先に作る（実装計画の書式を変えることになり、対象範囲の外）
- **代償**: 表の読み手は #3702 の実装で置き換わる。流す処理は #3702 で並列を足すときに書き直す部分がある
- 根拠: Value 5 / Value 11（MVV バージョン 11）

### 決定 2: 分けた変更が気づかれずに 1 本にならないよう、表だけを持つ実装計画は表のとおりに流し、課題 1 つの 1 単位にしない

- **質問**: #3702 の設計は単位のファイルを持たない旧い形の実装計画を課題 1 つの 1 単位にする。受け入れ条件 1 とどちらに合わせるか（要求の未決 2）
- **選んだ案**: 受け入れ条件 1 に合わせる。この課題の後は表を読んで流す。#3702 の実装は、読み手を単位のファイルへ差し替える。その後も、単位の見出しがあるのに単位のファイルが無い実装計画は、1 単位にまとめずに止める。#3702 の設計の「旧い形は課題 1 つを 1 単位」は、#3702 の実装でこの形に改める
- **理由**: 利用者が求めたのは、実装計画に書いた分け方のとおりに流れることである。表があるのに 1 本にすると、分けた意図が黙って捨てられる
- 採らなかった案: #3702 の設計に合わせて 1 単位にする（表で分けた実装計画が 1 本で実装され、この課題の事象がそのまま残る）
- 採らなかった案: #3702 の後も表の読み手を残して 2 通りを読む（同じ事実の読み手が 2 つになる）
- **代償**: #3702 の実装が入った時点で終わっていないスプリントは、単位のファイルを書き足すまで工程「実装」が止まる
- 根拠: Value 3 / Value 8 / Value 11（MVV バージョン 11）

### 決定 3: 同じ仕組みを 2 回作らないため、#3905 をこの課題へ統合する

- **質問**: 自動の経路で単位を実行しマージしてから `gathered` を記録する #3905 を統合するか（要求の未決 3）
- **選んだ案**: 統合する。#3905 の受け入れ条件 3 件（下の 1〜3）は、この課題の受け入れ条件 1〜5 に含まれる。「設計の結果」の表で #3905 の扱いを「マージする」（受け入れ内容を統合先 #4369 の実装へ含める）とし、設計の承認で確定する
  1. 単位ごとに実行し、マージの後に記録する
  2. 未マージなら記録せずに止まる
  3. 欄が無ければこれまでのとおりにする
- **理由**: #3905 が足すもの（単位の実行とマージの後の記録）は、この課題の流れの一部である。別に残すと、同じ処理を 2 回設計して確かめることになる
- 採らなかった案: 別の課題として残す（この課題の後には、#3905 で足すものが無くなる）
- **代償**: #3905 は自分の受け入れ条件を単独では確かめず、#4369 の確かめで閉じる
- 根拠: Value 11（MVV バージョン 11）

### 決定 4: 単位の無いスプリントの振る舞いを変えないため、工程の定義のステップは変えず、プランを呼ぶ層で単位の経路へ分ける

- **質問**: 単位の繰り返しをどこに置くか
- **選んだ案**: 工程「実装」の定義に `per_unit` を足し、プランを呼ぶ層（`invoke.py`）が単位の見出しの有無で分ける。単位 1 つの実行には、これまでのプランを呼ぶ処理を使い、入力を単位のものにする。この処理は、差し込みの組み立て・打ち直しの開始点・承認の回答を扱う。単位の表の開始前の確かめも、これまでの差し込みの確かめと同じ時点で行う。そのため、読めない表は工程を始める前に止まる。古いステートマシンが保存しているモードの定義のスナップショットに `per_unit` が無ければ、そのステートマシンはこれまでの経路のままである
- **理由**: 単位があるかは実装計画を読むまで分からず、単位の無いスプリントの流れは変えないと要求が決めている。分けるのをプランの呼び出しに置けば、今ある打ち直し・差し込みの確かめ・承認の回答をそのまま使える
- 採らなかった案: ステップを `ndf progress units run` の script に置き換える（単位の無いスプリントでも、プランの打ち直しと差し込みの事前確認の作り直しが要る）
- 採らなかった案: 単位の数だけ工程の行やステップを足す（行はモードの定義が決め、単位の数は計画の後にしか分からない）
- **代償**: 工程の定義を読むだけでは、単位の繰り返しがあることが `per_unit` の 1 語でしか分からない。途中の単位の進みは結果の `items` とプランの記録で見る
- 根拠: Value 3 / Value 9（MVV バージョン 11）

### 決定 5: 順序の食い違いと取り込みの衝突を生まないため、単位は並列にせず 1 つずつ流す

- **質問**: 同じ実行順の単位や、準備の単位の後の残りの単位を並列に流すか
- **選んだ案**: 1 つずつ流し、前の単位のマージの後に次の作業場所を切る
- **理由**: 単位が触るファイルは実装計画の表に無く、重なりを前もって確かめられない。順に流せば、後の単位は前の単位の変更の上で作られる
- 採らなかった案: 並列に流す（これまでの実装計画の表は触るファイルを持たない。そのため、重ならないことを機械で確かめられない。並列は触るファイルと承認を持つ #3702 が足す）
- **代償**: 単位が多いスプリントは、supervisor が並列に回すより遅い
- 根拠: Value 3 / Value 9（MVV バージョン 11）

### 決定 6: 未レビューや取り消し済みの変更を完了と読まないため、コードを書ける者だけが作れる取り込みコミットを完了の記録にする

- **質問**: どの単位が済んだかを何で持ち、誰が書いた記録を受け付けるか
- **選んだ案**: 工程が作る取り込みコミット（merge commit）の本文の末尾に記録を持つ。別の置き場は作らない

| 末尾の行 | 中身 |
| --- | --- |
| `Ndf-Unit` | 単位のブランチ名 |
| `Ndf-Pr` | レビューした PR の番号 |
| `Ndf-Def` | 単位の定義（含むタスクの番号と展開した条件）から作る短いハッシュ値（定義の指紋） |

- レビューした HEAD は取り込みコミットの 2 番目の親で、宛先はコミットが載っているブランチである
- **記録を作れる主体**: 記録を作れるのは、スプリントブランチへコードを push できる者（`Contents: write`）だけである。この権限があれば記録と無関係にコードを書き換えられるので、記録を受け付けても権限は広がらない。commit status・PR の本文・コメントを書ける権限だけでは、完了の記録は作れない
- **書く条件**: 工程が取り込みコミットを作るのは、次の 2 つがそろうときだけである。`impl` が最後まで通ったこと（レビューの完了と CI を含む）。`review-target` の番号と HEAD が、`unit-pr` と `reviewed-head` に一致すること。人の判断を待つ指摘が残る単位は `review-target` が無いので、取り込みコミットを作らない（決定 14）。記録の中身は工程が保存先の記録から組み、呼び出し側が選ぶ入力は無い
- **マージ済みの単位の確かめ**: 次の 3 つがそろえば、単位を完了とする。打ち直しと工程のマージの後で同じ確かめを使う
  1. スプリントブランチの先端から第 1 親だけをたどった、ベースブランチに無いコミットの中に、親を 2 つ持ち、`Ndf-Unit` がこの単位のコミットがある。単位のブランチの中の merge commit は第 1 親の列に無いので、数えない
  2. 上の表の 3 行がすべてあり、`Ndf-Def` が今の定義の指紋と同じである
  3. そのコミットが打ち消されていない
- **工程の外のマージ**: 利用者が GitHub で単位の PR をマージしても、記録が無いので完了にしない。工程は、単位のブランチを head、スプリントブランチを base とするマージ済みの PR を読む。その番号が、第 1 親の列のどの `Ndf-Pr` にも無ければ、工程の外のマージとして止まる
  - 工程は、工程の外のマージで入ったコミットの範囲を特定せず、取り消されたかも判定しない。マージの方式で範囲の形が違い、rebase merge ではコミットが書き直されるためである。何をどこまで打ち消しても、同じブランチ名では先へ進まない
  - 利用者への案内は、PR の URL を示し、次の 2 つを頼む。PR の画面と `git log` で入ったコミットを確かめて、すべて取り消すこと。実装計画の単位の名前を変えて打ち直すこと
- **取り消しの扱い**: 単位の変更を取り消すときは、利用者がスプリントブランチで取り込みコミットを `git revert -m 1` する。工程は次のように読む
  - 取り込みコミットより後に、本文に `This reverts commit <取り込みコミットの SHA>` を持つコミットがあれば、打ち消されている。その打ち消しがさらに打ち消されていれば、取り込みは残っている
  - 履歴の書き換えで取り込みコミットがスプリントブランチから消えた場合は、取り込みが無いと読む。同じブランチ名にマージ済みの PR が残っていれば、工程の外のマージと同じく止まる
  - 取り消した単位は未実装として扱い、次の番号のブランチをスプリントブランチから切って、実装とレビューを最初から通す。単位の名前は変えなくてよい。単位の指示のファイルには、取り消されたコミットと取り消したコミットを書く
- **単位のブランチ名**: `<スプリントブランチ>-u<代表の課題>-<単位の名前の短いハッシュ>`。この単位の取り込みが取り消されていれば、後ろに `-r<取り消された回数>` を付ける
- **最後の照合**: すべての単位をマージした後にも、取り込んだ実装計画を読み直して同じ確かめをする。読み直しで増えていた単位や、途中で取り消された単位があれば、未実装なので止まり、打ち直しで流す
- **確かめに通らないときの直し方**: 定義の違うマージは、利用者が取り消して打ち直す。実装の途中で単位を分け直すときは、マージ済みの単位の行は元に戻し、足す変更を新しい名前の単位に分ける
- **理由**: レビューと CI を通した変更が入ったことを、別のマシンの打ち直しでも確かめる必要がある。コミットはスプリントブランチと一緒に運ばれ、書けるのはコードを書ける者だけである
- 採らなかった案: PR の本文に目印の行を書く（本文を編集できる者が、レビューしていないマージを完了に見せられる）
- 採らなかった案: レビューした HEAD の commit status に記録する（コードを書けず commit status だけを書ける連携が、記録を作れる。書き込み元を絞るには、正しい書き込み元の一覧を別に持つ必要がある）
- 採らなかった案: 手元のファイルにだけ記録する（別のマシンの打ち直しで、済んだ単位を確かめられない）
- 採らなかった案: 取り消した単位は名前を変えて区別させる（名前を変えるまで、変更の欠けたスプリントブランチを完了と読む）
- 採らなかった案: ブランチ名に表の行の番号を使う（行を足すと番号がずれ、別の単位を済みと読む）
- 採らなかった案: 指紋をブランチ名に入れる（定義を直すとマージ済みの単位が新しい単位になり、同じタスクをもう一度実装する）
- **代償**: 打ち直しの間に単位の名前を変えると、その単位は新しい単位として流れる。タスクの番号を変えずに本文だけを直しても検出しない。`git revert` の本文の行を消した取り消しや、手で打ち消したコミットは検出しない
- 根拠: Value 3 / Value 8 / Value 13（MVV バージョン 11）

### 決定 7: 分けたはずの単位を落とさないため、表は決めた形だけを読み、読めなければ始めずに止まる

- **質問**: 実装計画を書く側の表記の揺れ（注記・範囲・番号の省略・「無し」）をどこまで受けるか
- **選んだ案**: 「入出力のコントラクト」の読み方の表の形を受ける。範囲には課題を付けられる。複数の課題の実装計画で、最初の要素に課題が無いセルは受けない。表のセルの分け方は、受け入れ条件の確認の表を読む既存の部品を使う
- **理由**: 読み違えた単位は、実装もレビューもされないまま `gathered` の後ろへ進む。始める前に止まれば、直すのは実装計画の 1 行で済む
- 採らなかった案: `<課題>:<番号>` だけを受ける（今ある実装計画の多くが範囲や番号の省略を使い、止まる）
- 採らなかった案: 読めない行を飛ばして残りを流す（落ちた単位に気づけないまま `gathered` が書かれる）
- **代償**: `5a` のような番号で条件を指す実装計画は、番号を直すまで止まる
- 根拠: Value 3 / Value 13（MVV バージョン 11）

### 決定 8: 単位の外の変更が単位の PR に入らないよう、単位の指示のファイルを実装・修正・レビューのすべてに渡す

- **質問**: 単位の範囲を、実装する worker と、後からコミットする修正担当へどう伝えるか
- **選んだ案**: 単位を流す処理が指示のファイルを単位の保存先に書き、`unit_file` で `impl` のプランに渡す。中身は、単位の名前・含むタスク・満たす条件・実装計画のパス・単位の外の扱いと、下の例外である。コミットする経路には次のように届ける

| コミットする経路 | 届け方 |
| --- | --- |
| 実装（`impl`）、手元のテストの修正（`fix`）、CI の修正（`ci-fix`）、push の拒否の修正（`fix-push`）、衝突の解消（`fix-base`） | worker の起動指示の入力 `unit_file` |
| レビューの修正担当（単位のレビューと差分のレビュー） | 環境変数 `NDF_UNIT_FILE`。相手役の指示にも同じ範囲を載せ、後の単位が担う条件を未達の指摘にしない（下の例外を除く） |

- **単位の外の変更が要るとき**: 今の単位のテスト・CI・レビューを通すのに要る最小の変更は入れてよく、コミットメッセージに理由を書く。後の単位のタスクは実装しない。後のタスクを実装しないと通らない場合は、直さずに失敗の理由を返し、単位がそこで止まる。レビューの指摘が後の単位の範囲なら、修正担当は見送り、どの単位が担うかを理由に書く（下の例外を除く）
- **例外（担当の単位にかかわらず、今の PR で扱う指摘）**: 範囲を理由に保留できるのは、受け入れ条件の未達と、今の差分に無い作業だけである。今の差分に含まれる、秘密・認証認可・利用者のデータ・戻せない操作の問題は、相手役（レビューする AI）が必ず指摘する。修正担当は、その指摘を後の単位を理由に見送らない。後の単位の範囲を直すことになっても、今の PR で直す
- **見送りの区分**: 修正担当が後の単位の範囲を理由に見送る指摘には、区分 `not_applicable` と担当の単位を書く。区分の無い見送りと `needs_user` の見送りは人の判断を待つ指摘になり、単位が止まる（決定 14）
- **理由**: 単位の PR を読み切れる大きさに保つには、後からコミットする修正担当にも同じ範囲が要る。範囲を渡さなければ、テストや CI の修正で後の単位の内容が混ざる。範囲を理由に危険な指摘が後回しにならないよう、例外を置く
- 例外の根拠: Value 7（秘密・利用者のデータ・戻せない操作に関わる指摘は直される）
- 採らなかった案: 初回の `impl` にだけ渡す（テストや CI が落ちたときに、修正担当が後の単位のタスクまで実装できる）
- 採らなかった案: 受け入れ条件の指定だけで絞る（1 つの条件が複数の単位にまたがる表があり、条件を持たない準備の単位もある）
- 採らなかった案: 課題の本文のコピーへ範囲の指示を足す（同じファイルが PR の本文になり、課題の本文と食い違う）
- **代償**: 設定でレビューや worker の起動を差し替えたリポジトリは、`unit_file`・`NDF_UNIT_FILE`・`NDF_UNIT_PR` を読む側も合わせる必要がある。範囲を守るのは指示で、差分を機械では確かめない
- 根拠: Value 3 / Value 9（MVV バージョン 11）

### 決定 9: 条件を持たない準備の単位を流せるよう、照らさないことを引数で明示する

- **質問**: 「満たす受け入れ条件」が「無し」の単位の確かめをどうするか
- **選んだ案**: `ndf loop acceptance check` に `--no-criteria` を足す。条件の無い単位には `--issue <代表の課題> --no-criteria` を渡す。代表の課題の決め方は「入出力のコントラクト」にある
- **理由**: 準備のリファクタリングの単位は、照らす受け入れ条件を持たない。条件の渡し忘れと区別するため、照らさないことは引数で書く
- 採らなかった案: `--issue` だけを渡す（課題のすべての条件を照らし、準備の単位が必ず止まる）
- 採らなかった案: 条件の無い単位を読めない表にする（準備のリファクタリングの単位を持つ実装計画が実際にある）
- **代償**: 条件の漏れはこの単位では見つからない。工程「完了判定」がすべての条件を照らす
- 根拠: Value 11 / Value 13（MVV バージョン 11）

### 決定 10: 後の工程をこれまでの入力のまま流すため、すべてのマージの後に工程「実装」がスプリントの PR を開く

- **質問**: 単位の経路ではスプリントの PR を誰も作らない。リファクタリングとコードレビューはそれを読む
- **選んだ案**: 最後のマージの後に、これまでのテンプレート `pr` を流し、スプリントブランチからベースブランチ宛ての PR を開く。開いた PR があれば作らない。マージはしない
- **課題の参照**: テンプレートの `refs` にはスプリントのすべての課題を渡し、本文に `Refs #<番号>` を載せる（これまでの工程から組む PR と同じ）。既存の PR の本文に欠けがあれば、テンプレートの今の振る舞いのまま、欠けた `Refs` を並べて `incomplete` で止まり、`gathered` を書かない。利用者が本文に足して打ち直す。PR の本文を自動では書き換えない
- **理由**: 工程「リファクタリング」「コードレビュー」はスプリントの PR を入力にする。単位の経路でそれを作れるのは、最後のマージを知る工程「実装」である
- 採らなかった案: 後の工程の側で PR が無ければ作る（作る場所が 2 つ以上になる）
- **代償**: 工程「実装」の仕事が 1 つ増える
- 根拠: Value 3 / Value 11（MVV バージョン 11）

### 決定 11: 本番へ届くブランチへの取り込みと保護の迂回を防ぐため、工程だけがマージし、保護の無いスプリントブランチへ merge commit を push する

- **質問**: PR をマージする API は、宛先も宛先の先端も条件にできない。保護を迂回できる資格情報で呼ぶと、保護を越える。単位のマージと、レビュー・CI の対象をどう縛るか
- **選んだ案**: GitHub の PR のマージもマージキューも使わない。工程が merge commit を作り、`refs/heads/<スプリントブランチ>` を指定して push する。この merge commit の親は、スプリントブランチの先端とレビューした HEAD の 2 つで、中身は HEAD と同じである。push の更新の条件は、親にした先端の SHA である（`--force-with-lease=refs/heads/<スプリントブランチ>:<先端の SHA>`）。merge commit はその先端を第 1 親に持つので、更新は常に fast-forward で、履歴は書き換わらない

| 守ること | どう守るか |
| --- | --- |
| 証跡 | 単位をマージする経路は工程の中だけにあり、`review-target`・`reviewed-head` を工程が自分で読む |
| 宛先 | push が宛先を指定するので、PR の宛先がいつ変わっても、ほかのブランチには入らない |
| CI を通した組み合わせ | 送る前に、スプリントブランチの先端がレビューした HEAD の祖先かを確かめる。祖先なら、取り込んだ結果の中身は CI が確かめた HEAD と同じである |
| 確かめた後の先端の移動 | リモートの先端が、親にした SHA と違えば GitHub が更新しない。レビューした HEAD の祖先へ進んだだけの場合も同じである。古い第 1 親のまま入ると、`revert -m 1` がほかの人の先に入れた変更まで打ち消すためである |
| 取り込みの範囲 | 単位の取り込みは、常に merge commit 1 つである |

- **保護の確かめ（I6）**: 開始前と、push の直前に、スプリントブランチの保護を読む。次のどちらかなら、工程はマージしない
  - 当たる ruleset に、削除の禁止・強制 push の禁止・作成の制限以外の規則（PR の必須、マージキュー、必須のチェックなど）がある
  - 従来のブランチ保護が有効である

  読めない場合もマージしない。保護を迂回できる権限かは調べず、迂回も使わない（リポジトリの指示書が管理者の迂回を禁じる場合にも合う）。開始前に当たれば、理由に保護の内容を書いて始めずに止まる
- **新しいスプリント**: 開始前の時点で、スプリントブランチがリモートに無いことがある。ブランチ名はスプリントの作業場所が今いるブランチから取り、次の順に確かめる
  1. `git ls-remote` でリモートにあるかを調べる
  2. ブランチ名に当たる ruleset の規則を読む（`rules/branches/<名前>` は、無いブランチにも空の並びや当たる規則を返す）
  3. リモートに無ければ、作業場所の HEAD でブランチを作る（同じ名前が無いことを条件にした push）
  4. 実在するブランチの従来の保護を読む（`branches/<名前>`。無いブランチには 404 `Branch not found` が返るので、作る前には読まない）

  4 で保護があれば、作ったブランチは残して止まる。ほかの読み取りの失敗は「読めない」と扱う
- これまでの経路の `impl` もスプリントブランチへ直接 push するので、そこに PR の必須などを掛けたリポジトリは、これまでも自動の実装を流せない
- 単位の PR は 1 つに決め、同じ番号を後のすべての段階に渡す。番号を取り直す照会は足さない

| 段階 | 単位の経路での扱い |
| --- | --- |
| 流し終えたかの確かめ（`done-check`） | head と宛先の両方でマージ済みの PR を選ぶ |
| PR を決める（`pr` のステップ） | 開いた PR は head と宛先の両方で選ぶ。新しく作った場合は、作成の出力の番号を使う。番号はこれまでと同じくステップの結果の `items[].number` で返し、同じステップが単位の保存先の `unit-pr` にも書く |
| 衝突の確かめ（`conflict-check`）と CI の完了の確認（`ci`） | ブランチ名から PR を引き直さず、`unit-pr` の番号を使う。`ci` が番号を引いていた照会は無くなる |
| 初回のレビューと差分のレビュー | `unit-pr` の番号を `NDF_UNIT_PR` で渡す。後ろに `--target-out <保存先>/review-target` を足す |
| マージ | `review-target` の番号が `unit-pr` と、HEAD が `reviewed-head` と一致するときだけ進む。PR を 1 回読み、開いていること、head が単位のブランチ、宛先がスプリントブランチ、HEAD がレビューした HEAD、本文に決めていない残リスクが無いことを確かめて push する |

番号・head・宛先・HEAD のどれかが違うか、`review-target` が無ければマージしない。公開のコマンド `ndf ci merge` に単位のマージを足すと、レビュー・CI の有無と記録の中身を呼び出し側が指定できるので、足さない。

- **push の後の PR**: 工程の完了の判定は、PR の表示を使わない。GitHub は、head のコミットがベースブランチから到達できると PR をマージ済みにすることがある（[間接的なマージ](https://docs.github.com/en/pull-requests/reference/pull-request-merges#indirect-merges)）。公式の説明が直接の push の例に挙げるのは既定ブランチで、スプリントブランチ宛てで同じになるかは確かめていない。工程は push の後に PR を 1 回読み、開いたままなら、取り込みコミットの SHA を書いたコメントを付けて閉じる
- **理由**: PR をマージする API は、宛先を指定できない。読んで確かめた後に宛先が変われば、本番へ届くブランチへ入る。宛先を指定できる操作は push である
- 採らなかった案: PR のマージの前に PR を読んで宛先を確かめる（読んでから要求を送るまでの間に宛先が変わると、本番へ届くブランチへ取り込む）
- 採らなかった案: `POST /repos/{repo}/merges` で宛先とコミットを指定する（宛先の先端を条件にできず、CI を通していない組み合わせが入る）
- 採らなかった案: 保護のあるスプリントブランチでは利用者にマージを頼む（手のマージは宛先を固定できず、方式によって取り込みが複数のコミットになる）
- 採らなかった案: 資格情報が保護を迂回できるかを調べ、できなければ送る（従来のブランチ保護の詳細は管理者しか読めず、迂回できるかを確かめきれない）
- 採らなかった案: レビューや CI がブランチから番号を引き直す形を残す（同じ head の PR が複数あると、別の PR のレビューや CI の結果で進むか止まる）
- 採らなかった案: 条件を付けずに push する（先端がレビューした HEAD の祖先へ進んでも fast-forward になり、古い第 1 親の merge commit が入る）
- **レビューを差し替えたリポジトリ**: 設定で差し替えたレビューの起動は、`NDF_UNIT_PR` の PR をレビューし、`--target-out` で指定されたファイルに結果を書く必要がある。ファイルを書かない起動では、単位はマージされず止まる。人の判断を待つ指摘が残るときにファイルを書かないことも、差し替えた起動の側が守る
- **代償**: 単位の取り込みは、リポジトリのマージの方式の指定に関わらず merge commit になる。スプリントブランチに保護を掛けたリポジトリは、単位の表を持つ実装計画を自動では流せない。ruleset は規則の種類で判定するが、従来のブランチ保護は有効なだけで止まる。そのため、強制 push の禁止だけでも、従来のブランチ保護で掛けていれば止まる（ruleset へ移せば流せる）。PR の画面の承認やマージの制限は、単位の PR には効かない。保護を読んでから push が届くまでの数秒の間に保護が付くと、その保護は確かめられず、迂回できる資格情報の push は保護を越えて入る。この隙間は受け入れる。対象はベースブランチでも本番ブランチでもないスプリントブランチで（I4）、入るのはレビューと CI を通した HEAD である。入った後は `git revert -m 1` で取り消せる
- 根拠: Value 3 / Value 13（MVV バージョン 11）

### 決定 12: 単位の数で流れを変えないため、単位が 1 つでも単位の PR とスプリントの PR の 2 本にする

- **質問**: 単位が 1 つのときは、分ける効果が無いのに PR の作成とマージが 1 回ずつ増える。これまでの経路（スプリントブランチで実装してベースブランチ宛ての PR をレビューする）を使えるか
- **選んだ案**: 使わず、PR を 2 本にする
- **理由**: 次の 3 つである
  - 受け入れ条件 1・4 は、表があれば単位の数に関わらず、次を求める。単位のブランチ、スプリントブランチ宛ての PR、単位の条件の `--criteria`、レビューした HEAD だけのマージである
  - これまでの経路は単位の範囲の指示も単位の条件も渡さず、レビューの後の取り込みを縛る段階が無い
  - 最後の読み直しで単位が増える場合と、取り消した単位を流し直す場合がある。1 単位だけ別の経路にすると、途中で経路が切り替わる
- 採らなかった案: 全体で 1 単位ならこれまでの経路を使う（要求の受け入れ条件を変える必要があり、経路の切り替わりの扱いが増える）。分けるつもりが無い課題は、実装計画に単位の見出しを置かなければこれまでの経路になるが、実装計画の書き方は変えない
- **代償**: 1 単位のスプリントでは、PR の作成とマージの要求が 1 回ずつ増える。両方の PR で CI が走る設定では、CI も 1 回増える
- 根拠: Value 3（MVV バージョン 11）

### 決定 13: スプリントブランチ宛てで起動しない CI があっても流せるよう、単位の PR で待つチェックを宣言で選べるようにする

- **質問**: 必須のチェックの宣言（`ci.required_checks`）は、ベースブランチ宛ての PR を前提にする。単位の PR にも同じものを待つか
- **選んだ案**: 設定に `workflow.unit_required_checks`（チェックの名前の並び）を足す

| 値 | 単位の PR の CI の完了の確認 |
| --- | --- |
| 書かない | `ci.required_checks` を待つ |
| 名前の並び | その名前を待つ |
| 空の並び | 待たない |

- スプリントの PR で待つチェックは、これまでのとおり `ci.required_checks` である
- **実装前の確かめ**: 開始前の確かめは、単位の PR の宛先（スプリントブランチ名）、待つチェックの名前、読んだキーを結果に出す。利用者は、そのブランチ宛ての PR で各チェックが起動する設定かを CI の定義で確かめられる。起動しないチェックを待って止まった場合の理由にも、このキーを書く
- **理由**: CI の起動の条件はリポジトリごとに違い、スプリントブランチ宛ての PR で起動しないチェックを待つと、最初の単位から進めない
- 採らなかった案: `ci.required_checks` をそのまま使う（ベースブランチ宛てでだけ CI が起動するリポジトリは、最初の単位から進めない）
- 採らなかった案: `ci` の下にキーを足す（`ci` はプロジェクトの解析が測って書く値で、利用者が選ぶ値は `workflow` に置く）
- 採らなかった案: CI の定義を読んで起動を機械で判定する（起動の条件の書き方は CI の提供元ごとに違う）
- **代償**: 空の並びや少ない並びを宣言すると、その分の検査はスプリントの PR まで行われない
- 根拠: Value 4（MVV バージョン 11）

### 決定 14: 利用者の承認を設計と本番の 2 回に保つため、人の判断を待つ指摘が残る単位は、分類を問わずマージせずに止める

- **質問**: レビューで人の判断を待つ指摘が残った単位を、どう扱うか
- **選んだ案**: 1 件でも残れば、その単位で止める。単位の名前と理由（指摘）を示し、後の単位は始めず、`gathered` を書かない。単位の承認の仕組みは作らない
- **理由**: 利用者の承認は設計と本番の 2 回のままになる。指摘の分類で通すものと止めるものを分けないので、分類の漏れでマージされることが無い。承認の依頼・承認の記録・承認資料を新しく作らずに済む

「人の判断を待つ指摘」は、用語集の「レビューの保留」と同じ 2 種類である。

| 種類 | 中身 |
| --- | --- |
| 必ず人の承認が要る操作に当たる指摘 | 相手役が共通原則の C<番号> かプロジェクト MVV の P<番号> を付け、直さずに残ったもの（レッドライン） |
| 利用者の判断を待つ見送り | 修正担当が見送り、区分が `needs_user`、区分が無い、知らない値のどれかのもの |

直していない通常の指摘（未解決）が残る単位も、これまでの `impl` と同じく `incomplete` で止まる。打ち直しの扱いは下と同じである。

**どう止まるか**: `--target-out` を渡したレビューは、人の判断を待つ指摘が残ると `incomplete` で終わる。`impl` のプランは、これまでの未解決の指摘と同じ流れになる。未解決のフラグを置き、CI まで進めてから `incomplete` で止まる。初回のレビューで残った指摘は、後の差分のレビューが通っても消えない。工程は、レビューのステップの結果の欠けから指摘を読んで理由に並べ、止まった時点の作業場所の HEAD を単位の保存先の `held-head` に書く。

**利用者の直し方**: 理由に並んだ指摘ごとに次のどれかを行ってコミットし、`ndf progress next` を打ち直す。

| 利用者の判断 | すること |
| --- | --- |
| 指摘のとおりに直す | 単位の作業場所で直してコミットする |
| 指摘された変更は単位に要らない | 単位の作業場所でその変更を取り除いてコミットする。後の単位で行うなら実装計画を直す |
| 指摘された変更は、このまま要る | 利用者が自分でその変更をスプリントブランチへコミットして push し、単位の作業場所へスプリントブランチをマージする。変更は単位の差分から外れ、スプリントの PR のレビューと本番の承認で見る |

打ち直す前に、利用者は残った指摘の PR のスレッドを resolve する。cross-review は resolve していないスレッドの指摘を次の回へ引き継ぐためである。行を指せずにスレッドにならなかった指摘が残る場合は、単位の PR を閉じる。工程は新しい PR を作り、前の指摘を引き継がずにレビューする。

打ち直した工程は、作業場所の HEAD が `held-head` から変わっていれば、その単位のレビューを始めからやり直す。変わっていなければ、レビューをやり直さず同じ理由で止まる。コードを変えない打ち直しでは、相手役が同じ指摘を挙げないことがあり、利用者が判断していない指摘を残したままマージできてしまうためである。

- 採らなかった案: 単位ごとに利用者の承認を受けて工程がマージする（承認の回数が単位の数だけ増え、依頼・記録・照合の部品が要る）
- 採らなかった案: 必ず人の承認が要る操作の一部の分類だけを止める（挙げていない分類の指摘が残ったまま自動でマージされる）
- 採らなかった案: 指摘を残したままマージし、本番の承認で見る（受け入れ条件 4 に反し、人が判断していない変更の上に後の単位が積まれる）
- 採らなかった案: 利用者の GitHub でのマージを承認と読む（指摘を知らない者の通常のマージが承認になる。マージの要求は宛先を固定できない）
- **代償**: 利用者が直さなくてよいと判断しても、承認するだけで単位を進める手段は無い。指示書の書き換えのように、必ず人の承認が要る操作を意図して含む単位は、利用者がその変更を自分でスプリントブランチへ入れるまで止まる
- 根拠: Value 1 / Value 9（MVV バージョン 11）
