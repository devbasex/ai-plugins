# #1241 の決定の記録

頭のファイルは [issue-1241-design.md](issue-1241-design.md) にある。ここでは決定と、その理由と、採らなかった案だけを扱う。

## 決定の記録

### 決定 1: 置き場の食い違いを作らないため、確認 (a)(b) を新しい 1 本のスクリプトの 2 つのサブコマンドにし、確定仕様化とは置き場の定数だけを共有する

確定仕様化の手順（`plan-to-spec-steps.py`）が持つのは設計の削除・索引・用語集の移し替えで、文書と実装を照らす処理は持たない（照合は `plan-to-spec` の手順 6 の LLM の作業である）。寄せる先の共通の処理が無いため、同じ層へ寄せても共有できるのは確定仕様の置き場だけになる。(a) と (b) は入力が違い（設計文書と差分）、どちらかだけを打つ場面がある（設計文書が無ければ (b) も打たない）ため、1 本のスクリプトのサブコマンドに分ける。

`plan-to-spec-steps.py` へサブコマンドとして足す案は採らない。確定仕様化の手順のスクリプトに完了判定の手順が混ざり、要求が「含まない」とする確定仕様化の手順の変更と読める。(a) と (b) を別々のスクリプトにする案も採らない。設計文書の探し方・結果の形・終了コードの扱いを 2 か所に持つことになる。

根拠: Value 6 / Value 4（MVV 版 2・スプリント MVV 503affec）

### 決定 2: #216 の実物で取りこぼさないため、テストの名前を拾う節に `## 構成要素` を足し、`## テスト設計` の `test` で始まる識別子も拾う

#216 の設計文書では、作ると書いたテストファイル `tests/ci/test_ci_workflow.py` は `## 構成要素` の表とパッケージの木にだけあり、`## 決定の記録` の決定 3 は「PyYAML の回帰テスト」と散文で書く。`## テスト設計` の表は `test_pull_request_is_not_filtered_by_branch` のようにパスの無い関数の名前だけを持つ。要求の前提 4 の 2 節と 2 つの形だけを拾うと、#216 の取りこぼしは (a) に掛からない（根拠の表の実測）。`## 構成要素` は雛形で「作るもの・変えるもの」を並べる節で、テストファイルを作ると書く場所として決定の記録と同じ重みを持つ。

設計文書の全体から拾う案は採らない。ドメインモデルや未確認の節は、消したテスト・既存のテスト・例として名前を書くことがあり、「無い」の誤検出になる。前提 4 のとおり 2 節だけにする案も採らない。実物の 7 件のうち (a) で拾えるはずの #216 を拾えない。

この決定は要求の前提 4 を広げる。承認ゲート 1 で認められたら、実装 PR で課題の本文の前提 4 を「実装で変えた」の形に直す。

根拠: Value 3 / スプリント Value 2（MVV 版 2・スプリント MVV 503affec）

### 決定 3: どの言語のリポジトリでも判定を返すため、関数の有無を言語の構文で見ず、名前がファイルに語として現れるかで見る

関数・テストの定義の形は言語とテストの枠組みごとに違い（`def`・`func Test`・`it('…')`・`@Test`）、構文で判定すると、このリポジトリの言語（Python と shell）だけを判定できる形になりやすい。語の一致（`git grep -w -F`）はどの言語でも同じに働き、要求の非機能の条件が「確かめられなかった」を返すとした「判定できない言語」が生じない。誤りはコメントや文字列にだけ名前がある場合に「ある」と読む側に倒れ、「無い」の誤検出は増えない。

言語ごとに定義の形の表を持つ案は採らない。表に無い言語では毎回「確かめられなかった」になり、配布先の多くで (a) の関数の判定が働かない。見逃しが実物で出たときに、その言語の形を足す（未確認のまま残ること）。

根拠: Value 5 / スプリント Value 6（MVV 版 2・スプリント MVV 503affec）

### 決定 4: 「無い」を見落とさないため、確認 (a) の終了コードは「無い」を「確かめられなかった」より先に返す

「無い」が 1 件でもあれば 1、「無い」が無く「確かめられなかった」があれば 2、すべてあれば 0 にする。「無い」は直すか節に並べる対象がはっきりしており、2 を先に返すと「無い」名前が読めない結果の中に埋もれる。設計文書が無いときの 3 は、判定を始める前に決まるため、ほかの値と重ならない。

「確かめられなかった」を 1 件でも含めば 2 を返す案は採らない。1 か所の git の失敗で、確かに無いと分かった名前の扱いが「確かめられなかった」に落ちる。

根拠: 根拠なし（MVV 版 2・スプリント MVV 503affec）

### 決定 5: 誤検出を抑えるため、確認 (b) のシンボルは差分の定義の行と大文字の定数だけから抜き、一致した語の種類の数で並べる

差分の増減の行のすべての識別子を語にすると、`self`・`path` のような語がすべての文書に一致する。hunk の見出しと増減の行のうち、`def` / `class` / `function` / `func` / `fn` に続く識別子と、`_` を含む大文字の識別子だけを語にすると、#247 の `SHELLCHECK_VERSION` は拾え、`4d82277` の差分では語は 10 個に収まった（根拠の表）。`.md` の差分は散文の見出しが `class` などの語を含むため、シンボルを抜かない。4 文字未満の名前は、ai-plugins の実測で `G` のような 1 文字の型が多くの文書に一致したため捨てる。

それでも広く使われるパスは多くの文書に一致する（`HEAD~60..HEAD` では 68 文書のすべて）。そこで一致した語の種類の数の多い順に並べ、1 文書に出す行を `--max-lines` で抑える。#247 では食い違った文書が 4 語で最上位に来た。

Serena のようなコードインテリジェンスで変えたシンボルを抜く案は採らない。言語サーバの用意がリポジトリごとに要り、スクリプトが LLM と外部の常駐の仕組みに頼らずに終わる条件（要求の非機能の条件）を満たせない。差分の行の識別子をすべて語にする案も採らない。並べても上位が誤検出で埋まる。

根拠: Value 3 / Value 5 / スプリント Value 2（MVV 版 2・スプリント MVV 503affec）

### 決定 6: 10 秒以内に収めるため、確認 (b) の照合は語を 1 つの正規表現にまとめ、文書ごとに 1 回だけ走査する

ai-plugins の `HEAD~60..HEAD`（語 2,472）で、語ごとに文書の行を照らすと 120 秒を超え、`git grep -F -f` は 6.8 秒、1 つの正規表現での走査は 2.6 秒だった（根拠の表）。`git grep` は一致した行は返すが、どの語が一致したかを返さないため、並びのためにもう 1 度照らす費用が加わる。1 つの正規表現なら一致した語が同じ走査で取れる。

`git grep -F -f` で行を取ってから語を割り当てる案は採らない。実測で倍以上遅く、規模が増えると 10 秒に近づく。

根拠: Value 3 / スプリント Value 2（MVV 版 2・スプリント MVV 503affec）

### 決定 7: 確定仕様の置き場を 2 か所に持たないため、`SPEC_DIR` を `lib/repo.py` に置き、`plan-to-spec-steps.py` と `design-match.py` がそれを読む

要求の前提 3 は、確認 (b) の置き場を確定仕様化と同じものにすると定める。今は `plan-to-spec-steps.py` が `docs/specifications` を索引のパスとして直に書いている。新しいスクリプトにも同じ字面を書くと、片方だけを変えたときに (b) が別の場所を見る。`lib/repo.py` はリポジトリの識別と起点を持つ層で、置き場の定数を持つのに合う。

置き場をプロジェクトの設定で変えられるようにする案は採らない。要求が「含まない」とする。

根拠: Value 6（MVV 版 2・スプリント MVV 503affec）

### 決定 8: 確認 (a) の失敗で取り込みを止めないため、CI に確認 (a) と節の検査を置かない

CI は設計 PR と `light` の PR にも走り、どの設計文書がどの PR に当たるかを PR から決める手段を持たない。(a) の「無い」は、作らなかった理由を `## 設計と違う点` に書いて満たせる（要求の前提 5）が、CI は本文の節と照らさずに落ちる。設計 PR の `pr-body-decisions.sh` は、本文と設計文書が機械で 1 対 1 に決まるから検査にできる。節の中身（違いの有無と理由）は判断で、機械で正誤を決められない。

節の有無だけは機械で見る。単発では `pr-steps.py create` / `update` が `next` で足すよう求め（`## 利用者向けの変化` と同じ形）、3 層では `PrStep` が必ず置く。どちらも止めず、知らせるか置くだけにする。

CI のジョブで (a) を落とす案は採らない。正当な違いのたびに CI が赤くなり、承認を要しない取り込みが止まる。

根拠: Value 2 / Value 4 / スプリント Value 4（MVV 版 2・スプリント MVV 503affec）

### 決定 9: 修正のたびに実装と突き合わせ直すため、3 層では `standard` のときだけ `test-limited` と `pr` の間に突き合わせの 3 ステップを置く

`fix` は `test-limited` へ戻るため、この位置なら修正の後に必ず突き合わせ直し、PR の本文の節が最後の実装に合う。`pr` より前に置くと、worker が直した文書（設計・既存の確定仕様・要求の写し）のコミットも同じ push に乗る。`standard` 以外では設計文書の無い変更が大半で、ステップを足すと `light` の手順と所要が変わる（受け入れ条件 14）。

全体テスト（`test-all`）の後に置く案は採らない。`pr` のステップが本文を作った後になり、節を載せるために本文をもう 1 度書き直す。モードを問わず置いて `tests` の 3 で飛ばす案も採らない。`light` でも run のステップが 1 つ増え、手順が変わる。

根拠: Mission / Value 4（MVV 版 2・スプリント MVV 503affec）

### 決定 10: 節の中身を判断した者が書くため、3 層では `design-match` の worker が節をファイルに書き、`PrStep` は置くだけにする

PR の本文の LLM（`PR_SYSTEM`）は Tool を持たず、材料の抜粋だけを根拠に書く。設計の決定と実装の一致は、コードを読み、テストを打てる worker でなければ判断できない。判断した worker が節を `{state_dir}/design-diff.md` に書き、`PrStep` がそれを本文の決まった位置へ置けば、本文を LLM に書かせるかどうかに関わらず節が残る。LLM の本文に同じ見出しがあれば置き換え、節を 2 つにしない。

`PR_SYSTEM` に節を書かせる案は採らない。突き合わせの判断を持たない LLM が、材料の抜粋から「無し」と書きうる。

根拠: Value 4 / スプリント Value 1（MVV 版 2・スプリント MVV 503affec）

### 決定 11: 要求の正を 1 つに保つため、実装で変えた受け入れ条件の前提は課題の本文を直し、写しは `spec-copy.py write` で作り直す

要求の正は課題の本文で、`issues/` の写しは「手で直さない」と頭に書いてある。写しだけを直すと、設計 PR の前の `spec-copy.py check` と同じ食い違いが生まれ、リリース後テストは本文の古い条件を読む（#218 の形）。書き方は `requirements-design` の「変更の途中で要求が変わったとき」の取り消し線と変更の理由の形を使い、条件を消して差し替えない。

`## 設計と違う点` にだけ「受け入れ条件 N を実装で変えた」と書く案は採らない。リリース後テストと確定仕様化は課題の本文を読み、PR の本文を読まない。

根拠: Value 7 / Value 6（MVV 版 2・スプリント MVV 503affec）

### 決定 12: 設計文書の無い変更に空の節を増やさないため、`pr-steps.py template` は `--mode standard` のときだけ `## 設計と違う点` の雛形を書く

雛形はすべてのモードの実装 PR が使う。`light` の PR に「該当なし」の節が毎回入ると、読み手が読む行が増えるだけで何も伝えない。`--mode` を省いたときの雛形は今のままにし、既存の呼び方を変えない。

すべてのモードの雛形に節を入れる案は採らない。設計文書の無い変更の本文の形が変わる（受け入れ条件 14 の趣旨）。
