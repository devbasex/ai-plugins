# #828 / #680: サブエージェントに Skill 本文を丸ごと読ませず、仕事を分ける器を比べて選ぶ — 要求と受け入れ条件

設計は [issue-828-680-design.md](issue-828-680-design.md)、決定の理由は
[issue-828-680-design-decisions.md](issue-828-680-design-decisions.md) にある。この文書は「何を満たすか」だけを扱う。

親は #827（トークン消費の実測）。マイルストーンは「17 トークン消費の削減」。

## 目的

- **サブエージェントの持ち越し量から、使わない Skill 本文を外す。** #827 の実測（2026-09-20 以降、サブエージェント 156 件）で、Skill 本文は持ち越し量の 16% を占めた。読み込みの多い 6 つのうち、supervisor / worker が本文の大半を使わないのは `progress-tracking` と `development-workflow` の 2 つである（40 回 × 7,649 と 28 回 × 10,679）
- **仕事を別の文脈・別のプロセスへ分けるときの選び方を、1 つの表から引けるようにする。** 同じ種類の仕事で器が回ごとに割れ（#680 の「割れている例」）、小さな作業にもサブエージェントの固定費を払っている

## 対象範囲

含む:

- supervisor / worker の起動指示の雛形から、Skill 本文の読み込みを外す（#828）
- `development-workflow` を読むのは conductor だけにする。supervisor にはモードの判定結果と、持ち場で通す工程と、記録のコマンドを渡す（#828）
- 進行の記録を、Skill を読まずにコマンド 1 行で行えるようにする（#828）
- 各 Skill の末尾の「この工程に入ったら `/ndf:progress-tracking` を呼ぶ」の文を、読み込みを求めない形へ変える（#828）
- 抜粋の形（呼び出し 1 行・結果の読み方・判断の基準）と置き場所を決める（#828）
- 仕事を分ける器（用語の表の 5 つ）を同じ観点で比べた表（#680 の問い 1）
- 小さな作業にサブエージェントを起こさない線引き（#680。#827 の提案 5・#773 の候補 2）
- 問い 2・3 を切り出すかの決定と、切り出すときの起票（#680）

含まない:

- 工程の Skill の本文を縮めること、各 Skill の抜粋の中身（#845 の子）
- 抜粋と本文の一致の検査（#855）、結果の契約（#846）
- `$SCRIPTS` の解決を 1 コマンドにすること（#847）
- supervisor のスクリプト駆動（#827 の方針）。比較表の上で位置づけるだけにする
- 持ち場の測定と粒度の見直し（#768 / #773）。#773 の候補 2 の線引きだけをこの変更で引く
- cross-review / cross-refactoring の駆動を `scripts/` へ出すこと（#560 / #870）
- 4 ランタイムの可搬性と共有する外部の枠（#680 の問い 2・3。前提 6）
- 設計の成果物のうちクラス図・画面: 作るのは文書と既存のシェルの引数の追加だけで、型も画面も持たないため対象が無い

## 受け入れ条件

### 起動指示の雛形（#828）

- [ ] AC1: `agent-layers.md` の 2 つの起動指示の雛形（conductor → supervisor と supervisor → worker）が、Skill 本文の読み込みを求めていない。読み込みとは `/ndf:<Skill>` の起動と `SKILL.md` の Read である。supervisor が持ち場の工程の Skill を起動することは除く（前提 1）
- [ ] AC2: supervisor の起動指示に、`development-workflow` を読まずに持ち場を通せるだけの値が入っている。値はモード・持ち場で通す工程の一覧・記録のコマンド 1 行（二重引用符で囲んだ絶対パス）である
- [ ] AC3: supervisor の守る規則と worker の守る規則に、Skill を起動しない旨がある。supervisor は `development-workflow` と `progress-tracking` を、worker は Skill 全般を起動しない（起動指示が Skill の起動を手順として渡した場合を除く）
- [ ] AC4: worker の起動指示の雛形に、worker が Skill を起動しないで済むよう、手順を抜粋で渡す項目がある

### 記録のコマンド（#828）

- [ ] AC5: 進行の記録（issue の本文と盤面の両方）が、`progress-tracking` を起動せずに 1 回の Bash 実行・1 コマンドで行える。盤面の宣言が無いリポジトリでは issue の本文だけに残る（今の振る舞いと同じ）
- [ ] AC6: AC5 のコマンドを呼んでも、今の `progress-record.sh` と `projects-sync.sh` を別々に呼んだときと同じ記録が残る。テストが確かめている
- [ ] AC7: 工程の Skill の末尾の「この工程に入ったら `/ndf:progress-tracking` を呼ぶ」の文が、AC5 のコマンド 1 行を示す形に変わっている。`progress-tracking` の本文を読まなければ記録できない Skill が無い
- [ ] AC8: 通過工程の控え（`stage-completeness.md`）が AC5 のコマンドの実行を記録として読める。今の検査が通る

### 抜粋の形（#828）

- [ ] AC9: 抜粋の形（呼び出し 1 行・結果の読み方・判断の基準）と置き場所が 1 か所に定義され、#855 の検査が読める目印を持つ。`progress-tracking` の抜粋が 1 つ、その形で書かれている（形の見本）

### 器の比較と線引き（#680）

- [ ] AC10: 器を同じ観点で並べた表が `development-workflow/references/` の 1 か所にあり、`agent-layers.md` から参照されている。器は用語の表の 5 つ、観点はコンテキスト・確実性・止まりにくさ・独立性・資源・観測性・手順の従いやすさである。#845 の判断の 3 段との対応が表から読める
- [ ] AC11: 「小さな作業にサブエージェントを起こさない」線引きが、AC10 の表から引ける基準（読む量・返す量・固定費の比）で書かれ、supervisor の守る規則から参照されている。#773 の候補 2（束ねる）との境が書かれている

### 効果の確認（リリース後）

- [ ] AC12: 変更を配布した後、#827 の計測スクリプトを変更前と同じ条件で回す。サブエージェント内の Skill 読み込み回数（Skill ごと）と、持ち越し量に占める割合を #828 に残している。比べる前の値は設計文書に固定している

### 範囲の切り出し（#680）

- [ ] AC13: #680 の問い 2（可搬性）と問い 3（共有する外部の枠）について、切り出すかの決定と理由が決定の記録にある。切り出すなら起票済みで、#680 の本文から番号で指されている

## 前提

- 前提 1: supervisor が工程の Skill を起動するのは、持ち場の仕事そのものである（`requirements-design` / `design` / `pr` / `cross-review` など）。**この変更は工程の Skill の起動を減らさない。** 減らすのは、工程の外から読まされる Skill（`development-workflow` と `progress-tracking`）と、worker が読む Skill である
- 前提 2: 工程の Skill 自体を「呼び出しと判断」だけに縮めるのは #845 の子（#856 #859 #858 #870 #873 ほか）が行う。この変更は抜粋の**形**を決め、各 Skill の抜粋の中身を作らない
- 前提 3: 抜粋と本文の一致の検査は #855 が行う。この変更は、検査が読める位置と形に抜粋を置くことまでを決める
- 前提 4: `$SCRIPTS` の解決を 1 コマンドにするのは #847 が行う。この変更では、conductor が 1 度解決した絶対パスを supervisor の起動指示へ渡す
- 前提 5: 受け入れ条件の数値の比較（AC12）は、変更を配布した後に `release-verification` で行う。設計と実装の Pull Request では、比べる手順と比べる前の値を固定するまでを扱う
- 前提 6: #680 の残る問い 2（4 ランタイムの可搬性）と 3（共有する外部の枠）は、この変更に含めない。切り出し先は設計の決定で決める

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | AC5 のコマンドは、今の 2 コマンドの合計より遅くならない（盤面への問い合わせの回数を増やさない） |
| 運用・保守性 | 抜粋の置き場所が本文と同じ Skill の中にあり、本文を直すときに抜粋が目に入る |
| 可用性 | 記録の失敗で工程を止めない（今の「何もしない条件」をそのまま守る） |

## 依頼（原文）

#828:

> supervisor / worker（サブエージェント）には、**その持ち場で要る手順だけ**を渡す。Skill の本文を丸ごと読ませない。

> ## 受け入れ条件
>
> - [ ] supervisor / worker を起動する指示の雛形が、Skill 本文の読み込みを求めていない（必要な手順だけが書かれている）
> - [ ] `progress-tracking` の記録が、Skill を読まずにコマンド 1 行でできる
> - [ ] #827 の計測スクリプトで、変更後の版を同じ条件で回すと、サブエージェント内の Skill 読み込み回数が減っている（数値を本 issue に残す）

> この課題は、`agent-layers.md` の supervisor / worker の起動指示の雛形と、抜粋の**形**を決める。各 Skill の抜粋の中身は作らない。

#680:

> それぞれの手法の利点・欠点を比べ、場面や Skill や実行内容によって選ぶ手法を変えるべきかを、コンテキスト・確実性などの観点から検討し、並列（またはバックグラウンド実行）の規則を定めたい。

> **小さな作業にサブエージェントを起こさない線引きはこの課題が持つ。** #827 の提案 5（小さな作業にサブエージェントを起こさない）と #773 の候補 2（実作業が固定費を下回る worker は束ねる）は、問い 1 の表から引く。

進行側からの補足（設計の持ち場の指示）:

> #680 は #828 の雛形に関わる部分（仕事を分ける手法の比較表と「小さな作業にサブエージェントを起こさない」線引き）までを同じ設計で扱い、可搬性・共有する外部の枠（#680 の残る問い 2・3）は切り出すかを設計で決め、切り出すなら out-of-scope で起票する。

## 用語

| 用語 | 意味 |
| --- | --- |
| Skill 本文の読み込み | Skill ツールで Skill を起動すること、または `SKILL.md` を Read すること。どちらも本文全体が文脈に載る |
| 工程の Skill | `development-workflow` の工程表が起動する Skill |
| 工程の外の Skill | 工程表に載らず、どの工程からも呼ばれる Skill（`progress-tracking` / `out-of-scope` など）と、工程の振り分けを持つ `development-workflow` |
| 抜粋 | Skill の本文から、呼ぶ側が要る部分だけを取り出した数行。形は「呼び出し 1 行・結果の読み方・判断の基準」 |
| 器 | 仕事を渡す先の実行の形。その場 / サブエージェント / CLI 実行 / 最小構成の `claude -p` / スクリプト（背景の bash を含む）の 5 つ |
| 固定費 | 器を 1 つ起こすたびに、仕事の前に読む量（システムプロンプト・ツール定義・指示）。`context-window.md` の定義と同じ |
