## 目的

並列の計画のリリース承認ゲートでは、承認の答えの時点で `develop` が承認したコミットより進んでいると、加わった範囲を添えて同じゲートを 1 回出し直す。加わった範囲が文書だけでも出し直すため、人の承認が 1 回増え、一時レーンの起動と提示の組み立ても 1 回増える。

加わった範囲が文書だけのときは出し直さずに、新しい範囲でそのままリリースへ進む。これで人の待ちと一時レーンの往復が 1 回減る。加わった範囲は、リリースの結果と利用者への報告に 1 行で載せる。

## 調べた事実

- 2026-11-11 12:02 JST、計画 p5 のリリース 4（ndf v10.27.54）を利用者が承認した後、#3015（確定仕様化: スプリント lcost-1）が develop へ入っていたため、出し直しの提示（`represent: true`）になった。加わった範囲は `issues/` の設計文書・要求文書を `docs/specifications/` へ移すだけの文書で（26 ファイル、+1501 / −4491、コードの変更なし）、利用者はもう 1 回「新しい範囲で出す」を答えた
- 出し直しの要否は `lib/parallel_run.py` の `confirm`（476 行）が `pr.moved(first.sha, head)` だけで決めており、加わった範囲の中身を見ない（2026-11-11、ソースを読んで確かめた）
- 差分を文書とコードに分ける判定は `lib/diff_kinds.py` の `DiffKinds` が持つ。`docs_only()` は「分類でき、コードのファイルが無く、文書のファイルが 1 件以上」で真になり、**振る舞いを決める文書（`behavior`）があっても真を返す**（`lib/diff_kinds.py` の `docs_only`）。受け入れ条件 2 は `docs_only()` だけでは満たせず、`behavior` が空であることも見る
- このリポジトリの宣言（`.ndf/project.json` の `docs`）は `files` と `tested` を持ち、`behavior` を持たない。振る舞いを決める文書は既定の `**/skills/**/*.md`・`**/agents/*.md` になる
- 提示を省くと、新しい範囲の提示の記録（`presented.json`。確定するコミットと Pull Request の一覧を持つ）は一時レーンの提示のプランが書かないため、今の `confirm` の読み方では範囲が空になる。範囲の求め方は設計で決める

## 前提

- 前提 1: 加わった範囲は、提示 1 で承認したコミットから、承認の答えの時点の `develop` の先頭までの差分のファイルである（消したファイルを含む。`diff_kinds.git_changed` の範囲）
- 前提 2: 「文書だけ」は、宣言で分けて、コードのファイルが 0 件、振る舞いを決める文書が 0 件、文書のファイルが 1 件以上のことを指す。テストが読む文書（`tested`）は文書として数える（起票者の推定 S6）
- 前提 3: 差分のファイルが 0 件で `develop` だけが進んだとき（打ち消し合う変更など）は、`docs_only()` の定義どおり文書だけに当たらず、今のとおり出し直す
- 前提 4: 省くかの判定は、提示 1 への承認の答えで 1 度だけ行う。出し直しの提示（提示 2）への答えでは比べない（今の決まり I14 のまま）
- 前提 5: 差し戻しの答えでは判定しない（今のとおり範囲を比べずに締める）
- 前提 6: `pace: auto` などで MVV 判定がリリース承認ゲートを答えたときも、同じ判定を通る

## 対象範囲

含む:
- 承認の後の出し直しの要否の判定（`lib/parallel_run.py` の `confirm`）
- 文書だけの判定に既存の `lib/diff_kinds.py` を使うこと
- 省いたときに、新しい範囲の版数・コミット・Pull Request の一覧で確定すること
- 省いたことを `wait` の知らせとリリースの結果に載せること
- 手順書 `plugins/ndf/skills/development-workflow/references/parallel.md` の「まとめたリリース」・「答えの後の整理」の記述
- テスト

含まない:
- 1 回目の提示の要否（リリース承認ゲートそのものは残す）
- 1 スプリントのレーン（並列の計画の外）のリリース
- 外のオーガナイザーのレーン（`--parallel-helper --external`）の提示の手順
- `diff_kinds` の分け方そのもの・宣言の項目の追加

## 用語

| 用語 | 意味 |
| --- | --- |
| 出し直しの提示 | 同じリリースのリリース承認ゲートを、加わった範囲を添えてもう 1 回出す提示（`represent: true`）。本文では 1 回目を提示 1、出し直しを提示 2 とも書く |
| 加わった範囲 | 提示 1 で承認したコミットから、承認の答えの時点の `develop` の先頭までに入った変更（前提 1） |
| 文書だけの範囲 | 加わった範囲のファイルを宣言 `docs` で分けて、コードのファイルと振る舞いを決める文書が 0 件、文書のファイルが 1 件以上のこと（前提 2） |
| 出し直しを省く | 提示 2 を出さず、新しい範囲で確定してリリースへ進むこと |
