### W: 多観点の設計レビューの工程化（全体）

経緯: #1142 の設計 PR は cross-review（codex・kiro）で収束していたが、観点を変えた 4 巡のレビューで critical が毎巡いくつも見つかり、約 200 件の指摘になった。NDF が利用者のために作るシステムの設計にも、この多観点の設計レビューを NDF の工程として持たせる。

あるべき姿:

1. 設計 PR には、設計の欠陥の種類（抜け・前提・規模・運用・移行・費用）を指摘の基準として渡し、「まず起きない条件」を書かない側に入れない
2. 設計の観点は、設計文書が触る領域（`design` の手順 1）と受け入れ条件から選ぶ。パスでの分類はコード PR だけに残す
3. ラウンドを重ねて磨く場（cross-review）と、観点を広げて抜けを探す場（多観点レビュー）を分ける
4. 多観点レビューは観点 1 つにつき独立したレビュー役を並列で立て、観点ごとに「見た・指摘なし」を記録する
5. 非機能の大項目ごとに「当たらない」と判断した理由を別の役が確かめる
6. 工程: 設計承認ゲートの前に、観点の一覧を読む → 観点ごとに独立したレビュー役 → 前の巡と既存の Issue で重複を除く → 指摘を分類し、分類ごとにあるべき姿と受け入れ条件にまとめる → **起票の前に人へ見せる場**（利用者の決定）→ 起票。`standard` は必ず、`documentation` は文書の観点で、`legacy-refactor` は設計 PR を分けたときだけ、`light`・`operation` は通さない。1 巡 5〜6 本、上限 2 巡（2 巡目は critical が出た分類だけ）、1 巡の予算を `limits.json` に置く
7. ndf-next の工程の語彙で、多観点レビューを 1 つのアクティビティの中で観点の数だけ並列に広げられる（`when` に規模の条件、`report.schema.json` の `items` に `lens`・`category`・`severity`・`acceptance`）
8. プロジェクトは `.ndf/` に観点（`lenses: [{name, when: {mode, doc_type, area}, instructions}]`）を足せ、NDF の既定の一覧に上乗せする
9. 多観点レビューの入力に、前の巡のまとめ（分類・Issue の番号・あるべき姿）を渡し、重複を除く
10. セキュリティの観点の一覧は新しい版にし、「安全でない設計」を設計のステップで使う

指摘（4 巡目の下書きのまま。重さは 11.x で着手するときに見直す）:

- 指摘の基準が、設計の高次の欠陥を書かない側に入れている: `plugins/ndf/scripts/lib/review_criteria.py` は設計への基準を「食い違い」の 1 つに限り、`NOT_WRITTEN` が「まず起きない条件での異常処理」を書かないと決める
- 設計 PR の観点がファイルのパスで決まり、設計文書には 3 つしか当たらない（`cross-review/scripts/review_lib/categories.py`）
- 全体を見る詳細レビューは実質 1 ラウンドで、直した後の打ち直しも無い（1 ラウンド目はドメインモデルの節だけ、2 ラウンド目以降は差分だけ。設計単体のレビューは 1 回）
- 2 者が同じ観点を受け取り、観点を分担していない
- 非機能と運用の観点は、要求の書き手が当たると決めたときだけ現れる
- 工程に多観点レビューのステップが無く、人がその場で頼むしかない（`qa-security-scan` は工程から呼ばれていない）
- ndf-next の工程の定義の語彙では、多観点レビューを別のステップとして置けない（同じ `range` と `subject` の `review` は 2 つ置けない）
- プロジェクトが足せる観点の宣言が、パスでしか選べない（`.ndf/review.json` の `paths`）
- 前の巡の指摘を除く仕組みが PR の中で閉じている
- `qa-security-scan` の一覧が古い版のまま

直す場所の案: 今の NDF の `design`・`cross-review`（多観点レビューを `design` の手順に足す。観点の語彙は cross-refactoring の `VIEWPOINTS` と同じ仕組み）と、ndf-next の工程の定義。
