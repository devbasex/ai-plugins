## 目的

- 同じスプリントで並行に出した Pull Request の取り込みで用語集（`glossary.json` と `glossary.md`）が衝突しても、worker や conductor が手で両方の語を残さずに済む状態にする。記録した 6 スプリント（m1693・m1385・m653・m1290・m1743・m1683）のすべてで、この手当てを LLM が行っていた
- 判断の要らない衝突（語の単位で重ならない変更）だけをスクリプトが解き、判断の要る衝突（同じ語の食い違い）は今までどおり止める

## 今の作り

- `glossary.py` の副命令は `gate,init,candidates,render,check,diff` の 6 つで、衝突を解く副命令は無い（`python3 plugins/ndf/scripts/glossary.py --help`）
- リポジトリに `.gitattributes` が無く、merge driver の設定も無い
- 用語集の設定 `.ndf/glossary.json` が `source`（`docs/glossary/glossary.json`）と `document`（`docs/glossary.md`）を持ち、`format` は `json` だけを受ける（`glossary.py` の `FORMATS`）
- `glossary.json` は `{"version", "contexts", "terms"}` の 1 ファイル。語は `(context, term)` の組で一意で、`check` が同じ組の重複を `duplicate` として拾う（`structure_findings`）。コンテキストは `id` で一意
- 衝突は 2 つの形で起きている
  - 設計 PR どうしが同じ位置へ語を足す（例: マージコミット ac09b6835 の衝突は、両側の語の追加）
  - 確定仕様化（plan-to-spec）が既存の語の `pending_source` を `source` へ書き換え、隣で設計 PR が語を足す（例: e7a286e33 の書き換え）
- 取り込みの衝突を扱う箇所は `supervise_lib/templates.py:387-399`（差分の検査の fix の指示文「両方の変更を残して衝突を解き」）だけで、LLM の worker に任せている

## 前提

- 前提 1: 解消は `glossary.py` の新しい副命令で行い、用語集のファイルの形（1 ファイル）は変えない。設計が 1 語 1 ファイルを選んだときは、受け入れ条件 1〜7 を「並行の Pull Request が語を足し合っても `glossary.json` が衝突しない」へ書き換え、書き換えた事実をこの本文に残す（未決 1）
- 前提 2: 取り込みは `git merge`（ベースブランチを PR のブランチへ取り込む、またはその逆）で行う。`git rebase` と `git cherry-pick` の途中の衝突は扱わない
- 前提 3: 語の単位の 3 方向の取り込みとして扱う。共通の祖先（`:1:`）・自分の側（`:2:`）・相手の側（`:3:`）を `(context, term)` で突き合わせ、片側だけが足した・書き換えた・消した語はその側を採る。両側が同じ語を同じ中身にしたときは 1 つにする。両側が同じ語を違う中身にしたとき・片側が消して片側が書き換えたときだけを「語の衝突」として止める。コンテキストも `id` で同じように扱う
- 前提 4: 取り込んだ後の語の並びは決定的にする（同じ入力から同じ `glossary.json` が出る）。並びの規則は設計で決める
- 前提 5: 結果は NDF のスクリプトの共通の形（`lib/step_result.py` の 1 行の JSON、`tool: "glossary"`）で出し、終了コードは `glossary.py` の決まり（0 = 通す / 1 = 止める / 2 = 読めない）に従う

## 対象範囲

含む:
- `glossary.py` に衝突を解く副命令を足す（名前は設計で決める）
- 解いた `glossary.json` を書き、`render` と同じ処理で `glossary.md` を作り直し、両方を index に載せる
- 他の衝突が無ければ取り込みのコミットを作る
- 一時リポジトリで衝突を作るテスト
- 用語集の形の説明（`requirements-design` の `references/glossary-format.md`）と `glossary.py` の docstring の副命令の一覧の更新

含まない:
- 取り込みのステップ・プランの雛形からこの副命令を呼ぶこと（#1912・#1917 が足す）
- `glossary.json` 以外の衝突の解消（止めて、パスを出すだけ）
- `git rebase` / `git cherry-pick` の途中の衝突（前提 2）
- 語の衝突を、どちらかの中身を選んで解くこと（人か worker の判断に残す）
- `.gitattributes` の merge driver の登録（未決 2 で採ると決めたときだけ範囲に入れる）

## 受け入れ条件

- [ ] 1. 一時リポジトリで、祖先から両側が `terms` へ別の語を足して `glossary.json` と `glossary.md` が衝突した `git merge` の途中で新しい副命令を打つと、0 で終わり、`glossary.json` が両側の語を 1 回ずつ持ち、`glossary.md` が `render` の出力と一致し、両ファイルが index に載る（`git diff --name-only --diff-filter=U` に出ない）
- [ ] 2. 一時リポジトリで、両側が同じ `(context, term)` の語を違う中身にした衝突と、片側が消して片側が書き換えた衝突では、0 以外（1）で終わり、`glossary.json` と `glossary.md` の中身と index を打つ前のまま残し、出力の `items` に衝突した語（`context` と `term`）を並べる
- [ ] 3. 一時リポジトリで、片側が既存の語の `pending_source` を `source` へ書き換え、もう片側がその隣へ語を足して衝突したときは、0 で終わり、書き換えと追加の両方を持つ `glossary.json` になる
- [ ] 4. 両側が同じ語を同じ中身で足したときは、取り込んだ `glossary.json` にその語が 1 回だけあり、`glossary.py check --rules structure` が `duplicate` を出さない
- [ ] 5. 一時リポジトリで、`glossary.json` のほかに別のファイルも衝突しているときは、`glossary.json` と `glossary.md` だけを解いて index に載せ、コミットを作らずに 0 以外（1）で終わり、出力に残りの衝突のパスを並べる
- [ ] 6. 一時リポジトリで、衝突が `glossary.json` と `glossary.md` だけのときは、副命令が取り込みのコミットを作り、終わった後に `git status` が取り込みの途中でない（`MERGE_HEAD` が無い）
- [ ] 7. 取り込みの途中でないとき・用語集の 2 ファイルのどちらも衝突していないときに打つと、ファイルを書かずに終わり、その理由を出力の `summary` に書く。`glossary.md` だけが衝突しているときは、`glossary.json` から作り直して解く
- [ ] 8. 用語集の置き場を用語集の設定（`.ndf/glossary.json` の `source` と `document`）から読む。設定の `source` を `docs/glossary/` 以外へ置いた一時リポジトリでも受け入れ条件 1 が通り、`glossary.py` の新しい処理に `docs/glossary` の文字列が無い
- [ ] 9. 同じ 3 つの版を 2 回取り込むと、同じバイト列の `glossary.json` が出る（前提 4）
- [ ] 10. 既存のテストが通る（`uv run --frozen --project . --all-extras pytest . -q -n 4`）
