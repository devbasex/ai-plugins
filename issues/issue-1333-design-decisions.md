# #1333: 解析と宣言の書き出し — 決定の記録・テスト設計・未確認

設計の本体は [issue-1333-design.md](issue-1333-design.md) にある。この文書は、その設計で選んだ結論と理由、
受け入れ条件と不変条件ごとの確かめ方、確かめられなかったことを持つ。

## 決定の記録

### 決定 1: 解析は手順 0 で、判定・測定・答え・書き出しの 4 手に分ける

判定（`check`）を分けるのは、新しい宣言のリポジトリで毎回の手順 0 を 5 秒以内に終えるためである（AC4）。測定と書き出しを
分けるのは、その間に conductor の判断（答え）を挟むためで、答えのファイルが測った値と判断した値の境目になる
（非機能の運用・保守性）。hook にしないのは、手順 0 の「拒否しない」と同じ理由で、4 ランタイムで同じに働かせる置き場が本文しか無いためである。

1 つのコマンドで測定から書き出しまでを通し、判断だけを別の CLI へ投げる形は採らない。CLI を起動する費用と認証の失敗が
工程の入り口に乗り、手順 0 を回している LLM が既にいるのに 2 つ目を立てることになる。

### 決定 2: 既存の 10 種類の宣言を移さず、`.ndf/project.json` を 1 つ足す

10 種類は、それぞれの機能が形と読み手を持っている（`worktree.json` だけで読み手はテストを除いて 21 ファイル、シェルと Python の両方）。
移すと、全読み手の書き換えと、移す前の形を読む経路の維持が要り、ai-plugins の振る舞いを変えない条件（移行性・AC3）を
移し方の正しさに預けることになる。新しく足す P1〜P5・P7〜P10 には読み手がまだいないため、1 つのファイルにまとめても何も壊さない。

すべてを 1 つの `project.yml` へまとめる形は採らない。YAML は標準ライブラリで読めず（システム環境の条件）、移す費用に見合う
読み手の得が無い。項目ごとにファイルを分ける形も採らない。#1334 が読む P2〜P5 が 4 ファイルに散り、schema も 4 本になる。

### 決定 3: 起点と本番（P6）は `worktree.json` に書き、`project.json` には持たない

`worktree.json` の `base_branch`・`production_branch` は、既に 21 の読み手（テストを除く）が使う起点の正本である。`project.json` にも持つと、
同じ事実が 2 か所に書かれ、片方だけを直した状態で読み手ごとに起点が変わる。解析は欠けたキーだけを足す（I2）。

`project.json` に持って読み手を順に移す形は採らない。決定 2 と同じく、移行の正しさに振る舞いを預けることになる。

### 決定 4: 値を 1 つに決める規則が書ける項目は測り、根拠が文書や慣行にしかない項目は問いにする

| 項目 | 測る（`measure`） | 問い（conductor が答える） |
| --- | --- | --- |
| P1 言語とフレームワーク | 拡張子ごとの追跡ファイルの数、依存の定義の版（`composer.json` の `php`・`requires-python`・`engines`）、依存の名前の表に当たるフレームワーク | — |
| P2 テストの走らせ方 | 実行器の候補（依存の定義・設定ファイル）、コマンドの候補（`scripts.test`・composer の scripts・`Makefile` の `test`・`scripts/*test*.sh`）、compose のサービス名 | どのコマンドで、どのコンテナ越しに、どのパスを走らせるか。根拠は指示書・README の該当行 |
| P3 全体テストの所要 | 3 つの出所をすべて（決定 9） | — |
| P4 CI の構成 | ワークフロー・直近の成功した run の job の数と壁時計・ruleset の必須のチェック | — |
| P5 DB とコンテナ | compose のファイルとサービス、DB のイメージ（`mysql`・`postgres`・`mariadb`・`redis`・`mongo`）、CI の `services:` | — |
| P6 起点と本番 | origin の HEAD、`main`・`master`・`develop` の有無と最後のコミットの日時、直近 100 件のマージ先の数 | 起点と本番をどれにするか（放置した `develop` を採らない判断はここで行う） |
| P7 配布 | 配布の設定ファイル（`amplify.yml`・`samconfig.toml`・`buildspec.yml`・`appspec.yml` など）、ワークフローの `deploy` を含む行、版数の置き場とタグ | 何を、どの契機で、自動か手動かで配布するか |
| P8 課題の正本 | `issues/*.md` の数、GitHub Issues の数、PR の本文と雛形に現れる課題管理のホスト名 | 正本をどれにするか |
| P9 検査 | 設定ファイルに当たる検査（Pint・Larastan・ESLint・Prettier・black・ruff など） | NDF の方針の検査（`ndf_policies`）を掛けるか。根拠は指示書の方針の行 |
| P10 指示書 | 指示書の有無・`@` の読み込み・古い NDF の案内（決定 12） | — |

**問いの答えは測った値を変えられない。** `write` は `status: question` の項目にしか答えを使わない（入出力の契約）。
LLM に全部を決めさせる形は採らない。決定論で決まる値まで判断が入ると、同じリポジトリで解析のたびに値が揺れ、
古さの判定（決定 6）が変わっていない入力で値を変える。すべてを決定論にする形も採らない。carmo-system-console の
「コンテナ越し」は `CLAUDE.md` の文章にしか無く、規則で拾うと言語とツールごとの表が増え続ける（G6 の範囲）。

### 決定 5: 宣言の形は pydantic のモデルを正とし、JSON Schema はそこから生成する

`check` と `write` はモデルで検証し、公開する schema（AC14）は `project-decl.py schema` の出力をそのまま置く。テストが
生成した結果と置いたファイルの一致を見る。形の正本が 1 つになり、検証と公開がずれない。

手で書いた JSON Schema を正にする形は採らない。検証に `jsonschema` の依存が増えるか、検証を自作することになる。
schema とモデルを別々に手で書く形も採らない。2 つの正本が食い違っても気づけない。

### 決定 6: 古さは、入力のパスの表に当たる追跡ファイルの HEAD の blob と、ブランチの構成で判定する

入力のパスの表（根と 1 段下）:

| 分類 | パス |
| --- | --- |
| CI | `.github/workflows/*` |
| 依存の定義 | `composer.json`・`package.json`・`pyproject.toml`・`requirements*.txt`・`Gemfile`・`go.mod`・`Cargo.toml` |
| テストの設定 | `phpunit.xml*`・`pytest.ini`・`tox.ini`・`vitest.config.*`・`jest.config.*` |
| コンテナ | `compose*.y*ml`・`docker-compose*.y*ml` |
| 配布 | `amplify.yml`・`samconfig.toml`・`buildspec.yml`・`appspec.yml` |
| 指示書 | `AGENTS.md`・`CLAUDE.md`・`.claude/CLAUDE.md`・`KIRO.md`・`GEMINI.md` |

ブランチの構成は、origin の HEAD の指す先と、`main`・`master`・`develop` と宣言した起点・本番の名前のうち origin にあるものの組である。

HEAD の木を使うのは、`git ls-tree -r HEAD` 1 回で blob が揃い、ファイルを開かずに済むためである（試作で 0.05 秒以下）。
コミットしていない手元の編集では古くならない。ロックファイルは入れない。依存を上げるたびに解析が走り、P1〜P10 のどれも
変わらないことが多い。

worktreeのファイルの内容で比べる形は採らない。未コミットの編集で解析が走る。期限で古くする形も採らない。入力の変化と
関係なく解析が走り、変わった直後には走らない。CI の結果（P3・P4 の値）だけが変わった場合は古くならない。測り直すときは
解析の 3 手を手で打つ（`project-analysis.md` に書く）。

### 決定 7: 手で直した値は、前の書き出しの値の指紋で見分ける

`analysis.written` に、`write` が書いた項目の値の SHA-256 を持つ。次の `write` は、今の値の指紋が一致する項目だけを
新しい値へ置き換え、一致しない項目（手で直した）を残して `mismatch` を出す（I1）。手で書いた値を正とする前提 3 と、
古い宣言を作り直す AC5 の両方が、項目の単位で成り立つ。

一度書いた項目を二度と変えない形は採らない。古いと判定しても値が直らず、AC5 の「解析が走る」が値に届かない。項目ごとに
「解析が書いた」の印を持つ形も採らない。手で直しても印が残り、次の解析が手の値を上書きする。

### 決定 8: `ndf_policies` のキーが無ければ、doc-lint の文体の規則も文言テストの拒否も掛けない

2 つは ai-plugins の方針で、宣言の無いリポジトリの既定にすると ai-plugins の形を他へ課す（Value 6）。ai-plugins は
解析で作った `project.json` に 2 つを `true` と書き、同じ Pull Request に入れるため、振る舞いは変わらない（AC9・移行性）。

キーが無ければ掛ける形は採らない。解析が失敗したリポジトリ・`project.json` を持たないリポジトリで、ai-plugins の方針が
既定として残る。宣言の無い既存の利用者は doc-lint が止まるが、手順 0 の解析で明示の値が入る。

### 決定 9: 全体テストの所要（P3）は、測れた出所をすべて並べ、NDF の実行の記録も読む

| 出所 | 何を測るか | サンプル |
| --- | --- | --- |
| `ndf-record` | NDF の実行の記録（`<metrics>/<owner>--<repo>/cross-refactoring-allocation.jsonl`）の `whole_test.init` の直近 10 件の中央値 | ai-plugins の直近の値 140.2 秒 |
| `ci-junit` | 直近の成功した run の artifact のうち JUnit の XML の `testsuite` の `time` の合計（直列の所要） | carmo-system-console 3,827 秒 |
| `ci-steps` | 同じ run のテストの step の所要の合計 | project-trygroup-prd の CI 88 秒 |

**どれを使うかは読み手が決める。** #1334 が要るのは直列の所要か手元の所要で、CI の壁時計は使わない。測定の側で 1 つを
選ぶと、選んだ規則が読み手の用途と合わないときに値を取り直せない。

NDF の実行の記録は、要求の前提 5 が挙げる読み先（worktreeのファイル・`gh`）の外にある。読むのは、ai-plugins の
「手元で約 140 秒」がこの記録にしか無いためである（CI は 2 本に分けて `-n auto` で走り、run の壁時計は約 5 分）。同じ機械の
NDF が書いた記録で、外部へ送らず、リポジトリにも書かないため、前提 5 の目的（外部へ送らない・書き込まない）は保つ。
解析の中で全体テストを走らせる形は採らない。carmo-system-console では 64 分かかり、120 秒の上限（非機能）を超える。

### 決定 10: 秘密は、開かないファイルの名前の表と、書かない値の形の表の 2 段で防ぐ

開かないファイル（I6）: `.env*`・`*.pem`・`*.key`・`id_rsa*`・`*credential*`・`*secret*`・`.npmrc`・`.pypirc`・`auth.json`。
パスだけを記録する。`.env.example` も開かない。雛形に実際の値が入っている例がある。

書かない値の形（I7）: AWS のアクセスキー（`AKIA` ＋ 16 文字）・GitHub のトークン（`gh[pousr]_`）・Slack のトークン（`xox[abprs]-`）・
`sk-` で始まる API キー・`-----BEGIN`・資格情報を含む URL（`://<user>:<pass>@`）。測定の結果の根拠の行にも同じ形の表を当て、
当たった行は伏せる。PR の本文からはホスト名だけを取る。

名前の表だけにする形は採らない。指示書や README の根拠の行に接続文字列が書かれていれば、名前では防げない。

### 決定 11: 宣言は上書きし、解析ごとの記録を積まない

宣言は今のプロジェクトの形を表し、過去の値を読む読み手がいない。積むと、解析のたびに宣言の差分が伸び、利用者が
差分で確かめる（前提 4）ときに読む量が増える。過去の値は、宣言をコミットしたときの git の履歴が持つ。

### 決定 12: 指示書の案内は、古い NDF が置いた印と、指示書が無いことだけを決定論で見る

古い NDF の案内は、ファイルの先頭にある `NDF_PLUGIN_GUIDE_START` の印で見分ける（with-ai-dev の `CLAUDE.ndf.md` は
v2.1.0 の案内でこの印を持ち、`.claude/CLAUDE.md` の `@../CLAUDE.ndf.md` から毎回読み込まれている）。指示書のファイルが
1 つも無ければ（carmo-contractors-app）その旨を出す。どちらも案内の行だけで、指示書を書き換えない（範囲の外）。

案内の中身（今は無い `ndf:*` の名前を探す）で見分ける形は採らない。NDF の Skill とエージェントの名前の一覧を解析が
持つことになり、版を上げるたびに一覧が古くなる。

### 決定 13: 宣言はメインディレクトリの `.ndf/` へ書き、コミットは利用者に任せる

`worktree-setup.sh init` と同じ置き場で、同じガードの扱いになる。解析はコミットも Pull Request も作らない（前提 5・AC15）。
出力に「差分を見て、要らなければコミットしない」と書く（前提 4）。`.gitignore` に当たるリポジトリ（carmo-system-console の
`worktree.json`）では、`git check-ignore` の結果を出力に出すだけで、`.gitignore` を変えない。

解析した工程の Pull Request に含める形は採らない。手順 0 は変更を決める前に走り、どの Pull Request に入るかが決まっていない。

### 決定 14: 課題の正本（P8）は名前だけを記録し、URL や識別子を持たない

`primary` と `others` の名前（`github`・`markdown`・`redmine`・`external` など）だけを持つ。工程を正本に合わせる変更
（#479）が要る値は、#479 の設計が形を足す。社内の課題管理の URL を宣言に書くと、公開リポジトリで社内の情報が出る。

### 決定 15: `supervise.json` の schema はこの課題で作らない

`supervise.json` の `test` の形は #1334 が戦略の宣言として変える。今の形で schema を作ると、#1334 で書き直すことになる。
#1334 が形を変えるときに、決定 5 と同じくモデルから生成する。

### 決定 16: 起点の解決は `lib/repo.py` の 1 つにまとめる

`merged-steps.py` の既定の `develop` を消し、`repo.base_branch()`（宣言 → origin の HEAD → `main` → `master`）を使う。
同じ解決を持つ `pr-steps.py` の `default_branch` を `lib/repo.py` へ移し、2 か所に置かない（`check-script-structure.py` の
`same-name`）。`merged-steps.py` の中で起点を別に書く形は採らない。3 つ目の解決が生まれ、宣言の無いリポジトリで経路ごとに起点が変わる。

## テスト設計

測定と書き出しは仮のリポジトリ（Laravel 風・pytest・CI 無し）で縛る。LLM の答えはテストで固定せず、答えのファイルを
テストが書いて渡す。4 つのサンプルと ai-plugins での値は実測で確かめる（要求の検証手段）。

### 受け入れ条件

| 受け入れ条件 | どの振る舞いで縛るか | どう壊したら落ちるべきか |
| --- | --- | --- |
| AC1 | `.ndf/` の無い仮のリポジトリで check → measure → write を通すと `project.json` ができ、出力に書いたパスと 10 キーの値か不明が出る | `write` が書いたパスを出さない・キーを 1 つ落とすと落ちる |
| AC2 | 4 つのサンプルで解析を走らせ、宣言を要求の表と突き合わせる（実測。不明は表の「不明可」だけ） | 実測なのでテストでは縛らない。結果は課題か Pull Request に残す |
| AC3 | ai-plugins で解析し、`git diff .ndf/` が空で、`test_duration` に `ndf-record` の約 140 秒、`worktree.json` の起点 `develop`・本番 `main` が保たれる（実測） | `write` が `worktree.json` のキーを並べ替える・書き直すと、実測の `git diff` が空でなくなる |
| AC4 | 新しい宣言で `check` が 0 を返し、`.ndf/` の内容が前後で同じで、`gh` を呼ばない | `check` が `gh` を呼ぶ・何かを書くと落ちる |
| AC5 | ワークフローのファイルか依存の定義のファイルを 1 つ変えてコミットすると `check` が 2 と変わったパスを返す。コミットしない編集では 0 のまま | 入力のパスの表から CI か依存の定義を外すと落ちる。worktreeの内容で比べると、未コミットの編集で落ちる |
| AC6 | `gh` を使えない状態（`PATH` に無い・失敗する）で `measure` が 0 で終わり、`ci` と `test_duration` の CI の出所が不明になる | `gh` の失敗で `measure` が 0 以外を返す・ai-plugins の値で埋めると落ちる |
| AC7 | 手で書いた `test` の値を持つ `project.json` と、欠けた `base_branch` を持つ `worktree.json` で `write` すると、手の値が残り、`mismatch` に両方の値が出て、`base_branch` だけが足される | 書いた値の指紋を見ずに置き換えると落ちる |
| AC8 | 宣言の無い仮のリポジトリ（origin の HEAD が `main`、`develop` もある）で後片付けの起点が `main` になる。起点を宣言すればその名前になる | `merged-steps.py` の既定を `develop` に戻すと落ちる |
| AC8 | 2 つの `.md` の手順の例に `origin/develop` が残らない | 文言の照合はテストにしない。レビューと `grep` で確かめる |
| AC9 | `ndf_policies` が無い・`false` の仮のリポジトリで doc-lint が `skipped` で 0、文言テストの拒否が当たらない。`true` なら今と同じに当たる | 宣言を読まずに常に掛けると落ちる。キーが無いときに掛けると落ちる |
| AC10 | JSON として読めない・model に合わない `project.json` で `check` と `write` が 3 を返し、箇所を出し、ファイルを変えない | `write` が壊れた宣言を作り直すと落ちる |
| AC11 | `measure` が 1 を返す・時間切れのとき、手順 0 の表が `解析: できなかった（<理由>）` で手順 1 へ進む | 手順の表の振る舞いなので、`measure` の終了コードの側を縛る（`--budget` を小さくしても 0 で終わり、項目が `時間切れ` の不明になる） |
| AC12 | `NDF_PLUGIN_GUIDE_START` を持つファイルを `@` で読み込む指示書で `note` が出る。指示書の無いリポジトリで「指示書が無い」の `note` が出る。どちらでも指示書の内容が変わらない | 印の判定を外すと落ちる。指示書へ書くと落ちる |
| AC13 | `.env` に秘密の形の値を置いた仮のリポジトリで測定の結果と宣言にその値が出ない。根拠の行に接続文字列を置いても伏せられる | 名前の表から `.env*` を外すと落ちる。形の表を当てずに書くと落ちる |
| AC14 | 置いた `project.schema.json` が `project-decl.py schema` の出力と一致する | モデルだけを変えて schema を置き直さないと落ちる。#1334 の参照は #1334 の設計レビューで見る |
| AC15 | `measure` の前後で仮のリポジトリの `git status` と追跡ファイルが変わらない。`gh` への呼び出しが GET だけである（偽の `gh` が受けた引数で見る） | `measure` が `.ndf/` へ書く・`gh` に POST を渡すと落ちる |

### 不変条件

| 不変条件 | どの振る舞いで縛るか | どう壊したら落ちるべきか |
