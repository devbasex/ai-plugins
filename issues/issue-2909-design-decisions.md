# 機械的なターンのスクリプト化の決定の記録（#2909）

設計の本体は [issue-2909-design.md](issue-2909-design.md) にある。外部の調査の番号（`STD1` など）は本体の表を指す。

## 決定の記録

### 決定 1: 依存を足さずに値を指せるよう、`--field` の書き方を JSON Pointer にする

取り出したい値は「計画の 3 つ目の PR」「結果の最初の項目のパス」のような 1 つの値である。絞り込みと射影は
`get` の既定の要約が引き受ける。JSON Pointer は標準であり、標準ライブラリだけで実装できる。プラグインの依存も
増えない。式の言語（JMESPath・JSONPath）は表現力が広いが、依存が 1 つ増え、AI が式を書き誤る余地も広がる。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1 / STD2 / LIB1 / LIB2 / LIB3

根拠: Value 5 / Value 6（MVV 版 6）

### 決定 2: 取り出しの規則を 1 か所に置くため、`--field` の評価を `lib/json_pick.py` に集め、`step_result.py pick` からも同じ関数を呼ぶ

スプリントの状態・開発ループの記録・用語集の結果・ほかの手順のスクリプトの結果で、同じ書き方の取り出しを
別々に実装しない。`pick` があれば、`--field` を持たないスクリプト（`handoff.py path` など）の結果も
`python -c` を書かずに読める。スクリプトごとに取り出しを足すと、同じ役割の関数がスクリプトの数だけ並ぶ。

- 作り方: 自前で作る
- 比べた候補: STD1 / LIB5

根拠: Value 7 / Value 8（MVV 版 6）

### 決定 3: 読み取りの副命令が工程を止めないよう、`get`・`loop get`・`lookup` は読めた限り `ok` で返し、次の操作は `next` に置くだけにする

取り出しは状態を読むだけで、続けてよいかを判断しない。手順の連続実行の中でも、読み取りの後に止まらず
次の手順へ進む。止まるべきかを決めるのは判断を伴う副命令（`pr-status`・`supervise.py wait`）で、
それぞれが `gate` を返す。読み取りに `gate` を返させると、同じ状態を読むたびに連続実行が止まる。

根拠: Value 2 / Value 5（MVV 版 6）

### 決定 4: 連続実行がマージへ進めてよい場合だけ続くよう、PR の照合は「マージへ進める」だけを `ok` にし、ほかの 3 つを `gate` にする

`ok` は「目標に届いた」を意味する（結果 JSON の正本）。PR の照合の目標はマージへ進めることで、待つ・直す・
人へ戻すはどれも目標の手前で止まる。待つと直すは、AI が次の 1 手を決められるため LLM の判断（21・20）にする。
人へ戻すは人の同意（10）にする。すべてを `ok` にすると、連続実行が失敗のある PR のまま
`merge-when-green` へ進む。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: PRD1 / PRD2 / PRD3 / LIB4

根拠: Value 5 / Value 7（MVV 版 6）

### 決定 5: PR の照合の取得を増やさないよう、`pr-info` の部品を使い、スレッド・マージの状態・PR が閉じる Issue を 1 回の GraphQL で読む

`pr-info` はメタ・畳んだチェック・未解決のスレッドをすでに返し、上限のときの退避も持つ（課題の本文の前提 4）。
足すのはマージの状態と Issue の開閉だけである。どちらもスレッドの照会と同じ PR のノードから読める。`pr-info` の照会を
書き換えると `pr-info` の出力が変わる恐れがあるため、新しい照会として足す。

- 作り方: 自前で作る
- 比べた候補: LIB4 / PRD2

根拠: Value 7（MVV 版 6）

### 決定 6: 連続実行を工程の駆動と同じ場所に置くため、「次へ進める」を `supervise.py` の副命令 `advance` にする

`supervise.py` は、判断の要らないステップをスクリプトで進める役割をすでに持つ。子の結果 JSON は
`step_read` で読んでいる。transcript で最も多い連続は `supervise.py new` の繰り返しと、`queue` の後の `wait` である。
どちらも同じスクリプトの中で閉じる。新しいスクリプトにすると、エントリポイントと契約が 1 つ増える。`sprint-state.py` は
状態の記録を持つスクリプトで、手順を打つ役割を持たない。

根拠: Value 5 / Value 7（MVV 版 6）

### 決定 7: Bash の検査を迂回する経路を作らないため、連続実行が打てるコマンドを NDF のスクリプトに限り、シェルを通さない

任意のコマンドを受けると、hook が見る Bash のコマンドの外で `git push --force` などが打てる。NDF のスクリプトは
結果 JSON を返すため、続けるかを `status` で決められる。ほかのコマンドは結果 JSON を返さず、続けるかを
決められない。

NDF のスクリプトでも、`--` の後のコマンドをそのまま走らせる中継の副命令（`gh_parts.py body-lock`・
`post_queue.py retry`）と `advance` 自身は打たない。所在だけで許すと、中継の副命令を通して任意のコマンドが打てる。
中継の副命令の一覧は `advance.py` の定数に置き、`argparse.REMAINDER` を持つ副命令がすべて一覧に載ることをテストで縛る。
中継の副命令を許したうえで中のコマンドを検査する形は、中継先の引数の書き方ごとに検査が要り、Bash の hook の検査を
写すことになるため採らない。

工程の起動（`supervise.py queue`・`run`）を `--step` に入れると、Bash の hook が見るコマンドは `advance` になる。
文脈が上限を超えた conductor がこの経路で工程を起動しないよう、既存の hook の起動の判定が `advance` の `--step` の
値も読む（I9）。`advance` の中で同じ判定を持つと、判定の記録と再起動の方針の読み込みが 2 か所に分かれる。

根拠: C4 / Value 3 / Value 5 / Value 7（MVV 版 6）

### 決定 8: 進行の連打を消すため、工程名を位置引数で複数受け、本文の書き換えを 1 回にする

今の呼び出しの形（`<番号> <工程名>`）の延長で、工程名を並べるだけで使える。2 つ目以降の位置引数は今は
誤りとして 2 を返すため、正しい呼び出しの出力は変わらない。工程名をカンマで区切る形は、工程名に区切りの文字が
入ったときに割れる。

根拠: Value 5 / Value 6（MVV 版 6）

### 決定 9: 呼んだときだけ働く補助として試すため、ターンの型を数える手段を実験版に置く

数える手段はリリース後テストと分析でだけ打ち、既定の振る舞いから呼ばれない。分類の規則は PR #2905 の型に
合わせるが、規則の原本が無いため、使って数え直しながら直す余地が大きい。実験版の台帳に 1 行を足し、
受け入れ条件 9 の判定に使った結果で本体へ移すかを決める。既存の `usage-report.py` は費用の帳簿の集計で、
Tool の呼び出しの分類を持たないため足さない。

- 作り方: 自前で作る
- 比べた候補: PRD4 / LIB6

根拠: Value 9 / Value 4（MVV 版 6）

### 決定 10: 承認と読み手の量をそろえるため、4 つの候補と数える手段を 1 つのスプリントで出す

4 つの候補は同じ結果 JSON の形と同じ Skill の文書（`waiting.md`・`projects-tracking.md` など）を触る。
候補ごとに分けると、設計承認ゲートとリリース承認ゲートが 4 倍になり、同じ文書を 4 回直す。実装の差分が
1 回の承認で読み切れる量を超えるときは、実装のプランで PR を候補ごとに分ける（承認ゲートは増やさない）。

根拠: Value 2（MVV 版 6）
