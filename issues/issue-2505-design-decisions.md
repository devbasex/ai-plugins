# 開発ループの上限の撤廃の決定の記録（#2505）

[issue-2505-design.md](issue-2505-design.md) から分けた節である。決定 11〜15 は承認ゲート 1 で利用者が決める項目で、ここには設計として採る案を書く。選択肢は設計文書の「利用者が決めること」にある。

## 決定の記録

### 決定 1: 暴走止めを再起動ループの検出 1 つにするため、1 日の起動回数の数えと、数えを守る排他を消す

ラッパーの次の区間の可否は、停止シグナルファイルと再起動ループの検出だけで決める。起動回数の数え（`count_today`）を消す。数えてから `start` を書くまでの排他（`count.lock`）も、数えのためだけにあるので一緒に消す。判定の型の名前（`StartLimit`）は中身に合わせ `SpinGuard` に改める。`NDF_RELAY_MAX_STARTS` は読まない。設定した環境でも誤りにしない。

値を増やす形は採らない。利用者の環境の暫定の 100000 と同じく、上限の意味を失った数が残るためである。

根拠: Vision / Value 2 / Value 5（MVV 版 5）

### 決定 2: 周回の数と時間は「書いたときだけ効く」に揃えるため、無制限を `null` で表す

宣言の既定を周回の数 `null`・経過時間 `null` にする。宣言に書かない場合と `null` を書いた場合は同じ意味で、ループの記録にも `null` が入る。判定は 1 つの関数（`over_budget(used, limit)`。`limit` が `null` なら偽）だけに置き、境の判定と再開の判定の両方がこれを呼ぶ。

| 採らない形 | 理由 |
| --- | --- |
| 無制限を大きな数で表す | このリポジトリの 1000 周・10000 時間は無制限を書けないための代用で、値から意図が読めない |
| `--budget-*` へ `none` のような語を足す | `default` で宣言へ戻せば足り、Factory の受け渡しの形も変えずに済む |

根拠: Value 3 / Value 5（MVV 版 5）

### 決定 3: 待ちを抱えたまま進むため、保留の周回の数を判定から消し、選べる課題が尽きたときの待ちだけで止める

周回の境から保留の周回の数の判定を消す。保留の周回の課題は今も選定から外れる。保留が増えると選べる課題が減り、尽きれば今の `waiting_only`（`no_selectable`）で止まる。止まる理由に `release_pending_max` が出る経路は無くなる。宣言の `loop.release_pending_max` は読まない。不正な値が書かれていても断らない（要求の前提 6）。

根拠: Vision / Value 2（MVV 版 5）

### 決定 4: 実装のステップの進みを手元で確かめられる信号で見るため、会話の記録の伸び・進捗ログの行・コミットの増加の 3 つを見る

進みとして数えるのは、次のどれかである。

| 信号 | 読み方 | 実測 |
| --- | --- | --- |
| 会話の記録の伸び | 実装のステップの `claude -p` に `--session-id` を渡して会話を残し、その記録の大きさを見る | 2026-11-06 の実測で、起動から 6 秒以内に作られ、メッセージのたびに伸び、20 秒の無音のコマンドの間は伸びなかった。`--no-session-persistence` を付けると作られなかった |
| 進捗ログの行 | worker が進捗ログへ書く行 | プランの実行 37 本で、行の間隔の最大は中央値 954 秒・最大 6479 秒。単独では許容時間に使えない |
| コミットの増加 | 作業場所の HEAD までのコミットの数 | 遅れの見張りが同じ値を使っている |

今の実装のステップは `--no-session-persistence` で起動するため、会話の記録が無い。実装のステップに限ってこの引数を外し、`full` のステップと同じく会話の id を決める。

| 採らない信号 | 理由 |
| --- | --- |
| 標準出力 | `--output-format json` は完了まで何も出さない。`stream-json` へ切り替えると 1 行ずつの読み取りが要り、待ちの部品（`run_ticking`）の書き換えが要る。得られる粒度はメッセージ単位で、会話の記録と同じである |
| worktree の変更の監視 | 編集のたびに会話の記録が伸びるため、足しても新しい情報が無い |
| 子プロセスの CPU 時間（psutil で読める） | テストの待ち合わせと固まった状態を区別できず、無音のコマンドの長さは許容時間で受けられる（決定 7） |

- 作り方: 自前で作る
- 比べた候補: PRD2 / PRD3 / PRD6 / LIB1

根拠: Value 4 / Value 5 / Value 6（MVV 版 5）

### 決定 5: 打ち切りの経路を 1 つにするため、既存の締め切りの延長で無進捗の締め切りを動かし、無進捗の打ち切りのステップでは遅れの見張りが打ち切らない

待ちの部品の `extend`（#2047 で駆動の締め切りを延ばすために入れた）を使い、締め切りを「最後の進みの観測 + 許容時間」へ動かす。打ち切りは今の時間切れと同じ経路（`subprocess.TimeoutExpired` → `ClaudeCall` の失敗 → `on_fail` と判定役）を通り、打ち切りの理由だけを記録で分ける。

遅れの見張りは、確認の回数が上限に達すると判定役へ回す。判定役は進んでいるステップにも `retry` / `stop` を返せる。これは「進み続けている間は打ち切らない」に反する。そのため `stall` を持つステップでは見張りを始めない形にし（`off` で始める）、所要の履歴だけを残す。

根拠: Value 5 / Value 7（MVV 版 5）

### 決定 6: 既定で打ち切られないようにするため、実装の上限を「書いたときだけ効く」にし、実績からの見込みを消す

`--impl-timeout` と `.ndf/supervise.json` の `impl_timeout` は書いたときだけ経過時間の上限として効く。書かなければ経過時間の上限は無い。ループの予算と同じ規則であり、書いたプロジェクトが選んだ止まり方を奪わない。

実績からの見込み（`impl_timeout_estimate` の履歴の経路と `estimate_predict.impl_limit`）は消す。打ち切りを決めなくなると読む者が無いためである。プランの `estimate` の欄と、`new` の結果の `impl_timeout_source`・「未校正」の文も一緒に消す。遅れの見張りの履歴は別のもので残す。

根拠: Value 3 / Value 5（MVV 版 5）

### 決定 7: 誤って打ち切らず、固まった実装を半時間で止めるため、無進捗の許容時間の既定を 1800 秒にする

`full` のステップの会話の記録 313 本で、連続する記録の間隔の最大は中央値 57 秒・99 パーセンタイル 590 秒・最大 706 秒だった。900 秒以上は 0 本である。Bash の前景の実行の上限 600 秒に近い値で頭打ちになっている。

誤った打ち切りは数時間分の実装を捨てる。待ちすぎの費用は LLM を使わない 15 分である。そのため実測の最大 706 秒を十分に上回る 1800 秒を既定にする。プロジェクトは `impl_stall_seconds` か `--impl-stall` で変える。

会話の記録が読めないとき（起動から 60 秒たっても記録が見つからないとき）は、進捗ログの行とコミットだけを見て、許容時間を 7200 秒にする。実測の行の間隔の最大 6479 秒を上回る値である。読めない場合に打ち切らない形は、固まった worker が無限に残るため採らない。

根拠: Value 4（MVV 版 5）

### 決定 8: Codex などのプロジェクトでも同じ規則で動くため、外部のランタイムは監視の無進捗の許容へ渡し、監視の上限を「無し」にできるようにする

外部のランタイムの実装のステップは、`external-ai.py run` に `--stall-timeout <許容時間>` を渡す。`--timeout 0` で経過時間の上限を外す。監視は既にログの大きさで無進捗を見ている。監視の `--timeout 0` は「経過時間の上限が無い」の意味とし、外側の待ちも `timeout` を渡さない。

`external-ai.py` は無進捗の打ち切りを結果の `items[0].result` の `stalled` で返す。`call_worker` は今 `status` だけを読むので時間切れと区別できない。この値が `stalled` のとき、Claude のステップと同じ `stalled` の行とステップの結果の `stalled` を書く。行の `last_signal` は `monitor_log`、`last_at` は打ち切りの時刻から許容時間を引いた時刻とする。監視の結果の形は変えない。

agy の `--print-timeout` は CLI の必須の上限で、外せない。工程 `implement` の値のまま残し、残リスクとして書く。

- 作り方: 自前で作る
- 比べた候補: PRD2 / PRD6

根拠: Value 6（MVV 版 5）

### 決定 9: 開発ループを止めずに値を見直せるため、実行環境の調査は読むだけの部品にし、ループの開始と並列の計画の開始で必ず通す

部品（`lib/run_environment.py`）は動く場所・使える CPU・メモリ・レーンの数と動いているプランの数を読み、候補を返す。ファイルへ書かない。`sprint-state.py loop environment` が単独で出力し、`loop start` と `parallel.py start` が同じ部品を呼んで結果に載せる。調査は 1 秒未満で LLM を使わないため、時点を絞る理由が無い。毎回通せば「実行環境が変わったとき」も同時に満たす。指紋を保存して変化を検知する形は採らない。

候補と今の値が違うとき、結果の 1 行とループの記録の `environments` に残して進む。宣言へ書くのは人で、変更は通常の Pull Request として承認ゲートを通る（C7）。読めなければ `unreadable` を載せて進む。

| 値 | 読み方 |
| --- | --- |
| CPU | `sched_getaffinity` と cgroup の `cpu.max` の小さい方 |
| メモリ | `/proc/meminfo` の合計と cgroup の `memory.max` の小さい方 |
| レーンの数（`parallel.py start`） | 開始する計画の `plan.json` の `lanes` の数。この時点ではレーンがまだ動いていないため、計画の値を引数で部品へ渡す |
| レーンの数（`loop start`・`loop environment`） | `.ndf/parallel/` の計画のうち、耐久ワークフローの状態（`parallel_lane.run_status`）が動いているものの `lanes` の数の和。無ければ 1 |

レーンの数の読み先を計画にするのは、ラッパーの一覧には計画と関係のないラッパーと一時レーンが混ざり、Factory の実行ジョブではハブが動かないためである。

`os.cpu_count()` はマシン全体の数を返し、コンテナの制限を見ない。NDF のスクリプトは Python 3.10 で動くため `os.process_cpu_count()`（3.13 以降）は使わない。

- 作り方: 自前で作る・ライブラリやサービスを使う
- 比べた候補: STD1 / STD2 / LIB1

根拠: Value 4 / Value 6 / C7（MVV 版 5）

### 決定 10: 実測のある 1 点から比で伸縮できるよう、候補の数を 8 コア・30 GB でプラン 6 本の比から導く

| 候補 | 式 |
| --- | --- |
| プランの本数の合計 | `max(1, min(floor(コア × 6 / 8), floor(メモリ GiB × 6 / 30)))` |
| 同時に動かすラッパーの数 | `max(1, floor(プランの本数の合計 / 2))` |
| 1 周回で選ぶ課題の数 | `max(1, floor(プランの本数の合計 / max(1, レーンの数)))` |

実測の 8 コア・30 GB でプラン 6 本（2026-09-25）を起点にする。ラッパーの数は今の既定の比（3 / 6）を保つ。課題の数は、1 周回が課題ごとに 1 本のプランを同時に流す（周回 19 の 3 課題で設計のプランが 3 本並んだ）ため、レーンの数で割る。レーンの数の読み先は決定 9 の表にある。3 レーンの計画の `parallel.py start` では 2（6 / 3）が候補になる。式は候補を出すだけで、人の読める量（Value 2）はこの式に入らない。候補の理由の行に「承認で読める量は別に見る」と添える。

根拠: Value 2 / Value 4（MVV 版 5）

### 決定 11: 周回と時間を外した後の歯止めを残すため、費用の予算を残し、周回の費用を使用量の帳簿から導く

費用の予算の既定 60 ドルと判定は変えず、`null` も受ける。周回を締めるときの費用は、使用量の帳簿の和とスプリントの報告の和の大きい方にし、内訳の `source` に採った方を残す。帳簿の和は Claude の行を周回のプランのパスで絞ったもので、cross-review・MVV 判定を含む。Codex と Kiro は USD を持たないため和に足さず、周回の費用の内訳へ呼び出しの数とトークンを残す。帳簿を読めないときは報告の和を使う。

帳簿の和だけにしないのは、Factory の実行ジョブの再開で帳簿の行が欠けるためである。再開は新しいコンテナで動き、帳簿はホームの下にあって保存と復元の対象（`factory/runner/src/state.ts` の `STATE_PATHS`）に入らない。スプリントの報告は `.ndf/` の下にあり復元される。帳簿を読めても行が欠けた小さい和になるので、大きい方を採って今の費用の数えより小さくならないようにする。

conductor の会話は和に入れない。周回を締める時点で conductor の会話を指す手段が無いためである。ラッパーの記録の `from_session` は区間が終わった後に書かれ、動いている区間の会話は載らない。

[費用の実測](#費用の実測) に 1 周回の内訳がある。

根拠: Value 3 / Value 4（MVV 版 5）

### 決定 12: 同じ失敗の費用を止めるため、同じ失敗の繰り返しの既定 2 回を残す

周回の数と違い、レーンを増やしても当たりやすくならない。ループの止まり 37 回に `same_failure` は 0 回である（要求の「目的」の表）。止まらない場合に回り続けるのは失敗の費用だけである。

根拠: Value 3（MVV 版 5）

### 決定 13: 上限を外しても別の数で止まるため、merge から取り込みへ戻る回数と配布の入れ直しの回数を残す

merge から取り込みへ戻る回数は、プランのステップの上限（戻りの輪を 3 回と数える）の中にある。これを外しても同じ回数でプランの上限に当たるため、外すにはステップの上限の式も変えることになる。記録で戻りの上限に当たった実行は 0 件、戻りを通った実行は 1 件である。`/work/ai-plugins/.ndf/loop` の `state.json` を検索し、`"result": "limit"` は 0 件だった。

配布の入れ直しは、回数が尽きると承認ゲートで人へ戻す形で、失敗で止まらない。先端が 4 回動く配布を自動で出さないことは、本番の配布の承認の範囲に沿う。

根拠: Value 3 / Value 4（MVV 版 5）

### 決定 14: Factory でも同じ規則にするため、区間の上限を `RUNNER_SECTION_LIMIT` を書いたときだけ効く形にし、再起動ループの検出を足す

区間の上限は回数の固定の上限で、種類 A（回数・時間の上限で開発ループを止めるもの）に当たる。`section_limit` の終わり方は値を書いた環境で残る。

Factory のランナー（`runSections`）には再起動ループの検出が無い。既定を外すだけでは、空回りする conductor を止めるのは 28,800 秒（8 時間）のジョブの打ち切りだけになる。ループの費用の予算は周回を締めるまで働かず、ループでない実行には予算が無い。そのため `runSections` に NDF のラッパーと同じ検出を足す。区間が 3 つ続けて 120 秒未満なら次の区間を起動しない。

検出で止まったジョブは `job.finished` の `stopped` で終え、理由は `summary` に書き、任意の `reason` は付けない。`reason` の値を増やさないので、契約の定義と API と画面は変えない。

根拠: Value 6（MVV 版 5）

### 決定 15: 動いている経路を壊さないため、耐久ワークフローの止まりの待ち 30 日を残す

`durable.pause()` は cross-review と cross-refactoring の駆動が呼ぶ（要求の前提 2）。`DBOS.recv` の `timeout_seconds` は数を取り、上限の無い待ちの指定は文書に無い（LIB3）。止まりの待ちが上限を過ぎた記録は 0 件である。`/work/ai-plugins/.ndf/loop` と `~/.local/state/ndf/sv` を全文検索し、当たりはスクリプトのコピーだけだった。

根拠: Value 3 / Value 4（MVV 版 5）

### 決定 16: 消した上限の説明を残さないため、`loop status` の `relay_max_starts` を消す

ラッパーの起動回数の止まりは起きなくなる。入れ替え前の古いラッパーが止まる場合は、ラッパー自身の `ndf-relay:` の 1 行とラッパーの記録に残る（要求の前提 4）。入れ替えの期間だけのために判定を残さない。

根拠: Value 5（MVV 版 5）

### 決定 17: 既存の上書きの形に揃えるため、起動の断りを問う回数を環境変数で変える

`NDF_PARALLEL_SPAWN_REFUSALS` を足す。同じ部品の `NDF_PARALLEL_STALL_MINUTES` と同じ読み方で、不正な値なら既定の 3 を使う。#2343 が上書きの経路を作った後は、そちらへ移す。

根拠: Value 6（MVV 版 5）

## 費用の実測

開発ループ lroot3 の周回 19（2026-11-05 22:24〜11-06 01:43 UTC）の内訳である。USD は定価の見積もりで請求額ではない（帳簿の行の `costBasis` は `list`、PRD6）。

| 範囲 | USD | 今の周回の費用に入るか |
| --- | ---: | --- |
| スプリントの報告に載った `claude -p`（プラン 4 本） | 23.93 | 入る |
| 帳簿にあり報告に載らない Claude の起動（cross-review 1.84・MVV 判定 0.40・検査のプラン 0.33・接続の確認 0.03） | 2.59 | 入らない |
| conductor の会話 2 本（`lroot3-19` を含む会話の、この時間帯のメッセージを `token_rates.py` の単価で換算） | 20.98 | 入らない |
| Codex の起動 9 回（155 万トークン） | USD なし | 入らない |
| Kiro の起動 11 回（使用量の記録なし） | 不明 | 入らない |
| USD の分かる範囲の合計 | 47.50 | 記録はその 50% |

```bash
# 帳簿: ~/.local/state/ndf/usage/<runtime>/devbasex__ai-plugins.jsonl の plan に lroot3/lap-19 を含む行の cost_usd の和
# 記録: /work/ai-plugins/.ndf/loop/lroot3/loop.json の laps[18].cost（23.934）
```

周回の費用の記録は 58 周で中央値 9.25 ドル・90 パーセンタイル 26.32 ドル・最大 71.74 ドルである。採る案は帳簿の範囲（この周回で 26.52 ドル）までを数えるので、記録は約 1.1 倍になり、既定 60 ドルで止まる周回の数は大きくは変わらない。実測は 1 周だけで、比は周回で変わる。ループ 10 本のうち 3 本（lroot3・lroot4・lfactory3）は `--budget-usd` で 100 万ドルを渡し、費用の予算を実質的に外している。
