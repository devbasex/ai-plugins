# #2172 の設計の決定

設計文書の本体は `issues/issue-2172-design.md` にある。I の番号はその「不変条件」、F の番号は「機能一覧」を指す。

## 決定の記録

### 決定 1: フェーズの名前を 1 つの意味にするため、ランナーがプランの `"フェーズ"` の値を 5 つの名前へ写し、`まとめ` も `仕上げ` へ写す

今のランナーは状態のディレクトリの名前（`5-impl-2171-state`）の断片を `phase` に送り、`impl`・`release-prod`・`sprint-branch` のようにプランの数だけ名前が増える。プランの JSON の `"フェーズ"` は NDF が持つフェーズの値で、実測で 6 つしか現れない。写しの表は `設計` → `設計`、`実装` → `実装`、`検査` → `検査`、`配布（開発版）` → `取り込み`、`配布（本番）` → `仕上げ`、`まとめ` → `仕上げ` とする。`まとめ` は `pace: fast` / `auto` のプラン（`new close`）で、振り返りと棚卸しを持つため仕上げに当たる（`agent-layers.md` の仕上げの行）。写しはランナーの翻訳だけが持ち、NDF の語を外へ出さない。プランの JSON が読めない・表に無い値は、今と同じくプランの名前を送り、画面は「その他（<名前>）」と出す（I5）。

状態のディレクトリの名前の断片から写す案は採らない。断片の語は NDF のプランのテンプレートの名前で、フェーズの名前と別に増える。

根拠: Value 6 / Value 8（MVV 版 3）

### 決定 2: 工程のフェーズを事象の並びに頼らず決めるため、`step.recorded` に `phase` を足す

1 つの実行ジョブの中で課題ごとの実装のプランが並列に流れ、ランナーはファイルが替わるたびに `phase.changed` を送る。工程のフェーズを「直前の `phase.changed`」で決めると、`order_key`（`at` のミリ秒と冪等の鍵の文字列）が同じミリ秒で `:10` を `:9` より前に並べたとき、隣のプランのフェーズに入る。ランナーは工程を送る時点でプランのフェーズを知っているため、工程に添えれば並びに頼らない。`phase` の無い事象（足す前の形）だけ、同じ実行ジョブの直前の `phase.changed` で読む（I7）。

`order_key` の作り方を変える案は採らない。事象の表の鍵で、既に残った事象の並びが変わる。

根拠: Value 6（MVV 版 3）

### 決定 3: 課題ごとの欄を課題を単位とするプランだけに絞るため、`issues` はプランの名前の番号から取る

NDF のプランの名前は、課題を単位とするもの（`1-design-2206`・`5-impl-2171`）だけが番号を持ち、スプリントで 1 つのもの（`4-sprint-branch`・`6-check`・`7-release`）は持たない。今の `phaseOf` が既にこの番号を取り、`phase.changed` の `issues` に入れている。工程にも同じ番号を添えれば、スプリントで 1 つの工程は番号を持たず「スプリント全体」の欄に入る（前提 5）。

プランの JSON の `"課題"` を使う案は採らない。検査・リリースのプランはスプリントのすべての課題を `"課題"` に持ち、スプリント全体の工程がすべての課題の欄に重なって出る。

根拠: Value 6（MVV 版 3）

### 決定 4: NDF を変えずに触ったファイルを取るため、作業場所の git の、工程の時間の窓のコミットから取る

NDF のステップの行は触ったファイルを持たない。プランの JSON の `"作業場所"` で `git log --no-merges --since=<at − seconds> --until=<at> --numstat` を打てば、その工程が作ったコミットのファイルと増減の行数が取れる。窓の最初のコミットの親と最後のコミットを `commit_range` に残し、差分とファイルのリンクを作る。コミットの無い工程は空の配列、作業場所が無い（消された）・git が 0 以外で終わるときは項目ごと省く。上限は 100 件で、超えた数を `files_omitted` に残す。

NDF のステップの行へファイルを足す案は採らない。`plugins/` を変えることになり、この課題の対象範囲の外である。工程の前後の `HEAD` を見回りが覚える案も採らない。見回り（2 秒ごと）の 1 回に複数の行が届くと、前後の `HEAD` が工程ごとに分かれない。

根拠: Value 5 / Value 6（MVV 版 3）

### 決定 5: 決めたことを工程へ結び付けるため、判断の台帳の `decision` の行を作業場所と時刻の窓で引く

ランナーは既に NDF の判断の台帳（`ask.jsonl`）の `decision` の行を `decision.delegated` として送っている。行は `cwd`（実際の作業のディレクトリ）と `at` を持つため、`cwd` が工程の作業場所の下にあり、`at` が工程の時間の窓（決定 4 と同じ）に入る行を、その工程の `decisions`（`by: ai`）にする。`decision.delegated` は今のまま送り、承認の欄の「AI が代わりに判断した件数」はその件数で数える。

派生が `decision.delegated` を時刻で工程へ結ぶ案は採らない。`decision.delegated` は作業場所を持たず、並列のプランのどれの判断かが分からない。

根拠: Value 6（MVV 版 3）

### 決定 6: 作業の報告とログを 1 つの項目 `output` にし、種類をステップの `type` から決め、32 KiB で切る

NDF はステップの出力を状態のディレクトリの `.out` に 1 つだけ書き（ステップの行の `out`）、`work` のステップでは作業の報告、`run` のステップではコマンドの出力（ログ）になる。項目を 2 つに分けても、どちらか一方しか埋まらない。`kind` を `report` / `log` にし、画面は「作業の報告を開く」か「ログを開く」の一方を出す。実測で `.out` の p99 は 19,323 バイトで、32 KiB で切れば 99% 以上がそのまま届き、最大（57,843 バイト）の報告でも事象 1 件の上限（256 KiB）に収まる。切ったときは `truncated` を真にする。

`.out` を事象に入れず、画面が別の置き場から読む案は採らない。ランナーの外に置き場が要り、事象の列だけから導くという前提 1 を外れる。

根拠: Value 3 / Value 10（MVV 版 3）

### 決定 7: 秘密を外へ出さないため、NDF の伏せ字の 4 つの規則を TypeScript へ写し、ランナーが持つ秘密の値をそのまま置き換える

作業の報告とログには、コマンドの失敗の出力に混ざった token が入りうる（未決 3）。NDF の `secret_redact.py` の 4 つの規則（URL の資格・GitHub の token の形・`x-access-token:` の値・認証ヘッダー）を `factory/runner/src/redact.ts` に写し、`output.text`・`decisions` の文・`files` のパスに当てる。加えて、ランナーが自分で持つ秘密の値（実行ジョブの token・導入の token・持ち込んだキーの値・引き受けたロールの資格）は形に頼らず文字列のまま `***` に置き換える。行と字の数の切り詰め（`redact_output` の 5 行・500 字）は写さない。外へ出す本文は 32 KiB の上限（決定 6）が縛る。

`plugins/` の Python を呼ぶ案は採らない。`factory/` から `plugins/` を参照しない境界（`check-service-boundary.py`）に反する。規則が 2 か所になるため、写した規則の出所（`secret_redact.py`）を `redact.ts` の先頭に書き、伏せ字のテストに NDF の規則の 4 つの形を入れる。

根拠: C1 / Value 1 / Value 6（MVV 版 3）

### 決定 8: 工程の費用を 1 つに結ぶため、ステップの行から作る `usage.recorded` の `at` を、同じ行の `step.recorded` の `at` に揃える

前提 6 の「`payload.step` が等しい `usage.recorded` の和」は、同じ名前のステップ（`pr`・`merge`）がプランごとに現れるため、そのままでは別の工程の費用まで足す。ランナーは 1 つのステップの行から `step.recorded` と `usage.recorded`（モデルごと）を作るため、同じ `at` を付ければ `job_id`・`step`・`at` の 3 つで一意に結べる（I8）。conductor の `usage.recorded`（`step: "conductor"`）はどの工程にも結ばず、使用量の和にだけ入る。揃える前の事象は結べず「—」になる。

`step.recorded` に費用を足す案は採らない。費用の正は `usage.recorded`（確定仕様の「`usage.recorded` は 3 つの形態とも出す」）で、2 つの項目に同じ値を持つと食い違ったときにどちらを読むかが決まらない。

根拠: Value 3 / Value 6（MVV 版 3）

### 決定 9: 派生の表を持たず、読み出しのたびに事象から導く。詳細の件数の上限は 2,000 件、応答の時間の上限は p95 2 秒とする

実測で 1 スプリントの事象は最大 233 件、32 KiB で切った報告の和は最大 375,257 バイトで、1 つの実行の事象は DynamoDB の Query の 1 ページ（1 MB）に収まる。一覧の 50 件は実行ごとに最後の事象から逆に読み、並列 10 本までで済む。派生の表を持つと、受け口が事象の表と別の表を同じ追記で書くことになり、書き手が 2 つになる（集約の持ち主は 1 つ）。件数の上限は実測の最大の約 8.6 倍の 2,000 件とし、超えたら古い工程から省く（I11）。表に `type` の索引が無いため、詳細は件数によらず実行の事象を `LastEvaluatedKey` が無くなるまで全ページ読み、古い `step.recorded` は手元で捨てる。上限が抑えるのは応答の大きさだけで、読み出しの量（RCU・ページの数）は抑えない。「Query の 1 ページに収まる」は実測の範囲（233 件）の見込みで、上限を超える実行は複数ページになる。`ScanIndexForward=false` と `Limit` で切ると古い `gate.reached`・`usage.recorded` を落とすため、その読み方はしない。時間の上限は実環境でしか測れないため、リリース後テストで測り、超えたら派生の表を課題にする（未確認 1）。

派生の表を持つ案（未決 4 のもう一方）は採らない。今の件数で要らず、受け口の書き込みの経路を増やす。

根拠: Value 3 / Value 10（MVV 版 3）

### 決定 10: 読み直しを軽く保つため、詳細の応答から工程の中身の本文を外し、工程の中身を 1 件ずつ読む経路を分ける

詳細は 30 秒ごとに読み直す（前提 7）。本文を含めると、実測の最大で 1 回 375 KB を超える応答を読み直すたびに返す。詳細の応答は工程の行（`StepRow`）と `has_details` だけを持ち、詳細パネルを開いたときに `GET …/steps/{stepKey}` で 1 件を読む。鍵は事象の `idempotency_key` で、冪等の鍵の表から `order_key` と実行の ID を引けるため、別の実行の鍵を渡されても 403 にできる（I12）。

詳細の応答に本文をすべて含める案は採らない。読み直しのたびに使わない本文を返す。

根拠: Value 10（MVV 版 3）

### 決定 11: NDF の版がフェーズを足しても記録を失わないため、受け口は `phase` を列挙で縛らず、フェーズの名前の列挙を依存の無い入口に置く

`phase.changed` と `step.recorded` の `phase` は定義の上では文字列のままにし、5 つの名前は `factory/contracts/src/phases.ts` の定数（`PHASE_NAMES`・`isPhaseName`）に置く（前提 2）。画面も同じ定数を読むため、`@ndf-factory/contracts/phases` の入口を `package.json` の `exports` に足し、ajv を読む今の入口（`src/index.ts`）を画面へ入れない。

定義の `enum` にする案は採らない。NDF の版がフェーズを足すと、その版の事象が 400 になり残らない。

根拠: Value 1 / Value 6（MVV 版 3）

### 決定 12: 読み直しの間隔を 1 か所で変えるため、画面の設定 `pollIntervalMs` に置き、環境変数 `FACTORY_POLL_INTERVAL_MS`（既定 30,000）から埋め込む

画面の設定は既に `vite.config.ts` が環境変数から `FactoryConfig` へ埋め込む形を持つ。同じ形に 1 項目を足し、一覧と詳細の読み直し（`poll.ts`）がそこから読む。読み直しは画面が見えている間だけ動き、前の読み直しが終わる前に次を打たない。

API が間隔を返す案は採らない。読み直しの前に 1 回の読み出しが増え、設定の置き場も 2 つになる。

根拠: Value 5（MVV 版 3）

### 決定 13: 事象の形の追加を承認ゲート 1 で見るため、この設計 Pull Request を「先に出す Pull Request」とし、確定仕様の本文は実装の中で直す

要求は、事象の形の追加を確定仕様を直す Pull Request で先に出し、承認ゲート 1 で見ることを求める。足す形（「データ構造」の表）と翻訳の規則（決定 1〜8）はこの設計文書が持ち、承認ゲート 1 で人が見る。確定仕様 2 本（`ndf-factory-service-boundary.md` の「進捗の事象の種類と受け口」と「受け持つ課題」、`ndf-factory-contracts-and-progress.md` の「進捗の事象の定義」）は、実装の Pull Request の中で定義と同時に直し、定義と仕様が別々の差分で食い違う時間を作らない。

確定仕様だけを直す Pull Request を設計の前に別に出す案は採らない。承認の工程が 1 つ増える（承認ゲートは設計と本番への配布の 2 回）。

根拠: Value 2 / Value 7（MVV 版 3）

### 決定 14: リポジトリの有無を明かさないため、登録の無いリポジトリのバックログも同じ 403 にする

バックログの経路は `repositoryId` を受ける。登録が無いときに 404 を返すと、他人のアカウントの 403 と区別でき、アカウントがそのリポジトリを取り込んでいるかが分かる。一覧と詳細の I12 と同じ本文の 403 に揃える。

404 を返す案は採らない。前提 9 の「有無を明かさない」に反する。

根拠: C2 / Value 6（MVV 版 3）
