# #4049: 中継のラッパー: 引継ぎで子を止める前に、背景の supervisor と ndf plan queue が終わるのを待つ

正は課題の本文（#4049）で、この文書はその写しである。本文から作り直す。手で直さない。

中継のラッパーが文脈の量で子に引継ぎを求めるとき、背景で supervisor や `ndf plan queue` が動く子を強制終了せず、その作業が終わるのを待ってから次の会話へ切り替える状態にする。背景に残るのが `ndf lanes wait` のような待つだけの監視なら、待たずに今のとおり切り替える。

## 何が起きたか

2026-11-22、#3995 の設計 Pull Request（ https://github.com/devbasex/ai-plugins/pull/4041 ）の cross-review で、レビュー担当が指摘 r1-1 を出した。#3995 は文脈の量の閾値を 800,000 から 500,000 へ下げる。中継のラッパーは、文脈の量が上限を超えて子（中継の下で動く claude）が静かになると、子を強制終了して同じ会話を起動し直す。背景で supervisor（`ndf:supervisor` のサブエージェント）が動いていても止めるので、そのフェーズの作業が失われる。困るのは、背景の supervisor やプランのキューの終わりを待っているレーンの conductor と、その結果を待つオーガナイザーと利用者である。

## 種類

機能追加（中継のラッパーが子の背景の作業を見て、引継ぎと起動し直しを待つことは、今の SSOT（`plugins/ndf/skills/development-workflow/references/relay.md` の「ラッパーは見回りごとに、次の順で最初に当たった条件の手を打つ」の表）に無い約束である。表の順 5 と順 6 は、背景の作業に依らず子を止めると書く）

## 今の姿

main の `0682abefe` で確かめた。パスは `plugins/ndf/src/ndf/domains/` からの相対で書く。

- **ラッパーは引継ぎを求めるとき、子を強制終了して同じ会話を起動し直す。** 子の文脈の量が上限（今は `relay.context` の 800,000。#3995 の後は運用上限 `context.limit` の 500,000）以上で、子の出力が静かな時間（`relay.quiet` の 5 秒）止まると、1 つのセグメントに 1 度、子を止めて同じ会話を引継ぎを求める文で起動し直す（`relay/switch_decide.py:116`・`relay/wrapper.py:427` の `_on_handover`）
- **子の出力が止まりの秒（`relay.stall` の 1,800 秒）止まると、同じ会話を起動し直す**（`relay/switch_decide.py:118`・`relay/wrapper.py:414` の `_on_resume`）。起動し直した会話には最初の入力が無い（`_on_resume` に渡る文が空）
- **どちらも子の背景の作業を見ない。** 背景の Agent（supervisor）・`run_in_background` の Bash（`ndf plan queue`・`ndf plan wait`・`ndf lanes wait`）・Monitor は、子を止めると子と一緒に終わる。背景の作業の終わりを待つ conductor は応答を終えて入力を待つので、子の出力は止まり、静かに見える
- **子の背景の作業は、Claude Code が Stop の hook の入力に渡す `background_tasks` の列で分かる。** 2026-11-22 に Claude Code 2.1.330 で、背景の Agent と背景の Bash を起動して応答を終えた会話の Stop の入力を採った。列に `{"type": "subagent", "status": "running", ...}` と `{"type": "shell", "command": "sleep 30", ...}` の 2 件が載り、Agent が終わった後の Stop では Agent の行が消えた
- **中継のマーカーの guard（`relay-marker`）は、この列が空でない間は次のセグメントのマーカーを書かない**（`hooks/guards/relay_mark.py:22`）。次のセグメントへの切り替えは背景の作業の終わりを待つが、引継ぎと起動し直しは待たない

## なぜ困るか

レーンの conductor は、フェーズを背景の supervisor かプランのキュー（`ndf plan queue`）へ渡し、完了の知らせを待つ。待つ間は応答を終えているので、文脈の量が上限を超えた会話や、知らせが 30 分以上来ない会話は、ラッパーに止められる。止めると supervisor とキューが途中で終わり、フェーズの作業（書きかけのコミット・レビューのラウンド・worker の結果）が失われ、conductor はフェーズを頭からやり直す。利用上限の手前でアカウントを替える守り 1 も、同じく背景の作業を見ずに子を止める。一方、監視の終わりまで待つと、`ndf lanes wait` を背景で張り続けるオーガナイザーは引継ぎへ一度も進めず、その間なにもできなくなる。起動し直した会話には背景の作業の知らせが届かないので、止まりの判定で起動し直した会話は入力を待ったまま進まない。#3995 は上限を 500,000 へ下げるので、当たる場面が増える。

## 目的

- 中継の下で背景に作業（背景の Agent の supervisor・`ndf plan queue` など）が残る子を、ラッパーが引継ぎ・止まりの判定・守り 1 の替えで止めない状態にする
- 背景に残るのが監視だけの子と、作業が終わった後の子は、今と同じく引継ぎへ進み、文脈の量の大きい会話が次のセグメントへ切り替わる状態にする

## 前提

- 前提 1: 子が応答の途中（ターンの途中）にある間は、Claude Code の画面が動き続け、子の出力は静かな時間（5 秒）止まらない。今の引継ぎの判定も同じ前提に立つ（応答の途中で子を止めれば、背景でない作業も失われる）
- 前提 2: 背景の作業は子のプロセスの中か子のシェルで動くので、子を止めて起動し直すと、起動し直した会話には背景の作業が残らない（Claude Code の列から消える）
- 前提 3: 中継の下では、Claude Code が Stop の hook の入力に `background_tasks` を渡す（今の見本 `plugins/ndf/tests/domains/hooks/samples/claude/2.1.325/Stop.json` と、2026-11-22 の 2.1.330 の実測）
- 前提 4: NDF は普及のフェーズの前で、シグナルファイルや hook の表の形を変えても互換の経路を持たない（MVV Value 4）
- 前提 5: 背景の作業を始める呼び出しとして hook から見えるのは、Agent・Monitor・`run_in_background` が真の Bash である。利用者の Ctrl+B や Claude Code の自動の切り替えで背景へ回った Bash と、ほかの種類（ワークフローなど）は、Stop の `background_tasks` だけで分かる
- 前提 6: 子を止めて起動し直すかの判定に使う「静かな秒」と「止まりの秒」は、子の出力か端末の入力が最後にあった時刻から数える（今と同じ）
- 前提 7: この課題の実装は、#3995 と lracct（#3604・#3864）の実装の後に行う。守り 1 は lracct の確定仕様（[docs/specifications/ndf-relay-account-switching.md](../docs/specifications/ndf-relay-account-switching.md) の「見回りと止めてよい時点」）の「止めてよい時点で子を止めて同じ会話を別のアカウントで続ける」手で、その止めてよい時点は背景の作業を見ない。背景の作業が残る子を止めない判定は、lracct の仕様ではなくこの課題（#4049）が担う
- 前提 8: 監視は、止めても打ち直せば同じ知らせを受け取れる待つだけの処理である（`ndf lanes wait <計画> --after <番号>` は同じ番号で打ち直すと同じ知らせを返す。`parallel.md` の手順 3）

## 受け入れ条件

この節で「作業」は背景の作業のうち監視でないものを、「監視」は待つだけの背景の作業（`ndf lanes wait`・`ndf plan wait` などの待つだけのコマンドを起動する背景の Bash と Monitor）を指す。見分ける規則は設計で決める。

- [ ] 1. 子の文脈の量が運用上限以上で静かになったとき、子の直前の Stop の入力の `background_tasks` に作業が 1 件以上あれば、ラッパーは子を止めず、引継ぎを求めない。作業が無ければ（空か、監視だけ）今のとおり子を止めて引継ぎを求める
- [ ] 2. 子の出力が止まりの秒（`relay.stall`）以上止まったとき、子の直前の Stop の入力の `background_tasks` に作業か監視が 1 件以上あれば、ラッパーは子を起動し直さない。どちらも無ければ今のとおり起動し直す（止まりの起動し直しは最初の入力を持たないので、監視を止めると子は監視を張り直さないまま入力を待つ）
- [ ] 3. 子が作業を始める呼び出し（Agent と、作業に当たる Monitor・`run_in_background` が真の Bash）をした後、次の Stop の前（Esc で応答を中断して Stop が来ない場合を含む）に 1・2・12 の条件がそろっても、ラッパーは子を止めない
- [ ] 4. 子を起動したばかりで Stop も作業を始める呼び出しもまだ無い起動では、作業が無いものとして 1・2・12 を判定する（運用上限以上で静かなら引継ぎを求める）
- [ ] 5. 前の起動（止めた子）の hook が後から書いた記録と、子のシェルから起動した別の claude（`ndf plan queue` の worker・`claude -p` など、同じ環境変数を引き継ぐ会話）の hook が書いた記録を、今の子の背景の作業として読まず、今の子の記録を書き換えさせない。読めない・形が違う記録は作業 0 件として扱わず、引継ぎを求めない。このとき止まりの判定は今のとおり子の出力と端末の入力で見る
- [ ] 6. 作業が終わった後に子が応答を終え、その Stop の `background_tasks` に作業が無くなれば、運用上限以上で静かな子に、ラッパーは引継ぎを求める（1 セグメントに 1 度。今と同じ）
- [ ] 7. 作業を始める呼び出しの記録を書けないとき（hook の失敗・締め切り）は、その呼び出しだけを拒否し（理由の文を返し、モデルが呼び直せる）、記録の無い作業を始めさせない。監視を始める呼び出し・ほかの Tool の呼び出し・応答の終わりは、記録を書けなくても止めない
- [ ] 8. Stop の入力に `background_tasks` の項目が無いとき・Stop の記録を書けないときは、前の記録を残す（作業 1 件以上の記録を 0 件や不明へ弱めない）
- [ ] 9. 作業を待つ間、`ndf relay ls` に出るラッパーの状態と理由が、背景の作業を待っていることと最後に分かった作業の件数（開始の記録なら「1 件以上」）・記録の時刻を示す。待ちが解けて子が動き出したら、状態が動いている子の形（`running`）へ戻る
- [ ] 10. 運用上限未満で、止まりの秒にも達せず、守り 1 の替える時点でもない見回りでは、ラッパーは背景の作業の記録を読まない（読み取りの回数が 0 回）
- [ ] 11. 背景に残るのが監視だけの子（`ndf lanes wait` を背景で張り続けるオーガナイザーを含む）は、運用上限で静かになれば待たずに引継ぎへ進み、守り 1 の替える時点では待たずに替える。監視と作業が混ざるときは待つ。止まりの秒では、監視だけの子も起動し直さない（2）
- [ ] 12. 守り 1（#3604・#3864 の設計の、利用上限の手前の閾値 A・C を越えて止めてよい時点で別のアカウントへ替える手）は、作業が 1 件以上あれば子を止めずに待ち、作業が無ければ今のとおり替える。記録が不明なら替えずに待つ。上限に達した後の替え（守り 3）は、作業が残っていても今のとおり待たずに替える
- [ ] 13. 見分ける規則で監視と言えない背景の作業（知らない種類・コマンドが読めない・切られた・待つだけのコマンドとほかのコマンドが混ざる）は作業として扱う
- [ ] 14. 設計文書が、利用者の全体の設計方針（#4069）との照らし合わせを決定の 1 つとして持ち、待つ子とプロンプトのキャッシュ・待ちを伝えること・再利用に備えた待機の 3 つについて、方針に合うかと、合わない部分の直し方か分けた Issue の番号を書く（設計レビューで確かめる）
- [ ] 15. 1〜13 を、文脈の量の境界の値（運用上限 − 1・運用上限）と呼び出しの回数で確かめるテスト（時間で区切らない。時刻は差し替えた時計で進める）がある。11 は、運用上限で監視だけ → 待たない・作業 1 件 → 待つ・監視と作業が混ざる → 待つ、の 3 つと、背景に `ndf lanes wait` だけがある子（オーガナイザーの会話の形）を 1 件含む。.md の文言を照らすテストにはしない
