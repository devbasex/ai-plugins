## 期待する結果

1. `current` が承認記録の最後の `body` から本文のパスを解き、`review-scope` の blob 照合も同じパスを使う。既定外のパスで承認したリポジトリのテストがある
2. `fenced_lines` が開いたフェンスの文字と長さを持ち、同じ文字で同じ長さ以上の閉じ行だけで閉じる。4 字で開き 3 字の行を含む例で、内側の `根拠:` を拾わないテストがある
3. `_changed` が取得した本文と全差分を使えるときは使い回し、足りない本文はまとめて読む。比較の基点と head が同じ間は成功した確認の結果を使い回す。複数の文書を含む無修正の収束で Git の起動回数を縛るテストがある。既存の FULL 差分・検証済みの head 側の文書を再利用し、増分ラウンドで全差分が要るときも比較の基点と head ごとに成功した結果を共有する。同じ head と更新した head の両方で起動回数を縛る。使い回す条件は比較の基点・head・MVV の識別子の 3 つが同じことで、どれかが変わったときか前の確認が失敗したときは打ち直す
4. 根拠の確認の成否を指摘の行とは別に終わり方の判定へ渡す。既存の NDF の指摘が 0 件でも、最後の読み取りの失敗で `mvv_unresolved` で止まるテストがある。検査に成功した head だけを収束として保存・再利用し、検査に失敗したラウンドの収束の記録を次回に使わない
5. 公開する引継ぎデータと復元の契約に MVV の分類と識別子を足す。空の状態ディレクトリから復元するテストがある
6. 各分類（`fixed`・`unresolved`・`redline`・`deferred`）が判定したときの識別子を持ち、旧版の行を今回の判定・結果・記録に使う前に再判定する条件が決まっている。旧版で `P1` とされた行が新版で `Value 5` の指摘として出し直されたとき、旧版のレッドライン扱いで差し戻しと収束の停止を抑えず、旧版の行は履歴に残す
7. 記録と `outputs.mvv` の自由記述を、既存のレビューの公開経路と同じ規則で伏せる。秘密の原文が出ないテストがある
8. 受け付ける根拠の行の形（区切りは ` / ` だけか、`・` と引用文も許すか）と、「括弧の前」を `（MVV バージョン <数>` の位置で決めることが詳細設計に書かれ、テストがある。`decisions.md` の形に合わせない既存の設計（#4051 の決定 1〜5 の根拠の行）の扱いも決まっている。決定の根拠の行を先に特定し、`（MVV 版 11）` のように版の書き方を外した行・版の欠けた行・解析できない行を通さず指摘する（書式を外すだけで版の誤りの指摘が解決扱いにならない）。PR #4095 の元の形（`- 根拠: Value 3「…」（MVV 版 11）`）を例としてテストに入れる
9. fetch した後のベースをコミットに固定し、MVV・差分の起点・再利用の判定のすべてへ同じコミットを渡す。古いローカルのブランチを置いた統合テストがある
10. 既存の写しも元の全 SHA-256 と照らし、違えば検証済みのバイト列で原子的に作り直すか `precondition` で止める
11. NDF が持つ共通原則の検証済みの参照を基準 5 の指示に渡し、その版をレビューの再利用の条件に含める
12. `by: ndf` の行をスレッドの resolve による解決（`_settle_resolved`）から外し、収束の再利用でも同じ対象の head での検査の成功を求める
13. CLI の `_mvv_current` も cross-review と同じく宛先を明示した refspec で取る（既存の `Git.fetch_branch`）。追跡の refspec を持たない clone で、取得した新しい版を読むテストがある
