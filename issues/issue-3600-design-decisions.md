# エピックのアーキテクチャ設計書の ADR（#3600）

設計文書 [issue-3600-design.md](issue-3600-design.md) の ADR（設計判断の記録）である。番号の `STD`・`PRD`・`LIB` は設計文書の「外部の調査」の表を指す。語の意味は設計文書の「用語」の表にある。

## 決定の記録

### 決定 1: 小さな作業にアーキテクチャ設計書を書かせないため、規模の判定を「1 つの目的が 2 本以上のレーンか 2 つ以上のスプリントに分かれる見込み」で切る

エピックに当たるのは、1 つの目的の作業が 2 本以上のレーンか 2 つ以上のスプリントに分かれる見込みのときである。1 つの目的とは、1 つの親 Issue か 1 つのプロンプトを指す。独立した Issue を並列の計画に並べただけのものは、レーンが複数でもエピックではない。共有する前提が無く、アーキテクチャ設計書に書く中身が無いためである。手がかり（Issue の数・プロンプトに書かれた範囲・既存の親子の Issue）が無いときはスプリントとして扱い、理由を判定結果の `規模:` の行に残す。

判定は `development-workflow` の本文に 4 行で置く。4 行は、判定・エピックのときの行き先・手がかりが無いとき・判定結果の出力の例への `規模:` の各 1 行である。判定はモードと進め方を変えない（決定 2）。境界の値と例はアーキテクチャ設計書のガイド（`design/references/epic-foundation.md`）が持つ。

「3 本以上のレーン」を境界にする形は採らない。#1142 の手戻りの多くは、2 つのサブ Issue が同じコントラクトを別々の形で作ったことから起きた。2 本で既に食い違いが起きる。

根拠: Value 1 / Value 2 / Value 3（MVV バージョン 7）

### 決定 2: 承認ゲートを足さず利用者の選択を変えないため、アーキテクチャ設計書を最初のスプリントの Pull Request に載せ、モードと進め方は利用者が選んだものに従う

アーキテクチャ設計書は、エピックの最初のスプリントの Pull Request に、そのスプリントの Issue の文書と並べて載せる。最初のスプリントのモードと進め方は、利用者が選んだものに従う。規模の判定はモードと進め方を変えず、`ndf progress new` は `--scale` の値で作成を断らない。アーキテクチャ設計書が通る承認ゲートは、選ばれたモードと進め方が決める。

| 選ばれたモード・進め方 | アーキテクチャ設計書が通る所 |
| --- | --- |
| 設計 PR を出すモード・進め方 `normal` | 設計 PR に載り、設計承認ゲートで人が見る |
| 設計 PR を出すモード・進め方 `auto`・`fast` | 設計 PR に載り、設計承認ゲートを通る。ゲートは、MVV の承認・ハッシュの一致・判定の記録がそろったときだけ MVV 判定が通し、そろわなければ人へ戻す（`development-workflow` の `references/pace.md`） |
| 設計 PR を出さないモード（`light`・`operation`） | 実装 PR に載り、その PR のレビューとリリース承認ゲートを通る |

どの経路でも、アーキテクチャ設計書の中身はベースブランチに入る前に承認ゲートを通る。さらに、並列の計画の起動前チェックが必須セクションの空と表の形を落とし（I1・I2）、CI がコントラクトテストを実行していることを起動の条件にする（I11）。守らせる所はこの 2 つの機械のチェックで、モードと進め方を固定しなくても、空のアーキテクチャ設計書でレーンが起動することは無い。2 つ目以降のスプリントは、アーキテクチャ設計書を読む側として各自のモードと進め方で進む。2 つ目以降のスプリントの実装 PR がアーキテクチャ設計書を書き換えるときも、承認ゲートは足さない。人はその PR のレビュー・CI のコントラクトテスト・変更通知の 3 か所で見る（設計文書の「アーキテクチャ設計書の形」）。

最初のスプリントをモード `standard`・進め方 `normal` に固定し、`ndf progress new` が `--scale epic-first` でほかの組み合わせを断る形は採らない。利用者が承認をどこまで AI に任せるかを決めるのは利用者であり（Value 1）、規模の判定がその選択を上書きすると、エピックの作業だけ利用者の選んだ進め方で進まない。進め方 `auto` でも、設計承認ゲートは MVV 判定の条件がそろわなければ人へ戻すため、人が見る経路は残る。

アーキテクチャ設計書だけの Pull Request を先に出して別に承認を取る形も採らない。承認ゲートの数と配置先は `development-workflow` だけが持ち、ゲートが 1 つ増える。

根拠: Value 1 / Value 4 / Value 5（MVV バージョン 7）

### 決定 3: NDF の工程と二重にしないため、仕様駆動の既存のツールを取り込まず、全体と機能ごとの 2 層の型だけを倣う

Spec Kit（LIB1）は、constitution をプロジェクトに 1 回・specify から tasks を機能ごとに回す形を持つ。NDF は要求・設計・実装計画・承認ゲートを既に持ち、Spec Kit の工程を入れると同じ工程が 2 つになる。Spec Kit には並列の計画・レーン・CI のコントラクトテストが無く、この Issue の受け入れ条件 2〜6 を満たさない。採るのは 2 つの型である。1 つは、全体の文脈（Kiro の steering・Spec Kit の constitution）と機能ごとの仕様を分ける 2 層の型である。もう 1 つは、必須の項目がそろうまで実装へ進めない KEP の型（STD4）である。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: LIB1 / PRD1 / PRD2 / STD1 / STD4

根拠: Value 11 / Value 12（MVV バージョン 7）

### 決定 4: 同じ事実を 2 か所に持たないため、エピックを集約にせず、完了条件の定義をアーキテクチャ設計書に置いて計画は番号で指す

エピックはアーキテクチャ設計書 1 本と、それを指す並列の計画で表す。エピックの状態のテーブルを作らない。完了条件の定義（項目の文と確認方法）はアーキテクチャ設計書の「完了条件」の表に置き、計画の設定ファイルの `epic.done` は番号（`D1` など）だけを持つ。続く複数の計画が同じエピックを進めても、定義は 1 か所に残る。`done` は必須で、既定値を持たない。省いたときに「すべて」と読むと、複数の計画で進めるエピックの最初の計画が、後の計画で満たす項目を待ち続けて終わらない。計画 1 つでエピックを終えるときは、番号をすべて並べる。

完了条件の定義を計画の設定ファイルに書く形は採らない。エピックが複数の計画にまたがると、同じ項目が計画ごとにコピーされ、片方だけ直ると食い違う。要求の対象範囲の「並列の計画の欄（エピックの完了条件）」は、番号のフィールドとして満たす。

根拠: Value 8 / Value 11（MVV バージョン 7）

### 決定 5: 先に決める範囲を絞るため、必須セクションを 9 つ、該当時のセクションを 3 つにし、セクションの一覧の正本をアーキテクチャ設計書のスキーマ 1 か所に置く

必須セクションは、変えると高くつく・元に戻せない・他のレーンと形が食い違うものに当たる 9 つである。目標と非目標・完了条件・用語・境界と責務・データ構造と状態の保存先・入出力のコントラクト・設定ファイルと環境変数・テストと検証の基盤・未決の問いを指す。横断の関心事・移行・ADR は該当時にする。arc42 の横断の概念（STD1）は、必要な話題だけを選ぶよう求める。Google の design doc（STD3）は目標と非目標・横断の関心事を、Twelve-Factor（STD6）は設定の分離を求める。

セクションの名前と表の列は `contracts/epic/foundation.schema.json` に置く。テンプレート（`ndf epic init`）・チェック（`ndf epic check`）・ガイドの表は、そこから読む。ガイドの表は手でコピーせず、ndf-next の規約の生成（`ndf check --write-spec`）で描く。

すべてのセクションを必須にする形は採らない。小さなエピックでも横断の関心事と移行を書かせると、空のセクションを「無し」で埋める作業だけが増える（PRD3 の指摘）。

根拠: Value 3 / Value 11 / Value 12（MVV バージョン 7）

### 決定 6: テンプレートのまま起動されないため、空のセクションを「HTML のコメントと空行のほかの行が無いセクション」と定める

テンプレートはセクションごとの書き方のガイドを HTML のコメントで置く。埋めずに残したセクションは、見出しとコメントだけになり、空と判定される。「無し」の 1 行は中身として数える。未決の問いが無いときなど、書き手が確かめて無いと書いたセクションを空と区別するためである。

文字数の閾値で空を決める形は採らない。閾値は書き手が短い文で満たせ、書き手が確かめたかを表さない。

根拠: Value 3 / Value 13（MVV バージョン 7）

### 決定 7: 言語とコントラクトの形を問わず検証できるよう、コントラクトの行の検証方法を `exists:`・`schema:`・`generated:`・`command:` の 4 つにし、実装前の行を `—` で置く

検証方法は次の 4 つである。

- `exists: <glob>`: コントラクトの名前（環境変数の名前・サブコマンドの名前など）が glob に当たるファイルに文字どおり現れるかを見る
- `schema: <glob>`: glob に当たるファイルが正本のスキーマ（JSON Schema）に通るかを jsonschema（LIB2）で見る
- `generated: <コマンド>`: コマンドの出力が正本と 1 字も違わないかを見る。この形は実装から正本を生成するリポジトリに当たり、ndf-next の #3518 の生成と突き合わせ（`ndf check` の規則 spec-docs）も同じ考えである
- `command: <コマンド>`: コマンドが終了コード 0 で終わるかを見る

正本が JSON Schema でない形と、正本から実装を生成する形（スキーマ駆動）は、`command:` で検証のツールを指す。OpenAPI の定義・TypeScript の型・GraphQL のスキーマ・DB のマイグレーションがこれに当たる。指すのは利用者のリポジトリが持つツール（lint・型検査・コード生成の `--check`・マイグレーションの試し適用）である。4 つの形の書き方は設計文書の「アーキテクチャ設計書の形」にある。アーキテクチャ設計書の表の解析は markdown-it-py（LIB3）で行う。

実装の前のコントラクトは検証方法を `—` にし、検証しない。チェックは `—` の行の数を警告として出す。実装する Pull Request が同じ差分で、自分が実装したコントラクトの行の検証方法だけを書き込む。並列のレーンの書き換えが隣り合う行で git の競合になったときは、後からマージするレーンがベースブランチを取り込んで解く。検証方法だけの書き換えはコントラクトの中身を変えないため、変更通知の比較では検証方法の列を除く（決定 13）。

言語ごとの解析器（構文木から環境変数の読みを集める）と、コントラクトの形ごとのアダプタ（OpenAPI・GraphQL・マイグレーションの差分を NDF が読む）を NDF に持たせる形は採らない。利用者のリポジトリの言語とコントラクトの形は限らず（Value 4）、形ごとの検証のツールは各エコシステムに既にある（Value 12）。ndf-next の自分のチェック（spec-io）は Python だけに当たる。

検証方法を 3 つのままにする形も採らない。`schema:` は正本が JSON Schema のときだけ、`generated:` は実装から正本を生成するときだけ書ける。OpenAPI から型を生成するリポジトリや DB のマイグレーションでは、行が `—` のまま残る。

- 作り方: 自前で作る・ライブラリやサービスを使う
- 比べた候補: LIB1 / LIB2 / LIB3

根拠: Value 4 / Value 12（MVV バージョン 7）

### 決定 8: 同じ検証を 2 度行わないため、起動前チェックはセクションと表の形だけにし、コントラクトテストは CI に任せる

`ndf lanes init`・`start` は、ベースブランチのアーキテクチャ設計書に `ndf epic check --shape-only` と同じチェックを当てる。見るのは必須セクションと表の列の形である。あわせて、計画の完了条件の番号をアーキテクチャ設計書と突き合わせる。コントラクトテストは行わない。コントラクトテスト（受け入れ条件 3）は Pull Request ごとの CI で `ndf epic check` を実行する。ベースブランチへ入る差分はその CI を通っており、起動前に当て直すと同じ検証を 2 度行う。実装前の行は検証方法が `—` で検証しない（決定 7）ため、コントラクトテストを起動前に当てても当てなくても、`—` の行で起動が止まることは無い。違いは費用だけで、起動前に当てると `schema:`・`generated:` のためにベースブランチのコミットを切り出す手間が起動のたびに増える。起動前チェックはアーキテクチャ設計書の blob だけを読む。

このリポジトリでは `.github/workflows/ndf-next-checks.yml` に 1 ステップを足す。利用者のリポジトリの CI は NDF が書き換えず、最初のスプリントで利用者のリポジトリの CI に足す。アーキテクチャ設計書の必須セクション「テストと検証の基盤」は、`触るファイル:` の行で CI の定義のファイルを名指す。`ndf lanes init`・`start` は、名指したファイルのどれかに `ndf epic check` が文字どおり現れるかを確かめる。無ければ `missing-ci-check` で落ちる（I11）。CI の製品を問わず、ファイルの中の文字列だけを見るため、言語や CI の種類に依らない（Value 4）。文章で書かせるだけにせず、CI が実際にコントラクトテストを実行することを起動の条件にする（要求の S5）。

根拠: Value 4 / Value 13（MVV バージョン 7）

### 決定 9: 計画のサブコマンドと責務を分けるため、アーキテクチャ設計書のサブコマンドを `ndf epic` として新設する

テンプレートの生成とコントラクトテストは、並列の計画が無くても使う（CI は計画を読まない）。計画のサブコマンド `ndf lanes` に入れると、`lanes init`（計画のワークフロー状態を作る）とアーキテクチャ設計書の `init` の意味が重なる。`ndf epic` は Skill ではなくサブコマンドで、配る Skill の表（受け入れ条件 9）は変わらない。サブコマンドの一覧（`docs/contracts/commands.md`）は生成で描かれる。

`ndf lanes epic-init` のように計画のサブコマンドの下へ置く形は採らない。CI が計画のサブコマンドを呼ぶ形になり、計画の無いリポジトリで使えない。

`ndf epic check` が読む入力は、アーキテクチャ設計書と、リポジトリの設定 `.ndf/project.json` の `issues.primary` の 2 つである。`issues.primary` は、完了条件の確認方法 `issues:` を書けるかの判定（決定 20）にだけ使う。これはリポジトリに 1 つの設定で、CI のチェックアウトにもあるため、計画を読まずに判定できる。計画の設定ファイルは読まない。次の 2 つは、計画を読む `ndf lanes init`・`start` の指摘にする。

- 計画の完了条件の番号の突き合わせ（指摘の種類 `unknown-done`）
- ベースブランチにアーキテクチャ設計書が無いことの指摘（`missing-foundation`）

根拠: Value 9（MVV バージョン 7）

### 決定 10: 利用者の設定を書き換えずにアーキテクチャ設計書を見つけるため、配置先を決めず、文書の先頭のマーカーで見つける

NDF はアーキテクチャ設計書の配置先を既定で持たない。アーキテクチャ設計書はリポジトリのどこに置いてもよい。テンプレートは先頭にマーカー `<!-- ndf: epic-foundation -->` を置く。`ndf epic check` は引数が無いとき、追跡しているファイルのうちマーカーを持つ Markdown をすべてチェックする。並列の計画は `epic.foundation` でパスを持つ。ガイドは配置先の例として `docs/epics/<エピックの名前>.md` を挙げる。

`.ndf/` にアーキテクチャ設計書の一覧の設定ファイルを足す形は採らない。エピックを始めるたびに利用者の設定を書き換えることになり、共通原則の C7 に当たる操作が工程の中に増える。

根拠: Value 4 / Value 6（MVV バージョン 7）

### 決定 11: 計画の状態の値を増やさないため、完了条件の項目が残る間を状態にせず、Durable Workflow が開いて閉じるリクエストでオーガナイザーへ通知する

全レーンの行が終わり、ほかに答えていないリクエストが無く、完了条件の項目が残るとき、計画は実行中のまま止まる。Durable Workflow はリクエストを 1 件開く（キーと理由は残りの完了条件の番号の並び）。完了条件の項目は、上限の設定の間隔（`limits.json` の `lanes.epic-recheck`）で再判定する。すべて満たしたら、Durable Workflow がリクエストを閉じ、同じループの 1 回で計画を完了にする。完了の判定は、このリクエストを答えていないリクエストに数えない。オーガナイザーはレーンか行を足すか、何もせずに項目の成立を待つ。オーガナイザーがリクエストを閉じても、同じキーでは開き直さず、残りの並びが変わったときだけ新しいキーで開く。既存の停止の通知（Durable Workflow が開き、レーンが動き出したら閉じる）と同じ扱いである。

判定し直せない回が続いたとき・アーキテクチャ設計書に無い番号・残った判定の作業ディレクトリのリクエストも同じ規則で開き閉じる（エピックのリクエスト）。完了を止めるのはリクエストではなく原因の条件（設計文書の I12〜I14）で、オーガナイザーがリクエストを閉じても、原因が残れば完了しない。判定の回の成否と続けて失敗した回数は `epic_judged` として記録し、`status` と再開した Durable Workflow は記録から引く。

完了の判定（#3092 の不変条件 I16。全レーンの行が完了か中止で、答えていないリクエストが無いときだけ完了にする）は、計画に `epic` フィールドがあるときだけ完了条件の項目を足して見る。

状態の値として持たない代わりに、`ndf lanes status` が導いた結果を結果 JSON の `metrics.epic_state` に出す。値は `running`・`waiting_done`・`done` のどれかである。導く関数は Durable Workflow の完了の判定と同じ 1 つである。Factory を含む読み手は、完了の規則を自分で組み直さずにこの値を読む（Value 11）。

完了を、オーガナイザーがリクエストを閉じることに結びつける形は採らない。項目がすべて満たされても人の操作を待つことになり、受け入れ条件 4 の「すべて満たしたときに終わる」が人の操作に依存する。

状態の値「完了条件待ち」を計画のワークフロー状態に足す形は採らない。状態の値と遷移の表（`progress.json`）が変わり、Factory を含む読み手すべてに新しい値の扱いが要る。行とイベントから出せる値は持たない（ndf-next のレーンの状態と同じ扱い）。

根拠: Value 1 / Value 8（MVV バージョン 7）

### 決定 12: 判定の結果を追跡できるよう、完了条件の判定を値が変わったときだけイベントとして追記する

Durable Workflow は完了条件の項目を判定し、前の記録と値が違うときだけ `done_checked` を書く。`status` は最後の記録を読むだけで、判定のコマンドを実行しない。`status` は人と Factory が何度も読み、そのたびに `command:` の確認方法を走らせると費用と時間がかさむ。判定の記録が無い項目は未判定と出す。判定は、計画が実行中の間も、行が終わるたびと上限の設定の間隔ごとに行う。全行が終わってから判定すると、実行中の `status` で項目がすべて未判定になり、進捗が出ない（受け入れ条件 5）。`done_checked` は、判定に使ったベースブランチのコミットを `commit` に持つ。`status` はそのコミットのアーキテクチャ設計書から項目の文を読み、`items` の `text` に出す。

`status` のたびに判定する形は採らない。上の費用に加え、同じ時点の 2 つの読み手が違う値を見る。

根拠: Value 2 / Value 8（MVV バージョン 7）

### 決定 13: 重ならないレーンを止めないため、変更通知の宛先を触るファイルの重なりで選び、未読を既読フラグで管理する

Durable Workflow は、ベースブランチのアーキテクチャ設計書の blob の識別子が比較元のリビジョンから変わったかを見る。変わったら、違うセクションの触るファイルを集める。既存の `touch_hit` で重なるレーンへ、`foundation_noticed` を 1 件書く。表の無いセクションで `触るファイル:` の行も無いもの（用語・目標と非目標など）は、全レーンに効くとして `**` を当てる。コントラクトの表は検証方法の列を除いて比べ、検証方法だけが変わった変更では変更通知を出さない（決定 7）。比較元のリビジョンは、最後の `foundation_noticed` の `to_rev` である。無ければ最初の `plan_started` の `foundation_rev`（`ndf lanes start` が起動時点のリビジョンを書く）を使う。Durable Workflow が再開しても、最新の記録から比較元が決まる。レーンの conductor は、次のサブコマンドの結果で未読の変更通知を受ける（受け入れ条件 6）。

| レーンの状態 | 変更通知を受けるサブコマンド |
| --- | --- |
| 未着手 | `row start` |
| 止まっている | `row resumed` |
| 実行中 | 工程の境の `ndf progress next` と、待ちの `ndf progress wait` |

結果に載せたサブコマンドが、レーンのワークフロー状態に `notice_read` を書く。既読フラグはレーンの所有で、計画のワークフロー状態に書かない。計画のワークフロー状態の書き手は、既存のオーガナイザーと Durable Workflow の 2 つのままにする。

変更通知をファイルに置く形は採らない。計画のワークフロー状態の外に状態が増え、Factory が読む経路も別に要る。

根拠: Value 3 / Value 8 / Value 9（MVV バージョン 7）

### 決定 14: 規模の判定を後から確かめられるよう、判定結果をスプリントのワークフロー状態の作成イベントと Issue の進行の行に残す

`規模:` の行は判定結果の出力に出し、`ndf progress new` の引数 `--scale`・`--scale-reason` で渡す。`ndf progress new` は、作成イベント `created` のコンテキストにキー `scale` として残す。コンテキストのスキーマ `context.schema.json` には任意のキーを足す。Issue の `## 進行` を描く処理が、その値を `モード:` の次の行に出す。手がかりが無くスプリントとした判定も、理由とともに残る（受け入れ条件 7）。

判定の記録だけの新しいファイルを置く形は採らない。判定の記録の保存先がワークフロー状態と別に増える。

根拠: Value 13 / Value 14（MVV バージョン 7）

### 決定 15: Factory の画面の変更を Factory の設計に任せるため、NDF の側はイベントと結果 JSON を公表された言語として出すだけにする

エピックが Factory に現れる所は、設計文書の「Neural Development Factory の画面構成への影響」の表で引き継ぐ。現れる所は、開発計画の一覧・詳細・作る画面、レーンの状況、承認待ちの一覧の通知の列、スプリントの詳細、オーガナイザーの会話である。公表された言語は、計画の設定ファイルのスキーマ・サブコマンドの結果 JSON・ワークフロー状態のイベントの 3 つである。Factory は計画を作るときに、設定ファイルを `ndf lanes init` へ渡す。起動前チェックの指摘は `ndf lanes init`・`start` の結果から、進捗と変更通知はイベントから読む。NDF の集約を直接書かない。NDF の側はイベント 3 つと `status` の結果 JSON のフィールドを足すだけで、Factory 向けの API を足さない。Factory の Issue は起票しない（前提 7）。

根拠: Value 4 / Value 9（MVV バージョン 7）

### 決定 16: アーキテクチャ設計書の決定を後から追えるよう、決定は既存の ADR の形で書き、覆したものは superseded と記して残す

アーキテクチャ設計書の該当時のセクション「ADR」は、設計文書と同じ `### 決定 N: …` の形にする。覆した決定は消さず、見出しに `（置き換え: 決定 M）` を足す。ADR（STD5）の superseded と同じ扱いで、番号を再利用しない。決定 1 件ごとに別のファイルを作る形は採らない（`design` の `decisions.md` の「置き場所」と同じ理由）。

根拠: Value 14（MVV バージョン 7）

### 決定 17: Walking Skeleton を機械で縛らないため、最初のスプリントで作ることをガイドの推奨にとどめる

アーキテクチャ設計書のガイドは、最初のスプリントで Walking Skeleton（端から端まで動くエントリポイントと試験実行の仕組み）を作ることを推奨として書く。#1142 では、試験実行 T2 の 1 回目でエントリポイントのパスの誤りが初めて見つかった。チェックにはしない。何が Walking Skeleton に当たるかはエピックごとに違い、機械が判定できる形が無い（要求の「含まない」）。

根拠: Value 5 / Value 13（MVV バージョン 7）

### 決定 18: 起動前チェックと Durable Workflow が同じアーキテクチャ設計書を読むよう、ベースブランチのリビジョンだけを読み、計画は最初のスプリントのマージの後に起動する

`ndf lanes init`・`start` と計画の Durable Workflow は、どちらもベースブランチ（プロジェクトの設定の値）のアーキテクチャ設計書を読む。手元の worktree のアーキテクチャ設計書は読まない。ベースブランチにアーキテクチャ設計書が無ければ、`ndf lanes init`・`start` は `missing-foundation` で落ちる。このため、並列の計画は、最初のスプリントの Pull Request（アーキテクチャ設計書を載せたもの）がマージされ、アーキテクチャ設計書がベースブランチに入った後（E5 の後）にだけ起動できる。最初のスプリントは並列の計画の外で、単独のスプリントとして走る。

読み手どうしが同じリビジョンを読むよう、次の 2 つも決める。

- **取得する主体と時点**: ベースブランチを `git fetch` で取得し直してから、リモート追跡ブランチの先端のコミットを読む。`ndf lanes init`・`start` はチェックの前に、Durable Workflow は各回の最初に取得する。取得しないと、その Pull Request のマージの直後でも `start` が `missing-foundation` で落ち、Durable Workflow は古いリビジョンを読み続ける
- **完了条件の `command:` を実行する場所**: その回に読んだコミットを `git worktree add --detach` で作業ディレクトリへ切り出し、そこで実行する。判定の後に作業ディレクトリを消す。メインディレクトリのチェックアウトで実行すると、完了の判定だけがベースブランチと別のリビジョンで決まる

手元の worktree のアーキテクチャ設計書をチェックする形は採らない。マージ前のアーキテクチャ設計書でチェックが通る一方、変更通知と完了の判定はベースブランチの別のリビジョンで動く。読み手によってアーキテクチャ設計書が食い違う。最初のスプリントを計画の中のレーンにする形も採らない。計画の起動の時点でベースブランチにアーキテクチャ設計書が無く、チェックが通らない。

根拠: Value 3 / Value 8（MVV バージョン 7）

### 決定 19: 読み手が説明なしで分かるよう、全レーンが先に読む文書を「アーキテクチャ設計書」と呼ぶ

エピックの全レーンが設計と実装の前に読む文書を「エピックのアーキテクチャ設計書」（Architecture Doc）と呼ぶ。arc42（STD1・STD2）はアーキテクチャ文書のテンプレートで、目標・制約・用語・横断の概念・ADR を 1 つの文書に持つ。この文書の必須セクションと同じ範囲であり、エンジニアが語から中身を推せる。Issue ごとの設計文書（`issue-<番号>-design.md`）とは「設計文書」の語で呼び分ける。

ほかの候補は次の理由で採らない。

| 候補 | 採らない理由 |
| --- | --- |
| 設計の前提（Foundation） | 「前提」は要求の「前提」のセクションと同じ語になり、1 語が 2 つの意味を持つ |
| steering（Kiro） | Kiro の steering はリポジトリに常に効く文脈で、エピックの単位で閉じない。読み手が Kiro の振る舞いを思い浮かべる |
| 土台 | 英語の foundation の直訳で、何の文書かが語から分からない（2026-11-15 の利用者の指摘） |

識別子は foundation のまま残す。`foundation.schema.json`・`epic-foundation.md`・`foundation_rev`・`missing-foundation` などがこれに当たる。英語の識別子として意味が通り、名前を変えるとコントラクトの名前が説明文の語に引きずられて揺れる。説明文では「アーキテクチャ設計書」と書き、識別子との対応は設計文書の「構成要素」の表で示す。

根拠: Value 14（MVV バージョン 7）

### 決定 20: NDF を使う汎用の開発へ ai-plugins の事情を持ち込まないため、課題の置き場を設定から読み、`issues:` は GitHub のときだけ書けるようにする

完了条件の確認方法 `issues: #<番号> ...` は、`.ndf/project.json` の `issues.primary` が GitHub のときだけ書ける。ほかの置き場（Redmine など）のリポジトリで `issues:` を書くと、起動前チェックと `ndf epic check --shape-only` が行の番号を出して指摘 `shape` で落とす。`ndf epic check` は `issues.primary` をこの判定にだけ読む（決定 9）。`.ndf/project.json` か `issues.primary` が無いリポジトリでは GitHub でないものとして扱い、課題の置き場を GitHub と決めつけない。ほかの置き場の項目は、置き場の CLI で状態を確かめるコマンドを `command:` に書く。

carmo-system-console の法人リースのエピックは、課題を Redmine に置く（`issues/corporate-lease/README.md`）。GitHub Issues は使わない。GitHub を前提に状態を読むと、このリポジトリでは項目が満たされず、計画が終わらない。

NDF に Redmine などの置き場のアダプタを足して `issues:` で読む形は採らない。置き場ごとの状態の読み方を NDF が持つことになり、置き場の種類だけアダプタが増える。`command:` で置き場の CLI を指せば、同じ判定（終了コード 0 で満たす）で受けられる。

リモートの名前は ndf-next の全体の定数（`ndf.adapters.git` の `ORIGIN`）を読み、この設計だけの設定を足さない。ベースブランチは `.ndf/worktree.json` の `base_branch` を読む（決定 18）。代表のリポジトリ 3 種での振る舞いと、ai-plugins の値を前提にしていた箇所の扱いは、設計文書の「適用範囲」にある。

根拠: Value 4 / Value 11（MVV バージョン 7）

### 決定 21: 実装の Pull Request のたびに変更通知が出ないよう、コントラクトの行の検証方法の列だけが変わった変更は受け入れ条件 6 の「変更」に数えない

受け入れ条件 6 の「アーキテクチャ設計書を変更する」は、コントラクトの表の検証方法の列を除いて比べた結果で判定する。検証方法の列だけが変わった変更では、変更通知（`foundation_noticed`）を書かず、比較元のリビジョンも進めない（設計文書の「変更通知の宛先」の手順 1。テスト設計の受け入れ条件 6・I7 の行）。

実装する Pull Request は、自分が実装した行の検証方法を `—` から書き換える（設計文書の「アーキテクチャ設計書の形」）。検証方法の列も比べに含める形は採らない。実装の Pull Request がマージされるたびに、コントラクトの中身（正本・形）が変わらないまま、触るファイルの重なるレーンへ変更通知が届き、レーンが読み直す必要の無い変更を読み直す。

根拠: Value 2 / Value 3（MVV バージョン 7）
