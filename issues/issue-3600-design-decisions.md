# エピックの土台の設計の決定（#3600）

設計文書 [issue-3600-design.md](issue-3600-design.md) の決定の記録である。番号の `STD`・`PRD`・`LIB` は設計文書の「外部の調査」の表を指す。

## 決定の記録

### 決定 1: 小さな依頼に土台を書かせないため、規模の判定を「1 つの目的が 2 本以上のレーンか 2 つ以上のスプリントに分かれる見込み」で切る

エピックに当たるのは、1 つの目的（1 つの親の課題か 1 つの依頼）の作業が、2 本以上のレーンか 2 つ以上のスプリントに分かれる見込みのときである。独立した課題を並列の計画に並べただけのものは、レーンが複数でもエピックではない。共有する前提が無く、土台に書く中身が無いためである。手がかり（課題の数・依頼に書かれた範囲・既存の親子の課題）が無いときはスプリントとして扱い、理由を判定結果の `規模:` の行に残す。

判定は `development-workflow` の本文に 4 行で置く（判定の 1 行・エピックのときの行き先の 1 行・手がかりが無いときの 1 行・判定結果の出力の例への `規模:` の 1 行）。境界の値と例は土台の参照（`design/references/epic-foundation.md`）が持つ。

「3 本以上のレーン」を境界にする形は採らない。#1142 の手戻りの多くは、2 つの子が同じ契約を別々の形で作ったことから起きており、2 本で既に食い違いが起きる。

根拠: Value 1 / Value 2 / Value 3（MVV 版 7）

### 決定 2: 承認ゲートを足さないため、土台を最初のスプリントの設計 PR に載せ、そのスプリントを `standard` で進める

土台は、エピックの最初のスプリントの設計 PR に、そのスプリントの課題の設計文書と並べて載せる。設計承認ゲートで人が土台を見る。最初のスプリントのモードは、土台が入出力の契約とデータ構造を決めるため `standard` とする。2 つ目以降のスプリントは、土台を読む側として各自のモードで進む。

土台だけの Pull Request を先に出して別に承認を取る形は採らない。承認ゲートの数と置き場は `development-workflow` だけが持ち、ゲートが 1 つ増える。

根拠: Value 1 / Value 5（MVV 版 7）

### 決定 3: NDF の工程と二重にしないため、仕様駆動の既存のツールを取り込まず、全体と機能ごとの 2 層の型だけを倣う

Spec Kit（LIB1）は、constitution をプロジェクトに 1 回・specify から tasks を機能ごとに回す形を持つ。NDF は要求・設計・実装計画・承認ゲートを既に持ち、Spec Kit の工程を入れると同じ工程が 2 つになる。Spec Kit には並列の計画・レーン・CI の照合が無く、この課題の受け入れ条件 2〜6 を満たさない。採るのは、全体の文脈（Kiro の steering・Spec Kit の constitution）と機能ごとの仕様を分ける 2 層の型と、必須の項目がそろうまで実装へ進めない KEP の型（STD4）である。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: LIB1 / PRD1 / PRD2 / STD1 / STD4

根拠: Value 11 / Value 12（MVV 版 7）

### 決定 4: 同じ事実を 2 か所に持たないため、エピックを集約にせず、完了条件の定義を土台に置いて計画は番号で指す

エピックは土台の文書 1 本と、それを指す並列の計画で表す。エピックの状態の表を作らない。完了条件の定義（条件の文と確かめ方）は土台の「完了条件」の表に置き、計画の宣言の `epic.done` は番号（`D1` など）だけを持つ。続く複数の計画が同じエピックを進めても、定義は 1 か所に残る。`done` を省いた計画は土台の完了条件のすべてを満たす計画になる。

完了条件の定義を計画の宣言に書く形は採らない。エピックが複数の計画にまたがると、同じ条件が計画ごとに写され、片方だけ直ると食い違う。要求の対象範囲の「並列の計画の欄（エピックの完了条件）」は、番号の欄として満たす。

根拠: Value 8 / Value 11（MVV 版 7）

### 決定 5: 先に決める範囲を絞るため、必須の節を 9 つ、該当時の節を 3 つにし、節の一覧の正本を土台の契約 1 か所に置く

必須の節は、変えると高くつく・元に戻せない・他のレーンと形が食い違うものに当たる 9 つ（目標と非目標・完了条件・用語・境界と責務・データ構造と状態の置き場・入出力の契約・設定と環境変数・テストと検証の基盤・未決の問い）である。横断の関心事・移行・決定の記録は該当時にする。arc42 の横断の概念（STD1）は必要な話題だけを選ぶよう求め、Google の design doc（STD3）は目標と非目標・横断の関心事を、Twelve-Factor（STD6）は設定の分離を求める。

節の名前と表の列は `contracts/epic/foundation.schema.json` に置き、テンプレート（`ndf epic init`）・検査（`ndf epic check`）・参照の表がそこから読む。参照の表は手で写さず、ndf-next の規約の生成（`ndf check --write-spec`）で描く。

すべての節を必須にする形は採らない。小さなエピックでも横断の関心事と移行を書かせると、空の節を「無し」で埋める作業だけが増える（PRD3 の指摘）。

根拠: Value 3 / Value 11 / Value 12（MVV 版 7）

### 決定 6: テンプレートのまま起動されないため、空の節を「HTML のコメントと空行のほかの行が無い節」と定める

テンプレートは節ごとの書き方の手引きを HTML のコメントで置く。埋めずに残した節は、見出しとコメントだけになり、空と判定される。「無し」の 1 行は中身として数える。未決の問いが無いときなど、書き手が確かめて無いと書いた節を空と区別するためである。

文字数の閾値で空を決める形は採らない。閾値は書き手が短い文で満たせ、書き手の確かめたかを表さない。

根拠: Value 3 / Value 13（MVV 版 7）

### 決定 7: 言語を問わず照合できるよう、契約の行の照合を `exists:`・`schema:`・`generated:` の 3 つの指定にし、実装前の行を `—` で置く

照合の指定は 3 つである。`exists: <glob>` は契約の名前（環境変数の名前・副命令の名前など）が glob に当たるファイルに文字どおり現れるかを見る。`schema: <glob>` は glob に当たるファイルが正本のスキーマ（JSON Schema）に通るかを jsonschema（LIB2）で見る。`generated: <コマンド>` はコマンドの出力が正本と 1 字も違わないかを見る。最後の形は ndf-next の #3518 の生成と照合（`ndf check` の規則 spec-docs）と同じ考えで、利用者のリポジトリが自分の生成のコマンドを指せる。土台の表の解析は markdown-it-py（LIB3）で行う。

実装の前の契約は照合の指定を `—` にし、照合しない。検査は `—` の行の数を警告として出す。実装する Pull Request が同じ差分で指定を書き込む。

言語ごとの解析器（構文木から環境変数の読みを集める）を NDF に持たせる形は採らない。利用者のリポジトリの言語は限らず（Value 4）、ndf-next の自分の検査（spec-io）は Python だけに当たる。

- 作り方: 自前で作る・ライブラリやサービスを使う
- 比べた候補: LIB1 / LIB2 / LIB3

根拠: Value 4 / Value 12（MVV 版 7）

### 決定 8: 実装が無い時点で起動を止めないため、起動の前の検査は節と表の形だけにし、照合は CI に任せる

`ndf lanes init`・`start` は土台を `ndf epic check --shape-only` で検査する。必須の節・表の列の形・計画の完了条件の番号を見て、照合を行わない。照合（受け入れ条件 3）は Pull Request ごとの CI で `ndf epic check` を打つ。エピックの始めには契約を実装する差分がまだ無く、起動の前に照合すると起動できない。

このリポジトリでは `.github/workflows/ndf-next-checks.yml` に 1 手順を足す。利用者のリポジトリの CI は NDF が書き換えず、土台の必須の節「テストと検証の基盤」に CI の手順を名指して書かせ、最初のスプリントで足す。

根拠: Value 4 / Value 13（MVV 版 7）

### 決定 9: 計画の副命令と責務を分けるため、土台の副命令を `ndf epic` として新設する

テンプレートの生成と照合は、並列の計画が無くても使う（CI は計画を読まない）。計画の副命令 `ndf lanes` に入れると、`lanes init`（計画の進行表を作る）と土台の `init` の意味が重なる。`ndf epic` は Skill ではなく副命令で、配る Skill の表（受け入れ条件 9）は変わらない。副命令の一覧（`docs/contracts/commands.md`）は生成で描かれる。

`ndf lanes epic-init` のように計画の副命令の下へ置く形は採らない。CI が計画の副命令を呼ぶ形になり、計画の無いリポジトリで使えない。

根拠: Value 9（MVV 版 7）

### 決定 10: 利用者の設定を書き換えずに土台を見つけるため、土台の置き場を決めず、文書の先頭の印で見つける

NDF は土台の置き場を既定で持たない。土台はリポジトリのどこに置いてもよい。テンプレートは先頭に印 `<!-- ndf: epic-foundation -->` を置き、`ndf epic check` は引数が無いとき、追跡しているファイルのうち印を持つ Markdown をすべて検査する。並列の計画は `epic.foundation` でパスを持つ。参照は置き場の例として `docs/epics/<エピックの名前>.md` を挙げる。

`.ndf/` に土台の一覧の宣言を足す形は採らない。エピックを始めるたびに利用者の設定を書き換えることになり、共通原則の C7 に当たる操作が工程の中に増える。

根拠: Value 4 / Value 6（MVV 版 7）

### 決定 11: 計画の状態の値を増やさないため、完了条件が残る間を状態にせず、依頼を 1 件開いてオーガナイザーへ戻す

全レーンの行が終わり、答えていない依頼が無く、完了条件が残るとき、計画は実行中のまま止まる。耐久ワークフローは依頼を 1 件開き（理由は残りの完了条件の番号）、完了条件を上限の宣言の間隔で判定し直す。オーガナイザーはレーンか行を足すか、依頼を閉じて条件の成立を待つ。完了の判定（I16）は、計画にエピックの欄があるときだけ完了条件を足して見る。

状態の値「完了条件待ち」を計画の進行表に足す形は採らない。状態の値と遷移の表（`progress.json`）が変わり、Factory を含む読み手すべてに新しい値の扱いが要る。行と事象から出せる値は持たない（ndf-next のレーンの状態と同じ扱い）。

根拠: Value 1 / Value 8（MVV 版 7）

### 決定 12: 判定の結果を追跡できるよう、完了条件の判定を値が変わったときだけ事象として追記する

耐久ワークフローは完了条件を判定し、前の記録と値が違うときだけ `done_checked` を書く。`status` は最後の記録を読むだけで、判定のコマンドを打たない。`status` は人と Factory が何度も読み、そのたびに `command:` の確かめ方を走らせると費用と時間がかさむ。判定の記録が無い条件は未判定と出す。

`status` のたびに判定する形は採らない。上の費用に加え、同じ時点の 2 つの読み手が違う値を見る。

根拠: Value 2 / Value 8（MVV 版 7）

### 決定 13: 重ならないレーンを止めないため、土台の知らせの宛先を触る場所の重なりで選び、未読を読んだ印で管理する

耐久ワークフローは、ベースブランチの土台の内容が前の知らせから変わったら、違う節の触る場所を集め、既存の `touch_hit` で重なるレーンへ `foundation_noticed` を 1 件書く。表の無い節で `触る場所:` の行も無いもの（用語・目標と非目標など）は、全レーンに効くとして `**` を当てる。レーンの conductor は `row start`・`row resumed` の出力で未読の知らせを受け、`notice_read` を書く。実行中のレーンは次の待ちと工程の境で読み、止まっているレーンは再開のときに読む（受け入れ条件 6）。

知らせをファイルに置く形は採らない。計画の進行表の外に状態が増え、Factory が読む経路も別に要る。

根拠: Value 3 / Value 8 / Value 9（MVV 版 7）

### 決定 14: 規模の判定を後から確かめられるよう、判定結果をスプリントの進行表の作成の事象と課題の進行の行に残す

`規模:` の行は判定結果の出力に出し、`ndf progress new` がスプリントの進行表を作るときに作成の事象の値として残す。課題の `## 進行` には `モード:` の次の行に出す。手がかりが無くスプリントとした判定も、理由とともに残る（受け入れ条件 7）。

判定の記録だけの新しいファイルを置く形は採らない。判定の記録の置き場が進行表と別に増える。

根拠: Value 13 / Value 14（MVV 版 7）

### 決定 15: Factory の画面の変更を Factory の設計に委ねるため、NDF の側は事象と結果 JSON を公開された言語として出すだけにする

エピックが Factory に現れる所（開発計画の一覧・詳細・作る画面、レーンの状況、承認待ちの一覧の知らせの欄、スプリントの詳細、オーガナイザーの会話）は、設計文書の「Neural Development Factory の画面構成への影響」の表に申し送る。NDF の側は計画の進行表の事象 3 つと `status` の結果 JSON の欄を足すだけで、Factory 向けの API を足さない。Factory の課題は起票しない（前提 7）。

根拠: Value 4 / Value 9（MVV 版 7）

### 決定 16: 土台の決定を後から追えるよう、決定は既存の「決定の記録」の形で書き、覆したものは置き換えの印を付けて残す

土台の該当時の節「決定の記録」は、設計文書と同じ `### 決定 N: …` の形にする。覆した決定は消さず、見出しに `（置き換え: 決定 M）` を足す。ADR（STD5）の superseded と同じ扱いで、番号を再利用しない。決定 1 件ごとに別のファイルを作る形は採らない（`design` の `decisions.md` の「置き場所」と同じ理由）。

根拠: Value 14（MVV 版 7）

### 決定 17: ウォーキングスケルトンを機械で縛らないため、最初のスプリントで作ることを参照の推奨にとどめる

土台の参照は、最初のスプリントで端から端まで動くスケルトン（エントリポイントと試走の仕組み）を作ることを推奨として書く。#1142 では、試走 T2 の 1 回目でエントリポイントのパスの誤りが初めて見つかった。検査にはしない。何がスケルトンに当たるかはエピックごとに違い、機械が判定できる形が無い（要求の「含まない」）。

根拠: Value 5 / Value 13（MVV 版 7）
