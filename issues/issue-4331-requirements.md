## 何が起きたか

2026-11-24 に、`ndf check` の規則 `budget` がテストの関数の件数に上限を置く仕組み（PR [#4324](https://github.com/devbasex/ai-plugins/pull/4324)、課題 [#3687](https://github.com/devbasex/ai-plugins/issues/3687)）の説明を受けた利用者が、「tests は数よりも CI でのテストの実行時間を気にしたいけど、測れる？」と尋ねた。

利用者が気にしているのは、テストの件数ではなく、CI でテストにかかる時間である。件数の上限は機能を足すたびに上げ直しになり（起票の時点で 4,400 → 4,650、2026-11-24 の `main` では 6,000）、遅いテストも見つけられない。

## 種類

機能追加（件数の上限を調べる規則 `budget` と CI のテストのジョブは今もある。テストの実行時間を測って知らせることは、どの SSOT にも約束が無く、新たに足す約束である）

## 今の姿

テストと CI の予算（設定 `budget`）は、テストの関数・CI のジョブ・使われない依存・置き換えられる自作の件数に上限を置く。`ndf check` の規則 `budget` は、上限を超えた Pull Request を落とす。テストの上限は `.ndf/project.json` の `budget.tests`（2026-11-24 の `main` で 6,000）である。仕様は [docs/specifications/ndf-split-tables-toolchain-and-budget.md](https://github.com/devbasex/ai-plugins/blob/main/docs/specifications/ndf-split-tables-toolchain-and-budget.md) にあり、同じ仕様が「CI でのテストの実行時間の計測（#4331）」を範囲の外に置いている。

CI のテストは、ワークフロー `Python tests`（[.github/workflows/pytest.yml](https://github.com/devbasex/ai-plugins/blob/main/.github/workflows/pytest.yml)）が 6 つのジョブに分けて流す。1 つのジョブの中で、根のテストと NDF のテスト（`plugins/ndf`）を続けて流す。

2026-11-24 に測った所要は次のとおりである。

- ワークフロー `Python tests` の所要（GitHub API の時刻の差）は、直近に成功した 60 回で中央値 157 秒・最小 36 秒・最大 583 秒だった。文書だけの差分でテストを省いた実行も混ざり、待ち行列と起動の時間も含む
- 1 回の実行（run 45280461372）では、6 ジョブの所要の合計が 452 秒、最も長いジョブが 97 秒だった

| 内訳（6 ジョブの合計） | 秒 |
| --- | ---: |
| NDF のテスト | 160 |
| 根のテスト | 114 |
| NDF のテストを流すファイルを決める手順（`--collect-only` を 6 ジョブがそれぞれ打つ） | 88 |
| 準備とクリーンアップ | 約 90 |

根のテストと NDF のテストでは、所要の残り方とジョブへの分け方が違う。

| | 根のテスト | NDF のテスト |
| --- | --- | --- |
| 1 件ごとの所要 | JUnit XML を成果物に残すので読める（1,725 件・合計 136 秒。最も遅いもので 3.8 秒） | JUnit XML を書かないので読めない |
| ジョブへの分け方 | ファイルごとの実測秒（[scripts/pytest-shard-seconds.json](https://github.com/devbasex/ai-plugins/blob/main/scripts/pytest-shard-seconds.json)）で分ける | ファイルごとのテストの数で分ける。実測秒のファイルのパスはリポジトリの根から見たもので、NDF のテストの名前と合わないためである（[scripts/pytest_shard.py](https://github.com/devbasex/ai-plugins/blob/main/scripts/pytest_shard.py) の説明） |
| ジョブごとの所要 | — | 15〜43 秒と偏る |

## 何を足すか・変えるか

| | 今 | 足した後 |
| --- | --- | --- |
| NDF のテストの 1 件ごとの所要 | 残らない | `main` の CI の 1 回ごとに残る |
| テストの所要を読む方法 | GitHub の画面か成果物を 1 つずつ開く | コマンド 1 つで、合計・遅い順の上位・ジョブごとの所要が読める |
| 所要が増えたことの知らせ | 無い | `main` の直近の複数回の中央値が上限を超えると分かる |
| 件数の上限 `budget.tests` | 上限を超えると Pull Request を落とす | 無くすか残すかを設計で決め、決めた形に設定とコードがそろう |
| NDF のテストのジョブへの分け方 | ファイルごとのテストの数 | ファイルごとの実測秒 |
| NDF のテストを流すファイルを決める手順 | 6 ジョブがそれぞれ全件を集める（合計 88 秒） | 重なりが減る |

## 今の利用者への影響と互換

NDF を導入した利用者のリポジトリで `.ndf/project.json` に `budget.tests` を書いている場合、上限を無くすと、規則 `budget` はテストの件数で Pull Request を落とさなくなる。ほかの 3 つの件数（CI のジョブ・使われない依存・置き換えられる自作）の上限は変わらない。

## なぜ困るか

- 件数の上限は、機能を足すたびに上げ直しになる。上げ直しのたびに作業と Pull Request が増える
- 件数を見ても、遅いテストを見つけられない。テストが遅くなれば、すべての Pull Request の CI の待ちと費用が増える
- NDF のテストは 1 件ごとの所要が残らないので、どのテストが遅いかを後から調べられない
- NDF のテストはテストの数で分けているので、ジョブの所要が 15〜43 秒と偏る。最も遅いジョブが CI 全体の待ちを決める

## 目的

CI でのテストの実行時間を `main` の CI の 1 回ごとに測って残し、増え方が見えるようにする。テストの量の目安を、件数でなく実行時間にする。

## 対象範囲

含む:
- NDF のテストの 1 件ごとの所要を CI で残すこと
- 根と NDF のテストの所要の合計・遅い順の上位・ジョブごとの所要を、コマンド 1 つで読めるようにすること
- `main` の直近の複数回の中央値が上限を超えたことを知らせること
- 件数の上限 `budget.tests` を無くすか残すかの決定と、決めた形に設定・コード・確定仕様をそろえること
- NDF のテストを流すファイルを決める手順の重なりを減らすこと
- NDF のテストを実測の秒でジョブに分けること

含まない:
- CI のジョブの数の上限（`budget.ci_jobs`）
- 使われない依存と、ライブラリへ置き換えられる自作の上限（別の課題）
- 1 件ずつのテストを速くする改修（遅いテストが見えるようになった後に、別の課題で扱う）

## 前提

- 前提 1: 中央値を求めるときは、テストが最後まで流れて成功した回だけを数える。失敗した回・取り消された回・文書だけの差分でテストを省いた回は数えない
- 前提 2: 所要の記録は、GitHub Actions の成果物の保存期間の内で読めればよい。保存期間を過ぎた回は、中央値の材料から外れてよい

## 受け入れ条件

- [ ] 1. `main` の CI の 1 回ごとに、根のテストと NDF のテストの両方について、テスト 1 件ごとの所要が成果物に残る
- [ ] 2. 1 つの実行を指してコマンドを 1 つ打つと、その回のテストの所要の合計・遅い順の上位・ジョブごとの所要が、根と NDF の両方について出る
- [ ] 3. 所要の記録が無い実行（記録を残す前の回・保存期間を過ぎた回）を指すと、記録が無いことを示して 0 以外で終わる
- [ ] 4. `main` の直近の複数回の中央値が設定した上限を超えたとき、超えたことと超えた量が分かる
- [ ] 5. `main` の直近の複数回の中央値が上限以下のときは、超えたという知らせが出ない
- [ ] 6. 1 回の実行の所要が上限を超えても、Pull Request の CI はそれを理由に落ちない
- [ ] 7. 件数の上限 `budget.tests` を無くすか残すかが決まり、`.ndf/project.json`・規則 `budget` のコード・確定仕様（[ndf-split-tables-toolchain-and-budget.md](https://github.com/devbasex/ai-plugins/blob/main/docs/specifications/ndf-split-tables-toolchain-and-budget.md)）が同じ決定になっている
- [ ] 8. NDF のテストが、ファイルごとの実測の秒でジョブに分けられている
- [ ] 9. NDF のテストを流すファイルを決める手順の秒（6 ジョブの合計）が変更前の 88 秒より減り、変更の前と後の CI の秒（6 ジョブの合計と、最も長いジョブ）が Pull Request に示されている
- [ ] 10. 分け方を変えた後も、根と NDF のテストのどのファイルも、ちょうど 1 つのジョブで流れる（退行しない）
      前提の確認: `printf 'tests/a.py::t1\ntests/a.py::t2\ntests/b.py::t1\ntests/c.py::t1\n' | python3 scripts/pytest_shard.py files --total 2 --index 0` → `tests/a.py`、`--index 1` → `tests/b.py` と `tests/c.py`（2026-11-24 の `main`）
- [ ] 11. 分け方を変えた後も、NDF のテストの ok の出力の確かめ（ジョブ `pytest (NDF の ok の出力)`）が、今と同じく 6 ジョブの記録を合わせて合否を決める（退行しない）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 所要を残す仕組みを足した後も、`Python tests` の 6 ジョブの所要の合計が変更前より増えない（受け入れ条件 9 の前と後の秒で示す） |
| 運用・保守性 | 中央値の上限は設定ファイルの 1 か所に置き、上限を変えるのにコードの変更が要らない |

| 対象 | 影響 |
| --- | --- |

> - どこで落とすか。GitHub の実行機の速さで秒はぶれるので、1 回の秒で PR を落とすと、コードと無関係に落ちる。PR では表示だけにし、`main` の直近の複数回の中央値が上限を超えたら知らせる形を第一の案とする
>
> ## 受け入れ条件（案）
>
> - [ ] `main` の CI の 1 回ごとに、根と NDF の両方のテストの所要の合計・遅い順の上位・ジョブごとの所要が残り、コマンド 1 つで読める
> - [ ] `main` の直近の複数回の中央値が、設定した上限を超えたことが分かる（1 回の秒では PR を落とさない）
> - [ ] 件数の上限 `budget.tests` を無くすか残すかが決まり、`.ndf/project.json` とコードがそろっている
> - [ ] NDF のテストの割り当てが実測の秒で分けられ、収集の重複が減った結果が前後の秒で示されている
>
> ## 影響
>
> テストが遅くなれば、すべての PR の CI の待ちと費用が増える。
>
> ## 起票者の推定
>
> - 1 回の秒で PR を落とさず、複数回の中央値で見る（推した出所: 実行機のぶれと、利用者の過去の方針「合否がスペック次第の負荷試験を流さない」#3423）
> - 収集の重複と割り当ての偏りの改善を含める（推した出所: 上の実測）
>
