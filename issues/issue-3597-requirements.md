## 期待する結果

- 本番のプランが承認ゲートで終わったら、一時レーンはリリース承認ゲートの依頼を送るか、送らない理由を残して止まる。黙って止まらない
- 起き直した一時レーンは、前の起動の依頼に台帳の答えがあれば、それを使う。同じ問いを新しい id で送り直さない
- 一時レーンの起動が、前の一時レーンが動いていることによる `limit` で断られたら、前の一時レーンが止まるのを待って起動し直す。人へ問わない

## 前提

- 前提 1: 直す先は今の NDF（`plugins/ndf/`）である。ndf-next（`plugins/ndf-next/`）は変えず、同じ決まりを ndf-next のリリースのドメインへ移す要否だけを設計の決定の記録に書く（オーガナイザーの指示）
- 前提 2: 確定の後に本番のプランが承認ゲートで止まったときは、既存のリリース承認ゲートの依頼の形で人へ戻す。新しい承認ゲートを足さない。#3572 の設計（設計 PR https://github.com/devbasex/ai-plugins/pull/3596 の `issues/issue-3572-design-decisions.md` の決定 3）は、承認の後に止まった本番の PR の次の手を、止まった理由から機械的に決まる打ち直し（`rerun`。オーガナイザーか一時レーンが打ってよい）と、直しを入れた新しい先端で承認を取り直す差し戻し（`reject`）の 2 つに分け、承認ゲートを新しく足さない。この課題もこの 2 つの分け方に合わせる。依頼の選択肢の名前と並び、打ち直しを人へ問わずに打てる止まった理由の範囲は設計で決める
- 前提 3: 「同じ問い」は、同じ並列の計画の同じ一時レーンの名前（`<計画名>-rel<連番>` か `<計画名>-rel<k>v`）が送った問いのうち、問いの区分（`metadata.source`）と操作の対象（ブランチ名と、そのブランチの先端のコミット、または課題・PR の番号）が同じものとする。言い回しの違いは同じかどうかに使わない。対象が動いた（先端のコミットが変わった）問いは別の問いである。対象をどの値で表すか（問いのどの欄から読むか）は設計で決める
- 前提 4: 前の一時レーンが止まるのを待つ上限は、今の立ち上がりの確かめの上限（120 秒、`NDF_PARALLEL_LAUNCH_SECONDS`）とは別に置き、その値は設計で決める。上限を過ぎても前の一時レーンが動いていれば、今と同じく区分 `spawn` の問いを立てる
- 前提 5: 台帳（`ledger.jsonl`）の行は追記だけで持ち、今の値は最新の行から引く（Value 8）。送ったかどうか・答えがあるかどうかは台帳から判定する
- 前提 6: リリース 17 の承認ゲートの引き金（プランを組んだ版の宣言 `cd-review` と今の宣言 `cd-admin` の食い違い）は、承認ゲートで止まる理由の 1 つとして扱い、この課題では食い違いそのものを直さない（「含まない」）

## 対象範囲

含む:
- 確定（`phase: confirmed`）の後に本番のプランが承認ゲートで終わったときの一時レーンの道（依頼を送る・送らない理由を残す）と、その依頼の id が提示 1 の依頼の id と重ならないこと
- `parallel.py request-gate2` などの依頼を送るコマンドが、台帳に書かなかった（同じキーの行が既にあった）ときに「送った」と返さないこと
- 起き直した一時レーンが、自分の名前の前の起動の依頼と台帳の答えを読み、同じ問い（前提 3）の答えを使うこと
- 耐久ワークフローの一時レーンの起動が、前の一時レーンが動いていることによる `limit` で断られたときに、前の一時レーンが止まるのを待って打ち直すこと
- 手順書（`references/parallel.md` の一時レーンと「起動と再起動」、`references/asking.md` の一時レーンの答えの読み方）を上の振る舞いに合わせること
- ndf-next へ同じ決まりを移す要否を、設計の決定の記録に書くこと

含まない:
- ndf-next（`plugins/ndf-next/`）の変更（前提 1）
- 本番のプランを組んだ版の宣言と今の宣言の食い違い（`cd-review` / `cd-admin`）を直すこと（前提 6。#3506 の範囲か別の課題かは「未決」）
- #3175（承認を送った後に約 6 時間進まない）と #2629（起き直すたびに「途中で止まった」を問う）の原因
- 役割 `helper` の同時数の上限（1 本）と、全体の上限（`NDF_RELAY_MAX_NAMED`）の値の変更
- 計画のレーン（一時レーンでないレーン）の起動と再起動の打ち直しの規則
- 時間で区切った負荷試験

      結果: 送らない理由が、耐久ワークフローの読む記録（台帳か、`settle` と同じ置き場）に残り、区分 `helper`（「途中で止まった」）の問いが立たない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | 前の一時レーンを待つ間も、耐久ワークフローは他のレーンの観測と答えの処理を止めない（待ちはループの 1 回をまたいで持ち、ループの 1 回の中で眠らない） |
| 運用・保守性 | 送らなかった依頼・答えを引き継いだ問い・待ってから打ち直した起動が、それぞれ台帳か起動の記録に、依頼の id・対象・理由と一緒に残り、後から読める |
| セキュリティ | 戻せない操作（`-D` の削除。共通原則 C4）の答えは、同じ一時レーンの名前・同じ対象（同じ先端）の問いにだけ当て、対象が動いたら人に確かめ直す（受け入れ条件 5・6・8） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`parallel.py request-gate2`（と依頼を台帳へ書くコマンド）の、同じキーの行があったときの終了コードと結果 JSON、`parallel.py helper` の結果に確定の後の承認ゲートの行が足される。互換の経路の要否は設計で決める |
| データ | 台帳の行の種類か欄が足される見込み（確定の後の依頼・送らなかった理由・答えの引き継ぎ）。既存の行は書き換えない（追記だけ） |
| 既存の振る舞い | 確定の後の承認ゲートで一時レーンが黙って止まらない。起き直した一時レーンが同じ問いを送り直さない。一時レーンの起動が前の一時レーンを待つ |
