# #2660: worktree を消した後もテスト環境の割り当てとコンテナが残り、スロットを占め続ける

正は課題の本文（#2660）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

worktree を消した後も、その worktree のテスト環境の割り当てが worktree レジストリに未解放のまま残り、コンテナも動き続ける。carul の worktree レジストリは 44 行のうち 40 行が未解放で、そのうち worktree のディレクトリが今もあるのは 10 行だけである（2026-11-06、`/work/carul/.git/ndf/worktree-registry.json` を読んで `released_at` と `os.path.isdir` で数えた）。残り 30 行はスロットを占めたままで、上限 64 のうち空きは 24 である。

## どこで見つけたか

#2567 の設計の工程で、carul の worktree レジストリと `docker ps` を突き合わせた。

## なぜこの変更の範囲外なのか

#2567 の受け入れ条件 14 は、これから `/ndf:merged` の後片付けで消す worktree のテスト環境を破棄する。すでに消えた worktree の行と、そのコンテナを片付けることは受け入れ条件に含まれない。worktree が無いと、`worktree-testenv.sh down` は compose の定義を読めず破棄できないため、別の手段が要る。根拠: Value 1（MVV 版 6）

## 直さないと何が起きるか

#2567 でテスト環境を自動で起こすようになると、スロットの消費が早まる。空きが無くなると、テストのステップが「空きスロットがありません」で止まる。残ったコンテナはメモリとディスクを使い続ける（`worktree/references/test-execution.md` の実測ではテスト環境 1 つあたり約 753 MiB のメモリと約 400 MB のデータ領域）。

## 目的

worktree が消えた後のテスト環境の割り当てとコンテナが、人の操作なしに回収される状態にする。テスト環境のスロットの空きが残った割り当てで減らず、開発ループのテストのステップが「空きスロットがありません」で止まらず、消えた worktree のコンテナがメモリとディスクを使い続けない。

## 前提

- 前提 1: 残った割り当ての破棄は、compose のプロジェクト名（行の環境名）だけで行い、compose の定義を読まない。Docker Compose v5.6.1 で実測した。これより古い版では確かめていない
- 前提 2: 残った割り当てが新しくできる経路は、破棄の失敗（`down` の失敗か上限の超過で、worktree を外して割り当てを残す。#2567 で決めた形）と、後片付けを通らない worktree の削除である。経路ごとに破棄を足さず、残った割り当てを見つけて回収する
- 前提 3: テスト環境のコンテナとボリュームは、worktree が無ければ使われない。compose の定義が worktree をバインドマウントする形のためである。作り直せないデータを持つプロジェクトは `testenv.discard_volumes` に `false` を宣言して残す（#2567 の前提 4）
- 前提 4: worktree レジストリを持つリポジトリの worktree は、回収を走らせる位置から同じパスで見える。見えない位置から打つと生きた行も回収の対象に入る。これはこの課題では防がない（残りリスクは「未決」の表）

## 対象範囲

含む:

- worktree のディレクトリが無い未解放の割り当ての回収（コンテナ・ネットワーク・宣言に従ったボリュームの破棄と、解放の時刻の記録）
- 回収を 1 度で走らせるサブコマンド（`worktree-testenv.sh reclaim`）
- `/ndf:merged` の後片付けからの自動の回収
- テスト環境のスロットが尽きたときの回収の 1 回の試行
- テスト環境の手順書の「後片付け」の更新

含まない:

- worktree を外す経路ごとに破棄の呼び出しを足すこと（前提 2）
- 使われていないテスト環境を定期的に止める処理（`reap` の呼び出し）。#2567 の非対象のままとする
- テスト環境のスロットの上限 64 の変更
- worktree レジストリに行の無いコンテナの片付け。テスト環境の形の名前では 0 件である（「調べて分かったこと」）。行の無いコンテナには、worktree のディレクトリ名をプロジェクト名にしたもの（`issue-21-l20261104-cust-10` の 4 個、`rf247/codex`・`rf242/codex` の 4 個）がある。同じ条件（作業ディレクトリのラベルのパスが見えない）に開発コンテナ 16 個が当たるため、ラベルのパスの有無では判定できない
- worktree が消えた後に公開を閉じる手段
- 導入先のリポジトリの宣言の変更

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | テスト環境の割り当ての持ち主は `worktree-testenv.sh` である。後片付けは `merged-steps.py` から呼ぶだけとし、判定を複製しない（MVV Value 7） |
| コーディング規約 | `AGENTS.md` の「最小限のコード実装」。`.md` の文言を照合するテストを書かない |
| テスト戦略 | 判定と回収は一時のリポジトリと偽の実行系で単体テストにする。実物の Docker の振る舞いは手動確認で見る |

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | 既存テストの実行、手順書の「後片付け」の更新 |

| 行わない | 定義に無いコンテナを削除する指定（`--remove-orphans`）。名前のパターンでのコンテナの検索。行の無いコンテナの破棄。導入先のリポジトリの変更 |
