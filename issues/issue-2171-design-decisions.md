# #2171 の設計の決定の記録

[設計文書](issue-2171-design.md) から分けた決定の記録である。形の詳細は [issue-2171-design-contracts.md](issue-2171-design-contracts.md) にある。

## 決定の記録

### 決定 1: 定義の正を 1 か所にするため、`factory/contracts/` を workspace にし、JSON Schema を正として OpenAPI はそれを指すだけにする

実行ジョブの指示は HTTP の経路でなく環境変数で渡すため、OpenAPI の中に置くと経路の無い定義を OpenAPI に持ち込むことになる。事象と指示を JSON Schema（2020-12）のファイルに置き、受け口の OpenAPI は要求の本文を `$ref` で指せば、同じ形を 2 か所に書かない。Spectral 6.17.0 は外部のファイルへの `$ref` を辿り、名前を壊すと `invalid-ref` で落ちることを実測した。`contracts/` を npm の workspace（`@ndf-factory/contracts`）にすれば、`api`・後の `runner`・`web` が名前で import でき、`check` を根の `npm run check` に足すだけで CI に入る（factory/README.md の「パッケージの管理」の規則どおり）。

OpenAPI の `components.schemas` を正にする形は、環境変数の指示を経路の無い部品として置くことになり、#2189 の受け取りの応答とも位置がずれる。`api` の中に定義を置く形は、ランナー（#2186）が `api` の workspace ごと依存することになる。

根拠: Value 6 / Value 7（MVV 版 3）

### 決定 2: 定義と型のずれを検査で落とすため、型を `json-schema-to-typescript` で生成してコミットし、`check` で作り直して比べる

生成した型をコミットすれば、レビューで型の差分が読め、`api` の `tsc --noEmit` は生成の手順を待たずに通る。`check -w contracts` のテストが同じ設定で作り直した文字列とコミットしたファイルを比べ、違えば `npm run generate -w contracts` を案内して落ちる。これで「定義を変えて型を作り直さないと落ちる」（受け入れ条件 3）が成り立つ。`json-schema-to-typescript` 16.0.0 は `$defs` と `oneOf` から `type` の値で分かれる共用の型を出すことを実測した。

検査の中で毎回作り直してコミットしない形は、作り直した型が常に定義と一致するため、ずれを落とす機会そのものが無くなり、受け入れ条件 3 を満たせない。`openapi-typescript` は OpenAPI からしか作れず、環境変数の指示の定義を OpenAPI へ入れることになる（決定 1）。型を正にして定義を生成する形（zod などから JSON Schema を出す）は、確定仕様が求める「機械可読な定義を置き、型をそこから生成する」の向きと逆になる。

根拠: Value 3 / Value 4（MVV 版 3）

### 決定 3: 型と検査が同じ定義から決まるよう、受け口の実行時の検査を `ajv` の 2020-12 版で同じ JSON Schema から作る

手で書いた検査は、定義を変えたときに直し忘れても型の検査で落ちない。`ajv`（8.20.0、`ajv/dist/2020`）と `ajv-formats` で定義のファイルをそのまま読み、`unevaluatedProperties`・`if`/`then`・`date-time` が効くことを実測した。検査の関数は起動のたびに 1 回だけ作る。

zod などで検査を書き直す形は、定義が 2 つになる。生成した型だけで済ませる形は、実行時に余分な鍵・知らない種類を落とせない（受け入れ条件 11）。

根拠: Value 6（MVV 版 3）

### 決定 4: 認証の手段を経路から一意に決めるため、出所ごとに経路を 3 つに分け、経路の出所と事象の `source` を照らす

`api` の出所は API Gateway の IAM 認可（SigV4）を要るが、IAM 認可は経路ごとの設定で、`runner` の Bearer の token と GitHub の署名とは同じ経路に同居できない。経路を `POST /ingest/events`（`runner`）・`POST /ingest/api/events`（`api`）・`POST /ingest/github`（`github`）に分ければ、経路が認証の手段を 1 つに決め、本文の `source` が経路と違うものを 403 で落とせる（I25）。3 つの経路は 1 つの Lambda の handler（`handlers/ingest.ts`）が受ける。画面向けの `createApiApp` は全経路に Cognito の token を要るため、そこに足さない。

1 つの経路で `source` を見て認証を切り替える形は、本文を読む前に認証の手段が決まらず、`api` の IAM 認可を API Gateway に置けない。

根拠: C2 / Value 6（MVV 版 3）

### 決定 5: 確かめる側が token を作れないよう、実行ジョブの token を EdDSA（Ed25519）の JWT にし、確かめる側は公開鍵の集合だけを読む

token を確かめるのは受け口と #2173 の 2 つで、作るのは #2186 だけである。共有の秘密（HS256）にすると、確かめる側が漏れれば任意のスプリントの実行へ書ける token を作れる。鍵の組にすれば、受け口と #2173 は公開鍵の集合（`RUN_JOB_TOKEN_VERIFY_KEYS_SECRET_ARN`）だけを読み、発行の鍵は #2186 だけが読む。`kid` で鍵を選ぶため、集合に新しい公開鍵を足してから発行の鍵を替えれば止めずに差し替えられ、集合に無い `kid` は「知らない鍵」として落ちる。`jose` はすでに `api` の依存にあり、4 つの「無効」が別々の `code` で取れることを実測した。発行の形（`signRunJobToken`）もこの課題が持ち、#2186 は期限と鍵の読み出しだけを決める。形を書く場所を 1 つにするためである。

ランダムな値を表に置いて照らす不透明な token は、期限より前の取り消しができる利点があるが、表の持ち主（#2186 の実行ジョブの状態）を受け口が読むことになり、前提 3 が範囲の外とした取り消しを持ち込む。RS256 は鍵と署名が長く、Ed25519 で足りる。

根拠: C1 / C2 / Value 6（MVV 版 3）

### 決定 6: 重複の拒否を確定仕様どおり 1 回のトランザクションにし、並びの鍵の時刻をミリ秒の 3 桁にそろえる

冪等の鍵の表への `attribute_not_exists` つきの `Put` と、事象の表への `attribute_not_exists(order_key)` つきの `Put` を 1 回の `TransactWrite` に入れる。取り消しの理由の 1 つ目が `ConditionalCheckFailed` なら重複として 202 を返し、ほかの理由（`TransactionConflict` など）は 503 にして送り手の送り直しに任せる。同時の 2 本はどちらかが取り消され、送り直しで重複になる。事象の表の `Put` にも条件を付け、どの経路でも既存の項目を上書きしない（I10）。

`order_key` の時刻は、送られた `at` を `Date` で読みミリ秒の 3 桁の UTC（`toISOString`）にそろえてから鍵と結ぶ。小数の桁が違う時刻を文字列のまま並べると、`…:00.5Z` が `…:00Z` より前に来るためである。`at` の列は送られた値のまま残す（確定仕様の「送り直しでも変えない」）。識別子は `^[A-Za-z0-9_-]{1,128}$` に限り、`order_key` の区切りの `#` と冪等の鍵の区切りの `:` を含めない。

1 つの表に 2 種類の項目を置く形は、確定仕様の区分の鍵（`sprint_run_id`）と冪等の鍵の項目の区分の鍵が合わず、#2172 が列を読むときに冪等の鍵の項目を除く手間を負う。

根拠: Value 6（MVV 版 3）

### 決定 7: GitHub の Webhook の宛先を引けるよう、`step.recorded` に Pull Request の参照を足し、事象の表の疎な GSI で引く（未決 1）

宛先のスプリントの実行を知っているのは、Pull Request を作ったランナーだけである。ブランチの名前は取り込んだリポジトリの NDF が決め、サービスの規則を置けない（確定仕様の決定 8）。リポジトリの登録（#2186）は Pull Request を知らない。そこで、ランナーが `pr` のステップを送る `step.recorded` に任意の `pull_request`（`repo`・`number`）を足し、受け口がその事象に `pr_ref` を置く。Webhook は `pr_ref-index` を引き、ちょうど 1 つのスプリントの実行に決まるときだけ残す。参照は事象の列の中に置くため、書き込みは 1 回のトランザクションのまま増えない。`step.recorded` の `payload` に鍵を足すことと正本の表に列を足すことは確定仕様の形の変更のため、同じ Pull Request で確定仕様を直し、ゲート 1 で利用者が見る。

新しい種類（`pr.linked` など）を足す形は、10 種類を前提にした受け入れ条件 1 と #2172 の読み手を変える。対応の表を別に作る形は、追記のトランザクションに 3 つ目の書き込みが入る。Pull Request を作った直後の `opened` は参照より先に届いて取りこぼすが、#2172 は最初の状態を `step.recorded` から読める（未確認のまま残ること）。

根拠: Value 1 / Value 6（MVV 版 3）

### 決定 8: 事象 1 件の上限を 256 KiB にし、超える承認資料はランナーが切り詰める（未決 2）

DynamoDB の項目の上限は 400 KB で、事象の表の項目は本文に加えて `order_key`・`pr_ref` と列の名前を持つ。256 KiB なら残りが 100 KB を超え、列を足しても上限に当たらない。NDF の承認資料は Pull Request の本文と同じ程度の長さで、256 KiB を超えるのは例外である。超えるときは、ランナー（#2186）が `material` を切り詰めて末尾に Pull Request の URL への案内を残す。承認資料の全文は Pull Request にあり、`gate.reached` は `pr_url` を持つため、人は全文を読める。確定仕様の形は変えない。

本文を S3 などの別の置き場へ移して事象に場所だけを載せる形は、確定仕様の `payload`（承認資料の本文）を変え、#2173 に読み出しの経路を足す。上限を 400 KB 近くまで上げる形は、列を 1 つ足しただけで書き込みが失敗しうる。

根拠: Value 1 / Value 10（MVV 版 3）

### 決定 9: 受け口を通らない書き込みを最小にするため、直の追記の関数は `job.finished`（`control`）だけを受ける

確定仕様で実行の制御が直に書くのは、ランナーが `job.finished` を送れずに終わったときの `job.finished`（`failed`）だけである。`appendControlEvent` は契約の検査と `control` の照合（種類と `<job_id>:finished` の鍵）を通し、受け口と同じ追記の関数（同じ重複の拒否）で書く。ほかの種類を受けると、受け口の認証を通らずに書ける経路が増える。

任意の事象を受ける追記の関数を公開する形は、`source` を偽った事象を API の外から書ける。

根拠: C2 / Value 6（MVV 版 3）

### 決定 10: #2173 を待たずに照合を作れるよう、保存済みの答えの読み出しを関数の型の口にし、既定は 503 にする

照合が読む「承認の依頼の保存済みの答え」は #2173 の集約で、まだ無い。`SavedAnswerReader`（依頼の識別子から答えか `null` を返す）を型として決め、受け口はそれを依存として受ける。テストは偽の実装で 5 つの項目の一致と未保存を縛る。handler が渡す既定は「読めない」として投げ、`api` の経路は 503 を返す。#2173 が `saved-answers.ts` の中身を替えれば、受け口のほかのファイルは変わらない。`gate.answered` を受け付けたことにせず、#2173 の再開の流れが先に進むこともない。

既定を「常に未保存」にする形は 403 を返し、#2173 の実装の途中の誤りを権限の誤りと区別できない。#2173 の表を受け口が直に読む形は、ほかの集約の表の形をこの課題が決めることになる。

根拠: Value 6（MVV 版 3）

### 決定 11: 有無を明かさないため、401・403 の本文を理由によらず 1 つにし、202 は重複でも同じ本文にする

送り手が理由を知ると、ほかのスプリントの実行や依頼の有無を試せる（非機能のセキュリティ）。400 だけは、送り手（ランナーの実装）が直すために失敗の位置（`instancePath`）と規則の名前を返す。定義は公開の契約で、位置と規則を返しても有無は分からない。値は返さない。202 の本文 `{"accepted": true}` は重複でも同じにする。送り手は重複かどうかで振る舞いを変えないためである。

理由を `code` に分ける形は、401 と 403 の区別だけで送り手が直せるのに、試す手がかりを増やす。

根拠: C2 / Value 6（MVV 版 3）

### 決定 12: IAM のロールの ARN を 1 つの変数で受けるため、呼び出し元はアカウントとロールの名前で照らす

API Gateway の IAM 認可を通った要求の呼び出し元は、引き受けたロールのセッションの ARN（`arn:aws:sts::<アカウント>:assumed-role/<ロールの名前>/<セッション>`）で届き、インフラが渡すロールの ARN（`arn:aws:iam::<アカウント>:role/<パス>/<ロールの名前>`）とは形が違う。両方からアカウントとロールの名前を取り出して比べる。セッションの名前とロールのパスは比べない。セッションの ARN はパスを持たないためである。IAM の文脈が無ければ 401、形が違うか一致しなければ 403 にする。

呼び出し元の ARN の一覧を変数に並べる形は、セッションの名前が呼び出しごとに変わるため書けない。

根拠: C2（MVV 版 3）
