## 目的

- Google か GitHub のアカウントで Neural Development Factory にログインでき、ログインした人がどのアカウント（個人かチーム）として操作しているかを、ほかの子課題が token 1 つから確かめられる状態にする
- プランと席ごとに使える量を 1 か所で決め、実行の制御（#2186）と課金（#2174）が同じ値を問い合わせて使える状態にする
- `factory/` に TypeScript のパッケージの管理の道具を決め、後続の子課題（#2171・#2172〜#2174・#2186）が同じ形で `factory/web/`・`factory/api/` にコードを足せる状態にする

## 前提

- 前提 1: Cognito の利用者プール・アプリのクライアント・外部の IdP（Google・GitHub）の登録・ドメインはインフラであり、private リポジトリ（owner = `volare`）が作る。この課題はその定義を書かず、受け取る変数の名前を `factory/.env.example` に足すだけにする（確定仕様の「データ・設定」。値は書かない、I6）
- 前提 2: GitHub のログインを Cognito へつなぐ形（Cognito の OIDC の IdP として直に登録できるか、OIDC の仲立ちのプログラムが要るか）は設計で確かめる。仲立ちが要り、それがインフラでなくサービスのコードなら `factory/api/` に置く。仲立ちの秘密（GitHub の OAuth の client secret）は Secrets Manager の ARN（`*_SECRET_ARN`）だけで受ける
- 前提 3: 1 人の人が Google と GitHub の両方でログインしたとき、2 つは別の利用者として扱い、自動で 1 つにまとめない（メールアドレスの一致でまとめると、片方の IdP でメールを偽れたときに他人のアカウントへ入れるため）。まとめる機能はこの課題に含めない
- 前提 4: アカウントは「個人」か「チーム」のどちらか。初めてログインした利用者には、その人だけの個人のアカウントがプラン Free で 1 つ作られる。チームのアカウントは席を持ち、席はそれぞれ 1 人の利用者と種類（standard / premium）を持つ。個人のアカウントは席を持たない（使える量はプランから決まる）
- 前提 5: チームへ人を入れるのは、チームの持ち主（チームを作った利用者）が、既に 1 度ログインした利用者を指して席を足す操作だけにする。招待のメールの送信はこの課題に含めない
- 前提 6: プランごと・席の種類ごとの使える量の値（同時のスプリントの数・月の token の上限）は、コードの分岐でなく 1 つの表（設定かデータ）で持つ。初めの値は設計で案を出し、ゲート 1 で利用者が決める。値を変えるのは表の 1 か所だけで済む
- 前提 7: 使える量の判定に要る「今の値」（動いているスプリントの実行の数・その月に使った token の数）は、この課題が持たない（スプリントの実行は #2186、使用量の台帳は #2174 の集約）。判定は呼び出す側が今の値を渡し、この課題は上限と照らした結果を返す。これで確定仕様の「使う契約は無い」を保つ
- 前提 8: プランを Free 以外へ変える経路（決済の後に誰が何を呼ぶか）は #2174 が決める。この課題は、アカウントのプランを書き換える操作を API の内側の関数として持つが、利用者が画面から自分のプランを変える経路は持たない
- 前提 9: 月の境目は UTC の暦月で数える（使用量の事象の `at` が UTC のため、確定仕様の「進捗の正本」）

## 対象範囲

含む:
- 画面（`factory/web/`）: Google か GitHub でログイン・ログアウトする画面と、自分のアカウント（プラン・使える量・チームなら席）を見る画面
- API（`factory/api/`）: Cognito の token の検証と `account_id` の解決、アカウント・席・プランの読み書き、使える量の問い合わせと判定
- チームのアカウントの作成と、席の追加・種類の変更・削除（チームの持ち主だけ）
- `factory/` の TypeScript のパッケージの管理の道具の決定と、`factory/web/`・`factory/api/` の雛形（依存の宣言・ロックファイル・型検査・テストのコマンド）
- `factory/web/`・`factory/api/` のテストと型検査を Pull Request で走らせる CI のジョブ
- `factory/.env.example` への変数の名前の追加と、用語集への語の追加

含まない:
- Cognito の利用者プールなどインフラの定義（private リポジトリ側。前提 1）
- 決済・料金・請求の画面と、プランを有料へ変える経路（#2174。前提 8）
- 使用量の台帳と、その月に使った token の集計（#2174。前提 7）
- スプリントの開始を断る処理そのもの（#2186。この課題は判定を返す）
- 2 つの IdP の利用者を 1 つにまとめる機能（前提 3）・招待のメール（前提 5）
- 確定仕様の契約の形の変更。変えるなら設計 Pull Request で確定仕様を先に直す（確定仕様の「サービス全体の契約」の冒頭）

## 用語

| 用語 | 意味 |
| --- | --- |
| アカウント | Neural Development Factory で、プランと使える量を持ち、リポジトリの登録とスプリントの実行を持つ単位。個人とチームの 2 種類。`account_id` で指す |
| 席 | チームのアカウントの中で、1 人の利用者に割り当てる枠。種類は standard と premium |
| プラン | アカウントの契約の種類。Free・個人 Pro・個人 Max・Team の 4 つ。Team の使える量は席の種類で決まる |
| 使える量 | プランか席の種類ごとに決まる上限。同時に動かせるスプリントの実行の数と、月の token の上限の 2 つ |

## 受け入れ条件

ログイン:

- [ ] 1. ログインの画面に Google と GitHub の 2 つのログインの操作があり、どちらでも Cognito を経てログインでき、ログイン後の画面に自分のアカウントのプランが出る
- [ ] 2. IdP の画面で利用者が取り消したか IdP が拒んだとき、ログインの画面へ戻り、ログインできなかったことが出る。token は保存されない
- [ ] 3. ログアウトすると、画面が保存した token が消え、API を呼ぶ画面を開くとログインの画面へ移る

認可の token と `account_id`:

- [ ] 4. API は Cognito の token を署名・発行元・対象のクライアント・期限で検証する。token が無い・署名が違う・期限切れ・別の利用者プールかクライアントのもののどれでも 401 を返し、アカウントの中身を返さない。それぞれを 1 つずつ入れたテストで確かめる
- [ ] 5. 検証を通った token から、その利用者が操作しているアカウントの `account_id` を得る関数が `factory/api/` にあり、#2171・#2186・#2174 の API が同じ関数を呼んで使える。チームのアカウントを指す要求で、その利用者がチームの席を持たなければ 403 を返す

プランと使える量:

- [ ] 6. 使える量の問い合わせに `account_id`（チームなら席の利用者も）を渡すと、同時に動かせるスプリントの実行の数と月の token の上限が返る。値はプラン（個人のアカウント）か席の種類（チームのアカウント）で決まり、Free・個人 Pro・個人 Max・Team standard・Team premium の 5 つで、表（前提 6）の値と一致する
- [ ] 7. 使える量の判定に今の値（動いているスプリントの実行の数・その月の token の数）を渡すと、上限より小さければ許す結果、上限に達していれば断る結果と理由（どの量が・上限がいくつで・今がいくつか）が返る。上限ちょうど・上限より 1 少ない・上限より多いの 3 つの境目をテストで確かめる
- [ ] 8. 画面の自分のアカウントの画面に、使える量の 2 つの上限が出る

チームと席:

- [ ] 9. 利用者がチームのアカウントを作ると、作った利用者がチームの持ち主になり、持ち主自身の席が 1 つ（種類は作るときに選ぶ）できる
- [ ] 10. チームの持ち主は、既に 1 度ログインした利用者を指して席を足し、席の種類を変え、席を外せる。持ち主でない利用者が同じ操作をすると 403 で、席は変わらない
- [ ] 11. 未ログインの利用者を指して席を足す・同じチームに既に席を持つ利用者を足す・持ち主自身の席を外すのどれも断られ、理由が出る。席は変わらない

起きてはいけないこと:

- [ ] 12. 同じ利用者が何度ログインしても、個人のアカウントは 1 つだけである（並べて 2 回ログインしても 2 つにならない）
- [ ] 13. 利用者 A の token で、A が席を持たないアカウント（他人の個人のアカウント・入っていないチーム）のプラン・使える量・席を読もうとしても書こうとしても 403 で、相手のアカウントの有無と中身が応答に出ない
- [ ] 14. このリポジトリに、Cognito の利用者プールなどインフラの定義・秘密・`.env` の実ファイルが入らない。境界の検査（`python3 scripts/check-service-boundary.py`）が 0 で終わる

パッケージの管理と検査:

- [ ] 15. `factory/` の TypeScript のパッケージの管理の道具が 1 つに決まり、`factory/web/`・`factory/api/` に依存の宣言とロックファイルがある。決めた道具と理由が設計文書にあり、後続の子課題が従う規則として `factory/README.md` に書いてある
- [ ] 16. `factory/web/`・`factory/api/` の型検査とテストが、それぞれ 1 つのコマンドで手元と CI の両方で走る。CI のジョブは `factory/` を変える Pull Request で走り、落ちれば Pull Request が赤になる
- [ ] 17. 既存のテスト（`uv run --frozen --project . --all-extras pytest . -q -n 4`）・`claude plugin validate .`・既存の CI の必須チェックが、この変更の前と同じに通る。プラグインの配布物と CLI だけで使う人の振る舞いは変わらない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| セキュリティ | token は API で毎回検証し、画面の判定だけで認可しない（受け入れ条件 4・13）。秘密は Secrets Manager の ARN だけで受け、値をコード・ログ・応答に出さない。token と利用者のメールアドレスをログに出さない。この変更は共通原則の C2（認証・認可を変える）に当たる |
| 運用・保守性 | 使える量の値は表の 1 か所で変える（前提 6）。断った判定の理由は、利用者に出す文と同じ中身を API の応答に構造で返す |
| システム環境 | 画面は React の SPA（Vite）、API は Node の Lambda、TypeScript（確定仕様の「構成と言語」）。Node の版は設計で決め、`factory/` の中で 1 つに揃える |
