# #3597 の設計の決定の記録

設計文書の本体は [issue-3597-design.md](issue-3597-design.md) にある。番号（`STD1` など）は本体の「外部の調査」の表を指す。

## 決定の記録

### 決定 1: 確定の後の依頼が提示の依頼と重ならないよう、id を `<計画名>-p<連番>-<提示>-c<確定の起動の連番>` にする

リリース 17 では、確定の後の依頼が提示 1 の依頼と同じ id `p6-p17-1` になり、台帳に書かれなかった。確定の起動の連番（耐久ワークフローが確定の起動で立てるイベント `pause` の `seq`）を足すと、提示の依頼とも、打ち直した後の確定の依頼とも重ならない。同じ起動の中の打ち直し（一時レーンが同じコマンドを 2 回打つ）は同じ id になり、1 つの依頼にまとまる。

本番のプランの done の中身から id を作る形は採らない。done は本番のプランを流し直すと上書きされ、同じ承認ゲートの結果から同じ id を作れることを確かめる手段が無い。台帳の行の数から振る連番も採らない。打ち直すたびに新しい id になり、要求の事象 2（答えのある問いの送り直し）と同じ送り直しが起きる。

根拠: Value 3 / Value 7（MVV 版 7）

### 決定 2: 確定の後の承認ゲートを既存のリリース承認ゲートの依頼の形で人へ戻し、選択肢を「打ち直す」「差し戻す」の 2 つにする

依頼は種類 `gate2` のまま、`after: "confirmed"`・止まった理由・本番の PR の番号を足す。承認ゲートを新しく足さない（要求の前提 2）。オーガナイザーは `parallel.py answer --choice` で答え、耐久ワークフローが答えを当てる。

| 答え | 起きること |
| --- | --- |
| 打ち直す | 新しい連番の確定の起動を流し、同じ承認のまま本番のプランを流し直す |
| 差し戻す | リリースを差し戻しで締め、範囲のレーンへ今のリリース承認ゲートの差し戻しと同じ結果を返す。開いている本番の PR は閉じ、差し戻しの理由と依頼の id をコメントに残す |

「差し戻す」の締めは、`parallel.py settle --rejected` が送る締めの再開と同じメソッドを `result: rejected` で通す。通るメソッドは `_Run.settle` から `_answer_settled` である。そのため、範囲のレーンへ返る結果が提示の差し戻しと同じになる。今の `_release_result` が確定の後の締めを終了コード 4 で断るのは、本番のプランの done を読むコマンドの側である。耐久ワークフローの中の締めはそこを通らない。

次のリリースの本番のプランは、開いている本番の PR だけを使い回す（`release-steps.py` の `_merge_prod_pr`）。そのため閉じた PR とは重ならず、新しい PR で提示から承認を取り直す。閉じた PR は開き直せるため、戻せない操作（C4）に当たらない。

答えを当てるのを耐久ワークフローにするのは、区分 `helper`・`spawn` の問いと同じ置き場にするためである。一時レーンの起動を耐久ワークフローだけが打つ決まりも保てる。

提示と同じく `confirm` / `settle --rejected` で答える形は採らない。`confirm` は同じ連番で 2 回目の行を台帳へ書けず（重複の判定のキー `resume:confirm:<連番>:<take>`）、打ち直しを表せない。

#3572 の設計の決定 3 との対応は次のとおりである。決定 3 は設計 PR https://github.com/devbasex/ai-plugins/pull/3596 にある。ファイルは `issues/issue-3572-design-decisions.md` である。食い違いは 3 件で、いずれも今の NDF に #3572 の止まった理由の分類と本番の PR の扱いが無いことによる。

| 観点 | #3572 の決定 3 | この設計 | 食い違いと理由 |
| --- | --- | --- | --- |
| 次の手の数 | `rerun` と `reject` の 2 つ | 「打ち直す」と「差し戻す」の 2 つ | 無し |
| 承認ゲートを足すか | 足さない | 足さない（リリース承認ゲートの依頼の種類 `gate2`） | 無し |
| 打ち直しの意味 | 同じ承認・同じ先端のまま `merge` を打ち直す | 同じ承認（承認したコミット）のまま確定の流すものを流し直す | 無し |
| 差し戻しの意味 | 本番の PR を開いたまま直しを同じ PR へ入れ、新しい先端で承認を取り直す | リリースを差し戻しで締めて本番の PR を閉じ、直しはスプリントの経路で入れて次のリリースの提示から新しい PR で承認を取り直す | 有り。今の NDF の差し戻しの道（`settle` の `rejected`）を使い、本番の PR を開いたまま直しを受ける道を足さない。足すと #3572 が ndf-next で作り直す道を今の NDF にも作ることになる |
| 既定の手（`suggested`） | 止まった理由から決まる | 示さない | 有り。今の NDF の本番のプランの done は承認ゲートの理由を文として持ち、分類（`infra_wait` など）を持たない（決定 3） |
| 人へ問わずに打ち直せる理由 | `infra_wait`・`ci_pending` はオーガナイザーか一時レーンが打ってよい | 無い。すべて人の答えで打ち直す | 有り。決定 3 |

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1 / PRD1

根拠: Value 1 / Value 7（MVV 版 7）

### 決定 3: 今の NDF では、人へ問わずに打ち直せる止まった理由を持たない

今の NDF の本番のプランが承認ゲートで終わる理由は、done とレポートの文（リリース 17 では「有効な承認のレビューが無い」）で表される。機械で分けられる分類は持たない。CI の待ちは、承認ゲートではなく本番のプランの `release` のステップの中で持つ（`release-steps.py release --ci-wait <秒>`。リリース 17 の `release.json` で確かめた）。分類の無い理由で問わずに打ち直すと、承認の証跡の不足のように打ち直しても通らない理由で繰り返す。

#3572 の分類（`infra_wait`・`ci_pending`）を今の NDF の本番のプランへ足す形は採らない。分類を作るのは ndf-next の `merge` の部品であり、今の NDF へ写すと同じ規則が 2 か所に分かれる（Value 11）。

根拠: Value 1 / Value 11（MVV 版 7）

### 決定 4: 確定の後の承認ゲートで依頼を送らない場合を持たない

確定の後の承認ゲートは、すべて「打ち直す」「差し戻す」の依頼にする。送らずに止まる理由になりうるのは、同じ確定の起動の依頼がすでにある場合だけである。そのときは依頼のコマンドが送り済みと返し（決定 5）、台帳に依頼の行がある。耐久ワークフローの途中停止の問いは、その連番の `gate2` の依頼があれば立たない（今の `_ask_helper`）。受け入れ条件 4 の「送らない理由を残して止まる」は、この決定により起きない。要求のドメインイベント E4 の「送らない理由を記録した」場合も、この決定で外した。

今の `_ask_helper` が確定の後の依頼を拾う根拠は、判定の条件が問いの一覧の種類と連番だけで、id の形と `after` を見ないことである。

```console
$ grep -n 'q.get("kind") == "gate2" and q.get("n") == rel\["n"\]' plugins/ndf/scripts/lib/parallel_observe.py   # 2026-11-15
47:    if row.get("state") != "stopped" or any(q.get("kind") == "gate2" and q.get("n") == rel["n"] for q in run.questions):
```

種類 `gate2` は耐久ワークフローが受け取る種類（`TAKE`）に入っており、確定の後の依頼も `receive_question` で問いの一覧へ入る。ただし処理済みのリリース承認ゲートの判定（`settled_gates`）は、台帳のチェックポイントより前に届いた `gate2` を、同じ連番の確定の行があれば処理済みにする。このままでは確定の後の依頼がチェックポイントを挟むと問いの一覧から外れ、途中停止の問いが立ちうる。そのため `settled_gates` は、確定の後の依頼をその id の答えの行かそれより後の締めの行でだけ処理済みにする（本体の構成要素の「台帳の判定」）。

送らない理由を `settle` と同じ置き場へ書く形は採らない。送らない場合を設けると、その条件を人が見ないまま本番へ出ないリリースが残る。

根拠: Value 1（MVV 版 7）

### 決定 5: 同じキーの行があったときは、中身が同じ再送なら最初の結果（送り済み）を返し、中身が違えば終了コード 5 で断る

`deliver_message` は台帳へ書いた結果を返し、依頼のコマンドがそれを読む。同じキーの行があったときは、その行と中身（送るたびに変わる `at` を除いた `msg`）を比べて返し方を分ける。

| 同じキーの行の中身 | 何が起きたか | 返すもの |
| --- | --- | --- |
| 同じ | 同じ依頼の送り直し | 答え待ち・答え済み・処理済みのどれでも、送ったときと同じ終了コードで `metrics.already: true`・`metrics.answered` と要約「送り済み」。送り手は今と同じく続く待ちで答えを読む |
| 違う | 別の依頼が同じ id を使った（リリース 17 の確定の後の依頼が提示 1 の id と重なった事象） | 終了コード 5 と、既にある id と理由。送り手は次の手を変える必要がある |

この返し方は 2 つに倣う。標準案（STD1）は、処理済みの再送には最初の結果に沿った応答を返し、別の中身は 422 で断る。Stripe（PRD1）は、同じキーの再送には保存した最初の結果を返し、引数が違えば誤りを返す。

答え済みか処理済みの再送をすべて断る形は採らない。レーンと一時レーンは、起き直しのたびに同じ依頼を同じ id で打ち直す（`request` は id をファイルから読み直す）。断ると、答えを受けた後に起き直したレーンの打ち直しが止まる。今の振る舞いでは、打ち直しは送り済みで返り、続く `parallel.py await` が答えを読んで進む。断る形はこれと食い違う（受け入れ条件 12）。同じキーをすべて断る形も、同じ理由で採らない。

- 作り方: 標準に倣う
- 比べた候補: STD1 / PRD1

根拠: Value 3 / Value 13（MVV 版 7）

**実装で変えた点（2026-11-15）:** 中身の違う同じキーの依頼を断る終了コードを 5 から 1（失敗）へ変えた。終了コード 5 は NDF の全体で「CD の結果が失敗」の意味を持ち、統一 JSON レポートの終了コードの決まり（`step_result.code_matches`）と契約の検査（`check-ndf-contracts` の exit-meaning）が落とすためである。断る理由は今と同じく `metrics.existing`・`metrics.reason` で区別できる。

### 決定 6: 問いの対象のブランチ名を問いの入力の `metadata.target` で受け、先端のコミットは `request-ask` が求める

対象は `<ブランチ名>@<先端のコミットの 40 桁>` か `#<課題か PR の番号>` の 1 つの文字列にする。一時レーンが `metadata.target` に書くのはブランチ名か `#<番号>` だけである。先端のコミットは、`request-ask` が問いを受けた時点に、問いを出した作業ディレクトリで `git rev-parse --verify` で求めて足す。先端を 40 桁で持つと、先端が動いた問いは文字列が変わり、比べるだけで別の問いになる（受け入れ条件 6）。`target` の無い問いと、先端を求められないブランチ名の問いは、比べずに新しい依頼にする。戻せない操作の答えを、対象の分からない問いへ当てないためである。

先端のコミットを一時レーンに書かせる形は採らない。一時レーンが前の起動の引継ぎ文書などから古い先端を書き写すと、先端が動いた後の問いが前の問いと同じ対象になる。すると、戻せない操作（C4）の答えが動いた後の先端へ当たる。`request-ask` が求めれば、書き写す道が無い。

問いの文から対象を読む形は採らない。リリース 17 の 2 つの問いは同じ対象を別の言い回しで書いており、文から読む規則は言い回しに依る（要求の前提 3）。`stamp`（問いを出した作業ディレクトリの先頭のコミット）も採らない。作業ディレクトリの先頭は操作の対象のブランチの先端と別で、リリース 17 では 2 つの問いの `stamp` が同じでも対象の先端は記録されていない。

`metadata.target` が問いの hook へ届くかは、設計の時点で確かめられていない（本体の外部の調査の「確かめられなかったこと」）。受け入れ条件 5〜8 の直しはこの設計に含め、実装の最初にリレーの対話のセッションで `metadata.target` を付けた問いを 1 回打って確かめる。届かなければ、受け入れ条件 5〜8 の実装を止めて、確かめた結果を添えて人へ戻す。届かなくても、`target` の無い問いと同じく新しい依頼になるだけで、前の答えを別の対象へ当てる側には倒れない。

受け入れ条件 5〜8 を確かめるまで別の課題へ分ける形は採らない。確かめる手段は実装の最初の 1 回の呼び出しで足り、分けると同じ問いの送り直し（要求の事象 2）が直るまでのリリースが 1 つ遅れる。

根拠: Value 8 / C4（MVV 版 7）

**実装で変えた点（2026-11-15）:** 実装の最初の確かめで、`AskUserQuestion` の `metadata` のスキーマは `source` だけを持ち `additionalProperties: false` で、`metadata.target` は入力の検証で落ちて hook へ届かないと分かった。この決定の取り決めどおり受け入れ条件 5〜8 の実装を止めて人へ戻し、利用者の決定「5〜8 を分けて出す」（並列の計画 p6 の依頼 `lfix-rel-qb045f34bd845`）で #3608 へ分けた。決定 7 の同じ問いの判定と、決定 8 の `asked` の `target` の比べ方は #3608 が決め直す（#3603 と一緒に設計する）。この課題で入れるのは決定 8 の `asked`（前の依頼と答えを読む場所）までで、`target` は常に空になる。

### 決定 7: 同じ問いの判定を `request-ask` の中に置き、答え済みなら答えを hook の拒否の理由で返す

一時レーンの問いは、すべて問いの hook が `request-ask` へ渡す。台帳へ書く手前の 1 か所で引けば、一時レーンの手順に依らずに送り直しが止まる。答え済みなら、hook は答えを拒否の理由に載せて返し、一時レーンはその答えで進む。答え待ちなら、その id で保留の手順を返す。どちらも台帳に `reused` の行を残し、後から引き継ぎを追える。判定そのものは台帳の行を受け取る純粋な関数（`parallel_question.py`）に置く。

一時レーンの手順書だけで「問う前に台帳を読む」と決める形は採らない。リリース 17 の一時レーンは、引継ぎ文書を読む前に問いを出した。手順書だけに頼ると、読み落としたときに前の答えのある問いが人へ送り直される（Value 3）。

この決定でも、一時レーンの手順に頼る部分が 1 つ残る。`metadata.target` にブランチ名を載せることである。載せ忘れたときは `target` の無い問いと同じく新しい依頼になる。起きるのは今と同じ送り直しまでで、前の答えを別の対象へ当てることは起きない。手順書だけで済ませる形では、読み落としが送り直しに直結する。この決定では、手順書の 1 か所（ブランチ名を載せる）を守れば送り直しが止まり、守れなくても安全な側（人へもう一度問う）に倒れる。先端の書き写しは決定 6 で一時レーンの手から外した。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1 / PRD1

根拠: Value 3 / C4（MVV 版 7）

### 決定 8: 起き直した一時レーンが前の依頼と答えを読む場所を、`parallel.py helper` の結果の `asked` に置く

一時レーンが最初に打つのは `parallel.py helper` であり、その結果に自分の名前の依頼と答えを並べると、手順を足さずに読める。手順書の一時レーンの手順 1 に、`asked` を読んで答えのある問いを出さないことを足す。`asking.md` が一時レーンに指す `parallel.py await` は、リリースの依頼の記録だけを読む。そのため、一時レーンの問いの答えには `asked` を指すよう直す。台帳を読めなければ、`parallel.py helper` は今と同じく終了コード 2 で止まる。一時レーンは問いを送らずに止まり、耐久ワークフローの途中停止の問いになる（要求の E8 の扱い）。

`parallel.py await` を問いの答えにも広げる形は採らない。`await` は依頼の記録のファイルを入力に取り、一時レーンは問いの依頼の記録のファイルを持たない。

根拠: Value 3（MVV 版 7）

### 決定 9: 一時レーンの同時数による断りを、リレーハブの結果の値 `helper-busy` で全体の上限の断りと分ける

今のリレーハブは、一時レーンの同時数と全体の上限の両方を `limit` で返し、違いは文にしか無い。待つのは一時レーンの同時数の断りだけで（受け入れ条件 9）、全体の上限の断りは今と同じ扱いにする（受け入れ条件 11）。そのため、機械で分ける値が要る。結果に動いている一時レーンの名前を載せ、区分 `spawn` の問いの本文へ出す（受け入れ条件 10）。標準 STD2 が、待って打ち直せる断りを別の状態コードと待つ時間で示す形に倣う。

断りの文を照らして分ける形は採らない。文は人が読むためのもので、変えると判定が黙って外れる。耐久ワークフローが一覧で動いている一時レーンを探して分ける形も採らない。断りを判定したリレーハブと別の時点の一覧を読むため、判定と食い違いうる。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD2

根拠: Value 3 / Value 9（MVV 版 7）

### 決定 10: 一時レーンの空き待ちを起動の記録に持ってループの 1 回ごとに読み直し、上限を 3,600 秒にする

`helper-busy` で断られた起動は 2 回目を打たず、起動の記録を `waiting`（最初に断られた時刻と動いている一時レーンの名前）にする。耐久ワークフローはループの 1 回の観測で空き待ちを読み直し、前の一時レーンが止まって観えれば打ち直す。上限を過ぎても動いていれば、今と同じく区分 `spawn` の問いを立てる。上限は 3,600 秒にし、上限の宣言 `parallel-launch.helper-wait` に置く。値は、リレーハブの記録にある一時レーンの稼働時間の実測（84 回、中央値 165 秒・90 パーセンタイル 2,057 秒・最大 3,512 秒）で観測した最大を含む。GitHub Actions の同時実行のグループ（PRD2）が、実行中のものがあれば断らずに待ちへ入れる形に倣う。

DBOS の耐久の待ち（LIB1 の `DBOS.sleep`・`DBOS.recv` のタイムアウト）でループの 1 回の中で待つ形は採らない。待つ間に他のレーンの観測と答えの処理が止まる（非機能の可用性）。tenacity（LIB2）は同じプロセスの中の打ち直しの部品で、ループの 1 回をまたぐ待ちを持たない。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: PRD2 / LIB1 / LIB2 / STD2

根拠: Value 1 / Value 13（MVV 版 7）

### 決定 11: ndf-next のリリースのドメインへ移すのは、同じ問いの答えの引き継ぎだけにする

ndf-next（`plugins/ndf-next/`）は変えず、決まりごとに移す要否を次のとおりにする（受け入れ条件 13）。根拠にした検索は表の下にある。

| 決まり | 移す要否 | 理由 |
| --- | --- | --- |
| 依頼の id が重ならない | 移さない | ndf-next の依頼の鍵は、計画の進行表の依頼の数から振る連番（`src/ndf/progress/plan/__init__.py` の `open_request`）で、提示と確定で同じ鍵を作る道が無い |
| 送らなかったことを送ったと返さない | 移さない | ndf-next の依頼は進行表へ追記してから鍵を返し（同上）、重複のキーで書かずに捨てる道を持たない |
| 同じ問いの答えの引き継ぎ | 移す | ndf-next のレーンの問いは、問いごとに新しい依頼を開く（`src/ndf/domains/relay/lane_question.py` から `open_request`）。レーンが起き直して同じ問いを出すと、要求の事象 2（答えのある問いの送り直し）と同じ送り直しが起きうる。範囲外の課題 #3599 として起票した |
| 前の一時レーンを待つ | 移さない | ndf-next の中継に役割 `helper` と一時レーンの同時数の上限が無い。起動の失敗は依頼（中身の `kind` が `launch_failed`）になるが、待つ相手の一時レーンが無い |

```console
0
$ grep -n 'key = f"{REQUEST_PREFIX}' plugins/ndf-next/src/ndf/progress/plan/__init__.py

```
