## 何が起きたか

2026-11-24、中継のラッパーの課題（ https://github.com/devbasex/ai-plugins/issues/4049 ）の開発で、conductor（スプリントの工程を進める AI）が、工程を自動で進めるコマンド `ndf progress next` を打った。作業場所の用意と計画に続けて、工程「実装」が止まらずに始まった。

計画の工程が書いた実装計画は、変更を 7 つのレビューの単位（U1〜U7、見込み約 3,400 行）に分けていた。ところが自動のプランは、課題 1 つを 1 本の worker（実装を担当する AI）に渡し、スプリントブランチの作業場所で直接実装した。実装のプランに渡った値は、ブランチがスプリントブランチ、マージ先が `main`、受け入れ条件が課題全体（`--issue 4049`）である。

conductor は worker を止め、単位ごとの実装を supervisor（フェーズを通す AI）に渡し直した。

## 種類

機能追加（単位ごとにプランを組む約束があるのは supervisor の手順だけで、自動のプランの側に単位の約束は無い）

## 今の姿

実装計画の「レビューの単位」は、1 本の PR にまとめて 1 回のコードレビューを掛ける変更のまとまりである。supervisor で回すときは、単位ごとにプランを組み、単位の PR をスプリントブランチへ出してレビューし、マージする（[agent-layers.md の「実装のフェーズの単位」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/agent-layers.md#実装のフェーズの単位)）。

自動のプランは単位を読まない（2026-11-25、main の 11.0.39 のコードを読んで確かめた。`ndf progress next` を流しての確認はしていない）。

- 工程「実装」の定義（[implement.json](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/contracts/workflow/stages/implement.json)）は、実装のプランを呼び、続けて集めた時点（`gathered`）を記録する。プランは工程 1 回につき 1 本で、課題が複数でも 1 本である（定義には課題ごとに分ける指定 `per_issue` があるが、分ける処理はまだ無い。2026-11-26 にコードを読んで確かめた）
- そのプランのブランチは、工程の作業場所が今いるブランチ（スプリントブランチ）になる（`plugins/ndf/src/ndf/progress/invoke.py` の差し込みの出所の表 `FILL_SOURCES`）
- 工程のプランを組むコード（`plugins/ndf/src/ndf/progress/`）に、実装計画の単位を読む処理は無い（`git grep` で `レビューの単位`・`units` を引いて 0 件）
- 実行中の工程には `disable` も `finish` も書けないので、止めるには worker のプロセスを止めて工程を失敗にするしかない

## 何を足すか・変えるか

| | 今 | 足した後 |
| --- | --- | --- |
| 実装のプランの数 | 課題が複数でも 1 本 | 単位がある実装計画を持つスプリントは単位ごとに 1 本 |
| ブランチと PR | スプリントブランチで直接実装する | 単位のブランチで実装し、PR をスプリントブランチ宛てに出す |
| 受け入れ条件の確かめ | 課題全体 | その単位が満たす条件（`--criteria`） |
| 単位の順序とマージ | 無い | 実行の順に流し、レビューした単位の PR をマージしてから次へ進む |

## 今の利用者への影響と互換

- 単位がある実装計画を持つ課題を自動で流すと、PR が単位の数だけ作られ、スプリントブランチへマージされる
- どの課題の実装計画にも単位の欄が無いスプリント（実装計画を省いた課題を含む）は、今と同じ流れになる

## なぜ困るか

- conductor は、自動で始まった実装を止めて組み直すことになり、止めるには worker のプロセスを落とすしかない
- 気づかなければ、1,000 行を超える変更が 1 本の PR になる。レビュー担当（人と AI）が 1 回で読み切れる大きさ（目安は 1 単位 400 行以下）を超える

## 目的

自動で工程「実装」を流しても、実装計画の分け方のとおりに、単位ごとの PR とレビューを経てスプリントブランチへ集まる。conductor が自動のプランを止めて組み直さなくてよい。

## 対象範囲

含む:
- 自動の経路（`ndf progress next`）の工程「実装」が実装計画の単位を読み、単位ごとに作業場所の用意・実装・PR・レビュー・マージを実行の順に流すこと
- すべての単位をマージした後に、集めた時点を記録すること

含まない:
- 実行中の工程を止める操作（`disable`・`finish` を書ける範囲の変更）
- 実装計画の書式の変更
- supervisor で回すときの手順の変更
- 実行中にプロセスを中断した場合の復旧と、レビューの後に PR が外から変えられた場合の復旧（ https://github.com/devbasex/ai-plugins/issues/4218 「レビューしていない中身をマージしない」が扱う）。今回の対象は、工程が失敗か待ちを返した後の打ち直し（条件 6）である。外から変えられた PR をマージしないことは、今回の条件 4 に含む
- 実装計画を設計の工程で書くことと、単位の大きさを機械で確かめること（ https://github.com/devbasex/ai-plugins/issues/3702 が扱う）

## 前提

- 前提 1: 単位の実行の順は、実装計画の単位の表に「実行順」の列があればその値とする（準備のタスクを含む単位も列の値に従う）。列が無ければ今の手順書の決まり（準備のタスクを含む単位を最初に流してマージし、残りの単位はその後に始める）とする。表の形は変えない
- 前提 2: 「単位の欄が無い」とは、実装計画に「レビューの単位」の見出しが無いことをいう

## 受け入れ条件

- [ ] 1. 実装計画に「レビューの単位」の表があるとき、`ndf progress next` の工程「実装」は、単位ごとに 1 本のプラン（単位のブランチ・スプリントブランチ宛ての PR・単位の受け入れ条件の `--criteria`）を、表の実行の順（前提 1）で流す。単位の欄がある課題と無い課題が混ざるときは、欄の無い課題は課題 1 つを 1 単位にして流す
- [ ] 2. どの課題の実装計画にも単位の欄が無いとき（実装計画を省いた課題を含む）は、今のとおり、課題が複数でも実装のプランを 1 本だけ流す
- [ ] 3. すべての単位をマージした後に、工程の出力 `gathered` が書かれる
- [ ] 4. 単位の PR は、レビューが収束し、レビューした PR の宛先がスプリントブランチのままで、HEAD がレビューした HEAD と同じときだけマージされる。人の判断を待つ指摘が 1 件でも残る単位はマージせず、その単位で止めて理由を示す。次の順の単位の作業場所は、前の順の単位をすべてマージした後のスプリントブランチから切られる
- [ ] 5. どれかの単位のプランが失敗するか、その PR をマージできないときは、後の順の単位を始めず、`gathered` を書かずに工程が止まる。止まった単位の名前と理由が結果から分かる
- [ ] 6. 止まった工程を打ち直すと、マージ済みの単位は実装もマージもし直さず、残りの単位から続く
- [ ] 7. 「レビューの単位」の見出しがあるのに単位を読み取れない（単位が 0 件、満たす受け入れ条件が課題の本文に無いなど）ときは、課題 1 つを 1 本にまとめて流さず、理由を示して実装を始める前に止まる

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。単位がある実装計画のとき、`ndf progress next` の工程「実装」が作るブランチ・PR・マージが増える。コマンドの引数を変えることは求めない |
| データ | スキーマの変更や移行は求めない |
| 既存の振る舞い | 工程「実装」の自動のプラン。単位の欄が無い場合と supervisor で回す場合は変わらない |

## 用語

| 用語 | 意味 |
| --- | --- |
| レビューの単位 | 1 本の PR にまとめ、1 回のコードレビューを掛ける変更のまとまり。実装計画が決める |
| 単位の PR | レビューの単位 1 つを載せ、スプリントブランチへ出す PR |
| 集めた時点 | すべての単位の PR をマージした時点のスプリントブランチのコミット（`gathered`）。後のコードレビューの起点になる |
