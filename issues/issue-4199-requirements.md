#4068 は、長く待つ AI の会話のプロンプトのキャッシュが切れないよう、切れる手前で会話を短く起こす仕組みである。その設計に、キャッシュの寿命の決め方の誤りが 1 つと、費用の数え方の誤りが 2 つある。あわせて、寿命が 1 度も分からない待ちの扱いが決まっていない。この Issue では、この 4 つを直す。寿命の誤りは、待っている会話を起こせなくする。費用の誤りは、「起こすのは割に合うか」を見直すときの数を狂わせる。#4068 の実装の前に設計を直し、寿命は常に最新の記録から決め、費用はキャッシュへ実際に書いた寿命ごとの値段で数えるようにする。

この Issue は #4068 へ統合し、#4068 と同じ設計の Pull Request で設計する。

**前に知っておくこと**（#4068 の仕組みの要点）:

- **キャッシュの寿命と値段。** キャッシュには寿命が 1 時間のものと 5 分のものがある。書き込みの値段は、寿命 1 時間なら入力の 2 倍、5 分なら 1.25 倍である。Claude Code は、応答ごとに 1 時間と 5 分の書き込みの量を別々に記録する
- **子と起こす hook。** 子は、NDF の中継（`ndf relay`）が包んで動かす Claude Code の会話である。子が 1 回の応答を終えるたびに（Stop）、NDF の hook が 1 つバックグラウンドで動く。hook はその応答の記録から寿命を読み、寿命の手前まで眠ってから子を起こす（「起床」。起こした後の応答を「起こした応答」と呼ぶ）
- **1 つの応答の中で、モデルを何度か呼ぶ。** Tool を使う応答では、Tool を呼ぶたびにモデルの呼び出しが 1 回増える。記録の書き込みの量は、呼び出しごとに載る
- **hook は追い越し合う。** hook はバックグラウンドで動くので、応答が続くと、前の応答の hook が後の応答の hook より遅れて動くことがある。そのため、hook どうしが共有する「会話ごとの状態」（寿命・起こした回数など）は、ロックの中で読み書きする。ロックは、同じ会話の状態を同時に 1 つの hook だけが読み書きできるようにする仕組みである（#4068 の設計では、中継が子を止めるときに取るロックを共用するので「子を止めるロック」と呼ぶ）
- **書き込みが無い応答。** まれに、応答の記録に 1 時間の書き込みも 5 分の書き込みも無い（両方 0）ことがある。そのときは寿命を前の状態から補う

## 何が起きたか

2026-11-23、#4089（文脈の量の読み取り関数）の設計 Pull Request（ https://github.com/devbasex/ai-plugins/pull/4194 ）の cross-review（別の AI によるレビュー）で、レビュー担当が #4068 の設計に次の 4 つの問題を見つけた。#4089 の範囲の外なので、この Issue に分けた。#4068 はまだ実装されていない（main の `2fd9227a4` に、起こす hook も `asyncRewake` の登録も無い）。

- 誤り 3 つ（4〜6 ラウンド目の指摘）: 下の表の 1〜3。このまま実装すると、表のとおり誤る
- 決まっていない点 1 つ（3 ラウンド目の指摘）: 寿命が 1 度も分からない待ちで、起こす回数の上限と費用をどう扱うか（「何を足すか・変えるか」の 2 行目）

誤り 1 は、hook が次の順で動いたときに起きる。

1. 新しい応答（書き込みが両方 0）の hook が、ロックの外で状態を読む。寿命はまだ「分からない」
2. 遅れて動いた前の応答の hook が、ロックの中で「寿命 1 時間で待ち始めた」と状態に書く
3. 新しい応答の hook がロックに入り、1 で読んだ古い「分からない」で寿命を補う。状態の寿命は「分からない」へ戻る

結果として、待っている会話の寿命が失われ、その会話は起こされなくなる。

| 2 | 寿命 1 時間の待ちで起こした後、起こした応答が 5 分のキャッシュへ 1,000 token 書いた | 1,000 × 2.0 = 2,000 token 相当と数える | 1,000 × 1.25 = 1,250 token 相当 |
| 3 | 待ちの直前の文脈が 100,000 token・寿命 1 時間の待ちが、利用者の入力で終わった。その入力への応答は 5 分のキャッシュへ書いた（Opus 5.5。読み出しは 0.05 倍）。「避けた書き直し」は、起こしたおかげで払わずに済んだ書き直しの費用で、起こす効果の見積りに使う | 避けた書き直しを (1.25 − 0.05) × 100,000 = 120,000 token 相当と数える | (2.0 − 0.05) × 100,000 = 195,000 token 相当 |

これらの誤りのきっかけになる応答は、実際の記録にある。2026-11-24 に、このマシンの会話の記録（`~/.claude/projects/` の下の 8,188 ファイル）を数えた。Claude Code が API の失敗などのときに自分で作る応答（合成応答。モデルを呼んでいない）を除き、同じ応答の複数の行は 1 つに数えた。表が示すのはきっかけの件数で、誤りが実際に起きた回数ではない。

- 誤り 1 のきっかけ: 書き込みが両方 0 の応答。メインの会話で 140,647 応答のうち 84（約 0.06%）とまれである。誤りになるのは、その応答の hook と前の応答の hook の追い越しが重なったときだけである。それでも、起きるとその会話は起こされなくなるので、実装の前に直す
- 誤り 2・3 のきっかけ: 同じ会話の中で寿命が 5 分と 1 時間の間で切り替わること。メインの会話で 100 回あった

## 何を足すか・変えるか

| | 今の設計 | 直した後 |
| --- | --- | --- |
| 書き込みが両方 0 の応答の寿命 | ロックの外で読んだ状態の寿命で補う | ロックの中で読んだ最新の状態の寿命で補う。一度分かった寿命が「分からない」へ戻らない |
| 寿命がまだ 1 度も分かっていない応答 | 起こさないとだけ決まっている。待ちの始まりで起こす回数の上限と倍率を計算できないときに、どう振る舞うかが決まっていない | 起こさず、寿命の分からない値で上限も費用も計算しない。寿命が分かった応答から、起こす対象に戻る |
| 起こした応答の費用 | 書き込みの合計に 1 つの倍率を掛ける | 1 時間の書き込みと 5 分の書き込みを別々に合計し、それぞれの倍率を掛けて足す |
| 避けた書き直しの費用 | 量と寿命が別の応答から来うる | 量と同じ応答（待ちが終わる直前の応答）の寿命の倍率で数える |

## なぜ困るか

- **待つ子を起こせなくなる。** 寿命が「分からない」へ戻ると起こす時点を決められず、待ちが終わった応答で文脈の全体を書き直す。500,000 token に近い文脈なら約 1,000,000 token 相当になり、#4068 が防ぐはずの費用が残る
- **閾値を誤った値で見直す。** 起こす応答 1 回の費用と避けた書き直しは、余白・起こす費用・起こす回数の上限を見直す材料である。上の例では、起床の費用を 1.6 倍に、避けた書き直しを約 0.62 倍に数える。どちらも「起こすのは割に合わない」側へ傾く
- **実装の後では直しが大きい。** 起こす記録の項目が変わるので、実装してから直すと、溜まった記録を捨てるか変換することになる

## 目的

- 待つ子の寿命が、並んで動く hook の順序に依らず、最新の状態から決まる
- 起こした費用と避けた書き直しが、書き込んだ寿命ごとの値段で数えられ、閾値の見直しに使える
- #4068 を実装する人が、直した設計だけを読んで実装できる

- 前提 3: 1 つの応答の寿命別の書き込みは、その応答の記録の行の項目（`usage.cache_creation` の `ephemeral_1h_input_tokens`・`ephemeral_5m_input_tokens`）から読める。この形は、Claude Code が変えないと約束したものではない。形が変われば読めなくなるので、そのときは費用を推し量らずに集計から外す（受け入れ条件 8）

## 受け入れ条件

この節の語の意味は次のとおりである。

- 「寿命別の書き込み」: 応答の記録が持つ、1 時間のキャッシュと 5 分のキャッシュへの書き込みの token
- 「状態」: 会話ごとの起こす状態
- 「ロック」: 子を止めるロック（#4068 の設計が状態の読み書きに使うもの。「前に知っておくこと」）
- 「起こした応答」: 起こす文から始まり、次の入力までに行われたモデルの呼び出しの全部

- [ ] 1. 寿命別の書き込みが両方 0 の応答の寿命は、ロックの中で読んだ状態の寿命になる。後の応答の hook が状態（寿命は不明）を読んだ後、ロックを取る前に、先の応答の hook が寿命 1 時間の待ちを始める順で動かすと、後の hook の後も状態の寿命は 1 時間のままで、その応答の起こす時点は 1 時間の寿命から決まる
- [ ] 2. 寿命別の書き込みのどちらかが正の応答の寿命は、状態の寿命に依らず、その応答の書き込みで決まる（1 時間が正なら 1 時間、1 時間が 0 で 5 分が正なら 5 分）。状態の寿命が 5 分で応答が 1 時間へ書けば、応答の後の状態は 1 時間になる
- [ ] 3. 状態に寿命が一度記録された後は、寿命別の書き込みが両方 0 の応答で、状態の寿命が不明に戻ることは無い
- [ ] 4. 寿命別の書き込みが両方 0 で、ロックの中で読んだ状態にも寿命が無ければ、起こす hook は子を起こさずに終了コード 0 で終わる。起こす回数の上限と費用を、仮の寿命で計算して記録することは無い。同じ会話の後の応答で寿命が分かれば、そこから起こす対象になる
- [ ] 5. 起こした応答の書き込みの費用は、属する全部の呼び出しの 1 時間の書き込みの合計 × 1 時間の倍率と、5 分の書き込みの合計 × 5 分の倍率の和になる。寿命 1 時間の待ちで、起こした応答が 5 分へ 1,000 token だけ書けば 1,250 token 相当、1 回目の呼び出しが 1 時間へ 300・2 回目が 5 分へ 1,000 書けば 1,850 token 相当になる
- [ ] 6. #4068 の受け入れ条件 12 が集計に出す 2 つの中央値（起こす応答 1 回の費用の中央値と、起こした応答 1 回の実費の中央値）は、どちらも書き込みの費用を条件 5 の数え方で出す。この Issue は集計の項目を足さず、数え方だけを決める。読み出しと出力の費用の数え方は #4068 の設計のまま変わらない
- [ ] 7. 起こした応答の最初の呼び出しの寿命別の書き込みが両方 0 でも、起こした応答の結果の行が 1 行記録され、その呼び出しの書き込みの費用は 0 で、当たりの判定は読み出しだけで決まる
- [ ] 8. 起こした応答のどれかの呼び出しで、寿命別の書き込みの項目が欠けている・整数でない・負のとき、または 2 つの和が書き込みの合計の項目と違うときは、その起床の費用を推し量って数えない。その待ちを「避けた書き直し」の集計から外し、#4068 の受け入れ条件 12 の「避けた書き直しの集計から外した待ちの数」に数える
- [ ] 9. 避けた書き直しの費用は、待ちが終わる直前の応答の量に、同じ応答の寿命の書き込みの倍率と、同じ応答のモデルの読み出しの倍率を使って数える。直前の応答が寿命 1 時間・Opus 5.5・100,000 token で、待ちを終えた応答が 5 分へ書いたとき、避けた書き直しの額（起こした費用を差し引く前）は 195,000 token 相当になる（120,000 にならない）
- [ ] 10. 待ちが終わった応答の後に次の待ちが始まるとき、次の待ちの起こす回数の上限は、条件 1〜4 で決めたその応答の寿命で決まる。条件 9 の例の続きで、5 分の寿命で始まる次の待ちでは子を起こさない
- [ ] 11. 起こす記録の起こした応答の行と待ちの終わりの行は、費用を出すのに要る量（起こした応答は寿命別の書き込み）と使った倍率を持つ。記録の後に上限の設定の倍率を変えても、集計が出すその行の費用は変わらない
