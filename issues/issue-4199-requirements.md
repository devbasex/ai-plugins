#4068 の設計（中継の下で待つ子を、プロンプトのキャッシュの寿命の手前で起こす hook）には、キャッシュの寿命の決め方に 1 つ、費用の数え方に 2 つの誤りがある。#4068 の実装の前に設計を直し、寿命を常に最新の状態から決め、費用をその書き込みが実際に使った寿命の倍率で数えるようにする。#4068 の要求と設計を読んだ人に向けて書く。

## 何が起きたか

2026-11-23、#4089（文脈の量の読み手）の設計 Pull Request（ https://github.com/devbasex/ai-plugins/pull/4194 ）の cross-review の 4〜6 ラウンド目で、レビュー担当が #4068 の設計に次の 3 つの誤りを見つけた。#4089 の範囲の外なので、この Issue に分けた。#4068 はまだ実装されていない（main の `2fd9227a4` に、起こす hook も `asyncRewake` の登録も無い）。このまま実装すると、次のように誤る。

キャッシュへの書き込みの値段は、寿命が 1 時間なら入力の 2 倍、5 分なら 1.25 倍である。Claude Code の記録は、応答ごとに 1 時間の書き込みと 5 分の書き込みの token を別々に持つ。

| --- | --- | --- | --- |

## 今の姿

main の `2fd9227a4` で確かめた。直す対象は、マージ済みで未実装の設計である。

- **#4068 の要求**（#4068 の本文）は、寿命を「最後の応答の寿命ごとの書き込み」で決め（受け入れ条件 6）、起こす費用を書き直し 1 回の費用と比べて起こす回数の上限を決め（同 4）、起こした費用と避けた書き直しを記録から集計する（同 11・12）
- **寿命の補い**（[#4068 の詳細設計](https://github.com/devbasex/ai-plugins/blob/2fd9227a475a95ef1f85f15062d73fa5ba344bc4/issues/issue-4068-design-detail.md) の `last_turn` と「処理の手順」の 2〜4）: 書き込みが両方 0 なら、引数の `known_ttl` を寿命にする。`known_ttl` は、ロックを取らずに読んだ起こす状態の寿命である。その後、子を止めるロックの中で状態を更新する（`_settle`）が、寿命は補い直さない
- **起床の費用**（同じ文書の「起こす記録」と「集計」）: 起こした応答に属する全呼び出しの書き込みを 1 つに合計し（`cache_write`）、1 つの書き込みの倍率（`w`）を掛ける。起床の最初の呼び出しの書き込みが両方 0 のときに、どの寿命を使うかは決まっていない
- **待ちの終わりの費用**（同じ文書の `wait_end` と「避けた書き直し」）: 量（`tokens`）は待ちが終わる直前の応答のもの、寿命と倍率（`ttl`・`w`）はどの応答のものかが決まっていない
- **#4089 の設計**（マージ済み・未実装。[詳細設計の「#4068 との受け渡し」](https://github.com/devbasex/ai-plugins/blob/2fd9227a475a95ef1f85f15062d73fa5ba344bc4/issues/issue-4089-design-detail.md)）は、書き込みが両方 0 のとき `known_ttl` を使うと書き、寿命の補いの見直しをこの Issue に任せている

## 何を足すか・変えるか

| | 今の設計 | 直した後 |
| --- | --- | --- |
| 書き込みが両方 0 の応答の寿命 | ロックの外で読んだ状態の寿命で補う | ロックの中で読んだ最新の状態の寿命で補う。一度分かった寿命が「分からない」へ戻らない |
| 寿命がまだ 1 度も分かっていない応答 | 起こさないとだけ決まっている。待ちの始まりで上限と倍率を決められず、その先が決まっていない | 起こさず、寿命の分からない値で上限も費用も計算しない。寿命が分かった応答から、起こす対象に戻る |
| 起こした応答の費用 | 書き込みの合計に 1 つの倍率を掛ける | 1 時間の書き込みと 5 分の書き込みを別々に合計し、それぞれの倍率を掛けて足す |
| 避けた書き直しの費用 | 量と寿命が別の応答から来うる | 量と同じ応答（待ちが終わる直前の応答）の寿命の倍率で数える |

## なぜ困るか

- **待つ子を起こせなくなる。** 寿命が「分からない」へ戻ると起こす時点を決められず、待ちが明けた応答で文脈の全体を書き直す。500,000 token に近い文脈なら約 1,000,000 token 相当になり、#4068 が防ぐはずの費用が残る
- **閾値を誤った値で見直す。** 起こす応答 1 回の費用と避けた書き直しは、余白・起こす費用・起こす回数の上限を見直す材料である。上の例では、起床の費用を 1.6 倍に、避けた書き直しを約 0.62 倍に数える。どちらも「起こすのは割に合わない」側へ傾く
- **実装の後では直しが大きい。** 起こす記録の項目が変わるので、実装してから直すと、溜まった記録を捨てるか変換することになる

## 目的

- 待つ子の寿命が、並んで動く hook の順序に依らず、最新の状態から決まる
- 起こした費用と避けた書き直しが、書き込んだ寿命ごとの値段で数えられ、閾値の見直しに使える
- #4068 を実装する人が、直した設計だけを読んで実装できる

## 対象範囲

含む:
- 起こす hook が、寿命別の書き込みが両方 0 の応答の寿命を決める規則（ロックの中の最新の状態で補う・分からないときの扱い）
- 起こした応答の書き込みの費用の数え方と、起こす記録・集計が持つ項目
- 待ちの終わりの、避けた書き直しの費用の数え方
- 上の 3 つを #4068 の設計書・詳細設計書と、#4089 の詳細設計書の「#4068 との受け渡し」へ反映し、#4068 の実装で満たすこと

含まない:
- 起こす間隔・起こす回数の上限の式・値（#4068 の受け入れ条件 1・4・13。式の `w` は待ちの始まりの寿命の倍率のままにする）
- 当たりの判定（#4068 の受け入れ条件 8）と、待ちの始まり・終わりを見分ける規則
- 読み出しと出力の倍率の値、定額のプランの週の利用上限との対応
- 起こす記録の壊れた行の集計での扱い（#4068 の設計の「読めない行は数える」のまま）
- 再利用できる supervisor・conductor の待機とサブエージェントのキャッシュ（#4071）
- 文脈の量を読む関数そのもの（#4089）

## 前提

- 前提 1: #4068 は、直した設計がマージされた後に実装する。#4068 とこの Issue は同じスプリントで設計・実装する
- 前提 2: キャッシュの寿命は 1 時間と 5 分の 2 つだけである（公式の文書。実測でもほかの寿命は無い）。書き込みの倍率は、上限の設定が寿命ごとに持つ値（#4068 の受け入れ条件 13。既定で 1 時間 2.0・5 分 1.25）だけを使う
- 前提 3: 1 つの応答の寿命別の書き込みは、その応答の記録の行の項目（`usage.cache_creation` の `ephemeral_1h_input_tokens`・`ephemeral_5m_input_tokens`）から読める。この形は Claude Code の公開のコントラクトではない
- 前提 4: 配ったバージョンに起こす記録は無いので、記録の項目を変えても互換の経路を持たない（MVV Value 4）

## 受け入れ条件

このセクションで「寿命別の書き込み」は、応答の記録が持つ 1 時間のキャッシュと 5 分のキャッシュへの書き込みの token を指す。「状態」は会話ごとの起こす状態、「ロック」は子を止めるロック（#4068 の設計が状態の読み書きに使うもの）を指す。「起こした応答」は、起こす文か引継ぎへ切り替える文から始まり、次の入力までに行われたモデルの呼び出しの全部を指す。

- [ ] 1. 寿命別の書き込みが両方 0 の応答の寿命は、ロックの中で読んだ状態の寿命になる。後の応答の hook が状態（寿命は不明）を読んだ後、ロックを取る前に、先の応答の hook が寿命 1 時間の待ちを始める順で動かすと、後の hook の後も状態の寿命は 1 時間のままで、その応答の起こす時点は 1 時間の寿命から決まる
- [ ] 2. 寿命別の書き込みのどちらかが正の応答の寿命は、状態の寿命に依らず、その応答の書き込みで決まる（1 時間が正なら 1 時間、1 時間が 0 で 5 分が正なら 5 分）。状態の寿命が 5 分で応答が 1 時間へ書けば、応答の後の状態は 1 時間になる
- [ ] 3. 状態に寿命が一度記録された後は、寿命別の書き込みが両方 0 の応答で、状態の寿命が不明に戻ることは無い
- [ ] 4. 寿命別の書き込みが両方 0 で、ロックの中で読んだ状態にも寿命が無ければ、起こす hook は子を起こさずに終了コード 0 で終わる。起こす回数の上限と費用を、仮の寿命で計算して記録することは無い。同じ会話の後の応答で寿命が分かれば、そこから起こす対象になる
- [ ] 5. 起こした応答の書き込みの費用は、属する全部の呼び出しの 1 時間の書き込みの合計 × 1 時間の倍率と、5 分の書き込みの合計 × 5 分の倍率の和になる。寿命 1 時間の待ちで、起こした応答が 5 分へ 1,000 token だけ書けば 1,250 token 相当、1 回目の呼び出しが 1 時間へ 300・2 回目が 5 分へ 1,000 書けば 1,850 token 相当になる
- [ ] 6. 起こす応答 1 回の費用の中央値（#4068 の値 `d` の見直しに使う値）と、起こした応答の実費の中央値の両方が、条件 5 の書き込みの費用を使う。読み出しと出力の費用の数え方は #4068 の設計のまま変わらない
- [ ] 7. 起こした応答の最初の呼び出しの寿命別の書き込みが両方 0 でも、起こした応答の結果の行が 1 行記録され、その呼び出しの書き込みの費用は 0 で、当たりの判定は読み出しだけで決まる
- [ ] 8. 起こした応答のどれかの呼び出しで、寿命別の書き込みの項目が欠けている・整数でない・負のとき、または 2 つの和が書き込みの合計の項目と違うときは、その起床の費用を推し量って数えず、その待ちを避けた書き直しの集計から外し、外した数が集計の結果に出る
- [ ] 9. 避けた書き直しの費用は、待ちが終わる直前の応答の量に、同じ応答の寿命の書き込みの倍率と、同じ応答のモデルの読み出しの倍率を使って数える。直前の応答が寿命 1 時間・Opus 5.5・100,000 token で、待ちを終えた応答が 5 分へ書いたとき、起床の実費を引く前の額は 195,000 token 相当になる（120,000 にならない）
- [ ] 10. 待ちが終わった応答の後に次の待ちが始まるとき、次の待ちの起こす回数の上限は、条件 1〜4 で決めたその応答の寿命で決まる。条件 9 の例の続きで、5 分の寿命で始まる次の待ちでは子を起こさない
- [ ] 11. 起こす記録の起こした応答の行と待ちの終わりの行は、費用を出すのに要る量（起こした応答は寿命別の書き込み）と使った倍率を持つ。記録の後に上限の設定の倍率を変えても、集計が出すその行の費用は変わらない
- [ ] 12. #4068 の受け入れ条件 1〜14 は文言のまま成り立つ。例えば、寿命 1 時間・Opus 5.5・400,000 token・`d` 2,000 で始まる待ちの起こす回数の上限は 35 のままである
      前提の確認: 式 `floor((2.0 − 0.05) × 400000 / (0.05 × 400000 + 2000))` を計算し、35（780,000 ÷ 22,000 = 35.45）になった（2026-11-24）
- [ ] 13. #4068 の設計書と詳細設計書、#4089 の詳細設計書の「#4068 との受け渡し」が条件 1〜11 の規則を持ち、互いに食い違わない。この反映は #4068 の実装の Pull Request より前にマージされる（設計レビューで確かめる）
- [ ] 14. 条件 1〜11 を、時計を差し替え、実際に待たずに、条件 1 の順（ロックの外の読み取りと別の hook の書き込みの前後）を再現して確かめるテストがある。`.md` の文言を確かめるテストにしない

> 1. **寿命の補いが排他の外の値を使う。** `last_turn` の引数 `known_ttl` は、`rewake.run` の手順 2〜3 が排他の外で読んだ状態の `last.ttl` である。応答の寿命別の書き込みが両方 0 の Stop が古い None を読んだ後、先行の Stop が排他の中で `1h` の待ちを始めると、新しい Stop は None のまま `_settle` へ進み、`last.ttl` を None に戻しうる
> 2. **起床の費用を 1 つの寿命の倍率で数える。** `wake_result` は `cache_write`（起床に属する全呼び出しの合計）に 1 つの倍率 `w` を掛ける。起床の後の呼び出しが待ちと違う寿命（例 待ちは 1 時間、起床後に 5 分のキャッシュへ 1,000 token）へ書くと、1,250 token 相当を 2,000 token 相当と数える
> 3. **待ちの終わりの寿命の取り方。** `wait_end` の `tokens` は待ちが明ける直前の量なのに、寿命を待ちを明けた今回の応答から取ると、避けた書き直しを直前と違う倍率（例 1 時間のキャッシュを 5 分の倍率）で数える
>
> ## 期待する結果
>
> - 寿命の補いを、排他の中で読んだ最新の状態で行う
> - 起床と待ちの終わりの費用を、寿命ごとの書き込みと、その量の寿命の倍率で数える
> - #4068 の実装の前に設計へ反映する
