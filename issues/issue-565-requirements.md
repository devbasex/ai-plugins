# #565: 進行の記録の値に制御演算子が密着すると、通過工程の控えが積まれない

設計は [issue-565-design.md](issue-565-design.md) にある。この文書は「何を満たすか」だけを扱う。

## 依頼（原文）

> 進行の記録を実行しても通過工程の控えが 1 件も積まれない（hook が発火していない）
>
> 1 つのセッションの間、進行の記録を 5 回実行したのに、通過工程の控えが 1 件も積まれなかった。
> （中略）**積む側の実装ではなく、hook が発火していない。**

（issue #565 の本文。原因は「特定できていない」と書かれている）

## 原因（調べて分かったこと）

**hook は発火している。値の読み取りで捨てている。** 進行の記録のコマンドの値の直後に `;` が
付いていると、控えは積まれない。

```bash
bash plugins/ndf/scripts/projects-sync.sh 565 stage "要求と受け入れ条件"; echo "exit=$?"
```

`wf_split`（`workflow-common.sh`）は空白とタブだけで語を区切る。引用符を解いた後の値は
`要求と受け入れ条件;` になり、`wf_is_stage` が工程名ではないと判定して、何も出さずに
終了コード 0 で返る。issue の手動の再現が通ったのは、流した本文の末尾に `;` が無かったためである。

裏付けと、退けた候補（bypass permissions モード / Skill 経由の登録 / Claude Code の版）は
設計文書の「原因の特定」にある。

## 目的

- 進行の記録を普通のシェルの書き方で実行したとき、通過工程の控えが積まれる
- 設計 Pull Request のマージを承認に縛る関門（#266）が、同じ書き方で外れない

## 前提

- 前提 1: hook の登録と発火は Claude Code 2.1.270 で動いている（対話・非対話、bypass
  permissions、`/goal` 経由のいずれでも実測で控えが積まれた）。hook の登録の仕組みは変えない
- 前提 2: 観測の対象は `projects-sync.sh` だけである（`stage-completeness.md` の契約）。
  `progress-record.sh` は観測しない。issue 本文の「5 回」は会話 `a27ffb35` の実行を要約した
  一覧で、`progress-record.sh` の 2 件と `projects-sync.sh` の 3 件を含む。`progress-record.sh`
  の 2 件が積まれなかったのは、この契約どおりである。設計文書の表の「5 件」は会話記録から
  拾った `projects-sync.sh` の実行の件数で、別の数である
- 前提 3: hook が受け取るのは書かれたままの本文で、展開はしない（`wf_split` の既存の方針）

## 対象範囲

含む:

- 語の分割で、引用の外にある制御演算子（`;` `&` `&&` `|` `||` `(` `)` と改行）をコマンドの
  区切りとして扱う
- 区切りを受け取る 3 つの読み手（進行の記録・マージの判定・Pull Request 作成の本文）が、
  1 つ目のコマンドの終わりで読むのを止める
- `stage-completeness.md` に、どの書き方の記録を読むかを 1 段落足す

含まない:

- 1 回の実行に並べた 2 件目以降の記録を積むこと（#487）
- 課題番号を変数で書いた記録を積むこと（#487）
- 1 回の実行に並べた 2 つ目のマージを判定すること（#581）
- ヒアドキュメントやコメントの中の記録の例を読み飛ばすこと（#580）
- 値を捨てたことを案内として表に出すこと（#459 の工程名の黙った破棄と同じ出口になるため、
  そちらで扱う）
- 本文と控えの食い違いに気づく仕組み（#452）
- 引用符の中のバックスラッシュのエスケープを解くこと（現状と同じ扱いのまま）

## 用語

| 用語 | 意味 |
| --- | --- |
| 控え | `${XDG_STATE_HOME:-$HOME/.local/state}/ndf/stages/<所有者>__<リポジトリ>__<課題番号>.json` |
| 進行の記録 | `projects-sync.sh <課題番号> <キー> <値>` の実行 |
| 制御演算子 | 引用の外にある `;` `&` `&&` `|` `||` `(` `)` と、本文の途中の改行（最後の改行は含まない）。`2>&1` `>&2` `&>` の `&` はリダイレクトの一部で、区切りではない |
| 区切り | `wf_split` が出す空の語。コマンドの境目を表す |

## 受け入れ条件

進行の記録:

- [ ] AC1: 値の直後に `;` を密着させた記録（`... stage "設計"; echo "exit=$?"`）で、控えの
  `stages` に `設計` が入る
- [ ] AC2: 値の直後に `&&` `||` `|` `)` を密着させた記録と、引用符を付けない値へ密着させた
  記録（`... stage 設計&&echo`）で、区切りの手前までの値（例: `設計`）が控えに入る
- [ ] AC3: 先頭に `cd <dir>;` などの別のコマンドを置いた記録（`cd /work/ai-plugins; bash
  plugins/ndf/scripts/projects-sync.sh 565 stage "要求と受け入れ条件"; echo "exit=$?"`）で、
  控えに値が入る
- [ ] AC4: 区切りより前に 3 語そろわない記録（`projects-sync.sh 161 stage; echo 設計`）は
  積まない
- [ ] AC5: いま積まれている書き方（`2>&1 | tail -3` を空白で続けた形、`"$SCRIPTS/projects-sync.sh"`、
  末尾に何も無い形）で、控えの内容が変わる前と同じになる

マージの判定:

- [ ] AC6: `gh pr merge 268; echo ok` で、番号 268 の Pull Request を判定する（ブランチからの
  引き当てへ回らない）
- [ ] AC7: `cd x&&gh pr merge 268` と `cd x;gh pr merge 268` と `true|gh pr merge 268` を
  マージとして判定し、印の無い設計 Pull Request なら拒否する
- [ ] AC8: `gh pr merge; echo 268` は番号の無いマージとして扱い、268 を番号に取らない

Pull Request 作成の本文:

- [ ] AC9: `gh pr create --body "Closes #161"; echo ok` で、閉じる語が指す #161 の控えに
  `Pull Request` が入る
- [ ] AC10: `gh pr create --title t; echo --body "Closes #161"` では、#161 の控えに何も入らない

退行しないこと:

- [ ] AC11: `2>&1` `>&2` `&>/dev/null` を含む本文で、リダイレクトの `&` が語を割らない
  （既存のマージの判定と記録のテストが通る）
- [ ] AC12: `plugins/ndf/skills/development-workflow/tests` の既存テストがすべて通る

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 36KB の本文で `wf_split` が 0.1 秒以内に終わる（変更前の実測は 0.012 秒。hook の制限時間は 10 秒） |
| 運用・保守性 | 分割は awk の 1 回の起動のまま保つ。bash の文字取り出しへ戻さない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない。`projects-sync.sh` と控えの JSON と `stage-check.sh` の契約はそのまま |
| `wf_split` の出力 | 空の語（区切り）が加わる。いまは空の語を出さないため、既存の語と衝突しない |
| 利用者の手順 | 変わらない。記録のコマンドの書き方に制約を足さない |
| 配布物 | `plugins/ndf/skills/development-workflow/` の中だけ。Claude Code 以外のランタイムは frontmatter の hook を読まないため影響しない |
