## 目的

- 本番の配布（main 宛の PR）と develop 宛の PR の継続的統合が、外部の CLI の版上げだけで落ちない状態にする。配布の可否は、こちらの変更とリポジトリに書いた版だけで決まる
- 外部の CLI の新しい版との食い違いは、配布の経路の外で先に見つかり、課題か PR として残る

## 前提

- 前提 0: この仕様では、develop・main 宛の Pull Request と develop・main への push で走る継続的統合（本番の配布の可否を決めるもの）を「配布の経路」と呼び、4 ランタイムの CLI を最新で入れて走らせる、配布の経路と別のスモークを「最新の版のスモーク」と呼ぶ。どちらもこの課題の中だけの言い方で、用語集へは足さない
- 前提 1: 4 ランタイムとも、版を指定して CLI を取れる。2026-10-13 に次を実測した
  - claude: npm の `@anthropic-ai/claude-code@<版>`
  - codex: インストーラの `--release <版>`（`CODEX_RELEASE` でも渡せる）
  - kiro: `https://prod.download.cli.kiro.dev/stable/<版>/kirocli-x86_64-linux.tar.xz` が 2.30.0・2.29.0 とも 200 を返す（インストーラ自体は `--channel` だけを受け、版を受けない）
  - agy: インストーラは最新の manifest だけを読む。manifest の `url` は `.../antigravity-cli/<版>-<ビルド番号>/linux-x64/cli_linux_x64.tar.gz` の形で、版ごとの取得先と `sha512` が載る
- 前提 2: 版を固定する対象は 4 ランタイムの CLI だけである。基底の像（`Containerfile.base` の `node:22-bookworm-slim` と apt のパッケージ）は今回の失敗の原因でないため固定しない
- 前提 3: 固定した版は、固定を入れる時点で配布の経路のスモークが 4 ランタイムとも通る版にする（入れた時点の最新でなくてよい）
- 前提 4: 最新の版のスモークは、ai-plugins の継続的統合の中だけの仕組みであり、NDF の配布物（`plugins/`）は変えない
- 前提 5: 最新の版のスモークの起動は、定期の起動に加えて手で起動できる形にする（workflow_dispatch）。起動の間隔は設計が決める
- 前提 6: 同じ Containerfile を使う手元の実行（`scripts/runtime-smoke-test.sh`）と、認証つきのスモーク（`runtime-plugin-authenticated-smoke.yml`）も、固定した版を入れる側に入る

## 対象範囲

含む:
- 配布の経路のスモーク（`runtime-plugin-smoke.yml` の `runtime-smoke (claude|codex|kiro|agy)`）が入れる 4 ランタイムの CLI の版の固定
- 版の書き場所（リポジトリの中の 1 か所以上。ランタイムごとに 1 つの版）
- 最新の版でスモークを走らせる、配布の経路と別の workflow と、落ちたことを課題か PR で知らせる仕組み
- 版を上げる手順の文書（`tests/runtime-smoke/README.md` の「像はランタイムを版の固定なしで導入する」の記述の更新を含む）

含まない:
- 基底の像と OS のパッケージの版の固定（前提 2）
- `|| true` で取得の失敗を読み飛ばす今の扱い（agy・kiro）を変えるか（未決 2）
- ランタイムの新しい版へ合わせるアダプタ・検査の修正（最新の版のスモークが見つけた後に、別の課題か PR で扱う）
- 必須のチェックの名前の変更（ruleset が待つ `runtime-smoke (<ランタイム>)` は変えない）
- NDF の配布物と、利用者の環境へ入る CLI の版の扱い

## 受け入れ条件

- [ ] 3. 書いた版より新しい版が外部に出ても、配布の経路のスモークが入れる CLI の版は変わらない（Containerfile か取得の手順が `latest` や版の無い取得先を使わない）
- [ ] 4. 固定を入れた PR で、配布の経路のスモークが 4 ランタイムとも通る
- [ ] 5. 最新の版のスモークが、配布の経路と別の workflow として定期に走り、手でも起動できる

- [ ] 7. 最新の版のスモークは、4 ランタイムとも書いた版ではなくその時点の最新の CLI を入れ、入れた版を成果物か実行ログに残す
- [ ] 8. 最新の版のスモークが落ちると、落ちたランタイム・入れた版・実行の URL を書いた課題か PR が GitHub にできる
- [ ] 9. 同じ失敗が続いても、課題か PR は 1 件に集まる（開いている同じものがあれば新しく作らない）
- [ ] 10. 版を上げる手順（どのファイルのどこを書き換えるか・上げた後に何で確かめるか）が `tests/runtime-smoke/README.md` に書いてあり、版の固定なしで導入すると書いた記述が残っていない
