## 目的

- 起票者が文書・コード・経緯から推して足した条件が、利用者の決定と見分けられる形で課題の本文と仕様のコピーに残り、承認ゲート 1 で利用者が確かめてから設計・実装へ進む。本番の直前（承認ゲート 2）で初めて退けられて、開発版の出し直しと修正 PR が増えることを防ぐ
- 承認ゲートで利用者が差し戻した回数が、MVV 判定の有無に関わらず振り返りで数えられる

## 前提

- 前提 1: 起票者の推定かどうかは、起票者（課題を書いた AI）が書くときに自分で区別する。書き手を機械で判定しない（課題の作成者はどれも同じ GitHub アカウントで、作成者の欄では利用者と AI を見分けられない）
- 前提 2: 利用者の指示の原文は、利用者が会話で書いた文と、利用者が自分で書いた課題の本文である。AI が書いた起動指示・起票の本文・振り返りの記録は、利用者の指示を引用していない限り原文に当たらない（#1658 の「依頼（原文）」は conductor の起動指示だった）
- 前提 3: 承認ゲート 1 で利用者が設計 PR を承認したとき、承認資料に並んだ起票者の推定は利用者が確かめた条件として扱う。差し戻された推定は、要求の「変更の途中で要求が変わったとき」の形（消さずに取り消し線と理由・日付）で書き換える
- 前提 4: `pace: auto` / `fast` の自動の通過の条件は変えない。起票者の推定が 1 件以上あることを、自動の通過を止める条件にしない（足すかは未決の 1）
- 前提 5: 承認ゲートの差し戻しは、覆し（承認ゲートで人の答えが直前の MVV 判定と食い違ったこと）とは別の数として出す。覆しの意味・件数・改訂の兆候の閾値は変えない（語は 1 語 1 意味。MVV 判定を持たない `pace: normal` の差し戻しを覆しに足すと、覆しの意味が変わる）
- 前提 6: 2026-10-10 の実測で、`~/.local/state/ndf/` の下に `gates` か `rejections` を持つ状態ファイルは 0 件、`project-mvv-signals.jsonl` は存在しない（`supervise.py` のスプリントのマニフェスト 14 件はどれも承認ゲートの記録を持たない）。`sprint-state.py gate --outcome rejected` の記録の経路はあるが、`pace: normal` の実際の運用では打たれていない。差し戻しを数えるには、`pace: normal` で利用者が承認ゲートに答える経路で記録が残る必要がある
- 前提 7: 既に起票された課題（起票者の推定の節を持たない本文）は書き直さない。要求の工程が本文を読むときに、節が無ければ起票者の推定を本文から拾い出して仕様に書く

## 対象範囲

含む:
- 範囲外の課題の起票（`out-of-scope`・`retrospective` が呼ぶ `issue-file.py create`）の本文に「起票者の推定」の節を置き、無ければ起票を止めること
- 要求の仕様（`requirements-design` の雛形）で、「依頼（原文）」の書き手を示すことと、「起票者の推定」の節を置くこと
- 承認ゲート 1 の承認資料に「起票者の推定」の行を足すこと
- 承認ゲートの差し戻しを、`pace` と MVV 判定の有無に関わらず記録に残すことと、振り返りでその件数を承認ゲートごとに出すこと
- 用語集に「起票者の推定」「承認ゲートの差し戻し」を足すこと

含まない:
- 起票済みの課題の本文を書き直すこと（前提 7）
- 書き手を機械で判定すること（前提 1）
- `pace: auto` / `fast` の自動の通過の条件を変えること（前提 4）
- 覆しの意味・`project-mvv.py signals` の件数と閾値を変えること（前提 5）
- 承認ゲート 2 の承認資料に起票者の推定を並べること（ゲート 1 で確かめた後の条件は利用者の決定として扱う）
- 新しい承認ゲートや確認の工程を足すこと（承認ゲートは設計と本番の配布の 2 回だけ）

## 起票時の記録

### 何を見つけたか

**課題を起票するときに起票者（conductor）が足した条件が、利用者の決めた条件と見分けられないまま要求・設計・実装・開発版まで進み、本番の承認ゲート 2 で初めて利用者に退けられた。**

- #1658 の題「閉じた・マージ済み・**Draft でない** PR にも提案から push まで進む」の Draft の条件は、利用者の指示ではなく、`cross-refactoring/SKILL.md` の前提の行「対象の Pull Request が Draft で開いている」（4c267d070 で直す前の行）から起票者が止める条件へ読み替えて足したものだった
- 要求（`issues/issue-1658-requirements.md`）・設計 PR #1815・承認ゲート 1・実装 PR #1821・スプリント PR #1825・開発版 10.17.66-dev.1 のどこでも、この条件が「起票者が足したもの」とは示されなかった
- 承認ゲート 2（2026-10-07）で利用者が「Draft でない PR の cross-refactoring を止める必要はない」と差し戻した。修正 PR #1827・CHANGELOG の直し PR #1829 を出し、開発版を dev.1 → dev.2 → dev.3 と 3 回出した
- 差し戻しは `project-mvv.py signals` の「覆し」に数えられない（2026-10-07 の実行で 覆し 0 件）。`pace: normal` の承認ゲートで人が退けた中身は、MVV 判定の記録を持たないためである

### どこで見つけたか

スプリント m1743 の振り返り（PR #1825）。修正の経緯は PR #1827 の本文にある。

### なぜこの変更の範囲外なのか

スプリント m1743 の受け入れ条件は cross-refactoring の振る舞いであり、起票と要求の工程の手順は含まない。根拠: Value 2（承認を求めるときは判断の材料を集めてから求める）・Value 7（MVV 版 2）。

### 直さないと何が起きるか

起票者が Skill の文面などから推して足した条件が、承認ゲート 1 で利用者の決定と同じ重みで通り、本番の直前で差し戻されて開発版の出し直しと修正 PR が増える。差し戻しが「覆し」に数えられないため、MVV の見直しの兆候にも出ない。

### 依頼（起票者の推定。上の S1・S2）

- 起票・要求の工程で、利用者の指示の原文に無く起票者が足した条件を「起票者の推定」として区別して書く
- 承認ゲート 1 の承認資料に、その条件を「利用者がまだ決めていない条件」として並べ、承認で確かめる

### 受け入れ条件（案）（起票者の推定。上の S1〜S3）
