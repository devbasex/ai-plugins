## 目的

Factory（Neural Development Factory）の実行ジョブで、`/ndf:development-workflow #<課題>` の conductor が人へ問い返さずに工程を進め、承認ゲート・終わり・続けられないときに、Factory が読める決まった形の報告を最後の応答に書いて区間を終えるようにする。

- 実行ジョブは、環境変数 `NDF_FACTORY_RUN` がある `claude -p` の実行である（以下「人のいない実行」）
- 人のいない実行では `AskUserQuestion` が使えず、利用者は応答を読まない。問いの文で区間を終えると、Factory はその区間を失敗として扱う

## 事象

人のいない実行で、conductor がモード判定の後に「確認したいこと」を文で並べ、「進めて」と返してもらえれば続けると書いて区間を終える。最後の応答に `- 結果:` の行が無い。

試しのリポジトリで、コードとテストを足す小さな課題（標準のモード）を流した（NDF 10.27.61）。conductor は手順 0 とモード判定までを済ませ、次のように書いて終えた。

```text
## 確認したいこと

1. `.ndf/` をコミットするか。…
2. このまま「次のコマンド」でスプリント `wc` を流してよいか。…

「進めて」と返してもらえれば、1 のコミットの扱いも含めて続けます。
```

もう 1 件の課題（外部の系を操作する手動確認）でも、conductor は「どちらで実行するか決まれば進めます」と書いて終えた。Factory の実行で承認ゲートまで届いた例はまだ無い。

NDF の現状（2026-11-13、ブランチ `design/issue-3242` で確認）:

| 確かめたこと | 結果 |
| --- | --- |
| `NDF_FACTORY_RUN` を読む箇所 | 並列の計画を断る判定（`plugins/ndf/scripts/lib/parallel_guard.py`・`parallel_external_cli.py`）と、動く場所の判定（`plugins/ndf/scripts/lib/run_environment.py`）だけ。`grep -rn NDF_FACTORY_RUN plugins/ndf` の当たりはこの 3 ファイルと、テスト・参照文書・契約の一覧だけで、conductor の止まり方を変える箇所は無い |
| 区分の無い問いを止める仕組み | `AskUserQuestion` の入力だけを hook が見る（`plugins/ndf/skills/development-workflow/references/asking.md` の「区分」）。応答の文に書いた問いは止まらない |
| 最後の `- 結果:` の行の読み方 | `plugins/ndf/contracts/forms/ndf-next-block.json` の規則が「応答の文の最後の『- 結果:』の行の値」を定め、Factory のランナーのテストも同じ例の組を読む |
| conductor の最後の応答の形 | supervisor → conductor のフェーズレポートの形（`references/agent-layers.md` の「報告の形」）はあるが、conductor が区間を終えるときの形は無い |

## 期待する結果

人のいない実行では、承認ゲートの外の区分の無い問いを AI が決めて記録し、承認ゲートまで進む。承認ゲートでは `- 結果: 判断が要る`、終わりでは `- 結果: 完了`、続けられなければ `- 結果: できなかった` を最後の応答に書く。

## 再現手順

1. `.ndf/` を持たない試しのリポジトリに、コードとテストを足す小さな課題を 1 件置く
2. そのリポジトリの根で `NDF_FACTORY_RUN=1 claude -p "/ndf:development-workflow #<課題>" --output-format stream-json --verbose --permission-mode acceptEdits` を打つ
3. 最後の `result` の文に `- 結果:` の行が無く、利用者への問いで終わっている

## 環境

- NDF 10.27.61（マーケットプレイスのコピーから導入）
- Factory のランナーのコンテナ（Debian bookworm、Node 24、jq・git・gh・python3 あり）。モデルは Claude Sonnet 5.5
- 人はその場にいない（`AskUserQuestion` が使えない）

## 影響

| 対象 | 影響 |
| --- | --- |
| 利用者 | Factory の実行が設計承認ゲートに届かず、どの課題でも最初の区間で失敗になる。Factory から NDF の開発を回せない |
| 公開インタフェース | 変わる。最後の応答の結果の行（値と位置・添えるもの）を、Factory が読む契約として新たに定める。既存の `ndf-next` のブロックの読み方の規則とは互換を保つ |
| データ | 変わらない。問いを AI が決めた記録は既存の `ask.jsonl` の形で追記する |
| 既存の振る舞い | 人のいない実行の conductor だけが変わる。`NDF_FACTORY_RUN` の無い実行は変えない |

## 前提

- 前提 1: Factory のランナーは、conductor の最後の応答の文の**最後の** `- 結果:` の行の値で区間の結果を決める（`判断が要る` → 承認ゲートで止まった、`完了` → 終わった、`できなかった` → 止まった、行が無い → 失敗）。値の外の行（承認資料・理由・人に頼むこと）は人が読むためのもので、ランナーは読まない。ランナーの側は別のリポジトリにあり、この課題では読み方を確かめていない（起票者の記述による）
- 前提 2: 「最後の `- 結果:` の行」の定義は、既存の `ndf-next` のブロックの規則（`plugins/ndf/contracts/forms/ndf-next-block.json`）と同じ読み方にする。2 つの定義を持たない
- 前提 3: 承認ゲートで区間を終えた後の再開は、Factory が承認の答えで次の実行ジョブを始め、同じ `/ndf:development-workflow #<課題>` で課題の進捗記録から続ける（用語集の「実行ジョブ」の定義）。再開の振る舞いはこの課題で変えない
- 前提 4: 人のいない実行は `NDF_FACTORY_RUN` が空でない値で設定されていることで判定する。並列の計画を断る判定（`parallel_guard.py` の `FACTORY_ENVS`）と同じ環境変数を使う
- 前提 5: プロジェクトの pace（`pace: auto` など）が設計承認ゲートを MVV 判定で通す場合は、その判定どおりに次の承認ゲートか終わりまで進む。人のいない実行だからといって pace を変えない

## 対象範囲

含む:

- 人のいない実行での conductor の決まり（`plugins/ndf/skills/development-workflow/` の SKILL.md と references）
  - 区分の無い問い（`.ndf/` をコミットするか、次のコマンドを流してよいか、など）は AI が決め、`ask.py decide` で記録して止まらない
  - 承認ゲートに着いたら、承認資料を添えて `- 結果: 判断が要る` を書いて区間を終える
  - 区分に当たる問いのうち承認を求めるもの（レッドライン・費用・取り消せない操作・規約への同意）は AI が決めず、`- 結果: 判断が要る` と問い・材料を書いて区間を終える
  - 人の操作が要る問い（区分 `ndf-ask:human-action`。対話のログイン・権限の付与・外部の系の手動確認など）は `- 結果: できなかった` と人に頼むことを書いて区間を終える
  - 工程を最後まで通したら `- 結果: 完了`、続けられない理由があれば `- 結果: できなかった` と理由を書く
- 最後の応答の報告の形（結果の行の値・位置・添える行）を、Factory が読む契約として `plugins/ndf/contracts/` の下に 1 か所で定める
- 人のいない実行で結果の行を書かずに区間を終えることを、仕組み（hook かスクリプト）で防ぐ

含まない:

- Factory のランナーの変更（ランナーのプロンプトを足して補うことを含む）
- 承認ゲートの後の再開の仕組み（前提 3）
- 並列の計画・レーン・一時レーンでの問いの送り方（`asking.md` の「並列の計画のレーン」。変えない）
- 人のいない実行での承認ゲートの数と置き場所（`development-workflow` の承認ゲートを変えない）
- `NDF_FACTORY_RUN` の無い実行の振る舞い

| 用語 | 意味 |
| --- | --- |
| 実行ジョブ | 用語集のとおり。実行基盤が 1 回起動するコンテナ 1 つ分の実行 |
| 区間 | 用語集のとおり。1 つの実行ジョブの中でランナーのエージェントが起動する `claude -p` の 1 回分 |

## 受け入れ条件

- [ ] 1. 人のいない実行の最後の応答の報告の形（結果の行の 3 つの値と意味・位置・値ごとに添える行）が `plugins/ndf/contracts/` の下の 1 か所に例つきで定まり、development-workflow の本文と hook・スクリプトはそこを参照する（形を写さない）。結果の行の読み方は `ndf-next-block.json` の規則と食い違わず、両方の例の組をテストが読む
- [ ] 2. 人のいない実行の `claude -p "/ndf:development-workflow #<課題>"` で、標準のモードの課題が問い返さずに設計まで進み、設計承認ゲートで区間を終える。最後の応答の最後の結果の行は `- 結果: 判断が要る` で、同じ応答に承認ゲートの名前（設計 Pull Request のマージ）と設計 Pull Request の URL が載る
- [ ] 3. 2 と同じ実行で、区分の無い問い（`.ndf/` をコミットするか・次のコマンドを流してよいか、など）は AI が決め、`ask.py summary` で、その区間に決めた問いが `ask.jsonl` に 1 件以上数えられる。最後の応答に、利用者の返答を求める文（「進めて」と返してもらえれば、など）が無い
- [ ] 4. 人のいない実行で人の操作が要る課題（外部の系の手動確認など）を流すと、最後の応答の最後の結果の行は `- 結果: できなかった` で、人に頼む操作が 1 行以上載る
- [ ] 5. 人のいない実行で承認を求める区分の問い（レッドライン・費用・取り消せない操作・規約への同意）に当たると、AI はその問いを決めずに区間を終え、最後の結果の行は `- 結果: 判断が要る` で、問いと材料が載る
- [ ] 6. 人のいない実行で工程を最後まで通したときは `- 結果: 完了`、続けられない理由に当たったときは `- 結果: できなかった` と理由 1 行が、最後の応答に載る
- [ ] 7. 人のいない実行で、最後の応答に結果の行が無いまま応答を終えようとすると、仕組み（hook かスクリプト）が差し戻し、結果の行を書くよう求める。差し戻しの判定はユニットテストで確かめる
- [ ] 8. `NDF_FACTORY_RUN` の無い実行（人がいる会話）では、7 の差し戻しが働かず、承認ゲートと区分の問いは今どおり `AskUserQuestion` で問う。既存のテスト（hook・問いの区分・`ndf-next` のブロック）が変更なしで通る
