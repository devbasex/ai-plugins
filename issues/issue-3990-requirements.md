## 前提

- 前提 1: リンクを固めるコミットは、この作業のブランチが分かれた元の `main` のコミット（分岐点）とする。分岐点は `main` の履歴に残るので、この作業がマージされた後も、そのコミットを指すリンクから消す前の 36 本を読める。#3412 の詳細設計書の手順 7 は「消すコミットの親」へ固めるとしている。このブランチでは消すコミットより前に設計のコミットが載るので、その親はブランチの上のコミットになり、マージの形によっては `main` の履歴に残らない。そこで分岐点に読み替えた
  - AI が最初に Issue の本文を書き換える前に、`main` で 36 本のどれかが変わっていれば、AI がブランチを最新の `main` へ載せ直して分岐点を取り直す。確かめてからコマンドを打つまでの間に変わることもある。そのため、コマンドは、書き換えを始める直前に 36 本が `main` で変わっていないかを自分で確かめる。変わっていれば、コマンドは 1 件も書き換えずに止まり、AI が分岐点を取り直してコマンドを作り直す
  - 最初に Issue の本文を書き換えた後は、取り直さない。書き換えたリンクは固めたコミットを指しているので、取り直すとリンクと食い違うからである。その後に `main` で 36 本が変わったときの扱いは、この Issue の設計書（`issues/issue-3990-design.md`）の「固めるコミットの選び方」にある
- 前提 2: リンクを書き換えるコマンドは、設計の承認の後に AI が打つ。利用者は打たず、ほかの NDF の作業も止めない
  - Issue の本文を書き換えている間に、利用者やほかの NDF の作業が同じ本文を編集すると、その編集を上書きして消すおそれがある。GitHub の Issue の更新には、ほかの編集が無いことを条件にした書き込みが無いので、誰が打ってもこのおそれを無くせない
  - そこでコマンドは、Issue ごとに、書き込む直前に本文を取り直し、取り直した本文に置換を当てて書く。それより前に入った編集は、置換を当てた本文に含まれるので消さない。残るのは、取り直しから書き込みまでの、API の 1 往復ほどの間の編集だけである。その間の編集は、書いた後に編集の履歴で見つけて利用者に知らせる（受け入れ条件 5）
  - #3412 の詳細設計書は、利用者が打ち、その間ほかの NDF の作業を止める形にしていた。しかし、このリポジトリの Issue を編集できるアカウントは利用者の 1 つだけで、利用者の手の編集も NDF の作業の編集も同じアカウントで記録される。利用者が打っても同じコマンドなので、取り直しから書き込みまでの間の編集は同じく残り、利用者がその間に手で編集することも仕組みでは止められない。ほかの NDF の作業をすべて挙げて止めているかを確かめるコマンドも無い。比べた表と採らなかった理由は、設計書の決定 5 にある

## 利用者がすること

コマンドを打つこと、試行の記録を Pull Request の本文に貼ること、止まったときに作り直すことは AI が行う。ほかの作業を止めることも要らない（前提 2）。利用者がするのは、AI が Pull Request の本文で答えを求めたときだけで、次の 3 つである。何も起きなければ、利用者がすることは無い。細かい手順は設計書の手順 6 と「固めるコミットの選び方」にある。

1. AI から、書き込みのほかの編集があったかもしれない Issue を知らされたら、GitHub の画面の編集の履歴で確かめて答える。上書きされていれば本文を戻す。AI が確かめられなかったリンクの変化や消えたリンクも、同じく確かめて答えるか、手で戻す（受け入れ条件 5）
2. 最初に書き換えた後に `main` で 36 本のどれかが変わったと AI から知らされたら、その変更を確定仕様へ移すかどうかを決める（前提 1）
3. 1・2 を、この作業の Pull Request が `main` へ入る前に終える（受け入れ条件 6）

### エンジニア向けの補足

受け入れ条件 2 の検査は次のコマンドで、0 行を合格とする。

```bash
git grep -n -e issue-1142- -e issue-3347- -e issue-3395- -e issue-3388- -- \
  plugins scripts docs .github AGENTS.md CLAUDE.md \
  ':!docs/archive' ':!docs/ndf-12-survey' ':!scripts/ndf-next-parity' ':!**/CHANGELOG.md'
```

受け入れ条件 3・4 の列挙は `gh api --paginate 'repos/devbasex/ai-plugins/issues?state=open&per_page=100' --jq '.[] | select(.pull_request | not)'` で行い、`gh search issues` は使わない（既定の上限 30 件に縛られる）。REST の Issue の一覧は Pull Request も返すので、`select(.pull_request | not)` で除く。置換案を作るとき、当てるとき、当てた後に読み直すとき、マージの前に確かめ直すときのすべてで、この同じ除外を使う。

置換案の形と消すコマンドは、#3412 の詳細設計書の「開いている Issue の列挙」「本文の書き戻しと同時の編集」「消すコマンド」にある。当てるコマンドの #3412 からの違い（対象のリポジトリの明示・確認済みの対象・試行の記録など）は、設計書の決定 4 にある。
