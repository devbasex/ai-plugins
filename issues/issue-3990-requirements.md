## 前提

- 前提 1: リンクを固めるコミットは、この作業のブランチが分かれた元の `main` のコミット（分岐点）とする。分岐点は `main` の履歴に残るので、この作業がマージされた後も、そのコミットを指すリンクから消す前の 36 本を読める。#3412 の詳細設計書の手順 7 は「消すコミットの親」へ固めるとしている。このブランチでは消すコミットより前に設計のコミットが載るので、その親はブランチの上のコミットになり、マージの形によっては `main` の履歴に残らない。そこで分岐点に読み替えた
  - AI が最初に Issue の本文を書き換える前に、`main` で 36 本のどれかが変わっていれば、AI がブランチを最新の `main` の上へ載せ直して（リベースして）分岐点を取り直す。確かめてからコマンドを打つまでの間に変わることもある。そのため、コマンドは、書き換えを始める直前に 36 本が `main` で変わっていないかを自分で確かめる。変わっていれば、コマンドは 1 件も書き換えずに止まり、AI が分岐点を取り直してコマンドを作り直す
  - 最初に Issue の本文を書き換えた後は、取り直さない。書き換えたリンクは固めたコミットを指しているので、取り直すとリンクと食い違うからである。その後に `main` で 36 本が変わったときは、利用者（このリポジトリの Issue を編集できる唯一のアカウントを使う人で、この作業を承認する人）が扱いを決める（「利用者がすること」の 2）
- 前提 2: リンクを書き換えるコマンドは、設計の承認の後に AI が打つ。利用者は打たず、ほかの NDF の作業も止めない
  - Issue の本文を書き換えている間に、利用者が手で、または並行して動くほかの NDF の作業（ほかの AI）が同じ本文を編集すると、その編集を上書きして消すおそれがある。GitHub の Issue の更新には、「読んだ後に誰も編集していなければ書く」という条件付きの更新が無い。そのため、誰がコマンドを打っても、このおそれを無くせない
  - そこでコマンドは、Issue ごとに、書き込む直前に本文を読み直し、読み直した本文に置換を当てて書く。読み直すより前に入った編集は、置換を当てた本文に含まれるので消さない。消すおそれが残るのは、読み直してから書き込むまでの、API の 1 往復ほどの間に入った編集だけである。以下では、この間に入った、AI の書き込み以外の編集（人の手の編集や、並行して動くほかの AI の作業の編集）を「ほかの編集」と呼ぶ。ほかの編集は、書いた後に AI が編集の履歴で見つけて利用者に知らせる（受け入れ条件 5）
  - #3412 の詳細設計書は、利用者が打ち、その間ほかの NDF の作業を止める形にしていた。しかし、このリポジトリの Issue を編集できるアカウントは利用者の 1 つだけで、利用者の手の編集も NDF の作業の編集も同じアカウントで記録される。利用者が打っても同じコマンドなので、読み直してから書き込むまでの間の編集は同じく残り、利用者がその間に手で編集することも仕組みでは止められない。ほかの NDF の作業をすべて挙げて止めているかを確かめるコマンドも無い。比べた表と採らなかった理由は、この Issue の設計書の決定 5 にある

## 利用者がすること

コマンドを打つことは AI が行う。試行の記録（置換のコマンドが Issue ごとに、いつ本文を読み直し、いつ書き込み、結果がどうだったかを残す記録）を Pull Request の本文に貼ること、コマンドが止まったときに作り直すことも、AI が行う。ほかの作業を止めることも要らない（前提 2）。

利用者の答えは、すべてこの作業の Pull Request（ https://github.com/devbasex/ai-plugins/pull/4470 ）へのコメントで受ける。Pull Request の本文の表は AI が書き、答えのコメントの URL を添える。コメントには GitHub が書いた人と時刻を残すので、誰がどの経路で答えたかを後から確かめられる。AI が会話で受けた答えや、Pull Request の本文を書き換えただけのものは、答えとして扱わない。

最初に Issue の本文を書き換える前に、利用者は必ず 1 回答える。AI は、書き換える Issue の番号と、替える前と後のリンクの組の一覧を、Pull Request の本文の「答えを求める組」に、そのままコメントに貼れる形で挙げる。利用者はその一覧を貼って「書いてよい」と書いたコメントを 1 つ書く。AI はこのコメントの答えがあるまで書き換えない。設計の承認だけでは書き換えない。後から組が増えたり変わったりしたときも、同じく増えた・変わった組に答える。

そのほかに利用者が答えを求められるのは、書き込んだ後に AI が次の表の状態を見つけたときである。AI は見つけた時点では Issue の本文を書き直さず、Issue の番号と見つけたことを Pull Request の本文に挙げる。利用者が答えた後に、表の「誰が何をするか」に AI がコマンドを打ち直すと書いた場合だけ、AI が書き直す。

| 状態 | どういう状態か | 誰が何をするか |
| --- | --- | --- |
| 上書きの疑い | AI が本文を読み直してから書き込むまでの間に、ほかの編集が入っていた。AI の書き込みが、その編集で足された文を消したおそれがある | 利用者が編集の履歴で確かめ、消えた文を本文へ戻す（下の 1）。戻した後に、AI がその Issue だけにコマンドを打ち直す。戻した文に固める前のリンクが入っていても固めるためで、固めるコミットは最初に書き込んだときと同じである（前提 1） |
| 確かめられない | 編集の履歴から、どれが AI の書き込みか、その前にほかの編集があったかを AI が決められない。編集の履歴では、どの編集も同じアカウントの名前で出る。そのため AI は、自分が送った本文のハッシュ（Pull Request の本文に貼る試行の記録にある）と同じ本文の版を、書き込んだ時刻の前後から探して自分の書き込みとする。その版が見つからない、2 つ以上ある、または時刻の前後を決められないときがこの状態である | 利用者が編集の履歴を見て答える（下の 1）。試行の記録にある書き込みの時刻を手がかりにする |
| 書いた後にリンクが変わった | AI が書き込んだ後に、ほかの編集が、置換したリンクの URL か `#` の後ろの見出しを変えた | AI が変化を起こした編集を履歴で探して挙げ、利用者が意図した変更かを答える（下の 1）。意図しない変更なら、AI がコマンドを打ち直して正しいリンクへ直す |
| 消えたリンク | AI が書き込んだ後に、ほかの編集が、置換したリンクを本文から消した | 利用者が意図して消したかを答える。意図していなければ、AI が挙げた URL を、AI が挙げた箇所（消える前の版でリンクの前後にあった文）へ手で書き戻す（下の 1）。AI のコマンドはリンクのある所しか書き換えないので、消えたリンクは戻せない |
| リンクの変化を AI が特定できない | 置換したリンクの数が書き込んだときより減ったが、どの編集でどの箇所が変わったかを AI が履歴から特定できない | 利用者が編集の履歴で箇所を探して答える。その答えで、「書いた後にリンクが変わった」か「消えたリンク」として扱う |

書き換える組への答えのほかに、利用者がすることは次の 4 つである。何も起きなければ、書き換える組への答えのほかにするのは 4 だけである。細かい手順は、この Issue の設計書の「手順 6 の確かめ方」「固めるコミットの選び方」「書いてよい組との照合」にある。

1. 上の表で答えを求められたら、GitHub の Issue の画面で編集の履歴を確かめて、Pull Request へのコメントで答える。復旧と書き戻しも、済んだことをコメントで答える。AI がその答えを、下に書いた Pull Request の本文の表に書く
   - 履歴の開き方: Issue の画面で、本文の上の投稿者の名前の横にある「edited」を押すと、編集の一覧（編集した人と時刻）が出る。一覧の 1 件を選ぶと、その編集で変わった所が出る
   - 上書きの疑い: AI が挙げた時刻の前後の編集を開き、AI の書き込みより前の編集で足された文が、今の本文に残っているかを見る。残っていなければ、本文を編集してその文だけを書き足す。残っていたときは書き足さない。どちらのときも、今の本文にその文があると確かめたら、消えたおそれのある編集ごとに、その編集の時刻と確かめた時刻をコメントで答える。AI は答えを Pull Request の本文の「復旧の確認」の表に、編集ごとに 1 行で書く。1 行は、上書きを疑われた書き込みの実行の識別子（試行の記録にある）・Issue の番号・消えたおそれのある編集の時刻・確かめた時刻・答えのコメントの URL を持つ。公開のリポジトリなので、ログイン名は表に書かない
   - 確かめられない: AI が挙げた時間に AI の書き込みがあったか、その前にほかの編集があったかを見て答える。編集の履歴ではどの編集も同じ名前で出るので、試行の記録にある書き込みの時刻を手がかりにする
   - 書いた後にリンクが変わった・消えたリンク: AI が挙げた編集が、意図したものかを答える。消えたリンクを戻すときは、最新の本文を開き、AI が「消えたリンク」の表に挙げた前後の文の箇所に、挙げた URL のリンクだけを書き足す。ほかの文は変えない。本文全体を前の版へ戻すと、その後に入った正しい編集まで消えるからである。書き戻した時刻をコメントで答える。AI がその時刻を、Pull Request の本文の「消えたリンク」の表に書く
2. 最初に書き換えた後に `main` で 36 本のどれかが変わったと AI から知らされたら、その変更を確定仕様へ移すかを決める（前提 1）
   - AI は Pull Request の本文に、変更したコミット、変わったファイル、変更の中身の要約、移すかどうかの推奨を示す。利用者は、推奨に同意するか、違う扱いにするかをコメントで答える
