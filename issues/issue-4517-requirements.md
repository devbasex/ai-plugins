## 何が起きたか

NDF（このリポジトリが作る、AI に開発の工程を進めさせるプラグイン）は、変更を 5 つのモードに分け、モードごとに通す工程の数を変える。小さな直しに設計や詳細設計を課さないためである。モードの中身は「今の姿」の表にある。ところが 2026-11-25 に集計すると、NDF の版 11.x（以下「11 系」）で作った 61 本のスプリント（1 つの版として出す課題のまとまりを、要求から本番まで工程どおりに進める単位。期間の区切りではない）はすべて `standard` で、`light` と `operation` は 1 本も無かった。10 系の工程の記録 289 件でも `light` は 2 件、`operation` は 0 件である。

| 記録 | 期間 | 件数 | standard | light | operation | モードの記録なし |
| --- | --- | --- | --- | --- | --- | --- |
| 11 系のスプリント（ai-plugins 38・別のリポジトリ 2 つで 23） | 11/19〜11/25 | 61 | 61 | 0 | 0 | — |
| 10 系の工程の記録（`~/.claude/ndf/state/stages/`） | 10 月〜11 月 | 289 | 141 | 2（#1142・#3410） | 0 | 146 |

軽い仕事は、モードを判定する工程を通らずに `main` へ入っている。11/19 以降に `main` へ入った ai-plugins の PR は 172 本ある。そのうち 52 本（`fix/` 27・`docs/` 13・`feature/` 6・ほか 6）は、スプリントも設計 PR もリリースの PR も通っておらず、モードの記録が無い（例: https://github.com/devbasex/ai-plugins/pull/4514 ）。見つけたその場で直す「即時修正」もこの経路で、何を直したかが工程の記録に残らない。

困るのは 2 者である。開発を任せる利用者は、小さな直しにも設計の承認を求められるか、工程を通らなかった直しを後から確かめられない。開発計画を立てる人は、課題ごとのモードが決まらないので、スプリントの切り方と工程の数を見積もれない。

## 種類

機能の変更（モードの判定の基準と、判定を行う場所を変える）

## 今の姿

今のモードは次の 5 つである。下の表の上ほど通す工程が多い（モードの「高さ」は `standard` が最も高く、`light` が最も低い。`documentation` はほかと比べない）。

| モード | どんな変更か（今の条件） | 主に通る工程 | 人の承認 |
| --- | --- | --- | --- |
| `standard` | 機能の追加・振る舞いの変更・バグ修正・複数のモジュールにまたがる変更 | 工程表の 18 行すべて（主に、要求・設計・詳細設計・設計のレビュー・計画・テスト駆動の実装・リファクタリング・コードレビュー・確定仕様化・リリース・リリース後テスト・振り返り） | 設計の承認（承認ゲート 1）とリリースの承認（承認ゲート 2） |
| `legacy-refactor` | 振る舞いを変えずに構造だけを変え、テストが少ない | 設計・現状を固定するテスト・段階的な整理・レビュー・リリース | 設計を実装と別の Pull Request で出したときだけ設計の承認（承認ゲート 1）。リリースの承認（承認ゲート 2） |
| `operation` | プログラムも文書も変えず、外部のシステムの設定や状態だけを変える | 要求・計画・実行・レビュー・リリース | 本番へ届く実行の前の承認（承認ゲート 2 に当たる） |
| `light` | 振る舞いもプログラムの構造も変えない局所の変更（文言・文書・テストの追加など） | 要求・実装・コードレビュー・リリース | リリースの承認（承認ゲート 2） |
| `documentation` | 社外の読み手へ渡すビジネス文書を作る（今は `README.md`・`docs/` は当たらず `light`） | 要求・設計・素材の収集・執筆・体裁レビュー・提出 | 構成の承認（承認ゲート 1 に当たる）と提出の承認（承認ゲート 2 に当たる） |

人の承認は、どのモードでも次の 2 か所（承認ゲート）だけで求める。承認ゲート 1 は「設計 Pull Request のマージ」（この設計で実装へ進んでよいか）、承認ゲート 2 は「本番系へ届く操作」（出してよいか）である。

判定の基準は `development-workflow` の SKILL.md の「2. 上から順に条件を判定する」と `references/workflow-modes.md` にある。基準は上から `operation` → `documentation` → `standard` → `legacy-refactor` → `light` の順に問う。判定の結果は、スプリントのステートマシンを作る `ndf progress new` の引数 `--mode` で渡し、その値の工程表（`contracts/workflow/modes/<モード>.json`）が作られる。

`standard` に寄る理由は 4 つある。

1. **並列の計画のレーン（複数のスプリントを同時に進めるための作業の列。計画の各行が 1 本のスプリントになる）は判定を通らない。** レーンの起動（`plugins/ndf/src/ndf/progress/lane/launch.py` の `DEFAULT_MODE = "standard"`）が、計画の行に `--mode` が無いと `standard` を入れる。61 本のうち 54 本がレーンで、`--mode` を持つ行は 0 本だった
2. **基準の上で `light` に入る余地がほとんどない。** `standard` の条件「本番の振る舞いの追加・変更、バグ修正」「複数モジュールにまたがる変更」が小さな直しも拾う。NDF では、AI が読んで従う手順書（Skill の本文と `references/` の文書）がプログラムと同じく AI の動き方を決める。そのため手順書の直しも「本番の振る舞いの変更」に当たり、`standard` になる。1 つのスプリントに違うモードの課題が混ざったときの規則「高い方のモードへ寄せる」もあり、レーン `p8-5-lrelay-r2` では手順書だけの直し 3 件（#3846・#3847・#3814）が、コードの直し #3842 と一緒に `standard` になった
3. **軽い仕事は Skill を通らずにマージされる。** 即時修正（見つけた不具合を、課題を起票せずにその場で直すこと）は、SKILL.md の「即時修正」の次の 4 条件をすべて満たすときに許される。しかしモードではないので、工程の記録の置き場が無い。手順書が記録の手順として案内する先（`pace.md` の「流出不具合の記録」、`new impl --escape-of`）も、今は存在しない
   - (a) 原因が特定でき、再現するテスト（書けなければ再現の手順）を先に置ける
   - (b) コマンドの引数と出力の形・設定のキーなどの既存の約束（コントラクト）を壊さない
   - (c) 方針・既定値・閾値そのものを変えない
   - (d) revert 1 回で戻せる
4. **`operation` の条件が実際の運用の形に合わない。** 条件は「プロダクションコードも文書も変えず、外部の系の状態だけを変える」だが、運用の仕事はたいてい IaC・設定・手順書の変更を伴う。そのため `standard` のスプリントに混ざるか、手で行われて記録に残らない。前者の例は、別のリポジトリで外部の認証の設定を有効にする課題が、機能の課題と同じ `standard` のレーンで流れたこと。後者の例は ai-plugins #3552（リリースの出し直し）と #3119（ブランチ運用の変更）である

開発計画（並列の計画 `issue-plan-strategy` の `parallel-plan.md`、実行計画の `execution-plan.md`）は、モードを決めずにスプリントを切っている。並列の計画のスプリントの行は課題の番号だけを持ち、実行計画の「モード」の列は書き手が埋めるだけで、判定の手順を持たない。

## 目的

- 仕事の重さに合ったモードが選ばれ、小さな直しと値の変更に設計や詳細設計を課さない
- 即時修正を、実装を先に出してリリースの後にレビューする 1 つのモードとして記録に残す
- どの経路（対話の conductor・並列の計画のレーン・開発ループ）でスプリントを始めても、Skill の中でモードを判定し、判定の根拠が残る
- 開発計画の時点で課題ごとのモードが決まり、モードでスプリントを切れる
- リポジトリの知識の文書（`docs/`）を新しく書く・組み直す仕事に、文書の構成を決める承認が掛かる

## 対象範囲

含む:
- 即時修正のモードの定義（工程表の列・リリースの後のレビューの工程・その指摘の扱い）
- `light`・`operation`・即時修正・`standard`・`legacy-refactor`・`documentation` の境界と、境界事例への答え
- スプリントを始めるときの判定の場所と記録の置き場、`ndf progress new --mode` の意味の変更、レーンの起動の既定のモードの廃止
- 開発計画（並列の計画・実行計画・開発ループの周）で課題ごとにモードを判定して計画に載せ、モードでスプリントを切ること。計画の時点の判定とスプリントの開始の判定が食い違ったときの扱い
- モードの違う課題が 1 つのスプリントに混ざったときの扱い
- 11/19 以降の 61 本のスプリントと直接マージの 52 本を新しい基準で判定し直した分布
- `docs/`（と `README.md`）の文書を `documentation` で扱うか、`docs/` 用のモードを作るか。扱うときの工程と、`light` に残す変更との境目

含まない:
- 人が GitHub の画面や端末で行うマージ（工程の外である）
- 承認ゲートの数と位置の変更（2 つのまま）
- `pace`（`normal`・`auto`・`fast`）の定義の変更
- 既にマージした 52 本の PR とスプリントの記録の書き換え

## 前提

- 前提 1: 承認ゲートは「設計 Pull Request のマージ」と「本番系へ届く操作」の 2 つで、増やさない（`development-workflow` の「人手の承認を求める承認ゲート」、NDF の共通原則）
- 前提 2: 判定の基準の正本は `development-workflow` の 1 か所に置き、計画の手順・テンプレート・コードは基準を写さずに指す（SKILL.md の「判定基準を持つのはこの Skill だけである」）
- 前提 3: 普及のフェーズまで後方互換は求めない（このリポジトリの判断の基準 MVV の Value 4。MVV は Mission・Vision・Value の略で、`.ndf/mvv.md` にある）。`--mode` の意味と工程表の値は作り直してよい

## 受け入れ条件

- [ ] 1. 即時修正のモードが工程表（`development-workflow` の「モードごとに起動する Skill」）に列を持つ。工程を記録する定義（`contracts/workflow/modes/`）もある
- [ ] 1-2. リリースの後のレビューの工程が定義され、そこで見つかった指摘の扱い（直す・戻す・見送る）が決まっている
- [ ] 1-3. 承認ゲートは 2 つのままで、即時修正のどの承認ゲートで人が承認するかが書かれている。人の承認を AI の判定で省く範囲は広げない（「境界」）
- [ ] 2. `light`・`operation`・即時修正・`standard`・`legacy-refactor`・`documentation` の境界が、課題の本文と差分から判定できる条件で書かれている。境界事例（設定値・定数だけの変更、手順書や Skill の本文だけの直し、IaC を伴う運用、バグ修正の大小、モードが混ざるスプリント）に表で答えが出る
- [ ] 3. 11/19 以降の 61 本のスプリントと直接マージの 52 本を新しい基準で判定し直した分布が、設計書に載っている（件数は全件。判定の根拠は、モードごとに 2〜3 件の例で示す）
- [ ] 4. スプリントのステートマシンを `ndf progress new --mode <モード>` で作っても、工程「要求と受け入れ条件」の終わりに判定が行われ、判定の記録（モード・根拠・課題ごとの判定）が無いまま後の工程へ進まない。判定したモードが `--mode` と違えば、後の工程はそのモードの工程表で流れる
- [ ] 5. 並列の計画のレーンの起動は、計画の行に `--mode` が無くても `standard` を判定として入れない。レーンで始めたスプリントも 4 と同じに判定される
- [ ] 6. モードの違う課題が 1 つのスプリントに混ざったときのスプリントのモードの決め方が、判定の記録から機械で決まる。即時修正と `documentation` はほかのモードの課題と混ぜない扱いが決まっている
- [ ] 7. 開発計画を作る手順（`issue-plan-strategy` の並列の計画・実行計画、開発ループの周）が、課題ごとのモードを判定して計画の行に載せ、モードでスプリントを切る。計画の時点の判定とスプリントの開始の判定が食い違ったときの扱い（どちらを採るか・計画をどう直すか）が決まっている
- [ ] 8. 判定の基準は `development-workflow` の 1 か所にだけあり、計画の手順・テンプレート・コードは基準を写していない
- [ ] 9. `docs/` の文書の扱いが決まっている。`documentation` に入れるか `docs/` 用のモードを作るか、通す工程と飛ばす工程（素材の収集・体裁レビュー・確定仕様化・リリース後テスト・デプロイ）、読み手、`light` に残す変更との境目、`README.md`・Skill の本文・コードのコメントの扱い、工程の産物として書く確定仕様を判定の対象外のままにすること、混ざりの規則との関係が書かれ、判定し直した分布にも反映されている

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`ndf progress new` の `--mode` が判定ではなく参考の値になる。工程「要求と受け入れ条件」の出力にモードの判定が加わる。並列の計画の行に課題ごとのモードが加わる。モードの値に即時修正が加わる |
| データ | スプリントのステートマシンの文脈にモードの判定の記録が加わる。判定でモードが変わったときは、定義の改訂（`rev`）が 1 つ増える |
| 既存の振る舞い | 判定の結果、`light`・`operation`・即時修正で流れるスプリントが増え、そのスプリントでは設計・詳細設計・リファクタリングなどを通らない。`--mode` を渡して始めたスプリントも、工程「要求と受け入れ条件」の後でモードが変わることがある |
| 重さ | 今は、仕事の重さに関係なく `standard` の 18 工程（設計 PR・詳細設計・リファクタリング・確定仕様化など）を通るか、工程を通らずに記録が残らない |

## 用語

| 用語 | 意味 |
| --- | --- |
| モード | 変更の種類ごとに、通す工程の組を決める区分。スプリントで 1 つ |
| 即時修正 | 見つけた不具合（リリースした版のものに限らない）を、4 つの条件を満たすときに、実装だけを先に出し、リリースの後にレビューする進め方。この要求でモードの 1 つになる |
| 判定 | 課題の本文と差分から、基準に照らしてモードを決めること。根拠を 1 行で残す |
| 計画の時点の判定 | 開発計画を作るときに、課題の本文から決めるモード。計画の行に載り、スプリントを始めるときの参考の値になる |
| スプリントの開始の判定 | スプリントの工程「要求と受け入れ条件」の終わりに、要求仕様と課題の本文から決めるモード。スプリントの工程表を決める |
| 直接マージ | スプリント・設計 PR・リリースの PR を通らずに `main` へ入った PR |
| 開発計画 | 複数の課題をスプリントへ切り分けて順序を決めた計画。並列の計画（レーンの表）と実行計画（`execution-plan.md`）と、開発ループの周を指す |
| スプリント | 1 つの版として出す課題のまとまりを、要求から本番まで工程どおりに進める単位。期間の区切りではない |
| 11 系・10 系 | NDF の版 11.x・10.x |
| レーン | 並列の計画で、スプリントを順に進める 1 本の作業の列。計画の 1 行が 1 本のスプリントになる |
| conductor | 利用者と対話し、工程を進める AI のセッション |
| 開発ループの周 | 開発ループ（スプリントを 1 つ終えるたびに次の課題を自動で選んで続ける進め方）の 1 回分 |
| ステートマシン | スプリントの工程の並びと、どこまで進んだかを記録するもの。`ndf progress new` で作る |
| 定義の改訂（`rev`） | ステートマシンの工程の並びの版。作り直すたびに 1 つ増え、前の版も記録に残る |
| IaC | インフラの構成をコードで書いて適用する仕組み（Terraform など） |
| 外部の系 | リポジトリの外にあるシステム（クラウドの設定・GitHub のリポジトリの設定・外部サービス・データベースのデータなど） |
| MVV 判定 | 利用者があらかじめ AI に承認を任せた進め方で、AI がプロジェクトの MVV に照らして承認ゲートを通してよいかを判定すること |

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | 判定の根拠を記録に残す。承認ゲートを 2 つに保つ |
| 確認してから行う | モードの値と工程表を変えること、`ndf progress new` の引数の意味を変えること（設計承認ゲートで見る） |
| 行わない | 判定の基準を計画の手順やコードへ写すこと。人の承認を MVV 判定で省く範囲を広げること |
