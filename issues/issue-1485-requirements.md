- `supervise.py new sprint` が書くプランだけで、課題を 1 つずつ流したとき（単発の工程）と同じ記録・本文・確認が残り、conductor がプランの外で手当てをしなくて済む状態にする（devbase のスプリント issue-273・m02-ci・snapshot-safety と、ai-plugins の #1142 スプリント 2 で、手当てが計 5 種類要った）

## 前提

- 前提 1: 「単発の雛形と同じ手順の定義」は、`templates.py` などにある定義を 1 か所に置き、単発の雛形とスプリントの雛形の両方がそれを呼ぶことを指す。今どちらにも無い手順（進捗記録・手動確認）は、共有の定義として新しく置き、単発の雛形も同じ定義を使う
- 前提 2: 対象の進め方は `normal`・`auto`・`fast` の 3 つすべてである。`fast` のスプリントブランチを持たない経路（`plan_fast_impl` / `plan_fast_check`）にも、意味の当たる手順（進捗記録・触るファイル・取り込んだ課題・手動確認）を同じ定義で入れる。スプリント PR を作らない `fast` では、「スプリント PR の本文」に当たる条件は対象にしない
- 前提 3: 「設計で閉じると決めた課題」「他の課題へ取り込んだ課題」「触るファイル」は、承認ゲート 1 でマージした設計文書（`issues/` の設計）か設計 PR の本文の「決めたこと」に、機械で読める形で書かれている。読む形（節の見出しと表の列）は設計で決め、`design` の Skill の雛形へ同じ変更で足す
- 前提 4: `new sprint` は設計より前にプランを書く。設計の結果（前提 3）は、実装のステージを流す時点で読む。プランを書いた時点で設計の結果が無いことは失敗にしない
- 前提 5: 進捗記録を 2 度打っても課題の本文は変わらない（`projects-sync.sh stage` は同じ工程に 2 度目の印を付けない）。単発の工程で conductor が打つ記録と重なっても害は無い
- 前提 6: 手動確認は人か実機が要るため、プランは確認そのものを行わない。プランが行うのは、要求の行を集めて PR 本文へ載せること、マージ前と決めた行が未確認ならマージの前に止まること、リリース後テストへ回す行をそう明記することである
- 前提 7: 検査の `--scope` の組み立て（#1295 #1417）は #1484 で扱い、この課題では変えない

## 対象範囲

含む:
- スプリントの雛形（`sprint_waves.py` の `plan_sprint_branch` / `plan_sprint_impl` / `plan_sprint_check` / `plan_fast_impl` / `plan_fast_check`）と、それが呼ぶ単発の雛形（`templates.py` の `plan_impl` / `plan_check` / `plan_check_since`）の手順の定義
- スプリント PR の本文を組む手順（`pr` のステップの材料）
- 設計の結果を読む形（前提 3）の、`design` の Skill の雛形への追記
- 子 issue 5 件（#1298 #1421 #1299 #1272 #1398）の受け入れ内容

含まない:
- 検査の `--scope` の組み立て（#1484・前提 7）
- 3 層の実行で通過工程の控えが積まれない件（#961）
- まとまりの実装 PR の閉じる語（#767）と、件名の `Fix: #N` を閉じる語と読む件（#1271）
- 設計のプラン（`plan_sprint_design` / `plan_mvv_design` / `plan_advise_design`）と配布のプラン（`plan_release` / `plan_mvv_release`）の手順。どちらも `記録` かそれに当たる手順を既に持つか、この課題の 5 種の手順と関係しない
- 手動確認そのものの実行（前提 6）

## 用語

| 用語 | 意味 |
| --- | --- |
| スプリントの雛形 | `supervise.py new sprint` がステージごとのプランを作る関数（`sprint_waves.py` の `plan_sprint_*` / `plan_fast_*`） |

| 取り込んだ課題 | 設計で、受け入れ内容を別の課題の実装へ含めると決めた課題。自分の実装プランを持たない |

## 受け入れ条件

### 共有の定義（#1485）

- [ ] AC1: 進捗記録・検査の記録・PR 本文の材料・触るファイル・手動確認の 5 種の手順は、それぞれ 1 つの関数（か定数）で定義され、単発の雛形とスプリントの雛形の両方がそれを呼ぶ。`sprint_waves.py` の中に、同じ手順のステップを文字列やリテラルで組み直す箇所が無い（`grep -n '"記録"\|check-done\|Closes' plugins/ndf/scripts/supervise_lib/sprint_waves.py` が 0 件）
- [ ] AC2: `new impl` / `new check --pr` / `new check --since-last` が書くプランは、AC3〜AC12 で足すキーとステップを除き、変更前と同じステップの並び（`id` の列）を持つ（退行しない）

### 進捗記録（#1299）

- [ ] AC3: `new sprint` が書くスプリントブランチ・実装・検査のプラン（`normal` / `auto` / `fast` のすべて）が、キー `記録` に `projects-sync.sh` の絶対パスを持つ
- [ ] AC4: スプリントで流した課題の本文の「進行」で、通ったステップの工程（実装・完了判定・Pull Request・リファクタリング・コードレビュー）に印が付く。テストでは、`記録` を持つプランを流したときに `projects-sync.sh <課題> stage <工程>` が課題ごと・工程ごとに 1 回呼ばれることを見る

### 検査の記録（#1272）

- [ ] AC5: `normal` / `auto` のスプリントの検査のプランが成功で終わると、origin の `check-done/review` と `check-done/check` が、マージしたスプリント PR のベースブランチ上のコミットを指す
- [ ] AC6: スプリントの検査の後の `check-trigger.py scope`（`--since-last` の範囲）が、スプリント PR に入った差分を含まない
- [ ] AC7: スプリントの検査が落ちた・止まったときは `check-done/*` を進めず、今と同じく落ちた行を検査の記録へ書く

### PR 本文の収集（#1298）

- [ ] AC8: スプリント PR の本文の「利用者向けの変化」の節に、スプリントブランチへマージした実装の PR ごとの「利用者向けの変化」の節の行が、PR の番号を添えて並ぶ。固定の文（`スプリント <名前> の課題を <起点> へ取り込む。`）だけの節にならない
- [ ] AC9: 実装の PR の「利用者向けの変化」が「無し」か節が無いときは、その PR を「利用者向けの変化なし」として並べる（空の行を足さない）。本文を読めなかった PR は名前を挙げて示す
- [ ] AC10: スプリント PR の本文に、スプリントの課題と、設計で閉じると決めた課題（取り込んだ課題を含む）が 1 つずつ `Closes #<番号>` の行で入る。「関連:」の後に番号を並べるだけの形にならない
- [ ] AC11: スプリント PR の本文の「課題と設計」の節が、承認ゲート 1 でマージした設計 PR を番号で指す（設計の課題が無いスプリントでは「設計なし」）
- [ ] AC12: `release-steps.py notes` にスプリント PR を渡すと、配布の説明文に AC8 の行が載る

### 触るファイルと取り込んだ課題（#1421）

- [ ] AC13: 設計の結果に触るファイルがある課題の実装プランは、キー `触るファイル` にそのパスを持つ。同じステージで `触るファイル` が重なる 2 本の実装プランを `queue --max 3` で流すと、1 本ずつ流れる（今の `admission.py` の重なりの組の扱い）
- [ ] AC14: 設計で他の課題へ取り込んだ課題には、実装のステージで実装のプランが流れない。取り込んだ課題は取り込み先の実装プランの `課題` に入り、取り込み先の実装の指示文が両方の課題の本文を読む
- [ ] AC15: 設計の結果が読めない課題（前提 4 で設計前、または書かれていない）は、今の振る舞い（`触るファイル` なし・取り込みなし）で流れ、読めなかったことが進捗ログに 1 行残る

### 要求の手動確認（#1398）

- [ ] AC16: スプリントの課題の要求（`issues/issue-<番号>-requirements.md`）に手動確認の行があると、スプリント PR（`fast` では実装の PR）の本文に「手動確認」の節が入り、行ごとに課題の番号・確認すること・時期（マージ前 / リリース後テスト）が並ぶ
- [ ] AC17: 時期が「マージ前」の行が未確認のまま残っていると、プランはマージの前で止まり、止まった理由に未確認の行を挙げる。確認済みと記録すると、同じプランを続きから流してマージへ進む
- [ ] AC18: 時期が「リリース後テスト」か、時期が書かれていない行は、本文で「リリース後テストへ回す」と明記され、マージを止めない
- [ ] AC19: 手動確認の行が 1 つも無いスプリントでは、「手動確認」の節を置かず、マージも止めない（退行しない）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 足すステップは LLM を呼ばない（`run` か `pr` のステップ）。スプリント 1 本あたりの LLM の呼び出し回数を増やさない（Mission・Value 4） |
| 移行性 | 既に書き出したスプリントの計画（`sprint-<名前>/`）は書き直さない。新しい形は次の `new sprint` から効く |
| システム環境 | ベースブランチ・テストのコマンド・要求の置き場（`issues/`）は宣言か引数で受け、ai-plugins の形を既定に埋め込まない（Value 5） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | `supervise.py new sprint` の引数は変えない（足すなら設計で決め、既存の引数の意味を変えない）。プランの JSON にキー `記録`・`触るファイル` と新しいステップが増える |
| データ | 課題の本文の「進行」の印が増える。origin の `check-done/*` がスプリントの検査で進む |
| 既存の振る舞い | スプリント PR の本文の節が変わる。マージ前の手動確認が残るとスプリントの検査がマージの前で止まる |

## 検証手段

| 項目 | 手段 |
