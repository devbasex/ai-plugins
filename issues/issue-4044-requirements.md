# #4044: ndf relay spawn・restart: 落ちたレーンの席を数えず、続きの起動の後に上限を超える

正は課題の本文（#4044）で、この文書はその写しである。本文から作り直す。手で直さない。

## 何が起きたか

PR #4041（#3995 の設計）のクロスレビューの指摘 r1-5 で、リレーハブの通常の起動と再起動が、マシン全体の上限（#3989）の数え方からずれていることが見つかった。#3995 の範囲の外なので分けた。

確定仕様 [docs/specifications/ndf-parallel-machine-plan-limit.md](https://github.com/devbasex/ai-plugins/blob/main/docs/specifications/ndf-parallel-machine-plan-limit.md) の「リレーハブの起動の判定」の表では、通常の `ndf relay spawn`（`--replace` なし）と `ndf relay restart` は、動いているラッパーの本数だけで上限（`relay.max-named`）を判定し、実行中の行を持つレーン（ラッパーの生死を問わない）を数えない。行を始める起動（`spawn --replace --seat <席>`）だけが、起動の許可が数えたそのレーンの名前（`held_seats`）を `--held` で受け取り、動いているラッパーとの和集合で数える。

## 種類

不具合（確定仕様が約束する「上限を下げていない限り、稼働中のレーンとほかの名前つきのラッパーの数は上限を超えない」を、許可を通らない起動の後にも成り立たせる）

## 今の姿

| 部品 | 今の振る舞い | 場所 |
| --- | --- | --- |
| 行を始める起動 | 起動の許可（`admitted`）が起動の排他の中で、実行中の行を持つレーンと動いているラッパーの和集合を数え、収まれば実行中の行を持つレーンの名前を `--held` でハブへ渡す。ハブは動いているラッパーと `--held` の和集合から対象を除いて数える | `src/ndf/progress/lane/machine.py` の `admitted`・`held_seats`、`src/ndf/domains/relay/hub.py` の `spawn`・`_over_cap` |
| 通常の起動 | ハブが動いているラッパーの本数 + 1 ≤ 上限で判定する。実行中の行を持つがラッパーの止まったレーンを数えない | `hub.py` の `spawn` → `_over_cap`（`held` を渡さない）→ `hub_decide.spawn` |
| 再起動 | ハブが対象を除いた動いているラッパーの本数 + 1 ≤ 上限と、日次の再起動の回数で判定する。実行中の行を持つがラッパーの止まったレーンを数えない | `hub.py` の `restart` → `hub_decide.restart` |
| 続きの起動 | 上限を読まない。登録簿のその名前の行の席が要求と同じなら通す | `hub.py` の `_seated_ok` |

パスは `plugins/ndf/` からの相対である。

## 事象

稼働中の行を持つレーンのラッパーが落ちると、その間に通常の `spawn`（オーガナイザーや手で打つもの）か、別のラッパーの `restart` が空いた 1 本を使える。その後、正規の続きの起動（`spawn --replace --seat <席> --seated`）は上限を読まずに通るので、上限を下げていないマシンでも動くラッパーが設定の本数を超える。確定仕様の同じ節の最後の段落は「許可を通らない起動（オーガナイザーや手の `ndf relay spawn`）が席を使った後は、動くラッパーの数が一時的に上限を超え得る」と書いて受け入れている。

## 期待する結果

通常の `spawn` と `restart` も、動いているラッパーと実行中の行を持つレーン（ラッパーの生死を問わない）の和集合で本数を数え、ラッパーの落ちたレーンの分を空きとして使わせない。上限を下げていない限り、続きの起動の後も動くラッパーの数が上限を超えない。

## 再現手順

1. 上限 N のマシンで、実行中の行を持つレーンを N 本動かす
2. 1 本のラッパーを止める（行は実行中のまま）
3. `ndf relay spawn` で別の名前のラッパーを起動する（動いている本数 N−1 + 1 ≤ N で通る）
4. 止めたレーンの続きの起動を行う（`--seated` は上限を読まない）→ 動くラッパーが N+1 本になる

仕様の表とコードを読んで組んだ手順で、実機では試していない。手順 3 を `ndf relay restart <別の名前>`（登録簿にあり止まっているラッパー）に替えても同じになる。

## 環境

main（96a9117bd、ndf v11.0.14 の後。#3989 の実装 PR #4001 のマージ後）

## なぜ困るか

並列は 6 本までという上限（2026-09-25 の実測で全体テスト 6 本の同時実行でメモリが残り 7.4 GB）を超え、マシンのメモリが足りなくなり得る。上限の判定が起動の経路ごとに違う数え方をするので、同じマシンの状態でも、どの経路で起動したかで上限を超えるかが変わる。

## 目的

- 通常の `spawn` と `restart` の上限の判定が、行を始める起動と同じ数え方（動いているラッパーと実行中の行を持つレーンの和集合）を使う
- ラッパーの落ちたレーンの続きの起動の後も、上限を下げていない限り、動くラッパーの数が上限を超えない（前提 4 の場面を除く）
- 確定仕様の「リレーハブの起動の判定」と既知の限界の記述を、直した振る舞いと一致させる

## 対象範囲

| 含む | 含まない |
| --- | --- |
| 通常の `ndf relay spawn` と `ndf relay restart` の本数の判定に、実行中の行を持つレーンを足すこと | 続きの起動（`--seated`）を上限で断ること（上限を下げても稼働中のレーンを止めない今の約束を変えない） |
| 実行中の行を持つレーンの名前を、計画を持たない頼む側（オーガナイザー・手の起動）から読む手段 | どの行を数えるか（数え方の規則 `lanes_of`。#4050 が変える） |
| 確定仕様の「リレーハブの起動の判定」「常に成り立つ条件」「エラー処理」「既知の限界」の該当箇所の書き直し | 計画の索引の寿命（#4051） |
| | 端末で打った `claude`（人の起動。上限で断らない今の約束） |
| | 上限を下げた直後に続きの起動で上限を超えること（今の約束のまま） |

## 前提

- 前提 1: 実行中の行を持つレーンの数え方（どの行を数えるか）は、起動の許可と同じ規則を使う。計画は計画の索引から見つけ、計画ごとに 1 回読む。登録簿の conductor の行にだけ載る計画は、頼む側からは読まない（読むと計画の数だけ Git の子プロセスが起きる）
- 前提 2: リレーハブのパッケージ（`ndf.domains.relay`）は計画のパッケージ（`ndf.progress.lane`）を読み込まない（子の依存の表 `src/ndf/checks/children.json` で M3b は P3 に依存しない）
- 前提 3: 人の起動（端末の `claude`）は今のとおり上限で断らない
- 前提 4: 次の場面は今の数え方のまま残り、確定仕様の既知の限界に書く。名前を読めない間（受け入れ条件 4）・頼む側が名前を読んでからハブが判定するまでに行を始めてすぐラッパーが落ちたレーン・旧い版のハブが要求を処理する間（プラグインの更新の直後）。あわせて、索引から外れて登録簿にだけ載る計画と、更新の前の形のまま残る索引の計画は、頼む側からは数えない（起動の許可は今のとおり数える）

## 受け入れ条件

- [ ] 1. 上限 N のマシンで、実行中の行を持つレーンが N 本あり、そのうち 1 本のラッパーが止まっているとき、通常の `ndf relay spawn`（別の名前）がハブの上限の断り（`cause: refused`、`items` に `{"refusal": "max-named", "running": N, "cap": N}`）で起動しない（テスト）
- [ ] 2. 同じ状態で、登録簿にあり止まっている別の名前のラッパーの `ndf relay restart` が上限の断りで起動しない。再起動の対象自身が実行中の行を持つレーンのラッパーなら、対象を数えずに判定して通る（テスト）
- [ ] 3. 実行中の行を持つレーンの名前を読めたとき、1 の状態から、止まったレーンの続きの起動（`--seated`）を打った後、動くラッパーが N 本を超えない（テスト）
- [ ] 4. 実行中の行を持つレーンの名前を読めない（読むサブコマンドが落ちた・時間内に返らない・結果を読めない）とき、通常の `spawn` と `restart` は今の数え方（動いているラッパーだけ）で判定し、結果の `warnings` に読めなかった理由を載せる（テスト）
- [ ] 5. 行を始める起動（`--replace`、`--held` つき）と続きの起動（`--seated`）の判定は今のまま変わらない（既存のテストが通る）
- [ ] 6. 確定仕様の「リレーハブの起動の判定」の表と最後の段落・「常に成り立つ条件」・「エラー処理」・「既知の限界」の記述が、直した振る舞いと一致する

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 計画のサブコマンドを 1 つ足す（実行中の行を持つレーンのラッパーの名前を返す）。`ndf relay spawn`・`restart` の引数と結果 JSON の形は変えない（`warnings` を載せることがある） |
| データ | 計画の索引に、計画のチェックアウトの保存先と DB の接続先（パスワードを除く）を足す（索引の版を 2 にし、版 1 も今のとおり読む）。登録簿と要求のファイルの形は変えない（要求の `held` を通常の起動と再起動の要求にも載せる） |
