## 何が起きたか

2026-11-24 に、NDF が工程を自動で進めている途中で、人がまだ承認していないスプリントの PR が 4 本、`main` へマージされた。ai-plugins の `main` は、マージした時点で利用者の取得元になるブランチ（自動反映の本番チャネル）である。本来は、工程「デプロイ」のリリース承認ゲートで人が承認してからマージする。

最初の 1 本は、ラッパーの PR（ https://github.com/devbasex/ai-plugins/pull/4401 、Claude Code を起動し直すラッパーがバックグラウンドの作業を待つ変更）である。工程を進める AI（conductor）は、工程「Pull Request」の後に、次の工程を自動で流すコマンド `ndf progress next` を 1 回打っただけで、マージは指示していない。それでも、続く工程「確定仕様化」が設計の文書を確定仕様へ移すついでにスプリントの PR をマージした。その後でリリース承認ゲートが、既にマージされた PR を承認資料にして回答を待ち始めた。同じ日に、同じ経路でさらに 2 本が入り、工程「Pull Request」のマージのステップでもう 1 本が入った（「事象」の表）。マージした時点で CI の必須のチェックはすべて通っていたが、PR の本文には「マージの前に残っている作業」が書かれたままだった。

## 種類

不具合（「自動反映の本番チャネルへのマージは承認を得るまで進めない」という約束が、今の手順書にすでにある。その約束に戻す）

## 今の姿

NDF は、マージ先が自動反映の本番チャネルかどうかで、マージの前に人の承認を求めるかを決める。この約束の SSOT は、`development-workflow` の手順書 `references/production-merge.md` の表「マージ先ごとの判定」である。

| マージ先 | NDF が行うマージ |
| --- | --- |
| 本番チャネルでない | そのまま進む |
| 自動反映の本番チャネル | 承認を得るまで進めない |
| 本番チャネルで、反映の設定（`release.deliveries`）が無い・読めない | 承認を得るまで進めない |
| 本番チャネルで、反映の設定に自動反映の行が無い（マージしただけでは利用者へ届かず、別のリリースの手順で届ける。承認はその手順で取る） | そのまま進む |

ai-plugins では、ベースブランチと本番チャネルがどちらも `main` で、`main` へのマージは自動反映に当たる（`.ndf/project.json` の `branch_strategy`）。スプリントの PR は `main` 宛てなので、このリポジトリではスプリントの PR のマージがリリース承認ゲートの対象になる。

ところが、工程の中で NDF がマージする 3 つの箇所が、マージ先を見ずにマージする。

| 工程 | マージする箇所 | 今の振る舞い |
| --- | --- | --- |
| 確定仕様化 | 確定仕様化のプランの最後のマージ | 開いたままのスプリントの PR を、確定仕様のコミットを足した後でマージする |
| Pull Request | ステップ `pr-merge` | スプリントの PR を出した後、CI が通ればマージする |
| ドキュメントレビュー | ステップ `docs-merge` | 文書の PR のレビューの後、承認ゲートを通らずにマージする |

AI が端末から直接 `gh pr merge` を打つ場合は、hook の検査（guard `merge-production`）がマージ先を判定して止める。工程のプランが打つマージのコマンド（`ndf ci merge`）には、この判定が無い。

### エンジニア向けの補足

- 確定仕様化のテンプレート `plugins/ndf/contracts/templates/plan-to-spec.json` は「worker がマージした PR（入力の pr）の設計を作業場所で確定仕様へ移す」前提で、`push` → `pr` → `ci` → `merge` と続く。`pr` のステップの確かめ（probe）が同じブランチの開いた PR を使い回すため、`merge`（`ndf ci merge --branch <スプリントのブランチ> --method merge`）がスプリントの PR をマージする
- 工程の順（`plugins/ndf/contracts/workflow/modes/standard.json`）は Pull Request → 確定仕様化 → クリーンアップ → デプロイで、確定仕様化の時点ではスプリントの PR はまだマージされていない。テンプレートの前提と工程の順が食い違う
- 工程「Pull Request」（`contracts/workflow/stages/pull-request.json`）のステップ `pr-merge` と、工程「ドキュメントレビュー」（`contracts/workflow/stages/document-review.json`）のステップ `docs-merge` は、どちらもテンプレート `merge`（`contracts/templates/merge.json`）を流す。このテンプレートには承認ゲートのステップ（`merge-gate`）が無い。即時修正のテンプレート `fix.json` と `close.json` も同じ形である。`check.json` と `design-merge.json` は `merge-gate` を持つ
- `ndf ci merge`（`plugins/ndf/src/ndf/ci_cli.py` の `_merge`）は、レビューを経た HEAD と、PR の本文に残った未決の行だけを見る。マージ先が本番チャネルかは見ない。`--help` に承認を渡す引数も無い（`--branch`・`--repo`・`--method`・`--reviewed` の 4 つ）。`production-merge.md` が書く「マージのステップが終了コード 10 で止まり、`--gate-approved` を付けて打ち直す」形は、今のコマンドに無い
- 工程「クリーンアップ」のテンプレート `merged.json` は、ブランチのマージ済みの PR が無いと `precondition` で止まる

## 期待する結果

- 自動反映の本番チャネルへの PR は、リリース承認ゲートの回答の前にマージされない（`production-merge.md` の表「自動反映の本番チャネル → 承認を得るまで進めない」）
- 確定仕様化のプランが開いたままのスプリントの PR を渡されたときは、確定仕様のコミットを push して CI を待つところで終わり、マージしない

## 再現手順

1. `branch_strategy` で `base` と `production` が同じブランチで、`release.deliveries` が `kind: auto` のリポジトリを用意する
2. スプリントを工程「Pull Request」まで進め、スプリントの PR を開いたままにする
3. `ndf progress next <スプリントのステートマシンの ID>` を打つ

## 環境

ndf 11.0.28（最初の発生）〜11.0.33（再発） / Claude Code / Linux

## なぜ困るか

人が承認していない変更が、利用者の取得元（`main`）に入る。人の承認が要る操作を、費用も時間も掛けずに機械が通してしまう。ai-plugins のようにベースブランチと本番チャネルが同じリポジトリで、工程を `ndf progress next` で自動で進めるすべてのスプリントに当たる。

直るまでの回避として、オーガナイザー（複数のレーンを束ねる AI）が、並行して動いている作業の流れ（レーン）へ「確定仕様化は `ndf progress next` で流さず `ndf:supervisor` で回し、スプリントの PR をマージしない」と伝えた（2026-11-24 20:5x JST）。この回避は工程「Pull Request」の `pr-merge` を塞がない。そのため、スプリントの PR を出す工程も `next` で流さず、マージのステップを外して回している。工程を自動で進められず、工程ごとに手で回す手間が続く。

## 目的

- 工程のどこから NDF がマージしても、マージ先が自動反映の本番チャネルなら、人の承認（リリース承認ゲートの回答）を得るまでマージしない状態に戻す
- 回避の手順を使わずに、スプリントを `ndf progress next` で最後まで進められるようにする

## 対象範囲

含む:
- 工程「確定仕様化」のプランが、開いたままのスプリントの PR をマージすること
- 工程「Pull Request」のステップ `pr-merge` が、承認の前にマージすること
- 工程「ドキュメントレビュー」のステップ `docs-merge` が、承認の前にマージすること
- 同じマージのステップを使うほかのプラン（即時修正 `fix`・`close`）が、承認の前に自動反映の本番チャネルへマージすること
- マージを承認まで待たせたときに、工程がデプロイのリリース承認ゲートまで進むこと（工程「クリーンアップ」が、マージされていないスプリントの PR のために止まらず、その PR を閉じない）

含まない:
- 人が端末や GitHub の画面で行うマージ（`production-merge.md` のとおり止めない）
- AI が端末から直接打つ `gh pr merge`（hook の検査 `merge-production` が既に止めている）
- 承認ゲートを持つ工程を `ndf progress finish` で終えると、回答を待たずに次の工程が始まる不具合（ https://github.com/devbasex/ai-plugins/issues/3957 。経路が違う）
- 既に承認の前に `main` へ入った 4 本の PR の扱い（3 本は利用者がリリース承認で扱いを決めた。#4461 は 利用者への確認（request-73）で問うている）
- ラッパーが引き継ぎの前にバックグラウンドの作業を待つ変更（ https://github.com/devbasex/ai-plugins/issues/4049 ）の受け入れ条件

## 前提

- 前提 1: 承認の記録とは、次のどちらかである（`development-workflow` の `references/pace.md`）
  - 利用者がリリース承認ゲートで承認した回答
  - 利用者があらかじめ、AI に承認を任せる進め方（`pace: fast` か `pace: auto`）を選んだときに、AI が判定した記録。AI は、利用者が承認した方針（MVV）に変更が合うかを見て、承認ゲートを通す（MVV 判定）。ただし、必ず人が承認すると決めた操作（レッドライン）は、AI が通さない

  どちらも、人が承認したか、人が前もって任せた範囲で通したものである。目的の「人の承認」はこの 2 つを指す
- 前提 2: マージ先が自動反映の本番チャネルかどうかは、`production-merge.md` の表「マージ先ごとの判定」と同じ規則で、マージ先のリポジトリの `branch_strategy` だけから決める

## 受け入れ条件

- [ ] 1. 前提: ai-plugins と同じ設定（ベースブランチと本番チャネルが同じで、自動反映の行がある）で、スプリントの PR が開いている
      操作: 工程「Pull Request」まで進めたスプリントで `ndf progress next` を打ち、確定仕様化のプランを流す
      結果: 確定仕様化のプランは確定仕様のコミットを同じブランチへ push し、CI を待ったところで終わる。スプリントの PR は開いたままである
- [ ] 2. 1 と同じ前提で、工程「Pull Request」のステップ `pr-merge` に着くと、承認の記録が無ければ PR をマージせずにステップを終え、工程は次へ進む。その場で承認を待たない。PR は開いたままで、デプロイのリリース承認ゲートまで残る
- [ ] 3. 1 と同じ前提で、工程「ドキュメントレビュー」のステップ `docs-merge` に着いたときも、2 と同じく PR をマージせずに次へ進み、PR は開いたままである
- [ ] 4. 即時修正のプラン（`fix`）と `close` のプランは、工程を通らずに単独で流れる。後ろにリリース承認ゲートが無いので、マージ先が自動反映の本番チャネルで承認の記録が無ければ、PR をマージせず、そのプランの中で承認待ちで止まる
- [ ] 5. 承認の記録（前提 1）を残した後に、次のとおり同じ PR がマージされる。承認の後に PR へコミットが足されていれば、承認した中身と違うので、マージせずに承認を求め直す（承認ゲートが、新しい中身で質問し直す）
      - 工程の中で開いたままにした PR（受け入れ条件 1〜3）: デプロイのリリース承認ゲートで承認すると、デプロイの工程がその PR をマージする
      - 承認待ちで止まった即時修正・`close` のプラン（受け入れ条件 4）: 承認の回答の後に、止まったところから続けるとマージされる
- [ ] 6. 承認ゲートのステップを既に持つプラン（設計 PR をマージするプラン `design-merge`、テスト・レビューの後に承認ゲートを通してマージする検査のプラン `check`）では、1 回のマージに承認を 2 回求めない
- [ ] 7. マージ先が本番チャネルでない PR（例: ベースブランチが `develop`、本番チャネルが `main` の設定で、`develop` 宛ての PR）は、今と同じく止まらずにマージされる（退行しない）
- [ ] 8. マージ先が本番チャネルで、反映の設定に自動反映の行が無い PR は、止まらずにマージされる（マージしただけでは利用者へ届かず、承認は別のリリースの手順で取るため）
- [ ] 9. マージ先が本番チャネルで、反映の設定が無いか読めないときは、承認の記録が無ければマージしない
- [ ] 10. 1 と同じ前提で、スプリントの PR を承認まで待たせても、工程はデプロイのリリース承認ゲートまで進む。工程「クリーンアップ」はその PR のブランチを消さず、PR を閉じない
- [ ] 11. 10 のリリース承認ゲートが回答を待ち始めた時点で、承認資料が指すスプリントの PR は開いたままである（マージ済みの PR を承認に出さない）
- [ ] 12. 「再現手順」の 3 つの手順を打っても、スプリントの PR が承認の前にマージされないことを、自動のテストが確かめる。このテストは、直す前の今の `main` では失敗する（このテストが不具合を見つけられることを示す）

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。マージ先が自動反映の本番チャネルのとき、工程の中のマージはデプロイのリリース承認ゲートの後へ移る。即時修正・`close` のプランは承認待ちで止まり、承認の後に続ける操作が増える。本番チャネルでないマージ先の振る舞いは変わらない |
| 重さ | 承認されていない変更が利用者の取得元へ入る。ベースブランチと本番チャネルが同じ設定で、工程を自動で進めるすべてのスプリントに当たる。回避は、確定仕様化と工程「Pull Request」を `ndf progress next` で流さず、マージのステップを外して手で回すこと |
| データ | 変わらない |
| 既存の振る舞い | マージ先が自動反映の本番チャネルのとき、確定仕様化・工程「Pull Request」・工程「ドキュメントレビュー」はマージせずに次へ進み、即時修正・`close` は承認待ちで止まる。工程「クリーンアップ」が、マージされていないスプリントの PR に当たったときの扱いが変わる |

## 用語

| 用語 | 意味 |
| --- | --- |
| 自動反映の本番チャネル | マージした時点で利用者へ届くブランチ。ai-plugins では `main` |
| リリース承認ゲート | 本番へ出す前に人の承認を得る承認ゲート。工程「デプロイ」にある |
| スプリントの PR | スプリントのブランチからベースブランチへ出す PR。ai-plugins では `main` 宛てになる |
| 確定仕様化 | 完了した設計と要求を `docs/specifications/` の確定仕様へ移す工程 |
| 承認資料 | 承認ゲートで人が判断に使う資料 |
| 工程・プラン・ステップ | 工程はスプリントを進める段階（Pull Request・確定仕様化・デプロイなど）。プランは、工程やコマンドがテンプレートから組む作業の手順で、ステップを順に流す。ステップはプランの中の 1 つの作業（`pr-merge` など）。工程を通らずに単独で流すプラン（即時修正 `fix` など）もある |
| `close` のプラン | 進め方 `pace: fast` のスプリントの終わりに単独で流すプラン。設計を確定仕様へ移し、その PR を出してマージする |

- 今の工程の順では、クリーンアップが PR のマージ（E8）より前に始まる。そのため、PR が開いていると止まる
