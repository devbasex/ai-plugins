# #735: quality-gates: 実データの結合確認で、設計時に独立に数えた値との突き合わせを証跡に含める

正は課題の本文（#735）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

`quality-gates` の standard の段階 4（結合・端から端まで）は、コマンドと終了コードを証跡に求めるが、**実データに対する結合確認の出力が期待値と合うか**を求めていない。

takemi-ohama/ideabase の PR #56 で、実データ 1 ヶ月分から変更計画を作る結合確認を `exit=0` で通した。出力は「変更 50 件 / -1,949,946 円」で、設計の段階で DB から独立に数えた値（同月は 37 件 / -172,155 円）と大きく食い違っていたが、突き合わせていなかった。原因は振替の行を未分類と読む不具合で、全月では振替 182 件 / -11,310,761 円を支出へ付け替える計画になっていた。マージ後、書き込みの直前に全月の合計（732 件）が設計の 535 件と合わないことで気づいた。

## どこで見つけたか

- `plugins/ndf/skills/quality-gates/SKILL.md` の「検証の段階」（段階 4）と「モード別の完了の定義」（standard: 受け入れ条件ごとの合否、契約・結合の結果）
- `plugins/ndf/skills/quality-gates/references/definition-of-done.md` の「`standard`」（「結合テストが通る（DB・外部通信を含む経路）」は通ったかだけを問う）
- takemi-ohama/ideabase PR #56 の Test plan（結合の行が exit=0 だけ）と PR #57

## なぜこの変更の範囲外なのか

takemi-ohama/ideabase #48 の範囲は MF ME の分類の是正であり、NDF の Skill の手順は含まない。

## 直さないと何が起きるか

実データを使う結合確認が「コマンドが落ちなかった」ことの証明にとどまり、設計や要求の段階で既に分かっている数量との食い違いを見逃す。取り消せない操作（外部の系への書き込み）の直前まで不具合が残る。

## 提案

standard の段階 4 に、**設計・要求で独立に求めた値（件数・金額・行数など）があるときは、結合確認の出力と突き合わせた結果を証跡に含める**ことを足す。値が無いときは「突き合わせる値が無い」と書く。

置き場は `plugins/ndf/skills/quality-gates/references/definition-of-done.md` の「`standard`」の項目 1 行と、`SKILL.md` の standard の「追加で要るもの」である。同じ定義の「対象を持たない項目は、持たないことを書いて満たす。空欄にしない」に従い、「突き合わせる値」と「突き合わせる値が無い」のどちらかを必ず書く。値の比較そのものは LLM が行う。

## 関連

- #1241（閉じた）— standard の完了の定義へ設計との突き合わせ (a)(b)(c) と `quality-gates/references/design-match.md` を足した。結合確認の出力と、設計で独立に求めた値の突き合わせは入っていない。足す 1 行は (c) の後に (d) として並べるか、`definition-of-done.md:45` の「結合テストが通る」に添えるかを着手の時に決める

# 要求と受け入れ条件

## 依頼（原文）

> standard の段階 4 に、**設計・要求で独立に求めた値（件数・金額・行数など）があるときは、結合確認の出力と突き合わせた結果を証跡に含める**ことを足す。値が無いときは「突き合わせる値が無い」と書く。
>
> 置き場は `plugins/ndf/skills/quality-gates/references/definition-of-done.md` の「`standard`」の項目 1 行と、`SKILL.md` の standard の「追加で要るもの」である。同じ定義の「対象を持たない項目は、持たないことを書いて満たす。空欄にしない」に従い、「突き合わせる値」と「突き合わせる値が無い」のどちらかを必ず書く。値の比較そのものは LLM が行う。

（上の「提案」の節。起票の本文から写した）

## 目的

- `standard` の完了判定で、実データを通す結合確認が「終了コード 0」だけで通らず、設計・要求の段階で別の経路から求めた値と出力が合うかまで証跡に残る状態にする
- 取り消せない操作（外部の系への書き込み）の前に、数量の食い違いで不具合に気づける機会を作る

## 前提

- 前提 1: 対象のモードは `standard` だけである。`light` / `operation` / `legacy-refactor` / `documentation` の完了の定義は変えない（`operation` は既に「反映を確かめた手段と結果」を、`documentation` は「事実確認」を求めている）
- 前提 2: 「独立に求めた値」は、結合確認の対象のコードを通さずに求めた値を指す（例: 設計の段階で DB へ直接数えた件数・合計金額、要求に書いた期待件数）。結合確認の出力から逆算した値は当たらない
- 前提 3: 突き合わせは担い手（LLM）が行い、スクリプトは足さない（依頼の原文「値の比較そのものは LLM が行う」）。値の形（件数・金額・行数・割合など）がプロジェクトごとに違い、決定論にできる共通の手順が無いためである
- 前提 4: 値が一致しないときは完了と呼ばない。一致しない値を「突き合わせた」と書いたまま完了にすると、突き合わせが証跡の形式だけになる（起票の事例はこの状態だった）。許容できる差（端数・期間の境界など）があるときは、差と許容した理由を証跡に書けば一致として扱ってよい
- 前提 5: 設計・要求の段階で独立の値を求めることを、この課題では新たに義務にしない。値が無いときは「突き合わせる値が無い」と書いて満たす（依頼の原文どおり）
- 前提 6: 結合テストそのものが無い変更（「対象を持たない項目」）では、この項目も「対象が無い」ことを書いて満たす。既存の「対象を持たない項目は、持たないことを書いて満たす」の規則に従う

## 対象範囲

含む:
- `quality-gates` の `standard` の完了の定義（チェックリスト）に、結合確認の出力と独立に求めた値の突き合わせの項目を 1 つ足す
- `quality-gates` の `SKILL.md` の、`standard` の「追加で要るもの」に同じ要求を足す
- 突き合わせた値が一致しない状態を「完了と呼べない状態」に含める（前提 4）

含まない:
- 突き合わせを行うスクリプト・hook の追加（前提 3）
- 設計（`design`）・要求（`requirements-design`）の手順へ、独立の値を求める工程を足すこと（前提 5）
- `standard` 以外のモードの完了の定義（前提 1）
- リリース後テスト（`release-verification`）の手順
- `design-match.py` の出力と、設計との突き合わせ (a)(b)(c) の判定の変更
- takemi-ohama/ideabase 側の不具合の修正
