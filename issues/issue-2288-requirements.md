# #2288: 本番のプランの verify が導入の確認だけを流して「リリース後テスト」を通ったと記録し、受け入れ条件ごとの記録が無いためスプリントを閉じる工程で課題が閉じない

正は課題の本文（#2288）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

スプリント m26-1（ndf v10.27.2）の本番のプラン（`supervise.py` が書く `8-release-prod.json`）は、`verify` ステップ（stage: リリース後テスト）で `release-verification-steps.py verify-install --ref main --expect 10.27.2 --runtimes claude,codex,kiro` だけを流し、exit 0 で次へ進んだ。プランはこれで「リリース後テスト」を通ったと記録し、conductor も済んだと扱った。

しかし `release-verification` の手順 2・3（受け入れ条件ごとの確認と、配布の記録の PR への `## リリース後テスト` の記録の投稿）は行われていない。その結果、仕上げのフェーズで `sprint-close.py --record-pr 2281 --with-verification --dry-run` を打つと、スプリント課題 12 件すべてが `kept_open`（理由「本番の版のリリース後テストの記録が無い」）になり、課題を閉じられなかった。スプリント PR https://github.com/devbasex/ai-plugins/pull/2268 の本文の「手動確認」が「リリース後テストへ回す」とした 2 件（#2227 の承認資料の検査の結果・#2229 の一時の worktree の片付け）も、誰も実施していなかった。

## どこで見つけたか

- 本番のプラン: `/work/ai-plugins/.ndf/tmp/sprint-m26-1/8-release-prod.json` の `verify` ステップ、結果 `/work/ai-plugins/.ndf/tmp/sprint-m26-1/8-release-prod-state/11-verify.out`
- 配布の記録の PR https://github.com/devbasex/ai-plugins/pull/2281 （`## 配布の記録` のコメントはあるが `## リリース後テスト` が無い）
- 仕上げのフェーズ（振り返り → スプリントを閉じる）での `sprint-close.py` の dry-run

## なぜこの変更の範囲外なのか

m26-1 の受け入れ条件は、工程の結果を統一した JSON で返すこと（#2227）と実行をまたぐ状態の寿命と持ち主（#2229）を扱い、本番のプランがリリース後テストのどこまでを流すかはどの条件にも入っていない。根拠: Vision（2 回の承認には未検証のまま残ることがそろって届く）・Value 7（判断の理由を残す）（MVV 版 3）

## 直さないと何が起きるか

本番のプランで流すスプリントは毎回、受け入れ条件ごとの確認が抜けたまま「リリース後テスト済み」と記録され、スプリントを閉じる工程で課題が閉じない。閉じないことに気づかずに `--with-verification` を外して閉じると、確かめていない条件が終わったように見える。

## 目的

- 課題の本文の進行の「リリース後テスト」の印を、受け入れ条件ごとに確かめた記録があることの印にする。印を見た人とスプリントを閉じる工程が、確かめていない条件を確かめたものと取り違えない状態にする

## 前提

- 前提 1: 受け入れ条件 1〜4 は、2026-11-01 の取り直しで合格した（記録: https://github.com/devbasex/ai-plugins/pull/2328#issuecomment-6551490972 ）。この変更では作り直さず、退行しないことだけを確かめる
- 前提 2: 受け入れ条件 5 の文言は変えない。進行の印は今、ステップを流す前に付く（`supervise_lib/state.py` の `record_stage` を `supervise_lib/engine.py` の `_run_step` がステップの実行の前に呼ぶ）。「リリース後テスト」の工程に限って、印を付ける時点をステップが ok で終わった後へ移せば、文言のまま満たせる
- 前提 3: 課題 #2356（進行の「リリース後テスト」の印が記録より先に付く）は、この課題の受け入れ条件 5 の不合格を起票したものであり、受け入れ条件 6・7 は #2356 の受け入れ条件 1・2 と同じ振る舞いを指す。同じ変更で両方を満たす
- 前提 4: ステップの ok は、プランの実行の核が返すステップの結果（#2337 が契約をそろえる結果）で判定する。#2337 が先に入って結果の形が変わっても、「ok で終わった」の意味は変わらない
