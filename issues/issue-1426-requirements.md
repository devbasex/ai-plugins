# #1426: スプリントの間に conductor が打つコマンドをキューと待ちだけにし、プランの外の手当てをなくす

正は課題の本文（#1426）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 要求

スプリントを流す間に conductor が打つコマンドを、プランのキューと終わりの待ちだけにする。conductor は工程を進める最上位のエージェントで、2 つのコマンドは `supervise.py queue` と `supervise.py wait` に当たる。プランのテンプレートが持たない手当てを、conductor がシェルのつなぎ・jq・sed で足さずに済むようにする。

手当てがプランの外にあると、失敗のたびに conductor がその場でコマンドをつなぎ直す。つないだコマンドは記録に残らず、止まった所から再開できず、同じ失敗を次のスプリントでも手で片付けることになる。

## 例: #1407 の設計 Pull Request のマージ（2026-09-28）

承認ゲート 1 の承認の後、conductor は次の 3 つを別々に打つ。3 つともプランに入っていない。手順は `plugins/ndf/skills/development-workflow/references/waiting.md` の「スプリントを流すコマンド」の 3・4 にある。

```bash
python3 "$SCRIPTS/merged-steps.py" merge-when-green 1423                       # 設計 Pull Request のマージ
python3 "$SCRIPTS/supervise.py" queue r-1407/3-mission-branch.json --done ...   # スプリントブランチ
python3 "$SCRIPTS/supervise.py" queue r-1407/4-impl-1407.json --done ...        # 実装
```

設計 Pull Request https://github.com/devbasex/ai-plugins/pull/1423 のマージは 2 回止まった。

1. 継続的統合の古い実行の失敗が残った。本文の「決めたこと」を同期する前の push で `PR body decisions` の実行が走り、失敗のまま残った。同期の後の実行は成功していたが、`merge-when-green` は失敗として止まった。conductor が `gh run rerun` で失敗した実行を再実行した
2. 用語集が衝突した。並行して進めた設計 Pull Request https://github.com/devbasex/ai-plugins/pull/1424 が先にマージされた。2 本とも `docs/glossary/glossary.json` の同じ位置へ語を足していた。conductor が両方の語を残し、`glossary.py render` で `docs/glossary.md` を作り直した

止まるたびに、conductor は `sleep 20; merge-when-green …; git pull && queue …` を 1 本のシェルでつなぎ、3 回起動し直した。前景の `sleep` は hook が拒むが、バックグラウンドの Bash の `sleep` と、NDF のスクリプトどうしのつなぎは拒まない。

## 目的

- スプリントの承認ゲート 1 の承認の後から本番の配布までを、conductor がキューと待ちのほかにコマンドを打たずに流せるようにする（Neural Development Factory のランナーが NDF を無人で動かすときに、プランの外の手当てで止まらないようにする）
- 途中で止まったプランを、プランのファイルを写して作り直さずに、キュー 1 回で続けられるようにする
- 承認ゲート 2 の承認の後に、承認の記録を書き忘れて本番のプランが止まらないようにする。ただし、利用者の承認が無いまま記録を書かない

## 前提

- 前提 1: このスプリントの #1426 の設計と実装は、残る子課題 4 件（#1912・#1918・#1920・#1921）の受け入れ条件を引き継いで 1 本で扱う。スプリント m1426 の課題の一覧（#1426・#1698・#1455・#1631）に子課題は入っていないが、#1426 の範囲（表の 12 と元の受け入れ条件 5 を除く）で残るのはこの 4 件だけである。子課題は実装の Pull Request のマージの後に、受け入れ条件を確かめて閉じる
- 前提 2: 元の受け入れ条件のうち 2・3・7〜11 と、表の 2・3・5〜10 は、閉じた子課題（#1645・#1913・#1915・#1916・#1651・#1767・#1340・#1917）で済んでいる（2026-10-11 の「子課題」の表）。この課題では作り直さず、受け入れ条件 18 の実物の確認で退行が無いことだけを見る
- 前提 3: 受け入れ条件 1〜4・9〜12 は `pace: normal` の経路を対象にする。`pace: auto` / `fast` は設計 Pull Request のマージ（`plan_mvv_design` の `approve` → `merge_steps`）・ステージのつなぎ（`then_of`）・本番の承認（MVV 判定）を既に持つため変えない。受け入れ条件 5〜8・13〜16 はどの進め方にも効く
- 前提 4: 承認ゲート 2 で利用者が承認したことは、本番のプランのステップが自分で作り出さない。ステップが `--by user` の記録を書くのは、利用者の承認の証跡があるときだけで、何を証跡とするか（`sprint-state.py gate <状態> "関門 2" --by user --outcome approved` の記録・承認資料のハッシュの一致など）は設計で決める（未決 1）。キューに本番のプランを入れたことだけを承認とは扱わない
- 前提 5: 止まったプランを続ける手段の形（`queue` の引数か、目録の `resume` の形か）は設計で決める。形にかかわらず、`run <プラン> --from <ステップ>` の判定（judge のステップが前の実行の結果を読む、#1676）を変えない
- 前提 6: 取り込んだ課題の引数の形（例: `--absorb 1688:1693`）は設計で決める。承認ゲート 1 の後に設計の結果の表から取り込む今の経路（`supervise_lib/design_stage.py` の `rewrite`）は残し、2 つの経路で取り込んだ課題の扱い（その実装のプランを流さない）を揃える
- 前提 7: 後片付けで消えた作業ディレクトリから起動したキューが `--then` で落ちる不具合（#1886）は、この課題で直さない。承認ゲート 1 の後を 1 本のキューにつなぐと当たる経路が増えるため、手順書はキューをリポジトリの根から起動する形で書く

## 受け入れ条件

- [ ] 1. `pace: normal` で `--design` を渡した `new sprint` の目録（`sprint.json`）に、承認ゲート 1 の後の最初のステージとして設計 Pull Request をマージするステージがある。そのプランは設計 Pull Request ごとに `merge_steps`（`merge-gate` → `merge`）を持ち、Pull Request の番号を設計のプランの報告から読む（番号を conductor が書き込まない）
- [ ] 2. 同じ目録で、承認ゲート 1 の後のステージ（設計 Pull Request のマージ → 設計の結果 → スプリントブランチ → 実装 → 検査 → 配布）が、最初のステージの `command` 1 本に `--then` でつながる。2 つ目以降のステージは `command` を持たず `then_of` を持つ
- [ ] 3. `--design` を渡さない `pace: normal` の `new sprint` では、マージのステージを置かず、スプリントブランチから配布までが `--then` でつながる
- [ ] 4. `waiting.md` の「1 スプリントの流し方」と「スプリントを流すコマンド」で、承認ゲート 1 の承認の後に conductor が打つコマンドがキュー 1 回と `wait` 1 回になり、`merge-when-green` と `release-steps.py approve` を conductor が打つ手順が無い。書いたコマンドは一時ディレクトリで `new sprint` を打って、目録の `command` と一致することを確かめる
- [ ] 5. 止まったプランを途中のステップから続け、完了したら `--then` の後続のステージも流すコマンドが 1 つある（形は設計で決める。前提 5）
- [ ] 6. 5 のコマンドで続けたとき、後続のステージは今の条件（前のステージのプランがすべて完了）のときだけ流れ、止まったプランと同じステージで既に完了していたプランは流し直さない
- [ ] 7. 一時ディレクトリで、3 ステップ目で止まるプランと後続のステージを作り、5 のコマンドで続けると、止まったステップから流れて後続のステージまで完了する（テストで確かめる）
- [ ] 8. `new sprint` の目録の `resume` と `waiting.md` の止まったときの手順が、5 のコマンドを 1 つだけ示す
- [ ] 9. `pace: normal` の本番のプラン（`new sprint` が書くものと `new release --channel prod` が書くもの）の先頭に、承認の記録を書くステップがある。`--approved-sha` は開発版のプランの `facts` のステップの結果（`metrics.approved_sha`）から読む
- [ ] 10. 開発版の `facts` の後に承認資料が書き直されていれば（SHA が違えば）、9 のステップは記録を書かずに承認ゲート（exit 10）で止まる
- [ ] 11. 利用者の承認の証跡（未決 1 で決めるもの）が無いとき、9 のステップは `--by user` の記録を書かずに承認ゲート（exit 10）で止まり、本番の `release` へ進まない
- [ ] 12. 一時ディレクトリに開発版の `facts` の結果・承認資料・利用者の承認の証跡を置いて本番のプランを流すと、`release-steps.py approve` を手で打たずに `release` の承認の照合を通る（`release` の `gh` はスタブで止める）
- [ ] 13. `new sprint` に取り込んだ課題と取り込み先の対応を渡すと、取り込み先の設計のプランの `課題` が両方の番号を持ち、requirements と design のステップの `prompt` が両方の課題を参照する
- [ ] 14. 取り込んだ課題には設計のプランを書かない。実装のプランは書かないか、書くなら `実行の条件` で飛ぶ（承認ゲート 1 の後に設計の結果から取り込んだときと同じ扱い）
- [ ] 15. 取り込んだ課題が受け入れ条件の節を持たなくても、`new sprint` の入力の確認（`sprint_inputs.criteria_refusal`）で止まらない
- [ ] 16. 取り込み先の課題が `--design` にも `--issue` にも無いときは、プランを書かずに理由を返す
- [ ] 17. `pace: auto` と `fast` の `new sprint` が書くプランの並びと本番のプランの先頭は変わらない（既存のテストで確かめる）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | プランが止まったとき、プランのファイルを写さずに 1 コマンドで続けられる（受け入れ条件 5）。続けた回の耐久の記録は、プロセスが落ちた後に同じコマンドを打ち直すと続きから流れる今の振る舞いを保つ |
| 運用・保守性 | 止まった・続けたことはキューの進捗ログと done に残り、conductor が手で作ったプランのファイル（`-r2.json` など）を残さない |
| 移行性 | 既に書き出した目録とプラン（この版より前の `new sprint` が書いたもの）は、今のキューでそのまま流せる。新しい引数は足すだけで、今の引数の意味を変えない |
| セキュリティ | 本番の配布（戻せない操作）の前の承認の記録は、利用者の承認の証跡が無ければ書かない（受け入れ条件 11。共通原則の C4・Value 2） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる（足すだけ）。`supervise.py queue` か目録の `resume` に止まったプランを続ける形が、`supervise.py new sprint` に取り込んだ課題の引数が増える。今の引数と結果 JSON の項目の意味は変えない |
| データ | 変わる。`pace: normal` の目録（`sprint.json`）のステージに、設計 Pull Request のマージのステージと `then_of`・`resume` が増える。スキーマの移行は要らない |
| 既存の振る舞い | `pace: normal` のスプリントで、承認ゲート 1 の後のステージが 1 本のキューで続けて流れる。本番のプランが承認の記録を自分で書く |
