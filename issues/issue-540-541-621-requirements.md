# #540 / #541 / #621: 並列の実行計画を初めに作り、メモリの見る本数の中で重なりを許して進める

設計は [issue-540-541-621-design.md](issue-540-541-621-design.md) にある。この文書は「何を満たすか」だけを扱う。

**3 つの課題を 1 本の設計 Pull Request で決める。** 3 つとも「まとまりをどれだけ並列に進めるか」の
入力（依存・重なり・メモリ）と、その判断を置く場所（実行計画・マイルストーンの説明）を扱う。

| 主題 | 課題 | 中身 |
| --- | --- | --- |
| A 実行計画 | #540 | 要求と設計の段階で並列にできる工程を実行計画に書き、工程の終わりごとに組み替える。依存は工程の対で書き、重なりは目安の範囲で許す |
| B マイルストーンの組 | #541 | マイルストーンへ課題を入れるときに「組」（触る場所の見込みと依存）を説明へ書き、実行計画の初期値にする |
| C 本数とメモリ | #621 | 担当を起動する前にホストのメモリを測り、起動してよい本数を決める。OOM Killer の発生を見て本数を下げる |

## 目的

- 長い待ちを持つ工程の間に、依存しない次の工程（設計）が起動される
- 触る箇所が多少重なる課題も、作業ツリーで分けて並行し、競合はマージの時点で解く。**レビューした差分と入る差分は食い違わない**
- 並列にできる単位が、マイルストーンを割り振る時点から実行計画まで同じ言葉で引き継がれる
- 並行の本数がホストのメモリで上から抑えられ、OOM Killer が本体を落として全担当が中断することが起きない

## 実測（要求の根拠）

### 並行度は、指示があると上がり、無いと 0 に戻る

**#541 の 11 版（v10.2.0〜v10.9.1）は 9 版が 0.0% だった。** その後の版を同じ方法で測った
（タグの間にマージされた Pull Request の作成からマージまでを区間とし、2 本以上が重なった時間の割合。
2026-09-17、`gh pr list --state merged`）。

| 版 | PR 数 | 期間（分） | 重なり（分） | 並行度 | 最大同時 |
| --- | ---: | ---: | ---: | ---: | ---: |
| v10.10.1 | 4 | 718 | 0 | 0.0% | 1 |
| v10.11.0 | 29 | 6924 | 6541 | 94.5% | 9 |
| v10.12.0 | 12 | 1872 | 604 | 32.3% | 4 |
| v10.13.0 | 18 | 1029 | 230 | 22.3% | 4 |
| v10.14.0 | 5 | 1030 | 0 | 0.0% | 1 |

**v10.11.0 以降は、利用者が「できるだけ並列で」と指示したまとまりで上がった。** 並列にする判断は
進行側の会話の中にしかなく、規約にも記録にも残らない。v10.14.0 は再び 0.0% である。

**v10.11.0 の設計の承認は 4 本 → 4 本 → 1 本 → 1 本 → 1 本の 5 回に分かれた（#540 のコメント）。**
後半の 3 回は実装のマージを待ってから設計を始めたためで、依存していたのは実装の順序だった。

### 並べた本数で本体が落ちた

**v10.11.0 を 5〜6 本の担当で並行したとき、claude 本体が 2 回落ちた（#621）。** 3 本へ下げた後は
落ちていない。担当 1 本はサブエージェントに加えて、cross-review / cross-refactoring の CLI
（codex / agy / kiro）とテストを起動する。runtime-smoke はコンテナも起動する。

**このホストの値（2026-09-17 時点）。** 他のプロジェクトのコンテナも同じ VM に常駐する。

| 項目 | 値 | 確かめ方 |
| --- | --- | --- |
| メモリ（VM 全体） | 21GiB、available 9.5GiB | `free -h` |
| スワップ | 2.0GiB、使用 1.7GiB | 同上 |
| cgroup の上限 | `max`（上限なし） | `cat /sys/fs/cgroup/memory.max` |
| cgroup の最大使用量 | 9.9GiB（このコンテナの起動以来） | `cat /sys/fs/cgroup/memory.peak` |
| OOM Killer の発生 | `oom_kill 1`（このコンテナの起動以来） | `cat /sys/fs/cgroup/memory.events` |
| claude 本体の常駐 | 約 470MiB | `ps -eo rss,comm --sort=-rss` |

**このマイルストーンの進行は、空き 8GiB・スワップ使い切りの状態から 2 本で進めている。**

**cgroup の値と VM の値は別物である。** cgroup の `memory.max` が `max` のとき、上限を決めるのは
VM 全体の空きで、他のコンテナの使用量もそこへ入る。`memory.events` の `oom_kill` はこの cgroup の中で
殺されたプロセスの数である。

### 重なりを見分けたのは設計の後だった

**マイルストーン 04 では #643 → #646 を逐次にした（#541 のコメント）。** `scripts/lib/worktree-common.sh`
と worktree Skill の `SKILL.md` を両方が触るためで、**どのファイルを触るかは設計が出た後にしか確定
しなかった。** 対象（マイルストーン）だけからは本数を決められなかった。

## 前提

| # | 前提 |
| --- | --- |
| 1 | 担当はそれぞれの作業ツリー（`.worktrees/<ブランチ名>`）で動く。作業ツリーを使わない進め方は並行の対象にしない |
| 2 | 担当を起動し、承認を仲介し、実行計画を持つのは進行側（親）である。担当は実行計画を書き換えない |

| 5 | 1 本あたりのメモリの使用量は、起動する CLI・テスト・コンテナで変わる。**規約は値の出し方と初期値を持ち、値はホストで測って直す** |
| 6 | 進行の記録は 1 回の Bash 実行につき 1 件だけ積む（#487 が直るまでの運用） |
| 7 | 工程を窓（使い捨てのサブエージェント）へ出す運転は G3（#550）が決める。この文書の「担当」は、G3 の窓も含めて「進行側が起動した実行主体」を指す |

- [ ] AC36: コンテナを起動する検査を持つ担当は同時に 1 本までと書かれている

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | 本数を決める値が OOM Killer の発生より前に出る。本体が再起動した後も、実行計画から本数と進み具合を読み直せる |
| 運用・保守性 | 本数の初期値を変えるときに直す場所が 1 か所である。測った値が実行計画に残り、初期値を直す根拠になる |

設計で決めきれなかったことは、設計文書の「未確認のまま残ること」が持つ。

## 用語

| 用語 | 意味 |
| --- | --- |
| 進行側 | 課題を束ね、担当を起動し、承認を仲介する実行主体。G3 の「親」 |
| 担当 | 進行側が起動し、作業ツリー 1 つで 1 本の Pull Request を進める実行主体。G3 の窓を含む |
| 本数 | 同時に動いている担当の数。**CLI・テスト・コンテナのどれかを起動しうる担当を数える** |
| 実行計画 | まとまりの課題を、束・工程ごとの依存・触る箇所・着手できる時点で並べた表。進行側が持つ |
| 束 | 1 本の設計 Pull Request で決める課題の集まり（マイルストーン 10 の G1〜G4） |
| 組 | マイルストーンの説明に書く、触る場所の見込みと依存でまとめた課題の集まり。実行計画の束の初期値 |
| 重なり | 2 つの Pull Request が同じファイルを触ること。節（見出し）・関数の単位で程度を分ける |
| 長い待ち | 構造改善・実装レビュー・ドキュメントレビューの収束、承認とマージを待つ間 |
| 並行度 | 対象の Pull Request のうち、2 本以上が同時に開いていた時間の割合 |
