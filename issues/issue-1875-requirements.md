## 目的

- 機械の判定が、記録の無い状態を「確かめ済み」と取り違えて課題を閉じること（#1875）と、「手動確認は無い」と書いた行を「確かめていない手動確認」と取り違えて承認ゲートで止まること（#1675）を無くす
- どちらも、人が後から結果を読んで「なぜ閉じた / 止まったか」を区別できる状態にする

## 前提

- 前提 1（#1875）: 「記録の置き場をプランが知らない」は、`--record-pr` の新しい値（形は設計で決める）で `sprint-close.py` へ渡す。`--record-pr 0` の意味（本番を飛ばした・配布なし。`--issues` と一緒のときだけ受け、閉じる条件を見ずに閉じる）は変えない
- 前提 2（#1875。起票者の「決めること」への答え）: 本番の行の無い経路（`[STG]` だけ）も、merge（`merged-by-check`）と manual の経路と同じく「記録の置き場が分からない」として扱い、課題を開いたまま残す。理由: 閉じ損ねは人が 1 回の操作で閉じて直せるが、誤って閉じた課題は確かめていないことが結果から見えない（共通原則の上位の原則・Value 1 の「まず届ける」は閉じる側を急ぐ理由にならない）
- 前提 3（#1875）: 届けない経路（`delivery` が `[]`、`STAGE_NONE`）だけから成るスプリントは、今どおり `0`（配布なし）を渡す
- 前提 4（#1675）: 「手動確認が無い」と読む行は、表の 2 列目の前後の空白を除いた文が「無し」「なし」「不要」「ない」「-」「—」「―」のどれかと等しいか、そのどれかの直後が「（」「(」「。」「、」または空白で続くものとする。「無しの場合は〜」のように語の続きがある文は手動確認の行のまま読む
- 前提 5（#1675）: 要求の雛形（`requirements-design` の `references/spec-template.md`）の「手動確認（マージ前）」の行には「無ければ行を消す」が既にある。雛形と手順の文は変えない
- 前提 6（#1675）: 既に作られた PR 本文の `## 手動確認` に残る「無し」の未チェック行は、検査のプランの pr ステップを流し直すと節ごと作り直されて消える（`manual_section` は要求から節を作り直す）。merge-gate 側（`unchecked_before_merge`）には判定を足さない
