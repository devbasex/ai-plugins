## 具体例: 性質の違う 2 つのプロジェクトで同じフローを回す

NDF の開発ワークフローを使うどのプロジェクトでも、棚卸しを 3 段に分け、数周回に 1 回の「見直し」でニーズとシーズを調べて起票する。**フローは共通で、何を材料に調べるかはプロジェクトが宣言する。**

| | Web サービス（例: 利用者向けの業務システム） | 開発ツールのプラグイン（例: このリポジトリ ai-plugins） |
| --- | --- | --- |
| 毎周回の差分の棚卸し | その周回の変更で食い違った本文を直す・直ったのに開いたままの課題を閉じる・新しく起票した課題に見積を付ける | 同じ |
| 3 周回に 1 回の見直し | 枝刈り → 順位付け・マイルストーン再編 → 調査 → 起票 | 同じ |
| ニーズの材料（宣言） | アクセス解析・機能ごとの利用率・問い合わせとサポートの記録・エラーの監視・競合の SaaS | Skill の利用統計・開発ループの記録（人へ戻した承認ゲート・止まった理由）・振り返り・競合の AI 開発エージェント |
| シーズの材料（宣言） | 使っているフレームワーク・ライブラリとクラウドの変更点、それらの競合（置き換え先の候補）・法令やブラウザの変化 | Claude Code・codex など配布先の CLI の変更点・Claude API とモデルの更新・使っているライブラリ（pytest・uv など）とその競合 |
| 十数周回に 1 回の大整理 | 後回しのマイルストーンの中身を前倒し・やらない・据え置きに分ける。未完了の課題すべてを原因の型で分け、Issue 単位では直らない根本原因を見つけたら、大方針の Issue を起票して課題とマイルストーンを組み直す | 同じ（ai-plugins の 2026-11-01 の大整理は、未完了 194 件から大方針 #2335 を立て、113 件を柱 9 本の子へ付け直した） |

たとえば Web サービスの見直しでは、アクセス解析から「月次の帳票の出力が 1 回 40 秒かかり、離脱が多い」を見つけてニーズの Issue にする。使っているフレームワークの新しい版の変更点から「今の自前のキャッシュを置き換えられる機能」を、使っている帳票のライブラリの競合から「出力が速く保守の続いている置き換え先」を見つけて、シーズの Issue にする。どちらも出典つきで起票し、プロジェクト MVV の判定が「従う」のものだけを順位付けに入れる。

## 何が起きたか

`/ndf:development-workflow` には「課題を見つけて足す」工程が `out-of-scope`（作業中に見つけた範囲外の不具合）と振り返り（その変更から出た取りこぼし）しかない。どちらも**いま触っているコードの近く**から課題を拾う。このため、どのプロジェクトでも開発が進むほど微細な不具合修正と小さな改善の Issue が増え、プロダクトの方向を変える課題が入ってこない。

棚卸し（`backlog-refinement`）は「扱う 5 つ」（誤りの訂正・マイルストーンの設定・やらないの判断・ルートコーズの判断・順位付け）を、スプリントの終わりに毎回同じ重さで回している。頻度の違う作業が 1 つの工程に混ざっている。

NDF を開発しているこのリポジトリでの実測（2026-11-01）:

| 項目 | 値 | 出所 |
| --- | ---: | --- |
| open の Issue | 185 件 | `gh issue list --state open` |
| そのうち後回しのマイルストーン | 80 件（43%） | 同上 |
| 周回ごとの棚卸しの所要 | 206〜224 秒・1.41〜1.61 ドル | 開発ループ l20261031 の周回 2・3 の `refine` のステップ |
| 1 回の棚卸しで区分を決める件数 | 10 件まで（候補の上限） | `backlog-refinement` の手順 1 |
| 周回 4 の棚卸しの持ち越し | 約 160 件 | 開発ループ l20261031 の `laps.md` |

**毎周回の棚卸しは重いのに、全体の見直しは追いついていない。** 1 回 10 件では、持ち越しが周回をまたいで溜まり続ける。一方で、差分の棚卸し（変更で食い違った課題を直す）は毎周回でないと遅れる。

## 目的

- 開発ワークフローに「課題を見つけて足す」工程を、いま触っているコードの近く（`out-of-scope`・振り返り）以外の 2 つの側面（利用動向と市場から見たニーズ・技術と環境の変化から見たシーズ）で持たせ、プロダクトの方向を変える課題が一覧に入るようにする
- 棚卸しを、遅れたときの害の出方で 3 つの深さ（毎スプリントの差分の棚卸し・数スプリントに 1 回の見直し・十数スプリントに 1 回の大整理）に分け、毎スプリントの棚卸しを軽くしつつ、全体の見直しと根本原因の発見が追いつく状態にする
- これらを ai-plugins に限らず、NDF を使うどのプロジェクトでも、そのプロジェクトの性質に沿った材料で同じフローとして回せるようにする

## 前提

- 前提 1: 数え方の単位は開発ループの周回とし、`--loop` を使わないプロジェクトではスプリント（版）の数で数える。どちらも「前の見直し・大整理から何回目か」が記録から機械で数えられる
- 前提 2: 「見直し」の対象は、後回しのマイルストーン（宣言で指す）を除いた open の課題すべてである。大整理の対象は、後回しを含む未完了の課題すべてである
- 前提 3: 既定の頻度は見直し 3・大整理 12 とし、設計で実測（周回ごとの棚卸しの所要と、open の件数の推移）から見直す。値はプロジェクトの設定で上書きできる
- 前提 4: 原因の型の既定の一覧は、用語集の「原因の型」（A〜I。#2335）を使う。プロジェクトは自分の一覧を宣言で置き換えられる
- 前提 5: 本番の利用の記録を読む先に認証が要るときは、その認証は人が済ませる（共通原則 C1）。NDF は認証済みの読み先を、宣言した範囲だけ読む
- 前提 6: 利用の記録を読む範囲の宣言が無いプロジェクトでは、利用の記録を何も読まず「材料なし（未宣言）」と報告する（未決 4 で利用者が別の既定を選んだらそれに従う）
- 前提 7: 調査が外部の Web（配布先の CLI の変更点・ライブラリのリリースノート・競合の製品のページ）を読むのは読み取りだけで、外部へ書き込まない（C5・C8 に当たらない）
- 前提 8: 起票・ラベル・マイルストーンの付け直しは GitHub Issues に対して行う。GitHub 以外の課題管理（`.ndf/project.json` の `issues` が `markdown`・`redmine` など）では、見直しの起票と付け直しは行わず、行わなかったことを報告に書く

## 対象範囲

含む:
- 毎スプリントの棚卸しを差分の棚卸しだけへ絞ること
- 見直しのフェーズ（枝刈り・順位付け・マイルストーンの再編・ニーズとシーズの調査・ホットスポットと失敗の集計・起票）と、その起動の条件
- 大整理（原因の型での分類・計数・コードの横断の計測・大方針の起票・付け直しと戻し・後回しの再評価）と、その起動の条件
- 待ち時間に調査を少しずつ進める調査の supervisor と、調査の記録
- 見直しの持ち主の宣言・ロック・生きている印・引き取り
- 調査の材料の宣言（項目・`project-analysis` での案の出し方・利用の記録を読む範囲）
- 見直しと大整理の報告（統一 JSON レポート）
- `--loop` を使わない進め方での単独の起動

含まない:
- GitHub 以外の課題管理への起票・付け直し（前提 8。今の棚卸しと同じ範囲）
- 利用の記録の読み先（アクセス解析・ログの基盤など）への認証の設定と、読み先そのものの構築
- `out-of-scope` と振り返りの起票の手順の変更
- 本番の利用の記録の個票（集計していない行）を読むこと
- 新しい承認ゲートを作ること

## 用語

| 用語 | 意味 |
| --- | --- |
| 差分の棚卸し | 毎スプリントのまとめで行う棚卸しの深さ。そのスプリントの変更で食い違った本文の訂正・直ったのに開いたままの課題を閉じる・閉じた親の子の見直し・そのスプリントで起票した課題への見積の段階の付与だけを行う |
| 見直し | 数スプリントに 1 回行う棚卸しの深さ。後回しを除く open の課題の枝刈り・順位付け・マイルストーンの再編と、ニーズ・シーズの調査からの起票を行う |
| 大整理 | 十数スプリントに 1 回行う棚卸しの深さ。未完了の課題すべてを原因の型で分け、Issue 単位では直らない根本原因を探し、見つかれば大方針を立てて課題とマイルストーンを組み直す。後回しの再評価を含む |
| 後回しの再評価 | 後回しのマイルストーンの課題を、前倒し・やらない・据え置きに分けること。大整理の一部 |
| ニーズの調査 | 宣言した利用の記録と市場・競合から、利用者が求めている変更を探すこと |
| シーズの調査 | 宣言した技術の構成・ライブラリの競合・周辺環境の変化から、取り入れられる変更を探すこと |
| 調査の記録 | 調査の項目ごとに出典と調べた日時を持つ結果。見直しのフェーズだけが読んで起票に使う |
| 材料の宣言 | プロジェクトがニーズとシーズの調査で読む先（プロダクトの種類と利用者・利用の記録と読む範囲・市場と競合・技術の構成・ライブラリの競合・周辺環境・後回しのマイルストーン）を書いたもの |
| 見直しの持ち主 | 見直しのフェーズ（待ち時間の調査を含む）を受け持つ 1 つのセッション。宣言をロックの中で取り、終わったら解放する |
| 大方針 | 大整理で見つけた根本原因を直す親の Issue。柱と受け入れ条件を持つ（例 #2335） |

## 受け入れ条件

番号は起票時の版から変えない（設計と考察が番号で指しているため）。

- [ ] 1. 毎スプリントのまとめの棚卸しは差分の棚卸しだけを行う: 変更で食い違った本文の訂正、直ったのに開いたままの課題を閉じる、閉じた親の子の見直し、そのスプリントで起票した課題への見積の段階の付与。優先順位の再評価・順位付け・マイルストーンの再編・枝刈りは行わない
- [ ] 2. 見直しのフェーズが、枝刈り（使われていない機能の廃止を含む）→ 優先順位の再評価と順位付け → マイルストーンの再編 → ニーズの調査 → シーズの調査 → ホットスポット分析と失敗の記録の集計 → 起票 の順に通り、その順が報告に残る
- [ ] 3. 見直しは後回しのマイルストーン（宣言で指したもの）の課題を対象から外す。後回しの課題の再評価（前倒し・やらない・据え置き）は大整理の中で行う。後回しの課題にも毎スプリントの差分の棚卸しはかかる
- [ ] 4. 見直しと大整理は、前の実行からの回数（既定は見直し 3・大整理 12）か溜まり具合の条件に当たったときに、スプリントのまとめで起動する。値はプロジェクトの設定で上書きできる。どの条件で起動したか（起動しなかったときはその判定）を周回の記録に残す
- [ ] 4a. 選べる課題が尽きて開発ループが `no_issue` で止まる前に、前の見直しから回数が満ちていなくても見直しが 1 回起動する
- [ ] 5. 見直しと大整理は `--loop` を使わない進め方でも、人が呼んで単独で起動できる
- [ ] 6. 調査は、conductor がプランの完了を待っている間に、並列の上限に空きがあるときだけ調査の supervisor を立ち上げて少しずつ進める。調査は結果を調査の記録に書くだけで、Issue の起票・クローズ・順位の変更をしない。待っていたプランが終わったら今の項目を終えて止まり、次の待ちで続きの項目から始める。見直しのフェーズは溜まった結果を読み、足りない項目と古い項目（前の見直しより前に調べたもの）だけをその場で調べる
- [ ] 6a. 並列の上限に空きが無いとき、調査の supervisor は立ち上がらない（スプリントの作業の起動を遅らせない）
- [ ] 7. 調査の記録は項目ごとに出典（URL・記録のパス・実行したコマンド）と調べた日時を持つ。調査の費用と時間は開発ループの予算に数え、周回の記録に別の行で残る
- [ ] 8. 並列で複数のセッションが動いていても、見直しのフェーズ（待ち時間の調査を含む）を行うのは見直しの持ち主 1 つだけである。持ち主は `.ndf/` に宣言を置いてロックの中で取り、終わったら解放する。2 つのセッションが同時に宣言を取ろうとしても、片方だけが取れることをテストで示す
- [ ] 9. 持ち主のセッションが終了・中断したら（プロセスが生きていない、または最後に動いた時刻から寿命を過ぎた）、別のセッションが宣言を引き取り、調査の記録に残った項目の続きから進める。誰から引き取ったかを記録に残す
- [ ] 9a. 持ち主のセッションが生きていて寿命の内にあるとき、別のセッションは宣言を引き取らない
- [ ] 10. 調査の材料（プロダクトの種類と利用者・利用の記録・市場と競合・技術の構成・ライブラリの競合・周辺環境・後回しのマイルストーン）はプロジェクトの材料の宣言から読む。フローとスクリプトに特定のプロジェクトの名前・マイルストーン名・材料を書かない
- [ ] 11. 材料の宣言は `project-analysis` の手順で案を出し、人が確かめて書ける。宣言の無い側面は「材料なし（未宣言）」と報告して飛ばし、推測で起票しない
- [ ] 12. 利用の記録を読む範囲（集計値だけ・期間・マスクの規則）を材料の宣言で持ち、範囲の外を読まない。範囲の宣言が無いときは利用の記録を読まない（前提 6）
- [ ] 13. 起票するニーズ・シーズの Issue は、出典と、そのプロジェクトの MVV のどこに当たるかを本文に持ち、区別できるラベルが付く。1 回の見直しで起票する件数に上限があり、上限を超えた分は報告に「起票しなかった」として載る。MVV 判定が「従う」以外の課題は順位付けへ入れず、人の判断待ちに置く
- [ ] 14. シーズの調査は、宣言した主要なライブラリ・フレームワークごとに、使っているものの変化（新しい版・非推奨・保守の停止・脆弱性・ライセンス）と競合（置き換え先の候補と比べた観点）を見る
- [ ] 15. 見直しの報告（統一 JSON レポート）に、閉じた件数・起票した件数・open の件数の前後・順位の変化・飛ばした側面とその理由・起動した条件が載る
- [ ] 16. 性質の違うプロジェクト（このリポジトリと、novel・carul・bi-tools の 3 つ。2026-11-02 承認ゲート 1 で利用者が選んだ）の材料の宣言で見直しを通し、どのプロジェクトでも宣言に沿った材料で調べたことを報告で示す

- [ ] 19. 大整理は、未完了の課題すべてを原因の型で分け、型ごとの件数と課題の集まる部品を数え、コードの横断の計測（プロジェクトが宣言した観点）で裏付け、Issue 単位では直らない根本原因の有無を報告する（統一 JSON レポート）

## 考察

起票時の検討で、受け入れ条件の出所である。この仕様の語に合わせ、「追従」を「差分の棚卸し」、見直しの「担当」を「持ち主」へ言い換えた。

### 1. 棚卸しを頻度で 3 段に分ける

遅れたときの害の出方で分ける。この分け方はプロジェクトの性質によらない。

| 段 | 作業 | 遅れると何が起きるか | 頻度 |
| --- | --- | --- | --- |
| 差分の棚卸し | 変更で食い違った本文の訂正・直ったのに開いたままの課題を閉じる・閉じた親の子の見直し | 次のスプリントが、直っている課題や前提の違う課題を選ぶ。害がすぐ出る | **毎スプリント** |
| 差分の棚卸し | そのスプリントで起票した課題に見積の段階を付ける | 段階が無い課題は順位に並ばず、選ばれない | **毎スプリント** |
| 見直し | 優先順位の再評価・順位付け・マイルストーンの再編・枝刈り（やらない・重複・ルートコーズへの統合）、ニーズとシーズの調査と起票 | 順位は数スプリントでは大きく動かない。件数の増加の害はゆっくり出る | 数スプリントに 1 回 |
| 大整理（後回しの再評価を含む） | 後回しのマイルストーンの中身を、前倒し・やらない・据え置きに分ける。課題の集まりから根本原因を探し、見つかれば大方針を立てて組み直す（考察 11） | 「今は選ばない」と決めた課題で、状況が変わることは少ない。毎回見ると見直しの大半を占める | 十数スプリントに 1 回 |

- 見直しは後回しのマイルストーンを対象から外す。ただし差分の棚卸しは後回しの課題にも毎スプリントかける。前提が古いまま十数スプリント後の再評価に入ると、判断を誤るためである
- 差分の棚卸しは差分から機械で候補が決まる（`backlog-refinement` の手順 1 の「機械の候補」「コミットの件名」「親 issue」）ため、件数が少なく速い。見直しは全件を見るので、まとめて回す方が判断がそろう
- 数え方は開発ループの周回を基本とし、`--loop` を使わないプロジェクトではスプリント（版）の数で数える

### 2. 「見直し」のフェーズの順序

**枝刈り（使われていない機能の廃止を含む）→ 優先順位の再評価と順位付け → マイルストーンの再編 → ニーズの調査 → シーズの調査 → ホットスポット分析と失敗の記録の集計 → 起票** とする。先に減らしてから足すのは、足した課題を古い課題と同じ基準で順位付けするためと、件数の上限（下の 8）を守るためである。

### 3. 調査の材料はプロジェクトが宣言する

何を見ればニーズとシーズが分かるかは、プロジェクトの性質で大きく違う。フローに材料を書き込むと、特定のプロジェクトでしか成り立たない。**材料はプロジェクトの宣言に置き、フローは宣言を読むだけにする。** 宣言の置き場は今の `.ndf/project.json`（`project-analysis` が測定 → 答え → 書き出しで作る）に新しい項目として足すのが自然である。

| 宣言する項目 | 中身 | 解析で埋められるか |
| --- | --- | --- |
| プロダクトの種類と利用者 | Web サービス・ライブラリ・開発ツール・社内システムなど。だれが使うか | README・指示書から案を出し、人が確かめる |
| ニーズ: 利用の記録 | 利用動向を読む先と読み方（アクセス解析・利用ログ・DB の集計・問い合わせ・エラーの監視・アプリストアの評価・会話の記録など）。読むコマンドか手順 | 設定ファイル・依存（解析の SDK など）から候補を出す。読む権限と範囲は人が書く |
| ニーズ: 市場と競合 | 比べる相手のサービス・製品と、見る観点 | 人が書く（空でもよい） |
| シーズ: 技術の構成 | 言語・フレームワーク・ライブラリ・クラウド・外部 API・配布先の基盤 | 既存の `languages` と依存の定義（lock ファイルなど）から埋まる |
| シーズ: ライブラリの競合 | 使っているライブラリ・フレームワークごとの置き換え先の候補と、比べる観点（保守の状況・性能・ライセンス・移行の費用） | 主要な依存から候補を出し、人が確かめる。見る対象の依存は宣言で絞る（全部の依存は見ない） |
| シーズ: 周辺環境 | 法令・業界標準・ブラウザや OS など、見ておく変化 | 人が書く（空でもよい） |
| 後回しのマイルストーン | 「今は選ばない」課題を置くマイルストーン。名前ではなく宣言で指す | 人が書く |

- 宣言が無い側面は、見直しの報告に「材料なし（未宣言）」と書いて飛ばす。材料の無いまま推測で起票しない
- 本番環境の利用の記録には個人情報や秘密が含まれうる。読んでよい範囲（集計値だけ・期間・マスクの規則）を宣言に持たせ、範囲の外は読まない。読む先の認証が要るときは、人にしかできない操作として扱う
- ライブラリの調査は 2 つを見る。**使っているものの変化**（新しい版の機能・非推奨・保守の停止・脆弱性・ライセンスの変更）と、**その競合**（同じ役割で、より速い・保守が続いている・自前の実装を置き換えられるもの）。自前で作った部分を既存のライブラリへ置き換える候補もここから出る
- 方向の判断はプロジェクトの MVV（`project-mvv`）に寄せる。調査で見つけた課題の採否は、そのプロジェクトの MVV の判定で決める

### 4. ニーズとシーズのほかに見直しで使う手法

ニーズとシーズは「足す」側の調査である。見直しでは、機械で材料が取れ、プロジェクトの性質によらず働く次の 3 つも通す。

| 手法 | 中身 | 材料 |
| --- | --- | --- |
| 使われていない機能の廃止 | 利用率の低い機能を見つけ、廃止の Issue にする。枝刈りを Issue だけでなく機能そのものへ広げる | 宣言した利用の記録（ai-plugins では Skill の利用統計） |
| ホットスポット分析 | 変更が多く、かつ複雑なファイルを探し、品質の課題を壊れやすい場所から選ぶ | git の履歴（変更回数）と複雑さの計測 |
| 失敗の記録の集計（ポストモーテム） | 止まった理由・人へ戻した承認ゲート・同じ失敗を束ね、共通の原因を 1 つの Issue にする | 開発ループの記録・振り返り・障害の記録 |

見つけた課題を MVV へつなぐ整理の仕方として、Opportunity Solution Tree（目標 → 機会 → 解決策 → 検証）を設計で検討する。

### 5. 調査は待ち時間に少しずつ進め、見直しで使う

調査（ニーズ・シーズ・ホットスポット・失敗の集計）は時間がかかり、まとめて回すと見直しの周回だけが重くなる。一方で conductor は、スプリントの中で supervisor やプランの完了を待つ時間（レビュー待ち・リファクタリング待ち・全体テスト待ち・CI 待ち）が長い。**調査はこの待ち時間に、調査の supervisor を立ち上げて少しずつ進める。** 見直しのフェーズは、溜まった調査の結果を読んで枝刈り・順位付け・起票を行う。

| 項目 | 決まり |
| --- | --- |
| 起動の時点 | conductor が実装・検査などのプランを流して待ちに入ったとき（`supervise.py wait` を背景で起動した後）。並列の上限に空きがあるときだけ |
| 1 回の量 | 調査の項目を小さく分け（例: ライブラリ 1 つ・競合 1 つ・利用の記録の 1 つの観点）、1 回に 1 項目〜数項目。時間と費用の上限を持つ |
| 書き込む先 | 調査の結果は記録（例: `.ndf/discovery/` の項目ごとのファイル。出典と調べた日時つき）にだけ書く。**Issue は起こさない・閉じない・順位を変えない。** 一覧への書き込みは見直しのフェーズだけが行う（足しすぎの上限と MVV 判定を 1 か所で通すため） |
| 止め方 | 待っていたプランが終わったら、調査の supervisor は今の項目を終えて止まる（項目の途中の結果は捨ててよい）。次の待ちで続きの項目から始める |
| 優先 | スプリントの作業が常に先。調査は CPU やメモリを食う全体テストと重ならないよう、並列の上限と資源の上限に数える。人へ問わない |
| 古さ | 調査の結果に調べた日時を持ち、見直しの時点で古すぎる項目（例: 前の見直しより前）は調べ直す |
| 予算 | 調査にかかった費用と時間は開発ループの予算に数え、周回の記録に別の行で残す |

これで見直しの周回は「溜まった結果を読んで判断する」だけになり、重さが周回の間に均される。待ち時間が無い進め方（`--loop` を使わない、1 本ずつ待たない）でも、見直しのフェーズの中で残りの項目を調べれば同じ結果になる。

### 6. 持ち主は 1 つのセッションだけにする

並列でエージェント（複数のセッション・複数の conductor）が動いているとき、見直しと待ち時間の調査を全員が始めると、同じ調査を重ねて費用を払い、同じ課題を 2 回起票し、枝刈りと順位付けが互いの反映を上書きする。**見直しのフェーズ（待ち時間の調査を含む）は、どれか 1 つのセッション（見直しの持ち主）だけが行う。**

実例: 2026-10-31〜11-01、開発ループ l20261031 の周回 5 を 2 つのセッションが同時に回した。両方が止まったキューを再開し、同じ課題の残りを 2 回起票した（https://github.com/devbasex/ai-plugins/issues/2309 と、重複で閉じた https://github.com/devbasex/ai-plugins/issues/2310 ）。検査は「別の実行が同じ作業場所を使っている」で止まった。どちらのセッションも、もう一方がいることを知る手段が無かった。

| 項目 | 決まり |
| --- | --- |
| 宣言 | 持ち主になるセッションは、メインディレクトリの `.ndf/` に持ち主の宣言（例: `.ndf/review/owner.json`）を置く。中身はセッションの識別子・プロセス（pid とホスト）・始めた時刻・最後に動いた時刻・今の項目 |
| 取り方 | 宣言の作成はファイルのロック（`lib/locks.py`）の中で行い、2 つのセッションが同時に取れないようにする。有効な宣言が他にあれば始めない（自分の作業を続ける） |
| 生きている印 | 持ち主のセッションは項目を 1 つ進めるたびと、一定の間隔で最後に動いた時刻を更新する |
| 解放 | 見直しを終えたら宣言を「終わった」にする（終わった時刻を書く）。待ち時間の調査を止めたときも、項目の区切りで更新する |
| 引き取り | 持ち主のセッションが終了・中断したら、別のセッションが引き取れる。宣言のプロセスが同じホストで生きていない、または最後に動いた時刻から一定の時間（寿命）を過ぎたら無効とみなし、ロックの中で宣言を書き換えて引き取る。引き取ったセッションは、記録に残った項目の続きから進める（調査の結果は項目ごとのファイルなので、途中の項目だけをやり直す） |
| 寿命 | 生きている印の間隔より十分長く、中断から引き取りまでを待たせすぎない長さ（例: 印の 3 倍程度）。今の作業場所の持ち主の記録（`lib/run_owner.py`）の寿命の窓 24 時間は、引き取りまでが長すぎる（作業場所が「使用中」のまま残る不具合 https://github.com/devbasex/ai-plugins/issues/2285 ） |
| 部品 | 既存の `lib/run_owner.py`（持ち主・最後に動いた時刻・終わった時刻・引き取り）と `lib/locks.py` を使い、同じ役割の部品を作らない。寿命とプロセスの生死の判定を足す |
| 見える化 | 持ち主の有無・持ち主のセッション・最後に動いた時刻を `loop status` などで表示する。引き取ったときは誰から引き取ったかを記録に残す |

### 7. 起動の条件

「N 回に 1 回」だけでは、課題が溢れても次の回まで待つ。回数に加えて、溜まり具合でも起動する。値はプロジェクトの設定（今の `.ndf/pace.json` や `.ndf/backlog.json`）で上書きできる。

| 条件 | 既定の例 |
| --- | --- |
| 前の見直しから N 回 | 3 |
| 前の後回しの再評価から M 回（後回しの再評価だけ） | 12 前後 |
| open の件数・持ち越しが閾値を超えた | open が前の見直しの時点から 30% 増えた、持ち越しが候補の上限の 10 倍を超えた |
| 選べる課題が尽きた | 開発ループは今 `no_issue` で止まる。止まる前に見直しを 1 回挟む |
| 人が呼ぶ | `--loop` を使わない進め方でも、単独で起動できる |

### 8. 足しすぎを防ぐ

調査は放っておくと課題を足し続け、今と逆の向きで一覧を埋める。

- 1 回の見直しで起票する件数に上限を置く（設定で変えられる）
- 起票したニーズ・シーズの課題はそのプロジェクトの MVV 判定（`mvv-gate.py`）を通し、「従う」だけを順位付けへ入れる。それ以外は人の判断待ちに置く（プロダクトの方向を決めるのは人、の原則）
- 起票する Issue は出典（URL・記録のパス・実行したコマンド）と、MVV のどこに当たるかを持ち、区別できるラベル（例: `needs` / `seeds`）が付く
- 枝刈りで閉じた件数と起票した件数を見直しの報告に並べ、open の件数の推移を記録する

### 9. 課題の置き場の違い

課題を GitHub 以外（`.ndf/project.json` の `issues` が `markdown`・`redmine` などのプロジェクト）に置くプロジェクトもある。今の棚卸しが GitHub の milestone と `gh` を前提にしている箇所は、見直しでも同じ前提になる。この課題では GitHub の外へ広げないが、見直しの手順が GitHub の固有の機能名に依存する箇所を増やさない。

### 10. NDF の中の置き場

既存の Skill へ統合してから新設を考える（`refactoring` の `lang-*`、`release` の `form-*` に前例がある）。

| 案 | 中身 | 得失 |
| --- | --- | --- |
| A（推奨） | 棚卸しは `backlog-refinement` に「差分の棚卸し」「見直し」「大整理（後回しの再評価を含む）」の 3 つの深さを持たせる。調査は `backlog-refinement` の references（ニーズ・シーズ）に置き、見直しの深さのときだけ読む。材料の宣言は `project-analysis` の項目に足す | Skill を増やさない。棚卸しと調査が同じ順位の基準を使う。Skill 本文が長くなる |
| B | 調査だけ新しい Skill（例: `product-discovery`）にし、見直しのフェーズが `backlog-refinement` の後に呼ぶ | 単独で呼びやすい。Skill が 1 つ増え、配布の manifests と frontmatter の規約に載せる |

### 11. 十数スプリントに 1 回の「大整理」: Issue 単位では直らない根本原因を見つけて組み直す

**具体例（2026-11-01、このリポジトリ）**: 未完了 194 件を原因の型で分けると、異常系・回復系（失敗の判定・記録・回復・待ちと上限・解決の時点・並行）が 103 件で、新機能と文書を除いた不具合の 82% だった。コードを横断して数えると、共通部品はあるのに通らずに済み（結果の共通の形を使う入口は 37 本中 24 本、例外を捨てる箇所 49、上限の直書き 195）、データと入出力の形もそろっていなかった（結果を表すキーが 9 通り、リポジトリの根を受け取る引数が 5 通り）。10 月の起票 289 件に対して完了 271 件で、1 件ずつ直しても減らない。利用者の指摘で大方針 #2335 を立て、柱 9 本（#2336〜#2344）を置き、113 件を子へ付け直し、マイルストーンを 2 大方針（25 Factory・28〜30 根本解決）とそれ以外（31〜34）へ組み直した。

**見直しとの違い**: 見直し（数回に 1 回）は課題を 1 件ずつ評価して、順位・マイルストーン・枝刈りを決める。大整理は課題の集まりを見て、**多くの課題に共通する原因**を探す。原因が見つかれば、個々の課題を直す代わりに原因を直す大方針を立てる。

| 手順 | 中身 | 今回の実物 |
| --- | --- | --- |
| 1. 分ける | 未完了の課題すべてを、原因の型（プロジェクトが宣言した型の一覧。無ければ既定の一覧）で分ける。並列の worker で分担する | 4 本の worker で 194 件を A〜I の 9 型へ |
| 2. 数える | 型ごとの件数、課題の集まる部品、マイルストーンごとの割合、起票と完了の推移 | A〜F が 103 件・不具合の 82%。部品の上位は supervise のプラン・cross-refactoring・閉じる処理 |
| 3. 裏付ける | コードを横断して、型に対応する観点（例外の扱い・ログ・入出力とデータの形・重複した実装・設定の置き場）を数える | 上の「共通部品はあるのに通らずに済む」の数字 |
| 4. 立てる | 根本原因を 1 つの大方針の Issue にし、柱（仕組みごとの子の親）と受け入れ条件を付ける | #2335 と柱 #2336〜#2344 |
| 5. 付け直す | 大方針で解消しうる課題を柱の子へ付け直し、マイルストーンを組み直す。付け直しの前の状態を記録に残す | 276 件の付け直し |
| 6. 止める | 大方針の設計が終わるまで、該当の型の新しい課題を個別に直さず子として起票する、と大方針の本文で宣言する | #2335 の「進め方」 |

**Skill の置き場**: 棚卸し（`backlog-refinement`）の「ルートコーズの判断」を広げて大整理の手順を持たせるか、新しい Skill を立てるかは設計で決める。既存の Skill へ寄せることを先に検討する。

**承認**: 新しい承認ゲートは作らない。大方針の Issue は MVV 判定にかけ、「従う」以外は人の判断待ちに置く。付け直しとマイルストーンの組み直しは取り消せる操作なので、前の状態を記録に残して進め、報告に戻し方を書く。
