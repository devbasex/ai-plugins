## 目的

- 実行ジョブの token を正しく持つランナーでも、自分のスプリントの実行と関係の無いリポジトリの Pull Request を自分の実行へ結び付けられないようにする。ほかの利用者のリポジトリの Pull Request と CI の状態（`pr.updated`・`ci.updated`）が、別のスプリントの実行の進捗に見えることを防ぐ
- 実行ジョブの中で別のリポジトリの修正が要るとわかったとき、ランナーの権限を広げずに、その修正を相手先へ届ける経路を持つ。サービスが起票してよい先にはサービスが起票し、起票してよいと言えない先は下書きを人へ回す

## 前提

- 前提 1: 照合に使う「そのスプリントの実行に許可されたリポジトリ」は #2186 のリポジトリの登録とスプリントの実行が持つ。この課題の実装は、#2186 がスプリントの実行とリポジトリの結び付き（または token の claim）を作った後に行う
- 前提 2: 1 つのスプリントの実行が扱うリポジトリはちょうど 1 つである（確定仕様 `docs/specifications/ndf-factory-service-boundary.md` の ER 図「リポジトリの登録 ||--o{ スプリントの実行」と、実行ジョブの指示の `REPO` が 1 つであること）
- 前提 3: factory/ は本番へ出していない。受け口の応答が 202 から 403 へ変わる場合について、旧い token・旧いランナーとの互換の経路を持たない
- 前提 4: リポジトリの名前（`owner/name`）は大文字と小文字を区別せずに比べる（GitHub の名前の扱いと、既存の `pr_ref` が小文字にそろえる形に合わせる）
- 前提 5: `pull_request` を持たない `step.recorded` と、ほかの種類の事象の照合は変えない（新しく足す起票の依頼の種類を除く）
- 前提 6: 403 の本文は既存の I30 のとおり理由によらず同じにする（照合で落ちたことを送り手へ明かさない）
- 前提 7: サービスが起票に使う GitHub App は、#2186 の決定 6 のとおり Issues の読み書きの権限を持つ。サービスは App の秘密鍵から、1 つのリポジトリと Issues の書き込みだけに絞った導入の token を作れる（#2186 の GitHub の口）
- 前提 8: 「同じアカウント」は、起票の依頼を送った実行ジョブのスプリントの実行が属するアカウントである。ほかのアカウントの登録の有無は、サービスが起票するかの判定にも、依頼への応答にも使わない（登録の有無を外へ明かさない）

## 対象範囲

含む:
- 進捗の受け口（`POST /ingest/events`、`runner` の経路）で、`step.recorded` の `payload.pull_request.repo` を、その事象のスプリントの実行に許可されたリポジトリと照合する
- 照合に要る情報の受け渡し（token の claim の発行と検証）
- 別のリポジトリの起票の依頼を、進捗の事象の新しい種類として受け付けて記録する（契約 `factory/contracts/` の変更）
- 記録した依頼を読み、サービスが起票してよい先ならサービスが起票し、そうでない先は下書きを人へ回し、どちらにしたかを進捗の事象に残す
- ランナーが NDF の起票の依頼を事象へ翻訳する口（#2186 のランナーの翻訳の表に 1 行）と、NDF がランナーの中で別のリポジトリへの起票を依頼として書き出す形
- 確定仕様 `docs/specifications/ndf-factory-contracts-and-progress.md`・`ndf-factory-service-boundary.md` の照合の規則・事象の種類・不変条件・決定の書き換え
- 照合と起票の経路のテスト

含まない:
- リポジトリの登録・GitHub App の導入・スプリントの実行の作成（#2186）
- 相手先の流儀（課題追跡の宣言 `.ndf/project.json` の `issues`・Issue テンプレート・外部チケット）を読む判定（#2239）。この課題は判定を呼ぶ口と、#2239 が入るまでの既定だけを持つ
- 下書きを受けた人への知らせの送り方（Web・Slack。#2173）と、下書きの見せ方（#2172）
- `github` の経路（Webhook）の照合の変更。宛先は今どおり `pr_ref-index` で引く
- 既に保存した事象の `pr_ref` の洗い直し（本番のデータが無い。前提 3）
- スプリントの実行の途中でリポジトリを改名したときの追従（未決 2）
- 作った Issue の番号を依頼の元の課題へ書き戻すこと
- インフラの定義（DynamoDB の表・GSI・ストリーム・秘密。private リポジトリ）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| セキュリティ | 照合に使うリポジトリの値は、ランナーが書き換えられない出所（サービスが署名した token か、サービスの表）から得る。ランナーの申告した値だけで許可を決めない。token の値・鍵をログ・応答・例外の文に出さない（既存の決まり）。起票に使う token は 1 リポジトリと Issues の書き込みだけに絞り、保存せず、ランナーへ渡さない。サービスが起票する先は、依頼を送った実行のアカウントが登録し App を入れたリポジトリだけである（ほかの利用者のリポジトリへ起票できない） |
| 性能・拡張性 | 受け口は起票の依頼の受け付けで GitHub を呼ばず、ほかの集約を読まない（起票は記録の後に別の処理が行う）。照合の読み出しは増やさない |
| 可用性 | 起票の処理が失敗しても、依頼の記録と実行ジョブの進行は止まらない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 配布物（プラグイン）は、NDF がランナーの中で別のリポジトリへの起票を依頼として書き出す形が増える（ランナーの外の NDF の振る舞いは変わらない）。factory の受け口の応答は、許可されないリポジトリの申告で 202 から 403 へ変わる（本番へ出していないため移行は要らない。前提 3）。実行ジョブの token の claim が増え、#2186 の発行と受け口の検証が変わる。進捗の事象の種類が 2 つ増える |
| データ | 進捗の事象に 2 つの種類が増える。起票の依頼を重ねずに数えるための記録がサービスの表に増える（表の形は設計で決める） |
| 既存の振る舞い | `runner` の経路の `step.recorded` の照合が 1 つ増える。ほかの経路と既存の種類は変わらない |

## 前提とする取り決め
