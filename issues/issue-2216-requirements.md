> ## 何が起きうるか
>
> 正しい token を持つランナーが、自分の実行と関係の無いリポジトリの Pull Request を `step.recorded` で申告すると、その Pull Request の `pr.updated`・`ci.updated`（GitHub の Webhook）が自分のスプリントの実行へ結び付く。他の利用者のリポジトリの Pull Request の状態が、別の実行の進捗に見える。

> いまは factory/ を本番へ出していないため、利用者への影響は無い。

## 目的

- 実行ジョブの token を正しく持つランナーでも、自分のスプリントの実行と関係の無いリポジトリの Pull Request を自分の実行へ結び付けられないようにする。ほかの利用者のリポジトリの Pull Request と CI の状態（`pr.updated`・`ci.updated`）が、別のスプリントの実行の進捗に見えることを防ぐ

## 前提

- 前提 1: 照合に使う「そのスプリントの実行に許可されたリポジトリ」は #2186 のリポジトリの登録とスプリントの実行が持つ。この課題の実装は、#2186 がスプリントの実行とリポジトリの結び付き（または token の claim）を作った後に行う
- 前提 2: 1 つのスプリントの実行が扱うリポジトリはちょうど 1 つである（確定仕様 `docs/specifications/ndf-factory-service-boundary.md` の ER 図「リポジトリの登録 ||--o{ スプリントの実行」と、実行ジョブの指示の `REPO` が 1 つであること）
- 前提 3: factory/ は本番へ出していない。受け口の応答が 202 から 403 へ変わる場合について、旧い token・旧いランナーとの互換の経路を持たない
- 前提 4: リポジトリの名前（`owner/name`）は大文字と小文字を区別せずに比べる（GitHub の名前の扱いと、既存の `pr_ref` が小文字にそろえる形に合わせる）
- 前提 5: `pull_request` を持たない `step.recorded` と、ほかの種類の事象の照合は変えない
- 前提 6: 403 の本文は既存の I30 のとおり理由によらず同じにする（照合で落ちたことを送り手へ明かさない）

## 対象範囲

含む:
- 進捗の受け口（`POST /ingest/events`、`runner` の経路）で、`step.recorded` の `payload.pull_request.repo` を、その事象のスプリントの実行に許可されたリポジトリと照合する
- 照合に要る情報の受け渡し（案 A なら token の claim の発行と検証、案 B ならスプリントの実行からリポジトリを読む関数の型の口）
- 確定仕様 `docs/specifications/ndf-factory-contracts-and-progress.md` の照合の規則・不変条件・決定の書き換え
- 照合のテスト

含まない:
- リポジトリの登録・GitHub App の導入・スプリントの実行の作成（#2186）
- `github` の経路（Webhook）の照合の変更。宛先は今どおり `pr_ref-index` で引く
- 既に保存した事象の `pr_ref` の洗い直し（本番のデータが無い。前提 3）
- スプリントの実行の途中でリポジトリを改名したときの追従（未決 2）
- インフラの定義（DynamoDB の表・GSI・秘密。private リポジトリ）

## 受け入れ条件

- [ ] 1. 前提: スプリントの実行 R の許可されたリポジトリが `org-a/repo-a`、R の実行ジョブの正しい token がある
      操作: `payload.pull_request.repo` が `org-b/repo-b` の `step.recorded` を `POST /ingest/events` へ送る
      結果: 403 と `{"error": {"code": "forbidden", "message": "この事象を書く権限がありません"}}` が返り、事象の表に 1 件も増えない（`pr_ref` の付いた項目も増えない）
- [ ] 2. 受け入れ条件 1 のあと、`org-b/repo-b` の Pull Request の `pull_request` の Webhook を送っても、R の事象の列に `pr.updated` が残らない
- [ ] 3. 前提は 1 と同じで、`payload.pull_request.repo` が `org-a/repo-a`（大文字と小文字の違う `Org-A/Repo-A` も含む）の `step.recorded` は 202 で残り、`pr_ref` は `org-a/repo-a#<番号>` になる
- [ ] 4. そのスプリントの実行の許可されたリポジトリが決まらない（案 A なら token に claim が無い、案 B なら実行が見つからない）とき、`pull_request` つきの `step.recorded` は 202 にならず、保存されない（401 か 403。どちらにするかは設計で決める）
- [ ] 5. 案 B を採る場合、許可されたリポジトリを読む関数が投げると 503 を返し、保存されない（案 A を採る場合はこの条件を消し、消した事実を残す）
- [ ] 6. `pull_request` を持たない `step.recorded`、ほかの種類の `runner` の事象、`api`・`github` の経路と `appendControlEvent` の応答と保存は変わらない（既存のテストがすべて通る）
- [ ] 7. 403 の本文は既存のほかの 403 と同じで、許可されたリポジトリの名前と照合で落ちたことを含まない（I30）
- [ ] 8. 照合の順序は既存どおり、大きさと JSON（400）→ token（401）→ 契約の定義（400）→ 出所の照合（403）である。契約の定義に合わない `pull_request` は 400 のまま
- [ ] 9. 確定仕様 `docs/specifications/ndf-factory-contracts-and-progress.md` の `runner` の照合の規則と不変条件（I27 か新しい番号）に、この照合が書かれ、`pr_ref` をランナーの申告だけで置くとした決定（#2171 の設計の決定 7）の書き換えが理由つきで残る
- [ ] 10. `cd factory && npm run check` が終了コード 0 で終わる

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| セキュリティ | 照合に使うリポジトリの値は、ランナーが書き換えられない出所（サービスが署名した token か、サービスの表）から得る。ランナーの申告した値だけで許可を決めない。token の値・鍵をログ・応答・例外の文に出さない（既存の決まり） |
| 性能・拡張性 | 案 B を採る場合、照合の読み出しは `pull_request` つきの `step.recorded` 1 件につき高々 1 回で、ほかの事象では読まない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 配布物（プラグイン）の公開インタフェースは変わらない。factory の受け口の応答は、許可されないリポジトリの申告で 202 から 403 へ変わる（本番へ出していないため移行は要らない。前提 3）。案 A では実行ジョブの token の claim が増え、#2186 の発行と受け口の検証が変わる |
