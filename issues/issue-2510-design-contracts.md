# #2510 の設計: データ構造と入出力の契約

設計文書の本体は [issue-2510-design.md](issue-2510-design.md) にある。

## データ構造

### 人の判断待ちの行に足す欄

既存の欄（`note`・`revise_count`・`request`・`stamp` ほか）の意味は変えない。

| 欄 | 型 | 空の扱い | 意味 |
| --- | --- | --- | --- |
| `by` | 文字列 | 無ければ人の答え | `auto` のとき自動の出し直し |
| `missing` | 文字列の配列 | 無ければ欠けなし | 自動の出し直しで名指しした、届いていない項目の識別子（`lroot3:1-2` など） |
| `requests_before` | `{id, stamp, settled}` の配列 | 無ければ送り直していない。`settled` が無ければ `false` | 問い直すときに置き換えた前の依頼の id と、その依頼の印（設計 PR の先頭）。`settled` が `true` の要素は、その id への答えを判定し終えたもので、答えを読む依頼の一覧に入れない |

`requests_before` の要素は消さず、判定し終えたら `settled` を `true` にする（`restamped` との対応と、置き換えた id の持ち主を引く手がかりを残すため）。`true` にするのは次の 2 つの時点である。

- 問い直しの判断（`regate1`）が、今の依頼への答えを読んだうえで先頭の動きを `False` か `None` と判定して問い直すとき。その依頼の id は `settled: true` で移す（答えは判定済みで、次の境から前の依頼の経路で読み直すと区分 `unmatched` の知らせが毎回出るため）。答えが届く前に先頭の動きで問い直すときは `settled: false` で移す
- 設計の承認の答えを当てる関数が、前の依頼の id への答えを判定したとき。当てたときも、当たらなかった答えとして知らせたときも `true` にする

自動の出し直しの行は `answer` を `revise`、`note` を空にする。項目は人の回の指摘からだけ数えるため（I2）、自動の回は指摘の本文を持たない。`restamped`（今の欄）は残し、`requests_before` の最後の印と同じ値を持つ。

### 出し直しの指摘の入力（`<周回のディレクトリ>/revise-<課題>.json`）

周回のスプリントを組むたびに、すべてのループの記録から作り直す。手で直さない。

```json
{
  "issue": 2338,
  "rounds": [
    {"loop": "lroot2", "round": 1, "at": "2026-11-03T10:00:00Z", "pr": 2497, "by": "user",
     "note": "- #2059 に絞る", "items": [{"id": "lroot2:1-1", "text": "#2059 に絞る"}], "missing": []},
    {"loop": "lroot3", "round": 1, "at": "2026-11-04T21:09:00Z", "pr": 2497, "by": "user",
     "note": "- #2059 と #2300 に絞る\n- PR は 2 本にする",
     "items": [{"id": "lroot3:1-1", "text": "#2059 と #2300 に絞る"}, {"id": "lroot3:1-2", "text": "PR は 2 本にする"}],
     "missing": []},
    {"loop": "lroot3", "round": 2, "at": "2026-11-05T10:00:00Z", "pr": 2497, "by": "auto", "note": "", "items": [],
     "missing": ["lroot3:1-2"]}
  ]
}
```

### 課題の本文の履歴の節

見出しは `## 出し直しの指摘の履歴` で、ループの名前を入れない（ループを替えても 1 つの節に続けて書く）。1 回分は次の形で末尾へ足す。

```markdown
### 第 2 回（2026-11-05・設計 PR #2497・開発ループ lroot3・自動）

届いていない項目: lroot3:1-2
```

人の回は「自動」の代わりに「人」と書き、見出しの下に指摘の全文を置く。見出しのループの名前と回数の組（例: `開発ループ lroot3` の `第 2 回`）が同じ見出しが既にあれば足さない（I3）。回数が同じでもループの名前が違えば別の回として足す。

### 指摘への対応の表（設計文書と設計 PR の本文の `## 出し直しの指摘への対応`）

| 列 | 書くこと |
| --- | --- |
| 項目 | 入力の項目の識別子（`lroot3:1-1`） |
| 指摘 | 項目の本文の要約 |
| 対応 | `直した` か `直せない` |
| 直した箇所・直せない理由 | 直した節の名前か、直せない理由 |

### 問いの一覧に足す問い

既にある設計の承認の依頼（`kind: gate1`、`lane` を持つ）の形は変えない。足すのは次の 2 つである。

| 問い | 欄 | id の決め方 |
| --- | --- | --- |
| 前のループの待ち | `kind: gate1`・`loop`（行を持つループの名前）・`issue`・`pr`・`lap`・`stamp`（送った時点の設計 PR の先頭）・`question`。`lane` を持たない | `<ループ>-w<課題>-l<行の周回>`。問い直すときは末尾に `-<新しい先頭の SHA の 12 桁>` を足す |
| 当たらなかった答え | `kind: unmatched`・`answered`（答えた依頼の id）・`lane`（レーンが知らせたとき）・`reason`・`question`・`options: ["確かめた"]` | `<答えた依頼の id>-unmatched` |

同じ行の古い問い（`lane` か `loop` と `pr` が同じで id が違う）は、新しい問いを受けたときに一覧から外し、新しい問いの `replaced` に古い問いの `{id, stamp}` と、古い問いの `replaced` の要素を引き継いで入れる（I11）。この置き換えは、レーンの設計の承認の依頼にも同じく当てる。`replaced` は、置き換えた id への答えの持ち主を耐久ワークフローが引く手がかりである。

置き換えた id への答えは、`replaced` にその id を持つ今の問いの持ち主へ流す。

- 持ち主がレーンなら、今の問いへの答えと同じく、止まっていればそのレーンを起こす対象へ入れる。当てるかどうかはレーンが周回の境で前の依頼の経路（前の印から今の先頭まで取り込みだけか）で判定し、当たらなければレーンが区分 `unmatched` の知らせを送る
- 持ち主が前のループの待ちなら、耐久ワークフローが `replaced` の `stamp` と今の先頭を判定の関数で比べ、取り込みのコミットだけなら `loop answer` で当てる。違えば区分 `unmatched` の問いにする

どの問いの `replaced` にも無く、一覧にも無い id への答えだけを、耐久ワークフローが受けた時点で区分 `unmatched` の問いにする。

計画を終えたときの要約（`parallel.py wait` の終わりの出力）に、答えのまだの前のループの問いを `prior_waits` として並べる（I12）。

## 入出力の契約

| コマンド | 足す引数 | 振る舞い |
| --- | --- | --- |
| `supervise.py new sprint` | `--revise-note <課題>=<パス>`（繰り返し可） | `--design` に含まれる課題の設計のプランだけを変える。ファイルを読めなければ組み立てを断る（終了コード 2） |
| `mvv-gate.py check --gate design` | `--revise-note <パス>` | 材料の先頭へ「出し直しの指摘」の節を足し、承認ゲートの問いへ判定の条件を足す。読めなければ承認ゲートへ戻す（今の材料を取れないときと同じ） |
| `revise-note.py check --pr <番号> --doc <設計文書> --notes <パス>` | 新規 | 終了コード 0（項目がそろった）/ 10（表が無い・行の無い項目・対応か箇所の欄が空の項目がある。届いていない項目を `items` に出す）/ 2（PR・設計文書・入力を読めない） |
| `parallel.py wait` | 無し | `questions` に区分 `unmatched` と前のループの待ちの問いが出る。終わりの出力に `prior_waits` が増える |
| `parallel.py answer` | 無し | 区分 `unmatched` の問いには `--choice 確かめた` で答える。前のループの待ちの問いには設計の承認と同じ `--approved` / `--revise --note` / `--rejected` で答える |

`loop answer`・`parallel.py answer` の引数は変えない。

### 取り込みのコミットだけかの判定（`gate1_requests.merge_only`）

入力は設計 PR の番号・課題の番号・問いの時点の先頭・今の先頭、出力は 3 値（`True` = 取り込みだけ、`False` = 違う、`None` = 判定できない）である。

1. 起点ブランチを `.ndf/worktree.json` の `base_branch` から読む（`repo.base_branch`）。読めなければ `None`
2. 起点ブランチと設計 PR の先頭を `git fetch` する。失敗すれば `None`
3. 問いの時点の先頭から今の先頭までの、設計 PR のブランチの上のコミットを並べる（`git rev-list --first-parent --parents <前>..<今>`）。それらがすべて親を 2 つ以上持ち、1 つ目以外の親がすべて `origin/<起点>` の祖先であることを確かめる。外れれば `False`
4. `git diff --quiet <前> <今> -- 'issues/issue-<課題>-*.md'` が 0 なら `True`、1 なら `False`、ほかは `None`
