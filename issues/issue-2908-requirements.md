## 目的

- conductor（オーガナイザー・レーン・単独の `/goal` の会話）の費用を下げる。PR #2905 の分析では、conductor の費用の 71% は文脈が 20 万 token を超える呼び出しで、1 回の呼び出しの平均文脈は 25 万 token である
- 文脈を「そのまま続ける」と「引継ぎ文書を書いて新しい会話で続ける」のどちらが費用と所要時間で有利かを実測で決め、切る規則（閾値・待ちの前に切るか・復元の量の上限）を hook と規約へ反映する

## 調べた事実

- 2026-11-10: transcript と使用量の帳簿から集計した（ https://github.com/devbasex/ai-plugins/pull/2905 の「費用」の節、`usage/week_by_layer.csv`・`usage/tool_wait.csv` ）
- 2026-11-10: 今の再起動の方針は現行方式（運用上限 200,000 token）である（`python3 plugins/ndf/scripts/context-policy.py resolve` の出力 `再起動の方針: current（判断開始の値 200000 / 運用上限 200000 / 余白 50000）`）
- 2026-11-10: このリポジトリの判定の記録（`~/.local/state/ndf/context/decisions/devbasex__ai-plugins.decisions.jsonl`、262 行）は、現行方式の「判定」238 行と「引継ぎ開始」24 行だけで、試行方式の行と「復元完了」の行は 0 行である（行ごとの方針とイベントを数えた結果）。そのため、試行方式の費用の見込みに要る復元の量（Q）と復元の区間の呼び出し数（q）の標本は、今の記録からは取れない
- 2026-11-10: 試行方式の判断帯は、続ける費用と再起動の費用を比べる式をすでに持つ（`plugins/ndf/skills/development-workflow/references/work-vessels.md` の「会話を替えて続けるか」）。式の値は `context-policy.py calibrate` が記録から作り、標本が 3 未満なら見込みを出さない

## 前提

- 前提 1: 「続けた場合」は試行方式で運用上限を窓 − 容量の余白まで上げた設定（`.ndf/context.json` か `NDF_CONTEXT_POLICY=trial` と `NDF_CONTEXT_LIMIT`）、「閾値で切った場合」は現行方式か、試行方式で候補の閾値を運用上限にした設定で作る。進め方を切り替えるための新しい仕組みは作らない
- 前提 2: 比べるフェーズの種類は、3 層の conductor が起動する 1 つの種類（設計か実装のどちらか 1 つ）に揃える。どちらにするかは設計で決め、選んだ理由を記録に書く
- 前提 3: 進め方ごとの標本は 3 回以上とする（`context-policy.py calibrate` が見込みを出す最小の標本数と同じ）。3 回に満たない進め方があれば、その旨と件数を記録に書き、閾値はその進め方の結果に依らずに決めた理由を添える
- 前提 4: 費用は、conductor の分を会話の記録から、NDF が起動した分（supervisor・worker・相手役）を使用量の帳簿から取り、PR #2905 の換算表（100 万 token あたり。Opus 5.5 は入力 4 / 出力 20 / cache 作成 5 分 5 / 1 時間 8 / cache 読み込み 0.2）で USD に換算する。集計は `context-policy.py report --work <課題番号の並び>` の区分（conductor・NDF が起動した分・引継ぎの区間・復元の区間）を使う
- 前提 5: 所要時間は、フェーズの起動からフェーズレポートを受け取るまでの実時間とする。人の答えを待った時間は所要時間から外し、待ちの回数と各回の長さを別の列に書く。引継ぎ文書を書く時間と新しいセッションが状態を戻す時間は所要時間に含める
- 前提 6: 品質が落ちる文脈の長さはこの課題で測らない。決める閾値は今の運用上限 200,000 token を上回らない（上回る値が費用で有利でも、品質の側の根拠が無いため）
- 前提 7: 調査の記録は `docs/metrics/` の規約（生の記録・会話の本文・会話の ID を置かない）に従って `docs/metrics/` の下へ置く

## 対象範囲

含む:
- conductor（オーガナイザー・レーン・単独の `/goal` の会話）の切る時点の規則
- hook の token の guard（`plugins/ndf/scripts/hook_lib/token_guard.py`・`plugins/ndf/scripts/token-guard.sh`）の閾値と、待ちの前に切る判定
- `plugins/ndf/skills/development-workflow/references/context-window.md` の規則（閾値・待ちの前に切る規則・復元の量の上限）
- 実測に要る「復元完了」の記録の打ち方の確認（記録が取れない原因が手順の側にあれば、その手順の直し）

含まない:
- supervisor・worker・相手役の起動ごとの cache の作成を減らす手（別の課題にする）
- 品質が落ちる文脈の長さの測定（前提 6）
- Codex で文脈の量を読む仕組み（Codex は今どおり現行方式のカットポイントで切る）
- 定型の判断をスクリプトの出力へ寄せて conductor の文脈を減らす手（PR #2905 の「直す順の提案」の 5。別の課題）
