# #3056: NDF のテストを CI に寄せる: CI を検知したら宣言し、宣言があれば手元でテストしない（指示書・スクリプト・hook で守る）

正は課題の本文（#3056）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 目的

NDF を使うプロジェクトのテストを CI に寄せる。CI でテストが走るリポジトリでは手元でテストを走らせず、PR の CI の結果だけで合否を決める。

- 手元のテストは CPU を取り合い（8 コアに負荷 30〜60）、検査の工程を何時間も延ばしている
- 手元で走らせない代わりに、PR の CI の結果をフローを止めずに監視し、失敗を見つけたら直して push する

## 規則（利用者の指示、2026-11-12）

1. テストは CI を設定してそこで行う。CI が設定されていることを検知したら、`.ndf/` にその宣言を書く
2. CI の設定が宣言されていれば、手元ではテストを行わない。CI に任せる
3. 手元でテストを走らせない代わりに、PR の CI のテストの結果を監視する。監視は非同期で、フローを止めない。失敗を検知したら改修する
4. CI が早く動くように、PR は早めに作る。実装の最初のコミットを push した時点で Draft の PR を出し、以後の push のたびに CI が走る

この 4 つを、指示書（Skill・エージェント定義）、スクリプト（プランの雛形・テストの実行口）、hook で守らせる。

## 前提

- 前提 1: 「CI でテストが走る」とは、`.ndf/project.json` の `test.suites[]` のうち静的解析でない suite（`kind` が `test` か未指定）が `ci_jobs` に 1 件以上のジョブを持ち、そのジョブのファイルがリポジトリにある状態を指す。CI の提供元は今の解析が読める GitHub Actions を対象にする
- 前提 2: 手元で止める対象はテスト（`kind` が `test` の suite）に限る。静的解析（`kind` が `lint`）を手元で走らせるかは未決 2 で決め、決まるまでは今の振る舞いのまま残す
- 前提 3: `.ndf/` への宣言の書き込みは、手順 0 の解析（`project-analysis`）の書き込みと同じ経路で行う。解析が新しく作るファイルではなく既存の `.ndf/project.json` へ足すときは C7 に当たるので、リリース承認ゲートで人が見る。新しい承認の工程は足さない
- 前提 4: このリポジトリ（ai-plugins）の `.ndf/project.json` にも宣言を書く。`pytest` の suite は `.github/workflows/pytest.yml` を `ci_jobs` に持つため、前提 1 の条件を満たす
- 前提 5: 既存のテストの戦略の値（`local-full`・`local-scoped-ci-whole`・`round-only`）は残す。宣言はそれと別の情報として読み、宣言があれば戦略の値に関わらず手元のテストを止める
- 前提 6: CI の結果の監視が改修を起こす回数には上限を置く。上限の値と、上限に当たったときに人へ戻す形は設計で決める。上限を置かず無限に改修を繰り返す形は採らない（Value 2）
- 前提 7: 監視が CI の結果を取得できない（`gh` の失敗・ネットワークの誤り）とき、監視は失敗を記録してフローを止めない。マージのステップが CI の結果を確かめられないときは、マージせずに理由を添えて人へ戻す

## 対象範囲

含む:

- CI の検知と宣言（`.ndf/project.json` の解析、`development-workflow` の手順 0）
- 宣言があるときの手元のテストの止め方。範囲テスト（`test-run.py scope`）、cross-review の指摘の検証（`verify-findings`）、worker が打つテスト、修正の後の打ち直し、完了判定（`quality-gates`）の証跡を含む
- 実装の最初のコミットの push の直後に Draft の PR を出すこと
- PR の CI の結果の非同期の監視と、失敗を検知したときの改修（今はマージのステップで止まるだけ）
- hook での拒否（宣言のあるリポジトリで、宣言の suite のテストのコマンドを手元で打つと止まる）
- cross-refactoring の改修。着手前のテスト・項目ごとの点検（`verify`）・安全網の判定・最終ゲートの全体テストを、手元のテストから CI の結果へ置き換え、改修の後に `CROSS_REFACTORING_SUSPENDED` を外して工程へ戻す
- 規則を Skill とエージェント定義の本文に書くこと
- このリポジトリの `.ndf/project.json` への宣言

含まない:

- 静的解析（lint）を手元で走らせるかどうかの決定（未決 2。設計で決める）
- CI の設定そのものを作ること（CI の無いリポジトリへワークフローのファイルを足すこと）。宣言の無いリポジトリの振る舞いは変えない
- GitHub Actions 以外の CI の提供元の検知
- CI の実行時間そのものの短縮（#3049・#3050 の範囲）
- 範囲テストが実質全体になる問題の修正（#3049）

6. - [ ] 宣言のあるリポジトリで PR を push した後、プランは CI の結果を待たずに次のステップへ進む。マージのステップより前に、CI の結果を待って止まるステップが無い

8. - [ ] マージのステップは、CI のテストのチェックが成功したときだけマージする。失敗・未完了・取得できないときはマージしない
9. - [ ] 宣言のあるリポジトリで、宣言の suite のテストのコマンド（`command`、または `scope_command` にパスを入れたもの）を手元で打つと、hook が止め、CI に任せる旨と CI の結果の見方を返す
10. - [ ] `development-workflow`・`quality-gates`・`cross-review`・`cross-refactoring` の Skill と、worker・supervisor のエージェント定義の本文に、規則 1〜4 が書かれている
11. - [ ] 宣言のあるリポジトリの cross-refactoring は、着手前のテスト・項目ごとの点検・安全網の判定・最終ゲートで手元のテストを走らせず、合否を PR の CI の結果で決める。改修の後、`CROSS_REFACTORING_SUSPENDED` が `False` になり、検査のプランにリファクタリング（`assess`・`refactor`）が戻る
12. - [ ] 宣言の無いリポジトリでは、プランのステップ・hook の判定・cross-refactoring・cross-review の振る舞いが今と同じである（宣言の無い既存のテストがそのまま通る）

## 調べた事実

- `.ndf/project.json` は、すでに `ci`（provider・workflows・required_checks）と、suite ごとの `ci_jobs` を持つ。テストの戦略の `local-scoped-ci-whole` は「範囲は手元、全体は CI」で、手元の範囲テストが残る
- このリポジトリの `.ndf/project.json` は `test.strategy` を持たない（所要から導く）。`pytest` の suite は `ci_jobs` に `.github/workflows/pytest.yml` を持つ
- 2026-11-11、lgate（PR #3037）の cross-refactoring の点検で、範囲のテストが全体の 8,436 件になり 72 分かかった（#3049）
- 2026-11-11、lflow の #1811 の実装の worker が、ステップの中で全体テストを打ち直し、30 分で打ち切られた
- PR #3054 で、全体テストを CI に任せる戦略では、実装と検査のプランの test-all（CI の待ち）を外した。worker の指示文に「全体テストを打たない」と書いたが、hook では止めていない
- リファクタリングの工程の停止は `plugins/ndf/scripts/supervise_lib/templates.py:230` の `CROSS_REFACTORING_SUSPENDED = True` が持つ

> * CI設定が宣言されていた場合、ローカルではテストを行わない。CIに任せる
> をルールとして、指示書、スクリプト、hookで制御してください

> ローカルでテストを走らせない代わりとして、CIによるPRのテスト結果は監視し(ただし非同期としてフローは停めない)、失敗を検知したら改修を行う

> cross-refactoringも対象としてください。改修しないと再開できません。

> テストを CI に寄せるため、PRは早めのタイミングで作成し、CIが動くようにする必要がある
