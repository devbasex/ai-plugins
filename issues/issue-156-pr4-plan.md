## モード

`standard`。状態ファイルの記録の形を広げ、読み取りのスクリプトを新設する。

## 目的と非目的

達成したい状態:

- 1〜3 本目が残した記録から、4 つの方式（1 者だけ・多数決・この変更の方式・上限）の
  結果を**同じデータで**計算できる
- 追加でかかった時間と実行の量、収束の終わり方を、方式の比較と並べて読める

やらないこと（設計の「未確認のまま残ること」と決定 2 / 4 / 5 から）:

- **精度（誤った指摘の割合）の測定** — 修正されなかった指摘が誤りだったかは記録から
  決まらない（設計の決定 2）。出すのは再現率だけである
- **状態ファイルを残す仕組みの作成** — 後片付けの工程が作業ツリーごと消す。残すのは
  測る側の手順に委ねる（設計の決定 4）
- **複数の状態ファイルを渡して集計すること** — 集計の単位は測る目的で変わる
  （設計の決定 5）。1 回の実行が測るのは 1 つの状態ファイルである
- **比較の対象となる Pull Request 群の選定** — 測る時点で決める
- **統合し損ねた組（`duplicate_candidates`）を多数決へ数え直すこと** — 3 本目の統合の
  実測が出てから決める
- **既知の不具合を仕込んだ比較用リポジトリの作成** — 要求の「含まない」に挙がっている
- **トークンの量の測定** — 状態ファイルが持たず、CLI ごとに取り方が違う
- **報告の形（`cmd_report`）の変更** — 設計の構成要素が「変えない」と定めている

## 前提

- 前提 1: 測定は収束ループの外で走る。測定が失敗しても収束の進行は止まらない
- 前提 2: 解決したスレッドの位置（`rounds[].fix.resolved_thread_positions`）を持たない
  過去の記録では、上限の方式（`oracle`）を計算できない。そのことは出力へ理由として残す
- 前提 3: 証拠集約を通ったラウンドの印（`evidence_rounds`）を持たない記録では、
  この変更の方式（`proposed`）を計算できない。同じく理由として残す
- 前提 4: 測定は状態ファイルを読むだけで、GitHub へ問い合わせない

## タスク分解

**順序は 1 → 2 → 3 → 4 → 5 → 6 → 7 である。** 上限の方式（Task 3）が、他の 3 つの方式が
拾えた件数（`matched`）の突き合わせ先になるため、方式の実装より先に置く。

### Task 1: 解決したスレッドの位置を記録へ残す

- **対象ファイル:** `scripts/state.py` の `_merge_fix_records` /
  `tests/test_state_merge_fix.py`
- **何を作るか:** 修正の担当の戻り値にある `resolved_threads[]` から、`thread_id` /
  `path` / `line` を写して `rounds[].fix.resolved_thread_positions` へ残す。既存の
  `resolved_thread_ids` と件数は変えない
- **どのテストで確かめるか:** `tests/test_state_merge_fix.py` へ足すテスト。位置つきの
  戻り値を渡して記録を読み出す。件数だけが返る形（整数）でも落ちないこと
- **満たす受け入れ条件:** 16
- **進め方:** 失敗するテスト → 実装 → 既存テストを通す

**このタスクを先頭に置く理由は、位置が記録に残らないと上限の方式を計算できないためである。**
位置は修正の担当の戻り値にあるが、現在の取り込みが件数と識別子だけを残して捨てている。

### Task 2: 測定のスクリプトの骨組みと、費用・収束の様子

- **対象ファイル:** `scripts/measure.py`（新設）/ `tests/test_measure.py`（新設）
- **何を作るか:** 状態ファイルのパスを 1 つ受け取り（`--output` は任意）、
  `pr` / `prs` / `rounds` と、費用（ラウンド数・レビュワーの起動回数・実時間）と、
  収束の様子（終わり方・振動・上限の到達を 0 か 1 で）を JSON で出す
- **どのテストで確かめるか:** `tests/test_measure.py`。時刻の差を持つ記録・4 つの
  終わり方それぞれ・ラウンドが 1 件も無い空の状態ファイル
- **満たす受け入れ条件:** 13 / 14 / 15
- **進め方:** 失敗するテスト → 実装

**費用はローテーション全体の合計である。** Pull Request ごとの内訳は出さない
（測る側が `rounds[].pr` を数えて得る）。

### Task 3: 上限の方式（`oracle`）

- **対象ファイル:** `scripts/measure.py` / `tests/test_measure.py`
- **何を作るか:** 解決したスレッドの位置と指摘の位置（`path` / `line`）を結び、修正された
  指摘の集合を作る。照合は**同じ Pull Request**の指摘に限り、**その解決を記録した
  ラウンド以下**の指摘に限る。複数が一致するときはラウンドが最も新しいものを採り、その
  ラウンドに 2 件以上あるときはどれとも結ばず `ambiguous` へ数える。どの指摘とも
  一致しないものは `unmatched` へ数える
- **どのテストで確かめるか:** `tests/test_measure.py`。位置つきの記録 / round 1 で解決した
  位置に round 2 の別の指摘がある記録 / 位置が合わない記録 / 同じラウンドの同じ位置に別の
  本文の指摘が 2 件ある記録 / Pull Request をまたぐ記録
- **満たす受け入れ条件:** 5 / 6 / 8 / 9 / 11
- **進め方:** 失敗するテスト → 実装

### Task 4: 1 者だけの方式と多数決の方式

- **対象ファイル:** `scripts/measure.py` / `tests/test_measure.py`
- **何を作るか:** 統合の代表だけを母集合とし（統合された側の要素は数えない）、提案した
  担当の一覧から 2 つの方式を出す。一覧を持たない指摘は取り込み時の担当 1 者として読む。
  1 者だけの方式は担当ごとに 1 通り出す。拾えた件数は上限の方式の集合との積集合で数え、
  指摘の識別子（`finding_id`）で突き合わせる
- **どのテストで確かめるか:** `tests/test_measure.py`。担当 2 者の記録 / 一覧を持たない
  指摘を 2 者分持つ記録（どちらの担当も 0 件にならないこと、多数決は 0 件）/ 統合された
  側と代表を混ぜた記録 / 修正済み 1 件と却下 1 件を出した記録（再現率が 1.0 を超えない）
- **満たす受け入れ条件:** 1 / 2 / 3 / 4 / 10
- **進め方:** 失敗するテスト → 実装

**位置が近いだけの組を自分で数え直さない。** 統合の判定は 3 本目が持っており、同じ判定を
2 か所に持つと片方だけが古くなる。

### Task 5: この変更の方式（`proposed`）

- **対象ファイル:** `scripts/measure.py` / `tests/test_measure.py`
- **何を作るか:** 証拠集約を通ったラウンドの印を持つラウンドだけを母集合とし、区分が
  `verified_blocking` か `needs_human_judgment` の指摘を採る。**分母も印のあるラウンドの
  上限の方式に限る。** 分母が他の 3 つと違うことを、母集合の名前（`oracle_scope`）と
  分母の件数（`oracle_base`）の 2 つのキーで常に出す
- **どのテストで確かめるか:** `tests/test_measure.py`。印の無いラウンドと印のあるラウンド
  に修正された指摘を 1 件ずつ持つ記録で、再現率が `1.0`、母集合の名前が `evidence_rounds`、
  分母の件数が `1` になること
- **満たす受け入れ条件:** 1 / 7
- **進め方:** 失敗するテスト → 実装

### Task 6: 決まらない値を理由つきの `null` で出す

- **対象ファイル:** `scripts/measure.py` / `tests/test_measure.py`
- **何を作るか:** キーは常に置き、決まらない値を `null` にする。印を持つラウンドが無い
  とき・位置の記録を持つラウンドが無いとき・上限の方式が 0 件のとき・印のあるラウンドに
  修正された指摘が無いときの 4 つを、設計の表のとおりに出し分ける。理由（`reason`）は値が
  `null` のときだけ置く
- **どのテストで確かめるか:** `tests/test_measure.py`。4 つの場面それぞれで、キーが
  欠けないことと理由の文字列を確かめる
- **満たす受け入れ条件:** 12
- **進め方:** 失敗するテスト → 実装

**この 4 つを 1 つのタスクにまとめるのは、「0 件」と「計算できない」を読む側が
区別できることが 1 つの機能だからである。** 方式ごとに分けると、キーの有無の規則が
方式ごとに分かれる。

### Task 7: 測る指標と限界を書く

- **対象ファイル:** `docs/06-evidence.md`
- **何を作るか:** 4 つの方式が読む規則、再現率が何を表すか、精度を測らないこと、
  上限の方式がインラインへ投稿された指摘の上限であること、比較には変更の前後の状態
  ファイルが要ることを書く。あわせて「この文書が扱わないこと」の表から、効果の測定の行を
  外す（この変更で入るため）
- **どのテストで確かめるか:** `python3 scripts/check-doc-line-limit.py` と
  `python3 scripts/check-markdown-links.py`。どちらも終了コードが 0
- **満たす受け入れ条件:** —（1〜16 の裏付け）
- **進め方:** 記述 → 検査を通す

**この文書は現在 198 行である**（`wc -l` で実測）。分割の基準（501 行以上）には届かない。

## リスクと対処

| リスク | 対処 |
| --- | --- |
| `state.py` が 4191 行あり、変更が他所へ波及しうる | 触るのは戻り値の辞書へ 1 項目を足すところだけにし、既存のキーを既存テストで固定する |
| 測定の失敗が収束の進行を止める | 測定を独立したスクリプトにし、収束ループから呼ばない |
| 修正の担当の戻り値に位置が欠けることがある | 欠けた要素を落とさず残し、上限の方式の側で一致しないものとして数える |
| 過去の記録で方式が計算できず、比較の根拠が空になる | 計算できないことを理由つきで出す。値を 0 で埋めない |
| 測定の結果が、統合の判定の厳しさを含んだ数字として読まれる | 限界を手順書へ書く（Task 7） |

**「先に構造を整える」は選ばない。** 新設する測定のスクリプトは状態ファイルを読むだけで、
`state.py` を読み込まない。`state.py` 側の変更は 1 関数の中の 1 項目の追加に閉じる。

## 切り戻し手順

Task ごとに 1 コミットで戻せる。**状態ファイルの移行を伴わない**（キーが無ければ、その
記録では上限の方式を計算しないだけである）。Task 1 だけを残して Task 2 以降を戻すこともでき、
その場合は記録に位置が残るが測る手段が無い状態になる。
