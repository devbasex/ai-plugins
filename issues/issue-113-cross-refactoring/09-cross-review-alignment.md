# cross-review への展開とコードの共有

[← 01-overview.md](01-overview.md)

本 Skill で作る「担当制」「CLI 駆動」「モデルを含む比較計測」は、`cross-review` にも同じ形で
必要になる。両者は**同じ骨組み（状態ファイル + 起動 + 監視 + 収束判定）を持つ**ため、
実装を二重に持たず共有する。

## 1. cross-review の現状と制約

| 観点 | 現状 | 制約 |
| --- | --- | --- |
| レビュー担当 | codex と gemini の固定 2 者 | claude と kiro を参加させられない。ホストが Codex でも codex がレビューする（自己レビューに近づく） |
| 修正の実行 | ホストのサブエージェント（`general-purpose`） | **Claude Code 以外のホストでは同じ形で動かない。** 3 ランタイムに配布しているが、この経路はランタイム中立でない |
| モデル | 各 CLI の既定に委ねる | どのモデルがレビューしたか記録されず、比較も再現もできない |
| 計測 | ラウンド数と収束理由のみ | 指摘の質（修正に至った率、担当同士の一致率）を測れない |

修正をホストのサブエージェントに任せている点は、本 Skill が
「参加者を全て CLI にすればランタイム中立になる」と判断した理由そのものである。
`cross-review` にも同じ整理を持ち込む。

## 2. 展開する 3 点

### 2-1. 担当制（母集合から選ぶ）

レビュー担当を固定の 2 者から、**ホストを除く母集合から選ぶ**方式へ変える。

```text
レビュー候補 = ["claude", "codex", "gemini", "kiro"] − ホスト   # 常に 3 者
レビュー担当 = 候補から 2 者（既定は codex と gemini、`--reviewers` で指定）
```

- **既定は現行と同じ codex と gemini** にして、後方互換を保つ。
- ホストが Codex のときに codex をレビュー担当から外せるようになる。同一モデルによる
  自己レビューを避けられる点が、担当制を入れる最大の利点である。
- **本 Skill と違い、実行の途中で担当を入れ替えない。** `cross-review` は同じ指摘が繰り返し
  出ることを振動として検知するため、担当が変わると検知が成り立たない。担当は初期化時に
  確定し、実行を通して固定する。

### 2-2. CLI 駆動

起動対象を 4 ランタイムへ広げ、**修正もサブエージェントに依存しない経路**を用意する。

| フェーズ | 現状 | 変更後 |
| --- | --- | --- |
| レビュー | codex / gemini を CLI 起動 | 4 ランタイムを CLI 起動（起動形式は [03-runtime-notes.md](03-runtime-notes.md)） |
| 修正 | ホストのサブエージェント固定 | **既定は CLI 駆動**。ホストが Claude Code のときのみサブエージェントも選べる |

修正担当は**レビュー担当ではないランタイム**から選ぶ。レビューした者が自分の指摘を直すと
独立性が失われるためで、これは本 Skill の担当分離と同じ考え方である。

> 修正をサブエージェントから CLI へ移すと、ホストの作業文脈に差分が載らなくなる副次的な
> 利点もある。`cross-review` が元から狙っていた「ホストの文脈を汚さない」方針とも合う。

### 2-3. モデル指定と比較計測

[05-measurement.md](05-measurement.md) の仕組みをそのまま使う。`cross-review` では
**レビュー担当の比較**が主目的になる。

- 起動時に `--model <ランタイム>=<モデル>` を受け取り、実行を通して固定する
- レビューコメントの先頭に担当のランタイムとモデルを書かせ、集計用のコメントを併記する
- 修正コミットに実行主体のトレーラーを付ける
- 報告でランタイムとモデルの組ごとに集計する

`cross-review` 固有の指標として次を足す。

| 指標 | 意味 |
| --- | --- |
| 指摘が修正に至った率 | 投稿した指摘のうち、修正コミットにつながった割合 |
| もう 1 人との一致率 | 同じ箇所・同じ趣旨の指摘をどれだけ共有したか |
| 振動への寄与 | 振動として検知された指摘を、どちらがどれだけ出したか |
| 初回ラウンドでの承認率 | 最初のラウンドで承認を出した割合（甘さの目安） |

## 3. 共有する部品

### 3-1. 置き場所

共通層は **`plugins/ndf-shared/skills/cross-review/scripts/lib/`** に置き、本 Skill から
参照する。監視スクリプトを共有する既存の方針と同じ形である。

- 配布物のビルドは Skill ディレクトリ単位でコピーし、Skill を跨ぐ参照パスを書き換える
  仕組みを既に持っているため、追加の仕掛けが要らない。
- 共通層のための Skill を新設する案は採らない。共通層は利用者が呼ぶものではなく**内部の
  ライブラリ**であり、Skill にすると初期一覧へ載って発動候補に混ざる。
  `disable-model-invocation` を付けても名前は一覧に残るため、利用者にとって意味のない
  項目が増えるだけになる。
- **`lib/` には収束ループ一般に必要なものだけを置く。** 振動検知や Pull Request の
  ローテーションは `cross-review` 固有なので `lib/` に入れない。3 つ目の利用者が現れた
  時点で独立したディレクトリへ移す。

### 3-2. 共有する範囲

| 部品 | 現状 | 共有後 |
| --- | --- | --- |
| 監視 | `monitor.py`（`cross-review` 専用の想定） | `lib/monitor.py`。対象と命名規則を引数化する |
| 一時ディレクトリの解決 | `_tmpdir.sh` | `lib/_tmpdir.sh`。環境変数名を Skill ごとに渡す |
| CLI 起動 | `launch-codex.sh` / `launch-gemini.sh` | `lib/launch-cli.sh`。ランタイム名で分岐し、固有処理は `lib/_runtime-*.sh` に分ける |
| gemini の環境設定 | `launch-gemini.sh` に内蔵 | `lib/_gemini-env.sh` |
| 作業ディレクトリ準備 | 状態管理スクリプトに内蔵 | `lib/prepare-worktrees.sh`。読み取り用の `--detach` と退避処理を共通化する |
| 担当の決定 | なし | `lib/assignment.py`。母集合の確定、ホスト判定、担当の選択 |
| モデルの記録 | なし | `lib/models.py`。指定の解析、フラグ生成、実測値の突き合わせ |
| 計測の集計 | なし | `lib/metrics.py`。担当ごとの指標算出と報告の整形 |
| 状態ファイルの基本操作 | `state.py` に内蔵 | `lib/statefile.py`。読み書き、eval 形式の出力、再開の冪等性 |

Skill 固有として残すもの。

- `cross-review`: 振動検知、Pull Request のローテーション、レビュー観点、修正の指示
- 本 Skill: 提案のマージ、改善項目の管理、適用結果の検証、見送り処理、リファクタリング観点

### 3-3. 共有の進め方

**先に本 Skill を `lib/` の上に実装し、動くことを確かめてから `cross-review` を載せ替える。**
逆順にすると、実績のある `cross-review` を未検証の共通層へ載せることになり、既存の運用を
壊すリスクが高い。

段階は次の 3 つに分ける。

1. **共通層の切り出し** — 監視スクリプトの汎用化に合わせて `lib/` を作り、本 Skill が使う。
   `cross-review` は既存のパスから `lib/` を読むだけの薄い変更にとどめ、挙動を変えない。
2. **`cross-review` の担当制と CLI 駆動** — レビュー担当の選択と修正の CLI 化を入れる。
   既定値を現行と同じにして、指定しなければ挙動が変わらないようにする。
3. **`cross-review` の計測** — モデル指定と集計を入れる。

各段階の完了条件は共通して「**`cross-review` の既存テストを 1 つも変更せずに通す**」とする。

## 4. 追加する作業単位

[07-tasks.md](07-tasks.md) の 12 個に続く。13 は本 Skill の実装と同時に行い、
14 以降は本 Skill が一周してから着手する。

### 13. 共通層の切り出し

- **対象:** `plugins/ndf-shared/skills/cross-review/scripts/lib/`,
  `cross-review` の既存スクリプト、`cross-review/tests/`
- **内容:** 監視スクリプトの汎用化（作業単位 9）に合わせて `lib/` を作り、一時ディレクトリの
  解決・CLI 起動・作業ディレクトリ準備・状態ファイルの基本操作を移す。`cross-review` からは
  移設先を読むだけにし、**引数の既定値で現行の挙動を完全に保つ**。
  本 Skill は最初から `lib/` を使って実装する。
- **完了条件:** `cross-review` の既存テストが無変更で通る。移設したモジュールに単体テストを
  追加する。

### 14. cross-review の担当制

- **対象:** `cross-review/scripts/state.py`, `SKILL.md`, `docs/01-state-and-review.md`
- **内容:** レビュー担当を母集合から選ぶ方式へ変える。引数 `--reviewers <csv>` を追加し、
  既定は codex と gemini とする。ホスト判定と母集合の確定は `lib/assignment.py` を使う。
  担当は初期化時に確定し、実行を通して固定する（振動検知が成り立つようにするため）。
  既存の `--only` は `--reviewers` の別名として残す。
- **完了条件:** 引数を指定しない実行が現行と同一の担当・同一の挙動になる。
  ホストを担当に含めようとしたら初期化が失敗する。

### 15. cross-review の修正を CLI 駆動にする

- **対象:** `cross-review/scripts/`, `docs/02-fix-and-rotation.md`, `SKILL.md`
- **内容:** 修正フェーズを `lib/launch-cli.sh` 経由の CLI 実行へ移す。修正担当は
  **レビュー担当ではないランタイム**から選ぶ。ホストが Claude Code のときに限り、
  従来のサブエージェント経路も選べるようにする（`--fix-mode cli|agent`、既定は `cli`）。
- **完了条件:** Codex と Kiro CLI をホストにした実行が、Claude Code をホストにした実行と
  同じ手順で一周する。修正担当がレビュー担当と重ならない。

### 16. cross-review の計測

- **対象:** `cross-review/scripts/`, `docs/`, `SKILL.md`
- **内容:** `--model <ランタイム>=<モデル>` を受け取って固定し、レビューコメントへの署名、
  修正コミットへのトレーラー、報告での集計を入れる。集計は `lib/metrics.py` を共有し、
  `cross-review` 固有の指標（指摘が修正に至った率、担当同士の一致率、振動への寄与、
  初回ラウンドでの承認率）を足す。
- **完了条件:** 同じ Pull Request に対してモデルだけを変えた 2 回の実行を、集計で比べられる。

## 5. リスク

| リスク | 対応 |
| --- | --- |
| 共通層の変更が `cross-review` の既存運用を壊す | 追加する引数は全て既定値で現行の挙動を保つ。各段階の完了条件を「既存テストの無変更通過」に固定する |
| 段階 1 の時点で共通層の切り方を誤り、後から作り直しになる | 本 Skill を先に `lib/` の上へ実装し、実際に使ってから `cross-review` を載せ替える。使われていない抽象を先に作らない |
| `lib/` が `cross-review` 配下にあるため持ち主が曖昧になる | `lib/` には収束ループ一般のものだけを置き、固有処理を混ぜない規約を `cross-review` の SKILL.md に明記する。3 つ目の利用者が出たら独立させる |
| 修正を CLI へ移すとホストのサブエージェントで得ていた文脈が失われる | 修正担当には Pull Request の指摘と作業ディレクトリを渡す。ホストが Claude Code の場合はサブエージェント経路も選べるようにして、移行期の逃げ道を残す |
| 担当制の導入でレビュー担当が変わり、過去の実行と比較できなくなる | 担当とモデルを状態ファイルと報告に必ず残す。集計は担当の組ごとに分けて出す |
