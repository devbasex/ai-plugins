# 手順書となる Skill の配置（Step 1）

[← 01-overview.md](01-overview.md)

実装担当は `refactoring` Skill の手順どおりに直すことが前提だが、**参加ランタイムに NDF が
入っている保証はない**。対象リポジトリは任意で、ホスト以外のランタイムはそのリポジトリに
初めて触れることも多い。そこで作業ディレクトリの準備に続けて、**手順書が使える状態かを
確認し、無ければ配置する**。

## 1. 配置先

ランタイム標準の場所へ、作業ディレクトリの中に閉じて置く。

| ランタイム | 作業ディレクトリ内の配置先 |
| --- | --- |
| claude | `<worktree>/.claude/skills/<name>/` |
| codex | `<worktree>/.agents/skills/<name>/` |
| kiro | `<worktree>/.kiro/skills/<name>/` |

- **配置は作業ディレクトリの中だけで完結させる。** 利用者のホーム（`~/.claude/` `~/.kiro/`）
  と対象リポジトリ本体には一切書き込まない。マシン全体の設定を変える操作も行わない。
- `work/` は Pull Request の head ブランチなので、**生成物が差分に混入しないよう
  `.git/worktrees/<name>/info/exclude` へ追加する**。適用結果の差分検証でも Skill の
  ディレクトリ配下は無視する。
- **実装担当はラウンドごとに変わる**ため、`work/` には **3 ランタイム分すべての配置先**を
  作る。提案・レビュー用のディレクトリには、そのランタイムの配置先だけでよい。

## 2. 手順

1. **検出** — 配置先に `<name>/SKILL.md` が既にあるかを見る。対象リポジトリが元から NDF を
   入れている場合は**それを使い、上書きしない**（利用者の設定を壊さない）。
2. **配置** — 無ければホストの `$PLUGIN_ROOT/skills/<name>/` から**コピー**する。
   シンボリックリンクにはしない（作業ディレクトリを消せば残らない状態にする）。
3. **記録** — 状態ファイルの `skills` に `preexisting` / `provisioned` / `missing` を残す。
4. **失敗時** — ホスト側にも見つからない Skill があれば初期化を失敗させる。
   黙って劣化した状態で走らせない。

配置するのは**適用で実際に使う 3 つ**に絞る。

| Skill | 用途 |
| --- | --- |
| `refactoring` | 手順の本体（スメル語彙 / 手法カタログ / 現状固定テスト / 表現の判断） |
| `tdd-cycle` | テストが乏しい経路で現状固定テストを先に書く手順 |
| `quality-gates` | 「直し終わった」と言える条件の判定 |

> `ndf-policies` は**配置しない**。git 運用やコミット規約といったリポジトリ運用の方針であり、
> 対象リポジトリの運用と食い違う可能性が高い。必要な規約（1 手 1 コミット、コミット
> トレーラー、`--force` 禁止など）は本 Skill のプロンプト側で明示する。

## 3. 読ませ方（明示パスを必ず書く）

Skill を配置しても、**本文を読むかどうかはランタイムによって違う**。
3 ランタイムで「Skill 名を出さないプロンプト」を実行し、本文が読まれたかを実測した
（本物の SKILL.md に合言葉を 1 行だけ足した版で判定。手順とログは
[検証記録](../issue-113-task3-cli-verification.md) §8）。

| ランタイム | 配置しただけで本文を読むか | 明示パス指定で読むか |
| --- | --- | --- |
| claude | 読む | — |
| codex | 読む | — |
| kiro | **読まない** | **読む** |

**Kiro は配置しただけでは SKILL.md 本文を読まない。** `description` に書かれた語彙と
モデルの一般知識だけで「それらしい」応答を返すため、**一見すると手順に沿っているように
見えて中身が違う**。実作業では「テストが乏しければ現状固定テストを先に書く」という中核の
手順を飛ばした。

> **必須要件**: プロンプトに **Skill の明示パスを必ず書く**。
> 例: `まず .kiro/skills/refactoring/SKILL.md を読み、その手順に従うこと`。
> Kiro で明示指定すると本文を読み込み、Skill の分岐判定どおりに振る舞うことを確認している。
> claude と codex には冗長だが、**3 ランタイムで同じプロンプトを使う**ため常に書く。

Skill として配置する意味は「ランタイム標準の仕組みに乗せ、参照ファイルまで含めて一式が
揃った状態にする」ことにある。読ませる確実性はプロンプトの明示指示で担保する。
どちらか一方に賭けず、両方を行う。

## 4. 手順を踏んだかは成果物で検証する

読ませても**従うとは限らない**。同じ課題を与えた実測では、3 ランタイムとも構造改善自体は
できたが、現状固定テストの追加数は claude が 17 本、codex が 1 メソッド、kiro が 0 本と
揃わなかった。

そのため適用結果の検証（[02-loop-design.md](02-loop-design.md) と
[06-schema.md](06-schema.md)）で次を必ず見る。

- テストが乏しいと申告された項目に、**現状固定テストの追加コミットが先行**しているか
- 各コミットでテストが成功しているか、コミットトレーラーが揃っているか

これらは「Skill が読まれたか」ではなく「**結果として手順が守られたか**」を見る検査であり、
読ませ方の不確実性に対する最後の砦になる。
