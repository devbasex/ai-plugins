## 目的

並列の計画で、最終の検査が変更なしで終わったスプリントのまとめ（確定仕様化・振り返り・棚卸し・課題を閉じる）が、人の介入なしに続けて流れるようにする。あわせて、出すものの無いリリースの依頼が耐久ワークフローに残って計画を終えられなくなること、処理済みのリリース承認ゲートが切り替えの判定を止めることを無くす。

## 事象

### リリースの依頼のプランが、最終の検査が変更なしでも依頼を送る（#3083）

並列の計画 p5 のレーン lgate のスプリント lgate-1 で `supervise.py new close` のまとめを流したところ（2026-11-12）、最終の検査が「変更なし」だったのにリリースの依頼が送られ、まとめが流れなかった。

| プラン | 結果 |
| --- | --- |
| `1-check.json`（最終の検査） | 完了。`finish` が exit=3（変更なし）で、検査の PR https://github.com/devbasex/ai-plugins/pull/3079 は閉じられた |
| `2-release.json`（開発版） | `実行条件に当たらない（検査 lgate-1-final は変更なし）`で飛んだ |
| `3-release-request.json`（リリースの依頼） | 飛ばずに `parallel.py request p5 --lane lgate --prs 3079` を打ち、依頼 `lgate-r887924761751` を台帳へ送って承認ゲートで終わった |
| `4-close.json`（まとめ） | 前の計画が承認ゲートのため流れなかった |

スプリント lflow-1 でも発生した（2026-11-12）。最終の検査が変更なし（Pull Request 無し）のとき、`3-release-request` が「--prs-from-queue の計画だが、先行の計画の報告に Pull Request が無い」で止まり、`4-close` も流れなかった。`4-close` を単独で流して回避した（ https://github.com/devbasex/ai-plugins/pull/3091#issuecomment-6812240126 の g ）。

### 耐久ワークフローが、Pull Request がマージされずに閉じた依頼を外せない（#3085）

依頼 `lgate-r887924761751`（`prs: [3079]`）の PR #3079 はマージされずに閉じた。耐久ワークフロー（`parallel.py run`）はこの依頼を一覧から外せず、依頼からリリース 7 を組み、差し戻すと同じ依頼からリリース 8 を組んだ。リリース 8 を開いたまま置く間、後から届いたレーン lflow の依頼（10:10 JST）はリリース 8 の締めを待って組まれなかった。リリース 8 を差し戻した後、lflow の依頼とともにリリース 9 が組まれ、lgate の依頼は残ったままである。依頼が残る限り計画は終わらない。

### 切り替えの判定が、処理済みのリリース承認ゲートを答え待ちの依頼に数える（#3080）

2026-11-12 07:10 JST、計画 p5 の台帳 `.ndf/parallel/p5/ledger.jsonl` のリリース承認ゲート（`gate2`）の行は 9 行で、どれも確定（`confirm`）か締め（`settle`）が済んでいた。`wait p5 --after 90` の戻りの `metrics.switch` は次のとおりで、同じ時点の `wait p5 --after 0` は問いを 1 件も返さなかった。

```json
{"verdict": "報告して待つ", "reason": "答えていない問いが 9 件ある", "inputs": {"unanswered": 9, "wait_s": 9717, "context": 165602}}
```

## 期待する結果

- 最終の検査が変更なしなら、リリースの依頼のプランは開発版と同じ実行条件で飛び、まとめが続けて流れる。変更があるときは今どおり依頼を送る
- 依頼の Pull Request がすべてマージされずに閉じているとき、耐久ワークフローはその依頼に「出すものが無い」と答えて一覧から外し、その依頼だけを理由にリリースを組まない
- 確定か締めで処理したリリース承認ゲートは答えた扱いになり、切り替えの判定は待ちの見込みと文脈の費用で決まる

## 再現手順

### #3083

1. 並列の計画のレーン（リリースの経路がテンプレート）で 1 スプリントを本番まで出す
2. `supervise.py new close --name <名> --worktree <根> --issue <N> --state <状態> --version <版> --out <置き場>` でまとめのプランを作る
3. 作ったプランの wave 1 の command（`--then` で `4-close` まで）を流す。最終の検査が変更なしで終わる
4. `3-release-request.json` が承認ゲートで終わり（Pull Request が無ければ止まり）、`4-close.json` が流れない

### #3085

1. 並列の計画でレーンが `parallel.py request --prs <N>` を送る
2. PR `<N>` をマージせずに閉じる
3. 耐久ワークフローがリリースを組む。`settle --rejected` で差し戻すと、同じ依頼から次のリリースが組まれる

### #3080

1. 並列の計画でリリースを 1 回出す（リリース承認ゲートを `parallel.py confirm` で承認し、`settle` まで流す）
2. 答えていない `gate1`・`ask` が無い状態で `parallel.py wait <計画> --after <seq> --timeout 5` を打ち、上限で戻らせる
3. `metrics.switch.inputs.unanswered` がリリース承認ゲートの行数になり、`reason` が `答えていない問いが N 件ある`になる

- 耐久ワークフローは 10.27.47 で起動したもの（`parallel.py run p5`）。10.27.55 の依頼に答える判定（`lib/parallel_release.py` の `answerable`）も同じ式
- 計画 `.ndf/parallel/p5`、スプリント `.ndf/sprint-lgate-1/close/`

## 前提

- 前提 1: 直す場所（まとめのプランの組み立て・依頼を外す処理の置き場・答え待ちの依頼の数え方）は設計が決める。この要求は振る舞いだけを決める
- 前提 2: 依頼の Pull Request の状態は GitHub から取得する。取得に失敗した Pull Request は「閉じた」と見なさない（誤って依頼を外すより、今どおり残す方が戻しやすい）
- 前提 3: 「出すものが無い」と答えた依頼を受けたレーンは、リリース済みと答えられたときと同じく、止まらずに続きへ進む。答えの値（`released` に理由を添えるか、新しい値にするか）は設計が決める
- 前提 4: 台帳に `opened` の行がある計画の答え待ちの依頼（`pending_questions`）にも同じ数え違いがあるかは未確認である。設計で確かめ、当たれば同じ規則で直す
- 前提 5: 3 件はどれも並列の計画のレーンとオーガナイザーの内部の振る舞いで、利用者の設定・公開のコマンドの引数は変えない

## 対象範囲

含む:

- まとめのプラン（`new close`）がレーンで組むリリースの依頼のプランに、開発版と同じ実行条件を付ける（#3083）
- 耐久ワークフローが、Pull Request がすべてマージされずに閉じた依頼に答えて一覧から外す（#3085）
- 答え待ちの依頼の数え方から、確定か締めで処理したリリース承認ゲートを除く（#3080）
- それぞれを再現するテスト

含まない:

- スプリントの途中のステージ（`new sprint` の本番・`pace: fast` の本番）のリリースの依頼のプラン。最終の検査を持たないため、この課題の条件は当てはまらない
- 依頼の Pull Request が 1 件も無い依頼（`prs` が空）の扱い。受け入れ条件 1・2 で、まとめから空の依頼は送られなくなる
- 組んだリリースを開いたまま置いたときに、比べる元のタグが組んだ時点のまま残る問題（#3085 の「影響」の 4 点目）。別の課題で扱う
- レーンがリリースの完了を待たずにまとめへ進む問題（#3060）
- 既に台帳に残っている依頼・計画 p5 の後始末

## 用語

| 用語 | 意味 |
| --- | --- |
| 最終の検査 | スプリントのまとめの先頭で流す検査（`<名>-final`）。変更が無ければ `finish` が終了コード 3 で終わる |
| 実行条件 | プランの `実行の条件` の欄。コマンドが `skip_code` で終われば、queue はそのプランを流さずに飛ばす |
| 答え待ちの依頼 | オーガナイザーに届いて、まだ答えていない依頼。台帳の問い（`gate1`・`gate2`・`ask`・`unmatched`）のうち、答え・処理の記録が無いもの。コードでは `unanswered` |

## 受け入れ条件

### 最終の検査が変更なしのとき、リリースの依頼を送らない（#3083）

- [ ] 1. 並列の計画のレーンで `supervise.py new close` が組むリリースの依頼のプランは、同じまとめの開発版のプランと同じ実行条件（最終の検査 `<名>-final` の変更の有無を見るコマンドと、飛ばす終了コード）を持つ
- [ ] 2. 最終の検査が変更なしで終わったとき、queue はリリースの依頼のプランを実行条件に当たらないとして飛ばし、`parallel.py request` を打たない。検査の Pull Request が閉じた場合と、Pull Request が無い場合の両方で、まとめのプランが続けて流れる
- [ ] 3. 最終の検査で変更があったときは、今どおりリリースの依頼を送り、承認ゲートで終わる
- [ ] 4. レーンでないとき（自分で本番を出すリポジトリ）のまとめの本番のプランと、`new sprint` の本番のステージは変わらない

### Pull Request がマージされずに閉じた依頼を外す（#3085）

- [ ] 5. 依頼の Pull Request がすべてマージされずに閉じているとき、耐久ワークフローはその依頼のためにリリースを組まず、依頼を送ったレーンへ「出すものが無い」と答え、受けている依頼の一覧から外す
- [ ] 6. 依頼の Pull Request の一部だけがマージされずに閉じているとき、閉じた Pull Request を除いた残りで、今と同じ判定（範囲に入れば答える）をする
- [ ] 7. 受け入れ条件 5 で依頼を外した後、ほかに依頼もリリースの途中も無く全レーンが止まれば、計画は `finished` で終わる
- [ ] 8. Pull Request がマージ済みか開いている依頼、状態を取得できなかった Pull Request を含む依頼の扱いは変わらない

### 処理済みのリリース承認ゲートを数えない（#3080）

- [ ] 9. 確定（`confirm`）か締め（`settle`）で処理したリリース承認ゲートは、答え待ちの依頼に入らない。リリースを 1 回出して問いが他に無い計画で、`parallel.py wait` の上限の戻りの `metrics.switch.inputs.unanswered` が 0 になる
- [ ] 10. 提示中で確定も締めも無いリリース承認ゲートは、今どおり答え待ちの依頼に数える
- [ ] 11. `gate1`・`ask`・`unmatched` の数え方は変わらない。台帳に `opened` の行がある計画でも、処理済みのリリース承認ゲートを数えない
- [ ] 12. `parallel.py status` の「答えを待つレーン」に、処理済みのリリース承認ゲートだけを持つレーンが載らない

### テスト

- [ ] 13. 受け入れ条件 1〜3・5〜7・9〜11 を再現するテストがあり、修正の前のコードで失敗し、修正の後に通る

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 依頼を外したときは、外した依頼の ID と理由（閉じた Pull Request の番号）が耐久ワークフローの記録に残る |
| 性能・拡張性 | 依頼の Pull Request の状態の取得は、依頼 1 件につき Pull Request の数の範囲に収める。耐久ワークフローの見回りのたびに全依頼を取得し直さない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない。コマンドの引数・プランの欄の名前は変えない |
| データ | 変わらない。台帳とチェックポイントの形は変えない（依頼への答えの値を足すかは前提 3 の設計で決める） |
| 既存の振る舞い | 最終の検査が変更なしのまとめで依頼が送られなくなる。閉じた Pull Request だけの依頼が答えられて外れる。処理済みのリリース承認ゲートが切り替えの判定を止めなくなる |
