# #828 / #680: 決定の記録

設計は [issue-828-680-design.md](issue-828-680-design.md)、要求は [issue-828-680-requirements.md](issue-828-680-requirements.md) にある。

## 決定の記録

### 決定 1: 記録のコマンドの入口は `projects-sync.sh` にし、issue の本文の更新をその中から呼ぶ

通過工程の控えは、Bash のコマンドの中の `projects-sync.sh <課題番号> <キー> <値>` を観測して
積む。根拠は `stage-completeness.md` の「用語」と「変わらない 4 つの契約」、`workflow-common.sh` の照合である。
記録を拒まれたときの案内も同じ形を示す。入口をこのコマンドにすれば、hook と控えの契約を
変えずに 1 行で 3 か所（issue の本文・盤面・控え）へ残せる。

`progress-record.sh` を入口にして盤面の同期を中へ入れる形は採らない。hook の照合と契約の表と
テストを変えることになり、`stage-completeness.md` が「変わらない」と定める契約を崩す。新しい
包みのスクリプトを足す形も、3 つ目の名前を hook に覚えさせることになるため採らない。

### 決定 2: `$SCRIPTS` は conductor が解き、絶対パスで起動指示へ書く

`$SCRIPTS` の解決は 59 行のコードブロックである。supervisor がそのたびに `scripts-lookup.md` を
読むと、`progress-tracking` の本文を外した効果の一部が戻る。conductor は `development-workflow` を読んで
いるため、解決の手順を既に持っている。

supervisor に解かせたまま #847 の 1 コマンドを待つ形は採らない。#847 は #828 を待たない別の
流れで、着手の順が決まっていない。#847 が入った後も、絶対パスを渡す形はそのまま使える。

### 決定 3: supervisor は工程の Skill を起動し続け、外すのは工程の外の 2 つだけにする

工程の Skill の起動は supervisor の持ち場の仕事そのものである（`agent-layers.md` の「3 層の責務」）。
減らせるのは、工程の外から読まされる `development-workflow`（振り分けは conductor が済ませている）と
`progress-tracking`（使うのは 1 行）である。

工程の Skill の抜粋もこの変更で作る形は採らない。表の 6 Skill のうち 5 つは #845 の子で
スクリプト主体へ移り、`SKILL.md` 自体が縮む。いま抜粋を作るとマイルストーン 29〜34 で書き直す。

### 決定 4: worker は Skill を起動しない。例外は起動指示が Skill の起動を手順として渡した場合だけ

worker が自分の判断で工程の Skill を起動すると、進行の記録や確認の段のように worker が持たない
責務が worker の文脈で動く。起動してよいかを起動指示を書く側に決めさせれば、例外は起動指示の
中に見える形で残る。今の例外は `cross-review` の修正の `/ndf:fix` だけで、#859 が抜粋へ置き換える。

例外を置かない形は採らない。`cross-review` の Step 5 / 7.5 が今の形のまま規則に反し、#859 が
入るまで修正の経路が規則と食い違う。worker の判断に任せる形も採らない。「必須」の手順が担当の
判断で置き換わった前例がある（#676）。

### 決定 5: 抜粋は Skill ごとの `references/excerpt.md` に置き、1 行目に目印を持たせる

抜粋を写す側（conductor・supervisor）は、本文を読まずに抜粋だけを開ける必要がある。別の
ファイルにすれば、その 1 ファイル（40 行以内）を読むだけで済む。同じ Skill の中に置けば、
本文を直す人の目に入り、#855 の検査は目印から本文との対を見つけられる。

`SKILL.md` の中の節に置く形は採らない。抜粋だけを開くには行の位置を知る必要があり、本文を
開けば全体が文脈に載る。`agent-layers.md` にまとめて持つ形も採らない。正本の本文から離れ、
本文を直した人が抜粋の食い違いに気づけない。

### 決定 6: 器の比較表と線引きは新しい文書 `work-vessels.md` に置き、`agent-layers.md` から指す

`agent-layers.md` は 477 行あり、表を足すと 500 行の上限を超える（`markdown-writing` の分量の
基準）。置き場所は、#680 で規則の置き場所に決まった `development-workflow/references/` の中にする。

`context-window.md` の「委譲する対象と、しない対象」に足す形は採らない。その文書は切れ目と
委譲の線と残量を持ち、器の選び方まで持つと責務が広がる。委譲の線からは 1 行で指す。

### 決定 7: #680 の問い 2（可搬性）と問い 3（共有する外部の枠）を切り出す

どちらも #828 の雛形に要らない。問い 2 は、ホストごとの代わりの手順を起動手段（`launch-cli.sh`）と
#760（worker の CLI 化）の上で設計する課題である。問い 3 は、並行の本数の数え方を、1 本あたりの
問い合わせの見込みと #849 の退避の上で設計する課題である。切り出し先は #888（可搬性）と
#889（外部の枠）で、#680 の本文の問い 2・3 から番号で指している。

同じ設計で扱う形は採らない。どちらも測定と別の課題の設計を入力に取り、この設計の Pull Request を
#845 系の着手条件（#855 は #828 のマージの後に始まる）より長く止めることになる。

### 決定 8: 線引きは比で書き、固定費の値を書かない

固定費はリポジトリとモデルで変わる（`context-window.md` の「固定費の値を規約へ書かない」）。
「読む量の見込みが worker の固定費を下回る」「返す量が読む量と変わらない」の 2 つの比にすれば、
導入した先で `skill-stats --agents` が測った値をそのまま当てられる。

行数やトークン数の閾値で書く形は採らない。書いたリポジトリの値が、別のリポジトリで読んだ人に
その環境の値として読まれる。

### 決定 9: supervisor の規則は数を 10 のまま、既存の規則 3 と 7 の文を書き換える

conductor の起動指示は「守る規則 10 個」と数で指し、起動指示を写した手順（引き継ぎの文書など）も
同じ数を持つ。新しい規則を 11 番目に足すと、数を持つ側がすべて古くなる。記録の規則 3 と委譲の
規則 7 は、書き換える内容と同じ主題を既に持つ。

worker の規則は 5 から 6 へ増やす。worker の起動指示は数で指していない（「守る規則 4 個」と書く
表があるが、本文の一覧は 5 個で既に一致していない）。実装で表の数を一覧に合わせる。
