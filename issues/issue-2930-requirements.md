# #2930: API キーの near-limit: 全アカウントの週の上限が近いときだけ、週の利用枠の中で claude -p をキーへ逃がす（5 時間の上限は待つ・キーを均等に・リセットで即座にやめる）

正は課題の本文（#2930）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 種類

機能

## 目的

`claude -p`（非対話の起動）の起動先を、アカウントの 5 時間の枠・週の枠と、API キーの月のクレジットの組み合わせで、1 つの規則の表から決める。達成したい状態は次の 2 つである。

- **アカウントの選び方**（#2931 を取り込む）: 5 時間の枠は使わなければ消えるため、5 時間の枠のあるアカウントを先に使い、週だけの枠のアカウントへは後で回る。切り替え（再起動による読み直し）の回数が最も少なくなる順に選ぶ
- **API キーへ逃がす条件**: 月のクレジットは対話の Claude Code に使えず `claude -p` にだけ使える（2026-11-10 に実機で確かめた: 同じキーで `claude -p` は exit=0、対話の claude は `Credit balance too low`）。そこで、登録済みのすべてのアカウントの週の枠が尽きかけたときだけ、週の利用枠の中で `claude -p` を API キーで起動し、対話のセッションのために週の枠を残す。5 時間の上限では API キーを使わず、解除を待つ

判定は、その時点で API から取った観測と使用量の帳簿だけから決める。判定のための状態（戻り先・戻り待ち・試し待ち・付与日・使い切った印）を内部に持たない。プロセスの終了やマシンの再起動の後も、同じ観測から同じ決定が出るようにするためである。

## 前提

- 前提 1: 対象の起動は `claude -p`（worker・supervisor の非対話の起動）と、relay（中継の再起動を担うラッパー）が区切りで行う起動先の選び直しである。対話の claude を API キーで起動しない
- 前提 2: アカウントの使用率・5 時間の枠の有無・リセット時刻は `GET /api/oauth/usage` の応答から取る。応答に 5 時間の枠が無いアカウントを「5 時間の枠の無いアカウント」とする
- 前提 3: Admin API（`credit_balance`・`cost_report`）は使わない（利用者の決定、2026-11-10）。API キーの使用額は使用量の帳簿にキーの名前を足して数える。帳簿は起きたことを追記するだけの記録で、判定のたびに読み直す
- 前提 4: アカウントの選び方で 5 時間の枠のあるアカウントを先に選ぶのをやめる週の閾値は、API キーへ逃がす閾値 T と同じ値を使う
- 前提 5: アカウントの週の使用率は、週の枠とモデル別の週の枠の使用率のうち最も大きい値である。5 時間の枠の使用率は API キーへ逃がす条件に入れない
- 前提 6: 消費の速さは、今の 5 時間の枠の使用率 ÷ その枠の開始（リセット時刻 − 5 時間）からの経過時間で見積もる。5 時間の枠の無いアカウントは週の枠で同じ形に見積もる。使用率が 0 のアカウントは、リセットまで持つものとして扱う
- 前提 7: 使用率の取得の費用を抑えるために控え（取得した値と時刻）を置く場合、控えの寿命は設計で決める。寿命を過ぎた控えと、控えの中のリセット時刻を過ぎた控えは使わずに取り直す。控えが無くても同じ決定が出る
- 前提 8: 週の利用枠の 1 週は「直近 7 日」（判定の時刻から 7×24 時間前まで）で数える。アカウントの週のリセット時刻には合わせない（利用者が「直近 7 日のキーごとの使用額がこれを超えないように」と決めたため）

## 対象範囲

含む:

- 起動先の決定を 1 か所に集め、観測 → 決定の純粋な関数と、観測を集める部分に分ける。決定は当たった規則の名前と根拠の値を持つ
- アカウントの選ぶ順（組の順と、同じ組の中の並べ方）と、区切りでの選び直し・切り替え（#2931）
- API キーへ逃がす条件（`near-limit`）、週の利用枠の計算、API キーの選び方、残高切れのときの扱い（#2930）
- API キーの登録での月の額の宣言と、登録済みの API キーへ月の額を宣言し直す操作
- 使用量の帳簿の記録への API キーの名前の追加
- `relay.py account list` の表示（5 時間の枠の有無・当たった規則の名前・API キーごとの月の額・直近 7 日の使用額・週の利用枠）
- 閾値 T の既定値を決める調査と、その結果の記録
- 今の判定（`claude_accounts.py` の `_try_order` / `_order_side` / `choose` の順、`claude_api_keys.py` の `near_limit` / `KeyRoute.wanted` / `pick_key`、API キーの状態のファイルと残高切れの 24 時間の保留）の置き換え

含まない:

- 対話の claude を API キーで起動すること（クレジットの対象外で、決済手段が無いと動かない）
- `api-key-use` の `always` と `off` の振る舞い
- Admin API の利用、クレジットの残高と期限の取得、付与日の推定、日に 1 回の試し
- 戻るためだけの確かめの間隔と、戻るためだけに区切りを早めること
- 従量の接続（`metered.json`）へ移る条件

## 用語

| 用語 | 意味 |
| --- | --- |
| 起動先の決定 | 1 回の起動について、どのアカウントか、どの API キーか、待つかを決めた結果。当たった規則の名前と根拠の値を持つ |
| 5 時間の枠の無いアカウント | 使用率の応答に 5 時間の枠が無い登録済みアカウント。`relay.py account list` の 5 時間の列が「-」になる |
| 週の使用率 | 週の枠とモデル別の週の枠の使用率のうち最も大きい値 |
| 閾値 T | API キーへ逃がすかを決める週の使用率の閾値。既定値は調査で決める（受け入れ条件 24） |
| 月の額 | API キーごとに宣言する、月に付与されるクレジットの額（ドル） |
| 週の利用枠 | API キーごとの、直近 7 日に使ってよい額。月の額 × 7 ÷ 30 |
| 使用の割合 | API キーの直近 7 日の使用額 ÷ その API キーの週の利用枠 |

## 受け入れ条件

決定の関数への入力（観測のスナップショットと宣言）と、期待する決定（規則の名前を含む）を並べた表のテストで確かめる。各行の例は、表のテストの行にそのまま使う。

API キーへ逃がす条件（#2930）:

- [ ] 1. `near-limit` で、5 時間の上限だけに当たり、週の使用率が T 未満のアカウントがあるとき、API キーで起動しない（解除を待つか、別のアカウントで起動する）
- [ ] 2. `near-limit` で、登録済みのすべてのアカウントの週の使用率が T 以上のときだけ、API キーで起動する。1 つでも T 未満のアカウントがあれば API キーで起動しない
- [ ] 3. 閾値 T は宣言で変えられ、宣言した値が受け入れ条件 2 の判定に効く
- [ ] 4. API キーの直近 7 日の使用額が週の利用枠以上なら、その API キーで起動しない
- [ ] 5. すべての API キーが週の利用枠を使い切っていれば、API キーで起動せず、アカウントの上限の解除を待つ今の扱いへ戻る。決定は規則の名前で「利用枠を使い切った」ことを示す
- [ ] 6. 週の利用枠は、宣言した月の額 × 7 ÷ 30 で計算される（例: 月の額 $200 → $46.67）
- [ ] 7. 2 本以上の API キーがあるとき、使用の割合が最も小さい API キーが選ばれる（例: キー A が利用枠 $46.67 に対し $30、キー B が $23.33 に対し $5 なら B）
- [ ] 8. API キーで起動した `claude -p` の帳簿の記録に、そのキーの名前が載る。キーの値は載らない。アカウントで起動した記録には載らない
- [ ] 9. どれか 1 つのアカウントの週の枠がリセットされた後の最初の起動は、API キーを使わない。前回の起動で API キーを使っていたことが、次の起動の決定に影響しない
- [ ] 10. API キーの起動が残高切れを返したら、その起動でだけそのキーを外して起動先を決め直す。次の起動ではそのキーがまた候補に入る（残高切れを内部に記録しない）
- [ ] 11. 月の額を宣言していない API キーは、`near-limit` で選ばれない。`relay.py account list` に宣言が無いことが出る
- [ ] 12. 月が替わってクレジットが付与し直されても、登録し直しも Admin API も使わずに、週の利用枠と使えるかどうかが直近 7 日の帳簿から計算し直される（例: 8 日前の使用額は直近 7 日の合計に入らない）

アカウントの選び方（#2931 を取り込む）:

- [ ] 13. 選ぶ順の組は次の順である。(1) 5 時間の枠があり 5 時間・週の両方に余裕があり、週の使用率が T 未満のもの → (2) 5 時間の枠が無く週に余裕のあるもの → (3) それ以外。5 時間の枠のあるアカウントと無いアカウントの両方に余裕があるとき 5 時間の枠のあるアカウントが選ばれ、5 時間の枠のあるアカウントの週の使用率が T 以上なら 5 時間の枠の無いアカウントが先に選ばれる
- [ ] 14. 5 時間の上限に当たったアカウントの次の起動では、その時点の規則で別のアカウントが選ばれる。戻り先・リセット時刻・戻り待ちの印を記録しない
- [ ] 15. 同じ組の中の順は次のとおり: 使い切るまでの時間が 5 時間のリセットまでの時間以上のアカウントがあれば、その中でリセットの早いものを選ぶ。どれもリセットまで持たなければ、使い切るまでの時間が最も長いものを選ぶ。例: 残り 30%・リセット 1 時間後の A と残り 30%・リセット 4 時間後の B では A、リセットまで持たない残り 5% の A と持つ残り 30% の B では B
- [ ] 16. 使用率が取れないアカウント（残量不明）は、取れるアカウントの後ろに並ぶ。取れるアカウントに余裕が無いときだけ選ばれる
- [ ] 17. 帳簿を読めないとき、API キーを使わない決定になり、決定の規則の名前がその理由を示す
- [ ] 18. relay の区切りのたびに起動先を選び直し、選んだアカウントが今のアカウントと違い、差が切り替えの余裕を超えるときだけ、その区切りで切り替える。5 時間の枠がリセットされたアカウントが規則で先頭に来ると、次の区切りでそのアカウントで起動し直される
- [ ] 19. 戻るためだけの確かめの間隔・印・区切りの前倒しを持たない。区切りと区切りの間に、戻るためだけの使用率の取得や再起動が起きない

決定の出し方と表示:

- [ ] 20. 起動先の決定は 1 つの関数が返し、その関数は I/O（API の呼び出し・ファイルの読み書き・時刻の取得）を持たない。同じ入力に対して同じ決定（規則の名前・根拠の値を含む）を返す
- [ ] 21. 判定のための状態のファイルを持たない。API キーの状態のファイル（残高切れ・認証の失敗の保留）と、一度立つと戻らない印（今の条件 3 の `limit_hit`）が無くなる。プロセスを起動し直しても、同じ観測から同じ決定が出る
- [ ] 22. `relay.py account list` に、アカウントごとの 5 時間の枠の有無と当たった規則の名前、API キーごとの月の額・直近 7 日の使用額・週の利用枠が出る
- [ ] 23. 起動先の決定（規則の名前と根拠の値）が、API キーへ移ったとき・アカウントへ戻ったとき・利用枠を使い切ったとき・区切りで切り替えたときに、relay の記録か進行の記録に残る
- [ ] 24. 閾値 T の既定値を、下の「T を決める調査」の結果から決め、根拠の数値とともに設計文書へ記録する

退行しない:

- [ ] 25. `api-key-use off` では起動の環境が変わらない（前提の確認: `tests/test_supervise_api_keys.py::test_off_keeps_the_launch_unchanged`）
- [ ] 26. `api-key-use always` では API キーを 1 本だけ子へ渡し、ほかの認証を外す。入れ子でも同じ（前提の確認: `test_always_puts_one_key_and_drops_other_auth`・`test_nested_always_drops_the_inherited_key_and_returns_to_an_account`）
- [ ] 27. 帳簿・表示・記録のどこにも API キーの値が出ない

## T を決める調査

受け入れ条件 24 のために、設計の工程で次を出す。

- 過去の週ごとの使用率の推移から、80%・85%・90% に達した時刻からリセットまでの消費量
- 発動の後、対話のセッションの消費の速さで、週の残りが何時間持つか
- 直近 7 日の `claude -p` の費用（帳簿）と、API キーごとの週の利用枠（月の額 × 7 ÷ 30）の比較

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 1 回の起動先の決定で使用率の API を呼ぶのは、登録済みアカウントごとに多くて 1 回。控えを置く場合は控えの寿命の中で呼ばない |
| 運用・保守性 | 決定ごとに規則の名前と根拠の値（週の使用率・リセット時刻・使用の割合など）が記録と表示に出て、利用者が後から「なぜそこで起動したか」を辿れる |
| 移行性 | 既存の API キーの登録（月の額の宣言が無いもの）は、登録し直さずに月の額を足せる。足すまでは受け入れ条件 11 のとおり `near-limit` で選ばれない。API キーの状態のファイルは読まなくなり、残っていても決定に影響しない |
| セキュリティ | API キーの値は帳簿・記録・表示・引数の誤りの表示に出さない（今の扱いを保つ） |

| 対象 | 影響 |

> - 設計文書に、決定の表（入力の組み合わせ → 決定と規則）と状態の遷移の表を載せ、設計承認ゲートで見られるようにする
