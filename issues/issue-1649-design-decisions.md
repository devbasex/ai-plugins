# #1649 #1668 #1669: cross-refactoring の取り消しの対象の決め方 — 決定の記録

この文書は、設計文書（`issues/issue-1649-design.md`）が持つ決定を記録する。要求は課題の本文（#1649・#1668・#1669）が正で、
`issues/issue-1649-requirements.md`・`issues/issue-1668-requirements.md`・`issues/issue-1669-requirements.md` がその写しである。
決定 1 は要求の工程で、決定 2〜11 は設計の工程で決めた。

## 決定 1: 工程の 1 つとして起動したときの最終ゲートの打ち切りは、案 A を主にし、通らないときだけ案 B へ落とす（#1669）

**状態: 推奨（設計の承認で人が採るかを決める）**

### 経緯

今の方針（`plugins/ndf/skills/cross-refactoring/docs/04-verify-and-report.md` の「最終ゲート修正は想定最大時間の終わりで打ち切る」）は、
最終ゲートは push 済みの地点なので打ち切っても取り消さず、取り消しの判断を Pull Request の読み手に任せる。

スプリント m725 の検査（Pull Request https://github.com/devbasex/ai-plugins/pull/1663 ）では、この方針のために次のことが起きた。

| 起きたこと | 数 |
| --- | --- |
| 結果 | `items 23 / adopted 0 / reverted 7 / unconfirmed 16 / final_gate failing` |
| 全体テストを落としたまま `sprint/m725` に残った未確認のコミット | 16 件（うち原因は 3 ファイルを触った 8 件） |
| conductor の手作業（原因の調査・`git revert`・全体テスト・`--from review` での流し直し） | 約 15 分 |

工程の 1 つとして起動したとき（`--workflow-step`）の読み手は人ではなく、プランと conductor である。プランは refactor の失敗で
`abort` へ進むだけで、判断の材料（どの項目が落ちたテストに関わるか）はスクリプトの手元にあるのに使われない。

### 比べた案

| | 案 A: 未確認の項目を取り消し、落ちたテストが通った時点で止める | 案 B: 着手前の HEAD の木へ戻すコミットを 1 本積む |
| --- | --- | --- |
| 残る改善 | 原因でない項目は残る（#1663 なら 16 件中 8 件、原因の項目の決め方（#1649）が効けばさらに多い） | 0 件。予算（30 分）と提案者の費用をすべて捨てる |
| 所要 | 取り消し 1 件ごとに落ちたテストを走らせ直す（#1663 の構造検査は 1 回約 3 秒）。件数に比例する | コミット 1 本。走らせ直しは要らない |
| 失敗の経路 | 積み直しの衝突・取り消し尽くしても通らない・時間切れがありうる | ほぼ無い（着手前の木は着手前の全体テストを通っている。既存失敗は既に除いてある） |
| 実装 | 既存の取り消し（`undo.drop`）と、検証の中の危険フラグの取り消し（新しい順・通ったら止める）と同じ形。#1649 の原因の項目の決め方を共有できる | 新しい操作（木を戻すコミット）が要る。取り消しの台帳（`ledger`）に項目ごとの理由が残らない |
| 記録 | 項目ごとに `reverted` と理由が残り、振り返りで原因の項目が分かる | 「全件を戻した」1 行だけ |

### 決めたこと（推奨）

**案 A を主にし、案 A で通らないとき（積み直しの衝突・候補を取り消し尽くしても通らない・時間の上限を使い切った）だけ案 B へ落とす。**
単独で起動したときは今の方針（取り消さずに報告）のまま残す。

### 理由

- **テストを壊していない改善を残す。** 案 B だけにすると、原因でない改善まで毎回 0 件にする。Mission（価値を届けるまでの時間と費用を減らす）と
  Value 1（まず届ける）に反する。案 A は #1663 で 8 件を残せた
- **同じ役割の処理を 2 つ作らない。** 案 A は検証の中の危険フラグの取り消しと、#1649 で直す原因の項目の決め方をそのまま使える（Value 6）。
  最終ゲート専用の取り消しを作らない
- **止まらずに終わることは案 B が保証する。** 案 A だけでは失敗の経路（衝突・時間切れ）でまたプランが止まる。案 B はコミット 1 本で
  走らせ直しを伴わないので、案 A の失敗の受け皿にすると、工程の 1 つとして起動した cross-refactoring はどの経路でも
  「全体テストが通る状態で完了」か「判断が要る（終了コード 4）」のどちらかで終わる
- **conductor の手当てをスクリプトへ移す。** 同じ手当て（原因の項目の手での取り消し）は #1634 と #1663 で 2 度起きている（Value 4）
- **単独の起動を変えない理由。** 単独では人が Pull Request を読み、取り消すかを人が決められる。読み手が判断を持つ場面で
  機械が先に取り消すと、人の判断の材料（落ちたままのコミット）が消える

### 守ること

- 取り消しはすべて `git revert` か、着手前の木へ戻す新しいコミットで行う。push 済みの履歴を書き換えず、強制 push はしない（共通原則 C4）
- 案 B の後の最終ゲートでも落ちたら、取り消しを重ねずに終了コード 4（判断が要る）で止まる
- 打ち切りの後の取り消しにかける時間の上限は `--budget-minutes` から算術で出す（式は設計で決める）

### 根拠にした項目

根拠: Mission / Value 1 / Value 4 / Value 6 / C4（MVV 版 2）

## 決定 2: 原因の判定を 1 か所にするため、判定は cross-refactoring の `culprit.decide` に置き、本文とパスの突き合わせだけをライブラリへ置く（#1649）

判定は改善項目・コミット・取り消しの順という cross-refactoring の語でできており、検証の全体テスト・寄せた危険フラグの取り消し・打ち切りの後の
取り消しの 3 か所が同じ関数を呼ぶ。ライブラリへ置くのは、項目を知らない 2 つの部品だけにする: JUnit の `failure` の本文を ID ごとに読む
`junit.failure_texts` と、本文に現れるパスを返す純粋な関数 `failure_paths.mentioned`。cross-review を調べた結果、失敗の本文から
パスや項目を引く処理は無かった（`review_lib/ci.py` は失敗したチェックの名前を `meta` と `code` に振り分けるだけ）。`mentioned` は
cross-review が CI の失敗ログと PR の変更ファイルを突き合わせるときにそのまま使える形にしておき、cross-review は変えない。

判定全体をライブラリへ置く案は採らなかった。ライブラリが改善項目と取り消しの順を知ることになり、supervise の `test-run.py` が使わない語を持つ。

根拠: Value 6 / Value 5（MVV 版 2）

## 決定 3: 出力に必ず現れる名前で誤って決めないため、手がかり 1 で落ちたテスト自身のファイルを外す（#1649 の未決 2）

pytest の本文はテストのファイルのパスを必ず含む。テストのファイルを変えた項目は、原因でなくても本文に現れる。外したことで原因を
見落とすのは、その項目がテストのファイルだけを変えたときに限られ、その場合は手がかり 2（外す走らせ直し）が拾う。

根拠: Value 3（MVV 版 2）

## 決定 4: 依存の用意をやり直さず、コンテナで走る suite にも届くように、項目を外す走らせ直しは同じ worktree で行う（#1649 の未決 1）

`git revert --no-commit <項目のコミット>` でworktree のファイルだけを変え、落ちたテストを走らせ、`git reset --hard HEAD` と `git clean -fd` で戻す。
HEAD は動かない。衝突しても `git reset --hard HEAD` で次の項目を外せることを、一時のリポジトリで確かめた（衝突の終了コードは 1）。
中断してworktree が汚れたまま残っても、次の副命令の後始末（`discard_impl_leftovers`）が戻す。

別の worktree で行う案は採らなかった。着手前の HEAD の見分け（`test_triage._failing_at`）と同じく、worktree を作るたびに依存を用意し直す
時間がかかり、コンテナで走る suite には届かない（その場合 `_failing_at` は見分けを諦める）。

根拠: Value 3 / Value 5（MVV 版 2）

## 決定 5: 決まらない判定で無関係な項目を直させないため、`undetermined` のときは修正へ回さずに取り消しへ進む（#1649）

要求のドメインイベント（E3 で決まらない → E6）のとおり、決まらないときは全項目を修正担当へ渡さない。全項目を `failing` にすると、
修正担当の起動と全項目の範囲テストの走らせ直しが増え、直せる見込みのない予算を使う。取り消しの順は、決まった項目を先に、
残りの候補を新しい順に並べる（`Verdict.order`）。一部の ID だけが決まったときも `undetermined` として扱う。

根拠: Value 1 / Value 4（MVV 版 2）

## 決定 6: 構造チェックの規則を 1 か所に保つため、ファイルの指定は検査の後の絞り込みだけにし、関わるファイルは違反が名指すファイルで決める（#1668）

同名・同じ本体の関数は木全体を見ないと決まらないため、検査は木全体で 1 回行い、指定は `items` と合否だけを変える。関わるファイルは、
違反の `path` と、同名・同じ本体のときは検査が集めたほかの定義のファイル。例外リストのファイルを変えた項目はその行に当たる違反を、
検査のスクリプト自身を変えた項目はすべての違反を数える。

規則ごとにファイルの単位の検査を足す案は採らなかった。規則が 2 か所に分かれ、木全体の検査と食い違う。`require-groups` と `hook-deps` の
間接の違反は範囲テストで拾えないことがあるが、全体テストの原因の判定（決定 2）が拾う。

根拠: Value 6 / Value 1（MVV 版 2）

## 決定 7: 新しい仕組みを作らないため、`.ndf/project.json` に suite を手で 1 つ足し、解析し直しでは今の規則（I1）に残させる（#1668 の未決）

`project-decl.py` は、前の解析の値のままでない項目を `kept` として残す（`project_lib/merge.py` の `merge_item`）。一時の複製に suite を
足して `write --dry-run` を打つと、`test` は `kept` になり、足した suite は消えなかった。宣言の印や解析の側の保持は足さない。

代わりに、`test` の項目はこの後の解析で自動では更新されなくなる（違えば `mismatch` として知らされる）。pytest の suite を変えるときは
手で直す。

根拠: Value 3 / Value 5 / C7（MVV 版 2）

## 決定 8: 打ち切りの後も refactor のステップの上限に収めるため、案 A の締め切りを `final_end_at + 0.20 × B` にする（#1669 の未決 1）

既定の B = 30 分で 6 分。外す走らせ直しと取り消しのたびの走らせ直し（PR 1663 の構造チェックは 1 回約 3 秒、pytest のファイル単位は
数十秒）が数件入る長さで、確かめ直しの全体テスト（実測 424 秒）を足しても 43 分になり、ステップの `timeout`（3600 秒）に収まる。
値はリファクタリング計画の時点で `limits` に書き出し、計画の上限の表へ載せる（時間に関わる数値はすべて `--budget-minutes` から算術で出す）。

固定の秒数にする案は採らなかった。予算を変えたときに追随しない。

根拠: Value 3 / Value 5（MVV 版 2）

## 決定 9: リファクタリング計画の記録と生成物を壊さないため、案 B の起点を `plan.base_sha`（リファクタリング計画を立てた時点の HEAD）にする（#1669 の未決 2）

`plan.base_sha` は、公開の台帳がまだ push していないときの公開の地点として使う値で、その後のコミットは改善項目・修正・オーケストレーターの
コミット（生成物の同期・リファクタリング計画の記録・取り消しの revert）だけである。木をこの地点へ戻すと、同期と計画の記録も消えるが、
次の push の直前の同期（`publish._sync_generated`）が積み直す。`init` の HEAD（`baseline_test.head`）との間にコミットは作られない。

根拠: Value 6（MVV 版 2）

## 決定 10: 止まらずに必ず終わるため、案 A と案 B を 1 回の実行でそれぞれ 1 度だけ使う（#1669）

案 A の後の確かめ直しで落ちたら案 B へ進み、案 B の後でも落ちたら終了コード 4（判断が要る）で止まる。使ったかは `final_gate.stop_revert.plan`
が持つ。案 B の後でも落ちるのは、着手前の木でも落ちる（変更起因ではない）か揺れであり、取り消しを重ねても直らない。

根拠: Value 2 / C4（MVV 版 2）

## 決定 11: 案 A の衝突を案 B へ渡すため、`undo.drop` に衝突を例外で返す選択を足す（#1669）

今の `drop` は、広げても積み直せないと HEAD を戻して終了コード 4 で止まる（`_restore_and_stop`）。案 A だけが `on_conflict="raise"` を渡し、
例外を受けて案 B へ進む。ほかの呼び出し元は今のまま止まる。取り消しの実装を最終ゲートのために別に作らない。

根拠: Value 6（MVV 版 2）
