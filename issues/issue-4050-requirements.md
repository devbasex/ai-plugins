# #4050: 並列の計画: 待っているレーンは設計を先に進め、承認が長く出ないときは設計するものが無くなるまで別の Issue の設計を流す

正は課題の本文（#4050）で、この文書はその写しである。本文から作り直す。手で直さない。

並列の計画で、実装が他のレーンと重なるレーンでも設計を先に進め、実装の手前でだけ待つ状態にする。あわせて、空いた時間にやることの一覧を計画に持たせて優先順位を決めておき、待ちに入ったレーンがラッパーを止めて枠を空け、オーガナイザーへ待ちを知らせ、耐久ワークフローが空いた枠へ一覧の先頭から別の Issue の設計を流し続ける状態にする。方針の出典は利用者の全体の設計方針（#4069 https://github.com/devbasex/ai-plugins/issues/4069 ）である。

## 何が起きたか

2026-11-22、計画 p12 で、実装が重なるために後ろへ回したレーンが、`issues/` しか触らない設計まで待たされた。

実測（11 系の 16 スプリント、2026-11-19〜21）では、リリースのフェーズが全体の 44%、うちリリースのリクエストが開いていた時間が 66.5 時間（中央 7.1 時間）で、中身はほぼ待ちだった。

## 今の利用者への影響と互換

- 計画の設定の形（`contracts/workflow/parallel-plan.schema.json`）は変えない。`after` の意味が、スプリントの行では「行を始める条件」から「実装のフェーズを始める条件」へ変わる。互換の経路は持たない（NDF は普及のフェーズの前で、MVV Value 5 の汎用性だけを守る）
- 動いている計画は、入れた後の最初の読み直しから新しい意味で動く。既に実行中の行は止めない

## なぜ困るか

実装が重なるだけで、設計（`issues/` と設計の文書しか触らない）まで後ろへ回る。待つレーンは何もせず、設計承認ゲートも実装を待った後に来るので、人の承認がさらに後ろへずれる。今はオーガナイザーが `touches` を `issues/` に絞り `after` を外す手作業と、conductor の画面への指示でしのいでいるが、`after` を外すと実装の手前で止まる仕組みが無くなり、止まるかは conductor が指示を覚えているかに掛かる。承認の待ちの間に別の Issue の設計を流す手順も、空いた時間にやることの一覧と優先順位も無いので、承認が何時間も出ない間、マシンの枠は待つレーンで埋まったままになる。利用者の全体の設計方針（2026-11-22）は、決められた範囲の資源をできるだけ使い、処理待ちを作らず、待つ間は別のことをするか待ちを上の層へ伝えて別のレーンを起動すること、そのために空いた時間にやることを常に整理し優先順位を決めておくことを求める。

## 目的

- **今どうなっているか**: レーンの `touches` と `after` はスプリント全体（要求から実装まで）に 1 つで掛かる。実装が重なるだけで、`issues/` しか触らない設計まで後ろへ回る。承認やほかのレーンを待つ間、レーンは何もしない。待ちの間に別の Issue の設計を進める仕組みも無い
- **誰に効くか**: 並列の計画を流すすべての利用者
- **変えると何が成り立つか**: 待ちの時間に、設計（と重ならない実装）が先に進む。承認が出た時点で、次に流すものの設計が既に承認待ちに並んでいる

## 前提

- 前提 1: 設計のフェーズの工程（`metadata.ndf.phase` が `design`）が触るのは、`issues/` の下のその課題の文書と設計 Pull Request だけで、ほかのレーンの実装と重ならない。課題の重なり（I19）が、同じ課題を 2 つのレーンで流すことを断っている
- 前提 2: スプリントの行のスプリントは `ndf progress new --parent <レーンのステートマシン>` で作られ、工程は `ndf progress next` が流す（`src/ndf/progress/lane/launch.py:182-214`）。実装のフェーズの最初の工程はこの口を通る
- 前提 3: 実装の待ちの行のレーンの conductor は、待ちの間にすることが無い。ラッパーを止めても、状態はステートマシンにあり、起動し直した conductor が `ndf progress next` で続けられる（今の回答の後の起動し直しと同じ）
- 前提 4: 設計の工程の承認ゲートで差し戻した行を中止し、同じ課題の行を足して設計し直す形は、今の計画で使われている（p12 の lracct の r1〜r3。`ndf progress new --carry`）
- 前提 5: 一覧を作り直すコマンドは GitHub を読むだけで書かない。二次レート制限（#4016）に当たらないよう、1 回の呼び出しの読み取りは計画のマイルストーンの数と項目の数に比例する回数に収める
- 前提 6: 開いたマイルストーンの名前は `<2 桁の連番> <主題>` で、連番が着手の順序を表す（`AGENTS.md` の「版とリリースの方針」）。連番を持たない名前のリポジトリもある

| 対象 | 影響 |
