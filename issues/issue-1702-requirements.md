## 何が起きたか

スプリントの Pull Request（16 ファイル・+973 / -441、4 課題分の差分）の cross-review で、レビューの担当が差分の末尾の 2 コミットだけを見て APPROVE した。

| round | 担当 | 見た範囲 |
| --- | --- | --- |
| 1 | codex / kiro | kiro は末尾の 2 コミットだけ。codex は総評から範囲が読めない |
| 2（`--reopen`） | claude / kiro | 2 者とも末尾の 2 コミット（cross-refactoring が足したもの）だけ。claude は「変更は manager.py だけ」と書いた |

スプリントの Pull Request は、検査のプランで cross-refactoring の後に cross-review が走るため、末尾にリファクタリングのコミットとリファクタリング計画のコメントが付く。担当はそれを手がかりに、範囲を末尾のコミットへ狭めた。round 1 の「全員 APPROVE・指摘 0」は、全差分を見た結果ではなかった。

## 原因の見立て

担当へのプロンプトに、レビューする差分の範囲（base と head の SHA）が書かれていない。担当は Pull Request のコメントや直近のコミットから範囲を推測する。

## 直し方の案

- 担当へのプロンプトに `git diff <base_sha>...<head_sha>` と対象のファイル数を書く（ラウンドごとに head を更新する）
- 総評に「読んだファイル数」を書かせ、差分のファイル数と大きく違えば収束と数えない

## 目的

- cross-review の収束（「新規の指摘 0 件・全員が通した」）を、担当が Pull Request の全差分を見た結果に限る。担当が範囲を推測して末尾のコミットだけを見た承認で、収束したと数えない
- 担当がレビュー範囲を推測しなくてよいように、範囲をプロンプトで渡す

## 前提

- 前提 1: レビュー範囲の base は、そのラウンドを始めた時点の Pull Request の base（`baseRefOid`）、head はそのラウンドの `rounds[-1].head_sha` である。3 点の `git diff <base>...<head>` は merge-base からの差分で、GitHub の Pull Request の差分と同じ範囲になる
- 前提 2: 差分のファイル数は、プロンプトに載せるのと同じ範囲の `git diff --name-only` の行数で数える（GitHub の API のファイル一覧の件数ではない）。担当がプロンプトのコマンドを打てば同じ数を得られるようにするためである
- 前提 3: 設計 Pull Request の 2 ラウンド目以降は、今の振る舞いのとおり前のラウンドの head からの変更だけを見る（#1005）。そのラウンドの差分のファイル数はその範囲で数える
- 前提 4: 読んだファイル数は担当の自己申告で受ける。担当が本当に読んだかを、担当のツールの呼び出しから確かめることはしない
- 前提 5: 担当の worktree に base のコミットが無ければ、範囲を求める前に取得する。取得しても範囲を求められないときは、ラウンドを止めず、今の振る舞い（範囲なしのプロンプト）に落とす

## 対象範囲

含む:
- cross-review の担当へのプロンプトに、レビュー範囲（base と head の SHA・差分のコマンド・ファイル数）を載せる
- 担当の結果ファイルに読んだファイル数を書かせ、判定で差分のファイル数と突き合わせる
- 突き合わせで外れた「通した」結果を収束に数えない
- 結果ファイルの契約の文書（`plugins/ndf/skills/cross-review/docs/`）の更新
- スプリント PR の形の入力でのテスト

含まない:
- cross-refactoring の提案担当・実装担当のプロンプト（この課題の現象は cross-review の担当で起きた）
- 担当が実際に読んだファイルを、ツールの呼び出しの記録から数えること（前提 4）
- 総評の文への読んだファイル数の記載（起票者の推定 S4）
- 最終スイープ（Step 7.5）・反証（critique）・検証（verify-findings）の担当への範囲の受け渡し
- ラウンドの上限・振動の判定の変更

## 受け入れ条件

- [ ] 1. code の Pull Request の各ラウンドで、担当へのプロンプトに base の SHA・head の SHA・`git -C <worktree> diff <base_sha>...<head_sha>` の形のコマンド・その範囲の差分のファイル数が載る
- [ ] 2. 2 ラウンド目以降のプロンプトの head の SHA は、そのラウンドの `rounds[-1].head_sha` であり、差分のファイル数はその head で数え直した値である（round 1 の head が A、round 2 の head が B なら、round 2 のプロンプトに B と B での数が載り、A は head として載らない）
- [ ] 3. 設計 Pull Request の 2 ラウンド目以降は、前のラウンドの head からそのラウンドの head までの範囲と、その範囲のファイル数が載る（前提 3）
- [ ] 4. 担当へのプロンプトが、結果ファイル（`result.json`）に読んだファイル数を整数のキーで書くよう指示し、`read-result` がその値を読んで状態ファイルのそのラウンドの担当の記録に残す
- [ ] 5. `judge` で、通した担当（`APPROVE`、または重大な指摘の無い `COMMENT`）の読んだファイル数が差分のファイル数としきい値以上に食い違うとき、その担当を「全員が通した」の判定に数えない。判定の出力に、その担当の席の名前・読んだファイル数・差分のファイル数が載る。差分 16 ファイルで読んだ数 2 なら数えず、読んだ数 16 なら数える（しきい値は設計が決め、この 2 例をこのとおりに分ける）
- [ ] 6. 通した担当の結果ファイルに読んだファイル数が無い、または整数でないときも、5 と同じく「通した」に数えず、理由が判定の出力に載る（測れないことを一致として扱わない）
- [ ] 7. 5・6 で外れた担当しか通していないラウンドは収束せず、ループは終了しない。外れた後に同じ席を起動し直すか次のラウンドへ進むかは設計が決め、どちらでもラウンドの上限は今のまま効く
- [ ] 8. レビュー範囲を求められないラウンド（前提 5）は止まらずに担当を起動し、プロンプトは今の形で、判定の出力にそのラウンドのファイル数を照合しなかったことが載る
- [ ] 9. スプリント PR の形の入力（base から 16 ファイルを変えた複数のコミットの末尾に、1 ファイルだけを変える cross-refactoring のコミットが 2 件付く）で、1・2・5 を確かめるテストがあり通る。末尾の 2 コミットだけの数（1）を申告した担当の `APPROVE` で収束しないことを含む
- [ ] 10. `REQUEST_CHANGES` の担当の指摘は、読んだファイル数に関わらず今と同じく取り込まれる（照合で指摘を捨てない）
- [ ] 11. cross-review の既存のテストが通る

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 差分のファイル数は worktree の `git` で数え、ラウンドごとに GitHub の API の呼び出しを増やさない（base の SHA の取得を除く） |
| 運用・保守性 | 照合で外れた担当・照合しなかったラウンドが判定の出力と状態ファイルに残り、後から読める |
| 移行性 | base の SHA を持たない前の版の状態ファイルから再開しても止まらない（取得し直すか、範囲なしに落ちる） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない（コマンドの引数は変えない）。担当の結果ファイルの契約にキーが 1 つ増え、`judge` の出力に行が増える。どちらも cross-review の内部の契約で、互換あり |
