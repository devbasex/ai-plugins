# 開発ループとキューの続きの決定の記録（#2664）

設計文書は [issue-2664-design.md](issue-2664-design.md) にある。

## 決定の記録

### 決定 1: 呼び手が周回の番号を知らなくても当たるよう、問いの当て先は `--plan` のパスが周回のディレクトリの下にあるかで引く

周回のプランは必ずその周回のディレクトリ（`.ndf/loop/<ループ>/lap-<N>`）の下に作られ、周回どうしで重ならない。問いを送る hook は周回の番号を持たず、引数を足すと手順書と保留の案内の両方を変えることになる。

プランの一覧を周回の記録と照らす形は採らない。一覧がマニフェストとまとめの 2 か所に分かれ、読む処理が増えるためである。

候補が進行中の周回 1 つだけでプランがディレクトリの外にあるときは、今と同じくその周回へ当てる。受け入れ条件 19 の退行を避けるためで、締め直しの途中の周回があるときはこの扱いをしない。

根拠: Value 7（MVV 版 6）

### 決定 2: 本番の版と費用の記録を失わないよう、問いが当たった締め直しの途中の周回は、締めの処理を通さずに質問待ちへ戻す

締めの処理（`close_lap`）は、版・費用・振り返りの値を周回の行へ固定する。周回の値が定まる最後の締め直しで 1 回通せばよい。戻すときは結果と終わった時刻だけを書き換える。こうすると `release` の答えと本番の版は手を入れずに残る。

`finish_lap` を通して版を退避し書き戻す形は採らない。途中の値が記録を上書きし、退避の漏れが版の欠けになるためである。

根拠: Value 7（MVV 版 6）

### 決定 3: 問いの記録を読む側を変えないよう、`question` は最後の問いのまま残し、前の問いは前の待ちの控えへ移す

`question` を読む箇所は、1 つの問いを前提にしている。一覧に変えるとそのすべてを直すことになる。最後の問いは `question`、前の問いは `held_history` に置けば、読む側は今のまま動き、受け入れ条件 16 の「最後の問いと答えの両方が読める」も満たす。周回の区間は両方の `finish` を足す。

`question` を上書きするだけの形は採らない。前の答えが消えると、周回が 2 回止まった理由を後から確かめられないためである。

根拠: Value 8（MVV 版 6）

### 決定 4: 遅れた `loop finish` が質問待ちへ戻した周回を締めないよう、`loop finish` は今の待ちの done だけを受ける

問いが当たると、今の待ちは新しい問いになり、答えを読むまで `finish` を持たない。done の照合だけで、受け入れ条件 4 が満たせる。周回に「締め直しの世代」の番号を足す形は採らない。done が同じ役割をすでに持つためである。

根拠: Value 5（MVV 版 6）

### 決定 5: 完了したプランを流し直さないよう、キューの中で止まったプランは `queue --resume` で続ける

今の形は `run` の後に新しい done で queue を流す。新しい done は新しい耐久の記録を開くため、同じステージで完了したプランが頭から流れる。止まったプランの done の一覧と耐久の記録を使う `queue --resume` なら、完了は流れず、残りのステージも同じ条件で流れる。問いの続きと強制終了の続きが同じ経路になり、根本原因が 1 か所に集まる。

止まった場所はプランが周回の最後の done の一覧にあるかで分かる。締め直しの途中で無いのは先頭の `run` で止まったときだけで、このときキューはまだ始まっていないため、前の body をそのまま使う。

進行中の周回の問いも同じ規則で組む。まとめは周回の done のキューに入るため（`sprint_pipeline`）、まとめの中で止まったプランは一覧に載り、新しい done で流すと同じステージの完了が流れ直す。一覧に無いプランは周回の done の外のキューで止まったもので、今の形のまま流し、受け入れ条件 19 の振る舞いを保つ。

- 作り方: 自前で作る
- 比べた候補: PRD1 / PRD3 / LIB1

根拠: Value 7 / Value 3（MVV 版 6）

### 決定 6: `{queue_pr:<名>}` と前提のプランの照合を変えないよう、`--from` の照合はキューの続きの中に閉じる

`queue_fill.named` は差し込みと前提のプランも使う。ここへパスの照合を足すと、受け入れ条件 21 の範囲まで振る舞いが変わる。キューの続きに、名前の一致かパスの一致を見る関数を置く。パスに `=` が入っても読めるよう、区切りは最後の `=` にする。

断るだけにして名前を求める形は採らない。一覧に載っている値を渡して断られる状態が残るためである。

根拠: Value 7（MVV 版 6）

### 決定 7: 指定が前の位置より勝つよう、`--from` があれば途中を子ごと止め、ほかのプランの位置は耐久の記録と状態のファイルから決める

止める条件は #2342 の決定 5 と同じで、`launch_queue` の `fresh` を「並びが変わった、または `--from` がある」に広げる。止めるとほかの途中のプランも取り消され、次の実行の回が頭から流れる。そのため、done が無いときは、`--from` の対象でないプランのうち最後の実行の回が完了でないものを選ぶ。それらは状態のファイルの最後のステップから続ける（受け入れ条件 9）。

止めるのは強制終了で残った途中だけで、動いている前の起動は止めない。`durable.launch` は排他が空くまで待つため、そのままでは待った後に古い位置で流れる。そこで `--from` があるときは位置を決める前に排他を待たずに試し、動いていれば done を消さずに `stopped` を返す。

取り消しを対象のプランだけに絞る形は採らない。プランの耐久ワークフローはキューの耐久ワークフローの子で、親を続けると新しい開始の位置を渡せないためである。

- 作り方: 自前で作る
- 比べた候補: PRD2 / LIB1 / LIB2

根拠: Value 7 / Value 2（MVV 版 6）

### 決定 8: 差し込みの書き換えを「変わった」と読まないよう、完了の判定は耐久の記録の最後の実行の回の中身のハッシュで行う

実行の回の ID には、差し込みを埋めた後のプランの中身のハッシュが入っている（`flow.prefix_of`）。ここと、続きの時点でまだ差し込みをしていない今のファイルのハッシュを比べる。別の置き場を足さずに、要求の未決の「前の中身の置き場」が解ける。最後の実行の回が完了でハッシュが違えば、変わったと判定する。後から新しい中身で流し始めた回があれば、最後の回は完了でない。そのため古い完了では止まらない。

done が完了と記録し、耐久の記録に完了の回が無いときは、done を採って流さない。手で書き換えた done と、30 日を過ぎて消えた記録がこれに当たる。#2349 で done を書き換えても流れた経路がこれである。

done の項目にハッシュを持つ形（#2344 の決定 7）は、このスプリントでは採らない。done を書けずに落ちた起動で判定できないためである。この形は #2344 の実装がプランの型と一緒に入れる。この判定はプランのファイルの中身で行い、#2344 の実装が来たら置き換える。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1 / PRD1 / LIB2

根拠: Value 7 / Value 8（MVV 版 6）

### 決定 9: 黙って流さず、人が 1 回で判断できるよう、変わったプランがあれば何も流さずに `gate` と終了コード 10 を返す

一部だけ流して途中で知らせると、同じ続きを 2 回読むことになる。先に知らせて止めれば done も耐久の記録も変わらず、判断の後に同じコマンドで続けられる。

終了コードはキューが承認ゲートで止まったときと同じ 10 にする。読み手は `status` か 10〜19 の範囲で分かれ、番号ごとに分ける箇所が無いためである。`plugins/ndf/scripts` の `*.py` を `== 1[1-9]` などで検索した（テストは除いた）。結果は、範囲の判定 `step_result.GATE_CODES`・`slow_step.py:214` と説明文だけである。

流さないと決めたときはプランのファイルを戻す。流さずに完了を受け入れる引数は足さない。使う場面の実測が無いためである。

根拠: Value 2 / Value 3（MVV 版 6）

### 決定 10: 飛ばすはずのプランが流れず、承認した配布が飛ばないよう、実行条件を評価するプランをキューの続きが選ぶ

#2349 の 2 本のプランは `--from` で始めたため、実行条件が見られなかった。一方、承認ゲートで止まったプランは条件を通った後で、承認の後に評価すると「変更が無い」で配布が飛ぶ（要求の前提 5）。`--from` で承認ゲートの後のステップへ入る経路（`pace.md` の「承認の後に別のエントリポイントから入るステップ」）も同じである。そのため、前の結果が承認ゲートのプランは `--from` があっても評価しない。質問待ちの続きは `--no-condition` で評価しない。`run --from` は変えない。

#2344 の決定 8 は開始のステップによらず評価する形で、要求の前提 5 のとおりこの課題はそれより狭い。

根拠: Value 7 / Value 2（MVV 版 6）

### 決定 11: 自由記述の意味を機械で推し量らないよう、機械が流さないのは `rejected`・`revise` だけにし、ほかは中身を持ち主へ渡す

`rejected`・`revise` は答えを送る人が選んだ機械の読める値である。自由記述（#2638 の「まだ」）の意味は機械では読めない。`metrics.answer` で持ち主の AI へ渡し、`references/loop.md` の手順 2' を「答えを読んでから pipeline を流すか見送るかを決める」に変える。

根拠: Value 5（MVV 版 6）

### 決定 12: 続けない周回を 1 つの手段で締めるよう、新しい副命令 `loop decline` を足し、`fixes` へ足すのは `revise` だけにする

`loop finish` は流した結果の done を読む命令で、流さなかった締めを足すと `--done` の必須が崩れる。`loop answer` は設計の承認の行への答えで、対象が違う。

`revise` は直して出し直す答えである。そのため `fixes` に行を足し、次の周回で先頭に選ぶ。`rejected` と見送りは続けない判断なので足さず、課題は次の棚卸しの順位に任せる。配布の差し戻しが `fixes` へ足すのは、配布を止めた変更の直しが要るためで、問いとは事情が違う。本番の版は締めの後も残す。

根拠: Value 3 / Value 5（MVV 版 6）
