# #550 / #657: 工程を window へ出して無人で通し、window の大きさと中断を扱う

設計は [issue-550-657-design.md](issue-550-657-design.md) にある。この文書は「何を満たすか」だけを扱う。

**2 つの課題を 1 本の設計 Pull Request で決め、実装は 3 本に分ける**（分け方と順序は設計文書が持つ）。
受け入れ条件は主題ごとに並べ、どの実装 Pull Request が満たすかは設計文書の表が対応を持つ。

| 主題 | 課題 | 中身 |
| --- | --- | --- |
| A 無人の運転 | #550 | `/goal` の工程を使い捨てのサブエージェントへ出し、親は指揮・承認の仲介・報告の受け渡しだけを持つ |
| B window の測定 | #550 | window ごとの固定費・最大充填・実作業を会話の記録から測り、振り返りへ集計を出す |
| C 中断と再開 | #657 | 工程の担当が利用上限（429）で落ちたことを親が見分け、解除を待って再開する |

## 目的

- `/goal /ndf:development-workflow <指示>` が、**2 つの関門以外は人間の入力なしで**、複数の課題を設計から振り返りまで通す
- 1 つの window が劣化の域へ入る前に工程の境で window を捨て、後の工程の判断を悪くしない
- 粒度とモデルの割り当てを、導入したリポジトリの実測で決められる
- 担当が利用上限で落ちても、人が「続けて」と指示しなくても工程が再開する

## 実測（要求の根拠）

**#550 の本文の実測に、#657 のための実測を足した。** 走査したのは
`~/.claude/projects/-work-ai-plugins/` の記録である（2026-09-17 時点）。

### 担当が利用上限で落ちたとき、親に何が届くか

**親には失敗の通知が届く。** 本文に種別と解除時刻が入っている（2026-09-01、Claude Code 2.1.252）。

```text
<task-notification>
<task-id>aad4dc48e9699f55e</task-id>
<status>failed</status>
<summary>Agent "Fix PR 213 round 2" failed: Agent terminated early due to an API error:
You've hit your session limit · resets 3:40pm (UTC) (error type rate_limit, HTTP 429, ...)</summary>
<note>... The user can send it another message and resume it, so the same task-id may notify more than once.</note>
```

**担当の記録にも同じ中断が残る。** 最後の行は合成の応答で、解除時刻を数値で持つ。

| キー | 値の例 | 意味 |
| --- | --- | --- |
| `isApiErrorMessage` | `true` | API の失敗を表す合成の応答 |
| `error` / `apiErrorStatus` | `rate_limit` / `429` | 種別（他に `server_error` / `authentication_failed` を観測） |
| `message.model` | `<synthetic>` | 合成の応答。`usage` はすべて 0 |
| `quotaLimits.rateLimitType` | `five_hour` / `seven_day` | 上限の種類 |
| `quotaLimits.resetsAt` | `1789452000` | 解除時刻（UNIX 秒） |

### 親も同じ上限に当たる

**通知を受けた親の応答も、同じ上限で失敗する。** 同じアカウントの割り当てを使うためである。
2026-09-14 の進行（2.1.265）では、担当 3 本の失敗の通知を受けた親の 3 回の応答が、いずれも
1 秒以内に `You've hit your session limit` で終わった。**上限の間、親は何もできない。**

### 解除の後に Claude Code が自動で続けた例が 1 つある

**週次の上限の解除時刻ちょうどに、親へ入力が積まれた**（2026-09-15 06:00:41、2.1.265）。

```text
system: Usage limit reset · continuing automatically
user（origin: auto-continuation）: Your claude.ai usage limit has reset. Continue the task you were
working on when the limit was reached; do not repeat work that is already complete.
```

親はこの入力で目を覚まし、中断した担当を `SendMessage` で再開した（`Resuming agent`）。
**再開の手順は会話の場で組み立てたもので、規約には無い。** 同じ日のセッション上限では、
利用者がアカウントを切り替えて「続けて」と送っていた（11:54）。**自動の継続を観測したのは
全記録でこの 1 回（ai-plugins）と別リポジトリの 1 回だけである。**

### `/goal` の見回りは止まる

親が背景の作業を待つ間、`/goal` は「Goal check-in」を積む。間隔は 30 分 → 61 分 → 120 分と
伸び、**120 分の後は `idle check-ins paused until your next message` で止まった**。
見回りに頼って再開を待つと、長い上限の間に見回りが尽きる。

### 担当の記録は応答を複数行に分けて持つ

**同じ `message.id` の行が並ぶ。** 1 本の担当で assistant の行が 212 行、固有の応答は 126 件だった。
行の数を応答数として数えると 7 割近く多く出る。起動時の `description` は
`subagents/agent-<id>.meta.json` にそのまま残る（28 件で一致）。

## 受け入れ条件（C: 中断と再開 #657）

- [ ] AC40: 親は、次のどれかの契機でそのセッションの window の記録を読む。
  契機は `<status>failed</status>` の通知・自動の継続・人の入力・背景の待ちの終わりの 4 つである。
  最後の応答が `apiErrorStatus: 429` の合成の応答である window を、**上限の中断**として分類する。
  `server_error`（500 / 529）と `authentication_failed` は、これと区別して扱う
- [ ] AC41: 上限の中断の解除時刻を、応答の記録（`quotaLimits.resetsAt`）から取る。**固定の間隔で待たない**
- [ ] AC42: 解除の後、親は中断した window を `SendMessage` で同じ window のまま続けさせる。
  続けられないとき（`SendMessage` の結果が `"success": true` を持たない）は、`progress-tracking` の記録が指す工程の頭から新しい window を起動する
- [ ] AC43: 親も上限に当たり、解除時刻に自動の継続が入ったとき、**人間の入力なしに** AC42 の再開が行われる。
  自動の継続が入ること自体は Claude Code の振る舞いで、この課題の条件にしない（未確認 U2）。条件にするのは、入った後の点検で再開が行われることである
- [ ] AC44: 親が上限に当たらずに window だけが中断したとき、親は解除時刻を過ぎるまで再開しない。
  待つ間に `/goal` の見回りが尽きても、解除時刻の後に親が目を覚ます経路がある
- [ ] AC45: 自動の継続が起きなかったとき、人間が送る 1 通（例:「続けて」）で AC42 と同じ手順が走ることが規約に書かれている。
  **この 1 通は承認ではなく、関門の数に数えない**
- [ ] AC46: 複数の window が同時に中断したとき、中断したすべての window が再開される。完了していた window は再開しない
- [ ] AC47: 親の window が中断の通知を失っても（自動の要約の後など）、`--session` で中断した window （終わり方 `rate_limit`）と解除時刻を一覧できる
- [ ] AC48: 再開した window は、既に済んだ外部への書き込み（Pull Request の作成・コメントの投稿・進行の記録）を重ねない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 工程の window 1 つの最大充填が、モデルに依る目安を超えない運用を既定にする。総消費（固定費 × window の数 + 実作業）が 1 つの window で通すより増えることを受け入れ、増え方は AC29 の表で見る |
| 運用・保守性 | 上限の中断と再開の回数が window の測定に残る。報告なしで続けさせた回数が親の報告に window ごとに残る。見回りが尽きたことに人が気づけるよう、親は止まる前に現在地を 1 回出す |
| セキュリティ | 測定は会話の記録をローカルで読むだけで、送信しない。出力にパス・本文・プロンプトを含めない（#159） |
| システム環境 | Claude Code の `/goal`・`Agent`・`SendMessage` を前提にする。自動の継続が無い版でも、AC45 の経路で工程が失われない |

## 用語

| 語 | この文書での意味 |
| --- | --- |
| セッション | 会話を保持しているプロセス。1 つのセッションが 1 つの window を持つ |
| window | そのセッションが保持している内容の全体。捨てると前の内容は残らない |
| 工程の window | 連続する工程を 1 つのサブエージェントで通す単位。終わると消え、親には報告だけが返る |
| 親 | 人間と対話しているセッション。`/goal` を受けた側 |
| 固定費 | window が作業を始める前に既に埋まっている量。**初回の応答の入力トークン**（`input_tokens` + `cache_read_input_tokens` + `cache_creation_input_tokens`） |
| 最大充填 | 応答ごとの同じ合計の最大 |
| 実作業 | 最大充填 − 固定費 |
| 合成の応答 | API を呼ばずに Claude Code が記録へ書いた応答。`message.model` が `<synthetic>` |
| 中断 | 工程の window が API の失敗で途中で終わること。利用上限（429）による中断を**上限の中断**と呼ぶ |
| 解除時刻 | 上限が解ける時刻。通知の文言と記録の `quotaLimits.resetsAt` が持つ |
| 自動の継続 | 解除時刻に Claude Code が親へ積む入力（`origin.kind` が `auto-continuation`） |
| 報告 | 工程の window が最後に返す、項目の決まった結果 |

**この用語は実装で触る規約の文書にも当てる**（AC16）。コンテキストの window を指す語は `window` と書き、「窓」を使わない。`monitor.py` の文脈窓や窓口のように別のものを指す語は対象外である。


## 依頼（原文）

### 進行側の指示（抜粋）

> #550 /goal の工程をサブエージェントへ出し、2 つの承認以外を無人で通す（工程ごとの window の大きさも測る）。本文に既に要求・受け入れ条件・対象範囲が詳しく書かれている（進行: 要求と受け入れ条件は記録済み）
>
> #657 担当が利用上限で落ちたことを進行側が検知できず、再開を手で指示している
>
> #550 の設計は大きいため、実装 Pull Request を複数に分ける案（例: 工程のサブエージェント化 / 測定と skill-stats / 中断の検知と再開）を設計文書に含めてよい

### #550 の受け入れ条件（原文）

> - [ ] `/goal /ndf:development-workflow <指示>` が、**2 つの関門以外で人間の入力を求めずに**、複数の課題を設計から振り返りまで通す
> - [ ] 関門では親が `AskUserQuestion` で止まり、承認の後に次の工程のサブエージェントが起動する。**人間は `/clear` も再開のコマンドもラベルも要らない**
> - [ ] 工程ごとに、「測定」の節が挙げる 6 項目が記録される。**固定費と実作業が分離して記録される**
> - [ ] 記録が `retrospective` の出力に集計として現れる
> - [ ] `cross-review` の「メイン」が何を指すかが規約に書かれている（工程のサブエージェントが主体になると、あの Skill の「メイン context に diff を載せない」の対象が変わる）
> - [ ] 工程ごとにモデルを選べる。既定と、軽いモデルへ落とす工程の判断基準が規約にある
> - [ ] **粒度の基準が値ではなく比で規約に書かれている。** 固定費の実測値を規約へ埋め込まない
> - [ ] `references/context-window.md` に、**モデルに依る目安**（劣化が始まる長さ）と**リポジトリに依る固定費**の区別が書かれている
> - [ ] 1 課題を実際に無人で通し、記録が残ることを確かめてある

### #657 の直し方の候補（原文）

> 1. `development-workflow` の並行開発の節へ、**担当の中断を検知して再開する**手順を足す。検知は担当の応答が上限の形で終わったこと（`api_error_status: 429` / 上限の案内）で行い、再開は工程の入口（`progress-tracking` の記録が指す工程）から行う
> 2. 再開の入口を決められる形にする。控え（通過工程）と進行の記録は工程の粒度で残っているため、**落ちた工程の頭から** やり直すのが既定になる。作業ツリーとブランチは残っているため、やり直しても差分は失われない
> 3. 上限の回復まで待つ長さを応答から取る（`issue-upkeep` の「外部への書き込みの制限」と同じ扱い。固定の間隔で待たない）
