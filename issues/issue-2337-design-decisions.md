# #2337 の設計の決定の記録

設計文書の本体は [issue-2337-design.md](issue-2337-design.md) にある。決定はどれも柱 P1 の形を決める。どれも #2335 の設計（`issues/issue-2335-design.md` と `issues/issue-2335-design-decisions.md`）の決定の範囲にある。

## 決定の記録

### 決定 1: 64 項目の本体とテストを柱ごとに書き直さないよう、柱 P1 では既存の `main(argv)` をそのまま本体として核へ渡す

P1 は `run_core.main("<契約の path>", main)` で既存の `main` を渡す。実行の文脈（実行の識別子・期限・契約）は `run_core.context()` で引けるようにする。核を通ったかの検査（`__main__` の中身が `run_core.main` の 1 文）は #2335 の決定 1 のまま成り立つ。

#2335 の設計は本体を `body(ctx) -> Outcome` と書く。この形へ移すには、引数の解決（`argparse`）を本体から外す必要があり、それは柱 P8（入力の部品）の仕事である。P1 で `ctx` の形へ書き換えると、P8 でもう一度書き換えることになる。書き換える対象は、64 項目の本体と、`main([...])` を呼ぶ既存のテストである。

本体を `body(ctx)` にそろえてから移す形は採らない。P8 の前に引数の解決の置き場を決めることになり、柱の順序を崩す。

根拠: Value 6 / Value 10（MVV 版 4）

### 決定 2: 46 項目の標準出力を柱 P7 の前に変えないよう、標準出力が結果 JSON でないエントリポイントの結果は `NDF_RESULT_FILE` が指すファイルへ書く

核は、呼ぶ側が環境変数 `NDF_RESULT_FILE` でファイルを渡したときだけ、最終の結果 JSON をそこへ 1 行で書く。結果を読みたい呼ぶ側（supervise の run のステップ・テスト）は、ファイルを渡して読む。

契約の `stdout` が `step-result` でない項目は 46 ある（`text` 34・`json` 5・`none` 5・`kv` 2）。その標準出力は、呼ぶ側の Skill の本文・プラン・利用者の端末がそのまま読む。核が標準出力へ結果 JSON を足すと、`| tail -1` や `KEY=VALUE` の読み手が壊れる。

標準エラーへ結果 JSON を出す形は採らない。`2>&1` で受けている呼ぶ側の出力が変わり、読み手が最後の行を結果と読み違える。終了コードだけを返す形も採らない。`summary` と `gaps` が届かず、運用・保守性の条件（止まった理由を結果 JSON だけで読める）を満たさない。

**核は本体を呼ぶ前に `NDF_RESULT_FILE` を自分の環境から外す。** 継ぐと、本体が起こした子のエントリポイントが親の結果ファイルを上書きする。

根拠: Value 2 / Value 6（MVV 版 4）

### 決定 3: 本体の中の `step_result.emit` を書き換えずに核へ結果を渡すため、核が動いている間の `emit` は `Emitted` を投げる

`emit` は、核が動いているときだけ標準出力へ書かずに `Emitted`（`SystemExit` の子クラス。結果と終了コードを持つ）を投げ、核が確かめてから出す。核が動いていないとき（テストが関数を直に呼ぶとき）は今と同じに出す。

契約の `stdout` が `step-result` の Python のエントリポイントは、結果を `step_result.emit` で出し、`SystemExit` で終わる。核がこの出力を確かめる（`ok` に欠けが無いか・契約に無い終了コードでないか）には、出す前に受け取る必要がある。

標準出力を受け取って最後の行を読み直す形は、Python のエントリポイントでは採らない。本体が流す途中の出力と結果の行の区別が、本体ごとの書き方に依存する。シェルのエントリポイントは子プロセスであるため、この形しか取れない（設計文書の「シェルのエントリポイント」）。

`Emitted` を `SystemExit` の子クラスにするのは、本体の `except Exception` が結果を握りつぶさないためである。

根拠: Value 6（MVV 版 4）

### 決定 4: 終了コードの意味を検査で確かめられるよう、終了コードの表に見出しを持たせ、契約の `exit` はその見出しで始め、エントリポイントは独自の `EXIT_` 定数を持たない

`step_result` に番号ごとの見出し（`EXIT_LABELS`）を持たせ、検査（`exit-meaning`）は 2 つを落とす。契約の `exit` の値が見出しで始まらない項目と、エントリポイントとその部品が `EXIT_` で始まる整数の定数を自分で持つことである。実行時には、核が契約の `exit` の鍵に無い終了コードを `stopped`・1 に変える（I3）。

`handoff.py` は 4 を「一致する本体が複数」、5 を「行数の上限を超える」の意味で返す（#2241）。表では 4 は「ベースブランチと衝突」、5 は表に無い。契約の `exit` は自由文のため、食い違いを機械で見つけられない。

意味ごとに新しい番号を表へ足す形は採らない。受け入れ条件 18 が表の意味を変えることを許さず、呼ぶ側の読み方（`code_matches`）を広げることになる。`handoff.py` の 2 つは、利用者へ聞く場面を承認ゲートの 10、上限を超える場面を違反の 1 へ寄せる。

根拠: Value 6 / Value 8（MVV 版 4）

### 決定 5: 核の対象外を印で決めて検査できるよう、契約の一覧の `core` に `hook` か `runtime` と根拠を書き、エントリポイント単位で外す

`hook` は根拠をファイルから確かめられる（hook の定義にパスが現れる・`callers` に `hook` の印を持つ項目がある）。そのため検査（`core-exempt`）が根拠の無い印を落とす。`runtime` は根拠をファイルから確かめられないため、印の数がベースブランチより増えたら落とし、増やす変更を承認ゲートで人が見る。

前提 4 の対象外は、hook の定義から起動されるものと、ランタイムが直接起動して標準出力をそのまま使うものである。今の 77 項目のうち 13 項目が当たる（設計文書の「核の対象外」）。

hook からも利用者からも呼ばれる 3 項目（`training-optout.py`・`statusline-switch.sh`・`relay.py`）は、副命令ごとには分けず、エントリポイント単位で外す。副命令ごとに外すと、`__main__` の 1 文の検査が副命令の分岐まで見ることになり、#2335 の決定 1（構文木で 1 文を確かめる）の範囲を超える。利用者向けの副命令の結果の形は柱 P7 がそろえる。

根拠: Value 4 / Value 6（MVV 版 4）

### 決定 6: 契約と例外リストを 1 か所で扱うため、検査の種類 `core-entry`・`core-exempt`・`exit-meaning`・`result-read` を `check-ndf-contracts.py` に足す

核の対象外の印・契約の `exit`・エントリポイントの一覧はどれも契約の一覧が持つ。同じ検査に足せば、読み込みと例外リストと増加の判定を共有できる。

要求の前提 2 は、`core-entry` を構造チェックの種類と書く。#2335 の構成要素の表は置き場を `check-script-structure.py` とした。柱 P0 は、契約の一覧の検査と例外リスト（`scripts/contract-allow/`）と増加の判定を `check-ndf-contracts.py` に置いた。

増加の判定（`contracts_lib/ratchet.py`）は、ベースブランチの検査（`check-ndf-contracts.py`）が知らない種類の行を数えないようにする。今はベースブランチに無い行をすべて増加として数える。新しい種類を入れる Pull Request は、その種類の行を初めて置く（#2335 の I11 の「ベースブランチにあった検査の種類について」）。

`check-script-structure.py` に置く形は採らない。契約の一覧の読み手と例外リストが 2 つの検査に分かれ、同じ役割の部品を 2 つ持つことになる。

根拠: Value 6（MVV 版 4）

### 決定 7: worker の成否を文の読み違いなく決めるため、worker は作業の結果ファイルを結果 JSON の形で書き、supervise はそのファイルだけを読む

worker は報告を終える前に `step_result.py emit --out <置き場>` でファイルを書く。CLI が形を確かめ、違えば終了コード 2 で拒むため、worker は形の違う結果を残せない。supervise は `step_read.read_result_file` で読み、`ok` のときだけ成功にする。外部 CLI を worker に使うステップも、`ndf:worker` のエージェントも、同じファイルを書く。

今は supervise が報告の文の「結果: 完了」を正規表現で照らす（`REPORT_DONE`・`REPORT_NOT_DONE`）。文の形はどこでも確かめられず、欠けを持つ置き場も無い。要求の子の課題の表は、#1682・#1699（残した作業があっても完了へ進む）を受け入れ条件 9 で解消しうると見込む。

報告の末尾に機械用のブロック（`<!-- ndf:... -->` の JSON）を置く形は採らない。応答の文から取り出す規則が要り、文を読む箇所が残る。#2335 の I15 は機械用のブロックを課題と PR の本文の値に使い、その検出の規則は柱 P7 が決める。worker の結果をそれに乗せると、P1 が P7 の規則を先に決めることになる。claude -p の構造化出力の機能に頼る形も採らない。外部 CLI（codex・agy・kiro）の worker には同じ機能が無く、ランタイムごとに読み方が分かれる。

人が読む「## 作業の報告」の節は残す。conductor と人が経緯を読む置き場であり、成否の判定には使わない。

根拠: Value 4 / Value 5（MVV 版 4）

### 決定 8: 課題を閉じる処理の後の棚卸しを止めずに人へ知らせるため、閉じなかった課題があれば `gate`・10 を返し、失敗があるときだけ `stopped`・1 を返す

閉じなかった理由は、条件 2（リリース後テストの行）や条件 3（振り返りの記録）を満たさないことで、処理の失敗ではない。満たすかどうかは工程を通すか人が確かめて手で閉じるかで決まり、人の判断が要る。プランの規則では 10〜19 は失敗にならず `next`（棚卸し）へ進み、フェーズの結果が承認ゲートになる。conductor と人は承認ゲートとして閉じなかった課題と理由を読む。`failed`（状態を読めない・閉じても CLOSED にならない）は処理の失敗のため、今と同じ `stopped`・1 で止める。

閉じなかった課題を `stopped`・6 にする形は採らない。プランが棚卸しの前で止まる。別のリポジトリの課題（#2327）のように工程を通しても満たせない課題があるたびに、まとめのプランが進まなくなる。プランの順を「振り返り → 課題を閉じる」から変える必要は無い。今のテンプレート（`supervise_lib/sprint_close_steps.py`）は既に振り返りの後に閉じる。

根拠: Value 2 / Value 7（MVV 版 4）

### 決定 9: 時間切れと SIGTERM を耐久のエントリポイントでも同じ形で扱うため、核は主スレッドで受けて結果を出し、耐久の記録を開いていれば DBOS を閉じずに抜ける

核は結果を出した後、`durable` が読まれて耐久の記録が開いているときだけ `durable.exit_leaving_pending` の出口を使う。

DBOS 3.1.0 の耐久ワークフローを動かしたまま、主スレッドで `signal.setitimer` の時間切れと SIGTERM を受けた（2026-11-02 の実測。設計文書の「あるべき姿の根拠」）。どちらも主スレッドの待ちが 0.3 秒以内に中断し、DBOS の内部のスレッドとの干渉は無かった。中断の後に DBOS を閉じる（`durable.close`）と、動いていたステップのスレッドが閉じたデータベースへ書こうとして例外の跡を 2 件出した。閉じずに `durable.exit_leaving_pending` で抜けると 0 件で、ワークフローは途中のまま残り、打ち直しで続く。

時間切れを別スレッドの監視で切る形は採らない。Python は主スレッド以外から主スレッドの処理を中断できず、本体の外から切れない。

根拠: Value 3（MVV 版 4）

### 決定 10: 柱 P4 の前に時間切れを確かめられるよう、核は時間切れの秒を環境変数 `NDF_RUN_TIMEOUT` から受け、子へ継がない

P1 の核は、呼ぶ側が `NDF_RUN_TIMEOUT` を渡したときだけ期限を置く。supervise の run のステップはステップの `timeout` をこの値で渡す。核は本体を呼ぶ前にこの値を外し、子のエントリポイントが親と同じ秒を自分の期限にしない。P4 は値の出所を上限の宣言へ移し、この環境変数を上書きの経路として残すかを決める。

受け入れ条件 1 は時間切れの終わり方を求めるが、上限の宣言（`contracts/limits.json`）は柱 P4 が作る。

P1 で上限の宣言を先に作る形は採らない。P4 の範囲（方針の名前・再試行の回数・同じ原因の上限）を P1 が部分的に決めることになる。

根拠: Value 6 / Value 10（MVV 版 4）

### 決定 11: 依存の欠けで止まるときも結果 JSON を返すため、`deps` の止まりは核の早い出口（`run_core.exit_early`）を通す

`deps` の止まりを `run_core.exit_early` に通す。書くのは `stopped`・69 と `gaps`（`kind` は `deps`、`name` はグループ）である。書き先は、契約の `stdout` が `step-result` なら標準出力、`NDF_RESULT_FILE` があればそのファイルである。核は標準ライブラリだけで書くため、extras が無い環境でも読める。

`deps.require` はモジュールの最上位で呼ばれ、`run_core.main` に届く前に止まる。今は標準エラーへ 1 行を出して 69 で終わり、結果 JSON を出さない。

`deps` に結果の組み立てを持たせる形は採らない。結果の出し方（標準出力か結果ファイルか）を決める規則が核と `deps` の 2 か所に分かれる。

根拠: Value 6（MVV 版 4）

### 決定 12: 結果の読み方を共通の読み手へ寄せたことを検査できるよう、最後の行を JSON として読む書き方を共通の読み手の外で禁じる

検査（`result-read`）は、`lib/step_read.py` の外で、名前に `last_json` を含む関数の定義と、`json.loads(<式>.splitlines()[-1])` の形を落とす。今の箇所は例外リストに置き、移す Pull Request が `step_read.read_completed` へ置き換えて行を消す。

ほかのエントリポイントの結果 JSON を読む箇所は、子プロセスの標準出力の最後の行を `json.loads` で読む。該当するのは `supervise_lib/steps.py` の `last_json`・`release-steps.py`・`lib/sprint_loop_record.py` である。GitHub の CLI の出力を読む箇所は、出力の全体を読む。

呼び出し先のパスから NDF のエントリポイントを呼ぶ箇所を見分ける形は採らない。パスは `paths` の定数・`HERE /` の式・文字列の組み立てで作られ、構文木から決まらない箇所が残る。

根拠: Value 6（MVV 版 4）
