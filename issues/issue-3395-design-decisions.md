# #3395 の決定の記録: 設計レビューの全項目の行き先と範囲の決定

設計文書 [issue-3395-design.md](issue-3395-design.md) の決定の記録である。決定番号は #1142 の作り直しの系統の最大（108）の次から取った（#3347 の決定 102）。

## 決定の記録

### 決定 109: 子の着手を表の上で再開するため、全 182 項目を 1 つの表へ割り当て、表に無い項目を検査で落とす

表は #1142 の設計文書の置き場（[issue-1142-design-review-routing.md](issue-1142-design-review-routing.md)）に置き、`children.json` の `review_items` をこの表と本文から生成し、規則 `review-items` で突き合わせる。表だけでは、項目を足した設計レビューの後に割り当て漏れが再び生まれる。コピーは手で写さず生成し、規則が生成し直した結果との一致も確かめる。手で写すと正本とコピーがずれても検出できない（Value 8・Value 11）。

項目を分類ごとの Issue の本文に残し、子の本文から指す形は採らない。項目と子の対応が 2 か所に分かれ、どちらが正か決まらない。

根拠: Value 3 / Value 11（MVV 版 7）

### 決定 110: 閉じた子の範囲を閉じたまま追えるよう、閉じた子への作業は追補の単位にする

追補の単位は元の子の記号に `+` を付ける（X0+・D1+・D2+・T1+・AD1+・AD2+・AD3+。X1+・C1+ は既にある）。Issue は元の子の番号を閉じたまま使い、受け入れ条件は元の子の本文の「追補（<記号>）」の節に置き、PR は `Refs #<元の子> #<出所>` と書く。C1+ と X1+ の前例と同じ形である。

閉じた子を開き直す形は採らない。閉じた PR と受け入れ条件の済みの記録が混ざり、何が残りかが読めなくなる。動いている C1+ には足さず、C1 の範囲の新しい項目は C2 へ送る（利用者の決定「動いている作業は流し切る」）。

根拠: Value 14（MVV 版 7）

### 決定 111: 1 本の PR に収まる大きさに揃えるため、受け入れ条件が 25 行を超える子を分ける

基準の値は、1 本の PR に収まらないと判断して分けた P1（38 行）と、分けた後の P1a（19 行）の間に置いた。行き先の表を足すと M3 は 28 行、S1 は 27 行になり、基準を超える。M3 は中継（M3b、順番 4）と hook（M3a、順番 5。hook が中継の印の関数を同じプロセスで呼ぶため後）に、S1 は Skill 本文（S1a）・エントリポイントと Codex（S1b）・文書（S1c）に分ける。分けた後は M3a 25 行・M3b 8 行・S1a 10 行・S1b 15 行・S1c 9 行である（共通の 4 行は分けた子のそれぞれに持たせて数えた。S1 の「行き先の無い機能の一覧」は X3 へ移す）。

基準を検査で縛ることは採らない。受け入れ条件は Issue の本文にあり、数え方（追補の節・取り消し線）を検査へ持ち込むと規則の方が大きくなる。設計 PR のレビューで見る。

根拠: Value 5 / Value 9（MVV 版 7）

### 決定 112: 持ち主の無い機能に席を作るため、X3・M8・T2・S3 を新設する

X3 は今の機能と行き先の子の対応表と、作り直しの間に `plugins/ndf` へ入る直しの棚卸し（#3342・#3343）。M8 は worktree のコンテキスト（3342-2）。T2 は入れ替えの前の試走（3342-6）。S3 は入れ替えの後の確定仕様化と測り直し（3381-2・3395-1）。

既存の子へ足す形は採らない。対応表は順番 2 で要り、S1（順番 8）に置くと後続の子が対応表なしで進む。worktree は M1〜M7 のどのコンテキストにも属さない。

### 決定 113: 範囲を 1 回で決められるよう、要求の行が無い 34 件と 7 点に推奨を付け、行き先の表をその推奨で書く

推奨の基準は 3 つである。人を守る（秘密・公開範囲・信頼境界）は広げる。入れ替え（S2）の CI か確定仕様化が通らなくなるものは広げる。作り直しの構造と独立し、既に #3388 へ回した主題と同じものは 11.x へ回す。この基準で 23 件を広げ、11 件を 11.x へ回した。

推奨を付けずに並べる形は採らない。判断の材料が利用者に偏り、承認の場で同じ検討を繰り返す。

根拠: 上位の原則（人を守る）/ Value 1 / Value 5（MVV 版 7）

### 決定 114: 入れ替えの前後を同じ物差しで比べるため、行き先を選んだ主体を選択の記録で数え、M7 が今の形と新しい形の両方を読む

選択の記録の契約は D1+、書き手は C2 と P1b、測るスクリプトは M7 が持つ。今の形の読み手は `plugins/ndf/scripts/lib` の import をやめ、`scripts/measure/` へ移す。

コマンドの文字の規則を新しいコマンド名へ書き足す形は採らない。名前が変わるたびに規則を直すことになり、主体（スクリプトか conductor か）を区別できない。

根拠: Value 13（MVV 版 7）

### 決定 115: 要求と実装の食い違いを実装の決定に沿って解くため、行数の上限と Python の下限は要求を書き換え、種類 6 は実装へ足す

行数は #2991（ファイルを分ける基準を行数から責務へ。X1 が取り込んで閉じた）で 1,000 に決めた。Python 3.10 は 2026-10-01 に保守を終えた（STD1）。種類 6 は要求の 324 行がそのまま求めており、実装の欠けである。

Python の下限を 3.10 へ戻すことは採らない。保守の終わった版のために、filelock の脆弱性の 14 件（#3380）を抱えることになる。

### 決定 117: 解消する Issue を改善を確かめてから閉じるため、閉じる証拠を 3 種類に決め、M6 の副命令が確かめて閉じる

子の PR の closing keywords で閉じる形は採らない。テストが無いまま閉じても止める手段が無い。M6 は Issue の一覧を GitHub のアダプター（AD1）で読む棚卸しの子で、閉じる操作も同じ境界に置ける。

### 決定 118: 依存の更新を自前で保たないため、Dependabot を使い、X2 を依存の版の一度の引き上げに縮める（推奨。結論は設計承認ゲートで利用者が決める）

この決定は推奨である（#3395 の前提 6）。利用者が別の結論を選んだときに書き直す行は、[issue-3395-design-scope.md](issue-3395-design-scope.md) の「依存の更新の比較」の「結論ごとに書き直す行」にある。推奨の理由の一部は未確認の挙動（Dependabot の `uv.lock` の推移的な依存の扱い）に依り、同じ節の「推奨が依る未確認の挙動」に並べた。

Dependabot は uv・公開から待つ設定・脆弱性の PR を持ち、このリポジトリで既に動いている（PRD2）。X2 は 13 本の一度の引き上げと、固定の理由を Dependabot の `ignore` へ移すことだけを持ち、`scripts/plugin-deps.py` と週 1 回のジョブは作らない。Dependabot の `plugins/ndf-next` の項目と security updates の有効化は X2 の PR で行う。

Renovate は採らない。lock ごとの作り直しは優れるが、GitHub App にリポジトリへの書き込みの権限を渡すか、セルフホストを保つ必要がある（PRD1）。X2 のまま作る形も採らない。脆弱性と推移的な依存を見ないまま、保つスクリプトが増える。結論までは X2 に着手しない（利用者の決定）。

- 作り方: ライブラリやサービスを使う
- 比べた候補: PRD1・PRD2

根拠: Value 2 / Value 12（MVV 版 7）

### 決定 119: 同じ概念を 2 つ持たないため、lock にある tenacity と filelock で自作を置き換え、使わない依存 11 本は 3 本を消して 8 本に使う子を決める
