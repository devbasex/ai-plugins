# #3613: ndf-next の用語: 直訳調の内部の呼び名（版・置き場・宣言・副命令・進行表など約 1.3 万回）を業界の語へ置き換え、1 語 1 意味にそろえる

正は課題の本文（#3613）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 目的

ndf-next（`plugins/ndf-next/`。11.0 で今の `plugins/ndf/` と入れ替わる作り直しの NDF）の利用者が読む文書と出力を、説明なしで分かる日本のエンジニア業界の語で書き、1 語 1 意味にそろえる。

- 利用者の指摘（2026-11-15）は「土台・印・版などの語が直訳すぎて分からない」だった
- ndf-next では直訳調の内部の呼び名が 51 語・約 1.3 万回出る（下の「調べた結果」）。11.0 の公開の後に直すと、利用者の設定・手順・記録へ旧い語が広がり、直す費用が増える
- 判断の根拠は MVV の Value 14（語は業界に流通している語で 1 語 1 意味にそろう）と Value 1（承認の材料が一度で読み切れる）

## 決まったこと（2026-11-16 03:0x JST、利用者の差し戻し）

設計 PR #3620 の設計承認ゲートで、利用者が問い「`promotion`・`vet` は本来どんなキー名であるべきか」への答えとして「案の名前で改名して出し直す」と書いた。次は、開発ループ（p6-lterms）がその答えを差し戻しの指摘として記録した内容である。利用者の設定ファイル（`.ndf/`）のキーも 11.0 で改名する。11.0 は互換を切る版（#1142「後方互換を意識しない」）で、後から改名するほど利用者が増えて費用が増えるため。

| 今 | 新しい名前 | 理由 |
| --- | --- | --- |
| `.ndf/worktree.json` の `branch_flow.promotion` | `branch_flow.release_strategy` | 英語の promotion は CD で「ビルドを環境間で進める」意味。ここで決めているのはブランチのリリースのやり方（release strategy・branching model） |
| 値 `whole` | `merge_base_branch` | ベースブランチ（develop など）を丸ごと main へマージする |
| 値 `selected` | `release_branch` | 承認したスプリントだけを、本番ブランチから作ったリリースブランチで出す |
| （新しく足す GitHub flow の値。#3572 の設計では `direct`） | `trunk` | スプリントの PR を直接 main へ入れる。#3572 の設計と名前をそろえる |
| `.ndf/mvv.json` の `versions[].vet` | `versions[].validation` | MVV の各版を承認するときの、言語モデルによる確かめの記録。`vet` は欄の名前から何の結果かが読めない |
| `vet.verdict`（`follow` / `unknown`） | `validation.result`（`pass` / `unknown`） | |
| `vet.at` | `validation.checked_at` | |
| `vet.accepted_unknown` | `validation.accepted_unknown`（そのまま） | |

- 取り込み方の表（`plugins/ndf-next/contracts/domains/branch-flows.json`）の行の id と列 `promotion` も、新しい名前にそろえる
- 入れ替え（#3304）の手順に、利用者の設定を新しいキーへ書き換える移行のコマンド（例: `ndf settings migrate`）を足す。書き換える前に差分を示し、リポジトリごとに利用者の承認を取る（C7）
- `vet` は NDF が書く記録なので、移行のコマンドが同じく書き換える
- 移行の後に旧いキーが残る設定は、読むときに旧いキーの名前と新しい名前を出して止める（既定の値へ倒さない）
- 「耐久」の置き換え先は、業界の「Durable Execution」「durable workflow」と、永続化（persistence）との紛れを比べて決め直す（指摘の推奨は「Durable ワークフロー」か「Durable Execution」）

## 前提

- 前提 1: 置き換えは 11.0 の公開（ndf-next と今の NDF の入れ替え）より前に、ndf-next の中で終える
- 前提 2: 漢字と結び付いて定着した複合語（正式版・開発版・実験版・安定版・リリース済み版）は置き換えない。業界で使われており、`AGENTS.md` と用語集が定義している。置き換えるのは単独で使う「版」（「MVV の版」「版の記録」など）である
- 前提 3: 用語集はリポジトリに 1 つ（`docs/glossary/glossary.json`。設定は `.ndf/glossary.json`）で、今の NDF と ndf-next が共有する。旧い語を廃止した語へ登録すると、今の NDF の側でも追加した行の検査（`glossary.py check --diff`）が旧い語を落とす。11.0 で今の NDF は入れ替わるため、これを受け入れる
- 前提 4: 1 文字の語（版・鍵・枠・印）は、用語集の「単独で照合する廃止した語」（`deprecated_standalone`。前後が漢字の出現に当てない）で登録する。2 文字以上の語は「廃止した語」（`deprecated`）で登録する
- 前提 6: 改名する利用者の設定のキーは、2026-11-16 03:0x の決定の表に載ったものに限る。`.ndf/mvv.json` の `revise_after` など、表に無いキーは改名しない
- 前提 7: 11.0 の入れ替えまでは、今の NDF が旧いキーを読み書きする（受け入れ条件 10 で今の NDF は変えない）。ndf-next は新しいキーだけを読む。利用者のリポジトリの `.ndf/` を書き換えるのは入れ替えの時点で、この課題では書き換えない
- 前提 8: GitHub flow の値の行は #3572 が取り込み方の表へ足す。この課題は値の名前を `trunk` に決め、#3572 の設計へ伝える。この課題のマージの時点で #3572 の `direct` の行が表にあれば、この課題で `trunk` へ改名する
- 前提 5: 同等性の表（`plugins/ndf-next/src/ndf/parity/`）のうち、今の NDF の文言をそのまま引いた箇所は、引用として旧い語を残してよい。残す箇所は禁止語の検査の例外（`rules.json` の `words.examples`）にファイル・語・理由を書いて外す

- ndf-next の利用者向けの面: Skill の本文と references・エージェント定義・`docs/`・契約の JSON の説明（`meaning` など）と、そこから生成される契約の文書（`docs/contracts/`）・副命令の出力の文言

- 利用者の設定を新しいキーへ書き換える移行のコマンドと、旧いキーが残る設定を読んで止める検査
- 入れ替え（#3304）の手順への、移行のコマンドを実行するステップの追記
- ndf-next の禁止語の検査が「単独で照合する廃止した語」を読むようにすること（前提 4。今は `deprecated` だけを読む。`plugins/ndf-next/src/ndf/checks/words.py` の `_words_from`）

| データ | 用語集（`docs/glossary/glossary.json`）の語・意味・廃止した語が変わる。用語集の文書（`docs/glossary.md`）を作り直す |
| 既存の振る舞い | 今の NDF の用語集の検査が、追加した行の旧い語を落とすようになる（前提 3） |
