## 事象

並列の計画 p6 のリリース 14（ndf v10.27.68）で、利用者がリリース承認ゲートで develop の 6fb221da を承認した（2026-11-15 14:49 JST）後に、一時レーン p6-rel14 の本番のプランの直しを受け持つ worker が、NDF のコード修正 5538d759「Fix(release): 使い回す -sync の PR の本文に ndf-next の port 検査の印を足す」をリリースブランチ `release/v10.27.68` へ積んだ。この修正は承認したコミットに含まれず、レビューも受けていない。修正で `plugins/ndf/scripts/release-steps.py` が 1411 行になり、行数の検査（上限 1409 行）が落ち、本番の PR https://github.com/devbasex/ai-plugins/pull/3570 をマージできなくなった。p6-rel14 が止まって問い直し、利用者の答えで修正を外して出すことにした。

リリース 8（2026-11-14 12:1x JST）でも、承認の後に修正の worker が 168affe0 を本番の PR へ積み、承認を取り直した。同じ形の 2 回目である。

## 期待する結果

リリース承認ゲートの承認の後、リリースブランチと本番の PR へ新しいコミットを積めない。CI が落ちたときの直しは、ベースブランチ（develop）宛ての PR で入れ、ベースブランチから組み直したリリースブランチで承認を取り直す。

## 再現手順

1. 並列の計画のまとめたリリースで、リリース承認ゲートの承認を送る（`parallel.py confirm`）
2. 一時レーンの本番のプランで、本番の PR かリリースブランチの CI が落ちる
3. プランの直しのステップ（fix の worker）が、落ちたチェックを直すためにコードを変えてリリースブランチへ push する

## 環境

NDF 10.27.66〜10.27.67（一時レーン p6-rel14）、Claude Code、Linux。2026-11-15。直す先の ndf-next は、このリポジトリの develop の ddaf18781 の時点のコードを読んだ。

## 前提

- 前提 1: ndf-next では、承認の対象は既にリリースの PR の先端（組み立てたリリースブランチの先端）である。確かめた根拠:
  - 組み立て（`release-steps assemble`。`plugins/ndf-next/src/ndf/domains/release/assemble.py`）が版上げ・CHANGELOG・宣言の手順のコミットを積んだリリースブランチと PR を作り、その後に承認資料を提示する
  - 判定（`approval_decide.judge`）は PR の今の先端への最新の答えだけを承認と読み、先端が動いた後の答えは `stale` になる（テスト `tests/domains/release/test_release_approval.py::test_judge_reports_stale_and_missing`）
  - マージ（`land.py` の `_refusal`）は、承認されていない先端と、待ちの間に動いた先端をマージしない
  - よって利用者の案の 1 つ目（組んでから承認する）は ndf-next では成り立っている。この課題で足すのは、承認の後に積むこと自体を止める仕組みと、直した後に組み直す経路である
- 前提 2: worker がリリースブランチへ積む原因（直しのステップの指示）は設計で特定する。受け入れ条件は原因によらず、GitHub の側で積めないことを求める（同じ形が 2 回起き、手順書の決まりだけでは止まらなかったため）
- 前提 3: 承認の後にリリースの工程がリリースブランチへ積むコミットは無い。ndf-next の組み立ては、版上げ・CHANGELOG・宣言の手順（トークン消費の記録など）を承認の前に 1 つのコミットにして積む（`assemble.py` の手順 3・4）。承認の後に積む種類が要ると設計で分かったら、その種類と積む主体を設計に書く
- 前提 4: ロックの付け外しは、リポジトリの管理の権限を持つ token（workflow の `secrets.NDF_RELEASE_TOKEN`）で行う。2026-11-15 にこのリポジトリの ruleset の一覧を読んだ結果、`protect develop`（id 26777950）と `protect main`（id 22332172）の 2 つだけがあり、`release/` で始まるブランチを対象にした規則は無い。利用者の token は管理の権限（`admin: true`）を持つ
- 前提 5: 対象のリポジトリは GitHub であり、リリースブランチの名前は `release/v<版>` で始まる（`version_decide.BRANCH_PREFIX`）

## 対象範囲

含む:
- ndf-next のリリース（`plugins/ndf-next/src/ndf/domains/release/`）で、リリース承認ゲートの承認の証跡を書いた時点に、そのリリースブランチを GitHub の側で書き込めなくする
- マージか差し戻しの後に、ロックを外し、リリースブランチを消す
- 差し戻しの後に、ベースブランチの先端から新しいリリースブランチを組み直し、承認を取り直す経路
- ndf-next のリリースの workflow（`.github/workflows/ndf-next-release.yml`）と雛形（`plugins/ndf-next/contracts/templates/`）のうち、上の 3 つに要る変更
- 設計承認の資料に載せる、ロックの手段を実物で確かめた結果と、承認の対象についての得失

含まない:
- 今の NDF（`plugins/ndf/`）の変更。11.0.0 の入れ替えまでは、今の NDF はマージの時点の先端の照合と CI で受ける
- 開発版チャネルのリリース（承認ゲートを通らずにマージされるため、承認の後という時点が無い）
- 本番ブランチ（`main`）とベースブランチ（`develop`）の ruleset の変更
- 直しのステップの worker の指示を書き換えるだけの対処（手順書だけでは 2 回とも止まらなかった）
- 時間で区切った負荷試験

## 受け入れ条件

設計の成果物への条件:

- [ ] 1. 設計承認の資料に、ロックの手段を実物で確かめた結果が載っている。結果は次の 4 点を含む: 使った API と要る権限、付けてから効くまでと外すまでの所要、ロックしたブランチへの push の拒まれ方（終了コードと出力）、ロックしたブランチを head にした PR を本番ブランチへマージできるか
- [ ] 2. 設計承認の資料に、承認の対象（ndf-next では組み立てたリリースブランチの先端。前提 1）についての得失が載っている

実装への条件:

- [ ] 3. 前提: 本番の PR の先端が承認された（証跡の判定が `approved`）
      操作: リリースブランチへ新しいコミットを push する
      結果: GitHub が push を断り、リリースブランチの先端は承認したコミットのまま変わらない
- [ ] 4. 承認の証跡を書いてからロックするまでの間に積まれたコミットがあれば、本番の PR はマージされず、止まった理由に先端が動いたことが出る（退行しない。前提の確認: `test_release_approval.py::test_judge_reports_stale_and_missing` と `land.py` の `_refusal`）
- [ ] 5. ロックに失敗した（権限が無い・API がエラーを返した）とき、本番の PR をマージせずに止まり、結果に失敗の理由が出る
- [ ] 6. ロックしたリリースブランチを head にした本番の PR は、承認と必須のチェックの後に今と同じ経路（迂回のマージを含む）でマージされる
- [ ] 7. 本番の PR をマージした後に、ロックが外れ、リリースブランチが消える。外せない・消せないときは、残ったブランチと理由が結果に出る
- [ ] 8. 差し戻しか、CI の落ちた本番の PR を閉じた後に、ロックが外れ、リリースブランチが消える
- [ ] 9. 前提: 差し戻した後、直しの PR がベースブランチへ入った
      操作: 本番チャネルの組み立てを起動する
      結果: ベースブランチの先端から新しいリリースブランチと本番の PR が作られ、承認資料の提示と承認がその PR の先端に対して改めて要る
- [ ] 10. ロックはリリースブランチ 1 本ごとに効き、ほかのブランチ（ベースブランチ・本番ブランチ・ほかのリリースブランチ・作業のブランチ）への push を断らない
- [ ] 11. 開発版チャネルの組み立てとマージは、ロックを付けずに今と同じく進む（退行しない）
