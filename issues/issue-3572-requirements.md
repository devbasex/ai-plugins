## 事象

並列の計画 p6 のリリース 14（ndf v10.27.68）で、利用者がリリース承認ゲートで develop の 6fb221da を承認した（2026-11-15 14:49 JST）後に、一時レーン p6-rel14 の本番のプランの直しを受け持つ worker が、NDF のコード修正 5538d759「Fix(release): 使い回す -sync の PR の本文に ndf-next の port 検査の印を足す」をリリースブランチ `release/v10.27.68` へ積んだ。この修正は承認したコミットに含まれず、レビューも受けていない。修正で `plugins/ndf/scripts/release-steps.py` が 1411 行になり、行数の検査（上限 1409 行）が落ち、本番の PR https://github.com/devbasex/ai-plugins/pull/3570 をマージできなくなった。p6-rel14 が止まって問い直し、利用者の答えで修正を外して出すことにした。

リリース 8（2026-11-14 12:1x JST）でも、承認の後に修正の worker が 168affe0 を本番の PR へ積み、承認を取り直した。同じ形の 2 回目である。

## 期待する結果

リリース承認ゲートの承認の後、リリースブランチと本番の PR へ新しいコミットを積めない。CI が落ちたときの直しは、ベースブランチ（develop）宛ての PR で入れ、ベースブランチから組み直したリリースブランチで承認を取り直す。

## 再現手順

1. 並列の計画のまとめたリリースで、リリース承認ゲートの承認を送る（`parallel.py confirm`）
2. 一時レーンの本番のプランで、本番の PR かリリースブランチの CI が落ちる
3. プランの直しのステップ（fix の worker）が、落ちたチェックを直すためにコードを変えてリリースブランチへ push する

## 前提

この節から「未決」までは、末尾の 3 節（「範囲の決定」「ロックの方針」「承認とマージの扱い」、いずれも利用者）に合わせて 2026-11-15 に書き直した。上の「期待する結果」と、「依頼（原文）」に引いた起票時の案（ruleset のロック・`-r2` の組み直し）は起票時の記録として残す。食い違うところは末尾の 3 節を正とする。

- 前提 1: ndf-next では、承認の対象は既にリリースの PR の先端（組み立てたリリースブランチの先端）である。確かめた根拠:
  - 組み立て（`release-steps assemble`。`plugins/ndf-next/src/ndf/domains/release/assemble.py`）が版上げ・CHANGELOG・宣言の手順のコミットを積んだリリースブランチと PR を作り、その後に承認資料を提示する
  - 判定（`approval_decide.judge`）は PR の今の先端への最新の答えだけを承認と読み、先端が動いた後の答えは `stale` になる（テスト `tests/domains/release/test_release_approval.py::test_judge_reports_stale_and_missing`）
  - マージ（`land.py` の `_refusal`）は、承認されていない先端と、待ちの間に動いた先端をマージしない。マージそのものも先端の照合（`merge` / `merge_as_admin` の `expect_head=pull.head_sha`。GitHub の `--match-head-commit`）を付けて打つ
- 前提 2: 承認からマージまでの間にコミットが積まれる経路は、承認の後に流れるプランに「CI が落ちたらコードを直して push する」ステップがあることである。ndf-next の雛形では、`merge.json` の `ci` が `test_failed` / `check_failed` で `repeat-check` → `ci-fix`（`{{worker}} ci-fix`）→ `ci-local` → `push` へ進む（`plugins/ndf-next/contracts/templates/merge.json`・`parts/steps.json`）。本番の PR をこの形のプランで流すと、承認の外のコミットが積まれる（リリース 8・14 と同じ形）。どのプランが本番の PR を流すか（`release.json` の `{{worker}} release` の中身を含む）は設計で特定する
- 前提 3: 承認の後にリリースの工程がリリースブランチへ積むコミットは無い。ndf-next の組み立ては、版上げ・CHANGELOG・宣言の手順（トークン消費の記録など）を承認の前に 1 つのコミットにして積む（`assemble.py` の手順 3・4）。承認の後に積む種類が要ると設計で分かったら、その種類と積む主体を設計に書く
- 前提 4: GitHub の ruleset でのロックは作らない（「ロックの方針」）。承認した先端の外のものは、前提 1 の先端の照合で止める
- 前提 5: 承認の経路は 2 つある（「承認とマージの扱い」）。(a) リリース承認ゲートで承認し、その直後に工程が本番の PR をマージする。(b) 利用者が GitHub で本番の PR をマージする。どちらもリリース承認かつマージ承認とみなし、どちらも承認した先端の後に積まれたコミットを越えない。(b) の土台として、`land.py` の `land` は PR がマージ済みなら `_resume_merged` へ進み、ベースブランチへの同期を行う。ただし迂回の記録は利用者の証跡がマージした先端への承認のときだけ補い、人のマージそのものを承認として記録する経路は無い
- 前提 6: ブランチの流れは #3119 の構想に合わせる（「範囲の決定」）。リリースブランチもスプリントブランチも本番ブランチ（`main`）から起こし、リリースブランチは前の版が出た直後に用意する。スプリントはリリースブランチへマージし、リリースブランチから develop と main へ入れる。develop は検証だけに使う。#3119 の設計（`issues/issue-3119-design.md`・`issues/issue-3119-design-detail.md`・`issues/issue-3119-requirements.md`、設計 PR #3281）はこの構想と異なるため、差分をこの課題の設計で書く
- 前提 7: 対象のリポジトリは GitHub であり、リリースブランチの名前は `release/v<版>` で始まる（`version_decide.BRANCH_PREFIX`）

## 対象範囲

含む:
- 承認の後に流れる本番のプランから、コードを変えてリリースブランチ・本番の PR へ push するステップ（fix の worker）を外す。CI が落ちたら止まり、差し戻しか次の版への回しにする
- 承認ゲートでの承認の直後のステップを、承認した先端との照合付きの本番の PR のマージにする（経路 (a)）
- 人が GitHub で本番の PR をマージしたことを検知し、承認済みとして後の工程（開発版との同期・後片付け・終わりの記録）へ進む経路（経路 (b)）
- 差し戻しの後、直しを入れたリリースブランチの先端で承認を取り直す経路。承認の後に見つかった直しを、次の版のリリースブランチへスプリントとして入れる経路
- #3119 の設計を、前提 6 の構想に合わせて直す差分（同じ設計 PR に載せる）。#3121 の宣言 `branch_flow` の値が構想に要るかの判断を含む
- 実装の範囲は ndf-next（`plugins/ndf-next/`）の中。主にリリースのドメイン `plugins/ndf-next/src/ndf/domains/release/` と雛形 `plugins/ndf-next/contracts/templates/` で、副命令を変える同じ変更で合わせる承認ゲートの待ち（`plugins/ndf-next/src/ndf/progress/gate/release.py`）と副命令の契約のスキーマ（`plugins/ndf-next/contracts/schemas/io/release-steps.*.schema.json`）を含む（設計の決定 4）

含まない:
- 今の NDF（`plugins/ndf/`）の変更。11.0.0 の入れ替えまでは、今の NDF はマージの時点の先端の照合と CI で受ける
- GitHub の ruleset（Lock branch を含む）によるリリースブランチのロック
- 臨時の組み直しのブランチ（`release/v<版>-r2` など）
- 開発版チャネルのリリース（承認ゲートを通らずにマージされるため、承認の後という時点が無い）
- 本番ブランチ（`main`）とベースブランチ（`develop`）の ruleset の変更
- 直しのステップの worker の指示を書き換えるだけの対処（手順書だけでは 2 回とも止まらなかった）
- 時間で区切った負荷試験

## 用語

| 用語 | 意味 |
| --- | --- |
| リリースブランチ | 版ごとに 1 本、前の版が出た直後に本番ブランチから用意する `release/v<版>` のブランチ。スプリントが溜まり、本番の PR の head になる |
| スプリントブランチ | 本番ブランチから起こし、リリースブランチへマージするブランチ |
| 本番の PR | リリースブランチから本番ブランチ（`main`）宛ての PR |
| 承認した先端 | 承認ゲートの承認の答え（経路 (a)）か、人のマージ（経路 (b)）が対象にしたリリースブランチの先端のコミット |
| 先端の照合 | マージの API に、承認した先端のコミットを渡して、先端が違えば GitHub に断らせること（`expect_head` / `--match-head-commit`）と、マージの前の証跡の読み直し（`land.py` の `_refusal`） |
| fix の worker | CI が落ちたときにコードを直して push するステップ（雛形の `ci-fix` とそれに続く `push`） |
| 差し戻し | 承認ゲートで承認しない答え、または CI の落ちた本番の PR を出さないと決めること。直しを入れた先端で承認を取り直すか、直しを次の版へ回す |

## 受け入れ条件

設計の成果物への条件:

- [ ] 1. 同じ設計 PR に、#3119 の設計（`issues/issue-3119-design.md`・`issues/issue-3119-design-detail.md`）を前提 6 の構想（本番ブランチから起こすリリースブランチとスプリントブランチ、前の版が出た直後のリリースブランチの用意、スプリント → リリースブランチ → develop・main、develop は検証だけ）に合わせて直す差分が載っている。差分には #3121 の宣言 `branch_flow` の値が構想に要るか（要るなら値）の判断が書かれている
- [ ] 2. 設計に、ndf-next で本番の PR を流すプランと、そのプランが承認の後に通るステップの一覧が書かれている（前提 2 の特定）

実装への条件:

- [ ] 3. 前提: 本番の PR の先端 A が承認ゲートで承認された（証跡の判定が `approved`）
      操作: 承認の後に流れる本番のプランを、生成した plan の JSON で読む
      結果: どのステップにも、コードを変えてリリースブランチか本番の PR の head へ push するもの（`ci-fix`・それに続く `push`・`fix-push` などの fix の worker）が無い。雛形のテストが、この形の plan を落とす
- [ ] 4. 前提: 承認の後に流れる本番のプランで、本番の PR の必須のチェックが落ちた
      操作: プランを進める
      結果: コードを直さずに止まり、リリースブランチの先端は A のまま変わらない。結果に、落ちたチェックと、次の手（差し戻して直しを入れた先端で承認を取り直す・次の版のリリースブランチへ回す）が出る
- [ ] 5. 前提: 承認ゲートで先端 A を承認した
      操作: 承認を受けたプランを流す
      結果: 承認の答えを受けた直後のステップが本番の PR のマージであり、間に別のステップ（CI の直し・待ちの後の再組み立てなど）を挟まない。マージは A との照合（`expect_head=A`）付きで打たれる
- [ ] 6. 前提: 先端 A の承認の後、マージの前にリリースブランチへコミット B が積まれた
      操作: マージのステップを流す
      結果: 本番の PR はマージされず、止まった理由に先端が A から B へ動いたことが出る（退行しない。`test_release_approval.py::test_judge_reports_stale_and_missing` と `land.py` の `_refusal`）
- [ ] 7. 前提: 本番の PR が承認ゲートで答え待ちのまま、利用者が GitHub で本番の PR を先端 A でマージした
      操作: マージを検知した工程（workflow か再開）を流す
      結果: 承認ゲートを問い直さず、承認済みとして開発版との同期・後片付け・終わりの記録へ進む。記録に、承認した人（マージした利用者のログイン）とマージしたコミット（A とマージコミット）が残る
- [ ] 8. 前提: 承認ゲートで先端 A を承認した後にコミット B が積まれ、利用者が GitHub で B の先端をマージした
      操作: マージを検知した工程を流す
      結果: 人のマージを B への承認として記録する（経路 (b) の承認は A への承認を引き継がない）。記録に、承認ゲートの承認が A に対するもので、マージした先端が B であることが両方残る
- [ ] 9. 前提: 差し戻した後、直しのスプリントがリリースブランチへ入り、先端が C になった
      操作: 承認資料を提示する
      結果: 資料の対象が C であり、C への承認が新しく要る。A への承認は `stale` として扱われ、C のマージに使われない。新しいリリースブランチ（`-r2` など）は作られない
- [ ] 10. 前提: 本番のマージ（経路 (a) か (b)）が済んだ
       操作: 後の工程を流す
       結果: 次の版のリリースブランチが本番ブランチのマージ後の先端から用意され、結果にその名前が出る
- [ ] 11. 開発版チャネルの組み立てとマージは、今と同じく進む（退行しない）
- [ ] 12. 変更は ndf-next（`plugins/ndf-next/`）の中だけにあり、`plugins/ndf/` の差分が無い
