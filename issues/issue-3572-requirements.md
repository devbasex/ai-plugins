## 事象

並列の計画 p6 のリリース 14（ndf v10.27.68）で、利用者がリリース承認ゲートで develop の 6fb221da を承認した（2026-11-15 14:49 JST）後に、一時レーン p6-rel14 のリリースのワークフローの修正を受け持つ worker が、NDF のコード修正 5538d759「Fix(release): 使い回す -sync の PR の本文に ndf-next の port 検査の印を足す」をリリースブランチ `release/v10.27.68` へ積んだ。この修正は承認済みのコミットに含まれず、レビューも受けていない。修正で `plugins/ndf/scripts/release-steps.py` が 1411 行になり、行数の検査（上限 1409 行）が落ち、本番の PR https://github.com/devbasex/ai-plugins/pull/3570 をマージできなくなった。p6-rel14 が止まって質問し直し、利用者の回答で修正を外して出すことにした。

リリース 8（2026-11-14 12:1x JST）でも、承認の後に修正用の worker が 168affe0 を本番の PR へ積み、承認を取り直した。同じ形の 2 回目である。

## 期待する結果

承認ゲートで承認したコミットより後に、本番の PR へ新しいコミットを積めない。CI が落ちたときの直しは承認の前の PR で入れ、直した head で承認を取り直す。

ブランチ戦略はリポジトリごとに設定ファイルで選ぶ。develop と main を分ける Web・アプリのリポジトリは既存のブランチ戦略（`promote-whole`・`promote-selected`）のまま動き、ai-plugins は `github-flow` 戦略を選ぶ。検証環境・バージョンアップの対象・マージの方式も、同じく設定ファイルで選ぶ。ほぼ同時に承認された複数のスプリントの PR は、組み合わせが必須のチェックを通ってから main へ入る。

## 再現手順

1. 並列の計画のまとめたリリースで、リリース承認ゲートの承認を送る（`parallel.py confirm`）
2. 一時レーンのリリースのワークフローで、本番の PR かリリースブランチの CI が落ちる
3. ワークフローの修正ステップ（fix の worker）が、落ちたチェックを直すためにコードを変えてリリースブランチへ push する

- 前提 1: ndf-next では、承認の対象は既に PR の head である。確かめた根拠:
  - 判定（`approval_decide.judge`）は PR の今の head への最新の回答だけを承認と読み、head が動いた後の回答は `stale` になる（テスト `tests/domains/release/test_release_approval.py::test_judge_reports_stale_and_missing`）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 止まった・マージした・キューへ入れた・キューから外れた・人のマージを検知した・バージョンを上げたことが、`release-steps` の結果 JSON と本番の PR のどちらかに、承認済みのコミット・マージした head・承認した人・作ったバージョンと一緒に残る |
| セキュリティ | 本番のマージ・merge queue への追加・検知・CD のバージョンアップに使う token は今の `secrets.NDF_RELEASE_TOKEN` か `github.token` だけにし、新しい秘密を足さない。ruleset の書き換えは、人の承認の後に実装のときに行う 1 回（merge queue を足す）だけで、工程は ruleset を読むだけにする |
| 移植性 | ブランチ戦略・検証環境・バージョンアップの対象・マージの方式は、設定ファイルの値だけで切り替わり、ai-plugins に固有の名前（`ndf`・`verify/next`・`ai-plugins-next`・`plugin.json`）をコードに決め打たない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。ndf-next のリリースのワークフローの形（fix の worker を外す・merge queue への追加）・`release-steps` のサブコマンドと結果 JSON・ブランチ戦略の一覧（`github-flow` 戦略を足す）・設定ファイル（検証環境・バージョンアップの対象・マージの方式）・CD の振る舞い（バージョンアップ）。ndf-next は未リリースのため `互換なし` で扱う |
| データ | 終わりの記録に、承認の経路・承認した人・承認済みのコミット・マージした head・作ったバージョンが足される |
| 既存の振る舞い | `promote-whole`・`promote-selected` 戦略のリポジトリは今と同じに動く。`github-flow` 戦略のリポジトリでは、承認の後に CI が落ちても直さずに止まり、人の GitHub でのマージが承認として扱われ、バージョンは PR で上げず CD が上げ、develop・常設のリリースブランチ・同期の PR が無くなる。今の NDF（`plugins/ndf/`）の振る舞いは変わらない |
| 外部の系の設定 | 実装のときに、main の ruleset へ merge queue を足す（人の承認の後） |
| 設定ファイル | ブランチ戦略・マージの方式・検証環境・バージョンの保存先の記載箇所が、3 つのファイルからブランチ戦略のセクションへ移る。旧い保存先からの移行は #3613 が持つ |
| 必ず人の承認が要る操作 | ブランチ戦略とバージョンの規則を変える（P1）・指示書の運用のセクション（`AGENTS.md`）を書き換える（C7）・main の ruleset へ merge queue を足す（誰がどの条件でマージできるかが変わる。該当の番号は設計が決める。受け入れ条件 2h）。前の 2 つは設計承認ゲートとリリース承認ゲートで人が見る。ruleset の書き換えは承認ゲートを通らない操作のため、実行の前に止めて人へ戻す |
