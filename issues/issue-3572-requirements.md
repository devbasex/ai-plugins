## 事象

並列の計画 p6 のリリース 14（ndf v10.27.68）で、利用者がリリース承認ゲートで develop の 6fb221da を承認した（2026-11-15 14:49 JST）後に、一時レーン p6-rel14 の本番のプランの直しを受け持つ worker が、NDF のコード修正 5538d759「Fix(release): 使い回す -sync の PR の本文に ndf-next の port 検査の印を足す」をリリースブランチ `release/v10.27.68` へ積んだ。この修正は承認したコミットに含まれず、レビューも受けていない。修正で `plugins/ndf/scripts/release-steps.py` が 1411 行になり、行数の検査（上限 1409 行）が落ち、本番の PR https://github.com/devbasex/ai-plugins/pull/3570 をマージできなくなった。p6-rel14 が止まって問い直し、利用者の答えで修正を外して出すことにした。

リリース 8（2026-11-14 12:1x JST）でも、承認の後に修正の worker が 168affe0 を本番の PR へ積み、承認を取り直した。同じ形の 2 回目である。

## 期待する結果

承認ゲートで承認した先端の後に、本番の PR へ新しいコミットを積めない。CI が落ちたときの直しは承認の前の PR で入れ、直した先端で承認を取り直す。

ndf-next（11.0.0）のブランチの運用は GitHub flow を土台にする。スプリントブランチは main から切り、PR で main へマージする。main へのマージがリリースで、版数とタグは CD がマージの時点に作る。マージの前の検証は、名前の違う 2 つ目のマーケットプレイスで行う。

## 再現手順

1. 並列の計画のまとめたリリースで、リリース承認ゲートの承認を送る（`parallel.py confirm`）
2. 一時レーンの本番のプランで、本番の PR かリリースブランチの CI が落ちる
3. プランの直しのステップ（fix の worker）が、落ちたチェックを直すためにコードを変えてリリースブランチへ push する

- 前提 1: ndf-next では、承認の対象は既に PR の先端である。確かめた根拠:

- 前提 2: 承認からマージまでの間にコミットが積まれる経路は、承認の後に流れるプランに「CI が落ちたらコードを直して push する」ステップがあることである。ndf-next の雛形では、`merge.json` の `ci` が `test_failed` / `check_failed` で `repeat-check` → `ci-fix`（`{{worker}} ci-fix`）→ `ci-local` → `push` へ進む（`plugins/ndf-next/contracts/templates/merge.json`・`parts/steps.json`）。どのプランが本番の PR を流すかは設計で特定する

## 対象範囲

- マージの前の PR を集めた検証の ref の作り方と、それを指す 2 つ目のマーケットプレイスの登録の形。検証の ref を main へ戻さない決まり

| 土台 | GitHub flow。スプリントブランチは main から切り、PR で main へマージする。develop と常設のリリースブランチは持たない |
| リリース | main へのマージがそのままリリース。マージ＝リリース承認＝マージ承認 |
| 版数 | マージの時点に CD が上げてタグを作る。PR は版数を触らない。main へのマージで CD が `plugin.json` を上げるコミットとタグ `ndf--v<版>`・GitHub Release を作る。上げ幅は PR の宣言（ラベルなど）で決める |
| マージの前の検証 | 名前の違う 2 つ目のマーケットプレイス（例 `ai-plugins-next`）が、main へマージする前の PR を集めた使い捨ての検証の ref を指す。名前が違うので正式版と両方を登録でき、登録し直しが要らない（Claude Code の公式の勧め。公式には release-channel の概念が無い）。検証の ref は main へ戻さない |
| 同期の PR | 無くす（戻す先のブランチが無い）。#3551 の形は仕組みごと無くなる |
| 承認の外のコミット | 承認するのは PR の先端。マージは先端の照合つき（`--match-head-commit`）。承認の後に直しのステップを置かない（決定 1・2 は残す） |

- 実装は ndf-next（11.0.0）。今の `plugins/ndf/` は 11.0.0 まで develop と main の運用のまま
- `AGENTS.md` の「版とリリースの方針」と `docs/versioning-and-distribution.md`（版数の扱いの正本）を書き直す。#188（2026-08-31）で main と develop に分けた理由（マージした時点で常用する利用者へ届く）は、2 つ目のマーケットプレイスの検証で受ける
- #3576（常設のリリースブランチの宣言）と #3119 の常設のリリースブランチの構想は、この方針で不要になる見込み。設計で扱いを決める

### CHANGELOG.md の扱い（2026-11-15 21:1x JST）

> CD でバージョンを確定するのだとすると、CHANGELOG.md は廃止した方がよさそうですかね

（書き手: 利用者。下はこの問いへのオーガナイザーの案で、設計承認ゲートで利用者が決める）

- 案: 廃止せず、CD が書く形にする。PR は CHANGELOG.md を触らない。main へのマージの時点に、CD が版数を上げるコミットと同じコミットで版の節を書き、GitHub Release の本文も同じ元（PR の「利用者向けの変化」）から作る（release-please と同じ形）。PR どうしの衝突は起きない
- 残す理由: 読むスクリプトが 7 本以上ある（`instructions_lib/versions.py`・`design-match.py`・`doc-lint.py`・`release_lib` など）。廃止すると GitHub の API で読む形へ書き換えが要り、手元で grep できず、API の利用上限に当たる（2026-11-15 も GraphQL の上限に当たった）
- 今の重複: GitHub Release の本文は CHANGELOG の版の節と同じ中身（10.27.67 で確認）
- あわせて: 配らないもの（入れ替えの前の ndf-next）の行は載せない
