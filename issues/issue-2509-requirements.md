## 目的

- 状態の一覧が一時的に失敗しても、並列の計画が取り消せない `finished` で終わらないようにする
- NDF のスクリプトの下で打つ利用者の `uv run --project <x>` が、NDF の共有の環境（`~/.cache/ndf/venv/<版>`）を作り直さないようにする。あわせて、利用者のテストが自分のプロジェクトの環境で走るようにする

## 前提

- 前提 1: NDF のスクリプトが共有の環境の `uv run` の下で動くのは、`lib/deps.py` の `require()` が自分を起動し直した経路だけである。起動し直した後の `require()` の中で外せば、そのスクリプトが起動するすべての子プロセス（スプリントのステップ・ラッパー・ラッパーの子の claude とその Bash）に効く。設計でこの経路のほかに `UV_PROJECT_ENVIRONMENT` を共有の環境へ向けて子へ渡す箇所が見つかれば、その箇所も同じ条件で外す
- 前提 2: 外すのは NDF が設定した値（共有の環境、または `require()` がリポジトリの根の `.venv` へ向けた値）だけである。利用者が自分のシェルで設定した `UV_PROJECT_ENVIRONMENT` は、ラッパーが起動する子の claude へもそのまま渡す。利用者の設定を NDF が黙って消さないため（共通原則 C6）
- 前提 3: 一覧の失敗が続いたと見なす長さは、停滞の区切り（`stall_seconds()`。`NDF_PARALLEL_STALL_MINUTES` で変えられる）を使う。新しい設定値は足さない
- 前提 4: `uv run` が子へ渡す `VIRTUAL_ENV` は、利用者の `uv run --project <x>` では使われず、共有の環境を変えない。この課題では扱わない。確かめた結果（2026-11-05、uv の手元の版）: 別の環境を指す `VIRTUAL_ENV` を付けて `uv run --project <別のプロジェクト>` を打つと、`<別のプロジェクト>/.venv` を作ってそこで動き、`VIRTUAL_ENV` の指す環境の `pyvenv.cfg` の更新時刻は変わらなかった
- 前提 5: 本文の「手元の回避」で退避した耐久の記録と、手元で常駐させた見張りは、この課題の変更の対象ではない

## 対象範囲

含む:
- 並列の計画のオーガナイザーの観測が、一覧の失敗を見分け、失敗した回の観測でレーンの状態を変えないこと
- 一覧の失敗が続くときに、計画を終えずに利用者へ問うこと
- NDF のスクリプトの子プロセスと、ラッパーが起動する子の claude へ、NDF が設定した `UV_PROJECT_ENVIRONMENT` を渡さないこと
- 上の 2 つの回帰テスト

含まない:
- `finished` で終わった計画を、レーンが動いたまま打ち直したときの戻り方（S6）
- ラッパーの環境の作り方（`--no-managed-python` で 3.14 と 3.13 が入れ替わること）の変更。共有の環境が作り直されなくなれば入れ替わりは起きない
- 利用者のリポジトリの `uv run` の書き方の変更（carul の `AGENTS.md` など）

## 依頼（原文）

書き手: 起票者（carul の並列の計画の記録を調べた AI）、日付: 2026-11-04。下は要求を書く前の課題の本文の全文である。同じ日のコメント（ https://github.com/devbasex/ai-plugins/issues/2509#issuecomment-6643815528 ）の内容は、本文へ反映されている。

> ## 何が困っているか
>
> 並列の計画で 3 本のレーンが動いている途中に、オーガナイザーの耐久ワークフロー（`parallel.py run`）が「全レーンが止まった」と判断し、`finished` で終わる。実際はレーンは 3 本とも動いていて、それぞれ周回 1 のスプリントを流していた。
>
> `finished` は耐久の記録に残る。そのため `parallel.py start` を打ち直しても、`resumed: true` で同じ `finished` を返すだけで、オーガナイザーは戻らない。レーンが配布の依頼や承認ゲートの依頼を送っても、受け取る側がいなくなる。
>
> 原因は 2 つが重なっている。
>
> 1. NDF のスクリプトが子プロセスへ `UV_PROJECT_ENVIRONMENT=~/.cache/ndf/venv/<版>` を引き継ぎ、利用者のリポジトリで打つ `uv run --project <x>` が共有の環境をそのプロジェクトの環境として作り直す。同期は exact なので、ラッパーの extras が抜ける
> 2. `step_observe` が `relay.py ls --json` の失敗を見ない。失敗して `items` が空のときも、全レーンを「行が無い ＝ stopped」と読む
>
> ## 具体例: carul の計画 l20261104（2026-11-04、NDF 10.27.16）
>
> | 時刻（UTC） | 出来事 |
> | --- | --- |
> | 22:12 | `parallel.py start l20261104` で 3 レーン（`l20261104-ux`・`-api`・`-cust`）が起動した |
> | 22:12〜 | 各レーンが `supervise.py queue` を `uv run --quiet --frozen --project <プラグイン> --extra md --extra mdtable ...` で流し始めた |
> | 22:19:46 | `~/.cache/ndf/venv/10.27.16` が丸ごと作り直された（ディレクトリ・`.gitignore`・`CACHEDIR.TAG` の時刻がすべてこの時刻）。`bin/python` は uv 管理の `cpython-3.13` を指していた |
> | 22:19 | `relay.py ls` が `ndf-relay: ラッパーの環境（/home/ubuntu/.cache/ndf/venv/10.27.16）が無い。/ndf:install-wrapper を打ち直す` で終了コード 3 を返すようになった。器はあり、`bin/python` も動いた。ラッパーの extras（`procs`・`locks`・`md`・`versions`・`terminal`）が import できず、`runtime.ready()` が偽になっていた |
> | 22:19 | `parallel.py wait` が `action: finished` を返した。items は 3 レーンとも `state: stopped` だった |
> | 22:20 | `relay.py status` で環境を作り直すと `relay.py ls` は 3 レーンとも `running` と答えた。このときの `pyvenv.cfg` は `version_info = 3.14.4`（`home = /usr/bin`）で、作り直しのたびに Python が 3.13 と 3.14 の間で入れ替わっている |
> | 22:20 | `parallel.py start` を打ち直したが、`resumed: true` の `finished` が返るだけだった |
>
> ### 共有の環境が作り直される理由
>
> `lib/deps.py` が `uv run` に渡す `UV_PROJECT_ENVIRONMENT=~/.cache/ndf/venv/<版>` が、その下で動く NDF のスクリプトの子プロセスへそのまま引き継がれる。レーンのスプリントは、利用者のリポジトリのテストを子プロセスで打つ。carul の `AGENTS.md` には `uv run --project infra pytest infra/tests` があり、この `uv run` は引き継いだ変数を読んで、NDF の共有の環境を carul の `infra` のプロジェクトの環境として同期し直す。
>
> - carul の `infra/pyproject.toml` は `requires-python = ">=3.13,<3.14"` なので、3.14 の環境は捨てられ、uv 管理の 3.13 で作り直される
> - 同期は exact なので、NDF の extras（ラッパーの `procs`・`locks`・`md`・`versions`・`terminal` を含む）はすべて消える
>
> 22:19:46 に環境が 3.13 で作り直されたことと、その後に `relay.py ls` が失敗したことは、どちらもこれで説明できる。NDF の `uv run` の経路だけなら、3.14 の環境をそのまま使う（作り直さない）。
>
> 再現（別の置き場で）:
>
> ```bash
> T=$(mktemp -d)/venv; R=<プラグインの根>
> # ラッパーと同じ作り方で NDF の環境を作る
> UV_PROJECT_ENVIRONMENT=$T uv sync --frozen --quiet --no-managed-python --project $R \
>   --extra procs --extra locks --extra md --extra versions --extra terminal --inexact
> grep version_info $T/pyvenv.cfg              # 3.14.4。psutil などを import できる
> # NDF の uv run の子が引き継ぐ変数のまま、利用者のプロジェクトを uv run する
> UV_PROJECT_ENVIRONMENT=$T uv run --quiet --project infra python -c pass   # carul の根で
> grep version_info $T/pyvenv.cfg              # 3.13。作り直された
> $T/bin/python -c "import psutil"             # ModuleNotFoundError
> ```
>
> 影響は並列の計画に限らない。
>
> - NDF の `uv run` の下から打つ利用者の `uv run --project <x>` は、どれも NDF の共有の環境を上書きする。同時に動いている NDF のスクリプトとラッパーの import が壊れる
> - 利用者のテストが、自分のプロジェクトの `.venv` ではなく NDF の置き場で走る。依存とバージョンが混ざり、結果が手元の実行と変わりうる
> - 単独のスプリントでも起きる。並列の計画では 3 レーンが同時に打つので、早く当たる
>
> ### 観測が失敗を見ない
>
> `lib/parallel_run.py` の `step_observe` は、`relay()` の終了コードを捨てる（`_, res = relay(Path(main), "ls", "--json")`）。`_observe_run` は行の無いレーンを `stopped` にし（`if st is None and run.lanes[n].get("started"): st = "stopped"`）、`_run_finished` が全レーンの停止として終える。1 回の観測の失敗で、計画全体が取り消せない形で終わる。
>
> ## 手元の回避
>
> 1. 共有の環境に全 extras を `--inexact` で入れた（`UV_PROJECT_ENVIRONMENT=~/.cache/ndf/venv/10.27.16 uv sync --frozen --project <プラグイン> --all-extras --inexact`）
> 2. 耐久の記録 `~/.local/state/ndf/dbos/parallel-<鍵>.sqlite` を退避して `parallel.py start` を打ち直した。動いているレーンは `spawn` が `name-taken` を成功として扱うので、二重には起動しなかった
> 3. 10 秒ごとに `relay.py ls` を確かめ、失敗したら 1 を打ち直す見張りを常駐させた
>
> ## 直し方の案
>
> - `step_observe`：`relay.py ls` が 0 以外で終わったら、その回の観測を捨てる（状態を変えない）。続けて失敗するときは、`stall` と同じく問いにする。行が無いことを `stopped` と読むのは、`ls` が成功したときだけにする
> - 共有の環境：`deps.py` が `os.execve` で起動し直した後、NDF のスクリプトの中で `UV_PROJECT_ENVIRONMENT` を `os.environ` から外す（再起動の判定は `REEXEC_ENV` で行う）。もしくは、利用者のコマンドを起動する共通の箇所（`supervise_lib` のステップの実行、`relay_lib/claude.py` の子の環境）で必ず外す。`relay.py` の子の claude の環境からも外す
> - `finished` で終わった計画を、レーンが動いているまま打ち直したときの戻り方を用意する。たとえば `start` が `relay.py ls` の `running` を見て、記録を作り直すか問う
>
> ## 受け入れ条件
>
> 1. `relay.py ls` が失敗を返す間（ラッパーの extras を抜いた環境で再現する）も、`parallel.py run` は終わらず、レーンの状態を変えない
> 2. NDF のスクリプトの子プロセスとして打った `uv run --project <別のプロジェクト>` が、NDF の共有の環境を変えない（`pyvenv.cfg` と時刻が変わらない）。子の環境に `UV_PROJECT_ENVIRONMENT` が無い
> 3. 1 と 2 の回帰テストが `scripts/tests/` にある
>
