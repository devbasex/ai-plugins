### 見つけたこと（#1693 の起票時の本文）

**cross-refactoring の最終ゲート修正のコミットは、範囲テストも静的解析も通らないまま push される。** 最終ゲートは入口で
push（`publish.enter_final_gate`。`plugins/ndf/skills/cross-refactoring/scripts/refactor_lib/commands/gate.py:79`）してから
静的解析の全体テスト（`gate_lint.lint_gate`。同 `:95`）を走らせる。最終ゲート修正の取り込み（`cmd_merge_final_fix`）は
範囲テストを走らせず、取り込みの終わりに push する（同 `:475`）。

このため、最終ゲート修正が整形の違反を入れると、取り込みの push か次の `final-gate` の入口の push が、push 前の検査（`.githooks/pre-push` の
`scripts/check-lint.sh`）で拒まれ、refactor が止まる。宣言に整形の suite を足しても（#464）この経路は塞がらない。
再発の実例は 2026-09-30 のスプリント m1523・PR 1564（#464 の本文の「再発」の節）。

### 取り込んだ課題（#1688 の起票時の本文の要点）

cross-refactoring の範囲テストに、リポジトリ全体を見る検査（`scripts/tests/test_check_script_structure.py::test_repository_matches_its_allow_list`）が入ると、別の項目が変えたファイルの違反で落ちる。落ちた項目は自分の変更と関係なく「範囲テストが修正に使える時間の内に通らなかった」として取り消される。

- スプリント m1649 の検査（PR #1673、実行 rf1673）で、改善項目 15 件のうち 9 件が取り消され、6 件（I-001・I-005・I-006・I-007・I-011・I-012）は `scripts/check-script-structure.py` を対象にした項目だった
- 検証の記録が残る 5 件で落ちたのはどれも `test_repository_matches_its_allow_list` の 1 件で、違反は `plugins/ndf/skills/cross-refactoring/scripts/refactor_lib/commands/gate.py` の 509 行（上限 500）。5 件とも `gate.py` を触っていない
- `gate.py` を 509 行にしたのは I-014 の実装コミット 7f95ad44。I-014 自身の範囲テスト（45 件）は通り、後で危険フラグの全体テストで取り消された
- 根拠: https://github.com/devbasex/ai-plugins/pull/1673#issuecomment-5965264354 ・#1688 の本文

## 目的

cross-refactoring が項目と最終ゲート修正を検証するときの物差しを、push 前の検査（宣言の静的解析の suite）と揃え、次の 2 つを無くす。

1. 検証を通った（または検証されていない）変更が、push 前の検査で拒まれて実行が止まる（#1693）
2. ある項目の違反で、その違反に触れていない別の項目が取り消され、原因の項目が記録から読めない（#1688）

共通の原則: **項目と最終ゲート修正の合否は、その変更が変えたファイルで判定し、push より前に決める。**

## 前提

- 前提 1: 「push 前の検査」に当たるものを cross-refactoring は宣言（`.ndf/project.json` の `test.suites`）の `kind: lint` の suite として読む。`.githooks/pre-push` などプロジェクト固有の仕組みを NDF が読んで解釈しない（Value 5）。宣言に静的解析の suite が無いプロジェクトでは、この変更による振る舞いの違いは無い
- 前提 2: 静的解析の suite の範囲テストは、既存の `scope_command` の `{paths}` へ変更ファイルを入れて組む（`targets.lint_runs` と同じ組み方）。範囲の組み方そのものは変えない
- 前提 3: 最終ゲート修正が静的解析で落ちたとき、その修正のコミットは公開せずに取り消し、違反の記録（suite とファイル）を添えて次の最終ゲート修正へ戻す。修正を続けるかは既存の締め切り（`_final_fix_stop`）が決める
- 前提 4: 「リポジトリ全体を見るテスト」を名前（`test_check_script_structure.py` など）で見分けない。見分けるなら、落ちた箇所が項目の変えたファイルに当たるかで判定する（Value 5）
- 前提 5: 違反を入れた項目は、自分の検証の静的解析の範囲テスト（`lint_runs`。変えたファイルを入れる）で落ちる。#1688 の I-014 の検証でこれが走らなかった理由（実行時点の宣言・版）は設計で確かめる（未決 1）

## 対象範囲

含む:
- 最終ゲート修正の取り込み（`merge-final-fix`）で、修正のコミットが変えたファイルへ静的解析の範囲テストを当て、push より前に合否を決めること（#1693）
- 最終ゲートの入口の push より前に、公開していないコミットが静的解析を通っていることを保つこと（#1693）
- 項目の範囲テストが、その項目が変えていないファイルの違反だけで落ちたとき、その失敗で項目を取り消さないこと（#1688）
- 違反を入れた項目を原因として記録し、取り消しの理由に違反の suite とファイルを残すこと（#1688）

含まない:
- push が拒まれたときの記録（#1648）
- cross-review の側の同じ形（#1507）
- 宣言に静的解析の suite を足す・範囲テストの組み方（`lint_runs` / `scope_runs`）を変える（#464）
- `scripts/tests/test_check_script_structure.py` など個別のテストを項目のファイルへ絞る変更（同じ形の全体テストが他に入れば再び起きるため、選ぶ側・判定する側で直す）
- `.githooks/pre-push` と `scripts/check-lint.sh` の変更

## 用語

| 用語 | 意味 |
| --- | --- |
| 範囲テスト | 項目（または最終ゲート修正）の変更に関わる対象だけを走らせるテスト。テストの種別は `test_targets`、静的解析は変えたファイルから組む |
| 最終ゲート修正 | 最終ゲートが落ちたときに修正担当が作るコミット。どの改善項目にも属さない |
| 原因の項目 | 失敗を起こした変更を入れた改善項目 |

## 受け入れ条件

### 最終ゲート修正（#1693）

- [ ] AC1: 前提: 宣言に静的解析の suite がある。操作: 最終ゲート修正のコミットが、その suite の違反（整形の違反・行数の上限超えなど）を変えたファイルに入れた状態で `merge-final-fix` を打つ。結果: push が 1 回も呼ばれず、修正のコミットは HEAD から外れ、終了コードは 2 になる
- [ ] AC2: AC1 のとき、最終ゲートの記録（状態ファイルの `final_gate`）に、落ちた suite の名前と違反のファイルが残り、次の最終ゲート修正の依頼にその内容が渡る
- [ ] AC3: 最終ゲート修正のコミットが静的解析の範囲テストを通るときは、従来どおり取り込み（`fix_commits` へ足す）、push する
- [ ] AC4: AC1〜AC3 は、全体テストの置き場が手元・`local-scoped-ci-whole`・`--ci-check` のどれでも同じ結果になる（単独の起動でも工程の 1 つとしての起動でも同じ）
- [ ] AC5: 静的解析の範囲テストの対象は修正のコミットが変えたファイルだけで、修正が触っていないファイルの既存の違反では落ちない
- [ ] AC6: 最終ゲートの入口の push（`publish.enter_final_gate`）は、静的解析の合否が決まっていないコミットを公開しない（検証を通ったコミットと、AC1〜AC3 で取り込んだコミットだけが公開される）

### 範囲テストの判定（#1688）

- [ ] AC7: 前提: origin/develop の `gate.py` が上限ちょうど（500 行）。項目 X が `gate.py` に 9 行足し、項目 Y が `scripts/check-script-structure.py` を変え、Y の `test_targets` に `scripts/tests/test_check_script_structure.py` を持つ。結果: Y は `gate.py` の違反を理由に取り消されない
- [ ] AC8: AC7 のとき、X は自分の検証で違反として落ち、取り消しの理由に違反の suite（または落ちたテスト）とファイル（`gate.py`）が残る。理由が「範囲テストが修正に使える時間の内に通らなかった」にならない
- [ ] AC9: 項目の範囲テストが、その項目の変えたファイルに当たる失敗で落ちたときは、従来どおり項目の失敗として扱う（退行しない）
- [ ] AC10: 全体を見るテストの見分けや判定に、このリポジトリのテスト名・パスを既定として埋め込まない（別の名前の全体テストでも AC7 と同じ結果になる）

### 両方に共通

- [ ] AC11: 既存の cross-refactoring のテスト（`plugins/ndf/skills/cross-refactoring/tests/`）がすべて通る
- [ ] AC12: 宣言に静的解析の suite が無いプロジェクトでは、`merge-final-fix` と項目の検証の振る舞いが変わらない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | `merge-final-fix` に足す静的解析の範囲テストは、既存のテスト 1 回の上限（`state_test_timeout`）の内で走らせ、上限を超えたら落ちた扱いにする。判定（E4）で足す走らせ直しは、既存の修正の締め切りを延ばさない |
| 運用・保守性 | 取り消し・差し戻しの記録から、原因の項目（または最終ゲート修正）と違反のファイルを状態ファイルだけで読める |
