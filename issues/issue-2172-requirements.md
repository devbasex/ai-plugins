## 目的

- 1 つのアカウントで並列に流れる複数のスプリントの実行が、それぞれ今どのフェーズにいて、承認待ちか止まったかを、1 つの画面で見分けられる状態にする（#2168 の受け入れ条件 5 の後半）
- 1 つのスプリントの実行について、課題ごとの工程・Pull Request・CI の結果・承認ゲートの状態を 1 つの画面で追え、工程を 1 行ずつ辿ってその工程の中身（触ったファイル・決めたこと・終了コード・秒・費用・ログ）まで確かめられる状態にする（#2168 の受け入れ条件 6）
- スプリントの外でも、取り込んだリポジトリの順位と棚卸しの記録を読める状態にする

## 前提

- 前提 1: 一覧と詳細は、進捗の記録（#2171）の事象の列と、スプリントの実行（#2186）の状態だけから導く。課題の本文・ボード・GitHub の API は読まない。例外はバックログの画面で、順位の表は #2186 の GitHub の口（`factory/api/src/github/port.ts` の棚卸しの順位の表の読み出し）を使う
- 前提 2: フェーズの名前の集合は `設計`・`実装`・`検査`・`取り込み`・`仕上げ` の 5 つとし、`factory/contracts/` に列挙として置く。NDF のプランの `"フェーズ"` の値 `配布（開発版）` は `取り込み`、`配布（本番）` は `仕上げ` へ、ランナーの翻訳が写す（NDF の `agent-layers.md` の「フェーズ」の表で、検証リリースは取り込み、本番へのリリースは仕上げの工程）。受け口は今どおり文字列で受け、集合に無い名前の `phase.changed` は 400 にせず残し、画面は「その他（<名前>）」と出す（NDF の版がフェーズを足しても記録が失われない）
- 前提 3: 一覧の「今のフェーズ」は、そのスプリントの実行の最後の `phase.changed` の `phase`（`order_key` の順）とする。並列の実装で複数の課題が同じフェーズにいるときも 1 つの名前になる。`phase.changed` が 1 件も無い実行は「始まる前」と出す
- 前提 4: 詳細パネルの「触ったファイル」「その工程で決めたこと」「ログと作業の報告」は、今の進捗の事象の形では届かない。この課題は `step.recorded` の `payload` に任意の項目（触ったファイルのパスの並び・決めたことの文の並び・作業の報告の本文）を足し、`schema_version` を上げない互換の追加とする（今のランナーの事象も通る）。足す形は設計で決め、確定仕様（`ndf-factory-service-boundary.md` の「進捗の事象の種類と受け口」・`ndf-factory-contracts-and-progress.md` の「進捗の事象の定義」）を直す Pull Request を先に出す。ランナーの翻訳（`factory/runner/`）もこの課題で直す
- 前提 5: 工程を課題へ結び付けるため、`step.recorded` の `payload` に課題の番号の並び（任意）を足す（前提 4 と同じ互換の追加）。番号を持たない `step.recorded`（スプリントで 1 つの検査・取り込み・仕上げの工程や、足す前のランナーの事象）は、課題ごとの欄でなく「スプリント全体」の欄に出す
- 前提 6: 工程の費用は、同じスプリントの実行の `usage.recorded` のうち `payload.step` がその工程と等しいものの `cost` の和とする。等しいものが無ければ「—」と出す。形態 ①・② の費用も同じく出す（確定仕様の「`usage.recorded` は 3 つの形態とも出す」）
- 前提 7: 一覧と詳細は、画面を開いている間 30 秒ごとに API を読み直して更新する。押し出しの通知は作らない。読み直しの間隔は設定の 1 か所で変えられる
- 前提 8: 承認ゲートの状態は、承認の依頼の集約（#2173。まだ実装されていない）を読まず、進捗の事象 `gate.reached`・`gate.answered`・`job.finished`（`gate`）と、スプリントの実行の状態 `awaiting_approval` から導く。状態は「承認待ち」「承認された」「差し戻された」「判断を待っている」「判断に答えた」の 5 つとする。承認するボタンは #2173 が置き、この課題は置かない
- 前提 9: 見せる範囲は、`resolveAccount` で解決できたアカウントのスプリントの実行だけ。チームのアカウントでは席を持つ人なら誰でも一覧と詳細を読める（スプリントの一覧と同じ。#2186 の確定仕様の「持ち主だけの経路」）。他人のアカウントのもの、アカウントに属さない `sprint_run_id` はどれも 403 `forbidden` と同じ本文で返し、有無を明かさない
- 前提 10: 詳細の読み出しは、1 つのスプリントの実行の事象を全件読んで導く。件数の上限は設計で過去のスプリントの `progress.jsonl` の行数を実測して決め、超えたら古い工程から省いて省いた件数を出す
- 前提 11: 時刻は ISO 8601 の UTC で受け、画面はブラウザの地域の時刻で出す
- 前提 12: 「仕上げのフェーズに振り返りと棚卸し（必須）を出す」は、仕上げのフェーズの欄に工程 `振り返り`・`棚卸し` の行を常に置き、`step.recorded` がまだ無ければ「まだ」と出すことを指す。工程の名前の照合は、ランナーが `step.recorded` の `step` に写す NDF のステップの識別子のうち、どれを振り返り・棚卸しと見なすかを設計で決める
- 前提 13: バックログの画面は、取り込んだリポジトリごとに、順位の表（#2186 の候補が読むものと同じ）と、そのリポジトリのスプリントの実行のうち仕上げのフェーズで記録された棚卸しの工程の一覧（日時・要約・Pull Request）を出す。読むだけで、課題やマイルストーンを書き換えない

## 対象範囲

含む:
- 画面（`factory/web/`）: スプリントの一覧・スプリントの詳細（工程の詳細パネルを含む）・バックログの画面と、そこへの導線（アカウントとリポジトリの画面から）
- API（`factory/api/`）: 一覧の派生を足した読み出し・詳細の読み出し・バックログの読み出しの経路と、その OpenAPI（`factory/contracts/openapi/`）
- 契約（`factory/contracts/`）: フェーズの名前の列挙と、`step.recorded` の任意の項目の追加（前提 4・5）。確定仕様を直す Pull Request を先に出す
- ランナー（`factory/runner/`）: フェーズの名前の写し（前提 2）と、`step.recorded` の足した項目の翻訳（前提 4・5）

- 承認と差し戻しの操作・承認の依頼の保存・Web と Slack の通知（#2173）

- 料金と請求の画面（#2174）
- 押し出しの通知（WebSocket・Server-Sent Events）
- DynamoDB の表と GSI・API の入口などインフラの定義（private リポジトリ）
- 課題の本文の `## 進行` とボードを読むこと

## 用語

| 用語 | 意味 |

| スプリントの一覧 | アカウントのスプリントの実行を新しい順に並べ、それぞれの今のフェーズと状態を出す画面 |

## 受け入れ条件

一覧:

- [ ] 1. アカウントに、フェーズの異なる 3 つのスプリントの実行（最後の `phase.changed` が `設計`・`検査`・`仕上げ`）があるとき、一覧の 3 行にそれぞれ `設計`・`検査`・`仕上げ` が出る
- [ ] 2. 一覧の各行に、リポジトリ・課題の番号・スプリントの実行の状態（実行中・承認待ち・終わった・止まった・失敗・取り消し）・今のフェーズ・始めた日時が出る。`phase.changed` が 0 件の実行は今のフェーズに「始まる前」が出る
- [ ] 3. `phase` が 5 つの名前に無い `phase.changed`（例 `準備`）が最後の実行は、今のフェーズに「その他（準備）」が出て、一覧の読み出しは 200 を返す
- [ ] 4. ランナーが NDF のプランの `"フェーズ"` の値 `配布（開発版）` を `取り込み`、`配布（本番）` を `仕上げ` として `phase.changed` に写す。5 つの名前はそのまま写す

詳細:

- [ ] 5. 課題 2 つ（#A・#B）を持つ実行で、`payload` に課題 #A を持つ `step.recorded` は #A の欄に、#B を持つものは #B の欄に、課題を持たないものは「スプリント全体」の欄に、`order_key` の順で並ぶ
- [ ] 6. 各課題の欄に、その課題の工程を作った・更新した Pull Request（番号と GitHub へのリンク）と、最後の `pr.updated` の状態（open / closed / merged）と、その Pull Request の `ci.updated` のチェックの名前ごとの最後の結論（未完了は「実行中」）が出る。`pr.updated` が無い Pull Request は状態に「不明」が出る
- [ ] 7. 工程の行を押すと、右側が詳細パネルに切り替わり、ステップ・終了コード・秒・費用（前提 6）・要約・触ったファイル（各パスが GitHub のそのリポジトリのファイルへのリンク）・決めたこと・作業の報告が出る。足した項目を持たない工程では、その欄に「記録なし」が出る
- [ ] 8. 承認ゲートの状態が、`gate.reached`（ゲート 1）だけの実行では「ゲート 1: 承認待ち」、続いて承認の `gate.answered` があれば「ゲート 1: 承認された」、差し戻しなら「ゲート 1: 差し戻された」と出る。判断の `gate.reached` は「判断を待っている」、答えがあれば「判断に答えた」と出る。承認ゲート 1・2 と判断の 3 つの欄を持ち、承認の欄は 2 つだけである
- [ ] 9. 仕上げのフェーズの欄に、工程 `振り返り` と `棚卸し` の行が常にあり、`step.recorded` が届く前は「まだ」、届いた後はその工程の終了コードと秒が出る
- [ ] 10. 一覧と詳細を開いたまま、新しい進捗の事象が追記されると、読み直しの間隔（既定 30 秒）の 2 倍以内に画面へ出る。読み直しが失敗しても前の表示は消えない
