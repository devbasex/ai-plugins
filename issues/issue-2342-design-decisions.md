# #2342 の設計: 決定の記録

設計文書の本体は [issue-2342-design.md](issue-2342-design.md) にある。要求の未決のうち、入口ごとの使用中のときの扱いと待つ上限は決定 2、
開発ループとキューの持ち主の鍵の形は決定 1・3、配布の承認資料と #2243 の 5 種類の載せ方は決定 11・13、#1886 の切り分けは決定 12 が受ける。

## 決定の記録

### 決定 1: 2 つ目の conductor を開発ループの入口で止めるため、持ち主の単位を実行とセッションの 2 つにし、開発ループはセッションで持つ

開発ループは `loop start`・`loop select`・`loop sprint` のように、1 つの conductor が別々のプロセスで副命令を打って進む。持ち主の単位を
入口の 1 回の実行にすると、`loop start` が終わった時点で記録が返り、2 つ目の conductor の `loop start` を止められない（#2316）。
単位 `session` は持ち主のプロセスをランタイムのセッションのプロセス（hook が今も使う祖先の探し方）にし、`loop stop`・`loop finish` か
セッションの終わりまで持つ。同じセッションの副命令は `inherited` で通る。

開発ループの記録（`.ndf/loop/<名>/loop.json`）に conductor のセッションを書き足す形は採らない。記録の書き手が開発ループの部品と
持ち主の部品の 2 つになり、生死の判定と排他が開発ループの部品の中にもう 1 つできる。

根拠: Value 7（MVV 版 5）

### 決定 2: 前提 3 の入口はすべて止まる（`stop`）にし、待つ（`wait`）は部品と契約の形だけを持つ

前提 3 の入口の持ち主は、どれも数分から数時間動く（収束ループ・リファクタリング・キュー・開発ループ・見直し）。待つにすると、後から来た
conductor が進まないまま上限まで止まり、持ち主の実行の識別子を知るのも上限の後になる。止まって結果に持ち主の実行の識別子を出せば、
conductor はその場で待つか別の仕事へ移るかを決められる。待つは、短い排他の区間を持つ入口が後から宣言できるよう、部品と契約の形と
テスト用の契約のテストだけを持つ。待つ上限の値は前提 5 のとおり契約の一覧に置く。

同じ PR の cross-review を待つにする形は採らない。同じ PR の収束ループが 2 本並ぶのは conductor の取り違えで、待った後に流すと同じ指摘を
二重に直す。

根拠: Value 3 / Value 2（MVV 版 5）

### 決定 3: 並行の衝突が起きた単位で取り合うため、キューは done のパス、`run` はプランのパス、開発ループは名前を持ち主の鍵にする

#2316 で衝突したのは、同じ done を再開した 2 つのキューと、同じ名前の開発ループの同じ周回である。鍵を done ごとにすれば、
`queue <プラン>... --done X` と `queue --resume X` が同じ鍵を取り合い、別の done のキューは並べて流せる。開発ループを周回ごとにすると、
周回の切れ目で 2 つ目の conductor が入れる。パスはリポジトリの根からの相対へ正規化し、worktree の違いで鍵が割れないようにする。

キューをプランごとの鍵にする形は採らない。1 つのキューが流す複数のプランの鍵を起動時にまとめて取ることになり、取れた分だけで流すか全部を
待つかの規則がもう 1 つ要る。

根拠: Value 6（MVV 版 5）

### 決定 4: drive が起こす init が自分の持ち主に断られないよう、根の実行が同じ子の実行は持ち主の鍵を取り直さずに使う

cross-refactoring の `drive.py` は `refactor.py init` を子のプロセスとして起こし、どちらも同じ鍵 `cross-refactoring:pr={pr}` を宣言する
（`init` は利用者が直に打つこともあるため）。子は `NDF_RUN_ROOT` で根の実行の識別子を受け継ぎ、記録の `run` と一致すれば `inherited` で
通る。返すのは根の実行だけで、子の終わりでは返さない。

今の `--run <実行の識別子>` を init へ渡す形は採らない。#2321 のとおり、プランから呼ぶ `drive.py` には渡す手段が無く、案内が打てない手段を示す。

根拠: Value 5（MVV 版 5）

### 決定 5: 旧い再開の形が前の実行を引けるよう、持ち主の記録は返しても消さず、鍵ごとの最後の実行の索引にする

旧い形（`run <plan> --from`・`queue --resume <done>`・`drive.py <PR> --reopen`）は実行の識別子を持たず、プラン・done・PR で前の実行を指す。
これは持ち主の鍵と同じ単位なので、鍵の記録の `run` を引けば再開の入口へ渡す識別子が決まる。記録は終わった時刻から 30 日で片付ける
（耐久の記録と実行の記録の寿命と同じ）。

旧い形のために鍵から実行の識別子への索引を別に置く形は採らない。同じ単位の記録が 2 つになり、片方だけが更新されたときにどちらが正かが決まらない。

根拠: Value 8（MVV 版 5）

### 決定 6: 持ち主の記録が実行の識別子と時刻とプロセスだけを持つよう、結び付きは状態の一覧の列で静的に宣言する

受け入れ条件 12 は、持ち主の記録が持つものを実行の識別子・入口・鍵・時刻・pid と開始時刻・ホスト名に限る。状態の一覧の種類に
列 `lease`（鍵の形）を足せば、返した後に片付けが鍵の値から置き場を導ける（例 `cross-refactoring:pr=2318` → `<base>/<slug>/rf2318`）。
実行中に作った状態を記録へ登録する仕組みは要らない。

持ち主の記録に結び付いた状態のパスの並びを持たせる形は採らない。受け入れ条件 12 の範囲を超え、子の実行が書き足すたびに記録の排他を取り合う。

根拠: Value 8 / Value 5（MVV 版 5）

### 決定 7: 自分でプロセスグループを抜けた子孫も打ち切りで止めるため、プロセスの子孫と根の実行の印を持つプロセスの両方を止める

#2285 で残った偽の claude は、テストが自分で `start_new_session=True` を付けて起こしたもので、プロセスグループを止めても届かない。
止める直前に `psutil` で子孫を読み、加えて同じユーザーのプロセスのうち環境変数 `NDF_RUN_ROOT` が根の実行と同じものを止める。親を失って
子孫の木から外れたプロセスも、環境変数は受け継いでいるため拾える。既存の `procs.stop_tree` の順（SIGTERM、猶予の後に SIGKILL）を使う。

cgroup で実行を囲む形は採らない。配布先のコンテナと CI で cgroup を作る権限があるとは限らず、どのリポジトリでも動く形を保てない。

根拠: Value 6 / Value 7（MVV 版 5）

### 決定 8: 再開の入口が入口ごとの引数を知らずに済むよう、実行の記録の始まりの行から入口と入力を組み直し、入口を子として起こす

実行の記録（柱 P2）は始まりの行に入口の id を、`input` の行に入力ごとの名前・出所・値を持つ。再開の入口はそれを読んで同じ入力で入口を
起こし、`NDF_RESUME`（引き継ぐ実行の識別子）と `NDF_RESUME_FROM` を付ける。入口の核は引き継いだ識別子で実行を始め、持ち主の記録の
取り合いも通常の起動と同じ経路を通る。秘密の入力は記録に値が無いため、出所の環境変数から読み直す。

再開の入口が入口の関数を同じプロセスで呼ぶ形は採らない。耐久の記録はプロセスに 1 つしか開けず（`durable.launch`）、入口ごとの
副命令の引数の組み立てを再開の入口が持つことになる。

根拠: Value 5 / Value 7（MVV 版 5）

### 決定 9: `--from` が常に勝ち、位置の出所が 1 つになるよう、`--from` があれば途中を子ごと止めて新しい実行の回で始め、キューの続きも耐久の記録から読む

#2325 は、`--from` があっても前の起動が途中で残っていると `durable.resolve` が `continue` を返し、前の入力で回復したことが原因である。
`durable.resume_ref(prefix, resume)` は `--from` があれば、`launch` の前に接頭辞の途中の耐久ワークフローを子ごと止め（`keep=()`）、新しい
実行の回を返す。`--from` が無ければ `resolve` のとおり続ける。キューの止まったプランの続きの位置は、前の実行の回の各プランの耐久ワークフローの
出力（止まったステップ）から読み、done と `progress.jsonl` から決めない。

`--from` が変わったときだけ新しい実行の回にする形は採らない。前の `--from` を覚えておく置き場がもう 1 つ要り、#2325 の `fresh` の判定と
同じく、判定の漏れが位置の食い違いになる。

根拠: Value 7（MVV 版 5）

### 決定 10: 旧い版との並走で排他が抜けないよう、旧い置き場の記録は読むだけにし、書かない

前の版の NDF が書いた `*.owner.json` と `.ndf/backlog/owner.json` は、新しい版の取る側と片付けが読み、旧い規則で生きていれば使用中として扱う。
新しい版は旧い置き場へ書かない。読む処理は、この柱を含む正式版の次の正式版で消す。

旧い置き場へも二重に書く形は採らない。書き手が 2 つの置き場を同時に更新する経路ができ、片方の書き込みの失敗で記録が食い違う。

根拠: Value 7（MVV 版 5）

### 決定 11: 配布の承認資料が版ごとに溜まらないよう、状態の一覧の種類にし、配布のプランの後片付けのステップが外す

配布の承認資料（`issues/approval-<plugin>-v<版>.md`）は配布のプランが書き、承認ゲート 2 の答えを待つ間に読まれる。後片付けのステップに
達した時点で承認は済み、記録は Pull Request とリリースに残る。種類 `approval-doc` を状態の一覧に載せ、後片付けのステップが
`run_state` を通してそのプランの承認資料を外す。後片付けに達しなかったプランの承認資料は残す。

持ち主の記録に結び付ける形は採らない。承認資料の置き場は配布のプランの入力から導けず、決定 6 の静的な結び付きに載らない。

根拠: Value 5（MVV 版 5）

### 決定 12: #1886 は入力の解決の問題として柱 P8 へ渡し、この柱では残す

#1886 は、キューの後片付けが起動したworktreeを消した後、次のプランの計画が `Path.cwd()` を読んで落ちる不具合である。持ち主の記録を
取ってもworktreeは消え、`cwd` を読む箇所（`decl.py`・`commands.py`・`sprint.py`・`templates.py`・`actuals.py`）は変わらない。
リポジトリの根を起動時に 1 度解決して実行の文脈に持たせるのは入力の部品（柱 P8 #2341）の責務である。

この柱でworktreeの片付けを持ち主の生存で止める形は採らない。後片付けはworktreeを消すステップそのもので、止めると後片付けが働かなくなる。

根拠: Value 7（MVV 版 5）

### 決定 13: #2243 の 5 種類は、退避先の 4 種類と承認ゲートの資料の置き場を残す理由つきで一覧に載せる

`ndf-stages`・`ndf-checks`・`ndf-usage` は状態の置き場が書けないときの退避先で、中身は通過記録・検査の事象・使用量の帳簿である。
一時の片付けで消すと記録が失われる。`ndf-guards` は hook が作る状態で、hook は #2335 の「含まない」に当たる。`<tmp>/ndf/` は承認ゲートで
人が読む資料と Skill の出力が同じ置き場にあり、最終更新から決まる寿命では答えを待つ間の資料を消しうる。5 種類とも持ち主を一覧に書き、
寿命の列に残す理由を書く。

`<tmp>/ndf/` を寿命の窓で片付ける形は採らない。承認の答えを待つ間に資料が消えると、承認する人が読む資料が無くなる。
置き場を種類ごとに分けるのは、ファイルの契約を持つ柱 P6 の仕事である。

根拠: Value 7（MVV 版 5）

### 決定 14: 持ち主の記録を通らない取り合いを黙って待たないよう、耐久の記録の排他は残し、待たない（`lock_timeout=0`）を既定にする

`durable.launch` の排他は耐久の記録（SQLite のファイル）を 1 つのプロセスだけが開くための錠で、持ち主の記録とは守る対象が違う。
持ち主の鍵を宣言した入口では持ち主の記録を先に取るため、この排他で待つことは起きない。持ち主の鍵の無い経路で取り合ったときに
`lock_timeout=None` のまま空くまで待つと、#2316 のように前の起動の後に続きとして流れる。既定を 0 にし、取れなければ `stopped`・3 で
返す。`parallel_run` のように待つ秒を渡す呼び出しはそのまま残す。

耐久の記録の排他を持ち主の部品へ置き換える形は採らない。耐久の記録の鍵（起動の種類と鍵の元）と持ち主の鍵は単位が違い、1 つの錠に寄せると
守る対象の片方を失う。

根拠: Value 3 / Value 7（MVV 版 5）
