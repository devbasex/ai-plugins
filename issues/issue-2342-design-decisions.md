## 決定の記録

### 決定 1: 2 つ目の conductor を開発ループの入口で止めるため、持ち主の単位を実行とセッションの 2 つにし、開発ループはセッションで持つ

開発ループは、1 つの conductor が別々のプロセスで副命令を打って進む（`loop start`・`loop select`・`loop sprint` など）。
持ち主の単位を入口の 1 回の実行にすると、`loop start` が終わった時点で記録が返る。
そのため、2 つ目の conductor の `loop start` を止められない（#2316）。
単位 `session` は、持ち主のプロセスをランタイムのセッションのプロセスにする（hook が今も使う祖先の探し方）。
記録は `loop stop`・`loop finish` かセッションの終わりまで持つ。同じセッションの副命令は、持ち主のプロセスが自分の祖先なので `inherited` で通る。`loop finish` は `loop start` と別の実行だが、持ち主のプロセスが同じランタイムのセッションなので返せる。

開発ループの記録（`.ndf/loop/<名>/loop.json`）に conductor のセッションを書き足す形は採らない。記録の書き手が開発ループの部品と
持ち主の部品の 2 つになる。生死の判定と排他も、開発ループの部品の中にもう 1 つできる。

根拠: Value 7（MVV 版 5）

### 決定 2: 並行の衝突が起きた単位で取り合うため、キューは done のパス、開発ループは名前を持ち主の鍵にする

#2316 で衝突したのは、同じ done を再開した 2 つのキューと、同じ名前の開発ループの同じ周回である。
鍵を done ごとにすれば、`queue <プラン>... --done X` と `queue --resume X` が同じ鍵を取り合う。別の done のキューは並べて流せる。開発ループを周回ごとにすると、
周回の切れ目で 2 つ目の conductor が入れる。パスはリポジトリの根からの相対へ正規化し、worktree の違いで鍵が割れないようにする。

キューをプランごとの鍵にする形は採らない。1 つのキューが流す複数のプランの鍵を、起動時にまとめて取ることになる。
取れた分だけで流すか全部を待つかの規則が、もう 1 つ要る。
`supervise.py run` には鍵を宣言しない。#2316 の衝突はキューの再開で起きており、`run` を直に 2 本並べた記録は無い。

根拠: Value 2 / Value 6（MVV 版 5）

### 決定 3: 旧い置き場の記録は読まない

前の版の NDF が書いた `*.owner.json` は、新しい版の取る側も片付けも読まない。
旧い記録の残りは、今の片付けがレビュー worktree を外すときに一緒に消す（`run_state.py:157`・`run_state.py:167`）。

旧い置き場を読む互換を持つ形は採らない。承認ゲート 1 の答えが範囲から外した。
読む処理を持つと、取る側と片付けの両方に旧い規則（寿命の窓だけで判定する規則）の分岐が残り、次の正式版で消す作業が要る。
外したことで残る並走の危険（旧い版と新しい版が同じ鍵を同時に取る）は、本文の「未確認のまま残ること」に書く。

根拠: Value 2 / Value 3（MVV 版 5）

### 決定 4: drive が起こす init が自分の持ち主に断られないよう、持ち主のプロセスが祖先である実行は持ち主の鍵を取り直さずに使う

cross-refactoring の `drive.py` は `refactor.py init` を子のプロセスとして起こす。
どちらも同じ鍵 `cross-refactoring:pr={pr}` を宣言する（`init` は利用者が直に打つこともあるため）。記録の持ち主のプロセス（pid と開始時刻）が自分の祖先のプロセスなら `inherited` で通る。返すのは記録の持ち主のプロセスと同じ実行だけで、`inherited` で使った子の終わりでは返さない。
祖先が持っていない鍵を子が取ったとき（プランから起こした `drive.py` など）は、その子が持ち主で、子の終わりで返す。

実行の識別子の一致（記録の `run`）で通す形は採らない。識別子は、子へ渡す経路ごとに受け渡しの漏れがある。#2321 の案内が示した `--run` も、プランから呼ぶ `drive.py` には渡す手段が無い。
プロセスの祖先は受け渡しを要らない。

根拠: Value 5（MVV 版 5）

### 決定 5: キューの再開で `--from` が勝つよう、`--from` があれば途中を子ごと止めてから耐久の記録を開く

#2325 の原因は、前の起動が途中で残っていると、`--from` があっても `durable.resolve` が `continue` を返すことである。
そのため前の入力で回復した。
`launch_queue` は、今もプランの並びが変わったとき（`fresh`）に途中の耐久ワークフローを子ごと止める（`keep=()`）。
この条件を「プランの並びが変わった、または `--from` がある」に広げる。`--from` も `--only` も無ければ今のまま前の起動を続ける。
`supervise.py run --from` は変えない。開始のステップを耐久ワークフローの接頭辞に含めており、すでに `--from` が勝つためである。

耐久の部品に再開の位置を決める関数を新しく置く形は採らない。食い違いはキューの入口の 1 か所の条件にあり、既存の `keep` で直せる。
`--from` が前の起動と変わったときだけ新しい実行の回にする形も採らない。前の `--from` を覚えておく置き場がもう 1 つ要り、判定の漏れが位置の食い違いになる。

根拠: Value 7 / Value 2（MVV 版 5）

### 決定 6: 引き取りは記録の書き直しだけにし、状態を持ち主の記録に結び付けない

死んだ持ち主を `reclaimed` で引き取るとき、持ち主の部品は自分の鍵の記録を書き直すだけにする。
死んだ持ち主が残したレビュー worktree は、入口が今と同じく作り直すか使い直す。
レビュー worktree の片付けは、今の時点と条件のまま、生死の判定だけを持ち主の部品の記録に置き換える。

状態の一覧の種類に結び付く鍵の列を足し、返した後と引き取りの中で結び付いた状態を片付ける形は採らない。
1 つのレビュー worktree の種類には、cross-review と cross-refactoring の 2 つの鍵が結び付く。そのため、複数の鍵の排他を順に取る規則が要る。
#2321 は記録の終わった時刻が書かれれば解消し、結び付きを要らない。

根拠: Value 2 / Value 3（MVV 版 5）

### 決定 7: 再開の入口は作らず、旧い再開の形を今のまま残す

#2335 の決定 15 は再開の入口（`supervise.py resume`）を置き、旧い再開の形をその別名にする。
承認ゲート 1 の答えは旧い形の別名を範囲から外した。
別名にしないまま再開の入口を足すと、再開の手段が 1 つ増えて 2 通りになる。
そのため、この柱では再開の入口を作らず、#2325 の食い違いを決定 5 のとおりキューの入口で直す。
再開の入口を求める子の課題（#1592・#1635）は残す。

再開の入口だけを足し、旧い形は後で別名にする形は採らない。再開の手段が 2 通りある期間ができ、どちらを案内するかを入口ごとに決め直すことになる。

根拠: Value 2 / Value 3（MVV 版 5）

### 決定 8: backlog-refinement の見直しの持ち主は `run_owner.py` のまま残す

見直しの持ち主（`.ndf/backlog/owner.json`）は、同じホストでも最後に動いた時刻から `depths.owner.ttl` を過ぎた宣言を別のセッションが引き取れる。
持ち主の部品へ移すと、同じホストの生死を pid と開始時刻で決める規則（I4）に入る。その結果、見直しの持ち主の振る舞いが変わる。
変える理由になる不具合は 3 件に無い。
`run_owner.py` からはレビュー worktree の持ち主の関数だけを消し、見直しの持ち主が使う関数を残す。

見直しの持ち主も同じ柱で移す形は採らない。振る舞いの変更と設定（`depths.owner.ttl`）の扱いの決定が加わり、承認ゲート 1 の答えの範囲を超える。
同じ役割の部品が `lease.py` と `run_owner.py` に分かれた状態は残る（Value 7）。移すときは、見直しの持ち主の生死の規則を決め直す変更として扱う。

根拠: Value 2 / Value 3（MVV 版 5）

### 決定 9: 持ち主の鍵を宣言する入口はすべて止まり、待つ形は作らない

持ち主の鍵を宣言する入口の持ち主は、どれも数分から数時間動く（収束ループ・リファクタリング・キュー・開発ループ）。
待つにすると、後から来た conductor が進まないまま上限まで止まる。持ち主の実行の識別子を知るのも上限の後になる。
止まって結果に持ち主の実行の識別子を出せば、conductor はその場で待つか別の仕事へ移るかを決められる。

部品と契約に待つ形だけを用意しておく形は採らない。承認ゲート 1 の答えが範囲から外した。使う入口が無い形は、テストと契約の検査だけを増やす。
同じ PR の cross-review を待つにする形も採らない。同じ PR の収束ループが 2 本並ぶのは conductor の取り違えで、待った後に流すと同じ指摘を二重に直す。

根拠: Value 3 / Value 2（MVV 版 5）
