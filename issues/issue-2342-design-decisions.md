## 決定の記録

### 決定 1: 2 つ目の conductor を開発ループの入口で止めるため、持ち主の単位を実行とセッションの 2 つにし、開発ループはセッションで持つ

開発ループは、1 つの conductor が別々のプロセスで副命令を打って進む（`loop start`・`loop select`・`loop sprint` など）。
持ち主の単位を入口の 1 回の実行にすると、`loop start` が終わった時点で記録が返る。
そのため、2 つ目の conductor の `loop start` を止められない（#2316）。
単位 `session` は、持ち主のプロセスをランタイムのセッションのプロセスにする（hook が今も使う祖先の探し方）。
記録は `loop stop`・`loop finish` かセッションの終わりまで持つ。同じセッションの副命令は、持ち主のプロセスが自分の祖先なので `inherited` で通る。`loop finish` は `loop start` と別の実行だが、持ち主のプロセスが同じランタイムのセッションなので返せる。

開発ループの記録（`.ndf/loop/<名>/loop.json`）に conductor のセッションを書き足す形は採らない。記録の書き手が開発ループの部品と
持ち主の部品の 2 つになり、生死の判定と排他が開発ループの部品の中にもう 1 つできる。

根拠: Value 7（MVV 版 5）

### 決定 2: 前提 3 の入口はすべて止まる（`stop`）にし、待つ（`wait`）は部品と契約の形だけを持つ

前提 3 の入口の持ち主は、どれも数分から数時間動く（収束ループ・リファクタリング・キュー・開発ループ・見直し）。
待つにすると、後から来た conductor が進まないまま上限まで止まる。持ち主の実行の識別子を知るのも上限の後になる。
止まって結果に持ち主の実行の識別子を出せば、conductor はその場で待つか別の仕事へ移るかを決められる。
待つは、部品と契約の形とテスト用の契約のテストだけを持つ。短い排他の区間を持つ入口が、後から宣言できるようにするためである。待つ上限の値は前提 5 のとおり契約の一覧に置く。

同じ PR の cross-review を待つにする形は採らない。同じ PR の収束ループが 2 本並ぶのは conductor の取り違えである。
待った後に流すと、同じ指摘を二重に直す。

根拠: Value 3 / Value 2（MVV 版 5）

### 決定 3: 並行の衝突が起きた単位で取り合うため、キューは done のパス、`run` はプランのパス、開発ループは名前を持ち主の鍵にする

#2316 で衝突したのは、同じ done を再開した 2 つのキューと、同じ名前の開発ループの同じ周回である。
鍵を done ごとにすれば、`queue <プラン>... --done X` と `queue --resume X` が同じ鍵を取り合う。別の done のキューは並べて流せる。開発ループを周回ごとにすると、
周回の切れ目で 2 つ目の conductor が入れる。パスはリポジトリの根からの相対へ正規化し、worktree の違いで鍵が割れないようにする。

キューをプランごとの鍵にする形は採らない。1 つのキューが流す複数のプランの鍵を、起動時にまとめて取ることになる。
取れた分だけで流すか全部を待つかの規則が、もう 1 つ要る。

根拠: Value 6（MVV 版 5）

### 決定 4: drive が起こす init が自分の持ち主に断られないよう、持ち主のプロセスが祖先である実行は持ち主の鍵を取り直さずに使う

cross-refactoring の `drive.py` は `refactor.py init` を子のプロセスとして起こす。
どちらも同じ鍵 `cross-refactoring:pr={pr}` を宣言する（`init` は利用者が直に打つこともあるため）。記録の持ち主のプロセス（pid と開始時刻）が自分の祖先のプロセスなら `inherited` で通る。返すのは記録の持ち主のプロセスと同じ実行だけで、`inherited` で使った子の終わりでは返さない。
祖先が持っていない鍵を子が取ったとき（プランから起こした `drive.py` など）は、その子が持ち主で、子の終わりで返す。

実行の識別子の一致（記録の `run` と `NDF_RUN_ROOT`）で通す形は採らない。再開の入口は前の実行の識別子を引き継ぐため（決定 8）、前の実行が生きているうちの再開も通り、持ち主が 2 つになる。

今の `--run <実行の識別子>` を init へ渡す形は採らない。#2321 のとおり、プランから呼ぶ `drive.py` には渡す手段が無い。
案内が、打てない手段を示すことになる。

根拠: Value 5（MVV 版 5）

### 決定 5: 旧い再開の形が前の実行を引けるよう、持ち主の記録は返しても消さず、鍵ごとの最後の実行の索引にする

旧い形（`run <plan> --from`・`queue --resume <done>`・`drive.py <PR> --reopen`）は実行の識別子を持たない。
プラン・done・PR で前の実行を指す。
これは持ち主の鍵と同じ単位なので、鍵の記録の `run` を引けば再開の入口へ渡す識別子が決まる。記録は終わった時刻から 30 日で片付ける
（耐久の記録と実行の記録の寿命と同じ）。

旧い形のために鍵から実行の識別子への索引を別に置く形は採らない。同じ単位の記録が 2 つになり、片方だけが更新されたときにどちらが正かが決まらない。

根拠: Value 8（MVV 版 5）

### 決定 6: 持ち主の記録が実行の識別子と時刻とプロセスだけを持つよう、結び付きは状態の一覧の列で静的に宣言する

受け入れ条件 12 は、持ち主の記録が持つものを実行の識別子・入口・鍵・時刻・pid と開始時刻・ホスト名に限る。
状態の一覧の種類に列 `lease`（鍵の形）を足す。返した後に、片付けが鍵の値から置き場を導ける（例 `cross-refactoring:pr=2318` → `<base>/<slug>/rf2318`）。
実行中に作った状態を記録へ登録する仕組みは要らない。

持ち主の記録に結び付いた状態のパスの並びを持たせる形は採らない。受け入れ条件 12 の範囲を超え、子の実行が書き足すたびに記録の排他を取り合う。

根拠: Value 8 / Value 5（MVV 版 5）

### 決定 7: 自分でプロセスグループを抜けた子孫も打ち切りで止めるため、プロセスの子孫と根の実行の印を持つプロセスの両方を止める

#2285 で残った偽の claude は、テストが自分で `start_new_session=True` を付けて起こしたもので、プロセスグループを止めても届かない。
止める直前に `psutil` で子孫を読む。加えて、同じユーザーのプロセスのうち環境変数 `NDF_RUN_ROOT` が根の実行と同じものを止める。
親を失って子孫の木から外れたプロセスも、環境変数は受け継いでいるため拾える。既存の `procs.stop_tree` の順（SIGTERM、猶予の後に SIGKILL）を使う。

cgroup で実行を囲む形は採らない。配布先のコンテナと CI で cgroup を作る権限があるとは限らず、どのリポジトリでも動く形を保てない。

根拠: Value 6 / Value 7（MVV 版 5）

### 決定 8: 再開の入口が入口ごとの引数を知らずに済むよう、実行の記録の始まりの行から入口と入力を組み直し、入口を子として起こす

実行の記録（柱 P2）は始まりの行に入口の id を、`input` の行に入力ごとの名前・出所・値を持つ。
再開の入口はそれを読んで、同じ入力で入口を起こす。`NDF_RESUME`（引き継ぐ実行の識別子）と `NDF_RESUME_FROM` を付ける。
入口の核は引き継いだ識別子で実行を始める。持ち主の記録の取り合いも、通常の起動と同じ経路を通る。秘密の入力は記録に値が無いため、出所の環境変数から読み直す。

再開の入口が入口の関数を同じプロセスで呼ぶ形は採らない。耐久の記録はプロセスに 1 つしか開けない（`durable.launch`）。
また、入口ごとの副命令の引数の組み立てを、再開の入口が持つことになる。

根拠: Value 5 / Value 7（MVV 版 5）

### 決定 9: `--from` が常に勝ち、位置の出所が 1 つになるよう、`--from` があれば途中を子ごと止めて新しい実行の回で始め、キューの続きも耐久の記録から読む

#2325 の原因は、前の起動が途中で残っていると、`--from` があっても `durable.resolve` が `continue` を返すことである。
そのため前の入力で回復した。
`durable.resume_ref(prefix, resume)` は `--from` があれば、`launch` の前に接頭辞の途中の耐久ワークフローを子ごと止める（`keep=()`）。
そのうえで新しい実行の回を返す。`--from` が無ければ `resolve` のとおり続ける。
キューの止まったプランの続きの位置は、前の実行の回の各プランの耐久ワークフローの出力（止まったステップ）から読む。done と `progress.jsonl` からは決めない。

`--from` が変わったときだけ新しい実行の回にする形は採らない。前の `--from` を覚えておく置き場がもう 1 つ要る。
#2325 の `fresh` の判定と同じく、判定の漏れが位置の食い違いになる。

根拠: Value 7（MVV 版 5）

### 決定 10: 旧い版との並走で排他が抜けないよう、旧い置き場の記録は読むだけにし、書かない

前の版の NDF が書いた `*.owner.json` と `.ndf/backlog/owner.json` は、新しい版の取る側と片付けが読む。
旧い規則で生きていれば使用中として扱う。
新しい版は旧い置き場へ書かない。読む処理は、この柱を含む正式版の次の正式版で消す。

旧い置き場へも二重に書く形は採らない。書き手が 2 つの置き場を同時に更新する経路ができ、片方の書き込みの失敗で記録が食い違う。

根拠: Value 7（MVV 版 5）

### 決定 11: 配布の承認資料が版ごとに溜まらないよう、状態の一覧の種類にし、配布のプランの後片付けのステップが外す

配布の承認資料（`issues/approval-<plugin>-v<版>.md`）は配布のプランが書き、承認ゲート 2 の答えを待つ間に読まれる。
後片付けのステップに達した時点で承認は済み、記録は Pull Request とリリースに残る。
種類 `approval-doc` を状態の一覧に載せる。後片付けのステップが、`run_state` を通してそのプランの承認資料を外す。後片付けに達しなかったプランの承認資料は残す。

持ち主の記録に結び付ける形は採らない。承認資料の置き場は配布のプランの入力から導けず、決定 6 の静的な結び付きに載らない。

根拠: Value 5（MVV 版 5）

### 決定 12: #1886 は入力の解決の問題として柱 P8 へ渡し、この柱では残す

#1886 は、キューの後片付けが起動した worktree を消した後、次のプランの計画が `Path.cwd()` を読んで落ちる不具合である。
持ち主の記録を取っても worktree は消える。`cwd` を読む箇所（`decl.py`・`commands.py`・`sprint.py`・`templates.py`・`actuals.py`）も変わらない。
リポジトリの根を起動時に 1 度解決して実行の文脈に持たせるのは入力の部品（柱 P8 #2341）の責務である。

この柱で worktree の片付けを持ち主の生存で止める形は採らない。後片付けは worktree を消すステップそのものである。
止めると後片付けが働かなくなる。

根拠: Value 7（MVV 版 5）

### 決定 13: #2243 の 5 種類は、退避先の 4 種類と承認ゲートの資料の置き場を残す理由つきで一覧に載せる

`ndf-stages`・`ndf-checks`・`ndf-usage` は状態の置き場が書けないときの退避先で、中身は通過記録・検査の事象・使用量の帳簿である。
一時の片付けで消すと記録が失われる。`ndf-guards` は hook が作る状態で、hook は #2335 の「含まない」に当たる。
`<tmp>/ndf/` は、承認ゲートで人が読む資料と Skill の出力が同じ置き場にある。最終更新から決まる寿命では、答えを待つ間の資料を消しうる。
5 種類とも持ち主を一覧に書き、寿命の列に残す理由を書く。

`<tmp>/ndf/` を寿命の窓で片付ける形は採らない。承認の答えを待つ間に資料が消えると、承認する人が読む資料が無くなる。
置き場を種類ごとに分けるのは、ファイルの契約を持つ柱 P6 の仕事である。

根拠: Value 7（MVV 版 5）

### 決定 14: 持ち主の記録を通らない取り合いを黙って待たないよう、耐久の記録の排他は残し、待たない（`lock_timeout=0`）を既定にする

`durable.launch` の排他は、耐久の記録（SQLite のファイル）を 1 つのプロセスだけが開くための錠である。持ち主の記録とは守る対象が違う。
持ち主の鍵を宣言した入口では持ち主の記録を先に取るため、この排他で待つことは起きない。
持ち主の鍵の無い経路で取り合ったときに `lock_timeout=None` のまま空くまで待つと、#2316 のように前の起動の後に続きとして流れる。
既定を 0 にし、取れなければ `stopped`・3 で返す。`parallel_run` のように待つ秒を渡す呼び出しはそのまま残す。

耐久の記録の排他を持ち主の部品へ置き換える形は採らない。耐久の記録の鍵（起動の種類と鍵の元）と持ち主の鍵は単位が違う。
1 つの錠に寄せると、守る対象の片方を失う。

根拠: Value 3 / Value 7（MVV 版 5）

### 決定 15: 生死の判定を 1 つの規則にするため、見直しの持ち主も同じホストでは寿命の窓を使わず、窓の値は契約の 900 秒に固定する

前提 6 は、同じホストの生死を pid と開始時刻で決め、寿命の窓を別のホストの実行にだけ使う。見直しの持ち主もこの規則に入れる（I4）。
これは見直しの持ち主の振る舞いの変更である。今の見直しの持ち主は、同じホストで pid が生きていても、最後に動いた時刻から `depths.owner.ttl`（既定 900 秒）を過ぎた宣言を別のセッションが引き取れる。
この柱の後は、単位 `session` の記録を、`release: true` の副命令（見直しの持ち主では `upkeep.py owner release`）を打つか、持ち主のランタイムのセッションが終わるまで持ち続ける。
`owner release` は見直し・大整理の成否によらず通すステップなので、見直しを終えた conductor は鍵を返す。途中で止まったままセッションを開いて放置した conductor がいると、ほかのセッションの見直しは `refused`・3 で止まり続ける。
止まった側の結果には持ち主の実行の識別子・pid・最後に動いた時刻が出る（入出力の契約）。持ち主の pid は利用者のランタイムのセッションなので、conductor は止めずに、`refused` の理由と pid を添えて人へ戻す。セッションを閉じるかどうかは人が決める（共通原則の C4）。

窓の値は契約の 900 秒に固定し、`.ndf/backlog.json` の `depths.owner.ttl` を持ち主の部品へ渡さない。
適用範囲のとおり持ち主の部品はプロジェクトの `.ndf/` を読まず、呼ぶ側が読んで宣言へ渡す経路を作ると、`.ndf/` を読む入口と読まない入口に分かれる。
窓を使うのは別のホストの記録と旧い置き場の記録だけなので、値を固定しても同じホストの判定は変わらない。

同じホストでも窓を過ぎた見直しの持ち主を死んだとみなす例外は採らない。生きた持ち主から記録を引き取ると、同じ鍵を生きた持ち主が 2 つ持つ（I1）。

根拠: Value 7 / Value 6（MVV 版 5）
