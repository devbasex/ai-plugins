## 目的

pytest などのテストが作業マシンの CPU とメモリを使いつぶし、OOM Killer が本体やテストを落とす事態を防ぐ。レーンがいくつあっても重い処理の同時実行が上限に収まり、足りないときは OOM Killer より先に NDF が待つか止める状態にする。

## 前提

- 前提 1: 使いつぶしの主因はテストの同時実行である。枠を入れた後もメモリで止まる回数が減らなければ、この前提が誤っていたと判定し、別の課題で原因を切り分ける
- 前提 2: 対象は作業マシンの上で動く NDF の実行であり、GitHub Actions の CI は 1 ジョブが 1 台を占めるため枠の対象にしない
- 前提 3: 人がシェルで直接打ったテストは枠に数えない。AI の実行を止める手段（hook）が届かないためである。人の実行が使うメモリは、使えるメモリの実測を通じて受け入れ条件 10・11 の判定に入る
- 前提 4: AI の Bash の実行を枠に入れる対象は Claude Code と Codex の 2 つである。Kiro と agy は相手役として起動するだけで、配らないため hook が届かない

## 対象範囲

含む:
- `test-run.py`・cross-refactoring の全体テスト・AI の Bash の直接の実行の 3 つの経路で、テストの同時実行を上限に収めること
- 起動の前と実行の間に使えるメモリを見て、待つか止めること
- 待った・止めたことの記録と、それを読むコマンド

含まない:
- CPU・メモリ・ストレージの常時の監視と、conductor へのアラート（#2710）
- ファイルとボリュームの後片付け（#2600・#2660）
- 全体テストそのものを軽くすること（#2291）、打ち切りの後に残る子プロセスの停止（#2291 の本文に記載）
- テストの揺れの修正（#1967・#2093）
- 止めたテストの自動の走らせ直し
- テスト環境のコンテナ（`worktree-testenv.sh`）のメモリ上限
- CI の `-n auto` の変更

## 用語

| 用語 | 意味 |
| --- | --- |
| 作業マシン | NDF の作業を動かす 1 台のマシン。同じカーネルとメモリを共有する範囲を指し、手元のマシンと開発コンテナの基盤のホストを含む。Factory のプログラムである「ランナー」とは別 |
| 重い処理 | 作業マシンの CPU とメモリを多く使うテストの実行。宣言のテストのコマンドによる全体テストと、並列の指定を持つ範囲テストを指す。静的解析は含まない |
| テストの枠 | 1 台の作業マシンで同時に走らせてよい重い処理の本数の上限と、その数え方 |
| メモリの下限 | 使えるメモリがこの値を割ると、重い処理を始めず、動いているものを止める境の値 |

## 受け入れ条件

テストの枠:

- [ ] 1. 前提: 上限を 2 にした作業マシンで、別々の worktree から全体テストを 4 本同時に起動する。結果: 同時に動くのは常に 2 本以下で、4 本とも最後まで走る
- [ ] 2. 前提: 上限を 1 にする。操作: `test-run.py`、cross-refactoring の全体テスト、AI の Bash の直接の実行（Claude Code と Codex）の 3 つの経路から 1 本ずつ同時に起動する。結果: 同時に動くのは常に 1 本で、並列の計画のレーンか単独の開発ループかで数え方が変わらない
- [ ] 3. 設定が無いとき、CPU 8 個・メモリ 30 GiB の作業マシンで `-n 4` の全体テストは同時に 2 本までに収まる。CPU かメモリの片方を半分にした入力では上限が下がり、1 を下回らない
- [ ] 4. プロジェクトの設定で上限・メモリの下限・待ちの上限を変えられる。0 以下や数値でない値は、テストを走らせず、設定の誤りと直す箇所を示して止まる
- [ ] 5. 並列の指定を持たない 1 ファイルの範囲テストは、上限に達していても枠を待たずに走る
- [ ] 6. 上限が 1 でも、枠を持つ実行の中から起動されたテスト（テストのテスト）は枠を取らず、待ちで止まらない
- [ ] 7. 枠を持つ実行を SIGKILL で止めると、待っていた実行が 10 秒以内に始まる
- [ ] 8. 枠とメモリの待ちはテストの時間の上限に数えず、全体テストの実測にも含めない。待った秒は結果の JSON に載る
- [ ] 9. 待ちの上限を超えると、テストを走らせず終了コード 2 で返し、`summary` に待った秒と理由が載る。変更起因の失敗に数えない

メモリ:

- [ ] 10. 使えるメモリが下限を割っているとき、テストは始まらずに待ち、下限を回復すると始まる
- [ ] 11. 実行中に使えるメモリが下限を割ると、動いているテストのうち最後に始めた 1 本をプロセスグループごと止め、終了コード 2 で「メモリが足りず止めた」と返す。conductor・ラッパー・supervisor は動き続け、変更起因の失敗に数えない
- [ ] 12. 使えるメモリを測れない環境（読めるファイルが無いなど）では、テストは始まり、記録に「測れない」と残る

記録:

- [ ] 13. 待った・止めた・諦めた実行ごとに、時刻・worktree・テストの種別・待った秒・使えるメモリ・結果が作業マシンの記録に 1 行残る
- [ ] 14. 1 つのコマンドで、指定した期間の「待った回数と合計秒・メモリで止めた回数・諦めた回数・OOM Killer の回数の増分」が JSON で読める

退行しないこと:

- [ ] 15. 枠の下でもテストのコマンドの出力と結果は変わらず、`test-run.py` は通ると 0、落ちると 1 を返す
      前提の確認: 一時リポジトリの `test-run.py scope` で 0 と 1 を確かめた（調べて分かったことの表）
- [ ] 16. pytest 以外の宣言のテストのコマンド（`.ndf/project.json` の `factory` の vitest）も同じ枠に入り、コードにリポジトリ固有のコマンドを持たない
- [ ] 17. `.github/workflows/` のテストのコマンドに差分が無い

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 待ちが起きないとき、枠の処理がテストの開始へ足す時間は 1 秒以内 |
| 運用・保守性 | 記録は直近 30 日か 10,000 行で古い方から消え、際限なく増えない |
| システム環境 | Linux と macOS で動く。macOS で使えるメモリを測れない項目は受け入れ条件 12 に従う |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。プロジェクトの設定にキーが増え、結果の JSON に項目が増える。既存のキーと項目は変えず、互換を保つ |
| データ | 作業マシンの状態の置き場に記録が増える。リポジトリの形式の移行は無い |
| 既存の振る舞い | 同時に走るテストは待つようになり、工程の経過時間が延びることがある。設定の無いリポジトリでも既定の上限が効く |
