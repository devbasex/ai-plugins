## 何が起きたか

2026-11-19、利用者は設計 Pull Request [#3866](https://github.com/devbasex/ai-plugins/pull/3866) を設計承認ゲートで読み、「結局のところ何が課題で何をしようとしているのかさっぱりわからない」と書いた。#3866 は、計画 p8-5（同じリポジトリで複数の開発の流れ（レーン）を同時に進める計画）のレーンの 1 つが出した PR で、3 つの小さな直し（#3851 #3856 #3854）を 1 本にまとめ、要求仕様 3 本・設計文書 488 行・詳細設計 268 行・合わせて 1,290 行を足していた。

たとえば #3856 の要求仕様（[issue-3856-requirements.md](https://github.com/devbasex/ai-plugins/blob/main/issues/issue-3856-requirements.md)）は、冒頭が「起票者の推定」の表で、その次の「事象」が「規則 15」「文脈のキー」「`stage-out`」を説明なしに使う。#3856 が直す仕組み（工程の出力の JSON を conductor が確かめる流れ）を知らない人は、1 段落目で読むのをやめる。

利用者の補足（同日）:

- 「最初に結論」だけが絶対的なルールではない。文書ごとにどう書くべきかを考えてから直す
- 機能追加や不具合の直しが、これまでその機能を担当していた人に割り当てられるとは限らない。読み手はその機能を初めて見る人である

## 種類

機能追加（今ある 5 つの文書の Skill とテンプレートの書き方を変える）

## 今の姿

NDF は、変更を実装する前に 5 つの文書を AI に書かせ、人が設計承認ゲートで読む。書き方は文書ごとの Skill とテンプレートが決めている。

| 文書 | 書く Skill とテンプレート | 今の書き方 |
| --- | --- | --- |
| 要求仕様 | `requirements-design`（[spec-template.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/requirements-design/references/spec-template.md)） | 起票者の推定 → 目的 → 事象・期待する結果・再現手順・環境（不具合のとき）→ 前提 → 対象範囲 → ドメインイベント → 用語 → 受け入れ条件 → …の 18 セクション。Issue の種類（不具合・機能・調査・運用）で要るセクションを削る |
| 設計文書 | `design`（[design-template.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/design/references/design-template.md)・[deliverables.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/design/references/deliverables.md)） | 目的 → 適用範囲 → 目指す姿 → 根拠 → ドメインモデル → 外部の調査 → 機能一覧 → … → 未確認の 30 を超えるセクション。`standard`（要求・設計・実装を通常の工程で通すモード）では 15 の成果物が「必須」 |

| 開発計画 | `issue-plan-strategy`（[execution-plan.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/issue-plan-strategy/references/execution-plan.md)・[parallel-plan.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/issue-plan-strategy/references/parallel-plan.md)） | 実行計画（スプリントの課題の表）と並列の計画（レーンの一覧） |

書いた文書は `document-rebuild` が組み直し、最後に読み手役（会話の文脈を持たない AI）に読ませる（[SKILL.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/document-rebuild/SKILL.md) の「読み手役に読ませる」）。読み手役は要点を言い直し、分からなかった語を返すが、「課題と解決を自分の言葉で言えたか」で合否を決めてはいない。

## 何を足すか・変えるか

| | 今 | 変えた後 |
| --- | --- | --- |
| セクションの並び | テンプレートが書く順で並ぶ。どの文書も同じ語彙と密度 | 読み手が、その文書で下す判断に要る順に読める。変更の種類（新規作成・機能追加・不具合）に合った事柄が中心にある |
| 当たらないセクション | 「無し」「省く:」と書いて残る | 読み手が、書くことの無いセクションを読まない |
| 3 つの文書の関係 | 同じ事実を粒度を変えて繰り返す | 読み手が、同じ事実を 2 度読まない |
| 分量 | 小さな直しでも要求・設計・詳細設計がそろい、1,000 行を超える | 文書の量が変更の大きさに見合う |
| 読み手役の確認 | 要点の言い直しと分からなかった語を返す | 初めて読む人が課題と解き方を言えるかが、承認の前に分かる |

## なぜ困るか

設計承認ゲートは、人が中身を読んで「この問題をこの解き方で解いてよいか」を決める唯一の場所である。読めない文書では、承認する人は読まずに承認するか、差し戻すしかない。#3866 は前者の危険を、別のレーン（lrelay）の設計 PR [#3867](https://github.com/devbasex/ai-plugins/pull/3867) は後者（「書き方を是正してから」と差し戻された）を示した。テンプレートを直さない限り、同じ文書が設計のたびに作られる。

課題の本文の 2026-11-19 の考察が、原因を 8 つに分けている（下の「リクエスト（原文）」の「実物で見えた原因」）。まとめると、テンプレートのセクションが「書く順」で並び、文書ごとの読み手と判断が決まっておらず、今の姿を知らない読み手を想定していない。

## 目的

- 5 つの文書それぞれで、読み手・読み手が下す判断・読み方が決まり、テンプレートのセクションがその判断の順に並ぶ
- 変更の種類（新規作成・機能追加・不具合）ごとに、文書の中心に置くものが決まる。どの種類も今の姿を最初に置く
- 当たらないセクションは消え、3 つの文書が同じ事実を言い直さない。分量が変更の大きさに合う
- 読み手役の確認が、読めたかどうか（課題と解き方を自分の言葉で言えたか）を見る

## 対象範囲

含む:

- 5 つの文書（要求仕様・設計書・詳細設計書・実装計画・開発計画）を書く Skill とテンプレート、`document-rebuild` の読み手役の確認、種類ごとの書き直しの例 3 本

含まない:

- `documentation`（業務文書を作るモード）の 6 つの文書タイプと、`legacy-refactor`（振る舞いを変えずに構造を直すモード）・`operation`（外部の系を操作するモード）の書き方を作り直す。新しい表と重なる所だけを、表を指す形にそろえる
- 過去の要求仕様・設計文書を書き直す（例として書き直す 3 本を除く）
- 承認ゲートの数と、設計承認ゲートで承認資料に載せる項目の種類を変える

- [ ] 3. 要求仕様と設計書のテンプレートが、どの種類でも今の姿（新規作成では「今はどうしているか」）から始まり、2 の表のセクションの順序で並ぶ

- [ ] 6. `document-rebuild` の読み手役の確認が、要求仕様なら課題と終わりの条件を、設計書なら解き方と捨てた案を、読み手役が自分の言葉で言えたかで合否を決める。言えなければ書き手が直して 1 回だけ読み直させ、それでも食い違えば報告に残す
- [ ] 7. 変更の種類ごとに 1 つ、書き直した例（前と後）がある（不具合: #3856、機能追加: #3854 か #3846、新規作成: 過去の課題から 1 つ）。利用者が設計承認ゲートで例を読み、課題と解き方を言える（言えなければ、利用者が変更を要求し、例とテンプレートを直す）
- [ ] 8. 退行しない: コードが読む見出し（要求仕様の「種類」と「影響」の表の「公開インタフェース」の行、設計文書の「設計の結果」の 4 列の表）が残り、承認資料（[approval-request.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/approval-request.md)）が載せる項目の出所が新しいテンプレートのセクションを指す。リポジトリの検査（`python3 scripts/check-skill-frontmatter.py` と CI）が通る

> ## 変更の種類による違い（2026-11-19 の利用者の補足と考察）
>
> **前提: 読み手は、その機能を初めて見る人である。** 機能追加や不具合の直しが、これまでその機能を担当していた人に割り当てられるとは限らない（利用者の指摘）。どの種類の文書も、読み手が今の機能を知っていると仮定しない。種類で変わるのは「読み手が知っていること」ではなく、**文書の中心に何を置くか**である。

> - 今回の話に要る用語と構成要素だけ（全体を言い直さない。足りない分はリンク先で読める）
>

> - 詳細設計書: 要る（作るものが多い）
> - 終わりの確かめ: 場面ごとに使えること
>
> **機能追加**（ある機能を広げる・変える）
> - 中心: 今の姿 → 何を足すか・変えるか（前と後を並べる）→ 今の利用者への影響と互換
> - 設計書: 変更の部分を詳しく書く。どこに足すか、変わる入出力の形、既存の決定との関係。今の構造は、変更の位置が分かる範囲で図に示し、全体の説明は正本へリンクする
> - 詳細設計書: 変更が大きいときだけ
> - 終わりの確かめ: 足した振る舞いが動き、今の振る舞いが壊れないこと
>
> **不具合**（期待と違う振る舞いを直す）
> - 中心: 今の姿（本来どう動くはずか、その根拠の正本）→ 起きたこと（コマンドと出力）→ 再現の手順 → 影響と重さ・環境
> - 設計書: 根本原因（どの部品で何が起き、なぜ検査で拾えなかったか）を、今の姿の上に示す。どこで直すか（症状か原因か）と同じ形の箇所。小さければ要求と 1 本にまとめる
> - 詳細設計書: 多くは不要
> - 終わりの確かめ: 再現の手順で起きないこと・再発を防ぐテスト
>
> - 種類は NDF のモード（`standard` など）とは別の軸である。`standard` には 3 種類とも入る。`documentation` の 6 つのタイプと同じく、テンプレートを選ぶ軸として持つ
> - 1 本の課題に 2 種類が混ざる（不具合の直しに機能追加が付く）ときは、主の種類のテンプレートで書き、従の部分を節で足す
> - 構造だけを変える変更（`legacy-refactor`）と外部の系の操作（`operation`）は、既にモードが別の書き方を持つので、この 3 種類に含めない。重なりがあれば設計で整理する
> - 読み手役の確認は、その機能を知らない読み手（前の文脈を持たない AI）で行う
>
