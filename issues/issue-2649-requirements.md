## 目的

- 並列の計画のオーガナイザーが、レーンの実際の状態と違う問いを出さず、止まったレーンを見落とさない状態にする
- 誤った問いの実例: 起動した直後の一時レーンへの「途中で止まった」3 件（#2629）、実際より長い「355 分動いていない」（#2585）
- 見落としの実例: 3 本のレーンの開発ループが止まったのに約 2 時間どの問いも来なかった（#2477）
- 誤った問いに「止める」と答えるとリリースを失敗で締めてしまうため、誤報は人の時間だけでなくリリースも損なう

## 前提

- 前提 1: 課題の本文の「今の状態」のとおり、一覧の失敗の扱いと起動の直後の確かめはコードに入っている。確かめた結果（2026-11-06、コミット 9f40de6a5）: `uv run --frozen --project . --all-extras pytest plugins/ndf/scripts/tests/test_parallel_run.py plugins/ndf/scripts/tests/test_relay_hub.py plugins/ndf/scripts/tests/test_parallel_answer.py -q -n 4` → 149 件が通過。`test_a_long_ls_failure_raises_one_question_per_limit`・`test_process_session_gone_after_launch_is_refused_and_not_registered` を含む
- 前提 2: 通常のレーンの状態の読み方に、今の起動の照合を足さない。`step_spawn` が返った後はセッションが残っており、一覧はラッパーの起動を待つ間も `running` と答える（`hub_client.py` の `pending`）。そのため古い `stopped` の行を読む隙間が無い。隙間があるのは、起動の指示から実際の起動までに人の手順が挟まる一時レーンだけである（#2629 の実例はすべて一時レーン）
- 前提 3: 一覧の時刻が入力待ちのまま 1 時間ごとに進む現象（#2477）は、2026-11-06 の手元では再現していない。確かめた結果: 同日 20:32 UTC に `relay.py ls` を打つと、承認待ちの `factory1` の時刻は 16:14 UTC のままで、4 時間以上進んでいなかった（入力待ちの実物 1 本の観測で、ループを終えたレーンそのものではない）。更新元が特定できないまま判定の基準を変えると、長い前景のコマンドを待っているレーンまで問いになる。よって開発ループの記録を読む経路で見落としを塞ぎ、時刻の更新元の特定はこの課題で扱わない
- 前提 4: 動いていない時間の区切りは、今の `stall_seconds()`（既定 60 分。`NDF_PARALLEL_STALL_MINUTES`）を使う。#2505 の決定どおり値を変えない
- 前提 5: 問いの種類を増やさない。開発ループが止まったことの問いも `kind: stall` で出す。選択肢（起こし直す / 止める / 待つ）がそのまま当てはまり、`parallel_answer.py` と手順書の分岐を増やさずに済むためである
- 前提 6: 取り下げた問いへの答えは、#2617 で入った保留と警告の経路に乗る。確かめた結果: `parallel_answer.py` の `owner_restart` は一覧に無い依頼に 1 行を返さず、`answer` は警告を返す（コードを読んで確かめた。実行は実装のテストで行う）

## 対象範囲

含む:
- 一時レーンの途中停止の問いが、今の起動より前の行と、届く途中の依頼で誤って出ないこと
- 停滞の問いの経過の数え方、添える情報、問いの取り下げ
- 開発ループが止まったのに一覧が `running` のレーンを問うこと
- 動いている計画が新しい版で再開しても、耐久ワークフローの記録が壊れないこと
- この課題にまとめた 5 課題（#2509 の受け入れ条件 1〜4・#2585・#2629・#2477・#2563）の再現の確かめと結果の記録

含まない:
- 一覧の時刻を更新している元の特定と、時刻の意味の変更（前提 3）
- 区切りの 60 分の変更（#2505）
- 持ち主の記録によるレーンの生死の判定（#2342）
- 統括役の版のバージョンディレクトリが消える問題（#2583 の受け入れ条件 1。#2647）
- 手で起動したラッパーから問いがオーガナイザーへ届くか（#2563 の末尾）。統括役を通す起動が直ったため手で起動する理由が減る。確かめた結果は受け入れ条件 20 で #2563 に書く
- `finished` で終わった計画の戻り方（#2509 の S6）

## 用語

| 用語 | 意味 |
| --- | --- |
| 今の起動 | 一時レーンでは、耐久ワークフローが最後に指示した起動。通常のレーンでは、ラッパーが最後に起動した回 |
| レーンの再起動 | 止まった、または動かないレーンを `relay.py restart` で起動し直すこと。問いの選択肢の「起こし直す」がこれに当たる |
| 停滞の問い | 動かないレーンについて耐久ワークフローが立てる問い（`kind: stall`） |
| 途中停止の問い | リリースの途中で止まった一時レーンについて耐久ワークフローが立てる問い（`kind: helper`） |
| 問いの取り下げ | 耐久ワークフローが、答えを待たずに自分の問いを問いの一覧から外すこと |

## 束 C（軸の外）: レーンの生死を一覧の 1 行（state・at）だけで決め、成否・起動の回・進みを照合しない

**根本原因。** オーガナイザーの耐久ワークフローも統括役も、レーンが動いているかを `relay.py ls` の行の `state` と `at` だけで判定する。
一覧の失敗、今の起動より前の行、起動した直後に死んだセッション、入力待ちで残った claude を区別しない。

**場所。**
- `plugins/ndf/scripts/lib/parallel_run.py:145-153`（`step_observe`: `relay` の終了コードを `_` で捨て、失敗でも空の行を返す → 全レーンを stopped と読む。#2509）
- `plugins/ndf/scripts/lib/parallel_run.py:705-720`（`_ask_stalls`: 最後の `at` からの分を数え、起こし直しの試みと結果を見ない。#2585・#2477）
- `plugins/ndf/scripts/lib/parallel_run.py:723-738`（`_ask_helper`: 行の stopped が `run.launch` より前かを見ない。#2629）
- `plugins/ndf/scripts/relay_lib/hub.py:434-449`（`launch`: `tmux.new_session` の後にセッションが残るかを見ずに started を返す。#2563・#2583 の受け入れ条件 2）
