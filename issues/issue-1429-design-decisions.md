# #1429: 決定の記録

調査 `issues/backlog-prioritization-survey-2026-09-28.md` の 5 章の論点 0〜8 を 1 つずつ決める。要求（`issues/issue-1429-requirements.md`）の前提はここを指す。設計文書（`issues/issue-1429-design.md`）はこの決定を引き継ぐ。決定 9〜18 は設計の決定、決定 19〜23 は利用者の決定で、要求の「未決」の 4 つ（宣言のファイル名とキー・説明の長さと表の切り方・入出力の形・アンカーの校正の起票の時期）はそこで決まる。

決めた日: 2026-09-28。人へ問わずに決めた（利用者の前提は 2026-09-28 の指示: マイルストーンの間＝プロダクトバックログ、マイルストーンの中＝スプリントバックログの候補の並び、層をまたいだ逆転は論点 0b の案 B で解く）。

## 決定 0: 2 層の対応づけは案 A（推奨を採る）

マイルストーンの中の順位を「スプリントバックログの候補」と呼び、次のスプリントはその先頭から容量の分を切り出す。確定したスプリントバックログはスプリントの目録（`sprint.json`）が持つ。全体の順序は「マイルストーンの順 → マイルストーンの中の順位」の辞書順で読み、これをプロダクトバックログと呼ぶ。「プロダクトバックログ」「スプリントバックログの候補」は用語集へ足す。

理由: 利用者の前提と一致し、#1407 の用語集の「スプリントはマイルストーンから切り出す」を変えずに済む。マイルストーン 26 のように 1 本から何十ものスプリントを出すマイルストーンでも成り立つ。案 B（直近だけ並べる）は、前倒しの規則（決定 0b）が後ろのマイルストーンの遅延コストを要するため、全件の採点と両立しない。案 C（1 マイルストーン＝1 スプリント）は #1407 の定義と衝突し、主題が 1 版に収まらないときに破れる。

根拠: Value 8・Value 6（MVV 版 1）

## 決定 0b: 層をまたいだ逆転は前倒しの規則で防ぐ（案 B。推奨の値をすべて採り、語だけ変える）

| 決めること | 決定 | 理由 |
| --- | --- | --- |
| 比べる量 | 遅延コスト（CoD） | WSJF で比べると大きい課題が割り算で沈み、調査の試算の #1399（CoD 24・Size 5）が #1422（WSJF 10）に負けて永久に前へ出ない。前倒しは「いつ着手するか」の判断で、遅れの費用そのものが根拠になる。決定 21 で順位の値の大きさの指数を下げた後も、前倒しは CoD のまま比べる |
| 比べる相手 | 直近のマイルストーンの切り出しの境界の課題 | 直近の最下位と比べると、98 件あるマイルストーンの最下位はほぼ必ず低く、候補が乱発する |
| 余白 | 尺度の 1 段階（境界の CoD より、尺度で次の値以上に高い） | LLM の見積の順位相関は 0.4 程度で、1 段階の差は揺れの範囲である。棚卸しのたびに境界の近くの課題が行き来するのを防ぐ |
| 移す先 | 直近のマイルストーン | 今の `milestones.md` の「重要度が高いのに直近でない → 直近へ移す」と同じ先。主題の合う前のマイルストーンがあれば候補に併記する |
| 対の後ろ倒し | 候補として出す（承認） | 前倒しだけを反映すると直近が膨らみ続ける。遅らせる判断は今の規則でも要判断である |
| 採点の範囲 | 初回に全 open を採点し、以後は新規・本文の変わった課題だけ付け直す | 同じ尺度で比べないと前倒しが成り立たない。毎回 162 件を付け直す費用を避ける |

**語は「昇格」ではなく「前倒し」にする。** 用語集に「昇格の Pull Request」（ベースブランチから本番チャネルへ入れる Pull Request）があり、同じ語が 2 つの意味を持つ。対になる語は「後ろ倒し」。

案 A（全 open を 1 本の順位）は、1 つのスプリントに主題の違う課題が混ざり、スプリント MVV と並列の組が成り立たないため採らない。案 C（切り出しの合成）は、後ろのマイルストーンの課題が先に閉じてマイルストーンの記録とリリース済み版が食い違うため採らない。

根拠: Value 8・Value 3（MVV 版 1）

## 決定 1: 尺度は 1, 2, 3, 5, 8, 13, 20 の 7 段階を既定にし、宣言で変えられる。アンカーはリポジトリの宣言に置く（尺度とラベルは推奨を採り、アンカーの置き場は推奨が無いため決める）

- **尺度**: WSJF の慣行の 7 段階を既定にする。LLM の順位相関が 0.4 程度で、細かくしても精度は上がらないが、5 段階に減らすと余白（1 段階）の幅が広すぎて前倒しがほぼ起きない。値は宣言で変えられる
- **アンカー**: 段階ごとに 1〜2 件の閉じた課題（題・要約・実績の差分行数と所要）をリポジトリの宣言に置く。課題番号はリポジトリに固有で、Skill の `references/` に置くと ai-plugins の値を埋め込むことになる。`references/` には段階ごとの意味の文と、アンカーの選び方だけを置く。宣言にアンカーが無いときは意味の文だけで付ける
- **`priority:*` ラベルと UBV**: ラベルを UBV の下限として読む。対応（ラベルの名前 → 下限の段階）は宣言に置き、無ければ下限は効かない。UBV からラベルを付け替えることはしない（今の「ラベルの説明に照らして重要度を付け替える」が付け替えを持ち、二重に持たない）
- **大きさは AI エージェントが実施したときの費用で付ける**（決定 22）。アンカーも閉じた課題の Pull Request の実績から選ぶ
- **確信度は掛けない**: 根拠の弱い課題は点数を割り引かず、「本文の書き足しが要る」の目印にして手順 2A へ戻す。掛けると書き方の薄い課題が静かに後ろへ沈む

根拠: Value 5・Value 3（MVV 版 1）

## 決定 2: 依存は制約と加点の両方にする。取り元の優先順はサブイシュー API → 本文 → マイルストーンの説明（推奨を採る）

- 制約: 同じマイルストーンの中で、依存先より後の順位にする（Kahn の算法で、同じ順に並べられる課題の中は順位の値の降順。順位の値は決定 21）。循環は順序を出さずに止める（記述の誤りであり、どちらを先にするかは人が決める）
- 加点: 被依存の数（その課題が解放する数）を対応表で段階へ換算し（既定は 0 件→1、1 件→5、2 件→8、3〜4 件→13、5 件以上→20。決定 21 の C で強めた。宣言で変えられる）、LLM の付けた RR/OE と大きい方を採る。制約だけでは、前提の課題が低い点のまま他の前提の課題に先を譲り、後ろの課題が待ち続ける
- 別のマイルストーンにある課題への依存は、上の層の制約へ自動で上げない。前のマイルストーンの課題が後ろのマイルストーンの課題に依存しているときは、今の `milestones.md` の「順序を直すとき」の材料として報告する。前倒しの候補が依存する課題が後ろにあれば、同じ候補の組に並べる（片方だけ前倒しすると着手できない）
- LLM は本文の依存の記述を抽出するだけで、順序はスクリプトが決める

根拠: Value 4（MVV 版 1）

## 決定 3: マイルストーンの順序は自動で変えない。未設定の課題も採点する。並列の組は順位の単位にしない（推奨を採る。並列の組は推奨が無いため決める）

- 上の層は人が決める。既存の「新しく作るときは末尾」「間への差し込みは要判断」は変えない。順位のサブコマンドは材料として集計値（CoD の合計・最大・`priority: high` にあたる件数）だけを出す
- マイルストーンの付いていない課題も採点し、前倒しの候補の対象に含める。今の「重要度が高い → 直近へ」を点数で判定する材料になる
- 並列の組（見込み）は並列にできるかの見込みで、順位の単位にしない。順位は課題単位で付け、組の表は変えない

根拠: Vision（人が止まるのは判断の要る所だけ）・Value 2（MVV 版 1）

## 決定 4: 自動で反映するのは「実害の観測あり かつ UBV か RR/OE が閾値以上」の前倒しと、マイルストーンの中の順位だけ。pace は承認の扱いを変えない（推奨を採る。マイルストーンの順序だけ推奨から外す）

| 変更 | 扱い | 理由 |
| --- | --- | --- |
| マイルストーンの中の順位の変更 | 自動で反映し、変化を報告に出す | 着手の順序の候補で、スプリントの確定は別の工程が持つ。取り消せる |
| 前倒し（実害の観測あり、UBV か RR/OE が閾値以上。閾値の既定は 8） | 自動 | 今の「早める判断は実害の記述が根拠」をそのまま点数へ広げた範囲に収まる |
| 前倒し（上に当たらないもの） | 一括で承認 | 点数だけを根拠に移すと、今の規則より根拠が弱い |
| 後ろ倒し | 一括で承認 | 遅らせるのは価値の判断で、今の規則でも要判断 |
| マイルストーンの順序 | 人が決める（集計値の提示だけ。調査の推奨の 2x2 の図は添えない） | 決定 3。順序は棚卸しの承認の対象にせず、人が別に決める。図は集計値（CoD の合計・最大・閾値以上の件数）から読める以上の材料を足さない |
| 尺度・アンカーの変更 | 宣言の変更として承認 | 点数の意味が全件で変わる。`.ndf/` の書き換えは C7 |

**`pace: fast` / `auto` でも承認側を MVV の事前の承認で代えない。** スプリント MVV が承認するのはそのスプリントの主題の範囲であり、主題の外から課題を入れる判断は含まない。棚卸しはスプリントの終わりに走るため、承認側の候補は次の承認の場（棚卸しの提示）に一括で並べ、新しい止まる所を増やさない。

根拠: Value 2・C7（MVV 版 1・共通原則）

## 決定 5: 容量は Size の和で、宣言か引数で受ける。無ければ境界を出さない。MoSCoW の上限と負債の取り置きはこの課題で扱わない（調査に推奨が無いため決める）

- 容量の単位は「大きさの見積の段階の和」にする。大きさは AI の実行の費用で付けるため（決定 22）、容量も同じ単位で宣言する。件数にすると、大きい課題 1 件と小さい課題 1 件が同じに数えられる
- 容量はプロジェクトごとに違うため、スクリプトに既定値を持たない。宣言にも引数にも無ければ、順位だけを出して境界と候補を出さず、`next` で渡し方を示す（止めない）
- 「必ず入れる」の割合の上限（MoSCoW の 60%）と負債への取り置き（SAFe の 10〜30%）は、スプリントの確定の規則であり、この課題の範囲（候補の並びと境界）の外である。容量の一部を大きい課題の 1 切れへ先に当てる「大きい課題の枠」（決定 21 の B）は、候補の境界の算出に含めるため扱う。枠も容量が無い回は出さない
- 切り出しを確定する担い手は、今どおり実行計画（`issue-plan-strategy`）とスプリントの開始である。`issue-upkeep` は候補の境界を示すだけ

根拠: Value 5・Value 1（MVV 版 1）

## 決定 6: 並べ直すきっかけは棚卸しの呼び所 1 つにする（調査の表のうち 2 行を外す）

| きっかけ | 扱い |
| --- | --- |
| 変更の終わり（今の `issue-upkeep` の呼び所） | 新規・本文の変わった課題の段階を付け直し、全件の順位を算出し直す |
| 依存先の課題が閉じた | 次の棚卸しで、スクリプトが被依存の数から RR/OE を算出し直す（LLM は要らない） |
| 実害の追記・同じ現象の起票 | 本文が変わった課題として次の棚卸しで付け直す |
| マイルストーンが閉じた・MVV が変わった | 集計値を出し直し、上の層の並べ替えは人へ示す |
| スプリントを切り出す直前 | 並べ直さない（段階の判定を着手の直前に行うと判断が歪む。`SKILL.md` の「いつ呼ぶか」）。前回の表を読む |
| スプリントを閉じた（アンカーの校正） | この課題では扱わない。起票の時期は決定 18 |

呼び所を増やさないのは、今の Skill の「いつ呼ぶか」の理由（着手の直前は判断が歪む）がそのまま当てはまるためである。

調査の表から外すのは 2 行である。「スプリントを切り出す直前に点数を再計算する」は、段階を変えずに再計算しても前回の表と同じ並びになるため、前回の表を読むことで代える。「スプリントを閉じたら Size の実績でアンカーを校正する」は、要求が範囲外とした（決定 18 で起票する）。

根拠: Value 4（MVV 版 1）

## 決定 7: 順位の表はマイルストーンの説明、段階の根拠は棚卸しの記録と報告に置く（調査に推奨が無いため決める。差分の説明の形は調査の案を採る）

- マイルストーンの説明の末尾に `### 順位` の表（順位・課題・UBV・TC・RR/OE・Size・CoD・順位の値）と、切り出しの境界・大きい課題の枠の行を置く。既存の `### 並列の組（見込み）` と同じ場所で、読み手が 1 か所で見られ、GitHub Projects の無いリポジトリでも動く
- 前回の順位はこの表から読み、差分（上がった / 下がった / 入った / 外れた・変わった列と前後の段階）を報告に出す。段階は固定のアンカーで付け、式はスクリプトが持つため、差分は必ず入力の差で説明できる
- 段階の根拠の 1 行は棚卸しの記録（`$NDF_UPKEEP_STATE_DIR`）と報告に残す。課題の本文には書かない（本文の書き換えが増えて書き込みの制限に当たり、経緯を本文に残さない規則とも衝突する）
- マイルストーンの付いていない課題は表を持たず、記録にだけ残る。前倒しか割り当てでマイルストーンへ入った時点で表に載る
- 説明の長さの上限と、超えたときの表の切り方は設計が実測して決める

根拠: Value 7・Value 5（MVV 版 1）

## 決定 8: 手順は 2A で材料、2B で列ごとの段階、`upkeep.py` のサブコマンドで算出、`apply` で反映（調査の案を採る）

- 手順 2A（件数で割る）は、課題ごとに段階の材料（本文の該当箇所・再現の記録の有無・依存の記述）を控えるだけにする
- 手順 2B（分担しない）で、列ごとに全件を並べて段階と根拠の 1 行を付ける。課題ごとに担当へ割ると担当ごとに尺度がずれる
- 算出は `upkeep.py` の新しいサブコマンドに置く（別のスクリプトにしない）。棚卸しの記録・`gh` の扱い・結果の形を `candidates` / `apply` / `report` と共有するためである
- 反映は今の `apply` の plan に、順位の表と前倒し・後ろ倒しの変更を足す。承認の要る変更は「やらない」と同じく `approved` の無い限り反映しない
- ラベル（重要度）は上の層（どのマイルストーンか）の材料、順位（順位の値）は下の層（マイルストーンの中のどこか）と分担を分け、UBV はラベルを下限として読むだけにする

根拠: Value 4・Value 6（MVV 版 1）

## 決定 9: 宣言は `.ndf/backlog.json` に置き、`project.json` に節を足さない

`project.json` は解析（`project-decl.py write`）が書き直す宣言で、人が決める方針（容量・閾値・アンカー）を混ぜると、
解析のたびに人の値と機械の値が 1 つのファイルで競う。`.ndf/review.json`・`.ndf/pace.json` と同じく、方針ごとに
1 ファイルにする。書き換えは C7 に当たるため、このリポジトリへの宣言の追加は試走の後に利用者が決める。

根拠: Value 5・C7（MVV 版 1・共通原則）

## 決定 10: 尺度の最大を超える CoD には、尺度を最後の差で延ばして閾値を決める

CoD は 3 列の和で、既定の尺度の最大 20 を超える（#1399 は 24）。延ばさないと境界の CoD が 20 以上のとき閾値が
決まらない。プランニングポーカーの慣行（40・100）で延ばすと、境界 24 の閾値が 40 になり前倒しがほぼ起きない。
最後の差（既定では 7）を足し続ける形は宣言の尺度を変えても同じ算術で決まる。

根拠: Value 5（MVV 版 1）

## 決定 11: 後ろ倒しの候補は 1 件で、依存されていない CoD 最小の課題を順序で次のマイルストーンへ

1 件にするのは、前倒しの件数と対にすると小さな直近が丸ごと後ろへ出る場合があり、人が判断する材料として過大に
なるためである。直近の中で他の課題が依存している課題は外す（後ろへ移すと依存する課題が着手できない）。前倒しの
候補の最小の CoD 以上の課題は出さない（入る課題より重要なものを出さない）。移す先は順序で次のマイルストーンで、
無ければ出さない。前倒しの元へ移す形は、主題の合わない先へ送ることになるため採らない。

根拠: Value 2・Value 1（MVV 版 1）

## 決定 12: 見積は手元の記録に置き、消えたときは説明の表から段階を戻す

見積は回をまたいで要る（決定 0b の「以後は新規・変更分だけ付け直す」）が、既定の置き場は一時ディレクトリである。
説明の `### 順位` の表は段階を持つため、記録が無い課題はそこから戻す。`（ラベル）`・`（被依存）` の印の付いた
セルは LLM の段階が分からないため尺度の最小として戻し、下限と被依存の対応表を掛け直す。実害の観測は表に無いため
`false` として戻し、前倒しは承認側に倒れる。根拠の 1 行は戻らないため、根拠の要る報告には「前回の表から戻した」と出す。
課題の本文へ書く案は決定 7 で退けている。

根拠: Value 4・Value 7（MVV 版 1）

## 決定 13: 未採点と本文の変わった課題は `candidates` の経路 `unscored` で拾う

記録の `estimates.json` に無い課題と、記録の `digest` が今の要約値と違う課題を `unscored` として返す。初回は全 open が
当たり、以後は新規と変更分だけになり、決定 0b の採点の範囲がスクリプトで決まる。`--all` を担当が選ぶ形は、
初回かどうかを LLM が判断することになる。

根拠: Value 4（MVV 版 1）

## 決定 14: 承認済みの移動は `rank --approved` で表に入れてから `apply` する

表の並びは移動の後の所属で決まる。`approved: true` だけで移動を反映すると、説明の表が移動の前の並びのまま

## 決定 21: 大きい課題を優先する（利用者の決定 2026-09-28）

**前提: 課題を実施するのは AI エージェントである。** 人が実施するより、基盤の課題と大きい課題を抱える許容度ははるかに高い（利用者 2026-09-28）。一般的な WSJF は人の工数を分母に置き、小さく速く片付く課題を先へ出す。AI の実施では、大きさの差が人ほど着手の妨げにならない。

経緯: 利用者は #1142（スクリプト全体をモデル設計からやり直す）・#760（worker を CLI へ変えて組を統計で選ぶ）・#889（並行の本数が外部の利用枠を使い切る）がいまだに解決されていないことを挙げ、一般的な手法より大きい課題を優先すると決めた。決定 0b〜5 のままでは、大きい課題が次の 3 つで構造的に沈む。

1. WSJF が遅延コストを大きさで割る（Size 20 の課題は Size 1 の課題の 20 倍の遅延コストが要る）
2. 容量に収まらない課題は、順位の先頭から取る切り出しに入らない
3. 土台であること（他の課題を解放すること）が点数に効きにくい（被依存の対応表の上限が 8）

| 案 | 決定 | 宣言のキー（既定値） | 理由 |
| --- | --- | --- | --- |
| A 大きさの効きを弱める | マイルストーンの中の順位を **順位の値 = 遅延コスト ÷ 大きさ^α** で決める。α を **大きさの指数** と呼ぶ。α=1 は人が実施する前提の一般的な WSJF、α=0 は遅延コストだけ | `size_exponent`（0.3） | α=0.3 では、遅延コストが 2 倍の課題は大きさが約 10 倍（2^(1/0.3)）まで先に出る。α=0.5 では約 4 倍までで、AI の実施の前提に対して大きさがまだ強く効く。0 にしないのは、同じ遅延コストなら小さい方を先に片付ける慣行を残すためである |
| B 大きい課題の枠 | 容量のうち枠の割合（切り捨て）を、マイルストーンの中で遅延コストが最大の **大きい課題**（大きさが閾値以上）の 1 切れへ先に当て、残りを順位の先頭から切り出す | `large_slot_ratio`（0.5）・`large_min_size`（尺度の上から 2 番目。既定の尺度では 13） | 容量を超える課題は、順位をいくら上げても切り出しに入らない。1 スプリントに 1 切れずつ当てれば、分けた後の子が他の課題と並んで沈まない。0.5 は AI の実施の前提で、容量の半分を基盤に使ってよいとした値である |
| C 土台の加点 | 被依存の数（その課題が解放する数）の対応表の既定を強める: 0 件→1、1 件→5、2 件→8、3〜4 件→13、5 件以上→20。換算した段階と LLM の RR/OE の大きい方を採る（決定 2） | `dependents_steps` | 旧の既定（4 件以上→8）では、10 件を解放する課題も 1 件を解放する課題と 1 段階しか違わない。解放する数は本文と API から数えられる事実で、LLM の見積の揺れを受けない |

**B の 1 切れの決め方:**

- 1 切れは、大きい課題の同じマイルストーンにある open のサブイシューのうち、依存の順で先頭（同じ順なら順位の値の降順 → 番号の昇順）で、大きさが枠に収まるものである。サブイシューが無く、課題そのものが枠に収まれば課題そのものを当てる
- 枠に収まる切れが無いとき（サブイシューが無く容量を超える課題を含む）は、その課題を **分割が要る** として報告に出し、その回の枠は順位の先頭からの切り出しへ戻す。自動で分割しない（分け方は内容の判断で、`issue-plan-strategy` の分割の手順が持つ）
- 大きい課題が無いマイルストーンでは、枠を順位の先頭からの切り出しへ戻す。容量が無い回は枠も出さない（決定 5）。枠の割合が 0 なら枠は無い
- 切り出しの境界は、枠の 1 切れを除いて順位の先頭から取った最後の課題である。前倒しは今どおりその境界の CoD と比べる（決定 0b）
- 容量の残りは、容量から実際に当てた 1 切れの大きさを引いた値である（枠の大きさではなく、例: 容量 13・1 切れ 5 なら残り 8）。1 切れが枠より小さいとき、使わなかった枠の分を順位の先頭からの切り出しに回すため（利用者の決定 2026-09-28）

**C の数え方:** 解放する数は、その課題を依存先とする open の課題の数である。辺はサブイシューの子・ルートコーズの親としてその課題を指す子・本文で「#N の後」「#N を前提に」と書かれた課題から取る（決定 2 の取り元に、ルートコーズの親を指す子を足す）。

**D（開いている期間の長さによる加点）は採らない。** 開いている期間は遅延の費用でも価値でもなく、古いだけの小さな課題まで押し上げる。大きい課題が前へ出る理由は、A〜C で遅延コストと解放する数に表れる。

## 決定 22: 費用の見積は AI エージェントが実施する前提で行う（利用者の決定 2026-09-28）

**この Skill が扱う費用の見積はすべて、AI エージェントが実施したときの費用で付ける。人の工数では見積らない。**

| 対象 | 置き場 |
| --- | --- |
| 大きさの段階（順位の値の分母・大きい課題の閾値・容量） | この課題の `references/ranking.md` とバックログの宣言 |
| 「やらない」の必要条件 1 の「直す費用」 | `issue-upkeep/references/no-work.md`（今は「触るファイル数」で数える。実装でこの原則に合わせて直す） |

- **単位**は AI の実行の費用で、所要時間・LLM の費用・変更量（差分の行数）の 3 つを見る
- **根拠**は閉じた課題の実績である。supervise の記録（`~/.local/state/ndf/sv/*/**/progress.jsonl` と `report.md` の秒と費用）と、Pull Request の差分の行数から取る。アンカー（決定 1）もこの実績から選ぶ
- **人の感覚で大きい課題も、AI の実績に照らすと段階が下がりうる。** 部品が揃っていて組み合わせるだけの課題は、新しく作る量が小さい（例: #760 を 13 でなく 8 とした。決定 21 の試算）
- **人の時間が掛かるのは承認ゲートと判断（`needs-decision`）だけで、費用に数えない。** これは「人の判断待ち」として別に扱う。順位の値は変えず、`rank` の行と `### 順位` の表と報告に印を付け、判断を先に求める材料にする（例: #760）

理由: 見積の単位が実施の担い手と違うと、人に重い課題ほど後回しになり、AI には軽い基盤の課題が沈む（決定 21 の経緯）。人の判断待ちを費用に混ぜると、判断を 1 つ待つだけの小さな課題が大きく見える。

## 決定 23: 実害の段階は影響範囲の目安で帯を決め、退避策は実際に止まるのを防いでいるときだけ段階を下げる（利用者の決定 2026-09-28）

経緯: 利用者の指摘（2026-09-28）「#889 は #1422 より危険度が高い」。決定 21 の試算では、#889（外部の利用枠を使い切って並行の全員が 40〜60 分止まる。2026-09-15 と 10.17.28 の本番で再発）が UBV 5、#1422（`merge-when-green` がマージに成功しても exit 1）が UBV 3 で、順位の値は #1422 10.0 > #889 9.3 だった。UBV を課題どうしの相対だけで付けたため、全体の停止と終了コードの誤りが 2 段階しか違わなかった。あわせて、#889 の RR/OE を「退避（`gh_quota.py`）は一部にある」で 3 へ下げていたが、その退避は 10.17.28 の本番の停止を防いでいない。

**1. 実害の目安:** UBV の帯を影響範囲で決める。帯の中の値は、決定 1 のアンカー（段階を比べる基準の課題）と比べて決める。

| 影響範囲（区分） | 例 | UBV の帯 |
| --- | --- | --- |
| 全体（全体の停止・データの損失・安全機構の欠落） | 並行の全員が止まる・取り消した変更が公開される | 13〜20 |
| 機能（一部の機能の誤動作・手戻り） | 承認ゲートの問い直しが繰り返される・1 つの手順の結果が誤る | 5〜8 |
| 表示（表示や終了コードの誤り。結果は正しい） | マージに成功したのに exit 1・状態の表示の欠け | 2〜3 |
| なし（上のどれにも当たらない） | 体裁・好み | 1 |

- **この表は「実害の目安」と呼び、「アンカー」と呼ばない。** アンカーは決定 1 の意味（段階を比べる基準の課題）だけに使う（1 語 1 意味）
- 表の区分と帯は宣言（`.ndf/backlog.json` の `harm_guide`）で変えられる既定値である。帯は尺度の値の範囲で、宣言の尺度に帯の中の値が 1 つも無ければ宣言の誤りにする
- 「なし → 1」の行は、利用者の示した 3 つの帯の外に尺度の最小 1 が残るため足した。帯のどれにも当たらない課題の置き場である
- 手順 2B は UBV の段階と一緒に区分を返し、`rank` が段階が帯に入っているかを確かめる。帯の外の段階は順位に入れず、理由つきで外す（I1 と同じ扱い。終了コード 20）。LLM が区分を選び、帯の判定はスクリプトが持つ（決定 8 の分担）

**2. 退避策の扱い:** 退避策・回避策は、実際に止まるのを防いでいるときだけ、UBV（区分を 1 つ下げてよい）と RR/OE を下げる根拠になる。「一部にある」「あるが効いたか分からない」では下げない。

- 手順 2B は退避策の状態を `防いでいる` / `部分的` / `無い` の 3 値で返す。`防いでいる` の根拠は、退避策が働いた後に止まらなかった記録（日時とログ）である
- `rank` は `防いでいる` のときだけ、区分を 1 つ下げた帯の中の UBV も受け付ける（下げられるのは 1 つまでで、最下位の区分は下げられない）。それ以外で帯の下端を下回る段階は帯の外として外す。RR/OE を退避策で下げたかはスクリプトが判定できないため、`references/ranking.md` の付け方と根拠の 1 行で縛る

**3. 決定 21 の試算を付け直した。** 7 件を実害の目安に照らし、#889・#760・#1399 の UBV を 13 へ、#889 の RR/OE を 5 へ直した。順位と切り出しは決定 21 の表にある。

理由: 帯を影響範囲で先に決めると、課題どうしの相対だけで付けたときに起きる「全体の停止と表示の誤りが隣の段階に並ぶ」逆転が起きない。退避策で下げる条件を「防いでいる記録がある」に絞ると、効いていない退避策で危険な課題が静かに沈むのを防げる。帯の判定をスクリプトに置くのは、同じ入力から同じ順位を出すため（AC1）と、判定をテストで縛るためである。
