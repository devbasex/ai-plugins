# #2923 の設計: 決定の記録

設計文書の本体は [issue-2923-design.md](issue-2923-design.md) にある。番号 `STD<数>`・`LIB<数>` は本体の「外部の調査」の表を、`I<数>` は本体の「不変条件」の表を指す。

## 決定の記録

### 決定 1: 課題ごとの根拠を 1 つの形で渡すため、判定の根拠は JSON のファイルで `loop sprint` に渡す

1 つの課題の根拠は順・モード・条件の文・触るファイルの一覧の 4 つを持ち、課題が 3 件なら値は 12 個になる。
ファイルにすると、`mode-materials.py` の下書きを conductor が埋めてそのまま渡せ、渡した形が記録の形と 1 対 1 になる。

引数で課題ごとに渡す形（`--judgment 2748:3:...`）は採らない。条件の文とパスの一覧を 1 つの引数に詰める区切りの規則が
要り、文に区切りの文字が入ると割れる。

根拠: Value 5 / Value 8（MVV 版 6）

### 決定 2: モードを根拠と食い違わせないため、スプリントのモードは根拠から `loop sprint` が算出し、`--mode` は照合だけに使う

判定表は「上のモードが勝つ」の規則で、課題ごとの順が決まればスプリントのモードは機械で決まる。決まった手順を
conductor に計算させると、根拠と食い違う値を渡せる余地が残る。`--mode` は省けるようにし、渡したときは算出した値と
照合して食い違えば断る（要求のドメインイベント E4 の例外）。

`--mode` を廃して受け付けない形は採らない。conductor が自分の判定を明示して照合させる使い方を残すためである。

根拠: Value 5（MVV 版 6）

### 決定 3: 決め直しに要る根拠を手元に持つため、残りの課題の根拠は `loop sprint` で記録した `judgments` から読む

決め直しの時点で conductor に根拠を渡し直させると、設計承認ゲートの処理（機械が進める）が conductor の入力を待つ。
`loop sprint` が I1 で全課題の根拠を記録するため、残った課題の根拠は必ず記録にある。

根拠: Value 5（MVV 版 6）

### 決定 4: 下がったモードを残りの工程すべてに当てるため、続きのステージは `new sprint --designed` で作り直す

モードはプランの組み立てに効く。リファクタリングのステップの有無・設計との突き合わせ・リリース承認ゲートの判定が
これに当たる。そのため、`モード` の値だけを書き換えても工程は変わらない。`new sprint` は設計を承認済みの課題を `--designed` で受け、
設計の結果から本番までを組む。これはゲートの後のステージと同じ並びで、組み立ての規則を 1 か所に保てる。

組み済みのプランの JSON からステップを外して書き換える形は採らない。ステップの `next` のつながりを
モードごとの組み立てと別の場所で再現することになり、組み立ての規則が 2 か所に分かれる。

モードが同じときは作り直さず、今の `continuation` で組む。変えない場合に既存の経路の振る舞いを保つためである。

根拠: Value 7（MVV 版 6）

### 決定 5: 推した候補を事実として渡さないため、触るファイルの候補は code span とリンクの宛先からだけ取る

課題の本文で、パスは code span かリンクで書かれる（`document-style` のルール 12）。地の文の語からパスらしいものを
推すと、識別子や語が候補に混じる。取った候補には見つけた節の見出しを添え、再現手順で触れただけの記録のファイルを
conductor が見分けられるようにする。Markdown の読み取りは既存の `lib/md.py`（LIB1 の包み）に `code_spans` を足して行う。

- 作り方: ライブラリやサービスを使う・標準に倣う
- 比べた候補: STD1 / LIB1 / LIB2

根拠: Value 4 / Value 7（MVV 版 6）

### 決定 6: モードの行を設計の段階から読めるよう、課題の本文のモードはループのスクリプトが書く

プランの通過記録（`supervise_lib/state.py`）は、進め方を最初の工程の記録で書く。ループの 1 回では、進め方を持つ
最初のプランが実装のプランである。そのため設計の間は `モード: —` のままになる。`loop sprint` と決め直しの時点に
`projects-sync.sh <課題> mode <モード>` を打てば、決めた時点から本文に出る。書けなくてもループを止めない
（`progress-record.sh` の「進行管理が理由で開発の工程を止めない」）。

根拠: Value 2（MVV 版 6）

### 決定 7: この版より前の記録で止まらないため、根拠を持たないループの 1 回は決め直さずに今の続きを組む

要求のドメインイベント E6 の例外は「残りの課題の根拠が記録に無いときは断る」とする。しかし、版を上げた時点で
進行中のループの 1 回は根拠を持たない。断るとそのループは設計承認ゲートの後に止まり、移行性の条件（読み込みと再開が失敗しない）を満たせない。
I1 により、この版で組んだループの 1 回では根拠の欠けは起きないため、断る対象は古い記録だけになる。

根拠: Value 1 / Value 6（MVV 版 6）
