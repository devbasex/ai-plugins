# #2721 の決定の記録

## 決定の記録

### 決定 1: 承認する人の問いを 1 行に 1 つにするため、承認資料の一覧を判断の問いの単位で 26 行に分ける

一覧の行の単位は、成果物の形式（図・表）ではなく判断の問いにする。前提 3 の重複しない条件は「同じ判断の問いに答える行が無い」ことである。形式で分けると、同じ問いに答える図と表が別の行になる（ER 図・テーブル定義・CRUD 図は、どれも「どのデータをどう持つか」に答える）。そのため、要否表の 20 行は一覧の 18 行に対応づけた。承認する人が読む欄は 3 つの問いに分けた。データ構造の 3 行・処理の流れの 2 行・構成要素とパッケージ構成・クラス図とオブジェクト図は、それぞれ 1 行にまとめた。これに次の行を加えた。

- 要求の 2 行（起票者の推定・要求と受け入れ条件）
- 依頼の 4 項目のうち新しい問いの 3 行（技術スタックの一覧・画面モック・デザインイメージ）
- 承認時に作る 3 行

画面は 3 行に分けた。画面の仕様（どこが変わるか）・画面モック（操作して確かめられるか）・デザインイメージ（見た目がどうなるか）は、承認する人が別々に確かめる問いである。技術の選定も 3 行（外部の調査・技術スタックの一覧・決定の記録）に分けた。比べた候補（調査）・依存と自作の一覧（技術スタック）・選んだ理由（決定）は、別々の問いである。arc42 は Solution Strategy と Architectural Decisions を別の節にしている（STD1）。Rust の RFC は Prior art を別の節にしている（PRD2）。

形式の単位で並べる形は採らない。図の種類が増えるたびに行が増え、どの行が同じ問いに答えるかを承認する人が読み分けることになる。

根拠: Value 2 / Value 8（MVV 版 6）

### 決定 2: 一覧を読む側を 1 つの表に向けるため、一覧を新しい参照 `approval-materials.md` に置き、要否表の `standard` の列をこの表の参照に置き換える

一覧は、設計の担い手（`design`）・承認の提示（`approval-request.md`）・検査のスクリプトの 3 者が読む。要否表（`deliverables.md`）はモードごとの水準を持つ表で、行の単位が成果物である。同じファイルに 2 つの表を置くと、どちらが `standard` の水準の正本かが読み分けられない。新しい参照に 1 つの表として置き、要否表の `standard` の列は外して「`standard` の水準は承認資料の一覧が持つ」と書く。`standard` は設計承認ゲートを必ず通るモードであり、一覧の水準はそのまま `standard` の水準になる。

起票者の推定 S1 は `deliverables.md` に寄せる形を挙げていた。置くファイルは要求の未決で設計者に任されており、受け入れ条件 1（1 つのファイルの 1 つの表）は新しい参照でも満たす。要否表に `standard` の列を残したまま一覧を足す形は、同じ水準を 2 か所に持つため採らない。

根拠: Value 8（MVV 版 6）

### 決定 3: 該当を機械で決めるため、触る領域を設計文書の適用範囲に 1 行で書き、行が無いときはすべての資料を該当として扱う

該当時の資料を検査するには、その設計が何の領域を触るかを機械が読めなければならない。今は手順 1 で決めた領域が文書に残らない。適用範囲の節に `- **触る領域**: <語>・<語>` の 1 行を足し、語は `design` の手順 1 の表の 7 つに限る。行が無い・読めないときは、要求のドメインイベント E2 の「判定できない資料は該当として扱う」に従い、該当時の資料をすべて該当にする。

設計文書の節の有無から領域を推す形は採らない。節が無いことが「触らない」なのか「書き忘れ」なのかを区別できず、欠けを見つける検査が成り立たない。

根拠: Value 5（MVV 版 6）

### 決定 4: 欠けを設計文書だけで判定するため、`standard` の必須の資料の対象が無いときは、置き場の節に `無し（<理由>）` を書く

今の要否表は、`standard` で必須の成果物の対象が無いとき、理由を仕様の「対象範囲（含まない）」に書くと定めている。この形では、節が無いことが「対象が無い」のか「欠け」なのかを検査が判定できない。外部の調査の節が `省く: <理由>` を節の中に書く形と同じく、必須の資料は節を作って `無し（<理由>）` を書く。リンク集はこの 1 行を要旨として出す（受け入れ条件 11）。

`light` / `operation` / `legacy-refactor` の省いた理由の書き先は変えない（受け入れ条件 14。新しい必須の資料を課すのは `standard` だけ）。

根拠: Value 5 / Value 2（MVV 版 6）

### 決定 5: 欠けの検査とリンク集の組み立てを同じ一覧で行うため、新しいスクリプト `design-materials.py` に `check` と `links` を置き、一覧の表を実行時に読む

検査とリンク集は、どちらも「一覧の行 × 触る領域 → 該当する資料 → 設計文書の節」を同じ規則で求める。2 つを別のスクリプトにすると、該当の規則が 2 か所に分かれる。一覧の表は実行時に読み、行を足しても検査のコードを変えずに効くようにする（該当時の行に新しい領域の語を使うときだけ、7 語の語彙を変える）。

既存の `design-survey.py` へ足す形は採らない。設計文書のまとまりを読む部分（`lib/design_docs.py`）は共有する。しかし責務は決定の 2 行の検査であり、終了コードと items の意味が混ざる。ADR の管理ツール（STD3 の系統）は 1 ファイル 1 決定の形で、設計文書の節の欠けを判定する機能を持たない。調べなかった理由は外部の調査の「確かめられなかったこと」にある。

- 作り方: 自前で作る・ライブラリやサービスを使う
- 比べた候補: LIB1 / LIB6 / STD3

根拠: Value 5 / Value 7（MVV 版 6）

### 決定 6: 画面モックの置き場をプロジェクトごとに受けるため、`.ndf/project.json` に `ui_mock`（`kind`・`location`）を足し、画面を変える `standard` の設計で未宣言なら検査で止める

表現方法はプロジェクトごとに違う（前提 5）。種類は、調べた 4 つの置き場（Claude の artifact・Storybook・Chromatic・プレビュー環境）を 3 つにまとめる。Chromatic は Storybook の公開先として `storybook` に含める。これに「その他」を足した 4 値（`artifact` / `storybook` / `preview` / `other`）にする。場所は URL のテンプレートかパスで受ける。欄は省略でき、今の宣言はそのまま読める。

未宣言のときは、画面を変える設計に限って検査を落とす（起票者の推定 S6 を採る）。依頼の原文は「プロジェクトでの表現方法の定義を必須とする」であり、表示だけにすると、宣言の無いまま画面モックの無い設計が承認ゲートへ届く。画面を変えない設計では挙げない（受け入れ条件 9）。S6 は利用者が設計承認ゲートで採った（2026-11-09）。

宣言を解析（`project-decl.py` の手順 0）で埋める形は採らない。リポジトリの中から画面モックの置き場は決まらず、推した値を書くと、利用者が決めていない置き場で検査が通る。

根拠: Value 6 / C7（MVV 版 6）

### 決定 7: 承認する人が 1 回で読み切れるよう、CLI の提示の本体を資料 1 件 1 行のリンク集にし、決定の見出しの羅列を決定の記録の節へのリンクに置き換える

提示の本体は `- <資料名>: <要旨> <URL>` の行の並びにする。決定の記録・起票者の推定・受け入れ条件は件数を要旨にし、中身はリンクの先で読む。依頼の原文は「メインのコンソールはリンク集となり、各リンクをたどって見れるようにする」であり、項目の中身を提示へ写す形はこれに合わない。

今の `approval-request.md` は「決定の見出しをそのまま並べる。件数だけを示す形も採らない」と定めている。その理由（要約で判断が変わる）は、見出しを言い換えないことで守る。リンクの先は設計文書の決定の節そのもので、提示が言い換えを作らない。対象を開くもの（Pull Request の URL・題・ベースと head・変更量）の層は変えない。

根拠: Value 2（MVV 版 6）

### 決定 8: 承認時の 3 行は既存のコマンドの結果から conductor が足し、`design-materials.py links` は設計時の行だけを組む

承認時の 3 行は、それぞれ次のものが出す。

| 行 | 出すもの |
| --- | --- |
| レビューの収束の状態 | `cross-review` の判定 |
| 本文との一致 | `pr-body-decisions.sh check` の終了コード |
| MVV 判定 | MVV 判定のコメント |

`links` にこれらを読ませると、3 つのコマンドの出力の形に依存し、どれかが変わるたびに `links` を直すことになる。`links` は設計文書と仕様のコピーから作れる行だけを組む。承認時の 3 行は、`approval-request.md` に行の形（`- <資料名>: <要旨> <URL>`）を定め、conductor が同じ形で足す。

根拠: Value 5 / Value 7（MVV 版 6）

### 決定 9: NDF と Factory を独立して変えられるよう、Factory は承認の依頼の事象に省略できる `links` を足して受け、画面の実装は #2815 に分ける

`links` の 1 件の形は `design-materials.py links` の結果の 1 件と同じにする（公開された言語）。省略できる欄にするため、今の実行の担い手と今の事象はそのまま通る。`material`（承認資料の本文）は残し、リンク集の無い承認の依頼（リリース承認ゲート・判断の依頼）は今と同じに表示する。

画面の実装・契約のスキーマの変更・実行の担い手の変更は #2815 に置く（前提 4）。この課題で契約のスキーマだけを先に変える形は採らない。受け手の無い欄が契約に残り、#2815 の設計で形を変えるときに互換の扱いが要る。

根拠: Value 3 / Value 6（MVV 版 6）

### 決定 10: リンクの先をレビューの直しの後も最新に保つため、URL は設計 Pull Request の head ブランチの blob URL と見出しのアンカーで作る

承認する人が開くのは、提示の時点の最新の設計文書である。コミットを固定した URL は、レビューの直しを送るたびに古くなる。アンカーは既存の `md.heading_anchor`（GitHub の規則に従う。STD6）で作り、同じ見出しが重なる文書でも GitHub と同じ番号が付く。

マージの後に head ブランチが消えると、リンクは開けなくなる。承認はマージの前に済むため、この形で足りる。

根拠: Value 2（MVV 版 6）
