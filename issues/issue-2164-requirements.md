## 目的

- 並行する別のスプリントが先に版を出しても、プランを作り直さずに配布まで進める（Vision: 人が手を止めるのは承認の 2 回に寄る。2 回の再発では conductor の作り直しと版の書き換えで止まった）
- 古いプランが既に使われた版より古い版へ戻して配布する事故を、配布の前に止める

## 前提

- 前提 1: 対象は `supervise.py` が組むスプリントのプランのうち、配布を雛形で組むもの（`.ndf/release.json` の `form: package-plugin`。版数が要るのは `delivery.needs_version` が真の経路だけ）。雛形で組まない経路は版数を持たないので変えない
- 前提 2: 「使われた版」（この要求の中だけの言い方。リリース済み版より広く開発版も含む）は、開発版なら origin のベースブランチ（`.ndf/worktree.json` の `base_branch`。ai-plugins は develop）の `plugin.json` の版、正式版なら origin のリリースタグ（`<plugin>--v<版>`）と本番のブランチの版で判定する。どちらも配布のステップの開始時に `git fetch` した後の値を読む
- 前提 3: 開発版の版の決め方は「版と配布の方針」に従う。ベースブランチの版が未リリースの正式版 X の開発版 `X-dev.N` なら `X-dev.(N+1)`、そうでなければ（ベースブランチの版が正式版、または X のタグがすでにある）最新のリリースタグの版を上げ幅で上げた Y の `Y-dev.1`
- 前提 4: 上げ幅（PATCH / MINOR / MAJOR）はプランを作る時点で指定でき、指定が無ければ PATCH とする（マイルストーンの間は PATCH で出す運用に合わせる）。上げ幅を版の決め方へどう渡すかは設計が決める
- 前提 5: m26-1 でスプリント PR が「版の行で衝突した」仕組み（スプリントの PR が版の行を持った理由）は調べていない。この要求は配布と本番のプランが版を決める時点だけを扱い、スプリント PR の衝突は受け入れ条件 2 が満たされたときに起きなくなるかを設計で確かめる

## 対象範囲

含む:
- `supervise.py new sprint` / `new close` が組む開発版と本番のプラン（MVV 判定で進めるもの・`pace: normal` の配布を含む）が、版をどの時点に決めるか
- 版を名前に持つもの（worktreeのパス・ブランチ名 `release/v<版>`・承認資料のパス・CHANGELOG の節・タグ）が、決めた版に揃うこと
- 配布の `bump` が、既に使われた版以下へ版を戻さないこと
- 決めた版を開発版と本番の結果 JSON（`metrics.version`）に載せること

含まない:
- 雛形で組まない配布の経路（`delivery` の行ごとの経路）
- 上げ幅を中身から自動で決めること（前提 4 のとおり指定か既定の PATCH）
- スプリントでない単独の `supervise.py new release` の版の決め方（版を明示して作るので、受け入れ条件 4 の止まり方だけが当たる）
- 他のプラグインの上げ幅（`bump-others`・`changed-plugins`）の決め方
- 承認ゲート 2 の承認の記録の形（`approved_sha` で中身を照合する仕組み）

## 受け入れ条件

- [ ] 1. 版数を明示せずに作ったスプリントのプラン（`sprint.json` と、開発版・本番のプランのファイル）は、具体的な版数（`10.27.6-dev.1` のような文字列）を持たない。worktreeのパス・ブランチ名・承認資料のパスも、プランを作った時点では版を含まない
- [ ] 2. 開発版の配布のステップは、流した時点の origin のベースブランチの版と最新のリリースタグから版を決める。例: ベースブランチが `10.27.5`・最新のタグが `ndf--v10.27.5`・上げ幅 PATCH なら `10.27.6-dev.1`。ベースブランチが `10.27.6-dev.1` でタグ `ndf--v10.27.6` が無ければ `10.27.6-dev.2`
- [ ] 3. プランを作った後、配布の前に別のスプリントがベースブランチか本番のブランチへ版を出しても、同じプランをそのまま流すと、2 の規則で次に空いている版に決まり開発版の配布が終わる。conductor がプランを作り直す・版を書き換える操作は要らない（作った時点のベースブランチが `10.27.5`、配布の前に別のスプリントが `10.27.6` を本番へ出したなら `10.27.7-dev.1`）
- [ ] 4. 版数を明示して作ったプランは、明示した版がすでに出ていれば（開発版はベースブランチの版と同じかそれより大きい版がある、正式版は同じ版のタグがある）、`bump` より前に止まり、止まった理由と既に出ている版を結果 JSON に載せる。別の版へ移って進まない
- [ ] 5. 配布の `bump` は、新しい版がベースブランチの版以下（semver の比較で同じか小さい）なら、ファイルを書き換えずに止まる（例: ベースブランチが `10.27.5` のとき `--to 10.27.5-dev.1` は止まる）。同じステップの打ち直し（作業場所がすでに新しい版で、ベースブランチの版より大きい）は今と同じく ok で返る
- [ ] 6. 本番のプランは、同じスプリントの開発版の版の系列（接尾辞を外した版。承認資料が持つ版）で出す。その版のタグがすでにあれば、本番のブランチへ入れる前に止まり、人へ戻す（止まった理由・既に出ている版・次に空いている版を結果 JSON に載せる）。別の版で黙って進めない
- [ ] 7. 同じプランの開発版の配布のステップを流し直すと、最初に決めた版を使う（自分が出した開発版を「使われた版」と見て次の版へ進まない）
- [ ] 8. 版を決めるときに origin のベースブランチ・本番のブランチ・タグのどれかを読めなければ、版を推定せずに止まり、読めなかったものを結果 JSON に載せる
- [ ] 9. 開発版と本番の結果 JSON（`release-steps.py release` の出力）の `metrics.version` に、決めた版が載る
- [ ] 10. 版数を明示して作ったプランで、明示の版がまだ出ていなければ、今と同じ版・同じステップで配布が進む（退行しない）
