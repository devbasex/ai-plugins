## 決定の記録

### 決定 1: アカウントの設定ディレクトリを子の `CLAUDE_CONFIG_DIR` にし、トークンとスコープの変数を渡さない

#1389 の決定 1 と #1523 の決定 1 を置き換える。変数のトークンは Claude Code が更新できず、8 時間で必ず 401 になり、
`/status` にアカウントが出ない（要求の実例）。設定ディレクトリの認証ファイルで認証させれば、claude が自分で更新し、
`oauthAccount` から識別を出す（実験 1・2）。2 つの決定が設定ディレクトリを分けない理由にした「会話の記録と設定が
分かれる」は、共有物を symlink にすると起きない（実験 3・7）。

採らなかった形は要求の「採らなかった形」の 4 つで、設計では選び直さない（要求の前提 2）。

根拠: Mission / Value 6 / C2（MVV 版 2）

### 決定 2: 共有の設定ディレクトリは、元の `CLAUDE_CONFIG_DIR` の値を `NDF_SHARED_CONFIG_DIR` で子へ渡して求める

子の中では `CLAUDE_CONFIG_DIR` がアカウントの設定ディレクトリを指す。そこから `supervise.py` が別のアカウントか従量の
接続を起動するには、共有の設定ディレクトリを別に知る手段が要る。変数の有無で `.claude.json` の置き場が変わる（実測 B）
ため、元の値をそのまま運び、無かったことは空文字で表す。従量の接続ではこの値で `CLAUDE_CONFIG_DIR` を元へ戻す。

アカウントの設定ディレクトリのパスをさかのぼる形と、`ndf` の symlink の実パスから求める形は採らない。どちらも
`NDF_ACCOUNTS_DIR` で置き場を移した環境で外れ、元の変数が無かったことを区別できない。

根拠: Value 5 / Value 6（MVV 版 2）

### 決定 3: 子の `CLAUDE_CODE_PLUGIN_CACHE_DIR` を共有の `plugins` へ向ける

`plugins` を symlink にしても、子が導入したプラグインの置き場はアカウント側のパスで共有の記録に残る（実測 D）。その
アカウントの登録を外すと、ほかのアカウントと素の claude からそのプラグインが読めなくなる。変数を足すと共有側のパスで
記録される（実測 D）。利用者が既にこの変数を持っていれば、その値を残す。

導入の記録を NDF が後から書き直す形は採らない。本体のファイルの形に NDF が合わせる箇所が増える。

根拠: Value 6 / Value 2（MVV 版 2）

### 決定 4: 固有の項目だけを一覧に持ち、一覧に無い項目はすべて共有する

要求の未決 5・7 の答えである。共有する側を一覧にすると、Claude Code が項目を足すたびに追随が要る（#1389 の決定 1 が
挙げた費用）。固有の側は認証と組織ごとの控えに限られ、増え方が遅い。用意のたびに共有側の直下を見て足りない分を足すので、
後から増えた項目も次の起動で共有される。NDF の hook のファイルは共有側とする（決定 14）。

共有側に無く、claude がアカウント側に新しく作った項目は、実体のまま残す（消さず、移さない。I5）。後で共有側に同じ名前が
できたら、飛ばして名前を記録する。

根拠: Value 5 / Value 1（MVV 版 2）

### 決定 5: 起動を止めるのは `projects` が共有されないときだけにする

要求の未決 5 の残りである。`projects` が共有側を指さないと、会話の記録がアカウント側に入り、替えた先で `--resume` が
通らない。ほかの項目は、共有されなくてもセッションを続けられるため、飛ばした名前を記録して起動する。共有側に無いと
claude がアカウント側に実体を作ってしまう `projects` と `settings.json` は、用意が先に共有側へ作る。

飛ばした項目が 1 つでもあれば起動しない形は採らない。利用者が置いた 1 つのファイルで、そのアカウントが使えなくなる。

根拠: Value 2 / Value 1（MVV 版 2）

### 決定 6: 共有する設定の部分は、同期の控えを加えた 3 つの突き合わせで両側へ写し、本体と同じ排他の中で書く

要求の未決 3 の答えである。起動の前に共有側の値で上書きし、終わった後に書き戻すだけでは、セッションの間に別の claude が
共有側で変えた値を古い値で上書きする。前の同期の値（同期の控え）を持てば、どちらの側で変わったかが葉ごとに決まる。
書く間は、本体が保存に使う排他（`<パス>.lock`）を取る。本体は排他の中で読み直してから重ねて書く（実測 B）ので、
動いている claude の書き込みと取り合わない。共有側へ書くキーは `projects` と `mcpServers` に限る（I10）。

同期の控えがあるのにアカウント側の `.claude.json` が無いか、控えに葉があるキーがアカウント側で無いか空のときは、
そのキーの控えを使わず最初の同期として扱う（I18）。控えのまま突き合わせると、控えにあった葉がすべて「アカウント側
だけで消えた」と読まれ、共有の `~/.claude.json` の `projects` と `mcpServers` が丸ごと消える。アカウント側の
ファイルは、利用者が消すことも、本体が壊れたファイルを初期化することもある。代わりに、アカウントのセッションの中で
最後の 1 件を消したことは共有側へ写らず、次の同期で共有側の値が戻る。利用者のデータを消さない側を採る。

同期の控えには、アカウント側の `.claude.json` の `userID` も控える。同期のとき、アカウント側の `userID` が控えの値と
同じでなければ（どちらかに無い場合を含む）、アカウント側は失われたとみなし、`projects` と `mcpServers` の両方で控えを
使わず最初の同期として扱う（I18）。本体は、新しいプロセスが壊れた `.claude.json` を読むと移行の印だけの内容へ初期化し、
動いている対話のセッションがそれを取り込むと、終了時のファイルは `projects` が今の作業ディレクトリの 1 件だけになる
（実測 I）。この形は「無いか空」に当たらず、控えのまま突き合わせると、控えの残りの葉がすべて「アカウント側だけで
消えた」と読まれて共有側から消える。`userID` は、正常なファイルでは起動を重ねても同じ値で、初期化のたびに別の値に
なるか無くなる（実測 I）ので、初期化をまたいだことの印になる。値は同期の控えのほかへ書かない（I14）。

控えに `userID` が無いとき（控えを書いた時点でアカウント側に `userID` が無かった）も、最初の同期として扱う。その後に
アカウント側へ `userID` が付いたのか、初期化で付け直されたのかを区別できないためである。代わりに、`userID` がまだ無い
アカウントの最初のセッションでアカウント側へ足した値（受け入れたプロジェクトの信頼など）は共有側へ写らず、次の同期で
共有側の値に戻る。claude -p と対話の起動は `userID` を書く（実測 I）ので、次の同期からは控えが効く。`oauthAccount` と
`hasCompletedOnboarding` が消えたことを印に足す形は採らない。控える項目と条件が増え、得られるのは最初の 1 回の
書き戻しだけである。

アカウント側の `.claude.json` が JSON として読めないとき（`account_unreadable`）は、その回の同期を飛ばすだけでなく、
同期の控えを消し、次の同期を最初の同期として扱う（I18）。本体は退避から自動では戻さず、利用者に `cp` で戻す案内を
出すだけである（実測 I）。退避は前の同期より古いことがあり、戻したファイルの `userID` は控えと同じなので、控えを残すと、
退避より後に両側へ足した葉が「アカウント側だけで消えた」と読まれて共有側から消える。代わりに、読めなくなる前の
セッションの中でアカウント側へ足した値は共有側へ写らない。用意で読めないと分かったアカウントでは、起動もしない（決定 19）。

アカウント側の `.claude.json` を共有側への symlink にする形は採らない。`oauthAccount` が共有側のものになる（実験 6）。
`~/.claude/` の外にある `~/.claude.json` へ書くことは確定案の 8 が求めており、設計の承認で人が見る（C6）。

根拠: Value 6 / C3 / C6（MVV 版 2）

### 決定 7: `hasCompletedOnboarding` と `lastOnboardingVersion` を、アカウント側に無いときだけ共有側から写す

登録で作られたアカウント側の `.claude.json` にはこの 2 つが無く、本体は無いと対話の起動で最初の案内を出す（実測 C）。
案内が出ると、ラッパーが入れる最初の入力が案内に吸われる。共有側で済ませた印を写せば出ない。アカウント側に値があれば
上書きしない。

共有側の `.claude.json` のキーをすべて写す形は採らない。`oauthAccount` とアカウントごとのキャッシュが混ざる（実験 6）。

根拠: Value 2（MVV 版 2）

### 決定 8: 書き戻しはラッパーのセッションの切れ目だけで呼び、`supervise.py` は呼ばない

`supervise.py` の claude -p は対話を持たず、プロジェクトの信頼や MCP サーバーの許可を足さない。呼び出しのたびに
書き戻すと、並列の worker の数だけ共有の `.claude.json` の排他を取る。claude -p が変えた値は、そのアカウントの次の用意の
同期が共有側へ写す（同じ関数）。

根拠: Value 1（MVV 版 2）

### 決定 9: NDF のアカウントごとの排他は `accounts/.locks/<名前>.lock` で取り、古い形の排他ファイルは消す

本体は更新のとき `<設定ディレクトリの実パス>.lock` も取る（実測 A）。`lib/locks.py` の排他は取るたびに排他ファイルの
更新時刻を進める（実測 G）ため、今のパスのままでは、NDF が触ってから 60 秒は claude の更新が通らない（実験 7・10・11）。
アカウントの設定ディレクトリの中に置く形は採らない。登録のやり直しと削除が、排他を握ったままディレクトリごと消す。

古い形の排他ファイルは、60 秒を過ぎれば claude の更新を妨げない（実験 12）が、受け入れ条件 13 のとおり消す。60 秒より
新しいものは、古い版のラッパーが使っているので残す（要求の前提 8）。

根拠: Value 6（MVV 版 2）

### 決定 10: NDF がトークンを更新するのは、動いている claude が無く、期限が切れたか 401 のときだけにする

要求の未決 2 の扱いである。更新するとリフレッシュトークンが替わる（実験 1）ため、動いている claude と NDF が同時に
更新すると、片方のリフレッシュトークンが無効になる。NDF は、呼ぶ側が渡す名前と環境の `NDF_CLAUDE_ACCOUNT` のアカウントを
更新しない（I8）。ほかのアカウントも、本体と同じ更新の排他を取り、排他の中で認証ファイルを読み直してから宛先を呼ぶ
（I9）。NDF から見えない claude（別の端末・別のコンテナ）が同じアカウントで動いていても、双方が同じ排他と読み直しを通る。

NDF の更新をなくす形は採らない。長く使っていないアカウントの残量が読めず、候補を残りの量の順に並べられない（確定案の 7）。

根拠: Value 6 / C1（MVV 版 2）

### 決定 11: 期限の前の更新と、`before`・`min_left` の引数をなくす

#1389 は、子へ渡したトークンが呼び出しの間もつように、期限の 1 時間前と「残りが打ち切りの秒より短いとき」に更新していた。
子が自分で更新する形では、渡す前に残りを確かめる理由が無い。期限の前の更新は、NDF から見えない claude と更新が重なる機会を
増やすだけである。候補として起動できるかは、ネットワークを使わない `usable()` で確かめる。

根拠: Value 1 / Value 6（MVV 版 2）

### 決定 12: 更新の排他は待たず、横取りせず、宛先の待ちは 3 秒までにする

本体は排他を取れないと 1〜2 秒おいて 5 回まで試す（実測 A。待ちの合計は 4 秒以上）。NDF が握る時間をそれより短くすれば、
同時に起動した claude は失敗しない。NDF の側は、取れなければその回の残量を読めなかったものとして扱い、次の取得でやり直す。
残った排他を NDF が消して取る形は採らない。取り違えるとリフレッシュトークンが無効になり、再登録が要る。残骸は、次に
そのアカウントで起動した claude が本体の規則（60 秒）で片付ける。

`.claude.json` の排他は扱いを変え、本体と同じ 10 秒で残骸とみなして取る。取り違えても失うのは設定の 1 回の書き込みで、
取れないままだと同期が飛び、対話にプロジェクトの信頼の確認が出うる。

根拠: Value 6 / C1（MVV 版 2）

### 決定 13: 認証の失敗では `needs_relogin` にせず、認証の失敗の観測を残して候補から外す

要求の未決 6 の答えである。今は 401 の後に NDF がトークンを更新し、断られたら `needs_relogin` にしている。動いている
claude のアカウントを NDF が更新しない形（I8）では、子が終わった時点で、リフレッシュトークンが断られたのか一時的な失敗かを
区別できない。観測を残してそのアカウントを除いて選び、子が終わった後の使用量の取得（NDF の更新を含む）が成功すれば観測を
解き、更新が断られれば `needs_relogin` にする。取得先が使えない間も外したままにならないよう、1 時間で解く（仮の値で、
`log.jsonl` の `auth` の行の間隔で見直す）。

すぐに `needs_relogin` にする形は採らない。一時的な失敗で利用者に再登録を求めることになる。観測を残さない形は、次の
選び直しで同じアカウントへ戻り、失敗を繰り返す。

`supervise.py` の claude -p も同じ扱いにする（E9 の受け手に `ClaudeRunner` を足す）。今は `child_env()` が起動の前に
トークンを更新し、得られなければ理由 `auth` で別のアカウントへ替えている。起動の前の更新をなくす（決定 11）と、
断られたリフレッシュトークンは claude -p の結果で初めて分かる。結果で受けなければ、同じアカウントのまま以後の
呼び出しがすべて失敗し、今の振る舞いから後退する。結果行の形は偽の認証ファイルで確かめた（実測 H）。経路は上限の
ときと同じにし、新しい分岐を作らない。

根拠: Value 2 / Value 6（MVV 版 2）

### 決定 14: NDF の hook は `settings.json` の実パスへ書き、排他・印・控えを実パスの隣に置く

symlink のパスへの `mv` は symlink を実体に置き換える（実測 E）。2 本の hook はこの形で書くため、アカウントの設定
ディレクトリでは共有の `settings.json` から切り離される。実パスを求めてから書けば symlink は残る（実測 E）。排他・印・
控えも実パスの隣に置き、どのアカウントから呼んでも同じファイルを使う。実パスを求める関数は 2 本が共有する
`scripts/lib/claude-settings.sh` に置く。

hook の中で `NDF_SHARED_CONFIG_DIR` から置き場を求め直す形は採らない。利用者が自分で `settings.json` を symlink にして
いる環境では今も同じ置き換えが起きており、実パスの解決はそちらも直す。

根拠: Value 6（MVV 版 2）

### 決定 15: 認証ファイルが別のアカウントのものになった設定ディレクトリでは起動せず、`needs_relogin` にする

要求の未決 4 の答えである。登録済みアカウントの claude の中で `/login` を打つと、その設定ディレクトリの認証が別の
アカウントに替わる。そのまま使うと、残量と上限の観測が別のアカウントのものになり、同じメールアドレスと組織を 2 つ登録
しない規則（#1389 の I3）も崩れる。用意のたびに、アカウント側の `.claude.json` の `oauthAccount` を `account.json` と
照らし（ネットワークを使わない）、メールアドレスが違うか、両方にある組織の識別が違えば、起動せずに `account add <名前>` を
案内する。`oauthAccount` が無いときは通す（claude が次の応答で取り直す。実験 8）。

`account.json` を新しい識別で書き直す形は採らない。利用者が付けた名前と中身が黙って食い違う。知らせるだけで起動する形は、
上の 2 つが崩れたまま動く。

根拠: Value 2 / C2（MVV 版 2）

### 決定 16: 再開の文は、切り替えの理由から表で決める

`resume_input()` は理由を受け取らず、認証切れでも「利用上限で」と入れていた（#1575 の 2）。画面の 1 行は既に理由ごとの表
（`_SWITCH_MESSAGES`）で決めているので、再開の文も同じモジュール（`relay_lib/switch.py`）の表に置き、`resume_input()` は
文を引数で受ける。未達の `/goal` を入れ直す規則は変えない。

根拠: Value 6（MVV 版 2）

### 決定 17: symlink と同期は `lib/claude_account_dir.py` に分け、置き場と排他は `claude_accounts` に残す

`lib/claude_accounts.py` は 859 行ある。symlink と `.claude.json` の同期は、置き場の決め方・排他・選び方を知らなくても
書け、パスだけを受ける関数として単体で試せる。呼ぶのは `claude_accounts` だけで、ラッパーと `supervise.py` のエントリ
ポイントは今の 1 つ（`account_env()`）のままにする（#1389 の決定 13）。登録の削除では、`claude auth logout` の前に symlink を
外す。logout が設定ディレクトリの中の何を消すかは本体が決めるため、先に共有側へ届かなくする。

根拠: Value 6（MVV 版 2）

### 決定 18: 同期の控えと認証の失敗の観測は、最新の 1 件を上書きで持つ

どちらも、次の判定に使うのは最新の値だけである（#1389 の決定 11 と同じ）。過去の値を失ってよいのは、切り替えと用意の
履歴を `log.jsonl` の `account`・`account_dir` の行が持つためである。

根拠: Value 1（MVV 版 2）

### 決定 19: アカウント側の `.claude.json` が JSON として読めないアカウントでは起動せず、NDF は壊れたファイルを直さない

用意のとき、アカウント側の `.claude.json` が JSON として読めなければ（0 バイトを含む。ファイルが無いのは読めるに含む）、
そのアカウントで claude を起動せず、次の候補へ移り、理由を画面の 1 行と記録に残す（I19。I6・I13 と同じ形）。そのまま
起動すると、対話では本体が `Configuration error` の 2 択の画面で止まり、ラッパーの最初の入力がそこへ入る。claude -p は
結果行を出さずに終了コード 1 で終わり、ファイルを初期化する（実測 I）。結果行が無いので、認証の失敗の結果行で受ける
経路（決定 13）には入らず、同じアカウントのまま以後の呼び出しが失敗しうる。起動の前に止めれば、どちらも起きない。

NDF が壊れたファイルを退避して空のファイルに直す形は採らない。用意は、アカウントの設定ディレクトリの実体を消さず、
移さず、上書きしない（I5）。壊れたファイルから何を戻すかは利用者が決める。本体に起動させて初期化を任せる形も採らない。
初期化で `oauthAccount` が消え、対話では 2 択の画面にラッパーの入力が入る。

利用者の戻し方は 2 つで、`references/relay.md` に書く。次の用意は、どちらの後も最初の同期になり（I18）、共有側の値に
そろう。

| 戻し方 | 操作 | その後 |
| --- | --- | --- |
| 退避から戻す | アカウントの設定ディレクトリの `backups/.claude.json.backup.<ミリ秒>` のうち、JSON として読める新しいものを `.claude.json` へ `cp` する（本体の案内と同じ操作） | `oauthAccount` とアカウントごとのキャッシュが残る |
| 壊れたファイルを消す | アカウントの設定ディレクトリの `.claude.json` を消す | `oauthAccount` は claude が次の応答で取り直す（実験 8）。最初の案内の印は共有側から写る（決定 7） |

書き戻し（`settle`）で読めないときは、起動を伴わないので、同期を飛ばして控えを消すだけである（決定 6）。用意と起動の
間や呼び出しの途中に壊れた場合は、この確かめを通らない（未確認のまま残ること）。

根拠: Value 2 / Value 6 / C3（MVV 版 2）
