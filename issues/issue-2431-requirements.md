# #2431: NDF Factory: 画面の地図の「予定」の画面に、作る課題（持ち主）が書かれていない（#2382 の受け入れ条件 2 の残り）

正は課題の本文（#2431）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

ndf v10.27.14（タグ `ndf--v10.27.14`、commit 84381ee8）のリリース後テストで、#2382 の受け入れ条件 2「まだ画面が無い機能は、載せる予定の画面と持ち主の課題が分かる」のうち、**持ち主の課題**が画面の地図に無い。

`docs/specifications/ndf-factory-screen-map.md` の「画面の地図」で状態が「予定」の 3 行（承認・請求と使用量・手元のマシン）は、載る機能だけを書き、どの課題がその画面を作るかを書いていない。

```text
| 未定 | 承認 | 個人・管理者・席 | 予定 | 承認の依頼・Web からの承認・通知 |
| 未定 | 請求と使用量 | 個人・管理者 | 予定 | 料金プランの料金・使用量の台帳・決済 |
| 未定 | 手元のマシン | 個人・管理者 | 予定 | 手元のマシンの登録・心拍 |
```

タグの時点（2026-11-02 21:50 JST に確かめた）と、確定仕様化の後の `develop` の両方で同じである。

## どこで見つけたか

- `docs/specifications/ndf-factory-screen-map.md` の「画面の地図」43〜45 行
- リリース後テストの記録: Pull Request #2426 のコメント

## なぜこの変更の範囲外なのか

リリース後テストは不合格を即時修正しない（`release-verification` の「合否を判定する」）。リリース後の修正は新しい変更として、モードの判定から始める。根拠: プロジェクト Value 7（判断の理由を残す・正本を 1 か所に）・スプリント Value 2（画面先行で地図を土台にする）（MVV 版 4）。

## 直さないと何が起きるか

画面を足す課題が、地図の「予定」の行を自分の持ち物か判断できない。#2382 の非機能の条件（運用・保守性）「画面を足す課題は、地図の行と翻訳のキーを足すだけで済む」の前提になる、行と課題の対応が無いままになる。#2382 が閉じられると、この条件の残りを持つ課題が無くなる。

## 目的

- 画面を足す課題が、画面の地図の「予定」の行を見て、その行が自分の課題の持ち物か（自分が作る画面か）を 1 回の読みで判断できる状態にする
- #2382 の受け入れ条件 2 の残り（まだ画面が無い機能の、作る課題）を満たし、#2382 が閉じた後もこの条件を持つ文書が残る状態にする

## 前提

- 前提 1: 承認の画面（承認の依頼・Web からの承認・通知）を作る課題は #2173 である。根拠: #2173 の受け入れ条件 5〜7 が「承認の画面」「判断の依頼の画面」を定め、受け入れ条件 4 が「承認の画面の URL」を Slack の通知へ入れる
- 前提 2: 請求と使用量の画面（料金プランの料金・使用量の台帳・決済）を作る課題は #2174（サブスクリプションと Bedrock の token 課金）である。根拠: #2174 の本文が「この課題の使用量の台帳」「決済の手段（Stripe など）」を持つ。#2174 の本文は画面をまだ受け入れ条件に書いていないため、画面を作るかどうかは #2174 の要求で決まる。この課題は地図に作る課題を書くだけで、#2174 の範囲を変えない
- 前提 3: 手元のマシンの画面（手元のマシンの登録・心拍）を作る課題は #2189（手元のマシン）である。根拠: #2189 の受け入れ条件 17 が「手元のマシンの一覧」の画面を定め、起票者の推定 S9 が「手元のマシンの一覧と登録の token の管理の画面を作る」とする
- 前提 4: 作る課題は、画面の地図の表の「予定」の行に、GitHub の課題の番号（`#<番号>`）で書く。列を足すか既存の列に書くかは設計で決める（未決 1）
- 前提 5: 状態が「あり」の行（すでに画面がある行）には、作った課題を書き足さない。#2382 の受け入れ条件 2 が課題を求めるのは「まだ画面が無い機能」だけである
- 前提 6: `factory/web/src/screens.ts` の予定の画面の定義（`approvals`・`billing`・`runners`）は、作る課題を持たない。画面の地図の文書が人の読む対応の正本で、`screens.ts` は経路の定義の正本である（文書の「概要」）。作る課題は経路を作らないため、`screens.ts` へ写さない

## 対象範囲

含む:
- 画面の地図（`docs/specifications/ndf-factory-screen-map.md`）の「予定」の 3 行に、作る課題を書く
- 画面の地図の冒頭の、画面を足す課題が行う手順の文に、「予定」の行を自分の課題が作るときの扱い（行を「あり」へ変える）を書く

含まない:
- 予定の画面そのものを作ること（#2173・#2174・#2189 が持つ）
- #2173・#2174・#2189 の本文と受け入れ条件を書き換えること
- `factory/web/src/screens.ts` と翻訳のファイルの変更（前提 6）
- 状態が「あり」の行へ、作った課題を書き足すこと（前提 5）
- 画面の地図のほかの節（ナビゲーション・動線・見本の画面）の変更

## 用語

| 用語 | 意味 |
| --- | --- |
| 画面の地図 | Factory の Web の画面の全体を 1 つの表にまとめた確定仕様（`docs/specifications/ndf-factory-screen-map.md`）。用語集の文脈 `ndf-factory` の語 |
