# #3518 の設計: 決定の記録

設計文書は [issue-3518-design.md](issue-3518-design.md) にある。外部の調査の表の番号（`STD`・`PRD`・`LIB`）はその文書の「外部の調査」の節を指す。

## 決定の記録

### 決定 1: 読み手のコードを変えずに宣言のキーの食い違いを落とすため、置き場の表の `keys` を読み手の約束として扱い、表とスキーマを突き合わせる

置き場の表の列 `keys` は、説明に「宣言の読み手はこの表に無いキーを読まない」と書かれた読み手への約束である。検査はこの約束を「コードが読むキー」として扱い、表とスキーマの食い違い（I2）と、表の行とスキーマの有無（I1）を落とす。キーを読むコードを足すときは表の `keys` に足すことになり、足したキーがスキーマと文書に無ければ落ちる。

構文木からキーを集める方法は採らない。2026-11-14 に宣言のファイル名を持つ 6 モジュールで添字・`.get`・`in` のキーの文字列を集めると、65 件だった。そのうち `core/route.py` の 20 件の大半は、宣言のキーではなかった。置き場の表の id を変数で渡す `domains/worktree/declaration.py` は読み手として見つからなかった。読み手を 1 つの読み口へ寄せてキーの道を文字列で渡させる方法は、宣言を読む 10 前後のモジュールの書き換えを要する。その中にはレーン lr-tail（`progress/`・`domains/release/`）と lr-fix-b（`testing/`・`domains/hooks/`）のファイルがあり、要求の境界に当たる。

初版で、表の `keys` を読み手のコードに合わせて直す。直すキーは、`domains/worktree/declaration.py` の `deps`・`localenv`・`testenv`・`follow_branch` などである。表に載らないキーを読むコードを機械で見つける形は、範囲外の課題として起票する。課題の題は「ndf-next: 宣言の読み手を 1 つの読み口に寄せ、置き場の表に無いキーを読むコードを検査で落とす」である。lr-tail・lr-fix-b のマージの後に着手する。

この扱いは受け入れ条件 3 の「コードが読むキー」を「置き場の表の `keys` に載るキー」に狭めて読むことになる。この読み方は決定 11 で決めた。

- 作り方: 自前で作る
- 比べた候補: LIB1・STD1

根拠: Value 3 / Value 11 / Value 13（MVV 版 7）

### 決定 2: 同じ事実を 2 か所に持たないため、契約のページはすべて生成し、手で書くのは正本の表に無い事実（宣言のキーの意味・結果の形・Skill の入出力）だけにする

| 事実 | 正本 | 規約での扱い |
| --- | --- | --- |
| 宣言の行・置き場・範囲・`keys`・`main_keys` | 置き場の表 | 生成（範囲は `tracked` から導く） |
| 宣言のキーの型・説明・既定値・取りうる値・例 | 宣言のスキーマ（手書き） | 生成 |
| 副命令の一覧と引数 | 副命令の表とコードの引数の定義 | 引数のスキーマも文書も生成 |
| 副命令の結果の `metrics`・`items` | 結果のスキーマ（手書き） | 生成 |
| 終了コード・止まった理由・環境変数・hook・受け渡しのファイル | それぞれの表 | 生成 |
| Skill の入出力 | 公開する Skill はエントリポイントの表、ほかは Skill の入出力の表 | 生成 |

既存の文書の生成のライブラリ（LIB2・LIB3）は、スキーマ 1 つを 1 ページにするだけである。置き場の表・副命令の表・公開か内部かの列と組み合わせられず、LIB2 は依存を 6 つ増やす。描画は事実の表を読む既存の部品（`ndf.contracts.facts`）の上に自前で書く。スキーマの語は JSON Schema 2020-12 の注釈（STD1）を使い、置き場と読む工程だけを `x-ndf-` の注釈の語（STD2）で足す。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: LIB2・LIB3・STD1・STD2

根拠: Value 11 / Value 8（MVV 版 7）

### 決定 3: 副命令のモジュールを変えずに引数を取り出すため、引数を読む直前で止めて argparse の定義を受け取り、下位の命令とその引数まで載せる

副命令の `main` を、argparse が引数を読む関数（`parse_args`・`parse_known_args`）の呼び出しで止め、その時点の定義から引数の木を作る。下位の命令（`_SubParsersAction` の選択肢）を辿り、下位の命令ごとの引数まで載せる。AI と連携システムが打つのは下位の命令の形（`ndf lanes add …` など）だからである。2026-11-14 の試作で、22 個のうち 20 個から木を取り出せた（下位の命令は最多で `lanes` の 14 個、引数は合わせて約 430 個）。

argparse を使わない副命令は 2 個ある（`launch-args` は引数を受けず、`notify` は `send` だけを受ける）。この 2 個は、引数を手書きの引数の表（`contracts/domains/manual-args.json`。事実の表の形）の行に書く。規約の生成は、その行から引数のスキーマを作る。引数のスキーマは 22 個すべてが生成物になる。`contracts/schemas/io/` の引数のスキーマを書くのは、規約の生成だけである。`--write-spec` が手で書いたものを上書きすることは無く、生成の差分の検査（I9）は 22 個すべてを比べる。検査は、手書きの引数の表に行を持つ副命令が argparse を使い始めたら（取り出せるようになったら）落とし、行を消して生成へ移させる（I13）。

手で書いた引数のスキーマを同じディレクトリに置き、印 `x-ndf-manual: true` で生成から外す形は採らない。同じ種類のファイルを 2 つの書き手が書くことになり、`--write-spec` が上書きしない規則と、差分の検査から外す規則を別に持つことになる。

すべての副命令に引数の定義を返す関数 `parser()` を持たせる形は採らない。22 個のうち 6 個（`answer`・`lanes`・`progress`・`test-slot`・`relay`・`hooks`）が、要求の境界の挙げるパスにある。並列の計画 p6 のレーン lr-tail・lr-fix-b が持つパスまで含めると、10 個（ほかに `release-steps`・`loop`・`launch-args`・`worker`）になる。argparse から文書を作るライブラリ（LIB4・LIB5）は Sphinx か man ページの形を出すだけで、JSON Schema を出さない。argparse の内部の属性（LIB6）に頼る点は、引数の取り出しのテストが Python の版の上げで壊れたことを落とすことで受ける。

- 作り方: 自前で作る
- 比べた候補: LIB4・LIB5・LIB6

根拠: Value 3 / Value 11（MVV 版 7）

### 決定 4: 手順書の置き換え用の値で誤検出しないため、書かれた呼び出しの照合は副命令・下位の命令・引数の名前だけを見て、値の型を見ない

Skill の本文の呼び出しは `ndf answer <ゲート> <番号>` のように値を置き換え用の語で書く。値の型まで照らすと、置き換え用の語がすべて型の誤りになる。照合は、行を `shlex` で語に分け、`ndf` か `bin/ndf` の後の語を副命令と下位の命令として引数の木を辿り、`-` で始まる語を引数の名前として木に当てる。位置の引数の数は見ない。

根拠: Value 3 / Value 13（MVV 版 7）

### 決定 5: 設定ページで書き誤りを捕まえ、実物の宣言も通すため、宣言のスキーマは知らないキーを拒み、ndf-next が読まないが実物に残るキーは非推奨として載せる

最上位とオブジェクトの値は `additionalProperties: false` にする。設定ページと連携システムの検証で、キーの書き誤りを捕まえられる。実物の `.ndf/` には、ndf-next が読まないキーが残る（2026-11-14 に `project.json` の `test_duration`・`supervise.json` の `test`）。それらを `deprecated: true`（STD1）と「ndf-next は読まない」の説明で載せる。非推奨のキーは置き場の表の `keys` との突き合わせ（I2）から外す。

知らないキーを許す形は、書き誤りが黙って通るため採らない。実物の `.ndf/` から古いキーを消す形は、今の版（`plugins/ndf/`）が読む設定を変え、利用者の設定の書き換え（C7）に当たるため採らない。

- 作り方: 標準に倣う
- 比べた候補: STD1・PRD1

根拠: Value 8 / C7（MVV 版 7）

### 決定 6: Skill の入出力を 1 か所で持つため、事実の表 `skill-io` を置き、公開する Skill の引数と環境変数はエントリポイントの表から読む

Skill の入出力の表（`contracts/domains/skill-io.json`）は、事実の表の形（`fact.schema.json`）で書く。既存の検査（規則 `fact-table`・`const-fact`）が、そのまま形と重複を見る。公開する Skill（エントリポイントの表の種類 `skill`・`block` の `target`）の引数と環境変数は、エントリポイントの表が正本である。`skill-io` の行は `args`・`env` を持たず、持てば規約の検査が落とす。

Skill の frontmatter に持つ形は採らない。Skill の本文は S1a #3303 が移す途中で、本文の書き換えはこの課題の範囲の外である。frontmatter の検査（`scripts/check-skill-frontmatter.py`）は、今の版のものである。ndf-next の事実の表の検査とは別の仕組みになる。

根拠: Value 11 / Value 9（MVV 版 7）

### 決定 7: ページの長さを 500 行以下に保つため、契約のページを 1 つのディレクトリの面ごとの 8 ページに分け、検査を責務ごとの 4 モジュールに分ける

契約のページは `plugins/ndf-next/docs/contracts/` に 8 ページで置く。ページは `index.md`・`declarations.md`・`commands.md`・`exit-codes.md`・`env.md`・`files.md`・`hooks.md`・`skills.md` である。副命令だけで、下位の命令と引数の行が約 430 ある。宣言の文書と契約のページの 2 ページにすると、規約の側が 500 行を超える（`document-style` の分割の基準）。`index.md` は面の一覧と、公開と内部の約束（内部は予告なく変えてよい）を持つ。

スキーマの置き場は、要求の仮の置き場のとおり `contracts/schemas/declarations/`・`contracts/schemas/io/` にする。検査は `src/ndf/checks/` に、モデル（読む）・引数の取り出し・描画（純粋な処理）・検査（突き合わせと書き込み）の 4 モジュールで置く。行き先の表には 3 行を足す。

| `plugins/ndf-next/docs/contracts/` | そのまま移す（`plugins/ndf/docs/contracts/` へ。入れ替えの後に `ndf check --write-spec` を打って差分が 0 件） | S2（中身は #3518） | 11.0.0 |

### 決定 8: 公開する面の表の不在の間も置き場を約束するため、エントリポイントの表に種類 `spec` の行を 3 つ足し、公開か内部かを表から導く

要求の前提 8 のとおり、S #3390 の公開する面の表が無い間は、エントリポイントの表と置き場の表の列 `reader` を公開する面の表として扱う。規約の置き場はエントリポイントの表の新しい種類 `spec` の 3 行（契約のページ・宣言のスキーマ・入出力のスキーマ）で持つ。宣言のスキーマの行の `files` に、公開する宣言（置き場の表で `tracked` が真の 18 行）の id を並べる。個人の設定（`worktree.local.json`）は連携システムの設定ページの対象でないため内部にする。

契約のページの公開か内部かの列は、表に当たるかで導き、手で書かない。手で書く列を置くと、表との一致を別に確かめることになる。公開する面の表の行が規約のどの項目にも当たらなければ、規約の検査が落とす（I10）。S #3390 が公開する面の表の置き場を別に決めたら、規約のモデルが読む表をそこへ向け直す。

根拠: Value 11 / Value 4（MVV 版 7）

### 決定 9: テストの用意を作り足さずに実際の出力を確かめるため、テストの間に出るすべての結果 JSON を結果のスキーマで確かめ、ok の出力が無い副命令を実行の終わりに落とす

結果 JSON を出す 1 か所（`ndf.contracts.result.emit`）をテストの間だけ包む。`emit` は結果 JSON と終了コードを受け、標準出力へ 1 行で書き、終了コードを返す（`src/ndf/contracts/result.py:144-154`）。包んだ `emit` は、受けた結果 JSON と終了コードの組を結果の契約（`result.errors`。状態・止まった理由と終了コードの対応を見る）で確かめる（I5）。あわせて、結果 JSON を副命令の結果のスキーマで確かめる（I14）。既存のテストが作った git のリポジトリ・偽の GitHub などの用意をそのまま使える。全体の実行の終わりに、ok の出力を 1 度も確かめなかった副命令の名前で落とす。

この検査は、標準出力（結果 JSON）と終了コードの両方を、すべての副命令について 1 つの仕組みで確かめる。そのため、K #3367 の「すべての副命令の標準出力と終了コードを確かめる 1 本のテスト」に当たる（要求の前提 6）。`emit` を通らずに終わる経路の終了コードは見えず、設計の「未確認のまま残ること」に残す。一部のテストだけを流したときは、終わりの確かめを行わない。

副命令ごとに呼び出しと用意を書いた専用のテストを並べる形は、22 個それぞれの用意（git・GitHub・状態の置き場）を作り直すことになるため採らない。既存のテストが ok の出力を出さない副命令にだけ、`tests/cli/test_every_output.py` に呼び出しを足す。

根拠: Value 2 / Value 13 / Value 11（MVV 版 7）

### 決定 10: 生成と検査を 1 つの仕組みにするため、規約の検査を `ndf check` の規則にし、書き込みは `ndf check --write-spec` で行う

生成と検査は同じ規約のモデルと描画を通り、検査は描画した中身とコミットされた中身を比べる。CI のジョブ ndf-next は既に `ndf check` を打つため、ワークフローを変えずに受け入れ条件 11・18 が CI で働く。要求の検証手段は打ち方を設計に委ねている。

副命令を新しく足す形は、要求が副命令の追加を範囲の外にしているため採らない。リポジトリの `scripts/` に別のスクリプトを置く形は、`ndf check` の外にもう 1 つの検査のエントリポイントを作ることになるため採らない。

根拠: Value 3 / Value 11（MVV 版 7）

### 決定 11: 要求の境界を守ってこの課題を他のレーンの完了で止めないため、受け入れ条件 3 を「置き場の表の `keys` に載るのにスキーマに無いキー」を落とすことと読む

受け入れ条件 3 の「ndf-next のコードが読むのに文書とスキーマに無いキー」は、次のとおりに読む。置き場の表（`contracts/domains/ndf-files.json`）の `keys` を読み手の約束とし、表の `keys` に載るのにスキーマに無いキーを落とす（決定 1 の前提）。表の `keys` に載らないキーを読むコードを足したことは機械では見つからず、レビューに頼る。コードから見つける検査は、宣言の読み手を 1 つの読み口へ寄せる範囲外の課題へ回す（起票は並列の計画 p6 のオーガナイザーへ同意を求めた。依頼 lspec-q7f47670784d0）。

この課題で読み手を 1 つの読み口へ寄せる形は採らない。宣言を読む 10 前後のモジュールを書き換え、レーン lr-tail・lr-fix-b のファイルを含むため、要求の境界に当たる。この課題が、両レーンのマージまで止まる。構文木からキーを集める方法は 65 件の候補の大半が宣言のキーでなく、使えなかった（決定 1）。

根拠: Value 5 / Value 13（MVV 版 7）

### 決定 12: 誤検出の数を測らない規則で検査を落とし続けないため、受け入れ条件 5 を「置き場の表にあって規約に無いファイル」を落とすことと読む

受け渡しのファイルのページは置き場の表から生成するため、表の行は必ず規約に載る。表に無いパスを文字列で書いて読み書きするコードを見つける検査は、決定 11 の範囲外の課題に含める。

この課題で `.ndf/` や状態の置き場を指すパスの文字列を構文木から集める規則を `spec-io` に足す形は採らない。決定 11 の構文木の方法と同じく誤検出の数が分からず、測らずに足すと検査が落ち続けるおそれがある。

根拠: Value 13（MVV 版 7）

### 決定 13: 他の子の進み具合でこの課題を止めず、持ち主の違う表の行を変えないため、公開する面の表で順番が `caller-first` の行を規約の検査 I10 の対象から外す

公開する面の表の行 `gate-record` は、副命令の表に無い `gate` を指す。この行は順番が `caller-first`（入れ替えの前に呼び手と合わせる行）で、持ち主は子 P2 である。順番が `caller-first` の行は I10 の対象から外し、契約のページに「呼び手と合わせる前の行」として載せる。判定は表の既存の列 `order` だけで決まり、他の子の行を変えない。

P2 の子が直すまで待つ形は、他の子の進み具合でこの課題が止まるため採らない。この課題で行を直すか消す形は、持ち主の違う表の行と、呼び手（volareinc/nd-factory#183）との約束を変えるため採らない。

根拠: Value 5 / Value 11（MVV 版 7）
