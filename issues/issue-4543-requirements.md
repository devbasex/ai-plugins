## 何が起きたか

2026-11-26、利用者が、NDF の AI が書いた設計書と Pull Request（PR。変更をマージする前にレビューを受けるためのもの）の本文を読んでいて、どこまでが現状で、どこからが改善の案なのかを区別できませんでした。いまの状態の説明も、これから変える内容も、同じ現在形で書かれていたためです。

実例は [PR 4509](https://github.com/devbasex/ai-plugins/pull/4509) の概要です。書き直す前は、次の文で始まっていました。

> 並列の計画のレーンはディレクトリ単位で書いた触る場所で待たされ、スプリントの中の実装のプランは触るファイルを持たずにすべて直列になっています。この設計は、設計の結果の「触るファイル」を両方の重なりの判定へ渡します。レーンはファイル単位、実装のプランは関数の単位まで分けて判定します。

書き分けると、次のようになります。

> **これまで**、並列の計画のレーンはディレクトリ単位で書いた触る場所で待たされ、スプリントの中の実装のプランは触るファイルを持たずにすべて直列になって**いました**。**この設計では**、設計の結果の「触るファイル」を両方の重なりの判定へ渡すように**します**。レーンはファイル単位、実装のプランは関数の単位まで分けて判定する**ようにします**。

## 種類

機能追加（現状と案を書き分けるという約束は、これまで配っている手順書にも書き方の基準にも無く、新しく足すため）

## 今の姿

NDF は、AI が書く設計書・PR の本文・承認を求める文について、読み手に通じる文章にするための書き方の基準と手順書を配っています。書いた文章の一部は、書いたときの会話を知らない別の AI に読み手の立場で読ませて確かめます（この役を「読み手役」と呼びます）。

| 項目 | これまでの状態（2026-11-27 に確認） |
| --- | --- |
| 書き分けの指示 | [書き方の基準](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/contracts/data/writing-criteria.md) にも、[設計書のテンプレート](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/design/references/design-template.md) や [PR を作る手順書](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/pr/SKILL.md) にも、現状と案を書き分ける指示はありませんでした |
| 読み手役が指摘する文 | 知らない言葉、不自然な日本語、説明の不足、詰め込みすぎの 4 つの型でした。現状と案を区別できない文は、型として挙げていませんでした |
| 読み手役が読むもの | 要求仕様、設計書、承認を求める文と承認資料などです。PR の題と本文は、書いた AI が自分で読み直していました（[読み手役の決まり](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/document-rebuild/SKILL.md)） |

利用者の指摘の後は、開発中の AI に作業の指示で書き分けを伝えて対応していました。配っている手順書には入っていませんでした。

### エンジニア向けの補足

- 上の確認は `git grep -nE 'これまで|過去形|現在形|時制' origin/main -- plugins/ndf/skills plugins/ndf/contracts plugins/ndf/agents` で行った。当たったのは確定仕様を現在形で書く指示（`plan-to-spec`）やイベントを過去形で書く指示などで、概要や承認資料の書き分けの指示は無かった
- 読み手役への指示に入る基準は、書き方の基準の「3. 読み手に通じない文の 4 つの型」のセクションだけである（`plugins/ndf/src/ndf/contracts/writing.py` の `types_section`）

## 何を足すか・変えるか

AI が次の書き分けで文章を書き、読み手役もそれを確かめるようにします。

| 何を書くとき | 書き方 |
| --- | --- |
| いまの状態（変える前） | 「これまで」「従来」などの語を入れるか、過去形で書く |
| 改善の案（変えた後） | 「この PR により〜する」「この設計では〜する」のように、これからの話だと分かる形で書く |

| 変わる点 | これまで | この変更の後 |
| --- | --- | --- |
| 設計書の概要 | 現状も案も現在形で書かれることがあった | 上の表のとおりに書き分ける |
| 設計の PR と実装の PR の本文の概要 | 同上 | 同上 |
| 承認を求めるときの承認資料と質問の文 | 同上 | 同上 |
| 読み手役の確かめ | 現状と案の混同は、指摘する型に入っていなかった | 現状と案を区別できない文を指摘する |

## なぜ困るか

読み手が現状と案を取り違えると、「すでにそう動いている」のか「承認するとそう変わる」のかが分からないまま判断することになります。承認する人は文章を読み返したり、書いた側に聞き直したりする必要があり、承認の判断を誤るおそれもあります。放置すると、設計書や PR が作られるたびに同じことが起きます。

## 目的

読み手が 1 回読んだだけで、現状とこれから変える内容を区別して、承認やマージの判断ができるようにすることです。

## 対象範囲

含む:

- 設計書の概要（題の直後の要約の段落と、解き方の全体像）の書き方
- 設計の PR と実装の PR の本文の概要の書き方
- 承認を求めるときの承認資料と質問の文の書き方
- 読み手役が、現状と案を区別できない文を指摘すること

含まない:

- すでに書かれた設計書・PR 本文の書き直し（これから書く文章を直すことが目的のため）
- 確定仕様（リリース後に実際の振る舞いを記録する文書）の書き方（現状だけを書く文書で、案と混ざらないため。現在形のままにする）
- 変更履歴・コミットメッセージ・レビューの指摘と返信
- PR の本文を、読み手役が読む対象に新しく加えること
- 「これまで」などの語があるかを機械で調べて合否を決める検査（語の有無では、読み手が区別できるかを判定できないため）
- テンプレート全体の形をそろえること（[テンプレートの形をそろえる課題](https://github.com/devbasex/ai-plugins/issues/4545) で扱う）

## 受け入れ条件

- [ ] 1. 設計書と Pull Request の概要を AI に書かせる手順と指示に、上の書き分けが入っている（判定: 設計書の概要を書く指示と、設計の PR・実装の PR の本文の概要を書く指示の両方から、「何を足すか・変えるか」の書き分けの表の 2 行にたどり着ける）
- [ ] 2. 文書を読み手役の AI に読ませて確かめるときに、現状と改善の案を区別できない文が指摘の対象になる（判定: 「何が起きたか」の書き分ける前の引用を読み手役に読ませると、現状と案を区別できないことが指摘の一覧に挙がる。書き分けた後の引用では、その指摘が挙がらない）
- [ ] 3. 実装した後に作る設計の Pull Request の概要で、現状と改善の案が書き分けられている（判定: この変更を含むバージョンで最初に作る設計の PR の本文の概要と、その設計書の概要を人が読み、現状の文と案の文を 1 文ずつ区別できる）
- [ ] 4. 承認資料と質問の文を AI に書かせる手順と指示にも、同じ書き分けが入っている
- [ ] 5. 承認資料の組み立てなど、仕組みが読み取る設計書の見出しと PR の本文の見出しは変わらず、自動テストが通る

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない |
| データ | 変更なし |
| 既存の振る舞い | AI が書く設計書・PR の本文の概要・承認資料・質問の文の書き方が変わる。読み手役が指摘する文が増えるため、書き直しが増えることがある |
| 既存の決まりとの関係 | 設計の PR の本文は、解き方と決定を言い換えて書かない決まりになっている。この決まりは変えず、本文に書く文の中で現状と案を書き分ける |
| ほかの変更との重なり | [テンプレートの形をそろえる PR](https://github.com/devbasex/ai-plugins/pull/4548) が、同じテンプレートと手順書を変える（2026-11-27 時点で未マージ） |

## リクエスト（原文）

> 設計やPR本文の概要について。全て現在形でかかれているため、どこまでが現状でどこからが改善プランなのかが分かりません。
>
> 例(PR #4509)
> 並列の計画のレーンはディレクトリ単位で書いた触る場所で待たされ、スプリントの中の実装のプランは触るファイルを持たずにすべて直列になっていた。設計の結果の「触るファイル」を両方の重なりの判定へ機械で渡し、レーンはファイル単位、プランは関数の単位まで分けて判定する。実装の途中で触る範囲が広がっても止めず、単位の PR が変えたファイルを拾って、ほかのレーンと重なればオーガナイザーへ知らせる。比べた案は「決定の記録」に、調べた製品と標準は末尾の「外部の調査」にある。
>
> * 現状は「これまで」「従来」などの副詞を入れるか過去形で書く。
> * 改善案は「このPRにより～とする」や「この設計で～」など、将来の話であることを示す
>
> Issueを起票して現在の開発計画に入れてください。

（書き手: 利用者、日付: 2026-11-26）
