# #2384 の設計: 決定の記録

[設計文書の本体](issue-2384-design.md) の決定の記録である。根拠の行の MVV は、プロジェクト MVV 版 5 と、マイルストーン「25 Neural Development Factory」のスプリント MVV（sha256 の先頭 8 文字 44cd096d）である。

## 決定の記録

### 決定 1: すべての操作を配列で受け渡すため、取得と削除は鍵の query の繰り返し、作成・更新・操作は本文の配列にする

取得を `GET` のままにするのは、読み取りと書き込みをメソッドで分け、オフラインの見せ方（最後に受け取った一覧と詳細を読む）とブラウザの開発ツールで要求を読みやすく保つためである。削除も鍵の query にし、`DELETE` の本文を使わない。HTTP の仕様（RFC 9110 の DELETE の節）は `DELETE` の本文に一般的な意味を定めておらず、実装によっては要求を断ると書いている。一覧は条件で集めた値だけを返し、要素の結果で包まない。

すべての操作を `POST` にして本文で鍵を渡す形は採らない。読み取りまで書き込みと同じメソッドになり、操作の扱い（読み取り・書き込み）をメソッドから読めなくなる。

根拠: Value 6 / スプリント Value 2（MVV 版 5・スプリント MVV 44cd096d）

### 決定 2: 認可の単位を今と変えないため、経路の変数はアカウントの ID だけにし、要素ごとに持ち主を照らす

アカウントを経路に置く今の決め方（`account_id` を token に載せず経路から解決する。認証の確定仕様の判断）を保つ。経路のアカウントを解決できなければ、今と同じく要求全体を 403 にする（受け入れ条件 26）。要素の識別子（実行・ループ・リポジトリ）は、そのアカウントに属するかを要素ごとに照らし、属さない要素だけを `forbidden` にする（受け入れ条件 7・15）。

要素ごとに `account_id` を持たせ、経路からアカウントを外す形は採らない。画面のリンクからどのアカウントの画面かを読めなくなり、1 回の要求の中でアカウントの解決が要素の数だけ走る。アカウントそのものの操作（`getAccount`・`setExecutionMode`）だけは、要素がアカウントであるため要素ごとに解決する。

根拠: Value 7 / スプリント Value 4（MVV 版 5・スプリント MVV 44cd096d）

### 決定 3: 一部の失敗を読めるようにするため、成功の状態は 200 にし、要素ごとに状態と本文を持つ結果を入力と同じ順で返す

要素の結果に今の誤りの状態（403・404・409・422）を残すのは、画面が状態で文言を分けている（`factory/web/src/context.tsx`）ためで、画面の分岐を変えずに済む。要求全体を断るのは、資格情報・操作の扱い・要素の数と重複・経路のアカウントの 4 つと、操作の記録の追記の失敗（503）だけにする。

207（Multi-Status）は採らない。WebDAV の XML の本文を前提にした状態で、JSON の API で使うと、呼ぶ側が 200 と 207 の両方を扱うことになる。

根拠: スプリント Value 1（MVV 版 5・スプリント MVV 44cd096d）

### 決定 4: 送り直しで 2 重に作らないため、新しい識別子を作る 4 つの作成だけに冪等の鍵を求め、鍵の行を作るものと同じ表へ同じトランザクションで書く

冪等の鍵が要るのは、送り直したときに別の識別子のレコードがもう 1 つできる作成だけである（スプリントの実行・開発ループ・チーム・委任の資格情報）。席とリポジトリの登録は鍵が自然に決まり（アカウントと利用者、アカウントとリポジトリ）、2 回目は今と同じ結果になる。更新・削除・取り消しは同じ値の書き込みで、送り直しても結果が変わらない。

鍵の行を別の表に置き、作成の前に鍵を取り、作成の後に結果を書く形は採らない。作成と鍵の書き込みの間で落ちると、鍵だけが残って結果が無い状態ができる。同じ表の 1 つのトランザクションなら、両方が書かれるか、どちらも書かれないかになる。

根拠: Value 7（MVV 版 5・スプリント MVV 44cd096d）

### 決定 5: 画面・API・MCP・認可の対応を 1 か所から導くため、契約に操作の扱いと鍵を拡張として持ち、操作の表を生成する

操作の扱い（`x-ndf-access`）・要素の鍵（`x-ndf-keys`）・作った識別子（`x-ndf-id`）を契約に持ち、操作の表をそこから生成する。API の経路の登録・範囲の照合・記録の鍵・MCP のツール・画面の要求の組み立てが同じ表を読むため、契約に操作を足すと 4 か所へ同時に届き、片方だけの操作ができない（受け入れ条件 1・2）。生成物はコミットし、今の型の生成と同じく `--check` で食い違いを落とす。

扱いを API のコードの表に持つ形は採らない。契約を読む MCP と画面と検査が、もう 1 つの表を読むことになり、正が 2 つになる。

根拠: Value 5 / Value 8 / スプリント Value 4（MVV 版 5・スプリント MVV 44cd096d）

### 決定 6: MCP のツールが別の保存の経路を持たないため、MCP の受け口はツールの呼び出しを同じアプリの経路へ内部の要求として送る

MCP の受け口が受け取る依存は、アプリの要求の関数（Hono の `app.request`）1 つだけにする。認証・範囲の照合・要素の検査・認可・記録が、画面と API と同じ処理をそのまま通る（受け入れ条件 3）。内部の要求は資格情報の検証をもう 1 度行い、表の読み出しが 1 回増えるが、読み出し 1 回は単価 100 万回で $0.125 の水準である。

MCP の受け口がユースケースの関数を直に呼ぶ形は採らない。認可と記録を MCP の側にもう 1 つ書くことになり、片方だけを直す誤りが起きる。

根拠: Value 7 / スプリント Value 4（MVV 版 5・スプリント MVV 44cd096d）

### 決定 7: 新しい認可サーバーを足さずに出すため、MCP の委任の認証は Factory が発行した資格情報を `Authorization` で直に受け、MCP の認可の仕様（OAuth 2.1）には今は沿わせない（未決 5）

MCP の仕様は認可を任意とし、独自の認証の方式を認めている（本体の「あるべき姿の根拠」）。直に受ける形なら、人が画面で発行して値を MCP のクライアントの設定へ写すだけで使え、要求の前提 6（発行と取り消しは人が画面で行う）にそのまま合う。仕様に沿わせるには、Factory に認可サーバー（認可と token の経路・PKCE・クライアントの登録・保護されたリソースのメタデータ）を作る必要がある。Cognito はクライアントの動的な登録を持たず、取り消しの直後から断る条件（受け入れ条件 12）も Cognito の token の検証だけでは満たせない。

この形では、1 時間を超えて動くエージェントのために、人が 1 時間ごとに発行し直すことになる。更新の token で解く場合は MCP の認可の仕様へ移り、委任の資格情報の表と範囲と人だけの操作の判定はそのまま使える。この形で出すかを承認ゲート 1 で利用者が見る（本体の「未確認のまま残ること」）。

根拠: Value 1 / Value 3 / スプリント Value 6（MVV 版 5・スプリント MVV 44cd096d）

### 決定 8: 取り消しを次の要求から効かせるため、委任の資格情報は不透明な値にし、要求のたびに表を強い整合で読む

値は `ndfd_<資格情報の ID>_<秘密>` で、ID で行を引き、秘密の SHA-256 を一定時間の比較で照らす。頭の `ndfd_` で Cognito の token と分ける。署名した token（JWT）は、取り消しを効かせるために結局は表を読む必要があり、署名の鍵の管理が増えるだけになるため採らない。照合の結果をためる（キャッシュする）形も、取り消しの直後の要求を通してしまうため採らない。

根拠: Value 7 / スプリント Value 4（MVV 版 5・スプリント MVV 44cd096d）

### 決定 9: 人が選びやすくするため、範囲は読み取りだけと読み書きの 2 つ、期限は 5 分〜1 時間にし、アカウントで絞る範囲は持たない

受け入れ条件 13 が求める区別は読み取りと書き込みの 2 つで、操作の扱い（`read` / `write`）と 1 対 1 に対応する。画面の期限の選択肢は 15 分・30 分・1 時間で、API は 300〜3,600 秒を受ける。アカウントや操作ごとに範囲を絞る形は、発行の画面の入力が増え、委任の側に認可の分岐を持つことになる（I6）。今の要求に絞る条件が無いため持たない。

根拠: スプリント Value 1 / スプリント Value 4（MVV 版 5・スプリント MVV 44cd096d）

### 決定 10: 人の承認を委任で確定させないため、扱い `human` の操作を 10 に定める

承認と判断の答え（`answerLoopPending`・`resolveStalledRelease`）、共通原則の C1 に当たるモデルの認証情報の保存と削除（`putModelCredential`・`deleteModelCredential`）、C2 に当たる席の追加・変更・削除とチームの作成（`addSeat`・`changeSeat`・`removeSeat`・`createTeam`）、委任の資格情報の発行と取り消し（`createDelegation`・`revokeDelegation`。要求の前提 6）の 10 である。#2173 が足す承認の操作も扱い `human` で足す。

リポジトリの登録と外す操作、実行の形態の変更は `write` にする。登録は GitHub の画面で人が認可した結果（`proof`）が無いと通らず、外す操作と実行の形態の変更は、人の承認が要る操作の一覧に当たらない。

根拠: C1 / C2 / スプリント Value 4（MVV 版 5・スプリント MVV 44cd096d）

### 決定 11: 記録の欠けを残さないため、記録の追記に失敗したら操作を 503 で返し、記録の全体を構造化ログへ出して補えるようにする（未決 1）

スプリント Value 4 は、読み取りを含むすべての操作を記録に残すことを求める。操作を通して後から補う形は、補う仕組み（再送のキューと、その失敗の扱い）が新しく要り、補えなかった記録を見つける手段も要る。503 にすると、読み取りは応答を返さず、書き込みは既に行われたことがあるが、送り直しは冪等の鍵と同じ値の書き込みで 2 重にならない（決定 4）。追記の失敗の 1 行は構造化ログに残り、記録の表へ入れ直せる。

この決定は承認ゲート 1 で利用者が決める項目で、可用性を優先するなら、503 にせず構造化ログの 1 行だけで補う形へ切り替えられる。切り替えても、記録の書き手の外の形は変わらない。

根拠: スプリント Value 4（MVV 版 5・スプリント MVV 44cd096d）

### 決定 12: 秘密と個人情報を記録に書かないため、記録の項目を許可した鍵の一覧だけで組む

記録は要求の本文を写さず、許可した 10 の鍵の値と固定の列だけを持つ。書かない値を並べる禁止の一覧は、新しい操作が新しい秘密の項目を足したときに漏れる。許可した鍵の一覧なら、足した項目は記録に入らない。検査は、すべての操作の鍵がその一覧に入っていることを確かめる。

根拠: Value 1 / スプリント Value 4（MVV 版 5・スプリント MVV 44cd096d）

### 決定 13: 呼び出し元の種類を偽れないようにするため、種類は資格情報の種類と MCP の受け口の内部の印だけで決める

Cognito の token は `screen`、委任の資格情報の API への直の要求は `api`、MCP の受け口が送る内部の要求は `mcp` にする。内部の印は Hono の要求の環境（`app.request` の第 3 引数）に置き、外から届くヘッダーでは決めない。Cognito の token を画面の外から使う要求も `screen` になるが、人の直の操作であることに変わりはない。

根拠: スプリント Value 4（MVV 版 5・スプリント MVV 44cd096d）

### 決定 14: 新しい実行基盤を足さないため、MCP の SDK は `@modelcontextprotocol/server` 2.4 を使い、状態を持たない JSON の 1 応答で既存の API の Lambda に置く

このパッケージは MCP の 2026-07-28 版に対応し、Web 標準の要求と応答で動く受け口を持つため、Hono の経路から `c.req.raw` を渡して使える。依存は `zod` と同じ系列の `core` だけである。旧来の `@modelcontextprotocol/sdk`（1.32）は Express と関連の依存を持ち込み、対応する版も 2025-11-25 までである。JSON-RPC と版の取り決めを自前で書く形は、仕様の版が変わるたびに直す範囲が増えるため採らない。

根拠: Value 4 / スプリント Value 6（MVV 版 5・スプリント MVV 44cd096d）

### 決定 15: 1 回の承認で読み切れる量に収めるため、設計は 1 本にし、実装は 4 本の Pull Request に分けて順に入れる（未決 4）

設計を 1 本にするのは、4 つの部分が操作の表と操作の登録の層を共有し、分けると同じ前提を 4 回承認することになるためである。実装は次の順に分け、どの Pull Request も画面の Vitest と Playwright が通る状態で入れる。

| 順 | 中身 | 前提 |
| --- | --- | --- |
| 1 | 契約の配列化・操作の表と生成・操作の登録の層・要素ごとの実行・作成の冪等の鍵・画面とダミーの API クライアント・対応の検査（MCP を除く） | — |
| 2 | 委任の資格情報（検証・管理・画面）と、扱い `human` と範囲の照合 | 1 |
| 3 | 操作の記録 | 1 |
| 4 | MCP の受け口と、MCP のツールの対応の検査 | 2 |

承認ゲート 2 は 4 本がそろった後の 1 回にする。4 つの課題へ分けるかは承認ゲート 1 で利用者が決める。

根拠: Value 2（MVV 版 5・スプリント MVV 44cd096d）
