# #712 / #713: 同じ上位原因を持つ課題群を束ねる判定と、構造の判断の担い手

設計は [issue-712-713-design.md](issue-712-713-design.md) にある。この文書は「何を満たすか」だけを扱う。

**2 つの課題は 1 本の Pull Request で直す。** #713 は #712 で決まる判定の形を前提にし、
どちらも `plugins/ndf/skills/issue-upkeep/SKILL.md` の「既存の Skill との境界」を触る。分けると
同じ節を 2 本の Pull Request が同時に書き換える。

## 依頼の原文

> /ndf:development-workflow https://github.com/devbasex/ai-plugins/issues/712 https://github.com/devbasex/ai-plugins/issues/713
>
> 今後のissue解決の進行に関わるので、先に直してしまいましょう。

**解釈。** 2 件を工程に乗せて直す。「先に」は着手の順序であり、工程を省くことではない。

## 目的

- 棚卸が同じ上位原因を持つ課題群を見つけたとき、**その群を記録して 1 つの根本修正へ向ける
  行き先がある**
- 4 つの Skill（`out-of-scope` / `problem-solving` / `retrospective` / `issue-upkeep`）の
  どれから読み始めても、**蓄積した課題群の共通原因を扱う Skill へたどり着ける**
- 2026-09-16 の棚卸で見つかった 4 群のうち 2 群以上が、実際に束ねられている

## 対象範囲

含む:

- `plugins/ndf/skills/issue-upkeep/SKILL.md` の判定の表・段 2B の突き合わせの表・
  自動で反映してよい変更の表・用語・完了報告・既存の Skill との境界
- `plugins/ndf/skills/issue-upkeep/references/` に、束ねる判断の必要条件と上位の課題の
  書き方を置く新しい参照
- `plugins/ndf/skills/issue-upkeep/references/milestones.md` の、束ねた上位の課題を
  割り当てる箇所
- `plugins/ndf/skills/out-of-scope/SKILL.md` の「蓄積した課題との境界」
- `plugins/ndf/skills/problem-solving/SKILL.md` の「上流で直す」と関連
- `plugins/ndf/skills/retrospective/SKILL.md` の「蓄積した課題を手入れする」
- `plugins/ndf/skills/issue-upkeep/tests/test_issue_upkeep_layout.py`
- 上の 4 群のうち 2 群以上を実際に束ねた結果（上位の課題の起票と、元の課題への結び付け）

含まない:

| 扱わないもの | 理由 |
| --- | --- |
| 4 群すべてを束ねること | 完了条件は 2 群以上である。残りは次の棚卸が同じ手順で扱う |
| 束ねた上位の課題そのものを直すこと | 束ねるのは判定であって、修正は各マイルストーンの着手で行う |
| 元の課題を閉じること | 下の AC7 で「閉じない」と決める。閉じる判断は上位が直った後の棚卸が既存の判定で行う |
| マイルストーンの新設・並べ替え | `references/milestones.md` の既存の規則で決まる。新しい規則を作らない |
| `out-of-scope` の 3 択を 4 択へ増やすこと | 発見の瞬間には群が見えない（#713 の分析）。入口は 3 択のままにする |
| `retrospective` に群の発見を担わせること | 振り返りは 1 回の変更を見るため、群は見えない |
| `CHANGELOG.md` と版数 | 配布の工程が書く |
| クラス図・データ構造の図 | 変えるのは文書の節と表であり、型を持たない |

## 前提

- **前提 1: 判定の名前は「束ねる」とする。** #712 / #713 の本文がこの語を使っており、
  別の語を当てると課題の本文と食い違う
- **前提 2: 判定は 8 つになる。** 既存の 7 つはいずれも残す。どれも別の意味を持ち、
  統合すると後から検索で区別できない（`no-work.md` が「閉じてよい」と「やらない」で
  同じ理由を挙げている）
- **前提 3: 上位の課題の起票は、承認を得てから行う。** 外部から見える場所への書き込みで
  あり、`out-of-scope` も起票の前に同意を取る

## 検証手段

| 何を確かめるか | コマンド |
| --- | --- |
| 判定の並び・参照・境界の記述 | `uv run --with pytest pytest plugins/ndf/skills/issue-upkeep/tests -q` |
| 他の Skill のテストを壊していないこと | `uv run --with pytest pytest scripts/tests plugins/ndf -q` |
| frontmatter の規約 | `python3 scripts/check-skill-frontmatter.py` |
| プラグイン定義 | `claude plugin validate .` |
| 上位の課題と元の課題の結び付き（AC19〜AC21） | `gh issue view <番号>` の出力を Pull Request の本文へ写す |

AC19〜AC21 は自動テストにできない（GitHub の状態であり、リポジトリの中に無い）。
**手動の確認手順**は、束ねた群ごとに `gh issue view <上位の番号>` と、元の課題それぞれの
`gh issue view <番号> --json body --jq '.body' | grep '#<上位の番号>'` を実行し、出力を
Pull Request の本文へ残すこととする。

## プロジェクト構造

| 置く場所 | 何を |
| --- | --- |
| `plugins/ndf/skills/issue-upkeep/SKILL.md` | 判定の表・段 2B・境界・完了報告 |
| `plugins/ndf/skills/issue-upkeep/references/` | 束ねる判断の必要条件と上位の課題の書き方 |
| `plugins/ndf/skills/issue-upkeep/tests/` | 構成と配線の検査 |
| `issues/` | この仕様・設計・実装計画 |

**置いてはいけない場所。** `docs/` へは置かない（確定仕様化の工程が行う）。Serena memory は
使わない（`CLAUDE.md`）。判定の基準を `SKILL.md` の外へ写さない（`development-workflow` が
「判定基準を持つのはこの Skill だけ」としたのと同じ理由で、判定の並びの正本は
`SKILL.md` の表 1 箇所である）。

## コーディング規約

- 文書は `markdown-writing` に従う。**変更の経緯を本文に残さない**
- パスの直後は半角スペースを置く
- frontmatter は `plugins/ndf/skills/AUTHORING.md` の規約に従い、
  `python3 scripts/check-skill-frontmatter.py` で検査する
- テストは既存の `test_issue_upkeep_layout.py` の書き方（docstring に理由、
  `SKILL.md` の文字列を直接照合）に合わせる

## テスト戦略

| 階層 | 何を担保するか |
| --- | --- |
| 構成の検査（既存の `test_issue_upkeep_layout.py`） | 判定の並びが 3 箇所で揃うこと、参照が存在すること、呼び出し元が指すこと |
| 手動確認 | AC19〜AC21（GitHub 上の状態） |

**新しいテストファイルを作らない。** 既存の 1 本が同じ Skill の構成を検査している。

## 境界

```text
常に行う      … 既存テストの実行、frontmatter の検査、変更した Skill の語の統一
確認してから行う … 上位の課題の起票、元の課題の本文の書き換え、マイルストーンの設定
行わない      … 元の課題を閉じること、4 群すべてを束ねること、out-of-scope の 3 択を増やすこと
```
