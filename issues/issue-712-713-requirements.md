# #712 / #713: 同じ原因から出た課題を、まとめて直せるようにする

設計は [issue-712-713-design.md](issue-712-713-design.md) にある。この文書は「何を満たせば
完了か」だけを扱う。

## この変更で何ができるようになるか

未解決の課題を一覧で見直す作業を、このリポジトリでは棚卸と呼ぶ（`/ndf:issue-upkeep`）。
棚卸は課題を 1 件ずつ実物と照らし合わせ、本文を直したり、すでに直っているものを閉じたりする。

**いまの棚卸には、「この何件かは結局ぜんぶ同じ原因だ」と気づいたときの行き先がない。**
気づいても、記録する場所がないまま個別に直す課題として並び続ける。

この変更で、その行き先を作る。同じ原因から出た課題をひとつのクラスタとして扱い、**その原因を
直すための課題を新しく 1 件つくる。** 新しく作る課題を親 issue と呼ぶ。クラスタに
属する既存の課題（子 issue）は閉じずに残し、親 issue を指す 1 行を本文へ足す。

**親 issue は「どこを直すか」と「どう直すか」を名指しする。** 課題が現れている場所
（現象レイヤー）と、直すべき場所（修正レイヤー）を分けて書き、採る手を 5 つ
（移動 / 統合 / 新設 / 向きの修正 / 分離）から 1 つ選ぶ。呼び出し側を 1 件ずつ直すのか、
上位の層を 1 度直すのかが、これで分かれる。

## 実例: 6 件が同じ原因から出ている

2026-09-16 の棚卸で、次の 6 件が見つかった。

| 課題 | 何が起きているか |
| --- | --- |
| #671 | 工程の進行を記録する処理が、書き込みに失敗しても理由を出さず正常終了する |
| #577 | 配布物の検査が落ちても、その理由が継続的統合の画面に出ない |
| #459 | 配布済みの版に無い工程名を記録すると、その記録が捨てられる |
| #684 | 行範囲を添えた改善提案が、必要な情報が無いものとして捨てられる |
| #642 | 書き方の違う同じ提案が統合されず、2 件目が申告なしとして扱われる |
| #653 | 継続的統合の 3 つの検査が必須になっておらず、落ちてもマージできる |

**6 件はどれも「失敗や欠落に気づいた場所が、それを誰にも伝えないまま先へ進む」という同じ形を
している。** 現れている場所（現象レイヤー）は 6 つとも別だが、**直すべき場所（修正レイヤー）は
同じ 1 つで、「失敗の扱いを決める共通の層」である。** その層はまだ無いため、採る手は新設になる。

1 件ずつ直すと、6 か所で同じ直し方を 6 回考えることになる。しかも、**7 か所目が同じ形で
また生まれる。** 届ける先を作るという判断が、どこにも記録されていないからである。

## いまとどう変わるか

同じ 6 件を棚卸したときの動きを並べる。

| | いま | この変更の後 |
| --- | --- | --- |
| 6 件への判定 | 1 件ずつ「そのまま」「追記が要る」などが付く | 6 件すべてに「クラスタ化」が付く |
| 原因の記録 | どこにも残らない | 修正レイヤー「失敗の扱いを決める共通の層」・採る手「新設」を持つ親 issue を 1 件つくる |
| 元の 6 件 | そのまま並ぶ | 子 issue として残す。本文に「共通の原因は #N にある」を 1 行足す |
| 次の棚卸 | 同じ 6 件を見て、また同じことに気づき直す | 親 issue から 6 件をたどれる |

**子 issue を閉じない理由は 2 つある。** 1 つ目は、各課題が固有の再現手順を持っており、
閉じるとそれが失われること。2 つ目は、原因を直した後も 6 か所それぞれに当てはめる作業が
残ることである。

## なぜ要るのか

**原因を残したまま個別に直すと、直した後に同じ形が別の場所で出る。**

実際にそうなった例がある。v10.13.0 では、レビューの打ち切りの上限（#598 / #537）を直した。
しかし、打ち切りの後に部分的な結果が失われる機構（#548 / #583 / #584 / #619）は 1 件も
直っていない。**上限は引き金であって、原因ではなかった。** 原因の側を指す記録がなかったため、
引き金だけが直った。

もう 1 つの理由は、着手の時期が原因と一致しないことである。#671 と #684 は同じ原因を
持つが、別のマイルストーンに入っており、別の版で直る予定になっている。

## 見つかっている 4 つのクラスタ

2026-09-16 の棚卸では、未解決の 62 件を 1 件ずつ実物と照らし合わせた。同じ原因から出た
クラスタが 4 つ見つかった。**以下ではこの 4 つを「4 クラスタ」と呼ぶ。**

| クラスタ | 修正レイヤー（直すべき場所と採る手） | 子 issue | 件数 |
| --- | --- | --- | ---: |
| 失敗・欠落を黙って捨てる | 失敗の扱いを決める共通の層（新設） | #671 #577 #459 #684 #642 #653 | 6 |
| 配布済みの版と開発中の版が食い違う | 実行する版を解決する層（統合） | #459 #590 #658 #534 | 4 |
| 打ち切りの後に部分的な結果が失われる | 担当の結果を保持する層（新設） | #548 #583 #584 #619 | 4 |
| 待ち方と起動の形が Skill ごとに決まっている | 起動と待ちの規則を持つ層（統合） | #560 #656 #680 | 3 |

**#459 は 1 行目と 2 行目の両方に属する。** 1 件が複数のクラスタへ入る形も扱う必要がある。

## 誰がこの判断を持つのかが書かれていない（#713）

課題に対する判断は 2 種類ある。**やるかどうかを決める判断**と、**どこを直すかを決める判断**で
ある。4 つの Skill の記述を読み合わせると、後者に空白がある。

| 判断 | 課題を見つけたその場で | 溜まった課題を見直すとき |
| --- | --- | --- |
| やるか（価値） | `out-of-scope` の「起票しない」 | `issue-upkeep` の「やらない」 |
| どこを直すか（構造） | `out-of-scope` の「範囲内へ入れる」、`problem-solving` の「上流で直す」 | **どの Skill も自分の役目と書いていない** |

- `out-of-scope` は「同じ原因・同じ形なら範囲へ入れる」という構造の判断を持つが、
  「発見の瞬間に限る」と自分で範囲を切っている
- `problem-solving` は 1 件の不具合の上流をたどる。複数の課題に共通する原因は扱わない
- `issue-upkeep` は価値の判断だけを自分のものと宣言し、構造の判断について何も書いていない
- `retrospective` が拾うのは起票の取りこぼしで、すでに起票された課題どうしの関係は見ない

**空白の升を `issue-upkeep` の「クラスタ化」で埋め、4 つの Skill の境界にそう書く。** これが
#713 で満たすことである。

## 用語

**用語は外来語由来のものを採る。** `グループ` `セット` `かたまり` のような一般語は、
指す対象が読み手ごとに変わるため使わない。地の文は和語で書く。

| 語 | この文書での意味 | 由来 |
| --- | --- | --- |
| 棚卸 | 溜まった課題の一覧を現状へ合わせる工程（`/ndf:issue-upkeep`）。変更が終わった時点で通す | — |
| 判定 | 棚卸が課題ごとに決める区分。いまは 7 つで、この変更で 8 つになる | — |
| クラスタ化 | 足す 8 つ目の判定。クラスタに属する各課題に付く | clustering |
| クラスタ | 同じ 1 つの原因から出た課題の集まり | cluster |
| 現象レイヤー | 子 issue が実際に現れている場所。ファイル・クラス・層のいずれか | layer |
| 修正レイヤー | 原因を直すべき場所。その責務を持つべき場所までさかのぼる | layer |
| 手 | 修正レイヤーへの直し方。移動 / 統合 / 新設 / 向きの修正 / 分離 の 5 つ | — |
| 親 issue | クラスタの共通の原因を直すために新しくつくる課題。修正レイヤーと手を名指しする | parent issue |
| 子 issue | クラスタに属する既存の課題。親 issue をつくった後も閉じない | sub-issue |
| マイルストーン | 着手の時期を表す単位。GitHub の milestone をそのまま指す | milestone |
| 重複 | 既存の判定の 1 つ。**同じ課題**であることを指す。クラスタ化（原因は同じだが別の課題）とは分ける | — |
| 段 2A / 段 2B / 段 3 | 棚卸の手順の段。2A は課題ごとに調べる（複数人で分担する）、2B は全体で突き合わせる（分担しない）、3 は結果を反映する | — |
| 4 クラスタ | 上の表の 4 つのクラスタ | — |

## 触らないもの

| 扱わないもの | 理由 |
| --- | --- |
| 4 クラスタすべてを処理すること | 完了条件は 2 つ以上である。残りは次の棚卸が同じ手順で扱う |
| 親 issue そのものを直すこと | この変更で作るのは判定である。原因の修正は各マイルストーンの着手で行う |
| 子 issue を閉じること | AC10 で閉じないと決める。閉じる判断は、原因が直った後の棚卸が既存の判定で行う |
| マイルストーンの新設・並べ替え | 既存の規則で決まる。足すのは親 issue を入れる先を決める記述だけである |
| 課題を見つけたその場の判断を 3 択から 4 択へ増やすこと | 発見の瞬間には指摘の周辺しか見えておらず、クラスタを判定する材料が無い |
| 振り返りにクラスタの発見を担わせること | 振り返りは 1 回の変更を見るため、クラスタが見えない |
| `issue-upkeep` の用語「まとまり」（1 度にマージする Pull Request の集合） | 着手の時期とは別の概念である。配布の単位を指すこの語は残す |
| `CHANGELOG.md` と版数 | 配布の工程が書く |
| クラス図・データ構造の図 | 変えるのは文書の節と表であり、型を持たない |

## 前提

| # | 前提 | 理由 |
| --- | --- | --- |
| 1 | 判定の名前は「クラスタ化」、作る課題の名前は「親 issue」とする | 技術文書の用語は外来語由来のものを採る。GitHub 自身が親 issue とサブイシューの語彙を持つ |
| 2 | 判定は 8 つになる。既存の 7 つはいずれも残す | どれも別の意味を持ち、統合すると後から検索で区別できない |
| 3 | 親 issue の起票・子 issue の本文の更新・#712 / #713 の本文の書き換えは、承認を得てから行う | いずれも外部から見える場所への書き込みである |
| 4 | 親 issue と子 issue の結び付きは GitHub のサブイシュー関係で持つ。2 つ目以降のクラスタだけ本文の 1 行で指す | 多数のケースは 1 対多で、この機能がそのまま当てはまる。子 1 件が持てる親は 1 件だけなので、少数の例外の側を本文へ寄せる |

実行して、出力を Pull Request の本文へ残す。
