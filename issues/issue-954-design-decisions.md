# #954: supervisor が長い待ちの後に文脈の全体を書き直す — 決定の記録

要求は [issue-954-requirements.md](issue-954-requirements.md) に、設計は [issue-954-design.md](issue-954-design.md) にある。
数値の前提（倍率・式・C / P / k / R の値）は末尾の「計算の約束」にある。

**関門で決めるのは決定 1〜3 である。** 1 は 3 つの候補の順序、2 は候補 1 と 2 の比べ方、3 は利用者の
方針（検査と取り込みに 1 時間）から外れる割り当てである。残りは設計の中で決めた。

## 決定の記録

### 決定 1: 3 つの候補を順に入れる。#954 で入れるのは候補 3 と 2 で、候補 1 は契約だけを置く（関門で最終決定）

候補 3（寿命 1 時間の定義）は定義の 1 行と起動の表で済み、すぐ効く。候補 2（収束ループの前の区切り）は
規約と hook で済み、待つ時点の文脈 C を小さくする。候補 1（drive が待ちを持つ）は最も下がるが、drive
（#870）・CLI の worker（#760・#859）・最小構成の `claude -p` の起動（#827）の 3 つが揃うまで入れられない。
そこで 1 の契約（設計の F5）をこの設計に置き、#870・#827 はそれに合わせて作る。

2 と 3 は重ねて効く。2 が C を小さくし、3 が残った待ちの後の書き直しを読み込みに変える。候補 1 が入ると
supervisor は収束ループで待たなくなり、3 の割り当てを外す（決定 3 の再計算で分かる）。

候補 1 だけを待つ案は採らない。#870 は #560 の後にあり、入るまで設計の持ち場 1 本あたり約 2.2M 換算
（$8.8）の書き直しが続く（決定 2 の表の「今」）。

### 決定 2: 候補 1 と 2 は #955 の式で比べ、どちらも「続ける」より得になる。1 は 2 より待ち 1 回あたり約 180k 得である

**待ち 1 回あたり**（k = 10、m = 1）:

| 比べる組 | C | P | 左辺 (C − P) × 1.75 | 右辺 1.25P + R | 判定 |
| --- | ---: | ---: | ---: | ---: | --- |
| 設計: 続ける ↔ 候補 2（新しい supervisor） | 333k | 43k | 508k | 59k | 新しい文脈が得 |
| 設計: 続ける ↔ 候補 1（最小構成の `claude -p`） | 333k | 7.3k | 570k | 14k | 新しい文脈が得 |
| 候補 2 の区間 ↔ 候補 1 | 118k | 7.3k | 194k | 14k | 候補 1 が得（差 180k） |

区切りの後を 1 時間の定義で起動すると、候補 2 の右辺は 2P + R = 91k になる。判定は変わらない。
候補 2 の区間の C は、収束ループから始めた supervisor が待つ時点の文脈として、検査（構造改善から始まる）の
書き直しの平均 118k を使った。

**持ち場 1 本あたり**の計算は次の約束で行った。

| 項目 | 値 |
| --- | --- |
| 待ちの回数（1 起動あたり） | 設計 3.77・検査 3.33 |
| 待ち 1 回の費用 | C × (1.25 + 0.05k) |
| 候補 2 に足すもの | 区切り 1 回分。区切りの後が 5 分なら 1.25P + R = 59k、1 時間なら 2P + R = 91k |
| 候補 1 に足すもの | conductor が drive を起動して通知を受ける 2 回の読み込み 0.05 × 80k × 2 = 8k |

| 持ち場 | 今 | 候補 2 | 候補 2 ＋ 1 時間 | 候補 1 |
| --- | ---: | ---: | ---: | ---: |
| 設計 | 2,197k（$8.8） | 837k（−62%） | 392k（−82%） | 89k（−96%） |
| 検査 | 688k（$2.8） | —（区切らない） | 398k（−42%。1 時間だけ） | 80k（−88%） |

- 設計の候補 2: 118k × 1.75 × 3.77 + 59k。1 時間を重ねると、待ちの後は読み込み（118k × 0.55 × 3.77 =
  245k）になり、区切りは 91k、区間の伸び（118k − 43k = 75k）の書き込みに 0.75 倍の割増し 56k が足される
- 検査: 検査は構造改善から 1 時間の supervisor で始まり、実装レビューの前で区切らない（決定 4）。値は 1 時間
  だけの効果で、待ちの後の 0.40M を読み込みにし（118k × 0.55 × 3.33 = 216k）、それ以外の書き込み 243k に
  0.75 倍の割増し 182k を足したもの
- 候補 1: 待ち 1 回あたり (7.3k + 5k) × (1.25 + 0.5) = 21.6k
- k の感度: k = 40 では左辺の係数が 3.25 になり、どの組も新しい文脈の側へさらに傾く。k = 0 でも係数は
  1.25 で、設計の組は左辺 363k・407k に対して右辺 59k・14k のまま変わらない

**式に入らない面も同じ向きである。** 文脈が長いほど判断の質が落ちる（#955 の「品質の面」）。候補 1 と 2 は
どちらも、待ちの後の判断を短い文脈で行う。

候補 2 を採らずに 1 時間の寿命だけを入れる案は採らない。設計の持ち場では待ちの後の読み込みが 333k × 0.55 ×
3.77 = 690k 残り、候補 2 ＋ 1 時間の 392k より大きい。

### 決定 3: 1 時間の定義は、収束ループの工程から始める supervisor に割り当てる。取り込みには割り当てない（関門で最終決定）

**利用者の方針は「検査と取り込み」だった。** 基準の実測で損益分岐を計算すると、取り込みは満たさず、
方針に無い設計が最も大きく満たす。1 時間が得になるかは、次の 2 つの大小で決まる（#954 の「候補 3 の調べ」。60 分を超える間隔は 0 回）。

| 向き | 量 |
| --- | --- |
| 得 | 待ちの後の書き直しが読み込みに変わる分。1.25 − 0.05 = 1.2 倍 × 待ちの後の量 |
| 損 | それ以外の書き込みの割増し。2 − 1.25 = 0.75 倍 × それ以外の書き込み |

| 持ち場 | 1.2 × 待ちの後の量 | 0.75 × それ以外の書き込み | 満たすか |
| --- | ---: | ---: | --- |
| 設計 | 19.55M | 7.80M | 満たす |
| 検査 | 5.69M | 2.18M | 満たす |
| 実装 | 2.63M | 3.32M | 満たさない |
| 取り込み | 0.49M | 1.33M | 満たさない |
| 仕上げ | 0.32M | 0.94M | 満たさない |

書き直しは収束ループに集まる（設計の「基準の実測」）。そこで割り当ての単位を持ち場ではなく**区間の最初の
工程**にした。検査は構造改善から始まるので 1 時間、設計は区切りの後（ドキュメントレビューから）だけ 1 時間に
なる。設計の前半（要求・設計・再構成）は worker の待ちしかなく、1 時間にすると書き込みの割増しだけを払う。

持ち場ごとに割り当てる案（利用者の方針どおり検査・取り込み）は採らない。取り込みは 1 起動あたり待ちの後の
書き直しが 0.04M しかなく、割増しで損をする。関門で方針どおりを選ぶなら、起動の表の取り込みの行を
`ndf:supervisor-waits` にするだけで変えられる。

**候補 1 が入ると、この割り当てを外す。** 収束ループの待ちが drive へ移ると、supervisor-waits の区間の待ちの
後の書き直しが無くなり、割増しだけが残る。AC9 の再計算がそれを示したら、起動の表を戻す。

### 決定 4: 区切るのは、今の文脈が最初の呼び出しの文脈の 2.5 倍以上のときである

**区切るのは、寿命 5 分の supervisor（`ndf:supervisor`）だけである。** 区切りの後は 1 時間の supervisor が
続ける（F1）。#955 の式を、続ける側と区切る側の寿命を分けて、次の待ち 1 回と後の k 回の呼び出しで比べた。
区間の伸びの割増しは決定 3 が持つので、ここには入れない。

| 今の supervisor | 続けた費用 | 区切った費用 | 区切りが得になる条件（k = 0） | k = 10 |
| --- | --- | --- | --- | --- |
| 5 分 | 1.25C + 0.05kC | 2P + R + 0.05(k + 1)P | **C > 1.64P + 0.8R** | C > 1.46P + 0.57R |
| 5 分（1 時間が効かないとき。U4） | 同じ | 1.25P + R + 1.25P + 0.05kP | C > 2P + 0.8R | C > 1.71P + 0.57R |
| 1 時間 | 0.05(k + 1)C | 2P + R + 0.05(k + 1)P | C > 41P + 20R | C > 4.6P + 1.8R |

**1 時間の supervisor では区切らない。** 待ちの後が読み込みで済むので、前提を 2 倍で書き直す分を取り返せない。
5 分の supervisor の条件は R を含むが、hook は R を知らない。そこで最も厳しい行（1 時間が効かない・k = 0）を
R を P の比で上から抑えて、比 1 つの規則にした。

| 比 | 損にならない R の範囲（最も厳しい行） | 見込み（P 43k・R 5k）での余裕 |
| --- | --- | --- |
| 2 | R = 0 のときだけ。C = 2P の近くでは R の分だけ損になる | 無い |
| **2.5** | **R ≤ 0.625P**（2P + 0.8R ≤ 2.5P） | R は 27k まで損にならない。見込みの 5 倍 |

比にしたのは、固定費の値を規約へ書かない規約（`context-window.md`）に従うためである。P は hook が
supervisor 自身の記録の最初の呼び出しから読む。R が P の 6 割を超える区切り（前の報告が極端に長い）は
AC7 の測定で区間の P として現れるので、そのとき比を見直す。

絶対値（例: 10 万）で区切る案は採らない。固定費はリポジトリと版で変わる（10.17.6 の P は 66.8k）。

### 決定 5: 候補 1 の drive を起動するのは conductor で、drive が自分で判断の相手を起こす（`--on-pause`）

drive を supervisor が起動すると、supervisor が完了を待つあいだ文脈を抱え、今と同じ書き直しが起きる。
conductor は寿命 1 時間で、3 層の起動では文脈が supervisor より小さい（10.17.x の conductor の P 40〜81k・
k 14〜193）。conductor が drive を背景で起動すれば、待つあいだ誰も長い文脈を持たない。

pause のたびに drive が止まって conductor が supervisor を起こす案は採らない。pause ごとに P = 43k を
書き込み、候補 2 と同じ費用になる。pause の中身が修正か裁定なら、drive が CLI の worker か最小構成の
`claude -p` を直接起こす（`--on-pause`）。`--on-pause` を付けなければ #870 の形（止まって JSON を出す）の
ままなので、Codex / Kiro / agy のホストはそのまま使える。

### 決定 6: supervisor の定義は 2 つに分け、本文は規約を指すだけにする

寿命は定義の frontmatter でしか区間ごとに変えられない（#954 の調べ。`Agent` の引数に無い）。組み込みの
`general-purpose` には frontmatter を足せないので、NDF に定義を置く。同じ本文で 2 つにするのは、寿命のほかに
違いを持たせないためである。

本文に supervisor の規則を写す案は採らない。規則は起動指示が 10 個（この設計で 11 個）を渡しており、
定義にも書くと 2 か所を直すことになる。道具も絞らない。supervisor は Skill と Agent を使う。

### 決定 7: 区切りを守らせる hook は、入力の `agent_type` で supervisor を見分ける

サブエージェントの中の PreToolUse の入力には `agent_id` と `agent_type` が付き、本体の入力には付かない
（#829 の実測、Claude Code 2.1.280）。hook は入力だけで定義の名前を知れるので、ファイルを読まずに外れの
起動を抜けられる。定義の名前の値の形（`ndf:supervisor` か、接頭辞の無い `supervisor` か）は見ていない（U2）。

meta の `agentType` や親の記録の `subagent_type` を hook で読む案は採らない。入力に同じ値があり、親の記録は
長い。集計（F4）は hook の入力を持たないので、その 2 つから引く。

`description` に 1 時間の印を足して見分ける案は採らない。測定（`skill-stats --agents`・`token-usage.py`）は
`description` の先頭語で持ち場を読み、印の形を 2 か所で持つことになる。`spawnDepth` で見分ける案も採らない。
conductor が直接起動した worker（読解だけを出すとき）も深さ 1 になる。

`general-purpose` を止めないのは、区切りの後に conductor が同じ持ち場を起動し直す形が、この変更を入れた
版の conductor にしか無いためである。

### 決定 8: 延命と、設定での一括の寿命と、`bg-wait.sh` の区切りを縮める手は採らない

#954 の調べのとおり、設定 `subagentPromptCacheTtl` と環境変数は worker にも効いて損をし、延命の仕掛けは
#829 の待ち方の規約を戻す。`bg-wait.sh wait` の 1 回を 540 秒から 270 秒へ縮めると、呼び直しがキャッシュの
寿命の中に収まるが、呼び出しが倍になり、これも一定の間隔で起きる待ちである。1 時間の区間では 540 秒でも
切れないので、縮める理由が無い。

### 決定 9: 集計に待ちの後の書き直しと読み込みの量の 2 列と、定義の名前の軸を足す

決定 3 の損益分岐は待ちの後の書き直しの量を要るが、今の集計は回数（`rewrites_after_5m`）と量の合計
（`rewrite_tokens`）しか出さない。この設計では回数の比で按分して推定した。AC9 の再計算を推定に頼らない
ため、`rewrite_tokens_after_5m` を足す。1 時間の区間では待ちの後が読み込みになり書き直しに数えられないので、
得の側を測る `read_tokens_after_5m` も足す。5 分と 1 時間の区間を分けて計算するため、定義の名前を軸に足す。

### 決定 10: クラス図を作らない

型を足さない。変えるのは Markdown の定義 2 つ、hook の判定 1 つ、集計の列 2 つと軸 1 つである。


### 決定 11: supervisor の定義は `plugins/ndf/agents/` に置き、agy へも配られることを受け入れる

`plugins/ndf/dev.agy/agents` は `../agents` への symlink で、agy は同じ定義を受け取る。worker の定義
（`worker.md`）も同じ経路で agy へ届いており、agy では 3 層の起動を使っていない。定義は起動されない限り
何もしない。`experimental.cacheTtl` は Claude Code の項目で、agy では効かない。

Claude Code だけのディレクトリへ分ける案は採らない。worker の定義と置き場所が割れ、agy の配り方
（ディレクトリの symlink）を一覧の形へ変える必要がある。agy の公開エージェントの数は 9 から 11 に増える。

## 計算の約束

- 倍率は Opus 5.5（入力 1・読み込み 0.05・書き込み 5 分 1.25・1 時間 2）。値は入力の換算（input 換算の
  トークン）で、× $4 / MTok で金額になる
- 損得の式は #955 のもの: 新しい文脈で始めるほうが得になるのは **(C − P) × (0.05k + 1.25m) > 1.25P + R**
  のとき。C は続けた場合の文脈、P は新しい文脈の前提、k は呼び出し回数、m は待ちでキャッシュが切れる回数、
  R は起動した側が結果を読み直す量
- C と m は設計の「基準の実測」の値。P は supervisor 43k（10.16.0 以降の P の値）、最小構成の `claude -p`
  7.3k（#827）。R は持ち場の報告と起動指示の読み直しで 5k と置く。k は待ち 1 回の後に続く呼び出しで、
  10 と置く（感度は決定 2 の末尾）
