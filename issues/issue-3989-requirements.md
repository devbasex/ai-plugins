# #3989: 並列の計画: 同時実行の制御を稼働中のレーンの数とテストのスロットの 2 層にし、max_lanes・max_plans・レーンの plans を廃止する

正は課題の本文（#3989）で、この文書はその写しである。本文から作り直す。手で直さない。

2026-11-21 に利用者が最終形を決めた: **同時実行の制御を 2 つの層にし、計画とレーンの上限の値（`max_lanes`・`max_plans`・レーンの `plans`）を廃止する。**

| 層 | 何を絞るか | 仕組み |
| --- | --- | --- |
| セッションの数 | マシン全体で稼働中のレーン（claude のセッション）の数 | `relay.max-named`（6、`NDF_RELAY_MAX_NAMED`）。リレーハブが名前つきラッパーの起動を断る数と同じ値で、耐久ワークフローがこの数で起動を待たせる |
| 重い処理 | テスト・LLM の CLI | テストのスロット（`plugins/ndf/src/ndf/testing/slots.py`、#2711・#3368）。重みを数え、メモリが下限を割れば待たせるか止める。**今のまま変えない** |

## 何が起きたか

2026-11-21、並列の計画 p9 へ relay のアカウント切り替えの直し（#3604 #3864）のレーンを足そうとしたところ、計画のレーンの上限の検査（I20）に断られた。動いているレーンは 3 本（lsplit・lz13-deps・ls3-spec）だけで、`after` 待ちで未着手のレーン 3 本（lz2-ci・lz1-contract・le2e）も数えられ、上限 6 に対して 6 になっていた。足すには上限を 7 へ上げる必要があった（`ndf lanes limits p9 --max-lanes 7`）。同じ日に利用者は、同時実行の制御を上の 2 つの層にし、計画とレーンの上限の値を廃止すると決めた。

## 種類

機能追加（今の SSOT の約束は「終わっていないレーンの数の上限」「レーンごとのプランの本数の上限」「マシン全体のプランの本数の上限」（`parallel-plan.md`・`parallel-plan.schema.json`・`parallel-checks.md`）で、実装はその約束どおりに動いている。稼働中のレーンの数で絞る形は今の約束に無い）

## 今の姿

並列の計画の同時実行に関わる値が 4 つあり、意味が重なっている。どれも、実際にメモリを使う量と結び付いていない。

| 値 | 今の振る舞い |
| --- | --- |
| 計画の `max_lanes`（既定は `relay.max-named`） | 終わっていないレーン（`after` 待ちの未着手を含む）の数を、計画の作成・レーンの追加・上限の変更のときに検査するだけ（I20、`plugins/ndf/src/ndf/progress/lane/rules.py` の `_limit_errors`）。起動では読まれない |
| 計画の `max_plans`（既定は `relay.max-named`） | 各レーンの `plans` がこの値以下かを検査するだけ（I2）。もとは計画の `plans` の合計の検査で、#3145 でレーン 1 本ずつに弱められた |
| レーンの `plans` | マシンの上限で数える重み（`plugins/ndf/src/ndf/progress/lane/machine.py` の `admit`: `total + plans <= cap`）。**申告にすぎず、レーンの conductor へ渡らない**ので、レーンが実際に流すプランや supervisor の数とつながっていない |
| マシンの `relay.max-named` | リレーハブは名前つきラッパーの数で断り、耐久ワークフローはプランの本数の合計で待たせる。同じ値を 2 つの意味で使っている |

`max_lanes` と `max_plans` は 10 系で「計画のレーンがリレーハブに断られないことを起動の前に保証する」ために足された（`docs/specifications/ndf-parallel-organizer.md` の「レーンの数の上限は…依存のあるレーンも数える」）。11 系では起動の待ちがこの保証を兼ね、**未着手のレーンが上限の数を占める弊害だけが残る。**

2026-11-21 の実測（30 GB・8 コア）: claude のセッション 8 本で合計 2.4 GB（1 本 0.3〜0.5 GB）、空き 18 GB。supervisor はサブエージェントで conductor のプロセスの中で動き、プロセスを増やさない。前に並列 6 本が限界だった原因は全体テストの同時実行（残り 7.4 GB）で、こちらはテストのスロットが絞っている。

2026-11-21 の計画 p9 で起きたこと: 動いているレーンは 3 本、`after` 待ちで未着手のレーンが 3 本。`max_lanes` 6 に対して 6 と数えられ、急ぎの直しのレーンを足すには上限を 7 へ上げる必要があった。

数え方の食い違いが 2 つある。

- **リレーハブは、この NDF の動いている名前つきラッパーを役（conductor か否か）に依らずすべて数える**（`plugins/ndf/src/ndf/domains/relay/hub.py` の `_own_count`）。耐久ワークフローの起動の許可（`machine.count`）は計画のレーンと conductor の役のラッパーだけを、しかも `plans` の重みで数える。オーガナイザーのセッションのように計画に無く conductor でもないラッパーが動いていると、待ちを通った起動をハブが断ることがある
- **上限の値を読む時点がプロセスごとに違う。** 値は `NDF_RELAY_MAX_NAMED` → 上限の設定 `relay.max-named`（プラグインの `contracts/limits.json`）の順で決まるが、`limits.json` は 1 プロセスに 1 回だけ読まれ（`limits.table` の `cached_reader`）、環境変数は起動した環境から引き継がれる。ハブの判定は要求を処理したプロセスの値で、耐久ワークフローは `ndf lanes start` を打った環境の値を使い続ける。値を書き込むサブコマンドは無い（`docs/specifications/ndf-next-closed-children-subcommands.md` の `from-issue:3569-relay-cap`）。動いている耐久ワークフローの上限を変える手段は無く、`ndf lanes limits --max-lanes` がその代わりだった

手順書の説明は `plugins/ndf/skills/issue-plan-strategy/references/parallel-plan.md`（`max_lanes`・`max_plans`・`plans` と I20・I2）・`plugins/ndf/skills/development-workflow/references/parallel.md`（`ndf lanes set --plans`・`ndf lanes limits`）・`plugins/ndf/skills/development-workflow/references/parallel-checks.md`（マシンの上限）にある。

## 何を足すか・変えるか

| | 今 | 足した後 |
| --- | --- | --- |
| 同時実行の上限 | 計画の `max_lanes`・`max_plans`、レーンの `plans`、マシンの `relay.max-named` の 4 つ | マシン全体の稼働中のレーンの数を `relay.max-named` で絞る 1 つ（セッションの数の層）。テストのスロット（重い処理の層）は変えない |
| マシンの数え方 | 動いているレーンの `plans` の合計（重み）と、conductor の役のラッパー | 稼働中のレーンとほかの動いている名前つきラッパーを 1 本ずつ。リレーハブが数えるラッパーを含む |
| 計画の設定・状態 | `max_lanes`・`max_plans`・レーンの `plans`、検査 I20・I2、`ndf lanes limits`、`ndf lanes set --plans` がある | 無い |
| 上限に当たったレーン | 計画を作れない・レーンを足せない（I20）か、起動の待ち（マシン） | 起動の待ちだけ。空いた周で計画のレーンの並び順に起動する |
| 上限の値を変える | 環境変数を渡して `ndf lanes start` を打ち直す・`ndf lanes limits` | マシンの設定を書くサブコマンドで変え、動いている耐久ワークフローとハブが次の判定から使う |
| `ndf lanes status` | マシンの上限の待ちだけを、ラッパーの一覧を読めたときに出す | 待ちのレーンと理由（マシンの上限・排他・ラッパーの一覧を読めない）、マシンの稼働中のレーンの数と上限を出す |

## 事象

並列の計画の同時実行に関わる値が 4 つあり、意味が重なっている。どれも、実際にメモリを使う量と結び付いていない（上の「今の姿」の表）。`after` で直列にした未着手のレーンが計画の上限の数を占める。

## 期待する結果

1. 計画の設定から `max_lanes`・`max_plans` を、レーンの設定から `plans` を外す。検査の規則 I20（終わっていないレーンの数）と I2（レーンのプランの本数）・`ndf lanes limits`・`ndf lanes set --plans`・計画の状態の該当の項目を消す。後方互換は要らない（普及フェーズの前）。既にある計画のファイル（`.ndf/parallel/p9/plan.json`・`p12/plan.json`）とステートマシンの記録にこれらの値があっても、`ndf lanes start` で再開できる（ファイルから消すか、読むときに捨てるかを設計で決める）
2. 耐久ワークフローは、マシン全体で稼働中のレーン（実行中の行を持つレーン。計画をまたいで数える）の数が `relay.max-named` 未満のときだけレーンを起動する。2 つの計画が同じ周に起動しても上限を超えない（排他 `parallel/admit.lock` の下で数える）
3. 上限に当たって起動できないレーンは起動の待ちに置き、稼働中のレーンが終わると、次の周で決まった順に起動する
4. 耐久ワークフローが待たせる数と、リレーハブが断る数が一致し、計画のレーンの起動がハブに断られない
5. `ndf lanes status` が、起動の待ちのレーンとその理由（マシンの上限・排他・ラッパーの一覧を読めない）、今のマシン全体の稼働中のレーンの数と上限を出す
6. 上限（`NDF_RELAY_MAX_NAMED` かマシンの設定）を変えると、次の周から新しい値で起動を決める。下げても稼働中のレーンは止めない
7. テストのスロットの振る舞いは変えない
8. 手順書（`issue-plan-strategy` の `parallel-plan.md`、`development-workflow` の `parallel.md`・`parallel-checks.md`）と確定仕様 `docs/specifications/ndf-parallel-machine-plan-limit.md` の説明を、2 つの層の形にそろえる
9. 上の 1〜6 を回数で確かめるテスト（時間で区切らない）がある。計画 2 本が同時に起動を求める場合を含む

## 再現手順

1. `max_lanes` が 2 の計画に、`after` で直列にしたレーンを 3 本書く
2. `ndf lanes init` が I20 で断る（同時に動くのは 1 本なのに 3 と数える）

## 環境

NDF 11.0.13・Linux

## なぜ困るか

`after` で直列にした未着手のレーンが上限の数を占め、急ぎのレーンを足すたびに上限を上げることになる。上限の値が 4 つあり、どれで止まった・待ったのかを見分ける手間がかかる。申告の `plans` は実際の負荷と合わないため、マシンの上限の数えが実際のメモリの使い方を表さない。

## 目的

- 同時実行の制御を、セッションの数（マシン全体の稼働中のレーンの数）とテストのスロットの 2 つの層にし、計画にレーンを足すのに上限を上げなくてよい状態にする
- 耐久ワークフローが待たせる数とリレーハブが断る数を同じ数え方にし、計画のレーンの起動がハブに断られない状態にする
- 待っているレーンと理由を、オーガナイザーが `ndf lanes status` で読める状態にする

## 前提

- 前提 1: 「稼働中のレーン」は、実行中の行（承認ゲート・質問の回答を待つ行と、区切りで止めた計画で流し続けている行を含む）を持つレーンか、ラッパーが動いているレーンである。ラッパーが動いている間は claude のセッションがメモリを使い、リレーハブも名前つきラッパーとして数えるため。ラッパーを数えるのは、起動の直後でまだ行が実行中でないレーンを数えるためでもある。実行中の行を持つのにラッパーが止まったレーンも数えるのは、そのレーンの `/goal` の入れ直しや回答の後の再起動の席を残すためである。起動しようとしているレーン自身のラッパーは数えない（起動の前に止める）
- 前提 2: マシンの数え方は、計画のレーンでない動いている名前つきラッパー（オーガナイザーのセッションなど）も 1 本ずつ数える。そのため、耐久ワークフローが数える数はリレーハブが数える数以上で、ハブより先に待つ。実行中の行を持つレーンのラッパーがどれも動いていれば、2 つの数は等しい
- 前提 3: ラッパーの一覧を読めないときは、自分の計画の稼働中のレーンだけで決める（今のマシンの上限の扱いと同じ）。このときはハブの数え方と合わせられないので、受け入れ条件 7 は一覧を読めたときの条件である
- 前提 4: 上限を次の周から変えられるよう、マシンの設定（状態の保存先に置くファイル。10 系の `relay.py cap --named <n>` と同じ役）と、それを書くサブコマンドを足す。リレーハブと耐久ワークフローの判定は、判定のたびにマシンの設定 → `NDF_RELAY_MAX_NAMED` → `relay.max-named` の順で読む（10 系と同じ順。マシンの設定を先にするのは、動いているプロセスが引き継いだ環境変数より新しい値を効かせるため）。名前と保存先は設計で決める
- 前提 5: 計画の設定（`plan.json`）は利用者の手元のファイルで、リポジトリには入らない（`.ndf/.gitignore` の `parallel/`）。このリポジトリの手元で動いている計画のファイルは `.ndf/parallel/p9/plan.json`・`.ndf/parallel/p12/plan.json` である
- 前提 6: NDF は普及のフェーズの前で、設定・コマンドの引数・結果の形を変えても互換の経路を持たない（MVV Value 4）
