## 何が起きたか

並列の計画（`ndf lanes`。複数の開発の流れ＝レーンを同時に進める仕組み）を流している最中に、開発コンテナが再起動された。このとき、計画の記録は「実行中」のまま残ったが、各レーンの AI の会話（conductor）と、それを監視するプロセス（ラッパー）、レーンの起動と監視を自動で行う処理（耐久ワークフロー）はすべて消えた。

計画の質問と承認の窓口となる会話（オーガナイザー）は再開しようとしたが、手順書に再開の手順が無く、計画を始めるコマンドは「実行中で、始められない」と断った。そこで内部の関数を直に呼んで conductor を手で起動し直したが、NDF はその conductor を認識せず、「レーンが止まった」「起動に失敗した」という通知が出続けた。

## 種類

機能追加（消えた conductor を起動し直す振る舞いは、これまで手順書にもコマンドの説明にも約束が無かったので、この変更で新しく約束に足す。手順書が「`start` は動いている計画をそのまま読む」と書いていたのに実際は断っていた、という食い違いの解消も含む）

## 今の姿

これまで並列の計画は、`ndf lanes start <計画のファイル>` で始めると、耐久ワークフロー（`ndf lanes run`）がレーンごとに conductor を起動し、計画が終わるまで監視していた。手順は [並列開発のオーガナイザーの手順書](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/parallel.md) にある。

コンテナの再起動などで conductor が消えた場合、これまでは次のように動いていた。

| 場面 | これまでの動き |
| --- | --- |
| 実行中の計画に `ndf lanes start` を打つ | 「実行中で、始められない」と断った。手順書の「セッションの切り替え」は「`start` は動いている計画をそのまま読む」と書いており、実際の動きと食い違っていた |
| 耐久ワークフローを `ndf lanes run <計画名>` で起動し直す | 耐久ワークフローは動き直すが、実行中の作業（スプリントか開発ループ）を持つレーンの conductor は起動し直さなかった。レーンごとに「止まった」と通知するだけだった |
| 回答が載り、conductor が続きを打つ前に消えた | その回答の起動を打った記録が残るため、起動し直さなかった。「レーンが止まった」のリクエストも開かず、`ndf lanes wait` が猶予の後に知らせるだけだった |
| conductor を手で起動する | NDF の記録にレーンの起動として残らず、後の自動の起動が「登録簿に無い」と断られた |

## 何を足すか・変えるか

| | これまで | この変更の後 |
| --- | --- | --- |
| 実行中の計画への `start` | 断った | 受け付け、消えたレーンの conductor を起動し直す |
| 耐久ワークフローの起動し直し | レーンは消えたままだった | 消えたレーンの conductor を自動で起動し直す |
| 起動の記録が無い・空のレーン | 起動の失敗を繰り返した | レーン数の上限の判定を通して起動する |
| 起動した直後の別のレーンの起動 | 「バージョンの違うラッパーが動いている」と断られることがあった | 同じバージョンなら断らない |
| 手順書 | 再開の手順が無かった | 再開の手順を書く |

## 今の利用者への影響と互換

- これまで使えていた呼び方は変わらない。これまで断っていた「実行中の計画への `start`」を、この変更により受け付ける
- `ndf relay stop` で 1 本だけ止めたレーンは、この変更の後も、耐久ワークフローが動き続けている間は今と同じく勝手に起動し直さない。ただし、作業が実行中のまま `start` を打つか耐久ワークフローを起動し直すと、そのレーンも起動し直される

## 期待する結果

この変更の後は、コンテナの再起動やラッパーの中断があっても、NDF のコマンドを 1 つ打てば、実行中のレーンが止まった所から続く。内部の関数を呼ぶ操作も、conductor を手で起動する操作も要らない。

## 再現手順

1. 3 本以上のレーンを実行中にする
2. 開発コンテナを再起動する（ラッパーと `ndf lanes run` のプロセスがすべて終わる）
3. 新しい会話で `ndf lanes start <計画のファイル>` を打つ → 断られる
4. `ndf lanes run <計画名>` を切り離して打つ → conductor は起動し直されず、`ndf lanes status <計画名>` の生死の判定は `ended` のままになる

## なぜ困るか

これまでは、コンテナの再起動やラッパーの中断が起きると、並列の計画のレーンが止まったままになった。元に戻す公式の手順が無いため、オーガナイザーは内部の仕組みを読んで手で起動することになった。手で起動すると NDF の状態の表示が実態とずれ、「止まった」「起動に失敗した」の通知が開き続けて、本当に対応が要る通知が埋もれた。

## 目的

この変更により、コンテナの再起動などで conductor が消えた並列の計画を、公式の手順 1 つで止まった所から続けられるようにする。再開の後は、状態の表示と通知が実態に合うようにする。

## 対象範囲

含む:

- 実行中の計画に打つ `ndf lanes start` と、`ndf lanes run` の起動し直しで、消えたレーンの conductor を起動し直すこと（区切りで止めた計画・すぐに中止した計画で実行中の作業が残る場合を含む）
- 起動の記録が無い・空のレーンの起動と、起動した直後の別のレーンの起動が断られないようにすること
- 手順書への再開の手順の記載

含まない:

- 手で起動した conductor を NDF に認識させる手段（席の登録のコマンドや、手で起動する手順）。再開の経路が起動するので、手で起動する必要が無くなる
- 計画の記録（状態の保存先・データベース）そのものが失われた場合の復元
- レーンで開いたままの質問に回答が届かないこと（[回答がレーンの質問の画面に届かない不具合 #4522](https://github.com/devbasex/ai-plugins/issues/4522)）と、起動し直した conductor が同じ質問をもう一度出した場合の古い質問の扱い
- ラッパーが生きたまま次の作業へ移ったレーンで起動が失敗すること（[起動の記録が前の作業のまま残る不具合 #4680](https://github.com/devbasex/ai-plugins/issues/4680)）
- 回答の後に起動する conductor の入力に `/goal` が無いこと（[目標の無いまま動く不具合 #4261](https://github.com/devbasex/ai-plugins/issues/4261)）
- 生死の判定の種類と、止まりの判定の基準の変更

## 前提

- 前提 1: 計画の記録（状態の保存先、または共有のデータベース）は、コンテナの再起動をまたいで残る
- 前提 2: 再開を指示するコマンドは新しく作らず、既存の `ndf lanes start <計画のファイル>` を使う
- 前提 3: 「消えたレーン」は、実行中の作業（スプリントか開発ループ）を持ち、ラッパーが動いていないと確かめられたレーンを指す。ラッパーの一覧を読めない場合は、消えたとみなさない

## 受け入れ条件

- [ ] 1. 計画が実行中で、耐久ワークフローもラッパーも動いておらず、3 本のレーンが実行中の作業を持つ状態（生死の判定が `ended`）で `ndf lanes start <計画のファイル>` を打つと、終了コード 0 になり、耐久ワークフローが動き、3 本すべての conductor が、通常の起動と同じ名前のラッパーで起動し直される。計画・レーン・作業の記録は作り直されない
- [ ] 2. 条件 1 で起動し直した conductor の最初の入力は `/goal` の行で始まり、新しいスプリントや開発ループを作らずに止まった所から続ける（スプリントは `ndf progress next <ID>`、開発ループは `ndf loop get <レーン>`）
- [ ] 3. 起動し直した後の `ndf lanes status` はそのレーンを `alive`（動いている）と判定し、開いていた「レーンが止まった」のリクエストは閉じる
- [ ] 4. `start` を打たず `ndf lanes run <計画名>` だけを起動し直しても、条件 1〜3 と同じく起動し直される。コンテナの再起動が 2 回起きても、2 回目も同じように起動し直される
- [ ] 5. 耐久ワークフローが動いたまま 1 本のレーンのラッパーだけが消えた状態で `start` を打つと、そのレーンだけが起動し直され、同じ計画の耐久ワークフローは 2 本にならない
- [ ] 6. 耐久ワークフローが動いたままで `start` を打たなければ、ラッパーが消えたレーンは今と同じく「止まった」と通知するだけで、起動し直さない
      前提の確認: 11.0.52 の `run_decide.decide` に実行中で `ended` のレーンを渡すと、起動ではなく通知の手が返る。`tests/progress/test_plan_run.py` の `test_a_stalled_lane_is_reported_once_per_notice_key` が通る
- [ ] 7. conductor が動いているレーンは、`start` を打っても起動し直されない。`start` を続けて 2 回打っても、1 レーンのラッパーは 1 本のままである
- [ ] 8. 回答が載り、conductor が続きを打つ前のレーンは、その回答の起動を打った後に消えていても起動し直され、回答を受け取る入力（`ndf lanes row resumed` から続ける）で再開する
- [ ] 9. 承認や質問の回答を待つレーンが消えた場合、そのレーンの質問かリリース承認のリクエストが計画に開いていれば起動し直さない（回答が載れば条件 8 で起動する）。開いていなければ起動し直し、オーガナイザーに質問が届く
- [ ] 10. 作業を実行中にする前に消えたレーンは、今と同じく起動の期限が過ぎた後に、最初の入力で起動し直される
      前提の確認: `tests/progress/test_plan_run.py` の `test_a_launched_lane_that_does_not_start_its_row_in_time_counts_as_a_failure` が 11.0.52 で通る
- [ ] 11. ラッパーの一覧かスプリントの状態を読めないレーン（`unknown`）と、ラッパーは無いがスプリントの工程の処理がまだ動いているレーン（`working`）は、起動し直されない
- [ ] 12. 区切りで止めた計画で実行中の作業が残る状態で耐久ワークフローを起動し直すと、実行中の作業は起動し直されるが、次の作業は始まらない。すぐに中止した計画で実行中の作業が残る場合は、中止させる入力で起動し直される。完了した計画と中止した計画への `start` は、今と同じく断る
      前提の確認: `tests/progress/test_plan.py` と `test_plan_run.py` の区切り停止・中止のテスト（`-k "paused or stopped_plan"`）が 11.0.52 で通る（PostgreSQL を使う 2 件は skip）。完了した計画を断ることはコードを読んで確かめた（`plan.start_plan`）
- [ ] 13. レーンの起動の記録が登録簿に無い、または空（手で起動した場合など）でも、再開の起動と回答の後の起動は失敗にならず、レーン数の上限の判定を受けて起動する。上限に当たれば起動の待ちになり、「起動に失敗した」のリクエストは開かない
- [ ] 14. 同じバージョンのラッパーを起動した直後（そのラッパーがバージョンを記録する前）に別のレーンを起動しても、「バージョンの違うラッパーが動いている」で断られない。メジャーバージョンが違うラッパーと旧い NDF 10.x のラッパーは、今と同じく断る
- [ ] 15. [並列開発のオーガナイザーの手順書](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/parallel.md) に、再開の手順（打つコマンド、起動し直されるレーンとされないレーン、手で起動しないこと）が書かれ、`start` についての記述が実際の動きと一致する

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 移行性 | この変更の前のバージョンで始めて、実行中のまま残った計画も、変更後のバージョンの `start` で条件 1 のとおりに再開できる |
| 運用・保守性 | 起動し直したレーンの名前、続ける作業、起動し直した理由を、耐久ワークフローの記録（`run.log`）に 1 レーンにつき 1 行残す |

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる（`ndf lanes start` が実行中の計画を受け付ける。これまで使えていた呼び方と結果の形は変わらない） |
| 重さ | これまでは、コンテナの再起動などの後、並列の計画の全レーンが止まった。回避の手段は内部の関数を呼んで手で起動することだけで、状態の表示と通知がずれた |

> ## 起きたこと
>
> 並列の計画（`ndf lanes`）の実行中に、開発コンテナが再起動された。計画のステートマシンは `running` のまま残り、レーンの conductor のラッパーと、計画を進める耐久ワークフロー（`ndf lanes run`）は消えた。オーガナイザーが再開しようとしたが、手順が無く、手で起動し直した conductor を NDF が認識しなかった。
>
> ## 再現の手順と結果
>
> 1. 3 本以上のレーンを実行中にして、コンテナを再起動する（ラッパーの子と `ndf lanes run` が終わる）
> 2. 新しい会話で `ndf lanes start <計画のファイル>` を打つ
>    - 結果: `計画 <名前> は実行中で、始められない`（終了コード 1）。区切りで止めた計画（`ndf lanes stop`）の再開には `start` を使うが、実行中のまま消えた計画の再開手順は `parallel.md` に無い
> 3. `ndf lanes run <計画名>` を切り離して打つ
>    - 結果: 耐久ワークフローは動き直す。しかし、実行中の行を持つレーンの conductor は、起動し直されない（「次の行を始められるレーン」「回答が載った行」「認証の失敗で `/goal` が外れたレーン」の 3 つの場面のどれにも当たらない）
>    - 結果: 止まりを知らせる `lane_stalled`（生死の判定 `ended`）が、レーンごとに開く
> 4. conductor を手で起動し直す。`ndf progress next <スプリントの ID>` を入力に持つ `/goal` の 1 行を、`launch.goal_prompt` で組み、`launch.spawn` で `ndf relay spawn` する
>    - 結果: conductor は動く。しかし `ndf lanes status` は `ended` のままで、`lane_stalled` のリクエストは閉じない
>
> ## 原因（コードを読んだ範囲）
>
> - ラッパーの名前は `wrapper_name(repo, plan, lane)` が、リポジトリ・計画・レーンの要約で決める（`src/ndf/progress/lane/launch.py`）。`ndf lanes status` と耐久ワークフローが渡す `repo` は `command.repo_id(cwd, root)`（リモートの URL。リモートが無ければメインディレクトリのパス）である
> - 手で組んだ起動で `repo` にパスを渡すと、要約が変わり、期待する名前のラッパーが無いと判定される（`liveness.py` の `ended`）
> - 手で起動した conductor は、席（`lane:<計画の ID>/<レーン>:<行>`）が登録簿に無い。そのため、耐久ワークフローの再起動が `席 ... は登録簿に無い（登録簿の席: None）。--seated を外して上限の判定を受ける` で断られ、`launch_failed` のリクエストが繰り返し開く
> - 手で起動した直後は、別のレーンの `spawn` が `バージョンの違うラッパーが動いている: <直前に起動した名前>（旧い NDF）` で断られる（数十秒、再試行すると通る）
>
> ## 困ること
>
> - コンテナの再起動や、ラッパーの中断の後に、計画を元の状態へ戻す公式の手順が無い。オーガナイザーは内部の関数を直に呼ぶしかなく、名前の食い違いで状態の表示が実態とずれる
> - ずれた状態では、`lane_stalled` と `launch_failed` が開き続け、オーガナイザーの知らせが増える
>
> ## 求めること（案）
>
> 1. 実行中のまま消えた計画を再開する手順を、`parallel.md` に書く。たとえば `ndf lanes resume <計画名>`（実行中の行を持つレーンで、ラッパーが動いていない行を、`ndf progress next` から続ける入力で起動し直す。耐久ワークフローが起動する経路と同じ席・名前・上限の判定を使う）
> 2. `ndf lanes run` を起動し直したとき、実行中の行でラッパーが動いていないレーンを、自動で続ける起動（認証の失敗の再起動と同じ `goal_prompt`）で起動する
> 3. 手で起動した conductor の席を、登録簿へ載せる手段を持つ（または、再開の手順が席を登録する）
>
