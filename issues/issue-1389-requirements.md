# #1389: ラッパーで複数の claude アカウントを持ち、利用上限の前後で自動で切り替えて作業を続ける

正は課題の本文（#1389）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 依頼（原文）

> relay.pyに複数アカウント管理機能を入れる
>
> * claudeのsubscriptionはセッションリミットと週間リミットを持つ(多分。要調査)
> * /goal /ndf:development-workflow など、長期のミッションを流していると途中でいずれかに達してしまうことがある
> * これに備えてあらかじめ利用者が持っている複数のclaudeアカウントの認証情報を持っておく
> * relay.pyは子プロセスのリミットを検知し、最も制限から遠いアカウントを選択し、認証して作業を再開できるようにする
>   * 定期的に情報を取得して、リミットの前のちょうどよいタイミングで切り替えられるとなお良い。(ただしここにコストが掛らないようにする)
> * この再認証自体もclaudeを使って良いが、Claude APIやBedrockなど、リミットの無い接続方法で接続して利用する。

（解釈: 「relay.py」はラッパー（`plugins/ndf/scripts/relay.py`・`relay_lib/`）を指す。「子プロセス」はラッパーが起動する claude（conductor）と、その子孫の claude -p（`supervise.py` のプランと worker）を指す。「リミット」は利用上限の 3 種類（`five_hour`・`seven_day`・支出上限）を指す。「コストが掛らない」は、残量の確認が推論を呼ばず、どのアカウントの使用量も増やさないことを指す。「再認証自体もclaudeを使って良い」は、切り替えの判断や操作に LLM を使うこと自体は許すが、その呼び出しは subscription のアカウントを使わないことを指す）

承認ゲート 1 での利用者の指示（2026-09-28、原文）:

> 全てのclaudeアカウントがlimitになった時はbedrockやclaude apiなど、利用制限のない接続方法に切り替える。この場合もアカウントを監視し、利用制限が解除されたら解除されたアカウントに切り替える、というセーフティネットを入れてください。

（解釈: 「利用制限のない接続方法」は Bedrock（`CLAUDE_CODE_USE_BEDROCK=1` など）か Anthropic API の API キー（`ANTHROPIC_API_KEY`）による従量の接続を指す。接続の中身は利用者が宣言し、リポジトリには持たない。「解除されたアカウントに切り替える」は、従量の接続には費用が掛かるため、登録済みアカウントが使えるようになった時点で戻すことを指す）

## 例: 2026-09-28 のセッション 24 で起きたこと

1. conductor（ラッパーの子の claude）が #1370 の検査と #1337 の設計を背景で流していた
2. 23:39 UTC、#1337 のレビューの claude が 429 `You've hit your individual spend limit` で止まった
3. 23:59 UTC、#1370 の実装担当の claude が 429 `You've hit your session limit · resets 2:10am (UTC)` で止まった
4. #1337 の修正担当は `supervise.py` の上限待ちに入り、リセット時刻（02:10 UTC）まで約 2 時間眠った
5. 利用者が手で `/login` して別のアカウントへ替え、conductor が止まったプランを探して流し直した（約 30 分）

この課題が済むと、2〜5 はラッパーと `supervise.py` が行う。上限に達したことを検知し、登録済みのアカウントから
最も上限から遠いものを選び、そのアカウントで作業を再開する。**利用者の操作と conductor の探し直しは要らない。**

## 目的

- 長いミッション（`/goal /ndf:development-workflow …`）が、利用者のアカウントの利用上限で止まらずに進む
- 上限に達する前に、費用を掛けずに残量を見て、切り替えの時点を選べる

## 今の状態（2026-09-28 に調べた）

- **上限は 3 種類ある。** 会話の記録の `quotaLimits.rateLimitType` に `five_hour`（session limit）と `seven_day`（weekly limit）が出る
  （`plugins/ndf/scripts/tests/fixtures/transcript_agents/` の実物の写し。読むのは `plugins/ndf/scripts/lib/transcript_agents.py`）。もう 1 つは追加利用の支出上限（`individual spend limit`、上の例の 2）
- **残量はトークンを使わずに読める。** `GET https://api.anthropic.com/api/oauth/usage`（`Authorization: Bearer <OAuth のアクセストークン>`・
  `anthropic-beta: oauth-2025-04-20`）が `five_hour` / `seven_day` の `utilization`（%）と `resets_at`、`extra_usage.spend_limit_reached` を返す
  （2026-09-28 00:35 UTC に 1 回呼んで 200。推論は呼ばない）。公開の文書は無く、形が変わりうる
- 認証情報は `${CLAUDE_CONFIG_DIR:-~/.claude}/.credentials.json` の `claudeAiOauth`（アクセストークン・リフレッシュトークン・期限・`subscriptionType`・
  `rateLimitTier`）に 1 つだけある。devbase では `~/.claude` が同じアカウントグループのコンテナで共有される（ファイルを書き換えると全コンテナに効く）
- ラッパー（`plugins/ndf/scripts/relay.py`・`relay_lib/`）は子の claude の会話の記録とシグナルファイルを見て、カットポイントで `/exit` と次の区間の起動を行う。
  子の環境は `relay_lib/claude.py` の `child_env()` が起動したときの環境から作る。**上限の検知とアカウントの切り替えは無い**
- `supervise.py` は claude -p の上限を検知して、リセット時刻まで待つ（`supervise_lib/claude.py` の `ClaudeRunner.call`、待ちの最大 `LIMIT_WAIT_MAX` 3 時間）。
  待つ前に 1 度だけ、`NDF_SUPERVISE_CLAUDE_FALLBACK`（`KEY=VALUE` の並び）の環境変数を足して起動し直す仕組みがある。**登録済みのアカウントから選んで替える仕組みは無い**
- 背景で動くプラン・worker・cross 系の CLI は、起動した時点の環境（認証）を引き継ぐ。conductor のアカウントを替えても、動いているものは古いアカウントのまま

## 前提

- 前提 1: 登録するアカウントは、利用者がこの作業に使ってよいものに限る（各アカウントの利用条件の判断は利用者が持つ）。登録は利用者が登録のコマンドを打ったときだけ行い、ラッパー・プラン・worker は登録を増やさない
- 前提 2: 切り替えの判断・再認証に LLM を使う場合は、上限の無い接続（Anthropic API の API キーか Bedrock）で呼ぶ。subscription のアカウントでは呼ばない。LLM を使わずに決められる判断（残量の比較）は LLM を使わない
- 前提 3: 残量の取得は推論を呼ばない。取得先は上の `api/oauth/usage` とし、取得先が使えないとき（通信の失敗・200 以外・形の変化）は、会話の記録の `quotaLimits` と 429 だけで判定する（上限に達した後の切り替えは働き、手前の切り替えだけが働かない）
- 前提 4: 「最も上限から遠い」は、上限に達していない（支出上限にも達していない）アカウントのうち、`five_hour` と `seven_day` の使用率の大きい方が最も小さいものとする。並んだら `five_hour` のリセット時刻が早い方を選ぶ。残量が読めないアカウントは、読めるアカウントが 1 つも無いときだけ候補にする
- 前提 5: 切り替えは、次に起動するプロセスから効く。動いている claude（conductor の背景のタスク・動いている worker・cross 系の CLI）の認証を途中で替えない。上限に当たったものは、ラッパーは次の区間の起動で、`supervise.py` は同じ呼び出しのやり直しで替える
- 前提 6: 上限の手前での切り替えは、カットポイント（ラッパーが `/exit` してよい点）でだけ行う。作業の途中で子を終えない
- 前提 7: 既存の `NDF_SUPERVISE_CLAUDE_FALLBACK` は、登録済みのアカウントが無いときの振る舞いとして残す（受け入れ条件 9 の「今と同じ」に含む）。登録済みのアカウントとの併用の順序は設計が決める
- 前提 8: 登録済みのアカウントがすべて上限に達したときは、利用者が宣言した従量の接続（Bedrock か API キー）へ切り替えて続ける（セーフティネット）。宣言はラッパーと `supervise.py` が同じものを読む。宣言が無ければ今と同じ（ラッパーは子を残し、`supervise.py` は上限待ち）。従量の接続で動いている間も登録済みアカウントの残量を費用なしに読み続け、どれかが上限を外れたら次の区間・次の worker の起動からそのアカウントへ戻す

## 対象範囲

含む:
- 利用者が複数の claude のアカウントの認証情報を登録・一覧・削除する手段（登録は利用者の明示の操作だけ）
- ラッパーが、子の claude が上限に達したことを検知すること（3 種類とも）
- 登録済みのアカウントの残量を費用なしに読み、最も上限から遠いアカウントを選ぶこと
- 選んだアカウントで次の区間を起動し、作業を続けること（ndf-next が無いときも `/goal` の条件か直前の会話から再開する）
- 定期的に残量を読み、上限の手前で切り替えること（間隔と閾値は設定で変えられる）
- `supervise.py` のプランと worker が上限に当たったとき、待つ前に別のアカウントへ替えて続けること
- 登録したアカウントのトークンの期限切れを扱うこと（更新するか、再登録が要ると示す）
- 登録済みのアカウントがすべて上限のとき、宣言された従量の接続へ移り、アカウントの上限が外れたら戻すこと（前提 8）

含まない:
- アカウントの作成・購入・プランの変更
- Anthropic API の従量課金・Bedrock 自体の上限（上限の無い経路として扱う）
- 従量の接続の中身（API キー・AWS のプロファイルとリージョン・モデルの名前）をリポジトリに持つこと。利用者が宣言する
- codex・kiro・agy の認証の切り替え（claude だけ）
- ラッパーを通さずに起動した claude（利用者が直接起動した対話）の切り替え
- 動いているプロセスの認証の途中での差し替え（前提 5）

## 用語

| 用語 | 意味 |
| --- | --- |
| 登録済みアカウント | 利用者が登録のコマンドで認証情報を預けた claude のアカウント。切り替えの候補になる |
| アカウントの切り替え | 次に起動する claude（ラッパーの次の区間・worker のやり直し）を、別の登録済みアカウントの認証で起動すること |
| 使用率 | `api/oauth/usage` が返す `five_hour` / `seven_day` の `utilization`（%） |
| 支出上限 | 追加利用の支出の上限（`individual spend limit`）。`extra_usage.spend_limit_reached` で読む |
| 従量の接続 | 利用上限の無い、使った分だけ費用が掛かる接続。Bedrock か Anthropic API の API キー。中身は利用者が宣言する |

## 受け入れ条件

- [ ] 1. 利用者がアカウントを 2 つ以上登録でき、一覧で各アカウントの識別（メールアドレスか利用者が付けた名前）と `five_hour` / `seven_day` の使用率・リセット時刻・支出上限に達しているかが出る。一覧は推論を呼ばない（一覧の前後で各アカウントの使用率が一覧のために増えない）
- [ ] 2. 認証情報は利用者だけが読める権限（0600、置き場のディレクトリは 0700）でリポジトリの外に置き、リポジトリ・ログ・会話の記録・Pull Request・プロセスの引数（`ps` に見える形）に出ない
- [ ] 3. ラッパーの子の claude が `five_hour` / `seven_day` / 支出上限のいずれかで 429 を受けると、ラッパーが検知し、上限に達していない登録済みアカウントのうち最も上限から遠いもの（前提 4）へ替えて次の区間を起動し、同じミッションを続ける。次の区間の最初の入力は、ndf-next があればそれ、無ければ `/goal` の条件か直前の会話の再開である。画面に `ndf-relay:` で始まる 1 行で、替えた理由（上限の種類）と替えた先の識別が出る
- [ ] 4. 登録済みのアカウントがすべて上限に達していて、従量の接続が宣言されていないときは、切り替えず、`ndf-relay:` で始まる 1 行で最も早くリセットされるアカウントとリセット時刻を示す。ラッパーは子の claude をそのまま残し（今と同じ）、`supervise.py` は今と同じ上限待ちに入る
- [ ] 5. 定期的な残量の確認で、今のアカウントの使用率が閾値を超えたとき、上限に達する前の次のカットポイントで、受け入れ条件 3 と同じ選び方で切り替える。確認は推論を呼ばない。間隔と閾値は設定で変えられ、既定値は設計が決める
- [ ] 6. `supervise.py` のプランの worker が上限に当たったとき、上限に達していない登録済みアカウントがあれば、待たずにそのアカウントで同じ呼び出しをやり直す。やり直した事実と替えた先の識別が、プランの状態（`st.cur["auth"]` 相当）とログに残る
- [ ] 7. 切り替えは、同じアカウントグループの別のコンテナで動いている claude の認証を変えない。切り替えの前後で、共有の `.credentials.json` をラッパーと `supervise.py` が書き換えない（claude 自身のトークン更新は除く）か、書き換えても別の設定ディレクトリで動く claude の使うアカウントが変わらないことを、テストか実測で確かめる
- [ ] 8. 切り替えに LLM を使う場合、その呼び出しは Anthropic API か Bedrock の接続で行われ、登録済みのどのアカウントの使用率も増やさない。LLM を使わない場合はこの条件を「使わない」と設計に書いて満たす
- [ ] 9. アカウントを 1 つしか登録していない・何も登録していないときは、今と同じ振る舞いになる（ラッパーは上限で何もしない。`supervise.py` は `NDF_SUPERVISE_CLAUDE_FALLBACK` と上限待ちのまま）
- [ ] 10. 登録したアカウントのアクセストークンが期限を過ぎていても、一覧と切り替えが働く。更新できないアカウントは一覧に「再登録が要る」と出て、切り替えの候補から外れる
- [ ] 11. 既存のテスト（`uv run --frozen --project . --all-extras pytest . -q -n 4`）が通る
- [ ] 12. 登録済みのアカウントがすべて上限に達し、従量の接続が宣言されているときは、ラッパーは次の区間を（受け入れ条件 3 と同じ再開の入力で）、`supervise.py` は同じ呼び出しを、宣言された接続で起動する。子の環境には登録済みアカウントのトークンを渡さない。`ndf-relay:` で始まる 1 行と記録（ラッパーの記録の `account` の行・プランの状態の `auth`）に、従量の接続へ移ったこと・理由（上限の種類）・時刻が残る。宣言の値（キーなど）は記録・画面・プロセスの引数に出ない
- [ ] 13. 従量の接続で動いている間も、登録済みアカウントの使用率とリセット時刻の確認を推論なしで続ける。いずれかのアカウントが上限を外れたら、ラッパーは次のカットポイントで、`supervise.py` は次の claude -p の起動で、そのアカウント（受け入れ条件 3 の選び方）へ戻す。戻したことが理由と時刻とともに受け入れ条件 12 と同じ記録に残る
- [ ] 14. 従量の接続が宣言されていないときは、登録済みのアカウントがすべて上限に達したときの振る舞いが今と同じである（ラッパーは受け入れ条件 4、`supervise.py` は上限待ち）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | 残量の取得先が使えないときも、上限に達した後の切り替え（受け入れ条件 3・6）は会話の記録と 429 だけで働く（前提 3） |
| 性能・拡張性 | 定期の残量の確認は、既定の設定で 1 アカウントにつき 5 分に 1 回を超えて取得先を呼ばない。取得に失敗しても、ラッパーの監視（子の出力の中継）を止めない |
| 運用・保守性 | 切り替えのたびに、時刻・替えた理由・替える前と後の識別をラッパーの記録（`relay_lib/record.py` の記録）に 1 行残す。従量の接続へ移ったとき・戻したときも同じ。トークンと従量の接続の宣言の値は残さない |
| セキュリティ | 受け入れ条件 2。登録・削除・切り替えの記録にトークン・リフレッシュトークンを書かない |
| システム環境 | Claude Code だけ（ラッパーと同じ）。devbase のコンテナ間で `~/.claude` を共有する構成で受け入れ条件 7 を満たす |

| データ | 認証情報の置き場が増える（リポジトリの外、0600）。既存の `.credentials.json` の形は変えない |
| 既存の振る舞い | 登録済みアカウントが 2 つ以上あるときだけ、ラッパーが上限とカットポイントで区間を起動し直し、`supervise.py` が上限待ちの前に別のアカウントでやり直す。従量の接続が宣言されていれば、すべて上限のときにラッパーもそれへ移る（今は `supervise.py` が 1 度だけ試す） |
