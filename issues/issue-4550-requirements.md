# #4550: 開発計画の名前を用途が分かる呼び名にし、形を揃え、耐久ワークフローを 2 つの計画から組む

正は課題の本文（#4550）で、この文書はその写しである。本文から作り直す。手で直さない。

## 何が起きたか

2026-11-26、利用者が実装計画と開発計画（スプリントやレーンの作業を、どの順で何を並行して進めるかを書く計画）のテンプレートを確かめ、開発計画について次の 2 点を指摘した。

- これまでの「実行計画」と「並列の計画」は、名前から用途が分かりにくかった
- 2 つの形が揃っていなかった。これまで、実行計画は進行役の AI が手で書く Markdown で、並列の計画は JSON だけだった

同じ日に利用者は、この Issue で耐久ワークフロー（処理が途中で落ちても記録から続けて、作業を順に進めるプログラム）が 2 つの計画の両方に基づいて作業を組むようにすることも指示した。

## 種類

機能追加（これまでの手順書とコマンドに無かった約束を足すため。足すのは、スプリントの中の順を JSON で持つこと、理由の欄、Markdown への変換、2 つの計画からワークフローを組むことである）

## 今の姿

これまで、開発計画は次の 2 つに分かれていた。

| | 実行計画 | 並列の計画 |
| --- | --- | --- |
| 決めていたこと | 1 つのスプリント（まとめて進める課題の一組）の中で、どの課題の設計と実装を、どの順で、何を並行して進めるか | 同時に流すレーン（独立した 1 本の開発の流れ）の一覧と、レーンの順 |
| 書いていた人と読んでいた相手 | 進行役の AI（conductor）が書き、conductor と進み具合を見る人が読んでいた | まとめ役の AI（オーガナイザー）か人が設定を書き、コマンドが読んでいた |
| 形式 | 手で書く Markdown の表 | JSON。Markdown へ変換する手段は無かった |
| 理由の欄 | 目標の 1 行と、見直した理由だけだった。作業の分け方と順の理由を書く欄は無かった | 無かった。決められていない欄は検査で断られていた |
| 順の進め方 | conductor が工程の終わりごとに表を読み直し、着手できる作業を選んで起動していた | 耐久ワークフローがレーンの順と依存を読んで起動していた |
| 書かない場合 | 課題が 1 件で Pull Request（PR）も 1 本のとき | レーンが 1 本のとき |

SSOT は、[実行計画の手順書](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/issue-plan-strategy/references/execution-plan.md) 、[並列の計画の手順書](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/issue-plan-strategy/references/parallel-plan.md) 、[並列の計画の JSON の定義](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/contracts/workflow/parallel-plan.schema.json) である。

### エンジニア向けの補足

値は NDF 11.0.52（`origin/main`、2026-11-28）で調べた。

- これまで、`plugins/ndf/src` と `plugins/ndf/contracts` に実行計画のファイルを読むコードは無かった（`git grep -ln 'execution-plan\|execution_plan' origin/main -- plugins/ndf/src plugins/ndf/contracts` は 0 件）
- これまで、並列の計画の設定は `ndf lanes init`・`start` が読み、状態は計画とレーンのステートマシンが持ち、`plugins/ndf/src/ndf/progress/plan/run.py` の耐久ワークフローがレーンを起動していた。`ndf lanes` に Markdown を出すサブコマンドは無かった
- これまでの呼び名は、`plugins/ndf` の skills・agents の 24 ファイルに 78 か所、src・contracts の 6 ファイルに 7 か所あった（`git grep -o '実行計画\|並列の計画'`）。このうち `agents/data-analyst.md` の 2 か所（データベースの問い合わせの実行計画）と `skills/pr-tests/SKILL.md` の 1 か所（テスト実行計画）は別の意味の語だった。起票の時点の値は、22 ファイルと 6 ファイルに合わせて 82 か所だった
- これまで、用語集には「実行計画」と「並列の計画」の 2 語が登録されていた

## 何を足すか・変えるか

呼び名の「スプリント実行計画」「並列開発計画」は案で、最終の呼び名は設計で確かめる。

| 点 | これまで | この Issue の後 |
| --- | --- | --- |
| 名前 | 実行計画（スプリントの中の並列） | **スプリント実行計画**と呼ぶ |
| 名前 | 並列の計画（複数レーン） | **並列開発計画**と呼ぶ |
| 形式 | 実行計画は手書きの Markdown、並列の計画は JSON | 2 つの形を揃える。SSOT は JSON でよく、**人が読む Markdown へ変換**する |
| 理由の記述 | 実行計画の「目標」と見直しの「理由」だけ | レーンや作業をそう分け、その順にした理由を書ける欄を持つ |
| ワークフローの組み立て | 耐久ワークフローは並列の計画だけを読み、スプリントの中の順と並行は conductor が実行計画を読んで進めていた | **耐久ワークフローが、2 つの計画の両方に基づいてワークフローを組む** |

## 今の利用者への影響と互換

- この Issue の後は、呼び名と計画の JSON の形が変わる。NDF は普及の前の段階なので、旧い形を読み続ける経路は持たない
- この Issue の後は、手で書いた実行計画の Markdown を作業の順の入力にせず、Markdown は SSOT の JSON から作る

関連する課題:

- レーンが順に流す作業の呼び方: https://github.com/devbasex/ai-plugins/issues/4250
- 計画を 7 つの段階に分け、段階ごとに待たせる仕組み: https://github.com/devbasex/ai-plugins/issues/4050 。同じ耐久ワークフローを変えるので、この Issue の実装はその後に重ねる見込みで、順番は設計で確かめる

## なぜ困るか

- これまでの名前では、2 つの計画がそれぞれどの範囲の順を決めるものかが分からなかった
- これまでの並列の計画は JSON だけで、人が中身を知るには JSON を開く必要があった。2 つの形が違うため、同じ読み方ができなかった
- これまでの計画には、なぜその分け方と順にしたかが残らず、計画が妥当かを後から判断できなかった
- これまでスプリントの中の順は、conductor が表を読んで手で決めていた。計画のとおりに進むかは conductor の読み方に左右され、計画を変えても仕組みの動きは変わらなかった

## 目的

この Issue では、名前から用途が分かり、2 つの計画を同じ形で読めるようにする。なぜこの順で、何を並行して進めるのかを、人が JSON を開かずに読めるようにする。あわせて、2 つの計画に書いた順と並行のとおりに、耐久ワークフローが作業を進めるようにする。

## 対象範囲

含む:
- 手順書・コードの表示の文・用語集の呼び名
- 2 つの計画の形（JSON の項目と Markdown への変換）
- 2 つの計画から耐久ワークフローを組む処理

含まない:
- 要求仕様・設計書・詳細設計書・実装計画のテンプレート（ https://github.com/devbasex/ai-plugins/issues/4545 ）
- 後方互換の経路（NDF は普及の前なので持たない）

## 前提

- 前提 1: 2 つの計画が扱う範囲は変えない。スプリント実行計画は 1 つのスプリントの中を、並列開発計画は複数のレーンを扱う
- 前提 2: 計画を書かずに済む条件（課題が 1 件で PR も 1 本のスプリント、レーンが 1 本）は変えない

## 受け入れ条件

1〜5 の 1 行目は起票の時点の受け入れ条件（廃止した語だけを用語集の語へ言い換えた）で、字下げした箇条は判定のしかたである。6 以降は要求の工程で足した（「起票者の推定」）。「スプリント実行計画」「並列開発計画」は、設計で確定した呼び名に読み替える。「作業」は、スプリント実行計画が順を決める 1 単位（課題のまとまりの設計か実装）を指す。

- [ ] 1. 手順書・用語集・コマンドの表示に、新しい呼び名が使われ、古い呼び名が残らない
  - `git grep -n '実行計画\|並列の計画' -- plugins/ndf/skills plugins/ndf/agents plugins/ndf/src plugins/ndf/contracts plugins/ndf/docs plugins/ndf/README.md docs/glossary.md docs/glossary` の当たりが、次の 3 つだけになる。新しい呼び名の一部、別の意味の語（データベースの問い合わせの実行計画、テスト実行計画）、用語集の廃止した語の欄
- [ ] 2. スプリント実行計画と並列開発計画が同じ構成で書かれ、SSOT の JSON から Markdown を作れる
  - どちらの計画も、コマンドで JSON から Markdown を作れる。手で Markdown を書く手順は手順書に残らない
  - 2 つの Markdown は、見出しの並びと表の列の意味が揃っている。片方の計画にしか無い項目は除く
  - 同じ内容の計画から何度作っても、同じ Markdown になる
  - 起動の後に計画を変えてから作り直すと、変えた後の内容が出る
  - 形の合わない JSON を渡すと、Markdown を作らず、当たった理由を示して失敗する
- [ ] 3. Markdown を読むだけで、行やレーンの分け方と順の理由が分かる
  - 作業とレーンの分け方の理由と、依存（順）ごとの理由が JSON の欄にあり、Markdown にすべて出る
  - 理由が空の計画は、検査で断られる
  - 計画を作っていない人が Markdown だけを読み、作業やレーンをそう分けた理由と、その順にした理由を言える
- [ ] 4. 耐久ワークフローが、スプリント実行計画の JSON と並列開発計画の JSON を読んでワークフロー（実行の順・依存・並列）を組み、起動する。計画を変えると、組むワークフローも変わる
  - 前提: 依存の無い作業が 2 つと、その片方に依存する作業が 1 つあるスプリント実行計画がある。操作: 起動する。結果: 2 つが並行して始まり、残りの 1 つは依存先が済んでから始まる
  - 同時に動かす数は、設定された上限を超えない
  - 依存は、相手の何を待つかを区別する。相手の設計のレビューが収束するまで待つ依存と、相手がマージされるまで待つ依存である
  - 計画の依存か分け方を変えて起動すると、コードと手順書を直さずに、起動する順と並行が変わる
  - 起動の後に計画を変えると、まだ始めていない作業には変えた内容が効き、済んだ作業は流し直さない
  - 並列開発計画のレーンが流すスプリントでは、そのスプリントのスプリント実行計画にも従う
- [ ] 5. 人や conductor が計画を読んで手で順を決めなくても、計画のとおりに進む
  - 起動の後に人と conductor の操作が要るのは、承認と質問への回答、止まった原因への対応、計画の変更だけである。次の作業を選んで起動する操作は要らない
  - 承認を待つ作業があっても、依存の無い作業は進む
  - 「工程の終わりごとに表を読み直して、着手できる作業を起動する」手順が、手順書から無くなる
- [ ] 6. 無い依存先を指す計画と、依存が輪になる計画を起動すると、作業を 1 つも始めず、当たった理由を示して止まる。起動の後の変更が同じ誤りを持つときは、その変更を断り、変える前の計画で進み続ける
- [ ] 7. 作業が 1 つ止まると、それに依存する作業は始まらず、依存の無い作業は進み、止まった作業と理由が conductor かオーガナイザーに届く。ワークフローが落ちた後に起動し直すと、済んだ作業を流し直さずに続く
- [ ] 8. 並列の計画の今の検査と、実行中の変更が、引き続き働く。検査は、同時に動くレーンの触る場所の重なり、レーンの間の課題の重なり、無い依存先と依存の輪を断る。実行中の変更は、レーンの追加、触る場所と依存の変更、レーンの作業の移動である
  - 前提の確認: `uv run --frozen --project . --all-extras pytest plugins/ndf/tests/progress/test_lane.py plugins/ndf/tests/progress/test_plan.py -q -n 4` → 120 passed、38 skipped（2026-11-28、手元の `main`。レーンのコードと `test_lane.py` は `origin/main` と差が無かった。`test_plan.py` は `origin/main` に 14 行の追加があった）
- [ ] 9. 課題が 1 件で PR も 1 本のスプリントは、スプリント実行計画を書かずに始められる
  - 前提の確認: `ndf progress new --help`（11.0.52）に、実行計画を渡す引数は無かった。[実行計画の手順書](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/issue-plan-strategy/references/execution-plan.md) の「作る時点と、作らないとき」も、この場合は書かないと定めていた
- [ ] 10. すべての作業が終わったスプリント実行計画の Markdown が、そのスプリントで最後にマージした PR のコメントに残り、振り返りが読める。コメントを残せないときは、計画の内容を消さない
  - 前提の確認: 実行計画の手順書の「閉じる」が、この順（投稿し、URL を確かめてからファイルを消す）を定めていた。手順書の記述で確かめ、投稿された実物は確かめていない

## 用語

| 用語 | 意味 |
| --- | --- |
| 実行計画 | スプリントの課題を、まとまり・工程ごとの依存・触る箇所・着手できる時点で並べた表。新しい呼び名の案は「スプリント実行計画」 |

| オーガナイザー | 並列の計画を受け持ち、レーンの承認待ちを受けて問う役の AI |
