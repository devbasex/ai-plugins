# #542 #786: cross-review のラウンドを減らす — 要求と受け入れ条件

設計は [issue-542-786-design.md](issue-542-786-design.md)、決定の理由は
[issue-542-786-design-decisions.md](issue-542-786-design-decisions.md) にある。この文書は「何を満たすか」だけを扱う。

マイルストーンは「17 トークン消費の削減」（効果の順 2'''）。版数は配布の工程が決める（`release`）。
#631（収束の条件を厳しくする）は #542 と逆向きの提案であり、この設計の中で採否を決める（採らない。決定 8）。

## 例: 設計 Pull Request の 3 ラウンド目

ホストは claude、引数は付けない。

今（v10.17.3）:

1. 母集合は claude / codex / agy / kiro の 4 者で、round 1 の座席は codex と agy。agy はテストを背景で起動したまま結果を残さずに終わることがある（#786）。実運用では毎回 `--exclude agy` を手で渡している
2. round 1 の担当は、指摘を出し切る指示を受けていない。round 2 の担当は、round 1 の後にどの節が直ったかを知らされない。既存コメントの控えは init の時点のもので、round 1 の指摘とその対応が入っていない
3. round 2 の修正が major の穴を作ると、round 3 の担当はそれを知らずに全体を読み直し、見つけた穴で round 4 へ進む

変更の後:

1. 母集合は claude / codex / kiro の 3 者で、round 1 の座席は codex と kiro。agy は `--include agy` で戻す
2. round 1 の担当は「見つけた指摘はこのラウンドですべて出す」指示を受ける。round 2 の担当は、前のラウンドの head と今の head、その間に変わったファイルの一覧、「変わった節とそれを参照する節を先に見る」観点を受ける。既存コメントの控えはラウンドごとに取り直され、round 1 の指摘と「対応しました」の返信が入る。設計 PR には設計向けの観点も渡る
3. round 3 の担当は round 2 の修正で変わった節から読むため、修正が作った穴を round 3 のうちに出す

## 目的

- **3 ラウンド以上に進む実行を減らす。** ai-plugins の 2026-09-01〜09-15 の 88 件では、3 ラウンド以上の 30% が所要の 70% を使った（#542）。直近の設計 PR は 8 ラウンド × 3 回（#908）や振動の検知での打ち切り（#911 #843）に至っている
- **ラウンドが増える 2 つの原因に手を打つ。** 1 つは 1 ラウンド目で出し切っていないこと、もう 1 つは前の修正が作った穴を次のラウンドが後追いで見つけること（PR #539 の 3 巡目以降の指摘はすべて後者だった）
- **動かない担当で収束が止まるのをやめる**（#786）。手で `--exclude agy` を渡す運用を既定にする
- **ラウンドを増やす方向の提案（#631）とは方針を 1 つにする**

## 対象範囲

含む:

- cross-review のレビュー担当の既定の母集合から agy を外すこと（`--include agy` で戻す）
- 既定の母集合に無い者を外す指定を、止めずに無視すること（共通層のため cross-review と cross-refactoring の両方）と、`--only` で名指しした者を母集合に無くても参加者にすること
- レビューのプロンプトに足すもの: 出し切りの指示（全ラウンド）/ 前のラウンドからの変更と、変わった節を先に見る観点（2 ラウンド目以降）/ テストと背景の処理を起動しない指示
- 既存コメントの控えをラウンドの開始ごとに取り直すこと
- 設計 PR を見分けて、設計向けの観点テンプレートを渡すこと
- cross-refactoring の適用のプロンプトに、背景で起動したテストを待たずに終わらない指示を足すこと（#786 の cross-refactoring 側）
- 上の変更に合わせた文書（`SKILL.md`・`docs/`・確定仕様・`README`・`CLAUDE.md` の cross-review 節）の更新

含まない:

- **#631 の収束の条件（母集合の全員が見るまで収束しない）。** 採らない（決定 8）
- **結果を残さなかった担当を別のランタイムへ振り替えること。** 範囲外の課題 #919 として起票した（決定 9）。置き場所の候補は #870 の drive だが、#870 の本文は扱っていない
- 収束の判定の変更。minor は証拠集約で数えない区分へ落ちるため、新しい指摘が minor だけのラウンドは今も収束する（#732。決定 7）
- 振動の検知の閾値・`max_rounds`・起動し直しの規則の変更（決定 10）
- 設計の成果物（`design` の `deliverables.md`）へ「状態を書き換える経路の一覧」を足すこと。レビューの観点の側で扱う（決定 5）
- 既存コメントの控えを圧縮すること（大きさは非機能の条件で見張る）
- cross-refactoring の参加者の既定（#664 で agy は外してある）
- 効果の測定の仕組み（#893 が扱う）
- 設計の成果物のうち画面・永続データ・API。画面は持たない。状態ファイル（`state.json`）に足すのは、参加者の記録の 1 項目だけである（旧い状態ファイルも読める）。呼び出しの約束はコマンドの引数と出力の行で、設計の入出力の契約の節で扱う

## 受け入れ条件

### 母集合（#786）

- [ ] AC1: ホストが claude で `--exclude` / `--include` を付けないとき、`init` の参加者は claude / codex / kiro の 3 者で、agy を含まない。座席は次の順になる
  - round 1: codex と kiro
  - round 2: claude と kiro
  - round 3: claude と codex
- [ ] AC2: ホストが codex または kiro のときも、既定の参加者は claude / codex / kiro の 3 者である
- [ ] AC3: ホストが agy のとき、参加者は agy を含む 4 者である（ホストは常に母集合に入る。#892）
- [ ] AC4: `--include agy` を付けると agy が参加者に戻り、座席は今（v10.17.3）の既定と同じ輪番になる。`--exclude agy` を付けても（既定に無い者を外す指定でも）終了コード 0 で進む
- [ ] AC4b: `--only agy` を `--include agy` 無しで渡すと、agy 1 者で回る（名指しした者は既定の母集合に無くても参加者になる）。`--only agy --exclude agy` は今どおり終了コード 1 で止まる。再開で `--only none` を渡すと既定の 3 者に戻る
- [ ] AC4c: cross-refactoring の `init` に `--exclude agy` を渡すと（cross-refactoring の母集合に agy は無い）、中断せずに `ℹ` で始まる 1 行を出して続ける。足す者と外す者の重なりは今どおり終了コード 4 で止まる
- [ ] AC4d: 完了の報告（`report`）に、`--exclude` で指定したが既定の母集合に無かった者が 1 行で出る
- [ ] AC5: 次の文書が、既定の母集合を「claude / codex / kiro とホスト。agy は `--include agy` で戻す」と書く。現行の説明として母集合を 4 者と書いた記述は残らない（出た版の変更点の記録は書き換えない）
  - `plugins/ndf/skills/cross-review/SKILL.md` と `docs/05-pool-and-convergence.md`
  - 確定仕様 `docs/specifications/cross-review-participants-and-seats.md`
  - `plugins/ndf/README.md` と `CLAUDE.md` の cross-review 節

### 担当が結果を残さずに終わらない（#786）

- [ ] AC6: レビューのプロンプトの「守るべきこと」が、テストを実行しないこと・背景で処理を起動しないことを求め、実行の確かめは進行側（`verify-findings`）が行うと書く
- [ ] AC7: cross-refactoring の適用のプロンプトが、テストを前景で実行して終わるまで待ち、背景で起動した処理を残したまま終わらないことを求める

### 出し切りと、前の修正の後の観点（#542）

- [ ] AC8: どのラウンドのプロンプトも「見つけた指摘はこのラウンドですべて出す。次のラウンドへ回さない」の指示を持つ。出す対象（修正アクションのある指摘だけ）と、含めてはいけないもの（良い点・nit）は今のまま変わらない
- [ ] AC9: 同じ PR の 2 ラウンド目以降で、前のラウンドの head と今の head が違うとき、プロンプトは「前のラウンドからの変更」の節を持つ。節には 2 つの head の SHA・その間に変わったファイルの一覧・差分を読むコマンド・「変わった節と、それを参照する節・同じ契約を使う節を先に見る。修正が新しく作った経路（状態・分岐・引数）の穴を見る」の観点が入る
- [ ] AC10: 1 ラウンド目と、前のラウンドと head が同じラウンド（修正のコミットが無い）のプロンプトは「前のラウンドからの変更」の節を持たない
- [ ] AC11: 変わったファイルの一覧は 50 件か 5,000 バイトの先に当たる方で打ち切り、残りは件数だけを書く。差分の本文はプロンプトへ入れない（担当が作業ツリーでコマンドを実行して読む）

### 既存コメントの控え（#542）

- [ ] AC12: ラウンドの開始（`start-round`）ごとに既存コメントの控えを取り直す。2 ラウンド目のプロンプトに、同じ実行の 1 ラウンド目で投稿された指摘と、その修正の返信が入る
- [ ] AC12a: 取り直しで 3 つの取得元（インラインコメント・レビュー本文・PR コメント）のどれか 1 つでも失敗したら、前の控えを残す（AC13 と同じ扱い）
- [ ] AC12b: PR の巻き直しの後の最初のラウンドでは、新しい PR の既存コメントで控えを取り直す
- [ ] AC13: 取り直しに失敗したとき（`gh` の失敗など）、ラウンドは止まらず、前の控えのままプロンプトを作り、`⚠` で始まる 1 行で理由を出す

### 設計向けの観点（#542）

- [ ] AC14: 設計 PR（用語の表）は分類に `design` が加わる。`review_instructions` には設計向けの観点テンプレートが入る。`common` / `docs_only` の分類は今のまま残る
- [ ] AC15: 設計向けの観点テンプレートは次の 3 つを求める
  - 要求・設計・決定の記録の 3 文書の間で、受け入れ条件・決定・テスト設計が対応しているか
  - 状態（ファイル・環境変数・状態ファイルの項目）ごとに書き手と読み手を並べ、矛盾する経路が無いか
  - 外部コマンドや外部ツールの挙動を断定する記述に、実測の根拠があるか
- [ ] AC16: 設計 PR でない PR は `design` に分類されない

### 収束の判定（#542）

- [ ] AC17: 収束の判定は変わらない。証拠集約を通ったラウンドで新しい指摘が minor だけなら、今と同じく新しい指摘 0 件として収束する

### 変えないこと

- [ ] AC18: 振動の検知の閾値（0.5）・`max_rounds`（12）・結果が無い担当の起動し直し（同じ席で 1 度だけ）は変わらない。これらのテストは変更なしで通る。`--only` は AC4b の点だけが変わる
- [ ] AC19: 収束の判定は母集合の各担当がレビューしたかを見ない（#631 を採らない）
- [ ] AC20: 既存のテストがすべて通る（下の検証手段）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 「前のラウンドからの変更」の節は、ファイル名の長さと件数によらず 6,000 バイト以下に収まる（差分の本文を入れず、一覧を 5,000 バイトで打ち切るため）。控えの取り直しで増えるのは、同じ実行の前のラウンドの指摘と返信の行だけである |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | `cross-review` の既定の参加者が変わる（agy が外れる）。引数は増えない。`--include agy` で今の既定へ戻せる |
| データ | 状態ファイルの参加者の記録に、無視した除外（`ignored_exclude`）が加わる。無い旧い状態ファイルは今の判定で読む |
| 既存の振る舞い | 2 ラウンド目以降のプロンプトが変わる / 控えがラウンドごとに新しくなる / 設計 PR に観点が 1 つ増える |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| テスト | `uv run --project plugins/playwright-kit/skills/playwright-kit-ops --with pytest pytest . -q -n 4` |
| プラグインの検査 | `claude plugin validate .`（終了コード 0） |
| 手動確認 | 実装の Pull Request の cross-review を新しい既定で回し、プロンプトの控えに前のラウンドの指摘が入ること・2 ラウンド目の「前のラウンドからの変更」の節を、作業ツリーの `.cross_review/*-prompt.md` で目で見る |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| ブランチと Pull Request | `AGENTS.md` の Git 運用ルール（`develop` 宛） |
| `.md` の文言のテスト | 書かない（#885 の方針）。プロンプトの文言は目で確かめ、テストは節の有無と条件の分岐を見る |
| 版 | マイルストーン 26 は 10.17.x の PATCH で出す |

## 用語

| 用語 | 意味 |
| --- | --- |
| 母集合 | レビュー担当になり得るランタイムの集まり。`--exclude` / `--include` を当てる前の既定 |
| 座席 | 1 ラウンドでレビューする 2 者。母集合のうち使える者から輪番で選ぶ（`review_seats`） |
| 新しい指摘 | 直前のラウンドの指摘と一致しない、そのラウンドの指摘（`_new_finding_count`）。証拠集約を通ったラウンドでは数える 3 区分（`verified_blocking` / `needs_human_judgment` / `unrefuted`）だけ |
| 既存コメントの控え | PR の既存のインラインコメント・レビュー本文・PR コメントを 1 行ずつ並べたファイル（`cross-review-pr<N>-existing-comments.txt`）。プロンプトへそのまま入る |
| 設計 PR | 変更ファイルに要求・設計・決定の記録の文書（`issues/` 配下の `*-requirements.md` / `*-design.md` / `*-design-decisions.md`）を含む Pull Request |
