# #4126: 中継の 3 つの環境変数を契約に載せても、検査 const-fact が #4049・#4062 の実装の PR を落とさない

中継は、NDF が claude の会話を包み、文脈が尽きる前に次の会話へ切り替えるラッパーである。中継が子の会話へ渡す 3 つの環境変数（`NDF_RELAY_DIR`・`NDF_RELAY_LAUNCH`・`NDF_RELAY_SESSION`）を環境変数の契約 `plugins/ndf/contracts/domains/env.json` に載せたまま、`ndf check` が #4049 と #4062 の実装の PR を通すようにする。ラッパーが子へ渡す名前と契約の行は、今の #4062 の設計のとおりテストで結ぶ。

## 何が起きたか

#4061・#4062・#4064 の設計（PR #4095、`issues/issue-4061-4062-4064-design.md` の決定 4）は、`NDF_RELAY_LAUNCH` の名前を `signals` の定数 `LAUNCH_ENV` に持つと書く。一方で、`env.json` に `NDF_RELAY_LAUNCH` の行を足すと、検査 `const-fact` の `table-str`（契約の表の `id` と同じ字を最上位の定数に写すことを禁じる）がその定数を落とす。#4101 の設計（PR #4125）の中で、一時の写しで見つかった。

この課題の設計で確かめ直すと、同じ形がほかに 2 つある。

- #4049 の詳細設計は、`NDF_RELAY_SESSION` の行を足し、定数 `SESSION_ENV` を `signals` に置く。#4049 の実装は #4062 より先なので、最初に落ちるのは #4049 の実装の PR である
- #4062 の詳細設計は、定数 `DIR_ENV`（`"NDF_RELAY_DIR"`）を `signals` に置く。`NDF_RELAY_DIR` の行は今の `env.json` に既にあるので、定数を足した時点で落ちる

## 種類

不具合（設計どうしの食い違い）。`ndf check` が通ることは、実装の PR を取り込む約束として今の SSOT（`plugins/ndf/src/ndf/checks/README.md` の検査の規則の表と CI のジョブ）にある。設計の書いた形のまま実装すると、その約束を破る。

`origin/main`（`ec8340675`）の写しのツリーで、#4049・#4062 の設計の形を当てて `ndf check --only const-fact` を打つと、次のとおり落ちる（2026-11-22）。

| 上に加えて `SESSION_ENV = "NDF_RELAY_SESSION"` を足す（#4049 の詳細設計） | 違反 2 件: `LAUNCH_ENV` と `SESSION_ENV` |

## 期待する結果

#4049 と #4062 の実装の PR が、`env.json` に中継の 3 行を載せたまま `ndf check` を通る。名前の正本は `env.json` の 1 か所で、コードは名前を写した最上位の定数を持たない（#4101 の決定 2 と同じ扱い）。ラッパーが子へ渡す名前と契約の行は、今の #4062 の設計のとおりテストで結ばれる。

4. 終了コード 1 で、`table-str: LAUNCH_ENV が表 env の id を写す` が出る

## なぜ困るか

#4049 の実装の PR は CI の `ndf check` で落ち、#4062 の実装の PR も落ちる。実装の途中で気付くと、設計を直す工程に戻り、設計承認ゲートを通し直す手戻りになる。#4049・#4062 は並列開発の計画 p12 で順に待たれている（#4049 → #4061・#4062 → #4101）ので、1 本が止まると後ろの 2 本も止まる。

## 目的

#4049・#4062・#4101 の実装の PR が、設計の書いたとおりに作って `ndf check` を通る状態にする。名前の持ち方を #4101 の方針にそろえ、3 つの設計の間に食い違いを残さない。

## 対象範囲

含む:

- 中継の 3 つの名前（`NDF_RELAY_DIR`・`NDF_RELAY_LAUNCH`・`NDF_RELAY_SESSION`）のコードでの持ち方と、ラッパーの `launch_env` が返す名前の組の持ち方
- 名前と契約を結ぶテストの形
- #4049・#4062 の設計の、食い違う記述の読み替え（この課題の設計に書く。2 つの設計文書そのものは書き換えない）
- 実装の置き場（どの実装の PR に入れるか）と、#4101 との順

含まない:

- 検査 `const-fact` の振る舞いの変更
- 中継の 3 行の値（`area`・`set_by`・`type`・`child`・`meaning`）。#4062 の設計の「データ構造」のとおりにする
- 中継の 3 つ以外の名前の定数（#4101 が外す）
- hook の見分け（`relay_role`）・締め切りの出力など、#4061・#4064 の振る舞い

## 前提

- 前提 1: #4049 の実装 → #4061・#4062 の実装（1 本目）→ #4101 の実装、の順はそれぞれの設計（#4049 の「影響と危険」・#4062 の決定 8・#4101 の決定 8）のとおりで、この課題は変えない
- 前提 2: hook の経路は `ndf.contracts` を import しない（`signals.py` の冒頭・決定 111）。hook が読む名前は字で書く
- 前提 3: 普及のフェーズの前で、互換の経路を持たない（MVV 版 11 の Value 4）
