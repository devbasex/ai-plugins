設計・実装・レビューなどの各工程が、プロジェクト MVV（`.ndf/mvv.md`）に従って動く。従ったかを工程ごとに機械と相手役で確かめ、外れていれば修正担当へ戻して直させる状態にする。

仕組みの大半は 11.0.31（ https://github.com/devbasex/ai-plugins/pull/4419 ）で入り、受け入れ条件 1〜6・8 を満たした。残っているのは受け入れ条件 7 だけである。MVV の Value 5 に反していた実物の設計を AI のレビュー（cross-review）に読ませても、レビューを担当する AI（相手役）が Value 5 を挙げなかった。この課題の残りの作業は、相手役への指示の基準 5 を具体にして、条件 7 を確かめ直すことである。

## 何が起きたか

2026-11-22、MVV に反する設計が、AI のレビューでも承認の資料でも見つからないまま承認された。

- その設計（#4049 の最初の設計、 https://github.com/devbasex/ai-plugins/pull/4060 ）では、引継ぎを、背景で動く監視が終わるまで待った。引継ぎは、AI（Claude Code）の作業内容を引継ぎ文書に残し、実行中の Claude Code を終了して、新しいセッションで作業を続ける処理である。全体を調整する AI は監視を常に続けるため、この条件では一度も新しいセッションへ引き継げない
- この設計は、MVV バージョン 11 の Value 5 に反する。Value 5 の文は「人の承認・ほかのレーン・背景の作業・CI を待つ間も待つだけで止まらない。待つ間は別の作業を進めるか、待っていることをオーガナイザーや conductor へ伝え、伝えられた側が別のレーンか supervisor を起動する」である。当時の設計は、このうち「背景の作業を待つ間」に当たる。人の承認を待つ形ではない
- AI のレビュー（cross-review）の 3 回も、設計承認の資料も、この問題を見つけなかった。利用者が承認の後に気づいて、設計を直させた
- 設計承認の資料の決定ごとの根拠の行（「根拠: Value N（MVV バージョン N）」）は、設計者の自己申告である。#4016 の資料（ https://github.com/devbasex/ai-plugins/pull/4058 ）は、今のバージョンが 10 なのに決定 10 件すべてを「MVV バージョン 1」と書いていた。バージョンと番号を確かめる検査が無かった（承認ゲートの MVV 判定の課題 https://github.com/devbasex/ai-plugins/issues/3959 が同じ事象を記録している）
- 同じ日に並行して作られたほかの設計も、今のバージョンが 11 なのに根拠の行を「MVV バージョン 1」と書いた。#4050 の設計（ https://github.com/devbasex/ai-plugins/pull/4072 の `issues/issue-4050-design.md`）は 13 行、#4049 の設計（ https://github.com/devbasex/ai-plugins/pull/4067 の `issues/issue-4049-design.md`）は 9 行である（2026-11-22 に `git show` と `grep` で数えた）。原因は、設計者がコピーする `design` の `references/decisions.md` の例がバージョン 1 のままであること（#3959）。どの検査も止めなかった

利用者は同じ日に MVV をバージョン 11 へ改訂し（ https://github.com/devbasex/ai-plugins/pull/4075 。全体の設計方針 #4069 を入れた）、各工程がこの MVV に従って動き、従ったことを確かめて直させる仕組みを求めた（「リクエスト（原文）」）。

2026-11-24 に、仕組みは 11.0.31 でリリースされた。同じ日のリリース後テストで、条件 7 は 2 回とも不合格だった（記録: https://github.com/devbasex/ai-plugins/pull/4419#issuecomment-7127514486 、振り返り: https://github.com/devbasex/ai-plugins/issues/4076#issuecomment-7127577428 ）。

- #4060 の最初のコミット 3daeda927 を 11.0.31 の cross-review に 2 通りの起点で読ませた。MVV の項目を挙げた指摘は Value 3・Value 6・C4 だけで、Value 5 を挙げた指摘は無かった。kiro は 2 回とも MVV の項目を挙げなかった
- 仕組みそのものは動いた。基準 5 は MVV バージョン 11 の本文の場所とともに相手役の指示に入り、根拠の行の誤り 5 件は NDF の機械の確かめが指摘した
- 相手役は「背景の監視が終わるまで引継ぎを待つ」設計を、作業を失わないための正しい待ち（Value 3・C4 の側）と読み、Value 5 の「待つだけで止まらない」に反するとは読まなかった。今の基準 5 の指示は、設計の振る舞いを Value の文と 1 つずつ突き合わせることを求めていない

### エンジニア向けの補足

- 2026-11-22 の作業計画 p12 の中で起きた。#4049 の最初の設計では、中継のラッパーが起動した Claude Code に `ndf lanes wait` などの監視だけが残っている場合も、ラッパーは監視が終了するまで引継ぎを待った。引継ぎでは、Claude Code が引継ぎ文書を書いて応答を終え、ラッパーが新しいセッションで次のセグメントを起動する（当時の設計書 `issues/issue-4049-design.md` の「背景の supervisor を待つレーンの conductor の例」）。オーガナイザー（全体を調整する AI）は `ndf lanes wait` を常に背景で張るので、この条件では新しいセッションへ引き継げない
- 「同じ日に並行して作られたほかの設計」は、計画 p12 のほかのレーンの設計である

## 今の姿

11.0.31 から、工程の担当と cross-review は承認済みの MVV を読んで動く。仕組みの SSOT は確定仕様の [cross-review-project-mvv.md](https://github.com/devbasex/ai-plugins/blob/main/docs/specifications/cross-review-project-mvv.md) と [ndf-mvv-current-and-stage-inputs.md](https://github.com/devbasex/ai-plugins/blob/main/docs/specifications/ndf-mvv-current-and-stage-inputs.md) 、工程での読み方は [project-mvv.md の「工程での読み方」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/project-mvv.md#工程での読み方) にある。

cross-review の相手役への指示は、指摘の基準の文を [review-criteria.json](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/contracts/data/review-criteria.json) から組む。承認済みの MVV があるとき、基準 5（`mvv_criterion` と `mvv.reviewer`）は相手役に次のことだけを求める（11.0.36 の main で確かめた）。

- 基準の文: MVV の Mission・Vision・Value に反するか、「必ず人の承認が要る操作」に当たるものを指摘する
- 書き方: 反している項目を 1 つ書き、impact に MVV のどの文に反するかと利用者に何が起きるかを書く

差分の中のどの振る舞いを、どの Value の文と比べるかは、相手役の読み方に任されている。

## 何を足すか・変えるか

受け入れ条件 1〜6・8 の分（工程の入力・指摘の基準 5・根拠の行の確かめ・修正担当へ戻す流れと記録・「工程での読み方」）は 11.0.31 で足した。残りの作業で変えるのは次の 1 点である。

| | 今 | 足した後 |
| --- | --- | --- |
| cross-review の基準 5 の指示 | MVV に反するものを指摘させるだけで、何をどの文と比べるかは相手役次第 | 差分の中の振る舞い（何かの終わりを待つ・止める・承認を省く・人へ問う、など）を挙げさせ、それぞれを MVV の各 Value の文と 1 つずつ突き合わせて、反する Value を指摘に書かせる |

## なぜ困るか

- 承認の場で MVV に照らす者が人だけになる。人は承認の後で気づき、やり直しは承認ゲートの後の手戻りになる（#4049 では設計のやり直し 1 回）
- 誤ったバージョンの根拠の行が、そのまま確定仕様へコピーされる（11.0.31 で機械の確かめを足した）
- 以前は、MVV に反するとされた指摘を修正担当が「反しない」として見送った件数を記録しておらず、判断の基準（MVV）を見直す手がかりが無かった。11.0.31 でこの記録を追加した（受け入れ条件 5。記録の置き場は `mvv-signals.jsonl`）
- 11.0.31 の後も、#4049 と同じ形の設計（承認の要らない作業を、背景の作業の終わりを待って止める設計）は、相手役が Value 5 に反すると読まないまま通りうる。仕組みがあっても、最初の事象を防げていない

## 目的

- 各工程の担当が承認済みの MVV を読んで動き、MVV に反する出力は承認ゲートより前に、機械と相手役が見つけて修正担当へ戻す
- 人の手を止めるのは、レッドライン（必ず人の承認が要る操作）に当たるときと、AI が決められないときだけにする
- 最初の事象（#4049 の最初の設計）と同じ形の設計を、cross-review の相手役が Value 5 に反すると指摘できるようにする

## 前提

- 前提 1: 「承認済みの MVV」は、PR のマージ先のブランチ（ベースブランチ）の `.ndf/mvv.json` の最後のバージョンで、`.ndf/mvv.md` の sha256 が一致するものを指す。PR の head が MVV を変えても、その PR の確かめには使わない（MVV を変える PR は共通原則の C7 で承認ゲートが人へ回す）
- 前提 2: 承認済みの MVV が無いリポジトリ（状態 `absent`・`unapproved`）では、MVV の観点も根拠の行の確かめも現れず、今の振る舞いのまま動く
- 前提 3: 条件 7 では、当時のファイル一式を参照できる状態で、設計書・詳細設計書・要求仕様書の 3 ファイルの差分を、今承認されている MVV（2026-11-25 の時点でバージョン 11）でレビューする。今の実装が混じると当時とは別の指摘が出るため、当時のファイルをそのまま使う。入力の組み方は設計で決める

### エンジニア向けの補足
