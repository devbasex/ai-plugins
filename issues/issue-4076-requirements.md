# #4076: 各工程（設計・実装・レビュー）がプロジェクト MVV に従って動き、従ったかを工程ごとに確かめて差し戻せるようにする

正は課題の本文（#4076）で、この文書はその写しである。本文から作り直す。手で直さない。

設計・実装・レビューなどの各工程が、プロジェクト MVV（`.ndf/mvv.md`）に従って動く。従ったかを工程ごとに機械と相手役で確かめ、外れていれば差し戻せる状態にする。

## 何が起きたか

2026-11-22 の計画 p12 で、MVV に反する設計がレビューと承認の資料を素通りした。

- #4049 の最初の設計（PR #4060）は、背景に `ndf lanes wait` などの監視だけが残る子も、監視が戻るまで引継ぎを待つ形だった。オーガナイザーは `ndf lanes wait` を常に背景で張るので、引継ぎへ一度も進めなくなる。MVV 版 11 の Value 5（「人の承認を待つ間も、承認の要らない作業は止まらずに進む」）に反する。cross-review の 3 ラウンドも、設計承認の資料も、これを MVV に照らして指摘しなかった。利用者が承認の後に気づいて、設計を直させた
- 設計承認の資料の決定ごとの根拠の行（「根拠: Value N（MVV バージョン N）」）は、設計者の自己申告である。#4016 の資料（PR #4058）は、今の版が 10 なのに決定 10 件すべてを「MVV バージョン 1」と書いていた。版と番号を確かめる検査が無い（#3959 が同じ事象を記録している）
- 同じ日の計画 p12 のほかのレーンの設計も、今の版が 11 なのに根拠の行を「MVV バージョン 1」と書いた。#4050 の設計（PR #4072 の `issues/issue-4050-design.md`）は 13 行、#4049 の設計（PR #4067 の `issues/issue-4049-design.md`）は 9 行である（2026-11-22 に `git show` と `grep` で数えた）。原因は、設計者が写す `design` の `references/decisions.md` の例が版 1 のままであること（#3959）。どの検査も止めなかった

利用者は同じ日に MVV を版 11 へ改訂し（PR #4075。全体の設計方針 #4069 を取り込んだ）、各工程がこの MVV に従って動き、従ったことを確かめて差し戻せる仕組みを求めた（「リクエスト（原文）」）。

## 種類

機能追加（工程が MVV を読んで従ったかを確かめる約束は、今の SSOT のどこにも無い。今の SSOT は承認ゲートの直前の判定だけを約束する）

## 今の姿

MVV の本文と承認の記録の形、承認ゲートの直前の判定は [project-mvv.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/project-mvv.md) と [pace.md の「MVV 判定」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/pace.md) にある。工程ごとの MVV との関わりは次のとおりである。

| 工程 | MVV との関わり | 確かめ | 差し戻し |
| --- | --- | --- | --- |
| 設計（`design`） | SKILL.md が「決定ごとに根拠の MVV の項目を書く」「反する疑いは人へ戻す」と書く | 無い（自己申告。版も番号も確かめない） | 無い |
| 実装（`tdd-cycle`） | SKILL.md の「実装の選択を MVV と突き合わせる」が、依存・公開インタフェース・データの扱いに限って書く | 無い | 無い |
| リファクタリング（`cross-refactoring`） | 提案と計画のプロンプトが MVV を `$RF_MVV` で受け、項目に `mvv_basis` を書く | 無い | 無い |
| コードレビュー・設計レビュー（`cross-review`） | 指摘の基準（`contracts/data/review-criteria.json`）に MVV が無い。相手役と修正担当は MVV を読まない | 無い | 無い |
| 承認ゲート | `ndf records mvv gate` が判定する。`normal` では判定しない（#3959） | ゲートの前だけ | 人の承認で |

- supervisor と worker の起動指示の項目（[agent-layers.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/agent-layers.md) の「起動の指示」）に MVV の欄が無い。担当が MVV を読むかは、Skill の本文を読んだかに任されている
- `design`・`tdd-cycle`・`requirements-design` の SKILL.md と `design` の `references/decisions.md` が指す `project-mvv.md` の「工程での読み方」の節は、今の `project-mvv.md` に無い（参照切れ）

## 何を足すか・変えるか

| | 今 | 足した後 |
| --- | --- | --- |
| 工程の入力 | 担当が MVV を読むかは担当次第 | 起動指示が承認済みの MVV の版と本文の場所を渡し、担当はそれを読んで動く |
| cross-review の指摘の基準 | MVV の観点が無い | 承認済みの MVV があるとき「MVV に反する」の観点が現れ、反する指摘は収束を止める重さで修正担当へ渡る |
| 根拠の行の版と番号 | 確かめない | 機械が版と番号を確かめ、外れれば直すまで工程が終わらない |
| 差し戻しと記録 | 無い | MVV に反する指摘と根拠の行の誤りは修正担当へ戻り、判定と差し戻しが MVV の記録に残って改訂の兆候に数えられる |
| `project-mvv.md` の「工程での読み方」 | 無い（参照切れ） | ある |

## なぜ困るか

- 承認の場で MVV に照らす者が人だけになる。人は承認の後で気づき、やり直しは承認ゲートの後の手戻りになる（#4049 では設計の差し戻し 1 回）
- 誤った版の根拠の行が、そのまま確定仕様へ写る
- 覆しの記録（`mvv-signals.jsonl`）は承認ゲートの判定と人の回答の食い違いからしか作られず、工程の中で MVV が判断の基準として働いたかが数えられない。MVV の改訂の兆候が集まらない

## 目的

- 各工程の担当が承認済みの MVV を読んで動き、MVV に反する出力は承認ゲートより前に、機械と相手役が見つけて差し戻す
- 人の手を止めるのは、レッドライン（必ず人の承認が要る操作）に当たるときと、AI が決められないときだけにする

## 対象範囲

含む:
- 設計・詳細設計・実装・リファクタリング・レビュー・完了判定の担当（supervisor・worker・相手役・修正担当）へ、承認済みの MVV の版と本文を渡す形
- cross-review の指摘の基準の MVV の観点（設計 PR と単位の PR の両方）と、その指摘の重さ・修正担当への渡し方
- 設計文書など PR の差分が引く根拠の行の版と番号を、機械で確かめる仕組み
- MVV に反する指摘・根拠の行の誤りの差し戻しと、その記録（`mvv-validation.jsonl`・`mvv-signals.jsonl`）
- `project-mvv.md` の「工程での読み方」の節

含まない:
- 承認ゲートの直前の MVV 判定を `normal` でも行うこと、承認資料の根拠の行の確かめ、即時修正のプランの MVV 判定（#3959 が持つ。この Issue が作る確かめの仕組みを #3959 が承認資料へ当てる）
- MVV 判定で通る設計を増やす判定の指示文（#2912・#3017）
- MVV の本文の改訂（利用者の承認で行う）
- cross-refactoring の提案の採否の基準そのもの（`$RF_MVV` へ承認済みの MVV の版と本文の場所を渡すことだけを含む。提案の `mvv_basis` の番号の確かめは含まない）

## 前提

- 前提 1: 「承認済みの MVV」は、PR の宛先のブランチ（ベースブランチ）の `.ndf/mvv.json` の最後のバージョンで、`.ndf/mvv.md` の sha256 が一致するものを指す。PR の head が MVV を変えても、その PR の確かめには使わない（MVV を変える PR は共通原則の C7 で承認ゲートが人へ回す）
- 前提 2: 承認済みの MVV が無いリポジトリ（状態 `absent`・`unapproved`）では、MVV の観点も根拠の行の確かめも現れず、今の振る舞いのまま動く

## 受け入れ条件

- [ ] 1. 設計・詳細設計・実装・リファクタリング・レビュー・完了判定の各工程の担当が、承認済みの MVV の本文と版を入力に受ける。起動指示の項目（supervisor へ・worker へ）、相手役と修正担当への指示、cross-refactoring の `$RF_MVV` のどれにも、承認済みの MVV の版と本文の場所が入る
- [ ] 2. cross-review の指摘の基準に「MVV への適合」の観点があり、反する指摘は収束を止める重さで修正担当へ渡る（設計 PR と単位の PR の両方）。承認済みの MVV が無いリポジトリでは観点が現れない
- [ ] 3. 設計文書など PR の差分が足した根拠の行の MVV の版が承認の記録の今の版と違うか、引いた項目の番号がその版に実在しなければ、機械がそれを指摘にして修正担当へ渡し、直るまでレビューが収束しない（工程が終わらない）。例: 版 11 のリポジトリで、PR #4072 の差分のように「根拠: Value 5（MVV バージョン 1）」を足すと指摘になる
- [ ] 4. MVV に反するとされた出力は修正担当へ差し戻され、直すまで次の工程へ進まない。レッドライン（共通原則の `C<番号>`・プロジェクト MVV の `P<番号>`）に当たるとされたものだけは修正担当へ渡さず、承認ゲートで人が見る
- [ ] 5. MVV に反する指摘の判定と差し戻し（直した・見送った）が MVV 判定の記録に残り、相手役と修正担当の判断が食い違ったもの（修正担当が「反しない」として見送ったもの）が `ndf records mvv signals` の改訂の兆候に数えられる
- [ ] 6. `design`・`tdd-cycle`・`requirements-design` の SKILL.md と `design` の `references/decisions.md` が指す `project-mvv.md` の「工程での読み方」の節があり、参照切れが無くなる
- [ ] 7. 2026-11-22 の #4049 の最初の設計（PR #4060 の最初の版。監視の終わりを待つ形）を入力に cross-review を流すと、相手役の少なくとも 1 つが MVV の Value 5 に反するとして指摘する
- [ ] 8. 承認済みの MVV が無いリポジトリで、cross-review の指示・指摘の扱い・結果の形が今と変わらない（退行しない）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 相手役 1 つ・1 ラウンドあたりに足す入力は、MVV の本文を 1 回読む分（版 11 で約 17 KB）を上限とする。指示の本文へ MVV を写さず、場所だけを渡す |
| 運用・保守性 | 指摘の基準の文と MVV の観点の文は `review-criteria.json` の 1 か所に置き、`fix` の SKILL.md の表は人向けの写しのまま |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`ndf records mvv` にサブコマンドが足される。相手役の出力の JSON の指摘に任意のキーが足される。cross-review の結果 JSON にキーが足される。どれも足すだけで、今の入出力は変わらない |
| データ | `mvv-validation.jsonl`・`mvv-signals.jsonl` に行の種類が足される。移行は無い |
