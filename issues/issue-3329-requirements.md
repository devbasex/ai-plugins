## 事象

## 期待する結果

プラグインの導入先を読めない権限でも、人のいない実行の最後の応答の結果の行が、契約の 3 つの値（`判断が要る` / `完了` / `できなかった`）のどれかになる。

## 再現手順

1. remote の無い使い捨てのリポジトリを作る（`git init` と小さな `calc.py`・`test_calc.py`）
2. その根で `NDF_FACTORY_RUN=1 claude -p "/ndf:development-workflow calc.py に足し算の関数 add(a, b) を足し、test_calc.py にそのテストを足す" --output-format stream-json --verbose --permission-mode acceptEdits --max-budget-usd 3` を打つ
3. 最後の `result` の文の最後の `- 結果:` の行の値が、契約の 3 つの値のどれでもない

## 前提

- 前提 1: Factory のランナーは、AI がプラグインの導入先（作業ディレクトリの外）を Read できない権限で動くことがある。この課題はその権限でも結果の行を契約の値にすることを扱い、ランナーの実際の権限の設定は確かめない
- 前提 2: Factory のランナーは、結果の行の値が契約の 3 つの値の外なら区間を失敗として扱う（#3242 の前提 1）。ランナーの側は別のリポジトリにあり、この課題では確かめない
- 前提 3: hook のプロセスは、AI の Read の権限に関わらずプラグインの導入先の契約のファイルを読める。今の Stop の hook が契約を読んで判定できていることが根拠である（「事象」の順 2 で、hook は契約に照らして「結果の行が無い」と差し戻した）
- 前提 4: Bash が承認待ちで拒まれて工程を続けられないこと自体は、この課題で直さない。続けられない区間は `- 結果: できなかった` と理由で終わるのが正しい振る舞いで、この課題はその結果の行を契約の形にする

## 対象範囲

含む:

- 人のいない実行の Stop の hook の差し戻しの文に、契約の結果の値と値ごとに要る項目を載せること
- 載せる値と項目を、契約のファイル（`plugins/ndf/contracts/forms/unattended-report.json`）から作ること（Python の文字列や文書へ写さない）
- 差し戻しの上限に達した後も、契約に無い値のまま区間が終わる場合への手当て（未決 2）
- UserPromptSubmit の案内に同じ値と項目を載せるか（未決 1）

含まない:

- 区間の報告の契約の形（結果の値・項目・値ごとに要る項目・材料の書き方）の変更
- Bash が承認待ちで拒まれる権限の扱い（前提 4）
- Factory のランナーの変更と、ランナーの権限の設定
- 差し戻しの上限の回数（`hook.unattended-pushback` の `attempts`）の変更
- `NDF_FACTORY_RUN` の無い実行の振る舞い

## 用語

| 用語 | 意味 |
| --- | --- |
| 人のいない実行 | 環境変数 `NDF_FACTORY_RUN` が空でない実行ジョブの区間（#3242 の定義） |
| 区間の報告 | 人のいない実行の conductor が区間を終える最後の応答の末尾に置く報告。形の正本は `plugins/ndf/contracts/forms/unattended-report.json` |
| 結果の行 | 最後の応答の文の中の、最後の `- 結果: <値>` の行 |

この文書では、次の言い方を本文で使う（プロジェクトの用語集の語ではない）。

- 値ごとに要る項目: 結果の値ごとに、無しにしてはいけない項目（契約の `shape.required`）。条件つきの項目（区分が `ndf-gate:` で始まるときの承認ゲートなど）を含む
- 差し戻しの文: Stop の hook が `decision: block` で返す `reason` の文
- 案内: UserPromptSubmit の hook が印を作るときに返す文
- プラグインの導入先: `${CLAUDE_PLUGIN_ROOT}` が指すディレクトリ。作業ディレクトリの外にある

## 受け入れ条件

- [ ] 1. 人のいない実行の Stop の hook の差し戻しの文に、契約の結果の 3 つの値（`判断が要る` / `完了` / `できなかった`）すべてと、値ごとに要る項目（条件つきの項目は条件も）が載る。誤りが「結果の行が無い」だけのときも載る。ユニットテストで、契約の値と要る項目がすべて差し戻しの文に現れることを確かめる
- [ ] 2. 差し戻しの文に載る値と項目は、hook が読んだ契約から作られる。契約の値か要る項目を変えた形（テストの中で作る別の契約）を与えると、差し戻しの文もその形に変わることをユニットテストで確かめる。値と項目の一覧を Python の文字列・Skill の本文へ写さない
- [ ] 3. 差し戻しの文だけを読めば、プラグインの導入先のファイルを Read せずに、契約に合う区間の報告（行頭の `- `・結果の行の位置・値ごとに要る項目）を書ける。差し戻しの文に載る例か形の説明から作った区間の報告が、契約の判定（`unattended_report.report_errors`）で誤り 0 件になることをユニットテストで確かめる
- [ ] 4. 差し戻しの上限に達した後の Stop で、結果の行の値が契約の外のときの扱いが設計の決定（未決 2）どおりに働き、その振る舞いをユニットテストで確かめる。どの決定でも、同じ区間の差し戻しの回数は上限の宣言（`hook.unattended-pushback`）を超えない
- [ ] 5. 退行しない: 形に合った Stop は差し戻されず回数が数え直される・背景の作業か予定が残る Stop は差し戻されない・契約か上限の宣言を読めなければ差し戻さずに通す・`NDF_FACTORY_RUN` の無い実行では登録の行が Python を起動しない。既存の `test_hook_unattended.py` と `test_unattended_report.py` のこれらの振る舞いのテストが、期待値を変えずに通る（差し戻しの文の中身を照合するテストは受け入れ条件 1〜3 に合わせて直してよい）
- [ ] 6. 区間の報告の契約のファイルの `shape`（値・項目・値ごとに要る項目・材料）と `cases` の期待値は変わらない
- [ ] 7. リリース後に「再現手順」の 2 を開発版チャネルの版で打つと、最後の `result` の文の最後の結果の行の値が契約の 3 つの値のどれかになる。同じ権限で Bash が拒まれる区間では、値は `できなかった` で `- 理由:` の行が無しでない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | `NDF_FACTORY_RUN` の無い実行では、登録の行の sh が Python を起動しない今の振る舞いを保つ。差し戻しの文を作るのに、Stop 1 回あたりで契約のファイルを読む回数を今の 1 回から増やさない |
| 運用・保守性 | 結果の値と値ごとに要る項目の正本は契約のファイル 1 つのまま。差し戻しの文はそこから作る（Value 11） |
