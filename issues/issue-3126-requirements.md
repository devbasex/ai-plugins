# #3126: まとめの最後の検査: 範囲がスプリントの変更でなく前回の印からのベースブランチ全部になり、レビュー済みの差分とほかのレーンの変更を cross-review し直す

正は課題の本文（#3126）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 事象

スプリントのまとめの最初のプラン「最後の検査」（`supervise.py new close` の `1-check`）が、そのスプリントの変更ではなく、前回の検査の印から今のベースブランチの先頭までの全部を検査する。すでにスプリントの検査で cross-review を通した差分と、ほかのレーンの変更までもう一度 cross-review にかけるため、まとめが長く終わらない。

実例（2026-11-12、計画 p5 のレーン lci）: v10.27.58 のリリースの直後（14:01 JST）にまとめが始まり、`1-check` の実行条件（`check-trigger.py eval --id lci-1-final --final`）が「範囲 a591736105..e404872785（origin/check-done/checkから）・PR 4 本」「ファイル 99 件」を返した。範囲には lci 自身のスプリント（スプリントの検査で cross-review 済み）、レーン lflow と aixrepo-1 の確定仕様化、リリースの版のマージが入る。review のステップ（kiro を相手役にした cross-review）が 40 分（`elapsed` 2308 秒）を超えても終わらず、確定仕様化・振り返り・棚卸し（`4-close`）に進まない。

同じ計画のレーン lgate のまとめでは範囲が空で、検査を飛ばしたため速く終わった。

**リリースの後にレビューしている。** まとめは、本番のリリースの答え（`released`）を受けてから始まる。そのため、最後の検査の cross-review は本番へ出し済みの差分を見ていることになり、指摘があってもリリースを止められない（直すには次のリリースが要る）。最後の検査の役割（スプリントの検査の後に入った差分を拾う）に当たる確定仕様化の差分は、まとめの 4 つ目（`4-close`）で作られるため、1 つ目の最後の検査の時点ではまだ無い。

2026-11-12 のレーン lci では、オーガナイザーが最後の検査を止めさせ、`4-close` へ進ませた（判断の記録あり）。

## 期待する結果

最後の検査は、本番のリリースの前に置くか、リリースの後に置くなら確定仕様化の後に置いて、その差分だけを見る。範囲は、そのスプリントが最後の検査の後に足した変更（スプリントの検査の後に入った確定仕様化の差分など）だけになる。スプリントの検査で通した差分と、ほかのレーン・ほかのスプリントの変更は、もう一度 cross-review にかけない。範囲が空か、文書のファイルだけなら、cross-review を回さない。

## 再現手順

1. 並列の計画で、2 本以上のレーンがスプリントを develop へマージし、リリースを出す
2. 後からまとめに入ったレーンで `supervise.py new close` のプランを流す
3. `1-check` の実行条件が、前回の検査の印からの develop の全部を範囲にし、cross-review を回す

## 影響

- 並列の計画のまとめが、ほかのレーンの変更の量に比例して長くなる。確定仕様化・振り返り・棚卸しと課題を閉じるのが遅れ、`after` で待つレーンの起動も遅れる
- 同じ差分を 2 回以上 cross-review にかけるため、token の費用が増える

## 前提

- 前提 1: 最後の検査の目的は「そのスプリントの変更のうち、どの検査も見ていない差分を拾う」ことである。ほかのレーン・ほかのスプリントの変更は、それぞれのスプリントの検査か最後の検査が見る
- 前提 2: 「文書のファイル」と「振る舞いを決める文書」の分け方は、リポジトリの宣言 `docs`（`.ndf/project.json`）と、まとめたリリースの「文書だけの範囲」が使う分け方（`plugins/ndf/scripts/lib/parallel_release.py` が呼ぶ `diff_kinds`）に揃える。範囲のファイルのうち、コードのファイルと振る舞いを決める文書が 0 件で、文書のファイルが 1 件以上なら「文書だけ」とする。新しい宣言は足さない
- 前提 3: リファクタリングを含む検査の印（`check-done/check`）は、リファクタリングを通していない差分を次のリファクタリングの範囲に残すための印であり、その役割は保つ。最後の検査がリファクタリングを含むかどうかで、範囲を数える起点の印が変わってよい
- 前提 4: `pace: auto` の開発ループのまとめ（最後の検査を置かない）は変えない
- 前提 5: 直列の計画（レーンが 1 本）でトリガーが立たずにスプリントの検査を通らなかった実装の Pull Request は、これまでどおり最後の検査の範囲に入る

## 対象範囲

含む:

- スプリントの終わりの最後の検査の範囲の決め方（`check-trigger.py eval --final` とその `prepare`、`supervise.py new close` が組む実行条件）
- 範囲が空か文書のファイルだけのとき、最後の検査で cross-review と cross-refactoring を回さず、開発版と本番も流さないこと
- 最後の検査の置き場所（まとめの中の順序）

含まない:

- develop にほかのレーンの変更が混ざること自体（#3119・#3121）
- まとめごとのレビューの方針（#3081）
- 工程の進行表が範囲を読む側（#3092）
- cross-review が収束しない問題（#3050）
- スプリントの途中の検査（`new sprint` の検査とコードレビューのステージ）の範囲の決め方
- 過去の検査の記録の書き換えと、origin の印のブランチを手で動かすこと

## 用語

| 用語 | 意味 |
| --- | --- |
| 最後の検査 | `supervise.py new close` が組む、スプリントの終わりの検査（計画名 `<スプリント>-final`）。スプリントの検査の後に入ったそのスプリントの差分を拾う |
| スプリントの検査 | `new sprint` が組む、スプリントの Pull Request を対象にした検査。マージの後に検査の印を進める |

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 最後の検査の実行条件は、通信せずに git の履歴と検査の記録だけで範囲を決める（今の `eval` と同じ）。並行するレーンの数が増えても、範囲の Pull Request の本数は S の Pull Request の本数を超えない |
| 運用・保守性 | 最後の検査が範囲をどう決めたか（起点のコミットと決め方、外した Pull Request の本数と理由）が判定の出力と検査の記録の `eval` の行に残る |
| 移行性 | 既存の検査の記録と origin の印のブランチをそのまま読む。移行の手順は要らない |
