# #3702 の詳細設計: 単位のファイル・単位の判定・単位のプランの組み立てと、設計のフェーズの工程の並び

設計文書 [issue-3702-design.md](issue-3702-design.md) の構成要素と決定を、ファイルと関数の粒度へ下ろした文書である。決定の番号・規則（U1〜U6・W1〜W2）は設計文書を指す。
パスは `plugins/ndf/` からの相対で書く（リポジトリの根からのパスは `/` で始めずにそのまま書く）。

依存の向きは一方向である。`units_decide` は標準ライブラリ（`graphlib`）と `inputs_decide.DesignResult` だけを読む。`units_files` は `units_decide`・`inputs_decide`（設計の結果の表の読み手）・`ndf.contracts`（スキーマと上限）・`ndf.core.route`（impl のテンプレートの描画）・`ndf.adapters.github`（課題の本文を承認と同じリポジトリから読む `criteria_of`。アダプターは呼び手が作って渡す）を読む。`cli.py` と `progress/units_invoke.py`・`progress/units_cli.py` は `units_files` を読み、`units_files` はどれも読まない。単位ごとの差し込み（題・本文・レビューの起動）は `progress` の `template_values` が組むので、それを使う手動の入口は `core/plan/cli.py` でなく `progress/units_cli.py` に置く。

**既存のファイルには呼び出しと登録だけを足す。** ファイルの行数の安全網（`src/ndf/checks/rules.json` の `structure.max_lines`。1,000 行を超えたファイルを `src/ndf/checks/structure.py` が指摘する）に対し、`adapters/github.py` は 1,000 行ちょうど、`progress/run.py` は 989 行、`progress/command.py` は 932 行、`progress/invoke.py` は 816 行である（2026-11-23 の main `8c79b73aa`）。新しい処理は新設のモジュールに置く: マージの照合は `adapters/github_merge.py`、工程の行を開き直す遷移は `progress/reopen.py`（`run.py` が呼ぶ）、`ndf progress units`・`ndf progress design` の入口は `progress/units_cli.py`（`command.py` は登録だけ）、単位を流す処理は `progress/units_invoke.py`（`invoke.py` は呼ぶだけ）。`core` から `domains` は読まない（設計の結果の表の読み手を `inputs_decide` に置き、`materials.collect` がそれを使う）。

### 単位のファイルの形（`review-units.schema.json`）

満たす決定: 2・3。満たす受け入れ条件: 2・3。

| キー | 形 | 規則 |
| --- | --- | --- |
| `version` | `1` | 定数 |
| `issues` | 整数の配列（1 以上） | 単位のファイルが扱う課題。ファイル名の番号の並びと一致する |
| `tasks[]` | `id`（`^T[0-9]+$`）・`title`・`issue`（整数。`issues` が 2 つ以上なら必須、1 つなら省けてその課題）・`files`（文字列の配列、1 以上。各値はリポジトリの根からの**正規形**のファイルのパス。スキーマの `pattern` は `^(?!/)(?!.*/$)(?!.*//)(?!(?:.*/)?\.{1,2}(?:/|$))[^*?\[\]\\]+$`＝先頭と末尾に `/` が無く、`//`・`.` と `..` の区切り・glob・`\\` を含まない。下の「パスの検査」も通す）・`lines`（整数 0 以上）・`criteria`（`^[0-9]+:[0-9]+$` の配列）・`after`（タスクの `id` の配列） | `additionalProperties: false` |
| `units[]` | `name`（1 文字以上）・`tasks`（タスクの `id` の配列、1 以上）・`after`（`{unit, reason}` の配列。`reason` は空白でない文字を含む）・任意の `actual_lines`（整数 0 以上） | `additionalProperties: false` |

**パスの検査**（`units_files.load`。スキーマで縛れない分）: 各値が `posixpath.normpath(値) == 値` であること、固定したコミット（下の「HEAD の照合」の「検査と組み立ての読み方」）で値が `tree`（ディレクトリ）でないこと、値か途中の要素がシンボリックリンク（モード `120000`）でないこと（リポジトリの外を指すシンボリックリンクを断る）を確かめ、当たれば `UnitsError`（パスとタスクの `id`）。まだ無いファイル（新設）は、親のディレクトリが無くても通す。正規形だけを通すので、U4 は文字列の一致で同じファイルを見分けられる。

タスクの所属の課題の正本は `tasks[].issue` である。単位の課題はその単位のタスクの `issue` の集まり（現れた順）、**代表の課題**は単位の最初のタスクの `issue` とする。スキーマで縛れない規則（重複・参照の実在・輪・覆い・重なり・行数・所属）は `units_decide.judge` が持つ。

### 単位の判定（`core/plan/units_decide.py`）

満たす決定: 3・4・5・6。満たす受け入れ条件: 2・5・7・8。ファイル・git・環境変数を読まない。

```python
class Task(NamedTuple): id: str; title: str; issue: int; files: tuple[str, ...]; lines: Optional[int]; criteria: tuple[str, ...]; after: tuple[str, ...]; whole: bool = False
class Edge(NamedTuple): unit: str; reason: str
class Unit(NamedTuple): name: str; tasks: tuple[str, ...]; after: tuple[Edge, ...]; actual_lines: Optional[int] = None
class Units(NamedTuple): issues: tuple[int, ...]; tasks: tuple[Task, ...]; units: tuple[Unit, ...]
class Limits(NamedTuple): target: int; max: int
class View(NamedTuple): name: str; order: int; merge: int; lines: Optional[int]; touches: tuple[str, ...]; issues: tuple[int, ...]; criteria: tuple[str, ...]; after: tuple[Edge, ...]
class Finding(NamedTuple): rule: str; unit: str; reason: str
class Proposal(NamedTuple): unit: str; units: tuple[Unit, ...]; rewired: tuple[Unit, ...]; note: Optional[str]; resplit: tuple[str, ...] = ()
class Judgement(NamedTuple): views: tuple[View, ...]; violations: tuple[Finding, ...]; warnings: tuple[Finding, ...]; proposals: tuple[Proposal, ...]
```

`Task.whole` は「課題のすべての受け入れ条件を持つ」の印で、単位のファイルからは作らない（スキーマにキーが無い）。`single` だけが真にする。`Proposal.resplit` は書き手に切り直しを求めるタスクの `id` で、空でなければ `units` も空にし、`note` に理由を書く（案を当てられない）。

#### 分け方の案の作り方（`split`）

1. 単位のタスクを、単位の中のタスクの依存の深さ（先に要るタスクの深さの最大 + 1。単位の外のタスクは数えない）で層に分ける
2. 同じ層の中で `files` の重なるタスクを連結成分に束ねる。成分の行数が `target` 以下なら 1 つの単位にする。超えるなら成分のタスクを 1 つずつの単位にし、同じファイルを触るタスクの単位どうしを `tasks[]` の並びで直列につなぐ（理由「同じファイルを触る」）。直列にした単位は案の中で実行順が分かれる
3. 重ならない成分は、`target` を超える手前まで同じ単位へ足し、超えたら次の単位を始める（`<元の名前> <番号>`）
4. 受け入れ条件を持たない案の単位（準備のタスクだけの単位）は、そのタスクを先に要る案の単位のうち `tasks[]` の並びで最初のものへ併せる（U2 を避ける）。併せた単位の行数が `target` を超えるか（タスクが 2 つ以上になるので、8 の「W1 はタスク 1 つの単位だけ」を満たさない。`max` を超える場合を含む）、先に要る案の単位が無いときは案を作らない: `units` を空にし、`resplit` にその準備のタスクと併せる先の単位のタスク、`note` に「条件を持たない T<n>（<行数> 行）と T<m> を併せると <行数> 行で目安 <target> を超える。T<n> に条件を割り当てて単独の単位にするか、T<n> を条件を持つタスクへ割って入れて 1 つのタスクにする」を返す（書き手の直し方はこの 2 つ。1 つのタスクにした単位は目安を超えても W1 のまま通り、`max` を超えれば U6 で切り直しを求められる）。例: 目安 400 行で、条件なしの準備 T1（250 行）と T1 に依存する条件ありの T2（200 行）は、併せると 450 行のタスク 2 つの単位になるので `resplit: ("T1", "T2")`。条件なしの T1（500 行）と T2（600 行）も同じく `resplit: ("T1", "T2")`
5. 各単位に、その単位のタスクが先に要るタスクを含む案の単位への依存を理由「タスクの依存の深さ」で付ける
6. 元の単位の `after` は、先に要る案の単位を持たない案の単位（最初の層）のすべてが引き継ぐ。元の単位を `after` で指していた後続の単位は、指す先を案の単位のうち後続を持たないもの（最後の層）のすべてに付け替え、`rewired` に返す
7. **グラフ全体で確かめ直す**: `apply` で元のグラフに当て、`orders` と U4 を**グラフ全体**で判定する。層の中を直列にすると案の単位の実行順が後ろへずれ、元の単位の外の単位（たとえば元の単位と同じファイルを触り、もともと実行順 2 にいた単位）と同じ実行順で重なることがある。当たった組（案の単位 P と外の単位 Q）ごとに次のどちらかにする。同じ実行順の 2 単位はどちらも相手を閉包に持たないので、依存を足しても輪にならない
   - **依存を直す**: Q が元の単位と同じ単位のファイルにあれば、Q を P の後に置く（Q の `after` に P、理由「同じファイルを触る」。Q を `rewired` に足す）。案はそのファイルの中で閉じるので書き手はそのまま写せる
   - **書き手に返す**: Q が別の単位のファイルにある（`merge` で接頭辞の違う単位）なら、単位の `after` はファイルをまたげないので直せない。案の単位を空にし、`resplit` に P と Q のタスク、`note` に「<P のファイル> の T<n> と <Q のファイル> の T<m> が同じファイルを触る。どちらかのファイルでタスクの触るファイルか実行順を直す」を返す

   足すたびに `orders` を取り直し、U4 の組が無くなるまで繰り返す（足す依存は組 1 つに 1 本で、組の数は有限なので止まる）。依存を足したことで、案の外の単位どうし（Q と、Q が後ろへずれて同じ実行順になった R）が新たに U4 に当たったときも同じ規則で直すか返す。R が Q と別の単位のファイルにあれば `resplit` に Q と R のタスクを載せて返す
8. **案を生成しない判定で検証する**: 終わった後のグラフを `check`（案を作らない）に通す。U1（4 の併せや 7 の依存で輪ができた）・U6（上限を超えるタスクを含む単位。1 つのタスクで `max` を超えるときは 1 の前に切り直しの指示を返して終える）を含め、違反が 1 つでも残れば、案を当てずに `units` を空にし、`resplit` に違反の単位のタスク、`note` に違反の行を返す。W1 はタスク 1 つの単位でだけ残ってよい（目安を超える 1 タスクの単位は分けようがない）。`split` は `judge` を呼ばず、`judge` は `split` の返りを再び `split` しないので、たとえば目安 400 行で条件を持つ 600 行の単独タスクの単位は、W1 のままで案を作らずに終わる（`judge` が案を作るのは U6 の単位と、W1 でタスクが 2 つ以上の単位だけ）。テストは、案を当てたグラフの `check` に違反が無いこと、併せで輪ができる入力と、依存を足して案の外の 2 単位が重なる入力で `resplit` が返ることを縛る

#### 単位のファイルの集め方（`collect`）

実装計画の Markdown と単位のファイルには、同じ名前の規則を当てる。**計画の名前**は `issues/issue-<番号の並び>-plan` で、番号の並びは `-` で区切った 1 つ以上の番号（`inputs_decide.PLAN_DOC = ^issues/issue-(\d+(?:-\d+)*)-plan(\.units\.json|\.md)$`）である。Markdown（`.md`）と単位のファイル（`.units.json`）は、計画の名前が同じものを対にする。

1. **扱いを先に決める**: `designed` で課題ごとの設計の結果の扱いを読み、計画のファイルを見る前に確定する。扱いが「マージする」「閉じる」の課題（以下、**単位を作らない課題**）は、計画の有無にかかわらず `skip` とする
2. `issues/` の下で `PLAN_DOC` に当たるファイルのうち、番号の並びのどれかがスプリントの課題の番号と一致するものを、計画の名前ごとに集める（統合の計画 `issue-10-11-plan.*` は #10 と #11 のどちらからも当たるが 1 回だけ読む）
3. 計画の名前ごとに、Markdown と単位のファイルを**双方向に**確かめる
   - 単位のファイルがあれば、同じ名前の Markdown が無ければ止める（`UnitsError`「単位のファイル `<パス>` に対の実装計画 `<名前>.md` が無い」）。Markdown に 2 つの区間の印（開始と終了の両方）がそろっていなければ止める（「`<名前>.md` に区間 <印> が無い」）。単位のファイルの `issues` がスプリントの課題の中にあり、名前の番号の並びと一致する
   - Markdown に `<!-- ndf:units:begin -->` の印があるのに、同じ名前の単位のファイルが無ければ止める（`UnitsError`「実装計画 `<パス>` があるのに単位のファイル `<名前>.units.json` が無い」）。`issue-10-11-plan.md` に印があり `issue-10-11-plan.units.json` が無いときも、#10・#11 のどちらも省いた扱いに落とさない
   - 印の無い Markdown だけの計画は、**スプリントの起点に既にあった**ときだけ旧い形とする: `git cat-file -e <remote>/<スプリントの PR の宛先>:<パス>`（宛先は `branch_strategy.pr_target("sprint")`。取得はしない）が通れば旧い形、通らなければ止める（「`<パス>` はこのスプリントで書いた実装計画なのに区間の印と単位のファイルが無い」）。新しく書いた計画の JSON と印の書き忘れを旧い形として通さない
   - 課題が 2 つの計画の名前に現れれば止める
   - **単位を作らない課題との矛盾**: 単位を作らない課題が計画の名前・単位のファイルの `issues`・`tasks[].issue` のどれかに現れれば止める（`UnitsError`「#<番号> は設計の結果で <扱い>（<設計文書のパス>）なのに、計画 `<パス>` にある」）。統合する課題（「マージする」）のタスクは統合先の課題（`issue` を統合先）として統合先の計画に書き、条件は `criteria` に `<統合する課題>:<番号>` で載せる（U2 がこれを許す）。統合する課題の旧い計画が残っていれば、それも止める（書き手が工程「計画」で消す）。止めるので、承認した扱いと矛盾する単位の PR は作られない
4. 単位を作らない課題を除き、どの計画の名前にも現れない課題は次の順で扱いを決める。**実装計画を省いてよいのは、工程「計画」が省くと決めて `plan_omitted` に載せた課題だけ**で、ファイルが無いことから省いたとは推さない

| 課題の状態 | 扱い |
| --- | --- |
| 設計の結果の表で扱いが「マージする」 | `skip`（単位を作らない。統合先の課題の単位が持つ）。統合先がスプリントの外か、統合先の扱いが「実装する」でなければ止める（`UnitsError`「#<番号> の統合先 #<統合先> がスプリントで実装されない（<文書のパス>）」）。**統合先が `single`（下の旧い形か `omitted`）でも止める**（`UnitsError`「#<番号> を #<統合先> へマージするので、#<統合先> の実装計画を省けない（統合する課題の条件を単位に割り当てる）」）: `single` の単位は `whole` で統合先の条件しか持たず、U2 の覆いも `whole` を対象外にするので、統合する課題の条件が承認資料・worker の指示・実装の確かめのどれにも入らないまま通ってしまうためである。統合する課題の条件は統合先の単位のファイルの `criteria` に `<統合する課題>:<番号>` で割り当て、U2 の覆いで確かめる。工程「計画」の `implementation-plan` も、統合する課題を持つ課題を `plan_omitted` に載せない（載せても `units check` がここで止める） |
| 設計の結果の表で扱いが「閉じる」 | `skip`（単位を作らない。実装の PR を持たずにスプリント PR で閉じる） |
| 設計の結果の表で扱いが「実装する」か、表に行が無い | 下の 3 行（計画の名前・`omitted`）で決める |
| 計画の名前に現れ、Markdown に印が無く単位のファイルも無く、スプリントの起点に既にあった（この変更より前に書いた実装計画） | `single`（今の振る舞いのまま）。`check` は `warnings` に「旧い形の実装計画で行数を確かめていない」を載せる |
| 計画の名前に現れず、`omitted` にある（工程「計画」が文書の役割の表の「省いてよい文書と条件」で省いた） | `single`。`check` の `metrics.omitted` に課題を載せ、承認資料に「実装計画を省いた課題（行数は確かめていない）」として出す |
| 計画の名前に現れず、`omitted` にも無い | 止める（`UnitsError`「#<番号> の実装計画が無く、省く判断も無い」）。作成必須の課題で Markdown と単位のファイルの両方を書き忘れても、行数を確かめずに進めない |

`plan_omitted` は工程「計画」の出力で、`implementation-plan` の worker が省くと決めた課題を報告に載せ、工程がそれを文脈へ書く（省かなかったスプリントでは空の配列）。新しく書く実装計画は worker が `render` で必ず印を置くので、印の有無で新旧を分けられる。

#### 設計の結果の表の読み手（`inputs_decide.design_results`）

`materials.collect.design_rows` は触るファイルしか返さず、`DESIGN_FILE` は名前の最初の番号しか拾わない。設計文書の名前の規則は `domains/loop/design_tests.py` の `DESIGN_FILE`（番号の並びをすべて拾う。下の `DESIGN_DOC` と同じ正規表現）にもある。`collect` が扱い・統合先を読み、統合文書の後ろの番号の行も読めるよう、読み手を次の形で `inputs_decide` に置き直す（Task 6）。

```python
class DesignResult(NamedTuple): issue: int; files: tuple[str, ...]; units: tuple[str, ...] = (); delegated: tuple[str, ...] = (); handling: str = "実装する"; into: Optional[int] = None
DESIGN_DOC = re.compile(r"^issues/issue-(\d+(?:-\d+)*)-design[^/]*\.md$")
def design_numbers(path: str) -> tuple[int, ...]  # DESIGN_DOC の番号の並び（当たらなければ空）
def design_results(text: str) -> list[DesignResult]  # 「設計の結果」の表の行ごと
```

- 行の型: 表の列は今の「課題・扱い・統合先・触るファイル」の順で、`row[0]` の `#<番号>` を `issue`、`row[1]` を `handling`（前後の空白を除いた値をそのまま持つ。値の検査はしない）、`row[2]` の `#<番号>` を `into`（「—」や空なら None）、`row[3]` を `files_cell` で `files` と `delegated` にする。列が 4 つに満たない行は飛ばす（今の `design_rows` と同じ）
- 扱いの値: 設計テンプレート（`skills/design/references/design-template.md` の「設計の結果の書き方」）と設計書の決定 2 のとおり `HANDLINGS = ("実装する", "マージする", "閉じる")` を `inputs_decide` に置く。`design_result_errors(result: DesignResult) -> list[str]` が 1 行の誤りを返す: 扱いが `HANDLINGS` に無い（空欄を含む）、「マージする」で `into` が None、「実装する」「閉じる」で `into` が None でない、`into` が自分の課題。`units_files.designed` は読んだ行ごとにこれを打ち、誤りがあれば `UnitsError`「<文書のパス> の #<番号> の行: <誤り>」で止める。`designed` は `units check --from-stage`（工程「ドキュメントレビュー」の ③）と `unit_plans` の両方が打つので、不正な行は設計承認の前に止まる。`materials.collect` は `design_results` の `files` だけを使い、検査を打たない（返りを今と変えない）
- 統合文書の探索: `design_numbers` が番号の並び全体を返すので、`issue-10-11-design.md` は #11 からも見つかり、その文書の #11 の行を読める
- 既存の材料収集: `materials.collect.design_files(root, number, files)` は `DESIGN_FILE.match` を `number in design_numbers(rel)` に、`design_rows(text, number)` を `[r.files for r in design_results(text) if r.issue == number]` の和に替える。返りの形（文書ごとの触るファイル）は変えない
- 設計のテストの読み手: `domains/loop/design_tests.py` は `DESIGN_FILE` を消し、`DESIGN_FILE.match(r)` と番号の取り出しを `design_numbers(r)` に替える（当たらなければ空）。振る舞いは変えず、既存のテスト `tests/domains/loop/test_loop_design_tests.py` が変えずに通る

#### 単位のプランの組み立て（`unit_plans`）

`UnitGiven` は工程が渡す値（スプリントの課題 `issues`・省いた課題 `omitted`・スプリントのブランチ `sprint`・リモート・状態の保存先・単位のキューの承認 `queue`（下の「単位のキューの承認の受け渡し」の `units_queue`）・テンプレートの差し込みの組み立て `values_of(unit, issue_text) -> 値`。`issue_text` は下の 1 で照合した代表の課題の題と本文）である。

1. `collect(repo, given.issues, given.omitted)` → 各ファイルを `load` → ファイルを持たない `single` の課題を足して `merge` → `designed` → `judge`。違反があれば何も書かない。ファイルをまたぐ U4 もここで当たる
   - **承認した入力との照合**（`judge` の前。`approved_inputs(repo, collected, queue) -> None`）: `given.queue`（照合済みの `units_queue`）の `issues`・`omitted` が `given.issues`・`given.omitted` と同じで、`collect` と `designed` が読んだ計画・単位のファイル・設計文書のパスの集合が `queue.files` のパスの集合と同じ（承認に無いファイルを読んだ・承認したファイルを読まなかった、のどちらも違い）で、**組み立てが実際に解析したバイト列**の blob の SHA が `queue.files` の値と同じかを確かめる。読み方は `units check` と同じ「固定したコミットから読む」（下の「検査と組み立ての読み方」）で、スプリントの作業場所の HEAD を最初に 1 回だけ SHA に固定し、`collect`・`load`・`designed` はそのコミットの内容だけを読む（作業ツリーのファイルを開かない）。照らす blob の SHA は、読んだときの `git cat-file --batch` の応答が返した値（＝解析したバイト列の SHA）で、読んだ後に `ls-tree` を打ち直して照らさない。違えば何も書かずに `UnitsError`（「承認した計画の入力と違う: 追加 <パス>／削除 <パス>／変更 <パス>」）で止める。**受け入れ条件も照らす**: `criteria_of(hub, criteria_targets(<merge した後のグラフ>, <single の課題>, designed))`（`hub` は照合済みの `queue.repo` と、`unit_plans` の中で 1 回だけ作った `github.client()` のアダプターで、この起動の読みと信頼の確かめのすべてが共用する。読む課題は `units check` と同じ `criteria_targets` の返りで、単位を持つ課題・その統合元・条件の課題の和を課題ごとに 1 回だけ読む）で読み直した課題ごとの `digest` が `queue.criteria` の値と同じかを確かめ、違えば同じく何も書かずに `UnitsError`（「#<番号> の受け入れ条件が承認の後に変わった」）。承認の後に本文の条件を並べ替えた・足した・言い換えた課題で、承認資料の `<課題>:<番号>` が別の条件を指したまま組み立てない。設計の同期の後にスプリントへ別の変更が取り込まれても、承認していない分け方・単位・課題で流さない。承認をやり直すには設計 PR を開き直す
   - **書き手の信頼を課題ごとに 1 回だけ確かめる**（照合の後、指示・プラン・本文のファイルを 1 つも書く前）: 読んだ課題ごとに `hub.trusts(<その課題の authored>)` を 1 回だけ打ち、`trusted: dict[int, bool]` に持つ。3 と 4 はこの値だけを使い、単位ごとに `trusts` を打ち直さない（同じ MEMBER・COLLABORATOR の課題を複数の単位が使っても、権限の読みは課題ごとに 1 回）。ここで、どれかの単位の条件の課題（タスクの `criteria` に現れる課題）を信用しなければ「#<番号> の書き手を信用しないので条件の文を指示に載せない」、どれかの単位の代表の課題を信用しなければ今の `FROM_UNTRUSTED_ISSUE` の理由で、どちらも何も書かずに `UnitsError` で止める。`trusts` が読めない（権限の読みの失敗）ときも何も書かずに止める。後続の単位で信頼に落ちて先行の単位のファイルだけが残ることはない
2. 単位に、スプリント全体で一意な連番 `seq` を、実行順 → マージの順（ファイルのパスの順 → `units[]` の並び → `single` の課題の番号の順）で振る（`numbering(units, order, files)`。`units check` の `unit` の項目も同じ関数で振る）。プランの名前・ブランチ・作業場所はどれも `<sprint>-u<seq>`、出力は `out/<sprint>-u<seq>.json`（別のファイルどうしで同じ名前にならない）
3. 単位ごとに指示のファイル `out/<sprint>-u<seq>.unit.json` を書く: 単位の名前・代表の課題・単位の課題・担当のタスク（`id`・`title`・`files`・`criteria`）・実装計画の文書のパスと、単位の条件の文 `criteria_text`（`[["<課題>:<番号>", 文], …]`。1 で指紋を照合した `criteria_of` の返りの `items` から取る）。`single` の単位には書かない（担当のタスクを持たないため。下の「worker への単位の指示」）。条件の課題の書き手の信頼は 1 の `trusted` で確かめ済みで、信用しない課題があれば 1 で止まっているので、ここでは `trusts` を打たない（今の `FROM_UNTRUSTED_ISSUE` と同じく、信用しない本文を worker の入力にしない）
4. 差し込み: `issue` は代表の課題、`acceptance` は**単位の条件（タスクの `criteria` の和）の課題の番号**から組む: 条件の `<課題>:<番号>` の課題ごと（現れた順）に `--issue <課題>` と、その課題の条件ごとに `--criteria <課題>:<番号>`。タスクの所属の課題（`tasks[].issue`）からは組まないので、統合先のタスクが持つ統合する課題の条件（`3673:2` を持つ `issue: 3672` のタスク）も `--issue 3673 --criteria 3673:2` として確かめに入り、確認の記録が無ければ `ndf loop acceptance` が止まる（承認資料に載った条件を実装の確かめから落とさない）。条件を持たない所属の課題には `--issue` を付けない（全部の条件を照らさないため）。`single` の単位は `--issue <課題>` だけ（課題のすべての条件）。どちらも `--issue <課題>` ごとに `--criteria-digest <課題>=<queue.criteria の値>` を足し、全体の先頭に `--repo <queue.repo>` と `--remote <given.remote>`（承認の照合と組み立てに使ったリモート。`units.json` の `remote` と同じ値）を 1 つずつ足して、実装の確かめと worker の記録が承認したリポジトリの承認した条件の中身と同じ本文を照らすことを縛る（下の「受け入れ条件の出典」）。`unit_file` は 3 の指示のファイル（`single` は空の文字列）。題・本文は**1 で指紋を照合した読みの返り**（代表の課題の `criteria_of` の `title`・`authored.body`。信頼は 1 の `trusted` で確かめ済み）を `values_of(unit, issue_text)` へ渡して組む（信用しない代表の課題は 1 で何も書かずに止まるので、ここに None は来ない）。単位の経路は `ISSUE_BODY_FILE`・`ISSUE_TITLE_FILE` のキャッシュを読まず、本文はプランと同じ計画の組として `out/<sprint>-u<seq>.issue-<番号>.md` へ書く（組み立ては `units.json` があれば打たないので、再開でもプランは変わらない）。残りの差し込み（`review`・`test_command` など）は `given.values_of` が組む（下の工程の流し方）
5. プランの最上位へ `touches`（単位の触るファイル。空なら書かない）を足す。`needs` は**同じ実行順のプランだけ**を指す（同じ実行順には依存が無いので、実際には書かない）。前の実行順への依存は、工程が前の実行順のマージを確かめてから次のキューを打つことで守る（今の `ndf plan queue` は起動ごとに済んだプランを空から数え、別の起動で済んだ `needs` を解けないため）。単位の依存は `items[].after` と指示のファイルに残す
6. 返りは実行順・マージの順に並べた `UnitPlan(path, unit_file, name, order, merge, branch)`

#### 受け入れ条件の出典（`criteria_of` と `ndf loop acceptance check`）

条件の番号を付ける処理（単位のファイルの `criteria` を検査する `units check` と、`acceptance` を組む `unit_plans`）と、実装で確かめる処理（`ndf loop acceptance check`）は、**同じリポジトリ・同じ出典・同じ読み手・同じ中身**を使う。

- **出典は課題の本文だけ**: 今の `loop acceptance check` は課題の本文の `## 受け入れ条件` から番号を数え、確認の記録も本文に書く。`criteria_of` もこれに合わせて本文だけを読み、要求仕様から番号を採らない。要求仕様にだけ条件を足した課題は、`units check` の段階で U2（「#<課題>:<番号> は課題に無い」）で止まり、承認まで進まない（実装の確かめで初めて止まらない）。要求仕様に条件を足すときは、工程「要求と受け入れ条件」の今の規則どおり本文を直す（本文が正で、要求仕様はその写し）
- **同じリポジトリから同じ読み手で読む**: 本文の読みはどれも既存の GitHub のアダプター（`github.GitHub(<repo>, github.client())` の REST の読み。今の `acceptance.read_body`・`invoke.issue_text` と同じ）で、`<repo>` は承認の記録の `repo`（上の「操作先のリポジトリ」）に揃える。`units check` は作業場所の `<remote>` から決めた値（`metrics.repo`）、`unit_plans` は照合済みの `queue.repo`、`loop acceptance check` と worker の `loop acceptance record` は `unit_plans` の 4 が渡す `--repo <queue.repo>` で作り、`--remote <given.remote>` のリモートと照らしてから読み書きする（既定のリモートに戻らない）。`gh issue view` を起動せず、`GH_REPO` や `gh repo set-default`・フォークの upstream の別のリモートに操作先を委ねないので、同じ番号の別の課題の条件を承認資料に載せたり、承認と実装で別の本文の指紋を比べたりしない
- **承認に結び付ける**: `units check` は `metrics.criteria`（課題ごとの `{"digest", "items": [[番号, 文], …]}`。`digest` は `items` の指紋）を出し、`design target` が課題ごとの `digest` を承認の記録の `criteria` に写す（`units-check.json` 全体は `units_check_sha256` の対象でもある）。承認資料は単位の表の条件の列に、番号と `items` の文を並べて載せる（承認者が番号でなく中身を見る）。**`whole` の単位（`single`）は課題の全条件に展開する**: `units check` の `unit` の項目の `criteria` は、`whole` のタスクを持つ単位では、その課題の `metrics.criteria.<課題>.items` のすべての番号を `<課題>:<番号>` で並べる（実装の確かめが `--issue <課題>` で照らす条件と同じ集合）。承認資料はほかの単位と同じくこの項目から条件の欄を作るので、計画を省いた課題の行も空欄にならず、実装で確かめる条件の文を承認者が見られる。条件を 1 つも持たない課題は「受け入れ条件なし」と書く。`units_queue` は記録の `criteria` を写し、`unit_plans` の 1 が組み立ての前に照らす（上の「承認した入力との照合」）
- **実装の確かめで同じ中身を照らす**（`domains/loop/acceptance.py` を変える。Task 8）: `ndf loop acceptance check` と `ndf loop acceptance record` の両方に `--repo <所有者>/<名前>`・`--remote <リモート名>`（どちらも任意）と `--criteria-digest <課題>=<SHA-256>`（`check` は繰り返し、`record` は `--issue` の課題に 1 つ。任意）を足す。3 つは組でだけ受け、どれかだけなら何も読まずに `invalid`。`--repo` を渡したときは、本文を読む前に作業場所（`--cwd`）の `Git.remote_repo(<--remote>)`（引数を省いた既定のリモートでなく、承認と組み立てに使ったリモートを明示して読む）と大文字と小文字を区別せずに比べ、違えば何も読まず何も書かずに `stopped`（`invalid`、「承認したリポジトリ <repo> と作業場所のリモート <remote> の操作先 <repo> が違う」）を返す。同じなら本文の読みも `record` の書き込みも `--repo` で作ったアダプターだけで行い、`Git.remote_repo()` の既定のリモートに戻らない（今の `acceptance._hub(cwd)` は読み・書きのたびに既定のリモートで作るので、`--repo` を渡した呼び出しでは使わず、起動の中で 1 つだけ作ったアダプターを読み・書き・当て直しで共用する）。`units plans --remote R` で R と既定のリモートが別の GitHub のリポジトリでも、承認したリポジトリと R が同じなら `check` は止まらず、`record` は別のリポジトリの同じ番号の課題を書き換えない。渡された課題は、本文を読んだ後に `inputs_decide.criteria_digest(body)` を取り、値が違えば記録を照らさずに `stopped`（`invalid`、「#<課題> の受け入れ条件が承認の後に変わった（承認 <値>・今 <値>）」）を返す。`--criteria-digest` に `--issue` に無い課題を渡せば `invalid`。渡さない従来の呼び出しは今のまま。番号の読み手は `acceptance_decide.criteria` がそのまま `inputs_decide.criteria` を使う（今と同じ）。`unit_plans` の 4 の `acceptance` がこの引数を必ず付けるので、組み立ての後・確かめの前に本文の条件が変わっても、承認した `<課題>:<番号>` と別の条件の記録で通らない。`ndf plan units prompt` も同じ `acceptance` の要素を受け取り、照らす条件の一覧には使わない `--repo`・`--remote`・`--criteria-digest` から、「担当の範囲」の節に課題ごとの記録のコマンド `ndf loop acceptance record --issue <課題> --repo <repo> --remote <remote> --criteria-digest <課題>=<値> --pre-merge …` を書く（worker はこの形で記録する。下の「記録を条件の版に結び付ける」）
- **記録を条件の版に結び付ける**（`domains/loop/acceptance_decide.py`。Task 8）: 今の確認の記録は条件の番号だけに結び付くので、本文の条件を並べ替えた・同じ番号の文を置き換えた後に設計を承認し直すと、新しい指紋は一致し、旧い条件に書いた同じ番号の記録で新しい条件が通ってしまう。そこで確認の表を「条件・区分・手段・条件の指紋」の 4 列にし、`record` は書く行ごとに、その番号の条件の文の指紋 `inputs_decide.criterion_digest(text)`（文の UTF-8 の SHA-256 の先頭 16 桁）を 4 列目に書く。**指紋は worker が確かめた版にだけ付ける**: 書いたときの本文から指紋を取るだけでは、worker が承認済みの旧い条件を確かめた後・`record` を打つ前に本文の条件が変わると、旧い条件を確かめた結果に新しい条件の指紋が付き、設計を承認し直すと確かめていない新しい条件がその記録で通る。そこで `record` は worker が確かめた条件の版 `--criteria-digest <課題>=<値>`（`unit_plans` の 4 が `acceptance` に載せた `queue.criteria` の値で、worker が読んだ指示のファイルの `criteria_text` と同じ版。プロンプトの記録のコマンドがそのまま渡す）を受け、**ロックの中の初回の読み**と、**`_reapply` の当て直しで読み直した本文のそれぞれ**（書く前の毎回）で `inputs_decide.criteria_digest(body)` と照らす。違えば、その時点から先を書かずに `stopped`（`invalid`、「#<課題> の受け入れ条件が確かめた版と違う（確かめた <値>・今 <値>）」）を返す（初回の読みで違えば何も書かない。当て直しの途中で違えば、それより前に書いた行は確かめた版の文の指紋を持つので、`check` は変わった条件をその記録で数えない）。4 列目の指紋は、照らして一致した本文（＝確かめた版）の文から取る。`--criteria-digest` を渡さない `record` は 4 列目を空にして書く（版の分からない記録に今の本文の指紋を付けない）ので、`check --criteria-digest` はその記録を数えず、単位の経路で worker が引数を省いても旧い条件の確かめで新しい条件を通さない。`read_checks` は 4 列目を `Check.digest` として読む（3 列の旧い表は `digest` が空）。`check` は `--criteria-digest` を渡された課題で、記録の `digest` が今の本文のその番号の文の `criterion_digest` と同じ記録だけを記録ありと数え、違う記録は `incomplete` の欠け（`gaps` の `reason`「記録の後に条件の文が変わった（#<課題>:<番号>）」）、空の記録は同じく欠け（「記録に確かめた条件の版が無い（#<課題>:<番号>）」）にする。worker は渡された版の条件で確かめ直し、`--criteria-digest` 付きで `record` を打ち直す（行を置き換えるので指紋も確かめた版の文になる）。本文の条件そのものが承認の後に変わっていれば、`record` も `check` も `invalid` で止まり、設計の承認をやり直す（新しい版の条件は、新しい承認の `queue.criteria` を受け取った worker が確かめるまで記録されない）。`--criteria-digest` を渡さない従来の呼び出しは 4 列目を見ない
- **回数**（工程全体。N は `criteria_targets` の返りの課題の数＝単位を持つ課題・その統合元・条件の課題の和。CLI の起動は下の認証の 1 回のほかに足さない）: 本文はどれもアダプターの REST の読み（`GET /repos/{repo}/issues/{n}` を課題ごとに 1 回。`gh` を起動しない）で読む。① 工程「ドキュメントレビュー」の `units check`（③）が N 回（新設。`docs-review` を打ち直せばその回ごとに N 回）、② 工程「実装」の `unit_plans` の 1 が N 回（組み立ては `units.json` が無いときの 1 回だけなので、再開では読まない）。② の読みは題・本文の差し込みにも共用するので、今の工程が代表の課題について打つ `_issue_values` の初回の読み（キャッシュが無いときの 1 回）は単位の経路では打たず、②で足すのは N − 1 回（キャッシュがあった今の工程と比べれば N 回）。書き手の信頼の確かめ（`trusts`）は `unit_plans` だけが、1 の照合の後に読んだ課題ごとに 1 回だけ打つ（単位の数によらない。OWNER の書き手なら API を呼ばず、MEMBER・COLLABORATOR なら権限の読み 1 回。今の `_issue_values` は代表の課題だけを確かめる）。③ `loop acceptance check` は今の読みの中で指紋を取り、`--repo` の照合は `--remote` のリモートの URL を読むだけ（API を呼ばない）なので回数を足さない。`record` も同じロックの中の今の読みから版を照らして文の指紋を取るので足さない。
  - **認証の取得と CLI の起動**: `github.client()` は作るたびに `github.token()` を打ち、`GH_TOKEN`・`GITHUB_TOKEN` のどちらかがあれば CLI を起動せず、どちらも無ければ `gh auth token` を 1 回起動する。そこで**クライアントはコマンドの起動ごとに 1 つだけ作って共用する**: `units check` は起動の中で 1 回だけ `github.client()` を作り、`criteria_of` のすべての読みに同じ `hub` を渡す。`unit_plans` も 1 回だけ作り、1 の `criteria_of`・信頼の確かめ・4 の差し込みのすべてが同じ `hub` を使う（単位ごと・課題ごとに作り直さない）。`loop acceptance check`・`record` は `--repo` を渡したとき起動の中で 1 回だけ作り、読み・書き・当て直しで共用する（`--repo` の無い従来の呼び出しは今のまま `_hub(cwd)`）。認証方式ごとの CLI の起動は次のとおり: 環境変数の token では、`units check`・`unit_plans` とも 0 回（今と同じ）。`gh auth login` だけの環境では、`units check` が起動ごとに `gh auth token` 1 回（新設。`docs-review` を打ち直せばその回ごとに 1 回）、`unit_plans` が組み立てごとに 1 回（再開では打たない）で、代わりに単位の経路では打たない `_issue_values` の `issue_text` が作っていた代表の課題ごとの 1 回（キャッシュが無いとき）が消える。`loop acceptance check`・`record` は `--repo` を渡すと起動ごとに 1 回（今は読み・書きのたびに `_hub` を作るので、当て直しのある `record` では今より減る）。`--remote` の照合の `git` の起動は起動ごとに 1 回で、今の `_hub` が読み・書きのたびに打つ `remote_repo()` の分より増えない
  - 合計で、今より API の呼び出しが課題の読みで `2N − 1`、信頼の確かめで代表でない課題の権限の読みの分だけ増え、CLI の起動は `gh auth login` の環境で `units check` の起動ごとの `gh auth token` 1 回だけ増える（`unit_plans` の 1 回は消える `_issue_values` の分と差し引きで増えない）。偽の GitHub で `units check`・`unit_plans` の課題の読みの回数と `trusts` の回数（2 単位が同じ MEMBER の課題を使っても権限の読み 1 回）を縛り、`unit_plans` の後の差し込みで `issue_text` を呼ばないことと、`github.token` の呼び出しが `units check`・`unit_plans` の起動ごとに 1 回であることをテストで縛る

#### 流し方の記録（`units.json`）

`unit_plans` は、プランと指示のファイルに加えて `out/units.json` を書く。工程（`_call_units`）と手動（`ndf progress units run`）はどちらもこのファイルだけから流し方を復元し、組み立ての後に起動が分かれても同じ計画で流す。

**計画と状態は 1 組**: `units.json`・プラン・指示のファイル（計画）と、`orders.<k>.base_sha`・`work_dir/units/<seq>.json`（状態）は、同じ組み立てから生まれた 1 組としてだけ使う。

- **初回だけ組み立てる**: `_call_units` は `out/units.json` が無いときだけ `unit_plans` を打つ。`unit_plans` はプランと指示のファイルを書いた後、最後に `units.json` を一時ファイルからの `os.replace` で書く（`units.json` があることが組み立てを終えた印。途中で止まった組み立ては、次の起動で `out` を消してからやり直す）
- **再開は保存した組を読む**: `units.json` があれば `unit_plans` を打たず、`units.json` とそこから指すプラン・指示のファイルを読み、`orders` と `<seq>.json` をそのまま続きに使う（`base_sha` を初期化しない）。`units.json` には組み立てに使った入力の指紋 `source`（`issues`・`omitted` と、読んだ計画・単位のファイル・設計文書のパスごとの、スプリントの HEAD での blob の SHA）を書き、再開のたびに今のスプリントの作業場所で同じ指紋を取り直して照らす
- **再計画で状態を引き継ぐ条件**: 指紋が違う（承認をやり直して計画が変わった）とき、状態が 1 つも無い（どの `orders.<k>.base_sha` も null で、`work_dir/units/` に記録が無い）ならそのまま `out` を消して組み立て直す。状態が 1 つでもあれば引き継がずに `precondition`（「単位の計画が変わったが、実行の記録 <パス> がある」）で止め、人に返す。`<seq>.json` は再採番した別の単位に当てない（`seq` は計画の組の中でだけ意味を持つ）

- `max` は `min(queue.parallel, 組み立ての時点の parallel_cap)`。`queue.parallel` は承認資料に載せた同時に流す本数の上限（`units-check.json` の `metrics.parallel` を承認の記録の `parallel` に写した値。下の「単位のキューの承認の受け渡し」）で、マシンの設定（`ndf relay cap`）や実行環境の `NDF_RELAY_MAX_NAMED` を承認の後に上げても、承認した本数を超えて流さない（下げたときは小さい方に従う）。`units run` の再開も `units.json` の `max` だけを使い、打ち直すたびに上限を取り直さない。`merge_method` は**承認資料に載せた方式**で、照合済みの承認の `units_method`（`units_queue.method`。下の「単位のキューの承認の受け渡し」）をそのまま写す。組み立ては常に照合済みの承認から行うので、`declared_merge_methods` を打たない（方式の読みの API を呼ばない）。単位のマージに `--method` で渡し、打ち直しでも `units.json` の同じ値を使う（組み立て直さない限り再計算しない）。承認の後に宣言・ruleset・キューの方式が変わって、この方式が宛先で使えなくなったときは、`ci merge` の照合（③ の `_method_refusal`、② のキューの方式の違い）が要求を送らずに断り、単位は `blocked` で止まる（下の工程の流し方の 6）。承認と違う方式へ替えてマージしない。`queue` は照合済みの承認から決めた単位のキューの承認（下の「単位のキューの承認の受け渡し」。単位のマージに `--queue-approved` を付けるかの唯一の根拠）。`orders.<k>.base_sha` は実行順 k を始めたときに固定した SHA（下の 2。始める前は null）

2. **作業場所**: 実行順 k を始めるときに `git fetch <remote> <sprint>` を**1 回だけ**打ち、`git rev-parse <remote>/<sprint>` の SHA を `units.json` の `orders.<k>.base_sha` に書いて固定する（既に書いてあれば取得も書き換えもしない。再開で起点が動かない）。その実行順の各単位について `ndf worktree create <sprint>-u<seq> --from <base_sha> --no-fetch --new-branch` で、前の実行順のマージをすべて含む同じコミットから単位専用のブランチと作業場所を用意する。今の `ndf worktree create` は `--from` があっても既定のリモートを取得するので、`--no-fetch`（取得を飛ばし、`--from` の SHA が手元に無ければ `precondition` で止める）を足す。また今の `create` は同名のローカルのブランチ（`refs/heads/<名前>`）かリモート追跡のブランチ（`refs/remotes/<remote>/<名前>`）があるとそれをチェックアウトし、`--from` を使わない。そこで `--new-branch`（どちらかの同名のブランチがある、または worktree の保存先が既にある・同名のブランチがほかの worktree に登録済みなら、何も作らずに `precondition`（「<名前> が既にある。起点 <SHA> から作れない」））を足し、単位の作業場所は常にこれで作る。取得は実行順ごとに 1 回で、単位の本数に比例して増えない。単位の PR の宛先はスプリントのブランチ（差し込み `base`）
   - **作る記録（2 段）**: `work_dir/units/<seq>.worktree.json` に `{"branch", "path", "base_sha", "source", "claim", "state"}`（`source` は `units.json` の `source` の SHA-256。今の計画の組の印。`claim` は記録を初めて書くときに `secrets.token_hex(16)` で作るこの作成の印で、書き直しても変えない）を、どちらの段も一時ファイルからの `os.replace` で書く。**作る前に** `state: "creating"` で書いてから `ndf worktree create` を打ち、成功したら `state: "created"` に書き換える。**作成先の確保と記録を `claim` で結ぶ**: `ndf worktree create` に `--claim <印>` を足し、`--new-branch` の作成を `git worktree add --lock --reason "ndf-claim <印>"` で行う（worktree の登録と同じ git の操作でロックの理由に印が付くので、作られた worktree には必ずこの実行の印が付き、作成の前からあった worktree には付かない）。名前・パス・起点の SHA は前の計画・手の作業の残りと偶然一致し得るので、持ち主の判定にはこの印だけを使う。`created` を書いた後に `git worktree unlock <path>` でロックを外す（外す前に止まれば、下の `created` の再開で外す）。どちらの段の記録も上の「計画と状態は 1 組」の状態に数える（再計画で引き継ぐ条件の「記録」に入る）
   - **初回**: その単位の記録が無ければ、`creating` を書いてから上の `--new-branch` で作る。同名のブランチ・worktree が残っていれば（前の計画・手の作業の残り）`ndf worktree create` が何も作らずに止まり、工程は `creating` の記録を消してから人に返す（残りを流用しない）。`creating` を書いた直後から記録を消すまでの間に止まっても、残っている worktree にはこの記録の `claim` の印が無いので、再開の (b) は引き取らずに (c) で止まる
   - **再開（`creating`）**: 作成の途中か、作成と `created` の書き込みの間で止まった。記録の `source`・`base_sha` が今の値（下の `created` と同じ照合）と同じことを確かめてから、ローカルの git で次の 3 通りに分ける。(a) 記録の `branch` のブランチも `path` も無い（作る前に止まった）なら、`--new-branch` で作って `created` にする。(a) で作るときも記録の `claim` を同じ値のまま `--claim` に渡す。(b) `git worktree list --porcelain` に記録の `path` が記録の `branch` で登録され、その項目の `locked` の理由が `ndf-claim <記録の claim>` と一致し、`git rev-parse <branch>` が記録の `base_sha` と一致する（この実行が作った直後でコミットが無い）なら、作り直さずに `created` に書き換えてからロックを外して確定する。ロックが無い・理由の印が違う worktree は、ブランチ・パス・SHA が記録と同じでも引き取らない。(c) それ以外（ブランチだけある・印の無いか違う worktree・別の起点・別のパス・コミットがある）は `precondition`（「単位 <seq> の作りかけの作業場所が記録と違う: <違い>」）で止め、消さずに人に返す
   - **再開（`created`）**: 作り直さず、再利用の前に次をすべて確かめる: 記録の `source` が今の `units.json` の `source` の SHA-256 と同じ、記録の `base_sha` が `orders.<k>.base_sha` と同じ、`git worktree list --porcelain` に記録の `path` が記録の `branch` で登録されている、`git merge-base --is-ancestor <base_sha> <branch>` が真。確かめた後、その項目にまだ `ndf-claim <記録の claim>` のロックが残っていれば（`created` の書き込みとロックの解除の間で止まった）外す。どれかが違えば `precondition`（「単位 <seq> の作業場所が記録と違う: <違い>」）で止め、作り直さない。どちらの再開もローカルの git だけを読み、API を呼ばない
   - 関数は `unit_worktree(main_dir, seq, branch, base_sha, source, work_dir) -> Path`（`progress/units_invoke.py`。新設。初回と 2 つの再開を分ける）
3. **キュー**: `ndf plan queue <その実行順のプランのパス>... --max <units.json の max> --resume` を打つ（`--resume` は常に付ける。初回はキューの記録が無いので全部流し、打ち直しでは完了したプランを流さずに続ける。今の `ndf plan queue` は `--resume` が無いと完了済みの記録を使わない）。supervisor が手で流すときも `ndf progress units run` が同じ `units.json` の `max` を使う
4. **マージの前の記録**: キューが `ok` で終われば、その実行順の単位ごとに、**最初のマージの要求より前に** `work_dir/units/<seq>.json` へ、**そのプランがレビューした組**を書く。組は単位のプランの中で決まった値だけから取り、キューの終わった後に GitHub を読み直さない（先に終わった単位の PR が残りの単位を待つ間に閉じて開き直された・宛先を変えて戻された・同じブランチと HEAD の別の PR に差し替えられた場合に、後から読んだ値で照合を通さないため。`gh` の既定のリポジトリの解決にも頼らない）
   - **PR の番号** `pr`: キューの結果（`queue.json`）のそのプランの `prs`（プランの `pr` ステップが作って返した番号。`queue_decide.Outcome.prs`）。ちょうど 1 つでなければ記録を書かずに `precondition`（「<プラン> のキューの結果に PR の番号が 1 つだけ無い」）。さらにそのプランの状態ディレクトリの `review-target`（上の 1 のとおり、レビューを実行した側が終了コード 0 で終わったときに書いた、実際にレビューした組）を読み、期待した組（`repo` が `units.json` の `repo`、`pr` がこの番号）と同じことを確かめる。無い・読めない・違えば記録を書かずに `precondition`（「<プラン> でレビューした PR の組 <repo>#<番号> がマージする組と違う」）で、マージへ渡さない。API を呼ばない
   - **宛先** `base`: スプリントのブランチ（そのプランの `pr` ステップに渡した差し込み `base` と同じ値）
   - **レビュー済みの HEAD** `head`: そのプランの状態ディレクトリの `reviewed-head`
   - **レビューの開始時刻** `since`: そのプランの状態ディレクトリの `review-started`（ISO 8601、UTC）。書くのはシェルでなく cross-review で、単位の包み（上の 1）が `review` のステップの起動にだけ `--started-out {state_dir}/review-started` を渡す。cross-review の `run` は `--started-out` を `--reviewed-out` と同じく始めに消す。**ラウンドの記録の `started` は、そのラウンドが読んだ差分の起点のレビューの開始時刻**で、`_prepare_round` が範囲を決めたときに次のとおり書く。(i) 範囲が `FULL`（最初のラウンド・`descended` で全差分へ戻した・`every_section` の未読のセクション・`--no-reuse` の起動の最初のラウンドを含む。PR の全差分 `<--base>...HEAD` を読む）なら、そのラウンドの差分を作る前の時刻。(ii) 範囲が `SINCE`（`state_scope` が前のラウンドの head を起点に選び、その head からの差分だけを読む）なら時刻を取り直さず、**起点にしたラウンド**（`state_scope` が head を選んだ、相手役の全員が読めた最後のラウンド。その起動の前の起動のラウンドでもよい）の `started` を引き継ぐ（起点のラウンドに `started` が無ければ、この変更より前の状態ファイルなので `started` を書かない）。`SINCE` のラウンドが読むのは起点の head からの変更だけで、それより前の変更は起点のラウンドの時点までに読んだものなので、PR の全体を読んだ時点（`since`）は起点のレビューの開始のままである。`--started-out` には、終わったときに相手役の全員が読めた最後のラウンド（`reviewed_head` を出したラウンド。**前回の `converged` を返した起動**（`_reusable`）では返したラウンド）の `started` を書き、無ければ何も書かない。たとえば修正を push したところで中断し、その間に PR が再オープンされた後に `--from <プラン>=review` で再開すると、再開の起動は修正の差分（`SINCE`）だけを読んで収束するが、その `started` は起点にした中断前のレビューの開始時刻なので、再オープンは `--since` より後の事象として `ci merge` の照合に当たる。収束の後・キューの完了の前に中断して同じ HEAD の収束が再利用されたときも同じく元の開始時刻が残る。開始時刻を新しくするのは PR の全差分を読み直したラウンド（`--no-reuse` の最初のラウンドを含む）だけである。ローカルの書き込みだけで API を呼ばない。無い・読めなければ記録を書かずに `precondition`
   - 状態 `queued`

   `ci merge --pr` には `pr`、`--base` には `base`、`--reviewed` には `head`、`--since` には `since` を渡す（5）。`since` がレビューの開始なので、レビューの間とキューの残りを待つ間の再オープン・宛先の変更はどれも `--since` より後の事象になる。差し替えで別の PR が開かれても、照合する番号はレビューした PR のままなので、その PR が閉じていれば `ci merge` が `refused`（`CLOSED`）で断る。記録を書けなければマージを要求しない。この組を作る関数は `unit_record(plan_state_dir: Path, outcome: Outcome, base: str, repo: str) -> dict`（`progress/units_invoke.py`。読めない・番号が 1 つでない・`review-target` の組が違えば `UnitsError`（`precondition`））
5. **マージ**: 記録のある単位をマージの順に、**単位の作業場所を cwd にして** `ndf ci merge --repo <units.json の repo> --branch <単位のブランチ> --pr <記録の番号> --base <スプリントのブランチ> --reviewed <記録の HEAD> --method <units.json の merge_method> --since <記録の since> --receipt <work_dir/units/<seq>.receipt.json>`（`units.json` の `queue.approved` が真で `queue.sprint` が `sprint` と同じときだけ `--queue-approved` を足す）を打つ。返りで記録の状態を書き換える（`ok` は `merged`、マージキューへ入れた・入っている `ci_pending` は `queued` のまま）。判定は下の「マージの対象の照合と再開」が `ci merge` の中で持つので、工程の側で `gh pr view` を打ち直さない
6. **再開と再レビュー**: 記録の状態は `queued`（マージ待ち）・`merged`・`stale`（レビューからやり直す）・`blocked`（人に返す）の 4 つで、遷移は次のとおり。打ち直しは常にこの表から続ける。`stale` の記録は理由 `reason`（`refused` か `base_conflict`）・開始点 `start`（`review` か `conflict-check`）・再レビューの回数 `restarts` を持ち、起動をまたいで残る

   | 今の状態と `ci merge` の返り | 次の状態と工程の振る舞い |
   | --- | --- |
   | 記録なし（4 の前に止まった） | 3 のキュー（`--resume`）の結果から始める |
   | `merged` | API を呼ばずに飛ばす |
   | `queued` → `ok` | `merged` |
   | `queued` → `ci_pending` | `queued` のまま。次の実行順を始めずに `ci_pending` で返す |
   | `queued` → `refused`（`OPEN` でキューにいない PR の、HEAD がレビュー済みと違う・承認後の再オープン）か `base_conflict`（キューにいない） | `restarts` が 0 なら `stale`（`reason`・`start`・`ci merge` の返りの `instance` を足し、`restarts` を 1 にする）を**先に書いてから**、同じ起動で下の `stale` の行を行う。`restarts` が 1 以上なら `blocked`（再レビューの後もまた断られた） |
   | `stale`（同じ起動で書いた直後か、前の起動で再レビューが中断・失敗した） | その単位のプランだけを `ndf plan queue <そのプラン> --resume --from <プラン>=<記録の start>` で打つ。開始点は `refused` なら `review`（今の HEAD をレビューし直す）、`base_conflict` なら `conflict-check`（マージ先の取り込みからレビューまで）。`--from` を付けるので、キューの記録に残る完了済みの古いレビューを使わない（3 の通常のキューの `--resume` では `stale` の単位のプランを渡さない）。**過去の成功結果を再利用しない**: `--from` だけでは、既定の cross-review が同じ状態ディレクトリで HEAD と比較基点が同じなら前回の `converged` を返し（`domains/crossreview/drive.py` の `_reusable`）、実際のレビューなしに `reviewed-head` が書き直される。そこでキューを打つ前に、そのプランの状態ディレクトリへ印 `review-fresh` を書く（記録を `stale` にした直後、同じ起動で。既にあれば書き直さない）。印の扱い（`--no-reuse` を足すこと・終了コード 0 のときだけ印を消すこと）は上の 1 の単位の包みが持ち、共有の `impl.json` の `review` のステップは変えない（`NDF_REVIEW_STEP=review` を置くだけで `exec` のまま）。cross-review に `--no-reuse`（`drive` が `_reusable` を見ずにラウンドを回す。状態ディレクトリの既存のラウンドと履歴は残し、次の番号から続ける）を足す。**`--no-reuse` の起動の最初のラウンドは PR の全差分を渡す**: `_reusable` を飛ばすだけでは、`_prepare_round` の `state_scope` が前回のラウンドの head を `SINCE` の起点に選び、同じ HEAD では `HEAD...HEAD` の空の差分が相手役に渡って、読まずに収束し新しい `since` でマージへ進んでしまう。そこで `_prepare_round` は、`--no-reuse` の起動の最初のラウンド（その起動で回す 1 つ目。番号は既存のラウンドの次）では `state_scope` を使わずに範囲を `FULL`（`<--base>...HEAD`）にし、ラウンドの記録の `scope` も `FULL` にする。2 つ目以降のラウンドは今のまま `state_scope` で決める（その起動の 1 つ目の head からの差分）。`params.json` の `review` の説明の単位の契約（上の 1）に「`stale` の再レビューでは後ろに `--no-reuse` を足して打つ。受けたら前回の結果を返さずにレビューし直す」を入れる。再レビューが中断・失敗すれば印も記録の `stale` も残るので、次の起動はこの行から同じ開始点で、再利用なしのレビューへ戻る。キューが `ok` で終われば、記録の `pr`・`base` は**書き換えずに**（レビューした PR の組を保つ。PR を読み直さない）、`review-target` の組が記録の `pr` と `units.json` の `repo` と同じことを 4 と同じく確かめてから（違えば `blocked`、`cause: refused`）、`head` と `since` だけをプランの状態ディレクトリの新しい `reviewed-head`・`review-started` で書き換え、状態を `queued` にしてから 5 を打つ（`restarts` は残す）。古い HEAD のまま同じ `ci merge` を繰り返さない |
   | `queued` → `refused`（`OPEN` の番号・ブランチ・宛先の違い、`CLOSED` の PR、`--method` が宛先で許されない（`_method_refusal`）、キューの方式が `--method` と違う、例外の承認の無いキュー、承認した経路がキューなのに宛先がキューを持たない（`route`）） | `blocked`（記録に `reason: refused`・`cause: refused` と `ci merge` の理由を足す。再レビューを打たない。HEAD が同じなのでレビューをやり直しても直らず、人の判断が要る: PR を開き直す・宣言かキューの設定を承認の方式に戻すか承認を取り直す）。工程は `precondition` で止め、次の実行順へ進まず人に返す。`queued` のまま同じ `ci merge` を繰り返さない |
   | `queued` → `precondition`（`metrics.refusal: risk`、`metrics.merged: false`。本文に決めていない「マージの前に決める」残リスクの行（`- [ ]`）が残る。キューにいない） | `blocked`（`cause: risk`。再レビューを打たない）。工程は `precondition` で止める。人が PR 本文の残リスクを決めた（`- [x]` にした）後の打ち直しは、下の `blocked` の行のとおり記録を直さずに同じ `ci merge` から続ける |
   | `queued` → `precondition`（`metrics.in_queue: true`。キューにいる PR を断る行に当たった・登録の受け取りを書けない） | `blocked`（`cause: in_queue`。キューから外すかを人が決める。工程は外さない。記録の `pr`・`head`・`since`・`restarts` と受け取りはそのまま残す）。工程は `precondition` で止め、次の実行順へ進まない |
   | `queued` → `precondition`（`metrics.merged: true`。承認外の宛先・承認の後の宛先の変更・この実行の要求と結び付けられない・キューにいる間に違反を見つけた登録がマージされた・実績の方式の違いか不明でマージされた） | `blocked`（`cause: merged`。`stale` にせず、再レビューを打たない。マージは戻せない）。工程は `precondition` で止め、次の実行順・早送り・`gathered` へ進まず、戻すかを人に返す（マージ済みでも成功にしない） |
   | `blocked`（`cause: in_queue` か `risk`） | 打ち直しのたびに、記録を書き換えずに `queued` と同じ `ci merge`（同じ argv・同じ受け取り）を 1 回打ち、返りを上の `queued` の行で写す。直す操作は GitHub の側（キューから外す・残リスクを決める）だけで、ローカルの記録を人が直す手順は要らない。たとえば人がキューから外した後なら、キューにいない `OPEN` の PR として `refused`・`base_conflict` の行へ進み（`restarts` は残っているので、再レビューを済ませた単位はもう一度断られれば `blocked`）、外す前にキューがマージしていれば受け取りの `violation` で `precondition`（`merged`）になる。直っていなければまた `blocked`（同じ `cause`）で止まる。1 回の打ち直しで打つ `ci merge` は 1 回で、待ちのループを持たない |
   | `blocked`（`cause: refused` か `merged`） | 人が記録を消すか直した後の打ち直しまで `precondition` を返し続け、`ci merge` を打たない（`ndf progress units run` は理由・`cause`・記録のパスを出す）。記録を消すと「記録なし」の行から、`state` を `stale` に直すとその行から続く |

7. **次の実行順と最後**: その実行順のすべての記録が `merged` になってから 2 へ戻る。最後の実行順まで済めば、スプリントの worktree（工程の cwd）で `git fetch <remote> <sprint>` と `git merge --ff-only <remote>/<sprint>` を打ち、ローカルの HEAD をマージ済みの先端まで進めてから工程の残りのステップ（`gathered`。`ndf progress gathered` は `<remote>/<sprint>` がローカルの HEAD の祖先であることを求める）へ進む。早送りの後に `git rev-parse HEAD` と取得した `git rev-parse <remote>/<sprint>` が一致することを求める。`git merge --ff-only` はローカルの HEAD がリモートの先端より先にある（リモートの先端がローカルの祖先）ときも成功して何もせず、push していないコミットを残すうえ、`gathered` の祖先の条件も通ってしまうため、終了コードだけで判定しない。早送りできない（分かれている）か、早送りの後も HEAD が先端と違う（ローカルだけにコミットが残る）なら止める（`precondition`、理由「スプリントの worktree の HEAD <SHA> が <remote>/<sprint> の <SHA> と違う（push していないコミットがある、または分かれている）」）。読むのはローカルの git だけで、取得は上の 1 回のまま

#### worker への単位の指示（`impl.json`）

今の `worker` は設定で与える任意の argv（`params.json` の `worker`。既定なし）で、テンプレートは末尾に作業名 `impl` を足して打つだけである。`ndf answer work` は `<state_dir>/impl-prompt.md` を読むが、そのファイルを書く共通の処理は無い。そこで、プロンプトの生成元と、任意の worker へ担当範囲を渡す契約を次のとおり定める。

- **生成元**: `ndf plan units prompt --out <プロンプト> [--unit <指示のファイル>] --issue <代表の課題> --title <題> --body <本文のファイル> --acceptance <acceptance の要素>…`（`core/plan/cli.py`。Task 8）が `impl` のプロンプトの全文を書く。**代表の課題と受け入れ条件の argv の境界**: `--acceptance` は必ず最後に置き、その後ろの要素をすべて（`argparse.REMAINDER`）差し込み `acceptance` の並びとしてそのまま受ける。`acceptance` の要素（上の `unit_plans` の 4 のとおり、先頭の `--repo`・`--remote`、条件の課題ごとの `--issue`・`--criteria`・`--criteria-digest`）は `prompt` 自身の引数として解析しないので、代表の課題の `--issue` を条件の課題の `--issue` が上書きせず、`--repo` などで引数エラーにもならない。代表の課題は `--acceptance` より前の `--issue` 1 つだけ（`--acceptance` より前に `--issue` が 2 つ以上、または `--acceptance` が無い・後ろが空なら `invalid`）。`acceptance` の並びは `ndf loop acceptance check` と同じパーサーで読み、条件の課題と `<課題>:<番号>` の一覧を「担当の範囲」に使う（追記でなく上書き。打ち直しでも同じ全文になる）。全文は「課題」（題・本文）と「担当の範囲」の 2 節からなる。「担当の範囲」は次の 2 通りで、文を分ける
  - `--unit` あり（単位）: 指示のファイルの担当のタスク（`id`・`title`・`files`・`criteria`）と条件の文（`criteria_text`。承認と同じ指紋の本文から取った文で、統合する課題の条件も文で載る）・実装計画の文書のパス・「上のタスクだけを実装し、ほかのタスクに手を付けない」
  - `--unit` なし（`single` の単位と、`unit_file` を渡さない従来の工程）: 「この課題の受け入れ条件のすべてを実装する」と、`acceptance` の課題と条件の一覧。タスクの一覧を書かず、「ファイル内のタスクだけ」の文も書かない
- **`single` の単位**: `unit_plans` の 3 は `single` の単位に指示のファイルを書かず、差し込み `unit_file` を空にする（指示のファイルにタスクの無い単位を作らない）。範囲は上の `--unit` なしの文になる
- **ステップ**: `params.json` に `unit_file`（「単位の指示のファイル。空なら課題の全体を実装する」、`"default": ""`）を足す。`impl.json` の worker のステップ（今は部品の参照 `{"use": "worker"}` で、中身は `contracts/templates/parts/steps.json` の `{"id": "work", "run": ["{{worker}}", "impl"]}`）の前にステップ `prompt` を足し、空かどうかで引数を分けて上のコマンドを打つ。argv は `["sh", "-c", "out=$0 unit=$1 issue=$2 title=$3 body=$4; shift 4; exec ndf plan units prompt --out \"$out\" ${unit:+--unit \"$unit\"} --issue \"$issue\" --title \"$title\" --body \"$body\" --acceptance \"$@\"", "{state_dir}/impl-prompt.md", "{{unit_file}}", "{{issue}}", "{{title}}", "{{body_file}}", "{{acceptance}}"]` とする。固定の 4 引数（`unit_file`・課題・題・本文のファイル）を変数へ取り出してから `shift 4` し、残った `"$@"` には `{{acceptance}}`（`list: true` なので `--repo R --remote origin --issue N --criteria N:M --criteria-digest N=<SHA-256> …` の要素に展開される）だけが残り、`--acceptance` の後ろに置かれる。`unit_file` が空でも固定の 4 つは位置で数えるので、空の文字列は `shift 4` で落ち、`--unit` も付かない（`shift` を省くと、固定の値と空の文字列が `"$@"` に重なって渡る）。引数の位置は実装で決めてよいが、`unit_file` が空のときに `--unit` を渡さないこと、`"$@"` に受け入れ条件の引数だけを残すこと、それを `--acceptance` の後ろの最後に置くことは守る。従来の工程（`light`・`operation`・`documentation` の `implement.json`）と手動の `ndf route render impl` も同じプロンプトを得る
- **worker への契約**: `impl.json` の worker のステップは部品の参照をやめて直書きにし（id は `work` のまま。共有の部品はほかのテンプレートも使うので変えない）、`run` を `["sh", "-c", "NDF_WORK_PROMPT=\"$0\" exec \"$@\"", "{state_dir}/impl-prompt.md", "{{worker}}", "impl"]` にし、環境変数 `NDF_WORK_PROMPT` にプロンプトのパスを渡す（argv の末尾は今のまま作業名だけなので、既存の worker の引数の受け方を変えない）。`params.json` の `worker` の説明に「作業名 `impl` の worker は `NDF_WORK_PROMPT` のファイルを作業の指示として読み、その『担当の範囲』の外を実装しない」を契約として書く。`ndf answer work` は今のまま `<state_dir>/impl-prompt.md`（同じファイル）を読むので変えない。契約に従わない worker を設定したプロジェクトでは範囲を守れないが、それは設定の誤りとして手順書（Task 9 の `agent-layers.md`）に書く

`stages.py` の工程の型と `definition.py:321` の読み手に `per_unit` を足す（既定は偽）。`per_issue` は改名せずに残す（`ndf.schema.json` の既存のキーと、保存済みのスナップショットの `per_issue` を今のまま読めるようにするため。`_stage_from` はキーをそのまま `StageDef` に渡すので、`per_unit` を持たない古いスナップショットは既定の偽で読める）。

### マージの対象の照合と再開（`ndf ci merge --pr --base`）

満たす決定: 1・7。設計 PR（`design-land`）と単位の PR（工程「実装」）の両方が使う。照合の処理（`merge_queues`・`recheck`・`merge_state`・`merge_approved`・`_merge_pull` の照合の経路・`merged_method`）の本体は `adapters/github_merge.py` に置く（地図の「既存のファイルには呼び出しと登録だけを足す」）。今の `ci merge --branch` はブランチの開いた PR を引き直してその最初の PR をマージし、マージ済みなら開いた PR が無いので止まる。承認・レビューした PR と違う PR をマージしない、マージキューの後に打ち直せる、の 2 つのため `--pr <番号>`（承認・記録した PR）と `--base <宛先>` を足す。

**引数の組み合わせ**: 経路は 2 つだけで、どちらにも当たらない呼び出しは PR を読まずに `stopped`（`invalid`、「--repo・--pr・--base・--reviewed・--method・--since・--receipt はそろえて渡す」）で止める。

| 経路 | 受け付ける引数 | 振る舞い |
| --- | --- | --- |
| 照合の経路 | `--repo`・`--branch`・`--pr`・`--base`・`--reviewed`・`--method`・`--since`・`--receipt` のすべて（任意で `--queue-approved`）。または `--target <ファイル> --answer <回答の記録>` だけ（設計の承認の記録と、それに対する回答。同じ値（`--repo` は記録の `repo`）と `queue.design` をそのファイルから読み、`--receipt` は記録と同じディレクトリの `design-receipt.json`。下の「回答との照合」） | 下の表で判定する |
| 従来の経路 | `--branch`（`--reviewed`・`--method` は任意）。`--pr`・`--base`・`--since`・`--receipt`・`--target` を渡さない | 今のまま（ブランチの開いた PR を引いてマージする） |
| 止める | 照合の経路の値が 1 つでも欠ける、`--target` と `--answer` の片方だけを渡す、または `--target` とほかの照合の値を併せて渡す | `invalid`。宛先・方式を照らさずにマージする呼び出しを作らない |

`--method` は下の「マージの方式の決め方」で決めた方式である（単位は `units.json` の `merge_method`、設計 PR は承認の記録の `method`）。

**操作先のリポジトリ**: PR の番号・ブランチ名・HEAD は別のリポジトリ（フォーク・同じ内容を持つ別の写し）でも一致し得るので、承認は GitHub のリポジトリの識別子 `repo`（`<所有者>/<名前>`）と組にする。

- **決め方**: 作業場所の `<remote>` の URL から今の `Git.remote_repo()` と同じ読み方で決める（API を呼ばない）。比べるときは GitHub と同じく大文字と小文字を区別しない
- **記録する**: `design target` は設計の作業場所の `<remote>` から決めた値を記録の `repo` に書き、承認資料に載せ、回答の `design-answer.json` が写す（「回答との照合」の ④）。`units_queue` は記録の `repo` を写し、`unit_plans` が `units.json` の `repo` に書く（指紋 `source` の `queue` にも入る）
- **PR を読む前に照らす**: 照合の経路の `ci merge` は、PR を読む前に、承認の値（`--target` では記録の `repo`、単位では `--repo`）と、作業場所の `<remote>` から決めた操作先が同じかを確かめ、違えば PR を読まずに `stopped`（`invalid`、「承認したリポジトリ <repo> と作業場所の操作先 <repo> が違う」）で止める。`GitHub` の操作先は承認の値で作る（今の従来の経路の「`--repo` か作業場所の remote」の選び方を照合の経路では使わない）。`invalid` は `restart_on` の対象でないので、設計 PR は開き直さずに止まり、単位は工程の失敗になる
- **同期と組み立ても照らす**: `design-sync` は「マージの後に承認済みのファイルをスプリント側へ揃える」の 0 で、取得と push に使う `<remote>` から決めた操作先を記録の `repo` と照らす。`units_queue` も記録の `repo` をスプリントの作業場所の `<remote>` と照らし、違えば `invalid`。`ndf progress units run` は `units.json` の `repo` を単位のマージの `--repo` に渡すので、ほかのリポジトリの同じ番号の PR へ承認が通らない

**マージの方式の決め方**（`core/route/__init__.py` の `declared_merge_methods(repo, bases: Sequence[str], remote) -> dict[str, str]`。新設。単位と設計 PR の両経路がこれだけを使う。宛先が 1 つなら `bases` に 1 つだけ渡す）: 今の `route.default_merge_method` は宛先で許された方式の先頭を選び、プロジェクトの宣言を読まないので、照合の経路では使わない。

**宛先ごとに決め、設定の読みは共有する**: 宛先で許された方式は、宛先ごとの ruleset（`GET /repos/{repo}/rules/branches/{branch}`）とリポジトリ全体の設定（`GET /repos/{repo}`）の 2 つから決まる（今の `allowed_merge_methods` は、ruleset が方式を空に絞ったときにリポジトリの設定を読まずに返すのを除き、1 宛先に 2 回読む）。`declared_merge_methods` は `bases` の**異なる宛先ごとに** ruleset を 1 回、リポジトリの設定を全体で 1 回だけ読み（`allowed_merge_methods(branch, settings=<読んだ設定>)`。`settings` を省けば今のとおり自分で読む）、宛先ごとに下の表で方式を決めて返す。読みの回数は宛先 1 つで 2、異なる 2 つで 3 で、宛先が同じなら 1 つに数える。宣言が無いときの方式（許された方式の先頭）は宛先ごとに違い得るので、2 つの宛先の方式を 1 つの値で代用しない。

宣言の `branch_strategy.merge` には 2 つの値があり、役割が違う。**方式**は `merge.commit`（`merge`・`squash`・`rebase`。`BranchStrategy.merge_commit`。`allowed_merge_methods`・`pick_merge_method` が扱う値と同じ）で、`declared_merge_methods` はこれだけを読む。**経路**は `merge.method`（`merge-queue`・`strict`・`direct`。`BranchStrategy.merge_method`）で、本番の PR の照合（`domains/release/land.py` の `check_production_pr`）が使う値である。`merge.method` を `pick_merge_method` に渡さない（本リポジトリの `merge-queue` は方式の値ではないので、渡すと設計の承認の記録も単位の計画も作れない）。設計 PR と単位の PR の宛先（スプリントか、`doc_prs: base` のベース）が本番のブランチと同じとは限らないので、この 2 つの経路はキューを使うかを `merge.method` から推さず、宛先が実際にキューを持つか（`GitHub.merge_queues(branches)`。下の「要求の時点の宛先」）で決める。

| 場合 | 決める方式 |
| --- | --- |
| 宣言 `branch_strategy.merge.commit` があり、宛先（`allowed_merge_methods(base)`。ruleset とリポジトリの設定）で許される | 宣言の方式（`pick_merge_method(宣言, allowed)`） |
| 宣言があり、宛先で許されない | 決めずに `RouteError`（「宣言の方式 <方式> は <宛先> で許されない」）。単位は `unit_plans` が `UnitsError` で止め、設計 PR は `design target` が `stopped`（`invalid`）を返して記録を書かない。許された方式へ黙って替えない |
| 宣言が無い | 宛先で許された方式の先頭（今の `default_merge_method` と同じ） |
| 宛先の許可を読めない（git・GitHub の失敗） | 決めずに `RouteError`（`precondition`）。None のまま記録に書かない |

宛先がマージキューを持つときも同じ値を記録に書く。キューへの登録では方式をキューの設定（`mergeQueue(branch).configuration.mergeMethod`）が決めるので、**キューの実際の方式を記録の方式と照らす**: `design target` は記録を書く前に、キューを持つ宛先ごとにその方式（`MERGE`・`SQUASH`・`REBASE` を小文字にした値）が、`declared_merge_methods` の返りの**同じ宛先の**方式と同じかを確かめ（設計 PR の宛先は記録の `method`、スプリントのブランチは記録の `units_method`。下の「設計の承認の記録」）、違えば記録を書かずに `stopped`（`invalid`、「<宛先> のキューの方式 <方式> が宣言 merge.commit の <方式> と違う」）で止める。承認資料に出す方式と実際にマージされる方式が食い違う記録は作らない。`ci merge` も登録の直前に、同じ読み（下の「キューと事象の読み」。今の `_MERGE_QUEUE_STATE` が既に `mergeMethod` を読む）のキューの方式を `--method` と照らし、違えば登録を送らずに `refused`（承認の後にキューの設定を変えた）。既存のマージの部品（`parts/steps.json` の `merge`）と差し込み `merge_method` の既定は変えない（この変更の外）。

**判定**（照合の経路。作業場所の HEAD と `--reviewed` の確かめは今のまま先に行う）: 読む順は **① PR を `GitHub.pull(番号)` で 1 回読む → ② `OPEN` か `MERGED` なら「キューと事象の読み」を 1 回 → ③ キューを持たない宛先へ直接マージするときだけ、方式の読み 2 → PR の読み直し 1 → 要求** に固定する。判定は上の行から順に当て、最初に当たった行で返す。マージ済みかどうかより先に head のブランチ・HEAD を照らす（今の `_preflight` の「マージ済みなら成功」を照合の経路では使わない）。① だけで返すのは、head のブランチ・HEAD の違い（番号の渡し間違いか、push で GitHub がキューから外した PR）と `CLOSED` だけとする。**`OPEN` の PR を断るほかの行（残リスク・衝突を含む）は、② を読んでキューにいるかを確かめてから返す**（キューへ登録した後に本文へ未決の残リスクが足されても、キューに残った PR を見落とさない。下の「キューにいる PR は断らずに人に返す」）。

**PR の読み取りの回数は経路ごとに固定する**（`GitHub.pull` と、`pull2` の `GitHub.recheck` の呼び出し）: 直接マージが成功する経路は ① の読み・要求の直前の読み直し `pull2`・要求の後の読み直しの **3 回**、`pull2` で初めて `MERGED` か照合の違いを見つける経路は ① と `pull2` の **2 回**、キューへの登録・キューの待ち・マージ済み・照合の失敗（③ の方式の断りを含む）の経路は ① の **1 回だけ**である。`pull2` は宛先の取り違えと承認の後の再オープンを防ぐための読みで、省けない: ① の後の方式の読み（2 往復）の間に宛先を変えられても、閉じて開き直されても、`pull2` で照らし直すので要求を送らない。

**要求の直前の読み直し**（`GitHub.recheck(number, since) -> tuple[Pull, MergeState]`。新設）: `pull2` は REST の `GitHub.pull` でなく、PR の項目（`PULL_FIELDS`）と、② と同じ `timelineItems(since: --since, itemTypes: [REOPENED_EVENT, BASE_REF_CHANGED_EVENT])` の件数・`isMergeQueueEnabled`・`isInMergeQueue` を 1 本の GraphQL で読む（`_MERGE_QUEUE_STATE` に PR の項目を足した問い合わせ）。状態・HEAD・宛先が同じでも、② の後に閉じて開き直された・宛先を変えて戻された PR は事象の件数で見つかる。1 回の呼び出しなので API の回数は今の `pull2` と同じで、`pull2` と要求の間に呼び出しを挟まない規則も変わらない。直接マージで要求が断られたときは、今の `after = self.pull(number)` の読み直しが要求の後の読み直しを兼ねる（3 回のまま）。

**マージ済みの PR で成功にしない行は `precondition` で返す**: 照合の経路で PR が `MERGED` なのに `ok` にしない行（下の表の ①②の `MERGED` の行、`pull2` で初めて見つけた `MERGED`、要求の後の読み直しで見つけた違いと `MERGED`）は、`refused` でなく `stopped`（`precondition`、`metrics.merged: true`）を返す。マージは戻せないので、承認の取り直しやレビューのやり直しへ自動で戻さず、人に返す。呼び手はこの種類を開き直しに写さない（設計 PR は `design-merge` の `restart_on` の外、単位は記録を `blocked`。下の「承認を無効にする遷移」と工程の流し方の 6）。`OPEN` でキューにいない PR の `refused` は今のとおり `refused` である。

**途中で初めて `MERGED` を観測する経路も同じ判定へ通す**: `MERGED` を ① で見るか、`pull2` で見るか、要求が断られた後の読み直しで見るかによらず、`ok` にしてよいのは下の「この実行の要求の受け取り」の照合と「マージの実績の方式」が通ったときだけである。`pull2` で `MERGED` を見たときは、この実行はまだ要求を送っていない（受け取りに `merge_sha` が無い）ので `precondition`。要求が断られた後の読み直しで `MERGED` を見たときも、断られた要求は `merge_sha` を返さないので `precondition`（その間に人が同じ HEAD を別の方式でマージした場合を成功にしない）。どちらも ② の読みは打ち直さず、追加の API を呼ばない。

**キューにいる PR は断らずに人に返す**（`GitHub.dequeue` を照合の経路で呼ばない）: GitHub のキューから外す操作（GraphQL の `dequeuePullRequest`。入力 `DequeuePullRequestInput` は PR の `id` だけ）は、登録（`mergeQueueEntry`）の ID を条件にできない。照合の後に人が同じ PR を外して入れ直すと、要求の時点では新しい登録を外してしまい、この実行の登録だけを外す保証が無い。また今の `GitHub.dequeue` は PR を読み直すので、判定の API の回数も超える。そこで照合の経路は自動で外さない。② の読みで `isInMergeQueue` が真の `OPEN` の PR を、下の表の `OPEN` の断る行（残リスク・衝突・宛先と事象・例外の承認・キューの方式）のどれかで断るときは、`refused`・`base_conflict` でなく `stopped`（`precondition`、`metrics.merged: false`・`metrics.in_queue: true`、「#<番号> はキューにいるが <断る理由>。キューから外すかを人が決める（GitHub は登録を条件に外せない）」）を返す。呼び手は開き直さず（設計 PR は `restart_on` の外）、単位は記録を `blocked`（`cause: in_queue`）にする。この `precondition` を返す前に、見つけた違反を受け取りの `violation`（`{"refusal": <metrics.refusal>, "reason", "at"}`）へ `os.replace` で書き足す（ローカルのファイルで API ではない。書けなければ同じ `precondition` の理由に「違反を受け取りへ残せない」を添える）。人が外した後の打ち直しは、キューにいない `OPEN` の PR として今の状態で判定し、同じ理由なら `refused`・`base_conflict`（残リスクは `precondition`、`risk`）になっていつもの遷移へ進む（設計 PR の `design-merge` も単位も同じ argv を打ち直すだけで、ローカルの記録を直さない。単位の再開は工程の流し方の 6 の `blocked`（`in_queue`）の行）。人が外した後に原因を直して照合が通れば、新しい要求の受け取りで `violation` の無い記録へ書き直してから登録する。人が外す前にキューがマージしたときは、次の打ち直しの `MERGED` の行で受け取りの `violation` を見て `precondition`（`metrics.merged: true`、「#<番号> はキューにいる間に <理由> を見つけた登録でマージされた」）を返す。キューにいる間に人が原因だけを直しても `violation` は消えないので、その登録のマージは成功にならない（直したうえで流すには、外してから打ち直す）。

**この実行の要求の受け取り**（`--receipt <ファイル>`。`--target` では記録と同じディレクトリの `design-receipt.json`、単位は `work_dir/units/<seq>.receipt.json`。工程が `unit_merge_argv` で渡す）: `MERGED` の PR がこの実行の要求でマージされ、その要求がどの経路（キューか直接か）だったかを裏づける唯一の記録である。マージの時点のキューの設定は GitHub から読めず、今見えるキューの設定はマージの後に変えられるので、`MERGED` の経路の判定に今のキューの設定を使わない。登録した人と時刻（`enqueuer`・`enqueuedAt`）も、同じアカウントで人が手で登録した場合と見分けられないので使わない。

- **書く**: 要求を送る**前に** `{"pr", "base": --base, "head": 送る HEAD, "route": "queue" | "direct", "method": --method, "since": --since, "requested_at", "entry": null, "merge_sha": null, "violation": null}` を一時ファイルからの `os.replace` で書く（新しい要求のたびに全体を書き直すので、前の要求の `entry`・`merge_sha`・`violation` は残らない）。書けなければ要求を送らずに `stopped`（`precondition`、`metrics.merged: false`）。キューへの登録の応答の `mergeQueueEntry { id }` を `entry` に、直接マージの成功の応答（REST の `PUT /pulls/{n}/merge` が返す `sha`）を `merge_sha` に書き足す。書き足せなければ `stopped`（`precondition`。登録なら `metrics.merged: false`・`metrics.in_queue: true`、直接マージなら `metrics.merged: true`）。API の回数は増えない（応答の値を使う）
- **照らす**: `MERGED` の PR を `ok` にするのは、受け取りが**今の承認対象と方式の要求**で（`pr`・`base`・`head`・`method`・`since` が PR の番号・`--base`・`--reviewed`・`--method`・`--since` と同じで、`requested_at` が `--since` より後）、`violation` が無く、次のどちらかのときだけ。`since` と `requested_at` を照らすので、別の承認（設計 PR の前の世代、単位の再レビューの前の `since`）で残った受け取りは使えない
  - `route: direct` で、`merge_sha` が PR の `mergeCommit.oid`（この実行の要求が作ったマージ）
  - `route: queue` で、`entry` があり、`--queue-approved`（`--target` では記録の `queue.design`）があり、**記録した登録がそのままマージにつながった**: ② の読みの `requested_at` より後のキューの事象（下の「キューと事象の読み」）で、`ADDED_TO_MERGE_QUEUE_EVENT` がちょうど 1 件（この実行の登録）で、`REMOVED_FROM_MERGE_QUEUE_EVENT` が 0 件（キューから外された後の手動のマージ・入れ直しの登録でない）。GitHub がキューのマージのときに外した事象を書くかは Task 7 の着手時に実物の PR の timeline で確かめ、書くならマージの事象と同じ時刻の 1 件だけを数えから除く（どちらの場合も、人が外してから手でマージした・外して入れ直した、は数えに残るので止まる）
- **特定できないとき**: 受け取りが無い・読めない、承認対象と方式の値（`pr`・`base`・`head`・`method`・`since`・`requested_at`）が今の引数と合わない、`route: direct` なのに `merge_sha` が無いか `mergeCommit.oid` と違う（要求の応答の前に止まった・人が別にマージした）、`route: queue` なのに `entry` か例外の承認が無いか、登録の後のキューの事象が上の数と違う、のどれかなら経路を特定できないので `stopped`（`precondition`、`metrics.merged: true`、「#<番号> のマージをこの実行の要求と結び付けられない」）で人に返す。`violation` があれば `precondition`（`metrics.merged: true`。上の「キューにいる PR は断らずに人に返す」）。承認の後にキューを有効にして人がキューでマージし、打ち直しの前に無効へ戻しても、受け取りが無いので成功にしない。この実行の登録を人がキューから外し、同じ HEAD のまま手でマージしても、外した事象が残るので成功にしない。逆に、この実行が直接マージした後にキューを有効にしても、受け取りの `merge_sha` で直接の経路と分かるので失敗にしない
- 受け取りはマージの後も消さない。設計 PR の世代が進むと `stage_dir` が新しくなるので、開き直した後の受け取りは空から始まる

| ② `MERGED` で、上の「この実行の要求の受け取り」の照合が通らない（受け取りが無い・承認対象と方式の値が違う・`merge_sha` が違う・キューの経路の承認が無い・登録の後に外された事象か別の登録がある・`violation` がある） | `precondition`（「#<番号> のマージをこの実行の要求と結び付けられない」。`violation` なら「キューにいる間に <理由> を見つけた登録でマージされた」）。今のキューの設定では経路を決めない | ①② |

| ② `MERGED` | `ok`（「既にマージ済み」。マージキューが済ませた後の打ち直しか、この実行の直接マージの後の打ち直し）。宛先の変更の事象・受け取り・実績の方式を照らしたうえでの成功なので、宛先を変えてマージした後に宛先の名前が戻って見えても、この実行の要求でないマージでも、承認と違う方式でマージされても成功にしない | ①② |
| ② `OPEN` で、宛先がキューを持ち、`--queue-approved` が無い | `refused`（下の「要求の時点の宛先」。登録を送らない）。既にキューにいれば上の行で `precondition`（例外の承認の無い登録を `ci_pending` で待ってマージ済みを成功にしない） | ①② |

| ② `OPEN` で、キューに入っている | `ci_pending`（マージの要求を打ち直さない） | ①② |

| ② `OPEN` で、宛先がキューを持たない（`--queue-approved` が無い＝承認した経路が直接マージ） | ③ 方式を `allowed_merge_methods(--base)` で読み、`pick_merge_method(--method, allowed)` が None なら要求を送らずに `refused`（今の `_method_refusal`。承認と違う方式でマージしない。承認の後に宣言・ruleset・リポジトリの設定が変わって方式が使えなくなった場合もここ）。合えば PR を**事象と一緒に**読み直し（`pull2`。下の「要求の直前の読み直し」の `GitHub.recheck`）、`pull2` を ① の行・② の `OPEN` の行（ブランチ・HEAD・状態・残リスク・衝突・`baseRefName`・`--since` より後の再オープンと宛先の変更の事象・宛先がキューを持つか）で照らし直して、当たればその行の返り（キューを持てば、② の後にキューを有効にされたので `--queue-approved` によらず `refused`（`queue_unapproved`）。この経路はキューの例外の承認を照らしていないので登録しない）。`pull2` が `MERGED` なら、上の「途中で初めて `MERGED` を観測する経路」のとおり `precondition`（要求を送っていないので受け取りの照合が通らない）。たとえば方式を読む間に宛先を変えられたら `pull2` の `baseRefName` で、同じ HEAD のまま閉じて開き直されたら `pull2` の `REOPENED_EVENT` で `refused` になり要求を送らない。通れば受け取り（`route: direct`）を書いてから `pull2` の HEAD で直接マージを要求し、成功したら応答の `sha` を受け取りの `merge_sha` に書き足し、PR を 1 回読み直して宛先を照らす（下の「要求の時点の宛先」）。違えば `precondition` | 成功: ①②・方式の読み 2・読み直し 1・要求 1・要求の後の読み直し 1（計 7、PR の読みは 3）。方式の断り: ①②・方式の読み 2（計 4、PR の読み 1）。`pull2` で断る・`MERGED` を見る: ①②・方式の読み 2・読み直し 1（計 5、PR の読み 2）。要求が断られた: 成功と同じ計 7（要求の後の読み直しが今の `after` を兼ねる） |

**キューと事象の読み**: 今の `_MERGE_QUEUE_STATE` の GraphQL（`isMergeQueueEnabled`・`isInMergeQueue`・`mergeQueue(branch).configuration.mergeMethod`）に、`timelineItems(since: --since, itemTypes: [REOPENED_EVENT, BASE_REF_CHANGED_EVENT])` の件数・マージの実績（`mergeCommit { oid parents(first: 2) { totalCount nodes { oid } } }`。`MERGED` のときだけ値を持つ）を足した 1 本の問い合わせ（`GitHub.merge_state(pull, since, queued_since: Optional[str]) -> MergeState`）にする。受け取りが `route: queue` のときは、同じ問い合わせに別名で `timelineItems(since: <受け取りの requested_at>, itemTypes: [ADDED_TO_MERGE_QUEUE_EVENT, REMOVED_FROM_MERGE_QUEUE_EVENT])` の種類ごとの件数を足す（`queued_since`。受け取りはローカルのファイルなので ② の前に読む。上の「この実行の要求の受け取り」の照合に使い、読みの回数は 1 のまま）。再オープン・宛先の変更・キューの状態と方式・マージの実績を 1 回で読み、照合の経路の `OPEN` と `MERGED` の行はどれもこの読みを 1 回だけ使う。`mergeQueueEntry` は照合に使わないので読まない（外す操作を持たないため）。閉じて開き直した PR は、番号・ブランチ・宛先・HEAD が同じでも `REOPENED_EVENT` で止まる（承認の後の状態の変更を照らす情報はこの事象で、承認の記録の時刻 `--since` より後のものだけを数える）。マージ済みの PR も宛先の変更の事象を数えるので、承認の後に宛先を変えてマージされたものを、今見える `baseRefName` が `--base` と同じでも成功にしない。

**マージの実績の方式**（`github_merge.merged_method(state, receipt, reviewed) -> frozenset[str]`。純粋な関数。上の読みの値と受け取りだけから決め、API を足さない。返りが空なら確かめられない）: GitHub はマージ済みの PR の方式を項目として返さず、コミットの `associatedPullRequests` もコミットを導入した PR との関連でマージの方式を表す契約が無いので、方式の証拠に使わない。方式は**この実行の要求**と、それで足りない分だけマージのコミットの親の形から決める。

| 経路（受け取りの `route`）とマージのコミットの形 | 実績の方式 |
| --- | --- |
| `direct` で、`merge_sha` が `mergeCommit.oid` | 受け取りの `method`（直接マージは要求の `merge_method` で方式を指定し、GitHub はその方式で作ったコミットの `sha` を返す。PR のコミットの数によらず方式が決まる） |
| `queue` で、親が 2 つで 2 つ目の親が `--reviewed` | `{merge}` |
| `queue` で、親が 1 つ | `{squash, rebase}`。キューの方式が `squash` と `rebase` のどちらだったかは、マージの後のコミットの形からも GitHub の API からも見分けられない。**仕様で許容する例外**とし、キューを持つ宛先の方式が `squash` か `rebase` のときは承認資料に載せる（下の「承認資料」）。`merge` との違いは見分けられるので止まる |
| ほか（受け取りの照合が通らない、`mergeCommit` が無い、親が 2 つで 2 つ目が `--reviewed` でない） | 空（確かめられない）。成功にせず `precondition` |

`--method` が返りに含まれれば一致とする。打ち直しの `MERGED` の行は経路を問わずこの規則で照らす（人が別の方式で手でマージした場合は受け取りの照合で止まる）。

**照合の経路の種類と、呼び手の写し方**（まとめ。単位の列は工程の流し方の 6 の表と同じ）:

| `ci merge` の返り | 設計 PR（`design-merge`） | 単位（工程の流し方の 6） |
| --- | --- | --- |
| キューにいない `OPEN` の `refused`（番号・ブランチ・HEAD・宛先・再オープン・`CLOSED`・方式が宛先で許されない・キューの方式の違い・例外の承認・承認と違う経路）・`base_conflict` | `stale_approval`（`restart_on` で「ドキュメントレビュー」を開き直す。今の経路で承認を取り直す） | HEAD の違い・再オープン・衝突は `stale`。番号・ブランチ・宛先の違い・`CLOSED`・方式が宛先で許されない（`_method_refusal`）・キューの方式の違い・例外の承認の無いキュー・承認と違う経路（`route`）は `blocked`（`cause: refused`） |
| キューにいない `OPEN` の `precondition`（`metrics.refusal: risk`。本文に未決の残リスク） | `precondition` のまま止める（開き直さない）。人が本文の行を決めた後に同じ argv の `design-merge` を打ち直す | `blocked`（`cause: risk`。決めた後の打ち直しで同じ `ci merge` から続ける） |
| `OPEN` の `precondition`（`metrics.in_queue: true`。キューにいる PR を断る行に当たった・登録の受け取りを書けない） | `precondition` のまま止める（開き直さない）。人がキューから外すかを決め、外した後に同じ argv を打ち直す | `blocked`（`cause: in_queue`。外した後の打ち直しで同じ `ci merge` から続ける） |
| `MERGED` の `precondition`（承認外の宛先・承認の後の宛先の変更・この実行の要求と結び付けられない・キューにいる間に違反を見つけた登録のマージ・実績の方式の違いか不明・要求の後の宛先の違い） | `precondition` のまま止める（開き直さない）。人が戻すかを決める | `blocked`（`cause: merged`。再レビューの `stale` にしない） |

`refused` の種類は理由の文でなく `metrics.refusal`（`head`（HEAD の違い）・`reopened`（再オープン）・`target`（番号・ブランチ・宛先の違いと宛先の変更）・`closed`・`method`（`_method_refusal`）・`queue_method`（キューの方式の違い）・`queue_unapproved`（例外の承認の無いキュー）・`route`（承認した経路がキューなのに宛先がキューを持たない））で返し、単位の呼び手はこの値だけで `stale`（`head`・`reopened`）と `blocked`（ほか）を分ける。残リスクは `refused` でなく `precondition` の `metrics.refusal: risk` で返す（上の表）。

**同じ読み取りを使う責務**（本体は `adapters/github_merge.py`。`adapters/github.py` の `GitHub` には委ねる呼び出しだけを足す）: `GitHub.merge_approved(pull: Pull, state: MergeState, base: str, reviewed: str, method: str, receipt: Path) -> MergeOutcome` を足す。`ci_cli._merge` は照合の経路で ① を読んで上の表の ① の行を判定し、`OPEN` か `MERGED` のときだけ ② を 1 回読んで ② の行を判定し、要求するときに ① の `pull` と `state` を `merge_approved` へ渡す。`merge_approved` は、キューがあれば受け取りを書いて ① の `pull` で登録し、無ければ ③（方式の読み → `pull2` の読み直しと照らし直し → 受け取りを書く → `_merge_pull(pull2, expect_head, method, route, collated=True)`）を打つ。`_merge_pull` は `_merge_with` の本体を `pull` を受け取る形に切り出したもの（`github_merge.py` に置く。`_merge_with` は `self.pull(number)` の後に `_merge_pull(..., collated=False)` を呼ぶ形にして、従来の経路の振る舞いを変えない）。**`collated=True`（照合の経路）では、今の本体が持つ 405 のときの `_enqueue` への切り替えを打たない**: 方式の再取得（`allowed_merge_methods`。③ で読み済みの方式をそのまま使う）もキューの読み直しも登録もせず、405 を含む要求の断り（`MERGE_REFUSED_STATUS`）は下の「要求が断られて PR を読み直すとき」の規則だけで扱う（読み直した PR がキューにいない `OPEN` で同じなら `refused`、`metrics.refusal` は今の `refusal_kind` の種類で、405 なら `queue_unapproved`）。② の後にキューを有効にされても、照合の経路はキューの例外の承認を確かめずに登録しないので、受け取りが `route: direct` のままキューに入ることは無い（`pull2` のキューの状態で先に断るので、405 は `pull2` から要求までの窓で有効にされたときだけ起きる）。方式の読みはキューを持たない宛先へ直接マージするときだけで、マージ済み・待機中・衝突・照合の失敗の早期の返りでは読まない。**`pull2` の読みと要求の間に別の API 呼び出しを挟まない**（方式の読みと ② は `pull2` より前に済ませる。受け取りの書き込みはローカルのファイルで API ではない）。要求が断られて PR を読み直すとき（今の `after = self.pull(number)`）は、読み直した PR を上の表の ① の行と宛先で照らし直してから成否を決める: `MERGED` なら宛先・head のブランチ・HEAD が同じでも `precondition`（上の「途中で初めて `MERGED` を観測する経路」。断られた要求は `merge_sha` を返さないので、この実行のマージと結び付けられない）、`OPEN` で違えば `refused`、ほかは今の `refusal_kind` の種類。この読み直しが要求の後の読み直しを兼ね、別に読まない

**要求の時点の宛先**: GitHub の直接マージ（REST の `PUT /pulls/{n}/merge` の `sha`）とキュー登録（`enqueuePullRequest` の `expectedHeadOid`）は HEAD を条件にできるが、宛先を条件にする引数を持たない。GitHub の API で宛先を要求の時点まで完全に固定する手段は無い。宛先の変更は PR の書き手か書き込み権限を持つ人だけができ、NDF の工程は記録済みの PR の宛先を変える操作を持たない（`gh pr edit --base` を打つステップを置かない。`test_sprint_templates.py` で全テンプレートの argv に無いことを縛る）。したがって宛先を変えられるのは、書き込み権限を持つ人のうっかりの操作だけである。そこで**自動の要求を送ってよい条件**を経路ごとに次のとおり決め、条件を満たさない要求は送らない

| 経路 | 自動の要求を送ってよい条件 | 条件を満たさないときと、要求の後に見つけた違い |
| --- | --- | --- |
| 直接マージ（宛先にキューが無い） | **承認した例外のときだけ**: 承認の記録の `queue` がその宛先について偽（記録を書いた時点で宛先がキューを持たない）で、承認資料がその宛先に「直接マージは最後の照合（`pull2`）から要求までの 1 往復の間の宛先の変更を防げず、要求の後の読み直しで見つけたときはマージ済みのまま止めて人に返す」の例外を載せ、回答がその記録の SHA-256 と結び付いたときだけ要求を送る（キューの例外と同じ照合）。承認の後にキューを外された宛先（記録の `queue` が真なのに今はキューが無い）は、直接マージの例外を承認していないので上の表の `route` の行で断る。宛先を照らす実際の順は、① の読みで照らす → ② で宛先の変更の事象を照らす → 方式の読み 2 → `pull2`（`recheck`）の読みで宛先・再オープンと宛先の変更の事象・キューの有無を照らし直す → 要求、である。最後に宛先を照らす `pull2` の読みと要求の間には API 呼び出しを挟まないので、変えられる窓は `pull2` の読みから要求までの 1 往復（秒の単位）の中だけになる（① から要求までの間の変更は `pull2` で見つける）。この窓は承認資料に載せて承認を得た例外で、承認なしには許容しない。自動の要求は、承認した経路が直接マージで、`pull2` が ① の行と宛先の行をすべて通ったときだけ送る | 要求の成功の後に PR を 1 回読み直し、`baseRefName` が `--base` と違えば `precondition`（「#<番号> が承認外の宛先 <宛先> へマージされた」）。後の打ち直しでは、マージ済みの PR を ② の宛先の変更の事象・受け取り・実績の方式でも照らす（上の表）。マージは戻せないので、工程は `precondition` のまま止め（単位なら記録を `blocked`）、次の実行順・スプリントの worktree の早送り・`gathered` へ進まず、戻すかどうかを人に返す（自動で revert しない） |
| マージキュー | **承認した例外のときだけ**: 登録からキューがマージするまでの間（分の単位）は宛先の変更を見張る手段が再開の照合しかないので、承認者がこの例外を見て承認したことを要求の前に確かめる。`design target` は記録を書くときに設計 PR の宛先と `--sprint` のブランチ（単位の宛先）がキューを持つかとその方式を読み（`GitHub.merge_queues(branches) -> dict[str, Optional[QueueConfig]]`。今の `_MERGE_QUEUE_STATE` の `mergeQueue(branch)` の部分を、**異なる宛先ごとに別名（`_alias`）で並べた 1 本の問い合わせ**。宛先が 2 つでも読みは 1 回で、`doc_prs: sprint` のように同じなら別名も 1 つ）、記録に `queue: {"design": 真偽, "units": 真偽}` と単位の宛先 `sprint`（`--sprint` の値）を書く。キューを持つ宛先ごとに、その方式を同じ宛先の `declared_merge_methods` の値と照らす（上の「マージの方式の決め方」）。承認資料は真の宛先ごとに「宛先がキューを持つので、登録の後の宛先の変更は再開の照合で見つける」を載せ、回答の事象は記録の SHA-256 と組なので、この例外の承認も同じ照合で確かめられる。`ci merge` の照合の経路は `--queue-approved` が無ければ登録しない。`--target` は記録の `queue.design` が真のときだけ登録を許し、単位は下の「単位のキューの承認の受け渡し」で照合済みの根拠から `--queue-approved` を決める | 宛先がキューを持つのに例外の承認が無い（承認の後にキューを有効にした、を含む）なら、登録を送らずに `refused`（「宛先 <宛先> がキューを持つが、承認でその例外を認めていない」）。既にキューにいれば `precondition`（`in_queue`。上の表）。設計 PR は `refused` なら `stale_approval` で承認を取り直し、単位は `blocked` で人に返す。登録の後は、`ci_pending` で返った工程の打ち直しのたびに ① と ② の行で照らし、キューの中で違いを見つければ外さずに `precondition`（`metrics.in_queue: true`）で人に返す。キューがマージした後に見つけた違いは `precondition`（`metrics.merged: true`）で返し、設計 PR は開き直さず、単位は `blocked` にする（上の「マージ済みの PR で成功にしない行」）。承認者が直接マージで流したいときは宛先のキューを外す判断を人に委ねる |

**API の回数**（照合の経路。PR の読み 1 を含む）: ブランチ・HEAD・閉じた PR の失敗 1、残リスク・衝突の失敗 2（PR・キューと事象。キューにいるかを確かめるため）、マージ済みの打ち直し 2（PR・キューと事象。宛先の変更の事象を読むため）、宛先・事象・例外の承認・キューの方式・承認と違う経路（`route`）の失敗とキューにいる PR の `precondition` 2（外さないので要求を足さない）、キューの待ち 2（PR・キューと事象）、キューへの登録 3（PR・キューと事象・登録）、直接マージの方式の断り 4（PR・キューと事象・方式 2）、`pull2` で断る・`MERGED` を見る 5（加えて要求の直前の読み直し）、直接マージ 7（PR・キューと事象・方式 2・要求の直前の読み直し・要求・要求の後の読み直し。要求が断られたときも同じ 7）。マージの実績の方式と受け取りの照合は ② の同じ読みの欄とローカルのファイルなので回数を足さない。今の従来の経路の直接マージ 4（PR・方式 2・要求）より 3 回多い（キューと事象の読み、要求の直前の読み直し、要求の後の読み直し）。要求の直前の読み直しは、宛先を最後に照らす読みと要求の間を 1 往復にするための 1 回で、方式の読みを ① より前へ移して省くと、マージ済み・待機中・照合の失敗でも方式を読む（2 回増える）ので採らない。偽の GitHub で呼び出しを数え、返りごとにこの回数と、そのうちの `GitHub.pull` の回数（直接マージの成功と要求の断りで 3、`pull2` で断る・`MERGED` を見るで 2、登録・待ち・マージ済み・照合の失敗で 1）をテストで縛る（マージ済み・待機中で方式を読まないこと、`pull2` と要求の間に呼び出しが無いこと、照合の経路で `dequeue` を呼ばないことを含む）。

**単位のキューの承認の受け渡し**（工程と手動の両方）: 単位のマージに `--queue-approved` を付けてよいかは、照合済みの承認の回答と単位の宛先（スプリントのブランチ）を結び付けた 1 つの値 `units_queue` から決める。単位の方式（`units.json` の `merge_method`）も同じ値の `method` から取る。承認の回答の事象には `queue` を載せず、`design-answer.json` の場所（世代ごとの `stage_dir`）を工程「実装」が探すこともしない。

1. **作る**: `progress/gate` に `units_queue(target: Path, answer: Path, sprint: str) -> UnitsQueue` を置く。中で `ci merge --target --answer` と同じ「回答との照合」の関数を打ち（通らなければ `precondition`。設計 PR のマージの後に打つので開き直さない）、記録の `sprint` が引数の `sprint` と同じかを確かめ（違えば `invalid`）、`{"approved": 記録の queue.units, "repo": 記録の repo, "sprint", "method": 記録の units_method, "parallel": 記録の parallel, "criteria": 記録の criteria, "issues": 記録の issues, "omitted": 記録の omitted, "files": 記録の files（パス → blob の SHA）, "target_sha256", "answer_sha256"}` を返す。`method`・`parallel`・`criteria`・`issues`・`omitted`・`files` は照合した同じ記録のバイト列から取るので、承認資料に載せた単位の方式・同時に流す本数の上限・受け入れ条件の中身・承認した計画の入力と同じ値になる（`unit_plans` の 1 の照合と `units.json` の `max` に使う）
2. **工程**: `design-sync`（`ndf progress design sync --target … --answer …`）が**取り込みの前に**これを打ち（照合に落ちれば何も取り込まない）、照合した記録の値で取り込みと push を済ませてから出力 `units_queue` を出す。工程「ドキュメントレビュー」の `outputs` に `units_queue`、`context.schema.json` に同じキー、工程「実装」（`implement-units.json`）の `inputs` に `units_queue` を足す。`_call_units` は `units_queue` を `unit_plans` へ渡す（`UnitGiven.queue`）
3. **手動**: `ndf progress units plans` に `--target <design-target.json> --answer <design-answer.json>`（2 つそろえて渡す。片方だけは `invalid`）を足し、同じ `units_queue` を打つ。`--from-stage` では文脈の `units_queue` を使う。どちらも無ければ `stopped`（`invalid`、「承認の記録と回答（--target --answer）か --from-stage が要る」）で止める。承認した入力の一覧と指紋が無い組み立ては、`unit_plans` の 1 の照合を打てないので許さない
4. **保存と再開**: `unit_plans` は `units_queue` を `units.json` の `queue` に書き、`queue.method` があればそれを `merge_method` に写す（`queue.sprint` が `units.json` の `sprint` と違えば何も書かずに `UnitsError`）。`queue` は指紋 `source` にも入れ、承認を取り直して値が変わったら上の「再計画で状態を引き継ぐ条件」に従う。`run_units`（工程の `_call_units` と手動の `units run` の共通の関数）は、`units.json` の `queue.approved` が真で `queue.sprint` が `units.json` の `sprint` と同じときだけ、単位の `ci merge` に `--queue-approved` を付ける。再開はいつも `units.json` から読むので、工程でも手動でも同じ根拠から同じ値になる

### 設計 PR の承認とマージ（`design-review`・`design-land`）

満たす決定: 1。満たす受け入れ条件: 1。工程「ドキュメントレビュー」（`design-approval`）のステップの中身である。

#### ブランチと作業場所

今の工程「作業場所の用意」が出すのは `worktree` と `branch` の 1 組（スプリントのブランチとその作業場所）で、後の工程もその作業場所で書く。設計 PR をスプリントへ入れるには、head と宛先を別のブランチにする必要があるので、次の 2 組に分ける。

| 組 | ブランチ | 作業場所 | 作る工程 | 使う工程 |
| --- | --- | --- | --- | --- |
| スプリント | `branch`（今のまま） | `worktree`（今のまま） | 作業場所の用意 | 要求・実装（単位の作業場所の起点と、最後の早送り）・その後の工程。設計の承認の後にここで承認済みのファイルを読む |
| 設計 | `design_branch` = `<branch>-design` | `design_worktree` = `.worktrees/<branch>-design` | 設計（`design-draft` の最初のステップが `ndf worktree create <branch>-design --from <remote>/<design_base>` で作る。既にあれば作り直さない） | 設計・詳細設計・計画・ドキュメント再構成・ドキュメントレビュー。設計 PR の head |

- 設計 PR の宛先 `design_base` は**宣言から決める**: `branch_strategy.pr_target("doc", sprint_branch=branch)`。`branch_strategy.sprint.doc_prs` が `sprint` ならスプリントのブランチ、`base` ならベースブランチ。`design-draft` はこの値を `base` として明示して PR を開き（`route.derived` の既定の `pr_target("sprint")` に任せない）、`design_base` を出力する。`design-land` の `--base` も同じ `design_base` を使うので、PR を開いた宛先と照らす宛先がずれない
- **設計ブランチの起点は宛先**: 設計ブランチは `<remote>/<design_base>` から切る（`doc_prs: sprint` ならスプリントの先端で今と同じ、`base` ならベースブランチの先端）。ベースに未マージのスプリント側のコミットは設計 PR の差分に入らず、設計承認でベースへ公開されない。`doc_prs: base` のとき、スプリント側の変更のうち設計 PR に入れるのは、工程「要求と受け入れ条件」が書いたスプリントの課題の要求仕様 `issues/issue-<番号>-requirements.md`（設計の worker が読み、承認者が設計と並べて見る）だけとする。`design-draft` は作業場所を作った直後に `git checkout <remote>/<branch> -- <そのパス>...`（スプリントのブランチにあるものだけ）で取り込み、1 つのコミット（「要求仕様をスプリントから取り込む」）にする。ほかのスプリント側の変更（コード・設定・ほかの文書）は入れない。`doc_prs: sprint` では起点がスプリントの先端なので取り込みは打たない
- 工程「詳細設計」「計画」「ドキュメント再構成」「ドキュメントレビュー」は、設計の作業場所で書く**新しい経路の工程の定義**（下の「工程の定義」の `design-detail-pr.json`・`plan-pr.json`・`document-rebuild-pr.json` と `design-approval.json`）だけが `worktree_input: "design_worktree"`（`ndf.schema.json` に足す。省けば今のまま `worktree`）を持ち、テンプレートの `worktree`・`branch` を設計の組から組む。`light`・`operation`・`documentation` が指す共有の `design-detail.json`・`plan.json`・`document-rebuild.json` は変えないので、`design_worktree` を出力しない従来の経路は今の `worktree` と出力契約のまま通る。`worktree_input` の文脈のキーが文脈に無ければ、工程は `worktree` へ黙って落とさず `invalid`（「工程 <名前> の作業場所 <キー> が文脈に無い」）で止める
- **マージの後に承認済みのファイルをスプリント側へ揃える**（ステップ `design-sync`。`ndf progress design sync --target <記録> --answer <回答>`）: スプリントの作業場所で次の順に打つ。工程「実装」はスプリントの作業場所の `collect` でこのファイルを読む。**照合は取り込みと push より前に済ませ、同期に使う値は照合した記録のバイト列からだけ取る**（設計 PR のマージから同期までの間に記録を差し替えられても、差し替え後の記録でスプリントへ push しない）
  0. **先に照合する**: `design-target.json`・`design-answer.json` をそれぞれ 1 回だけバイト列で読み、そのバイト列に「回答との照合」（`ci merge --target --answer` と同じ関数）を当て、記録の `sprint` が文脈の `branch`（手動では `--sprint`）と同じか、記録の `repo` がスプリントの作業場所の `<remote>` から決めた操作先（下の「操作先のリポジトリ」。取得先と push 先は同じ `<remote>`）と同じかを確かめる（`units_queue` の 1 と同じ照合。下の「単位のキューの承認の受け渡し」）。通らなければ何も取得・取り込み・push せずに `precondition`（マージの後なので開き直さない）。通れば、その読んだ記録から `repo`・`head`・`files`・`sprint` と `units_queue` を決め、以降の手順は記録を読み直さない
  1. 取り込みの前の HEAD を控え、`git fetch <remote> <design_base>` を打つ
  2. 取り込む: `doc_prs` が `sprint` なら `git merge --ff-only <remote>/<0 の sprint>`、`base` なら `git merge --no-edit <remote>/<design_base>`（今の部品 `base-sync` がスプリントの PR に打つのと同じ取り込み。衝突すれば `git merge --abort` で戻して `precondition`）
  3. **入力の集合と内容を照らす**: 取り込んだ後の HEAD に、`unit_plans` の 1 と**同じ関数** `approved_inputs` を当てる。取り込んだ後の HEAD を固定したコミットとして `collect`・`designed` が読む計画・単位のファイル・設計文書のパスの集合を求め（上の「検査と組み立ての読み方」。記録の `issues`・`omitted` で集める）、その集合が 0 の `files` のパスの集合と同じで、各パスの blob の SHA が 0 の `files` の値と同じかを確かめる。承認に無い計画のファイルが取り込みで増えた（`doc_prs: base` のベースに承認の後で対象の課題の計画が足された、を含む）・承認したファイルが消えた・変わった（スプリント側の既存の変更との自動の合成を含む）のどれも違いとする。違えば push せずに `git reset --keep <控えた HEAD>` で取り込みを手元から外し、`precondition`（「承認した計画の入力と違う: 追加 <パス>／削除 <パス>／変更 <パス>」）で止める。`plans` で初めて止まるのでなく、承認と違う入力をスプリントへ公開する前に止める。工程の文脈の `design_head` は工程の終わりに入る値なので、ここでは使わない
  4. 一致したときだけ、`base` なら `git push <remote> HEAD:refs/heads/<0 の sprint>`（`sprint` はマージでリモートのスプリントが既に進んでいるので push しない）。承認と違う計画をスプリントへ公開しない。push の後に 0 で決めた `units_queue` を出力する
- `doc_prs: base` を選んだプロジェクトも宣言を変えずに使える。マージ先は宣言のまま（ベースブランチ）で、スプリントへは `design-sync` の取り込みで届く。移行の手順は要らない

**スプリントのブランチは引数で明示する**: `doc_prs: base` では `--base` がベースブランチなので、ほかの引数から単位の宛先を決められない。そこで `--sprint`（必須。省けば `invalid`）でスプリントのブランチを渡し、記録の `sprint`・`queue.units`・`units_method` と承認資料の単位の宛先はこの値だけから作る。工程では、`worktree_input` を持つ工程の差し込みの `branch` が設計の組（`design_branch`）になるので、`invoke` は文脈の `branch`（スプリントのブランチ）を差し込み `sprint_branch` として別に渡す（`worktree_input` を持たない工程でも同じ値。`design-approval.json` の `inputs` は既に `branch` を持つ）。手動では supervisor が工程「作業場所の用意」の `branch` の値を渡す。`design target` は `--base` が `branch_strategy.pr_target("doc", sprint_branch=--sprint)` と同じかを確かめ、違えば記録を書かずに `invalid`（「設計 PR の宛先 <base> が --sprint <sprint> の宣言の宛先 <期待> と違う」）。`design-sync` の `units_queue` も同じ値（文脈の `branch`）と記録の `sprint` を照らすどれかが通らなければ記録を書かずに `stopped`（`stale`。結果の失敗・用途の違いは `invalid`）を返し、① へ戻る。

1. **結果の成功と用途**: `ci.json` が `tool: ci` の `ci watch` の結果で `status: ok`、`metrics.pr` が `--pr` と同じ（別の PR の CI・失敗・待ちの結果を通さない）。`units-check.json` が `tool: plan` の `units check` の結果で `status: ok`、`metrics.docs` が真（`--docs` 付きで表まで照らした）
2. **4 つの SHA**: `units-check.json` の `metrics.head`（単位を確かめた HEAD）、ローカルの HEAD、`gh pr view <design_pr> --json headRefOid`（PR の HEAD）、`ci.json` の `instance`（CI を判定した PR の HEAD）が同じ。今の `ci_cli._report` は失敗のときだけ `instance` に SHA を入れるので、**成功の結果にも判定に使った `pull.head_sha` を `instance` に載せる**（Task 7。`ci watch` の成功を読むほかの呼び手は `instance` を読まないので振る舞いは変わらない）。違えば（⑤ の後に push があった、PR を別の HEAD で更新した）`stale`
3. **検査がそのコミットの内容を読んだこと**: `units-check.json` の `metrics.files` のすべてのパスの blob の SHA を、`git ls-tree -z <head> -- <パス>...` の **1 回の起動**で取り（ファイルの数によらず CLI の起動は 1 回。引数の長さが OS の上限を超えるときだけ、上限に収まる束に分けて打つ）、各パスの SHA が記録の値と同じかを照らす（出力に無いパス＝コミットに無いのに読んだファイルがあれば違いとする）。ファイルごとに `git rev-parse` を打たない。`metrics.files` の SHA は、`units check` が**解析したバイト列そのもの**の blob の SHA なので（下の「検査と組み立ての読み方」）、この照合で表と記録した blob が同じ内容から生まれたことが言える

**検査と組み立ての読み方**（`units check`・`unit_plans`・`design-sync` の 3 の照合が共有する `units_files.snapshot(repo) -> Snapshot`）: 検査の途中で作業ツリーのファイルが更新され、照合の前に元へ戻っても、表と記録した blob が食い違わないよう、作業ツリーでなく**固定したコミット**から読む。

1. 始めに `git rev-parse HEAD` を 1 回打ち、その SHA を `Snapshot.head` に固定する（`units check` の `metrics.head` はこの値で、検査の後に HEAD を読み直さない）
2. `git ls-tree -r -z <head> -- issues/` を 1 回打ち、`collect` のファイルの列挙（`PLAN_DOC`・`DESIGN_DOC` に当たるパス）と、パスの検査の「ディレクトリでない」「リポジトリの外を指さない」をこの出力の種類で決める（`tree` はディレクトリ、モード `120000` のシンボリックリンクは断る）。まだ無いファイル（新設）はコミットに無いので、今までどおり通す
3. 読むと決めたパスのすべてを `git cat-file --batch` の 1 回の起動へ `<head>:<パス>` で渡し、応答の `<blob の SHA> blob <長さ>` と続くバイト列を受け取る。`load`・`designed`・`render --check` が解析するのはこのバイト列だけで、`metrics.files`（`unit_plans` では `approved_inputs` が照らす値）に書く SHA はこの応答の SHA である。作業ツリーのファイルを開かないので、読んだ後にファイルが変わっても解析した内容と記録した SHA はずれない
4. `units check` は、加えて作業ツリーが固定したコミットと違う（読んだパスと `issues/` の `git status --porcelain -z --untracked-files=all -- issues/` の 1 回の起動で、変更か未追跡の行が出る）なら `stopped`（`invalid`、「<パス> がコミットされていない。コミットしてから確かめる」）を返す。これは書き手がコミットし忘れた変更を確かめたつもりにならないための案内で、承認の証明は 1〜3 が持つ

外部の起動は内容の数によらず `rev-parse`・`ls-tree`・`cat-file`・`status` の 4 回（`unit_plans` と `design-sync` は `status` を打たないので 3 回）

`method`・`units_method` は `route.declared_merge_methods(repo, [design_base, --sprint])` の返りのそれぞれの宛先の値（上の「マージの方式の決め方」）、`queue` は上の「要求の時点の宛先」の `merge_queues([design_base, --sprint])`、`since` は書いた時刻。キューを持つ宛先ごとに、そのキューの方式を同じ宛先の方式（`queue.design` なら `method`、`queue.units` なら `units_method`）と照らす。`design target` の外部の起動は、ローカルの HEAD 1・remote の URL の読み 1（記録の `repo`）・PR の HEAD 1・blob の一括の読み 1・キューの読み 1（宛先の数によらず別名で 1 本）・方式の読み（宛先ごとの ruleset ＋リポジトリの設定 1。宛先が同じなら 2、違えば 3）に固定し、計画・単位のファイル・設計文書の数に比例して増えない（テストで、宛先が同じ場合と違う場合のそれぞれの起動の回数を縛る）。承認の記録はこの `head` と組なので、承認した PR の HEAD・CI が通った HEAD・単位を確かめた HEAD とその内容は 1 つに結び付き、`design-land` が同じ組を照らす。

**承認資料**: `asking.py` は設計承認ゲートの資料に、操作先のリポジトリ（記録の `repo`）・設計 PR の URL・`head`・宛先・単位の宛先（記録の `sprint`。`--sprint` で渡した値）・宛先ごとの方式（`method`・`units_method`）・宛先ごとのマージの経路と宛先を固定できない窓の例外（`queue` の真の宛先はキューの例外の文、偽の宛先は直接マージの例外の文。どちらも上の「要求の時点の宛先」の表の文で、承認するとその経路だけを許す。その宛先の方式が `squash` か `rebase` なら、加えて「キューがマージした後は squash と rebase を見分けられないので、承認の後にキューの方式をこの 2 つの間で変えられても止まらない」。上の「マージの実績の方式」）と、`units-check.json` の**スプリント全体の**単位の表を載せる。表は `unit` の項目の `seq`・名前・ファイル・実行順・マージの順（実装が使う番号）・並列の相手（`parallel_with`）・先に要る単位・課題・条件・行数・触るファイル（`touches`。並列の相手と重ならないことを承認者が見る）と、同時に流す本数の上限（`metrics.parallel`）である。実装計画の文書の表はファイルの中で番号を振るので、承認者が実装の順を見るのはこの資料の表とする（2 ファイルに独立な単位が 1 つずつあれば、文書ではどちらも「マージの順 1」だが、資料では `seq` 1・2 の並列の相手どうしとして出る）。

**手で流す経路（#3908 でテンプレートが動かない間）**: supervisor が工程の外で同じ検査・停止・照合を打つ。手順は Task 9 で `references/approval-request.md` に書き、どの手順も工程と同じコマンドなので結果は同じになる

1. 設計の作業場所で最終の HEAD を push した後に `ndf plan units check --issue <課題>... [--omitted <課題>]... --docs --out <dir>/units-check.json`。`ok` でなければ承認を求めず、書き手に直させてからやり直す（`units check` は固定したコミットを読むので、手元にコミットしていない変更を残したまま打つと、上の「検査と組み立ての読み方」の 4 のとおり止まる）
2. `ndf ci watch --pr <design_pr> --conflict ... | tee <dir>/ci.json` が `ok` の後に `ndf progress design target ...`（上と同じ引数）。`stopped` なら 1 からやり直す
3. 承認資料は `ndf progress design ask --target <dir>/design-target.json --out <dir>/design-material.md` で作る（`progress/command.py`。工程の `asking.py` と同じ関数で、同じ照合をしてから資料を作り、`<dir>/design-material.json` に 2 つの SHA-256 を書く）。今の `ndf answer ask` はゲート待ちを返すだけで資料を読まず回答も保存しないので、この経路では使わない
4. 人が回答した後に、supervisor がその回答を `ndf progress design answer --material <dir>/design-material.json --approved --out <dir>/design-answer.json` で記録する（工程の `answering.py` と同じ関数。打つ時点で記録と検査の結果の SHA-256 が資料と同じかを確かめ、違えば書かずに `stopped`（`stale`）で 1 からやり直す）。人の回答が無いときは打たない
5. `ndf ci merge --target <dir>/design-target.json --answer <dir>/design-answer.json`（上の「回答との照合」で、提示した記録に対する回答との一致をマージの要求の前に機械で確かめる）。`refused`・`base_conflict` なら 1 から（承認を取り直す）。`precondition`（`metrics.merged: true`）ならマージ済みなので 1 へ戻らず、戻すかを人に返す。`precondition`（`metrics.in_queue: true`）ならキューから外すかを人に返し、外した後に同じ argv を打ち直す（`refused` になれば 1 から）。`precondition`（`metrics.refusal: risk`）なら 1 へ戻らず、人が PR 本文の残リスクの行を決めた後に同じ argv を打ち直す。受け取りは `<dir>/design-receipt.json`
6. `ndf progress design sync --target <dir>/design-target.json --answer <dir>/design-answer.json --sprint <スプリントのブランチ>` で、照合を先に済ませてからスプリント側へ揃え、`<dir>/units-queue.json` に `units_queue`（上の「単位のキューの承認の受け渡し」）を書く。単位は `ndf progress units plans … --target <dir>/design-target.json --answer <dir>/design-answer.json` で組む

#### 承認を無効にする遷移

今の進行管理は、完了した工程を再実行せず（`decide` は最初の未完了の行を選ぶ）、失敗した工程は失敗したステップから再開する。また `gate/answering.py` は課題を外した回答を承認として記録し、文脈の `issues` を書き換え、外した課題をスプリントを持つレーンの順番表の次の行へ運ぶ（`_carry` → `lane.carry_issues`。同じトランザクション）。回答の後に対象が変わって回答を待ちへ戻すとき（`recheck`）は、文脈の `issues` を回答の前へ戻し（`_undropped`）、運んだ行を取り消す（`_uncarry`）。この運び方と取り消し方は変えない。古い承認と工程の出力を使わずに戻すため、行を開き直す事象を足す。遷移の読みと書きの本体は新設の `progress/reopen.py` に置き、`run.py` と `answering.py` はそれを呼ぶ（地図の「既存のファイルには呼び出しと登録だけを足す」）。

- **事象 `reopened`**（`progress/reopen.py`。`run.py` が呼ぶ）: 工程の行を `pending` に戻し、その工程の**世代**を 1 つ進める。世代は新しく作らず、今の `StepProgress.generation`（承認ゲートの変更要求で 1 つ進み、ステップを初めから流し直す値）をそのまま使う。`_SEES` に `reopened` の読み手を足し、変更要求の `_answered` と同じく `generation` を 1 つ進めて `done`・`waiting`・`answer` を捨て、数え始め `anchor` を `reopened` の番号へ移す（世代は、その行の変更要求と `reopened` の数の和）。ステップの進み・待ち・回答（古い承認）は捨てられる。文脈（`View.context`）は、開き直した工程が出した出力をその `reopened` より後に書き直されるまで重ねない（`design_head` など古い出力を後の工程が読まない）
- **世代ごとの保存先**: ステップの作業ディレクトリは今のまま、`_run_step` が `work_root(...) / <工程の id> / step_location(...)` で組む `work_root/<機械>/<工程の id>/<ステップ>-g<世代>` とする（`step_location` が返すのは `<ステップ>-g<世代>` で、今の形が既に世代を含む）。`{{stage_dir}}` は同じ規則で `work_root/<機械>/<工程の id>/shared-g<世代>` にする（新設なので前の場所は無い）。保存先の形を変えないので、**進行中のスプリントの互換の規則は要らない**: この変更の前に保存された工程は `reopened` を持たず、世代は変更要求の数だけで今と同じ値になり、事象が参照する従来の実行の記録を同じ場所から読む（途中まで済んだプランを最初から起動しない、待ちの記録を見失わない）。`reopened` の後は世代が進むので新しい場所に切り替わる。テストは、`reopened` を持たない保存済みの事象の列で `step_location` が今と同じ文字列を返すこと、`reopened` の後に `-g<世代+1>` になることを縛る。ステップの id `shared` は `{{stage_dir}}` と重なるので `ndf.schema.json` で断る（今の定義に `shared` という id のステップは無い）。今の `plan_argv` は同じ保存先・同じ HEAD の完了したプランの結果を再利用するが、開き直した後は保存先が新しく空なので、宛先の変更など HEAD が動かない理由で開き直しても `docs-review` を打ち直し、承認の記録・資料・回答も作り直す。古い世代のファイルは消さずに残す（読む経路が無い。後片付けは今の工程の作業ディレクトリと同じ）
- **`restart_on`**（工程の定義のメタデータ。`design-approval.json` に `{"design-gate": ["stale_approval"], "design-merge": ["stale_approval"]}`）: ステップがこの種類で失敗したら、`run.py` は `reopen.py` を呼んでその工程に `reopened` を書く。`precondition` は載せないので、`design-merge` がマージ済みの PR で返す `precondition` では開き直さない。次の起動は工程の最初のステップ（`docs-review`）から流れ、レビュー・MVV 判定・承認をやり直す。`design-gate` は承認資料を作るときの照合の不一致（下の表）を `stale_approval` で失敗するので、今の「失敗したステップから再開する」規則で同じ資料作りを打ち直し続けず、`docs-review` から検査をやり直す
- **回答の時点の照合の不一致**: `answering.py` は回答を記録する前に、`design-material.json` の 2 つの SHA-256 が今の `design-target.json`・`units-check.json` のバイト列の SHA-256 と同じかを確かめる。違えば回答を承認として記録せず（`design-answer.json` も書かない）、回答の事象の代わりに「ドキュメントレビュー」の行へ `reopened` を書く（`restart_on` と同じ世代の更新。理由「資料を作った後に承認の記録か検査の結果が変わった」）。次の起動は `docs-review` から流れ、資料を作り直して承認を求め直す
- **課題セットは工程の出力と独立**: 今の `answering.py` は課題を外した結果の `issues` を承認ゲートの工程の出力として書くので、その工程を `reopened` にすると除外が一緒に捨てられ得る。そこで課題セットの変更を工程に属さない事象 `issues_set`（`{"issues": [...], "excluded": [...], "reason": "excluded" | "restored"}`）として書き、`View.context` は `issues` と `excluded` を `reopened` に関係なく最後の `issues_set` から取る（無ければ工程「要求と受け入れ条件」までの `issues` と空の `excluded`）。`reopened` が捨てるのは工程の出力だけで、`issues_set` は捨てない。書く順は `issues_set` → `reopened`（同じ書き込みの中）
- **レーンの順番表の行との関係**: `issues_set` は文脈の課題セットだけを持ち、外した課題をレーンの次の行へ運ぶのは今のまま `_carry`、取り消すのは `_uncarry` である。外す回答では、`answering.answer` の 1 つのトランザクションの中で `_carry`（レーンの行）→ `issues_set` → `reopened` の順に書く（`_carry` が断れば何も書かない）。待ちへ戻すときは、`recheck` の 1 回の書き込みで待ちへ戻す事象 → `issues_set`（`reason: restored`）→ `reopened` を書き、その書き込みの後処理で `_uncarry` を打つ（今の `_undropped` と `_uncarry` の組と同じ順）。`excluded` は文脈の値で、レーンの行の中身（運んだ課題）とは別に持つ
- **除外の集合は累積する**: `issues_set` の `excluded` は直近の回答で外した課題でなく、**スプリントで今外れている課題のすべて**とする。`answering.py` は今の文脈の `issues`・`excluded`（最後の `issues_set`）から次の値を作る: 追加の除外は `issues` = 今の `issues` − 外した課題、`excluded` = 今の `excluded` ∪ 外した課題（並びは外した順）。戻しは `issues` = 今の `issues` ∪ 戻した課題、`excluded` = 今の `excluded` − 戻した課題（一部だけ戻せば残りは `excluded` に残る）。たとえば #10 を外し、次の承認で #11 を外すと、2 回目の `excluded` は `[10, 11]` で、2 回目の「計画」の `drop.json` と後段の検査は #10 も扱う（書き直しで #10 への参照が戻れば止まる）。`design-drop` は同じ課題を何度扱っても結果が同じ（既に取り除いた文書・行は差分に無いので触らない）

| 起きること | 遷移 | 捨てるもの |
| --- | --- | --- |
| 承認で課題を外した（`answering.py`） | 今の `_carry` で外した課題をレーンの次の行へ運び、同じ書き込みで `issues_set`（`issues` = 今の `issues` − 外した課題、`excluded` = 今の `excluded` ∪ 外した課題。上の「除外の集合は累積する」）と、「計画」「ドキュメント再構成」「ドキュメントレビュー」の 3 行に `reopened`。回答は承認として消費しない（`design-merge` を打たない）。次の「計画」は `issues` に**残った課題だけ**、`excluded` に外した課題を受け取り、最初のステップ `design-drop`（下）で外した課題の文書と設計の結果を設計 PR から取り除いてから、残った課題で実装計画と単位のファイルを書き直す（外した課題のタスク・条件・依存を除く。統合の計画なら名前の番号の並びも書き直す） | 3 つの工程の出力（`plan_omitted`・`rebuild_findings`・`design_head`）と、ドキュメントレビューの承認の記録・資料・回答（世代が進むので読まれない） |
| `design-gate` が資料を作るときに記録と検査の結果が食い違った（`stale_approval`） | `restart_on` で「ドキュメントレビュー」に `reopened`。次は `docs-review` から（同じ資料作りを打ち直さない） | 承認の記録・資料 |
| 回答を記録するときに資料の SHA-256 と今の記録・検査の結果が食い違った（`answering.py`） | 回答を記録せず、同じ書き込みで「ドキュメントレビュー」に `reopened`。次は `docs-review` から | 承認の記録・資料（回答は記録されない） |
| `design-merge` が `OPEN` の PR の照合で断られた・衝突した（`stale_approval`） | `restart_on` で「ドキュメントレビュー」に `reopened`。次は `docs-review` から | 承認の記録・資料・回答 |
| `design-merge` が `MERGED` の PR を成功にしなかった（`precondition`。承認外の宛先・この実行の要求と結び付けられない（承認していないキューの経路を含む）・承認の後の宛先の変更・承認と違うか確かめられない方式でマージされた）か、キューにいる PR を断った（`precondition`、`in_queue`） | `precondition` で止める（`stale_approval` に写さず、開き直さない）。人が戻すかを決め、決めた後に conductor が `reopened` を書くか工程を進める | なし |
| 回答の後に対象が変わって待ちへ戻した（今の `recheck` と `_undropped`。戻す回答が課題を外していたとき） | `recheck` の中で、待ちへ戻す事象と同じ書き込みで `issues_set`（`issues` = 今の `issues` ∪ 戻した課題、`excluded` = 今の `excluded` − 戻した課題、`reason: restored`）と、「設計」から「ドキュメントレビュー」までの 5 行に `reopened`。次の「設計」は**戻した後の `issues` のすべて**を受け取り（まだ外れている課題は `excluded` に残り、次の「計画」の `design-drop` が引き続き扱う）、`design-drop` で取り除いた戻した課題の設計を書き直す（既にある設計の作業場所と設計 PR をそのまま使う。`design-draft` は作業場所・PR があれば作り直さない）。書き込みの後に `_uncarry` で運んだレーンの行を取り消す | 5 つの工程の出力と、承認の記録・資料・回答 |

**外した課題の文書を取り除く**（ステップ `design-drop`。`ndf progress design drop`。新しい経路の「計画」`plan-pr.json` の最初のステップ。`excluded` が空なら何もせずに通り、空の指示のファイルを書く）: 設計の作業場所で次を行い、1 つのコミット（「外した課題 #<番号> の設計を取り除く」）にして push する。**変えてよいのは、このスプリントが設計 PR で追加・変更した差分だけ**とする。起点は設計 PR の宛先との分岐点 `git merge-base <remote>/<design_base> HEAD`（取得はしない。工程「設計」が作業場所を作るときに取得済み）で、起点に既にあった内容（前のスプリントまでの要求仕様・設計文書）は消さない。

1. **先に全部を決める（書き換えない）**: 作業場所が clean（`git status --porcelain` が空）でなければ `precondition` で止める。起点からの差分 `git diff --name-status <起点> HEAD -- issues/` を 1 回だけ読み、外した課題に関わるファイルごとに次の扱いを決める。残った課題の行が「マージする」で外した課題を統合先に持つかの検査（当たれば `precondition`、「#<残った課題> の統合先 #<外した課題> を外した」。人が扱いを決め直す）もここで行い、当たれば何も書き換えずに止める
   - 名前の番号の並び（`DESIGN_DOC`・`PLAN_DOC` と要求仕様・詳細設計の名前）が**外した課題だけ**からなるファイルで、起点に無い（差分で `A`）: `git rm`
   - 同じく外した課題だけのファイルで、起点にあり、このスプリントで変えた（`M`）: `git checkout <起点> -- <パス>` で起点の内容へ戻す（消さない）
   - 同じく外した課題だけのファイルで、このスプリントで変えていない（差分に無い）: 触らない
   - 名前に残った課題と外した課題の両方を含む統合の文書: 「設計の結果」の表の外した課題の行を、**起点のその文書の同じ課題の行と同じにする**。起点に無い行は消し、起点にあった行は起点の内容（扱い・統合先・触るファイルの列を含む行の全文）へ戻し、起点にあってこのスプリントで消した行は起点の位置へ戻す。このスプリントでその行の扱いや統合先を変えていても、除外の後に変更が PR に残らない。起点にその文書が無ければ、外した課題の行はすべて消す。本文の外した課題の記述は機械で消さず、下の 3 の指示のファイルに載せる
2. **書き換えて 1 つのコミットにする**: 1 の扱いを当て、コミットして push する。書き換え・コミット・push の途中で失敗したら、`git reset --hard <始めの HEAD>` で作業場所を始めの HEAD に戻してから失敗を返す（始めに clean を確かめたので、捨てるのはこの手順の編集だけ。push の前に戻すので、途中の編集が設計 PR に残らない）
3. **次のステップへの受け渡し**: 結果を `{{stage_dir}}/drop.json`（`{"excluded": [...]`（文脈の累積した `excluded` のすべて）`, "base": <起点の SHA>, "removed": [パス], "restored": [パス], "rows": [{"path", "issue", "action": "removed" | "restored"}], "rewrite": [{"path", "issues": [外した課題]}]}`）に書き、同じ `items` を結果にも載せる。`implementation-plan` のテンプレートに差し込み `drop_file`（`params.json`。既定は空の文字列）を足し、空でなければ worker の指示に「`<drop_file>` の `rewrite` の文書の本文から、`issues` の課題の記述を取り除く。外した課題の番号を計画・単位のファイル・統合の文書の本文に残さない」を加える。今の `_run_step` は前のステップの `items` を入力に入れないので、`plan-pr.json` の `plan` ステップの `with` に `"values": {"drop_file": "{{stage_dir}}/drop.json"}` を書き、`invoke` が `{{stage_dir}}` を同じ工程・同じ世代の保存先に置き換えて渡す（ファイルが無ければ `invalid`。`design-drop` が終わっていない）。`light`・`operation`・`documentation` の `plan.json` は `drop_file` を渡さないので空のまま今と同じ
4. **残りの検査**: `docs-review` の再レビューは 2 の差分を含む HEAD を読む。`units check --from-stage` は文脈の `excluded` と、`drop.json` を受け取り（`design-drop` が出力 `drop_file` に `drop.json` のパスを出し、工程「計画」の `outputs` に `drop_file`、`context.schema.json` に同じキー、工程「ドキュメントレビュー」の `inputs` に `drop_file` を足す。`NDF_STAGE_INPUT` の `drop_file` から読む。`excluded` が空なら空の `drop.json` を指す）、次のどれかが残れば止める（`stopped`（`invalid`）、「外した #<番号> が <パス> に残る」）: 外した課題を名前の番号に含む計画・単位のファイル（起点に無いもの）、外した課題の `tasks[].issue`・`criteria`、**外した課題の「設計の結果」の行**: 文書ごとに、HEAD の外した課題の行の並びが起点のその文書の同じ課題の行の並びと全文で一致しないもの（起点に無い行が残る、起点にあった行の扱い・統合先・触るファイルが変わっている、起点にあった行が無い。`design_results` で読んだ値でなく行の文字列で照らす。起点に文書が無ければ行が 1 つでもあれば当たる）、**本文**: 対象の文書を `drop.json` の `rewrite` のパスに限らず、**最終の HEAD の差分から列挙する**。`git diff -M --name-status <起点> HEAD -- issues/` と `git diff -M -U0 <起点> HEAD -- issues/` を 1 回ずつ打ち（文書の数によらず起動は 2 回）、追加・変更・改名の後のパスが設計文書（`DESIGN_DOC`。詳細設計を含む）か計画の文書（`PLAN_DOC` の `.md`）のものすべてについて、起点から足した行（`+` の行。改名は改名前の内容との差分だけを数えるので、起点にあった記述は足した行にならない）に、外した課題の番号の参照 `#<番号>`（後ろが数字でないもの）があるもの。除外の後に統合の文書の名前から課題の番号を外して改名しても（`issue-10-11-design.md` → `issue-10-design.md`）、改名先の本文が検査に入る。`rewrite` は worker への指示にだけ使い、検査の範囲を決めない。起点にあった記述は数えないので、前のスプリントの文書が外した課題に触れていても止まらない。worker が統合の文書の本文を消し残しても、承認の前に機械で止まる

変更の無い経路（レビューが収束し CI が通り、衝突が無い）では、承認は `design-gate` の 1 回だけである。

### 工程の定義（`contracts/workflow/`）

## 異常系の処理

| 起きること | 扱い |
| --- | --- |
| 単位のファイルが壊れている（JSON・スキーマ） | `check`・`plans` は `stopped`（`invalid`）。工程「ドキュメントレビュー」の `units check` で止まり、修正の worker が直して push する |
| 単位の違反（U1〜U6）・表の食い違い | `check` は案を添えて `stopped`。`plans` は何も書かない。工程「実装」は失敗し、実装を始めない |
| 新しい形の実装計画に単位のファイルが無い | `stopped`（`invalid`、「実装計画があるのに単位のファイルが無い」）。設計承認の前に止まる |
| 宣言の誤り（`target_lines >= max_lines`・形の違い） | `stopped`（`invalid`、理由に `.ndf/project.json` の `workflow.review_units`）。`invoke._project` は今のまま `WORKFLOW_SCHEMA` で断る |
| 単位のファイルが無い課題（実装計画を省いた・旧い形） | 課題 1 つを 1 単位（`single`）。行数を知らないので U6・W1 を当てず、`check` が省いた・旧い形であることを報告する |
| 承認の後に設計 PR の HEAD が変わる | マージせずに止まり、レビューから打ち直す（承認の記録は使わない） |
| 承認した設計 PR を閉じて開き直した・宛先を変えた（番号・ブランチ・宛先・HEAD が同じままの再オープンを含む） | `ci merge` が承認の記録の `since` より後の `REOPENED_EVENT`・`BASE_REF_CHANGED_EVENT` か宛先の違いで `refused`。`stale_approval` で「ドキュメントレビュー」を開き直し、レビューから打ち直す。既にマージされていれば `precondition` で止め、開き直さない |
| 照合の後、要求までの間に宛先が変わった | 直接マージは `pull2` で見つければ要求を送らずに `refused`、要求の後の読み直しで見つければ `precondition`。キューは再開の照合で見つけ、キューの中なら外さずに `precondition`（`in_queue`）、マージ済みなら `precondition`（`merged`）。マージ済みの `precondition` では開き直さず（設計 PR）・`blocked` にし（単位）、次の実行順へ進まず戻す判断を人に返す。直接マージ・キューのどちらの経路も、宛先を固定できない窓を承認資料に載せて承認した例外としてだけ流す |
| 承認の後に宛先のキューを有効にした・外した（承認した経路と要求の時点の経路が違う） | 要求を送らずに `refused`（`queue_unapproved` か `route`）。設計 PR は `stale_approval` で今の経路について承認を取り直し、単位は `blocked` |
| キューへ登録した後にキューの方式を変えられ、次の照合より先にマージされた | 打ち直しの ② でマージの実績の方式を照らし、`merge` と `squash`・`rebase` の間の違いか確かめられなければ `precondition`（開き直さず人に返す）。`squash` と `rebase` の間の変更は見分けられない例外として承認資料に載る |
| 承認の後にキューを有効にして人がマージし、打ち直しの前に無効へ戻した・人が別の方式で手でマージした | この実行の要求の受け取り（`--receipt`）と結び付かないので `precondition`（`merged`）。今のキューの設定で経路を決めない |
| 照合の後に人が同じ PR をキューへ入れ直した・キューにいる PR の照合が落ちた | GitHub は登録を条件に外せないので、照合の経路は `dequeue` を呼ばず `precondition`（`in_queue`）で人に返す。設計 PR は開き直さず、単位は `blocked` |
| キューへ登録した後に本文へ未決の残リスクが足された | ② でキューにいると分かるので `precondition`（`in_queue`）。キューに残る PR を見落として承認を取り直さない |
| 直接マージの要求が断られた後、または要求の直前の読み直しで初めて `MERGED` を見た | この実行の要求の `merge_sha` が無いので `precondition`（`merged`）。宛先・ブランチ・HEAD が同じでも成功にしない |
| 本文に決めていない「マージの前に決める」残リスクがある | 照合の経路は要求を送らずに `precondition`（`metrics.refusal: risk`。今の `_preflight` と同じ判定）。設計 PR は開き直さず、単位は `blocked`（`cause: risk`）。人が本文の行を決めた後に同じ argv を打ち直せば続く（レビュー・承認をやり直さない） |
| 宣言の方式が許されない | 照合の経路も要求を送らずに `refused`（今の `_method_refusal` と同じ。キューにいれば `precondition`）。単位は `blocked` で人に返す（レビューをやり直さない） |
| 照合の後に方式を読む間に、同じ HEAD のまま PR を閉じて開き直した | `pull2`（`recheck`）の `REOPENED_EVENT` で要求を送らずに `refused`（`reopened`）。API は 5 回 |
| 照合の経路の直接マージが 405 で断られた（`pull2` の後にキューを有効にした） | キューへ切り替えず（`_enqueue` を打たない）、読み直した PR で `refused`（`queue_unapproved`）。受け取りは `route: direct` のまま `merge_sha` が無いので、後でマージされても成功にしない |
| この実行の登録を人がキューから外し、同じ HEAD のまま手でマージした | 受け取りの `requested_at` より後の `REMOVED_FROM_MERGE_QUEUE_EVENT` で `precondition`（`merged`） |
| キューにいる間に違反を見つけて `precondition`（`in_queue`）で止めた後、人が外す前にキューがマージした | 受け取りの `violation` で `precondition`（`merged`）。同期へ進まない |
| 単位の PR の HEAD がレビュー済みと違う・衝突した | 記録を `stale` にし、その単位のプランだけを `--resume --from` でレビュー（か取り込み）から打ち直して記録の HEAD を書き換える。2 回目は `blocked` で人に返す |
| JSON だけの計画・区間の印の欠けた計画・このスプリントで書いた印の無い計画 | `stopped`（`invalid`）。設計承認の前に止まる |
| 設計の結果で「マージする」「閉じる」の課題が計画やタスクにある | `stopped`（`invalid`）。設計承認の前に止まる |
| 受け入れ条件の番号が課題に無い・どの単位にも割り当たらない条件がある | U2 で `stopped`。設計承認の前に止まる |
| 正規形でない・ディレクトリ・リポジトリの外を指すパス | `stopped`（`invalid`、パスとタスク）。設計承認の前に止まる |
| 設計の結果の表の扱いが空欄・許容値の外、「マージする」に統合先が無い | `check`・`plans` が `stopped`（`invalid`、文書のパスと課題の番号）。設計承認の前に止まり、単位を作らない |
| 実装計画も省く判断も無い課題 | `stopped`（`invalid`、「#<番号> の実装計画が無く、省く判断も無い」）。設計承認の前に止まる |
| 分け方の案を機械で作れない（条件の無い準備のタスクが大きい・別のファイルの単位と同じファイルを触る） | `check` が `split` の `resplit` と `note` を返して `stopped`。書き手がタスクを切り直す |
| 承認で課題を外した | 承認として扱わず工程「計画」へ戻り、`design-drop` で外した課題の文書と設計の結果を設計 PR から取り除き、残った課題で計画を書き直してから承認を求め直す。外した課題は工程の出力の開き直しで復元されない（`issues_set`） |
| 承認資料を作るときに検査の結果が記録と違う・回答と違う記録でマージを求めた | 資料を作らずに `stale_approval`／`ci merge` が要求を送らずに `refused`。工程は「ドキュメントレビュー」を開き直す |
| 宛先がマージキューを持つのに承認でその例外を認めていない | 登録を送らずに `refused`。設計 PR は承認を取り直し、単位は `blocked` |
| 宣言のマージの方式が宛先で許されない・許可を読めない | 記録を書かずに止める（`invalid`／`precondition`）。別の方式へ替えない |
| `design-sync` の取り込みで承認したファイルが変わる | push せずに取り込みを手元から外して `precondition` |
| 工程「実装」の再開で単位の計画が変わった | 実行の記録が無ければ組み立て直し、あれば `precondition` で人に返す（記録を別の単位に当てない） |
| 実装の途中で止まる（キュー・マージ・マージキューの待ち） | 打ち直すと、マージ済みの単位を飛ばし、記録の状態から続ける。キューから外れた PR はマージを要求し直す |
| 最後のマージの後にスプリントの worktree を早送りできない | `precondition` で止まる（`gathered` へ進まない） |
