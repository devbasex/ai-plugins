# #3603 の決定の記録

設計文書は [issue-3603-design.md](issue-3603-design.md) にある。

## 決定の記録

### 決定 1: 送り手の手順に依らずに設計承認の依頼で届けるため、設計承認の依頼に組むかを `request-ask` の中で決める

1 スプリントのレーンの設計承認の問いは、すべて問いの hook が `parallel.py request-ask` へ渡す。台帳へ書く手前の 1 か所で「設計承認の依頼に組めるか」を決めれば、レーンの conductor の手順に依らずに `gate1` で届く。hook は今どおり問いを渡すだけにし、設計 PR とスプリントを読む処理は `request-ask` の子プロセスに置く。子プロセスは今も hook の残りの秒を上限に打たれており、過ぎれば問いを通す（I10）。依頼の中身は開発ループのレーンと同じ `request_gate1` で組み、MVV 判定・古い依頼の整理・マージは今の `gate1` の処理がそのまま掛かる。

設計のプランが承認ゲートで終わった時点に `supervise.py` が依頼を送る形は採らない。conductor はその後も `ndf-gate:1` の問いを出すため、hook の側でも同じ依頼へ寄せる判定が要り、送り手が 2 か所になる。hook の中で依頼を組む形も採らない。hook はプロセスの起動のたびに読まれ、スプリントと PR を読む処理を持つと、上限の秒を越えたときの扱いが子プロセスの上限と二重になる。

- 作り方: 自前で作る
- 比べた候補: STD1

根拠: Value 3 / Value 11（MVV 版 7）

### 決定 2: 設計 PR を特定できない問いへ承認を当てないため、問いの文が名指す設計 PR だけを設計承認の依頼にする

区分 `ndf-gate:1` には、設計 PR の承認でない問い（実装の途中で設計の前提が崩れたときの判断、設計承認ゲートの委任の承認）も入る。`request-ask` は、レーンのスプリントで承認ゲートで終わった設計のプランの設計 PR の番号を集め、問いの文と選択肢に書かれた PR の URL か `#<番号>` と突き合わせる。一致した PR だけを依頼にし、一致しなければ今どおり `ask` で送る。GitHub の課題と PR は番号を共有するため、`#<番号>` が課題と PR を取り違えることは無い。

承認ゲートで終わった設計 PR があれば問いの文を見ずに依頼にする形は採らない。そのとき同じレーンが別の `ndf-gate:1` の問いを出すと、問いが設計 PR の承認にすり替わり、元の問いが人へ届かない（受け入れ条件 9）。

根拠: Value 1 / Value 13（MVV 版 7）

### 決定 3: 古い先頭への承認でマージしないため、名指した設計 PR が開いていないか先頭を読めなければ `ask` で送る

依頼の id と承認した先頭（`stamp`）は、問いを受けた時点の設計 PR の先頭の SHA から作る。`gh pr view` で状態と先頭を 1 回で読み、PR が開いていないか読めなければ依頼に組まない。マージ済みの設計 PR の問いは、設計の前提に関わる別の判断である見込みが高く、`ask` のまま人へ届けるのが安全である。

先頭を読めないときに `0` を並べた先頭で依頼を組む形（開発ループのレーンの `lane_gate1` の扱い）は採らない。承認の答えは `no_stamp` でマージされず、承認してもマージされない今の事象が別の形で残る。`ask` で送れば、少なくとも今と同じ扱いで人へ届く。

根拠: Value 7 / Value 13（MVV 版 7）

### 決定 4: 承認の答えをレーンの手で写さないため、答えを読む副命令 `parallel.py design-answer` を足す

起き直したレーンは、保留の手順が引継ぎ文書に書かせた `design-answer <計画> <依頼> --state <スプリント状態>` を打つ。副命令は答えを読み、利用者が設計承認ゲートで答えたときに conductor が書く承認ゲートの記録（`approval-request.md` の「利用者が承認ゲートで答えたら」の表）を、答えの `by`（`user` か `mvv`）で書き、続きの 1 行を返す。答えの読み方とスプリント状態への書き方がスクリプトに固まり、レーンごとに書き方がぶれない。

`parallel.py await` を設計承認の依頼の答えにも広げる形は採らない。`await` はリリースの依頼の記録のファイルを入力に取り、答えの値（`released`・`rejected`・`failed`）と終了コードもリリースのものである。conductor が答えを読んで `sprint-state.py gate` を自分で打つ形も採らない。答えの `by` とマージの結果を書き移す手順が conductor に残り、書き忘れると設計 PR のマージのプランが承認ゲートで止まる。

根拠: Value 3（MVV 版 7）

### 決定 5: 承認の後にマージされた設計 PR でプランを止めないため、マージ済みの設計 PR は承認の確かめを通す

`answer --approved` は答えの前に設計 PR をマージする。レーンが起き直すと、続く設計 PR のマージのプランの最初のステップ（`design-approved`）が承認ラベルか利用者の承認の記録を求める。MVV 判定の承認（`by: mvv`）の記録は利用者の承認として数えないため、マージ済みでも承認ゲートで止まる。`design-approved` は PR の状態も読み、マージ済みなら通す。このステップが守るのはマージの操作であり、マージが済んだ PR には守る操作が残っていない。

MVV 判定の承認の記録を利用者の承認として数える形は採らない。承認ラベルとスプリント状態の記録の意味（利用者の承認）が変わり、まだ開いている設計 PR を MVV 判定の記録だけでマージする道ができる。

根拠: Value 1 / Value 3（MVV 版 7）

### 決定 6: MVV 判定で承認したのにマージできなかった設計を人へ届けるため、同じ先頭の問い直しを印 `returned` の新しい依頼にする

`by: mvv` で承認し、マージが緑でない・衝突などで失敗すると、設計 PR は開いたまま残り、レーンは設計 PR のマージのプランで同じ問いを出し直す。同じ先頭なら同じ id になり、答え済みとして返り続ける。`request-ask` は、同じ id の依頼に承認の答えがあり PR が開いたままなら、id に接尾辞 `-r<連番>` を付け、印 `returned` と答えに載ったマージの結果の理由を足した新しい依頼にする。印 `returned` の依頼には `mvv_mark` が `eligible: false` を返し、MVV 判定による承認が掛からない。開発ループのレーンが同じ場面で利用者へ戻す扱い（#2507 の決定 9）と同じ形になる。

`by: user` の承認では新しい依頼にしない。`design-answer` が利用者の承認の記録を書き、設計 PR のマージのプランがレーンの側でマージし直すため、同じ問いは出ない。

根拠: Value 1（MVV 版 7）

### 決定 7: 入力の検証で落ちずに問いの対象を届けるため、対象を問いの文の対象の行に書く

区分つきの問いの最初の問いの文に `対象: <ブランチ名>` か `対象: #<番号>` の 1 行を置き、`request-ask` が最後の対象の行を読む。`AskUserQuestion` の入力は対象を載せる欄を持たない（STD1。`metadata` は `source` だけを通す）。問いの文は検証で落ちず、人が読む問いにも対象が見える。行の形を固定するため、言い回しの違いに依らずに読める。#3597 の決定 6 が採らなかった「問いの文から読む形」は、言い回しから対象を推す形であり、固定の 1 行を読むこの形とは別である。先端は今までの決まりどおり `request-ask` が求め、一時レーンに書き写させない。

`header` に対象を書く形は採らない。`header` は短い語として表示され（STD1）、長いブランチ名が収まる保証が無い。問いの前に `parallel.py` へ対象を登録する形も採らない。登録と問いが別の操作になり、登録が残ったまま別の問いが出ると、戻せない操作の答えが別の対象へ当たる（C4）。区分（`metadata.source`）の値に対象を足す形も採らない。区分の形の判定（`ask_policy`）が形に合わない区分として問いを止める。

- 作り方: 自前で作る
- 比べた候補: STD1

根拠: Value 3 / C4（MVV 版 7）

### 決定 8: 同じ問いを人へ 2 回届けないため、前の答えを hook の拒否の理由で返す

同じ問いの鍵は（一時レーンの名前・区分・問いの対象）にする。前の依頼に答えがあれば、`request-ask` は `reused` の行を書いて前の id と答えを返し、hook は答えを載せた `deny` を返す。一時レーンはその答えで操作を進める。答えが無ければ前の id で保留の手順を返す。同じキーの再送に最初の結果へ沿った応答を返す扱い（STD2）と同じ形である。`reused` の行を書けないときは答えを使わずに新しい依頼を送り、後から追えない引き継ぎを作らない。

hook が `allow` と `updatedInput` の `answers` で問いに自動で答える形（STD1）は採らない。レーンの中の Claude Code の版でこの振る舞いを確かめておらず、効かなかったときは問いが人のいないレーンの画面で開いたまま止まる。`deny` の理由が AI へ届くことは今の保留の手順で確かめてある。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1 / STD2

根拠: Value 1 / Value 3 / C4（MVV 版 7）

### 決定 9: 起き直した一時レーンが前の答えを自分でも読めるよう、`asked` に対象を持つ `ask` の答えの中身を載せる

`parallel.py helper` の `asked` は、今は `ask` の答えに `answered: true` だけを付ける（対象が無く、前の答えを今の問いへ当てられなかったため）。問いの対象を持つ `ask` には、`gate2` と同じく答えの `result`・`choice` を載せる。対象を持たない `ask` は今どおり `answered: true` だけにする。判定の正本は `request-ask` の同じ問いの判定であり、`asked` は一時レーンが問いの前に読める、同じ判定の結果である。

根拠: Value 3（MVV 版 7）
