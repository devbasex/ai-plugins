## 目的

- **進め方（`pace`）を 3 つに整理し、それぞれの意味とフローを定義し直す。** 今の文書は `fast` を `normal` との差分で書いており、何のための進め方かが読めない
  - `normal`: **ウォーターフォール。** 各工程（設計レビュー・テスト・リファクタリング・コードレビュー・完了判定）を配布の前に検証し、設計と本番への配布で人の承認を取って進める
  - `auto`: **`normal` と同じ工程で、承認だけを MVV に基づいて半自動にする。** MVV 判定が「従う」なら自動で通し、ほかは人が承認する
  - `fast`: **スタートアップ的。** 実践投入（開発版の配布と利用）の中で検証しながら、MVV に基づいて自動で開発を進める。検査（リファクタリング・コードレビュー）は配布の後にトリガーでまとめて通す
- 進め方（`pace`）に `auto` を足す。工程の並び・検査の時機・Pull Request の単位は `normal` と同じまま、承認ゲート 1（設計 Pull Request のマージ）と承認ゲート 2（本番系へ届く操作）だけを MVV 判定（`mvv-gate.py`）で自動にする
- MVV 判定は #1366 のプロジェクト MVV（NDF の共通原則 → プロジェクト MVV → ミッション MVV の順）に従う。「従う」でレッドラインに当たらないときだけ自動で通し、「反する疑い」「判定できない」は人へ戻す（共通原則: AI が取れる行動は「進める / 止めて人へ戻す」の 2 つだけ）
- `fast` が持つ「トリガーで通す検査」「課題ごとの Pull Request が develop へ直接入る」は `auto` に持ち込まない。`fast` の仕組みは変えず、文書の書き方だけを「実践投入の中で検証する流れ」として書き直す

## 前提

- 前提 1: MVV 判定の仕組みは既存の `mvv-gate.py`（#1078）と #1366 で足すプロジェクト MVV の節をそのまま使い、判定の規則（従う / 従わない / 判定できない・レッドライン）は変えない
- 前提 2: `auto` を使ってよい条件は `fast` の 5 つ（`references/pace.md` の「使ってよい条件」: 開発版のチャネルがある・インストール確認のコマンドがある・`.ndf/pace.json` が許している・モードが対象に入る・MVV が承認済み）に準じる。ゲート 2 は開発版のインストール確認の結果を判定の材料にするため、開発版のチャネルとインストール確認のコマンドを外さない。MVV は、承認済みのプロジェクト MVV があればミッション MVV は要らない（#1366 の決定 12 と同じ）
- 前提 3: 3 つの進め方は次の表で定義し、`auto` は `normal` の列の承認の行だけを MVV 判定にしたものである。`fast` の「実践投入」は、実装の Pull Request が develop（開発版のチャネル。マージされた変更がそのまま載る）へ入ることを指す。検査はその後、次の開発版のリリースの前にトリガーが立ったときだけ通る（今の `references/pace.md` の「プランのステージ」の振る舞いを変えない）

| | `normal` | `auto` | `fast` |
| --- | --- | --- | --- |
| 何のための進め方か | ウォーターフォール。各工程を検証し、人の承認を取って進める | `normal` と同じ工程で、承認だけを MVV で半自動にする | スタートアップ的。実践投入の中で検証しながら MVV で自動に進める |
| 検証の場所 | 各工程で、配布の前（設計レビュー・テスト・リファクタリング・コードレビュー・完了判定） | 同じ | 実践投入の中（開発版の配布と利用）。検査は配布の後にトリガーでまとめて |
| 承認 | 人が 2 回（設計・本番への配布） | MVV 判定が「従う」なら自動、ほかは人 | MVV 判定で自動（ほかは人） |
| 判定と配布の単位 | ミッション（1 つの版として出す課題のまとまり） | ミッション | 課題ごとの Pull Request（develop へ直接入り、開発版も課題ごと。ここがスピードの本質） |
| 確定仕様化・振り返り | 各工程の順に | 同じ | ミッションの終わりにまとめて |
| 向く場面 | 影響が大きい・戻しにくい変更、複数の課題を 1 版にまとめる | `normal` と同じ場面で、人の待ち時間を減らしたい | 小さく出して実践で確かめられる変更、開発版の利用者が近い |

- 前提 4: この課題の実装は #1366 の実装がマージされた後に始める（プロジェクト MVV の節と `mission-state.py` の覆しの記録を使うため）。設計は並行して進める
- 前提 5: `auto` でも承認ゲートの数は 2 つのまま増やさない。判定が人へ戻したときの提示は `approval-request.md` の形で、判定の理由と根拠の項目を添える

## 対象範囲

含む:
- `development-workflow` の「進め方」の節と `references/pace.md` を、3 つの進め方の定義（何のため・検証の場所・承認・単位・向く場面）とフロー（進め方ごとに 1 つ）で書き直す。`fast` を `normal` との差分でなく、実践投入の中で検証する流れとして書く
- `supervise.py new mission --pace auto`（使ってよい条件の判定、ステージの並び、ゲート 1・2 のステップを MVV 判定へ替える、判定が従うときに次のステージへ続ける）
- `development-workflow` の判定結果の出力（`pace: auto`）と `references/pace.md` の表・条件・記録の読み方
- `.ndf/pace.json` の宣言（`auto` の許可）
- 判定と覆しの記録（既存の `mvv-gate.jsonl`・ミッション状態ファイルの承認ゲートの記録・#1366 の覆しの記録）
- ai-plugins で `auto` のミッションを 1 本通す実測

含まない:
- `mvv-gate.py` の判定の規則の変更
- `fast` の条件・トリガー・ステージの変更（文書の書き直しだけ）
- 承認ゲートの追加・削除
