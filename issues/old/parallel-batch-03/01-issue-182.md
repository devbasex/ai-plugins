# 担当 A — pytest のテストを CI で実行する（#182）

- issue: https://github.com/devbasex/ai-plugins/issues/182
- ブランチ: `feature/issue-182-pytest-in-ci`
- モード: `light`（本番の振る舞いも本番コードの構造も変えない。継続的統合の設定を足すだけ）
- 工程: `worktree` → 限定的な検証 → `quality-gates` → `pr` → `merged` → `release`

`light` のため、要求と受け入れ条件・設計・`cross-review` の工程は通らない。設計文書も作らない。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| 継続的統合 | GitHub Actions。`.github/workflows/` の各ファイルが 1 つの単位 |
| ワークフロー | `.github/workflows/` の 1 ファイル。名前が Pull Request の確認欄に並ぶ |
| ジョブ | ワークフローの中で独立に動く単位。1 つが落ちても他は最後まで走る |
| 束 | pytest を 1 回起動したときに収集されるテストの集まり |
| 起点 | pytest が設定ファイルと相対パスの基準にするディレクトリ（`rootdir`） |
| 収集 | pytest がテスト関数を見つける段階。ここで除外されたものは実行も報告もされない |

## 何を解決するか

pytest で書かれたテストが、継続的統合のどのジョブからも実行されていない。テストが落ちる変更を
Pull Request がそのまま受け入れる。手元で実行した担当だけが気づくため、実行しなかった変更は
気づかれずにマージへ進む。

このバッチの他の 3 担当は、いずれもテストを持つ領域（`plugins/ndf/skills/cross-review/` と
`scripts/tests/`）を書き換える。テストが継続的統合に載っていれば、3 件の Pull Request は
互いの変更を壊していないことを機械的に示せる。

### 束が 2 つに分かれる理由

1 回の起動でまとめると、収集の段階で止まる。

```console
$ uv run --with pytest pytest plugins/playwright-kit -q
Defining 'pytest_plugins' in a non-top-level conftest is no longer supported:
It affects the entire test suite instead of just below the conftest as expected.
  /work/ai-plugins/plugins/playwright-kit/skills/playwright-kit-ops/tests/conftest.py
Please move it to a top level conftest file at the rootdir:
  /work/ai-plugins
1 error in 0.05s
```

`playwright-kit-ops` は自分の `pyproject.toml` に `[tool.pytest.ini_options]` を持ち、
起点がそのディレクトリになることを前提にしている。起点をリポジトリの根へ置くと、その前提が
崩れて収集が止まる。**そのため、ジョブを 2 つに分ける。**

### 対象の指定は「全体から別の束を外す」形で足りる

`.worktrees/` の下には 72 個のテストファイルがあるが、上の全体対象の実行では収集されていない。
pytest は既定で先頭が `.` のディレクトリへ降りない。件数が明示指定（`scripts/tests plugins/ndf`）
と一致することがその根拠になる。

```console
$ find .worktrees -name 'test_*.py' | wc -l
72
$ uv run --with pytest pytest scripts/tests plugins/ndf -q | tail -1
1397 passed in 48.86s
```

### `jq` が無いと、テストが実行されないまま終了コード 0 になる

`worktree` と `development-workflow` と `scripts/tests` のテストは `bash` / `jq` / `git` を
使う。無いときは収集の対象から外れるか読み飛ばされ、終了コードは 0 のままになる。

```console
$ PATH=<bash git python3 uv だけを置いたディレクトリ> \
    uv run --with pytest pytest scripts/tests plugins/ndf/skills/worktree -q
ssssssssssssssssssssssssssssssssssssssssssssssssssssssssssssssssssss.... [ 67%]
........................ssssssss...                                      [100%]
31 passed, 76 skipped in 0.63s
```

`worktree` の 658 件は 1 件も収集されず、`scripts/tests` の 76 件は読み飛ばされる。それでも
終了コードは 0 である。**継続的統合に載せるときは、この状態を失敗として扱う手当てが要る。**

`jq` は実行環境に含まれている。

```console
$ gh api repos/actions/runner-images/contents/images/ubuntu/Ubuntu2404-Readme.md \
    --jq '.content' | base64 -d | grep '^| jq'
| jq                     | 1.7.1-3ubuntu0.24.04.2       |
```

いま入っていることと、これからも入り続けることは別である。確認の手順を 1 ステップ置く。

### `uv` は実行環境に含まれていない

## 決めたこと

### `uv` を使う。導入は pip で行う

このリポジトリの手順書は、テストの実行を `uv run --with pytest pytest <パス> -q` と定めている
（`issues/parallel-batch-03/00-overview.md`）。継続的統合が別の手順で動かすと、手元で通った
ものが継続的統合で落ちたときに、原因が変更なのか手順の差なのかを切り分けることになる。
**手元と同じコマンドを書く。**

別の束は自分の `pyproject.toml` に依存関係を持つ。`uv run pytest` はその解決と仮想環境の
用意を 1 コマンドで行う。上の実測はこの形で 179 件が通っている。

導入は `astral-sh/setup-uv` ではなく `python3 -m pip install uv` にする。

| 方法 | 採否 | 理由 |
| --- | --- | --- |
| `python3 -m pip install uv` | 採用 | 既存 4 本が使う action は `actions/*` だけである。この形なら追加の提供元を増やさない |
| `astral-sh/setup-uv@v10.0.1` | 不採用 | 移動する major タグが無く、版を上げ続ける手間が増える |
| `pip install pytest`（`uv` を使わない） | 不採用 | 手元の手順と別のコマンドになる。別の束は `pip install -e .` が別途要る |

`astral-sh/setup-uv` に移動タグが無いことは実測している。

```console
$ gh api repos/astral-sh/setup-uv/git/matching-refs/tags/v10 --jq '.[].ref'
refs/tags/v10.0.0
refs/tags/v10.0.1
```

`v10` そのものは無く、公開されているのは正確な版だけである。

### 対象の指定は 2 つ

| 束 | 起点 | コマンド | 件数 |
| --- | --- | --- | ---: |
| 主 | リポジトリの根 | `uv run --with pytest pytest . --ignore=plugins/playwright-kit -q` | 1397 |
| 別 | `plugins/playwright-kit/skills/playwright-kit-ops` | `uv run pytest` | 179 |

主の束を明示のパス（`scripts/tests plugins/ndf`）ではなく全体対象にするのは、テストの置き場所が
今後増えたときに、載せ忘れが起きないようにするためである。上の実測のとおり、いまはどちらの
書き方でも 1397 件で一致する。

`00-overview.md` が書いている手元の手順（`uv run --with pytest pytest scripts/tests plugins/ndf -q`）は
そのまま残す。この指示書では変更しない。

### ジョブは 2 つに分ける

| ジョブ | 対象 |
| --- | --- |
| `pytest` | 主の束 |
| `pytest-playwright-kit` | 別の束 |

起点が違うため 1 回の起動にまとめられない（上の実測）。ジョブを分けると、確認欄にどちらの束が
落ちたかが名前で出る。並列に動くため、全体の所要時間は長いほうに揃う。既存の
`runtime-plugin-validate.yml` も 4 つの確認を 4 ジョブへ分けており、その書き方に合わせる。

### 新しいワークフローを 1 本足す

`runtime-plugin-validate.yml` へジョブを足す形も取れるが、そちらは名前のとおり配布物と説明文書の
突き合わせを扱う。テストは別の関心事であり、確認欄に「Python tests」と出るほうが、落ちたときに
何が起きたかが読み取れる。**新しいファイル `.github/workflows/pytest.yml` を作る。**

起動の条件は既存 2 本に合わせる。テストは `scripts/` と `plugins/` の中身を読むため、この 2 つと
ワークフロー自身を対象にする。

## やること

1. 作業ツリーを用意する（`/ndf:worktree`）。

   ```bash
   main_dir=/work/ai-plugins
   git -C "$main_dir" fetch origin
   git -C "$main_dir" worktree add -b feature/issue-182-pytest-in-ci \
     "$main_dir/.worktrees/feature/issue-182-pytest-in-ci" origin/main
   cd "$main_dir/.worktrees/feature/issue-182-pytest-in-ci"
   ```

2. `.github/workflows/pytest.yml` を作る。骨子は次のとおり。

   ```yaml
   name: Python tests

   on:
     pull_request:
       paths:
         - ".github/workflows/pytest.yml"
         - "plugins/**"
         - "scripts/**"
     push:
       branches:
         - main
         - develop
         - "release/**"
       paths:
         - ".github/workflows/pytest.yml"
         - "plugins/**"
         - "scripts/**"

   jobs:
     pytest:
       runs-on: ubuntu-latest
       steps:
         - uses: actions/checkout@v4
         - uses: actions/setup-python@v5
           with:
             python-version: "3.x"
         - name: Install uv
           run: python3 -m pip install --upgrade uv
         # 無いと収集されないまま終了コード 0 で終わるため、先に確かめる
         - name: Check the commands the tests need
           run: |
             for c in bash jq git; do
               command -v "$c" >/dev/null || { echo "missing command: $c" >&2; exit 1; }
             done
         - run: uv run --with pytest pytest . --ignore=plugins/playwright-kit -q

     pytest-playwright-kit:
       runs-on: ubuntu-latest
       defaults:
         run:
           working-directory: plugins/playwright-kit/skills/playwright-kit-ops
       steps:
         - uses: actions/checkout@v4
         - uses: actions/setup-python@v5
           with:
             python-version: "3.x"
         - name: Install uv
           run: python3 -m pip install --upgrade uv
         # 起点をこのディレクトリへ置く。pyproject.toml が対象と表示を決める
         - run: uv run pytest
   ```

   `defaults.run.working-directory` が効くのは `run` のステップだけで、`actions/checkout` は
   リポジトリの根へ展開する。

3. 手元で 2 つの束をそれぞれ実行し、いずれも通ることを確かめる。

   ```bash
   uv run --with pytest pytest . --ignore=plugins/playwright-kit -q
   (cd plugins/playwright-kit/skills/playwright-kit-ops && uv run pytest)
   ```

4. ワークフローの書式を確かめる。`.github/workflows/` 以外を変更しないことも合わせて確認する。

   ```bash
   uv run --with pyyaml python3 -c "
   import glob, yaml
   for p in sorted(glob.glob('.github/workflows/*.yml')):
       yaml.safe_load(open(p, encoding='utf-8'))
       print('ok', p)
   "
   git status --porcelain
   ```

5. `quality-gates` に従い、実行したコマンドと出力を証跡として残す。

6. `pr` で Pull Request を作る（宛先は `main`。`develop` はまだ無いため `--base` は指定しない）。
   本文に `Closes #182` を書く。

7. 継続的統合の 2 ジョブが緑になることを確かめる。件数が実測（1397 と 179）と一致することを
   ログで確認する。**一致しない場合は、収集の段階で外れているものがある。**

   ```bash
   gh pr checks <PR番号>
   ```

8. マージ後に `merged` で後片付けをし、`release` の要否を判断する。継続的統合の設定だけの
   変更のため配布物に差分は出ない。差分が無ければ `release` 自身が飛ばす。

## 完了条件

- [ ] `.github/workflows/pytest.yml` があり、`pytest` と `pytest-playwright-kit` の 2 ジョブを持つ
- [ ] Pull Request の確認欄に 2 ジョブが並び、どちらも緑になる
- [ ] `pytest` ジョブのログに `1397 passed` と同じ件数が出る（このバッチの他の担当がテストを足した後は、その分だけ増える）
- [ ] `pytest-playwright-kit` ジョブのログに `179 passed` と同じ件数が出る
- [ ] `bash` / `jq` / `git` のいずれかが無い実行環境では、テストの実行前にジョブが落ちる
- [ ] 起動の条件が `plugins/**` と `scripts/**` と自ファイルを対象にしている
- [ ] 変更したファイルが `.github/workflows/pytest.yml` の 1 件だけである（`git status --porcelain` で確認）
- [ ] 既存 4 本のワークフローを変更していない
- [ ] 範囲外と判断した事柄が `out-of-scope` で issue になっている

## 範囲外とするもの

| 事柄 | 理由 |
| --- | --- |
| `plugins/playwright-kit/.../tests/conftest.py` の `pytest_plugins` の置き場所 | `plugins/` は他の担当が触る。またテストの構造を変える変更で、`light` の範囲を超える。**起票の対象**（下記） |
| リポジトリの根への `pytest.ini` / `pyproject.toml` の新設 | いまは各束が自分の設定で完結している。根へ設定を置くと 2 つの束の起点が競合する。#182 が求めているのは「継続的統合で実行されること」である |
| `jq` が無いときに終了コード 0 になる仕組みそのもの | 直すには各 `conftest.py` の `collect_ignore_glob` と `skipif` を見直すことになる。`plugins/` と `scripts/` は他の担当が触る。**起票の対象**（下記） |
| 実行時間の短縮（`pytest-xdist` による並列化） | いまの所要は主の束が 48 秒で、待ち時間として支障が出ていない。速くする前に、まず実行されている状態を作る |
| 依存関係の取得結果の再利用（`actions/cache`） | 別の束は毎回 70 MB ほど取得する（`playwright` 43.8 MiB / `imageio-ffmpeg` 24.4 MiB / `pygments` 1.2 MiB）。まず動く形を入れ、所要が問題になったときに足す |
| テストの網羅率の計測 | #182 の対象ではない |
| `00-overview.md` が書く手元の手順の変更 | 手元の手順は現状のままで通る。この指示書はその手順を変えない |
| 既存 4 本のワークフローの起動条件の見直し | #182 の対象ではない |

### 起票する（`out-of-scope`）

着手したその場で issue にする。判断は 3 択（起票する / 範囲内へ入れる / 起票しない）に限る。

1. **起点をリポジトリの根へ置くと `playwright-kit-ops` のテストが収集できない。**
   `tests/conftest.py` の `pytest_plugins` が原因である。リポジトリ全体を 1 回で回せないため、
   継続的統合のジョブが 2 つに分かれる。起票する。

2. **`bash` / `jq` / `git` が無い実行環境で、テストが実行されないまま終了コード 0 になる。**
   実測で `worktree` の 658 件が 1 件も収集されず、`scripts/tests` の 76 件が読み飛ばされた。
   継続的統合の側はコマンドの確認で塞ぐが、手元で実行したときは同じ状態が起きる。起票する。

3. **issue #182 の本文が挙げる置き場所と件数が現状と合っていない**（4 箇所・378 件 → 7 箇所・1576 件）。
   起票しない。理由: この指示書の「現状（実測）」が現在の値を記録しており、#182 は本担当の
   Pull Request で閉じるため。
