# 292: Skill 本文から自リポジトリ前提を外す

NDF の Skill は任意のリポジトリに対して実行される。`cross-review` の最終スイープの手順は、
修正を push した後に通す検証として `claude plugin validate` を名指ししている。この命令は
`.claude-plugin/plugin.json` を持つリポジトリでしか成立せず、それ以外のリポジトリでは
担当したサブエージェントが自分の判断で別の検証へ振り替える。振り替えた事実は完了報告に
残らない。この文書は「どう直すか」だけを扱う。全体の境界と着手の順序は
[00-overview.md](00-overview.md) にある。

**モードは `standard` である。** 変更するのは Skill の本文と 1 本の新しい検査で、
永続データも公開インタフェースも持たない。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| 対象リポジトリ | Skill を実行する先のリポジトリ。ai-plugins 自身とは限らない |
| 自リポジトリ前提 | 対象リポジトリが ai-plugins であるときにだけ成立する操作・パス・値を、条件を付けずに実行させる記述 |
| Skill 本文 | `SKILL.md` と、そこから読ませる `docs/` `references/` `prompts/` の Markdown |
| 最終スイープ | `cross-review` の Step 7.5。収束ループを抜けた後に未解決の指摘を片付ける工程 |
| 検証 | 変更が壊れていないことを push の前に確かめる実行。テストと静的解析とビルドを指す |
| 配布物の形 | `release` が持つ 5 分類（パッケージ・プラグイン / サービス / デスクトップ / モバイル / 手順） |
| 公開する Skill | `plugins/ndf/manifests/*-skills.txt` のいずれかに載っている Skill |

## 受け入れ条件

| 番号 | 条件 |
| --- | --- |
| A1 | 最終スイープの手順に、特定のランタイムでしか成立しない検証コマンドが残っていない |
| A2 | 最終スイープの手順が、対象リポジトリから検証コマンドを決める手順を持つ |
| A3 | 決められないときに推測で実行せず、実行しなかったことを記録する経路が手順に書かれている |
| A4 | 実行した検証コマンドと終了コードを残す先が、結果ファイルの項目として定義されている |
| A5 | ai-plugins 自身でこの手順を辿ると `claude plugin validate` を含む検証に到達する |
| A6 | Skill 執筆規約に、対象リポジトリを仮定しないための書き方が節として置かれている |
| A7 | 公開する Skill の本文に自リポジトリ前提が入ったとき、`scripts/check-skill-repo-assumptions.py` が失敗する |
| A8 | 検査の除外は、対象と理由の対で宣言され、対象が実在しないときに検査自体が失敗する |
| A9 | 棚卸しの網羅性が、走査したコマンド・走査した本数・ヒット数で示されている |
| A10 | `uv run --with pytest pytest scripts/tests plugins/ndf -q` がリポジトリの根から通る |

対象範囲に含まないもの:

- `state.py` の処理（担当 B の範囲。結果ファイルへ足す項目は `verify-sweep` が読まない）
- `cross-review/SKILL.md`（担当 E の範囲）
- `cross-review/docs/01-state-and-review.md`（担当 E の範囲）
- 継続的統合の照会と収束判定（担当 B の範囲）
- 対象リポジトリの検証コマンドを宣言ファイルで受け取る仕組み（範囲外として起票する）

## 設計

### 最終スイープの検証を対象リポジトリから決める

`cross-review/docs/02-fix-and-rotation.md` の Step 7.5 のサブエージェント向けプロンプト
（339〜369 行）のうち、362 行の 1 行を次の形へ置き換える。

> **修正で push した場合は、対象リポジトリの検証を 1 度通すこと。** 何を実行するかは
> 対象リポジトリを見て決める。**コマンドを推測して組み立てない。**
>
> 1. 実行手段を探す。`Makefile` の `test` / `lint` / `check` ターゲット、`package.json` の
>    `scripts`、`pyproject.toml` の `[tool.pytest.ini_options]`、`composer.json` の
>    `scripts`、継続的統合の定義（`.github/workflows/*.yml`）が実行しているコマンド
> 2. 見つかったもののうち、**変更したファイルに掛かるもの**を実行する
> 3. 1 つも見つからないときは実行しない
>
> 実行したコマンドと終了コード、実行しなかった場合はその理由を、結果ファイルの
> `verification` へ書く。

探す順序を「テスト → 静的解析 → 継続的統合の定義」ではなく**並べて提示する**のは、
どれが最も強い検証かがリポジトリで変わるためである。`devbase` の継続的統合は
`python -m compileall` と ruff と shellcheck を実行し、テストは実行しない
（`grep -nE 'run:|pytest' /work/devbase/.github/workflows/ci.yml` → 3 行、pytest は 0 行）。
一方でテストランナーの設定は存在する（`grep -n '\[tool.pytest' /work/devbase/pyproject.toml`
→ 22 行目）。順序を固定すると、この 2 つのどちらかを取り逃がす。

**ai-plugins ではこの手順が `claude plugin validate` へ到達する**（受け入れ条件 A5）。
手順 1 が `.github/workflows/runtime-plugin-validate.yml` の 4 ジョブを返し、そのうち
`bash scripts/validate-runtime-plugins.sh` が `claude plugin validate` を実行する
（`scripts/validate-runtime-plugins.sh:410`）。実測でも `plugins/ndf` を渡した実行は
`✔ Validation passed` を返し、終了コードは 0 である。

### 結果ファイルへ残すもの

結果ファイル `$TMP_DIR/sweep-pr<STATE_PR>-result.json` に項目を 1 つ足す。

```json
"verification": {
  "commands": [{"command": "bash scripts/validate-runtime-plugins.sh", "exit": 0}],
  "skipped_reason": null
}
```

- 検証を実行したときは `commands` に実行順で並べ、`skipped_reason` を `null` にする
- 実行手段が見つからなかったときは `commands` を空にし、`skipped_reason` に何を探して
  見つからなかったかを書く
- push しなかったラウンドでは `commands` を空にし、`skipped_reason` に「push なし」と書く

**この項目は `state.py verify-sweep` が読まない。** `verify-sweep` は結果ファイルから
`remaining_open` / `remaining_reason` / `resolved` / `fixed_in_sweep` / `commit` の 5 つだけを
取り出し、未知の項目を落とす（`plugins/ndf/skills/cross-review/scripts/state.py:2273-2296`）。
記録は結果ファイルとサブエージェントの最終メッセージに残り、メインが完了報告へ書き写す。
Step 8 の「メインはこれに `resolved` / `fixed_in_sweep` を添えて最終報告する」の一文へ
`verification` を足す。

**申告のままで、GitHub 側と突き合わせる相手を持たない。** `remaining_open` のような
突き合わせを入れるには `state.py` を変える必要があり、そのファイルは担当 B の範囲にある。

### 起点ブランチの決め打ちを外す

`retrospective/SKILL.md:138` の `BASE=develop` を、他の 4 Skill と同じ解決へ置き換える。

```bash
BASE=$(jq -r 'select(.version == 1) | .base_branch | select(type == "string")' \
  .ndf/worktree.json 2>/dev/null)
[ -n "$BASE" ] || BASE=$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null | sed 's|^origin/||')
```

ai-plugins で実行すると 1 行目が `develop` を返す。宣言を持たないリポジトリでは 2 行目が
`main` を返す（`git symbolic-ref --short refs/remotes/origin/HEAD` の実測値は `origin/main`）。
まとまりの配布を対象にする場合は正式版のチャネルを使うため、その旨のコメントは残す。

### 再発防止の規約

`plugins/ndf/skills/README.md` へ「対象リポジトリを仮定しない」の節を置く。規約の本文は
次の 4 点である。

| 項目 | 内容 |
| --- | --- |
| 適用対象 | 公開する Skill の本文が、対象リポジトリに対して実行を指示する記述 |
| 求めること | 対象リポジトリに無い場合の振る舞いを、コマンドとセットで書く |
| 書き方 | 探して決める（見つけ方と、見つからないときの振る舞いを書く）か、形で分岐する（`release/references/form-*.md` のように、その形のときだけ読む参照へ置く） |
| 適用外 | 記述の主題が NDF 自身の配置・配布であるもの |

冒頭の「本文の書き方は各 `SKILL.md` に委ね、規約は発動と配布に関わる部分だけを扱う」を
「本文のうち、実行先のリポジトリに依存する部分は規約が扱う」へ改める。

置き場所を `README.md` にするのは、Skill を書く人がその場で読み返す文書だからである。
`AGENTS.md` と `CLAUDE.md` はこのリポジトリの開発全般を扱い、Skill を書くときに開かれない。
`markdown-writing` は利用者のリポジトリの文書にも効くため、NDF の Skill だけに効く規約を
入れると適用範囲が広がりすぎる。

### 機械の検査

`scripts/check-skill-repo-assumptions.py` を新設し、継続的統合のワークフロー
`.github/workflows/runtime-plugin-validate.yml` へジョブを 1 つ足す。

| 項目 | 内容 |
| --- | --- |
| 走査の範囲 | `manifests/*-skills.txt` の和集合が指す Skill の `*.md`（`tests/` を除く） |
| 検知する語 | 走査 1 の `PAT` と同じ 13 語 |
| 除外 | ファイルと理由の対。宣言した対象が実在しないときは検査自体が失敗する |
| 終了コード | ヒットが除外の外にあれば 1、無ければ 0 |

除外に載せるのは棚卸しで対象外と判定した 4 ファイルである。

| 除外するファイル | 理由 |
| --- | --- |
| `release/references/form-package-plugin.md` | 配布物の形がプラグインのときだけ読む参照 |
| `development-workflow/references/projects-tracking.md` | NDF 自身の複製先の説明 |
| `official-skills-autoloader/SKILL.md` | NDF 自身の配布先の指定 |
| `out-of-scope/references/issue-target.md` | NDF の実体を持つ clone を見分ける手順 |

`check-skill-frontmatter.py` へ足さないのは、そちらの対象が frontmatter であり、本文の語を
見る検査は入力も出力も別だからである（同スクリプトの docstring が individual / aggregate /
cross の 3 種を frontmatter の項目として定義している）。

## 決定の記録

### 決定 1: 検証コマンドを名指しせず、探し方を書く

対象リポジトリごとに検証手段は変わるため、名指しでは成立しないリポジトリが必ず残る。
**探し方を書けば、成立しないときに「見つからなかった」という結果が出る。** 名指しでは
「実行できなかった」だけが残り、サブエージェントが何に振り替えたかは記録に入らない。

`.ndf/` の宣言ファイルで検証コマンドを受け取る形も採れる。宣言があるリポジトリでは
確実に正しい手段が得られるが、宣言を持たないリポジトリでは同じ探し方が要る。**探し方を
先に入れ、宣言はその上に載せる。** 宣言の新設は範囲外として起票する。

### 決定 2: 探す先を順序ではなく一覧で示す

継続的統合の定義を最上位に置くと、テストを継続的統合で回さないリポジトリでテストを
取り逃がす（`devbase` の実測がこれに当たる）。テストランナーの設定を最上位に置くと、
テストを持たないリポジトリで静的解析を取り逃がす。**探す先は並べ、変更したファイルに
掛かるものを選ばせる。**

### 決定 3: 記録の突き合わせを入れない

`remaining_open` は `verify-sweep` が GitHub 側と突き合わせる。同じ形を検証の記録へ入れる
には `state.py` を変えることになり、そのファイルは担当 B の範囲にある。**この Pull Request
では記録までとし、突き合わせは入れない。** 記録が申告であることを手順に書く。

### 決定 4: 規約を `plugins/ndf/skills/README.md` へ置く

Skill を書く人が読み返す文書であり、機械の検査の規約本文としてすでに使われている
（`check-skill-frontmatter.py` の docstring が「規約の本文は plugins/ndf/skills/README.md に
ある」と書いている）。`AGENTS.md` と `CLAUDE.md` はこのリポジトリの開発全般を扱うため、
Skill を書く場面で開かれない。`markdown-writing` は利用者の文書にも効く。

### 決定 5: 除外をファイル単位で持ち、理由を必須にする

除外を行単位で持つと、行番号が動くたびに宣言が合わなくなる。ファイル単位にすると
そのファイルの中の新しい混入を見逃すが、除外した 4 ファイルはいずれも**その文書の主題が
NDF 自身**であり、対象リポジトリへの指示が新しく入る余地が小さい。**宣言した対象が
実在しないときに検査自体を失敗させる**ことで、ファイルを消したり移したりしたときに
除外が残り続けることを防ぐ。

### 決定 6: 棚卸しの結果を別の文書に残さない

棚卸しの結果はこの設計文書と、検査の除外一覧が持つ。**除外一覧は検査が実行されるたびに
実体と突き合わされるため、古くならない。** `docs/specifications/` へ一覧を写すと、
Skill が増えるたびに写しが古くなり、どちらが正かが決まらなくなる。

### 決定 7: `retrospective` の 1 行をこの Pull Request で直す

同じ課題（自リポジトリの値がそのまま書かれている）であり、他の 4 Skill が持つ解決を
2 行写すだけで済む。別に起票すると、棚卸しで見つけた 2 件のうち 1 件だけが直った状態が
残る。
