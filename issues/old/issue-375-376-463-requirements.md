# #375 / #376 / #463: 設計と要求の成果物の定義

マイルストーン「07 設計と要求の成果物の定義」のうち、`design` と `requirements-design` の
規約に関わる 3 件をまとめる。Skill が求める成果物そのものが変わり、工程の分類
（`WF_STAGE_MATRIX`）も変わるため、モードは `standard` である。

**3 件を 1 本にするのは、依存の順序と触るファイルの両方が重なるためである。** #375 が新設する
非機能の設計表は、#376 が決める 6 大項目を前提にする。#375 と #463 はどちらも
`design/SKILL.md` と `design/references/design-template.md` を触る。

## 依頼（原文）

> /ndf:development-workflow https://github.com/devbasex/ai-plugins/milestone/11

### #375 の本文（抜粋）

> `design` は設計工程の成果物を規約で決める Skill だが、**そこへ載せる構造と振る舞いの定義が
> 薄い**。成果物として名指ししている図は「処理の流れ 1 枚」と「画面遷移 1 枚」の 2 つだけで、
> クラス図・オブジェクト図・ER 図・システム構成図・状態遷移図は求めていない。機能一覧表と、
> 非機能をどう実現するかを書く節も無い。

### #376 の本文（抜粋）

> `requirements-design` が扱う非機能の条件は **性能・容量・権限・記録の 4 種**である。IPA
> 「非機能要求グレード」が定める 6 大項目のうち、可用性・運用保守性・移行性・システム環境が
> 入らず、セキュリティは権限の 1 行に縮んでいる。

### #463 の本文（抜粋）

> **`design` の手順 4（設計 Pull Request を出す）の前に、文書の内部整合を確かめる手順を置く。**
>
> **内部整合の 6 件は、同じ文書の中で突き合わせれば拾えるものだった。** 図と本文、構成要素の
> 表と処理の流れ、件数の記述と表の行数は、いずれも外部の情報を必要としない。

## 目的

| 課題 | 達成したい状態 |
| --- | --- |
| #376 | 非機能の要求が 6 大項目を軸に書かれ、設計側が実現方式を決める根拠を持つ |
| #375 | 設計文書が構造と振る舞いを図として確定させ、成果物の要否がモードと領域で決まる |
| #463 | 設計 Pull Request を出す前に、同じ文書の中で突き合わせられる誤りを落とす |

## 前提

- 前提 1: 3 件を 1 本の Pull Request にする。設計 Pull Request（`design/` 接頭辞）を先に出し、
  承認を得てマージしてから実装の Pull Request を出す
- 前提 2: 配布 Skill の数は変わらない。参照ファイルの追加は Skill の追加ではないため、
  `manifests/*-skills.txt` と版数を持つ 15 箇所は影響を受けない
- 前提 3: 盤面の工程の値（`PJ_STAGES` と 4 箇所の並び）は変えない。#375 が変えるのは
  `WF_STAGE_MATRIX` の「設計」の行の値であって、工程名の並びではない
- 前提 4: 図の記法・横幅の上限・使ってよい形式は `markdown-writing` の図表ガイドが持つ現行の
  分担を変えない。`design` が決めるのはどの図をいつどの粒度で描くかまでである

## 対象範囲

含む:

- `requirements-design` の非機能の条件を IPA 6 大項目へ広げ、該当の判定表を置く
- `design` のモードごとの成果物を、モード × 成果物の要否表へ置き換える
- `light` / `operation` でも該当すれば `design` を通す条件と、設計の書き先を決める
- 工程表と `WF_STAGE_MATRIX` の「設計」の行を合わせる
- `development-workflow` の説明文書のうち、`light` / `operation` が設計工程を通らないと
  書いている記述を、条件付きで通る形へ改める
- `design` の手順 4 の前に、文書の内部整合を突き合わせる手順を置く

含まない:

- `implementation-plan` / `tdd-cycle` / `quality-gates` の変更
- 盤面の工程名の追加・並べ替え
- 既存の設計文書（`issues/` / `docs/specifications/`）を新しい要否表へ書き直すこと

## 用語

| 用語 | この文書での意味 |
| --- | --- |
| 成果物 | 設計文書に載せる表・図・別ファイルの記述。節そのものではない |
| 水準 | ある成果物をそのモードで求める度合い。「必須」と「該当時」の 2 つだけを置く |
| 領域 | 変更が触る対象の区分。読む参照と、成果物が該当するかを決める |
| 6 大項目 | IPA 非機能要求グレードの大項目。可用性・性能拡張性・運用保守性・移行性・セキュリティ・システム環境 |
| 内部整合 | 同じ文書の中の記述どうしが食い違わないこと。外部の情報を必要としない |
| 工程の分類 | `WF_STAGE_MATRIX` が持つ `R`（必須）/ `C`（条件付き）/ `-`（対象外）の値 |

## 非機能の条件

| 種類 | 条件 |
| --- | --- |
| 容量 | 参照ファイルは 1 本 500 行以下。超えるものは領域の単位で分ける |
| 記録 | 決定の理由は `docs/specifications/ndf-design-phase.md` に残す |

該当しない項目（性能・権限）は書かない。

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | Skill の名前と数は変わらない。`design` が受け取る入力（モード・受け入れ条件・触る領域）も変わらない |
| データ | 無し |
| 既存の振る舞い | `light` / `operation` で、領域が該当すると `design` を通るようになる。設計文書の必須の節が増える |

**利用者から見た破壊的変更にあたる。** これまで設計工程を通らなかった 2 つのモードが、
条件付きで通るようになる。
