# 進行の構造と担当の輪番

[← 01-overview.md](01-overview.md)

## 1. レビューの単位は提案ラウンド

レビュー収束は**改善項目 1 件ごとではなく、提案ラウンドの差分全体**に対して回す。
項目ごとにレビュー収束を回すと、CLI の起動回数が**採用件数に比例**して膨らむためである。

採用 5 件・各項目で修正 1 回として、1 提案ラウンドあたりの起動回数を比べる。

| レビューの単位 | 内訳 | 起動回数 |
| --- | --- | --- |
| 改善項目ごと | 提案 3 + 5 ×（適用 1 + レビュー 2 + 修正 1 + 再レビュー 2） | 33 |
| **提案ラウンドごと（採用）** | 提案 3 + 適用 1 + レビュー 2 + 修正 1 + 再レビュー 2 | **9** |

3 ラウンド回すと 99 対 27 になる。claude が参加する構成では実際のリファクタリング 1 件で
$1.42 の実測があり（[検証記録](../issue-113-task3-cli-verification.md) §8-5）、
項目ごとのレビューは運用コストに耐えない。

代わりに失うものと、その埋め合わせは次のとおり。

| 失うもの | 埋め合わせ |
| --- | --- |
| 項目ごとに実装者が入れ替わらない（1 ラウンド 1 実装担当） | 輪番の単位がラウンドなので、ラウンドを重ねれば実装者は分散する |
| 指摘がどの項目に対するものか曖昧になる | レビュー結果に改善項目 ID を**必須**とし、未知の ID と欠落は差し戻す |
| 1 件の失敗がラウンド全体を巻き込む | 項目ごとに 1 手 1 コミットを保ち、**取り消しは項目単位**で行う |

## 2. 担当の輪番

母集合は固定順 `["claude", "codex", "gemini", "kiro"]` を基準に初期化時へ確定し、
状態ファイルに記録する（再開時も変えない）。

```text
全ランタイム   = ["claude", "codex", "gemini", "kiro"]
提案・レビュー = 全ランタイム − ホスト        # 常に 3 要素
適用候補       = 全ランタイム − "gemini"      # 常に ["claude", "codex", "kiro"]

実装担当       = 適用候補[ラウンド番号 % 3]
候補           = 提案・レビュー − 実装担当    # 実装担当がホストなら 3 者、それ以外は 2 者
レビュー担当   = 候補が 2 者ならそのまま
                 3 者なら 候補[(ラウンド番号 // 3) % 3] を除いた 2 者
```

実装担当がホストと同じランタイムのとき、その者は提案・レビューの母集合に含まれないため
候補が 3 者残る。**レビュー担当は常に 2 者**とし（起動回数を抑える方針と揃える）、
余る 1 者はラウンドを跨いで順に外して負荷を均す。

ホストの判定は `--host claude|codex|kiro` の明示指定を第一とし、未指定時のみ環境変数
（`CLAUDE_PLUGIN_ROOT` など）から推定する。誤検出すると**提案・レビューの母集合が狂う**
（ホストが提案側に混ざる、参加すべき者が外れる）ため、**推定結果は初期化時の出力に表示し、
状態ファイルにも残す**。

- 適用 1 : レビュー 2 を常に維持し、**2 者の承認で通過**とする。リファクタリングは必須作業
  ではないため、疑義が残るなら通さない側に倒す。
- 指摘の修正は**実装担当が行う**。レビュー担当に直させるとレビューの独立性が失われる。
- **実装担当がホストと同じランタイムでも、必ず CLI プロセスとして起動する。**
  ホストのサブエージェント機能は使わない。Claude Code がホストで claude が実装担当になる
  場合も `claude -p` を別プロセスとして起動する。これにより、適用がホストセッションの
  作業文脈を汚さない性質と、レビュー担当 2 者が実装者と別モデルである性質の両方が保たれる。
- **輪番の単位はラウンドである。** 1 ラウンドの適用を 1 者に集約することで、レビュー担当を
  「実装担当以外」から機械的に決められる。項目ごとに実装担当を替えると 1 ラウンド内で
  実装者が複数になり、実装とレビューの分離が成立しない。
- 割り当ては状態ファイルの `rounds[].impl` / `rounds[].reviewers` に記録し、再開時も変えない。

## 3. 終了条件

| 繰り返し | 終了条件 |
| --- | --- |
| レビュー収束 | レビュー担当 2 者の承認 / `--max-fix-rounds`（既定 3）到達で**未解決の項目を取り消して見送り** |
| 提案ラウンド | 採用 0 件 / `--max-outer-rounds`（既定 3）到達 / 提案の重複率が前ラウンド比 70% 以上 |

**収束しない改善項目は捨てる**のが `cross-review` との重要な差である。レビュー指摘の修正は
必須だが、リファクタリングは任意の作業なので、揉める提案は Pull Request に残さない方が
安全である。見送った項目は理由付きで記録し、次ラウンドの提案時に「対象外」として渡す。

### 取り消しは改善項目の単位で行う

レビューはラウンドの差分に対してまとめて実施するが、修正ラウンドの上限に達したときに
捨てるのは**未解決の指摘が紐づく改善項目だけ**であり、指摘が無い項目と解決済みの項目は
Pull Request に残す。これを可能にするため、適用は項目ごとに 1 手 1 コミットへ分け、
状態ファイルの `items[].commits` にコミット SHA を記録しておく。

どの項目にも紐づかない指摘（ラウンド全体に対する指摘）が未解決で残った場合は、
そのラウンドで適用した項目を全件取り消す。

## 4. 作業ディレクトリ

参加ランタイムごとに git worktree を用意する。

```text
<worktree-base>/<owner>--<repo>/rf<PR>/
├── work/              # 書き込み用。PR の head ブランチを checkout（唯一の非 detach）
├── <参加1>/           # 読み取り用。git worktree add --detach <sha>
├── <参加2>/           # 読み取り用。--detach
├── <参加3>/           # 読み取り用。--detach
└── work/.cross_refactoring/   # 状態ファイル / プロンプト / 結果 / ログ
```

`<参加N>` は状態ファイルの `runtimes`（ホストを除いた 3 者）から決まる。ホストが
Claude Code なら `codex/` `gemini/` `kiro/`、ホストが Codex なら `claude/` `gemini/` `kiro/`
になる。

**実装担当がホストと同じランタイムでも、追加の作業ディレクトリは要らない。** 適用は常に
`work/` の中だけで行うため、読み取り用を持つのは提案・レビュー参加者だけで足りる。
実装担当はランタイムを問わず作業ディレクトリを `work/` に固定して起動する。

- `<worktree-base>` の解決順は `cross-review` と同じ（環境変数 `NDF_WORKTREE_BASE` >
  `<システム tmpdir>/ndf-worktrees`）。
- **同一ブランチを 2 つの worktree に checkout できない**という git の制約があるため、
  提案・レビュー用は必ず `--detach` にする。各フェーズの開始時に `git fetch` と
  `git checkout --detach <対象 sha>` で同期する。

  ```console
  $ git worktree add ../wt2 feature/x
  fatal: 'feature/x' is already used by worktree at '.../wt1'
  ```

- 読み取り専用でも作業ディレクトリを分ける理由は 3 つある。
  1. レビュー担当が**テストを実行して振る舞い不変を確認する**ため、書き込み可能な領域が要る
  2. テスト実行が生む生成物（`.pytest_cache` / `node_modules` / ビルド出力）が競合しない
  3. gemini の作業領域制約（領域外への書き込みが拒否される）を、各自のディレクトリ内に
     一時ファイルを置くことで回避できる
- 適用は常に `work/` の中だけで行う。並列適用はしない（同一ブランチへの同時コミットは
  競合の温床になる）。**並列にするのは提案とレビューだけ**。
- 手順書となる Skill の配置は [04-skill-provisioning.md](04-skill-provisioning.md) を参照。

## 5. 参加者を全て CLI にすることの帰結

参加者を全て CLI プロセスにしたことで、**進行全体を 1 本の bash で駆動できる**。
claude が参加する場合もヘッドレス CLI（`claude -p`）として起動し、ホストのサブエージェント
機能は一切使わない。**ホスト自身と同じランタイムが実装担当になるラウンドでも同じで、
ホストは自分と同じランタイムの CLI を別プロセスとして起動する。**

そのため `cross-review` が必要としていた「bash を抜けてホストがサブエージェントを起動し、
再び bash に戻る」中断・再開の受け渡しが要らない。結果として次がそのまま流用できる。

- `cross-review` と同じ「状態管理スクリプト + 起動スクリプト + 監視スクリプト」の骨組み
- 監視スクリプトの多軸完了判定（プロセス ID / 完了印 / 早期エラー / 無反応 / 打ち切り / 結果ファイル）
- 「AI 自身が `gh api` で Pull Request へ直接投稿する」ことでホストの作業文脈を汚さない方針

ホストが行うのは bash の駆動と、最後の `/ndf:cross-review` 実行だけである。
ホストと同じランタイムが実装担当のラウンドでも、ホストセッション自身が編集するわけでは
ないので変わらない。
