# 受け入れ条件とリスク

[← 01-overview.md](01-overview.md)

## 1. 受け入れ条件

### 進行と担当

- [ ] `/ndf:cross-refactoring` が Draft PR 作成から完了報告まで、中断・再開可能に一周する
- [ ] **提案・レビューの参加者がホストを除いた 3 CLI** で確定し、ホストは提案とレビューに
      参加しない
- [ ] **適用の母集合が claude / codex / kiro**（gemini を含まない）で確定し、ホストと同じ
      ランタイムが実装担当になるラウンドが存在する
- [ ] 実装担当がホストと同じランタイムのときも **CLI プロセスとして起動**され、
      ホストのサブエージェント機能を使わない
- [ ] gemini が提案とレビューには参加し、**適用では一度も起動されない**
- [ ] `--host` の明示指定と環境変数からの推定の両方が動き、確定結果が状態ファイルに残る
- [ ] 全ラウンドで実装担当とレビュー担当が重ならない（状態ファイルで検証できる）
- [ ] レビューが**ラウンド単位で 1 回**回り、CLI 起動回数が採用件数に比例しない

### 作業ディレクトリと Skill

- [ ] 作業ディレクトリが参加者分作られ、読み取り用は `--detach`、書き込みは `work/` のみ
- [ ] **配置前に Skill の有無を検出**し、無ければ配置して状態ファイルに記録する。
      既存の Skill を上書きしない
- [ ] 配置が**作業ディレクトリの中だけ**で完結し、利用者のホームと対象リポジトリ本体、
      および Pull Request の差分に一切現れない
- [ ] ホスト側にも見つからない必須 Skill があれば初期化が失敗する
- [ ] `kiro-cli agent set-default` を呼ばない（マシン全体の既定を書き換えない）

### 適用・レビュー・見送り

- [ ] Kiro と Claude が非対話で提案・レビューを完了し、結果ファイルを書き出す
- [ ] 提案 → 適用 → レビュー → 修正 のレビュー収束が、指摘 0 で完了に到達する
- [ ] 収束しない改善項目が取り消され、Pull Request に未完成の差分が残らない。かつ
      **同じラウンドで合意済みの項目は取り消されずに残る**
- [ ] 適用に失敗した項目がラウンドを止めず、その項目だけ見送りになる
- [ ] 提案が尽きる（または上限到達）で提案ラウンドの繰り返しが終了し、
      `/ndf:cross-review` で最終収束する

### 計測

- [ ] `--model <ランタイム>=<モデル>` で各 CLI のモデルを指定でき、指定値が状態ファイルに
      記録されて全ラウンド不変である
- [ ] `--model kiro=<name>` を指定しない実行では、報告が当該ラウンドを「モデル未確定」と
      して集計から分離する
- [ ] **全コミットに `Item-Id` / `Round` / `Impl-Runtime` / `Impl-Model` のトレーラーが付き**、
      `git log --format='%(trailers:key=Impl-Model,valueonly)'` で集計できる
- [ ] 全レビューコメントにレビュー担当のランタイムとモデルが明記される
- [ ] Pull Request 本文のラウンド表に実装担当とレビュー担当のランタイムとモデルが載る
- [ ] `report --metrics` がランタイムとモデルの組で指標を出し、既定モデルのラウンドを区別し、
      比較の限界を添える

### 全体

- [ ] ホストセッションの作業文脈に差分・レビュー本文・エラーログが載らない
- [ ] 監視スクリプトの既存テストが無変更で通る
- [ ] `claude plugin validate` / `build-runtime-plugins.sh --check` /
      `validate-runtime-plugins.sh` / `check-skill-frontmatter.py` / `check-markdown-links.py`
      が全て通る

## 2. リスクと対応

### 担当の決定と起動

| リスク | 対応 |
| --- | --- |
| ホスト判定を誤り、提案・レビューの母集合が狂う | `--host` の明示指定を第一とし、推定結果を初期化時の出力と状態ファイルに必ず残す。提案・レビューの母集合にホストが含まれたら初期化を失敗させる（適用の母集合はホスト非依存なのでこの検査の対象外） |
| ホストと同じランタイムが実装担当のとき、サブエージェント機能で実装させてしまう | 起動スクリプトはランタイム名だけで分岐し、ホストか否かを見ない。受け入れ条件で CLI 起動を検証する |
| `codex exec` にコマンド引数でプロンプトを渡してハングする | 標準入力が開いている限り待ち続ける（600 秒でも終了しない）。`cross-review` と同様に**標準入力から渡す**。コマンド引数の形式なら `< /dev/null` が必須 |
| root 実行で claude の `bypassPermissions` が使えない | `acceptEdits` と `--allowed-tools` の明示を起動スクリプトの既定にする（root でも通ることを実測） |
| Kiro の承認漏れが終了コード 0 のまま素通りする | 停止ではなく「拒否して終了コード 0」で現れる。標準エラー出力の拒否メッセージを早期エラーに加え、終了コード 0 を成功とみなさない |
| ツールの絞り込みが防御にならない | シェル実行を許可すると書き込み制限を迂回できる。防御は作業ディレクトリの隔離に一本化し、絞り込みは使わず全許可にする |
| 全許可で作業ディレクトリの外を触られる | 参加 CLI の作業ディレクトリを固定し、書き込み可能なのは `work/` のみ、他は `--detach` にする。ホストのリポジトリ本体は参加 CLI に渡さない |

### 手順の遵守

| リスク | 対応 |
| --- | --- |
| Kiro が Skill 本文を読まないまま「それらしく」直す | 配置しただけでは本文を読まず、`description` の語彙で答える。プロンプトに明示パスを必ず書き、さらに適用結果の機械検証（現状固定テストの先行 / テスト成功 / トレーラー）で結果側からも担保する |
| Skill を読ませても手順を守らない | 同じ課題で現状固定テストの追加数が 17 本 / 1 メソッド / 0 本と揃わなかった。テストが乏しい項目は固定テストの先行を機械検証し、守られていなければ失敗として扱う |
| 振る舞い不変が検証されないまま通る | 着手前のテスト成功を必須化し、テストが乏しい項目は固定テストの先行を機械検証し、レビュー観点の筆頭に置く |
| 提案が発散して Pull Request が肥大する | 対象範囲の指定を必須化し、1 ラウンドの採用上限（既定 5）と提案ラウンドの上限（既定 3）で抑える |
| 同じ提案が毎ラウンド出続けて終わらない | 提案の重複率 70% で収束と判定する。見送った項目は次ラウンドの提案時に「対象外」として渡す |
| 語彙を守らず重複排除が効かない | 語彙外は `unknown` として最低の重要度へ降格し、しきい値で自動的に落ちるようにする |
| 参加ランタイムに NDF が未導入で参照ファイルを読めない | 各作業ディレクトリのランタイム標準の配置先へ Skill をコピーし、相対パスだけを参照させる |

### 計測

| リスク | 対応 |
| --- | --- |
| モデル比較の数値が誤読される | 改善項目の難易度・提案との相性・レビュー担当の厳しさで簡単に揺れる。集計の出力に比較の限界を必ず添え、厳密に比べるなら「同じ範囲で `--model` だけ変えて複数回走らせる」ことを案内する |
| AI がコミットトレーラーを書き忘れて集計できない | プロンプトの指示だけに頼らず、適用結果と修正結果の検証でトレーラーの有無を確認して失敗にする |
| 指定したモデルと実際に動いたモデルが違う | 取得できるランタイムでは実測値を記録して指定値と突き合わせ、食い違いを警告にする。取得できないランタイムは既定として集計から区別する |
| ラウンド単位のレビューで指摘と項目の対応が崩れる | 指摘に項目 ID を必須にし、未知 ID と欠落は差し戻して再レビューする。紐づかない指摘は `null` を明示させ、取り消し時はラウンド全件を対象にする |
| 1 ラウンドの実装者が 1 者に固定され、モデルの癖が偏る | 輪番の単位がラウンドなので、ラウンドを重ねれば実装者は分散する。提案ラウンドの上限を 1 にしない |

### コストと時間

| リスク | 対応 |
| --- | --- |
| claude 参加時の実行コスト | 単純な 3 ターンで 0.26 ドル、実際のリファクタリング 1 件（29 ターン / 218 秒）で 1.42 ドルの実測。レビューをラウンド単位にして 1 ラウンドの起動回数を 33 から 9 に抑えたが、claude が絡む起動が 1 ラウンドに数回あるため 1 実行で数ドルから十数ドルに達しうる。上限値の既定を保守的に置き、報告に実測コストを必ず出す |
| CLI の実行時間が長く全体が長丁場になる | 提案とレビューは並列にする。適用は 1 ラウンド 1 回に集約したので起動回数は減るが、**1 回あたりは採用件数分だけ長くなる**。1 ラウンドの採用上限で 1 回の長さを抑え、状態ファイルで常時再開可能にする |
| 初期一覧の予算を超える | 制約になるのは Codex で、予算 15,123 文字に対し現在 5,443 文字（2.8 倍の余裕）。本 Skill 1 個の追加は 200 文字程度で影響しない。`python3 scripts/check-skill-frontmatter.py` で確認する |
| 監視スクリプトの変更が既存の進行を壊す | 追加オプションは全て既定値で現行の挙動を維持し、既存テストの無変更通過を完了条件にする |

## 3. 対象外

初版では次を扱わない。

- Pull Request のローテーション（件数上限で総量を抑える方針を先に検証する）
- 複数の改善項目の並列適用（同一ブランチへの同時コミットは競合を招く。1 ラウンドの適用は
  実装担当 1 者が直列に行う）
- 改善項目ごとのレビュー収束（CLI 起動回数が件数に比例し、運用コストに耐えないため）
- ホストと同じランタイムを**提案・レビュー**に参加させること（適用には CLI として参加する）
- gemini を適用に参加させること（NDF Skill を配布していないため）
- リファクタリング以外の変更（機能追加・不具合修正）の取り込み
