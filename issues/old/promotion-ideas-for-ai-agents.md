# ai-plugins を広めるための施策（AI エージェントが実行できるもの）

モード: `documentation` / 文書タイプ: 提案

## 依頼（原文）

> ai-pluginsを多くの人に使ってもらいたいです。
> どのようにプロモーションすべきですか？
>
> ai agentで実行可能なアイデアをまとめてissues/ に出力してください

**この文書は施策の元になるアイデア集である。** 2026-09-15 に全 15 施策をマイルストーン
[14 利用者を増やす](https://github.com/devbasex/ai-plugins/milestone/22) へ起票した（#689〜#703）。
**着手の順序と各施策の中身はこの文書が持ち、進行は issue が持つ。** 起票の単位は末尾の「起票の分け方」にある。

## 結論

**まず受け皿を整え、その後に流入を増やす。** 今は来た人が価値を読み取れる状態になっていない。
その状態で記事や SNS から人を呼んでも、訪問が導入につながらない。

最初の 2 週間でやること:

1. **E1（#689） 流入の定点観測**。GitHub の traffic API は直近 14 日分しか返さない。今日から保存しないと、施策の前の数値が消える
2. **A5（#690） リポジトリ設定と GitHub Releases**。数十分で終わり、検索と通知に直接効く
3. **A1（#691） README の冒頭の書き直し** と **A2（#692） 英語 README**
4. **A3（#693） デモの録画**。記事・SNS・README のどれでも使い回せる

この 4 つが済んでから、発信（B）と掲載（C）を始める。

## 前提: AI エージェントに任せる範囲

**社外へ出す操作は、すべて人間の承認を関門にする。** 記事の投稿、SNS への投稿、他のリポジトリへの
Pull Request、リポジトリ設定の変更がこれに当たる。一度公開すると取り消せない。また、他人の
リポジトリに届く操作は、送った側の評判に直接はね返る。

| 自律度 | 意味 |
| --- | --- |
| ◎ | エージェントだけで Pull Request まで作れる。人間はマージを承認するだけ |
| ○ | エージェントが下書きまで作る。公開・送信は人間が行うか、人間の承認を得てから行う |
| △ | 人間の作業が主。エージェントは準備と下調べを担う |

## A. 受け皿を整える

### A1 README の冒頭を 30 秒で価値が伝わる形にする（#691）

**狙い。** 今の README は、冒頭から Skill 45 個の分類の羅列が続く。初めて来た人が「何が
嬉しいのか」「どう試すのか」にたどり着く前に離脱する。

エージェントがやること:

- 冒頭の「内部マーケットプレイス」を、社外にも開いた表現へ直す。`docs/project-overview.md` の「（内部用）」も合わせて直す
- 冒頭を次の順に組み直す: 1 文の価値提案 → 導入の 2 行 → デモ（A3）→ 代表的な Skill 3〜5 個の「何が起きるか」→ 詳細への導線
- Skill の全件の羅列は `plugins/ndf/README.md` か A4 のカタログへ移す
- バッジ（ライセンス・対応ランタイム・最新版）を置く

人間の関門: 価値提案の 1 文と、「内部」の表記を外してよいかの判断。

完了条件:

- [ ] README の最初の 1 画面に、価値提案・導入コマンド・デモの 3 つがある
- [ ] 「内部」の表記が README と `docs/project-overview.md` から消えている（外すと判断した場合）
- [ ] `python3 scripts/check-markdown-links.py` が通る

### A2 英語 README を用意する（#692）

**狙い。** Claude Code / Codex の利用者の大半は日本語を読まない。Skill の `description` は既に
英語で書かれているため、入口の README さえ英語になれば海外の利用者に届く。

エージェントがやること:

- `README.en.md` を作り、`README.md` の冒頭から相互にリンクする
- `plugins/ndf/README.md` の導入の節も英語版を作る
- 日本語版との食い違いを防ぐため、英語版に対応する日本語版の commit を記録し、日本語版だけが更新されたら検出する検査を足す

人間の関門: 英語版をどこまで保守するか（README の冒頭だけか、全文か）の決定。

完了条件:

- [ ] `README.en.md` だけを読んだ人が、Claude Code と Codex で NDF を導入できる
- [ ] 導入コマンドを実際に実行し、成功を確かめた記録がある

### A3 デモを再現可能な形で録画する（#693）

**狙い。** 動くところを見せるのが、価値を伝える最短の方法である。記事・SNS・README・ランディング
ページのどれでも同じ素材を使い回せる。

エージェントがやること:

- 見せる場面を 3 つに絞る。候補: `/ndf:cross-review` が指摘と修正を繰り返して収束する場面、`/ndf:development-workflow` のモード判定、worktree のフックが主ディレクトリでの編集を案内する場面
- 端末の録画を、スクリプトから再生成できる道具で作る（候補: VHS の tape ファイル、asciinema）。手で録った動画だと、版を上げたときに撮り直せない
- GIF（README 用、数 MB 以内）と MP4（SNS 用）を出力する

人間の関門: 録画に社内のリポジトリ名・PR の内容が映っていないかの確認。**デモ用の公開リポジトリで録る。**

完了条件:

- [ ] 録画の台本（tape ファイルなど）がリポジトリにあり、1 コマンドで再生成できる
- [ ] 映っている情報に社内の情報が含まれていない

### A4 GitHub Pages を Skill カタログつきのランディングページにする（#695）

**狙い。** Pages は有効なのに、発表資料へ転送するだけで終わっている。検索エンジンと SNS の
リンクカードに載る入口として使える。

エージェントがやること:

- `docs/index.html` をランディングページにする（価値提案・デモ・導入・Skill カタログ・発表資料へのリンク）
- Skill カタログは `plugins/ndf/manifests/*-skills.txt` と各 `SKILL.md` の frontmatter から CI で生成する。手で書くと、Skill の増減に追随しなくなる
- OGP 画像と `<meta>` を置き、SNS に貼ったときにカードが出るようにする

人間の関門: デザインの確認。

完了条件:

- [ ] カタログの件数が manifests の行数と一致することを CI が検査している
- [ ] X / Slack にリンクを貼るとカードが表示される

### A5 リポジトリ設定・Releases・Discussions を整える（#690）

**狙い。** 数十分で終わり、GitHub 内の検索と通知に直接効く。

エージェントがやること（**設定の変更は、変更内容を示して承認を得てから適用する**）:

- description を 4 ランタイム対応が伝わる文にする。現状は「Claude Codeプラグインマーケットプレイス」だけ
- topics に `codex`、`kiro`、`agent-skills`、`mcp`、`ai-code-review` などを足す（GitHub 上で実際に使われている topic を調べてから選ぶ）
- social preview 画像を設定する（A4 の OGP 画像を流用）
- 既存タグ `ndf--v*` から GitHub Releases を作る。本文は `CHANGELOG.md` の該当節から作る。今後は `/ndf:release` の工程で Release も作るようにする
- Discussions を有効にし、「質問」「使い方の共有」「アイデア」のカテゴリを置く

人間の関門: 各設定の適用。Discussions を運用する人を決める。

完了条件:

- [ ] 最新の正式版に GitHub Release がある
- [ ] `/ndf:release` の手順に Release の作成が入っている

### A6 「最初の 1 個」の導線を作る（#694）

**狙い。** Skill 45 個・エージェント 8 個・フック一式をいきなり入れるのは重い。単体で価値が
分かる Skill を 1 つ選び、5 分で試せる道筋を作る。

エージェントがやること:

- `/ndf:skill-stats` の集計から、利用回数が多く単体でも価値が分かる Skill を候補にする（`cross-review` が有力）
- 「5 分で試す」手順を書く。前提（codex / agy の認証など）、試すためのサンプル PR、期待される出力を含める
- 手順を新しい環境で実際に通し、詰まった箇所を手順か実装へ戻す

完了条件:

- [ ] 手順を README の冒頭から 1 クリックで開ける
- [ ] まっさらな環境で手順を通した記録がある

## E. 測る

### E1 流入の定点観測を自動化する（#689）

**狙い。** 施策が効いたかを判断するための土台である。GitHub の traffic API は直近 14 日分しか
返さないため、保存を始めた日より前の数値は取り戻せない。**他のどの施策より先に始める。**

エージェントがやること:

- 週 1 回、次の値を取得して保存する GitHub Actions のワークフローを作る: star、fork、views、clones、referrers、popular paths、Release ごとのダウンロード数
- 保存先は、リポジトリの専用ブランチか Actions の artifact にする（`develop` に毎週 commit すると履歴を汚す）
- traffic API には push 権限のあるトークンが要る。`GITHUB_TOKEN` で足りるかを実行して確かめ、足りなければ必要な権限を README に書く
- 月 1 回、施策の実施日を重ねたグラフを作る

完了条件:

- [ ] ワークフローが 2 回以上成功し、2 週を超える期間の数値が残っている
- [ ] 施策（A〜D）ごとに、実施日と、実施前後の数値の比較がある

## 範囲外で見つけたこと

**`docs/id_rsa.pub` が GitHub Pages の公開範囲に入っている。** Pages の公開元が `main` の `docs/` で
あるため、`https://devbasex.github.io/ai-plugins/id_rsa.pub` から取得できる（2026-09-15 に HTTP 200 を確認）。
公開鍵なので秘密情報ではない。ただし、知識を置く `docs/` にある理由が読み取れず、外部の人が見ると
誤って置いたものに見える。起点は `dde450c`（`takemi-ohama/ai-plugins` からの同期）である。
**この指摘は 2026-09-15 に解消した。** PR #688（`ddcd8fc`）で `docs/id_rsa.pub` を削除した。
