# #1468: 決定の記録・テスト設計・未確認のまま残ること

設計の本文は [issue-1468-design.md](issue-1468-design.md) にある。要求と受け入れ条件は #1468 の本文
（コピーは [issue-1468-requirements.md](issue-1468-requirements.md)）にある。

## 決定の記録

### 決定 1: 副命令は `add-bedrock`・`check metered`・`remove metered` にする

`account add <名前>` の名前には `bedrock` が使えるため、`add bedrock` や `add --bedrock` は既存の登録と同じ形の中に
別の意味を持ち込む。`metered` は従量の接続を表す予約の名前として既にあり（`claude_accounts.METERED`）、一覧の行の名前も
`metered` になるので、外す・確かめるはその名前で指す。Vertex は同じ形で `add-vertex` を足す。

`add-metered --provider bedrock` は採らない。提供元ごとに要る引数（Bedrock はプロファイル、Vertex はプロジェクト）が違い、
1 つの副命令の引数が提供元で変わる。

根拠: Value 8 / Value 5（MVV 版 1）

### 決定 2: OAuth の 2 回の登録は、`claude auth login` を生かしておき FIFO で認可コードを渡す

1 回目で `claude auth login` を新しいセッション（`start_new_session=True`）で起動し、標準入力を FIFO にして生かしておく。
2 回目は FIFO へコードの 1 行を書き、終了を待つ。2026-09-28 に 2.1.284 で、標準入力を端末でないパイプにして起動すると
認可の URL と `Paste code here if prompted >` を出して標準入力を待ち、不正なコードの 1 行で終了コード 1 になることを実測した。
資格情報のファイルと `.claude.json` を書くのは今までどおり claude 自身であり、登録の後の確かめ（`auth status`・重複）も
今の 1 回の登録と同じ関数を通る。

PKCE の検証子を relay.py が持ち、トークンの交換を自分で行う案は採らない。claude の資格情報の形（`.credentials.json` の
項目・`.claude.json` の `oauthAccount`）を再現することになり、claude の版が上がるたびに壊れうる。1 回目で子を終わらせ
2 回目で `claude auth login` を起動し直す案は成り立たない（検証子と `state` が変わり、1 回目の URL で得たコードが通らない）。

根拠: Value 6 / Value 4（MVV 版 1）

### 決定 3: 登録の途中の状態の期限は 10 分にする

利用者がブラウザで認可し、コードを conductor へ返すまでの往復に足りる長さを取る。長くすると、生きたままの待機中の
ログインと、コードを受け付ける FIFO が置き場に残る時間が延びる。claude 側や認可の提供元の期限がこれより短ければ、
2 回目は `bad_code` になる（未確認のまま残ること 1）。

根拠: Value 2 / C1（MVV 版 1）

### 決定 4: 呼べるかの確認は `aws sts get-caller-identity` と `aws bedrock-runtime converse`（最大 1 トークン）で行う

`aws` のエラーは `An error occurred (<種類>)` の形で種類の名前を返し（2026-09-28 に `NoCredentials` で実測）、非機能の条件の
「元になった AWS のエラーの種類の名前」をそのまま出せる。認証を先に `sts` で分けると、`converse` の失敗を権限・地域・
モデルの 3 つだけで振り分ければよい。`converse` は保存するのと同じプロファイル・地域・モデルの ID で呼ぶ。

`claude -p` で 1 回呼ぶ案は採らない。エラーの種類の名前が出力に残らず 4 区分へ振り分けられないうえ、1 回の起動で
システムの指示の分のトークンが掛かる。

根拠: Value 3 / Value 4（MVV 版 1）

### 決定 5: モデルは宣言に `ANTHROPIC_MODEL` として入れ、候補から選ばせる。自動では選ばない

候補は `aws bedrock list-inference-profiles --type-equals SYSTEM_DEFINED` のうち ID に `anthropic.claude` を含むものである。
1 つなら確認、複数なら番号で選ぶ。端末でなければ `missing_args` に候補を添えて返し、AI が利用者に問うか選ぶ。
宣言にモデルを入れるのは、呼べるかの確認で確かめたモデルと、子が実際に使うモデルを同じにするためである。

宣言にモデルを入れず claude の既定に任せる案は採らない。claude が Bedrock で既定に使う ID を relay.py は外から知る手段が
無く、確認と起動が別のモデルになる。候補から「最新」を自動で選ぶ案も採らない。ID の形が世代で揃っておらず（日付を
含むものと含まないものがある）、並べ方の規則を持つと規則の方が古くなる。

根拠: Value 5 / Value 2（MVV 版 1）

### 決定 6: 宣言はアカウントの置き場の `metered.json` に保存する

アカウントの置き場（`NDF_ACCOUNTS_DIR` があればそれ）の中に置くと、置き場を分けた利用者とテストで、アカウントと宣言が
同じ組で切り替わる。既定では relay の置き場（`${CLAUDE_CONFIG_DIR:-~/.claude}/ndf/`）の中の `accounts/` であり、要求の
保存先の範囲に収まる。書く関数は `claude_accounts` の既存の `_write`（0600・置き換え）を使う。

`ndf/` の直下に置く案は採らない。`NDF_ACCOUNTS_DIR` で置き場を分けても宣言だけが共有され、別の組のアカウントに別の
組の宣言が混ざる。

根拠: Value 6 / C6（MVV 版 1）

### 決定 7: 環境変数 `NDF_SUPERVISE_CLAUDE_FALLBACK` は、空でも定義されていれば保存した宣言より優先する

前提 6（効くのは環境変数だけ）を、定義の有無で判定する。空で定義すれば、保存した宣言を消さずに一時的に止められる。
今は空の値を「宣言なし」として扱っており、保存した宣言が無い利用者の振る舞いは変わらない（AC10）。

空のときだけ保存した宣言へ落とす案は採らない。止める手段が「ファイルを消す」だけになる。

根拠: Value 2（MVV 版 1）

### 決定 8: `--yes` と `--json` はすべての副命令が受ける。確認の無い副命令では `--yes` は何もしない

AI が副命令ごとに `--yes` を付けてよいかを判断しなくて済み、同じ打ち方で通る。`account list --json` の出力は今の形
（行の配列）を保ち、各行に `kind` を足し、宣言の行を最後に足す。ほかの副命令は `{"ok": …}` の 1 つの JSON を返す。

`list --json` も `{"ok": …, "rows": […]}` に揃える案は採らない。今の形を読む呼び出し側（利用者のスクリプト）を壊す。

根拠: Value 2 / Value 4（MVV 版 1）

### 決定 9: 副命令の引数の読み取りを `argparse` に移す

引数が 6 種類（`--profile`・`--region`・`--model`・`--code`・`--yes`・`--json`）に増え、今の「長さと並びの完全一致」では
組み合わせを書き切れない。`argparse` は読めない引数で usage を出して終了コード 2 で終わり、今の振る舞い（usage と 2）と
合う。標準ライブラリだけを使う relay の規約にも収まる。

根拠: 根拠なし（MVV 版 1）

### 決定 10: Bedrock の登録は macOS でも許す

macOS で OAuth の登録を断るのは、claude が資格情報を Keychain に置き `.credentials.json` を書かないためである。Bedrock の
登録は `aws` と `metered.json` だけを使い、この理由に当たらない。

根拠: Mission（MVV 版 1）

### 決定 11: 宣言の中身は `provider`・`env`・`details` の 3 つに分け、Vertex は `provider: "vertex"` を足すだけにする

子の環境へ足すのは `env`、一覧に出すのは `details` で、どちらも提供元を知らずに扱える。Vertex を足すときに変えるのは、
`add-vertex` の副命令と、確かめる手段（提供元ごとの `verify`）だけになる。`check metered` は今回 `bedrock` だけを確かめ、
それ以外は `not_bedrock` で 1 を返す。

根拠: Value 5（MVV 版 1）

### 決定 12: 呼べるかの確認の失敗に、4 区分のほか `unclassified` を置く

通信の失敗やスロットリングを 4 区分のどれかへ寄せると、利用者は直す必要の無いものを直しに行く。4 区分は「呼べない
プロファイル」の理由（AC3）であり、`unclassified` でも宣言は保存しない（I2）。エラーの種類の名前は出すので、利用者は
打ち直すかを判断できる。

根拠: Value 3（MVV 版 1）

### 決定 13: 認可コードは `--code -`（標準入力の 1 行）を案内の既定にし、`--code <値>` も受ける

コマンドの引数は同じホストの `ps` と、打った側の記録（Bash の Tool の入力）に残る。標準入力で渡せばどちらにも残らない。
要求の形（`--code <認可コード>`）も受けるのは、端末の利用者が貼り付けて打つ形を塞がないためである。認可コードは
待機中のログインが持つ検証子と組でなければ使えず、期限も短いため、引数に載っても再利用される余地は小さい。

根拠: C1 / Value 2（MVV 版 1）

### 決定 14: 保存した宣言で起動する子からは、AWS の鍵の変数を外す

AWS の SDK は `AWS_PROFILE` より環境変数の鍵を先に使う。親の環境に鍵があると、確かめたプロファイルとは別の資格情報で
子が動く。呼べるかの確認も同じ変数を外して呼ぶので、確認と起動の環境が揃う。環境変数の宣言では外さない
（今の振る舞いを変えない。AC10）。

根拠: Value 6（MVV 版 1）
