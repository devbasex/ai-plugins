# #541: マイルストーンの組（`milestones.md`）

## 関連リンク

- 要求: [issue-540-541-621-requirements.md](issue-540-541-621-requirements.md)（AC20〜AC22・AC24）
- 設計: [issue-540-541-621-design.md](issue-540-541-621-design.md)（決定 10・11）
- 契約: [issue-540-541-621-design-contracts.md](issue-540-541-621-design-contracts.md)（「マイルストーンの組」の節）

**設計の決定 1 の 3 本のうちの 1 本目である**（本数の測定 #621 と並行。触るファイルが重ならない）。
実行計画（#540）は組を**読む**側で、この Pull Request は**書く**側を実装する。

## モード

`standard`。文書の節の新設とテストの追加で、受け入れ条件が 4 件ある。

## 目的と非目的

達成したい状態:

- マイルストーンへ課題を入れるときに、その課題の**組**（触る場所の見込みと依存）が説明へ書かれる
- 組が、実行計画（#540）の**束の初期値**として読める形で置かれる

やらないこと:

- 既存のマイルストーンの束ね直し・改名・型の宣言（決定 10）
- 既存の説明の一括の書き直し（決定 11。課題を足す時点で、その課題の行だけを作る）
- マイルストーンの名前・連番・着手の順序の規則の変更（AC24）
- 段 2A の控える項目を増やすこと（AC21）
- 実行計画の側（`issue-plan-strategy`・`issues/README.md`）— #540 の Pull Request が持つ

## 前提

- 前提 1: 組の触る場所と依存は、段 2A が既に控える「修正レイヤー」と「依存する課題の番号」から写す。`SKILL.md` の段 2A の控える項目の表は 6 行で、この Pull Request は増やさない
- 前提 2: 組の形（見出し・表の列）は契約の文書が持つ。`milestones.md` はその形をそのまま写す
- 前提 3: `milestones.md` は現在 91 行。1 文書 500 行の上限に余裕がある

## 受け入れ条件

- [ ] AC20: マイルストーンへ課題を入れるとき（新しく作る・既存へ足す・直近へ移す）に、その課題の組を説明へ書く手順がある。組は触る場所の見込みと依存を持つ
- [ ] AC21: 組の触る場所は段 2A の修正レイヤーから導く。**段 2A の控える項目は増えない**（`SKILL.md` の表の行数が変わらない）
- [ ] AC22: 組の間は並列にできる見込み、組の中は同じ Pull Request へ束ねるか順に進める見込みである、と書かれている。**見込みであり、確定は設計の後に実行計画が持つ**ことも書かれている
- [ ] AC24: 名前・連番・着手の順序の規則は変わらない。組のために既存のマイルストーンを分けたり束ね直したりしない
- [ ] 退行しないこと: 既存の `test_issue_upkeep_layout.py` がそのまま通る

## 代替案と採否

| 案 | 内容 | 採否 | 理由 |
| --- | --- | --- | --- |
| A | `milestones.md` に「組を書く」の節を新設し、契約の形をそのまま写す | 採用 | 設計の決定 10・11。マイルストーンを決める手順と同じ文書にあるのが自然 |
| B | `grouping.md`（クラスタ）へ書く | 不採用 | クラスタは「同じ原因で括る」判断で、組は「触る場所で並列にできるか」の見込み。別の軸である |
| C | 新しい参照文書を作る | 不採用 | 91 行の文書に 1 節を足すだけで、上限に余裕がある |

## ドメイン用語

| 用語 | 意味 |
| --- | --- |
| 組 | マイルストーンの説明に書く、触る場所の見込みと依存でまとめた課題の集まり。実行計画の束の初期値 |
| 束 | 1 本の設計 Pull Request で決める課題の集まり（実行計画が持つ） |
| 修正レイヤー | 直すべき場所。段 2A が課題ごとに控える |

## 不変条件

- 組は**見込み**であり、確定した触る場所は実行計画だけが持つ（書き戻さない）
- 組の番号は詰めない（課題が 0 件になった組の行は消すが、番号は再利用しない）
