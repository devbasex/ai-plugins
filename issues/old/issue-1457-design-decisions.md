# #1457: 決定の記録・テスト設計・未確認のまま残ること

設計の本体は `issues/issue-1457-design.md` にある。要求と受け入れ条件は #1457 の本文（コピーは `issues/issue-1457-requirements.md` ）。

## 決定の記録

### 決定 1: 経路 `promote` の確認は、昇格のプランの先頭のステップ `verify` に置く

確認と承認ゲート 2 を同じプランに置けば、「確認が通った後にだけ MVV 判定へ進む」をステップの並びだけで守れる。先頭に置くのは、
確認が落ちたときに昇格の Pull Request を作らないためである。 `prepare` の後に置くと、落ちたスプリントごとに開いたままの
昇格の Pull Request が残り、次のスプリントの `prepare` がそれを使い回す。

昇格のプランの前に別のステージを置く形は採らない。ステージが増えると、止まった後の打ち直しが 2 つのプランにまたがり、
`then_of` の連結も 1 つ増える。

根拠: Value 4 / Value 6（MVV 版 2）

### 決定 2: 確認の承認資料は `approval-verify.md` に分け、 `mvv` に `--material` で 2 つ渡す

`mvv-gate.py check` の `--material` は複数のファイルを受け取る（ `nargs="+"` ）。確認の資料を別のファイルにすれば、
`merged-steps.py promote --prepare` を変えずに済み、 `--from verify` で打ち直しても同じファイルへ書き直すだけで節が重ならない。

`approval-promote.md` へ節を追記する形は採らない。 `verify` を `prepare` より前に置く（決定 1）と追記先がまだ無く、打ち直すたびに
節が重なる。 `deploy-facts` をそのまま使う形も採らない。見出しと「本番系へ届ける行」が手動反映の本番系のもので、
昇格の資料として読むと誤る。

根拠: Value 4 / Value 6（MVV 版 2）

### 決定 3: `verify-facts` を足し、 `deploy-facts` と確認の実行・ログ・「導入の確認」の節を共有する

確認を走らせる処理（先頭への fast-forward・HEAD の照合・ `sh -c` ・0600 のログ）は、手動反映の本番系と同じ部品を使う
（非機能の条件）。違うのは承認資料の残りの節（本番系の行の有無と、届けるコミットの説明）だけなので、共有する部分を
`run_verify` と `verify_lines` に切り出し、サブコマンドは資料の形ごとに 1 つずつ置く。

`deploy-facts` にフラグを足して資料の形を切り替える形は採らない。フラグの組み合わせごとに `delivery` を読むか・本番系の行を
書くかが変わり、1 つのサブコマンドが 2 つの意味を持つ。 `verify-facts` は `--base` を受け取り、配布の宣言を読まない。

根拠: Value 6 / Value 8（MVV 版 2）

### 決定 4: 経路 `merge` だけのスプリントには、MVV 判定を持たない「導入の確認」のステージを置く

経路 `merge` の反映は開発版のチャネルへのもので、承認ゲート 2 に当たらない（ `pace.md` の経路の表）。このスプリントでは
承認ゲート 2 の MVV 判定がそもそも無いため、確認は「落ちたら止める」ことだけを担う。手で届ける経路（ `manual` ）もあれば、
「リリース」の手で行うステージはこの後に続き、確認が落ちれば queue がそこまで進まない。

確認を検査のプランの最後のステップへ足す形は採らない。検査のプランは雛形の経路・手動反映の本番系とも共有しており、
経路ごとに検査のステップが変わる。

根拠: Value 2 / Value 6（MVV 版 2）

### 決定 5: 経路 `merge` と `promote` の両方があれば、確認は昇格のプランにだけ置く

ベースブランチへのマージ（経路 `merge` の反映）は、昇格のプランより前に済んでいる。昇格のプランの先頭で確認を 1 度走らせれば、
開発版のチャネルの確認と承認ゲート 2 の前の確認を兼ねる（前提 4）。

根拠: Value 4（MVV 版 2）

### 決定 6: 進め方の節の `verify` は `pace_verify` 1 つで読み、無ければプランを書かない

`manual_production_waves` が持っていた「節を選ぶ（ `new close` は `fast` ）・ `verify` が無ければ `DeclError` 」を切り出し、
`route_waves` と共有する。 `new close` は `pace_refusal` を通らないため、 `verify` が無い宣言ではここで止まる。
これは `new close` で経路 `merge` / `promote` を持つ宣言の振る舞いを変える（今は確認なしで流れる）が、確認の無い承認ゲート 2
を通さないというこの課題の目的どおりである。

`verify` が無いときに確認のステップを省いて流す形は採らない。 `pace.md` の「インストール確認がある」の意味を、経路ごとに
「書いてあれば走る」と「必ず走る」に分けることになる。

根拠: Value 1 / Value 6（MVV 版 2）

### 決定 7: 確認したコミットと、昇格でマージされるコミットの一致は、この変更では照合しない

承認資料には確認したコミットを載せ（AC5）、MVV 判定と人がそれを読める。ただし `merged-steps.py promote` は CI が通った
先頭（ `--match-head-commit` ）をマージし、確認の後にベースブランチが進んでいてもそのまま昇格する。照合するには、確認の
ステップが書いたコミットを `promote` のステップへ渡す仕組みが要り、受け入れ条件の外に当たる。範囲外の課題 #1529 として起こした
（未確認のまま残ることの 1 行目）。

根拠: Value 1 / Value 3（MVV 版 2）

## テスト設計

| 受け入れ条件・不変条件 | どの振る舞いで縛るか | どう壊したら落ちるべきか |
| --- | --- | --- |
| AC1 / I2 | 例の宣言で `new sprint --pace auto` を組むと、昇格のプランのステップの id が `verify` → `prepare` → `mvv` の順に並び、 `verify` の `cmd` に `auto.verify` がある | `verify` を置かない・ `mvv` の後に置く |
| AC2 / I3 | `auto.verify` と `fast.verify` が違う宣言で `--pace fast` を組むと、 `verify` の `cmd` に `fast.verify` があり `auto.verify` が無い | 節を `auto` に固定する |
| AC3 / I2 | 確認のコマンドを `false` にした昇格のプランを `supervise.py run` で流すと、報告が止まった で、 `prepare` 以降のステップが走っていない（ `merged-steps.py` と `gh` を呼ばない） | 確認の失敗で `next` へ進ませる・ `on_fail` を付ける |
| AC4 | 確認のコマンドを `true` にすると、 `prepare` → `mvv` → `note` → `promote` の順に進む | `verify` の `next` を `mvv` にする（ `prepare` を飛ばす） |
| AC5 | `verify-facts` を 0 で終えた後、 `--out` にコマンド・終了コード・確認したコミットがあり、 `mvv` の `--material` に `approval-verify.md` がある | 資料を書かない・ `--material` に足さない |
| AC6 / I4 | 標準出力と標準エラーに目印を出す確認で `verify-facts` を打つと、目印が承認資料に無く、 `<out>.verify.log` にあり、権限が 0600 | 出力を資料へ書く・ログの権限を既定のままにする |
| AC7 / I5 | worktreeの HEAD を先頭と違うコミットにするか、追跡中のファイルを変えて `verify-facts` を打つと 3 で終わり、確認のコマンドが走らない（副作用のファイルが無い） | 照合を外す・照合の前に確認を走らせる |
| AC8 | 経路 `merge` だけの宣言で `--pace auto` / `fast` を組むと、検査の後に「導入の確認」（プラン `verify` ）が `then_of` で置かれ、 `false` の確認で流すと止まった になる | ステージを置かない・確認の失敗を通す |
| AC9 / I1 | 経路 `merge` と `promote` の両方がある宣言で組んだ全ステージのプランを数えると、 `verify-facts` を打つステップが 1 つ | 両方の経路に確認を置く |
| AC10 / I7 | `new close` （状態あり）で AC1・AC8 の形のステージが組まれ、「本番」と「導入の確認」のプランが `changed` の実行条件を持つ。条件が 3 を返すと確認のコマンドが走らない | 導入の確認のプランに条件を付けない |
| AC11 / I6 | `--pace` 無しで組んだ昇格のプランのステップが `promote` → `promote-approved` で、 `verify` が無い | `mvv` の有無によらず確認を置く |
| AC12 / I6 | 手動反映の本番系の宣言の `gate-2` のプランと、 `release.form: package-plugin` の宣言のステージが、変更の前と同じ（ `facts` の `cmd` ・上限・ `cwd` を含む） | `facts_step` の切り出しで上限か `cwd` を変える |
| AC13 | `pace.md` を変えた後に `doc-lint.py` が通る（文言は照合しない） | — |
| I3（ `verify` 無し） | `new close` で `fast` の節に `verify` の無い宣言だと、プランを書かずに終了コード 2 で終わる | 空の `verify` で確認のステップを組む |

## 未確認のまま残ること

| 項目 | 内容 |
| --- | --- |
| 確認したコミットと昇格でマージされるコミットの一致 | 照合しない（決定 7）。範囲外の課題 #1529 で扱う |
| 開発版のチャネルへの反映の完了 | NDF は待たない。 `<節>.verify` のコマンドが反映を待たずに走ると、古い版を確かめて通る（前提 2） |
| AC10 の「 `new close --pace auto\|fast` 」 | `new close` は `--pace` を持たず、節はいつも `fast` である（処理の流れ）。AC10 は `--state` 付きの `new close` で確かめ、AC2 の節の選び分けは `new sprint` だけで確かめる。要求の文言との差は設計レビューで確かめる |
| `new close` の振る舞いの変化 | `verify` の無い宣言で経路 `merge` / `promote` を持つと、今は流れる `new close` が止まる（決定 6）。そうした宣言が実在するかは確かめていない |
