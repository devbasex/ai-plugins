# #1319: cross-refactoring: 提案の前に言語に合ったツールで指標を測り、参加者が読んで提案する

正は課題の本文（#1319）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 依頼（原文）

> `/ndf:cross-refactoring` の提案の前に、対象範囲（`--scope`）のコードの指標を、プロジェクトが使う言語に合ったツールで測る。提案する参加者は、その結果を読んだうえで提案する。（2026-09-26 利用者の指示）

## 背景

- 今の提案の材料は、手順書・観点・兆候の語彙・対象範囲だけである（`plugins/ndf/skills/cross-refactoring/prompts/propose.md`）。どこが複雑かは、参加者が各自でコードを読んで見つけている
- 2026-09-26 に radon で測った結果（`~/.local/state/ndf/measure-radon/e1960245/summary.md`）では、本体の関数 2,887 個のうち CC 11 以上が 344 個、CC 41 以上が 10 個（例: `supervise_lib/engine.py` の `Engine.run` が CC 45）、MI が C のファイルが 6 本あった。数値があれば、提案の対象と優先度を根拠つきで選べる
- 言語ごとの知識は `refactoring` の `references/lang-*.md`（Python / JavaScript / TypeScript / PHP）にある。**4 本とも測定ツールの記載はまだ無い**（`grep -n "radon\|lizard\|eslint\|complexity\|phpmetrics" plugins/ndf/skills/refactoring/references/lang-*.md` が 0 件、2026-09-26）
- 提案の枠は今 `開始 + 0.20·B` で終わる（`scripts/refactor_lib/timeline.py` の `PROPOSE_SHARE`）。測定はこの枠か、その前の時間を使う

## 目的

- 参加者が、対象範囲のどこが複雑で大きいかを**同じ数値**から読み、提案の対象と重要度を根拠つきで選べる状態にする
- 測れないプロジェクトでも、今と同じように cross-refactoring が最後まで進む状態を保つ

## 解釈

依頼文の「指標」「言語に合ったツール」「読んだうえで」を次のように具体化する。

| 依頼文の語 | 具体化 |
| --- | --- |
| 指標 | 関数・メソッドごとの循環的複雑度（CC）、ファイルごとの保守性指数（MI）か大きさ（関数の数・最長の関数の行数）、ファイルごとの行数（SLOC） |
| 言語に合ったツール | 対象範囲のファイルの拡張子から言語を判定し、その言語に割り当てたツールで測る。割り当ては既定を持ち、プロジェクトが上書きできる |
| 読んだうえで | 提案のプロンプトが指標のファイルのパスを示し、提案の項目に根拠にした値を書ける欄がある |

## 前提

- 前提 1: 測るのは提案の前に 1 回だけである。リファクタリング計画・実装・検証の途中で測り直さない（改修後の指標の比較は範囲外）
- 前提 2: 測るのはオーケストレーター（`drive.py` / `refactor.py` の側のスクリプト）であり、参加者の CLI には測らせない。LLM の申告を数値の出所にしない
- 前提 3: 対象は `--scope` のうち、git が追跡しているファイルだけである（生成物・無視されたファイルを測らない）
- 前提 4: ツールの一時実行に要るもの（`uvx` / `npx` などのランナー）が無い環境は「ツールが無い」として扱う。ランナー自体を入れない
- 前提 5: ツールの取得に通信が要る場合、その所要も測定の時間に数える。通信できないのは測定の失敗として扱う
- 前提 6: 指標のファイルは提案の前に 1 つだけ作り、参加者の全員が同じ内容を読む。参加者ごとに作り分けない
- 前提 7: 指標があっても、提案の採否・順位の規則（`merge-proposals` とリファクタリング計画）は変えない。指標は参加者が読む材料に留まる
- 前提 8: `.ndf/` の測定の宣言が JSON として読めない・形が違うとき、cross-refactoring は止めずに既定で測り、宣言を使わなかった理由を指標のファイルと計画に残す（課題の元の受け入れ条件「測定の失敗では止めない」に揃える）

## 対象範囲

含む:
- 提案の前に、対象範囲の言語を判定して指標を測る手順
- 言語とツールの対応の既定と、プロジェクトごとの上書き（`.ndf/` の宣言と引数）
- 指標のファイル（形・置き場・載せる範囲）
- 提案のプロンプトへの指標のファイルの提示と、提案の JSON の根拠の欄
- 測定の時間の上限と、想定最大時間の配分
- 測れなかったときの記録と続行
- 計画と完了報告への、言語・ツール・版・所要秒の記載
- `refactoring` の `references/lang-*.md` への、言語ごとのツールの記載

含まない:
- cross-review への指標の受け渡し（効いたら別の課題で広げる）
- 指標の閾値でリファクタリングの採否を機械的に決めること（採否は今の計画の規則のまま）
- 改修の前後で指標を比べること
- 対象プロジェクトの依存（`pyproject.toml` / `package.json` / `composer.json` など）へのツールの追加
- `lang-*.md` の無い言語向けの参照文書の新設

## ドメインイベント

| # | イベント | 引き金 | 失敗したとき | 順序の前提 |
| --- | --- | --- | --- | --- |
| E1 | 測定の設定を読み込んだ（既定・`.ndf/` の宣言・引数を重ねた） | `init` | 宣言が壊れている → 宣言を使わずに既定で続け、読めなかった理由を指標のファイルに残す（前提 8 へ） | — |
| E2 | 対象範囲のファイルを言語ごとに分けた | E1 の後、提案の前 | 対象範囲に言語を判定できるファイルが 1 本も無い → 「測る言語が無い」と記録して提案へ進む | `--scope` が確定している（`init` の範囲の確定） |
| E3 | 言語ごとにツールを起動した | E2 | ツールが無い・起動に失敗した・上限の時間を超えた → その言語を「測れなかった」として理由を残し、ほかの言語を続ける | E2 |
| E4 | ツールの出力を指標の共通の形へ直した | E3 が成功した言語 | 出力を読めない → その言語を「測れなかった」として理由を残す | E3 |
| E5 | 指標のファイルを書き出した | 全言語の E3/E4 が終わった | 書き出せない → 指標なしで提案へ進み、理由を状態ファイルと計画に残す | E4（測れた言語が 0 でも書く） |
| E6 | 参加者が指標のファイルを読んで提案した | 提案の手順の起動 | 指標のファイルが無い → 今と同じ材料で提案する | E5、読み取り用の作業ディレクトリの同期 |
| E7 | 計画と完了報告に測定の記録を載せた | リファクタリング計画の書き出し・`report` | — | E5 |

## 用語

| 用語 | 意味 |
| --- | --- |
| 指標 | 対象範囲のコードをツールで測った値。関数ごとの循環的複雑度、ファイルごとの保守性か大きさ、行数 |
| 指標のファイル | 提案の前に 1 回だけ作り、参加者の全員が読む測定の結果 |
| 測定ツール | 言語ごとに指標を測る外部のコマンド（Ruff・complexipy・lizard など） |

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 測定の所要は AC13 の上限に収まる。上限は想定最大時間から出る（既定 30 分での実値は設計で示す） |
| 運用・保守性 | 測れなかった理由は識別子（例: `tool_missing` / `unsupported_language` / `tool_failed` / `unreadable_output` / `timeout` / `disabled`）で残し、指標のファイル・計画・完了報告で同じ識別子を使う |
| システム環境 | 測定のために、利用者の環境へ常駐のインストールを増やさない。一時実行のキャッシュ（`uv` / `npm` のキャッシュ）への書き込みは許す（設計で扱いを決める） |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | cross-refactoring の本体は `plugins/ndf/skills/cross-refactoring/`。**既定で動くものから `plugins/ndf/scripts/experimental/` を参照しない**（`AGENTS.md`「安定版と実験版」）。この変更は既定で働く手順を変えるため安定版の経路で入れる |
| コーディング規約 | `refactor.py` は標準ライブラリだけで動かす（`SKILL.md` の「uv 自己完結、標準ライブラリのみ」）。測定ツールは外部コマンドとして呼び、Python の依存に足さない。外部コマンドは書く前に実行して挙動を確かめる（`AGENTS.md` の DO） |
| テスト戦略 | 言語の判定・設定の重ね合わせ・出力の読み取り・時間の算術は単体テスト。測れない経路は偽のツールのコマンドで確かめる。`.md` の文言を照合するテストは書かない（`AGENTS.md` の DON'T） |
| 共通の部品 | cross-review と同じ役割の定数・関数を分けない（範囲外の cross-review への受け渡しを後で足せる置き場にするかは設計で決める） |
