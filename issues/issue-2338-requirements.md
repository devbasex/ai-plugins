## 目的

- NDF のスクリプトの 1 回の起動について、始まり・判断・診断・失敗・終わりと止まった理由を、実行の識別子 1 つで 1 つのファイルから追える状態にする
- 標準エラーへの診断を書く経路を 1 つにし、記録に残らない診断と、途中で切れた理由を無くす
- 記録とログの不統一が原因の課題（#2335 の型 B）を、仕組みを入れた後にまとめて確かめて閉じる

## 前提

- 前提 1: 柱 P1（#2337 結果の契約と核のスケルトン）がマージされ、入口が実行の核（`lib/run_core.py` の `main`）を通っている。この課題の実装は P1 のマージの後に始める。2026-11-04 時点で #2337 は未完了（`gh issue view 2337` の state が OPEN）で、`plugins/ndf/scripts/lib/` に `run_core.py` は無い（`ls plugins/ndf/scripts/lib/ | grep run_` の結果は `run_metrics.py`・`run_owner.py`・`run_state.py`・`run_state_kinds.py` の 4 件）
- 前提 2: 実行の記録の行の形・置き場・寿命は #2335 の設計に従う。行は `run_id`・`parent_id`・`at`・`event`・`entry`・`fields` を持ち、置き場は `${NDF_STATE_DIR:-~/.local/state/ndf}/runs/<リポジトリ>/<UTC の日付>/<起点の実行の識別子>.jsonl`、寿命は 30 日である（`issues/issue-2335-design.md` の「実行の記録の行」「非機能の実現方式」、決定 6）
- 前提 3: 使用量の帳簿・プランの状態の記録（`progress.jsonl`）・問い合わせの記録（`ask.jsonl`）は、今の置き場と形のまま業務のデータとして残し、行に実行の識別子を足して実行の記録とつなぐ（#2335 決定 6）。帳簿の集計を実行の記録から数え直す変更はこの課題に含めない
- 前提 4: シェルの入口は、#2335 の設計どおり実行の核が子として起こし直す（`rc_enter`）。シェルの本体が標準エラーへ書いた行は、核が受けて実行の記録へ診断として書く。シェルの本体の `>&2` は書き換えの対象にしない
- 前提 5: 対象は `plugins/ndf/scripts` と `plugins/ndf/skills/*/scripts` の、テスト・実験版（`plugins/ndf/scripts/experimental/`）・hook を除く入口とステップである（#2335 の対象範囲）
- 前提 6: 実行の記録へ書けないとき（始まりでも途中でも）、核は標準エラーへ理由を出し、結果を `stopped` にする（#2335 の不変条件 I3）
- 前提 7: SIGKILL で終わった実行には終わりの行が無い。終わりの行が無いことを「途中で強制終了した」と読む
- 前提 8: 1 スプリントで出す入口の移し替えは 3 本の Pull Request までとし、残りは同じ柱の次のスプリントへ送る（`issues/issue-2335-design-pillars.md` の「移す順序と大きさ」）

## 対象範囲

含む:
- 実行の記録の書き口（`lib/run_log.py`）と、核からの呼び出し（始まり・判断・診断・失敗・終わり）
- 子の実行が親の実行の識別子を受けて同じファイルへ書くこと
- 標準エラーへの診断の経路を 1 つにすること（Python は実行の文脈の書き口、シェルは核が受ける）と、直書きを落とす構造チェック
- 止まった理由を切る処理を外すこと
- 使用量の帳簿とプランの状態の記録の行へ実行の識別子を足すこと
- 記録の寿命（30 日）の掃除
- 子の課題 8 件（#1687・#1839・#1893・#1979・#2059・#2132・#2205・#2300）の再現の手順を通し、閉じるか残すかを本文へ記録すること

含まない:
- hook を核へ移すこと、hook が書く問い合わせの記録の形を変えること（#2335 の対象範囲の外）
- 使用量の帳簿・プランの状態の記録・問い合わせの記録を実行の記録へ吸い込むこと（前提 3）
- 子の課題を 1 件ずつ直す Pull Request
- 人へ見せる Markdown の報告の形（柱 P7 #2340）
- 持ち主の記録の取り合い（柱 P3 #2342）と、入力の出所の記録（柱 P8 #2341）。どちらも実行の記録の書き口を使うが、行を書く処理はそれぞれの柱が足す
- 実行の記録を読んで集計する道具（集計の手段は子の課題の判断で決める）

## 用語

| 用語 | 意味 |
| --- | --- |
| 実行の核 | 入口・ステップが必ず通る共通の実行の仕組み（#2335） |
| 実行の識別子 | 1 回の入口の実行に実行の核が振る識別子（`run_id`） |
| 実行の記録 | 1 回の起動（子の実行を含む）の始まりから終わりまでを、実行の識別子つきで書く JSON Lines のファイル |
| 実行の文脈 | 実行の核が本体へ渡す 1 つの値。記録の書き口（`ctx.log`）を持つ |
| 起点の実行 | 親の実行の識別子を持たない実行。実行の記録のファイル名になる |
| 子の実行 | 核を通る入口が子プロセスとして起こした、核を通る入口の実行。親の実行の識別子を持つ |
| 診断 | スクリプトが人へ向けて標準エラーへ出す文（警告・進み具合・失敗の理由）。結果 JSON とは別の出力 |
| 使用量の帳簿 | NDF が起動したエージェントの呼び出しごとの使用量を追記する JSON Lines |

## 受け入れ条件

### 1 つの記録で追える

- [ ] 1. 核を通る入口を正常・例外・SIGTERM・時間切れの 4 つの終わり方で起動すると、どの場合も実行の記録の 1 ファイルに、同じ実行の識別子を持つ行が始まりの行（`event: start`）から終わりの行（`event: end`）まで並ぶ。すべての行が `run_id`・`at`（UTC の ISO 8601）・`event`・`entry`・`fields` を持つ
- [ ] 1a. 核を通る入口が別の入口を子プロセスで起こすと、子の行は親と同じファイルに書かれ、子の行の `parent_id` が親の `run_id` と一致する
- [ ] 1b. 子の実行が親と並行に同じファイルへ書いても、ファイルのすべての行が 1 行ずつ JSON として読める
- [ ] 1c. 本体が下した判断（`event: decision`）と、止まった理由（例外の理由・`stopped` の `summary` と `gaps`）が行として残る。終わりの行の `fields` は、標準出力へ出した結果 JSON と終了コードを持つ
- [ ] 1d. 核を通る起動の中で追記された使用量の帳簿の行とプランの状態の記録（`progress.jsonl`）の行が、その実行の識別子を持つ。核の外の起動で書いた行は、実行の識別子を持たないまま今と同じ形で読める
- [ ] 1e. 核の起動が、30 日を超えた日付のディレクトリを実行の記録の置き場から消す。消せなかったときは診断を書いて本体を続ける
- [ ] 1f. 実行の記録の置き場を書けない場所にして起動すると、標準エラーに書けなかった理由が出て、結果が `stopped` になる

### 診断の経路が 1 つ

- [ ] 2. 対象（前提 5）の Python の入口とステップで、標準エラーへの出力が実行の文脈の書き口（`ctx.log("diag", ...)` に当たる関数）1 つを通る。`print(..., file=sys.stderr)` と `sys.stderr.write` の直書きを構造チェック（`scripts/check-script-structure.py`）が落とす。2026-11-04 の時点の直書きは 131 か所（`print(..., file=sys.stderr)` 126 か所・63 ファイル、`sys.stderr.write` 5 か所。下の「調べ方」のコマンド）
- [ ] 2a. 書き口を通した診断は、標準エラーと実行の記録（`event: diag`）の両方に出る。シェルの本体が標準エラーへ書いた行も、実行の記録に `event: diag` で残る
- [ ] 2b. 移す途中は、まだ直書きを持つファイルを例外リストに載せ、例外リストに行を足す変更を構造チェックが落とす（#2335 の受け入れ条件 1a と同じ扱い）

### 止まった理由が切れない

- [ ] 3. 本体が渡した止まった理由の文字列（`summary`・`gaps`・例外の理由）が、結果 JSON と実行の記録の終わりの行に、途中で切られずに同じ文字列で残る。2026-11-04 の時点で理由・出力を先頭 N 字で切っている 10 か所（下の「調べ方」のコマンド）を、実行の記録へ全文を書いた後に人へ見せる表示だけを短くする形にする
- [ ] 3a. 外部コマンドの失敗の出力のように 1 行の上限（未決 1）を超える理由は、全文を記録からたどれる（全文の置き場のパスと長さが行に残る）

### 子の課題

- [ ] 4. 子の課題 8 件（#1687・#1839・#1893・#1979・#2059・#2132・#2205・#2300）それぞれについて、柱の仕組みを入れた後に再現の手順を 1 回通し、閉じた（解消を確かめた）か残した（理由つき）かをこの課題の本文の「子の課題の判定」の節へ記録する

### 起きてはいけないこと

- [ ] 5. 実行の記録に、秘密（トークン・鍵・認証情報）の値が書かれない。秘密を入れた環境変数で起動し、本体がその値を診断と例外の理由へ入れても、ファイルに値が出ない（#2335 の受け入れ条件 13・不変条件 I9）
- [ ] 6. 利用者の端末に出る診断の文が、移す前と同じ文で標準エラーへ出る（記録へ書くことで端末の出力が消えない）
- [ ] 7. 既存の全体テストが、この柱の各 Pull Request のマージの前後で通る

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 1 回の起動を実行の識別子 1 つで、始まりから終わりまで 1 ファイルから追える（受け入れ条件 1）。記録の寿命は 30 日（前提 2） |
| 移行性 | 移す対象: Python の入口の標準エラーへの直書き。順序: #2335 の部品の順（supervise のプラン・判定・キュー → cross-refactoring → 課題を閉じる処理 → リリース → 外部 CLI の監視 → 使用量の帳簿 → 残り）。並走: 例外リストに載った入口は直書きのまま動く。切り戻し: Pull Request ごとの revert で前の形へ戻る。実行の識別子を持たない既存の帳簿と状態の記録の行は、そのまま読める（受け入れ条件 1d） |
| セキュリティ | 受け入れ条件 5。秘密の扱い（C1）と認証・認可（C2）は変えない |
| システム環境 | Claude Code と Codex の両方の配布で同じ核が動く。シェルの入口は bash で動く |
