## 目的

- NDF のスクリプトの 1 回の起動について、始まり・判断・診断・失敗・終わりと止まった理由を、実行の識別子 1 つで 1 つの記録から追える仕組みを作る
- その仕組みへ、実際に起きた不具合の場所を 2 つ移す。監視のループ（`lib/monitor_loop.py`。#2059: 先に出た警告に拒否の件数の警告が消される）と、検査の記録（`check-trigger.py`。#2300: 落ちた工程が「不明」になる）である
- 記録の出力先を 1 つの設定で差し替えられる形にし、手元はファイル、Factory は別の出力先（#2608 が作る）へ書けるようにする

## 前提

- 前提 2: 実行の記録の行の形は #2335 の設計に従う。行は `run_id`・`parent_id`・`at`・`event`・`entry`・`fields` を持つ。既定の置き場は、#2606 の寿命の区分の「永続」として、状態の置き場の関数（`lib/state_home.py`。#2766）が返す利用者の根の下の `runs/<リポジトリ>/<UTC の日付>/<起点の実行の識別子>.jsonl` に置く。寿命は 30 日である。理由: 実行の記録は振り返りで止まった原因を探すために使い、コンテナの再起動で消える場所（コンテナの根 `~/.local/state/ndf`）に置くと残らない（#2606 の実測）。同じ利用者の根に、検査の記録（`checks/`）がすでにある
- 前提 3: 使用量の帳簿・プランの状態の記録（`progress.jsonl`）・問い合わせの記録（`ask.jsonl`）・検査の記録（`checks/`）は、今の置き場と形のまま業務のデータとして残す。検査の記録の行には、#2300 の判定（受け入れ条件 2d・2e）のために実行の識別子を任意の鍵として足す。ほかの記録の行には足さない
- 前提 4: シェルのエントリポイントの標準エラーを記録へ写すことは、この課題に含めない。移す 2 ファイルはどちらも Python である

- 前提 6: SIGKILL で終わった実行には終わりの行が無い。終わりの行が無いことを「途中で強制終了した」と読む
- 前提 7: この課題の実装は 1 スプリント、Pull Request 1〜2 本に収める（2026-11-05 の利用者の答え）
- 前提 8: CloudWatch Logs への出力の実装は #2608 が持つ。この課題は出力先を差し替える仕組みと、既定のファイルの出力だけを作る
- 前提 9: 設計の前に、複数のプロセスに対応したログの出力・収集・保管の既存の仕組みを比べ、設計の外部の調査に採否の表を置く。比べる候補は、出力（Python 標準の `logging` の `QueueHandler` / `QueueListener`・structlog・loguru の `enqueue`・concurrent-log-handler など複数のプロセスから 1 ファイルへ書けるハンドラ）、形式と相関（OpenTelemetry の logs と trace の相関と実行の識別子の伝え方・JSON Lines）、収集と保管（Fluent Bit・Vector など手元の収集・journald・CloudWatch Logs）である。観点は、並行の書き込みの安全さ・プロセスの親子と別のコンテナ・中断に強いか・依存の重さ・出力先の切り替え・保管と寿命・秘密の伏せ方・運用の実績の 8 つである。自作を残すなら、比べた候補と採らない理由を決定の記録に書く（プロジェクトの方針「基盤は既存ライブラリを使う」）

## 用語

| 用語 | 意味 |
| --- | --- |
| 実行の核 | エントリポイント・ステップが必ず通る共通の実行の仕組み（#2335） |
| 実行の識別子 | 1 回のエントリポイントの実行に実行の核が振る識別子（`run_id`） |
| 実行の記録 | 1 回の起動（子の実行を含む）の始まりから終わりまでを、実行の識別子つきで書く JSON Lines の行の並び。既定の出力先はファイル |
| 実行の文脈 | 実行の核が本体へ渡す 1 つの値。記録の書き口（`ctx.log`）を持つ |
| 出力先 | 実行の記録の行を書く先。既定はファイル。設定 1 つで別の出力先へ差し替える |
| 起点の実行 | 親の実行の識別子を持たない実行。実行の記録のファイル名になる |
| 子の実行 | 核を通るエントリポイントが子プロセスとして起こした、核を通るエントリポイントの実行。親の実行の識別子を持つ |
| 診断 | スクリプトが人へ向けて標準エラーへ出す文（警告・進み具合・失敗の理由）。結果 JSON とは別の出力 |
| 検査の記録 | `check-trigger.py` が検査の事象（eval・check・escape）を 1 行ずつ追記する JSON Lines（`checks/<所有者>__<リポジトリ>.jsonl`。置き場は `${CLAUDE_PLUGIN_DATA}` があればその下、無ければ利用者の根の下） |

## 受け入れ条件

### 1 つの記録で追える

- [ ] 1. 核を通るエントリポイントを正常・例外・SIGTERM・時間切れの 4 つの終わり方で起動すると、どの場合も実行の記録の 1 ファイルに、同じ実行の識別子を持つ行が始まりの行（`event: start`）から終わりの行（`event: end`）まで並ぶ。すべての行が `run_id`・`at`（UTC の ISO 8601）・`event`・`entry`・`fields` を持つ
- [ ] 1a. 核を通るエントリポイントが別のエントリポイントを子プロセスで起こすと、子の行は親と同じファイルに書かれ、子の行の `parent_id` が親の `run_id` と一致する
- [ ] 1b. 子の実行が親と並行に同じファイルへ書いても、ファイルのすべての行が 1 行ずつ JSON として読める。テストでは子の実行を 4 つ以上並行に起こし、各子が 100 行以上を書く
- [ ] 1i. 同じ利用者の根を共有する 2 つのコンテナ（テストでは、同じ置き場を指す別々のプロセスの木）が同じ日付のディレクトリへ同時に書いても、どのファイルのすべての行も JSON として読め、行の数が書いた数と一致する
- [ ] 1j. 書いている途中の子の実行を SIGKILL で止めても、ほかの実行の行はすべて JSON として読め、止めた子の実行は終わりの行が無いことで判別できる（前提 6）。止めた子の書きかけの 1 行が残る場合は、読む側が JSON として読めない行を飛ばして数えられる
- [ ] 1c. 本体が下した判断（`event: decision`）と、止まった理由（例外の理由・`stopped` の `summary` と `gaps`）が行として残る。終わりの行の `fields` は、標準出力へ出した結果 JSON と終了コードを持つ
- ~~1d. 核を通る起動の中で追記された使用量の帳簿の行とプランの状態の記録の行が、その実行の識別子を持つ~~ → 外す（2026-11-05、承認ゲート 1 の利用者の答え。検査の記録への追加は受け入れ条件 2d へ移した）
