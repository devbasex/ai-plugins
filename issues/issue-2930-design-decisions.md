# claude -p の起動先の設計: 決定の記録（#2930）

設計文書の本体は [issue-2930-design.md](issue-2930-design.md) にある。外部の調査の番号（`STD1` など）は本体の「外部の調査」の表を指す。

## 決定の記録

### 決定 1: 規則を if 文の連鎖にしないため、起動先を「観測のスナップショット → 決定」の純粋な関数と、規則の関数の並びで決める

規則は 7 つ、組は 4 つ、組の中の並べ方は 3 通りある。条件の連鎖で書くと、規則の順序と条件の組み合わせがコードの入れ子に埋もれ、表のテストの行と対応しなくなる。規則と組を「名前と小さな関数」の並びにすると、並びがそのまま設計文書の表になり、決定には当たった規則の名前を載せられる。観測を集める部分を分けるので、決定の関数は時刻もファイルも読まず、同じ入力から同じ決定が出る（I1）。

外部の規則エンジン（決定表のライブラリ）は採らない。規則が 7 つで、Python の関数の並びで足り、依存を増やす理由が無い。既存の切り替えの CLI（LIB1・LIB2）は、API キーの利用枠と区切りでの選び直しを持たないため使えない。

- 作り方: 自前で作る
- 比べた候補: LIB1 / LIB2 / LIB3 / PRD1 / PRD2

根拠: Value 5 / Value 7（MVV 版 6）

### 決定 2: 判定のための状態を持たないため、API キーの状態のファイルと一度立つと戻らない印を外し、除外は 1 回の呼び出しの中だけに置く

残高切れ・認証の失敗・上限を返した API キーは、その呼び出しの除外の集合へ足すだけにし、ファイルへ書かない。次の呼び出しではまた候補に入る。費用は、尽きたキーで起動した 1 回の失敗だけである（STD1 の残高切れは要求の受付で返り、推論を伴わない）。上限で替えるアカウントが無いときにキーを使う印（`limit_hit`）も外し、その判定は規則 2 の述語へ移す。

認証の失敗を保留するファイルを残すと、キーを登録し直すまで状態の掃除が要り、プロセスの終了と再起動のたびに扱いを決めることになる。外したキーを日に 1 回だけ試す形も、試した時刻を持つため採らない。

根拠: Value 7 / Value 5（MVV 版 6）

### 決定 3: 5 時間の上限の観測を控えとして残すため、`account.json` の `limit` はリセット時刻で切れる観測として扱い続ける

5 時間の上限に当たった応答は、使用率の応答と同じく提供元から取った観測である。使用率の控えは最長 300 秒古く、上限の直後に読むと 95% のように上限でない値を返すことがある。上限の観測を捨てると、同じアカウントを選び直して 1 回の起動を無駄にする。今の `limit` はリセット時刻を過ぎるか、後に読んだ使用率が上限でないと分かった時点で効かなくなる（`Account.observed_until`）。決定の関数はこれを `limited_until` の時刻として受け取るだけで、復帰先や戻り待ちの印は持たない。

上限の観測を外して使用率の応答だけで決める形は、上の無駄な起動が残るため採らない。

根拠: Value 7（MVV 版 6）

### 決定 4: 付与日を持たずに月が替わっても計算し直せるよう、週の利用枠を「月の額 × 7 ÷ 30」、使用額を帳簿の直近 7 日の合計で数える

月のクレジットは請求の周期ごとに付与され繰り越さない（STD1）。直近 7 日の使用額が「月の額 × 7 ÷ 30」を超えない範囲で使えば、付与日・期限・残高を持たずに、月の途中のどの 7 日を取っても利用枠に収まる。8 日前の使用は合計から自然に抜ける（受け入れ条件 12）。残高を読む手段（Admin API）は利用者の決定で使わない。

更新日を宣言して月ごとに使用額を 0 へ戻す形は、宣言が 1 つ増え、更新日を過ぎた時点の扱い（状態）が要るため採らない。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1 / STD2

根拠: Value 3 / Value 6（MVV 版 6）

### 決定 5: 「即座にやめる」を観測で満たすため、使用率の控えをリセット時刻で取り直し、前回の決定を次の決定へ渡さない

どれか 1 つのアカウントの週の枠がリセットされると、そのアカウントの週の使用率は T を下回り、規則 2 の述語が偽になる。控えの寿命の中でもリセット時刻を過ぎた控えは取り直すので、リセットの後の最初の起動で API キーを使わない（受け入れ条件 9）。前回 API キーを使ったことは、スナップショットの入力に無い。

リセットを検知するために短い間隔で使用率を取りに行く確かめの処理は、起動のたびに決めるため要らない。

根拠: Value 5（MVV 版 6）

### 決定 6: 切り替え（再起動）の回数を減らすため、切り替えの余裕を「今のアカウントが最良の候補と同じ組にあるなら替えない」に置く

費用を生むのは切り替えである。組が同じなら、今のアカウントのまま続けても組の方針（5 時間の枠を先に使う・週だけの枠へ後で回る）は守られる。組が変わったとき（5 時間の枠がリセットされたアカウントが組 1 に戻った、今のアカウントの週の使用率が T を超えて組 3 へ移った、今のアカウントが上限に当たった）だけ替える。受け入れ条件 18 の「5 時間の枠がリセットされたアカウントが先頭に来ると次の区切りで切り替わる」は、今のアカウントが組 2 か組 3 にあれば成り立つ。

使用率の差（例: 10 ポイント）を余裕にする形は、組 1 の中で 2 つのアカウントの間を行き来しうるうえ、差の値の根拠が無いため採らない。同じ余裕を worker・supervisor の起動口にも当て、規則を 1 つにする。

根拠: Value 3 / Value 7（MVV 版 6）

### 決定 7: 使用率の定期の確認を外すため、relay の `UsageWatch` を消し、区切りの決定に閾値の切り替えと従量の接続からの戻りを任せる

`UsageWatch` は 300 秒ごとに今のアカウントの使用率を読み、「次の区切りで替える」印（`due`）と「従量の接続から戻せる」印（`recover`）を立てる。どちらの印も、区切りの時点で決定の口を呼べば同じ結論が出るため要らない。区切りの間に使用率を取りに行かないので、受け入れ条件 19 を満たす。

印だけを外して画面への案内のために確認を残す形は、区切りの間の取得が残るため採らない。

根拠: Value 5 / Value 3（MVV 版 6）

### 決定 8: 組 3（週の使用率が T 以上）の中は、週の使用率の小さい順に並べる

組 3 のアカウントは、どれも週の枠が尽きかけている。週の枠は数日戻らないため、残りの割合の大きいものから使う。今の並べ方（枠の大きさの換算表 × 残りの割合）は、換算表に無いプランの値を宣言で補う必要があり、組 3 の目的（週の枠を均して使い切る時期を遅らせる）に対して入力が多い。

根拠: Value 3（MVV 版 6）

### 決定 9: near-limit の発動の判定から、再登録が要るアカウントを除き、使用率を読めないアカウントは発動を止める側に数える

再登録が要るアカウントは利用者が直すまで使えず、使用率も取れない。数えると、そのアカウントがある限り API キーへ逃がせない。使用率を読めないだけのアカウント（一時的な取得の失敗）は、週の枠が残っている可能性があるため、T 未満と同じく発動を止める側に数える（I2）。誤って API キーを使うより、1 回の取得の失敗で発動が遅れるほうが、週の利用枠を守れる。

根拠: Value 3（MVV 版 6）

### 決定 10: 閾値 T の既定値を 85% にする

下の「閾値 T の既定値」の数値から決める。80% では、アカウントの残りが `claude -p` の 1.6 日分ある時点で利用枠を使い始め、本当に尽きかけたときに利用枠が残らない。90% では、残りが 0.8 日分になってから発動し、API キーの利用枠（約 10 時間分）を使い切った後に対話のセッションへ残る量が少ない。85% は、発動の時点でアカウントの残り（$426）と API キーの利用枠（$150）を足して `claude -p` の約 1.6 日分を確保する。T は `api-key-use near-limit --weekly-at` で変えられる。

根拠: Value 4（MVV 版 6）
