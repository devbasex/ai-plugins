## 何が起きたか

2026-11-14、#1142（NDF の作り直し）の設計レビュー #3347 で、作り直しの NDF の依存 24 本のうち 14 本が最新の安定版より古いと分かった。バージョンの遅れを知らせる検査も、バージョンを上げる決まった操作も無かった。利用者は「依存はできるだけ最新の安定版。公開から 7 日待つ。httpx は 0.28.1 に固定」と決め、仕組みは Renovate（依存の更新の PR を作るツール）と比べてから決めるとした（原文は末尾）。

設計は 2026-11-15 に済み、Renovate を GitHub Actions の上で動かす形を選んだ（設計 PR #3522、`issues/issue-3370-design.md` の決定 1）。その後 11.0.0 の入れ替え（#3304）で、作り直しの保存先 `plugins/ndf-next/` は `plugins/ndf/` になった。実装はまだ入っていない。

## 種類

機能追加（依存のバージョンを上げる仕組み・遅れの知らせ・7 日待つ規則は、今の定義と CI に約束が無い）

## 今の姿

NDF の Python の依存は、プラグインの中の定義と lock が持つ。11 系の配置は次のとおりである（2026-11-20、main `ad05e476d` で確かめた）。

| ファイル | 中身 | この課題での扱い |
| --- | --- | --- |
| `plugins/ndf/pyproject.toml` | NDF の依存 23 本（`dependencies`）と dev グループの 2 本（pytest・pytest-xdist）。バージョンはすべて `==` で固定し、`dbos==3.4.0`・`httpx==0.28.1` を持つ。`[tool.uv]` は `package = false` だけで、7 日待つ設定（`exclude-newer`）は無い | 対象 |
| `plugins/ndf/uv.lock` | 上の定義の lock | 対象 |
| 根の `pyproject.toml`・`uv.lock` | 根のテストと `scripts/` の環境。NDF の依存の一部を extra に別のバージョンで持つ（例: `githubkit==0.16.1`・`dbos==3.1.0`）。NDF のプラグインはここを読まない（根の `pyproject.toml` の頭の注記） | 含まない（#3691） |
| `plugins/playwright-kit/…`・`plugins/mcp/mcp-serena/` の `pyproject.toml`・`uv.lock` | ほかのプラグインの依存 | 含まない（#3691） |

- **遅れ**: `uv tree --outdated --depth 1 --frozen --project plugins/ndf`（2026-11-20）で、25 本のうち 13 本に新しいバージョンがある（dbos・filelock・markdown-it-py・mdit-py-plugins・pydantic・python-dotenv・ruff・semver・slack-sdk・sqlalchemy・tenacity・tree-sitter・pytest）。この数は公開から 7 日の規則を当てていない
- **検査**: CI は `uv lock --check --project plugins/ndf` で定義と lock の食い違いを落とす（`.github/workflows/script-structure.yml:97`）。遅れを知らせる検査は無い
- **上げる手段**: 決まった操作は無い。リポジトリの Dependabot（`.github/dependabot.yml`）は GitHub Actions だけを週 1 回見て、Python の依存は見ない。Renovate の設定（`.github/renovate.json`）は無い
- **定義の頭の注記**は作り直しの間のまま残っている（プロジェクト名 `ndf-rebuild`、バージョンの形 `11.0.0-dev.N` の決め方、「根の pyproject.toml は今の NDF のため」）

設計（済み）の決定の要点は次のとおりである。設計文書は 11 系の配置へ直し、#3691 の設計とまとめて [issue-3370-3691-design.md](https://github.com/devbasex/ai-plugins/blob/main/issues/issue-3370-3691-design.md) へ移した（2026-11-21、設計 PR は lz13-deps のレーンが出す）。 まとめた設計は #3691 の範囲（ほかの lock・推移的な依存・脆弱性・Actions・外部 CLI）を足し、下の要点のうち対象の絞り（前の決定 6）と固定の理由の形（前の決定 5）を置き換えた。実装は、まとめた設計に従う。

- Renovate を GitHub Actions の上で GitHub App の token で動かし、対象を `plugins/ndf` の Python の依存に絞る（決定 1・2・6。まとめた設計の決定 6 は、対象をすべての lock へ広げた）
- 依存の一覧の Issue でチェックを入れたときだけ、更新を 1 本にまとめた PR を作る（決定 3）
- 7 日は Renovate の待つ日数と uv の `exclude-newer` の 2 か所に置き、値の一致をテストで縛る（決定 4）
- httpx の固定と理由は Renovate の依存ごとの規則に書く。DBOS は対象から外す（決定 5・7。まとめた設計の決定 5 は、理由を種類・相手・制約・見直す日の欄で書く）
- 最初の版上げは実装の PR が行い、上げる先は実装の時点で uv に決めさせる（決定 7）
- lock を作り直せない上げ方は、Renovate のチェック `renovate/artifacts` が赤になることで失敗を返す（決定 8）

## 何を足すか・変えるか

| | 今 | 足した後 |
| --- | --- | --- |
| `plugins/ndf` の依存のバージョン | 25 本のうち 13 本が最新より古い | DBOS と httpx を除き、公開から 7 日たった最新の安定版 |
| 7 日待つ規則 | どこにも無い | `plugins/ndf/pyproject.toml` の `exclude-newer = "7 days"` と Renovate の設定 |
| 遅れの知らせ | 無い | Renovate が週 1 回、遅れを 1 件の Issue（依存の一覧）にまとめる |
| バージョンを上げる操作 | 無い | 依存の一覧の Issue でチェックを入れると、更新を 1 本にまとめた PR が届く |
| httpx の固定の理由 | 定義のバージョンだけ | Renovate の依存ごとの規則に理由の文とともに書く |

## 今の利用者への影響と互換

- NDF の利用者には、依存のバージョンが変わるだけで、コマンドと結果の形は変わらない
- このリポジトリの開発者には、依存の一覧の Issue と、チェックを入れたときの更新の PR が届くようになる

## なぜ困るか

- 依存が古いまま残り、直しの入ったバージョンを使えない。遅れに気づく手段が無いため、遅れは数えるまで分からない
- バージョンを上げるたびに手でバージョンと lock を書き換えるので、公開から 7 日待つ規則を人が忘れると破れる

## 目的

- NDF（`plugins/ndf`）を保守する開発者が、公開から 7 日たった最新の安定版へ依存を保ち、週 1 回の知らせとチェック 1 つで上げる PR を作れる

## 対象範囲

含む:
- `plugins/ndf/pyproject.toml`・`plugins/ndf/uv.lock` のバージョンを、DBOS と httpx を除いて上げる先へ上げる
- Renovate の導入（設定・GitHub Actions のワークフロー・GitHub App）。対象は `plugins/ndf` の Python の依存
- `exclude-newer = "7 days"` と Renovate の待つ日数の一致のテスト
- 上げたバージョンで落ちる既存のコードとテストの直し（#3347 の決定 108）
- `plugins/ndf/pyproject.toml` の頭の注記を、バージョンの選び方と上げる操作を書いた形に直す

含まない:
- DBOS のバージョン（3.5.0 以上へ上げるのは C1+ の続き。#3285 の追補）
- 根の `pyproject.toml`・`uv.lock`、ほかのプラグインの lock、推移的な依存、コードの中で固定したバージョン、外部 CLI と GitHub Actions のバージョン（#3691・#3380 の範囲）
- 脆弱性の知らせ（#3691 が持つ。まとめた設計の決定 9）
- GitHub Actions の SHA での固定と Dependabot の `cooldown`（#3388 へ回した）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 遅れの知らせは 1 件だけで、週ごとに新しい Issue を増やさない（MVV の Value 6） |
| セキュリティ | GitHub App の権限は設計の「非機能の実現方式」の範囲（Contents・Pull requests・Issues・Commit statuses の読み書き、Checks・Metadata の読み取り）に限り、秘密鍵は Actions の秘密に置く。導入は設計承認とリリース承認を通す（C1・C2） |
| システム環境 | 検査は GitHub Actions の `ubuntu-latest` と、リポジトリで使っている uv で動く |

## 用語

| 用語 | 意味 |
| --- | --- |
| 安定版（依存の） | PEP 440 の pre-release でも developmental release でもないバージョン（#3347 の決定 106）。「最新の安定版」の形でだけ使う |
| 上げる先（依存のバージョンの） | 決定 106 の規則で選んだ、最初のアップロードから 7 日たったバージョン |
| 遅れ（依存のバージョンの） | 定義のバージョンが上げる先より古く、固定する理由も無い状態 |
