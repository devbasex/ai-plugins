# バックログの並べ方と優先度の算定の調査（issue-upkeep に「順位付け」を足す材料）

調査日: 2026-09-28。対象: `plugins/ndf/skills/issue-upkeep/`（`SKILL.md`・`references/milestones.md`）と
open の課題 162 件・open のマイルストーン 7 本。書き込みはこのファイルだけ（課題・マイルストーンは読んだだけ）。

## 1. 結論

### 1.1 前提の対応づけ（利用者の案）

**マイルストーンの間の並びをプロダクトバックログ、マイルストーンの中の並びをスプリントバックログ
（の候補の並び）と捉える。** 並べる問題を 2 層に分け、層ごとに別の手法を当てる。

| 層 | Scrum の対応 | 並べるもの | 主な問い | 推奨する手法 |
| --- | --- | --- | --- | --- |
| 上の層 | プロダクトバックログ | open のマイルストーン（主題のまとまり） | どの主題から着手するか | **Now / Next / Later の 3 区分 + 依存の制約 + 人の承認**。材料として各マイルストーンの集計値（下記）を添える |
| 下の層 | スプリントバックログの候補 | 1 つのマイルストーンの中の課題 | 次のスプリントへどの課題を、どの順に切り出すか | **WSJF（CD3 の形）を主、依存は順序の制約、確信度は手入れの合図** |

ただし用語集（#1407）では「スプリント＝1 つの版として出す課題と PR のセット」「マイルストーン＝着手の
順序を表す単位。スプリントはこの中から切り出す」であり、**1 マイルストーン ≠ 1 スプリント**である
（マイルストーン 26 は 10.17.x を何十本も出した）。このずれの解き方は 5 章の論点 0 に置いた。
推奨は案 A（マイルストーン内の順位を「スプリントへ切り出す候補の並び」とし、先頭から 1 版分を切る）である。

**2 層に分けると層をまたいで優先度が逆転しうる**（後ろのマイルストーンの重要な課題が後回しになる）。
これは層を分けたまま**CoD で昇格の候補を出す規則**で防ぐ（1.4、論点 0b の案 B）。

### 1.2 下の層の主手法: WSJF（CD3 の形）

```text
遅延コスト CoD = 実害の大きさ（UBV） + 時間的重要度（TC） + リスク低減・他を解放（RR/OE）
WSJF        = CoD ÷ 大きさ（Size）
尺度        = 1, 2, 3, 5, 8, 13, 20 の段階（相対値。各列の最小の課題を 1 にする）
```

**採る理由は 4 つある。**

1. **このリポジトリの課題の多くは不具合と工程の欠陥で、価値の差より「放置すると毎回かかる費用」の差が大きい。**
   CoD はまさにその量を測る（Reinertsen「1 つだけ定量化するなら遅延コスト」）。RICE の Reach（利用者数）や
   Kano（利用者調査）は、利用者が実質 1 チームの NDF では入力が取れない
2. **大きさで割るので、小さく切る動機が働く**（Black Swan Farming の CD3）。棚卸しの「親 issue へ束ねる」
   「分けて出す」の判断と同じ向きである
3. **4 列とも issue の本文・ラベル・依存・閉じた課題の実績から取れる**（1.4）。点数を人が毎回付けずに済む
4. **既存の規約と衝突しない。** `priority: high/medium/low` のラベルは UBV の下限（アンカー）として読み、
   「高いものは直近のマイルストーンへ」の既存の規則は上の層の規則として残る

**WSJF をそのまま使わない点が 3 つある。**

- **依存は点数に混ぜず、順序の制約にする。** 先に要る課題は、後の課題より必ず前に置く（トポロジカル順）。
  点数の側では、前提になる課題の RR/OE を「解放する課題の数」で上げる
- **確信度（RICE の Confidence・ICE の C）は掛けない。** 本文の根拠が弱い課題は点数を割り引くのでなく、
  「手入れが要る」に落として棚卸しの手順 2A へ戻す（DEEP の「上位ほど詳しく」）。掛けると、書き方の
  薄い課題が静かに後ろへ沈む
- **並べ方の結果は提案であり、確定ではない。** 下の層の並べ替えは自動で反映してよい（既存の「早める
  方向だけ自動」と同じ扱いに寄せる案もある。論点 6）。上の層の並べ替えは人の承認を取る

### 1.3 上の層: Now / Next / Later + 依存 + 承認

**マイルストーンに WSJF をそのまま当てない。** 大きさで割ると、課題の多いマイルストーン（26 は 98 件）が
構造的に後ろへ回り、主題の重要さと関係なく並ぶ。上の層で決めるのは主題の順序で、これは MVV（プロジェクト
の Mission / Vision / Value）に照らす価値判断である。

- **区分は 3 つ**: Now（直近。今スプリントを切り出している）/ Next（次に着手）/ Later（それ以降）。
  連番の名前（`<2 桁の連番> <主題>`）はそのまま使い、区分はマイルストーンの説明の「着手の順序」で表す
- **依存の記述（「25 の次」「#1323 の後」）は制約として先に効かせる。** 食い違いの修正は既存の
  `milestones.md` の「順序を直すとき」が持つ
- **材料として集計値を添える**: マイルストーンごとに「課題の CoD の合計」「`priority: high` の件数」
  「最大の CoD」「CoD 上位 5 件の平均 WSJF」。これを並べ替えの提案に添えて人が決める
- **例外は既存の規則のまま**: CoD が高い（`priority: high` 相当）課題は主題によらず直近へ入れる

### 1.4 層をまたいだ逆転を防ぐ: 昇格の規則（推奨は論点 0b の案 B）

**2 層に分けると、後ろのマイルストーンに入った重要な課題が、前のマイルストーンの軽い課題より後に回る。**
これを防ぐため、**層は分けたまま、点数で昇格の候補を出す**（今の `milestones.md` の「重要度が高いのに
直近でない → 直近へ移す」を点数で一般化したもの）。

1. **全 open の課題を同じアンカー・同じ尺度で採点しておく。** マイルストーンごとに尺度を変えると比べられない。
   採点は新規・変更のあった課題だけを付け直し、値は記録に残す（毎回 162 件を付け直さない）
2. **比べる量は WSJF ではなく CoD にする。** 昇格は「いつ着手するか」を早める判断で、遅れの費用そのもの
   （CoD）が根拠になる。WSJF で比べると大きな課題は割り算で沈み、#1399 のような「CoD 最大・大きい」課題が
   永久に昇格しない（6 章の試算）。マイルストーン内の並び（下の層）は WSJF のまま
3. **比べる相手は「次のスプリントに切り出す境界」の課題の CoD にする。** 前のマイルストーンの最下位と比べると、
   直近の 98 件の最下位はほぼ必ず低く、昇格が乱発する
4. **余白（ヒステリシス）を置く。** LLM の順位相関が 0.4 程度なので、**CoD が境界を 1 段階以上（尺度の
   次の値以上）上回るときだけ**候補にする。ぎりぎりの課題が棚卸しのたびに行き来するのを防ぐ
5. **自動と承認の分け目は既存の「早める判断は実害の記述が根拠」に揃える。** 本文に実害の観測
   （再現の記録・起きた日時とログ）があり、かつ UBV か RR/OE が上位の段階（例: 8 以上）なら自動で直近へ
   移す。それ以外は候補として一括で提示し承認を取る
6. **昇格と対にして、直近のマイルストーンの CoD 最下位を「後ろへ移す候補」として並べて提示する**（承認）。
   早める方向だけを自動にすると直近が膨らみ続けるためである（既存の規則でも、遅らせるのは要判断）

### 1.5 入力を issue のどこから取るか

| 列 | 取る場所 | 誰が出すか |
| --- | --- | --- |
| UBV（実害の大きさ） | 本文の「直さないと何が起きるか」「何が起きたか」の節、`priority:*` ラベル（下限）、マイルストーンの MVV との一致 | LLM（アンカー付き） |
| TC（時間的重要度） | 発生の頻度（「毎回」「〜のたびに」）、同じ現象の課題・コメントの件数（再発）、期限（「次の正式版で」など固定日型）、`bug` ラベル | LLM ＋ スクリプト（件数） |
| RR/OE（リスク低減・解放） | サブイシュー API の子の数、本文の「#N の後」「親」、マイルストーン説明の「並列の組」の依存列、安全機構の欠落（誤 push・データ消失・承認の迂回） | **スクリプト（被依存の数）** ＋ LLM（安全機構か） |
| Size（大きさ） | 受け入れ条件の数、「対象範囲」「修正レイヤー」のファイル数、似た閉じた課題の PR の実績（`additions+deletions`・`changedFiles`・レビューの回数・所要） | スクリプト（実績の集計）＋ LLM（似た課題の選択） |
| 確信度（割り引かない。合図にだけ使う） | 再現の記録（コマンドと出力・ログのパス）の有無、「疑い」「と思われる」の語 | LLM |

**計算はスクリプト、段階の判定は LLM、根拠は記録に残す**の分担にする。LLM は各列の段階と 1 行の根拠を
JSON で返し、スクリプトが式・依存のトポロジカル順・同点の扱い（古い番号を先）を決定的に計算する。

## 2. バックログ管理の考え方

### 2.1 Scrum Guide の Product Backlog

- **「プロダクトバックログは、プロダクトの改善に必要なものを創発的に並べた一覧」**（emergent, ordered list）。
  「優先度」ではなく**順序（order）**である。同点を許さない 1 本の列が要る
- 並べる責任（accountability）は Product Owner にあり、委ねてもよい（may delegate）。**NDF では LLM に
  並べる作業を委ね、責任（承認）は人に残す**形がこれに一致する
- **手入れ（refinement）**は「項目を小さく詳しく分け、説明・順序・大きさを足す継続的な活動」。大きさを
  付けるのは作業する Developers
- **スプリントプランニングで、Developers はプロダクトバックログからスプリントに入れる項目を選ぶ。**
  スプリントレビューでは「新しい機会に合わせてプロダクトバックログを調整してよい」

### 2.2 DEEP（Roman Pichler）

| 性質 | 意味 | NDF への写し |
| --- | --- | --- |
| Detailed appropriately | 上位ほど詳しく、下位は粗くてよい | 上位の課題だけ受け入れ条件と修正レイヤーまで揃える。下位は題と実害だけでよい |
| Estimated | 大きさが付いている | Size の段階 |
| Emergent | 追加・変更・並べ替え・削除が続く | 棚卸しのたびに並べ直す |
| Prioritized | 重要なものが上 | 「まずリスクで、リスクが片付いたら費用対効果と依存で」並べる（Pichler） |

### 2.3 Now / Next / Later（Janna Bastow、ProdPad、2012）

日付ではなく**確信の度合い**で 3 区分に分けるロードマップ。Now は着手中、Next は検証中の問題、Later は
検討中の賭け。**マイルストーンの連番（着手の順序）と相性がよく、上の層の区分にそのまま使える。**
「Later が Never になる」批判があるため、Later に長く残ったものは「やらない」の候補として棚卸しへ回す。

## 3. 優先度の算定手法

### 3.1 比較表

| 手法 | 式・形 | 入力 | 得 | 失 | この用途への適否 |
| --- | --- | --- | --- | --- | --- |
| **WSJF（SAFe）** | (UBV + TC + RR/OE) ÷ Job Size。各入力を 1,2,3,5,8,13,20 の相対値で | 4 列の相対値 | 遅延の費用と大きさを 1 つの比で比べる。相対値なので精度が要らない | 相対値の和と比は数学的に粗い（Black Swan の批判: 優先付けの道具へ矮小化）。尺度の漂流 | **◎ 下の層の主**。入力が本文とラベルと実績から取れる |
| **CoD / CD3（Reinertsen・Arnold）** | CoD（週あたりの金額）÷ Duration | 金額の遅延コスト、所要 | 理論的に正しい。例では FIFO より遅延の総費用 61% 減 | 金額の見積が要る | ○ 考え方として採る（WSJF の列を CoD の構成要素と読む）。金額は出せないので相対値で代える |
| **緊急度の型（Black Swan）** | 4 つの型: 短命でピークが下がる / 長命でピークが下がる / 長命でピーク不変 / 期限 | 型の判定 | TC を「毎回かかる」「期限がある」で分けられる | 型の判定は主観 | ○ TC の判定の補助（期限型は #1427 のような「次の正式版で」） |
| **RICE（Intercom）** | Reach × Impact × Confidence ÷ Effort。Impact は 3/2/1/0.5/0.25、Confidence は 100/80/50%、Effort は人月 | 到達人数・影響・確信・工数 | 確信度を明示する。多数の項目に向く | Reach（利用者数）が取れない。Intercom 自身も「絶対の規則ではない。依存・戦略で覆してよい」 | △ Confidence の考え方だけ借りる（掛けずに合図にする） |
| **ICE（Sean Ellis）** | Impact × Confidence × Ease（各 0〜10） | 3 つの主観値 | 速い。実験の選別向き | 主観が強い。値そのものは無意味で比較にだけ使う（Gilad）。Ease は大きさの逆数で WSJF と重なる | △ 手入れ前の粗い選別には使えるが、WSJF で足りる |
| **MoSCoW（DSDM）** | Must / Should / Could / Won't（今回は）。Must は工数の 60% 以下、Could を 20% 程度 | 区分 | タイムボックスの中の範囲の調整に強い | 期限の決まった箱が無いと Must が膨らむ（NN/G）。順序は出ない | △ スプリントの範囲の切り出しの補助。Won't は既存の「やらない」が担う |
| **Kano（狩野 1984）** | 当たり前品質 / 一元的品質 / 魅力的品質 / 無関心 / 逆 | 利用者アンケート | 満足と不満足を別の軸で見る | 利用者調査が要る | × 利用者調査が取れない。「当たり前品質の欠落＝不具合」の見方だけ UBV に効く |
| **Value vs Effort（2x2）** | Quick Wins / Big Bets / Fill-Ins / Money Pits | 価値と工数の 2 値 | 視覚的で合意しやすい | 2 軸だけ。象限の中の順序が出ない | △ 提示の図として使える（WSJF の分子と分母をそのまま 2 軸にできる） |
| **Buy a Feature（Hohmann）** | 価格付きの機能を関係者が仮想通貨で買う | 関係者の合意 | 関係者の交渉で本音が出る | 複数の関係者が要る。LLM 単独では成り立たない | × 利用者 1 人の承認で代える |
| **Cohn の 4 要因** | 価値・費用・得られる知識・リスク | 定性 | 「リスクが高く必要なものは早く」 | 式が無い | ○ RR/OE と「確信度が低い＝先に調べる」の根拠 |

### 3.2 各手法の要点

**WSJF（SAFe）。** 「相対的な利用者・事業価値、時間的重要度、リスク低減・機会の創出、ジョブサイズに基づく」
並べ方で、SAFe は「相対的な遅延コストを相対的な所要で割ったもの」として見積もる。各入力は
1, 2, 3, 5, 8, 13, 20 の修正フィボナッチで付ける。**実務の慣行として、1 列ずつ全項目を横に並べて付け、
各列の最小を 1 にする。** 1 項目ずつ 4 列を付けると、項目どうしの相対が崩れる。

**CoD / CD3。** Reinertsen の WSJF を、Joshua Arnold（Black Swan Farming）が CD3 として実務化した。
「分子の方がはるかに重要」で、所要の精度にこだわるより遅延コストの理解に力を使う。遅延コストは
**緊急度の型**で形が変わる（期限型は期限の直前まで 0、長命でピーク不変型は常に一定）。Reinertsen は
経済的なトレードオフの U 字曲線の底が平らなので、粗い見積でも無いよりはるかによいとする。

**RICE。** Reach × Impact × Confidence ÷ Effort。「かけた時間あたりの総インパクト」。Confidence は
50% 未満を「ムーンショット」とする。**Intercom 自身が、依存・競争上の必要・戦略で高得点の項目を
後回しにしてよいとしている。** 点数は判断を置き換えず、意図したトレードオフを見える化する道具である。

**ICE。** 0〜10 の 3 値を掛ける。Gilad は「値そのものは無意味で、比較にだけ使う」とし、検証を経て
Confidence を上げる循環（学ぶ）を勧める。Confidence を「どれだけ証拠があるか」の尺度にする点は、
NDF の「再現の記録があるか」に写せる。

**MoSCoW。** DSDM が時間・費用・品質を固定し、範囲だけを Must / Should / Could / Won't で調整する
ために使う。Must の工数を 60% 以下にし、Could を 20% ほど持つ。**スプリントを 1 版分で切るときの
「この版に必ず入れる課題」と「余れば入れる課題」の区別に使える。**

**Kano。** 満足と不満足は別の次元だとする。NDF では「当たり前品質の欠落（成功を失敗と返す・承認を
迂回する）」が UBV を押し上げる、という見方だけ取る。

**Value vs Effort。** Quick Wins を先に、Big Bets を計画的に、Money Pits を捨て、Fill-Ins は余力で。
**WSJF の分子（CoD）と分母（Size）をそのまま 2 軸にすれば、承認の提示に図として使える。**

**Buy a Feature。** 仮想通貨で関係者が機能を買う合意型。関係者が 1 人の NDF では成り立たないが、
「人が承認で並べ替えを覆す」ことが合意型の代わりになる。

## 4. 依存・リスク・技術的負債・見積

### 4.1 依存のある課題の順序

- **依存は点数ではなく制約として扱う。** 点数に混ぜると、前提の課題が低い点で後ろに回り、後の課題が
  着手できないまま上位に残る。**並べ方は「依存のトポロジカル順を守る範囲で WSJF の降順」**にする
  （同じ段の中で WSJF の高いものから取る Kahn の算法で決定的に出せる）
- **前提の課題は RR/OE で持ち上げる。** 「この課題を閉じると何件が着手可能になるか」（被依存の数）を
  スクリプトが数え、段階へ写す（0 件→1、1 件→3、2〜3 件→5、4 件以上→8 など）。親 issue は子の数が
  そのまま効く
- **循環があれば止めて返す**（要判断）。依存の記述の誤りである
- **取る場所**: サブイシュー API、本文の「#N の後」「#N が前提」、`blocked` ラベル、マイルストーン説明の
  「並列の組」の依存列。**依存の記述が本文にしか無いときは LLM が抽出し、スクリプトは抽出結果だけを使う**

### 4.2 リスクの高いものを先に

- Cohn: 価値・費用・得られる知識・リスクの 4 要因で並べる。**リスクが高く必要なものは早く**やる
  （そのリスクが実際に起きるかを早く知るため）。価値が低くリスクが高いものは避けるか先送り
- Pichler: まずリスクで、その後に費用対効果と依存で並べる
- **NDF への写し**: RR/OE に「安全機構の欠落（誤 push・データ消失・承認の迂回・関門を通らずに本番へ）」を
  入れる。#1227（関門なしで本番へマージ）・#1399（取り消した改善が origin へ出た）がこれに当たる

### 4.3 技術的負債

- Fowler: 新機能を足すときの余分な手間が**利息**、片付けが**元本の返済**。**活動の多い領域は利息が
  重いので負債を許さず、安定して触らない領域は放っておいてよい**
- SAFe の実務では負債・イネーブラーに容量の一定割合（10〜30%、目安 15〜25%）を取り置く
- **NDF への写し**: 負債の課題の TC を「その場所を触る頻度」で決める。スクリプトが直近 N 日のコミットで
  修正レイヤーのファイルが何回変わったか（`git log --since --format= --name-only`）を数えて段階へ写す。
  容量の取り置きはスプリントを切るときの規則（論点 5）で扱う

### 4.4 相対見積と LLM が付けるときの注意

- **相対見積の尺度はフィボナッチ風に段階を広げる**（Cohn）。人は差を割合で知覚する（ウェーバーの法則）ため、
  約 60% ずつ増える列が見分けやすい。慣行は 1, 2, 3, 5, 8, 13, 20, 40, 100。倍々（1, 2, 4, 8…）でも同等
- **LLM の見積の実測**（arXiv 2603.06276、16 プロジェクト・4 モデル）: ゼロショットでも順位相関
  0.39〜0.41 で、学習データ 80% で訓練した教師ありの基準（0.32）を上回った。**プロジェクトの実例 5 件を
  足すと約 18% 改善した。** 一方、LLM は人と逆に、2 件の比較より直接の値付けの方が正確だった
  （直接の値から出した組の正答 0.74 に対し、明示の比較は 0.63）
- **ここから導く注意**:
  1. **アンカーを渡す。** 閉じた課題から段階ごとに 1〜2 件の実例（題・本文の要約・実績の差分行数と所要）を
     渡す。実例 5 件で改善したのと同じ効果を狙う。アンカーは 1 回決めて固定し、棚卸しのたびに変えない
  2. **1 列ずつ全件を並べて付ける。** 課題ごとに別の担当へ割ると、担当ごとに尺度が漂流する。棚卸しの
     手順 2A（件数で割る）は材料を控えるだけにし、**段階の判定は手順 2B（分担しない）でまとめて行う**
  3. **点数ではなく段階と根拠を返させる。** 根拠の 1 行（本文のどの記述から取ったか）を必ず添え、記録に
     残す。後で並べ替えを説明できる
  4. **LLM に割り算をさせない。** 式・依存の順・同点の扱いはスクリプトが決める
  5. **相関 0.4 程度であることを前提にする。** 点数の差が 1 段階以内なら同順位とみなし、依存・古さで決める
     か人へ返す。点数の小数点以下を順位の根拠にしない
  6. **大きさは実績で校正する。** スプリントを閉じたら、付けた Size と実績（差分行数・所要・レビュー回数）を
     並べ、外れた段階のアンカーを差し替える

## 5. 設計で決めるべき論点

### 論点 0: 利用者の捉え方と用語集の定義のずれ（先に決める）

**利用者の案**: マイルストーンの中＝スプリントバックログ、マイルストーンの間＝プロダクトバックログ。

**用語集（#1407、`.worktrees/feat/issue-1407-m1407` のコミット c0ec151b の
`plugins/ndf/skills/development-workflow/references/glossary.md`）の定義**:

- スプリント: 1 つの版として出す課題と Pull Request のセット。**期間ではなく中身で切る**
- マイルストーン: 着手の順序を表す単位。**スプリントはこの中から切り出す**

**ずれ**: Scrum のスプリントバックログは「そのスプリントで行うと選んだ項目」であり、1 スプリント分である。
NDF のマイルストーンは複数のスプリント（26 は 10.17.x の版を何十本も）を含むため、
**マイルストーンの中身全体はスプリントバックログより大きい**。

| 案 | 内容 | 得 | 失 |
| --- | --- | --- | --- |
| **A（推奨）: マイルストーン内の順位＝スプリントへ切り出す候補の並び** | マイルストーンの中の並びを「スプリントバックログの候補」と呼び、次のスプリントはその先頭から 1 版分（容量）を切り出す。確定したスプリントバックログはスプリントの目録（`sprint.json`）が持つ | 用語集の定義を変えない。26 のように多スプリントのマイルストーンでも成り立つ。Scrum の「スプリントプランニングでプロダクトバックログの上から選ぶ」と同じ動き | 利用者の言う「スプリントバックログ」と字義が 1 段ずれる。マイルストーン内の並びは実質プロダクトバックログの一区画（主題ごとの区間）であり、説明で補う要がある |
| B: 直近（Now）のマイルストーンだけをスプリントバックログ扱いにする | Now のマイルストーンの中の並びだけを細かく並べ、Next / Later のマイルストーンの中は並べない（DEEP の「下位は粗く」） | 並べる手間が直近に集中する。Now / Next / Later と自然に重なる | 直近が 98 件あり、スプリントバックログ（1 版分）の意味からは外れたまま。高い課題を直近へ入れる例外で Now が膨らみ続ける |
| C: 1 マイルストーン＝1 スプリントに定義を寄せる | マイルストーンを 1 版分の大きさに保ち、閉じると 1 つの版数へ改名する（今の closed の命名と一致） | 利用者の捉え方と GitHub の一般的な慣行（milestone ≒ sprint）に一致する。「閉じたら `v<版数>`」とも 1 対 1 になる | #1407 の定義と衝突する。26 のような主題のまとまりを版ごとに分ける移行が要る。主題（着手の順序）とスプリント（版）の 2 つを 1 つの容れ物に持たせるため、主題が 1 版に収まらないときに破れる |

**案 A を採るときの補い**: 主題のまとまり（マイルストーン）はプロダクトバックログの**区間**で、
全体の順序は「マイルストーンの順（上の層）→ マイルストーン内の順位（下の層）」の辞書順になる、と説明する。
「スプリントバックログの候補」という語を用語集へ足すかどうかも決める（足すなら 1 語 1 意味で）。

### 論点 0b: 層をまたいだ優先度の逆転の防ぎ方（推奨は B）

**懸念**: 後ろのマイルストーンに入った課題のうち本当は重要なものが、前のマイルストーンの軽い課題より後に
回る。2 層に分けると、上の層の順序が下の層の点数に優先するため、構造的に起きる。

| 案 | 内容 | 得 | 失 |
| --- | --- | --- | --- |
| A: 全 open を 1 本の順位で並べる | プロダクトバックログを 1 本の順位にし、マイルストーンは主題のまとまりとして後から付ける。スプリントは全体の順位の上から取る | 逆転が構造的に起きない。Scrum の「1 本の順序付きの一覧」に最も忠実 | 1 つのスプリントに主題の違う課題が混ざり、スプリント MVV（マイルストーンの説明から写す）と課題グループ（並列の組）が成り立たない。相関 0.4 程度の点数の揺れがそのまま主題の行き来になる。162 件を 1 列で並べる採点の費用。マイルストーンが「着手の順序」を表さなくなり、用語集の定義と食い違う |
| **B（推奨）: 層は分け、昇格の規則を置く** | 後ろのマイルストーンの課題の点数が、前のマイルストーンの比較の相手より高ければ前へ移す候補として出す | 既存の規則（重要度が高いのに直近でない → 直近へ）の一般化で、用語集・MVV・並列の組を変えない。逆転を「候補」として見える化し、根拠（どの列が高いか）付きで説明できる | 全マイルストーンの課題を同じ尺度で採点しておく要がある。比べる量・相手・余白を決めないと、昇格が乱発するか行き来する。移すたびにマイルストーンの説明の表を書き換える |
| C: 切り出しを合成にする | スプリントを「今のマイルストーンの先頭 N 件 ＋ 全体で閾値を超える課題（マイルストーンを問わない）」で切る | マイルストーンを動かさずに、急ぐ課題がすぐスプリントへ入る | 課題は後ろのマイルストーンに属したまま先に閉じるため、マイルストーンの記録（閉じたら版数へ改名）と実際に出た版が食い違う。スプリント MVV の外の課題が混ざる。切り出しの規則が 2 本になり、説明しにくい |

**B を推奨する理由**: 逆転の懸念は「重要な課題が後ろに埋もれて気づかれない」ことであり、B は埋もれた
課題を棚卸しのたびに必ず候補として表へ出すことで解く。A と C は逆転を消す代わりに、マイルストーンが
持つ 3 つの役割（着手の順序・スプリント MVV の元・並列の組）のどれかを壊す。

**B で決めること**（推奨の値は 1.4）

| 決めること | 選択肢 | 推奨 |
| --- | --- | --- |
| 比べる量 | CoD / WSJF | **CoD**（WSJF は大きい課題を沈める。昇格は「いつ」の判断で、遅れの費用が根拠） |
| 比べる相手 | 前のマイルストーンの最下位 / 次のスプリントに切り出す境界 / 前のマイルストーンの中央値 | **切り出す境界**（最下位は低すぎて乱発する） |
| 余白 | なし / 1 段階 / 割合（1.5 倍） | **1 段階以上**（LLM の揺れを吸収する） |
| 移す先 | 直近のマイルストーン / 1 つ前のマイルストーン | 直近（既存の規則と同じ）。主題の合う前のマイルストーンがあれば候補に併記 |
| 対の降格 | しない / 候補として出す | **候補として出す**（承認）。直近が膨らみ続けるのを防ぐ |
| 全件の採点 | 棚卸しの対象だけ / 全 open | **全 open を 1 度採点し、以後は新規・変更分だけ付け直す** |

**昇格を自動にするか承認を取るか**

| 案 | 得 | 失 |
| --- | --- | --- |
| 全部自動（今の「早める方向だけ自動」をそのまま広げる） | 手間が無い。既存の規則と一貫する | 点数の揺れで移動が起き、直近が膨らむ。点数だけを根拠に移すと、今の規則（実害の記述が根拠）より根拠が弱い |
| 全部承認 | 誤った移動が無い | 棚卸しのたびに提示が増える。`pace: fast` の「承認は関門 2 つだけ」と衝突しうる |
| **実害の記述があり UBV か RR/OE が上位の段階なら自動、他は一括で承認（推奨）** | 今の規則の根拠（実害の記述）を保ったまま点数で広げる。自動で動くものは今の「重要度が高い → 直近へ」と同じ範囲に収まる | 「上位の段階」の閾値を決める要がある |

`pace: fast` / `auto` のとき、承認側の昇格を MVV の事前の承認で代えられるかも決める（MVV は主題の
範囲を承認しており、主題の外からの昇格は含まないと読むのが自然である）。

### 論点 1: 点数の尺度

- 段階を 1, 2, 3, 5, 8, 13, 20 にするか、1〜5 の 5 段階にするか。LLM の順位相関が 0.4 程度なので、
  段階を細かくしても精度は上がらない。**5〜7 段階で十分**と見る
- アンカーの課題を何件・どこに置くか（Skill の `references/` に固定するか、リポジトリの設定に置くか）
- `priority:*` ラベルと UBV の関係（ラベルを UBV の下限にするか、UBV からラベルを付け替えるか）。
  既存の「ラベルの説明に照らして重要度を付け替える」との二重持ちを避ける

### 論点 2: 依存の扱い

- 制約（トポロジカル順）と加点（RR/OE の被依存の数）の両方にするか、制約だけにするか
- 依存の取り元の優先順（サブイシュー API > 本文の記述 > マイルストーン説明の並列の組）
- 別のマイルストーンにある課題への依存（例: 05 の課題が 20〜25 の課題の後）を上の層の制約へ上げるか

### 論点 3: マイルストーンとの関係

- 上の層の並べ替え（マイルストーンの順序）を自動にしないことの確認。既存の「新しく作るときは末尾」
  「間への差し込みは要判断」は維持する
- マイルストーンが未設定の課題（今は 162 件中の多数）を点数付けの対象に含めるか。含めるなら、
  割り当ての前に点数を出し、CoD の高いものを直近へ入れる既存の規則の材料にできる
- 課題グループ（並列の組）と順位の関係。組の中の順位と組の間の順位のどちらを先に決めるか

### 論点 4: 人の承認をどこで取るか

| 変更 | 案 |
| --- | --- |
| マイルストーン内の順位の変更 | 自動で反映し、変わった分を報告に出す |
| 課題を直近のマイルストーンへ早める（昇格） | 実害の記述があり UBV か RR/OE が上位なら自動、他は一括で承認（論点 0b） |
| 課題を後ろのマイルストーンへ移す | 既存どおり要判断 |
| マイルストーンの順序の変更 | 一括で提示して承認（集計値と 2x2 の図を添える） |
| アンカー・尺度の変更 | 承認（点数の意味が全件で変わるため） |

`pace: fast` / `auto` で MVV の承認を上の層の承認に使えるか（MVV が主題の順序まで含むか）も決める。

### 論点 5: スプリントの切り出し

- 容量（1 版分）の単位: Size の合計の上限にするか、課題の件数にするか。過去のスプリントの実績から取るか
- MoSCoW の 60% のように、「必ず入れる」の割合に上限を置くか
- 負債・保守の課題に容量の一定割合を取り置くか（SAFe の実務は 10〜30%）
- 切り出しの担い手は issue-upkeep か、実行計画（`issue-plan-strategy`）か、`supervise.py new` か

### 論点 6: 並べ直すきっかけ

| きっかけ | 何を並べ直すか |
| --- | --- |
| 変更の終わり（今の issue-upkeep の呼び所） | 対象になった課題の点数を付け直し、両層を並べ直す |
| スプリントを切り出す直前（Scrum のスプリントプランニング相当） | Now のマイルストーンの中だけ。ただし「着手の直前は判断が歪む」（SKILL.md）ため、並べ直しは点数の再計算に限り、段階の判定はしない |
| 依存先の課題が閉じた | 被依存の数が変わった課題の RR/OE を再計算（スクリプトだけで済む） |
| 実害の追記・同じ現象の起票（再発） | その課題の UBV・TC を付け直す |
| マイルストーンが完了した・MVV が変わった | 上の層を並べ直す（承認） |
| スプリントを閉じた | Size の実績でアンカーを校正する |

### 論点 7: 結果をどこに書くか・変更をどう説明するか

| 置き場 | 得 | 失 |
| --- | --- | --- |
| マイルストーンの説明の表（順位・課題・CoD・Size・WSJF・根拠） | 既存の「並列の組」の表と同じ場所。読み手が 1 か所で見る | 説明の長さに上限がある。更新のたびに説明を書き換える |
| GitHub Projects の数値フィールド（Status と同じボード） | 並べ替え・絞り込みがボードでできる。本文を汚さない | Projects の無いリポジトリで動かない（「他のリポジトリで動くこと」） |
| 各課題の本文の節（「優先度の根拠」） | 課題ごとに根拠が残る | 本文の書き換えが増え、書き込みの制限に当たる。経緯を本文に残さない規則と衝突しうる |
| 棚卸しの記録（`$NDF_UPKEEP_STATE_DIR`）＋報告 | 書き込みが要らない | 手元にしか残らず、他の担当が見られない |

**順序の変更の説明**: 前回の並びとの差分を「上がった / 下がった課題と、変わった列（例: TC 3→8、
理由: 再発の起票 #xxxx）」の表で報告する。**変わった理由が入力の変化で説明できない並べ替えは起こらない**
形（段階は固定のアンカーで付け、式はスクリプト）にしておけば、差分は必ず入力の差で説明できる。

### 論点 8: 既存の手順への組み込み

- 手順 2A（件数で割る）で控える項目に「UBV/TC/RR/Size の材料（本文の該当箇所）」を足し、段階の判定は
  手順 2B（分担しない）で 1 列ずつ全件に対して行う
- `upkeep.py` に `rank` のサブコマンド（依存の抽出結果と段階を受け、順位と差分を 1 行の JSON で返す）を
  足すか、別のスクリプトにするか
- 「重要度」（ラベル）と「順位」（WSJF）の 2 つを持つことの整理。ラベルは上の層（どのマイルストーンか）、
  順位は下の層（マイルストーン内のどこか）と分担を分ける案がある

  `cross-refactoring` は検査のプランで毎回走り、取り消しが起きるたびに再発する。RR/OE 8 = 安全機構の欠落
  （取り消した変更が公開される・最終ゲートが走らずに落ちる項目が残る）。Size 5 = 直すことが 3 項目
  （取り消しの対象・途中の push・最終ゲート）で、取り消しのロジックは #1237 と同じ場所を触る
- **#1289**: UBV 5 = 関門 1 の問い直しが 9 回（子 #772）。TC 3 = 設計の関門のたびに起きるが、回避策
  （人が問う）がある。RR/OE 5 = 子 2 件（#772・#785）を閉じる。Size 3 = 雛形 2 ファイルの欄の新設
- **#1382**: UBV 3 = 接続先の取り違えにその場で気づける（Bedrock に戻った例あり）。TC 1 = 期限も再発の
  費用も無い（長命でピーク不変型）。RR 2。Size 2 = `statusline.sh` とテスト 3 本、受け入れ条件 5 つ

**読み取れること**

1. **並びは #1422 → #1399 → #1289 → #1382 になる。** #1422 が首位なのは Size 1 で割るためで、Quick Win
   として正しい（小さく速く片付けるものを先に）。**ただし CoD が最大なのは #1399 で、2x2 では「Big Bet」**
   に当たる。上の層の規則（CoD が高い＝`priority: high` 相当は直近へ）が別に効くべき課題である
2. **#1399・#1422・#1382 はラベルもマイルストーンも無い。** 今の issue-upkeep では「低い → 未設定のまま
   残す」に落ちうる。CoD を出すと、#1399 は `priority: high`（実害・安全機構の欠落）へ付け替える根拠が
   本文から揃うことが分かる
3. **依存**: #1399 と #1237（積み直しの衝突で取り消しが広がる）は同じ取り消しのロジックを触る。依存か
   ルートコーズのクラスタかは手順 2B で決める。クラスタなら親 issue の RR/OE が子の数だけ上がる
4. **層をまたいだ昇格（1.4）**: 仮に #1399 が後ろのマイルストーンにあっても、比べる量を CoD（24）にすれば
   直近の境界を上回り昇格の候補に出る。WSJF（4.8）で比べると #1422 のような小さい課題に負け、埋もれる。
   本文に実害の観測（2026-09-28 のログと force push）があり RR/OE が 8 なので、推奨の規則では自動で直近へ移る
5. **確信度**: #1399 は原因を「疑い」と書いており、中。割り引かず、上位にあるので「手入れ（再現と原因の
   特定）を先に」の合図にする。DEEP の「上位ほど詳しく」と一致する
