## 決定の記録

### 決定 1: 実行前確認の要否を「戻せないものを拒まれずに消すか・新しい内容を外へ出すか・判断を問うか」の 3 つで決める

#561 の提案は「実際に取り消せるか」の 1 つだった。それだけで決めると、`pr` の push と Pull Request の
作成、`out-of-scope` の起票も取り消せる（閉じる・消す）ため確認が外れる。利用者は #561 の判断が要る点で
`out-of-scope` と `issue-upkeep` の確認を残す案を推しており、残す理由を基準の中に持つ必要がある。
問い 2 は「見た人は戻らない」という関門 2 と同じ性質、問い 3 は判断そのものへの同意である。
取り消せるかの 1 問に例外の一覧を添える形は採らなかった。例外の理由が書き手ごとに増える。

### 決定 2: 止める合図は git の拒否だけにし、`-D` の代わりになる判定を NDF の側に作らない

squash でマージしたブランチは、リモートのブランチが消えた後の `git branch -d` で拒まれる（要求文書の実測 2 行目）。
先端が Pull Request の `headRefOid` と一致すれば `refs/pull/<番号>/head` から戻せるため、`-D` で自動に
消す案もあった。採らなかったのは、利用者の指示（#561 の提案「`git branch -d` のみ。`-D` は使わない」）と、
NDF の判定を安全の網にすると #561 が問題にした二重の確認が形を変えて残るためである。代わりに、止まった
一覧に一致の有無と戻し方を並べ、判断の材料を揃える。このリポジトリはマージコミットだけを許す
（`allow_squash_merge: false`）ため、通常の経路では止まらない。

### 決定 3: 起点・本番のチャネル・現在のブランチは、同意を求めずに対象から外す

#561 は「同意を求める（残す）」側に置いていた。起点から本番へ出す Pull Request（PR #617 は head が `develop`）
では、`merged` の対象が起点ブランチそのものになる。消してよいかを尋ねる場面が作られること自体が誤りで、
同意を求めると 1 回の誤答で開発の本流が消える。今の「マージ済みブランチの整理」も起点と現在のブランチを
「必ず除外する」としており、それをクリーンアップの手順と本番のチャネルへ広げる。

### 決定 4: 同意なしに消すリモートブランチは、同じリポジトリにあるマージ済み Pull Request の head で、先端が `headRefOid` と一致するものに限る

利用者の指示 1 は対象を「マージ済みかつ当該 Pull Request の head」に限った。先端の一致を足すのは、
マージの後に積まれたコミットは Restore branch で戻らないためである（Restore branch が戻すのは
`headRefOid`）。「マージ済みブランチの整理」で見つかるブランチも同じ扱いにする。`gh pr list --state merged --head <名前>`
で Pull Request を引き、先端が一致すれば消す。引けなければ止まる側へ積む。

### 決定 5: 作業ツリーの無視されたファイルは、消さずに退避してから作業ツリーを消す

`git worktree remove` は無視されたファイルを拒まずに消し（要求文書の実測 4 行目）、その複製元があるとは限らない
（`.env` の手直し・生成途中の成果物）。止める条件にすると `__pycache__` を持つほぼすべての作業ツリーで止まる
（このリポジトリのレビュー用の作業ツリーでも `git status --ignored --porcelain` が `!! plugins/ndf/scripts/lib/__pycache__/` を出す）。
そこで消さずに退避し、戻せる操作にする。手順は次の 3 つである。

1. `git -C <path> status --porcelain` が空でなければ止まる側へ積む（git が拒む条件と同じ。退避より先に見る）
2. `git -C <path> status --ignored --porcelain` の `!!` の行（作業ツリーからの相対パス）を、同じ相対パスで
   `<退避先>` の下へ移す。**先に退避先の親を作る。** 追跡されたディレクトリの配下のパス（`a/b/__pycache__/`）は
   親が退避先に無く、そのまま `mv` すると終了コード 1 になる（要求文書の実測 6 行目）。末尾の `/` は外さなくてよい（同じ行）
   ```bash
   git -C "$path" status --ignored --porcelain | sed -n 's/^!! //p' | while IFS= read -r rel; do
     mkdir -p "$(dirname "$trash/$rel")" && mv "$path/$rel" "$trash/$rel" || exit 1
   done
   ```
   `$trash` は `<共通の git ディレクトリ>/ndf/worktree-trash/<ブランチ名の / を __ に置換>-<YYYYmmddHHMMSS>` で、
   共通の git ディレクトリの絶対パスは `worktree-common.sh` の `wt_common_git_dir "$path"` で得る（引数が空なら終了コード 1）。
   開発用の作業ツリーと同じファイルシステムにあることが多く、`mv` が名前の付け替えで済む（テスト環境の台帳も同じ `ndf/` に置いている）
   **1 件でも失敗したら残りを移さず止まり、作業ツリーを消さない。** ループは `|| exit 1` で抜け、パイプの終了コードが 1 になる
   （要求文書の実測 7 行目）ので、`git worktree remove` へ進まず止まる側へ積む。退避済みのものは退避先に残し、退避先・移したもの・
   失敗したパスと `mv` の出力を報告に載せる（戻すなら同じ `mv` の逆）。別のファイルシステムでの `mv` の失敗も同じ扱いにする
3. `git worktree remove <path>`（要求文書の実測 5 行目）。2 がすべて 0 で終わったときだけ行う

「止める」は採らなかった。通常の経路で止まる。「`localenv.copy_from_main` にあるものだけ自動で消す」も採らなかった。
宣言の無いリポジトリで常に止まる。

### 決定 6: 後片付けは、まとまりの最後か判断できなくても待たない

版を上げるのは `release` で、`merged` は版を上げない。判断が要るのは配布を始める時点であり、確認は
`release` の開始条件（まとまりのすべての Pull Request がマージされている）へ移す。`merged` で待つと、
配布をしない後片付けでも止まる。

### 決定 7: まとまりの課題は、まとまりの終わりの工程を通った時点で閉じ、`merged` では閉じない

#623 の 4 案のうち「まとまりは配布の後に閉じる」を採る。開いている課題が「利用者へ届いて確かめるまでが
終わっていない」を表し、配布・リリース後テスト・振り返りの記録を開いた課題へ書ける。v10.11.0 の締めで
運用が選んだのもこの時点である。**本番への配布とリリース後テストの合格を閉じる条件にする。** v10.11.0 の締めでは
配布・リリース後テスト・振り返りを終えてから閉じた。検証への配布は「提示して進めてよい」段階で、利用者が常用する版に
まだ届いていない。不合格・保留の課題を閉じると、確かめていないことが終わったように見える。

「マージで閉じ、記録を続ける」は採らなかった。盤面の `Item closed` で
起点へのマージ時に Done になり、配布で問題が出ても課題の一覧に出ない。「盤面の自動クローズを正とする」は
盤面の設定しだいで時点が変わり、宣言の無いリポジトリに別の規則が要る。

**利用者の指示 2（閉じ忘れた課題のクローズを自動にする）は、閉じる場所を移しても守る。** 閉じる操作は
同意を求めず、reopen の手段を報告へ載せる。`merged` に残すのは、まとまりの課題の OPEN の一覧を報告する
ことだけである。**この移動は指示の文面（`merged` の手順で閉じる）から外れるため、ドキュメントレビューの
承認で確かめる。**

単独の変更は 1 件のまとまりで、終わりの工程は配布（`light`）・リリース後テスト（リリース後テストだけを通る `operation`）・振り返り（`standard`）のどれかである。チャネルを
分けないリポジトリでは既定ブランチへのマージで GitHub が先に閉じ、「まとまりを閉じる」は何もしない。

### 決定 8: 閉じる手順は `progress-tracking` の 1 か所に置き、盤面を Done にしてから OPEN のものだけを閉じる

閉じる時点は終わりの工程で、終わりの工程はモードで `release`・`release-verification`・`retrospective` の 3 つに分かれる。
どれかへ置くと、残りへ写しが要る。`progress-tracking` は既に「終わりの工程の後に Done を書く」を持ち、
どの工程からも呼ばれる。盤面を先に書くのは、`Auto-close issue` の有無によらず終わりの状態を揃えるため
である。その前に状態を読んで控えるのは、Done で閉じた課題を `既に閉じていた` ではなく `閉じた` と数えるためである。新しいスクリプトは作らない。手順は `closing-issues.sh` と `gh` で足りる。盤面を書くのは記録のリポジトリの
課題だけである。**失敗の契約は通常の進行の記録と分け、閉じられなければ止まる。** 進行の記録は失敗しても
工程を止めないが、閉じる操作は #623 の目的そのもので、黙って通すと OPEN が残ったまま終わりに見える。

### 決定 9: コミットメッセージに閉じる語を書かない

v10.11.0 では、コミットメッセージに `Closes` を持つ 2 件だけが `main` へのマージで閉じ、まとまりが
2 件と 12 件に割れた。「必ず書く」は採らなかった。`main` へのマージは終わりの工程より前に来ることがあり
（PR #617 のマージは振り返りの記録の 17 分前）、全件が早く閉じる。Pull Request の本文の閉じる語は残す。
作成の時点の案内が本文を入力にしている（`stage-completeness.md`）。

### 決定 10: 記録は工程を行った側が、工程の単位に含まれる課題すべてへ書き、まとまりの課題は本文の閉じる語から集める

v10.11.0 では、担当が記録した工程で止まり、進行側が行った工程が 14 件とも空欄だった。記録の担い手を
「行った側」と決めれば、工程表の単位の表から一意に決まる。集め方にマイルストーンを使う案は採らなかった。
マイルストーンには、このまとまりで直さない課題も割り当てられ得る。閉じる語は `merged` と作成の時点の
案内が既に使う指し方である。**まとまりの Pull Request の一覧は、配布の Pull Request の本文の `まとまり:` の行から取る。**
別の実行の `retrospective` からも読め、`release` の出力物に既にある形を再利用できる。マイルストーンから引く案は、
Pull Request にマイルストーンが付くとは限らないため採らなかった。

### 決定 11: 関門の節には原則を 1 文で足し、`development-workflow/SKILL.md` の行数を増やさない

このファイルは 500 行ちょうどで、#550 #657 の設計も「`/goal` の引数として呼ばれたとき」を触る。基準の
中身は `AUTHORING.md` が持ち、関門の節は冒頭 2 段落の中で「関門の外で工程の側が実行前確認を足さない。
取り消せる操作は止めずに行い、戻し方を報告する（基準は AUTHORING.md）」を既存の行へ織り込む。
