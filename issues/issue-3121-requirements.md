## 目的

- **今どうなっているか**: NDF はブランチについて、`.ndf/worktree.json` の `base_branch`（ベースブランチ）と `production_branch`（本番チャネル）だけを宣言で受ける。次は NDF の中に決め打ちされている
  - スプリントブランチを切る元は、いつもベースブランチである（`plugins/ndf/scripts/supervise_lib/sprint_waves.py:141` などのプランの `"起点": f"origin/{a.base}"`）
  - 設計 PR の宛先はベースブランチである
  - リリースはベースブランチを丸ごと本番チャネルへ入れる。並列の計画のまとめたリリースも、ベースブランチの先頭が提示の時点から動いたかで範囲を決める（`plugins/ndf/scripts/lib/parallel_release.py:24` の `moved`）
  - Pull Request の宛先の区分は、スプリントブランチ宛てでなければ `develop` という名前の区分になる（`plugins/ndf/scripts/lib/pr_mode.py:27` の `pr_target`）
- **困っていること**: リポジトリが「スプリントブランチを本番チャネルから切り、承認したスプリントだけをリリースブランチで本番へ届ける」運用（#3119）を選ぶと、NDF がそれに合わせて動けない。2026-11-12 の計画 p5 では、リリース 9 に計画の外のスプリント aixrepo-1（#3074）が入った（#3119 の「目的」）
- **変えると何が成り立つか**: ブランチ運用はリポジトリの事情で決まる。NDF は特定の運用を前提にせず、リポジトリの宣言どおりに、スプリントの起点・結合・本番への取り込み方を選ぶ。宣言が無いリポジトリは今の振る舞いのまま動く。ai-plugins は宣言の値として #3119 の運用を載せ、承認したスプリントだけを本番へ届けられる

## 宣言の CRUD（2026-11-12、起票者が利用者の指示から組み立てた。起票者の推定 S3。設計承認ゲートで確かめる）

既存のリポジトリでは、ブランチの使い方を調べて宣言を作る。NDF のプロジェクトの宣言（`plugins/ndf/scripts/project-decl.py` の `check` → `measure` → 答え → `write`）と同じ流れに乗せる。

| 操作 | いつ | 誰が | どのように |
| --- | --- | --- | --- |
| C: 作成 | `development-workflow` の手順 0 で、ブランチ運用の宣言が無いと分かったとき | conductor（`project-decl.py` の流れで） | (1) `measure` が git と gh だけで実際の使い方を測る（下の表） (2) 項目ごとに推した値・確からしさ・根拠を出す (3) 根拠が足りない項目は conductor が利用者に問う (4) `.ndf/` を書く前に、推した宣言を示して利用者の承認を取る（共通原則 C7） (5) `write` で書く |
| R: 参照 | スプリントを切る・設計 PR を出す・リリースを組む・worktree を作るとき | NDF のスクリプト（`new sprint`・`release`・並列の計画のリリース・`worktree`） | 宣言を読んで振る舞いを選ぶ。宣言が無ければ今の振る舞いのまま |
| U: ずれの検出 | 手順 0 の `check` と、振り返り・棚卸しのとき | `project-decl.py`（`check` か `measure` の再実行） | 宣言の値と実際の使い方（直近のマージした PR の起点と宛先など）を突き合わせ、ずれていれば更新の案を根拠つきで出す |
| U: 運用の変更 | リポジトリが運用を変えると決めたとき（#3119 など） | conductor | 新しい値を答えとして `write` で書く。書く前に利用者の承認を取る（C7） |
| U: 動いているスプリント | 宣言を変えたとき | NDF のスクリプト | 変えた宣言はそれから始めるスプリントにだけ効く。動いているスプリントは始めた時点の宣言のまま進む（#3092 の「始めた時点の定義を入力に残す」と同じ考え方） |
| D: 削除 | 宣言をやめるとき | 利用者の承認を得た conductor | 宣言を外すと既定の振る舞い（ベースブランチから切り、ベースブランチを丸ごと出す）へ戻る。宣言は `.ndf/` に置いてコミットするので、履歴は git に残る |

`measure` が調べるもの:

| 項目 | 調べ方 |
| --- | --- |
| 本番チャネル | 既定ブランチと、リリースのタグが付いたコミットのあるブランチ |
| スプリントを切る元 | 作業ブランチ（`sprint/*` など）と候補のブランチの分岐点（`git merge-base`） |
| 結合ブランチ | マージした PR の宛先の分布（`gh pr list --state merged --json baseRefName,headRefName`） |
| 本番への取り込み方 | 本番チャネル宛ての PR の head が結合ブランチそのものか、リリースブランチか。リリースブランチなら何を集めているか |
| 設計 PR の宛先 | `design/*` の PR の宛先 |
| 守らせている仕組み | ルールセット（`gh api repos/<R>/rulesets`）と、CI の宛先の検査 |

## 前提

- 前提 1: 宣言の置き場は 1 か所で、`.ndf/worktree.json` か `.ndf/project.json` のどちらかを設計が決める。どちらにしても既存の `base_branch`・`production_branch` と同じ置き場から読め、宣言の形はスキーマで検査される
- 前提 2: 宣言で受ける本番への取り込み方は少なくとも 2 つ — 「結合ブランチを丸ごと本番へ出す」（今の振る舞い）と「本番チャネルから切ったリリースブランチへ、選んだスプリントブランチを集める」。ほかの取り込み方は、同じ宣言の項目に値を足して受けられる形にする（値を足すときに NDF の別の箇所の書き換えが要らない形を設計が示す）
- 前提 3: 宣言の作成（測った結果からの新規作成）は共通原則 C7 の「解析で新しく作るのは除く」に当たり、`project-decl.py` の今の流れ（推した値と根拠を示し、根拠が足りない項目だけ conductor が利用者に問う）で書く。宣言の変更と削除は C7 に当たり、実装の中でコミットして既存の承認ゲート（設計承認ゲートかリリース承認ゲート）で人が見る。新しい承認の工程は足さない
- 前提 4: 宣言を変えても動いているスプリントに効かないようにするため、スプリントを始めた時点の宣言をプランか状態の記録に残し、そのスプリントの後の工程はその記録を読む
- 前提 5: ai-plugins の宣言を新しい運用の値へ書き換える（#3119 の切り替え）のは、この課題の版を本番へ出した後である。先に切り替えると、動いているレーンと並列の計画のリリースが新しい宣言と食い違う
- 前提 6: リポジトリの側の検査（CI の宛先の検査・ルールセット）は、NDF ではなくリポジトリが持つ。ai-plugins の分（`scripts/check-pr-base.sh` とルールセット）は #3119 の範囲として、この設計に含める

## 対象範囲

含む:
- ブランチ運用の宣言（前提 1・2）。スプリントの起点・結合ブランチと入れる時点・設計 PR と確定仕様化の PR の宛先・本番への取り込み方を受ける

- 宣言が無いリポジトリで、今の振る舞いのまま動くこと
- 宣言の CRUD: 測って作る（`measure` → `write`）・読む・ずれの検出（`check` と、振り返り・棚卸しの再測定）・運用の変更・削除

- 工程の進行表（#3092）そのもの
- 閉じた PR の依頼を外せずリリースを組み直し続ける件（#3085）のうち、範囲の決め方に関わらない部分

- cherry-pick で選んだコミットを集める取り込み方（#3119 の調べた事実で採らないとした。何が入ったかを git が追えないため）

## 用語

| 用語 | 意味 |
| --- | --- |
| ブランチ運用の宣言 | リポジトリがスプリントの起点・結合ブランチ・設計 PR の宛先・本番への取り込み方を書いた `.ndf/` の設定 |
| スプリントの起点 | スプリントブランチを切る元のブランチ |
| 結合ブランチ | スプリントブランチを入れて、スプリントどうしの組み合わせを試すブランチ。開発版のチャネルを兼ねることがある（ai-plugins の `develop`） |
| 本番チャネル | 正式版のチャネル。既存の `production_branch`（用語集の語） |
| リリースブランチ | 本番チャネルへ入れる変更を集めるブランチ（`release/v<版>`） |
| 本番への取り込み方 | 本番チャネルへ何をどう入れるか。「結合ブランチを丸ごと出す」か「選んだスプリントブランチを集める」など |

## 受け入れ条件

宣言と NDF の振る舞い:

- [ ] 1. ブランチ運用の宣言がスキーマに定義され、スプリントの起点・結合ブランチと入れる時点・設計 PR と確定仕様化の PR の宛先・本番への取り込み方の 4 項目を受ける。スキーマに合わない宣言は、読む側のスクリプトが終了コード 0 以外と直す箇所を出して止まる
- [ ] 2. 宣言の無いリポジトリで、`supervise.py new sprint` が組むプランの起点・設計 PR の宛先・リリースの範囲と比べる元が、変更前と同じ値になる（退行しない）。前提の確認: 設計の時点で、変更前の版で同じ入力からプランを組み、比べる値を記録する
- [ ] 3. 宣言の無いリポジトリで、並列の計画のまとめたリリースの範囲の決め方（ベースブランチの先頭が提示の時点から動いたら組み直す）が変更前と同じである（退行しない）。前提の確認: 変更前の `plugins/ndf/scripts/tests` の並列のリリースのテストが、変更後も手を入れずに通る
- [ ] 4. 「スプリントの起点 = 本番チャネル・結合ブランチ = 別のブランチ・選んだスプリントブランチを集める」の宣言のリポジトリで、`new sprint` のプランの起点が `origin/<本番チャネル>` になり、設計 PR の宛先が宣言どおり（スプリントブランチ）になる
- [ ] 5. 同じ宣言のリポジトリで、リリースを組むと、本番チャネルから切ったリリースブランチに、承認したスプリントブランチだけがマージされる。承認していないスプリントブランチのコミットはリリースブランチに含まれない（`git merge-base --is-ancestor` で確かめる）
- [ ] 6. 同じ宣言のリポジトリで、承認資料の範囲が「承認したスプリントブランチの PR の和」になり、比べる元が前の本番のタグになる。結合ブランチの先頭が動いても、選んだスプリントブランチが動いていなければリリースを組み直さない
- [ ] 7. NDF のコード（`plugins/ndf/scripts`。テストと `experimental` を除く）・Skill の本文・手順書・エージェントの本文に、特定のブランチ名（`develop`・`main`・`master`）と特定の運用を前提にした決め打ちが無い。残るものは、宣言の既定値か測る候補として 1 か所にまとまり、その一覧を検査（テストかチェックスクリプト）が持つ。一覧の外に出たら検査が落ちる
- [ ] 8. 宣言の書き方（項目・値・既定値・例）が `worktree` か `release` の手順書にあり、その手順書の例をスキーマの検査に通すと通る

- [ ] 9. 宣言の無い既存のリポジトリで `project-decl.py measure` を打つと、4 項目それぞれに推した値・確からしさ・根拠（測ったコマンドとその結果の要約）が出る。根拠が取れない項目は推した値を出さず「不明」と理由を出す

- [ ] 13. 宣言のブランチ運用の項目を外すと、宣言の無いリポジトリと同じ振る舞い（受け入れ条件 2・3）に戻る

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 宣言の作成・ずれの検出の結果は、項目ごとに根拠（打ったコマンドと結果の要約）を残し、人が後から読んで確かめられる |
| 移行性 | 宣言の無い既存のリポジトリは、何もしなくても今の振る舞いで動く。ai-plugins の切り替えは、この課題の版の本番リリースの後に行い、動いているスプリントブランチ（develop から切ったもの）の扱いを移行の手順に書く（未決 3） |
| セキュリティ | ルールセットの変更は人が設計承認ゲートで見る。宣言の作成で `gh api` を打つときも、出力に秘密を残さない（`project-decl.py` の既存の伏せ字を通す） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`.ndf/` の宣言に項目が増える。既存の `base_branch`・`production_branch` はそのまま読め、互換を保つ |
| データ | スキーマに項目を足す。既存の宣言の書き換えは要らない |
| 既存の振る舞い | 宣言の無いリポジトリでは変わらない。宣言のあるリポジトリでは、スプリントの起点・設計 PR の宛先・リリースの範囲が宣言どおりになる。Pull Request の宛先の区分の名前（`develop`）は宣言に依らない名前へ変わる |
| ai-plugins の運用 | スプリントの起点が main に、設計 PR の宛先がスプリントブランチに、リリースの範囲が選んだスプリントブランチの和に変わる（前提 5 の時点から） |

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | 宣言の無いリポジトリの振る舞いを退行させない。範囲のテストとリンタを通す |
| 確認してから行う | 宣言のスキーマの追加（公開インタフェース）・ai-plugins の `.ndf/` と `AGENTS.md` の書き換え（C7）・ルールセットの変更。いずれも設計承認ゲートかリリース承認ゲートで人が見る |
