# 決定の記録: 検査のプランと CI: 差分の中身で工程を選び、文書だけの変更にリファクタリングと全体テストを掛けない（#2925）

設計文書の本体は [issues/issue-2925-design.md](issue-2925-design.md) にある。

## 決定の記録

### 決定 1: 検査のプランと CI が同じ分け方を読むよう、差分の分類を NDF の部品 1 つにする

分類は検査のプランの 4 つの判定（リファクタリングの要否・範囲・全体テスト・振る舞いの確認）と CI の判定が使う。部品を 1 つにし、各呼び出し元は差分の一覧を自分の手段（REST・git）で取って渡す。ai-plugins の CI は同じコミットの部品を import する。GitHub のアクション（LIB1）でパスを判定する形は採らない。手元で動く検査のプランから呼べず、分け方が 2 か所になるためである。

- 作り方: 自前で作る・ライブラリやサービスを使う
- 比べた候補: LIB1 / LIB3 / LIB4 / PRD1

根拠: Value 7 / Value 6（MVV 版 6）

### 決定 2: テストが読む文書とテストの対応は、プロジェクトの宣言で持つ（未決 1）

宣言の `tested` に、文書のパターンとそれを読むテストのパスの組を書く。テストの側に印を書かせる形は、テストのランナーごとに印の書き方が違い、どのプロジェクトでも同じ形で読めないため採らない。テストの実行から依存を自動で求めるツール（LIB2）は、データとして読むファイルを追わないため使えない。宣言の漏れは、ai-plugins では宣言の漏れの検査で見つける。この検査は、テストのソースに文書のパスを書いたテストが宣言に入っているかを見る。最後は develop への push で回る全体の pytest が拾う。ai-plugins の最初の宣言は、実装で全体テストを開いたファイルの記録つきで回して決め、手順と結果を実装の Pull Request に載せる。

- 作り方: 自前で作る
- 比べた候補: LIB2 / PRD1

根拠: Value 6 / Value 4（MVV 版 6）

### 決定 3: 文書のファイルの既定は、Markdown と用語集の設定が指すファイルにする

要求の前提 1 は用語集の機械向けの形（`docs/glossary/`）を既定に含めるが、そのパスは ai-plugins のものである（受け入れ条件 11）。用語集の場所は NDF の用語集の設定（`.ndf/glossary.json` の `source`・`document`）が既に持つため、既定はそこから読む。

根拠: Value 6（MVV 版 6）

### 決定 4: cross-refactoring を飛ばす判定は、今のリファクタリングの要否の判定（`assess`）へ足す

`assess` は既にプロダクションコードの差分が無ければ飛ばし（終了コード 3）、検査のプランは `skip_to` でコードレビューへ進む。文書だけの判定をここへ足し、理由を「差分が文書のファイルだけ」にする。検査のプランに新しいステップを足す形は、同じ判定が 2 つに分かれるため採らない。

根拠: Value 5 / Value 7（MVV 版 6）

### 決定 5: 全体テストの選び方は `test-run.py whole` の中で決める

全体テストは検査のプラン 2 つと実装のプランが同じ `whole_cmd` で呼ぶ。中で決めれば 3 つのプランが同じに振る舞い、プランの雛形を変えない。文書だけで走らせるテストがあるときは、CI に任せる戦略でも手元で走らせる（数本で終わり、CI の待ちを足さない）。lint の suite は今と同じに走らせる（文書の検査を省かない。受け入れ条件 13）。

根拠: Value 5 / Value 3（MVV 版 6）

### 決定 6: 振る舞いの確認は、worker が `claude -p` で 1 対象 1 回起動し、Pull Request のコメントに記録する（未決 3）

何を確かめるか（変わった指示と、それが効く依頼文）は差分の中身で決まり、スクリプトでは決められないため worker が担う。対象の抽出・記録の形・記録があるかの確認はスクリプトが担う。費用の上限は 1 回 1 ドル（`--max-budget-usd`）と対象 6 件で決め、超えた分は止めて人へ戻す。記録は head のコミットの印で結び、確かめた後に Skill の本文を変えたら確かめ直しになる（I6）。

根拠: Value 5 / Value 1 / Value 3（MVV 版 6）

### 決定 7: 新しいモードを足さない（未決 2）

この表で、文書だけの差分は cross-refactoring・全体テスト・CI の全体の pytest を通らなくなる。残る工程は設計（Skill の本文は AI の振る舞いを変えるため `standard` に当たる）・cross-review・完了判定・文書の検査で、どれも文書の変更に意味を持つ。モードを足すと判定の基準と工程表の列が増え、判定の誤りの経路も増える。`light` と `documentation` の定義も変えない。`light` は既に文書の局所変更を受け、`documentation` はリポジトリの外の読み手へ渡す文書の工程（素材の収集・体裁レビュー）を持つためである。

根拠: Value 3 / Value 5（MVV 版 6）

### 決定 8: runtime smoke では、振る舞いを決める文書をコードとして扱う

Skill の本文の frontmatter はランタイムの読み込みを変える。frontmatter の検査は `runtime-plugin-validate.yml` が Pull Request ごとに回すが、ランタイムで読み込むことは smoke だけが確かめる。smoke の所要は 1 分程度（`.ndf/project.json` の `ci` の実測 73 秒）で、残しても待ちは増えない。

根拠: Value 1（MVV 版 6）
