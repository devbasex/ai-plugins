## 目的

- Web サービスのコードを、ライセンスを差し替えてもプラグインの配布に何も起きない 1 つのディレクトリにまとめる
- インフラと秘密がこのリポジトリへ入らないことを、人の注意でなく機械で守る
- #2170〜#2174 が互いに食い違わずに並列で進められるよう、サービス全体の形（構成要素・実行基盤・進捗の正本・構成要素の間の契約）を先に決める

## 前提

- 前提 1: ライセンスの切り離しは、この課題では行わない。Web サービスのディレクトリには根と同じ MIT の `LICENSE` を置き、差し替えはそのファイル 1 つ（と根の `README.md` の案内）で済む形にする。切り離す時期と新しいライセンスは利用者が決める
- 前提 2: Web サービスは NDF を配布物（マーケットプレイスから導入したプラグイン）として使う。`plugins/` のファイルをパスで読み込まない。これで、プラグインの版と配布の規則（`docs/versioning-and-distribution.md`）がサービスにもそのまま当たる
- 前提 3: CDK のスタック・ネットワーク・秘密の管理は private リポジトリ（owner = `volare`）が持つ。この課題はそのリポジトリへ何も書かない。このリポジトリ側は、インフラへ渡す値（環境変数の名前など）の一覧を `.env.example` の形で持つだけにする
- 前提 4: Web サービスのディレクトリの名前と置き場所、使う言語・フレームワークは設計で決め、ゲート 1 の承認資料に載せる
- 前提 5: 既存のテストの入力に、秘密の形をした偽の値がある（`plugins/ndf/scripts/tests/test_project_decl.py:22` の `AKIA` で始まる値。2026-10-30 に `git grep -nE 'AKIA[0-9A-Z]{16}'` で 1 件）。境界の検査はこれを許可の一覧で個別に除き、受け入れ条件 4 と 5 を両立させる。許可の一覧はファイルと値の組で持ち、ディレクトリごと除かない
- 前提 6: `.env.example`（値を持たない雛形。既存は `plugins/mcp/mcp-dbhub/`・`plugins/mcp/mcp-redash/` の 2 件）は受け入れ条件 4 の「`.env` の実ファイル」に当たらない

## 対象範囲

含む:
- Web サービスのディレクトリの作成（`README.md`・`LICENSE`・`.env.example`・最小の雛形）
- 境界の検査（下の受け入れ条件 2〜4）を CI へ足す
- サービス全体の設計文書: 構成要素、実行基盤（スプリントを動かすコンテナ・ジョブの単位、`supervise.py` のプランと進捗ログをどう Web へ渡すか）、進捗の正本、構成要素の間の契約、#2170〜#2174 の境界
- 用語集へサービスの語を足す

含まない:
- 認証・プラン（#2170）、取り込みと実行（#2171）、一覧と詳細の画面（#2172）、通知と Web からの承認（#2173）、課金と決済の手段（#2174）の実装
- CDK のスタック・ネットワーク・秘密の管理の実装（private リポジトリ側）
- ライセンスの差し替え（前提 1）
- プラグインの配布の仕組みと版の規則の変更（MVV の P1 に当たる）

## 用語

| 用語 | 意味 |
| --- | --- |
| Neural Development Factory | NDF を Web UI から操作できる Software Factory のサービスとして提供するときの名前。プラグインとしての NDF と区別するときに使う |
| サービスのディレクトリ | Web サービスのコードを置く、プラグインと分けた 1 つのディレクトリ |
| 境界の検査 | サービスのディレクトリとプラグイン・配布物・インフラの境目が守られているかを CI で見る検査 |
| 実行基盤 | Web サービスからスプリントを動かす、コンテナとジョブの仕組み |

## 受け入れ条件

- [ ] 1. サービスのディレクトリの中のファイルを足しても消しても、`claude plugin validate .` の結果と、各プラグインの配布物（`.claude-plugin/marketplace.json` の `source` が指す木）の中身が変わらない
- [ ] 2. `plugins/` の下と `.claude-plugin/marketplace.json` のどのファイルも、サービスのディレクトリを参照しない。参照を 1 つ足した Pull Request は境界の検査で落ちる
- [ ] 3. サービスのディレクトリの `LICENSE` を別の文面へ差し替えても、受け入れ条件 1・2 の検査と既存のテストが通る
- [ ] 4. 境界の検査は、リポジトリの中に次のどれかがあれば落ちる: CDK などインフラの定義（`cdk.json`・`aws-cdk-lib` への依存・CloudFormation / Terraform の定義）、秘密らしい値（AWS のアクセスキーの形・秘密鍵の PEM・`.env` の実ファイル）。それぞれを 1 つずつ入れたテストの入力で落ちることを確かめる
- [ ] 5. 既存のテスト（`uv run --frozen --project . --all-extras pytest . -q -n 4`）・`claude plugin validate .`・既存の CI の必須チェックが、この変更の前と同じに通る。プラグインの利用者の手順と振る舞いは変わらない
- [ ] 6. 設計文書が次を決めている: サービスのディレクトリの名前と置き場所、構成要素とその間の契約、実行基盤（スプリントの実行の単位、`supervise.py` のプランと進捗ログを Web へ渡す経路）、進捗の正本、#2170〜#2174 がそれぞれ受け持つ範囲と、互いに依存する契約
- [ ] 7. 設計文書が、ai-plugins の形（ブランチ名・テストのコマンド・配布の手段）を Web サービスの既定に埋め込まない。取り込むリポジトリごとの違いは、そのリポジトリの `.ndf/` の設定で受ける（MVV の Value 5）
