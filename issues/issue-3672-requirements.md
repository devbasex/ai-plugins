## 目的

## 前提

- 前提 1: 普及の前なので、後方互換は要らない（利用者の決定、2026-11-16）。旧い 4 か所の置き場は移行の後に読まない
- 前提 2: ai-plugins は 11.0 を待たずに develop と開発版（`-dev.N`）をやめる（利用者の決定、2026-11-16 04:0x JST。#3641 の追加の決定）。行き先のブランチ戦略は GitHub flow と決め打ちせず、前提 3 の調べで決める（後の決定を正とする）。これは ai-plugins の宣言の値であり、製品の既定ではない。製品は develop→main の行と開発版のデプロイの機能を残す
- 前提 3: ai-plugins はこの機会に plugin 開発のベストプラクティスへ移す（利用者の決定、2026-11-16。設計承認ゲートの第 1 回の出し直しの指示で再度明示）。値は、Claude Code・Codex の plugin とマーケットプレイスを開発するリポジトリのベストプラクティス（ブランチ戦略・版の付け方・タグと Release・利用者が取得する ref）を調べて決める
- 前提 4: 同時に承認した変更の組み合わせの確認は merge queue に任せる（利用者の決定、2026-11-16）
- 前提 5: ruleset でのロックは作らない。承認したら間を置かずにマージし、承認の外の先端は head の一致の確認で止める（利用者の決定、2026-11-15。#3572）
- 前提 6: 宣言のキーの名前は #3613 の改名表（`issues/issue-3613-design.md` の「データ構造」。`branch_flow.promotion` → `release_strategy`、値 `merge_base_branch`・`release_branch`・`trunk`、各版の `vet` → `validation`、移行のコマンド `ndf settings migrate`）と食い違わせない。#3613 が先にマージされても後にマージされても、マージの時点の改名表の名前に合わせる
- 前提 7: 承認ゲートは設計承認ゲートとリリース承認ゲートの 2 つのままにする。宣言の作成・更新・移行・ai-plugins の運用の変更の承認は、この 2 つのどちらかで取る（共通原則の「承認は既存の承認ゲートで取る」）
- 前提 8: 本文と設計で、本番へ届ける操作は「リリース」と呼ぶ。用語集が廃止した語（`.ndf/glossary.json` の `banned` と各語の `deprecated`）を使わない
- 前提 9: 入力（「関連」のセクション）の設計と調査は、この要求を書く時点（2026-11-16）の内容を読む。マージされていない PR（#3649・#3650・#3669）は、その時点の head の内容を読む

## 対象範囲

含む:

- **宣言の形:** 置き場（1 つの設定ファイルの 1 つのセクション）・キー・値・既定値・組み合わせの検査（スキーマ）。表すものは S1 の 9 つ
- **代表のリポジトリの値の表:** S2 の 5 種で、宣言に何を書き、10 系と 11.0 がどう動くか
- **宣言の CRUD:** 宣言を誰が作り（Create）、どの工程と部品が読み（Read）、誰がいつ書き換え（Update）、いつ消すか（Delete）の表
  - 作るのは Skill かスクリプトで、人やエージェントが手で書かない
  - 新規リポジトリ: 代表のリポジトリの種類から選ぶベストプラクティスの既定で作る
  - 既存リポジトリ: そのリポジトリのルールを、過去の事例（マージ済みの PR・ブランチ・タグ・Release の履歴、ruleset、CI のワークフロー）と文書（README・CONTRIBUTING・AGENTS.md など）から読み取って作り、読み取った根拠を作成の結果に残す
  - 履歴と文書が食い違うとき（例: CONTRIBUTING は develop 宛てなのに実際の PR は main 宛て）や根拠が足りないときは、推定で埋めず、根拠を添えて人へ問い、答えを宣言に書く
  - 更新は同じ Skill かスクリプトで行い、組み合わせの検査を通してから書く
  - 消す場面は 2 つ: NDF を外すとき（セクションごと）と、キーを使わなくなったとき（キー単位。同じ Skill かスクリプトが消し、旧いキーの検査に載せる）
- **ai-plugins の値:** plugin とマーケットプレイスの開発のベストプラクティスを出典つきで調べて決めた値と、今の運用から変える点の表。値は宣言を作る Skill かスクリプトが「plugin のリポジトリ」の種類で返す既定と一致させ、ai-plugins の `.ndf/` にだけ書く
- **10 系の読み手:** `plugins/ndf/` のリリースとマージの部品が、新しい宣言だけを読む
- **11.0 の読み手:** `plugins/ndf-next/` の `domains/release`・`progress/gate`・宣言のスキーマが、同じ宣言を読む
- **承認とマージの 1 本化:** 承認した先端だけがマージされる。承認の後にコミットを積まない。承認の記録と証跡の書き手を宣言のケースごとに 1 つに決める
- **移行:** 今の 4 か所の値を新しいセクションへ移すコマンドと、ai-plugins の移行
- **従来の仕組みの削除:** 旧い 4 か所の宣言のキー（`.ndf/worktree.json` の `branch_flow`・`base_branch`・`production_branch`、`.ndf/project.json` の `production_merge`・`delivery`、`.ndf/release.json` の `version_store`、ほかに新しいセクションへ移るキー）、それを読むコード、ブランチ運用とリリースの旧い手順を書いた文書と Skill の本文、旧い分岐を消す。旧い宣言が置かれたリポジトリで旧い経路が動かないことを検査で止める
- **置き換える設計の明記:** #3119・#3121・#3572・#3641・#3576・#3615・#3506・#1338 の設計のうち、宣言と方法論の部分をこの設計が置き換えることと、開いている設計 PR #3649・#3650 の行き先

含まない:

- 用語の改名そのもの（#3613）。宣言のキーの名前だけはこの設計で決め、#3613 と食い違わせない（前提 6）
- リリース後テスト・振り返り・確定仕様化の工程の中身
- 12.0 の作り直し（#3668）。ただし #3668 の観点 V4（製品と ai-plugins を最初から分ける）・V11（リリースはほぼ既製品に任せる）はこの設計の入力にする
- 開いている設計 PR #3649・#3650 を閉じる操作そのもの。設計が行き先を書き、閉じるのは計画の運用が行う
- ほかの開発を止める運用（S8）
