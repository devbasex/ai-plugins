# #2567: 開発ループのテストのステップが、作業場所のテスト用コンテナが止まっているのを確かめずに走り、偽の失敗か出力なしの遅れで止まる

正は課題の本文（#2567）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

DooD（ホストの Docker を共有するコンテナ）で動かすプロジェクトでは、実装・検査・昇格のプランが作る作業場所のテスト用コンテナ（compose の api）が起動していないか、途中で止まる。テストのステップはこれを確かめずに走り、次の形で止まる。

- 全体テストが「4 本落ちた」と報告するが、JUnit に落ちたテストが無く、判定の worker が原因を見分けられずに stop する
- 開発のビルドの確認（`auto.verify`）が出力を一度も出さないまま履歴の最長の 7 倍を超え、終了コード 125 で止まる
- リファクタリング（cross-refactoring）の作業場所は detached HEAD のため、`worktree-testenv.sh up` が「ブランチを取れません」で断る

いずれも人が `worktree-testenv.sh up` を打ち、プランを `--from` で流し直すと通った。

## どこで見つけたか

開発対象リポジトリ（volareinc/carul）の開発ループ l20261104-ux の周回 2（スプリント l20261104-ux-2・l20261104-ux-3 の課題）。

| プラン | ステップ | 時刻（UTC） | 結果 |
| --- | --- | --- | --- |
| 検査（4-check） | test-all | 2026-11-05 04:35 | 判定が stop（落ちたテストが JUnit に無い） |
| 昇格（5-promote） | verify | 2026-11-05 | 終了コード 125（出力なしの遅れ） |

同じ事象は 2026-11-04 の開発ループ l20261103 の周回 3・4 でも 3 回起きている（判定の stop）。

## なぜこの変更の範囲外なのか

スプリントの課題（検証環境の認証・導入の確認・権限のモデル）の受け入れ条件に、プランのテスト環境の起動は含まれない。プランの手順は NDF が持ち、開発対象リポジトリでは直せない。根拠: Value 5（MVV 版 8）

## 直さないと何が起きるか

DooD のプロジェクトで開発ループを流すたびに、テストのステップが止まり、人がテスト環境を起こして流し直すまで周回が進まない。偽の失敗を判定の worker が読むため、そのつど判定の費用もかかる。

## 目的

宣言でコンテナを使うプロジェクトの開発ループが、テスト環境の用意のために人を待たず、テストのステップが止まったときは、原因が読める結果を返す状態にする。

## 前提

- 前提 1: 自動で起こす対象は、`.ndf/project.json` の `test.suites[].container` を宣言したサービスだけである。コマンドの語からは判定しない（#1337 と同じ）
- 前提 2: 全体テストの「JUnit に落ちたテストが無い」の原因は未確認である。この課題は原因を決めずに、次に起きたときに原因が読める結果を返す（受け入れ条件 12）
- 前提 3: 導入の確認の遅れは、テスト環境の停止ではなく、確認のコマンドの中の長い待ちの出力が見えないことで起きた見込みが高い（「調べて分かったこと」の導入の確認の行）。この課題は出力を走っている間に見えるようにする（受け入れ条件 11）。導入の確認の前にテスト環境を用意することは行わない。確認のコマンドが要るコンテナは、コマンド自身が起こす
- 前提 4: ホストの `/work` は使用率 98%・空き 6.4 GB で、テストを走らせる worktree のすべてに 1 環境約 390 MB のボリュームが増える形は続けられない。自動の後片付けでボリュームも消す。作り直せないデータを持つプロジェクトは `.ndf/worktree.json` の `testenv.discard_volumes` に `false` を宣言して残す（2026-11-06 の利用者の答えの変更）

## 対象範囲

含む:
- 範囲テスト・範囲の静的解析・全体テスト（`test-run.py`）の前のテスト環境の用意
- cross-refactoring の着手前のテストと以後のテストの前のテスト環境の用意
- 導入の確認（`verify-facts`・`deploy-facts`）の、走っている間の出力のログへの書き出し
- detached HEAD の worktree でのテスト環境の採番と起動
- 全体テストの失敗の報告（落ちたコマンドが分かる形）
- worktree の削除に合わせたテスト環境の破棄
- テスト環境を自動で起こさないと書いた手順書の更新

含まない:
- 導入の確認の前のテスト環境の用意（前提 3）

- `worktree-testenv.sh test` の経路。人が打つコマンドで、届かなければ今のまま止まる
- 着手前の HEAD の一時の worktree。今のまま見分けられないとして扱う
- carul の `scripts/verify-dev.sh` と宣言の変更
- `testenv` を宣言していないリポジトリ向けに NDF が compose を直接起動すること
- #2624 の残りの項目

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | 起動は上限つきの 1 回で終わる。上限を超えたら受け入れ条件 5 で止まり、待ち続けない |
| 性能・拡張性 | 既に届く worktree では、追加の処理は今の到達の確認 1 回だけである |
| 運用・保守性 | 起こしたこと・起こせなかった理由が結果の JSON に残り、判定の worker と人が同じ材料を読める |
| 移行性 | 導入先の宣言の変更は要らない。`testenv` と `container` を宣言済みのリポジトリは、版を上げるだけで自動で起きるようになる |
| セキュリティ | 確認のコマンドの出力は今と同じく所有者だけが読める権限で書く（出力に秘密が含まれうる）。結果の JSON とログの末尾へ載せるのは全体テストの出力だけで、導入の確認の出力は載せない |
| システム環境 | ホストの Docker を共有するコンテナの中と、ホストの直下の両方で動く。`WT_DOCKER_COMMAND` の差し替えを守る |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| テスト | `uv run --frozen --project . --all-extras pytest plugins/ndf -q -n 4`。コンテナの実行系は `WT_DOCKER_COMMAND` の差し替えで偽物を使う |
| 静的解析・型検査 | リポジトリの CI の既定のジョブ（`python3 scripts/check-skill-frontmatter.py` と `claude plugin validate .`） |
| 手動確認 | carul の開発ループを 1 周流し、人が `worktree-testenv.sh up` を打たずに実装・検査・昇格のプランが通ることを見る。リリース後テストで確かめ、通ったらこの課題を閉じるか残すかを決める |
