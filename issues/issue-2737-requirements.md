## 目的

- Issue を読む人と開発ループ（要求・設計・棚卸し）が、どの Issue でも同じ項目を同じ場所で当てにできる状態にする
- 何を書けば Issue として足りるかを 1 か所に定め、起票の経路（Web のフォーム・`out-of-scope`・`requirements-design`・手で打つ起票）が同じ定義に従う
- 定義に従わない起票が、起票の前か直後に見つかる

## 前提

- 前提 1: これまでの Issue の調査（受け入れ条件 1）と外部資料の調査（受け入れ条件 2）は設計の工程で行い、結果は設計文書に置く。要求の工程では外部資料を取得していない
- 前提 2: Issue の種類は「不具合・機能・調査・運用」の 4 つから始める。調査で 4 つに当たらない Issue が見つかれば、設計で種類を足す
- 前提 3: NDF の中で GitHub へ Issue を作る関数（`gh_rest.issue_create`）を呼ぶのは `issue-file.py` の 1 か所である。確かめた手段: `grep -rn "issue_create(" plugins/ndf/scripts --include=*.py` → 定義の行を除くと `plugins/ndf/scripts/issue-file.py:448` の 1 件（2026-11-08）。これ以外の AI の起票は、AI が `gh issue create` を直接打つ経路である
- 前提 4: Web から起票された Issue は起票の前に止められない（GitHub のフォームの必須欄だけが効く）。この経路は起票の後の検査で拾う
- 前提 5: 起票の前に止める仕組みは Claude Code の上で働けば足りる。Codex の上の起票は起票の後の検査で拾う
- 前提 6: 課題の置き場は `.ndf/project.json` の `issues.primary` が示す。このリポジトリでは `github` である

## 対象範囲

含む:
- Issue に記載すべき記載項目の定義（種類ごとの必須・該当時の区分と、各項目の水準）を 1 か所に置く
- GitHub のフォーム（`bug_report`・`feature_request`・`skill_proposal`）、`out-of-scope` の本文の骨格、`requirements-design` の仕様のテンプレートを、その定義に合わせる
- 定義とテンプレートの食い違いを見つける検査
- AI の起票の前の検査と、open の Issue に対する起票の後の検査
- 課題の置き場ごとの表し方（GitHub・markdown。Redmine は表し方の対応だけ）

含まない:
- open の Issue の本文の書き換え（子の課題 #2738）
- 閉じた Issue の書き換え
- 新しい Skill の追加
- GitHub 以外の課題の置き場（Redmine・Notion など）への書き込み（共通原則の C8）
- 起票の後の検査が見つけた欠けを、機械が自動で書き足すこと

## 用語

| 用語 | 意味 |
| --- | --- |
| Issue の種類 | 不具合・機能・調査・運用など、記載すべき項目の組を決める Issue の区分 |
| 記載項目 | Issue の本文（または課題の置き場の欄）に書く 1 つの事柄。例: 受け入れ条件・再現手順・担当者 |
| 必須の項目 | その種類の Issue で、欠けると起票の前の検査で止まる項目 |
| 該当時の項目 | 条件に当たるときだけ書く項目。当たる条件を定義に書く |
| 記載の水準 | 記載項目に何を書けば満たしたことになるかの基準 |
| 記載項目の定義 | 種類ごとの記載項目・区分・記載の水準をまとめた 1 か所の正本 |
| 起票の前の検査 | AI が Issue を作る前に、本文が記載項目の定義を満たすかを判定する検査 |
| 起票の後の検査 | 作られた open の Issue の本文が記載項目の定義を満たすかを判定する検査 |
| 課題の置き場 | Issue を管理するシステム（GitHub・Redmine・リポジトリの中の markdown など）。`.ndf/project.json` の `issues` が示す |
