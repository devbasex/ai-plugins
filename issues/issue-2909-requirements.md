## 目的

NDF の開発で、スクリプトにできる機械的なターン（AI が判断を伴わずに出力を読み直す・状態を照合する・スクリプトを 1 行ずつ打つ Tool の呼び出し）を減らし、conductor・supervisor・worker とスクリプトの往復の数と費用を下げる。達成したい状態は、次の 4 つの操作で、AI がスクリプトの結果 JSON を 1 回読めば次の 1 手を決められることである。

- スプリントの状態・開発ループの状態・用語集の検査の結果から、次の操作か必要な欄だけを取り出す
- PR・Issue・CI の状態（PR の情報・チェックジョブ・未解決のレビュースレッド）を照合する
- NDF のスクリプトを判断なしで続けて打つ往復を、1 つの「次へ進める」エントリポイントで進める
- 工程の進捗記録（`progress-record.sh`）を、複数の工程についてまとめて 1 回で書く

## 前提

- 前提 1: 削減額の見込み（S1）は目安であり、完了の判定に使わない。完了の判定はターンの数（受け入れ条件 9）で行う
- 前提 2: 「半分以下」（S2）は、ターンの型ごとの**全 Tool の呼び出しに占める割合**で比べる。基準は 2026-10-13〜2026-11-09 の 4 週、比較はこの変更をリリースした日の翌日から 14 日間とする。件数そのものは開発の量で上下するため、割合で比べる
- 前提 3: ターンの型の分け方は、PR #2905 の分析（`usage/mechanical_turns*.csv` の `kind` と `command`）の分類に合わせる。分析の集計スクリプトはリポジトリに置かれていない（PR #2905 の「置かなかったもの」）ため、同じ分類で数える手段をこの変更で用意し、基準もその手段で数え直す（受け入れ条件 8）
- 前提 4: 新しい出力と入口は、既存のスクリプトの副命令か選択肢として足す。PR・CI の照合は、PR の情報・チェックジョブ・未解決スレッドをすでに 1 回で返す `lib/gh_parts.py pr-info` を土台にし、同じ役割の取得を別に作らない（プロジェクト MVV の Value 7）
- 前提 5: 置き換えの効果は、AI が新しい手段を使って初めて出る。そのため、手作業の型を指示している Skill の本文・起動指示の雛形も、新しい手段を指すように直す（受け入れ条件 6）
- 前提 6: 対象とする層は conductor・supervisor・worker である。cross-review・cross-refactoring の相手役（別の CLI のプロセス）の Tool の呼び出しは数えるが、相手役の手順書の書き換えは含まない

## 対象範囲

含む:

- スプリントの状態（`sprint-state.py`）・開発ループの状態（`sprint-state.py loop` と開発ループの状態ファイル）・用語集の検査（`glossary.py`）に、次の操作か指定した欄だけを結果 JSON で返す出力を足す
- PR・Issue・CI の照合を 1 回の実行で要約し、結果 JSON の `next` に次の 1 手（待つ・直す・マージへ進める・人へ戻す）を載せる手段
- NDF のスクリプトを判断なしで続けて打つ往復をまとめる「次へ進める」エントリポイント。判断が要る所で止まり、その理由を `next` に載せる
- `progress-record.sh` で複数の工程を 1 回の実行で記録する手段（Issue の本文の書き換えは 1 回）
- 手作業の型を指示している Skill の本文・起動指示の雛形を、新しい手段へ向け直すこと
- ターンの型ごとの件数と割合を、transcript から数える手段（前提 3）

含まない:

- git の状態の確認（`git status`・`git log`・`git fetch` など）のスクリプト化（S4。候補の表に無い）
- コード探索（grep・sed・cat などでソースを読むこと）の置き換え（S5。判断の材料である）
- 手書きの待ちと `tmux capture-pane` の置き換え（S6。待ちは既存の `merge-when-green`・`supervise.py wait` が担う。使われていない理由の調査は別の課題で扱う）
- 削減額の実測（費用の比較は受け入れ条件にしない。前提 1）
- 相手役の CLI が読む手順書の書き換え（前提 6）

## 用語

| 用語 | 意味 |
| --- | --- |
| 機械的なターン | AI が判断を伴わずに行う Tool の呼び出し。出力の読み解き・状態の照合・スクリプトを 1 行打つ・手書きの待ち・本文の転記。分類は PR #2905 の分析に合わせる |
| ターンの型 | 機械的なターンの分類（例: 「変換: JSON・出力を python -c / jq / cut で読む」「照合: gh で PR・Issue を読む」「往復: NDF スクリプトを 1 行打つ」） |
| 結果 JSON | NDF の手順のスクリプトが最後に 1 行で出す JSON。形の正本は `plugins/ndf/scripts/lib/README.md` の「手順のスクリプトの結果」 |

## 受け入れ条件

- [ ] 1. スプリントの状態・開発ループの状態・用語集の検査のそれぞれに、次の操作か指定した欄だけを返す出力がある。出力は結果 JSON の形（`step_result.py` の `validate_result` を通る）で、次の操作は `next` に、指定した欄の値は `metrics` に載る。同じ状態ファイルに対して、既存の出力から AI が `python -c` で取り出していた値と同じ値が返ることを pytest で確かめる
- [ ] 2. PR 番号を 1 つ渡すと、1 回の実行で PR の状態・チェックジョブの結果（名前ごとの最新の実行）・未解決スレッドの数・PR が指す Issue の開閉を返す。`next` は次の 4 つのどれかの次の 1 手を載せる: 待つ（実行中のチェックジョブがある）・直す（失敗したチェックジョブか未解決スレッドがある）・マージへ進める（すべて成功し未解決スレッドが 0）・人へ戻す（上のどれにも当たらない。理由を添える）。4 つの場合を、GitHub の呼び出しを差し替えたテストで確かめる
- [ ] 3. 「次へ進める」エントリポイントは、判断の要らない手順を続けて実行し、判断が要る所か失敗した所で止まる。止まったときは結果 JSON の `status` が `gate` か `stopped` で、`next` に止まった理由と次の 1 手が載る。続けて実行した手順の一覧が `process` に載る
- [ ] 4. `progress-record.sh` に複数の工程を 1 回で渡すと、Issue の本文の `## 進行` の節にすべての工程の印が付き、本文の書き換え（`gh issue edit` か同等の REST の呼び出し）は 1 回である。通過記録には工程ごとに 1 件ずつ積まれる
- [ ] 5. 受け入れ条件 1〜4 の手段は、ai-plugins に固有の値（リポジトリ名・ブランチ名・テストのコマンド）を既定に持たず、設定か引数で受ける
- [ ] 6. 手作業の型（`python -c` での状態ファイルの読み解き・`gh pr view` と `gh pr checks` の続けての呼び出し・`progress-record.sh` の連打）を指示している Skill の本文と起動指示の雛形が、受け入れ条件 1〜4 の手段を指す。指示が残っていないことを、検索のコマンドとその結果で示す
- [ ] 7. 既存の副命令・選択肢の出力と終了コードは、新しい選択肢を渡さないときに変わらない。全体の pytest が通る
- [ ] 8. ターンの型ごとの件数と、全 Tool の呼び出しに占める割合を、期間を指定して transcript から数える手段がリポジトリにある。この手段で基準の期間（2026-10-13〜2026-11-09）を数え、候補ごとの基準の割合を設計文書に記録する
- [ ] 9. （リリース後テスト）リリースの翌日から 14 日間について受け入れ条件 8 の手段で数え、4 候補それぞれのターンの型の割合が、基準の割合の半分以下である

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 受け入れ条件 2 の 1 回の実行が呼ぶ GitHub の API の回数は、同じ情報を `gh pr view`・`gh pr checks`・未解決スレッドの取得で別々に得るときの回数以下である。API の上限に当たったときは既存の `gh_quota.py` の退避の規則に従う |
| 運用・保守性 | 新しい出力の形は結果 JSON の正本（`lib/README.md` の「手順のスクリプトの結果」）に従い、独自の形を足さない。足した副命令・選択肢はスクリプトの冒頭の説明と Skill の本文の両方から辿れる |
| セキュリティ | 受け入れ条件 8 の数える手段は、会話の本文・会話の ID をリポジトリへ書き出さない（`docs/metrics/README.md` の規約） |
