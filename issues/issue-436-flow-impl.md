## モード

`standard`。工程の構造（ラウンドの層）という公開インタフェースを変え、`refactor.py` /
`SKILL.md` / 手順書 4 本にまたがる。

## 目的と非目的

**達成したい状態**: ラウンドが 4 層になり、レビューがテストへ置き換わり、取り消しが
適用ラウンドの単位で閉じる。

**やらないこと**:

- `cross-review` の内部の変更
- 輪番の決め方（`lib/assignment.py`）の変更
- 構造改善の提案の語彙（兆候 17 種・手法 18 種）の変更
- `monitor.py` の変更

## タスク分解

**機能単位で分ける。各タスクの完了時点でテストが通る状態にする。**

### Task 1: 適用ラウンドの割り当て

- **対象**: `refactor.py`（`merge_proposals` の後段）
- **変更**: 採用した項目を、書き換えるファイルが重ならない群へ分ける関数を足す
- **満たす条件**: A2 / A3
- **進め方**: 先に失敗するテストを書く（同じファイルの項目が別の群へ入ること）

### Task 2: 適用ラウンドごとの適用と検証

- **対象**: `refactor.py`（`cmd_merge_apply` / `cmd_judge_review` の置き換え）
- **変更**: 群ごとに適用 → 検証 → 失敗ならその群だけ取り消す。コミットは群ごとに 1 つ
- **満たす条件**: A4 / A5 / B1 / B3
- **進め方**: レビューの起動を外し、`--baseline-test` の実行で判定する

### Task 3: テスト整備ラウンド

- **対象**: `refactor.py`（新しい副コマンド）/ `docs/01-state-and-propose.md`
- **変更**: 提案ラウンドの前に、テストの薄い箇所へ現状固定テストを足すラウンドを置く。
  提案の語彙は既存の 3 本の参照から採る
- **満たす条件**: B4 / C1 / 語彙外の降格
- **進め方**: 提案ラウンドの構造を流用する

### Task 4: 上限と引数

- **対象**: `refactor.py`（引数）/ `SKILL.md`（用語表・引数の表）
- **変更**: `--max-test-rounds`（既定 2）と `--ci-check` を足し、`--max-outer-rounds` の
  既定を 3 へ。用語表に 4 つのラウンドを並べる
- **満たす条件**: A1 / A6 / E1

### Task 5: 最終ゲートの分岐

- **対象**: `refactor.py` / `docs/04-fix-and-report.md`
- **変更**: 起動のされ方を引数で受け取り、`cross-review` を省略する経路を足す。
  `--ci-check` があれば手元のテストを実行せず `check-runs` で判定する（fail-closed）
- **満たす条件**: B2 / B5 / B6

### Task 6: 提案の時点で防ぐ

- **対象**: `refactor.py`（提案プロンプトの生成 / `init` の検査）
- **変更**: 提案プロンプトへ採用上限を書く。`--scope` にテストの置き場所が無ければ止める
- **満たす条件**: C2 / C3

### Task 7: 改修計画と外へ出す文章

- **対象**: `refactor.py`（改修計画の書き出し / 報告の生成）
- **変更**: 改修計画を Pull Request のコメント 1 件へ書き、2 回目以降は編集する。
  外へ出す文章に `<ファイル>#<シンボル>` と改修計画の URL を入れる
- **満たす条件**: D1 / D2 / D3 / D4

### Task 8: 取り消した項目の除外

- **対象**: `refactor.py`（`excluded_keys` の扱い）
- **変更**: 取り消した項目を次の提案の「対象外」へ入れる（改善項目とテスト項目の両方）
- **満たす条件**: 決定 10

### Task 9: 手順書の追随

- **対象**: `SKILL.md` / `docs/01` / `docs/02` / `docs/04`
- **変更**: 全体フローの図、Step 4 / 5 / 7 の記述、実行のコマンド列
- **満たす条件**: A1 / B6

### Task 10: 実機での確認

- **対象**: 実行のみ
- **変更**: 無し
- **満たす条件**: E4
- **進め方**: **次の実装（#423 運用モードの新設）の Pull Request に対して 1 度通し、
  実測を報告に残す**（利用者の判断）

**この Pull Request では E4 を満たしていない。** 机上の確認（テスト 2507 件・検査 9 本）
までである。**#423 の構造改善の工程で新しい `cross-refactoring` を回し、そこで実測を残す。**

**#436 自身の Pull Request を対象にしない。** 新しい実装が自分自身を改善する形になり、
失敗したときに「実装の誤り」か「対象の問題」かを切り分けられない。

`development-workflow` の記述が参照する。**引数が増えるため、呼び出し例も変わる。**
