# #2225: sprint-close がリリース後テストの「対象の版:」に v の付いた版を読めず、課題を閉じない

正は課題の本文（#2225）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

リリース後テストの記録の `対象の版:` を `v10.26.1（…）` と `v` を付けて書くと、`sprint-close.py --with-verification` がそのブロックを読めず、`kept_open`・理由「本番の版のリリース後テストの記録が無い」を返す。

- 配布の記録（PR #2218 の本文）は `版: 10.26.0 → 10.26.1` で、`lib/dist_record.py` の `parse_record` は本番の版を `10.26.1` と読む
- リリース後テストのコメント（https://github.com/devbasex/ai-plugins/pull/2218#issuecomment-6536126596 ）は `対象の版: v10.26.1（2026-10-31 08:52 JST に…）` で、`_strip_note` の後は `v10.26.1` になる
- `_pick_verify_block` は `b["ver"] == version` の完全一致で探し、外れると「対象の版が版数でないブロック」だけへ落とす。`v10.26.1` は `_EXPLICIT_VERSION`（`v?\d+\.\d+\.\d+`）に当たるため、そこでも外れて `None` になる

実行: `python3 sprint-close.py --record-pr 2218 --with-verification`（2026-10-31、ndf 10.26.1）→ `{"number": 2171, "result": "kept_open", "reason": "本番の版のリリース後テストの記録が無い"}`

## どこで見つけたか

#2171 の振り返りの後の「スプリントを閉じる」（`progress-tracking`）。`plugins/ndf/scripts/lib/dist_record.py` の `_pick_verify_block`（develop では 115〜128 行）と `_strip_note`（47〜49 行）、`plugins/ndf/skills/release-verification/SKILL.md` の 115 行（`対象の版: <配布した版>（<配布した時刻>）`）

## なぜこの変更の範囲外なのか

#2171 の受け入れ条件は `factory/` の契約と受け口だけで、NDF の配布の記録の読み取りを含まない。#2171 は実環境の保留 5 行で開いたままにする判断のため、この不具合が今回の結論を変えてはいない。根拠: NDF の共通原則の「判断の範囲は目の前の変更・操作に限る」（MVV 版 3）

## 直さないと何が起きるか

リリース後テストの書き手が `v` を付けると、すべての条件が合格でも課題が閉じず、受け入れ条件の印も付かない。理由の文が「記録が無い」のため、書いた記録が読めていないことに気づきにくい。

## 目的

- リリース後テストで全条件が合格した課題が、版の書き方（先頭の `v` の有無）だけを理由に開いたまま残らない状態にする
- 書いた記録が読まれなかった理由を、「記録が無い」と取り違えずに済む状態にする

## 用語

| 用語 | 意味 |
| --- | --- |
| リリース記録 | 本番へ出したときに、記録の PR へ書く `## 配布の記録` の見出しのブロック。`版: <前の版> → <出した版>` の行を持つ |
| リリース後テストの記録 | 記録の PR へコメントで投稿する `## リリース後テスト` の節。`対象の版:` の行と合否の表を持つ |
| 対象の版 | リリース後テストの記録の `対象の版:` の行に書く版。全角の括弧から後ろは注記として読まない |
| 本番の版 | リリース記録の `版:` の行の `→` の右に書く版。全角の括弧から後ろは注記として読まない |
| 版の表記の揺れ | 同じ版を指す書き方の違いのうち、この課題が扱うもの。先頭の小文字の `v` の有無だけを指す |

## 前提

- 前提 1: そろえる表記の揺れは、版の先頭の小文字の `v` 1 文字の有無だけである。大文字の `V`、`ndf--v10.26.1` のようなタグ名、前後の余分な語は、この課題では版として読まない（いずれも記録の書き方の手順 `release-verification` が示す形 `対象の版: <配布した版>（<配布した時刻>）` から外れる。実際に書かれた例は PR #2195・PR #2218 の `v` 付きの 2 件だけで、ほかの形は見つかっていない）
- 前提 2: 先頭の `v` を落とす規則は、対象の版と本番の版の両方へ同じように当てる。読み取りの規則を 1 か所（リリース記録を読む共通の部品）に置き、比べる側ごとに写さない
- 前提 3: 本番の版の読み取り結果（スプリントを閉じる処理・リリース記録の重複の確認・プランの版の差し込みが使う値）は、`版:` の行に `v` が付いていても `v` を付けない形で返す。これらの使い手は `v` を付けない版を前提に比べている（リリース記録を書く側は `v` を付けずに書く）ため、返す形を変えても既存の記録の読み取り結果は変わらない
- 前提 4: この課題は柱の課題 #2340（機械が読む出力を 1 行 JSON にそろえ、本文の見出しから判定しない）の子の課題である。#2340 は人が書いた本文から読む値を機械用のブロックへ移す。この課題は移す前の今の読み取りで、表記の揺れを吸収するところまでを扱う。#2340 の仕組みが入った後も、この課題の受け入れ条件 7・8 の再現の手順は #2340 の子の課題の確認にそのまま使える
- 前提 5: リリース後テストの記録の書き方の手順（`release-verification` の「出力物」）は変えない。読む側が `v` の有無を吸収するので、書き手へ `v` を付けないよう求める規則を足さない（Value 5: 要らない決まりを足さない）

## 対象範囲

含む:
- 対象の版と本番の版を比べるときに、先頭の `v` の有無を同じ版として扱うこと
- 本番の版の読み取り結果を、`v` を付けない形にそろえること
- PR #2218（#2171）と PR #2195（#2170）の記録が、本番の版のリリース後テストの記録として読まれることの確認

含まない:
- 実際に版数が食い違う記録（対象の版を `10.26.2` と誤記したなど）で出る理由の文「本番の版のリリース後テストの記録が無い」を言い換えること。原因が書き手の誤記であり、表記の揺れとは別の不具合である。本文の値を機械用のブロックへ移す #2340 で扱う
- 大文字の `V`・タグ名など、前提 1 の外の書き方を読むこと
- リリース後テストの記録の書き方の手順の変更（前提 5）
- #2170 を閉じること。この課題の修正が入った後に、#2170 のスプリントを閉じる工程で判定する
- 設計のクラス図と非機能設計表。変更はリリース記録を読む共通の部品の関数の中に収まり、型（クラス）を足さず変えない。仕様に非機能の条件が無い
