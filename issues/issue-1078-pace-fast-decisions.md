# #1078: 決定の記録・テスト設計・未確認のまま残ること

[issue-1078-pace-fast-design.md](issue-1078-pace-fast-design.md) と
[issue-1078-pace-fast-flow.md](issue-1078-pace-fast-flow.md) の続きである。

## 決定の記録

### 決定 1: `pace` をモードとは別の軸として持つ

モードは変更の中身で決まり、複数に当たれば上のモードが勝つ。進め方は中身と独立に選ぶもので、
同じ判定の表に入れると「上が勝つ」の規則が進め方にも掛かる。6 番目のモードにする案は、
`standard` かつ `fast` のような組を表せないため採らない（2026-09-25 の利用者の判断）。

### 決定 2: 検査の範囲を「前回の検査の時点を宛先にした Pull Request」で表す

`cross-refactoring` と `cross-review` はどちらも Pull Request 1 本を入力に取る。宛先を
`check-base/<名>`（前回の検査の時点）にすれば、差分がそのまま検査の範囲になり、2 つの駆動を
変えずに使える。検査の後に宛先を `develop` へ付け替えると、差分は検査の中で直した分だけになり、
いつものマージの手順で取り込める。

**検査の間に develop が進んでも、差分は検査の修正だけになる。** Pull Request の差分は宛先と head の
マージベースからの 3 点の差分（`base...head`）で、`check/<名>` は検査の開始時の `origin/develop` から切るため、
付け替えた後のマージベースはその開始時の点のままである。develop 側で進んだ分は差分に入らない。
`finish` は付け替えの前に同じ `git diff origin/develop...HEAD` を手元で数え、0/3 をそれで決める。
進んだ develop との衝突は、付け替えの後の `merge-when-green` がいつもの Pull Request と同じに扱う。
そのため develop を取り込む段は置かない。

駆動に範囲（`--since <コミット>`）の引数を足す案は、2 つの駆動と投稿の経路（行への指摘は
Pull Request の差分の行に付く）を両方変えることになるため採らない。マージ済みの Pull Request を
1 本ずつ検査する案は、PR ごとの検査と同じ回数になるため採らない。

### 決定 3: 検査の記録をリポジトリの外の事象の記録に持つ

前回の検査はミッションをまたぐ（期限のトリガーは時刻で立ち、ミッションの境と関係しない）ため、
ミッションの状態には置けない。リポジトリの `.ndf/` に置くと、検査のたびに記録のためのコミットと
Pull Request が要る。置き場所は通過工程の控えと同じ規則にそろえる。**上書きせずに追記だけを行う**
のは、閾値を見直すときに、立たなかった評価の回も数に入れるためである（Value 2）。

別の端末から回すと記録が無く、最新の正式版のタグから数え直す。範囲が広がる側に倒れるだけで、
取りこぼしは起きない。タグで検査の時点を残す案は、タグが関門に当たる操作であるため採らない。

### 決定 4: 逃げた不具合は、その場で直すときに明示して記録する

2026-09-25 の区間（数え方は設計の「具体例」）では、配布を除くマージ 41 本のうち、`fix/` のブランチから
入ったものが 16 本ある（再集計の値。`--format=%s` の件名の `from <所有者>/fix/` を数えた）。大半は前から
起票されていた不具合で、マージ済みの変更から逃げたものではない。題名で数えると、重なりのトリガーが
毎回立つ。そこで conductor がその場で直すと決めた時点で `new impl --escape-of <持ち込んだ PR>` を
渡し、計画が `escape` の事象を書く。持ち込んだ Pull Request が分からないときは `0` を渡す。
**領域は直した Pull Request のファイルから機械で決める。**

### 決定 5: トリガーの評価を計画の外側の「実行の条件」で行う

計画の組み立ての時点で評価すると、実装の queue が終わるまでの間のマージが数に入らない。計画の
最初の段で評価すると、`queue` と `run` が段より先に作業ツリー（`check/<名>`）を作るため、立たない
回にも作業ツリーとブランチが残る。実行の条件は作業ツリーより先に打たれるため、どちらも起きない。
同じ仕組みを、ミッションの終わりの開発版と本番（「最終の検査で変更があったときだけ」）にも使う。

### 決定 6: `eval` の「立たない」を終了コード 3 で返し、読めないときは 2 で返す

`supervise.py` の飛ばしは終了コード 3 を既定にしている（`refactor.py assess` と同じ）。共通の契約
では 3 が「前提が無い」を兼ねるため、`check-trigger.py` は前提の欠け（宣言が読めない・git が無い）を
すべて 2 で返し、3 を「立たない」の 1 つだけに使う。共通の契約の文言（`lib/step_result.py` の
`EXIT_PRECONDITION` のコメント）は、実装で「前提が無い、または各スクリプトが定めた正常な否定の結果
（立たない・変更なし・飛ばしてよい）」に書き直し、`check-trigger.py` の `finish` / `changed` と
`refactor.py assess` の 3 もこの側で読めるようにする。**読めないのに黙って飛ばすと、検査が永久に
立たなくなる**ためである。

### 決定 7: MVV はマイルストーンの説明に置き、承認はハッシュ付きでミッションの状態に残す

マイルストーン 26 は既に説明へ Mission / Vision / Value を持ち、利用者はそこを読んで承認している。
ミッションの初期化の時点でその節をファイルへ写してハッシュを取り、利用者の承認の記録にも同じ
ハッシュを残す。**承認の後に MVV を書き換えると、ハッシュが食い違い、判定は利用者の承認へ戻る。**
LLM が MVV を書き換えて自分の変更を通すことを、この一致で防ぐ。

承認をラベルで表す案は、ラベルが Pull Request に付くもので、ミッションに付けられないため採らない。

### 決定 8: 越えない線は、機械の検査を LLM の判定より先に通す

LLM の `boundary` だけに頼ると、同じ材料でも回によって結果が変わる（Value 1）。パスで決められる
もの（認証の部品・CI の設定・秘密のファイル）は `boundary_paths` で先に止め、パスで決められない
もの（戻せない操作・他のリポジトリへの公開）だけを LLM に見させる。機械の検査で止めるときは
LLM を呼ばない（費用も掛けない）。

### 決定 9: MVV の承認を関門 1・2 の事前の許可として扱い、関門の数は 2 つのまま

関門を省くのは「承認が要らない」からではなく、利用者が MVV の承認を通じて、その範囲の設計と
配布を先に許したからである。そのため `AGENTS.md` の「ユーザーの許可なく PR を承認しない」とは
矛盾しない。許可として扱うのは、次の 3 つがそろったときに限る。MVV の承認の記録があり、
そのハッシュが今の MVV と一致し、判定の記録（判定・理由・ログの行）がミッションの状態と
Pull Request のコメントに残っていること。レビューの approve は行わない。

MVV の承認を 3 つ目の関門として数える案は、関門を「取り消せない操作の前」に限る規則と合わない
（MVV の承認そのものは何も反映しない）ため採らない。

### 決定 10: `fast` の実装 Pull Request は develop へ直接入れる

ミッションのブランチに集めると、develop への取り込みがミッションで 1 回になり、開発版で早く
試せない（Value 3）。2026-09-25 の区間は実際に配布を除く 41 本（配布のマージを含めて 56 本）を develop へ直接入れて回っており、その形を
既定にする。モードを判定する単位もそれに合わせて実装 Pull Request 1 本になる。

### 決定 11: `--then` を段として順に流す

今の `--then` は後続の計画を同じ枠で同時に流す。検査と開発版と本番は順に流れなければならない
（検査の修正を開発版に含めるため）。`--then` を繰り返したときに段として扱えば、1 つだけ渡す今の
呼び方は変わらない。後続の計画の中から次の計画を起動する案は、計画どうしが互いのパスを
知ることになり、queue の結果（`done`）に後続が載らないため採らない。

### 決定 12: トリガーの初期値は #1078 の見積もりのとおりにし、見直しは記録から行う

点数 15（共通層 2 点）・5,000 行・重なり 2 件・24 時間で始める。2026-09-25 の区間（41 本・約 9 時間）に
当てはめると約 4 回で、PR 約 10 本・約 2 時間に 1 回である。**共通層を触ったことは単独の
トリガーにしない**（同じ区間で 31/41 本 = 76% が共通層を触っていた）。見直しは `eval` と `check` と
`escape` の事象から、立った回数・検査 1 回の指摘の件数・検査の後に逃げた不具合の件数を数えて行う。

### 決定 13: `mvv-gate.py` を安定の経路で本体へ移す

`fast` の関門の判定は既定の手順（`new mission --pace fast` の計画）から呼ばれる。試行の置き場を
既定の手順から参照すると `test_experimental.py` が落ちる規約であり、移すしかない。台帳の
「行き先」には本体へ移したことを書く。

## 未確認のまま残ること

| 項目 | 内容 | いつ決まるか |
| --- | --- | --- |
| `cross-review` の指摘が範囲の外の行に付くか | 検査の Pull Request の差分は複数の Pull Request にまたがり、大きい（5,000 行を超えうる）。駆動の分類と上限（ラウンド数・時間）がこの大きさで収まるか | 最初の検査の実測。収まらなければ `scope` の順で範囲を割る課題を起票する |
| 初期の閾値の妥当性 | 4 回 / 9 時間の見積もりは 1 区間から出したものである | 検査を 5 回回した後の振り返りで、`eval` の事象から見直す |
| MVV の写しの取り出し方 | マイルストーンの説明の見出しの形（`## Mission` / `## Vision` / `## Value`）が、マイルストーン 26 以外でも同じか | `new mission --pace fast` を 2 つ目のマイルストーンで使ったとき。見出しが無ければ `stopped` で止める |
| 別の端末から回したときの範囲 | 検査の記録が端末に閉じるため、別の端末では最新の正式版のタグから数え直す。範囲が広がった検査の費用 | 別の端末で回したとき。費用が問題になれば記録の置き場を見直す |
