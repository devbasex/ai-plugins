## 目的

cross-refactoring の実行がどの結果の出口で終わっても、Pull Request に残る記録（リファクタリング計画のコメント）と結果 JSON の件数が、その時点でブランチに残ったコミットと一致する状態にする。読み手と承認する人が、どの改善項目が採用・未確認・取り消し・見送りなのかを、コミットの一覧と突き合わせずに読めるようにする。

## 修正レイヤー（根本原因）

**cross-refactoring の記録の契約: リファクタリング計画のコメントを書く時点と、そこに書く状態の決め方。**

- 書く時点: 今は `plugins/ndf/skills/cross-refactoring/scripts/refactor_lib/publish.py` の `push_head` の末尾（push が成功した直後）だけが `publish_plan_comment`（`refactor_lib/plan.py`）を呼ぶ。push が落ちたとき（`git push` の拒否・`_require_publishable` / `_require_no_tool_paths` の中断）、最終ゲートが判定した後、打ち切った後、取り消した後に push しない経路からは呼ばれない
- 書く状態: 項目の状態の表示（`ITEM_STATUS_LABELS`）は `verified` を最終ゲートの結論にかかわらず「採用」と書く。結果 JSON（`drive.py` の `counts`）は最終ゲートが `passed` でなければ採用を 0 にして `unconfirmed` を出すため、コメントと結果 JSON とで同じ項目の数え方が食い違う
- 読む側: 検査のプランの件数（`plugins/ndf/scripts/check-trigger.py` の `findings_of`）は `adopted` と `reverted` だけを写し、`unconfirmed` を落とす。#1652 の「採用 0」はここで読み手へ届く

修正方針は移動（`move_responsibility`）である。書く責務を `push_head` の末尾から、結果の出口の側へ移し、状態の数え方を結果 JSON と 1 か所で揃える。

## 前提

- 前提 1: 「結果の出口」は、リファクタリング計画ができた後（状態ファイルに `plan` がある後）に cross-refactoring のスクリプト（`drive.py` と `refactor.py` の子コマンド）が終了コードを返して終わる地点すべてを指す。プロセスが外から強制終了された場合（SIGKILL・コンテナの停止）は含まない
- 前提 2: リファクタリング計画ができる前に止まった実行（提案の段で止まった・提案が 0 件）では、コメントを作らない。書く改善項目も見送った提案の理由も、まだ状態ファイルに無いためである
- 前提 3: プランの外の取り消し（conductor が `git revert` で項目のコミットを取り消すこと）は、スクリプトが終わった後に起きるため自動では拾えない。conductor が 1 つのコマンドを打ってコメントを書き直す。どの項目が取り消されたかは、ブランチの履歴（取り消しのコミットが項目のコミットを指すか）から決める
- 前提 4: リファクタリング計画のコメントは対象の Pull Request（同じリポジトリ）へ書くため、共通原則の C5（他のリポジトリへの公開）に当たらない。投稿の手段は今の `gh api`（コメントの作成と編集）のままとする
- 前提 5: 最終ゲートを経ていない項目を採用と数えない決まり（I8。`ledger.adoption_confirmed`）は変えない。`metrics.adopted` は最終ゲートが `passed` のときだけ数え、それ以外は今と同じく 0 とする
- 前提 6: 置き場所が `--plan-file`（ファイル）か「記録しない」の実行は、今の振る舞いのままとする。ファイルへの書き出しはコミットと push を要し、push が落ちた経路で書き直せないためである

## 対象範囲

含む:

- リファクタリング計画のコメントを、すべての結果の出口で書き直すこと（push の成功・push の失敗・最終ゲートの通過・最終ゲート修正の打ち切り・打ち切りの後の取り消し・駆動の中断・finalize）
- コメントの各項目の状態と冒頭の件数を、結果 JSON と同じ数え方（採用・未確認・取り消し・見送り）で書くこと
- コメントに、ブランチへの公開の状態（公開できたか、できなかった理由、未公開の改善項目があるか）を書くこと
- プランの外の取り消しの後に、conductor が打つ 1 つのコマンドでコメントを書き直せること
- 検査のプランの件数（`check-trigger.py` の `findings_of`）が `unconfirmed` を写すこと（#1652）

含まない:

- push が落ちる原因そのもの（整形違反は #464・#1507 が持つ。利用上限・権限・一時的な拒否も直さない）
- 検査のプランを `--from review` で流し直したときに、refactor のステップの失敗が報告に残らないこと（#1648 の観測 5。検査のプランの再開の契約に触れるため別の課題で扱う。下の「未決」）
- 最終ゲートを経ていない項目の扱いの変更（未確認の項目を自動で取り消す・採用と数える、のどちらもしない。前提 5）
- `--plan-file` の置き場所の振る舞い（前提 6）
- cross-review の記録（コメント・結果 JSON）
- 過去の Pull Request（#1663・#1634 など）に残ったコメントの書き直し

## ドメインイベント

| # | イベント | 引き金 | 失敗したとき | 順序の前提 |
| --- | --- | --- | --- | --- |
| E1 | リファクタリング計画を作った | `merge-plan` が計画を取り込んだ | 計画を取り込めず止まった → コメントは作らない（前提 2） | — |
| E2 | 改善項目を検証した・取り消した | 範囲テストの結果 | 直しの打ち切り → 項目を取り消した | E1 |
| E3 | 最終ゲートへ入る push を試みた | `enter_final_gate` | E5 へ | E1 |
| E4 | push が通った | `git push` の成功 | — | E3 |
| E5 | push が落ちた | push の時の検査の拒否・利用上限・権限・一時的な拒否・`_require_publishable` / `_require_no_tool_paths` の中断 | 駆動が止まる（E9） | E3 |
| E6 | 最終ゲートが判定した（通過 / 落ちた / 打ち切った） | `final-gate` | CI が終わらない → 終了コード 4（E9） | E4 |
| E7 | 打ち切りの後に取り消した（案 A / 案 B） | 最終ゲート修正の打ち切り（工程の 1 つとして起動したとき） | 案 B の後でも落ちた → 終了コード 4（E9） | E6 |
| E8 | finalize した | 駆動の `done` | 履歴へ追記できない → 進行は止めない | E6 |
| E9 | 駆動が止まった（中断） | 子のスクリプトの非ゼロ終了・最終ゲートを経ていない | — | E1 の後か前か（前なら E10 を起こさない） |
| E10 | リファクタリング計画のコメントを書き直した | E4〜E9 のどれか、または E11 | 投稿できない → 進行も終了コードも変えず、出力に残す | E1 |
| E11 | プランの外で項目のコミットを取り消した | conductor の `git revert` と push | — | E9 か E8 の後 |
| E12 | 結果 JSON を出した | 駆動の終わり（done / stopped / pause） | — | E10 の後 |
| E13 | 検査のプランが件数を写した | 検査のプランのステップの終わり | — | E12 |

順序の前提: E10 は、その結果の出口で状態ファイルを保存した後・プロセスが終わる前に起きる。E12 の件数と E10 のコメントの件数は同じ状態ファイルから数える。

## 用語

| 用語 | 意味 |
| --- | --- |
| リファクタリング計画のコメント | cross-refactoring が対象の Pull Request に 1 件だけ置き、実行のたびに同じものを編集する記録。目印 `<!-- cross-refactoring plan rf<ID> -->` で引き当てる |
| 結果の出口 | cross-refactoring のスクリプトが、その時点の結果を確定させて終了コードを返す地点 |
| 未確認 | 範囲テストで検証済み（`verified`）だが、最終ゲートが `passed` になっていない改善項目の状態。採用とは数えない |
| プランの外の取り消し | スクリプトが終わった後に、conductor が項目のコミットを `git revert` で取り消すこと |

## 受け入れ条件

コメントの中身:

- [ ] AC1: リファクタリング計画のコメントの各項目の「状態」は、状態が `verified` の項目を、最終ゲートが `passed` のときだけ「採用」と書き、それ以外のときは「未確認」と書く
- [ ] AC2: リファクタリング計画のコメントの冒頭に、採用・未確認・取り消し・見送りの件数と最終ゲートの状態を書く。4 つの件数は、同じ時点の結果 JSON の `metrics`（`adopted` / `unconfirmed` / `reverted` / `deferred`）と一致する（`unconfirmed` が出ない実行では未確認を 0 と書く）
- [ ] AC3: リファクタリング計画のコメントに、ブランチへの公開の状態を書く。push が通ったときは公開した地点の SHA、push が落ちたときは落ちた理由（コマンドの出力の要約か中断の文言）と「未公開の改善項目がある」ことを書く

結果の出口ごとの書き直し:

- [ ] AC4: 最終ゲートへ入る push が通ったとき、コメントを書き直す（今の振る舞いを保つ）
- [ ] AC5: 最終ゲートへ入る push が落ちたとき（`git push` の拒否・`_require_publishable` / `_require_no_tool_paths` の中断のどれでも）、プロセスが終わる前にコメントを作るか書き直す。コメントは AC3 の「落ちた」を記す。リファクタリング計画ができた後で初めての公開が落ちた実行でも、コメントが 1 件できる（#1648 の再現）
- [ ] AC6: 最終ゲートが `passed` になったとき、コメントを書き直し、残った改善項目を「採用」と記す
- [ ] AC7: 最終ゲート修正を打ち切って取り消さずに終わったとき（単独の起動の終了コード 1）、コメントを書き直し、残った改善項目を「未確認」と記す（#1684 の 16 件「採用」の再現）
- [ ] AC8: 打ち切りの後の取り消し（案 A / 案 B）の後、コメントを書き直し、取り消した項目を「取り消し」と記す。案 B の後でも落ちて終了コード 4 で止まったときも書き直す
- [ ] AC9: リファクタリング計画ができた後に駆動が中断（`stopped`）で終わったすべての経路で、プロセスが終わる前にコメントを書き直す。リファクタリング計画ができる前に止まった実行ではコメントを作らない
- [ ] AC10: プランの外の取り消しの後、conductor が 1 つのコマンド（引数は実行の ID か Pull Request の番号）を打つと、コメントが書き直され、ブランチの履歴で実装コミットが取り消された項目を「取り消し」と記す。コマンドとその使いどころを cross-refactoring の手順の文書に書く（#1684 の手での 8 件の再現）

結果 JSON と読む側:

- [ ] AC11: 最終ゲートを経ずに終わった実行（push が落ちた実行を含む）の結果 JSON は、`metrics.adopted` を 0 のままにし、`metrics.unconfirmed` に残った改善項目の数を出す（今の振る舞いを保つ）。あわせて、未公開の改善項目があるか（手元の HEAD が公開した地点より進んでいるか）を `metrics` に出す
- [ ] AC12: 検査のプランの件数（`check-trigger.py` の `findings_of` が返すもの）は、refactor のステップの `metrics.unconfirmed` があれば `unconfirmed` として写す。#1652 の 5 本の形（採用 0・残った改善項目 N 件）の入力から、`applied` 0 と `unconfirmed` N の両方が出る

退行しないこと:

- [ ] AC13: 同じ実行のリファクタリング計画のコメントは何度書き直しても 1 件のまま（目印で同じコメントを編集する）
- [ ] AC14: コメントの投稿・編集が失敗しても、どの結果の出口の終了コードも結果 JSON も変わらない。失敗したことは出力に 1 行残す
- [ ] AC15: 最終ゲートが通って finalize まで進んだ実行の結果 JSON の件数は、今と同じ値になる
- [ ] AC16: 置き場所が `--plan-file` か「記録しない」の実行は、コメントを作らない（前提 6）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | コメントの投稿の失敗（`gh` の失敗・権限・利用上限）で実行を止めない（AC14） |
| 性能・拡張性 | 書き直しは 1 つの結果の出口につき `gh api` の呼び出しを、コメントの検索 1 回と作成か編集 1 回までに抑える（コメントの ID を状態ファイルに持っていれば検索しない） |
| 運用・保守性 | 状態の数え方（採用・未確認・取り消し・見送り）を 1 か所で決め、コメント・結果 JSON・報告（`refactor.py report`）が同じものを使う |
| セキュリティ | コメントへ書く push の失敗の理由に、認証情報（URL に埋め込んだトークンなど）を含めない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 結果 JSON の `metrics` にキーが 1 つ増える（AC11。既存のキーは変えない）。検査のプランの件数に `unconfirmed` が増える（AC12）。プランの外の取り消しの後に打つコマンドが 1 つ増える（AC10） |

## MVV との突き合わせ

反する疑いは無い。記録が実際と食い違わないことを求める（Value 7 判断の理由を残す）、件数を実測と揃える（Value 3 測って決める）、書く時点を現象の場所でなく記録の契約の側で直す（Value 6 根本原因の場所で直す）。書き込むのは同じリポジトリの Pull Request のコメントで、C1〜C8・P1 に当たる操作は増えない。
