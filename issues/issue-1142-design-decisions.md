# 1142: 決定の記録

[issue-1142-design.md](issue-1142-design.md) の決定の節である。

### 決定 1: コンテキストを 8 つにする

要求の初期値の 6 つに、外部 CLI の起動と文書の検査を足す。`lib/monitor.py`・`lib/launch-cli.sh`・
`external-ai.py` は収束ループとプランの実行の両方から起動され、どちらに入れても片方の語で名前を
付けることになる。文書の検査（用語集・指示書・仕様のコピー・棚卸し）は、用語集に既に別の `id` がある。

6 つのままにして、この 2 つを「記録と測定」へ入れる形は採らない。監視の結果や上限時間は測定の語ではなく、
起動の語である。

### 決定 2: ライブラリは `lib/` のフラットなモジュールのまま足す

共通の概念の新しい 6 本（`clock`・`jsonio`・`proc`・`repo`・`loop_drive`・`usage_ledger`）と、分けた
`monitor_patterns.py`・`worktree-*.sh` 4 本を `lib/` の直下に置く。
33 本のスクリプトが `sys.path` に `lib/` のディレクトリを足して `import step_result` の形で読んでおり、
同じ書き方で新しいモジュールも読める。シェルの移植性テストが `lib/*.sh` を glob で拾う前例とも揃う。

`lib/ndf/` のようなパッケージにする形は採らない。既存の import をすべて書き換えることになり、コンテキストの
移行ステップがすべて同じ 33 本に触れて、並列に流せなくなる。モジュール名は `git.py` / `gh.py` にしない。
スクリプトの中の関数名 `git` / `gh` と紛れる。

### 決定 3: テストの差し替えは定義元のモジュールへ向け直す

分けた関数を差し替えるテスト（`state.py` 146 か所・`supervise.py` 8 か所）は、
差し替え先を関数の定義元のモジュールへ変える。受け入れ条件は「置き換え先の変更だけで通る」ことを
求めており、差し替え先の変更はこれに当たる。境界が実際のモジュールになるため、`refactor_lib` の
境界テスト（`test_module_boundaries.py`）と同じ型の検査を `supervise_lib`・`review_lib` に掛けられる。

`cross-review/scripts/monitor.py` の前例のように、分けたモジュールを `exec` で 1 つの名前空間へ読み込む
形は採らない。テストは無修正で通るが、境界が名前だけになり、I1 と境界テストが掛けられない。この形で
いったん分けてから向け直す 2 回の移行も採らない。同じファイルを 2 回触る移行ステップが増える。

### 決定 4: エントリポイントを残し、中身を隣のパッケージへ移す

`supervise.py`・`state.py`・`relay.py` は同じパスのまま引数の解析と `main` だけを持ち、中身を隣の
`supervise_lib/`・`review_lib/`・`relay_lib/` へ移す。前提 1 のとおり、手順書・プランのテンプレート・hook が
呼ぶパスを変えずに済む。`refactor.py` と `refactor_lib/` が同じ形で既に動いている。

エントリポイントを新しいパスへ分け、古いパスを中継として残す形は採らない。変えるエントリポイントが
3 本増え、中継を外す移行ステップも要る。

### 決定 5: ラッパーはバージョンごとのディレクトリと、それを指すファイルで複製する

`relay.py` が 1 本のファイルである理由は 2 つある。シグナルファイルの形を hook 側と共有して食い違わない
こと（`docs/specifications/ndf-relay-segment-restart.md`）と、動いているラッパーが途中で別の版を読まない
ことである。バージョンディレクトリはこの 2 つを別の方法で保つ。hook も複製も同じ `relay_lib/` を読むため、形の定義は
1 か所に残る。バージョンディレクトリは版と digest ごとの新しいディレクトリに書き終えてから `relay.current` を替え（I9）、
`run` は起動時にバージョンディレクトリの全モジュールを import する。ランチャーはプラグインと複製で同じバイト列にし、今の
「中身が同じか」の比較をランチャーに、バージョンディレクトリの比較を `MANIFEST` の digest に当てる。

採らない形と理由:

- zipapp で 1 ファイルにまとめる形: 実際に試すと Python 3.10 で動いたが、`__file__` が zip の中を指して
  `_self_body` と版の読み取りが壊れ、`spec_from_file_location` のテストも使えない。生成物の差分が読めない
- ビルドで 1 本の `.py` へ結合する形: 約 2000 行の生成物が残り、1000 行の上限に例外が要る。名前の衝突を
  書き換える処理も増える
- `run` の系だけを 1 本で複製する形: シグナルファイルの形の定義が複製側と hook 側の 2 か所になる
- 同じディレクトリを上書きする形: 置き直しの途中に起動したラッパーが新旧のファイルを混ぜて読む

### 決定 6: ラッパーのバージョンディレクトリにライブラリの `clock.py` と `jsonio.py` を入れる

`relay.py` の `now_iso`・`read_json`・`write_json_atomic` はライブラリと同じ概念である。バージョンディレクトリに 2 本のコピーを
入れれば、ラッパーもライブラリの 1 つの実装を使い、例外リストに残さずに済む。2 本は標準ライブラリだけを
import する（I1）ため、バージョンディレクトリの中で閉じる（I2）。ラッパーの時刻の形（UTC・ミリ秒・`Z`）は `clock.iso` の引数で
表し、`log.jsonl` の形は変えない。

ラッパーのコピーだけを例外として残す形は採らない。片方だけ直した不具合がもう片方に残るという、要求が
挙げた問題がそのまま残る。

### 決定 7: 例外リストは「ファイル:名前」と理由で持ち、規則で外すものを分ける

`scripts/script-structure-allow.json` の 1 行は `{"path", "name", "kind", "reason"}` を持つ。副命令の
ハンドラー（`cmd_*`）・`main`・`build_parser`・`_build_parser`・シェルの `usage` は規則で外し、リストに
載せない。**使われない行は構造チェックが落とす。** 直した移行ステップが同じ PR で行を消すことになる。
行はパスの順に並べ、コンテキストごとにまとまるため、並列の移行ステップが同じ行を触らない。

名前だけで持つ形は採らない。`load`・`parse` のように同じ概念の重複と別の概念が同じ名前に混ざり、
名前ごと許すと新しいコピーを見逃す。先頭が `_` の関数を一律に外す規則も採らない。統合の対象の
`_parse_time`・`_git`・`_tmp_dir`・`_sh` が含まれる。

### 決定 8: 本体の比較は docstring・型注釈・関数名を除き、シェルも対象にする

計測の `structure.py` は `ast.dump` をそのまま比べるため、docstring だけが違う `call`・`review_status` と、
名前だけが違う `_repo_slug` と `repo_slug` を取り逃す。構造チェックはこれらを除いた構文木で比べる。
シェルは同じ名前の関数を数える（`resolve_print_timeout` の 3 つのような重複がある）。シェルの本体の
比較は行を正規化した文字列で行う。

E1 と E9 の比較には、計測の `structure.py` をそのまま `measure/structure-baseline.py` として使う。
物差しを直すと、移行の前後の値を比べられなくなる。

### 決定 9: 不足 d は、収束した drive が `init` を打ち直さない形で直す

根の原因は、`drive.py` が呼ばれるたびに `state.py init` を打ち、`final` が決まった状態を再開の対象にしない
`init` が、空のレビューの状態で上書きすることである（r18 の `01-review.out` で確かめた）。過去を上書きで
失う構造なので、上書きそのものを止める。`init` の値を drive の状態の `init_vars` に残し、`stage` が `sweep` と
`done` のときはそれを使う。

`sweep` に入るときに件数を控えて `done` がそれを使う形は採らない。件数は合うが、空の状態のファイルが
残り、`report` や再開が空の状態を読む。`state.py init` の再開の規則を変える形も採らない。規則は利用者が
打ち直す再開にも効き、影響がこの不足の外へ広がる。

### 決定 10: 不足 f は 1 呼び出し 1 行の帳簿と、状態の実体の置き場で直す

`claude -p` の結果の `usage` と `modelUsage` を、呼び出しごとに使用量の帳簿へそのまま追記する。5 分と
1 時間の区別は `usage.cache_creation` にしか無く、合計にした時点で戻らない。帳簿は `mvv-gate.py` の
呼び出しも受ける。プランの状態は、プランが一時ディレクトリの下にあるときだけ実体を状態の置き場に作り、
`<プラン>-state` をシンボリックリンクにする。読む側はパスを変えずに済む。

`--no-session-persistence` を外して会話の記録を残す形は採らない。`token-usage.py` はその会話を別の
conductor として、その時に入っていた版で数える。状態の既定のパスを状態の置き場へ変える形も採らない。
`<プラン>-state/` を読む手順と試行が壊れ、エントリポイントの形が変わる。

### 決定 11: 不足 a は `new fix` を新しい種別として足す

`new fix` は `impl` のテンプレートから worker の実装のステップを除いたプランを作る。必須の引数が `impl` と違う
（課題は要らず、worktree が要る）ため、種別を分ければ `new fix --help` がその種別の引数だけを出す。

`new impl` に「worker を起動しない」の引数を足す形は採らない。`--issue` を必須から外す条件分岐が
`NEW_REQUIRED` と `cmd_new` の名前の決め方に入り、`impl` の説明が 2 つの使い方を持つ。

### 決定 12: 計測の 2 本は S1 で根の `scripts/measure/` へ移す

要求の本文は「設計 PR で `scripts/` へ移す」と書くが、設計 PR は要求と設計の文書だけを載せる
（`design` の手順 5）。E1 の値はコメントとスクリプトの今の置き場所（`~/.local/state/ndf/measure-1142/`）で
打ち直せるため、移すのが 1 つ後の PR になっても基準は失われない。S1 は移すときに、決め打ちのパス
（`/work/ai-plugins`・`/tmp/ndf-sv`）を引数へ出す。数え方は変えない。

### 決定 13: 不足 c は差分から他のプラグインを列挙し、本番のプランだけが PATCH を上げる

`changed-plugins` が前のタグからの差分でプラグインを列挙し、本番のリリースプランの `bump-others` が
プラグインごとに PATCH を 1 つ上げる。10.17.9 と 10.17.26 で手で足したステップと同じ操作である。
宣言の `release.plugin` は単数のまま使い、ndf のタグ・題名・CHANGELOG の扱いは変えない。開発版の
プランは他のプラグインの版を上げない。他のプラグインは開発版の接尾辞を持たずに配っている。

宣言を `release.plugins` の配列へ広げる形は採らない。schema と宣言の形が変わり、前提 1 に当たる。
他のプラグインのタグは付けない（今 0 件）。付けるかどうかは版と配布の方針の判断で、この課題の外にある。

### 決定 14: シェルを Python へ書き換えない

`worktree-common.sh` は分けるだけにし、字句解析は bash のまま残す。hook は毎回の Tool の呼び出しで
読み込まれ、Python の起動を足すと遅くなる。`workflow-common.sh` の `wf_split` と `worktree-common.sh` の
`_wt_tokenize` は目的が同じだが、出力の形（NUL 区切り / 配列）と精度（heredoc・リダイレクト）が違い、
2 つの契約（#427・#565）を同時に満たす統合は振る舞いを変えるため、この課題の構造の変更に含めない。

### 決定 15: 語の移行は、コンテキストの移行の後の別のミッションで行う

中身を移す差分と語を替える差分を 1 つの PR に混ぜると、移しただけの行と意味が変わった行をレビューで
見分けられない。読み替えの要る値（R1〜R5）は書く側と読む側を同じ移行ステップで変える必要があり、
モジュールの置き場所が決まった後なら、1 つの移行ステップが 1 つのコンテキストの中で閉じる。

コンテキストの移行ステップの中で語も替える形は採らない。ミッション 2 の PR が大きくなり、C1〜C7 の
差分が読めなくなる。

### 決定 16: 不足 g は GitHub の呼び出しを `gh_parts` へ集め、2 つの枠を使い分けて、読み直しを ETag で数えさせない

GraphQL と REST の上限は、どちらも 1 時間に 5000 で、アカウント単位でほかのコンテナ・セッションと共有する。
1 回の消費はほぼ同じである（2026-09-26 の実測: `gh pr view` 1 点・`gh pr checks` 2 点・`gh issue list --limit 300`
5 点、REST は 1 回で 1）。上限に当たったのは、`gh pr` / `gh issue` の高水準コマンドがすべて GraphQL を使い、
NDF の呼び出し（23 ファイル・115 か所）がすべて GraphQL の枠に偏ったためである（同じ時刻に REST は 4700 以上残っていた）。
すべてを REST へ移すと、偏る先が変わるだけで使える量は変わらない。

**消費の大部分は同じものの読み直しである。** merge-when-green は CI を 10 秒ごと（配布の中からは 5 秒ごと）に読み、
1 回で約 3 点を使う。REST の `If-None-Match`（ETag）付きの要求は、変わっていなければ 304 を返し、上限に数えない
（実測: 3 回打って残りが変わらない）。

| 呼び出し | 使う枠 | 理由 |
| --- | --- | --- |
| 読み直し（CI の結果・PR の状態・コメントの増減の待ち） | REST の ETag 付き | 変わるまで上限に数えない |
| PR と課題の単発の読み書き（読み取り・一覧・作成・編集・コメント・マージ） | REST | GraphQL の枠を、代われない操作のために残す |
| 入れ子の読み取り（レビューのスレッドとコメント） | GraphQL | 1 回で済む。REST ではページとスレッドの数だけ要る |
| REST に無い操作（スレッドの resolve・Projects のボード・draft を ready にする） | GraphQL | 代われない |

片方の枠が上限のときは、代われる操作をもう片方の枠で行う（REST の関数は GraphQL の `--json` と同じ形で返すので、
呼び出し側は枠を知らない）。代われない操作は回復の時刻（`rate_limit` の reset）まで待ってからやり直す。
待ちの問い合わせの間隔は、変化が無い間は 10 秒から 60 秒まで伸ばし、変化があったら縮める。

即時修正 #1211 の `view_json`（GraphQL が上限のときだけ REST で読む）は、この使い分けの一部になる。残りの
呼び出し側は、ファイルを移す移行ステップ（C1〜C7）の中で置き換える。別の移行ステップにすると、同じファイルを
2 度触り、移行ステップどうしが同じ行で衝突する。

### 決定 17: 不足 h は外部パッケージを 1 つの宣言と lock で固定し、エントリポイントが uv の環境へ自分を起動し直す

**標準ライブラリだけで書く前提をやめる。** GitHub のクライアントが最初の例で、配布先のクラウドの SDK
（boto3 など）のように、それが無いと始まらない依存もこれから増える。そのたびに自前で書くと、上限・待ち直し・
認証の扱いを外部パッケージより弱い形で持ち続けることになる。この決定は、外部パッケージを使う一般の仕組みを決める。

**依存の宣言は `plugins/ndf/pyproject.toml` と `plugins/ndf/uv.lock` の 1 組にする。** 版は lock が固定し、
ハッシュも lock が持つ。外部パッケージを足す・版を上げるのは、この 2 つを変える PR だけである
（要求の境界の「確認してから行う」）。

**パッケージは用途ごとのグループ（`[project.optional-dependencies]` の extra）に分ける。** 例は `github`（githubkit）・
`aws`（boto3）である。エントリポイントは `require("github")` のように使うグループを名前で渡し、`require()` は
そのグループだけを入れた環境で起動し直す（`uv run --extra <名前>`）。`uv run` の同期は足すだけで、別の extra で起動し直しても前に入れたものは消えない（2026-09-26 に github → aws → github の順で確かめた）。boto3 と botocore だけで約 30 MB になるため（同日の実測）、
GitHub しか使わないエントリポイントの初回の解決に AWS の SDK を含めない。グループに無いパッケージを
import するモジュールは、構造チェックが落とす（I1）。

**エントリポイントを起動する形（`python3 <パス>`）は変えない**（前提 1）。外部パッケージを使うエントリポイントは、
最初に `lib/deps.py` の `require()` を呼ぶ。`require()` は標準ライブラリだけで書き、次の順に動く。

| 順 | 条件 | 動き |
| --- | --- | --- |
| 1 | 渡したグループのパッケージが import できる | そのまま戻る（uv の環境の中で起動されたとき） |
| 2 | 環境変数 `NDF_DEPS_REEXEC` がある | 起動し直したのに import できないので、理由を出して止まる（終了コード 3）。起動し直しを繰り返さない |
| 3 | uv が見つかる（`PATH`・`~/.local/bin`・`~/.cargo/bin`） | `uv run --frozen --project <プラグインの根> --extra <名前> python <パス> <引数>` で自分を起動し直す（`os.execv`）。環境は `UV_PROJECT_ENVIRONMENT` で `~/.cache/ndf/venv/<版>` に置き、プラグインのキャッシュの中に作らない |
| 4 | uv が無い | 版を固定した公式のインストーラで `~/.local/bin` へ入れ（`UV_NO_MODIFY_PATH=1`）、stderr に 1 行を出してから 3 へ進む。curl が無ければ `python3 -m pip install --user uv==<版>` を使う |
| 5 | 入れられない（ネットワークが無い・権限が無い） | 何が無いかと、手で入れるコマンドを出して止まる（終了コード 3） |

2026-09-26 の実測（uv 0.12.19・githubkit 0.16.1）では、初回の解決と取得が 1.19 秒、2 回目以降の起動し直しの
上乗せは 0.12〜0.18 秒である（標準ライブラリだけの `python3` の起動は 0.014 秒）。

**hook とラッパーのバージョンディレクトリは外部パッケージを使わない**（I13）。hook は Tool の呼び出しごとに起動され、0.1 秒の
上乗せが毎回かかる。ラッパーのバージョンディレクトリは `~/.claude/ndf/` へ複製して動くため、プラグインの宣言を参照できない。
それ以外のエントリポイント（プランの実行・リリース・収束ループ・記録と測定など）は外部パッケージを使ってよい。どれも外部の呼び出しを持ち、1 回の起動が 0.1 秒の上乗せより十分に長い。

**最初に使うのは GitHub のクライアントである。** `lib/gh_parts.py` の中身を githubkit の上に置き、
決定 16 の使い分け（REST の ETag での読み直し・2 つの枠の代替・上限の待ち）を githubkit の
`http_cache`・`auto_retry` で実現する。認証は `gh auth token` の値を渡す（`gh` は認証の出どころとして残す）。
githubkit の待ち直しは既定で 1 回、ETag のキャッシュはプロセスの中だけ、同時数の制限もプロセスの中だけなので、
上限の回数・回復の時刻までの待ち・間隔の伸長は `gh_parts` が持つ。merge-when-green は 1 本のプロセスで
読み直すため、プロセスの中の ETag で足りる。

**githubkit を L0 に入れる前に、試行で 3 つを確かめる**（`experimental/` に置き、既定で動くものから参照しない）。
githubkit の ETag 付きの読み直しが上限に数えられないこと、4 ランタイム（Claude Code・Codex・Kiro・agy）から
起動し直しが動くこと、uv の無い環境で入れてから続くこと。どれかが成り立たなければ、`gh_parts` は
決定 16 のとおり標準ライブラリで書き、`require()` と宣言だけを残す。

パッケージのファイルをプラグインへ同梱する形は採らない。githubkit が引き込む pydantic-core はバイナリで、
アーキテクチャと Python の版ごとに要る。スクリプトごとに PEP 723 で宣言する形も採らない。ライブラリの
モジュールが外部パッケージを使うと、そのモジュールを import するエントリポイントのすべてに同じ宣言が要り、
版が食い違う。

### 決定 18: 行数の上限を 500 にし、例外リストのラチェットで減らす

2026-09-26 の develop の実測（テストを除く `.py` / `.sh` の 128 本）で、中央値は 216 行・75 パーセンタイルは 389 行・
90 パーセンタイルは 822 行である。1 行は平均 45〜49 バイトで、1000 行のファイルは約 48 KB になり、worker が 1 回読むと
1 万数千トークンを使う。1000 行は pylint の `max-module-lines` の既定と同じで、明らかに長いものを落とす値であり、
この課題の目的（worker が 1 回の修正で読む量を減らす）には大きい。設計の時点で 991 行だった `gitfacts.py` は
1011 行に増えた。

**行数の区分は、`markdown-writing` のルール 9（文書の長さと分割ルール）と同じ 3 つにする。** 文書とスクリプトで
「長い」の基準を分けない。構造チェックが落とすのは 501 行以上だけで、300 行は目安である。

| 行数 | 対応 |
| --- | --- |
| 300 行まで | そのまま。新しく作るファイルはここを目安にする |
| 301〜500 行 | 分けると読み手の理解が落ちるなら、1 ファイルのままでよい。1 つの状態機械・1 つのクラスの本体・大半が照合の表やデータのファイルがこれに当たる。独立して読める単位があるなら 300 行以下でも分ける |
| 501 行以上 | 分ける。構造チェックが落とす（I5） |

501 行以上のファイルは 23 本ある。一度に分けると移行の範囲が大きく増えるため、例外リストのラチェットで減らす。

| 対象 | 扱い |
| --- | --- |
| 分けて新しく作るファイル・新しく足すファイル | 500 行以下。例外リストに載せない |
| 移行ステップが中身を移すファイル（移行の文書の「中身を移すもの」と `lib/gh_parts.py`） | 分けた後のすべてを 500 行以下にし、例外リストから消す。分け方は関数の単位で設計が決める（[issue-1142-design-modules.md](issue-1142-design-modules.md) ） |
| 重複だけをライブラリへ置き換えるファイルと、移行の範囲の外で 500 行を超えるファイル | 例外リストに理由と今の行数を載せる。載せた行数を超えたら構造チェックが落とす。触って 500 行以下にしたら消す |

上限を下げるのは L0 である。S1 の構造チェックは 1000 行で入っており、ミッション 1 の移行ステップを流している間に
上限を変えると、並列の PR の例外リストが食い違う。

**AI が読むときも、行数より 1 ファイル 1 責務のほうが効く。** 長いファイルは、読む量がそのまま費用になり、関係の
無い行が多いほど似た名前の別の関数を直す誤りが増える。Edit の置き換えは一致が一意であることを求めるため、
長いファイルほど一致が重なる。並列の worker が同じファイルを触ると順に流すしかない（ミッション 1 の S3 と S5 は
`supervise.py` を共に触るため順に流した）。一方で細かく分けすぎると、1 つの変更で読むファイルと Read の回数が増える。
301〜500 行を認めるのはこのためである。300 行を落とす値にすると 44 本が対象になり、移行ステップの中で分け切れない。効果は E9 で、worker が
1 回の修正で読んだバイト数を移行の前と比べて確かめる。
