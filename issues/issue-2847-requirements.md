## 目的

並列の計画で複数のレーンが同じリポジトリの棚卸しを流しても、見直し・大整理の報告と深さの記録が、その実行自身が集めた候補・反映・順位の値を載せる状態にする。

今は、記録の置き場（`$NDF_UPKEEP_STATE_DIR` の下のリポジトリごとのディレクトリ）が 1 つで、差分の棚卸しは見直しの持ち主を取らない。このため、見直しの最中に別のレーンの差分の棚卸しが候補の記録を書き換え、前の回の反映と順位の記録を消す。見直しの報告は、別の実行の対象の件数と open の件数を自分の値として返す（2026-11-08、見直しが集めた対象は 283 件・open は 283 件だったが、報告は対象 10 件・`open_before` 281 を返した）。深さの記録（`depths.jsonl`）は報告の値を写すため、深さの記録にも別の実行の値が残る。

## 前提

- 前提 1: 見直し・大整理は、`candidates` を打つより前に `owner claim` で持ち主になり、実行の識別子（`run`）を持っている。まとめのステップ（`plugins/ndf/scripts/supervise_lib/sprint_close_steps.py` の `_depth_steps`）は `claim` の後に本体を動かすため、今の手順はこれを満たす
- 前提 2: 持ち主が引き取られた（`taken_from` が付いた）見直しでは、引き取った側が `candidates` から打ち直す。引き取られた側の候補・反映・順位の記録を、引き取った側の報告へ持ち越さない
- 前提 3: 記録の置き場は一時ディレクトリにあり、版を上げたときに候補・反映・順位の記録（`candidates.json`・`apply.json`・`rank.json`）を引き継がなくてよい。その回の記録は次の `candidates` から作り直せる
- 前提 4: 回をまたいで共有する記録（反映の済みの記録 `ledger.json`・見積もりの記録 `estimates.json`・人が退けた移動 `rejected.json`）は、実行ごとに分けずに共有のままにする。2 度書かない照合と、見積もりの引き継ぎがこれに頼っているためである
- 前提 5: 書き込みはどれも一時ファイルからの置き換え（`jsonio.write_atomic`）で行われ、1 つのファイルが途中まで書かれた形で読まれることは起きない。この変更で扱うのは、別の実行の書き込みを自分の記録として読むことである

## 対象範囲

含む:

- 持ち主を持つ見直し・大整理の実行と、同じリポジトリで並行する別の実行（差分の棚卸し）との間で、候補・反映・順位の記録を取り違えないようにすること
- 見直し・大整理の `report --depth` と `depth record` が、自分の実行の記録を読むこと
- 差分の棚卸しの `report` と `depth record` が、並行する見直しの記録を自分の値として読まないこと
- 2 つの実行を交互に進める自動テスト

含まない:

- 持ち主を持たない実行どうし（差分の棚卸しが 2 本並行する場合）の取り違え。扱うかは「未決」に置く
- 回をまたいで共有する記録（前提 4）の同時の書き込みの扱い
- 見直しの持ち主の取り方・寿命・見張り（`owner claim`・`keepalive`）の変更
- 記録の置き場の既定の場所（一時ディレクトリ）の変更
- 既に起きた lcore 周回 2 の深さの記録の行の書き直し

## 用語

| 用語 | 意味 |
| --- | --- |
| 棚卸し | 課題の一覧を現状へ合わせる作業（`backlog-refinement`）。深さは差分の棚卸し・見直し・大整理の 3 つ |
| 差分の棚卸し | 前の版からの差分に関わる課題だけを拾う、浅い棚卸し（`candidates --depth diff`）。持ち主を取らない |
| 見直し | 後回しを除く open の全件を対象にする棚卸し（`--depth review`）。持ち主を取ってから流す |
| 大整理 | 後回しの課題も含めて付け直す棚卸し（`--depth overhaul`）。持ち主を取ってから流す |
| 見直しの持ち主 | 見直し・大整理・調査を行ってよい 1 つの実行。`.ndf/backlog/owner.json` の宣言が示す |
| 棚卸しの実行 | 棚卸しを 1 回流すまとまり。持ち主を持つ実行は、`owner claim` が返した識別子（`run`）で区別する |
| 棚卸しの記録の置き場 | `upkeep.py` が候補・反映・順位の記録を置くディレクトリ（`$NDF_UPKEEP_STATE_DIR` の下にリポジトリごと） |
| 候補の記録 | `candidates` が書く記録（`candidates.json`）。対象の件数・経路ごとの件数・open の件数を持つ |

## 受け入れ条件

1. [ ] 見直し（以下「実行」は棚卸しの実行を指す）の持ち主が有効な間に、見直しが `candidates --depth review` を打ち、続けて別の実行が同じリポジトリで `candidates --depth diff` を打った後でも、見直しの `report --depth review --run <run>` の `metrics.targets`・`metrics.by_route`・`metrics.open_before` が、見直しの `candidates` が返した `metrics.candidates`・`metrics.by_route`・`metrics.open` と一致する
2. [ ] 1 と同じ順序で、別の実行の `candidates` の後に見直しが `apply` を打ったとき、見直しの `report` の区分の内訳（`metrics.verdicts`）と反映の件数（`metrics.applied`・`metrics.closed`）が見直しの `apply` の値と一致する。また、別の実行の `candidates` が、見直しがそれより前に打った `apply` と `rank` の記録を消さない
3. [ ] 見直しが `rank` を打った後に別の実行が `rank` を打っても、見直しの `apply`（plan の `rank` に見直しの `rank` の `metrics.digest` を書いたもの）が順位の表を書き（`metrics.tables.failed` が空で、「plan の rank が rank.json と合わない」で止まらない）、見直しの `report` の順位の節（`metrics.ranked`）が見直しの `rank` の値と一致する
4. [ ] 大整理の持ち主が有効な間に別の実行が `candidates`・`rank` を打っても、大整理の `report --depth overhaul --run <run>` の `metrics.open_before`・`metrics.closed`・`metrics.created` に別の実行の記録の値が入らない（大整理自身の記録の値か、記録が無ければ `null`）。大整理の `apply` の記録を別の実行の `candidates` が消さない
5. [ ] 見直しが同時に流れていても、差分の棚卸しの `report` の `metrics.targets` と、`depth record --depth diff` が深さの記録へ写す open の件数が、差分の棚卸し自身の `candidates` の値と一致する
6. [ ] 持ち主がいない直列の使い方は振る舞いを変えない。同じ実行で `candidates` を打ち直すと前の `apply` と `rank` の記録を報告に混ぜない。見直しの `rank` が書いた見積もりの記録を、後の差分の棚卸しの `candidates` の `unscored` の判定が読む。反映の済みの記録は実行をまたいで 2 度書きを防ぐ。既存の棚卸しのテスト（`plugins/ndf/skills/backlog-refinement/tests/`、193 件）がすべて通る
7. [ ] 2 つの実行（見直しと差分の棚卸し）が同じリポジトリの記録の置き場を共有して、2026-11-08 の順序（E2 → E3 → E4 → E5 → E6 → E7 → E8）を交互に流す自動テストがあり、1〜3 と 5 を確かめる。このテストは変更前のコードでは失敗する
