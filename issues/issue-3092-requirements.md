## 目的

- **今どうなっているか**: `/ndf:development-workflow` は、モードごとの工程を `SKILL.md` の表で定める。工程は要求と受け入れ条件・設計・ドキュメントレビュー・計画・実装・リファクタリング・コードレビュー・完了判定・Pull Request・確定仕様化・後片付け・デプロイ・リリース後テスト・振り返り・棚卸しである
- 今の目録（`.ndf/sprint-<名>/sprint.json`）が持つステージは「設計 … 検査・デプロイ・本番」までである。まとめ（確定仕様化・リリース後テスト・振り返り・棚卸し・課題を閉じる）は今の目録に無い
- まとめは、レーンの conductor が手順書を読んで組んでいる。読むのは `references/parallel.md` の「レーンの側」で、conductor が自分で `supervise.py new close` を組んで流す（2026-11-12、計画 p5 のレーン lgate・lcost2）
- 工程の有効・無効もコードと手順書に散っている。リファクタリングを外す判定は `supervise_lib/templates.py` の関数 `refactor_suspended` が持ち、緊急の停止の定数 `CROSS_REFACTORING_SUSPENDED`（PR #3054 で足し、2026-11-13 の時点の値は `False`）と CI テストの宣言（`.ndf/project.json` の `test.ci.only`）から決める（#3056）。文書だけの差分で cross-refactoring と全体テストを飛ばす条件は Skill の本文の表が持つ
- 次に何をするかの判断と、工程が終わったことの記録が 1 か所に無い。再開は `queue --resume --from <プラン>=<ステップ>` を conductor が組み立てる。`--from` の扱いの不具合（#3086・#3047・#2806・#2639・#2349）で止まる。通した工程の記録はプランのステップと食い違う（#2921・#1893）
- 並列の計画の状態は `plan.json`（レーンの配列）・計画の台帳（`ledger.jsonl`・`checkpoint.json`）・耐久ワークフローの DBOS の記録の 3 か所に分かれる。レーンは 1 スプリントか開発ループ 1 つしか持てず、外した課題を次のスプリントで流すときは `after` 付きの新しいレーンを足している（計画 p5 のレーン lcost の残りを、レーン lcost2 で流した）。#3085・#3080・#3021 はこの分かれ方から起きた（#3097 から取り込んだ）
- スプリントで外した課題や、スプリントの中で起票した課題を次へ回すのは手作業である。オーガナイザーが会話の中で `parallel.py lane add`・`set` を打っている（計画 p5 のレーン lcost2・lgate・lci・ltask。#3098 から取り込んだ）
- **変えると何が成り立つか**: モードごとの全工程が進行表の行としてスクリプトで組まれ、工程の状態を進行表が持つ。スクリプトは進行表だけを読んで次にやる工程を決め、終わった工程に終了の印を付ける。conductor は異常のときだけ、進行表に従って進めるか、進行表の状態を書き換える。手順書を読み落としても工程が抜けない。計画の状態は計画の進行表とレーンの進行表から読め、スプリントの終わりで同じレーンの次のスプリントへ進む。スプリントで分かったことは、組み換えの工程が終わった時点で計画へ戻す
- **誰に効くか**: NDF で並列の計画とスプリントを流す利用者と、その conductor・オーガナイザー。手順書の読み落としによる工程の抜け・再開の手組みの失敗・課題の持ち越しの手作業が減る

## 方針（利用者の指示、2026-11-12）

- ここでいう工程は `/ndf:development-workflow` が定めるモードごとの工程を指し、**状態はこのレベルで管理する**
- 進行表で**工程ごとに有効・無効を宣言できる**ようにする（例: 今止めている cross-refactoring を、コードではなく進行表の宣言で止める）
- **スクリプトは進行表に従って次にやるべきことを判断し、その工程が終わったら終了の印を付ける**
- **conductor は異常を検知したら、進行表に従って進捗させるか、進行表自体の状態を変更する**
- **工程ごとに入出力規約が JSON で定められている**
- **開発計画（レーンの配列と、レーンの中のスプリントの順番表の配列）も、同じように進行表と状態で管理する**（利用者 2026-11-12。レーンは開発計画が生成するため）
- **レーンの中のスプリントの順番表の管理は、レーンの conductor が持つ**（利用者 2026-11-12）。順番表は開発計画から分けてレーンの進行表に置く
- **進行表と状態の置き場は、ローカルと Factory で互換のある形にする**（利用者 2026-11-12）。例: RDBMS で管理し、ローカルは SQLite、Factory は PostgreSQL とし、アダプターを切り替えるだけで済む
- **進行表は工程より細かいステップの粒度でも持つ**（利用者 2026-11-12）。工程（`development-workflow` の工程表の行）は利用者が見る進み具合の単位として残し、その中にステップ（実行の単位。DBOS のステップ 1 つ）を持つ。ステップごとに入力（対象の差分の範囲など）と出力の規約を持たせ、ステップの順序の決まりを定義の時点で機械で確かめる。きっかけは、まとめのプランの雛形が「最後の検査（cross-review）」を本番のリリースの後に置き、出し済みの差分をレビューしていたこと（#3126）
- **工程の実行には DBOS を採用し、ワークフローの定義の書式は標準（Serverless Workflow）を借りる**（利用者 2026-11-12 に決定）。定義の書式を自作しない

## 前提

- 前提 1: 工程の実行には DBOS（2026-11-12 の時点で手元にある 3.1.0 の系列）を使い、置き場の URL を `sqlite:///` から PostgreSQL の URL へ替えるだけで同じコードが動く。DBOS の版を上げる必要が出たら、依存の追加として設計承認ゲートで見る
- 前提 2: #3097（開発計画の進行表とレーンの進行表）と #3098（組み換えの工程）は #3092 へ取り込み、3 件を 1 つの要求として設計承認ゲートを通す。実装は スプリントの進行表 → 計画の進行表とレーンの進行表 → 組み換え の順に積み、Pull Request を何本に分けるかは計画（`implementation-plan`）で決める
- 前提 3: 承認ゲートの答えとリリースの結果の待ちに、今の `parallel.py await` の待ち方のほかの上限を足さない
- 前提 4: 組み換えの工程は、工程表で「振り返り」を通るモード（`light` を除く 4 つ）にだけ置く。振り返りを通らないスプリントでは、組み換えの行は「無効（振り返りが無い）」で記録する
- 前提 5: 並列の計画の外の単独の作業でも、その会話の conductor がレーンの conductor の役を持ち、同じスプリントの進行表を使う
- 前提 6: 取り込みの前に #3097・#3098 の本文が持っていた受け入れ条件は、すべて受け入れ条件 13〜21 に写した。#3097・#3098 の本文は書き換えない

## 対象範囲

含む:
- `supervise.py new sprint` が、判定したモードの工程表の全行を進行表の行として組むこと（まとめの工程を含む。`new close` が今組む内容を進行表の最後の行へ入れる）
- 進行表の各工程の状態（未着手・実行中・終了・失敗・無効・中止）と終了の印。印は進行表のワークフローが、工程の出力を入出力規約で検査してから書く
- 工程ごとの有効・無効の宣言（プロジェクトの宣言から既定を受け、スプリントの進行表で上書きできる。計画の単位は未決 2）。`CROSS_REFACTORING_SUSPENDED` と「差分の中身で選ぶ工程」の条件を宣言へ移す
- 進行表を読んで次の工程を返し、流すスクリプト（`queue --resume --from` を conductor が組み立てなくてよくする）
- conductor が進行表の状態を変える操作（工程を無効にする・やり直す・終了にする）と、その記録
- 進捗記録（課題の工程表・スプリント PR の「通した工程」・ボード）を進行表から作ること
- 進行表を RDBMS のスキーマで持ち、DBOS と同じ接続の差し替えで置き場を切り替えること（ローカルは SQLite、Factory は PostgreSQL）。スクリプトは置き場の種類を知らずに読み書きする
- 工程ごとの入出力規約（工程が受け取る入力と、終わったときに返す出力の JSON の形）を `plugins/ndf/contracts/` に定め、進行表の行がそれを参照すること。スクリプトは工程の出力を規約で検査してから終了の印を付け、次の工程の入力を前の工程の出力から作る
- 工程とステップの 2 段と、順序の決まりの検査（章「工程とステップの 2 段と、順序の決まり」）
- 計画の進行表とレーンの進行表（章「開発計画の進行表とレーンの進行表」の行と状態・レーンをまたぐ制約・CRUD・段ごとの書き手）。`parallel.py init`・`start`・`lane add`・`set`・`stop`・`status` を計画の進行表の読み書きへ置き換えること（#3097 から取り込んだ）
- 組み換えの工程（章「組み換えの工程」の置き場・入力・要否の判定・出力・書き手・承認・終わり）と、`development-workflow` の工程表へ「組み換え」の行を足すこと（#3098 から取り込んだ）
- リリースの後に、工程の遷移を進行表のほかで決める Skill の本文・手順書・スクリプトを残さないこと（受け入れ条件 11）

含まない:
- モードの判定基準と工程表の中身そのもの（`development-workflow` の `SKILL.md` が持つ。進行表はそれを読む側）。工程表へ足すのは「組み換え」の行だけ
- 並列の計画の耐久ワークフローの責務のうち、レーンの終わりを観測してラッパーを止める部分（#3058 が持つ）
- 開発ループの選定（`loop select`）の組み直し（#2994）
- DBOS Conductor（商用の管理画面）の導入。ライセンスの判断が要る
- Factory の側の DB と画面の実装（#2608）。この Issue は PostgreSQL の URL で動くことまでを持つ

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | conductor のセッションやプロセスが途中で止まっても、再開は最後に終了の印が付いた工程（ステップ）の次から始まり、終わった工程を流し直さない。進行表のワークフローを動かすプロセスの持ち主は未決 7 |
| 性能・拡張性 | 組み換えの「変更なし」と、次の工程の判断は LLM を起動しない。スプリントは数時間〜数日続き、承認待ちを挟んでも進行表が状態を失わない |
| 運用・保守性 | 進行表の変更（誰が・いつ・何を・理由）は履歴へ追記だけで残し、消さない。進行表の表示は統一 JSON レポートで返す |
| 移行性 | 今の目録 `sprint.json`・進捗記録のファイル・`plan.json`・計画の台帳から進行表への移し方と、実行中のスプリントと計画をどう扱うかは未決 1 で設計が決め、実装の Pull Request の「移行の手順」に書く |
| システム環境 | ローカルでは追加の常駐サーバーを要さず、SQLite で動く。Factory では PostgreSQL の URL で動く。追加する依存は Serverless Workflow の Python の SDK（未決 8）だけを見込む |

## 調べた事実

2026-11-12、手元の DBOS 3.1.0（`~/.cache/ndf/venv/10.27.55` の `dbos` パッケージ）の API を読んで確かめた。

| この Issue の要求 | DBOS が持つもの |
| --- | --- |
| 工程ごとの状態と終了の印 | ワークフローのステップごとに出力かエラー・開始と終了の時刻を記録する（`list_workflow_steps` の `StepInfo`）。ワークフローの状態は `PENDING`・`SUCCESS`・`ERROR`・`CANCELLED`・`ENQUEUED`・`DELAYED`・`MAX_RECOVERY_ATTEMPTS_EXCEEDED` |
| 次にやることの判断・再開 | 落ちても最後に終わったステップの次から自動で再開する |
| conductor が状態を変える | `fork_workflow(id, start_step)`（指定したステップからやり直す）・`cancel_workflow`・`resume_workflow`・`send`／`recv` |
| 進行を外から読む | `set_event`／`get_event`・`list_workflows` |
| ローカルと Factory の互換 | 置き場を URL で受け、SQLite と PostgreSQL に対応（`_datasource_sqlite.py`・`_datasource_postgres.py`）。NDF の耐久ワークフロー（`lib/durable.py`）は `sqlite:///` で使っている |

DBOS に無いもの:
- 工程の並びを定義のデータとして持つこと。DBOS の「登録」は、`@DBOS.workflow()` を付けた関数をプロセスの起動時にメモリの対応表（`_dbos.py` の `workflow_info_map`）へ入れることで、定義を DB や外部へ保管する機能は無い。DB に残るのは実行の記録（ワークフローの名前・入力・ステップごとの出力）とアプリの版（全ワークフロー関数のソースから計算する。`application_version` で固定もできる）で、落ちた後の再開は版が同じコードでだけ行う。登録済みのワークフローの一覧や工程の並びをデータで返す API は無い
- 登録されていない工程。工程の並びはワークフローの定義（コード）が持ち、実行の記録に残るのは実行したステップだけである。残りの工程は、登録した定義と実行の記録を突き合わせれば出せる。出せないのは、実行の途中で定義に無い工程を差し込むことと、実行中に並びを変えること（新しい版の定義で途中から始め直す扱いになる）
- 工程ごとの有効・無効の宣言
- 工程の入出力の JSON 規約。ステップの出力は既定で pickle を base64 にして保存する（`_serialization.py`）
- 実行中の進行表の書き換え。ワークフローは再実行のとき同じ順でステップを通る前提のため、進行表と宣言はステップの中で読むか、`fork_workflow` で新しい実行として始める。コードの変更は `patched` に乗せる

DBOS の周辺の進行管理のツール（2026-11-12 に調べた）:

| ツール | 提供の形 | 持つもの |
| --- | --- | --- |
| DBOS Transact の CLI（`dbos workflow list`・`get`・`steps`・`cancel`・`resume`・`fork`）と `DBOSClient` | オープンソース。手元に入っている | 実行したワークフローとステップの一覧・状態・出力、取り消し・再開・指定したステップからのやり直し |
| DBOS Conductor（ https://docs.dbos.dev/production/hosting-conductor ） | 商用。自前で動かすにはライセンスキーが要る。手元のパッケージには接続部（`dbos/_conductor/`）だけがある | 管理画面（取り消し・再開・やり直し・キューの管理）、ステップのタイムラインの表示、失敗したところからのやり直し（`fork_from_failure`）、巻き戻し（`rewind_workflow`）、通知、保持期間、集計 |

どちらも「実行したワークフロー」を見て操作するもので、工程の並びは登録したワークフローの定義が持つ。工程ごとの有効無効・入出力規約の検査・計画とレーンの段は持たない。操作と実行の記録の参照は CLI と `DBOSClient` を使い、定義の登録・有効無効・入出力規約・計画とレーンのデータは NDF が足す（「直し方の案」の線引きと同じ）。Conductor を Factory の運用の画面に使うかは、ライセンスの判断が要るため、この Issue では決めない。

定義を登録して実行する形のワークフローツール（2026-11-12 に調べた。DBOS に対応したものは見つからなかった。DBOS は公式の資料で、ワークフローをコードで書く作りに限られる）:

| ツール | 定義と置き場 | NDF に載せる重さ | 確かめた範囲 |
| --- | --- | --- | --- |
| Conductor（オープンソース。商用版は Orkes） | JSON の定義を API でサーバーへ登録し DB に置く。条件分岐・繰り返し・飛ばし・途中からのやり直し・未実行の工程の表示 | Java のサーバーと DB が要る | JSON・YAML の定義は一覧で確認。保管と機能の詳細は未確認 |
| Kestra | YAML の定義を DB に置く | Java のサーバーが要る | 保管の詳細は未確認 |
| Hatchet | SDK で書いた DAG を起動時にエンジンへ登録し PostgreSQL に置く | Go のエンジンと PostgreSQL が要る | 未確認 |
| Apache Airflow | Python で DAG を書き、構造を DB に置く | スケジューラと DB が要る | 確認 |
| Dagu | YAML の DAG | 単体のバイナリ | 確認 |
| n8n | JSON の定義を PostgreSQL か SQLite に置く | Node.js のサーバーが要る | 一覧で確認 |
| Serverless Workflow（CNCF の仕様。エンジンではなく定義の書式） | JSON・YAML の定義。Python の SDK（PyPI の `serverlessworkflow.sdk`、 https://github.com/serverlessworkflow/sdk-python ）で読み込みと検証ができる | ライブラリだけ | SDK が対応する仕様は 0.8。1.0 の書式への対応は未確認 |

実行エンジンの候補は、どれも別のサーバーと DB を常に動かす必要があり、利用者の手元で動くプラグインに載せるには重い。DBOS はライブラリとしてプロセスの中で動き、SQLite と PostgreSQL の両方に対応する。

## 直し方の案

決定ではない。設計で確かめる。後の「進行表の CRUD」「開発計画の進行表とレーンの進行表」「組み換えの工程」の 3 章も、この案の中身であり、設計承認ゲートで確かめる。**「進行表の CRUD」の章は、スプリントの進行表を NDF の表として書く前提で書いてある。下の採る案（登録した定義と DBOS の実行の記録で状態を持つ）に合わせ、設計で読み替える**（「進行表を作る」は「登録した定義を選んでジョブを実行する」、「進行表へ書く」は「DBOS の実行の記録に残る」にあたる）。

- 採る案（実行に DBOS を使うことと、定義の書式に標準を借りることは決定済み。ほかは設計で確かめる）: `development-workflow` のモードごとの工程の並び（モードは 5 つで、進め方を掛けても組み合わせは限られる）を、**あらかじめ NDF の定義のデータへ登録**する（DBOS には定義を保管する機能が無いため、登録先は NDF の側。置き場は `plugins/ndf/contracts/` の JSON などで設計が決める）。定義のデータはモード → 工程の並びと各工程の入出力の型を持ち、DBOS の側には定義のデータを読んで工程を 1 つずつステップとして流す汎用のワークフロー関数を 1 つだけ置く。表示（Factory・`status`）も同じ定義のデータを読む。スプリントは、登録した定義を選び、課題と有効・無効の宣言を引数にした **1 つのジョブ**（DBOS のワークフロー 1 本）として実行する。工程はステップ（か子のワークフロー）1 つにする
  - **決定（利用者 2026-11-12）**: 定義の書式は自作せず、標準の Serverless Workflow を借りる。Python の SDK で読み込み・検証し、DBOS の汎用のワークフロー関数が解釈する。使う範囲と仕様の版は未決 8
  0. スプリントを始める時点で使う定義（モードの工程の並びと定義の版）を、ワークフローの入力として渡す。入力は実行の記録に残るため、後で定義のデータを変えても、動いているスプリントは始めたときの定義のまま進み、再開もずれない。実行の途中で定義のデータを読み直さない
  1. 状態の正本は DBOS の実行の記録とする。残りの工程は、入力に残った定義と実行の記録の突き合わせで出す。NDF 独自の状態の表は持たない見込み（未決 5）
  2. 有効・無効は実行の引数で渡し、ワークフローが無効の工程を「無効（理由）」のステップとして記録して飛ばす
  3. 入出力規約は、登録した工程ごとの入力と出力の型から JSON のスキーマを作り、工程の境で検査する
  4. 登録の外の操作（定義に無い工程の差し込み・実行中の並びの変更・モードの引き上げ）は、新しい版の定義で途中から始め直す（`fork_workflow` と版の切り替え）。conductor が異常のときに打つ
  5. 計画とレーンの段（どのレーンでどのスプリントを順に流すか）は計画ごとに変わるデータのため、登録する定義ではなく、親のワークフローが各スプリントの境で読むデータとして持つ
- 採る案の続き: `supervise.py queue` の再開（`--resume --from`）の大部分を DBOS へ置き換える
- 採らない案: 工程の実行と再開の仕組み（ステップの記録・落ちた後の回復・置き場の切り替え）を NDF が自作する。DBOS が持つものを作り直すことになる（基盤は既存のライブラリを使う方針）。進行表は DBOS と同じ接続（URL）で読み書きし、置き場の切り替えも DBOS と同じ URL の差し替えで済ませる

## 進行表の CRUD: 主体・作成・参照

前提: **進行表はスプリントに 1 つ**（進行表 1 つ ＝ スプリント 1 つ ＝ DBOS のワークフロー 1 本）。工程 1 つ ＝ ステップ（か子のワークフロー）1 つ（「直し方の案」）。開発ループのループの 1 回は 1 スプリントにあたり、進行表 1 つを持つ。`pace: fast` の課題ごとの Pull Request は、スプリントの進行表の中の課題ごとの行として持つ（行の持ち方は未決 3）。

状態: 工程の状態は **未着手・実行中・終了・失敗・無効・中止** の 6 つ、進行表全体の状態は **実行中・完了・中止** の 3 つとする。

### 登場する主体

| 主体 | 進行表に対して持つ権限 |
| --- | --- |
| 進行表のスクリプト（`supervise.py` の進行表の副命令。名前は設計で決める） | レーンの conductor が作成と更新に使うツールで、参照の受け口。進行表へ書けるのはこのスクリプトと、進行表のワークフローだけ。自分からは進行表を作らない |
| 進行表のワークフロー（DBOS） | 工程の状態の遷移と終了の印。工程のプランを流し、出力を入出力規約で検査する |
| レーンの conductor（1 スプリントのレーン・開発ループのレーン・単独の conductor） | **進行表の作成者（原則）。** 異常のときの更新（無効にする・やり直す・手で終了にする・範囲を変える・中止）も持つ |
| オーガナイザー | 承認ゲートの答えとリリースの結果を、進行表のワークフローへ送る（`send`）。進行表の工程の状態は直接書かない |
| 耐久ワークフロー（`parallel.py run`） | 進行表の終わりを読み、レーンを止める（#3058）。進行表は書かない |
| 人・Factory の画面 | 参照だけ。変えるときは conductor の操作を通す |

### C: 作成

| 項目 | 決まり |
| --- | --- |
| いつ | スプリントの課題が決まり、要求と受け入れ条件とモードの判定が済んだ直後（工程の順序「要求と受け入れ条件 → モード判定 → 作業場所の用意」の、作業場所の用意の前）。開発ループでは、ループの 1 回の課題を選んだ直後 |
| 誰が | **原則としてレーンの conductor**（進行表はスプリントに 1 つで、スプリントを持つのはレーンのため）。conductor が進行表のスクリプトを打つ（今の `supervise.py new sprint` の位置）。開発ループのレーンも、そのレーンの conductor が選定の後に打つ。オーガナイザー・耐久ワークフロー・スクリプトは自分から進行表を作らない。並列の計画の外の単独の作業では、その会話の conductor がレーンの conductor の役を持つ |
| どのように | (1) モードの工程表（`development-workflow` の工程表を機械で読める形にした定義。置き場は `plugins/ndf/contracts/`）から、モードの全工程を行として作る (2) 各行に入出力規約の参照を付ける (3) 有効・無効の宣言を、プロジェクトの既定 → スプリントの順に重ねて各行へ書き（計画の単位を挟むかは未決 2）、無効の行は理由を持つ (4) 要求と受け入れ条件・モード判定の行は、その時点で終了の印を付けて作る（出力は要求の文書とモード判定の結果） (5) 進行表は自分の ID を持ち、進行表のワークフローを起動して、その ID を「今の実行」として記録する（やり直しで実行が替わっても進行表の ID は変わらない） |
| 1 つだけ | 同じスプリントの進行表は 1 つ。同じ名前で 2 つ目を作ろうとしたら断り、今の進行表の ID を返す |

### R: 参照

| 誰が | 何を読むか | 手段 |
| --- | --- | --- |
| 進行表のワークフロー | 次の工程（未着手で有効な最初の行）と、その入力（前の工程の出力） | 進行表 |
| conductor・オーガナイザー・人 | 工程ごとの状態・終了の時刻・出力の要約・無効の理由・変更の履歴 | 進行表のスクリプトの表示の副命令（統一 JSON レポートで返す）。Factory は同じ DB を読む |
| 耐久ワークフロー | 進行表が終わったか（終了・中止） | 進行表の状態 |
| 進捗記録（課題の工程表・スプリント PR の「通した工程」・ボード） | 終了の印 | 進行表から作る。手で書かない（受け入れ条件 6） |

## 進行表の CRUD: 更新・終了

### U: 更新

| 何を | いつ | 誰が | どのように |
| --- | --- | --- | --- |
| 工程の状態（未着手 → 実行中 → 終了／失敗） | 工程の開始と終了 | 進行表のワークフローだけ | 開始で「実行中」。出力が入出力規約に合えば「終了」と終了の印、合わなければ「失敗」にして conductor へ返す |
| 承認ゲートの答え・リリースの結果 | 人が答えたとき・まとめたリリースを締めたとき | オーガナイザーが送り、進行表のワークフローが書く | `send` で答えを送り、待っていたゲートの工程が受け取って終了にする（今の `parallel.py await` を置き換える） |
| 有効・無効 | 工程の開始の前ならいつでも | conductor | 進行表のスクリプトで理由つきで変える。実行中の工程は変えられない（先にやり直しか中止をする） |
| やり直し | 工程が失敗したとき・出力を直したいとき | conductor | 進行表のスクリプトがその工程から `fork_workflow` で新しい実行を始め、前の実行を取り消す。進行表の「今の実行」を新しいワークフローの ID に替え、前の実行は履歴に残す。進行表の ID は変えない |
| 手で終了にする | 工程を手で行ったとき（手で届けるリリースなど） | conductor | 出力のファイルを渡し、進行表のスクリプトが入出力規約で検査してから終了の印を付ける。規約に合わなければ断る |
| 範囲（課題の追加・外し）とモードの引き上げ | 設計承認ゲートで課題を外したとき・モードを上げたとき | conductor | 進行表のスクリプトが進行表の版を上げ、影響する工程から後をやり直しとして始める。モードは上げる方向だけ（下げたいときは新しい進行表） |
| 変更の履歴 | 上のすべて | 進行表のスクリプト | 誰が・いつ・何を・理由を、進行表の履歴へ追記する。消さない |

### D: 終了

| 終わり方 | いつ | 誰が | どのように |
| --- | --- | --- | --- |
| 完了 | 有効な最後の工程が終わったとき | 進行表のワークフロー | 最後の工程の終了で進行表の状態を「完了」にし、ワークフローが `SUCCESS` で終わる。保留した受け入れ条件がある課題は開いたまま残し、保留の一覧を出力に載せる（#2330 が拾う） |
| 中止 | 設計承認ゲートで「やらない」・計画から外す・放棄 | conductor（オーガナイザーの指示を含む） | 進行表のスクリプトが理由つきで「中止」にし、残りの工程を「中止」で閉じてワークフローを取り消す（`cancel_workflow`） |
| レーンの終わり | 進行表が完了か中止になったとき | 耐久ワークフロー | 進行表の状態を読んでレーンのラッパーを止める（#3058）。止められなければオーガナイザーへ返す |
| 物理的な削除 | しない | — | 進行表と履歴は消さない（振り返り・計測・Factory の画面が読む）。置き場の寿命は #2606 の「永続」に置く |

## 開発計画の進行表とレーンの進行表

#3097 https://github.com/devbasex/ai-plugins/issues/3097 から取り込んだ範囲である（受け入れ条件 13〜17）。

レーンは開発計画が生成する。このため、スプリントの進行表と同じ考え方で、開発計画とレーンにも進行表と状態を持たせる。**レーンの中のスプリントの順番表は、開発計画から分けてレーンの進行表に置き、レーンの conductor が持つ**（利用者 2026-11-12）。進行表は 3 段になる。

```text
計画の進行表（計画 1 つ。オーガナイザーが持つ）
├─ レーン A ─ レーンの進行表 A（レーン A の conductor が持つ）: [スプリント A1, スプリント A2, ...]
│                └─ スプリント A1 ─ スプリントの進行表（工程の行。上の「進行表の CRUD」）
└─ レーン B ─ レーンの進行表 B: [スプリント B1, ...]（after: レーン A のスプリント A1）
```

**今どうなっているか**: 計画は 3 か所に分かれる。`plan.json`（レーンの配列）・計画の台帳（`ledger.jsonl`・`checkpoint.json`）・耐久ワークフローの DBOS の記録である。`plan.json` のレーンは、`input` に 1 スプリント（`{"kind": "sprint", "issues": [...]}`）か開発ループ 1 つを持つ。レーンの中にスプリントの順番表は無く、外した課題を次のスプリントで流すときは `after` 付きの新しいレーンを足している（計画 p5 のレーン lcost の残りを、レーン lcost2 で流した）。レーンの状態はリレーハブのラッパーの状態から推し、スプリントの終わりは記録に無い（#3058）

**レーンの conductor に持たせる理由**:
- 順番表を変える材料（外した課題・スプリントの中で起票した課題・振り返りの結果）は、そのレーンのスプリントから出る
- 開発ループのレーンは、すでに自分で次のスプリントを選んでいる（`loop select`）。1 スプリントのレーンの順番表は、その選定をあらかじめ並べたものにあたり、持ち主をそろえると 2 種類のレーンを同じ形で扱える
- 書き手が段ごとに 1 つに寄る（計画の進行表はオーガナイザー、レーンの進行表とスプリントの進行表はレーンの側）

### 行と状態

| 段 | 行 | 状態 | 持ち主 |
| --- | --- | --- | --- |
| 計画の進行表 | 計画 1 つと、レーンの配列（触る場所の見込み・プランの本数・レーンをまたぐ `after`）・規則・同時に動くレーンの上限 | 計画: 未着手・実行中・完了・中止。レーンの状態は持たず、レーンの進行表から出す | オーガナイザー |
| レーンの進行表 | スプリントの順番表（行はスプリント 1 つ: 課題かタスクの一覧・順番。#3081 のタスクを単位にできる） | 行: 未着手・実行中（スプリントの進行表の ID を持つ）・完了・中止。実行中から後はスプリントの進行表の状態を写す | レーンの conductor |
| スプリントの進行表 | 工程の行 | 上の「進行表の CRUD」 | レーンの conductor |

### レーンをまたぐ制約

レーンの進行表はレーンの conductor が書くが、次の 3 つは計画の進行表が持つ決まりで守る。

| 制約 | 守り方 |
| --- | --- |
| 別のレーンとの触る場所の重なり | レーンの進行表への書き込みは、レーンの進行表のスクリプトが計画の進行表の決まりで検査してから書く。オーガナイザーの操作は要らない |
| 別のレーンの `after` が指す行 | その行は消せず、後ろへも回せない。変えたいときはオーガナイザーへの依頼になる |
| 同時に動く本数の上限 | 耐久ワークフローが起動の時点で守る |

### CRUD

| 操作 | 対象 | いつ | 誰が | どのように |
| --- | --- | --- | --- | --- |
| C | 計画の進行表と、各レーンの最初の順番表 | 開発計画を立てたとき（`issue-plan-strategy` の parallel-plan の手順の終わり） | オーガナイザー | 計画の進行表のスクリプト（今の `parallel.py init`・`start` の位置）が、レーンの配列と各レーンのレーンの進行表（最初の順番表。今の `input` にあたる）を作り、検査（触る場所の重なり・上限・`after` の輪）を通してから耐久ワークフローを起動する。作った後のレーンの進行表の持ち主はレーンの conductor になる。スプリントの行は「未着手」で作り、スプリントの進行表はまだ作らない |
| R | 両方 | いつでも | 耐久ワークフロー・オーガナイザー・レーンの conductor・人・Factory | 耐久ワークフローは計画の進行表とレーンの進行表を読み、起動できるスプリント（`after` が満たされた未着手の行）を決める。`parallel.py status` は 2 つの進行表から作る |
| U: スプリントの開始 | レーンの進行表 | レーンの conductor がスプリントの進行表を作ったとき | レーンの conductor | スプリントの進行表を作る操作が、レーンの進行表のその行へ進行表の ID を書き「実行中」にする |
| U: スプリントの終わり | レーンの進行表 | スプリントの進行表が完了か中止になったとき | スプリントの進行表のワークフロー | レーンの進行表の行を「完了」「中止」にする。次の行があれば耐久ワークフローが同じレーンで次のスプリントを始めさせ、無ければレーンを止める（#3058） |
| U: レーンの中の組み換え | レーンの進行表 | 組み換えの工程の変更案・設計承認ゲートで外した課題の持ち越し | レーンの conductor（組み換えの工程を含む） | レーンの進行表のスクリプトが「レーンをまたぐ制約」の検査を通してから書き、変更の履歴を残す。外した課題は同じレーンの順番表の次の行へ足す（`after` 付きの新しいレーンを作らない）。実行中と完了の行は書き換えられない |
| U: レーンをまたぐ変更 | 計画の進行表 | レーンを足す・課題を別のレーンへ移す・`after` を変える・上限を変えるとき（利用者の指示・レーンの側からの依頼） | オーガナイザー | 計画の進行表のスクリプト（今の `parallel.py lane add`・`set`）が検査を通してから書く。移す先のレーンの進行表へは、そのレーンの進行表のスクリプトを通して行を足す |
| U: 承認とリリース | — | 承認ゲートの答え・まとめたリリースの結果 | オーガナイザー | 計画の進行表もレーンの進行表も書かず、スプリントの進行表のワークフローへ送る（上の「進行表の CRUD」の U） |
| D: 完了 | 計画の進行表 | 全レーンの進行表の行が完了か中止になり、答えていない依頼が無いとき | 耐久ワークフロー | 計画の進行表を「完了」にし、`wait` が `finished` を返す。オーガナイザーが `[ndf-parallel] finished <計画>` を出す |
| D: 中止 | 計画の進行表 | 計画を放棄するとき | オーガナイザー | 計画の進行表のスクリプト（今の `parallel.py stop`）が理由つきで「中止」にし、各レーンの進行表の未着手の行を中止にして、実行中のスプリントの進行表へ中止を送る |
| D: 物理的な削除 | — | しない | — | スプリントの進行表と同じく履歴として残す |

**段ごとの書き手**: 計画の進行表へ書くのは計画の進行表のスクリプトだけで、呼ぶのはオーガナイザー（作成・レーンをまたぐ変更・中止）と耐久ワークフロー（完了）に限る。レーンの進行表へ書くのはレーンの進行表のスクリプトだけで、呼ぶのはレーンの conductor（スプリントの開始・レーンの中の組み換え）、スプリントの進行表のワークフロー（スプリントの終わり）と、作成のときのオーガナイザー・レーンをまたぐ移動のときのオーガナイザーに限る。工程の状態はスプリントの進行表だけが持つ。

## 組み換えの工程

#3098 https://github.com/devbasex/ai-plugins/issues/3098 から取り込んだ範囲である（受け入れ条件 18〜21。置く位置は未決 6）。

スプリントのまとめの「振り返り」の後に、**必要に応じて次以降のスプリントを組み換える工程**（工程名は「組み換え」。`development-workflow` の工程表へ行を足す）を置く。スプリントで分かったことを、終わった時点で計画へ戻すためである。今は、外した課題やスプリントの中で起票した課題を次へ回すのも手作業である。オーガナイザーが会話の中で `parallel.py lane add`・`set` を打っている（計画 p5 のレーン lcost2・lgate・lci・ltask）。

| 項目 | 決まり |
| --- | --- |
| 置き場 | スプリントの進行表の工程。まとめの中で「振り返り」の直後 |
| 入力 | 振り返りの出力（進め方の見直し・拾った起票）・設計承認ゲートで外した課題・リリース後テストで保留にした受け入れ条件・スプリントの中で起票した課題・計画の進行表の自分のレーンと他のレーンの未着手の行（触る場所の見込みを含む） |
| 要否の判定 | 入力に「次へ回す課題」「順番や組を変える理由（触る場所の重なり・依存・優先の変化）」が 1 つも無ければ、スクリプトが「変更なし」を出力して終了の印を付ける（LLM を起動しない） |
| 出力 | レーンの進行表への変更案と、レーンをまたぐ変更の依頼（JSON。行の追加・順番の入れ替え・課題の移動・行の取り消しと、それぞれの理由）。入出力規約で検査する |
| 誰が案を作るか | スプリントの進行表のワークフロー（その工程のプラン）。レーンの conductor は異常のときだけ関わる |
| 誰が進行表へ書くか | 自分のレーンの中の変更は、レーンの進行表のスクリプト（「開発計画の進行表とレーンの進行表」の「U: レーンの中の組み換え」）。工程が変更案をスクリプトへ送り、スクリプトが「レーンをまたぐ制約」の検査を通したものを書く。オーガナイザーの操作は要らない。レーンをまたぐ変更（別のレーンへ課題を移す・レーンを足す）は、オーガナイザーへの依頼として出す。検査で断られた案は理由つきでオーガナイザーへ返す |
| 承認 | 承認ゲートを足さない。新しいスプリントは、それ自身の設計承認ゲートを通る。計画から課題を外す（やらない）案だけは、棚卸しの「やらない」と同じく AI が決めて記録する |
| 終わり | 変更案が計画の進行表に反映されたか、「変更なし」か、断られた理由が記録された時点で終了の印を付ける |

## 工程とステップの 2 段と、順序の決まり

| 段 | 持つもの | 例 |
| --- | --- | --- |
| 工程 | `development-workflow` の工程表の行。利用者が見る進み具合の単位 | コードレビュー・デプロイ・確定仕様化 |
| ステップ | 工程の中の実行の単位（DBOS のステップ 1 つ）。ステップごとに入力（対象の差分の範囲など）と出力の規約を持つ | cross-review を回す・全体テスト・PR のマージ・本番の PR・タグ・確定仕様化の PR |

登録する定義に、次の順序の決まり（不変条件）を持たせ、定義を登録するときと実行の前に検査する。破る定義は登録できない。

| 決まり | 弾ける誤り |
| --- | --- |
| 同じ差分の範囲について、レビューとテストのステップは本番へ出すステップより前にある | リリースの後にレビューする（2026-11-12 のレーン lci のまとめの最後の検査。#3126） |
| レビューとテストのステップの入力の範囲は、その進行表（そのスプリント）の差分に限る | 範囲がベースブランチ全部になり、ほかのレーンの変更とレビュー済みの差分をレビューし直す（#3126） |
| 一度通したステップを同じ範囲で 2 度通さない。やり直しは conductor の操作として記録する | レビュー済みの差分を別の工程でもう一度レビューする |
