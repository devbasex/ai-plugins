# #933: cross-refactoring を想定最大時間に収める 1 回の計画実行へ改める — 決定の記録

要求は [issue-933-requirements.md](issue-933-requirements.md)、設計は [issue-933-design.md](issue-933-design.md) にある。

**関門で決めるのは決定 1〜3 である。** 残りは設計の中で決めた。

## 決定の記録

### 決定 1: 計画以降の実装担当は、名指し → ホスト → 参加者の先頭の順で 1 者に決める。輪番は廃止する（関門で最終決定）

#933 は「選ばれた 1 ランタイムが通す」と定め、選び方を設計に委ねた。#917 では、群の 1 件あたりの適用が claude 36〜66 秒・codex 102〜125 秒・kiro 120〜216 秒だった。既定のホストは claude が多く、ホストを既定にすれば速い者が選ばれやすい。決め方が状態に依らないため、再開しても変わらない。

実行ごとに輪番で回す案は採らない。時間の上限の中で遅い者に当たる回が生じ、所要がばらつく。履歴の中で最も速い者を選ぶ案も採らない。完了した履歴は #917 の 1 件しか無く、1 度選ばれなかった者の標本が増えない。

### 決定 2: Jev は判断の主として使い、公開リポジトリに限る（関門で最終決定）

#933 は「Jev を使える箇所はできるだけ使う」と定める。#841 は、`claude -p` を正として Jev との一致率を記録する形（Shadow Mode）から入る方針である。この課題は利用者の指示に従い、**Jev の答えを主に使う。** ただし答えごとに確信度の下限を置き、下回ったら実装担当の答えを使う。実装担当は計画と実装の結果で同じ判断（段・重複・`risk`）を必ず返すため、Jev が失敗しても答えが欠けない。

**公開リポジトリに限る。** 送った中身は Vercel と TypeSafe を通り、#841 は規約を確かめるまで顧客のリポジトリで使わないと定めている。ファイルの本文は送らない。

Shadow Mode で入れる案は採らない。判断が実装担当のままで、#933 の指示に届かない。非公開のリポジトリでも使う案は、#841 の規約の確認が終わるまで採らない。

### 決定 3: #754 は #933 の実装のマージで閉じ、#755 は前提が無くなったとして「やらない」で閉じる（関門で最終決定）

#754 の方針 1〜3（枠の持ち越し・採用上限・ラウンドの上限）は、ラウンドと採用上限が無くなると対象が消える。指針の「60 分以内」はこの課題の `--budget-minutes` の既定が持つ。#755 は、群の中のファイルが重ならない項目を複数の担当で並列に適用する課題で、「実装は 1 者」と衝突する。

#755 を「計画の中のファイルが重ならない束を並列に」と読み替えて残す案は採らない。1 者が通す前提と両立せず、再び並列を入れるなら、この課題の結果を測ってから新しく起票するほうがよい。課題の本文の書き換えと閉じる操作は、関門の答えを受けてから行う。

### 決定 4: 引数は `--budget-minutes`（既定 30）とし、目安の上限として扱う（「実行中の CLI を止めない」は決定 23 で改めた）

**既定は 30 分とする（2026-09-24 利用者の指示。関門 1 の承認時は 60 分）。** 設計の見積り（#917 と同じ範囲で `--budget-minutes 60` を渡した場合）は、引数を明示した例として残す。

**「実行中の CLI を止めない」と監視の上限の表の扱いは決定 23・24 で改めた。** 今は段の終わり + 余裕で監視が止め、表の固定値は使わない。

分の整数にするのは、#933 と #754 が分で語っているためである。**実行中の CLI を時間切れで止めない。** 止めると作業ディレクトリに半端な変更が残り、取り消しの手順が増える。代わりに、計画で見積りを収め、実装の中は項目ごとの締め切りで着手を止める。監視の上限（`limits.py`）は、止まらない CLI への歯止めとして残す。

#754 の `--time-budget-min` の名前は採らない。単位を名前の末尾に置くほうが、既存の `--test-timeout`（秒）と並べたときに読み違えにくい。

### 決定 5: ラウンド制の引数は、この変更を含む版では知らせて無視し、その次の版で外す

廃止する 3 つ（`--max-test-rounds` / `--max-outer-rounds` / `--max-items-per-round`）は、呼び出し元の文書が使っていない。`development-workflow` を含めて `grep` で 0 件だった。利用者の手元の手順に残っている場合に備え、この変更を含む版では止めずに知らせる。`--max-fix-rounds` は「項目あたり」として残す。修正の上限は項目の単位の取り消しと対になる（決定 24 で `--max-fix-rounds` と `--test-timeout` も廃止へ加えた）。

受け取ったら止める案は採らない。版を上げただけで利用者の手順が壊れる。

### 決定 6: 配分テーブルの種類は `test` と `structure/<technique>` にする

見積りは「何をするか」で決まり、手法（`technique`）がそれを表す。兆候（`smell`）は「なぜ直すか」で、同じ兆候でも手法で手数が変わる（#917 の `long_method` は `extract_method` と `split_into_pipeline` に分かれた）。テストの追加は経路の種類（`case`）で分けない。#917 の 10 件を 4 つに分けると 1 種類 1〜5 件になり、1 件あたりの値が定まらない。

標本が無い手法は `structure/*` をまとめた値へ、それも無ければ初期値へ落とす。

### 決定 7: 配分テーブルは保存せず、利用者の手元の履歴から計画のたびに集計する

履歴は実行の要約と同じ根（`run_metrics.metrics_dir()`）の下に、リポジトリごとの JSONL で置く。テストの所要はリポジトリで大きく違うため、リポジトリを混ぜると見積りが外れる。集計した表を別に保存すると、履歴と表が食い違う。

リポジトリの中のファイルに置く案は採らない。対象のリポジトリに cross-refactoring の都合のコミットが混ざる。状態ファイルの中に置く案も採らない。状態ファイルは Pull Request ごとで、次の実行へ渡らない。

### 決定 8: 所要は進行側の時計とコミットの時刻で測り、担当の申告を使わない

#917 では、担当の申告（`durations.apply`）と監視の実測が食い違った（申告 1420 秒・実測 1081 秒、申告 300 秒・実測 616 秒）。フェーズは進行側が開始と終了を書き、項目は前のコミットから自分のコミットまでの時刻の差で測る。1 項目 = 1 コミットにする（決定 12）ことで、項目ごとの所要が git から出る。

### 決定 9: 初期値は #917 の適用の実測を件数で割った値にする

#933 が示した 1 件あたり（テスト 3.6 分・構造改善 2.3 分）は、提案と採否の時間を含む。新しい形では提案と計画を別に測り、経過として差し引くため、項目の見積りに含めると二重に数える。そこで適用の CLI の実測だけを使う（テスト 2.7 分・構造改善 1.3 分）。修正は #917 で 0 回だったため、構造改善の群の適用の中央値（5.5 分）で代え、未確認として残す。

### 決定 10: 件数は、順位の順に入る項目を入れ、入らない項目を飛ばして詰める

順位の上から入らなくなった時点で打ち切ると、大きな項目 1 件の後ろの小さな項目が入らず、時間が余る。飛ばして詰めても、順位の高い項目が先に着手される順序は変わらない。最適な組み合わせを解く案は採らない。見積りの誤差の方が、組み合わせの最適化で得る差より大きい。

### 決定 11: 順位は（段、賛同した者の数、重要度）で決め、段を Jev または実装担当が付ける

数え上げと比較はスクリプトが行う。Jev は数え上げと計算が不得意で、段（高・中・低）の判断は得意である（#841）。実装担当は計画の中で全件に段を付けるため、Jev の確信度が足りない項目にも段がある。

参加者の投票で順位を決める案は採らない。提案の後にもう 1 度、全員の CLI を起動することになり、計画の前の時間が倍になる。

### 決定 12: 実装は 1 回の起動で順位の順に行い、1 項目 = 1 コミットにする。着手は項目ごとの締め切りで止める

項目ごとに起動すると、起動ごとに文脈を読み直し、トークンと時間が項目の数だけ増える。このまとまり（17 トークン消費の削減）の目的に反する。1 回の起動の中で項目ごとにコミットすれば、所要の測定と項目の単位の取り消しが git から行える。

今の「群 = 1 コミット」は採らない。群は複数の担当と並列を前提にした単位で、1 者が順に適用するなら分ける理由が無い。`CLAUDE.md` の cross-refactoring の節が既に「1 改善項目 = 1 コミット」と書いており、実装（群 = 1 コミット）と食い違っていた。この決定で実装を記述に合わせる。

### 決定 13: テストの追加は、計画が項目に紐づけたテストだけにし、足したテストが今のコードで落ちた項目は見送る

現状固定テストは、今のコードで通って初めて、構造改善の後の振る舞いの比較の基準になる。落ちるテストを直して通すと、テストの側に振る舞いの前提が入る。項目ごと見送れば、他の項目は進められる。

**見送った項目のテストのコミットは取り消す。** 落ちるテストが HEAD に残ると、限ったテスト・全体のテスト・最終ゲートがすべて落ちる。締め切りで着手されなかった項目（`not_done`）のテストも取り消す。通るテストではあるが、この Pull Request が直す項目の検証に使われず、「採った項目に要るテストだけ」から外れる。

### 決定 14: 検証は HEAD で項目ごとの限ったテストを走らせる。全体のテストは危険の印が立ったときに 1 度だけ走らせる

項目のコミットを 1 つずつ取り出して試す案は採らない。後の項目が前の項目の上に積まれるため、HEAD で通ることが Pull Request に残る条件である。

危険の印は、限ったテストで覆えない変更を git の事実で表したもの（D1〜D4）と、公開の入出力の判断（D5）である。D4 は覆っていると示せないときに立てる。D3 の見落としは残る危険として受け入れる（決定 20）。D5 は Jev が使えなければ実装担当の `risk` を使うが、**印を立てる側にだけ使う。** 申告で検証を減らさない。

### 決定 15: 危険の印の全体のテストが落ちたら、印を持つ項目を取り消し、検証の中では走らせ直さない。取り消した後の HEAD は最終ゲートが全体のテストで確かめる（決定 22 で改めた）

**落ちたときの扱いは決定 22 で改めた。** 落ちたテストを取り出せないときだけ、この決定のとおりまとめて取り消す。検証の中で全体のテストを走らせ直さないこと・二分探索を採らないことは決定 22 でも保つ。

検証の中で走らせ直すと、検証の中の全体のテストが 2 回になる。取り消した後の HEAD は最終ゲートで確かめる。単独起動の最終ゲートは、今（#880）と同じく `cross-review` の前に全体のテストを 1 度走らせる（`--ci-check` があれば継続的統合が確かめる）。検証の中で通った後に取り消しが無く HEAD が進んでいなければ使い回す（決定 16）。この 1 回は控え（`final_whole_test`）として時間に入れる。どの項目が壊したかを二分探索で特定する案は採らない。全体のテストを何度も走らせることになる。

### 決定 16: 最終ゲートの全体のテストは、検証の中で通った後に HEAD が進んでいなければ、その結果を使い回す

工程の 1 つとして起動し `--ci-check` が無いとき、最終ゲートは全体のテストである。検証の中で通った後に HEAD が 1 つも進んでいなければ、同じ結果になる。走らせ直さない。生成物の同期のコミットが積まれていれば、そのコミットはまだ全体のテストを通っていないため走らせる。

着手前の全体のテスト（`init`）は残す。壊したのか元から壊れていたのかを区別する唯一の材料で、#917 では 59 秒だった。

### 決定 17: 提案は観点を並べて観点ごとに探させ、合計の件数の上限を示さない。計画へ渡す候補は 30 組（組の中の上位 3 件、最大 90 件）までにする

「多面的に」を雛形で観点の一覧として示す。一覧が無いと、参加者は目についた兆候（#917 では `long_method` が 10 件）に偏る。合計の上限を示すと、今の採用上限のように、出す前に絞られる。

計画へ渡す候補は、統合の後に（賛同した者の数、重要度）で並べ、`path` + `symbol` の組の単位で上位 30 組にし、組の中は上位 3 件まで渡す（最大 90 件）。計画の入力と Jev の呼び出しの数を抑えるためである。外れた候補は `rank` の理由で見送る。件数で 30 件を切ると、意味の上で同じ提案が枠を占め、計画の中で統合された後に空いた枠を埋められない。「同じ変更か」は同じ組の中でしか問わないため、組の単位で切れば統合で組の数は減らない。

### 決定 18: 旧い形の状態ファイルは読み替えずに止める

ラウンドと群の途中の状態を 5 フェーズへ読み替えると、どのコミットがどの項目かの対応を作り直すことになる。旧い形で途中まで進んだ実行は、旧い版で終えるか、始め直す。

### 決定 19: クラス図を作らない

`refactor_lib` は関数の集まりで、型を定義していない。状態は辞書として状態ファイルに持つ。変更が触る型が無いため、クラス図の対象が無い。代わりに状態ファイルの形（データ構造）と項目の状態遷移図を書いた。

### 決定 20: D3 と D4 は名前の一致で判定する。D4 は示せないときに立て、D3 の見落としは残る危険として受け入れる。言語ごとの参照の解決は持たない

`refactor.py` は標準ライブラリだけで、対象のリポジトリの言語を問わない。言語ごとの参照の解決（import の解析）を持つと、言語の数だけ解析器が要る。D4（テストが覆うか）は、名前が限ったテストに現れなければ立てる。示せない変更は全体のテストの 1 回へ倒れる。D3（外から参照されるか）は、名前が当たったときとパッケージの入口（再 export を持ちうる）のときに立てる。動的な読み込みや文字列で組み立てた import は名前が当たらず、見落とす。0 件のときにも立てると、ほぼすべての変更で全体のテストが走り、#933 の「原則実施しない」が成り立たない。見落としは最終ゲートが拾う。

**D3 はコードのファイルだけを、モジュールの参照の形で探す。** `plan` / `setup` / `report` のような一般的な語幹をそのまま探すと、範囲の外の文書や無関係なコードに必ず当たり、ほぼすべての項目で D3 が立つ。親ディレクトリ付きのパスとドットの形・`from` の形・修飾名の全体に絞れば、当たるのは参照している見込みの高い箇所になる。

ファイル名や `symbol` の名前だけを語として探す案は採らない。一般的な名前では当たり過ぎ、別名で読む形も拾えない。

### 決定 21: `--round-test` をそのまま使う項目の D4 は、`--round-test` の対象の語の配下のファイルで判定し、対象の語が無ければ立てる（実装の持ち場で決めた）

設計のレビューで、`test_targets` から語の並びを組み立てられず `--round-test` をそのまま使う項目の D4 が未定のまま残った。D4 は「限ったテストのファイル」に名前が現れるかを見るため、そのファイルの集合を決める必要がある。

`--round-test` の対象の語（`scope.round_test_roots` が範囲の関門で既に読み分けている語）の配下の追跡されたファイルを限ったテストのファイルとする。その項目を検証したのは実際にそのコマンドであり、覆う範囲を最も正しく表す。対象の語が無いコマンド（`make test`・ラッパー）では走ったファイルを挙げられないため、決定 20 の「示せないときに立てる」に従って立てる。

`--round-test` をそのまま使う項目では常に D4 を立てる案は採らない。`--round-test` は利用者が範囲のテストとして渡したもので、名前が現れるなら覆っていると読める。常に立てると、`test_targets` を返せなかった項目があるだけで全体のテストが走り、「原則実施しない」が崩れる。

### 決定 22: 危険の印の全体のテストが落ちたら、落ちたテストだけを走らせ直して揺れ・元からの失敗・変更が原因を見分け、変更が原因なら締め切りまで直しを試み、直らなければ印の項目を新しい順に 1 件ずつ取り消す（決定 15 を改める）

**経緯（2026-09-24 利用者の指摘と指示）。** PR #951 の実行の報告を見た利用者から「全体テストが改善起因で落ちたのか、元から落ちていたのかが区別つかない」と指摘があった。決定 15 は原因を確かめずに印の項目をまとめて取り消すため、揺れで落ちても元から落ちていても採用した項目を失う。着手前の全体のテストの結果も報告に出ていなかった。利用者の指示は「もったいないから締め切りが来るまでは修正を試みましょう」である。

**採った形。**

| 段 | すること |
| --- | --- |
| 基準を示す | `init` が着手前の全体のテストの HEAD を残し、結果（通過/失敗・秒・HEAD の短い SHA）を報告と改修計画に載せる |
| 見分ける | 全体のテストの出力から落ちたテストの ID を取り出し、それだけを今の HEAD で走らせ直す。通れば揺れ。まだ落ちるものを着手前の HEAD（一時の detach の作業ツリー）で走らせ、落ちれば元からの失敗。どちらも取り消さず、`whole_test` に分類して残す |
| 直す | 残り（今の HEAD で落ち、着手前の HEAD で通る）は変更が原因とみなし、印の項目を既存の修正の経路（`VERIFY=fix` → 修正 → `merge-fix` → `verify`）へ回す。修正担当には落ちたテストだけを走らせ直すコマンドとその出力を渡す。次の `verify` は落ちたテストだけを走らせ直す |
| 絞って取り消す | 締め切り（`budget.fix_time_left` と控えの `fix`。回数の上限は決定 23 で外した）までに通らなければ、印の項目を新しい順に 1 件ずつ取り消し、落ちたテストだけを走らせ直して通った時点で止める（限ったテストの `_revert_shared` と同じ形） |
| 取り出せないとき | 実行器が pytest でない・出力に `FAILED` / `ERROR` の行が無い・打ち切られたときは、見分けも直しもせず決定 15 のとおりまとめて取り消し、理由を `whole_test` と報告に残す |

**迷ったら変更が原因の側へ倒す。** 走らせ直しの出力から ID を読めなければ全部がまだ落ちているとみなし、着手前の HEAD の出力から読めなければ元からの失敗とはみなさない。取り消さない側へ倒すと、壊した変更が Pull Request に残る。

**検証の中の全体のテストは 1 度のままである**（決定 14）。走らせ直すのは落ちたテストだけで、最終ゲートの全体のテストと決定 16 の使い回しは変えない。落ちた時点で `whole_test.status` は `fail` なので使い回さず、最終ゲートが走らせる。

**取り出しは pytest に限る。** pytest は `-q` でも末尾の要約に `FAILED <ID> - <理由>` / `ERROR <ID>` を出す（pytest 9 で実測。収集の失敗はファイルの単位、パラメータの値が ` - ` を含むこともある）。jest / vitest の出力の形は確かめていないため、取り出さずに決定 15 の扱いへ倒す。

**着手前の HEAD は作業ディレクトリを動かさずに走らせる。** checkout で動かすと、途中で落ちたときに HEAD が戻らず、以後の取り消しと公開が別の HEAD の上で行われる。一時の detach の作業ツリーで走らせて消す。未追跡の依存（仮想環境・`node_modules`）はその作業ツリーに無いため、そこで落ちても読めなければ元からの失敗とはみなさない（上の「迷ったら」）。

採らなかった案:

- **二分探索で原因の項目を特定する。** 決定 15 と同じ理由で採らない。全体のテストを何度も走らせる。落ちたテストだけを走らせ直す新しい順の絞り込みで足りる
- **揺れを全体のテストの走らせ直しで確かめる。** 全体のテストが検証の中で 2 回になる（決定 14）
- **元からの失敗を `init` の全体のテストの結果だけで判定する。** `init` は通らなければ止まるため、`init` の時点では常に通っている。着手の後に環境が変わって落ちるもの（時刻・外部の状態に依るテスト）は、着手前の HEAD で走らせ直さないと変更が原因と見分けられない

### 決定 23: 締め切りは LLM の自己申告に頼らずスクリプトが守らせる。直しは回数でなく締め切りまで試み、テストの追加と実装の段の監視の上限を「最後の項目の完了の締め切り + 余裕」に詰める（決定 4 を改める）

**経緯（2026-09-24 利用者の判断）。** 決定 22 の「締め切りが来るまで直しを試みる」を、担当の CLI の申告ではなくスクリプトが管理する形にする。あわせて、テストの追加と実装の段の監視の上限（`max(表の値 3600 秒, 締め切りまでの残り) + 600 秒`、最長約 70 分）を詰める。表との max は取らない。

**採った形。**

- **直しの 1 回 = 実装担当の 1 起動。** 既存の `VERIFY=fix` → 修正の起動 → `merge-fix` → `verify` の 1 周が 1 回で、次の試行の前に `verify` が時計を見る（`budget.fix_time_left` が控えの `fix` より短ければ打ち切る）。**`--max-fix-rounds` の回数は使わない**（決定 24 で廃止）。打ち切ったら、限ったテストは共有した項目を、全体のテストは印の項目を、新しい順に絞って取り消す
- **段の監視の上限 = その段の終わりまでの残り + 余裕。** テストの追加と実装の終わりは最後の項目の完了の締め切り（着手の締め切り + 見積り）、修正は直しの試行の打ち切り、最終ゲートの修正は想定最大時間の終わりである。`start-phase` が `PHASE_TIMEOUT` として返し、駆動は `--timeout` と `--stall-timeout` の両方へ渡す
- **止めたときの取り込みは変えない。** 未コミットの変更は取り込みの前に捨て（`discard_impl_leftovers`）、コミット済みの項目は git の時刻による判定（完了の締め切りを過ぎたら `not_done`）へそのまま流す。**止めたかどうかは監視の結果ファイル（`<stem>-monitor.json` の `reason` が `timeout` / `stalled`）から読む**（`monitor.py` の終了コード 2 / 5 と同じ事実。駆動は終了コードを捨てるため、取り込みが結果ファイルを読む）。`phases.<段>.stopped` に残し、報告に「監視が止めた段」の 1 行を出す
- **最終ゲートの修正も回数でなく時計で打ち切る。** 想定最大時間の終わりを過ぎていれば、落ちても取り消さず報告で終わる（終了コード 1。1 回目は打ち切らないと決定 26 で改めた）。利用上限のように起動し直しても解けない結末は `no_relaunch` の印で同じく打ち切る

**余裕は 0.05·B（予算の 5%）にする。** 今の 600 秒は流用しない。600 秒は「最後の項目が締め切りの直前に着手した分」の余裕で、終わりを着手の締め切り（`T`）に置いていたために要った。終わりを完了の締め切り（着手の締め切り + 見積り）へ移したので、余裕が覆うのはコミットを書き終えるまでの遅れだけになる。完了の締め切りを過ぎたコミットは `not_done` で採らないため、それ以上待っても採れる項目は増えない。固定の秒にすると 10 分の予算で上限の 1 割を占め、予算に比例させる決定 24 とも合わない。

採らなかった案:

- **担当の CLI に締め切りを守らせ、監視は歯止めの長い上限のままにする。** LLM の申告に時間を預けると、予算の外まで走る（#917 の申告と実測の食い違い。決定 8）
- **止めたら段の結果を捨てる。** コミット済みの項目は締め切りで正しく判定できる。捨てると、締め切りの内に終えた項目まで失う
- **修正の回数の上限を残す。** 利用者の指示は「締め切りまで試みる」で、回数で切ると時間が残っていても止まる

### 決定 24: 時間に関わる数値はすべて `--budget-minutes` から算術で逆算し、計画の終わりまでに状態ファイルと改修計画へ書き出す

**経緯（2026-09-24 利用者の判断）。** 監視の上限の表（提案と計画 1200 秒・書き換える段 3600 秒）・余裕 600 秒・テスト 1 回の上限 900 秒・無進捗の余白 900 秒・ランタイムごとの無音の許容・CLI の余白 120 秒・修正の回数 3 が固定値で、予算と連動しなかった。提案と計画は予算に入っておらず、30 分の予算でも最長 40 分使えた。利用者は、固定値を置かずすべて予算から逆算し、式と係数をこの決定で決めきり、実行の途中で数値のために LLM へ問わないよう求めた。

**式と係数**（B = 想定最大時間、w = 着手前の全体のテストの実測秒。係数は `refactor_lib/timeline.py` にだけ置き、式の正本は `docs/02-plan-and-implement.md` の「締め切り」の節）。

| 値 | 式 | 30 分の例 |
| --- | --- | --- |
| 余裕 | 0.05·B | 90 秒 |
| 着手前のテスト 1 回の上限 | 0.10·B | 180 秒 |
| テスト 1 回の上限（着手の後） | max(3·w, 0.01·B) | w = 59 秒なら 177 秒 |
| 提案の枠の終わり | 開始 + 0.20·B | 6 分 |
| 計画の枠の終わり | 開始 + 0.30·B | 9 分 |
| テストの追加・実装の終わり | 最後の項目の完了の締め切り | 計画で決まる |
| 直しの試行の打ち切り | 開始 + B − 全体のテストの控え 2 つ − 最終ゲートの修正の控え（決定 26 で改めた） | 計画で決まる |
| 最終ゲートの修正の打ち切り | 開始 + B（1 回目は打ち切らない。決定 26 で改めた） | 30 分 |
| 段の監視の上限 / 無音の打ち切り | 終わりまでの残り + 余裕（同じ値） | — |
| CLI の上限 | 段の監視の上限 + 余裕 | — |

- **提案と計画の枠は予算からの比率にする**（0.20 と 0.10）。#917 の実測を 60 分の予算へ当てた例（設計の冒頭）は提案 4.5 分・計画 3 分で、終わりは 6 分と 9 分だった。60 分の比率では 12 分と 18 分になり、実測に倍の余裕がある。配分表の実測から出す案は採らない。配分表は提案と計画の所要を持たず（決定 9）、履歴が無いと決まらない。計画の時点の「想定最大時間 − 経過 − 控え」は経過を実測するため、枠の内で終わればそのまま整合する
- **テスト 1 回の上限は 3·w。** 限ったテストは全体のテストの部分で、w を超えることは本来ない。3 倍は負荷の揺れの幅である。下限の 0.01·B は、w がほぼ 0 秒のときに起動の揺れで打ち切らないための床である。着手前のテスト自体は w がまだ無いため 0.10·B を上限にする
- **無音の打ち切りは段の監視の上限と同じ値にする。** ランタイムごとの無音の性質（claude は完了まで 1 バイトも出さない）を下限の目安に残すと固定値が残り、実装担当が claude のときは段の途中で止まる。締め切りが待ちの長さを上から抑えるため、無音の許容を別に持つ必要が無い（監視は「無進捗の許容が上限以上」の警告を 1 行出すが止めない）
- **`--max-fix-rounds` と `--test-timeout` は廃止する**（決定 5 と同じく知らせて無視し、次の版で外す）。修正は締め切りまで試み（決定 23）、テストの上限は予算と w から出す。利用者が上書きする口を残すと、固定値が予算と連動しない経路が戻る
- **`limits.py` の表は変えない。** cross-review と共有しているため、cross-refactoring の側で計算した値を `monitor.py` の `--timeout` / `--stall-timeout` と CLI の `cli_timeout`（`launch-cli.sh` が読む）で渡す。`start-phase` を通らない起動だけが表の値を使う
- **配分表の見積りはそのまま残す。** 上限ではなく、予算から差し引く実測値である
- **値は `init`（計画の前の値）と `merge-plan`（計画の後の値）が `state["limits"]` へ書き出す。** 以後の段は書き出した値と時計の比較だけで進む。改修計画のコメントに「時間の上限」の表として載せ、読み手が実行の前にすべての時刻を見られるようにする。計画の前に予算を置き換えた再開は表を組み直す

**固定のまま残す値**（報告の「固定のまま残した値」に並べる）。予算と性質が違い、逆算が意味を成さない。

| 値 | 置き場所 | 理由 |
| --- | --- | --- |
| 打ち切ったプロセスグループへ SIGKILL を送るまでの待ち 5 秒 | `gitfacts.run_with_timeout` の `kill_grace` | OS がシグナルを配って子が終わるまでの時間。予算が長くても短くても変わらない |
| 監視が止めた CLI へ SIGKILL を送るまでの待ち 3 秒 | `monitor.py` | 同上。cross-review と共有 |
| 結果ファイルを書き終えたとみなす経過 30 秒 | `monitor.py` の `RESULT_AGE_GRACE` | ファイルの書き込みの完了の目安。cross-review と共有 |
| 監視の見回りの間隔 15 秒 | `monitor.py` | 監視の 1 周期。上限の粒度を決めるだけで、予算に比例させると短い予算で見回りが粗くなる |
| Jev の通信 1 回の待ち 10 / 20 秒 | `jev.py` | 計画までの HTTP の待ち。予算に比例させても応答は速くならない |
| 認証の確認 1 回の待ち 120 秒 | `auth.py` | `init` の参加者の確認。予算が決まる前の段で、cross-review と共有 |

### 決定 25: 計画の後で LLM が動くのは作業の CLI だけにする。D5 の Jev は計画の段へ前倒しし、テストの差分の判定の段 2（AI）は規則（最終ゲートのレビューへ引き継ぐ）に置き換える

**経緯（2026-09-24 利用者の判断）。** 数値を計画で決めきるのと同じ理由で、計画の後の判断も LLM へ問わない。取り消し・見送り・絞り込み・揺れの判定・次の試行に進むかは、状態ファイルの値・git・テストの終了コードだけでスクリプトが決める。

**計画の後に残っていた判断の呼び出しと扱い。**

| 呼び出し | 段 | 扱い |
| --- | --- | --- |
| D5（公開の入出力が変わりうるか）を Jev に問う | 検証 | **計画の段へ前倒しする。** `merge-plan` が採った項目ごとに問い、`items[].public_io` に残す。検証は読むだけ |
| テストの差分の判定（段 2、`judge-test-changes` の CLI） | 実装の取り込みの後 | **規則に置き換える。** 段 1（機械）で決まらない差分は、項目ごとに `review_test_judgements` へ残して最終ゲートのレビューへ引き継ぎ、改修計画に載せる |
| 揺れ・元からの失敗の見分け（決定 22） | 検証 | もとからスクリプト（落ちたテストの走らせ直し） |

**D5 を前倒しすると差分が見えない。** 以前は `git diff --stat` を添えて問うていたが、計画の時点では差分がまだ無いため、提案の文（手法・理由・手順）だけで問う。D5 は印を立てる側の材料で、見落としは最終ゲートが拾う（決定 14・20）。検証の段で問い続けると、計画で見積もった時間の外で所要が伸び、Jev の応答で結果が変わる。

**段 2 を規則に置き換えると、機械で決まらない差分は自動では落ちない。** 読み手のレビューへ引き継ぐ。段 2 の答えが `undecidable` のときも以前から同じ引き継ぎだった。すべてを取り消す規則は採らない。経路だけの変更（import の書き換え）のような安全な差分まで失う。

**計画の後に残る LLM の呼び出しは、作業の CLI（テストの追加・実装・直し・最終ゲートの修正）と、単独起動の終わりの `cross-review` だけである。** SKILL.md の駆動は 1 本の bash のまま、ホストへ段ごとの介入を求めない（単独起動の終わりの `cross-review` とその後の報告を除く）。

### 決定 26: 最終ゲートの修正 1 回分の控えを計画の時点で予算から差し引き、予算を使い切った後に最終ゲートが落ちても必ず 1 度は直しを試みる（決定 24 の「最終ゲートの修正の打ち切り = 開始 + B」を改める）

**経緯（2026-09-24 06:05 利用者の判断）。** 決定 23・24 では、最終ゲートの修正は想定最大時間の終わり（開始 + B）を過ぎていれば 1 度も試みずに打ち切った。控えの `fix` は検証の直し（`budget.fix_end` は `fix` を引かない）が使い切れるため、検証の直しが長引くと、最終ゲートが落ちた時点で終わりを過ぎていて、直しを 1 度も試みずに失敗で終わる。全体のテストが落ちたまま Pull Request に残るのは、構造改善の結末として最も悪い。

**採った形。**

| 値 | 改める前 | 改めた後 |
| --- | --- | --- |
| 控え R | `danger_whole_test + final_whole_test + fix` | `+ final_fix`（配分テーブルの `fix` と同じ値。修正の起動 1 回分） |
| 直しの試行の打ち切り（`budget.fix_end`） | 開始 + B − 全体のテストの控え 2 つ | さらに `final_fix` を引く。検証の直しに最終ゲートの修正の時間を食わせない |
| 最終ゲートの修正の打ち切り | 開始 + B を過ぎていれば打ち切る | **1 回も試みていなければ時計で打ち切らない。** 2 回目からは今までどおり開始 + B |
| 最終ゲートの修正の段の監視の上限 | 終わりまでの残り + 余裕（過ぎていれば余裕だけ） | 1 回目は `max(残り, final_fix_seconds) + 余裕`。`final_fix_seconds` は控えの `final_fix` を秒へ直した値で、`merge-plan` が `state["limits"]` へ書く |

- **1 回目の判定は `final_gate.fix_rounds` で見る。** `final-gate` は修正を起動する前に回数を上げるため、打ち切りの判定では 0、`start-phase` では 1 が 1 回目である。回数の上限としては使わない（決定 23 のまま）
- **利用上限（`no_relaunch`）は 1 回目でも打ち切る。** 印は 1 度起動した結末で立つため、1 回目の前には立っていない
- **計画を経ずに最終ゲートへ進んだ実行（`plan.reserve` が無い）は控えが 0 になる。** 1 回目の長さの下限も 0 で、余裕だけを渡す。控えを持たない実行に固定の秒を足すと、決定 24 の「固定値を置かない」に反する

**予算を超えうる幅は、最終ゲートの修正 1 回分の見積り + 余裕に限られる。** 控えとして計画の時点で予算から差し引いてあるため、見積りどおりに進んだ実行は予算の内で終わる。超えるのは、検証の直しと最終ゲートの全体のテストが見積りより長引いたときだけである。

採らなかった案:

- **検証の直しの控え（`fix`）を最終ゲートへ回す。** 検証の直しの 1 回分が無くなり、落ちた項目を直さずに取り消す実行が増える。利用者の指示は控えを「差し引く」で、既存の控えの流用ではない
- **最終ゲートの修正を時計で打ち切らない（回数で 1 回に限る）。** 2 回目以降が予算の外で走り続ける。決定 23 の「回数でなく時計」とも合わない
- **`final_end_at` を開始 + B + `final_fix` へ延ばす。** 1 回目の前に修正が 2 回走りうる（1 回目が早く終われば 2 回目も予算の外に入る）。延ばすのは 1 回目の長さだけにする
