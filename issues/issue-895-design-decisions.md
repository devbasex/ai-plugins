# #895: 決定の記録

設計は [issue-895-design.md](issue-895-design.md)、要求は [issue-895-requirements.md](issue-895-requirements.md) にある。

## 決定の記録

### 決定 1: 区間の終わりは、最後の応答の `ndf-next` のブロックで決める

Stop hook の標準入力には `last_assistant_message` が来る（「確かめたこと」の 1）。conductor は既に切れ目で
引き継ぎの 1 行を出す規約を持つので、その 1 行を決まった囲みに入れるだけで機械が読める。情報文字列を
`text` ではなく `ndf-next` にするのは、説明のために引いたコマンドの例を印と取り違えないためである。

引継ぎ文書の決まった見出しを hook が読む形は採らない。引継ぎ文書はマイルストーンを進める利用者が
任意に置くもので、置き場所も名前も決まっていない。transcript の `goal_status` で決める形も採らない。
`/goal` を使わない区間では現れず、書かれる時点も command hook より後である。

### 決定 2: 関門の承認は区間の中で `AskUserQuestion` のまま受け、ブロックは承認の後に出す

`AskUserQuestion` の応答待ちでは Stop が起きない（「確かめたこと」の 6）。関門を区間の切れ目にせず、
承認と取り込みを済ませてから次のコマンドを出せば、中継は関門のことを知らなくてよい。
`context-window.md` の「報告が `結果: 関門` なら、関門の承認と取り込みの後に出す」がすでにこの順である。

関門で止まっていることを中継が画面（`capture-pane` の選択肢の行）から読む形は採らない。画面の
文言は Claude Code の版で変わり、読み違えると関門の前で会話を切る。

### 決定 3: `stop_hook_active` を見ず、印は最新の Stop の中身で置き換え、中継は静まってから動く

`/goal` の判定は Stop hook と並んで発火し、止めを拒むと応答が続く。標準入力だけでは最後の Stop か
分からない（「確かめたこと」の 4）。そこで hook は Stop のたびに印を書き直すか消し、中継は印と
会話の記録の更新が 15 秒止まってから `/exit` を送る。応答が続けば記録が動くので、中継は待つ。
`/goal` の目標がある区間では、印の後の `goal_status` の記録も待つ。判定は command hook より後に記録へ
書かれるため、判定に 15 秒を超えて掛かっても、その記録が現れる前に `/exit` を送らない。

`stop_hook_active` が真の Stop を捨てる形は採らない。`/goal` が 1 度拒んだ後の Stop こそ区間の最後で
ありうる。

### 決定 4: 中継を始めるのは利用者で、最初の区間は中継の子でなくてよい

利用者は既に tmux の中で claude を動かしている（#895 の「確かめたこと」）。印がペインの ID を持てば、
中継は利用者が開いたペインも終わらせられる。中継が最初の区間から起動する形にすると、利用者は
今の会話を捨てて中継から入り直すことになる。

中継の有無は tmux のセッションの環境変数 `NDF_RELAY_DIR` と pid で hook に知らせる。hook を呼ぶ
claude の環境変数に頼る形は採らない。中継より先に起動した claude はその値を持たない。

### 決定 5: プラグインの更新は区間ごとに毎回行う

配布の直後かどうかを中継が判定するには、配布の事実をどこかから読む必要がある。毎回
`marketplace update` と `plugin update -y` を打てば、版が変わっていないときは何も変わらず、
数秒で終わる。更新の後の版を記録に残し、AC8 の確かめに使う。

更新に失敗したら止まる。古い版のまま次の区間を始めると、配布した hook と Skill で進んだと
記録が誤って示す。

### 決定 6: 同じコマンドを起動し直さない。印の無い終わりと空回りで止まる

中継が起動した区間の claude が印を書かずに終わるのは、人が `/exit` した・落ちた・認証が切れたの
いずれかである。同じコマンドで起動し直しても、前者では人の意図に反し、後の 2 つでは同じく
落ちる。止まって人へ渡す。

空回りは「印を書いて 120 秒未満で終わった区間が 3 回続いた」で見る。同じコマンドの繰り返しを
比べる形は採らない。3 層の入口のコマンドは区間が違っても同じ文字列になりうる（`/goal
/ndf:development-workflow <マイルストーン>`）。

### 決定 7: 1 日の起動回数の上限は 20、残すウィンドウは 10、静まりは 15 秒を初期値にする

切れ目の再起動は、持ち場の境（1 つのまとまりで設計・実装・検査・取り込み・仕上げの 5 つ）と
関門の後に起きる。1 日に 2〜3 のまとまりを進めても 20 には届かず、空回りの検出を抜けた暴走は 1 日で止まる。
残すウィンドウの 10 はその半分で、前の数区間を遡れれば足りる。いずれも `run` の引数で変えられる。

### 決定 8: 中継は Python の 1 ファイルで書き、hook も同じファイルの副命令にする

印の形・作業ディレクトリの場所・pid の読み方を hook と中継が共有する。2 つのファイルに分けると、
片方だけが変わって食い違う。Python にするのは、JSON の読み書きとファイルの排他と引数の配列での
起動を標準ライブラリだけで書け、単体テストで tmux と claude の呼び出しを差し替えやすいためである。
hook の定義の側で `TMUX` を見て、tmux の外では `python3` を起こさない。

bash で書く形は採らない。`last_assistant_message` の複数行の抜き出しと JSON の書き出しを `jq` へ
頼ることになり、中身をシェルを通さずに `new-window` へ渡す扱いも難しくなる。

### 決定 9: 次のコマンドの中身はシェルを通さずに 1 つの引数で渡す

中身は LLM の出力であり、引用符や `$(...)` を含みうる。`new-window` に引数の配列で渡せば、tmux は
シェルを介さずに実行する（「確かめたこと」の 9。引数が 2 つ以上のときに限るため、先頭は常に固定の `env`）。
`env -u` で Claude Code の中から継いだ環境変数を外す（「確かめたこと」の補足）。

中身をファイルに書いて固定のラッパーに読ませる形は採らない。引数の配列で既にシェルを通らず、
ファイルの後片付けと、ラッパーの置き場所の解決が増える。

### 決定 10: 記録は区間ごとに起動の 1 行と終わりの 1 行に分ける

版は起動の時点で、長さと終わり方は終わった後に分かる。1 行にまとめると、起動の後に落ちた区間の
行が書かれないか、行を書き直すことになる。空回りの判定（決定 6）は、直前の 2 区間を `end` の行の長さで、今の区間を印の `written_at` とその区間の
`start` の差で読み、中継が起動した区間だけを数える。`end` は区間が
実際に終わったときだけ書き、停止の印・上限・空回りで止まったときは `stop` の行の理由だけを残す。

終わり方を次の区間の起動の行へ持たせる形は採らない。最後の区間と、印なしで終わった区間の
終わり方が残らない。

### 決定 11: 中継は `/exit` の前に、利用者が開いたペインにも `remain-on-exit on` を置く

最初の区間は利用者が開いたペインで動く（決定 4）。何も置かなければ、`/exit` の後にシェルへ戻るか
ウィンドウが閉じ、前の区間の画面を遡れない。上限で閉じるのは中継が開いたウィンドウだけにし、
利用者のウィンドウは閉じない。

残すのを中継が開いたウィンドウに限る形は採らない。関門をまたぐ最初の区間こそ、後から判断の
経緯を見返す画面である。

### 決定 12: 印を書くのはペインの前面の claude だけにし、中継は最初の印から 1 本の列だけを追う

conductor が Bash から起こす `claude -p`（cross-review の担当など）は `TMUX` と `TMUX_PANE` を継ぎ、
Stop hook も走る。そのまま印を読み書きさせると、担当の応答にブロックがあれば関門の前で会話を切り、
無ければ前面の印を消して静まりの待ちを崩す。ペインの ID では両者を分けられないため、hook の親を
たどってペインの前面の claude（`#{pane_pid}` そのものかその子）かを確かめる。

同じセッションの別のウィンドウで別の conductor を動かす利用者もいる。中継は最初の印のペインに縛られ、
以後は自分が開いたペインだけを追う。`run --pane` を必須にする形は採らない。利用者がペインの ID を
調べて渡す手間が増え、区間ごとに付け替える処理も要る。

### 決定 13: 前提の確かめと導入はスクリプト（`relay.py setup`）が行い、`run` も始める前に同じ処理を通る

今の環境では、VS Code の統合ターミナルが tmux を開く設定は手元のユーザー設定にしかなく、どのリポジトリも
用意していない。文書の手順にすると、利用者ごとに手で写すことになり、写し間違いも残る。スクリプトが
確かめ、無ければ入れ、入れた内容を示す。既にあれば何もしない。`run` の前にも通すのは、`setup` を
打ち忘れた利用者でも同じ状態から始まるようにするためである。

### 決定 14: 入れる先は VS Code のリモートの Machine 設定だけにし、既にある既定は替えない

Machine 設定はコンテナの中から書け、そのリモートの利用者だけに効き、手元のユーザー設定より強い。
ワークスペースの設定はリポジトリに入り他の利用者にも効くため書かない。上書きしていれば場所を示す。
既定のプロファイルが別の値なら、利用者が選んだものなので書き換えずに示す。書くときはバックアップを
残し、戻す 1 行を示す。注釈を含むファイルは書き戻すと注釈が失われるため書かない。

tmux そのものは入れない。パッケージの入れ方と権限は環境ごとに違い、失敗したときの戻し方も決まらない。
