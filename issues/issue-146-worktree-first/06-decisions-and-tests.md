# 詳細設計: 決定の記録とテスト設計

この設計で下した判断と、その検証方法を残す。各決定は結論を先頭に置き、理由を後に書く。

## 決定の記録

### 決定 1: 主ディレクトリの編集を拒否しない

**結論。** tool 実行前の hook は案内を返すだけで、`permissionDecision` を返さない。

**理由。** 目的は作業ツリーで開発する原則を通すことであり、編集の物理的な阻止ではない。誤検知が
起きたとき、利用者が作業を続ける手段を失う状態を作らない。逸脱はセッション開始時の検知が拾い、
事後に是正する。

**採らなかった案。** 拒否する形。強制力は上がるが、宣言の誤りや推定の外れが作業の停止に直結する。

### 決定 2: 開発用の作業ツリーを `.worktrees/` に置く

**結論。** 主ディレクトリ直下の `.worktrees/<ブランチ名>` を配置先とする。

**理由。** 3 ランタイムで同じ場所になる。ランタイム既定の配置先はパス名が 1 つのランタイム由来で、
共有する運用に合わない。作成後にパスを指定して入る手順が要るが、これは 1 度の手間で済む。

**採らなかった案。** ランタイム既定の配置先へ合わせる形。作成ツールがそのまま使えるが、他の
ランタイムから見て命名の意味が通らない。

### 決定 3: レビュー用の一時作業ツリーを移さない

**結論。** 相互レビューと相互リファクタリングが使う一時的な作業ツリーは、非永続領域のままにする。

**理由。** 1 つの Pull Request あたり最大 4 個が増え、後片付けの主体も寿命も開発用と異なる。
非永続領域では領域の再作成で自動的に消えるが、リポジトリ配下では明示的な削除が要る。集約すると
`merged` の削除対象に読み取り用の残骸が混ざる。切り替えは既存の環境変数で可能なため、選択肢は残る。

**採らなかった案。** 配置を 1 箇所へ集約する形。

### 決定 4: ブランチの追従を detached HEAD で行う

**結論。** 主ディレクトリは、稼働中の開発用作業ツリーのブランチが指すコミットを detached HEAD で開く。

**理由。** 同じブランチを 2 つの作業ディレクトリへ checkout できないという git の制約がある。
detached HEAD ではコミットしてもブランチが動かないため、主ディレクトリで加えた変更が作業ツリーの
ブランチへ混ざることもない。

**採らなかった案。** 制約を無視して同じブランチを開く形。2 箇所が同じブランチを保持し、片方の
コミットが他方の作業ディレクトリへ現れない状態になる。

### 決定 5: AI への誘導は Skill が担い、hook は補助に留める

**結論。** 作業ツリーで作業させる誘導は Skill の記述を主たる手段とし、hook はランタイムが持つ
手段の範囲で補助する。

**理由。** 編集先のパスを見た誘導を、拒否せずにモデルへ渡せるランタイムが揃わない。Claude Code と
Codex CLI は tool 実行前の hook で `additionalContext` を渡せる。Kiro CLI はこの事象で標準出力を
読まず、モデルへ渡す手段は終了コード 2 に限られ、これは tool の実行を拒否する
（[`05-interface-contract.md`](05-interface-contract.md) の実測表）。拒否しない方針（決定 1）の
もとでは、Kiro CLI へ渡せるのはパスを見ない案内だけになり、プロンプト送信時の hook が担う。
3 ランタイムへ同じ内容が届く手段は Skill の記述だけである。

利用者への提示も揃わない。`systemMessage` を解釈するのは Claude Code と Codex CLI で、
Kiro CLI はこの事象で利用者へ提示する手段を持たない。

**採らなかった案。** hook を主たる誘導手段とする形。

### 決定 6: 依存物をハードリンクで複製し、symlink を使わない

**結論。** 追跡されない依存物は作業ツリーへ複製する。複製はハードリンクで行い、書き換えられる
ディレクトリだけ実体を複製する。

**理由。** 読み込み定義が親ディレクトリを実体解決する構成があり、symlink にすると作業ツリーで
起動した処理が主ディレクトリのコードを読む。失敗として現れないまま別のコードを検証することになる。
ハードリンクは実測で 0.55 秒 / 54,180 ファイル / 実容量の増加なしで済む。

**採らなかった案。** 主ディレクトリへの symlink。容量は増えないが、検証対象を取り違える。

### 決定 7: 台帳を共通の git ディレクトリへ置き、解放しても行を消さない

**結論。** 割り当ての記録は共通の git ディレクトリ配下に置く。解放時は行を削除せず、解放の時刻を
書き込む。

**理由。** 作業ツリーの中に置くと、削除した時点で記録が消える。共通の git ディレクトリはすべての
作業ツリーから同じ場所として解決でき、作業ツリーの生死に影響されない。

行を消さないのは、**同じ番号を別の作業ツリーが使った履歴と、外部公開の記録を残すため**である。
番号の衝突や残骸の混入を後から調べられる。どのブランチのコードがいつ外から到達可能だったかは、
後から必要になる。空きの判定は解放時刻が空の行だけを見るため、履歴は判定に影響しない。

**採らなかった案。** 解放時に行を削除する形。ファイルは小さく保てるが、過去の割り当てを追えない。

### 決定 8: 判定を共通ライブラリへ集め、入口は整形だけ行う

**結論。** hook とコマンドの入口は入力の受け取りと出力の整形だけを行い、判定はすべて共通ライブラリの
関数に置く。

**理由。** 同じ判定を 3 ランタイム分の入口へ書くと、片方だけが古くなる。テストを関数に対して書ける
ため、ランタイムを起動せずに判定の網羅ができる。

### 決定 9: 宣言が無いリポジトリでは何もしない

**結論。** 宣言ファイルが存在しない、読めない、版が未対応のいずれの場合も、何も出力せず終了コード 0
で終わる。

**理由。** この仕組みは多くのリポジトリへ配布される。宣言の誤りや不在が編集や検証を妨げる状態を
作らない。

### 決定 10: テスト用の分離は保存先の実体で行う

**結論。** データ保存先の分離は、名前の付け替えではなく実体を分けることで行う。

**理由。** 初期化の処理が接続先を記述の中に固定している構成があり、名前を変える方式では投入時に
書き換えが要る。実測では、副系統を指す記述を含むスクリプトが 109 本と 15 本存在した。実体を分け
れば名前を変えずに済む。

**採らなかった案。** 1 つの実体の中で名前を分ける形。消費資源は小さいが、初期化処理の書き換えが要る。

## テスト設計

### 階層の使い分け

| 階層 | 対象 | 実行 |
| --- | --- | --- |
| 単体 | 共通ライブラリの判定関数 | `python3 -m pytest plugins/ndf/skills/worktree/tests -q` |
| 結合 | 入口のスクリプト（隔離した一時リポジトリ上で実行） | 同上 |
| 手動 | 3 ランタイムでの結線、起動を伴う検証、外部公開 | 実機で手順を実行 |

既存の検証スクリプトと同じく、隔離した作業領域で bash を子プロセスとして実行し、最終状態を観測する
形を採る。`bash` と `jq` が無い環境ではモジュールごと読み飛ばす。

### 受け入れ条件との対応

| 条件 | 階層 | 検証の要点 |
| --- | --- | --- |
| 1〜3（作業ツリーの用意） | 単体 + 結合 | 現在地の判定が主ディレクトリ / 作業ツリー / サブモジュールの 3 通りで正しいこと。登録されていない配置で作成を試みると登録が先に走ること |
| 4〜5（外部 Skill への委譲） | 手動 | 導入の有無で結果が変わらないこと |
| 6〜8（編集時の案内） | 単体 | 案内を出す例と出さない例の対。保護対象 / 許可パス / 作業ツリー内の 3 通り |
| 9（逸脱の提示） | 結合 | 変更あり / なしの 2 状態 |
| 10（移送手順） | 手動 | 実際に変更を作って移し、両側の状態を確認する |
| 11〜15（ブランチ追従） | 単体 | 作業ツリー 0 / 1 / 複数 × 変更あり / なしの 6 通り。レビュー用の作業ツリーが数に入らないこと |
| 16〜19（退行しないこと） | 結合 | 既存テストと各検査コマンドの実行 |
| 20（実行時間） | 手動 | hook 追加の前後で計測 |
| 21（宣言が無い場合） | 単体 | 出力が空で終了コードが 0 |
| 22（設定の複製） | 結合 | 内容が食い違う場合に中断すること |
| 23（照合の 3 状態） | 単体 | 一致 / 不一致 / 未起動の 3 通りが終了コードで分かれること |
| 24（モードの提示） | 単体 | 変更ファイルの一覧を条件に当てた結果 |
| 25（切り替えの確認） | 手動 | 宣言した判定コマンドがブランチ名を返すこと |
| 26（分離時の重複なし） | 手動 | 2 本を起動して名前・ポート・ボリューム・ネットワークを突き合わせる |
| 27（ハードリンクの退避） | 結合 | ハードリンクが使えない配置での複製 |
| 31（外部依存なしの実行） | 手動 | 保存先を起動せずに完了すること |
| 32（同時実行） | 手動 | 2 本の同時実行後に互いのデータが変わらないこと |
| 33（読み込み定義の基準） | 結合 | 複製した作業ツリーで基準が作業ツリー側を指すこと |
| 34（基準の再利用） | 手動 | 2 回目に焼き直しが起きないこと。所要時間の計測 |
| 35（入口への到達） | 手動 | ホストポートを公開せずに到達すること。証跡の出力先 |
| 36〜37（公開の拒否と期限） | 手動 | 条件を満たさないテスト環境の公開が拒否されること |
| 38（後片付け） | 手動 | 削除後に資源が残らないこと |
| 39（種類の宣言が無い場合） | 単体 | 出力が空で終了コードが 0 |

### テストファイルの構成

```text
plugins/ndf/skills/worktree/tests/
├── conftest.py                     隔離リポジトリを作る補助
├── test_location.py                現在地の判定（条件 1〜3）
├── test_allow_path.py              許可パスの判定（条件 6〜8）
├── test_write_target.py            書き込み先の推定（条件 6〜8 の Bash 側）
├── test_follow_target.py           追従先の判定（条件 11〜15）
├── test_declaration.py             宣言の読み取りと未対応版の扱い（条件 21、39）
├── test_setup_copy.py              設定と依存物の複製（条件 22、27、33）
├── test_verify_exit_code.py        照合の 3 状態（条件 23）
├── test_mode_hint.py               モードの提示（条件 24）
└── test_registry.py                台帳の割り当てと解放、履歴の保持（条件 26 の前提）
```

**起動を伴う検証は単体テストへ持ち込まない。** コンテナの起動は所要時間が読めず、環境によって
結果が変わる。手動確認の手順として残し、実行した結果を Pull Request へ記録する。

### 台帳のテスト

履歴を残す設計（決定 7）は、次の 4 点を確かめる。

1. 解放した行が残り、解放の時刻が入る
2. 空きの判定に解放済みの行が影響しない
3. 同じ作業ツリーへ再度割り当てると新しい行が増え、過去の行が変わらない
4. 1 年を超えた解放済みの行が読み取り時に無視され、ファイルからは消えない
