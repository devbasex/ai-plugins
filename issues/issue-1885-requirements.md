# #1885: スプリントの開発版の材料に develop へ直接入った PR が含まれず、CHANGELOG と承認資料から漏れる

正は課題の本文（#1885）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

スプリントの開発版のプラン（`new sprint` が書き出す `7-release.json`）は、`changelog`・`notes`・`approval-facts`・`changed-plugins` の `--prs` にスプリントの PR（`{queue_prs}`）だけを渡す。前の正式版の後に develop へ直接マージされた PR は材料から外れる。

- 再現: 10.17.68 の後に PR 1869（mcp-bigquery をリモート MCP へ置き換え。ツール名・認証・環境変数が変わり、移行の手順がある）を develop へ直接マージし、スプリント m1492 の開発版 10.17.69-dev.1 を `--prs 1882` で出した
- 結果: CHANGELOG の `[ndf 10.17.69]`・承認資料の「含む PR」「配る中身」「移行の手順」のどれにも #1869 が載らない。「版を上げる他のプラグイン」で mcp-bigquery が「材料に互換の無い変更の記述が無い」として PATCH（2.0.1）になった

## どこで見つけたか

スプリント m1492 の開発版のリリース（承認資料 `issues/approval-ndf-v10.17.69.md`、PR 1883）。プランの雛形は `plugins/ndf/scripts/supervise.py` の `new sprint`。

## なぜこの変更の範囲外なのか

m1492 の受け入れ条件（#1492・#1870・#1867）は開発版のプランが材料にする PR の範囲を扱わない。根拠: MVV なし（判断はこのスプリントの受け入れ条件による）。

## 直さないと何が起きるか

スプリントの外で develop へ入った変更が、利用者向けの更新案内（CHANGELOG）と承認資料から抜け、互換の無い変更が PATCH で配られる。承認者は中身を見ないまま本番を承認しうる。今回は conductor が `--prs 1882 1869` で dev.2 を出し直して回避した。`changed-plugins --since` の差分から PR を拾う（前のタグから develop までのマージ PR）などで直せる見込み。

## 目的

- スプリントの開発版の配布で、CHANGELOG と本番の承認資料が「その版が含む変更の全体」と「未検証のまま残る危険」を、conductor の手当て無しにそろえて持つ。承認する人が資料だけで承認ゲート 2 を 1 回で決められる状態にする（Vision・Value 2）
- conductor が毎回手で足している `--prs` と「未検証・残る危険」の書き足し（#1885 の 10.17.69・10.17.71・10.17.75、#1488 の 10.17.66〜10.17.71）を無くす（Value 4）

## 前提

- 前提 1: 「その版が含む PR」は、前の正式版のタグ（`<plugin>--v<版>`）からベースブランチ（`release.base`。ai-plugins では `develop`）の先端までにマージされた PR と、スプリントブランチ経由でその範囲へ入った実装 PR の和である。版上げの PR（`release/` で始まるブランチ）と PR でない番号は除く（#1274 の `included.range_prs` の除外の規則を引き継ぐ）
- 前提 2: 配布物に入らない変更（PR の本文の `## 利用者向けの変化` が変化なしと書く PR）は、承認資料の「含む PR」に載せ、「配る中身」と CHANGELOG（利用者向けの更新案内）には載せない。CHANGELOG は利用者が版を選ぶための文書で、配布物の外の変更は利用者の判断に効かないためである（#1686 の「決めること」をこの形で決める。承認ゲート 1 で確かめる）
- 前提 3: `--prs` は残し、範囲の PR との和として扱う（既存の呼び方とプランを壊さない）
- 前提 4: 「未実施のリリース後テスト」は、スプリントが閉じる課題の本文の `## 受け入れ条件` のうち、承認資料を書く時点でリリース後テストの記録（`release-verification` の結果の表）に合格の行が無いものを指す。承認資料を書く時点でリリース後テストを一度も行っていなければ、全条件が未実施として並ぶ
- 前提 5: 5 つの材料（レビュー・リファクタリング・全体テスト・設計文書の未確認・未実施のリリース後テスト）は、検査のプランの状態・設計文書（`issues/issue-<番号>-design.md`）・課題の本文・リリース後テストの記録から機械で読む。読む場所と形は設計が決める。新しい記録の工程を人や conductor に足さない
- 前提 6: 3 つの課題の受け入れ条件はこの本文（#1885）に課題番号つきで置き、#1686・#1488 を閉じる判定もこの本文の該当する番号の条件で行う
- 前提 7: 対象は NDF の配布の材料（`release-steps.py` の `changelog`・`notes`・`approval-facts`・`changed-plugins` と、`new sprint` が書くプラン、スプリント PR の本文）である。ほかのプラグイン（playwright-kit・mcp-*）の配布も同じ経路を通るため、同じ振る舞いになる

## 対象範囲

含む:
- 開発版の CHANGELOG の版の節と承認資料の「含む PR」「配る中身」「移行の手順」が、範囲の PR（前提 1）から作られること（#1885・#1686）
- 他のプラグインの上げ幅の候補が、範囲の PR の互換の無い変更の記述を読むこと（#1885）
- 同じ版の開発版の出し直しで、前の開発版の PR が CHANGELOG の版の節から落ちないこと（#1885）
- 承認資料が 5 つの材料を集めること（#1488）
- 材料が無いときに、どの材料が無いかを書くこと（#1488）

含まない:
- 本番（正式版）の配布の手順と承認の記録の形（`approve`・`record`）を変えること
- 「配る中身」の箇条の文面の作り方（PR 本文の `## 利用者向けの変化` から作る現行の規則）を変えること
- 開発版の出し直しで手で足した節を残す仕組み（#1834 で入った `kept_sections`）を作り直すこと
- 検査のプラン（cross-review・cross-refactoring・全体テスト）の進め方と、そこで記録する中身を変えること（読むだけにする）
- ほかの主題（#1263 #1944 #1513・#1875 #1675）の課題が扱う振る舞い

### #1885 develop へ直接入った PR が材料から漏れる

| 既存の振る舞い | 開発版の CHANGELOG と承認資料の中身（載る PR と「未検証・残る危険」）が変わる |
