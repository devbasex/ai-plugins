### 原文から導いた解釈

- conductor がプランへ足した指示は、プランを書き直す側が消してはならない。足さなければならない指示（設計文書のパス・用語集の確認）は、雛形の側が持つ（#1651）

## 目的

- conductor がスプリントのたびに実装のプランへ手で足している指示（設計文書のパス・`check-lint --fix`・用語集の確認）と、整形の違反の後の手当て（`check-lint.sh --fix` を打って再開・`fix_commit` の書き換え）を無くす（Value 4 の「同じ手当てが 2 度目になったら雛形へ入れる」）
- GitHub の一時的な失敗で、触るファイルの無い実装プランが `status: ok` のまま流れることを無くす

## 前提

- 前提 1: 3 課題の本文に利用者の文は無い。条件はすべて起票者の推定（上の S1〜S8）として承認ゲート 1 で確かめる
- 前提 2: 「conductor が足した指示」とは、`new sprint` / `new impl` が書いた後に conductor が `impl` の `prompt` へ足した行を指す。`design-results` は、雛形が作る部分（課題への参照・触る範囲・共通の規則）だけを作り直してよい。見分け方（別のキーに置く・印で囲む など）は設計が決める
- 前提 3: 設計文書のパスは、設計 PR が変えた `issues/*.md` のうち「設計の結果」の表を持つファイルのパス（リポジトリの根からの相対）である。設計 PR の無い課題（`design-results` を通らない `new impl`）には書かない
- 前提 4: 用語集の確認の行は、そのプロジェクトに用語集の設定と用語集がある（`glossary.py gate` が 0）ときだけ入れる。無いプロジェクトでは入れない（Value 5）
- 前提 5: 整形のコマンドと静的解析のコマンドは、プロジェクトの宣言（`.ndf/`）から読む。ai-plugins の `check-lint.sh` / `check-script-structure.py` を既定に埋め込まない（Value 5）。宣言の置き場（`.ndf/supervise.json` の `sync_checks` を使うか、別のキーを足すか、`.ndf/project.json` の `kind: lint` の suite を使うか）は設計が決める。ai-plugins の宣言を書き換えるのは C7 に当たるが、実装の中でコミットし承認ゲート 2 で人が見る（共通原則「承認は既存の承認ゲートで取る」）
- 前提 6: 宣言が無いプロジェクトでは、整形と静的解析のステップを置かず、今の振る舞いのまま動く
- 前提 7: 一時的な失敗とは、`gh` / `git fetch` / `git show` が 0 以外で終わったことを指す。「PR が無い」は `gh` が 0 で終わり結果が空のとき、「設計の結果の表が無い」は文書を読めたうえで表が無いときを指す。打ち直しの回数と間隔は設計が決める（少なくとも 1 回は打ち直す）
- 前提 8: 3 主題が同じファイルを触る箇所の受け持ちは次のとおりとし、設計文書の「設計の結果」で関数の単位で確定する
  - `supervise_lib/design_stage.py`: この主題だけが触る（`merged_design_pr`・`changed_design_docs`・`read_results`・`rewrite`・`cmd_design_results`）
  - `supervise_lib/templates.py`: この主題が触るのは `IMPL_RULES`・`impl_prompt` と、`plan_to_merge` のうち「実装（head）の後・範囲テスト（`test-limited`）の前」のステップ列だけ。`plan_to_merge` の `上限` の行と、`test-limited` から後のステップは触らない（#1909 と #1917 #2003 の受け持ち）
  - `supervise_lib/flow.py`: この主題は触らない
  - ステップを足すため経路が長くなる。上限は #1909 の「経路から決める」形が数える前提とし、この主題では `上限` の値を変えない
- 前提 9: cross-review の送信（`merge-fix` の push）は `lib/result_posts.py` と `cross-review` の `merge_fix.py` の側にあり、他の 2 主題は触らない

## 対象範囲

含む:
- `supervise.py design-results` の実装プランの書き直し（指示の保持・設計文書のパス・一時的な失敗の扱い）
- 実装のプランの雛形（`new impl` と、`new sprint` が作る実装のプラン）の指示文と、範囲テストの前の整形・静的解析のステップ
- cross-review の修正の送信（`merge-fix`）の push の前の整形
- 整形のコマンドの宣言と、それを読む共通の関数（実装のプランと cross-review が同じものを使う。Value 6）

含まない:
- GitHub の障害そのもの（#1941 の本文のとおり）
- 実装のプランの `上限`・遅れの見張り（主題「上限と見張り」#1909 #1676 #1623 #1496）
- ベースブランチの取り込み（主題「起点の取り込み」#1917 #2003）
- `timeout: 5400` の手直し（#1916 の側）
- cross-refactoring の修正の送信（#464 の型。共通の関数を使えば後から寄せられるが、この主題では変えない）
- 整形で直らない規則の違反を自動で直すこと（worker が直す今の経路のまま）

## 用語

| 用語 | 意味 |
| --- | --- |
| 補正 | conductor が雛形の書いた実装のプランへ手で足した指示や値 |
| 設計の結果 | 設計文書の節。課題ごとに実装する・取り込む・閉じると触るファイルを表で持つ |

## 受け入れ条件

### #1651（実装のプランの指示と整形）

- [ ] 1651-1: `impl` の `prompt` に雛形に無い行（補正）を足したプランへ `design-results` を流すと、流した後の `prompt` に補正の行がすべて同じ順で残り、触る範囲と課題の行は設計の結果のとおりに更新される。同じ入力で 2 回流しても、補正の行も触る範囲の行も重ならない
- [ ] 1651-2: `design-results` が設計の結果を読めた課題の `impl` の `prompt` に、その課題の設計文書のパス（前提 3）が入る。取り込んだ課題があれば、取り込んだ課題の設計文書のパスも入る
- [ ] 1651-3: 用語集のあるプロジェクト（前提 4）で `new impl` / `new sprint` が書く実装のプランの `impl` の `prompt` に、用語集と突き合わせる行（`glossary.py check` を打つ）が入る。用語集の無いプロジェクトでは入らない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | GitHub の一時的な失敗のとき、`design-results` は誤った内容のプランを書かず止まる（1941-2）。打ち直しの合計の待ちは設計が上限を決め、ステージの timeout を超えない |
| 性能・拡張性 | 整形と変更範囲の静的解析のステップは、範囲テスト 1 回（m1693 の実測で約 310 秒）より短い。完了判定で実測した秒を実装の PR に書く |

| 移行性 | 宣言を足さないプロジェクトは今のまま動く。既にある実装のプランの JSON は書き直さずに流せる |
