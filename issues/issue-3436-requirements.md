## 目的

非機能の条件の書き方（`requirements-design` の `references/nonfunctional-requirements.md` と、`design` の `references/nonfunctional.md`）は、性能を「対象操作・データ量・上限値」（例: 「1 万件で一覧の初期表示が 2 秒以内」）で書かせ、**どのマシンで測るかを書かせていない**。そのため、マシンのスペックと同時に動かす本数で決まる所要時間が、そのまま受け入れ条件の合否になる。

2026-11-14 に、#1142 の設計からこの形の受け入れ条件が 4 本（#3291 の B3・B6、#3092 の P1-3・P1-6）生まれ、共有の 8 コアのマシンで 34 本のプロセスを 30 分流す負荷試験が 2 つのレーンで走った。1 回目は p95 が 1.62 秒で不合格になったが、不合格がコードの問題か CPU の取り合いかを区別できず、マージの判断に使えなかった。利用者の指摘:「所要時間はマシンスペックの問題で、DB の作りでは直らない」「負荷試験に意味があるとすれば、どういうスペックのマシンでどういう条件で動かしたらこうなりました、という資料を作って、上限なりの目安を提供するぐらい」。

達成したい状態: 受け入れ条件を書く人が規則と例に従うと、マージの合否がコードの振る舞いだけで決まり、マシンのスペックと同時に動かす本数で変わらない。時間で区切った負荷試験が、受け入れ条件として生まれない。

## 前提

- 前提 1: 規則が対象にするのは、これから書く受け入れ条件と非機能の条件である。既にある仕様文書（`issues/`・`docs/specifications/`）は書き直さない。開いている課題で規則に当たる行（#3006・#2647 の 1 回の操作の所要、#3297 の M3-H13）の扱いは、それぞれの課題が決める
- 前提 2: `requirements-design` の `references/acceptance-criteria.md` の書き換えの例「1 万件のデータで、検索 API の応答が 1 秒以内に収まる」（40 行目）も同じ形の例なので、置き換えの対象に含める。題の「受け入れ条件に入れない」の範囲に入り、残すと同じ形の条件を生む
- 前提 3: 「マシンに依らない形」は、実行のたびに同じ入力で同じ合否になる条件を指す。正しさ（例: 同時に書いて `database is locked` が 0 回・取りこぼしが 0 件）、回数と計算量（例: 呼び出しが件数に比例しない・n に対して線形）、同じマシンの上で測った基準との相対（例: 基準の 3 倍以内）の 3 つである
- 前提 4: 「スペックの決まった場所」は、実行環境の種類が設定で固定された場所（例: GitHub Actions の `ubuntu-latest` のランナー）を指す。共有の開発機と、利用者の手元の端末は当たらない
- 前提 5: 規則を機械で強制する検査（受け入れ条件の文から秒数や「N 分」を拾って落とすスクリプト）は作らない。文言の検査は振る舞いを保証せず（`AGENTS.md` の「`.md` の文言を照合するテストを書く」）、合否はレビューで見る

## 用語

| 用語 | 意味 |
| --- | --- |
| マシンに依らない条件 | 同じ入力なら、どのマシンで実行しても同じ合否になる受け入れ条件（前提 3） |
| 時間で区切った負荷試験 | 「N 分流す」のように、流す時間と同時に動かす本数を決めて所要や失敗を測る試験 |
