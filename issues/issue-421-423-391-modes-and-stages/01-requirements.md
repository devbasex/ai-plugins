# 要求と受け入れ条件: モードの母集合の再編と工程表への追加（v10.5.2）

## 何を作るか

**`development-workflow` の 2 つの軸を同時に変える。** モードの母集合（列）と、工程表の
行である。

| 課題 | 変えるもの | 軸 |
| --- | --- | --- |
| #421 | 現 `standard` を廃止し、現 `architecture` を `standard` へ改名する | 列 |
| #423 | 運用のモードを新設する | 列 |
| #391 | 「ドキュメント再構成」を足し、「設計レビュー」を「ドキュメントレビュー」へ改名する | 行 |

**3 件を 1 つの設計として扱う。** #421 と #423 は課題の本文自身が「同時に決める」と述べて
おり、どちらも `WF_MODES` の列を動かす。#391 は行を足すが、書き換える表とファイルは列の
2 件と重なる。別々に通すと同じ表を 3 度書き換え、記録済みの値の読み替えも 3 度要る。

## 依頼

**原文をそのまま写す。** 要約は解釈を含むため、判断の材料としては原文を残す。

```text
/goal /ndf:development-workflow https://github.com/devbasex/ai-plugins/milestone/12
```

```text
v10.5.2としてリリースしてください
```

**解釈**: マイルストーン v10.5.1 に残っていた 3 件を実装し、版 10.5.2 として配布する。

## なぜ必要か

**モードは判定の費用を払って選ぶものである。** 払った費用に見合う差が無ければ、判定そのものが
無駄になる。

| 課題 | 現状の問題 |
| --- | --- |
| #421 | `standard` と `architecture` の差は工程表 15 行のうち 3 セル。分類（`WF_STAGE_MATRIX`）で見ると 2 セルしかない |
| #423 | コードを触らず実行と設定の変更だけを行う変更が、4 モードのどれにも収まらない |
| #391 | 書き上げた文書を章立てから組み直す工程が無く、書き手が調べた順のまま残る |

## 前提

**決められない点を放置しない。** 誤っても局所的に直せるものは前提として書き、手戻りの大きい
ものは設計で決めて承認を求める。

| # | 前提 |
| --- | --- |
| 1 | 版は `10.5.2`。開発版（`-dev.N`）を経てから正式版を出す |
| 2 | 設計文書は 1 本にまとめ、実装の Pull Request は分ける。列を触る 2 件と行を触る 1 件は同じファイルを触るため、並行させない |
| 3 | 記録済みの旧い値（控えの `mode`、盤面の工程）は消さない。読み替えの規則を設計で決める |
| 4 | このリポジトリのマージには管理者の bypass が要るが、承認できる人は 1 人である。到達点は置き直さない |

## 設計で決めること

**ここでは問いだけを置く。** 答えは設計文書が持ち、設計レビューの承認を経て確定する。

| # | 問い | 由来 |
| --- | --- | --- |
| Q1 | 改名後の `standard` は、旧 `architecture` の値をそのまま採るか | #421 |
| Q2 | 旧 `standard` の条件付き（確定仕様化・リリース後テスト）を残すか、必須へ倒すか | #421 |
| Q3 | 記録済みの `architecture` をどう読むか（読めない値とするか、読み替えるか） | #421 |
| Q4 | 運用モードの名前 | #423 |
| Q5 | 「コードを触らない」をどう見分けるか | #423 |
| Q6 | 運用モードで必須にする工程はどれか | #423 |
| Q7 | 実行前の承認を、既存の関門 2 つとどう並べるか | #423 |
| Q8 | 実行結果をどこへ、どの書式で保全するか | #423 |
| Q9 | 実行が途中で失敗したときの記録と戻し方 | #423 |
| Q10 | 盤面へ記録済みの古い工程名をどう扱うか | #391 |
| Q11 | `document-restructuring` を 4 つの配布一覧へ載せるか | #391 |

**Q7 は関門の数に関わる。** v10.5.1 は「関門は 2 つで、増やさない」と定めた。運用モードの
実行前の承認が 3 つ目になるのか、既存の「本番のチャネルへ届く操作」に含まれるのかを決める。

## 対象と非対象

| 含む | 含まない |
| --- | --- |
| モードの母集合と判定の基準 | モード判定の単位（v10.5.1 で Pull Request に確定済み） |
| 工程表の行と列、および 4 か所の並び | 収束ループ（`cross-review` / `cross-refactoring`）の内部 |
| 記録済みの値の読み替え | 盤面そのものの設定（単一選択の値の追加は利用者側の操作） |
| `document-restructuring` の新設 | 既存文書の一括再構成（適用は新規と改訂から） |
| 版 10.5.2 の配布 | v10.5.1 以前の版の記述 |

## 受け入れ条件

### A. モードの母集合（#421）

- [ ] A1. `WF_MODES` が新しい母集合と一致し、旧 `architecture` を含まない
- [ ] A2. `WF_STAGE_MATRIX` の列数が `WF_MODES` の要素数と一致する
- [ ] A3. `WF_MODE_HEIGHT` が新しい母集合の全要素を持ち、列の位置から導いていない
- [ ] A4. `SKILL.md` の判定の基準の表と工程表が、同じ母集合を同じ並びで示す
- [ ] A5. 記録済みの旧い `mode` を読んだときの動作が定まり、テストが固定する
- [ ] A6. `architecture` を現行のモード名として書いている箇所が、履歴と記録を除いて 0 件になる
      （現況: 21 ファイル・59 か所）

### B. 運用モード（#423）

- [ ] B1. 新しいモードの名前が `WF_MODES` にあり、判定の基準の表に 1 行加わる
- [ ] B2. 判定の順序が定まり、他のモードとの境界が境界事例の表に書かれている
- [ ] B3. 工程表に 1 列加わり、15 行すべてに必須・条件付き・対象外のいずれかが入る
- [ ] B4. 実行前の承認の扱いが定まり、関門の節がその結論を述べている
- [ ] B5. 実行結果の保全先と書式が定まり、コマンド・出力・終了コードを残す手順がある
- [ ] B6. 実行が途中で失敗したときの記録と戻し方が手順として書かれている
- [ ] B7. 取り消せない操作を含むときの扱いが書かれている

### C. ドキュメント再構成（#391）

- [ ] C1. `document-restructuring` が `skills/` にあり、少なくとも 1 つの配布一覧へ載る
- [ ] C2. 工程表に「ドキュメント再構成」の行が入る
- [ ] C3. 「設計レビュー」が「ドキュメントレビュー」へ変わり、並びを持つ 4 か所が揃う
- [ ] C4. 工程名を本文で参照している箇所が漏れなく直る（現況: 19 ファイル・34 か所）
- [ ] C5. 章立ての並びの標準が、読み手の問う順で `SKILL.md` にある
- [ ] C6. 測る指標と目安があり、目安を超えるときに理由を残す手順がある
- [ ] C7. 再構成の前後の値を並べて報告する手順がある
- [ ] C8. 組み直しと書き足しを分ける手順があり、混ざったことを前後の値から見分けられる
- [ ] C9. 書き方のルールは `markdown-writing` を呼び、この Skill に写しを持たない
- [ ] C10. 測る手段を「探して決める」形で書き、特定の道具を名指ししない
- [ ] C11. 言語固有の数え方は `references/lang-<言語>.md` にあり、言語を 1 つ足すときに
      他のファイルを変更しない
- [ ] C12. 盤面へ記録済みの古い工程名の扱いが決まっている

### D. 横断（配布まで）

- [ ] D1. 検査 10 本がいずれも終了コード 0 で終わる
- [ ] D2. テストがリポジトリの根から 1 回の起動で終了コード 0 で終わる
- [ ] D3. 配布一覧の行数と説明文書の記載が一致する
- [ ] D4. 版数を持つ 15 箇所が `10.5.2` で揃う
- [ ] D5. `CHANGELOG.md` に `## [ndf 10.5.2]` の節があり、破壊的変更が書かれている
- [ ] D6. `plugins/ndf/README.md` の更新案内が、この版の変更を説明している
- [ ] D7. 3 本とも `cross-review` を収束させている

## 検証手段

**合否は終了コードで見る。** 出力の末尾だけを読まない。

```bash
uv run --with pytest pytest scripts/tests plugins/ndf -q
python3 scripts/check-skill-frontmatter.py
python3 scripts/check-doc-staleness.py
python3 scripts/check-doc-line-limit.py
python3 scripts/check-markdown-links.py --root .
python3 scripts/check-skill-repo-assumptions.py
python3 scripts/check-cross-skill-refs.py
python3 scripts/check-pr-base.sh
bash scripts/build-runtime-plugins.sh --check
bash scripts/validate-runtime-plugins.sh
claude plugin validate .
```

**機械で判定できない受け入れ条件がある。** B4 から B7、C5 から C10 は文書の中身を問うため、
レビューが読む。

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | 既存テストの実行、工程名と母集合の並びの突き合わせ、進行の記録 |
| 確認してから行う | モード名の確定、関門の増減、記録済みの値の読み替え、本番のチャネルへの配布 |
| 行わない | 収束ループの内部の変更、既存文書の一括再構成、盤面の単一選択の値の書き換え |
