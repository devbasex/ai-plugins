# #712 / #713: 設計の決定の記録

設計は [issue-712-713-design.md](issue-712-713-design.md)、何を満たせば完了かは
[issue-712-713-requirements.md](issue-712-713-requirements.md) にある。この文書は
**選んだ結論と、その理由と、採らなかった案**だけを持つ。用語も要求の文書が定める。

## 決定の記録

### 決定 1: 判定を 8 つにし、「ルートコーズ」を「重複」と「要判断」の間に置く

「ルートコーズ」は課題をまたいで決まるため、同じ性質を持つ「重複」の隣が読みやすい。「要判断」は
自動で決められないものの受け皿であり、末尾にあることに意味がある。

既存の 7 つへ統合する案は採らない。「重複」へ寄せると、片方を閉じてよいものと閉じられない
ものが同じ判定になり、後から検索で区別できない（`no-work.md` が「閉じてよい」と「やらない」を
分けたのと同じ理由である）。

### 決定 2: 用語は外来語由来のものを採る

技術文書の用語には、その領域で定着した外来語を採る。**一般語を用語にしない。** 一般語は
読み手ごとに指す対象が変わり、定義を読み飛ばされたときに別のものが思い浮かぶ
（`markdown-writing` のルール 2）。

| 概念 | 採る用語 | 採らない語 |
| --- | --- | --- |
| 8 つ目の判定 | ルートコーズ | 束ねる |
| 同じ原因から出た課題の集まり | クラスタ | 群・かたまり・グループ |
| 共通の原因を直すために作る課題 | 親 issue | 上位の課題 |
| クラスタに属する既存の課題 | 子 issue | 元の課題 |
| 着手の時期を表す単位 | マイルストーン | まとまり |

**地の文は和語のままにする。** 用語を外来語にするのは、指す対象を一意にするためであり、
文章全体を外来語で書くためではない。

**親 issue と子 issue は GitHub 自身の語彙である。** このリポジトリでもサブイシューの
API が通る（`gh api repos/devbasex/ai-plugins/issues/712/sub_issues` が `[]` を返し、
終了コードは 0 だった）。造語を当てるより、実物の機能名に揃えるほうが指す対象が一意になる。
**採るのは語彙だけで、機能そのものは使わない**（決定 15）。

**判定の名前と、作る課題の名前を分ける。** 判定はルートコーズで、作る課題は親 issue である。
同じ語を両方へ当てると、`markdown-writing` のルール 2（1 つの語が 2 つの対象を指さない）に
外れる。

#712 / #713 の本文は「束ねる」を使っているため、**課題の本文もこの用語へ揃える**（AC34）。
揃えないと、判定の名前で検索したときに起点の課題が漏れる。

### 決定 3: まとめるのは目的ではなく、根本原因を直すための手段にする

**目的は、課題を根本原因の場所で直すことである。** 同じ根本原因を持つ課題をまとめるのは、
そのための手段の 1 つでしかない。判定の条件を「修正レイヤーが現象レイヤーと違う」の 1 つに
したのは、目的の側を条件に置くためである。

**件数は判定の条件ではない。** 1 件でも、直す場所が上位にあるなら上位で直す。件数が決めるのは
記録の持ち方だけで、2 件以上なら親 issue、1 件ならその課題の本文である。

**1 件のときに親 issue を作らないのは、指す先が増えないためである。** 親と子が 1 対 1 に
なり、同じ内容の課題が 2 件並ぶ。**どこで直すかの記録は、件数によらず残る。**

件数の上限も置かない。上限を置くと、1 つの層を直せば済むクラスタが件数だけの理由で分断される。

### 決定 4: 子 issue を閉じない

閉じると固有の再現手順が消える。原因を直しても、各課題には個別の適用が残る（条件 2 がこれを
必要条件にしている）。**原因が直った後の棚卸で、子 issue は既存の「閉じてよい」の判定で
閉じられる。** 再現手順を実行して確かめる手順がそのまま使えるため、新しい閉じ方を作らない。

閉じて親 issue へ集約する案は採らない。個別の再現手順が失われ、原因を直した後に
「本当に全部直ったか」を確かめる材料が無くなる。

### 決定 5: 親 issue は子 issue の中身を写さず、番号と 1 行の表で持つ

写すと同じ再現手順が 2 か所に残り、片方だけが古くなる。子 issue を閉じない（決定 4）
ため、本体はそちらに残り、失われない。

### 決定 6: 1 件が複数のクラスタへ属してよい

子 issue を閉じないため、属するクラスタの数だけ 1 行を足せばよい。#459 は「失敗・欠落を
黙って捨てる」と「配布済みの版と開発中の版が食い違う」の 2 つに属する。

**親 issue どうしが同じ箇所を直すなら、それは 1 つのクラスタである。** 段 2B で
親 issue の完了条件を並べ、作るものが同じなら統合する。

**複数のクラスタへ属するため、1 行の有無だけでは起票済みと決められない。** 1 行が指す
親 issue の修正レイヤーを読み、このクラスタのものと一致するときだけ起票を飛ばす。

### 決定 7: 親 issue の重要度はクラスタの最高値を採り、マイルストーンは重要度の規則を先に効かせる

**重要度が決まれば `milestones.md` の既存の表が入れ先を決める。** 高い重要度は主題に
よらず直近のマイルストーンへ入る。**クラスタの中で最も早いものを採る規則は、この後で効く。**
順序を逆にすると、最高重要度が「高い」クラスタが直近より遅いマイルストーンへ置かれ、既存の
「高いものは直近へ」と衝突する。足す記述も、既存の表を適用した後に読む位置へ置く。

**主題で決まる重要度では、子 issue が既に属するマイルストーンのうち最も早いものを採る。**
既存の表は主題が複数に当てはまるときを**要判断**へ倒すが、クラスタは 1 つの原因で括られて
おり、選ぶのは主題ではなく着手の時期である。最も早いものを採るのは、原因を直すまでクラスタの
どの課題も直らないためで、遅い側に合わせると早いマイルストーンの課題が待つ。どの子
issue もマイルストーンを持たないときだけ、既存の表がそのまま決める。

**子 issue のマイルストーンは動かさない。** 振り直しは重要度と位置の食い違いで決まるもので、
既存の「既に設定されているものを振り直す」がその判断を持つ（実害のある課題を直近へ早める形は
そこが自動で反映する）。クラスタへ属したことは重要度を変えないため、振り直しの理由にならない。
ルートコーズが決めるのは親 issue の入れ先だけである。

### 決定 8: 大きさの歯止めを判定に置かない

**層が 2 つ以上にまたがっても、直さなければならないことは変わらない。** 判定で止めると、
実在するクラスタが記録されないまま残り、次の棚卸が同じものを見つけ直す。棚卸の役目は
記録することであって、着手できる大きさへ整えることではない。

**大きさの調整は着手の時点が持つ。** どこで分けるかはマイルストーンの割り当てと実装計画が
決める。`cross-refactoring` が範囲の指定を必須にするのも、提案の時点ではなく適用の時点で
効かせるためである。

**親 issue には修正レイヤーと採る手を必ず書く。** 判定の条件ではないが、着手する側が分ける
材料になる。1 つに決まらないときは当てはまるものを全部書く。

### 決定 9: 起票の例外は親 issue 1 つだけにする

「手入れは起票を含まない」は残し、例外を 1 つ書く。**親 issue は新しい発見ではなく、
既存の課題から導かれるものである。** 課題を見つけたその場の起票は発見の瞬間しか見ないため、
クラスタを作れない。

その場の判断を 3 択から 4 択へ増やす案は採らない。発見の瞬間には指摘の周辺しか見えておらず、
クラスタを判定する材料が無い。

### 決定 10: 重複を固定の行き先とする既存の 2 か所へ「ルートコーズ」を足す

中身は「既存の規則のうち、直すもの」の表にある。**注記も同じ軸を扱っている。** 注記は
「起点が同じでも片方が残るなら重複ではない」と述べており、クラスタの条件 2 と同じ判断を
している。行き先を書かないままにすると、注記を読んだ担当がクラスタを重複として
分断する。

### 決定 11: 2 × 2 の表の正本を `issue-upkeep` に置き、他の 3 つは指す

**溜まった課題を扱う側に置く。** 両方の升を埋めるのはこの Skill であり、表を持つ側と
埋める側が一致する。4 つへ写すと、判定を増やしたときに 3 つが古くなる。

### 決定 12: `retrospective` はクラスタの発見を担わない

**振り返りは 1 回の変更を見るため、クラスタが見えない。** 拾うのは起票の取りこぼしであり、
すでに起票された課題どうしの関係は対象にしていない。担わないことを書き残す。書かないと、
次に読む人が同じ検討を繰り返す。

### 決定 13: 着手の時期を指す「まとまり」を「マイルストーン」へ揃える

`milestones.md` は着手の時期を「まとまり」と「マイルストーン」の 2 通りで書いている。決定 7 で
このファイルへ親 issue の割り当てを足すため、どちらで読むかが判断に効く。

**`SKILL.md` の用語「まとまり」は残す。** そちらは「1 度にマージする Pull Request の集合」で
あり、配布が版を上げる単位を指す。着手の時期とは別の概念である。揃えるのは着手の時期を指す
側だけで、揃えた結果、残る「まとまり」は配布の単位だけを指すようになる。

### 決定 14: 共通の原因を「修正レイヤー」と「採る手」の 2 つへ分解する

「何が無いか」を 1 文で書くだけでは、直す場所と直し方が決まらない。**どこを直すか（修正
レイヤー）と、どう直すか（採る手）を分けて書く。** 分けないと、呼び出し側を 1 件ずつ直す形と、
上位の層を 1 度直す形が同じ記述になり、ルートコーズした意味が出ない。

**さかのぼる段数を決めない。** 現象レイヤーから呼び出し元・親クラス・移譲元をたどり、その
責務を持つべき場所で止まる。段数で切ると、直すべき場所が段数の都合で決まる。止める目印は
「そこを直せば現象レイヤーの各所が同じ形で直るか」であり、直らないならまだ届いていない。

**採る手は 5 つに限る**（移動 / 統合 / 新設 / 向きの修正 / 分離）。5 つは、修正レイヤーが
既にあるか（移動 / 統合 / 向きの修正 / 分離）、まだ無いか（新設）で分かれる。**手は判定の
条件ではない**（決定 8）。親 issue に書く項目であり、1 つに決まらなくても判定は止めない。

**手法の呼び名は増やさない。** `refactoring` の `references/vocabulary.md` が呼び名を持つ
唯一の場所であり、そこから採る。当てはまる手法が無いのは新設だけで、そのときは完了条件が
作る対象を名指しする。

### 決定 15: 親子の結び付きはサブイシュー関係で持つ

**多数のケースは 1 対多である。** 1 件の親 issue に複数の子 issue が付く形で、サブイシュー
関係がそのまま当てはまる。関係を張れば、GitHub の画面と API から親子をたどれる。

| 状況 | 持ち方 |
| --- | --- |
| 子 issue が属するクラスタが 1 つ | **サブイシュー関係** |
| 2 つ目以降のクラスタ | 本文の 1 行で親 issue を指す |
| サブイシューの API を持たないリポジトリ | すべて本文の 1 行 |

**2 つ目以降だけを本文へ逃がす。** 子 1 件が持てる親は 1 件だけであり（下の実測）、決定 6
（1 件が複数のクラスタへ属してよい）を関係だけでは扱えない。**例外の側を本文へ寄せる。**
すべてを本文の 1 行にする案は採らない。少数のケースのために、多数のケースが画面から
たどれなくなる。

実測で確かめたこと。

```console
$ gh api repos/devbasex/ai-plugins/issues/712/sub_issues --jq 'length'
0
$ gh api --method POST repos/devbasex/ai-plugins/issues/712/sub_issues
{"message":"Invalid request.\n\nInvalid input: data cannot be null.",
 "documentation_url":"https://docs.github.com/rest/issues/sub-issues#add-sub-issue","status":"422"}
$ gh api graphql -f query='{repository(owner:"devbasex",name:"ai-plugins")
    {issue(number:712){number parent{number}}}}'
{"data":{"repository":{"issue":{"number":712,"parent":null}}}}
$ gh api repos/devbasex/ai-plugins/issues/671 --jq '{number, id}'
{"id":5462992209,"number":671}
```

読み取れること。**親から子は REST の一覧で引ける。子から親は GraphQL の `parent` で引け、
単数である**（複数の親を持てない）。付けるときに渡すのは issue の番号ではなく
データベースの ID である。

### 決定 16: 段 2B は重複の突き合わせを先に行う

ルートコーズの条件 2 は「同じ課題ではない」ことを確かめるため、重複の正本が決まっている必要が
ある。**順序を逆にすると判定が循環する。** 条件 1 が欠けたときの行き先を「重複の突き合わせへ」
と書くと、その突き合わせの結果を条件 2 が待つ形になり、どちらも終わらない。

先に重複を決めておけば、条件 1 が欠けたものの行き先は**既存の判定のまま**で終端する。
2 件以下で重複でもないなら寄せ先が無く、`no-work.md` の条件 2 もそのまま満たされる。

### 決定 17: 直近のマイルストーンを連番で決める

`milestones.md` は直近を「open のうち版数が最も小さいもの」と定めているが、**このリポジトリの
open のマイルストーンは版数を持たない。** 名前は `<2 桁の連番> <主題>` で、版数の名前を持つのは
closed だけである（`AGENTS.md` の「版と配布の方針」。実測でも open は `03 研究基盤`
`14 利用者を増やす` のような連番だった）。連番で決める形へ直す。

**同じファイルの「順序を直すとき」も版数を読む。** 依存の記述と突き合わせる相手を
「版数の順序」と書いているため、直近だけを直すと 1 つのファイルが 2 つの基準を持つ。
連番へ揃える。

別の課題として残す案は採らない。親 issue の入れ先を決めるのは決定 7 が委ねたこの規則であり、
直近が決まらないままでは AC14 を実行できない。

### 決定 18: ルートコーズの分岐で「要判断」へ倒さない

**判定の行き先は 2 つ（ルートコーズ / 既存の判定のまま）、段 3 での対応の行き先は 3 つ
（その課題の本文へ書く / 親 issue をつくる / 重複として正本へ寄せる）である。**
「要判断」は人へ返して反映しない判定であり、返した先で人が見る材料は段 2A の控えと同じである。
同じ材料で決められることを返すと、棚卸の回数だけ人の作業が増える。

分岐ごとに、返さずに決まる理由は次のとおりである。

| 分岐 | 行き先 | 返さずに決まる理由 |
| --- | --- | --- |
| 同じ層を指すものが 1 件 | その課題の本文へ書く | どこで直すかはその課題に書ける。親 issue を作っても指す先が増えない |
| 層を名指しできない | 既存の判定のまま | 名指しできないなら、現れている場所がそのまま直す場所である |
| 直すと個別の作業が残らない | 重複 | 同じ課題であることの定義そのものである |
| 層が 2 つ以上にまたがる | ルートコーズ | またがることは直さなくてよい理由にならない（決定 8） |
| 採る手が 1 つに決まらない | ルートコーズ | 手は判定の条件ではなく、親 issue に書く項目である（決定 8） |

**既存の判定が「要判断」を持つこと自体は変えない。** そちらは本文の読み方が複数あるときや、
起票の意図が現在も要るかを判断できないときの受け皿であり、材料が本文の外にある。
ルートコーズの分岐は段 2A の控えだけで決まるため、同じ受け皿を使わない。

### 決定 19: Skill には、その場で決められないことだけを書く

**`grouping.md` は棚卸のたびに読まれる。** 書式の雛形を置くと、その分だけ判断の材料が
読み手の手元から押し出される。**書式を決めても読み手の判断は変わらない。**

| 書くもの | 書かないもの |
| --- | --- |
| 実測でしか分からないこと（サブイシューに渡すのはデータベースの ID） | 親 issue の見出しの並び |
| 判断の基準（条件・行き先・止める目印） | 本文へ足す 1 行の文面 |
| 書かないと失われるもの（子 issue の中身を写さない理由） | 置き場所の細かい指定 |

**親 issue に書く 4 つは残す。** 修正レイヤー・採る手・子 issue の一覧・完了条件は、
書く項目が決まっていないと抜けるためである。抜けたことは後から気づけない。
