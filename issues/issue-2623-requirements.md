## 何が問題か

### 起きたこと（#2616）

プラグインでないアプリのリポジトリ（carul）で並列の計画を流すと、レーンの「`配布の依頼`」に対して耐久ワークフローがプラグインの版（`plugin.json`）を読もうとし、読めずに計画全体が止まった。carul は develop へのマージで検証環境へ、main へのマージで本番へ、CD（環境ごとのパイプライン）が反映しており、NDF が版を上げてまとめて出す工程はそもそも要らなかった。

### 根にあること

**NDF は、デプロイとリリースを自分の工程（`release` の Skill とスクリプト）で行う前提で作られている。** CD を持つリポジトリはその例外として扱われる（`release/SKILL.md` の「サービスは、反映を誰が起こすかでこの工程の形が変わる」、`production-merge.md`）。このため:

- **ai-plugins 自身に CD が無い。** `.ndf/project.json` の `delivery` は `kind: manual`（「release の工程で版を上げ、main へマージしてタグ ndf--v<版> を打つ」）で、版上げ・main への昇格の PR・タグ・GitHub Release を NDF のスクリプト（`release-steps.py` 1,168 行・`supervise_lib/release_templates.py` 488 行・`delivery_templates.py` 220 行・`lib/delivery.py` 333 行）が順に打つ。`.github/workflows/` には検査のジョブしか無い
- その仕組みを、版とタグで出すプラグインの形のまま他のリポジトリへ当てはめるので、#2616 のように形の違うリポジトリで壊れる
- 並列の計画のまとめたリリース（提示のプラン・本番のプラン・一時レーン）も、この前提の上に積まれている

**利用者の判断: デプロイ・リリースは CD で解くべき課題で、NDF の工程が担うものではない。**

## 直す向き（利用者の指示）

1. **NDF の「`配布`」の工程の定義を、CD を前提に改める。** NDF の工程が受け持つのは、CD を起こすマージ（とその前のリリース承認ゲート、#2619）と、CD の結果を確かめること（リリース後テスト）である。環境へ届ける手順そのものは CD が持つ
2. **CD が無いリポジトリでは、CD の設定とその方式の記録を促す。** NDF が代わりにデプロイの手順を打つことを既定にしない。方式の記録の置き場は `.ndf/project.json` の `delivery`（今の宣言）を使う
3. **ai-plugins 自身に CD を設ける**（根本課題）。たとえば develop・main へのマージを起点に、版の確かめ・タグ・GitHub Release を CD が行う

## 起票時の受け入れ条件（案）

1. `development-workflow` の工程表と `release` の Skill が、デプロイとリリースを「CD が行い、NDF はマージ・承認・確かめを受け持つ」形で定義している。CD を持つリポジトリで、NDF のスクリプトが版上げ・タグ・公開などの届ける手順を打たない

## 目的

- CD の有無にかかわらず、どのリポジトリでも開発の工程が止まらない状態にする。CD を持つリポジトリでは、NDF が要らない版上げ・タグ・リリースの Pull Request に入らない
- 環境へ届ける手順を CD へ移し、NDF の工程をマージ・承認・確かめに絞る。形の違うリポジトリへプラグインの手順を当てはめて壊れる原因（#2616）を、例外の追加でなく定義の変更で無くす
- CD が無いリポジトリには、設定と方式の記録を促す。あえて CD を置かないリポジトリには促さず、その判断を記録として残す

## 前提

- 前提 1: 語は #2620・#2619 の定義に従う。デプロイは環境へ届けること、リリースは本番へのデプロイだけを指す
- 前提 2: CD の有無は `.ndf/project.json` の `delivery` の宣言だけで判定する。`kind: auto` の行が CD を指す。宣言と実際の CD が食い違っていても検出しない
- 前提 3: `documentation` モードの生成と提出、モバイルアプリのストアへの提出は CD の定義に含めず、提出の工程として今の手順を残す

- 前提 5: 手動の行に理由が書かれていれば「あえて CD を置かない」と読む。手順は今ある `trigger` の欄を使い、理由だけを新しい欄として足す
- 前提 6: 案内の後の工程は、今の手で行うステージのまま続く。案内はリポジトリの設定を書き換えず、CD を作らない
- 前提 7: #2616 の実装は #2616 の課題で進める。受け入れ条件 21 は #2616 の実装が入った状態で確かめる

## 用語

| 用語 | 意味 |
| --- | --- |
| CD | 継続的デリバリー（Continuous Delivery）。ブランチへのマージを起点に、環境への反映を NDF の工程の外の仕組みが行うこと。宣言の `kind: auto` で表す |
| CD の案内 | CD が無いリポジトリで、工程がデプロイに入ったときに出す案内。CD の設定と方式の記録を促す。承認ゲートではない |
| 手動反映の理由 | 宣言の手動の行に書く、あえて CD を置かない理由。これがある行には CD の案内を出さない |
| 自動反映の本番チャネル | 本番チャネルのうち、マージで本番系への反映が自動で始まるもの |
| 手動反映の本番系 | 宣言の行のうち、本番系へ届き、担い手が手で起こすもの |
| 昇格の Pull Request | ベースブランチから本番チャネルへ変更を入れる Pull Request |
| リリースの経路 | 変更が本番系へ届く道筋。宣言から決まる |
| リリースタグ | 正式版を出したときに本番チャネルのコミットへ打つタグ `<プラグイン>--v<版>` |

工程の定義:

- [ ] 1. 文書を知らない読み手が `development-workflow` の工程表と `release` の Skill を読んだだけで、「環境へ届ける手順は CD が持ち、NDF はマージ・リリース承認ゲート・結果の確かめを受け持つ」ことと、CD が無いときの進み方を答えられる。確認: 別の LLM のセッションへ 2 つの文書だけを渡して問い、答えを記録する

CD を持つリポジトリ:

- [ ] 2. CD の形で `supervise.py new sprint` / `new close` が組むプランに、版上げ・変更履歴・リリースタグ・GitHub Release を打つステップが 1 つも無い
- [ ] 3. CD の形で `release` の工程が `release/v<版>` の Pull Request を求めず、リビジョンを記録の値にしてスプリントを閉じられる
- [ ] 4. CD の形で開発ループの `loop sprint` が開発版の版数の引数なしで周回を始められる
- [ ] 5. 版を持つ CD の形の行は、リリースの経路が手で行うステージにならない
- [ ] 6. 昇格の Pull Request のマージは、今と同じくリリース承認ゲートで止まり、承認の後にだけマージされる。承認ゲートの数は増えない（退行しない）
      前提の確認: `uv run --frozen --project . --all-extras pytest plugins/ndf/scripts/tests/test_delivery.py -q -n 4` → 30 件が通る（7db74dfa6）
- [ ] 7. 本番チャネルへのマージの後に、NDF が CD の結果（成功・失敗・未確定）とリビジョンをリリース記録へ残す
- [ ] 8. CD の結果が失敗なら、デプロイの工程は完了にならず、理由が報告される。結果を読む手段が宣言されていないか待ちの上限に当たったときは、未確定と書き、成功と書かない

CD の案内:

- [ ] 9. `delivery` が無いか `{"unknown": ...}` のリポジトリで工程がデプロイに入ると、CD の案内が 1 件出る。案内は、何が無いか・CD の設定の手順の参照先・`delivery` への記録の例・手動反映の理由を記録する方法の 4 つを含む
- [ ] 10. 手動の形で手動反映の理由の無い行があると、その行についての CD の案内が出る
- [ ] 11. 手動の形で全行に手動反映の理由があると、CD の案内が出ず、`trigger` の手順で手で行うステージへ進む
- [ ] 12. `delivery: []` と CD の形では CD の案内が出ない。自動の行と手動の行の混在では、理由の無い手動の行についてだけ出る
- [ ] 13. CD の案内の有無で、承認の問いの数・プランのステージの数・コマンドの終了コードが変わらず、`.ndf/project.json` が書き換わらない
- [ ] 14. `delivery` の宣言が壊れていて読めないときは CD の案内を出さず、今と同じく読めない理由を示して止める側へ倒す（退行しない）
      前提の確認: 受け入れ条件 6 と同じコマンド（`judge_target` の決められない判定を含む）

ai-plugins の CD:

- [ ] 15. ai-plugins の `.ndf/project.json` の `delivery` に、`kind: auto`・本番チャネルの行があり、`trigger` が CD のワークフローの名前を指す
- [ ] 16. 昇格の Pull Request が `main` へマージされると、CD がマージのコミットへ `ndf--v<版>` のタグを打ち、題が `ndf v<版>`、本文が変更履歴の版の節の GitHub Release を Latest で作る。版は `main` の `plugins/ndf/.claude-plugin/plugin.json` から読む
- [ ] 17. `develop` へのマージではタグも GitHub Release も作られない
- [ ] 18. CD の再実行で、タグだけがあるときは GitHub Release を補い、両方あるときは何も変えずに成功する
- [ ] 19. 版に `-dev` の接尾辞があるとき、または同じ名前のタグが別のコミットにあるときは、タグも GitHub Release も作らず、ワークフローが失敗し、既存のタグを書き換えない。取得元のブランチと版の形は変わらない
- [ ] 20. CD のワークフローは新しい秘密を要さず、書き込みの権限（`contents: write`）をタグと GitHub Release を作るジョブだけに与える。既存のワークフローの権限は変わらない。CD を含む版の本番リリースで、タグと GitHub Release は 1 組だけできる

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | CD の結果を確かめた対象と返ってきた値が、リリース記録に 1 回のリリースごとに残る。CD のワークフローの失敗は GitHub の実行の記録で読める |
| 移行性 | `delivery` の新しい欄は任意とし、今の宣言がそのまま読める。解析（`project-decl.py`）をやり直しても手動反映の理由が消えない。手動の行を持つ既存のリポジトリには、理由を書くまで CD の案内が出る（工程は止まらない）。ai-plugins の切り戻しの手順（CD を外してタグと GitHub Release を作る手段）を、CD を含む版の承認資料に書く |
| セキュリティ | CD はタグと GitHub Release を作る書き込みの権限だけを持つ。Pull Request の head のコードを書き込みの権限で実行しない |
| システム環境 | CD の設定の案内は特定の CI を前提にせず、手順の例として GitHub Actions を示す |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`delivery` の行に任意の欄（手動反映の理由）が増える。互換あり。`kind: auto`・`versioned: true` の行の経路が変わる |
| データ | スキーマの追加のみ。既存の宣言と記録の移行は無い |
| 既存の振る舞い | CD の形でデプロイの工程が短くなる。手動の行と宣言の無いリポジトリに CD の案内が出る。devbase の形は手で行うステージから外れる。ai-plugins のタグと GitHub Release の作成が NDF のスクリプトから CD へ移る |

## 検証手段

| 項目 | 手段 |

| 起動 | `supervise.py new sprint` / `new close` を宣言の形ごとの作業用のリポジトリで打ち、プランを読む |

| 手動確認 | CD を含む版の本番リリースの後に、`gh release view ndf--v<版>` とタグのコミットを見て、受け入れ条件 16・20 を判定する（リリース後テスト） |
