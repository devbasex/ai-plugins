# #2335 の設計: 決定の記録

設計文書の本体は [issue-2335-design.md](issue-2335-design.md) にある。要求の「決めること（設計で）」の 5 項目は決定 1・3・6・11・10 が、
要求の未決のうち設計 Pull Request までに決めるものは決定 7・9・16 が受ける。

## 決定の記録

### 決定 1: 核を通ったかを構文木で確かめられるよう、入口の末尾を `run_core.main("<入口の id>", body)` の 1 文にする

核は本体を引数に取る関数で、入口のモジュールの `if __name__ == "__main__":` の中身はこの 1 文だけにする。
本体は `RunContext` を受けて `Outcome` を返す普通の関数で、テストは核を通さずに本体を呼べる。構造チェックは
`__main__` の文の形だけを見れば「核を通らない入口」を落とせる。

装飾子は採らない。関数の呼び方が見た目と変わり、本体を単体で呼ぶテストも核を通ってしまう。コンテキストマネージャ（`with run_core.run(...)`）は
本体の戻り値を結果へ変えられず、`with` の後ろに書いた出力を核が止められない。`supervise.py run` のような別の実行器は、
Skill の本文が書くすべてのコマンドの形を変え、起動ごとにプロセスが 1 つ増える。

根拠: Value 4 / Value 6（MVV 版 3）

### 決定 2: シェルの入口に別の実装を持たせないため、シェルは Python の核の子として起こし直す

シェルの入口は先頭の `rc_enter` で `python3 run_core.py exec <入口の id> -- "$0" "$@"` へ置き換わり、核が入力の解決・記録・
持ち主・期限・結果の確かめを行ってから、`set -euo pipefail` を付けた本体を子として動かす。解決した入力は `NDF_IN_<名前>` の
環境変数で渡す。呼ぶ側のコマンド（`bash foo.sh ...`）は変わらない。

シェルで同じ段（trap での後片付け・記録・持ち主）を書き直す案は採らない。同じ役割の処理が 2 つの言語に分かれ、片方だけが直る。
解決した値を `eval` する KEY=VALUE で返す案も採らない。機械が読む出力を 1 行 JSON にそろえる方針（受け入れ条件 11）に反する。

根拠: Value 6 / Value 4（MVV 版 3）

### 決定 3: 型の検査を読み書きの両方で 1 か所に置くため、データの型は pydantic の型に版と移行関数を持たせて書く

種類ごとに `lib/model/<種類>.py` を置き、型（`schema.Shape` の子）・今の版・`v<N>→v<N+1>` の移行関数を持つ。核の `ctx.read` /
`ctx.write` が `schema.load_shape` / `dump_shape` を通す。契約の一覧の形も同じ書き方で `lib/contracts.py` が持つ。
人が読むスキーマが要るときは、型から `model_json_schema()` で出す。

`dataclass` は読むときに形を確かめず、確かめる処理を種類ごとに手で書くことになる。JSON Schema を正にすると検査の
ライブラリ（jsonschema）を新しい依存として足し、コードの型と 2 か所で同じ形を持つ。pydantic は既にある extras（`schema`）で、
`lib/schema.py` が理由の文を出す形まで持つ。

根拠: Value 6 / 前提 5 の範囲（MVV 版 3）

### 決定 4: 1 つの意味を 1 つの名前にするため、プランの JSON の日本語のキーを英語の名前へそろえ、旧いキーは移行関数で読む

プラン・状態・記録・結果のキーは名前の対応表の正しい名前（英語）だけを書く。`課題`・`フェーズ`・`触るファイル` などの
日本語のキーは、プランの型の移行関数が読み替える。人が読む形は描画の部品が日本語の見出しで描く。

日本語のキーを残す案は採らない。プランを書くのは雛形と AI で、人はプランの JSON を直に書かない。同じ意味を状態の側では英語、
プランの側では日本語で持つ今の形が、名前の対応表の 2 重の別名を生んでいる。

根拠: Value 8（MVV 版 3）

### 決定 5: 並列の Pull Request が衝突せずに書けるよう、契約の一覧は JSON の 1 項目 1 ファイルで `plugins/ndf/contracts/` に置く

入口・ファイル・設定・環境変数を種類ごとのディレクトリに 1 項目 1 ファイルで置く。上限の宣言と名前の対応表は
全体で 1 つの表なので、それぞれ 1 ファイルにする。

コードの中で宣言する案（各入口の `CONTRACT = ...`）は採らない。「1 か所の宣言」にならず、ファイルの契約のように
入口に属さない行の置き場が無い。1 つの大きなファイルは、柱の Pull Request が並列で同じファイルを触り、マージで衝突する。
YAML は読むのに `yamlio`（ruamel）を要し、核が読む度に依存が増える。1 項目 1 ファイルは `script-structure-allow/` で衝突しない
ことを確かめた形である。

根拠: Value 4 / Value 3（MVV 版 3）

### 決定 6: 1 回の起動を 1 つのファイルで追えるよう、実行の記録は起点の実行ごとに 1 ファイルを状態の置き場へ置き、30 日で消す

置き場は `${NDF_STATE_DIR:-~/.local/state/ndf}/runs/<リポジトリ>/<UTC の日付>/<起点の実行の識別子>.jsonl` で、子の実行は
`NDF_RUN_ID` から起点を引き継いで同じファイルへ書く。寿命は耐久の記録と同じ 30 日で、日付のディレクトリごと消す。
`progress.jsonl`（プランの状態）・使用量の帳簿・`ask.jsonl`（hook が書く）は、記録ではなく業務のデータとして今の置き場に残し、
行に `run_id` を足して実行の記録とつなぐ。

リポジトリで 1 つのファイルにする案は採らない。並列のループが同じファイルへ追記して排他を取り合い、1 回の起動を
読むたびに全体を絞り込むことになる。worktree や `.ndf/` に置く案も採らない。worktree は `merged` が消し、`.ndf/` は利用者の
設定の置き場（C7）である。既存の 3 つの帳簿を実行の記録へ吸い込む案は、hook が核の外にある（要求の「含まない」）ため
`ask.jsonl` を移せず、帳簿の読み手（見積・使用量の集計）もすべて書き直すことになる。

根拠: Value 6 / Value 7（MVV 版 3）

### 決定 7: 持ち主の鍵を入力から作れるよう、核の順を入力の解決 → 記録の始まり → 持ち主の記録にする（E2 → E3 → E4）

持ち主の鍵（例 `cross-refactoring:pr={pr}`）は解決した入力から作るため、持ち主の記録は入力の解決の後にしか取れない。
入力の解決はファイルも状態も書かない処理にし、失敗しても残骸が無い。記録の置き場はリポジトリから決まるため、
リポジトリの根が解決できないときは `runs/_unresolved/` へ書く。

持ち主の記録を先に取る案は採らない。鍵を決める値（PR・課題の番号）がまだ無く、リポジトリ全体の鍵で取ると
並行する別の PR の実行を止める。

根拠: Value 6（MVV 版 3）

### 決定 8: 入口の呼び方の変更で利用者の手を止めないよう、旧い引数名は公開の入口だけ次の正式版まで受け、内部の呼び方は同じ Pull Request で直す（受け入れ条件 D5）

入力の宣言の `aliases` が旧い名前を受け、使われたら実行の記録へ `diag` を書く。`public: true`（利用者が直に呼ぶ）の入口は、
旧い名前を受けた版の次の正式版で外す。それ以外の入口は、呼ぶ側（Skill の本文・プランの雛形・他の入口）が同じプラグインの中に
あるため、同じ Pull Request で呼ぶ側を直し、旧い名前を受けない。状態ファイルの形は移行関数で 2 つ後の正式版まで読む。
引数の旧い名前の表は `legacy_names.py` の書き換えを入力の部品へ取り込み、名前の対応表 1 つにする。

すべての入口で旧い名前を期限なく受ける案は採らない。別名が残り続け、名前の対応表の検査（受け入れ条件 10a）が
いつまでも空にならない。旧い名前を一切受けない案は、版の上げの最中に動いているループ（前の版のプランと状態）を止める。

根拠: Value 2 / Value 8（MVV 版 3）

### 決定 9: 起動の増分を測れる上限に収めるため、上限を 150 ms に置き、DBOS は再開と耐久の入口でだけ読む

部品の import の中央値（10 回）は、`step_result` だけで 35 ms、核が常に使う部品（`jsonio`・`clock`・`locks`・`schema`・`waits`）を
足して 164 ms、`durable` を足すと 550 ms だった。常に読む部品の増分は 129 ms で、上限 150 ms に収まる。`durable` は
`resume: true` の入口だけが核の中で遅れて読む。

上限を置かずに P1 で測るだけにする案は採らない。要求が上限の値を設計に置くことを求め、超えたときに何を直すかが決まらない。

根拠: Value 3 / Value 10（MVV 版 3）

### 決定 10: A〜F の課題が別のループで 1 件ずつ直されないよう、103 件を属する柱のマイルストーン（28〜30）へ移す

柱の子の課題を柱と同じマイルストーンに置き、ループ `lroot` は柱だけを選ぶ（子は選定から外す）。マイルストーン 24・26・03・23 を
選ぶ他のループからは見えなくなる。進行中のスプリントの課題は、その閉じる処理の後に移す。

元のマイルストーンに残す案は採らない。前提 4（個別に直さない）を、選定の規則ではなく人の注意で守ることになる。

根拠: Value 4 / Value 10（MVV 版 3）

### 決定 11: 入口の本体を柱ごとに書き直さないよう、P1 がすべての入口を核へ移し、P2 以降は核の段と契約の行を足す

核の各段は契約の行が無ければ何もしない（`lease` が空なら持ち主を取らない、`refs` が無ければ解決しない）。P1 で入口の末尾を
`run_core.main` にそろえれば、P2〜P8 は核の段を足し、入口に残る重複（自前の再試行・持ち主・`argparse`・Markdown の読み取り）を
消すだけになる。柱は「核の段の Pull Request」と「部品ごとに入口を移す Pull Request」に分け、1 スプリントは 1 つの柱、
部品の Pull Request は 3 本までとする。部品の順は課題の集まる順（supervise → cross-refactoring → 課題を閉じる処理 → リリース →
外部 CLI の監視 → 使用量の帳簿 → 残り）。

型ごと（柱ごと）に全入口を 1 回ずつ書き直す案は採らない。1 本の入口を 8 回触り、柱の Pull Request が同じファイルで衝突する。
部品ごとに 8 つの型を一度に入れる案は採らない。核の段がそろうのを待つため、最初の部品が移るのがマイルストーン 30 の後になる。

根拠: Value 10 / Value 1（MVV 版 3）

### 決定 12: 例外リストが減る方向にしか動かないよう、既存の例外リストの置き場を使い、ベースブランチと比べて行の増加を落とす

例外リストは `scripts/script-structure-allow/` の 1 項目 1 ファイルをそのまま使い、新しい検査の種類（`core-entry`・`contract`・
`limit-literal`・`name-alias`・`argv`・`md-read`）の行を足す。構造チェックはベースブランチ（`.ndf/worktree.json` の `base_branch`）の
置き場と比べ、起点に既にあった種類で行が増えたら落とす。新しい種類を入れる Pull Request だけが、その種類の最初の行を足せる。

別の一覧のファイルを新しく作る案は採らない。同じ役割の一覧が 2 つになり、`unused-allow`（直した行を消し忘れると落ちる）を
もう一度書くことになる。

根拠: Value 6（MVV 版 3）

### 決定 13: 上限の値を 1 か所に置くため、`limits.py` の表を `contracts/limits.json` へ移し、`limits.py` は読み手にする

上限の宣言は方針の名前ごとに上限の秒・再試行の回数・待ちの間隔・同じ原因の上限を持つ。入口の契約は `limits` で方針の名前を指す。
`limits.py` の今の工程 × 担当の表と順序のチェック（無進捗の許容 < 監視の上限 < CLI の上限）は、宣言を読んで同じ判定をする。
同じ原因かどうかは、例外の型と、数字と時刻とパスを伏せた理由の文から作る原因の鍵で見る。

`limits.py` の Python の表に全部を足す案は採らない。契約の一覧と別の場所に上限が残り、入口の行から上限をたどれない。

根拠: Value 6 / Value 5（MVV 版 3）

### 決定 14: 再開の手段を 1 つにするため、`supervise.py resume <実行の識別子> [--from <ステップ>]` を唯一の再開の入口にする

`supervise.py run --from` と `queue --resume --from` は `resume` へ寄せ、旧い形は決定 8 の別名として次の正式版まで受ける。
`resume` は耐久の記録から位置を読み、`--from` があればその位置を上書きする。drive の `save_ds` などの再開の位置の手書きは
`durable-boundary` の検査が既に落としている。

入口ごとに `--from` を残す案は採らない。#2325 のように、入口ごとに `--from` と耐久の記録のどちらが勝つかが違う。

根拠: Value 6（MVV 版 3）

### 決定 15: 持ち主と排他を同じものにするため、持ち主の記録を `lease.py` が排他の中で読み書きし、置き場を状態の置き場の `leases/` に移す

`lease.acquire(key)` は `locks.exclusive(<鍵のファイル>)` の中で持ち主の記録を読み、生きた持ち主（pid と開始時刻が一致する）がいれば
宣言どおり待つか断り、死んでいれば片付けてから書く。返すときも排他の中で終わった時刻を書く。記録の形は `run_owner.py` の形
（実行の識別子・開始・最後に動いた時刻・終わった時刻・pid と開始時刻）を引き継ぐ。置き場は `leases/<リポジトリ>/<鍵>.json` で、
同じリポジトリの別の clone や worktree の実行どうしも取り合う。

状態のディレクトリの横に持ち主の記録を置く今の形は採らない。状態のディレクトリが worktree ごとにあるため、並行の衝突（F）を
同じリポジトリの単位で防げない。片付けの対象（`run_state` の掃除）は今の置き場のまま、持ち主の記録だけを移す。

根拠: Value 6（MVV 版 3）

### 決定 16: 受け入れ条件 9 の基準値を同じ手順で再現できるよう、分類の記録を P0 が 1 行 1 課題の JSON Lines で作り直す

`issues/issue-2335-classification.jsonl` に 194 件を 1 行ずつ（番号・主の型・従の型・理由の 1 文）書く。2026-11-01 の分類の記録は
リポジトリに無いため、本文の手順で分類し直す。割合が 82% と食い違えば基準値を差し替えずに要求へ戻す。

本文の 82% をそのまま基準にする案は採らない。30 日後の分類と同じ手順で比べられたことを示せない。

根拠: Value 3 / Value 7（MVV 版 3）
