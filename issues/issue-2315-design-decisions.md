# backlog-refinement の 3 つの深さ: 決定の記録（#2315）

[issue-2315-design.md](issue-2315-design.md) の「決定の記録」の節を分けたファイルである。

## 決定の記録

### 決定 1: Skill を増やさず同じ順位の基準を使うため、見直しと大整理を `backlog-refinement` の深さとして持たせる

見直しは今の扱う 5 つ（訂正・マイルストーン・やらない・ルートコーズ・順位付け）をそのまま使い、大整理はルートコーズの判断を課題の集まりへ広げたものである。別の Skill にすると、同じ区分と見積の段階と `apply` を 2 か所から呼ぶことになる。調査と大整理の手順は `references/research.md`・`overhaul.md` に置き、深さが `review`・`overhaul` のときだけ読む。利用者の「Skillを設定し」は `/ndf:backlog-refinement --depth overhaul` を入口とすることで満たすとみなす（2026-11-02 の承認ゲート 1 で利用者が承認した）。

調査だけ、または大整理だけを新しい Skill にする案は採らない。単独で呼びやすくなるが、manifests と frontmatter の規約に 1 つ増え、起票の上限と MVV 判定を 2 つの Skill で守ることになる。

根拠: Value 6（MVV 版 4）

### 決定 2: 既存の呼び出しが軽くなるよう、深さの指定が無いときは差分の棚卸しにする

今の呼び出し（まとめの `refine`・人の `/ndf:backlog-refinement`）は、受け入れ条件 1 と 24 のとおり差分の棚卸しで動けばよい。見直しを望む人は `--depth review` を付ける。無指定を今の全部の棚卸しにすると、まとめのステップの指示を書き換え忘れた呼び出しが重いまま残る。

無指定を今の扱う 5 つのままにする案は採らない。重さの原因がそのまま残り、受け入れ条件 17 を満たせない。

根拠: Value 1 / Value 10（MVV 版 4）

### 決定 3: 差分の棚卸しはマイルストーンを設定せず、マイルストーンの無い新しい課題は見直しで割り当てる

受け入れ条件 1 は差分の棚卸しの作業を 4 つに限り、マイルストーンの再編を見直しへ送る。新しく起票された課題がマイルストーンの無いまま最大 3 周回待つことになるが、開発ループは周回の中で起票した課題を次の周回まで選ばず（今の除外）、選べる課題が尽きる前に見直しが挟まる（決定 12）ため、着手が止まることはない。`no-milestone` と `closed-milestone` の経路は見直しの候補へ移る。

差分の棚卸しで新しい課題にだけマイルストーンを付ける案は採らない。どのマイルストーンへ入れるかは順位とマイルストーンの主題を見て決めるもので、全体を見ない回で決めると見直しのたびに付け直しが起きる。

根拠: Value 1（MVV 版 4）

### 決定 4: `--loop` の外でも同じ数え方になるよう、回数と溜まり具合を深さの記録から数える

`.ndf/backlog/depths.jsonl` に棚卸しのたびに 1 行を足し、前の見直し・大整理からの差分の棚卸しの回数・open の件数の推移・起票と完了の推移をここから数える。開発ループの記録はループの中にしか無く、ループを使わないプロジェクトでは数えられない。GitHub のマイルストーンや課題から数える案は、棚卸しの実行の時点が残らず、起動しなかった判定も残せない。

ループの記録（`loop.json`）だけから数える案は採らない。前提 1 の「スプリントの数で数える」を満たせない。

根拠: Value 5 / Value 7（MVV 版 4）

### 決定 5: 起動の判定をスクリプトが行うよう、大整理と見直しをまとめのプランの後ろに実行条件つきのプランとして置く

まとめの最後のステージに `refine`（差分）を置き、次のステージに大整理のプランと見直しのプランを置く。各プランの実行条件は `upkeep.py depth due overhaul|review` で、起動しないときは skip のコードでプランが飛ぶ。どちらも起動する周回では大整理を先に流す。組み直した後の課題で順位を付けるためである。

`refine` のステップの中で LLM が深さを決める案は採らない。判断の要らない回数の比較を LLM に任せることになり、判定の記録の形もそろわない。`loop lap` で決める案は、ループの外の進め方で働かない。

根拠: Value 4（MVV 版 4）

### 決定 6: #2342 を待たずに入れられるよう、持ち主を今の `run_owner` と `locks` の上に作り、寿命の窓を引数にする

`run_owner` は記録・最後に動いた時刻・終わった時刻を持ち、`locks` は錠を持つ。足りないのは窓の長さ（今は 24 時間の定数）と pid での生死の判定だけで、`alive` に窓を引数で渡す形へ変え、`pid`・`host` を記録に足す。どのホストでも最後に動いた時刻と寿命の窓を見て、同じホストではさらに pid の生死も見る（窓を過ぎたか pid が死んだら無効。別のホスト（同じメインディレクトリを共有する別のコンテナ）は窓だけで決める。不変条件 I2・受け入れ条件 9・9a）。窓の既定は 900 秒、生きている印の間隔は 120 秒（窓は印の 7.5 倍。`claude -p` の待ちが印の間隔を超えても、`run_ticking` の tick で印を書くため窓を短くできる）。#2342 が持ち主の部品（`lib/lease.py`）を入れたら、その鍵の 1 つへ移す。

#2342 を待つ案は採らない。#2342 はマイルストーン 28 の柱で、この課題（35）より先に終わる保証が無い。持ち主のための別の錠の部品を作る案は、同じ役割の部品を 2 つにする。

根拠: Value 6（MVV 版 4）

### 決定 7: 待ちの判断を LLM に持たせないため、待ち時間の調査はスクリプト（`upkeep.py research run`）が項目ごとに `claude -p` を起こす

conductor は `supervise.py wait` と並べて、`loop sprint` が返す `metrics.research` の 1 行を背景で起動する。スクリプトが持ち主を取り、空きと完了のファイルを見て、1 項目ずつ上限つきで `claude -p` を起こし、出典と日時のそろった結果だけを書く。止め方・空きの判定・上限・記録の形はすべてスクリプトが持ち、LLM は 1 項目の調べと要約だけを担う。

conductor が `ndf:supervisor` を立てて調査を回す案は採らない。止める時点と空きの判定を LLM が持つことになる。`supervise.py wait` が待ちの間に調査を流す案は、多くの工程が使う待ちの入口に調査の責務を混ぜ、待ちの終わり方が調査の失敗に左右される。

根拠: Value 4 / Value 10（MVV 版 4）

### 決定 8: 起票の上限と持ち主の照合を 1 か所で守るため、課題の一覧への書き込みを `apply` 1 つに寄せる

ニーズ・シーズ・大方針の起票は `apply` の `create`、付け直しは `reparent` で行う。`apply` が深さ・持ち主の実行の識別子・件数の上限・出典と MVV の当たる所とラベルの有無・付け直しの前の状態を確かめる。既存の `apply` は照合・やり直しで 2 度書かない・書き込みの制限の待ち方をすでに持つ。

LLM が `gh issue create` と `gh api` を直接打つ案は採らない。上限と持ち主の照合を手順の文で頼むことになり、守れているかを検査できない。

根拠: Value 4 / Value 6（MVV 版 4）

### 決定 9: 利用者のデータを宣言の範囲の外へ出さないため、利用の記録はスクリプトが宣言のコマンドを打ち、マスクを通した集計値だけを LLM へ渡す

`needs.usage` の行は `aggregate_only: true`・期間・マスクの正規表現を持つときだけ読み、出力に `mask` と `secret_redact` を当ててから調査の supervisor へ渡す。調査の supervisor は利用の記録の読み先へ自分でつながない。宣言が無いプロジェクトでは利用の記録を何も読まない（前提 6）。この既定は 2026-11-02 の承認ゲート 1 で利用者が承認した。

調査の supervisor が宣言を読んで自分でコマンドを打つ案は採らない。範囲の外を読まないことを手順の文でしか保てない。宣言が無いときに集計値だけ読む案は、何が集計値かをプロジェクトごとに機械で決められない。

根拠: C1 / C3 / Value 5（MVV 版 4）

### 決定 10: 足しすぎを防ぐため、1 回の見直しの起票の上限を既定 5 にし、MVV 判定が従う以外の課題に `needs-decision` を付ける

周回 1 回で選ぶ課題は 2〜3 件（l20261031 の周回 1〜4）で、見直しの 3 周回の間に着手する件数は 6〜9 件である。起票を 5 件までにすると、見直しの回の起票が間の着手を上回らない。MVV 判定は `project-mvv.py vet` に種類 `issue` を足して行う。従う以外の課題に既存の `needs-decision` を付けると、順位付け（`rank` の `waiting_decision`）と開発ループの選定がすでにその課題を外すため、新しい除外の仕組みが要らない。

新しいラベル（「判定待ち」など）を作る案は採らない。選定と順位付けに同じ除外をもう 1 つ足すことになる。承認ゲートの MVV 判定（`mvv-gate.py`）を使う案は、承認ゲートを省いた記録を書く入口で、課題の判定の記録と混ざる。

根拠: Value 10 / Value 6（MVV 版 4）

### 決定 11: 見直しが一覧の全体に追いつくよう、見直しは候補の上限で切らず、費用と秒の上限で止めて古い順に持ち越す

見直しの候補は後回しを除く open の全件で、`--limit` を効かせない。代わりに見直しのステップに `review.usd`（既定 6 ドル）と `review.seconds`（既定 1800 秒）を置き、当たったら手順 2A を止めて、最後に見直した時刻の古い順で残りを持ち越す。次の見直しは持ち越しから始まるため、何回かの見直しで全件を一巡する。6 ドルは今の毎周回の棚卸しの 3 周回分（4.23〜4.83 ドル）より少し上に置いた値で、差分の棚卸しが軽くなった分と合わせて、最初の 3 回の見直しの実測で見直す。

候補の上限 10 件のまま見直しを回す案は採らない。周回 4 の持ち越し約 160 件は、10 件ずつでは追いつかないことを示している。

根拠: Value 10 / Value 3（MVV 版 4）

### 決定 12: 選べる課題が尽きても調査からの起票を試すため、`no_issue` の前に見直しを 1 回だけ挟む

`loop select` が候補 0 件に当たったとき、前の周回を締めてから見直しが走っていなければ、止まらずに `review_first` を返し、見直しのプラン（`trigger: no_issue`）を流して選定をやり直すコマンドを `next` に置く。見直しの後も 0 件なら今までどおり `no_issue` で止まる。1 回だけにするのは、起票が MVV 判定で `needs-decision` に回り続けると、見直しと選定の間を回り続けるためである。

選定のたびに見直しを先に流す案は採らない。課題があるときの周回が見直しの費用を毎回払う。

根拠: Vision / Value 2（MVV 版 4）

### 決定 13: 溜まり具合の閾値は、今の 1 本のループの値から置き、最初の 3 回の見直しで見直す

見直しは open が前の見直しから 30% 増えたとき、または持ち越しが候補の上限の 10 倍を超えたときにも起動する。周回 4 の持ち越し約 160 件は上限 10 の 16 倍で、この条件に当たる。大整理は、見直しの記録で起票が完了を上回る・open が増える状態が 3 回の見直しで続いたとき、または 1 つの原因の型が不具合（`cause_types` で `defect: false` の型を除いた課題）の 30% を超えたときにも起動する。#2335 の 2026-11-01 の分類では、最も多い A（失敗の判定）が 39 件で不具合 125 件の 31% だった。30% はこの状態で起動する値である。型の割合は、見直しが新しく起票された課題に付けた型（`.ndf/backlog/causes.jsonl`）から数える。

閾値を置かず回数だけで起動する案は採らない。課題が溢れても次の回まで待つことになる。

根拠: Value 3（MVV 版 4）

### 決定 14: 材料は人が書く値として `.ndf/project.json` の `materials` に置き、頻度と上限は `.ndf/backlog.json` の `depths` に置く

材料の宣言は `project-analysis` の 3 手（measure → 答え → write）で案を出し、`write` は手で書いた値を変えない規則をすでに持つ。頻度・閾値・件数の上限・寿命の窓は棚卸しの設定で、今の `candidate_limit`・`quality` と同じ `backlog.json` に置く。

材料を新しいファイル（`.ndf/discovery.json` など）に置く案は採らない。解析の 3 手と手の値を保つ規則を、もう 1 つのファイルのために作り直すことになる。頻度も `project.json` に置く案は、解析が書く宣言と棚卸しの調整の値を混ぜる。

根拠: Value 5 / Value 6（MVV 版 4）

### 決定 15: 調べる依存を絞るため、ライブラリの変化と競合は `seeds.libraries` に宣言したものだけを調べる

`project-decl.py measure` は直接の依存から候補を出し、人が残したものだけが調べる対象になる。各行は変化（新しい版・非推奨・保守の停止・脆弱性・ライセンス）と競合（`alternatives` と比べる観点）の 2 つの調査の項目になる。

直接の依存をすべて調べる案は採らない。依存の数に比例して調査の費用が増え、主要でない依存の項目が見直しを占める。

根拠: Value 10 / Value 5（MVV 版 4）

### 決定 16: 付け直しを戻せるよう、`apply` が最初の書き込みの前に対象の全件の前の状態を書き、戻しを 1 つのコマンドにする

`before.json` は課題ごとの親とマイルストーンを持ち、`apply` は書き終えてから `reparent` の最初の書き込みに入る。途中で失敗したら結果に `revert_command`（`upkeep.py revert --run <実行>`）を載せる。戻しは記録の値へ親とマイルストーンを書き戻し、戻せなかった番号を一覧で返す。

付け直しの度に 1 件ずつ前の状態を書く案は採らない。書き込みの途中で落ちると、前の状態の無い課題が残る。

根拠: C4 / Value 1（MVV 版 4）

### 決定 17: 受け入れ条件 22 の入力をリポジトリに固定するため、2026-11-01 時点の未完了の一覧を作り直して試験のデータにする

#2335 の分類の記録はリポジトリに無い。2026-11-01T04:23Z 時点で open だった課題を `createdAt`・`closedAt` から作り直し、題名・ラベル・マイルストーン・本文の先頭 2500 字を `tests/fixtures/overhaul-20261101.json` に置く。`count` の値は試験で縛り、分類・柱・付け直しの一覧は手動確認で #2335 と比べて差を報告に書く。

分類まで固定して試験で一致を求める案は採らない。分類は LLM の判断で、同じ入力から同じ文字列は返らない。

根拠: Value 3 / Value 7（MVV 版 4）
