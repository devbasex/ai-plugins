# #1453: relay: アカウントを使用率でなく残りの量（倍率 ×（1 − 利用率））で選ぶ

正は課題の本文（#1453）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 依頼（原文）

> ## 背景
>
> relay.py（`lib/claude_accounts.py` の `choose`）は、アカウントを**使用率**（`five_hour` と `seven_day` の `utilization` の大きい方、`Usage.score`）の低い順に選ぶ。アカウントごとに容量が違う（Max 20x・Max 5x・Team）ため、使用率が同じでも残っている量は違う。容量の大きいアカウントに余りがあっても、使用率が少し低い小さいアカウントへ切り替わる。
>
> 容量の逆算は `issues/relay-capacity-estimate-2026-09-28.md` にある（5 時間の枠は 20x : 5x ≒ 4.0 で公式の比と一致。週の枠は 20x ≒ 1,100 USD、5x と Team は未確定）。
>
> あわせて、残量の読み取りに不具合が 2 つある。
>
> 1. **`limits[].weekly_scoped`（モデル別の週の枠。例: Fable）を読まない。** ohama では Fable の週の枠が 58% で、全体の週の枠（38%）より先に尽きる
> 2. **支出上限の超過を見逃す。** `spend.percent` が 100・severity が critical でも、`spend_limit_reached` が偽のままで返る事例がある。`spend_limit_reached` だけを見ているため、上限に達したアカウントを選びうる
>
> ## 要求
>
> - アカウントを**残りの量**で選ぶ。残りの量 = 倍率 ×（1 − 効いている利用率）
>   - 効いている利用率: 5 時間の枠・週の枠・モデル別の週の枠（`weekly_scoped`）のうち、そのアカウントを止める側の値
>   - 倍率は資格情報の `rateLimitTier` から対応表で決める。**週の枠は 5 時間の枠と別の表**にする（利用者の決定 B）
>   - 対応表の値はアカウントの宣言で上書きできる（未確定の 5x・Team の週の枠を実測で置き換えるため）
> - 比べる単位は API 料金の換算額（USD）とし、表の既定値は `issues/relay-capacity-estimate-2026-09-28.md` の結論から取る
>   - 5 時間の枠: 公式の Pro 比（Max 5x = 5・Max 20x = 20・Team premium = 6.25。Team の個人の tier が `default_claude_max_5x` ならその値）
>   - 週の枠: 20x ≒ 1,100 USD を基準に、5x と Team は非公式の比（1 : 3.5 : 6）から仮置きする
> - 不具合 2 つを直す（`weekly_scoped` を読む／`spend.percent` ≥ 100 か severity critical を支出上限の到達として扱う）
> - 残量が読めない・tier が表に無いときは、今の振る舞い（使用率で選ぶ）へ戻る。止めない
>
> （原文の受け入れ条件 AC1〜AC8・範囲・進め方は、下の各節へ語を揃えて引き継いだ。原文の「利用率」は用語集の「使用率」と同じ量である）

## 目的

- 登録済みアカウントの枠の大きさ（Max 20x・Max 5x・Team）の違いを選び方に入れ、枠の大きいアカウントに余りがあるのに小さいアカウントへ切り替わることを無くす
- 使用量の応答のうち読み落としている 2 つ（モデル別の週の枠・支出上限の到達）を読み、尽きかけた・上限に達したアカウントを選ばないようにする

## 前提

- 前提 1: 残りの量は枠ごとに「枠の大きさ ×（1 − 使用率 / 100）」で求め、アカウントの残りの量はそのうち最も小さい値とする。原文の「効いている使用率」は、この最小を与える枠の使用率を指す（5 時間の枠と週の枠で枠の大きさが違うため、使用率の大きい方が止める側とは限らない）
- 前提 2: 枠の大きさの単位は API 料金の換算額（USD）で、5 時間の枠と週の枠を同じ単位で比べる。既定値は `issues/relay-capacity-estimate-2026-09-28.md` から次のとおり導く（値の丸めは設計が決める）

  | `rateLimitTier` | 5 時間の枠（USD） | 週の枠（USD） | 根拠 |
  | --- | ---: | ---: | --- |
  | `default_claude_max_20x` | 210 | 1,100 | 実測（5 時間の枠は観測 7 点、週の枠は上限の事例 W3） |
  | `default_claude_max_5x` | 52.5（= 210 × 5 / 20） | 約 640（= 1,100 × 3.5 / 6） | 5 時間の枠は公式の比と実測（S2〜S4 の 49〜55 USD）、週の枠は非公式の比による仮置き |

  Team premium の tier の文字列は手元に実物が無い（手元の Team のアカウントの tier は `default_claude_max_5x`）。文字列が分かるまで表に載せず、下の前提 5 の扱いにする
- 前提 3: モデル別の週の枠（`limits[]` の `kind` が `weekly_scoped` のもの）の枠の大きさは、同じアカウントの週の枠と同じ値とする。使用率が 100 以上なら、その `resets_at` まで上限に達したとして扱う。relay は子がどのモデルを使うかを選ぶ時点で知らないため、安全側に倒す
- 前提 4: 切り替えの閾値（`NDF_ACCOUNT_SWITCH_AT`、既定 90%）は今のアカウントの**使用率**のまま比べる。その使用率にモデル別の週の枠を含める。変えるのは「どのアカウントへ替えるか」と「候補が今のアカウントより良いか」の比べ方だけである
- 前提 5: 枠の大きさの分からないアカウント（tier が表に無く、宣言も無い）は、残りの量を持つアカウントより後に並べ、その中では今の規則（使用率の小さい順）で並べる。残量の読めないアカウントの扱い（読める候補が無いときだけ候補にする）は今のまま変えない
- 前提 6: 枠の大きさの宣言は登録済みアカウントごとにアカウントの置き場へ持ち、プロセス・コンテナをまたいで効く。宣言を書く手段（コマンドを足すか、`account.json` を手で書くか）は設計が決める
- 前提 7: `rateLimitTier` はアカウントの置き場の `.credentials.json`（`claudeAiOauth.rateLimitTier`）から読む。トークンの更新はこの値を残す（`refresh_oauth` は元の辞書を写して上書きする）
- 前提 8: 使用量の取得先の呼び出しの回数・間隔は変えない（1 アカウントにつき `NDF_ACCOUNT_CHECK_INTERVAL` 秒に 1 回まで）

## 対象範囲

含む:
- 使用量の応答から `limits[]` の `weekly_scoped` と `spend.percent`・`spend.severity` を読み、保存した残量（`usage.json`）に残す
- 支出上限の到達の判定に `spend.percent` ≥ 100 と `spend.severity` = `critical` を加える
- 枠の大きさの対応表（5 時間の枠・週の枠の 2 つ）、アカウントごとの宣言による上書き、残りの量の計算
- `choose` の並べ方と、区間の起動で「候補が今のアカウントより良いか」を比べる箇所を残りの量へ替える
- `relay.py account list`（表と `--json`）へ枠の大きさと残りの量を出す
- 上のテスト

含まない:
- 残量の絶対値を返す API を使うこと（応答の `remaining_dollars` は null で、使えない）
- 使用量の観測を積んで枠の大きさを自動で学習すること
- 切り替えの閾値の意味を使用率から残りの量へ替えること（前提 4）
- 子の使うモデルに応じてモデル別の週の枠を効かせる・外すこと（前提 3）
- `lib/claude_usage.py`・`lib/claude_accounts.py`・`relay.py` の `account` の出力の外（`supervise.py` の呼び出し方・中継の画面の文言）の変更。`choose` の返り値の形が変わっても、呼び出し元の振る舞いは変えない

## 用語

| 用語 | 意味 |
| --- | --- |
| 残りの量 | 登録済みアカウントが上限に達するまでに使える量の見積り。枠ごとの「枠の大きさ ×（1 − 使用率 / 100）」の最小（USD 換算） |
| 枠の大きさ | 1 つの枠（5 時間の枠・週の枠・モデル別の週の枠）が 0% から 100% になるまでに使える量（USD 換算）。原文の「倍率」。支出上限（追加利用の上限額）とは別の量である。tier と枠から対応表で決まり、宣言で上書きできる |
| 枠の大きさの対応表 | `rateLimitTier` から枠ごとの枠の大きさを引く表。5 時間の枠と週の枠で別に持つ |
| モデル別の週の枠 | 使用量の応答の `limits[]` のうち `kind` が `weekly_scoped` のもの。特定のモデル（例: Fable）だけの週の上限 |

## 受け入れ条件

- [ ] AC1: 前提: 5 時間の枠の使用率が Max 5x のアカウントで 40%、Max 20x のアカウントで 50%、週の枠はどちらも 0%。操作: `choose` を呼ぶ。結果: Max 20x のアカウントを選ぶ（残りの量 52.5 × 0.6 = 31.5 < 210 × 0.5 = 105）
- [ ] AC2: 週の枠の大きさが 5 時間の枠と別の表から引かれる。表を差し替えたテストで、週の枠の大きさだけを変えると選ぶアカウントが入れ替わる
- [ ] AC3: アカウントの宣言で枠の大きさを上書きすると、残りの量がその値で計算される（`account list --json` の残りの量が宣言の値 ×（1 − 使用率 / 100）になる）
- [ ] AC4: `limits[]` に `weekly_scoped` があり、その使用率が週の枠より高いとき、その枠が残りの量を決める。あわせて `Usage.score()`（切り替えの閾値と比べる使用率）にもその値が入る
- [ ] AC5: `spend.percent` が 100 以上か `spend.severity` が `critical` のアカウントは、`extra_usage.spend_limit_reached` が偽でも支出上限に達したとして選ばず、一覧の状態は「支出上限」になる（2026-09-28 の nyle-team の応答の形をテストに使う）
- [ ] AC6: 枠の大きさの分からないアカウント・残量の読めないアカウントが混ざっても `choose` は例外を出さずに 1 つを選ぶか、今どおり候補無しを返す。枠の大きさの分からないアカウントは前提 5 の順に並ぶ
- [ ] AC7: `relay.py account list` の表と `--json` で、アカウントごとに 5 時間の枠と週の枠の大きさ・残りの量が読める（不明は表で `-`、JSON で null）
- [ ] AC8: 区間の起動で今のアカウントが使えて閾値を超えているとき、候補の残りの量が今のアカウントの残りの量以下なら替えない（今の「候補の使用率が今以上なら替えない」を残りの量で置き換える）
- [ ] AC9: 退行しない: `limits[]`・`spend` の無い応答（今までの形）でも残量を読め、枠の大きさの分かるアカウントどうしの選び方と既存のテスト（`plugins/ndf/scripts/tests/` の relay・accounts の関係）がすべて通る
- [ ] AC10（リリース後テスト）: 実物の 2 アカウント（nyle-personal・ohama-personal）で `relay.py account list` を打ち、残りの量の大小が `issues/relay-capacity-estimate-2026-09-28.md` の比（5 時間の枠 20x : 5x ≒ 4.0）と使用率から計算した値と矛盾しない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | 枠の大きさ・残りの量が求まらないことを理由に、選ぶ・一覧を出す・中継を続ける処理を止めない（E3・E4 の失敗の経路） |
| 性能・拡張性 | 使用量の取得先を呼ぶ回数を増やさない（前提 8）。選び方と判定に LLM を呼ばない |
