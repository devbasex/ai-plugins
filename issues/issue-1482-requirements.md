## 目的

- `cross-refactoring` が「取り消した」と報告した改善項目のコミットが、Pull Request へ push されない状態にする
- 取り消しを何度くり返しても、作業ディレクトリの履歴が取り消しの回数に比例して伸びない状態にする
- 積み直しの衝突で取り消しを広げる範囲を、`CLAUDE.md` の取り決め（衝突した項目と同じファイルを触った項目まで）に収める

## 今のコードで分かっていること

- **取り消しの範囲は毎回、起点（`plan.base_sha`）から HEAD までの全コミットである**（`undo.py` の `drop` → `commits_in_range`）。前の取り消しが作った revert と積み直しのコミットも範囲に入り、取り消しのたびに逆再生の対象が約 2 倍になる。#1399 の 54 → 121 → 254 → 518 → 1043 と #1237 の 5 → 12 → 25 はこの増え方と合う
- **積み直しの衝突の 3 段目 `all` は、起点より後の改善項目をすべて取り消す**（`_replay_without_dropped`）。`CLAUDE.md` の取り決め（同じファイルまで）より広い
- **「どの項目にも属さないコミット」の検査は、実装のマージ処理（`merge-implement` の `_group_by_item`）の時点にだけある。** `publish.py` の `push_head` は生成物を同期して `HEAD` を push するだけで、マージ処理の後に増えたコミットを照合しない
- **取り消しを行う経路が 4 つに分かれている。** `undo.drop`（改善項目の単位）、`intake.discard_unverified`（結果を残さなかった起動の範囲）、`converge._apply_fix_result`（手順を外れた修正の範囲。`revert_range` を直接呼ぶ）、最終ゲート修正のマージ処理。どのコミットを取り消し・残し・公開するかを、それぞれが別に決めている
- **push は最終ゲートより前にも起きる。** 実装のマージ処理の終わり（`implement._finish`）、結果なしの起動を閉じたとき（`intake.close_without_result`）、修正のマージ処理（`cmd_merge_fix`）、やり残しの反映（`flush_pending_push`）がそれぞれ `pending_push` を見て push する

## 前提

- 前提 1: **最終ゲートより前には push しない。** 公開は、検証（`verify`）を終えて最終ゲートへ入る時点の 1 回にまとめる。最終ゲートの後（CI で見るテストの戦略で CI を動かす push、最終ゲート修正と寄せた危険フラグの取り消しを反映する push）は今の回数のまま残す。最終ゲートは push 済みの地点を判定するためである
- 前提 2: **push の直前の照合で、公開してよくないコミットを見つけたら、push をせずに中断する**（終了コード 4。該当のコミットの SHA・`Item-Id`・件名を出力に並べる）。その場で取り消して push し直す形にはしない。見放した担当のプロセスが生きている疑いがあり、取り消した後にまたコミットされうるためである
- 前提 3: **公開してよいコミットは次の 2 種類だけである。** (a) 取り消されていない改善項目（`status` が `LIVE`）に記録されたコミット、(b) オーケストレーターが自分で作ったコミット（取り消し・積み直し・生成物の同期・リファクタリング計画の記録）。(b) を見分ける手段（状態ファイルへの記録か、コミットのトレーラーか）は設計が決める
- 前提 4: **積み直しの衝突で、同じファイルを触った項目まで広げても衝突が残ったときは、全件へ広げずに、取り消しの前の HEAD へ戻して中断する**（終了コード 4）。前提 1 により中断した時点の変更は Pull Request へ出ていない
- 前提 5: **取り消しでコミット数を抑えるために、push 済みの履歴を書き換えない**（`--force` を使わない。共通原則 C4）。push 前の手元の履歴をどう組み直すか（`reset` して積み直すか、項目のコミットだけを revert するか）は設計が決める
- 前提 6: 取り消しの判定は `cross-refactoring` の中に置く。`cross-review` は取り消しと積み直しを持たないため対象にしない

## 用語

| 用語 | 意味 |
| --- | --- |
| 取り消しの判定 | 改善項目ごとに「取り消したか」と、起点から HEAD までの各コミットが「公開してよいか・積み直すか」を 1 か所で決める処理。取り消しの 4 つの経路と push の直前の照合が同じものを呼ぶ |
| 残留コミット | 見放した（STALLED・結果なし）担当のプロセスが、オーケストレーターの判定の後に積んだコミット |
| 途中の push | 最終ゲートへ入るより前の push |
