# #4102: 止めた前の起動の Stop が遅れて書いた次のセグメントのマーカーを、ラッパーが今の起動のものとして読まない

正は課題 #4102 の本文で、この文書はその写しである。本文から作り直す。手で直さない。

中継のラッパーが子を止めて起動し直した後、止めた前の起動の Stop の hook が遅れて次のセグメントのマーカーを書いても、ラッパーがそれを今の起動のマーカーとして読まず、今の起動のマーカーを上書きもしないようにする。止める前にラッパーが読んだマーカーの扱いは今のとおり残す。

## 何が起きたか

2026-11-22、#4061・#4062・#4064 の設計（ https://github.com/devbasex/ai-plugins/pull/4095 ）で、中継へ書く hook を `signals.relay_role` で子の会話だけに絞る中で、範囲の外として見つけた。止めた前の起動の hook を見分ける起動の ID（`NDF_RELAY_LAUNCH`・`launch.json`。#3814）は、質問のファイル（`question.json`）と #4049 の背景の作業の記録（`busy-<起動>.json`）には効くが、次のセグメントのマーカー（`next.json`）には効かない。#4061 の設計は「データ構造」の「止めた前の起動への保証」の表で、`next.json` を「照らさない。変えない」とし、この課題へ分けた。

## 種類

不具合の修正。ラッパーの見回りは「今のセグメントのセッションが書いた次のセグメントのマーカー」だけで切り替える約束である（`wrapper.py` の `_next_mark`）。止めた前の起動が止めた後に書いたマーカーは今のセグメントのものでないが、その約束を守れていない。

## 今の姿

2026-11-22 に main の `428f91f9e` で読んで確かめた（パスは `plugins/ndf/src/ndf/domains/` からの相対）。

| 部品 | 今の振る舞い | 場所 |
| --- | --- | --- |
| マーカーを書く | Stop の hook（guard `relay-marker`）が、最後の応答に次のセグメントのブロックがあれば `next.json` を書く。中身は会話の ID（`session_id`）・ブロック・最初に書いた時刻（`first_written_at`）など。起動の ID は持たない。前の中身があれば、書き手に依らず `first_written_at` を引き継ぐ | `hooks/guards/relay_mark.py`・`relay/signals.py` の `write_next` |
| マーカーを読む | ラッパーは見回りごとに `next.json` を読み、会話の ID が今のセグメントと違えば消して読まない（記録の行 `stale_next`）。同じなら今のセグメントのマーカーとして切り替えの判定へ渡す | `relay/wrapper.py` の `_next_mark` |
| 子を止める | ラッパーは質問のロックを持ったまま子を強制終了し、今の起動の記録（`launch.json`）を外す。新しいセッションへ切り替える手（`switch`）は止めた後に `next.json` を消す。同じ会話を `--resume` で起動し直す手（`account`・`restart`・`handover`）は消さない | `relay/wrapper.py` の `_stop_if_clear`・`_on_switch`・`_on_resume`・`_on_handover` |
| 起動の ID | ラッパーは子を起動するたびに新しい起動の ID を作り、`launch.json` に書いて子へ `NDF_RELAY_LAUNCH` で渡す。質問のファイルは、書く・消す hook がロックの中でこれを照らす | `relay/wrapper.py` の `_start`・`relay/signals.py` の `write_question`・`drop_question` |

## 事象

止めた前の起動 L1 の Stop の hook が、ラッパーが次の起動 L2 を記録した後に遅れて書くと、書き込みは通り、会話の ID だけを持つマーカーが残る。

```console
$ PYTHONPATH=plugins/ndf/src .venv/bin/python repro.py <一時ディレクトリ>
write_next の返り: True
next.json: {"session_id": "S", "block": "/goal 止めた前の起動のブロック", "goal_active": false, "first_written_at": "2026-11-22T13:09:55+00:00", "written_at": "2026-11-22T13:09:55+00:00"}
```

`repro.py` は `signals.set_launch(d, "L2")` の後に `signals.write_next(d, "S", "/goal 止めた前の起動のブロック", False, 0.1)` を呼び、`signals.read_next(d)` を出すだけの 9 行である。`--resume` で起動し直した L2 の会話の ID も S なので、ラッパーの `_next_mark` はこのマーカーを今のセグメントのものとして読む。

## 期待する結果

止めた前の起動が止めた後に書いたマーカーは、ラッパーの切り替えの判定に入らず、今の起動のマーカーを上書きしない。

## 再現手順

1. ラッパーの保存先のディレクトリで、今の起動の記録を L2 にする（`signals.set_launch(d, "L2")`。ラッパーが子 L1 を止めて L2 を起動した後の状態）
2. L1 の Stop の hook の代わりに、会話の ID S で `signals.write_next` を呼ぶ
3. `signals.read_next` が L1 のブロックを返し、会話の ID S で動くラッパーの `_next_mark` が捨てない

## 環境

- NDF 11.0.15（main の `428f91f9e`）
- 中継のラッパー（`ndf relay run`）の下の Claude Code の子。Codex は中継のラッパーが包まないので当たらない

## なぜ困るか

ラッパーは止めた前の起動のブロックで、今の子 L2 を止めて次のセグメントへ切り替える。L2 が引継ぎを書いている最中でも、L2 が書いた新しいブロックを L1 の遅れた書き込みが上書きしても、静かな時間を待った後に古いブロックで次のセグメントが始まる。前の中身の `first_written_at` を書き手に依らず引き継ぐので、L2 のマーカーが L1 の時刻を持ち、静かな時間を待たずに切り替わることもある。

## 目的

次のセグメントのマーカーを、書いた起動のものとして持ち、ラッパーが今の起動のマーカーだけで切り替える。質問のファイルと背景の作業の記録と同じく、止めた前の起動の遅れた hook が今の子の切り替えを動かさない状態にする。

## 対象範囲

含む:

- 次のセグメントのマーカーの持ち方（ファイルの名前と中身）と、書く関数・読む関数（`relay/signals.py`）
- Stop の hook の guard `relay-marker` がマーカーを書く経路（`hooks/guards/relay_mark.py`）
- ラッパーがマーカーを読む・消す・同じ会話の起動し直しへ引き継ぐ経路（`relay/wrapper.py`）
- 中継のファイルの契約（`contracts/domains/ndf-files.json` の `relay-next` の行）と生成文書、手順書（`development-workflow` の `references/relay.md`・`references/glossary.md`）と用語集の直し

含まない:

- 子の会話か入れ子の claude かの見分け（#4061 の `signals.relay_role`）。この課題は子の会話の hook の中で、どの起動の書き込みかだけを扱う
- 質問のファイルと背景の作業の記録の、止めた前の起動の扱い（#3814・#4049 のとおり）
- 切り替えの判定の順（`switch_decide.decide`）と、利用上限の画面とマーカーが同時にあるときに選ぶ手
- 子を止めるときに、止めた子の hook のプロセスまで止めること
- Codex（中継のラッパーは Claude Code だけを包む）

## 前提

- 前提 1: #4049 の実装の後に実装する。#4049 が起動ごとのファイル（`busy-<起動>.json`）の形・起動の ID の形の検査（`LAUNCH_ID_RE`）・ほかの起動のファイルを消す関数（`drop_other_busy`）を足す
- 前提 2: 止めた子の hook は、ラッパーが子の claude を強制終了した後も動きうる（#3814 の確定仕様 `docs/specifications/ndf-relay-pending-question-guard.md` が同じ前提で質問のファイルを守る）。この課題はその有無を実測せずに、動いても今の起動の切り替えに入らない形にする
- 前提 3: NDF は普及のフェーズの前で、中継のファイルの名前と中身を変えても互換の経路を持たない（MVV 版 11 の Value 4）。ラッパーと hook は同じプラグインの版で動く

## 受け入れ条件

- [ ] 1. 止めた前の起動（ラッパーが止めて今の起動から外した起動）の Stop の hook が止めた後に書いたマーカーは、ラッパーの切り替えの判定に入らない。同じ会話を `--resume` で起動し直した後（`account`・`restart`・`handover`）も、新しいセッションで次のセグメントを始めた後（`switch`）も同じ
- [ ] 2. 止めた前の起動の遅れた書き込みは、今の起動のマーカーを上書きせず、消さない。今の起動が書いたマーカーのブロックと最初に書いた時刻は変わらない
- [ ] 3. マーカーの最初に書いた時刻は、同じ起動のマーカーの前の中身からだけ引き継ぐ。ほかの起動のマーカー（止めた前の起動・前の実行の残り）からは引き継がない。例外は受け入れ条件 4 でラッパーが引き継いだマーカーで、引き継いだ時刻は起動し直した起動の後の Stop でも保たれる
- [ ] 4. ラッパーが子を止めた見回りで読んだマーカーは、今のとおり扱う。新しいセッションへの切り替えではそのブロックを次のセグメントの文にし、同じ会話の起動し直し（`account`）では起動し直した起動のマーカーとして最初に書いた時刻ごと引き継ぐ。止めるのを見送った見回りの読みと、止めた後の読み直しは引き継がない。ラッパーを起動した最初の `--resume` は何も引き継がない
- [ ] 5. 子の会話の Stop の hook は、起動の ID（`NDF_RELAY_LAUNCH`）が無いか形が違うときマーカーを書かない
- [ ] 6. ラッパーは子を起動する前に、見つけたほかの起動のマーカーを消す。消せなかったものと、消した後に止めた子が書いたものは残りうるが、どれも判定に入らない
- [ ] 7. 1〜6 を、マーカーを書く・読む関数、Stop の hook のエントリポイント、ラッパーの見回り（偽の子と起動の差し替え）で、ファイルの有無と中身・ラッパーが選んだ手と起動した引数で確かめるテストがある。受け入れ条件 1 は `account`・`restart`・`handover`・`switch` のそれぞれの後で確かめる。時間で区切らず、.md の文言を照らさない
