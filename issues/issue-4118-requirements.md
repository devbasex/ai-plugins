# #4118: 並列の計画: リレーの版が混在する間（旧版のハブ・頼む側）に、新しい版の一覧が旧版の起動を見落とさない（#4103 から分けた）

正は課題の本文（#4118）で、この文書はその写しである。本文から作り直す。手で直さない。

## 目的

- **今どうなっているか**: #4103 の設計（PR #4112）は、起動の券・起動の印で取り直しの起動の結果を確定させる。券と印は新しい版のハブと頼む側だけが知っている。プラグインの版を上げた直後は、券を知らない旧い版のハブ・旧い版の頼む側が、同じリレーの状態の保存先で動き続けることがある。この間に新しい版の一覧が旧版の起動を見落とすと、席を返して上限を超えて 2 本が動く
- **誰に効くか**: 版を上げた直後に並列の計画を動かしている利用者と、#4103 を実装する人
- **変えると何が成り立つか**: 版が混在する間も、新しい版の一覧は旧版の起動を不在と読まない。旧版の跡を照らし終えたら、新しい版だけの判定へ戻る。新しい版だけで動いている間の費用は増えない

## 種類

機能追加（#4103 の起動の券と起動の印を、版を上げた直後にも安全に有効にする前提。今のリレーハブは、旧い版のハブが動いているか・動いた跡があるかを見分ける手段を持たない）

## 今の姿

パスは `plugins/ndf/` からの相対で書く。#4103 は設計がマージ済みで、実装はまだである。

- **ハブは常駐せず、要求を書いた頼む側が兼ねる。** `ndf relay spawn`・`restart`・`stop` は要求を受付箱へ書き、自分の `drain` でハブの排他（`relay/hub/hub.lock`）を取りにいく。取れたら受付箱の要求を古い順に処理する（`src/ndf/domains/relay/hub.py` の `submit`・`drain`）
- **受付箱は版ごとに分かれ、ハブは自分の版の受付箱だけを読む。** 11.0.0〜11.0.11 は `requests/`、11.0.12〜11.0.15 は `requests-v2/`、#4103 の後は `requests-v3/` である。排他の `hub.lock` は全部の版で共通である（各版のタグの `hub.py` で確かめた）
- **旧版のハブの跡は消えうる。** ハブは記録（`hub-log.jsonl`）を処理の後に書く。旧版のハブがセッションを作った後・記録を書く前に落ち、頼む側が待ち切れで要求を消すと、要求も記録も残らない（`hub.py` の `submit`・`drain`）
- **旧版のハブは、新しい版の起動の途中を数えない。** 旧版の上限の判定は、動いているラッパーの錠（と置き換えの `held`）だけを数え、券と印を読まない（`hub.py` の `_over_cap`）
- **旧版の頼む側の置き換え（`requests-v2` の `replace`）は、親の `admit.lock` を根拠に `held` を載せるが、ハブはその錠が今も持たれているかを確かめる手段を持たない**

## 対象範囲

含む（PR #4112 の `issues/issue-4103-design.md` の決定 6 のうち、次の部分。指摘は PR #4112 の cross-review のラウンド 2 の r2-6〜r2-10）:

- 旧版のハブの検出: 処理中のハブの版を確実に決める方式（r2-6）
- 旧版のハブの痕跡: 完了の記録を書く前に落ちた旧版の実行も照合の対象にするか、旧版が処理できる間は不在の確定を保留する条件（r2-7）
- 照合を確定できない間の起動の扱い: 上限に関わる起動を保留し、停止は処理できる分岐（r2-8）
- 旧版の頼む側の置き換え（`requests-v2` の `replace`）を通す条件と、排他の生存を確かめられないときの扱い（r2-9）
- 照合済みの位置の記録方式: 新しい版の行だけの範囲を読み飛ばせて、処理量が累積の要求数に比例しないこと（r2-10）
- 一覧を「読めない」（`legacy: true`）にする条件と、新しい版へ戻る条件

含まない:

- 起動の券・起動の印・一覧の「起動の途中」そのもの、手動の `relay restart` との直列化、期限を越えた続きの手（#4103）
- 子の `bin/ndf` の版の対応を券を取る前に確かめること（`relay-protocol.json` の `inbox`）と、券つきの要求を `requests-v3` へ分けること。この 2 つは #4103 が持つ
- #4091 だけを実装した状態の席の返却（T2）の排他と不在の確かめ（#4110）

## 受け入れ条件

- [ ] 1. 旧版のハブが処理中の間、新しい版の一覧はその起動を不在と読まず、席を返さない（テスト）
- [ ] 2. 旧版のハブが完了の記録を書く前に落ちても、残ったセッションを上限から外さない（テスト）
- [ ] 3. 旧版の痕跡を照合できない間は、上限に関わる起動を保留し、停止は処理する（テスト）
- [ ] 4. 新しい版だけで動いている間、一覧と `drain` の処理量が累積の要求数に比例しない（テスト）
- [ ] 5. 新しい版がハブの排他を取った後は、旧版の頼む側の起動・置き換え・再起動・停止は、新しい版の上限の判定の外でラッパーを起こさない。そのとき受付箱に残っていた旧版の要求は、断りの結果を受け取る（テスト）
- [ ] 6. 後の版がこの版の受付箱を閉じたら、この版の一覧は「読めない」を返し、この版の頼む側は要求を書かずに断る（テスト）

## 境界

- #4103 とは、一覧の「起動の途中」・起動の印・印の見直し・一覧の `relay_protocol` を #4103 が、版が混在する間に一覧を読めない扱いにする条件と、旧版が残したセッションに印を書くことをこの課題が持つ
- #4110（#4091 の不在の確かめ）とは、#4091 だけを実装した状態の T2 の排他と不在の確かめを #4110 が、一覧の `legacy` とハブが起動を保留する条件をこの課題が持つ。T2 の不在の確かめは、一覧が `legacy: true` なら不在と読まない（#4103 の `unknown` の扱いのまま）

## 起票者の推定

- 版の混在の間の安全は #4103 の本体と分けて設計できる（推した出所: PR #4112 の cross-review のラウンド 1 の r1-4・r1-5 とラウンド 2 の r2-6〜r2-10 が、どれも決定 6 の旧版の検出と照合に集まり、券と印の本体の指摘と独立していること）
- 子の版の確かめと受付箱の分離は #4103 に残す（推した出所: 同じ設計の決定 6。どちらもファイルを読むだけで、旧版の券の無視を入口で防ぐ）

## 由来

PR #4112（#4103 の設計）の cross-review。ラウンド 1 で 13 件、ラウンド 2 で 17 件の重い指摘が出て、そのうち版の混在（決定 6）の検出と照合に、ラウンドごとに新しい穴が続いた（r1-4・r1-5 を直した後に r2-6〜r2-10）。起動指示の「3 ラウンドの上限で同じ境の穴が続くなら、さらに範囲を分けて起票し、早めに止める」に従い分けた。#4103 の受け入れ条件 1〜5 は、新しい版だけが状態保存先を使う場合で確かめられる。根拠: Value 5「完璧なものより、小さく「たぶん動く」ものが早く届く」・Value 2「役に立たない繰り返しに費用を使わない」（MVV 版 11）
