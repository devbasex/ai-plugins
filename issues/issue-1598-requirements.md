# #1598: 使ってよいランタイムをリポジトリの .ndf/ で宣言し、cross-review などの参加者と worker をそれに従わせる（1 ランタイムなら別々の起動で 2 席を埋める）

正は課題の本文（#1598）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 依頼（原文）

> ## 何を足すか
>
> 1. 利用側のリポジトリが `.ndf/` の宣言で、使ってよいランタイム（例: claude だけ）を決める項目
> 2. cross-review・cross-refactoring・external-ai・supervise の worker の runtime が、その宣言に従う
> 3. 宣言で参加者が 1 つのランタイム（例: claude だけ）になるとき、cross-review の 2 者の担当を、そのランタイムの別々の起動（`claude` と `claude-2`）で埋める
>
> ## なぜ要るか
>
> AI の利用の方針やデータの扱いの決まりで、使える CLI が限られるリポジトリがある（例: claude 以外の agent を使わない）。今は参加者を `--only` / `--exclude` / `--include` の引数でしか絞れず、起動のたびに付け忘れると、codex・kiro が担当に入る。
>
> 確かめた事実（NDF 10.17.51）:
>
> - cross-review と cross-refactoring の母集合の既定は claude / codex / kiro と起動元の CLI で（`lib/assignment.py` の `default_pool`）、引数でしか絞れない
> - cross-review と supervise のスクリプトが読む `.ndf/*.json` は project・supervise・code-metrics だけで、参加者を宣言する項目が無い
> - `--only claude` は担当を 1 者へ絞り、スロットのフォールバックを行わない（cross-review の SKILL.md）。2 者のレビューにならない
> - 利用可能な参加者が 1 者のときに同じランタイムの 2 つ目（`claude-2`）で埋める動作はあるが、#1412 のとおり `claude-2` は起動直後に `PIDFILE_BAD` で止まる
>
> ## 求める形
>
> - 例: `.ndf/project.json`（または専用のファイル）に `"runtimes": {"allowed": ["claude"]}`
> - 宣言があるとき、`--include` で宣言の外のランタイムを足そうとすると `init` が理由を出して止まる
> - 宣言で 1 つのランタイムだけが残るとき、`--only` を付けずに 2 席を `claude` と `claude-2` で埋める（#1412 が直っていることが前提）
> - supervise の worker の runtime と external-ai も、宣言の外のランタイムを選ばない
> - **2 者の組を宣言で選べる。** 複数のランタイムが使えるときも、同じランタイムの 2 席（例: `claude` と `claude-2`）を組として選べる。宣言が無ければ今の選び方（2 者の異なるランタイム）のまま
> - **組の効果を後から比べられる記録を残す。** レビュー 1 回ごとに、席（`claude` / `claude-2`）・ランタイム・実際に動いたモデル（#759）・組の相手を状態ファイルと実行の要約（`run_metrics.py`）に残す。同じランタイムの 2 席の組と異なるランタイムの組を、見逃し率と覆した率で比べられるようにするためである（下の計測の節）
>
> ## 受け入れ条件の案
>
> - [ ] 宣言が claude だけのリポジトリで、引数なしの cross-review が `claude` と `claude-2` の 2 席で回り、codex・kiro を起動しない
> - [ ] 宣言の外のランタイムを引数で足すと、理由を出して止まる
> - [ ] 宣言が無いリポジトリの動作は今と同じ
> - [ ] 複数のランタイムが使えるリポジトリで、宣言により `claude` と `claude-2` の組を選ぶと、その 2 席で回る
> - [ ] レビュー 1 回ごとに、席・ランタイム・実際に動いたモデル・組の相手が実行の要約に残り、`run_metrics.py aggregate` で組ごとに数えられる
>
> ## 同じランタイムの 2 席でレビューの質が落ちないか（計測 2026-10-02）
>
> **claude は自作のコードにも甘くならない。** 計測の対象は 10 リポジトリ（cross-review のあった PR 1,090 件・レビュー 6,842 件）で、9/15 以降の、同じ PR・同じラウンドに並んだ相手との比較である。実装と `/ndf:fix` は全件 claude で、claude のレビューはすべて自作のコードへのレビューになる。
>
> | ランタイム（モデル） | APPROVE 率 | 自分が APPROVE したラウンドで相手の重大な指摘が採用された率 | 相手が APPROVE したラウンドで自分の重大な指摘が採用された率 |
> | --- | ---: | ---: | ---: |
> | claude（opus-5-5） | 21% | 28% | 47% |
> | codex（gpt-5.6-sol） | 28% | 20% | 42% |
> | kiro（auto） | 50% | 33〜37% | 7〜9% |
> | agy（gemini-3.8-flash） | 60% | 12% | 18% |
>
> - **採否を決めた `/ndf:fix` も claude であるため、出どころを伏せて第三者に判定させた。** 40 件を codex と claude の 2 者に判定させた。codex の判定者が「実在する欠陥」とした率は、claude 由来・codex 由来・kiro 由来のどれも 40% で同じだった。claude の判定者は、どの出どころにも甘めに付け（60〜73%）、claude 由来だけを贔屓する形は無かった
> - **組ごとの補い合い方:**
>   - claude ＋ codex は両方向に補い合う。claude が APPROVE したラウンドで codex の重大な指摘が採用された率は 31%（42 件中 13）、逆向きは 38%（65 件中 25）
>   - claude ＋ kiro では、kiro が足したのは 9%（34 件中 3）で、逆向きは 48%（138 件中 66）
> - **測っていないこと:** claude と claude-2 の組が、互いの見逃しをどれだけ拾うか。`claude-2` のレビューの記録はまだ 1 件も無い（#1412 で起動直後に止まる）。上の 13 件（claude が APPROVE し、codex の重大な指摘が採用されたラウンド）を claude の 2 つ目の起動でレビューし直せば、同じランタイムの 2 席が codex の役割をどこまで代われるかが測れる
>
> **選び方への含意:** 宣言で claude だけに絞ったリポジトリでも、`claude` と `claude-2` の 2 席は、claude ＋ kiro の組より劣らない見込みが高い（kiro がほとんど指摘を足さないため）。claude ＋ codex の組と同じ水準かどうかは、上の再レビューの計測で決める。
>
> 材料: 計測のスクリプトとデータ（`analyze.py`・`traits.py`・`blind_summary.md`）はセッションのスクラッチパッドの `xr-measure/` にある。リポジトリには入れていない。
>
> 関連: #1412、#1290

## 目的

- AI の利用の方針やデータの扱いの決まりで使える CLI が限られるリポジトリで、利用者が `.ndf/` に 1 度宣言すれば、cross-review・cross-refactoring・external-ai・supervise の worker が宣言の外のランタイムを起動しない状態にする。引数の付け忘れで、決まりに反する CLI へコードが渡ることを無くす
- 使えるランタイムが 1 つでも、cross-review が 2 つのスロットのレビューで回る状態にする
- 同じランタイムの組と異なるランタイムの組を、後から記録で比べられる状態にする

## 前提

- 前提 1: 宣言は NDF が読むだけで、NDF は宣言を書かない。利用者が手で書く（共通原則の C7）。`project-decl.py write` などの解析で `.ndf/` を書き直すときも、宣言の項目を消さない（受け入れ条件 AC11）
- 前提 2: 宣言の置き場（`.ndf/project.json` の項目か専用のファイルか）と項目の名前は `design` で決める。この仕様は「`.ndf/` の宣言」とだけ書き、受け入れ条件の例は `"runtimes": {"allowed": [...]}` の形で書く
- 前提 3: 宣言の対象は NDF が CLI として起動するランタイム（参加者・実装担当・worker・external-ai の起動先）だけである。いま動いているホストのセッション（利用者が自分で起動した CLI）は止めない。ホストのランタイムが宣言の外にあるときは、ホストを参加者プールへ足さない
- 前提 4: `claude-2` などの 2 つ目のスロットが起動直後に止まる不具合は #1412 が直す。この課題の受け入れ条件 AC2・AC6 の確認は #1412 が直った後に行う。#1412 が直る前でも、スロットの選び方（どのスロット名を選ぶか）は単体のテストで確かめられる
- 前提 5: 実際に動いたモデルは、#759 が直るまで `--model` を指定しないと分からないことがある。分からないときは記録のモデルを「不明」（JSON の `null`）として残し、組の集計からは落とさない
- 前提 6: 宣言の項目は、どのランタイムを使ってよいかと、cross-review の組の選び方の 2 つだけを持つ。モデルの許可・禁止は扱わない（含まないへ）
- 前提 7: 宣言が壊れている（JSON として読めない・知らないランタイム名・空の一覧）ときは、宣言が無いものとして動かず、理由を出して止まる。宣言を無視して全ランタイムで動くと、決まりに反する CLI へコードが渡るためである（共通原則の上位の原則）
- 前提 8: 再開（状態ファイルがある実行の続き）でも、再開した時点の宣言に従う。状態ファイルに宣言の外のランタイムが参加者として記録されていても、そのランタイムを起動しない

## 対象範囲

含む:
- `.ndf/` に、使ってよいランタイムの一覧と、cross-review の組の選び方を書く宣言の項目
- cross-review・cross-refactoring の参加者プール・`--include`・`--only`・スロットのフォールバックの候補を、宣言の範囲へ絞ること
- external-ai（`external-ai.py check` / `run`）が宣言の外のランタイムを起動しないこと
- supervise のプランの work / drive のステップに書いた `runtime` と、`runtime` を書かないときの既定の worker（claude -p）が宣言に従うこと
- 宣言で使えるランタイムが 1 つになるとき、cross-review の 2 スロットを同じランタイムの 1 つ目と 2 つ目（`claude` と `claude-2`）で埋めること
- 宣言で同じランタイムの組を選べること
- cross-review のラウンドごとに、スロット・ランタイム・実際に動いたモデル・組の相手を状態ファイルと実行の要約へ残し、`run_metrics.py aggregate` で組ごとに数えること

含まない:
- #1412（`claude-2` が起動直後に `PIDFILE_BAD` で止まる不具合）の修正。別の課題で直す
- #759（`--model` を指定しないとモデルが記録されない）の修正
- 同じランタイムの組と異なるランタイムの組の見逃し率・覆した率を計算すること、組の既定を変えること。この課題は比べるための記録までを残す。計測（依頼の 13 件の再レビュー）は記録がそろった後の別の作業にする
- モデル単位の許可・禁止
- 宣言を作る・書き換える機能（NDF は宣言を書かない。前提 1）
- conductor・supervisor など、NDF の 3 層のうち Claude Code のサブエージェントとして動く層（ランタイムは常に claude で、CLI を選ぶ場面が無い）
- relay（`relay.py`）が起動する claude のセッション

## 用語

| 用語 | 意味 |
| --- | --- |
| ランタイムの宣言 | `.ndf/` に置く、そのリポジトリで NDF が起動してよいランタイムの一覧と、cross-review のレビューの組の選び方。無ければ制限しない |

## 受け入れ条件

宣言の例は `{"runtimes": {"allowed": [...]}}` で書く（形は `design` が決める。前提 2）。

- [ ] AC1: 宣言が無いリポジトリで、cross-review と cross-refactoring の `init` が決める参加者、cross-review の各ラウンドのスロット、external-ai と supervise の worker の起動先が、この変更の前と同じになる（既存のテストがすべて通る）
- [ ] AC2: 宣言の `allowed` が `["claude"]` のリポジトリで、引数なしの cross-review の各ラウンドのスロットが `claude` と `claude-2` になり、codex・kiro・agy の CLI を起動しない（認証確認でも起動しない）
- [ ] AC3: 宣言の `allowed` が `["claude"]` のリポジトリで、cross-review / cross-refactoring の `init` に `--include codex` を渡すと、参加者を決める前に終了コード 0 以外で止まり、出力に「codex は宣言の外」と分かる理由と宣言のファイルのパスが出る
- [ ] AC4: 宣言の `allowed` が `["claude"]` のリポジトリで、`--only codex` を渡すと AC3 と同じ形で止まる
- [ ] AC5: 宣言の `allowed` が `["claude", "codex"]` のリポジトリで、ホストが kiro でも、参加者プールに kiro が入らない
- [ ] AC6: 宣言の `allowed` が `["claude", "codex", "kiro"]` で、組の選び方として「claude の同じランタイムの組」を宣言したリポジトリで、引数なしの cross-review の各ラウンドのスロットが `claude` と `claude-2` になる
- [ ] AC7: 宣言の `allowed` が `["claude", "codex"]` で、codex の認証確認が通らないとき、スロットは `claude` と `claude-2` になり、宣言の外のランタイムで埋めない
- [ ] AC8: 宣言の `allowed` が `["codex"]` のリポジトリで、`external-ai.py run claude ...` と `external-ai.py check claude` は CLI を起動せずに前提条件の失敗の終了コードで止まり、結果の JSON の理由に宣言の外であることが出る
- [ ] AC9: 宣言の `allowed` が `["codex"]` のリポジトリで、supervise のプランに `"runtime": "kiro"` の work のステップ、または `runtime` を書かない work のステップ（既定の claude -p）があると、そのステップの worker を起動せずに理由を出して止まる。止まるのはそのステップの起動より前である
- [ ] AC10: 宣言が壊れている（JSON として読めない・`allowed` が空・`ALL_RUNTIMES` に無い名前を含む）とき、cross-review / cross-refactoring の `init`、external-ai、supervise は CLI を起動せずに止まり、壊れている箇所を出す
- [ ] AC11: 宣言のある `.ndf/project.json` に `project-decl.py write`（解析による書き直し）を打っても、宣言の項目が残る（宣言を `.ndf/project.json` に置くと `design` が決めたときだけ確かめる）
- [ ] AC12: 状態ファイルの参加者に codex を記録した cross-review を、宣言の `allowed` を `["claude"]` にしてから再開すると、codex を起動しない
- [ ] AC13: cross-review の状態ファイルの各ラウンドに、2 つのスロットのそれぞれについて、スロットの名前（`claude-2` など）・ランタイム・実際に動いたモデル（分からなければ `null`）・組の相手のスロットの名前が残る
- [ ] AC14: cross-review の実行の要約（`run_metrics.py` が書く JSON）に、AC13 の 4 つの値がラウンドごとに残る
- [ ] AC15: `run_metrics.py aggregate --kind cross-review` に組ごとの集計の指定を渡すと、レビューの組（例: `claude+claude`・`claude+codex`）ごとのラウンド数が Markdown の表で出る。組の記録が無い古い要約のラウンドは「不明」の行へ数え、エラーで止まらない
- [ ] AC16: 宣言の外のランタイムで止まったときの理由の文に、宣言のファイルのパスと使ってよいランタイムの一覧が入る（利用者が宣言を直すか引数を直すかを決められるため）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| セキュリティ | 宣言の外のランタイムの CLI を、認証確認も含めて 1 度も起動しない（AC2・AC8・AC9）。宣言が読めないときは制限を外さず止まる（AC10） |
| 運用・保守性 | 宣言で止まったときの出力から、どのファイルのどの項目が原因かを利用者が読み取れる（AC3・AC16）。組の記録は `run_metrics.py aggregate` で集計できる（AC15） |
| 移行性 | 宣言が無いリポジトリの動作は変わらない（AC1）。組の記録が無い古い実行の要約も集計できる（AC15） |

## 前提とする取り決め

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | 既存のテストの実行、配布物の同期、宣言が無いときの動作を変えないことの確認 |
| 確認してから行う | このリポジトリ（ai-plugins）の `.ndf/` に宣言を置くこと（共通原則の C7） |
| 行わない | 利用者の `.ndf/` を NDF が書くこと、#1412・#759 の修正をこの課題へ混ぜること、組の既定の変更 |
