## 依頼（原文）

> ## 何が起きたか
>
> 2026-11-06 12:3x JST、アカウント `main` が週の上限に達した。レーン lroot2・lfactory2 を起こし直すと、`relay.py account list` に `gmail`（週 6%）と `team` があるのに、3 回とも `main` で起動し、起動の直後に「usage limit reached」で止まった。`relay.py account use gmail` で指定を替えても変わらなかった。
>
> ## 原因
>
> tmux の専用サーバー（`tmux -L ndf-relay`）は、最初に `new-session` を打った claude のセッションの環境を、サーバーのグローバルな環境として持ち続ける。確かめた値（`tmux -L ndf-relay show-environment -g`）:
>
> ```text
> CLAUDE_CONFIG_DIR=/home/ubuntu/.claude/ndf/accounts/main
> NDF_CLAUDE_ACCOUNT=main
> NDF_RELAY_DEPTH=1
> NDF_RELAY_DIR=/home/ubuntu/.local/state/ndf/relay/20261104T203914Z-3164-81017316
> CLAUDECODE=1
> CLAUDE_CODE_SESSION_ID=9518c67a-...（ほか CLAUDE_CODE_*）
> ```
>
> このサーバーで起こしたラッパーは `NDF_RELAY_DEPTH=1` を受け取り、すでにラッパーの中にいると判断して、アカウントの選定（指定・残量・上限での切り替え）を通らずに `CLAUDE_CONFIG_DIR` の `main` のまま claude を起動する。一覧の区間の数も 4・5 のまま増えなかった。
>
> グローバルな環境からこれらの変数を外して起こし直すと、区間が 1 に戻り、`gmail` で起動した。
>
> ## 直し方の案
>
> 1. レーンと一時レーンを起こす経路（統括役の `launch`・手で起動する形）で、親のセッションの環境（`CLAUDECODE`・`CLAUDE_CODE_*`・`CLAUDE_CONFIG_DIR`・`NDF_CLAUDE_ACCOUNT`・`NDF_RELAY_DEPTH`・`NDF_RELAY_DIR`）を子へ渡さない
> 2. tmux の専用サーバーを起こすときに、グローバルな環境からこれらを外す
> 3. ラッパーが、親のラッパーの中にいるかを環境変数だけで決めず、親のプロセスが生きているかを確かめる
>
> ## 受け入れ条件
>
> 1. 親の claude のセッションから tmux の専用サーバーを起こしても、レーンがアカウントの選定を通る（`relay.py ls` の区間が新しく始まり、指定どおりのアカウントで起動する）
> 2. 指定のアカウントが上限のとき、別の使えるアカウントで起動する
> 3. 1 と 2 を縛るテストがある
>

## 目的

親のセッションから tmux の専用サーバーが起きても、レーンがアカウントの選定を通り、使えるアカウントで動く状態にする。上限に達したアカウントのまま起動して止まる事象をなくす。

## 前提

- 前提 1（再現で確認）: 専用サーバーの子は、サーバーを起こした側の環境を受け取る。後から `new-session` を打つクライアントの環境は届かない。使い捨ての tmux 3.6 で、サーバーを起こす側に置いた変数が子に届き、後のクライアントに置いた変数は届かないことを 2026-11-07 に確かめた
- 前提 2（再現で確認）: パススルーの判定の引き金は `NDF_RELAY_DIR` である（`plugins/ndf/scripts/relay_lib/run.py:448`）。擬似端末と偽の claude で `relay.py run` を起動した結果は次のとおり

  | 起動時の環境 | 結果 |
  | --- | --- |
  | `NDF_RELAY_DIR` と `NDF_RELAY_DEPTH=1` | ラッパーを始めずにパススルーする。子の深さは 2 で、親の `NDF_CLAUDE_ACCOUNT` と `CLAUDE_CONFIG_DIR` がそのまま残る |
  | `NDF_RELAY_DEPTH=1` だけ | パススルーの判定を通り抜け、ラッパーを始める手順へ進む |
  | `NDF_RELAY_DEPTH=2` | `起動が入れ子になっている` を出して終了コード 127 |
  | どちらも無し | ラッパーを始める手順へ進む |

- 前提 3: 親のセッションの環境に当たる変数は、セッションごとの値（セッションの識別子・動いているラッパーの作業ディレクトリ・起動の深さ・動いている claude のアカウント・役割・費用の記録先）に限る。利用者が宣言する認証の変数（`CLAUDE_CODE_OAUTH_TOKEN`・`CLAUDE_CODE_USE_BEDROCK` など）と利用者の設定（`NDF_ACCOUNT_SWITCH_AT` など）は残す
- 前提 4: 親の環境に `NDF_SHARED_CONFIG_DIR` があるとき、その値が元の `CLAUDE_CONFIG_DIR` である（空は「元に無かった」を指す）。`plugins/ndf/scripts/lib/claude_accounts.py` の従量の接続の環境を作る処理が同じ規則で戻している
- 前提 5: 手で起動する形は `NDF_RELAY_SPAWNED=1` を付ける形を対象にする。2026-11-05 19:12:44 UTC に今の専用サーバーを起こしたプロセスと、#2563 の手の起動がこの形である。`NDF_RELAY_SPAWNED` は `child_env` が子へ渡さないため、この印を持つプロセスはラッパーの子の claude ではない
- 前提 6（確かめた範囲）: #2563 の起動（2026-11-05 13:34 UTC）は今の専用サーバーの開始（同日 19:12:44 UTC）より前で、当時のグローバルな環境は残っていない。ただし #2563 では同じサーバーの上で手で起動すると動いた。新しい `new-session` はどちらもサーバーの環境を受け取るため、環境の継承だけでは同じサーバーでの成否の差を説明できない。#2563 の原因は未確認のまま残る

## 対象範囲

含む:
- 統括役の起動（`relay.py spawn`・`restart`・起動のブロック）と手で起動する形で、親のセッションの環境を持つ専用サーバーの上にレーンと一時レーンを起動する経路
- レーンの中で読む、元の設定ディレクトリと共有の設定ディレクトリの求め方
- `docs/specifications/ndf-relay-multi-session-supervisor.md` の「統括役の環境がそのまま継がれ」の記述の整合（統括役の環境が届くのは統括役がサーバーを起こしたときだけである。前提 1）

含まない:
- spawn が `ok` を返すのに立ち上がらない不具合（#2563）の原因の特定
- 切り替えの閾値と 5 時間の制限の無いプランの優先（#2588）、上限の撤廃（#2505）
- `NDF_RELAY_SPAWNED` を付けずに `relay.py run` を tmux で起動する形。今と同じくパススルーのまま（前提 5）
- 計画の状態の置き場（#2647）。短命な値を子が持つ形は同じだが、対象の状態が別である
- 利用者の既定の tmux サーバーと Codex の経路
- クラス図・配置の図・永続データの図・API の仕様記述。型・実行の単位・保存するデータ・`relay.py` の副命令と出力の形を変えないため、対象が無い

## 用語

| 用語 | 意味 |
| --- | --- |
| tmux の専用サーバー | 中継のレーンを動かす tmux サーバー（`tmux -L ndf-relay`）。利用者の既定の tmux サーバーとは別である。文中では専用サーバーと書く |
| 親のセッションの環境 | 動いている claude のセッションとそのラッパーに固有の環境変数。別のプロセスへ継がれると、そのプロセスを親のセッションの中にいると誤らせる |
| アカウントの選定 | ラッパーが区間を起動するときに、指定・残量・上限から使うアカウントを決める手順 |

## 受け入れ条件

以下の「親の環境を持つサーバー」は、グローバルな環境に `CLAUDECODE=1`・`CLAUDE_CODE_SESSION_ID`・`CLAUDE_CODE_ENTRYPOINT`・`CLAUDE_CONFIG_DIR=<main の設定ディレクトリ>`・`NDF_CLAUDE_ACCOUNT=main`・`NDF_RELAY_DEPTH=1`・`NDF_RELAY_DIR=<別のラッパーの作業ディレクトリ>`・`NDF_SHARED_CONFIG_DIR=` を持つ専用サーバーを指す。テストは使い捨ての `TMUX_TMPDIR` で作る。

- [ ] 受け入れ条件 1: 親の環境を持つサーバーの上で `relay.py spawn --name <名前>` を実行すると、新しいラッパーの作業ディレクトリが作られ、`relay.py ls` の区間が 1 になり、子の claude の `NDF_CLAUDE_ACCOUNT` が `relay.py account use` の指定と一致する
- [ ] 受け入れ条件 2: 同じサーバーの上で `relay.py restart <名前>` を実行しても、受け入れ条件 1 と同じ結果になる
- [ ] 受け入れ条件 3: 同じサーバーの上で `tmux -L ndf-relay new-session -d -s <名前> -e NDF_RELAY_NAME=<名前> -e NDF_RELAY_SPAWNED=1 -- <python> relay.py run -- '<最初の入力>'` を打っても、受け入れ条件 1 と同じ結果になる
- [ ] 受け入れ条件 4: 環境の `NDF_RELAY_DIR` が指すラッパーが動いているときも、受け入れ条件 1 と 3 の結果は変わらない
- [ ] 受け入れ条件 5: グローバルな環境の `NDF_RELAY_DEPTH` が 2 のサーバーの上で受け入れ条件 1 と 3 を実行しても、終了コード 127 で止まらず同じ結果になる
- [ ] 受け入れ条件 6: 親の環境を持つサーバーの上で、指定の `main` が上限で `gmail` が使えるとき、子の claude の `NDF_CLAUDE_ACCOUNT` は `gmail` になる
- [ ] 受け入れ条件 7: 登録のすべてのアカウントが上限のとき、親の環境を持つサーバーと持たないサーバーで、選ばれる結果（アカウントと理由）が同じである
- [ ] 受け入れ条件 8: 親の環境を持つサーバーのグローバルな環境に `NDF_RELAY_ROLE=helper`・`NDF_RELAY_PLAN`・`NDF_USAGE_PLAN`・`NDF_USAGE_STEP` があっても、役割を付けずに起動したレーンは役割のファイルを持たず、子の claude の環境にこの 4 つが残らない
- [ ] 受け入れ条件 9: `NDF_SHARED_CONFIG_DIR=<元>` を持つサーバーの上のレーンでは、共有の設定ディレクトリが `<元>` になる。値が空なら既定の `~/.claude` になり、`<main の設定ディレクトリ>` にならない
- [ ] 受け入れ条件 10: 親の環境を持つサーバーの上でも、利用者の設定と認証の宣言（`NDF_ACCOUNT_SWITCH_AT`・`CLAUDE_CODE_OAUTH_TOKEN`・`CLAUDE_CODE_USE_BEDROCK`）はレーンの子の claude まで届く（退行しない）
- [ ] 受け入れ条件 11: 動いているラッパーの子の claude の中で `claude` を打つと、今と同じくパススルーになり、新しい作業ディレクトリを作らない（退行しない）
      前提の確認: `NDF_RELAY_SPAWNED` を付けずに `NDF_RELAY_DIR` と `NDF_RELAY_DEPTH=1` で `relay.py run` を擬似端末で実行し、偽の claude がパススルーで起動した（2026-11-07）
- [ ] 受け入れ条件 12: `NDF_RELAY_SPAWNED` が無く `NDF_RELAY_DEPTH=2` の `relay.py run` は、今と同じく終了コード 127 で止まる（退行しない）
      前提の確認: `NDF_RELAY_SPAWNED` を付けずに `NDF_RELAY_DEPTH=2` で `relay.py run` を擬似端末で実行し、終了コード 127（2026-11-07）
- [ ] 受け入れ条件 13: 受け入れ条件 1〜10 を、実物の tmux と偽の claude で確かめるテストがある。環境の値を外す処理を取り除くと受け入れ条件 1・3・6 のテストが落ちる
