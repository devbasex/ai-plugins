## 調べた事実

1. **周回 3 の昇格のプランは queue を通らず、`run` で流れた。** carul の `loop.json` の周回 3 の問いの記録の `finish.pipeline` は `supervise.py run .../5-promote.json --from verify && supervise.py queue .../1-close.json ...` である。周回 3 に状態ディレクトリがあるプランは昇格だけで、検査のプランは流れていない（`lap-3/sprint/` の一覧）。`record` は `error: argument --prs: invalid int value: '{queue_prs}'` で終了コード 2 になった（`lap-3/sprint/5-promote-state/run-stderr.log`）。
2. **`{queue_prs}` は残っても止まらない。** `plan.py:219` の `QUEUE_NAMED` は `{queue_pr:<名>}`・`{queue_state:<名>}`・`{queue_record}` だけを検出し、`{queue_prs}` を含まない。queue でも先頭のステージでは `fill_stage` が `prs = None` にして埋めない（`queue.py:224`）。`run` は差し込みを解決しない（`fill_stage` の呼び出しは `flow.py:289` の queue の経路だけ）。そのため文字列のままコマンドへ渡り、配布が済んだ後のステップで落ちる。
3. **前の実行の件数は記録に残らない。** carul の周回 2 の `4-check-state/state.json` の log は最後の実行の 3 ステップ（merge-gate・merge・record）だけで、`counts` は持たない。実行の始まりごとに `state.json` は書き直される。進捗ログ（`progress.jsonl`）は追記だが、ステップの行に件数が無い（`state.py:225` `step_line`）。出力のファイル（`NN-<ステップ>.out`）は番号が実行ごとに 1 から振り直され、同じ番号と名前なら上書きされる。
4. **課題を閉じる PR は GitHub から引ける。** 周回 3 のまとめのプランの止まった理由は「課題 #110 #114 #102 を閉じる PR #143 を読んだが、本番か配布なしの段階のリリース記録が無い」であり（`lap-3/done-2.json`）、`find_record` は周回をまたいで #143 に届いている。

## 目的

- 昇格だけの周回でも、配布の後のリリース記録が人の手当て無しで残り、まとめのプランが流れる状態にする
- 検査のプランを途中から流し直しても、検査の記録の行に指摘の件数が残り、`pace: fast` のトリガーの閾値を見直す材料に使える状態にする

## 前提

- 前提 1: #2344 の仕組みは未実装である。`git ls-tree -r --name-only origin/develop plugins/ndf/scripts/lib` に `ref_kinds` を含むパスは 0 件（2026-11-06、`origin/develop` は 742ef62fe）。PR #2482 の本文は「この PR は文書だけを変更します」と書く。#2344 と、その実装の前提になる #2339・#2341・#2342 はいずれも OPEN である。したがって、この課題は今の差し込みの処理（`supervise_lib/queue.py`・`supervise_lib/queue_fill.py`）へ足す
- 前提 2: プランに `{queue_prs}` が使われる経路は、昇格の record（`delivery_templates.py:101`）、本番の配布（`release_templates.py:351`）、承認ゲート 2 のプラン（`sprint_routes.py:146`）、配布の依頼（`sprint.py:70`）である。解決は差し込みの処理の中で行うため、どの経路にも同じ規則が効く
- 前提 3: プランの `課題` の欄は開発ループでも保たれる（carul の `5-promote.json` は `[110, 114, 102]`）
- 前提 4: 既にある検査の記録の行と、この変更より前の進捗ログは書き換えない。過去の行の件数は null のままである
