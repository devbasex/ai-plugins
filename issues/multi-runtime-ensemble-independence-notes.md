## この文書の位置づけ

手元の実測データ、その突き合わせを残す。設計へ反映した結果は

## 発端となった問い

`cross-refactoring` Skill は、4 つの CLI（claude / codex / gemini / kiro）に構造改善を
提案・適用・レビューさせ、合議で採否を決める設計へ向かっている。その設計を検討する中で、
次の 3 つの問いが立った。

1. 同じモデルファミリーの参加者は、同じ偏りを持つと見なすべきか
2. モデルの違いとハーネス（CLI・スキャフォールド）の違いは、どちらが結果を分けるか
3. 合議の集約に多数決を使ってよいか

とくに手元の構成では、**kiro CLI が `claude-sonnet-5` を使い、ホストの claude CLI と
同じ Anthropic 系列になる**。4 者のうち 2 者が同族という状態を、独立性の毀損として
扱うべきかが具体的な争点だった。

## 問い 1: モデルファミリーは独立性をどれだけ損なうか

### 文献の数値

| 出典 | 同一ファミリー / アーキテクチャ | 異なる場合 | 差 |
| --- | ---: | ---: | ---: |
| Hidden Clones（VQAv2、17 モデル） | r = 0.67 ± 0.12 | r = 0.53 ± 0.07 | 0.14（p < 0.001） |
| Hidden Clones（TextVQA） | — | — | 0.13 |
| Hidden Clones（GQA） | — | — | 0.15 |

Correlated Errors は回帰分析で要因を分解している。

| 要因 | HuggingFace | Helm |
| --- | ---: | ---: |
| 同じ企業 | 0.066 | 0.022 |
| 同じアーキテクチャ | 0.076 | — |
| 両モデルの精度の交互作用 | 0.023 | 0.026 |
| ベースライン（ランダム） | 約 0.127 | — |

いずれも p < 0.01。決定係数は HuggingFace 0.340、Helm 0.613、Resumes 0.415。

### 読み取れること

ファミリーの効果は存在するが、2 つの理由で「同族なら同じ偏り」という二値の扱いは支持されない。

1. **異なるファミリーでも相関は高い。** Hidden Clones で r = 0.53、同一ファミリーとの差は 0.14 に
   とどまる。ファミリーを分散させても相関は消えない
2. **ファミリーより精度の交互作用のほうが効く。** Correlated Errors の著者は「より正確な
   モデルペアほど誤りが相関する」と述べている。前線モデルを並べる構成では、ファミリーを
   分散させても両者が高精度である限り相関は残る

Hidden Clones はこの帰結として、17 モデルの統計的な力が**実質 2.5〜3.6 の独立投票者**に
しか相当しないことを固有値分析で示している（VQAv2 2.86 / TextVQA 3.59 / GQA 2.49。
第 1 固有値がそれぞれ分散の 58.0% / 50.9% / 62.5% を説明）。

同論文はまた、各ファミリー 1 モデルずつ選んだ 8 モデルの均衡アンサンブルが、17 モデルの
99.9% の性能を出すことを報告している（VQAv2 86.63% 対 86.70%）。**投票者を増やすより
相関を下げるほうが効く**という結果になる。

## 問い 2: モデルとハーネスのどちらが結果を分けるか

### Harness-Bench

6 ハーネス × 8 モデル × 106 タスク = 5,194 軌跡の測定。

- ハーネス間の差は **23.8 ポイント**（NanoBot 76.2% ↔ OpenClaw 52.4%）
- 強いモデルほどハーネス差に頑健で、弱いモデルほどハーネス設定に敏感
- 失敗の症状の分布: 契約・フォーマット違反 36.4% / ツール・リカバリー失敗 24.6% /
  証拠のグラウンディング不完全 14.6% / 成果物の未コミット 11.1% / 状態の喪失 9.3%

著者の結論は「エージェントの能力はベースモデルだけでは特徴づけられず、観測・行動・回復・
成果物生成を仲介する実行層にも規定される」である。

### CORE-Bench 事例

手元の構成に最も近い測定である。

> Opus 4.5 において、CORE-Agent と OpenCode は**どちらも 82.1% の精度**でありながら、
> **39 タスク中 12 タスク（31%）で結果が一致しなかった**

失敗の種類もスキャフォールドで偏る。

| 失敗の種類 | 偏り |
| --- | --- |
| 計算エラー | CORE-Agent に 14 件 |
| タイムアウト | OpenCode に 8 件 |
| 依存関係の失敗 | OpenCode に 6 件 |

解決戦略の選択にも差が出ている。直接修正の成功率は 95.2%、全面書き直しは 67.8% で、
Codex CLI は 82% が直接修正を選ぶのに対し CORE-Agent は 49% にとどまる。この傾向が
全体精度と相関しており、**スキャフォールドが取りうる解決戦略を制約している**と分析されている。

### 読み取れること

**同一モデル・同一精度でも、ハーネスが違えば 3 割のケースで別の結論に至る。** これは
モデルファミリーの相関ギャップ（0.14）より大きな効果である。

ただし、この事例は 39 タスクの単一比較であり、一般化には追試が要る。

## 問い 3: 集約に多数決を使ってよいか

### Minority Sentinel

3 ベンダーの LLM で議論させ、1,754 サンプルを測定。

| 指標 | 値 |
| --- | ---: |
| 2:1 の意見分裂が起きた割合 | 39.1%（686/1,754） |
| 分裂のうち少数派が正しかった割合 | 25.5%（175/686） |
| 多数決の精度 | 74.3% |
| 少数派を全て正しく救った場合の上限 | 84.3% |
| 回復の余地 | 10.0 ポイント |

覆す判定に何を使うかで結果が分かれる。

| 判定方法 | ネットゲイン |
| --- | ---: |
| 学習した分類器（22 次元の議論の特徴量 + LightGBM） | +1.71% |
| ロジスティック回帰 | +0.68% |
| **LLM を審判にする** | **−1.37%** |

著者は原因を「現代の LLM は事前学習コーパスを共有するため誤りが強く相関し、Condorcet の
陪審定理が前提とする独立性が破綻する」と説明している。LLM 審判が負のゲインになるのは
「同じ知識の盲点を共有する」ためとされる。

### Hidden Clones の対応する結果

「最良モデルが正解しているのに多数決で全滅する」層（Misleading Tier）が存在する。

| ベンチマーク | 該当割合 | 最良モデル精度 | 多数決の精度 |
| --- | ---: | ---: | ---: |
| VQAv2 | 2.5% | 78.9% | 0% |
| TextVQA | 1.5% | — | 0% |
| GQA | 6.5% | — | 0% |

### 読み取れること

相関のある参加者による多数決は、少数派の正解を系統的に潰す。集約を LLM に委ねても
改善しない（負のゲイン）。**機械的に検証できる証拠を、投票より上に置く根拠**になる。

`cross-review`（ai-plugins の Pull Request #155、6 ラウンド）で得たデータである。
いずれも N=1 の事例で、統計的な主張はできない。実運用での観測として記録する。

### 提案の重複率

3 者が同じ範囲（1,189 行）に対して独立に提案した結果である。

| ラウンド | codex | gemini | kiro | 計 | 統合後 | 重複 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 3 | 4 | 3 | 10 | 9 | 1 |
| 2 | 3 | 4 | 0 | 7 | 5 | 2 |
| 3 | 4 | 3 | 1 | 8 | 8 | 0 |
| 4 | 1 | 2 | 2 | 5 | 4 | 1 |
| 合計 | 11 | 13 | 6 | 30 | 26 | 4 |

**重複率 13.3%。** 提案の 86.7% は 1 者だけが挙げたものだった。採用された 19 件のうち、
2 者以上が挙げたものは 4 件（21.1%）である。

この数値は 2 通りに読める。どちらが支配的かは、この試行では切り分けられていない。

- 参加者の探索が独立している（ハーネスの違いが効いている）
- 提案の空間が広く、3 者が別々の場所を見ただけである（合意の機会がそもそも少ない）

### レビューの判定の分岐

`cross-refactoring` のレビューは 2 者で行う。6 回の判定は次のとおり。

| ラウンド | 実装担当 | レビュー担当と判定 | 一致 |
| ---: | --- | --- | --- |
| 1（1 回目） | codex | gemini APPROVE / kiro REQUEST_CHANGES | 分岐 |
| 1（2 回目） | codex | gemini REQUEST_CHANGES / kiro REQUEST_CHANGES | 一致 |
| 2（1 回目） | kiro | codex APPROVE / gemini REQUEST_CHANGES | 分岐 |
| 2（2 回目） | kiro | codex APPROVE / gemini APPROVE | 一致 |
| 3 | claude | codex APPROVE / kiro APPROVE | 一致 |
| 4 | codex | gemini APPROVE / kiro REQUEST_CHANGES | 分岐 |

**判定が分岐したのは 6 回中 3 回（50%）。** Minority Sentinel の「2:1 分裂が 39.1%」と
同じ桁である（参加者数が違うため直接比較はできない）。

分岐したケースでは、いずれも `REQUEST_CHANGES` 側に具体的な根拠があった。ラウンド 1 で
kiro が単独で挙げた指摘は次のもので、これにより振る舞いが変わる項目 1 件が Pull Request から
外れている。

> 共通化した `_environment_entries` が常にキーを strip するため、`_apply_dev_environment` の
> list 分岐で空白を含むキーの扱いが変わる（旧: 重複追記、新: 既存要素を除去して追記）。
> 現状固定テストで拾われていない。

**少数派（1 者）の指摘が正しかった事例**として記録する。

### 判定の分岐が続いた事例（cross-review）

ai-plugins の Pull Request #155 を codex と gemini が 6 ラウンドレビューした結果である。

| ラウンド | codex | gemini |
| ---: | --- | --- |
| 1 | REQUEST_CHANGES (3) | REQUEST_CHANGES (3) |
| 2 | REQUEST_CHANGES (1) | REQUEST_CHANGES (3) |
| 3 | REQUEST_CHANGES (1) | REQUEST_CHANGES (1) |

## 設計への含意

この調査の結果、`cross-refactoring` の設計案を 3 点改めた。

| 項目 | 調査前の案 | 調査後 |
| --- | --- | --- |
| 採否の第 1 関門 | 提案者の合意 2 者以上 | **合意を第 1 関門にしない。** 少数派の正解を切り捨てる構造になる |
| モデルファミリー | 独立性の必須条件として扱う | 観測項目として記録する。相関は程度問題で、支配的な要因ではない |
| ハーネスの違い | 言及なし | **独立性の主要な根拠として明示する** |

採否の順序は次の形へ改める。

1. 機械検証（テスト・参照検索・静的解析）で立証できるものは、支持が 1 者でも採用する
2. 反証が出たものは、支持数によらず落とす
3. 残りを支持数と影響の広さで並べる
4. 支持が割れたものは採用しない。得点と内訳は報告へ残す（自律実行を止めないため、
   人の判断は待たない）

## 未解決の問いと検証計画

### この試行では切り分けられなかったもの

| 問い | なぜ切り分けられないか | 測り方 |
| --- | --- | --- |
| 提案の重複率 13.3% は独立性の高さか、探索空間の広さか | 対照条件が無い | 同一モデル・同一ハーネスを 3 プロセス並列で走らせ、重複率を比較する |
| 同族（claude / kiro）の提案は他より似ているか | 提案元別の対比較をしていない | 提案の対象・手法の一致率を提案者ペアごとに測る |
| ハーネスとモデルのどちらが提案を分けるか | 両方が同時に変わっている | モデルを固定してハーネスだけ変える条件と、その逆を組む |
| 機械検証は投票より良い採否を出すか | 投票を実装していない | 同じ提案集合に対し、投票の結果と機械検証の結果を両方記録して比較する |

### 8 回目以降で残すべき評価ログ

- 各ランタイムの提案数、単独提案数、提案者ペアごとの重複率
- 各候補の提案者集合、有効投票者数、支持・反証の内訳
- 機械検証の実行有無と結果
- 単純多数決なら採用されたか / 証拠ベースの判定なら採用されたか
- 最終レビューで残った件数 / 取り消された件数
- 少数派のみが支持したが正しかった提案の数
- 所要時間と利用量

これにより「合議制にした」ではなく、**単一モデル・単純多数決・証拠ベース集約のどれが
品質と費用の面で良かったか**を比較できる。

## 記事・論文にするときの切り口

想定している主張は次の 3 つである。いずれも追試が要る。

1. **多ランタイム合議の独立性は、モデルの系統よりハーネスの違いに依存する。**
   文献（Harness-Bench、CORE-Bench 事例）と、手元の重複率 13.3% が支持する
2. **相関のある参加者の多数決は、リファクタリング提案の採否には向かない。**
   Minority Sentinel と Hidden Clones が示す構造で、手元でも 1 者の指摘が
   振る舞いの変化を捕捉した事例がある
3. **機械検証を持つドメインでは、合議より検証を上に置ける。**
   コードのリファクタリングはテスト・参照検索・静的解析という相関しない証拠を
   持つ点で、自然言語の推論タスクより有利である

3 点目が、この題材の固有性である。多くの LLM 合議研究は正解ラベルのある推論タスクを
扱うが、リファクタリングは「振る舞いが変わらないこと」を機械的に確かめられる。
合議を判定の中心に置かずに済むドメインとして提示できる。
