# #4051: 並列の計画の上限: 計画の索引を耐久ワークフローの終了で消すので、区切りの後に実行中の行を別の計画が数えられない

正は課題の本文（#4051）で、この文書はその写しである。本文から作り直す。手で直さない。

## 何が起きたか

PR #4041（#3995 の設計）のクロスレビュー（r1-1）で、並列の計画のマシン全体の上限（#3989）が使う計画の索引に、次の 2 つの食い違いが見つかった。#3995 の範囲の外なので分けた。

- 索引は耐久ワークフローが終わるとき（区切り・中止・完了・失敗のどれでも）に消える（`plugins/ndf/src/ndf/progress/plan/run.py` の `_indexed_until_done` が `finally` で `machine.unindex_plan` を呼ぶ）。実行中の行を持ったまま耐久ワークフローが終わると、その後にラッパーがすべて止まって登録簿から消えた時点で、索引にも登録簿にも計画が残らない。別の計画の起動の許可（`machine.machine_plans`）はその行を数えられず、上限を超えて起動しうる
- 確定仕様 [docs/specifications/ndf-parallel-machine-plan-limit.md](https://github.com/devbasex/ai-plugins/blob/main/docs/specifications/ndf-parallel-machine-plan-limit.md) の「稼働中の数の数え方」は、異常終了で残った索引を「実行中の行が無い計画として 0 本と数える」と書く。実装の `machine_plans` は、索引に載った計画のステートマシンを読み、保存された実行中の行を数える。仕様と実装が食い違っている

## 種類

不具合（確定仕様が約束する「ラッパーがすべて止まって登録簿から消えた計画を、実行中の行を持つ間は索引から見つける」を回復する）

## 今の姿

| 部品 | 今の振る舞い | 場所 |
| --- | --- | --- |
| 索引を書く | 起動の許可が通ったときに、起動の排他の中で書く | `src/ndf/progress/lane/machine.py` の `admitted` → `index_plan` |
| 索引を消す | `ndf lanes run` の耐久ワークフローが終わるとき（`finally`）に、終わり方を問わずに消す | `src/ndf/progress/plan/run.py` の `_indexed_until_done` |
| 索引を読む | 起動の許可と `ndf lanes status` が、索引の計画のステートマシンを読み、実行中の行（`state == running`）を持つレーンを数える | `machine.machine_plans` → `read_lanes` → `lanes_of` |
| 耐久ワークフローの終わり | 区切り（`paused`）と中止（`stopped`）は、スプリントの ID を持つ実行中の行（`LaneRow.active`）が無くなってから終わる。中止を起動できなかった（`cancel_failed`）ときと、耐久ステップが例外で落ちたときは、実行中の行を持ったまま終わる | `src/ndf/progress/plan/run_decide.py` の `_end_of`・`_cancels_given_up` |

パスは `plugins/ndf/` からの相対である。

## 事象

- 中止を起動できずに `cancel_failed` で終わった計画と、耐久ステップの例外で終わった計画は、実行中の行を持ったまま索引から消える。ラッパーがすべて止まって登録簿から消えると、別の計画の起動の許可はその行を数えず、上限を超えて起動する
- 区切りと中止の終わりが実行中の行の無い時点に限られるのは、終わりの判定（`LaneRow.active`）が守っている。数え方（`state == running`）とは別の場所に書いた別の条件で、索引の寿命はどちらにも結び付いていない
- 確定仕様は残った索引を 0 本と数えると書き、実装は実行中の行を数える。仕様の「マシンの計画の索引」のファイルの形にも、実装が書く `plan_id` が無い

## 期待する結果

計画の索引は、その計画が数え方で数える行（実行中の行）を持つ間は残り、持たなくなってから消える。耐久ワークフローの終わり方には左右されない。確定仕様は、残った索引を実装どおりに数える（実行中の行があれば数え、無ければ 0 本）と書く。

## 再現手順

1. 上限 1 のマシンで計画 A のレーンが実行中の行を持つ（承認ゲートの回答を待つ行など）
2. `ndf lanes stop A --now --reason <理由>` で止め、中止の起動を回数の上限まで失敗させる（耐久ワークフローが `cancel_failed` で終わり、索引が消える）
3. A のラッパーを止め、登録簿から消える
4. 計画 B の耐久ワークフローがレーンを起動する → A の実行中の行が数えられず、B が起動する（上限 1 を超える）

コードを読んで組んだ手順で、実機では試していない。

## 環境

main（96a9117bd、ndf v11.0.14 の後。#3989 の実装 PR #4001 のマージ後）

## なぜ困るか

並列は 6 本までという上限（2026-09-25 の実測で全体テスト 6 本の同時実行でメモリが残り 7.4 GB）を超え、マシンのメモリが足りなくなり得る。仕様と実装が食い違うので、仕様を読んで残った索引を消してよいと判断すると、数えるべき行を数え落とす。

## 目的

- 実行中の行を持つ計画を、耐久ワークフローがどう終わっても、別の計画の起動の許可が数えられるようにする
- 実行中の行を持たなくなった計画の索引は、今のとおり片付く
- 確定仕様の索引の記述を実装と一致させる

## 対象範囲

| 含む | 含まない |
| --- | --- |
| 索引を消す条件と、消す担い手 | どの行を数えるか（数え方の規則。#4050 が承認ゲートの待ちなどの行を数えない形へ変える） |
| 確定仕様の「稼働中の数の数え方」「マシンの計画の索引」と、モジュールの説明文の書き直し | リレーハブの数え方（#4044） |
| | 耐久ワークフローの終わりの条件（`_end_of`）の変更 |
| | チェックアウトが消えた計画の索引を片付ける手段 |

## 前提

- 前提 1: 計画の索引のファイルを書き換える担い手は、その計画の耐久ワークフロー（`ndf lanes run`。実行のキーのロックで 1 計画 1 本）だけである。起動の許可は自分の計画の索引だけを書く
- 前提 2: 異常終了（プロセスが殺された・マシンが落ちた）の後も、計画の行はステートマシンに残り、`ndf lanes run` を打ち直せば耐久ワークフローが回復して続く

## 受け入れ条件

- [ ] 1. 実行中の行を持ったまま耐久ワークフローが終わった計画（区切りで止めた後に耐久ワークフローが例外で落ちた計画と、`cancel_failed` で終わった計画）について、そのラッパーがすべて止まって登録簿から消えても、別の計画の起動の許可がその行を数えて待つ（テスト）
- [ ] 2. 異常終了で索引が残った計画について、仕様の記述と `machine_plans`（`machine_count` が通る）の数え方が一致する（実行中の行を持てば数え、持たなければ 0 本）（テスト）
- [ ] 3. 確定仕様の「稼働中の数の数え方」と「マシンの計画の索引」の記述が実装と一致する（索引を消す条件・消す担い手・ファイルの形）
- [ ] 4. 実行中の行を持たなくなって耐久ワークフローが終わった計画（完了・中止・区切り）の索引は、今のとおり消える（テスト）
- [ ] 5. 耐久ワークフローが終わるときに計画のステートマシンを読めなければ、索引を消さない（テスト）
