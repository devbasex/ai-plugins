## 何が起きたか

2026-11-16、#3672（ブランチ戦略の設定の作り直し）の実装が、1 本の PR #3698 に 319 ファイル・+11,923 / −4,834 行でまとまった。cross-refactoring（複数の AI で構造の改善を提案し合う工程）に約 49 分、cross-review（複数の AI で差分をレビューし合う工程）に 2 時間以上かかり、指摘の直しの間に CI の失敗が 85 件出た。#3092 の実装 PR #3247（246 ファイル・CI の失敗 70 件）も同じ形だった。

利用者は「本来 #3672 に対しては複数の PR を立てて個別に refactoring や cross-review を並行して進めるべきだった」と指摘し、詳細設計の後に実装計画を作り、順序と並列にするものを決めるよう求めた（原文は末尾）。

そのうち、PR をレビューできる大きさに分ける部分は 11.0.10 で入った（#3879・#3868）。残っているのは、**分け方を設計承認ゲートの前に決めること**と、**順序と並列を表で持ち、機械が読んで大きさを確かめること**である。

## 種類

機能追加（今の約束は「実装のフェーズの中で実装計画を書き、レビューの単位を AI が読んで実装の手順を組み立てる」で、設計 PR に載せること・実行順の表・機械が読む形・大きさの検査は約束に無い）

## 今の姿

実装計画（Skill `implementation-plan`）は、実装する人とコードレビュー担当が「どの順で、どのタスクに分けて作るか」を引く文書である。11.0.10 で次が入った。

| 入ったもの | 中身 | SSOT |
| --- | --- | --- |
| 「レビューの単位」の欄 | 単位ごとに 1 行。列は単位の名前・含むタスク・満たす受け入れ条件・見込みの差分の行数・実際の行数 | [implementation-plan の SKILL.md の「レビューの単位」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/implementation-plan/SKILL.md) |
| 課題 1 つを 1 単位にする既定 | 見込みが 1,000 行を超える課題はタスクの依存の向きで分け、同じファイルを触って切り離して読めない小さな課題（合わせて 400 行以下）は 1 単位にまとめてよい | 同上 |
| 大きさの目安 | 1 単位 400 行以下、1,000 行を超える単位は作らない。行数は追加と削除の和で、再生成するファイルと lock は数えない | 同上 |
| 単位ごとの PR と cross-review | 単位ごとに PR をスプリントブランチへ出し、その PR で cross-review を収束まで回してからマージする | [development-workflow の SKILL.md の工程表](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/SKILL.md)・[agent-layers.md の「実装のフェーズの単位」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/agent-layers.md) |
| 単位の実装とレビューの重ね合わせ | 準備のタスクを含む単位を最初に流してマージし、残りの単位は並列に流す。ある単位の cross-review の間に別の単位の実装が進む | 同上 |

まだ次の形である（2026-11-26、main `0e4b7db05` で確かめた）。

- **実装計画を作るのは実装のフェーズの中である。** 工程「計画」（[stages/plan.json](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/contracts/workflow/stages/plan.json)）は `phase: implement` で、作業場所（worktree）を用意した後に動く。分け方は設計承認ゲートの後に決まり、承認する人は見ない。スプリントの作業の順と進み具合を書く予定表（実行計画）の実装の行も、まず課題ごとの仮の行を置き、計画が書けた後に単位の行へ置き直す（[execution-plan.md の「実装の行は 2 回置く」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/issue-plan-strategy/references/execution-plan.md)）
- **順序は「準備の単位が先、残りは並列」の 2 通りだけである。** 単位どうしの依存・実行順・マージの順と、並列にするもの・直列に残すものを書く欄が無い
- **設計承認ゲートの後に機械が読むのは、設計書の「設計の結果」の表（課題・扱い・統合先・触るファイル）だけで、単位は課題である。** 1 つの課題を複数の単位に分ける形を持たない（[design-template.md の「設計の結果の書き方」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/design/references/design-template.md)）
- **単位の欄を読むのは AI だけである。** 工程を順に流す仕組みは、実装を単位に分けない。単位ごとのプラン（手順をステップの列にした実行の定義）は、実装のフェーズの supervisor（工程を回す AI）が Markdown の表を読んで組み直す。プログラムは単位を読まない
- **400 行・1,000 行は手順書の目安で、機械は確かめない。** 単位の行数を数えるプログラムは無い

### エンジニア向けの補足

- 工程「実装」の定義（`plugins/ndf/contracts/workflow/stages/implement.json`）には `per_issue: true` があるが、課題ごとに分ける処理は無く、実装のプランは工程 1 回につき 1 回呼ばれる。単位ごとの組み直しは `ndf route render implement` を supervisor が打つ（[agent-layers.md の「実装のフェーズの単位」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/agent-layers.md)）
- スプリントの状態を作る `ndf progress new`、プランを実行する `plugins/ndf/src/ndf/core/plan/`、計画の検査（`ndf lanes init`・`ndf plan check`）は単位を読まない
- 工程を順に実行する `ndf progress next` は main にある（足す課題 https://github.com/devbasex/ai-plugins/issues/3092 は open のまま）。工程「実装」がレビューの単位を読み、単位ごとに実装する処理は未実装で、 https://github.com/devbasex/ai-plugins/issues/4369 （open）が足す予定である
- `git grep -n 'レビューの単位' -- 'plugins/ndf/src/**/*.py'` で当たるのは、受け入れ条件の突き合わせ方の注記（`domains/loop/acceptance.py`）1 件だけである
- 1 つの課題の「設計の結果」の表が PR を 2 つ以上に分けていると、実装のプランを組めない理由を返す関数（`core/plan/inputs_decide.py` の `design_gaps`）がある。受け入れ条件 3・8 の「1 課題を複数の単位に分ける」形と食い違う。`git grep -n design_gaps -- plugins/ndf` では、定義と単体テストのほかに呼び出し元は当たらない

| --- | --- | --- |

| 単位を読む側 | 実装のフェーズの supervisor（AI）が文書を読む | 実装計画をプログラムが読めるデータでも出し、NDF がそれを読んで、先に必要な変更が取り込まれた順に単位ごとの作業を始める |

## 今の利用者への影響と互換

- 設計 PR に実装計画が加わり、設計承認ゲートで見る文書が 1 つ増える。承認ゲートの数は変わらない
- 実装計画を省く課題（[文書の役割の表の「省いてよい文書と条件」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/requirements-design/references/document-roles.md#省いてよい文書と条件)）は、今どおり課題 1 つを 1 単位にする

## なぜ困るか

- 分け方が設計承認の後に決まるので、承認する人は「何本の PR に分かれ、どの順に入るか」を見ずに承認する。分け方が誤っていても、実装が始まるまで誰も気づかない
- 順序と並列を書く欄が無いので、コントラクトを作る単位と使う単位を並列に流す・同じファイルを触る単位を並列に流すなど、作り直しやマージの衝突を生む組み方を止められない
- 大きさを機械が確かめないので、目安を外れた単位（#3698 の 16,757 行のような）が手順書の読み落とし 1 つで再び 1 本の PR になる

## 目的

- 大きな課題（統合 Issue・作り直し・用語の置き換え）を NDF で実装する利用者が、設計承認ゲートで PR の分け方・順序・並列にするものを見て承認でき、上限を超える単位を機械が止める

## 対象範囲

含む:
- 詳細設計の直後に実装計画を作り、設計 PR に載せる（`standard`・`legacy-refactor` の設計のフェーズ）
- 実装計画の単位に、実行順・依存の向き・マージの順を持たせ、並列にするもの・直列に残すものの表を置く（下の「前提」の決め方）
- 実装計画を文書と機械が読む形の両方で出す。機械が読む形は、単位・実行順（`after`）・触るファイル（`touches`）を持つ
- NDF が機械が読む形を読み、単位ごとの実装の作業を実行順に並べて流す
- 大きさの確かめ: 単位ごとの見込みの行数を数え、上限を超える単位で止まるか警告し、分け方の案を返す。上限は設定で変えられる
- `standard`・`legacy-refactor` の工程「計画」（実装計画を書く工程）を設計のフェーズへ移し、詳細設計の後に実装計画を書く
- 設計書の「設計の結果」の表と実装計画の単位の関係を決める（課題ごとの表のままにするか、単位まで広げるか）

含まない:
- 11.0.10 で入った部分（レビューの単位の欄・単位ごとの PR と cross-review・課題 1 つを 1 単位にする既定・400 / 1,000 行の目安・単位の実装とレビューの重ね合わせ）。上の「今の姿」の表のとおりで、作り直さない
- 実装の途中で範囲が広がったときの分け直し。広がった分は、その場で直せる不具合は直す。ほかは、利用者に届いた不具合と、人の安全・秘密・利用者のデータ・戻せない操作・承認資料の正しさに関わるものだけを別の課題にし、残りは実装計画か元の課題の記録に残す

## 前提

- 前提 1: 実行順は、単位ごとに「先に要る単位の実行順の最大 + 1」（先に要るものが無ければ 1）とする。実行順は依存の深さを読むための番号である。単位は、先に要る単位をすべてマージしたら始め、依存していない単位の終了は待たない。依存の関係が無い単位は並列に実装する。レビューと自動の検査が済んだ単位から 1 つずつマージする。実装計画の「マージの順」は、同時に済んだ単位のうちどれを先にマージするかの順である。1 回の実装で同時に流す本数には上限があり、超える単位は待って、枠が空いたら始める。コンピュータ全体で同時に動く重い処理（AI の起動とテスト）の量は、今ある空き待ちの仕組みで抑える。実行順は変わらない
- 前提 2: 依存の向きの既定は、コントラクトと共有の部品 → 読み手の付け替え → 旧いものの削除の順とする。単位 A が単位 B の作るもの（型・コントラクト・関数）を使うなら、B に A より前の実行順を付ける
- 前提 3: 並列にできるものの例は、依存の無い単位の実装・テストの先書き・文書だけの単位・機械的な一括の変更（ディレクトリ単位に割る）である。直列に残すものの例は、共有のコントラクトを作る単位とそれを使う単位・同じファイルを触る単位・旧いものの削除（読み手の付け替えがすべて入った後）である
- 前提 4: 行数の数え方は、11.0.10 の目安と同じく追加と削除の和で、再生成するファイルと lock を数えない
- 前提 5: 機械が読む形の「触るファイル」は予測であり、制限ではない。実装が書かれた以外のファイルを変えても、それだけでは失敗にしない（利用者が 2026-11-24 に決めた方針。 https://github.com/devbasex/ai-plugins/issues/4295 ）
- 前提 6: 設計承認ゲートで利用者が変更を求めたら、実装計画を直し、単位の大きさを数え直す

## 受け入れ条件

- [ ] 1. `standard`・`legacy-refactor` の設計のフェーズが、詳細設計の後に実装計画を作り、設計 PR に載せる。設計承認ゲートの数は変わらない
- [ ] 2. 実装計画の単位が、実行順・依存の向き・マージの順を持ち、実装計画に並列にするもの・直列に残すものの表が理由つきである
- [ ] 3. 実装計画が機械が読む形（単位・実行順・触るファイル・満たす受け入れ条件）でも出て、NDF がそれを読んで単位ごとの実装の作業を実行順に並べる。依存の無い単位は並列に流れる
- [ ] 4. 工程「計画」が設計のフェーズへ移り、設計承認ゲートの前に実装計画を書く（`standard`・`legacy-refactor`。`operation`・`documentation` の工程「計画」は実装のフェーズに残す）。実装計画を省く課題は今どおり課題 1 つを 1 単位にする
- [ ] 5. 見込みの行数が上限を超える単位で、NDF が大きさの確かめで止まるか警告し、分け方の案を返す
- [ ] 6. 上限は設定で変えられ、既定値は 11.0.10 の目安と同じ 1 単位 400 行と、超えてはならない 1,000 行である。既定値の根拠（過去の PR の大きさと cross-review の時間・指摘の数）が設計にある
- [ ] 7. #3698 と #3247 の大きさの単位を入力にしたテストで、大きさの確かめが止まるか警告する。400 行以下の単位では何も出ない
- [ ] 8. #3672 の詳細設計（`issues/issue-3672-design-detail.md`）を入力にすると、上限に収まる複数の単位に分かれ、実行順が依存の向きに沿う（コントラクト → 読む部品と解析 → 工程の読み手の付け替え → 削除とテストの移し替え）

## 用語

| 用語 | 意味 |
| --- | --- |
| レビューの単位 | 1 本の PR にまとめ、1 回のコードレビューを掛ける変更のまとまり。この本文の「単位」はこれを指す |
| 単位の PR | レビューの単位 1 つを載せ、スプリントブランチへ出す PR |
| 実装計画 | 実装の前に `issues/` へ書く、どの順で、どのタスクに分けて作るかの計画 |
| 設計の結果 | 設計文書の同じ名前の表。課題ごとの扱い・統合先・触るファイルを持つ |
| 触るファイル | その実装が変えると見込むファイルの一覧 |
| 設計承認ゲート | 設計の Pull Request のマージの前に、人の承認を求める点 |

この本文の「実行順」は単位の依存の深さを表す番号（前提 1）、「機械が読む形」はプログラムが読める、実装計画と同じ内容のデータを指す。
