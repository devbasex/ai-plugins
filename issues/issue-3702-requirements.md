## 何が起きたか

2026-11-16、#3672（ブランチ戦略の宣言の作り直し）の実装が、1 本の PR #3698 に 319 ファイル・+11,923 / −4,834 行でまとまった。cross-refactoring（複数の AI で構造の改善を提案し合う工程）に約 49 分、cross-review（複数の AI で差分をレビューし合う工程）に 2 時間以上かかり、指摘の直しの間に CI の失敗が 85 件出た。#3092 の実装 PR #3247（246 ファイル・CI の失敗 70 件）も同じ形だった。

利用者は「本来 #3672 に対しては複数の PR を立てて個別に refactoring や cross-review を並行して進めるべきだった」と指摘し、詳細設計の後に実装計画を作り、順序と並列にするものを決めるよう求めた（原文は末尾）。

そのうち、PR をレビューできる大きさに分ける部分は 11.0.10 で入った（#3879・#3868）。残っているのは、**分け方を設計承認ゲートの前に決めること**と、**順序と並列を表で持ち、機械が読んで大きさを確かめること**である。

## 種類

機能追加（今の約束は「実装のフェーズの中で実装計画を書き、レビューの単位を AI が読んでプランを組む」で、設計 PR に載せること・実行順の表・機械が読む形・大きさの検査は約束に無い）

## 今の姿

実装計画（Skill `implementation-plan`）は、実装する人とコードレビュー担当が「どの順で、どのタスクに分けて作るか」を引く文書である。11.0.10 で次が入った。

| 入ったもの | 中身 | SSOT |
| --- | --- | --- |
| 「レビューの単位」の欄 | 単位ごとに 1 行。列は単位の名前・含むタスク・満たす受け入れ条件・見込みの差分の行数・実際の行数 | [implementation-plan の SKILL.md の「レビューの単位」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/implementation-plan/SKILL.md) |
| 課題 1 つを 1 単位にする既定 | 見込みが 1,000 行を超える課題はタスクの依存の向きで分け、小さな課題（合わせて 400 行以下）は束ねてよい | 同上 |
| 大きさの目安 | 1 単位 400 行以下、1,000 行を超える単位は作らない。行数は追加と削除の和で、再生成するファイルと lock は数えない | 同上 |
| 単位ごとの PR と cross-review | 単位ごとに PR をスプリントブランチへ出し、その PR で cross-review を収束まで回してからマージする | [development-workflow の SKILL.md の工程表](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/SKILL.md)・[agent-layers.md の「実装のフェーズの単位」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/agent-layers.md) |
| 単位の実装とレビューの重ね合わせ | 準備のタスクを含む単位を最初に流してマージし、残りの単位は並列に流す。ある単位の cross-review の間に別の単位の実装が進む | 同上 |

まだ次の形である（2026-11-20、main `ad05e476d` で確かめた）。

- **実装計画を作るのは実装のフェーズの中である。** 工程「計画」（[stages/plan.json](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/contracts/workflow/stages/plan.json)）は `phase: implement` で、作業場所（worktree）を用意した後に動く。分け方は設計承認ゲートの後に決まり、承認する人は見ない。実行計画の実装の行も、まず課題ごとの仮の行を置き、計画が書けた後に単位の行へ置き直す（[execution-plan.md の「実装の行は 2 回置く」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/issue-plan-strategy/references/execution-plan.md)）
- **順序は「準備の単位が先、残りは並列」の 2 通りだけである。** 単位どうしの依存・実行順・マージの順と、並列にするもの・直列に残すものを書く欄が無い
- **設計承認ゲートの後に機械が読むのは、設計書の「設計の結果」の表（課題・扱い・統合先・触るファイル）だけで、単位は課題である。** 1 つの課題を複数の単位に分ける形を持たない（[design-template.md の「設計の結果の書き方」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/design/references/design-template.md)）
- **単位の欄を読むのは AI だけである。** 実装のフェーズの supervisor（工程を回す実行主体）が Markdown の表を読んで単位ごとにプランを組む。スプリントの組み立て（`ndf progress new` と、プランを組む `plugins/ndf/src/ndf/core/plan/`）と計画の検査（`ndf lanes init`・`ndf plan check`）は単位を読まない
- **400 行・1,000 行は手順書の目安で、機械は確かめない。** `plugins/ndf/src/` に単位の行数を数えるコードは無い（`git grep -n 'レビューの単位' -- 'plugins/ndf/src/**/*.py'` は受け入れ条件の照らし方の注記 1 件だけ）

## 何を足すか・変えるか

| | 今 | 足した後 |
| --- | --- | --- |
| 実装計画を作る時点 | 実装のフェーズの中（worktree の後） | 詳細設計の直後。設計 PR に載り、設計承認ゲートで設計と一緒に見る |
| 単位の順序 | 準備の単位が先、残りは並列 | 単位ごとに実行順・依存の向き・マージの順を持つ。並列にするもの・直列に残すものを理由つきの表で持つ |
| 単位を読む側 | 実装のフェーズの supervisor（AI）が文書を読む | 実装計画を機械が読む形でも出し、スプリントの組み立てがそれを読んでプランを実行順に積む |
| 大きさの確かめ | 手順書の目安だけ | スプリントの組み立てか計画の検査が数えて、上限を超える単位で止まるか警告し、分け方の案を返す |
| 工程「計画」 | 実装のフェーズで実装計画を書く | 設計のフェーズで書いた実装計画を読む側にするか、外す |

## 今の利用者への影響と互換

- 設計 PR に実装計画が加わり、設計承認ゲートで見る文書が 1 つ増える。承認ゲートの数は変わらない
- 実装計画を省く課題（[文書の役割の表の「省いてよい文書と条件」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/requirements-design/references/document-roles.md#省いてよい文書と条件)）は、今どおり課題 1 つを 1 単位にする

## なぜ困るか

- 分け方が設計承認の後に決まるので、承認する人は「何本の PR に分かれ、どの順に入るか」を見ずに承認する。分け方が誤っていても、実装が始まるまで誰も気づかない
- 順序と並列を書く欄が無いので、契約を作る単位と使う単位を並列に流す・同じファイルを触る単位を並列に流すなど、作り直しや取り込みの衝突を生む組み方を止められない
- 大きさを機械が確かめないので、目安を外れた単位（#3698 の 16,757 行のような）が手順書の読み落とし 1 つで再び 1 本の PR になる

## 目的

- 大きな課題（統合 Issue・作り直し・用語の置き換え）を NDF で実装する利用者が、設計承認ゲートで PR の分け方・順序・並列にするものを見て承認でき、上限を超える単位を機械が止める

## 対象範囲

含む:
- 詳細設計の直後に実装計画を作り、設計 PR に載せる（`standard`・`legacy-refactor` の設計のプラン）
- 実装計画の単位に、実行順・依存の向き・マージの順を持たせ、並列にするもの・直列に残すものの表を置く（下の「前提」の決め方）
- 実装計画を文書と機械が読む形の両方で出す。機械が読む形は、単位・実行順（`after`）・触るファイル（`touches`）を持つ
- スプリントの組み立てが機械が読む形を読み、単位ごとのプランを実行順に積む
- 大きさの関門: 単位ごとの見込みの行数を数え、上限を超える単位で止まるか警告し、分け方の案を返す。上限は宣言で変えられる
- 工程「計画」を、設計のフェーズで書いた実装計画を読む側に変えるか外す
- 設計書の「設計の結果」の表と実装計画の単位の関係を決める（課題ごとの表のままにするか、単位まで広げるか）

含まない:
- 11.0.10 で入った部分（レビューの単位の欄・単位ごとの PR と cross-review・課題 1 つを 1 単位にする既定・400 / 1,000 行の目安・単位の実装とレビューの重ね合わせ）。上の「今の姿」の表のとおりで、作り直さない
- 実装の途中で範囲が広がったときの分け直し（別の課題にする）

## 前提

- 前提 1: 実行順は、単位ごとに「先に要る単位の実行順の最大 + 1」（先に要るものが無ければ 1）とする。同じ実行順の単位は並列に実装し、次の実行順は前の実行順のマージの後に始める。同じ実行順で同時に流す本数は、1 本のレーンが同時に流せるプランの本数とマシンの上限の中に収め、超える分は次の実行順へ送る
- 前提 2: 依存の向きの既定は、契約と共有の部品 → 読み手の付け替え → 旧いものの削除の順とする。単位 A が単位 B の作るもの（型・契約・関数）を使うなら、B に A より前の実行順を付ける
- 前提 3: 並列にできるものの例は、依存の無い単位の実装・テストの先書き・文書だけの単位・機械的な一括の変更（ディレクトリ単位に割る）である。直列に残すものの例は、共有の契約を作る単位とそれを使う単位・同じファイルを触る単位・旧いものの削除（読み手の付け替えがすべて入った後）である
- 前提 4: 行数の数え方は、11.0.10 の目安と同じく追加と削除の和で、再生成するファイルと lock を数えない

## 受け入れ条件

- [ ] 1. `standard`・`legacy-refactor` の設計のプランが、詳細設計の後に実装計画を作り、設計 PR に載せる。設計承認ゲートの数は変わらない
- [ ] 2. 実装計画の単位が、実行順・依存の向き・マージの順を持ち、実装計画に並列にするもの・直列に残すものの表が理由つきである
- [ ] 3. 実装計画が機械が読む形（単位・実行順・触るファイル・満たす受け入れ条件）でも出て、スプリントの組み立てがそれを読んで単位ごとのプランを実行順に積む。同じ実行順の単位は並列に流れる
- [ ] 4. 工程「計画」が設計のフェーズへ移り、設計承認ゲートの前に実装計画を書く（`standard`・`legacy-refactor`。`operation`・`documentation` の工程「計画」は実装のフェーズに残す）。実装計画を省く課題は今どおり課題 1 つを 1 単位にする
- [ ] 5. 見込みの行数が上限を超える単位で、スプリントの組み立てか計画の検査が止まるか警告し、分け方の案を返す
- [ ] 6. 上限は宣言で変えられ、既定値は 11.0.10 の目安と同じ 1 単位 400 行と、超えてはならない 1,000 行である。既定値の根拠（過去の PR の大きさと cross-review の時間・指摘の数）が設計にある
- [ ] 7. #3698 と #3247 の大きさの単位を入力にしたテストで、関門が止まるか警告する。400 行以下の単位では何も出ない
- [ ] 8. #3672 の詳細設計（`issues/issue-3672-design-detail.md`）を入力にすると、上限に収まる複数の単位に分かれ、実行順が依存の向きに沿う（契約 → 読む部品と解析 → 工程の読み手の付け替え → 削除とテストの移し替え）
