# #1111 プロジェクトのユビキタス言語を先に定めて設計する: 要求と受け入れ条件

この文書は課題 #1111 の本文の写しである。**正は課題の本文**で、食い違ったときは本文に合わせる（本文の「進行」の節は写さない）。

## 依頼（原文）

> 用語集作って思ったけど、この開発ワークフロー、DDDの発想があまり入っていないですね。
> 設計レビューが遅い原因の一つの一つな気がする。
>
> 改善案を出してください

> 「今回の用語集を唯一の語彙にし」など、ai-agentsが前提になってる。汎用的にするなら「まずプロジェクトのユビキタス言語を定め、それに基づいて設計する」とかではないでしょうか。全体的に見直し。

（2026-09-25 利用者。見直した案を「起票して要求から」で承認）

## 目的

- 要求と設計の前に、そのプロジェクトのユビキタス言語（語・意味・コンテキスト）が定まっている状態にする
- 設計レビューで、語のずれ・文書間の食い違いを LLM が見つけ直すラウンドを減らす（ai-plugins の設計 PR #742 では、返信を除いたインラインの指摘 97 件のうち、語・定義に当たるものが 32 件、食い違いに当たるものが 45 件あった。数え方は設計の決定 10 の語の並び）

## 決めたこと（2026-09-25 利用者）

| 問い | 決定 |
| --- | --- |
| 用語集の形 | 構造化ファイルを正とし、人が読む Markdown の文書を必ずそこから作る（ユビキタス言語は関係者全員が読むため、人が読める文書は必須） |
| 宣言の無いプロジェクト | 必ず作らせる。宣言と用語集が無いうちは設計の工程へ進めない |
| チェックが当たったときの強さ | すべて落とす（廃止した語も未登録の語も） |
| 1 語 1 意味を守る範囲 | コンテキストごと。境界を越えれば同じ字が別の意味を持ってよい |
| 用語集の育て方 | ほぼ空から始める。既に内容のあるプロジェクトは文書とコードから語を集め、スクラッチから作るプロジェクトは要求から大まかに起こす。どちらも設計とレビューをしながら育てる |

## 前提

- 前提 1: 「必ず作らせる」が当たるのは、工程表に設計の工程を持つモードである。`light` / `documentation` / `operation` の振る舞いは変えない
- 前提 2: 宣言のファイル名・用語集の形式（YAML か JSON か）・項目の名前は設計で決める。この文書は項目が持つべき情報だけを決める
- 前提 3: 用語集はプロジェクトのリポジトリに置き、レビューを通して変える。NDF のプラグインの中には置かない
- 前提 4: 「必ず作らせる」が求めるのは宣言と用語集のファイルがあることで、中身の量は問わない。ほぼ空の用語集で設計の工程へ進んでよい
- 前提 5: 未登録の語が落ちたときは、その語を同じ変更の中で用語集へ足せば通る。用語集はこの繰り返しで育つ
- 前提 6: NDF が配る開発ワークフローの語彙（`development-workflow/references/glossary.md`）は、この課題のユビキタス言語とは別のものである。NDF の語彙の改名は #1107 が持つ

## 対象範囲

含む:
- `.ndf/` の宣言で、プロジェクトの用語集の場所と形式を受ける仕組み
- 用語集の項目: 語・意味・コンテキスト・廃止した語（旧称）・正本
- 要求の工程（`requirements-design`）で用語集を起こす手順。既に内容のあるプロジェクトは文書とコードから語の候補を集め、スクラッチから作るプロジェクトは要求から大まかに起こす。どちらも利用者が採った語だけを書く
- 要求に出る語を用語集と突き合わせる手順
- 設計とレビューの中で用語集を育てる手順（新しい語・意味の変わった語・廃止する語を、同じ変更の中で用語集へ反映する）
- 設計の工程（`design`）の設計文書の雛形に、ドメインモデルの節（コンテキスト・集約とその持ち主・不変条件・ドメインイベント）を置くこと
- 宣言された用語集を読み、追加した行の廃止した語・未登録の語を落とす汎用のチェック
- 設計レビューをモデル → 詳細の 2 段にすること（関門の数は変えない）と、`cross-review` の設計の観点に用語・不変条件・コンテキストの境界を足すこと
- 振り返りと `issue-upkeep` で、増えた語・揺れた語を拾うこと
- 要求の工程に、ドメインイベントを時間の順に書き出して要求の抜け（例外の経路・順序の前提）を探す手順を置くこと（イベントストーミング）
- 設計の不変条件ごとに、実装の前に失敗するテストを 1 つ書くこと（`tdd-cycle`）
- `design` の references に、コンテキストマップの関係（共有カーネル・顧客 / 供給者・順応者・腐敗防止層・公開された言語）・集約の設計の規則（小さく保つ・ほかの集約は ID で参照する・1 トランザクションで 1 集約・集約の間は結果整合）・エンティティと値オブジェクトの区別を足すこと
- ai-plugins に宣言と用語集を置き、この仕組みで次の設計を通すこと

含まない:
- NDF の語彙の改名（#1107）
- コードの識別子の改名（語のチェックの対象は文書に限る。コードに広げるかは別の課題にする）
- 既存の設計文書（`issues/` の過去の設計）を用語集どおりに書き直すこと
- サブドメインの分類（コア / 支援 / 汎用）で工程の重さを変えること（別の課題）
- `legacy-refactor` でのバブルコンテキスト（別の課題）

## 用語

| 用語 | 意味 |
| --- | --- |
| ユビキタス言語 | プロジェクトの関係者とエージェントが、要求・設計・コードで同じ意味に使う語の集まり |
| 用語集 | ユビキタス言語を持つ構造化ファイル（正）と、そこから作る人が読む Markdown の文書。どちらもプロジェクトのリポジトリに置く |
| コンテキスト | 語の意味が 1 つに決まる範囲（境界づけられたコンテキスト） |
| ドメインモデルの節 | 設計文書の先頭に置く節。変更が属するコンテキスト・変える集約とその持ち主・不変条件・ドメインイベントを書く |
| 廃止した語 | 用語集で別の語へ置き換えた語。文書に出たら落とす |
| 不変条件 | 集約がいつも満たす条件。設計のドメインモデルの節に書き、実装の前にテストにする |
| 未登録の語 | 用語として書かれているのに用語集に無い語。何を用語として書いたとみなすかは設計が 1 つに決める |

## 受け入れ条件

- [ ] 設計の工程を持つモードで、宣言か用語集が無いまま設計の工程へ入ろうとすると止まり、用語集を作る手順（要求の工程）を示す
- [ ] 用語集の無いプロジェクトで要求の工程を始めると、ほぼ空の用語集が作られる。既に文書かコードのあるプロジェクトでは、そこから集めた語の候補の一覧が、スクラッチのプロジェクトでは要求から起こした候補の一覧が示され、利用者が採った語だけが用語集に書かれる
- [ ] 語が 0 件か数件の用語集でも、設計の工程へ進める
- [ ] 構造化ファイルから人が読む Markdown の文書が作られ、構造化ファイルを変えて文書を作り直していない変更は、用語集のチェックが落ちる
- [ ] 人が読む文書は、コンテキストごとに語・意味・廃止した語・正本を読める
- [ ] 設計文書かレビューの修正で新しい語を使うと、語のチェックが落ち、同じ変更の中で用語集へ語を足すと通る。語の意味を変えたとき・語を廃止したときも、同じ変更の中で用語集を直す
- [ ] 要求の工程で、要求文書に出る語のうち用語集に無いもの・廃止した語が一覧になり、受け入れ条件を書く前に解消される
- [ ] 用語集の項目は、語・意味・コンテキスト・廃止した語・正本を持つ。同じコンテキストの中で同じ語が 2 つの意味を持つと、用語集のチェックが落ちる
- [ ] 異なるコンテキストでは同じ語が別の意味を持ってよく、用語集のチェックは落ちない
- [ ] 設計文書の雛形の先頭にドメインモデルの節があり、`design` の手順がそれを最初に書かせる
- [ ] 要求の工程の手順に、ドメインイベントを時間の順に書き出す段があり、書き出した一覧が要求文書に残り、設計のドメインイベントの節の材料として渡る
- [ ] 設計の不変条件の 1 つごとに、実装の前に失敗するテストが 1 つある。`tdd-cycle` の手順が、設計の不変条件の一覧からテストを書かせる
- [ ] コンテキストをまたぐ変更の設計文書は、コンテキストマップの関係を 1 つ宣言する。`design` の references に、関係の一覧・集約の設計の規則・エンティティと値オブジェクトの区別がある
- [ ] 語のチェックは、宣言された用語集を読み、追加した行に廃止した語か未登録の語があれば終了コード 0 以外で終わり、当たった語と行を返す
- [ ] 語のチェックのスクリプトに、特定のプロジェクトの語は無い（ai-plugins の語を消した用語集でも動く）
- [ ] 設計レビューは、ドメインモデルの節を先に確定させ、確定の後で詳細をレビューする。関門の数は増えない
- [ ] `cross-review` の設計の観点に、用語集どおりか・不変条件を破っていないか・コンテキストの境界を越えていないかがある
- [ ] 振り返りと `issue-upkeep` が、その変更で用語集に足された語・廃止された語を報告に出す
- [ ] ai-plugins に宣言と用語集があり、次の設計 PR で、設計の決定 10 の語の並びで数えた語・食い違いの指摘の件数とレビューのラウンド数を記録する
- [ ] `light` / `documentation` / `operation` のモードの工程と所要は変わらない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 語のチェックは LLM を使わない。ai-plugins の設計文書 1 本に対して 5 秒以内に終わる |
| 運用・保守性 | 用語集の形式・チェックの対象・厳しさはプロジェクトの宣言が持ち、NDF のスクリプトに埋め込まない |
| 移行性 | 宣言の無い既存のプロジェクトは、次に設計の工程へ入るときに用語集を作る手順へ案内される。それまでの工程は止まらない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`.ndf/` に宣言が 1 つ増え、設計の工程の入口の条件が 1 つ増える |
| データ | プロジェクトのリポジトリに用語集のファイルが 1 つ増える |
| 既存の振る舞い | 設計の工程を持つモードで、宣言が無いと設計の工程へ進めなくなる |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| テスト | `uv run --project plugins/playwright-kit/skills/playwright-kit-ops --with pytest pytest . -q -n 4` |
| 語のチェック | 一時リポジトリに宣言と用語集を置き、廃止した語・未登録の語・同じコンテキストの重複・別のコンテキストの同じ語を入れた文書でチェックを打ち、終了コードと出力を確かめる |
| 汎用性 | ai-plugins の語を 1 つも含まない用語集で、上の確かめ方がすべて通る |
| 効果 | ai-plugins の次の設計 PR で、レビューコメントを設計の決定 10 の語の並び（試行のスクリプト）で数え、目的の #742 の値と比べる |
