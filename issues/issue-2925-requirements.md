## 目的

リポジトリの文書（`docs/`・README・Skill の本文・エージェント定義・手順書・`issues/`）の変更に、リファクタリング（cross-refactoring）と全体テストを掛けない。文書にリファクタリングを通しても得るものが無く、全体テストは CI で 1 回あたり中央値 12.6 分掛かり、Pull Request あたり 3〜4 回走る（#2907）。

今の決まりでは次のようになる。

- `docs/` と README だけの変更は light で、リファクタリングの工程を通らない
- NDF の Skill の本文は AI の振る舞いそのものなので、変えると「本番の振る舞いの変更」として standard になり、cross-refactoring と全体テストを必ず通る
- コードと文書が混ざった Pull Request（例: スプリントの Pull Request #2917・#2748）は全体が standard になり、文書の部分にも cross-refactoring が掛かる
- documentation モードは、リポジトリの外の読み手へ渡すビジネス文書だけが対象で、リポジトリの文書は対象外

文書の変更に合った工程にすると、開発者と並行開発のレーンが Pull Request のマージまで待つ時間と、CI のランナーと AI の費用が減る（PR #2905 の分析で、仕上げと検査のプランの費用・テストの時間が大きかった）。

## 前提

- 前提 1: 「文書のファイル」の既定は Markdown（`*.md`）と、用語集の機械向けの形（`docs/glossary/` の JSON）とする。それ以外はコードのファイルとして扱う。既定はプロジェクトの設定で変えられる（受け入れ条件 11）
- 前提 2: 差分のファイルの一覧が取れないとき・分け方の設定が読めないときは、文書だけと判定せず、今と同じ工程を通す
- 前提 3: ビジネス文書の documentation モードの工程（素材の収集・体裁レビューなど）は変えない
- 前提 4: CI のワークフローの変更（#2907 の受け入れ内容）は ai-plugins のリポジトリの中の変更で、NDF のリリース対象の振る舞いではない。同じ「文書のファイル」の分け方を使う

## 対象範囲

含む:

- `development-workflow` のモードの判定表と工程表（light と documentation の定義・例示、リファクタリングの行の決まり）
- 検査のプランが cross-refactoring と全体テストを掛けるかの選び方と、cross-refactoring へ渡す範囲
- CI のワークフローの、変更されたパスによるジョブの選び方（#2907 を取り込む）
- Skill の本文・エージェント定義・手順書を変える Pull Request の、振る舞いを確かめる工程

含まない:

- ビジネス文書の documentation モードの工程
- テストそのものの棚卸しと削除（2026-10-31 の方針「テストを削る」は別に扱う）
- 新しいモードの追加（未決 2）
- コードレビュー（cross-review）・完了判定・文書の検査を省くこと。文書だけの差分でもこれらは今と同じに通る

## 受け入れ条件

差分の中身による工程の選び方:

- [ ] 1. 差分が文書のファイルだけの Pull Request では、検査のプランが cross-refactoring を起動しない。実行の記録に、飛ばしたことと理由（文書だけの差分）が残る
- [ ] 2. 差分が文書のファイルだけの Pull Request では、検査のプランが全体テストを走らせない。実行の記録に、飛ばしたことと理由が残る
- [ ] 3. コードと文書が混ざった Pull Request では、cross-refactoring へ渡す範囲に文書のファイルが入らない（範囲はコードのファイルとテストの置き場所だけ）。全体テストは今と同じに走る
- [ ] 4. テストが読む文書を含み、コードのファイルを含まない Pull Request では、全体テストの代わりに、その文書を読むテストが走る。落ちればマージを塞ぐ
- [ ] 5. 差分のファイルの一覧が取れないとき、または分け方の設定が読めないときは、cross-refactoring と全体テストを今と同じに通す

CI（#2907 を取り込む）:

- [ ] 6. 差分が文書のファイルだけの Pull Request で、CI の pytest の全体のジョブ（`pytest (0/2)`・`pytest (1/2)`）が走らない。用語集を変えた設計 Pull Request・確定仕様化の Pull Request（#2852・#2926・#2929 と同じ形の差分）もこれに当たる。文書の検査のジョブは走る
- [ ] 7. 省いたときも、必須のチェック `pytest` は成功で終わり、マージを塞がない
- [ ] 8. コードかテストを含む Pull Request では、今と同じジョブが走る

Skill の本文の変更:

- [ ] 9. Skill の本文・エージェント定義・手順書を変える Pull Request では、振る舞いの確認を通り、確かめた手順と結果が Pull Request の記録に残る（cross-refactoring と全体テストは通らない）

モードの定義:

- [ ] 10. `development-workflow` の判定表・工程表に、差分の中身で cross-refactoring と全体テストを選ぶことと、その条件が書かれている。light と documentation の定義・例示を見直した結果（変えた点、または変えない理由）が設計文書にある
- [ ] 11. 文書のファイルの分け方はプロジェクトの設定で変えられ、設定が無いプロジェクトでは前提 1 の既定で動く。ai-plugins のパス（`docs/glossary/` など）を NDF の既定に埋め込まない
- [ ] 12. 採る工程の表を、設計承認ゲートで利用者が決める

退行しないこと:

- [ ] 13. 文書だけの差分でも、コードレビュー（cross-review）・完了判定・文書の検査は今と同じに通る
- [ ] 14. ビジネス文書の documentation モードの工程は変わらない

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 用語集を変えた文書だけの Pull Request で、CI の pytest の所要が今の 1 ジョブ 11〜15 分から、用語集を読むテストだけの所要へ縮む。実測を実装の Pull Request に載せる |

| システム環境 | NDF を使う他のプロジェクトでも、設定を置かずに前提 1 の既定で動く（Value 6） |
