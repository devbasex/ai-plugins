## 目的

範囲外の課題を起票するとき、今は LLM が `out-of-scope/SKILL.md`（10,372B）と `references/issue-target.md`（7,536B）を読み、起票先の解決（bash の囲み 20 行余り）・重複の検索・本文の 5 項目の確認・由来の書き込みを 1 手ずつ組み立てている。この決まった手順を 1 本のスクリプトへ移し、LLM に残すのは「範囲内か・起票するか」の判断、起票先の判断表で決まらないときの判断、本文を書くことだけにする（#845 の段 1 をスクリプトへ）。

達成したい状態: `out-of-scope` と `retrospective` の起票まわりの決まった手順が、`issue-file` の呼び出しと結果 JSON（#846 の形）の読み取りになる。起票先・重複・由来の扱いは今の手順書と同じ結果になる。

## 前提

- 前提 1: #480 の抽象化は作らない（閉じた）。`issue-file` は GitHub を `gh_call` 経由で呼ぶ。GitHub 以外の追跡先は扱わない
- 前提 2: 起票先が決まらないときの終了コードは、依頼文の exit 2 ではなく、#846 の契約の「LLM の判断待ち」（20〜29）を使う。2 は「呼び出しの誤り・読めない」に残す（2 を判断待ちに使うと、gh の失敗と見分けられない）
- 前提 3: 部品を呼ぶ側の置き換えは、`out-of-scope`（#865）と `retrospective` の手順 1 の検索に限る。`fix` と `pr-review` は `/ndf:out-of-scope` を経由するため、本文を変えなくても部品を使う。`backlog-refinement` の親 issue の起票は 5 項目の骨格と由来を持たないため対象にしない
- 前提 4: `out-of-scope` の置き換え（#865）は、この課題と同じ Pull Request で行う。呼ぶ側の無い部品だけを先に出さないためである。#865 固有の受け入れ条件（本文の量）は #865 が持つ
- 前提 5: 起票の前に起票先・題・本文・ラベルを提示して同意を取る、という今の決まり（`out-of-scope` の手順 5）は変えない。起票先が開発対象リポジトリと別のとき、起票は他のリポジトリへの公開（C5）に当たる
- 前提 6: `orphans` が返すのは、由来で見つかった起票済みの課題の一覧である。「起票されていない指摘」の判定（3 か所との突き合わせ）は、指摘の文面を読む判断なので LLM に残す。サブコマンドの名前は設計で決め直してよい
- 前提 7: 起票した番号を元の場所（Pull Request の本文・実装計画・レビューの返信）へ戻す手順（`out-of-scope` の手順 6）は呼ぶ側に残す。戻す先が場面ごとに違い、レビューの返信と resolve は `fix` が持つためである
- 前提 8: スクリプトは `$SCRIPTS`（`development-workflow` の `references/scripts-lookup.md`）で引ける場所に置き、4 ランタイムへ配る。`out-of-scope` の中だけに置かない（`retrospective` からも呼ぶため）

- `issue-file` のスクリプトと、4 つのサブコマンド（起票先の解決・重複の検索・骨格の検査つき起票・由来での検索）と、既存の課題へ由来を 1 行足す操作（`out-of-scope` の手順 4 の `gh issue comment`）
