## 目的

- cross-review の担当がレビュー本文（総評）にだけ書いた指摘を、インラインのスレッドの指摘と同じく、修正の worker が必ず振り分け、件数に入り、決着するまで収束を止める状態にする
- 振り分けの対象に入れるかを修正の worker（LLM）の読み方に任せず、スクリプトが雛形へ入れる。設計 PR 1970 では worker が総評だけの指摘を拾い、スプリント PR 1973 では拾わなかった。経路によって扱いが揃わない原因は、対象の決め方が未解決のスレッドだけを見ていることにある

## 前提

- 前提 1: 原文の受け入れ条件 1 の「重大以上」は、自動で直す重要度（`critical` / `major`）を指す。PR 1973 で落ちた 5 件が `major` であるため。`minor` / `nit` の総評だけの指摘も同じ雛形へ入り、既存の「重要度の判定」の規則（直さずに見送りの返事を付ける）で振り分ける
- 前提 2: 本文にだけある指摘とは、状態ファイルの `review_findings[]` のうち `posted_to` が `body` のものを指す。差分の外を指す指摘と、`HTTP 422`（`could not be resolved`）で総評へ移した指摘を区別しない（どちらも `posted_to` が `body` になる。`docs/06-evidence.md` の「総評だけへ書いた指摘」）
- 前提 3: `posted_to` を持たない記録は、今の契約どおり `inline` として扱う（`docs/04-contracts.md`）。この変更より前の状態ファイルで総評だけの指摘が数えられないことは許す
- 前提 4: 対象は cross-review の中で `/ndf:fix` を呼んだとき（環境変数 `CROSS_REVIEW_STATE` が状態ファイルを指すとき）に限る。単独で呼んだ `/ndf:fix` は状態ファイルを持たず、今の振る舞いのまま
- 前提 5: GitHub はレビュー本文への返信を受け付けない。総評だけの指摘への返事は、今と同じく修正のまとめのコメントの「レビュー本文の指摘への返事」の行で残す（`skills/fix/SKILL.md` の「戻り値ファイル」）
- 前提 6: 総評だけの指摘が決着したとは、その指摘が修正の戻り値ファイルの `resolved_threads` / `deferred` / `rejected` のどれかに入り、取り込み（`state.py merge-fix`）がそれを記録したことを指す。GitHub の上にスレッドが無いため、決着は状態ファイルが持つ

## 対象範囲

含む:
- 修正の worker へ渡す雛形（`fix-steps.py context` が書く decisions と文脈のファイル）へ、総評だけの指摘を入れる
- `finalize` の検査で、総評だけの指摘の振り分けの漏れを止める
- 取り込みで、総評だけの指摘の決着を状態ファイルに記録する
- 収束の判定（`state.py judge`）・最終スイープ（`state.py verify-sweep`）・まとめの件数（`drive.py` の `findings` / `unresolved`）で、決着していない総評だけの指摘を数える
- PR 1973 のラウンド 1 の形を写したテスト

含まない:
- `HTTP 422` で要求のインラインをすべて総評へ移す振る舞いの変更（差分の中を指す指摘まで本文へ移ることを減らす改善）。総評だけの指摘を落とさなくなれば不具合は起きないため、この課題では扱わない
- 単独で呼んだ `/ndf:fix`（前提 4）
- 担当へ差分の範囲を渡すこと（#1702）と、2 ラウンド目以降に渡す変更（#934）
- PR 1973 で落ちた 5 件の中身の修正（#1979）
- 過去の状態ファイルの書き直し（前提 3）
