# #1909 #1676 #1623 #1496 の設計の決定

設計文書は [issue-1909-design.md](issue-1909-design.md) にある。ここには決定の記録だけを置く。

## 決定の記録

### 決定 1: 上限の数を見える所に残し、手で書いたプランの扱いを変えないため、上限は `new` のときに遷移から求めてプランへ書く

`run` のときに求める形は、`上限` の無いプランの既定 30 を変えてしまい、前提 3 に反する。`new` のときに書けば、conductor はプランを開くだけで上限を読め、手で上げた値もそのまま効く（I3）。照合（L3）は `run` が流す前に毎回行うため、手で書いたプランも、書いた後に雛形が変わったプランも同じように守られる。

採らなかった案: `run` のときに `上限` を求め直す形。書き済みのプランの値を黙って上書きし、移行性の条件（手で上げた `上限` もそのまま効く）を満たせない。

根拠: Value 4 / Value 5（MVV 版 2）

### 決定 2: 計算を速く決まった形にするため、ループを通らない最長の経路は、プランの並びで後ろのステップへ行く遷移だけをたどって求める

並びで後ろへ行く遷移だけのグラフは輪を持たないため、並びの逆順に 1 回たどれば最長が求まり、ステップ 50 本でも時間が延びない。この経路はどれも同じステップを 2 度通らないため、すべての単純な経路を数えた最長を超えない。L3 は「上限がこれより短ければ止める」照合なので、短めに出ても正しく流れるプランを止めない。今のすべての雛形で、2 つの求め方は同じ値（15・1・13・12・10・11）になった。一致し続けることはテストが縛る。

採らなかった案: すべての単純な経路を数える形。ステップの数に対して指数の時間が掛かりうる。

根拠: Value 3 / Value 4（MVV 版 2）

### 決定 3: 要求の実測の伸び（全体テスト +8・doc-lint +2）と同じ長さを数えるため、修正のループは検査のステップの失敗の遷移ごとに数え、長さは修正の work を含む最長の単純な輪にする

実装のプランで全体テストの修正の輪は 8 本である（test-all → judge → fix → test-limited → design-tests → design-specs → design-match → pr）。#1909 の本文の +8 と一致する。最も短い輪を採ると、design-tests の `skip_to` で突き合わせを飛ばす輪（6 本）が選ばれ、突き合わせを通す実際の経路より短くなる。修正の work を含むことを条件にするのは、design-match（設計との突き合わせの work）のように直さない work だけを通る輪を修正と数えないためである。修正の work を含まない輪のうち、`kind: 戻り` のステップを含むもの（起点の取り込み #1917 のマージの衝突からの戻り）は、戻りの上限の回数だけ回るため「戻りの輪」として別に 3 倍で数える（設計文書の「上限の計算」）。

採らなかった案: 後ろへ戻る遷移 1 本ごとに 1 つのループと数える形。範囲テストと全体テストの修正が fix → test-limited の 1 本を共有するため、両方を 3 回ずつ通す経路を数え足りない。

根拠: Value 3 / Value 6（MVV 版 2）

### 決定 4: 雛形がステップを足しても上限を書き直さずに済むよう、雛形の関数から `上限` の数を消し、書き出しの 1 か所で埋める

数を雛形ごとに持つと、ステップを足すたびに数え直しが要り、今回の 4 課題はどれもその数え直しが漏れて起きた。書き出し（`cmd_new`・`cmd_new_sprint`）は全プランが通る 1 か所で、ほかの 2 主題（起点の取り込み・指示と整形）が雛形へステップを足しても `上限` に触れずに済む。雛形の関数で変えるのは `"上限": N,` の 1 行を消すことだけで、steps の並びと遷移は触らない。

採らなかった案: 雛形の数を残し、書き出しが計算の値と大きい方を取る形。残した数は意味を持たないのに、読む人には上限に見える。

根拠: Value 6 / Value 7（MVV 版 2）

### 決定 5: 打ち切りの再試行が上限を食わないよう、遅れの見張りの再試行をステップの数に数えない

再試行の回数はステップごとに `max_retry`（既定 1）が既に止める。上限は修正のループの歯止めで、再試行まで数えると、同じ経路でも見張りの判定しだいで止まるかどうかが変わる。数えないのは「直前のステップが遅れの再試行で同じステップへ戻った」回だけで、ほかの回はすべて数えるため、上限は有限の歯止めのまま残る（L4）。

採らなかった案: 上限に再試行の分を足す形。何本のステップが再試行されるかは流すまで分からず、足す数を決められない。

根拠: Value 1 / Value 6（MVV 版 2）

### 決定 6: 前の実行の結果を確かに引くため、進捗ログの `step` の行へ出力ファイルの名前を足し、それを読む

`state.json` は実行のたびに今の実行の記録だけで書き直され、本文も持たない。`.out` のファイル名の番号は実行ごとに 1 から振り直され、落ちた後に同じステップを流し直すと番号と行の数がずれるため、行の順から番号を数える形は確かでない。`step` の行に `out` を足せば、前の実行の最後の結果のファイルを名前で引ける。鍵を足すだけで、ほかの行と鍵の意味は変わらない。

状態ディレクトリは、`--from` の有無によらず実行の始まりに消さず初期化もしない（今の動きのまま）。前の実行の `.out` は、後の実行が同じ名前（`NN-<ステップ>.out`）を書くまで残る。同じ名前を書き直すのは今の実行で流れたステップだけで、そのステップは今の結果が先に使われる（I7）ため、前の実行の結果としては読まれない。前の実行の結果として今の内容を返す経路は無いので、`.out` をいつ読むかは決めない。`--from` を付けない実行では前の結果を渡さない（I8）ので、残った `.out` は読まれない。

採らなかった案: 実行ごとに状態ディレクトリを分ける形。状態ディレクトリの形が変わり、記録を読む既存の手順（振り返り・`report.md`）が追従を要する。

根拠: Value 4 / Value 6（MVV 版 2）

### 決定 7: 再開で戻す範囲が Pull Request とステップの結果で食い違わないよう、前の実行の範囲の切り方を `recorded_pr` と 1 か所で共有する

前提 4 は、前の実行を Pull Request を戻す範囲と同じにすると決めている。切り方（`--from` を付けない最後の `run` の行より後）を関数 1 つにし、`recorded_pr` と `prior_results` の両方がそれを使う。

採らなかった案: `prior_results` に同じ切り方を書き写す形。片方だけを直すと、Pull Request とステップの結果が別の実行を指す。

根拠: Value 6（MVV 版 2）

### 決定 8: コミットも行も書かない要求・設計の worker の進みを見るため、会話を残す claude -p に `--session-id` を渡し、セッションの記録の伸びを数える

実測では、この worker の claude -p は標準エラーへ 0 バイトしか書かず、標準出力の JSON は終わりにしか出ない。一方でセッションの記録は作業の間ずっと伸びた。`--session-id` で id を起動の前に決めれば、終わる前に記録の置き場を引ける。前提 5 が遅れの見張りの既定の値を変えないと決めているため、下限を延ばす形は採れない。

採らなかった案: 出力の形を `stream-json` に変えて標準出力の伸びを見る形。claude -p の結果の読み方（`call_claude`）の契約が変わり、使用量の帳簿の記録まで直すことになる。

根拠: Value 3 / Value 6（MVV 版 2）

### 決定 9: cross-review の駆動を変えずに進みを見るため、drive の一次の調査で Pull Request の投稿・レビュー・コミットの最も新しい時刻を前の確認の時刻と比べる

#1496 の cross-review は、進みを Pull Request への投稿とコミットで残していた。見張りの側で数えれば、cross-review にも cross-refactoring にも同じように効く。pause を受けた修正の worker の間（`run_log` が外れて出力を見られない間）にも効く。gh はステップの開始では呼ばず、遅れたステップの確認 1 回につき 1 回だけ呼ぶ。数を始まりと比べる代わりに、投稿・レビュー・コミットの時刻（`createdAt`・`submittedAt`・`committedDate`）の最も新しいものを、ステップの開始か前の確認の時刻（`StepWatch.pr_checked`）と比べる。遅れに達しないステップでは gh の呼び出しが増えない。gh が落ちたときは今と同じく出力の伸びだけで判定する。

採らなかった案: cross-review の駆動が段ごとに 1 行を標準エラーへ書く形。ラウンドの途中や修正の worker の間は書かれず、別の Skill の駆動を変えることになる。履歴が少ないときの既定を段の種類ごとに持つ形は、前提 5（既定の値を変えない）に反する。

根拠: Value 4 / Value 6（MVV 版 2）

### 決定 10: 流さないと決まったプランで記録とファイルを作らないため、上限の照合と知らない行き先の照合は `Engine.setup` で最初のステップの前に返す

`setup` はファイルを書かない準備で、耐久ワークフローの打ち直しでも毎回同じ答えを返す。今の `on_exit` の照合もここにあり、同じ場所で行き先の照合を全部の鍵へ広げる。`prepare`（worktree を作る）より前に止まるため、流さないプランが worktree を作らない。

採らなかった案: `flow._plan_steps` の繰り返しの手前で照らす形。`prepare` の後になり、worktree と実行の始まりの行を作ってから止まる。

根拠: Value 2 / Value 4（MVV 版 2）
