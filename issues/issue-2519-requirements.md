## 何が困っているか

`design` など設計の Skill には、設計の前に外部の最新動向・事実上の標準（デファクトスタンダード）・使える既存のライブラリやサービスを調べ、その結果を設計の判断に反映する手順が無い。設計の雛形には「あるべき姿の根拠」の表（種類に「外部の一次情報」がある）はある。しかし「何を調べるか」「いつ調べるか」「調べた結果で何を決めるか」は決まっていない。

そのため設計は、手元のコードと要求の文だけから組み立てられる。業界の標準の形や枯れたライブラリがあっても、自前で作る設計になったり、古い形のまま決まったりする。利用者が後から気づいて指示し、設計をやり直すことになる。

> ## 直し方の案
>
> `design`（と、設計の材料を作る `requirements-design`）に、設計の判断の前に通す「外部の調査」の手順を足す。
>
> 1. **調べる対象を決める。** 触る領域ごとに、次を調べるかを決める。
>    - 業界の事実上の標準・仕様（例: 認可なら IAM・Cedar・OAuth 2.1・RFC 8693・MCP の認可の仕様。認証なら NIST SP 800-63B）
>    - 主要な製品・競合の形（同じ問題を世界の主要な製品がどう解いているか）
>    - 使える既存のライブラリ・マネージドサービス（自前で作る前に）
> 2. **調べた結果を表に残す。** 一次情報の出典（URL と取得日）を付ける。ライブラリは、バージョン・ライセンス・保守の状態（最後のリリース・終了のアナウンス）・要件を満たすかを並べる。
> 3. **判断へつなぐ。** 「自前で作る」「ライブラリを使う」「標準に倣う」のどれを採ったかを決定の記録に書き、採らない案とその理由を残す。自前で作る決定には、比べた候補を必ず並べる。
> 4. **調べられなかったことを書く。** 公開の資料が無い・取得できなかった対象は、「確かめられなかったこと」として残す（`investigation-rules` に合わせる）。
> 5. **省ける条件を決める。** 文言の修正や既存の形の延長など、外部の判断が要らない変更は省けるようにする。省いた理由は 1 行で残す。
>
> 検査の案: 設計文書の決定の記録に「自前で作る」とあるのに、比べた候補（ライブラリ・サービス・標準）の行が無ければ、設計のレビューか `requirements-recheck` に相当する機械の確かめで指摘する。
>
> ## 受け入れ条件（起票時）
>
> 1. `design` の SKILL.md（または references）に、上の 1〜5 の手順と、手順を省ける条件がある
> 2. 設計の雛形に、外部の調査の節（標準・製品・ライブラリの比較と出典）と、「確かめられなかったこと」の欄がある
> 3. 「自前で作る」決定に比べた候補が無い設計文書を、設計のレビューの観点か機械の検査が指摘する
> 4. プロジェクトの MVV に調査の Value が無くても、この手順が働く

## 目的

- 設計が手元のコードと要求の文だけから組み立てられ、業界の標準の形・枯れたライブラリ・主要な製品の解き方を比べないまま「自前で作る」「古い形に寄せる」と決まる状態をなくす
- 設計の承認（承認ゲート 1）の時点で、承認する人が「何と比べてこの形にしたか」を出典つきで読めるようにし、利用者が後から気づいて設計をやり直す手戻りを減らす
- プロジェクトの MVV に調査の Value を足さなくても、`design` を通すだけでこの調査が行われるようにする

## 前提

- 前提 1: 外部の調査は `design` の手順に置き、`requirements-design` には足さない。要求は「何を満たすか」を決め、標準・製品・ライブラリとの比較は「どう作るか」の判断の材料だからである。調べる対象は、`design` の手順 1 で決める触る領域から決める
- 前提 2: 領域ごとに調べるべき標準・製品・ライブラリの一覧を Skill に持たない。一覧は古くなり、プロジェクトごとに領域が違う（Value 6）。手順は「何の種類を調べるか」と「調べた結果の形」だけを決め、例は読み手の理解のために示すにとどめる
- 前提 3: 外部の調査は、`design` を通すすべてのモードで「通すか省くか」を決める。省ける条件に当たる変更（文言・書式の修正、既存の形の延長、外部の判断が要らない変更）は、省いた理由を 1 行残して省く。`light` / `operation` で `design` を通さない変更には掛からない
- 前提 4: 一次情報の取得は、設計を書くエージェントが手元の取得の手段（Web 検索・URL の取得・`gh` など）で行う。取得できなかったものを推定で埋めない
- 前提 5: 既存の設計文書（`issues/` の過去の設計、`docs/specifications/` の確定仕様）を遡って直さない。手順と検査は、この変更の後に書く設計文書に効く
- 前提 6: 棚卸しの見直しで行う「シーズの調査」（ライブラリの競合・周辺環境の変化を調べて起票する。#2315）とは時期と目的が別である。結果の形（出典と調べた日時を持つ）を揃えるかは設計で決める（未決 2）

## 対象範囲

含む:
- `design` の手順に、外部の調査（調べる対象の決定・結果の表・決定への反映・確かめられなかったことの記録・省ける条件・調べる量の上限）を足す
- 設計文書の雛形に、外部の調査の節を足す
- 「自前で作る」と決めた決定に比べた候補が無い設計文書を指摘する仕組み（設計 PR のレビューの観点か、機械の検査）
- 用語集へ新しい語を足す

含まない:
- `requirements-design` の手順の変更（前提 1）
- 領域ごとの標準・製品・ライブラリの一覧（前提 2）
- 既存の設計文書・確定仕様の遡った修正（前提 5）。carul #117 のような既存の決定の見直しは、各プロジェクトの課題で行う
- 棚卸しのシーズの調査（#2315）の変更
- 外部の調査を行う新しい Skill・エージェントの追加

## 用語

| 用語 | 意味 |

| 外部の調査 | 設計の判断の前に、業界の事実上の標準・仕様、主要な製品の解き方、使える既存のライブラリとマネージドサービスを一次情報で調べ、設計文書に残す手順 |

## 受け入れ条件

- [ ] 1. `design` の手順に、外部の調査の手順がある。調べる対象の 3 種類（業界の事実上の標準・仕様 / 主要な製品の解き方 / 使える既存のライブラリとマネージドサービス）ごとに調べるかを決め、調べない種類には理由を 1 行残すと書かれている
- [ ] 2. 設計文書の雛形に外部の調査の節があり、標準・仕様、主要な製品、ライブラリとサービスの比較の表と、確かめられなかったことの欄を持つ。どの表の行も出典（URL と取得日）の列を持つ
- [ ] 3. 雛形のライブラリとサービスの表は、版・ライセンス・保守の状態（最後のリリースの日付・終了のアナウンスの有無）・要件を満たすかの列を持つ

## 根拠にした MVV の項目

- Mission: 開発者が価値を利用者へ届けるまでの時間と費用を減らす（設計のやり直しの手戻りを減らす）
- Value 4: 外の利用で測って決める（carul での実際の手戻りが起点）
- Value 3: やめる・縮めるを既定にする（調べる量の上限と省ける条件）
- Value 6: どのプロジェクトでも使える形を保つ（領域ごとの一覧を持たない・MVV に依らず働く）
- Value 7: 根本原因の場所で直す（プロジェクトの MVV で補うのでなく `design` に置く）
