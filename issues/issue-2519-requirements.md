## 何が困っているか

`design` など設計の Skill には、設計の前に外部の最新動向・事実上の標準（デファクトスタンダード）・使える既存のライブラリやサービスを調べ、その結果を設計の判断に反映する手順が無い。設計の雛形には「あるべき姿の根拠」の表（種類に「外部の一次情報」がある）はある。しかし「何を調べるか」「いつ調べるか」「調べた結果で何を決めるか」は決まっていない。

そのため設計は、手元のコードと要求の文だけから組み立てられる。業界の標準の形や枯れたライブラリがあっても、自前で作る設計になったり、古い形のまま決まったりする。利用者が後から気づいて指示し、設計をやり直すことになる。

## 目的

- 設計が手元のコードと要求の文だけから組み立てられ、業界の標準の形・枯れたライブラリ・主要な製品の解き方を比べないまま「自前で作る」「古い形に寄せる」と決まる状態をなくす
- 設計の承認（承認ゲート 1）の時点で、承認する人が「何と比べてこの形にしたか」を出典つきで読めるようにし、利用者が後から気づいて設計をやり直す手戻りを減らす
- 設計を書く側だけに頼らず、設計 PR・実装 PR のレビューでも「標準・主要な製品・既存のライブラリと比べたか」を確かめる。比べた候補の欠け・出典の欠けと古さ、より良い標準やライブラリの見落としを、レビューの指摘として承認の前に拾う
- プロジェクトの MVV に調査の Value を足さなくても、`design` とレビューの工程を通すだけでこの調査と確認が行われるようにする

## 前提

- 前提 1: 外部の調査は `design` の手順に置き、`requirements-design` には足さない。要求は「何を満たすか」を決め、標準・製品・ライブラリとの比較は「どう作るか」の判断の材料だからである。調べる対象は、`design` の手順 1 で決める触る領域から決める
- 前提 2: 領域ごとに調べるべき標準・製品・ライブラリの一覧を Skill に持たない。一覧は古くなり、プロジェクトごとに領域が違う（Value 6）。手順は「何の種類を調べるか」と「調べた結果の形」だけを決め、例は読み手の理解のために示すにとどめる
- 前提 3: 外部の調査は、`design` を通すすべてのモードで「通すか省くか」を決める。省ける条件に当たる変更（文言・書式の修正、既存の形の延長、外部の判断が要らない変更）は、省いた理由を 1 行残して省く。`light` / `operation` で `design` を通さない変更には掛からない
- 前提 4: 一次情報の取得は、設計を書くエージェントが手元の取得の手段（Web 検索・URL の取得・`gh` など）で行う。取得できなかったものを推定で埋めない
- 前提 5: 既存の設計文書（`issues/` の過去の設計、`docs/specifications/` の確定仕様）を遡って直さない。手順と検査は、この変更の後に書く設計文書に効く
- 前提 6: 棚卸しの見直しで行う「シーズの調査」（ライブラリの競合・周辺環境の変化を調べて起票する。#2315）とは時期と目的が別である。結果の形は出典の項目だけ揃える（設計で決めた。未決の項目 2）
- 前提 7: `design` の手順・設計文書の雛形・検査のスクリプト（`design-survey.py`）は、承認ゲート 1 に出した設計（設計 PR #2523 の `issues/issue-2519-design.md`）の形のまま残す（利用者の指摘）。設計へ新たに足すのは、レビューの側の確認（受け入れ条件 12〜16）と、実装の PR の分け方（受け入れ条件 17）である
- 前提 8: レビューの側の確認は、レビューの工程の 2 つの経路に載せる。1 つは `pr-review` の観点（単独のレビュー）で、もう 1 つは `cross-review` が担当（codex・kiro・claude など）を起動するときに渡す観点である。設計 PR と実装 PR の両方に載せる。設計 PR では設計文書の外部の調査の節と決定の作り方・比べた候補を見る。実装 PR では、差分が同じ課題の設計の作り方と比べた候補に沿っているかを見る
- 前提 9: レビューの担当が自分で外部を調べる取得の手段は、担当のランタイムがすでに持つもの（Web 検索・URL の取得など）に限る。この変更で担当の取得の権限やサンドボックスの設定を広げない。取得できない担当は、推定で「より良いものがある」と指摘せず、取得できなかったことを指摘の本文に書く（前提 4 と同じ規則）
- 前提 10: 実装は 2 つの PR に分ける。1 つ目は `design` の手順・雛形・検査のスクリプトと用語集、2 つ目は `pr-review` の観点と `cross-review` の起動指示の観点である。MVV 版 5 の Value 2 は量の上限の数値を実測から決めるとしており、この要求の時点で数値は決まっていない。そのため、分け方は利用者の指摘の例に合わせる。2 つ目の観点は 1 つ目が決める節の名前と行の形（外部の調査・作り方・比べた候補）を参照するため、1 つ目を先にマージする。版はスプリント単位で上げるため、2 つの PR は同じスプリントで出す

## 対象範囲

含む:
- `design` の手順に、外部の調査（調べる対象の決定・結果の表・決定への反映・確かめられなかったことの記録・省ける条件・調べる量の上限）を足す
- 設計文書の雛形に、外部の調査の節を足す
- 「自前で作る」と決めた決定に比べた候補が無い設計文書を指摘する仕組み（機械の検査 `design-survey.py` と、設計 PR のレビューの観点）
- `pr-review` の観点に、外部の調査の確認（設計 PR・実装 PR）を足す
- `cross-review` の担当への起動指示に、同じ観点と、担当が自分で外部を調べて指摘してよいことを足す（設計 PR・実装 PR）
- 用語集へ新しい語を足す
- 実装を 2 つの PR に分ける

含まない:
- `requirements-design` の手順の変更（前提 1）
- 領域ごとの標準・製品・ライブラリの一覧（前提 2）
- 既存の設計文書・確定仕様の遡った修正（前提 5）。carul #117 のような既存の決定の見直しは、各プロジェクトの課題で行う
- 棚卸しのシーズの調査（#2315）の変更
- 外部の調査を行う新しい Skill・エージェントの追加
- レビューの担当の取得の権限・サンドボックスの設定の変更（前提 9）
- `cross-refactoring` の提案の担当への観点の追加（利用者の指摘はレビューの工程を挙げており、リファクタリングの提案は挙げていない）

| 外部の調査 | 設計の判断の前に、業界の事実上の標準・仕様、主要な製品の解き方、使える既存のライブラリとマネージドサービスを一次情報で調べ、設計文書に残す手順 |
| 自前で作る決定 | 既存のライブラリ・サービス・標準の実装を使わず、プロジェクトの中で作ると決めた決定の記録 |
| 確かめられなかったこと | 外部の調査で、公開の資料が無い・取得できなかった・上限で止めた対象と、その理由（取得の拒否・HTTP の状態・ネットワークの誤り・上限）を並べた欄 |
| 作り方 | 決定の記録の中の 1 行。その決定が機能をどう得るか（自前で作る / ライブラリやサービスを使う / 標準に倣う）を書く |
| 比べた候補 | 決定の記録の中の 1 行。外部の調査の表で比べた行の番号を並べる |

## 受け入れ条件

`design` の手順・雛形・検査（承認ゲート 1 に出した設計のまま残す。前提 7）:

- [ ] 1. `design` の手順に、外部の調査の手順がある。調べる対象の 3 種類（業界の事実上の標準・仕様 / 主要な製品の解き方 / 使える既存のライブラリとマネージドサービス）ごとに調べるかを決め、調べない種類には理由を 1 行残すと書かれている
- [ ] 2. 設計文書の雛形に外部の調査の節があり、標準・仕様、主要な製品、ライブラリとサービスの比較の表と、確かめられなかったことの欄を持つ。どの表の行も出典（URL と取得日）の列を持つ
- [ ] 3. 雛形のライブラリとサービスの表は、版・ライセンス・保守の状態（最後のリリースの日付・終了のアナウンスの有無）・要件を満たすかの列を持つ
- [ ] 4. 手順に調べる量の上限（候補の数か時間）があり、上限に当たったら調査を止め、残りの対象を確かめられなかったことへ書くと書かれている
- [ ] 5. 手順に、取得できなかった対象・公開の資料が無い対象を推定で埋めず、URL か検索の語と理由を確かめられなかったことへ書くと書かれている。書き方は `investigation-rules` の否定的な結論のエビデンスの規則と食い違わない
- [ ] 6. 手順に省ける条件があり、省いたときは理由を 1 行、設計の書き先（`deliverables.md` の「設計の書き先」）に残すと書かれている。省けるか決められないときは通す
- [ ] 7. 決定の記録の書き方（`decisions.md`）に、自前で作る・ライブラリやサービスを使う・標準に倣うのどれを採ったかと、自前で作る決定には外部の調査の節で比べた候補を並べることが書かれている
- [ ] 8. 自前で作る決定に比べた候補が無い設計文書を、機械の検査と設計 PR のレビューの観点が指摘する。指摘の例（候補が無い決定を持つ設計文書）と、指摘されない例（候補を並べた決定・外部の調査を理由つきで省いた設計文書）で確かめられる
- [ ] 9. 手順・検査・レビューの観点は、プロジェクトの MVV が無いプロジェクト・MVV に調査の項目が無いプロジェクトでも働く。手順の文・検査の条件・観点の文が MVV の項目を参照しない
- [ ] 10. 既存の設計文書（`issues/` の過去の設計）があっても、機械の検査がその文書で落ちない（前提 5）
- [ ] 11. 退行しない: `python3 scripts/check-skill-frontmatter.py`・`claude plugin validate .`・全体テストが通る。設計文書の雛形は 500 行以内に収まる

レビューの側の確認（`pr-review` と `cross-review`）:

- [ ] 12. `pr-review` の観点に、外部の調査の確認がある。設計 PR では、設計文書の外部の調査の節と決定ごとの作り方・比べた候補を見て、次を指摘にすると書かれている: 自前で作る決定に比べた候補が無い / 調べた行に出典（URL と取得日）が無い / 出典の取得日が古い（古さの基準は未決の項目 4。設計で決まった） / 外部の調査の節が無い、または省いた理由が無い
- [ ] 13. `pr-review` の観点の実装 PR の側に、差分が同じ課題の設計の作り方・比べた候補に沿っているかを見ることが書かれている。指摘にする例: 設計で「ライブラリやサービスを使う」とした機能を自前で作った / 設計に作り方の行が無い自前の部品を足した / 新しく足した依存（ライブラリ・サービス）が設計の比べた候補に無い
- [ ] 14. `cross-review` が担当（codex・kiro・claude など、選ばれたすべての担当）を起動するときに渡す観点に、受け入れ条件 12（設計 PR）と 13（実装 PR）と同じ観点が載る。観点が載ることを、起動の観点を組む処理（`review_focus.py`）の単体テストで、設計 PR と実装 PR の両方について確かめる。ドキュメントだけの PR には載らない
- [ ] 15. `cross-review` の担当へ渡す観点に、担当が自分で外部の一次情報を調べ、より良い標準・ライブラリ・主要な製品の形があれば出典（URL と取得日）を添えて指摘してよいと書かれている。取得できないときは推定で指摘せず、取得できなかったこと（URL か検索の語と理由）を書くと書かれている（前提 9）
- [ ] 16. 担当が外部を調べる量に上限があり、観点に書かれている。上限の値は設計で決め、`design` の手順の上限と同じ置き場から読むか、違う値にする理由を設計に書く（未決の項目 5。設計で決まった）

実装の進め方:

- [ ] 17. 実装は 2 つの PR に分かれる。1 つ目は受け入れ条件 1〜11（`design` の手順・雛形・検査のスクリプト・用語集。受け入れ条件 8 のうち設計 PR のレビューの観点の側は除く）、2 つ目は受け入れ条件 12〜16 と、受け入れ条件 8 の設計 PR のレビューの観点の側（`pr-review` の観点と `cross-review` の起動の観点）を持つ。どちらの PR も単独で全体テストが通り、1 つ目を先にマージする（前提 10）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 外部の調査が設計の所要を際限なく延ばさない。上限（受け入れ条件 4）の値は設計で決め、実測から見直せる場所に置く。レビューの担当の外部の調べも、レビューのラウンドの所要を際限なく延ばさない（受け入れ条件 16） |
| システム環境 | 手順と観点は Claude Code と Codex のどちらをホストにしても同じに働く。レビューの担当（codex・kiro・claude）ごとに取得の手段が違っても、観点の文は特定のランタイムだけの取得の手段を前提にしない |

## 根拠にした MVV の項目

- Mission: 開発者が価値を利用者へ届けるまでの時間と費用を減らす（設計のやり直しの手戻りを減らす）
- Value 2: 人が判断できる量に収める（実装を 2 つの PR に分ける）
- Value 3: やめる・縮めるを既定にする（調べる量の上限と省ける条件。レビューの担当の調べにも上限を置く）
- Value 4: 外の利用で測って決める（carul での実際の手戻りが起点）
- Value 6: どのプロジェクトでも使える形を保つ（領域ごとの一覧を持たない・MVV に依らず働く・担当のランタイムに依らない観点の文）
- Value 7: 根本原因の場所で直す（プロジェクトの MVV で補うのでなく `design` とレビューの工程に置く）
