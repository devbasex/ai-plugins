## 目的

- NDF の手順のスクリプトが、成功・失敗の判定・記録・後片付け・再試行と上限・入力の解決と、受け渡すデータの名前と形を、それぞれ自分で書かずに済む状態にする。新しいステップを足しても、A〜F（失敗の判定・記録・回復・待ちと上限・解決の時点・並行の衝突）の型の不具合が同じ仕組みで防がれる
- 達成したい状態: 入口とデータの契約が 1 か所の宣言にあり、宣言と実行の核を通らないコードを検査が落とす。既存の A〜F の課題は、型ごとの仕組みを入れた後にまとめて確かめて閉じる

### コードの実物: 入力の渡し方もそろっていない

同じものを受け取るのに、入口ごとに名前・渡し方・置き場所が違う。呼ぶ側（Skill の本文・プランの雛形・conductor）が入口ごとの違いを覚えて書くため、渡し忘れと渡し違いが起きる。

| 観点 | 実物 |
| --- | --- |
| 引数の読み方 | `argparse` 59 ファイル、`sys.argv` を手で読む 16 ファイル。オプションは 311 種類、位置引数は 78 |
| 同じものの別の名前 | リポジトリの根が `--root`（26 ファイル）・`--repo`（17）・`--worktree`（3）・`--dir`（2）・`--cwd`（1）。出力先が `--out`・`--out-dir`・`--output`・`--json`・`--report`。上限が `--timeout`・`--budget`・`--budget-minutes`・`--limit`・`--max`。版が `--version`・`--to`・`--dev`・`--prod`。PR は `--pr` のほかに位置引数で受ける入口がある |
| 環境変数 | 読む環境変数が 56 種類（`NDF_*`・`CROSS_REVIEW_TMP_DIR`・`CROSS_REFACTORING_TMP_DIR` など）。どの入口がどれを読むかの一覧が無い |
| 設定ファイル | `.ndf/` の設定と記録が 15 種類（`project.json`・`worktree.json`・`supervise.json`・`release.json`・`pace.json`・`ask.json`・`review.json`・`runtimes.json` など）。同じ値を 2 か所が持つ（本番のブランチが `worktree.json` の `production_branch` と `project.json` の `delivery`、#2097）。どのファイルをメインディレクトリから読み、どれを worktree から読むかが入口ごとに違う（#2317・#1709） |
| 標準入力 | 標準入力から読むファイルが 28 |
| 値の優先順位 | 引数・環境変数・設定ファイル・既定値のどれが勝つかが入口ごとに違う |

入力が原因に関わる課題の例:

- 雛形が `--sync-command` を渡さない（#2049）
- 予算を渡さず既定の 30 分で打ち切る（#2047）
- オプションの付け忘れで判定が飛ぶ（#2293 の `--with-verification`）
- 着手前のテストがディレクトリを `{paths}` に入れる（#2096）
- 起動の形が書かれておらず codex が標準入力待ちで止まる（#2114）

**成り立ち**: NDF は Skill の手順をスクリプトへ移すことで育った。スクリプトは Skill の 1 つの手順を自動にするために書かれ、そのたびに入力・出力・状態の形をその場で決めた。入口は scripts 直下に 52 本、Skill の scripts 直下に 39 本あり、Skill の本文から呼ばれるスクリプトの行は 60 種類ある。どの入口についても、受け取るもの・返すもの・書く状態を 1 か所に宣言した契約は無い（契約は Skill の本文・README・コードの docstring に散っている）。その後スクリプト同士が互いの出力と状態を読むようになり、決めていなかった契約が、読み違いの不具合として現れている。

**根本の原因**: 1 つのステップが「成功・失敗の判定」「記録」「後片付け」「再試行と上限」「入力の解決」をそれぞれ自分で書き、受け渡すデータの名前と形もそれぞれが決める。部品は呼べば使えるが、呼ばなくても書けて、検査も落とさない。そのため新しいステップのたびに同じ型の不具合が生まれる。

## あるべき姿

**すべての手順のステップは 1 つの実行の核の中で動く。** 核が次の 8 つを引き受け、ステップは仕事の中身だけを書く。

| 核が持つもの | 今の型 | 決まり |
| --- | --- | --- |
| 結果の契約 | A | ステップの出口は `ok` / `gate` / `stopped` の 3 つだけ。例外・中断・時間切れ・判定できないは核が `stopped` と理由に変える。ok は欠けが無いときだけ。worker の報告も同じ形で返し、自由文から完了を読まない |
| 記録 | B | 核が実行の識別子を振り、開始・終了・判断・失敗を 1 つの形の JSON Lines へ書く。標準エラーへの診断も同じ関数を通る。止まった理由は切らずに残す |
| 持ち主と後片付け | C・F | 核が実行の持ち主（lease）を取り、どの終わり方でも（正常・例外・シグナル・時間切れ）終了時刻と片付けを書く。並行の排他も同じ lease で取る |
| 再試行と上限 | D | 上限と再試行の方針を 1 つの表（宣言）に置き、核が当てる。同じ原因の失敗を繰り返さない（打ち直しの回数と、原因が同じかを核が見る） |
| 入力の契約 | E・A | 入口が受け取るもの（引数・環境変数・設定・標準入力）を契約の一覧に宣言し、同じものには同じ名前を使う（リポジトリの根は `--root`、出力先は `--out`、上限は `--timeout` など）。値は 1 つの読み込み部品が「引数 → 環境変数 → 設定 → 既定値」の決まった順で解決し、どこから来た値かを記録へ書く。設定は 1 つの値を 1 か所だけが持つ |
| データの契約 | A・E | 実行・プラン・状態・記録・結果の種類ごとに型（スキーマと版）を 1 つ持ち、同じ意味には 1 つの名前を使う（結果は `status`、時刻は UTC の ISO 8601 の `at` など）。核が読み書きの両方で型を確かめ、合わなければ `stopped` にする |
| 出力の形 | A・B | 機械が読む出力は 1 行 JSON の 1 形だけにする。Markdown は人へ見せる描画で、機械はそれを読まない（フェーズレポートも JSON を正にして Markdown を生成する）。課題・PR の本文から値を読む箇所は、本文に埋めた機械用のブロック（例 `<!-- ndf:... -->` の JSON）か、記録の JSON から読む |
| 入力の解決 | E | プランは値でなく参照（版・PR・宣言・予算）を持ち、核がステップの直前に解決して記録する。解決できなければ流さずに止まる |

**再開は耐久の記録（`durable`）を唯一の手段にする。** `--from` と状態ファイルの手当ては核の上の 1 つの入口へ寄せる。

## 進め方

1 件ずつ直すのをやめ、型ごとにまとめて直す。

0. **契約の棚卸しと定義（最初に行う）**: 入口 91 本と、入口の間で受け渡す状態・記録・結果のファイル（名前 114 種類）を一覧にし、それぞれの入力（引数・環境変数・設定・標準入力）・出力・書く状態・終了コードを 1 か所の宣言（契約の一覧）へ書き出す。`.ndf/` の設定 15 種類と環境変数 56 種類も、どの入口が読むかを書く。今の振る舞いを写すだけで、変えない。ドメインの語（スプリント・プラン・ステップ・実行・課題・PR・リリース・記録）ごとに型を決め、同じ意味の別名を対応表にまとめる。以後の手順はこの一覧を正として進める
1. **止血（先に入れる）**: 新しく足すステップと入口が核を通らなければ、構造の検査（`scripts/check-script-structure.py`）が落とす。今の外れは許可の一覧に載せ、一覧は減る方向にしか変えられない（ratchet）
2. **核とデータの型を作る**: 既存の `step_result`・`proc`・`jsonio`・`locks`・`waits`・`durable`・`run_state` を束ねる。新しく書くのは束ね方・記録と上限の表・データの型の定義（名前の対応表を含む）だけにする。データの型は版を持ち、古い形の読み込みは型の側の移行関数 1 か所で受ける
3. **移す**: 課題の集まる部品から順に核へ移す。分類で集まった部品は次のとおり
   - supervise のプラン・judge・キュー（`supervise_lib`）
   - cross-refactoring（`refactor.py`・持ち主・着手前テスト・最終ゲート）
   - 課題を閉じる処理（`sprint-close.py`・`sprint_close_lib`）
   - リリース（`release-steps.py`・`release_templates.py`）
   - 外部 CLI の監視と結果の受け渡し（`lib/monitor_*`・external-ai）
   - 使用量の帳簿（`lib/usage_*`）
4. **既存の課題をまとめて閉じる**: 移した部品に属する A〜F の課題は、移した後に再現の手順を 1 回ずつ通し、再現しないものを理由を添えて閉じる。1 件ずつの修正の Pull Request は作らない

## ドメインイベント

1 回の入口の実行で起きることを時間の順に並べる。設計のドメインモデルの節は同じ番号を引き継ぐ。

| # | イベント | 引き金 | 失敗したとき | 順序の前提 |
| --- | --- | --- | --- | --- |
| E1 | 入口が起動された | Skill の本文・プラン・conductor・利用者のコマンド | 契約の一覧に無い引数・環境変数を受けた → `stopped`（理由に名前） | — |
| E2 | 入力を解決し、値ごとの出所（引数・環境変数・設定・既定値）を決めた | E1 | 必須の値が無い・1 つの値を 2 か所の設定が持つ → `stopped` | E1 |
| E3 | 実行の識別子を振り、記録へ開始を書いた | E2 | 記録の置き場へ書けない → 標準エラーへ理由を出して `stopped` | E2（記録の置き場はリポジトリの根から決まる） |
| E4 | 持ち主（lease）を取った | E3 | 他の生きた実行が持つ → 待つか `stopped` を結果に出す。死んだ実行の残骸 → 片付けてから取る | E3 |
| E5 | プランの参照（版・記録の PR・宣言・予算）を解決して記録した | E4 | 解決できない・承認ゲートで見た値と食い違う → `stopped` か `gate` | E4（解決は lease の中で行い、並行する実行と同じ値を取り合わない） |
| E6 | 読んだデータの型と版を確かめた | E5 | 古い版 → 型の側の移行関数で読み替える。読み替えられない → `stopped` | E5 |
| E7 | ステップの中身を実行した | E6 | 例外・SIGTERM・時間切れ → `stopped` と理由 | E6 |
| E8 | 失敗したステップを再試行した | E7 の一時的な失敗 | 同じ原因の失敗が宣言の回数に達した → `stopped` | E7 |
| E9 | 書くデータの型と版を確かめた | E7 | 合わない → 書かずに `stopped` | E7 |
| E10 | 結果を `ok` / `gate` / `stopped` と決まった終了コードで返した | E9 か、E1〜E8 のどこかの失敗 | — （欠けがあれば `ok` にしない） | E1 |

| E13 | 中断した実行を耐久の記録から再開した | 利用者・conductor の再開の指示 | 耐久の記録が無い・壊れている → `stopped`。`--from` の指定がある → 指定のステップから始める | E3 の識別子と耐久の記録がある |
