## 目的

- #1142 の移行（2c）の前と後で、**費用**（`claude -p` の使用量をモデル・書き込みの 5 分 / 1 時間の別まで）と**検査**（検査の回数・指摘・修正・流出不具合）を、同じスクリプト・同じ規則で数えられるようにする
- 移行の前に 1 回測って基準を残せる状態にする（基準を取るのはこの課題の後の計測の作業）

## 前提

- 前提 1: 版を寄せる規則は、起票の本文の候補どおり **「PR が載ったリリース済み版」**（CHANGELOG に載った版 → マージの時刻の後の最初の正式版のタグ → 行の時刻の後の最初の正式版のタグ、の順）に 2 本でそろえる。**動いた NDF の版**（帳簿の `ndf_version`・会話の Skill の版）は捨てず、出力に別の値として残す。`token-usage.py --by version` がこれまで出していた「動いた版」の表を読む側が、比べ直せなくなるのを避けるためである（誤っても表の軸を 1 つ変えるだけで戻せる）
- 前提 2: 帳簿の無い期間の境目は、日時を埋め込まず、**帳簿の最も古い行の時刻**から決める。起票時の境目（2026-09-26 07:11 UTC）の帳簿は手元に無く（調べた事実）、境目は環境ごとに違うためである
- 前提 3: `full` の行（Skill を回すステップ）は、会話の記録（出所 A）と帳簿（出所 B）の両方に現れる。1 つの呼び出しを 2 度数えない。どちらで数えるかは設計が決める（`token-usage.py` は会話で数えて帳簿の `full` を読まない。今の規則をそのまま使ってよい）
- 前提 4: 流出不具合の記録の `of` は、今の意味（不具合を持ち込んだ PR）を変えない。`of` は `--escape-of` と `check-trigger.py escape --of` の契約で、conductor の手順と記録の読み手が使っている。**どの検査から逃げたか**は、別の値として記録するか、`stats` が記録から導く（起票の本文の候補「`of` に検査を入れる」は、この形で満たす）
- 前提 5: 検査の記録の書き手は `check-trigger.py`（`record`）の 1 つにする。フェーズレポートは読み手であって、記録を別に書かない
- 前提 6: 計測のスクリプト（`scripts/token-usage.py`・`scripts/measure/claude-p-usage.py`）はリポジトリの根の `scripts/`（開発用・配布しない）にある。`check-trigger.py` と計画の雛形は配布物（`plugins/ndf/scripts/`）で、ほかのプロジェクトでも動く形を保つ
- 前提 7: 2c（DBOS への移行）はこの課題より後に入る。この課題は今の計画の実行（`supervise.py` の雛形と状態の置き場）の上で直し、移行で雛形の置き場が変わっても、記録の形（帳簿の行・検査の記録の行）は変えない

- [ ] 7. `supervise.py new check --pr <N>` の計画を 1 本流して終えた後、`check-trigger.py stats` にその検査が 1 行出る。行は検査の名前・結果（マージ・変更なし・落ちた）・PR・件数を持つ
- [ ] 8. `--since-last` の検査も、今までどおり `eval` と `check` の行を書く（退行しない）。どちらの検査も、落ちたときに `result: failed` の行を書く
- [ ] 9. 検査の行の件数は、同じ計画のフェーズレポートの件数（ラウンド・指摘・修正・未解決）と一致する。書き手は `check-trigger.py record` の 1 つである（前提 5）
- [ ] 10. 流出不具合を記録したとき、その不具合を持ち込んだ PR（`of`）を最後に範囲に含めた検査が分かれば、`stats` がその検査に結び付けて出す。分からない（`of: 0`、または範囲に含めた検査が無い）ときは「結び付かない」とその理由を出す。`of` の意味は変えない（前提 4）
- [ ] 11. 指摘と修正の件数は、同じ単位で数えた値だけを「指摘」「修正」の名前で並べる。単位の違う値（レビューのコメントの数・修正担当が申告した件数）を並べるときは、別の名前で出し、同じ単位の値として比べない。r28/check-review のような「修正 > 指摘」が、同じ単位の値の間では起きない

**両方**

- [ ] 12. 上の 1〜11 は、手元の帳簿・検査の記録・計画の状態を模したデータを入力にしたテストで確かめられ、全体テストが通る
- [ ] 13. 記録の形（帳簿の行の列、検査の記録の `eval` / `check` / `escape` の既存の列）を読む既存の読み手（`token-usage.py`・`check-trigger.py eval` のトリガーの計算）は、振る舞いを変えない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 版を寄せる規則は 1 か所に置き、2 本のスクリプトから同じ関数を使う（Value 6） |
| 移行性 | 既存の帳簿・検査の記録の行はそのまま読める。行を書き換えない（追記だけ） |
| システム環境 | 配布物（`check-trigger.py`・雛形）は ai-plugins の形（タグの接頭辞・置き場のパス）を既定に埋め込まない（Value 5） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | `check-trigger.py` の副命令と引数・`--escape-of` の意味は変わらない。検査の記録の行に列が増えることがある（読み手は未知の列を無視する） |
| データ | 帳簿と検査の記録の形は追記だけ。既存の行の移行は無い |
| 既存の振る舞い | PR を指す検査が記録を書くようになり、`check-trigger.py eval` の範囲の起点（前回の検査）に影響し得る。影響させるかは設計が決める（未決） |
