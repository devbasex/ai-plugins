# #1340 の設計: 決定の記録

本体は [issue-1340-design.md](issue-1340-design.md) にある。

### 決定 1: ラウンドを足す入口は `state.py init` そのものにし、副命令も引数も足さない

`final` が確定したレビューの状態ファイルがあれば、`init` の再開の経路が `final` を外し、足した記録を積んでから
今の再開（引数の反映・worktree の同期・引継ぎの記録）へ進む。`drive.py` も `SKILL.md` の手順も最初に `init` を
打つため、利用者が覚える手順が増えない。今の `init` は確定した状態ファイルを新しい状態で上書きして履歴を捨てて
おり、この振る舞いを残す理由が無い。

副命令 `state.py reopen` と `init --reopen` は採らなかった。どちらも打ち忘れると今の「履歴を捨てて上書き」の
経路へ落ち、手で直す元の問題が形を変えて残る。

根拠: Value 2 / Value 6（MVV 版 2）

### 決定 2: `drive.py` が前回の結果を返すかは、完了の時点の head と今の PR の head で決める

差分を足したかどうかは、利用者に申告させずに PR の head で分かる。最終スイープは修正を push して head を進めるため、
比べる相手は最後のラウンドの `head_sha` ではなく、`finish` の時点に取り直した head にする。比べた結果は標準エラーへ
1 行出し、前回の結果を返したことも返さなかったことも見える形にする。

差分を足さずにもう一度回したいとき（`final=error` の原因が担当の認証だった、など）のために `drive.py --reopen` を
置く。head が取れない・古い記録で比べられないときは今の振る舞い（前回の結果を返す）に倒し、`--reopen` を案内する。
比べられないときに新しく回す案は採らなかった。GitHub の一時的な不調のたびに、完了したレビューがもう 1 ラウンド
回って費用が掛かる。

根拠: Value 2 / Value 3（MVV 版 2）

### 決定 3: 新しく始める理由の判定は `scripts/lib/loop_drive.py` に置き、#1263 と共有する

`rerun_reason(recorded_head, current_head, forced)` は「新しく始める理由（無ければ `None`）」を返す。#1263 は同じ
入口で「完了した状態の引数と今回の引数が違えば新しく始める」を足す。同じ役割の判定を cross-review と
cross-refactoring の駆動ごとに持たないよう、両方の駆動が既に読む `loop_drive.py` に置く。この課題では
cross-refactoring の `finished` は変えない（要求の前提 5）。

根拠: Value 6（MVV 版 2）

### 決定 4: ラウンドの上限・巻き直し・振動検知は、最後に足した時点より後のラウンドだけで数える

`reopens[-1].base_round` を境にする。上限で終わった状態から足したとき、全ラウンドで数えると `start-round` が
すぐに `max_rounds` で止まる（要求の前提 3）。振動検知も同じ境を使う。境の前のラウンドと比べると、
`oscillation` で終わった状態から足した最初のラウンドが同じ箇所を指してまた中断し、足す意味が無くなる。
判定の基準（重なり 50%・3 つの一致）は変えない。

根拠: Value 2（MVV 版 2）

### 決定 5: 足す前のラウンドには `start-round` の後始末の確認を当てない

`oscillation` と `max_rounds` で終わったラウンドは、修正の工程を通らずに最終スイープへ進む。最後のラウンドが
`changes_requested` のまま修正の記録を持たないため、確認を当てると足した直後に終了コード 5 で止まる。
最終スイープが返信と Resolve を済ませ、`verify-sweep` が GitHub の実数で確かめているため、確認が守る対象は
残っていない。

根拠: Value 2 / Value 6（MVV 版 2）

### 決定 6: 足すときに `ended_at` と `sweep` を足した記録へ移し、状態からは消す

`run_metrics.ended_at`・`report`・`loop_drive.review_status`・`drive.counts()` は `final`・`ended_at`・`sweep` を
「今の実行の終わり」として読む。消さずに残すと、足した後の実行が前の実行の最終スイープの結果で
`approved` に見える。移す先を足した記録にするのは、過去を上書きで失わないためである。

根拠: Value 7（MVV 版 2）

### 決定 7: 振動検知は `final` が確定していれば判定せずに終了コード 2 で抜ける

`check-oscillation` 自身が見るため、`drive.py` の経路と副命令を手で順に打つ経路の両方に効く（要求の前提 6）。
新しい終了コードを足さず、今の「続ける」（2）を返す。`drive.py` は `judge` が 2 のときだけ呼ぶため、2 を受けて
修正へ進む経路は生じない。

`judge` が収束したら `drive.py` の呼び出しだけを止める案は採らなかった。今の `drive.py` は既に `judge` が 0 なら
呼ばず、矛盾は手で打つ経路で起きていた。

根拠: Value 6（MVV 版 2）

### 決定 8: 修正の記録を作る入口は `state.py record-fix` にし、`merge-fix` と同じ取り込みを通す

ホストが自分で直したとき、手で書いていたのは戻り値ファイルの JSON である。`record-fix` は引数と GitHub の状態から
同じ形の戻り値ファイルを書き、`merge-fix` の取り込みの関数をそのまま呼ぶ。記録の形も、本文の揃えとまとめの投稿も
`/ndf:fix` を通したときと同じになる。

確かめるのは 2 つで、どちらかが欠ければ記録を作らずに終了コード 5 で止まる。コミットが PR の head から辿れること、
申告したスレッドが未解決の一覧に無いこと。一覧を取れないときも止める。`start-round` は取れないときに確認を飛ばして
進むが、`record-fix` は記録を作る側であり、確かめずに作ると確認の抜け道になる。

`/ndf:fix` に「直さずに記録だけ作る」形を足す案は採らなかった。`/ndf:fix` は Skill（LLM の手順）であり、決まった
確認と書き込みはスクリプトに置く。

根拠: Value 4 / Value 6（MVV 版 2）

### 決定 9: `merge-fix` は同じコミットを 2 回取り込まない

`drive.py` の修正の止まりでホストが `record-fix` を打つと、取り込みは済んでいる。続けて `drive.py` を打ち直すと、
修正の段階が戻り値ファイルを見つけて `merge-fix` を打つ。最後のラウンドの `fix.commit` と戻り値ファイルの
コミットが同じでも、それだけでは済んだと決めない。今の取り込みは投稿の前に修正の記録を保存するため、投稿に失敗した後の
打ち直しを 0 で返すと返信・Resolve が送られず、コード関連の CI 失敗で返した 3 も成功に変わる。そこで取り込みの段階
（`rounds[-1].fix.merge`）を書き進め、`done` なら `取り込み済み` を出して記録した終了コードを返し、`done` でなければ
済んでいない段階から続ける。

根拠: Value 6（MVV 版 2）

### 決定 10: hook の締め切りは 3.5 秒の定数 1 つにし、全ランタイムで使う

NDF が配る PreToolUse と userPromptSubmit の hook の上限は 5 秒か 10 秒である。最も短い 5 秒から余裕 1.5 秒を引いた
3.5 秒を、ランタイムを問わず使う。今の所要は 0.03 秒で、3.5 秒は通常の 100 倍を超える。ランタイムごとに締め切りを
引数で渡す案は採らなかった。hook の定義の `timeout` と引数の 2 か所に同じ値を書くことになり、片方だけを変える
誤りが起きる。上限と締め切りの対応は、hook の定義を読むテストが確かめる（I13）。

上限（`timeout`）を上げる案は採らなかった（要求の対象範囲の「含まない」）。

根拠: Value 5 / Value 7（MVV 版 2）

### 決定 11: 締め切りは `signal.setitimer` の割り込みで掛け、過ぎたら集めた結果だけを出して通す

時間を使いうる所は `git` の呼び出しだけでなく、ロックの待ち（`locks.exclusive`）と構文解析の読み込みにもある。
呼び出しごとに残り時間を渡すと、新しく足した呼び出しが締め切りの外に漏れる。割り込みなら hook の 1 回の全体に
掛かる。過ぎたときは、それまでに終わった判定の結果（拒否を含む）を今の `_merge` の規則で出し、残りを飛ばして
終了コード 0 で抜ける。拒否を返しうる token の guard の結果も、済んでいれば失わない。

判定を飛ばして通すのは要求の前提 9 による。止めると、`git` が遅いリポジトリでは Tool の呼び出しが全部止まる。

根拠: Value 2（MVV 版 2）
