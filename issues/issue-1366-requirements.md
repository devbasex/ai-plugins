## 目的

- プロジェクトの判断の基準を **1 つの宣言（プロジェクト MVV）** に置き、NDF が判断する地点（承認ゲートの判定・レビューの指摘の基準と修正の可否・リファクタリングの提案の採否・範囲外の起票・judge のステップ）がその宣言を読んで判断する
- MVV が無いプロジェクトでも、履歴（git・課題・文書）から候補を出し、利用者との対話で定められる。履歴が育っていないプロジェクトでは大まかな傾向から候補を出す
- MVV の上位に、**人類を守り、発展させる**という原則を置く。プロジェクト MVV はこの原則の範囲でだけ定められ、どのプロジェクトも上書きできない
- MVV は固定しない。改訂の契機・手順・記録を持ち、版を重ねる
- ai-plugins 自身のプロジェクト MVV を、これまでの判断の記録から抽出して定め、`.ndf/` に宣言する

## 前提

- 前提 1: 宣言は `.ndf/` に置き、人が読む本文は Markdown で、マイルストーン 26 の MVV（`issues/mvv-milestone26.md`。Mission / Vision / Value / レッドライン）と同じ節の構成を引き継ぐ。承認の記録（ハッシュ・日時・版・承認者）の置き方は設計で決める
- 前提 2: ミッションの MVV（`mission.json` の `mvv`）は残す。プロジェクト MVV を上位とし、ミッション MVV はその範囲での具体化である。ミッション MVV が無いミッションはプロジェクト MVV だけで判定する
- 前提 3: 候補の抽出は、材料集め（git の履歴・課題の題名と本文・`docs/` の決定の記録・`AGENTS.md`・README）を決定論のスクリプトが行い、候補の文章は最小構成の `claude -p` が書く（Value 1「決定論が先」・Value 6「汎用を保つ」に従う）
- 前提 4: 利用者との対話は conductor が `AskUserQuestion` で候補と分かれる点を示して行い、承認の前に宣言を書き込まない。承認は利用者が行う
- 前提 5: 「すべての行動が MVV に従う」は、判断を持つ地点へ MVV の本文を渡し、判断の記録に根拠の項目番号を残すことで観測する。行動のすべてを機械で保証することはできないため、渡した事実と記録の有無を受け入れ条件にする
- 前提 6: 改訂は利用者の承認で成立する。改訂で本文のハッシュが変わると、承認済みだったミッションの `pace: fast` は次の承認ゲートで利用者の承認へ戻る（既存の仕組み。`mission.py` の `mvv_refusal`）
- 前提 7: 他のプロジェクト（サンプル 4 つ）への適用は #1337 以降で行い、この課題では候補の抽出が `.ndf/` の無いリポジトリで通ることだけを確かめる
- 前提 8: 上位の原則「人類を守り、発展させる」は NDF が持つ固定の文で、宣言の側に写しは持たず、候補の生成・矛盾の検出・判断の地点への配線のすべてで先頭に付く。原則に反する候補・改訂・ミッション MVV は承認の前に止まる

## 対象範囲

含む:
- 上位の原則（人類を守り、発展させる）の置き場と、候補・改訂・ミッション MVV の検証への組み込み
- プロジェクト MVV の宣言の形（本文・承認の記録・版）と、その有無の判定（`development-workflow` の手順 0 と同列）
- 候補の抽出（材料集めのスクリプト + 候補の生成）と、履歴が少ないときの「傾向」モード
- 候補の提示と対話の手順（conductor が行う）、承認と書き込み
- 改訂の契機・手順・記録（版・理由・前の版との差分）
- 判断の地点への配線: `mvv-gate.py`、cross-review（担当のレビュー基準・修正・最終スイープの見送り判断）、cross-refactoring（提案と採否）、supervise の judge のステップ、`out-of-scope` の 3 択
- ミッション MVV とプロジェクト MVV の関係（矛盾の検出）
- ai-plugins のプロジェクト MVV の策定（候補の抽出 → 対話 → 承認 → `.ndf/` へ宣言）と文書

含まない:
- `mvv-gate.py` の判定の規則そのもの（従う / 従わない / 判定できない・レッドライン）の変更。渡す材料を足すだけ
- サンプル 4 つのリポジトリで MVV を定めること（#1337 以降）
- `pace: fast` の条件やトリガーの変更（#1078 の設計のまま）

## 用語

| 用語 | 意味 |
| --- | --- |
| 上位の原則 | 「人類を守り、発展させる」。NDF が持つ固定の文で、すべてのプロジェクト MVV の上に立ち、上書きできない |
| プロジェクト MVV | プロジェクト全体の Mission / Vision / Value とレッドライン。`.ndf/` に宣言し、利用者が承認する。判断の基準の上位 |
| ミッション MVV | ミッション単位の MVV（既存の `mvv.md`）。プロジェクト MVV の範囲での具体化 |
| MVV の版 | 承認のたびに 1 ずつ上がる番号。改訂の理由と前の版との差分を伴う |
| MVV の改訂 | プロジェクト MVV の本文を変え、利用者の承認で新しい版にすること |
| 判断の地点 | NDF が LLM の判断を挟む場所（承認ゲートの判定・レビューの指摘と修正の可否・リファクタリングの提案の採否・judge のステップ・範囲外の起票の 3 択） |
| MVV 候補 | 材料から書いたプロジェクト MVV の案。2 案以上と分かれる点を利用者へ示す |
| 傾向モード | 履歴が育っていないプロジェクトで、README・指示書・依頼文の傾向から候補を出す抽出の形 |

## 受け入れ条件

- [ ] AC1: `.ndf/` にプロジェクト MVV が無いリポジトリで有無の判定を打つと、終了コード 2 と「プロジェクト MVV が無い」の案内が出て、LLM も `gh` も呼ばず、ファイルを書かない
- [ ] AC2: 材料集めは `git`・`gh`（読み取りだけ）・ファイルの読み込みだけで材料のファイルを 1 つ書き、LLM を呼ばない。ai-plugins で 60 秒以内に終わる
- [ ] AC3: 履歴が閾値（コミット数・課題数。宣言で変えられる）に満たないリポジトリでは傾向モードになり、README・指示書・依頼文だけから材料のファイルができる。`.ndf/` も履歴もほぼ無いリポジトリで 1 度実測する
- [ ] AC4: 候補は 2 案以上で、各案に Mission / Vision / Value / レッドラインと根拠（ファイルと行・課題番号・コミットの件名のいずれか）が付き、「利用者に決めてもらう点」が箇条書きで出る
- [ ] AC5: conductor は候補と分かれる点を `AskUserQuestion` で示し、利用者が承認するまで `.ndf/` へ宣言を書かない（承認前の状態で宣言のファイルが存在しない）
- [ ] AC6: 承認すると宣言（本文・版 1・sha256・日時・承認者）が書かれ、有無の判定が 0 を返す。本文を手で変えると判定が「承認と一致しない」を返す
- [ ] AC7: `mvv-gate.py check` は、プロジェクト MVV とミッション MVV の両方を材料に渡す。ミッション MVV が無いミッションはプロジェクト MVV だけで判定する。プロジェクト MVV が未承認かハッシュ不一致なら承認ゲートへ戻す（終了コード 10）
- [ ] AC8: cross-review の担当のプロンプト・修正と最終スイープの見送り判断・cross-refactoring の提案と採否・supervise の judge のステップ・`out-of-scope` の 3 択に、プロジェクト MVV の本文（または本文のパス）が渡り、渡した事実がそれぞれの記録（状態ファイルかログ）に残る
- [ ] AC9: 判断の記録（見送りの返信・`mvv-gate.jsonl`・提案の見送り理由・judge の結果）に、根拠にした MVV の項目（例: `Value 3`）が入る。MVV が無いときは「MVV なし」と入る
- [ ] AC10: 改訂の手順で、理由・前の版との差分・新しい版・承認の記録が残り、前の版の本文を取り出せる。改訂の後、承認済みだったミッションの `pace: fast` は次の承認ゲートで利用者の承認へ戻る（既存テストで確かめる）
- [ ] AC11: 改訂の契機として、`retrospective` が「MVV を見直すか」の問いを持ち、`mvv-gate.py` が「判定できない」を宣言で決めた回数（初期値は設計で決める）だけ続けて返したときに改訂を提案する

- [ ] AC15: 既存の `pace: fast` の流れ（ミッション MVV の承認・ハッシュ・承認ゲート 1・2）が既存テストで退行しない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 材料集めは ai-plugins で 60 秒以内。候補の生成は最小構成の `claude -p` 1 回 |
| 運用・保守性 | 判定・承認・改訂は jsonl と git の履歴に残り、あとから「どの版で何を根拠に判断したか」をたどれる |
| セキュリティ | レッドライン（秘密・認証認可・利用者のデータ・戻せない操作・他リポジトリへの公開）は MVV があっても承認ゲートを省かない（既存） |

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 宣言のファイルと判定・抽出・改訂のサブコマンドを足す（後方互換）。`mission.json` の契約は変えず、プロジェクト MVV の参照を任意の項目として足す |
