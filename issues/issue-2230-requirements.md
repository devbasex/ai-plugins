## 目的

- 本番まで届けて受け入れ条件を満たしたスプリントで、リリースの経路（雛形・昇格・merge・手で届ける・検証の環境だけ・開発ループの周回）にかかわらず、まとめの close がリリース記録を読んで課題を閉じられるようにする（今は merge・手で届ける経路で毎回手で閉じ、開発ループでは検査のスプリント PR を記録として読む）
- 記録の PR が見つからないとき、まとめが「閉じずに ok」で先へ進まず、止まって理由を返すようにする（親 A の規則）

## 前提

- 前提 1: 直す層は、まとめのプランが記録の PR を決める箇所（`supervise_lib/sprint_routes.record_pr_ref`・`supervise_lib/sprint.close_plan`）と、ステージを流す時点の差し込みの解決（`supervise_lib/queue_fill.py`）、開発ループのまとめの組み立て（`lib/sprint_loop.gate2_pipeline`・`lib/sprint_loop_gate.build_close`）である。`sprint-close.py` の閉じる条件（`--with-verification`・最終工程の記録）は変えない
- 前提 2: merge・手で届ける経路でも、`release` の手順はリリース記録（`## 配布の記録`）を Pull Request に残す（`plugins/ndf/skills/release/SKILL.md` の「出力物」: リリースの PR の本文、PR を作らない形ではスプリントの最後にマージした PR へコメント）。この課題はその記録を読む側を直し、記録を書く手順の形は変えない（記録の PR の番号を置く場所を足すかは未決 1）
- 前提 3: 「実行の時点」は、まとめのステージ（close の queue）がそのプランを流し始める時点を指す。まとめのプランを組む時点（`supervise.py new close`・`new sprint` の組み立て、開発ループの承認ゲート 2 の時点）に記録の PR が無くてもよい
- 前提 4: 届けない経路だけのスプリント（記録の PR が `0`。`sprint_routes.RECORD_NONE`）は、記録を読まずに閉じる今の扱いを変えない
- 前提 5: 呼ぶ側が `--record-pr <番号>` を明示して `new close` を打ったときは、その番号を使う今の扱いを変えない

## 対象範囲

含む:

- merge（`merged-by-check`）・手で届ける・検証の環境だけ（`production: false` の行だけ）・手動反映の本番系の昇格の経路で、まとめの close が `unknown` でなく、実行の時点に解決したリリース記録の PR を受け取る（#2044）
- 開発ループ（`sprint-state.py loop`）の承認ゲート 2 の後のまとめが、検査のスプリント PR でなく、本番のリリース記録の PR を受け取る（#2121 の問題 1）
- 記録の PR を解決できないとき、まとめのステップが止まり、課題を開いたまま ok で返さない
- 上の経路で記録の PR が解決できたときに、まとめのリリース後テストのステップがその PR を受け取る

含まない:

- #2121 の問題 2（manual ステージを含む経路で、手作業を終えるまでまとめを始めない並びの直し）。子の #2121 で扱う。この課題では、記録が無い時点で走ったまとめが止まることだけを保証する
- リリース記録の形（`lib/dist_record.py`・`progress-tracking` の「配布の記録」の表）と、記録を書く `release-steps.py record` の出力の変更
- `sprint-close.py` の閉じる条件（配布の段階・リリース後テスト・最終工程の記録）の変更
- 雛形・昇格の経路で、本番のプランが飛ばされた（最終の検査で変更が無い）ときの扱い
- 課題を閉じる時点と順序（親 B の #2228）、結果の共通形式そのもの（親 A の #2227）

| 用語 | 意味 |

| リリース記録 | release が Pull Request へ残す `## 配布の記録` のブロック。段階・版・スプリントの Pull Request を持つ（用語集の語） |

## 受け入れ条件

- [ ] 1. merge（`merged-by-check`）・手で届ける・検証の環境だけの経路のスプリントで、`supervise.py new sprint` / `new close` が組むまとめの close のステップは `--record-pr unknown` を持たず、ステップを流す時点でリリース記録（`## 配布の記録`）を置いた PR の番号を `--record-pr` に受け取る（#2044 の受け入れ条件 1）
- [ ] 2. 開発ループの承認ゲート 2 の後のまとめの close は、止まった記録の `values.pr`（検査のスプリント PR）でなく、本番のリリース記録を置いた PR の番号を `--record-pr` に受け取り、配布して閉じる条件を満たした課題を閉じる（#2121 の受け入れ条件 1）
- [ ] 3. 受け入れ条件 1・2 の経路で記録の PR を解決したとき、まとめのリリース後テストのステップは同じ PR の番号を受け取る
- [ ] 4. まとめのステップを流す時点で記録の PR が見つからないとき、まとめは止まる（close を走らせないか、close が 0 でない終了コードで終わる）。課題は開いたまま残り、まとめの報告の結果は「完了」にならない。止まった理由に、探した経路と見つからなかったことが載る（#2044 の受け入れ条件 2）
- [ ] 5. どの経路のまとめのプランも、`--record-pr unknown` を組まない
- [ ] 6. 雛形（`{queue_pr:release-prod}`）と昇格（`{queue_pr:promote}`）の経路のまとめのプランの内容と、それを流したときの close の引数・出力は変わらない（#2044 の受け入れ条件 3）
- [ ] 7. 届けない経路だけのスプリントのまとめ（`--record-pr 0`）と、`--record-pr <番号>` を明示した `new close` の振る舞いは変わらない
- [ ] 8. 開発ループを使わない起動の出力と終了コードは、受け入れ条件 1・4・5 で変わる部分のほかは変わらない（#2121 の受け入れ条件 3）

## MVV との突き合わせ

反する疑いは無い。Value 6（根本原因の場所で直す: 子の 2 件を記録の PR を決める層で直す）、Value 5（どのプロジェクトでも使える形: 経路はリリースの宣言から決まり、ai-plugins の形を埋め込まない）、Value 2（利用者の手を止めない: 本番まで届けたスプリントの課題を手で閉じなくてよくなる）に沿う。記録が見つからないときに止まるのは、共通原則の優先順位（承認資料と記録の正しさを効率より上に置く）と親 A に沿う。

## 未決

1. **記録の PR を実行の時点で解決する手段。** 候補は (a) queue の `{queue_pr:<名>}` の探し場所を広げる（開発ループのまとめは本番のプランと別の queue・別のディレクトリにある）、(b) 手で行うリリースのステージ・merge の経路の導入の確認に、リリース記録を置いた PR の番号を記録するステップを足し、まとめがそれを読む（#2044 の直し方の案）、(c) まとめの close の前に、スプリントの PR を指すリリース記録を GitHub から探すステップを置く。設計（`design`）で決める
2. **`sprint-close.py --record-pr unknown` の受け付けを残すか。** まとめのプランは組まなくなる（受け入れ条件 5）。手で打つ入口として残すか、親 A に合わせて止まる（ok で返さない）値にするか、受け付けをやめるかを設計で決める
