## 同じ形（検査のプラン、2026-10-12 スプリント m1910）

スプリントの検査のプラン（`6-check`、上限 12）が、`merge`（exit=0）まで 12 本通った後、`record` の手前で「ステップの数が上限 12 を超えた」で止まった。経路: collect → pr → assess → refactor → review → test-all(exit=1) → judge[fix] → fix → test-all → ready → merge-gate → merge。全体テストの修正 1 回で +3 本になり、修正の無い経路（record まで 11 本）を超える。

## 再発（2026-10-14、スプリント m1982・PR 1993）

#1702 の実装のプラン（`5-impl-1702`）が、範囲テストの修正 3 回（中身の違う失敗なので「同じ失敗なら stop」に当たらない）と doc-lint の修正 1 回で経路が 23 本になり、21 本目の `ready` で上限 20 に達して止まった。conductor が `--from ready` で再開した。上限は `supervise_lib/templates.py:179` の固定値、判定は `flow.py:244-249`。振り返り: release PR https://github.com/devbasex/ai-plugins/pull/1999

## 目的

- `supervise.py` が組むプランが、修正のループを数回通る普通の経路でも「ステップの数が上限 N を超えた」で止まらず、承認ゲートか end まで届く。conductor の手当て（`--from merge-gate` / `--from ready` / `--from gate` / `record` を手で流す）を無くす（#1909 #1676）
- 止まったプランを `--from` で再開したとき、judge が前の実行の結果を材料に判定でき、「入力なし」で stop しない（#1676）
- 遅れの見張りが、出力の行とコミットのほかの形で進んでいる worker と cross-review を、作業の途中で打ち切らない。打ち切りの再試行で上限に当たらない（#1623 #1496）

## 前提

- 前提 1: 1 本の実行で、修正のループ（範囲テスト・全体テスト・文書の検査・同期の検査・push 前の検査・用語チェックのそれぞれの修正）は**それぞれ 3 回まで**通るものとして上限を決める。根拠は実測の最大（#1909 の再発: 範囲テストの修正 3 回）。4 回目以降は judge の「2 回直しても同じ失敗なら stop」か上限が止める
- 前提 2: 4 課題を 1 つの設計で直す。上限の決め方は雛形ごとに書かず、プランの遷移から求める共通の部品 1 か所に置く（Value 6）
- 前提 3: 手で書いたプランの `上限` は、書かれた値をそのまま使う（上書きしない）。`上限` が無いプランの既定 30 も変えない
- 前提 4: 前の実行は、Pull Request を戻す範囲（`RunState.recorded_pr`）と同じく、`--from` を付けない最後の実行の始まりより後の記録を指す
- 前提 5: 遅れの見張りの既定の値（`floor` 300 秒・`default` 900 秒・`factor` 3・`max_retry` 1）は変えない。進みの見方を足して直す
- 前提 6: 上限の計算に使う「遷移」は、ステップの `next`・`on_fail`・`skip_to`・`on_exit` の行き先・judge の `choices` と、プランの読み替えが足す行き先（`on_section_missing` など）である。どの鍵を数えるかの一覧は設計が決める

## 対象範囲

含む:
- `supervise.py new`（impl・fix・check・`check --since-last`・release）と `supervise.py new sprint` が書くすべてのプランの `上限` を、プランの遷移から決める（#1909 #1676）
- `supervise.py run` が、流す前にプランの `上限` とループを通らない最長の経路を照らす（#1909 #1676。手で書いたプランにも効く）
- `run --from` の再開で、ステップの `inputs` が前の実行の結果を読む（#1676）
- 遅れの見張りの一次の調査（probe）が、要求・設計の work の worker のセッションの伸びと、cross-review の drive の PR への投稿・コミットの伸びを「進んでいる」に数える（#1623 #1496）
- 遅れの打ち切りの再試行が、プランをステップの上限で止めない（#1623）

含まない:
- 止まったプランの続きと後続のステージ（`--then`）の流し方（#1918）
- ベースブランチの取り込みのステップを足すこと（#1917 #2003。この主題の上限の決め方を前提にステップを足す）
- 実装の指示の作り直しと整形のステップ（#1651 #1507）と、設計の結果の読み取りの失敗の扱い（#1941）
- 遅れの見張りの既定の値の変更と、`max_retry` などの見張り自身の回数の上限の変更
- 利用上限・GitHub の上限の待ち（ステップの数の上限とは別のもの）

## 用語

| 用語 | 意味 |

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 上限の計算と L3 の照合は、ステップ 50 本のプランで 1 秒以内に終わる（`new` と `run` の所要を目に見えて延ばさない） |
| 運用・保守性 | 上限で止まったときと L3 で流さなかったときは、フェーズレポートの理由に `上限` の値と経路の長さが載る。遅れの見張りが待ち直した根拠（どの伸びを見たか）は進捗ログの `slow` の行の一次の調査に載る |
| 移行性 | 書き済みのプランのファイルは書き直さない。手で上げた `上限` もそのまま効く（前提 3）。L3 で止まった書き済みのプランは、`上限` を上げるか `new` で書き直せば流れる（報告の理由に書く） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない。プランの JSON の鍵（`上限`・`slow`・`inputs`）と `supervise.py new` / `run` の引数は同じ。雛形が書く `上限` の数が増える |
| データ | 変わらない。状態ディレクトリ（`state.json`・`NN-<ステップ>.out`・`progress.jsonl`）の形は同じで、`--from` が読む側だけが増える |
| 既存の振る舞い | 雛形のプランの `上限` が増える。`上限` がループを通らない最長の経路より短いプランは、流し始める前に止まる（今は途中で止まる）。`--from` の再開で judge と work の入力に前の実行の結果が載る。遅れの見張りが要求・設計の work と cross-review の drive を打ち切る回数が減る |

| 項目 | 手段 |
