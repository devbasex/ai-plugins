# #2216 の設計: 決定の記録

頭の文書は [issue-2216-design.md](issue-2216-design.md) にある。根拠の行の MVV は ai-plugins のプロジェクト MVV（版 3）である。

## 決定の記録

### 決定 1: 照合のために受け口がほかの集約を読まないよう、取り込むリポジトリを実行ジョブの token の claim で運ぶ

実行の制御（#2186）は実行ジョブを起動するとき、実行ジョブの指示の `REPO` と token を同じスプリントの実行から作るため、token にリポジトリを入れる費用は 1 つの値だけである。署名された値はランナーが書き換えられず、受け口は今と同じく token だけで照合を閉じられる。確定仕様は期限より前の取り消しを「#2186 の集約を読むことになるため」持たないと決めており、照合のためにスプリントの実行を読む形はその判断と食い違う。#2186 の設計（PR #2236）の決定 1 も同じ形を採り、照合を I37 として置いた。

受け口がスプリントの実行からリポジトリを引いて照らす形は採らない。#2186 の表の形が決まるまで読み出しの口を作れず、事象 1 件ごとに読み出しと 503 の経路が増える。

根拠: Value 6 / Value 4 / C2（MVV 版 3）

### 決定 2: 照らせない token を残さないため、`repo` を必須の claim にし、無い token は 401 にする

`sprint_run_id` と同じく必須の claim にすれば、無い・形が違う token は検証の段で `malformed` になり、受け口と #2173 で同じ扱いになる。要求の受け入れ条件 4 が求める「202 にならず保存しない」を、照合の分岐を増やさずに満たす。

`repo` を任意にし、`pull_request` つきの `step.recorded` のときだけ 403 にする形は採らない。照らせない token が有効なまま残り、照合の側に「claim が無い」分岐が増える。旧い token との互換は前提 3 のとおり持たない。

根拠: Value 6 / C2（MVV 版 3）

### 決定 3: 照合と `pr_ref` と起票の代行が同じ規則で名前をそろえるよう、小文字にする関数を `github.ts` に 1 つだけ置く

GitHub はリポジトリの名前の大文字と小文字を区別せず、`pr_ref` は既に `owner/name` を小文字にそろえる。照合・起票先の照合（I45）・登録の引き当て・台帳の要約値が別々にそろえると、照合を通った値が引き当てで外れる食い違いが起こりうる。`repoKey` をすべてが使う。token の `repo` の形は契約の `RepoFullName` の `pattern` を読んで確かめ、正規表現を写さない。

根拠: Value 6（MVV 版 3）

### 決定 4: 照合の単位をリポジトリの名前（`owner/name`）にし、GitHub のリポジトリの識別子にしない

事象の `pull_request` が運ぶのは `repo`（`owner/name`）と番号だけで、識別子で照らすには進捗の事象の契約とランナーの申告を変えることになる。名前で照らすと、実行ジョブの途中で改名したときその後の申告は 403 になるが、改名の後は `pr_ref` も既に合わなくなる（確定仕様の運用の節）ため、照合が新しく失わせる情報は無い。起票の依頼の引き当ても同じく名前で行い、改名の後の依頼は `not_registered` の下書きになる（人が起票できる）。

要求の未決 2 は #2186 の設計に置いたままにする。#2186 が識別子で照らすと決めたときは、token の `repo` と事象の契約を同じ変更で替える。

根拠: Value 1 / Value 10（MVV 版 3）

### 決定 5: #2171 の設計の決定 7 を、`pr_ref` を「token のリポジトリと照らした申告」から置く形へ書き換える

#2171 の決定 7 は、宛先のスプリントの実行を知るのが Pull Request を作ったランナーだけであることから、`pr_ref` をランナーの申告で置くと決めた。この理由は変わらず、申告で置く形も残す。変えるのは、申告の `repo` が token のリポジトリと一致するときだけ置くことである。確定仕様の背景の段落にこの条件と理由（申告だけで置くと、正しい token を持つランナーが関係の無いリポジトリの Pull Request を自分の実行へ結び付けられる）を書き足す。

根拠: Value 7 / C2（MVV 版 3）

### 決定 6: ランナーの権限を広げずに別のリポジトリの修正を届けるため、起票の依頼を `runner` の新しい種類 `issue.requested` にし、受け口は記録だけをする

利用者の答えのとおり、ランナーは依頼を送るだけで、起票はサービスが行う。依頼を進捗の事象にすれば、既存の token の検証・冪等の鍵・送り直しがそのまま使え、依頼と結果が実行の列に並ぶため #2172 が新しい読み出しを持たずに見せられる。`payload` は起票先・題・本文の 3 つだけにする。ラベルと相手の課題の番号は相手先の流儀に属し（#2239）、本文の「由来」の節が元の課題を指す。題の上限 256 字は GitHub の題の上限で、本文の上限 50,000 字は、4 バイトの文字だけでも事象の 256 KiB に収まる長さである。

受け口は登録を読まず、起票先が token の `repo` と同じ依頼だけを 403 にする（I45）。実行のリポジトリへはランナーが自分の導入の token で起票でき、同じことに 2 つの経路を作らないためである。起票してよいかの判定を受け口で行う形は採らない。受け口が #2186 の集約と GitHub を読み、決定 1 の境目が崩れる。依頼を `attention` の `payload` に載せる形も採らない。`attention` は人の手を止める知らせで、サービスが起票した依頼まで人へ知らせることになる。

根拠: Value 6 / Value 4 / C2（MVV 版 3）

### 決定 7: NDF の起票の手順を変えずにランナーから依頼を出すため、`issue-file.py create` に環境変数 `NDF_ISSUE_REQUEST_FILE` の分岐を 1 つ足す

NDF は別のリポジトリへの起票を `issue-file.py create` に集めており、起票先が開発対象リポジトリと別なら承認資料を書いて 10 で止まる。ランナーの中ではこの承認を人に問えず、`gh` の token も 1 リポジトリに絞られている。そこでランナーが変数を渡したときだけ、承認資料の代わりに依頼の 1 行（`{"repo", "title", "body"}`）をファイルへ足して 0 を返す。人の承認の代わりはサービスの判定（決定 11）が持つ。手順書（`out-of-scope`）は変わらず、ランナーの外では変数が無いため今どおり止まる。

ランナーが NDF の承認資料（Markdown）を読み取って依頼にする形は採らない。承認資料は人が読む形で、題と本文の切り出しが壊れやすく、NDF は 10 で止まって人へ戻すため実行ジョブが承認待ちになる。conductor に API を直接呼ばせる形も採らない。実行ジョブの token を NDF の手順へ渡すことになる。

根拠: Value 6 / P1（MVV 版 3）

### 決定 8: 流儀の判定を 2 か所に書かないため、起票の代行は #2239 の判定を型の口 `FilingStyleResolver` で呼ぶだけにし、既定を GitHub Issues とテンプレート無しにする

相手先の課題追跡の宣言・Issue テンプレート・外部チケットを読む判定は #2239 が持ち、NDF とサービスが同じ判定を使う形も #2239 が決める。ここは判定を呼ぶ口と、判定が GitHub Issues 以外を返したときに下書きへ回す（`unsupported_tracker`）扱いだけを持つ。#2239 が入るまでの既定は「GitHub Issues へ、テンプレートを使わず、依頼の題と本文のまま」で、`saved-answers.ts` と同じく同じファイルの中身を替えれば済む形にする。相手先のファイルを読む token（Contents の読み取り）の要否も #2239 が決める。起票に使う token は Issues の書き込みだけのまま広げない。

起票の代行の中に `.ndf/project.json` と `.github/ISSUE_TEMPLATE/` を読む規則を書く形は採らない。NDF の側と判定が 2 つになり、片方だけ直したときに食い違う。

根拠: Value 4 / Value 6（MVV 版 3）

### 決定 9: 人の手を止める承認を増やさないため、下書きは #2173 の承認の依頼にせず、結果の事象 `drafted` を知らせとして回す

承認を求める種類はゲート 1・ゲート 2 の 2 つだけで、判断は知らせである（全体の契約の I11）。下書きの起票はスプリントの進行を止める答えを要らず、人が相手先の流儀に沿って起票すれば済む。#2173 は `outcome` が `drafted` の `issue.request_resolved` を知らせの受け手に足し、#2172 は依頼の題と本文を、写せる形の下書きとして見せる。知らせの送り方（Web・Slack）は #2173 が決める。

承認の依頼の 3 つ目の種類にする形は採らない。I11 を破り、答えを待つ間に実行ジョブが止まる。

根拠: Mission / C2（MVV 版 3）

### 決定 10: 同じ依頼から Issue を 2 件作らないため、結果を `control` の直の追記で 1 件だけ残し、起票の前に台帳の行を条件つきで書き、作成の要求の後はやり直さない

結果は依頼 1 件に 1 件で、鍵を `<依頼の鍵>:resolved` にすれば鍵の表が重複を拒む。書き手は受け口の認証を通らないサービスの中の処理のため、`appendControlEvent` と同じ `control` の出所で、受ける種類を `issue.request_resolved` に限った `appendIssueRequestResolved` を足す。同じ中身の別の依頼（送り直し・再開のジョブ）は、台帳の行（`RUN#<sprint_run_id>` / `ISSUE#<digest>`）を条件つきで書くことで 1 件目だけが起票へ進み、2 件目以降は 1 件目の結果を `duplicate_of` つきで写す。Issue の作成の要求を出す直前に `attempted_at` を書き、それがある行は作り直さずに `filing_failed` の下書きにする。GitHub が作ったのに応答が届かなかったとき、2 件目を作らないためである。

出所に `service` を足す形は採らない。種類の表と全体の契約の I25 の受け手がすべて新しい値を扱うことになり、「サービスの中から直に書く」という意味は `control` で足りる。作成の失敗をやり直す形も採らない。GitHub の Issue の作成は冪等の鍵を持たない。

根拠: Value 6 / Value 2（MVV 版 3）

### 決定 11: ほかの利用者のリポジトリへ書かず、情報の公開範囲を広げないため、サービスが起票する先を「依頼の実行のアカウントの登録」と「公開範囲が広がらない向き」に限り、token を 1 リポジトリと Issues の書き込みに絞る

利用者の答えのとおり、起票してよいのは同じアカウントが登録し App を入れたリポジトリだけである。アカウントは依頼の `sprint_run_id` からサービスの表で引き、依頼の値はリポジトリの名前を引く鍵にしか使わない。導入の token は `repository_ids` に起票先の数の ID 1 つ、`permissions` に `issues: write` だけを入れて作り、GitHub の口の中で 1 回使って捨てる（I47）。App の導入が起票先を含まなければ作成が断られ、`not_installed` の下書きになる。理由はアカウントの中の登録だけから決め、未登録とほかのアカウントの登録を同じ `not_registered` にする（I50）。

加えて、起票先が公開で実行のリポジトリが非公開なら起票しない（`visibility`）。AI が書いた本文は非公開のコードや設定を含みうる。同じアカウントのリポジトリでも公開のリポジトリへ出すと誰でも読める。この向きだけは人が本文を見てから起票する。ほかのアカウントの登録でも、そのアカウントの同意があれば起票する形は採らない。同意の記録と取り消しの経路が要り、利用者の答えの範囲を超える。

根拠: C2 / Value 2（MVV 版 3）

### 決定 12: 暴走した実行が自分のリポジトリへ大量に起票しないよう、スプリントの実行ごとの起票の数を 10 までにし、秘密らしい値を含む依頼は起票しない

ほかの利用者のリポジトリへの起票は決定 11 で塞がり、残る害は 1 つの実行が自分の登録したリポジトリへ同じ種類の Issue を並べることである。数の行を条件つきで増やし（I49）、超えた依頼は `limit_exceeded` の下書きにする。上限の 10 は実測に基づかない初期値で、環境変数 `ISSUE_REQUEST_LIMIT_PER_RUN` で変え、本番の結果の事象で見直す。下書きは数に入れない。下書きはアカウントの中の人へ回るだけで、外へ出ない。

秘密らしい値は、AWS のアクセスキー（`AKIA` / `ASIA` と 16 字）・PEM の秘密鍵の始まりの行・GitHub の token（`ghp_`・`gho_`・`ghu_`・`ghs_`・`ghr_`・`github_pat_`）・Anthropic の API キー（`sk-ant-`）・JWT の形（実行ジョブの token）を、題と本文の両方で探す。当たれば `secret_suspected` の下書きにする。依頼の事象はアカウントの中でだけ読まれ、外へ出す前の最後の検査は起票の代行が行う。依頼の本文はログに出さない。日や起票先ごとの数も数える形は採らない。行と条件が増え、1 つの実行の暴走を止めるには実行ごとの数で足りる。

根拠: Value 10 / C2（MVV 版 3）
