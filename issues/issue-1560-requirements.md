> ## 決めたこと（2026-09-30 利用者）
>
> - **置き場は `.ndf/handoff/<名>.md`**。メインディレクトリに置き、VS Code でいつでも読める
>   - `issues/` は NDF を使うプロジェクトに必ずあるとは限らない。`.ndf/` は `development-workflow` の手順 0 が作るため必ずある（`worktree/SKILL.md` のメインディレクトリで編集してよいパスにも載る）
>   - VS Code はドットで始まるフォルダを先頭に並べるので目に入る。ワークスペース直下は並行すると根に何本も並ぶため採らない

> - **CRUD の規則を定める**（下の案を設計で確定する）
>
> ## CRUD の規則（案）
>
> | 操作 | いつ | だれが | 規則 |
> | --- | --- | --- | --- |
> | 作る | 対象（スプリント・マイルストーン・課題）で最初のカットポイント、または `/ndf:restart` を打ったときに、その対象の文書が無ければ | conductor だけ（supervisor・worker は書かない） | `<名>` は並行しても衝突しない対象の名前（`sprint-m1142c`・`milestone-26`・`issue-1523`）。節の形は下の「節の形」 |
> | 読む | 新しいセッションの `development-workflow` が状態を戻すとき（`context-window.md` の「新しい会話で戻す」の表） | 新しいセッションの conductor | 再開コマンドが文書を名指ししていればそれを読む。名指しが無ければ `.ndf/handoff/*.md` を並べ、`/goal` の目標や課題番号と一致する 1 本だけを読む。**複数が当たれば推測せずに利用者へ聞く** |
> | 更新する | カットポイントごと・`ndf-next` のブロックを出す直前・利用者の決定を受けた直後 | conductor だけ | 「現在地」と「次にやること」を**書き直す**（追記を積まない）。終わった項目は `<名>-history.md` へ移し、本体は行数の上限（例: 300 行）に収める |
> | 消す | 対象が閉じたとき（スプリントなら本番の配布とリリース後テスト・振り返りの後、マイルストーンなら閉じた後） | conductor | 消す前に、以後も要る事実（決定・未検証の項目・起票）が課題の本文か Pull Request にあることを確かめる。追跡外なので git で戻せない。消したパスを報告する |
>
> **書かないもの**
> - 承認・同意を、次のセッションへの許可として書かない（「承認済みなのでマージしてよい」など）。承認は事実として課題・PR の URL と日時で書き、承認ゲートは次のセッションが課題と PR から読み直す（`restart` の「再開コマンドに承認・同意・判断の結果を書かない」と同じ理由。文書は次のセッションが指示として読む）
> - 認証情報・トークン
> - 課題の本文・PR・`progress.jsonl` が既に持つ状態の写し（置き場所へのリンクだけを書く）
>
> ## 節の形（案。今の文書から起こす）
>
> 1. 進め方（利用者の指示）: 対象の間ずっと効く指示（pace・版の付け方・並列の上限など）
> 2. 課題の順: 着手の順と状態
> 3. 現在地: 本番の版・動いているプラン（状態ディレクトリのパス）・利用者の側で残っていること
> 4. 次にやること: 番号付きで、最初の 1 つが次のセッションの最初の作業
> 5. 運用の知見（任意）: その対象で繰り返し効いた手順と落とし穴。対象をまたいで効くものは Skill か課題へ移す
> 6. 次に実行するコマンド: `ndf-next` のブロック（形は `context-window.md` が持つ）
>
> ## 範囲
>
> - `restart/SKILL.md`: 再開コマンドを決める前に文書を作る・更新する手順。再開コマンドに文書のパスを含める
> - `development-workflow/references/context-window.md`: 「新しい会話で戻す」の表に文書を読む行を置き、置き場・形・CRUD の規則の正本をどちらか 1 か所に置く
> - 雛形（節の形）の置き場
> - 移行: `issues/handoff-milestone26.md`・`issues/handoff-milestone26-history.md` を `.ndf/handoff/milestone-26.md`・`milestone-26-history.md` へ移す
>
> ## 受け入れ条件（案）
>
> - `/ndf:restart` を打つと、対象の文書が `.ndf/handoff/<名>.md` にでき（無ければ）、「次に実行するコマンド」の節が出したブロックと同じ中身になる
> - 新しいセッションで `/ndf:development-workflow <文書のパス> の続きから` を打つと、文書の「次にやること」の最初の項目から始まる
> - 名指しの無い再開で `.ndf/handoff/` に対象の一致する文書が 2 本あると、読まずに利用者へ聞く
> - 対象が閉じると文書が消え、消したパスが報告に出る
> - 文書はコミットされず、`.gitignore` にも載らない

## 目的

- 会話を切って新しいセッションで続けるための引継ぎ文書を、置き場・名前・節の形・作る／読む／更新する／消す時期と担い手が決まった NDF の仕組みにする
- 達成したい状態: どのプロジェクトでも、`/ndf:restart` かカットポイントで conductor が同じ場所・同じ形の文書を残し、次のセッションの `development-workflow` がその文書から迷わずに続きを始められる。対象が閉じたら文書は残らない

## 前提

- 前提 1: モードは `standard` として扱う（本文の `## 進行` のモードは未記入。変更は Skill 本文の手順と、スクリプトの既定のパスに及ぶため）
- 前提 2: 引継ぎ文書は conductor の作業の文書であり、共通原則の「利用者の設定（`.ndf/`）」（C7）にも「利用者のデータ」（C3）にも当たらない。`.ndf/handoff/` へ書く・消すのに利用者の承認は要らない（置き場は 2026-09-30 に利用者が決めた）
- 前提 3: 引継ぎ文書を消す操作は `-D` / `--force` を要しない追跡外のファイルの削除で、C4 に当たらない。代わりに、消す前に以後も要る事実が課題の本文か Pull Request にあることを確かめる（下の受け入れ条件 11）
- 前提 4: 置き場の `.ndf/handoff/` は**メインディレクトリ**（clone したディレクトリ）のものを指す。conductor が worktree の中で動いていても、worktree の `.ndf/` には書かない（worktree は後片付けで消え、VS Code で開いているのはメインディレクトリであるため）
- 前提 5: `.ndf/` が無いリポジトリでは、`development-workflow` の手順 0 が `.ndf/` を作るまで引継ぎ文書を作らない（`.ndf/` は手順 0 で必ずできる）
- 前提 6: 引継ぎ文書の「今の会話の進み」の節は、今までどおり `sprint-state.py render` が書く。本文の案の「節の形」の 6 節に、この節を加える（今の `relay.md` の「カットポイントの引継ぎ文書と ndf-next はスクリプトで作る」と、`context-window.md` の「新しい会話で戻す」の表の 4 行目がこの節を読むため）
- 前提 7: 本体の行数の上限は 300 行とする（今の `issues/handoff-milestone26.md` は 137 行、`-history.md` は 172 行。上限は設計で変えてよい）
- 前提 8: `/ndf:restart` は Claude Code だけの Skill である。Codex / Kiro / agy では、カットポイントで conductor が文書を作る・更新する規則だけが効く

## 対象範囲

含む:
- 引継ぎ文書の置き場（メインディレクトリの `.ndf/handoff/<名>.md` と `<名>-history.md`）・名前の付け方・節の形・作る／読む／更新する／消す規則を、`development-workflow` の参照文書 1 か所に正本として置き、ほかは指す
- `/ndf:restart`: 再開コマンドを決める前に文書を作る・更新する手順と、再開コマンドに文書のパスを含める規則
- `development-workflow` の `context-window.md`「新しい会話で戻す」の表に、引継ぎ文書を読む行を置く
- 節の形の雛形の置き場
- 引継ぎ文書を既定で `issues/handoff-<名>.md` と書いている箇所の置き換え（`relay.md` の例・用語集 `glossary.md` の「引継ぎ文書」の行）
- 移行: `issues/handoff-milestone26.md`・`issues/handoff-milestone26-history.md`（どちらもメインディレクトリの追跡外のファイル）を `.ndf/handoff/milestone-26.md`・`milestone-26-history.md` へ移す

含まない:
- 引継ぎ文書をコミットする仕組み、`.gitignore` への登録（利用者が採らないと決めた）
- `sprint-state.py` / `supervise.py note` の節を書き換える振る舞いの変更（引数で受けるパスが変わるだけで、書き方は変えない）
- ラッパー（`relay.py`）が `ndf-next` の囲みを拾う規則の変更
- `issues/old/` にある過去の引継ぎ文書の移動・削除
- 引継ぎ文書を人へ見せる UI（VS Code の拡張など）

- [ ] 1. `/ndf:restart` を、`/goal` の目標か課題番号がある会話で打つと、その対象の文書がメインディレクトリの `.ndf/handoff/<名>.md` に無ければ作られる。`<名>` は `sprint-<スプリント名>`・`milestone-<番号>`・`issue-<番号>` のどれかである
- [ ] 2. conductor が worktree（`.worktrees/<ブランチ名>`）の中で 1 を行っても、文書はメインディレクトリの `.ndf/handoff/` にでき、worktree の `.ndf/handoff/` にはできない
- [ ] 3. 作った後のメインディレクトリで `git status --short` を打つと `?? .ndf/handoff/` が出て、`git check-ignore .ndf/handoff/<名>.md` は終了コード 1 を返す（コミットされず、無視もされない）
- [ ] 4. `.ndf/handoff/` に追跡外の文書がある状態で、`check-markdown-links.py` と `check-doc-line-limit.py` がその文書を理由に落ちない

作る・更新する
- [ ] 5. 作られた文書の見出しは、正本が定める節（進め方・課題の順・現在地・次にやること・今の会話の進み・運用の知見・次に実行するコマンド。運用の知見と今の会話の進みは無くてよい）を正本の順に持つ
- [ ] 6. `/ndf:restart` が出した `ndf-next`（ラッパーの外では `text`）の囲みの中身と、文書の「次に実行するコマンド」の節の囲みの中身が一字一句同じである
- [ ] 7. `/ndf:restart` が出す再開コマンドは、文書のパス（`.ndf/handoff/<名>.md`）を含む
- [ ] 8. 対象の文書が既にあるとき、`/ndf:restart` は新しい文書を作らず、既存の文書の「現在地」と「次にやること」を書き直す（同じ見出しの節が 2 つにならない）
- [ ] 9. 更新の後に本体が 300 行を超えたら、終わった項目が `<名>-history.md` へ移り、本体は 300 行以下になる
- [ ] 10. supervisor・worker の起動指示と本文は、引継ぎ文書を書く手順を持たない（作る・更新する・消すのは conductor だけ）

消す
- [ ] 11. 対象が閉じたとき、conductor は文書の決定・未検証の項目・起票が課題の本文か Pull Request にあることを確かめてから本体と `-history.md` を消し、報告に消したパスを並べる。確かめられない事実があれば消さずに、その事実を報告に並べる

読む
- [ ] 12. 新しいセッションで `/ndf:development-workflow .ndf/handoff/<名>.md の続きから` を打つと、conductor は文書の「次にやること」の最初の項目から始める
- [ ] 13. 名指しの無い再開で、`.ndf/handoff/` に `/goal` の目標か課題番号と一致する文書が 1 本だけあれば、その文書を読む
- [ ] 14. 名指しの無い再開で、一致する文書が 2 本以上あると、どれも読まずに候補のパスを示して利用者へ聞く
- [ ] 15. 名指しした文書が無いとき、conductor は別の文書を推測で読まず、課題の本文と Pull Request から状態を戻し、無かったパスを報告する

書かないもの
- [ ] 16. 文書の正本の規則が、承認・同意を次のセッションへの許可として書くこと（「承認済みなのでマージしてよい」など）・認証情報・課題の本文と Pull Request と `progress.jsonl` が持つ状態の写しを禁じ、承認は課題か Pull Request の URL と日時の事実として書くと定める

正本と移行
- [ ] 17. 置き場・名前・節の形・CRUD の規則は 1 か所だけに書かれ、`restart/SKILL.md`・`context-window.md`・`relay.md`・用語集はそこを指す

- [ ] 19. 移行の後、メインディレクトリに `.ndf/handoff/milestone-26.md` と `milestone-26-history.md` があり、`issues/handoff-milestone26*.md` は無い。中身は移す前と同じである

退行しないこと
- [ ] 20. 既存のテスト（`sprint-state.py`・`supervise.py note` のテストを含む）がすべて通る
- [ ] 21. `/ndf:restart` の、再開コマンドを決められないとき（表の 3 行目）の振る舞いは変わらない（文書を作らず、ブロックを出さずに終える）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 本体は 300 行以下に保つ（前提 7）。消した文書のパスが報告に残る |
