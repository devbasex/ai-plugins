# #1560: 決定の記録

設計の本体は [issue-1560-design.md](issue-1560-design.md) にある。この文書は本体の「決定の記録」の節を分けたものである。

## 決定 1: 正本は新しい参照 `development-workflow/references/handoff.md` に置く

`context-window.md` は 292 行で、context window の切り方・委譲・残量を扱う。引継ぎ文書の置き場・節・4 つの操作を
足すと主題が 2 つになり、restart と relay が指す先が節単位になる。独立した参照にすれば、restart・context-window・
relay・用語集が 1 つのファイルを指すだけで済む。`context-window.md` の節に置く案は、上の理由で採らない。

根拠: Value 7（MVV 版 2）

## 決定 2: 節の見出しの唯一の定義は雛形のファイルに置き、スクリプトはそれを読む

`init` が写す見出しと `check` が確かめる見出しを 1 つのファイルから読めば、2 か所がずれない。正本の参照は
節ごとの書くことを表で持ち、見出しの文はその雛形を指す。見出しをスクリプトの定数に持つ案は、雛形と定数の
2 か所になるため採らない。雛形を Skill の参照の中に置く案は、スクリプトが Skill の文書を読む依存になるため採らない
（`scripts/data/` に `ndf-common-principles.md` の前例がある）。

根拠: Value 7 / Value 6（MVV 版 2）

## 決定 3: パスの解決・作る・探す・置き換え・検査・消すを `handoff.py` にする

worktree の中からメインディレクトリを見つける・名の形を確かめる・一致する本体を数える・囲みを一字一句同じに置く・
行数を数えるは、判断の要らない手順である。手順に書いて LLM に回すと、worktree の `.ndf/` へ書く誤り（I1）と
囲みの食い違い（I4）を防げない。LLM に残すのは、対象の決め方・節の中身・終わった項目の選び方・消す前の事実の照合である。
手順だけに書く案は、上の 2 つの誤りを機械で止められないため採らない。

根拠: Value 4（MVV 版 2）

## 決定 4: 名指しの無い再開の一致は、ファイル名の名と入力の語で決める

`issue-<N>` は `#<N>`、`milestone-<N>` はマイルストーンの番号、`sprint-<X>` はスプリント名で当てる。課題が属する
マイルストーンを GitHub から引いて広く当てる案は、外への呼び出しが要り、当たる本数が増えて聞き返しが増えるため
採らない。restart が必ずパスを名指しするため、名指しの無い再開は人が手で打ったときだけに限られる。

根拠: Value 4 / Value 2（MVV 版 2）

## 決定 5: 本体の上限は 300 行のままにし、`--max-lines` で変えられるようにする

今の本体は 137 行、履歴は 172 行で、1 対象の 42 セッション分が 300 行に収まっている。値はプロジェクトで変わりうる
ため引数で受ける。宣言（`.ndf/`）に置く案は、使う側が現れるまで設定の項目を増やすだけのため採らない。

根拠: Value 3 / Value 5（MVV 版 2）

## 決定 6: 「前の会話の進み」だけを機械で履歴へ移し、ほかの終わった項目は conductor が移す

`sprint-state.py render --demote` が作る節は、次のセッションでは必ず終わっている。ほかの節のどの項目が
終わったかは中身を読まないと決まらない。すべてを conductor に任せる案は、決まった形の移しを LLM に回すため採らない。
すべてを機械で移す案は、終わったかの判断ができないため採らない。

根拠: Value 4（MVV 版 2）

## 決定 7: 消す前の事実の照合は conductor が行い、`remove` は消すだけにする

決定・未検証の項目・起票が課題の本文か Pull Request に「ある」かは、文面の一致ではなく意味で決まる。
スクリプトで課題の本文を引いて文字列で照らす案は、言い換えた記録を「無い」と誤り、消せない文書が残るため採らない。

根拠: Value 4 / Mission（MVV 版 2）

## 決定 8: 新しいセッションは「次にやること」の 1 つ目から始め、状態は課題の本文と Pull Request で確かめる

文書は前のセッションが書いた計画で、状態の正は課題の本文と Pull Request である（写しを書かない規則と同じ理由）。
1 つ目が既に済んでいれば次へ進み、食い違いを報告する。文書の項目を状態より優先する案は、文書が古いときに
済んだ工程をやり直すため採らない。

根拠: Value 7（MVV 版 2）

## 決定 9: 節の読み書きの関数を `lib/handoff_doc.py` へ移し、`sprint-state.py` と `handoff.py` で共有する

同じ文書の同じ節を 2 つのスクリプトが書く。見出しの照合を 2 か所に持つと、囲みの中の `#` の扱いなどがずれる。
`handoff.py` が `sprint-state.py` を読み込む案は、スクリプトどうしの依存になるため採らない。

根拠: Value 6（MVV 版 2）

## 決定 10: 移行は中身を変えずに移し、パスの参照は次の更新で直す

受け入れ条件 19 は移す前後の中身が同じことを求める。移した後、今の本体の「次に実行するコマンド」と先頭の
履歴へのリンクは古いパス（`issues/handoff-milestone26*.md`）を指すため、移行の直後の更新（`handoff.py next` と
リンクの書き直し）で新しいパスへ直す。移しながら書き換える案は、同じであることを sha256 で確かめられなくなるため採らない。

根拠: Value 3（MVV 版 2）
