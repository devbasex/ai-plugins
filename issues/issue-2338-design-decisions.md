# #2338 の設計: 決定の記録

設計文書の本体は [issue-2338-design.md](issue-2338-design.md) にある。番号 `STD<数>`・`PRD<数>`・`LIB<数>`・`MSR<数>` は外部の調査の表を指す。外部の調査は [issue-2338-design-research.md](issue-2338-design-research.md) にある。

## 決定の記録

### 決定 1: 出力先を既存のハンドラと差し替えられるよう、書き口の枠組みに標準の `logging` を採り、別々に起動したプロセスから 1 ファイルへ書くハンドラだけを自前で作る

書き口は専用の logger `ndf.run` を 1 つ持ち、出力先を `logging.Handler` の派生として足す（LIB1）。`propagate` を偽にし、ルートの logger には
ハンドラを足さない。依存先のライブラリが `logging` へ出す行は記録へ入らず、記録の行が依存先の出力へ混ざることもない。出力先を `Handler` に
そろえると、#2608 が既存のハンドラを書き直さずに足せる。OpenTelemetry へ送る `LoggingHandler`（LIB5）と、CloudWatch Logs へ送る watchtower（LIB6）である。
秘密を伏せる処理と 1 行の上限の判定は、出力先へ渡す前に書き口が済ませる（決定 4）。

自前で作るのは、ファイルの出力先の `Handler` 1 つである。Python の公式の手引き（LIB1）は、複数のプロセスから 1 ファイルへ書く道の 1 つに、
書き込みを直列化するハンドラを自分で書く形を挙げる。この `Handler` はその道に当たる。手引きの例の `multiprocessing` の `Lock` は
`subprocess` で起こした子へ届かないため、直列化には `fcntl.flock` を使う。記録のファイルは `O_RDWR|O_APPEND` で開く。`fcntl.flock(LOCK_EX)` の中で 1 行の全バイトを
書き切るまで `os.write` を呼ぶ（STD4・STD5）。書き切れないときは、排他を持ったまま追記前の長さへ戻す。強制終了で残った書きかけの行は、
次に書く者が改行で閉じる（決定 14）。行の形は #2335 の JSON Lines（STD1）のままにし、親子の関係を `run_id` と `parent_id` で持つ。
この 2 つは OpenTelemetry の TraceId と SpanId（STD2）と同じ役割を持つ。OpenTelemetry へ送る出力先は、送るときに `trace_id`・`span_id`（STD6）へ写す。

比べた候補と採らない理由は次のとおりである。

| 候補 | 採らない理由 |
| --- | --- |
| `QueueHandler` / `QueueListener`（LIB1） | 公式の手引きが、複数のプロセスから 1 ファイルへのログを非対応と書く。キューを共有できるのは同じプロセスのスレッドと `multiprocessing` の子だけで、`subprocess` で起こす別のエントリポイントには届かない。手引きの代わりの形（全員が `SocketHandler` で送り、受け手のプロセスが書く）は、起点の実行が先に終わる場合と子が別のリポジトリで動く場合に受け手を常駐させる運用が要る |
| concurrent-log-handler（LIB4） | 別々のプロセスから排他で書ける点は要件に合う。ただし書き切れなかった行を戻す処理と、強制終了で残った書きかけの行を閉じる処理を持たない。別のロックファイルを介すため、短命のプロセスでは LIB7 と同じく遅い。依存の検査（`lib/deps.py`）が依存の欠けで止めたことも記録へ残すには、書き口が標準ライブラリだけで動く必要がある。主な機能のファイルの回転は、日付のディレクトリと 30 日の寿命で足りる |
| filelock（LIB7） | NDF の extra `locks` で導入済みだが、短命のプロセスの 1 行に 113 ms かかる（import 82 ms と 0.05 秒間隔の試し直し。`fcntl.flock` は 0.21 ms。MSR2）。書きかけの行を閉じない（MSR3）。依存の欠けで止めたことを記録へ残せない点は LIB4 と同じ |
| portalocker（LIB8） | `fcntl.flock` を包むだけで、書き切れなかった行を戻す処理と書きかけの行を閉じる処理は自分で書くことになる。extras が要り、LIB4 と同じく依存の欠けで止めたことを記録へ残せない |
| SQLite の WAL（LIB9） | 8 プロセスの並行で壊れた行 0（MSR1）だが、短命のプロセスの 1 行に 13.2 ms かかり、`fcntl.flock` の約 60 倍である（MSR2）。読むのに SQL が要り、`jq`・`grep` と、ファイルを読む収集の仕組み（PRD2・PRD3）が使えない。WAL は同じホストが前提である |
| SQLite の DELETE journal（LIB9） | 読むのに SQL が要る点は WAL と同じである。書くたびに journal のファイルを作って消すため、WAL より遅い。POSIX の助言ロックに頼り、NFS では壊れる |
| DuckDB（LIB10） | 書けるのは 1 つのプロセスだけで、別々に起動したプロセスから同じ記録へ書けない |
| LMDB（LIB11） | extras が要り、読むのに専用の API が要る。リモートのファイルシステムでは使えない |
| Redis Streams（LIB12） | サーバーの常駐が要る。起点の実行が先に終わる場合と、利用先のリポジトリで動く子にも受け手を用意する運用が要る |
| syslog とソケットの受け手（PRD5） | 手元のコンテナに `/dev/log` が無く、受け手の常駐が要る。`QueueHandler` の行の受け手の形と同じ運用が要る |
| Fluent Bit の forward と Vector の socket（PRD6） | 受け手の常駐が要る。手元の既定は受け手が無くても書けるファイルにし、受け手へ送る形は出力先の 1 つとして #2608 が足す |
| ローカルの OpenTelemetry Collector（PRD7） | 受け手の常駐が要る。LIB5 と同じく送る出力先の 1 つとして残す |
| 実行ごとの別ファイル | 排他は要らなくなるが、1 回の起動（子の実行を含む）を 1 つの記録から読めない（F1・受け入れ条件 1a） |
| structlog（LIB2） | 書き出しを LIB1 のハンドラへ任せるため、加えても複数のプロセスの排他は解けない。行の形は #2335 が決めており、処理の連鎖を足す理由が無い。extras が要る |
| loguru（LIB3） | `enqueue` が守るのは `multiprocessing` で起こした子に logger を渡した場合だけで、`subprocess` の子と別のコンテナを守らない。extras が要る |
| opentelemetry-sdk（LIB5）を書き口にする | 送り先（Collector か OTLP の受け手）の運用が前提で、手元の既定のファイルを持たない。LIB1 の `Handler` として足せるため、送る出力先の 1 つとして残す |
| journald（PRD4）へ書く | 手元のコンテナに journald が無い |

`fcntl` を import してよいのは `lib/locks.py` だけである（構造の検査 `scripts/check-script-structure.py` の I14）。`lib/locks.py` は filelock を要するため、
`run_log.py` は読まない。`run_log.py` が `fcntl` を直に使う許可を `scripts/script-structure-allow/` に置く（前例は `lib/state_home.py` の許可）。
許可の理由には「標準ライブラリだけで書く・filelock の遅さ」を書く。

- 作り方: ライブラリやサービスを使う・自前で作る
- 比べた候補: STD1 / STD2 / STD4 / STD5 / STD6 / LIB1 / LIB2 / LIB3 / LIB4 / LIB5 / LIB6 / LIB7 / LIB8 / LIB9 / LIB10 / LIB11 / LIB12 / PRD4 / PRD5 / PRD6 / PRD7

根拠: Value 6 / Value 7（MVV 版 5）。プロジェクトの方針「基盤は既存ライブラリを使う」に従い、枠組みは標準の `logging` を使い、要件を満たす既存のハンドラが無い 1 つだけを自前で作る

### 決定 2: 既存の収集の仕組みが既定の設定のまま 1 行を読めるよう、1 行の上限を 32,000 バイトとして上限の宣言に置き、超える分は長い文字列から全文ファイルへ移す

Fluent Bit の入力 `tail` は、1 ファイルの読み込みの領域の既定が 32k で、超える行に当たるとそのファイルの監視をやめる（PRD2）。上限を改行を含めて
32,000 バイトに置けば、Fluent Bit も Vector（既定 102,400 バイト、PRD3）も既定の設定のまま記録のファイルを後から集められる。CloudWatch Logs の
1 イベントの上限 1,024 KB（PRD1）にも収まる。手元で測った行の最大は、プランの状態の記録で 570 バイト、使用量の帳簿で 1,929 文字（UTF-8 で
多くとも 5,787 バイト）である。上限はその 5 倍を超える。通常の行は全文ファイルを作らずに済み、外部コマンドの失敗の出力のような長い理由だけが移る。
移す単位は行ではなく文字列にし、移した値の位置へ参照（パス・文字数・sha256）を置く。行の残りの鍵は行に残り、`grep` と `jq` で行を絞れる。
値は上限の宣言（`contracts/limits.json` の `run-log.line`）に置く。`limits.py` が持てる値に `bytes` を足す。

32,000 バイトの理由が効く範囲は、ファイルの出力先と、そのファイルを後から集める場合である。書き口は出力先によらず同じ上限で判定するため、
ほかの出力先も 32,000 バイトを超える行を受け取らない。

上限を置かない形は採らない。外部コマンドの出力の長さには上限が無く、記録の 1 ファイルを読むツール（`jq`・エディタ・収集の仕組み）が重くなるか、
読むのをやめる。

- 作り方: 標準に倣う
- 比べた候補: PRD1 / PRD2 / PRD3 / STD1

根拠: Value 1 / Value 4（MVV 版 5）

### 決定 3: 途中で記録へ書けなくなっても外の世界を中途半端に残さないよう、本体は終わりまで動かし、結果だけを `stopped` にする

本体の途中で止めると、push の後・Pull Request を作る前のような半端な状態が残り、利用者が手で戻すことになる。終わりまで動かして結果を `stopped` に
すれば、呼ぶ側は止まったことを知る。途中で書けなくなったときは `end` の行も書けない。そのため核は本体の元の結果 JSON を鍵 `original_result` へ入れて
標準出力へ出す。本体が済ませた外の操作の結果（作った Pull Request の番号など）が呼ぶ側に届き、再実行で同じものを二重に作ることを防ぐ。
始まりの行を書けないときは本体を動かさない。この時点ではまだ外の世界を変えていないためである。

次の書き込みで例外を投げて本体を止める形は採らない。記録の失敗が、記録とは関係の無い外の操作を途中で止めることになる。

根拠: 上位の原則（人を守る） / Value 2（MVV 版 5）

### 決定 4: 動く場所ごとに出力先を変えられるよう、出力先を環境変数 `NDF_RUN_LOG_SINK` 1 つで選び、出力先の実装は名前で登録する

出力先を変えたいのは動く場所（手元か Factory のランナーか）であり、リポジトリではない。同じリポジトリが手元でも Factory でも動くため、
リポジトリに置く設定（`.ndf/`）では切り替えられない。ランナーが起動時に環境変数を 1 つ立てれば足り、子の実行へもそのまま届く。
出力先は `logging.Handler` の派生で、`emit` で 1 行を書き、加えて全文ファイルを置く `put_text` を持つ（決定 1）。伏せる処理と上限の判定は書き口が先に済ませる。
こうすると、どの出力先も秘密の値と上限を超える行を受け取らない。既定で登録するのは `file` だけである。CloudWatch Logs の出力先（LIB6 か、ECS の `awslogs`・FireLens。PRD1）は #2608 が登録する。

`.ndf/` の宣言で選ぶ形は採らない。上の理由で、場所ごとの切り替えにならない。環境変数にモジュールのパスを書いて読み込む形も採らない。
環境変数を書ける者が任意のコードを読み込ませられる経路を、記録のために増やすことになる。
記録の行を標準出力か標準エラーへ出して、コンテナのログドライバー（PRD1）に集めさせる形は既定にしない。標準出力は結果 JSON、標準エラーは人へ見せる診断に使っており、
記録の行を混ぜると呼ぶ側と人の両方が読み分けることになる。手元で集めたいときは、Fluent Bit か Vector（PRD2・PRD3）が記録のファイルを読む。

- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB1 / LIB5 / LIB6 / PRD1 / PRD2 / PRD3

根拠: Value 6 / Value 5（MVV 版 5）

### 決定 5: 子の実行が親と別のリポジトリや日付で動いても同じ記録へ書けるよう、出力先の位置を `NDF_RUN_LOG` で渡す

置き場のパスは起点の実行のリポジトリと UTC の日付を含む。子が自分のリポジトリと日付からパスを作ると、別のリポジトリで動く子（リリースを届ける利用先のリポジトリ）と
UTC の 0 時をまたいだ子が、別のファイルへ書く。親が自分の識別子（`NDF_RUN_ID`）と位置（`NDF_RUN_LOG`）を環境変数で渡せば、子は計算せずに同じ位置へ
書ける。子プロセスへ環境変数で文脈を渡し、子が起動時に取り出す形は STD3 に倣う。受け継いだファイルが無いときは起点の実行として自分のファイルを作る。
古い環境変数が残った端末で、存在しないファイルへ書こうとして止まるより、記録を残す方を選ぶ。

`NDF_RUN_ID` から起点の識別子をたどってパスを作る形は採らない。子の子をたどるために起点の識別子をもう 1 つ渡すことになり、リポジトリの違いも解けない。

- 作り方: 標準に倣う
- 比べた候補: STD3

根拠: Value 6（MVV 版 5）

### 決定 6: 複数のコンテナが利用者の根を共有しても記録が混ざらないよう、同じファイルへ書くのを同じコンテナの親子に限り、共有するのは日付のディレクトリだけにする

利用者の根は、同じホストの複数のコンテナが共有する docker のボリュームにある（設計文書の「あるべき姿の根拠」の実測）。記録のファイル名は起点の実行の識別子
（`uuid4` の 16 進 12 字）である。ファイルへ書くのはその起点の実行と、環境変数を受け継いだ子だけである。環境変数はコンテナの境界を越えて受け継がれない。
そのため別のコンテナの実行は、同じ日付のディレクトリの別のファイルへ書く。共有する操作はディレクトリの作成と寿命の掃除の 2 つである。どちらも相手が
先に済ませていても誤りにしない（`exist_ok`・消す対象が無くなっていれば飛ばす）。これで要求の未決 5 は、コンテナをまたぐ排他に頼らずに満たす。

コンテナごとに置き場を分ける形は採らない。利用者の根に置く理由（コンテナの再起動で消えない・複数のコンテナで集計に使う）が失われる。

根拠: Value 6 / Value 7（MVV 版 5）

### 決定 7: シグナルで中断しても記録の行が切れず、核が自分の排他を待って止まらないよう、排他の区間の中で届いた中断を区間の後へ遅らせる

P1 の核の受け手は、主スレッドで `_Interrupt` を投げる。受け手が排他の区間の中で投げると、行が途中で切れたまま抜け、続けて `end` を書く核が自分の
排他を待つ（STD4。開き直した記述どうしで排他になる）。主スレッドが区間にいる間は印を立て、受け手は印を見たら終わり方を保留して戻る。`write` は区間を
出た後に保留を見て `_Interrupt` を投げる。核の今の `except _Interrupt` がそのまま受ける。印は `Lock` を取る前に立て、返した後に下ろし、隙間を作らない。

区間の間だけシグナルを止める形（`signal.pthread_sigmask`）は採らない。Python の受け手は、どのスレッドがシグナルを受けても主スレッドで動くため、
主スレッドで止めても受け手が区間の中で動くことを防げない。

根拠: Value 7（MVV 版 5）

### 決定 8: 核の外の起動が親の記録の `run_id` を汚さないよう、`run_log.diag` と `run_log.clip` は、記録を開いたときと、親の文脈を受け継いで子の実行として開いたときだけ記録へ書く

ライブラリの関数は、hook や核を通らない CLI（監視のループを動かす `lib/monitor.py` など）からも呼ばれる。それらが親の `run_id` で行を書くと、
親の `end` の後に行が並び得て I1 が破れる。そこで、プロセスの中で記録を開いていないときの `diag`・`clip` は次のどちらかにする。

| 起動時の環境変数 | 振る舞い |
| --- | --- |
| `NDF_RUN_ID` と `NDF_RUN_LOG` の両方がある | 最初の 1 行の前に、子の実行として自分の `run_id` で記録を開く（`start` の `fields` に `outside_core: true`）。`end` はプロセスの終わり（`atexit`）に `how: "exit"`・`result: null` で書く。記録へ書けなければ標準エラーにだけ出し、結果を置き換えない（核の外のため） |
| どちらかが無い | 標準エラーへ書くだけ（`clip` は切るだけ） |

これで、監視のループを動かす CLI が核を通らなくても、核から起動されたときは拒否の件数の警告が記録に残る（受け入れ条件 2c・前提 10）。
SIGTERM と SIGKILL で終わると `end` が無く、前提 6 のとおり「途中で強制終了した」と読む。

環境変数があるだけで親の `run_id` のまま書く形は採らない。上に書いたとおり I1 が破れる。

根拠: Value 7（MVV 版 5）

### 決定 9: 任意の形の認証情報も記録へ残さないよう、トークンの形の置き換えに加え、秘密と宣言した環境変数の値を伏せる

`secret_redact` の置き換えは、決まった形（GitHub のトークン・URL の資格情報・認証ヘッダー）だけを伏せる。`AI_GATEWAY_API_KEY` のような任意の形の値は
伏せない。環境変数の契約の行に `secret: true` を足し、書き口がその空でない値を、出力先へ渡す前に置き換える。空の値は照合しない
（空文字列で置き換えると、すべての文字の間に伏せ字が入る）。`redact_output` は短く縮める処理も兼ねるため、伏せる処理（`redact`）を分け、記録は
伏せる処理だけを通す。入力の宣言の `secret`（柱 P8）が入った後は、核がその値も同じ置き換えへ足す。

秘密の名前は、書き口（`run_log`）が記録を開くときに自分で環境変数の契約（プラグインの根の `contracts/env/`）から読む。核から渡さない。
核を通らない監視の CLI が決定 8 で子の実行として記録を開く経路にも、核が名前を読む場所が無いためである。名前を呼ぶ側の引数で受けると、
空で開く実装ができ、任意の形の値が記録へ残る（I5・受け入れ条件 5）。契約を読めないときは記録を開かず、書けないときと同じ扱いにする
（核の中は I7、核の外は標準エラーにだけ出す）。

根拠: C1 / 上位の原則（人を守る）（MVV 版 5）

### 決定 10: 止まった理由を失わずに今の表示を保つため、2 ファイルの切る箇所は全文を記録へ書いてから今の長さで返し、核は理由を切らない

受け入れ条件 3 は、本体が渡した理由が結果 JSON と `end` の行に同じ文字列で残ることを求める。核が理由を縮めると両方がそろわないため、核は
例外の理由を切らない。2 ファイルの 6 か所は、結果の `summary` や端末の行として人へ見せる文を作る箇所である。ここで全文を出すと、端末の文と

### 決定 14: 書いている途中の実行を SIGKILL で止めても、ほかの実行の行が読めるよう、排他を取った書き手が書きかけの行を改行で閉じてから書く

SIGKILL は受け手を動かさないため、決定 1 の戻す処理は働かず、書きかけの 1 行が残り得る。そのまま次の行を追記すると、次の行が書きかけの行へ

改行でなければ先に改行を書く。書きかけの行は JSON として読めない 1 行として残り、読む側が飛ばして数える。止めた実行は `end` が無いことで判別する（前提 6）。
Fluent Bit と Vector も行を改行で区切るため（PRD2・PRD3）、後から集める仕組みでも同じ 1 行だけが読めない行になる。
8 プロセスで書き続ける書き手を SIGKILL で計 320 回止めた実測で、この形は書きかけの行が次の行とつながらなかった（MSR3）。

書きかけの行を消す形は採らない。消すには行の始まりを探して切り詰めることになり、その間に別の書き手が待つうえ、残った手がかりを失う。
