# #2338 の設計: 決定の記録

設計文書の本体は [issue-2338-design.md](issue-2338-design.md) にある。番号 `STD<数>`・`PRD<数>`・`LIB<数>` は [issue-2338-design-research.md](issue-2338-design-research.md) の「外部の調査」の表を指す。

## 決定の記録

### 決定 1: 依存を足さずに行が混ざらない記録を得るため、書き口を標準ライブラリで自前で作り、1 行を排他の中で書き切る

書き口は extras の無い環境でも記録を残す必要がある（依存の検査 `deps.py` の止まりも核を通る）。そのため標準ライブラリだけで書く。
記録のファイルを `O_APPEND` で開き、`fcntl.flock(LOCK_EX)` の中で 1 行の全バイトを書き切るまで `os.write` を呼ぶ。`os.write` は容量不足などで
要求より少ないバイト数を返すことがある（STD5）。書き切れないときは、排他を持ったまま追記前の長さへ戻す。途中まで書いた行が残ると、
次に書く子の行が同じ行へつながるためである。行の鍵は #2335 の形（JSON Lines、STD1）のままにする。親子の関係は `run_id` と `parent_id` で持つ。
この 2 つは OpenTelemetry の TraceId と SpanId（STD2）と同じ役割を持つ。

Python 標準の `logging`（LIB1）は採らない。その上の structlog・python-json-logger（LIB2・LIB3）も採らない。`logging` はプロセスの全体で共有されるため、
`argparse` や依存先の出力まで記録へ混ざる。排他・全文ファイル・秘密を伏せる処理は、どれを使っても自前で足すことになる。LIB2・LIB3 は extras が要る。
opentelemetry-sdk（LIB5）は送り先（Collector）の運用が前提である。手元の既定のファイルへ排他で書く形を持たない。排他に filelock（LIB6）を使う形も採らない。
extras の無い環境で動かず、標準の `fcntl.flock`（STD4）で足りる。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1 / STD2 / STD4 / STD5 / LIB1 / LIB2 / LIB3 / LIB5 / LIB6

根拠: Value 6 / Value 7（MVV 版 5）

### 決定 2: 理由を切らずに 1 行を読める大きさに保つため、1 行の上限を 64 KiB として上限の宣言に置き、超える分は長い文字列から全文ファイルへ移す

上限は、手元で測った行の最大（プランの状態の記録で 570 バイト、使用量の帳簿で 1,929 文字）の 30 倍以上に置いた。通常の行は全文ファイルを作らずに済み、
外部コマンドの失敗の出力のような長い理由だけが移る。CloudWatch Logs の 1 イベントの上限 1,024 KB（PRD1）にも収まる。差し替えた出力先でも 1 行を
1 イベントで送れる。移す単位は行ではなく文字列にし、移した値の位置へ参照（パス・文字数・sha256）を置く。行の残りの鍵は行に残り、`grep` と
`jq` で行を絞れる。値は上限の宣言（`contracts/limits.json` の `run-log.line`）に置く。`limits.py` が持てる値に `bytes` を足す。

上限を置かない形は採らない。外部コマンドの出力の長さには上限が無く、記録の 1 ファイルを読むツール（`jq`・エディタ）が重くなる。

- 作り方: 自前で作る
- 比べた候補: PRD1 / STD1

根拠: Value 1 / Value 4（MVV 版 5）

### 決定 3: 途中で記録へ書けなくなっても外の世界を中途半端に残さないよう、本体は終わりまで動かし、結果だけを `stopped` にする

本体の途中で止めると、push の後・Pull Request を作る前のような半端な状態が残り、利用者が手で戻すことになる。終わりまで動かして結果を `stopped` に
すれば、呼ぶ側は止まったことを知る。途中で書けなくなったときは `end` の行も書けない。そのため核は本体の元の結果 JSON を鍵 `original_result` へ入れて
標準出力へ出す。本体が済ませた外の操作の結果（作った Pull Request の番号など）が呼ぶ側に届き、再実行で同じものを二重に作ることを防ぐ。
始まりの行を書けないときは本体を動かさない。この時点ではまだ外の世界を変えていないためである。

次の書き込みで例外を投げて本体を止める形は採らない。記録の失敗が、記録とは関係の無い外の操作を途中で止めることになる。

根拠: 上位の原則（人を守る） / Value 2（MVV 版 5）

### 決定 4: 動く場所ごとに出力先を変えられるよう、出力先を環境変数 `NDF_RUN_LOG_SINK` 1 つで選び、出力先の実装は名前で登録する

出力先を変えたいのは動く場所（手元か Factory のランナーか）であり、リポジトリではない。同じリポジトリが手元でも Factory でも動くため、
リポジトリに置く設定（`.ndf/`）では切り替えられない。ランナーが起動時に環境変数を 1 つ立てれば足り、子の実行へもそのまま届く。
出力先は `open`・`append`・`put_text`・`close` の 4 つの操作だけを持つ。伏せる処理と上限の判定は書き口が先に済ませる。
こうすると、どの出力先も秘密の値と上限を超える行を受け取らない。既定で登録するのは `file` だけである。CloudWatch Logs の出力先（LIB4 などを使う）は #2608 が登録する。

`.ndf/` の宣言で選ぶ形は採らない。上の理由で、場所ごとの切り替えにならない。環境変数にモジュールのパスを書いて読み込む形も採らない。
環境変数を書ける者が任意のコードを読み込ませられる経路を、記録のために増やすことになる。

- 作り方: 自前で作る
- 比べた候補: LIB1 / LIB4 / LIB5

根拠: Value 6 / Value 5（MVV 版 5）

### 決定 5: 子の実行が親と別のリポジトリや日付で動いても同じ記録へ書けるよう、出力先の位置を `NDF_RUN_LOG` で渡す

置き場のパスは起点の実行のリポジトリと UTC の日付を含む。子が自分のリポジトリと日付からパスを作ると、別のリポジトリで動く子（リリースを届ける利用先のリポジトリ）と
UTC の 0 時をまたいだ子が、別のファイルへ書く。親が自分の識別子（`NDF_RUN_ID`）と位置（`NDF_RUN_LOG`）を環境変数で渡せば、子は計算せずに同じ位置へ
書ける。子プロセスへ環境変数で文脈を渡し、子が起動時に取り出す形は STD3 に倣う。受け継いだファイルが無いときは起点の実行として自分のファイルを作る。
古い環境変数が残った端末で、存在しないファイルへ書こうとして止まるより、記録を残す方を選ぶ。

`NDF_RUN_ID` から起点の識別子をたどってパスを作る形は採らない。子の子をたどるために起点の識別子をもう 1 つ渡すことになり、リポジトリの違いも解けない。

- 作り方: 標準に倣う
- 比べた候補: STD3

根拠: Value 6（MVV 版 5）

### 決定 6: 複数のコンテナが利用者の根を共有しても記録が混ざらないよう、同じファイルへ書くのを同じコンテナの親子に限り、共有するのは日付のディレクトリだけにする

利用者の根は、同じホストの複数のコンテナが共有する docker のボリュームにある（設計文書の「あるべき姿の根拠」の実測）。記録のファイル名は起点の実行の識別子
（`uuid4` の 16 進 12 字）である。ファイルへ書くのはその起点の実行と、環境変数を受け継いだ子だけである。環境変数はコンテナの境界を越えて受け継がれない。
そのため別のコンテナの実行は、同じ日付のディレクトリの別のファイルへ書く。共有する操作はディレクトリの作成と寿命の掃除の 2 つである。どちらも相手が
先に済ませていても誤りにしない（`exist_ok`・消す対象が無くなっていれば飛ばす）。これで要求の未決 5 は、コンテナをまたぐ排他に頼らずに満たす。

コンテナごとに置き場を分ける形は採らない。利用者の根に置く理由（コンテナの再起動で消えない・複数のコンテナで集計に使う）が失われる。

根拠: Value 6 / Value 7（MVV 版 5）

### 決定 7: シグナルで中断しても記録の行が切れず、核が自分の排他を待って止まらないよう、排他の区間の中で届いた中断を区間の後へ遅らせる

P1 の核の受け手は、主スレッドで `_Interrupt` を投げる。受け手が排他の区間の中で投げると、行が途中で切れたまま抜け、続けて `end` を書く核が自分の
排他を待つ（STD4。開き直した記述どうしで排他になる）。主スレッドが区間にいる間は印を立て、受け手は印を見たら終わり方を保留して戻る。`write` は区間を
出た後に保留を見て `_Interrupt` を投げる。核の今の `except _Interrupt` がそのまま受ける。印は `Lock` を取る前に立て、返した後に下ろし、隙間を作らない。

区間の間だけシグナルを止める形（`signal.pthread_sigmask`）は採らない。Python の受け手は、どのスレッドがシグナルを受けても主スレッドで動くため、
主スレッドで止めても受け手が区間の中で動くことを防げない。

根拠: Value 7（MVV 版 5）

### 決定 8: hook や核の外の起動が他人の記録へ書かないよう、`run_log.diag` と `run_log.clip` は自分のプロセスで記録を開いたときだけ記録へ書く

ライブラリの関数は hook や核を通らない CLI からも呼ばれる。それらは核が起動した claude の下で動くと `NDF_RUN_LOG` を受け継ぐが、
自分の実行の識別子を持たない。環境変数だけで書くと、識別子の無い行が親の記録へ混ざり、I1 が破れる。プロセスの中で `open_run` が開いた記録が
あるときだけ書けば、核の外では標準エラーへ書くだけ（`clip` は切るだけ）になる。移していないスクリプトとも並んで動く。

根拠: Value 7（MVV 版 5）

### 決定 9: 任意の形の認証情報も記録へ残さないよう、トークンの形の置き換えに加え、秘密と宣言した環境変数の値を伏せる

`secret_redact` の置き換えは、決まった形（GitHub のトークン・URL の資格情報・認証ヘッダー）だけを伏せる。`AI_GATEWAY_API_KEY` のような任意の形の値は
伏せない。環境変数の契約の行に `secret: true` を足し、書き口がその空でない値を、出力先へ渡す前に置き換える。空の値は照合しない
（空文字列で置き換えると、すべての文字の間に伏せ字が入る）。`redact_output` は短く縮める処理も兼ねるため、伏せる処理（`redact`）を分け、記録は
伏せる処理だけを通す。入力の宣言の `secret`（柱 P8）が入った後は、核がその値も同じ置き換えへ足す。

根拠: C1 / 上位の原則（人を守る）（MVV 版 5）

### 決定 10: 止まった理由を失わずに今の表示を保つため、2 ファイルの切る箇所は全文を記録へ書いてから今の長さで返し、核は理由を切らない

受け入れ条件 3 は、本体が渡した理由が結果 JSON と `end` の行に同じ文字列で残ることを求める。核が理由を縮めると両方がそろわないため、核は
例外の理由を切らない。2 ファイルの 6 か所は、結果の `summary` や端末の行として人へ見せる文を作る箇所である。ここで全文を出すと、端末の文と
結果の文が変わる（受け入れ条件 6）。そこで `run_log.clip` が全文を記録へ書いてから、今と同じ長さで返す。

2 ファイルの 6 か所で切るのをやめる形は採らない。表示の文が変わり、受け入れ条件 6 に反する。

根拠: Value 1 / Value 8（MVV 版 5）

### 決定 11: 検査の記録の既存の集計を変えずに「不明」の理由を読めるよう、`failed_at` の決め方を変えずに `failed_reason` を足す

#2300 の「不明」の 17 行は、計画の状態から落ちたステップを読めなかった行である。原因は、状態のファイルが無い・記録が空・欠けを残して進んだ
ステップだけで終わった、のどれかである。`failed_at` の決め方を変えて欠けのステップを落ちた工程に数えると、`stats` の既存の集計と過去の行が
食い違う。そこで決め方は変えず、読めなかった理由をパスと見つからなかったものとして `failed_reason` に残す。同じ理由を実行の記録の `decision` に書く。
行の `run_id` から、その実行の記録の全体（gh・git の失敗の出力を含む）をたどれる。

根拠: Value 4 / Value 8（MVV 版 5）

### 決定 12: 監視のループの早期の警告を落とさないよう、出した印を警告の種類ごとに持ち、同じ回の確認で初めて現れた種類は今の 1 行の形で出す

今は 1 つの印で早期の警告を 1 回だけ出す。そのため先に標準エラーの記録の警告を出すと、後から現れた拒否の件数の警告が出ない（#2059）。印を種類
（`stderr`・`denials`）ごとに持てば、それぞれ 1 回ずつ出る。同じ回の確認で 2 つが初めて現れたときは今と同じく ` / ` でつないだ 1 行にし、
既存の出力と同じ文を保つ。`_early_error` の戻り値の形は変えず、種類つきの組を返す関数を別に足す。既存のテストの呼び方を書き換えずに済む。

根拠: Value 7（MVV 版 5）

### 決定 13: 人が 1 回で読み切れる量に収めるため、実装を核の拡張と 2 ファイルの移し替えの Pull Request 2 本に分ける

核の拡張は、すべての核を通るエントリポイントの振る舞い（記録・結果の置き換え）を変える。2 ファイルの移し替えは、その上で 2 件の不具合を直す。
分けると、核の拡張だけを revert して 2 ファイルの前の形へ戻す範囲が小さくなる。また 2 件の再現の手順を核の拡張が入った状態で通せる。
1 スプリント・Pull Request 1〜2 本は利用者の答え（2026-11-05）である。

根拠: Value 2（MVV 版 5）
