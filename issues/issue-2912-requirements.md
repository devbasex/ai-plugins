## 何が起きたか

NDF で開発ループを自動で回していると、AI が書いた設計が「設計承認ゲート（設計の Pull Request をマージする前に人の承認を求める点）で利用者が決める」という判断を残すことがある。承認ゲートの手前では、AI がプロジェクトの判断基準（MVV: Mission / Vision / Value）に照らして承認を省けるかを判定する（MVV 判定）。判断が残った設計は省けないと判定され、人の回答を待って止まる。10 月は、課題の作成から設計のマージまでの中央値が 87 時間あった（[課題の流れを分析した PR #2905](https://github.com/devbasex/ai-plugins/pull/2905)）。

この課題は一度 10 系の NDF で実装してリリースした（v10.27.53）。ただしリリース後テストで、人の承認が必須の操作（レッドライン）を含む設計まで承認を省けるという不合格が出たため、開いたままにしている（[リリース記録 PR #3013](https://github.com/devbasex/ai-plugins/pull/3013)）。

## 種類

機能追加（設計の書き方と MVV 判定に、新しい約束を足す）

## なぜ困るか

利用者は業務時間外に回答できないため、人へ戻った設計は翌営業日まで止まる。開発ループ（`.ndf/loop/lcore/laps.md`・`.ndf/loop/lproc/laps.md` の 2026-11-08〜11-10）で MVV 判定が承認を省かなかった理由の最多は、設計文書が「設計承認ゲートで利用者が決める」判断を含むことで、12 件あった。一方で、承認を省きすぎると、認可・戻せない削除・利用者のデータに関わる設計が人の目を通らずに実装へ進む。

## 目的

- 誰に効くか: `pace: fast` / `pace: auto` で開発ループを回す利用者
- 達成したい状態: 設計の判断は AI が理由とともに記録し、人へ戻るのはレッドラインに当たる判断と、AI が材料から決められない設計だけになる。人を待つ件数が減り、レッドラインの守りは弱まらない

## 対象範囲

含む:
- 設計の手順書（`design`）と設計文書のテンプレートのうち、判断の書き方
- MVV 判定の指示文のうち、人へ戻す条件
- 番号を示さずに「利用者が決める」行を止める、設計文書の検査（受け入れ条件 4）
- 承認を省けた割合を変更の前と後で比べる手段（形は設計が決める）
- 受け入れ条件 5・6 を実物の LLM で確かめること（この課題は、確かめるまで閉じない）

含まない:
- レッドラインを含む設計が承認なしで通る不具合の直し（[#3017](https://github.com/devbasex/ai-plugins/issues/3017) が扱う）
- 詳細設計の検査の移植（[#3664: 詳細設計のテンプレートと検査](https://github.com/devbasex/ai-plugins/issues/3664) が扱う）
- 承認ゲートの数（2 つのまま）
- レッドラインに当たる判断の扱い（人へ残す。緩めない）
- MVV 判定を読めない・打てないために人へ戻る場合（10 系の記録の 5 件。[#2614: 同じ本文を判定し直して揺れる](https://github.com/devbasex/ai-plugins/issues/2614)・[#2388: 判定を飛ばして「判定できない」になる](https://github.com/devbasex/ai-plugins/issues/2388) で扱い、どちらもクローズ済み）
- この要求の「境界」の節で「確認してから行う」に置いた項目の扱い。この課題では変えない（起票者の推定 S4）
- `pace: normal` の進め方（MVV 判定は参考の扱いで、承認は人が行う）

## 前提

- 前提 1: 「設計の判断」は、設計文書の「決定の記録」「未確認のまま残ること」の節に書く、作り方・範囲の取り方・既定値・扱いの選択を指す。必ず人の承認が要る操作の一覧（共通原則の C1〜C8）・プロジェクト MVV の P の番号・スプリント MVV の R の番号に当たる操作の承認は、ここに含めない
- 前提 2: 「未確認のまま残ること」の節は残す。この節に置くのは、デプロイの前に確かめられない事実（実測・外部の振る舞い）だけで、利用者に選ばせる判断を置かない
- 前提 3: MVV 判定が人へ戻すのは、「判断を人へ残している設計」ではなく「レッドラインに当たる判断がある設計」と「材料から決められない設計」になる
- 前提 4: 承認を省けた割合の比べ方を設計が決めるまで、比べる対象は「開発ループの記録の設計の行のうち、人へ委ねた判断を理由に人へ戻った 12 件」とする

## 受け入れ条件

- [x] 1. 設計文書のテンプレートと `design` の Skill の本文は、設計の判断を AI が決め、「決定の記録」に結論・理由・採らなかった案を書くよう求める。「設計承認ゲートで利用者が決める」形で判断を残す書き方を、テンプレートと本文のどこにも載せない
- [x] 2. テンプレートの「未確認のまま残ること」の節の説明は、置くものをデプロイの前に確かめられない事実に限り、利用者に選ばせる判断を置かないと書く
- [x] 3. 人へ残す判断があるとき、設計文書はその判断ごとに当たるレッドラインの番号（`C<番号>` / `P<番号>` / `R<番号>`）と、なぜ当たるかを 1 行で名指しする。テンプレートにその書き場所がある
- [ ] 4. 前提: レッドラインの番号を名指しせずに「利用者が決める」判断を書いた設計文書がある。操作: 設計の手順 5 の検査（設計文書の検査のスクリプト）を打つ。結果: 検査はその行を指摘して終了コード 1 で止まる。番号を名指しした行と、判断を人へ残さない設計文書では 0 を返す
- [ ] 5a. 指示文: MVV 判定の判定者（LLM）へ渡す指示文は、レッドラインに当たらない判断を AI が決めて記録した設計と、扱いが書かれた起票者の推定を、それだけを理由に「判定できない」へしないと定める
- [ ] 5b. 判定者の boundary: 設計文書の本文の変更がレッドラインに当たると判定者が判定した場合、判定者はその判断を回答の boundary（変更が当たるレッドラインの番号と中身）に載せ、承認ゲートは省かれない
- [ ] 5c. 機械の表の確かめ: 判定の後に機械が Pull Request の head の設計文書の「人へ残す判断」の表を読み、レッドラインの番号を持つ行が 1 つでもあれば承認ゲートを残して、判定の結果の理由（`why`）に表のパスと番号を残す。その行を前の Pull Request で人が承認したかは問わない（承認済みの判断を残したまま誤字を直す設計も止まる）。boundary は判定者の回答なので、機械は表の行の番号を boundary に書き足さない
- [ ] 6. 退行しない: レッドラインに当たる変更（例: `.ndf/` を書き換える設計＝C7）を含む設計文書を MVV 判定へ渡すと、今どおり承認ゲートを省かない。合格は、判定の boundary に C7 があるか、実際に変えたパスが MVV の設定ファイル（`.ndf/mvv.*`）かプロジェクトが宣言した承認必須のパス（`boundary_paths`）に当たって機械の検査で戻り、どちらの場合も承認を省かないことである。機械の検査が見るのはこの 2 つだけで、`.ndf/` の下のほかのファイルは見ない
- [ ] 7. 同じ課題の集合（未決 1）で、変更の前と後の MVV 判定の結果を数え、「従う」で承認ゲートを省いた割合が変更の後に上がる。数えた件数・割合・使ったコマンドをリリース後テストの記録に残す
- [ ] 8. 既存のテスト（`uv run --frozen --project . --all-extras pytest . -q -n 4`）がすべて通る

受け入れ条件 5 と書くときは、5a〜5c の 3 項目を指す。5a〜5c は 2026-11-27 に、もとの条件 5 の文を意味を変えずに分けたものである。

受け入れ条件 5・6 のチェックは 2026-11-26 に外した。v10.27.53 のリリース後テストで不合格になり、11 系の実物の LLM でも確かめていないためである。同じ日に、設計のレビューの指摘で 2 つの条件の文も書き直した。条件 5（今の 5c）は、表の行を判定の後の機械の確かめで止め、理由を `why` に残す設計（[設計書](./issue-2912-design.md) の決定 7）に合わせた。条件 6 は、機械の検査が見るパスを「今の姿」の補足の表のとおりに書いた。どちらも、承認ゲートを省かないという求めは変えていない。2026-11-27 に条件 5（今の 5c）を絞った。番号を持つ表の行は、前に人が承認したかを問わずに止める。承認済みの行を見分けるには、行ごとに入れた Pull Request と承認の記録をたどる仕組みが要り、それで省けるのは表のある設計文書を後の設計の Pull Request が直す場合だけで少ないためである（設計書の決定 7）。省く範囲は狭まり、承認ゲートを省かないという求めは強まる方向にだけ変わった。

## 用語

| 用語 | 意味 |
| --- | --- |
| レッドライン | MVV 判定が「従う」でも利用者の承認を省かない操作。共通原則の `C<番号>`・プロジェクト MVV の `P<番号>`・スプリント MVV の `R<番号>` の 3 層 |
| MVV 判定 | 承認ゲートのエビデンスが共通原則・プロジェクト MVV・スプリント MVV に従うかの判定。auto と fast では「従う」でレッドラインが無いときだけ承認ゲートを省く |
| 承認ゲート | 人手の承認を求める点。設計承認ゲートとリリース承認ゲートの 2 つだけ |
| 起票者の推定 | 課題の題・本文のうち、利用者の指示の原文に無く起票者が推して足した条件 |
| boundary | MVV 判定の結果の欄の 1 つ。変更が当たるレッドラインの番号と中身を並べる。空でなければ承認ゲートは省かれない。進め方の設定の `boundary_paths`（機械の検査が見るレッドラインのパス）とは別のもの |
