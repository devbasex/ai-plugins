# #842: retrospective が最後に issue-upkeep を呼ぶが、その作業は工程表にも持ち場にも無く、範囲と費用の上限が無い

正は課題の本文（#842）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 依頼（原文）

起票時の本文を、見出しの深さだけを 1 段下げてそのまま残す。

### 何を見つけたか

**`retrospective` は最後に `issue-upkeep` を呼ぶよう指示しているが、その作業は `development-workflow` の工程表にもフェーズの表にも無い。** 3 層で通すとき、supervisor は skill の指示に従って**工程表に無い作業へ入り、範囲と費用の上限が無いまま進む**。

| 文書 | 記述 |
| --- | --- |
| `retrospective/SKILL.md:344` | **「ミッションを閉じる」の後に `/ndf:issue-upkeep` を呼ぶ。** |
| `retrospective/SKILL.md:360` | `/ndf:issue-upkeep` — 蓄積した課題の棚卸し（この工程の最後に呼ぶ） |
| `development-workflow/SKILL.md` の「モードごとに起動する Skill」 | **`issue-upkeep` の行が無い**（`grep -n issue-upkeep` が 0 件） |
| `development-workflow/references/agent-layers.md` のフェーズの表 | 仕上げ = 配布（本番）/ リリース後テスト / 振り返り。**終わりの条件は「振り返りの記録を投稿した」**。`issue-upkeep` は現れない |

**supervisor から見ると、フェーズの終わりの条件を満たした後に、skill が次の作業を指示している状態**になる。どちらに従っても、もう一方の文書に反する。

### 観測（devbase v3.7.0、2026-09-23）

仕上げのフェーズの担当が、振り返りの記録を投稿した**後**に、開いている 21 件すべての棚卸しへ入った。

| 時刻（JST） | 出来事 |
| --- | --- |
| 08:18 | 振り返りを配布の Pull Request へ投稿（**フェーズの終わりの条件を満たした**） |
| 08:18〜08:38 | 取りこぼしの起票（6 件）に続けて、open 21 件の判定・本文の書き換え・ラベル付け・マイルストーンの操作 |
| 08:38 | オーケストレーター（conductor）が範囲外と判断して打ち切り |

打ち切りまでに外部へ書かれていたもののうち、**このミッションと関係のない課題への書き込みが 5 件**あった（他リポジトリの課題 4 件の本文の書き換えと追記、1 件の書き直し）。ほかにラベル 2 件、マイルストーンのクローズ 1 件。

**担当は指示に従っただけである。** `retrospective` を最後まで読めばこの動きになる。

### なぜ問題か

1. **フェーズの終わりの条件と、skill の指示が食い違う。** supervisor は「報告を返す」か「skill を最後まで通す」かを選ばされる
2. **費用に上限が無い。** 対象は「変更をまたいで溜まった課題そのもの」で、件数はリポジトリの状態で決まる。1 回の変更の工程としては、かかる費用が事前に読めない。今回の担当は 368k トークン / 277 回のツール実行を使い、その最後の 20 分がこの作業だった
3. **オーケストレーター（conductor）に止める材料が無い。** conductor は工程表とフェーズの表を基準にフェーズを組む。工程表に無い作業が始まっても、それが正しい手順なのか逸脱なのかを判定できない
4. **取り消しにくい書き込みが混ざる。** 課題の本文の書き換え・ラベル・マイルストーンは、ミッションの外の課題に対して行われる。レビューを通らない

### 修正レイヤー

**現象レイヤー**: `retrospective/SKILL.md` の「蓄積した課題を棚卸しする」の節。

**修正レイヤー**: **工程の境界を決めている `development-workflow`**。`issue-upkeep` を工程として扱うかどうかは、工程表とフェーズの表が唯一の基準である（`development-workflow/SKILL.md` の「判定基準を持つのはこの Skill だけである」）。`retrospective` の側だけを直すと、同じ食い違いが別の skill で再発する。

`retrospective` は既に、境界そのものは正しく述べている（`:345-346`）。

> 振り返りが拾うのは、この変更から出た取りこぼしである。**変更をまたいで溜まった課題そのもの**は対象にしていない。

**対象が違うと書きながら、同じ節で呼び出しを指示している**のが食い違いの本体である。

### 決めること

- `issue-upkeep` を工程表の行にするか。するなら**単位は何か**（ミッションではない。リポジトリ単位で、配布とは別の周期になるはず）
- 工程にしないなら、`retrospective` の「この工程の最後に呼ぶ」を落とし、**人が別に起動するもの**として書き直すか
- 3 層で通すとき、**skill がフェーズの終わりの条件の先を指示していたらどうするか**の規約を置くか（supervisor は報告を優先する、など）
- `issue-upkeep` に、**このミッションに関係する課題だけを対象にする**入口を設けるか（振り返りから呼ぶ経路に上限を与える）

書き換えると、新しい本文へ同じ呼び出しの指示が写される。

**上限の入口は `upkeep.py candidates --limit`（1 回に扱う候補の上限、`issue-upkeep/scripts/upkeep.py:607`）である。**
振り返りから呼ぶ経路に上限を与えるなら、ここを使う。

### 決定（2026-09-30 利用者）

backlog-refinement を **development-workflow の工程表の行にする**（人が別に起動するものにはしない）。範囲と費用の上限は工程の行として決める。

## 目的

- 棚卸し（`backlog-refinement`）を、開発工程の外で始まる作業から、工程表の 1 行として始まり・範囲と費用の上限を持って終わる工程にする
- 3 層（conductor → supervisor → worker）で通すとき、supervisor が「フェーズの終わりの条件」と「Skill の本文の続きの指示」のどちらに従うかを迷わない状態にする
- 1 回の棚卸しで扱う件数と書き込む先が事前に読め、conductor が逸脱を判定できる状態にする

## 前提

- 前提 1（利用者の決定 2026-09-30）: 棚卸しは `development-workflow` の工程表の行にする。人が別に起動するものにはしない
- 前提 2: 工程表の行は「スプリントの中で 1 回ずつ動く」という既存の規則に従い、棚卸しの単位はスプリントとする。リポジトリ単位の別周期の起動は設けない
- 前提 3: 工程表の行名は `棚卸し` とする（用語集にある語。行名は進捗記録の `stage` の値になり、課題の本文の「進行」の一覧に 1 行増える）
- 前提 4: 1 回の棚卸しで扱う候補の上限の既定値は 10 件とする。根拠は devbase v3.7.0 の観測（open 21 件で約 20 分 = 1 件あたり約 1 分）で、1 回を 10 分程度に収める。値は設計で実測を足して見直してよく、見直したら本文を書き換える
- 前提 5: 上限の入口は既存の `upkeep.py candidates --limit` を使う（#864 で入った）。上限を超えた候補は `metrics.deferred` に番号だけが載り、次のスプリントの棚卸しで `--add` で拾われる
- 前提 6: 棚卸しの判断の中身（区分・見積・順位の付け方）は変えない

## 対象範囲

含む:
- `development-workflow` の工程表（「モードごとに起動する Skill」）へ `棚卸し` の行を足す
- `references/agent-layers.md` のフェーズの表で、`棚卸し` をどれか 1 つのフェーズの「通す工程」に載せ、そのフェーズの終わりの条件を直す
- `retrospective` / `release-verification` / `release` の「蓄積した課題を棚卸しする」の節から、Skill の呼び出しの指示を外し、工程表の行を指す形にする
- `progress-tracking` の「スプリントを閉じる」の「`backlog-refinement` へ進む / 呼ばずに止まる」の記述を、工程表の次の工程を指す形にする（「スプリントを閉じる → 棚卸し」の順序の制約は 1 か所に残す）
- 棚卸しの工程から起動するときの上限（件数）を有限の値で渡し、既定値を 1 か所に置き、プロジェクトの設定（`.ndf/`）で変えられるようにする
- 3 層の規約: supervisor はフェーズの終わりの条件を満たしたら、Skill の本文が続きの作業を指示していても始めずにフェーズレポートを返す、を `agent-layers.md` に 1 か所置く
- `pace: fast` のまとめのプラン（`supervise.py new close`）で、振り返りのステップと棚卸しを分け、棚卸しを `棚卸し` の stage を持つ別のステップにする
- 工程名からフェーズを引く対応表（`lib/transcript_agents.py` の工程 → フェーズ）へ `棚卸し` を足す

含まない:
- 棚卸しの判断の規則（区分・ルートコーズ・見積・順位・マイルストーン）の変更
- `upkeep.py` の候補の集め方（5 つの経路・`--all` の基準）の変更
- 承認ゲートの数の変更（2 つのまま増やさない）
- リポジトリをまたぐ課題の一括の棚卸し（他のリポジトリの課題の書き換え）
- `retrospective` の取りこぼしの起票（振り返りの範囲として残す）
- #845 の子 issue が扱う Skill のスクリプト化そのもの
