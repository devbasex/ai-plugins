# #919: 結果を残さなかった担当の振り替え — 決定の記録

設計の本体は [issue-919-design.md](issue-919-design.md)、テスト設計は [issue-919-design-tests.md](issue-919-design-tests.md) にある。

## 決定の記録

### 決定 1: 規則の正本を 1 か所にするため、`assignment.py` に純粋な関数 `after_no_result` を置き、リトライ可否も移す

答え（`relaunch` / `reassign` / `abort`）と振り替え先は、記録と参加者と理由だけで決まる。副作用を持たない関数にすれば、全分岐を単体テストで見られる（要求のテスト戦略）。`NO_RELAUNCH_REASONS` と `relaunch_same_agent` は規則の一部で、理由の語彙ではないため、`monitor_outcome.py` から移す。`LaunchOutcome.relaunch_same_agent` も消す。起動結果が可否を持つと、規則を変えるときに触る場所が 2 つになる（AC5）。

`monitor_outcome.py` に規則を残す形は、AC5 の「理由の語彙と起動結果の読み書きだけ」に反する。Skill ごとに振り替えの関数を置く形は、同じ役割の関数を 2 つ持つことになる（#1142）。

根拠: Value 6（MVV 版 2）

### 決定 2: 外した担当を状態に残すため、追記だけの結果なしの記録（`no_results`）を持ち、外した担当・今のアカウント・起動し直し済みかは記録から導く

結果なしの 1 回ごとに 1 件を足す。何が外れたか・claude が今どのアカウントか・同じ担当を起動し直したかは、すべてこの記録から関数で導く（`excluded_runtimes` / `current_account` / 規則の順 1）。導いた値を別の欄に持つと、記録と欄の 2 か所が食い違いうる。2 つの Skill で記録の形を同じにし、規則が同じ入力を受ける。

`participants.available` から外した者を消す形は採らない。初期の解決の記録が失われ、再開で参加者を作り直したときに外した者が戻る。外した者だけの欄（`dropped`）を別に持つ形も採らない。記録から導ける値の二重持ちになる。

根拠: Value 6 / Value 7（MVV 版 2）

### 決定 3: 振り替え先の順を実装担当の決め方と同じにするため、残りの候補に `choose_implementer` の「ホスト → 先頭」を当てる

要求の未決 1 への答えである。実装担当は初めから「ホスト → 参加者の先頭」で決まっており、振り替え先も同じ順にすれば、選び方の規則は 1 つで済む。ホストは利用者が今使っている CLI で、認証が通っている見込みが最も高い。cross-review の席にも同じ順を当てる。席の輪番（`review_seats`）は次のラウンドから今の表のとおりに戻るため、1 ラウンドの中の振り替えだけが「ホスト → 先頭」になる。

`ALL_RUNTIMES` の順だけで選ぶ形は、実装担当で初めの決め方と食い違う。輪番や統計で選ぶ形は #760 の範囲である。

根拠: Value 6（MVV 版 2）

### 決定 4: 規則を純粋に保つため、アカウントの選び方は呼ぶ側が渡す関数（`pick_account`）にし、子の環境は起動のたびにアカウントの名前から組む

`claude_accounts.choose` は使用量を取りに行く（ネットワークと錠を使う）。規則の関数がそれを呼ぶと単体テストで差し替えられない。`resolve_participants` が認証確認を `probe` として受けるのと同じ形にする。`pick_account` は `assignee_env.py` が `claude_accounts.choose_env` を包んで作り、環境を用意できるアカウントの名前だけを返す。

環境は状態ファイルにも耐久の記録にも書かない。起動の耐久ステップの中で `assignee_env` が組み、ステップへ渡すのはアカウントの名前だけにする。環境は `CLAUDE_CONFIG_DIR` のパスを含み、打ち直しのたびに作り直せば足りる。`claude_accounts.py` は変えない（要求の「使うだけ」）。

根拠: C1 / Value 6（MVV 版 2）

### 決定 5: 終了コードを増やさないため、cross-review の振り替えは judge の 7 の経路に載せ、`REASSIGNED` の 1 行を足す

7 は「このラウンドで担当を起動する」出口で、起動し直しと振り替えは `drive.py` の動き（席を起動して監視し、もう一度 judge）が同じである。新しい終了コードを足すと、`drive.py` と状態の副命令を呼ぶ手順の文書の両方に出口が 1 つ増える。既存の `RELAUNCH_AGENTS` の 3 行は「同じ席で起動し直す席」の意味のまま残し、振り替えは別の行に出す（AC10）。

`drive.py` の「1 度だけ」の局所の旗は外し、7 の間は繰り返す。回数の上限は記録が持つ（I4・I5）。`drive.py` が別の上限を持つと、規則と駆動の 2 か所に回数の判断が散る。

根拠: Value 4 / Value 6（MVV 版 2）

### 決定 6: 振り替えた後の judge が新しい席だけを数えるよう、ラウンドの `reviewers` と `seats` を書き換え、元の席の結果なしの欄は残す

judge と反証（`critique-round.sh`）は `reviewers` の席の結果を読む。書き換えなければ、元の席の `NO_RESULT` が次の judge でも結果なしとして数えられる。元の席の欄（`rounds[].<元の席>`）は、振り替えの事実の元として残す。正は `no_results` で、`rounds[].reassigned` は報告と出力のための写しである。

ラウンドを閉じて次のラウンドとして振り替え先を起動する形は採らない。上限のラウンド数を 1 つ使い、利用上限のたびに収束までのラウンドが減る。

根拠: Value 2 / Value 7（MVV 版 2）

### 決定 7: 実装担当の振り替えを耐久の記録のどの単位で行うかについて、工程を流し直さず、同じ工程の中で起動を足す

要求の未決 2 への答えである。`drive.py` の `impl_phase` が監視の後に `reassign` を打ち、7 なら同じ工程の中で起動と監視をもう一度行う。それぞれが既存の耐久ステップ（`refactor_drive.call`）なので、打ち直しは記録した順に再生される。工程を流し直すと `start-phase` と工程の起点・締め切りの扱いを変えることになり、PR #1673 の手当て（`run --from refactor`）と同じ費用が残る。

`fix` と `final-fix` は同じ工程の中で起動し直さず、今の流れ（取り込み → 次の修正）のまま担当だけを替える。`final-fix` の試行の番号は修正ラウンドで、同じラウンドの中でもう一度起動すると、取り込みの「閉じ済みか」（`already_closed`）が 2 回目の結果を読まずに返す。

根拠: Value 4 / Value 6（MVV 版 2）

### 決定 8: 手順の上限で監視が止めた起動（`timeout` / `stalled`）を、cross-refactoring では振り替えの対象にしない

cross-refactoring の上限での打ち切りは設計どおりの起動結果で（cross-refactoring の決定 23）、取り込みが締め切りとして扱う。振り替えると、上限を使い切った工程を別の担当がもう一度上限まで回す。`reassign` は `STOPPED_REASONS` を「結果なしとして扱わない」として 0 を返す。cross-review の `timeout` / `stalled` は今のとおり規則へ渡す（同じ席で 1 度起動し直し、2 度目は振り替え）。

これは「結果なしと数えるか」の判断で、起動し直すか・誰へ振り替えるかの判断ではない（AC5 の範囲外）。

根拠: Value 1（MVV 版 2）

### 決定 9: 起動し直し済みかを担当の単位で数えるため、記録の照合の鍵を「工程・試行・席・アカウント」にする

claude のアカウントへの振り替えでは席の名前が変わらない。席だけで照合すると、別のアカウントで起動した担当が「起動し直し済み」と読まれ、1 度目の結果なしで外れる。アカウントを鍵に入れれば、新しいアカウントの担当も 1 度は起動し直せる。cross-review の既存の `rounds[].relaunched` は今の形のまま書き続ける（出力の行と既存の読み手のため）が、規則は記録だけを読む。

根拠: Value 6（MVV 版 2）

### 決定 10: 固定の組（`review_seats`）は、どちらかのランタイムが振り替えの元になった時点で、同じ実行の残りでは渡さない

前提 6 のとおりである。claude のアカウントへの振り替えも「振り替えの元になった」に含める。固定の組は利用者が選んだ 2 者の組で、片方が 1 度でも結果を残さなかった実行では、組の前提（その 2 者で毎ラウンド回る）が既に崩れている。判定は `pinned_in_force(pinned, log)` が記録から行う。

根拠: Value 6（MVV 版 2）

### 決定 11: `worker_steps.py` の担当の選択はこの課題で触らない

要求の未決 3 への答えである。`worker_steps.py` が選ぶのは supervise の worker の担当で、cross-review / cross-refactoring の担当とは起動の経路が違う。#760 の輪番・統計と同じ層で直すため、この課題では触らない。設計の中で #760 と食い違う点は見つからなかった（`after_no_result` は輪番を持たず、`review_seats` と `choose_implementer` の形を変えない）。

根拠: Value 6（MVV 版 2）

### 決定 12: 再開の規則「リファクタリング計画の後は実装担当を替えない」は残し、同じ実行の中の振り替えには当てない

再開で参加者を作り直したとき（`_recheck_implementer`）に止めるのは、見積りと項目の対応を読む者が食い違うためである。振り替えでは、計画・項目・締め切りはそのまま引き継がれ、記録に誰がいつ替わったかが残る（AC12）。再開の規則は、記録の外した担当を参加者から引いてから当てる。引かなければ、外した担当が再開で実装担当に戻る。

根拠: Value 7（MVV 版 2）

### 決定 13: 振り替えの後の工程の締め切りは延ばさない

振り替え先は、今の工程の残り時間と、計画で決めた項目の締め切りのまま続ける。締め切りは想定最大時間（`--budget-minutes`）から算術で出した値で、延ばすと実行の全体が予算を超える。締め切りに間に合わない項目は今のとおり `not_done` で見送られ、理由が報告に残る。

根拠: Value 3 / Value 4（MVV 版 2）

### 決定 14: 新しい副命令 `reassign` を置き、取り込み（`merge-*`）には振り替えを入れない

`plan` / `add-tests` / `implement` の取り込みは結果ファイルを読まず、git のコミットだけで判定する。振り替えを取り込みに入れると、取り込みが起動結果の読みと担当の書き換えの両方を持つ。`reassign` は「監視の後、取り込みの前」の 1 か所で、6 つの工程に同じ手順を当てる。`final-fix` の範囲の取り消しだけは、今のとおり `merge-final-fix` が持つ（決定 7）。

根拠: Value 6（MVV 版 2）

### 決定 15: クラス図は規則の関数と 2 つの値の型だけにする

触る型は `Assignee` と `NoResultDecision` の 2 つで、ほかは関数と状態ファイルの欄である。judge と `reassign` の中の関数は図に載せない（処理の流れが順序を持つ）。

根拠: 根拠なし（MVV 版 2）
