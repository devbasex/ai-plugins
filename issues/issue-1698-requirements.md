# #1698: supervise.py のステップで WebFetch・WebSearch が拒否され、設計が外部の文書（規約など）を読めないまま承認ゲート 1 へ進む

正は課題の本文（#1698）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 起きたこと

takemi-ohama/novel のスプリント post25（課題 #25、2026-10-03）で、`supervise.py` が起動した設計のステップ（`1-design-25.json` の design）が、投稿先の規約を原文で読めなかった。WebFetch と WebSearch が権限で拒否され、設計は規約の中身を「未確認」として実装へ先送りした。

実装のプランの `prompt` に「Bash の `curl -sL <URL>` で取得して読む（WebFetch はこの実行に無い）」とエントリポイントの URL を足したところ、実装のステップは原文を読んで条件の表を書けた。

このリポジトリのスプリント m1856（#1856）でも同じ形で止まった。設計のキューの 1 回目（2026-10-15 23:36〜23:58 JST、`1-design-1856.json` の design）で、worker は研究 5 件の一次資料を WebFetch / WebSearch が許可されず確かめられないとして「判断が要る」を返した。判断を待ったまま design のステップが 49 往復・$32.80 を使い、exit 1 で止まった（キュー全体の費用 $34.39 のほとんどがこの分）。supervisor が一次資料を確かめ直して再開し、承認ゲート 1 まで進んだ。

許可するツールは `plugins/ndf/scripts/supervise_lib/claude.py` の `WORK_TOOLS`（49 行）と `FULL_TOOLS`（66 行）が決め、どちらにも WebFetch・WebSearch が無い。worker が「判断が要る」を返したことは `plugins/ndf/scripts/supervise_lib/prompts.py` の `REPORT_NOT_DONE`（45 行）で拾い、`plugins/ndf/scripts/supervise_lib/worker_steps.py` の 151 行でステップを失敗にするが、同じ判断待ちが続いたときにその場で打ち切る扱いは無い。

## 困ること

- 外部の文書（規約・API の仕様・ライブラリの文書）を読む必要のある設計が、読めないまま承認ゲート 1 へ進む。設計の決定が後の工程へずれる

## 目的

- `supervise.py` が回す設計・要求・実装のステップが、外部の文書（規約・API の仕様・ライブラリの文書・一次情報の記事）を原文で読めるようにする。読めなかったときは、未確認のまま承認ゲート 1 へ進まずに止まる
- worker が「判断が要る」と報告したステップを、その場で打ち切って conductor へ戻す。同じ続行を繰り返して費用と往復を使わない（m1856 では 49 往復・$32.80）
- 同じ手当て（conductor がプランの外で一次情報を調べる）が m1856・s2089 と 2 度以上起きたので、NDF の雛形の側で直す（プロジェクト MVV の Value 4）

## 前提

- 前提 1: 外部の文書を読む手段は、ステップの許可の一覧へ WebFetch と WebSearch を足すことで与える。プランの prompt の既定文へ curl の指示を足す案（S2）は採らない。理由: worker は既に Bash（curl を含む）を許可されており、WebFetch・WebSearch を足しても外へ読みに行ける範囲は広がらない。足さないと、Skill の本文が WebFetch を前提に書かれている箇所で拒否され、プランごとの手当てが残る
- 前提 2: 許可を足すのは `supervise.py` が claude -p を直接起動するステップ（`full` の work と、最小構成の work）に限る。Tool を持たない呼び出し（judge・遅れの判定・PR の本文）は Tool 無しのまま変えない
- 前提 3: 「判断が要る」で打ち切ったステップは、judge を通さずにステップの失敗として計画を止める（今の `on_fail` の無い work のステップと同じ行き先）。judge が判断を決めることはしない（共通原則: AI が取れる行動は「進める / 止めて人へ戻す」。判断を求めた worker の問いを別の AI が代わりに答えない）
- 前提 4: 打ち切りの対象は、作業の報告が「結果: 判断が要る」か「結果: できなかった」で終わった応答とする。どちらも worker が報告を書いて意図して止まった状態で、同じ会話へ「続けて」を送る起こし直し（報告が無いまま終わったときのためのもの）の対象ではない
- 前提 5: claude -p 以外のランタイム（codex・kiro・agy の `runtime` を指定した work）の Tool の許可は、この課題で扱わない。各ランタイムの許可の形が違い、拒否の事例は claude -p だけで起きている

## 対象範囲

含む:
- `supervise.py` が claude -p を起動する work のステップ（`full` と最小構成）の許可の一覧へ WebFetch・WebSearch を足す
- 作業の報告が「判断が要る」「できなかった」のとき、`full` のステップの起こし直し（`RESUME_PROMPT` の送信）をしない
- 外部の文書を取得できなかったときに、worker が報告へ取得できなかった URL と理由を書き、結果を「完了」にしない取り決め（置き場は設計が決める。`FULL_SYSTEM` などの起動指示か、`design` / `requirements-design` の Skill の本文）

含まない:
- claude -p 以外のランタイム（codex・kiro・agy）の Tool の許可（前提 5）
- judge の規則・遅れの判定（`slow.py`）の変更
- conductor（supervisor）が止まった計画をどう再開するかの手順
- WebFetch の取得先の制限（許可するドメインの一覧など）。必要になれば別の課題にする
- takemi-ohama/novel の `docs/process/08-development.md` の取り決めの撤去（そのリポジトリの運用。この課題の配布の後に、そちらで外す）

## 受け入れ条件

外部の文書を読む:
- [ ] 1. `full` の work のステップを起動する claude -p の引数の `--allowed-tools` に、`WebFetch` と `WebSearch` が含まれる
- [ ] 2. 最小構成の work のステップを起動する claude -p の引数の `--tools` と `--allowed-tools` の両方に、`WebFetch` と `WebSearch` が含まれる（`serena` を付けたステップでも含まれる）
- [ ] 3. judge・遅れの判定・PR の本文を書く呼び出しの引数は、変更の前と同じ `--tools ""` のまま（Tool が増えない）
- [ ] 4. 外部の文書を取得できなかった worker の作業の報告に、取得できなかった URL（または検索の語）と失敗の理由（拒否・HTTP の状態・ネットワークの誤り）が書かれる
- [ ] 5. 外部の文書を取得できなかった設計のステップの報告の結果は「完了」にならず、ステップは失敗になり、設計 PR（承認ゲート 1）へ進まない

「判断が要る」の打ち切り:
- [ ] 6. `full` のステップの最初の応答の作業の報告が「結果: 判断が要る」のとき、`--resume` の起動が 0 回で、ステップは失敗（exit 1）になる
- [ ] 7. `full` のステップの最初の応答の作業の報告が「結果: できなかった」のとき、`--resume` の起動が 0 回で、ステップは失敗（exit 1）になる
- [ ] 8. `full` のステップで作業の報告が無いまま応答が終わったときは、今と同じく 3 回まで起こし直す（退行しない）
- [ ] 9. 6・7 で失敗したステップに `on_fail` が無いとき、計画の結果は「止まった」になり、止まったステップの記録（状態の `text`）に worker の作業の報告がそのまま残る
- [ ] 10. 起こし直しの途中の応答が「判断が要る」「できなかった」を報告したときも、その時点で起こし直しを止める（残りの回数を使わない）
