# Factory のオーガナイザーの設計: 決定の記録（#2439）

設計文書 [issue-2439-design.md](issue-2439-design.md) の決定を分けたファイル。要求の「起票者の推定」（S1〜S11）と「未決」（1〜4）への答えを含む。

## 決定の記録

### 決定 1: 実行基盤の違う 2 つの実装を互いに独立して変えられるよう、Factory のオーガナイザーを `factory/` に置き、#2436 の契約だけに依る

1 台の中のオーガナイザーは SQLite（DBOS）の耐久ワークフローで、実行ジョブの間をまたげない。Factory の実行はジョブごとに別のコンテナと clone を持ち、共有できるのは DynamoDB と GitHub だけである。そのため同じ層の別の実装として `factory/` に置く。共有するのは、依頼と答えの形（#2436 の `parallel-request.json`）と配布の規則（#2436 の決定 13〜15）だけである。2 つは排他で、Factory の実行ジョブの中では 1 台の中のオーガナイザーを起動しない（I68。#2436 が `NDF_FACTORY_RUN` で断る）。

Factory のオーガナイザーの仕事は、1 台の中のオーガナイザーの仕事すべてに Factory 固有の仕事（ランナーの制御・枠・状態の置き場）を足したものである。固有の仕事とレーンの起動・停止は、既存の実行の制御とループの制御がすでに持つ。そのため作り直さずに役割の一部として数える。足すのは、足りない「配布を 1 本にまとめる」「問いを集める」「共有の作業を渡す」だけで、配布のまとめと配布の実行として足す。

#2436 の設計へ組み込む案は採らない。`plugins/` から `factory/` を参照できない（`scripts/check-service-boundary.py`）。#2436 の設計はすでに 6 ファイル 1,445 行ある。

根拠: Value 5 / Value 6（MVV 版 4）

### 決定 2: 新しい常駐とインフラを足さずに済ませるため、オーガナイザーの進行を実行の表の DynamoDB の行で持ち、API の handler と見回りが進める

要求の未決 3 への答えである。配布のまとめの 1 手は「根を読み、条件つきで書き、必要なら実行を起こす」で、待ちは人の答えか次の事象である。今の実行の制御（`startNextLap`・`finalize`）が同じ形で動いている。同じ表に置けば、まとめた配布と配布の実行を 1 回のトランザクションで書ける（I57）。足すのは疎な GSI 1 つだけである。費用は行の読み書きに比例し、依頼の無いリポジトリには掛からない。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| DynamoDB の行（実行の表）と既存の handler・見回り | **採る** | 部品が既にあり、実行の行と同じトランザクションに入る。常駐が無い |
| AWS Step Functions の Standard ワークフロー（人の答えをタスクの token で待つ） | 採らない | ステートマシン・IAM・起動の経路を private リポジトリに足す。実行の行と同じトランザクションに入らず、ワークフローと表の二重の記録の整合が要る |
| 配布のまとめ用の別の表 | 採らない | 配布の実行との原子的な作成ができない |

根拠: Value 4 / Value 10 / Mission（MVV 版 4）

### 決定 3: 配布の実行を 2 本作らないため、配布の実行をまとめた配布と同じトランザクションで作り、範囲のどの実行でもない専用の実行にする

要求の S5 への答えである。範囲の実行のどれかに配布を流させると、その実行のループの周回と配布が同じジョブに混ざる。ループの予算と打ち切りの時間が配布に掛かる。配布の実行を専用にすれば、範囲の実行は答えを待たずに次の周回へ進める（AC 7）。作成をまとめた配布と別のトランザクションにすると、間で止まったときに見回りが 2 本目を起こす。依頼が 1 件でも同じ経路を通す（S8）。1 本のときだけ今の経路に残すと、1 本から 2 本へ増えた瞬間の扱いが要るためである。

根拠: Value 6 / Value 2（MVV 版 4）

### 決定 4: 承認済みの開発の配布を枠で止めないため、配布の実行は実行の枠を持たず使える量の判定にかけず、費用は登録したアカウントの利用量へ数える

要求の未決 1 への答えで、S11 を採る。配布の実行は範囲の実行がすでに入った枠の続きの仕事である。枠を持たせると、ループが枠を埋めたリポジトリで配布が組めず、`develop` の変更が `main` へ届かない。同時の数はリポジトリに 1 本まで（I56・I57）で、枠が無くても増えない。トークンと費用は今の `usage.recorded` で配布の実行の識別子に付く。アカウントの利用量と `managed` の月のトークンに数える。範囲の実行の数で割る案は、割り方と表示の規則が増えるため採らない。

承認ゲート 1 でこの数え方を利用者が確かめる（要求の未決 1 の「誰が決めるか」）。

根拠: Value 2 / Value 10（MVV 版 4）

### 決定 5: NDF を Factory に依らずに外のオーガナイザーへつなぐため、切り替え口をこの課題で作り、置き場のファイルの契約にする

要求の未決 2 への答えで、S7 を採る。#2436 は 1 台の中に閉じ、依頼をメッセージで送る。Factory のランナーはメッセージを受けられず、NDF の書くファイルを読んで翻訳する形（腐敗防止層）がすでにある。そのため、環境変数 `NDF_ORGANIZER_DIR` があるときだけ、依頼と答えを置き場のファイルで受け渡す。切り替え口の唯一の使い手は Factory なので、この課題で作る。#2436 の契約がマージされてから実装する（前提 1）。

環境変数の名前を `NDF_FACTORY_RUN` 1 つにまとめる案は採らない。`plugins/` の切り替え口に Factory を名指しせず、手元の別のまとめ役からも同じ切り替え口を使えるようにするためである。

根拠: Value 5（MVV 版 4）

### 決定 6: Factory の今の承認の流れを保つため、置き場で依頼にするのは本番の配布だけにし、承認ゲート 1 と問いは一覧への並べ方だけをまとめる

要求の S9 を採る。Factory の実行は承認の依頼でジョブを終えて費用を止め、答えで再開する。承認ゲート 1 と問いを依頼にしてレーンを進め続けると（#2436 の I17）、待つ間もジョブが動く。今の形と違う費用の掛かり方になる。設計 Pull Request は互いに独立で、まとめて 1 つの承認にできる単位も無い。そのため 3 種類の承認の依頼とループの人の判断待ちを、リポジトリごとの 1 つの一覧に並べるだけにする（AC 9）。

根拠: Value 2（MVV 版 4）

### 決定 7: 承認したコミット以外を出さないため、答えの時点の `develop` の比べを API の側で GitHub の口から 1 回だけ行う

要求の S4 を採る（#2436 の決定 14 と同じ規則）。比べる時点は答えが保存された直後で、配布の実行のジョブはまだ起きていない。API で比べれば、出し直し（`represent`）か確定（`confirm:1`）かを再開の指示に載せられる。ジョブを 1 回起こして比べる費用が要らない。出し直しへの答えでは比べないため、出し直しは連鎖しない（I60）。

根拠: Value 4 / Value 10（MVV 版 4）

### 決定 8: 2 つのオーガナイザーが互いの記録を読めなくても衝突させないため、GitHub の上の開いている本番の Pull Request と古い版の実行で待つ

要求の S6 を採る。両方が読めるのは GitHub の状態だけである。待つ相手は `main` 宛の Pull Request で、head が `release/v` で始まるものと、head が `develop` のものの両方である。#2436 の配布の規則より前の NDF の版は head が `develop` の Pull Request を作るためである。同じ理由で、リポジトリに古い版の実行がある間（`legacyCount` が 1 以上）も組まない。その実行は自分で本番を配布する。禁止の案は、利用者の手元の作業を Factory が止めるため採らない。

根拠: Value 6 / C4（MVV 版 4）

### 決定 9: ループの周回と手動の実行の今の待ち方を変えないため、依頼の後のループの実行は `done`、手動の実行は理由つきの `awaiting_approval` にする

ループは周回を配布待ちで締めると次の周回を起こせる（#2436 のレーンのループ）。手動の実行は今もゲート 2 の待ちで枠を持ったまま `awaiting_approval` になっている。同じ状態に理由（`release_requested`）を足せば、状態の遷移を増やさずに済む。答えは `requestResume` で届け、NDF は残りの工程を流す。新しい状態 `awaiting_release` を足す案は、状態の遷移の表・一覧の絞り込み・ループの写し方の 3 つを変えるため採らない。

根拠: Value 2 / Value 6（MVV 版 4）

### 決定 10: 承認の依頼の持ち主を 1 つに保つため、一覧は既存の承認の依頼と人の判断待ちを読んで並べ、新しい保存を作らない

承認の依頼の保存と答えの経路は #2173 が持つ（前提 3）。配布のまとめがコピーを持つと、答えたかどうかが 2 か所に分かれる。一覧は、同じリポジトリの `awaiting_approval` の実行から #2173 の読み出しで承認の依頼を引き、ループの行から人の判断待ちを引いて並べる。答えは今の経路（#2173 の答え → `requestResume`、ループの答えの経路）で持ち主へ届く。

根拠: Value 7 / Value 6（MVV 版 4）

### 決定 11: `main` へのマージの後の配布を差し戻さないため、配布の実行は失敗しても終わりの状態にせず、止まった配布を「続きから流す」か「差し戻す」で解く

配布の実行を `failed` で終えると、続きを流すには別の実行を作るしかない。1 つのまとめた配布に 1 本の守り（I57）が崩れる。理由 `release_stalled` の `awaiting_approval` で止めれば、今の再開の書き込みで続けられる。`main` のマージの後は選択肢を「続きから流す」だけにし（AC 13）、マージを `release.progress` と GitHub の両方から照らす。ジョブが段を書く前に落ちても、GitHub でマージ済みと分かるためである。解く操作は承認ゲートではなく失敗の扱いで、承認の工程を足さない。

根拠: Value 1 / C4（MVV 版 4）

### 決定 12: 語の衝突を読み手の側で解くため、「手元のマシン」と「料金プラン」へ改め、識別子は変えない

要求の未決 4 への答えで、S10 を採る。マシン単位の受け手は、利用者が自分の環境に登録するマシンそのものとして読めればよく、要求と #2189 がすでに「手元のマシン」と書いている。「手元の受け手」は業界で流通していない語である。「エージェント」「ホスト」はこのリポジトリの別の意味（AI のエージェント、Claude Code などのホスト）と重なる。アカウントの契約の種類は、料金の契約であることを語に含めて `ndf-workflow` の「プラン」（`plan.json`）と分ける。識別子（`runnerId`・`plan`）を変えると、API の互換と保存済みのデータの移行が要る。衝突しているのは説明文の語だけである。

根拠: Value 8（MVV 版 4）
