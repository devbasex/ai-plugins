# 工程の進行表: 工程の定義と進行表で、スクリプトが次の工程を決めて終了の印を付ける（#3092）

## 目的

- **今どうなっているか**: 工程の並びは `development-workflow` の工程表にある。しかしスプリントの目録（`sprint.json`）はまとめの工程を持たず、conductor が手順書を読んでまとめ・再開・課題の持ち越しを組む。工程の有効・無効はコードの定数と手順書に散り、計画の状態は 3 か所に分かれる
- **誰に効くか**: 並列の計画とスプリントを流す利用者と、その conductor・オーガナイザー
- **変えると何が成り立つか**: モードごとの全工程を登録済みの工程の定義から進行表の行として組み、スクリプトが進行表だけを読んで次の工程を流し、出力を入出力規約で検査して終了の印を付ける。計画とレーンも進行表で持ち、振り返りの後の組み換えでスプリントの結果を計画へ戻す

## 適用範囲

- **働く範囲**: NDF を使うすべてのリポジトリ。進行表の DB はリポジトリごとに 1 つの SQLite を既定にし、Factory は PostgreSQL の URL を渡す。SQLite はメインのチェックアウトに置き、どの worktree からも同じファイルに解決する（決定 2）
- **プロジェクトごとに違うもの**: 工程の有効・無効の既定はプロジェクトの宣言（`.ndf/project.json` の `workflow`）で、スプリントごとの上書きは引数で受ける。DB の置き場は環境変数（`NDF_PROGRESS_DB`）で受ける
- **当たるモード**: 5 つすべて（`light`・`operation`・`legacy-refactor`・`standard`・`documentation`）。並列の計画の外の単独の作業も同じ進行表で流す

## ドメインモデル

### コンテキスト

| コンテキスト | 何の語が 1 つの意味に決まるか |
| --- | --- |
| NDF の開発ワークフロー（`ndf-workflow`） | 工程・アクティビティ・進行表・終了の印・組み換え・レーン・計画 |
| Neural Development Factory（`ndf-factory`） | 進行表の画面と、PostgreSQL の進行表の DB |

関係は**公開された言語**とする。進行表の DB のスキーマと進行の事象の形を、文書化した共通の形式にする。2 つの形は [issue-3092-design-runtime.md](issue-3092-design-runtime.md) の「データ構造」にある。Factory はこれを読むだけで、書き込みは NDF の進行表のスクリプトを通す。

| 集約 | 持ち主（書き換えてよいもの） | 根 | エンティティ | 値オブジェクト |
| --- | --- | --- | --- | --- |
| 工程の定義 | リポジトリの変更（CI の定義の検査を通ったものだけ）。実行の中では読むだけ | モードの定義 | 工程の定義・アクティビティの定義 | 入出力規約の参照・順序の属性（種類と範囲）・有効の条件 |

### 不変条件

| # | 集約 | 条件 | 破れたときの扱い |
| --- | --- | --- | --- |
| I1 | スプリントの進行表 | 同じリポジトリの同じ名前のスプリントの進行表は 1 つ。計画の中か外かを問わず、中止した進行表の名前も使えない | 作成を断り、今の進行表の ID を返す（決定 15） |
| I2 | すべての進行表 | 進行の事象は追記だけで、表ごとの番号は 1 ずつ増える。更新と削除をしない | 番号のぶつかりは追記を断り、読み直して判定し直す |
| I3 | スプリントの進行表 | 工程とアクティビティの行が終了になるのは、出力が出力の規約に合ったときだけ | 終了の印を付けず「失敗」にし、conductor へ返す |
| I4 | スプリントの進行表 | 実行中の行は無効にできない | 操作を断る |
| I5 | スプリントの進行表 | モードは上げる方向だけ変わる | 下げる操作を断る（新しい進行表を作る） |
| I6 | すべての進行表 | 事象の種類ごとに書ける役が決まっている（[issue-3092-design-runtime.md](issue-3092-design-runtime.md) の「事象の種類と書き手の表」） | 追記を断る |
| I7 | 工程の定義 | 工程とアクティビティのすべてが入力と出力の規約を参照し、参照先がある | 登録（CI と実行の前の検査）を断る |
| I8a | 工程の定義 | 取り込み前の検査（レビューとテストのアクティビティ）は、同じ範囲の本番へ出すアクティビティより前にある | 本番へ出すアクティビティより後ろに同じ範囲のレビューかテストがあれば、登録を断る |
| I8b | 工程の定義 | リリースした版を確かめるアクティビティ（リリース後テスト）は、モードの工程の並びで本番へ出すアクティビティより後ろにある | 本番へ出すアクティビティより前にあるか、モードに本番へ出すアクティビティが無ければ、登録を断る |
| I9 | 工程の定義 | レビューとテストのアクティビティの範囲は差分（スプリントの差分か課題の差分）である。リリースした版を確かめるアクティビティの範囲はリリースした版である | 登録を断る |
| I10 | 工程の定義 | 一度通したステップを同じ範囲で 2 度置かない。レビューは範囲と対象（コード・文書・設計）の組で、テストは範囲で数える（決定 5） | 登録を断る。やり直しは conductor の操作の事象で表す |
| I11 | 工程の定義 | モードの工程の並びが `development-workflow` の工程表のそのモードの列（`—` でない行）と一致する | CI の検査が落とす |
| I12a | レーンの進行表 | 実行中と完了の行の入力（課題の一覧）と位置を書き換えず、取り消さない | 書き込みを断り、オーガナイザーへの依頼にする |
| I12b | レーンの進行表 | 行の状態を進めるのは `row_started`（未着手から実行中）・`row_cancelled`（未着手から中止）・行を終える関数（`row_ended`。実行中から完了か中止）だけである | 書き込みを断る |
| I13 | 計画の進行表 | 同時に動き得る順番表の行の組（別のレーンの行どうしで、どちらからどちらへも `after` とレーンの中の並びをたどる順序の鎖が無い組）の間で、触る場所が重ならない。この鎖で前後が決まる行の間は重なってよい（例: レーン B の B1 が `after: A1` なら A1 と B1 は重なってよいが、A2 と B1 は同時に動き得るので重なれない） | 作成と変更を断る |
| I14 | スプリントの進行表 | 動いている実行は 1 つ。排他は進行表の DB の側で取り、どの端末やコンテナから `progress.py next` を打っても効く（決定 20） | 2 つ目の起動を断る |
| I15 | スプリントの進行表 | 定義のスナップショットは改訂ごとに追記し、書き換えない | 書き換えを断る（決定 16） |
| I16 | 計画の進行表 | 完了は、全レーンの行が完了か中止で、答えていない依頼が無いときだけ | 完了にしない |
| I17 | スプリントの進行表 | 手で終了にする出力は出力の規約に合う | 操作を断る |
| I18 | レーンの進行表 | 別のレーンの `after` が指す行は消さず、後ろへ回さない | 書き込みを断り、オーガナイザーへの依頼にする |
| I19 | 計画の進行表 | レーンの間で課題が重ならない | 作成と変更を断る |
| I20 | 計画の進行表 | レーンの数が上限を超えない | 作成と変更を断る |
| I21 | 計画の進行表 | `after` が輪にならない | 作成と変更を断る |
| I22 | スプリントの進行表 | 範囲とモードの変更は改訂を 1 つ上げ、影響する工程から新しい実行で流す | 動いている実行がある間の改訂を断る（決定 16） |
| I23 | スプリントの進行表 | 行の状態は今の改訂の事象だけから引く | 前の改訂の事象を畳み込みに使わず、履歴にだけ出す |

## 決定の記録

### 決定 1: 工程の状態を手で終了にした分や変更の履歴まで残すため、状態の正本を NDF の進行の事象にし、DBOS の実行の記録はアクティビティの再開にだけ使う

DBOS の実行の記録は、実行したステップの出力だけを持つ。手で終了にした工程・始める前に無効にした工程・conductor の変更の理由・計画とレーンの行は表せない。ステップの番号は実行ごとに振られ、やり直しで実行が替わると工程との対応が切れる。このため、工程の状態は進行表の DB の進行の事象（追記だけ）に置き、今の状態は最新の事象から畳み込む。DBOS の記録は、落ちた後にアクティビティを流し直さないための実行の控えとして使う。2 つは別の事実を持つ（業務の状態と、実行の控え）。

状態を DBOS の実行の記録だけから導く形は、上の 4 つを表せないため採らない。行の状態を上書きする表は、履歴を失うため採らない（非機能の「変更を追記だけで残す」）。

- 作り方: ライブラリやサービスを使う・自前で作る
- 比べた候補: LIB1 / PRD1 / PRD3

根拠: Value 8 / Value 3（MVV 版 7）

### 決定 2: ローカルと Factory を URL の差し替えだけで切り替えるため、DBOS の記録と進行表を 1 つの DB に置き、SQLAlchemy Core で読み書きする

URL は環境変数 `NDF_PROGRESS_DB` で受ける。無ければ、チェックアウトの状態の置き場 `lib/state_home.py` の `checkout_home()`（`<git の共通ディレクトリ>/ndf/state`） の下の SQLite のファイル `progress/ndf-progress.sqlite` を使う。git の共通ディレクトリはどの worktree から引いても同じであり、コミットされる設定の置き場 `.ndf/` の外にあるため、DB のファイルが利用者のリポジトリの変更として現れない。このため、オーガナイザーとすべてのレーンの worktree が同じファイルに解決し、計画・レーン・スプリントの進行表が 1 つの DB でつながる（決定 17 の 1 つのトランザクションの前提）。リポジトリをまたぐ計画では、耐久ワークフローがレーンを起こすとき（`parallel.launch`）に、自分が使う URL を `NDF_PROGRESS_DB` でレーンへ渡す。worktree ごとの置き場は、3 つの階層の進行表が別の DB に分かれるため採らない。DBOS は同じ URL を `system_database_url` に受け、実行者の ID を進行表の ID にして回復を進行表ごとに分ける。表は 3 つ（進行表・定義の改訂・進行の事象。決定 16）と表の版の 1 行で、版を上げるときは起動の時に足りない列と表を足す。SQLAlchemy は DBOS の依存として手元にあり、新しい依存にならない。DBOS はリポジトリが固定している 3.1.0（`pyproject.toml`・`plugins/ndf/pyproject.toml` の `durable` のグループと `uv.lock`）のまま使う。この設計が使う機能は、手元の 3.1.0 にあることを確かめた（2026-11-13）。使う機能は `system_database_url`・`executor_id`・`DBOS.send`・`DBOS.recv`・`DBOS.cancel_workflow`・`DBOSClient` である。版を上げる要は無く、上げない。上げると #1142 の耐久ワークフロー（並列の計画・supervise・cross-review・投稿キュー）すべてに効き、この課題の範囲を超えるため、上げるなら別の課題にする。SQLite のファイルへの書き込みが詰まるときの代わりの形は決定 18 にある。

DBOS の記録と進行表を別の DB に置く形は、接続先が 2 つになり Factory の設定が増えるため採らない。移行のツール（LIB5）は、新しく置く 2 つの表に比べて重いため採らない。

- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB1 / LIB4 / LIB5

根拠: Value 4 / Value 12（MVV 版 7）

### 決定 3: 定義の書式を標準どおりに検査するため、Serverless Workflow 1.0.3 の公式スキーマを手元に置き、`jsonschema` で検査する

Python の SDK は仕様 0.8 にしか対応せず、2022-04 から出ていない。公式スキーマ（STD1）を JSON に直して `plugins/ndf/contracts/workflow/serverless-workflow-1.0.3.schema.json` へ置く。取得元の URL と sha256 は、文書の `$comment` に書く。形は `jsonschema` の draft 2020-12 の検査器で確かめる。1.1.0 は出て 1 日のため採らず、上げるときはスキーマの差し替えと検査の通過で判断する。依存は `jsonschema` 1 つを足す（グループ `workflow`）。

SDK を使う形は 1.0 の書式を読めないため採らない。書式を自作する形は、利用者の決定（標準を借りる）に反するため採らない。

- 作り方: 標準に倣う・ライブラリやサービスを使う
- 比べた候補: STD1 / STD2 / LIB2 / LIB3

根拠: Value 12 / Value 11（MVV 版 7）

### 決定 4: モードの間で同じ工程を写さないため、工程を 1 つの文書にし、モードの文書は工程の文書を順に呼ぶだけにする

工程の文書（`stages/<工程の ID>.json`）が、アクティビティの並びと入出力規約を持つ。モードの文書（`modes/<モード>.json`）は、`run.workflow` で工程の文書を名前と版で呼ぶ行を並べる。同じ工程を 5 つのモードで持っても、アクティビティの並びは 1 か所にある。工程の差がモードで要るときは、別の工程の文書を作る（例: `operation` の実装）。

モードごとの文書に全アクティビティを書く形は、同じ並びを最大 5 回写すため採らない。

根拠: Value 11（MVV 版 7）

### 決定 5: 式の評価器を持たずに済ませるため、NDF に固有の条件と属性は `metadata.ndf` に置き、定義の要素の `if` を使わない

`metadata.ndf` には、次の 3 つを閉じた語彙で書く。

| 書くもの | 例 |
| --- | --- |
| 有効の条件 | 差分にコードがある・CI テストの宣言がある・振り返りが有効、など |
| アクティビティの種類 | レビュー・テスト・本番へ出す・記録 |
| 範囲 | スプリントの差分・ベースブランチ |
| レビューの対象 | コード・文書・設計 |

語彙は定義の検査が持つ一覧に限り、知らない語は登録で断る。レビューの対象を持つのは、I10 を範囲と対象の組で判定するためである。`standard` のコードレビュー（コード）とドキュメントレビュー（文書）は、どちらも範囲がスプリントの差分でも、対象が違うため断られない。最後の検査のように、コードレビューと同じ範囲でコードをもう一度レビューする形を断る。レビューを範囲だけで判定する形は、正しい定義（コードレビューとドキュメントレビューを持つ `standard`・`documentation`）まで落とすため採らない。

テスト（`kind: test`）も同じ決まりに入れ、同じ範囲の 2 つ目を断る。テストには対象の区別が無いため、範囲だけで数える。`kind: test` は、取り込み前に差分を確かめるテストのアクティビティ（完了判定の全体テストなど）に付ける。実装やリファクタリングのプランが自分の中で流すテスト（振る舞いを固定するテストの実行など）は、その工程の作業（`kind: work`）の一部であって `kind: test` を付けない。リファクタリングと完了判定でテストを 2 度流しても、前者は作業の中の確かめ、後者が差分のテストであり、決まりに当たらない。要求の決まり（「一度通したステップを同じ範囲で 2 度通さない」）はレビューに限らないため、テストを外す形は受け入れ条件 12 を狭めることになり採らない。使う要素は `do`・`run`（工程の呼び出し）・`call`（アクティビティ）・`listen`（承認ゲートの待ち）・`for`（`fast` の課題ごと）の 5 つに限る。

`if` は実行時の式（既定は jq）を求め、評価器の依存と、条件の誤りが実行の時に初めて分かる経路を足すため採らない。

根拠: Value 3 / Value 2（MVV 版 7）

### 決定 6: 再開とやり直しを `--from` の手組みから外すため、やり直しは新しい実行を始め、終わった行を事象から読んで飛ばす

進行表のワークフローは、工程を始める前に進行の事象からその行の状態を読み（読む処理は DBOS のステップにして実行の控えに残す）、終了か無効なら飛ばす。

やり直し（`retry`）は失敗の行だけに当たり、その行を未着手へ戻す事象を書くだけである。工程が失敗すると、進行表のワークフローは `failed` を書いて実行を終える（DBOS の実行は終わった状態になる）。このため、やり直しの時点で取り消す実行は無い。次の `progress.py next` が新しい実行を始める。動いている実行（`progress.py next` のプロセスが持つ実行の鍵の排他。I14・決定 20）がある間のやり直しは断る。

実行を取り消すのは、範囲とモードの変更（`scope`）と中止（`cancel`）だけである。どちらも、待ちに入って途中のまま残った実行（プロセスは無い）を `DBOS.cancel_workflow` で取り消す。範囲とモードの変更は、改訂を上げた定義のスナップショットで新しい実行を始める（決定 16）。プロセスが動いている間は、どちらも断る。

DBOS の `fork_workflow` で指定したステップから流し直す形は、ステップの番号を工程へ写す対応が要り、定義を変えた後に使えないため採らない。

根拠: Value 7 / Value 3（MVV 版 7）

### 決定 7: 常駐のサーバーを置かずに承認待ちを挟むため、進行表のワークフローは conductor が前景で打つ `progress.py next` の中で動かし、待ちに入ったら抜ける

`progress.py next` は DBOS を起動し、途中の実行を回復して、承認ゲートかリリースの結果の待ちに入るか、失敗するか、完了するまで流す。待ちに入ったら耐久の記録を途中のまま残して `gate` で返す。答えは `progress.py answer` が DB へ送るため、プロセスが無い間も失われない。conductor は答えの後に同じ `progress.py next` を打つ。

この流れが頼る DBOS の挙動は、手元の 3.1.0 で次の 4 つを確かめた（2026-11-13）。コマンドと出力は [issue-3092-design-dbos-behavior.md](issue-3092-design-dbos-behavior.md) にある。

| 確かめたこと | 結果 |
| --- | --- |
| `recv` の待ちの途中でプロセスを抜けた実行 | `PENDING` のまま残る |
| プロセスが無い実行へ別のプロセスから送った答え（`DBOSClient.send`） | 実行は `PENDING` のまま、答えが DB に残る |
| 同じ `executor_id` と同じアプリの版で起動した別のプロセス | 起動の回復で実行を拾い、終わったステップを流し直さずに `recv` から続け、送った答えを受け取って `SUCCESS` で終わる |
| `executor_id` かアプリの版が違うプロセス | 実行を拾わず、`PENDING` のまま残る（決定 21 の前提） |

`recv` の待ちの上限は、DBOS が開始の時刻からの期限として実行の控えに残す（`_sys_db.py` の `recv_setup` が `record_sleep` を呼ぶ）。期限を過ぎた後に回復すると、答えが無くても `None` で戻る。このため上限は承認待ちの期間より長い 30 日にし、`None` が戻ったら工程を失敗にする。待ちに入ったことは、アクティビティがプロセスの中の印で主のスレッドへ知らせる。主のスレッドは `gate` の結果を書いてからプロセスを終える。抜け方は実測で確かめた `os._exit` に揃え、ほかの抜け方での実行の状態は確かめていない。

並列の計画の耐久ワークフローは、この決定で新しく置く常駐ではない。今と同じく、オーガナイザーが `parallel.py start` で切り離して起動し、計画が終わると抜ける。この起動と終わり方は [docs/specifications/ndf-parallel-organizer.md](../docs/specifications/ndf-parallel-organizer.md) にある。計画の外の単独のスプリントには、耐久ワークフローが無い。変わるのは、耐久ワークフローが 1 周ごと（`NDF_PARALLEL_POLL`。既定 60 秒）に読む先が、計画の台帳から計画の進行表とレーンの進行表になることだけである。

次のスプリントを conductor へ伝える経路は、次の 2 つに分ける。

| 場面 | 誰が伝えるか | どう伝えるか |
| --- | --- | --- |
| レーンの conductor が動いている | `progress.py next` の結果 | 完了の結果の `metrics.next_row` に、同じレーンの次の行を載せる。`after` が満たされていれば、conductor は続けて `progress.py new --lane <ID> --row <番号>` を打つ。満たされていなければ `metrics.next_row` は `waiting_after` で、conductor は自分を止める。次の行が無ければ `null` で、conductor は自分を止める |
| レーンの conductor が止まっている | 耐久ワークフロー | 実行中の行が無く、`after` を満たす未着手の行があるレーンを、今の耐久ステップ `parallel.launch`（`relay.py spawn`。[docs/specifications/ndf-parallel-durable-lane-launch.md](../docs/specifications/ndf-parallel-durable-lane-launch.md) ）で起こす。最初の入力は、その行の `progress.py new` の引数である |

耐久ワークフローは conductor へメッセージを送らず、起こすだけである。起きた conductor は、レーンの進行表を読んで行を実行中にする（E4）。1 台に 1 つの常駐やレーンごとの常駐は、ローカルで追加の常駐を要さない条件（非機能）に反するため採らない。進行表のワークフローを耐久ワークフローの中で流す形は、レーンの作業（worktree・Claude の起動）をオーガナイザーのプロセスへ寄せることになるため採らない。耐久ワークフローが conductor へメッセージで次の行を送る形は、止まっている conductor が受け取れず、起こす経路が別に要るため採らない。

根拠: Value 2 / Value 5（MVV 版 7）

### 決定 8: 有効・無効を 1 か所で読めるようにするため、宣言は定義の条件 → プロジェクトの宣言 → スプリントの引数と conductor の操作の 3 つの順位で上書きし、計画の順位を置かない

番号の大きい順位が、小さい順位を上書きする。

| 順位 | 置き場 | 役割 |
| --- | --- | --- |
| 1 | 定義の `metadata.ndf.when` | 既定の条件を持つ |
| 2 | `.ndf/project.json` の `workflow.stages.<工程>`（`enabled` と `reason`） | プロジェクトの既定を上書きする |
| 3 | スプリントの作成の引数（`--disable <工程>=<理由>`）と conductor の操作 | 最後に上書きする |

リファクタリングの停止は、定義の条件（CI テストの宣言がある・差分にコードがある）と、止めるときのプロジェクトの宣言で表す。停止の定数 `CROSS_REFACTORING_SUSPENDED` と `refactor_suspended` は消す。計画の単位で止めたいときは、オーガナイザーがレーンの入力の引数へ同じ `--disable` を渡す。

計画の進行表に宣言の順位を置く形は、上書きの順位が 4 つになり読む場所が増えるため採らない。

根拠: Value 4 / Value 11（MVV 版 7）

### 決定 9: 進め方とループで単位を変えないため、進行表はどの経路でもスプリント 1 つに 1 つとし、`fast` の課題ごとの作業は工程の行の子の行にする

1 スプリントのレーン・単独の作業・開発ループの 1 周は、それぞれスプリントの進行表 1 つを持つ。開発ループのレーンは、選定（`loop select`）の後に自分のレーンの進行表へ行を 1 つ足してから進行表を作る。`fast` の課題ごとの作業（実装〜完了判定〜Pull Request）は、定義の `for` が課題ごとに子の行（行の鍵 `<工程>#<課題番号>`）を作り、工程の行は子の行がすべて終わったときに終わる。定義は進め方で分けず、進め方はアクティビティの引数として渡す。

進め方ごとに定義を分ける形は、同じ工程の並びを写すため採らない（決定 4 と同じ理由）。

根拠: Value 11 / Value 4（MVV 版 7）

### 決定 10: 既存の読み手を壊さずに型を足すため、入出力規約は統一 JSON レポートを包む形にする

根拠: Value 11 / Value 3（MVV 版 7）

### 決定 11: 棚卸しが持ち越した課題を「やらない」と読まないため、組み換えを振り返りの直後・棚卸しの前に置く

組み換えの入力（振り返りの出力・外した課題・保留した受け入れ条件・スプリントの中で起票した課題）は振り返りまでにそろう。棚卸しは課題の一覧全体の順位を決めるため、組み換えで次のスプリントへ入れた課題を見てから動く方が、持ち越した課題を閉じる判断を避けられる。工程表で振り返りを通らない `light` は組み換えの行を持たず、振り返りが条件つきの `operation` は、振り返りが無効なら組み換えも「無効（振り返りが無い）」にする。

棚卸しの後に置く形は、棚卸しが持ち越した課題を閉じうるため採らない。

根拠: Value 6 / Value 1（MVV 版 7）

### 決定 12: 工程の遷移を進行表のほかに残さないため、置き換わる公開インタフェースに互換の経路を残さず、実行中のスプリントと計画は取り込みの副命令で移す

次のものを取り除く。

- `supervise.py new sprint`・`new close`・`queue --resume --from`
- `sprint.json` の書き出し
- `sprint-state.py next` の工程の判断

`parallel.py` の副命令は名前と引数を保ち、中身だけを替える。リリースの時点で動いているスプリントと計画は、`progress.py adopt` が進行表へ取り込む。取り込みの元は、`sprint.json` と `done-<番号>.json`、`plan.json` と計画の台帳である。終わったステージに当たる工程は、「手で終了（取り込み）」の事象で閉じる。元のファイルは消さない。ステージと工程が 1 対 1 でないときの判定と、取り込みが失敗したときの戻し方は決定 19 にある。

互換の経路を期間を決めて残す形は、遷移を決める場所がその期間 2 つになり受け入れ条件 11 に反するため採らない。

根拠: Value 3 / Value 6（MVV 版 7）

### 決定 13: 書き手を階層ごとに 1 つに寄せるため、事象の種類ごとに書ける役を表で持ち、追記の関数が検査する

追記の関数は、事象とその書き手の役（進行表のワークフロー・conductor・オーガナイザー・耐久ワークフロー・取り込み）を受ける。[issue-3092-design-runtime.md](issue-3092-design-runtime.md) の「事象の種類と書き手の表」にない組は断る。役はエントリポイント（`progress.py` の副命令・`parallel.py` の副命令・ワークフローの中）が決め、利用者は渡さない。脅威はうっかりの書き込みで、なりすましは考えない。

DB の権限（ロール）で分ける形は、SQLite で表せないため採らない。

根拠: Value 9 / Value 8（MVV 版 7）

### 決定 14: 進捗記録と流れた工程を食い違わせないため、課題の工程表・通した工程・ボードを進行の事象から生成し、Skill の本文から進捗記録の呼び出しを外す

工程の開始と終了の事象を書いた直後に、進行表のワークフローが進捗記録を生成するアクティビティを流す（ボードは開始、課題の工程表と通した工程は終了）。Skill の本文にある `projects-sync.sh <番号> stage` の呼び出しは、工程の遷移を Skill が書く箇所にあたるため外す。

Skill が記録し、進行表と突き合わせる形は、記録が 2 か所になり #2921・#1893 と同じ食い違いが残るため採らない。

根拠: Value 11 / Value 13（MVV 版 7）

### 決定 15: I1 を DB の制約で確実に守るため、一意を主キー（階層・リポジトリ・名前）だけで持ち、空を許す親の識別子を一意の列から外す

一意の制約に空を許す `parent_id` を含めると、SQLite と PostgreSQL のどちらも空どうしを別の値として扱う。このため、計画の外の単独のスプリントは同じ名前で 2 つ作れてしまう。そこで、一意は主キー `id`（`<階層>:<リポジトリの短い鍵>:<名前>`）だけで持ち、`parent_id` は参照だけに使う。

| 階層 | 名前の形 | 一意になる範囲 |
| --- | --- | --- |
| 計画 | 計画名 | リポジトリ |
| レーン | `<計画名>/<レーン名>` | リポジトリ。別の計画が同じレーン名を使ってもぶつからない |
| スプリント | スプリント名 | リポジトリ。計画の中か外かを問わない（I1） |

中止した進行表の名前も使えない。モードを下げるとき（I5）と中止の後に同じ作業を始め直すときは、別のスプリント名で作る。

PostgreSQL の `NULLS NOT DISTINCT` で空どうしを等しく扱う形は、SQLite に無く、2 つの置き場で同じテストが通る条件（受け入れ条件 9）に反するため採らない。空の代わりに番兵の値（空文字）を入れる形は、主キーと同じ事実を 2 か所に持つため採らない。

根拠: Value 8 / Value 4（MVV 版 7）

### 決定 16: 範囲とモードの変更でも定義のスナップショットを書き換えないため、スナップショットを改訂ごとの表へ追記し、行を改訂と工程の名前の組で決める

進行表（`ndf_progress_tables`）は作った後に変えない。定義のスナップショットは、定義の改訂（`ndf_progress_definitions`）の表へ改訂（`rev`）ごとに 1 行ずつ追記する。作成で改訂 1 を書き、`progress.py scope` が改訂を 1 つ上げる。スプリントの進行の事象は `rev` の列を持ち、行は（`rev`, `row_key`）で決まる。行の今の状態は、今の改訂（最大の `rev`）の事象だけから畳み込む。

改訂を上げるとき、`progress.py scope` は 1 つのトランザクションで次の 3 つを書く。

1. 新しい改訂のスナップショット
2. `scope_changed` か `mode_raised` の事象（理由と、影響する最初の工程）
3. 新しい改訂の全行の `created` の事象。影響する最初の工程より前の行は、前の改訂の状態（終了・無効）を写した `carried` の事象にする

影響する工程から後ろは未着手で始まり、次の `progress.py next` が新しい実行で流す。前の改訂の事象は残り、`show` の履歴に出る。

スナップショットを進行表の列に置いて上書きする形は、作成後に変えない表（I2 の追記だけ）と食い違い、前の定義を失うため採らない。行の鍵に工程の名前だけを使い、前の改訂の行を `cancelled` で閉じる形は、同じ鍵の行が 2 つの意味を持ち、畳み込みが事象の順序に依るため採らない。

根拠: Value 8 / Value 14（MVV 版 7）

### 決定 17: スプリントの終わりがレーンの進行表へ写らないまま残らないため、`row_ended` を書くのは E13 と同じトランザクションの中のレーンの進行表の関数だけにする

スプリントの終わり（E13）の書き手は 2 つある。完了は進行表のワークフローの `completed` で、中止は `progress.py cancel` の `cancelled` である。どちらの書き込みも、同じトランザクションでレーンの進行表のスクリプトの関数（行を終える関数）を呼ぶ。この関数だけが `row_ended` を書き、計画の決まり（I12a・I12b・I13・I18〜I21）を検査する。事象の書き手の役は E13 を書いた役を継ぐ。スプリントの進行表がレーンの行を持たない（計画の外）ときは呼ばない。

E13 を事象として受けて、別のプロセスが後でレーンの進行表へ写す形（結果整合）は、写す前にプロセスが止まると行が実行中のまま残り、耐久ワークフローが次のスプリントを起こせないため採らない。2 つの表は同じ DB にあり、1 つのトランザクションで書ける。

根拠: Value 8 / Value 3（MVV 版 7）

### 決定 18: SQLite のファイルへの書き込みが詰まったときに設計を戻さず切り替えるため、DBOS の記録を実行の鍵ごとのファイルへ分ける形を代わりに用意し、測った値で選ぶ

進行表のワークフローの既定は決定 2 のとおり、進行表と DBOS の記録を 1 つの SQLite のファイルに置く。そのために `lib/durable.py` へ進行表の DB の URL を渡す。`lib/durable.py` 自身の既定は、鍵ごとのファイルのままである（決定 20）。接続は WAL を有効にし、書き込みの待ちの上限（`busy_timeout`）を 30 秒にする。実装で 6 レーン相当の `progress.py next` と耐久ワークフローを同時に流し、次のどちらかに当たれば代わりの形へ切り替える。

| 切り替える条件 | 測り方 |
| --- | --- |
| `database is locked` の失敗が 1 回でも出る | 6 レーン相当を 30 分流すテストの失敗の数 |
| 書き込みの待ちの 95 パーセンタイルが 1 秒を超える | 追記の関数の所要時間の記録 |

代わりの形では、DBOS の記録だけを実行の鍵ごとの SQLite のファイルへ分け、進行表と進行の事象は 1 つのファイルに残す。分けたファイルは `<git の共通ディレクトリ>/ndf/state/progress/dbos/<実行の鍵>.sqlite` に置く。書き込みの多くは DBOS のステップの記録で、進行の事象は 1 スプリントで数百件にとどまるためである。この形は、今の `lib/durable.py` が耐久ワークフローごとにファイルを分けている形（#1142 の決定 34）と同じで、包みの関数を新しく作らない。PostgreSQL の URL を渡したときは、どちらの形でも 1 つの DB に置く。

切り替えは進行表のワークフローが `lib/durable.py` へ URL を渡すかどうかだけで行い、進行表のモデルと進行表のワークフローは変えない。手元で PostgreSQL を常駐させる形は、追加の常駐を要さない条件（非機能）に反するため採らない。

根拠: Value 3 / Value 12（MVV 版 7）

### 決定 19: 取り込みで終わっていない工程を終了と誤らないため、工程は当たるステージがすべて終わったときだけ終了にし、一部だけなら失敗にして conductor へ渡す。取り込みは 1 つのトランザクションで行い、失敗したら何も書かない

ステージと工程の対応（[issue-3092-design-runtime.md](issue-3092-design-runtime.md) の「移行」）は 1 対 1 でない。1 つの工程に 2 つ以上のステージが当たるとき（例: `実装レビュー` に `検査` と `実装レビュー`、`デプロイ` に `開発版`・`デプロイ`・`本番`）は、次の規則で決める。

| 当たるステージの終わり | 取り込んだ工程の状態 | 理由の欄 |
| --- | --- | --- |
| すべて終わっている | 終了（`adopted`） | 取り込みの元のファイル |
| 1 つも終わっていない | 未着手（`created` だけ） | — |
| 一部だけ終わっている | 失敗（`adopted`） | 終わったステージと終わっていないステージの名前 |

一部だけのときに失敗にするのは、流し直すか（`retry`）、手で終了にするか（`finish`）を conductor が決めるためである。デプロイのように、流し直すと本番へ 2 度届きうる工程がある。1 つのステージが 2 つ以上の工程に当たるとき（例: `設計` → `設計`・`ドキュメント再構成`・`ドキュメントレビュー`）は、そのステージの終わりをそれぞれの工程へ数える。モードの行に無い工程と、宣言で無効の工程は、ステージの終わりにかかわらず定義どおりにする。

取り込みは、入力 1 つ（スプリント 1 つか計画 1 つ）を 1 つのトランザクションで書く。読めない・対応の無いステージがある・I1 に当たるときは、トランザクションを戻して何も書かず、2 と理由を返す。元のファイルは消さないため、入力を直して打ち直せる。取り込みがどうしても通らないスプリントは、conductor が `progress.py new` で作り直し、終わった工程を `finish` で閉じる。リリースそのものを戻すときは、前の版のタグ（`ndf--v<版>`）へ戻せば、残した元のファイルで今の経路が続く。

一部だけでも終了にする形は、終わっていないデプロイやコードレビューを飛ばすため採らない。一部だけなら未着手にする形は、終わった本番のリリースを流し直しうるため採らない。

根拠: Value 3 / Value 13（MVV 版 7）

### 決定 20: #1142 の作り直しと同じ形にするため、次の行の選択と組み換えの要否は DBOS を import しない純粋な関数にし、DBOS は `lib/durable.py` の殻を通して使う

#1142 の子の課題 #2990 と #2963 は、次の 2 つを方針にしている。#2990 は耐久ワークフローの判断を純粋な関数に、耐久の層を薄い殻に分ける。#2963 は supervise のステップの遷移の判断を耐久の起動から切り離す。

- 遷移の判断は、状態と入力を受けて次の手を返す純粋な関数に置く
- DBOS を import するのは `lib/durable.py` だけにする（#1142 の I16）

この設計はこれに合わせる。

| 要素 | 形 |
| --- | --- |
| 進行表のモデル（`progress_model.py`）・組み換えの要否の判定（`reshuffle.py`） | 判断の関数。DBOS も `durable` も import しない。次の工程の選択・畳み込み・書き手の表・不変条件の判定を、DBOS を起動しない単体のテストで確かめる |
| 進行表のワークフロー（`progress_run.py`） | 判断の関数を回す殻。DBOS のワークフローとステップは `lib/durable.py` の包みを通して作り、DBOS を直接 import しない |
| 実行の鍵の排他（I14） | 進行表の DB の種類ごとに、DB と同じ範囲に効く排他を取る。SQLite は DB のファイルの隣のロックのファイル（`<DB のファイル>.<進行表の ID>.lock`）を今の `lib/locks.py`（`filelock`）で取る。SQLite のファイルを読み書きできるのは同じ端末だけなので、端末の中の排他で足りる。PostgreSQL は、進行表の ID から作った鍵でセッションの勧告的ロック（`pg_try_advisory_lock`）を取り、`progress.py next` が終わるまで専用の接続で持つ。取れなければ待たずに偽が返るので 2 つ目の起動を断る。プロセスが落ちて接続が切れると、ロックは DB が外す（PostgreSQL の文書 13.3.5「Advisory Locks」の "Once acquired at session level, an advisory lock is held until explicitly released or the session ends."、9.28.10 の `pg_try_advisory_lock` の "return false without waiting if the lock cannot be acquired immediately"。2026-11-13 に取得）。排他を取る関数は進行表の DB（`lib/progress_db.py`）が持ち、呼び手は DB の種類を知らない |

食い違う点が 1 つある。#1142 の今の `lib/durable.py` は、記録の置き場を実行の鍵ごとの SQLite のファイルに固定し、URL を受けない。この設計は `lib/durable.py` の起動の関数に、記録の置き場の URL を受ける引数を足す（構成要素の「耐久の記録の包み」）。既定は呼び手ごとに次のとおりで、`lib/durable.py` が持つ既定は 1 つである。

| 呼び手 | 渡す URL | 置き場 |
| --- | --- | --- |
| #1142 の耐久ワークフロー（並列の計画・supervise・cross-review・投稿キュー） | 渡さない | `lib/durable.py` の既定。今と同じ実行の鍵ごとの SQLite のファイル |
| 進行表のワークフロー | 進行表の DB の URL（`NDF_PROGRESS_DB` か決定 2 の既定） | 進行表と同じ 1 つの DB（決定 2）。決定 18 の条件に当たったときだけ、SQLite では URL を渡さず鍵ごとのファイルにする |

記録の形（`FORMAT`）は変えない。#2990 が判断の関数の型と DBOS を起こさない実行器を先に入れたときは、進行表のワークフローはそれに乗る。後になったときは、#2990 の実装がこの殻を手本の 1 つに数える。

進行表のワークフローが DBOS を直接 import する形は採らない。#1142 の I16 に反し、判断のテストのたびに DBOS の起動（1 回 3.4〜4.6 秒。#2963 の実測）を払うためである。

### 決定 21: NDF の版が上がって回復できなくなった実行で行を実行中のまま残さないため、`progress.py next` が古い実行を取り消し、実行中の行を失敗にしてから新しい実行を始める

DBOS は、起動したプロセスと同じアプリの版の実行だけを回復する（決定 7 の実測）。起動の回復は、`_dbos.py` の `get_pending_workflows(executor_id, app_version)` で実行を拾う。アプリの版はワークフローの関数のソースから計算されるため、承認待ちの間に NDF の版が上がると、途中の実行は新しいコードで回復されない。

`progress.py next` は、排他（I14）を取った後に、進行表の最新の `execution` の事象が指す実行の状態を DBOS から読む（`DBOSClient` の取得）。

| 実行の状態 | 扱い |
| --- | --- |
| 無い・終わっている | 新しい実行を始める（決定 6） |
| `PENDING` で、アプリの版が今のプロセスと同じ | 起動の回復に任せる（決定 7） |
| `PENDING` で、アプリの版が違う | 古い実行を `DBOS.cancel_workflow` で取り消し、新しい実行を始める。新しい実行は最初のステップで、今の改訂の実行中の行に `failed`（理由: 版が替わり、途中の実行を回復できない。古い実行の ID と 2 つの版）を書き、`stopped` で conductor へ返す |

conductor は、ほかの失敗と同じく `retry`・`finish`・`cancel` から選ぶ。デプロイのように流し直すと 2 度届きうる工程があるため、決定 19 と同じく conductor が決める。承認ゲートとリリースの結果の待ちの行も失敗になるが、答えは `answered` の事象にも残っている。`listen` のアクティビティは `recv` の前に今の改訂のその行の `answered` の事象を読み、あれば受信を待たずにそれを使う。このため、古い実行へ送った答えは `retry` の後の新しい実行で失われない。取り消しは別のプロセスから `PENDING` の実行へ効くことを確かめた（決定 7 の実測の続き）。

アプリの版（`application_version`）を NDF の版によらない固定の値にし、古い実行を新しいコードで回復させる形は採らない。ワークフローのコードが変わった後に古い実行の控えを新しいコードでなぞることになり、控えと処理がずれても検出できないためである。実行中の行を未着手へ戻して黙って流し直す形は、本番へ出すアクティビティを 2 度流しうるため採らない。
