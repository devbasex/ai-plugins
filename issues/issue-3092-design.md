# 工程の進行表: 工程の定義と進行表で、スクリプトが次の工程を決めて終了の印を付ける（#3092）

## 目的

- **今どうなっているか**: 工程の並びは `development-workflow` の工程表にあるが、スプリントの目録（`sprint.json`）はまとめの工程を持たず、conductor が手順書を読んでまとめ・再開・課題の持ち越しを組む。工程の有効・無効はコードの定数と手順書に散り、計画の状態は 3 か所に分かれる
- **誰に効くか**: 並列の計画とスプリントを流す利用者と、その conductor・オーガナイザー
- **変えると何が成り立つか**: モードごとの全工程を登録済みの工程の定義から進行表の行として組み、スクリプトが進行表だけを読んで次の工程を流し、出力を入出力規約で検査して終了の印を付ける。計画とレーンも進行表で持ち、振り返りの後の組み換えでスプリントの結果を計画へ戻す

## 適用範囲

- **働く範囲**: NDF を使うすべてのリポジトリ。進行表の DB はチェックアウトごとの SQLite を既定にし、Factory は PostgreSQL の URL を渡す
- **プロジェクトごとに違うもの**: 工程の有効・無効の既定はプロジェクトの宣言（`.ndf/project.json` の `workflow`）で、スプリントごとの上書きは引数で受ける。DB の置き場は環境変数（`NDF_PROGRESS_DB`）で受ける
- **当たるモード**: 5 つすべて（`light`・`operation`・`legacy-refactor`・`standard`・`documentation`）。並列の計画の外の単独の作業も同じ進行表で流す

## あるべき姿の根拠

| 根拠 | 種類 | 何を示すか |
| --- | --- | --- |
| STD1 | 外部の一次情報 | ワークフローの定義を標準の書式で持ち、定義の要素ごとに入出力のスキーマと付帯情報（`metadata`）を書ける |
| LIB1 | 外部の一次情報 | DBOS は SQLite と PostgreSQL を URL の差し替えで扱い、実行者ごとに回復を分ける（`executor_id`） |
| 利用者の指示の原文（2026-11-12） | 利用者の指示 | 「スクリプトはこの目録に従って次にやるべきことを判断し、その工程が終ったら終了マークをつける」「DBOSを採用し、定義の書式は標準を借りる、で決定」 |
| 計画 p5 のレーン lci の 2026-11-12 のまとめ | 実測 | 最後の検査が本番のリリースの後に置かれ、出し済みの差分をレビューした（#3126）。順序の決まりを定義で検査する根拠 |

要求と受け入れ条件は #3092 の本文にある（コピーは [issue-3092-requirements.md](issue-3092-requirements.md) ）。取り込んだ #3097・#3098 の受け入れ条件は、その 13〜21 にある。この文書は「どう作るか」だけを扱う。データ構造・入出力の契約・処理の流れ・非機能・移行は [issue-3092-design-runtime.md](issue-3092-design-runtime.md) にある。

## ドメインモデル

### コンテキスト

| コンテキスト | 何の語が 1 つの意味に決まるか |
| --- | --- |
| NDF の開発ワークフロー（`ndf-workflow`） | 工程・アクティビティ・進行表・終了の印・組み換え・レーン・計画 |
| Neural Development Factory（`ndf-factory`） | 進行表の画面と、PostgreSQL の進行表の DB |

関係は**公開された言語**とする。進行表の DB のスキーマと進行の事象の形（[issue-3092-design-runtime.md](issue-3092-design-runtime.md) の「データ構造」）を文書化した共通の形式として、Factory は読むだけで、書き込みは NDF の進行表のスクリプトを通す。

### 集約

| 集約 | 持ち主（書き換えてよいもの） | 根 | エンティティ | 値オブジェクト |
| --- | --- | --- | --- | --- |
| 工程の定義 | リポジトリの変更（CI の定義の検査を通ったものだけ）。実行の中では読むだけ | モードの定義 | 工程の定義・アクティビティの定義 | 入出力規約の参照・順序の属性（種類と範囲）・有効の条件 |
| スプリントの進行表 | 進行表の追記の関数（工程の状態は進行表のワークフロー、異常の操作は進行表のスクリプト。事象の種類ごとの書き手は I6） | スプリントの進行表 | 工程の行・アクティビティの行・課題ごとの子の行 | 定義のスナップショット・状態・終了の印・無効の理由 |
| レーンの進行表 | レーンの進行表のスクリプト（呼ぶのはレーンの conductor の側。作成と移動のときだけオーガナイザー） | レーンの進行表 | 順番表の行（スプリント 1 つ） | 課題の一覧・触る場所の見込み |
| 計画の進行表 | 計画の進行表のスクリプト（呼ぶのはオーガナイザーと耐久ワークフロー） | 計画の進行表 | レーンの行 | 規則・上限・レーンをまたぐ `after` |

ほかの集約は ID で参照する。レーンの進行表の行はスプリントの進行表の ID を持ち、スプリントの進行表はレーンの進行表の ID と行の番号を持つ。スプリントの終わりをレーンの進行表へ写すのは、ドメインイベント E13 を受けたレーンの進行表のスクリプトである（結果整合）。

### 不変条件

| # | 集約 | 条件 | 破れたときの扱い |
| --- | --- | --- | --- |
| I1 | スプリントの進行表 | 同じリポジトリの同じ名前のスプリントの進行表は 1 つ | 作成を断り、今の進行表の ID を返す |
| I2 | すべての進行表 | 進行の事象は追記だけで、表ごとの番号は 1 ずつ増える。更新と削除をしない | 番号のぶつかりは追記を断り、読み直して判定し直す |
| I3 | スプリントの進行表 | 工程とアクティビティの行が終了になるのは、出力が出力の規約に合ったときだけ | 終了の印を付けず「失敗」にし、conductor へ返す |
| I4 | スプリントの進行表 | 実行中の行は無効にできない。手で終了にする出力は規約に合う | 操作を断る |
| I5 | スプリントの進行表 | モードは上げる方向だけ変わる | 下げる操作を断る（新しい進行表を作る） |
| I6 | すべての進行表 | 事象の種類ごとに書ける役が決まっている（[issue-3092-design-runtime.md](issue-3092-design-runtime.md) の「事象の種類と書き手の表」） | 追記を断る |
| I7 | 工程の定義 | 工程とアクティビティのすべてが入力と出力の規約を参照し、参照先がある | 登録（CI と実行の前の検査）を断る |
| I8 | 工程の定義 | 同じ範囲について、レビューとテストのアクティビティは本番へ出すアクティビティより前にある | 登録を断る |
| I9 | 工程の定義 | レビューとテストのアクティビティの範囲はスプリントの差分である | 登録を断る |
| I10 | 工程の定義 | 同じ範囲で同じ種類のレビューを 2 度置かない | 登録を断る。やり直しは conductor の操作の事象で表す |
| I11 | 工程の定義 | モードの工程の並びが `development-workflow` の工程表のそのモードの列（`—` でない行）と一致する | CI の検査が落とす |
| I12 | レーンの進行表 | 実行中と完了の行は書き換えない。別のレーンの `after` が指す行は消さず、後ろへ回さない | 書き込みを断り、オーガナイザーへの依頼にする |
| I13 | 計画の進行表 | レーンの間で触る場所と課題が重ならず、上限を超えず、`after` が輪にならない | 作成と変更を断る |
| I14 | スプリントの進行表 | 動いている実行は 1 つ | 2 つ目の起動を断る |
| I15 | スプリントの進行表 | 実行の途中で定義のスナップショットを変えない。範囲とモードの変更は版を上げ、影響する工程から新しい実行で流す | 実行中の書き換えを断る |
| I16 | 計画の進行表 | 完了は、全レーンの行が完了か中止で、答えていない依頼が無いときだけ | 完了にしない |

| E6 | 工程を無効として飛ばした | 進行表のワークフロー | 進捗記録の生成 |

### 用語

| 用語 | 意味 | 用語集への反映 |
| --- | --- | --- |
| アクティビティ | 工程の中の実行の単位。DBOS のステップ 1 つで流し、入力の範囲と出力の規約を持つ。プラン 1 本の実行・承認ゲートの答えの待ち・記録の 3 種類がある。要求の文の「ステップ」にあたり、プランのステップとは別 | 追加 |
| 進行表のワークフロー | スプリントの進行表 1 つを、登録した工程の定義に沿って流す DBOS のワークフロー。実行のたびに ID が替わり、進行表の ID は変わらない | 追加 |
| 進行の事象 | 進行表への変更 1 件の記録。誰が・いつ・何を・理由と変更後の状態を持ち、追記だけで残す。行の今の状態は最新の事象から引く | 追加 |
| 進行表の DB | 進行表と DBOS の記録を置く 1 つのデータベース。URL で指し、ローカルは SQLite、Factory は PostgreSQL | 追加 |
| 進行表 | （意味は変えない。用語集の確定前の語を確定する） | 追加 |
| 工程の定義 | モードの工程の並びと、工程ごとのアクティビティの並び・入出力規約の参照・順序の属性を持つ、Serverless Workflow の書式の JSON 文書 | 意味の変更（書式とアクティビティを足す） |

## 構成要素

| 要素 | 責務 |
| --- | --- |
| 工程の定義（`plugins/ndf/contracts/workflow/`） | モードの文書 5 つ・工程の文書・入出力規約・借りた標準のスキーマ。データだけを持つ |
| 定義の検査（`lib/workflow_def.py`） | 定義のファイルを読み（ファイルを読むのはこの関数の読み込みだけ）、標準のスキーマ・使う要素の範囲・規約の参照・順序の決まり（I7〜I10）・工程表との一致（I11）を検査し、定義のスナップショットを返す。検査の本体は純粋な処理で、誤りは例外の理由の一覧で返す |
| 進行表のモデル（`lib/progress_model.py`） | 進行の事象から行の状態を畳み込む・次の行を選ぶ・書き手の表（I6）・不変条件 I1〜I5・I12〜I16 の判定。純粋な処理 |
| 進行表の DB（`lib/progress_db.py`） | URL で接続し、表を作り、事象を追記する唯一の関数。番号のぶつかりで断る（I2） |
| 進行表のワークフロー（`lib/progress_run.py`） | DBOS のワークフロー 1 つ。定義のスナップショットに沿って工程を流し、入力と出力を規約で検査し、事象を書く |
| アクティビティの関数（`lib/progress_activities.py`） | 定義の `call` の名前 → 関数の対応。プランの実行（今の `supervise.py` の実行の核を呼ぶ）・承認ゲートの待ち・記録・組み換え |
| 進捗記録の生成（`lib/progress_projection.py`） | 事象から課題の工程表・スプリント PR の「通した工程」・ボードを作る |
| 組み換え（`lib/reshuffle.py`） | 要否の判定（純粋）・変更案の検査と反映・オーガナイザーへの依頼 |
| 進行表のスクリプト（`scripts/progress.py`） | スプリントの進行表とレーンの進行表の副命令のエントリポイント。統一 JSON レポートで返す |
| 計画の進行表のスクリプト（`scripts/parallel.py` の `init`・`start`・`lane add`・`set`・`stop`・`status`） | 副命令の名前を保ち、中身を計画の進行表とレーンの進行表の読み書きへ替える |
| 耐久ワークフロー（`lib/parallel_run.py`） | 計画の進行表とレーンの進行表を読み、起こせるスプリントを決め、レーンを止める |
| 耐久の記録の包み（`lib/durable.py`） | DBOS の起動に進行表の DB の URL と実行者の ID を渡せるようにする |

構成要素の関係と配置の図、パッケージの構成は [issue-3092-design-runtime.md](issue-3092-design-runtime.md) の「構成要素の図と配置」にある。

## 決定の記録

### 決定 1: 工程の状態を手で終了にした分や変更の履歴まで残すため、状態の正本を NDF の進行の事象にし、DBOS の実行の記録はアクティビティの再開にだけ使う

DBOS の実行の記録は、実行したステップの出力だけを持つ。手で終了にした工程・始める前に無効にした工程・conductor の変更の理由・計画とレーンの行は表せない。ステップの番号は実行ごとに振られ、やり直しで実行が替わると工程との対応が切れる。このため、工程の状態は進行表の DB の進行の事象（追記だけ）に置き、今の状態は最新の事象から畳み込む。DBOS の記録は、落ちた後にアクティビティを流し直さないための実行の控えとして使う。2 つは別の事実を持つ（業務の状態と、実行の控え）。

状態を DBOS の実行の記録だけから導く形は、上の 4 つを表せないため採らない。行の状態を上書きする表は、履歴を失うため採らない（非機能の「変更を追記だけで残す」）。

- 作り方: ライブラリやサービスを使う・自前で作る
- 比べた候補: LIB1 / PRD1 / PRD3

根拠: Value 8 / Value 3（MVV 版 7）

### 決定 2: ローカルと Factory を URL の差し替えだけで切り替えるため、DBOS の記録と進行表を 1 つの DB に置き、SQLAlchemy Core で読み書きする

URL は環境変数 `NDF_PROGRESS_DB` で受け、無ければチェックアウトの状態の置き場の SQLite（`<状態の置き場>/progress/ndf-progress.sqlite`）を使う。DBOS は同じ URL を `system_database_url` に受け、実行者の ID を進行表の ID にして回復を進行表ごとに分ける。表は 2 つ（進行表・進行の事象）と表の版の 1 行で、版を上げるときは起動の時に足りない列と表を足す。SQLAlchemy は DBOS の依存として手元にあり、新しい依存にならない。

DBOS の記録と進行表を別の DB に置く形は、接続先が 2 つになり Factory の設定が増えるため採らない。移行の道具（LIB5）は、新しく置く 2 つの表に比べて重いため採らない。

- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB1 / LIB4 / LIB5

根拠: Value 4 / Value 12（MVV 版 7）

### 決定 3: 定義の書式を標準どおりに検査するため、Serverless Workflow 1.0.3 の公式スキーマを手元に置き、`jsonschema` で検査する

Python の SDK は仕様 0.8 にしか対応せず、2022-04 から出ていない。公式スキーマ（STD1）を JSON に直して `plugins/ndf/contracts/workflow/serverless-workflow-1.0.3.schema.json` へ置き（取得元の URL と sha256 を文書の `$comment` に書く）、`jsonschema` の draft 2020-12 の検査器で形を確かめる。1.1.0 は出て 1 日のため採らず、上げるときはスキーマの差し替えと検査の通過で判断する。依存は `jsonschema` 1 つを足す（グループ `workflow`）。

SDK を使う形は 1.0 の書式を読めないため採らない。書式を自作する形は、利用者の決定（標準を借りる）に反するため採らない。

- 作り方: 標準に倣う・ライブラリやサービスを使う
- 比べた候補: STD1 / STD2 / LIB2 / LIB3

根拠: Value 12 / Value 11（MVV 版 7）

### 決定 4: モードの間で同じ工程を写さないため、工程を 1 つの文書にし、モードの文書は工程の文書を順に呼ぶだけにする

工程の文書（`stages/<工程の ID>.json`）がアクティビティの並びと入出力規約を持ち、モードの文書（`modes/<モード>.json`）は `run.workflow` で工程の文書を名前と版で呼ぶ行を並べる。同じ工程を 5 つのモードで持っても、アクティビティの並びは 1 か所にある。工程の差がモードで要るときは、別の工程の文書を作る（例: `operation` の実装）。

モードごとの文書に全アクティビティを書く形は、同じ並びを最大 5 回写すため採らない。

根拠: Value 11（MVV 版 7）

### 決定 5: 式の評価器を持たずに済ませるため、NDF に固有の条件と属性は `metadata.ndf` に置き、定義の要素の `if` を使わない

有効の条件（差分にコードがある・CI テストの宣言がある・振り返りが有効、など）・アクティビティの種類（レビュー・テスト・本番へ出す・記録）・範囲（スプリントの差分・ベースブランチ）は、`metadata.ndf` に閉じた語彙で書く。語彙は定義の検査が持つ一覧に限り、知らない語は登録で断る。使う要素は `do`・`run`（工程の呼び出し）・`call`（アクティビティ）・`listen`（承認ゲートの待ち）・`for`（`fast` の課題ごと）の 5 つに限る。

`if` は実行時の式（既定は jq）を求め、評価器の依存と、条件の誤りが実行の時に初めて分かる経路を足すため採らない。

根拠: Value 3 / Value 2（MVV 版 7）

### 決定 6: 再開とやり直しを `--from` の手組みから外すため、やり直しは新しい実行を始め、終わった行を事象から読んで飛ばす

進行表のワークフローは、工程を始める前に進行の事象からその行の状態を読み（読む処理は DBOS のステップにして実行の控えに残す）、終了か無効なら飛ばす。やり直しは、conductor の操作が「やり直し」の事象を書いて動いている実行を取り消し、次の `progress.py next` が新しい実行を始める。範囲とモードの変更も同じで、版を上げた定義のスナップショットで新しい実行を始める。

DBOS の `fork_workflow` で指定したステップから流し直す形は、ステップの番号を工程へ写す対応が要り、定義を変えた後に使えないため採らない。

根拠: Value 7 / Value 3（MVV 版 7）

### 決定 7: 常駐のサーバーを置かずに承認待ちを挟むため、進行表のワークフローは conductor が前景で打つ `progress.py next` の中で動かし、待ちに入ったら抜ける

`progress.py next` は DBOS を起動し、途中の実行を回復して、承認ゲートかリリースの結果の待ちに入るか、失敗するか、完了するまで流す。待ちに入ったら耐久の記録を途中のまま残して `gate` で返す。答えは `progress.py answer` が DB へ送るため、プロセスが無い間も失われない。conductor は答えの後に同じ `progress.py next` を打つ。1 台に 1 つの常駐やレーンごとの常駐は、ローカルで追加の常駐を要さない条件（非機能）に反するため採らない。耐久ワークフローの中で流す形は、レーンの作業（worktree・Claude の起動）をオーガナイザーのプロセスへ寄せることになるため採らない。

根拠: Value 2 / Value 5（MVV 版 7）

### 決定 8: 有効・無効を 1 か所で読めるようにするため、宣言は定義の条件 → プロジェクトの宣言 → スプリントの引数と conductor の操作の 3 段にし、計画の段を置かない

定義の `metadata.ndf.when` が既定の条件を持ち、`.ndf/project.json` の `workflow.stages.<工程>`（`enabled` と `reason`）がプロジェクトの既定を上書きし、スプリントの作成の引数（`--disable <工程>=<理由>`）と conductor の操作が最後に上書きする。リファクタリングの停止は、定義の条件（CI テストの宣言がある・差分にコードがある）と、止めるときのプロジェクトの宣言で表し、`CROSS_REFACTORING_SUSPENDED` と `refactor_suspended` を消す。計画の単位で止めたいときは、オーガナイザーがレーンの入力の引数へ同じ `--disable` を渡す。

計画の進行表に宣言の段を置く形は、上書きの段が 4 つになり読む場所が増えるため採らない。

根拠: Value 4 / Value 11（MVV 版 7）

### 決定 9: 進め方とループで単位を変えないため、進行表はどの経路でもスプリント 1 つに 1 つとし、`fast` の課題ごとの作業は工程の行の子の行にする

1 スプリントのレーン・単独の作業・開発ループの 1 周は、それぞれスプリントの進行表 1 つを持つ。開発ループのレーンは、選定（`loop select`）の後に自分のレーンの進行表へ行を 1 つ足してから進行表を作る。`fast` の課題ごとの作業（実装〜完了判定〜Pull Request）は、定義の `for` が課題ごとに子の行（行の鍵 `<工程>#<課題番号>`）を作り、工程の行は子の行がすべて終わったときに終わる。定義は進め方で分けず、進め方はアクティビティの引数として渡す。

進め方ごとに定義を分ける形は、同じ工程の並びを写すため採らない（決定 4 と同じ理由）。

根拠: Value 11 / Value 4（MVV 版 7）

### 決定 10: 既存の読み手を壊さずに型を足すため、入出力規約は統一 JSON レポートを包む形にする

アクティビティの出力の規約は、共通のスキーマ（`schemas/report.schema.json`。`tool`・`status`・`summary`・`items`・`metrics`）を `allOf` で含み、アクティビティごとに必須の項目を足す。工程の出力の規約は、アクティビティの出力をまとめた形（`stages/<工程>.output.schema.json`）で、次の工程の入力はこれから作る。プランの JSON はアクティビティの中の実行の形として今のまま使う。統一 JSON レポートを置き換える形は、今の手順のスクリプトのすべてを書き換えることになり、範囲を超えるため採らない。

根拠: Value 11 / Value 3（MVV 版 7）

### 決定 11: 棚卸しが持ち越した課題を「やらない」と読まないため、組み換えを振り返りの直後・棚卸しの前に置く

組み換えの入力（振り返りの出力・外した課題・保留した受け入れ条件・スプリントの中で起票した課題）は振り返りまでにそろう。棚卸しは課題の一覧全体の順位を決めるため、組み換えで次のスプリントへ入れた課題を見てから動く方が、持ち越した課題を閉じる判断を避けられる。工程表で振り返りを通らない `light` は組み換えの行を持たず、振り返りが条件つきの `operation` は、振り返りが無効なら組み換えも「無効（振り返りが無い）」にする。

棚卸しの後に置く形は、棚卸しが持ち越した課題を閉じうるため採らない。

根拠: Value 6 / Value 1（MVV 版 7）

### 決定 12: 工程の遷移を進行表のほかに残さないため、置き換わる公開インタフェースに互換の経路を残さず、実行中のスプリントと計画は取り込みの副命令で移す

`supervise.py new sprint`・`new close`・`queue --resume --from`・`sprint.json` の書き出しと、`sprint-state.py next` の工程の判断を取り除く。`parallel.py` の副命令は名前と引数を保ち、中身だけを替える。リリースの時点で動いているスプリントと計画は、`progress.py adopt` が `sprint.json` と `done-<番号>.json`、`plan.json` と計画の台帳から進行表を作り、終わったステージに当たる工程を「手で終了（取り込み）」の事象で閉じる。元のファイルは消さない。

互換の経路を期間を決めて残す形は、遷移を決める場所がその期間 2 つになり受け入れ条件 11 に反するため採らない。

根拠: Value 3 / Value 6（MVV 版 7）

### 決定 13: 書き手を段ごとに 1 つに寄せるため、事象の種類ごとに書ける役を表で持ち、追記の関数が検査する

追記の関数は、事象とその書き手の役（進行表のワークフロー・conductor・オーガナイザー・耐久ワークフロー・取り込み）を受け、[issue-3092-design-runtime.md](issue-3092-design-runtime.md) の「事象の種類と書き手の表」にない組を断る。役はエントリポイント（`progress.py` の副命令・`parallel.py` の副命令・ワークフローの中）が決め、利用者は渡さない。脅威はうっかりの書き込みで、なりすましは考えない。

DB の権限（ロール）で分ける形は、SQLite で表せないため採らない。

根拠: Value 9 / Value 8（MVV 版 7）

### 決定 14: 進捗記録と流れた工程を食い違わせないため、課題の工程表・通した工程・ボードを進行の事象から生成し、Skill の本文から進捗記録の呼び出しを外す

工程の開始と終了の事象を書いた直後に、進行表のワークフローが進捗記録を生成するアクティビティを流す（ボードは開始、課題の工程表と通した工程は終了）。Skill の本文にある `projects-sync.sh <番号> stage` の呼び出しは、工程の遷移を Skill が書く箇所にあたるため外す。

Skill が記録し、進行表と突き合わせる形は、記録が 2 か所になり #2921・#1893 と同じ食い違いが残るため採らない。

根拠: Value 11 / Value 13（MVV 版 7）
