> ## 原因
>

> ## 影響
>

> ## 直し方の案
>
> 1. 出し直しの設計のプランに、指摘の全文を入力として渡す（設計の worker の起動指示に「この指摘を満たすように直す。満たせない項目は理由を書く」として載せる）

>
> ## 受け入れ条件
>
> 1. `loop answer --revise --note` の指摘の全文が、次の周回の設計のプランの入力に入る
> 2. 課題の本文の指摘の履歴は、次の周回で人の判断待ちへ移しても消えない
> 3. 出し直しの設計 PR の本文に、指摘ごとの対応の表がある
>
> ## 広げた範囲: オーケストレーターからレーンへの指示が伝わらない（利用者の指示で検討、2026-11-05）
>
> 「直して出し直す」の指摘は 1 つの例である。2026-11-04〜05 の計画 p3 では、次の形が起きた。
>
> | 送ったもの | 届いたか | 落ちた場所 |
> | --- | --- | --- |
> | 設計の承認（approved） | 記録には届いた | 承認の後のマージに持ち主がいない（#2507） |
> | 直して出し直すの指摘（note） | 記録には届いた | 設計のプランが読まない。本文の節は次の周回で上書きされる（この課題） |
> | 同じ問いへの答え | 行き違いで再送が来た | 答えが届く前に、レーンが同じ問いを送った |
> | 引継ぎ文書の書き換え（ループ名・予算） | 届いた | レーンが起こし直しのときに読むので伝わった |
>
> **共通の原因**: 答えは記録（`loop.json`・耐久のイベント）には届く。しかし、その値を読んで動く側が決まっていない値がある。レーンが指示どおりに動いたかを確かめる手順も無く、人が設計を読んで初めて気づいた。
>
> ### 直し方の案
>
> - **A. 読む側を決める（元を断つ）**: 答えの種類ごとに、読んで動く手順を 1 つ決める。承認はオーガナイザーが設計 PR をマージする（#2507）。直して出し直すは、指摘の全文を設計のプランの入力に入れる（上の 1・2）。予算は `loop start --budget-*` で上書きする
> - **B. 届いたかを確かめる（漏れを拾う）**: 出し直しの設計 PR の本文に「指摘への対応」の表を置く（上の 3）。オーガナイザーは人に問う前に、指摘と表を突き合わせる。足りなければ人に聞かず、直して出し直すへ自分で戻す（同じ指摘のまま、届かなかった項目を名指しする）
> - **C. 指示の通り道を 1 本にまとめる**: 承認・指摘・止める・予算などを、種類を持つ 1 つのメッセージにする。レーンは周回の境で読んで「当てた」を記録し、当てていない指示はオーガナイザーの `wait` に出す。A・B の上位の形だが大きな作り直しになるので、A・B で効き目を確かめてから要否を決める
>
> 推奨は A と B を両方入れること。
>
> ### 受け入れ条件（足すもの）
>
> 4. オーガナイザーは、出し直しの設計の承認を人に問う前に、指摘と「指摘への対応」の表を突き合わせる。届いていない項目があれば、人に問わずに直して出し直すへ戻す
> 5. 答えの種類（承認・直して出し直す・やらない・予算・止める）ごとに、読んで動く手順が 1 つ決まっていて、手順書（`references/parallel.md`・`loop.md`）に書かれている
> 6. 直して出し直す指摘を持つ課題の設計のプランでは、要求の写しが一致して `requirements-check` が 0 を返しても要求のステップが流れ、起動指示に指摘の本文が入る（テストで確かめる）
> 7. 直して出し直す指摘を持つ課題の MVV 判定（`mvv-gate.py check --gate design`）の材料に指摘の本文が入り、指摘と食い違う設計は「従う」にならない（テストで確かめる）

## 目的

- 人が承認ゲート 1 で「直して出し直す」と答えて送った指摘を、次の周回の設計が必ず読み、指摘ごとに直したか・直せない理由を示した状態で人へ戻す
- 指摘が届いていない出し直しの設計を、人が読む前に機械と AI が見つけて戻す。人が同じ指摘を 2 回送ることを無くす
- 人の答え（承認・直して出し直す・やらない・予算・止める）ごとに、その答えを読んで動く手順を 1 つに決める
- 並列の計画で、オーガナイザーが送った承認がレーンのループの記録に必ず当たり、当たらなかったときはオーガナイザーが知る
- 取り込みのコミットだけで設計 PR の先頭が動いても、同じ設計の承認を人へ問い直さない
- 計画を始める前のループで承認待ちになった設計を、オーガナイザーの問いの一覧に出し、人の判断が要る設計を埋もれさせない

## 前提

- 前提 1: 設計のプランに渡す指摘は、その課題について送られた全回の出し直しの指摘とする（最新の 1 回だけにしない）。前の回の指摘を満たした状態を、次の回の設計で崩さないためである。別の開発ループで送った回も含める。ループが替わると前のループの指示が届かない形は、この課題の受け入れ条件 12 と同じ根を持つためである
- 前提 2: 指摘の項目は、`--note` に渡したファイルの箇条書き（`-` / `*`）と番号付きの行を 1 項目として数える。どちらも無ければ全文を 1 項目とする。「指摘への対応」の表はこの項目ごとに 1 行を持つ
- 前提 3: 出し直しの指摘と「指摘への対応」の表の突き合わせ（受け入れ条件 5）は、人の判断待ちの行へ移す共通の経路で行う。並列の計画のオーガナイザーが問う場合と、並列でない開発ループの conductor が問う場合の両方に効く（Value 7。直す場所を経路ごとに分けない）
- 前提 4（利用者の決定、2026-11-05）: 人へ問わずに直して出し直すへ自分で戻すのは、人の出し直し 1 回につき 1 回までとする。2 回目も届いていない項目が残れば、届いていない項目を添えて人へ問う
- 前提 5: 課題の本文の「出し直しの指摘の履歴」の節を書けなかった（GitHub の書き込みの失敗）ときも、ループの記録の人の判断待ちの行に指摘が残り、設計のプランは記録から指摘を読む。本文の節は人が読むための写しで、設計のプランの入力の正本はループの記録とする
- 前提 6: 予算の答えは、既にある `loop start --budget-*` / `sprint-state.py loop budget`（予算の反映）が読んで動く手順とし、この課題で新しい経路を作らない。止めるの答えは、既にある `loop stop` が置く止める指示を周回の境で読む手順とする
- 前提 7: 「取り込みのコミットだけの違い」は、問いの時点の先頭から今の先頭までに足されたコミットがすべて起点ブランチ（`.ndf/worktree.json` の `base_branch`）を取り込むマージコミットで、かつ設計 PR が変える設計文書と要求の写し（`issues/issue-<番号>-*.md`）の中身が問いの時点の先頭と同じであることで判定する。判定できない（照会の失敗・履歴を辿れない）ときは、今どおり問い直す
- 前提 8: 「前のループ」は、同じリポジトリの開発ループの記録（`.ndf/loop/<名>/loop.json`）のうち、計画のレーンでないループすべてとする。名前の付け方や順序で前後を決めない。レーンのループが「人の判断待ち」を理由に選定から外す課題の待ちは、どのループの記録にあっても対象に入る
- 前提 9: #2474 の承認がレーンの記録に当たらなかった原因は、この要求の時点で特定していない。依頼の id の打ち直し（設計 PR の先頭が動いたときに依頼を送り直すと、行の依頼の id が新しい id に置き換わり、古い id への答えが行に当たらない）が候補の 1 つである。受け入れ条件 10 は原因によらず観測できる形で書き、原因の特定は設計で行う

## 対象範囲

含む:
- 出し直しの指摘を、次の周回の設計のプランの要求のステップと設計のステップの起動指示へ入れる
- 出し直しの指摘を持つ課題では、要求の写しが一致しても要求のステップを流す
- 課題の本文に、回ごとに追記して上書きしない「出し直しの指摘の履歴」の節を置く
- 出し直しの設計 PR の本文に「指摘への対応」の表を置く
- 人の判断待ちの行へ移す前に、出し直しの指摘と「指摘への対応」の表を突き合わせ、届いていない項目があれば直して出し直すへ戻す
- 承認ゲート 1 の MVV 判定（`mvv-gate.py check --gate design`）の材料へ出し直しの指摘を入れる
- 答えの種類ごとの、読んで動く手順の表を `development-workflow` の `references/parallel.md`・`references/loop.md` に書く
- オーガナイザーの答え（`parallel.py answer`）がレーンのループの記録に当たらないときに、黙って捨てずにオーガナイザーへ知らせる
- 取り込みのコミットだけで設計 PR の先頭が動いたときに、設計の承認の依頼を送り直さず、問いの時点の依頼への答えを当てる
- 計画を始めるときと周回の境で、前のループの答えがまだの人の判断待ちを、オーガナイザーの問いの一覧へ送る

含まない:
- 承認・指摘・止める・予算を種類つきの 1 つのメッセージにまとめる作り直し（元の本文の直し方の案 C）。この課題の効き目を確かめてから要否を決める
- 承認の後に設計 PR をマージする持ち主を決めること（#2507 が持つ）

## 用語

| 用語 | 意味 |
| --- | --- |
| 出し直しの指摘 | 承認ゲート 1 で人が「直して出し直す」と答えたときに `--note` に渡したファイルの全文。レビューの担当が書く指摘ファイルとは別のもの |
| 出し直しの指摘の履歴 | 課題の本文に置く、出し直しの指摘を回ごとに追記する節。人の判断待ちの節を書き直しても消えない |
| 指摘への対応の表 | 出し直しの設計 PR の本文に置く表。出し直しの指摘の項目ごとに、直した / 直せない、直した箇所か直せない理由を 1 行で持つ |
| 設計のプラン | 開発ループの周回が課題ごとに組む、設計のフェーズのプラン（`sprint/<番号>-design-<課題>.json`）。要求・設計・レビュー・承認ゲート 1 のステップを持つ |
| 答えの種類 | 人が承認ゲートや問いに返す答えの区分。承認・直して出し直す・やらない・予算・止めるの 5 つ |
| 設計の承認の依頼 | 並列の計画のレーンが、承認ゲート 1 の判断をオーガナイザーへ求めて送る依頼。設計 PR の先頭の SHA を持つ |
| 取り込みのコミット | 起点ブランチを設計 PR のブランチへ取り込むマージコミット。判定は前提 7 |
| 前のループ | 同じリポジトリの開発ループのうち、計画のレーンでないもの（前提 8） |

## 受け入れ条件

- [ ] 1. 課題に出し直しの指摘が 1 回以上ある状態で次の周回の設計のプランを組むと、要求のステップと設計のステップの起動指示に、その課題の全回の出し直しの指摘の全文が入る。起動指示は「この指摘を満たすように直す。満たせない項目は理由を書く」の旨を含む（テストで確かめる）
- [ ] 2. 出し直しの指摘を持つ課題の設計のプランでは、要求の写しが課題の本文と一致して `requirements-check` が 0 を返しても、要求のステップが流れる（テストで確かめる）
- [ ] 3. 直して出し直すの答えを当てるたびに、課題の本文の「出し直しの指摘の履歴」の節へ、回数・日付・設計 PR・指摘の全文が 1 回分ずつ追記される。その課題を次の周回で人の判断待ちへ移して判断待ちの節を書き直した後も、前の回の指摘が本文に残る（テストで確かめる）
- [ ] 4. 出し直しの設計 PR の本文に「指摘への対応」の表があり、出し直しの指摘の項目（前提 2）ごとに 1 行を持つ
- [ ] 5. 出し直しの設計を人の判断待ちの行へ移す前に、出し直しの指摘の項目と「指摘への対応」の表を突き合わせる。表が無い・行の無い項目がある・対応の欄が空の項目があるときは、人に問わずに、届いていない項目を名指しした直して出し直すへ戻す。戻すのは人の出し直し 1 回につき 1 回まで（前提 4）で、上限に達したら届いていない項目を添えて人へ問う（テストで確かめる）
- [ ] 6. 出し直しの指摘を持つ課題の承認ゲート 1 の MVV 判定（`mvv-gate.py check --gate design`）の材料に、出し直しの指摘の全文が入る。判定の問いは、指摘の項目を満たさない設計を「従う」にしないことを含む（テストで確かめる）
- [ ] 7. `references/parallel.md` と `references/loop.md` に、答えの種類（承認・直して出し直す・やらない・予算・止める）ごとに、その答えを読んで動く手順を 1 つずつ示す表がある。両方の文書で同じ表を写さず、片方が正本で、もう片方は正本を指す
- [ ] 8. 出し直しの指摘を持たない課題の設計のプランは変わらない。要求の写しが一致すれば要求のステップを飛ばし、起動指示に指摘の欄が入らない（テストで確かめる）
- [ ] 9. 直して出し直す以外の答え（承認・やらない）を当てたときの、承認の記録・ラベル・人の判断待ちの節の振る舞いは変わらない（既存のテストが通る）
- [ ] 10. `parallel.py answer <計画名> <依頼> --approved` を送ると、持ち主のレーンの次の周回の境で、そのレーンのループの記録の該当する人の判断待ちの行に承認が当たる。レーンの記録が `waiting_only` で止まっていても当たる。設計 PR の先頭が動いて依頼を送り直した後に、送り直す前の依頼へ答えた場合も、取り込みのコミットだけの違い（受け入れ条件 11）なら当たる。当てる行が見つからないときは、答えを捨てずに、依頼の id と理由がオーガナイザーの `parallel.py wait` の出力に出る（テストで確かめる）
- [ ] 11. 設計の承認の依頼を送った後に設計 PR の先頭が動いても、動いた分が取り込みのコミットだけ（前提 7）なら、レーンは依頼を送り直さず、問いの時点の依頼への答えを当てる。設計文書か要求の写しを変えるコミットが含まれるときと、判定できないときは、今どおり新しい先頭で問い直す（テストで確かめる）
- [ ] 12. 計画を始めるときとレーンの周回の境で、前のループ（前提 8）の記録にある答えがまだの人の判断待ちの行が、オーガナイザーの問いの一覧（`parallel.py wait` の `questions`）に、ループの名前・課題・設計 PR を添えて出る。同じ行を 2 回出さない。その問いへの答えは、その行を持つループの記録へ当たる（テストで確かめる）
- [ ] 13. レーンのループが「人の判断待ち」を理由に選定から外した課題は、その待ちを持つ行がオーガナイザーの問いの一覧に出ている（受け入れ条件 12 の行と同じものか、レーン自身の依頼）。問いの一覧に出ていない待ちを理由に外し続けることが無い（テストで確かめる）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 出し直しの指摘を読む処理と、指摘の項目を数える処理は、並列でない開発ループと並列の計画のレーンで 1 つの関数を共有する（Value 7）。取り込みのコミットだけかの判定は 1 つの関数に置き、依頼を送り直すかの判断と答えを当てるかの判断の両方がそれを使う |
| 移行性 | 既にある課題の本文の「人の判断待ち（開発ループ <名>）」の節に残る指摘は移さない。この変更の後に当てた答えから履歴の節へ書く。ループの記録の既存の `note` は、設計のプランの入力として読める。既にある前のループの答えがまだの行は、この変更の後に計画を始めたときか次の周回の境で、問いの一覧に出る |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない。`loop answer`・`parallel.py answer` の引数は今のまま。ループの記録の人の判断待ちの行は欄を足すだけで、既存の欄の意味を変えない。`parallel.py wait` の出力は、当たらなかった答えと前のループの問いの分だけ項目が増える |
| データ | ループの記録（`.ndf/loop/<名>/loop.json`）の人の判断待ちの行に、自分で戻した回数・前の依頼の id などの欄が足りうる（形は設計で決める）。課題の本文に履歴の節が増える |
| 既存の振る舞い | 出し直しの指摘を持つ課題の設計のプランの要求のステップ・起動指示・MVV 判定の材料・人の判断待ちへ移す経路が変わる。設計 PR の先頭が動いたときの依頼の送り直しの条件が変わる。オーガナイザーの問いの一覧に、前のループの待ちが加わる |
