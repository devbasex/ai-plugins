# #1389: 決定の記録・テスト設計・未確認のまま残ること

設計の本体は [issue-1389-design.md](issue-1389-design.md) にある。

## 決定の記録

### 決定 1: 子の認証は環境変数 `CLAUDE_CODE_OAUTH_TOKEN` で渡し、設定ディレクトリは分けない

Claude Code は `CLAUDE_CODE_OAUTH_TOKEN` を設定ディレクトリの `.credentials.json` より優先する（2.1.283 で実測: 共有の
設定ディレクトリのまま変数を足すと、`claude auth status` の `authMethod` が `oauth_token` になる）。環境変数は子孫の
プロセス（`supervise.py`・worker・cross 系の CLI）へそのまま継がれ、設定・プラグイン・hook・会話の記録の置き場は
今のまま変わらない。共有の `.credentials.json` を書き換えないので、別のコンテナの claude のアカウントも変わらない（受け入れ条件 7）。

設定ディレクトリをアカウントごとに分けて `CLAUDE_CONFIG_DIR` で渡す形は採らない。設定ディレクトリには
`.credentials.json` のほかに設定・プラグイン・`projects/`（会話の記録）・`.claude.json` が入る（実測: 空のディレクトリを
渡すと `projectsDirectory` もそこへ移る）。分けると会話の記録が分かれて切り替えた先で `--resume` できず、共有するために
リンクを張ると Claude Code がファイルを足すたびに追随が要る。共有の `.credentials.json` の `claudeAiOauth` を差し替える形は、
同じアカウントグループのすべてのコンテナのアカウントを替えるため採らない。

トークンと一緒に、アカウントのスコープを `CLAUDE_CODE_OAUTH_SCOPES` で渡す（#1523。変数のトークンだけでは Claude Code が
スコープを `user:inference` だけとみなし、claude.ai のコネクタを読まないため。`issues/issue-1523-design.md` の決定 1）。

### 決定 2: 登録は専用の設定ディレクトリで `claude auth login` させ、既存の認証情報を複製しない

`account add` は `CLAUDE_CONFIG_DIR=<置き場>/<名前> claude auth login` を起動する。ログインのたびに独立した許可が発行され、
リフレッシュトークンを持つのは置き場だけになる。共有の `.credentials.json` を写すと同じリフレッシュトークンを 2 か所が
持ち、片方が更新した時点でもう片方のトークンが使えなくなる（更新でリフレッシュトークンが置き換わるため）。

`claude setup-token` の長期トークンを受け取る形は採らない。1 年もつため更新は要らないが、発行の手順が別に要り、
使用量の取得先を読めるスコープを持つかが確かめられていない（要求の未決 2）。`auth login` のトークンは `user:profile` を
含み、使用量の取得先が 200 を返すことを実測した。

### 決定 3: 登録済みアカウントのトークンの更新は NDF が行う

子へ渡すトークンは Claude Code が更新しない（環境変数のトークンは固定の値として使われる）。置き場のリフレッシュトークンを
使えるのは NDF だけなので、NDF が更新する。渡す直前に期限の 60 分前を切っていれば更新し、アカウントごとの排他の中で
書き戻してから使う（I5）。更新で古いアクセストークンが失効するかは未確認のため、`supervise.py` は動いている区間のアカウントを更新せず、
更新は区間の起動（カットポイントを含む）と、動いている区間が使っていないアカウントを渡すときに限る（I9 と両立させる）。更新の宛先は Claude Code 自身が使うもの（2.1.283 の本体に含まれる）を使う。

専用の設定ディレクトリで `claude auth status` を打って Claude Code に更新させる形は採らない。そのコマンドが期限切れの
トークンを更新するかは確かめられず、確かめるには実際のリフレッシュトークンを消費する。

### 決定 4: 置き場は共有の設定ディレクトリの下（`${CLAUDE_CONFIG_DIR:-~/.claude}/ndf/accounts/`）に置く

devbase では `~/.claude` が同じアカウントグループのコンテナで共有・永続化される。登録は利用者の対話（ブラウザでの認可）を
要するため、コンテナごとに求めると手間が増える。ラッパーの複製（`~/.claude/ndf/relay.py`）と同じ親に置き、利用者が
1 か所を見れば済むようにする。排他（`lib/locks.py`）は同じ親のファイルで取るため、コンテナをまたいだ更新も並ばない。

`${XDG_DATA_HOME:-~/.local/share}` に置く形は採らない。devbase では永続化されず、コンテナの作り直しで登録が消える。

### 決定 5: 登録が 2 つ以上なら、区間 1 から登録済みアカウントで起動する

今のアカウントが常に登録済みの 1 つになり、定期の確認は置き場のトークンで今のアカウントを読める。区間 1 を利用者の
既定のログインで起動すると、今のアカウントの残量を読むには共有の `.credentials.json` のトークンを使うことになり、
I4（読まない・書かない）を破る。読まずに済ませると、区間 1 だけ閾値による切り替えが働かない。

登録が 1 つ以下なら、区間 1 も以後も今と同じ環境で起動する（受け入れ条件 9）。

### 決定 6: 上限の検知は `StopFailure` hook のシグナルファイルと会話の記録で行う

Claude Code は応答が API の失敗で終わると、`Stop` の代わりに `StopFailure` を発火する（2.1.283 の本体の説明と、無効な
トークンでの実測。入力に `error`・`transcript_path`・`session_id` がある）。hook の出力は無視されるが、ラッパーへ知らせる
だけなら足りる。種類とリセット時刻は、シグナルファイルが指す会話の記録の最後の合成応答（`quotaLimits`）から読む。
`transcript_agents.py` が既に同じ値を読んでいる。

ラッパーが常に会話の記録を走査する形は採らない。`ndf-next` のシグナルファイルが無い間は、ラッパーは子の会話の記録の場所を
知らない。画面の出力を照合する形は、端末の描画に左右されるため採らない。

### 決定 7: 上限の後の区間は、同じ会話を `--resume` で開き、未達の `/goal` を入れ直す

上限で止まった会話には、作業の途中の文脈が残っている。新しい会話で `/goal` の条件だけを渡すと、途中まで進めた作業を
conductor が探し直す（例の 5 の約 30 分）。`--resume` は会話の記録（ローカルのファイル）から開くため、アカウントを替えても
開ける見込みが高い（未確認のまま残ること）。`/goal` の条件は `goal_status` の添付の `condition` にあり、`--resume` が
目標を戻すかに関わらず入れ直せば同じ状態になる。

`ndf-next` のシグナルファイルがあるときは、それが次の区間の入力として作られたものなので優先する。

### 決定 8: 上限の後も、背景の作業が残っている間は子を終えない

背景の作業（プラン・待ちの Bash・`ScheduleWakeup`）が残ったまま `/exit` すると、Claude Code が選択肢を出して止まる
（`relay_lib/claude.py` の `pending_wakeups` を足した理由と同じ）。背景のプランは worker の呼び出しで自分でアカウントを
替えて進むため（F7）、conductor が待つ間も作業は止まらない。作業が終わると conductor が起こされ、また上限シグナルファイルが来るので、
そこで判定し直す。読めないときを「残っている」とするのは、誤って終えるとプランが途中で止まり、戻せないためである。

### 決定 9: 定期の確認は今のアカウントだけを 300 秒ごとに読み、閾値の既定は 90% とする

要求の性能の条件（1 アカウントにつき 5 分に 1 回まで）の上限をそのまま間隔にする。他のアカウントは選ぶ直前にだけ読む
（間隔の中なら保存した値）。閾値の 90% は、残りの 10 ポイントを次のカットポイントまでの余白とする見込みで置く。
使用率の増え方を測った値は無く、見込みが足りるかは未確認のまま残す。閾値を下げると、使える量を残したまま替える回数が増える。

確認は別スレッドで行う。中継の繰り返しの中で取得すると、取得先が遅いときに子の出力が止まる（性能の条件）。

### 決定 10: `supervise.py` は登録済みアカウント → `NDF_SUPERVISE_CLAUDE_FALLBACK` → 上限待ちの順に試す

登録済みアカウントは利用者の subscription で、追加の費用が掛からない。`NDF_SUPERVISE_CLAUDE_FALLBACK` は API キーなどの
従量の接続を渡すのに使われうるため、費用の掛からない経路を先に使い切る。登録が 1 つ以下なら FALLBACK の意味と順序は
今と同じである（前提 7）。

**登録が 2 つ以上のとき、FALLBACK は「すべて上限のときに移る従量の接続」の宣言として読む（決定 14）。**
順序は変えない。変わるのは移った後で、同じプランの以後の呼び出しも従量の接続で起動し、起動のたびに
登録済みアカウントが上限を外れたかを確かめて戻る（呼び出しごとに上限のアカウントを試し直して 429 を
受け直さない）。登録が 1 つ以下なら、今と同じく呼び出しごとに 1 度だけ試す。

### 決定 11: 残量は最新の 1 件だけを上書きで持つ

残量は選ぶときと一覧のときに最新の値だけを使い、過去の値を比べる機能が無い。何がいつ起きたかは、切り替えの行
（`log.jsonl` の `account`・プランの `auth`）が時刻と理由とともに残す。上限の観測も最後の 1 件だけを持ち、リセット時刻を
過ぎたら読む側が無視する。

### 決定 12: 切り替えに LLM を使わない

選び方は 2 つの数の最大と比較で決まり、上限の種類は記録の値で読める。LLM に判断させる余地が無く、呼べば
費用と失敗の経路が増える。受け入れ条件 8 はこの決定で満たす。

### 決定 13: 置き場の読み書きと選び方は `lib/claude_accounts.py` の 1 つに置く

ラッパーと `supervise.py` が同じ選び方・同じ排他・同じ取得の間隔を使うためである（要求の「前提とする取り決め」）。
`relay_lib/` に置くと `supervise_lib/` から読む経路が無く、`supervise_lib/` に置くとラッパーの複製（バージョンディレクトリ）に
入らない。`lib/` に置き、ラッパーの複製の対象（`LIB_FILES`）に足す。部品は標準ライブラリと `lib/locks.py` だけを読み、
通信は `urllib` で行う（新しい依存を足さない）。

### 決定 14: すべて上限のときは宣言された従量の接続へ移り、上限が外れたアカウントへ次の起動で戻す（セーフティネット）

承認ゲート 1 での利用者の指示（要求の前提 8）による。

**宣言は既存の `NDF_SUPERVISE_CLAUDE_FALLBACK`（`KEY=VALUE` を空白区切り）をそのまま使い、ラッパーも読む。**
読む関数（今の `supervise_lib/claude.py` の `fallback_env`）を `lib/claude_accounts.py` へ移し、ラッパーと
`supervise.py` が同じものを呼ぶ（決定 13）。環境変数はラッパー → conductor → `supervise.py` へ継がれるので、利用者が
シェルで 1 度設定すれば両方に届く。宣言の例（値は利用者が持ち、リポジトリには書かない）:

```bash
export NDF_SUPERVISE_CLAUDE_FALLBACK='CLAUDE_CODE_USE_BEDROCK=1 AWS_PROFILE=<名前> AWS_REGION=us-east-1 ANTHROPIC_DEFAULT_OPUS_MODEL=<モデル>'
export NDF_SUPERVISE_CLAUDE_FALLBACK="ANTHROPIC_API_KEY=$(<秘密の仕組みから読む>)"
```

新しい名前の変数や設定ファイルを足す形は採らない。宣言が 2 つになり、片方だけ直した食い違いが起きる。
変数の名前に `SUPERVISE` が残るが、既存の利用者の設定を変えずに済むほうを取る。共有の `~/.claude/settings.json` の
`env` に Bedrock を書く形（この環境の `settings.json.bak-bedrock-*` の形）も採らない。`~/.claude` は同じアカウント
グループのコンテナで共有されるため、すべての claude が従量の接続へ移る（受け入れ条件 7 と同じ理由）。

**環境は混ぜない。** 従量の接続で起動する子の環境は、宣言の変数を足し、`CLAUDE_CODE_OAUTH_TOKEN` を外し、
`NDF_CLAUDE_ACCOUNT=metered`（予約の名前。`account add` は拒む）とする。登録済みアカウントで起動する子の環境は、
宣言のキーを外してからトークンを足す（従量の接続で動いた conductor から起動したプランは、宣言の変数を継いでいる）。
2.1.283 の `claude auth status`（推論を呼ばない）で、`CLAUDE_CODE_USE_BEDROCK=1` は `CLAUDE_CODE_OAUTH_TOKEN` があっても
`apiProvider: bedrock` を返した。`ANTHROPIC_API_KEY` と `CLAUDE_CODE_OAUTH_TOKEN` を両方持つと `authMethod: oauth_token`・
`apiKeySource: ANTHROPIC_API_KEY` を返し、推論にどちらを使うかは読めなかった。混ぜなければ、どちらが優先されても
意図した接続で動く。

**移る時点は、登録済みアカウントの選び方（`choose`）が候補を返さなかった時点である。** ラッパーは区間の起動（区間 1 を
含む）と上限の後の切り替え（F5）、`supervise.py` は登録済みアカウントを試し尽くした時点（決定 10）。背景の作業が残っている
間は子を終えない（決定 8）のは同じである。

**戻るのは、次のカットポイント（ラッパー）と次の claude -p の起動（`supervise.py`）である。** 従量の接続で動いている間、
ラッパーの定期の確認は今のアカウントの代わりに登録済みのすべてのアカウントを読む（1 アカウントにつき I6 の間隔を守る。
推論は呼ばない）。`choose` が候補を返し、その `score` が切り替えの閾値未満なら戻す予定を立てる。閾値以上のアカウントへ
戻すと、すぐ閾値による切り替えでまた移るためである。`supervise.py` は起動のたびに `choose` を呼ぶ（保存した残量を使い、
間隔の中なら取得先を呼ばない）。上限の観測はリセット時刻を過ぎると無視されるため、取得先が使えなくてもリセット時刻の後に
戻れる。作業の途中で子を終えて戻す形は採らない（前提 6・決定 8）。戻りを待つ間は従量の費用が掛かり続ける。

**登録が 1 つ以下なら、ラッパーはセーフティネットを持たない（受け入れ条件 9）。** 区間 1 を登録済みアカウントで起動しない
（決定 5）ため、今のアカウントの残量を読めず（I4）、戻る判定ができない。`supervise.py` は今の FALLBACK のまま（決定 10）。

**宣言が無ければ、すべて上限のときは今と同じ**である（ラッパーは受け入れ条件 4、`supervise.py` は上限待ち）。従量の接続でも
上限か失敗に当たったら（Bedrock の絞り込み・認証の失敗など）、ラッパーは 1 行を出して子を残し、`supervise.py` は今と同じ
上限待ちに入る。切り替えに LLM を使わないこと（決定 12）は変わらない。

| I3 | 同じメールと組織で 2 つ目を `add` すると 1 で終わり、作りかけのディレクトリが残らない。組織が違えば登録できる | 重複の確かめを外すと落ちる |
| I5 | 2 つのプロセスが同時に同じアカウントを更新すると、更新の宛先は 1 度だけ呼ばれ、両方が同じ新しいトークンを使う | 排他を外すと宛先が 2 度呼ばれて落ちる |
| I5（動いている区間） | `NDF_CLAUDE_ACCOUNT` のアカウントが期限の 60 分前を切っていても、`supervise.py` は更新の宛先を呼ばない。期限を過ぎていれば別のアカウントでやり直す | プランの中で動いている区間のアカウントを更新すると落ちる |
| I6 | 間隔の中で一覧・選び方・定期の確認を繰り返しても、取得先の偽物は 1 アカウントにつき 1 度しか呼ばれない。別のプロセスの取得も数える | `fetched_at` を見ないように壊すと落ちる |
| I7 | 選び方の表のテスト（使用率・上限の観測・支出上限・残量不明・再登録が要る・リセット時刻の同点）で、期待の名前を返す | 並んだときの規則を逆にする・残量不明を常に候補にすると落ちる |
| I9 | 切り替えの判定が動いている間、子へ何も書かない（`/exit` を除く）。worker の呼び出しの途中で環境を替えない | 閾値を超えた時点で子へ入力を書くと落ちる |
| I11 | 会話の記録に終わっていない背景の Tool の呼び出しがあると、上限シグナルファイルでも `/exit` を書かず、1 行を出してシグナルファイルを残す。終わりの通知の行が来た後のシグナルファイルで切り替わる | 背景の作業を見ないように壊すと落ちる |
| I15 | `Relay` が読んだ後に hook が `limit.json` を書き直すと、`Relay` はそのファイルを消さない。利用者の入力の後の読み捨ても、読んだ内容と同じときだけ消す | 内容を比べずに消すと落ちる |
| I12 | 切り替えごとに `log.jsonl` に `account` の行が 1 つ増え、時刻・理由・前後の名前がある | 行を書かない・理由を落とすと落ちる |
| 受け入れ条件 12・I16 | すべてのアカウントが上限で、宣言に `CLAUDE_CODE_USE_BEDROCK=1` があると、ラッパーは次の区間を宣言の変数を足し `CLAUDE_CODE_OAUTH_TOKEN` を外した環境で `--resume` 付きで起動し、1 行と `log.jsonl` の `to: "metered"` の行を出す。`supervise.py` は同じ呼び出しを同じ環境でやり直し、`cur["auth"]` に `従量の接続` と変数の名前が残る。宣言の値（偽のキーの文字列）は `log.jsonl`・画面・子の引数に現れない | 移るときにトークンを残す・値を記録へ書く・宣言があるのに子を残すと落ちる |
| 受け入れ条件 13・I17 | 従量の接続で動く間、取得先の偽物が 1 つのアカウントの上限の解除を返すと、ラッパーは次の `ndf-next` の区間をそのアカウントの環境（宣言のキーを外す）で起動し、`reason: "recovered"` の行を出す。カットポイントの前には `/exit` を書かない。`supervise.py` は次の呼び出しをそのアカウントで起動する。解除されたアカウントの使用率が閾値以上なら戻さない | 戻さない・カットポイントの前に `/exit` する・宣言のキーを残したまま戻すと落ちる |
| 受け入れ条件 13（取得先が使えない） | 取得先の偽物が常に失敗しても、上限の観測のリセット時刻を過ぎた後の次の起動で戻る | 戻りを取得先の成功だけで判定するように壊すと落ちる |
| 受け入れ条件 14・9 | 宣言が無いとき、すべて上限の振る舞いが今と同じ。登録が 1 つ以下なら、宣言があってもラッパーは何もせず、`supervise.py` は呼び出しごとに 1 度だけ FALLBACK を試す | 宣言が無いのに移る・登録 1 つで従量の接続へ移ると落ちる |
| 性能の条件 | 取得先の偽物が 30 秒応答しなくても、子の出力の中継が止まらない | 取得を中継の繰り返しの中で行うように壊すと落ちる |

**実測（1 回）:** 2 つのアカウントを登録し、一覧が推論を呼ばずに出ること・片方で上限（または閾値）に当たったときに
もう片方で次の区間が起動することを確かめる。受け入れ条件 7 は、別の設定ディレクトリ（別のコンテナか `CLAUDE_CONFIG_DIR`）で
起動した claude の `auth status` のメールが、切り替えの前後で同じことを見る。

## 未確認のまま残ること

| 項目 | 内容 | いつ決まるか |
| --- | --- | --- |
| トークンの更新の要求の形 | 宛先は本体から読んだが、要求の項目（`client_id` など）と応答の形は確かめていない。確かめると実際のリフレッシュトークンを消費する | 実装で、登録したアカウント 1 つで 1 回確かめる |
| 更新で古いアクセストークンが失効するか | トークンを更新すると、動いている claude が環境変数で持つ古いアクセストークンが失効するかは確かめていない。設計は失効する側に倒し、動いている区間のアカウントをプランが更新しない（I5） | 実装で、登録したアカウント 1 つで更新の前後に古いトークンで推論を 1 回呼んで確かめる。失効しなければ I5 の条件を外せる |
| 支出上限の会話の記録 | 支出上限の合成応答が `quotaLimits` を持つか、`error` が `rate_limit` か `billing_error` かは実物を見ていない（本文の文言だけが例にある）。設計はどちらでも本文で `spend` と読む | 実装で、実物が採れれば写しをテストへ足す |
| 共有の `.claude.json` と別のアカウントのトークン | 共有の `.claude.json` の `oauthAccount` が既定のログインのまま、別のアカウントのトークンで推論が通るか | 実測（2 つのアカウント）で確かめる。通らなければ設計へ戻す |
| `--resume` をアカウントをまたいで使えるか | 会話の記録はローカルにあるが、アカウントをまたいだ再開を実物で見ていない | 実測で確かめる。開けなければ `/goal` の条件か定型の文で新しい会話を始める |
| 背景の作業の読み取り | 終わりの通知の行の形（`task-notification`）と Tool の呼び出しの対応づけは、実装で会話の記録の写しから決める | 実装（`tdd-cycle`） |
| 使用量の取得先の形 | 公開の文書が無く、項目が変わりうる。変わったら残量不明として扱い、上限の後の切り替えだけが働く | 形が変わったとき |
| Bedrock の接続で動くか | 宣言が Bedrock のとき、ラッパーの子（対話の claude）と `claude -p` の推論が通るかは確かめていない。2026-09-28 にこのコンテナで確かめようとしたが、`AWS_PROFILE`（`carmo-dev`）の設定が無く（`aws sts get-caller-identity` が `could not be found`）、推論を呼べなかった。`claude auth status` が `apiProvider: bedrock` を返すことだけを見た（推論なし） | 実装で、AWS の認証がある環境で `claude -p` を 1 回呼んで確かめる |
| 接続をまたいだ `--resume` | subscription のアカウントで始めた会話を、Bedrock か API キーの接続で `--resume` で開けるか（逆も）は確かめていない。会話の記録の置き場（`projectsDirectory`）は接続を替えても変わらないこと（`auth status` の出力）だけを見た。Bedrock ではモデルの名前（`ANTHROPIC_DEFAULT_*_MODEL`）が違う | 実測で確かめる。開けなければ、移るときと戻るときは `/goal` の条件か定型の文で新しい会話を始める |
| 対話の claude と `ANTHROPIC_API_KEY` | 対話の claude に `ANTHROPIC_API_KEY` を渡したとき、Claude Code がキーを使うかの確認を出して止まるかは確かめていない。出るならラッパーの子が入力待ちで止まる | 実装で、API キーを持つ環境で 1 回確かめる。止まるなら宣言が API キーのときラッパーは移らず、`supervise.py`（`claude -p`）だけが移る形へ設計を戻す |
| `ANTHROPIC_API_KEY` と OAuth のトークンの優先 | 両方を持つと推論にどちらを使うかは `auth status` から読めなかった。設計は混ぜない（決定 14）ので、確かめなくても成り立つ | 確かめない |
| 従量の接続の上限・失敗の形 | Bedrock の絞り込み（`ThrottlingException`）や認証の失敗が、`StopFailure` の `error` と `claude -p` の結果でどう出るか、利用上限と区別できるかは確かめていない | 実装で、会話の記録の写しが採れればテストへ足す |
| 戻りを待つ間の費用 | 戻りをカットポイントまで待つため、カットポイントが長く来ないと従量の費用が掛かり続ける。どれだけ掛かるかは測っていない | 使った結果（`log.jsonl` の `metered` と `recovered` の行の間隔）で見直す |
| 閾値と間隔の既定 | 90% と 300 秒が、上限の前に替えるのに足りるか | 実測の後、`docs/ndf-experiments.md` と同じく使った結果で見直す |
