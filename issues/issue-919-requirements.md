# #919: cross-review / cross-refactoring: 結果を残さなかった担当を別のランタイムへ振り替える規則が無く、2 度目の結果なしと利用上限で収束が止まる

正は課題の本文（#919）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

親 issue: #1290（修正レイヤー: `plugins/ndf/scripts/lib/assignment.py` の担当の選択。振り替えの規則はここに置き、`judge.py` と `monitor_outcome.py` からは判断を移す）

## 何を見つけたか

cross-review / cross-refactoring の担当が結果を残さずに終わった（監視が `NO_RESULT` を返した）とき、今の規則は**同じ席・同じランタイムで 1 度だけ起動し直す**だけである。2 度目も結果が無いときと、理由が `usage_limit` のときは `final = error` で止まり、収束のループが進まない。

別のランタイムへ振り替える仕組みは無い。

```console
$ grep -rn "振り替\|代わりの担当\|別の担当へ" plugins/ndf/skills/cross-review/scripts plugins/ndf/skills/cross-review/docs/*.md plugins/ndf/skills/cross-review/SKILL.md
（0 件）
```

手元の記録では、結果なしは #794 の agy 1 件と、#819 の codex 2 件（利用上限）だった。回避は状態ファイルの手編集（`only` を別の担当へ、`final` を `null` へ）である。

## どこで見つけたか

- `plugins/ndf/skills/cross-review/scripts/review_lib/commands/judge.py` の `_handle_no_result_round`（`:81`。起動し直しは同じ席で 1 度だけ。2 度目と起動し直しても解けない理由は `_abort_no_result_round`（`:57`）で `final = error`）
- `plugins/ndf/scripts/lib/monitor_outcome.py` の `NO_RELAUNCH_REASONS = frozenset({"usage_limit"})`（`:58`）と `relaunch_same_agent`（`:110`）
- `plugins/ndf/skills/cross-review/scripts/review_lib/participants.py` の `participants.fallback` は常に空（`:297`。説明は `:260`）。`plugins/ndf/scripts/lib/assignment.py` の `review_seats`（`:274`）は fallback を受ける形をすでに持つ
- #786 の「対処の候補と置き場所」（振り替えは drive が `no_result` を受けた地点、と候補に挙がっている。`cross-review/scripts/drive.py` は振り替えを扱っていない）

## なぜこの変更の範囲外なのか

#542 #786 の設計（issue #542 / issue #786、決定 9）は、cross-review の既定の母集合から agy を外すことで #786 に対処し、振り替えは含めないと決めた。振り替えの規則（いつ・誰へ・何回、利用上限のときに同じ実行の中で再び当たらないか）は、母集合の既定とは別の判断になるため。

## 直さないと何が起きるか

- `--include agy` で agy を戻したとき、または codex / kiro / claude が利用上限や無進捗で結果を残さなかったとき、収束のループが `final = error` で止まり、状態ファイルの手編集が要る
- cross-refactoring でも同じ群が同じ担当へ割り当て直され、手で担当を差し替えるまで進まない（#786 の本文）

# 要求と受け入れ条件

## 依頼（原文）

> この課題の本文の「何を見つけたか」「直さないと何が起きるか」と、追記の「この課題の振り替えの規則には、実装担当が利用上限で落ちたときの扱い（別のアカウントか別のランタイムへ振り替えるか・未確認の項目から再開するか）も含める。」
>
> 親 #1290 の修正方針: 「散った選び方と振り替えの規則を `lib/assignment.py` へ統合し、呼ぶ側（`worker_steps.py`・`monitor_outcome.py`・`cross-review` / `cross-refactoring`）からは判断を移す。」

## 目的

- cross-review / cross-refactoring の担当が結果を残さなかったとき（利用上限・起動し直した後の 2 度目の結果なし）に、状態ファイルを手で編集しなくても、別の担当へ振り替えて実行が先へ進む
- 「同じ担当で起動し直すか・誰へ振り替えるか」の規則を `plugins/ndf/scripts/lib/assignment.py` の 1 か所に置き、2 つの Skill が同じ規則で動く（親 #1290）

## 前提

決められない点を、後から成否を判定できる文にした。誤っても局所的に直せるため、人へ問わずに前提として置く。

- 前提 1: 振り替え先の候補は、その実行で「利用可能な参加者」（`resolve_participants` が認証確認を通した者。`.ndf/runtimes.json` の宣言があれば `allowed` の内側）だけである。母集合の外の者（既定で外れている agy など）を振り替えのために足さない
- 前提 2: 利用上限（理由 `usage_limit`）に当たった担当は、上限が解ける時刻に関わらず、**同じ実行の残りでは割り当てない**。解ける時刻を待って戻す仕組みは持たない
- 前提 3: 起動し直しても 2 度続けて結果を残さなかった担当も、同じ実行の残りでは割り当てない
- 前提 4: claude の担当が利用上限に当たり、利用者が登録したアカウント（`claude_accounts` の置き場。#1389・#1576）に使えるアカウントが残っていれば、**別のランタイムより先に、別のアカウントの claude へ振り替える**。アカウントは既存の選び方（`claude_accounts.choose` / `account_env`）で選び、子へは `CLAUDE_CONFIG_DIR` だけを渡す。登録が無いか使えるアカウントが残っていなければ、別のランタイムへ振り替える。アカウントへの振り替えは利用上限のときだけで、それ以外の結果なしでは行わない
- 前提 5: `--only`（1 者指定）では振り替えない。今の決定 9（1 者指定はフォールバックをしない）を保つ
- 前提 6: 固定の組（`.ndf/runtimes.json` の `review_seats`）の片方が振り替えの対象になったら、その実行の残りでは固定の組を使わず、今の表の規則（`review_seats` の n 別の規則）へ戻る。固定の組のランタイムが使えないときの今の振る舞いと同じである
- 前提 7: 実装担当の振り替えでは、採用済みの改善項目を残し、**未確認の改善項目から続ける**。結果を残さなかった起動の範囲は、今の `close_without_result` のとおり取り消してから振り替える
- 前提 8: 振り替えの回数の上限は「候補が尽きるまで」とし、別の数値の上限は置かない。候補は前提 2・3 で減るだけなので、1 回の実行の振り替えは参加者の数（アカウントを含む）を超えない
- 前提 9: 提案担当（cross-refactoring の `propose`）の一部が結果を残さなくても、残りの提案で続く今の振る舞いを保つ。提案担当の全員が結果を残さなかったときだけ振り替えの対象にする

## 対象範囲

含む:
- cross-review のレビューの席が結果を残さなかったときの振り替え（利用上限・起動し直した後の結果なし）
- cross-refactoring の実装担当（計画・テスト追加・実装・修正・最終ゲート修正）が結果を残さなかったときの振り替えと、未確認の改善項目からの続行
- cross-refactoring の提案担当が全員結果を残さなかったときの振り替え
- 利用上限に当たった担当を同じ実行の残りで割り当てない記録（状態ファイル）
- claude の担当の、別のアカウントへの振り替え（前提 4）
- 振り替えの規則の正本を `plugins/ndf/scripts/lib/assignment.py` へ置き、`judge.py` / `monitor_outcome.py` / cross-refactoring の呼ぶ側から「誰へ振り替えるか」の判断を移すこと
- 振り替えの事実（誰から誰へ・理由・ラウンドか工程）を状態ファイルと報告に残すこと

含まない:
- 担当の輪番と統計による選択（#760。親 #1290 のもう 1 つの子）
- supervise.py の worker の担当の選択（`worker_steps.py`。#760 の側）
- cross-review の既定の母集合の変更（#542 / #786 の決定 9 のまま。agy は既定で入れない）
- 利用上限が解ける時刻を読んで、同じ実行の中で担当を戻すこと（前提 2）
- 監視が理由を決める文言の照合（`usage_limit` の検出）の変更
- アカウントの登録・使用量の取得の仕組みの変更（`claude_accounts.py` は使うだけ）
- codex / kiro / agy の複数アカウントへの振り替え（アカウントの仕組みが claude にしか無い）

## 用語

| 用語 | 意味 |
| --- | --- |
| 担当 | レビュー・提案・実装を受け持つ CLI の起動の単位。ランタイム（claude / codex / kiro / agy）と、claude ではアカウントで決まる |
| 席 | cross-review の 1 ラウンドの 2 つの担当の枠。名前は `kiro` / `kiro-2` の形（`SEAT_PATTERN`） |
| 結果なし | 担当が結果ファイルを残さずに終わったこと（judge の `verdict = no_result`、cross-refactoring の `failed_attempts`） |
| 利用上限 | 担当の CLI が使用量の上限に当たって止まったこと（監視の理由 `usage_limit`） |
| 振り替え | 結果なしの担当の役割を、同じ実行の中で別の担当へ移すこと。同じ担当で起動し直すことは含まない |
| 実装担当 | cross-refactoring の計画・テスト追加・実装・修正・最終ゲート修正を通す 1 者（`choose_implementer`） |
| 提案担当 | cross-refactoring の `propose` で提案を出す参加者 |
| 未確認 | 取り消されずに残ったが、最終ゲートが passed になっていない改善項目の状態（用語集の既存の語） |

## 受け入れ条件

振り替えの規則（`lib/assignment.py`）:

- [ ] AC1: 「結果なしの担当・理由・その実行で利用可能な参加者・既に外した担当・起動し直し済みか」を受け、「同じ担当で起動し直す / 振り替え先 / 中断」のどれかを返す関数が `plugins/ndf/scripts/lib/assignment.py` に 1 つあり、`plugins/ndf/scripts/tests/test_lib_assignment.py` の単体テストで次の組を確かめる
  - 理由が `usage_limit` 以外で起動し直していない → 同じ担当で起動し直す
  - 理由が `usage_limit` → 起動し直さず、振り替え先を返す
  - 起動し直した後も結果なし → 振り替え先を返す
  - 既に外した担当と、今のラウンドのもう一方の席のランタイムは、振り替え先にならない
  - 候補が尽きた → 中断
- [ ] AC2: 利用上限で外したランタイムは、その `-2` の席（`kiro-2` など）を含めて振り替え先にならない
- [ ] AC3: 振り替え先は利用可能な参加者（前提 1）の中だけから選ばれ、`.ndf/runtimes.json` の `allowed` の外の者・母集合の外の者を返さない
- [ ] AC4: claude の担当が利用上限に当たり、使えるアカウントが別に 1 つ以上あれば、振り替え先は別のアカウントの claude になる。使えるアカウントが無ければ別のランタイムになる。理由が `usage_limit` 以外のときはアカウントへ振り替えない
- [ ] AC5: `judge.py`・`monitor_outcome.py`・cross-refactoring のコマンドに、振り替え先・リトライ可否を自分で決める分岐が残らない（3 か所はいずれも AC1 の関数の答えに従う）。`monitor_outcome.py` は理由の語彙と起動結果の読み書きだけを持つ

cross-review:

- [ ] AC6: レビューの席の 1 つが利用上限で結果を残さなかったとき、利用可能な参加者が 3 者以上なら、同じラウンドの中でその席を別のランタイムへ振り替えて judge が先へ進み、`final = error` にならない（駆動 `drive.py` を通す結合テストで確かめる）
- [ ] AC7: 起動し直した後も結果を残さなかった席も、AC6 と同じく振り替えて先へ進む
- [ ] AC8: 利用上限で外したランタイムは、同じ実行の以後のラウンドで席に選ばれない（状態ファイルに外した担当と理由が残り、ラウンドの席の選択がそれを読む）
- [ ] AC9: 振り替え先が無い（利用可能な参加者が尽きた・`--only` の 1 者指定）ときは、今と同じく `final = error` で止まり、メッセージに試した担当と理由が並ぶ
- [ ] AC10: judge の出力の行に、振り替えの事実（`REASSIGNED` の形の 1 行。元の席・振り替え先・理由）が出る。既存の行（`NO_RESULT_REASONS` / `RELAUNCH_AGENTS` / `RELAUNCH_AGENTS_CSV` / `RELAUNCH_TARGET`）の形と意味は変わらない

cross-refactoring:

- [ ] AC11: 実装担当が利用上限で結果を残さなかったとき、結果なしの起動の範囲を取り消した後、AC1 の振り替え先を実装担当として同じ工程を未確認の改善項目から続け、採用済みの項目は取り消さない
- [ ] AC12: 実装担当の振り替えは、リファクタリング計画の後でも止まらない（今の「リファクタリング計画の後なら止める」は再開で参加者を作り直したときの規則として残し、同じ実行の中の振り替えには当てない）
- [ ] AC13: 最終ゲート修正の実装担当が利用上限で結果を残さなかったとき、`no_relaunch` で打ち切る前に振り替え先を試す。振り替え先が無いときだけ今の打ち切りになる
- [ ] AC14: 提案担当の全員が結果を残さなかったとき、利用可能な参加者に、提案を出していない担当が残っていれば、その担当へ振り替えて提案を集める。一部だけが結果なしなら今のとおり残りの提案で続く（退行しない）
- [ ] AC15: 振り替えの事実（工程・試行番号・元の担当・振り替え先・理由）が状態ファイルの `failed_attempts` と並ぶ記録に残り、結果 JSON の `metrics` に振り替えの回数が出る
- [ ] AC16: PR #1673 と同じ状況（実装担当 claude が実装の工程で利用上限）を再現するテストで、手で状態を退避して流し直さなくても、振り替え先が未確認の改善項目を引き継いで最終ゲートまで進む

退行しないこと:

- [ ] AC17: 結果なしが起きない実行では、席・実装担当・状態ファイルの形・終了コードが今と同じである（既存のテストがそのまま通る）
- [ ] AC18: 理由が `usage_limit` 以外の 1 度目の結果なしは、今と同じく同じ担当で 1 度だけ起動し直す
