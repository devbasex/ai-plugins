# #1482: 決定の記録

設計の本体は [issue-1482-design.md](issue-1482-design.md) にある。ここには、選んだ結論と理由と採らなかった案だけを置く。

## 決定 1: 取り消しの判定を `refactor_lib/ledger.py` に新しく置き、git を書き換えない関数だけにする

取り消しの範囲・積み直しの対象・push してよいコミットは、どれも「このコミットは残すコミットか」という同じ問いへの
答えから導ける。今はこの答えを `undo._owner`・`implement._group_by_item`・`intake.discard_unverified`・
`converge._apply_fix_result` が別々に出している。push の直前には誰も出していない。答えを出す関数を 1 つのモジュールに
置き、取り消しの経路と push の経路の両方から呼ぶ。

判定のモジュールは git を書き換えず、終了もしない。書き換えと終了は `undo.py`（取り消し）と `publish.py`（公開）が持つ。
判定を純粋に保つと、再現手順のテストを git の書き換えなしで組める。

判定を `undo.py` の中へ置く案は採らない。`publish.py` が `undo.py` を読むことになり、公開が取り消しの内部に依存する。
`commands/` に置く案も採らない。複数のコマンドが読む層であり、`intake.py` の冒頭の取り決め（`commands` どうしの
取り込みを作らない）に反する。

根拠: Value 6 / Value 4（MVV 版 2）

## 決定 2: 未公開のコミットは積み直しの起点へ `reset` して残すコミットだけを積み直し、公開済みのコミットだけを `revert` する

要求の未決「push 前の手元の履歴を組み直す方式」への答えである。

最終ゲートより前には push しない（要求の前提 1）ため、最終ゲートより前の取り消しでは、起点から HEAD までの
コミットはすべて未公開である。未公開のコミットは、`reset --hard` で外して残すコミットだけを `cherry-pick` し直せば、
revert のコミットを 1 つも作らずに取り消せる。前の取り消しの積み直しのコミットは、元のコミットを置き換えた
「残すコミット」として扱われるだけなので、取り消しを何度くり返してもコミット数は伸びない（AC-1399-1・AC-1399-2）。
worktree の内容は「起点に残すコミットを古い順に当てた内容」に定義どおり一致する（AC-1399-3）。

公開済みのコミット（最終ゲートの後の取り消し。寄せた危険フラグの項目など）は書き換えない（要求の前提 5・共通原則 C4）。
取り消す改善項目のコミットだけを新しい順に `revert` する。各コミットは取り消しで 1 度しか戻らないため、
`revert` の数は改善項目のコミットの数を超えない。

`reset --hard` は push していない手元のコミットだけに掛かり、外したコミットは reflog に残る。共通原則 C4 の
「戻せない操作」（push 済みの履歴の書き換え・強制 push）に当たらない。

取り消す項目のコミットだけを `revert` する案は、最終ゲートより前には採らない。取り消す項目より新しい項目が同じ箇所を
触っていると必ず衝突し（`undo.py` の冒頭の実測）、未公開なのに revert のコミットを積むことになる。
今の「範囲全体を逆再生して積み直す」方式は採らない。範囲に前の取り消しの revert と積み直しが入り、取り消しのたびに
対象が約 2 倍になる（#1399 の 54 → 1043、#1237 の 5 → 25）。

根拠: Value 6 / C4（MVV 版 2）

## 決定 3: オーケストレーターのコミットは状態ファイルに SHA で記録して見分ける

要求の未決「オーケストレーターが作ったコミットを見分ける手段」への答えである。

オーケストレーターが作ったコミットの完全な SHA を `ledger.orchestrator_commits` へ足す。同期・リファクタリング計画の
記録のコミットは作った直後に、公開済みの取り消しの `revert` は取り消しの記録の時点に足す。改善項目のコミットも、今と同じく状態ファイルに記録した SHA で見る。
残すかどうかは SHA の一致だけで決まり、コミットの中身（トレーラー・件名）には依らない。

コミットのトレーラーで示す案は採らない。トレーラーは実装担当の CLI も書ける。見放した担当の残留コミットが
オーケストレーターのトレーラーや採用済みの項目の `Item-Id` を書けば、照合を通ってしまう。また `git revert` と
`cherry-pick` は元のトレーラーを引き継がず、付け直す手順が要る。

根拠: Value 6（MVV 版 2）

## 決定 4: 受け入れた最終ゲート修正のコミットを「残すコミット」に含める

要求の前提 3 は、公開してよいコミットを (a) 取り消されていない改善項目のコミットと (b) オーケストレーターが作った
コミットの 2 種類とする。最終ゲート修正のコミットはどちらでもない。ただし `merge-final-fix` が申告・トレーラー・手順を
検証して `final_gate.fix_commits` へ受け入れたもので、今も公開している。最終ゲートは push 済みの地点を判定するためである。
含めないと、最終ゲート修正を受け入れた後の push が必ず止まり、今の振る舞いから後退する。

そこで、オーケストレーターがマージ処理で受け入れを記録したコミットとして (b) の側に読み、`kind: final_fix` として
残す。見分けは決定 3 と同じく記録した SHA の一致で行う。

最終ゲート修正のコミットを公開しない案は採らない。最終ゲート修正のループ（`final-fix` → `merge-final-fix` →
`final-gate`）が CI で見る戦略で成り立たなくなる。

この読みは要求の前提 3 の文言より広いため、設計 Pull Request のレビューで確かめる（「未確認のまま残ること」）。

根拠: Value 1 / Value 6（MVV 版 2）

## 決定 5: push の直前の照合の範囲は、公開した地点ではなく origin の head から HEAD までにする

push が origin へ足すのは、origin の head（取り込んだ `FETCH_HEAD`）から HEAD までのコミットである。照合をこの範囲に
合わせると、送るものと照らすものが一致する。`FETCH_HEAD` は `_require_no_tool_paths` が既に取り込んでおり、
新しい通信は増えない。

公開した地点（台帳の値）から HEAD までを照らす案は採らない。台帳を持たない旧い状態ファイルから再開したときに、
照らす範囲と送る範囲がずれる。起点（`plan.base_sha`）から HEAD までを照らす案も採らない。最終ゲートの後に
取り消した改善項目のコミットは、公開済みの範囲に正しく残り（その上に revert がある）、照合に掛かって push が必ず止まる。

根拠: Value 6（MVV 版 2）

## 決定 6: 積み直しの衝突で広げるのは同じファイルまでの 1 段とし、`all` を無くす

`CLAUDE.md` の cross-refactoring の節は、取り消しを広げる範囲を「同じファイルを触った項目まで」と決めている。
今の 3 段目 `all` はこれより広く、#1237 で別のファイルの採用 3 件を巻き込んで採用 0 にした。広げる基準のファイルは、
取り消す項目のコミットに加えて、消す `stray` のコミットと戻すコミットが触ったファイルとする。衝突の原因はどれも
「消えた変更の上に書かれた変更」であるためである。広げるのは 1 段だけで、足した項目のコミットからさらに広げない。

広げても衝突したら、HEAD を取り消しの前へ戻して終了コード 4 で止まる（要求の前提 4）。最終ゲートより前には
push していないため、止まった時点の変更は Pull Request へ出ていない。

同じファイルの項目を足しながら衝突が消えるまでくり返し広げる案は採らない。広がる範囲が実行ごとに変わり、
何件巻き込むかを事前に言えなくなる。

根拠: Value 6 / Value 7（MVV 版 2）

## 決定 7: 公開の入口は最終ゲートへ入った後だけ push し、入る前に呼ばれたら止まる

要求の前提 1 を、呼び出し元から push を外すだけでなく、`publish` の入口の条件として持つ。「最終ゲートへ入った」は
`state["phase"]` が `final` か `done` であることで判定する。入る前に呼ばれたら終了コード 4 で止まる。呼び出し元の
誤りであり、黙って飛ばすと、将来足した呼び出しが途中の push を再び生んでも気づけない。

最初の push は 2 か所から起こりうる。検証の終わり（`cmd_verify`）と、最終ゲートの入口（`cmd_final_gate`）である。
残る改善項目が 0 件になった実行は検証を通らずに最終ゲートへ進むため、入口でも 1 度だけ push する（HEAD が公開した
地点と同じなら何もしない）。CI で見る戦略では、この push が無いと最終ゲートが読むチェックが動かない。

最終ゲートの後の push（`recheck`・`merge-final-fix`・結果なしの最終ゲート修正を閉じた後）は今の回数のまま残す。
最終ゲートは push 済みの地点を判定するためである（要求の前提 1）。

取り消した改善項目を origin からも外す案（#1399 の「直すこと」の 2 つ目の選択肢）は採らない。push 済みのコミットを
外すには履歴の書き換えか revert の積み増しが要り、前者は C4、後者は #1399 のコミット数の問題を公開側へ移すだけである。

根拠: Value 6 / C4（MVV 版 2）

## 決定 8: 最終ゲートを経ずに終わった実行は、drive を `stopped`（終了コード 1）で終える

要求の未決「最終ゲートを経ずに終わった実行の終了コードの値」への答えである。

drive の終了コードの表（`scripts/lib/drive_pause.py`）には、完了（0）・pause（20〜23）・中断（1）しか無い。
新しい値を足すと、表を読む `cross-review` 側と conductor の手順にも分岐が要る。最終ゲートが `passed` でない終わり方は
「完了していない」ので、既存の中断（`stopped`・1）に載せ、`metrics.exit` に最終ゲートの終了コードを写す。
`metrics.adopted` は 0 にし、残った改善項目の数は `metrics.unconfirmed` に出す。

`refactor.py report` の終了コードは 0 のまま変えない。状態を読んで文章を出すだけのコマンドであり、drive は
報告を作るために呼ぶ。報告の中身で「採用」を出さないことで AC-1399-6 を満たす。

新しい終了コード（例 3）を足す案は採らない。止まり方の区別は `metrics.exit` と `summary` で足りる。

根拠: Value 2 / Value 3（MVV 版 2）

## 決定 9: 取り消しの再開は、記録した取り消しの前の HEAD へ戻してから判定し直す

`pending_drop` に取り消しの前の HEAD（`before`）を持たせ、再開では `reset --hard before` の後に同じ `targets` で
計画を作り直す。計画は状態ファイルと HEAD だけから決まるため、同じ結果になる（I7）。改善項目の `status` と
コミットの記録は計画を打ち終えた後に 1 度だけ保存するので、途中で落ちても「取り消し済み」と「未記録」が混ざらない。

`before` へ戻すのは、未公開の範囲の書き換えに限られる。取り消しの間は push しないため、`before` は公開した地点より
新しい。

旧い状態ファイルで `before` が無いときは、今の HEAD から判定し直す。旧い方式が積んだ revert のコミットは記録に無い
ため `stray` として消え、同じ結果へ収まる。

範囲全体の逆再生を最初からやり直す今の方式は採らない。やり直すたびに前の途中の revert が範囲へ入る。

根拠: Value 6（MVV 版 2）

## 決定 10: 積み直しで SHA が変わる地点を、項目のコミット以外も対応表で書き直す

積み直すと、起点より後のコミットの SHA が変わる。今の `_remap` は改善項目のコミットだけを書き直す。
`reset` を使うと、ほかの保存済みの地点も外したコミットを指しうる。手順の起点（`phases.*.base_sha`）・
修正の起点（`fix.base_sha`）・最終ゲート修正の起点と受け入れたコミット・台帳のオーケストレーターのコミットである。書き直さないと、
次のマージ処理が履歴に無い起点から範囲を取り、`commits_in_range` が確定できずに止まる。

地点の新しい値は「元の履歴でその地点以前にある最後の残すコミットの、新しい SHA。無ければ積み直しの起点」とする。
地点の意味（「これより後が、この手順のコミットである」）が積み直しの後も保たれる。

起点を持つ各コマンドが自分で起点を取り直す案は採らない。取り直す規則が経路ごとに分かれ、判定を 1 か所にまとめる
目的に反する。

根拠: Value 6（MVV 版 2）
