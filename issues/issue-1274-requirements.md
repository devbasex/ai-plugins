# #1274: 本番の承認ゲート 2 の提示物が、直前の開発版から後の PR しか載せない

正は課題の本文（#1274）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

**この本文は「何を満たすか」だけを扱う。** どう作るか（PR の集め方・関数の置き場所・結果 JSON の形）は設計が決める。モードは `standard`（`release-steps.py approval-facts` が出す承認資料の中身を変える）。

## 例: ndf 10.17.69 の承認資料を、変えた後の形で作ると

直前の正式版 `ndf--v10.17.68` から `develop` へ入ったマージ（first-parent）は次のとおり（2026-10-10 に `git log --first-parent --format=%s ndf--v10.17.68..ndf--v10.17.69^2` で実測）。

| マージ | 中身 |
| --- | --- |
| #1868 `docs/spec-m1847` | 変更 |
| #1869 `feat/mcp-bigquery-remote` | 変更 |
| #1878 / #1876 / #1874 `design/issue-*` | 変更（設計 PR） |
| #1882 `sprint/m1492` | 変更（スプリント PR） |
| #1883 `release/v10.17.69-dev.1` | 開発版の版上げ |
| #1884 `release/v10.17.69-dev.2` | 開発版の版上げ |

今（ndf 10.17.69）: 配布のプランは、その開発版で渡した PR だけを `approval-facts --prs` へ入れる。dev.2 のプランなら、dev.1 までに入った PR が承認資料の「含む PR」から落ちる（10.17.30 では #1238 #1239 #1250 #1251 などが落ち、手で直した）。

変えた後: dev.2 のプランが `--prs` に dev.2 の PR だけを渡しても、承認資料の「含む PR」には #1868 #1869 #1874 #1876 #1878 #1882 の 6 件が並ぶ。版上げの #1883 #1884 は並ばない。「配る中身」と「未検証・残る危険」も同じ 6 件の PR の本文から書かれる。

## 依頼（原文）

課題 #1274 の起票時の本文を、そのまま写す。

````text
## 何を見つけたか

**本番の承認ゲート 2 の提示物（`issues/approval-ndf-v<版>.md`）が、直前の開発版から後の PR しか載せない。** 10.17.30 は開発版を 2 回（dev.1・dev.2）出したため、dev.1 に入った PR が提示物から落ちた。手で 10.17.29 以降へ直して利用者へ出した。

## どこで見つけたか

- 本番 10.17.30 の承認（2026-09-26 10:50 UTC）の前。提示物の PR の一覧に #1238 #1239 #1250 #1251 などが無かった

## 現状（develop 0aa346f7）

**compare の起点と変更量は、直前の正式版から出る。** `plugins/ndf/scripts/release-steps.py` の `approval-facts`
（`cmd_approval_facts`）は、compare の起点を `release_tag_before`（前の正式版のタグ。`:868`）から決め、変更量を
`origin/<本番>...origin/<開発>` で数える（`:873`）。

**残るのは「含む PR」の一覧である。** 一覧は `--prs` で渡した PR だけを並べる（`:879` の `for n in a.prs`）。
`supervise_lib/release_templates.py:89` は当該の開発版の PR を `--prs` に渡すため、dev.2 のときは dev.1 の PR が落ちる。

## 直さないと何が起きるか

承認する人が、本番に入る変更の一部しか見ずに承認する。承認の意味が「直前の開発版の差分」に縮む。

## 案

- `approval-facts` の「含む PR」を、直前の正式版のタグ（`ndf--v<前の版>`）から `develop` までのマージ済み PR から並べる

由来: issue #1142 スプリント 2（2026-09-26 振り返り）

## 関連

- #1834（open）— 開発版の出し直しで approval-facts が承認資料の手の節を消す。10.17.66 ではこの課題の回避として `--prs` に全 PR を手で並べた
- #1488（open）— 承認資料の材料（未検証・残る危険）が集まらない。3 つとも `cmd_approval_facts` の組み立てに触る
````

## 目的

- 本番への配布の承認（承認ゲート 2）で、利用者が**本番に入る変更のすべて**を承認資料の上で見て決められるようにする。承認の意味を「直前の開発版の差分」に縮めない

## 前提

- 前提 1: 「本番に入る変更」は、直前の正式版のタグ（`<プラグイン>--v<前の版>`。`--prev-tag` で渡せば その値）からベースブランチ（`.ndf/` の宣言の `base`。ai-plugins では `develop`）の先頭までに、ベースブランチへマージされた PR の集合とする。compare の起点と変更量（`approval-facts` の今の振る舞い）と同じ範囲である
- 前提 2: 版上げだけの PR（head が `release/` で始まる PR）は「含む PR」に並べない。中身の変更を持たず、承認する人の判断に要らないため。`check/`（検査の修正）など、ほかのブランチの PR は中身を持つので並べる
- 前提 3: `--prs` は残し、集めた PR と合わせて並べる（同じ番号は 1 回だけ）。10.17.66 の回避のように全 PR を手で並べたプランと、マージ前の PR を渡すプランが、そのまま通る
- 前提 4: 「配る中身」と「未検証・残る危険」（`release-steps.py notes --approval` が書く欄）も、同じ PR の集合から書く。理由: 欄を書く PR が「含む PR」と食い違うと、承認する人が見る変更の一部が落ちる問題が別の欄に残る（課題の「直さないと何が起きるか」と同じ）。誤っても局所的に戻せるため前提として進める
- 前提 5: マージの形は merge commit と squash merge（件名の末尾 `(#番号)`）の両方を数える。ai-plugins は merge commit だが、NDF を使うほかのプロジェクトが squash を使うため

## 対象範囲

含む:
- 承認資料の「含む PR」の欄を、前提 1〜3 の集合から書く
- 承認資料の「配る中身」「未検証・残る危険」の欄を、同じ集合から書く（前提 4）
- `approval-facts` の結果 JSON の PR の件数と items を、同じ集合に合わせる

含まない:
- 開発版の出し直しで、承認資料の手で足した節が消える問題（#1834）
- 承認資料の材料（未検証・残る危険）が PR の本文に無いときに集まらない問題（#1488）
- CHANGELOG の版の節（`notes` を `--approval` なしで打つ経路）の PR の集合。当たるかは設計で確かめる（未決の 1）
- 配布のプランの雛形（`supervise_lib/release_templates.py`）が `--prs` へ渡す PR の選び方
- compare の起点と変更量の数え方（今のまま）

## ドメインイベント

| # | イベント | 引き金 | 失敗したとき | 順序の前提 |
| --- | --- | --- | --- | --- |
| E1 | 配布のプランが `approval-facts` を起動した | 開発版の配布のプランの `facts` のステップ、または conductor の手打ち | — | 開発版の配布が終わっている |
| E2 | 直前の正式版のタグを決めた | E1 | タグが無く `--prev-tag` も無い: 承認資料を書かずに止まる（今の振る舞い。終了コード 3） | E1 |
| E3 | タグからベースブランチの先頭までにマージされた PR を集めた | E2 | 集められない（git・GitHub の読み取りの失敗）: 欠けた一覧で承認資料を書かずに止まる | E2。`origin` のタグとブランチを取り込み済み |
| E4 | 集めた PR と `--prs` を合わせ、版上げの PR を外した | E3 | — | E3 |

## 用語

| 用語 | 意味 |
| --- | --- |
| 承認資料 | 本番への配布の承認（承認ゲート 2）で利用者へ示す文書 `issues/approval-<プラグイン>-v<版>.md` |
| 開発版 | 開発版のチャネル（`develop`）へ出す版。版数に接尾辞（`-dev.<n>`）が付く |
| 正式版 | 正式版のチャネル（`main`）へ出す版。タグ `<プラグイン>--v<版>` を打つ |

## 受け入れ条件

- [ ] AC1: 直前の正式版のタグの後に、ベースブランチへ PR A をマージし（dev.1）、続けて PR B をマージした（dev.2）リポジトリで、`approval-facts --version <版> --prs B` を打つと、承認資料の「含む PR」に A と B の両方が並ぶ
- [ ] AC2: AC1 のリポジトリで、head が `release/` で始まる PR（開発版の版上げ）は「含む PR」に並ばない
- [ ] AC3: `--prs` に集めた PR と同じ番号を渡しても、「含む PR」に同じ PR は 1 回だけ並ぶ
- [ ] AC4: `--prs` に範囲の外の PR（マージ前の PR など）を渡すと、その PR も「含む PR」に並び、状態（open など）が行に出る（今の振る舞い）
- [ ] AC5: squash merge（件名の末尾 `(#番号)`）で入った PR も、merge commit で入った PR と同じく並ぶ
- [ ] AC6: `approval-facts` の結果 JSON の `kind: pr` の items と要約の「PR N 件」が、「含む PR」の行と同じ集合・同じ件数になる
- [ ] AC7: AC1 のリポジトリで `notes --version <版> --prs B --approval <承認資料>` を打つと、「配る中身」と「未検証・残る危険」に A と B の両方の本文の箇条が載る
- [ ] AC8: PR の集合を集められない（git の範囲が読めない・GitHub の読み取りが失敗する）とき、`approval-facts` と `notes --approval` は欠けた一覧で承認資料を書かず、0 以外で終わり、理由を出す
- [ ] AC9: 直前の正式版のタグが無く `--prev-tag` も無いときの振る舞い（終了コード 3 で止まる）は変わらない
- [ ] AC10: compare の URL・変更量（ファイル数・追加・削除）・`approved_sha` は今と同じ値になる

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 範囲の PR を集める処理は、同じ役割の既存の処理（`check-trigger.py` の `merged_prs`）と分けて持たない（AGENTS.md の MVV Value 6） |
| システム環境 | ai-plugins の形（`develop` / `main` / merge commit）を既定に埋め込まない。ベースブランチ・本番チャネルは `.ndf/` の宣言から読む（MVV Value 5） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない。`approval-facts` と `notes` の引数は今のまま（`--prs` の意味が「並べる PR のすべて」から「範囲の PR に足す PR」へ広がる） |
| データ | 無し |
| 既存の振る舞い | 承認資料の「含む PR」「配る中身」「未検証・残る危険」に、直前の開発版より前に入った PR が載る。結果 JSON の PR の件数が増える |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| テスト | `uv run --frozen --project . --all-extras pytest plugins/ndf/scripts/tests -q -n 4`（一時の git リポジトリに正式版のタグ・merge commit・squash merge・`release/` の PR を作り、gh の応答を差し替えて AC1〜AC10 を確かめる） |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | `plugins/ndf/scripts/` の release の層（`release-steps.py`・`release_lib/`）に置く。実験版の置き場（`scripts/experimental/`）には置かない（既定で動く安定版の変更） |
