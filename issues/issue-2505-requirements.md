## 環境に合わせて決める値

1 周回で選ぶ課題の数（`loop.max_issues`）は、上限として撤廃するのではなく、環境に合わせて設定する（利用者の指示、2026-11-05）。

- **初期値**: 3（今の既定のまま）
- **環境を調べる工程を入れる**: 調べるのは、動く場所（コンテナだけか、Factory の実行ジョブの中か）・CPU のコア数・メモリ・同時に動くレーンとプランの数。その結果から、`loop.max_issues` を決めて宣言（`.ndf/pace.json`）に書く
- **調べる時点**: 設計で決める。候補はループの開始（`loop start`）・並列の計画の開始（`parallel.py start`）・環境が変わったとき（Factory へ移した、マシンを替えた）
- **同じ考え方の値**: プランの本数の合計 6（8 コア・30 GB での実測）と、同時に動かすラッパーの数 3 も環境で決まる値である。同じ工程で一緒に決めるかを、設計で決める

## 目的

レーンを増やしても、回数と時間の固定の上限で開発ループが止まらない状態にする。止まる理由を、人の判断が要る状態と資源・費用の限界に絞る。

効果の見込みは次の実測のとおりで、止まる回数そのものは大きくは減らない。レーンを増やしたときに当たり始める上限を、当たる前に外すことが目的である。

メインディレクトリのループの記録（`/work/ai-plugins/.ndf/loop/*/loop.json` の `stops`）の集計、2026-11-06 時点、37 回:

| `user_stop` | 1 | 消えない |

ラッパー側の止まり（`max-starts`）はこの集計の外にあり、2026-11-04 に ai-plugins で 4 回、2026-11-05 に carul で少なくとも 2 回起きた（起票の本文とコメントの記録）。

## 前提

- 前提 1: 種類 A の表の数値は 10.27.16 の値で、6c78fe695（10.27.27）でも値は同じである。定義の行は `lib/sprint_loop_record.py:63`（保留の周回）・`lib/sprint_loop_select.py:368-369`（保留の周回の判定）・`lib/parallel_run.py:138-139`（問うまでの分と回数）へ動いている。ほかの行は変わっていない
- 前提 2: 起票の本文の「`durable.pause()` はテストのほかに呼び手が無い」は 6c78fe695 の事実と異なる。`rg -n 'durable\.pause' plugins/ndf` はテスト 3 行のほかに `plugins/ndf/skills/cross-review/scripts/drive.py:484` と `plugins/ndf/skills/cross-refactoring/scripts/drive.py:499` に当たる。どちらも収束ループの止まりで呼ぶ稼働中の経路で、関数を消すと cross-review と cross-refactoring が動かなくなる。利用者との確認（関数ごと消す）はこの前提の上の判断だったため、受け入れ条件にせず未決 8 で確かめ直す
- 前提 3: 再起動ループの検出は、`NDF_RELAY_SPIN=0` を設定すると働かない（`s < self.spin` が常に偽になる。`relay_lib/record.py:200`）。carul の開発コンテナは暫定でこの値を設定している。起動回数の上限を外した後、この値を設定した環境には暴走止めが無くなる。この変更は `NDF_RELAY_SPIN` の扱いを変えず、残リスクとして残す
- 前提 4: 上限を外した版が届いた後も、既に動いているラッパーは起動の時の版を持つ。ラッパーの入れ替えの後に効く
- 前提 5: ループの記録は開始時に予算を写している。既存のループの `budget` の数（このリポジトリの 1000・10000 など）は書き換えない
- 前提 6: `loop.release_pending_max` を書いた宣言は、書いてあっても断らず、値を使わない。外のプロジェクトの宣言で開発ループが断られると、上限を外す目的に反するためである
- 前提 7: 無進捗の打ち切りを当てるのは実装のステップだけである。ほかのステップの `timeout` は変えない
- 前提 8: 実行環境の調査に失敗したとき（値が読めないとき）は、`loop.max_issues` の今の値で進む。開発ループを止めない
- 前提 9: `--impl-timeout` と `.ndf/supervise.json` の `impl_timeout` の扱いは未決 4 で決める。決まるまでの受け入れ条件 12〜14 は、どちらも渡していないときの振る舞いを指す
- 前提 10: 1 つの課題のまま要求を書く。範囲は上限 10 件ほどで、実装の Pull Request をいくつに分けるかは `implementation-plan` が決める

MVV との突き合わせ: 反する疑いは無いと判定した。周回と時間の既定を外しても、上限に当たったら止まる仕組み（Value 3）として、費用の予算・同じ失敗の繰り返し・再起動ループの検出が残る。費用の予算まで撤廃すると判定が変わるため、未決 3 に分けて承認ゲート 1 で決める。根拠: Vision / Value 2 / Value 3 / Value 6（MVV 版 5）

## 用語

| 用語 | 意味 |
| --- | --- |
| 開発ループ | スプリントを 1 つ終えるたびに次を選んで続ける進め方 |
| 周回 | 開発ループの 1 回分 |
| ループの予算 | 開発ループが使ってよい量の上限。周回の数・費用・経過時間で数える |
| 保留の周回 | 答えを待たずに締めた周回（配布待ち・質問待ち） |
| レーン | 並列の計画の下で、名前つきのラッパー 1 本が進める開発の流れ |
| 一時レーン | オーガナイザーが共有の作業のために起動するレーン |
| ラッパー | 利用者の claude を包んで常駐し、次のセッションを起動する常駐プロセス |
| 再起動ループ | セッションが短い時間で続き、進まずに起動だけが重なる状態 |
| 実装の上限 | プランの実装のステップの `timeout`（秒） |
| 無進捗の打ち切り | 実装のステップで、進みの観測が許容時間を越えて途絶えたときだけ打ち切ること |
| 実行環境の調査 | 動く場所・CPU のコア数・メモリ・同時に動くレーンとプランの数を調べ、1 周回で選ぶ課題の数の候補を出す工程 |

## 非機能の条件

| 大項目 | 条件 |
