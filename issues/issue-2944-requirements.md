## 何が起きたか

NDF は、開発の工程を AI に分担させて進める。2026-11-10 に費用を調べると、作業の重さによらず、ほぼすべての作業を同じモデル（AI の種類）と effort（モデルがどれだけ深く考えるかの指定）で動かしていた。整形や題の付け直しのような機械的な作業にも、設計と同じ Opus 5.5 を使っている。

直近 4 週の費用の 47% は、工程のステップごとに起動する AI（worker。`claude -p` で起動する）が使っていた（[費用とリードタイムの集計 2026-11-10](https://github.com/devbasex/ai-plugins/pull/2905)）。全期間では 2,333 回起動している。割合が全期間の 24% から上がったのは、全体の指揮役（conductor）とサブエージェント（会話の中から別に起動する AI）が持っていた作業を worker へ移したためで、フェーズ 1 回の費用はサブエージェントより 3〜6 割安い（仕上げのプランだけは [#2914](https://github.com/devbasex/ai-plugins/issues/2914) で調べる）。worker を使うこと自体は進んでいる。残る課題は、その 2,000 回を超える起動が、全部 Opus 5.5 の既定で動いていることである。

### エンジニア向けの補足

集計は 10 系の `supervise.py` が起動した `claude -p` を「supervisor の層」と数えている。3 層の定義（`references/agent-layers.md`）では、この `claude -p` は worker である。

2026-11-27 に利用者が、モデルと effort を固定値で決めず、設定した選択肢を実験で選ぶ方針を示した（末尾の「リクエスト（原文）」）。この要求はその方針に合わせて直してある。

## 種類

機能追加（層・工程・ステップの種類からモデルと effort を選ぶ約束は、今のコードにも手順書にも無いため）

## 今の姿

この文書の「工程」は、要求・設計・実装のような開発の区切りである。工程の中の手順（ステップ）を順に並べた実行の定義を「プラン」、プランの元になる定型を「テンプレート」、あるステップの結果に応じて次のステップへ進むことを「遷移」と呼ぶ。「相手役」は、レビューや提案を頼むほかの AI である。

モデルと effort は、起動する場所ごとに別々に決まっている。コード上の位置は 2026-11-26 に確かめた。

| 起動の形 | 今の決め方 | コード上の位置 |
| --- | --- | --- |
| conductor と、並列に流す開発の 1 本分（レーン。`ndf relay`） | Claude Code の既定（`--model`・`--effort` は引数を通す） | `plugins/ndf/src/ndf/domains/relay/claude_args.py` |
| worker（プランのステップ） | `--model` も effort も渡さない | `plugins/ndf/src/ndf/core/worker.py:398` |
| 工程から Skill を回す起動 | `--model` を渡さない | `plugins/ndf/src/ndf/progress/invoke.py:943` |
| 形の決まった回答を返す判定の起動 | `--model` を渡さない | `plugins/ndf/src/ndf/adapters/llm.py:111` |
| 応答の終わりの待ちを調べる判定 | 設定ファイルの値（`haiku`）を渡す | `plugins/ndf/src/ndf/domains/hooks/judge_child.py:165`、`plugins/ndf/contracts/limits/hook.stop-wait.judge.json` |
| `claude -p` の起動の組み立て | モデルの指定があるときだけ `--model` を足す。effort を渡す手段は無い | `plugins/ndf/src/ndf/adapters/claude.py` の `claude_launch` |
| サブエージェント | 定義ファイルの冒頭の `model` が固定値（`director` は opus、ほか 7 つは sonnet）。effort は書いていない | `plugins/ndf/agents/*.md` |
| Codex（レビューとリファクタリングの相手役） | effort を指定しない | `plugins/ndf/contracts/domains/runtimes.json` の codex の行 |
| Codex（外部の AI へ作業を渡すとき） | effort は `medium` の固定 | `plugins/ndf/skills/external-ai/SKILL.md`・`references/cli-codex.md`、`plugins/ndf/agents/corder.md` |

使った量の記録にも足りない所がある。使用量ログ（使ったトークンを 1 起動 1 行で追記する記録）はモデルの欄を持つが effort の欄を持たない。また、`claude -p` の行を書く関数を本体のコードから呼んでいないため、worker の起動は使用量ログに残らない（2026-11-26 に検索で確かめた。「調べた事実」）。

## 何を足すか・変えるか

| | 今 | 足した後 |
| --- | --- | --- |
| モデルと effort の決め方 | 起動する場所ごとに別々。多くは Claude Code の既定 | 工程ごとに選択肢（モデルと effort の組）を設定ファイルに書き、実験の割り付けで起動のたびに選ぶ |
| 選び方の根拠 | 無い | 工程ごとの効果指標（実装ならレビューで受けた指摘の数など）と費用から組ごとの ROI を出し、出現率を自動で調整する |
| 上書き | 起動する人が引数で渡すだけ | リポジトリの設定（`.ndf/`）の選択肢の置き換えと、環境変数でも上書きできる |
| 失敗したとき | 同じモデルで打ち直す | 失敗の判定がはっきりしたステップは、段階を 1 つ上げて打ち直す |
| 記録と見直し | worker の起動は使用量ログに残らない | 使ったモデル・effort・割り付けの根拠・効果指標が残り、組ごとの比較を読める |

## 今の利用者への影響と互換

NDF を使うプロジェクトでは、NDF を更新すると、設定を変えなくても工程の一部が、実験の選択肢の 1 つとして今と違うモデルと effort で動く（「前提」の 2）。今の振る舞いに当たる組も選択肢の 1 つで、比較の基準になる。今の設定や入力で読めなくなるものは無い。実験を止めたいプロジェクトは、リポジトリの設定か環境変数で指定する。

## なぜ困るか

軽い作業にも重い作業と同じ単価を払い続ける。Sonnet 5.5 の単価は Opus 5.5 の半分、Haiku 5.5 は入力が 10 万トークン以下なら 40 分の 1 である。反対に、難しい作業の effort を上げて手戻りを減らす手段も無い。

## 目的

- モデルと effort が、工程ごとの効果と費用の実測に基づいて選ばれる
- 選択肢は設定ファイルにまとまり、スクリプトがそこから読む
- 固定の値を人が直すのでなく、統計に基づいて出現率が自動で変わる

## 対象範囲

含む:

- 工程ごとの選択肢（モデルと effort の組）と効果指標を持つ設定。NDF が初期の選択肢を同梱し、リポジトリの設定で置き換えられる
- 実験の割り付け・効果指標の記録・ROI の計算・出現率の自動調整。対象は、効果指標と費用を機械で取れる起動（プランの worker のステップ、レビューの相手役、判定の起動）
- 選ぶ処理（1 か所）。worker の起動・Skill を回す起動・判定の起動・相手役の起動・外部の AI への委譲が使う
- 使ったモデル・effort・値の出所・割り付けた確率を記録に残すこと。そのために要る、`claude -p` の起動の行の書き込み
- 環境変数と起動の引数による一時的な上書き
- 失敗の後に段階を 1 つ上げる打ち直し（失敗の判定がはっきりしたステップだけ）
- 組ごとの件数・効果・費用・ROI・出現率を読むコマンド

別の Issue に分ける案（設計承認ゲートで決める。設計文書の「この設計の範囲と、分ける案」）:

- 効果指標か費用を取れない起動（サブエージェント・レーン・オーガナイザー・応答の終わりの判定）の割り付け
- cross-refactoring の提案と実装の相手役の実験
- 実験の記録を複数のマシンや利用者で共有すること
- 作業の難しさに応じて割り付けを変えること

含まない:

- 承認ゲートの数と区分
- Kiro・agy のモデルの選び方（相手役として起動するだけで、effort の仕組みが違う）
- オーガナイザーの中継を減らす変更（[#2936](https://github.com/devbasex/ai-plugins/issues/2936) が持つ）
- conductor の文脈を小さく保つ変更（[#2595](https://github.com/devbasex/ai-plugins/issues/2595) などが持つ）
- 起動で読み込む Tool の定義を減らす変更（[#1959](https://github.com/devbasex/ai-plugins/issues/1959)）

## 前提

- 前提 1: 切り替えるのは、新しいプロセスか新しい会話を始めるときだけである。会話の途中ではモデルも effort も替えない
- 前提 2: ~~NDF が持つ初期の対応表は、設定が無いプロジェクトでも効く~~ → NDF が同梱する初期の選択肢は、設定が無いプロジェクトでも実験に使う。選択肢には、今の振る舞いに当たる組を比較の基準として必ず含める（2026-11-27）。受け入れ条件 7 の「指定が無い種類」は、同梱の選択肢にもリポジトリの設定にも無い種類を指す
- 前提 3: ~~値が重なったときの優先は、引数 → 環境変数 → リポジトリの設定 → 対応表の順である~~ → 値が重なったときの優先は、起動する人が引数で渡した値 → 環境変数 → 実験の割り付け（リポジトリの選択肢があればそれを、無ければ同梱の選択肢を使う）の順である（2026-11-27）
- 前提 4: ~~対応表の初期値は、「参考: 軸ごとのマトリクス（案）」を元に設計で決める~~ → 固定の値の対応表は持たない。「参考: 軸ごとのマトリクス（案）」は、初期の選択肢を選ぶ材料にする（2026-11-27、利用者の方針）
- 前提 5: モデルと effort の選択は、起動のたびの人の承認を必要としない。Tool と安全装置の承認（[#1959](https://github.com/devbasex/ai-plugins/issues/1959)）とは別に扱う

## 受け入れ条件

番号 1〜9 は起票の時の条件で、番号 10〜14 は対象範囲に書かれていて条件が無かった点を足したものである。

- [ ] 1. ~~対応表が 1 ファイルにあり、モデルと effort を引ける~~ → 工程ごとの選択肢（モデルと effort の組）と効果指標が 1 つの形の設定にあり、起動の層・作業の名前・ランタイムから選択肢を取得できる。選択肢の無い作業は、指定せずに起動する（2026-11-27）
- [ ] 2. プランのステップの `claude -p`（`ndf worker run`）が、ステップごとに選んだ `--model` と `--effort` で起動する。環境変数による一時的な上書きを持つ（10 系の `NDF_SUPERVISE_MODEL` は 11 系に無い）
- [ ] 3. codex の相手役が、役割ごとに選んだ effort で起動する。通常のレビューの effort は low にも high にも固定せず、選択肢に入れて実験で選ぶ。`external-ai` と `corder` の本文に書いた固定の `medium` は消え、値は設定から取る
- [ ] 4. 使用量ログの各行に、使ったモデル・effort・値の出所が残る。`claude -p` の起動も 1 起動 1 行で残る。工程 × モデル × effort の費用と成功率を出すコマンドがある
- [ ] 5. 会話の途中でモデルや effort を替えたとき、cache（読み込んだ文脈を安く読み直す仕組み）が書き直されるかを `claude -p` の stream-json で実測し、結果を確定仕様に書く
- [ ] 6. ~~初期の対応表で 1 スプリントを流し、全部を Opus 5.5 / medium に固定したスプリントと比べる~~ → 配ったバージョンで実験を 2 スプリント以上流し、組ごとの件数・効果指標・費用・ROI・出現率と、判断できる件数に達したかを確定仕様に書く。今の振る舞いに当たる基準の組と、同じ期間に並行して割り付けて比べる（2026-11-27）
- [ ] 7. リポジトリの設定（`.ndf/`）でステップの種類ごとに選択肢を置き換えられる。選択肢を 1 つにすればその値に固定できる。指定が無い種類は今と同じく既定のモデルで動く（「指定が無い」の範囲は前提 2）
- [ ] 8. プランの記録の `models` に、ステップの種類ごとに実際に動いたモデルが残り、設定との食い違いを集計で出せる（11 系のプランの記録に、この項目は今は無い）
- [ ] 9. ステップの種類ごとに、呼び出し・費用・やり直しの率をモデル別に並べる集計がある。やり直しは、同じステップの再実行と、判定の起動が回答の形を 2 回続けて満たせず人へ戻した件数（judge の stop）である
- [ ] 10. テスト・検査・結果の形のように失敗の判定がはっきりしたステップは、同じ失敗への 2 回目以降の打ち直しがモデルか effort を 1 段上げて起動し、上げたことが使用量ログに残る。打ち直しの回数の上限は今より増えない。最上の段階では同じ値で打ち直す。判定がこれらでないステップは上げない
- [ ] 11. ~~モードの補正が対応表にあり、補正した値が使われる~~ → モード（`light` など、工程の重さの区分）が分かる起動は、記録にモードが残り、集計をモードごとに読める。固定の補正はしない（2026-11-27）
- [ ] 12. 判定の起動が同じ処理で選択肢を取得する。起動する人が `--model`・`--effort` を引数で渡したときは、その値で起動し、実験の集計に入れない。~~レーンとオーガナイザーの起動、サブエージェントの起動の指示も同じ処理で引く~~ → 効果指標を取れないため、別の Issue に分ける案を設計承認ゲートで決める（2026-11-27）
- [ ] 13. NDF が続きから再開する起動（同じ会話の `--resume`）は、その会話を始めたときに NDF が指定したモデルと effort で動く。指定せずに始めた項目と、利用者が自分で打つ `--resume` は、ランタイムの決め方に任せる
- [ ] 14. 同梱の選択肢かリポジトリの設定が読めない・形が違う・存在しない effort の値を持つときは、黙って別の値で起動せず、理由と直す場所を示して止まる
- [ ] 15. 実験の割り付けは、工程の単位（1 回のスプリントの中の 1 つの工程など）ごとに 1 つの組を決め、その単位の起動はすべて同じ組を使う。割り付けた組と確率が記録に残る
- [ ] 16. 工程ごとの効果指標が決まっていて、どの起動の成果かを単位で対応付けて記録する。指標を取れなかった単位は、成功にも失敗にも数えない
- [ ] 17. 組ごとの効果・費用・ROI を出し、必要な件数を集めた後は出現率を自動で調整する。どの組も下限の出現率を持ち、明らかに劣る組は打ち切る。打ち切りは後で戻れる
- [ ] 18. 効果が基準の組より決めた幅を超えて劣る見込みの組は、安くても出現率を上げない
- [ ] 19. 実験を止める指定と、指定した 1 つの値に固定する指定ができる
- [ ] 20. 必要な件数、下限の出現率、打ち切りの条件、割り付けの方法、記録の形が設計に書かれ、方法とライブラリは既存の実績のあるものを調べて比べた出典がある

| Opus 5.5 | 4 / 20 / 0.20 | medium | 既定は `medium`。上の段階では `max_tokens` を大きくする |
| Sonnet 5.5 | 2 / 10 / 0.10 | medium | 仕様が明確なエージェントのコーディングは `medium`、難しく長い作業は `high` |
| Haiku 5.5 | 0.10 / 0.50 / 0.01（入力 10 万 token 以下）、0.50 / 2.50 / 0.05（超） | medium | エージェントのコーディングも含めてまず `medium`。単純な大量処理は `low` |

effort の各段階の用途（公式）:

| 段階 | 用途 |
| --- | --- |
| `low` | 最も効率的。単純な作業とサブエージェント向け |
| `medium` | 速度・費用・性能の釣り合い。エージェント作業向け |
| `high` | 複雑な推論・難しいコーディング・エージェント作業 |
| `xhigh` | 長時間のエージェント作業（コーディングで 30 分超、数百万 token の規模） |
| `max` | 上限なし。最も深い推論。上限の測定用 |

- effort は思考の token の厳密な予算ではなく、振る舞いの目安である。低い段階ほど tool の呼び出しが減り、説明が短くなる
- Claude Code での effort の決まり方は、優先の高い順に `CLAUDE_CODE_EFFORT_LEVEL` → セッション中の `/effort` → 起動時の `--effort` → 設定（`effortLevel`・モデル別の保存値）→ モデルの既定、である。Skill とサブエージェントの frontmatter の `effort` は実行中の値を上書きする。ただし `CLAUDE_CODE_EFFORT_LEVEL` があればそちらが勝つ
- user settings のトップレベルの `effortLevel` は、Opus 5.5 には効かない（公式に明記）
- モデルの別名 `opus`・`sonnet`・`haiku` は、Anthropic API では Opus 5.5・Sonnet 5.5・Haiku 5.5 を指す
- 第三者の測定では、普通のコード検索をサブエージェントに任せると、正答率は変わらず費用だけが増えた（Haiku 5.5 で +74〜116%、Opus 5.5 で +143〜221%）。「自分の作業で効果を測るまでは、サブエージェントの effort を既定のまま変えない」ことが勧められている

### GPT（Codex）

- 公式の Codex prompting guide: `medium` は対話のコーディング全般向けの釣り合いの取れた段階。`high`・`xhigh` は最も難しい作業と、数時間に及ぶ自律作業向け
- 公式の設定リファレンス: 使える段階はモデルとクライアントで変わり、low・medium・high・xhigh・max・ultra がある。設定の例では既定のモデルを `gpt-6.1-sol`、effort を `medium` にしている
- 既定の effort の値は情報源の間で食い違う（`gpt-6.1-sol` の既定を low とするもの・medium とするもの）。手元の `codex-cli 0.167.0` で確かめる
- 第三者の目安: `xhigh` は `medium` の約 8〜15 倍の推論 token を使う（非公式）。`low`・`minimal` は小さな不具合の修正・単純な整形向け

## 参考: どういう単位で切り替えるか（考察）

**切り替えは、プロセスか会話の切れ目でだけ行う。** 会話の途中でモデルを替えると、prompt cache はモデルごとに別なので、それまでの文脈の全体を cache に書き直す。conductor の文脈は平均 25 万 token あるため、1 回の切り替えで Opus 5.5 の cache の作成（1 時間）に約 $2 かかる。effort の途中の切り替えも、thinking の設定の変更として cache を無効にする恐れがある（推定。受け入れ条件 5 で確かめる）。

| 単位 | 切り替えの費用 | 判断の材料の粒度 | 評価 |
| --- | --- | --- | --- |
| 会話の途中（`/model`・`/effort`） | 文脈の全体を cache に書き直す | 細かい | **採らない** |
| 会話（conductor・レーンの起動、カットポイントの再起動） | 0（起動のたびに cache を作る） | 粗い（層とレーンの役割） | 層ごとの既定に使う |
| `claude -p` の 1 ステップ（プランのステップ） | 0（ステップごとに新しいプロセス。今も費用の 49〜62% が cache の作成） | 工程とステップの種類が分かる | **主な単位にする** |
| サブエージェントの起動 | 0（新しい文脈） | 役割（定義）とリクエストの中身 | 定義の frontmatter に役割の既定、起動のときに上書き |
| 相手役の CLI の起動（cross 系・external-ai） | 0 | 役割（レビュー・提案・実装） | 起動の引数で渡す |
| 失敗の後の打ち直し | 0（打ち直しは新しいプロセス） | 1 回目の結果 | 段階を 1 つ上げて打ち直す（安い方から始める） |

- **主な単位を `claude -p` のステップにする理由:** プランのテンプレート（`plugins/ndf/contracts/templates/`）はステップの id と工程を持ち、`claude -p` の起動は権限の種類（`ClaudeCall.permission`。FULL・TOOLS・JUDGE）で分かれている。新しい判定を足さずに、この 2 つから引ける（10 系の `claude_kind` は 11 系に無い）
- **失敗の後に上げる打ち直し**は、安いモデルで始める案の安全網になる。ただし、失敗の判定がはっきりしたステップ（テスト・検査・JSON の形）に限る。判定の曖昧な設計やレビューは、最初から上の段階で始める
- **Haiku 5.5 は入力 10 万 token を超えると単価が 5 倍になる。** worker の平均の文脈は 13 万 token なので、Haiku を割り当てるのは入力が小さいと分かっているステップに限る
