# #880 / #883 / #494 / #723 / #885: 決定の記録

設計は [issue-880-885-design.md](issue-880-885-design.md)、要求は [issue-880-885-requirements.md](issue-880-885-requirements.md) にある。

## 決定の記録

### 決定 1: 群と修正コミットの検証は `--round-test` で行い、全体テストは `init` と最終ゲートの 2 回に限る

#880 の直し方の候補 1（反復中と最後で検証を分ける）と 2（起動する側の基準を書く）の両方を採る。
群の検証で見たいのは、範囲の中の書き換えが振る舞いを変えていないことである。範囲外を触ったコミットは
今も失敗になるため（前提 2）、群ごとに全体を走らせても範囲のテストより多くは分からない。範囲の外への
波及は、最終ゲートの全体テスト 1 回で見る。

ラウンドの終わりごとに全体テストを走らせる形は採らない。ラウンドの数（テスト整備 2 ＋ 提案 3）だけ
全体テストが増え、最終ゲートの 1 回で見るものと同じものを見る。

### 決定 2: `--round-test` は明示の引数にし、`--scope` から自動で導かない

テストのコマンドの形はリポジトリごとに違う（`pytest` の引数・`uv run` の前置き・`npm test --` の後ろ）。
`--scope` のテストの置き場所から組み立てると、その形を cross-refactoring が知ることになる。範囲を決めた
起動する側が、範囲のテストも決める（決定 5 の手順の順 2）。

### 決定 3: `--round-test` を省いたら今と同じ検証をし、範囲より広い `--baseline-test` には案内だけを出す

省いた起動と、変更の前の状態ファイルの再開は、今の振る舞いを保つ（互換）。範囲より広いことは誤りでは
ないため止めない。#880 の候補 3（`scope_problem` と同じ場所の案内）を、止めない 1 行として採る。

### 決定 4: 単独の起動でも、2 つのテストが違えば最終ゲートで全体テストを 1 回走らせる

今の単独起動の最終ゲートは cross-review へ渡すだけで、手元のテストを走らせない。今までは群ごとに全体
テストを走らせていたため、それで足りていた。群の検証を範囲のテストへ替えると、単独の起動では範囲の外への
波及を誰も見なくなる。2 つのテストが同じ（`--round-test` を省いた）なら今のままにする。

### 決定 5: 飛ばす条件は「本番コードの差分が無い、または 10 行以下」とし、判定は差分から機械で行う

#494 の案「本番コードの差分が無い、または改善の対象になる構造を持たない」のうち、後者は機械で決まらない。
行数の上限で近似する。#489 は本番コードが 1 行で、飛ばした理由は「改善する構造が 1 行しかない」だった。
構造改善の所要の中央値は 1 本あたり 75.9 分で（前提 3）、数行の変更に見合わない。

本番コードは「コードの拡張子を持ち、テストの置き場所でないファイル」とする。テストの置き場所の判定は
cross-refactoring が既に持つ `_is_test_path` を使い、別の定義を作らない。テストだけの差分も飛ばす。
構造改善はテストを守りに本番コードを整える工程で、テストそのものは改善の対象に置いていない。

判定に LLM を使わない。差分から決まることなので、スクリプトが返す。supervisor はその結果を読む
（#494 の「条件の判定は差分から決まるので、スクリプトに持たせる」）。

### 決定 6: 飛ばした記録は工程の値を増やさず、工程の記録と Pull Request の本文の 1 行で残す

飛ばしたときも工程「構造改善」を記録する。通し忘れは「記録なし」のまま残るため、飛ばした場合と見え方が
分かれる。飛ばしたのか通したのかは、Pull Request の本文の `構造改善: 飛ばした（<理由>）` が持つ。

`projects-sync.sh` に `--note` を通す形は採らない。記録の入口の引数の形が変わり、通過工程の控えを
積む hook の観測の形にも触る。区別に要るのは Pull Request を読む人と配布の工程であり、本文で足りる。
工程の値（`構造改善（飛ばした）` など）を増やす形も採らない（#494 が退けたとおり、盤面の単一選択に響く）。

### 決定 7: 判定の副命令は cross-refactoring の `refactor.py assess` に置く

#494 は置き場所の候補に development-workflow の `scripts/` を挙げた。判定に使う知識（テストの置き場所の
印・範囲の扱い）は cross-refactoring が持ち、`_is_test_path` もそこにある。development-workflow 側へ置くと、
同じ印の定義を 2 か所に持つ。飛ばしてよいかは「cross-refactoring を通す価値があるか」の問いであり、
その前提を知る側に置く。

### 決定 8: #883 は親シェルの回収を足すだけにし、打ち切りの判定はグループの存否のまま

原因は、打ち切った親シェルがゾンビとして残り、`killpg(pgid, 0)` がそれを「生きている」と数えることにある。
存否を見る前に `proc.poll()` で親を回収すれば、グループに残るのは本物の子だけになる。

親の終了だけで打ち切る形は採らない。SIGTERM を無視する子がグループに残る。その子は作業ディレクトリを書き換え
続ける（今の `_kill_process_group` の docstring の理由）。

### 決定 9: #723 は提案の取り込みと適用の検証の 2 か所で弾き、誤検知は取り消しの側に倒す

提案の基準（`propose-tests.md`）だけでは、実装担当が書いたテストに混じったときに止まらない（#723 の
「修正レイヤー」）。そこで 2 か所で弾く。取り込みでは、`target` が `.md` の提案を見送る。適用の検証では、
追加したテストの行が追跡している `.md` を指していれば群を取り消す。

適用の検証の判定は、追跡している `.md` のパスとの一致で行う。`.md` で終わる文字列をすべて弾く形は
採らない。検査スクリプト自体のテストは一時ファイルの `.md` を入力に渡し、#885 の境界でも残す側に当たる。
追跡している `.md` と同じ名前の一時ファイル（`README.md` など）を使うテストは弾かれる。そのときも群が
取り消されるだけである。Pull Request に文言固定テストが残る側には倒れない。

### 決定 10: #885 の境界は issue の表をそのまま採り、参照切れは検査スクリプトへ寄せる

削る・寄せる・残すの境界は、利用者が #885 で決めた表のとおりにする。参照切れ（文書が指すファイルの実在）は
文言ではなく構造を見ているため、残す価値がある。ただし pytest で `.md` を読む形のままだと、文言固定と区別が
付かない。検査スクリプト（`scripts/check-markdown-links.py` ほか）へ寄せ、削る前に同じ参照を壊して
失敗が現れることを確かめる。

### 決定 11: 実装は 2 本の Pull Request に分け、#885 を先に入れる。#885 は #892 #901 の実装の後に始める

#885 は数百の関数の削除で、レビューで見るのは分類の妥当性である。#880 #883 #494 #723 はコードの振る舞いの
変更で、レビューで見るのは契約とテストである。1 本にすると、削除の差分が振る舞いの変更を埋もれさせる。

#885 を先にするのは、#880 ほかの検査の持ち場で構造改善を戻せるかを確かめるとき（AC20〜AC23）、範囲の
Skill に文言固定テスト（`cross-refactoring/tests/test_skill_terms.py` など）が残ると、文書の整理が取り消される。
それでは AC23 が測れない。#892 #901 の後にする理由は、#901 の実装にある。`agent-layers.md` と、その文言を
照合するテストを触りうる。

### 決定 12: 構造改善を戻すかは、#880 ほかを実装した Pull Request 自身の検査の持ち場で AC20〜AC23 を見て決める

戻してよいかは、直した cross-refactoring を実際に通して初めて分かる。直した Pull Request 自身は範囲が
cross-refactoring のコードとテストに閉じ、範囲のテストがある。これを最初の実行に使えば、戻す判断のために
別の Pull Request を待たずに済む。

判断は conductor が行う（利用者の指示を解くのは、その指示を受けた層である）。満たさなかった条件は issue に
して、指示を保つ。

### 決定 13: 境界の表に収まらない形は「スクリプトが実行時に読むか、テストが中のコードを実行するか」で分ける

棚卸で、issue の境界の表に収まらない形が 3 つ見つかった。文書に埋め込んだ bash を実行するテスト（P1）、
プロンプトの契約の語（P2）、文書の表とコードの一致（P3）である。

判定の問いを 1 つにする。**その `.md` をスクリプトが実行時に読むか、テストがその中のコードを実行するか。**
どちらかなら、その `.md` は機械が読む契約か、実行されるコードの置き場所であり、テストは振る舞いを見ている。
どちらでもなければ、テストが見ているのは文言で、#885 の方針（前提 4）どおり削る。

この問いで、P1 と、スクリプトが読むプロンプトのプレースホルダ・解析する語（P2）、スクリプトが読む表（P3）は
残る。スクリプトが読まない文書の値とコードの定数の一致（P3'）と、2 つの文書の表の並びの一致は削る。
文書の値の正しさはレビューが見る。

P3' を残す形は採らない。文書の値の照合であることは言い回しの照合と変わらず、残すと「どこまでが一致の
検査か」を毎回判断することになる。削った結果、文書とコードが食い違っても気付けない場面は増える。
これは #885 が受け入れた費用である。
