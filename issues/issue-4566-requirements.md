## 何が起きたか

NDF の利用先から、「CI でテストを走らせる設定が無いリポジトリでは、本当にリファクタリングの工程が行われないのか」と問い合わせがありました（起票の本文の日付で 2026-11-27）。調べると、そのとおりでした。NDF の工程「リファクタリング」（実装で入ったコードの構造を、振る舞いを変えずに直す工程）は、リポジトリに「CI テストの設定」がある場合にだけ実行されます。起票の本文によると、利用者はこの停止を NDF の開発リポジトリ（ai-plugins）だけの事情だと考えていましたが、利用先でも効いています。

CI テストの設定とは、テストを作業しているマシンで走らせず CI の結果で合否を決める、という NDF の設定です（`.ndf/project.json` の `test.ci.only`）。

## 種類

機能追加（今の手順書と確定仕様が「CI テストの設定が無いリポジトリでは通さない」と定めており、その約束を変えるため。Issue の種類のラベルは `bug` のままです）

## 今の姿

工程「リファクタリング」は、開発の進め方のうち `standard` と `legacy-refactor` の 2 つに含まれます。今の実行条件は次のとおりです。

| 場面 | 今の振る舞い |
| --- | --- |
| 差分にコードのファイルがあり、CI テストの設定がある | 実行する |
| CI テストの設定が無い（`false` を含む） | 差分にコードがあっても実行しない |
| 差分が文書のファイルだけ | 実行しない |
| リポジトリの設定で、この工程を無効にしている | 実行しない。無効にした理由が記録に残る |
| リポジトリの設定で、この工程を有効にしている | 実行する。CI テストの設定の有無も、差分の中身も見ない |

最後の 2 行の設定（`.ndf/project.json` の `workflow.stages`）は、今もあります。ただし手順書には説明がありません（`git grep workflow.stages` を `plugins/ndf/skills` に打つと、当たるのは設定の形を定めるファイルだけです）。

停止の経緯は次のとおりです。2026-11-11 に、このリポジトリでリファクタリングが 2 回続けて時間の上限で打ち切られ、全部のリポジトリで一時的に外しました（ https://github.com/devbasex/ai-plugins/issues/3051 ）。その後、テストを CI で走らせる仕組み（ https://github.com/devbasex/ai-plugins/issues/3056 ）を入れたときに、CI テストの設定があるリポジトリに限って戻しました。

今の約束（実行条件の決まり）が書いてある文書:

- 工程の表: [development-workflow の SKILL.md](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/SKILL.md) の「リファクタリング」の行
- 確定仕様: [ndf-ci-only-tests.md](https://github.com/devbasex/ai-plugins/blob/main/docs/specifications/ndf-ci-only-tests.md)・[ndf-review-units-and-refactoring-timing.md](https://github.com/devbasex/ai-plugins/blob/main/docs/specifications/ndf-review-units-and-refactoring-timing.md)

### エンジニア向けの補足

- 条件の定義は `plugins/ndf/contracts/workflow/stages/refactor.json` の `when`（`code_in_diff` と `ci_declared`）です
- 条件を外すだけでは足りません。工程が打つ `ndf refactor run` は、必須のチェック（PR のマージの前に通すと決めた CI の検査。`ci.required_checks`）の名前を 1 つ以上求めます。最後の合否の確かめ（最終ゲート）も、この CI の検査を待ちます。必須のチェックが無いリポジトリでは起動の引数が組めず、工程が失敗します（[ndf-stage-plan-work-prompts.md](https://github.com/devbasex/ai-plugins/blob/main/docs/specifications/ndf-stage-plan-work-prompts.md) の「運用」）
- 今のコードを読むかぎり、`ndf refactor run` が項目ごとに手元で打つのは、静的解析と、項目が触るモジュールに対応するテストです。テスト全体は打ちません（`domains/crossrefactor/verify.py`。実機では未確認）
- 工程の表は「CI テストの設定が無いリポジトリでは、まとめた検証のプランもリファクタリングのステップを持たない」と書いていますが、プランのテンプレート `check.json` はステップを常に持ちます（読解だけで、実行は未確認）

## 何を足すか・変えるか

| | 今 | 足した後 |
| --- | --- | --- |
| 工程を実行するかの決め手 | 差分にコードがあり、**かつ** CI テストの設定がある | 差分にコードがあり、**かつ**テストを確かめる手段（前提 2）がある。手段は、CI の必須のチェックか、CI テストの設定が無いリポジトリの手元で打てるテストである |
| 必須のチェックが無いリポジトリ | 条件を満たして工程に入ると、起動できず失敗する | 必須のチェックが無くても、手元のテストに合格すればこの工程を完了できます。直す所が無く変更が残らなければ、テストを打たずに完了します。確かめる手段が無い場合は理由を残して工程を飛ばし、テストに失敗した場合は停止します。スプリントが自動でこの工程まで進むには、手前の工程の修正（ https://github.com/devbasex/ai-plugins/issues/4472 ）が必要です |
| 利用者がこの工程を止める手段 | 設定はあるが、手順書に説明が無い | 同じ設定を使い、手順書に書き方を載せる |

## 今の利用者への影響と互換

- CI テストの設定が無く、テストを確かめる手段（前提 2）があるリポジトリでは、`standard`・`legacy-refactor` のスプリントに工程が 1 つ増えます。そのぶん、所要時間・LLM の token・CI の時間（手元で確かめる場合はマシンの負荷）が増えます。増やす理由は、手順書の「差分にコードがあれば必ず通す」を、どのリポジトリでも守るためです
- 増やしたくないリポジトリは、設定でこの工程を無効にすると、今と同じ工程の並びになります
- CI テストの設定があるリポジトリ（ai-plugins を含む）と、工程を設定で有効・無効にしているリポジトリの振る舞いは変わりません

## 事象

CI テストの設定を持たないリポジトリでは、工程「リファクタリング」の条件が偽になり、工程が飛ばされます。NDF 11.0.42 の判定の関数を、必須のチェックが空の一時リポジトリに対して呼んだ結果です。

```text
ci_declared = {'ci_declared': False}
default: Enablement(enabled=False, reason='ci_declared', source='definition')
stopped by project: Enablement(enabled=False, reason='手元のテストが重い', source='project')
launch without required checks: None
```

2 行目が事象、3 行目は設定で無効にできること、4 行目は必須のチェックが無いと起動の引数が組めないことを示します。

## 期待する結果

リファクタリングを通すかどうかが、テストを CI で走らせる設定の有無で決まらない。手元のテストの負荷などの事情で止めたいリポジトリは、自分の設定で止められる。

## 再現手順

1. CI テストの設定（`test.ci.only`）を持たないリポジトリで、`standard` のスプリントを作る
2. コードのファイルを変える実装を終える
3. 工程「リファクタリング」が、理由 `ci_declared` で飛ばされる

確かめたのは上の「事象」の判定の関数の呼び出しまでです。利用先の実機でのスプリントの結果は未確認です。

## 環境

NDF 11.0.42。判定の関数の確認は Linux で行いました。

## なぜ困るか

- CI テストの設定が無い利用先では、実装で入ったコードの整理が一度も行われず、直しにくい構造が積み上がります
- 利用者は工程が通ったと考えがちです。手順書の「必ず通す」は、設定があるリポジトリに限った決まりだからです
- ai-plugins で起きた一時的な事情が、NDF を使うすべてのリポジトリの制約として残っています

## 目的

差分にコードがあるスプリントでは、どのリポジトリでもリファクタリングが行われる状態にします。行わないのは、利用者が自分の設定で選んだ場合か、結果を確かめる手段が無く理由が記録された場合だけにします。

## 対象範囲

含む:

- 工程「リファクタリング」を実行するかの条件
- 必須のチェックが無いリポジトリで、工程がスプリントを止めないこと
- 手順書と確定仕様の記述（実行条件と、工程の止め方）

含まない:

- CI テストの設定がほかの場面で持つ意味（実装やまとめた検証のプランが手元のテストを持たないこと、手元のテストを止める hook など）
- 工程を無効・有効にする新しい設定の追加（今ある設定を使う）
- 利用先のリポジトリの CI や必須のチェックの用意
- 更新の前に作ったスプリントの工程の変更
- `light`・`operation`・`documentation` の工程の構成
- リファクタリング自体の進め方（項目の選び方、時間の上限の既定値など）

## 前提

- 前提 1: 条件の変更は、NDF を更新した後に作るスプリントに適用します
- 前提 2: 「テストを確かめる手段」は、次のどちらかです。必須のチェックがある。CI テストの設定が無く、`.ndf/project.json` に手元で実行するテストのコマンドがある（`test.suites`）。`kind` が `test` の設定と、`kind` を省略した設定が対象になる
- 前提 3: 工程の無効化は、スプリントを作る前に設定へ書いたものが効きます（今の振る舞いのまま）

## 受け入れ条件

- [ ] 1. 前提: CI テストの設定が無く（キーが無い）、必須のチェックがあり、差分にコードのファイルがある。操作: `standard` と `legacy-refactor` のスプリントを工程「リファクタリング」まで進める。結果: 工程は飛ばされず、リファクタリングが起動する
- [ ] 2. CI テストの設定が `false` のリポジトリでも、条件 1 と同じ結果になる
- [ ] 3. CI テストの設定があり、必須のチェックがあるリポジトリでは、今と同じく工程が実行され、手元でテストを打たない
- [ ] 4. 前提: CI テストの設定が無く、必須のチェックも無く、手元で打てるテストの設定がある。結果: 必須のチェックが無いことを理由に失敗しない。変更が残った場合は、手元でテストを実行する。合格した場合は変更を PR に送って完了（`ok`）し、失敗して直せない場合は変更を送らずに停止する。変更が残らなかった場合は、テストを打たずに完了し、打っていないことを結果に載せる（元からテストが落ちていても、この工程では検出しない）
- [ ] 5. 前提: テストを確かめる手段（前提 2）がどちらも無い。結果: コードを変えずに工程を飛ばし、飛ばした理由が進捗記録に残り、スプリントは次の工程へ進む
- [ ] 6. CI テストの設定があり、必須のチェックが無いリポジトリでも、工程の失敗でスプリントが止まらない。テストを確かめずに変更を「完了」にしない（確かめる先は未決 1）
- [ ] 7. リポジトリの設定でこの工程を無効にすると（`workflow.stages` の「リファクタリング」を `enabled: false` と理由）、CI テストの設定の有無にかかわらず工程は実行されず、その理由が記録に残る
- [ ] 8. リポジトリの設定でこの工程を有効にしたリポジトリは、今と同じく、定義の条件を見ずに実行される
- [ ] 9. 差分が文書のファイルだけのスプリントでは、今と同じく工程を飛ばす
- [ ] 10. `light`・`operation`・`documentation` のスプリントには、今と同じく工程「リファクタリング」が現れない
- [ ] 11. 工程の表（development-workflow の SKILL.md）に、新しい実行条件と、利用者が工程を止める設定の書き方（書く場所・キー・理由が必須であること・新しく作るスプリントから効くこと）が載る
- [ ] 12. 手順書と確定仕様に、「CI テストの設定が無いリポジトリではリファクタリングを通さない」という内容が、今の振る舞いの説明として残らない

条件 7・8 の今の振る舞いは、それを固定する自動テスト（`plugins/ndf/tests/progress/test_model.py`・`test_run.py`）を読んで確かめ、条件 7 の判定は上の「事象」の関数の呼び出しでも確かめました。条件 3 の「手元でテストを打たない」は、コード（`domains/crossrefactor/verify.py`）の読解で確かめています。このリポジトリは CI テストの設定があるため、手元でテストは打っていません。

必須のチェックが無いリポジトリでは、今はスプリントが手前の工程で止まります。手前の工程の手順を組み立てるのに必須のチェックの名前が要るためで、別の Issue「必須のチェックが無いリポジトリで、設計から先の手順を組み立てられない」（ https://github.com/devbasex/ai-plugins/issues/4472 ）で扱います。この Issue の設計では直さない案を、設計の承認で確かめます。その案の場合、条件 4・5 は工程の単位で確かめ、スプリントを通した確認は #4472 を直した後になります。

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 必須のチェックがあるリポジトリでは、最終ゲート（工程の最後の合否の確かめ）は CI を待ち、工程が手元でテスト全体を打たない。項目ごとに対応するテストを手元で打つのは、CI テストの設定（`test.ci.only`）が無いか `false` の場合だけで、静的解析は設定の有無によらず打つ |
| 運用・保守性 | 工程を飛ばしたときは、どの理由で飛ばしたか（設定で無効・差分が文書だけ・確かめる手段が無い）を進捗記録から区別できる |

## リリース後の確認の計画

「経路を動かすバージョン」は、確かめるときに実際に動かす NDF の版です。

| 条件 | 経路を動かすバージョン | 確かめる時点 |
| --- | --- | --- |
| 1. CI テストの設定が無いリポジトリで工程が起動する | 配ったバージョン | このリリースの後 |
| 4. 手元のテストに合格した変更が PR に送られ、完了になる | 配ったバージョン | このリリースの後 |
| 4. 手元のテストに落ちる変更は PR に送られない | 配ったバージョン | このリリースの後 |
| 5. テストを確かめる手段が無ければ、理由を残して飛ばす | 配ったバージョン | このリリースの後 |

条件 4・5 は、配った版を入れた利用先で、必須のチェックが無いリポジトリを使って次のように確かめます。#4472 を直すまではスプリントが手前の工程で止まるため、条件 4 は工程のコマンドを直接打ちます。

| 場面 | 確認の手順 | 完了条件 |
| --- | --- | --- |
| 手元で合格する | 検証用の PR の先頭に、手元で実行するテストの設定をコミットする（最終ゲートは PR の先頭の設定を読むので、手元で編集しただけの設定は使われない）。その PR の worktree で、PR の番号、PR のブランチ、差分の起点、変更を許すファイルを指定して、`ndf refactor run --pr <番号> --branch <PR のブランチ> --base <起点> --scope <ファイル> --local-test` を打つ | 結果が `ok` で、PR のブランチの先頭が、テストに合格したコミットになる。改善の項目を 1 件以上採った実行で確かめる |
| テストに落ちる | 検証用の PR で、着手時の PR の先頭では成功し、変更後のコミットでは失敗するテストを設定して、同じコマンドを打つ。例: 着手時の先頭の SHA をリポジトリの外のファイルに書き、テストのコマンドを `test "$(git rev-parse HEAD)" = "$(cat <そのファイル>)"` にする。改善の項目を 1 件以上採った実行で確かめる | 最終ゲートでテストが失敗して結果が `test_failed` になり、PR のブランチの先頭が打つ前のまま変わらない |
| 手段が無い | テストの設定も必須のチェックも無いリポジトリで `standard` のスプリントを作り、手前の工程を手で閉じて工程「リファクタリング」まで進める | 進捗記録の工程の行に飛ばした理由が残り、PR のコミットは増えず、次の工程へ進む |
