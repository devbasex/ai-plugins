# #1273: sprint-close.py が本番のリリース PR から配布の記録を読めず、スプリントの課題を毎回手で閉じる

正は課題の本文（#1273）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 依頼（原文）

> ## 何を見つけたか
>
> **`sprint-close.py` がリリース PR（#1268、10.17.30）から「## 配布の記録」を読めず、スプリントの課題を閉じられない。** 10.17.29 の後（セッション 7）と 10.17.30 の後（セッション 10）の 2 回、`gh issue close` を手で打って閉じた。
>
> ## どこで見つけたか
>
> - 10.17.30: #876 #875 #1249 を閉じるときに `sprint-close.py` が「配布の記録が読めない」で閉じる課題 0 件になった
> - 10.17.29: 記録の PR が無く exit=2
> - 10.17.45: 本番のリリース PR（#1479）と #1473 の本文とコメントにも「## 配布の記録」は無い。記録を書く処理は `plugins/ndf/scripts` に無く、`sprint-close.py` は読む側だけを持つ（`supervise_lib/sprint.py:115` が `record_pr` を本番の PR にする）
>
> ## 直さないと何が起きるか
>
> 本番の計画（`new release --channel prod`）のリリース PR の本文に「配布の記録」のブロックが入らないため、閉じる手順が毎回手作業になる。#837（承認前の記録が更新されない）とは別で、こちらは記録そのものが無い。
>
> ## 案
>
> - 本番の計画の最後のステップが、リリース PR へ `## 配布の記録`（段階: 本番・版・スプリントの PR）をコメントで足す
> - あるいは `sprint-close.py` がタグ `ndf--v<版>` と queue の done から同じ値を組む
>
> 由来: issue #1142 スプリント 2（2026-09-26 振り返り）
>
> 親 issue: #850（修正レイヤー: 配布の記録ブロックの書き手と読み手（#850 の dist-record））

## 目的

- 本番のリリースプランを通したスプリントで、まとめの `close` ステップ（`sprint-close.py`）が本番のリリースの PR からリリース記録（`## 配布の記録` のブロック）を読めるようにする。conductor が `gh issue close` を手で打つ手当て（10.17.29・10.17.30 の 2 回。10.17.55・10.17.57 でも手で閉じた。#1683）をやめられる状態にする
- 書く側の形は `progress-tracking` の「配布の記録」の表がすでに定めている（置く側は `release`、置き場所は配布の Pull Request）。読む側（`sprint-close.py`）は揃っており、欠けているのはスクリプトで組んだ本番のリリースプランの書き手である

## 前提

- 前提 1: リリース記録を置く先は、`close` ステップの `--record-pr` に入る PR、つまり本番のリリースプランの PR（`release/v<版>` → ベースブランチ。#1268 がその例）である。`sprint.py` の `close_plan` が `{queue_pr:release-prod}` をこの PR で埋める
- 前提 2: 読む側の形（見出し・`段階:`・`版:`・`スプリント:` の 3 行、本文とコメントのうち最後のブロックを読む）は変えない。書き手を `progress-tracking` の契約に合わせて足す。`sprint-close.py` がタグと queue の done から値を組む案（課題の「案」の 2 つ目）は採らない。契約の正本が 2 つになるためである（Value 6・Value 7）
- 前提 3: リリース記録を書く時点は、本番の配布（本番チャネルへのマージ・タグ・GitHub Release）が済んだ後である。承認の前に書くと、配布が止まったときに `段階: 本番` が事実と食い違う（#837 と同じ形の食い違いを新しく作らない）
- 前提 4: `版:` の行の矢印の後ろは、リリース後テストの `対象の版:` と突き合わせるため、`v` を付けない版数そのもの（例: `10.17.30`）にする。矢印の前は直前の正式版の版数である
- 前提 5: `スプリント:` の行に並べるのは、本番のリリースプランが出す版の PR として受けた一覧（`--prs` に入る PR）である
- 前提 6: 書き込みは GitHub の Pull Request へのコメント 1 件である。秘密・認証認可・利用者のデータ・他のリポジトリへの公開（C1〜C3・C5）に当たらない。書くのは記録のリポジトリの PR だけである

## 対象範囲

含む:
- スクリプトで組む本番のリリースプラン（`release.form` の雛形。今は `package-plugin`）が、本番の配布の後に本番のリリースの PR へリリース記録を書くこと
- 書けなかったときに、プランが失敗として止まり、配布をやり直さずに記録だけを書き直せること
- 本番のリリースプランの後の `close` ステップが、そのリリース記録を読んで閉じる条件 1 を満たすこと

含まない:
- 閉じる条件 2（リリース後テストのブロック `## リリース後テスト` の書き手）。本番のリリースプランは今これを書かないため、`--with-verification` 付きの `close` ステップは、この変更の後も「本番の版のリリース後テストの記録が無い」で課題を開いたまま残す。#1683 が扱う
- 開発版のリリースプランが `段階: 検証` の記録を書くこと（`close` ステップは本番のリリースの PR しか読まない）
- 承認の前に書いた記録が更新されない件（#837）。この変更は承認の前に記録を書かない
- 雛形で組まない経路（昇格のプラン・手で届ける経路・`--record-pr 0`）の記録
- 実装 PR に閉じる語が無く課題を集めきれない件（#767）
- `sprint-close.py` の読み方と閉じる条件の変更

## ドメインイベント

| # | イベント | 引き金 | 失敗したとき | 順序の前提 |
| --- | --- | --- | --- | --- |
| E1 | 本番のリリースプランが本番の配布を終えた（本番チャネルへのマージ・タグ・GitHub Release） | 承認ゲート 2 の承認（`pace: fast` / `auto` は MVV 判定）の後の `release` ステップ | 今のまま `judge` へ進む。リリース記録は書かない | 承認ゲート 2 を通った |
| E2 | 本番のリリースの PR にリリース記録を書いた | E1 が成功した | プランが失敗として止まり、`judge` から記録を書くステップだけをやり直せる（E1 をやり直さない） | E1 |
| E3 | まとめの `close` ステップが `--record-pr` を本番のリリースの PR で埋めた | まとめのステージの開始 | 本番のリリースプランの PR が見つからなければ `0`（今の振る舞い。範囲外） | E2 |
| E4 | `sprint-close.py` がリリース記録を読み、閉じる条件 1 を判定した | E3 | 記録が読めなければ全課題を `kept_open`（理由「配布の記録が読めない」。今の振る舞い） | E2・E3 |
| E5 | リリース後テストのブロックを書いた | — | — | E1（#1683 が扱う。この変更の範囲外） |

E5 の引き金が無いことは、この変更の後も `--with-verification` の判定が課題を閉じないことを意味する（「含まない」の 1 つ目）。

## 用語

| 用語 | 意味 |
| --- | --- |
| リリース記録 | release が Pull Request へ残す記録のブロック。見出しは `## 配布の記録` |
| リリースプラン | リリースの手順をステップの列として持つプラン。ここでは `package-plugin` の本番のもの |
| スプリント課題 | スプリントに含まれる Pull Request の本文が、閉じる語で指す課題 |

## 受け入れ条件

- [ ] AC1: 本番のリリースプラン（`supervise.py new release --channel prod`、`package-plugin` の形）が、本番の配布のステップより後に、本番のリリースの PR へリリース記録を書くステップを持つ。開発版のリリースプランはこのステップを持たない
- [ ] AC2: 書かれたリリース記録は、`## 配布の記録` の見出しの直後に `段階: 本番（…）`・`版: <直前の正式版> → <出した版>（…）`・`スプリント: PR #<番号> / #<番号>…` の 3 行を持ち、`sprint-close.py` の `parse_record` に渡すと `found` が真、`stage` が `本番` で始まり、`version` が出した版（`v` なし）、`sprint_prs` がプランの受けた PR の番号の並びになる
- [ ] AC3: 偽の `gh` で、本番の配布が成功した後のリリース記録を書くステップを流すと、本番のリリースの PR へコメントが 1 件投稿される。本番の配布が失敗したときは、記録のコメントは投稿されない
- [ ] AC4: リリース記録を書くステップが失敗する（`gh pr comment` が非 0 で終わる）と、プランはそのステップの失敗として `judge` へ進み、成功として終わらない。そのステップからやり直しても、タグの作成・GitHub Release・本番チャネルへのマージは 2 度目が走らない
- [ ] AC5: AC2 のリリース記録を本文かコメントに持つ PR を `--record-pr` に渡し、`--with-verification` を付けずに `sprint-close.py --dry-run` を打つと、`--issues` に渡した OPEN の課題が `would_close` になる（「配布の記録が読めない」の `kept_open` にならない）
- [ ] AC6: 退行しない: `sprint-close.py` の既存のテスト（`test_sprint_close_issues.py`・`test_sprint_close_merge_green.py`・`test_legacy_names.py`）と、リリースプランの既存のテストがすべて通る
- [ ] AC7: 退行しない: リリース記録の形の正本は `progress-tracking` の「配布の記録」の表 1 か所のままで、書く側のコードがこの形と食い違わない（AC2 を書く側の出力から作るテストで確かめる）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | リリース記録の書き込みの失敗は、本番の配布そのものを取り消さない。失敗はプランの失敗として見え、記録だけを書き直せる（AC4） |
| 運用・保守性 | 読む側と書く側で同じ見出しと行の名前を使う（同じ役割の定数を 2 か所に持たない。Value 6） |
| セキュリティ | 書く先は記録のリポジトリの PR だけで、秘密を本文に含めない |
