## 何が起きたか

2026-10-17、PR #2043（#1873。11 ファイル・33 行）の検査のプラン（`supervise.py new check --pr 2043`）で、構造改善（`refactor`）のステップが終了コード 1 で落ち、プランは abort へ進んだ。

- 出力: 「`--budget-minutes` を 39 以上にして 5 分以内に init を打ち直すと、着手前のテストを走らせ直さずに続けます（下限では 1 件だけが入ります）」
- プランの `refactor` の cmd は `--budget-minutes` を持たず（`.ndf/supervise.json` に `refactor_budget_minutes` も無い）、timeout は 1980 秒だった
- `new check --refactor-budget-minutes 40` で書き直し、`run --from refactor` で再開した

## 問題

- `new check` が書く既定の予算が、cross-refactoring の下限（着手前のテストの時間から求める値）を下回り、小さな差分でも必ず落ちる。下限は init が知っているのに、プランを書く時点で予算へ反映されていない
- 落ちたときは abort へ進み、検査の記録も「落ちた」になる。案内の「5 分以内に打ち直す」は、無人のキューでは間に合わない

## 依頼（案）

- `new check` / `new sprint` の検査のプランが、予算を下限以上にして書く（予算を省いたときは下限を使う）か、`refactor` の下限不足を abort ではなく予算を上げての打ち直しへつなぐ

## 目的

- 検査のプラン（`supervise.py new check` / `new sprint` / `new close` が書くプラン）のリファクタリングのステップが、想定最大時間の既定値（30 分）と着手前のテストの上限の決め方のせいで落ち、検査が abort へ進むことを無くす
- 無人のキューで、人が想定最大時間を書き直して打ち直さなくても、検査がコードレビューまで進む状態にする

## 前提

- 前提 1: 「想定最大時間を明示した」とは、`--refactor-budget-minutes` の引数か `.ndf/supervise.json` の `refactor_budget_minutes` で想定最大時間を書いたことを指す。どちらも無いときを「想定最大時間を省いた」と呼ぶ
- 前提 2: 想定最大時間を省いたときに想定最大時間を下限まで上げることに、別の上限は設けない。費用の上限を持ちたい利用者は `refactor_budget_minutes` を書く（前提 1 の明示になり、受け入れ条件 5 の扱いになる）
- 前提 3: 初回の上限に使う既知の所要は、手元の全体テストの直近の実測（`whole_runs` の記録）を先に採り、無ければ `.ndf/project.json` の `test_duration` を採る。どちらも無いときは今の値（想定最大時間の 10%）のままにする
- 前提 4: 全体テストそのものを速くする作業は #2291 が持つ。この課題は、テストが遅いままでも検査が止まらないことだけを受け入れ条件にする
- 前提 5: この変更より前に書き出したプランのファイル（`--budget-minutes` を持たない `refactor` の cmd と、既定の想定最大時間から求めた timeout）は書き直さない。新しい振る舞いは、この変更の後に書いたプランから効く

## 対象範囲

含む:
- 着手前のテストの初回の上限の決め方（既知の所要を読む）
- 想定最大時間を省いたときの、リファクタリングの想定最大時間の決め方（下限を下回らない）
- 想定最大時間を省いたときの、プランの `refactor` のステップの timeout（リファクタリングの実行中に切れない）
- リファクタリングが時間の枠に収まらないときの、プランの進み方（abort ではなくコードレビューへ進む）と検査の記録
- `new check` / `new sprint` / `new close` の 3 つの雛形（どれも同じリファクタリングのステップを書く）

含まない:
- 全体テストを速くすること（#2291）
- 打ち切ったときに子のプロセスが残る問題（#2285）
- 再開で前回の時間枠を引き継ぐ問題（#1944）
- cross-refactoring の枠の配分（提案 0.20·B・リファクタリング計画 0.10·B・打ち直しの見込み 300 秒）の見直し
- 想定最大時間の既定値（30 分）そのものの変更

## 用語

| 用語 | 意味 |
| --- | --- |
| 想定最大時間 | 用語集のとおり（`--budget-minutes`）。プランでは `--refactor-budget-minutes` か `.ndf/supervise.json` の `refactor_budget_minutes` で渡す。本文の「依頼（原文）」の「予算」はこの語を指す |
| 想定最大時間の下限 | 着手前のテストの実測 x から求める、手順の枠が収まる想定最大時間の最小値（`timeline.required_budget_minutes`）。init が「`--budget-minutes` を N 以上に」と案内する N |
| 着手前のテスト | `refactor.py init` が改修の前に走らせるテスト（範囲テストか全体テスト） |
| 着手前のテストの初回の上限 | 同じ範囲の打ち切りの記録が配分の履歴に無いときの、着手前のテストの上限（秒） |

## 受け入れ条件

- [ ] 1. 手元の全体テストの直近の実測 m（`whole_runs` の記録）があり、同じ範囲の配分の履歴が無いとき、着手前のテストの上限は 3·m 秒以上になる（例: m = 620 秒なら 1,860 秒以上。今は想定最大時間 30 分の 10% の 180 秒）
- [ ] 2. m が無く `.ndf/project.json` の `test_duration` の所要 w があるとき、着手前のテストの上限は 3·w 秒以上になる。m も w も無いときは今と同じ想定最大時間の 10% になる
- [ ] 3. 想定最大時間を省いたとき、着手前のテストの実測 x から求めた下限が既定の想定最大時間（30 分）を超えても、`refactor.py init` は「`--budget-minutes` を N 以上に」で止まらず（終了コード 4 を返さず）、想定最大時間を下限以上にして続ける。使った想定最大時間と、それを下限から決めたことが状態ファイルと標準出力に残る（例: x = 495 秒で、今は止まる入力が通る）
- [ ] 4. 想定最大時間を省いて書いたプランの `refactor` のステップは、受け入れ条件 3 で上げた想定最大時間でリファクタリングが終わる前に、ステップの timeout で切られない
- [ ] 5. 想定最大時間を明示し、下限がその想定最大時間を超えるとき、および着手前のテストが上限で打ち切られたとき、プランは abort へ進まずコードレビュー（`review`）へ進む。検査の記録とフェーズレポートには、リファクタリングを「時間の枠に収まらず飛ばした」ことと、理由（要る下限の分、または打ち切った上限の秒）が残り、「落ちた」とは書かれない
- [ ] 6. 想定最大時間を明示し、下限がその想定最大時間以下のときの振る舞い（想定最大時間・上限・枠の配分）は今と変わらない
- [ ] 7. 起動の失敗・最終ゲートの失敗など、時間の枠と関係のない理由でリファクタリングが落ちたときは、今と同じく abort へ進む（受け入れ条件 5 の経路に混ざらない）
- [ ] 8. `new check` / `new sprint` / `new close` の 3 つの雛形のどれで書いたプランでも、受け入れ条件 3〜5 が同じに効く

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 受け入れ条件 1・2 の上限は、テストが固まったときに待つ時間の最大を延ばす。延びる分は既知の所要の 3 倍までにとどまる |
| 運用・保守性 | 想定最大時間を下限から決めたこと（受け入れ条件 3）と、リファクタリングを飛ばしたこと（受け入れ条件 5）は、人が後から記録だけで経緯を追える |
| 移行性 | 書き出し済みのプランは書き直さない（前提 5）。古いプランで止まったときは、今と同じく `--refactor-budget-minutes` を付けて書き直す |
