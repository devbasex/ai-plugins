## 具体例

2026-11-01、利用者は 3 本の開発ループを並列で回すと決めた（Factory の `l20261031`・根本解決の `lroot`・開発フローの見直しの `lflow`。引継ぎ文書 `.ndf/handoff/loop-*.md`）。今のラッパー（`relay.py`）では、利用者が端末を 3 つ開き、それぞれで `claude` を打ち、文書の `ndf-next` のコマンドを手で貼る必要がある。

- 3 本のどれが動いていて、どれが止まり、どれが承認待ちかを一目で見る手段が無い
- `relay.py stop` は 3 本すべてを止める。1 本だけを止められない
- 端末を閉じるとそのラッパーが終わる
- conductor（m26 を回しているセッション）が「3 本のループを始める」と決めても、自分では起動できない
- 3 本が同じアカウントの 5 時間の枠を 3 倍の速さで使うが、枠を見るのは区間ごとのラッパーで、3 本をまとめて見ていない

この課題が終わると、2 本目の `claude` を打てばその端末が tmux の window の中の新しいラッパーへ結び付き、`relay.py ls` で 3 本の状態と承認待ちが 1 つの表で見え、`relay.py stop lroot` で 1 本だけを止められる。

## 目的

- 同じコンテナで複数の開発ループを並列に回すとき、利用者が端末を開いてコマンドを貼る手間をなくし、どのループが動き・止まり・承認待ちかを 1 か所で見て、1 本ずつ止め・やり直し・結び付け直せる状態にする
- conductor が自分の判断で別の開発ループを起動できるようにする（人の手を止めない。Value 2）

## 前提

- 前提 1: 構成は案 B に従う。tmux がラッパーごとの端末の親になり、各 window で今の `relay.py run` を動かす。統括役は登録・起動・方針・一覧だけを持ち、各ラッパーの状態機械（区間の切り替え・`ndf-next` の拾い方・質問シグナルファイル）を変えない（S1。承認ゲート 1 で確かめる）
- 前提 2: 1 本目の `claude` は今どおり利用者の端末の前景で動き、tmux の中へ移さない。1 本目の端末を閉じれば 1 本目のラッパーは今どおり終わる。統括役の役目は、そのとき受け入れ条件 21 に従って次の `claude` へ移る
- 前提 3: 端末から打った 2 本目以降の `claude` に名前の指定が無いときは、統括役が重ならない名前を自動で付ける。名前の形は設計で決める
- 前提 4: 利用者のシェルの設定（`claude` の alias・関数）を書き換える手段は、今の `relay.py install` が置いたものの範囲に留める。新しく利用者のシェルの設定へ書き込む必要が出たら、設計で止めて人へ戻す（共通原則 C6）
- 前提 5: 区間の数・最後に動いた時刻は各ラッパーの作業ディレクトリの記録から読める。使った費用はラッパーが記録を持っていない区間があり得るため、読めないときは空の値（`null`）で出し、0 と書かない
- 前提 6: アカウントの 5 時間の枠の使用率はアカウントごとの値で、どのラッパーが読んでも同じ値になる（今の `relay_lib/switch.py` の読み方）。ラッパーをまたいだ枠の数え方は、この値を共有することで満たす
- 前提 7: 承認待ち通知は、今ある待ち通知（`lib/notify.py`・`lib/wait_notice.py`）の経路を使い、通知先を新しく足さない
- 前提 8: 対象は 1 つのコンテナ（1 つの OS の利用者）の中だけで、ほかのコンテナや機械のラッパーは統括しない
- 前提 9: 対象のランタイムは Claude Code だけである（ラッパーが Claude Code だけのため）。Codex は対象外

## 対象範囲

含む:
- 2 本目以降の `claude` が統括役に起動を頼み、tmux の window へ結び付く入口
- 副命令 `relay.py spawn`・`ls`・`attach`・`restart`、名前つきの `stop`
- conductor の応答から名前つきのラッパーを起動する口
- 同時に動かすラッパーの数の上限の宣言と判定
- 統括役が落ちたときの引き継ぎ、tmux の無い環境での今の起動への戻り
- 一覧と通知での承認待ちの表示

含まない:
- 統括役が claude の擬似端末の親になる形（案 A）
- 複数のコンテナ・機械をまたいだ統括
- Factory の実行ジョブの指示でラッパーを起動する入口（手元のランナー #2189 が担う。ここでは語と形を揃えるだけ）
- 各ラッパーの区間の切り替え・`ndf-next` の拾い方・アカウントの切り替えの規則そのものの変更
- tmux の導入（入っていなければ今の起動に戻るだけで、入れない）
- 同時に流すプランの合計の上限（未決 1）

## 用語

| 用語 | 意味 |
| --- | --- |
| 統括役 | 同じコンテナで最初に起動したラッパーが兼ねる役。ほかのラッパーの登録・起動・同時に動かす数の判定・一覧だけを持ち、各ラッパーの状態機械には触れない。課題の本文の「ホスト」に当たる（用語集の「ホスト」は cross-review の収束ループを起動する CLI を指すため使わない） |
| 名前つきのラッパー | 統括役に名前で登録され、tmux の 1 つの window で動く `relay.py run` の 1 本。カットポイントで区間（セッション）を切り替えても同じ名前で続く。課題の本文の「セッション」に当たる（用語集の「セッション」は claude の 1 回の起動を指すため使わない） |
| 端末の結び付け | 利用者の端末を、名前つきのラッパーの tmux の window へ attach すること。端末を閉じても window の中のラッパーは動き続ける |

## 背景

### 今の仕組み（2026-11-01、`plugins/ndf/scripts/relay_lib/`）

| --- | --- |
| 起動 | `claude` の alias が `relay.py run` を前景で起動し、ラッパーが claude を擬似端末の子として 1 つ持つ（`run.Relay`・`terminal.Terminal`、ptyprocess） |

### Neural Development Factory との関係（2026-11-01 に確かめた）

Factory（確定仕様 `docs/specifications/ndf-factory-runs-and-runner.md`）は、並行を**サービスの側**で持つ。スプリントの実行 1 本を実行ジョブ（ECS Fargate のタスク 1 つ）で動かし、conductor は端末の無い `claude -p` で起動する。同時に動かせる数は「実行の枠」（アカウントごと・リポジトリごと。プランの表で上限 3 など）が開始のトランザクションで数える。承認ゲートで止まったら状態を S3 へ保存してジョブを終え、答えで別のコンテナが続ける。人は端末でなく画面（#2172 一覧・詳細、#2173 承認と通知）で見る。

この課題と重なるのは **手元のランナー（#2189）** である。どちらも「利用者の機械の上で、複数の claude を起動し、見て、止める常駐のプロセス」になる。

| | この課題（ラッパーの統括役） | #2189（手元のランナー） |
| --- | --- | --- |
| 起動の出所 | 端末の `claude`・conductor の応答・`relay.py spawn` | Factory の実行ジョブの指示（サービスから受け取る） |
| claude の形 | 対話の端末（tmux の window） | 端末の無い `claude -p` |
| 見る場所 | `relay.py ls` と tmux | Factory の画面 |

起動・一覧・停止の口を Factory の契約と同じ語と形で持てば、#2189 は統括役に「Factory から受け取った指示で起動する」入口を足すだけで作れる。`plugins/` は `factory/` を参照しないため、共有するのは契約の形だけである（受け入れ条件 26・27）。
