# 並列の計画の別のリポジトリのレーンと計画の外のセッション: 決定の記録（#2733）

設計文書 [issue-2733-design.md](issue-2733-design.md) の決定の記録である。語の置き換えの対象と量は [issue-2733-design-terms.md](issue-2733-design-terms.md) にある。

## 別のリポジトリのレーンと計画の外のセッション（決定 1〜9）

### 決定 1: 別のリポジトリのセッションが計画を見つけられるよう、マシンに計画の所在の一覧を置く

`parallel.py init`・`start`・`lane add` が `$XDG_STATE_HOME/ndf/parallel/homes/` へ置き場を書く。レーンの判定と起動の判定が、それを読む（STD1）。一覧は置き場を指すだけで、計画の中身を写さない。

レーンの判定は今、自分のメインディレクトリの `.ndf/parallel/` しか探さない。計画の置き場の絶対パスが分かれば、耐久ワークフローの記録は今のキーのまま開ける（LIB1）。足りないのは「マシンのどこに計画があるか」だけである。計画の外のセッションの判定も「マシンに動いている計画があるか」を知る必要があり、同じ一覧で足りる。

レーンの起動のときに計画の置き場を環境変数で渡す形は採らない。手で起動したレーンと再起動したレーンには環境変数が渡らない。計画の外の判定では、マシンのすべての計画を数える必要がある。どちらにも一覧が要る。リレーハブの登録簿のオーガナイザーの作業ディレクトリから計画の置き場を導く形も採らない。オーガナイザーのセッションは切り替わり、止まっている間も計画は動く。所在を計画より短命なセッションに頼ることになる（#2647 の根本原因 A と同じ形）。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1・LIB1

根拠: Value 7 / Value 6（MVV 版 6）

### 決定 2: 同じ記録を読み書きするため、記録のキーを変えず、レーンの側の置き場を計画の置き場から求める

依頼・答え・止める指示はすべて計画の置き場の側にある。レーンの判定は、計画の置き場（`home`）とレーンのリポジトリ（`repo`）の 2 つを返す。送る・読む処理は `home` を使い、自分のループの記録と引継ぎ文書は `repo` を使う。オーガナイザーの側は逆に、レーンの記録を読むときと設計 PR をマージするときだけ `repo` を使う。

記録をレーンのリポジトリへコピーし、2 か所を同期する形は採らない。同じ状態を 2 か所で持つと、どちらが正かを決める規則が要り、片方の書き込みの失敗が食い違いになる。

根拠: Value 7（MVV 版 6）

### 決定 3: レーンのリポジトリを計画の宣言で読めるよう、レーンに任意の `repo` を足す

計画の宣言は計画の正本で、オーガナイザーと人が読む `plan.md` もここから描く。レーンのリポジトリを宣言に書けば、検査（`I20`）・描画・起動の `cwd`・記録の読み先が 1 か所から決まる。省いた計画は今のまま読める。

セッションの起動の場所（リレーハブの登録簿の `cwd`）から導く形は採らない。手で起動したレーンは別の場所で起動しうるため、判定の正しさが起動の仕方に依存する。レーンの判定は、宣言の `repo` と自分のメインディレクトリが一致する計画だけを当て、違う場所で起動したセッションを別の計画のレーンにしない。

根拠: Value 6 / Value 8（MVV 版 6）

### 決定 4: リリースの中身を混ぜないため、別のリポジトリのレーンは自分のリポジトリの設定で本番を出す

別のリポジトリのレーンはリリースの依頼を送らず、今の本番のステージを組み、リリース承認ゲートの問いだけをオーガナイザーへ送る。まとめたリリースの対応づけ（`map_lanes`）からも外し、課題番号の重なりで別のリポジトリの課題を誤って結ばない。

まとめたリリースは計画の置き場のリポジトリの 1 本の `main` と版を組む。別のリポジトリの変更は版もチャネルも違うため、同じリリースに入れられない。

まとめたリリースを複数のリポジトリへ広げる形は採らない。リポジトリごとにリリースの設定が違い、まとめる利点（1 回の承認で 1 本の版）が成り立たない。

根拠: Value 2 / C5（MVV 版 6）

### 決定 5: 対話だけのセッションを止めないよう、計画の外の判定を開発ループとスプリントの起動のエントリポイントに置く

判定は `sprint-state.py loop start` と `supervise.py new sprint` の、何かを書く前に置く。前提 3 は、開発ループもスプリントも始めない対話だけのセッションを対象外とする。セッションの開始の hook で判定すると、対話も止まる。リレーハブの `spawn` に置く形は採らない。人が端末で起動したセッションは `spawn` を通らない。

根拠: Value 2（MVV 版 6）

### 決定 6: 窓口を割らないことを優先し、計画の状態を読めないときは止める

計画の所在の一覧にある計画の状態が読めないとき、動いているかは分からない。通すと、動いている計画の横で窓口が割れる状態を判定の失敗が作る。止める出力には読めなかった計画と例外の起動の 1 行を出すので、人は理由を添えて進められる。読めない計画を読み飛ばして通す形は採らない。記録が壊れた計画が 1 つあるだけで、止める仕組み全体が働かなくなる。

根拠: Value 2 / Value 7（MVV 版 6）

### 決定 7: 例外を人が選んだと記録に残すため、例外の起動は理由つきのコマンドの指定だけで通す

例外の起動は `--outside-plan <理由>` だけで通し、理由と時刻とリポジトリを記録に残す。環境変数での指定は採らない。シェルの設定に残ると、利用者が選んだと分からないまま毎回の起動が通る。

根拠: Value 8 / Value 2（MVV 版 6）

### 決定 8: 動いている計画を止めずに上限を変えられるよう、レーン数の上限をマシンの設定のファイルで持つ

`relay.py limit --named <n>` が `$XDG_STATE_HOME/ndf/relay/hub/limits.json` に書く。リレーハブの判定と計画の検査が、毎回同じ関数で読む。順序は設定のファイル → 環境変数 → 既定 3 で、環境変数の利用者はそのまま動く。

今の上限は `NDF_RELAY_MAX_NAMED` で、リレーハブのプロセスの環境から読む。リレーハブは最初に起動したラッパー（多くはオーガナイザー）が兼ねる。そのため、環境変数を変えるにはオーガナイザーを起動し直す必要がある。

上限を計画ごとの宣言に置く形は採らない。上限はマシンの資源を守る値で、複数の計画と計画の外のラッパーに共通である。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1

根拠: Value 5 / Value 6（MVV 版 6）

### 決定 9: 計画と描画と引継ぎ文書が食い違わないよう、動いている計画のレーンの追加と書き換えをコマンドにする

`parallel.py lane add`・`set` が検査（上限を含む）を通してから、`plan.json`・`plan.md`・引継ぎ文書の 3 つを書く。書いた後に、耐久ワークフローへ `lanes_changed` を送る。耐久ワークフローは耐久ステップで計画を読み直すため、記録の再生でも同じ計画を読む。レーンの名前と `repo` は `set` で変えない（決定 13）。

今は `plan.json` を手で書き換えており、`plan.md` の描き直し忘れと古いループ名が残った（並行開発のモデルの文書の「欠けている規定」の 1・2 行目）。

手順書に手の書き換えの手順だけを書く形は採らない。決まった手順はスクリプトが進める（Value 5）。

根拠: Value 5（MVV 版 6）

## 語（決定 10〜17）

### 決定 10: 統括役が判断する役に読めないよう、語をリレーハブへ改める（語の決定 5）

実体は `relay.py` のプロセスで、判断を持たない。「役」は人か AI を思わせる。コード上の名前 `relay_hub` と語がそろう。統括役は用語集の廃止語に載せ、`glossary.py check` が言い換えを出す。識別子と状態のファイルの名前は変えない（決定 15）。

根拠: Value 8（MVV 版 6）

### 決定 11: 利用者と #2710 の使い方にそろえ、ランナーをマシンの意味に統一する（語の決定 1）

利用者と資源の課題はランナーを「作業を動かす 1 台」の意味で使う。製品の用法も、ジョブを実行するシステムをランナーと呼び、そこで動くソフトウェアを呼び分ける例がある（PRD1）。一方で、アプリケーションをランナーと呼ぶ製品もある（PRD2）ため、用語集で 1 語 1 意味に決める。Factory の実行ジョブの中のプログラムは「ランナーのエージェント」と呼ぶ。`手元のランナー` を廃止語から外す。CI のランナーとテストのランナーは複合語で指す対象が決まるため書き換えない。

今の意味（プログラム）を残し、マシンを「マシン」と呼び続ける形は採らない。利用者の使い方と食い違ったままになり、語の混乱の出所が残る。語は PR 2723 の文書の語の決定 1 で決まった（量と I68 の扱いは [issue-2733-design-terms.md](issue-2733-design-terms.md) ）。

- 作り方: 標準に倣う
- 比べた候補: PRD1・PRD2

根拠: Value 8（MVV 版 6）

### 決定 12: ラインをレーンへ統一するため、ラインをレーンの廃止語にし、検査がカタカナの複合語を拾わないようにする（語の決定 2）

PR 2723 の文書の語の決定 2 は、ラインをレーンと同じものとし、語をレーンへ統一する。説明文で単独の「ライン」を使う箇所は 0 行で、置き換えは要らない。用語集のレーンの `deprecated` へラインを足すだけで、`glossary.py check` が言い換えを出す。

ただし、検査は日本語の廃止語を部分一致で拾うため、ガイドライン・ステータスラインのように用語集に無い複合語も「レーン と書く」と出る。カタカナだけの廃止語は、前後がカタカナのときに一致させない規則を `glossary.py` の `word_pattern` に足す。複合語を 1 つずつ用語集へ生きた語として載せる形は採らない。用語集に業務の語でない複合語が増え、新しい複合語が出るたびに検査が誤って落ちる。廃止語のほうを `deprecated` に書かない形も採らない。言い換えを出すことが受け入れ条件 12 である。

根拠: Value 7 / Value 8（MVV 版 6）

### 決定 13: レーンの名前と担当が食い違わないよう、レーンの名前に役割を含めない（語の決定 4）

レーンの名前はリレーハブのラッパーの名前で、答え待ちの停止・再開の印・依頼の持ち主のキーになる。役割の変更で改名すると、これらのキーが変わる。名前は役割を含めない短い名前（`lane1` など）とし、役割は計画の宣言の入力と `plan.md` で読む。手順書の「レーンごとに決めること」に書く。検査では強制しない（今の計画 p3 の名前を変えずに入れるため）。

改名の手順を作る形は採らない。キーを持つ記録をすべて書き換える必要があり、動いている計画では戻せない。

根拠: Value 3 / Value 8（MVV 版 6）

### 決定 14: 並列の計画の語を 1 つにするため、並列の計画ではオーケストレーターを使わない（語の決定 3）

並列の計画の意味でオーケストレーターと書いた箇所は無い。cross-review・cross-refactoring 以外の 130 行は、実行計画とスプリントの複数の Pull Request を回す役の意味である。並列の計画の手順書・確定仕様・並行開発のモデルの文書では、オーガナイザーだけを使う。用語集のオーガナイザーの意味に「並列の計画のまとめ役は、オーケストレーターと呼ばずオーガナイザーと呼ぶ」を足す。cross 系と実行計画のオーケストレーターは別の意味として残す（要求の「含まない」）。

根拠: Value 8（MVV 版 6）

### 決定 15: 置き換え前の記録をそのまま読むため、語の置き換えは説明文と表示の文字列だけにする

JSON のキー・環境変数・状態のファイルの名前・コード上の名前（`relay_hub`・`lap`・`--lap`・`laps.md` など）は変えない（要求の「含まない」、受け入れ条件 11）。スクリプトの出力では、利用者に見える文字列（`relay.py ls` の列の見出し、問いの hook の案内など）だけを置き換え、キーは変えない。

根拠: Value 1 / Value 3（MVV 版 6）

### 決定 16: 周回の言い換えを書き手によらずそろえるため、元の形ごとの言い換えの規則の表を置く（語の決定 6）

周回は 651 行あり、前後の語との組み合わせ（周回の境・次の周回・周回の数・保留の周回など）が多い。「ループの 1 回」を機械的に差し込むと「ループの 1 回の数」のような読めない形になる。そこで、元の形ごとの言い換えを表で決め（[issue-2733-design-terms.md](issue-2733-design-terms.md) の「周回」）、表に無い形が出たら表へ足してから直す。用語集では周回の項目を「ループの 1 回」へ置き換え、周回を廃止語に載せる。周回を名前に含む 2 つの項目（保留の周回・周回の費用の内訳）も名前を変える。残すと、生きた語の内側の一致として周回が検査から外れ、廃止語の言い換えが働かない。

周回を言い換えずに定義だけ足す形は採らない。利用者の指示（受け入れ条件 12）が言い換えを求める。量が多いため、語の置き換えのスプリントを 2 つに分けてよい（分け方は `implementation-plan` が決める）。

根拠: Value 8 / Value 2（MVV 版 6）

### 決定 17: supervisor の主と代行の向きを 1 つにするため、定義を 1 文に決めて 5 か所へ同じ文で書く（語の決定 7）

利用者は supervisor の役割を `supervise.py` が主に担い、対応できないときだけサブエージェントが代行すると定めた。この定義の文へ、用語集・`agent-layers.md` の 2 か所・`supervise.py` の docstring・2 つのエージェント定義の `description` をそろえる。

今の用語集は supervisor をサブエージェントと定義している。手順書と `supervise.py` の docstring は `supervise.py` を「代わり」と書いており、向きが逆である。エージェントの名前（`ndf:supervisor`）と `supervise.py` のファイル名は変えない。改め方は #2042 が持つ。

正本を用語集だけにして、ほかを用語集への参照に置き換える形は採らない。エージェント定義の `description` は起動の判断に使われる短い文で、参照では役割が読めない。

根拠: Value 8（MVV 版 6）
