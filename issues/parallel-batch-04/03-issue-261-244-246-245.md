## 用語

| 語 | この文書での意味 |
| --- | --- |
| レビュアー | レビューを実行する側の AI。`codex` と `gemini` の 2 つ |

## 設計

### 手順書から参照へ移す（#245）

新しい参照 `docs/03-review-output.md` を作り、次の 4 節を移す。

| 移す節 | 行数 | 何を書いているか |
| --- | --- | --- |
| レビュー出力の制約 | 59 | 投稿の書式、インラインコメントの絞り込み、判定の付け方 |
| CI failure の分類（誤中断防止） | 15 | 継続的統合の失敗を中断と継続へ分ける規則 |
| アンチパターン | 25 | 過去に踏んだ形の一覧 |
| monitor.py が誤って kill する場合の手順 | 23 | 誤検知の切り分けと回避 |

移した後の手順書は約 385 行になり、余白は 115 行である。

**移す先を既存の 2 本にしない。** `docs/01-state-and-review.md` は 507 行、
`docs/02-fix-and-rotation.md` は 433 行で、どちらも足すと文書の分割の基準（501 行以上は
分割）を超える。

**移すのは、実行の途中で読まなくてよい内容に限る。** レビュー出力の制約はレビュアーの
起動スクリプトが同じ内容を持っており、手順書の側は規約の記録である。継続的統合の分類は
修正の取り込みが判定に使う。どちらも骨組みの実行に必要な行ではない。

手順書には、移した見出しと読む場面を表で残す。

### 投稿が届いていないことの判定（#261）

結果ファイルを取り込む処理（`cmd_read_result`）へ、投稿が届いたかの確認を足す。

| 結果ファイルの状態 | 扱い |
| --- | --- |
| `post_error` に値がある | 届いていない |
| `review_url` が空、または識別子を取り出せない | 届いていない |
| 識別子から照会して、レビューが存在する | 届いた |
| 識別子から照会できない（通信の失敗など） | 申告を採用し、確認できなかったことを出力へ残す |

届いていないときは、結果なしとして記録してから止める。記録の理由は `not_posted` とする。
既存の記録の仕組み（`_record_no_result`）をそのまま使うため、判定の側は変更しない。

```text
結果ファイル → 届いたか → 届いていない → 結果なしとして記録 → 判定が起動し直す（exit 7）
                       → 届いた       → これまでどおり取り込む
```

**判定（`cmd_judge`）は変更しない。** 結果なしを起動し直しへ回す経路は v9.4.0 で入っており、
そこへ乗せる。修正の担当から見ると、結果が残らなかった場合と、結果はあるが指摘が届いて
いない場合は同じ状態である（読むべき指摘が無い）。

既存の件数の突き合わせ（申告が 1 以上のとき GitHub 側と数を比べる）は残す。届いたことの
確認と、届いた数の確認は別の問いである。

### 巻き直しの後の枝名（#244）

`set-current-pr` へ、新しい枝名を渡す引数を足す。巻き直しのスクリプトは light と squash の
どちらでも `NEW_BRANCH=` を出力しているため、骨組みはその値を渡す。

| 枝名の決め方 | 条件 |
| --- | --- |
| 引数で受け取った値 | 骨組みが `NEW_BRANCH` を渡したとき |
| 新しい Pull Request から取り直す | 引数が無いとき（`gh pr view <番号> --json headRefName`） |
| 既存の値を残す | 取り直せないとき。取れなかったことを出力へ残す |

**取り直せないことで進行を止めない。** ラウンドの開始時の同期が毎回取り直すため、古い値の
ままでも次のラウンドで書き戻される。ここで止めると、巻き直しの直後だけ進めなくなる。

### 振動の測り方（#246）

指摘の同一性を 3 つの一致で測る。いずれか 1 つで結びつけば、同じ箇所として数える。

| 一致 | 条件 |
| --- | --- |
| 位置の一致 | ファイルが同じで、行が同じ |
| 近傍の一致 | ファイルが同じで、行の差が 3 以内 |
| 本文の一致 | ファイルが同じで、正規化した本文が同じ |

本文の正規化は、小文字へ揃え、英数字以外を落とし、先頭 80 文字を取る。行番号・引用符・
記号の違いで別物にならないようにする。

重なりの比は、現ラウンドの指摘のうち前ラウンドと結びついたものの割合とする。閾値は 0.5 の
まま変えない。

出力には内訳を出す。

```text
振動検知: overlap=3/5 (60%) 位置=1 近傍=1 本文=1
```

**行を持たない指摘は対象外のままとする。** 明細ファイルに載るのはインラインの指摘だけで、
総評に書かれた指摘は行を持たない。対象を広げると、総評の書き方の揺れで比が動く。

## 決定の記録

### 参照を 1 本増やす

既存の 2 本へ足す形も採れるが、どちらも分割の基準に近い。役割で見ても、既存の 2 本は実行の
手順（状態とレビュー / 修正と巻き直し）であり、移す 4 節は出力の規約と運用の切り分けである。
同じ文書に混ぜると、実行中に読む部分と読まない部分が混ざる。

### 届いたかの確認を、取り込みの側に置く

判定の側に置くと、結果なしの経路が 2 か所に分かれる。取り込みの側で結果なしとして記録すれば、
判定は既存のまま 1 つの経路で扱える。`cross-refactoring` が v8.5.3 で入れた確認と同じ位置になる。

### 照会できないときは申告を採用する

通信の失敗で止めると、GitHub 側の一時的な不調でループが止まる。既存の件数の突き合わせも同じ
扱いにしてあり、そろえる。確認できなかったことは出力へ残す。

### 近傍の幅を 3 行とする

修正で指摘の位置が前後にずれる幅として、同じ処理のまとまりの中の移動を拾い、隣の指摘まで
巻き込まない値を採る。**この値の根拠となる実測はまだ無い。** 定数を 1 か所へ置き、あとから
変えられる形にする。内訳を出力へ出すのは、実測を集めるためである。

### 閾値を据え置く

一致の条件を広げると、重なりの比は現状より大きくなる方向にしか動かない。閾値も同時に動かすと、
どちらの変更が結果を変えたのかが分からなくなる。閾値は 0.5 のままとし、内訳の記録が貯まって
から見直す。

**残リスク（未確認）**: 一致の条件を広げたことで、収束へ向かっている進行を振動として止める
回数が増える可能性がある。内訳の出力で、どの一致で止まったのかを追える形にしておく。
