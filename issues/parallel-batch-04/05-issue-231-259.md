# 担当 E — 工程の記録と、閉じ忘れる issue（#231 / #259）

- issue: [#231](https://github.com/devbasex/ai-plugins/issues/231) / [#259](https://github.com/devbasex/ai-plugins/issues/259)
- ブランチ: `fix/issue-231-workflow-records`
- モード: `standard`

この文書は仕様と設計の両方を持つ。`standard` のため設計は独立したファイルにせず、同じ
ファイルの別の節として置く（`design` の規約）。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| 盤面 | 進行を記録する GitHub Projects のプロジェクト 1 つ |
| 工程表 | `development-workflow` の「モードごとに起動する Skill」の表 |
| 対応表 | `development-workflow/references/projects-tracking.md` の「工程と値の対応」の表 |
| 値の一覧 | `plugins/ndf/scripts/lib/projects-common.sh` が持つ工程の値の並び |
| 閉じる語 | Pull Request の本文で issue を閉じるための語（`Closes` / `Fixes` / `Resolves`） |
| 起点ブランチ | 開発の本流のブランチ。このリポジトリでは `develop` |
| 既定ブランチ | GitHub がリポジトリの既定として持つブランチ。このリポジトリでは `main` |

## 何を解決するか

| 課題 | 現在の状態 |
| --- | --- |
| #231 | 盤面へ工程「設計レビュー」を記録できない。値の一覧にこの値が無い |
| #259 | 起点ブランチ宛の Pull Request では閉じる語が働かず、完了した issue が残る |

**2 件は「工程を通しても記録が残らない」という点で同じ性質を持つ。** 片方は進行が盤面に、
もう片方は完了が課題の一覧に残らない。

## 現状（実測）

### 値の一覧に「設計レビュー」が無い

```console
$ bash plugins/ndf/scripts/projects-sync.sh 196 stage "設計レビュー"
ERROR: stage が取らない値です: 設計レビュー

$ grep -c '設計レビュー' plugins/ndf/scripts/lib/projects-common.sh
0
```

工程表と対応表には、この工程がある。

```console
$ grep -n '^| 設計レビュー' plugins/ndf/skills/development-workflow/SKILL.md
70:| 設計レビュー | — | `pr` → `cross-review` → `merged` | ... |
$ grep -n '^| 設計レビュー' plugins/ndf/skills/development-workflow/references/projects-tracking.md
（対応表に行がある）
```

値の一覧は 14 個で、工程表と対応表は 15 行である。**値の一覧を持つ箇所が 2 つあり、片方だけが
更新された。** 手順としては「工程を足したときは、同じ表から盤面側も更新する」と書かれているが、
機械では突き合わせていない。

### 起点ブランチ宛の Pull Request では閉じる語が働かない

| Pull Request | 宛先 | 本文 | マージ後の issue |
| --- | --- | --- | --- |
| #255 | `develop` | `Closes #248` | #248 は OPEN のまま |
| #257 | `develop` | `Closes #254` | #254 は OPEN のまま |

GitHub の自動クローズは既定ブランチへマージしたときにだけ働く。このリポジトリの既定ブランチは
`main` で、開発の変更は `develop` へマージする。`main` を進めるのは配布の工程で、
fast-forward の push で行うため Pull Request を経由しない。**この形では自動クローズは
一度も働かない。**

## 受け入れ条件

### 盤面の値（#231）

1. `bash plugins/ndf/scripts/projects-sync.sh <番号> stage "設計レビュー"` が値の検査で弾かれない
2. 値の一覧の並びが、工程表の行の並びと一致する
3. 工程表の行名・対応表の 2 つの列・値の一覧の 4 つが一致していることを、機械で確かめる
4. 4 つのどれか 1 つを変えると、その検査が落ちる

### 閉じ忘れた issue（#259）

5. `merged` の手順に、マージした Pull Request の本文の閉じる語が指す issue を閉じる項目がある
6. 閉じる対象は、Pull Request の本文にある閉じる語が指す番号のうち、まだ OPEN のものに限る
7. 閉じる前に対象の一覧を示し、同意を得る
8. 閉じた番号が作業完了報告に載る
9. 本文から番号を読み取る処理に、次の書き方を通すテストがある
   - `Closes #12`
   - `Fixes #12, #13`
   - `Resolves #12` と `closes #13`（大文字と小文字を区別しない）
   - 閉じる語を伴わない `#12`（対象にしない）
10. `uv run --with pytest pytest plugins/ndf -q` が通る

### 全体

11. `bash scripts/build-runtime-plugins.sh` を実行し、生成物の差分をコミットしている

## 設計

### 値の一覧（#231）

値の一覧へ `設計レビュー` を足す。位置は工程表の並びに合わせ、`設計` の次に置く。

```text
作業場所の用意 → 要求と受け入れ条件 → 設計 → 設計レビュー → 計画 → 実装 → 構造改善
  → レビュー → 完了判定 → Pull Request → 確定仕様化 → 後片付け → 配布
  → リリース後テスト → 振り返り
```

同じ食い違いが次に起きないよう、4 つの並びを突き合わせる検査を足す。

| 突き合わせる先 | 何を読むか |
| --- | --- |
| 工程表 | `development-workflow/SKILL.md` の表の 1 列目 |
| 対応表の工程の列 | `projects-tracking.md` の表の 1 列目 |
| 対応表の値の列 | 同じ表の 3 列目 |
| 値の一覧 | `projects-common.sh` の並び |

4 つが同じ並びであることを確かめる。並びまで見るのは、盤面の単一選択の順序が工程の順序を
表すためである。

**読み取れないこと自体も失敗として扱う。** 表を見つけられないときに素通りさせると、
表の書き方を変えるだけでこの検査を無効にできる。

### 閉じ忘れた issue（#259）

`merged` の手順へ、閉じる語が指す issue を閉じる項目を足す。位置は作業ツリーとブランチの
後片付けの後、復元の前とする。

```text
マージ確認 → 作業ツリー退避 → 起点ブランチの更新 → 作業ツリー削除 → ブランチ削除
  → マージ済みブランチの整理 → 閉じ忘れた issue を閉じる → 復元
```

番号の読み取りは、`merged` が持つスクリプト 1 本に集める。手順の側は入出力の整形だけを行う
（`worktree` と `projects-sync` が採っている構造と同じ）。

| 段階 | 何をするか |
| --- | --- |
| 読み取り | Pull Request の本文から、閉じる語が指す番号を取り出す |
| 絞り込み | 取り出した番号のうち、まだ OPEN のものだけを残す |
| 同意 | 対象の番号とタイトルを一覧で示し、同意を得る |
| 実行 | `gh issue close` を番号ごとに実行する |
| 報告 | 閉じた番号を作業完了報告へ載せる |

読み取りの規則は GitHub の閉じる語に合わせる。

| 書き方 | 扱い |
| --- | --- |
| `Closes #12` / `Fixes #12` / `Resolves #12` | 対象 |
| `close` / `closed` / `fix` / `fixed` / `resolve` / `resolved` | 対象 |
| 大文字と小文字の違い | 区別しない |
| `Fixes #12, #13` | 2 件とも対象 |
| 閉じる語を伴わない `#12` | 対象にしない |

**同意を求めるのは、閉じる操作が取り消しにくいためである。** `merged` は削除の対象を一覧で
示して同意を得てから消す形をすでに持っており、そこへ揃える。

**既定ブランチへマージした場合は、GitHub が先に閉じている。** 対象を OPEN のものに限るため、
この手順は二重に実行しても結果が変わらない。

## 決定の記録

### 値の一覧の並びまで突き合わせる

集合の一致だけを見る形も採れるが、盤面の単一選択は並びを持ち、その並びが工程の順序を表す。
順序が入れ替わっても集合は一致するため、集合だけでは食い違いを拾えない。

### 検査は工程表を基準にする

`development-workflow` の工程表が判定の基準を持つ唯一の場所である。対応表も値の一覧も、
その表から作られる。基準を工程表に置けば、工程を足したときに直す順序が 1 つに決まる。

### 閉じる操作を `merged` に置く

継続的統合で閉じる形は、書き込みの権限と、誤って閉じたときの戻しが要る。閉じ忘れた issue は、
マージ済みのブランチや作業ツリーと同じく「残ったままだと次の担当が拾ってしまう残骸」であり、
後片付けの工程が扱う対象と性質が同じである。

### 番号の読み取りをスクリプトへ集める

手順の文章として書くと、実行するたびに読み取りの規則が揺れる。閉じる語の一覧と大文字小文字の
扱いはテストで固定できるため、スクリプトへ集めてテストを書く。

**残リスク（未確認）**: 本文に閉じる語を書かずにマージした Pull Request は、この手順でも
拾えない。issue の番号をブランチ名に持つ運用と突き合わせる形は、この変更には含めない。
