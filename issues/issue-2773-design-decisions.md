# #2773 の設計: 決定の記録

設計文書の本体は [issue-2773-design.md](issue-2773-design.md) にある。

## 決定の記録

### 決定 1: main へのマージの時点で承認済みを GitHub に保証させるため、証跡のチェックを commit status で付け、出元を GitHub Actions のアプリに限って必須にする

`issue_comment` で起動した実行のチェックは既定ブランチの最新のコミットに付き、PR の先端に付かない（STD2）。commit status は SHA を指定して付けられ（STD3）、ruleset の必須チェックは出元のアプリを選べる（STD1）。API で同じ名前を付けても出元が違えばマージを通さないため、受け入れ条件 8 を ruleset の設定で満たせる。

commit status は SHA に付くため、同じ先端を持つ main 宛ての PR のすべてに効く。そのまま判定すると、一方の PR の証跡で付いた `success` が、証跡の無いもう一方の PR のマージも通す。そのため、同じ先端の SHA を持つ main 宛ての開いた PR がほかにあれば落とす（I10）。リリースの PR は 1 つの版に 1 本で、同じ先端の PR を並べる正当な場面は無い。

Environments の必須レビュアー（PRD1）と workflow の中で承認を待つ action（LIB1）は、承認がマージの後のジョブに付くため採らない。ruleset の必須の workflow は提供範囲を確かめられなかったため採らない。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1 / STD3 / PRD1 / PRD2 / LIB1 / LIB2

根拠: Value 1 / Value 13（MVV 版 7）

### 決定 2: PR の中の書き換えで判定を変えさせないため、証跡のチェックは `pull_request_target` と `issue_comment` で起動し、PR のコードを取り出さない

どちらの出来事も既定ブランチの workflow の定義で動く（STD2）。判定のスクリプトも既定ブランチから取り出すため、PR が workflow や `release-steps.py` を書き換えても判定は変わらない。PR の先端は API で SHA を読むだけにする。

PR のコードを取り出して動かす `pull_request` は、PR の中の定義で動くため採らない。

根拠: Value 1（MVV 版 7）

### 決定 3: 承認資料と取り違えないため、証跡を隠しの印と `承認したコミット:` の 1 行で書き、人と時刻は GitHub の記録で読む

承認資料も利用者のアカウントで PR に置くため、印を分けないと承認資料に書いた SHA が証跡に読まれる。承認した時刻は作成の時刻（`created_at`）で読み、作成の後に編集された証跡は数えない。書き込み権限を持つ人は、他人の PR のコメントを編集できる（STD5）。編集された証跡を数えると、書き込み権限だけの人が admin の証跡の SHA を新しい先端へ書き換えて通せる。編集者を編集の履歴で確かめる作り方は、履歴を読む API が増え判定が複雑になるため採らない。承認をやり直すときは新しい証跡を置く。本文の `担い手:` は MVV 判定で通したかを後から読むための記述で、判定に使わない。

根拠: Value 14（MVV 版 7）

### 決定 4: fork や書き込み権限だけの人の証跡を数えないため、承認権限を共同作業者の権限の API の `role_name` で読み、読めなければ落とす

`permission` は maintain を write へ丸める（STD4）ため、`role_name` が `admin` か `maintain` のときだけ数える。読めない人の証跡は数えず、ほかに通る証跡が無ければ落ちる。読めないまま通すと、権限を確かめずにマージが通る。

根拠: Value 1（MVV 版 7）

### 決定 5: 承認を取る場所を宣言と GitHub の設定から機械で決めるため、場合の判定は ruleset を読み、読めないときは「CD があり、レビューなしでマージできる」へ倒す

CD の有無は、`delivery` の本番チャネルへのマージで届く行（`kind: auto`）の有無で決める。レビュー必須かは本番チャネルの ruleset（`GET /repos/{owner}/{repo}/rules/branches/{branch}`）の `pull_request` 規則の承認数で決める。ruleset に規則が無ければ、呼び手のトークンで従来のブランチ保護の API を読み、読めれば承認数で決める。どちらも読めなければ場合 1 として扱う。場合 1 の経路は管理者の迂回を使わない（I7・決定 8）。そのため、レビューが本当は必須でも GitHub がマージを拒んで止まるだけで、承認なしのマージは起きない。場合 2 へ倒すと、レビューが必須でないリポジトリで承認なしのマージが通る。

従来のブランチ保護を workflow から読む作り方は、`GITHUB_TOKEN` で読めない（要求の前提 2）ため採らない。

根拠: Value 4 / Value 1（MVV 版 7）

### 決定 6: 承認の後にリリースの手順がコミットを足さないため、本番のプランを「版上げ → リリースの PR → 承認資料 → 承認ゲート → 証跡 → マージ」の順に並べ替える

今の本番のプランは承認の記録（`approve`）を先頭に置き、その後に bump・changelog・notes・トークン消費の記録を積む。並べ替えて、承認を求める時点の先端に版上げまでのコミットがそろうようにする。承認資料を組むステップ（facts・explain・others と助言の MVV 判定）は、開発版のプランから本番のプランの release の後へ移す。他のプラグインの上げ幅は、開発版のプランの候補をそのまま bump-others が使い、承認資料の差分として人が見る。差し戻しなら bump-others からやり直す。

根拠: Value 1 / Value 3（MVV 版 7）

### 決定 7: 承認の外の変更を本番へ入れないため、場合 1 では先端と証跡、場合 2 では先端と承認のレビューのコミットの完全な一致だけを通し、許可リストの許容を使わない

今の照合は、`docs/`・`issues/` の下だけを変えたコミットを承認の外でも許し、先端が動けば比べ直して入れ直す（`UNGATED`・`HEAD_MOVED_RETRIES`）。この許容を残すと、証跡のチェック（完全な一致）と手元の照合が別の答えを返す。選んで集める取り込み方も、リリースのブランチの先端を同じ比較に掛ける。組み直しや追加のコミットで落ち、承認を取り直すまでマージされない（要求の S6）。場合 2 は証跡を書かない（I8）。そのため必須レビューの承認者として有効な人（共同作業者の権限の API の `permission` が `admin` か `write`）の最新の承認（`APPROVED`）のレビューが付いたコミット（レビューの `commit_id`）を先端と比べ、違えば 10 で止める。read の権限の人の承認は必須レビューに算入されないため、照合に使うと、旧先端への有権限者の承認と新先端への read の権限の人の承認の組み合わせで未承認の変更が通る。古いレビューの承認を push で取り消す ruleset の設定（`dismiss_stale_reviews_on_push`）は、ほかのリポジトリで有効とは限らないため頼らない。場合 3 は今の照合のまま残す。

根拠: Value 1 / Value 7（MVV 版 7）

### 決定 8: 承認したコミットだけを入れ、CD を確実に起動するため、場合 1・2 のマージは利用者のアカウントで `--admin` なしに行う

`GITHUB_TOKEN` で main へマージすると、その push は CD の workflow を起動しない（STD2）。利用者のアカウントで、証跡の SHA を `--match-head-commit` に固定してマージする。`merge-when-green` へ `--no-admin` を足し、場合 1・2 の本番の経路（`release --channel prod` と `promote`）が渡す（I7）。場合 3 と、develop など本番チャネル以外へのマージは今のまま `--admin` を使う。CD の無いリポジトリや開発の途中のマージでレビューの迂回に頼る運用を、この変更で壊さないためである。場合 1・2 では迂回を使わない。そのため決定 5 で場合 1 へ倒したときにレビューが本当は必須なら、GitHub がマージを拒んで止まる。

根拠: Value 4（MVV 版 7）

### 決定 9: 開発版のデプロイを GitHub の上で起こすため、PR は手元で作り、CI の通過を待つマージを `workflow_dispatch` の workflow が行う

`GITHUB_TOKEN` で作った PR では CI が起動しない（STD2）。必須チェックが付かないため、develop へマージできない。秘密を置かない（受け入れ条件 21）ため、PR の作成は利用者のアカウントで手元から行い、マージだけを workflow が行う。workflow の名前は `.ndf/supervise.json` の `release.dev_workflow` で受け、無いリポジトリは今のまま手元でマージする。

GitHub の自動マージ（PRD3）は、受け入れ条件 1 が workflow を求め、リポジトリの設定（`allow_auto_merge`）の変更も要るため採らない。

- 作り方: 自前で作る
- 比べた候補: STD2 / PRD3 / LIB3

根拠: Value 4 / Value 5（MVV 版 7）

### 決定 10: 承認の正本を 1 つにするため、場合 1・2 の `release --channel prod` は承認したコミットの引数を受けない

承認したコミットは、場合 1 では PR の証跡から、場合 2 では最新の承認のレビューから読む（決定 7）。引数でも受けると、引数と証跡の 2 つの正本ができる。場合 1・2 で `--approved-sha` か `--approval` を渡すと 3 で止まり、`next` に証跡を書くコマンドを出す。場合 3 は今の引数を受ける。手元の承認資料は承認資料のコメントの元として書き続けるが、承認の正本ではない。

根拠: Value 8 / Value 11（MVV 版 7）

### 決定 11: CI と同じテストを繰り返さないため、場合 1・2 では検査のプランから全体テストのステップを外し、マージが CI の結果を待つ

CI テストの宣言（`test.ci.only`）があるリポジトリでは今も外している（`without_ci_wait`）。場合 1・2 でも同じ外し方を使う。場合 3 は今のまま残す（受け入れ条件 19）。受け入れ条件 16 は、場合を分けずに全体テストを流さないことを求めている。場合 3 では受け入れ条件 19 と両立しない。そのため受け入れ条件 16 を場合 1・2 に限る解釈を、[設計文書の本体](issue-2773-design.md) の「人へ残す判断」に挙げる。承認資料の「全体テスト」の欄は CI の結果を載せる。

根拠: Value 2 / Value 3（MVV 版 7）

### 決定 12: 移行の途中で承認なしのマージを起こさないため、ruleset の変更を「workflow を main へ入れる → 必須チェックへ足す → 確認用の PR で 1 回通ることを確かめる → 承認数を 0 にする」の順にする

証跡のチェックの workflow は既定ブランチ（main）に入るまで起動しない（STD2）。移行は次の順で進める。

1. この変更を含む版は、そのリリースの時点で導入済みの NDF（この変更を含まない版）の手順で出す。その手順はリリースの場合を判定せず、今の形でマージする
2. 人が `protect main` の必須チェックへ `ndf/release-approval` を出元 15368 に限って足す（承認数は 1 のまま）
3. main 宛てのマージしない確認用の PR を作る。まず証跡の無い状態で、必須チェックが満たされないことを見る。次に `approve --pr` で証跡を置き、`ndf/release-approval` が `success` で付いて必須チェックが満たされることを、マージの判定の表示で確かめる。確かめたら PR を閉じる
4. 人が承認数を 0 にする。これ以降の本番のリリースは場合 1 になる

確認用の PR はリリースの PR ではなく、I8 の対象に当たらない。手順 3 で必須チェックが満たされなければ、手順 2 の必須チェックを外して止め、人へ戻す。戻すときは承認数を 1 に戻す。

手順 1 から手順 4 までの間（移行の途中）は本番のリリースを出さない。出す必要が生じた場合、場合の判定は場合 2 を返し、NDF は I7・I8 のとおり迂回なしでレビューの承認を待つ。リリースの PR の作成者は自分の PR を承認できない。そのためコードオーナーの別の人が承認するまで止まり、人へ戻す（別の承認者がいるかは、[設計文書の本体](issue-2773-design.md) の「未確認のまま残ること」）。

根拠: Value 1 / C2（MVV 版 7）

### 決定 13: 必須チェックの入れ忘れの検査を保つため、API で付ける commit status の名前を宣言に足す

`check-required-checks.py` はジョブの名前と ruleset の必須チェックを照らす。証跡のチェックは、ジョブの名前でなく commit status の名前で必須になる。そのため `required-checks-allow.json` に commit status の宣言（名前・付ける workflow・理由）を足し、照合はそれをジョブの名前と同じ扱いで数える。証跡のチェックの workflow のジョブそのものは必須にしない宣言へ入れる。

根拠: Value 13（MVV 版 7）

### 決定 14: CD のある他のリポジトリでも証跡を PR に残すため、`merged-steps.py promote` の承認の後の打ち直しも、場合 1 ではマージの前に同じ書き手で証跡を書く

リリースの PR（develop → main）で届く経路は、承認資料と `--approved-from` で先端を照らしてマージする。場合 1 では、マージの前に `approve --pr` と同じ書き手で証跡を置く。証跡のチェックの workflow が無いリポジトリでも、GitHub に承認の記録が残る。場合 1・2 のマージは `--no-admin` で行う（I7・決定 8）。判定は同じ純粋な関数を使い、手元で照らす。

根拠: Value 4 / Value 11（MVV 版 7）
