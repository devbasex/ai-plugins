## 決定の記録

### 決定 1: 分割と抽出の行き先を塞がないため、起点のツリーに無いパスを置き場所によらず範囲の中として扱う

新しいファイルは「リファクタリング計画の起点（`plan.base_sha`）のツリーに無いパス」で決める。コミットの状態（`A`）では決めない。状態で決めると、作ったコミットの後で同じ項目・修正・最終ゲート修正が直したとき（`M`）に範囲の外へ戻り、PR 1732 の修正と同じ形で取り消される（前提 1）。起点は `plan.base_sha` を使う（未決 4）。計画の時点の HEAD で、テストの追加・実装・修正・最終ゲート修正のコミットはすべてその後に積まれ、取り消しの積み直し（`undo.py`）でも書き換わらない。

置き場所を範囲の中のディレクトリに限る案は採らない。利用者の判断（2026-10-07）が明示して退けており、共通モデルを別の場所へ抽出できなくなる。生成物を新しいファイルとして作る危険は、プロンプトの「同期をしない」と公開直前の同期で拾う（前提 3。未確認のまま残ることに記載）。

根拠: Value 1 / Value 6（MVV 版 2）

### 決定 2: 呼び手の書き換えを許しつつ無関係な変更を落とすため、範囲の外の既存のファイルはハンクごとに「変えた名前」で判定し、通したファイルをレビューへ引き継ぐ

未決 1 の判定の線である。**設計の承認で人が決める項目なので、承認資料にこの決定を載せる。**

範囲の外の既存のファイルは、`-U0` のハンクごとに 2 条件で判定する（設計の「呼び手の書き換えの条件」）。H1: 変えた行に「変えた名前」が 1 つ以上ある。H2: 追加の行にだけ現れる識別子は、ありふれた語か、変えた名前か、同じハンクの削除の行にあるものに限る。変えた名前は、単位のコミットが範囲の中と新しいファイルで変えた行の識別子と、作った・消した・移したパスの語幹とディレクトリ名から、ありふれた語（追跡しているコードのファイルの 20% 以上かつ 3 ファイル以上に現れる語）を除いたものである。修正・最終ゲート修正の単位では、項目（最終ゲート修正なら採った全項目）の実装・修正のコミットも変えた名前を集める先に加える。実装が移した名前の呼び手を修正担当が追従させる経路を取り消さないためである。ありふれた語の表は 1 実行に 1 度、起点のツリーを走査して作る。範囲の外の既存のファイルを消す・名前を変えて元を消すのは常に取り消す（I3）。

この線で通る形と落ちる形は次のとおりである。

| 戦略 | 呼び手のハンク | H1 で当たる変えた名前 | 結果 |
| --- | --- | --- | --- |
| 移動・分割 | `from pkg.a import f` → `from pkg.b import f` | `f`（`a.py` の削除行）・`b`（新しいファイルの語幹） | 通る |
| 改名 | `foo(x)` → `bar(x)` | `foo` / `bar` | 通る |
| シグネチャの変更 | `g(1, 2)` → `g(1)` | `g`（`def g(a, b)` の削除行） | 通る |
| インライン化 | `y = h()` → `y = x + 1` | `h` | 通る（`x` が変えた名前か削除の行にあるとき） |
| 無関係な変更 | `timeout = 30` → `timeout = 60` | 無し | 落ちる |
| 名前を含む行での機能の追加 | `f(x)` → `f(x, retry=True)` | `f` | 落ちる（`retry` が H2 に当たらない） |

**機械が通したものも「正しい」とは言わない。** 通したファイルは `review_scope_judgements` に載せ、最終ゲートのレビューへ引き継ぐ（テストの差分の `review_test_judgements` と同じ扱い。#933 決定 25）。D1 が立つため全体テストも 1 度走る。リテラルだけを変えたハンクのような通しすぎは、この 2 つが拾う。

言語ごとの構文解析（import 文・呼び出しの解決）は採らない。`refactor.py` は標準ライブラリだけで言語を問わない（#933 決定 20）。元のモジュールから再公開させて呼び手を変えさせない案も採らない。改名とシグネチャの変更は再公開では済まず、再公開の名前が残ること自体が整理の対象になる。呼び手の書き換えをすべて通して最終ゲートのレビューにだけ任せる案は、受け入れ条件 1b（無関係な箇所の変更を取り消す）を満たさない。

閾値（20%・3 ファイル）は初期値である。リリース後テストで取り消しの理由と `review_scope_judgements` の件数を見て較正する。

根拠: Value 1 / Value 4 / Value 5（MVV 版 2）

### 決定 3: #622 を悪化させないため、範囲の外の既存のファイルの縛りはファイル単位からハンク単位へ細かくするだけにとどめる

#622 は、範囲がファイル単位なので課題と関係の無い関数まで整理される問題である。この変更は範囲の中のファイルの扱いを変えない。範囲の外の既存のファイルは、今は「1 行も変えない」で、変更後は「変えた名前に結びつくハンクだけ変えてよい」になる。範囲の外で整理の対象が広がる経路は、変えた名前を含まないハンクが H1 で落ちることで塞がる。新しいファイルの中身は範囲の判定に掛からないが、新しいファイルは項目が範囲の中から移した・抽出したものの置き場所で、機能変更の禁止と期待値の判定は今のまま掛かる（未決 2）。

根拠: Value 6（MVV 版 2）

### 決定 4: 移した行を 2 回数えて正当な項目を落とさないため、差分予算による取り消しを外し、実差分は `-M` で数えて記録だけにする

差分予算が守っていたのは「範囲の逸脱」で、その役目は範囲の判定（決定 1・2）が直接持つ。実測の予算超過 4 件はいずれも適用が成り立っており、取り消すべきものは無かった。`verify_diff_budget`・`diff_budget_factor`・`DIFF_BUDGET_FACTOR`・`EXTRACTION_DIFF_BUDGET_FACTOR`・`EXTRACTION_TECHNIQUES` と、語彙の表の「手法ごとの差分予算の倍率」の節を消す（未決 5）。

実差分（`items[].diff_lines`）は記録として残し、`commit_diff_lines` に `-M` を付けて名前の変更を 1 回に数え、項目の全コミットの和にする。見積（`estimated_diff_lines`）は提案の時間の見積りの材料として残る。

`-M` を足して予算を残す案は採らない。名前の変更は 1 回に数えられるが、ファイルの一部を移す分割は `-M` でも削除と追加の 2 回に数えられ、予算超過は残る。結果 JSON に「逸脱の目安」の欄を足す案も採らない。読む側が無く、範囲の判定と重なる。

根拠: Value 1 / Value 3（MVV 版 2）

### 決定 5: テストの値を補助のファイルへ移しただけの項目を取り消さないため、期待値は単位が変えたテストのファイルの和集合で判定する

単位（実装は項目の全コミット、修正は修正の範囲の項目ごと）が触ったテストのファイルごとに、前は「そのファイルを最初に触ったコミットの親」の内容、後は「最後に触ったコミット」の内容を取る。前の値の和集合から後の値の和集合を引いて残れば `changed`（取り消し）とする。和集合で値が残っていてファイルごとに食い違うものは、今と同じく `undecidable` として最終ゲートのレビューへ引き継ぐ。

今の `collect_test_changes` は後のコミットの組で前の組を上書きするため、複数コミットの単位では「前」が最初の状態を指さない。決定 6 で複数コミットを許すのに合わせて、最初の前・最後の後を取る形へ直す。

「テストのファイル」は今の `is_test_path` が当たるファイルで、新しく作った補助のファイル（`tests/helpers.py`・`conftest.py` など）を含む。値を製品のコードへ移した変更は、和集合に入らないため今と同じく `changed` になる（前提 8）。

根拠: Value 1 / Value 6（MVV 版 2）

### 決定 6: 改名と中身の変更を分けられるようにするため、実装の項目は同じ `Item-Id` のコミットを何件でも受け入れ、`commits.implement` を並びにする

レビューの観点（`docs/03-review-viewpoints.md:20`）は改名と中身の変更を分けることを求め、取り込みは 2 コミット目で取り消していた。実装の 2 件以上の拒否を外し、項目のコミットはすべて単位として判定する。

状態ファイルの `commits.implement` は文字列から並び（古い順）へ変える（未決 6）。修正の `commits.fix` がすでに並びで、取り消し・積み直し（`item_shas`・`undo._remap_commits`）は並びを扱える。読む側は `items.implement_shas` を通し、古い状態ファイルの文字列を 1 件の並びとして読む。`implement` を最初の 1 件に保ち残りを別の欄へ置く案は、同じ役割の値を 2 つの欄に分けることになり採らない（Value 6）。

締め切りと所要は最後のコミットの時刻で測る（AC6a）。完了期限は完了の時刻で見るのが今の設計の趣旨で、2 件目以降の作業を締め切りから外さないためである。積み直しの再開で同じ `Item-Id` を読み直さない今の扱い（`_remember`）は、取り消しのやり直しのためのもので、変えない。

テストの追加の 1 コミットの規則は変えない（要求の「含まない」）。

根拠: Value 1 / Value 6（MVV 版 2）

### 決定 7: 死んだコードを消す項目を検証できるようにするため、対象の無い `remove_dead_code` を `deletion` として残し、D4 で全体テストを 1 度走らせる

`limited_runs` が組めず項目の手法が `remove_dead_code` のとき、`none` ではなく `([], "deletion")` を返し、計画は見送らない。検証では静的解析の範囲テストが今どおり走る。全体テストは新しい起動を足さず、危険フラグ D4（範囲テストが触った本番のファイルを覆うと示せない）を使う。`deletion` の項目は範囲テストのファイルを持たないため、`_test_files` が `None` を返し、D4 の定義どおりに立つ。全体テストは今の経路で 1 実行に 1 度だけ走る（前提 9。性能の条件）。

新しい危険フラグ D6 を足す案は採らない。D4 の定義（覆うと示せない）にそのまま当たり、D1〜D5 を前提に書かれた規則と文書を広げずに済む。手法でなく兆候（`dead_code`）で決める案も採らない。見送りを外すのは「消す」という手の性質によるためである。

根拠: Value 1 / Value 4（MVV 版 2）

### 決定 8: 足すテストを範囲の外へ置けるようにするため、項目が足すテストは suite が覆えば `--scope` のテストの置き場所の外でも `test_targets` に入れる

`valid_targets` の置き場所の条件（`covered_by_roots`）は、`planned`（リファクタリング計画の `tests`）のパスに限って、「テストの種別の suite のどれかの `paths` が覆う」に置き換える（未決 3）。既存のテストのパスは今の条件のままにする。範囲テストは suite の雛形で組むため、suite が覆わないパスは組んでも走らない。置き場所を問わず通す案は、組めないコマンドを計画に載せることになり採らない。

テストの追加の取り込みは決定 1 の判定を通るため、範囲の外の新しいテストのファイルは範囲の外として取り消されない。

根拠: Value 1 / Value 5（MVV 版 2）

### 決定 9: 正当な提案を語彙で落とさないため、手法 5 つと兆候 3 つを足し、観点を語彙の表へ移して代表の兆候へ写す

手法に `extract_class`（クラスの抽出）・`split_module`（モジュールの分割）・`inline`（インライン化）・`change_signature`（シグネチャの変更）・`extract_test_helper`（テストの共通化）を足す。共通モデルの抽出は `extract_class` と既存の `move_responsibility`、移動は `move_responsibility` が受ける。

観点の識別子は今は `vocabulary.py` の辞書にあり、兆候の `duplication` と同じ識別子を持つ（1 語 2 意味）。観点を `vocabulary.md` の「観点」の節へ移し（呼び名を持つ唯一の場所）、`duplication` の観点を `duplicated_knowledge` へ改める。観点にはそれぞれ代表の兆候を 1 つ持たせ、提案の `smell` に観点の識別子が書かれたら代表の兆候へ写して降格しない（未決 7）。

| 観点 | 代表の兆候 |
| --- | --- |
| `duplicated_knowledge` | `duplication` |
| `mixed_responsibility` | `divergent_change`（足す。変更の理由が 1 つに定まらない） |
| `branching` | `conditional_chain` |
| `naming` | `inconsistent_naming` |
| `dependency_direction` | `circular_dependency` |
| `testability` | `hidden_dependency`（足す。外部への依存や隠れた状態が引数に現れない） |
| `data_shape` | `data_clump`（足す。いつも一緒に渡る値の組） |
| `size` | `long_method` |

写すのは、統合の重複排除（`path` / `symbol` / `smell`）が同じ箇所の提案を 1 つにまとめるためである。観点の識別子を兆候の表へそのまま足す案は、観点と兆候を同じ語で呼ぶことになり採らない（Value 8）。`smell` を空にして手法だけで通す案は、重複排除の鍵が欠ける。旧い観点の識別子 `duplication` は兆候にあるため、そのまま兆候として通る。

識別子が表の間で重ならないこと（I11）と、代表の兆候が兆候の表にあること（I12）は、`vocabulary.py` の読み込みで確かめ、破れていれば `VocabularyUnavailable` で止める（今の「読めなければ止める」と同じ扱い）。

根拠: Value 1 / Value 8（MVV 版 2）

### 決定 10: 分割に伴う作業を「手順の外」と読ませないため、プロンプトは許すことを列挙し、禁じることを機能変更とついでの整理に絞る

`implement.md` / `fix.md` / `final-fix.md` の「範囲の外を 1 つも変更しない」を次の 4 点に置き換える。

| 書くこと | 理由 |
| --- | --- |
| 新しいファイルは置き場所を問わず作ってよい。ただし生成物・配布物は作らない | 決定 1・前提 3 |
| 範囲の外の既存のファイルは、項目が移した・改名した・シグネチャを変えた・インライン化した・分割した名前の読み込みと呼び出しの書き換えだけ変えてよい。消さない | 決定 2 |
| 上の 2 つと、それに伴う読み込みの書き換えは「提案された手順」の中である | 要求の表の最終行 |
| 機能変更とついでの整理は今までどおり禁じる | 残す制約 |

`implement.md` の「1 項目に 2 コミット以上作らない」と `git reset --soft` の手順は、「改名と中身の変更のように分けたほうが読みやすいときは、同じ `Item-Id` で複数のコミットにしてよい」に置き換える（決定 6）。`add-tests.md` の 1 コミットの規則は残す。

根拠: Value 1 / Value 2（MVV 版 2）

### 決定 11: 経路ごとに判定が食い違わないため、範囲の判定を `scope_check.judge_unit` に置き、実装・修正・最終ゲート修正・テストの追加が同じ関数を呼ぶ

今の `verify_commit_basics` はコミット 1 件を見る形で、変えた名前（決定 2）と和集合（決定 5）は複数コミットを見る必要がある。範囲の判定を新しいモジュールへ出し、単位（コミットの組）を受け取る。`verify_commit_basics` は実在とトレーラーの検査だけを持つ。`verify.py` は 472 行で、判定を足すと構造検査の上限（500 行）を超えるため、別のモジュールに置く。

修正の取り込みは、修正の範囲を `Item-Id` ごとの単位に分けて判定し、1 つでも外れれば今と同じく修正の範囲ごと取り消す。最終ゲート修正は `Item-Id` を持たないため、全コミットを 1 つの単位にする。

根拠: Value 6（MVV 版 2）

### 決定 12: 指示書の書き換えを人の承認に掛けるため、`CLAUDE.md` の cross-refactoring の節は設計の承認と別に承認を取ってから書く

`CLAUDE.md` の「1 改善項目 = 1 コミット」は決定 6 と食い違うため直す（AC5）。指示書の運用の節の書き換えは共通原則の C7 に当たり、設計の承認では代えられない。実装の PR で差分を示して承認を取り、承認の後にコミットする。用語集（`docs/glossary/glossary.json`）の「改善項目」の意味の変更は設計の変更に含め、C7 には当たらない（指示書ではない）。

根拠: C7（MVV 版 2）
