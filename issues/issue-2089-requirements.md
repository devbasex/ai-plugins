# #2089: development-workflow: 棚卸しの結果から次のスプリントを決めて自動で始め、スプリントを繰り返す開発ループのモードを持つ

正は課題の本文（#2089）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何をしたいか

`/goal /ndf:development-workflow` を、スプリントの終わり（振り返り・Issue の見直し）で止めずに、見直しの結果から次のスプリントを決めて自動で始められるようにする。1 スプリントで終わる今の進め方に加えて、スプリントを繰り返す「開発ループ」を NDF のモードとして持たせる。

## MVV

- **Mission**（利用者の指定 2026-10-25）: `/goal /ndf:development-workflow` を完全自動でループ開発できるようにする
- **Vision**（利用者の指定）: NDF に、完全に自動で開発を進める Software Factory のモードを持たせる
- **Value**（利用者の依頼で AI が作成。要求の工程で利用者に確かめる）
  1. **承認は MVV のレッドラインだけで止まる。**（利用者の指定 2026-10-25）ループのモードは `pace: auto` を基本とし、承認ゲート 1（設計 Pull Request のマージ）と承認ゲート 2（本番への配布）も MVV の判定で通す。人の承認を求めるのは MVV のレッドラインに当たったときだけで、それ以外では承認を一切求めない。今の `auto` は判定が「従う」以外（「判定できない」「反する疑い」）なら人へ戻すため、その扱いをこのモードでどう変えるかと、`.ndf/pace.json` の `boundary_paths`（触ると人へ戻すパス）との関係は設計で決める
  2. **止まる条件を必ず持つ。** 予算（トークン・時間）・同じ失敗の連続・着手できる Issue が無い・MVV の外の Issue しか残らない、のどれかでループを止め、止まった理由と再開のコマンドを残す。外部の事例でも、止まる条件の無いループは「進んでいると思い込んだまま予算を使い切る」と警告されている
  3. **次のスプリントは棚卸しの結果だけで決める。** 選ぶ根拠は `backlog-refinement` の順位とマイルストーンの順位、MVV で、ループの中で AI が範囲を思いつきで広げない。選んだ理由をスプリントごとに記録する
  4. **1 周ごとに後から追える記録を残す。** 振り返り・棚卸し・次のスプリントの選定・配布した版を、周回ごとに人が読める形で残す
  5. **今の進め方を壊さない。** ゴールを明確に定めた 1 スプリントの開発は、今までどおり動く。ループのモードは引数で切り替える
  6. **今ある仕組みを使う。** 中継（`relay.py` と `ndf-next`）・`sprint-state.py`・`supervise.py new sprint`・棚卸しの `rank` を組み合わせ、新しい仕組みは足りない部分だけにする
  7. **外部の最新動向を取り入れる。** loop engineering（起動の条件・結果の評価・止まる条件・状態の引き継ぎを設計する）と software factory（人はコードを書かず、検証の仕組みと仕様に手を掛ける）の考え方を調べ、出典を付けて設計に反映する

## 外部の動向（起票時の検索。要求・設計の工程で一次情報に当たって調べ直す）

- loop engineering は 2026 年に広まった語で、プロンプトを磨くのではなく「いつ起動するか・結果をどう評価するか・いつ追加の実行を起こすか・状態をどう記録して次へ渡すか」を設計する実践と説明されている。止まる条件とガードレールの無いループが予算を使い切る危険が繰り返し指摘されている（[Loop Engineering with Agents](https://dassum.medium.com/loop-engineering-with-agents-5e9b984e8d8a)・[What is loop engineering](https://mindstudio.ai/blog/what-is-loop-engineering-autonomous-ai-agent-workflows)・[loop engineering developer guide 2026](https://noqta.tn/en/blog/loop-engineering-ai-agents-developer-guide-2026)）

- 出典の多くは事業者のブログや解説記事で、成果の数字は自己申告である。設計の根拠にするときは一次情報（Anthropic・OpenAI の公式ドキュメント、発表の原典）を確かめる

## 目的

- 利用者が 1 回ループを始めれば、NDF がスプリントを「選ぶ → 設計 → 実装 → 検査 → 配布 → 振り返り → 棚卸し → 次を選ぶ」と繰り返し、人が手を止めるのはレッドラインに当たったときと、ループが止まる条件に当たったときだけになる状態にする
- 1 スプリントの今の進め方（ゴールを決めた `/goal /ndf:development-workflow #<課題>`）は、引数を変えなければ今と同じに動く

## 前提

- 前提 1: ループを始めるのは利用者の操作であり、ループの開始をもって承認ゲート 1・2 を MVV 判定に任せる事前の委任とする（プロジェクト MVV の Vision「利用者が進め方ごとに事前に選ぶ」）。委任が有効なのは、`.ndf/pace.json` がループを許し、プロジェクト MVV が承認済みでハッシュが一致するときだけである
- 前提 2: ループの各周回は承認済みのプロジェクト MVV で判定する。周回ごとにスプリント MVV の承認を人へ求めない（マイルストーンに承認済みのスプリント MVV があればそれを使い、未承認のスプリント MVV しか無いマイルストーンの課題は選ばない）
- 前提 3: レッドラインは今の定義（NDF の共通原則 C1〜C8・プロジェクト MVV の P1・スプリント MVV の R・`.ndf/pace.json` の `boundary_paths`・`mvv-gate.py` の機械のチェック）をそのまま使い、ループのために緩めない
- 前提 4: ループは Claude Code のラッパー（`relay.py`）の下で動くことを主な形とする。ラッパーの外では、カットポイントで `ndf-next` を出して止まり、利用者が貼り直せば同じ周回から続く（今の中継と同じ）
- 前提 5: #2086（document-restructuring → document-rebuild）が触るファイル（`plugins/ndf/skills/document-restructuring/`・`markdown-writing/`・文書系の Skill）はこの課題の対象に入れない。`development-workflow` の共通の文書は、節を足すか新しい `references/` の文書を作る形で触る
- 前提 6: この実行では WebSearch・WebFetch が許可されておらず、外部の動向は要求の工程で一次情報を確かめていない。確かめるのは設計の工程である（受け入れ条件 20）

## 用語

| 用語 | 意味 |
| --- | --- |
| 開発ループ | スプリントを 1 つ終えるたびに、棚卸しの結果から次のスプリントを選んで続けて始める進め方。引数で切り替え、止まる条件に当たるまで繰り返す |
| 周回 | 開発ループの 1 回分。次のスプリントの選定から、そのスプリントの棚卸しと止まる条件の判定まで |
| ループの予算 | 開発ループが使ってよい量の上限。周回の数・費用・経過時間で数え、超えたら止まる |
| 止まる条件 | 開発ループを止める、機械で判定できる条件。予算を超えた・同じ失敗が続いた・着手できる課題が無い・MVV の外の課題しか残らない・利用者が止めた |

## 受け入れ条件

起動と切り替え:

- [ ] 1. ループの引数を付けない `development-workflow` の起動（`#<課題>` やマイルストーンを指す今の形）は、ループの記録を作らず、棚卸しの後に次のスプリントを始めない（今の振る舞いのまま）
- [ ] 2. ループの引数を付けた起動は、`.ndf/pace.json` がループを許していない・プロジェクト MVV が未承認か承認と一致しない・ループの予算の設定が読めない、のどれかで周回を始めず、断った理由と 1 スプリントの起動の形を返す（機械で判定する）
- [ ] 3. ループの周回のスプリントは `pace: auto` で組まれ、承認ゲート 1・2 は `mvv-gate.py check` の判定だけで通る。レッドライン（機械のチェック 1〜5 と判定の `boundary`）に当たったときだけ利用者の承認を求め、それ以外の判定で `AskUserQuestion` も本文の承認待ちも出さない

次のスプリントの選定:

- [ ] 4. 次のスプリントの課題の組は、直前の棚卸しの `rank` の結果（マイルストーンの順位・切り出しの境界・容量）と承認済みの MVV だけから機械で決まる。同じ入力（`rank` の結果・MVV・前の周回の記録）からは同じ組が選ばれる
- [ ] 5. 選定は、課題ごとに「選んだ・外した」と理由（順位・容量・MVV の外・人の判断待ち・レッドラインに当たる見込み）を周回の記録へ書く
- [ ] 6. ループの中で AI が新しく起票した課題は、その周回の組へ入らず、次の周回の棚卸しで順位が付いてから選定の対象になる

止まる条件:

- [ ] 7. 周回の数・費用・経過時間のどれかがループの予算を超えたら、次の周回を始めずに止まる。判定は周回の境で行い、周回の途中では止めない（止める点はカットポイントと同じ）
- [ ] 8. 同じ失敗（同じ課題の同じステップの失敗）が宣言の回数続いたら止まる
- [ ] 9. 選定で選べる課題が 0 件なら「着手できる課題が無い」で止まる
- [ ] 10. 候補がすべて MVV の外・人の判断待ちとして外れたら「MVV の外しか残らない」で止まる
- [ ] 11. 利用者は 1 つのコマンドかファイルでループを止められ、止める指示は次の周回の境で効く
- [ ] 12. 止まったときは、止まった条件・判定に使った値・再開のコマンド（`ndf-next` の形）を周回の記録と引継ぎ文書に残し、レッドラインと止まる条件以外では利用者へ問わない
- [ ] 13. 再開のコマンドで始めたループは、止まった周回の次から続き、周回の数と予算の消費を引き継ぐ

記録:

- [ ] 14. 周回ごとに、選定（課題と理由）・承認ゲート 1・2 の判定（MVV 判定の結果と根拠の項目）・配布した版・振り返りの置き場・棚卸しの結果（順位の変化・持ち越し）・費用と秒・止まる条件の判定が、人が読める 1 つの記録に残る
- [ ] 15. ループの記録から、周回の一覧（何周目・選んだ課題・版・費用・止まった理由）を 1 つのコマンドで出せる
- [ ] 16. 前の周回の棚卸しの持ち越し（`metrics.deferred`）は、次の周回の棚卸しへ渡る（手で `--add` しない）

人へ戻した課題:

- [ ] 17. レッドラインか「判定できない・反する疑い」で人へ戻した課題は、承認を待つ間ループを止めず、周回の記録と課題の本文に「人の判断待ち」と理由が残る。人が答えた後の周回でだけ再び選定の対象になる（未決 1 の推奨の形。利用者が別の案を選べば、この条件を書き換えて事実を残す）

退行しないこと・作り方:

- [ ] 18. 今の 1 スプリントの進め方（`normal` / `auto` / `fast`）で、`supervise.py new sprint`・`new close`・`sprint-state.py`・`relay.py` の出力と終了コードが変わらない（既存のテストが通る）
- [ ] 19. ループの状態（周回の数・予算の消費・止まった理由・選定の理由）は、既存の `sprint-state.py`・引継ぎ文書・中継（`relay.py` と `ndf-next`）を広げて持つ。新しい基盤（キュー・常駐の処理）を作らない。新しいスクリプトを足すときは、既存のものでは足りない理由を設計文書に書く
- [ ] 20. 設計文書に、loop engineering と software factory の一次情報（Anthropic・OpenAI の公式ドキュメントかエンジニアリングブログ、発表の原典）の出典 URL と、取り入れる考え方・取り入れない考え方を理由付きで書く。起票時に挙げた解説記事だけを根拠にしない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | ラッパーの 1 日の起動回数の上限（`NDF_RELAY_MAX_STARTS`、既定 20）に当たったら、ループの止まる条件と同じ形で理由と再開のコマンドを残す |
| 運用・保守性 | 止まる条件の判定は LLM を呼ばずにスクリプトが行う（プロジェクト MVV の Value 4）。閾値はリポジトリの設定で受け、スクリプトに埋め込まない（Value 5） |
| セキュリティ | レッドラインと `boundary_paths` はループの中でも今と同じに効く。ループのために緩める設定を作らない（共通原則の C1〜C8・P1） |
| 移行性 | ループの設定が無いリポジトリでは、何も変わらない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる（足すだけ）。`development-workflow` の引数・`.ndf/pace.json` の項目・スクリプトの副命令を足す。既存の引数・項目・副命令の意味は変えない |
| データ | スプリント状態ファイルか引継ぎ文書に周回の項目を足す。既存の項目は変えず、古い形のファイルも読める |
| 既存の振る舞い | 変わらない（受け入れ条件 1・18） |
