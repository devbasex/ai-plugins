## 何を見つけたか

push の直後に打った sync が、送ったばかりの設計文書ではなく古い差分を読んだと見ている（未再現）。

## なぜこの変更の範囲外なのか

スプリント m725（#725・#1289・#842・#824）の受け入れ条件に、cross-review の取り込みの手順は入っていない。原因が特定できておらず、即時修正の 4 条件の 1 つ目を満たさない。根拠: Value 3（MVV 版 2）。

## 直さないと何が起きるか

設計の直しで決定の見出しが変わる PR では、レビューが収束していても駆動が止まる。conductor が手で sync して `--from review` で流し直すことになり、1 回あたり数分と $0.3 程度の LLM の費用が掛かる。

## 経路（ndf 10.17.68 のコードで確認）

- `plugins/ndf/scripts/lib/design_body.py` の `sync_after_push` は push の直後に待たずに sync を 1 回打ち、送ったコミットの SHA を渡さない
- `pr-body-decisions.sh` の `read_pr`（126〜131 行）は head の SHA を `pulls/{pr}` から読み、手元の HEAD と照合しない
- `sync_section`（334〜348 行）は本文を書いた後に PR を読み直し、head が進んでいれば進んだ先の文書と突き合わせて 1 を返す
- `merge_fix.py` の 284〜289 行は、この 1 を受けると再試行せずに止まる

pulls API が push を反映する前に読むと、この経路で mismatch になる（手で数分後に打つと 0 になる観測と合う）。直し方の候補: 送ったコミットの SHA を sync へ渡し、PR の head がその SHA になるまで待ってから読む / head が進んだのを見たら進んだ先の文書でもう 1 度だけ書く。`fix-steps.py` と `result_posts.py` も同じ関数を通るため、一緒に直る。

## 目的

- 設計の PR で、修正が決定の見出しを変えても、cross-review の駆動が本文の同期で止まらずに次のラウンドへ進む状態にする
- 本文の同期が「揃った」と報告したときは、送ったコミットの設計文書と本文の「決めたこと」が実際に揃っている状態にする（古い設計文書と突き合わせて 0 を返さない）

## 前提

- 前提 1: 原因は再現できていない。push と本文の書き込みの直後に、GitHub の `pulls/{pr}` の読みが数秒〜数十秒のあいだ古い head か古い本文を返すことがある、と置く。受け入れ条件はこの 3 つの読み（書く前の head・書いた後の head・書いた後の本文）のどれが古くても満たす形にし、原因がどれかに依らない
- 前提 2: 待つ時間の上限は、駆動の 1 ステップの時間を目に見えて延ばさない値（数十秒の桁）に置く。具体の値と既定・変え方は `design` が決める。上限を超えるほどの遅れは、今と同じく止めて打ち直す扱いでよい
- 前提 3: 止まるたびの費用（数分・$0.3 程度）は起票者の見積で、測っていない。直した効果は「同じ停止が出なくなる」ことで見て、費用の削減額を受け入れ条件にしない
- 前提 4: 当時の記録（`~/.local/state/ndf/sv/sprint-m725/1-design-1289-state/07-review.out`）は 2026-10-12 の時点で手元に無く、読み直していない。経路はコード（ndf 10.17.71 のworktree）で確かめた

## 語の使い方

この要求では、設計の PR の本文の「決めたこと」の節を PR の head の設計文書の決定の見出しへ書き直すこと（`pr-body-decisions.sh sync`）を「本文の同期」、修正の取り込みが push したコミット（`merge-fix` の `fix_commit`、無ければ `commit_sha`）を「送ったコミット」と呼ぶ。どちらもこの課題の中だけの言い回しで、用語集へは足さない。

## 受け入れ条件

- [ ] 1. 送ったコミットで決定の見出しが変わり、`pulls/{pr}` が push の後の最初の何回かの読みで送る前の head を返しても（上限の内）、push の直後の本文の同期は送ったコミットの設計文書の見出しで本文を書き直し、0 を返す
- [ ] 2. 本文を書いた後の読み直しが、上限の内で書く前の本文か送る前の head を返しても、本文の同期は 1 を返さず、揃ったのを確かめてから 0 を返す
- [ ] 3. 送った後に別の push で head が送ったコミットの先へ進んでいたら、本文の同期は進んだ先の設計文書と突き合わせる（古い決定を一致と報告しない、今の振る舞いを保つ）
- [ ] 4. 上限を超えても PR の head が送ったコミット（かその子孫）に届かないとき、本文の同期は 0 を返さず、標準エラーか理由の欄に、待ったコミットの SHA と上限の値を書く
- [ ] 5. 受け入れ条件 1・2 は、`state.py merge-fix`・`state.py record-fix`・`result_posts.py fix` の 3 つの呼び出し元のどれから通しても成り立つ（呼び出し元ごとに待ちを書かない。待ちは共通の層 1 か所に置く）
- [ ] 6. 本文の同期が 0 でないとき、`merge-fix` は今と同じく修正の取り込みを記録せずに止まり、同じ `merge-fix` を打ち直すと本文の同期からやり直す（退行しない）
- [ ] 7. head のブランチが `design/` で始まらない PR、または送ったコミットが無い（push しなかった）ときは、今と同じく本文の同期を打たず、GitHub を読まず、待たない
- [ ] 8. 引数なしの既存の呼び方（`pr-body-decisions.sh sync <PR番号> [--repo ...]`・`check`・`render`）の振る舞いと終了コードの意味は変わらない
- [ ] 9. 遅れが無い（最初の読みが送ったコミットを返す）とき、本文の同期の GitHub への読みの回数と所要時間は今と同じで、待ちを足さない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | push の直後の読みの遅れ（前提 1）で、本文の同期が誤って 1 を返して駆動を止めない（受け入れ条件 1・2）。遅れが上限を超えたときは止め、0 に畳まない（受け入れ条件 4） |
| 性能・拡張性 | 遅れが無いときに待ちを足さない（受け入れ条件 9）。遅れがあるときの待ちは前提 2 の上限の内 |
| 運用・保守性 | 止めたときの理由に、待ったコミットの SHA と上限を書き、手で打ち直すか調べるかを判断できる（受け入れ条件 4） |
