## 目的

- NDF が工程境界で会話を切る条件を「一律 200K と 4 つのカットポイントで必ず切る」から「容量・運用上限・費用・レビューの独立性で理由を付けて判断する」へ変えられるようにし、不要な再起動・引継ぎ・復元に掛かる費用と時間を、品質を落とさずに減らせるかを実測で確かめられる状態にする
- 判断の値を hook・statusline・skill-stats で 1 か所から読み、表示・停止・統計の値の食い違いを無くす

## 前提

- 前提 1: 既定は現行方式のまま変えない。試行方式は利用者が設定で明示的に選んだときだけ働き、選ばない利用者の振る舞い（200K で止める・4 カットポイントで `ndf-next` を出す）は変わらない
- 前提 2: 200K と 400K は比較実験の初期値であり、品質が落ちる境目を測った値ではない。値は設定で変えられ、仕様の文書にその旨を書く
- 前提 3: 試行方式の判定は既定で働く hook（`token_guard.py`）の中に入るため、実験版（`plugins/ndf/scripts/experimental/`）ではなく安定版の経路で入れる。既定値を現行方式に保つことで「呼んだときだけ違う振る舞いになる」性質を設定の側で持たせる
- 前提 4: 実行環境の窓の大きさと自動圧縮の条件は、取れるランタイム（Claude Code の statusline に渡る `context_window` の大きさなど）でだけ使う。取れないときは推測した値で埋めず、適用中の方針の上限（現行方式なら 200K）だけで判定する
- 前提 5: 比較実験はこの課題の実装を配布した後に、利用者の通常の課題を使って行う。同じ課題を 2 方式で再実行するのは費用が倍になるため必須にせず、行えなかったときは「同程度の課題」での比較と、その限界を報告に書く
- 前提 6: 比較の結果から既定を変える（試行方式を既定にする・適用するモデルを広げる）のは、この課題の範囲では行わない。結果の報告で採否を示し、既定を変えるなら別の課題として設計の承認を通す（MVV Value 3「測って決める」、P1 には当たらない）
- 前提 7: 方針を選ぶ設定は `.ndf/` に新しく置く（既存の `.ndf/*.json` の値を書き換える場合は C7 に当たり、承認ゲート 2 で人が見る）。置き場の名前とキーは設計が決める
- 前提 8: 費用の単位は API 料金の換算（入力・出力・キャッシュの読込・書込の単価）と秒で比べ、サブスクの利用上限の消費と同じものとして扱わない。換算の単価と前提は報告に書く

## 対象範囲

含む:
- 方針（現行方式 / 試行方式）と、判断開始の値・運用上限・容量の余白の設定の正本と優先順位
- conductor が次の工程を起動するときの判定（`token_guard.py`）を、方針と理由に沿って継続 / 再起動 / 拒否にする変更。relay の直接の子での繰り返し拒否の扱い
- 4 カットポイントの規約（`context-window.md`）を、試行方式では「再起動を判断できる安全な境界」として書き直すこと。`work-vessels.md`・`relay.md` と関連する Skill 本文の追従
- statusline の警告の値と skill-stats の「割る候補」の判定を、同じ適用済みの設定から読むこと
- 境界ごとの判定（継続 / 再起動と理由・方針・値）の記録と、引継ぎの作成と復元の区間の token・秒の記録、作業の識別子で複数セッションを結んだ集計
- hook の無いランタイム（Codex）に向けた、工程境界の共通の規約としての記述
- 比較実験の手順・判定の方法の事前の記録と、結果の報告

含まない:
- 既定の方針を試行方式へ変えること（前提 6）
- 引継ぎ文書の肥大化の整理（#1785）。比較の条件として引継ぎ文書の量を記録するだけにする
- conductor の持ち越し量の削減（#827）
- 質問に答える前の relay の切り替え（#1286）の契約の変更
- supervisor のスイッチポイント（収束ループの前で `ndf:supervisor-waits` へ替える点）の撤去・変更
- ツール呼び出しの途中で処理を止める仕組み
- モデルごとの最適値を決めること

## 用語

| 用語 | 意味 |
| --- | --- |
| 再起動の方針 | conductor が工程境界で会話を切るかを決める規則の組。現行方式と試行方式の 2 つ |
| 現行方式 | 運用上限 200K を超えたら次の工程を止め、4 つのカットポイントでは文脈の量に関わらず `ndf-next` を出す方針 |
| 試行方式 | カットポイントを「再起動を判断できる境界」として扱い、判断開始の値と運用上限と容量で継続か再起動かを決める方針 |
| 判断開始の値 | 試行方式で、これを超えたら工程境界で継続と再起動を比べ始める文脈の量（初期値 200K） |
| 運用上限 | これを超えたら次の工程への進入を止める文脈の量（現行方式 200K・試行方式の初期値 400K）。ツール呼び出しの途中では止めない |
| 容量の余白 | 実行環境の窓の上限（または自動圧縮が始まる量）から、次の作業・ツール結果・出力と進行の保存のために空けておく量 |
| 再起動の理由 | 工程境界で会話を切ったときの理由。容量・運用上限・費用・独立性・手動のどれか |
| 復元の区間 | 再起動した新しいセッションが、引継ぎ文書を読み始めてから最初の工程を起動するまで |

## 受け入れ条件

方針の選択と既定

- [ ] 1. 方針を指定しない状態で、conductor の文脈が 200,001 token のときに次の工程を起動すると、hook は現行と同じ文面と同じ判定（relay の下では拒否・外では 1 度目を拒否し 2 度目を通す）を返す。200,000 token 以下では通す
- [ ] 2. 設定で試行方式を選ぶと、hook・statusline・skill-stats の 3 つが試行方式の値を使い、設定を消すか現行方式に戻すと 3 つとも 1 の振る舞いへ戻る
- [ ] 3. 試行方式で、文脈が判断開始の値未満のまま 4 つのカットポイントのどれかに着いても、規約（`context-window.md` と関連の Skill 本文）も hook も `ndf-next` を出すことを求めない。ただし再起動の理由が費用・独立性・手動のときは切ってよいと規約に書かれている
- [ ] 4. モデル名（`[1m]` を含む名前や 1M の窓のモデル）だけを理由に試行方式へ切り替わる処理が無い。方針の既定は現行方式で、200K / 400K が「実験の初期値で、品質が落ちる境目の実測ではない」と仕様の文書に書かれている

境界の判定

- [ ] 5. 試行方式（初期値）で、文脈が 200,000 以下なら判定は「継続」、200,001〜400,000 なら「判断」（費用の比較で継続か再起動を決める）、400,001 以上なら次の工程の起動を止める。この 3 つの帯の境界の値（200,000 / 200,001 / 400,000 / 400,001）でテストが通り、仕様の表と実装の定数が同じ値を指す
- [ ] 6. 容量が取れる実行環境で、窓の上限から容量の余白を引いた量が運用上限より小さいとき、判定はその小さいほうの値で止める（小さい窓・早い自動圧縮を数値の帯より優先する）。判定の理由は「容量」になる
- [ ] 7. 容量やコンテキスト量が取れないとき（記録の無いセッション・hook の入力に値が無い）、判定は推測の値を使わず、取れた値と方針の運用上限だけで決め、取れなかった値を判定の理由に書く。コンテキスト量そのものが取れないときは起動を止めない（現行と同じ）

設定の一元化と互換

- [ ] 8. 方針・判断開始の値・運用上限・容量の余白の正本が 1 か所に決まっていて、hook・statusline・skill-stats がそこから読む。statusline の表示の値と hook の止める値が違う場合は、それぞれの意味（表示の警告 / 止める上限）が文書に書かれている
- [ ] 9. `NDF_CONTEXT_LIMIT`・`NDF_CONTEXT_GUARD`・`skill-stats --window-limit` が今の意味のまま効き、設定との優先順位（例: CLI 引数 > 環境変数 > 設定 > 既定）が文書とテストに残っている。`NDF_CONTEXT_GUARD=0` で判定が止まることは方針に関わらず変わらない
- [ ] 10. 継続か再起動かの判定は、スクリプトが記録から計算した値（コンテキスト量・費用の見込み）で決まり、判定のために追加の LLM 呼び出しをしない。費用の見込みは `work-vessels.md` の比較の考え方を使い、再起動の側に引継ぎの作成・復元の再読込・状態確認の呼び出し・キャッシュの書き直しを含める。見込みが出せないときの扱い（運用上限だけで決める）が仕様に書かれている

記録と集計

- [ ] 11. 工程境界で判定するたびに、モデル・ランタイム・方針・使った値・工程・コンテキスト量・判定（継続 / 再起動 / 拒否）・理由（容量 / 運用上限 / 費用 / 独立性 / 手動）・作業の識別子が 1 件の記録として残る
- [ ] 12. 同じ課題の複数のセッションを作業の識別子で結び、課題ごとに conductor の分・NDF が起動した分・引継ぎの作成の分・復元の区間の分の token（入力・出力・キャッシュの読込・書込）と秒、再起動の回数、自動圧縮の回数を出せる。同じ呼び出しを 2 つの分へ数えない（同じ記録を 2 回数えないことをテストで確かめる）
- [ ] 13. skill-stats の「割る候補」は、その記録に残った方針と値で判定する。方針の記録が無い過去の記録は現行方式（200K）として判定し、そう扱ったことを出力に示す。品質の記録（要件の漏れ・工程のやり直し・レビュー後の修正量）のうち取れなかったものは 0 件ではなく「不明」と出す

退行しないこと

- [ ] 14. 試行方式でも次のことが変わらない: 承認ゲートを越えない、動いているプランと supervisor を止めずに報告を待ってから引継ぎ文書を作る、新しいセッションは引継ぎ文書から状態を再確認する、承認待ち・質問待ちは引継ぎ文書に保留として残す、ツール呼び出しの途中で処理を止めない
- [ ] 15. supervisor のスイッチポイント（収束ループの前で寿命 1 時間の supervisor へ替える点）とサブエージェントの中で hook が判定しないこと（`agent_id` を持つ呼び出し）は、方針に関わらず今のまま働く
- [ ] 16. 既存のテスト（`test_token_guard*.py` と statusline・skill-stats のテスト）が、現行方式の既定のままで通る

比較実験

- [ ] 17. 比較を始める前に、対象の課題・比べる量（キャッシュを考慮した費用・完了までの秒・引継ぎと復元の費用・再起動の回数・品質の記録）・品質の判定の方法・費用の換算の前提が、課題のコメントか文書に記録されている
- [ ] 18. 比較の結果が、両方式の費用・秒・品質の値と、比較の限界（課題の難しさの違い・件数・モデルとランタイムの範囲）と、既定の変更の採否とその理由を含めて報告されている。改善が出ないときは「採らない」の結論でよい

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | hook の判定は、追加の LLM 呼び出しもネットワークの呼び出しもせず、今の `token_guard` と同じく記録の末尾を読むだけで終わる |
| 運用・保守性 | 判定ごとの記録（受け入れ条件 11）から、なぜ切ったか・切らなかったかを後から人が読める |
| 移行性 | 既定は現行方式のため、設定を置かない利用者に移行の手順は要らない。方針の記録が無い過去の記録は現行方式として読む |
| システム環境 | Claude Code（hook あり）と Codex（工程境界の規約で同じ判断をする）の両方で、取れない値を推測で埋めない |

## 起票時の本文

以下は 2026-10-31 に起票者が書いた本文で、上の要求の出所である。書き換えていない。

### 現状と問題

現在の既定ブランチで確認したもの:

- `plugins/ndf/skills/development-workflow/references/context-window.md`: 「1工程100Kを目安、遅くとも200Kで切る」。4つのカットポイントでは、使用量に関係なく `ndf-next` を出す。
- `plugins/ndf/scripts/hook_lib/token_guard.py`: conductorが次の工程を起動するとき、最後のassistantの入力usage合計を既定200,000と比較する。relayの直接の子では上限を超えている限り拒否し続ける。
- `plugins/ndf/skills/skill-stats/scripts/skill-stats.py`: `DEFAULT_WINDOW_LIMIT = 200000` を超えると「割る候補」。
- `plugins/ndf/scripts/statusline.sh`: 通常の警告は500K、コンテキスト上限200K以下のモデルでは150K。hook・統計と基準が異なる。
- `references/work-vessels.md`: 新しい文脈と継続の費用を比較する式はあるが、100Kに近い場合はカットポイントの規定が優先する。
- `docs/specifications/ndf-context-window-metrics.md`: 通常の使用量帳簿には利用者が開いたconductor自身を含めない。

200Kは外部評価から推定した運用上の目安で、このワークフローにおける品質低下の境界を実測した値ではない。#827 の持ち越し量の計測・削減見込みは重要だが、再起動の復元費用と品質を含めた比較実験とは区別する。

また、閾値だけ400Kへ変更しても、4つの工程境界で無条件に `ndf-next` を出す規約が残れば、再起動回数は十分に減らない。

### 改善方針

#### 1. 再起動の理由を分ける

| 理由 | 判断と動作 |
| --- | --- |
| 容量不足 | 実行環境で実際に使える窓、自動圧縮の条件、次の作業・ツール結果・出力のための余白を見て、足りなければ状態を保存して再起動する |
| 品質を守る運用上の上限 | 適用した方針の上限を超えたら、次の安全な工程境界で再起動する。モデルの仕様上の最大長を、そのまま安全な運用上限とは扱わない |
| 費用の削減 | 続ける費用と、引継ぎの作成・再起動・復元を含めた費用を工程境界で比較する |
| レビューの独立性 | 独立した視点が必要なレビューは新しい文脈で実行する。親のconductorも再起動する必要があるかは別に判断する |

既存の4つのカットポイントは「再起動を判断できる安全な境界」として残し、試行する方式では「必ず再起動する点」から変更する。ひとつの課題の実装・デバッグは連続性を保つ。

容量不足と運用上限は区別する。運用上限は次の工程への進入を止める基準であり、任意のツール呼び出しを途中で中断する上限とはしない。容量不足には、進行の保存ができる余白を確保する。

#### 2. 現行方式を残して、明示的に選ぶ試行方式を追加する

| 方式・範囲 | 振る舞い |
| --- | --- |
| 現行方式 | 現在の200Kと工程境界の再起動を比較対象として保持する |
| 試行方式: 200K未満 | 工程境界でも原則継続。費用やレビューの独立性などの理由があれば切る |
| 試行方式: 200K〜400K | 工程境界で継続・再起動を判断する。同じ課題の実装・デバッグは継続可能 |
| 試行方式: 400K超 | 次の安全な工程境界で再起動する |
| 小さい窓・早い自動圧縮 | 上記の数値より実行環境の容量制約と余白の確保を優先する |
| 未検証のモデル・実行環境 | 現行方式を既定として維持する |

**200K/400Kは比較実験の初期値であり、精度低下の科学的な境目ではない。** 1M対応のモデル名だけで自動的に緩和しない。試行方式を明示的に選択でき、現行方式へ戻せるようにする。

conductorとsupervisorの役割を区別する。既存のsupervisorのキャッシュ寿命・費用によるスイッチポイントは、この試行のためだけには撤去しない。

#### 3. 設定と判定を一元化する

- 方針、判断開始の値、工程境界で切る上限、容量用の余白の設定について、正本と優先順位を定める。
- hook・statusline・skill-statsが、同じ適用済み設定を参照できるようにする。表示・停止・統計の値が異なる場合は、それぞれの意味を明示する。
- 既存の `NDF_CONTEXT_LIMIT`、`NDF_CONTEXT_GUARD`、`--window-limit` の互換性・上書きの優先順位を決め、文書とテストに残す。
- `skill-stats` の「割る候補」は、その実行で使った方針と上限に基づいて判定する。過去の記録に設定がなければ、現行方式として扱ったことを表示する。
- 継続・再起動の判断は、可能な部分をスクリプトで決定論的に行う。追加のLLM呼び出しを毎回発生させない。
- hookがないランタイムにも、工程境界の共通規約として適用する。取得できない値を推測した精密な値として扱わない。

費用の比較は `work-vessels.md` の既存の考え方を再利用する。ただし、独立した仕事を委譲する式を、セッション全体の再起動へ無検討に流用しない。再起動後に必要な仕様・差分の再読込、状態確認の呼び出し、引継ぎの作成、キャッシュの状態を含める。推定が不確かなときの扱いも定める。

#### 4. 再起動と復元を含む全体で比較する

現在の使用量帳簿の範囲を無条件に変更するのではなく、この比較に必要なconductorと再起動後の復元分を取得し、NDF起動分との二重計上を防ぐ。

記録するもの:

- モデル、ランタイム、適用した方針・閾値、工程、現在のコンテキスト量。
- 境界ごとの継続／再起動とその理由（容量・運用上限・費用・独立性・手動など）。
- 同じ作業をセッション間で結び付ける識別子。
- 引継ぎ作成・復元に使った入力／出力／キャッシュ読込／書込と所要時間。復元区間の定義も明記する。
- 完了した課題あたりの費用・所要時間・再起動回数、自動圧縮の発生。
- 要件漏れ、工程のやり直し、レビュー後の修正量など品質を判断する記録。数を取得できないものを0件と扱わない。

ランタイムやサブスクの利用上限とAPI料金を同じものとして扱わず、比較の単位と換算の前提を明記する。

### 比較実験

1. 現行方式と試行方式を、同じモデル・ランタイム・同程度の課題で比較する。可能なら同じ課題を独立した作業場所で再実行し、同じ検査を適用する。
2. 単純な累積入力tokenだけでなく、キャッシュを考慮した費用、完了までの時間、引継ぎ・復元費用、品質を比較する。
3. 比較前に対象と品質の判定方法を決め、記録を残す。課題の難しさの違いなど、比較上の限界も示す。
4. 改善が確認できたモデル・環境にだけ適用範囲を広げる。効果がなければ現行方式を維持する。全モデルに共通する最適値を主張しない。

### 受け入れ条件の案（起票時）

上の「受け入れ条件」の 1〜18 へ、観測できる形に書き分けた。対応は括弧の番号。

- 現行方式と試行方式を明示的に選べ、試行を無効にすると現行の再起動動作へ戻る。（1・2）
- 試行方式では、200K未満でも工程境界に到達しただけで必ず再起動する規約・処理が残らない。（3）
- 200K〜400Kの継続判断、400K超で次の工程への進入を止めること、容量制約を優先することが仕様と実装で一致する。（5・6）
- 200K/400Kは実験の初期値と明記され、未検証のモデル・環境へ自動適用されない。（4）
- hook・statusline・skill-statsの設定が一元化され、既存の環境変数・CLI引数の互換性と優先順位が説明される。（8・9）
- 再起動理由と適用した方針が記録され、複数セッションにまたがる同じ課題のconductor・NDF起動分・引継ぎ・復元を二重計上せず集計できる。（11・12・13）
- 閾値の境界、設定の上書き、小さい窓、値が取れない場合、relay下の繰り返し拒否、稼働中の作業を残した切り替え、承認待ちの扱いを検証する。（5・6・7・9・14、検証手段）
- 承認ゲートを越えない、稼働中のプランやsupervisorを不用意に止めない、引継ぎから状態を再確認する既存の契約が保たれる。（14・15）
- 現行方式との比較結果を、費用・時間・品質と比較の限界を含めて報告し、既定変更の採否を決める。改善が出ない場合は採用しない結論でもよい。（17・18）
