# #3058: 並列の計画: 1 スプリントのレーンの終わりを決め、まとめの後に自分のラッパーを止める

正は課題の本文（#3058）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 目的

並列の計画の 1 スプリントのレーンについて、次の 3 つを決めてスクリプトで固定する。3 つは同じ「リリースの依頼からレーンの終わりまで」の流れの部品で、1 つの設計で扱う（#3060 と #3070 の受け入れ内容をこの課題の設計に含める）。

1. **レーンの終わりと、止める主体**（#3058）。今は決まりが無く、止まるかどうかがレーンの conductor の判断に任されている。止まらないと、`after` でそのレーンを待つレーンが起動しない
2. **リリースを待たずにまとめへ進む**（#3060）。今はリリースの答え（`released`）が届くまでレーンが何もせずに待つ
3. **承認したコミットのまま出す**（#3070）。今はまとめたリリースの承認の答えの時点で `develop` が進んでいると、同じリリースを出し直しの提示（提示 2）でもう一度問う。計画 p5 では 6 回のうち 3 回で起きた

## 方針（利用者の指示、2026-11-12）

- **レーンを終了させるのは耐久ワークフロー（`parallel.py run`）の責務である。** レーンの終わりを観測したら、耐久ワークフローがそのレーンのラッパーを止める
- **耐久ワークフローで止められなかった場合は、オーガナイザーが終了させる。** 耐久ワークフローは止められなかったことを `wait` でオーガナイザーへ返し、オーガナイザーが `relay.py stop <レーン>` を打つ
- **リリースの依頼を送ったレーンは、リリースの完了を待たずにまとめへ進む。** リリースの完了を待つのは、出した版が要る作業（リリース後テスト）だけにする（#3060）
- **まとめたリリースの出し直しが毎回起きている状態を直す**（#3070）

## 用語

| 用語 | 意味 |
| --- | --- |
| 1 スプリントのレーン | 並列の計画のレーンのうち、最初の入力が課題の番号のもの（`/goal /ndf:development-workflow #<課題>`）。開発ループのレーン・一時レーンと区別する |
| まとめ | リリースの後に流す作業のまとまり（`supervise.py new close` のプラン）。確定仕様化・課題を閉じる・リリース後テスト・振り返り・棚卸しを持つ |
| 版の要らないまとめ | まとめのうち、出した版が無くても流せる作業（確定仕様化・振り返り・棚卸し） |
| 版の要るまとめ | まとめのうち、出した版の上でしか流せない作業（リリース後テストと、その結果で課題を閉じる作業） |
| レーンの終わり | 1 スプリントのレーンが版の要らないまとめを流し切った時点。終わりの記録として耐久ワークフローが読める置き場に残る |
| 終わりの記録 | レーンの終わりを示す記録。置き場と書き手は設計で決める |
| 加わった範囲 | 承認したコミット（提示 1 の `sha`）から、承認の答えの時点の `develop` の先頭までの差分 |
| 出し直しの提示 | 加わった範囲を添えて同じリリース承認ゲートをもう一度出すこと（提示 2） |

## 対象範囲

含む:
- 1 スプリントのレーンの終わりの条件（最初の入力の `/goal` の「終わり」）と、終わりの記録
- 耐久ワークフローが終わったレーンのラッパーを止めることと、止められなかったときにオーガナイザーへ返す経路
- `supervise.py new sprint` が目録（`sprint.json`）にまとめのステージを組むこと
- リリースの依頼の後のレーンの手順（`references/parallel.md` の「レーンの側」）と、まとめのプランの並び
- リリース後テストと課題を閉じる作業を、`released` の後に出した版の上で流す経路
- まとめたリリースの範囲の決め方（承認資料のコミットと答えの時点の `develop` の扱い）、出し直しの提示を出す条件、`release/v<版>` の切り方
- 手順書（`references/parallel.md`）の該当の節

含まない:
- 開発ループのレーンの終わり（`[ndf-loop] stopped` で決まっている）と、リリース待ちの扱い（すでに答えを待たずに次の 1 回へ進む）
- 一時レーンの終わり（`helper-done` と `relay.py stop` で決まっている）
- 別のリポジトリのレーンの本番（まとめたリリースに入らない）の範囲の決め方
- 上限の検査が終わったレーンも数える件（#3021）

## 調べた事実

- 1 スプリントのレーンの最初の入力（`lib/parallel_plan.py` の `Lane.start_command`、116 行目）は `/goal /ndf:development-workflow #<課題>` で、「-- 終わり:」が無い。ループのレーンは `[ndf-loop] stopped <名>`、一時レーンは `helper-done` と `relay.py stop <名前>` を終わりに持つ
- 耐久ワークフローがレーンを止まったと数えるのは、ラッパーの状態が `stopped` のときだけ（`lib/parallel_run.py` の `_Run.stopped`、299 行目）。`after` の起動の判定（`lib/parallel_plan.py` の `ready_lanes`、498 行目）は「依存先がすべて止まった」で決まる
- 計画 p5 の lspeed・lcost・lstruct は、リレーハブの記録で `stopped`（reason: stop）になっていた。レーンの conductor が自分で `relay.py stop` を打ったとみられ、手順書にもプランにもその決まりは無い
- `references/parallel.md` の「レーンの側」は、1 スプリントのレーンが `parallel.py await` で答えを待ち、`released` ならまとめのステージを流すと定める。まとめの後に止まることは書いていない。手順書の規定 R5 は「止まったかはレーンの側の記録で決め、ラッパーの状態だけで決めない」と定める
- 今のスプリントの目録（`.ndf/sprint-lrel-1/sprint.json`）のステージは「設計」から「本番」までの 9 つで、まとめのステージが無い。レーンの conductor が手順書の文章を読んで自分で `new close` を組んでいる（2026-11-12 の lgate・lcost2）
- まとめのプランのステップ（例: `.ndf/sprint-lcost-1/close/4-close.json`）は `spec → pr → ready → config-save → release-verify → config-check → … → retro → refine → …` で、リリース後テスト（`release-verify`）が確定仕様化と振り返りの間にある
- 2026-11-12、計画 p5 の lcost2 は、スプリント PR #3036 がリリース 5（v10.27.55）の範囲に入った後、リリースの完了を待って止まっていた
- まとめたリリースの本番のプランは、すでに「確定した提示のプランの承認したコミット（`{queue_approved:present}`）」から `release/v<版>` を切る（`lib/parallel_release.py` の `plan_parallel_release`、391 行目の説明）
- 出し直しの判定は、承認の答えの時点の `develop` の先頭と提示 1 のコミットを比べ、進んでいれば提示 2 を作る（`lib/parallel_run.py` の `_Run.confirm`）。加わった範囲が文書だけなら出し直しを省く（#3020）
- 計画 p5 のリリース 6 回のうち 3 回（1・4・6）で出し直しが起きた（`.ndf/parallel/p5/releases/<n>/2/`）。加わった範囲は、リリース 1 が PR #2982、リリース 4 が PR #3015、リリース 6 が PR #3062 と開発版 10.27.56-dev.2 の版上げ。リリース 6 は提示 1 から答えまで 4 時間半（01:45 JST → 06:23 JST）で、#3062 がコードを含むため #3020 の省略に当たらなかった
- 依頼への答え（`_Run.settle`）は、範囲の Pull Request で全部が出る依頼にだけ答える。範囲に入らない依頼は残り、次のリリースになる

## 前提

- 前提 1: 1 スプリントのレーンの終わりは、版の要らないまとめを流し切った時点とする。リリース後テストと課題を閉じる作業はレーンの終わりに含めない（#3060 の規則でレーンがリリースを待たないため、版の要る作業をレーンの中に残すとレーンが終われない）
- 前提 2: `after` でレーンを待つレーンは、待たれるレーンの終わりで起動する。待たれるレーンのリリースの完了は待たない
- 前提 3: 課題を閉じるのは、今の規則のとおり、受け入れ条件を出した版で確かめた後（リリース後テストの後）である。レーンの終わりで課題を閉じない
- 前提 4: 承認したコミットを出すことで、`main` へ入るのは承認資料のコミットまでである。加わった範囲は `develop` に残り、次のリリースの範囲に入る
- 前提 5: 止める 1 行は `relay.py stop <レーン>` とする。止めた後もラッパーが動いているかは、レーンの状態の一覧（`relay.py ls --json`）で確かめる

## 受け入れ条件

### A. レーンの終わりと止める主体（#3058）

- [ ] A1: 1 スプリントのレーンの終わり（版の要らないまとめを流し切ったこと）が、終わりの記録として耐久ワークフローの読める置き場に残る。レーンの最初の入力（`Lane.start_command` の出力）は「-- 終わり:」を持ち、この時点を指す
- [ ] A2: 耐久ワークフローは、終わりの記録を観測したレーンのラッパーを `relay.py stop <レーン>` で止める。止めたこと（レーン名・時刻・結果）は計画の台帳に 1 行残る
- [ ] A3: 止める 1 行が失敗したとき、または止めた後のレーンの状態の一覧でラッパーが動いて見えるとき、`wait` はオーガナイザーへ「止められなかった」ことと止める 1 行（`relay.py stop <レーン>`）を返す。`references/parallel.md` に、オーガナイザーがその 1 行を打って終了させる手順が書かれている
- [ ] A4: 終わりの記録があって止まったレーンは終わったと数えられ、`after` でそのレーンを待つレーンが起動する
- [ ] A5: 終わりの記録が無いまま止まったレーン（答えや承認を待つ間の停止・途中の停止）は終わったと数えられず、今のとおり再開の印で起こされる。`after` で待つレーンは起動しない
- [ ] A6: レーンの conductor が自分のラッパーを止めなくても、A2・A3 で止まる。conductor が自分で止めた場合も、終わりの記録があれば A4 と同じに数えられる
- [ ] A7: `supervise.py new sprint` が組む目録（`sprint.json`）の「本番」の後に、まとめのステージ（`new close` のプラン）がある。レーンはそのステージを目録の `command` / `resume` で流し、自分で `new close` を組まない
- [ ] A8: 開発ループのレーンと一時レーンの終わり方・止め方は変わらない（今のテストが通る）

### B. リリースを待たずにまとめへ進む（#3060）

- [ ] B1: 1 スプリントのレーンは、リリースの依頼を送った直後に、答え（`released`）を待たずに版の要らないまとめ（確定仕様化・振り返り・棚卸し）を流す。依頼の後に `parallel.py await` で答えを待って止まる手順は、手順書にもプランにも残らない
- [ ] B2: リリース後テストは、リリースの答えが `released` になった後に、出した版の上で流れる。流す主体は設計で決め（未決 1）、レーンがリリースを待って止まらない
- [ ] B3: 課題を閉じる作業は、リリース後テストで受け入れ条件を確かめた後に流れる（前提 3）。版の要らないまとめでは課題を閉じない
- [ ] B4: リリースが `rejected` で答えられたとき、差し戻しの直しが、先に流した版の要らないまとめと食い違わない。レーンがすでに終わっていても、差し戻しが失われずに直しを流す主体へ届く（扱いは設計で決める。未決 2）
- [ ] B5: 手順書（`references/parallel.md` の「レーンの側」）とまとめのプランのステップの並びの両方が、B1〜B4 の規則で書かれている

### C. 承認したコミットのまま出す（#3070）

- [ ] C1: リリース承認ゲートで承認したリリースは、承認したコミット（提示 1 の `sha`）までの範囲のまま本番へ入る。承認の答えの時点で `develop` が進んでいても、同じリリースをもう一度問わない
- [ ] C2: 加わった範囲の Pull Request は、次のリリースの範囲に入る。加わった範囲のレーンの依頼は、今のリリースで答えられずに残り、次のリリースで答えられる
- [ ] C3: 承認したコミットを出した後も、`main` は `develop` の祖先のままで、`scripts/check-pr-base.sh` の判定（head が先頭が `origin/develop` の祖先の `release/v<版>`）を通る。出した版の版数と、`develop` の開発版の版数（接尾辞つき）が食い違わない（版上げのコミットの扱いを含む）
- [ ] C4: 出し直しの提示を使う場面が残るなら、その条件が `references/parallel.md` に書かれ、承認の後に `develop` が進んだことだけでは起きない。残さないなら、出し直しの提示と #3020 の省略の経路（`carried`）の扱いを設計で決める（未決 3）
- [ ] C5: 計画 p5 のリリース 6 と同じ形（提示 1 の後にコードを含む PR と開発版の版上げが `develop` へ入り、その後に承認する）を再現したテストで、提示 2 が作られずに提示 1 のコミットで `released` になる

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | 耐久ワークフローを作り直しても、止めたことの記録（A2）を読み直し、同じレーンへ止める 1 行を打ち直さない。止められなかった返し（A3）は、オーガナイザーが止めるまで `wait` の結果から消えない |
