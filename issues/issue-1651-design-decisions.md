# #1651 #1941 #1507 の設計: 決定の記録

設計文書は `issues/issue-1651-design.md` にある。

## 決定の記録

### 決定 1: conductor の書き方を変えずに補正を残すため、雛形の行の和に無い行を補正として取り出す

`design-results` は、書き直しの前のプランの状態から組んだ指示と、書き直しの後の状態から組んだ指示の、空でない行の和を雛形の行とみなし、今の `prompt` のうちそれに無い行を順のまま補正として末尾へ残す。conductor は今のまま `prompt` へ行を足せばよく、覚える約束が増えない。後の状態の行も和に入れるため、2 回流しても設計文書や触る範囲の行が補正と見なされて重ならない（I2）。

補正を別のキーへ置かせる形は採らない。conductor が `prompt` を直接直すと黙って消える今の形が残る。補正を印で囲ませる形も、印を忘れたときに同じく黙って消える。

根拠: Value 4 / Value 2（MVV 版 2）

### 決定 2: 書き直しを同じ入力で同じ結果にするため、設計文書のパスをプランの `設計文書` と `Row.doc` に持つ

設計文書のパスは `prompt` の文だけでなく、プランの `設計文書` のキーにも書く。決定 1 の「書き直しの前の状態から組んだ指示」を再現するには、前回入れたパスをプランから読めなければならない。パスの出所は、設計の結果の行を読んだ文書（`Row.doc`）とし、課題の行と取り込んだ課題の行の文書を合わせる（1651-2）。`design-results.json` にも `doc` が載り、スプリント PR の材料からも同じパスを辿れる。

パスを `prompt` の中だけに持つ形は採らない。前回のパスを読み戻せず、2 回目の書き直しで古い行が補正と見なされる。

根拠: Value 7 / Value 4（MVV 版 2）

### 決定 3: 用語集の無いプロジェクトへ空振りの指示を出さないため、用語集の行は設計の工程の入口と同じ判定で入れる

`glossary.py gate --mode standard` が 0 のときだけ用語集の行を入れる。設計の工程の入口（`design` の手順 0）が使う判定と同じなので、「設計では用語集を求めたのに実装では求めない」食い違いが起きない。判定は `decl.glossary_ready` が 1 か所で持ち、雛形と `design-results` が同じ値を使う。

常に入れる形は採らない。用語集の無いプロジェクトで worker が打てないコマンドを指示される（Value 5）。

根拠: Value 5 / Value 6（MVV 版 2）

### 決定 4: 整形をプロジェクトごとの宣言で受けるため、`.ndf/supervise.json` に `format`（名前とコマンドの並び）を置く

整形のコマンドは `.ndf/supervise.json` の `format` に `{"name", "command"}` の並びで書く。`sync_checks` と同じ形にすると、宣言の書き手が新しい形を覚えずに済み、形の検査も同じ部品で書ける。読むのは `lib/formatting.py` の `format_commands` だけで、雛形（`decl`）と送信（`push_fix`）が同じ関数を通る（1507-5）。

`sync_checks` の lint を `--fix` 付きに変える形は採らない。同期とチェックはビルドを含む重い並びで、送信の前に毎回すべてを打つことになり、コミットも build が通ったときだけという別の約束を持つ。`.ndf/project.json` の suite に `kind: format` を足す形も採らない。`project.json` はテストの戦略（範囲・JUnit・CI のジョブ）を持つ宣言で、解析で作り直される。`ruff` を既定に埋め込む形は Value 5 に反する。

根拠: Value 5 / Value 6（MVV 版 2）

### 決定 5: 静的解析の宣言を重ねないため、範囲の静的解析は `project.json` の `kind: lint` の suite を `test-run.py scope --only-kind lint` で当てる

範囲テストは既に `kind: lint` の suite を変更したファイルへ当てている（m1693 で落ちたのはこれである）。同じ suite を、テストの suite を打たずに先に当てるステップ（`lint-limited`）を置く。新しい宣言は要らず、ai-plugins では lint と script-structure がそのまま当たる。範囲に入るファイルが無ければ通る。

`sync_checks` に script-structure を足す形は採らない。全体に当たり、変更起因かを分けられない。新しい宣言のキーを足す形も、同じコマンドを 2 か所に書くことになる。

根拠: Value 6 / Value 3（MVV 版 2）

### 決定 6: 修正の後にも整形と静的解析を通すため、`impl → format → sync → lint-limited → test-limited` と並べ、修正の行き先を先頭にする

`format` を `sync` の前に置き、`sync` の中の lint が整形だけの違反で落ちないようにする。`lint-limited` は `sync` が生成物を揃えた後に当てる。`fix`・`fix-format`・`fix-lint` の行き先は `pre_test_steps` の先頭（`format`）とし、修正の worker が作った整形の違反も push の前に直る。並びは `pre_test_steps(a)` が 1 か所で組み、宣言の無いステップは置かない（I7）。

`pr` の直前に整形を置く形は採らない。範囲テストと設計との突き合わせが整形の前のコードを見ることになり、整形で変わったコードはテストを通らずに push される。

根拠: Value 4 / Value 1（MVV 版 2）

### 決定 7: 送信の経路を 1 つに保つため、送信の前の整形は `result_posts.push_fix` の中で当てる

`push_fix` は cross-review の `merge-fix` と `/ndf:fix` の単独の送信が共に通る送信の部品である。ここで `formatting.apply_format` を呼べば、`merge-fix` を変えずに 1507-1 が成り立ち、送る側どうしで整形の有無が分かれない。整形が落ちたときは `PushResult(ok=False)` の `detail` に名前と出力の末尾を入れ、`merge-fix` は今の `die` で止まる（1507-4）。ホストが自分で送った修正（`record-fix`）は `push_fix` を通らないため整形しない。cross-refactoring の送信は `push_fix` を通らず、この主題では変えない。

`merge_fix._record_new_fix` で整形する形は採らない。`/ndf:fix` の単独の送信に同じ穴が残る。

根拠: Value 6（MVV 版 2）

### 決定 8: `fix_commit` の判定を保つため、整形は新しいコミットとして上に足し、整形で変わったファイルだけを入れる

`apply_format` は整形の前に変更の無かった追跡ファイルのうち、整形で変わったものだけを `git add` してコミットする。`fix_commit` は書き換えないので、送り先の祖先の判定がそのまま通る（I5）。整形の前から変わっていたファイルは worker の作業の途中かもしれないので、コミットに入れずに結果へ出す（I6）。

amend で修正のコミットへ混ぜる形は採らない。`fix_commit` の SHA が変わり、送り先に載った判定が落ちる。`git add -A` は worker の残したファイルを巻き込む。

根拠: Value 1 / Value 6（MVV 版 2）

### 決定 9: 共通の待ちの部品を使って待ちの合計を抑えるため、打ち直しは `waits.retry_call` で 15 秒の間隔・1 コマンド 30 秒・1 回の実行で合計 120 秒とする

`gh` と `git` の 0 以外の終了を、`waits.retry_call` で 15 秒おきに打ち直す（1 コマンドで最大 3 回打つ）。#1941 では 1 度の打ち直しで 5 件とも読めたため、1 コマンド 30 秒で足りる。待ちの合計を 1 回の実行で 120 秒に抑え、課題が多いときもステージの `timeout` 600 秒の内に収まる。

`gh_call.gh` の中で一律に打ち直す形は採らない。投稿や状態の照会など、打ち直しの扱いが別に決まっている呼び出し元の振る舞いまで変わる。

根拠: Value 6 / Value 3（MVV 版 2）

### 決定 10: 復旧していない GitHub を待ち続けないため、打ち直しても失敗が残った最初の課題で止める

失敗が残った課題で読み取りを止め、`summary` にその課題・コマンド・出力の末尾と、まだ読んでいない課題を出す。プランと `design-results.json` は書かない（I4）。障害の間に残りの課題でも同じ待ちを重ねると、待ちの合計の上限に先に当たるだけで得る情報が無い。

残りの課題も読み続けて失敗をすべて集める形は採らない。打ち直すときは全課題を最初から読むので、途中の結果を残しても使われない。

根拠: Value 1 / Value 4（MVV 版 2）

### 決定 11: 消えた文書を一時的な失敗と取り違えないため、`git show` は `git ls-tree` で起点にあるパスだけに打つ

設計 PR が変えたファイルには、後で起点から消えた・名前を変えたものも含まれる。そのパスへの `git show` は何度打っても 0 以外で終わり、打ち直しの対象にすると止まらなくてよい書き直しが止まる。取り込み（`git fetch`）が通った後の `git ls-tree -r --name-only origin/<base> -- issues/` に無いパスは読み飛ばし、あるパスの `git show` の失敗だけを一時的な失敗として扱う。

根拠: Value 1（MVV 版 2）

### 決定 12: ほかの 2 主題と同じ関数を書き換えないため、`plan_to_merge` で触るのは `pre_test_steps` の呼び出しと 2 つの `next` だけにする

この主題のステップは新しい関数 `pre_test_steps(a)` が組み、`plan_to_merge` では `sync` を組む行をその呼び出しへ置き換え、`head[-1]["next"]` と `fix` の `next` をその先頭へ向ける。`上限` の値（#1909）、`test-limited` から後のステップと `judge_step`（#1917 #2003）、`flow.py`（#1909 #1676）には触らない。#2003 の起点の取り込みは、`head` の後に置いて `next` を `pre_test_steps` の先頭へ向ければ、この主題と同じ行を書き換えずに済む。

根拠: Value 6 / Value 7（MVV 版 2）
