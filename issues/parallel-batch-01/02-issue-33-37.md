# 担当 B — レビューの収束判定に未解決の指摘を入れる（#33 / #37）

- issue: https://github.com/devbasex/ai-plugins/issues/33 、 https://github.com/devbasex/ai-plugins/issues/37
- ブランチ: `fix/issue-33-37-unresolved-threads`
- モード: `standard`

2 件の issue は別々に起票されているが、**同じ解に収束する**。どちらも「Pull Request 上に
残っている未解決の指摘を機械的に数え、判定へ入れる」ことで塞がる。1 つの Pull Request で
両方を閉じる。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| 指摘 | Pull Request 上のレビューコメントの塊（review thread）。Resolve できる単位 |
| 未解決の指摘 | Resolve されていない指摘 |
| 引き継いだ指摘 | 前のラウンドで投稿され、まだ Resolve されていない指摘 |
| 投稿数 | そのラウンドで外部の AI が新しく投稿した件数（`result.json` の `comments_count`） |
| 最終スイープ | ループの終了後に残った未解決の指摘をすべて片づける手順（Step 7.5） |

**投稿数と未解決の指摘の数は一致しない。** 両者を取り違えないことが、この課題の中心にある。

## 何を解決するか

レビューを収束させるループは、そのラウンドで外部の AI が返した判定だけを見て「両方が
承認した」と決めている。Pull Request 上に前のラウンドの未解決の指摘が残っていても、判定には
入らない。

中断したレビューを再開し、再開したラウンドで両者が承認すると、**前のラウンドで受けた
修正必須の指摘を一度も修正の工程へ通さないまま収束する**。

### 観測された経路

別のリポジトリの Pull Request で次が起きた（#33 の記録による）。

| 段階 | 起きたこと |
| --- | --- |
| 1 | あるラウンドで一方が修正必須の判定を返し、指摘 3 件を投稿した状態で中断 |
| 2 | 後日、そのラウンドの続きから再開 |
| 3 | 再開したラウンドは承認 0 件と軽微 2 件。判定は「収束」 |
| 4 | Pull Request 上の未解決の指摘は 5 件（前のラウンドの 3 件 + そのラウンドの 2 件） |
| 5 | 最終スイープが 5 件すべてを拾って修正・Resolve した |

事故には至っていない。最終スイープが唯一の受け皿になっている。

### #37 のうち解消済みの項目

#37 が挙げた 3 点のうち、返信の呼び出し方は既に直っている。Skill 名も `fix` へ改名済みで、
issue 本文の `resolve-pr-comments` は現存しない。

```console
$ grep -rn "in_reply_to" plugins/ndf/skills/
plugins/ndf/skills/fix/SKILL.md:266:# 特定のコメントに返信（in_reply_to にコメント ID を指定）
plugins/ndf/skills/fix/SKILL.md:268:  -f body="対応しました。" -F in_reply_to={comment_id}
```

`-F` で渡す形になっており、issue が報告した状態とは異なる。**この項目は対応不要**で、
issue を閉じるときにその旨を残す。

## やること

### 1. 未解決の指摘を数える手段を用意する

Pull Request 上の未解決の指摘を GraphQL で数え、件数と識別子を返す処理を
`state.py` へ加える。ラウンドの記録へ保存し、後の判定から参照できるようにする。

### 2. 再開したときに引き継いだ指摘を検出する

レビューを再開したとき、その時点で未解決の指摘があれば記録する。記録があるうちは、
**そのラウンドの判定が承認でも収束させない**。修正の工程を必ず 1 度は通す。

### 3. 修正の記録が無いまま次のラウンドへ進めない

前のラウンドが修正必須の判定だったのに修正の記録が無い場合、または前のラウンドで対象と
した指摘が未解決のまま残っている場合、次のラウンドの開始を失敗させる。

手で修正して次へ進めた場合に、返信と Resolve が飛ばされたまま進むのを防ぐ。

### 4. 最終スイープの結果を必須の検証にする

最終スイープの後、未解決の指摘が 0 件であることを確認してから完了報告へ進む。0 件に
できない場合は、残った件数と理由を完了報告に含める。

### 5. 投稿数と未解決の指摘の数を取り違えない注意を書く

修正の担当を起動するテンプレートは、そのラウンドの投稿数を埋め込んでいる。この数だけ
対応すればよいと読めるため、**未解決の指摘は必ず GraphQL で数え直す**ことをテンプレートと
最終スイープの両方へ書く。

### 6. 判定の流れを文書へ残す

どの段階で未解決の指摘が判定へ入るか、最終スイープが何を受け持つかを
`docs/01-state-and-review.md` へ書く。

## 設計上の判断が要る点

**すべてのラウンドで未解決の指摘が 0 件になるまで収束させない、という形にはしない。**
承認されたラウンドで軽微な指摘が新しく投稿された場合も収束せず、レビューのラウンドが
際限なく増える。現在はその分を最終スイープが受け持っている。

判定へ入れる対象を次の 2 つに分けて設計し、採否と理由を実装計画へ残す。

| 対象 | 判定への入れ方 |
| --- | --- |
| そのラウンドで新しく投稿された指摘 | 現行どおり、外部の AI が返した判定と重要度で見る |
| 引き継いだ指摘 | 修正の工程を 1 度通すまで収束させない |

## 完了条件

- [ ] 引き継いだ指摘があるとき、そのラウンドの判定が両者とも承認でも収束しない
- [ ] 引き継いだ指摘が無いときの収束の振る舞いが、現行と変わらない
- [ ] 前のラウンドが修正必須の判定だったのに修正の記録が無い状態で次のラウンドを開始すると失敗する
- [ ] 最終スイープの後、未解決の指摘が 0 件であることを確認する経路が通っている
- [ ] 0 件にできないとき、件数と理由が完了報告に含まれる
- [ ] 修正の担当を起動するテンプレートと最終スイープの両方に、未解決の指摘を数え直す指示がある
- [ ] 判定の流れが `docs/01-state-and-review.md` に書かれている
- [ ] 上記の振る舞いに対応する自動テストがあり、`uv run --with pytest pytest plugins/ndf/skills/cross-review/tests -q` が通る
- [ ] 既存の 148 件のテストが引き続き通る
- [ ] #37 の返信の呼び出し方が既に直っていることを、issue を閉じる際に記録する
