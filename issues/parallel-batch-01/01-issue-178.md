# 担当 A — 版を上げるときに古くなる記載を検査の対象へ広げる（#178）

- issue: https://github.com/devbasex/ai-plugins/issues/178
- ブランチ: `feature/issue-178-staleness-checks`
- モード: `standard`

## 用語

| 語 | この文書での意味 |
| --- | --- |
| 検査 | `scripts/validate-runtime-plugins.sh` が行う機械的な突き合わせ。値が食い違えば 0 以外の終了コードで終わる |
| 配布 Skill | ランタイムごとの一覧ファイル（`plugins/ndf/manifests/*-skills.txt`）に載っている Skill |
| 実体 | `plugins/ndf/skills/` に置かれた Skill のディレクトリ。配布先はここから選ばれる |

## 何を解決するか

配布する Skill の数は 3 つのランタイムごとに違い、その数が 2 つの説明文書に書かれている。
数を機械的に突き合わせる検査は、プラグインの定義ファイルにしか届いていない。説明文書の
側は人が読んで直す必要があり、版を上げるたびに古い数が残る。

v9.3.0 を出したとき、次の 3 箇所が古いまま残った。いずれもその作業の中で直したが、
古くなる仕組みは残っている。

| 箇所 | 何が残っていたか |
| --- | --- |
| `README.md` の公開 Skill 数と元 Skill 数 | 前の版の数（28 / 27 / 26、32 個）のまま |
| `plugins/ndf/README.md` の配布先の表 | 27 / 25 / 26。1 つ前の版の実測値とも食い違っていた |
| `plugins/ndf/README.md` の更新案内の節 | 版数だけが置き換わり、本文は前の版の説明のまま |

配布先の表は、**1 つ前の版から食い違ったまま利用者へ届いていた**。レビューで拾えなければ
同じことが起きる。

## 現状（実測）

現時点の数はすべて一致している。検査が無いだけである。

```console
$ for f in plugins/ndf/manifests/*-skills.txt; do
    printf '%s: %s\n' "$f" "$(grep -v '^\s*#' "$f" | grep -c '[^[:space:]]')"
  done
plugins/ndf/manifests/claude-skills.txt: 31
plugins/ndf/manifests/codex-skills.txt: 29
plugins/ndf/manifests/kiro-skills.txt: 30

$ find plugins/ndf/skills -maxdepth 2 -name SKILL.md | wc -l
31
$ ls -d plugins/ndf/optional-skills/*/ | wc -l
4
```

既存の検査は、プラグインの定義ファイルと marketplace の説明文だけを見ている。

```python
# scripts/validate-runtime-plugins.sh 内の Python ブロック
def manifest_skill_count(family: str, runtime: str):
    manifest = plugin_dir_of(family) / f"manifests/{runtime}-skills.txt"
    ...

def published_skill_count(family: str):
    skills_dir = plugin_dir_of(family) / "skills"
    ...
```

この 2 つの関数がすでに正しい値を返す。**検査の対象を説明文書へ広げるだけで済む。**

## やること

### 1. 説明文書の数を検査の対象へ入れる

次の 4 箇所を突き合わせる。

| 記号 | 記載箇所 | 突き合わせる相手 | 現在値 |
| --- | --- | --- | --- |
| A | `README.md` の「公開Skills: Claude Code向け core N 個、Kiro向け core N 個、Codex向け core N 個」 | 各 `manifests/*-skills.txt` の行数 | 31 / 30 / 29 |
| B | `README.md` の「元Skills（N 個）」 | `skills/` の実体数 + `optional-skills/` の数 | 35 |
| C | `README.md` のカテゴリ内訳の合計 | 同上 | 35 |
| D | `plugins/ndf/README.md` の配布先の表の 3 行 | 各 `manifests/*-skills.txt` の行数 | 31 / 29 / 30 |

**A と D はランタイムの並び順が違う。** `README.md` は Claude Code / Kiro / Codex の順、
`plugins/ndf/README.md` は Claude Code / Codex / Kiro の順で書かれている。位置ではなく
ランタイム名で対応づける。

`plugins/ndf/README.md` のレイアウト図にも `skills/` の実体数（31 個）と
`optional-skills/` の数（4 個）が書かれている。同じ仕組みで拾えるなら含めてよい。実装が
大きくなるようなら範囲外として `out-of-scope` で起票する。

### 2. 数を読み取れないこと自体を失敗として扱う

既存の検査は、説明文から数を読み取れないときも失敗として扱う。同じ方針を引き継ぐ。

```python
# 抽出できないこと自体をエラーにする。素通りさせると、Skill 数の記述を消すか書式を変える
# だけでこの検査を無効化できてしまう。
```

記載を消せば検査を通せる状態を作らない。

### 3. 更新案内の節が古くなる経路を塞ぐ

`plugins/ndf/README.md` の「v&lt;版&gt; へ更新するとき」は数ではなく本文であり、内容の
正しさは機械では判定できない。次の 2 つを行う。

- 見出しの版数が `plugins/ndf/.claude-plugin/plugin.json` の版と一致することを検査する。
  版を上げたときに必ずこの節へ触ることになる
- 版を上げる手順に「この節の本文を読み直し、その版の変更内容へ書き直す」を項目として
  加える。置き場所は `docs/plugin-development-guide.md` のバージョン管理の節とする

見出しの版数だけを置き換えて本文を残しても検査は通る。本文の正しさは人が読んで判断する
部分として残り、手順の項目がその機会を作る。**この 2 つで役割を分ける前提を、実装計画へ
理由として残す。**

### 4. 検査そのもののテストを置く

`scripts/` に既存のテストは無い。`plugins/ndf/skills/cross-review/tests/` と
`plugins/ndf/skills/worktree/tests/` に pytest の実績があり、同じ書き方で置ける。

置き場所は `scripts/tests/` とする。テストは、説明文書と突き合わせ先を書き換えた
一時的なディレクトリを作り、検査を実行して終了コードを見る形にする。実物の
`README.md` を書き換えるテストにしない。

### 検証手順

崩したときに失敗することを、実際に崩して確かめる。作業ツリーの中で行い、確認後に戻す。

```bash
# 1. 現在の内容で通ることを確認する
bash scripts/validate-runtime-plugins.sh; echo "exit=$?"     # exit=0 を期待

# 2. 説明文書の数を 1 つ崩す
sed -i 's/Claude Code向け core 31個/Claude Code向け core 30個/' README.md
bash scripts/validate-runtime-plugins.sh; echo "exit=$?"     # 0 以外を期待

# 3. 戻す
git checkout README.md
```

同じ手順を表 B / C / D と更新案内の見出しについても行う。
