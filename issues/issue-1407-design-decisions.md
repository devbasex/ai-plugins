# #1407: 決定の記録

設計文書 `issues/issue-1407-design.md` の「決定の記録」の節。1 ファイル 500 行の上限を超えるため分けた。

## 決定の記録

### 決定 1: 旧名の受け付けを `lib/legacy_names.py` の表 1 つに集める

旧名が効く所は、入口の引数・スクリプトのパス・プランのキー・記録のキー・ブランチの頭・記録の行の見出しの 6 種類に散っている。
それぞれの場所で旧名を持つと、受け付けをやめるときに消し残しが出る。前例の `bundle-close.py`（#987 で `mission-close.py` へ
改名）は、やめる版を決めずに残した結果、呼ぶ Skill が無くなった後も残っている。表 1 つに集めれば、消すときは表を引く所を
モジュール名で探せば尽きる。

各所に `if name == "mission"` を足す形は採らない。同じ役割の分岐が 6 か所に分かれ、I2 をテストで守れない。

根拠: Value 6 / Value 7（MVV 版 1）

### 決定 2: 旧名のスクリプトは、表の `forward` を呼ぶ数行の入口にする（シンボリックリンクにしない）

入口は案内の 1 行を出してから `os.execv` で新しいスクリプトへ引数をそのまま渡す。前例の `bundle-close.py` と同じ形で、結果と
終了コードは渡し先のものになる。

シンボリックリンクは採らない。リンクは呼ばれた名前を知らないため案内を出せず（AC4）、案内を出すには新しいスクリプトが自分の
呼ばれた名前を見る分岐を持つことになり、旧名が表の外へ漏れる（I2）。

根拠: Value 6（MVV 版 1）

### 決定 3: 受け付けをやめるときは、呼び出しを断る版を出してから消す

受け付けをやめる課題は、表の `MODE` を `refuse` にする。旧名の呼び出しは新しい名前を示して終了コード 2 で止まる（AC7）。
読み取り（キー・頭と見出し）は、その時点で進行中の改名の前の実行が無いため、同じ課題で行ごと消す。表と入口のファイルを
消すのは、断る振る舞いを 1 つの正式版として出した後で、その課題が時期を決める。

旧名を黙って消す形は採らない。改名の前に覚えた人やプランが、何が変わったか分からないまま失敗する。

根拠: Value 2（MVV 版 1）

### 決定 4: 受け付けをやめる課題は、実装の Pull Request を出す前に起票し、版数はリリースで書き足す

起票するのは実装の最後のタスクである（未決の 1 つ目）。外す対象は旧名の対応表の行で、行が確定するのは実装の後である。本文には
「改名を載せた正式版の次の正式版で `MODE` を `refuse` にする」と規則で書き、改名を載せた正式版の版数は `release` がその版を
出した時点で書き足す。決めの記録（`docs/ndf-version-decisions.md`）にも、その版のリリースで同じ規則と版数を書く（AC7）。

この課題の振り返りまで待つ形は採らない。振り返りは配布の後で、そこまでの間に規則が記憶にしか無い期間ができる。

根拠: Value 7（MVV 版 1）

### 決定 5: 用語集の `deprecated_code` に `mission` を載せない

用語チェックの識別子の照合は、識別子の意味を区別できない。MVV の Mission は `mission` の識別子を使い続ける（MVV の候補の
`mission` のキー、I5）。旧名の対応表も旧名を文字列で持つ。`mission` を載せると、どちらも変えた行が廃止した識別子として当たる。
日本語の 5 語は `deprecated` へ載せ、本文の置き換えの漏れは語で拾う。受け付けをやめる課題で表を消した後に、載せるかを決め直す。

根拠: Value 8（MVV 版 1）

### 決定 6: 既存の `mission/<名前>` は、ローカルと origin の参照だけで見つける

`new sprint` は、同じ名前の `sprint/` の参照が無く `mission/` の参照があれば、`mission/<名前>` を使う（I4）。参照は
`git for-each-ref` で見て、ネットワークへ出ない。プランを書き出すだけのコマンドが fetch で待たされず、ネットワークの無い所でも
同じ結果になる。

`git ls-remote` で origin を問い合わせる形は採らない。改名の前のスプリントは、そのスプリントブランチの worktree を同じ
リポジトリに持つため、ローカルの参照で足りる。

根拠: Value 4（MVV 版 1）

### 決定 7: 旧名の呼び方のテストは `test_legacy_names.py` の 1 本に集める

AC3〜AC5 の新しい名前のテストは、改名したテストのファイル（`test_sprint_state.py` など）がそのまま持つ。旧名の呼び方の
テストだけを 1 本に集めると、受け付けをやめる課題はこのファイルを「断る」テストへ書き換えるだけで済む。

旧名のテストを既存の各ファイルへ足す形は採らない。消すときに各ファイルを探すことになり、決定 1 と同じ消し残しが出る。

根拠: Value 6（MVV 版 1）

### 決定 8: 実際の出力を写したテストの素材は書き換えない

`plugins/ndf/scripts/tests/fixtures/wait_notice_corpus.json` は、過去の通知の本文を写した素材である。本文の「ミッション」は
その時点の出力で、書き換えると素材が実際の出力でなくなる。要求の前提 6（過去の記録は書いた時点の記録）と同じ扱いにし、AC2 の
grep の残りに数えない。

根拠: Value 3（MVV 版 1）

### 決定 9: スクリプトの出力のキーは、旧名を併記しない

`project-mvv.py` の `sprint_mvv`・`sprint-close.py` の内部の `sprint_prs`・`sprint-state.py status` の見出しの行は、新しい名前
だけを出す。出力を機械で読む所は、この 3 つのどれにも無い（`project-mvv.py` の出力を読むのは worker と conductor）。旧名の
キーを併記すると、同じ値のキーが 2 つある出力を、受け付けをやめる課題が消すまで配ることになる。

根拠: Value 1（MVV 版 1）

### 決定 10: `.ndf/pace.json` の「駆動」のパスの置き換えを、承認ゲート 1 の承認の対象に加える

`.ndf/pace.json` の `areas` の「駆動」は `plugins/ndf/scripts/mission-state.py` を指す。改名の後は処理の本体が
`sprint-state.py` にあるため、置き換えないと本体の変更が「駆動」の区分に数えられず、検査の起動の判定（`check-trigger.py`）の
点数が下がる。`.ndf/` の書き換えは共通原則の C7 に当たるため、要求の前提 7 の対象（`AGENTS.md`・`CLAUDE.md`・共通原則）と
合わせて、承認ゲート 1 で語とパスの置き換えだけを承認に掛ける。承認が無ければ置き換えない。

根拠: C7 / Value 2（MVV 版 1）

### 決定 11: 用語集の旧名の廃止は、設計ではなく実装の最初のコミットで行う

新しい 5 語は要求の Pull Request で用語集へ足してある。旧名を `deprecated` へ移すのは実装の最初のコミット（E1）にする。
設計の時点で廃止すると、実装までの間に進行中のスプリント（`m1389`・`m1400`）の Pull Request が旧名の行を足すたびに、用語
チェックが落ちる（要求の前提 8）。

根拠: Value 2（MVV 版 1）

### 決定 12: スプリント MVV の項目の頭は「スプリント」だけを読む

`lib/project_mvv.py` の項目の読み取り（`ITEM_RE`）は、頭の「スプリント」だけを認める。worker と判定は、改名の後の MVV の節の
説明（「頭に『スプリント』を付ける」）に従って答えるため、旧名の頭が返るのは説明に従わなかったときだけである。旧名の頭を
読むと、旧名の受け付けが表の外（正規表現）に漏れる（I2）。

根拠: Value 6（MVV 版 1）
