# #1843: cross-review: 投稿キューが GitHub の一時的な 500 で送れないだけで、結果を手元に持つ担当を missing とみなし、起動し直し・振り替え・中断まで進む

正は課題の本文（#1843）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

cross-review の round 1 で、codex と kiro はレビューを書き終え、結果ファイルと payload が手元に残っていた。しかし GitHub の REST API への POST が一時的に「HTTP 500・本文なし」を返したため、`gh api` は `unexpected end of JSON input`（終了コード 1）で失敗し、投稿キューの先頭（`0001-review-post-codex-r1`）が送れなかった。

このとき cross-review は、両者を「結果なし（missing）」とみなした。そのまま起動し直し → 振り替え → 中断へ進み、`final=error` で終わった。

- 起動し直した 2 者の投稿（0003・0004）も投稿キューに積まれ、1 回目の分と別のレビューとして並ぶことになった
- GitHub の POST が戻った後に `--from review` で再開すると、投稿キューが流れる

## どこで見つけたか

- スプリント m845 の検査、PR 1842 https://github.com/devbasex/ai-plugins/pull/1842 の round 1（2026-10-07 16:57 UTC）

- 投稿の処理: `skills/cross-review/scripts/review_lib/commands/read_result.py` の `posted.failed` で `die` する箇所、`scripts/lib/post_queue.py:126-131`（`(HTTP nnn)` が無いと状態を `None` にする）

## なぜこの変更の範囲外なのか

スプリント m845（#851・#865・#860）は起票の部品と pr-review のスクリプト化を扱い、cross-review の投稿の失敗の扱いは受け入れ条件に含まない。根拠: Value 4（利用者の手を止めない。一時的な失敗で検査が止まり、conductor が原因を調べて再開する手間が出た）・Value 3（戻せるようにする）（MVV 版 2）

## 直さないと何が起きるか

GitHub の一時的な障害のたびに、レビューの結果があるのに cross-review が中断し、検査のプランが止まる。起動し直した担当の分だけ LLM の費用とレビューの時間が余計にかかり、PR には同じラウンドのレビューが二重に並ぶ。

## 目的

- **GitHub の一時的な障害で、手元にあるレビューの結果を捨てない。** 結果ファイルが残っている担当を「結果なし」と数えず、起動し直し・振り替え・中断へ進ませない
- **一時的な失敗を、上限（rate limit）と同じ「待てば流れる」側へ寄せる。** 投稿キュー（`lib/post_queue.py`）はもともと上限のために積んで後で流す仕組みを持っている。見分ける語を足すのは共通の層で行い、cross-review だけに分岐を足さない（Value 6）
- **同じラウンド・同じ席のレビューが PR に二重に並ばない**

## 前提

- 前提 1: 「一時的な失敗」は、次のどれかに当たる送りの失敗とする。設計がこれより狭めるときは理由を残す
  - 標準エラーの `(HTTP <番号>)` が 500・502・503・504 のどれか
  - `(HTTP <番号>)` が無く、標準出力の本文が空で、標準エラーが応答を読めなかったことを示す（実例: `unexpected end of JSON input`）
  - `gh` の実行がネットワークの失敗（接続の切断・名前解決の失敗・時間切れ）で終わった
- 前提 2: 400・401・403（上限でないもの）・404・410・422 の扱いは変えない。恒久の失敗（`is_permanent_failure`）と、位置を解決できない拒否の退避（`is_position_unresolved`）もこれまでどおりである
- 前提 3: 一時的な失敗の後に GitHub 側でレビューが作られていた場合も、流し直す前の冪等の照会（`posted_match`。ラウンドと席までの鍵）が見つけるため、二重には送られない。照会そのものが一時的に失敗したときは送らずに残す（既存の `posted_match` が `None` を返す経路）
- 前提 4: 一時的な失敗は数分で戻ることが多い。流し直しの待ちの上限は、上限（rate limit）のときの既存の待ち（`retry` の既定 900 秒・間隔 30 秒）を超えない値を設計が決める
- 前提 5: 投稿キューは `cross-refactoring`（`refactor.py`）も使う。見分けの変更は共通の層に入るため cross-refactoring の投稿にも効く。cross-refactoring 側で投稿の失敗を受けて止める箇所の振る舞いは、設計で影響を確かめて記録する

## 対象範囲

| 含む | 含まない |
| --- | --- |
| 送りの失敗が一時的かを見分ける判定（`lib/post_queue.py`） | GitHub 側の障害そのものへの対処 |
| 一時的な失敗のときに積んだまま先へ進む扱い（`post`・`flush` の結果・`result_posts.post_review` と返信の送り） | 上限（rate limit）の見分け方の変更 |
| `read-result` が一時的な失敗のとき、結果を取り込んで 0 で終わること | 恒久の失敗（4xx）と位置の拒否の扱いの変更 |
| `drive.py` の判定の後の流し直し（終了コード 8 の枝）が、一時的な失敗のとき上限つきで待って流し直すこと | 既に PR 1842 で積まれた 0003・0004 の後始末 |
| 待ちの上限を超えたときに「投稿待ち」として止まり、担当を起動し直さないこと | 巻き直し（PR の作成・close・reopen）の `retry` の経路の変更 |
| cross-review の文書（`docs/07-posts-and-records.md`・`docs/01-state-and-review.md`）の該当の表 | 投稿キューの記録の形（耐久ワークフローの形）の変更 |

## ドメインイベント

| # | イベント | 引き金 | 失敗したとき | 順序の前提 |
| --- | --- | --- | --- | --- |
| E1 | 担当がレビューを書き終えた（結果ファイルと payload が残った） | 担当の CLI の終了 | 結果ファイルが無い → 既存の `NO_RESULT`（変えない） | — |
| E2 | 投稿を投稿キューへ積んだ | `read-result` | 積めない（記録の失敗）→ 既存どおり止める | E1 |
| E3 | 積んだ投稿を送ろうとして、一時的な失敗が返った | `read-result` の中の `flush` | — （このイベントが失敗の経路そのもの） | E2 |
| E4 | 送れていない投稿のまま、担当の結果を記録へ取り込んだ（`queued` が真） | E3 の後の `read-result` | 指摘ファイルを読めない → 既存どおり止める | E3 |
| E5 | 判定が「投稿が残っている」と答えた（終了コード 8） | `judge` | — | E4（両方の担当の取り込み） |
| E6 | 投稿キューを流し直し、送れた | `drive.py` の 8 の枝 | 一時的な失敗が続く → E7 | E5 |
| E7 | 流し直しの上限を超え、「投稿待ち」として止まった | E6 の失敗の繰り返し | — | E5 |
| E8 | 再開で投稿キューを流し、判定へ進んだ | `--from review` の再開 | 再び一時的な失敗 → E6・E7 と同じ | E7 |

順序の前提の確認: E4 は「投稿を送れていない担当の結果も取り込む」ことを仮定する。これは受け入れ条件 AC2 で定める。E6 の送り直しが既にある投稿と重ならないことは前提 3 に移した。

## 用語

| 用語 | 意味 |
| --- | --- |
| 一時的な失敗 | 前提 1 に当たる送りの失敗。送り直せば届く見込みがある。上限（rate limit）は含めず、別に扱う |
| 投稿待ち | 担当の結果は取り込んであり、投稿だけが投稿キューに残っている状態 |
| 結果なし | 起動した担当が使える結果を残さなかった状態（`NO_RESULT`）。投稿待ちとは別である |

## 受け入れ条件

- [ ] AC1: `gh api` の送りが前提 1 のどれかで失敗したとき、投稿キューの項目は消えずに残り、`flush` の結果は「待てば流れる失敗」として返る（`failed` を持つが、上限のときと同じく呼び出し側が失敗として扱わない印を持つ）。テストは HTTP 500・502・503・504、`(HTTP nnn)` 無しで本文が空の `unexpected end of JSON input`、ネットワークの失敗の 3 形を入力にする
- [ ] AC2: `read-result <PR> <担当>` で、今回分の投稿が一時的な失敗で送れなかったとき、終了コードは 0 で、ラウンドのその担当の記録に `queued` が真・指摘の件数が入り、標準出力に `QUEUED=1` が出る
- [ ] AC3: AC2 のとき、そのラウンドの `judge` は担当を `NO_RESULT` に数えず、起動し直し・振り替え（終了コード 7）も中断（終了コード 1・`final=error`）もしない。投稿が残っていれば終了コード 8（`verdict=queued`）を返す
- [ ] AC4: 終了コード 8 の後、一時的な失敗が戻れば、`drive.py` は担当を起動し直さずに投稿キューを流し切り、判定（0 か 2）へ進む
- [ ] AC5: 一時的な失敗が設計の決めた待ちの上限を超えて続いたとき、`drive.py` は担当を起動し直さずに止まり、止まった理由に「投稿待ち」と残りの件数と最後の失敗（`last_error`）を出す。`final` は `error` にしない（再開できる状態のまま残す）
- [ ] AC6: AC5 の後に `--from review` で再開すると、担当を起動し直さずに投稿キューを流し、送れたら判定へ進む
- [ ] AC7: 一時的な失敗を挟んだラウンドで、PR に同じラウンド・同じ席のレビューは 1 件だけである（流し直しの前に GitHub 側で作られていた場合を含む。前提 3）
- [ ] AC8: 退行しない — 400・404・410・422 の失敗は今までどおり `read-result` を止め（`review-post` は先頭で止め、ほかの種別は恒久の失敗として `dropped/` へ控える）、位置を解決できない 422 は今までどおり総評へ退避して送り直す。上限（403・429・上限の語）は今までどおり積んで先へ進む
- [ ] AC9: 退行しない — 送りが成功したときの `read-result` の出力（`POSTED review_url=` / `INLINE= BODY= QUEUED=0` / `FINDINGS=`）と記録の形は変わらない
- [ ] AC10: 返信と解決の送り（`result_posts` の返信の経路）も、一時的な失敗のとき失敗とせず残す。`pr-comment` の `post()` も一時的な失敗なら積んで `QUEUED` を返す
- [ ] AC11: 一時的な失敗かどうかの判定は `lib/post_queue.py` の 1 か所にあり、cross-review の `review_lib` と cross-refactoring は同じ判定を呼ぶ（同じ役割の関数を Skill ごとに分けない）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | GitHub の一時的な障害（前提 4 の範囲）で cross-review が中断しない（AC3〜AC6） |
| 性能・拡張性 | 一時的な失敗で担当を起動し直さないため、LLM の費用とレビューの時間が増えない。流し直しの待ちは前提 4 の上限に収まる |
| 運用・保守性 | 止まったときの出力から、投稿待ちと結果なしを読み分けられる（AC5） |
| 移行性 | 該当なし（投稿キューの記録の形は変えない） |
| セキュリティ | 該当なし（認証情報・権限に触れない） |
| システム環境 | 該当なし（`gh` CLI の出力の形にだけ依存する。前提 1） |
