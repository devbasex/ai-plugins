# #2347 の設計: 決定の記録

設計文書の本体は [issue-2347-design.md](issue-2347-design.md) 、入出力の契約とテスト設計は
[issue-2347-design-contracts.md](issue-2347-design-contracts.md) にある。

## 決定の記録

### 決定 1: 常駐の費用を増やさないため、実行をまたぐ制御は API と見回りに、ジョブの中の区切りはランナーに置く

利用者の原文は「relay.py に相当するオーケストレーターが低コストで常に動いている」構想を問うた。relay.py の役割は 2 つに分かれる。
1 つは周回をまたいで次を起こすことで、これは前の実行の終わり（停止の知らせ）と 5 分ごとの見回りという、既に呼ばれている契機で足りる。
もう 1 つは 1 つの会話の中の区切りで claude を起動し直すことで、ジョブの間だけ動くランナーがその場で行える。どちらも新しい常駐の
プロセスを要らない。

常駐の制御の Lambda や Step Functions の状態機械を置く案は採らない。待ちの大半は人の承認と枠の空きで、時間で起きる必要があるのは
リセット時刻だけであり、5 分の見回りで足りる。常駐を置くと、ループが 1 本も動かないアカウントにも費用が掛かる。

根拠: Value 4 / Value 10（MVV 版 4）

### 決定 2: 周回の実行を 2 本起こさないため、開発ループを実行の制御が持ち、ループ・実行・枠を 1 つのトランザクションで書く

ループの「今の実行」と実行の作成を別のトランザクションにすると、間で止まったときに見回りがもう 1 本を起こす。要求の非機能の
可用性はこれを禁じる。開始と終わりの状態への移りを 1 つのトランザクションで書く既存の例外（実行と枠）に、ループを 3 つ目として
足す。持ち主は実行の制御のまま 1 つにし（`factory/api/src/runs/loops.ts`）、別の構成要素がループの行を書かない。
DynamoDB のトランザクションは 100 件まで書け、最も多い書き込み（手動の開始で、実行 1・ジョブ 1・枠 2・課題の持ち分 20 の 24 件）でも足りる。

ループを別の持ち主（新しい `loops/` のサービス）にし、実行の終わりを事象で受けて結果整合で揃える案は採らない。事象の取りこぼしを
見回りで補う間に、同じ周回の実行が 2 本になる経路が残る。

根拠: Value 6（MVV 版 4）

### 決定 3: 選定から外す課題を機械で渡すため、NDF の `loop select` が環境変数 `NDF_LOOP_EXCLUDE` を読む

`loop exclude` は選定の後・`loop sprint` の前にしか打てず（`sprint_loop_select.py` の `cmd_exclude`）、ランナーはその間に
割り込めない。conductor への指示の文で「この課題を外す」と頼むと、決まった手順が LLM の判断へ回る。`loop select` が
環境変数の番号をその周回の除外（`excluded`、理由「別の実行が持つ課題」）へ足せば、手元の relay.py で複数のループを並べるときにも
同じ口が使える。環境変数は契約の一覧（`plugins/ndf/contracts/env/`）に宣言する。

根拠: Value 4 / Value 5（MVV 版 4）

### 決定 4: ループの状態を 1 つの表で決めるため、実行の終わり方と `loop.stopped` の組からだけ写す

| 実行の終わり方 | `loop.stopped` | ループ | 止まった理由 |
| --- | --- | --- | --- |
| `awaiting_approval` | `gate2_returned` か無し | `awaiting_approval` | — |
| `awaiting_reset` | — | `running` のまま | — |
| `done` | 無し | `between_laps` → `startNextLap` | — |
| `done` か `stopped` | `gate2_returned` 以外の条件 | `stopped` | 条件と `detail` |
| `failed` | 無し | `stopped` | `run_failed`（実行の `failureReason` を `detail` に） |
| `stopped` | 無し | `stopped` | `run_stopped`（`finishReason` を `detail` に） |
| `cancelled` | — | `cancelled` | — |

要求の E8 は失敗した周回の後も次を起こすとし、受け入れ条件 2 は `loop.stopped` の無いまま終わったループを `stopped` にする。
NDF が周回を失敗で締めた場合（`loop lap --failed`）、ジョブは `done` で終わり、`same_failure` の数え方は NDF に残る。
ジョブそのものが落ちた場合は NDF が周回を締めておらず、次の実行は同じ周回を `in_lap` で続けるため、起こし続けると同じ失敗を
数えないまま繰り返す。そこで実行の `failed` は受け入れ条件 2 のとおり止める。差し戻しで `gate2_returned` の周回が「人へ戻した」で
締まった後の `done` は、`loop.stopped` が無ければ次の周回へ進む。

根拠: Value 6（MVV 版 4）

### 決定 5: 周回 1 回をスプリントの実行 1 本に保つため、ランナーは周回が締まった区間の後に次の区間を起動しない

NDF の `loop lap` は周回を締めると、次の周回を始める `ndf-next` を返す。ランナーがそれに従うと、1 つのジョブが次の周回へ進み、
実行の枠・持ち分・費用の区切りがずれる。ランナーは区間ごとに `loop.json` の締めた周回の数と `stop` を読み、増えていれば終える。
次の周回は実行の制御が新しい実行で起こし、その時点の枠と取り合いを照らす。

ジョブの中で周回を続け、実行を周回の束にする案は採らない。並行する実行の取り合い（課題の持ち分・`EXCLUDE_ISSUES`）は実行を
起こす時点でしか照らせない。

根拠: Value 6（MVV 版 4）

### 決定 6: 承認の依頼の種類を増やさないため、`local` の次の周回と人の判断待ちは、ループの操作と知らせにする

全体の契約の I11 は承認の種類をゲート 1・2 に限り、決定 15 はサービスの側で承認を足さないとする。`local` の次の周回（未決 1）は、
今の手動の開始と同じ「利用者が始める」操作であり、承認の依頼ではない。ループは `between_laps`（`waitReason: user_start`）で
待ち、一覧の行と詳細に「次の周回を始める」を出し、#2173 は知らせ（承認の依頼にしない）を送る。

人の判断待ちの課題（未決 2）は、NDF の開発ループが周回を止めずに残す課題で、答えは今の実行を再開しない（次のジョブが
`loop answer` で書く）。承認の依頼にすると、#2173 の答えが `requestResume` を呼び、承認待ちでない実行に断られる。ループの詳細に
並べ、答えをループの行に持ち、知らせだけを #2173 が送る。

どちらも承認の依頼の新しい種類（例 `lap_start`）にする案は採らない。承認の工程を足すことになり、設計の規約にも I11 にも当たる。

根拠: Value 2（MVV 版 4）

### 決定 7: 利用上限の後に同じ周回を続けるため、実行を `awaiting_reset` にし、承認の依頼の識別子の無い `resume` で起こす

`stopped` は実行の終わりの状態で、そのまま写すと周回が途中で終わる。承認待ちと同じく、今のジョブを空にし枠を持ったまま待つ
状態 `awaiting_reset` を実行に足し、見回りがリセット時刻を過ぎたものに `START=resume` のジョブを作る。指示の
`APPROVAL_REQUEST_ID` は `resume` で必須だったが、答えを書かずに続ける再開のために省けるようにする（ランナーは手順 6 を飛ばし、
conductor へ「前回の続きから進めてください。」だけを渡す）。指示の形は緩めるだけで、今の書き手はそのまま通る。

新しい `START` の値（`continue`）を足す案は採らない。状態の復元と conductor の起動は `resume` と同じで、違いは答えの有無だけである。

根拠: Value 6（MVV 版 4）

### 決定 8: 2 つの読み手を食い違わせないため、`ndf-next` の読み方を NDF の契約の一覧に「受け渡しの形」として宣言し、例の組を両方のテストが読む

relay.py の規則（`relay_lib/mark.py` の `next_blocks`・`_mark_action`）は、CommonMark の 3 つのバッククォートの囲みで情報文字列が
`ndf-next` のもの、2 つ以上あれば書かない、である。ランナーは `plugins/` を参照しないため（全体の契約の I1 の逆向きは許されるが、
ランナーは実行時に NDF をマーケットプレイスから入れる）、規則を写すしかない。写した規則が古くなるのを防ぐため、契約の一覧に
新しい区分 `forms/`（ファイルでなく文の形の受け渡し）を足し、規則の文と例の組（入力の文・取り出すブロック・起動するか）を
置く。NDF の pytest と Factory の vitest が同じ例の組を読み、どちらかの答えが違えば落ちる（I55）。構造チェックは `forms/` の
項目の形を確かめる。

例の組を `factory/` に置く案は採らない。規則の持ち主は NDF で、NDF の変更が例を直す。

根拠: Value 6 / Value 7（MVV 版 4）

### 決定 9: リセット時刻を読めないときの待ち（未決 3）を、NDF の `supervise` と同じ 900 秒にする

`supervise_lib/claude.py` の `LIMIT_RETRY` は 900 秒で、NDF の中で同じ問題に既に使っている値である。Factory だけ別の値を持つと、
同じ利用者の機械で同じ上限に当たったときの振る舞いが分かれる。`local` の待ちはコンテナの費用を払わないため、短く刻んでも費用は
増えない。値はサービスの設定 `USAGE_LIMIT_RETRY_SECONDS`（既定 900）で変えられる。

5 時間（`five_hour` の窓の長さ）にする案は採らない。窓の終わりがいつかは分からず、多くの場合は待ちすぎる。

根拠: Value 3 / Value 6（MVV 版 4）

### 決定 10: 取り込みの衝突を `base_conflict` で出すため、ランナーの翻訳が `attention` の行の `step` から写す

NDF の base-sync は衝突で止まると `attention` の行を書くが、理由の語は工程の共通の語（止まった・同じ失敗など）で、`base_conflict`
を持たない。Factory の語へ変えるのは腐敗防止層の仕事で、翻訳を持つのはランナーだけである（全体の契約の決定 6）。`step` が
`base-sync` の行だけを写し、ほかの行は今の理由のまま送る。

NDF の supervise に新しい理由の語を足す案は採らない。NDF の側で `attention` の理由を読むのは conductor の文で、語を増やしても
NDF の振る舞いは変わらない。

根拠: Value 6（MVV 版 4）

### 決定 11: 課題とマイルストーンの取り合いを条件つきの書き込みで守るため、持ち分を実行の枠の行で持つ

同じ課題が 2 つの実行に入らないこと（I47）と、ループどうしのマイルストーンが重ならないこと（I45）は、読んでから書くと同時の
2 本がどちらも通る。手動の開始は課題ごとに、ループの開始はマイルストーンごとに行を `attribute_not_exists` で書き、実行・ループと
同じトランザクションで消す。手動の開始は、動いているループのマイルストーンに属する課題も断る（409 `issue_in_loop`）。マイルストーンを
ループに持たせた以上、外から課題を差すと周回の選定と同じ課題を取り合うためである。ループの周回が選ぶ課題は持ち分の行を書かない。
ループどうしはマイルストーンで分かれ、手動の実行とは `EXCLUDE_ISSUES` と `issue_in_loop` で分かれる。

周回の選定の結果（`phase.changed` の課題）を事象から持ち分へ書く案は採らない。受け口が実行の制御を呼ぶことになり、全体の契約の
向きに反する。

根拠: Value 6（MVV 版 4）

### 決定 12: 古い版どうしの衝突を避けるため、リポジトリの枠に古い版の数を持ち、下限は設定で持つ

並行を許すかは、新しく起こす実行と動いている実行の両方の版で決まる。リポジトリの枠の行に `legacyCount` を足し、古い版の実行は
`count` が 0 のとき、新しい版の実行は `legacyCount` が 0 のときだけ書く。比べるのは版の `@` より前を semver として読んだ値で、
開発版の接尾辞は semver の前置きの版として小さく読む。下限は `NDF_PARALLEL_MIN_VERSION`（コードに埋め込まない。前提 6）で、
無ければすべての版を古い版として扱う。#2164 の最初の開発版を許したいときは、その接尾辞つきの版を下限に置く。

実行の行を読んで版を数える案は採らない。読んでから書く間に別の開始が通る。

根拠: Value 5 / Value 6（MVV 版 4）

### 決定 13: 手元の機械を守るため、`max_jobs` の申告は #2189 の登録が持ち、受け取りの条件と目安の関数をこの課題が持つ

申告の値の保存は手元のランナーの登録（#2189）の集約に属する。この課題は `claimLocalRunJob` の入力にランナーの識別子と申告を
足し、手元のランナーの枠を条件にした書き込みで `max_jobs` を超えて渡さない（I50）。目安は 2026-09-25 の実測（8 コア・30 GB で
6 本）から 1 本あたり 4/3 コア・5 GiB とし、`max(1, min(floor(CPU の数 × 3 / 4), floor(メモリの GiB / 5)))` で出す。申告が目安を
超えれば手元のランナーが標準エラーへ 1 行の警告を出し、申告はそのまま送る。

サービスが目安で申告を切り詰める案は採らない。手元の機械の資源を知るのは手元だけで、サービスは利用者の環境を知らない。

根拠: Value 3 / Value 5（MVV 版 4）

### 決定 14: 状態の数を増やさないため、止まった・取り消したループは終わりとし、続きは新しいループで始める

NDF の止まる条件の多くは再開で解ける（`budget_*` は予算の上書き、`no_issue` は選定のやり直し）。Factory でそれを受けると、
`stopped` から戻る遷移と、どの条件が戻れるかの表が要る。止まった後に続けたい利用者は、同じマイルストーンで新しいループを
始める（持ち分は止まった時点で消えている）。予算の変更は終わりの状態でないループにだけ効き、次のジョブの指示から NDF の
`--budget-*` へ渡る。

根拠: Value 1（MVV 版 4）

### 決定 15: 取り消しの経路を 1 つにするため、ループを止めるときに NDF の `loop stop` を打たない

要求の前提 5 は、止めたループのランナーへ `loop stop` に当たる知らせを渡すとする。動いている実行は今の取り消し（`cancelSprintRun`）で
止まり、ランナーは `SIGTERM` で何も送らずに終わる。取り消したループには次のジョブが起きないため、NDF の記録に止める印を
書く先が無く、書いても読む者がいない。知らせはループの `cancelled` そのものとする。

根拠: Value 1（MVV 版 4）

### 決定 16: 予算の残りが止まる判定と食い違わないため、周回の数・費用・時間は NDF が締めた周回の値で出す

止まる条件を判定するのは NDF で、NDF は締めた周回の費用と秒を和にして予算と比べる。Factory の `usage.recorded` の和で残りを出すと、
画面の残りが 0 でも止まらない、またはその逆が起きる。一覧の「費用」「周回の数」「予算の残り」は `loop.lap_closed` の和で出し、
今の周回の分は詳細の画面で実行ごとの `usage.recorded` の和として別に出す。

根拠: Value 3（MVV 版 4）
