# #526 設計文書で、表から導ける値を数え直す

`design` の手順を変え、利用者のエージェントが設計文書を書くときの振る舞いが変わる。配布する
Skill の手順の変更であるため、モードは `standard` である。

## 依頼（原文）

> **設計文書で「表の値」を根拠にした判断が、数え直すと成り立たなかった。**
>
> マイルストーン 10 の設計（PR #516）で、`documentation` の高さを 5 にする根拠を
> 「必須の工程が最も多い」と書いた。**同じ設計文書に載っている工程表で `R` を数えると、
> `standard` が 16 個、`documentation` は 14 個で成り立たない。**
>
> **同じ形の指摘がもう 1 件あった。** 対象外のセルの数を「9 セル」と書いたが、内訳を足すと
> 21 セルだった（新しい 2 行 × 既存 4 モードの 8 セル + 既存 16 行の 13 セル）。
>
> `design` の手順（設計文書を書く段）へ、次の 1 行を足す候補がある。
>
> > **同じ文書の表から導ける値を本文へ書くときは、書いた後に数え直す。** 「最も多い」「N 件」
> > 「すべて」は、表を数えれば確かめられる。
>
> **`design/references/` には既に内部整合を確かめる手順がある**（#463 で入れた「同じ文書の中で
> 突き合わせる 6 件」）。そこへ 1 件足す形が候補になる。
>
> **あわせて、値を足す変更では既存の規則がその値に当たるかを 1 度通す。** マイルストーン 10 の
> 実装 2（PR #519）では、`documentation` の 4 形を足したことで既存の規則 3 つが新しい形に
> 当てはまらなくなっており、レビューが major 3 件として拾った。

（issue #526 の本文から「何を見つけたか」と「何をするか（案）」を抜粋した）

## 目的

| 問題 | 達成したい状態 |
| --- | --- |
| 表から導ける値を、数えずに本文へ書く | 設計 Pull Request を出す前に、本文の値と表を数え直した値が一致している |
| 値の集合へ値を足しても、旧い集合を前提にした規則が残る | 変える対象の規則が、設計の時点で構成要素の表に載っている |

## 現状（2026-09-13 の `develop` で数えた）

**突き合わせる対は 6 つである**（`design/references/design-template.md` の「進む前に突き合わせる
対」の表の行数）。issue が書いた件数と一致する。

**表から導ける値を扱う対は、3 つ目の 1 つだけである。**

| 突き合わせる対 | 何を見るか |
| --- | --- |
| 件数の記述 ↔ 表の行数 | 「次の N か所」と書いた直下の表が N 行あるか |

この対が見るのは**直下の表の行数**だけで、PR #516 の 2 件はどちらも当たらない。

| PR #516 の指摘 | 導いた値の形 | 3 つ目の対に当たらない理由 |
| --- | --- | --- |
| 「必須の工程が最も多い」 | 列ごとの `R` の数の比較 | 行数ではない。値は決定の記録（分割した別のファイル）に書かれ、表は設計文書の「工程表」の節にある |
| 「9 セル」 | セルの数の内訳の合計 | 行数ではない |

**値の集合へ値を足したときに、既存の規則を集める手順は `design` に無い。** 6 つの対はいずれも
同じ文書の中だけで確かめるもので、文書の外にある規則を見ない。

## 前提

- 前提 1: 設計 Pull Request（`design/` 接頭辞）を先に出し、マージしてから実装の Pull Request を出す
- 前提 2: 配布する Skill の数は変わらない。`manifests/*-skills.txt` と版数を持つ 15 箇所は影響を受けない
- 前提 3: 突き合わせる対の定義（同じ文書の中だけで確かめられる。確かめた結果は残さない）は変えない
- 前提 4: #493（図の連結を見る対を足す）は別のマイルストーンで扱う。この変更には取り込まない

## 対象範囲

含む:

- 突き合わせる対のうち、表から導ける値を扱う対を、行数以外の値と別の節の表へ広げる
- 表を直したときに、その表から導いた本文を数え直すことを書く
- 値の集合へ値を足す設計で、その集合を前提にした既存の規則を集めて判定する手順を置く

含まない:

- 図の連結を見る対（#493）
- 突き合わせを機械で確かめる検査スクリプト（理由は設計文書の決定の記録にある）
- 確定仕様 `docs/specifications/ndf-design-phase.md` への反映（`plan-to-spec` の工程が行う）
- 既存の設計文書（`issues/` / `docs/specifications/`）を数え直すこと
- 設計の成果物のうち、クラス図・非機能設計表・配置の図（`standard` で必須だが対象が無い。
  型を持たず、非機能の条件を持たず、実行の単位が変わらない文書の変更である）

## 用語

| 用語 | この文書での意味 |
| --- | --- |
| 導ける値 | 表を数えれば決まる値。行やセルの数、列ごとの数の最大と最小、「すべて」「どれも」 |
| 値の集合 | モード・出力の形・種類のように、規則が値ごとに分岐する対象の一覧 |
| 既存の規則 | 配布物の文書に書かれ、集合のそれまでの値だけを前提にした記述。値の名前を書かないものも含む |

## 受け入れ条件

- [ ] `design-template.md` の対の表に、本文に書いた導ける値と、その表を数え直した値を照らす対がある
- [ ] その対の「何を見るか」が、行数に加えて、セルの数・最大と最小・「すべて」を対象に含む
- [ ] その対が、直下の表だけでなく同じ文書の別の節（分割した設計文書では別のファイル）にある表から導いた値も対象にする
- [ ] 表を直したときに、その表から導いた本文も数え直すことが対の節に書かれている
- [ ] 突き合わせる対の数を書いた 2 箇所（`SKILL.md` の手順 4 と対の節の冒頭）が、対の表の行数と一致する
- [ ] `SKILL.md` の手順 2 に、値の集合へ値を足す設計では、その集合を前提にした既存の規則を集め、
      新しい値に当たるかを判定し、当たらない規則を構成要素の表へ載せる手順がある
- [ ] その手順の集め方が、集合と値の名前での検索と、新しい値が通る手順を読むことの 2 つである
- [ ] 手順 2 に置く規則は、対の表にも手順 4 にも置かれていない（対は同じ文書の中だけで確かめる定義のまま）
- [ ] `python3 scripts/check-doc-line-limit.py` / `python3 scripts/check-markdown-links.py --root .` /
      `python3 scripts/check-skill-frontmatter.py` / `claude plugin validate .` が終了コード 0 で終わる

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない。Skill の名前・起動の説明文・引数は同じ |
| データ | 無い |
| 既存の振る舞い | `design` を通すエージェントが、設計 Pull Request の前に表を数え直す。値を足す設計で既存の規則を集めて判定する |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| 文書の分量 | `python3 scripts/check-doc-line-limit.py` |
| リンク | `python3 scripts/check-markdown-links.py --root .` |
| Skill の frontmatter | `python3 scripts/check-skill-frontmatter.py` |
| 定義の検査 | `claude plugin validate .` |
| 手動確認 | 受け入れ条件 1〜8 を、差分の本文を読んで判定する。対の数は表の行を数えて確かめる |

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | 変更後に対の数と表の行数を数え直す。上の 4 つの検査を実行する |
| 確認してから行う | 対の定義（同じ文書の中だけで確かめる）を変えること。検査スクリプトを足すこと |
| 行わない | #493 の対を足すこと。既存の設計文書の書き直し。版数の変更 |
