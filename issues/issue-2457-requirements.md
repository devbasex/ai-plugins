## 目的

cross-refactoring が選んだリファクタリングを、最後まで入れ切れるようにする。今は時間の予算と実装以降の制約が、テストの失敗や時間切れを理由に項目を取り消すため、改修を 5 件実装しても採用 0 件で終わる回がある（下の「起きたこと」）。予算は「何件を選ぶか」を決めるためだけに使い、選んだ項目は、成立しない（企画に無理がある）と判定したときと、安全網の上限に当たったとき以外は止めない。

## 起きたこと（2026-11-03、#2436 のスプリント）

スプリントの develop 宛て PR https://github.com/devbasex/ai-plugins/pull/2452 の完了判定で、cross-refactoring はリファクタリング計画の 5 項目を実装し、範囲のテストも通した。それでも **採用 0・取り消し 5・見送り 26** で終わった。

1. 最終ゲートの CI で、リファクタリングと無関係のテスト 1 件が落ちた（`plugins/mcp/mcp-serena/tests/test_serena_lsp_this_repo.py`。develop の取り込みで bash がしきい値を割った。PR https://github.com/devbasex/ai-plugins/pull/2456 で直した）
2. CI の JUnit を読めず、変更起因かどうかを判定しないまま不合格になった。締め切りで最終ゲート修正を打ち切り、5 項目すべてを起点の木へ戻した（コミット `695946cb1`。理由は「落ちたテストを走らせ直す語が無い（変更起因を挙げられない）」）
3. 再開した実行は、木が起点と同じなので最終ゲートの確かめを省き、`passed` を返した。リファクタリングが 1 件も入らないまま検査が先へ進んだ
4. 見送り 26 件はすべて `budget`（時間の予算）が理由だった

## 根本原因

**制約が実装の後まで掛かり、破れたら取り消す設計になっている。** 時間の予算は選ぶ件数だけでなく、実装・修正・最終ゲートの締め切りにも使われる。テストの失敗・範囲のはみ出し・記名の欠けなどは、直す代わりに項目を取り消す理由になる。棚卸しでは、取り消しか打ち切りを起こす制約が 21 件、不要か阻害する制約が 15 件あった（下の「制約の棚卸し」）。

## 原則

1. **予算は選定にだけ使い、予算を理由に打ち切らない。** 予算に数えるのはコーディング（実装）の時間だけで、案出し・選定・テスト・CI の待ちは数えない
2. **テストが落ちたら、まずリファクタリングが成立しているかを判定する。成立している限り直し切る。** 成立しない（企画に無理がある）ときに限り、その項目を打ち切る。失敗そのものは取り消しの理由ではない
3. **制約は案出しと選定のときだけ参照する。選定したリファクタリングは最後までやり通す**
4. **不要な制約・リファクタリングを阻害する制約は取り除く**

## 変えること

| 項目 | 今 | 変えた後 |
| --- | --- | --- |
| 予算の既定 | 30 分（`refactor_lib/vocabulary.py` の `DEFAULT_BUDGET_MINUTES`。手順の枠が収まらなければ下限まで上げる） | **60 分** |
| 予算の使い道 | 選定・手順の上限・テスト 1 回の上限・無音の打ち切りのすべてを、この値から逆算する | **選定にだけ使う** |
| 予算に数える時間 | 案出し・選定・テスト・CI の待ち・修正を含む全体 | **コーディングの時間だけ** |
| 選び方 | 順位 → 見積り → 時間に収まる件数 → 締め切り | **従来どおり Skill の選定を使う**（グレード・賛同数・重要度の順位で並べ、見積りの合計が予算に収まるまで採る）。変えるのは、見積りに数える時間をコーディングだけにすることと、締め切りを外すことだけ |
| 予算の延長 | 無い | **順位の高いものを予算の境目で絞り切れないときは、2 倍（既定なら 120 分）まで延ばしてよい。** 延ばした理由を記録する |
| テストの失敗 | 締め切りまで直し、通らなければ原因の項目から取り消す。原因を挙げられなければ起点の木へ戻す | **リファクタリングが成立しているかを判定する。** 成立している限り直し切る。成立しない（企画に無理がある）場合に限り、その項目を打ち切る |
| 実装での範囲のはみ出し | 範囲の外の既存ファイルを、呼び手の書き換え（H1・H2）以外で変えた・消した・改名した項目を取り消す | **制約から外す。** 範囲（`--scope`）は案出しの対象を決めるのにだけ使う。ライブラリへの統合・共通部品の切り出しなど、リファクタリングが範囲を超えるのは普通のことである |
| 実装の中の制約違反（記名の欠け・手順外のコミットなど） | 項目か修正の範囲ごと取り消す | **差し戻して直させる** |
| 無関係な失敗（ベースブランチ由来・既存失敗） | JUnit を読めないと変更起因と区別できず、不合格のまま打ち切りへ進む | **着手前の木と比べて見分け、無関係なら項目の合否に数えない** |
| フレーキーなテスト | 走らせ直して通れば無視する | **見つけたら即時修正する。** 後からでは再現が難しく直せないため。直しは項目とは別のコミットにし、項目の合否に数えない（#2458） |
| 記録 | 手順ごとの所要と想定最大時間との差 | **項目ごとの内容・見積りの時間・実際にかかったコーディング時間**を記録し、次回以降の見積り（`/ndf:estimate`）の参考にする |

## 前提

- 前提 1: 対象は `plugins/ndf/skills/cross-refactoring/` と、その既定値を持つ `plugins/ndf/contracts/limits.json` の `cross-refactoring.default-budget`（今は 1800 秒）である。cross-review と fix は、フレーキーの扱い（#2458）を除いて対象にしない
- 前提 2: 下の「制約の棚卸し」の行番号は v10.27.14 の時点のもので、v10.27.50 では行番号がずれている箇所がある（`DEFAULT_BUDGET_MINUTES` は今 `limits.json` から読む形になっている）。設計で行ごとに今の位置を引き直す。制約の中身は変わっていない前提で進め、変わっていた行は設計で分類を付け直す
- 前提 3: 安全網の上限の既定は「実装の予算の 2 倍（延長したときは延長後の値の 2 倍）」、停滞は「落ちたテストの集合が 2 回続けて同じ」、振動は「前に見た集合へ戻る」とする。値と定義は設計で見直せる既定値であり、`limits.json` などの設定に置いて変えられる
- 前提 4: 実装の時間は、オーケストレーターの時計とコミットの時刻で測る（今の見積りの測り方を引き継ぐ。担当の申告を使わない）
- 前提 5: 1 回の採用が増えると Pull Request の差分も増える。差分の大きさの上限はこの課題では決めず、受け入れ条件 14 の実績を見て別の課題で決める
- 前提 6: 打ち消しは、打ち消すコミットを積む形で行う（`git revert` の形）。履歴の書き換え・強制 push は使わない

## 用語

| 用語 | 意味 |
| --- | --- |
| 実装の予算 | `--budget-minutes` の値。改善項目を何件選ぶかを決めるためだけに使う、実装（コーディング）時間の見積りの合計の上限。今の用語集の「想定最大時間」（実行全体の子プロセスを止める締め切り）を置き換える |
| 実装時間 | 改善項目のテスト追加・実装・修正で担当の CLI が動いた時間。提案・選定・テストの実行・CI の待ちは含めない |
| 予算の延長 | 順位の高い候補を境目で絞り切れないときに、実装の予算を 2 倍までの範囲で増やすこと |
| リファクタリングの成立 | 改善項目が、振る舞いを変えずに、計画の前提にした構造の上で直し切れる見込みがあること。成立しない例: 振る舞いを変えないと直せない・前提の構造が実在しない |
| 無関係な失敗 | 着手前の木（取り込んだベースブランチを含む）でも落ちるテストの失敗。改善項目の合否に数えない |
| 停滞 | 修正の後の落ちたテストの集合が、前の回と同じであること |
| 振動 | 修正の後の落ちたテストの集合が、前に見た集合へ戻ること |
| 安全網の上限 | 実装時間と修正の時間の合計に置く上限。異常の検知にだけ使い、当たっても取り消さずに止めて人へ渡す |

## 受け入れ条件

予算と選定:

- [ ] 1. `--budget-minutes` を省いたとき、実装の予算が 60 分になる（結果 JSON の予算の値で見る）
- [ ] 2. 実装の予算に数えるのは実装時間だけである。提案・選定・テストの実行・CI の待ちに何分かかっても、選定で採れる件数は変わらない（同じ候補と配分テーブルで、テストの所要だけを変えて選定を 2 回走らせ、採る件数が同じになる）
- [ ] 3. 選定は棚卸しの制約 #6〜#11 の順位（グレード・賛同数・重要度）と見積りを使い、見積りの合計が実装の予算に収まる分だけを採る。収まらない候補は `budget` で見送られる
- [ ] 4. 順位の高い候補を予算の境目で絞り切れないとき、2 倍までの範囲で予算を延ばして採る。延ばしたこと・延ばした後の値・理由が結果 JSON と報告に残る。2 倍に収まらなければ延ばさない

実装以降で取り消さない:

- [ ] 5. 実装の予算を超えても、実装・テスト・最終ゲートを打ち切らない（予算を短くした実行で、予算を超えた後も最終ゲートまで進む）
- [ ] 6. テストが落ちたら、改善項目ごとにリファクタリングの成立を判定する。判定と根拠が項目ごとに結果 JSON に残る
- [ ] 7. 成立している項目は、テストの失敗でも制約違反（記名の欠け・手順の外のコミット・期待値の欠け・文言を固定するテスト）でも取り消さない。失敗は修正へ回し、制約違反は差し戻して直させる
- [ ] 8. 実装・修正・最終ゲート修正が範囲の外のファイルを変えても（既存ファイルの変更・削除・改名を含む）、範囲を理由に項目を取り消さない。範囲の外で変えたファイルは報告に載り、コードレビューへ引き継がれる
- [ ] 9. 成立しないと判定した項目に限り打ち切り、その項目のコミットだけを打ち消す。理由が項目ごとに記録に残る（棚卸し #12・#32 の扱い）
- [ ] 10. 無関係な失敗（PR 2452 の Serena のテストの形: ベースブランチの取り込みで落ちたテスト）を再現するテストで、通っていた項目が取り消されず、その失敗が無関係と記録される
- [ ] 11. フレーキーと見分けたテストは、その実行の中で直す（規則と受け入れ条件の正本は #2458）
- [ ] 12. 打ち消しが要るときは、改善項目のコミットだけを打ち消す。着手の後に取り込んだベースブランチの変更は消えない（#2323 の形を再現するテストで見る）
- [ ] 13. 最終ゲートで CI の JUnit を読めないときも、落ちたテストの ID・ログの場所・走らせ直すコマンドが修正担当の CLI へ渡る（#1657）

記録と棚卸し:

- [ ] 14. 実行ごとに、改善項目ごとの内容・見積りの時間・実際の実装時間が記録され、次回の選定の見積り（配分テーブル）が読める場所に残る。安全網で止まった実行でも残る
- [ ] 15. 下の「制約の棚卸し」の C と D の各行が、実装の後に「置き換えた」「削った」「残した（理由）」のどれかになっている（設計文書か実装の PR に表で残る）

止め方:

- [ ] 16. 修正 1 回ごとに落ちたテストの集合を前の回と比べ、件数が減るか別のテストへ移る限り、回数の上限なく修正を続ける
