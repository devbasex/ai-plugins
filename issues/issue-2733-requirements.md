## 目的

- 並列の計画を動かしているマシンで、人との窓口をオーガナイザーの 1 か所にする。別のリポジトリの開発セッションも、問いと承認をオーガナイザー経由で受ける
- 計画の外で開発のセッションが動き、窓口が割れる状態をスクリプトで防ぐ。必要な並行の作業は、レーン数の上限を変えてレーンとして足す
- 並行開発の語と規定を `docs/ndf-parallel-model.md` を仮の正本としてそろえ、用語集・確定仕様・手順書・スクリプトの間で食い違いを無くす。辻褄が合わない点は文書の側を直す

## 前提

- 前提 1: 別のリポジトリのレーンは、計画と同じマシン（文書の実行の形 A: 1 台）で動く。Factory の形とマシンをまたぐ形のレーンの登録は含まない
- 前提 2: 別のリポジトリには NDF が導入され、`.ndf/` の設定（ベースブランチ・リリースの設定）を持つ。そのレーンのリリースは、そのリポジトリの設定に従う
- 前提 3: 「計画の外のセッション」は、動いている計画（耐久ワークフローが終わっていない計画）があるマシンで、計画のレーンでもオーガナイザーでもないのに開発ループかスプリントを始めるセッションを指す。開発ループもスプリントも始めない対話だけのセッションと、動いている計画が無いマシンのセッションは対象外で、振る舞いは変わらない
- 前提 4: 語の決定 5 件は PR 2723 の文書の「語の決定」の表で進める（S6・S7）。PR 2723 のレビューか設計承認ゲートで利用者が差し戻した語は、その決定に従って受け入れ条件 9〜12 を満たす
- 前提 5: 計画の外のセッションは、起動を止め（終了コード非 0）、レーンの追加の手順を案内する。例外の起動は明示の指定でだけ通す（S10）。指定の形は `design` で決める
- 前提 6: 作業は少なくとも 2 つのスプリントに分ける（S1・S2）。分け方と順序は `implementation-plan` が決め、受け入れ条件はどのスプリントで満たすかを計画に書く
- 前提 8: 実装は PR 2723 のマージの後に始める。それまでの仮の正本は PR 2723 のブランチ（`docs/ndf-parallel-model`）の文書である。2026-11-08 時点で PR 2723 は開いたままで、`origin/develop` に `docs/ndf-parallel-model.md` は無い（`git show origin/develop:docs/ndf-parallel-model.md` が `does not exist` を返した）
- 前提 7: 受け入れ条件 4 は、#2707（答えを待つ問いの件数でレーンを止める）が入っていることを前提にする。#2707 が先に入らない場合、受け入れ条件 4 は #2707 の実装で満たす

## 受け入れ条件

### 別のリポジトリのレーンと計画の外のセッション

- [ ] 1. 前提: リポジトリ X に動いている計画がある。操作: リポジトリ Y のセッションを、その計画のレーンとして登録して起動する。結果: Y のセッションでレーンの判定（今の `lane_of` に当たる判定）が、X の計画名とそのレーンを返す
- [ ] 2. 1 のレーンが設計承認ゲートか区分つきの問いに当たると、問いは Y のセッションの画面に出ず、X のオーガナイザーの依頼の一覧に 1 件載る。オーガナイザーが答えると、Y のレーンがループの 1 回の境でその答えを読んで進む
- [ ] 3. 1 のレーンのリリース承認ゲートの後、リリースは Y の設定のチャネルへ出て、X の計画のまとめたリリースの中身（リリースの依頼の一覧）に Y の変更が入らない
- [ ] 4. 答えを待つ問いの件数（#2707）に、1 のレーンの問いが 1 件ずつ数えられる
- [ ] 5. 前提: マシンに動いている計画がある。操作: 計画のレーンでもオーガナイザーでもないセッションで開発ループかスプリントを始める。結果: 起動は終了コード非 0 で止まり、レーン数の上限を変えてレーンを足す手順の置き場が出力に出る。明示の例外の指定があれば起動する
- [ ] 6. 動いている計画が無いマシンでは、5 の操作は今と同じく起動する（退行しない）
- [ ] 7. レーン数の上限を変更して計画へレーンを足す手順が手順書にあり、その手順のコマンドを実際の計画で 1 度通した記録（コマンドと結果）が実装の Pull Request にある
- [ ] 8. 上限を変えずに上限を超えるレーンを足そうとすると、計画の検査が断り、上限の変え方を出力に出す

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 5 で止めたとき、止めた理由と案内が統一 JSON レポートの形で出る。別のリポジトリのレーンの問いは、オーガナイザーの一覧で同じリポジトリのレーンの問いと区別できる（どのリポジトリのレーンかが分かる） |

## 設計の手がかり（PR 2723 の作業でコードを読んだ見立て。未確認）

2026-11-07 に PR 2723 の作業の中で読んだコードからの見込み。`design` で確かめる。

- 同じマシンの計画の一覧（ランナー全体の台帳）を 1 つ持たせると、別のリポジトリのレーンの判定（指摘 1）と計画の外のセッションの判定（指摘 2）を同じ部品で賄えそう
- 計画の置き場を決める `parallel_plan.plan_dir` の 1 か所で別のリポジトリへ解決すれば、呼び出し元を個別に直さずに済みそう
- 別のリポジトリのレーンの承認済みの設計 PR を、オーガナイザーが自分のリポジトリでマージしてしまう恐れがある（`parallel_answer.merge_design` は計画の置かれたリポジトリで動く）
- リレーハブの上限 `NDF_RELAY_MAX_NAMED` はハブのプロセスの環境から読むため、上限を変えるにはハブの起動し直しが要りそう
