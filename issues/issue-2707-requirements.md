## 目的

並列の計画で、人が答えを読み切れる量を超えて依頼が溜まり続ける状態を作らない。溜まったら、人が答えるまで新しい作業を増やさず、答えたら人の操作なしで作業へ戻る。

## 前提

- 前提 1: 上限の撤廃（#2505）はこの作業のブランチの起点（develop、227851142、版 10.27.37-dev.1）に入っている。`rg -n release_pending_max plugins/ndf/scripts/lib` は 0 件で、保留の周回の上限は判定から消えている
- 前提 2: 閾値は止める引き金であり、依頼を受け付ける上限ではない。止める判断の後も、動いている周回とプランは区切りまで進むため、答え待ちの依頼は閾値より増えることがある。増える数の上限はこの要求では決めず、残リスクとする
- 前提 3: 対象は並列の計画（`.ndf/parallel/<計画名>/`）の下のレーンである。外のオーガナイザーのレーンは設計の承認と問いを依頼にしない（`parallel.md` の「外のオーガナイザーのレーン」）ため、数えるものが無い。1 台の中のオーガナイザーを持たない Factory の実行ジョブも同じである
- 前提 4: 利用者がオーガナイザーの問いへ答えないまま止まり続けても、期限で再開しない。人が読み切れないという理由で止めているため、時間では解消しない
- 前提 5: 依頼の一覧は耐久ワークフローが持つ（`plugins/ndf/scripts/lib/parallel_run.py`）。#2647（PR 2704）と #2649（PR 2703）は同じ経路を変える未マージの設計である。どちらが先に入っても、受け入れ条件の振る舞いは変えない。設計は、それらの設計の取り込み後の形で書き直す要否を確かめる
- 前提 6: オーガナイザーは `AskUserQuestion` の答えを待つ間、`parallel.py wait` の知らせを読めない（`parallel.md` の「答えの後の整理」）。そのため止める判断はオーガナイザーのセッションの外で行い、利用者への知らせは答えの後か次の `wait` で表に出る

MVV との突き合わせ: 反する疑いは無いと判定した。承認の工程を足さず、既存の依頼へ答えるまで作業を増やさないだけである（Value 2・Value 3・Vision）。閾値を既定へ固定せず宣言で変えられる形にする（Value 6）。必ず承認が要る操作（C1〜C8・P1）には当たらない。根拠: Vision / Value 2 / Value 3 / Value 6（MVV 版 6）

## 対象範囲

含む:

- 答え待ちの依頼の数え方（計画全体と 1 つのレーン）
- 閾値を超えたときに新しい作業を止めること。件数が戻ったときの再開

- 外のオーガナイザーのレーン、並列の計画の外の開発ループ（前提 3）
- 動いているプランを途中で打ち切ること
- 人の読める量の実測と、閾値の値の見直し
- スプリントで作る量の上限（Value 2 の課題の数と承認資料の分量）
- #2505 で外した上限を戻すこと

## 用語

| 用語 | 意味 |
| --- | --- |
| 答え待ちの依頼 | オーガナイザーに届いて、まだ答えていない依頼。設計の承認・リリース承認ゲート・承認ゲートの外の問い・耐久ワークフローが自分で立てた問いの 4 種類である |
| 計画の閾値 | 計画全体の答え待ちの依頼の件数の閾値。既定は 4 で、これを超えると計画のすべてのレーンを止める |
| レーンの閾値 | 1 つのレーンが送った答え待ちの依頼の件数の閾値。既定は 3 で、これを超えるとそのレーンを止める |
| 答え待ちの停止 | 答え待ちの依頼が閾値を超えたため、レーンに新しい作業を始めさせない状態。件数が閾値以下へ戻ると解ける |

## 受け入れ条件

計画全体の数え方:

- [ ] 1. 計画の閾値が 4 のとき、答え待ちの依頼が 4 件ではどのレーンも止めない

- [ ] 5. 同じ原因で 1 つにまとめた問いは 1 件と数え、同じレーンの同じ設計 Pull Request の新旧の依頼も 1 件と数える

1 つのレーンの数え方:

- [ ] 7. レーンの閾値が 3 のとき、1 つのレーンが送った答え待ちの依頼（設計の承認と承認ゲートの外の問い）が 3 件ではそのレーンを止めない

| 確認してから行う | 公開インタフェースの変更と閾値の宣言の形（設計承認ゲート で人が見る） |
| 行わない | 依頼を捨てること、動いているプランの打ち切り、作業を止めるための新しい承認の工程、既存の宣言の書き換え |
