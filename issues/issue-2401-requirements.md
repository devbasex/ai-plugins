## 目的

- リリース後テストを何度回しても、利用者の Claude Code と Codex に導入済みのプラグインの版と取得元の登録が、利用者の操作なしに変わらない状態にする（上位の原則「人を守る」、C6 の趣旨）
- 万一変わったときは、その場で人が知り、戻すかどうかを決められる状態にする

## 前提

- 前提 1: 「利用者の設定ディレクトリ」は、Claude Code の設定ディレクトリ（環境変数 `CLAUDE_CONFIG_DIR`、無ければ `~/.claude`）と Codex の設定ディレクトリ（`CODEX_HOME`、無ければ `~/.codex`）を指す。この 2 つの中の導入済みのプラグインの記録と取得元の登録を守る対象にする
- 前提 2: 2026-11-02 の事象で環境変数が効かなかった理由は未確認である。記録（ https://github.com/devbasex/ai-plugins/pull/2395#issuecomment-6570809748 ）には worker が付けた変数の名前が無い。この環境では `CLAUDE_CONFIG_DIR=/home/ubuntu/.claude/ndf/accounts/team` が設定されており（2026-11-02 に `echo $CLAUDE_CONFIG_DIR` で確かめた）、`HOME` だけを差し替えても Claude Code の設定ディレクトリは変わらない、という推定に留まる。この要求は理由に依らず、手で導入しないこと（受け入れ条件 1〜3）と、変わったら検出すること（受け入れ条件 4・5）で守る
- 前提 3: 変わったことの検出は、導入した後に知らせる仕組みであり、導入を防ぐ仕組みではない。防ぐのは手順書と起動指示（受け入れ条件 1・2）である
- 前提 4: `verify-install` が隔離した設定ディレクトリで導入する振る舞い（`isolated_env` と `env -i`）は今のまま正しい。この要求では変えない

## 対象範囲

含む:
- リリース後テストの手順書（`release-verification` の Skill）で、導入の確かめを `verify-install` に限り、利用者の設定ディレクトリでの導入の操作を禁じること
- まとめのプランのリリース後テストのステップ（`release-verify`）の、worker への起動指示に同じことを書くこと
- 利用者の設定ディレクトリへの導入が要る受け入れ条件に当たったときの、worker の振る舞い（導入せずに保留とし、人へ戻す）
- リリース後テストのステップの前後で、利用者の設定ディレクトリの導入済みのプラグインと取得元の登録を比べ、変わっていたら人へ戻す検査
- `verify-install` が比べる「利用者の環境」に、利用者の設定ディレクトリの導入済みのプラグインと取得元の登録を加えること

含まない:
- 2026-11-02 に 10.27.10 へ上がった、利用者の設定ディレクトリの ndf を 10.27.7 へ戻すこと（リリースした版と同じであり、戻すかは利用者が決める）
- 別の開発ループが版のディレクトリを名指しで使い、そのディレクトリが消えると止まる問題（課題の本文の「何を見つけたか」の 2 点目。別の課題で扱う）
- `release` の手順書にある、隔離した設定ディレクトリで取得の経路を確かめる手順（`release/references/form-package-plugin.md` の「隔離した設定ディレクトリで取得の経路を確かめる」）の見直し。`CLAUDE_CONFIG_DIR` と `CODEX_HOME` を差し替えており、リリース後テストの工程ではない
- リリース後テスト以外の工程（実装・完了判定など）での導入の操作の禁止
- 利用者の設定ディレクトリを守るための権限の仕組み（hook で `claude plugin install` を拒否するなど）

## 受け入れ条件

手順書と起動指示:
- [ ] 1. `release-verification` の Skill の手順に、導入の確かめは `verify-install` だけで行い、利用者の設定ディレクトリで導入の操作を打たないことが書かれている。隔離のつもりで環境変数を付けて手で導入することも、この禁止に含まれる
- [ ] 2. まとめのプランの `release-verify` のステップを生成すると、worker への起動指示に、受け入れ条件 1 と同じ禁止と、`release-verification` の Skill の該当の節への参照が入る
- [ ] 3. 受け入れ条件の確認に利用者の設定ディレクトリへの導入が要るとき、worker は導入の操作を打たず、記録の表のその行を「保留（理由: 利用者の設定ディレクトリへの導入が要る）」とし、作業の報告を「判断が要る」で返す。このことが手順書と起動指示に書かれている

検出:
- [ ] 4. `release-verify` のステップの前後で、利用者の設定ディレクトリの導入済みのプラグインの記録と取得元の登録（Claude Code と Codex の両方）を比べる。変わっていなければステップは今と同じく次（振り返り）へ進む。変わっていれば次へ進まず、変わった項目（プラグインの名前か取得元の名前）と前後の値を結果に載せて人へ戻す。控えが取れなかったときも人へ戻す（テストで、一時ディレクトリの設定ディレクトリを書き換えて確かめる）
- [ ] 5. `verify-install` の結果の「利用者の環境が変わっていない」（`metrics.user_env_unchanged`）が、利用者の設定ディレクトリの導入済みのプラグインの記録と取得元の登録も比べる。導入の途中でそれが変わると `user_env_unchanged` が false になり、`status` は `ok` にならず、変わった項目が `items` に `kind: user_env` で載る（テストで確かめる）

退行しない:
- [ ] 6. 利用者の設定ディレクトリが変わらない場合、`verify-install` の結果の形・終了コード・`status` は今と同じである。既存のテスト（`test_step_scripts.py` などの `verify-install` を扱うテスト）が書き換えずに通る
- [ ] 7. NDF のテスト（`uv run --frozen --project . --all-extras pytest plugins/ndf/scripts/tests -q -n 4`）とチェック（`python3 scripts/check-skill-frontmatter.py`・`claude plugin validate .`）が通る

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| セキュリティ | 利用者の設定ディレクトリは読むだけで、書かない。比べるのはプラグインの名前・版・取得元の名前と場所だけで、認証情報（Codex の `auth.json` など）を読まず、結果へも載せない |
