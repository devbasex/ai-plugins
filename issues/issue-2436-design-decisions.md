# 並列開発の設計の決定（#2436）

設計文書 [issue-2436-design.md](issue-2436-design.md) の決定の記録を分けたファイル。

## 決定の記録

### 決定 1: 計画と起動の受け皿を既存の手順へ寄せるため、新しい Skill を作らず `issue-plan-strategy` と `development-workflow` の `--parallel` で受ける

並列の計画を作る手順は、分割と並行の手順である。`parallel-work.md` の境界では `issue-plan-strategy` の担当に当たる。起動は `development-workflow` の `--loop` と同じ形の引数で受け、判定の手順へ進まずに専用の参照へ進む。利用者が覚えるエントリポイントは今の 2 つのまま増えない。

新しい Skill にする形は採らない。計画と起動の手順が既存の 2 つの Skill の担当と重なり、同じ役割の手順が 2 か所に分かれるためである。

根拠: Value 6 / Value 2（MVV 版 4）

### 決定 2: 11-02 の配布の衝突を繰り返さないため、オーガナイザーを置き、起動の後も残して本番の配布を 1 本にまとめる

レーンごとに本番を出すと、先に出したレーンが `develop` にある他のレーンの変更も出す。調整する役が無ければ衝突は再発する。オーガナイザーは依頼を受けて、1 回の承認ゲート 2 と 1 本の本番の配布にまとめる。承認する人は 1 度に全レーンの内訳を見て決められる。

計画の手順が `ndf-spawn` のブロックを並べて出すだけの形は、起動は楽になるが配布の衝突を防げないため採らない。

根拠: Mission / Vision（MVV 版 4）

### 決定 3: 機械が検査でき、ループの記録と同じ扱いにするため、並列の計画の正本を `plan.json`（pydantic のモデル）にし、`plan.md` を描画にする

検査（I1〜I4）と起動はスクリプトが行い、表の Markdown を解析するより JSON を読む方が誤りが少ない。形は pydantic のモデル `ParallelPlan` が持ち、I1〜I3 は検証の誤りの種類で返す。循環は標準の `graphlib.TopologicalSorter` の `CycleError` で見つける。どちらも依存にあるもので、検査の手書きの分岐を持たない。人が読む形は `plan.md` として描画し、書き換えるたびに作り直す。`.ndf/loop/<名>/loop.json` と `laps.md` の組と同じ形で、利用者は同じ読み方で済む。レーンに共通の決まりは `plan.json` の `rules` の 1 か所に置き、引継ぎ文書へ写さない。

Markdown の表を正本にする形は、検査のたびに表の解析が要り、表の形の崩れが検査の誤りとして現れるため採らない。JSON Schema（`jsonschema`）で形を書く形は、レーン名の重なりと依存先の照合を schema の外に書くことになり、検査が 2 か所に分かれるため採らない。

根拠: Value 4 / Value 7（MVV 版 4）

### 決定 4: 統括役の作業ディレクトリの読み方に揃えるため、オーガナイザーの印を作業ディレクトリの役割のファイルで持つ

統括役は作業ディレクトリの今のファイル（`relay.lock`・`question`・`name`）だけを読んで数える（#2346 の I5）。役割も同じ置き場に `relay.py role` が書き、`live()` が読む。オーガナイザーは名前の無い前景のラッパー（統括役を兼ねるもの）で動くことが多い。このラッパーは登録簿（名前つきのラッパーの一覧）に載らない。外すのは印を持つ動いているラッパーのうち 1 本だけにし、印を置けば上限を越えられる経路を 1 本に限る（I13）。

環境変数で持つ形は、別のプロセス（統括役）から読めないため採らない。登録簿の役割で持つ形は、名前の無い前景のラッパーを表せないため採らない。

根拠: Value 6（MVV 版 4）

### 決定 5: レーンの最初の入力を変えずに済ませるため、レーンかどうかをラッパーの名前と動いている計画の照合で決める

統括役が起動するラッパーは `NDF_RELAY_NAME` にレーン名を持つ。その環境は、レーンの conductor とプランのステップへ受け継がれる。耐久ワークフロー `parallel-<計画名>` が終わっていない（`PENDING`）計画のレーンにその名前があればレーンとし、無ければ今の振る舞いのまま（I12）。状態は `durable.status_of` で外から読み、DBOS を起動しない。区間を切り替えても名前は変わらないため、再開の経路に引数を足さずに済む。判定はプランを組む時点に 1 度だけ行い、組んだプランに計画名を書く。

`--loop` や `#<課題>` に並列の計画を示す引数を足す形は採らない。ループの記録・再開のコマンド・スプリントの状態の 3 か所へ、引数を引き継ぐ変更が要るためである。

根拠: Value 6 / Value 5（MVV 版 4）

### 決定 6: レーンの工程を変えずに配布だけを差し替えるため、本番のステージを組む 1 つの関数でだけ配布の依頼のプランへ置き換える

本番のステージは `supervise_lib/sprint.py` の 4 か所（`fast`・`auto`・最終の検査の後・通常）で組まれる。4 か所が同じ関数を通り、その関数がレーンのときだけ配布の依頼のプランを返す。依頼のプランは `parallel-request` と `parallel-await` の 2 つの run のステップを持つ。`parallel-request` は、自分の Pull Request がすでに `main` にあれば依頼を送らずに `released` で進める（I15）。差し戻しは、承認ゲートを返す終了コード（10）で返す。ループはこれを今の `gate2_returned` の経路で扱い、新しい止まり方を足さない。

ループの側（`sprint_loop`）で本番のステージを外す形は、ループでないスプリントのレーンに効かないため採らない。

根拠: Value 6（MVV 版 4）

### 決定 7: 承認ゲートを増やさないため、まとめた配布の承認は今の本番のプランの承認ゲート 2 をそのまま使う

まとめた配布の本番のプランは、今のスプリントと同じ `plan_mvv_release` で作る。出す版の Pull Request には、提示のプランが範囲から求めた Pull Request を渡す（決定 13）。`pace: auto` なら MVV 判定が、それ以外なら利用者が、今と同じ承認ゲート 2 で範囲を 1 回承認する。出し直しは同じ承認ゲート 2 の提示のやり直しで、新しい承認ゲートではない（決定 14）。版は耐久ステップが配布を組む時点の `develop` の開発版の版数から決め、依頼はレーンの希望の版を持たない。

依頼ごとに承認ゲート 2 を求める形は、範囲に入った他のレーンの変更も出るため、依頼の数と承認の対象が一致せず採らない。

根拠: Value 2（MVV 版 4）

### 決定 8: 統括役を並列の計画から独立させるため、計画名での停止を `relay.py` ではなく `parallel.py stop` に置く

統括役はリポジトリをまたいで動くラッパーの層で、並列の計画はリポジトリのメインディレクトリにある。`parallel.py stop <計画名>` が計画のレーン名を読み、レーンごとに今の `relay.py stop <名前>` を打つ。統括役が知る語は役割の印だけに留まる。要求の「影響」に挙げた `relay.py` の計画名の指定は、この形で受け入れ条件 8 を満たす。

`relay.py stop --plan <計画名>` を足す形は採らない。統括役がリポジトリの置き場を探す処理を持つことになり、2 つのコンテキストの境界が崩れるためである。

根拠: Value 6（MVV 版 4）

### 決定 9: 計画の大きさを起動の前に確かめられる形にするため、レーンの数の上限を `NDF_RELAY_MAX_NAMED` から読み、依存のあるレーンも数える

レーンの数の上限は統括役が実際に断る値と同じ `NDF_RELAY_MAX_NAMED` から読み、別の設定を持たない。依存のあるレーンは同時には動かないが、検査は計画の全レーンを数える。同時に動く本数を依存から求める形は、どのレーンがいつ止まるかに依って値が変わり、起動の前に確かめられないため採らない。上限を越える計画は、利用者が `NDF_RELAY_MAX_NAMED` を上げるか計画を分ける。

根拠: Value 3 / Value 5（MVV 版 4）

### 決定 10: オーガナイザーの手順を記録から決まる 1 手に絞るため、進行を耐久ワークフロー 1 本にし、AI は承認ゲート 2 の提示だけを担う

起動・観測・配布を組む・答えを返す・終わりの判定は、耐久ワークフロー `parallel-<計画名>` が耐久ステップとメッセージで行う。オーガナイザーの conductor は `run` と `wait` を背景で打ち、返った 1 手（知らせる・配布を流す・承認を問う・終える）を打つだけにする。プロセスが落ちても打ち直した `run` が記録から続け、記録のある耐久ステップ（レーンの起動）は流し直さず、答えのイベントは同じ値を返す（I7・I10）。止まっている間に届いた依頼は SQLite のメッセージとして残る。オーガナイザーのための引継ぎ文書の名を新しく作らず、再開のコマンドは起動と同じ 1 行にする。

状態ファイル（`state.json`）・依頼と答えのファイル（`requests/`・`results/`）・停止の印・冪等の 1 手（`tick`）・ファイルを問い合わせる待ちを自分で書く形は採らない。打ち直しで続く性質・依頼の取りこぼしの防止・待ちを、依存にある DBOS がすでに持っているためである（決定 12）。オーガナイザーの conductor が状態を判断して起動と配布を決める形は、切り替えのたびに判断の材料を読み直す費用がかかり、判断が揺れるため採らない。

根拠: Value 4 / Value 6（MVV 版 4）

### 決定 11: ラッパーの外では配布をまとめずに今の振る舞いへ戻すため、手で起動した計画では耐久ワークフローを始めない

ラッパーの外・tmux が無いときは、オーガナイザーが動き続けられず、依頼に答える役が居ない。`run` はレーンごとの手で起動する 1 行を示して、耐久ワークフローを始めずに `manual` で終える。耐久ワークフローの無い計画はレーンの判定（I12）に当たらないため、手で起動したレーンは今どおり自分で本番を出す。

手で起動したときも依頼を送らせる形は、答える役が居ないためレーンが待ち続けるので採らない。

根拠: Value 2（MVV 版 4）

### 決定 12: 自分で書く部品を減らすため、並列の進行を DBOS の耐久ワークフローとメッセージで作り、検査を pydantic と graphlib で行う

並列の進行に要るのは、状態を残すこと・別のプロセス（レーン）から依頼を受けて答えを返すこと・待つこと・落ちた後の打ち直しで続けることである。DBOS Transact 3.1.0 は依存（グループ `durable`）にあり、#1142 の包み `lib/durable.py` が起動・実行の鍵・止まりと続き（`pause`・`resume`・`wait`・`exit_leaving_pending`）を持つ。2026-11-02 の試行で、1 つのプロセスの耐久ワークフローが `recv` で待つメッセージを、別のプロセス 2 本が `DBOSClient` で SQLite へ送り、`get_event` で答えを読めた（サーバー無し）。包みには外のプロセスから送る・読む関数が無いため、`durable.py` に `DBOSClient` の関数を足す。DBOS を import するのは今どおり `durable.py` だけである（#1142 の I16）。

#1142 の I17（1 つの SQLite を開くプロセスは同時に 1 つ）は、DBOS を起動して耐久ワークフローを回復・実行するプロセスに限る。`DBOSClient` は耐久ワークフローを流さず、送る・読むだけで、回復が混ざる理由（決定 26 の耐久キューの取り出し）に当たらない。複数のプロセスが書くときのロックの待ちは未確認として残す。

| 候補 | 何に向くか | 採否と理由 |
| --- | --- | --- |
| DBOS Transact 3.1.0（`durable.py`） | 長く動く耐久ワークフロー・プロセスをまたぐメッセージとイベント・SQLite でサーバー無し | **採る。** 依存にあり、包みと試行がある |
| pydantic 2.13.5（グループ `schema`） | JSON の形の検証と誤りの種類 | **採る。** 依存にあり、`project-decl.py` などに前例がある |
| `graphlib.TopologicalSorter`（標準ライブラリ） | 依存の順序と循環の検出 | **採る。** 依存を足さない |
| Optuna | 短く独立した試行を共有のストレージと study 名で複数の worker が取り合う | 採らない。共有のストレージと名前で合流する形（耐久の記録と計画名）は借りる。試行の間の依存・配布のまとめ・対話のセッションを扱わない |
| Hydra の multirun と joblib / submitit の launcher、Ray Tune | 設定の組み合わせごとのジョブを並べて流す | 採らない。Optuna と同じ理由 |
| scipy・pyDOE | 実験の条件の組み合わせを作る | 採らない。条件を作るもので、実行を制御しない |
| doit・Snakemake・Luigi・pipefunc | バッチの依存グラフ（DAG）を流す | 採らない。レーンの依存は「先のレーンが止まってから起動」だけで、ステージの直列は `supervise.py queue` が持つ。長く動いて人の承認を待つ流れに向かない |
| Prefect・Airflow | サーバーを持つワークフローの基盤 | 採らない。上の理由に加え、サーバーが要る |
| tmuxp・libtmux | tmux のセッションの起動 | 採らない。起動には合うが、`relay.py` が専用のソケットで tmux を包み済みで、範囲は #2346 |
| GitHub の merge queue | ベースブランチへのマージの直列化 | 採らない。`develop` へのマージを直列にするもので、`develop` → `main` の本番の配布をまとめない |

根拠: Value 4 / Value 6（MVV 版 4）

### 決定 13: レーンの変更はすでに `develop` にあるため、配布の中身を依頼の集合ではなく承認資料を作る時点の `develop` のコミットで決める

本番の配布は `develop` の先端を `main` へ出す。依頼を送った時点で、そのレーンの変更も他のレーンの変更も `develop` に入っている。そのため、依頼の集合で中身を決めても、実際に出る中身と一致しない（Pull Request 2420 の件）。中身は提示のプランが承認資料を作る時点の `origin/develop` のコミット（`main..<SHA>`）で決め、範囲に入るレーンを依頼済みかどうかの印つきで承認資料に載せる。範囲に入ったレーンには依頼の有無によらず結果を返し、後から依頼のステップに来たレーンは出し直さずに進む（I15）。依頼は「配布を始めてほしい」という合図で、届いた時点で配布が流れていなければ他のレーンを待たずに直ちに組む（I9）。配布は 1 本ずつ直列で、流れている間に `develop` へ入った変更と届いた依頼は、今の配布の直後に組む次の配布になる。

本番のプランへ渡す Pull Request は、今の approval-facts が範囲から求める「含む PR」（#1274）を `present` が `work/prs.txt` へ書き、差し込み `{queue_prs:<計画名>}` で渡す。本番のプランの changelog・notes・後片付けのステップは `--prs` を受ける作りで、範囲から機械で求めた番号を渡せば今のステップのまま使える。SHA と範囲のレーンの一覧を本番のプランへ直接渡す形は、これらのステップの引数をすべて変えることになるため採らない。

`develop` → `main` をやめ、レーンのブランチを個別に `main` へ出す形は採らない。スプリントのブランチは `base-sync` で他のレーンの変更を含み、切り分けられない。`main` 宛は `develop` からだけという方針（`scripts/check-pr-base.sh`）と 2 つのチャネルの前提を崩し、`main` と `develop` が分かれる。

今の本番のプランは `develop` の先端だけを出し、承認したコミットの後に配布の外のコミットが入ると承認ゲート（10）で止まる（#815）。確定したコミットから `main` へのマージまでに `develop` が進んだときの扱いは、設計文書の「未確認のまま残ること」の 1 行目に 3 つの道を挙げ、判断を待つ。

根拠: Mission / Value 2（MVV 版 4）

### 決定 14: 承認待ちの間の `develop` の進みは 1 回だけ出し直す

人の答え待ちの実測は 10 分〜40 時間（`.ndf/loop/*/loop.json` の `waiting`）で、本番のプランの所要は 855〜1,406 秒（`.ndf/loop/l20261031/lap-2`・`lap-3` の done）である。答え待ちが本番のプランより 1 桁以上長いため、待つ間に他のレーンのマージが `develop` へ入る見込みは高い。出し直さない形では、そのレーンは今の配布が終わった後の次の配布で、2 回目の人の答え待ちを負う。

承認の答えを受けた時点で `origin/develop` の先端を 1 度だけ比べる。同じならそのコミットで確定する。進んでいれば、今の承認資料の生成を新しいコミットで呼び直し、加わった範囲（レーンと Pull Request）を添えて同じ承認ゲート 2 を 1 回だけ出し直す。選択肢は「新しい範囲で出す」「最初の範囲だけ出す」「差し戻す」である。出し直した後の進みは次の配布へ回す。新しい部品は作らず、比べるのは 1 つの関数、資料は今の生成の呼び直し、出し直しはオーガナイザーの手順の 1 段である。`pace: auto`・`fast` で MVV 判定が通すときは答え待ちが無く、比べない。

| 比べた形 | 採否と理由 |
| --- | --- |
| 出し直さない | 採らない。答え待ちの間にマージしたレーンが、次の配布で 2 回目の答え待ちを負う |
| 回数の上限なしで出し直す | 採らない。答え待ちの間に毎回 `develop` が進むと、出し直しが続いて配布が始まらない |
| 承認のときに次の範囲を続けて承認させる | 採らない。まだ資料の無い範囲を承認することになり、承認したものと出すものの一致（I14）が崩れる |
| 1 回だけ出し直す | **採る。** 答え待ちを 1 回で済ませる見込みが高く、連鎖しない |

根拠: Value 2 / Value 4（MVV 版 4）
