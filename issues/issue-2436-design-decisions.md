# 並列開発の設計の決定（#2436）

設計文書 [issue-2436-design.md](issue-2436-design.md) の決定の記録を分けたファイル。

## 決定の記録

### 決定 1: 計画と起動の受け皿を既存の手順へ寄せるため、新しい Skill を作らず `issue-plan-strategy` と `development-workflow` の `--parallel` で受ける

並列の計画を作る手順は、分割と並行の手順である。`parallel-work.md` の境界では `issue-plan-strategy` の担当に当たる。起動は `development-workflow` の `--loop` と同じ形の引数で受け、判定の手順へ進まずに専用の参照へ進む。利用者が覚えるエントリポイントは今の 2 つのまま増えない。

新しい Skill にする形は採らない。計画と起動の手順が既存の 2 つの Skill の担当と重なり、同じ役割の手順が 2 か所に分かれるためである。

根拠: Value 6 / Value 2（MVV 版 4）

### 決定 2: 11-02 の配布の衝突を繰り返さないため、オーガナイザーを置き、起動の後も残して本番の配布を 1 本にまとめる

レーンごとに本番を出すと、先に出したレーンが `develop` にある他のレーンの変更も出す。調整する役が無ければ衝突は再発する。オーガナイザーは依頼を受けて、1 回の承認ゲート 2 と 1 本の本番の配布にまとめる。承認する人は 1 度に全レーンの内訳を見て決められる。

計画の手順が `ndf-spawn` のブロックを並べて出すだけの形は、起動は楽になるが配布の衝突を防げないため採らない。

根拠: Mission / Vision（MVV 版 4）

### 決定 3: 機械が検査でき、ループの記録と同じ扱いにするため、並列の計画の正本を `plan.json` にし、`plan.md` を描画にする

検査（I1〜I4）と起動はスクリプトが行い、表の Markdown を解析するより JSON を読む方が誤りが少ない。人が読む形は `plan.md` として描画し、書き換えるたびに作り直す。`.ndf/loop/<名>/loop.json` と `laps.md` の組と同じ形で、利用者は同じ読み方で済む。レーンに共通の決まりは `plan.json` の `rules` の 1 か所に置き、引継ぎ文書へ写さない。

Markdown の表を正本にする形は、検査のたびに表の解析が要り、表の形の崩れが検査の誤りとして現れるため採らない。

根拠: Value 4 / Value 7（MVV 版 4）

### 決定 4: 統括役の作業ディレクトリの読み方に揃えるため、オーガナイザーの印を作業ディレクトリの役割のファイルで持つ

統括役は作業ディレクトリの今のファイル（`relay.lock`・`question`・`name`）だけを読んで数える（#2346 の I5）。役割も同じ置き場に `relay.py role` が書き、`live()` が読む。オーガナイザーは名前の無い前景のラッパー（統括役を兼ねるもの）で動くことが多い。このラッパーは登録簿（名前つきのラッパーの一覧）に載らない。外すのは印を持つ動いているラッパーのうち 1 本だけにし、印を置けば上限を越えられる経路を 1 本に限る（I13）。

環境変数で持つ形は、別のプロセス（統括役）から読めないため採らない。登録簿の役割で持つ形は、名前の無い前景のラッパーを表せないため採らない。

根拠: Value 6（MVV 版 4）

### 決定 5: レーンの最初の入力を変えずに済ませるため、レーンかどうかをラッパーの名前と動いている計画の照合で決める

統括役が起動するラッパーは `NDF_RELAY_NAME` にレーン名を持つ。その環境は、レーンの conductor とプランのステップへ受け継がれる。`state.json` が `running` の計画のレーンにその名前があればレーンとし、無ければ今の振る舞いのまま（I12）。区間を切り替えても名前は変わらないため、再開の経路に引数を足さずに済む。判定はプランを組む時点に 1 度だけ行い、組んだプランに計画名を書く。

`--loop` や `#<課題>` に並列の計画を示す引数を足す形は採らない。ループの記録・再開のコマンド・スプリントの状態の 3 か所へ、引数を引き継ぐ変更が要るためである。

根拠: Value 6 / Value 5（MVV 版 4）

### 決定 6: レーンの工程を変えずに配布だけを差し替えるため、本番のステージを組む 1 つの関数でだけ配布の依頼のプランへ置き換える

本番のステージは `supervise_lib/sprint.py` の 4 か所（`fast`・`auto`・最終の検査の後・通常）で組まれる。4 か所が同じ関数を通り、その関数がレーンのときだけ配布の依頼のプランを返す。依頼のプランは `parallel-request` と `parallel-await` の 2 つの run のステップを持つ。差し戻しは、承認ゲートを返す終了コード（10）で返す。ループはこれを今の `gate2_returned` の経路で扱い、新しい止まり方を足さない。

ループの側（`sprint_loop`）で本番のステージを外す形は、ループでないスプリントのレーンに効かないため採らない。

根拠: Value 6（MVV 版 4）

### 決定 7: 承認ゲートを増やさないため、まとめた配布の承認は今の本番のプランの承認ゲート 2 をそのまま使う

まとめた配布の本番のプランは、今のスプリントと同じ `plan_mvv_release` で作る。出す版の Pull Request には、依頼の Pull Request の和を渡す。`pace: auto` なら MVV 判定が、それ以外なら利用者が、今と同じ 1 回の承認ゲート 2 で決める。版は流す時点に決め（#2164）、依頼はレーンの希望の版を持たない。承認ゲート 2 を求めた後に届いた依頼は次の配布へ回す（I9。要求の前提 5）。

依頼ごとに承認ゲート 2 を求める形は、承認の回数がレーンの数だけ増えるため採らない。

根拠: Value 2（MVV 版 4）

### 決定 8: 統括役を並列の計画から独立させるため、計画名での停止を `relay.py` ではなく `parallel.py stop` に置く

統括役はリポジトリをまたいで動くラッパーの層で、並列の計画はリポジトリのメインディレクトリにある。`parallel.py stop <計画名>` が計画のレーン名を読み、レーンごとに今の `relay.py stop <名前>` を打つ。統括役が知る語は役割の印だけに留まる。要求の「影響」に挙げた `relay.py` の計画名の指定は、この形で受け入れ条件 8 を満たす。

`relay.py stop --plan <計画名>` を足す形は採らない。統括役がリポジトリの置き場を探す処理を持つことになり、2 つのコンテキストの境界が崩れるためである。

根拠: Value 6（MVV 版 4）

### 決定 9: 計画の大きさを起動の前に確かめられる形にするため、レーンの数の上限を `NDF_RELAY_MAX_NAMED` から読み、依存のあるレーンも数える

レーンの数の上限は統括役が実際に断る値と同じ `NDF_RELAY_MAX_NAMED` から読み、別の設定を持たない。依存のあるレーンは同時には動かないが、検査は計画の全レーンを数える。同時に動く本数を依存から求める形は、どのレーンがいつ止まるかに依って値が変わり、起動の前に確かめられないため採らない。上限を越える計画は、利用者が `NDF_RELAY_MAX_NAMED` を上げるか計画を分ける。

根拠: Value 3 / Value 5（MVV 版 4）

### 決定 10: オーガナイザーの手順を記録から決まる 1 手に絞るため、`tick` を冪等にし、AI は承認ゲート 2 の提示だけを担う

起動・まとめ・終わりの判定は、`tick` が記録と `relay.py ls --json` から決める。オーガナイザーの conductor は、返った 1 手（待つ・配布を流す・終える）を打つだけにする。起動し直したオーガナイザーも同じ `tick` で続き、二重の起動と依頼の取りこぼしを記録の側で防ぐ（I7・I10）。オーガナイザーのための引継ぎ文書の名を新しく作らず、再開のコマンドは起動と同じ 1 行にする。

オーガナイザーの conductor が状態を判断して起動と配布を決める形は採らない。切り替えのたびに判断の材料を読み直す費用がかかり、判断が揺れるためである。

根拠: Value 4（MVV 版 4）

### 決定 11: ラッパーの外では配布をまとめずに今の振る舞いへ戻すため、手で起動した計画を `manual` にしてレーンと見なさない

ラッパーの外・tmux が無いときは、オーガナイザーが動き続けられず、依頼に答える役が居ない。`start` はレーンごとの手で起動する 1 行を示して、`manual` で終える。`manual` の計画はレーンの判定（I12）に当たらないため、手で起動したレーンは今どおり自分で本番を出す。

手で起動したときも依頼を置かせる形は、答える役が居ないためレーンが待ち続けるので採らない。

根拠: Value 2（MVV 版 4）
