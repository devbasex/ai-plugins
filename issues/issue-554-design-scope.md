# #554: 走査の範囲と、指摘が出たときに何をするか

設計は [issue-554-design.md](issue-554-design.md)、観点は [issue-554-design-criteria.md](issue-554-design-criteria.md)、
決定は [issue-554-design-decisions.md](issue-554-design-decisions.md) にある。この文書は 3 つを持つ。
**どこまでを見るか。指摘が出たときに何をするか。#743（Skill の陳腐化）との関係。**

## どこまでを見るか

**指示書は 3 つのスコープに置かれる。** 実行したランタイムから見えるものがすべて対象になりうる。

| スコープ | 位置の例 | 直せるか | 既定で走査するか |
| --- | --- | --- | --- |
| プロジェクト（根） | `CLAUDE.md` / `AGENTS.md` / `KIRO.md` | 直せる（git の管理下） | **する** |
| プロジェクト（配下） | `docs/AGENTS.md` のような入れ子 | 直せる（同上） | **する** |
| ユーザー | `~/.claude/CLAUDE.md` など、利用者の home | 直せる（git の管理下とは限らない） | しない（`--scope user` で足す） |
| プラグインの配布物 | 取得元から取った先の `CLAUDE.md` / `AGENTS.md` | **直しても次の取得で消える** | しない（`--scope plugins` で足す） |

**既定をプロジェクトに絞るのは、主な実行先が継続的統合だからである。** そこには利用者の home も
プラグインの取得先も無い。**手元で広げるときだけ `--scope` を足す**（`--scope project,user,plugins` の形で重ねる）。

**走査の対象と、追跡の条件はスコープで変わる。** プロジェクトは `git` が追跡するものだけを見る
（手元にだけある草稿を入れない）。ユーザーとプラグインは `git` の外にあるため、位置の一覧から集める。
**位置はランタイムごとに違う**ため、`--scope user` / `--scope plugins` を使うリポジトリは、
宣言の `scopes` へ見に行く位置を書く（既定は持たない。**書かなければそのスコープは走査されない**）。

## 指摘が出たときに何をするか

**扱いは、実行しているリポジトリと対象のスコープで決まる。** 分ける理由は**直したものが残るかどうか**である。
プラグインの配布物は取得元の更新で上書きされるため、その場で直しても次の取得で消える。

| 実行しているリポジトリ | 対象 | 扱い |
| --- | --- | --- |
| NDF の開発リポジトリ | すべて | **その場で直す** |
| それ以外 | プロジェクトスコープ | **その場で直す** |
| それ以外 | ユーザースコープ | **その場で直す** |
| それ以外 | NDF が配るもの | **課題を起票する**（直さない） |
| それ以外 | 他のプラグインが配るもの | **報告だけ**（版の更新を促す） |

**検査は扱いを判定して出力へ載せるだけで、直しも起票もしない。** 書き込みと外部への投稿を行うのは
呼び出し側（`release` の手順、または人）である。**検査が副作用を持たないことは、`--refresh` と同じ約束である**（決定 14）。
指摘の 1 行には `[直す]` / `[起票]` / `[報告]` の印が付く。

### 1. NDF の開発リポジトリかをどう判定するか

**名前を書き込まない。** fork でも移設でも外れない判定として、**実行しているスクリプトの実体が
`--root` の下にあるか**を見る。配布物の中のスクリプトが、その作業ツリーの中から実行されていれば、
そこは NDF の開発リポジトリである。

| 判定 | 意味 |
| --- | --- |
| スクリプトの実体（symlink を解決した後）が `--root` の下にある | NDF の開発リポジトリ |
| それ以外（取得先や別の場所から実行） | 利用者のリポジトリ |

**取得元の名前・リポジトリ名・リモートの URL は見ない。** どれも fork と移設で変わる。

### 2. 起票先と、書き込めないときの退避

**起票先は、対象を配っているリポジトリである。** NDF が配るものなら NDF のリポジトリへ立てる。
配布物は `plugin.json` の位置から取得元をたどれる。

**利用者がそこへ書き込めるとは限らない。** 権限が無いときは**起票の下書きを標準出力へ出す**
（題名・本文・宛先のリポジトリ）。**ファイルを書かない。** 退避先を勝手に作ると、次の実行で同じ下書きが増える。

### 3. その場で直すときの安全

| 対象の状態 | 直す前にすること |
| --- | --- |
| `git` の管理下にある | そのまま直す（戻す手段は履歴が持つ） |
| `git` の管理下にない（ユーザースコープに多い） | **直す前に控えを取る**（`<ファイル>.orig-<日時>`）。控えの位置を出力へ出す |

**直す内容を先に示す。** 直しは差分として提示し、**利用者が見てから適用する**。検査自身は直さない
（この節の冒頭のとおり、書き込むのは呼び出し側である）。

### 4. 同じ指摘を重ねて起票しない

**起票の前に、同じ対象・同じ観点の open な課題を探す。** 見つかればその番号を出力へ出し、立てない。
探せるように、**題名へ印を付ける**。

```text
[instructions] <観点の id> <対象のパス>
```

例: `[instructions] broken-import plugins/ndf/README.md`。**印は題名の先頭に置く**（検索で前方一致が効く）。

### 5. 報告だけのときに何を出すか

| 出すもの | なぜ |
| --- | --- |
| 対象のパスと、それを配っているプラグインの名前と版 | 利用者が「どれを更新すればよいか」を決められる |
| 観点の id と、その根拠の出典（名前と参照日） | 助言の出どころをたどれる |
| 取得元と、更新の手立て（取得元の更新のコマンド） | **報告だけで終わらせない** |

## #743（Skill の陳腐化）との関係

**#743 は Skill の陳腐化を扱う隣の課題で、この設計と同じ「調べ直して追随する」形を必要とする。**
**調べ直しの仕組みを 2 か所に分けない。**

| 層 | 置き場所 | #554（この課題） | #743 |
| --- | --- | --- | --- |
| 調べ直しの部品（取得・指紋の比較・一覧の提示・待ち） | `plugins/ndf/scripts/lib/`（共通） | **この課題で作る** | そのまま使う |
| 観点と出典のデータ | `plugins/ndf/scripts/data/instruction-criteria.json` | 指示書の観点を持つ | **別のファイル**（Skill の観点）を足す |
| 判定の手続き | 検査のスクリプト | 指示書の検査 | Skill の検査（`AUTHORING.md` と既存の検査の側） |
| 指摘が出たときの扱い | 上の表（直す / 起票 / 報告） | **この課題で決める** | 同じ表を使う |

**この課題では、共通の部品を `lib/` へ置くところまでを行う。** 部品が 1 つの呼び出し側しか持たない
状態で切り出すのは早すぎるように見えるが、**#743 が同じ引き金・同じ出典の持ち方を必要とすることが
分かっている**ため、置き場所だけ先に決める（切り出す単位は実装で決める）。

**この課題で Skill の観点は持たない。** 指示書に閉じる。#743 が合流するときに足すのは、観点のデータと
判定の手続きだけで、**引き金・出典の持ち方・扱いの表は共有する**。
