# #860 の決定の記録

設計の本体は [issue-860-design.md](issue-860-design.md) にある。ここには、複数の選択肢から選んだことと、その理由と、採らなかった案だけを置く。

## 決定 1: SKILL.md の観点の節を読めるよう、スクリプトを Skill の `scripts/` に `pr-review-steps.py` として置く

スクリプトは SKILL.md の `## 観点` の節を読んでプロンプトを組む（決定 6）。同じ Skill の下に置けば、隣の `../SKILL.md` を読むだけで済み、配布の経路（manifests と各ランタイムの組み立て）も Skill のディレクトリと一緒に動く。Skill 固有の手順を Skill の `scripts/` に `<Skill>-steps.py` で置く形は `skills/fix/scripts/fix-steps.py` に前例があり、`resolve.sh scripts pr-review` で解ける。

`plugins/ndf/scripts/pr-review-steps.py`（`pr-steps.py` の並び）は採らない。プラグインの根の `scripts/` から Skill の本文を読む向きの依存が生まれ、Skill を動かすと読めなくなる。

根拠: Value 5 / Value 6（MVV 版 2）

## 決定 2: 他の Skill の写しを後で置き換えられるよう、ベースブランチの実在の確認を `lib/repo.py` の `existing_base_branch` に足す

ベースブランチの解決の写しは `pr-review` のほかに 4 つの Skill（`merged` / `cherry-pick-pr` / `deploy` / `retrospective`）にある（#845）。確認をスクリプト側に置くと、4 つを置き換えるときに同じ確認がもう 1 つ生まれる。`repo.py` は「git だけで決める」層で、`git show-ref` と `git ls-remote` はその範囲に収まる。既存の `base_branch` は変えずに関数を足すため、今の呼び手には効かない。

`base_branch` そのものに実在の確認を入れる案は採らない。今の呼び手の `pr-steps.py` は PR の宛先の名前として使い、宛先が無ければ PR の作成の側で失敗が出る。確認を入れると、確認の要らない呼び手にも `git ls-remote` の通信と「無い」の扱いの変化が及ぶ。

根拠: Value 6（MVV 版 2）

## 決定 3: 仕様適合の指摘を機械で数えられるよう、指摘ファイルに段の鍵 `stage`（`spec` / `quality`）を足す

本来の判定の表は「仕様適合を満たさない指摘が 1 件以上なら `REQUEST_CHANGES`」を求める。分類（`category`）は本文の接頭辞に入る自由な文字列で、「仕様適合」と書くか「受け入れ条件」と書くかが揺れると数え漏れる。値が 2 つに決まった専用の鍵にすれば、読めない値を I3 として止められる。省いたときは `quality` とし、第 2 段の指摘で LLM が鍵を書き忘れても止まらない。

`severity` に `spec` を足す案は採らない。重要度は `/ndf:fix` が直すかを決める軸で、段とは別の軸である。混ぜると `/ndf:fix` の判定の表が変わる。

根拠: Value 8（MVV 版 2）

## 決定 4: 観点の中身を変えないため、外部 AI のプロンプトに `review_criteria.py reviewer` の節を入れない

`reviewer` の節は「重要度は `critical` か `major` だけを使う（`minor` / `nit` は使わない）」と定める。pr-review の観点は 4 段の重要度と、`minor` / `nit` だけなら `COMMENT` とする判定を持ち、節を入れると同じプロンプトの中で指示が食い違う。合わせるには pr-review の観点を変えることになり、要求の「含まない」（観点そのものの見直し）に当たる。ホストの LLM がレビューするときも同じ節は渡さないため、委譲の有無で基準が変わらない。

節を入れて pr-review の重要度を 2 段へ寄せる案は、この変更の範囲の外に置く。

根拠: Value 7 / 共通原則（判断の範囲は目の前の変更に限る）（MVV 版 2）

## 決定 5: 共通の部品の引数を変えないため、`review-post` へは `--round 0 --seat pr-review-<レビューする者>` を渡す

`review-post` は `--round` と `--seat` を必須で受け、総評の先頭行を `## 🤖 cross-review | round <R> | <席> | <判定>` で書く。単発のレビューにはラウンドが無いため 0 を渡し、席の名前でレビューする者が pr-review のものと分かるようにする。0 にすれば、先頭行からラウンドの最大を数える集計（`scripts/experimental/review-terms-count.py`）の値も上がらない。二度送らない照合はラウンドと席と入口の時刻で行われるため、同じ PR への pr-review と cross-review の投稿は混ざらない。

先頭行の `cross-review` の語を変える引数（見出しの書式）を `review-post` に足す案は採らない。要求の境界で「確認してから行う」に当たる共通の部品の引数の変更で、得られるのは見出しの語の違いだけである。

根拠: Value 1 / Value 6（MVV 版 2）

## 決定 6: 観点の写しを作らないため、プロンプトの観点はスクリプトが SKILL.md の `## 観点` の節を読んで組む

受け入れ条件は「SKILL.md に第 1 段・第 2 段の観点が残る」と「SKILL.md と別ファイルに同じ文が 2 つ無い」を同時に求める。SKILL.md を正本にし、スクリプトが節を見出しで切り出せば、写しは生まれない。節の切り出しは既存の `gh_sections.get_section` を使う（見出しの行が完全に一致する節を、同じ深さの次の見出しまで下位の節ごと返す）。今の見出し `## 観点は 2 段に分ける` は `## 観点` に改め、PR モードの手順の中にある重要度の表を `### 重要度` としてその下へ移して、1 回の切り出しで揃える。中身の文は変えない。

観点を `references/` の別ファイルへ移し SKILL.md から参照する案は採らない。観点が SKILL.md から消え、受け入れ条件の 1 つ目に反する。スクリプトの定数に持つ案は、SKILL.md と同じ文が 2 つになる。

根拠: Value 7 / Value 6（MVV 版 2）

## 決定 7: LLM とプロンプトの両方が同じ形の指摘ファイルを書くよう、指摘ファイルの書き方は文脈ファイルの節だけが持つ

ホストの LLM がレビューするときも、外部 AI がレビューするときも、`finish` が読むのは同じ指摘ファイルである。書き方を SKILL.md とプロンプトの 2 か所に置くと、片方だけが変わる（今の SKILL.md の「`--print-timeout` が実際に食い違っていた」と同じ形）。`collect` が文脈ファイルに書き方の節を書き、プロンプトはその文脈ファイルを含む。SKILL.md は「文脈ファイルの『指摘ファイルの書き方』に従って書く」とだけ書く。

根拠: Value 4 / Value 7（MVV 版 2）

## 決定 8: LLM のレビューを挟めるよう、部分命令を `collect` / `finish` / `delegate` の 3 つにする

ホストの LLM がレビューするときは、集める処理と判定・投稿の間に LLM の判断が入る。スクリプトは途中で LLM を待てないため、前後を 2 つの部分命令に分ける。外部 AI へ委譲するときは間にスクリプトだけが入るため、`delegate` が `collect` → `run` → `finish` を 1 回で行う。3 つは同じモジュールの関数を共有し、`delegate` だけの処理はプロンプトの組み立てと `run` の呼び出しに限る。

1 つの命令に「LLM のレビューを待つ」状態を持たせ、終了コードの判断待ち（20 番台）で返して呼び直す案は採らない。呼び直しのための状態のファイルが要り、2 回の呼び出しで済む流れより手順が増える。

根拠: Value 4（MVV 版 2）

## 決定 9: 外部 AI の結果を投稿の前に検査できるよう、指摘ファイルを読むだけにし、送る payload は別のファイルに書く

`review-post` は送れた先（`posted_to`）を payload のファイルへ書き戻す。指摘ファイルをそのまま payload にすると、レビューする者が書いたファイルを投稿する側が書き換え、再実行で前回の書き戻しを読む。`finish` は指摘ファイルを読み、仕様適合の箇条と本文の接頭辞を足した `payload.json` と、本来の判定の `result.json` を書く。

根拠: Value 6（MVV 版 2）

## 決定 10: 待ちの上限を 1 か所に保つため、上限は `external-ai.py run --phase review` の表の値を使い、`--timeout` だけを通す

`run` は工程 `review` の上限（`limits.PHASE_TIMEOUT`。1,200 秒）で監視し、越えると必ず終わる。環境変数 `MONITOR_TIMEOUT` と `MONITOR_TIMEOUT_<担当>` で利用者が延ばせる。pr-review に独自の上限を持たせると、延ばしたつもりの値が片方にしか効かない。`delegate` の `--timeout` は `run --timeout` へそのまま渡し、上限越えのテストで短い上限を渡す口にもなる。

根拠: Value 6 / Value 3（MVV 版 2）

## 決定 11: 起点が決まらないまま違う差分を出さないため、宣言が無く既定ブランチも決まらないときは止まる

今の SKILL.md は、宣言も origin の HEAD も `main` / `master` も無いときに `main` を仮に置き、続く `git fetch origin main` で失敗する。`existing_base_branch` が `None` と理由を返し、`collect` が 3 で止まれば、失敗の理由が「起点が決まらない」として出る。宣言のブランチが無いときに止まる今の振る舞い（I1）と同じ扱いにそろう。

根拠: Value 2（MVV 版 2）

## 決定 12: 引数の組を減らさないため、`--branch` でも委譲を受ける

引数の形 `[PR番号 | --branch] [codex|agy]` は `--branch codex` を許す。今の SKILL.md は委譲の手順を PR 前提でしか書いていないが、指摘ファイルを介する形ではモードの違いが文脈ファイルの中身と `finish` の出口（投稿か報告か）だけになる。PR モードに限る分岐を足すほうが、受ける組を黙って減らすことになる。

根拠: Value 5（MVV 版 2）

## 決定 13: 重複防止の材料を共通の部品の形のまま使うため、未解決のスレッドは位置（`path:line`）だけを渡す

`pr-info --with threads` が返すのはスレッドの ID・path・line で、本文を持たない。本文まで渡すには `gh_graphql` の問い合わせと `pr-info` の結果の形を変えることになり、要求の境界で「確認してから行う」に当たる（`cross-review` と `/ndf:fix` も同じ部品を使う）。要求の前提 2 は、重複防止の材料を未解決のスレッドに絞ることを決めている。位置だけでの重複防止が足りるかは「未確認のまま残ること」に置き、リリース後テストで見る。

根拠: Value 1 / Value 6（MVV 版 2）

## 決定 14: 「直前の PR」を一意に決めるため、PR 番号を省いたときは今のブランチの PR を対象にする

今の SKILL.md は既定を「直前の PR」とだけ書き、決め方を持たない。スクリプトにするには 1 つに決める必要がある。`gh pr view`（引数なし）と同じく、今のブランチを head とする開いた PR を対象にし、無ければ 3 で止まる。最後に作った PR を探す案は、他の人の PR や別の worktree の PR を拾う。

根拠: Value 2（MVV 版 2）
