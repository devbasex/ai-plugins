# #2707 の決定の記録

設計文書は [issue-2707-design.md](issue-2707-design.md) にある。

## 決定の記録

### 決定 1: 答えを待つ間も止まるよう、耐久ワークフローが今の一覧から停止の範囲を 1 周ごとに導く

オーガナイザーは `AskUserQuestion` の答えを待つ間に通知を読めないため、判定はセッションの外に置く。停止の範囲は問いの一覧と閾値の純粋な関数とし、耐久ワークフローの 1 周の終わりに導く。どの経路で問いが消えても同じ結果になる。#2649 の問いの取り下げや #2647 の作り直しが入っても、数える処理は変わらない。

| 採らなかった形 | 理由 |
| --- | --- |
| オーガナイザーが `wait` の結果で判定する | 答えを待つ間に判定できない |
| 受け付けと答えの処理で増減を数える | 問いを外す経路（答え・リリースの答え・一覧の失敗の解消）ごとに手を入れることになる |

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1 / STD3 / PRD1

根拠: Vision / Value 2 / Value 7（MVV 版 6）

### 決定 2: 区切りでレーンが読めるよう、止める指示を計画の置き場のファイルで届ける

耐久ワークフローは `answer-hold.json` を停止の範囲があるときだけ置き、レーンは自分の区切りで読む。読むのが区切りの時点の今の停止の範囲なので、区切りの前に解ければ止まらない（受け入れ条件 14）。ファイルなら DBOS を起動しないプロセスからも読め、耐久ワークフローが一時的に動いていなくても読める。

| 採らなかった形 | 理由 |
| --- | --- |
| `relay.py stop` で止める | 動いているプランを打ち切る |
| イベントで届ける | 読む側に記録を開く費用がかかり、ファイルに対して得るものが無い |
| ループの `.ndf/loop/<名>/stop` を置く | 再開の後も残る人の指示の置き場である。理由が `user_stop` になり、1 スプリントのレーンに無い |

- 作り方: 自前で作る・標準に倣う
- 比べた候補: LIB1 / PRD3

根拠: Value 3 / Value 5（MVV 版 6）

### 決定 3: 作りかけを残さないよう、区切りをループは周回の境、1 スプリントのレーンはプランの開始にする

ループのレーンは今の止まる条件の判定と同じ周回の境で止まる。保留の周回の処理より先に止まるよう、すぐ止まる条件へ入れる（受け入れ条件 24）。1 スプリントのレーンはステージの中で枠を待つプランもあるため、ステージの境でなくプランの開始（`Engine.prepare`）で読む。読むのはキューから流すプランだけで、1 か所でキューのプランの開始のすべてに効く。`supervise.py run` の単発の開始では読まない。`park` の続きは `queue --resume` であり、単発の実行には続きの形が無いためである。

| 採らなかった形 | 理由 |
| --- | --- |
| キューのステージの間で読む | 同じステージの枠待ちのプランが流れる |
| ループのレーンをプランの開始でも止める | 周回の途中で止まる理由が増える |

- 作り方: 標準に倣う
- 比べた候補: PRD2

根拠: Value 1 / Value 3（MVV 版 6）

### 決定 4: 長い停止でも費用を使わないよう、1 スプリントのレーンも自分のラッパーを止める

答えが届くまでの時間は決まらない。その場で待つと、会話が待ちの再実行のたびにトークンを使い、同時に動かせる数も占める。止める手順は `parallel.py park` が引継ぎ文書と再開の印を書くため、問いの保留と同じ形である。続きは `supervise.py queue --resume` になる。

キューの中で解けるまで待つ形は採らない。プロセスは軽いがセッションが残り、止めたレーンへ動かないレーンの問いも立つためである。

- 作り方: 自前で作る
- 比べた候補: PRD1

根拠: Value 3 / Value 5（MVV 版 6）

### 決定 5: 通知の取りこぼしで止まったままにならないよう、再開の印と停止の範囲を 1 周ごとに突き合わせる

レーンが区切りで再開の印を置き、耐久ワークフローが観測で印を読み、停止の範囲の外で止まっているレーンへ `relay.py restart` を実行する。解けた瞬間と印を置いた瞬間が前後しても、次の 1 周で再開される。動いて見えるだけでは印を消さない。止まる直前のレーンが後から止まっても再開の対象に残すためである。消すのは、印のあるまま止まったと観た後で動いたレーンだけにする。止まったという観測は印の `at` で控え、そのとき観た印 1 つにだけ効かせる。レーン名だけで控えると、再開の後の次の停止で置いた新しい印まで消すためである。人が止めたままにするレーンの印は、人が `parallel.py park --clear` で消す。消すのはファイルだけでは足りない。答えを受けたレーンは耐久ワークフローの `wake` と `revive` にも入っているため、`--clear` は `inbox` で耐久ワークフローへ知らせ、持ち主である耐久ワークフローが自分の状態を変える。`relay.py stop` はレーンが自分を止めるときにも使うため、人の停止と区別できない。再開の担い手を耐久ワークフローにするのは、オーガナイザーが次の `AskUserQuestion` を待つ間も戻すためである。停止の間に答えを受けた持ち主のレーンにも同じ印を置き、再開の経路を 1 つにする。

| 採らなかった形 | 理由 |
| --- | --- |
| レーンがメッセージで止まったことを送る | 一度に 1 件しか読まないため、計画の終わりの判定と前後して読み逃す |
| 解けた瞬間に 1 度だけ再開する | その直後に止まったレーンが起きない |

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD3 / LIB1

根拠: Vision / Value 2 / Value 5（MVV 版 6）

### 決定 6: プロジェクトごとに見直せるよう、閾値を `.ndf/pace.json` の節 `parallel.answer_limit` に置く

閾値は進め方の値で、計画ごとでなくプロジェクトの読む量に結び付く。節が無ければ 4 と 3 で動き、値ごとに検査して不正な値だけを既定へ戻し、警告を残す。`read_loop` と違って例外を上げないのは、閾値の誤りで計画を止めないためである（受け入れ条件 28）。

| 採らなかった形 | 理由 |
| --- | --- |
| 環境変数 | 宣言として残らない |
| 計画の `plan.json` | 計画を作るたびに書く必要がある |

根拠: Value 2 / Value 6（MVV 版 6）

### 決定 7: 動いている計画を止めないよう、観測の値で新旧を分け、`durable.patched` を使わない

閾値と再開の印は既存の耐久ステップ「観測」の結果へ載せる。古い記録の再生では値が無く、新しい処理は動かないため、記録の順が変わらない。実時間へ戻ると値が載り、動いている計画でも次の 1 周から働く。プランの開始の判定も既存の耐久ステップ `prepare` の中で読むため、呼び出しが増えない。

| 採らなかった形 | 理由 |
| --- | --- |
| 先頭で `patched` を呼ぶ | 更新の前に始まった計画で最後まで働かない |
| 判定のたびに `patched` を呼ぶ | 呼ぶたびに記録の行が増える（`dbos/_sys_db.py` の `patch` は記録の無い位置でマーカーを書く） |

根拠: Value 1 / Value 3（MVV 版 6）

### 決定 8: 後の通知で消えないよう、通知をイベント `answer-hold` に分け、変化の全件は履歴から返す

イベントはキーごとに上書きされる（LIB1）。`pause` に載せると別の通知で消える。専用のキーにしても次の変化で上書きされるため、イベントは最新の変化だけを持ち、`wait` が履歴（`answer-hold-log.jsonl`）から未出の変化をすべて返す。オーガナイザーは出した最後の番号を `--changes-after` で渡し、返った変化ごとに 1 行を出す。セッションが替わって番号を失ったときは、出した変化をもう一度出す（取りこぼす側へ倒さない）。

| 採らなかった形 | 理由 |
| --- | --- |
| イベントへ直近の決まった件数を載せる | オーガナイザーが `AskUserQuestion` の答えを待つ間に件数を超えた変化が失われる |
| イベントへ全件を載せる | 変化のたびに耐久の記録へ全件を書き直す |

根拠: Value 2 / Value 8（MVV 版 6）

### 決定 9: 読み取りの失敗でレーンを止めないよう、読めないファイルは止める指示なしと読む

読み取りが起きるのはレーン側の止める指示のファイルである。数える一覧は耐久ワークフローのメモリにあるため、読み取りの失敗が起きない。書き手は一時ファイルからの置き換えで書くため、途中の内容を読まない。

それでも読めないときは止めない。レーンに直前の判定の記憶は無く、止める側へ倒すと再開の対象が増えるためである。要求の未決 3 は「直前の判定を保つ」を候補としていた。停止の範囲の書き込みに失敗した 1 周は停止の範囲を進めず、次の 1 周で書き直す。

根拠: Value 3（MVV 版 6）

### 決定 10: 要求の候補どおりに数えるよう、レーンの数へ設計の承認を含め、MVV 判定で答えられる依頼も数える

要求の未決 1・2 は利用者が設計承認ゲートで決める項目で、候補を既定として設計した。答えが変わったときの変更は `decide` の種類の絞りの 1 か所で済む。

根拠: Value 2（MVV 版 6）
