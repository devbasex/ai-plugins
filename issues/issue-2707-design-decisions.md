# #2707 の決定の記録

設計文書は [issue-2707-design.md](issue-2707-design.md) にある。

## 決定の記録

### 決定 1: 答えを待つ間も止まるよう、耐久ワークフローが今の一覧から範囲を毎周導く

オーガナイザーは `AskUserQuestion` の答えを待つ間に知らせを読めないため、判定はセッションの外に置く。範囲は問いの一覧と閾値の純粋な関数とし、周の終わりに導く。どの経路で問いが消えても同じ結果になり、#2649 の問いの取り下げや #2647 の作り直しが入っても、数える処理は変わらない。

オーガナイザーが `wait` の結果で判定する形は、答えを待つ間に判定できないため採らない。受け付けと答えの処理で増減を数える形は、問いを外す経路（答え・リリースの答え・一覧の失敗の解消）ごとに手を入れることになるため採らない。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1 / STD3 / PRD1

根拠: Vision / Value 2 / Value 7（MVV 版 6）

### 決定 2: 区切りでレーンが読めるよう、止める指示を計画の置き場のファイルで届ける

耐久ワークフローは `answer-hold.json` を範囲があるときだけ置き、レーンは自分の区切りで読む。読むのが区切りの時点の今の範囲なので、区切りの前に解ければ止まらない（AC 14）。ファイルなら DBOS を起動しないプロセスからも読め、耐久ワークフローが一時的に動いていなくても読める。

`relay.py stop` で止める形は動いているプランを打ち切るため採らない。イベントで届ける形は読む側に記録を開く費用がかかり、ファイルに対して得るものが無いため採らない。ループの `.ndf/loop/<名>/stop` を置く形は、再開の後も残る人の指示の置き場で、理由が `user_stop` になり、1 スプリントのレーンに無いため採らない。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: LIB1 / PRD3

根拠: Value 3 / Value 5（MVV 版 6）

### 決定 3: 作りかけを残さないよう、区切りをループは周回の境、1 スプリントのレーンはプランの開始にする

ループのレーンは今の止まる条件の判定と同じ周回の境で止まる。保留の周回の処理より先に止まるよう、すぐ止まる条件へ入れる（AC 24）。1 スプリントのレーンはステージの中で枠を待つプランもあるため、ステージの境でなくプランの開始（`Engine.prepare`）で読む。1 か所で開始のすべてに効く。

キューのステージの間で読む形は、同じステージの枠待ちのプランが流れるため採らない。ループのレーンをプランの開始でも止める形は、周回の途中で止まる理由が増えるため採らない。

- 作り方: 標準に倣う
- 比べた候補: PRD2

根拠: Value 1 / Value 3（MVV 版 6）

### 決定 4: 長い停止でも費用を使わないよう、1 スプリントのレーンも自分のラッパーを止める

答えが届くまでの時間は決まらない。その場で待つと、会話が待ちの打ち直しのたびにトークンを使い、同時に動かせる数も占める。止める手順は `parallel.py park` が引継ぎ文書と印を書くため、問いの保留と同じ形で、続きは `supervise.py queue --resume` になる。

キューの中で解けるまで待つ形は、プロセスは軽いがセッションが残り、止めたレーンへ動かないレーンの問いも立つため採らない。

- 作り方: 自前で作る
- 比べた候補: PRD1

根拠: Value 3 / Value 5（MVV 版 6）

### 決定 5: 通知の取りこぼしで止まったままにならないよう、再開の印と範囲を毎周突き合わせる

レーンが区切りで印を置き、耐久ワークフローが観測で印を読み、範囲の外で止まっているレーンへ `relay.py restart` を打つ。解けた瞬間と印を置いた瞬間が前後しても、次の周で再開される。再開の担い手を耐久ワークフローにするのは、オーガナイザーが次の `AskUserQuestion` を待つ間も戻すためである。停止の間に答えを受けた持ち主にも同じ印を置き、再開の経路を 1 つにする。

レーンがメッセージで止まったことを送る形は、一度に 1 件しか読まないため、計画の終わりの判定と前後して印を読み逃す。解けた瞬間に 1 度だけ再開を打つ形は、その直後に止まったレーンが起きない。どちらも採らない。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD3 / LIB1

根拠: Vision / Value 2 / Value 5（MVV 版 6）

### 決定 6: プロジェクトごとに見直せるよう、閾値を `.ndf/pace.json` の節 `parallel.answer_limit` に置く

閾値は進め方の値で、計画ごとでなくプロジェクトの読む量に結び付く。節が無ければ 4 と 3 で動き、値ごとに検査して不正な値だけを既定へ戻し、警告を残す。`read_loop` と違って例外を上げないのは、閾値の誤りで計画を止めないためである（AC 28）。

環境変数は宣言として残らないため採らない。計画の `plan.json` は計画を作るたびに書く必要があるため採らない。

根拠: Value 2 / Value 6（MVV 版 6）

### 決定 7: 動いている計画を止めないよう、観測の値で新旧を分け、`durable.patched` を使わない

閾値と印は既存の耐久ステップ「観測」の結果へ載せる。古い記録の再生では値が無く、新しい処理は動かないため、記録の順が変わらない。実時間へ戻ると値が載り、動いている計画でも次の周から働く。プランの開始の判定も既存の耐久ステップ `prepare` の中で読むため、呼び出しが増えない。

先頭で `patched` を打つ形は、更新の前に始まった計画で最後まで働かないため採らない。判定のたびに `patched` を打つ形は、打つたびに記録の行が増えるため採らない（`dbos/_sys_db.py` の `patch` は記録の無い位置で印を書く）。

根拠: Value 1 / Value 3（MVV 版 6）

### 決定 8: 後の知らせで消えないよう、知らせをイベント `answer-hold` に分け、直近の変化を載せる

イベントはキーごとに上書きされる（LIB1）。`pause` に載せると別の知らせで消える。専用のキーにしても次の変化で上書きされるため、直近 8 件の変化を毎回載せ、オーガナイザーは未出の番号だけ 1 行を出す。

根拠: Value 2 / Value 8（MVV 版 6）

### 決定 9: 読み取りの失敗で作業を動かさないよう、読めないファイルは止める指示なしと読む

要求の未決 3 は「直前の判定を保つ」を候補としていた。数える一覧は耐久ワークフローのメモリにあるため読み取りの失敗が起きない。読み取りが起きるのはレーン側の止める指示のファイルで、書き手は一時ファイルからの置き換えで書くため、途中の内容を読まない。それでも読めないときは止めない。レーンに直前の判定の記憶は無く、止める側へ倒すと再開の対象が増えるためである。範囲の書き込みに失敗した周は範囲を進めず、次の周で書き直す。

根拠: Value 3（MVV 版 6）

### 決定 10: 要求の候補どおりに数えるよう、レーンの数へ設計の承認を含め、MVV 判定で答えられる依頼も数える

要求の未決 1・2 は利用者が設計承認ゲートで決める項目で、候補を既定として設計した。答えが変わったときの変更は `decide` の種類の絞りの 1 か所で済む。

根拠: Value 2（MVV 版 6）
