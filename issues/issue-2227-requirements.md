## 目的

- 自律で回す工程（プラン・supervisor・conductor）が、失敗・未収束・欠けた材料・未記録を成功と読んで先へ進まないようにする。承認ゲート 2 の承認資料へ、落ちた試行の値や「無し」が黙って載らないようにする
- 工程ごとの結果 JSON から、後で人と AI が「何を実行し、何を根拠にどう決め、何ができて何が欠けたか」を追えるようにする（振り返りと承認の判断の材料にする）

## 前提

- 前提 1: 「全ての工程」は、Skill の本文かプランのステップから呼ばれ、結果を読み手（LLM・`supervise.py`・承認資料の組み立て）が読む手順のスクリプトを指す。hook・statusline・利用者が手で打つだけの補助は含まない
- 前提 2: 実験版（`plugins/ndf/scripts/experimental/`）は対象に含まない。既定の振る舞いから参照されず、安定版へ移す時点で形式に合わせる（AGENTS.md の「安定版と実験版」）
- 前提 3: 対象のシェルのスクリプトは、前提 1 に当たるもの（例: `progress-record.sh`・`projects-sync.sh`・`pr-body-decisions.sh`）に限る。どれが当たるかの一覧は設計で決め、設計文書に載せる
- 前提 4: 結果 JSON を読むのは同じ版の `plugins/ndf` の中のコードと Skill の本文だけである。Factory（`factory/`）は結果 JSON を直接読まない（`factory/contracts` の `result` は進行のイベントの別の語彙で、この課題では変えない）
- 前提 5: 子の 7 件（#2143・#2079・#2129・#2157・#2183・#671・#1849）の個別の直しは、この課題の共通の形式と読む側の規則が入った後に、子の課題で行う。この課題が閉じる条件は、子の 7 件が閉じていることを含む（受け入れ条件 7）

## 対象範囲

含む:
- 結果 JSON の形式の正本（`plugins/ndf/scripts/lib/README.md` の「手順のスクリプトの結果」）と、それを確かめる `lib/step_result.py` の `validate_result` / `emit`
- `ok` を返してよい条件と、欠け・未達・未記録を返す形（状態の値・終了コード）
- 過程・判断・結果を結果 JSON に書く項目
- 読む側の共通の規則: 複数の試行から値を採る規則、置き場が無いことと材料が無いことの区別
- シェルのスクリプトが同じ形式の結果 JSON を出すための共通の手段
- 形式の変更に合わせた、`lib/README.md` 以外の文書（Skill の本文・references）からの参照の付け替え（形式を写さずに正本を指す）

含まない:
- 子の 7 件の個別の直し（子の課題で行う。前提 5）
- 判定の中身の誤り（#2067 のように、`status` の値ではなく判定の論理が誤っているもの）
- 既存の全スクリプトへの過程・判断の項目の書き足し（この課題では形式と共通の手段を定め、`ok` を誤って返す箇所を直すことを優先する。書き足しの範囲は未決 2）
- 実験版のスクリプト（前提 2）
- Factory の進行のイベントの語彙（前提 4）

## 用語

| 用語 | 意味 |
| --- | --- |
| 結果 JSON | 手順のスクリプトが返す 1 行の JSON。`status` で読む（既存の語） |
| 試行 | 同じステップを流し直したときの 1 回ごとの実行と、その結果 JSON。状態ディレクトリの `NN-<ステップ>.out` の 1 つが 1 試行に当たる |
| 欠けの残る結果 | 手順は終わったが、出すはずの材料・記録の一部が無いか、目標（収束など）に届かなかった結果 |
| 結果の置き場 | 読む側が結果 JSON や材料を探す場所（状態ディレクトリ・記録のファイル）。置き場が無いことと、置き場はあるが材料が 0 件であることを分けて扱う |

## 受け入れ条件

1. - [ ] `lib/README.md` の「手順のスクリプトの結果」が、結果 JSON の全ての項目と状態の値・終了コードの表を持ち、過程（何を実行したか）・判断（何を根拠にどう決めたか）・結果（何ができ、何が欠けたか）をどの項目に書くかを定める。Skill の本文と references は形式の表を写さず、この節を指す（`grep` で、`status` の値の表を持つ文書が `lib/README.md` の 1 か所だけであることを確かめる）
2. - [ ] `lib/README.md` が、`ok` を返してよいのは「手順が成功し、目標（収束など）に届き、欠けが無い」ときだけと定め、欠けの残る結果・未記録を返す状態と終了コードを定める
3. - [ ] 欠けの残る結果を表す項目（名前は設計で決める）を 1 件以上持つ結果 JSON を `status: ok` で `emit` すると → 標準出力へ何も出さず、標準エラーへ理由を出して終了コード 2 で終わる（`validate_result` が誤りとして返す）
4. - [ ] 同じステップの試行が複数ある状態ディレクトリから値を読む共通の関数が `lib` に 1 つあり、`status` が `ok` の試行のうち最も新しいものだけを採る。`ok` の試行が 1 つも無いとき → 落ちた試行の値を返さず、採れる試行が無いことを呼び出し側が区別できる形で返す。番号の最大の試行が `stopped` で、それより前の試行が `ok` のとき → 前の `ok` の試行の値を返す（単体テストで固定する）
5. - [ ] 読む側の共通の規則として、渡された置き場（ファイル・ディレクトリ）が存在しない・読めないとき → 材料が 0 件・「無し」とは返さず、`ok` 以外の状態で返す。置き場が存在し材料が 0 件のとき → 0 件であることを、置き場が無いときと別の値で返す（単体テストで両方を固定する）
6. - [ ] 前提 3 のシェルのスクリプトは、共通の手段を通して結果 JSON を 1 行出し、その出力は `validate_result` を通る。中で呼んだ `gh` が失敗したとき → `status` は `ok` でなく、`summary` か `items` に失敗の理由（`gh` の標準エラーの要旨）が入り、終了コードは 0 以外になる（偽の `gh` を `PATH` の先頭に置くテストで確かめる）
7. - [ ] 子の 7 件（#2143・#2079・#2129・#2157・#2183・#671・#1849）が、それぞれの受け入れ条件を満たして閉じている。各子の課題の再現の手順を流したとき、失敗・未収束・欠けた材料・未記録が `status: ok` で返らない（子の課題で確かめ、この課題では閉じていることを見る）
8. - [ ] 退行しない: 成功し欠けの無い場合、既存の手順のスクリプトは今と同じ `status: ok`・終了コード 0 を返す。既存の `gate` / `stopped` の終了コード（1・2・3・4・10〜19・20〜29・69・75）の意味は変わらない（既存のテスト全体が通る）
9. - [ ] 退行しない: 新しい状態の値か終了コードを足した場合、結果 JSON の `status` を読む既存の読み手（`supervise_lib` のステップの成否の判定など）は、それを成功として読まない（`ok` だけを成功とする判定のまま、新しい値で止まることを単体テストで確かめる）
