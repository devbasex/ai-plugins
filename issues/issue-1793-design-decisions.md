# #1793 の設計: 決定の記録

設計の本文は [issue-1793-design.md](issue-1793-design.md) にある。ここには、選んだ結論と理由と採らなかった案だけを置く。規則の番号（R1〜R6）は #1793 の本文の「決め直した規則」の表の番号である。

## 規則の組の最終形

| # | 規則 | 最終形 | 決定 |
| --- | --- | --- | --- |
| R1 | 取り消しの単位 | 維持（項目の単位。外すときも項目の全体） | — |
| R2 | 積み直しが衝突したとき | 衝突したコミットの持ち主の項目だけを外し、計画を作り直して続ける。積み終えたら残った項目を確かめ直す。`widened` と「広げても積み直せない → 終了コード 4」は無くす | 決定 1・2・5・7 |
| R3 | 修正の打ち切り | 締め切りは維持し、結果を残してコミットしなかった項目は次の検証の最初に取り消す | 決定 3 |
| R4 | コミットの形 | 維持（1 項目 = 1 コミット、テストを足す項目は 2 コミット） | — |
| R5 | 範囲テストへ渡す対象 | `{paths}` へは `::` より前のパスだけを渡す（共通のライブラリ） | 決定 4 |
| R6 | 「直すものは無い」と答えた項目 | R3 で扱う（申告は読まない） | 決定 3 |

**判断の軸は 1 つにした。項目を残すかは、その項目を積んだ HEAD の範囲テストで決める。** git の衝突は「その項目をそのまま積めない」ことを示すだけで、外す相手は衝突したコミットの持ち主に限る。修正担当が何もコミットしなかったことは git で観測でき、同じ項目を同じ状態で渡し直しても結果は変わらない。

### 決定 1: テストを通る改善を巻き込んで捨てないため、積み直しの衝突では衝突したコミットの持ち主だけを外し、計画を作り直して続ける

衝突したら、衝突したコミットを記録に持つ生きている項目を外し、`plan_rebuild` を「指定した項目 + 外した項目」で作り直して起点から積み直す。外した項目に依存して後で衝突した項目も、同じ繰り返しで 1 件ずつ外れる。PR 254 の reflog の 12 件で、この手順は 6 件を残した（手元で確認済み）。今の積み直しの仕組み（`plan_rebuild`・`replay_commits`）をそのまま使え、足すのは繰り返しと持ち主の引き当てだけである。

**計画を作り直すのは、外した項目のコミットのうち衝突より前に積み直し終えたもの（テストのコミットなど）も消すためである。** 衝突したコミットだけを抜くと、テストだけが HEAD に残る。

採らなかった案:

- **同じファイルを触った項目まで広げる（今の `widened`）を、範囲テストの掛け直しつきで残す**: 掛け直しても、広げた時点で同じファイルの改善はすでに消えている。ファイルの一致は衝突の相手を示さず、PR 254 では 7 件、#1733 では 18 件を捨てた
- **項目ごとに範囲テストを掛けてから次を積む（逐次の採用）**: 取り消しの巻き込みが原理的に無いが、実装担当の 1 回の起動で順に実装する形（#933 決定 12）を変え、範囲テストの回数が項目の数だけ増える。R5 で偽の失敗を断てば PR 254 では差が無い。効果を実測してから判断する（要求の対象範囲「含まない」）
- **ハンクの行範囲の重なりで広げる相手を絞る**: 行範囲の重なりは git の衝突と一致せず（文脈 3 行の差）、試しに積む方が正確で単純である

根拠: Value 1 / Value 6（MVV 版 2）

### 決定 2: 取り消した項目の変更が消えた HEAD を検証済みと言わないため、最終ゲートより前の取り消しで HEAD が変わったら、残った検証済みの項目をすべて確かめ直す

取り消しは HEAD の木を変える。積み直した後ろの項目だけでなく、前の項目の範囲テストも、取り消した項目の変更（テストのコミットを含む）の上で通っていた可能性がある。どの項目の結果が変わりうるかを依存から絞るのは決定 1 で退けたファイル単位の推測と同じ形になるため、生きている `verified` の項目をすべて `implemented` へ戻し、検証の判定に任せる。範囲テストは同じ語の並びを 1 回だけ走らせるため（`scope_verdict._run_once`）、増えるのは語の並びの数までで、R5 で同じファイルの項目は 1 回にまとまる。

採らなかった案:

- **外した項目があったときだけ確かめ直す**: 外さずに積み直せた場合も木は変わる。要求の E9 は「E8 があったか、HEAD の SHA が変わった」を引き金にしている
- **積み直した（SHA が変わった）項目だけを確かめ直す**: 起点より前の項目も、後ろの変更が消えた木の上で範囲テストを走らせ直していない点は同じで、条件を足すだけ規則が増える

根拠: Value 1 / Value 3（MVV 版 2）

### 決定 3: 直すものの無い項目に予算を使わないため、結果を残してコミットしなかった項目を次の検証の最初に取り消す

判定は 2 つの観測だけで行う。修正の起動が結果ファイルを残したか（`read_result(...).payload`）と、修正の範囲のコミットのトレーラーにその項目の `Item-Id` があるか、である。両方を満たさない項目は今のとおり締め切りまで回る。取り消すのは `merge-fix` ではなく次の `verify` の最初で、直さなかった項目を 1 回の `drop` でまとめて取り消す。取り消しを決めるのを検証に集め（要求の E6）、取り消しの後の確かめ直し（決定 2）が同じ検証の中で続くためである。

**手順を外れて範囲ごと捨てた修正は「作った」に数える。** 直そうとしてコミットした項目は、直さなかった項目ではない。違反の扱いは今のまま（範囲ごと捨てて締め切りまで回す）である。

採らなかった案:

- **結果ファイルの申告（`not_fixed`）で決める**: オーケストレーターは git だけを見る規則（`merge-fix` の説明）を崩す。申告と git が食い違ったとき（`fixed` と書いてコミットが無い）に判定が割れる
- **項目ごとの修正の回数に上限を置く**: 回数で切ると時間が残っていても止まる（#933 決定 23 が退けた形）。コミットしなかったことは 1 回目で分かるため、回数を待つ理由が無い
- **`merge-fix` の中で取り消す**: 取り消しの後の確かめ直しを `merge-fix` が持つことになり、検証が 2 か所に分かれる

根拠: Value 1 / Value 4（MVV 版 2）

### 決定 4: `{paths}` の約束をどのランナーでも守らせるため、`::` を落とす場所を共通のライブラリの `test_strategy.suite_groups` にする

`{paths}` の約束は「パス」である（範囲テストの雛形の用語）。`::` を受け付けるかはランナーごとに違い、宣言の `runner` は自由な文字列なので見分けられない。雛形へ語を入れる経路（項目の範囲テスト・`test-run.py scope`・失敗の走らせ直し）はすべて `suite_groups` を通るため、ここで `::` より前のパスへ直し、重なりを 1 つにまとめ、最初に現れた順を保つ。失敗の走らせ直しはすでにファイル単位で渡しており（`test_triage.by_file`）、振る舞いは変わらない。`valid_targets` は今のとおり `::` 付きの値を受け取る（計画が書いても項目を見送らない）。

採らなかった案:

- **宣言の `runner` が `unittest` なら計画に `::` を書かせない**: `runner` は自由な文字列で、unittest の包み（PR 254 の `scope_command`）は名前から見分けられない（Value 5）。プロンプトだけの約束は担当が破れる
- **終了コード 2 と出力から「1 件も走らせなかった」を見分けて起動の失敗にする**: `::` 以外の原因も含む一般の検出で、#1630 が扱う（要求の対象範囲「含まない」）。`::` を渡さなければこの経路は起きない
- **cross-refactoring の `targets` の側だけで落とす**: `test-run.py scope --paths` の経路に同じ不具合が残る（Value 6）

根拠: Value 5 / Value 6（MVV 版 2）

### 決定 5: 最終ゲートの中の取り消しに締め切りを足さないため、確かめ直しを最終ゲートの判定に任せる

最終ゲートへ入った後（`phase` が `final` / `done`）の取り消しは、打ち切りの後の取り消し（`stop_revert`）と最終ゲートの原因の判定が行い、どちらも取り消した後に最終ゲートが HEAD を全体テストか CI で確かめ直す（`FINAL_GATE=recheck`）。全体テストは範囲テストを含むため、ここで範囲テストの確かめ直しを足しても新しい失敗は見つからず、打ち切りの後の取り消しの締め切り（`stop_revert_end_at`）を超えるかどうかの規則だけが増える。したがって最終ゲートの中の取り消しでは `verified` を戻さず、`recheck` を空にする。要求の未決「締め切りを過ぎてから確かめ直しが要るときの扱い」はこの決定で起きなくなる。確かめ直さずに採ることも無い（採用は最終ゲートが `passed` のときだけ。`ledger.adoption_confirmed`）。

採らなかった案:

- **最終ゲートの中でも範囲テストで確かめ直し、締め切りを超えたら取り消す**: 全体テストと同じ確かめを重ね、締め切りの扱いを 1 つ足す
- **最終ゲートの中でも `implemented` へ戻す**: 最終ゲートが通っても `verified` でない項目は採用に数えられず、採用が 0 になる

根拠: Value 1 / Value 4（MVV 版 2）

### 決定 6: #1733 の受け入れ条件を 1 本の変更で満たすため、実装を #1793 の 1 本に寄せる

#1733 の受け入れ条件（18 件のうち 8 件が直されない形で採用 ≥ 1・終了コード 4 でない）は、R3（8 件を 1 回目の後に取り消す）と R2（取り消しで同じファイルの残りを消さない）の両方が揃って初めて満たせる。触るファイルも重なる（`converge.py` の分割・`scope_verdict.pending`・`undo`）。分けると、先に入った方の受け入れ条件のテストが後の変更を前提にして書けない。R5 は独立しているが組み立ての 1 か所で、別の実装にするほどの大きさが無い。実装の中の順序は R5 → R3 → R2（`merge_fix` の分割を R3 の最初に置く）とする。

採らなかった案:

- **#1733（R3）と #1793（R2・R5）を別の実装の PR にする**: どちらかの受け入れ条件が片方だけでは満たせず、同じファイルを 2 本が触る

根拠: Value 1 / Value 6（MVV 版 2）

### 決定 7: 取り消しの理由を読み違えないため、外した項目の理由を上書きし、取り消しとして数え、記録の `mode` を `ejected` にする

外した項目の `failure_reason` は「`<by> の取り消しで <12 桁の SHA> の積み直しが衝突したため外した`」で上書きする。`mark_dropped` の `setdefault` のままだと、自分の範囲テストで落ちていた項目は前の理由が残り、実際の取り消しの理由（衝突）が読めない（PR 254 の I-007・I-009）。落ちた検査は `failed_check` に残る。直さなかった項目の理由は「修正担当が直さなかった（修正の範囲にこの項目のコミットが無い）」とする。

外した項目と直さなかった項目は取り消し（`reverted`）として数え、見送りの理由を足さない。見送りは計画と実装の取り込みで外したものに限る今の区分を保つ。取り消しの記録は `mode` に `ejected` を足し、外した記録を `ejected[]`（`item`・`commit`・`by`）に置く。`mode` を読んで分岐する処理は無いため、旧い `widened` の記録はそのまま読める。

**理由の文に「巻き込まれた」を使わない。** 用語集の「巻き込まれた項目」は、他の項目の変更で範囲テストが落ちて取り消さずに待つ項目を指す。今の `widened` の理由が同じ語を別の意味に使っていた。

採らなかった案:

- **新しい見送りの理由（`conflict` など）を足す**: 検証より後の取り消しを見送りに数えると、報告の件数の区分（取り消し・見送り）が変わり、件数の和の不変条件（#1692 の Tally）を見直すことになる
- **`mode` を `item` のままにして `ejected[]` だけを足す**: 1 行で外した項目の有無が読めない

根拠: Value 7 / Value 8（MVV 版 2）

### 決定 8: 偽の失敗で修正を回して取り消しで巻き込む組み合わせを残さないため、引き金（R5・R6）を同じ設計で直す

R5（`::` を拒んだ終了コード 2 をテストの失敗と数える）と R6（直すものは無いと答えた項目を回し続ける）は、R2・R3 と同じ「失敗した項目の扱い」の経路の入口である。引き金だけを直すと、別の偽の失敗（揺れ・コマンドの不一致）で同じ巻き込みが起きる。規則だけを直すと、PR 254 では偽の失敗で 4 件が取り消され、外す規則でも 6 件しか残らない。R5 は組み立ての 1 か所、R6 は R3 そのものなので、設計を分けるほどの大きさが無い。

採らなかった案:

- **引き金を別の課題に分ける**: 上の組み合わせが片方だけ残り、PR 254 の目安（12 件すべてが残る）を満たせない

根拠: Value 6（MVV 版 2）

### 決定 9: 構造検査の上限を超えずに R3 を足すため、`merge-fix` を `commands/merge_fix.py` へ分ける

`converge.py` は今 500 行ちょうどで、構造検査（1 ファイル 500 行）の上限にある。`merge-fix` は検証と別の工程で、取り込みの関数（`_fix_problems`・`_inspect_fix_commits`・`_apply_fix_result`・`_account_fix`・`cmd_merge_fix`）は検証の関数を呼ばない。工程の境で分けると、R3 の判定が取り込みの側に、取り消しが検証の側に置かれ、決定 3 の分担がファイルの分け方と一致する。

採らなかった案:

- **構造検査の例外リストに `converge.py` を足す**: 例外は行数を固定するラチェットで、次の変更でまた同じ判断が要る

根拠: Value 4 / Value 6（MVV 版 2）
