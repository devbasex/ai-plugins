## 目的

利用者が承認した設計が、承認の直後から実装の対象になる状態にする。今は承認しても設計の Pull Request（以下、設計 PR）が `develop` へマージされず、選定が「設計 PR がマージ待ち」でその課題を外し続ける。ループは残りの候補の設計だけで周回を使い切る（並列の計画 p3 のレーン lroot2 のループ lroot3 で、8 周すべてが設計の段階で終わった）。

あわせて、オーガナイザーが 1 つの問いの答えを待つ間に届いた依頼を、答えの直後にまとめて捌く。出した問いは AI の側から取り下げられないため、待つ間に届いた依頼は答えの後まで表に出ない。

## 前提

- 前提 1: 承認済みの 3 本（PR #2481・#2480・#2500）は、2026-11-04 にすでに `develop` へマージ済みである（`gh pr view` の `mergedAt` が 21:57:18Z・21:56:56Z・22:26:52Z）。この課題は手でのマージを要さない
- 前提 2: 設計 PR の宛先は `develop` で、`develop` へのマージは共通原則の「必ず人の承認が要る操作」（C1〜C8）とプロジェクトの P1 のどれにも当たらない。承認ゲート 1 の答えそのものが、マージの許可を兼ねる
- 前提 3: マージは、設計 PR の必須の検査（継続的統合）が緑のときだけ行う。必須の検査を管理者の権限で飛ばしてマージしない。ルールセットのレビューの要件を通す手段（管理者の権限を使うか）は設計で決める
- 前提 4: オーガナイザーが MVV 判定で自分で決めてよいのは、`.ndf/pace.json` がその承認ゲートと区分を MVV 判定に任せることを許し、MVV の承認とハッシュの一致がそろうときだけである（`plugins/ndf/skills/development-workflow/references/pace.md`）。レッドライン（C1〜C8・P1）に当たる依頼は自分で決めない
- 前提 5: 答えを送る前に、問いの時点の設計 PR の先端と今の先端を比べる今の決まり（先端が動いていれば新しい先端で問い直す）は残す。承認したのと違う中身をマージしないためである

## 対象範囲

含む:
- 並列の計画の下で、オーガナイザーが設計の承認を送るときに設計 PR を `develop` へマージすること
- 1 本の開発ループで、利用者が設計の承認を答えるときに設計 PR を `develop` へマージすること

- オーガナイザーが問いの答えを受けた後、待つ間に届いた依頼を読み直し、整理して、残りをまとめて問い直すこと
- 上の振る舞いに合わせた手順書（`development-workflow` の `references/parallel.md`・`references/loop.md`）と、確定仕様 `docs/specifications/ndf-parallel-organizer.md` の不変条件 I18（オーガナイザーは作業を持たない・`answer` は答えのメッセージを送るだけ）の書き換え

## 受け入れ条件

設計の承認とマージ:

- [ ] 1. 並列の計画の下で `parallel.py answer <計画名> <依頼> --approved` を打つと、依頼の設計 PR の先端が問いの時点と同じで、必須の検査が緑なら、その設計 PR が `develop` へマージされた状態でコマンドが返る。結果の JSON にマージの結果（マージした / できなかった理由）が載る
- [ ] 2. 1 の設計 PR の先端が問いの時点と違うとき、`answer` はマージせず、今の決まりどおり新しい先端で問い直される
- [ ] 3. 1 本の開発ループで `loop answer <名> <課題> --approved --pr <設計 PR>` を打つと、1・2 と同じ条件で設計 PR が `develop` へマージされる
- [ ] 4. マージできないとき（衝突・必須の検査が緑でない・権限が無い）、`answer` は終了コード 0 で返り、答えは送られ、理由がループの記録の人の判断待ちの行に残る。`answer` は検査の完了を待たない
- [ ] 5. 承認とマージが済んだ課題は、次の周回の選定で、順位によらず先頭に選ばれる（選定の行に外す理由「設計 PR がマージ待ち」が出ない）
- [ ] 6. 4 で未マージのまま残った承認済みの設計 PR は、次の周回の選定の前にマージし直される。またマージできなければ、その課題だけを外して他の課題で周回が進み（周回は止まらない）、その次の周回でもう一度マージし直される
- [ ] 7. 承認済みの設計 PR がある状態で、ループが他の課題の設計だけで周回を使うのは、その設計 PR がマージできなかった周回に限られる（テストで、承認済み・マージ可能の設計 PR があるときの次の周回の選定に、その課題が含まれることを確かめる）

答えの後の依頼の整理:

- [ ] 8. オーガナイザーが問いの答えを送った後、手順書の手順で、答えを待つ間に届いた依頼が取り直され、次の 3 種が除かれてから、残りが区分ごとに 1 回 4 件までの問いにまとめて出される: 同じ依頼の再送 / 送った答えで要らなくなった依頼 / MVV 判定で自分で決められる依頼
- [ ] 9. 8 の「MVV 判定で自分で決められる依頼」は前提 4 の条件を満たす依頼だけで、自分で決めた依頼には判定の記録（根拠にした MVV の項目と理由）が残る。レッドラインに当たる依頼は除かれず、利用者へ問われる

退行しないこと:

- [ ] 10. `--revise` と `--rejected` の答えでは設計 PR をマージしない
- [ ] 11. 承認ゲート 2 の答え（`confirm` / `settle`）の振る舞いは変わらない

| --- | --- |
| 性能・拡張性 | `answer` は設計 PR の検査の完了を待たない。オーガナイザーが答えの直後に次の依頼を捌けるようにするためである |
| 可用性 | マージの失敗で周回もオーガナイザーも止まらない（受け入れ条件 4・6） |
| 運用・保守性 | マージの結果と失敗の理由が、`answer` の結果の JSON とループの記録の両方から読める |
| セキュリティ | 必須の検査を飛ばしてマージしない（前提 3）。承認した先端と違う中身をマージしない（前提 5） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。`parallel.py answer --approved` と `sprint-state.py loop answer --approved` がマージを行い、結果の JSON にマージの結果の項目が増える。引数は変えない（互換あり） |
| データ | ループの記録の人の判断待ちの行に、マージの失敗の理由の項目が増える。既存の記録の移行は要らない（項目が無い行は今の振る舞い） |
| 既存の振る舞い | 確定仕様の不変条件 I18 の「`answer` は答えのメッセージを送るだけ」が変わる。ラベルと承認の記録は今どおり持ち主のレーンが周回の境で書く |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| テスト | `uv run --frozen --project . --all-extras pytest plugins/ndf/scripts/tests -q -n 4`（並列の計画と開発ループの選定・答えのテスト。`gh` は偽のコマンドで置き換える） |
| 静的解析・型検査 | 継続的統合の既存のジョブ（`ruff` ほか）と `python3 plugins/ndf/scripts/instructions-check.py --root .` |
| 手動確認 | リリース後、並列の計画のレーンで設計の承認を送り、設計 PR が `develop` へマージされ、次の周回でその課題が実装に選ばれることを、ループの記録と `gh pr view` で確かめる |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | スクリプトは `plugins/ndf/scripts/`、手順は `plugins/ndf/skills/development-workflow/references/`。新しい仕組みは安定版の経路（`AGENTS.md` の「安定版と実験版」） |
| コーディング規約 | `AGENTS.md`。PR の CI 待ちとマージは `merged-steps.py merge-when-green` の既存の部品を使い、手で `gh pr checks --watch` と `gh pr merge` をつながない（`development-workflow` の `references/waiting.md`） |
| テスト戦略 | 振る舞い（マージする条件・失敗の扱い・選定の順）は単体テストで担保する。`.md` の文言を照合するテストは書かない（`AGENTS.md`） |

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | 既存テストの実行、承認した先端との照合 |
| 確認してから行う | 確定仕様の不変条件 I18 の書き換え（承認ゲート 1・2 で人が見る） |
