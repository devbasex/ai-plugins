# #1529: 昇格のプランが、導入の確認をしたコミットと違う先頭を本番チャネルへマージしうる

正は課題の本文（#1529）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 何を見つけたか

`pace: auto` / `fast` の昇格のプラン（`supervise_lib/delivery_templates.py` の `plan_promote`）の `promote` ステップ（`merged-steps.py promote --gate-approved mvv`）は、CI が通った昇格の Pull Request の先頭（`merged_lib/merge.py` の `merge_when_green` の `--match-head-commit watch.last_sha`）をマージする。#1457 の設計では、導入の確認（`.ndf/pace.json` の `<節>.verify`）をベースブランチの先頭で走らせ、確かめたコミットを承認資料に載せる。しかし確認の後にベースブランチが進むと（別のスプリントのマージなど）、昇格の Pull Request の先頭も進み、確認していないコミットが MVV 判定の後にそのまま本番チャネルへマージされる。

## どこで見つけたか

#1457 の設計（`issues/old/issue-1457-design-decisions.md` の決定 7）。`plugins/ndf/scripts/merged_lib/merge.py` の `merge_when_green`・`promote`。

## なぜこの変更の範囲外なのか

#1457 の受け入れ条件は、確認を走らせることと、確かめたコミットを承認資料へ載せること（AC5）までを求め、確かめたコミットとマージするコミットの照合は求めていない。照合するには、確認のステップが書いたコミットを `promote` のステップへ渡す仕組みが要る。根拠: Value 1 / Value 3（MVV 版 2）

## 直さないと何が起きるか

`delivery` で経路 `promote` を組むリポジトリの `auto` / `fast` で、承認ゲート 2 の MVV 判定が読んだ確認の記録と、本番チャネルへ入るコミットが食い違いうる。手動反映の本番系（#1454）は「先頭が変わったら承認ゲート 2 からやり直す」を手順で求めているが、昇格の経路には同じ照合が無い。

## 追記（2026-10-05、スプリント m815・PR #1763）

#815（10.17.62）が本番の配布（`release --channel prod`）に、承認したコミットと配布の時点の先端を比べる判定を入れた。比べる関数は `plugins/ndf/scripts/lib/approved_commit.py` に置き、昇格の経路からも呼べる形にしてある（#815 の確定仕様 `docs/specifications/ndf-release-approved-commit.md` の「決定の理由」。`allowed` を 0 個にすれば「先端の木が承認したコミットの木と等しいか」の判定になる）。#815 の要求の前提 5 が「promote を直すのは別の課題にする」としたのは、この課題である。

`merged-steps.py merge-when-green` の `--expect-head <SHA>`（`merged-steps.py:471`、照合は `merged_lib/checks.py:310`）は、PR の先端がその SHA のときだけマージし、違えば `result: head_moved` で止まる。これを渡すのは本番の配布（`release-steps.py:664`）だけである。`promote` の副命令はこの引数を持たないが、`merged_lib/merge.py:300` の `promote` は同じ引数のまま `merge_when_green` を呼び、照合は `expect_head` を読む。`promote` に同じ引数を足し、昇格のプランの `promote` ステップ（`supervise_lib/delivery_templates.py` の `plan_promote`、142 行の `--gate-approved mvv`）へ確認の記録の SHA を渡せば、確かめたコミットとマージするコミットの照合になる。

## 目的

- `pace: auto` / `fast` で昇格の Pull Request を MVV 判定で通すとき、**本番チャネルへ入るコミットを、MVV 判定が読んだ導入の確認の記録のコミットと同じにする。**
  承認ゲート 2 の判定の材料と、実際に本番へ届く中身が食い違わない状態にする

## 前提

- 前提 1: 対象は昇格のプランの `fast` / `auto` の経路（`verify` → `prepare` → `mvv` → `note` → `promote --gate-approved mvv`）だけである。`normal` の経路（`promote` → 利用者の承認 → `promote-approved --gate-approved user`）は導入の確認を走らせず、照合する記録が無い
- 前提 2: 照合の仕組みは、既存の `merged-steps.py merge-when-green --expect-head`（`merged_lib/checks.py` の `_check_expected` と `merge.py` の `--match-head-commit`）か `lib/approved_commit.py` を使い、新しい比べ方を作らない。どちらを使うか・SHA をどう渡すかは設計が決める
- 前提 3: 昇格の Pull Request の head はベースブランチそのものなので、導入の確認がベースブランチの先頭で確かめたコミットと、そのときの昇格の Pull Request の先端は同じコミットである（`release_lib/deploy.py` の `head_of_base` は `origin/<ベースブランチ>` を確かめる）
- 前提 4: 食い違ったときは、承認資料を作り直して自動で判定し直さず、既存の `handoff` で承認ゲート 2 へ落として人へ戻す（#815 の確定仕様が「止まって人へ戻すまでを扱う」としたのと同じ範囲）。人が承認した後の続き（`--from promote-approved` か、プランを `verify` から流し直すか）は既存の手順のまま変えない

## 対象範囲

含む:
- 昇格のプランの `fast` / `auto` の `promote` ステップが、導入の確認の記録に書かれたコミットと昇格の Pull Request の先端を照合し、等しいときだけマージすること
- 食い違い・記録が読めないときに、マージせずに止まり、承認ゲート 2 へ戻ること
- `merged-steps.py promote` の引数と使い方の説明（モジュールの docstring・`--help`）と、`development-workflow` の `references/pace.md` の昇格のプランの説明を、変えた振る舞いに合わせること

含まない:
- `normal` の昇格（`promote-approved --gate-approved user`）の照合。利用者が承認ゲート 2 で見た先端と、承認の後にマージする先端の照合は、この課題の記録（導入の確認）とは別の材料が要る（未決 1）
- 食い違ったときに、導入の確認と MVV 判定を自動でやり直す仕組み
- 本番の配布（`release --channel prod`）と手動反映の本番系（`gate-2` のプラン）。どちらも既に照合を持つ（#815・#1454）
- 導入の確認そのもの（`verify-facts`）の走らせ方と承認資料の中身

## 受け入れ条件

この節の「導入の確認の記録」は `release-steps.py verify-facts` が書く承認資料（`approval-verify.md`）を、「確かめたコミット」はそこに書かれた、導入の確認を走らせたベースブランチの先頭のコミット（ドメインイベントの X）を指す。

- [ ] 1: `fast` / `auto` の昇格のプランで、昇格の Pull Request の先端が確かめたコミット X と等しく CI が通ったとき、`promote` ステップは X を本番チャネルへマージし、続く `record` へ進む（今の成功の経路が変わらない）
- [ ] 2: 導入の確認の後に先端が X から Y へ進んでいたとき（E5 が E1〜E6 のどこで起きても）、`promote` ステップは `gh pr merge` を呼ばず、結果 JSON に `head_moved` と X・Y を出して非 0 で終わる
- [ ] 3: CI を待つ間に先端が X から Y へ進んだときも、Y をマージしない（2 と同じ結果になる）
- [ ] 4: 2・3 のとき、プランは `handoff` へ進み、承認ゲート 2 の `by: mvv` の記録を外して終了コード 10（承認ゲート）を返す。本番チャネルの先端は変わらない
- [ ] 5: 導入の確認の記録が無い・確かめたコミットの欄が読めない・40 桁の SHA でないとき、`promote` ステップはマージせずに非 0 で終わり、4 と同じく承認ゲート 2 へ戻る（照合しないままマージしない）
- [ ] 6: 照合に使うコミットは、MVV 判定（`mvv` ステップ）が読んだのと同じ導入の確認の記録から取る。プランを組む時点の先端や、ブランチ名から引き直した先端を使わない
- [ ] 7: `normal` の昇格のプラン（`promote` と `promote-approved`）の組み立てとコマンドは今と同じである
- [ ] 8: ベースブランチ・本番チャネルの名前を埋め込まない（`develop` / `main` を新しく書かない。名前は今と同じく引数と宣言から読む）
- [ ] 9: `merged-steps.py promote` の `--help` と `pace.md` の昇格のプランの説明が、照合と、食い違ったときに承認ゲート 2 へ戻ることを書いている

## MVV との突き合わせ

反する疑いは無い。根拠: Vision（承認ゲート 2 に届く判定の材料と本番へ入る中身をそろえる）・Value 2（承認を MVV 判定に任せる経路でも、判定の材料の外のコミットを本番へ入れない）・Value 6（既存の照合を使う）・Value 5（ブランチ名を埋め込まない）。
本番チャネルへの反映は P1・C5 に当たらない（取得元・版の規則は変えない）。
