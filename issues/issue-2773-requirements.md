# #2773: release: デプロイとリリースを workflow で行い、リリース承認をマージの前に取る

正は課題の本文（#2773）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 今の形

本番へのリリースは、指揮役の会話のセッション（conductor）の中でコマンドを打って行う。

```bash
release-steps.py release --version <版> --channel prod --approved-sha <SHA>
```

中身は 3 つ。

1. 承認したコミットとリリース用ブランチ（`release/v<版>`）の先端を比べ、承認の外の変更があれば終了コード 10（`gate`）で止める
2. `release/v<版>` を develop へ取り込み、main への PR を作って CI を待ち、マージする（`protect main` の ruleset が承認 1 件を求めるため `--admin`）
3. main への push で `.github/workflows/release-cd.yml` が `release-steps.py publish` を動かし、タグ `ndf--v<版>` と GitHub Release のうち無いものを作る（#2623 で CD へ移した。`.ndf/project.json` の `delivery` は `kind: auto`）

人の承認（リリース承認ゲート）は会話の問い（`AskUserQuestion`。区分 `ndf-gate:2`）で取る。記録は `release-steps.py approve` が手元の承認資料（`issues/approval-ndf-v<版>.md`。`.gitignore` の対象）に書く。GitHub の上には承認の記録が残らず、main の ruleset も承認の有無を見ていない。

開発版のデプロイ（`release-steps.py release --channel dev`）も、会話のセッションの中で打つ。

## 目的

- 本番へのリリースと開発版のデプロイを、ローカルの会話のセッションに依存させず、GitHub の上で起こす
- リリース承認をマージの前へ移し、「リリース承認 → main へのマージ → workflow が自動でデプロイ」の流れにする。main へのマージの時点で承認済みであることを、GitHub の上の記録と ruleset で保証する
- `development-workflow` のマージからリリースまでの工程を、リポジトリの設定（CD の有無・レビュー必須の有無）で 3 つの場合に分ける

| 場合 | 例 | リリース承認を取る場所 |
| --- | --- | --- |
| CD があり、レビューなしでマージできる | ai-plugins（`protect main` の承認数を 0 にした後） | マージの前。証跡は PR へのコメント。承認の後に AI がマージし、CD が反映する |
| CD があり、レビューが必須 | — | PR のレビューの承認。レビューの承認をそのままリリース承認とみなし、証跡の記録とチェックの仕組みは足さない |
| CD が無い | `delivery` に `kind: auto` の行が無いリポジトリ | 今の `release` の工程（マージの後に手でリリースする） |

## 前提

- 前提 1: 2026-11-08 に、ruleset を `protect main`（id 22332172。承認 1 件・コードオーナーのレビュー必須）と `protect develop`（id 26777950。承認 0 件）に分けてある。PR 経由のマージ・必須ステータスチェック 17 件・削除と force push の禁止はどちらも同じ
- 前提 2: レビュー必須かは ruleset を読んで見分ける（`GET /repos/{owner}/{repo}/rules/branches/{branch}`）。workflow の `GITHUB_TOKEN` で読めることを public（ai-plugins）と private（volareinc/nd-factory）の両方で確かめた（2026-11-08）。従来のブランチ保護（classic）の API は `GITHUB_TOKEN` では読めない（403）
- 前提 3: main への push でタグと GitHub Release を作る仕組み（`release-cd.yml` と `release-steps.py publish`）は既にあり、この課題ではそのまま使う
- 前提 4: 承認権限を持つ人のアカウントで AI が書いた証跡は、その人の承認として扱う（利用者 2026-11-08「承認権限を持った人のAIによる偽装は不問」）。会話の問いで得た答えを、AI が利用者のアカウントで証跡のコメントとして書いてよい
- 前提 5: CI の必須ステータスチェックが通らない PR は main・develop へマージできない（前提 1 の ruleset）。リリースの workflow が「CI のテストが通った後に始まる」ことは、マージを起動の条件にすることで満たす
- 前提 6: 証跡の比較の対象は PR の head のコミット（先端）である。マージのコミットそのものは比べない

## 対象範囲

含む:
- 本番のリリースの PR へ承認資料と承認の証跡をコメントで置く手順と、証跡を確かめる必須ステータスチェックの workflow
- `protect main` への必須ステータスチェックの追加と、承認数を 0 にする変更（実行は境界の「確認してから行う」）
- 開発版のデプロイを workflow で行えるようにすること
- `release-steps.py release` の本番の経路を、証跡を置いてマージを待つ形へ変えること
- `development-workflow`・`release`・`merged` の手順書で、3 つの場合を見分けてリリース承認の場所とマージの主体を決めること
- リリースの手順（workflow と `/ndf:release`）から全体テストの流し直しを外すこと
- 選んで集める取り込み方のリリースで、承認の後の変更が本番へ入らないこと（#3168 を統合）

含まない:
- 従来のブランチ保護（classic）でレビュー必須を見分ける実装（未決。設計で決める）
- タグと GitHub Release を作る処理の作り直し（前提 3）
- 他のリポジトリ（volareinc/nd-factory など）の ruleset の変更
- 版数の付け方・チャネルの構成の変更（共通原則の P1 に当たる変更はしない）

## 用語

| 用語 | 意味 |
| --- | --- |
| リリースの PR | 本番チャネル（main）へ版を入れる Pull Request。版上げまでのコミットを積み終えた状態で承認を求める |
| 承認の証跡 | リリースの PR へのコメントで、承認したコミットを書いたもの。誰がいつ承認したかは GitHub がコメントに付けた作成者と作成時刻で読む |
| 証跡のチェック | PR に承認の証跡があり、書かれたコミットが PR の先端と一致し、書いた人が承認権限を持つときだけ通る必須ステータスチェック |
| 承認権限 | リポジトリの admin か maintain の権限 |

## 受け入れ条件

- [ ] 1. 開発版のデプロイ（今の `release-steps.py release --channel dev` に当たる処理）を GitHub Actions の workflow で行える。承認は求めない
- [ ] 2. リリースの PR を main へマージすると、workflow がタグ `ndf--v<版>` と GitHub Release を作る（会話のセッションでタグを打たない）
- [ ] 3. リリースの PR に、承認したコミットの SHA を書いた承認の証跡がコメントで残る
- [ ] 4. マージを GitHub App や AI が行っても、証跡のコメントの作成者と作成時刻から、誰がいつ承認したかを読める
- [ ] 5. 証跡のコミットと PR の先端が違えば、証跡のチェックが落ち、理由（証跡のコミットと先端の SHA）を出す
- [ ] 6. 証跡の無い PR では証跡のチェックが落ち、main へマージできない
- [ ] 7. 承認権限（admin か maintain）を持たない人が書いた証跡では、証跡のチェックが落ちる
- [ ] 8. 証跡のチェックと同じ名前の commit status を API で付けても、main の必須チェックを満たさない（必須チェックを GitHub Actions のアプリに限る）
- [ ] 9. PR の中で証跡のチェックの workflow を書き換えても、チェックの判定は変わらない（既定ブランチの定義で動く）
- [ ] 10. 証跡の本文に書いた人・時刻は判定に使わない
- [ ] 11. `protect main` の必須ステータスチェックに証跡のチェックが入っている（ruleset の API の出力で確かめる）
- [ ] 12. 11 の後に、`protect main` の承認数が 0 になり、`release-steps.py` が `--admin` を使わずに main へマージする
- [ ] 13. 選んで集める取り込み方のリリースでも、承認の後にリリースのブランチへコミットが足されるか、集めたスプリントが動いて PR を組み直すと、証跡のチェックが落ち、承認をやり直すまで main へマージされない
- [ ] 14. 版上げ・CHANGELOG・トークン消費の記録など、リリースの手順が書くコミットは、承認を求める前にリリースの PR へ積み終えている（承認の後にリリースの手順がコミットを足さない）
- [ ] 15. リリースの workflow（本番・開発版）は、対象のコミットで CI の必須チェックが通るまで始まらない。テストが落ちたら始まらない
- [ ] 16. リリースの手順（workflow・`/ndf:release`・リリースの前の検査のプラン）が全体テスト（`test-run.py whole`）を流さない
- [ ] 17. `development-workflow` が、CD の有無（`delivery` の `kind: auto`）とレビュー必須の有無（ruleset）で 3 つの場合を見分け、場合ごとにリリース承認を取る場所とマージする主体を返す。ai-plugins は「CD があり、レビューなしでマージできる」と判定される
- [ ] 18. 「CD があり、レビューが必須」の場合は、証跡のコメントを書かず、証跡のチェックも求めない
- [ ] 19. 「CD が無い」場合の工程は今の `release` の工程から変わらない（既存のテストが通る）
- [ ] 20. `release`・`merged`・`development-workflow` の手順書が、workflow を起動して結果を待つ形を書き、会話の中でタグを打つ手順を残さない
- [ ] 21. 秘密の値（トークン）をリポジトリに置かない。workflow は `GITHUB_TOKEN` だけを使う（`scripts/check-repo-secrets.py` が通る）

## 承認の証跡の信用

チェックが防ぐのは、承認権限を持つアカウント以外からの偽装と誤りである。承認権限を持つ人のアカウントでの AI による偽装は防がない（前提 4）。

| 観点 | 防ぐか | 作り方 | 受け入れ条件 |
| --- | --- | --- | --- |
| 承認の後のコミットが混ざる | 防ぐ | 証跡に書いたコミットと PR の先端を比べる | 5・13 |
| 承認の取り忘れ・別の PR のマージ | 防ぐ | 証跡が無ければ落とす | 6 |
| 承認権限の無い人（fork・書き込み権限だけの人）の証跡 | 防ぐ | コメントを書いた人の権限を確かめる | 7 |
| チェックの結果の偽装 | 防ぐ | 必須ステータスチェックを GitHub Actions のアプリの ID に限る | 8 |
| PR の中でチェックを書き換える | 防ぐ | `pull_request_target` か ruleset の必須の workflow で、既定ブランチの定義を使う | 9 |
| 承認した人と時刻の偽装 | 防ぐ | 証跡の本文に書かず、GitHub の作成者と作成時刻で読む | 10 |

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | CD の実行が途中で落ちても、再実行でタグと GitHub Release のうち無いものだけを作る（今の `publish` の振る舞いを保つ） |
| 運用・保守性 | 証跡のチェックが落ちた理由は、チェックの結果の要約に 1 行で出る |
| 移行性 | 承認数を 0 にする変更は、証跡のチェックが必須チェックとして通ることを 1 回確かめた後に行う。戻すときは ruleset の承認数を 1 に戻す |
| セキュリティ | workflow の権限は必要な範囲（`contents: write` はタグと Release を作るジョブだけ、証跡のチェックは読み取りと status の書き込み）に限る |
