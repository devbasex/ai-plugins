## 目的

1 つのリポジトリで複数の開発の流れ（レーン）を同時に進めるとき、利用者が並列の計画を 1 度書いて 1 行で始められ、本番の配布がレーンどうしでぶつからない状態にする。11-02 の手作業（引継ぎ文書への決まりの書き写し・セッションの手での起動）と、配布の衝突（Pull Request 2420 を閉じた件）を繰り返さない。

## 前提

1. 統括役・名前つきのラッパー・`ndf-spawn`・`relay.py spawn/ls/attach/stop/restart` は #2346 のとおりに動く（v10.27.14）
2. 同時に流すプランの合計は 6 本まで（2026-09-25 の実測。8 コア・30 GB）
3. 承認ゲートは 2 つのまま増やさない。並行したレーンの本番の配布は、承認ゲート 2 の 1 回の承認へまとめる（`parallel-work.md` の「承認は承認ゲートでまとめる」）
4. Claude Code だけで動く（ラッパーが Claude Code だけのため）。ラッパーの外・tmux が無いときは、手で起動するためのコマンドを示して終わる
5. 本番の配布の中身は依頼の集合ではなく、develop に入ったコミットで決まる。依頼の有無によらず、承認したコミットまでに develop にある変更はすべて入る
6. レーンどうしは同じ `develop` へマージする。本番の配布は `develop` の先頭をまとめて出すため、配布の時点で `develop` にある他のレーンの変更も含む（承認資料にレーンごとの内訳を載せる）

- Codex で動かす並列（ラッパーが Claude Code だけのため）

## 用語

| 用語 | 意味 |
| --- | --- |
| 並列の計画 | 1 つのリポジトリで同時に進めるレーンの一覧と、レーンに共通の決まりを書いた 1 つの文書。オーガナイザーが読む。名前（計画名）を持つ |
| レーン | 並列の計画の下で、名前つきのラッパー 1 本が進める開発の流れ。最初の入力は開発ループかスプリントの 1 つ |
| オーガナイザー | `--parallel <計画名>` で起動した conductor の役割。レーンを起動・監視し、配布の依頼をまとめて本番の配布を 1 本にする。統括役（ラッパーの役）とは別 |
| 配布の依頼 | レーンが承認ゲート 2 の手前で、本番の配布をオーガナイザーへ頼む 1 件の依頼（DBOS のメッセージ） |

## 受け入れ条件

1. `issue-plan-strategy` が並列の計画を作る手順を持つ。並列の計画は、レーンごとに名前・最初の入力・触る場所・同時に流すプランの本数・始める条件（他のレーンへの依存）を決め、1 つの文書に書く
2. 並列の計画を作る手順が、レーンの数だけ引継ぎ文書を作る。レーンに共通の決まり（プランの本数の配分・触る場所・配布の担当）は並列の計画の 1 箇所に置き、引継ぎ文書は並列の計画を参照する（各文書へ写さない）。同じ名前の引継ぎ文書が既にあれば上書きせずに止める
3. 並列の計画をスクリプトが検査する。レーンの数が上限を超える・プランの本数の合計が 6 を超える・名前の形が違う・依存先が並列の計画に無いか循環する・触る場所が重なる（重なりは警告）を、統一 JSON レポートで返す。誤りがあれば終了コードは 0 以外
4. `/goal /ndf:development-workflow --parallel <計画名>` で起動したセッションがオーガナイザーになり、検査を通った並列の計画のレーンをすべて起動する（依存のあるレーンは依存先が止まってから）。各レーンは引継ぎ文書を読んで開発を始める。検査に誤りがあれば、レーンを 1 本も起動しない
5. オーガナイザーは、レーンの状態が変わる（承認待ち・止まった・配布の依頼）まで、スクリプトで待つ。手書きのループや前景の sleep で待たない
6. 並列の計画の下のレーンは、本番の配布を自分で行わず、オーガナイザーへ依頼する。**配布のために他のレーンを待たない。** 依頼が届いた時点で流れている配布が無ければ、オーガナイザーは直ちに配布を組む。配布の中身は依頼の集合ではなく、承認資料を作る時点の develop の SHA で決まる（`main..<SHA>`）。承認の答えを受けた時点で develop が提示した SHA より進んでいれば、加わった範囲を添えて同じ承認ゲート 2 を 1 回だけ出し直す（「新しい範囲で出す」「最初の範囲だけ出す」「差し戻す」）。出し直しの後に develop が進んでも、出すのは出し直しで承認した SHA である。develop へのマージは保留しない（レーンの開発版の配布と確認を止めない）。承認した SHA より後に develop へ入った変更・届いた依頼は次の配布になる（今の配布が終わった直後に組む）。範囲に入っていたレーンには、依頼の有無によらず配布済みと版を返し、そのレーンは本番を出し直さずに続きの工程（振り返り・まとめ）へ進む。並列の計画の外で動くループ・スプリントの配布の手順は変わらない
6a. レーンは配布の依頼を置いた後、答えを待たずに次の周回（スプリント）へ進む。配布待ちの周回の課題は次の周回の選定に入れない。答えが届いたら、レーンは周回の境で配布待ちの周回の残りの工程（リリース後テスト・振り返り・課題を閉じる・棚卸し）を流してから続ける。差し戻されたら、その周回を今の差し戻しの扱いで締める
6b. 承認した SHA をそのまま出せるよう、本番チャネルへの PR の規則を改める。main 宛の PR は「develop から出たものだけ」から「develop に含まれるコミットだけ」にし、head を `release/v<版>`（承認したコミット + 版を上げたコミット。先に develop へマージ済み）とする。`scripts/check-pr-base.sh`・`release-steps.py` の本番の PR・#815 の承認の照合・`AGENTS.md` の Git 運用ルール・`docs/versioning-and-distribution.md` を合わせて直す。版を上げたコミットを develop へ戻すときの版数の衝突は配布のステップが本番の版を取って解く
6c. 並列の計画の下では、承認ゲート 1（設計の承認）と承認ゲート 2 の問いはオーガナイザーだけが出す。レーンは AskUserQuestion で止まらない。設計の承認が要るとき、レーンはオーガナイザーへ依頼を送り、その課題を人の判断待ちへ移して残りの課題か次の周回へ進む（ループでないレーンは依頼の後に終わり、承認の後にオーガナイザーが起こし直す）。オーガナイザーは届いている設計の承認の依頼を 1 回の問いにまとめ、答えの時点で新しい依頼が届いていれば続けて問う。承認の後の操作（承認ラベル・設計 Pull Request のマージ・`loop answer`）はオーガナイザーが行い、その課題は次の周回の選定へ戻る。承認ゲートの外の問い（費用・取り消せない操作・人にしかできない操作）はレーンに残す
7. オーガナイザーのセッションは `NDF_RELAY_MAX_NAMED` に数えない。既定のままで、オーガナイザー 1 本とレーン 3 本が同時に動く
8. 計画名を指定して全レーンを止められる。1 本のレーンだけを止めるのは今の `relay.py stop <名前>` で行う
9. ラッパーの外・tmux が無いときは、オーガナイザーはレーンを起動せず、手で起動するためのコマンド（レーンごとの 1 行）を示して終わる
10. `relay.md` の `ndf-spawn` の節と用語集から、並列の計画の手順へ辿れる
11. オーガナイザーを起動し直すと、`.ndf/parallel/<計画名>/` の記録から続ける。起動済みのレーンを二重に起動せず、処理していない配布の依頼を取りこぼさない
12. 全レーンが止まり、処理していない配布の依頼が無ければ、オーガナイザーはレーンごとの結果（配布した版・止まった理由）を要約して終わる

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | オーガナイザーが止まっても、レーンは動き続ける。配布の依頼を置いたレーンは、結果が返るまで待つ（受け入れ条件 11 で再開する） |
| 性能・拡張性 | 同時に流すプランの合計は 6 本まで（前提 2）。レーンの数の上限は `NDF_RELAY_MAX_NAMED` に従う |
| 運用・保守性 | 検査・待ち・停止のスクリプトは統一 JSON レポートを返す。並列の計画と配布の依頼はメインディレクトリの `.ndf/parallel/<計画名>/` に置き、コミットしない |
| システム環境 | Claude Code とラッパー（relay.py）と tmux があるときだけ起動まで行う（前提 4） |

| 行わない | 統括役の起動の仕組みの作り直し、レーンの中の工程の変更（配布の依頼の分岐を除く）、別のマシンにまたがる並列 |

## 設計の手がかり（起票者が調べたこと）

設計の工程はこれを出発点にし、比べた結果を「決定の記録」へ書く。

| 論点 | 調べた事実 | 起票者の見立て |
| --- | --- | --- |
| 案の比較 | A: 新しい Skill（依頼の形）／B: 既存 Skill へ統合（S1）／C: オーガナイザーを置かず、計画の手順が `ndf-spawn` のブロックを並べて出すだけ | B。C は 11-02 の配布の衝突を防げない |
| オーガナイザーの居場所 | 端末で最初に打った `claude` のラッパーが統括役（`relay_lib/hub.py`）。上限の判定は `Hub.judge` の `now.count >= max_named()` だけで、統括役も数える | オーガナイザーは統括役のセッションで動かし、印（環境変数か登録簿の役割）を持つラッパーを数から外す |
| レーンの起動 | 応答の ` ```ndf-spawn <名前> ` のブロック（中身が最初の入力）か `relay.py spawn --name <名前> --json -- <入力>` | スクリプトから `relay.py spawn` を打つ（結果を JSON で受け取れる） |
| 監視 | `relay.py ls --json` が名前・状態（running / awaiting_approval / stopped）を返す。待つコマンドは無い | 状態が変わるか配布の依頼が届くまで戻らない待ちのコマンドを足す（`supervise.py wait` と同じ使い方） |
| 配布のまとめ | レーンのループの `pipeline` は開発版 → 承認ゲート 2 → 本番まで流す（`loop.md`）。11-02 は先に出したレーンが develop にある他のレーンの変更も出した | 並列の計画の下では、レーンは承認ゲート 2 の手前で依頼のファイル（メインディレクトリの `.ndf/parallel/<計画名>/`）を置いて待ち、オーガナイザーが 1 回の承認ゲート 2 で 1 本の本番を出し、レーンへ結果を返す |
| 置き場 | 引継ぎ文書は `.ndf/handoff/`（`handoff.md`）、ループの記録は `.ndf/loop/<名>/`。どちらもメインディレクトリに置きコミットしない | 並列の計画と配布の依頼は `.ndf/parallel/<計画名>/`、レーンの引継ぎ文書は今の名前（ループなら `loop-<名>.md`）のままにする |
| 語 | 「統括役」は relay.py のハブ（ラッパー）を指す。実行主体の 3 層は conductor → supervisor → worker | 「オーガナイザー」は並列の計画を受け持つ conductor の役割名として用語集へ足す。統括役と混ぜない |
