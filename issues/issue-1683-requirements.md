## 目的

- スプリント課題が閉じた後に本文を読めば、受け入れ条件のどれをリリース後テストで確かめたかが分かる状態にする
- 確かめていない受け入れ条件が残る課題は、`--with-verification` の経路では閉じずに残り、理由が結果に出る状態にする
- 工程表（課題の本文の `## 進行` のチェックリスト）に、その課題のモードで通らない工程が未チェックの行として残らない状態にする
- リリース後テストの表に課題へ結び付かない行（導入の確認など）が混ざっても、ほかの課題の判定が止まらない状態にする

## 前提

- 前提 1: 受け入れ条件の番号は、課題の本文の `## 受け入れ条件` の節にあるチェックボックスの行（`- [ ]` / `- [x]`）を上から数えた順番（1 から）とする。行の頭に書いた番号（`- [ ] 1. …`）があれば、それと一致するものとして扱う。取り消し線で差し替えた行（`- ~~…~~ → …`）はチェックボックスを持たないため数えない
- 前提 2: リリース後テストの表の `受け入れ条件` の列は、セルの頭に前提 1 の番号を `<番号>.` の形で書く（例 `2. 一覧は更新日時の降順で並ぶ`）。番号の無いセルの行は、どの受け入れ条件にも結び付かない行として扱う
- 前提 3: 課題の本文に `## 受け入れ条件` の節が無い、または節にチェックボックスが 0 個の課題は、今と同じく表の行の合否だけで閉じる条件 2 を判定する
- 前提 4: `--with-verification` を付けない経路（`light` など、リリース後テストを通らない経路）と `--record-pr 0` の経路は、本文を書き換えず、閉じる条件も今のままとする
- 前提 5: 他のリポジトリの課題（`<所有者>/<リポジトリ>#<番号>`）は、閉じる条件を同じ規則で判定するが、本文は書き換えない（共通原則 C5 の「他のリポジトリへ公開する」に当たるかの判断を、この課題に持ち込まない）
- 前提 6: `sprint-close.py` は閉じた課題を開き直さない。既に閉じた課題が条件を満たさないときは、結果に理由を載せて人へ戻す
- 前提 7: 工程表の行がどのモードで通るかの正本は `development-workflow` の `WF_STAGE_MATRIX` である。モードは `## 進行` の見出しの `モード:` の行から読む。モードが `—`（未記録）の課題は、今と同じく全工程の行を持つ

## 対象範囲

含む:
- リリース後テストの表のうち、`課題` の列が課題を指さない行（`—`・`PR 1869` など）を、表全体を読めなくする理由にせず飛ばす読み方（読む側で受けると決めた。書く側で禁じると、導入の確認のように課題を持たない検証を書く場所が無くなるため）
- `--with-verification` の閉じる条件に「本文の受け入れ条件のすべてに合格の行がある」を足すこと
- 閉じる条件を満たした課題の本文の受け入れ条件に、合格の行がある番号の印（`[x]`）を付けること
- 既に閉じていた課題が閉じる条件を満たさないとき、`already_closed` と区別できる結果にすること
- 工程表を、その課題のモードで通る工程の行（`WF_STAGE_MATRIX` で `R` か `C`）と、記録の済んだ行だけで書くこと
- `release-verification` の表の定め（`受け入れ条件` の列の番号・課題に結び付かない行の書き方）と、`progress-tracking` の「スプリントを閉じる」の閉じる条件と結果の表を、上の振る舞いに合わせること

含まない:
- 論点 (1)（本番のプランに閉じるステップを入れる）。#1870 で塞いだ
- 論点 (3)（コミットの件名の closing keywords で GitHub が先に閉じる経路を塞ぐ）。2026-10-03 以降に閉じた 60 件で再発が 0 件であり、先に閉じた課題も「既に閉じていた課題の判定」（受け入れ条件 7）で人へ戻るため、この課題では塞がない（Value 1）
- 工程表の「後片付け」の行が記録されないこと（`merged-steps.py` の後片付けが工程を記録しない）。工程表の別の欠けであり、閉じる条件とは別の経路である（未決の表）
- 受け入れ条件を確かめる手順そのもの（`release-verification` が何をどう確かめるか）の変更
- 既に閉じた課題（#1340・#1649・#1668・#1669・#1822・#1843・#1847・#1867・#1870・#1492 など）の本文をさかのぼって直すこと
- 他のリポジトリの課題の本文の書き換え（前提 5）

## 受け入れ条件

- [ ] 1. リリース後テストの表に、`課題` の列が `—` の行と `PR 1869` の行があっても、`#<番号>` の行を持つ課題の判定は、その 2 行が無い表と同じになる（PR #1887 の直す前の表で `sprint-close.py --record-pr 1887 --with-verification --dry-run` を打つと、#1867 が `already_closed`、#1492・#1870 が保留の行で `kept_open` になり、「条件と課題の対応が読めない」の行が出ない）
- [ ] 2. `課題` の列が課題を指す行が 1 行も無い表では、今と同じく全件が `kept_open`（条件と課題の対応が読めない）になる
- [ ] 3. 本文の `## 受け入れ条件` に 3 個のチェックボックスを持つ課題で、表に番号 1 と 2 の合格の行しか無いとき、`--with-verification` の結果はその課題を `kept_open` にし、`reason` に合格の行が無い番号（`3`）が載る。課題は閉じず、本文も変わらない
- [ ] 4. 同じ課題で表に番号 1〜3 の合格の行がそろうと、課題は `closed` になり、閉じた後の本文の `## 受け入れ条件` の 3 個のチェックボックスがすべて `[x]` になる
- [ ] 5. 4 の本文の書き換えで、`## 受け入れ条件` の節の外の内容と、節の中のチェックボックス以外の文字（取り消し線の行・説明の行）は 1 文字も変わらない
- [ ] 6. 同じ番号に合格の行と保留の行が両方あるときは、その番号を合格として扱わない（課題は `kept_open`、`reason` は今の「リリース後テストに合格でない条件がある（不合格・保留）」）
- [ ] 7. 既に閉じていた課題が閉じる条件 2 を満たさないとき、結果の `result` は `already_closed` でも `would_close` でもなく、`reason` に閉じているが条件を満たさないことと満たさない番号が載る。課題は開き直さない
- [ ] 8. 既に閉じていた課題が閉じる条件 2 を満たすときは、`already_closed` になり、本文の受け入れ条件の印が 4 と同じく付く
- [ ] 9. `--dry-run` では本文を書き換えず、結果の項目に印を付ける予定の番号が載る
- [ ] 10. 本文の書き換えが失敗した課題は `failed` になり、閉じない。結果の `cmd` にやり直すコマンドが載り、終了コードは 1 になる
- [ ] 11. `## 受け入れ条件` の節が無い課題・チェックボックスが 0 個の課題は、表の行の合否だけで判定され、本文は変わらない（前提 3）
