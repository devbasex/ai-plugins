# #2963 の設計の決定の記録

設計文書 [issue-2963-design.md](issue-2963-design.md) の決定である。番号の付いた語（RF1〜RF8・STD1・LIB1 など）は設計文書の「子 Issue の行」と「外部の調査」の表を指す。

## 決定の記録

### 決定 1: 判断を DBOS の外で確かめられるよう、判断の関数と耐久の層を判断のループでつなぎ、DBOS を起こさない実行器を同じループの別の呼び方にする

判断のループ（`lib/decide_loop.py`）は、判断の関数（状態と前の結果 → 次の手）と、手を実行する関数を受け、終わりの手が出るまで回す。
耐久の層は実行する関数に耐久ステップを渡し、テストはただの関数を渡す。ループの本体は 1 つなので、テストが通る経路と本番の経路は手の実行のしかただけが違う。
判断の関数は状態と入力だけで次の手を決めるため、耐久ワークフローに課される決定性の要件（STD1・STD2）も同じ形で満たす。

テスト用に別の実行器（判断の関数を回す第 2 のループ）を置く案は採らない。ループが 2 つになると、本番のループにだけある順序の誤りをテストが見逃す。
DBOS の関数をテストで回す勧め（PRD1）は、テストごとに DBOS を作り直す費用を払うため、判断のテストには使わず、耐久を通すことを確かめる代表のテストに限る。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: STD1 / STD2 / PRD1 / PRD2 / LIB5

根拠: Value 9 / Value 10（MVV 版 7）

### 決定 2: 判断の関数の純粋さを検査が名前で見分けられるよう、置き場のモジュールの名前を `_decide.py` で終える

判断の関数を置くモジュールは名前の末尾を `_decide.py` にし、構造の検査の規則 `decide-pure`（決定 6）が、そのモジュールの import に `durable`・`dbos`・プロセスとファイルを扱う部品が無いことを確かめる。
名前で決めると、子 Issue が判断のモジュールを足すたびに検査の一覧を書き足さずに済み、子 Issue どうしが一覧のファイルで重ならない。

モジュールの一覧を検査の側に持つ案は、子 Issue が並列に流れるときに 1 つのファイルを奪い合うため採らない。docstring の印で見分ける案は、印の付け忘れを検査が見つけられないため採らない。

根拠: Value 3 / Value 9（MVV 版 7）

### 決定 3: `engine`・`flow`・`queue` の輪をほどくため、耐久ワークフローを起こすのを `flow` だけにし、`engine` と `queue` は `flow` を読まない

今の `Engine.run` は関数の中で `flow` を読み、`queue` の `cmd_*` も関数の中で `flow` を読む（L5）。耐久ワークフローの始まりを `commands` から呼ぶ `flow` の関数へ移し、`engine` はステップの実行、`queue` はキューのファイルとコマンドの組み立てだけを持つ。
向きは `commands → flow → engine・queue → _decide のモジュール` の一方向になる。判断は `_decide` のモジュールにあり、どの層からも読める。

`flow` を `engine` に吸収して 1 つのモジュールにする案は、耐久の層と実行の層が 1 つに戻り、行数も 1,000 に近づくため採らない。

根拠: Value 9（MVV 版 7）

### 決定 4: 判断のテストが DBOS を import しないよう、判断のループを `durable.py` の外の新しいモジュールに置く

`lib/durable.py` は DBOS の包みで、構造の検査の `wrapped` の規則が `dbos` の import をこのモジュールだけに許す（I16）。判断のループを `durable.py` に置くと、判断のテストが `durable` を import し、DBOS の読み込みを払う。
判断のループは `durable` を import せず、耐久の層の側（`flow.py`・`parallel_run.py`）が `durable` と判断のループの両方を読んでつなぐ。

`durable.py` の側に置く案（#2990 の起票の推定）は、上の理由で採らない。`durable.py` が 500 行ちょうどで、足すと分割が要る点も同じ向きの理由である。

根拠: Value 9（MVV 版 7）

### 決定 5: 行数に合わせるためだけの分割をやめるため、構造の検査の行数の上限を 1,000 の安全網にし、300 行・500 行は設計の目安として確定仕様に残す

構造の検査は 1,000 行を超えるファイルだけを落とす。1,000 行を超える今の 3 本（`check-trigger.py` 1,101・`lib/claude_accounts.py` 1,153・`release-steps.py` 1,316）は例外リストに今の行数で残し、触って 1,000 行以下にしたら消す。
1,000 行以下になる 24 本の `lines` の例外は RF2 が消す。300 行・500 行は、新しく作るファイルと分け方を決めるときの目安として `docs/specifications/ndf-script-structure-criteria.md` に書き、検査では落とさない。
分け方の基準は責務と層の向きで、検査が見るのは遅延の輪（決定 6）・判断のモジュールの純粋さ（決定 2）・関数の長さと分岐の多さ（A0）である。組み直しの間の特別な扱いは置かない（1,000 行の内で責務で切る）。

500 行の上限を保って例外のラチェットを組み直しの間だけ緩める案は、組み直しの子 Issue ごとに例外の足し引きが要り、往復が残るため採らない。検査をやめる案は、極端に長いファイルを止める手段が無くなるため採らない。
1,000 は pylint の `max-module-lines` の既定（PRD3）で、#1142 の決定 18 の前に構造の検査が入れていた値でもある。A0 との受け持ちは、モジュールの行数をこの検査、関数の単位の大きさを A0 とし、同じ量を 2 つの検査で数えない。

- 作り方: 標準に倣う
- 比べた候補: PRD3

根拠: Value 3 / Value 10（MVV 版 7）

### 決定 6: 輪を作り直す手順に頼らず CI で止めるため、遅延の輪と判断の純粋さを構造の検査の規則にし、例外は組ごとに 1 ファイルにする

構造の検査に規則 `lazy-cycle` と `decide-pure` を足す。`lazy-cycle` は、最上位・関数の中の import と `importlib.import_module` の文字列の定数を辺にした強連結成分を数え、例外リストに無い組を落とす（関数の中の import を数える範囲は PRD4 に倣う。`if TYPE_CHECKING:` の中は実行時に読まないため数えない）。
今の 10 組（`docs/scripts-map/README.md` の L1〜L10）は例外リストに組ごとに 1 ファイルで載せ、L3・L7・L9（RF6a・RF6b）・L5（RF5a）・L10（RF7）はその子 Issue が輪をほどいて自分の項目を消す。残る L1・L2・L4・L6・L8 は 8 件の範囲の外で、項目の理由にそう書く。
今の `tests/test_import_cycles.py` が確かめる 2 組（I7〜I9）は、この規則が同じことを全体で確かめるため、規則へ移してテストを消す。C15 の「`docs/scripts-map/` を作り直して確かめる」は、地図を作るスクリプトがリポジトリに無い（`grep -rln 強連結 scripts/ plugins/ndf/scripts` は該当なし、2026-11-13）ため、この規則の結果で確かめる。

import-linter（LIB1）と grimp（LIB2）は対象がパッケージで、`lib/` の直下に並ぶモジュールを扱えないため採らない。pylint（LIB3）はスクリプトが実行時に足す検索経路をたどらず、依存も増えるため採らない。pydeps（LIB4）は図を描くツールで、例外つきで落とす検査を持たないため採らない。
例外を 1 つのファイルの一覧に持つ案は、輪をほどく子 Issue が並列に流れるときに同じファイルを奪い合うため採らない。

- 作り方: 自前で作る・標準に倣う
- 比べた候補: LIB1 / LIB2 / LIB3 / LIB4 / PRD4

根拠: Value 9 / Value 11（MVV 版 7）

### 決定 7: 解析の重複を除くため、1 回の実行の中で構文木を覚える部品を 2 本の検査で共有し、実行をまたぐ記憶と A0 の検査は含めない

`scripts/lib/parsed.py` が、パスごとに構文木を `functools.cache`（LIB6）で覚えて返す。構造の検査と契約の検査はこの部品から構文木を受け、`py_imports.imported` も構文木を受ける版を使う。
契約の検査は `limits_decl.references` を 1 回だけ呼び、結果を描画と違反の両方へ渡す。構造の検査の `py_body_key` は `copy.deepcopy` をやめ、注釈と名前を除いた鍵を走査で作る（今の 13.8 秒のうち、プロファイラの下で `deepcopy` が 9.9 秒を占める）。
共有した構文木は書き換えない。書き換えると後の規則の結果が変わる（I10）。

実行をまたいで結果を覚える案は #2965 の範囲である。A0 の検査（`check-ai-smells.py`）は別のエントリポイントで別のプロセスとして走るため、1 回の実行の中の共有に含められず、含めない（smells の決定 43 が #2996 に委ねた点の結論）。

- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB6

根拠: Value 2 / Value 11（MVV 版 7）

### 決定 10: 子 Issue の変更で直る見込みを確かめられるよう、bug は判断の関数へ移す関数の中の判断の誤りだけを割り当てる

子 Issue は判断を判断の関数へ移し、単体のテストで網羅する。移す関数の中にある判断の誤りは、その単体のテストで再現でき、同じ PR で直せる。実行の誤り（作業場所・プロセス・記録の書き漏らし）と手順書の誤りは、判断を移しても変わらないため割り当てない。
割り当てた Issue は、子 Issue の PR で再現の手順を 1 回通し、直った PR を添えて閉じる（E8）。

ファイルが重なる bug をすべて割り当てる案は、#1142 の頭の詳細設計と同じ理由（直る見込みの無い割り当てが Issue を閉じない）で採らない。

根拠: Value 7（MVV 版 7）

### 決定 12: 周の記録が実際のリリースと食い違わないよう、周の結果はステップの終了コードではなくリリースの事実から導く

周の結果の判断（`lib/sprint_loop_decide.py`）は、その周で出した版のタグとリリース記録の有無（リリースの事実）を入力に取り、完了・失敗・人へ戻したを返す。ステップの終了コードは「なぜ止まったか」の材料にだけ使う。
食い違いの原因が今の判定の構造にあるかは確かめていない（設計文書の「未確認のまま残ること」）。原因が別にあっても、結果を事実から導く形にすれば C23 の形の食い違いは生じない。

今の判定の分岐を直すだけの案は、原因を確かめるまで直す場所が決まらないため、事実から導く形を先に決める。

根拠: Value 7 / Value 13（MVV 版 7）

### 決定 13: 段階ごとの判断を単体で確かめるため、`release-steps.py` を 5 つの段階のモジュールに分け、エントリポイントは引数と振り分けだけを持つ

段階は提示（`stage_present`）・承認（`stage_approve`）・本番（`stage_production`）・CD の結果（`stage_cd`）・リリース後テスト（`stage_verify`）の 5 つで、今の 14 の副命令をどれか 1 つに振り分ける。`release_lib/` の今のモジュール（`included`・`materials`・`approval` ほか）は段階のモジュールから呼ばれる部品として残し、同じ処理を段階のモジュールに重ねて持たない。
副命令の振り分けの表は詳細設計の段が書く。K3（HTTP を `notify` へ移す）は `release-steps.py` を触るため RF8 の後に置く。

副命令ごとに 1 モジュールにする案は、14 のモジュールに同じ段階の部品の呼び出しが散るため採らない。

根拠: Value 9 / Value 11（MVV 版 7）

### 決定 14: 所要の比べ方をそろえるため、着手前と後の値を CI の JUnit の成果物から同じ集計で取る

テストの所要は、develop と子 Issue の PR の `pytest` のワークフローの JUnit の成果物から、対象のファイルの `testcase` の `time` の和で取る。並列数と分割の数は CI の設定でそろう。手元でテストを走らせる測り方は、`.ndf/project.json` の `test.ci.only` の宣言が止めるため使わない。
検査の所要（RF2・RF3）は、テストではなくエントリポイントの経過の秒なので手元で測る。

要求の検証手段にある `pytest --durations=0 -n 4` を手元で打つ案は、上の宣言と合わないため採らない。

根拠: Value 13（MVV 版 7）
