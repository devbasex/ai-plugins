## 具体例

2026-11-01、このリポジトリでは開発ループを 3 本並列で回すと決めた（Factory の `l20261031`・根本解決の `lroot`・開発フローの見直しの `lflow`。どれも同じリポジトリの develop へ入る）。そのとき決めたことは次の 4 つである。

- ループごとに選定の対象のマイルストーンを分ける
- 同時に流すプランは 1 本のループにつき 2 本までにする（全体テスト 6 本の同時実行が実測の上限）

## 目的

- 同じリポジトリで方針の違う開発ループを複数並べる運用（2026-11-01 の 3 本並列）を、Factory の利用者が Web から同じ形で行えるようにする
- 並行する実行どうしの取り合い（課題・版・触るファイル）と、手元の機械の資源の上限を、機械で守る
- 8 時間のジョブの中で conductor の context window が埋まっても、手元の relay.py と同じく区切りで起動し直して続けられるようにする
- 利用者の 3 つの原文に答える: 並行開発のオーケストレーションの構想を、決まっていない点を残さず仕様として定義する

## 前提

- 前提 1: この課題は設計の課題で、成果は Factory の確定仕様（`docs/specifications/ndf-factory-*.md`）へ入る設計文書と、その設計を実装する子の課題である。受け入れ条件は実装の後に観測する振る舞いとして書き、設計の承認（承認ゲート 1）で範囲を確かめる
- 前提 2: 実行の制御（`factory/api/src/runs/`）とランナー（`factory/runner/src/`）の既存の形（`docs/specifications/ndf-factory-runs-and-runner.md`・`ndf-factory-runs-state-and-data.md`）は変えずに足す。実行の枠の数の行（I34・I35）と開始のトランザクションはそのまま使う
- 前提 3: Factory は NDF のループの記録（`.ndf/loop/<名>/loop.json`）を直接読まず、ランナーが進捗の事象へ翻訳したものだけを読む（腐敗防止層の向き）
- 前提 4: NDF の止まる条件のうち、周回の途中で止まる `gate2_returned` はループの状態の `awaiting_approval` へ写し、`stopped` にしない。答え（承認）で `resume` が続く。ほかの条件（`user_stop`・`mvv_changed`・`same_failure`・`budget_laps`・`budget_usd`・`budget_hours`・`no_issue`・`outside_mvv`・`refused`）は `stopped` へ写し、条件と値を止まった理由に残す。`refused` は元の定義 1 の列挙に無いが、`loop.md` が周回の途中で止まる条件として持つため足す
- 前提 5: 利用者が画面から止めたループは `cancelled` にし、ランナーへは NDF の `loop stop` に当たる知らせを渡す。周回の実行が動いていれば、今の取り消し（`cancelSprintRun`）と同じ形で止める
- 前提 6: 「#2164 を含む NDF の版」は、#2164 を含んで出た最初の NDF の版数を下限とし、実行が使う NDF の版数（実行ジョブの指示が持つ版）と比べて決める。下限の版数は #2164 のリリースの後に決まり、設計はその版数を設定の値として持つ（コードに埋め込まない）
- 前提 7: `local` の形態の「次の周回を起こしてよいか」の承認は、承認の依頼（#2173）の新しい種類として画面と通知に並ぶ。今の 3 種類（ゲート 1・ゲート 2・判断）のどれかへ寄せるか新しい種類にするかは設計で決める（未決 1）
- 前提 8: 「低コストで常に動いているオーケストレーター」（利用者の 3 つ目の原文）は、常駐のプロセスとしては作らない。実行をまたぐ制御は今の呼ばれたときだけ動く実行の制御（事象と見回りで起きる）に置き、ジョブの中の区切りだけをランナー（ジョブの間だけ動く）に置く。常駐の費用は増えない
- 前提 9: 区間の上限の既定 20 とジョブの打ち切りの時間 8 時間は、今の手元の relay.py の運用の値に合わせた起票者の値で、設計の時点で実測（手元の relay の区間の数の分布）があれば置き換える
- 前提 10: 利用上限の検出は `claude -p` の結果（`result` の文と終了の形）から読む。`managed`・`byok` の形態では上限の切り替えをせず、API の失敗は今の失敗の扱いのまま

## 定義

### 1. 開発ループ（新しい集約）

**開発ループは、1 つのリポジトリの登録に属し、スプリントの実行を順に起こし続ける集約である。** 周回 1 回がスプリントの実行 1 本に当たる。課題の選定と周回の締めは、ランナーの中の NDF の開発ループ（`/ndf:development-workflow --loop`、`sprint-state.py loop`）がそのまま行い、Factory は選定の規則を持たない（腐敗防止層の向きを変えない）。

| 項目 | 定義 |
| --- | --- |
| 持つ値 | 名前（NDF のループ名の規則）・リポジトリの登録・選定の対象のマイルストーン（1 つ以上）・予算（周回の数・費用・時間。NDF の `loop.budget` と同じ 3 つ）・状態・今の周回の実行・止まった理由 |
| 状態 | `running`（周回の実行が動いている）→ `between_laps`（次の実行を起こす前）→ `awaiting_approval`（承認ゲート 2 で止まった）→ `stopped`（止まる条件に当たった）/ `cancelled`（利用者が止めた）。写し方は前提 4・5 |
| 周回の起こし方 | 実行の制御が、前の実行の終わり（`done` か「人へ戻した」）を受けて、同じループの次の実行を `START=loop` で起こす。指示に `LOOP_NAME` を足し、ランナーは `/ndf:development-workflow --loop <名前>` で conductor を起動する |
| 止まる条件 | NDF の止まる条件（`user_stop`・`mvv_changed`・`same_failure`・`budget_laps`・`budget_usd`・`budget_hours`・`no_issue`・`outside_mvv`・`gate2_returned`・`refused`）をランナーが進捗の事象 `loop.stopped`（条件と値）で送り、Factory はそれをループの状態へ写す。Factory が足す条件は「実行の枠が空かない」だけで、空くまで `between_laps` で待つ |
| 承認ゲート | 承認ゲート 1 で MVV 判定が「従う」以外の課題は、NDF の規則どおり人の判断待ちへ移り、周回は残りで続く。人の判断待ちの課題は承認の依頼（#2173）として画面に並ぶ。承認ゲート 2 は今の承認の依頼と同じで、答えで `resume` が続く |
| 実行の枠 | 枠を数えるのは動いている実行だけで、ループそのものは数えない。`between_laps` のループは枠を使わない |
| 同じリポジトリの複数のループ | 選定の対象のマイルストーンが重なるループは同じリポジトリで同時に動かせない（開始で断る）。重ならなければ並べてよい |

### 2. 同じリポジトリで並行する実行の調整

| 観点 | 定義 |
| --- | --- |
| 同じ課題の取り合い | 同じ課題を 2 つの動いている実行に入れない。開始の入力（課題の並び）と、ループの周回の選定の両方で、動いている実行が持つ課題を外す。実行の制御は動いている実行の課題の並びをランナーへ `EXCLUDE_ISSUES` で渡し、NDF の `loop exclude` で選定から外す |
| 版 | 版数は流す時点に NDF が決める（#2164）。同じリポジトリで並行する実行を許すのは、#2164 を含む NDF の版を使う実行だけで、それより古い版では同じリポジトリの実行を 1 本に絞る（前提 6） |
| 触るファイルの重なり | 重なりは止めずに、取り込み（base-sync）の時点で NDF が解く。解けずに止まった実行は `attention`（`reason: base_conflict`）を送り、画面に並ぶ |
| 本数の上限 | リポジトリごとの同時の実行の数はプランの表が決め（今の実行の枠）、宣言でそれより小さくできる |

### 3. 手元のランナーの同時実行数

| 項目 | 定義 |
| --- | --- |
| 上限 | ランナーは登録と心拍で `max_jobs`（同時に動かすジョブの数、既定 1）を申告し、サービスは動いているジョブがその数に達したランナーへ指示を渡さない |
| 資源 | ランナーは起動の時点の CPU の数とメモリから上限の目安を出し、申告がそれを超えれば警告する（2026-09-25 の実測: 8 コア・30 GB で全体テスト 6 本の同時実行が上限） |
| relay のホストとの関係 | #2346（relay.py が複数の claude セッションを統括する）のホストは、手元のランナーとして登録できる。そのときの `max_jobs` はホストの同時のセッションの上限である |

### 4. 見え方と承認

| 項目 | 定義 |
| --- | --- |
| ループの一覧 | 画面（#2172）にリポジトリごとのループの一覧を足す。列は名前・選定の対象・状態・周回の数・費用・予算の残り・最後に動いた時刻・止まった理由 |
| ループの詳細 | 周回ごとの実行（課題・結果・版・費用）と、人の判断待ちの課題の並び |
| 承認の依頼 | 承認の依頼（#2173）にループの名前と周回の番号を載せ、複数のループの依頼を 1 つの一覧で並べる |
| 操作 | 画面から、ループを始める・止める・予算を変える・人の判断待ちに答える（NDF の `loop answer`） |

### 5. 手元のランナーの自動実行（#2189 の未確認の扱い）

**確かめるまで、`local` の形態ではサービスがジョブを自動で起こさない。** 開発ループの周回の起こし方（定義 1）は、`local` の形態では「次の周回を起こしてよいか」を利用者に問う承認の依頼に置き換える。Anthropic に確かめた結果は #2189 の本文に記録し、認められればこの置き換えを外す。`managed`・`byok` の形態は今のまま自動で起こす。

### 6. ジョブの中の区切り（relay.py の役割をランナーへ）

**オーケストレーターの役割は 2 層に分ける。** 実行をまたぐ制御（開始・停止の知らせ・見回り・周回の起こし方）は今の実行の制御（呼ばれたときだけ動くサーバーレス。常駐のプロセスを持たない）が持つ。1 つのジョブの中の区切りは、手元の relay.py と同じ役割をランナーが持つ。

| 項目 | 定義 |
| --- | --- |
| 区切りの検出 | conductor の最後の `result` の文に `ndf-next` のブロックがあり、`- 結果:` の行が `判断が要る` でないとき、ランナーはそのジョブの中で次の区間を `claude -p <ブロックのコマンド>` で起動する |
| 区間の数 | 1 つのジョブの区間の上限を持ち（既定 20）、超えたら `job.finished`（`stopped`、理由 `section_limit`）で終える。打ち切りの時間（8 時間）はジョブ全体に掛かる |
| 事象 | 区間を起動するたびに `section.started`（区間の番号・コマンド）を送り、画面の詳細に区間の並びが出る |
| 状態の引き継ぎ | 区間は同じコンテナ・同じ作業場所で続くため、S3 への保存は要らない。保存はジョブの終わり（承認ゲート・終わり）だけのまま |
| 共通の部品 | `ndf-next` のブロックの読み方は NDF の relay.py（`relay_lib/mark.py`）と同じ規則にする。規則は NDF の契約（#2336）に宣言し、ランナーは形だけを写す（`plugins/` は `factory/` を参照しない） |

### 7. 利用上限での切り替え（`local` の形態）

| 項目 | 定義 |
| --- | --- |
| 検出 | conductor が利用上限で止まったことを、ランナーが `claude -p` の結果から読む |
| 扱い | `local` の形態では、ランナーはそのジョブを `job.finished`（`stopped`、理由 `usage_limit`、回復の時刻）で終え、実行の制御は回復の時刻の後に `resume` のジョブを起こす。複数のアカウントの切り替えは #2346 のホストが手元で行い、サービスはアカウントを知らない |
| `managed`・`byok` | 上限の切り替えは要らない。API の失敗は今の失敗の扱いのまま |

## 何が決まっていなかったか（確定仕様 `docs/specifications/ndf-factory-*.md` を 2026-11-01 に読んだ）

| 観点 | 今の仕様 | 足りなかったもの | 埋める定義 |
| --- | --- | --- | --- |
| 開発ループ | 開始のたびに課題の番号を 1〜20 件渡す。状態の保存に `.ndf/loop` は入る（I42） | ループを始める・止める・予算を持つ入口、周回、方針ごとにループを並べる形 | 1・4 |
| 同じリポジトリの並行 | 実行の枠がリポジトリごとの本数だけを数える | 同じ課題の取り合い、版の衝突、触るファイルの重なりの扱い | 2 |
| 手元のランナーの並行 | #2189 は登録・心拍・指示の受け取りだけ | 1 つのランナーが同時に動かすジョブの数 | 3 |
| 見え方と承認 | #2173 が承認の依頼を知らせる | 複数のループのどれが待っているかを並べて見る形 | 4 |
| ジョブの中の区切り | ランナーは 1 つのジョブで `claude -p` を 1 回だけ起動し、conductor の `ndf-next` を読まない（`factory/runner/src/` に語が無い。2026-11-02 に `grep -rn ndf-next factory/runner/src` が 0 件） | 手元の relay.py が持つ「区切りで claude を起動し直す」役割。ジョブは最大 8 時間で、その間に conductor の context window が埋まる | 6 |
| 利用上限での切り替え | `managed`（サービスの Bedrock）と `byok` は上限の切り替えが要らない | `local`（利用者の `claude` ログイン）で利用上限に当たったときの扱い。手元の relay.py はアカウントを替えて続ける（#1389） | 7 |
| 手元のランナーの自動実行 | #2189 の「未確認」: サービスが起動する自動実行が Claude のプラン（Pro・Max）の使い方として認められるか | 確かめるまでの扱い | 5 |

## 受け入れ条件

- [ ] 1. 利用者が画面から、リポジトリの登録ごとに開発ループを始め・止め・予算（周回の数・費用・時間）を変えられ、ループは周回ごとにスプリントの実行を `START=loop`・`LOOP_NAME` つきで起こし続ける。周回の課題の選定と締めはランナーの中の NDF の開発ループが行い、Factory のコードに選定の規則が無い
- [ ] 2. NDF の止まる条件（前提 4 の 10 個）はすべて進捗の事象 `loop.stopped`（条件と値）で届き、前提 4 の写し方どおりにループの状態（`stopped` か `awaiting_approval`）と止まった理由として画面に出る。`loop.stopped` が届かずにジョブが終わったループは、失敗を理由として `stopped` になる
- [ ] 3. 実行の枠が空くまで次の周回を起こさず、`between_laps` のループは枠を使わない（枠の数は動いている実行の数と等しいまま。I34 が崩れない）。枠が空いたら、待っていたループの次の周回が起きる
- [ ] 4. 選定の対象のマイルストーンが重なる 2 つのループを同じリポジトリで始めようとすると、後の方を理由（重なったマイルストーンと相手のループの名前）つきで断る。重ならない 2 つは始められる
- [ ] 5. 同じ課題が 2 つの動いている実行に入らないことを、開始の入力（課題の並びで動いている実行の課題を指すと断るか外す）とループの選定（`EXCLUDE_ISSUES` に動いている実行の課題が並ぶ）の両方で確かめるテストがある
- [ ] 6. #2164 を含まない NDF の版を使う実行は、同じリポジトリで 1 本に絞られる（2 本目の開始が理由つきで断られる）。下限の版数は設定の値で持つ
- [ ] 7. 取り込みで解けない衝突は `attention`（`reason: base_conflict`）として画面に並ぶ
- [ ] 8. リポジトリごとの同時の実行の数は、プランの表の値と、宣言した小さい方の値のうち小さい方で断られる
- [ ] 9. 手元のランナーは登録と心拍で `max_jobs`（既定 1）を申告し、サービスは動いているジョブがその数に達したランナーへ指示を渡さない
- [ ] 10. 手元のランナーは起動の時点の CPU の数とメモリから同時のジョブの数の目安を出し、申告が目安を超えると警告を出す（申告は受ける）
- [ ] 11. 画面にリポジトリごとのループの一覧（名前・選定の対象・状態・周回の数・費用・予算の残り・最後に動いた時刻・止まった理由）がある
- [ ] 12. 画面にループの詳細（周回ごとの実行の課題・結果・版・費用と、人の判断待ちの課題の並び）があり、人の判断待ちの課題に画面から答えると NDF の `loop answer` が働く
- [ ] 13. 承認の依頼にループの名前と周回の番号が載り、複数のループの承認の依頼が 1 つの一覧に並ぶ
- [ ] 14. `local` の形態では、次の周回を起こす前に利用者の承認を求め、承認されるまで次の実行を起こさない。Anthropic の確認の結果が #2189 にあり認められていれば、設定でこの置き換えを外せる。`managed`・`byok` は承認を挟まずに起こす
- [ ] 15. ランナーは conductor の最後の `result` の `ndf-next` のブロックを読み、`- 結果:` が `判断が要る` でないとき同じジョブの中で次の区間を起動する。`判断が要る` のときとブロックが無いときは起動しない。区間ごとに `section.started`（区間の番号・コマンド）が届く
- [ ] 16. 区間の数が上限（既定 20）を超えたジョブは `job.finished`（`stopped`、理由 `section_limit`）で終わる。打ち切りの時間（8 時間）は区間の合計に掛かる
- [ ] 17. `ndf-next` のブロックの読み方の規則は NDF の契約（#2336 の宣言）にあり、ランナーの読み方と NDF の relay.py（`relay_lib/mark.py`）の読み方が同じ入力で同じ答えを返すことを確かめるテストがある。`plugins/` は `factory/` を参照しない（`python3 scripts/check-service-boundary.py` が通る）
- [ ] 18. `local` の形態で利用上限に当たったジョブは `job.finished`（`stopped`、理由 `usage_limit`、回復の時刻）で終わり、実行の制御が回復の時刻の後に `resume` のジョブを起こす
- [ ] 19. `managed`・`byok` の形態では `usage_limit` の扱いをせず、API の失敗は今の失敗の扱いのまま（既存のテストが通る）
- [ ] 20. 進捗の事象と実行ジョブの指示の追加（`loop.stopped`・`section.started`・`LOOP_NAME`・`EXCLUDE_ISSUES`・`START=loop`・`max_jobs`）は `factory/contracts/` の定義と生成した型にあり、契約の検査が通る
- [ ] 21. 既存の開始の入口（課題の番号を 1〜20 件渡すスプリントの実行）の振る舞いは変わらない（既存の Factory のテストが通る）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 可用性 | ループの次の周回は、実行の制御のどの処理が途中で止まっても、見回りか知らせの再送で同じ結果へやり直せる（1 つの周回の実行を 2 本起こさない） |
| 性能・拡張性 | 常駐のプロセスを足さない（前提 8）。手元のランナーの同時のジョブの数は `max_jobs` を上限とする |
| 運用・保守性 | ループの状態と止まった理由、区間の並び、`usage_limit` の回復の時刻が画面から読める |
| 移行性 | 既存のスプリントの実行と実行ジョブの指示・進捗の事象は互換のまま足す（足す欄は省略できる）。既存のランナーの登録に `max_jobs` が無ければ 1 として扱う |
| セキュリティ | サービスは `local` の形態のアカウントと認証を知らない（アカウントの切り替えは手元で行う）。ループの操作は、そのリポジトリの登録を持つアカウントだけができる |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。Factory の API にループの入口を足し、進捗の事象・実行ジョブの指示・ランナーの登録と心拍に欄を足す。どれも足すだけで、既存の欄は変えない（互換あり） |
| データ | 開発ループの集約の表（または行）を足す。既存の実行・実行ジョブ・枠の行の形は変えない |
| 既存の振る舞い | ランナーが 1 つのジョブで `claude -p` を複数回起動するようになる（`ndf-next` があるとき）。`local` の形態で利用上限に当たったジョブの終わり方が `failed` から `stopped`（`usage_limit`）に変わる |
