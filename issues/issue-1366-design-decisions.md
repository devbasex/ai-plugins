# #1366: 決定の記録・テスト設計・未確認のまま残ること

設計の本体は `issues/issue-1366-design.md` にある。この文書は、その設計で選んだ結論と理由、受け入れ条件と不変条件の確かめ方、
確かめられなかったことを持つ。

## 決定の記録

### 決定 1: 宣言は本文 `.ndf/mvv.md` と履歴 `.ndf/mvv.json` の 2 ファイルにする

本文は人が読み、利用者との対話で直す対象なので、Markdown のまま置く。承認の記録（版・sha256・日時・承認者・照合）は機械が読んで
一致を判定するため、スキーマで検証できる JSON に置く。本文を JSON に入れると人が読めず、JSON の値を Markdown の前付けに入れると
`lib/schema.py` の検証の外になる。

1 ファイルの前付けにする形は採らない。前付けを書き換えると本文の sha256 まで変わり、「本文が承認と一致するか」を本文だけで判定できない。

### 決定 2: 過去の版の本文は `mvv.json` の `versions[].body` に持つ

`show --version N` と差分の計算が宣言だけで完結する。git の履歴から取り出す形は、`approve` の後にコミットされていない版を取り出せず、
コミットの有無という宣言の外の条件に頼る。版ごとのファイルを `.ndf/` に並べる形は、現行の本文が 3 か所に増える。

現行の本文は `mvv.md` と最後の版の `body` の 2 か所にあるが、これは重複ではなく照合の対である。一致が「承認と一致する」の定義になる。

### 決定 3: NDF の共通原則は配布物のデータファイル 1 つに本文全体を置き、宣言に写さない

共通原則は NDF が持ち、プロジェクトが上書きも除外もできない（前提 8・AC19）。宣言に写すと、宣言を書き換えれば原則も書き換わる経路が
できる。コードの定数にすると、手順書（`references/project-mvv.md` ）と利用者が同じ文を指せない。データファイルなら、
`lib/project_mvv.py` が読んでプロンプトの先頭に置き、手順書はそのパスを指す。

置くのは上位の原則の 1 文だけでなく、承認済みの文面（`issues/ndf-common-principles.md` ）の全体である。優先順位・AI の行動の 2 択・
判断の範囲と記録・人と AI の対話・必ず承認が要る操作 C1〜C8 は、AI が判断のたびに使う基準そのものであり、1 文だけを渡すと
「何に照らして進めてよいか」を各地点が独自に補うことになる。判断の地点へ渡す順は 共通原則 → プロジェクト MVV → ミッション MVV で、
下位が上位を上書きできない優先順位と同じ並びにする。

`approve` と `vet` は本文に共通原則の写し（上位の原則の節・優先順位の節・`C<番号>` の行）があれば止める（I4）。写しを許すと、
改訂で共通原則が変わったときに古い写しが残り、C を 1 行外した写しを検出する検査が別に要る。

### 決定 4: エントリポイントは新しいスクリプト `project-mvv.py` 1 本にし、手順は `development-workflow` の参照に置く。Skill は新設しない

プロジェクト MVV は判断の基準であり、`project-decl.py` が持つ実行の宣言（テスト・ブランチ・配布の手段）とは読み手も書き手も違う。
`project-decl.py write` は解析の答えを宣言へ書く副命令で、利用者の承認を必須とする MVV の書き込みと同じ口に置くと、承認の要否が
副命令ごとに分かれる。既存の Skill へ統合する方針に従い、策定と改訂の手順は `development-workflow` の手順 0 から参照する
`references/project-mvv.md` に置く。

### 決定 5: 改訂は策定と同じ副命令の並び（`propose --current` → `vet --kind revision` → `approve --reason` ）で行い、契機は 3 つにする

改訂の入口（未決の 3 つ目）は、専用の副命令を作らず、策定の手順の分岐にする。改訂と策定の違いは「現行の本文と理由を候補の材料に
足すか」「版を 1 にするか N+1 にするか」だけで、`approve` が版と `changes` を宣言から計算できる。契機は `retrospective` の問い・
mvv-gate の連続した「判定できない」・利用者の指示の 3 つで、どれも同じ手順へ入る。

`retrospective` の中に改訂の手順を持つ形は採らない。振り返り以外の契機（mvv-gate・利用者の指示）から同じ手順へ入れなくなる。

### 決定 6: 承認は照合の記録の sha256 で縛る。「反する疑い」は承認できず、「判定できない」は人が引き受けたときだけ承認できる

`approve` は `project-mvv.jsonl` から、同じリポジトリ・同じ本文の sha256 の直近の照合を読む。照合を飛ばした承認と、照合の後に本文を
変えた承認は、どちらも sha256 が合わずに止まる。

優先順位（前提 9）は上位の原則を利用者の承認より上に置くため、「反する疑い」の本文は利用者が望んでも承認へ進めない。本文を直して
照合をやり直す。AI は共通原則を基準に判断するが、判断の結果として取れる行動は「進める」と「止めて人へ戻す」の 2 つだけである。
「判定できない」は後者に当たるので人へ戻し、利用者が引き受けると決めたときだけ `--accept-unknown` で承認し、その事実を版の
`vet.accepted_unknown` に残す。照合は本文を書き換えず、利用者の指示を退けない（I14）。止めて示すだけである。

### 決定 7: 傾向モードは、コミット数と課題数の両方が閾値（既定 100 件・20 件）に満たないときだけ選ぶ

課題を GitHub の外（Redmine・Notion）で持つプロジェクトは課題数が 0 でも git の履歴が育っている。どちらか一方で傾向モードにすると、
育った git の履歴を材料から落とす。100 件は、ai-plugins の最初の 100 コミットの件名のうち 52 件が `Fix` 、
17 件がマージで、判断を書いた件名がほとんど無い規模であることから置いた初期値である（境目の妥当性は未確認の表を見る）。閾値は
宣言の `settings` と引数で変える。

### 決定 8: 改訂の契機は「判定できない」の連続（初期値 3）と、改訂の兆候の閾値（覆し 3・「判定できない」の総数 5・流出不具合 3）の 2 つで立てる

1 回の「判定できない」は材料の不足でも起きる。2 回では同じ PR の再判定（修正の後にもう一度打つ）で届いてしまう。3 回続けば、別々の
判断で MVV が基準として働いていないと読める。回数は同じプロジェクト MVV の sha256 のもとでだけ数え、改訂で数え直す（I13）。

連続とは別に、人が AI の判断を覆した回数（承認ゲートで「従う」を退けた・「反する疑い」か「判定できない」を通した）・「判定できない」の
総数・流出不具合の件数を、現行の版の承認の日時より後の記録から数える（AC17）。覆しは MVV が人の判断と食い違った直接の証拠で、
流出不具合は検査の基準（MVV に照らした見送り）が甘かった証拠である。閾値は宣言の `settings.revise_after` で変え、初期値は
「同じ版のもとで 3 度食い違えば方向が違う」と読める 3 を覆しと流出不具合に、連続でない「判定できない」には材料の不足を見込んで 5 を置く。

**置き場と形。** 覆しだけを新しく書き、置き場は `~/.local/state/ndf/project-mvv-signals.jsonl` 、書き手は `mission-state.py gate`
である（`--by user` が同じ承認ゲートの直前の MVV 判定と食い違うときだけ 1 行）。「判定できない」は `mvv-gate.jsonl` に、流出不具合は
トリガーの記録（`new impl --escape-of` の `kind: escape` ）に既にあるため書き足さず、`project-mvv.py signals` が 3 つを読んで集計する。

`.ndf/mvv.json` に件数を持つ形は採らない。宣言を書くのは `approve` だけという集約の決まり（I1）が破れる。conductor が手で件数を
打つ形も採らない。判断の要らない集計を LLM にさせることになり、打ち忘れで数が欠ける。

### 決定 9: 判断の地点への配線は `lib/project_mvv.block` 1 つの出力を、各地点の既存の基準の節へ入れる

MVV の節は 共通原則の本文全体 → プロジェクト MVV（または「MVV なし」）→ 固定の指示（決定 17）の順で、mvv-gate はその後ろへ
ミッション MVV を続ける。cross-review では `reviewer_block` / `fixer_block` の後ろへ足す。今の `.ndf/review.json` の重点と同じ経路で、
担当・修正担当・最終スイープの見送りの返信の 3 か所へ同時に届く。cross-refactoring では `RF_MVV` を提案と計画のプロンプトへ、
supervise では judge のプロンプトへ足す。MVV の節を組む関数は 1 つで、cross 系で同じ役割の関数を分けない。

`--extra-instructions-file` で渡す形は採らない。担当のプロンプトにしか届かず、修正と見送りの判断に MVV が渡らない。`.ndf/review.json`
へ鍵を足す形も採らない。cross-refactoring と supervise はその宣言を読まない。

### 決定 10: 根拠の項目が返されなくても止めず、「根拠なし」と記録する

根拠の項目を求めるのは、あとから「どの版の何を根拠に判断したか」をたどるためで、判断を止めるためではない。欠けたら止める形にすると、
宣言を置いたリポジトリで既存のレビュー・リファクタリング・judge の流れが止まり、AC15 の「退行しない」に反する。欠けは「根拠なし」
として残り、`retrospective` がその数を見られる。

### 決定 11: ミッション MVV の矛盾の検出は `mission-state.py init` で行う

要求の AC12 は `new mission --mvv` を指すが、その引数は無い。ミッション MVV が状態へ入るのは `mission-state.py init --pace fast`
（`--milestone` か `--mvv` ）だけで、`new mission --pace fast` はその状態を読んで許可を判定する。矛盾はミッション MVV が入る所で
止めるのが最も早いため、`init` で `vet --kind mission` を呼び、「反する疑い」なら状態を書かずに箇所を示して止まる。`new mission
--pace fast` は、状態に残したプロジェクト MVV の参照が現行の宣言と一致するかだけを見る（I11）。AC12 の「`new mission --mvv` が止まる」
はこの 2 か所の組で満たす。

### 決定 12: `pace: fast` は、ミッション MVV が無くても承認済みのプロジェクト MVV で許可する

前提 2 は、ミッション MVV の無いミッションをプロジェクト MVV だけで判定するとしている。プロジェクト MVV も利用者が承認した基準で
あり、#1078 が求めた「利用者の事前の承認」を満たす。改訂で本文が変われば参照の sha256 が食い違い、次の承認ゲートで利用者の承認へ戻る
（前提 6）。

### 決定 13: 候補の生成と照合は `supervise_lib/claude.py` の `call_claude` を Tool なしで呼ぶ

利用上限の待ち・使用量の帳簿・打ち切りを既に持つ唯一の口である。mvv-gate の `ask` は同じ引数を書き写した実装で、新しい副命令が
それを写すと 3 つ目の写しになる。mvv-gate の `ask` を `call_claude` へ寄せることは、この変更の範囲の外として #1367 にした。

### 決定 14: cross-refactoring の見送りの理由（8 つ）は増やさず、根拠は `mvv_basis` の項目で持つ

見送りの理由は「この 8 つに限る」と決めている（#933 の AC9）。MVV に反する提案は、実装担当の計画の答え（`tier` ）と提案者の
`mvv_basis` として記録すれば、理由を足さなくてもたどれる。理由に `mvv` を足すと、理由の一覧を前提にした集計・計画の表・`CLAUDE.md`
の列挙のすべてを直すことになる。

### 決定 15: 宣言を変える PR は、MVV 判定で通さない

`.ndf/mvv.md` と `.ndf/mvv.json` を同じ PR で整合させて変えれば、`check` の一致の判定をくぐれる。LLM が MVV を書き換えて自分の
変更を通す経路（#1078 がハッシュで防いだもの）がプロジェクト MVV の側に開く。宣言の書き換えは共通原則の C7 に当たるため、
mvv-gate がそのパスを常に利用者へ戻す。これは `.ndf/pace.json` の `boundary_paths` ではなく mvv-gate の固定の検査に置く。
プロジェクトごとの宣言で外せてはならないためである。

### 決定 16: ai-plugins の宣言は設計 PR に含めず、実装の中で利用者の承認の後に書く

`.ndf/` への書き込みは「確認してから行う」操作で（要求の「境界」）、`approve` を打つのは利用者の承認の後である。設計 PR で宣言を
置くと、設計の承認と MVV の承認が 1 つの操作に混ざる。

実装では、承認済みの文面をそのまま書く。`.ndf/mvv.md` の本文は `issues/mvv-ai-plugins.md` の文面そのまま（「NDF の共通原則との
関係」「必ず人の承認が要る操作（ai-plugins に固有のもの）」の P1・「改訂」の節を含む。I4 が読むのは Mission / Vision / Value と
P の番号だけ）を `vet` と `approve` へ通す。共通原則は `issues/ndf-common-principles.md` の文面そのままを配布物の
`scripts/data/ndf-common-principles.md` へ置く（決定 3）。ai-plugins は NDF を作るプロジェクトであると同時に NDF を使うプロジェクトの
1 つでもあり、共通原則は配布物に、自分の MVV は `.ndf/` に持つ。文面を設計で言い換えない。承認したのは文面であり、言い換えると
承認と本文が食い違う。

### 決定 17: 判断を求めるプロンプトの固定の指示は 1 つの文面（`lib/project_mvv.contract` ）にし、AI の行動を「進める」「止めて人へ戻す」の 2 つに限る

共通原則は AI が判断のたびに使う基準で、レッドラインの照合だけに限らない（前提 9）。自動化を進めるには AI に判断させる必要があり、
一方で「人類のため」と称して指示と違う変更を加える経路は塞ぐ必要がある。両立させるのは、判断は AI が行い、結果として取れる行動は
2 つだけという契約で、これをどの地点のプロンプトにも同じ文面で置く（I16）。地点ごとに文面を書くと、地点によって 3 つ目の行動
（独自の修正）が紛れ込んでも検査で見つからない。

出力の形は既存のまま（`verdict` ・`decision` ・振り分けの `fix` / `waive` ・提案の採否）にし、`basis` だけ足す。どの出力も 2 つの
行動のどちらかに写像でき、既存の記録の読み手を変えずに済む。

共通原則を判断に使わせず、照合だけに限る形は採らない。人が見ている所でしか原則が効かず、判断の地点で MVV を渡す意味が薄れる。

### 決定 18: プロジェクト MVV の固有の操作は `## 必ず人の承認が要る操作` の `P<番号>` で書き、共通の C の行は持たない。照合が C を外す・優先順位を変える本文を止める

共通の C1〜C8 は配布物にあり（決定 3）、プロジェクトが足せるのは固有の操作だけである（AC19）。番号を `C` / `P` / `R` で分ければ、
根拠の項目（`C4` ・`P1` ・`R2` ）を見るだけでどの層のレッドラインかが分かり、判断の記録から 3 層を区別してたどれる。C を外している
本文は形の検査（I4。C の行を持てない）と意味の検査（I17。C の操作を承認なしで行えると書いていないか・優先順位を入れ替えていないか）の
両方で止め、箇所を示す。

`## レッドライン` の `R<番号>` に共通と固有を混ぜて書く形は採らない。ミッション MVV の R と区別できず、C を 1 行外した写しを
「R が 7 行しか無い」と数える以外に検出できない。C を宣言へ写して配布物との一致を検査する形も採らない。共通原則の改訂のたびに
すべてのプロジェクトの宣言が「承認と一致しない」になる。

### 決定 19: 改訂の兆候の記録は既存の記録から集計し、新しく書くのは覆しだけにする

決定 8 の置き場と形のとおり、「判定できない」と流出不具合は既に記録があり、覆しだけが無い。覆しは承認ゲートで人の答えが記録される
`mission-state.py gate` が、直前の MVV 判定と比べて書く（I18）。人の答えを記録する場所は 1 つで、そこで比べれば打ち忘れも二重の
記録も起きない。

`gate --by user` に `--outcome rejected` を足すのは、差し戻しが今は記録されないためである。「従う」を退けた回数は、差し戻しの記録が
無ければ数えられない。

### 決定 20: 人へ示す文面は、経緯・前提・根拠・選択肢の 4 節を先頭に持つ形を `propose` の出力と手順書の雛形の両方で決める

AI が人に判断や承認を求める提示（候補の提示・改訂の提案・承認ゲートの資料）は、初めて読む人が経緯と前提を知らなくても答えられる形に
する（AC18。共通原則の「人と AI の対話」）。`propose` が書く `candidates.md` と改訂案はスクリプトの出力なので、4 節を形として
検査できる（I19）。承認ゲートの資料は conductor が組むため、`references/project-mvv.md` に雛形（4 節と、内部の用語の言い換えか
説明を付ける決まり）を置き、手順が雛形を指す。

conductor の裁量に任せる形は採らない。文面の形は判断ではなく決まった手順であり、決まった手順はスクリプトか雛形に置く。

## テスト設計

| 受け入れ条件・不変条件 | どの振る舞いで縛るか | どう壊したら落ちるべきか |
| --- | --- | --- |
| AC1・I8 | `.ndf/` の無いリポジトリで `check` を打つと 2 と「プロジェクト MVV が無い」が出て、LLM と `gh` を呼ばず、ファイルが増えない | `check` が `gh` か LLM を呼ぶ、または状態ディレクトリへ書く |
