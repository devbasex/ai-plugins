# #1366: 決定の記録・テスト設計・未確認のまま残ること

設計の本体は `issues/issue-1366-design.md` にある。この文書は、その設計で選んだ結論と理由、受け入れ条件と不変条件の確かめ方、
確かめられなかったことを持つ。

## 決定の記録

### 決定 1: 宣言は本文 `.ndf/mvv.md` と履歴 `.ndf/mvv.json` の 2 ファイルにする

本文は人が読み、利用者との対話で直す対象なので、Markdown のまま置く。承認の記録（版・sha256・日時・承認者・照合）は機械が読んで
一致を判定するため、スキーマで検証できる JSON に置く。本文を JSON に入れると人が読めず、JSON の値を Markdown の前付けに入れると
`lib/schema.py` の検証の外になる。

1 ファイルの前付けにする形は採らない。前付けを書き換えると本文の sha256 まで変わり、「本文が承認と一致するか」を本文だけで判定できない。

### 決定 2: 過去の版の本文は `mvv.json` の `versions[].body` に持つ

`show --version N` と差分の計算が宣言だけで完結する。git の履歴から取り出す形は、`approve` の後にコミットされていない版を取り出せず、
コミットの有無という宣言の外の条件に頼る。版ごとのファイルを `.ndf/` に並べる形は、現行の本文が 3 か所に増える。

現行の本文は `mvv.md` と最後の版の `body` の 2 か所にあるが、これは重複ではなく照合の対である。一致が「承認と一致する」の定義になる。

### 決定 3: 上位の原則は配布物のデータファイル 1 つに置き、宣言に写さない

原則は NDF が持つ固定の文で、プロジェクトが変えてはならない（前提 8）。宣言に写すと、宣言を書き換えれば原則も書き換わる経路ができる。
コードの定数にすると、手順書（`references/project-mvv.md` ）と利用者が同じ文を指せない。データファイルなら、`lib/project_mvv.py` が
読んでプロンプトの先頭に置き、手順書はそのパスを指す。

`approve` は本文に「上位の原則」の節があれば止める（I4）。`issues/mvv-ai-plugins.md` のように案の段階で原則を並べて書いても、宣言には
入らない。

### 決定 4: エントリポイントは新しいスクリプト `project-mvv.py` 1 本にし、手順は `development-workflow` の参照に置く。Skill は新設しない

プロジェクト MVV は判断の基準であり、`project-decl.py` が持つ実行の宣言（テスト・ブランチ・配布の手段）とは読み手も書き手も違う。
`project-decl.py write` は解析の答えを宣言へ書く副命令で、利用者の承認を必須とする MVV の書き込みと同じ口に置くと、承認の要否が
副命令ごとに分かれる。既存の Skill へ統合する方針に従い、策定と改訂の手順は `development-workflow` の手順 0 から参照する
`references/project-mvv.md` に置く。

### 決定 5: 改訂は策定と同じ副命令の並び（`propose --current` → `vet --kind revision` → `approve --reason` ）で行い、契機は 3 つにする

改訂の入口（未決の 3 つ目）は、専用の副命令を作らず、策定の手順の分岐にする。改訂と策定の違いは「現行の本文と理由を候補の材料に
足すか」「版を 1 にするか N+1 にするか」だけで、`approve` が版と `changes` を宣言から計算できる。契機は `retrospective` の問い・
mvv-gate の連続した「判定できない」・利用者の指示の 3 つで、どれも同じ手順へ入る。

`retrospective` の中に改訂の手順を持つ形は採らない。振り返り以外の契機（mvv-gate・利用者の指示）から同じ手順へ入れなくなる。

### 決定 6: 承認は照合の記録の sha256 で縛る。「反する疑い」は承認できず、「判定できない」は人が引き受けたときだけ承認できる

`approve` は `project-mvv.jsonl` から、同じリポジトリ・同じ本文の sha256 の直近の照合を読む。照合を飛ばした承認と、照合の後に本文を
変えた承認は、どちらも sha256 が合わずに止まる。

序列（前提 9）は上位の原則を利用者の承認より上に置くため、「反する疑い」の本文は利用者が望んでも承認へ進めない。本文を直して照合を
やり直す。一方で機械は原則を判断しないため、「判定できない」は人へ戻し、利用者が引き受けると決めたときだけ `--accept-unknown` で
承認し、その事実を版の `vet.accepted_unknown` に残す。照合は本文を書き換えず、利用者の指示を退けない（I14）。止めて示すだけである。

### 決定 7: 傾向モードは、コミット数と課題数の両方が閾値（既定 100 件・20 件）に満たないときだけ選ぶ

課題を GitHub の外（Redmine・Notion）で持つプロジェクトは課題数が 0 でも git の履歴が育っている。どちらか一方で傾向モードにすると、
育った git の履歴を材料から落とす。100 件は、ai-plugins の最初の 100 コミット（2026-04-21〜06-03）の件名のうち 52 件が `Fix` 、
17 件がマージで、判断を書いた件名がほとんど無い規模であることから置いた初期値である（境目の妥当性は未確認の表を見る）。閾値は
宣言の `settings` と引数で変える。

### 決定 8: 改訂を提案する「判定できない」の連続回数の初期値は 3 にする

1 回の「判定できない」は材料の不足でも起きる。2 回では同じ PR の再判定（修正の後にもう一度打つ）で届いてしまう。3 回続けば、別々の
判断で MVV が基準として働いていないと読める。回数は同じプロジェクト MVV の sha256 のもとでだけ数え、改訂で数え直す（I13）。

### 決定 9: 判断の地点への配線は `lib/project_mvv.block` 1 つの出力を、各地点の既存の基準の節へ入れる

cross-review では `reviewer_block` / `fixer_block` の後ろへ足す。今の `.ndf/review.json` の重点と同じ経路で、担当・修正担当・
最終スイープの見送りの返信の 3 か所へ同時に届く。cross-refactoring では `RF_MVV` を提案と計画のプロンプトへ、supervise では judge の
プロンプトへ足す。MVV の節を組む関数は 1 つで、cross 系で同じ役割の関数を分けない。

`--extra-instructions-file` で渡す形は採らない。担当のプロンプトにしか届かず、修正と見送りの判断に MVV が渡らない。`.ndf/review.json`
へ鍵を足す形も採らない。cross-refactoring と supervise はその宣言を読まない。

### 決定 10: 根拠の項目が返されなくても止めず、「根拠なし」と記録する

根拠の項目を求めるのは、あとから「どの版の何を根拠に判断したか」をたどるためで、判断を止めるためではない。欠けたら止める形にすると、
宣言を置いたリポジトリで既存のレビュー・リファクタリング・judge の流れが止まり、AC15 の「退行しない」に反する。欠けは「根拠なし」
として残り、`retrospective` がその数を見られる。

### 決定 11: ミッション MVV の矛盾の検出は `mission-state.py init` で行う

要求の AC12 は `new mission --mvv` を指すが、その引数は無い。ミッション MVV が状態へ入るのは `mission-state.py init --pace fast`
（`--milestone` か `--mvv` ）だけで、`new mission --pace fast` はその状態を読んで許可を判定する。矛盾はミッション MVV が入る所で
止めるのが最も早いため、`init` で `vet --kind mission` を呼び、「反する疑い」なら状態を書かずに箇所を示して止まる。`new mission
--pace fast` は、状態に残したプロジェクト MVV の参照が現行の宣言と一致するかだけを見る（I11）。AC12 の「`new mission --mvv` が止まる」
はこの 2 か所の組で満たす。

### 決定 12: `pace: fast` は、ミッション MVV が無くても承認済みのプロジェクト MVV で許可する

前提 2 は、ミッション MVV の無いミッションをプロジェクト MVV だけで判定するとしている。プロジェクト MVV も利用者が承認した基準で
あり、#1078 が求めた「利用者の事前の承認」を満たす。改訂で本文が変われば参照の sha256 が食い違い、次の承認ゲートで利用者の承認へ戻る
（前提 6）。

### 決定 13: 候補の生成と照合は `supervise_lib/claude.py` の `call_claude` を Tool なしで呼ぶ

利用上限の待ち・使用量の帳簿・打ち切りを既に持つ唯一の口である。mvv-gate の `ask` は同じ引数を書き写した実装で、新しい副命令が
それを写すと 3 つ目の写しになる。mvv-gate の `ask` を `call_claude` へ寄せることは、この変更の範囲の外として #1367 にした。

### 決定 14: cross-refactoring の見送りの理由（8 つ）は増やさず、根拠は `mvv_basis` の項目で持つ

見送りの理由は「この 8 つに限る」と決めている（#933 の AC9）。MVV に反する提案は、実装担当の計画の答え（`tier` ）と提案者の
`mvv_basis` として記録すれば、理由を足さなくてもたどれる。理由に `mvv` を足すと、理由の一覧を前提にした集計・計画の表・`CLAUDE.md`
の列挙のすべてを直すことになる。

### 決定 15: 宣言を変える PR は、MVV 判定で通さない

`.ndf/mvv.md` と `.ndf/mvv.json` を同じ PR で整合させて変えれば、`check` の一致の判定をくぐれる。LLM が MVV を書き換えて自分の
変更を通す経路（#1078 がハッシュで防いだもの）がプロジェクト MVV の側に開く。宣言の書き換えはレッドライン R7 に当たるため、
mvv-gate がそのパスを常に利用者へ戻す。これは `.ndf/pace.json` の `boundary_paths` ではなく mvv-gate の固定の検査に置く。
プロジェクトごとの宣言で外せてはならないためである。

### 決定 16: ai-plugins の宣言は設計 PR に含めず、実装の中で利用者の承認の後に書く

`.ndf/` への書き込みは「確認してから行う」操作で（要求の「境界」）、`approve` を打つのは利用者の承認の後である。設計 PR で宣言を
置くと、設計の承認と MVV の承認が 1 つの操作に混ざる。本文は `issues/mvv-ai-plugins.md` から「上位の原則」と「改訂」の節を除いた
ものを、手順どおりに `vet` と `approve` へ通す。
