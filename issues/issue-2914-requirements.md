# #2914: supervise.py の仕上げ（close）のプランがサブエージェントの頃の約 3 倍の費用になっている原因を調べて下げる

正は課題の本文（#2914）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 種類

調査

## 目的

supervisor の層をサブエージェント（Agent の `ndf:supervisor`）から supervise.py のプラン（`claude -p` の起動）へ移した後、仕上げのフェーズのプラン（close のプラン。確定仕様化・リリース後テスト・振り返り・棚卸し・期限が来たときの大整理と見直しのステップを持つ）だけが費用と所要時間の両方で重い。

- 費用: Opus 5.5 の単価にそろえた 1 本の費用の中央値は $8.2。34 本で $295 になる。設計（$11.0 → $7.1）と実装（$6.4 → $2.2）のプランは移行で安くなっている
- 所要時間: 1 本の中央値は 37.4 分、最大 64.9 分。利用者から「時間かかりすぎ」と指摘を受けた

close のプランの費用と所要時間をステップごとに分けて、どのステップが占めるかと、その原因を確かめる。そのうえで、1 本の費用と所要時間の中央値を、いまの半分以下へ下げる。

サブエージェントの頃の「仕上げ」フェーズ（1 回 $2.9）は取り込みとマージが中心で、いまの close のプランとは中身が違う。そのため、9 月の値との比較は目的の根拠にせず、いまの close のプラン同士の前後で比べる。

## 前提

- 前提 1: 「直す前」の基準は、2026-11-10 時点で記録が最後まで残っている close のプラン 9 本（`.ndf/loop/*/lap-*/close*/1-close-state/progress.jsonl`）とする。`kind: step` の行の `cost` と `seconds` を 1 本ごとに足した値の中央値は、費用 $8.21、所要時間 38.0 分である（集計の手段は「調べた事実」）。受け入れ条件 3・4 の閾値は、この半分の $4.10 と 19.0 分とする
- 前提 2: 「直した後」の値は、直した版をリリースした後に走った close のプランのうち、最初の 3 本以上の中央値とする。棚卸しの見直し（review）は期限が来たときだけ走るため、3 本の中に review を含む回と含まない回が混ざってよい
- 前提 3: 費用は `progress.jsonl` の `cost`（各ステップの `claude -p` の記録の費用）で測る。使用量の帳簿（`usage-report.py --ledger claude --by plan`）の close のプランの値と ±10% 以内で一致することを、受け入れ条件 1 の表を作るときに確かめる
- 前提 4: merge のステップ（確定仕様化の PR の継続的統合の待ち、中央値 15.0 分・費用 $0）の短縮は #2907・#2925 が扱う。この課題の受け入れ条件 4 は、それらがリリースされた後の値で判定してよい
- 前提 5: リリース後テスト（release-verify のステップ）は、回数を減らさない。出した版を実際に使って確かめることが、プロジェクトの判断の基準（Value 1）だからである。下げる手は、1 回の費用・所要時間か、ほかのステップとの並び方で取る

```python
import glob, json, statistics
rows = []
for p in sorted(glob.glob('.ndf/loop/*/lap-*/close*/1-close-state/progress.jsonl')):
    cost = sec = 0
    for line in open(p):
        d = json.loads(line)
        if d.get('kind') == 'step':
            cost += d.get('cost') or 0
            sec += d.get('seconds') or 0
    rows.append((p, cost, sec / 60))
print(len(rows), statistics.median(r[1] for r in rows), statistics.median(r[2] for r in rows))
```
