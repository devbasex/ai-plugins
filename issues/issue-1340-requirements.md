# #1340: cross-review を収束・異常終了の後に state を手で直さずにもう一度回せるようにし、振動検知と hook の止まり方を直す

## 依頼（原文）

> cross-review を、収束・異常終了の後にもう一度回すとき、state を手で書き換えずに済むようにする。あわせて、サンプルの会話の記録で見つかった cross-review と hook の止まり方を直す。（2026-09-27 利用者の指示。根拠は `issues/genericity-survey-2026-09-27.md` の G8）
>
> ### 今の状態（2026-09-27 に carmo-system-console の会話の記録から集めた）
>
> - `final=approved` の PR に差分を足して再実行すると `❌ state.json not found`。エージェントが state を `mv` で退避して init し直した。`final=error` のときは python で `d['final']=None` と書き換えた。利用者は自作のラッパー `crx.sh` に「reopen: final を外す」を常備していた（手の修正 6 件。`~/.claude/projects/-work-carmo-system-console/f4608e2e-...jsonl`、`61e6d7e8-...jsonl`）
> - 収束の直後に振動検知が中断を出す（2026-09-24、同じ出力の中で `✅ 収束` の直後に `❌ 振動検知`）。計 5 件
> - ホストが自分で直した場合も修正の記録の戻り値ファイルが要り、エージェントが JSON を手書きした（`❌ round 2 は修正必須の判定でしたが、修正の記録がありません`、4 件。#888 と近い）
> - hook の打ち切り: `worktree-guard.sh` が 5 秒、`hooks/pretooluse.py` が 10 秒の上限に対し 41 秒（2026-09-14 ほか）
> - worktree-guard の誤検知は #734 で扱う（調べた 10 件のうち 8 件が誤検知）
> - 認証の確認で止まった後、エージェントが `NDF_SKIP_AUTH_CHECK=1` を付けて確認を黙って外した（#461 と近い）
>
> ### 設計で決めること（原文）
>
> - 収束・異常終了の後にラウンドを足す正規の入口（`state.py reopen` など）
> - 振動検知を収束の判定の後に走らせない順序
> - hook の重い判定の打ち切りと、打ち切られたときの振る舞い
>
> ### 受け入れ条件（原文）
>
> - 収束した PR に差分を足して、state を手で書き換えずに cross-review をもう 1 ラウンド回せる
> - 収束と振動検知が同じ出力で矛盾しない
> - 上の hook の打ち切りが起きたコマンドの形で、hook が上限の中で終わる
>
> 関連: #734、#888、#461、#1263（完了した状態が残ると前回の結果を返す。同じ再開の入口に触る）

## 目的

- cross-review のレビューの状態ファイルの `final` が確定した後（`approved` / `error` / `oscillation` / ラウンドの上限）でも、利用者とエージェントがレビューの状態ファイルを手で書き換えず、決まった入口からラウンドを足せる
- cross-review の 1 回の出力の中で、終わり方が 1 つに決まる（収束と中断が並ばない）
- NDF の hook が、各ランタイムの hook の上限の中で終わる。重い判定が終わらないときの振る舞いが決まっていて、利用者から理由が読める

## 前提

- 前提 1: 「収束・異常終了の後」とは、レビューの状態ファイルの `final` が `null` 以外の値（`approved` / `error` / `oscillation` / ラウンドの上限）になった状態を指す。どの値からでも同じ入口でラウンドを足せる
- 前提 2: ラウンドを足すと、前のラウンドの履歴（`rounds`・投稿・指摘）は同じレビューの状態ファイルに残ったまま、次の番号のラウンドが始まる。番号は 1 へ戻らない
- 前提 3: ラウンドを足した後のラウンド数の上限は、足した時点から数え直す（分類ごとの既定の数か、`--max-rounds` で渡した数）。上限に達していたことで入口が拒まれない
- 前提 4: 正規の入口は、`state.py` の副命令（例: `reopen`）でも `init` の引数でもよい。形は設計が決める。どちらでも、`/ndf:cross-review` の手順（`drive.py` を通る経路）から打てる
- 前提 5: `drive.py` の耐久の記録が完了済みを返す問題は、cross-review の再開に関わる範囲だけをこの課題で扱う。`supervise.py run --from` で引数を変えて流し直す場合と cross-refactoring は #1263 が扱う
- 前提 6: 振動検知は、レビューの状態ファイルの `final` が確定しているときは判定せずに通す（`final` を書き換えない）。順序の保証は `drive.py` の経路だけでなく、副命令を手で順に打つ経路にも効かせる
- 前提 7: ホストが自分で直したときの修正の記録は、エージェントが JSON を手で書かずに作れる。記録の中身（コミット・返信・Resolve したスレッド）の契約は今の戻り値ファイルの形を変えない
- 前提 8: hook の打ち切りの対象は、NDF が配る hook のうち PreToolUse で重い判定（git を打つもの）を持つもの全部とする。Claude Code の `hook.py`、Codex の上限 5 秒の hook、agy の `worktree-guard.sh` を含む
- 前提 9: 重い判定が締め切りまでに終わらないとき、hook はその判定を飛ばして操作を通し、飛ばしたことを標準エラーへ 1 行残す（止めない）。書き込み先の誤りは #734 が実行後の差分の観測で拾うため、事前の判定を飛ばしても取りこぼしは残らない
- 前提 10: 打ち切りが起きたコマンドの形（会話の記録の 2026-09-14 ほか）は、設計の工程で記録から特定してテストの入力にする。特定できない形は、`git` の応答が遅いリポジトリ（大きいworktree・ネットワーク上のファイルシステム）を擬似的に作って代える

## 対象範囲

含む:
- レビューの状態ファイルの `final` が確定した後に、cross-review のラウンドを足す正規の入口と、その手順の記載（`SKILL.md` と `docs/`）
- `drive.py` から打ったときに、前回の結果を返さずに新しいラウンドへ進むこと（cross-review の範囲）
- 振動検知が収束（`final` の確定）の後に `final` を上書きしないこと
- ホストが自分で直したときに、修正の記録を手書きせずに作る入口
- NDF の PreToolUse の hook が上限の中で終わるための締め切りと、締め切りを過ぎたときの振る舞い（Claude Code・Codex・agy の hook）

含まない:
- worktree-guard の誤検知（#734 で扱った）
- 認証確認を `NDF_SKIP_AUTH_CHECK=1` で黙って外すこと（確認の中身は #461 が扱う。この課題では入口と振る舞いを変えない）
- `supervise.py run --from` の流し直しと cross-refactoring の完了済みの扱い（#1263）
- Codex / Kiro / agy がホストのときの修正の代わりの手順（#888 で扱った）
- 振動検知の判定の基準（重なりの割合 50%・3 つの一致）の変更
- hook の上限の値（各ランタイムの `timeout`）を上げて済ませること

| # | イベント | 引き金 | 失敗したとき | 順序の前提 |
| --- | --- | --- | --- | --- |
| E1 | cross-review の収束ループが終わり、`final` が確定した | `judge` の収束・`check-oscillation` の中断・`merge-fix` の `error`・ラウンドの上限 | — | — |
| E2 | 利用者かエージェントが PR に差分を足した | 修正の push | — | E1 |
| E3 | ラウンドを足す入口が打たれた | 利用者かエージェントが `/ndf:cross-review` をもう一度起動した | レビューの状態ファイルが無い・壊れている → 何が無いかを示して止まる（手で書き換える案内を出さない） | E1 |
| E4 | レビューの状態ファイルの `final` が外れ、ラウンドの上限が数え直された | E3 | 書き込みに失敗 → レビューの状態ファイルは E3 の前のまま残る | E3 |

| E6 | `judge` がラウンドを判定した（収束 / 修正へ） | E5 の結果の取り込み | 結果なし → 起動し直す（今の振る舞い） | E5 |

| E9 | PreToolUse の hook が操作を判定した | ツールの実行の前 | 重い判定が締め切りを過ぎた → 判定を飛ばして操作を通し、標準エラーへ 1 行残す | — |

## 用語

| 用語 | 意味 |
| --- | --- |
| レビューの状態ファイル | cross-review が `<worktree>/.cross_review/cross-review-pr<PR>-state.json` に置く、ラウンドの履歴と終わり方（`final`）の記録 |
| 修正の記録 | 修正の工程が作る戻り値ファイル（`fix-pr<PR>-result.json`）を `merge-fix` がレビューの状態ファイルへ取り込んだもの |
| hook の上限 | ランタイムの hook の定義（`hooks/*.json`）の `timeout`。過ぎるとランタイムが hook を打ち切る |

## 受け入れ条件

- [ ] 前提: `final=approved` のレビューの状態ファイルがある PR に差分を 1 コミット足した
      操作: `/ndf:cross-review <PR>` の手順どおりに打つ（レビューの状態ファイルを開かない・`mv` しない・python で書き換えない）
      結果: 次の番号のラウンド（前の最後のラウンドの番号 + 1）が始まり、レビュー担当の起動まで進む。前のラウンドの `rounds` の要素がそのまま残っている
- [ ] `final` が `error` / `oscillation` / ラウンドの上限のレビューの状態ファイルでも、上と同じ手順で次の番号のラウンドが始まる（値ごとに 1 件ずつ確かめる）
- [ ] 上の手順を `drive.py` を通して打ったとき、前回の結果（`収束ループが終わった（final=approved…）`）を返さずに新しいラウンドへ進む
- [ ] ラウンドの上限に達して終わったレビューの状態ファイルから足したとき、足した時点から既定の数（または `--max-rounds` の数）だけラウンドを回せる
- [ ] `final` が `null` のレビューの状態ファイルに対して入口を打つと、今の再開（`↻ 前回中断 state から再開`）と同じ振る舞いになる（退行しない）
- [ ] レビューの状態ファイルが無いときに入口を打つと、今の新規の経路と同じ振る舞いになる。レビューの状態ファイルが壊れている（JSON として読めない）ときは、パスと理由を示して終了コード 1 で止まり、手で書き換える案内を出さない
- [ ] 前提: `judge` が `final=approved` を書いたレビューの状態ファイル
      操作: `state.py check-oscillation <PR>` を打つ
      結果: `final` は `approved` のまま変わらず、出力に `振動検知 — … 中断` が出ず、終了コードは 4 以外である
- [ ] 収束したラウンドの 1 回の出力（`drive.py` の出力と、副命令を `SKILL.md` の順に打った出力のどちらも）に、`✅ … 収束` と `振動検知 — … 中断` が並ばない
- [ ] 前提: 前のラウンドが `changes_requested` で、ホストが自分で修正をコミットして push した
      操作: 修正の記録を作る入口を打ち、続けて `start-round` を打つ
      結果: エージェントが JSON を手で書かずに修正の記録ができ、`修正の記録がありません` で止まらずに次のラウンドが始まる。記録の形は今の戻り値ファイルの契約（`docs/04-contracts.md`）を満たす
- [ ] 修正の記録を作る入口は、コミットが送り先に無いとき・Resolve したと申告したスレッドが未解決のときに記録を作らず、理由を示して 0 以外で終わる（今の `start-round` の確認を飛ばす抜け道にならない）
- [ ] 打ち切りが起きたコマンドの形（前提 10）を入力にして、Claude Code の `hook.py`・Codex の hook・agy の `worktree-guard.sh` が、それぞれの hook の上限より短い時間で終わる。`git` の応答を遅くした擬似のリポジトリでも同じ
- [ ] 重い判定が締め切りを過ぎたとき、hook は操作を拒まずに終了コード 0 で終わり、標準エラーに飛ばした判定の名前を含む 1 行が出る
- [ ] 重い判定が締め切りの中で終わるとき、hook の判定（拒む / 通す）は変更の前と同じである（既存の hook のテストが通る）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | PreToolUse の hook の全体の所要が、各ランタイムの hook の上限より短い締め切りの中に収まる（締め切りの値は設計が決め、上限との差を設計に書く） |
| 運用・保守性 | ラウンドを足したことがレビューの状態ファイルに残る（いつ・どの `final` から足したか）。hook が判定を飛ばしたことが標準エラーに 1 行残る |
| 移行性 | 今の形のレビューの状態ファイル（`final` の値・`rounds` の形）をそのまま読める。移行のコマンドを要さない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | `state.py` に入口が 1 つ増える（副命令か `init` の引数）。修正の記録を作る入口が 1 つ増える。既存の副命令の引数と終了コードは変えない（`check-oscillation` は `final` が確定しているときの振る舞いだけが変わる） |
| データ | レビューの状態ファイルにラウンドを足した記録の鍵が増える。既存の鍵は変えない |
| 既存の振る舞い | `final` が確定したレビューの状態ファイルで `init` を打ったとき、履歴を捨てて新しい状態を書く振る舞いが変わる。hook は締め切りを過ぎた判定を飛ばす |
