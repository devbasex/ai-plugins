## 目的

- 打ち切り・例外・シグナル・強制終了で終わった実行の記録が、次の実行を「使用中」で止めない状態にする（今は #2321・#2285 のように、終わった時刻の無い持ち主の記録が寿命の窓の 24 時間だけ次の実行を断る）
- 並行する 2 つの実行（2 つの conductor・同じプランを流す 2 つのキュー）が同じ対象を同時に書き換えず、後から来た側が待つか止まるかを結果で知る状態にする（今は #2316 のように、互いに気づく手段が無い）
- 中断した実行を再開する手段を 1 つにし、`--from` の指定が耐久の記録の位置より常に優先される状態にする（今は #2325 のように、入口ごとにどちらが勝つかが違う）

- 前提 3: 持ち主の記録を取る入口は、契約の一覧（`plugins/ndf/contracts/`）の入口の行に持ち主の鍵の形が宣言されたものに限る。宣言の無い入口は持ち主の記録を取らない（#2335 の設計の移行性）。少なくとも、今持ち主の記録を書いている入口（cross-refactoring・cross-review・backlog-refinement の見直しの持ち主）と、キュー（`supervise.py queue`）・開発ループ（`supervise.py loop start`）に鍵を宣言する

## 用語

| 用語 | 意味 |
| --- | --- |
| 持ち主の記録 | 残る状態ごとに、作った実行が書く記録。実行の識別子・開始・最後に動いた時刻・終わった時刻、またはプロセス（pid と開始時刻）を持つ。起票時の本文の「lease」はこの記録と、それを取り合う排他を指す |
| 持ち主の鍵 | 持ち主の記録を取り合う単位。入口の契約が、解決した入力から作る形を宣言する（例 `cross-refactoring:pr=2301`） |
| 寿命の窓 | 持ち主の記録が終わっていなくても、最後に動いた時刻からこの時間を過ぎた実行を終わったとみなす長さ |
| 片付け | 状態の一覧に従い、持ち主の終わった残る状態を外し、残したものと理由を返す処理 |
| 耐久の記録 | 1 回の起動が持つ DBOS の SQLite のファイル（`~/.local/state/ndf/dbos/<種類>-<鍵>.sqlite`） |
| 実行の識別子 | 1 回の入口の実行に実行の核が振る識別子。記録・持ち主の記録・耐久の記録をつなぐ |
| 実行の核 | 入口・ステップが必ず通る共通の実行の仕組み |

## 受け入れ条件

- [ ] 1. 持ち主の鍵を宣言した入口が、正常・例外・SIGTERM・時間切れのどれで終わっても、持ち主の記録に終わった時刻が書かれる。同じ鍵で続けて起動した実行は「使用中」で止まらずに始まる。終わり方ごとのテストと、#2321 の再現の手順（cross-refactoring の着手前のテストを上限で打ち切った後に、同じプランのステップを `--from` で流し直す）で確かめる
- [ ] 1a. 時間切れで打ち切った実行の子のプロセス（テストの子が起こしたプロセスを含む）が、打ち切りの後に残らない。#2285 の再現の手順（着手前のテストの打ち切りの後に `ps` で子のプロセスを探す）で確かめる
- [ ] 2. SIGKILL で終わった実行の持ち主の記録を、同じ鍵の次の実行が死んだ持ち主として片付けてから取り、止まらない。pid が別のプロセスに再利用されていても（pid が一致し開始時刻が違う）死んだ持ち主として扱う
- [ ] 3. 持ち主の記録を返した後、その実行に結び付いた状態（片付けの状態の一覧の種類）が片付けられるか、残した理由が片付けの結果に出る。結び付いた状態のうち「持ち主が生きている」を理由に残るものが無い
- [ ] 3a. 片付けの状態の一覧に載らない一時の置き場の種類（#2243 の 5 種類）が、一覧に持ち主と寿命を持つか、残す理由を一覧に持つ。一覧に無い種類をテストが落とす
- [ ] 4. 前の版の NDF が状態ディレクトリの横に書いた持ち主の記録（`*.owner.json`）が残っていても、新しい版の実行はそれを読んで生死を判定し、死んでいれば止まらない
- [ ] 5. 同じ持ち主の鍵で 2 つの実行を同時に起動すると、後から来た実行は契約の宣言どおり、待ってから始めるか、`stopped`（終了コード 3）で止まる。結果の JSON に、待ったか止まったか・持ち主の実行の識別子・待った秒数が出る。2 つのプロセスを並べて起動するテストで確かめる
- [ ] 5a. 生きた持ち主がいる鍵を、2 つの実行が同時に取れない（持ち主の記録を読んでから書くまでが排他の中にある）
- [ ] 6. 2 つの conductor が同じ開発ループの周回、または同じキューの記録（done のファイル）を同時に流そうとすると、後から来た側の `supervise.py loop start`・`supervise.py queue` は、前の側が生きている間、続きとして流さず（`resumed` を返さず）、持ち主の実行の識別子を添えて止まるか待つ。#2316 の再現の手順で確かめる
- [ ] 7. 再開の入口（`supervise.py resume <実行の識別子> --from <ステップ>`）は、前の起動が強制終了で途中のまま残っていても、指定のステップから新しい実行の回で流し、前の途中の耐久ワークフローを子ごと止める。#2325 の再現の手順で確かめる
- [ ] 8. `--from` の無い再開は、耐久の記録の位置（済んだステップを流し直さない）から続ける
- [ ] 9. 旧い再開の形（前提 7）は、再開の入口と同じ結果を返し、標準エラーに新しい形を案内する。再開の位置を耐久の記録以外（drive の状態ファイルなど）から決める入口が無いことを、構造の検査（`scripts/check-script-structure.py`）が確かめる
- [ ] 10. 子の課題 18 件（下の「子の課題」の表）それぞれについて、再現の手順を 1 回通した結果（コマンドと出力の要点）と、閉じた（解消を確かめた）か残した（理由つき）かを、この課題の本文の表に記録する。閉じた課題には、確かめた結果へのリンクを添える
- [ ] 11. 持ち主の鍵を宣言していない入口の振る舞いが変わらない。全体テストが柱のマージの前後で通る
- [ ] 12. 持ち主の記録に、秘密（トークン・鍵・認証情報）の値が書かれない。持ち主の記録が持つのは実行の識別子・入口・鍵・時刻・pid と開始時刻・ホスト名だけである

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 持ち主の記録を取って返す段が、1 入口の起動に足す時間は、#2335 の上限 150 ms（核全体）の内側に収まる。柱の Pull Request で `--help` ではなく持ち主の鍵を宣言した入口の起動を前後で 10 回ずつ測り、差の中央値を本文に書く |
| 可用性 | 待つ上限に達した実行は、待ち続けずに `stopped` で返る（受け入れ条件 5）。上限の値は前提 5 |
| 運用・保守性 | 取った・待った・断った・片付けた・返したを、実行の記録（#2335 の P2）の `lease` の行に実行の識別子つきで書く |
| 移行性 | 移す対象: 持ち主の記録の置き場（状態ディレクトリの横 → `leases/`）と、旧い再開の形。並走: 旧い置き場の記録を読む（受け入れ条件 4）。旧い再開の形は次の正式版まで受ける（前提 7）。切り戻し: 持ち主の段の Pull Request と入口を移す Pull Request を、それぞれ revert すれば前の形へ戻る |
| セキュリティ | 受け入れ条件 12。認証・認可（C2）と秘密の扱い（C1）は変えない |
| システム環境 | 排他は既存の optional extras の `filelock`（`lib/locks.py`）を使う。extras が無い環境では、核が `stopped`（終了コード 69）と足りない extras の名前を返す（#2335 の受け入れ条件 15） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。再開の入口 `supervise.py resume` が増え、旧い再開の形は別名になる（前提 7）。持ち主がいるときの断りは `stopped`・終了コード 3 になる |
| データ | 変わる。持ち主の記録の置き場が `${NDF_STATE_DIR:-~/.local/state/ndf}/leases/` へ移る。旧い置き場の記録は読む（受け入れ条件 4）。利用者の `.ndf/` は変えない |
| 既存の振る舞い | 変わる。打ち切りの後の流し直しが止まらなくなる。並行する conductor・キューの後から来た側が、続きとして流さずに止まるか待つ |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | 持ち主の部品は `plugins/ndf/scripts/lib/` に置く。既定で働くため `experimental/` に置かない（`AGENTS.md` の「安定版と実験版」）。`factory/` を参照しない |
| コーディング規約 | `AGENTS.md` の「最小限のコード実装」と、外部コマンド（`ps`・シグナル・プロセスグループ）の挙動を書く前に実行して確かめる決まり |
| テスト戦略 | 持ち主の部品は単体テストで終わり方と取り合いを担保し、入口は契約のテストで担保する。子の課題は再現の手順で確かめる。`.md` の文言を照合するテストは書かない |

| 区分 | 内容 |
