## 目的

- 検査のプランを流し直したとき、drive が「前回の結果」や「時間の残っていない枠」で `ok` を返して承認ゲートまで進むことを無くす。承認する人が、検査が実際に回ったかを結果 JSON とリファクタリング計画から読めるようにする（#1263・#1944）
- 実装担当の CLI が仕事を終えた後の読み取り 1 回の拒否で、検査のプランが止まることを無くす（#1513）

## 前提

- 前提 1（#1263）: 完了した回の引数が今回と違うときは、知らせて止まらずに新しい実行の回を始める。止まると conductor が手で外す手順が残り、「人の手を止めない」に反するため
- 前提 2（#1263）: 比べる引数は「結果を変える init の引数」に限る。どれが当たるか（テストのコマンド・scope・予算・最終ゲートなど）の一覧は設計が決める。出力の置き場・表示だけを変える引数は比べない
- 前提 3（#1944）: 「使える時間が無い」は、計画の時点の使える時間が 0 分以下で、候補が 1 件以上あることを指す。使える時間が正で、どの候補も入らなかったときは今と同じく `ok` で返す（予算が小さい実行の正常な終わりを止めないため）。`ok` で返さないときは、drive の既存の中断（`status: stopped`）で返す
- 前提 4（#1513）: 「仕事を終えた」は、claude の `--output-format json` の出力が `"is_error": false` で、`subtype` が `success` であることで判定する。結果ファイルの有無は既存の完了の判定が見る（#1513 の再発では結果ファイルを書いていたのに `result_exists: false` と記録された。その食い違いは未決 2）
- 前提 5（全体）: 引数を記録していない古い完了の記録（この変更の前に作られたもの）は、head の比べ方と同じく前回の結果を返す側に倒し、比べられないと標準エラーへ知らせる

## 対象範囲

含む:
- cross-review と cross-refactoring の drive が、完了した回の結果を返してよいかを決める判定（#1263）
- cross-refactoring の再開で、止まっていた時間を経過時間から除く扱い。計画の前の中断を含む（#1944）
- cross-refactoring の計画で、使える時間が無いまま全候補を見送ったときの結果と、時間で見送った件数の出し方（#1944）
- 監視が claude の標準出力の `permission_denials` を致命と読む条件（#1513）

含まない:
- supervise のプランの進め方（`supervise.py` と `supervise_lib/`）。#1263 の現象は supervise から起きるが、判定は drive にある。配布の材料の漏れ（#1885 #1686 #1488）と誤判定（#1875 #1675）の主題が `supervise.py`・`supervise_lib/` を触るため、この主題は触らない
- cross-refactoring に `--reopen` を足すこと（#1263 の求めは引数と head の比較で満たせる）
- 中断した実行（完了していない回）の再開で引数を比べること（#648 #782 で閉じた）
- 提案の担当の監視の上限（90 秒）の決め方そのもの。止まっていた時間を除けば上限は計画の前の枠から求まり直す（受け入れ条件 1944-2）
- `permission_denials` 以外の致命のパターン（`is_error: true`・利用上限など）の変更

#### 何を見つけたか

`supervise.py run --from refactor` でステップの引数（`--round-test` など）を変えて流し直した。前回の cross-refactoring と cross-review の状態ファイルが共有の worktree（`$TMPDIR/ndf-worktrees/<owner>--<repo>/rf<PR>`・`pr<PR>`）に残っていた。すると drive は再開と判断し、前回の完了した結果をそのまま返した。

devbasex/devbase PR #301 の検査のプランでの観測（`progress.jsonl`）:

| 時刻 | ステップ | 秒 | 結果 |
| --- | --- | ---: | --- |
| 17:51:05 | refactor | 957.8 | 1 回目の完走（項目 0） |
| 17:56:52 | review | 347.0 | 1 回目の完走（final=approved） |
| 18:01:01 | refactor | 1.3 | 引数を変えた流し直し。前回の「項目 0・採用 0」をそのまま返した |
| 18:01:01 | review | 0.1 | 前回の「1 ラウンド・指摘 2」をそのまま返した |

どちらも `status: ok` で、プランはそのまま `test-all` → `ready` → 承認ゲート 2 まで進んだ。変えた引数は反映されず、反映しなかったという知らせも出なかった。worktreeを外して最初から通し直すと、提案 14 件のうち 11 件が採用された。

#### どこで見つけたか

devbasex/devbase PR #301（スプリント names-env）の検査のプラン（`supervise.py run --from refactor`、ndf 10.17.29）。drive の入口で、既存の状態ファイルを再開の材料として読む箇所。

#### なぜこの変更の範囲外なのか

devbase の変更（名前の規則の整理）とは関係しない。NDF の supervise / cross-refactoring / cross-review の再開判定の不具合である。#648 と #782 は「中断した実行を再開したとき引数が黙って無視される」を扱って閉じた。この課題は「**完了した**実行の状態が残っているとき、新しい実行が前回の結果を返す」形で、そちらの対象になっていない。

#### 直さないと何が起きるか

- 引数を直して検査を流し直しても前回の結果が返り、検査を通ったように見えて承認ゲート（本番へのマージの承認）まで進む。承認する人は、実際には検査が回っていないことに気づけない
- 回避には、共有の worktreeを手で外して最初から流し直す手順が要る

期待する振る舞い: 完了した状態の引数（テストのコマンド・scope・予算など）が今回の引数と違えば、前回の結果を返さずに新しく始める。少なくとも「前回の結果を返した」と知らせて止まる。

#### 修正レイヤー

**完了した実行の回を返してよいかの判定（cross 系で共有する `plugins/ndf/scripts/lib/loop_drive.py` の `rerun_reason` / `keep_finished`）。**
