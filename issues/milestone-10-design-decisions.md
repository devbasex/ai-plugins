# マイルストーン 10: ビジネス文書ワークフロー — 決定の記録

設計の本体は [milestone-10-design.md](milestone-10-design.md) にある。この文書は、9 件の
子 issue が「決めること」として残した論点への結論を持つ。

## 軸とモードの高さ

### 決定 1: 文書タイプ・出力の形・ドキュメンテーションシステムを別の軸にする

3 つは別々に変わる。同じ提案書がスライドとページの両方で存在し、同じスライドが Drive にも
Notion にも載る。1 つの軸へ潰すと値の数が 6 × 4 × 5 に膨らみ、システムを 1 つ足すたびに
すべての値を書き直すことになる。

`form-notion.md`（システム）と `form-slide.md`（形）を同じ並びに置く案は採らない。同じ表に
異なる軸の値が並ぶと、次に足す値がどちらの軸なのかを読み手が判断できない。

### 決定 2: `documentation` の高さを 5 にする

高さが使われるのは 1 か所で、**1 つの Pull Request が閉じる課題のモードが食い違ったときに、
どちらで検査するかを決める**（`_wf_collect_targets`）。

**根拠は工程の数ではない。** 工程表で `R` を数えると `standard` が 16 個、`documentation` は
14 個で、`documentation` が最多ではない。どちらの列も相手が持たない必須の工程を持つため、
数の大小では決まらない。

根拠は**混在が決定 7 の違反であること**にある。`documentation` と他のモードが混ざる
Pull Request は分割しなければならず、混在が起きている状態は分割し損ねた状態である。
`documentation` の列にしかない必須の工程は 2 つある（素材の収集と出典の確定 / 体裁レビュー）。
`standard` の側で検査すると、その 2 つは一度も求められず、**文書が混ざっていること自体が
表に出ない**。`documentation` の側で検査すれば、文書の工程の欠落として現れる。

高さを `standard` と同じ 4 に置く案は採らない。同じ高さでは先に与えた方が返り、どちらで
検査したかが呼び出しの順序で変わる。

### 決定 3: 高さを「モードを上げる」判断の根拠にしない

**`standard` から `documentation` への変更は、重くなったのではなく対象が変わったのである。**
本番コードを触ると分かった変更を文書のモードへ移すのは誤りで、高さの大小はその判断に使えない。
「途中でモードが変わったとき」の表へは、`documentation` と他のモードの間だけ**分割する**行を
置く。

## 判定と工程

### 決定 4: 判定の順序で `documentation` を 2 番目に置く

`operation` の次で `standard` より前に置く。**文書の中に公開インタフェースの説明が含まれても
`standard` にしないため**である。後ろに置くと、API の説明を書いた提案資料が `standard` に
当たり、テスト駆動と構造改善を課すことになる。

### 決定 5: リポジトリの説明文書は `documentation` に当たらない

判定を分けるのは**読み手**である。`README.md` と `docs/` はリポジトリを読む人へ向けたもので、
これまでどおり `light` として扱う。`documentation` の対象は、リポジトリの外にいる読み手へ渡す
ビジネス文書だけである。

**読み手ではなくファイルの拡張子で分ける案は採らない。** どちらも Markdown であり、区別が
つかない。

### 決定 6: 工程の行を 2 つ増やす

v10.3.0 で「工程表の行は増やさない」と決めた。**例外にするのは、どちらも判定の手段が既存の行と
違うためである。** 素材の収集は文書の外（数値の出所）を見て、体裁レビューは描画した画像を見る。
既存の行へ畳むと、文字を読む判定と描画を見る判定が同じ行に同居し、どちらの指摘なのかが混ざる。

### 決定 7: `documentation` と他のモードが混ざる Pull Request は分ける

判定の単位は Pull Request である。コードと提案資料が同じ差分に入る場合は、**文書の側を別の
Pull Request へ出す**。混ぜたまま高い方のモードで進める案は採らない。文書に構造改善を、
コードに体裁レビューを課すことになり、どちらの工程も空回りする。

### 決定 8: 開発を持たないリポジトリでも工程が通る

工程が求めるのは git と Pull Request だけである。本番コードが 1 行も無いリポジトリでも、
`worktree` `cross-review` `pr` `merged` はそのまま動く。**文書だけを置くリポジトリを対象外に
しない。**

## 承認

### 決定 9: 提出先を `.ndf/document.json` で宣言する

文書の提出先は git の外にあるため、`.ndf/worktree.json` の `production_branch` では指せない。
`.ndf/worktree.json` と `.ndf/projects.json` に続く 3 つ目の宣言ファイルとして分ける。
**1 つのファイルへまとめる案は採らない。** 作業ツリーの運用だけを使うリポジトリに、文書の
提出先の欄が現れる。

### 決定 10: 本番の系かどうかを `production` の真偽で表す

開発側は「マージ先が本番のチャネルか」で判定する。文書では提出先ごとに真偽を宣言する。
**社内の下書き共有が検証への提出、正式な提出・共有が本番への提出**にあたる。

**公開範囲（`visibility`）で代用しない。** 社内限りの稟議書も、決裁の場に出た時点で本番の系へ
届いている。公開範囲と、取り消せるかどうかは別の性質である。

### 決定 11: 制作物承認の提示物に描画した画像を必ず含める

**文字だけでは体裁を承認できない。** 枠からの文字あふれ・図の重なり・改ページの位置は、
ソースを読んでも分からない。承認する人が版面を見ないまま通すと、体裁レビューを置いた意味が
失われる。

### 決定 12: 取り消しの手段は共有の解除と版の差し戻しで、限界を必ず添える

**既に見た人には効かない。** 開発側の配布が「取得元をタグへ固定する」で戻せるのに対し、文書は
読まれた時点で戻せない。完了報告には手段と、この限界の両方を書く。

## 素材と事実確認

### 決定 13: 出所はソースの `## 出典` の節へ置く

**生成物から消えない場所を選ぶ。** frontmatter は生成の経路で落ち、別ファイルは生成物に
含まれない。読み手が確かめられなければ、出所を書いた意味が無い。

### 決定 14: 出所として残すのは、後から同じ値へ戻れる 4 項目である

URL だけでは戻れない。スプレッドシートは値が後から変わり、画面は絞り込みの条件で表示が変わる。

| 項目 | 何を書くか |
| --- | --- |
| 場所 | URL、またはシステムと識別子 |
| 位置 | シート名とセル範囲、クエリ、画面の絞り込み条件 |
| 時点 | 取得した日時 |
| 手段 | 画面 / クエリ / API のどれで取ったか |

### 決定 15: 出所の無い値を拒否せず、区別する語を付ける

拒否すると見込みと概算を書けなくなり、実在の文書の多くが通らない。代わりに**実績 / 見込み /
概算**の 3 語で区別し、**実績にだけ出所を必須にする**。見込みと概算には、代わりに前提を書く。

### 決定 16: 事実確認は `cross-review` のレビュワーが行う

書いた本人が確かめると、同じ思い込みで通る。**外部 AI のレビュワーが、出典の節と本文の値を
突き合わせる。** 新しい仕組みは作らず、レビューの観点として渡す。

### 決定 17: 取得の手段は作らない

`google-drive` が Drive の取得を持ち、`ndf:data-analyst` が SQL を持つ。`document-sources` が
決めるのは**出所の残し方だけ**である。取得の手段を持つと、システムが増えるたびにこの Skill が
太る。

### 決定 18: `documentation` の必須の段は 3 で、事実確認を追加で求める

文書には段階 1（変更箇所のテスト）と段階 2（全体テスト）に実行するものが無い。段階 3
（静的解析）にあたるのが**リンク・記法・行数の検査**である。`light` と `operation` が既に
同じ形を採っている。**段の並びは変えない。**

## 執筆

### 決定 19: 執筆の Skill を 1 個にし、タイプ別の中身を参照で持つ

タイプごとに Skill を分けると 6 個になる。`refactoring` の `lang-<言語>.md` と `design` の
領域別参照に前例がある。**1 つの Skill が対象のタイプの参照だけを読ませれば、タイプを足す
ときに他のファイルを変更しない。**

### 決定 20: スライドの区切りを見出しの階層で表す

`##` の見出し 1 つが 1 枚に対応する。**特定の変換器の記法（`---` など）を持ち込まない。**
記法を持ち込むと、その変換器を使わない経路でソースが読めなくなる。区切りの意味を見出しが
持てば、AI エージェントが組む経路でも同じソースを解釈できる。

### 決定 21: 1 枚 1 主張は執筆と体裁で分担する

**主張がいくつあるかは中身の話**で `document-drafting` が持ち、**1 枚に収まるかは版面の話**で
`design` の `layout-<出力の形>.md` が持つ。片方へ寄せると、版面を変えたときに主張の数まで
書き直すことになる。

### 決定 22: マニュアルの改訂は版の記録で扱う

初版と改訂で工程は変わらない。変わるのは**何を残すか**である。改訂では、変更点・改訂の日付・
前の版の所在を本文へ残す。**古い版を消さない。** 手順書は読み手が過去の手順で作業している
可能性があり、消すとどこが変わったのかを確かめられない。

## 生成と提出

### 決定 23: ソースは案件ごとのリポジトリの配下に置き、持たない文書は共通のリポジトリへ置く

案件リポジトリがあれば `docs/documents/<文書名>/` に置く。文書とコードが同じ差分に載る。
**案件リポジトリを持たない文書（全社説明資料・稟議・人事のガイドライン）には、文書用の
リポジトリを 1 つ持つ。** 置き場所を決めないまま進めると、同じ種類の文書が人ごとに別の場所へ
散る。

### 決定 24: 生成物を保存するかは、形ではなく経路で決まる

**非決定的な経路（AI エージェントが組む）では、ソースから生成物を復元できない。** 生成物こそが
成果物になるため保存する。決定的な経路（変換器）では、ソースと設定から同じものが出るため
保存は任意である。

Google スライドと Notion のページは git の外にあり、そちらは提出先そのものが保存にあたる。

### 決定 25: 生成の経路に既定を置かず、体裁設計が決める

変換器と AI エージェントのどちらが良いかは、出力の形と求める見栄えで変わる。**既定を置くと、
合わない対象へも同じ経路が選ばれる。** 代わりに、体裁設計の時点でどちらを使うかを決めて記録し、
その選択が「生成物を保存するか」の答えを決める。

### 決定 26: 公開範囲は設定した後に読み直して確かめる

**設定したことと、そう設定されていることは別である。** 提出の手順は、設定の操作の後に公開範囲を
取得し直して突き合わせる。社外へ出す提案資料と社内限りの稟議書で求める値が違うため、
`.ndf/document.json` の `visibility` を期待値にする。

### 決定 27: 索引への登録を提出の工程に含める

Notion 側のデータベースへ行を足さないと、本体が Drive にあっても見つけられない。**提出は
「置くこと」ではなく「読み手が辿れること」で完了する。** 宣言に `index` があるときだけ行い、
無ければ飛ばす。

## 体裁

### 決定 28: 体裁設計は `design` へ入れ、体裁レビューだけを新設する

`design` は既に「触る領域が読ませる参照を決める」構造を持つ。**出力の形が読ませる参照を
決める、で同じ形になる。** 一方、体裁レビューは判定に描画が要るため既存の行へ畳めない。
**新設するのは、判定の手段が違うものだけである。**

### 決定 29: 描画できない・画像を読めないときは止める

体裁レビューは制作物承認（取り消せない）の手前にある。**判定できないまま通すと、版面を
一度も見ないまま提出へ進む。** 止めたうえで、人が描画結果を見て承認する経路を残す。
**工程を飛ばす案は採らない。**

### 決定 30: 機械で見る項目と人が見る項目を分ける

| 見方 | 項目 |
| --- | --- |
| 機械で測る | 外部アセット参照の残り / 図の横幅 / ページ数 / 文字数の上限 |
| 人が画像を見る | 枠からの文字あふれ / 図の重なり / 改ページの位置 / 書体の代替 |

**既知の失敗のリストでは足りない。** リストは生成の経路ごとに違い、AI エージェントが組む
経路では列挙できない。だから描画して見る。

### 決定 31: 書体の代替は、描画の環境と配布先の環境を区別する

ヘッドレスの描画環境に日本語書体が無いために起きる欠けは、**成果物の欠陥ではない**。
配布先の環境で起きるかどうかを先に確かめ、描画環境だけの問題なら記録して先へ進む。

### 決定 32: `01-diagram-guide.md` の記述を移さず、軸を足す

既存のガイドは「GitHub がレンダリングするか」を根拠に使ってよい形式を決める。
`layout-<出力の形>.md` の根拠は「生成の経路が何を描画できるか」で、**根拠が違うため結論も
変わる**。移すと、本文へ埋める図の規約が版面の都合で書き換わる。

## システム

### 決定 33: 新設 4 個を 4 ランタイムすべてへ配る

`layout-review` を配らないランタイムを作る案は採らない。**配布の可否と、判定できないときの
倒し方は別である。** 画像を読めないランタイムでは決定 29 のとおり止まる。配らないと、
そのランタイムでは工程が存在しないことになり、止まったことにも気づけない。

### 決定 34: 既存の 2 実装を移植せず、知識として書き起こす

Confluence と SharePoint の実装は別のリポジトリの `.claude/skills/` にあり、自リポジトリ前提
（サイト名・組織名・認証情報の識別子）を含む。**`system-<名前>.md` が持つのは手順と落とし穴
だけで、スクリプトは持ち込まない。** `scripts/check-skill-repo-assumptions.py` が機械で検査する。

### 決定 35: `system-<名前>.md` は 8 項目を持つ

認証 / 取り込みの手段と取れないもの / 投稿の手段 / 本文の表現 / 版の扱い / 図の扱い /
描画して見る手段 / 既知の失敗。**システムを 1 つ足すときに他の `system-*.md` を変更しない。**

### 決定 36: MCP と REST のどちらを使うかはシステムごとに決める

Confluence では MCP が認証で失敗しやすく、REST を直接呼ぶ運用が要る。Google Drive は MCP が
動く。**共通の既定を置くと、合わないシステムで毎回失敗する。**

## 取り込み

### 決定 37: 取り込みの正規化を決定的にし、正本とは別のファイルへ置く

同じ対象を 2 回取り込んで差分が出ると、レビューできない。スライドごとに分ける・文単位で
改行する・ページ番号の連結を外すまでを正規化に含める。**正本の Markdown と取り込んだ
Markdown を同じファイルにしない。** どちらが正本か分からなくなる。

### 決定 38: 外部で編集されたものの追従は、人が気づいたときに実行する

`modifiedTime` を比較して自動で検知する案は採らない。**気づく仕組みを持つ前に、取り込みが
決定的であることを確かめる必要がある。** 差分が毎回出る状態で検知を回すと、変更が無くても
通知が出続ける。

### 決定 39: 取り込みでは画像を参照だけ残す

スライドの中の図は取り込みで取れない。**内容のレビューは差分に載ればよく、図そのものは
体裁レビューが描画して見る。** 別に取得する手段を作ると、決定 17（取得の手段を作らない）と
食い違う。
