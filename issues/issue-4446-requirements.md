## 何が起きたか

承認を求める前の「読み手役の確認」が、承認を問う直前になって初めて行われている。読み手役の確認とは、文書を書いた経緯を知らない AI に、承認する人などの立場で文書と質問の文を読ませ、判断を誤らせる文を挙げさせることである。そのため、通じない文は承認の直前に見つかり、承認を求めては変更を求められる往復が増えている。

今、読み手役の確認は次の 2 か所で、承認を問う直前に行っている。

- 開発を進めるレーン（並行して進める作業の 1 本）の conductor（人と対話するセッション）が、承認を問う前に読ませる
- 並列の計画を取りまとめるオーガナイザーが、まとめて出す質問の文を読ませる。加えて利用者の指示で、レーンが読ませた文書と承認資料も、問う前にもう一度読ませている

文書を書く工程「ドキュメント再構成」（文書を組み直して整える工程。Skill `document-rebuild`）にも「読み手役に読ませる」手順はある。ただし、この工程の担当の AI がほかの AI を起動できないと、「読ませていない」と報告して終わる。

2026-11-24 に、並列の計画で 4 本の Pull Request（PR）の承認を求めたときの実例:

| 承認を求めた PR | 承認を求めた回数 | 変更を求めた理由（読み手役が挙げた、判断を誤らせる文） |
| --- | --- | --- |
| 設計 PR [#4407](https://github.com/devbasex/ai-plugins/pull/4407)（工程「設計」「ドキュメント再構成」が設定の無いリポジトリで始まらない問題の設計。課題 [#4337](https://github.com/devbasex/ai-plugins/issues/4337)） | 5 回（承認は 5 回目） | 11・7・7・1・2 件。最後の 2 回は質問の文だけで、オーガナイザーが書き直した |
| 設計 PR [#4432](https://github.com/devbasex/ai-plugins/pull/4432)（課題 [#4068](https://github.com/devbasex/ai-plugins/issues/4068)・[#4199](https://github.com/devbasex/ai-plugins/issues/4199) の設計） | 1 回（変更要求を受けて直している） | 承認資料が「判断できない」とされた。要求仕様と設計書に 20 件 |
| 設計 PR [#4441](https://github.com/devbasex/ai-plugins/pull/4441)（課題 [#3955](https://github.com/devbasex/ai-plugins/issues/3955) の設計） | 2 回（2 回目を確認中） | 4 件（PR の本文が要求仕様の古いバージョンのまま、など） |
| PR [#4419](https://github.com/devbasex/ai-plugins/pull/4419)（バージョン 11.0.31 のリリース） | 1 回 | オーガナイザーが承認資料を 2 回直してから問うた |

1 回の確認に読み手役を 1〜2 回起動し、1 回あたり 6〜18 万 token を使う。変更を求められるたびに、レーンが直し、オーガナイザーが確かめ直すまで数十分待つ。

## 種類

機能追加（読み手役の確認を行う担当と時点を、承認を問う直前から文書を作る工程へ移す。今の手順書は承認を問う側が読ませると約束しており、その約束を変える）

## 今の姿

- 承認を問う側の手順: 承認や判断を求める質問を出す前に、質問を出す AI が読み手役に質問の文・承認資料・承認する PR の文書を読ませ、結果を記録する（[approval-request.md の「読み手役の確認」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/approval-request.md#読み手役の確認)）。オーガナイザーがまとめて出す質問の文は、オーガナイザーが読ませる
- 記録と止め方: 読ませた結果は `ndf records reading add` で記録する（課題 [#4285](https://github.com/devbasex/ai-plugins/issues/4285)、バージョン 11.0.30 で入った）。Claude Code では、hook（質問を出す直前に働く検査）が、確認の記録が無い質問と、確認の後に PR のコミットが変わった質問を止める。PR の本文や題だけが変わったときは、hook は止めない
- 文書を作る工程の手順: 工程「ドキュメント再構成」は、組み直した文書を読み手役に読ませる（[document-rebuild の「読み手役に読ませる」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/document-rebuild/SKILL.md#読み手役に読ませる)）。課題 #4337 の変更で、この工程を自動で流すときの担当の AI に限り、読み手役を起動してよくなった。その結果は工程の結果ファイルに残るが、上の記録には入らない

## 何を足すか・変えるか

| | 今 | 足した後 |
| --- | --- | --- |
| 読み手役に読ませる担当 | 承認を問う側（レーンの conductor、オーガナイザー） | 文書を作る工程（「ドキュメント再構成」と、リリースの承認資料を作るステップ） |
| 読ませる時点 | 承認を問う直前 | 文書・承認資料・質問の文を作った工程の中 |
| 承認を問う側がすること | 読み手役を起動して読ませ、記録してから問う | 記録があることを確かめて問う。読み手役は起動しない |
| 工程の担当がほかの AI を起動できないとき | 「読ませていない」と報告して終わり、承認の直前に読ませる | 「読ませていない」で終わる経路が無い |
| 工程が読ませた結果 | 工程の結果ファイルにだけ残る | 質問を止める hook が見る記録にも残る |

## 今の利用者への影響と互換

- 承認する人が受け取る承認資料と質問の文は、承認を求める時点で読み手役の確認を終えている。承認する人の操作は変わらない
- 質問を止める hook は今のまま働く。hook は、確認の記録が無い場合や、確認の後に PR のコミットが変わった場合に、今と同じく質問を止める。PR の本文や題だけが変わった場合は、承認を求める前の確認コマンドで見つける

## なぜ困るか

- 通じない文が承認の直前に初めて見つかる。承認する人は、読めない承認資料を受け取るか、直した資料を待つことになる
- 変更を求められるたびに、読み手役の起動（1 回 6〜18 万 token）と、レーンの直しとオーガナイザーの確かめ直し（数十分）がかかる
- レーンとオーガナイザーが承認の手前で読み手役の往復に時間を取られ、ほかのレーンの承認待ちが詰まる

## 目的

- 読み手役の確認を、文書を作る工程の中で終わらせる
- 承認ゲートに届いた時点で、文書・承認資料・質問の文が読み手役の確認を通っており、承認の直前に読み手役の往復が起きない状態にする

## 対象範囲

含む:
- 設計 PR に載る文書（要求仕様・設計書・詳細設計書・実装計画）の確認を、工程「ドキュメント再構成」で行うこと。どの文書を読み手役に読ませ、どれを担当が自分で読み直すかは、今の「読み手役に読ませる」の「対象」の行のまま
- 設計承認ゲートで示す承認資料（PR の本文）と質問の文の読み手役の確認を、承認を問う直前より前の工程で行うこと
- リリース承認ゲートで示す承認資料と質問の文の読み手役の確認を、リリースの工程の承認資料を作るステップで行うこと
- 工程が読ませた結果を、質問を止める hook が見る記録に残すこと
- 承認を問う側（レーンの conductor・オーガナイザー）の手順から、記録があるときに読み手役を起動し直す手順を外すこと

含まない:
- 読み手役の確認の中身（読み手の立場・渡すもの・合格の条件・立場ごとに 2 回までという回数）の変更
- 質問を止める hook の判定の条件の変更
- 承認ゲートの数と置く場所の変更
- 承認ゲートの外の質問（判断を求める質問）の読み手役の確認。今の手順のまま、質問を出す AI が読ませる
- この課題に着手する時機（計画のどのレーンで流すか）。リクエストの「レーンが空いたらすぐに実行」は計画の運用で扱う

## 前提

- 前提 1: 工程「ドキュメント再構成」を自動で流すときの担当の AI は、読み手役を起動してよい。課題 #4337 の設計（設計 PR [#4407](https://github.com/devbasex/ai-plugins/pull/4407)、2026-11-24 にマージ）の決定 5 で決まっている
- 前提 2: 読み手役の確認を終えた後に文書が変わったときは、変わった部分とその前後の段落だけを読ませ直す。今の「一部だけ読ませるとき」の決まりをそのまま使う

## 受け入れ条件

- [ ] 1. 設計のプランを流すと、工程「ドキュメント再構成」が、設計 PR に載る要求仕様・設計書・詳細設計書を読み手役に読ませる。読ませた結果（文書・立場・回・合否）が、質問を止める hook が見る記録に残る
- [ ] 2. 設計承認ゲートの承認資料（PR の本文）と質問の文は、承認を問う直前より前の工程で読み手役に読まれ、その結果が同じ記録に残る
- [ ] 3. 設計承認ゲートで、承認を問う側（レーンの conductor・オーガナイザー）は、記録があれば読み手役を起動せずに問う。問う直前に読み手役が起動されないことを、ゲートまでの実行の記録で確かめられる
- [ ] 4. リリース承認ゲートの承認資料と質問の文は、リリースの工程の承認資料を作るステップで読み手役に読まれ、その結果が同じ記録に残る。ゲートで問う直前に読み手役は起動されない
- [ ] 5. 工程の担当の AI がほかの AI を起動できないために「読み手役: 読ませていない」と報告して終わる経路が、工程「ドキュメント再構成」とリリースの承認資料を作るステップに無い
- [ ] 6. 工程で読ませた後に文書・承認資料・質問の文が変わったときは、変わった部分だけが読み手役に読ませ直され、記録が新しい内容で作り直される。変わっていないときは読ませ直さない
- [ ] 7. 質問を止める hook は今のまま働く。hook は、確認の記録が無い場合や、確認の後に PR のコミットが変わった場合に質問を止める（退行しない）。PR の本文や題だけが変わった場合は、承認を求める前の確認コマンドで見つける
- [ ] 8. 承認を問う側の手順書（`approval-request.md` の「読み手役の確認」と、オーガナイザーの手順）から、記録があるときに問う前にもう一度読ませる手順が無くなる

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 1 つの承認ゲートに向けて、同じ文書を同じ立場で読ませる回数は、文書を作る工程の中の最大 2 回だけで、承認の直前に足されない（文書が変わったときの読ませ直しを除く） |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わる。工程「ドキュメント再構成」の結果と、読み手役の記録（`ndf records reading`）を書く担い手が増える。互換の扱いは設計で決める |
| データ | 読み手役の記録を書く担い手に、文書を作る工程が加わる。既存の記録の移行は無い |
| 既存の振る舞い | 承認を問う側（レーンの conductor・オーガナイザー）が読み手役を起動する手順が無くなる。工程「ドキュメント再構成」と、リリースの承認資料を作るステップが読み手役を起動する |

## 用語

| 用語 | 意味 |
| --- | --- |
| 読み手役 | 文書と、想定した読み手の説明と、通じない文の 4 つの型だけを渡され、会話や経緯を知らずに読む AI。要点の言い直しと、読み手に通じない文の引用を返す |
| 承認資料 | 承認ゲートで、承認する人が判断するために読む資料。設計承認ゲートでは設計 PR の本文 |
| 設計承認ゲート | 設計 PR のマージの前に、人が設計を承認する場 |
| リリース承認ゲート | 変更を利用者へ届ける前に、人がリリースを承認する場 |
| オーガナイザー | 並列の計画を取りまとめ、各レーンの承認待ちを受けて人へ問う役割 |
