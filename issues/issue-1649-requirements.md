## 目的

- 全体テストで変更起因の失敗が出たとき、修正と取り消しの対象を「危険フラグの項目」ではなく「その失敗を起こした改善項目（原因の項目）」に向ける
- テストを壊していない改善項目を巻き込まず、原因の項目だけを直すか取り消して、最終ゲートを通す
- 同じ件は #1663 と #1634 の 2 回起きた。2 回とも conductor が手で原因を探して取り消している。この手作業をスクリプトへ移す（Value 4）

この主題は #1649（原因の項目の決め方）・#1668（構造検査を範囲テストへ入れる）・#1669（工程の 1 つとして起動したときの最終ゲートの打ち切り）の 3 つで 1 つにまとまる。設計文書は 1 本（`issues/issue-1649-design.md`）で 3 つを扱う。

## 前提

- 前提 1: 原因の項目は、次の 2 つの手がかりを順に使って機械で決める。修正担当の申告（`not_caused` やコミットの指名）は候補を絞る手がかりにだけ使い、決め手にしない（検証は git と実際のテストの実行から取る、という今の規則のとおり）
  1. 落ちたテストの出力（JUnit の失敗の本文）に現れるパスが、項目のコミットが変えたファイルと一致する
  2. 1 で決まらないときは、項目を 1 件ずつ外した木で落ちたテストを走らせ直し、通るようになる項目を原因とする
- 前提 2: 候補にするのは、取り消されていないすべての改善項目である（危険フラグの有無を問わない。範囲テストを通った `verified` の項目も含む）
- 前提 3: 2 つの手がかりのどちらでも決まらないとき（複数の項目の組み合わせで落ちる・走らせ直しが時間内に終わらない）は、候補のすべてを新しい順に 1 件ずつ取り消し、落ちたテストが通った時点で止める。今の「危険フラグの項目を新しい順に」を、候補を全項目へ広げた形にする
- 前提 4: 落ちたテストの見分け（フレーキー・既存失敗・変更起因）は今のまま変えない（`test_triage.classify`）。原因の項目を決めるのは、変更起因が 1 件以上あるときだけである
- 前提 5: 原因の項目の決め方は 1 つの関数に置き、検証の中の全体テスト（`converge.py`）と、最終ゲートへ寄せた危険フラグの取り消し（`gate_ci.revert_deferred`）と、#1669 の最終ゲートの打ち切りの取り消しが同じものを使う（Value 6）
- 前提 6: 原因を決めるための走らせ直しにかかる時間は、検証の修正の締め切りの内に数える。締め切りを過ぎたら前提 3 の取り消しへ進む

## 対象範囲

含む:
- 全体テスト（危険フラグで走らせたもの・最終ゲート）で変更起因の失敗が出たときに、原因の項目を決める処理
- 決めた原因の項目を、修正担当へ渡す対象と、取り消しの対象にする
- 原因の項目と、それを決めた手がかり（パスの一致 / 1 件ずつ外した走らせ直し / 決まらず）を状態ファイルと報告に残す
- 決まらなかったときの取り消しの対象を、危険フラグの項目から、取り消されていないすべての改善項目へ広げる

含まない:
- 構造検査を範囲テストへ入れること（#1668）
- 工程の 1 つとして起動したときの最終ゲートの打ち切りの扱い（#1669）
- 危険フラグ（D1〜D5）の立て方と、全体テストを走らせる時期
- 落ちたテストの見分け方（フレーキー・既存失敗・変更起因）
- 失敗したときに記録が残らない件（#1648）

## 用語

| 用語 | 意味 |
| --- | --- |
| 原因の項目 | 全体テストで変更起因として落ちたテストを、その変更で落とした改善項目。危険フラグの有無とは関係しない |
| 危険フラグ | 範囲テストでは覆えない変更（D1〜D5）。立てば全体テストを 1 度走らせる。**全体テストを走らせる理由であって、失敗の原因を指すものではない** |
| 変更起因 | 今の HEAD で再び落ち、着手前の HEAD では通るテスト |

## 受け入れ条件

- [ ] 1. 危険フラグの全体テストで変更起因の失敗が出て、落ちたテストの出力に、危険フラグの無い項目 X が変えたファイルのパスが現れるとき、X が原因の項目として状態ファイルに記録され、修正担当へ渡す項目に X が入る（危険フラグの項目だけが渡されない）
- [ ] 2. 1 の状態で締め切りを過ぎたとき、取り消されるのは X だけで、危険フラグの付いた項目は取り消されない（X を取り消した後に落ちたテストが通る場合）
- [ ] 3. 落ちたテストの出力にどの項目のパスも現れないとき、項目を 1 件ずつ外した木で落ちたテストを走らせ直し、通るようになった項目が原因の項目として記録される
- [ ] 4. 原因の項目が 2 件以上（#1634 の I-005・I-006 のように、別々のテストを別々の項目が落とす）のとき、すべてが原因の項目として記録され、それ以外の項目は取り消されない
- [ ] 5. 1・3 のどちらでも決まらないとき、取り消されていないすべての改善項目を新しい順に 1 件ずつ取り消し、落ちたテストが通った時点で止める。状態ファイルに「決まらず」と記録される
- [ ] 6. 最終ゲートへ寄せた危険フラグの項目の取り消し（全体テストを CI に任せる戦略）も、1〜5 と同じ決め方で対象を選ぶ
- [ ] 7. 原因の項目と、それを決めた手がかり（`path` / `isolate` / `undetermined` のいずれか）が、状態ファイルの全体テストの記録と `refactor.py report` の出力に出る
- [ ] 8. #1634 と #1663 の観測と同じ形（危険フラグの項目は落ちたテストに関わらず、危険フラグの無い項目が行数の上限か同名関数の検査を落とす）を再現するテストで、危険フラグの項目が 1 件も取り消されない
- [ ] 9. 退行しない: 変更起因の失敗が危険フラグの項目にあるとき（今の想定どおりの場合）の結果は今と同じ（その項目が直されるか取り消される）
- [ ] 10. 退行しない: フレーキーと既存失敗だけのときは、どの項目も取り消されない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | 1 件ずつ外した走らせ直しは、落ちたテストだけを走らせる（変更起因のファイルを走らせ直すコマンド）。回数は候補の件数以下で、修正の締め切りを過ぎたら打ち切って前提 3 へ進む |
| 運用・保守性 | 原因の項目を決める処理は 1 か所に置き、検証・最終ゲートの両方から呼ぶ |
