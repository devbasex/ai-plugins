## 目的

リリース後テストの計画（受け入れ条件の確認の表の「リリース後」の行と、リリースの承認資料のリリース後テスト）が、**その経路を動かすのはどのバージョンのコードか**を書かない。届け方そのもの（更新の処理・ラッパー・hook の入れ替え）を変える変更では、配った版の処理は、その版を動かした後の次のリリースで初めて動く。

11.0.8（#3812。ラッパーがカットポイントでプラグインを更新する処理を足した）のリリース承認資料は、リリース後テスト 2 を「11.0.7 のラッパーが 11.0.7 → 11.0.8 に更新する」前提で書いた。11.0.7 のラッパーは更新の処理を持たず、手で 2 コマンドを打ち、旧いラッパーのまま切り替え、`/exit` してから `claude` を打ち直した。同じ誤りの例は手順書と確定仕様にも入り、PR #3850 で直した。受け入れ条件 1 は 11.0.9 のリリースの後まで保留になった。

## 前提

- 前提 1: 経路を動かすバージョンは、配ったバージョン（このリリースで出したバージョン）と利用者の手元の旧いバージョン（リリースの前に利用者が動かしていたバージョン）の 2 つで足りる
- 前提 2: 次のリリースの後に確かめるのは、確かめる処理が今回のバージョンで初めて入り、今回のバージョンが動いている状態から（今回のバージョンを更新元として）動かす必要がある経路の条件だけである。旧いバージョンが経路を動かすことだけでは次へ回さない。旧いバージョンが既にその処理を持つなら、旧いバージョンから今回のバージョンへの更新はこのリリースの後に確かめられる（設計のクロスレビュー r1-3 で絞った。2026-11-19）
- 前提 3: 保留にした条件を次のスプリントで拾い直す工程は #2330 が扱い、この課題は扱わない

## 対象範囲

含む:
- `requirements-design` の受け入れ条件の確認の区分と、`release-verification` の計画に「動かすバージョン」を書く欄か規則を足す。届け方を変える変更では区分を「次のリリースの後」にできるようにする

含まない:
- 中継の手順書の例（PR #3850 で直した）
- 確認の区分の語（`マージ前` / `リリース後`）と、それを読み書きするコマンド（`ndf loop acceptance`）・結果 JSON の変更（起票者の推定 S2）
- 保留にした条件を後で拾い直す工程（#2330）

## 受け入れ条件

- [ ] 受け入れ条件の確認の表か、リリース後テストの計画で、各行の経路を動かすバージョン（配った版 / 利用者の手元の旧い版）を書く規則がある
- [ ] 配った版の次のリリースで初めて確かめられる条件を、保留の理由として最初から書ける
- [ ] `release-verification` が、前提 2 で次のリリースの後に確かめるとした条件を、このリリースの後のリリース後テストで保留（理由に動かすバージョンと確かめる時点）として記録し、記録の JSON を `not_run` にすると書く
