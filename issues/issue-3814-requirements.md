# #3814: 中継: 手順書の承認ゲートの守り（/exit・question.lock・wait-held）が 11 系の強制終了による切り替えと食い違う

正は課題の本文（#3814）で、この文書はそのコピーである。本文から作り直す。手で直さない。

## 何が起きたか

2026-11-18、11 系の中継の手順書（[relay.md](../plugins/ndf/skills/development-workflow/references/relay.md)）と実際のコードを突き合わせる洗い出しで、手順書の「承認ゲートを越えない守り」が 10 系の仕組みを書いたまま残っていると分かった。手順書を 11 系に合わせる設計の中で、コードの側にも欠けが見つかった。中継のラッパーは、子の claude が承認ゲートの質問（`AskUserQuestion`）を画面に出していても、回答を待たずに子を強制終了して次の会話へ移ることがある。2026-11-19 に偽の子で再現した。

困るのは、ラッパーの下で開発のループやレーンを回し、承認ゲートの質問に答える利用者とオーガナイザーである。答える前に質問が画面から消え、次の会話が始まる。

## 種類

不具合（手順書が既に約束している「質問の表示中は子の端末へ何も書かない」守りが、11 系のラッパーでポーリング 1 回分しか続かない。質問の hook がロックを取れないときに質問を拒否することと、回答の後に hook が質問のファイルを消すことは、その直しの従の部分）

## 今の姿

中継のラッパー（`ndf relay`）は、子の claude を擬似端末の下で動かし、0.5 秒ごとのポーリングで状態を集め、次の操作を 1 つ決めて実行する。判断は純粋な関数（`switch_decide.decide`）が持ち、ラッパーはファイルと画面と会話の記録を読んで値で渡すだけである（#2962）。

- **会話の切れ目での切り替え**: 子の応答が `ndf-next` のブロックで終わると、Stop の hook（`relay-marker`）が作業ディレクトリへマーカーのファイル（`next.json`）を書く。ラッパーは静かな時間（既定 5 秒）の後、子を強制終了（`terminate(force=True)`）して、ブロックを入力に次の会話（セグメント）を起動する。`/goal` が未達でも切り替える（#2438）
- **質問の受け渡し**: 子が `AskUserQuestion` を呼ぶと、PreToolUse の hook（`ask-forward`、[ask.py](../plugins/ndf/src/ndf/domains/hooks/guards/ask.py)）が質問のファイル（`question.json`）を書く。書くときはロック（`question.json.lock`）を最大 0.3 秒待ち、取れなければ書かずに通す（[limits.json](../plugins/ndf/contracts/limits.json) の `hook.ask-forward`）。ラッパーは質問のファイルを見つけると、質問を人かオーガナイザーへ転送する操作（`forward`。計画のレーンなら計画のリクエストへ載せる）を実行する
- **状態と記録**: ラッパーは今の状態（動いている `running`・待っている `waiting` など）と理由を状態のファイル（`wrapper.json`）に書き、一覧が読む。判断の変わり目は記録のファイル（`log.jsonl`）へ 1 行ずつ書く
- **承認待ちの文で終えた応答**: 子の応答が `AskUserQuestion` を呼ばずに「承認を待つ」文で終わると、本文の待ちを見分ける Stop の hook（`stop-wait`、[stop_wait.py](../plugins/ndf/src/ndf/domains/hooks/guards/stop_wait.py)）が、`AskUserQuestion` で問い直すよう変更を要求する。応答の種類を「本文の待ち」（`prose_wait`）と見分けるのは hook の入力を読む部品（`hooks/context.py`）で、11 系は `log.jsonl` に `prose_wait` の行を書かない
- **そのほかに子へ触る操作**: 文脈の量が上限を超えて静かなら、引継ぎを頼む 1 行と改行を子の端末へ書く（`handover`）。出力が止まりの秒を超えれば子を起動し直す（`restart`）。利用上限ならアカウントを替えて起動し直す（`account`）
- **手順書の守り**: [relay.md の「承認ゲートを越えない守り」](../plugins/ndf/skills/development-workflow/references/relay.md#承認ゲートを越えない守り)は、質問の表示中に端末へ書いた改行が選択肢 1 を決めるため、そのあいだは子の端末へ何も書かないと約束する。ただし、その実現の手段として 10 系の仕組み（`/exit` での切り替え・`question.lock`・`asked`・`wait-held.json`）を書いている

## 事象

手順書の守りは 10 系の仕組みを書いている。

- ラッパーが `/exit` と改行を書き、アイドルを待つ
- 質問の hook と同じロック（`question.lock`）の中で確かめ直す。ロックを 3 秒以内に取得できない質問の hook は、その質問を拒否する
- 質問が出た時刻を `asked` に書く
- 止めた直後の Stop を `wait-held.json` で見分ける

11 系のコードは違う。`wrapper.py` の `_stop_child` が `terminate(force=True)` で子を強制終了してから、次のセグメントを始める。`plugins/ndf/src` で `question.lock`・`wait-held`・`"asked"` を探しても 0 件だった。質問の表示中かどうかは `signals.has_question` で見ている。

そのうえ、ラッパーは質問を転送する操作（`forward`）の直後に質問のファイルを消す（`wrapper.py` の `_on_wait_like`）。次のポーリングからは質問が無いと読むため、マーカーが残っていれば質問の表示中でも子を強制終了して次のセグメントへ切り替え、文脈の量が上限を超えていれば引継ぎの 1 行と改行を子の端末へ書く（改行は質問の選択肢 1 を決める）。

| 再現（2026-11-19、`test_relay_wrapper.py` の偽の子） | 結果 |
| --- | --- |
| マーカーを書いた子が質問を出したまま生き続ける | `log.jsonl` の `kind` が `section` → `forward` → `wait` → `switch` → `section`。最初の子は終了コード -9（強制終了） |

## 期待する結果

- 質問の表示中は、回答が済むまでラッパーが子を止めず、子の端末へ書かない
- 手順書の守りの表が、`switch_decide.decide` と `wrapper.py` の振る舞いと一致する

## 再現手順

1. ラッパーの下で、応答の最後に `ndf-next` のブロックを出す（Stop の hook がマーカーを書く）
2. `/goal` が未達のため応答が続き、その中で `AskUserQuestion` を呼ぶ
3. 静かな時間（既定 5 秒）の後、質問に答える前に子が強制終了され、次のセグメントが始まる

（3 は偽の子で再現した。実際の claude では打っていない）

## 環境

NDF `main` の 2e43af7bc（11.0.8 の後）・Linux。ptyprocess 0.7.0。

## なぜ困るか

承認ゲートの質問は、人の判断を待つ場所である。答える前に子が止まると、質問は画面から消え、次のセグメントは承認の無いまま先へ進む。文脈の上限で引継ぎの 1 行を書く経路では、改行が選択肢 1 を選び、人に代わってラッパーが答えてしまう。手順書が 10 系の仕組みを書いているため、読み手は守られていると思い込み、欠けに気づけない。

## 目的

- 中継のラッパーが、質問の表示中に子を止めたり子の端末へ書いたりせず、承認ゲートの質問を利用者かオーガナイザーが答えるまで残す
- 手順書 `relay.md` の「承認ゲートを越えない守り」が、11 系のラッパーと hook の振る舞いだけを書く

## 対象範囲

含む:

- ラッパーが、質問のファイルを回答が済むか子が終わるまで残し、その間は切り替え・起動し直し・引継ぎの送信をしない
- 1 つの質問を転送する操作（`forward`）を 1 回だけにする
- 質問の hook（`ask-forward`）が、ラッパーと同じロックを取れたときだけ質問のファイルを書いて質問を通し、取れない・書けないときは質問を拒否する。ラッパーはロックを持ったまま質問が無いと確かめてから子を止める
- 回答の後に hook が質問のファイルを消す（`AskUserQuestion` の PostToolUse。回答されずに閉じた質問は Stop・UserPromptSubmit）
- 手順書 `relay.md` の「承認ゲートを越えない守り」を、11 系のラッパーと hook（`ask-forward`・質問のファイルを消す hook・`relay-marker`・`stop-wait`）の振る舞いへ書き直す

含まない:

- 切り替えを `/exit` で行うこと（起票者の推定 S1）
- 会話の記録から回答の無い質問を推し量ること・質問のファイルを手で消すコマンド（2026-11-20、利用者の決定で hook の形にした）
- 手順書の「上限」（#3815）とリレーハブ（#3818）の食い違い
- マーカーの後の利用者の入力・背景の作業で切り替えを取り消すこと（起票者の推定 S4）
- ラッパーを挟まない起動・会話ごとの引数・SessionStart での向け直し（#3807 で直した）と、Skill の本文を 11 系に合わせること（#3799）

## 前提

- 前提 1: Claude Code は、Stop の hook を呼ぶ前に最後の応答を会話の記録へ書き終える（Stop の hook の `last_reply` は入力の `last_assistant_message` か会話の記録の末尾から読む。`hooks/context.py`）
- 前提 2: `terminate(force=True)` は SIGHUP・SIGCONT・SIGINT を 0.1 秒おきに送り、それでも終わらなければ SIGKILL を送る（ptyprocess 0.7.0 の `PtyProcess.terminate`）
- 前提 3: `AskUserQuestion` の PreToolUse の hook は選択肢の表示の前に動き、hook が拒否すると選択肢は出ない。質問への回答（選択肢を選ぶ・自由入力）では、回答の時点で PostToolUse の hook が `tool_response.answers` を持って動く。回答されずに閉じた質問（Esc・Chat about this）では PostToolUse も PostToolUseFailure も動かない。Chat about this の後は応答を終えたときに Stop が動き、Esc の後は人が次に入力を送ったときの UserPromptSubmit まで hook は動かない。Ctrl+C では質問は閉じない（Claude Code 2.1.329 の対話の起動で実測、2026-11-20）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | ラッパーがロックを持つのは、質問の確かめから子が終わるまで（`terminate(force=True)` の最大 0.4 秒。SIGKILL の後も子が終わらなければ、さらに `relay.child-exit` の 5 秒まで）だけにする。待っても終わらなければ、前の子が生きたまま次の子を起動せず、ラッパーを止める。hook のロックの待ちの上限（`hook.ask-forward` の 0.3 秒）と PreToolUse の予算は変えない |
