# #1241: quality-gates: 設計の決定で作ると書いたテストと、変えた振る舞いを書いた既存の確定仕様を、実装の完了判定が突き合わせない

正は課題の本文（#1241）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 目的

- 実装の途中で決めたこと・作らなかったものを、**実装 PR の完了判定の時点で**設計・要求・既存の確定仕様と突き合わせ、食い違いをマージの前に見えるようにする
- 確定仕様化（plan-to-spec）やリリース後テストで初めて見つかる手戻り（devbasex/devbase の m6・m7b・m7e で 7 件）を、実装 PR の段階へ前倒しする

## 前提

- 前提 1: 突き合わせの対象は、設計文書（`issues/` の設計。`## 決定の記録` と `## テスト設計` を持つ）がある変更に限る。設計文書が無い変更（`light` / `operation` / `documentation` と、設計を持たない `legacy-refactor`）では、3 つの確認を「該当なし（設計文書が無い）」として満たす
- 前提 2: 確認 (a)（テストの実在）は名前の抽出と存在の判定までをスクリプトが行う。確認 (b) は参照する文書の列挙をスクリプトが行い、記述が変更後の振る舞いと合うかの判断は LLM が行う。確認 (c)（決定と実装の一致）は LLM が判断する（Value 4）
- 前提 3: 既存の確定仕様の置き場は、確定仕様化（`plan-to-spec-steps.py`）が使う置き場と同じものを使う（現状は `docs/specifications/`）。この課題で置き場の新しい設定を作らない。変更履歴は対象リポジトリの根の `CHANGELOG.md` とプラグインごとの `CHANGELOG.md` のうち、あるものを見る
- 前提 4: 設計に名前の出るテストとは、設計文書の `## 決定の記録` と `## テスト設計` の節に、バッククォートで囲んで書かれたテストファイルのパス（例: `tests/ci/test_ci_workflow.py`）とテスト関数（例: `tests/x.py::test_y`）を指す。散文で書かれただけの「〜を確かめるテスト」は (a) の機械の判定の対象にせず、(c) の決定との突き合わせで LLM が見る
- 前提 5: 食い違いの解消は「実装 PR の本文の `## 設計と違う点` の節に並べる」か「設計文書・要求の文書を同じ PR で直す」のどちらかで満たす。どちらを選ぶかは実装の担い手が決め、完了判定は「食い違いが記録されずに残っていないか」だけを見る
- 前提 6: この課題で「既存の確定仕様」は、今回の変更より前から確定仕様の置き場にある文書を指す。同じ差分で新しく足した確定仕様は含まない
- 前提 7: 新しい承認ゲート（人の承認）は足さない。完了判定のチェックリストの項目と、実装 PR の本文の節として足す（Value 2）

## 対象範囲

含む:
- `quality-gates` の `standard` の完了の定義に、確認 (a)(b)(c) の 3 項目を足す
- 確認 (a) を機械で行うスクリプト（設計文書から名前を抜き、HEAD に実在するかを判定する）
- 確認 (b) のための列挙（変更したファイルのパス・変えたシンボルの名前を参照する既存の確定仕様と `CHANGELOG.md` の該当箇所を並べる）
- 実装 PR の本文に `## 設計と違う点` の節を置く取り決め（違いが無いときは「無し」と書く）
- 実装で受け入れ条件の前提を変えたとき、要求の文書（課題の本文と `issues/` の写し）を同じ PR で直すか、条件ごとに「実装で変えた」と残す取り決め（`requirements-design` の「変更の途中で要求が変わったとき」の形を使う）
- 3 層（supervise.py）の実装フェーズで、完了判定がこの 3 項目を通る経路

含まない:
- 確定仕様化（plan-to-spec）の手順の変更（今の突き合わせはそのまま残す）
- 要求から設計・コード・テスト・リリースの証拠までの全体の追跡（#337。やらないで閉じた）
- 実データの結合確認の値の突き合わせ（#735。同じ完了判定へ足すが別の課題）
- 設計 PR の本文の「決めたこと」の節の仕組み（`pr-body-decisions.sh`）の変更
- 決定の表を issue のコメントに持つ変更（#1447 の carmo-cdk の形）への対応
- 確定仕様の置き場をプロジェクトの設定で変えられるようにすること

## 受け入れ条件

- [ ] 設計文書の `## テスト設計` か `## 決定の記録` にバッククォートで書かれたテストファイルのパスが HEAD に無いとき、確認 (a) のスクリプトはそのパスを「無い」として出し、0 以外で終わる（#216 の `tests/ci/test_ci_workflow.py` の形）
- [ ] 設計文書に `<パス>::<関数>` の形で書かれたテスト関数が、ファイルはあるが関数が無いとき、確認 (a) はその関数を「無い」として出し、0 以外で終わる
- [ ] 設計に名前の出るテストがすべて HEAD にあるとき、確認 (a) は 0 で終わる
- [ ] 設計文書に名前の出るテストが 0 件のとき、確認 (a) は 0 で終わり、0 件であることを出力に残す
- [ ] 設計文書・git が読めないとき、確認 (a) は「確かめられなかった」を表す終了コード（0 とも「無い」とも別の値）で終わり、0 へ畳まない
- [ ] 変更したファイルのパスか、変更で増減したシンボルの名前を含む既存の確定仕様と `CHANGELOG.md` があるとき、確認 (b) の列挙はそのファイルと行を出す（#247 の `base-image-shellcheck.md` の形）
- [ ] 確定仕様化で新しく足した確定仕様（同じ差分で追加したファイル）は、確認 (b) の列挙に出ない
- [ ] `quality-gates` の `standard` の完了の定義に、(a) 設計に名前の出るテストが実在する・(b) 列挙した既存の確定仕様と変更履歴が変更後の振る舞いと合う・(c) 決定の記録の各決定が実装と一致するか違いが記録されている、の 3 項目がある
- [ ] 設計文書が無い変更では、3 項目を「該当なし（設計文書が無い）」と書いて満たせることが完了の定義に書かれている
- [ ] 実装 PR の本文に `## 設計と違う点` の節があり、違いが無いときは「無し」と書かれる。3 層の実装フェーズが作る実装 PR でも同じ節が入る
- [ ] 実装されなかった決定（m7e の #214 の決定 6 の形）は、`## 設計と違う点` に「実装しなかった」として並ぶか、設計文書を同じ PR で直す取り決めがある
- [ ] 実装で受け入れ条件の前提を変えたとき、要求の文書を同じ PR で直すか、条件ごとに「実装で変えた」と残すことが完了の定義に書かれている（#218 の形）
- [ ] devbasex/devbase の m6・m7b・m7e の 7 件のうち、設計文書が手に入るものを 1 件以上使い、確認 (a) か (b) がその食い違いを出すことを実測で示す（実測の結果を設計 PR か実装 PR に残す）
- [ ] 設計文書を持たない変更（`light` など）の完了判定の手順と所要は変わらない（追加の確認を走らせない）
- [ ] 既存の全体テストが通る

> ## 直さないと何が起きるか
>
> - 設計が約束した回帰の防止が無いまま閉じる（#216 は、`branches: [main]` が戻っても CI が落ちない）
> - 既存の仕様と変更履歴が、リリースの時点で実装と矛盾する
> - 受け入れ条件が実装の判断と食い違ったまま、リリース後テストで「不合格か合格か」の判断を迫る
> - 設計と違う実装が、違いを本文に書かないまま実装 PR を通り、確定仕様化が拾わなければ残る
>
> ## 直し方の案
>
> - quality-gates の完了判定に 3 つの確認を足す。(a) 設計のテスト設計・決定の記録に名前の出るテストファイル・テスト関数が実在するか（機械で拾える）。(b) 変更したファイルやシンボルを参照する既存の `docs/specifications/*` を列挙し、記述が変更後の振る舞いと合うか。(c) 決定の記録の各決定を実装と突き合わせ、違えば実装 PR の本文に「設計と違う点」として並べる（または設計の文書を同じ PR で直す）
