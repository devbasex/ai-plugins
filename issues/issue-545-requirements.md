# #545: 設計 Pull Request の本文を設計文書の決定から外れさせない — 要求と受け入れ条件

設計は [issue-545-design.md](issue-545-design.md) にある。この文書は「何を満たすか」だけを扱う。

## 目的

- 設計 Pull Request の本文を読んで承認する人が、**現在の設計文書と違う決定を読まない**状態にする
- 本文を書き換えた経路（`pr` / `fix` / 進行側の直接の修正）によらず、承認を求める前に食い違いが見つかる

## 対象範囲

含む:

- 本文の「決めたこと」の節と、設計文書の決定の見出しとを突き合わせるスクリプト
- ずれていたときに、本文のその節だけを書き直す手段
- `pr` / `fix` の手順と、承認を求めるときの提示物の手順から、上の 2 つを呼ぶこと
- 設計 Pull Request の本文に書く範囲（決定の中身を本文へ写さない）
- このリポジトリの継続的統合で突き合わせを走らせること

含まない:

- 本文の自由文（Summary）が決定を言い換えているかの判定。機械では判定できず、規約として書くに留める
- 実装の Pull Request の本文。承認の関門を通らない
- `cross-review` の手順の変更。修正と最終スイープは `fix` を呼ぶため、そちらで拾える（設計の決定 7）
- 継続的統合の検査を ruleset の必須の検査へ加えること。リポジトリの設定の変更で、利用者の承認が要る
- クラス図。触る型が無い（シェルスクリプトと Skill 本文の変更である）

## 依頼（原文）

> **レビューで設計を変えても、Pull Request の本文が古いまま残る。** 直す手順がどこにも無い。
>
> PR #539 で実際に起きた。7 巡のレビューが収束した後、設計を 1 点変えた（実行してよい
> コマンドの受け取り方を、宣言ファイルから起動の引数へ）。**設計文書 2 本は直したが、
> 本文は宣言ファイルの説明を載せたままだった。**
>
> | 誰が直すか | 本文を直す手順 |
> | --- | --- |
> | `pr`（Skill） | **持つ**（「既存 PR がある場合は説明を更新する」） |
> | `fix`（レビューの修正） | **持たない**。PR 本文を**読む**手順はある（`fix/SKILL.md:129`）が、書く手順が無い |
> | 進行側が直接直したとき | 手順を通らない |
>
> **承認する人は本文を読む。** `development-workflow` の `references/approval-request.md` は
> 「決めたこと」を提示物へ含めており、その出所は本文と設計文書である。**本文が古いと、
> 承認の判断が古い前提で行われる。**

（issue #545 の本文から抜粋。考えられる形の 3 案は設計の工程で扱う）

## 現状の確認

`origin/develop`（`d068c61`）で数え直した。

| 経路 | 現状 | 位置 |
| --- | --- | --- |
| `pr` | 既存の Pull Request があれば本文を全体から作り直す手順を持つ。設計 Pull Request の本文の形は決めていない | `pr/SKILL.md` の「PR説明の更新」（199〜217 行） |
| `fix` | 本文を**読む**だけで、書く手順が無い。サマリはコメントとして投稿する | `fix/SKILL.md` 129 行 / 手順 7（207 行） |
| 進行側が直接直したとき | 通る手順が無い | — |
| `cross-review` | 本文に触れるのはローテーションで新しい Pull Request を作るときだけ。修正と最終スイープは `fix` を呼ぶ | `cross-review/SKILL.md` の Step 5 / Step 6b / Step 7.5 |
| 承認の提示 | 「決めたこと」の出所を設計文書の決定の節とする。本文との照合は無い | `approval-request.md` 34 行 |

**PR #539 では決定の見出しそのものが変わっていた。** 修正のコミット `0c77982f` の前後で、
設計文書の `### 決定 1` の見出しが「実行してよいコマンドをリポジトリが宣言する」から
「実行してよいコマンドは起動の引数で受け取る」へ変わった。見出しを照合する手段があれば
検出できた。

## 前提

- 前提 1: 対象は head のブランチ名が `design/` で始まる Pull Request である。開発版のチャネルへ
  入れるマージのうち、承認の関門を通るのはこの Pull Request だけである（`pr/SKILL.md` の「マージに人手の承認が要るか」）
- 前提 2: 設計文書の決定は `decisions.md` の規約どおり、`## 決定の記録` の節の下に
  `### ` の小見出しとして 1 件ずつ書かれている。見出しは結論を 1 文で表す
- 前提 3: 本文と設計文書は GitHub の REST API で読める（`gh api` が認証済み）

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | `plugins/ndf/scripts/` にスクリプトを 1 本足す。既存のスクリプトの引数は変わらない |
| データ | 無し |
| 既存の振る舞い | 設計 Pull Request の本文に `## 決めたこと` の節が入る。`fix` が設計 Pull Request の本文を書き換えうる |

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| セキュリティ | 継続的統合の突き合わせは本文を読むだけで、書き込みの権限を持たない。本文の書き直しは、利用者が認証済みの `gh` の権限の範囲でだけ行う |

## 前提とする取り決め

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | 複数の Skill から呼ぶスクリプトは `plugins/ndf/scripts/` に置く（`progress-record.sh` と同じ）。位置は `development-workflow/references/scripts-lookup.md` で決める |
| コーディング規約 | `AGENTS.md` の「最小限のコード実装」。本文の節の差し替えは `progress-record.sh` の「見出しは行頭の単独の行として探す」に合わせる |
| テスト戦略 | スクリプトは `gh` を差し替えた単体テスト。Skill 本文の変更は受け入れ条件 13〜17 を読んで確かめる |

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | 読めなかったことを一致として扱わない。節の外の本文を書き換えない |
| 確認してから行う | ruleset の必須の検査へ加えること |
| 行わない | 本文の自由文の意味の照合。`design/` で始まらない Pull Request の本文への節の追加 |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| テスト | `uv run --with pytest pytest plugins/ndf/scripts/tests -q`（`gh` を差し替えて 1〜12 と 20 と 22 を確かめる） |
| 静的解析 | `python3 scripts/check-skill-repo-assumptions.py` / `python3 scripts/check-doc-line-limit.py` / `python3 scripts/check-markdown-links.py` と、新設のスクリプトへの `bash -n` |
| 手動確認 | 実装の Pull Request の作業中に、検証用の `design/` ブランチで Pull Request を下書きとして開き、`sync` の後に `check` が 0、見出しを 1 つ変えて push した後に継続的統合が落ちることを見る。確かめたら閉じる |

## 受け入れ条件

### 突き合わせ（`check`）

- [ ] 1. 本文の決めたことの節が、設計文書の決定の見出しから作った節と一致するとき、終了コード 0 を返す
- [ ] 2. 設計文書の決定の見出しが本文の節と違うとき（#539 の形: 見出しの文言が変わった）、終了コード 1 を返し、食い違った行を出力する
- [ ] 3. 設計文書に決定があるのに本文に決めたことの節が無いとき、終了コード 1 を返す
- [ ] 4. 本文に決めたことの節があるのに、変更したファイルのどれも決定の記録の節を持たないとき、終了コード 1 を返す
- [ ] 5. コードフェンスの中にある `## 決定の記録` と `### ` は数えない（本文の側のコードフェンスの中の `## 決めたこと` も同じ）
- [ ] 6. 本文か設計文書を読めなかったとき（存在しない番号・`gh` が無い・API の失敗）、終了コード 2 を返す。**0 を返さない**
- [ ] 7. 設計文書は Pull Request の head のコミット（`ref` に head の SHA）から、本文は Pull Request の `body` から読む。手元の作業ツリーの内容に左右されない
- [ ] 8. head が `design/` で始まらない Pull Request では、変更したファイルも設計文書も読まず、対象外であることを 1 行出して終了コード 0 を返す

### 書き直し（`sync`）

- [ ] 9. 決めたことの節だけを差し替え、節の外の本文は 1 バイトも変えない
- [ ] 10. 本文に節が無ければ `## Test plan` の直前へ足し、`## Test plan` も無ければ末尾へ足す
- [ ] 11. すでに一致しているときは書き込みの API を呼ばず、終了コード 0 を返す
- [ ] 12. 書き込んだ後に突き合わせ直し、一致したときだけ 0 を返す。読めなかったときは 2 を返す

### 手順

- [ ] 13. `pr/SKILL.md` に、設計 Pull Request の本文が決定の中身を持たず、決めたことの節を `sync` で作ることが書かれている
- [ ] 14. `pr/SKILL.md` の作成（手順 5）と既存の本文の更新（「PR説明の更新」）の後に、`sync` を実行する手順がある（対象かどうかはスクリプトが決める）
- [ ] 15. `fix/SKILL.md` の修正手順に、**コミットの有無によらず** `sync` を実行する手順があり、完了報告にその終了コードを載せる
- [ ] 16. `approval-request.md` の「設計 Pull Request のマージ」に、提示の前に `check` を実行する手順がある。結果が 1 なら `sync` してから提示し、2 なら「未確認」と明記して提示する
- [ ] 17. `design/SKILL.md` の設計 Pull Request の本文の行が、本文の形を `pr` の規約へ渡している（同じ規約を 2 箇所に書かない）

### 継続的統合

- [ ] 18. Pull Request を開いた・push した・本文を編集した・開き直したときに `check` が走り、その終了コードが検査の結果になる
- [ ] 19. 検査のジョブは読み取りの権限だけを持つ

### 退行しないこと

- [ ] 20. `design/` で始まらない Pull Request に `sync` を実行しても、書き込みの API を呼ばない
- [ ] 21. 検証手段の表の「静的解析」に挙げた文書の検査 3 本が、いずれも終了コード 0 で終わる

### 呼び出しの誤り

- [ ] 22. 副コマンドが無い・未知の副コマンド・PR 番号が数値でないとき、GitHub を読まずに終了コード 3 を返す

## 用語

| 用語 | 意味 |
| --- | --- |
| 設計 Pull Request | head のブランチ名が `design/` で始まる Pull Request |
| 設計文書 | Pull Request が変更したファイルのうち、`## 決定の記録` の節を持つ Markdown |
| 決定の見出し | `## 決定の記録` の節の下にある `### ` の見出しの文字列 |
| 決めたことの節 | 本文の `## 決めたこと` の見出しから、次の `# ` または `## ` の見出しの手前まで（後続の見出しが無ければ本文の末尾まで） |
