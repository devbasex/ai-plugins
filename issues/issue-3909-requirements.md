## 何が起きたか

計画 p8-5 の途中で NDF 11.0.9（2026-11-20 12:32 JST）と 11.0.10（同 18:48 JST）を出したが、どちらの後でも、中継のラッパーが自分でプラグインを上げる場面（#3812 の受け入れ条件 1: 記録の `plugin_update` の行が from=旧・to=新・result `updated`）が一度も起きなかった。

どちらのリリースでも、ラッパーより先に **Claude Code のマーケットプレイスの自動更新** が NDF を新しいバージョンへ入れ替えていた（`~/.claude/plugins/known_marketplaces.json` の `ai-plugins` が `autoUpdate: true`）。その後に起動したラッパーは、自分のコードのバージョン（11.0.8）と同じ導入を探して見つけられず、更新も起動先の確認も飛ばした。さらに、耐久ワークフロー（`ndf lanes run p8-5`。11.0.8 で起動）が起動し直すラッパーも 11.0.8 のコードで動き、子の claude の `ndf` も 11.0.8 に解決した。

- 11.0.9: 12:35 JST に、ラッパーの外で導入が 11.0.9 へ上がった。13:12 JST の lstage の切り替えの記録は `from 11.0.9・to 11.0.9・up_to_date` で、何も出ていないときと同じ形だった
- 11.0.10: 18:49:48 JST にラッパーの外で導入が 11.0.10 へ上がった。その直前の 18:49:31〜41 JST に耐久ワークフローが起動し直した 5 本のラッパーと、18:58:38 JST に起動した lupd のラッパーは、6 本とも `plugin_update` が `skipped`（理由「動いている導入先と一致する有効な NDF の導入が無い」）

記録の場所: `~/.local/state/ndf/relay/wrappers/p8-5-*/log.jsonl` と `wrapper.json`。根拠の時刻・プロセス・コードの位置は設計書（`issues/issue-3909-design.md` の「今の姿」）にまとめた。

## 種類

不具合（ラッパーの手順書が「次のセグメントの claude は更新後の導入先を読む」と約束しており、導入がラッパーの外で上がったときにその約束が守られない）

## 今の姿

中継のラッパー（`ndf relay`）は、新しい会話で始める最初のセグメントの前とカットポイントの切り替えで、マーケットプレイスと NDF を `claude plugin` のコマンドで最新のバージョンへ上げてから次のセグメントの claude を起動する。リリースした直しは、利用者の操作なしで次のカットポイントから動いているレーンへ届く、という約束である。

- 約束のSSOT: [relay.md の「プラグインの更新とラッパーのバージョン」](https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/relay.md#プラグインの更新とラッパーのバージョン)、確定仕様 [ndf-relay-plugin-update.md](https://github.com/devbasex/ai-plugins/blob/main/docs/specifications/ndf-relay-plugin-update.md)
- 更新の対象（マーケットプレイス・プラグインの ID・スコープ）は、「ラッパーが動いている導入先と一致する有効な `ndf@` の 1 件」から読む。一致しなければ更新せず `skipped` の行を残す。これは `--plugin-dir` や開発のチェックアウトから動くラッパーを更新しないための決まり（#3812 の受け入れ条件 6）で、ラッパーの外で導入が上がった場合を想定していない
- ラッパー自身のコードは、動いている間は入れ替わらない。新しいバージョンのラッパーは、次にラッパーを起動したときから動く
- 耐久ワークフロー（`ndf lanes run`）は、レーンを起動し直すとき、自分のコードのバージョンの `bin/ndf` でラッパーを起動する
- Claude Code は、自動更新が有効なマーケットプレイスのプラグインを、ラッパーと無関係に裏で入れ替える。サードパーティのマーケットプレイスは既定で無効で、利用者が有効にできる（[公式: When auto-update runs](https://code.claude.com/docs/en/plugins/loading)）

## 事象

18:58:38 JST に耐久ワークフローが起動した lupd のラッパー（11.0.8 のコード）の `log.jsonl` の 1 行目:

```json
{"at": "2026-11-20T09:58:38+00:00", "section": null, "kind": "plugin_update", "result": "skipped", "from": null, "to": null, "launched": null, "reason": "動いている導入先と一致する有効な NDF の導入が無い", "seconds": 0.7}
```

その時点の導入の一覧（`installed_plugins.json`）の `ndf@ai-plugins` は `version: 11.0.10`・`installPath: ~/.claude/plugins/cache/ai-plugins/ndf/11.0.10` の 1 行だけだった。続けて起動した子の claude の Bash では次のとおりだった。

```console
$ command -v ndf
/home/ubuntu/.claude/plugins/cache/ai-plugins/ndf/11.0.8/bin/ndf
$ ndf progress check ...
ndf progress: error: argument action: invalid choice: 'check' (choose from 'new', 'show', ...)
```

`ndf progress check` は 11.0.10 にあるサブコマンドで、11.0.8 には無い。

## 期待する結果

ラッパーの外で導入が上がっていても、ラッパーは今の有効な導入を更新の対象として読み、次のセグメントの claude をそのバージョンで起動し、子の claude の `ndf` もそのバージョンに解決する。耐久ワークフローが起動し直すラッパーは、その時点の有効な導入のバージョンで動く。

## 再現手順

1. NDF のバージョン N を入れ、`ai-plugins` マーケットプレイスの自動更新を有効にした Claude Code で、`ndf lanes run <計画>` か `claude`（中継のラッパー）を起動する
2. マーケットプレイスにバージョン N+1 を出し、Claude Code の自動更新で導入が N+1 へ上がるのを待つ（`installed_plugins.json` の `ndf@ai-plugins` の `version` が N+1 になり、`cache/ai-plugins/ndf/N/.orphaned_at` ができる）
3. バージョン N のコードからラッパーを起動する（耐久ワークフローがレーンを起動し直す、またはバージョン N の `bin/ndf relay run` を打つ）
4. ラッパーの `log.jsonl` の `plugin_update` の行が `skipped`・`launched: null` になり、子の claude の `command -v ndf` がバージョン N の `bin/ndf` を指す

2026-11-20 に 2 回（11.0.9・11.0.10）とも起きた。

## 環境

- NDF: ラッパー・耐久ワークフローは 11.0.8（`wrapper.json` の `version`）、有効な導入は 11.0.9 → 11.0.10
- Claude Code 2.1.329、Linux（dev コンテナ）
- `~/.claude` は `/persistent/group/.claude` へのシンボリックリンク。`ai-plugins` は `extraKnownMarketplaces`（`~/.claude/settings.json`）と `known_marketplaces.json` の両方で `autoUpdate: true`

## なぜ困るか

- **リリースした直しが、動いているレーンへ届かない。** 自動更新で導入だけが上がり、ラッパーは古いバージョンのまま `skipped` を続けるので、#3812 が約束した「次のカットポイントから効く」が成り立たない。子の claude は新しいバージョンの hook と Skill を読む一方、Bash の `ndf` は古いバージョンで、手順書（新しいバージョン）に書かれたコマンドが無いと断られる（この課題の設計の作業中にも起きた）
- **何が起きたかを記録から読めない。** 外で上がった後の切り替えは、何も出ていないときと同じ `up_to_date` の行になる
- **#3812 の受け入れ条件 1 を確かめる場面が来ない。** 外の自動更新が先に上げるので、ラッパーが自分で上げる経路が実物で一度も動かない。11.0.9・11.0.10 とも未確認のまま残った

## 目的

- 導入がどの経路で上がっても、ラッパーが次に起動する claude と、その claude が呼ぶ `ndf` が、今の有効な導入のバージョンにそろう
- 記録から「外で上がっていた」と「ラッパーが自分で上げた」を区別して読める
- ラッパーが自分で上げる経路（#3812 の受け入れ条件 1）を、実物で確かめられる

## 対象範囲

含む:
- ラッパーが更新の対象にする導入の決め方（ラッパーのコードのバージョンと導入のバージョンが食い違うとき）
- 記録の `plugin_update` の行で、外で上がっていたことと自分で上げたことを区別できるようにすること。手順書の「記録の読み方」の表と例
- ラッパーが起動する子の claude の `PATH` で、`ndf` が起動先の導入のバージョンに解決すること
- 耐久ワークフローがレーンのラッパーを起動するとき、その時点の有効な導入の `bin/ndf` を使うこと
- Claude Code のマーケットプレイスの自動更新を止める・戻す方法と、#3812 の受け入れ条件 1 をリリース後に確かめる手順を手順書に載せること

含まない:
- 耐久ワークフローのプロセス自身を新しいバージョンへ入れ替えること、およびレーンの最初の入力（`/goal` など。#3858）を新しいバージョンの形で組むこと。耐久ワークフローの中で組まれる入力は、起動したときのバージョンの形のまま残る（#3918 で扱う）
- 動いているラッパーのプロセス自身を新しいバージョンへ入れ替えること（#3812 の決定どおり、次にラッパーを起動したときから新しいバージョンになる）
- NDF のコードから Claude Code の自動更新の設定を書き換えること、利用者の設定の既定を変えること
- 10 系のラッパー・11.0.7 以前のラッパーの振る舞い

## 前提

- 前提 1: 「ラッパーの外で上がった導入」は、ラッパーのコードと同じプラグインのキャッシュの、同じマーケットプレイスの `ndf` の下（`<キャッシュ>/<マーケットプレイス>/ndf/<版>`）にある導入を指す。キャッシュの外（`--plugin-dir`・開発のチェックアウト）から動くラッパーは今のとおり更新しない
- 前提 2: Claude Code の自動更新の既定・優先順・止め方は、2026-11-20 に読んだ公式ドキュメント（plugins/loading・plugins/install・plugins/org・env-vars）と Claude Code 2.1.329 の help で確かめた事実に従う

## 受け入れ条件

- [ ] 1. バージョン N のコードのラッパーを、有効な導入が同じマーケットプレイスのキャッシュのバージョン M（M ≠ N）にある状態で起動すると、最初のセグメントの前とカットポイントの切り替えで、マーケットプレイスの更新と NDF の更新のコマンドがバージョン M の導入の ID とスコープでこの順に 1 回ずつ走り、`plugin_update` の行の `result` が `skipped` にならず、`launched` が次の子の読むバージョン（M か、更新で上がったバージョン）になる
- [ ] 2. 受け入れ条件 1 の行から、ラッパー自身のバージョンと、コマンドを打つ前の有効な導入のバージョンと、打った後のバージョンの 3 つが読める。relay.md の「記録の読み方」の表が「コマンドの前のバージョンがラッパーのバージョンと違えば外で上がっていた」「`result` が `updated` ならラッパーが自分で上げた」を書き、載せた `jq` の例を実物の記録に打つとその行が返る
- [ ] 3. 受け入れ条件 1 の状態で、ラッパーがセグメントの claude を起動すると、その claude の Bash の `command -v ndf` は `launched` のバージョンの導入の `bin/ndf` を指す。ラッパーの起動の経路で `PATH` に入った別のバージョンの NDF のプラグインの `bin` と NDF の仮想環境の `bin` は、子の `PATH` に残らない
- [ ] 4. 起動先のバージョンのメジャーバージョンがラッパーと違うときは、受け入れ条件 1 の状態でも #3812 の受け入れ条件 11 のとおり次のセグメントを起動せず、案内の 1 行を出して終わる（`launched` が null のまま素通りしない）
- [ ] 5. バージョン N のコードの耐久ワークフローが、有効な導入がバージョン M に上がった後にレーンのラッパーを起動する（起動・起動し直し）と、ラッパーのプロセスはバージョン M の導入の `bin/ndf` で動き、`wrapper.json` の `version` が M になる。導入の一覧が読めない・有効な `ndf` の導入が無いときは今のとおり自分のバージョンの `bin/ndf` で起動し、その理由を 1 行残す
- [ ] 6. 退行しない: キャッシュの外から動くラッパー、別のマーケットプレイスの `ndf` の導入、同じ導入先を複数のスコープが指す場合は、今のとおりコマンドを打たず `skipped` の行を残す。バージョンが一致する（外で上がっていない）ときの `updated`・`up_to_date`・`failed` の振る舞いと記録は変わらない
- [ ] 7. relay.md に、Claude Code のマーケットプレイスの自動更新について、既定（サードパーティは既定で無効）・決まる順（設定ファイルの `extraKnownMarketplaces` → `known_marketplaces.json` → 既定）・止める方法（`/plugin` の Marketplaces タブ、設定ファイルの `extraKnownMarketplaces.<名前>.autoUpdate: false`）・戻す方法が、公式ドキュメントへのリンク付きで載っている
- [ ] 8. relay.md に、#3812 の受け入れ条件 1（ラッパーが自分で上げる）をリリース後に確かめる手順が載っている。手順は、リリースの前に受け入れ条件 7 の方法で自動更新を止め、リリースの後のカットポイントで `plugin_update` の行（`result: updated`・`from`=旧・`to`=新・`launched`=新）を `jq` で確かめ、最後に自動更新を元へ戻す、の順である
- [ ] 9. 受け入れ条件 8 の手順で、このリリースの次のリリースの後に、実物の記録に `result: updated` の行が 1 行以上残る
