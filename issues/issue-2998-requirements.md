## 目的

- **今どうなっているか**: 進捗ログ（`progress.jsonl` の `alive` など）に load average・メモリ・スワップが残らず、キューで待った時間の理由（ファイルの重なり・`plans`・上限 6）も残らない。プランの上限 6 の根拠は 2026-09-25 の測定（全体テスト 1 本 93 秒）で、今は全体テストが 850〜1,000 秒かかり、スワップ 8 GB を使い切ることがある。上限を変えるかを決める材料が無い
- AI が Bash で直接打つ pytest と conductor の対話は記録の外にあり、同時実行数が少なめに出る
- **変えると何が成り立つか**: 上限と並べ方を、測った値で決め直せる

## 前提

- 前提 1: 負荷とメモリの値は Linux の `/proc/loadavg` と `/proc/meminfo` から読む。読めない環境（macOS など）では値を省き、記録の行そのものは今どおり書く
- 前提 2: マシンの上の pytest の数は、プロセスの一覧から命令行に `pytest` を含むものを数えた値とする。`pytest-xdist` の作業プロセス（`-n 4` なら 4 本）は親と分けて数える。人がシェルで打った pytest も数に入る（区別しない）
- 前提 3: 「計画の上限」による待ちは #2999 が作る。この課題では理由の名前を決めて記録の形に含め、実際に書くのは #2999 である。#2999 が別の形を選んだら、この課題の記録の形に合わせる
- 前提 4: メモリの山の計測は 1 回の手動の計測で、自動のテストにしない。結果は計測した日・マシンの CPU 数とメモリ量・NDF の版とともに確定仕様に載る

## 対象範囲

含む:
- 進捗ログ（`progress.jsonl`）の `alive` の行とステップの終わりの行へ、load average・MemAvailable・スワップの値とマシンの上の pytest の数を足す
- queue が流したプランごとに、キューで待った秒を理由ごとに数えて queue の結果へ残す
- 全体テストを 1・2・3 本同時に流したメモリの山を 1 回測り、上限の確定仕様へ載せる

含まない:
- 上限の値（`NDF_PARALLEL_MAX_PLANS`・`--max`）の変更。測った後に別の課題で決める
- 「計画の上限」による待ちを作ること（#2999）
- 重い処理の枠（#2711）。この課題は数えるだけで、待たせない
- 記録の値を集計するスクリプト（スプリントをまたいで並べる集計）。値が残れば手で集計できる
- 同じスプリントの課題の選び方（離れたファイルを触る課題を組にする）の変更。依頼の原文のこの部分は別の課題で扱う

## 用語

| 用語 | 意味 |
| --- | --- |
| 負荷とメモリの値 | load average（1・5・15 分）、MemAvailable（MiB）、スワップの合計と空き（MiB）の組 |
| マシンの上の pytest の数 | 記録の行を書いた時点で、同じマシンに動いている pytest のプロセスの数（前提 2） |
| 待ちの理由 | プランがキューで流れ始めるまでに待った原因。重なり・`plans`・資源の枠・前提のプラン・計画の上限の 5 つ |
| メモリの山 | 全体テストを流している間に、マシンの使用中のメモリ（合計 − MemAvailable）とスワップの使用量が取った最大の値 |

## 受け入れ条件

- [ ] 1. `progress.jsonl` の `alive` の行に、load average の 3 つの値、MemAvailable（MiB）、スワップの合計と空き（MiB）がある
- [ ] 2. `/proc/loadavg` と `/proc/meminfo` を読めない環境で、`alive` の行は負荷とメモリの値を省いて今どおり書かれ、supervise は失敗しない
- [ ] 3. ステップの終わりの行（`kind: step`）にも、受け入れ条件 1 と同じ負荷とメモリの値がある
- [ ] 4. 受け入れ条件 1・3 の行に、マシンの上の pytest の数がある。supervise の外で打った `pytest` を 1 本動かしておくと、その数が 1 以上になる
- [ ] 5. queue の結果の JSON（`--done` のファイル）のプランごとの項目に、待った秒が理由（重なり・`plans`・資源の枠・前提のプラン）ごとにある（待たなかった理由の書き方は未決 3 の決定に従う）
- [ ] 6. 前提: 同じファイルを触る 2 本のプランを `--max 2` で queue に入れる。結果: 後のプランの重なりの待ちの秒が、前のプランが流れていた秒（±5 秒）になり、`plans` の待ちは 0 になる
- [ ] 7. 理由の名前に「計画の上限」が定義され、#2999 が書ける形が設計文書に載る
- [ ] 8. 全体テストを 1・2・3 本同時に流したときのメモリの山（使用中のメモリとスワップの使用量）と所要の秒が、本数ごとに測られている
- [ ] 9. 受け入れ条件 8 の値が、計測の日・CPU 数・メモリ量・NDF の版とともに `docs/specifications/ndf-parallel-organizer.md` の上限の行の根拠に載る
- [ ] 10. 計測の途中で MemAvailable が下限を割ったときは、残りの本数を流さずに打ち切り、打ち切った本数とその時点の値が受け入れ条件 9 の記録に載る
- [ ] 11. 上限の値（`DEFAULT_MAX_PLANS`・queue の `--max` の既定）が変わっていない（退行しない）
- [ ] 12. 既存の `alive` の行の項目（`step`・`type`・`elapsed`・`worker`・`last_output`）が残っている（退行しない）

## 非機能の条件

| 大項目 | 条件 |

| 性能・拡張性 | 負荷とメモリの値と pytest の数を読む処理は、1 行あたり 1 秒以内に終わる。`tick` の間隔を延ばさない |
