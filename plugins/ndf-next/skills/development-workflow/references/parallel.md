# 並列開発のオーガナイザー（`--parallel <計画名>`）

並列の計画（[issue-plan-strategy の parallel-plan.md](../../issue-plan-strategy/references/parallel-plan.md) で作る）を、
1 行で始める。

```text
/goal /ndf:development-workflow --parallel p1 -- 終わり: [ndf-parallel] finished p1 の行を出したとき
```

このセッションの conductor が**オーガナイザー**になる。オーガナイザーは、設計の承認の回答で設計 PR をマージするほかは作業を持たない。レーンの起動・観測・リリースのまとめは
耐久ワークフロー（`parallel.py run`）が、リリースプランの実行は一時レーンが、回答の後の処理はオーナーのレーンが行う。
一時レーンの起動と、回答を受けた止まったレーンの再起動も耐久ワークフローが打ち、立ち上がりを確かめる。オーガナイザーが打つのは質問と回答だけで、
`wait` がオーガナイザーへ返るのは人へ問うもの・計画の終わり・耐久ワークフローが自分で解けない異常のときだけである。再開のコマンドも同じ 1 行である。

## 手順

1. `python3 "$NDF_SCRIPTS/parallel.py" start p1` を打つ。検査に誤りがあればレーンを 1 本も起動せずに 1 で終わる。
   ラッパーの外・tmux が無い・リレーハブが居ないときは 3 で終わり、`items` にレーンごとの手で起動する 1 行が並ぶ。
   その 1 行を示して終える
2. `metrics.next` の `parallel.py wait p1` を背景で打ち、完了の通知を待つ（[waiting.md](waiting.md) の形。前景の sleep で待たない）
3. 返った `metrics.action` ごとに次の 1 手を打ち、`wait p1 --after <metrics.seq>` を背景で打ち直す

| `wait` が返したもの | すること |
| --- | --- |
| `questions` | 届いているリクエスト（`items`）を下の「質問の仕方」で質問、リクエストごとに回答を送る。回答を送ったリクエストだけが残る一覧では返らない。`metrics.batch` が `true` なら業務時間外に溜めたリクエストのまとめで、`metrics.deferred` があれば業務時間外に今問うリクエストだけが返っている（下の「業務時間外のリクエスト」） |
| `answer_hold` | `metrics.changes` の各行の `line` を利用者へそのまま 1 行ずつ出す（質問にしない）。出した最後の `n` を、以後の `wait` の `--changes-after` に渡す（下の「回答待ちの停止」） |
| `finished` / `stopped` | レーンごとの結果（リリースしたバージョン・停止理由）を要約し、`metrics.prior_waits`（回答のまだの前のループの待ち）があれば並べ、`[ndf-parallel] finished p1` の行を出して終える |
| 終了コード 3 | 上限（既定 1800 秒）で戻ったときは、下の「長い待ちの状況報告と切り替え」に従う。業務時間外にリクエストを溜めただけのときも 3 で、`metrics.next` の 1 行を打ち直す |
| 終了コード 1・`action: error` | 耐久ワークフローが失われた（下の「失われた計画」）。`metrics.next` の `parallel.py start p1` を 1 回打つ |
| `release` / `confirmed` / `held` / `notice` など（バージョンを上げる前に始めた計画だけ） | 起動を耐久ワークフローが打たない古い記録の道。`metrics.spawn`（`metrics.release.spawn`）の 1 行を、その `seq` でまだ打っていなければ打ち、`metrics.wake` の各行も打つ。質問の回答の後に `metrics.next` が返ればそれも打つ |

レーンの様子は `python3 "$NDF_SCRIPTS/parallel.py" status p1` で読む。レーンごとに 1 行（`state`・何回目のループか `lap`・今の課題 `issues`・
ジャーナルでそのレーンが最後に送った時刻 `last_at`・ループの記録の費用 `cost_usd`）を返し、承認待ちのレーンと回答していないリクエストを送ったレーンの行には
人が入る 1 行 `attach`（`tmux -L ndf-lanes attach -t <レーン>`）が載る。起動を待っているレーンの行には `waiting`（理由・マシンのプランの本数・
このレーンの本数・上限・待ち始めた時刻）が載り、要約に起動待ちの数が出る（[parallel-checks.md](parallel-checks.md) の「マシン全体のプランの本数」）。値の取れない欄は `null` で、一覧が読めなくても失敗しない。
レーンの画面を見に行く前にこれを読む。

`wait` の `metrics` には、計画のジャーナルから読んだ次の項目が載ることがある。どれも計画を止めず、利用者へ 1 行で伝える。

| 項目 | 意味 |
| --- | --- |
| `versions` | レーンの NDF のバージョンがオーガナイザーのバージョンと違う（`organizer` と、レーンごとの `lanes`）。違うときだけ載る |
| `unknown`・`unknown_ids` | このバージョンが知らない形のジャーナルの行の数とリクエストの id。行は残り、読めるバージョンで作り直せば反映する |
| `broken` | 読めないジャーナルの行の数（途中で切れた行など）。外して続けている |
| `orphans` | レーンのループの記録が回答を待つのに、ジャーナルに無いリクエストの id。届いていないリクエストなので、レーンに送り直させる |

### 質問の仕方

並列の計画の下で区分つきの質問を出すのはオーガナイザーだけである。レーンと一時レーンの質問はリクエストとして `items` に届く。

1. 区分ごとに `AskUserQuestion` を呼ぶ（`metadata.source` は呼び出しごとに 1 つ）。順は `ndf-gate:1` → `ndf-ask:redline:*` →
   ほかの `ndf-ask:*` → `ndf-gate:2`。リリース承認ゲートを最後にするのは、回答の時点でベースブランチの先頭を比べるためである
2. リクエスト 1 件を質問 1 つにし、5 件以上の区分は届いた順に 4 件ずつ続けて呼ぶ。各問いにはレーン名・課題・設計 PR の URL か作業の場所を添える。
   リクエストの行の `repo`（計画の設定から導いたレーンのリポジトリ）が計画の保存先と違えば、そのリポジトリも添える
3. `ndf-ask:human-action` のリクエストは `attach`（`tmux -L ndf-lanes attach -t <レーン>`）の 1 行を添えて「済んだ」「まだ」で問う。
   `merged` があれば、同じ原因でまとめた各レーンの元の文面を並べる（回答は全レーンへ届く）
4. 耐久ワークフローが自分で立てる質問（`kind` が `stall`・`helper`・`spawn`・`observe`・`build`）は `options` で問う。選んだ回答（「再起動する」「続きから再起動する」「止める」）は耐久ワークフローが当てる。`observe` の「ラッパーの環境を作り直す」だけは、回答を送った `answer` が `metrics.next` に `ndf relay status` の 1 行を返すので、それを打つ
5. 回答を送り、下の「回答の後の整理」を通す

回答の種類ごとに読んで動く手順は [loop.md](loop.md) の「回答を読んで動く手順」にある。

| リクエストの `kind` | 質問の回答 | 送るコマンド |
| --- | --- | --- |
| `gate1`（設計の承認） | 承認 / 直して出し直す（指摘を書く） / やらない | `parallel.py answer p1 <id> --approved` / `--revise --note <指摘ファイル>` / `--rejected`。`reasons` にマージできなかった理由があれば添えて問う（利用者へ戻したリクエスト） |
| `gate1` で `loop` を持つ（前のループの待ち） | 設計の承認と同じ。ループの名前を添えて問う | 設計の承認と同じ。回答は耐久ワークフローがそのループの `loop answer` で当てる |
| `gate2`（リリース承認ゲート） | 下の「リリース承認ゲート」 | `confirm` / `settle --rejected` |
| `unmatched`（当たらなかった回答） | `reason` を読んで回答し直しの要否を確かめる。質問として人へ問わず、人の判断が要れば回答したリクエストを添えて伝える | `parallel.py answer p1 <id> --choice 確かめた` |
| `ask`・`stall`・`helper`・`spawn`・`observe`・`build` | リクエストの選択肢 | `parallel.py answer p1 <id> --choice <選んだ回答>` |

`gate1` の `--approved` では、`answer` が回答を送る前に設計 PR をマージ先へマージしてみる（[loop.md](loop.md) の「承認した設計のマージ」）。
結果は `metrics.merge` に載り、回答にも載ってレーンへ届く。マージできなくても回答は送られ、終了コードは 0 である。`answer` はほかに、
回答のイベントを立てるだけで、ラベル・記録・直し・マージし直し・クリーンアップはオーナーのレーンがループの 1 回の境で行う。回答を待って止まったオーナー
（1 スプリントのレーン・記録が `waiting_only` で止まったループのレーン・質問を保留して止まった一時レーン）は、耐久ワークフローが `ndf relay restart` で
再起動する。オーガナイザーは起動しない。オーナーの 1 スプリントのレーンが回答待ちの停止の範囲にあるときは、次に始めるプランで決める。
次に始めるプランに承認の要らないプラン（設計 PR のマージなど）があり、再開のマーカーを持たなければ、範囲の外と同じく再起動する。
それ以外は再起動せず `metrics.held_owners` にレーン名が載り、停止が解けたときに再開のマーカーで起きる。オーナーがループのレーンなら範囲の中でも再起動する。起きたレーンは境で承認の要らない作業（承認した設計の実装など）を選び、無ければ止まり直す。

同じ行の新しいリクエストは、古いリクエストを一覧から外して置き換える（`replaced` に前の id とマーカーが残る）。置き換えた id への回答は今の質問のオーナーへ流れ、
マージのコミットだけの違いなら当たる。当たらないと区分 `unmatched` の質問になる。前のループの待ちは、計画を始めるときとレーンのループの 1 回の境で
届く。同じ行は同じ id で 1 つにまとまり、計画を終えることを止めない。

### 回答の後の整理

出した `AskUserQuestion` は取り下げられず、回答を待つ間に届いたリクエストは回答の後まで表に出ない。回答を受けたら、溜まったリクエストを
整理してまとめて質問し直す。

1. リクエストごとに回答を送る（`parallel.py answer`）。`metrics.merge.result` が `merged`・`already_merged` 以外なら、理由（`reason`）を
   1 行で利用者へ伝える（質問にしない。ループの次の 1 回の境でレーンが結果に応じた手を打つ）。`production` なら、リリース承認ゲートで人が
   マージするまで実装に選ばれないことを添える
2. 最後の `answer` の `metrics.after`（回答の後に残るリクエスト）から、`drop` が付いたリクエストを除く。`settled` は今送った回答と同じ設計 PR のリクエスト、
   `resend` は同じレーンの同じ設計 PR に、より新しい HEAD のリクエストがある古いリクエストである
3. `mvv.eligible` が `true` のリクエスト（設計の承認で、レーンの判定が「判定できない」「判定を読めない」で、レッドラインが空のリクエスト）ごとに、
   `mvv-gate.py check --sprint <リクエストの sprint_state> --gate design --pr <リクエストの pr>` を 1 回だけ打つ。「従う」（終了コード 0）なら
   `parallel.py answer p1 <id> --approved --by mvv` を送る（判定の記録は `mvv-gate.py` が書く）。ほかの結果なら、打ち直さずに残す。
   「従わない」・レッドライン・リリース承認ゲート・区分つきの質問は自分で回答しない
4. 残りがあれば、上の「質問の仕方」の区分の順と 4 件ずつで、まとめて `AskUserQuestion` を出す。残りが無ければ
   `wait p1 --after <metrics.seq>` を背景で打ち直す

リリース承認ゲートは、提示 1 なら「承認」「変更を要求する」で質問、`parallel.py confirm p1 <連番>` か
`parallel.py settle p1 <連番> --rejected` を打つ。出し直しの提示（`represent: true`）なら加わった範囲を添えて
「新しい範囲で出す」「最初の範囲だけ出す」「変更を要求する」で質問、`confirm --take new` / `--take first` / `settle --rejected` を打つ。

`wait` が `action: carried` の知らせを返したら、出し直しを省いた確定の確かめ直し（下の `parallel.py carried`）が通り、新しい範囲で出すことを指す。
回答の時点では返さない。
「承認の後に入った文書だけの Pull Request #<番号>（`metrics.carried.prs`）も含めて出す」と 1 行で利用者へ伝え（質問にしない）、
`wait p1 --after <metrics.seq>` を背景で打ち直す。

### セッションの切り替え

カットポイントでは、質問を出していなければ次の順で切る。引継ぎ文書は `.ndf/handoff/parallel-p1.md` で、「次に実行するコマンド」には
起動と同じ 1 行（新しいセッションの最初の入力）を、「現在地」には新しいセッションが `start` の後に打つ `wait` の 1 行を書く。

1. 「次に実行するコマンド」に起動と同じ 1 行を書く
2. 背景で打った `wait` が残っていれば、その行（`--after <seq>` と、付けていれば `--changes-after <n>`）をそのまま「現在地」に書く
3. その `wait` を `TaskStop <task id>` で止め、完了通知で確かめる。`killed` 以外（`completed` など）で届いたら、止める前に
   `wait` が戻っていた。その結果を上の表のとおりに扱い、回答していない質問があれば先に処理してから 2 からやり直す
4. `ndf-next` を出して切る

**3 を飛ばすと切り替わらない。** オーガナイザーは `wait` を常に背景で打ち直すため、上限で戻る前に切り替えると `wait` のシェルが残る。
残るとラッパーはシグナルファイルを書かず、claude の終了を止める（[waiting.md](waiting.md) の「バックグラウンドの作業を止める」）。
`wait` を止めても耐久ワークフローとレーンは止まらない（止めた後の知らせの扱いは下の「長い待ちの状況報告と切り替え」の手順 3）。

新しいセッションの `start` は動いている `run` をそのまま使い、「現在地」の `wait`（無ければ `wait --after 0`）が回答していない質問を返す。
`start` と `run` は、どの経路でも打ったセッションへオーガナイザーのマーカーを付け、同じ計画の前のセッションのマーカーを外す（`metrics.organizer`）。

### 長い待ちの状況報告と切り替え

`wait` は上限（`--timeout` を省けば 1800 秒）で終了コード 3 で戻る。上限をプロンプトキャッシュの寿命（最後に使われてから 1 時間）より
短くしてあり、戻るたびに報告すればキャッシュは切れない。上限で戻った出力には次が載る。

| 項目 | 中身 |
| --- | --- |
| `summary` | 上限に達したことと、レーンの数え上げ（`status` の要約） |
| `items` | `parallel.py status p1` と同じレーンごとの行。計画を読めなければ空 |
| `metrics.switch.verdict` | 切り替えの判定（`切り替える` / `報告して待つ`） |
| `metrics.switch.reason` | 判定の理由の 1 文 |
| `metrics.switch.inputs`・`cost`・`defaults`・`missing` | 使った材料の値、2 つの費用の見込み、既定値で代えた項、読めなかった材料 |
| `metrics.switch.record` | 判定が `切り替える` のときだけ、再起動の判定の記録へ残す 1 行 |

判定が `報告して待つ` のときは、状況報告をする。`items` のレーンごとに 1 行（レーン名・`state`・`lap`・`issues`・`last_at`）を
利用者へ出し、`metrics.next` を背景で打ち直す。質問にしない。

判定が `切り替える` のときは、次の順に打つ。

1. 引継ぎ文書 `.ndf/handoff/parallel-p1.md` の「現在地」に `metrics.next` の 1 行（`wait p1 --after <seq>`）を書く。「次に実行するコマンド」と
   「進め方」は書き換えない。書けなければ切り替えず、`metrics.next` を打ち直す
2. `metrics.switch.record` の 1 行を打つ（理由「待ち」。書けなくても切り替えは止めない）
3. `ndf-next` を出して切る。戻った `wait` のほかに背景の `wait` が残っていれば、先に上の「セッションの切り替え」の手順 3 で止める。
   新しいセッションは引継ぎ文書を読み、`start` の後に「現在地」の `wait --after <seq>` を打つ。
   切り替えの間に届いた知らせは `seq` より後のイベントとして残っており、その `wait` が返す

`wait` は判定の規則を次の順に見て、最初に当たった行で決める。言語モデルを呼ばない。

| 順 | 条件 | 判定 |
| --- | --- | --- |
| 1 | 回答していない質問（業務時間外に溜めたリクエストも含む）が 1 件以上か、読めない | 報告して待つ |
| 2 | ラッパー（`ndf relay`）の直接の子でない（`ndf relay notice` の `metrics.inside` が偽） | 報告して待つ |
| 3 | 待ちの見込み W を出せない | 報告して待つ |
| 4 | 会話の文脈 C か、新しいセッションの文脈 Q を読めない | W が 4 時間（14,400 秒）以上なら切り替える。ほかは報告して待つ |
| 5 | 上のどれでもない | 報告を続ける費用が切り替える費用を超えれば切り替える。ほかは報告して待つ |

- **待ちの見込み W**: 計画のジャーナルの質問の行（`gate1`・`gate2`・`ask`・`unmatched`）の時刻の間隔のうち、最後の質問から今までの経過 e を
  超えるものだけを選び、`間隔 − e` の中央値を W とする。選んだ間隔が 3 件未満なら W は出せない
- **文脈**: C は会話の記録（`CLAUDE_CODE_SESSION_ID` の記録）の最後の応答の入力 token（入力・キャッシュの読み・書きの和）、
  Q は較正した復元の文脈か、無ければこの会話の最初の応答の入力 token
- **費用**（入力の単価を 1 とする）: 報告の回数 n = ⌈W ÷ 上限の秒数⌉、報告を続ける費用 = n·r·C、
  切り替える費用 = h·r·C + 5·H + 2·Q + q·r·Q + n·r·Q。r はモデルのキャッシュの読み込みの倍率、h・H・q は
  `ndf relay context calibrate` の見込み（標本 3 件以上）で、無ければ h = 3・H = 2,000・q = 5 を使い `defaults` に出す

Opus 5.5 で C が 47 万 token なら、W が 4 時間を超えると切り替える。C が 19 万 token なら 9.5 時間を超えると切り替える。
ラッパーの外では次のセッションが自動で起動しないため、判定は `切り替える` にならず、30 分ごとの報告を続ける。

### 失われた計画

耐久ワークフローが ERROR になったか、耐久の記録（`~/.local/state/ndf/dbos` などの保存先の SQLite）が消えた計画を「失われた計画」と呼ぶ。
受けたリクエスト・質問・回答・リリースの連番・起動したレーンは、計画の保存先の計画のジャーナル（`journal.jsonl` と `checkpoint.json`）に残っている。

- 戻すのは `python3 "$NDF_SCRIPTS/parallel.py" start p1` の 1 回だけである。`run` が耐久の記録を `<キー>.sqlite.retired-<時刻>` へ退避し、
  同じ耐久ワークフローで新しく始めてジャーナルから状態を戻す。結果の `metrics.rebuilt` が true で、`metrics.restored` に戻すリクエストと質問の数・外した行数が載る。
  ジャーナルと耐久の記録を手で編集しない
- 作り直しの後の `wait --after <前の seq>` は、作り直しの後の知らせを取りこぼさない。起動済みのレーンは起動し直さない
- 失われた間もレーンの `request`・`request-ask`・`request-gate2` とオーガナイザーの `answer`・`confirm`・`settle` は受け付け、
  `metrics.queued` が true になる。作り直しの後に反映する
- 放棄する計画は `parallel.py stop p1` で閉じる。閉じた計画は `start` で作り直さない

### 回答待ちの停止

回答を待つリクエストが人の読める量を超えたら、耐久ワークフローがレーンに新しい作業を始めさせず、閾値以下へ戻ったら人の操作なしで再開する。
オーガナイザーが `AskUserQuestion` の回答を待つ間も、セッションが無い間も働く。閾値は止める引き金であり、リクエストは捨てない。

たとえば回答していないリクエストが 8 件の計画へ 9 件目が届くと、全レーンが区切りで止まる。2 件へ回答して 7 件になると、止まったレーンが起きて続きを流す。

| 範囲 | 閾値（既定） | 数えるもの | 止まる時点 |
| --- | --- | --- | --- |
| 計画全体 | `plan`（8） | 回答していないリクエストの全件（`gate1`・`gate2`・`ask` と、耐久ワークフローが立てた質問）。MVV 判定で回答できるリクエストも回答するまで数える | 超えたとき。計画の全レーンが止まり、まだ起動していないレーンを起動せず、新しいリリースを組まない |
| 1 つのレーン | `lane`（3） | そのレーンが送った回答していない `gate1` と `ask`。まとめた質問は送った各レーンへ 1 件ずつ数える | 超えたとき。そのレーンだけが止まる |

- 閾値は設定 `.ndf/pace.json` の `{"parallel": {"answer_limit": {"plan": 8, "lane": 3}}}` で変える。正の整数でない値は既定へ戻り、`check`・`start` が警告を出す
- 同じ原因でまとめた質問と、同じレーンの同じ設計 PR の新旧のリクエストは 1 件と数える。回答した設計 PR の古いリクエストは一覧から外れる。リリースのリクエストは数えない
- 止まるのは区切りである。ループのレーンはループの 1 回の境、1 スプリントのレーンはキューのプランの開始で止まる。動いているプランと流れているリリースは最後まで流す。`ndf plan next` の単発の開始は止めない
- 1 スプリントのレーンが止まるのは、新しい承認を生むプラン（開始のステップから設計を書くステップへ行けるプラン。設計のステージのプラン）を始めるときだけである。設計 PR のマージ・実装・検査・リリースのプランは範囲の中でも流し、キューの結果の行に `answer_hold_ran`（範囲の値とレーン）が載る
- ループのレーンは止まる前に承認の要らない作業を進める。回答の届いた保留したループの 1 回の残りを流し、承認とマージが済んだ設計の課題があれば選んで進む。設計を承認していない課題（新しい承認を生む作業）は選ばず、選べる課題が無いときだけ止まる（[loop.md](loop.md) の「回答待ちの停止の範囲の選定」）
- 止まったレーンは再開のマーカーを置いて自分のラッパーを止める。耐久ワークフローが停止の範囲の外へ戻ったレーンを `ndf relay restart` で起動する。再開を断られると起動の断りと同じに数えて問う
- 再開のマーカーが残る間は計画を終えない。止めたままにするレーンは `parallel.py park p1 --lane <レーン> --clear` でマーカーを消す

### 業務時間外のリクエスト

進め方の設定 `.ndf/pace.json` に業務時間（[pace.md](pace.md) の「業務時間」）があれば、業務時間外の `wait` は設計の承認と質問
（`gate1`・`ask`）を返さずに溜める。業務時間に入った後の最初の `wait` が、回答していないリクエストの全件を `metrics.batch: true` で 1 回に返す。
設定が無いリポジトリの `wait` は今と同じに返す。`answer` の `metrics.after` も同じ表で振り分け、業務時間外に溜めたリクエストは載せず
`metrics.deferred` に件数を載せる（「回答の後の整理」が朝まで溜めるリクエストを質問し直さないため）。

| 業務時間外に届いたリクエスト | `wait` の扱い |
| --- | --- |
| `gate2`・`unmatched`・耐久ワークフローが立てた質問 | 今と同じく返す（溜めると復旧が業務時間まで遅れる） |
| `mvv.eligible` の設計の承認 | 1 回だけ返す。「回答の後の整理」の手順 3 と同じく `mvv-gate.py check` を 1 回打ち、「従う」なら `--approved --by mvv` を送る。ほかの結果なら利用者へ問わず、同じ `wait` を打ち直す（回答の無いリクエストは朝のまとめに入る） |
| ほかの `gate1`・`ask` | 返さずに溜める。今問うリクエストが無ければ終了コード 3 で、`summary` に溜めた件数と業務時間の始まりが載る |
| 業務時間内に示したリクエスト | 溜め直さず、返しもしない（回答が届くまで利用者の手元にある） |

- 業務時間外の `wait` の待ちの上限は、次の業務時間の始まりで切れる。終了コード 3 で打ち直すと、始まりの後の最初の `wait` がまとめを返す
- まとめは上の「質問の仕方」で問う。設計の承認の行には課題の題（`title`）・設計 PR の URL（`url`）・レーンの判定（`verdict`）・MVV 判定のマーカー（`mvv`）が付く。
  `gh` で引けなかった値は `null` で、件数が `metrics.annotate_errors` に載る
- 溜めたリクエストのバックアップは `.ndf/parallel/p1/deferred.json` に置く。リクエストそのものはリクエストの一覧にあり、バックアップが読めなくても失わない（読めなければ溜めたリクエストを作り直し、示したリクエストも次のまとめでもう一度示す）
- 溜めても回答待ちの停止の数え方は変わらない。業務時間外に作る設計は閾値で止まる

## まとめたリリース

リリースのリクエストが届いた時点で流れているリリースも流しているバージョンの要るまとめ（下）も無ければ、他のレーンを待たずに直ちにリリースを組む。リリースの中身は、承認資料を作る時点の `origin/<ベースブランチ>` のコミット（提示 1 の承認したコミット）までの範囲で決まる。範囲に入ったレーンは、リクエストしていなくても結果を受ける。承認したリリースは承認したコミットのまま本番へ入る（リリースのワークフローはそのコミットから `release/v<バージョン>` を切る）。承認の回答の時点で ベースブランチが進んでいても同じリリースをもう一度問わず、加わった範囲（承認したコミットから回答の時点の先頭まで）は次のリリースの範囲に入る。流れているリリースは 1 本までで、範囲に入らないリクエストは今のリリースが終わった直後の次のリリースになる。

マーカー `parallel-approved-sha` の無い記録（この規則より前に始めた計画）の打ち直しだけは今までの道を通る: 回答の時点でベースブランチが進んでいれば加わった範囲を添えて同じリリース承認ゲートを 1 回だけ出し直し（出し直しの提示）、加わった範囲が文書だけ（設定 `.ndf/project.json` の `docs` で分ける。`lib/diff_kinds.py`）なら出し直しを省いて提示 1 の承認を引き継ぐ（一時レーンが `parallel.py carried p1 <連番>` で確かめ直し、文書だけでなくなっていれば提示 2 のリリース承認ゲートで止まる。イベント `range-<連番>` の `added` に確かめ直しの範囲の Pull Request が載る）。

### バージョンの要るまとめ

1 スプリントのレーンのリクエストは、バージョンの要るまとめ（リリース後テスト → 課題を閉じる）のプラン `lane-verify.json` を `verify_plan` に持つ。耐久ワークフローはそのリクエストへ `released` で回答すると待ちを作り、流れているリリースが無いときに、レーンの終わりの記録（バージョンの要らないまとめの完了）がある待ちの先頭を一時レーンで流す。課題を閉じる最終工程はリリース後テストで判定する（振り返りはリリースより前のまとめで済む）。流している間は次のリリースを組まず、待ちが残る間は計画を終えない。自分の Pull Request がすでに本番チャネルにありリクエストを送らなかったときも、`parallel.py request` が待ちを知らせる。リリース後テストが失敗したら課題を閉じずに止まり、結果はジャーナルの `verified` の行に残る。

### リリースの組み方
リクエストを受けるたびに、耐久ワークフローはリリースの組み方を ブランチ戦略の設定の `release.form` と ブランチ戦略の設定の `release.deliveries` から読み直す。

| リポジトリの設定 | リリースの組み方 | リクエストへの回答 |
| --- | --- | --- |
| `release.form` にテンプレートがある | 組む | リリースの結果（`released`・`rejected`・`failed`） |
| `release.deliveries` の行がすべてマージで届くか、`release.deliveries` が `[]` | 組まない | その場で `released`（`version` は `null`）。提示のプラン・リリースのワークフロー・一時レーンは作らない |
| 手動の経路がある、設定が無い・不明・読めない、テンプレートの無い `release.form` | 組めない | その場で `failed` と直す設定を示す理由 |

組まないときの `released` は、オーガナイザーが組むリリースが要らないことを指す。本番系へ届いたことはリリース後テストが確かめる。

組むはずのリリースを組めないとき（出すバージョンを読めない・連番の上限・組み立ての失敗・ブランチ戦略の設定の `release_strategy` が `release_branch`）も同じく `failed` と理由を回答する。`release_branch`（選んで集めるリリース方式）では、各レーンが自分のリリースのプランで出す（`production-merge.md` の「選んで集めるリリース方式のリリース」）。
範囲が決まる前なら受けているリクエストのすべてへ回答、提示の出し直しを組めないときは範囲のリクエストだけへ回答して、残りは次のリリースへ回す。
リリースを組めないことでは計画は止まらない。止めるかは質問 `kind: build`（下の「異常のとき」）への回答で決まる。

## 一時レーン（`--parallel-helper`）

オーナーのいない共有の作業は、耐久ワークフローが起動する一時レーン（`<計画名>-rel<連番>`、役割 `helper`）が行う。
耐久ワークフローはリリースを組んだとき（提示）・リリース承認ゲートの承認を受けたとき（確定）・保留したループの 1 回とバージョンの要るまとめ（`<計画名>-rel<k>v`）を流すときに一時レーンを起動し、
立ち上がりを確かめる（下の「起動と再起動」）。オーガナイザーは一時レーンを起動しない。
最初の入力は次のどれかで、`development-workflow` は判定の手順へ進まずこのセクションの手順で進める。

```text
/goal /ndf:development-workflow --parallel-helper p1 <連番> <提示> -- 終わり: [ndf-parallel] helper-done p1 の行を出し、ndf relay stop p1-rel<連番> で自分のラッパーを止めたとき
/goal /ndf:development-workflow --parallel-helper p1 pending <ループ名> -- 終わり: [ndf-parallel] helper-done p1 の行を出し、ndf relay stop p1-rel<連番> で自分のラッパーを止めたとき
/goal /ndf:development-workflow --parallel-helper p1 verify <リクエスト> -- 終わり: [ndf-parallel] helper-done p1 の行を出し、ndf relay stop p1-rel<k>v で自分のラッパーを止めたとき
```

**リリース（`<連番> <提示>`）:**

1. `python3 "$NDF_SCRIPTS/parallel.py" helper p1 <連番> <提示>` を打つ。`metrics.phase` が流すものを決める
2. `metrics.pipeline` を流す（待ちは背景で打ち、完了の通知を待つ）
   - `phase: present`: 提示のプラン → リリースのワークフローの queue と待ち。提示のプランがリリース承認ゲートで止まったら（done の提示のプランの結果が承認ゲートで止まった値）、
     `metrics.gate2` の 1 行でリリース承認ゲートのリクエストを送り、手順 4 へ進む。流れ切れば手順 3 へ進む。出し直しを省いた確定も
     この流し方で、提示のプランが MVV 判定の代わりに確かめ直し（`carried`）→ 引き継いだ承認の記録 → `approve` を流す
   - `phase: confirmed`: 回答の記録 → 提示のプランを `approve` から → リリースのワークフローの queue と待ち。`approve` が承認ゲート（終了コード 10）で
     終わればリリースのワークフローを流さず、質問として送って手順 4 へ進む
3. `metrics.settle` の 1 行（`parallel.py settle p1 <連番> --done <D>`）を打つ。結果は耐久ワークフローが範囲のレーンへ返す
4. `[ndf-parallel] helper-done p1` の行を出し、最後に最初の入力の「終わり」にある `ndf relay stop <自分の名前>` の 1 行を打って
   自分のラッパーを止めて終える。止めないと対話の claude が入力待ちで残り、続きの一時レーンの起動が同じ名前か上限で断られる。
   回答の後は、耐久ワークフローが続きの一時レーンを起動する。リリース承認ゲートのリクエストか `settle` を送ってから止まるのは手順どおりの停止で、
   「途中で止まった」の質問にならない

CI の失敗・衝突・版数の衝突は、リリースプランの直しの手順（judge・fix）で直す。直せない失敗は質問にする（区分つきの `AskUserQuestion` を
出すと、質問の hook がオーガナイザーへ送り、拒否の理由に保留の手順が返る）。保留したら手順 4 で終える。

**保留したループの 1 回（`pending <ループ名>`）:** `python3 "$NDF_SCRIPTS/sprint-state.py" loop pending <ループ名>` を打ち、`metrics.pipeline` を流す。
`metrics.status` が `none` になるまで繰り返し、手順 4 で終える。別のリポジトリのレーンのループなら、耐久ワークフローがそのリポジトリで
一時レーンを起動し、一時レーンはそのリポジトリで動く。

**バージョンの要るまとめ（`verify <リクエスト>`）:** `python3 "$NDF_SCRIPTS/parallel.py" verified p1 <リクエスト>` を打ち、`metrics.pipeline` を流す（待ちは背景）。終われば `metrics.verified` の 1 行（`--done <D>`）で結果を送り、手順 4 で終える。

一時レーンは並列の計画の `lanes` に載らず、リリースのリクエストを送らない。同時に 1 本までで、同時に動かせる数を 1 本だけ超えて通る。

### 起動と再起動

耐久ワークフローは、一時レーンの起動（提示・確定・保留したループの 1 回）と、回答を受けた止まったレーンの再起動を、耐久ステップ `parallel.launch` で打つ。

1. 打つ前にレーンの状態の一覧（`ndf relay ls`）を読み、そのレーンが動いて（`running` か `awaiting_approval`）いれば打たずに立ち上がったと数える
2. `ndf relay spawn`（一時レーン）か `ndf relay restart`（止まったレーン）を打ち、一覧を 5 秒ごとに読んで立ち上がりを確かめる。上限は 120 秒
   （`NDF_PARALLEL_LAUNCH_SECONDS`）。動いて観えるか、止まっていても最後に動いた時刻が打った後なら立ち上がったと数える
3. 立ち上がらなければ 1 回だけ打ち直す。2 回目も立ち上がらなければ区分 `spawn` の質問（再起動する / 止める）を立てる

起動の目的（リリースの連番と提示とステップ・保留したループ・再起動の回）ごとに結果を起動の記録へ残し、耐久ワークフローを作り直しても記録のある目的は打ち直さない。
質問の回答の「再起動する」は新しい目的として流し、そこでも 1 回だけ打ち直す。

一時レーンの「途中で止まった」の質問（区分 `helper`）は、今の起動の立ち上がりを確かめた後に、その一時レーンが今の起動より後に止まった行を
2 回続けて観たときだけ立つ。リリース承認ゲートのリクエスト・`settle`・その一時レーンの回答していない質問のどれかがあれば立たない。前の起動の止まった行は数えない。

## レーンの側

並列の計画の下のレーン（`NDF_RELAY_NAME` が動いている計画のレーンにある）の本番のステージは、リリースの経路（ブランチ戦略の設定の
`release.form` と `release.deliveries`）で決まる。`ndf progress new` が経路ごとに組むため、conductor は組み上がった
プランを手で置き換えない（本番チャネルへ入れるリリースプランをリリースのリクエストへ書き換えない）。リリースの Pull Request で届く経路では、レーンは本番チャネルへ入れるリリースプランをそのまま流す。

| リリースの経路 | 本番のステージ | レーンがすること |
| --- | --- | --- |
| テンプレートで出す | リリースのリクエストのプラン（ステップ `parallel-request` の 1 つ。フェーズ「リリースのリクエスト」） | リクエストを送る。1 スプリントのレーンのプランは完了で終わって続くまとめのステージへ進み、開発ループのレーンのプランは承認ゲートとして終わる。自分の Pull Request がすでに本番チャネルにあれば、送らずにリリース済みとして続きへ進む |
| リリースの Pull Request | 本番チャネルへ入れるリリースプラン 1 本 | そのまま流す。`pace: auto`・`fast` は MVV 判定が通ると本番チャネルへマージし、通らなければ止まる。`pace: normal` は `promote` がリリース承認ゲートで終わり、承認の後に `--from promote-approved` で続ける。1 スプリントのレーンは続くまとめのステージがまとめと終わりの記録を流す |
| マージで届く | `pace: auto`・`fast` は導入の確認のプラン、`pace: normal` は置かない | そのまま流す。1 スプリントのレーンは続くまとめのステージがまとめと終わりの記録を流す |
| 手で届ける | 手で行うリリースのステージ | 手で行うリリースの手順に従う。オーガナイザーはこの経路のリリースを組めない（上の「まとめたリリース」） |

リリースのリクエストの課題の一覧はプランの `課題` だけが持ち、コマンドの `--issues {plan_issues}` は流す時点の `課題` で埋まる。設計承認ゲートで
外した課題は、リクエストにも本番チャネルへ入れるリリースプランにもまとめにも載らない。レーンで `ndf plan queue` を打つときは
`--max <レーンのプランの本数>`（並列の計画のそのレーンの設定の `plans`）を必ず渡す。省くと触るファイルの重ならないプランをすべて一度に起動し、
マシン全体の本数の判定（設定の `plans` で数える）を超えて流れる。

リリースのリクエストを送ったレーンの続きは次のとおりである。

| レーン | リクエストの後 | 回答が届いたら |
| --- | --- | --- |
| 開発ループ | `loop lap` がループの 1 回を「リリース待ち」で締め、回答を待たずにループの次の 1 回へ進む（[loop.md](loop.md)） | ループの 1 回の境の `loop select` が回答を読み、まとめを流してループの 1 回を締め直す |
| 1 スプリント | 回答を待たずに目録のまとめのステージ（バージョンの要らないまとめ: 確定仕様化 → 振り返り → 棚卸し → マージ → 終わりの記録）を流す | `released` なら耐久ワークフローがバージョンの要るまとめを一時レーンで流す。変更要求と失敗は下の「レーンの終わり」 |

### レーンの終わり

1 スプリントのレーンの終わりは、目録のまとめのステージの最後のステップ `parallel.py end p1 --lane <レーン> [--request <リクエストの記録>]` がジャーナルへ終わりの記録（`lane_end`）を書いた時点で、最初の入力の「終わり」（`[ndf-parallel] lane-end p1 <レーン>`）が指す。conductor は `new close` を自分で組まず、自分のラッパーも止めない。耐久ワークフローが終わりの記録から 60 秒の後に `ndf relay stop <レーン>` を打ち、一覧で止まったかを確かめてジャーナルに `lane_halt` の行を残す（止まらなければ下の「止める」）。`after` の依存と計画の終わりでは、1 スプリントのレーンを終わりの記録があり止まって観えたときだけ止まったと数え、終わりの記録の無い停止は数えない（今のとおり再開のマーカーで起動される）。`end` はリクエストの回答が `rejected` か `failed` なら記録を書かずに承認ゲート（10）で返し、レーンは今のリリース承認ゲートの変更要求と同じに直しを流す。終わりの記録の後に届いた変更要求と失敗は区分 `after_end` の質問になる。マーカー `parallel-lane-end` の無い記録の計画は今までの数え方を通し、その計画のレーンの目録はリクエストの回答を待ってから今までのまとめ（課題を閉じる）を流す（耐久ワークフローのイベント `lane-end` で見分ける）。

設計承認ゲート・リリース承認ゲート（リリースの Pull Request で届く経路の `pace: normal` を含む）・承認ゲートの外の質問は、1 台の中のレーンではオーガナイザーへ送られる（[asking.md](asking.md) の「並列の計画のレーン」）。

回答待ちの停止の範囲に入ったレーンは、区切りで止まる。

| レーン | 止まり方 |
| --- | --- |
| 開発ループ | `loop select` か `loop lap` が `answer_hold` で止まる（[loop.md](loop.md) の「止まる条件」） |
| 1 スプリント | 新しい承認を生むプランを始めるとき、キューがそのプランを流さずに止まる（この止まり方は `ndf plan queue` がまだ持たず、P3 #3097 が `ndf` のサブコマンドに足す。新しいプラグインだけではまだ打てない）。止まったら `parallel.py park p1 --lane <レーン> --done <D>` を打ち、止まる手順なら自分のラッパーを止める 1 行を最後に打って終える。停止が解けたら `ndf plan queue <プラン>... --resume` で続ける |

## 別のリポジトリのレーン

計画の設定のレーンに `repo`（レーンのリポジトリのメインディレクトリ）を書くと、計画の保存先と違うリポジトリのセッションもレーンになる
（同じマシンの同じ利用者に限る）。`parallel.py init`・`start`・`lane add` が計画の保存先を計画の所在の一覧へ書き、別のリポジトリの
セッションはその一覧から自分の計画を見つける。

| 場面 | 振る舞い |
| --- | --- |
| 起動 | 耐久ワークフローがレーンのリポジトリで `ndf relay spawn` を打つ。引継ぎ文書はレーンのリポジトリの `.ndf/handoff/` にある |
| 承認ゲートと区分つきの質問 | 同じリポジトリのレーンと同じく、オーガナイザーのリクエストの一覧に届く（行の `repo` で区別する）。設計の承認の回答では、オーガナイザーがレーンのリポジトリで設計 PR をマージする |
| 本番 | リリースのリクエストを送らず、レーンのリポジトリの設定（`.ndf/supervise.json`）で本番のステージを組む。リリース承認ゲートの質問はオーガナイザーへ届く。まとめたリリースには入らない |
| 回答待ちの停止 | 同じリポジトリのレーンと同じく、レーン名で数える |

レーンの作業の途中で別のリポジトリの改修が要ると分かったときの既定の手順は、[parallel-cross-repo.md](parallel-cross-repo.md) の「別のリポジトリの改修が要るとき」にある。

## レーンの動き方

並列の計画のレーンに共通の規定である。各規定の「起きた例」は、並行開発のモデルの文書（NDF のリポジトリの `docs/ndf-parallel-model.md`）の
「レーンの動き方の規定で欠けているもの」の表の行を指す。

### 形によらない規定

| # | 規定 | 内容 | 起きた例 |
| --- | --- | --- | --- |
| R1 | 役割の変更 | 役割は計画の設定の入力で変え、レーンの名前は変えない | レーンの役割を途中で変える手順 |
| R2 | ループの始め直し | 新しいループの名前を計画の設定へ書いてから始める | ループを始め直すときの計画の更新 |
| R3 | 優先順位の指示 | 優先順位は引継ぎ文書の「次にやること」に書き、画面への入力では伝えない。除く課題は開発ループの除外で指す | 優先順位の指示の届け方 |
| R4 | レーンへの指示の手段 | 指示は引継ぎ文書と計画の設定に書き、レーンはループの 1 回の境とセッションの切り替えで読む。画面への入力は「引継ぎ文書を読み直す」の 1 行だけにする | レーンへ指示を送る手段 |
| R5 | 止まったレーン | 止まったかはレーンの側の記録（ループの記録・引継ぎ文書）で決め、ラッパーの状態だけで決めない | ループが止まったレーンの扱い |
| R6 | 手で起動したレーン | 手で起動するときも、レーンの名前とレーンのリポジトリを計画の設定と一致させる。一致しないセッションはレーンでなく計画の外のセッションとして止まる | 手で起動したレーンの扱い |
| R7 | 計画の外のセッション | 動いている計画があるとき、計画の外の開発ループとスプリントは止まる（基本不許可）。必要ならレーン数の上限を変えて計画へレーンを足す。急ぎの例外は理由を添えて起動する | 計画の外のセッションを止める仕組みとレーンの追加の手順 |

### 1 台だけの規定

| # | 手順 |
| --- | --- |
| R1 | `python3 "$NDF_SCRIPTS/parallel.py" lane p1 set --lane <名> --from <JSON>` で書き換える（書き換えられるキーは `input`・`plans`・`touches`・`after`・`handoff`。`plan.md` を書き直し、耐久ワークフローへ知らせる。在る引継ぎ文書は残し、ループの名前を変えて引継ぎ文書の名が変わったときだけ新しく書く）。`name` と `repo` は変えられない |
| R2 | `lane set` で `input.loop` を書き換え、結果の `items` の `rule: relaunch` の `next`（レーンを止めて新しい最初の入力で起動する 1 行）で再起動する。`ndf relay restart <名>` は前の入力を使い直すため使わない |
| R3 | 引継ぎ文書は `handoff.py` で書き、除く課題は `sprint-state.py loop exclude` で指す |
| R4 | 1 行の入力は `tmux send-keys` で行い、画面へ指示の本文を打たない |
| R5 | `ndf relay ls` の `running` を止まっていない根拠にしない |
| R6 | レーンのリポジトリのメインディレクトリで `ndf relay run --name <レーン名>` を打つ |
| R7 | 下の「レーンを足す」の手順で足す。例外は `sprint-state.py loop start --outside-plan <理由>` で起動する（`ndf progress new` で起動する例外の働きは P1b #3092 が `ndf progress` に足す。新しいプラグインだけではまだ打てない。理由は `<状態の根>/parallel/outside-plan.jsonl` に残る） |

計画の外のセッションの判定は、`sprint-state.py loop start` と `ndf progress new` が何かを書く前に行う。動いている計画が
（計画の所在の一覧と自分のメインディレクトリに）あり、レーン・一時レーン・オーガナイザーのどれでもなく、`--outside-plan` も無ければ、
終了コード 3（`metrics.blocked: true`）で止まり、`items` にレーンの足し方の 2 行が、`next` に例外の起動の 1 行が出る。計画の状態を
読めないときは動いている計画として扱う。動いている計画が無いマシンと、Factory の実行ジョブ（`NDF_ORGANIZER_DIR` か `NDF_FACTORY_RUN`）
では判定せずに起動する。

#### レーンを足す

上限を変えるのは人の指示を受けたときだけである。オーガナイザーは上限の値を人へ問うてから打つ。

1. 足すレーン 1 本の設定を JSON のファイルに書く（形は [parallel-plan.md](../../issue-plan-strategy/references/parallel-plan.md) の
   「レーンごとに決めること」。別のリポジトリなら `repo` を書く）
2. `python3 "$NDF_SCRIPTS/parallel.py" lane p1 add --from <JSON>` を打つ。上限を超えるときは何も書かずに 1 で終わり、`items` に
   `ndf lanes limits <計画> --max-lanes <n> --reason <理由>` の 1 行が出る
3. 人の指示を受けて `ndf lanes limits <計画> --max-lanes <n> --reason <理由>` を打つ（計画の DB の上限の行を変え、計画の検査は次の判定から
   その値を読む）。リレーハブの名前つきのラッパーの数の上限は別の値で、`ndf relay` を打つ環境の `NDF_RELAY_MAX_NAMED`（無ければ
   `contracts/limits.json` の `relay.max-named`）を毎回読む。マシン全体の本数の判定（`ndf lanes run` の中）も同じ環境変数を読む。
   `<n>` がその上限を超えるなら、`ndf lanes stop <計画> --reason <理由>` で区切りまで止め、`NDF_RELAY_MAX_NAMED=<n> ndf lanes start <計画のファイル>`
   で再起動する（レーンの `ndf relay spawn` を打つのは `ndf lanes start` が切り離して起動した `ndf lanes run` で、その環境を引き継ぐ。
   動いている `ndf lanes run` の環境は後から変えられない。打ち直した `start` は止めた所から続く）
4. もう一度 2 を打つ。通ると `plan.json`・`plan.md`・引継ぎ文書を書き、耐久ワークフローへ知らせる。耐久ワークフローが計画を読み直し、
   足したレーンを起動の候補に入れる。計画がまだ動いていなければ、次の `start` で起動する

#### マシン全体のプランの本数

マシン全体のプランの本数の上限と起動の待ちは [parallel-checks.md](parallel-checks.md) の「マシン全体のプランの本数」にある。

## 外のオーガナイザーのレーン（`NDF_ORGANIZER_DIR`）

環境変数 `NDF_ORGANIZER_DIR` があるセッションは、外のオーガナイザー（サービスが実行ジョブの間で動かすまとめ役など）のレーンである。
名前は `NDF_ORGANIZER_LANE` で、リクエストと回答は保存先のファイルで受け渡す（形は `contracts/forms/parallel-external.json`）。
並列の計画（`.ndf/parallel/`）は使わず、計画名の代わりに `--external` を付ける。

| 点 | 決まり |
| --- | --- |
| 本番のステージ | 上の「レーンの側」の表のとおり経路で決まる。テンプレートで出すリポジトリではリリースのリクエストのプラン（`parallel.py request --external`）になり、リクエストを `requests/<id>.json` へ書いて 10 で終わる。自分の Pull Request がすでに本番チャネルにあれば書かずに 0 で終わる |
| 回答 | `parallel.py await --external --from <プランの状態ディレクトリ>/work/request.txt` が `answers/<id>.json` を読む。ループのレーンはループの 1 回の境で読む（上の「レーンの側」と同じ） |
| 質問 | 設計の承認、リリースの Pull Request で届く経路のリリース承認ゲート、承認ゲートの外の質問はリクエストにしない。今どおり止まって人へ戻す |
| 1 台の中のオーガナイザー | 起動しない。`NDF_FACTORY_RUN` がある実行ジョブでは `parallel.py init`・`start`・`run` が 1 で断る |

### リリースの実行（`--parallel-helper --external`）

外のオーガナイザーがまとめたリリース 1 つのために起動するセッションは、次の 1 行で始める。`batch.json` の手（`step`）ごとに 1 手を打って終える。

```text
/goal /ndf:development-workflow --parallel-helper --external -- 終わり: 作業の報告を出したとき
```

1. `python3 "$NDF_SCRIPTS/parallel.py" compose --external` を打つ。`metrics.pipeline` が流すものを決める
2. `metrics.pipeline` を流す（待ちは背景で打ち、完了の通知を待つ）

| `step` | 流すもの | 終わり方 |
| --- | --- | --- |
| `present` / `represent` | 提示 1（`represent` は提示 2）の提示のプラン → リリースのワークフロー | 提示のプランがリリース承認ゲートで止まったら `metrics.record` の 1 行で提示を書き返し、「判断が要る」で終える。流れ切れば手順 3 |
| `confirm:<k>` | 回答の記録 → 提示 k のプランを `approve` から → 提示 k のリリースのワークフロー | 手順 3。確定しない提示のリリースのワークフローは流さない |
| `continue` | 止まったリリースのワークフローを `--resume` で続ける | 手順 3 か、直せない失敗を質問にして止まる |

3. `metrics.settle` の 1 行（`parallel.py settle --external <連番> --done <D>`）を打つ。届いたステップと結果を保存先へ書き、作業の報告で終える

CI の失敗・衝突・版数の衝突は一時レーンと同じくリリースプランの直しの手順で直す。直せない失敗は「判断が要る」で止まる。

## 止める

`python3 "$NDF_SCRIPTS/parallel.py" stop p1` で計画の全レーンへ停止を打ち、耐久ワークフローを終える。リリースの途中なら、リリースが終わる
（`settle` が届く）のを待ってから終える。バージョンの要るまとめを流している間も、結果（`verified`）が届くのを待つ。`--force` を付けると待たずに終え、一時レーン（バージョンの要るまとめを含む）も止める（リリースのワークフローの状態ディレクトリは
残り、`ndf plan queue ... --resume` で続けられる）。止まらないレーンがあれば名前を返して 1 で終わる。1 本だけを止めるのは
`ndf relay stop <名前>` である。

終わったレーンを耐久ワークフローが止められなかったとき（止める 1 行の失敗か、止めた後も一覧で動いて観える）は、区分 `halt` の質問が `commands` に止める 1 行（`ndf relay stop <レーン>`）を持って `wait` に返る。オーガナイザーはその 1 行を打ってから「止めた」と回答する。次の観測でまだ動いて観えれば、同じレーンの質問が新しい ID で立ち直る。

## 異常のとき

耐久ワークフローは次の場面で自分で質問を立て、`questions` で返す。

| 場面 | 質問 |
| --- | --- |
| レーンが承認待ちでも止まってもいないのに、最後に動いた時刻から 60 分（`NDF_PARALLEL_STALL_MINUTES`）を越えた | 再起動する / 止める / 待つ（次の区切りまで問わない）。「再起動する」は耐久ワークフローが `ndf relay restart` を打ち、「止める」は `ndf relay stop <レーン>` を打つ |
| リリースの途中で一時レーンが止まり、`settle` もリリース承認ゲートのリクエストも届いていない（上の「起動と再起動」の条件） | 続きから再起動する / 止める。「続きから再起動する」は耐久ワークフローが同じ一時レーンを起動し直す。「止める」はリリースを失敗として締める |
| ループのレーンの起動が 3 回（`NDF_PARALLEL_SPAWN_REFUSALS`）続けて断られた | 再起動する / 止める。断りの後も起動の条件がそろうたびに耐久ワークフローが打ち直す |
| 一時レーンの起動か止まったレーンの再起動が、打ち直しても立ち上がらない | 再起動する / 止める。「止める」は、計画のレーンなら止まったものと数え、一時レーンならリリースを失敗として締める |
| リリースを組めない（`kind: build`。レーンに結び付けず、依存先のレーンの起動を止めない。回答していない質問のうち同じ理由のものは 1 件にまとまる） | 直してから組み直す / 止める。「止める」は流れているリリースの後に計画を止める。「直してから組み直す」は組めなかったリクエストを組み直しのリクエスト（元の回答は変えない）として入れ直し、次のリリースで扱う |
| レーンの状態の一覧（`ndf relay ls`）の失敗が、同じ区切りより長く続いた（失敗した回の観測は捨て、レーンの状態を変えない） | ラッパーの環境を作り直す / 待つ（次の区切りまで問わない）。一覧が成功に戻れば質問は外れる |
| 1 スプリントのレーンが終わりの記録も回答待ちも再開のマーカーも無いまま、同じ区切りより長く止まって観えた（区分 `unended`） | 終わったと数える / 再起動する / 待つ。「終わったと数える」は書き手 `organizer` の終わりの記録にし、止める 1 行は打たない |
| 終わりの記録の後に、そのレーンのリクエストが `rejected` か `failed` で回答できた（区分 `after_end`） | レーンを足して直す / 見送る。終わったレーンは起動しない。直すなら `commands` の `lane add` の 1 行でレーンを足す |
| バージョンの要るまとめの一時レーンが `verified` を送らずに止まった | 続きから再起動する / 止める。「止める」は待ちから外す（課題は閉じない） |

全レーンが止まっても、回答していないリクエストか質問・再開のマーカー・バージョンの要るまとめの待ちが残る間は終えない（前のループの待ちの質問は除く）。

回答を当てられないときと、前のループの記録を読めないときも `kind: unmatched` の質問を立てる。一覧に無いリクエストへの回答は保留され、そのリクエストが届けば
質問は外れて回答が当たる。

### レーンの画面を見るとき

レーンの状態は先に `parallel.py status p1` で読む。画面は、人が求めたときか `status` で分からないときだけ見る。
レーンは既定の tmux とは別のサーバーで動く。`tmux ls` には出ず、`tmux -L ndf-relay ls` と
`tmux -L ndf-relay capture-pane -p -t <レーン>` で見る（人が入るのは `tmux -L ndf-lanes attach -t <レーン>`）。

**画面の入力欄（`❯` の行）の文字は、判断の材料にしない。** Claude Code やエディタのサジェストが薄い色で出ており、
`capture-pane` は色を落とすため、人が打った文字と区別できない。サジェストを「送信されていない人の指示」と読むと、
誰も出していない指示で再起動を止める（2026-11-04、計画 p3 の lflow で起きた）。レーンを再起動するかは、
`[ndf-loop] stopped` の行と `ndf relay ls` の状態だけで決める。

## 数え方

オーガナイザーのセッションは `ndf relay spawn --role organizer --plan p1` のマーカーを持ち、同時に動かせる数（`NDF_RELAY_MAX_NAMED`）に数えない。
同じ計画のマーカーは 1 本のセッションだけが持つ（別のリポジトリの同じ名前の計画とは、計画の保存先の絶対パスで分ける）。
既定のままで、オーガナイザー 1 本とレーン 3 本が同時に動く。一時レーン（`ndf relay spawn --role helper`）は同時に 1 本までで、
上限を 1 本だけ超えて通る。
