# レビュー観点

[← SKILL.md](../SKILL.md)

リファクタリングのレビューは、通常の Pull Request レビューとは見るところが違う。
**「良くなったか」より先に「変わっていないか」を見る。**

`prompts/review.md` がこの表をレビュープロンプトへ埋め込む。

| 観点 | 具体的に見るもの |
| --- | --- |
| 振る舞い不変 | 公開インタフェースの入出力、例外種別、副作用の順序、境界条件 |
| テストの妥当性 | 現状固定テストが実際にその経路を通しているか、実装詳細に結合していないか |
| 手法の適合 | 宣言されたスメルに対して手法が妥当か、別の手法の方が適切でないか |
| 範囲の逸脱 | 提案した手順の範囲を超えた変更が混ざっていないか、機能変更が混入していないか |
| 改善の実質 | 行数が動いただけでなく、責務・依存・可読性が実際に改善しているか |
| コミット分割 | 改名と中身の変更が同一コミットに混ざっていないか、1 手 1 コミットか |
| 性能退行 | ループの入れ替え、呼び出し回数の増加、N+1 の発生 |

## 振る舞い不変を筆頭に置く理由

機械的に検証できるのは「テストが通った」ところまでである。**テストが無い経路の振る舞いが
変わっていないこと**は、テストでは示せない。ここだけは人（この場合は別ランタイム）が
読むしかない。

疑わしければ、レビュー担当は自分の作業ディレクトリでテストを実行してよい。
読み取り用の作業ディレクトリを参加者ごとに分けているのはこのためである。

## 機能変更の混入は機械判定できない

`merge-apply` が検証するのは、コミットの分割・トレーラー・テストの成功・差分予算までで
ある。「この差分は振る舞いを変えていないか」は判定できない。**レビュー観点の 4 番目と
5 番目は、機械検証の穴を埋めるためにある。**

同じ差分に機能変更と構造改善が入っていると、レビュー担当は「意図した振る舞いの変更」と
「構造改善の事故」を区別できない。混入を見つけたら、その改善項目は変更要求にする。

## 指摘の書き方

- **1 コメント = 1 修正アクション。** 観察・感想・現状説明だけのコメントは書かない
- `[重要度 / 観点]` を先頭に付ける（例: `[major / 振る舞い不変]`）
- 本文の冒頭に **`Item-Id: R1-001`** を必ず書く。どの改善項目に対する指摘かを
  示すためで、これが無いと取り消しの範囲を決められない
- ラウンド全体に対する指摘は `item_id` を **`null` と明示**する。省略は差し戻しになる
- 「良い点」の節は書かない。解決すべきスレッドが増えるだけで、収束を遅らせる

## 判定

`APPROVE` と `REQUEST_CHANGES` の 2 値だけを使う。**`COMMENT` は使わない。**

リファクタリングは必須の作業ではない。疑義が残るなら通さない側に倒してよい。
修正ラウンドの上限に達した改善項目は自動で取り消されるので、
**通さないことの代償は「その改善が入らない」だけ**である。
