# progress-tracking の抜粋

## 呼び出し

bash "$SCRIPTS/projects-sync.sh" <課題番号> <キー> "<値>"

- `stage`: 工程に入るたび（課題ごと）。値は工程名
- `mode`: 最初の工程で 1 度。値はモード
- `worktree`: 作業場所の用意の後に 1 度。値はworktree のパス
- `plan`: 計画の後に 1 度。値は実装計画のファイルのパス

## 結果の読み方

標準出力は 1 行の結果 JSON である（形と状態の意味は `$SCRIPTS/lib/README.md` の「手順のスクリプトの結果」）。
`ERROR:` / `NOTE:` の行は標準エラーへ出る。**記録できなくても工程は止めない。**

| 終了コード | 意味 | 次にすること |
| --- | --- | --- |
| 0 | 本文へ記録した・変える内容が無かった。ボードも記録した（宣言が無ければ `items` の board が `not_declared`） | 先へ進む |
| 6 | 本文かボードのどれかを書けなかった（`gaps` に書けなかったものと理由） | `summary` と `gaps[].reason` を報告の「見つけたもの」へ載せて先へ進む |
| 3 | `gh` が無い（通過記録は積んだ） | 同上 |
| 1 | 何も書けなかった | 同上 |
| 2 | 知らないキー・工程表に無い値・引数の不足。何も書かれていない | 値を直して打ち直す |

**`items` に `kind: "stage-missing"` の要素があれば、どの終了コードでも先に記録し直す。** `配布` を記録したときに、
記録の無い必須の工程（`result: "missing"`）か条件付きの工程（`result: "conditional"`）がある。実施済みの工程は
要素の `reason` のコマンドで記録してから先へ進む。

## 判断の基準

- 工程に入った時点で打つ。出るときではない
- 値は引用符で囲む（`Pull Request` のように空白を含む工程名がある）
- 1 回の実行に並べてよい。番号を変数で書いてもよい（記録のスクリプトが自分で通過記録へ積む）
- 打つのはその工程を行った側。worker は打たない
- ボードの `Status` を `Done` にするのは「スプリントを閉じる」だけ。そのときは本文を読む
- 他のリポジトリの課題は `progress-record.sh --repo` を使う。そのときは本文を読む
