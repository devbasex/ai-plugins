# 工程の進行を記録する

いまどの工程まで終わったかを、セッションの外へ残す。**判定したモードも、通った工程も、
記録しなければ会話の中にしか残らない。** セッションが変わると引き継がれない。

**この Skill は順序を持たない。** 工程表には載らず、モードごとの要否も持たない。どの工程からも
呼ばれる（`out-of-scope` と同じ扱いである）。**例外は「スプリントを閉じる」の 1 つだけである。**
そちらは**最終工程を出るときに 1 度だけ**行う（契機が違う）。

## 何を記録するか

| 記録先 | 何が残るか | 要る条件 |
| --- | --- | --- |
| issue の本文 | 工程のチェックリスト・モード・worktree・実装計画のファイル | `gh` が使えること |
| ボード（GitHub Projects） | 工程・モード・worktree・計画ファイル | リポジトリに `.ndf/projects.json` があること |

**ボードの設定が無いリポジトリでも issue へ残る。** 設定はボードへ書くかどうかだけを決める。

**この記録を判定の入力に使わない。** 工程の飛ばしの検知は通過記録が担う
（`development-workflow` の `references/stage-completeness.md`）。ここに残すのは、**人が
セッションの外から現在地と成果物の所在をたどるためのもの**である。

## この文書が受け取る値

| 変数 | 値 | 決め方 |
| --- | --- | --- |
| `$SCRIPTS` | プラグインの `scripts/` の絶対パス | [references/scripts-lookup.md](../development-workflow/references/scripts-lookup.md)。シェルが変わったら決め直す |

## 呼び方

**工程に入った時点で 1 度、進捗記録を 1 行打つ。** 入った時点で記録
すれば、途中で止まった実行の現在地が残る。**この 1 行で issue の本文の `## 進行` とボードの
両方に残り、`stage` / `mode` / `pace` は通過記録にも積まれる。** この Skill の本文を読まなくても記録できる。

**通過記録へ積むのは記録のスクリプト（`progress-record.sh`）自身である。** hook には依らないため、ランタイム（Claude Code・Codex・Kiro CLI・agy）・Skill の起動の有無・
`supervise.py` の子プロセスのどれから呼んでも積まれる。`projects-sync.sh` は中で
`progress-record.sh` を呼び、1 回の記録で積むのは 1 件である。

```bash
bash "$SCRIPTS/projects-sync.sh" <issue番号> <キー> "<値>"
```

| キー | 打つ時点 | 値 | issue の本文 |
| --- | --- | --- | --- |
| `stage` | 工程に入るたび（課題ごと） | 工程名 | チェックを付ける |
| `mode` | 最初の工程で 1 度 | モード | 見出し行だけ |
| `worktree` | 作業場所の用意の後に 1 度 | worktree のパス | 見出し行だけ |
| `plan` | 計画の後に 1 度 | 実装計画のファイルのパス | 見出し行だけ |
| `status` | 「スプリントを閉じる」だけ | `Done` | 書かない（ボードだけ） |

**値は引用符で囲む。** 工程名には空白を含むもの（`Pull Request`）がある。囲まないとシェルの
側で分割され、引数のチェックで終了コード 2 になる。**1 回の実行に何件並べてもよく、課題番号を
変数で書いてもよい**（`for n in 11 12; do …; done`）。どの呼び出しも自分で通過記録へ積む。

```bash
bash "$SCRIPTS/projects-sync.sh" 186 stage "設計"
bash "$SCRIPTS/projects-sync.sh" 186 mode "standard"
```

**呼ぶ側へ渡す抜粋は [references/excerpt.md](references/excerpt.md) にある。** supervisor や
worker の起動指示へはこれをコピーし、本文を読ませない。

**`progress-record.sh` を直接呼ぶのは 2 つの場合だけである。** 他のリポジトリの課題へ書く
（`--repo`。ボードへは書かない）ときと、付随情報を足す（`--note`）ときである。

**`配布` を記録したとき、記録の無い必須の工程があれば、同じ呼び出しの標準出力に案内が出る**
（`記録なし:` / `条件付き:` の行と、記録し直すコマンド）。実施済みであれば記録してから先へ進む。

**最終工程でボードの `Status` を `Done` にするのは、下の「スプリントを閉じる」だけである。**
工程に入った時点の記録では書かない。工程の開始時に書くと、ボードの `Auto-close issue` が先に課題を
閉じ、`閉じた` として数えるはずの課題が `既に閉じていた` になって reopen の手段が報告から
落ちる。issue の側は工程のチェックリストが埋まることで表せるため、この値はボードにだけ書く。

**工程名の一覧は工程表が持つ。** この Skill は一覧を持たない
（`development-workflow` の「モードごとに起動する Skill」の表が唯一の基準である）。一覧に
無い値を渡すと、どちらのコマンドも終了コード 2 で弾く。

## 何もしない条件

**進行管理が理由で開発の工程を止めない。** 次のいずれでも、理由を 1 行出して終了コード 0 で
終わる。

| 条件 | どちらが止まるか |
| --- | --- |
| `gh` が無い | issue とボードへの記録（通過記録は積む） |
| issue を取得できない | issue への記録 |
| リポジトリを特定できない・`jq` が無い・通過記録が使用中 | 通過記録（`NOTE:` を 1 行知らせる） |
| `.ndf/projects.json` が無い | ボードへの記録 |
| ボードへの問い合わせが上限に達した | ボードへの記録（1 行知らせる） |
| ボードにアイテムが無く、追加もできない | ボードへの記録（1 行知らせる） |

**呼び出し側の誤りだけは 2 を返す。** 知らない工程名・引数の不足がこれにあたる。黙って進むと、
綴りの違う値が入るか、書き込んだつもりの値が入らない。

## issue の本文に残る形

```markdown
## 進行

モード: standard / 作業ツリー: `.worktrees/feat/issue-243`

- [x] 作業場所の用意 — 2026-09-04 06:12
- [x] 要求と受け入れ条件 — 2026-09-04 06:40
- [ ] 設計
- [ ] ドキュメント再構成
- [ ] ドキュメントレビュー
```

- **節の外は書き換えない。** 更新のたびに本文を取得し、`## 進行` の見出しから次の見出しまで
  だけを差し替える。人が本文へ書いた内容は残る
- **飛ばした工程は空欄のまま残る。** チェックの穴として見える
- **判断を伴う場面だけコメントを残す。** モードを途中で上げた・工程を意図して飛ばした・
  受け入れ条件を変えたの 3 つは、本文を見ても理由が分からない

## ボードの設定

ボードへも残す場合の設定ファイル・フィールド・工程との対応は
[references/projects-tracking.md](../development-workflow/references/projects-tracking.md)
にある。アイテムの追加・識別子のキャッシュ・ボードが決まらないときの扱いは
[references/board.md](references/board.md) にある。

## 工程の単位と記録する課題

**工程が動く単位は 3 つある。** 記録する側は「その工程を行った側」で、記録する先は単位に
含まれる課題すべてである。**誰が書くかを決めておかないと、supervisor が行った工程だけが埋まり、
オーケストレーターが行った工程が空欄のまま残る。**

| 工程の単位（`parallel-work.md` の表） | 記録する側 | 記録する課題 |
| --- | --- | --- |
| 課題 | その課題を扱う supervisor | その課題 |
| Pull Request（後片付けを含む） | その工程を行った側。後片付けはマージした側 | その Pull Request の本文の GitHub の closing keywords（PR 本文に `Closes #123` のように書くと、マージ時にその課題を自動で閉じる機能）が指す課題すべて |
| スプリント（確定仕様化・リリース・体裁レビュー・リリース後テスト・振り返り） | その工程を行った側。リリース以降はオーケストレーター | スプリント課題すべて |

**記録は 1 回の実行に課題を並べてよい。** どの記録も記録のスクリプトが自分で通過記録へ積むため、
並べても・課題番号を変数で書いても、本文と通過記録は食い違わない。

**他のリポジトリの課題へは `progress-record.sh --repo` だけを使い、`projects-sync.sh` を
呼ばない**（理由は次の節の箇条書き）。

## スプリントを閉じる

**契機は最終工程を出るときである。** この手順はそこで **1 度だけ**行う。
**最終工程とは、棚卸しの前にその実行で最後に通る工程である**（工程表は `development-workflow` の
「モードごとに起動する Skill」。`operation` のリリース後テストと振り返りはそれぞれ条件付き）。
検証リリースで止めた実行も、その実行の最終工程でこの手順を行う。課題は閉じる条件に
当たらず OPEN のまま残り、後で本番へのリリースを行った実行の最終工程が改めて行う。

**正本はここだけである。** 呼ぶ側は手順をコピーせず、この節を指す。worker は呼ばない
（supervisor か conductor が呼ぶ）。

| 呼ぶ Skill | 呼ぶ時点 | 呼ぶ条件 |
| --- | --- | --- |
| `retrospective` | 記録を投稿した後 | 振り返りを通る変更 |
| `release-verification` | 検証結果を記録した後 | 後に振り返りが続かない変更（振り返りを通らない `operation`） |
| `release` | 配布を終えた後 | 後にリリース後テストも振り返りも続かない変更（`light`、どちらも通らない `operation`） |

**閉じた後は、工程表の次の工程 `棚卸し`（`backlog-refinement`）へ進む。「スプリントを閉じる → 棚卸し」の
順序の正本はここである。** 逆にすると、`backlog-refinement` の手順 1 が読む「このスプリントで閉じた課題」が
まだ閉じていない。呼ぶ側の Skill は棚卸しを呼ばない（棚卸しは工程表の行として、同じフェーズの担当が始める）。

**利用者の入力を求めない。** 閉じる判断は、スプリントの工程を通ったことで既に済んでいる
（実行前確認の要否の基準は `AUTHORING.md`）。閉じた課題と reopen の手段を報告へ載せる。

### 手順

次のコマンドを打ち、結果 JSON の `status` を見る。記録の PR は配布の記録を置いた PR である
（別の実行なら `retrospective` の「Pull Request の番号を特定する」で引く）。

```bash
python3 "$SCRIPTS/sprint-close.py" --record-pr <記録のPR番号> \
  [--with-verification] [--label "<マイルストーン>の<工程名>"] [--prs <番号,番号>] [--dry-run]
```

- `--with-verification`: リリース後テストを通る経路で付ける（閉じる条件 2 を見る）
- `--prs`: 同じ実行の中で `release` が承認の提示に並べた一覧を渡すとき。省けば最後の
  「## 配布の記録」の `スプリント:` の行を使う
- スクリプトが行うこと: 配布の記録の読み取り → closing keywords（`Closes #N` などの記法）が指す課題の収集 → 閉じる条件の判定 →
  課題ごとに「状態を読む → 記録のリポジトリの課題ならボードを Done → 読み直して OPEN なら閉じる →
  読み直して CLOSED を確かめる」。他のリポジトリの課題にはボードを書かない

| `status`（終了コード） | 次にすること |
| --- | --- |
| `ok`（0） | `items` の表を報告に貼り、棚卸しの工程へ進む |
| `stopped`（1） | 失敗した課題がある。`items[].reason` と `cmd`（やり直すコマンド）を報告し、最終工程を完了と報告せず、棚卸しへ進まずに止まる |
| `stopped`（2） | スプリントの PR の一覧が取れない。推測せず運用者に一覧を聞き、`--prs` で打ち直す |
| `stopped`（3） | 呼び出しの誤り。引数を直して打ち直す |

`items[]` の `kind: "issue"` の `result` は次の 4 つのどれかになる（`--dry-run` では
`would_close` も出る）。`kind: "board_note"` はボードの NOTE で、報告にそのまま載せる。

| `result` | 意味 | 報告に載せるもの |
| --- | --- | --- |
| `closed` | 閉じた（ボードの自動化が閉じた場合を含む） | 番号と `cmd`（戻し方 `gh issue reopen`） |
| `already_closed` | 手順の前から閉じていた（既定ブランチへのマージで GitHub が閉じた場合を含む） | 番号 |
| `failed` | 状態を読めない、または閉じた後も CLOSED でない | 番号・`reason`・`cmd`（やり直す `gh issue close`） |
| `kept_open` | 閉じる条件に当たらない | 番号と `reason`（いつ閉じるか） |

**`kept_open` は止める理由にしない。** 棚卸しへ進んでよい。

### 閉じる条件

| # | 条件 | 満たさないとき |
| --- | --- | --- |
| 1 | 最後の「## 配布の記録」の `段階:` が `本番` または `配布なし` で始まる | スプリント課題すべてを OPEN のまま残す |
| 2 | リリース後テストを通る経路では、その課題の受け入れ条件がすべて `合格` | その課題を OPEN のまま残す |

**検証リリースは閉じる条件を満たさない。** 利用者が常用する版にまだ届いていない段階で、
確かめていないことが終わったように見える。

### 配布の記録

**配布の記録は Pull Request に置く。** 書く側はこの形で書き、`sprint-close.py` はこの形だけを読む。

| 記録 | 書く形 | 置く側 | 置き場所 |
| --- | --- | --- | --- |
| 配布の記録 | 見出し `## 配布の記録` の直後に `段階: <検証 / 本番 / 配布なし>（本番なら承認を得た時点、止めたなら理由、配布なしなら飛ばした理由）`・`版: <前の版> → <新しい版>（<根拠>）`（`配布なし` のときは書かない）・`スプリント: PR #<番号> / #<番号>` の行が続くブロック。終わりは次の `## ` 見出しか入力の終わり | `release`（スクリプトで組む本番のリリースプランでは、本番の配布の後に `release-steps.py record` が書く） | 配布の Pull Request の本文。配布の形が Pull Request を作らないときと配布を飛ばしたときは、スプリントの最後にマージした Pull Request へ同じブロックをコメントで投稿する |
| リリース後テスト | `## リリース後テスト` から `合否:` までのブロック。`対象の版: <配布した版>（<配布した時刻>）` の行と、列が `課題`（`#<番号>`、他のリポジトリなら `<所有者>/<リポジトリ>#<番号>`）/ 受け入れ条件 / 実行したこと / 実行時刻 / 結果 の表を持つ | `release-verification` | 上と同じ Pull Request へコメントで投稿する |

読むのは本文とコメントを投稿の順に並べたうちの最後の配布の記録 1 つで、リリース後テストは
`対象の版:` が本番の版と一致する最後のブロック（`配布なし` ならその記録より後の最後のブロック）を使う。

## 関連

- `/ndf:development-workflow` — 工程名の一覧（工程表）
- `/ndf:out-of-scope` — 同じく順序を持たない横断的な手順
- `/ndf:release` — 配布の記録を置く工程。後に工程が続かなければ「スプリントを閉じる」を呼ぶ
- `/ndf:release-verification` — リリース後テストの記録を置く工程
- `/ndf:retrospective` — 振り返りを通る変更で「スプリントを閉じる」を呼ぶ工程
