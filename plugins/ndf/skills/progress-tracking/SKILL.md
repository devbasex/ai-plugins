# 工程の進行を読み、スプリントを閉じる

いまどの工程まで終わったかは、スプリントのステートマシン（`ndf progress`）が持つ。**記録を打つ手順は無い。**
工程を流すプラン（`ndf plan`・`ndf route`）が終わった工程に終了のマーカーを付け、そのマーカーから課題とスプリントの
Pull Request の本文を書き直す。この Skill が持つのは、記録の読み方と、最終工程の後に 1 度だけ行う「スプリントを閉じる」である。

**この Skill は順序を持たない。** 工程表には載らず、モードごとの要否も持たない（`out-of-scope` と同じ扱いである）。
**例外は「スプリントを閉じる」の 1 つだけで、最終工程を出るときに 1 度だけ行う。**

## 何が記録されるか

| 記録先 | 何が残るか | 書き手 |
| --- | --- | --- |
| ステートマシン | 工程ごとの状態（終わった・飛ばした・中止）と時刻・理由、承認ゲートの回答 | `ndf progress` と、工程を流すプラン |
| 課題の本文の `## 進行` | モードと、工程表の全工程のチェックリスト | ステートマシンの終了のマーカーから作り直す（手で書かない） |
| スプリントの Pull Request の本文の `## 通した工程` | 終わった工程の並び | 同上 |

**この記録を判定の入力に使わない。** 工程の飛ばしの検知は通過記録が担う
（`development-workflow` の `references/stage-completeness.md`）。本文のセクションは、**人がセッションの外から現在地を
たどるためのもの**である。

**supervisor と worker は記録を打たない。** 工程の終わりはプランが付ける。conductor が手で状態を変えるのは、
下の「conductor の操作」に当たるときだけである。

## 現在地を読む

```bash
ndf progress show <ステートマシンの ID>
```

結果は 1 行の結果 JSON である（形と終了コードの意味は [終了コードと停止理由](../../docs/contracts/exit-codes.md) と
[結果のコントラクト](../../contracts/schemas/result.schema.json)）。止まっていたら `summary` と `next` を読む。
セッションの外からは、課題の本文の `## 進行` を読む。

**呼ぶ側へ渡す抜粋は [references/excerpt.md](references/excerpt.md) にある。** supervisor や worker の起動指示へは
これをコピーし、本文を読ませない。

```markdown
## 進行

モード: standard

- [x] 作業場所の用意 — 2026-09-04 06:12
- [x] 要求と受け入れ条件 — 2026-09-04 06:40
- [ ] 設計
- [ ] ドキュメント再構成 — 無効（文書を変えない）
<!-- ndf:section-end -->
```

- **セクションの外は書き換えない。** 見出しから終わりのマーカーまでだけを差し替えるため、人が本文へ書いた内容は残る
- **飛ばした工程と中止した工程は、チェックの無い行に状態と理由が付く。** 何も付かない空欄は、まだ通っていない工程である
- **判断を伴う場面だけコメントを残す。** モードを途中で上げた・工程を意図して飛ばした・受け入れ条件を変えたの 3 つは、
  本文を見ても理由が分からない

## conductor の操作

工程表のとおりに進まないときだけ、conductor がステートマシンの状態を変える。どれも理由を残す。

| したいこと | コマンド |
| --- | --- |
| 工程を飛ばす・飛ばしを戻す | `ndf progress disable <ID> <工程> --reason "<理由>"`・`ndf progress enable <ID> <工程> --reason "<理由>"` |
| 工程をやり直す | `ndf progress retry <ID> <工程> --reason "<理由>"` |
| プランの外で済ませた工程を終える（supervisor で回したフェーズの工程を含む） | `ndf progress finish <ID> <工程> --output <工程の出力の JSON> --reason "<理由>"`。出力の `outputs` に要る文脈のキーは `show` の各行の `outputs`、型は [context.schema.json](../../contracts/workflow/context.schema.json) |
| スプリントを中止する | `ndf progress cancel <ID> --reason "<理由>"` |

**どのサブコマンドも `--cwd <パス>` で対象のリポジトリを渡せる。** 既定はカレントディレクトリで、git の外で打つと止まる。

**supervisor のフェーズレポートを受け取ったら、レポートの `終えた工程` に挙がった工程だけを、その行の出力の JSON を `--output` に渡して `finish` で 1 行ずつ終える。** 規約は
`development-workflow` の `references/agent-layers.md` の「conductor → supervisor」にある。

**工程名は工程表の行名で渡す。** 一覧は `development-workflow` の「モードごとに起動する Skill」の表が唯一の基準で、
この Skill は持たない。値は引用符で囲む（`Pull Request` のように空白を含む工程名がある）。

**本文を書けなくても工程は止めない。** 本文の書き直しに失敗しても工程は進み、結果 JSON に書けなかった保存先が載る。
`summary` を作業の報告の「見つけたもの」へ載せて先へ進む。

## スプリントを閉じる

**閉じる時点の決まりの SSOT はこのセクションだけである。** 呼ぶ側（Skill・まとめのプラン・`pr`）は閉じる時点と順序と
閉じる条件を写さず、このセクションを指す。worker は行わない（supervisor か conductor が行う）。

**課題を閉じてよいのは、その課題がその実行の最終工程を終えたときだけである。**
**最終工程とは、棚卸しの前にその実行で最後に通る工程である**（工程表は `development-workflow` の
「モードごとに起動する Skill」。`operation` のリリース後テストと振り返りはそれぞれ条件付き）。
開発版のデプロイで止めた実行は、課題が閉じる条件に当たらず OPEN のまま残り、後で本番へのリリースを行った実行の
最終工程が改めて行う。

| 行う側 | 行う時点 | 行う条件 | 最終工程 |
| --- | --- | --- | --- |
| `retrospective` | 記録を投稿し、課題の本文に辿る経路の行を足した後 | 振り返りを通る変更 | 振り返り |
| `release-verification` | リリース後テストの記録を書いた後 | 後に振り返りが続かない変更（振り返りを通らない `operation`） | リリース後テスト |
| `release` | デプロイを終えた後 | 後にリリース後テストも振り返りも続かない変更（`light`、どちらも通らない `operation`） | デプロイ |

**閉じた後は、工程表の次の工程 `棚卸し`（`backlog-refinement`）へ進む。「スプリントを閉じる → 棚卸し」の
順序の SSOT はここである。** 逆にすると、`backlog-refinement` の手順 1 が読む「このスプリントで閉じた課題」が
まだ閉じていない。呼ぶ側の Skill は棚卸しを呼ばない（棚卸しは工程表の行として、同じフェーズの担当が始める）。

**利用者の入力を求めない。** 閉じる判断は、スプリントの工程を通ったことで既に済んでいる
（実行前確認の要否の基準は `AUTHORING.md`）。閉じた課題と reopen の手段を報告へ載せる。

### 手順

閉じる操作のサブコマンドは無い。条件 2 の判定だけを `ndf records close-check` で行い、ほかは `gh` で読んで手で閉じる。

1. **記録の PR を決める。** リリース記録を持つ PR である（下の「リリース記録」。別の実行なら `retrospective` の
   「Pull Request の番号を特定する」で引く）。`ndf release-steps records --pr <記録のPR>` で最後のリリース記録を読む
   （write 以上の権限を持つ書き手の記録だけを読む。`gh pr view --json comments` で数えると、権限を持たない書き手の記録まで候補に入る）。
   **workflow でリリースする形では、そのリリース記録の `included` から次の順で 1 本を選び、記録の PR にする。**
   `included` を小さい順に `ndf release-steps records --pr <PR>` で読み、`outputs.releases`（リリース記録のすべて）に同じバージョンの記録が無い PR は飛ばす
   （書き込みが一部の PR で失敗した場合など）。照らすのは最新の `outputs.release` 1 件でなく `outputs.releases` のすべてである。
   後から別のバージョンのリリース記録が付いた PR や、単位ごとに別のバージョンの記録を持つ PR も、書く側と同じく候補に入れるためである
   1. 同じバージョンのリリース記録と、同じバージョンのリリース後テストの記録（`outputs.verifications`）を両方持つ PR のうち番号が最も小さいもの
   2. 無ければ、同じバージョンのリリース記録を持つ PR のうち番号が最も小さいもの

   先に 1 を見るのは、部分失敗からの再実行で小さい番号の PR へ後からリリース記録が付いても、読む先を記録のある PR から動かさないためである。
   書く側（`release-verification` の「出力物」と `ndf release-steps verification-record` が示す `items[]` の先頭）も同じ規則で選ぶ
2. **スプリント課題を集める。** リリース記録の `included` の PR ごとに `gh pr view <PR> --json body` で本文を読み、
   closing keywords（`Closes #N` などの記法）と参照（`Refs #N`。下の「既定ブランチ宛ての Pull Request の参照」）が指す課題を集める。PR の本文が
   指さない課題（`pace: fast` の実装 PR など）は、閉じる理由を確かめてから足す。0 件なら推測で足さず、PR が参照した番号を
   報告に並べて止まる
3. **課題ごとに閉じる条件を確かめる**（下の「閉じる条件」）。条件 2 はリリース後テストの記録の JSON をファイルへ写して打つ

   ```bash
   ndf records close-check <課題> --verification <リリース後テストの記録の JSON> [--require]
   ```

   リリース後テストを通る経路（最終工程が `リリース後テスト`、または後に振り返りが続く）では `--require` を付ける。
   結果が `ok` でなければ、その課題は閉じない（`items[].reason` が理由）。結果は次の 3 つである

   | 結果 | 意味 | 続き |
   | --- | --- | --- |
   | `ok`（0） | 閉じてよい | 手順 4 へ |
   | `stopped`（`refused`・1） | 閉じない（`failed` の行がある。`--require` で記録が無いか、記録にその課題の行が無い） | 報告の「閉じなかった」に理由を載せる |
   | `gate`（10） | 人が決める（`failed` が無く `not_run` の行がある） | 報告の「閉じなかった」に、人が決めることを理由として載せる。止まらずに次の課題へ進む |
4. **閉じる。** 条件を満たした課題だけを `gh issue close <課題> --comment "<最終工程> を終えたので閉じる（記録: <記録の PR の URL>）"`
   で閉じ、`gh issue view <課題> --json state` で `CLOSED` を確かめる。条件 2 を満たした課題は、閉じる前に本文の
   `## 受け入れ条件` のチェックボックスへマーカー（`[x]`）を付ける（`gh issue edit <課題> --body-file <ファイル>`。変えるのは
   チェックボックスの空白 1 文字だけで、セクションの外と説明の行は変えない）。他のリポジトリの課題の本文は書かない
5. **報告する。** 課題ごとに次のどれかを表にして載せる

| 結果 | 意味 | 報告に載せるもの |
| --- | --- | --- |
| 閉じた | この手順で閉じた | 番号と戻し方（`gh issue reopen <課題>`） |
| 前から閉じていた | 手順の前から閉じていた（既定ブランチへのマージで GitHub が閉じた場合を含む） | 番号。閉じる条件を満たさなければ、その理由を添え、受け入れ条件を確かめるか開き直すかを人が決める（開き直さない） |
| 閉じなかった | 閉じる条件に当たらない | 番号と理由（いつ閉じるか） |
| 失敗 | 状態か本文を読めない、閉じた後も `CLOSED` でない | 番号・理由・やり直すコマンド。最終工程を完了と報告せず、棚卸しへ進まずに止まる |

閉じなかった課題があっても棚卸しへ進む。人は報告で閉じなかった課題と理由を読み、条件を満たす工程を通してから
この手順をやり直すか、確かめて手で閉じる。

### 閉じる条件

| # | 条件 | 満たさないとき |
| --- | --- | --- |
| 1 | 本番へ入れたバージョンのリリース記録がある（デプロイを飛ばした実行は、飛ばした記録がある） | スプリント課題すべてを OPEN のまま残す |
| 2 | リリース後テストの記録がある経路では、その課題の行に不合格（`failed`）が無く、保留（`not_run`）も無い。`not_run` があれば閉じるかを人が決める。`--require` では記録そのものと、記録の中のその課題の行が 1 行以上要る | その課題を OPEN のまま残す（`not_run` なら人が決める課題として報告する） |
| 3 | その課題の最終工程の記録がある。`デプロイ` は条件 1、`リリース後テスト` は条件 2 がそれに当たる。`振り返り` は課題の本文に行頭から `振り返り: https://github.com/<所有者>/<リポジトリ>/(issues\|pull)/<番号>#issuecomment-<識別子>` の行があり、記録の PR の最後のリリース記録より後に書かれたものである。前の実行の振り返りの行は数えない | その課題を OPEN のまま残す |

**開発版のデプロイは閉じる条件を満たさない。** 利用者が常用するバージョンにまだ届いていない段階で、
確かめていないことが終わったように見える。

### 既定ブランチ宛ての Pull Request の参照

**既定ブランチ宛ての Pull Request の本文には closing keywords を書かず、`Refs #<番号>` で参照する。** GitHub は既定ブランチへの
マージの時点に closing keywords の課題を閉じ、最終工程より先に閉じてしまう。`Refs` の形では GitHub は閉じず、手順 2 が
スプリント課題として集める。マージ先が既定ブランチでない Pull Request（スプリントブランチ宛て）は closing keywords で書いてよい。

指し先は closing keywords と同じ 3 つ（`#<番号>`・`<所有者>/<リポジトリ>#<番号>`・課題の URL）で、1 つの指し先に 1 つ書く。
コミットメッセージには closing keywords を書かない（push の前の `ndf worker closing-check --base <参照>` が止める）。

### リリース記録

**リリース記録は、本番へ入れたバージョンに含めた PR の各々へコメントで置く。** 書くのは `release`（`ndf release-steps record`）である。
**リリース後テストの記録は、そのうちの 1 本（手順 1 の規則で選ぶ。既に同じバージョンのリリース後テストの記録を持つ PR を先に、無ければ同じバージョンのリリース記録を持つ PR で番号が最も小さいもの）にだけ置く。** 書くのは
`release-verification`（`ndf release-steps verification-record`）で、閉じる側はその 1 本の PR から両方を読む。

| 記録 | 見分け方 | 機械が読む中身 |
| --- | --- | --- |
| リリース記録 | マーカーの行 `<!-- ndf:release-record -->` | 後に続く JSON のコードブロックの `version`（v の前置きの無い版数）・`release`（リリースの PR の番号）・`included`（含めた PR の番号） |
| リリース後テストの記録 | マーカーの行 `<!-- ndf:release-verification -->` | 後に続く JSON のコードブロック（[release-verification のスキーマ](../../contracts/schemas/release-verification.schema.json) の `version` と `issues`） |

**読むのは JSON のコードブロックだけで、見出しや本文の文から読まない。** 同じマーカーのコメントが複数あれば、
条件 1 は本番のバージョンと `version` が一致する最後の記録を、条件 2 は同じバージョンの最後のリリース後テストの記録を使う。

## 関連

- `/ndf:development-workflow` — 工程名の一覧（工程表）
- `/ndf:out-of-scope` — 同じく順序を持たない横断的な手順
- `/ndf:release` — リリース記録を置く工程。後に工程が続かなければ「スプリントを閉じる」を行う
- `/ndf:release-verification` — リリース後テストの記録を置く工程
- `/ndf:retrospective` — 振り返りを通る変更で「スプリントを閉じる」を行う工程
