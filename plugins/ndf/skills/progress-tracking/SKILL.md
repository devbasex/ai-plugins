# 工程の進行を記録する

いまどの工程まで終わったかを、セッションの外へ残す。**判定したモードも、通った工程も、
記録しなければ会話の中にしか残らない。** セッションが変わると引き継がれない。

**この Skill は順序を持たない。** 工程表には載らず、モードごとの要否も持たない。どの工程からも
呼ばれる（`out-of-scope` と同じ扱いである）。**例外は「スプリントを閉じる」の 1 つだけである。**
そちらは**最終工程を出るときに 1 度だけ**行う（契機が違う）。

## 何を記録するか

| 記録先 | 何が残るか | 要る条件 |
| --- | --- | --- |
| issue の本文 | 工程のチェックリスト・モード・worktree・実装計画のファイル | `gh` が使えること |
| ボード（GitHub Projects） | 工程・モード・worktree・計画ファイル | リポジトリに `.ndf/projects.json` があること |

**ボードの設定が無いリポジトリでも issue へ残る。** 設定はボードへ書くかどうかだけを決める。

**この記録を判定の入力に使わない。** 工程の飛ばしの検知は通過記録が担う
（`development-workflow` の `references/stage-completeness.md`）。ここに残すのは、**人が
セッションの外から現在地と成果物の所在をたどるためのもの**である。

## この文書が受け取る値

| 変数 | 値 | 決め方 |
| --- | --- | --- |
| `$SCRIPTS` | プラグインの `scripts/` の絶対パス | [references/scripts-lookup.md](../development-workflow/references/scripts-lookup.md)。シェルが変わったら決め直す |

## 呼び方

**工程に入った時点で 1 度、進捗記録を 1 行打つ。** 入った時点で記録
すれば、途中で止まった実行の現在地が残る。**この 1 行で issue の本文の `## 進行` とボードの
両方に残り、`stage` / `mode` / `pace` は通過記録にも積まれる。** この Skill の本文を読まなくても記録できる。

**通過記録へ積むのは記録のスクリプト（`progress-record.sh`）自身である。** hook には依らないため、ランタイム（Claude Code・Codex・Kiro CLI・agy）・Skill の起動の有無・
`supervise.py` の子プロセスのどれから呼んでも積まれる。`projects-sync.sh` は中で
`progress-record.sh` を呼び、1 回の記録で積むのは 1 件である。

```bash
bash "$SCRIPTS/projects-sync.sh" <issue番号> <キー> "<値>"
```

| キー | 打つ時点 | 値 | issue の本文 |
| --- | --- | --- | --- |
| `stage` | 工程に入るたび（課題ごと） | 工程名 | チェックを付ける |
| `mode` | 最初の工程で 1 度 | モード | 見出し行だけ |
| `worktree` | 作業場所の用意の後に 1 度 | worktree のパス | 見出し行だけ |
| `plan` | 計画の後に 1 度 | 実装計画のファイルのパス | 見出し行だけ |
| `status` | 「スプリントを閉じる」だけ | `Done` | 書かない（ボードだけ） |

**値は引用符で囲む。** 工程名には空白を含むもの（`Pull Request`）がある。囲まないとシェルの
側で分割され、引数のチェックで終了コード 2 になる。**1 回の実行に何件並べてもよく、課題番号を
変数で書いてもよい**（`for n in 11 12; do …; done`）。どの呼び出しも自分で通過記録へ積む。

```bash
bash "$SCRIPTS/projects-sync.sh" 186 stage "設計"
bash "$SCRIPTS/projects-sync.sh" 186 mode "standard"
```

**呼ぶ側へ渡す抜粋は [references/excerpt.md](references/excerpt.md) にある。** supervisor や
worker の起動指示へはこれをコピーし、本文を読ませない。

**`progress-record.sh` を直接呼ぶのは 2 つの場合だけである。** 他のリポジトリの課題へ書く
（`--repo`。ボードへは書かない）ときと、付随情報を足す（`--note`）ときである。

**`配布` を記録したとき、記録の無い必須の工程があれば、同じ呼び出しの標準出力に案内が出る**
（`記録なし:` / `条件付き:` の行と、記録し直すコマンド）。実施済みであれば記録してから先へ進む。

**最終工程でボードの `Status` を `Done` にするのは、下の「スプリントを閉じる」だけである。**
工程に入った時点の記録では書かない。工程の開始時に書くと、ボードの `Auto-close issue` が先に課題を
閉じ、`閉じた` として数えるはずの課題が `既に閉じていた` になって reopen の手段が報告から
落ちる。issue の側は工程のチェックリストが埋まることで表せるため、この値はボードにだけ書く。

**工程名の一覧は工程表が持つ。** この Skill は一覧を持たない
（`development-workflow` の「モードごとに起動する Skill」の表が唯一の基準である）。一覧に
無い値を渡すと、どちらのコマンドも終了コード 2 で弾く。

## 書けなかったときの返し方

**進行管理が理由で開発の工程を止めない。** 記録のスクリプト（`progress-record.sh`・`projects-sync.sh`）は
1 行の結果 JSON を返し（形と状態の意味は `$SCRIPTS/lib/README.md` の「手順のスクリプトの結果」）、
書けなかったことを `ok` で隠さない。止めない判断は呼ぶ側が持ち、`ok` 以外が返っても先へ進んで、
`summary` と `gaps[].reason` を作業の報告の「見つけたもの」へ載せる（読み方は
[references/excerpt.md](references/excerpt.md) の「結果の読み方」）。

| 条件 | 書けないもの | 終了コード |
| --- | --- | --- |
| `gh` が無い | issue とボードへの記録（通過記録は積む） | 3 |
| issue を取得できない・書けない・本文の錠を取れない | issue への記録（`gaps` に `gh` の標準エラーの要旨） | 6 |
| ボードへの問い合わせが上限に達した・ボードにアイテムが無く追加もできない・書けない | ボードへの記録（`gaps` に理由） | 6 |
| 本文もボードも通過記録も書けない | 全部 | 1 |
| リポジトリを特定できない・`jq` が無い・通過記録が使用中 | 通過記録（`NOTE:` を 1 行知らせ、`process` に残す。これだけでは `ok` のまま） | 0 |
| `.ndf/projects.json` が無い | ボードへの記録（ボードを使わないリポジトリ。欠けにしない） | 0 |

**呼び出し側の誤りは 2 を返す。** 知らない工程名・引数の不足がこれにあたる。黙って進むと、
綴りの違う値が入るか、書き込んだつもりの値が入らない。

## issue の本文に残る形

```markdown
## 進行

モード: standard / 作業ツリー: `.worktrees/feat/issue-243`

- [x] 作業場所の用意 — 2026-09-04 06:12
- [x] 要求と受け入れ条件 — 2026-09-04 06:40
- [ ] 設計
- [ ] ドキュメント再構成
- [ ] ドキュメントレビュー
```

- **節の外は書き換えない。** 更新のたびに本文を取得し、`## 進行` の見出しから次の見出しまで
  だけを差し替える。人が本文へ書いた内容は残る
- **飛ばした工程は空欄のまま残る。** チェックの穴として見える
- **モードで通らない工程の行は書かない。** モードが `WF_MODES` のどれかなら、`WF_STAGE_MATRIX` のその列が `-` で
  記録の無い工程の行を持たない。記録の済んだ行は、列が `-` でも残る。モードが `—` か知らない値なら全工程の行を書く
- **判断を伴う場面だけコメントを残す。** モードを途中で上げた・工程を意図して飛ばした・
  受け入れ条件を変えたの 3 つは、本文を見ても理由が分からない

## ボードの設定

ボードへも残す場合の設定ファイル・フィールド・工程との対応は
[references/projects-tracking.md](../development-workflow/references/projects-tracking.md)
にある。アイテムの追加・識別子のキャッシュ・ボードが決まらないときの扱いは
[references/board.md](references/board.md) にある。

## 工程の単位と記録する課題

**工程が動く単位は 3 つある。** 記録する側は「その工程を行った側」で、記録する先は単位に
含まれる課題すべてである。**誰が書くかを決めておかないと、supervisor が行った工程だけが埋まり、
オーケストレーターが行った工程が空欄のまま残る。**

| 工程の単位（`parallel-work.md` の表） | 記録する側 | 記録する課題 |
| --- | --- | --- |
| 課題 | その課題を扱う supervisor | その課題 |
| Pull Request（後片付けを含む） | その工程を行った側。後片付けはマージした側 | その Pull Request の本文の GitHub の closing keywords（PR 本文に `Closes #123` のように書くと、マージ時にその課題を自動で閉じる機能）と閉じる予定の参照（下の「閉じる予定の参照」）が指す課題すべて |
| スプリント（確定仕様化・リリース・体裁レビュー・リリース後テスト・振り返り） | その工程を行った側。リリース以降はオーケストレーター | スプリント課題すべて |

**記録は 1 回の実行に課題を並べてよい。** どの記録も記録のスクリプトが自分で通過記録へ積むため、
並べても・課題番号を変数で書いても、本文と通過記録は食い違わない。

**他のリポジトリの課題へは `progress-record.sh --repo` だけを使い、`projects-sync.sh` を
呼ばない**（理由は次の節の箇条書き）。

## スプリントを閉じる

**閉じる時点の決まりの正本はこの節だけである。** 呼ぶ側（Skill・まとめのプラン・`pr`）は閉じる時点と順序と
閉じる条件を写さず、この節を指す。worker は呼ばない（supervisor か conductor が呼ぶ）。

**課題を閉じてよいのは、その課題がその実行の最終工程を終えたときだけである。** NDF のどの経路
（まとめのプランの `close`・最終工程を担う Skill・conductor の手打ち）で打っても、`sprint-close.py` が課題ごとに
最終工程の記録（閉じる条件 3）を確かめ、無ければ閉じない。呼ぶ側の手順の並びに頼らない。
**最終工程とは、棚卸しの前にその実行で最後に通る工程である**（工程表は `development-workflow` の
「モードごとに起動する Skill」。`operation` のリリース後テストと振り返りはそれぞれ条件付き）。
検証リリースで止めた実行も、その実行の最終工程でこの手順を行う。課題は閉じる条件に
当たらず OPEN のまま残り、後で本番へのリリースを行った実行の最終工程が改めて行う。

| 呼ぶ側 | 呼ぶ時点 | 呼ぶ条件 | `--final-stage` |
| --- | --- | --- | --- |
| まとめのプラン（`supervise.py new close`）の `close` のステップ | 振り返りの後、棚卸しの前 | プランで仕上げる実行（どのモードも `retro` を通す） | `振り返り` |
| `retrospective` | 記録を投稿し、課題の本文に辿る経路の行を足した後 | 振り返りを通る変更 | `振り返り` |
| `release-verification` | 検証結果を記録した後 | 後に振り返りが続かない変更（振り返りを通らない `operation`） | `リリース後テスト` |
| `release` | 配布を終えた後 | 後にリリース後テストも振り返りも続かない変更（`light`、どちらも通らない `operation`） | `配布` |

まとめのプランの並びは `merge →（配布の記録があれば）release-verify → retro → close → refine` である。
`release-verify` と `retro` の指示は課題を閉じない。プランの中では最終工程が振り返りになるため、`close` が閉じる。
プランの外で Skill を直接通すときは、上の表の Skill がこの手順を行う。両方が打っても、早すぎる時点では
閉じる条件 3 で閉じず、2 度目は `already_closed` になる。

**閉じた後は、工程表の次の工程 `棚卸し`（`backlog-refinement`）へ進む。「スプリントを閉じる → 棚卸し」の
順序の正本はここである。** 逆にすると、`backlog-refinement` の手順 1 が読む「このスプリントで閉じた課題」が
まだ閉じていない。呼ぶ側の Skill は棚卸しを呼ばない（棚卸しは工程表の行として、同じフェーズの担当が始める）。

**利用者の入力を求めない。** 閉じる判断は、スプリントの工程を通ったことで既に済んでいる
（実行前確認の要否の基準は `AUTHORING.md`）。閉じた課題と reopen の手段を報告へ載せる。

### 手順

次のコマンドを打ち、結果 JSON の `status` を見る。記録の PR は配布の記録を置いた PR である
（別の実行なら `retrospective` の「Pull Request の番号を特定する」で引く）。

```bash
python3 "$SCRIPTS/sprint-close.py" --record-pr <記録のPR番号> [--final-stage <配布|リリース後テスト|振り返り>] \
  [--with-verification] [--label "<マイルストーン>の<工程名>"] [--prs <番号,番号>] [--issues <番号,番号>] [--dry-run]
```

- `--final-stage`: その実行の最終工程（上の表の値）。省けば `振り返り`。省いても閉じる条件は緩まない
- `--with-verification`: リリース後テストを通る経路で付ける（閉じる条件 2 を見る）。`--final-stage リリース後テスト`
  では付けなくても条件 2 を見る
- `--prs`: 同じ実行の中で `release` が承認の提示に並べた一覧を渡すとき。省けば最後の
  「## 配布の記録」の `スプリント:` の行を使う
- `--issues`: スプリントの PR の本文が指さない課題を足すとき（`pace: fast` の実装 PR など）
- スクリプトが行うこと: 配布の記録の読み取り → スプリント課題（スプリントの PR の本文の closing keywords
  （GitHub が課題を自動で閉じるキーワード。`Closes #N` などの記法）と閉じる予定の参照が指す課題と `--issues` の課題）の収集 →
  閉じる条件 1〜3 の判定 → 課題ごとに「状態を読む → 記録のリポジトリの課題ならボードを Done → 読み直して OPEN なら閉じる →
  読み直して CLOSED を確かめる」→ 参照だけの課題の報告。他のリポジトリの課題にはボードを書かない
- `--with-verification` の経路では、課題ごとの錠の中で状態と本文を 1 回で読んで閉じる条件 2 を判定し、満たした
  記録のリポジトリの課題は、本文の `## 受け入れ条件` のチェックボックスに印（`[x]`）を付けてから閉じる。変えるのは
  チェックボックスの空白 1 文字だけで、節の外と説明の行は変えない。他のリポジトリの課題の本文は書かない。
  閉じる条件 3 を満たさない課題には印を付けない
- 閉じる条件 3 は条件 2 と同じ 1 回の本文の読みを使う（`--final-stage 振り返り` で条件 2 を見ないときも本文を 1 回読む）
- 参照だけの課題: スプリントの PR の題か本文が `#<番号>` か課題の URL で参照し、スプリント課題に入らない
  記録のリポジトリの開いた課題。閉じずボードも書かず、`kept_open` で載せる。件数は `metrics.referenced_only` にある

状態と終了コードの意味は `$SCRIPTS/lib/README.md` の「手順のスクリプトの結果」にある。

| 終了コード | 次にすること |
| --- | --- |
| 0 | `items` の表を報告に貼り、棚卸しの工程へ進む |
| 1 | 失敗した課題がある。`items[].reason` と `cmd`（やり直すコマンド）を報告し、最終工程を完了と報告せず、棚卸しへ進まずに止まる |
| 2 | スプリントの PR の一覧が取れない。推測せず運用者に一覧を聞き、`--prs` で打ち直す。または、PR を読んだのにスプリント課題が 0 件（PR の本文に closing keywords（GitHub が課題を自動で閉じるキーワード Closes / Fixes / Resolves）も閉じる予定の参照も無く、`--issues` も無い）。`next` に並ぶ PR が参照した番号から閉じる課題を選び、`--issues` で渡して打ち直す |
| 3 | 呼び出しの誤り。引数を直して打ち直す |

`items[]` の `kind: "issue"` の `result` は次の 5 つのどれかになる（`--dry-run` では
`would_close` も出る）。`kind: "board_note"` はボードへ Done を書けなかった理由（`projects-sync.sh` の結果 JSON が `ok` でない）で、報告にそのまま載せる。課題を閉じる処理は止めない。
印を付けた受け入れ条件の番号は `checked`、`--dry-run` で付ける予定の番号は `would_check` に載る。
判定に使った最終工程は `metrics.final_stage` と `decisions` に載る。

| `result` | 意味 | 報告に載せるもの |
| --- | --- | --- |
| `closed` | 閉じた（ボードの自動化が閉じた場合を含む） | 番号と `cmd`（戻し方 `gh issue reopen`） |
| `already_closed` | 手順の前から閉じていた（既定ブランチへのマージで GitHub が閉じた場合を含む） | 番号 |
| `failed` | 状態を読めない、または閉じた後も CLOSED でない。本文を読めない（最終工程の記録を確かめられない。閉じない）。`--with-verification` では、本文の錠を取れない・受け入れ条件の印を書けない（閉じない） | 番号・`reason`・`cmd`（やり直す `gh issue close`。本文の失敗では同じ `sprint-close.py` の呼び出し） |
| `closed_unverified` | 既に閉じていたが閉じる条件 2 か 3 を満たさない。開き直さない | 番号と `reason`（満たさない理由と番号）。受け入れ条件を確かめて印を付けるか、開き直すかを人が決める |
| `kept_open` | 閉じる条件に当たらない（条件 3 では `reason` が「最終工程（<工程>）の記録が無い: <何が無いか>」）。または参照だけの課題（`reason` が「closing keywords（…）も --issues も無い参照」。状態を読めなければ先頭に「状態を読めない」） | 番号と `reason`（いつ閉じるか。参照だけの課題は、閉じるなら `--issues` で渡す） |

**`kept_open` と `closed_unverified` は止める理由にしない。** 棚卸しへ進んでよい。

### 閉じる条件

| # | 条件 | 満たさないとき |
| --- | --- | --- |
| 1 | 最後の「## 配布の記録」の `段階:` が `本番` または `配布なし` で始まる | スプリント課題すべてを OPEN のまま残す |
| 2 | リリース後テストを通る経路（`--with-verification` か `--final-stage リリース後テスト`）では、その課題の行がすべて `合格` で、課題の本文の `## 受け入れ条件` のチェックボックスの番号（上から数えた順、1 から）のすべてに合格の行がある。同じ番号に合格でない行があればその番号は合格でない。チェックボックスが無い課題は行の合否だけで見る | その課題を OPEN のまま残す（`reason` に合格の行が無い番号）。既に閉じていれば `closed_unverified` |
| 3 | その課題の最終工程の記録がある。`配布` は条件 1、`リリース後テスト` は条件 2 がそれに当たる。`振り返り` は課題の本文に行頭から `振り返り: https://github.com/<所有者>/<リポジトリ>/(issues\|pull)/<番号>#issuecomment-<識別子>` の行があり、そのうち 1 つ以上の識別子が、記録の PR の最後の配布の記録を含むコメントの識別子以上である（配布の記録が本文にあれば記録の PR の最初のコメントの識別子と比べ、コメントが無ければ満たさない。`--record-pr 0` は行があれば満たす）。前の実行の振り返りの行は数えない | その課題を OPEN のまま残す（`reason` に通っていない工程）。既に閉じていれば `closed_unverified`。本文を読めなければ `failed` |

**検証リリースは閉じる条件を満たさない。** 利用者が常用する版にまだ届いていない段階で、
確かめていないことが終わったように見える。

`--record-pr 0`（本番の記録なし）は条件 1・2 を見ない。`--record-pr unknown`（記録の置き場が分からない）は
本文を読まずにすべて `kept_open` で返す。

### 閉じる予定の参照

**既定ブランチ宛の Pull Request の本文には closing keywords を残さない。** GitHub は既定ブランチへのマージの時点に
closing keywords の課題を閉じ、最終工程より先に閉じてしまう。NDF の手順（`pr-steps.py create` / `update` と
まとめのプランの pr のステップ）は、宛先が既定ブランチ（既定ブランチを決められないときを含む）なら、本文の
closing keywords を閉じる予定の参照へ置き換えてから送る。宛先が既定ブランチでない Pull Request の本文は書き換えない。

```text
最終工程の後に閉じる: <指し先>
```

`<指し先>` は closing keywords と同じ 3 つ（`#<番号>`・`<所有者>/<リポジトリ>#<番号>`・課題の URL）で、1 つの指し先に
1 つ書く。GitHub はこの形では閉じず、`sprint-close.py`（`lib/closing-issues.sh`）がスプリント課題として集める。
形の正本は `$SCRIPTS/lib/closing.py` の `DEFERRED` である。置き換えた指し先は `pr-steps.py` の結果の
`metrics.deferred_closing` に載る。

### 配布の記録

**配布の記録は Pull Request に置く。** 書く側はこの形で書き、`sprint-close.py` はこの形だけを読む。

| 記録 | 書く形 | 置く側 | 置き場所 |
| --- | --- | --- | --- |
| 配布の記録 | 見出し `## 配布の記録` の直後に `段階: <検証 / 本番 / 配布なし>（本番なら承認を得た時点、止めたなら理由、配布なしなら飛ばした理由）`・`版: <前の版> → <新しい版>（<根拠>）`（`配布なし` のときは書かない）・`スプリント: PR #<番号> / #<番号>` の行が続くブロック。終わりは次の `## ` 見出しか入力の終わり | `release`（スクリプトで組む本番のリリースプランでは、本番の配布の後に `release-steps.py record` が書く） | 配布の Pull Request の本文。配布の形が Pull Request を作らないときと配布を飛ばしたときは、スプリントの最後にマージした Pull Request へ同じブロックをコメントで投稿する |
| リリース後テスト | `## リリース後テスト` から `合否:` までのブロック。`対象の版: <配布した版>（<配布した時刻>）` の行と、列が `課題`（`#<番号>`、他のリポジトリなら `<所有者>/<リポジトリ>#<番号>`、課題に結び付かない行は `—`）/ 受け入れ条件（セルの頭に `<番号>.`）/ 実行したこと / 実行時刻 / 結果 の表を持つ | `release-verification` | 上と同じ Pull Request へコメントで投稿する |

読むのは本文とコメントを投稿の順に並べたうちの最後の配布の記録 1 つで、リリース後テストは
`対象の版:` が本番の版と一致する最後のブロック（無ければ、版数を上げない配布として、最後の配布の記録より後で
`対象の版:` が版数でない最後のブロック。`配布なし` ならその記録より後の最後のブロック）を使う。
表の `課題` の列の頭が課題の参照でない行は飛ばす。課題を指す行が 1 行も無い表は、スプリント課題すべてを
「条件と課題の対応が読めない」で OPEN のまま残す（すべての条件をマージ前に確かめたと本文に記録した課題は除く）。

## 関連

- `/ndf:development-workflow` — 工程名の一覧（工程表）
- `/ndf:out-of-scope` — 同じく順序を持たない横断的な手順
- `/ndf:release` — 配布の記録を置く工程。後に工程が続かなければ「スプリントを閉じる」を呼ぶ
- `/ndf:release-verification` — リリース後テストの記録を置く工程
- `/ndf:retrospective` — 振り返りを通る変更で「スプリントを閉じる」を呼ぶ工程
