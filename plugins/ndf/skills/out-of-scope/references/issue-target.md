# 起票先を決める

**「起票する」を選んだときだけ読む。** NDF を使う開発では、関わるリポジトリが 2 つになることがある。
**どちらへ起票するかは課題の性質が決める。** 見つけた場所は決め手にならない。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| 上流リポジトリ | NDF の Skill・エージェント・hook の実体を持つリポジトリ |
| 開発対象リポジトリ | NDF を使って開発している側のリポジトリ。`gh repo view` が返すもの |
| 起票先 | `gh issue create --repo` で課題を作るリポジトリ |

2 つが同じリポジトリなら、この判断は要らない。

## 判断表

| 課題の性質 | 起票先 |
| --- | --- |
| 工程と Skill の手順そのもの | 上流リポジトリ |
| 開発対象のコード・データ・設定・運用 | 開発対象リポジトリ |
| 両方にまたがる | 上流リポジトリと開発対象リポジトリの 2 つ |

**どちらで直せるかで分ける。** 手順書の記述が原因なら、開発対象リポジトリを直しても
次の利用者が同じ場所で止まる。逆に、開発対象の設定の誤りを上流リポジトリへ起票しても、上流リポジトリには
直す対象が無い。

起票先が別のリポジトリで、並列の計画のレーンなら、[parallel-cross-repo.md](../../development-workflow/references/parallel-cross-repo.md) の「別のリポジトリの改修が要るとき」へ進む。

## 上流リポジトリの名前

**NDF を導入したマーケットプレイスの取得元（ランタイムに登録したマーケットプレイスのリポジトリ）が上流リポジトリである。**
1 つに決められなければ推測せず、候補を示して利用者に聞く（`metadata.source` は `ndf-ask:redline:C5`）。
決まったときも、起票の前の提示に起票先を含める（fork した利用者では、取得元が実際の上流リポジトリと違うことがある）。

## 両方にまたがる課題

**上流リポジトリを先に起票する。** 番号が先に決まれば、開発対象リポジトリの本文へその番号を書ける。
逆順にすると、どちらの本文にも相手の番号が無い状態が一度できる。

1. 上流リポジトリへ `gh issue create` で起票する
2. 開発対象リポジトリへ起票する。由来のセクションに上流の課題（`<上流の所有者>/<リポジトリ>#<番号>`）を書く
3. 上流の課題へ `gh issue comment` で開発対象の課題の番号を 1 行足す。上流は開発対象と別のリポジトリなので、
   SKILL.md の手順 4 と同じく、打つ前に示して同意（`ndf-ask:redline:C5`）を取る。人に問えない起動では打たず、承認資料を添えて人へ戻す
