# 見積もりの規約

AI エージェントが実施する前提で、作業の大きさを見積もるときの規約の正本。Skill `estimate`・`backlog-refinement`
の Size・`supervise.py new` の実装の上限は、この規約と部品（`scripts/estimate.py`）を使い、定義を写さない。

## 例: 課題 1 件を見積もる

課題 #1856（見積もりの部品を作る）を、実装のフェーズの完了まで見積もる。AI は本文を読んで着手前の 6 項目を判定し、
部品を呼ぶ。

```bash
python3 "$SCRIPTS/estimate.py" predict --issue 1856 --done 実装 \
  --items requirements=軽,information=軽,spread=重,verification=軽,environment=軽,rework=判定できない --save
```

部品は、近い実績から 4 つの値を別々に返す。実績が無い値には `未校正` か `材料なし` が付く（下の値は形を示す例）。

| 値 | 見込み | 印 | 根拠 |
| --- | --- | --- | --- |
| A（AI の実行量） | 通常 5400 秒・追加の調査が要るとき 8100 秒 | 実績 | #1601（5400 秒）・#1631（8100 秒）・#1623（3900 秒） |
| H（人の作業時間） | — | 材料なし | 人の作業時間の記録が無い |
| L（完了までの時間） | 通常 7200 秒 | 実績 | 同上の 3 件 |
| C（利用費用） | 通常 12.4 USD | 実績 | 同上の 3 件（費用の取れない実行を含む） |

**4 つの値を足して 1 つの「工数」にしない。** 上の例で「A + H + L」に意味は無い。

## 4 つの値

| 値 | 定義 | 単位 | 用途 |
| --- | --- | --- | --- |
| A（AI の実行量） | 調査・設計・実装・検証・修正で AI エージェントが動いた時間の合計。並列に動いた分は足す | 秒 | 実行の容量の計画・Size |
| H（人の作業時間） | 要件の判断・説明・レビュー・手動の確認・修正への介入に人が手を動かした時間。判断を**待つ**時間は含まない | 秒 | 人員の計画 |
| L（完了までの時間） | 着手から完了条件に届くまでの経過時間。並列・依存・CI・承認の待ちを含む | 秒 | 納期・実行の順序 |
| C（利用費用） | LLM と実行環境の費用。サブスクリプションの枠の消費は別に記録する | USD | 予算・利用枠の管理 |

例: AI が 3 本並列で各 20 分動き、人が 5 分レビューしたなら、A は 60 分・L は約 20 分・H は 5 分である。
人の判断を待つ時間は L に入れ、人が判断のために作業した時間は H に入れる。

## 見積もりの完了条件

見積もる作業がどこまで終われば完了かを、supervise のフェーズの名前で決める: `設計`・`実装`・`検査`・`配布（開発版）`・
`配布（本番）`。部品は、そのフェーズまでの実行（失敗・中断・取り消し・再試行を含む）を足し、そのフェーズが
`成功` で終わった課題だけを類似の実績の候補にする。

## 実行の構成

実績を比べる前提になる、モデル・ハーネス・レビューの方式・テストの方式・並列の数の組。今の構成は最新の実行の
記録から決め、構成の違う実績は値に入れずに `other_config` に示す。分からない（空の）項目は比べない。構成を
変えた直後は `未校正` が増えるが、それは事実であり、補正の係数で埋めない。

## 着手前の 6 項目

| 項目（`--items` の鍵） | 軽 | 重 |
| --- | --- | --- |
| 要件の確定度（`requirements`） | 期待する結果と受け入れ条件が明確 | 正解を関係者と決める必要がある |
| 必要な情報の取得（`information`） | 対象・仕様・類似の実装が見つかっている | 原因が不明・情報が散らばる・外部の情報が要る |
| 変更の波及（`spread`） | 局所的で既存の契約を保つ | API・DB・複数のサービス・移行の順序にまたがる |
| 検証のしやすさ（`verification`） | 短い自動テストで合否が分かる | 実機・本番相当のデータ・目視・長い観測が要る |
| 環境の準備（`environment`） | 起動・権限・データ・テストが揃っている | 環境の構築・権限の取得・外部との調整が要る |
| 手戻りの見込み（`rework`） | 同じ種類の変更が安定して通っている | 類似の実績で修正が多い・新しい方式・戻しにくい |

値は `軽`・`重`・`判定できない` の 3 つ。判定できない項目は `判定できない` のまま残し、見積もりは続ける。
**加点して時間へ換算しない。** 6 項目は、類似の実績を選ぶ材料と、見積もりが膨らむ理由の説明に使う。
着手前に分かっていたことだけで判定し、実行の後に分かった修正の回数や差分を着手前の特徴として書かない。

## 類似の実績の選び方

1. 候補は、完了条件のフェーズで `成功` した課題の実績の合計である
2. 比べる課題を AI が選んだら `--like` で渡す。部品はその課題だけを候補にする（どれが近いかの判断は AI が持つ）
3. `--like` が無ければ、見積もりの記録の 6 項目と比べ、`判定できない` を除いて値の違う項目が 1 つ以下の課題を、
   違いの少ない順・新しい順に最大 10 件選ぶ
4. 構成の違う候補は値から外し、`other_config` に示す
5. 残った件数で値の形を決める。5 件以上は中央値と 80 分位（`P50/P80`）、1〜4 件は中央値（通常）と最大
   （追加の調査が要るとき）。少ない件数で確率を装わない

2 つ以上の課題を 1 本で流した実行は課題の数で等分し、根拠に `shared` を付ける。

## 実績が足りないとき

**人の工数の基準で見積もらない。人日や AI の倍率から換算しない。** 研究の効果量（何倍速いか・何割短いか）を
見込みの数値に使わない。

- 類似の実績が 0 件の値は `未校正` にする。AI が、想定の手順と既知のテストの所要（部品の
  `materials.test_seconds`）から暫定の範囲を作れるときは `--provisional A=1800-5400` で渡す。部品は渡された
  範囲を `未校正` の印で返し、渡されなければ値を空にする
- H は、`estimate.py human` で人が記録した時間だけから取る。記録が無ければ `材料なし`
- 原因や検証の方法が分からない部分は、短い調査の課題として切り出し、分かった時点で残りを見積もり直す
- 見積もりを返すときは、どの値が `実績`・`未校正`・`材料なし` かを必ず示す

## Size への換算

Size は A の見込みを表す。比 r = A ÷ Size 1 の基準とし、尺度 `1, 2, 3, 5, 8, 13, 20` の隣り合う段階の中点で
丸める（境界は 1.5・2.5・4・6.5・10.5・16.5）。r が尺度の最大を超えたら Size は `尺度を超える` で、最大へ
潰さない。分割を検討する印にする。

- Size 1 の基準は `.ndf/estimate.json` の `size_unit_seconds`。無ければ、実績のある課題のうち A の小さい
  4 分の 1 の中央値（4 課題以上のとき）。それも無ければ Size は丸めず、棚卸しは手順 2B で付けた段階を使う
- A が `実績` でないときは丸めない
- スプリントの容量を厳密に計画するときは、丸めた Size の和でなく A の見込みを使う
- 順位の重み（`size_exponent`）は運用の方針で、AI の速さの係数ではない。この規約では変えない

## 実装の上限

`supervise.py new` の実装のステップの上限（秒）は、`--impl-timeout` → `.ndf/supervise.json` の `impl_timeout` →
実績の見込み → 3600 の順に決まる。実績の見込みは、同じ構成でフェーズ `実装`・ステップ `impl` の直近 10 件
（失敗を含む）の最大に余裕を足した値で、3 件未満なら 3600 秒で `uncalibrated` と出る。

## 記録

| 記録 | 中身 | 書き手 |
| --- | --- | --- |
| 実績の記録（`actuals.jsonl`） | 実行の始まり・ステップの終わり・実行の終わり（成功・承認ゲート・失敗・取り消し）と、人の作業時間。終わりの行の無い実行は中断として数える | supervise の実行・`estimate.py human`・`estimate.py import` |
| 見積もりの記録（`estimates.jsonl`） | 見積もりの時点の 6 項目・完了条件・実行の構成・4 つの値・Size | `estimate.py predict --save` |

置き場は `NDF_ESTIMATE_DIR` → `.ndf/estimate.json` の `records_dir` → `<git の共通ディレクトリ>/ndf/estimate`
（worktree をまたいで 1 つ。コミットされない）→ git でなければ `$XDG_STATE_HOME/ndf/estimate/<リポジトリの
パスの指紋>`。どちらも追記だけで、見積もりを直すときは新しい行を足す。

`.ndf/estimate.json`（任意）で受ける項目: `size_unit_seconds`（Size 1 の基準の秒）・`scale`（尺度）・
`records_dir`（記録の置き場）・`window` と `min_samples`（実装の上限に使う直近の件数と、実績から出す最少の件数。既定は 10 と 3）。

## 限界

- work のステップの秒はステップの経過で、中で並列に動いたサブエージェントの時間を足していない。A を少なく見積もる
- 打ち切られた実装の秒は上限と同じ値で残るため、直近 10 件に打ち切りがある間は実装の上限が下がらない
- 取り込んだ実行（`estimate.py import`）は終わり方を持たず、完了した課題の実績にならない（実装の上限の材料にはなる）

## 根拠にした研究

研究からは定性の知見だけを採り、数値は式・既定値・この規約に写さない。出典と確かめた数値・採らなかった知見は
設計文書（#1856）にある。

| 研究 | 採った知見 |
| --- | --- |
| HIE（Alaswad ほか、Discover Computing 29 巻 424、2026。https://link.springer.com/article/10.1007/s10791-026-10331-6 ） | 人の作業時間を左右するのは検証と手直しである。H を A と分け、6 項目に検証のしやすさと手戻りの見込みを置く |
| ACEM（El-Ramly、arXiv 2608.02582。https://arxiv.org/abs/2608.02582 ） | 差し戻しと再試行は費用そのものである。失敗・中断・再試行の実行を実績から除かない |
| METR の生産性実験（Becker ほか、arXiv 2507.09089。https://arxiv.org/abs/2507.09089 ）と 2026 年の更新（https://metr.org/blog/2026-02-24-uplift-update/ ） | 人の予想は効果の向きまで外れうる。見積もりを判断でなく類似の実績から出し、誤差を集計する。複数のエージェントを並べると人の作業時間を経過時間から測れないため、H は別に記録する |
| METR の time horizon（https://metr.org/time-horizons/ ） | タスクの難しさの尺度で、AI が完了に掛ける時間ではない。見積もりの値に使わない |
| Cui ほか（Microsoft などの 3 つの企業の実験。https://www.microsoft.com/en-us/research/?p=1148213 ） | 効果は人と条件で大きく違う。平均の効果量を当てず、同じ構成の実績だけを比べる |
| E3（Yin・Feng、arXiv 2607.13034。https://arxiv.org/abs/2607.13034 ） | 同じ作業でも進め方で A と C が大きく変わる。構成の違う実績を比べない |
