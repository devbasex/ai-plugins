# 設計との突き合わせ

`standard` の完了判定で、実装を設計文書・既存の確定仕様・要求と照らし、食い違いをマージの前に見えるようにする。
確認は (a)(b)(c) の 3 つで、結果は実装 PR の本文の `## 設計と違う点` のセクションに残す。

## 実例

あるリポジトリ（`<owner>/<repo>`）の #216 の設計文書は、`## 構成要素` に回帰テスト `tests/ci/test_ci_workflow.py` を、
`## テスト設計` にテスト関数 `test_pull_request_is_not_filtered_by_branch` などを書いていた。実装の HEAD で
確認 (a) を打つと、次のように「無い」が出て終了コード 1 で終わる。

```bash
ndf loop design-tests --issue 216
# items: tests/ci/test_ci_workflow.py missing（構成要素）・test_pull_request_is_not_filtered_by_branch missing（テスト設計）…
```

同じスプリントで shellcheck のバージョンを固定した変更（同じリポジトリの `4d82277`）で確認 (b) を行うと、既存の確定仕様 `docs/specifications/base-image-shellcheck.md` が
変えたパス 3 つと `SHELLCHECK_VERSION` の 4 語に一致し、「バージョンは固定せず」と書いた行が見つかる。
担い手はテストを作るかセクションに「作らなかった」と理由を並べ、確定仕様の記述を同じ PR で直す。

## いつ行うか

| モード | 行うこと |
| --- | --- |
| `standard` | (a) → (b) → (c) の順に行い、セクションを実装 PR の本文に置く |
| `light` / `operation` / `documentation` / `legacy-refactor` | 行わない。手順も所要も変えない |

`standard` でも設計文書が無ければ（`ndf loop design-tests` が終了コード 3・`cause.kind` が `not_applicable`）、実装計画の頭で分ける。

| 実装計画 | すること |
| --- | --- |
| `issues/issue-<番号>-plan.md` の頭に `省いた文書: 設計書` の行がある（設計書を省いた変更） | 3 つの確認を「該当なし」で満たさず、下の「設計書を省いた変更」の突き合わせに置き換える |
| その行が無い（省く条件ができる前からある課題など） | 3 つの確認を「該当なし（設計文書が無い）」と書いて満たし、(b) は行わない |

3 層（`ndf plan`）の完了判定のプラン（テンプレート `quality-gates`）は、
手元のテストの後に (a) を流し、(b) と (c) は続く worker が行う。

## 確認 (a): 設計に名前の出るテストが実在する

```bash
ndf loop design-tests --issue <番号>
```

`issues/` の設計文書（決定の記録の別ファイルを含む）を HEAD から読み、`## 決定の記録`・`## テスト設計`・
`## 構成要素` にバッククォートで書かれたテストファイルのパス・`<パス>::<名前>` と、`## テスト設計` の `test` で始まる
識別子を拾う。関数の有無は、名前がファイルに語として現れるかで見る（言語を問わない）。

**設計文書は、名前に含む番号のどれかで探す。** 読むのは `issues/issue-<番号の並び>-design*.md` のうち、`-` で区切った
番号のどれかが指定と一致するものである（番号の一部とは合わせない）。根本原因が共通で複数の課題を 1 本にまとめた
設計文書（`issue-7-8-design.md`）を、先頭以外の課題番号からも引けるようにするためで、`ndf loop design-tests` の読み方と
同じである（7 でも 8 でも読み、78 では読まない）。手で探すときも先頭の番号だけと照らさない。

| 終了コード | 読み方 | すること |
| --- | --- | --- |
| 0 | すべてある（0 件を含む。`metrics.names` が 0） | 次へ |
| 1 | 「無い」（`missing`）がある | 作るか、セクションに「作らなかった」と理由を並べる |
| 2 | 設計文書か git が読めない（`invalid`） | 自分で確かめる。確かめられなければ報告の「未検証の項目」とセクションに書く。「ある」と読まない |
| 3 | 設計文書が無い（`not_applicable`） | 3 つの確認を「該当なし（設計文書が無い）」で満たす |
| 6 | 「確かめられなかった」名前だけが残る（`incomplete`） | 終了コード 2 と同じく自分で確かめる |

## 確認 (b): 既存の確定仕様と変更履歴が変更後の振る舞いと合う

起点との merge-base から HEAD までに変えたファイルのパスと、増減したシンボル（定義の名前と `_` を含む大文字の定数）を
語として集め、`docs/specifications/` の `.md` と `CHANGELOG.md` から、その語を含む文書を探す。同じ差分で足した文書は除く。

```bash
git diff --name-only origin/<ベースブランチ>...HEAD          # 変えたファイルのパス
git diff origin/<ベースブランチ>...HEAD | grep -E '^[-+]'     # 増減した定義の名前と定数を拾う
grep -rnF -e '<語>' docs/specifications CHANGELOG.md           # 語ごとに一致する行
```

一致した語の種類の多い文書から読み、変更後の振る舞いと合わない記述は同じ PR で直す。直せない記述はセクションに並べる。広く使われるパスは多くの
文書に一致するため、一致した語がパス 1 つだけの文書は、その記述がこの差分の変更に触れているかを見るだけでよい。

## 確認 (c): 設計の決定が実装と一致する

設計文書の `### 決定 N` を 1 件ずつ実装と照らし、次のどれかに分ける。

| 分け方 | 扱い |
| --- | --- |
| 一致する | 並べない |
| 違う | セクションに「何が違うか」と理由を並べるか、設計文書を同じ PR で直す |
| 実装しなかった | セクションに「実装しなかった」と理由（別の課題へ分けたなら番号）を並べるか、設計文書を同じ PR で直す |
| 判断できない | セクションに「判断できない」と理由を並べる |

**詳細設計の中身も実装と照らし、同じ分け方で並べる。** 読む先は文書の有無だけで 1 つに決まる。

| ある文書 | 照らすもの |
| --- | --- |
| 詳細設計書（名前に含む番号のどれかが一致する `issues/issue-<番号の並び>-design-detail.md`） | その「モジュールマップ」の表のパスと「関数の仕様」の表の関数（シグネチャ・責務） |
| 設計書だけ（詳細設計を畳んだ） | 設計書の「どこを変えるか」の表のパスと関数（新設する関数の入力・返り・異常系、責務や失敗時の扱いを変える関数の変える前と後） |
| 設計書も省いた | 実装計画の「修正対象」（下の「設計書を省いた変更」） |

詳細設計は実装の後に追随させない文書のため、違いは設計文書を直すよりセクションに並べることを先に考える。
突き合わせを入れるモードは今までどおり `standard` だけである。

## 設計書を省いた変更

実装計画（`issues/issue-<番号>-plan.md`）の頭に `省いた文書: 設計書` の行があり、`ndf loop design-tests` が設計文書なし
（`not_applicable`）を返したときは、3 つの確認を次に置き換える。設計書を省いても、実装を何かと照らさずに完了にしないためである。

- **確認 (a) と (c) の代わり**: 実装計画の「修正対象」の行（ファイル・関数・変える前と後）を差分と照らす。
  差分のファイル（`git diff --name-only <ベース>...HEAD -- . ':(exclude)issues/issue-*'`。実装計画など工程が書く文書は「修正対象」にも
  触るファイルの数にも入れない）が「修正対象」に無い、「修正対象」のファイルが差分に無い、
  関数の行と実装が違う、のどれかは `## 設計と違う点` に並べる（設計の箇所の列は「実装計画の修正対象」）
- **確認 (b)**: 設計文書が無くても差分から行えるので、そのまま行う
- **省く条件の数え直し**: 設計書を省く条件（公開インタフェースに触れない・触るファイル 4 以下・
  新設する関数 0・シグネチャを変える関数 0。正は `requirements-design` の
  [document-roles.md の「省いてよい文書と条件」](../../requirements-design/references/document-roles.md#省いてよい文書と条件)）を、
  実装の差分から数え直す。小さな変更に限って設計書を省いた前提が、実装の後も成り立つかを確かめるためである。手順は下の 1〜4

### 数え直しと流し直しの判定

1. **実装計画の頭に `省いた文書: 設計書` の行があるときだけ行う。** 行が無ければ数え直さない
2. **差分から 4 つの値を数え直す。** 触るファイルの数は下のコマンドの行数で数える。新設する関数の数とシグネチャを変えた
   既存の関数の数は、同じ差分から数える。公開インタフェースに触れるかは、差分が要求仕様の「影響」の表の「公開インタフェース」の
   行の対象に触れるかで決める。課題の数はスプリントの課題の並びで、設計書を省けるときは必ず 1 である

   ```bash
   # 触ったファイルの数。工程が書く文書 issues/issue-<番号>-*.md は省く条件の見込みと同じく数えない
   git diff --name-only <ベース>...HEAD -- . ':(exclude)issues/issue-*' | wc -l
   ```

3. **1 つでも外れたら、工程「完了判定」を失敗で返す。** 外れるのは、上の「省く条件の数え直し」の条件のどれかを
   満たさないときである。`## 設計と違う点` に外れた値と
   数えた結果を並べ、理由を「設計書を省く条件から外れた: <外れた値>」にする。完了にせず、マージへ進まない
4. **失敗の後の流し直しは、`development-workflow` の SKILL.md の [「文書を省いたときの工程」](../../development-workflow/SKILL.md#文書を省いたときの工程) に従う。**

外れなければ、上の (a)(c) の代わりの照らし合わせと (b) を今のとおり行う。

## 要求の前提を変えたとき

実装で受け入れ条件の前提を変えたら、課題の本文の条件を `requirements-design` の「変更の途中で要求が変わったとき」の形
（取り消し線と変更の理由）に直す。本文は `gh issue view <番号> --json body --jq .body` で読み、受け入れ条件のセクションだけを直して
`gh issue edit <番号> --body-file <ファイル>` で書き戻す。ほかのセクションは変えない。
写し（`issues/issue-<番号>-requirements.md`）があれば、同じ内容に直して同じ PR でコミットする。

## 実装 PR の本文のセクション

```markdown
## 設計と違う点

| 設計の箇所 | 違い | 理由 |
| --- | --- | --- |
| 決定 3 | 戻り値を `0` ではなく `2` にした | 呼び手が「読めない」と区別できないため |
| 決定 6 | 実装しなかった | #1234 へ分けた |
| `tests/ci/test_ci_workflow.py` | 作らなかった | `tests/ci/test_trigger.py` に入れた |
| `docs/specifications/x.md` の 59 行 | 直していない記述がある | 判断できない（記述の意図が読めない） |
| 受け入れ条件 2 | 実装で変えた | 接続の設定を隔離の前に引き継ぐため |
| 実装計画の修正対象 | `src/app/retry.py` が差分にあり、修正対象に無い | 呼び出し元の引数も直す必要があった |
```

違いが無ければ `- 無し`、設計文書が無ければ `- 該当なし（設計文書が無い）` の 1 行にする（設計書を省いた変更は
「該当なし」にせず、上の「設計書を省いた変更」の突き合わせの結果を並べる）。同じ PR で設計文書・既存の
確定仕様・要求の文書を直した箇所は並べない（直した文書が正になる）。

セクションは担い手が上の形で書き、実装 PR の本文に 1 つだけ置く（`gh pr edit <PR> --body-file <ファイル>`）。
3 層では完了判定のプランの worker（`judge` のステップ）がセクションを書く。
