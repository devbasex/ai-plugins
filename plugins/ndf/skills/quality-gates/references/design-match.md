# 設計との突き合わせ

`standard` の完了判定で、実装を設計文書・既存の確定仕様・要求と照らし、食い違いをマージの前に見えるようにする。
確認は (a)(b)(c) の 3 つで、結果は実装 PR の本文の `## 設計と違う点` の節に残す。

## 実例

devbasex/devbase の #216 の設計文書は、`## 構成要素` に回帰テスト `tests/ci/test_ci_workflow.py` を、
`## テスト設計` にテスト関数 `test_pull_request_is_not_filtered_by_branch` などを書いていた。実装の HEAD で
確認 (a) を打つと、次のように「無い」が出て終了コード 1 で終わる。

```bash
python3 "$SCRIPTS/design-match.py" tests --issue 216
# items: tests/ci/test_ci_workflow.py missing（構成要素）・test_pull_request_is_not_filtered_by_branch missing（テスト設計）…
```

同じスプリントで shellcheck の版を固定した変更（devbasex/devbase の `4d82277`）に確認 (b) を打つと、既存の確定仕様 `docs/specifications/base-image-shellcheck.md` が
一致した語 4 つ（変えたパス 3 つと `SHELLCHECK_VERSION`）で最上位に並び、「版は固定せず」と書いた行が出る。
担い手はテストを作るか節に「作らなかった」と理由を並べ、確定仕様の記述を同じ PR で直す。

## いつ行うか

| モード | 行うこと |
| --- | --- |
| `standard` | (a) → (b) → (c) の順に行い、節を実装 PR の本文に置く |
| `light` / `operation` / `documentation` / `legacy-refactor` | 行わない。手順も所要も変えない |

`standard` でも設計文書が無ければ（`tests` が終了コード 3）、3 つの確認を「該当なし（設計文書が無い）」と書いて満たし、
`specs` は打たない。3 層（supervise.py）の実装プランは、範囲テストと PR の間で同じ 3 つを流す。

## 確認 (a): 設計に名前の出るテストが実在する

```bash
python3 "$SCRIPTS/design-match.py" tests --issue <番号>
```

`issues/` の `issue-<番号>-design*.md`（決定の記録の別ファイルを含む）を HEAD から読み、`## 決定の記録`・`## テスト設計`・
`## 構成要素` にバッククォートで書かれたテストファイルのパス・`<パス>::<名前>` と、`## テスト設計` の `test` で始まる
識別子を拾う。関数の有無は、名前がファイルに語として現れるかで見る（言語を問わない）。

| 終了コード | 読み方 | すること |
| --- | --- | --- |
| 0 | すべてある（0 件を含む。`metrics.names` が 0） | 次へ |
| 1 | 「無い」（`missing`）がある | 作るか、節に「作らなかった」と理由を並べる |
| 2 | 設計文書か git が読めない、または「確かめられなかった」（`unverified`）がある | 自分で確かめる。確かめられなければ報告の「未検証の項目」と節に書く。「ある」と読まない |
| 3 | 設計文書が無い | 3 つの確認を「該当なし（設計文書が無い）」で満たす |

## 確認 (b): 既存の確定仕様と変更履歴が変更後の振る舞いと合う

```bash
python3 "$SCRIPTS/design-match.py" specs --base origin/<起点のブランチ>
```

起点との merge-base から HEAD までに変えたファイルのパスと、増減したシンボル（定義の名前と `_` を含む大文字の定数）を
含む文書を、`docs/specifications/` の `.md` と `CHANGELOG.md` から並べる。同じ差分で足した文書は並ばない。
並びは一致した語の種類の多い順で、1 文書の行は `--max-lines`（既定 10）まで出る。

上から読み、変更後の振る舞いと合わない記述は同じ PR で直す。直せない記述は節に並べる。広く使われるパスは多くの
文書に一致するため、一致した語がパス 1 つだけの文書は、その記述がこの差分の変更に触れているかを見るだけでよい。

## 確認 (c): 設計の決定が実装と一致する

設計文書の `### 決定 N` を 1 件ずつ実装と照らし、次のどれかに分ける。

| 分け方 | 扱い |
| --- | --- |
| 一致する | 並べない |
| 違う | 節に「何が違うか」と理由を並べるか、設計文書を同じ PR で直す |
| 実装しなかった | 節に「実装しなかった」と理由（別の課題へ分けたなら番号）を並べるか、設計文書を同じ PR で直す |
| 判断できない | 節に「判断できない」と理由を並べる |

## 要求の前提を変えたとき

実装で受け入れ条件の前提を変えたら、課題の本文の条件を `requirements-design` の「変更の途中で要求が変わったとき」の形
（取り消し線と変更の理由）に直す。本文は節ごとに `gh_parts.py body-section replace --issue <番号> --heading <節の見出し>`
で差し替え、`gh issue edit --body-file` で本文全体を書き直さない（課題ごとの錠の中で書き、進行の記録と互いに消さない）。
続けて `spec-copy.py write <番号> issues/issue-<番号>-requirements.md` で写しを作り直し、同じ PR でコミットする。

## 実装 PR の本文の節

```markdown
## 設計と違う点

| 設計の箇所 | 違い | 理由 |
| --- | --- | --- |
| 決定 3 | 戻り値を `0` ではなく `2` にした | 呼び手が「読めない」と区別できないため |
| 決定 6 | 実装しなかった | #1234 へ分けた |
| `tests/ci/test_ci_workflow.py` | 作らなかった | `tests/ci/test_trigger.py` に入れた |
| `docs/specifications/x.md` の 59 行 | 直していない記述がある | 判断できない（記述の意図が読めない） |
| 受け入れ条件 2 | 実装で変えた | 接続の設定を隔離の前に引き継ぐため |
```

違いが無ければ `- 無し`、設計文書が無ければ `- 該当なし（設計文書が無い）` の 1 行にする。同じ PR で設計文書・既存の
確定仕様・要求の文書を直した箇所は並べない（直した文書が正になる）。

単発では `pr-steps.py template --mode standard` が節の雛形を書き、`create` / `update` に `--mode standard` を渡すと、
節が無ければ `next` で足すよう求める。3 層では `design-match` のステップの worker が節を書き、`pr` のステップが本文へ
1 つだけ置く。節のファイルが無いまま設計文書があると、`pr` のステップは PR を作らずに止まり、judge へ戻る。
