# モード別の完了の定義

完了の定義は変更の性質によって変わる。モードの判定基準は `development-workflow` が持つ。
ここでは**判定結果ごとに何が揃っていれば完了か**だけを定める。どのモードに当たるかを
この文書で判定しない。`development-workflow` が使えない場合は、変更の影響範囲（公開
インタフェース・スキーマ・認証を含むか、既存の振る舞いを変えるか）を報告に書き、
どのモードとして扱うかを依頼者に確認してから該当節のチェックリストを使う。

チェックリストは省略できない。該当しない項目は「該当なし」と理由を書く。

## `light`

- [ ] 変更した箇所が実際に読み込まれる経路を 1 度実行した
- [ ] 静的解析・型検査・ビルドが通る（コマンドと終了コード）
- [ ] 変更範囲が依頼どおりで、無関係な整形が混ざっていない
- [ ] ドキュメントの変更ならリンクと手順が実行可能である

全体テストは必須にしない。ただし**変更が振る舞いに影響しないという判断の根拠**を書く。
根拠が書けないなら `light` ではない。

## `operation`

- [ ] 実行の範囲が単位に分かれており、単位ごとに取り消しの手段が書かれている
- [ ] 本番の系へ届く単位について、実行の前に承認を得ている
- [ ] 単位ごとにコマンド・出力・終了コードが記録に残っている
- [ ] 反映を確かめた手段と結果が残っている（確かめられない単位は「確かめられない」と残す）
- [ ] 失敗した単位がある場合、そこで止めており、部分適用の範囲が記録に残っている
- [ ] 取り消せない単位は、取り消せないことと影響の範囲が実行の前に書かれている
- [ ] 記録に機微情報（資格情報・鍵・個人を特定できる情報）が含まれていない
- [ ] 静的解析・型検査・ビルドが通る（本番コードを触っていない場合は「該当なし」と書く）

全体テストは必須にしない。本番コードを触らないためである。**触るなら `operation` ではない。**
手順は `development-workflow` の `references/operation-run.md` にある。

## `standard`

- [ ] 受け入れ条件ごとに検証手段と結果が対応している
- [ ] 追加・変更した振る舞いのテストがある（バグ修正なら再現テストが残っている）
- [ ] 全体テストが通る
- [ ] 静的解析・型検査・ビルドが通る
- [ ] カバレッジ設定がある場合、その閾値を満たす（設定がなければ測定値のみ記録）
- [ ] 依頼範囲外の変更が混ざっていない
- [ ] 失敗・未検証の項目が残っていない（残る場合は列挙して理由を書く）
- [ ] 契約テストが通る（呼ぶ側・呼ばれる側の双方）
- [ ] 結合テストが通る（DB・外部通信を含む経路）
- [ ] 後方互換の扱いが決まっており、破る場合は移行手順がある
- [ ] データ移行がある場合、**前進と巻き戻しの両方**を実行して確認した
- [ ] 設定・秘密情報の追加が必要な場合、反映手順が記録されている
- [ ] 切り戻し手順が書かれている
- [ ] 設計判断の記録（採否の理由）が残っている

移行の巻き戻しを試していない状態を完了にしない。巻き戻せない移行は、その旨を明示する。

**対象を持たない項目は、持たないことを書いて満たす。** 契約テストも結合テストも移行も、
変更が触らなければ実行するものが無い。**空欄にしない**（実行して結果が無かったのか、
対象が無かったのかが読み分けられない）。

## `legacy-refactor`

- [ ] 現状固定テストがあり、改善の前後で同じ結果になる
- [ ] 公開インタフェースの入出力が変わっていない
- [ ] 全体テストが通る
- [ ] 静的解析・型検査・ビルドが通る
- [ ] カバレッジ設定がある場合、その閾値を満たす（設定がなければ測定値のみ記録）
- [ ] 機能変更が混ざっていない（混ざる場合は差分を分けた）
- [ ] 性能が明らかに悪化していない（呼び出し回数・入出力の増加を確認した）
- [ ] 固定テストのうち不具合を固定したものに印がある

## どのモードでも書くこと

| 項目 | 内容 |
| --- | --- |
| 検証の証跡 | `SKILL.md` の「証跡として必要なもの」の全項目を、「検証の段階」の段階ごとに書く |
| 未検証の項目 | 何を検証していないか。理由 |
| 既存の失敗 | 変更前でも失敗することの根拠 |
| 範囲外と判断したもの | 何を、なぜ今回やらないか |

## 完了と呼べない状態

- テストが失敗したまま「後で直す」としている
- 検証コマンドを実行せず、コードを読んだだけで判断している
- 受け入れ条件のうち一部に検証手段がない
- 生成物（ビルド出力・同期されるファイル）を再生成していない
- 継続的インテグレーションが失敗しており、内容を確認していない
