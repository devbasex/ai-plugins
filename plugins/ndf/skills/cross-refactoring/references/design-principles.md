# 設計方針

| 観点 | 方針 |
| --- | --- |
| 参加者 | **全員 CLI プロセス。** 提案は提案の参加者が 1 度ずつ、リファクタリング計画以降は修正担当（claude）1 者。ホストと同じランタイムでも別プロセスで起動する |
| 時間 | **実装の予算（`--budget-minutes`）は選定にだけ使う。** 見積り（テストの追加と実装の和）の合計が実効の予算に収まる項目を採る。予算から締め切りを導かず、選んだ項目を時間で打ち切らない。時間の上限は安全網（コードを書く工程の起動の秒の累計）だけに置き、当たっても取り消さずに止める |
| 検証の単位 | **項目。** 項目が触るモジュールに対応するテストと検査だけを打ち、項目の起点から在った失敗はその項目の失敗に数えない。全体テストは最終ゲートの CI が見る |
| 収束しない項目 | **落ちたキーの集合の履歴で決める。** 停滞か振動したら、修正担当と別のランタイムが成立を判定する。成立しない項目と、判定で続けた後も停滞か振動した項目は、項目の起点まで戻す |
| 見積り | 配分の表（初期値・設定・履歴の実測）から付け、担当の申告を使わない。所要は `run` の時計で測る |
| 範囲の扱い | `--scope` は案出しの対象と、最終ゲート修正が変えてよい範囲を決める。提案と項目は課題が触る関数を指すものだけを採る |
| 公開の責務 | **`run` だけが push する。** 担当はコミットまでで、送らない |
| 検証の情報源 | **git と実際のテスト・検査の実行。** 結果ファイルの申告は検証に使わない |
| 外へ出す文章 | 項目は **`<ファイル>#<シンボル>` を併記**し、リファクタリング計画は**生の URL** で書く |
| 最終ゲート | PR の head へ送り、ベースとの衝突を確かめてから CI の必須のチェックを待つ。落ちたテストは対象範囲の中だけで直させる |
| 状態の永続化 | 作業場所の根の `state.json`。止まっても同じコマンドで続けられる |
