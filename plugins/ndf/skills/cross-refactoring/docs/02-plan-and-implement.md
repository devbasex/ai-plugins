# リファクタリング計画・テスト追加・実装

[← SKILL.md](../SKILL.md)

**リファクタリング計画以降の 4 つの手順は実装担当 1 者が通す**（決定 1）。1 回の起動の中で項目ごとに
コミットさせ、所要の測定と項目の単位の取り消しを git から行う（決定 12）。

## リファクタリング計画

```bash
rf_eval start-phase "$ID" plan               # PHASE_TIMEOUT = リファクタリング計画の枠の終わりまでの残り + 余裕
"$SCRIPTS/launch-cli.sh" "$IMPL" plan "$ID"
"$LIB/monitor.py" "$ID" --agents "$IMPL" --tmp-dir "$TMP_DIR" \
    --stem-template "{agent}-plan-rf$ID" --phase plan \
    --timeout "$PHASE_TIMEOUT" --stall-timeout "$PHASE_TIMEOUT" \
    --alive-file "$TMP_DIR/cross-refactoring-rf$ID-alive"
rf_eval merge-plan "$ID"          # TESTS_NEEDED=0|1。2 = 項目 0 件（readopt を経て最終ゲートへ）
```

実装担当は改善候補の全件について判断を返す。**コマンドは返さない。**

```json
{"items": [
  {"key": "src/a.py#Foo.run#long_method", "tier": "high",
   "tests": ["tests/test_a.py"], "test_targets": ["tests/test_a.py::TestFoo"],
   "merge_into": null, "risk": false}
]}
```

| 項目 | 意味 |
| --- | --- |
| `tier` | 適用する価値（`high` / `medium` / `low`）。返らなければ `medium` |
| `tests` | リファクタリングの前に足す現状固定テストの置き場所。空なら足さない |
| `test_targets` | 範囲テストの対象（パスか `<パス>::<名前>`）。オーケストレーターがコマンドへ差し込む |
| `merge_into` | 同じ `path` + `symbol` の別の改善候補と同じ変更なら、その改善候補の `key` |
| `risk` | 公開の入出力が変わりうるか（危険フラグ D5 の材料。Jev が使えなければこれを使う） |

**リファクタリング計画を読めなくても止めない。** グレードは既定（または Jev）、テストは足さず、`round-only` なら
ラウンドテストをそのまま使う形で進める。止めると提案に使った時間が丸ごと無駄になる。

### `merge-plan` がすること

1. **グレードを決める。** Jev が使えるときは改善候補ごとに `score`（low / medium / high）を問い、
   確信度 0.6 以上なら Jev のグレード、未満か失敗なら実装担当のグレード（失敗は `judge.failures` に数える）
2. **同じ変更を統合する。** 同じ `path` + `symbol` の組の中の 2 件だけを比べる。Jev が
   確信度 0.8 以上で「同じ」と答えたら統合し、それ以外は実装担当の `merge_into` に従う。
   統合された改善候補は `duplicate` で見送り、賛同した者を統合先へ足す
3. **範囲テストを組み立てる**（下の節）。組み立てられない改善候補は `no_target` で見送る（手法が `remove_dead_code` なら `deletion` として残す）
4. **見積もる。** 配分テーブル（[04](04-verify-and-report.md#配分テーブル)）から
   `test`（足すテストがあるときだけ）+ `structure/<手法>`。**検証・テストの実行・CI の待ちは見積りに入れない**（#2457 決定 1）
5. **順位を決める。** (グレード, 賛同した者の数, 重要度) の降順、同じなら見積りの昇順
6. **予算を延ばすかを決める。** グレード `high` の候補の見積りの和 S が実装の予算 B を超え、`2·B`（倍率は `limits.json` の
   `cross-refactoring.budget-extension`）以下なら、実効の予算を `ceil(S)` 分にする。延ばしたことと前後の値と理由を
   `budget.extension` に残す。S が 2 倍を超えれば延ばさない（決定 2）
7. **実効の予算に収まる件数を選ぶ。** 順位の順にたどり、**入る項目は入れ、入らない項目は飛ばして次を見る**（`budget` で
   見送る。決定 10）。経過時間を引かない。採った項目は `I-001` の形の ID と巡の番号 `round: 1` を持ち、期限を持たない
8. **D5 を決める。** 採った項目ごとに、公開の入出力が変わりうるかを Jev に問い（確信度 0.7
   以上で採る）、使えなければ実装担当の `risk` を使う。`items[].public_io` に残し、検証は
   読むだけにする（決定 25）
9. **値を書き出す。** 予算（`budget`）・安全網の上限（`safety_net.limit_minutes`）・テストと CI の待ちの上限（`limits`）を
   状態ファイルへ書く

**リファクタリング計画は叩き直しても作り直さない。** 採用の件数と実効の予算はこの時点の値で固定する。
採る件数を増やすのは、検証の後の採り直し（下の「採り直し」）だけである。

### 範囲テストの組み立て

戦略のテストの種別の範囲テストのテンプレート（宣言の `scope_command`。`test_targets` の各パスを `paths` で受け持つ suite のもの）の
`{paths}` の字句を、シェルの引用で守った `test_targets` の並びへ置き換え（共通ライブラリの `test_strategy.scope_runs`）、項目の
`scope_commands` に置く。組み立てたコマンドは**シェルで 1 本ずつ**走らせる。**コマンドを読むのは `{paths}` の置き換えだけである**
（ランナーの名前・前置き・オプションの値は見ない）。静的解析の suite の範囲テストは計画で組まず、検証のたびに項目のコミットが
変えたファイルから組む。テストの種別の suite が無い戦略では、項目の `tests` を空にし（テスト整備ラウンドを行わない）、
項目を `no_target` で見送らない。足したテストの成否はテストの種別の suite だけで判定する。

`test_targets` の各要素は次をすべて満たす。1 つでも満たさなければ組み立てない。

- `--scope` のテストの置き場所の中のパスか、そのパスに `::` で続くノード ID である。**ただし、その項目が足すテスト
  （`tests`）は、テストの種別の suite のどれかの `paths` が覆えば置き場所の外でもよい**（範囲テストは suite のテンプレートで組むため、
  suite が覆わないパスは組んでも走らない）
- パスの部分が作業ディレクトリに実在する。**ただし、その項目が足すテスト（`tests`）は
  まだ無くてよい**（足さなければ持ち越しになり、採り直しに入らなければ `not_done` で見送られる）
- シェルの構文の文字（`;` `&` `|` `$` `` ` `` `<` `>` `(` `)` 改行）と空白を含まない

`round-only` はラウンドテストをそのまま使う（`command_source: round_test`）。組み立てられない項目は `no_target` で見送る。
**全体テストを項目の範囲テストに使うことはない**（全体テストは危険フラグの 1 回だけ）。

**ただし、組み立てられない `remove_dead_code` の項目は見送らない**（`command_source: deletion`）。死んだコードには呼ぶテストが
無いためである。範囲テストを持たず、静的解析の範囲テストと、危険フラグ D4（範囲テストが覆うと示せない）で 1 度走る
全体テストで検証する。全体テストの起動は足さず、今の危険フラグの経路だけを使う。

### 時間の上限

**実装の予算（`--budget-minutes`、既定は `limits.json` の `cross-refactoring.default-budget` の 60 分）は選定にだけ使う**。
予算から締め切りを導かず、選んだ項目を時間で打ち切らない。時間の上限はハングの検知と安全網だけで、
どちらも予算に縛られない（安全網の既定は実効の予算から決まる）。

| 上限 | 決め方 | 当たったとき |
| --- | --- | --- |
| テスト 1 回・手元の全体テスト 1 回・着手前のテスト 1 回の上限 | 共通ライブラリ `test_strategy.limits` の予算なしの式。`3·max(w, m)`（w は宣言の全体テストの所要、m は手元の全体テストの直近の実測、x は着手前のテストの実測）。所要が無ければ既定の秒（`UNKNOWN_DURATION_LIMITS`）。下限は 60 秒 | ハングの検知。着手前のテストなら `SKIP=init-timeout`（終了コード 6）、ほかは落ちた扱い |
| CI の待ちの上限 | `3·c`（c は CI の壁時計）。無ければ既定の秒 | 「判断が要る」で止まる |
| 指標の測定の上限 | 提案の工程の監視の上限の半分 | 測れなかった言語を `timeout` にして続ける |
| 提案・計画・判定の手順の監視の上限 | `limits.json` の `monitor.phase.<手順>` | 止まった CLI として扱う |
| 安全網の上限（コーディングの CLI） | `--safety-net-minutes`、無ければ実効の予算 × `cross-refactoring.safety-net` の倍率（2）。コーディングの CLI（テストの追加・実装・修正・最終ゲート修正）の起動ごとの秒（監視の開始から終わり）の累計を数える。提案・計画・判定・テストの実行・CI の待ちと止まっていた時間は数えない | 項目を取り消さず、HEAD をそのまま残して止め、人へ渡す（結果 JSON は `gate`・終了コード 10） |

コーディングの手順の監視の上限は、`start-phase` が安全網の残りで切る（CLI の上限はそれに `monitor.cli-margin` を足す）。
起動の前に残りが 0 以下なら、起動させずに `HALT=1` を返す。駆動は監視の後に `coding-time` でその起動の秒を足し、上限に
届いたら新しいコーディングの CLI を起動せずに止まる。止まった実行は、より大きい `--safety-net-minutes` で同じコマンドを
打ち直すと続く。

**検査のプランのステップの締め切りは、子プロセスごとに延ばす**（決定 8）。雛形の `refactor` のステップの `timeout` は
「実装の予算 ×（1 + 安全網の倍率）」に `with_margin` を足した秒で、テストの実行・CI の待ちはこの外にある。駆動と
`refactor.py` は子プロセス（テスト・CI の待ち・CLI）を起動する前に、ステップの開始からの経過とその子プロセスの上限の和を
ステップの延長のファイル（`drive_pause.write_extension`）へ書く。ステップの開始は駆動が環境変数
`CROSS_REFACTORING_STEP_STARTED` で渡す。

**着手前のテストは成否と打ち切りを問わず、配分の履歴へ 1 行足す**（`kind: init_test`。範囲・戦略・秒）。

値は `state["limits"]` に書き出し、リファクタリング計画のコメントに「時間の上限」の表として載せる。
**手順の監視の上限で CLI を止めたときは**、未コミットの変更を捨て、コミット済みの項目はそのまま取り込み、コミットの無い
項目は持ち越す（採り直しの候補へ戻る）。止めたことは `phases.<手順>.stopped` に残り、報告に 1 行出る。

固定のまま残すのは、OS の後始末と通信の待ち（`kill_grace` 5 秒・監視の SIGTERM の猶予
3 秒・`RESULT_AGE_GRACE` 30 秒・見回り 15 秒・Jev の通信 10 / 20 秒・認証確認 120 秒）
だけである。報告の「固定のまま残した値」に並ぶ。

## 結果を残さなかった担当の振り替え

**監視が非ゼロ（手順の上限での打ち切り `timeout` / `stalled` を除く）で終わったら、取り込みの前に `reassign` を打つ**。
起動し直すか・誰へ振り替えるかは共通ライブラリの規則（`assignment.after_no_result`）だけが決める。

```bash
rf reassign "$ID" implement      # 工程は propose / plan / add-tests / implement / fix / final-fix
```

| 終了コード | 意味 | 駆動がすること |
| ---: | --- | --- |
| 0 | 結果なしとして扱わない（結果がある・上限での打ち切り） | そのまま取り込みへ |
| 7 | 同じ工程を起動する（`IMPL` / 提案は `PROPOSERS`、振り替えなら `REASSIGNED`） | 返された担当で同じ工程を起動し、監視へ戻る。起動のたびに `start-phase` を打ち直し、安全網の残りから上限を出し直す |
| 2 | 次の起動から担当を替えた、または今のまま起動し直す（`fix` / `final-fix`） | 取り込み（`merge-fix` / `merge-final-fix`）へ |
| 3 | 振り替え先が無い（`REASSIGN=abort`） | `plan` / `add-tests` / `implement` は止まる。`fix` / `final-fix` は取り込みへ（修正は打ち切り） |
| 4 | 範囲を確定できない | 中断 |

`plan` / `add-tests` / `implement` では、範囲を取り消す前に担当が残した未コミットの変更を捨てる（検証を受けていない変更を次の担当へ渡さない）。

規則は上から順に当てる。

| 順 | 条件 | 答え |
| ---: | --- | --- |
| 1 | 理由が `usage_limit` 以外で、同じ工程・試行・担当（アカウントを含む）をまだ起動し直していない（`fix` / `final-fix` は起動し直しが次の試行になるため、1 つ前の試行の起動し直しも同じ件として数える） | 同じ担当で起動し直す |
| 2 | claude の `usage_limit` で、登録済みの別のアカウントが使える | 別のアカウントの claude へ振り替える（子へ渡すのは `CLAUDE_CONFIG_DIR` を向けた環境だけ） |
| 3 | 利用可能な参加者から外した担当と結果なしの担当を引いて、1 者以上残る | 「ホスト → 先頭」で 1 者へ振り替える |
| 4 | どれにも当たらない | 中断 |

| 工程 | 範囲の取り消し | 振り替えた後 | 振り替え先が無いとき |
| --- | --- | --- | --- |
| `plan` / `add-tests` / `implement` | `reassign` が工程の起点から HEAD までを取り消してから答えを求める | 同じ工程を振り替え先が続ける。採用済みの項目のコミットは起点より前にあり触らず、未確認の項目（`implement` なら `planned` / `tested`）から続ける | 止まる |
| `fix` | 取り消さない（`merge-fix` が `Item-Id` で受け取り、次の `verify` が見直す） | 次の修正から振り替え先 | `fix_no_relaunch` を立てる。落ちたテストの集合が変わらないため、次の `verify` が停滞として判定し直しへ回す |
| `final-fix` | 今の `merge-final-fix` が取り消す | `final_gate.impl` も替え、次の修正ラウンドから振り替え先 | `final_gate.no_relaunch` を立て、次の最終ゲートが止めて人へ渡す |
| `propose` | 範囲は無い | 全員が結果なしのときだけ、提案を出していない担当で集め直す | 止まる |

振り替え先は同じ工程を続け、コミットの無い項目は持ち越され、採り直しにも入らなければ `not_done` で見送られる。振り替えの事実は状態ファイルの `no_results`（結果なしの記録。追記だけ）に残り、報告の
「振り替え」の行と結果 JSON の `metrics.reassigned` に出る。外した担当は同じ実行の残りで実装担当にも振り替え先にもならない。

## テストの追加

```bash
rf_eval start-phase "$ID" add-tests          # PHASE_TIMEOUT
"$SCRIPTS/launch-cli.sh" "$IMPL" add-tests "$ID"
"$LIB/monitor.py" "$ID" --agents "$IMPL" --tmp-dir "$TMP_DIR" \
    --stem-template "{agent}-add-tests-rf$ID" --phase add-tests \
    --timeout "$PHASE_TIMEOUT" --stall-timeout "$PHASE_TIMEOUT" \
    --alive-file "$TMP_DIR/cross-refactoring-rf$ID-alive"
rf merge-tests "$ID"                         # 2 = 残る項目 0 件（検証を飛ばして readopt へ）
```

**足すのはリファクタリング計画が「足すテスト」を持つ項目のテストだけである**（網羅の提案はしない）。
`merge-tests` は手順の起点から HEAD までのコミットを `Item-Id` で項目へ振り分ける。対象は今の巡（`readopt.round`）で採った
`planned` の項目だけで、前の巡で検証を終えた項目とそのコミットに触れない。

| 見つけたもの | 扱い |
| --- | --- |
| `Item-Id` が無い・リファクタリング計画に無い・テストを足さない項目のコミット | そのコミットだけを `git revert` で打ち消し、差し戻し（`sendbacks`。付け直して出し直させる）に残す |
| テスト以外のファイルを変えた・2 コミット以上・トレーラー欠け・文言固定テスト | 取り消さない。項目の `sendbacks[]` に残し、報告に出す |
| 範囲の外の既存のファイルを変えた（下の「範囲の判定」） | 取り消さない。項目の `outside_scope[]` に残し、報告とコードレビューへ引き継ぐ |
| コミットが無い | 持ち越し（`carried`）にする。採り直しに入らなければ `not_done` で見送る |
| 足したテストが**今のコードで落ちた** | 取り消さない。差し戻し（`test_failed`）に残し、実装の後の検証が落ちたテストとして修正へ回す |

**現状固定テストは今のコードで通って初めて比較の基準になる。** 落ちるテストは実装の後の検証で直させる。

## 実装

```bash
rf_eval start-phase "$ID" implement          # PHASE_TIMEOUT
"$SCRIPTS/launch-cli.sh" "$IMPL" implement "$ID"
"$LIB/monitor.py" "$ID" --agents "$IMPL" --tmp-dir "$TMP_DIR" \
    --stem-template "{agent}-implement-rf$ID" --phase implement \
    --timeout "$PHASE_TIMEOUT" --stall-timeout "$PHASE_TIMEOUT" \
    --alive-file "$TMP_DIR/cross-refactoring-rf$ID-alive"
rf merge-implement "$ID"                     # 2 = 残る項目 0 件（検証を飛ばして readopt へ）
```

実装担当は順位の順に 1 件ずつ適用し、項目の変更を同じ `Item-Id` のコミットにする。改名と中身の変更のように
分けたほうが読みやすいときは、**1 項目を複数のコミットにしてよい**（`commits.implement` は古い順の並び）。
テストの追加は 1 項目 1 コミットのままである。全項目を終えるか監視が CLI を止めるまで続け、コミットの無い項目は持ち越す。

### マージ処理のチェック

`merge-implement` は次を git から確かめる。**結果ファイルの申告は検証に使わない。**

| 検証 | 情報源 | 満たさないとき |
| --- | --- | --- |
| 項目とコミットの対応 | トレーラー `Item-Id` | 属さないコミットだけを `git revert` で打ち消し、差し戻しに残す |
| 実行主体の明記 | `Item-Id` / `Impl-Runtime` / `Impl-Model` のトレーラー（コミットごと） | 取り消さない。差し戻しに残して報告に出す |
| 範囲の判定 | 項目の全コミットのファイルの状態と `-U0` のハンク（下の「範囲の判定」） | 取り消さない。範囲の外で変えたファイルを `outside_scope` に残す |
| **テストの期待値が変わっていない** | 項目の全コミットが変えたテストのファイルの和集合（一次の判定） | 値がどこにも無くなれば、項目を `failing`（落ちた検査 `sendback`）にして期待値を戻すよう修正へ差し戻す。決まらない差分は最終ゲートのレビューへ引き継ぐ |
| 文書の文言を固定するテストを足していない | 追加行の文字列 | 項目を `failing` にして、そのテストだけを外すよう修正へ差し戻す |
| コミットが無い | — | 持ち越し（`carried`）。採り直しに入らなければ `not_done` |

**項目の所要はコミットの時刻で測る**（決定 8）。終わりは項目の最後のコミットの時刻、起点は、その手順で最初の項目なら
手順の開始、2 件目からは同じ手順の直前の項目の最後のコミットの時刻である。

**実差分の行数では取り消さない。** 範囲の逸脱は範囲の判定が直接見る。分割はファイルの一部を
移すため、移した行を削除と追加の 2 回に数え、見積の何倍にもなる。実差分（`items[].diff_lines`）は名前の変更を `-M` で
1 回に数え、項目の全コミットの和を記録だけする。

### 範囲の判定

**分割・抽出の行き先と、移動・改名・シグネチャの変更・インライン化に伴う呼び手の書き換えを塞がない。**
実装・修正・最終ゲート修正・テストの追加の取り込みは、同じ関数（`scope_check.judge_unit`）で単位のファイルを分ける。
1 つのパスは上から最初に当たった分類になる。

| 順 | 条件 | 分類 | 扱い |
| --- | --- | --- | --- |
| 1 | `--scope` の前方一致 | 範囲の中 | 受け入れる |
| 2 | リファクタリング計画の起点（`plan.base_sha`）のツリーに無い | 新しいファイル | どこに置いても受け入れる。同じ実行の後のコミットが直しても新しいファイルのまま |
| 3 | 単位のどれかのコミットで消した（名前を変えた元を含む） | 範囲の外 | 受け入れ、`outside_scope` に載せてコードレビューへ引き継ぐ |
| 4 | 単位のコミットのそのファイルのハンクがすべて呼び手の書き換え | 呼び手の書き換え | 受け入れ、`review_scope_judgements` に載せて最終ゲートのレビューへ引き継ぐ |
| 5 | それ以外 | 範囲の外 | 受け入れ、`outside_scope` に載せてコードレビューへ引き継ぐ |

**範囲の外の変更で取り消さない**（#2457 受け入れ条件 8）。範囲（`--scope`）は案出しの対象を決めるのにだけ使う。
ライブラリへの統合・共通部品の切り出しなど、リファクタリングが範囲を超えるのは普通のことである。

呼び手の書き換えは `-U0` のハンクごとに 2 つの条件で見る。識別子は `[A-Za-z_][A-Za-z0-9_]*` で、言語を問わない。

| # | 条件 | 通る例 | 落ちる例 |
| --- | --- | --- | --- |
| H1 | 変えた行に「変えた名前」が 1 つ以上ある | `from pkg.a import f` → `from pkg.b import f` | `timeout = 30` → `timeout = 60` |
| H2 | 追加の行にだけ現れる識別子は、ありふれた語か、変えた名前か、同じハンクの削除の行にある | `g(1, 2)` → `g(1)` | `f(x)` → `f(x, retry=True)` |

**変えた名前**は、単位のコミットが範囲の中と新しいファイルで変えた行の識別子と、作った・消した・移したパスの語幹と
ディレクトリ名から、**ありふれた語**（起点のツリーのコードのファイルの 20% 以上かつ 3 ファイル以上に現れる語。1 実行に
1 度だけ数える）を除いたものである。修正・最終ゲート修正の単位では、その項目（最終ゲート修正なら採った全項目）の実装と
前の修正のコミットからも集める。実装が移した名前の呼び手を、修正が追従させる道を塞がないためである。

機械が通したものも正しいとは言わない。通したファイルは最終ゲートのレビューが読み、新しいファイルの項目には危険フラグ D1
が立って全体テストが 1 度走る。新しいファイルの置き場所は限らないため、生成物を新しいファイルとして作らないことは
プロンプトの「同期をしない」と公開の直前の同期で守る。

打ち消しは項目のコミットの `git revert` だけで行う（[04](04-verify-and-report.md#打ち消しは項目のコミットの-git-revert-だけ)）。同じ取り込みの打ち消しを
2 度行わない判定は、取り込みの名前と巡（`drops[].round`）の組で見る。

### 採り直し

**検証の後に実装の予算が残れば、見送った候補を採り直す**（#1743 決定 10）。駆動は検証の繰り返しの後、最終ゲートの前に
`readopt` を打つ。取り込みが残る項目 0 件で検証を飛ばしたときも打つ。

```bash
rf_eval readopt "$ID"     # 0 = 採った（TESTS_NEEDED）/ 2 = 入らない（最終ゲートへ）
```

| 項目 | 決まり |
| --- | --- |
| 残り | `実効の予算 − Σ（採っていて取り消していない項目の見積り）`。実装時間の実績は使わない |
| 候補 | `budget` で見送った候補と、持ち越しの項目だけ。ほかの理由の見送り・取り消しは採らない |
| 順序と選び方 | 計画と同じ順位で並べ、入る候補は入れ、入らない候補は飛ばして次を見る |
| 値 | 見積り・範囲テスト・グレード・`risk` は計画の時点の値。D5 は実装担当の `risk`。**LLM を呼ばない** |
| 採ったとき | 続きの ID と次の巡の番号で項目を足し（持ち越しの項目は戻し）、前の巡の手順の記録と全体テストの記録を `phases_history` / `whole_test_history` へ移して、テストの追加・実装・検証をもう 1 巡回す |
| 入らないとき | 持ち越しの項目を `not_done` で見送り、`phase` を `final` にする（最終ゲートへ移すのはここだけ） |

検証の終わりでは push しない。公開は最終ゲートへ入るときの 1 度だけで、巡ごとに CI を起動しない。叩き直したときは、
採った巡の検証がまだ終わっていなければ記録を返して採り直しを重ねない。

### 範囲の指定は検証にも効かせる

`--scope` を必須にした目的は**提案の発散と変更の肥大を防ぐ**ことなので、指定を検証へ
反映しないと目的を果たせない。実測では、編集元からアーティファクトを生成する規約に従った結果として
範囲外の 3 系統が変更され、差分が 4 倍に膨らんだ。実装担当の判断自体は
リポジトリの規約に沿っており、**規約と範囲の指定が衝突していた**のが原因である。

そこで責務を分ける。

| 誰が | 何を |
| --- | --- |
| 実装担当 | `--scope` の中と、新しいファイルと、範囲の外の既存のファイルの呼び手の書き換えだけを変更する。生成物の同期もしないし、**push もしない** |
| オーケストレーター | 検証を通した後に公開する。`--sync-command` を **push の直前**に実行する |

### 公開するのはオーケストレーターだけである

**実装担当に push させない。** 検証を通る前に変更が Pull Request へ現れると、
取り消しの反映が漏れたときにそのまま残る。オーケストレーターが push するのは、
**最終ゲートへ入る時点と、その後だけである**（検証を終えた時点か最終ゲートへ入る時点が最初の push）。
マージ処理・取り消しの途中では push しない。push の直前に、送るコミットがすべて残すコミットかを
取り消しの判定で照らす（`04-verify-and-report.md` の「公開は最終ゲートへ入る時点から」）。

生成物の同期も同じ経路に乗せる。`--sync-command` を指定すると、**push の直前**に
オーケストレーターが実行し、差分があれば**どの改善項目にも属さないコミット**として積む。

| 案 | 結果（実測） |
| --- | --- |
| 同期しない | 同期をチェックする pre-push で**あらゆる push が落ちる**。取り消しを反映できない |
| 実装担当に同期させる | 範囲外の変更になり、**採用 5 件が全件失敗**した |
| **オーケストレーターが push の直前に同期する** | 採用 |

同期コミットは作った直後に台帳（`ledger.orchestrator_commits`）へ記録し、残すコミットとして扱う
（記録しないと push の直前の照合で止まる）。同期に失敗したら**中断する**（終了コード 4）。同期できない状態を
公開すると、利用者のリポジトリのチェックを壊したまま進むことになる。

**同期の前に worktree が綺麗であることを求める。** 汚れたまま同期すると、同期が
作った差分と元からあった差分を区別できない。区別しようと `git status` の状態コードを
比べても足りず、次の 2 つを取りこぼす。

| 取りこぼし | 何が起きるか |
| --- | --- |
| 元から ` M` のファイルを同期がさらに書き換える | 状態コードが変わらず検知できない。その変更がコミットされず **push がまた落ちる** |
| 同期の前から index に staged された変更がある | `git commit` は index を丸ごと含めるため、`git add` の対象を絞っても**検証を受けない変更が公開される** |

無視されたファイルは判定に現れない。生成物やキャッシュを `.gitignore` へ入れてあれば
止まらない。制御用ディレクトリ（状態ファイル・結果・ログ）も判定から外す。

**同期が途中で失敗したら、作った差分を捨ててから中断する。** 残すと次の実行は
清浄性のチェックで必ず止まり、`pending_push` の再試行が永久に進まない。着手前が
綺麗だったことは確認済みなので、そこにある変更は全て同期が作ったものだと分かる。
無視されたファイルは消さない（`git clean` に `-x` を付けない）。

判定は**前方一致だけ**で行い、除外規則は持たない。規則を書けるようにすると、
規則を 1 行足すだけで範囲のチェックを骨抜きにできる。

そのため **`--scope` には現状固定テストの置き場所も含める**。含めないと、テストの
追加で「テストを足せ」と「範囲外を触るな」が両立しなくなり、その項目は
必ず取り消される。**`init` がこれをゲートとして見て、含まれていなければ止める**
（#436 決定 5。案内だけでは同じ失敗を繰り返し、実測では 4 回続けて同じ理由で
項目が落ちた）。**あわせて、その置き場所が範囲テストのテンプレートの `{paths}` に入ることも
同じゲートで見る**（入らないと、足したテストが検証で一度も実行されない）。

```bash
# ❌ テストの置き場所が入っていない
--scope src/services

# ✅ 直す対象とテストの置き場所を両方入れる
--scope src/services tests/services
```

### 実装担当のコミットはフックのチェックを通さなくてよい

**生成物の同期を pre-commit でチェックするリポジトリでは、そのままだとコミットを作れない。**
実装担当は範囲内だけを変更するので生成物は必ず古くなり、同期は禁じられている。

公開はオーケストレーターが検証を通してから行うため、**実装担当のコミット時点で生成物が古いのは
設計どおり**である。そこで、フックが原因でコミットできないときは
`git -c core.hooksPath=/dev/null commit ...` で**そのコミットだけ**フックを外させる。

- 禁止は `--no-verify` だけを名指しにしない。手段の名前で書き分けると、同じことが
  別の名前で起こる。実測では、同じ実装担当が適用手順ではフックを迂回し、
  修正手順では迂回せず 0 コミットで終えた
- **直した内容は必ずコミットさせる。** worktree に置いたまま終えると、検証を
  受けていない変更としてマージ処理（`merge-tests` / `merge-implement` / `merge-fix`）が捨てる

### マージ処理の前に置き土産を捨てる

マージ処理（`merge-tests` / `merge-implement` / `merge-fix`）と `verify` は、実装担当が
残した未コミットの変更を捨ててから git を読む。コミットされなかった変更はどの検証も受けておらず、公開する道が無い。

残したまま進むと、push の直前の清浄性のチェックで中断する。実測では、修正手順で
コミットを作れなかった実装担当が直しかけの差分を置いたまま終え、続く `merge-fix` が
「修正 0 件」として先へ進むこともできなくなった。

制御用ディレクトリ（状態・結果・ログ）は無視の設定で守られており、消えない。

### コミットトレーラーの形式

テストの追加・実装・修正のコミットメッセージ本文の末尾に、**git のトレーラー形式**で実行主体を残す。

```text
Refactor: extract_method — src/foo/bar.py#BarService.handle

（変更の説明）

Item-Id: I-003
Impl-Runtime: codex
Impl-Model: gpt-5.5
```

トレーラー形式にするのは
`git log --format='%(trailers:key=Impl-Model,valueonly)'` で**集計できる**ためである。
自由文で「codex が実装」と書かせると集計に使えない。プロンプトに書くだけでは守られない
ので、マージ処理が有無を検証する。**`Item-Id` は項目とコミットを結ぶ唯一の手がかり**で、
結果ファイルの申告は使わない（`Round` はラウンドが無くなったため求めない）。

**読み方は 2 つあり、見る範囲が違う。**

| 読み手 | 読み方 | 見る範囲 |
| --- | --- | --- |
| 人（集計） | `git log --format='%(trailers:key=Impl-Model,valueonly)'` | **最後の段落だけ** |
| オーケストレーター（検証） | 末尾の段落から前へ 1 段落ずつ `git interpret-trailers --parse` に掛け、記名の段落と判定しなかったところで止める | 末尾から続く記名の段落すべて |

実行環境が `Co-Authored-By:` などの帰属行を別の段落として足しても、オーケストレーターはその段落を
飛ばして前まで読むため検証は通る。人の集計は最後の段落しか読まないので、**テンプレートでは
帰属行を空行を挟まず同じ段落に続けるよう求めている**（従わなくても検証は通る）。
**1 段落目（題名）は判定に掛けない。** 掛けると `Item-Id: 本文の題名` の形の題名を記名
として読む（実測）。散文と記名の形が混ざる段落は、git が記名の段落と判定しない。

`Impl-Model` には**実際に使ったモデル名**を書かせる。既定モデルで走った場合は
`default` として報告時に区別する。

## テストの差分の判定

**テストの差分は 一次と二次の 2 回で判定する**（#443、決定 25）。リファクタリング計画の後に判断のために LLM を起動しない。

| 順 | 誰が判定するか | 何を見るか |
| --- | --- | --- |
| 1 | `verify.py`（`merge-implement` の中） | 前後が同一か。**前にあった値（文字列・数値・真偽・None）が、後のテストファイルのどこにも無ければ、期待値を戻すよう修正へ差し戻す**。コメントの中の値は数えない |
| 2 | 最終ゲートのレビュー | 一次の判定で決まらなかったもの（テストの追加・値の出現が減っただけの差分・識別子だけの差分） |

値が残っていれば、出現が減っても一次の判定では取り消さない。同じ値を定数へ寄せた差分や、
内部の関数を指す `assert` を消した差分（兆候 `test_coupled_to_internals`）がこれに当たる。
最終ゲートのレビューは、失われたものが公開インタフェースの期待値か、内部のシンボルへの参照かを見る。

一次の判定で決まらなかった差分は、項目ごとに `items[].review_test_judgements` へ記録し、
リファクタリング計画のその項目の節に「レビューで確かめるテストの差分」として載せる。**通ったものとしては
扱わない。** 読み手（単独起動なら `cross-review`、工程の 1 つなら工程表のコードレビュー）が
確かめる。

一次の判定の後に AI エージェントの判定（`judge-test-changes`）は挟まない。リファクタリング計画の
後の LLM の呼び出しを作業の CLI だけにするためである（決定 25）。変えてよい範囲の定義は
`refactoring` の `references/test-changes.md` が持つ。
