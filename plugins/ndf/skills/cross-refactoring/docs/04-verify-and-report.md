## 検証と修正

```bash
while :; do
  rf_eval verify "$ID"             # VERIFY=done|fix|judge|halt
  if [ "$(jq -r '.flaky_request.tests // [] | length' "$STATE")" != 0 ]; then   # フレーキーの直し（決定 9）
    rf_eval start-phase "$ID" flaky-fix
    "$SCRIPTS/launch-cli.sh" "$IMPL" flaky-fix "$ID"   # 監視と coding-time は fix と同じ
    rf_eval merge-flaky-fix "$ID"                      # FLAKY_FIX=kept|none|sendback|reverted。sendback なら 1 回だけ起動し直す
  fi
  case "$VERIFY" in
    judge) "$SCRIPTS/launch-cli.sh" "$JUDGE_IMPL" judge "$ID"; rf_eval judge "$ID"; continue ;;  # 成立の判定
    halt) break ;;                                                                                # 止めて人へ渡す
    fix) ;;
    *) break ;;
  esac
  rf_eval start-phase "$ID" fix     # 安全網の残りが PHASE_TIMEOUT。尽きていれば HALT=1
  "$SCRIPTS/launch-cli.sh" "$FIX_IMPL" fix "$ID"
  "$LIB/monitor.py" "$ID" --agents "$IMPL" --tmp-dir "$TMP_DIR" \
      --stem-template "{agent}-fix-rf$ID" --phase fix \
      --timeout "$PHASE_TIMEOUT" --stall-timeout "$PHASE_TIMEOUT" \
      --alive-file "$TMP_DIR/cross-refactoring-rf$ID-alive"
  rf coding-time "$ID" fix --seconds "$SECONDS_OF_THE_LAUNCH"   # 安全網へ足す。止めるのは次の start-phase（取り込みを先に打つ）
  rf merge-fix "$ID"
done
```

検証の繰り返しの後は採り直し（`readopt`。[02 の「採り直し」](02-plan-and-implement.md#採り直し)）へ進み、採ったら
テストの追加・実装・この繰り返しをもう 1 巡回す。`verify` は次の順で進む。

1. 判定を待つ項目（実装・修正を取り込んだ項目と、打ち消しの後に確かめ直す項目。`scope_verdict.pending`）ごとに、
   **HEAD で範囲テスト**（テストの種別の `scope_commands` と、項目のコミットが変えたファイルに
   かける静的解析）を走らせる。範囲テストのテンプレートの `{paths}` へは、`test_targets` の `::` より前のパスだけを、
   重なりを 1 つにまとめて渡す（`::` を受け付けるかはランナーごとに違うため）。コマンドの並びが同じ項目どうしは 1 回だけ走らせて結果を共有する。出力は
   `<TMP_DIR>/verify-<項目>.log` に残り、修正のテンプレートへ渡る。起動の失敗なら、その項目の状態を変えずに中断する
2. 落ちた項目が無ければ危険フラグを判定する（下の節）。今の巡で採った項目に危険フラグが 1 つでもあり、その巡でまだ
   走らせていなければ**全体テスト**を走らせる。直した後は落ちたテストだけを走らせ直して確かめる
3. **落ちた項目ごとに次の手を決める**（`fixloop`。#2457 決定 3・4）。**時計と回数を見ない。**
   - 落ちたテストの集合 F(n)（ID。無ければ落ちた検査の鍵、それも無ければ `<whole>`）を項目の `fix_history[]` へ積み、
     前の集合と比べる。F(n) = F(n−1) が 2 回続けば**停滞**、前に見たどれかの集合へ戻れば**振動**、それ以外は**前進**
     （回数は `limits.json` の `cross-refactoring.fix-progress`）
   - **初めて落ちた項目と、停滞か振動した項目は、成立を判定する。** 判定の担い手は参加者のうち実装担当でない者を
     ホスト → 参加者の並びで 1 者選ぶ（`assignment.choose_implementer`）。`VERIFY=judge`・`JUDGE_IMPL` を返し、駆動が担い手を
     読み取り用の作業ディレクトリ（HEAD へ同期）で起動して、`judge` が答え `{"item", "feasible", "reason", "evidence"}` を
     項目の `feasibility[]` へ積む。答えが無ければ「判定できない」として積む
   - **成立しない**と判定した項目は、その項目のコミットだけを `git revert` で打ち消す（`revert_reason: infeasible`）
   - 停滞か振動して**成立**なら、修正担当を別のランタイムへ 1 度だけ替える（`fixer`・`fixer_switched`）。替えた後も停滞か
     振動したら打ち消す（`revert_reason: stalled_after_switch`）
   - 判定の担い手が居ないとき、初回は成立と同じに続ける。判定し直しで担い手が居ない・替える修正担当が居ない・打ち消しが
     衝突したときは `VERIFY=halt` を返し、駆動が止めて人へ渡す
   - 落ちた項目が残れば `VERIFY=fix`・`FIX_IMPL`（先頭の項目の修正担当）を返す。修正は同じ修正担当の項目をまとめて 1 回起動し、
     修正の回数も対象の項目に同じだけ数える。**共有した範囲テストが落ちた項目は、共有した項目すべてを修正へ回す**
4. 全体テストが落ちたら、**落ちたテストだけ**を走らせ直して見分ける（決定 22）
   - 出力（pytest の要約の `FAILED` / `ERROR` の行）から落ちたテストの ID を取り出し、
     今の HEAD で走らせ直す。通れば**フレーキー**
   - まだ落ちるもののうち、`init` の既存失敗（`baseline_test.existing_failures`）に無い ID を**比較の木**で走らせる。
     比較の木は、今の HEAD から取り消していない改善項目と最終ゲート修正のコミットを新しい順に `git revert --no-commit` で
     外した木で、着手の後に取り込んだベースブランチの変更を含む（`comparison.py`。#2457 決定 7）。作業ディレクトリは
     動かさず、一時の detach の worktree で走らせて消す。落ちれば**既存失敗**（無関係な失敗）。比較の木を作れない
     （外すコミットが衝突する）ときは着手前の HEAD（`init` が残した SHA）で走らせ、理由を `comparison_fallback` に残す
   - フレーキーと既存失敗は取り消さず、項目の合否と停滞の判定に数えず、`whole_test` に分類して残す
   - フレーキーと見分けたテストは、その実行の中で直す（#2457 決定 9）。同じテストは 1 回の実行で 1 回だけ、実装担当へ
     `flaky-fix` の工程で依頼する（`flaky_request`。ID・ログの置き場・そのファイルだけを走らせ直すコマンドを渡す）。
     直しは `Flaky-Fix: <テストの ID>` のトレーラーを持つテストのファイルだけのコミットで、オーケストレーターが残すコミット
     として台帳に載る。項目の合否と実装時間には数えず、安全網には数える。手順の違反は 1 回だけ差し戻し
     （`FLAKY_FIX=sendback`）、直らなければ直しのコミットを `git revert` で打ち消す（`reverted`）。結果は `flaky_fixes[]`
     に残る。最終ゲートで見分けたときは、直してから確かめ直す（`FINAL_GATE=flaky`）
   - 残り（**変更起因**）があれば、**原因の項目**（その失敗を起こした改善項目）を決める（`culprit.judge`。#1649）。
     危険フラグは全体テストを走らせる理由であって、失敗の原因を指さない。候補は取り消されていないすべての改善項目で、
     修正担当の申告は使わない。決めた結果は `whole_test.culprit`（`culprits`・`basis`・`evidence`・`order`・`seconds`）に残る

     | 手がかり（`basis`） | 決め方 |
     | --- | --- |
     | `path` | 落ちたテストの JUnit の本文（`message` と本文）に、項目のコミットが変えたファイルのパスが現れる。落ちたテスト自身のファイルは数えない |
     | `isolate` | 1 で決まらない ID について、項目を新しい順に 1 件ずつ同じ worktree で `git revert --no-commit` して外し、残った ID のファイルだけを走らせ直す。通るようになった項目が原因。HEAD は動かさず、1 件ごとに `reset --hard HEAD` と `clean -fd` で戻す |
     | `undetermined` | どちらでも決まらない ID が残った（組み合わせで落ちる） |

   - 原因が決まれば（`path` / `isolate`）、原因の項目を 3 の手で修正へ回す。修正担当には落ちたテストだけを走らせ直す
     コマンドとその出力を渡し、次の `verify` は落ちたテストだけを走らせ直す。通れば残す
   - 原因が決まらない（`undetermined`）ときは取り消さず、`whole_test.resolution` を `deferred` にして最終ゲート修正へ寄せる
   - 落ちたテストの ID は suite の `junit`（JUnit XML）から読む（`file::classname::name`。絶対パスは追跡ファイルの
     末尾の一致で相対へ直す）。走らせ直すのは落ちたファイルの単位で、テンプレートの `{paths}` へ入れる
   - **JUnit を読めない**（`junit` の宣言が無い・打ち切り）ときは、`whole_test.fallback_reason` に理由を書いて
     全体を 1 度走らせ直す。通ればフレーキー（残す）。落ちれば、着手前が green なら変更起因として、走らせ直しのログに現れる
     パスだけで原因の項目を決めて直しに回す。着手前も red なら見分けられないので、取り消さずに**落ちたテストの材料**
     （ログの要約の行の ID・ログの置き場・走らせ直すコマンド。`whole_test.material`）を残して最終ゲートへ寄せる
   - **全体テストを CI に任せる戦略（`local-scoped-ci-whole`）では走らせない。** 立った危険フラグと項目を
     `whole_test.deferred` に書き、最終ゲートの 1 回へ寄せる（項目ごとに CI を回すと待ちが積み上がる）
5. 打ち消しで確かめ直す項目が残ったら 1 へ戻る
6. `phase` を `readopt` にして `VERIFY=done` を返す。**ここでは push しない**（公開は最終ゲートへ入るときの 1 度だけ）

**継続的統合では代替しない。** 検証が見るのは手元の未 push のコミットである。代替できる
のは push の後の最終ゲートだけである。

### 修正のマージ処理（`merge-fix`）

修正の起点（落ちたときの HEAD）から HEAD までのコミットを `Item-Id` で読み、修正の対象の
項目のものだけを受け取る。**手順を外れたコミットだけを差し戻す**。対象でない `Item-Id`・
トレーラーの欠け・期待値の変更があるコミットだけを `git revert` で打ち消し、項目の `sendbacks[]` に残す。手順どおりの
コミットは受け取る。範囲の外の変更は取り消さず `outside_scope` に残す。範囲と期待値は `Item-Id` ごとの単位で見て、変えた
名前はその項目の実装と前の修正のコミットからも集める（[02](02-plan-and-implement.md#範囲の判定)）。**修正の回数は数える**
（報告に出す）。往復を止めるのは前進の判定（上の 3）である。

**修正の起動が結果ファイルを残して終わり、修正の範囲にその項目の `Item-Id` のコミットが 1 つも無い項目は、
直さなかった項目として `unfixed`（修正の起動の番号）を付け、`failing` のまま残す。** 落ちたテストの集合が変わらないため、
次の `verify` が停滞として数えて判定し直しへ回す。結果の申告（`fixed` / `not_fixed`）は読まない。結果を残さずに終わった
起動は振り替えの経路で扱い、数えない。修正の所要は `start-phase fix` からの時計で測り、配分テーブルの `fix` に使う。

**マージ処理を済ませていない修正があるまま `verify` を呼ぶと、先にマージ処理を行う。** 修正の後に落ちて
再開したとき、修正のコミットが項目に結ばれないまま HEAD に残るのを防ぐ。

### 危険フラグ

| 危険フラグ | 条件 | 見るもの |
| --- | --- | --- |
| D1 | 項目のコミットが、項目の `path` と `tests` 以外のファイルを触った | `git show --name-only` |
| D2 | ファイルを消した・名前を変えた | `git diff-tree --name-status -M` の `D` / `R` |
| D3 | 触ったプロダクションコードのファイルが `--scope` の外のコードから参照されている | `git grep -lE`（下の注） |
| D4 | 範囲テストが触ったプロダクションコードのファイルを覆うと示せない | 範囲テストのファイルに、拡張子を除いたファイル名と `symbol` の名前のどちらも現れない |
| D5 | 公開の入出力が変わりうる | Jev（確信度 0.7 以上で真）。使えなければ実装担当の `risk` |

- **D3** は `--scope` の外の**コードのファイルだけ**を、モジュールの参照の形で探す。探す語は
  触ったファイルの末尾の 2 区切り（`refactor_lib/plan.py` なら `refactor_lib/plan`・
  `refactor_lib\.plan`・`refactor_lib\\plan`（PHP の名前空間）・`refactor_lib::plan`（Rust のパス）・
  `refactor_lib import .*\bplan\b`）と、修飾名の `symbol` の全体である。言語の表は持たない。
  直下のファイルは行頭の `import <語幹>` / `from <語幹>`。パッケージのエントリポイント（`__init__.py` /
  `index.*` / `mod.rs` など）は探さずに立てる。**当たらないときは立てない**。動的な読み込みの
  見落としは残る危険として受け入れ、最終ゲートが拾う（決定 20）
- **D4** の「範囲テストのファイル」は、`test_targets` から組み立てた項目では対象のパス、
  ラウンドテストをそのまま使う項目では `--scope` のテストの置き場所の配下の追跡されたファイルである。
  コマンドの語からは読まない（`docker compose exec -T app ...` の `app` を起点と読み違えるため）。
  置き場所に追跡ファイルが無いときは示せないので立てる（決定 21）
- **D5 の `risk` は危険フラグを立てる側にだけ使う。** 申告で検証を減らさない
- **D5 はリファクタリング計画の手順で問い、検証は `items[].public_io` を読むだけである**（決定 25）。Jev へ送るのは
  提案のフィールド（手法・理由・手順）だけで、差分の本文・ファイルの本文・テストの出力は送らない
- 危険フラグは項目ごとに `items[].danger`、全体として走らせた理由は `whole_test.flags` に残る

### 打ち消しは項目のコミットの git revert だけ

**改善項目の打ち消しは、その項目のコミット（テスト・実装・修正）を新しい順に `git revert` する**（`undo.revert_items`。#2457 決定 6）。
公開の前でも後でも同じ手順である。`reset --hard` で未公開のコミットを外す経路と、起点の木へ戻すコミットを積む経路は無い。
どの記録にも無いコミット（取り込んだベースブランチのマージなど）には触れないため、着手の後に取り込んだベースブランチの
変更は消えない。複数の項目を打ち消すときは新しい項目から打ち消す。

| 打ち消すもの | 経路 | 理由 |
| --- | --- | --- |
| 成立しないと判定した項目 | `revert_items`（`verify`） | `infeasible` |
| 修正担当を替えた後も停滞か振動した項目 | `revert_items`（`verify`） | `stalled_after_switch` |
| どの項目にも属さないコミット（計画に無い `Item-Id` など） | `revert_unattributed`（取り込み） | 差し戻し |
| 修正の手順を外れたコミット | `fix_intake`（`merge-fix`） | 差し戻し |

**打ち消しが衝突したら、打ち消しの前の HEAD へ戻して止まる**（`UndoConflict`。I9）。衝突した項目を外して続けない。
`verify` は `VERIFY=halt` を返し、駆動が `gate`・終了コード 10 で人へ渡す。

打ち消したコミット（revert）はオーケストレーターが残すコミットとして台帳（`ledger.orchestrator_commits`）へ記録する。
打ち消した項目のコミットは revert と一緒に履歴に残り、公開してよいコミットとして扱う（`reverted_by_commit`）。
記録は `drops[]`（`mode: revert`・`reason`・`round`・`dropped`・`reverted`・`before`・`recheck`）に残る。

**残すかは範囲テストで決める。** 最終ゲートより前の打ち消しで HEAD が変わったら、残った `verified` の項目を `implemented`
へ戻し（確かめ直し。`drops[].recheck`）、検証が新しい HEAD の範囲テストで判定し直す。最終ゲートの中の打ち消しでは、
最終ゲートが HEAD を確かめ直すため戻さない。

どの項目にも記録されていないコミットを消す `undo.discard_range`（結果を残さなかった起動の範囲を閉じる）だけは、未公開の範囲を
積み直しの起点へ戻して残すコミットを積み直す。

### 公開は最終ゲートへ入る時点から

**最終ゲートより前には push しない。** 取り消し・マージ処理・結果なしの起動を閉じる処理は push を伴わない。
最初の push は最終ゲートのエントリポイント（`final-gate`）で行う（`publish.enter_final_gate`）。採り直す巡ごとには push しない。最終ゲートの後の push（`recheck`・`merge-final-fix`・結果なしの最終ゲート修正を閉じた後）は
最終ゲートが push 済みの地点を判定するために残す。最終ゲートへ入る前（`phase` が `final` / `done` でない）に公開のエントリポイントが
呼ばれたら、呼び出し元の誤りとして終了コード 4 で止まる。

**push の直前に、送るコミット（origin の head から HEAD まで）がすべて残すコミットかを照らす**（`ledger.unpublishable`）。
見放した担当の残留コミットのように記録に無いコミットがあれば、push せずに終了コード 4 で止まり、そのコミットの SHA・
`Item-Id`・件名を 1 行ずつ出す。残すかは状態ファイルに記録した SHA の一致だけで決め、担当が書けるトレーラーでは決めない。
同期とリファクタリング計画の記録のコミットは、作った直後に台帳（`ledger.orchestrator_commits`）へ記録する。

**公開の結果は状態ファイルの `publication` に残す。** push が通れば `pushed` と SHA、同期・ツールのパスの照合・残すコミットの
照合・`git push` のどれかで止まれば `refused` と理由（認証情報を伏せ、末尾の 5 行・500 字に縮めたもの。伏せ字は共通ライブラリの
`scripts/lib/secret_redact.py`）を残してから終了コード 4 で止まる。`publication` は次の push の照合の起点
（`ledger.published_sha`）とは別に持つ。

**最終ゲートを経ずに終わった実行は、残った改善項目を「採用」と表さない。** `refactor.py report` は「採用: 未確定」と書き、
drive は `stopped`（`metrics.exit` に最終ゲートの終了コード・`metrics.adopted` は 0・`metrics.unconfirmed` に残った項目の数）で終える。
項目の表示の状態と件数は `ledger.display_status`・`ledger.tally` の 1 か所で決め、リファクタリング計画のコメント・結果 JSON・
報告が同じものを使う。

| 項目の `status` | 最終ゲートが `passed` | 表示の状態 |
| --- | --- | --- |
| `reverted` | どちらでも | 取り消し |
| `deferred` | どちらでも | 見送り |
| `verified` | 通った | 採用 |
| `planned` / `tested` / `implemented` / `failing` / `verified` | 通っていない | 未確認 |
| `planned` / `tested` / `implemented` / `failing` | 通った | 未着手・テストを追加済み・検証中・修正中 |

持ち越し（`carried`）は採り直しの判定の前だけの状態で、採り直しに入らなければ `deferred`（`not_done`）になる。

## 最終ゲート

```bash
"$SCRIPTS/refactor.py" final-gate "$ID"   # FINAL_GATE=... を返す
```

| 全体テストの置き場（戦略） | 最終ゲート | 検証の中の全体テストとの関係 |
| --- | --- | --- |
| CI（`local-scoped-ci-whole`、または `--ci-check`） | push 済みの HEAD のチェック（`--ci-check` → 宣言の `test.ci.check` → `ci.required_checks` のすべて）を `limits.ci_wait_timeout`（`3·c`）まで待つ | 打ち消した後の HEAD も継続的統合が確かめる |
| 手元・工程の 1 つ | 全体テスト（戦略のテストの種別の suite の `command`） | **検証の中で走って通り（取り消しが無く）、その後に HEAD が 1 つも進んでいなければ走らせずに通す** |
| 手元・単独 | 全体テストを 1 度 → 通れば `cross-review` | 同上（使い回せれば走らせない） |

生成物の同期のコミットが積まれていれば HEAD は進んでいるので走らせる。**木が起点と同じでも確かめを省かない**（I11）。最終ゲートの
全体テストの所要は `final_gate.whole_test_seconds` に残り、履歴の `whole_test.final` になる。

**落ちたら見分ける。** 手元なら suite の `junit`、CI なら落ちたチェックの run の成果物（`test.ci.junit_artifacts` の glob、
無ければ解析と同じ名前の規則）の JUnit から落ちた ID を読み、検証の中と同じくフレーキー・既存失敗・変更起因に分ける
（`final_gate.triage`）。**変更起因が無ければ通す**（既存失敗とフレーキーだけ）。変更起因があれば最終ゲート修正へ回す。
落ちたときは**落ちたテストの材料**（`final_gate.material`。ID は JUnit から、読めなければ手元のログの要約の行から取り、
ログの置き場は手元のログか CI の run の URL、走らせ直すコマンドは見分けのものか全体テスト）を組み、最終ゲート修正の依頼
（`final_gate.fix_request`）に載せる。JUnit を読めないときも材料は渡る（受け入れ条件 13）。

**静的解析の全体テストは、どの戦略でも、使い回しがあっても手元で走らせる**（記録は `final_gate.checks[]` の
`mode: lint` と `final_gate.lint`）。落ちた suite は着手前の suite ごとの成否（`baseline_test.suites`）で分ける。

| 着手前 | suite の `scope_command` | 判定 |
| --- | --- | --- |
| green | — | 変更起因。最終ゲート修正へ回す |
| red | ある | 着手前の HEAD からの変更したファイルに絞った範囲テストが通れば既存失敗、落ちれば変更起因 |
| red | 無い | 既存失敗として判定から外し、報告に「着手前から落ちていたため判定から外した」と出す |

テストか静的解析のコマンドを起動できなければ、最終ゲートは判定せずに中断（終了コード 4）し、`launch_failure` を残す。

| 終了コード | 意味 | 進行 |
| --- | --- | --- |
| 0 | 通過した（`FINAL_GATE=cross-review` なら続けて `cross-review` を実行する） | 次へ |
| 2 | 落ちた（`FINAL_GATE=failing`）か、止めて人へ渡す（`FINAL_GATE=halt`・`HALT_REASON`） | 最終ゲート修正を回す。`halt` なら駆動が `gate`・終了コード 10 で止まる |
| 4 | 判断できない（CI が上限までに終わらない・照会できない・待つチェックの名前が無い・テストのコマンドの起動の失敗） | 待った秒か起動できなかったコマンドと理由を出して止まる |

**CI と手元は排他である。** CI で見る実行は手元のテストの種別の全体テストを実行せず継続的統合の結論だけで判定し、手元で見る実行は
手元のテストだけで判定する（静的解析はどちらでも手元で走らせる）。**採った側が失敗した・結果を得られないときは通過させない**（fail-closed）。

- 読むのは `check-runs` だけ。**`status` は使わない**（GitHub Actions は
  チェックジョブを記録し commit の状態を記録しないため、常に `pending` を返す）。`pending` の間は
  `lib/waits.py` の `wait_until` で間隔を伸ばしながら待つ
- 同名のチェックは名前ごとの最新の実行（`completed_at` と `started_at` の新しい方）で判定する。
  別の実行で成功したチェックの、前の実行の失敗は数えない（畳み方は共通ライブラリの `gh_parts` が持つ）
- 名前が一致するチェックが 1 件も無いときも通過させない。**別のチェックの成功で通さない**
- **「どちらか一方が通れば通過」とはしない。** OR で採ると、手元のテストの失敗を
  継続的統合の成功が覆す

**最終ゲート修正は時間で打ち切らない**。落ちたテストの集合（変更起因の ID と変更起因の静的解析の
suite。無ければ `<whole>`）を `final_gate.fix_history[]` へ積み、検証の中と同じ前進の判定を当てる。前進する限り続け、
停滞か振動したら修正担当を別のランタイムへ 1 度だけ替える（`final_gate.fixer_switched`）。替えた後も停滞か振動した・替える
修正担当が居ない・起動し直しても解けない起動結果（利用上限で振り替え先も無い）のときは、最終ゲートの失敗は打ち消す項目を
決められないため、**取り消さずに**止めて人へ渡す（`final_gate.status: halted`・`FINAL_GATE=halt`・`state.halt`）。
起動のされ方（単独か工程の 1 つか）で扱いは変わらない。

### 最終ゲート修正は項目の修正と別物である

```bash
rf_eval start-phase "$ID" final-fix                        # PHASE_TIMEOUT = 安全網の残り
"$SCRIPTS/launch-cli.sh" "$FINAL_FIX_IMPL" final-fix "$ID"   # 担当は final-gate が返す
"$LIB/monitor.py" "$ID" --agents "$FINAL_FIX_IMPL" --tmp-dir "$TMP_DIR" \
    --stem-template "{agent}-final-fix" --phase final-fix \
    --timeout "$PHASE_TIMEOUT" --stall-timeout "$PHASE_TIMEOUT"
"$SCRIPTS/refactor.py" merge-final-fix "$ID"                 # 2 = 結果なし / 範囲が確定しない / 公開前の静的解析で差し戻した
```

**最終ゲート修正は push の前に、変えたファイルで静的解析を通す。** 落ちたら修正の範囲を取り消し、push せずに
`FINAL_FIX=lint_rejected` と終了コード 2 で最終ゲートへ戻す。次の最終ゲートは違反を修正の依頼に載せて差し戻す。

**`fix` 手順と `merge-fix` は使い回せない。** どちらも落ちた項目の記録を読み、
`Item-Id` で修正を項目へ結ぶ。最終ゲートが直すのは**全体テストの失敗**で、どの項目にも
属さない。流用すると、`Item-Id` の無い修正が全件不正として取り消される。

そのため `final-gate` は落ちるときに**担当と範囲の起点を記録して返す**。

| 返す値 | 何に使うか |
| --- | --- |
| `FINAL_GATE=failing` | 最終ゲート修正へ入ることを示す |
| `FINAL_GATE=halt` | 修正担当を替えた後も停滞した・起動し直しても解けない起動結果だった。取り消さずに止め、駆動が人へ渡す |
| `FINAL_FIX_IMPL` | 修正を起動する担当。**実装担当**（輪番は無い） |
| `FINAL_FIX_ROUND` | 何回目の修正か |

起点（`final_gate.fix_base_sha`）は落ちた時点の HEAD である。`merge-final-fix` は
その範囲だけを見る。

**求めるトレーラーは 2 つである**（`Impl-Runtime` / `Impl-Model`）。`Item-Id` は
書かせない。実在しない番号を実装担当が作ることになるためである。

**コミットごとのテストの合否は見ない。** CI で見る実行では手元の
テストを 1 度も走らせないと決めてあるので、ここでコミットごとに走らせるとその排他を
この経路だけが破る。合否は直後の `final-gate` が採った側で 1 度だけ見る。

**申告から漏れたコミットは、この修正の範囲を取り消して差し戻す**（検証を受けていない修正コミットだからである）。
範囲の外の変更は取り消さず報告とコードレビューへ引き継ぐ。範囲は修正の全コミットを 1 つの単位として見て、変えた名前は
採った全項目の実装・修正と前の最終ゲート修正のコミットからも集める。

**修正担当が結果を残さなかったときも同じ手順を通る。** 取り消して起点を取り消し後の
先端へ進め、最終ゲートの記録の `failed_attempts[]` へ 1 件（工程 `final-fix`）を残し、
終了コード 2 で最終ゲートへ判定を戻す。取り消さずに抜けると、次の最終ゲートがその
コミットを含む先端でテストし、落ちれば起点をそこへ置き直すため、未検証の差分が
Pull Request に残る。**修正の回数はここでは進めない。** 進めるのは次の最終ゲート
である。取り込みの前に駆動が `reassign "$ID" final-fix` を打ち、振り替え先があれば `final_gate.impl` と実装担当を
替えて次の修正ラウンドから振り替え先が直す（取り込みは結果を残さなかった元の担当の試行として閉じる）。**振り替え先が
無いときだけ打ち切りのフラグ（`no_relaunch`）を立てる**。次の最終ゲートは、テストが落ちれば取り消さずに止めて人へ渡す
（`FINAL_GATE=halt`）。

### テストで見つからない誤りは誰が拾うか

検証をテストで行い、最終ゲートの `cross-review` を条件付きで省くと、実行の流れからレビューが
2 か所とも消えうる。**答えは起動のされ方で分かれる。**

| 起動のされ方 | 誰が拾うか |
| --- | --- |
| 単独 | **最終ゲートの `cross-review`。** 省略しない |
| `development-workflow` の 1 工程 | **工程表の「コードレビュー」。** この Skill の後に `pr` → `cross-review` が続く |

**この Skill の中へ軽量なレビューを足さない。** 工程として起動したときに `cross-review` を
省くのは、**同じ差分を 2 度レビューしないため**である。v10.5.1 で `light` も
`cross-review` を通すと決めたため、モードによらずレビューは必ず 1 度掛かる。

### 単独起動の終わり

**`FINAL_GATE=cross-review` のときは `/ndf:cross-review <PR>` で Pull Request 全体を承認収束に
かける。** 項目の妥当性は範囲テストで判定済みのため、**項目をまたいだ整合**を見させる。

```bash
/ndf:cross-review "$PR" --focus "項目をまたいだ整合を見る。個々の改善項目の妥当性は範囲テストで判定済みのため対象外とする。複数の項目で触った箇所の重複・打ち消し・命名の揺れ、取り消した項目の残骸、生成物とリリース対象の同期を確かめる"
```

**cross-review が終わったら、その最終ステータスを渡して `finalize` を呼ぶ。** 最終ステータスは
`scripts/lib/loop_drive.py` の `review_status` だけが cross-review の状態ファイルから決め、cross-review の駆動が
結果の `metrics.review_status` に載せる。`finalize` は `approved` のときだけ配分の履歴へ 1 行を足す。

`drive.py` はこの地点で `pause: cross-review` を返して止まる。`items[0].command` は cross-review の駆動に
`--result-file <回答ファイル>` を付けたもので、`items[0].cwd`（対象のリポジトリの根）で打つ。駆動が ok で終わると、
その最終ステータスを回答ファイル（`items[0].result_file`）へ `{"review_status": "<値>"}` として書く（LLM は書かない）。打ち直すと
`finalize <ID> --review-status <値>` を呼んで終わる。Draft を解除するのは、結果 JSON の `metrics.review_status` が
`approved` のときだけである。

## 配分テーブル

**配分テーブルは保存しない。** リファクタリング計画のたびに、利用者の手元の履歴から集計する（決定 7）。

- 履歴の置き場所: `<metrics>/<owner>--<repo>/cross-refactoring-allocation.jsonl`。
  根は実行の要約と同じ（`NDF_METRICS_DIR` → `$XDG_STATE_HOME/ndf/metrics` →
  `~/.claude/ndf/state/metrics`）。`NDF_METRICS=0` でも書く（リファクタリング計画の材料として扱い、計測の設定に従わない）
- 行は 2 種類ある（`kind`）。実行の行（`run`）は 1 実行 = 1 行で、**最終ゲートが通った実行だけ**を `report` が追記する
  （単独起動は `cross-review` が `approved` のときだけ）。中断した実行と、最終ゲートが通らなかった実行は追記しない。
  着手前のテストの行（`init_test`）は `init` が着手前のテストの後に、最終ゲートの成否と打ち切りを問わず 1 行足す。
  項目の行（`item`）は改善項目を採った実行が、**終わり方（最終ゲートの通過 `final_gate`・安全網や打ち消しの衝突で止めた
  `safety_net`・中断 `aborted`）を問わず**、採った項目ごとに 1 行足す（`item_actuals.append_item_rows`。#2457 決定 10）。項目の
  内容（`item_id`・`target`・`technique`・`tier`）・選定に使った見積り（`estimate_minutes` の `test` / `implement`）・
  実装時間の実績（`coding_seconds` の `test` / `implement` / `fix`。修正は起動の秒を対象の項目の数で等分）・表示の状態・
  終わり方・予算（`budget_minutes` / `effective_budget_minutes`）を持つ。配分テーブルの集計は実行の行だけを読み、
  着手前のテストの行と項目の行を入れない
- 実行の行の `whole_test.init` は着手前に全体テストを走らせたときだけ秒を持つ（範囲テストだけなら `null`）。
  `kind` を持たない旧い行は実行の行として読む
- 旧い実行の行の `reserve`・`paused_seconds` は読めるまま残し、配分テーブルの集計に使わない。手順ごとの秒（`phases`）と
  `whole_test.danger` は採り直しの巡の分を足した値
- `elapsed_seconds` は開始から終わりまでの壁時計で、止まっていた時間を含む

| 種類 | 1 件あたりの値 | 足りないときの代わり |
| --- | --- | --- |
| `test` | その種類を含む直近 10 行の Σ秒 ÷ Σ件数 | 初期値 |
| `structure/<手法>` | 同上 | `structure/*` をまとめた値 → 初期値 |
| `verify` | 直近 10 行の Σ秒 ÷ Σ検証した改善項目 | 初期値 |
| `fix` | 直近 10 行の Σ秒 ÷ Σ起動 | 初期値 |

初期値は `data/allocation-defaults.json` にあり、出所（#917 の記録の URL）と式を持つ。
**担当の申告ではなく適用の CLI の実測の秒を件数で割った値**である（決定 9）。履歴が
無い・読めないときは初期値でリファクタリング計画し、1 行知らせる（`plan.table_source` が `defaults`）。

## 報告

```bash
"$SCRIPTS/refactor.py" report "$ID"            # --metrics で種類別の件数と所要も出す
```

報告は手順別の所要・実装の予算と延長・安全網の累計と上限・所要（`cross-review` を除く）・改善項目の表・
採用・未確認・取り消し・見送りの件数（リファクタリング計画のコメントと結果 JSON の `metrics` と同じ集計。見送りは見送った改善項目と、時間で見送り項目に入っていない候補の数。後者が 1 件以上なら `見送り N（うち時間 M）`）と
見送った提案の総数と理由別の件数（件数の行と別の行）・着手前の全体テストの結果（基準。
リファクタリング計画にも載る）・検証の中の全体テストと落ちたときの見分けとその結果・Jev の使用・
最終ゲートの結果・指標の測定（言語・ツール・版・ランナー・所要秒と、測れなかった言語と理由の識別子）を持つ。
指標の測定の表はリファクタリング計画と同じ行である（組み立ては `codemetrics_view.record_lines` の 1 か所）。
最後の行に実行の要約の置き場所を出す。

判定と止まりの行は次のとおりである（どれも無ければ出さない）。

| 行 | 中身 |
| --- | --- |
| 判定・判定し直し | 項目ごとの担い手・成立 / 成立しない / 判定できない・理由 |
| 修正担当の替え | 停滞か振動で替えた項目と替えた先 |
| 打ち消し | 打ち消した項目と理由（`infeasible` / `stalled_after_switch`） |
| 差し戻し | 項目ごとの種類と理由 |
| 範囲の外で変えたファイル | 項目ごとのパス（コードレビューへ引き継ぐ） |
| 止めた理由 | 安全網・打ち消しの衝突・判定の担い手が居ない・最終ゲート修正の停滞 |
| 採り直し | 回数・件数・項目、最後の判定の実装の予算の残り、採らずに残った `budget` の候補の数 |

### リファクタリング計画は Pull Request のコメントに残す

**なぜ直すのか（理由）とどう直すのか（手順）は、提案の時点でしか残らない。**
状態ファイルには入っているが、そのディレクトリは差分から除外されるため、
Pull Request を読む側からは見えない。

**リファクタリング計画は実行の記録であり、リポジトリの知識には含めない**。既定の
置き場所は**対象の Pull Request のコメント 1 件**で、結果の出口のたびに**同じ
コメントを編集する**。

| 置き場所 | URL の安定 | 差分に混ざるか | 更新の手数 |
| --- | --- | --- | --- |
| **Pull Request のコメント 1 件**（既定） | **永続** | 混ざらない | 編集 1 回 |
| ファイル（`--plan-file`） | `<ref>` に依存。ブランチが消えると切れる | **混ざる** | コミットと push |

- 内容は**状態から決まる**。同じ状態からは同じ本文が出る（コメントの公開の行と書き直した時刻を除く）
- 冒頭に 3 行を置く。件数の行（採用・未確認・取り消し・見送りと最終ゲートの状態。結果 JSON の `metrics` と同じ集計）、
  公開の行（push した SHA・push できなかった理由と未公開の改善項目があるか・`--scan-reverts` で読んだ origin の地点）、
  書き直した時刻である。ファイル（`--plan-file`）へ書く本文は件数の行だけを持つ
- **書き直すのは `refactor.py plan-comment` だけである。** 駆動が done・中断・最終ゲートの止まりの各出口で 1 度ずつ打つ。
  push の後には書かない。リファクタリング計画ができる前に止まった実行では作らない
- **プランの外の取り消しの後は `refactor.py plan-comment <PR> --scan-reverts` を打つ。** origin の head ブランチの
  `plan.base_sha` から先端までの `This reverts commit <SHA>` を古い順に読み、実装コミットが取り消されたままの項目を
  取り消しにする（取り消す前の状態を項目の `outside_revert` に残す）。取り消しが取り消された項目は `outside_revert` から
  元の状態へ戻す。スクリプトが取り消した項目は戻さない。origin を取り込めなければ終了コード 4 で、状態もコメントも変えない
- **見送った提案と取り消した項目の内訳を持つのはリファクタリング計画だけである。** 他の文章は件数だけ述べる。見送りは理由（8 つ）と補足を、取り消した項目は「取り消した理由」を持つ
- 本文の先頭に目印（`<!-- cross-refactoring plan rf<ID> -->`）を置く。状態ファイルの
  記録が失われても、目印で同じコメントを引き当てられる。**引き当てられないと、
  公開のたびに新しいコメントが積まれる**
- **投稿に失敗しても進行は止めない。** 記録が残らないことと、変更が検証を通って
  いないことは別である。失敗したことは出力に残り、駆動の結果 JSON と終了コードは変わらない
- `gh api` は 1 つの出口につき、コメントの ID を持っていれば編集 1 回、無ければ検索 1 回と作成か編集 1 回である

**`--plan-file` は残す。** 明示したときだけファイルにする。この経路では公開を
生成物の同期と**同じコミット**に乗せる（分けるとオーケストレーターのコミットが公開のたびに
2 つずつ積まれる）。空文字を渡すと記録しない。

**絶対パスと親へ抜ける経路は受け取った時点で拒む**（終了コード 4）。オーケストレーターは利用者の
リポジトリを触るため、作業ディレクトリの外へ書き出す余地を残さない。あわせて
`./issues/plan.md` のような表記も正規化する。git が返すパスと形が違うと、公開の
コミットメッセージが取り違えられる。

### 報告も外へ出す文章である

| 規約 | 報告での書き方 |
| --- | --- |
| 項目の指し方 | 改善項目の表は **`<ファイル>#<シンボル>`** を持つ（項目 ID だけでは何を直したか分からない） |
| 取り消した項目・見送った提案 | **件数だけ**述べる。内訳はリファクタリング計画にある |
| リファクタリング計画 | **生の URL**を見出しの直後と見送りの節へ入れる |
