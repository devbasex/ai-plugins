# 検証の失敗の修正（cross-refactoring / $RF_RUNTIME）

あなたは **$RF_RUNTIME**（モデル: $RF_MODEL）として、**範囲テスト（または危険フラグで
走らせた全体テストのうち変更起因で落ちたテスト）が落ちた項目を直します**。同じテストのコマンドを共有した項目は、どの項目が落としたかまでは
分かっていません。まとめて 1 つの修正の対象です。

## 必須コンテキスト

- リポジトリ: $RF_REPO / Pull Request #$RF_PR
- 作業ディレクトリ: `$RF_WORKDIR`（**ここでだけ作業する**）
- ブランチ: `$RF_HEAD_BRANCH`

## 手順書

$RF_SKILL_BLOCK

## 直す項目

```json
$RF_ITEMS
```

- `test_command` が落ちたコマンド、`test_log` がオーケストレーターで走らせたときの出力です
- `failed_check` があれば、落ちた検査です。`kind`（`lint` = 静的解析 / `test` = テスト）・`suite`・`command`・
  `files`（違反の出たファイル）・`tests`（落ちたテストの ID）を読み、まずそこを直します。`by_item` があれば、
  この項目のファイルが別の項目（`by_item`）の範囲テストを落としています
- `fix_count` はこれまでの修正の回数です。回数の上限はありません。落ちたテストが減るか別のテストへ移る限り、
  修正は続きます。**落ちたテストが前の回と同じままか前に見た組へ戻ると**、別のランタイムが成立を判定し直し、
  修正担当が替わるか、その項目が打ち消されます

## やること

1. `test_log` を読み、`test_command` を実行して**どのテストがなぜ落ちているか**を読む
2. **振る舞いを元へ戻す方向で**直す。テストの側を書き換えて通すのではありません
   （**テストを緩めた時点で、振る舞い不変を示す手段が消えます**）
3. 直してから `test_command` をもう 1 回実行し、**項目ごとにコミットする**（その項目の `Item-Id` を付ける。
   分けたほうが読みやすければ複数のコミットでもよい）。構造検査（ファイルの行数など）で落ちたときは、
   範囲の外の新しいモジュールへ分けて直してよい

**振る舞いを変えないと直せない**と判断したときは、直さずに終え、結果ファイルの `reason` に成立しない理由を
書いてください。オーケストレーターが別のランタイムに成立を判定させ、成立しないと判定した項目だけを打ち消します。

## コミットの規約

```text
Fix: 検証の失敗を直す — src/foo/bar.py#BarService.handle

（何をどう直したか）

Item-Id: I-002
Impl-Runtime: $RF_RUNTIME
Impl-Model: $RF_MODEL
```

- `Item-Id` は**上の直す項目のどれか**。それ以外の `Item-Id`・トレーラーの欠け・期待値の変更があると、
  **そのコミットだけ**が打ち消され、次の修正へ差し戻されます
- **3 つのトレーラーはメッセージの最後の段落に置く**

## 作業の進み具合を残す

**作業段階が進むたびに `$RF_STEM-progress.log` へ 1 行追記してください**
（`start` / `edit` / `test` / `commit` / `done`）。

## 守ること

- **push しない。** 公開するのはオーケストレーターだけで、**検証を通した後**に行います
- **`git push --force` と `--no-verify` を使わない**
- コミット時のフックが生成物の同期を求めても同期しない。フックが原因でコミットできない
  ときは `git -c core.hooksPath=/dev/null commit ...` で**そのコミットだけ**フックを外す
- 直した内容は必ずコミットする。worktree に置いたままの変更は捨てられます
- 作業ディレクトリの外を変更しない
- **新しいファイルは置き場所を問わず作ってよい**（分割・クラスの抽出・共通モデルの抽出の行き先。対象範囲の外の
  ディレクトリでもよい）。ただし生成物・リリース対象は作らない
- **直すのに要るなら対象範囲（`$RF_SCOPE`）の外のファイルも変えてよい。** 範囲の外で変えたファイルは報告に載り、
  コードレビューへ引き継がれます
- 生成物・リリース対象の同期をしない
- 上の新しいファイル・呼び手の書き換えと、それに伴う読み込みの書き換えは直す手順の中である。
  失敗と関係の無い箇所を「ついでに」直さない
- **テストの期待値を緩めて通さない**

## 提出形式

結果を **`$RF_STEM-result.json`** に書いてください。**オーケストレーターは git だけを見ます。**

```json
{"items": [{"item_id": "I-002", "status": "fixed"}]}
```
