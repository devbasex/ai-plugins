# リファクタリング提案（cross-refactoring / $RF_RUNTIME / 提案ラウンド $RF_ROUND）

あなたは **$RF_RUNTIME**（モデル: $RF_MODEL）として、下記の範囲から
**構造改善すべき箇所を提案**します。この段階では**コードを 1 行も変更しません**。

## 必須コンテキスト

- リポジトリ: $RF_REPO / Pull Request #$RF_PR
- 作業ディレクトリ: `$RF_WORKDIR`（**ここから外は読まない・書かない**）
- 対象範囲: `$RF_SCOPE`（**この範囲の外は提案しない**）
- 着手前のテスト: `$RF_BASELINE_TEST`
- 採用上限: 3 者の提案を統合したうえで、**合計 $RF_MAX_ITEMS 件までが採用**されます

## 手順書

$RF_SKILL_BLOCK

## 対象外（過去に見送った提案）

同じ提案を繰り返さないでください。

$RF_EXCLUDED

## 語彙（この値だけを使う）

`smell` と `technique` には**下の識別子をそのまま**書いてください。日本語の説明は
意味の対応を示すためのもので、**出力に日本語を書くと語彙外**として扱われ、
自動的に最低の重要度へ降格し、しきい値で落ちます。

### `smell` に書ける値

$RF_VOCAB_SMELLS

### `technique` に書ける値

$RF_VOCAB_TECHNIQUES

### `severity` に書ける値

$RF_VOCAB_SEVERITIES

## やること

1. 対象範囲のコードを読み、**調べる価値がある兆候**を探す
2. 気づいた箇所ごとに、兆候の語彙のどれに当たるかと、対応する手法を決める
3. その手法で**どう直すか**を、順序のある手順として書く
4. 対象にテストがあるかを確かめ、乏しければ `test_gap` を真にする
5. 変更行数を見積もる（追加 + 削除。**楽観側へ倒さない**）。抽出する手法では、
   抽出した本体だけでなく**呼び出し側の書き換え・import の追加・引数の受け渡し**も
   数える。`test_gap` を真にしたなら、**先に足す現状固定テスト**も見積に含める

多く出すことより、**採れる提案だけを出す**ことを優先してください。上限を超えた分は
その場で見送られ、以後は「対象外」として扱われます。
1 件も見つからなければ空の配列で構いません。無理に絞り出さないでください。

## 提出形式

結果を **`$RF_STEM-result.json`** に次の形で書いてください。

```json
{
  "items": [
    {
      "path": "src/foo/bar.py",
      "symbol": "BarService.handle",
      "smell": "long_method",
      "technique": "extract_method",
      "severity": "major",
      "rationale": "1 メソッドに入力検証・変換・永続化が同居し、分岐が 7 本ある",
      "plan": "1. 検証部を validate_request として抽出\n2. 変換部を to_entity として抽出",
      "test_gap": false,
      "estimated_diff_lines": 40
    }
  ]
}
```

- `path` はリポジトリ相対、`symbol` は関数・メソッド・クラスの名前
- `smell` / `technique` / `severity` は**上に列挙した識別子のいずれか**。
  列挙にない値（日本語を含む）は自動で最低の重要度へ降格され、しきい値で落ちます
- `path` + `symbol` + `smell` が同じ提案は 1 件へ統合されます。**他のランタイムと
  合意した提案ほど優先される**ので、独自性を狙わず素直に挙げてください

## 守ること

- **コードを変更しない。** この段階は提案だけです
- 作業ディレクトリの外を触らない
- 機能追加・不具合修正は提案しない（**振る舞いを変えない改善だけ**が対象）
