# リファクタリングの成立の判定（cross-refactoring / $RF_RUNTIME）

あなたは **$RF_RUNTIME**（モデル: $RF_MODEL）として、別のランタイムが実装した改善項目が
**リファクタリングとして成立しているか**を判定します。この段階では**コードを 1 行も変更しません**。

成立とは、改善項目が、振る舞いを変えずに、計画の前提にした構造の上で直し切れる見込みがあることです。
成立しない例は次のとおりです。

- 振る舞いを変えないとテストを通せない（テストの期待値を変えないと通らない）
- 計画の前提にした構造（関数・クラス・呼び出しの関係）が実在しない
- 直すたびに別のテストが落ち、元の構造へ戻さない限り収まらない

テストが落ちていること自体は、成立しない理由ではありません。直せる見込みがあれば成立です。

## 必須コンテキスト

- リポジトリ: $RF_REPO / Pull Request #$RF_PR
- 作業ディレクトリ: `$RF_WORKDIR`（**読むだけ**。HEAD へ同期してある）
- 対象範囲: `$RF_SCOPE`

## 判定する項目

```json
$RF_ITEMS
```

- `commits` が項目のコミット、`failed_check` が落ちた検査（落ちたテストの ID・ファイル）、`fix_history` が
  これまでの修正ごとの落ちたテストの組、`rejudge` が真なら修正が停滞か振動したための判定し直しです
- `git show <コミット>` で差分を読み、落ちたテストを走らせて出力を読んでよい（コミットはしない）

## 提出形式

結果を **`$RF_STEM-result.json`** に書いてください。項目ごとに 1 行です。

```json
{"items": [{"item": "I-002", "feasible": true, "reason": "抽出した関数の引数の順が呼び手と食い違っているだけで直せる", "evidence": "tests/test_bar.py::test_handle の出力: TypeError ..."}]}
```

- `feasible` は `true` か `false`
- `evidence` には、根拠にした差分の行かテストの出力を引く

## 守ること

- 作業ディレクトリのファイルを変えない。コミットしない。push しない
- 作業段階が進むたびに `$RF_STEM-progress.log` へ 1 行追記する（`start` / `read` / `test` / `done`）
