# リファクタリング計画（cross-refactoring / $RF_RUNTIME）

あなたは **$RF_RUNTIME**（モデル: $RF_MODEL）として、参加者の全員が出した
リファクタリングの改善候補を**判断**します。この後のテストの追加・実装・修正もあなたが担います。
この段階では**コードを 1 行も変更しません**。

時間に収まる件数を選ぶのはオーケストレーターです（配分テーブルの見積りで計算します）。
**あなたが返すのは、改善候補ごとの判断だけです。**

## 必須コンテキスト

- リポジトリ: $RF_REPO / Pull Request #$RF_PR
- 作業ディレクトリ: `$RF_WORKDIR`（**読むだけ**。ここから外は読まない）
- 対象範囲: `$RF_SCOPE`
- ラウンドテスト: `$RF_ROUND_TEST`
- 全体テスト: `$RF_BASELINE_TEST`
- 想定最大時間: $RF_BUDGET_MINUTES 分

## 手順書

$RF_SKILL_BLOCK

## 改善候補

```json
$RF_ITEMS
```

## 改善候補ごとに決めること

| 項目 | 決め方 |
| --- | --- |
| `tier` | 適用する価値。`high` / `medium` / `low` の 3 グレード。**全件に付ける** |
| `tests` | リファクタリングの前に足すべき現状固定テストの置き場所（リポジトリ相対のパス）。既存のテストで振る舞いが固定されているなら空 |
| `test_targets` | この項目の検証に走らせるテストの対象（パスか、`<パス>::<名前>` のノード ID）。オーケストレーターがテストのコマンドへ差し込む。**対象ラウンドテストの置き場所の中で、実在するもの**に限る（足すテストを含めてよい） |
| `merge_into` | 同じ `path` + `symbol` の別の改善候補と**同じ変更**なら、その改善候補の `key`。違えば `null` |
| `risk` | 公開の入出力（関数の引数と戻り値・CLI の引数と出力・ファイルの形）が変わりうるなら `true` |

- **コマンドは書かない。** `test_targets` だけを返します。空白・`;` `&` `|` `$` などを
  含む値は使われません
- `test_targets` を決められない改善候補は空の配列にします（ラウンドテストをそのまま使うか、
  ラウンドテストが無ければ見送られます）
- `tests` に書いたテストは、次のテストの追加で**あなたが**足します。多く書くほど
  時間の見積りが増え、採られる件数が減ります。**その項目の検証に要るテストだけ**を
  書いてください

## 提出形式

結果を **`$RF_STEM-result.json`** に次の形で書いてください。**改善候補の全件**について
1 件ずつ書きます。

```json
{
  "items": [
    {"key": "src/a.py#Foo.run#long_method", "tier": "high",
     "tests": ["tests/test_a.py"], "test_targets": ["tests/test_a.py::TestFoo"],
     "merge_into": null, "risk": false}
  ]
}
```

## 守ること

- **コードを変更しない**
- 作業ディレクトリの外を触らない
