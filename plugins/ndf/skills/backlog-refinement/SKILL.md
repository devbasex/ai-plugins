# 蓄積した課題を棚卸しする

**変更をまたいで溜まった課題そのものを見直す。** 起票はその場で行い、その変更から出た
取りこぼしは振り返りが拾うが、**一覧の全体を現状に合わせる手順**はどちらも持たない。

2026-09-04 に open 43 件を 1 件ずつ実物と突き合わせたところ、**24 件（56%）の本文が現状と
食い違っていた**。食い違いの原因は 3 つの版をまたいだ変更に集約された。

**直さないと、すでに直っている課題を拾って作業する。** 前提の違う課題を、書かれたとおりに
直す。着手のマイルストーンが決まらないまま溜まる。

## いつ呼ぶか

**変更が終わった時点で呼ぶ。** 振り返りがあればその後、無ければリリースの後である。

**着手の直前は判断が歪む場所である。** 実装を担う側には締め切りがあり、そこで「この課題は
成り立たない」と気づいても、止める判断は自分の作業を遅らせる。判断を下す人が、その判断で
損をする立場にある。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| スプリント | 1 つの版として出す課題と Pull Request のセット。リリースが版を上げる単位 |
| マイルストーン | 着手の時期を表す単位。GitHub の milestone を指す |
| 棚卸し | 既存の課題の本文・マイルストーン・ラベルを現状に合わせ、着手の順位を決め直すこと。起票は親 issue に限って含む。スクラムのバックログリファインメントに当たる |
| 区分 | 課題ごとに決める 8 つの値 |
| やらない | 課題そのものは成り立つが、抱える費用が直す費用を下回ると決めること |
| 再検討条件 | 「やらない」で閉じた課題を、再び考える条件 |
| 現象レイヤー | 課題が実際に現れている場所。ファイル・クラス・層のいずれかで書く |
| 修正レイヤー | 原因を直すべき場所。その責務を持つべき場所までさかのぼる |
| ルートコーズ | 修正レイヤーが現象レイヤーと違う課題に付ける区分。現れている場所では直さない |
| クラスタ | 同じ修正レイヤーを指す課題の集まり |
| 親 issue | クラスタの修正レイヤーを直すために新しくつくる課題 |
| 子 issue | クラスタに属する既存の課題。親 issue をつくった後も閉じない |
| プロダクトバックログ | open の課題を着手の順に並べた全体。マイルストーンの順 → マイルストーンの中の順位の辞書順で読む |
| スプリントバックログの候補 | 1 つのマイルストーンの中の課題を順位で並べたもの。次のスプリントはその先頭から容量の分を切り出す |
| 見積の段階 | 実害の大きさ（UBV）・時間的重要度（TC）・リスク低減（RR/OE）・大きさ（Size）に付ける、尺度の中の相対値 |
| 遅延コスト | UBV・TC・RR/OE の実効の段階の和。略して CoD |
| 順位の値 | 遅延コストを大きさの見積の段階の α 乗（α は大きさの指数）で割った値。マイルストーンの中の順位を決める |
| 切り出しの境界 | 容量に収まるまで順位の先頭から取ったときの最後の課題 |
| 前倒し / 後ろ倒し | 課題を直近のマイルストーンへ移すこと / 直近から順序で次のマイルストーンへ移すこと |

語の正本は用語集（`ndf-issue-upkeep` の文脈）にある。段階の付け方と、式・判定の置き場は
[references/ranking.md](references/ranking.md) にある。

**「棚卸し」は起票を含まない**（新しい課題を作るのは `out-of-scope` の役目である）。
**例外は親 issue の起票 1 つだけである。** 親 issue は新しい発見ではなく、既存の課題から
導かれる。課題を見つけたその場の起票は発見の瞬間しか見ないため、クラスタを作れない。

## 扱う 5 つ

| # | 扱うこと | 決めること |
| --- | --- | --- |
| 1 | 誤りの訂正 | 本文が現状と食い違っている課題を、実物に合わせて直す |
| 2 | マイルストーンの設定 | どのマイルストーンで着手するかを決める。無ければ新しく作る |
| 3 | やらないの判断 | 成り立つ課題でも、費用に見合わないものを再検討条件付きで閉じる |
| 4 | ルートコーズの判断 | 課題を、現れている場所ではなく根本原因の場所で直すと決める。直す場所と直し方を記録に残す |
| 5 | 順位付け | マイルストーンの中の着手の順位と、次のスプリントへ切り出す候補の境界を決める。後ろのマイルストーンに埋もれた課題を前倒しの候補として示す |

2 の決め方は [references/milestones.md](references/milestones.md)、3 の必要条件は
[references/no-work.md](references/no-work.md)、4 の条件と書き方は
[references/grouping.md](references/grouping.md)、5 の段階の付け方は [references/ranking.md](references/ranking.md) にある。
**マイルストーンの順序そのものは人が決める。** 順位付けは集計値（遅延コストの合計・最大・閾値以上の件数）を示すだけで、
順序を書き換えない。**手順 1 では読まない**
（対象を選ぶ手順では、どの判断も起きない）。手順 2A は 4 の「修正レイヤーの決め方」だけを読む。

## 手順

**5 つの手順に分け、区分の決定と反映を分ける。**

| 手順 | 何をするか | 分担 | 書き込み |
| --- | --- | --- | --- |
| 1 | 対象を選ぶ | しない | なし |
| 2A | 課題ごとに調べる | **件数で割る** | **なし（読み取りだけ）** |
| 2B | 全体で突き合わせて区分と見積の段階を確定する | **しない** | なし |
| 2C | 順位を算出する | しない | なし（記録だけ） |
| 3 | 反映する | 依存の無いものだけ割る | あり |

**手順 1 で対象が 0 件なら、そこで飛ばす。** 飛ばしたことを報告へ残す。

**候補の収集（手順 1）・順位の算出（手順 2C）・反映（手順 3）・報告の値は `upkeep.py` が持ち、区分と見積の段階の
決定（手順 2A / 2B）だけを LLM が持つ。** スクリプトの置き場所 `$R` の決め方は `development-workflow/references/scripts-lookup.md`
にある。出力はどれも 1 行の JSON（形は `$R/scripts/lib/README.md`）で、記録は
`$NDF_UPKEEP_STATE_DIR`（既定は一時ディレクトリの `ndf/backlog-refinement/`）の下にリポジトリごとに置く。

```bash
UPKEEP=$(bash "$R/scripts/resolve.sh" scripts backlog-refinement) || exit 3
```

| 終了コード | status | 次の手 |
| --- | --- | --- |
| 0 | `ok` | 次の手順へ進む |
| 10 | `gate` | `presentation_path` を示して「やらない」と、承認の要る前倒し・後ろ倒しの承認を一括で得る |
| 20 | `gate` | `next` に従う（上限を超えた候補・照合で飛ばした課題・部分的に終わった反映・段階の欠けた課題・`rank` と合わない plan） |
| 1 / 2 / 3 | `stopped` | `summary` と `items[].reason` を報告して止まる |

**区分の決定を 2A と 2B に分けるのは、課題どうしが独立しないためである。** 重複の判定・正本の
決定・関連する課題の状態・マイルストーンの完了・同じ修正レイヤーを指す課題の突き合わせ・
同じ前提の変化を受けた課題群の書き換えは、いずれも課題をまたいで決まる。件数で割ると、担当 A が「#10 は #20 の重複」、担当 B が
「#20 は #10 の重複」と判定しうる。

### 手順 1: 対象を選ぶ

5 つの経路で集め、重複を除く。**対象は open の課題だけである。**

| 経路 | 取り方 | 拾えるもの |
| --- | --- | --- |
| 機械の候補 | 前のリリースから今までの差分のファイルのパスと、削除された行に現れる識別子を検索語にする | 消えたパス・改名された識別子を指す課題 |
| 担当が足す | 差分に現れない前提の変化（運用の開始、外部の状態、版が上がった外部コマンド） | 実在するようになったブランチのような、差分に出ないもの |
| マイルストーン | このスプリントで閉じた課題が属するマイルストーンと、**マイルストーンの付いていない open の課題すべて** | 完了したマイルストーン、どのマイルストーンへも割り当てられていない課題 |
| 親 issue | このスプリントで閉じた親 issue の子 issue（`gh api repos/<所有者>/<リポジトリ>/issues/<親の番号>/sub_issues` と、本文で親 issue を指す課題） | 原因が直った後も open のまま残る子 issue |
| コミットの件名 | 前のリリースから今までのコミットの件名が `#番号` で指す課題 | 直してリリースしたのに閉じ忘れた課題。差分のパスに現れない課題も拾う |

**子 issue は閉じないため、親 issue が閉じた後も open のまま残る。** 子 issue は親と別の
マイルストーンにいることがあり、ほかの 3 経路では拾えない。拾った後は既存の「閉じてよい」が
再現手順を実行して決める。

**機械の候補だけでは足りない。** 上の 3 原因のうち、`develop` の実在は差分に現れないため
取りこぼす（3 件）。担当が足す経路がこれを拾う。**候補は広めに出して落とす**
（`out-of-scope` が「迷ったら起票する側へ倒す」としたのと同じ考え方である）。

**起票者は問わない。** 絞ると、未設定のまま溜まる課題を誰も見ないことになる。

```bash
python3 "$UPKEEP/upkeep.py" candidates --since-ref <前のリリースのタグ> [--all] [--add 12,34] [--limit N]
```

機械の候補・マイルストーン・親 issue・コミットの件名の 4 経路は `candidates` が集める（`items[].routes` が
`diff-path` / `diff-identifier` / `no-milestone` / `closed-milestone` / `sub-issue` /
`commit-subject`）。`commit-subject` の候補は上限で切るときも先に残す。`rank` を打ったことのあるリポジトリでは、記録の
見積が無い課題と、見積を付けた後に要約値が変わった課題も拾う（`unscored`。上限で切るときの経路の数には入れない）。
`rank` を打ったことが無い初回は、手順 2C の `rank` が見積の無い open の課題をすべて `excluded` で返し、その全件が採点の対象になる。担当が足す
経路の課題は `--add` で渡す（`manual`）。候補ごとに `updated_at` と課題の要約値（`digest`。題名・本文・
状態・マイルストーン・ラベルから作る）を返し、手順 3 の照合に使う。未完了が 0 件になったマイルストーンは `kind: milestone` の項目で返る。

**`--limit` で 1 回に扱う件数に上限を置く。** 経路の多い候補から残し、超えた分は `items` に載せず
`metrics.deferred` に番号だけを並べて終了コード 20 で返る。判定するのは `items` の候補だけである。残りは次の回に `--add` で渡すか、上限を上げる。

**全体に影響する変更では、触った領域では足りない。** 次のいずれかに当たるときは対象を
open の全件へ広げる（`--all`）。

| 全体に影響する変更 | 例 |
| --- | --- |
| ディレクトリの移動・統合 | 配布物の置き場所を変える |
| 対応する実行環境の増減 | 配る先のランタイムを足す |
| ブランチ戦略の変更 | リリースチャネルを分ける |
| 識別子の一括改名 | 委譲先の CLI を置き換える |

**着手の前に対象の件数を示す。** 選んだ結果が少ないとき、担当は全件へ広げる判断をできる。
件数の閾値は決めない（リポジトリによって open の規模が違うため）。

### 手順 2A: 課題ごとに調べる

**この手順では何も書き込まない。** 課題ごとに独立するため、件数で割って同時に進めてよい。

確かめるのは 6 点である。**本文が指す対象が現在も存在するか / すでに直っているか（再現手順を
実行して確かめる）/ 前提が現状と食い違っていないか / 他の課題と重複していないか / 抱える
費用が直す費用を下回るか / 修正レイヤーが現象レイヤーと違うか。**

| 区分 | 選ぶ条件 | 手順 3 での対応 |
| --- | --- | --- |
| そのまま | 本文と現状が一致している | 何もしない |
| 追記が要る | 本文は有効だが、数値・パス・関連する課題の状態が古い | 該当箇所だけを直す |
| 書き直しが要る | 本文の前提が現状と食い違う | 主旨を変えずに前提を書き直す |
| 閉じてよい | すでに直っている | 実行結果を添えて閉じる |
| **やらない** | **課題は成り立つが、抱える費用が直す費用を下回る**（[references/no-work.md](references/no-work.md)） | **`wontfix` を付け、理由と再検討条件を添えて閉じる** |
| 重複 | 他の課題と同じもの | 手順 2B で正本を決める |
| **ルートコーズ** | **修正レイヤーが現象レイヤーと違う。現れている場所では直さない**（[references/grouping.md](references/grouping.md)） | **修正レイヤーと修正方針を記録する。同じ修正レイヤーを指すものが 2 件以上なら親 issue をつくって結び付ける** |
| **要判断** | **自動で決められない** | **人へ返す。反映しない** |

**「閉じてよい」と「書き直しが要る」には実行結果を添える**（`investigation-rules`）。読んだ
だけで直っていると判断しない。

手順 2A は課題ごとに次を控える。

| 控える項目 | 何に使うか |
| --- | --- |
| 番号・`updated_at`・課題の要約値（`candidates` の値をそのまま写す） | 手順 3 の照合 |
| 区分と根拠（実行したコマンドと出力） | 手順 2B と手順 3 |
| 反映で行う変更 | 手順 3 |
| 依存する課題の番号 | 手順 2B と反映の順序 |
| 現象レイヤー | この課題が現れている場所。ファイル・クラス・層のいずれかで書く |
| 修正レイヤー | 直すべき場所。その責務を持つべき場所までさかのぼり、本文が書いている直し方をそのまま採らない（[references/grouping.md](references/grouping.md) の「修正レイヤーの決め方」）。手順 2B がクラスタを確定する材料 |
| 段階の材料（`unscored` の課題と、手順 2C が `excluded` で返した課題） | 本文の該当箇所・実害の観測（再現の記録・起きた日時とログ）の有無・退避策が止まるのを防いだ記録・依存の記述（「#N の後」「#N を前提に」・ルートコーズの親）・人の判断待ちか。**段階はここでは付けない**（[references/ranking.md](references/ranking.md) の「材料の取り場所」） |

**手順 2A ではクラスタを決めない。** 複数人で分担しており、他の課題の記録が見えないためである。
決めるのは、この課題の修正レイヤーが現象レイヤーと違うかだけである。

### 手順 2B: 全体で突き合わせて区分を確定する

**この手順は分担しない。** 課題をまたいで決まるものを、ここでまとめて確定する。

| 突き合わせるもの | 何を決めるか |
| --- | --- |
| 重複と判定された組 | どちらを正本にするか。片方を閉じたときに残らないものが無いか |
| 同じ原因を持つクラスタ | 「ルートコーズ」の課題のうち、同じ修正レイヤーを指すものはどれか。手順 3 で本文へ書くか、親 issue をつくるか、重複へ寄せるか |
| 関連する課題の状態 | 一方を閉じると、他方の本文が指す前提が変わらないか |
| マイルストーン | 未完了が 0 件になったものはあるか。設定されていない課題をどこへ入れるか |
| ラベルの体系 | 新しく起票された課題に付いているか。基準はそのリポジトリのラベルの説明が持つ |
| 同じ前提の変化を受けた課題群 | 同じ書き換えを、同じ言い回しで行うか |

**重複の突き合わせを、クラスタより先に行う。** 手順 3 での対応は「別の課題である」ことを
前提にするため、重複の正本が決まっている必要がある。

**クラスタと、同じ前提の変化を受けた課題群は別のものである。** クラスタは直す場所を 1 つに
するために原因でまとめる。後者は、各課題の本文の書き換えの言い回しを揃えるだけで、直す場所は
課題ごとに残る。

**重複の判定では、起点が同じことと同じ課題であることを分ける。** 同じ誤りから出た 2 件でも、
片方が 1 行を直すもの、もう片方が手順に確認の項目を足すものであれば、片方を閉じるともう
片方が残らない。**修正レイヤーを直した後に個別の作業が残るなら重複ではない。** 同じ
修正レイヤーを指すものが 2 件以上あれば「ルートコーズ」として親 issue をつくり、残らない
なら重複として正本へ寄せる。

**「やらない」の候補は、この手順の後に一括で提示して承認を得る。** 件ごとに聞かない。提示する
項目は [references/no-work.md](references/no-work.md) にある。

**見積の段階は、列ごとに全件を並べて付ける。** UBV の列を全件で付けてから TC の列へ移る。課題ごとに担当へ割ると、
担当ごとに尺度がずれる。段階と根拠の 1 行を JSON（見積の入力）で書き、式・依存の順序・同点の扱い・前倒しの判定は
手順 2C のスクリプトに任せる。付け方と見積の入力の形は [references/ranking.md](references/ranking.md) にある。

### 手順 2C: 順位を算出する

```bash
python3 "$UPKEEP/upkeep.py" rank --scores scores.json [--capacity N] [--approved 12,34]
```

`rank` は open の課題・マイルストーンの説明・サブイシューを読み、マイルストーンごとの順位・大きい課題の枠・切り出しの
境界・前倒しと後ろ倒しの候補・前回の `### 順位` の表からの変化を返す。見積は `--scores`（この回に付けた課題）→ 記録 →
説明の `### 順位` の表の順に採る。設定（尺度・余白・容量など）は引数 → `.ndf/backlog.json` → 既定値の順に採る。

| 返り | 次の手 |
| --- | --- |
| 0（容量あり） | 候補を plan に入れて手順 3 へ |
| 0（容量なし） | 順位の表だけを反映する。境界と候補は出ないため、`next` に従って容量を渡す |
| 20（`excluded` あり） | 外れた課題（段階が無い・尺度に無い値・根拠が空・UBV が実害の目安の帯の外）に手順 2B で段階を付けて打ち直す |
| 2（依存の循環） | 循環する課題の依存の記述を人へ返す。どちらを先にするかは人が決める |

マイルストーンの無いリポジトリでは算出を飛ばす（`metrics.skipped`）。

### 手順 3: 反映する

区分がすべて揃ってから始める。区分と変更を plan.json に書き、`apply` で反映する。plan.json の
形は `upkeep.py` の冒頭にある。

```bash
python3 "$UPKEEP/upkeep.py" apply --plan plan.json [--max-waits N]
```

- **本文は全文を書き直す。** コメントの追記ではなく本体を直す
- **変更の経緯を本文に残さない**（`markdown-writing` のルール 4）。書くのは確定した現在の情報だけ
- **反映する側も 1 度は実物と突き合わせる。** 手順 2A の値が現物と合わないことがある

**手順 2A と手順 3 の間に、別の担当や人が課題を書き換えることがある。** そのまま反映すると相手の
変更を消すため、手順 3 は反映の直前に照合する。**`updated_at` が変わっていれば課題の要約値を
見る。** 要約値も変わっていればその課題だけを手順 2A へ戻し、同じ（コメントが付いただけ）ならそのまま反映する。
1 つの課題の反映が途中で止まったときは、書き込んだ後の要約値を記録へ残し、打ち直しではそれを自分の
書き込みとして照合を通す。記録のキーは plan の `updated_at` と要約値を含み、後の回で同じ変更を決めても
「済み」にしない。
`apply` はこの照合を課題ごとに行い、飛ばした課題を `skipped_changed` に並べる。

**反映は同じ操作を 2 度行っても結果が変わらない形にする。** 済んだ課題を記録へ記録して
やり直しのときは飛ばし、変える内容が無いときは書き込みを行わない。`apply` は記録（`already`）と
いまの状態との比較（`unchanged`）でこれを行う。「やらない」は `"approved": true` の無い限り
反映せず（`needs_approval`）、「要判断」は反映せずに返す（`returned`）。

**順位の表と前倒し・後ろ倒しは、`rank` の結果を plan に入れて反映する。** plan の `rank` に `rank` の
`metrics.digest` を書くと、`apply` が各マイルストーンの説明の末尾の `### 順位` の節を書き換える（節の外は変えず、
同じ順位なら書かない）。前倒し・後ろ倒しは、候補ごとに `"reschedule": "前倒し"`（または `後ろ倒し`）と
`"changes": {"milestone": <候補の移す先>}` を書く。前倒しの候補に `group`（後ろに残る依存先）があれば、その各課題にも
同じ移す先の前倒しの action を書く（欠けると `apply` が plan の誤りとして止まる）。扱いが「自動」の前倒しはそのまま反映し、「承認」の候補は
`approved` によらず `needs_approval` へ回る。承認を得た番号を `rank --approved` で渡して打ち直し、「承認済み」になった
結果で plan を作り直す。人が退けた移動は plan の `rejected`（`[{number, direction}]`）に書くと、`apply` が記録に残し、
同じ移動は次の回から候補に出ない。**`pace` の値によってこの扱いは変わらない**（スプリント MVV の事前の承認は、主題の
外から課題を入れる判断を含まない）。

**親 issue の起票と子 issue の結び付けは、手順 2B の後に一括で提示し、承認を得てから行う。**
起票はクラスタに 1 度、結び付けは課題ごとに行う。2 度行わない見分け方は
[references/grouping.md](references/grouping.md) の「やり直しで 2 度行わない」にある。

## 自動で反映してよい変更と、返す変更

| 変更 | 自動で反映してよいか |
| --- | --- |
| パス・行番号・版数の更新 | よい |
| 再現手順を実行して直っていることを確かめて閉じる | よい |
| 明らかな重複を正本へ寄せる | よい |
| 課題をマイルストーンへ入れる。無ければ末尾に新しく作る | よい |
| 依存の記述と食い違うマイルストーンの順序を直す | よい |
| マイルストーンの中の順位（説明の `### 順位` の表） | よい。前回からの変化を報告に出す |
| 前倒し（実害の観測があり、UBV か RR/OE が自動の閾値以上） | よい（`rank` の扱いが「自動」） |
| **ほかの前倒しと、すべての後ろ倒し** | **一括で提示し、承認を得てから行う** |
| **マイルストーンの順序（連番と着手の順序）を変える** | **返す。集計値を材料として示すだけ** |
| ラベルの説明に照らして重要度を付け替える | よい |
| 前提が反転した課題の問いを立て直す | よい |
| **やらないと判断して閉じる** | **一括で提示し、承認を得てから行う** |
| **親 issue を作る** | **一括で提示し、承認を得てから行う** |
| **子 issue を親 issue へ結び付ける（サブイシュー関係を張る / 子 issue の本文へ 1 行を足す）** | **一括で提示し、承認を得てから行う** |
| **起票の意図が現在も要るかを判断できない** | **返す** |
| **正しい読み方が複数ある** | **返す** |

**分かれ目は、判断の材料が本文の外にあるかどうかである。** ラベルの説明・依存の記述・実物の
状態に照らして 1 つに決まるものは反映し、決まらないものだけを返す。

### 重要度と問いの形を変えるときの基準

**新しい基準を作らない。** 判断の材料はリポジトリの側にある。

| 変えるもの | 基準 | 材料の在り処 |
| --- | --- | --- |
| 重要度 | 実害の観測が変わったか | **ラベルの説明**（`gh label list --json name,description`） |
| 問いの形 | 前提が反転したか | 本文が指す実物の状態 |

**重要度は、ラベルの説明が持つ区分へ当てはめる。** 実害の観測が本文へ追記された課題は上げ、
実害が起きない経路だと分かった課題は下げる。**説明の無いラベルへは付け替えない。**

**問いを立て直すのは、前提が反転したときに限る。** **立て直すのは問いの形であって、主旨では
ない。** 何が困るかは変えない。**主旨まで変わるなら、それは別の課題である。** 元の課題を
閉じて新しく起票する判断になるため、返す。

## 外部への書き込みの制限

課題の作成と本文の更新を続けると、GitHub がコンテンツの作成を拒む。実測では 60 秒の間隔で
13 回待った例がある。**待つ長さは応答から取る。** 固定の間隔で待たない。

| 状況 | 待ち方 |
| --- | --- |
| 応答が `Retry-After` を返す | その秒数だけ待つ |
| 上限の回復時刻を返す | その時刻まで待つ |
| どちらも無い（作成の二次的な制限） | 間隔を倍にしながら待つ |
| 一定の回数を超えた | 部分的に終わった状態として止め、何が済んだかを報告へ残す |

`apply` がこの待ち方を持つ（`metrics.waits`）。回数の上限は `--max-waits`、1 回の長さの上限は
`--max-wait` で、超えると `partial` を立てて残りを `pending` に並べる。同じ plan で打ち直すと、
済んだ課題は記録で飛ぶ。`report` の反映と待ちの件数は、同じ回（前の `candidates` 以降）に打った
`apply` をすべて足し合わせた値（`metrics.round`）である。

## 他のリポジトリで動くこと

前提にしてよいのは `gh` が使えることと、課題管理に issue を使っていることだけである。

| 無いもの | 振る舞い |
| --- | --- |
| マイルストーン | 手順 1 の 3 つ目の経路と `unscored`、扱うこと 2 と 5（手順 2C）を飛ばす |
| サブイシューの API | 子 issue の結び付けを、すべて子 issue の本文の 1 行で行う。依存は本文と説明の並列の組から取る |
| バックログの宣言（`.ndf/backlog.json`） | 一般的な WSJF の既定値で動く。ラベルの下限は効かない。容量が無ければ境界と候補を出さない |
| 重要度ラベル | `gh label list` が返す説明を基準にする。説明が無ければ付け替えない |
| `wontfix` にあたるラベル | ラベルを付けずに閉じる。理由と再検討条件は本文に残るため検索で拾える |

## 既存の Skill との境界

| Skill | 扱うもの |
| --- | --- |
| `out-of-scope` | 範囲外の課題を、**見つけたその場で**起票する |
| `retrospective` | **その変更の進め方**を見直し、起票の取りこぼしを拾う |
| `backlog-refinement` | **蓄積した既存の課題**を棚卸しする |

**課題に対する判断は 2 種類ある。** やるかどうかを決める価値の判断と、どこを直すかを決める
構造の判断である。溜まった課題に対しては、どちらもこの Skill が持つ。

| 判断 | 発見の瞬間 | 溜まった課題 |
| --- | --- | --- |
| 価値（やるか） | `out-of-scope` の「起票しない」 | `backlog-refinement` の「やらない」 |
| 構造（どこを直すか） | `out-of-scope` の「範囲内へ入れる」、`problem-solving` の「上流で直す」 | `backlog-refinement` の「ルートコーズ」 |

**この表の正本はここである。** 他の Skill はこの表を指し、写さない。

**発見の瞬間の判断は、蓄積した課題には及ばない。** **発見の瞬間には、指摘の周辺しか見えて
いない。** 同じ原因の課題がほかにあるか、抱える費用が直す費用を下回るかは、一覧を見る棚卸しで
しか分からない。`problem-solving` の「上流で直す」は、見つけて直している最中の不具合の上流を
たどる。溜まった課題を見比べて直す場所を決めるのは「ルートコーズ」である。

## 完了報告

| 項目 | 何を書くか |
| --- | --- |
| 対象 | 手順 1 で選んだ件数と、選んだ経路。0 件なら飛ばしたことと理由 |
| 区分の内訳 | 8 つの区分ごとの件数 |
| クラスタ | 処理したクラスタの数と、クラスタごとの親 issue の番号・子 issue の番号 |
| 反映 | 直した件数・閉じた件数・返した件数 |
| 未設定のまま残った課題 | 件数と理由（主題が合わず重要度も低い / 1 件しか残らない / 複数に当てはまる） |
| 待った回数 | 外部への書き込みの制限に当たった回数と、待った長さ |
| 順位 | マイルストーンごとの件数と切り出しの境界（課題の番号と Size の和 / 容量）。容量が無ければ境界を書かない |
| 前回からの変化 | 上がった・下がった・入った・外れた課題と、変わった列と前後の段階（例: `TC 3→8`） |
| 前倒し・後ろ倒し | 候補ごとの移す元と先・扱い（自動 / 承認 / 承認済み）・境界との差。退けたものも並べる |
| 分割が要る・人の判断待ち・本文の書き足しが要る | 大きい課題の枠に収まらなかった課題、`needs-decision` などで判断を待つ課題、段階の根拠が本文に無い列 |
| 用語集の変化 | 足された語の数・廃止された語の数と、語の並び（`glossary.py diff` の結果）。用語集の設定が無いプロジェクトでは書かない |

対象・区分の内訳・反映・待った回数・順位付けの値は `report` が記録から返す。用語集の変化は、棚卸しの対象の期間の
起点（直近の本番のタグ）と終点（`HEAD`）で `glossary.py diff` を打って取る。

```bash
python3 "$SCRIPTS/glossary.py" diff --base "$(git describe --tags --abbrev=0)" --head HEAD
```

```bash
python3 "$UPKEEP/upkeep.py" report
```

**未設定の件数を報告へ残す。** 残った件数と理由が、次の棚卸しの材料になる。

この工程に入ったら進捗記録のコマンド `bash "$SCRIPTS/projects-sync.sh" <issue番号> stage "振り返り"` を 1 行打つ（この Skill は工程表に載らないため、直前の工程の値をそのまま使う。issue の本文とボードの両方に残る。`$SCRIPTS` の決め方は `development-workflow` の `references/scripts-lookup.md`、3 層では起動指示の進捗記録のコマンドを使う）。
