# リリース後テスト

**リリースされた成果物が、利用者の環境で受け入れ条件を満たすことを確かめる。**

マージ前の検証では踏めない経路がある。実物のデータ、サービス一式、導入済みの環境、
リリースの手続きそのもの。これらは取り込み前には用意できない。

## `quality-gates` との境界

| | `quality-gates` | この Skill |
| --- | --- | --- |
| 対象 | 取り込み前の差分 | リリースされた成果物 |
| 実行する場所 | 開発の worktree | 利用者が受け取るのと同じ導入経路をたどった環境 |
| 何を示すか | 退行を出していないこと | 受け入れ条件を利用者の環境で満たすこと |
| いつ | 完了報告の前 | 版のリリースが終わった後 |

`quality-gates` の段階 4（結合・端から端まで）も取り込み前の検証である。この Skill は
その先を扱う。

## 開始条件

**版のリリースが終わっていること。** リリースの手続き（版の更新・タグ・公開）は直前の工程である
`release` が行う。それを終え、利用者が受け取れる状態になってから実行する。マージ直後に
実行すると、リリースの過程で壊れるものが対象から外れる。

リリースの形は対象によって変わる。開始できるかは、次のどれが済んだかで判断する。

| リリースの形 | 開始できる時点 |
| --- | --- |
| パッケージ・プラグイン | 版を公開し、利用者が取得できるようになった時点 |
| サービス | 対象の系へ反映が終わった時点 |
| デスクトップ・モバイルアプリ | 配布物が置かれた時点。ストアを経るものは審査を通った時点 |
| 手順・設定の変更 | 利用者へ配った時点 |

**リリース種別ごとに行う。** 検証リリースの後は検証環境で、本番へのリリースの後は本番で確かめる。
**検証で確かめたことは本番で確かめたことにならない。** 環境が違えばデータも設定も違い、
リリースの手続きそのものも別に走る。どちらを対象にした検証かを記録へ書く。

## 入力

新しく基準を作らない。次の 2 つを受け取る。

| 入力 | どこから |
| --- | --- |
| 受け入れ条件 | `requirements-design` が作った仕様 |
| 未検証の項目 | `quality-gates` の完了報告の「未検証の項目」 |

**「未検証の項目」がこの工程の主対象になる。** マージ前に実施できなかった条件は、
ここで実施するか、実施しない理由を残すかのどちらかにする。

## 手順

### 1. 対象の版を確かめ、利用者と同じ導入をやり直す

**導入経路をたどった側を見る。手元の worktree は見ない。** Claude Code のプラグインの形では、
次を打ち、結果 JSON の `status` を見る。

```bash
python3 "$SCRIPTS/release-verification-steps.py" verify-install --ref <develop|main> --expect <版> \
  [--plugins ndf,...] [--runtimes claude,codex,kiro] --root .
```

隔離した HOME で ref から導入し、導入された版と、前の正式版のタグから変わったファイルの中身が
ref と一致するか、利用者の HOME の設定が変わっていないかを確かめる。

| `status`（終了コード） | 次にすること |
| --- | --- |
| `ok`（0） | 手順 2 へ進む。`items[]` を証跡として記録へ載せる |
| `stopped`（1） | 版か中身が一致しない・導入が失敗した。先へ進めず不合格として手順 3 へ |
| `stopped`（2 / 3） | 呼び出しの誤りか plugin が無い。引数を直して打ち直す |

ほかの形では、導入状況を表示するコマンドでリリースした版との一致を確かめ、再インストール・
再取得・再起動のうち利用者が実際に行うものを行う。

### 2. 受け入れ条件ごとに確かめる

条件 1 つずつに、実行したコマンドと結果を対応させる。証跡の書き方は `quality-gates` の
規則に従う（実行したコマンド・終了コード・実行時刻・対象範囲）。

### 3. 合否を判定する

| 結果 | 判定 | 次にすること |
| --- | --- | --- |
| すべての条件を満たした | 合格 | 記録を残す |
| 満たさない条件があった | 不合格 | 修正の変更として起票し、通常の工程で直す |
| 実施できない条件があった | 保留 | 実施できない理由と、いつ実施するかを記録に残す |

**振り返りを通る変更では、合否によらず記録を残して `retrospective` へ進む。** 振り返りの
対象は進め方であり、検証の合否ではない。不合格や保留が出たときこそ、マージ前に踏めなかった
経路が何だったかを見直す材料になる。**振り返りを通らない変更では、この工程がその実行の
最終工程である**（下の「ミッションを閉じる」）。

**不合格を即時修正しない。** リリース後の修正は新しい変更であり、モードの判定から始める。

範囲外の課題が見つかったときは `/ndf:out-of-scope` で起票する。

## 出力物

検証結果を記録に残す。**置き場所は `release` が「配布の記録」を置いた Pull Request で、
そこへコメントで投稿する。** 会話や `issues/` の実装計画のファイルに残すと、別の実行の終わりの
工程から読めない。

```markdown
## リリース後テスト

対象の版: <配布した版>（<配布した時刻>）
導入経路: <利用者が行うのと同じ手順>

| 課題 | 受け入れ条件 | 実行したこと | 実行時刻 | 結果 |
| --- | --- | --- | --- | --- |
| #561 | 1. ... | `<コマンド>` | 2026-08-31 12:10 | 合格 / exit=0 |
| #561 | 2. ... | 手動確認（<何を見たか>） | 2026-08-31 12:15 | 合格 |
| #623 | 3. ... | — | — | 保留（理由: ...） |

合否: 合格（3 件中 2 件を実施、1 件は保留）
起票したもの: なし
```

**保留を空欄にしない。** 書かずに省くと、実施済みと読まれる。

**先頭の `課題` の列を空欄にしない。** ミッション課題を閉じる条件は課題ごとに見るため、
どの課題の条件だったかが読めないと**ミッション課題すべてが `開いたまま` になる**
（`progress-tracking` の「ミッションを閉じる」の「配布の記録」の読み方）。他のリポジトリの
課題は `<所有者>/<リポジトリ>#<番号>` と書く。`対象の版:` の行も、その版のブロックを
選ぶ入力であるため省かない。

## モードごとの要否

要否を決めるのは `development-workflow` である。この Skill は判定結果を受け取って実行する。
呼ばれた時点で、この工程が要ると判定されている。

この工程に入ったら進捗記録 `bash "$SCRIPTS/projects-sync.sh" <issue番号> stage "リリース後テスト"` を 1 行打つ（issue の本文とボードの両方に残る。`$SCRIPTS` の決め方は `development-workflow` の `references/scripts-lookup.md`、3 層では起動指示の「進捗記録」を使う）。

## ミッションを閉じる

**後に振り返りが続かない変更（振り返りを通らない `operation`）では、この工程がその実行の
最終工程である。** 検証結果を記録した後に、`progress-tracking` の「ミッションを閉じる」を
行う。**手順はそこが正本で、ここには写さない。** 振り返りを通る変更では、そちらが行うため
ここでは行わない。

**不合格・保留の条件を持つ課題は閉じない。** その課題は `開いたまま` になり、判定と理由が
報告に載る。確かめていないことが終わったように見えないためである。

## 蓄積した課題を棚卸しする

**後に振り返りが続かない変更では、「ミッションを閉じる」の後に `/ndf:issue-upkeep` を呼ぶ。**
順序を逆にすると、`issue-upkeep` の手順 1 が読む「このミッションで閉じた課題」がまだ閉じていない。
振り返りを通る変更では、そちらの最後で呼ばれるためここでは呼ばない。

対象が 0 件ならその Skill 自身が飛ばす。

## 関連

- `/ndf:quality-gates` — マージ前の検証の証跡
- `/ndf:release` — この工程の前に行うリリース。開始条件はその完了である
- `/ndf:retrospective` — この工程の後に行う振り返り
- `/ndf:progress-tracking` — 「ミッションを閉じる」の正本と、記録の置き場所
- `/ndf:issue-upkeep` — 蓄積した課題の棚卸し（振り返りが続かないときに呼ぶ）
- `/ndf:out-of-scope` — 検証で見つけた範囲外の課題の起票
