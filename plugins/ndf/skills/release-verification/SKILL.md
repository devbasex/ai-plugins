# リリース後テスト

**配布された成果物が、利用者の環境で受け入れ条件を満たすことを確かめる。**

マージ前の検証では踏めない経路がある。実物のデータ、サービス一式、導入済みの環境、
配布の手続きそのもの。これらは取り込み前には用意できない。

## `quality-gates` との境界

| | `quality-gates` | この Skill |
| --- | --- | --- |
| 対象 | 取り込み前の差分 | 配布された成果物 |
| 実行する場所 | 開発の作業ツリー | 利用者が受け取るのと同じ導入経路をたどった環境 |
| 何を示すか | 退行を出していないこと | 受け入れ条件を利用者の環境で満たすこと |
| いつ | 完了報告の前 | 版の配布が終わった後 |

`quality-gates` の段階 4（結合・端から端まで）も取り込み前の検証である。この Skill は
その先を扱う。

## 開始条件

**版の配布が終わっていること。** 配布の手続き（版の更新・タグ・公開）は直前の工程である
`release` が行う。それを終え、利用者が受け取れる状態になってから実行する。マージ直後に
実行すると、配布の過程で壊れるものが対象から外れる。

配布の形は対象によって変わる。開始できるかは、次のどれが済んだかで判断する。

| 配布の形 | 開始できる時点 |
| --- | --- |
| プラグイン・ライブラリ | 版を公開し、利用者が再インストールで取得できるようになった時点 |
| サービス | 対象の系へ反映が終わった時点 |
| 手順・設定の変更 | 利用者へ配った時点 |

## 入力

新しく基準を作らない。次の 2 つを受け取る。

| 入力 | どこから |
| --- | --- |
| 受け入れ条件 | `requirements-design` が作った仕様 |
| 未検証の項目 | `quality-gates` の完了報告の「未検証の項目」 |

**「未検証の項目」がこの工程の主対象になる。** マージ前に実施できなかった条件は、
ここで実施するか、実施しない理由を残すかのどちらかにする。

## 手順

### 1. 対象の版を確かめる

```bash
# 例: 導入済みの版と、配布した版が一致するか
<導入状況を表示するコマンド>
```

**手元の作業ツリーではなく、導入経路をたどった側を見る。** 一致していない状態で先へ
進むと、別のものを検証したことに気づけないまま合格になる。

### 2. 利用者と同じ導入をやり直す

再インストール・再取得・再起動のうち、利用者が実際に行うものを行う。開発の途中で作った
状態が残っていると、初めて導入する利用者の環境と食い違う。

### 3. 受け入れ条件ごとに確かめる

条件 1 つずつに、実行したコマンドと結果を対応させる。証跡の書き方は `quality-gates` の
規則に従う（実行したコマンド・終了コード・実行時刻・対象範囲）。

### 4. 合否を判定する

| 結果 | 判定 | 次にすること |
| --- | --- | --- |
| すべての条件を満たした | 合格 | 記録を残す |
| 満たさない条件があった | 不合格 | 修正の変更として起票し、通常の工程で直す |
| 実施できない条件があった | 保留 | 実施できない理由と、いつ実施するかを記録に残す |

**合否によらず、記録を残して `retrospective` へ進む。** 振り返りの対象は進め方であり、
検証の合否ではない。不合格や保留が出たときこそ、マージ前に踏めなかった経路が何だったかを
見直す材料になる。

**不合格をその場で直さない。** 配布後の修正は新しい変更であり、モードの判定から始める。

範囲外の課題が見つかったときは `/ndf:out-of-scope` で起票する。

## 出力物

検証結果を記録に残す。置き場所は変更の記録と同じ場所（`issues/` の計画ファイル、または
Pull Request のコメント）とする。

```markdown
## リリース後テスト

対象の版: <配布した版>（<配布した時刻>）
導入経路: <利用者が行うのと同じ手順>

| 受け入れ条件 | 実行したこと | 実行時刻 | 結果 |
| --- | --- | --- | --- |
| 1. ... | `<コマンド>` | 2026-08-31 12:10 | 合格 / exit=0 |
| 2. ... | 手動確認（<何を見たか>） | 2026-08-31 12:15 | 合格 |
| 3. ... | — | — | 保留（理由: ...） |

合否: 合格（3 件中 2 件を実施、1 件は保留）
起票したもの: なし
```

**保留を空欄にしない。** 書かずに省くと、実施済みと読まれる。

## モードごとの要否

要否を決めるのは `development-workflow` である。この Skill は判定結果を受け取って実行する。
呼ばれた時点で、この工程が要ると判定されている。

進行を盤面へ記録する場合は `bash "$SCRIPTS/projects-sync.sh" <issue番号> stage リリース後テスト` を
実行する（`.ndf/projects.json` が無いリポジトリでは何も起きない。詳細は [references/projects-tracking.md](../development-workflow/references/projects-tracking.md)）。

## 関連

- `/ndf:quality-gates` — マージ前の検証の証跡
- `/ndf:release` — この工程の前に行う配布。開始条件はその完了である
- `/ndf:retrospective` — この工程の後に行う振り返り
- `/ndf:out-of-scope` — 検証で見つけた範囲外の課題の起票
