# リリース後テスト

**リリースされた成果物が、利用者の環境で受け入れ条件を満たすことを確かめる。**

マージ前の検証では踏めない経路がある。実物のデータ、サービス一式、導入済みの環境、
リリースの手続きそのもの。これらはマージ前には用意できない。

## `quality-gates` との境界

| | `quality-gates` | この Skill |
| --- | --- | --- |
| 対象 | マージ前の差分 | リリースされた成果物 |
| 実行する場所 | 開発の worktree | 利用者が受け取るのと同じ導入経路をたどった環境 |
| 何を示すか | 退行を出していないこと | 受け入れ条件を利用者の環境で満たすこと |
| いつ | 完了報告の前 | バージョンのリリースが終わった後 |

`quality-gates` の段階 4（結合・端から端まで）もマージ前の検証である。この Skill は
その先を扱う。

## 開始条件

**バージョンのリリースが終わっていること。** リリースの手続き（バージョンの更新・タグ・公開）は直前の工程である
`release` が行う。それを終え、利用者が受け取れる状態になってから実行する。マージ直後に
実行すると、リリースの過程で壊れるものが対象から外れる。

リリースの形は対象によって変わる。開始できるかは、次のどれが済んだかで判断する。

| リリースの形 | 開始できる時点 |
| --- | --- |
| パッケージ・プラグイン | バージョンを公開し、利用者が取得できるようになった時点 |
| サービス | 対象の系へ反映が終わった時点 |
| デスクトップ・モバイルアプリ | リリース対象が置かれた時点。ストアを経るものは審査を通った時点 |
| 手順・設定の変更 | 利用者へ配った時点 |

**リリース種別ごとに行う。** 開発版のデプロイの後は検証環境で、本番へのリリースの後は本番で確かめる。
**検証で確かめたことは本番で確かめたことにならない。** 環境が違えばデータも設定も違い、
リリースの手続きそのものも別に走る。どちらを対象にした検証かを記録へ書く。

## 入力

新しく基準を作らない。次の 2 つを受け取る。

| 入力 | どこから |
| --- | --- |
| 受け入れ条件 | `requirements-design` が作った仕様 |
| 未検証の項目 | `quality-gates` の完了報告の「未検証の項目」 |

**「未検証の項目」がこの工程の主対象になる。** マージ前に実施できなかった条件は、
ここで実施するか、実施しない理由を残すかのどちらかにする。

## 手順

### 1. 対象のバージョンを確かめ、利用者と同じ導入をやり直す

**導入経路をたどった側を見る。手元の worktree は見ない。** Claude Code・Codex のプラグインの形では、
隔離した設定ディレクトリへ ref から導入し直し、導入されたバージョンと、前の正式版のタグから変わったファイルの中身が
ref と一致するかを確かめる。打ち方は `release` の
[form-package-plugin.md](../release/references/form-package-plugin.md) の「隔離した設定ディレクトリで取得の経路を確かめる」にある。
`<ref>` にはベースブランチか本番チャネル（承認の前に試すなら版上げの PR の head）を渡す。

| 結果 | 次にすること |
| --- | --- |
| ランタイムごとの一覧の版数が出したバージョンと一致し、変わったファイルの中身が ref と一致した | 手順 2 へ進む。打ったコマンドと出力を証跡として記録へ載せる |
| 版数か中身が一致しない・導入が失敗した | 先へ進めず不合格として手順 3 へ |

ほかの形では、導入状況を表示するコマンドでリリースしたバージョンとの一致を確かめ、再インストール・
再取得・再起動のうち利用者が実際に行うものを行う。

#### 利用者の設定ディレクトリで導入しない

**Claude Code・Codex のプラグインの導入の確かめは、隔離した設定ディレクトリでだけ行う。** 隔離先は新しく作ったディレクトリで、
Claude Code へは `CLAUDE_CONFIG_DIR`、Codex へは `CODEX_HOME` で渡す。利用者の設定ディレクトリ
（Claude Code は `CLAUDE_CONFIG_DIR`、無ければ `~/.claude`。Codex は `CODEX_HOME`、無ければ `~/.codex`）で、
導入の操作（プラグインの導入・更新と取得元の登録・更新。`claude` と `codex` の `plugin` のサブコマンド `install` /
`add` / `update` / `marketplace add` / `marketplace update`）を打たない。打つと、利用者が導入したバージョンと
取得元の登録が黙って変わり、戻すには前のバージョンを入れ直す操作が要る。

**確かめるのに利用者の設定ディレクトリへの導入が要る条件は、導入しない。** 記録の表のその行を
`保留（理由: 利用者の設定ディレクトリへの導入が要る）` とし、作業の報告を「判断が要る」で返す。導入するかは人が決める。

**手順 1 の前に利用者の設定ディレクトリのスナップショットを取り、記録を投稿した後に比べる。**

```bash
ndf release-steps config-snapshot --out <スナップショットのファイル>   # 手順 1 の前
ndf release-steps config-check --before <スナップショットのファイル>   # 記録の後
```

`config-check` が `ok`（0）なら変わっていない。`check_failed`（1）なら変わった項目が `items[]` の `change` に載る。
スナップショットが読めなければ止まり、比べられない。`ok` 以外のときは、結果を添えて人へ戻す。
状態と終了コードの意味は [終了コードと停止理由](../../docs/contracts/exit-codes.md) にある。

### 2. 受け入れ条件ごとに確かめる

リポジトリのリリースの設定（`.ndf/release.json`）に `stage: verify` の手順があれば、先にリポジトリの根で書いた順に打ち
（`{version}` は出したバージョン）、手順の名前と終了コードを記録へ載せる。`ndf release-steps` はこの段階の手順を流さない。

条件 1 つずつに、実行したコマンドと結果を対応させる。証跡の書き方は `quality-gates` の
規則に従う（実行したコマンド・終了コード・実行時刻・対象範囲）。

### 3. 合否を判定する

| 結果 | 判定 | 次にすること |
| --- | --- | --- |
| すべての条件を満たした | 合格 | 記録を残す |
| 満たさない条件があった | 不合格 | 修正の変更として起票し、通常の工程で直す |
| 実施できない条件があった | 保留 | 実施できない理由と、いつ実施するかを記録に残す |

**振り返りを通る変更では、合否によらず記録を残して `retrospective` へ進む。** 振り返りの
対象は進め方であり、検証の合否ではない。不合格や保留が出たときこそ、マージ前に踏めなかった
経路が何だったかを見直す材料になる。**振り返りを通らない変更では、この工程がその実行の
最終工程である**（下の「スプリントを閉じる」）。

**不合格を即時修正しない。** リリース後の修正は新しい変更であり、モードの判定から始める。

範囲外の課題が見つかったときは `/ndf:out-of-scope` で起票する。

**リリース記録の `CD の結果:` が未確定なら、CD の状態の代わりに本番の状態を直接確かめる。** 本番で動いている
リビジョンかバージョンを読み、記録のリビジョンと照らした結果を行として載せる。確かめられなければ合格と書かず、保留にする。

## 出力物

検証結果を記録に残す。**置く場所は `release` が「リリース記録」を置いた Pull Request で、
そこへコメントで投稿する。** 会話や `issues/` の実装計画のファイルに残すと、別の実行の終わりの
工程から読めない。

```markdown
## リリース後テスト

対象のバージョン: <デプロイしたバージョン>（<デプロイした時刻>）
導入経路: <利用者が行うのと同じ手順>

| 課題 | 受け入れ条件 | 実行したこと | 実行時刻 | 結果 |
| --- | --- | --- | --- | --- |
| — | 導入の確認: 利用者と同じ手順で入れ直して起動する | `<コマンド>` | 2026-08-31 12:05 | 合格 |
| #561 | 1. ... | `<コマンド>` | 2026-08-31 12:10 | 合格 / exit=0 |
| #561 | 2. ... | 手動確認（<何を見たか>） | 2026-08-31 12:15 | 合格 |
| #623 | 1. ... | — | — | 保留（理由: ...） |

合否: 合格（3 件中 2 件を実施、1 件は保留）
起票したもの: なし
```

**保留を空欄にしない。** 書かずに省くと、実施済みと読まれる。

**課題を閉じる判定が読むのは、機械が読む記録である。** 表を書いた後に、同じ結果を
[リリース後テストの記録のスキーマ](../../contracts/schemas/release-verification.schema.json) の JSON
（`version` と、課題ごとの `number`・`result`（`passed` / `failed` / `not_run`）・`evidence`）にして、リリース記録と同じ PR へ書く。

```bash
ndf release-steps verification-record --pr <リリース記録の PR> --record <記録の JSON>
```

PR が同じバージョンのリリース記録を持たない・JSON の形が違う・書く token の書き手が信用されないときは、書かずに `precondition`（3）で止まる。

| 列 | 書くこと |
| --- | --- |
| 課題 | `#<番号>`、他のリポジトリの課題は `<所有者>/<リポジトリ>#<番号>`。課題に結び付かない検証（導入の確認など）は `—` |
| 受け入れ条件 | セルの頭に受け入れ条件の番号を `<番号>.` で書く（例 `2. 一覧は更新日時の降順で並ぶ`）。番号は課題の本文の `## 受け入れ条件` のチェックボックスの行を上から数えた順（1 から）。課題に結び付かない行は番号を書かない |
| 結果 | `合格` / `不合格` / `保留` で始める。`合格` で始まる行が合格の行である |

**課題の本文の受け入れ条件 1 つにつき 1 行以上を置く。** スプリント課題を閉じる条件は、本文の受け入れ条件の
番号のすべてに合格の行があることを見る。番号の無い行・行の無い番号があると、その課題は閉じない
（`progress-tracking` の「スプリントを閉じる」の閉じる条件 2）。`課題` の列の頭が課題の参照でない行は、
どの課題の判定にも使わない。課題を指す行が 1 行も無い表では、スプリント課題すべてが `開いたまま` になる。

**合否を読むのは課題の表だけである。** 課題の表は、見出しに `課題` と `結果` の両方の列を持つ表をいう。
ブロックの中の課題の表はすべて読み、2 つ以上あれば行を 1 つの表として合わせる（どれかの表に合格でない行がある
課題は合格でない）。`課題` と `結果` の列を持たない表（補足の表。例: 主なテストの実行の表）は、置く位置に依らず
どの判定にも使わない。課題の表が 1 つも無いと、スプリント課題すべてが `開いたまま` になる。
`対象のバージョン:` の行も、そのバージョンのブロックを選ぶ入力であるため省かない。

## モードごとの要否

要否を決めるのは `development-workflow` である。この Skill は判定結果を受け取って実行する。
呼ばれた時点で、この工程が要ると判定されている。

## スプリントを閉じる

**後に振り返りが続かない変更（振り返りを通らない `operation`）では、この工程がその実行の
最終工程である。** 検証結果を記録した後に、`progress-tracking` の「スプリントを閉じる」を
`--final-stage リリース後テスト` で行う。**手順・閉じる条件・閉じた後の順序はそこが SSOT で、ここにはコピーしない。**
振り返りを通る変更と、まとめのプランの `release-verify` のステップでは、課題を閉じない（振り返りの後に閉じる）。
閉じなかった課題は `開いたまま` になり、判定と理由が報告に載る。

## 関連

- `/ndf:quality-gates` — マージ前の検証の証跡
- `/ndf:release` — この工程の前に行うリリース。開始条件はその完了である
- `/ndf:retrospective` — この工程の後に行う振り返り
- `/ndf:progress-tracking` — 「スプリントを閉じる」の SSOT と、記録の置く場所
- `/ndf:backlog-refinement` — 蓄積した課題の棚卸し（工程表の最後の工程）
- `/ndf:out-of-scope` — 検証で見つけた範囲外の課題の起票
