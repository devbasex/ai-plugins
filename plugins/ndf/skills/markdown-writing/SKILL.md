# Markdown Writing Skill

読み手は**その場の会話・コードベース・検討過程を知らない第三者**（社外・レビュアー・将来の担当者）である、という前提で書く。

適用対象: 仕様書 / 設計書 / README / OpenAPI 説明 / PR タイトル・本文 / コミットメッセージ / 調査レポート / 実装プラン / レビューコメント。

## 重要ルール

### 1. 説明文に内部識別子・略語を持ち込まない

**テーブル名・カラム名・クラス名などの内部識別子や、その場で作った略語を、説明文の主語・目的語に使わない。**

「何のために」「何をやったか」を説明する文でこれらを使うと、読み手が識別子の意味を知っている前提になり、**書いた側は説明した気になり、読み手には何も伝わらない**。

| | 例 |
|---|---|
| ❌ Bad | `user_subscriptions` の `plan_id` を更新し、us と sp を再生成する |
| ✅ Good | 利用者の契約プランを変更し、請求明細を作り直す |
| ❌ Bad | lcr がないと provisional に fallback する |
| ✅ Good | 計算結果の控えが無い場合は、現在のマスタ値を参照する |

**識別子を書いてよい場所**（むしろ書くべき）:

- コードブロック・差分・スキーマ定義・SQL
- 「どこを直したか」の指し示し（`app/Services/Foo.php:120` / 変更ファイル一覧）
- 調査レポートのエビデンスブロック（クエリと実行結果）
- 用語を導入する目的で、業務用語に括弧書きで添える場合

**やること**:

- 説明は業務用語・日本語で書き、識別子は必要なら括弧で添える（例: 「請求明細（`billing_details`）」）
- 同じ文書で識別子を繰り返し使うなら、冒頭に**用語の対応表**を置き、本文は業務用語で通す
- 略語は初出で正式名称を併記する。会話中に作ったローカル略称は文書に持ち込まない
- プロジェクトに用語集（`terminology` skill、`docs/` の用語定義、UI ラベルの翻訳ファイル等）があれば、そこの表記に合わせる

### 2. 指す対象が文脈で変わる語に、この文書での意味を与える

**読み手が語自体は知っているが、指す対象が文脈によって変わる語**を、言い換えも定義もせずに使わない。

ルール 1 が「読み手が知らない語を使わない」ことを求めるのに対し、こちらは**読み手が別の意味で知っている語**を扱う。知らない語ではないため読み飛ばされ、**読み手は分かったつもりで先へ進み、別の対象を思い浮かべたまま作業する**。

| 対応 | 使う場面 |
|---|---|
| 一意な語へ言い換える | **既定。** 文書の主題を表す語がこれに当たる場合 |
| 初出で定義する | 言い換えると不自然になる場合、業界で定着した呼び方がある場合 |

**言い換えを既定とする理由。** 定義は読み飛ばされる。読み手が知っている語であるほど、定義を読まずに自分の解釈で読み進める。語そのものを一意にすれば、読み飛ばしても誤解が生じない。

| | 例 |
|---|---|
| ❌ Bad | スタックを 3 つ並列で起動する |
| ✅ Good | テスト環境を 3 つ並列で起動する |
| ❌ Bad | 環境ごとにモデルを切り替える |
| ✅ Good | 検証用と本番用で、呼び出す言語モデルを切り替える |

**やること**:

- 同じ文書の中で、1 つの語を 2 つ以上の意味に使わない
- 説明文で使う語と、コマンド名・設定のキー名を対応させる（説明を言い換えたら識別子も揃える）
- 定義を置く場合は、**用語表と初出の本文の両方**に置く。片方だけだと、読む順序によって定義に当たらない
- 語の一覧・出現数の閾値・候補が出たときの判断は [02-ambiguous-terms.md](02-ambiguous-terms.md) にある
- 適用するのは新しく書く文書と改訂する文書である。既存の文書を一括で直す必要はない

### 3. 検討過程の痕跡を残さない

作成者とその場の相談相手（AI との対話含む）だけに通じるラベルや言い回しは、第三者には意味不明なので本文に書かない。

- 検討時の選択肢ラベル（「案A / 案B」「Option A」「パターン1」などの符丁）
- 「今回の相談で」「壁打ちの結果」「先ほど決めた」など会話由来の指示語
- 不採用にした代替案との比較を、比較のためだけに残すこと

**やること**: 決まった内容を、ラベルなしで断定形で書く。「なぜそうするか」は理由として本質的なものだけを一般的な言葉で残す。

### 4. 変更履歴を本文に残さない

指摘を受けて直した場合でも、**修正の経緯そのもの**を本文に含めない。

- 「以前は X だったが、指摘を受けて Y に変更した」式の記述
- 「〜という誤りがあったため修正」「レビュー対応で追加」などの由来説明
- 不採用になった案の書きかけ

**やること**: 現時点で正しい確定情報だけを書く。変更理由・経緯はコミットメッセージ / PR 説明 / レビュー返信に置く（git 履歴に残るので本文で二重に持たない）。

- **stale 化防止**: 「以前は〜」式の履歴は、さらに変更が入ると二重に古くなる
- **責務分離**: 「何が正か」は文書、「なぜ変えたか」は git / PR

### 5. 敬意と節度のある表現で書く

文書は**関係者本人が読む**前提で書く。仕様・実装・レビュー・調査の対象には必ず書き手以外の
担当者がいる。**強い否定・過剰な装飾・根拠の曖昧な断定**は、いずれも内容より先に印象を作り、
**書かれた判断そのものの信頼性を下げる**。判断や事実は省かずに、語を選び直す。

| 種類 | ❌ Bad | ✅ Good |
|---|---|---|
| 強い否定 | 案 A は廃案 | 今回は非同期方式を採用する（理由: 送信量が上限を超えるため） |
| 強い否定 | 修正していただけていない | 該当箇所は現在も旧仕様のまま。次の PR で反映する |
| 強い否定 | この実装は間違っている | この実装は在庫 0 のとき負数を返す。期待値は 0 |
| 強い否定 | ドキュメントが不十分 | 手順 3 に前提条件を追記すると、初見でも再現できる |
| 過剰な装飾 | 劇的に性能が改善 | 一覧表示の応答が 1.8 秒から 0.4 秒になった |
| 過剰な装飾 | 完璧に動作する / 圧倒的に安全 | 受け入れ条件 5 件をすべて満たした |
| 曖昧な断定 | 明らかに影響はない | 呼び出し元 3 箇所を確認し、いずれもこの引数を渡していない |
| 曖昧な断定 | おそらく問題ないはず | 未確認。ステージングで手順 2 を実行して確認する |

**やること**:

- 評価は**人ではなく対象物**（コード・仕様・手順・データ）の振る舞いに向ける
- 不採用にした案は、否定語ではなく**採否と理由**として書く（比較のためだけに残さない点はルール 3 のとおり）
- 不足を指摘するときは、**現在の状態と、次にやると解決すること**をセットで書く
- 程度を表す語（劇的・大幅・圧倒的・完璧）は、**数値・条件・実測値**に置き換える。太字や感嘆符の多用も同じく印象で押す書き方になる
- 確認していないことは断定せず「未確認」と書く。断定するならルール 6 のエビデンスを添える

### 6. 否定的な結論にはエビデンスを添える

「存在しない」「呼ばれていない」「データがない」「影響がない」といった**否定的な結論**は、読み手が最も検証しづらく、外れたときの被害が大きい。**必ず実行結果を根拠として添える。**

| 主張 | 添えるエビデンス |
|---|---|
| カラム / テーブルが存在しない | スキーマ照会の実行結果 |
| データが存在しない | 件数クエリの実行結果 |
| どこからも呼ばれていない | 検索コマンドと結果（呼び出し元を辿った経路） |
| 影響範囲がない | 洗い出した対象の一覧と、それぞれの判定 |

やってはいけないこと:

- コードを読んだだけで「無い」と断定する
- エビデンスなしで残課題の優先度を下げる
- 一部だけ見て「他にはない」と判断する

確認しきれなかったことは、**「未確認・残リスク」として明示的に残す**。書かずに省くと「確認済み」と読まれる。

### 7. 個人情報・機密情報を書かない

文書・PR 本文・コミットメッセージ・添付ファイルに、実在の個人を特定できる情報や認証情報を含めない。コミットメッセージとマージ済み PR 本文は**後から消しにくく、履歴に残る**。

- 氏名（フルネーム）/ 電話番号 / メールアドレス / 住所 / 生年月日
- 個体を特定できる番号（車台番号、シリアル、口座番号など）
- 認証情報・トークン・接続文字列
- エクスポートしたままの実データ（CSV / XLSX / スクリーンショット）

**やること**: 主キー・管理番号・記号（「対象A」「①」）で参照する。実データが必要なら社内アクセス制限のある場所に置き、文書には URL とサマリだけ書く。

### 8. 図表作成ルール

図を入れると決めたら、**次の順で進める**。

1. **[01-diagram-guide.md](01-diagram-guide.md) を Read する。** 使ってよい形式と記法、横方向の
   要素数の上限（本文幅を超えると図が縮小され、文字が読めなくなる）はガイドだけが持っている。
   読まずに図種別と向きは決められない
2. ガイドの基準で図種別と向きを決める
3. 図を書く

本文で守る原則は 3 つ:

- 図は**インライン**で書く。図のソースが本文に残るため、差分でレビューでき、図と記述の乖離にも気づける
- 状態の対比（修正前 vs 後 / 期待 vs 実態 / 環境 A vs B）や定義の列挙は、図ではなく Markdown の**表**
- ディレクトリツリーは ASCII の罫線でよい。それ以外を ASCII ART で描かない

### 9. 文書の長さと分割ルール

| 行数 | 対応 |
|---------|-----|
| ~300行 | そのまま |
| 301~500行 | 内容によっては単一ファイルのままでよい（下記の判断基準） |
| 501行以上 | セクションごとに分割 |

300行を超えても、**分割すると読み手の理解が落ちる**場合は単一ファイルのままにする。

- 通しで読んで初めて意味が通る一連の説明（手順書、設計の導出過程）
- 分量の大半が表・コードブロックで、文章としての密度が低い
- 相互参照が多く、分割すると行ったり来たりが増える

逆に、独立して読める単位が明確にあるなら300行以下でも分割してよい。

**書式が 1 ファイルであることを前提にする文書は、この基準の対象外とする。**

| 例 | なぜ対象外か |
| --- | --- |
| 変更履歴（Keep a Changelog の `CHANGELOG.md`） | 最新の版が先頭にあり、版の見出しを上から辿れることが読み手の期待である。分割すると「最新の版で何が変わったか」を探す入口が増える |

**対象外にした文書は、行数の検査からも外す。** 外し忘れると、書き足すたびに継続的統合が
落ちる。外したことと理由は、検査の側の除外の一覧に書く。

**「長くなったら分けない」という意味ではない。** 際限なく伸びる文書は、書式が許す範囲で
古い部分を退避する。変更履歴なら、直近のメジャーを残して以前を別ファイルへ移し、末尾から
リンクする。**退避の時期はメジャーの区切りで決める**（行数で決めると、版を足した拍子に
退避が要るかどうかが変わる）。

**分割時のファイル名**: 順序prefix（01-, 02-, ...）+ ケバブケース

```
docs/feature-guide/
├── 01-introduction.md
├── 02-installation.md
└── 03-usage.md
```

## 書き終えたらセルフチェック

**識別子と略語の混入**（説明文の中に裸で出ていないか。コードブロック内のヒットは無視してよい）:

```bash
grep -nE '[a-z]+_[a-z0-9_]{2,}' <対象ファイル>
```

**検討痕跡・変更履歴の混入**（プロジェクトやその場の符丁に応じて語を足す）:

```bash
grep -nE '案 ?[A-Z]|Option ?[A-Z]|パターン[0-9]|今回|壁打ち|以前は|当初は|に変更|指摘を受け|レビュー対応|誤りのため' <対象ファイル>
```

**強い否定語の混入**（相手の不作為や案の否定を指す語）:

```bash
grep -nE '廃案|却下|無意味|不十分|不備|間違って|誤って|できていない|いただけていな|いただけません|考慮漏れ|すべきだった|放置' <対象ファイル>
```

**過剰な装飾語の混入**（程度を印象で示す語）:

```bash
grep -nE '劇的|圧倒的|完璧|万全|飛躍的|画期的|抜群|最強|非常に|極めて|大幅|かなり|絶対に' <対象ファイル>
```

**根拠の曖昧な断定の混入**（確認と推測が混ざる語）:

```bash
grep -nE '明らかに|当然|言うまでもな|のはず|はずで|はずだ|と思われ|おそらく|恐らく|一般的に|に違いない|問題ないと' <対象ファイル>
```

**多義語の混入**（指す対象が文脈で変わる語。同一ファイル内で 5 回以上出た語だけを候補にする。
一覧と閾値の根拠は [02-ambiguous-terms.md](02-ambiguous-terms.md)）:

```bash
FILE=<対象ファイル>
for w in 環境 エージェント コンテナ モデル セッション タスク トークン ポリシー サービス リソース ジョブ スタック; do
  n=$(grep -o "$w" "$FILE" | wc -l)
  if [ "$n" -ge 5 ]; then echo "$w: $n 回"; fi
done
```

複合語（「環境変数」など）も 1 件として数える。候補が出たら内訳を確認し、複合語で指す対象が
一意に決まる箇所は書き換えない。

ヒットしたら、業務用語での説明・最終確定形の記述へ置き換える。強い否定語は対象物の状態と
次の一手へ、装飾語は数値・条件へ、曖昧な断定はエビデンス付きの事実か「未確認」へ書き換える。
多義語は一意な語へ言い換えるか、用語表と初出の本文の両方へ定義を置く。

ヒットは**確認の候補**であって、書き換えの確定ではない。不具合レポートで事象を事実として
述べる場合など、その語が正確な記述である行はそのまま残す。

## チェックリスト

- [ ] 説明文がテーブル名 / カラム名 / ローカル略語ではなく業務用語で書かれている
- [ ] 略語は初出で正式名称を併記している
- [ ] 指す対象が文脈で変わる語について、言い換え・定義・そのままでよい理由のいずれかを確認している
- [ ] 同じ文書の中で、1 つの語を 2 つ以上の意味に使っていない
- [ ] 検討過程のラベル（案A / Option A 等）と会話由来の指示語が残っていない
- [ ] 「以前は〜だったが変更した」式の経緯が本文に残っていない
- [ ] 強い否定語ではなく、対象物の状態と次にやることで書かれている
- [ ] 不採用の案が、否定ではなく採否と理由として書かれている
- [ ] 程度を表す装飾語が、数値・条件・実測値に置き換わっている
- [ ] 断定にはエビデンスがあり、確認していないことは「未確認」と書かれている
- [ ] 否定的な結論に実行結果のエビデンスが添えられている
- [ ] 未確認事項が「残リスク」として明示されている
- [ ] 個人情報・認証情報・実データが含まれていない
- [ ] 図を書く前に `01-diagram-guide.md` を読んだ
- [ ] 図はインラインで書いている（ディレクトリツリーはASCIIでよい）
- [ ] 図の向きと横方向の要素数がガイドの上限に収まっている
- [ ] plantUML / HTML / インライン`<svg>` を使っていない
- [ ] ファイル長は300行以内（301~500行は内容次第で可、501行以上は分割）
- [ ] 分割時は順序prefix使用（01-, 02-, ...）
