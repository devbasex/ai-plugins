# 読み手へ渡す文書の受け入れ条件

**`documentation` モードで読む。** 動く対象が無いため、受け入れ条件の形が変わる。

## 3 つを先に決める

| 決めること | 何を書くか | 決めないと何が起きるか |
| --- | --- | --- |
| 読み手 | **誰が読むか。** 役割と、その人が持っている前提知識 | 一般論から書き始め、読み手が自分の話として読まない |
| 目的 | **読み手が読み終えた後にどうなるか** | 何を載せるかが決まらず、載せられるものを全部載せる |
| 読み手に求める判断 | **採否 / 承認 / 理解 / 操作のどれか** | 文書タイプが決まらない |

**この 3 つがタイプの判定の入力になる**（`development-workflow` の
`references/document-types.md`）。

## 観測できる形へ言い換える

**「分かりやすい資料」は条件にならない。** 読み手の行動で書く。

| 依頼文の語 | 観測できる形 |
| --- | --- |
| 分かりやすくする | 読み手が**その場で採否を決められる**（決めるための値がすべて載っている） |
| 説得力のある | 主張ごとに**出典を持つ数値**が添えられている |
| ボリュームを抑える | **1 枚あたりの主張が 1 つ**で、全体が N 枚に収まる |
| きれいな見た目 | 版面の条件は**体裁設計**が持つ（`design` の `layout-<出力の形>.md`） |

## 受け入れ条件の例

```markdown
- [ ] 条件 1: 読み手（先方の事業責任者）が、費用・期間・体制の 3 つを冒頭 1 画面で読める
- [ ] 条件 2: 実績として書いた数値がすべて出典を持つ（出典の節の 4 項目が埋まっている）
- [ ] 条件 3: 「決めてほしいこと」の節があり、読み手が答える問いが 1 つに絞られている
- [ ] 条件 4: 触れない範囲（今回の提案に含まない領域）が明記されている
```

**「触れない範囲」を条件に入れる。** 書かないことを決めておかないと、レビューで
「これも載せるべきでは」が出るたびに範囲が広がる。

## 対象範囲の書き方

含むものと含まないものを対にする。**文書では「含まない」が特に効く**（載せられるものは
いくらでもあるため）。
