# 受け入れ条件の書き方

受け入れ条件は、**実装が終わったかどうかを他人が判定できる文**である。判定できない文は
受け入れ条件ではない。

## 満たすべき 3 つの性質

| 性質 | 意味 | 反例 |
| --- | --- | --- |
| 観測可能 | 出力・状態・記録のどれかを見れば判定できる | 「設計がきれいになる」 |
| 一意 | 読み手が違っても同じ判定になる | 「レスポンスが十分速い」 |
| テスト可能 | 手順またはコマンドで再現できる | 「本番でも問題なく動く」 |

## 形式

2 つの形式を使う。どちらでもよいが、1 つの変更の中では揃える。

### 条件と観測を対にする形式

```markdown
- [ ] 未ログインで `/orders` を開くと、`/login` へ 302 で遷移する
- [ ] 期限切れトークンで API を呼ぶと、401 と `{"error": "token_expired"}` が返る
- [ ] 一覧は既定で更新日時の降順に並ぶ
```

### 前提・操作・結果に分ける形式

振る舞いに前提条件が絡む場合はこちらを使う。

```markdown
- [ ] 前提: 下書きの記事が 1 件ある
      操作: 公開ボタンを押す
      結果: 記事の状態が `published` になり、公開日時に操作時刻が入る
```

## 書き換えの例

| 受け入れ条件になっていない文 | 書き換え |
| --- | --- |
| 検索を速くする | 1 万件のデータで、検索 API の応答が 1 秒以内に収まる |
| バリデーションを追加する | 数量に 0 以下を入れて送信すると、保存されず「1 以上を入力してください」が表示される |
| エラー処理を入れる | 外部 API が 500 を返したとき、注文は作られず、警告ログに注文 ID が残る |
| 権限を見る | 閲覧権限のない利用者が詳細を開くと 403 になり、他人のデータが応答本文に含まれない |
| リファクタリングする | 変更前後で既存テストがすべて通り、公開インタフェースの入出力が変わらない |

## 非機能の条件

条件を書かないと実装後に基準が作られる。軸は 6 大項目である。

| 大項目 | 何を決めるか |
| --- | --- |
| 可用性 | 運転時間、復旧の時間、停止の許容、冗長化 |
| 性能・拡張性 | 応答時間、容量、処理量、増加への備え |
| 運用・保守性 | 記録、監視、保存、障害時の切り分け |
| 移行性 | 移す対象、順序、切り戻し、並走 |
| セキュリティ | 権限、認証、通信と保存の保護、秘密情報 |
| システム環境 | 動作環境、依存する実行基盤、資源の制約 |

**該当しない項目は書かない。** 触らない項目へ条件を求めると、空欄か「特になし」で埋まり、
書き忘れと意図的な省略を読み手が区別できなくなる。

書き方・例・該当の判定は
[nonfunctional-requirements.md](nonfunctional-requirements.md) にある。

## 境界と異常系を条件に含める

正常系だけの受け入れ条件は、実装後に必ず穴が見つかる。**変更が扱う入力の境界**を条件へ
入れる。

- 空・0 件・1 件・上限・上限 + 1
- 重複・順序が入れ替わった入力
- 権限がない、対象が存在しない、すでに処理済み
- 外部依存が失敗する（タイムアウト・エラー応答）

すべてを書く必要はない。**その変更で判断が分かれる境界**だけを書く。

## 満たさないことを条件にする

「起きてはいけないこと」も条件になる。退行を防ぐ条件はここに書く。

```markdown
- [ ] 既存の公開 API のレスポンス項目が削られていない
- [ ] 移行後も既存の URL が同じ画面を返す
- [ ] 個人情報がログへ出力されない
```

## 受け入れ条件とテストの対応

受け入れ条件は、そのままテストの名前になる粒度で書く。1 条件に複数の判定を詰め込むと、
どの判定が失敗したのかが分からなくなる。

```markdown
❌ 一覧が正しく表示され、絞り込みと並び替えも動作する
✅ 一覧は更新日時の降順で並ぶ
✅ 状態で絞り込むと、選んだ状態の項目だけが残る
```

対応するテストが書けない条件は、観測可能になっていない可能性が高い。書けない理由が
「テスト環境がない」場合は、確認手順（誰が何を見て判定するか）を条件のそばに書く。
