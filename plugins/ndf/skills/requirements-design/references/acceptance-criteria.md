# 受け入れ条件の書き方

受け入れ条件は、**実装が終わったかどうかを他人が判定できる文**である。判定できない文は
受け入れ条件ではない。

## 満たすべき 3 つの性質

| 性質 | 意味 | 反例 |
| --- | --- | --- |
| 観測可能 | 出力・状態・記録のどれかを見れば判定できる | 「設計がきれいになる」 |
| 一意 | 読み手が違っても同じ判定になる | 「レスポンスが十分速い」 |
| テスト可能 | 手順またはコマンドで再現できる | 「本番でも問題なく動く」 |

## 形式

2 つの形式を使う。どちらでもよいが、1 つの変更の中では揃える。

### 条件と観測を対にする形式

```markdown
- [ ] 未ログインで `/orders` を開くと、`/login` へ 302 で遷移する
- [ ] 期限切れトークンで API を呼ぶと、401 と `{"error": "token_expired"}` が返る
- [ ] 一覧は既定で更新日時の降順に並ぶ
```

### 前提・操作・結果に分ける形式

振る舞いに前提条件が絡む場合はこちらを使う。

```markdown
- [ ] 前提: 下書きの記事が 1 件ある
      操作: 公開ボタンを押す
      結果: 記事の状態が `published` になり、公開日時に操作時刻が入る
```

## 書き換えの例

| 受け入れ条件になっていない文 | 書き換え |
| --- | --- |
| 検索を速くする | 1 万件のデータで、検索 API の応答が 1 秒以内に収まる |
| バリデーションを追加する | 数量に 0 以下を入れて送信すると、保存されず「1 以上を入力してください」が表示される |
| エラー処理を入れる | 外部 API が 500 を返したとき、注文は作られず、警告ログに注文 ID が残る |
| 権限を見る | 閲覧権限のない利用者が詳細を開くと 403 になり、他人のデータが応答本文に含まれない |
| リファクタリングする | 変更前後で既存テストがすべて通り、公開インタフェースの入出力が変わらない |

## 非機能の条件

条件を書かないと実装後に基準が作られる。軸は 6 大項目である。

| 大項目 | 何を決めるか |
| --- | --- |
| 可用性 | 運転時間、復旧の時間、停止の許容、冗長化 |
| 性能・拡張性 | 応答時間、容量、処理量、増加への備え |
| 運用・保守性 | 記録、監視、保存、障害時の切り分け |
| 移行性 | 移す対象、順序、切り戻し、並走 |
| セキュリティ | 権限、認証、通信と保存の保護、秘密情報 |
| システム環境 | 動作環境、依存する実行基盤、資源の制約 |

**該当しない項目は書かない。** 触らない項目へ条件を求めると、空欄か「特になし」で埋まり、
書き忘れと意図的な省略を読み手が区別できなくなる。

書き方・例・該当の判定は
[nonfunctional-requirements.md](nonfunctional-requirements.md) にある。

## 境界と異常系を条件に含める

正常系だけの受け入れ条件は、実装後に必ず穴が見つかる。**変更が扱う入力の境界**を条件へ
入れる。

- 空・0 件・1 件・上限・上限 + 1
- 重複・順序が入れ替わった入力
- 権限がない、対象が存在しない、すでに処理済み
- 外部依存が失敗する（タイムアウト・エラー応答）

すべてを書く必要はない。**その変更で判断が分かれる境界**だけを書く。

## 満たさないことを条件にする

「起きてはいけないこと」も条件になる。退行を防ぐ条件はここに書く。

```markdown
- [ ] 既存の公開 API のレスポンス項目が削られていない
- [ ] 移行後も既存の URL が同じ画面を返す
- [ ] 個人情報がログへ出力されない
```

**退行しない条件は、前提にした今の振る舞いを書く前に 1 度実行して確かめる。** 「今と同じく〜する」は、
今の振る舞いが本当にそうであることを前提にしている。前提が事実と違うと、条件はリリース後テストで初めて崩れる
（例: 「収束しないときは止まる」と書いたが、`final` が `max_rounds` のときは変更前から止まらなかった）。
確かめた手段（実行したコマンドかテストの名前）とその結果を、条件のそばか課題の本文に書く。

```markdown
- [ ] 区分の記録が無い課題では、今と同じくマーカーの無い条件がすべて載る（退行しない）
      前提の確認: `pytest tests/test_release_materials.py -k unverified` → マーカーの無い 3 件が載る（10.27.3）
```

前提が事実と違ったら、条件を今の振る舞いに合わせて書き直すか、違いを別の課題にする。

## 受け入れ条件とテストの対応

受け入れ条件は、そのままテストの名前になる粒度で書く。1 条件に複数の判定を詰め込むと、
どの判定が失敗したのかが分からなくなる。

```markdown
❌ 一覧が正しく表示され、絞り込みと並び替えも動作する
✅ 一覧は更新日時の降順で並ぶ
✅ 状態で絞り込むと、選んだ状態の項目だけが残る
```

対応するテストが書けない条件は、観測可能になっていない可能性が高い。書けない理由が
「テスト環境がない」場合は、確認手順（誰が何を見て判定するか）を条件のそばに書く。

## 「人が見る」条件は振る舞いと見た目に分ける

**「人が実際の端末（画面）で〜を見る」という条件は、振る舞いと見た目の 2 つに分けて書く。**
振る舞い（キーを打つと効くか・出力が変わるか）は、擬似端末（`script` / `expect` / pty）や使い捨ての
環境で機械が確かめられる。人にしか見られないのは、実際の端末エミュレータや画面での描かれ方だけである。
1 つの条件にまとめると、機械で確かめられる振る舞いまで人の確認として残り、マージの後へ回る。

```markdown
❌ 人が実際の端末で `tmux-menu` を打ち、一覧 → メニュー → `a` が効くことを見る
✅ 擬似端末に attach したクライアントへ `tmux-menu` と `a` を打つと、選んだセッションへ切り替わる
✅ 人が実際の端末エミュレータで、メニューのスロットと選択中の行が崩れずに描かれることを見る
```

振る舞いの条件はマージ前に確かめる（`quality-gates` の「受け入れ条件との対応」）。

## リリース後の確認の計画

**リリース後に確かめる条件があるときは、条件ごとに経路を動かすバージョンと確かめる時点を、仕様の
`## リリース後の確認の計画` に書く**（[spec-template.md](spec-template.md)）。次のリリースまで確かめられない経路を、
計画の時点で見分けるためである。見分けないと、リリース後テストと承認資料が、まだ動かせない経路を今回の実施予定として扱う。

| 列 | 書くこと |
| --- | --- |
| 条件 | 受け入れ条件番号で始める（例: `2. 11.0.8 から次のバージョンへ更新できる`）。番号は課題本文の `## 受け入れ条件` のチェックボックスの行を上から数えた順（1 から）で、`release-verification` は番号で照合する。番号の後ろは条件の要約でよい |
| 経路を動かすバージョン | `配ったバージョン` か `利用者の手元の旧いバージョン`。リリース後に確かめる経路を実際に動かすコードのバージョンである |
| 確かめる時点 | `このリリースの後` か `次のリリースの後` |

**`次のリリースの後` にするのは、確かめる処理が今回のバージョンで初めて入り、今回のバージョンが動いている状態から
（今回のバージョンを更新元として）動かして初めて確かめられる行だけである。** それが保留の理由になる。
旧いバージョンが経路を動かすことだけでは次へ回さない。旧いバージョンが既に同じ処理を持つなら、旧いバージョンから
今回のバージョンへの経路はこのリリースの後に確かめられる。

| | 変更の例 | 確かめる時点 |
| --- | --- | --- |
| 当たる | 更新の処理・ラッパー・hook など、利用者の手元で動いているコードが新しいバージョンを取りに行く経路を、今回のバージョンで初めて足す・作り直す（例: 11.0.7 のラッパーは更新の処理を持たず、11.0.8 で初めて入った処理は 11.0.8 から次のバージョンへ上げるときに初めて動く） | `次のリリースの後` |
| 当たらない | 旧いバージョンが既に同じ処理を持つ（例: 旧いバージョンの更新の処理で、今回のバージョンへ上げる） | `このリリースの後` |

**この書き落としは検査で止めない。** どの変更が届け方を変えるかは差分の語やファイルの名前から機械では見分けられず、
検査を置くと誤検知か見逃しが出る。要求を書く担い手が書き、設計承認ゲートとリリース承認ゲートで人が見る。

### 受け入れ条件を編集したとき

番号は課題本文のチェックボックスの順なので、チェックボックスを足す・消す・並べ替えると、計画表の番号が別の条件を指す。
例えば保留にした条件 2 の前に条件を 1 つ挿入すると、古い計画表のままでは `release-verification` が新しい条件 2（挿入した条件）を
保留にし、保留にすべき条件（新しい条件 3）を確かめに行く。

- **受け入れ条件のチェックボックスを足す・消す・並べ替える編集は、同じ編集の中で計画表の `条件` 列の番号を付け直す。**
  番号の後ろの要約は残すので、付け直しの前後で番号と要約の対応を見比べられる
- **承認するときは、計画表の各行の番号が指す課題本文の条件と、行の要約が同じ条件かを確かめる。** 設計承認ゲートで要求を見るとき、
  リリース承認ゲートで承認資料の「未実施のリリース後テスト」を見るときの両方で行う（`quality-gates` の「受け入れ条件との対応」）
