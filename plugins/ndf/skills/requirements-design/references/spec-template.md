# 要求仕様のテンプレート

要求仕様は、「何を満たすか」を書く文書である。解き方、タスクの分け方、触るファイルは書かない（それぞれ設計と実装計画が持つ）。読み手は [文書の書き方・直し方の基準](../../../contracts/data/writing-criteria.md) の「1. 読み手を想定する」の表で決める。読み手が下す判断は「この問題を、この受け入れ条件で解いてよいか」である。

いちばん大事なのは「なぜやるのか」である。何が起きて誰が困り、放置すると何が続き、何のために変えるのかを、読み手が納得できるまで書く。欄の中身が重なるときも、理由は削らない。

下の本体を課題の本文に書く。課題の題は `<対象>: <何ができるようになるか>（#<番号>）` の形にする。

- 書き方: [SKILL.md](../SKILL.md) の「手順」。受け入れ条件は [acceptance-criteria.md](acceptance-criteria.md)
- どの文書にも当たる決まり（記入欄の読み方・当たらない欄の扱いなど）と、見出しの順: [document-roles.md](document-roles.md)

```markdown
## 何が起きたか

（必ず書く）いつ・誰が・何をしていて・何が起き、誰がどう困ったかを、その機能を初めて見る人が分かる場面として書く。この変更を始めるきっかけになる。利用者の補足があれば添える。

## 種類

（必ず書く）1 行目に変更の種類（新規作成 / 機能追加 / 不具合）を書く。調査・運用の課題は、代わりに「調査」か「運用」と書く。続けて括弧で、そう決めた理由を 1 行で書く。

## 今の姿

（当たるときだけ: 機能追加か不具合）その機能が何のためにあり、今どう動いているかを短く書き、その事実を決めている文書やコードへのリンクを添える。不具合では、期待する結果の根拠になる約束もここで示す。

## 今はどうしているか

（当たるときだけ: 新規作成）今は手作業・別の手段・何も無い、のどれで済ませているかを書く。「今の姿」は置かない。

## 誰が・どんな場面で困るか

（当たるときだけ: 新規作成）困る人と場面を 1 行に 1 つ書く。

| 誰が | どんな場面で | 何に困るか |
| --- | --- | --- |
| <誰が> | <場面> | <困ること> |

## 何を足すか・変えるか

（当たるときだけ: 機能追加）変わる点を、今と足した後を並べて書く。

| | 今 | 足した後 |
| --- | --- | --- |
| <変わる点> | <今の動き> | <足した後の動き> |

## 今の利用者への影響と互換

（当たるときだけ: 機能追加で、今の使い方が変わる・読まなくなる入力がある・返りが変わる）誰の何が変わるかを書く。

## 事象

（当たるときだけ: 不具合か、課題のラベルがこの項目を必須とする）観測した結果を、コマンドと出力・終了コード・画面のとおりに書く。

## 期待する結果

（当たるときだけ: 不具合か、課題のラベルがこの項目を必須とする）本来の振る舞いを 1〜2 行で書く。根拠は「今の姿」で示す。

## 再現手順

（当たるときだけ: 不具合か、課題のラベルがこの項目を必須とする）打った手順と、その前の状態を書く。再現しないときは頻度と「再現しない」を書く。

## 環境

（当たるときだけ: 不具合か、課題のラベルがこの項目を必須とする）確かめたバージョン（バージョン番号かコミット）・実行した環境・OS を書く。

## なぜ困るか

（必ず書く）なぜこの変更が要るのかを書く。放置すると、誰に何が起き続けるか、何ができないままになるか。「不便だから」で終えず、起きる損失や手間を具体的に書く。

## 目的

（必ず書く）何のための変更か、その状態になるとなぜよいのかを、達成したい状態と一緒に書く。手段（何を作るか）だけを書かない。

- <達成したい状態>（<そうしたい理由>）

## 対象範囲

（必ず書く）扱うものと扱わないものを対にして書く。扱わないものには、扱わない理由を添える。

含む:
- <この変更で扱うもの>

含まない:
- <扱わないもの>（<扱わない理由>）

## 前提

（当たるときだけ: 受け入れ条件が参照する前提がある）決められない点を、後から正しかったかを判定できる文で書く。

- 前提 1: <前提>

## 受け入れ条件

（必ず書く）満たせば完了と言える条件を 1 行に 1 つ書く。観察でき、読み方が 1 つで、確かめられる文にする。起きてはいけないことと、壊してはいけない今の動きも条件にする。形は acceptance-criteria.md。

- [ ] 1. <条件>
- [ ] 2. <条件>
- [ ] 3. <起きてはいけないこと・壊してはいけないこと>

## 非機能の条件

（当たるときだけ: 速さ・止まらないこと・安全性などの条件がある）当たる大項目の行だけを残して書く。判定と書き方は nonfunctional-requirements.md。

| 大項目 | 条件 |
| --- | --- |
| 可用性 | <条件> |
| 性能・拡張性 | <条件> |
| 運用・保守性 | <条件> |
| 移行性 | <条件> |
| セキュリティ | <条件> |
| システム環境 | <条件> |

## 影響

（必ず書く）この変更が及ぶ先を書く。「重さ」の行は不具合のときだけ残す。公開インタフェースは外から使う人やプログラムとの約束（コマンド・API・画面の操作など）で、互換を保つ手段を持たないときは `互換なし` と書く。

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | <変わる / 変わらない。変わる場合は互換の扱い> |
| 重さ | <誰の何が止まる・誤るか。回避の手段があればそれも> |
| データ | <データの形の変更・移行の有無> |
| 既存の振る舞い | <変わる場所> |

## 用語

（当たるときだけ: リクエストの文と実装で呼び方が違う、または業務の固有の語がある）語と意味を書く。用語集に無い語は、用語集にも足す（glossary-format.md）。

| 用語 | 意味 |
| --- | --- |
| <語> | <意味> |

## ドメインイベント

（当たるときだけ: モードが `standard` で、起きる出来事を書き出した）業務で起きる出来事を時間の順に書く。書き出し方は SKILL.md の手順 3a。

| # | イベント | 引き金 | 失敗したとき | 順序の前提 |
| --- | --- | --- | --- | --- |
| E1 | <過去形で書く。例: 注文を確定した> | <何が起動するか> | <失敗の経路> | <先に起きている必要のあるイベント。無ければ —> |

## 検証手段

（必ず書く）受け入れ条件を何で確かめるかを書き、当たらない行は消す。自動で確かめられない条件は手動確認に書く。マージの前に確かめなければならない確認だけを「手動確認（マージ前）」の行にし、項目名は変えない。

| 項目 | 手段 |
| --- | --- |
| 起動 | <コマンド> |
| テスト | <コマンド> |
| 静的解析・型検査 | <コマンド> |
| 手動確認 | <誰が何を見て判定するか。リリース後に確かめる> |
| 手動確認（マージ前） | <マージの前に誰が何を見て判定するか> |

## リリース後の確認の計画

（当たるときだけ: リリース後に確かめる条件がある）条件ごとに、確かめるときに動くバージョンと時点を書く。書き方は acceptance-criteria.md の「リリース後の確認の計画」。

| 条件 | 経路を動かすバージョン | 確かめる時点 |
| --- | --- | --- |
| <受け入れ条件番号で始める。例: `2. 11.0.8 から次のバージョンへ更新できる`> | <`配ったバージョン` / `利用者の手元の旧いバージョン`> | <`このリリースの後` / `次のリリースの後`> |

## 前提とする取り決め

（当たるときだけ: この変更が従う取り決めがある）プロジェクトの記録（`AGENTS.md`・`README`・設定ファイル）にあるものは参照先を、無いものは新たに決めた内容を書く。守る規則だけを書き、対象ファイルは並べない。

| 項目 | 参照先 / 決めたこと |
| --- | --- |
| プロジェクト構造 | <変更を置く場所と、置いてはいけない場所> |
| コーディング規約 | <従う規約と、その確かめ方> |
| テスト戦略 | <どの階層のテストで何を確かめるか> |

## 境界

（当たるときだけ: 作業中に勝手に行ってよいこととよくないことを分ける必要がある）区分ごとに書く。

| 区分 | 内容 |
| --- | --- |
| 常に行う | <内容> |
| 確認してから行う | <内容> |
| 行わない | <内容> |

## 方針の分け方

（当たるときだけ: リクエストに運用の方針（ブランチの運用・リリースの形など）が含まれる）このリポジトリの設定に置くものと、作るものの動きを分けて書く。

| 方針 | このリポジトリの運用の決まり（設定の値） | 作るものの振る舞い |
| --- | --- | --- |
| <リクエストの方針> | <置く設定のファイルとキーと値。無ければ —> | <作るもので変わること。変わらなければ —> |

## 未決

（当たるときだけ: 決まっていないことがある）決まっていないことと、誰がいつまでに決めるかを書く。

| 項目 | 誰が決めるか | 期限 |
| --- | --- | --- |
| <項目> | <決める人> | <期限> |

## 起票者の推定

（当たるときだけ: 題か本文に、利用者の指示の原文に無く、起票した人が推して足した条件がある）利用者の決定と混ぜずに、1 行に 1 条件で書く。

| # | 条件 | 推した出所 | この要求での扱い |
| --- | --- | --- | --- |
| S1 | <条件> | <ファイルと行・PR・会話など> | <受け入れ条件 N / 前提 N / 含まない / 採らない> |

## リクエスト（原文）

（必ず書く）リクエストの文を要約せずに引用し、書き手と日付を添える。書き手が利用者でない文は、利用者の指示の原文として扱わない。長いときは `<details>` で畳んでよい。

> <リクエストの文>

（書き手: <利用者 / AI の起動指示 / 起票者 / 不明>、日付: <YYYY-MM-DD>）
```
