# 仕様のテンプレート

**正は課題の本文である。** このテンプレートで本文を書き、`standard` では本文から `issues/` に仕様のコピーを作る
（`SKILL.md` の手順 7）。

「何を満たすか」だけを書く。タスク分解・対象ファイル・実装順序は書かない（それらは
`implementation-plan` の担当）。解き方も書かない（`design` の担当）。同じ変更で計画も作る場合は、同一ファイルの別のセクションにする。

読み手は承認する人で、その機能を初めて見る。読み手が「この問題を、この終わりの条件で解いてよいか」を判断できる順に並べる。
読み手・判断・セクションの順序と、変更の種類ごとの中心のセクションは [document-roles.md](document-roles.md)（文書の役割の表）が決める。
このテンプレートはその順で見出しを並べたもので、順序の理由は表にある。

## 書く前に決めること

1. **変更の種類を決める。** 新規作成・機能追加・不具合のどれか 1 つを選び、「種類」のセクションの 1 行目に書く。不具合と機能追加の境目は、要求が満たそうとする約束が今の SSOT にあるかで決める（[document-roles.md の「変更の種類の決め方」](document-roles.md#変更の種類の決め方)）。Issue の種類が調査・運用の課題は変更の種類に入らないので、「種類」に Issue の種類を書き、種類ごとの中心のセクションを置かずに書く
2. **Issue の種類のラベルを 1 つ付ける。** Issue の種類（不具合・機能・調査・運用）は変更の種類とは別の軸で、ラベルは変更の種類に合わせて変えない。ラベルの名前は、プロジェクトの記載項目の定義（`.ndf/issue-items.json`）に `kind_labels` があればそこに書かれた名前を使い、無い種類は既定の名前（`bug`・`enhancement`・`investigation`・`operation`）を使う。定義があれば、セクションの名前と書く水準はそちらを使う
3. **ラベルが必須とする項目を、変更の種類によらず書く。** 記載項目の必須は Issue の種類（ラベル）で決まる（[ndf-issue-items.md](../../../../../docs/specifications/ndf-issue-items.md) の区分の表）。変更の種類の順に無い必須の項目は、種類ごとの中心のセクションの後ろ・「なぜ困るか」の前に、記載項目の定義の順で置く。中身は中心のセクションと重ねず、事象はコマンドと出力、期待する結果は本来の振る舞いを 1〜2 行で書く（例: ラベル `bug` の機能追加は、「何を足すか・変えるか」の後ろに事象・期待する結果・再現手順・環境を置く）

## 書く水準

- 各セクションに **必ず書く** か **当たるときだけ** を付けてある。種類ごとの中心のセクションは、その変更の種類のときに必ず書き、ほかの種類では置かない
- **当たらないセクションは見出しごと消す。** 「無し」「該当なし」と書いて残さない。空の見出しも残さない
- **「リクエスト（原文）」のセクションは、書き手が書くセクションの一番最後に置く。** 読み手が先に読むのは要求の全体像で、原文はその根拠として後から当たるものだからである。後ろに置いてよいのは、起票の後に工程が足すセクション（進行・承認ゲートの回答・閉じた理由など）だけである

## 書くときの注意

- **前の文書にある事実を写さない。** SSOT（手順書・コントラクト・過去の課題）にある事実はリンクで指し、「今の姿」には読み手が要る分だけを短く書く
- **識別子だけで文を作らない。** 規則の番号・キーの名前などは、普通の言葉の後ろに括弧で添える
- **原文の引用を省かない。** 要約だけを残すと、解釈のずれに後から気づけない
- **運用の方針を作るものの仕様として書かない。** リクエストの「このリポジトリは〇〇の運用にする」は、そのリポジトリの設定の値として「方針の分け方」の左の列に置く。作るものの振る舞いが変わるときだけ右の列に書く
- **起票者の推定を利用者の決定と混ぜない。** 書き手が利用者でない条件は「起票者の推定」のセクションに置き、設計承認ゲートで確かめる（`SKILL.md` の手順 1a）
- **受け入れ条件を終わりの条件の中心に置く。** 目的や背景を長く書いても完了判定には使えない
- **未決を空欄で放置しない。** 決まっていないこと自体を書き、誰が決めるかを添える
- **手動確認の時期は項目名で分ける。** 項目が `手動確認（マージ前）` の行だけが、PR 本文の「手動確認」のセクションにチェックボックスで並び、マーカーが付くまでマージの前で止まる。`手動確認` の行は「リリース後テストへ回す」と載り、マージを止めない
- 実装中に条件が変わったら、消さずに変更履歴として残す（`SKILL.md` の該当節を参照）
