# 並列の計画を作る

1 つのリポジトリで複数の開発ループかスプリントを同時に進めるときに、**並列の計画**を 1 度書く。並列の計画は
レーンの一覧と、レーンに共通の決まりを 1 つの文書に持つ。オーガナイザー（`--parallel <計画名>` で起動した conductor）が
これを読んでレーンを起動する。起動の手順は [development-workflow の parallel.md](../../development-workflow/references/parallel.md) にある。

## 例

3 本の開発ループ `lroot`・`lflow` と、`lflow` が終わってから始めるスプリント 1 本（課題 2400）を同時に進める。

```bash
python3 "$NDF_SCRIPTS/parallel.py" init p1 <<'EOF'
{"version": 1, "rules": ["取り込みの衝突は base-sync で解く"],
 "lanes": [
  {"name": "lroot", "input": {"kind": "loop", "loop": "lroot", "args": ["--milestones", "26"]}, "plans": 2, "touches": ["plugins/ndf/"]},
  {"name": "lflow", "input": {"kind": "loop", "loop": "lflow", "args": ["--milestones", "23"]}, "plans": 2, "touches": ["docs/"]},
  {"name": "lfac", "input": {"kind": "sprint", "issues": [2400]}, "plans": 2, "touches": ["web/"], "after": ["lflow"]}
 ]}
EOF
```

`init` は検査を通った下書きから、メインディレクトリの `.ndf/parallel/p1/plan.json`（計画の入力）・`plan.md`（人が読む描画）と、
レーンの数だけの引継ぎ文書（`.ndf/handoff/loop-lroot.md`・`loop-lflow.md`・`issue-2400.md`）を書く。
どれもコミットしない。

計画の状態の正本は、`start` が作る計画の進行表（レーンの配列・上限・答えていない依頼。オーガナイザーが書く）と、レーンごとの
レーンの進行表（スプリントの順番表。最初の行は `input`。レーンの側が書く）である。置き場は工程の進行表と同じ DB（環境変数
`NDF_PROGRESS_DB`。無ければチェックアウトの状態の置き場の SQLite）。`lane add`・`set` は書く前に計画の決まり（触る場所の重なり・
`after` の輪・上限）で判定し、断れば何も書かない。計画の台帳はメッセージの記録だけを持つ。

## レーンごとに決めること

| 項目 | 意味 |
| --- | --- |
| `name` | レーン名。ラッパーの名前になる（英小文字・数字・`-`・`_`、32 字まで。`-rel` と数字で終わる名前は一時レーンの名前のため使えない）。名前に役割を含めない（`lane1` など）。名前は答え待ちの停止・再開の印・依頼の持ち主のキーで、途中で変えられない。役割は `input` と `plan.md` で読む |
| `repo` | 任意。レーンのリポジトリのメインディレクトリ（絶対パス）。計画の置き場と違うリポジトリのレーン（別のリポジトリのレーン）にするときだけ書く。省くと計画の置き場のリポジトリ。worktree・存在しないパスは検査の規則 `I20` で断る |
| `input` | 最初の入力。`{"kind": "loop", "loop": <ループ名>, "args": [...]}` か `{"kind": "sprint", "issues": [<番号>...]}`。スプリントのレーンには課題のまとまり（`bundles`。次の節）を書ける |
| `plans` | 同時に流すプランの本数（1 以上） |
| `touches` | 触る場所（パスか glob） |
| `after` | 始める条件。ここに並べたレーンがすべて止まってから起動する |
| `handoff` | 任意。引継ぎ文書の名（既定はループなら `loop-<ループ名>`、スプリントなら `issue-<最初の番号>`）。名の形は `handoff.py` と同じ `loop-`・`sprint-`・`milestone-`・`issue-` で始まるものだけで、在る文書と重なるときに別の名を与える（例: `loop-lroot2-lane`） |

課題・マイルストーンの重なり（`I19`）・触る場所の重なり（`I4`）・引継ぎ文書の重なりは、同じリポジトリのレーンの間だけで見る。
別のリポジトリのレーンの引継ぎ文書は、そのリポジトリの `.ndf/handoff/` に書く。
レーンの作業の途中で別のリポジトリの改修が要ると分かったときに足すレーンは、[parallel-cross-repo.md](../../development-workflow/references/parallel-cross-repo.md) の「別のリポジトリの改修が要るとき」にある。

## 課題のまとまり

**レーンとスプリントはテーマで組まず、触る場所が互いに離れた課題のまとまりで組む。** テーマ（マイルストーン）は計画に入れる
課題を集めるのに使う。集めた課題のうち似た課題を課題のまとまりへまとめ、まとまり 1 つが実装の Pull Request 1 本になる。
まとまりの Pull Request はスプリントブランチへ入れる前に、そのまとまりの差分だけで cross-review を回す
（[pr の SKILL.md](../../pr/SKILL.md) の「スプリントブランチ宛てとベースブランチ宛て」）。

例: テーマ「レビュー」で #3001・#3004・#3010・#3012 を集めた。#3001 は「前提」に #3004 の結果を挙げ、ほかの組はどの条件にも
当たらない。

```json
{"kind": "sprint", "issues": [3001, 3004, 3010, 3012],
 "bundles": [{"name": "review-scope", "issues": [3004, 3001]}]}
```

まとまりは `review-scope`（#3004・#3001。代表の課題は #3004）・`issue-3010`・`issue-3012` の 3 つになる。

| 欄 | 決まり |
| --- | --- |
| `bundles` | 任意。省くと「まとまりの記録なし」で、課題ごとに実装の Pull Request を出し、スプリントの Pull Request の全差分を 1 回 cross-review する。空の配列は「すべての課題が 1 件のまとまり」 |
| `bundles[].name` | まとまりの名前（英小文字・数字・`-`・`_`、32 字まで）。同じレーンの中で一意で、どのまとまりにも入っていない課題に補う名前 `issue-<番号>` とも重ならない |
| `bundles[].issues` | まとまりの課題（1 件以上）。先頭が代表の課題で、まとまりの設計文書と実装の Pull Request はこの番号で作る。どの課題も 2 つ以上のまとまりに入れず、`input.issues` に無い課題を書かない |

課題の集合の正本は `input.issues` で、`bundles` は課題をどのまとまりに入れるかの対応だけを持つ。どのまとまりにも入っていない
課題は、その 1 件だけのまとまりとして扱う。ループのレーンには書けない（ループの課題は開発ループの選定が選ぶ）。

**まとめ方は次の順で決める。** 2 件ずつ当てて、最初に当たった行のまとめ方を採る。

| 順 | 条件 | まとめ方 |
| --- | --- | --- |
| 1 | 一方の受け入れ条件が、すべて他方の受け入れ条件に含まれる（同じ事象の報告を含む） | 統合する。含まれる側にしか無い記述（再現手順・出典）を残す側の本文へ移してから、`gh issue close <含まれる側> --duplicate-of <残す側>` で閉じる。両方が互いに含むときは番号の小さい側を残す。閉じた課題は `input.issues` にも `bundles` にも書かない |
| 2 | 1 に当たらず、(a) `parallel.py check` が 2 件を重なる組として出した（規則 `bundle-overlap` か `I21`）か、(b) 一方の本文の「前提」か「関連」が他方の番号を挙げ、他方の結果を前提にすると書いている | 同じまとまりにする。代表の課題は (b) の前提にされる側、無ければ番号の小さい側 |
| 3 | どちらにも当たらない | まとめない（1 件のまとまり） |

親の課題を新しく起こさず、GitHub の sub-issue にも写さない。まとまりの正本は計画の記録である。

**同じ時間帯に動くまとまりは、触る場所の見込みが重ならないように組む。** 下書きを `init` で書いた後に `parallel.py check` を打ち、
規則 `bundle-overlap`（同じスプリントのレーンの異なるまとまり）と `I21`（同じ時間帯の 2 レーン）の警告の案に沿って、
まとまりを別のスプリントのレーンへ移すか、新しいレーンへ移して `after` を足す。

計画名は 24 字まで。レーンに共通の決まり（プランの本数の配分・触る場所・リリースの担当）は `plan.md` の 1 箇所に置き、
引継ぎ文書へは写さない。引継ぎ文書は計画名・レーン名・`plan.md` のパスと、レーンの開始のコマンドだけを持つ。

## 検査

`init` は書く前に、`parallel.py check <計画名>` は書いた後に、同じ検査を行う。結果は統一 JSON レポートで、
`items[].rule` に誤りの種類を持つ。

| 種類 | 誤りになるもの |
| --- | --- |
| `I1` | 計画名・レーン名の形、レーン名の重なり、一時レーンの名前の形 |
| `I2` | レーンの数がレーン数の上限（マシンの設定 → `NDF_RELAY_MAX_NAMED` → 既定 3）を超える、この計画のプランの本数の合計がプランの本数の上限（マシンの設定 → `NDF_PARALLEL_MAX_PLANS` → 既定 6）を超える |
| `I3` | 依存先が計画に無い、依存が循環する |
| `I19` | レーンの間で課題かマイルストーンが重なる（`--milestones` の無いループのレーンは、ほかのレーンと重なるものとする） |
| `bundle` | 課題のまとまりの形: 2 つ以上のまとまりに入る課題、`input.issues` に無い課題、名前の形、同じレーンの中の名前の重なり |
| `machine-plans`（警告） | 同じマシンで動いている他の計画の宣言の合計とこの計画の合計の和が、プランの本数の上限を超える。`check` と `start` が見る。終了コードは 0 のまま。超えた分のレーンは耐久ワークフローが起動を待たせる |
| `I4`（警告） | 触る場所が重なるレーンの組。終了コードは 0 のまま |
| `I21`（警告） | `after` で順序の付かない同じリポジトリの 2 レーンの課題の、触る場所の見込みが重なる組（直し方の案 `after`・`move` を添える）と、見込みを集められなかったこと。`parallel.py check` だけが見る。終了コードは 0 のまま。見込みの出し方は `development-workflow` の `references/parallel-checks.md` の「課題の見込みの重なり（`I21`）」にある |
| `bundle-overlap`（警告） | 同じスプリントのレーンの異なるまとまりの課題の、触る場所の見込みが重なる組（直し方の案 `move`・`after` を添える）。同じまとまりの課題どうしは出さない。`parallel.py check` だけが見る。終了コードは 0 のまま。項目の欄は `development-workflow` の `references/parallel-checks.md` の「課題のまとまりの見込みの重なり（`bundle-overlap`）」にある |
| `release`（警告） | リリースを組めないリポジトリ（手動の経路がある、リリースの宣言が無い・不明・読めない、組む形で出す版を読めない）。`parallel.py check` だけが見る。レーンがリリースの依頼を送らない計画もあるので起動は断らず、終了コードは 0 のまま |

誤りがあれば終了コードは 1 で、`init` は 1 つも書かない。同じ名前の引継ぎ文書か計画が既にあれば、
`init` は上書きせずに名前を返して止まる。名前を変えるか、在る文書を片付けてから打ち直す。

起動の前なら `plan.json` を手で直してよい。直したら `parallel.py check <計画名>` を打ち直す。手の直しで `bundle` の誤りが
残った計画は、`parallel.py start` が計画の進行表を作らずに止める。
