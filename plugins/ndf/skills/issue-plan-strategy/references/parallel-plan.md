# 並列の計画を作る

読み手はオーガナイザーと、計画を見る人である。読み手が下す判断は「どのレーンを同時に流すか」で、設定を引いて読む。
文書ごとの読み手と順序は [文書の役割の表](../../requirements-design/references/document-roles.md) が持つ。

1 つのリポジトリで複数の開発ループかスプリントを同時に進めるときに、**並列の計画**を 1 度書く。並列の計画は
レーンの一覧と、レーンに共通の決まりを 1 つの文書に持つ。オーガナイザー（`--parallel <計画名>` で起動した conductor）が
これを読んでレーンを起動する。起動の手順は [development-workflow の parallel.md](../../development-workflow/references/parallel.md) にある。

## 例

3 本の開発ループ `lroot`・`lflow` と、`lflow` が終わってから始めるスプリント 1 本（課題 2400）を同時に進める。

```bash
cat > p1.json <<'EOF'
{"version": 1, "name": "p1", "rules": ["マージの衝突は base-sync で解く"],
 "lanes": [
  {"name": "lroot", "input": {"kind": "loop", "loop": "lroot", "args": ["--milestones", "26"]}, "plans": 2, "touches": ["plugins/ndf/"]},
  {"name": "lflow", "input": {"kind": "loop", "loop": "lflow", "args": ["--milestones", "23"]}, "plans": 2, "touches": ["docs/"]},
  {"name": "lfac", "input": {"kind": "sprint", "issues": [2400]}, "plans": 2, "touches": ["web/"], "after": ["lflow"]}
 ]}
EOF
ndf lanes init p1.json
```

`ndf lanes init` は計画の設定（形は `contracts/workflow/parallel-plan.schema.json`）の検査を通し、計画のステートマシンと
レーンごとのステートマシンを未着手で作る。計画の状態はステートマシンが持ち、設定のファイルは入力にすぎない（コミットしない）。
始めるのは `ndf lanes start p1.json`、状態を見るのは `ndf lanes status p1` である。

## レーンごとに決めること

| 項目 | 意味 |
| --- | --- |
| `name` | レーン名。ラッパーの名前になる（英小文字・数字・`-`）。名前に役割を含めない（`lane1` など）。名前は回答待ちの停止・再開のマーカー・リクエストのオーナーのキーで、途中で変えられない。役割は `input` で読む |
| `repo` | 任意。レーンのリポジトリ。計画の保存先と違うリポジトリのレーン（別のリポジトリのレーン）にするときだけ書く。省くと計画の保存先のリポジトリ |
| `input` / `rows` | 最初の順番表。1 行なら `input` に `{"kind": "loop", "loop": <ループ名>, "args": [...]}` か `{"kind": "sprint", "issues": [<番号>...]}` を書き、2 行以上なら同じ形の行を `rows` に並べる（行はスプリント 1 つ）。どちらか一方だけを書く |
| `plans` | 同時に流すプランの本数（1 以上） |
| `touches` | 触る場所（パスか glob） |
| `after` | 始める条件。`<レーン>`（そのレーンの全行の後）か `<レーン>/<行のキー>`（その行の後） |

計画の全体には `version`（1）・`name`（計画名）・`rules`（レーンに共通の決まり）と、任意の `max_lanes`（終わっていないレーンの
数の上限）・`max_plans`（レーンごとのプランの本数の上限）を書く。上限を省くと上限の設定 `relay.max-named` の値になる。
**ここに無い欄はスキーマが断る。**

課題の重なりと触る場所の重なりは、同じリポジトリのレーンの間だけで見る。
レーンの作業の途中で別のリポジトリの改修が要ると分かったときに足すレーンは、[parallel-cross-repo.md](../../development-workflow/references/parallel-cross-repo.md) の「別のリポジトリの改修が要るとき」にある。

## 課題のまとまり

**レーンとスプリントはテーマで組まず、触る場所が互いに離れた課題のまとまりで組む。** テーマ（マイルストーン）は計画に入れる
課題を集めるのに使う。集めた課題のうち似た課題を課題のまとまりへまとめ、まとまり 1 つが実装の Pull Request 1 本になる。
まとまりの Pull Request はスプリントブランチへ入れる前に、そのまとまりの差分だけで cross-review を回す
（[pr の SKILL.md](../../pr/SKILL.md) の「スプリントブランチ宛てとベースブランチ宛て」）。

まとまりは計画の設定には書かない。レーンのスプリントの実行計画（[execution-plan.md](execution-plan.md)）のバンドルとして置く。
先頭の課題を代表の課題とし、まとまりの設計文書と実装の Pull Request はこの番号で作る。どの課題も 2 つ以上のまとまりに入れない。
どのまとまりにも入れない課題は、その 1 件だけのまとまりとして扱う。

例: テーマ「レビュー」で #3001・#3004・#3010・#3012 を集めた。#3001 は「前提」に #3004 の結果を挙げ、ほかの組はどの条件にも
当たらない。まとまりは `review-scope`（#3004・#3001。代表の課題は #3004）・`issue-3010`・`issue-3012` の 3 つになる。

**まとめ方は次の順で決める。** 2 件ずつ当てて、最初に当たった行のまとめ方を採る。

| 順 | 条件 | まとめ方 |
| --- | --- | --- |
| 1 | 一方の受け入れ条件が、すべて他方の受け入れ条件に含まれる（同じ事象の報告を含む） | 統合する。含まれる側にしか無い記述（再現手順・出典）を残す側の本文へ移してから、`gh issue close <含まれる側> --duplicate-of <残す側>` で閉じる。両方が互いに含むときは番号の小さい側を残す。閉じた課題は計画にもまとまりにも書かない |
| 2 | 1 に当たらず、(a) 2 件の触る場所の見込み（課題の本文から AI が読む）が重なるか、(b) 一方の本文の「前提」か「関連」が他方の番号を挙げ、他方の結果を前提にすると書いている | 同じまとまりにする。代表の課題は (b) の前提にされる側、無ければ番号の小さい側 |
| 3 | どちらにも当たらない | まとめない（1 件のまとまり） |

親の課題を新しく起票せず、GitHub の sub-issue にも写さない。

**同じ時間帯に動くレーンは、触る場所が重ならないように組む。** 重なる組は `ndf lanes init` の検査が断る（下の `I13`）ので、
まとまりを別のレーンへ移して `after` を足すか、`touches` を分ける。

## 検査

`ndf lanes init`（と `ndf lanes start`）は、計画の設定をスキーマで検査し、続けて計画の決まりを検査する。どれかに当たれば
ステートマシンを 1 つも作らず、結果 JSON の `summary` に当たった決まりを並べて止まる。

| 決まり | 誤りになるもの |
| --- | --- |
| スキーマ | 欄の形・計画名とレーン名の形・スキーマに無い欄 |
| レーン名 | 同じ計画の中のレーン名の重なり |
| `I2` | 1 本のレーンの `plans` がレーンごとのプランの本数の上限を超える |
| `I20` | 終わっていないレーンの数が上限を超える |
| `I21` | `after` の先が計画に無い、`after` が輪になる |
| `I19` | 同じリポジトリのレーンの間で課題が重なる |
| `I13` | 同時に動き得る行（`after` で前後の付かない別のレーンの行）の触る場所が重なる |

同じ名前の計画のステートマシンが既にあれば、`init` は作らずに止まる。始めるときは `ndf lanes start` を打つ（作ってあれば読む）。
起動の前なら設定のファイルを直して `init` を打ち直してよい。
