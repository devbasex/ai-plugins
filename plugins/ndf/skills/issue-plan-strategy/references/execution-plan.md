# 実行計画

**スプリントを渡されたら、最初の supervisor を起動する前に実行計画を書く。** バンドルごとの依存と触る箇所を
1 つの表に置き、工程の終わりごとに読み直して、着手できる行を起動する。

**書くのはオーケストレーターだけである。** supervisor（worktree 1 つ分）は絶対パスで読むだけで、書き換えない。

## 作る時点と、作らないとき

| 状況 | 実行計画 |
| --- | --- |
| 複数の課題を渡された | **最初の supervisor を起動する前に書く** |
| 1 件の課題を複数の Pull Request に分ける | 書く。行は Pull Request の単位である |
| **課題が 1 件で、Pull Request も 1 本** | **書かない。** 依存も変更重複も本数も、比べる相手がいない |

## 置く場所と名前

| 項目 | 値 |
| --- | --- |
| 場所 | メインディレクトリの `issues/` |
| 名前 | `issues/execution-plan-<キー>.md` |
| キー | マイルストーンの名前の先頭の 2 桁の連番（`10 無人運転と工程の測定` なら `10`）。マイルストーンが無いときは `issue-<バンドルの課題の最小の番号>` |
| コミット | **しない。** 閉じるまで worktree の外のファイルとして置く |

**開いている間はコミットしない。** 見直しのたびに Pull Request を通すと、計画の更新がマージを
待ち、実行計画が進み具合に遅れる。メインディレクトリの `issues/` は worktree の外で編集してよい
場所で、オーケストレーターの会話が失われても（本体が再起動しても）同じ内容を読み直せる。

## 文書の形

**セクションの見出しと表の列名は、この形のまま写す。**

```markdown
# 実行計画: <マイルストーンの名前、または課題の番号の並び>

状態: 進行中
開始: 2026-09-17T03:00Z

## 行

| 行 | バンドル | 種類 | 課題 | モード | 触るファイルとセクション | 確度 | 設計の依存 | 実装の依存 | 状態 | Pull Request |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| G2-設計 | G2 | 設計 | #540 #541 #621 | standard | `parallel-work.md`「守る下限」、`issue-plan-strategy/SKILL.md` | 見込み | なし | — | 動いている | — |
| G3-設計 | G3 | 設計 | #550 #657 | standard | `stage-windows.md`（新設） | 見込み | なし | — | 承認待ち | #740 |

## 変更重複

| 行の組 | ファイルとセクション | 区分 | 扱い |
| --- | --- | --- | --- |
| G2-実装1 / G2-実装2 | `parallel-work.md`「守る下限」 | 書き換え | G2-実装2 の実装の依存へ `G2-実装1:マージ` を足した |

## 見直し

| 時刻 | 契機 | 変えたこと | 理由 |
| --- | --- | --- | --- |
| 2026-09-17T05:10Z | G3-設計の報告 | G3-実装1〜3 を足した | 設計文書の決定 1 が実装を 3 本に分けた |
```

**1 行が `動いている` とき、その行に当たる supervisor は 1 つ（worktree 1 つ分）である。**
supervisor の中で動く worker は、この 1 行の中に含める。

## 列の値

| 列 | 値 |
| --- | --- |
| 行 | `<バンドル>-設計` / `<バンドル>-実装<N>`。1 つの文書の中で一意 |
| 種類 | `設計` / `実装` |
| 触るファイルとセクション | ファイルのパスと、セクションの見出し（「」で囲む）。関数を触るなら関数名 |
| 確度 | `見込み` / `確定`。設計のレビューが収束した見直しで、そのバンドルの行を `確定` にする |
| 設計の依存・実装の依存 | `なし`、または `<行>:収束` / `<行>:マージ` を読点で並べる。設計の行の「実装の依存」は `—` |
| 状態 | `待ち` / `着手できる` / `動いている` / `承認待ち` / `止まった` / `マージ済み` |

**本数に数えるのは `動いている` だけである。** 承認待ちの supervisor は報告を返して終わっており、CLI も
テストも動かしていない。

**依存は工程の対で書く。** B の設計が A の決定を読むなら `A-設計:収束` を B の設計の行へ、B の
実装が A の実装を前提にするなら `A-実装:マージ` を B の実装の行へ書く。**B の設計の行に、B の
実装の依存を書かない**（`parallel-work.md` の必須ルール 4）。

## 行を置く（バンドルの初期値）

**マイルストーンの説明に「### 並列の組（見込み）」の表があれば、その課題グループをバンドルの初期値として読む。**
課題グループ 1 つがバンドル 1 つで、課題グループの「依存」はバンドルの間の依存になる。

| 課題グループの表の列 | 読み方 |
| --- | --- |
| 組 | バンドルの名前にする |
| 課題 | そのバンドルの設計の行の「課題」にする |
| 触る場所の見込み | そのバンドルの設計の行の「触るファイルとセクション」にし、確度を `見込み` にする |
| 依存 | バンドルの間の依存。設計の行の「設計の依存」へ `<先のバンドル>-設計:収束` として写す |

**表を書く側は `backlog-refinement` の
[milestones.md](../../backlog-refinement/references/milestones.md) である。** 読む側のこの手順は、
書く側の手順が入る前でも動く（表が無ければ次の段落の作り方へ落ちる）。

```bash
gh api "repos/{owner}/{repo}/milestones" --jq '.[] | select(.title | startswith("10 ")) | .description'
```

**並列の計画のレーンのスプリントでは、課題のまとまりをバンドルの初期値とし、課題グループより先に使う。** まとまり 1 つが
バンドル 1 つで、設計の行の「課題」はまとまりの課題、設計と実装の Pull Request は代表の課題（先頭）の番号で作る。
まとめ方は [parallel-plan.md](parallel-plan.md) の「課題のまとまり」にある。

**課題グループが無いとき**（表がまだ無い・表に載っていない課題・マイルストーンを使わないリポジトリ）は、
課題の本文を読んでバンドルを決める。**同じ場所（同じ Skill・同じスクリプト・同じ文書）を触る見込みの
課題を 1 つのバンドルにし、違えば別のバンドルにする。** 読んだ結果をマイルストーンの説明へ書き戻さない。
書き戻すと 2 か所が同じ事実を持つ。

**バンドル 1 つにつき、最初は設計の行だけを置く。** 実装を何本に分けるかは設計文書の決定が持つため、
着手の時点では書けない。触るファイルとセクションは課題グループの「触る場所の見込み」からコピーし、確度は `見込み` に
する。

## 同時に動かす本数

**本数はこの文書で測らない。** 同時に流すプランの本数は `ndf plan queue --max` と上限の設定 `relay.max-named` が持ち、
メモリの待ちは `ndf test-slot run` が持つ。

**コンテナを起動するチェックを持つ行は、既に 1 本動いていれば起動しない**（`parallel-work.md` の
必須ルール 6）。

## 見直す

**契機は 4 つである。**

| # | 契機 |
| ---: | --- |
| 1 | supervisor の報告を受け取った（要求が書けた・設計のレビューが収束した・実装のレビューが収束した） |
| 2 | Pull Request がマージされた |
| 3 | supervisor が止まった |
| 4 | オーケストレーターが再起動して、実行計画を読み直した |

| 順 | 行うこと |
| ---: | --- |
| 1 | 契機になった行の状態を更新する。設計のレビューが収束したバンドルは、設計文書の分け方から実装の行を足し、確度を `確定` にする |
| 2 | `確定` になった行どうしの触るファイルとセクションを突き合わせ、「変更重複」の表へ書く。区分が `書き換え` なら、後の行の実装の依存へ先の行の `:マージ` を足す |
| 3 | 依存がすべて済んだ `待ち` の行を `着手できる` にする |
| 4 | `着手できる` の行を表の上から起動し、`動いている` にする。プランで流す行（`development-workflow` の `agent-layers.md` の「プランで流すか supervisor で回すか」）は `ndf plan queue <プラン>... --max <本数>` へ渡し（queue は計画の上限 `ndf lanes limits` を読まないため、本数は `--max` で渡す）、テンプレートの無い行だけ supervisor を起動する |
| 5 | 1〜4 でバンドル・順序・依存を変えたら、「見直し」の表へ **1 行足して理由を残す**。状態の更新だけなら足さない |

**着手できるかは依存と本数だけで決まる。** 他の supervisor が長い待ち（収束レビュー・承認・マージ待ち）に
入ったことをオーケストレーターが知らなくても、依存が済んで空きがあれば次の行が起動される。工程を supervisor へ
出すと、supervisor の中の待ちはオーケストレーターから見えないため、待ちを契機にしない。

**区分の判定は `parallel-work.md` の「変更重複の目安」に従う。** 設計の行どうしは、どの区分でも
並行してよい。

**競合は、後からマージする側が解く。** 解いた後の head でコードレビューを収束させてからマージする
（必須ルール 5）。収束の前にマージしない。

**承認で A の設計が変わったら、A の決定を読む B の設計の行を `待ち` へ戻す。** 戻したことを
「見直し」の表へ理由とともに残す。

## 閉じる

**すべての行が `マージ済み` になったら閉じる。**

```bash
gh pr comment <最後にマージした Pull Request の番号> --body-file issues/execution-plan-<キー>.md
```

| 順 | 行うこと |
| ---: | --- |
| 1 | 先頭の「状態」を `閉じた` にする |
| 2 | 全文を、スプリントで**最後にマージした Pull Request** へコメントとして投稿する |
| 3 | 投稿の URL を確かめてから、**ファイルを消す** |

**振り返りはこのコメントを読む。**
