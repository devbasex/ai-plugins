# 実行計画

**まとまりを渡されたら、最初の担当を起動する前に実行計画を書く。** 束ごとの依存と触る箇所と
本数を 1 つの表に置き、工程の終わりごとに読み直して、着手できる行を起動する。

**書くのは進行側だけである。** 担当（作業ツリー 1 つ分）は絶対パスで読むだけで、書き換えない。

## 作る時点と、作らないとき

| 状況 | 実行計画 |
| --- | --- |
| 複数の課題を渡された | **最初の担当を起動する前に書く** |
| 1 件の課題を複数の Pull Request に分ける | 書く。行は Pull Request の単位である |
| **課題が 1 件で、Pull Request も 1 本** | **書かない。** 依存も重なりも本数も、比べる相手がいない |

## 置き場所と名前

| 項目 | 値 |
| --- | --- |
| 場所 | 主ディレクトリの `issues/` |
| 名前 | `issues/execution-plan-<キー>.md` |
| キー | マイルストーンの名前の先頭の 2 桁の連番（`10 無人運転と工程の測定` なら `10`）。マイルストーンが無いときは `issue-<束ねた課題の最小の番号>` |
| コミット | **しない。** 閉じるまで作業ツリーの外のファイルとして置く |

**開いている間はコミットしない。** 見直しのたびに Pull Request を通すと、計画の更新がマージを
待ち、実行計画が進み具合に遅れる。主ディレクトリの `issues/` は作業ツリーの外で編集してよい
場所で、進行側の会話が失われても（本体が再起動しても）同じ内容を読み直せる。

## 文書の形

**節の見出しと表の列名は、この形のまま写す。**

```markdown
# 実行計画: <マイルストーンの名前、または課題の番号の並び>

状態: 進行中
開始: 2026-09-17T03:00Z
oom_kill の起点: 1

## 行

| 行 | 束 | 種類 | 課題 | モード | 触るファイルと節 | 確度 | 設計の依存 | 実装の依存 | 状態 | Pull Request |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| G2-設計 | G2 | 設計 | #540 #541 #621 | standard | `parallel-work.md`「守る下限」、`issue-plan-strategy/SKILL.md` | 見込み | なし | — | 動いている | — |
| G3-設計 | G3 | 設計 | #550 #657 | standard | `stage-windows.md`（新設） | 見込み | なし | — | 承認待ち | #740 |

## 重なり

| 行の組 | ファイルと節 | 区分 | 扱い |
| --- | --- | --- | --- |
| G2-実装1 / G2-実装2 | `parallel-work.md`「守る下限」 | 書き換え | G2-実装2 の実装の依存へ `G2-実装1:マージ` を足した |

## 測った値

| 時刻 | 空き（MiB） | cgroup の残り（MiB） | スワップの空き（MiB） | oom_kill | 動いている本数 | 起動してよい本数 | 決めた条件 | 起動した行 |
| --- | ---: | ---: | ---: | --- | ---: | ---: | --- | --- |
| 2026-09-17T03:00Z | 9742 | max | 310 | 1 | 0 | 2 | memory,max,swap_low | G2-設計 |

## 見直し

| 時刻 | 契機 | 変えたこと | 理由 |
| --- | --- | --- | --- |
| 2026-09-17T05:10Z | G3-設計の報告 | G3-実装1〜3 を足した | 設計文書の決定 1 が実装を 3 本に分けた |

## 閉じたときの測定

| 対象の Pull Request | 期間（分） | 重なり（分） | 並行度 | 最大同時 | oom_kill の増分 |
| --- | ---: | ---: | ---: | ---: | ---: |
```

**1 行が `動いている` とき、その行に当たる担当は 1 つ（作業ツリー 1 つ分の supervisor）である。**
担当の中で動く worker は、この 1 行の中に含める。

## 列の値

| 列 | 値 |
| --- | --- |
| 行 | `<束>-設計` / `<束>-実装<N>`。1 つの文書の中で一意 |
| 種類 | `設計` / `実装` |
| 触るファイルと節 | ファイルのパスと、節の見出し（「」で囲む）。関数を触るなら関数名 |
| 確度 | `見込み` / `確定`。設計のレビューが収束した見直しで、その束の行を `確定` にする |
| 設計の依存・実装の依存 | `なし`、または `<行>:収束` / `<行>:マージ` を読点で並べる。設計の行の「実装の依存」は `—` |
| 状態 | `待ち` / `着手できる` / `動いている` / `承認待ち` / `止まった` / `マージ済み` |

**本数に数えるのは `動いている` だけである。** 承認待ちの担当は報告を返して終わっており、CLI も
テストも動かしていない。

**依存は工程の対で書く。** B の設計が A の決定を読むなら `A-設計:収束` を B の設計の行へ、B の
実装が A の実装を前提にするなら `A-実装:マージ` を B の実装の行へ書く。**B の設計の行に、B の
実装の依存を書かない**（`parallel-work.md` の下限 4）。

## 行を置く（束の初期値）

**マイルストーンの説明に「### 並列の組（見込み）」の表があれば、その組を束の初期値として読む。**
組 1 つが束 1 つで、組の「依存」は束の間の依存になる（組の形は `issue-upkeep` の
[milestones.md](../../issue-upkeep/references/milestones.md) が持つ）。

```bash
gh api "repos/{owner}/{repo}/milestones" --jq '.[] | select(.title | startswith("10 ")) | .description'
```

**組が無いとき**（表がまだ無い・表に載っていない課題・マイルストーンを使わないリポジトリ）は、
課題の本文を読んで束を決める。**同じ場所（同じ Skill・同じスクリプト・同じ文書）を触る見込みの
課題を 1 つの束にし、違えば別の束にする。** 読んだ結果をマイルストーンの説明へ書き戻さない。
書き戻すと 2 か所が同じ事実を持つ。

**束 1 つにつき、最初は設計の行だけを置く。** 実装を何本に分けるかは設計文書の決定が持つため、
着手の時点では書けない。触るファイルと節は組の「触る場所の見込み」から写し、確度は `見込み` に
する。

## 起動の前に本数を測る

**担当を起動する前に、毎回これを実行し、出力を「測った値」の表へ 1 行残す。**

```bash
python3 "$SCRIPTS/parallel-measure.py" capacity \
  --running <動いている行の数> --oom-baseline <oom_kill の起点>
```

`$SCRIPTS` の決め方は
[scripts-lookup.md](../../development-workflow/references/scripts-lookup.md) にある。
予備・1 本あたりの見込み・上限・スワップの閾値は引数（`--reserve-mib` / `--per-lane-mib` /
`--max` / `--swap-free-min-pct`）で上書きできる。**既定値はコマンドだけが持つ。** この文書は
値を写さない。測った値の表が、初期値を直す根拠になる。

| 出力のキー | 写す列 |
| --- | --- |
| `mem_available_mib` | 空き（MiB） |
| `cgroup_available_mib` | cgroup の残り（MiB） |
| `swap_free_mib` | スワップの空き（MiB） |
| `oom_kill` | oom_kill |
| `running` | 動いている本数 |
| `allowed` | 起動してよい本数 |
| `limited_by` | 決めた条件 |

`swap_total_mib`・`oom_kill_increased`・`by_memory` は写さない。起動のたびに変わらないか、
他の列から導ける。

| 終了コード | 扱い |
| --- | --- |
| 0 | 出力をそのまま写す |
| 2 | 引数の誤り。直して測り直す |
| **3** | **測れない**（`/proc/meminfo` が無い環境など）。空きの列に `測れない` と書き、**起動してよい本数を 1 として扱う** |

**コンテナを起動する検査を持つ行は、既に 1 本動いていれば起動しない**（`parallel-work.md` の
下限 6）。

## 見直す

**契機は 5 つである。**

| # | 契機 |
| ---: | --- |
| 1 | 担当の報告を受け取った（要求が書けた・設計のレビューが収束した・実装のレビューが収束した） |
| 2 | Pull Request がマージされた |
| 3 | 担当が止まった |
| 4 | 測定で OOM Killer の回数（`oom_kill`）が増えていた |
| 5 | 進行側が再起動して、実行計画を読み直した |

| 順 | 行うこと |
| ---: | --- |
| 1 | 契機になった行の状態を更新する。設計のレビューが収束した束は、設計文書の分け方から実装の行を足し、確度を `確定` にする |
| 2 | `確定` になった行どうしの触るファイルと節を突き合わせ、「重なり」の表へ書く。区分が `書き換え` なら、後の行の実装の依存へ先の行の `:マージ` を足す |
| 3 | 依存がすべて済んだ `待ち` の行を `着手できる` にする |
| 4 | `capacity` を実行し、「測った値」の表へ 1 行足す |
| 5 | `起動してよい本数 − 動いている本数` の数だけ、`着手できる` の行を表の上から起動し、`動いている` にする |
| 6 | 1〜5 で束・順序・依存を変えたら、「見直し」の表へ **1 行足して理由を残す**。状態の更新だけなら足さない |

**着手できるかは依存と本数だけで決まる。** 他の担当が長い待ち（収束レビュー・承認・マージ待ち）に
入ったことを進行側が知らなくても、依存が済んで空きがあれば次の行が起動される。工程を supervisor へ
出すと、supervisor の中の待ちは進行側から見えないため、待ちを契機にしない。

**区分の判定は `parallel-work.md` の「重なりの目安」に従う。** 設計の行どうしは、どの区分でも
並行してよい。

**競合は、後からマージする側が解く。** 解いた後の head で実装レビューを収束させてからマージする
（下限 5）。収束の前にマージしない。

**承認で A の設計が変わったら、A の決定を読む B の設計の行を `待ち` へ戻す。** 戻したことを
「見直し」の表へ理由とともに残す。

### `oom_kill` が増えていたとき

`capacity` の出力が `oom_kill_increased=yes` のときは、**その見直しでは新しい担当を起動しない**
（手順 5 を行わない）。同じ見直しで次の 2 つを行う。

1. 文書の先頭の「oom_kill の起点」を、いま測った値へ更新する
2. 「見直し」の表へ 1 行足す（契機: OOM Killer の回数が増えた、変えたこと: 起点を N へ更新、理由）

**起点を更新しないと、以後の見直しがすべて「増えた」になり、進行が再開しない。** 次の見直しからは
新しい起点と比べるため、再び増えない限り起動を再開する。起動してよい本数が下がった分は、動いて
いる担当を止めずに、終わるのを待って減らす。

## 閉じる

**すべての行が `マージ済み` になったら閉じる。**

```bash
python3 "$SCRIPTS/parallel-measure.py" concurrency <行の Pull Request の番号すべて>
gh pr comment <最後にマージした Pull Request の番号> --body-file issues/execution-plan-<キー>.md
```

| 順 | 行うこと |
| ---: | --- |
| 1 | `concurrency` を実行し、並行度・最大同時本数・対象の期間を「閉じたときの測定」の表へ写す。`oom_kill の増分` は、いま測った値 − 「測った値」の表の**最初の行**の `oom_kill`（起点は見直しで更新されるため、開始時の値から数える） |
| 2 | 先頭の「状態」を `閉じた` にする |
| 3 | 全文を、まとまりで**最後にマージした Pull Request** へコメントとして投稿する |
| 4 | 投稿の URL を確かめてから、**ファイルを消す** |

**振り返りはこのコメントを読む。** 並行度と最大同時本数は、次のまとまりの本数の判断の材料になる。
