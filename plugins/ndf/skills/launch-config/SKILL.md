# 起動の設定の承認（launch-config）

NDF が非対話で起動する AI（プランの worker・Skill を回す起動）は、既定では決まった Tool だけを読み込み、MCP を読まない。
工程で MCP や Tool を足したいとき、委譲や相手役でサンドボックスを外してよいときは、リポジトリの `.ndf/launch.json` に書き、
**利用者がこのマシンで承認する**。承認していない指定を使う起動は止まり、止まった文がこの Skill を指す。

例: 工程 `impl` で社内検索の MCP を使いたい。`draft` で候補を作り、候補に `"impl": {"mcp": [".ndf/mcp/search.json"], "allow": ["mcp__search__query"]}`
を書き、利用者に承認の対象を示し、承認の質問に「承認する」と回答してもらってから `.ndf/launch.json` へ反映する。

**`ndf` のコマンドは 1 回の Bash の呼び出しで 1 つだけ打ち、対象のリポジトリ（worktree）の中で打つ。** どのコマンドも結果 JSON を
標準出力の最後の 1 行に出す。

## 守ること

- **`.ndf/launch.json` を書き換える前に、毎回利用者に確かめる。** 承認の対象が空の場合も、承認済みの場合も同じである（手順 4）。
  `.ndf/` の書き換えは、共通原則の「必ず人の承認が要る操作」の C7 に当たる。`.ndf/launch.json` を直接編集しない。直すのは `draft` が作った候補だけである
- **承認を確定するのは人だけである。** 利用者の回答が無いまま `approve` を打たない。「承認しない」と回答されたら記録も反映もしない
- **MCP の定義ファイルと `.mcp.json` を読まず、作らず、編集しない。** 定義の引数・`env`・URL には資格情報が書かれうる。定義ファイルは利用者が書き、
  中身は利用者が自分で開いて読む
- **`allow` の指定子に資格情報を書かない。** 資格情報は環境変数で渡し、指定子には `$名前` の参照だけを書く。秘密の形の値があると `show` が止まる
- **`show --question approve` が返した質問は、1 字も変えずに出す。** 警告の文（`unsandboxed` があるとき）はコマンドが入れる。Skill は文を足さない。
  変えると回答が記録されず、`approve` が拒む

## 設定の形

```json
{
  "version": 1,
  "permissions": {
    "steps": {
      "*": {"load": ["LSP"]},
      "design": {"mcp": "inherit"},
      "impl": {"mcp": [".ndf/mcp/search.json"], "allow": ["mcp__search__query"]}
    },
    "unsandboxed": ["codex"]
  }
}
```

| キー | 意味 |
| --- | --- |
| `permissions.steps.<工程>` | `<工程>` は worker の作業の名前か Skill の名前。`*` はすべての工程。工程の指定のキーは `*` の同じキーを置き換える |
| `load` | 読み込みに足す組み込みの Tool の名前（英字だけ）。足しただけでは、尋ねずに使えるようにはならない |
| `allow` | 尋ねずに使ってよい許可の指定（Tool の名前・`Bash(git log:*)` の形・`mcp__<サーバ>__<Tool>`） |
| `mcp` | MCP の定義ファイル（リポジトリの根からの相対パス）の配列か、環境の MCP をすべて読む `"inherit"` |
| `permissions.unsandboxed` | サンドボックスが使えない環境で、安全装置を外して起動してよいランタイム（`claude` 以外）。利用者は、このマシンが外側で隔離されていることを自分で確かめてから承認する |

### モデルと effort の実験（`experiments`）

今の `experiments` は、`ndf models pick` が返すモデルと effort を変えるだけで、worker や委譲の実際の起動には効かない。

NDF は工程ごとの選択肢（モデルと effort の組）を同梱している。各工程の選択肢の先頭の組を、基準の組と呼ぶ。`ndf models pick` は、設定で上書きした工程・ランタイムの基準の組を返す。`experiments` は同梱の値のうち書いたキーだけを置き換える。`enabled` による抽選の切り替えと、実際の起動への反映は今後対応する。利用者には、設定を書き換えても今の worker や委譲の起動のモデルと effort は変わらないと伝える。

```json
{
  "version": 1,
  "experiments": {
    "enabled": true,
    "stages": {"impl": {"arms": {"claude": [{}, {"model": "sonnet", "effort": "medium"}]}}},
    "allocation": {"window_days": 60}
  }
}
```

| キー | 今の動き（`ndf models pick` の結果） | 今後の動き（実際の起動への反映と抽選が入った後） |
| --- | --- | --- |
| `enabled` | 今は `enabled` の値を選択に使わない。モデルか effort のどちらかを環境変数で指定した場合は、再試行時も指定した値を使い、指定のない項目には基準の組の値があれば使う。再試行の値を確かめるときは `--retry <失敗の理由>` を指定する。省くと値は上がらない。指定できる理由は、`contracts/domains/launch-experiments.json` の工程の行にある `retries` の値（たとえば `test_failed`）で、それ以外の値を渡すとコマンドが止まる。モデルと effort のどちらにも手動指定がなければ、基準の組に引き上げの規則を適用する。規則に該当する値がなければ、基準の組の値をそのまま返す | 偽なら抽選を止め、手動指定がない項目には基準の組の値を使う。環境変数などによる手動指定は引き続き優先する |
| `stages.<工程>.arms.<ランタイム>` | 上書きや再試行時の引き上げが無ければ、先頭の組（基準の組）を使う。`{}` はモデルも effort も指定しない組である。NDF の環境変数（`NDF_LAUNCH_*`）で上書きした項目は、引数を返す。Claude 自身の effort の環境変数（`CLAUDE_CODE_EFFORT_LEVEL`）を引き継ぐときは、effort の引数を返さない | その工程の選択肢。単位ごとに選択肢から抽選する。1 組だけならその値に固定する |
| `allocation` | 効かない。値の制約だけを確かめる | 割り付けの値（`floor`・`min_units`・`margin`・`window_days`）。省いたキーは同梱の値 |

工程とランタイムは、同梱の表（`contracts/domains/launch-experiments.json`）にあるものだけを書ける。

- **`experiments` は承認の対象ではない。** 承認のハッシュに入らないので、書き換えても承認をやり直さない。ただし `.ndf/launch.json` の書き換えなので、
  手順 2〜4 のとおり候補を直して、反映の前に利用者に確かめる
- effort が順位に無い・選択肢が空か重なる・値の制約に外れると、`ndf models pick` が理由と直す場所を示して止まる。書き換えた後は
  `ndf models pick` で、今の設定から選ばれる値を確かめる。変更した工程に対応する `--layer` と `--name` を指定し、Codex を確かめるときは
  `--runtime codex` を付ける。たとえば Claude の実装 worker なら `ndf models pick --layer worker --name impl` と打つ
- 一時的に上書きするときは、設定を書き換えずに環境変数 `NDF_LAUNCH_MODEL`・`NDF_LAUNCH_EFFORT`（Codex は `NDF_LAUNCH_CODEX_MODEL`・`NDF_LAUNCH_CODEX_EFFORT`）を使う。今は `ndf models pick` の結果だけが変わる。抽選が入った後は、上書きした起動を実験に数えない

## 手順

### 1. 今の指定と状態を読む

```bash
ndf launch-config show
```

- `metrics.approved` が今の内容がこのマシンで承認済みか、`items` の `launch-target` が承認の対象の一覧である
- 結果に `next` があれば、回答済みで反映が済んでいない承認がある。先に `next.argv` のコマンドをそのまま打って片付ける。
  今の設定が壊れていて `stopped` で止まった結果にも、`next` は付く
- `metrics.cleanup_targets` は、利用者が手で消してよい候補の一覧である。利用者に示すときは、その候補を開いているエディタを閉じてから消すよう添える
- **`stopped`（`precondition`）で止まっても、手順はそこで終えない。** 止まった文のファイルと位置を利用者に伝え、元のファイルは変えずに次へ進む
  - 壊れているのが `.ndf/launch.json` なら、手順 2 の候補の中身を読んで直す（`--candidate` を付けた `show` と `approve` は今の `.ndf/launch.json` を解析しない）
  - 壊れているのが MCP の定義ファイルか `.mcp.json` なら、利用者が直してから手順 1 をやり直す。AI は直さない

### 2. 候補を作って直す

```bash
ndf launch-config draft
```

結果の `metrics.candidate` が候補のパス（利用者の状態の保存先の下の `candidate.json`）で、中身は今の `.ndf/launch.json` の写しである。
利用者のリクエストに合わせて、この候補を編集する。MCP の定義ファイルが要るなら、パスを候補に書き、ファイルは利用者に書いてもらう。
NDF が起動した AI の中（`NDF_AI_CHILD`）では `draft` は拒まれる。

### 3. 承認の対象を示し、承認の質問を作る

候補を直し終えたら、承認の対象の一覧と承認の質問を、次の 1 回のコマンドで作る。

```bash
ndf launch-config show --question approve --candidate <候補のパス>
```

結果の `items` の `launch-target` から、次を利用者に示す。MCP の定義の中身は出ないので、ファイルを開いて読むよう伝える。

- 工程ごとの `load`・`allow`・`mcp` の指定
- MCP の定義ファイルごとの場所・ハッシュ・サーバ名・コマンド名
- 安全装置を外してよいランタイム（`unsandboxed`）
- 承認の対象のハッシュ（`metrics.sha256`）

**承認の対象が空か承認済みでも、手順 4 を飛ばさない。** 手順 4 の進め方は、この結果の形で分かれる。

### 4. 承認を取り、承認されたら反映する

**`items` に `question` がある（Claude Code の対話の会話）**

1. **読み手役に読ませる。** 手順 3 の結果の `items` の `question` にある `input.questions[0].question`（質問の文）と、手順 3 で利用者に示した説明を、
   1 つのファイルに書く。`ndf records reading prompt --file <JSON>` で読み手役への指示を作り、指示の文だけを渡して読み手役を起動する
   （Claude Code では新しい `ndf:worker`、`description` は `検証: 読み手役（起動の承認・利用者）`）。直してよいのは手順 3 の説明だけで、質問の文は直さない。
   JSON には次の 3 つのキーだけを入れる。
   - `files`: 書いたファイルのパスを 1 要素にした配列
   - `reader`: `position`・`words`・`knowledge` の 3 つの空でない文字列を持つオブジェクト。読み手は起動の設定を承認する利用者
   - `questions_kind`: `none`
2. **確認を記録する。** `ndf records reading add --file <JSON>` を打つ。記録が無いと、hook の guard `reading-check` が質問を止める。
   JSON には次の 3 つのキーだけを入れる。
   - `questions`: `input` の `questions` をそのまま
   - `prs`: 空の配列
   - `reads`: 2 要素の配列。各要素に `name`（質問の文は `question`、手順 3 の説明は `material`）、`reader`（`承認する人`）、
     `round`（1 か 2）、`result`（合格なら `passed`、2 回目にも残ったなら `remained`）を入れる
3. **質問を出す。** `input` を 1 字も変えずに `AskUserQuestion` へ渡す。区分は `input.metadata.source` の `ndf-ask:redline:C7`（利用者の設定の書き換え）である
4. 利用者が「承認する」を選んだら、`routes.approved.argv` のコマンドをそのまま打つ（`approve --sha256 <値> --request <リクエスト> --candidate <候補>`）。
   承認の対象が空か承認済みでも、この回答が無いと反映しない。回答した質問と別の候補・別の作業場所の候補には使えない。`ok` なら反映が済んだ。「承認しない」を選んだら何も打たず、記録も反映もしていないこと、`.ndf/launch.json` は変わっていないことを伝える
5. 選択肢の承認者の名前は `git config user.name` から作る。利用者が名前が違うと回答したら、利用者に直してもらってから手順 3 をやり直す

**`items` に `question` が無く、`metrics.terminal` がある（回答を記録できない会話）**

次の場合がここに当たる。

- NDF が起動した AI・人のいない実行・計画のレーン・外のオーガナイザーのレーン
- `AskUserQuestion` の無いランタイム（Codex など）
- GitHub のリモートの `<所有者>/<リポジトリ>` を求められない作業場所（リモートが無い・GitHub のリモートでないなど）。質問の前の確認（`ndf records reading add`）は、その `<所有者>/<リポジトリ>` で記録するため、記録を作れない

`metrics.terminal` は、候補の内容で `.ndf/launch.json` の置き換えを試みるコマンドである。コマンドは、置き換える反映先のパスと承認の対象を表示し、
承認者の名前とハッシュの先頭 8 文字の入力を求める。承認の対象が空か承認済みでも、書き換えには毎回この入力が要る。打ち間違えると何も変えずに止まる。
正しく入れたときに承認も記録するかは、コマンドを打った時点の内容と承認の状態で決まる。次の表は、手順 3 の結果の `metrics.required`（許可を広げる内容か）と
`metrics.approved`（その内容がこのマシンで承認済みか）から見た、表示した時点の見込みである。

| 手順 3 の結果 | 正しく入れたときの動き（見込み） |
| --- | --- |
| `metrics.required` が真で、`metrics.approved` が偽 | 承認を記録してから置き換える |
| `metrics.required` が偽か、`metrics.approved` が真 | 承認の記録は書かずに置き換える |

打った時点で見込みと違えば、コマンドは次のように動く。

- 手順 3 の後に承認が取り消されていれば、表の 1 行目と同じく、入力した確認で承認を記録する
- 手順 3 の後に候補の承認の対象（許可の指定か MCP の定義ファイル）が変わっていれば、置き換えずに拒む
- ハッシュを照らした後、置き換える前に候補が変わっていれば、置き換えずに拒む
- 候補が別の作業場所で作ったもので、反映先がこの作業場所の `.ndf/launch.json` でなければ、置き換えずに拒む
- 今の `.ndf/launch.json` が候補と違い、候補を作った時点から別の作業で変わっていれば、置き換えずに拒む
- 今の `.ndf/launch.json` が候補と同じなら（利用者が候補と同じ内容を手で保存した場合など）、設定を書き換えずに完了する。
  承認が要るのに未承認なら、入力した確認で承認を記録する

1. **読み手役に読ませる。** 利用者に伝える文を 1 つのファイルに書く。文には、`metrics.terminal` のコマンド、そのコマンドを打つと置き換えを試みること、
   反映先のパスを確かめて名前とハッシュの先頭 8 文字を入れること、上の表のどちらに当たる見込みか（承認も記録するか）、打った時点で内容が変わっていれば拒まれること、
   手順 3 で示した説明を入れる。このファイルを、`items` に `question` がある場合の 1 と同じ入力
   （`files` はそのファイルのパスを 1 要素にした配列）で読み手役に読ませる。質問ではないので、同じ場合の 2 の記録は作らない。
   直してよいのはコマンドの外の説明だけで、コマンドは変えない
2. **端末で打ってもらう。** 読ませた文を、区分の名前 `ndf-ask:redline:C7` を先頭に書いて利用者に伝え、利用者自身に端末で打ってもらう
3. **結果を確かめる。** 打ち終えたと聞いたら、`routes.approved.argv` のコマンド（同じ候補を付けた `show`）を打つ。次の 2 つを分けて確かめる。
   - 設定へ反映したか: この結果の `metrics.reflected` が真なら反映済み。真になるのは、反映の完了の記録がこの候補のもので、今の `.ndf/launch.json` と、
     残っていれば候補も、記録した中身のままのときである。反映の後に候補を直し直していれば偽になる。
     承認の対象のハッシュ（`metrics.sha256`）は反映の確認に使わない。許可の指定だけから求めるので、設定が無い状態と許可の指定が無い候補とで同じになる
   - 起動の許可を記録したか: この結果の `metrics.required` が真なら、`metrics.approved` が真のときに記録済み。`metrics.required` が偽なら、許可の記録は要らない

   `show` が `stopped` で止まったときと、どちらかが済んでいないときは、端末に出た拒否の文を利用者に聞き、次の「`approve` が拒んだとき」の表に従う

### `approve` が拒んだとき

`stopped`（`refused`）の文のとおりにする。

| 文の中身 | すること |
| --- | --- |
| 示した内容と今の内容が違う | 候補か定義ファイルが変わった。手順 3 から示し直す |
| 人の確認が無い | 質問への回答も端末での入力も無い。承認の対象が空か承認済みでも当たる。手順 4 で回答を取るか、端末で打ってもらう |
| ハッシュを照らした後に候補が変わった | 手順 3 から示し直し、承認を取り直す |
| 候補の反映先が、この作業場所の `.ndf/launch.json` と違う | 別の作業場所の候補を渡した。この作業場所で手順 2 からやり直す。`show --question approve` も同じ文で止まる |
| 承認の回答が無いか使えない | 未回答・別の候補か反映先への回答・より新しい質問・取り消し・設定の変更のどれか。手順 3 から質問を作り直す |
| 反映の直前に、この内容の承認が取り消された | 手順 3 から示し直し、承認を取り直す |
| 候補を作った後に設定が別の作業で変わった | 手順 2 からやり直す。利用者の保存を別の名前で残したと書かれていれば、そのパスを伝える |
| 候補が無く、反映も確かめられない | 手順 2 からやり直す |

## 承認を取り消す

```bash
ndf launch-config revoke --sha256 <ハッシュ>
```

取り消すと、その内容を使う起動は止まる（許可は広がらない）。回答を記録しない会話（NDF が起動した AI・人のいない実行・計画のレーン・外のオーガナイザーのレーン）では拒まれる。利用者が端末で打つ。

## 完了の報告

反映したか（しなかったなら理由）、承認の対象のハッシュの先頭 8 文字、承認者、`metrics.cleanup_targets` に残った候補を書く。
