# バックグラウンドの作業が残る claude を止めずに待つ（Claude Code だけ）

**中継のラッパーは、自分が起動した claude（子）にバックグラウンドの作業が残っている間、次の 3 つの理由では子を止めずに、作業の終わりを待つ。**
子を止めると、supervisor やプランのキューも一緒に終了し、そのフェーズの成果が失われるためである。

- 会話の文脈の量が運用上限を超えたので、引継ぎを求める
- 子の出力と端末への入力が止まったので、同じ会話を起動し直す
- 利用上限に達する前に、別のアカウントへ切り替える

例: レーンの conductor が supervisor（Agent）を 1 つ起動して応答を終えた。会話の文脈の量は運用上限（既定 500,000 トークン）を超えている。

1. Agent を呼び出す直前に、hook（`relay-busy`）が、この子の記録（下の「起動ごとの記録」）に作業「1 件以上」と書く。応答が終わると、hook（`relay-marker`）が件数を 1 件に書き直す
2. 子の出力も端末への入力も静かな時間（`relay.quiet`、5 秒）だけ無くなっても、ラッパーは引継ぎを求めずに待つ。`ndf relay ls` に出る状態は `waiting`、理由は次のとおりである

   ```text
   バックグラウンドの作業 1 件が終わるのを待つ（ほかに監視 0 件。2026-11-24T02:16:05+00:00 の記録）。待つ間は子を止めず、引継ぎ・起動し直し・利用上限に達する前のアカウントの切り替えをしない
   ```

3. supervisor が終わると、Claude Code がその報告を子へ知らせ、子が応答する。応答が終わると件数は 0 件になる。子の出力も端末への入力も静かな時間（`relay.quiet`、5 秒）だけ無くなれば、ラッパーが引継ぎを求める

ラッパーが次に何をするかを決める順は [relay.md](relay.md#承認ゲートを越えない守り) の表にある。この文書は、そのうち
5（利用上限に達する前のアカウントの切り替え）・6（引継ぎ）・7（出力と端末への入力が止まったときの起動し直し）で作業の終わりを待つ決まりを説明する。

## 作業と監視を見分ける

バックグラウンドの作業は、Claude Code が会話の外で動かし、終わると会話へ知らせるものである（Agent・`run_in_background` の Bash・Monitor など）。
NDF はこれを、止めると成果を失う**作業**と、待つだけなので止めてよい**監視**に分ける。

| 種類 | 当てはまるもの | 例 |
| --- | --- | --- |
| 監視 | 実行するコマンドが、待つだけのコマンド（`ndf lanes wait`・`ndf plan wait`・`ndf ci watch`）だけの、Monitor とバックグラウンドの Bash。待つだけのコマンドどうしを `;`・`&&`・`\|\|` でつないでもよい。`timeout` を前に置くことと、出力をファイルへリダイレクトすることもできる | `ndf lanes wait p1 --after 3`、`timeout 590 ndf plan wait plan.json > wait.log 2>&1` |
| 作業 | 監視に当てはまらないものすべて | Agent、`ndf plan queue plan.json`、`cd <場所> && ndf lanes wait p1`、`ndf lanes wait p1 \| tail -1`、`until` や `for` のループ、`npm run build \| grep warn` を実行する Monitor |

**監視だと確かめられないものは作業として扱う。** 作業を監視と取り違えると成果を失うが、監視を作業と取り違えても、待つ時間が延びるだけで済むためである。
オーガナイザーとレーンの conductor は、待つだけのコマンドを、ほかのコマンドとつながず、パイプにも渡さずに実行する（`timeout` は付けてよい）。
つなぐと作業に数えられ、終わるまで引継ぎへ進まない。待つだけのコマンドの一覧は `contracts/hooks/guards.json` の `relay-busy` の `params` が持つ。

## どの場面で何を待つか

ラッパーは、件数を起動ごとの記録から読む。「確かめられない」は、記録が無い・読めない・形が違うときである
（この仕組みが入る前のバージョンの hook で動いている子や、`NDF_HOOK_OFF` で `relay-busy` を止めた子）。

| ラッパーがすること | 作業も監視も無い | 監視だけが残る | 作業が残る | 確かめられない |
| --- | --- | --- | --- | --- |
| 利用上限に達する前のアカウントの切り替え（順 5） | 切り替える | 切り替える | 待つ | 待つ。子の出力も端末への入力も `relay.stall` の秒数（1,800 秒）だけ無ければ起動し直す |
| 文脈の量が上限以上で、子の出力も端末への入力も静かな時間（`relay.quiet`、5 秒）だけ無いときの引継ぎ（順 6。1 つのセグメントで 1 回だけ） | 引継ぎを求める | 引継ぎを求める | 待つ | 同上 |
| 子の出力も端末への入力も `relay.stall` の秒数だけ無いときの起動し直し（順 7） | 起動し直す | 待つ | 待つ | 起動し直す |

- **出力が止まったときは、監視だけが残る子も起動し直さない。** この起動し直しでは子へ何も送らないので、監視が失われると、会話は利用者の入力を待つだけになるためである
- **監視を始め直すよう子へ伝えるのは、見回りによるアカウントの切り替え（順 5。利用上限に達する前の切り替えと、従量の接続から戻す切り替え）だけである。** 切り替えで監視も終わるので、切り替えた後に子へ送る文に、監視を始め直すことを足す。
  `ndf lanes wait` は、最後に受け取った結果の知らせのうち処理していないものだけを処理してから、その結果の `next` を打つ。結果を受け取っていないか読めなければ、終わった `wait` の元の行（同じ `--after`）を打つ。ほかの監視は同じコマンドを打つ。
  同じ会話を続けるので、受け取った結果と、どの知らせまで処理したかは会話に残っている。結果を受け取った `wait` を打ち直すと、処理済みで開いたままの知らせ（`lane_stalled` など）も再び返り、利用者への報告が重なる
- **利用上限に達した後・認証に失敗した後・API キーの子を止めた後のアカウントの切り替えでは、監視を始め直すよう伝えない。** 監視は終わったままになるので、監視を待っていた会話には、利用者が上と同じ始め直し方を入力する
- **次の操作は、作業が残っていても待たずに行う。** 利用上限に達した後のアカウントの切り替え、認証に失敗したときのアカウントの切り替え、次のセグメントへの切り替え、子が終わった後の起動し直し、API キーで動く子の停止（設定の変更や認証の失敗のとき）
- **子を止める直前に、記録を読み直す。** 質問を記録する hook（`ask-forward`）と同じロックを取って読む。判定の後に作業が始まっていれば子を止めず、次の見回りで判定し直す

次のセグメントへの切り替えは、hook（`relay-marker`）が書くマーカー（`next.json`）で始まる。応答が `ndf-next` のブロックを持っていても、
**作業が残っていれば、hook はマーカーを書かずに応答を続けさせる**（変更要求）。監視だけなら書く。件数は Stop の入力の `background_tasks` から数える。
入力に `background_tasks` が無いときは起動ごとの記録の件数を使い、記録も無ければマーカーを書く。

**変更要求は、利用者の入力ごとに合計 2 回（`hook.pushback`。`stop-wait` などの変更要求と合わせて数える）までである。** 上限に達した後は、作業が残ったまま応答が終わり、
マーカーは書かれない。同じ入力の間は、ブロックの出し直しも求められない。作業が終わってもその会話が次のセグメントへ切り替わらなければ、その会話に
「`ndf-next` のブロックをもう一度出して応答を終える」と入力する（利用者の入力で変更要求の回数は数え直す）。

## 起動ごとの記録

記録は、ラッパーの作業ディレクトリの `busy-<起動の ID>.json` である（起動の ID は、ラッパーが子を起動するたびに振る）。
**書くのは子の会話の hook だけで、ラッパーは書かない。** 子を起動するときに、ほかの起動の記録を消すだけである。
子が Bash から別の claude を起動しても、その会話の ID は環境変数 `NDF_RELAY_SESSION` の値と一致しないので、その hook は書かない。

| hook | いつ | 書くもの |
| --- | --- | --- |
| `relay-busy`（SessionStart） | 会話が始まったとき（`startup`・`resume`） | 作業も監視も 0 件 |
| `relay-busy`（PreToolUse） | 作業を始める呼び出し（Agent と、作業に当たる Monitor・バックグラウンドの Bash）の前 | 作業「1 件以上」。書けなければ呼び出しを拒否する |
| `relay-busy`（PreToolUse） | 監視を始める呼び出し（監視に当たる Monitor・バックグラウンドの Bash）の前 | 作業の件数を変えずに、監視を 1 件以上にする。書けなくても拒否しない。この起動の記録が無ければ書かない |
| `relay-marker`（Stop） | 応答が終わったとき | 入力の `background_tasks` を作業と監視に分けて数えた件数。入力に `background_tasks` が無いときと、`relay-busy` を止めた環境では書かないので、前の記録が残る |

作業も監視も始めない呼び出し（Read・フォアグラウンドの Bash など）は、記録に触れずに通す。ラッパーの下でないセッションと Codex では、`relay-busy` は何もしない。

**作業の開始を拒否したときの文は次のとおりである。** `relay-busy` は、自身の処理に失敗したときも、作業の開始を拒否する。

```text
バックグラウンドの作業の開始を記録できなかったので、この呼び出しを拒否した。もう一度呼び出す（記録が無いと、中継のラッパーが作業の途中で claude を終了させることがある）
```

| 拒否された理由 | 直し方 |
| --- | --- |
| ほかの処理がロックを取っていた・hook が時間切れになった | 同じ呼び出しをもう一度行う |
| ラッパーが子を終了させている最中である | 何もしない。起動し直された会話が続ける |
| 作業ディレクトリが消えた・書けない | 書けるようにする（ディスクの空きを増やすなど）。できなければ `/exit` して `claude` を打ち直す |

## 待ち続ける子を見つけて起動し直す

**作業がいつまでも終わらない子を、ラッパーは待ち続ける。** 待つ時間の上限は無い。監視が終わらない子も、出力と端末への入力が止まっただけでは起動し直されない。
待っている子は、`ndf relay ls` の `state` と `reason` で分かる。

```bash
ndf relay ls | jq -c '.items[] | select(.state == "waiting") | {name, reason}'
```

| `reason` の始まり | 意味 |
| --- | --- |
| `バックグラウンドの作業 N 件が終わるのを待つ` | 直前の応答が終わったときに、作業が N 件残っていた。時刻は件数を書いた時刻（UTC） |
| `バックグラウンドの作業 1 件以上が終わるのを待つ` | 作業を始めた後、その応答がまだ終わっていない |
| `監視 M 件が終わるのを待つ` | 作業は無く、監視だけが残ったまま、子の出力も端末への入力も `relay.stall` の秒数だけ無い |
| `バックグラウンドの作業が残っているかを確かめられない` | 今の起動の記録を読めない |

`reason` がほかの文なら、別の待ち（回答待ちの質問・利用上限のリセットなど）である。子が動き出すと、状態は `running` に戻る。

待ちが長いときは、次の順で確かめる。**子を起動し直すと、残っている作業は失われる。**

1. 子の画面（名前つきのラッパーは `tmux -L ndf-lanes attach -t <名前>`）で、作業が進んでいるかを見る。進んでいれば待つ
2. 終わらない作業だけを止めたいときは、その会話に、`TaskStop` で該当の作業を止めるよう頼む（運用上限を超えた会話でも、hook は `TaskStop` を拒否しない。
   task id は作業を始めたときの応答にある）。応答が終わると件数が書き直され、0 件ならラッパーの待ちが終わる
3. 会話が応答しないときは、`ndf relay restart <名前>` で起動し直す。そのラッパーを始めたときの最初の入力で、新しい会話が始まる。
   端末で `claude` を打って始めたラッパー（`ndf relay ls` の `registered` が偽）は `ndf relay restart` の対象にならない。`/exit` するか Ctrl-C を 2 回押して終え、`claude` を打ち直す
