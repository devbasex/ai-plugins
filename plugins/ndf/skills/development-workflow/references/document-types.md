# 文書タイプの判定

**モードが `documentation` に決まった後に、6 つのうち 1 つを選ぶ。** タイプが決めるのは
**何を書くか**である。書いた中身をどう見せるか（出力の形）とどこへ置くか（システム）は
別の軸で、それぞれ `design` の `layout-<出力の形>.md` と `document-systems` が持つ。

## 何が `documentation` に当たるか

**判定を分けるのは読み手である。** リポジトリの外にいる人へ渡すものだけが当たる。

| 対象 | モード |
| --- | --- |
| 提案資料・稟議書・定例報告・指標の定義・運用マニュアル・説明資料 | `documentation` |
| `README.md`・`docs/`・Skill の本文・コードのコメント | `light`（これまでどおり） |
| 課題の本文・Pull Request の本文・実装計画 | 工程の産物であり、モードの判定の対象ではない |

**ファイルの形式では分けない。** どちらも Markdown であり、区別が付かない。

## 6 つのタイプ

**境界は「読み手に何を求めるか」で切る。** 同じ内容でも、採否を求めれば提案、承認を求めれば
決裁である。

| タイプ | 読み手に求めるもの | 本体になるもの | 読み手 |
| --- | --- | --- | --- |
| 提案・企画 | **採否の判断** | まだ決まっていないことの提案 | 社外 / 社内 |
| 決裁・稟議 | **承認** | 金額・期間・責任の所在 | 社内 |
| 定例報告 | 現状の把握と次の打ち手の合意 | **決まった周期の値と、その差分** | 社内 |
| 指標定義 | 何を数えるかの合意 | **指標の定義**（値ではない） | 社内 |
| 運用マニュアル | **その場で手を動かすこと** | 手順 | 社内 |
| 説明・研修 | **理解**（判断も操作も求めない） | 説明 | 社内 |

## 複数に当たったとき

**読み手が実際に取る行動で決める。** 判断材料を並べただけで承認欄が無ければ提案であり、
承認欄があれば決裁である。

それでも決まらないときは、上の表の順で先に来るものを採る。

## 境界事例

| 事例 | どちらか | 理由 |
| --- | --- | --- |
| 提案資料に決裁欄が付いている | 決裁・稟議 | 読み手が押すのは承認であり、採否の議論は済んでいる |
| 定例報告の中で新しい施策を提案している | 定例報告 | 枠と周期が決まっており、読み手が見るのは差分である |
| 指標の値を並べた月次の資料 | 定例報告 | 定義は既にあるものとして扱っている |
| 指標の定義を変える提案 | 指標定義 | 変えた後の定義が本体で、読み手は数え方に合意する |
| 手順を説明する研修資料 | 説明・研修 | 読み手はその場で手を動かさない |
| 操作しながら読む手順書 | 運用マニュアル | 読み手がその場で手を動かす |
| 会議の議事録 | **対象外** | 会議の自動生成物であり、工程を持たない |

## 改訂と初版

**運用マニュアルだけは改訂が続く。** 題名に更新の継続が書かれ、識別子を持つものがある。
初版と改訂で工程は変わらず、変わるのは**何を残すか**である（変更点・改訂の日付・前の版の
所在）。書き方は `document-drafting` の `type-manual.md` が持つ。
