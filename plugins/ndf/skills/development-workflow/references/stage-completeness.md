# 通過記録と、本番へ届くマージの縛り

必須の工程を通らずにリリースまで進んでも、それに気づく出力がどこにも出ない。本番へ届くマージが、人間の承認を経ずに
実行できる。前者はスプリントのステートマシンが持つ通過記録で、後者は tool 実行前の hook の guard で扱う。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| ステートマシン | スプリントの工程と状態を持つ記録。`ndf progress new` が作り、ID を結果に返す |
| 通過工程 | あるスプリントについて、ステートマシンが終わりを記録した工程の集合 |
| 通過記録 | 通過工程とモード・進め方をスプリントごとに残したもの。ステートマシンが持つ |

## 判定の 2 つ

| 何を見るか | 誰が見るか | 何をするか |
| --- | --- | --- |
| 工程の通過 | スプリントのステートマシン（`ndf progress`） | 工程の終わりを積む。プランが工程を流すと、その工程の記録をステートマシンへ書く |
| 本番へ届くマージ | hook の guard `merge-production`（`contracts/hooks/guards.json`） | Bash で直に打つ `gh pr merge` を、マージ先のリポジトリの delivery で判定し、自動で本番へ届くなら止める |

**記録の無い工程は拒否しない。** 記録が無いのは、記録の側が遅れているだけのこともある。
その状態でマージやリリースが止まると、正当な操作が止まる。

**本番へ届くマージだけは拒否へ踏み込む。** 編集は続けても元へ戻せるが、本番へ届いたマージは戻せない。
承認を取ったマージはプラン（`ndf release-steps merge` などのステップ）が行う。

## 通過記録

通過記録はステートマシンが持つ。`ndf progress show <ステートマシンの ID>` は工程ごとの状態を結果 JSON で返す。

- **書き手はプランと conductor である。** プランは流した工程の終わりを書き、conductor は工程を飛ばす・戻す・手で終えるときに
  `ndf progress disable`・`ndf progress enable`・`ndf progress retry`・`ndf progress finish` を `<ステートマシンの ID> <工程> --reason <理由>` で打つ（`finish` は `--output <出力のファイル>` も要る）
- **工程名は工程表の行名である。** [SKILL.md](../SKILL.md) の「モードごとに起動する Skill」の表と、工程の定義（`contracts/workflow/modes/`）が同じ並びを持つ
- **「1 つの Pull Request に 1 つのモード」は、スプリントに 1 つのモードで表す。** モードは `ndf progress new --mode` で決め、スプリントの課題すべてに当たる

```bash
ndf progress show <ステートマシンの ID>   # ID は ndf progress new の結果にある
```

## 報告の読み方

記録の無い必須の工程を見つけたら、実施済みかを確かめてから記録して先へ進む。

```bash
ndf progress finish <ステートマシンの ID> 確定仕様化 --output <出力のファイル> --reason <理由>
```

- **判定は工程の集合で行い、並びは見ない。** ドキュメントレビューの工程が `pr` → `cross-review` →
  `merged` を呼ぶため、同じ Skill が 2 回現れる。隣り合う 2 つの値を比べる判定にすると毎回ひっかかる
- **見る範囲は、いちばん先まで進んだ記録までとする。** まだ来ていない工程は欠落ではない
- 必須・条件付き・対象外の別はモードが決める。一覧は [SKILL.md](../SKILL.md) の「モードごとに起動する Skill」の表にある

### 進め方 `fast` の扱い

`pace` が `auto` のスプリントは `normal` と同じく全工程の記録を求める。

`pace` が `fast` のスプリントでは、トリガーで通す工程（`リファクタリング` / `コードレビュー`）と、
スプリントの終わりにまとめる工程（確定仕様化 / 振り返り）を、記録が無くても欠落として扱わない。
まとめる工程は、スプリントの終わりのプランが記録する。

## 対象にしないこと

**本番へのリリースの承認は含めない。** その承認は `release` が持つ。承認の所在を 2 つに分けない。
正式版のチャネルへ向けた Pull Request を塞ぐかは、対象リポジトリの CI が決める。
