# 通過工程の控えと、設計 Pull Request のマージの縛り

必須の工程を通らずに配布まで進んでも、それに気づく出力がどこにも出ない（#221）。設計
Pull Request のマージが、人間の承認を経ずに実行できる（#266）。この 2 つを、同じ tool
実行前の判定の上で扱う。

**この仕組みは任意である。** 控えを書けない環境でも工程はそのまま通り、承認の印
（ラベル `design-approved`）が定義されるまでマージの拒否は働かない。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| 盤面 | 進行を記録する GitHub Projects のプロジェクト 1 つ |
| 進行の記録 | `projects-sync.sh` の呼び出し 1 回 |
| 通過工程 | ある課題について、進行の記録が実際に書かれた工程の集合 |
| 控え | 通過工程を課題ごとに残したファイル |
| 承認の印 | 人間が設計を承認したことを表す、Pull Request に付くラベル |

## 有効にする

承認の印を作る。**この 1 回の操作が、マージの拒否を有効にする宣言を兼ねる。**

```bash
gh label create design-approved --description "ドキュメントレビューを人間が承認した" --color 0e8a16
```

新しい宣言ファイルは置かない。宣言があるのにラベルが定義されていない状態が作れてしまい、
そのとき人間は承認できないのに拒否だけが起きる。ラベルの定義そのものを宣言にすれば、
**承認の手段と有効化が同じ 1 つの対象になる。**

**印を偽装できないことは求めない。** 工程を進める AI も同じ資格情報を持つため、どの印も
機械的には付けられる。この仕組みが止めるのは、承認を求めずに工程を続けてしまうことである。

## 通過工程の控え

進行の記録のコマンドを観測して積む。**盤面は読み返さない。** 盤面は各フィールドの現在の値
だけを持ち、単一選択の独自フィールドの変化は課題の時系列にも残らない。盤面に載っていない
課題では記録そのものが生まれない。記録を書く**コマンド**は盤面の有無にかかわらず発行される
ため、そちらを観測すると両方の制約を受けない。

### 置き場所

リポジトリの中には置かない（変更として Pull Request に載るため）。次の順で決める。

```text
${CLAUDE_PLUGIN_DATA}/stages/            # 与えられていればここ
${XDG_STATE_HOME:-$HOME/.local/state}/ndf/stages/
${TMPDIR:-/tmp}/ndf-stages/              # どちらも作れないとき
```

ファイル名は `<所有者>__<リポジトリ>__<課題番号>.json` である。所有者とリポジトリは
`git config --get remote.origin.url` から取る。**通信しない。**

```json
{"version": 1, "repo": "devbasex/ai-plugins", "issue": 221, "mode": "standard",
 "stages": ["作業場所の用意", "要求と受け入れ条件", "設計", "ドキュメント再構成",
            "ドキュメントレビュー"],
 "updated_at": "2026-09-03T00:00:00Z"}
```

| 項目 | 内容 |
| --- | --- |
| `mode` | この課題を閉じる Pull Request に対して判定したモード |
| `stages` | 進行の記録が書かれた工程の並び。**工程を通ったことではなく、記録が書かれたことを表す** |
| 時系列の扱い | 事象の記録を採る。値を追加するだけで、既にある値を書き換えない。同じ値が 2 回来ても両方残す |
| 移行 | `version` が `1` 以外のファイルは読まず、記録が無いものとして扱う |
| 同時の書き込み | `mkdir` で排他を取り、その中で読み直してから置き換える。**排他を取れないときは書き込みそのものを行わない** |

### 鍵は課題のままにする

**モードを判定する単位は Pull Request だが、控えの鍵は課題番号である。** 判定の時点で
Pull Request の番号はまだ無い。工程表では `Pull Request` はモード判定より後にあり、判定は
「これから 1 本にまとめる変更」に対して行う。番号を鍵にすると、判定から作成までの記録の
置き場所が無くなる。

**「1 つの Pull Request に 1 つのモード」は、鍵ではなく値の一致で表す。** 判定した 1 つの
モードを、その Pull Request が閉じる課題すべての控えへ同じ値で書く。

そのため次の 4 つは変わらない。

| 契約 | 形 |
| --- | --- |
| 控えの名前 | `<所有者>__<リポジトリ>__<課題番号>.json` |
| 控えの JSON | `.repo` / `.issue` / `.mode` / `.stages` |
| `stage-check.sh` | `record <課題番号> <stage\|mode> <値>` / `report <課題番号>` |
| `projects-sync.sh` | `<課題番号> <キー> <値>`（盤面の項目は課題である） |

**記録が食い違うときは、記録の誤りである。** 1 本の Pull Request が閉じる課題の控えに
違うモードが入っていたら、**最も高いモードを取って**工程の充足を見る。食い違っていること
自体も案内に出す。**鍵の不足ではない**ため、鍵を Pull Request へ広げても解けない。

**排他を取れないときは、その 1 回の記録を捨てる。** 飛ばしても終了コード 0 で返って工程は
続き、飛ばした工程は報告の「記録なし」に含まれる。工程を止めることと、排他なしで書くことは
別である。

**`mkdir` の成功だけでは持ち主を 1 つに絞れない。** 実測した overlayfs では、同時に走らせた
6 つのうち 2 つが同じ名前の作成に成功した。印を書いてから読み直し、自分の印が残っていると
きだけ持ち主とする。競り負けた側はロックを消さずに待つ側へ回る。

## 呼び方

```bash
bash "$SCRIPTS/../skills/development-workflow/scripts/stage-check.sh" report <課題番号>
```

`$SCRIPTS` の決め方は [scripts-lookup.md](scripts-lookup.md) に
ある。この Skill のスクリプトは、その 1 つ上（プラグインの根）から辿る。

| 呼び方 | 出力 | 終了コード |
| --- | --- | --- |
| `record <課題番号> <stage\|mode> <値>` | 無し。排他を取れなかったときだけ標準エラーへ 1 行 | 0 |
| `report <課題番号>`（記録が無い） | 記録が無い旨の 1 行 | 0 |
| `report <課題番号>`（欠落が無い） | 通過工程の一覧 | 0 |
| `report <課題番号>`（欠落がある） | 通過工程の一覧と、記録の無い必須の工程 | 0 |
| 引数の誤り | 標準エラーへ 1 行 | 2 |

**終了コードで工程を止めない。** 呼び出し側の誤りだけを 2 で返すのは、`projects-sync.sh` が
採っている扱いと同じである。`record` は hook が自動で呼ぶため、手で呼ぶのは `report` だけである。

## 報告の読み方

```text
#161 の通過工程（standard）
  記録あり: 作業場所の用意 / 要求と受け入れ条件 / 設計 / ドキュメント再構成 / ドキュメントレビュー / 計画 / 実装 / 構造改善 / 実装レビュー / 完了判定 / Pull Request / 後片付け
  記録なし: 確定仕様化
実施済みであれば、記録してから先へ進んでください。
  bash "$SCRIPTS/projects-sync.sh" 161 stage "確定仕様化"
```

- **判定は工程の集合で行い、並びは見ない。** ドキュメントレビューの工程が `pr` → `cross-review` →
  `merged` を呼ぶため、`実装レビュー` と `後片付け` は 2 回ずつ現れる。隣り合う 2 つの値を比べる
  判定にすると毎回ひっかかる
- **見る範囲は、いちばん先まで進んだ記録までとする。** まだ来ていない工程は欠落ではない
- 条件付きの工程（モードによって要否が変わるもの）は `条件付き:` として必須と分けて出す
- モードの記録が無いときは必須の工程を判定しない
- 必須・条件付き・対象外の別はモードが決める。一覧は
  [SKILL.md](../SKILL.md) の「モードごとに起動する Skill」の表から機械で導ける

## Pull Request の作成の時点で見るもの

**配布の記録まで待たない。** `gh pr create` を観測し、本文の閉じる語が指す課題の控えを
読んで、記録の無い必須の工程を案内する（#424）。

| 何を見るか | 出すもの |
| --- | --- |
| モードの記録が無い | その旨 |
| 控えの記録が 0 件 | その旨。**v10.5.0 はこの状態で、gate が一度も走らなかった** |
| 工程表で `Pull Request` より前にある必須の工程に記録が無い | 工程名の一覧 |
| 閉じる課題どうしでモードが食い違う | 最も高いモードと、食い違っていること |

- **拒否しない。** 判定できないとき（`jq` が無い・閉じる語を取れない・控えが読めない）も
  何も出さずに通す
- **検査の終点は工程表の並びで決める。** 記録済みの最も先の工程に置くと、Pull Request を
  作る時点では常にその手前であるため、欠落が 1 件も出ない
- **「実装レビュー」だけは求めない。** `cross-review` は Pull Request が無いと回せないため、
  求めれば毎回欠落として出て、案内が読まれなくなる
- **`light` を外さない。** 必須の工程が少ないモードほど、通していないことが見えにくい

### 本文を読み取れる形

**閉じる語は Pull Request の本文にある。** 本文の渡し方によって、hook が受け取る未展開の
コマンドから読み取れるかが変わる。

| 形 | 読み取れるか |
| --- | --- |
| `--body "<本文>"` / `--body=<本文>` / `-b <本文>` | 読み取れる |
| `--body "$(cat <<'EOF' … EOF)"`（`pr` が必須と定める形） | 読み取れる。引用符の中の改行は語の一部として保つ |
| `--body-file <パス>` / `-F <パス>` | 読み取れる（ファイルを読む。無ければ何も出さない） |
| `--body-file -`（標準入力） | **読み取れない。** hook はコマンドの本文しか受け取らない |
| `--fill` / `--fill-first`（コミットから本文を作る） | **読み取れない** |
| `gh api .../pulls`（REST の経路） | **観測しない。** 対象は `gh pr create` に限る |

**読み取れない形では何も出さずに通す。** 案内が出ないことは、工程を通っていることの
裏付けにはならない。

## 設計 Pull Request のマージ

head のブランチ名が `design/` で始まる Pull Request のマージを、承認の印が付くまで止める。

| 何を見るか | どこから取るか | 取れないときの扱い |
| --- | --- | --- |
| マージの対象の番号 | コマンドの本文（`gh pr merge <番号>` / REST の経路の番号） | 現在のブランチ名から引く |
| head のブランチ名 | 番号があるとき `GET /repos/{所有者}/{リポジトリ}/pulls/{番号}` の `.head.ref` | 拒否する |
| 番号（本文に無いとき） | `GET /repos/{所有者}/{リポジトリ}/pulls?head={所有者}:{ブランチ名}` の先頭の要素 | 一致が 0 件のときも拒否する |
| 承認の印 | 同じ応答の `.labels[].name` に `design-approved` があるか | 拒否する |
| 印の定義の有無 | `GET /repos/{所有者}/{リポジトリ}/labels/design-approved` | 拒否する。定義が**無いことを確かめられた**ときだけ通す |

**問い合わせは REST に限る。** GraphQL は利用上限で落ちる（`gh pr view --json` が
`API rate limit already exceeded` を返した実測がある）。マージそのものも REST で行われる
ことがあるため、判定の対象とするコマンドの形も 2 つ拾う。

**判定できないときは拒否する。判定に要るコマンドが無い場合も含む。** `curl` の REST は
`gh` が無くても成立し、通せば判定が抜けたままマージが動く。通す理由にするのは、記録の
案内（#221）の側だけである。

拒否の理由には、**通すために何をするか**を書く。承認の印を付ける手順と、設計 Pull Request
でない場合にブランチ名を変える手順の両方を出す。判定できなかったときは、確かめられな
かった値も添える。

## 誤検知で正当な操作が止まらないための担保

| 起きうること | 記録の案内 | マージ |
| --- | --- | --- |
| `gh` / `jq` / `git` が無い。問い合わせが失敗する | 何も出力せず通す | 拒否する |
| Pull Request の番号を取れない | 判定に入らない | 現在のブランチ名から引く。ブランチ名が空（detached HEAD）のときと、一致が 0 件のときは拒否する |
| 承認の印がリポジトリに定義されていない | 判定に入らない | 通す（有効化の宣言にあたる） |
| `design/` で始まるが設計ではない Pull Request | 判定に入らない | 拒否する。理由にブランチ名を変える手順を書く |
| 控えが読めない・壊れている | 記録が無いものとして扱い、欠落を並べない | 判定に入らない |
| 同じ課題へ同時に記録が走る | 排他を取れた側の値は残る。取れなかった側の工程は記録の無い工程として挙がる | — |
| 判定に時間がかかる | — | hook の制限時間を 10 秒とし、判定の対象でないコマンドでは問い合わせない |

## 対象にしないこと

**本番への配布は含めない。** その承認は `release` が持つ。承認の所在を 2 つに分けない。
正式版のチャネルへ向けた Pull Request を塞ぐかは、対象リポジトリの継続的統合が決める。
この判定は関与しない。

**この Skill を呼ばない会話の単位では働かない。** hook はこの Skill の frontmatter が
登録するため、工程を通していない場面では走らない。拒否が働かない状態はこの仕組みを入れる
前と同じであるのに対し、判定が広く走る状態は新しい停止を生む。**通す側へ倒す。**
