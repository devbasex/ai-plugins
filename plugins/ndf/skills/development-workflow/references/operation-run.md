# 運用モードの実行

`operation` の「実装」の工程で行うこと。**この工程は外部の系の状態を変える。** 差分を
戻せば元に戻るコードの変更とは違い、**反映した瞬間に効き、取り消しても「その状態を見た人」は
戻らない。**

この文書が扱うのは、実行の範囲の決め方・承認の受け方・記録の残し方・失敗したときの止め方で
ある。**モードの判定基準は
[SKILL.md](../SKILL.md) が持つ**。ここでは判定が済んでいることを前提にする。

**対象のリポジトリと対象の系を仮定しない。** 置き場所も照会の手段も名指しせず、**探して
決める**形で書く。

## 1. 実行の範囲を書く

**先に文字にする。** 実行の前の承認が読むのはこの表であり、書かれていないものは承認の対象に
ならない。

| 項目 | 何を書くか |
| --- | --- |
| 対象の系 | どの系へ操作するか。**本番系か、検証用の系か**を明示する |
| 使う権限 | どの資格情報・どの役割で操作するか。**値そのものは書かない** |
| 行うこと | 何をどう変えるか。変更前の値と変更後の値 |
| 依存する項目 | 変える対象に結び付いている他の項目と、操作の後にそれがどう変わるか（下の「依存する項目を読み取る」） |
| 単位 | 実行を分けた 1 つ 1 つ。**単位ごとに成否が決まる粒度**にする |

**単位に分けるのは、失敗したときに部分適用の範囲を確定させるためである。** 1 つの塊として
実行すると、途中で失敗したときにどこまで反映されたのかが後から読めない。

**単位の粒度は「1 つのコマンドとその結果で成否が決まること」に置く。** 1 つの単位が複数の
系にまたがるなら、系ごとに分ける。

### 依存する項目を読み取る

**変える対象だけでなく、その対象に依存している項目も実行の前に読み取る。** 外す・消す・
置き換える操作は、対象に結び付いていた別の項目を巻き添えで変える。読み取らないまま
実行すると、承認の時点で示した「変更前と変更後」に無い変化が本番の系に起きる。

例: 二重に連携したカードの片方をグループから外したら、その連携に結び付いていた引き落とし
14 件が計算対象へ変わった。系が引き落としとカードの対応付けを連携ごとに持っていたためで
ある。

読み取り方:

- 対象の系が持つ読み取りの手段で、**対象を参照している項目**（結び付き・対応付け・
  集計の対象・権限の付与先など）を一覧にする
- 一覧の項目ごとに、操作の後にどう変わるか（変わらない・巻き添えで変わる・消える）を
  範囲の表の「依存する項目」へ書く。**巻き添えで変わる項目は、変更前と変更後の値も書く**
- 依存を読み取る手段が無いときは「読み取れない」と書く。読み取っていないことを、依存が
  無いことのように書かない

**巻き添えで変わる項目は、変える対象と同じ扱いにする。** 2 の取り消しの手段と 4 の承認の
対象に含める。

## 2. 取り消しの手段を単位ごとに書く

**単位ごとに、戻せるかどうかを先に決める。**

| 区分 | 書くこと |
| --- | --- |
| 戻せる | 戻す手順そのもの（実行するコマンドと、戻ったことの確かめ方） |
| 戻せない | **戻せないことと、影響が及ぶ範囲**（誰の何が変わるか、いつから効くか） |

**取り消せない単位は、実行の前にそのことを示す。** 承認はその前提で行われる。実行してから
「戻せなかった」と報告する形にはしない。

**「たぶん戻せる」は戻せる側に数えない。** 戻す手順を書けないものは、戻せない側として扱う。

## 3. 単位の型ごとに 1 件で分岐を踏む

**dry-run は、対象を特定するところで止めず、操作の分岐まで踏む。** 対象の件数が期待どおりでも、
操作の後に出る確認・選択・エラーの分岐は、操作してみるまで現れない。

例: 22 単位の dry-run が対象の行の特定まで全件通ったが、実行すると単位 18 で止まった。
操作の後の確認ダイアログのボタンの文言が想定（「OK / はい / 切り替える」）と違い、実際は
「実行する」だった。dry-run では押していないため見つからなかった。

踏み方:

- 単位を**操作の型**（同じコマンド・同じ画面の手順で進むもの）で分け、型ごとに 1 件を選ぶ
- 選んだ 1 件を、**確定の直前まで**進める。確認ダイアログ・選択肢・入力の検査など、確定の
  前に現れる分岐をすべて表示させ、文言と選択肢を記録へ残してから取り消す
- 検証用の系があれば、そこで確定まで実行して、確定の後に現れる分岐と依存する項目の変化も読む

**本番系で確定まで実行するのは、4 の承認の後に限る。** 確定の後にしか現れない分岐が残るときは、
その型の 1 件を実行の順の先頭へ置き、実行して読み直してから同じ型の残りへ進む。踏めなかった
分岐は「確定の後は未確認」と範囲の表へ書き、承認を求めるときに示す。

## 4. 実行の前に承認を得る

**この工程は「本番系へ届く操作」の承認ゲート（ゲート 2）に当たる**（[SKILL.md](../SKILL.md) の
「人手の承認を求める承認ゲート」）。**承認ゲートは 2 つのままで、この工程のために新しい承認ゲートを足さない。**

- 対象の系が**本番系**なら、承認を得るまで実行しない
- 検証用の系への操作は、提示して進めてよい
- 承認を求めるときに提示するものは
  [approval-request.md](approval-request.md) が定める

**提示するのは、1 の範囲の表（依存する項目を含む）と 2 の取り消しの手段と 3 で踏めなかった
分岐である。** 承認する側が読むのは、何が
どうなるかと、戻せるかどうかである。

## 5. 記録の置き場所を探して決める

**実行の記録はリポジトリの中のファイルへ書く。** `operation` でも Pull Request は通るため、
**この記録そのものが差分になる**。

**候補は順序ではなく一覧である。** 対象のリポジトリに実在するものを採る。

| 候補 |
| --- |
| 変更の記録を置いているディレクトリ |
| 課題や計画を置いているディレクトリ |
| 運用手順を置いているディレクトリ |

**順序を固定しないのは、上位の候補を持たないリポジトリで下位を取り逃がすためである。**
複数が実在するときは、**その変更を読む人が最初に開く場所**を選び、選んだ理由を記録の冒頭へ
1 行残す。

**どれも見つからないときは、リポジトリの根へ記録用のディレクトリを作り、その旨を完了報告へ
残す。** 候補が無いことを理由に記録を省かない。記録が無ければ差分が空になり、Pull Request を
作れない。

**記録はその時の出来事であり、リポジトリ知識ではない。** 知識の置き場所（仕様や手順の
ディレクトリ）へ混ぜない。実行で決まった設定が以後の判断の前提になるときは、確定仕様化の
工程が別に扱う。

### 設計を通る場合の書き先

**触る領域が「すべての変更」以外に 1 つ以上当たるとき、このモードでも `design` を通る**
（条件はその Skill の「触る領域を決める」の表が持つ）。**独立した設計文書は作らず、上で決めた
実行の記録と同じファイルの節へ書く。** 1 節で足りる内容のために設計 Pull Request が生まれる
形にしない。

**この手順書が既に求めているものを、設計の節へ再掲しない。**

| 何を書くか | どこが持つか |
| --- | --- |
| 実行の範囲、単位の分け方 | この手順書の 1 |
| 取り消しの手段、戻せない単位 | この手順書の 2 |
| 記録の置き場所 | この手順書の 5 |
| **その構成を選んだ理由** | 設計の節 |
| **非機能の実現方式**（このモードでは無条件の成果物） | 設計の節 |

**非機能の実現方式が無条件なのは、このモードが必ず外部の系の状態を変えるためである。**
可用性・セキュリティ・移行性・システム環境のいずれかに必ず当たる。書き方は `design` の
`references/nonfunctional.md` が持つ。

## 6. 単位ごとに実行し、結果を残す

**単位ごとに、コマンド・出力・終了コードの 3 つを残す。**

| 残すもの | 理由 |
| --- | --- |
| 実行したコマンド | 同じ操作を後から追える。**書き写しではなく、実際に実行した形で残す** |
| 出力 | 系が返した応答。**機微情報は伏せる**（後述） |
| 終了コード | **合否は終了コードで見る。** 出力の末尾だけでは成否が定まらない |

記録の形は次のようにする。**単位の見出しと、この 3 つが対応していれば書式は問わない。**

```text
## 単位 2: <何をしたか>

対象の系: <系の名前>  区分: 本番 / 検証
取り消し: 戻せる（手順は「取り消しの手段」の 2 番）

$ <実行したコマンド>
<出力>
終了コード: 0

反映の確認: <確かめた手段と結果／確かめられない場合はその旨>
```

### 反映の確かめ方も探して決める

**照会の手段を名指ししない。** 対象の系が持つ読み取りの手段を探し、**実行した経路とは別の
経路**で確かめられるならそれを使う。

- 別の経路で確かめられる → その手段と結果を記録へ残す。これはリリース後テストの工程にも
  当たる（工程表の `operation` 列を参照）
- 実行そのものの応答しか無い → **「確かめられない」と記録へ残す。** 確かめていないことを、
  確かめたことのように書かない

## 7. 失敗したら、その時点で止める

**失敗した単位より後の単位を実行しない。** 部分適用の範囲を確定させるためである。失敗を
無視して続けると、どこまで反映されたのかが後から読めなくなる。

止めた後に残すもの:

| 残すもの | 内容 |
| --- | --- |
| どこまで反映されたか | 成功した単位の一覧と、失敗した単位 |
| 失敗の内容 | 失敗した単位のコマンド・出力・終了コード |
| 戻したかどうか | 戻す手順を持つ単位を戻したか、戻さずに残したか。**判断の理由も書く** |
| 残りの単位 | 実行していない単位の一覧 |

**戻すかどうかは操作の性質で変わる。** この文書が求めるのは「どこまで反映されたか」を
残すところまでで、そこから戻すかは次のように決める。

| 状況 | 対応 |
| --- | --- |
| 途中の状態が系として成り立たない | 戻せる単位を逆順に戻す。戻した結果も記録へ残す |
| 途中の状態のままでも系が成り立つ | 戻さずに残してよい。**残したことと、その理由を書く** |
| 戻せない単位が含まれる | 戻せないことを記録へ残し、影響の範囲を完了報告へ書く |

**失敗を記録しないまま再実行しない。** 何が起きたのかが残らないと、同じ失敗を繰り返す。

## 8. 記録に機微情報を残さない

**資格情報・鍵・トークン・個人を特定できる情報を記録へ書かない。** 記録は差分として
Pull Request に載り、リポジトリの履歴へ残る。

| 対象 | 残し方 |
| --- | --- |
| 資格情報・鍵・トークン | **値を書かず、種類と取得元だけを書く**（例: 「環境変数から読む配備用の資格情報」） |
| 個人を特定できる情報 | 識別子へ置き換えるか、件数だけを残す |
| 出力に混ざったもの | **伏せてから記録へ貼る。** 伏せたことが分かるマーカーを残す |

**伏せた事実は残す。** 消した跡が無いと、読む側は出力が全部だと読む。

## 完了の条件

- [ ] 実行の範囲が単位に分かれており、単位ごとに取り消しの手段が書かれている
- [ ] 変える対象に依存する項目を読み取り、巻き添えで変わる項目が範囲の表に書かれている
- [ ] 単位の型ごとに 1 件で分岐を踏み、踏めなかった分岐が範囲の表に書かれている
- [ ] 本番系へ届く単位について、実行の前に承認を得ている
- [ ] 単位ごとにコマンド・出力・終了コードが記録に残っている
- [ ] 反映を確かめた手段と結果が残っている。確かめられない単位はその旨が残っている
- [ ] 失敗した単位がある場合、そこで止めており、部分適用の範囲が記録に残っている
- [ ] 記録に機微情報が含まれていない
