# 仕事を分ける実行方式を選ぶ

**仕事を別の文脈・別のプロセスへ渡すときは、この表から実行方式を選ぶ。** 同じ種類の仕事で実行方式が回ごとに
割れると、確実性も費用も読めなくなる（#680）。**小さな作業にサブエージェントの固定費を払わない
線引き**と、**新しい文脈で始めるか続けるかを決める費用の式**もここが持つ。委譲してよい対象としない対象は [context-window.md](context-window.md)、
起動指示の形は [agent-layers.md](agent-layers.md) が持つ。

## 例: supervisor が進行を記録し、既存の規約を調べる

1. 工程に入った supervisor は、起動指示の進捗記録を 1 行打つ。決まった手順なので
   **スクリプト**である。Skill も worker も要らない
2. 次に、ある規約が `references/` のどこにあるかを 3 ファイルの中から探す。`wc -l` で見ると
   合わせて 200 行で、worker を起こす固定費を下回る。**インライン実行**で読む
3. 同じ調べ物が `skills/` の 60 ファイルに及ぶと分かった。読む量が大きく、返す量は場所の
   一覧だけである。**サブエージェント**（worker の `調査`）へ出す

## 比べる実行方式

| 実行方式 | 何か | #845 の実行レベル |
| --- | --- | --- |
| インライン実行 | いまの会話の文脈で行う | レベル 3（その会話の LLM） |
| サブエージェント | ホストの Agent ツールで別の窓を起こし、報告を受け取る | レベル 3 |
| CLI 実行 | codex / agy / kiro-cli / claude を別プロセスで起動し、結果ファイルを読む | レベル 3（別の LLM） |
| 最小構成の `claude -p` | Tool と指示を絞った 1 回の判断 | レベル 2（分類の判断） |
| スクリプト | 決まった手順を bash / Python で実行する。長いものは背景で起動して完了通知を待つ | レベル 1 |

## 比べる観点

| 観点 | インライン実行 | サブエージェント | CLI 実行 | 最小構成の `claude -p` | スクリプト |
| --- | --- | --- | --- | --- | --- |
| 上の層の文脈 | 読んだ量がそのまま残る | 報告の量だけ残る | 結果ファイルを読んだ量だけ | 判断の出力だけ | 出力を読んだ量だけ |
| 固定費 | 無し | 起こすたびに払う（指示・規約・Tool の定義） | 起こすたびに払う。親の課金には載らない | 小さい（Tool と指示を絞る） | 無し |
| 確実性 | 手順を読んだ本人が行う | 報告と実物が食い違うことがある。「必須」の手順が置き換わる | CLI ごとに完了の判定と終了コードの癖が違う | 出力の形をチェックで縛れる | 手順どおりに動く。書いた範囲しか扱えない |
| 止まりにくさ | 待ちで応答を終えると止まる | 待ちで応答を終えると止まる（#656）。本体が落ちると全員止まる | 本体と別プロセスで動く | 1 回で終わる | 実行環境の上限を背景の起動で越えられる |
| 独立性 | 無し | 同じモデル・別の窓 | 別のモデル・別の視点 | 同じモデル・判断 1 つ | — |
| 資源 | 本体のメモリ | 本体のメモリ。並行の本数に数える（[parallel-work.md](parallel-work.md) の必須ルール） | 別プロセスのメモリ。外部の利用上限 | 別プロセス | 実行する処理による |
| 観測性 | 会話の記録に残る | 会話の記録に残る（`skill-stats --agents`） | 結果ファイルと実行の記録（`run_metrics.py`） | 出力を残せば読める | 出力と終了コード |
| 手順の従いやすさ | 読んだ本文に従う | 渡した指示に従う。Skill を読ませると本文の全体に従おうとする | 渡したプロンプトに従う | 1 つの問いに答える | 従う必要が無い |

**可搬性の列は置かない。** 4 ランタイムでの扱いは #888 が決める。

## 仕事ごとの選び方

| 仕事 | 実行方式 | 根拠（表の観点） |
| --- | --- | --- |
| 決まった手順（進捗記録・集計・チェックの実行・待ち） | スクリプト | 固定費も判断も要らない。LLM を起こさない |
| 小さな読解・1 コマンドの実行（下の線引きに当たるもの） | インライン実行 | 固定費が読む量を上回る |
| 読む量が大きく返す量が小さい読解（探索・全文の読解・ログの集計） | サブエージェント（worker の `調査` / `集計`） | 上の層の文脈に残るのが報告だけになる |
| worktree を書き換える修正 | サブエージェント（worker の `修正`） | [agent-layers.md](agent-layers.md) の「委譲の線」 |
| 別の視点のレビュー・提案 | CLI 実行 | 独立性 |
| 分類の判断 1 つ | インライン実行 | 最小構成の `claude -p` は #841 が入るまで選ばない |
| 600 秒を超える待ち | スクリプトを背景で起動して完了通知を待つ | [waiting.md](waiting.md) |

**supervisor のスクリプト駆動（#827 の方針）は、この表の上で「工程の進行をスクリプトへ、判断を
最小構成の `claude -p` へ」と位置づける。** 採否は #827 が決める。

## 小さな作業にサブエージェントを起こさない

**起こす前に 1 件ごとに判定する。** 次のどちらかに当たる作業は worker へ出さず、インライン実行で行う。

| # | 条件 | 例 |
| --- | --- | --- |
| 1 | **読む量の見込みが、worker の固定費を下回る** | 1 つのファイルの数十行を読む、`gh issue view` を 1 回打つ、進捗記録を打つ |
| 2 | **返す量が読む量と変わらない**（結果を上の層がそのまま読む） | 1 つのコマンドの出力を全部読む必要がある確認、短い差分の確認 |

- **固定費の値は書かない。** [context-window.md](context-window.md) の「固定費の値を規約へ
  書かない」に従い、導入した先で `skill-stats --agents` が測った値を使う。測っていなければ
  「起こす会話の最初の 1 回の読み込み量」を目安にする
- **読む量が見込めないときは、インライン実行で量だけを測ってから決める**（`wc -l` や件数の問い合わせ）
- **この判定は起こす前の見込みである。** 起こした後の測定で、フェーズの中の小さな worker を
  1 つに合わせるかを決めるのは #773 の候補 2 である。この線引きは #773 の測定の入力になるが、#773 の
  判定を置き換えない

## 新しい文脈で始めるか、今の文脈で続けるかを式で決める

**作業を新しい文脈（CLI 実行・新しいサブエージェント・新しい会話）へ出すか、今の文脈で続けるかは、
次の式で決める**。上の線引きの 1（読む量と固定費の比べ）を、呼び出しの回数とキャッシュの
倍率まで入れて量にしたものである。

### 例: supervisor が「PR の未解決のスレッドを数える」1 往復を持っている

ai-plugins の実測を入れた例である。倍率は正本の Opus 5.5 の値で計算した。

| 場面 | C | P | k | m | 結果 |
| --- | --- | --- | --- | --- | --- |
| 文脈 400k の supervisor が、最小構成の `claude -p` へ出すか | 400k | 7.3k（最小構成の `claude -p`） | 1 | 0 | **約 1 呼び出しで新しい文脈が得になる。** 出す |
| 文脈 100k の会話が、サブエージェントへ出すか | 100k | 60k（サブエージェントの固定費に近い値。中央値は 43k） | — | 0 | **約 38 呼び出しまでは続けた方が安い。** インライン実行で行う |

続けると、呼び出しのたびに C をキャッシュから読み直す。出すと、P をキャッシュへ書き込み、
結果の R を読み直す。前の例では C が大きく P が小さいため読み直しの差がすぐ書き込みを上回り、
後の例では C − P が小さいため上回るまでに多くの呼び出しが要る。

### 式

新しい文脈で始める方が得になるのは、次が成り立つときである。

**(C − P) × (r × k + w × m) > w × P + R**

| 記号 | 意味 | どこで測るか |
| --- | --- | --- |
| C | 続けた場合の文脈の長さ | 会話の記録の `usage`（`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`） |
| P | 新しい文脈で起動するたびに送る前提（指示・規約・Tool の定義） | サブエージェントは `skill-stats --agents` の固定費。CLI 実行は送るプロンプトと前提の量 |
| k | その作業の呼び出しの回数 | 同じ種類の作業の記録の集計 |
| m | その作業の間に、待ちでキャッシュが切れる回数 | 待ちの長さとキャッシュの寿命（サブエージェントは 5 分、本体の会話は 1 時間。#954） |
| R | 起動した側が結果を読み直す量 | 報告・結果ファイルの長さ |
| r | キャッシュの読み込みの倍率（入力の単価との比） | 下の「倍率の正本」 |
| w | キャッシュの書き込みの倍率（入力の単価との比。使う寿命の値） | 下の「倍率の正本」 |

**倍率の正本は ai-plugins の `scripts/token-usage.py` の換算表（`READ_RATES` / `READ_RATE_DEFAULT` /
`WEIGHTS`）である。** 読み込みの倍率はモデルで変わるため、この文書は値を写さない。モデルを
替えたら正本の値で計算し直す。

- **m ≥ 1（キャッシュが切れる長い待ちを挟む）なら、新しい文脈がほぼ必ず得になる。** 切れるたびに
  C − P を書き込み直すためである
- **1 往復の確認を CLI 実行へ出すのは、C が大きいときだけ割に合う**
- **P が大きく作業が短いときは、出すと損になる。** CLI 実行は前提を毎回送る。codex は PR 1 本あたり
  入力 1.8〜4.9M に対し出力 8〜27k だった（cross-review のスロットはラウンドごとに差分と指示を送り直す）
- P、k、m は導入した先で測った値を入れる。上の例の値は ai-plugins だけで使う
  （[context-window.md](context-window.md) の「固定費の値を規約へ書かない」）

### 前提を安くする

| 手 | 効き方 |
| --- | --- |
| 毎回同じ前提は、先頭をバイト単位で固定する | 2 回目以降の P がキャッシュの読み込みになる |
| 本文の代わりにパスを渡す | 要る範囲だけを相手が読むため、P が小さくなる |
| Skill は抜粋を渡す | 同上 |

### 式に入らない品質の面

**文脈が長いほど、正確さと想起が落ちる**（context rot。モデル提供者の公式ドキュメントの
「コンテキストウィンドウ」の節と、第三者が 18 モデルを比べた公開の研究。後者では 200k の窓で
50k 程度から落ち始めた）。**式が「続ける方が安い」を返しても、長い文脈で判断の質が落ちる分は
式に入らない。** C が [context-window.md](context-window.md) の目安（1 工程あたり 10 万）に
近いときは、式の結果よりカットポイントで切る規定を先に当てる。

## サブエージェントの Tool を定義で絞る

**worker が Skill を起動しない規則（[agent-layers.md](agent-layers.md) の worker の規則 6）を
文面だけにせず、worker のエージェント定義で Skill と Agent のツールを外す。** 定義は
`plugins/ndf/agents/worker.md`（`disallowedTools: Skill, Agent`）で、起動指示は
`subagent_type: ndf:worker` で指す。

| 書き方 | 理由 |
| --- | --- |
| Agent も外す | Skill だけを外した子が Agent で起こした `general-purpose` の孫は Skill を使えた。worker は葉であるという規則も同じ 1 行で定義が守る |
| 拒否の一覧（`disallowedTools`）で書く | 許可の一覧（`tools`）で書くと、書いた `Grep` / `Glob` が子に現れなかった |
| 例外の経路は定義を分ける | 定義の中で Skill を 1 つだけ許す書き方はできない。`cross-review` の修正は `general-purpose` のまま起動し、#859 の後に `ndf:worker` へ移す |

**`SKILL.md` の Read は定義では塞げない。** worker は抜粋を読むために `skills/` 配下の Read を
要し、Read をパスで分ける手段は定義に無い。規則 6 の文面で縛り、起動指示の「手順」に抜粋を
写して渡すことで読む理由を無くす。
