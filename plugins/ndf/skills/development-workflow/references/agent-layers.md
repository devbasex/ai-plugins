# 3 層で工程を通す（conductor / supervisor / worker）

**工程を 3 層へ出し、2 つの承認ゲート以外を人間の入力なしで通す。** 人間と対話しているセッション
（conductor）がフェーズごとにプラン（`ndf plan`）をキューで流し、プランが 1 つの作業を worker
（毎回新しい `claude -p`）へ出す。**supervisor の役割は `ndf plan` が主に担い、`ndf plan` で対応できないとき
（プランのテンプレートが無いときなど）だけ、supervisor のサブエージェント（`ndf:supervisor`）が代行する。** そのときは
conductor が代行のサブエージェントを起動し、代行が 1 つの作業をサブエージェント（worker）へ出す（下の「プランで流すか
supervisor で回すか」）。

**`/ndf:development-workflow` を呼べば 3 層へ出す。** 人がその場にいて指示を変えたいときは、
conductor へ伝えれば次のフェーズから反映する。

**この規約は無人でない進行にも効く。** 「上の層が起動した相手」と読めば、人が指示して
サブエージェントを起動する形にもそのまま当たる。

## 3 層の責務

| 層 | 何者か | 人間へ問えるか | 起動する相手 | 持たないもの |
| --- | --- | --- | --- | --- |
| conductor | 人間と対話しているセッション。`/ndf:development-workflow` を受ける | **問える**（`AskUserQuestion`） | プラン（キュー）。テンプレートの無いフェーズだけ supervisor。承認の前の読み手役だけ worker | 工程 Skill の実行。**`development-workflow` と `issue-plan-strategy` 以外を起動しない** |
| supervisor | 1 つのフェーズ（連続する工程のグループ）を通す役割。`ndf plan` が主に担い、プランのテンプレートが無いなど対応できないフェーズだけサブエージェント（`ndf:supervisor`）が代行する | 問えない | worker | 人間への質問、設計 Pull Request のマージ、承認のない本番の操作 |
| worker | 1 つの作業（調査・修正・検証・集計）を行うサブエージェント | 問えない | 起動しない。**別のサブエージェントを起動しない** | 人間への質問、進捗記録、収束の判定、設計の決定 |

**worker は葉である。** 深さ 3（worker がさらに起動する形）は実測していない。

| 層 | 持つ単位 | 何を持って帰るか |
| --- | --- | --- |
| conductor | スプリント | 着手の判定（課題の組み方・モード・到達点）、承認ゲートでの質問、承認の受け渡し、最後の報告 |
| supervisor（またはプラン） | フェーズ | 工程 Skill の起動、進捗記録、収束の判定、フェーズレポート |
| worker | 1 つの作業 | その作業の報告だけ |

**着手の判定は conductor が行う。** 課題の組み方・スプリントのモード・到達点の
置き直しは、最初のプランを流す（または最初の supervisor を起動する）前に決める。課題が多く本文の読解が conductor の
context window を埋めるときは、**読解だけを worker へ出す**。判定そのものは conductor が行う。
**conductor が worker を直接起動してよいのは、この読解と、承認や判断を求める前の読み手役の 2 つだけである。** 読み手役の手順と `prompt` の決まりは [approval-request.md の「読み手役の確認」](approval-request.md#読み手役の確認) にある。

## フェーズ

**フェーズは supervisor 1 つ（またはプラン 1 本）が通す工程のグループで、6 つある。** `context-window.md` のカットポイント 4 点で
切った下の表の 5 つと、`ndf route render release` のプランが通す**デプロイ**（プランの `"フェーズ"` の値は `開発版のデプロイ` / `リリース`）
である。[承認ゲート](../SKILL.md)の 2 つはそれぞれ設計とマージの終わりに当たる。

| フェーズ | 通す工程（工程表の行） | 単位 | 始まりの条件 | 終わりの条件 | 返す承認ゲート |
| --- | --- | --- | --- | --- | --- |
| 設計 | 要求と受け入れ条件 / 作業場所の用意 / 設計 / 詳細設計 / ドキュメント再構成 / ドキュメントレビュー（Pull Request を出して `cross-review` が収束するまで。設計は上限 3 ラウンド） | 設計 Pull Request（スプリントの設計を同時に並列で回す） | conductor がモードと課題を渡した | 設計 Pull Request の `cross-review` が収束した、または上限に達した | 設計 Pull Request のマージ（スプリントで 1 回） |
| 実装 | ドキュメントレビューのクリーンアップ（`merged`）/ 作業場所の用意（スプリントブランチから切る）/ 計画 / 実装。単位ごとに単位の PR をスプリントブランチ宛てに出し、`cross-review` を収束まで回してからマージして集める（下の「実装のフェーズの単位」） | レビューの単位（準備のタスクを含む単位を最初に、残りはスプリントの中で並列） | 設計承認ゲートでスプリントの設計 Pull Request がマージ済み | すべての単位の PR をスプリントブランチへマージした | 無し |
| 検査 | リファクタリング（スプリントの終わり）/ コードレビュー（つなぎ目）/ 完了判定 / Pull Request（スプリントのベースブランチ宛てを出し、Draft を外す） | スプリント | すべての単位の PR をスプリントブランチへマージした | スプリントの Pull Request のコードレビューが収束し、レビュー待ちにした | 無し |
| マージ | 確定仕様化 / スプリントの Pull Request のマージ / クリーンアップ / デプロイ（検証まで） | スプリント | スプリントの Pull Request が検査を終えた | 開発版のデプロイが済んだ。正式版だけをリリースするリポジトリではスプリントの Pull Request のマージとクリーンアップが済んだ。本番へのリリースが要らないリポジトリではリリースが済んだ | 本番系へ届く操作（要るときだけ） |
| 仕上げ | デプロイ（本番）/ リリース後テスト / 振り返り / 棚卸し | スプリント | 本番への承認を受け取った。要らないリポジトリではマージが終わった | 棚卸しの報告を返した（候補が 0 件で飛ばした場合を含む） | 無し |

**承認ゲートは 2 つで、増やさない。** 承認の止まり方と承認資料は `SKILL.md` の「人手の承認を求める
承認ゲート」と [approval-request.md](approval-request.md) が持つ。この文書はどのフェーズが返すかだけを決める。

| カットポイント（[context-window.md](context-window.md)） | フェーズの境 |
| --- | --- |
| 1 ドキュメントレビューのマージの後 | 設計 → 実装。マージするのは承認を取った conductor である |
| 2 リファクタリングとコードレビューの前後 | 実装 → 検査 |
| 3 スプリントの Pull Request を出した後 | 検査 → マージ |
| 4 マージのフェーズを終えた後（本番へのリリースの前） | マージ → 仕上げ。上のフェーズの表のマージの終わりの条件を満たしてから切る。開発版をリリースするリポジトリでは開発版のデプロイの後、正式版だけをリリースするリポジトリではスプリントの Pull Request のマージと**クリーンアップ**の後である。仕上げのフェーズの工程にクリーンアップは無いため、クリーンアップが済む前に切らない。本番へのリリースが要らないリポジトリではリリースの後で切る |

**Draft を開く位置は既存の規約のとおりである**（[stage-notes.md](stage-notes.md) のリファクタリングのセクション）。
フェーズの表は、その 1 度の呼び出しを実装のフェーズの終わりに置いただけで、工程表の順序を変えない。

**スプリントの中の並列は、設計と実装のフェーズで開く。** `ndf progress new` が `.ndf/` の設定から
設計のプランを設計 Pull Request ごとに、実装のプランを課題ごとに書き出し（レビューの単位に分けるときは、実装のフェーズの supervisor が単位ごとに組み直す。上の「実装のフェーズの単位」）、`ndf plan queue --max 3` が
同時に 3 本まで流す（`--max` を省くと、触るファイルの重ならないプランをすべて一度に起動する）。検査・マージ・仕上げはスプリントで 1 つずつ流す。スプリントブランチ（`sprint/<名前>`）は、
設計承認ゲートの承認とマージの後に、スプリントブランチのステージのプランがスプリントの起点（ブランチ戦略の設定の
`sprint.start`）から 1 度だけ切る。supervisor で回すフェーズも同じ単位と本数で起動する。

### 実装のフェーズの単位

**実装のフェーズの supervisor は、実行計画の実装の行（レビューの単位 1 つ）ごとに実装のプランを 1 本組む。** 下は課題 1 の条件 1・2 を満たす単位の例で、`acceptance` のステップは `ndf loop acceptance check --issue 1 --criteria 1:1 --criteria 1:2` になる。 単位の名前・含むタスク・満たす受け入れ条件は実装計画の「レビューの単位」の欄から読む。準備のタスクを含む単位を最初に流してスプリントブランチへマージし、残りの単位はその後に始める（残りはスプリントブランチから切るので、マージの前に始めると準備の変更を含まない）。

```sh
ndf route render implement --set branch=<単位のブランチ> --set base=<スプリントブランチ> --set issue=1 \
  --add acceptance=--issue --add acceptance=1 --add acceptance=--criteria --add acceptance=1:1 --add acceptance=--criteria --add acceptance=1:2 --out <プラン>
```

- **`acceptance` は並び全体を `--add` で 1 つずつ渡す。** `--issue` を必ず含め（含まない並びはプランを組む時点で断られる）、`--criteria <課題>:<条件>` は値 1 つごとに繰り返す。課題を束ねた単位は課題ごとの `--issue` を渡す（例 `--issue 3 --issue 4`）。渡さなければ `--issue <issue>` が補われ、その課題の条件をすべて照らす。`issue` には単位の課題のうち番号の最も小さいもの（代表の課題）を渡し、PR の題と本文もこの課題から作る
- **単位の欄が無い実装計画（欄ができる前に書いた計画など）と、実装計画を省いた課題は、課題 1 つを 1 単位にする。** 欄が無いことは実装計画の見出しで確かめ、`acceptance` は渡さない。実行計画の行の備考に「単位の欄なし。課題 1 つを 1 単位」と書く
- **実装のプランは単位の PR に `cross-review` を収束まで回し、レビューした HEAD をプランの状態ディレクトリの `reviewed-head` に書いて終わる。** 単位のマージは単位の worktree で `ndf ci merge --branch <単位のブランチ> --reviewed <reviewed-head のコミット>` を打ち、作業場所の HEAD がレビューした HEAD と違えばマージせずに止まる。スプリントブランチは本番へ届かないので、このマージは承認ゲートに当たらない
- **すべての単位をマージしたら、工程「実装」の出力に集めた時点 `gathered` を書く。** 工程から組む経路では工程「実装」の `gathered` のステップが `ndf progress gathered` を打つ。supervisor で回すときは手で打つ（下の「supervisor が守る規則」の 15）。工程「コードレビュー」はこの値を起点に、つなぎ目だけをレビューする

### プランで流すか supervisor で回すか

**フェーズは、下の表のプランで流すのが既定である。** conductor が `Agent` で supervisor を起動するのは、
「supervisor で回すとき」の列に当たるときだけである。プランは、supervisor が持つと抜けやすいステップ
（用語集のエントリポイントの検査、設計 Pull Request の「決めたこと」の同期、上限 3 ラウンドの judge、
進捗ログの `attention`）をテンプレートとして持つ。打つコマンドの並びは [waiting.md](waiting.md) の
「スプリントを流すコマンド」にある。

| フェーズ | プラン（`ndf plan` new` の種別） | ステージ（目録 `<out>/sprint.json`） | supervisor で回すとき |
| --- | --- | --- | --- |
| 設計 | `new sprint --design <課題>...` の設計のプラン（設計 Pull Request ごと）。終わりの judge が設計承認ゲートを返す。設計書を省くスプリントも `--design` で起動する（工程「設計」が実装計画を載せる） | 設計 → 設計承認ゲート | `--design` を渡さないときの要求と受け入れ条件（`requirements-design`）の工程。設計のプランはこの工程を持つ（課題の本文と仕様のコピーが一致すれば飛ばす） |
| 実装 | `new sprint` の実装のプラン（課題ごと。スプリントブランチ宛て。レビューの単位に分けるときは supervisor が単位ごとに組み直す）。スプリントブランチはその前のステージのプランが切る。単発は `new impl` | スプリントブランチ → 実装 | — |
| 検査 | `new sprint` の検査のプラン（スプリントの Pull Request を出し、リファクタリング・コードレビュー・完了判定を通してマージする）。単発は `new check`、`pace: fast` は `new check --since-last` | 検査 | — |
| マージ | スプリントの Pull Request のマージは検査のプランが、開発版のデプロイは開発版のリリースプランが持つ（クリーンアップは本番のリリースプランの最後のステップ） | デプロイ（検査のキューが `--then` で流す） | 確定仕様化（`plan-to-spec`）。worker へ委ねるときは全課題を 1 件の worker に委ね、起動指示の「手順」へ `plan-to-spec` の抜粋（`references/excerpt.md`）をコピーする。`normal` のプランはこの工程を持たない（`pace: fast` は `new close` が持つ） |
| 仕上げ | `new sprint` の本番のリリースプラン（本番へのリリース・リリース後テスト・クリーンアップ）。単発は `new release --channel prod` | `リリース承認ゲート` → `本番`（リリース承認ゲートの承認の後に、`本番` のステージの `command` を単独で流す） | 振り返り（`retrospective`）と棚卸し（`backlog-refinement`）。同じ supervisor が振り返りに続けて棚卸しを通す。`normal` のプランはこの 2 つの工程を持たない（`pace: fast` は `new close` が持つ） |
| リリース | `new sprint` の開発版と本番のリリースプラン。単発は `new release --channel dev` / `--channel prod` | デプロイ・本番 | —（テンプレートがあればプランだけが通す。無い期間は下の表の後を参照） |

**supervisor へ落とすのは、次の 2 つのときだけである。** 11.x では #3092 が `ndf progress new` へステージのプランの書き出しを足すまで、すべてのフェーズのテンプレートが無い。`ndf plan` に `new` は無い。
その間は、フェーズの表の 5 つ（設計・実装・検査・マージ・仕上げ）を supervisor で回す。**6 つ目のデプロイのフェーズ（リリースのプラン）は立てない。**
デプロイの工程（`release`）は、フェーズの表のとおりマージと仕上げの supervisor が通す。マージの supervisor は、開発版をリリースするリポジトリ
（リリースの形が開発版のチャネルを持つとき）だけ開発版のデプロイと検証を通す。正式版だけをリリースするリポジトリでは開発版のデプロイを飛ばし、
マージの完了条件にしない。`結果: 承認ゲート` は、本番へ届く操作（本番へのリリース・main へのマージなど）が残るときだけ、その操作の前で返す。
本番へ届く操作が無ければ承認ゲートを返さずに `結果: 完了` で終える。仕上げの supervisor は、起動指示の `承認` にリリース承認ゲートの承認があるときだけ本番へのリリースを通す（規則 1）。

| 条件 | 見分け方 | conductor の動き |
| --- | --- | --- |
| プランのテンプレートが無い | 表の「supervisor で回すとき」の列の工程、表に無いモードの組み方（`operation` の実行、`documentation` の素材の収集など）、リリースの形（ブランチ戦略の設定の `release.form`）のテンプレートが無い | その工程だけを supervisor で回し、残りはプランで流す |
| テンプレートに要る設定が無い | `ndf progress new` が設定の不足（ブランチ戦略の設定（`.ndf/project.json` の `branch_strategy`）、テストの設定（`.ndf/project.json` の `test`、無ければ `.ndf/supervise.json` の `test.command`））で止まる | 設定を足せるなら足して打ち直す。足せなければそのフェーズを supervisor で回す |

**`ndf plan --help` の説明を読んでプランを外さない。** `new sprint` は設計承認ゲートの前の設計から
書き出す（`--design` を渡したとき）。

### モードごとの組み方

**フェーズの名前は変えない。** モードは、各フェーズがどの工程を含むかと、承認ゲートを返すかだけを
変える。工程の要否は `SKILL.md` の「モードごとに起動する Skill」の表が唯一の基準である。

| モード | 組み方の差 |
| --- | --- |
| `standard` | 上の表のまま |
| `documentation` | 設計に素材の収集と出典の確定、仕上げに体裁レビューが入る。実装は執筆、検査はリファクタリングを含まない |
| `legacy-refactor` | 設計 Pull Request を分けないときは設計のフェーズを作らない。実装は現状固定テストと段階的改善、コードレビューは `pr-review` |
| `light` | 設計のフェーズを作らない。実装は `計画` の工程を含まず、検査はリファクタリングを含まない。本番の承認が要らなければ仕上げも作らない。仕上げを作らないときは、棚卸しをマージの最後に入れ、マージの終わりの条件に「棚卸しの報告を返した」を足す |
| `operation` | 設計が**本番系へ届く実行の前で承認ゲートを返す**。実装は実行（[operation-run.md](operation-run.md)） |
| `pace: fast`（モードに重ねる） | 実装はベースブランチへ直接入れる。検査はトリガーごと（実行条件が立ったときだけ。範囲は前回の検査からの差分）。設計承認ゲート・リリース承認ゲートは MVV 判定が承認ゲートを返したときだけ conductor が承認を取る（`ndf-gate:1` / `ndf-gate:2`）。確定仕様化・振り返り・棚卸しはスプリントの終わりのプランへ移る（[pace.md](pace.md)） |
| `pace: auto`（モードに重ねる） | フェーズと単位は `normal` と同じ。設計のプランが本番まで `--then` で流し、設計承認ゲート・リリース承認ゲートは MVV 判定が承認ゲートを返したときだけ conductor が承認を取る。本番のリリースプランはスプリントの中に入る（[pace.md](pace.md)） |

**作らないフェーズの工程は、次のフェーズの先頭へ入る。始まりの条件も一緒に移る。** 後ろにフェーズが無い
仕上げだけは、工程が前のフェーズ（マージ）の最後へ入り、終わりの条件も一緒に移る。承認ゲートを返す
フェーズは、中身が少なくても作る。

## 起動の指示

**このセクションは supervisor で回すフェーズ（「プランで流すか supervisor で回すか」）にだけ当たる。** プランで流す
フェーズは、[waiting.md](waiting.md) の「スプリントを流すコマンド」のキューと `wait` で起動する。

### conductor → supervisor

| 引数 | 値 |
| --- | --- |
| `description` | `<フェーズ>: <課題番号を空白区切り>`（例 `設計: #550 #657`）。フェーズの後ろは半角の `:` と空白 1 つ |
| `subagent_type` | その supervisor が最初に通す工程で選ぶ。収束ループ（リファクタリング・コードレビュー・ドキュメントレビュー）から始めるなら `ndf:supervisor-waits`（キャッシュの寿命 1 時間）、それ以外は `ndf:supervisor`（寿命 5 分）。定義が使えないときは省く（`general-purpose`）。選び方の全体は [context-window.md](context-window.md) の「supervisor の定義を選ぶ」 |
| `model` | 省く（conductor と同じモデルで動く） |
| `prompt` | 下の 10 項目と、守る規則 18 個 |

**`description` の先頭語は規約である。** 測定（`skill-stats --agents`）は先頭語からフェーズと
作業種別を読む。語彙に無い語で始めた記録は `その他` に落ち、どのフェーズが幾らの
context window を使ったかが読めなくなる。**語彙は次の 2 つだけである。**

| 種類 | 値 |
| --- | --- |
| フェーズ（supervisor） | `設計` / `実装` / `検査` / `マージ` / `仕上げ`（`デプロイ` はプランのフェーズの名前で、supervisor の `description` には使わない。テンプレートが無い期間のデプロイの工程はマージと仕上げに含める） |
| 作業種別（worker） | `調査` / `修正` / `検証` / `集計` |

`prompt` に必ず入れる項目:

| 項目 | 中身 |
| --- | --- |
| フェーズ | フェーズの名前と、通す工程の一覧（フェーズの表からコピーする。`結果: スイッチポイント` の後の起動では `次の工程` からコピーする） |
| 課題 | 課題番号 |
| モード | conductor が判定したモード |
| MVV | 承認済みの MVV のバージョンと本文の場所の 1 行。conductor が `ndf records mvv current --base <マージ先のブランチ>` を打ち、結果から書く。書き方は [project-mvv.md の「工程での読み方」](project-mvv.md#工程での読み方) |
| 作業場所 | worktree のパスとブランチ（まだ無ければ「無し」） |
| 前のフェーズレポート | 直前の supervisor の `## フェーズレポート` の本文をそのまま |
| 承認 | 承認ゲートの承認を受けた後なら、承認した内容と承認した時刻。無ければ「無し」 |
| 到達点 | 置き直した到達点（「到達点を置き直す」）。置き直していなければ「ゴール条件のとおり」 |
| 承認資料の置く場所 | 承認ゲートを返すときに承認資料を書くファイルの絶対パス |
| 作業ディレクトリ | supervisor が作業ファイルを置くディレクトリの絶対パス（例 `<scratchpad>/<フェーズ>-<課題番号>/`）。**conductor が supervisor ごとに決め、並行する supervisor どうしで重ならないようにする** |

**工程の進捗記録はスプリントのステートマシン（`ndf progress`）が持つ。** supervisor は進捗記録を打たず、`progress-tracking` も `development-workflow` も起動せずにフェーズを通せる。

**supervisor のフェーズレポートを受け取ったら、conductor はレポートの `終えた工程` に挙がった工程だけを 1 行ずつ終える。**
打たないと、通した工程がステートマシンで未着手のまま残る。`結果` が `止まった` や `スイッチポイント` のときも同じで、`終えた工程` に無い工程（まだ通していない工程・途中の工程）は終えない。`終えた工程` が `無し` なら何も打たない。プランで流したフェーズはプランが記録するので打たない。

```bash
ndf progress finish <ステートマシンの ID> "<工程>" --output <終えた工程のその行の出力の JSON> --reason "<理由>"
```

- `--output` には `終えた工程` のその行に書かれたパスをそのまま渡す。conductor は出力を自分で組み立てない
- 出力の `outputs` に要る文脈のキーは `ndf progress show` の各行の `outputs` にある（例 作業場所の用意は `worktree`・`branch`、設計は `design_pr`・`mvv_gate`）。型は [context.schema.json](../../../contracts/workflow/context.schema.json) にある
- git の外で打つときは `--cwd <リポジトリの中のパス>` を足す
- 操作の一覧は `progress-tracking` の「conductor の操作」の「プランの外で済ませた工程を終える」にある

supervisor が守る規則:

1. 承認ゲートに達したら承認を求めずに `結果: 承認ゲート` で返す。**設計 Pull Request をマージしない。** 本番系へ届く操作を、`承認` が無いまま行わない
2. **承認ゲート以外の Skill の確認は、提示して進める。** `pr` はブランチとファイルを示してから進め、
   `merged` は削除の一覧を示す。supervisor は人間へ問えないため、**確認待ちで止まらない**
3. **`development-workflow` を起動しない**（モードと工程は起動指示が持つ）。
   **スプリントを閉じるときだけ `progress-tracking` を起動して本文の手順に従う**
4. 待ちで応答を終えない。待ちの Tool から戻った後、同じ応答の中で次の作業へ進む
   待ち方は [waiting.md](waiting.md) に従う（`sleep` を挟んだ問い合わせの繰り返しと、出力ファイルの読み直しをしない）。
   **worker の中間通知を受けたときも応答を終えない。** 報告コピーの待ちを自分のバックグラウンドの処理として
   起動してから終える（[waiting.md](waiting.md) の「中間通知を受けたとき」）
5. 外部へ書く前に、既に書いたものがあるかを確かめる（Pull Request・コメント・進捗記録）
6. 範囲外の課題は `out-of-scope` で起票する
7. 委譲してよい作業は worker へ出す。委譲しない 5 つは自分で行う（「委譲の線」）。
   **小さな作業は worker へ出さずにインライン実行で行う**（[work-vessels.md](work-vessels.md) の線引き）
8. **worker の報告をそのまま conductor へ渡さない。** フェーズレポートへ畳む
9. 最後の応答の末尾にフェーズレポート（`## フェーズレポート`）を置く
10. モードを上げるべきだと分かったら、進めずに `結果: 止まった` で返す。`到達点` が置き直されていて、その到達点に達したときは、承認ゲートを返さずに `結果: 完了`・`次のフェーズ: 無し` で返す
11. **作業ファイル（スクリプト・初期化の出力・プロンプト）は、起動指示の「作業ディレクトリ」の中に置く。** conductor の scratchpad の直下には置かない（並行する supervisor と同じ名前で上書きし合う）。worker へ渡す `保存先` も、この作業ディレクトリの下のパスにする
12. 収束ループの工程（リファクタリング・コードレビュー・ドキュメントレビュー）の Skill を起動して hook に止められたら、同じ起動をやり直さずに `結果: スイッチポイント`・`次の工程: <その工程>` で返す。起動の前に済ませること（Pull Request を出す・進行を記録する）は、起動の前に済ませておく。**スイッチポイントを自分で決めない。** hook が通したら、そのまま続ける
13. **設計の工程（設計文書を書く・直す作業）は、`design` の [design-template.md の「承認する人が読む欄」](../../design/references/design-template.md#承認する人が読む欄) に従わせる。** 設計承認ゲートを返す前に、埋められる欄は埋める。承認資料を返す前に `ndf records mvv cite` で根拠の行を確かめ、結果の分岐に従う（[approval-request.md の「承認資料を組んだら」](approval-request.md#承認資料を組んだら)）
14. **フェーズの終わりの条件を満たしたら、Skill の本文が続きの作業を指示していても始めず、フェーズレポートを返す。** 続きの指示は、フェーズレポートの `理由` に「<Skill>: <続きの作業>（始めていない）」と書く。工程表とフェーズの表に無い作業は、Skill の本文が指示しても工程として扱わない
15. **工程を終えるたびに、その工程の出力の JSON を作業ディレクトリへ書き、フェーズレポートの `終えた工程` に工程とパスを足す。** 値は `ndf progress show` のその行の `outputs` のキーに、工程で得た実際の値を入れる（例 設計は `design_pr` に Pull Request の番号・`mvv_gate` に判定の結果のオブジェクト）。実装の `gathered` は、すべての単位の PR をスプリントブランチへマージした後にスプリントブランチの worktree で `ndf progress gathered` を打ち、結果の `outputs.gathered` をそのまま写す（マージ先がスプリントブランチの開いた Pull Request が 1 つでもある・worktree がマージしていないときは止まるので、直してから打ち直す）。途中で返す（`止まった`・`スイッチポイント`）ときも、終えた工程の分だけを載せる。形は工程の出力の規約（[stage-io.schema.json](../../../contracts/workflow/stage-io.schema.json) の `stage-out`）で、`steps` と `summary` が要る。`outputs` が空の工程は `outputs` を省く。**書いた後に `ndf progress check <ステートマシンの ID> "<工程>" --output <パス>` を打ち、`ok` になってから `終えた工程` に足す。** `check` は conductor の `ndf progress finish` と同じ規則で確かめ、ステートマシンへは書かない。`metrics.outputs` がその工程の置いてよいキーで、`warnings` は `finish` が捨てるキーである。`refused` なら `cause.detail` の誤りに従って出力を直し、打ち直す。起動指示がこの規則を渡さなくても行う。設計の `mvv_gate` は出力の JSON ファイルにだけ置き、フェーズレポートの本文へ写さない。出力の JSON ファイルは `mktemp` で作った新しいファイルに書いてから置き換える（下の「承認ゲートの前の MVV 判定」）
16. **起動指示の MVV の欄にあるスナップショット（本文と共通原則）の全体を、作業の前に読む。** 判断への使い方と人へ戻す形は [project-mvv.md の「工程での読み方」](project-mvv.md#工程での読み方) に従う。worker へは、起動指示の MVV の欄の 1 行をそのままコピーして渡す
17. **設計承認ゲート（`結果: 承認ゲート`）を返す前に、作業場所で `ndf records mvv gate --gate design --machine <ステートマシンの ID>` を打つ。** 結果は作業ディレクトリの `mvv-gate-design.json` に保存し、`outputs.mvv_gate` を設計の工程の出力と承認資料の「MVV 判定」の欄に載せる（下の「承認ゲートの前の MVV 判定」）。プランの経路では打たない
18. **リリース承認ゲートを手動の経路で返す前に、承認する PR を先に決め、`ndf records mvv gate --gate release --machine <ステートマシンの ID> [--expect-pr <承認する PR の番号>]` を打つ。** 結果は作業ディレクトリの `mvv-gate-release.json` に保存し、承認資料の「MVV 判定」の欄にだけ載せる（下の「承認ゲートの前の MVV 判定」）。プランの経路では打たない

```json
{"steps": [], "summary": "<工程> を supervisor が終えた", "outputs": {"worktree": "/work/repo/.worktrees/fix/x", "branch": "fix/x"}}
```

#### 承認ゲートの前の MVV 判定（規則 17・18）

**プランを使わずに承認ゲートを返す supervisor は、自分で MVV 判定を打ち、結果を承認資料に載せる。** プランの経路
（判定のステップ `design-mvv`・`release-mvv` を持つプラン）では判定のステップが打つので、打たない。判定の条件は
[pace.md の「MVV 判定」](pace.md#mvv-判定)、承認資料への載せ方は [approval-request.md の「MVV 判定の欄」](approval-request.md#mvv-判定の欄) にある。

打つ場所と保存先は、どちらの承認ゲートでも同じである。

- **打つ場所**: 起動指示の「作業場所」の worktree で打つ。設計承認ゲートでは、判定する PR がその worktree のブランチの開いた PR に決まる
- **保存先**: 起動指示の「作業ディレクトリ」の下の `mvv-gate-design.json`・`mvv-gate-release.json`。結果 JSON は PR から取った
  自由記述（判定の理由・保留の文）を含むので、コミットの対象になる worktree の中に置かない。作業ディレクトリが作業場所の worktree の
  下にある（`git -C <作業場所> rev-parse --show-toplevel` の下）なら、保存せずに `結果: 止まった` で返す（`理由` に作業ディレクトリが
  worktree の中にあることを書く）
- **書き方**: `mktemp` で作った新しいファイル（0600）に書いてから、所定のパスへ `mv` で置き換える。判定が `stopped` で終わったとき
  （終了コードが 0 でない）も置き換えるよう、判定のコマンドと `mv` を `&&` でつながない。打ち直しで同じパスへ書くときも、既にある
  ファイルの権限を引き継がない

```bash
tmp=$(mktemp "<作業ディレクトリ>/.mvv-gate-design.XXXXXX") && { ndf records mvv gate --gate design --machine <ステートマシンの ID> > "$tmp"; mv -f "$tmp" "<作業ディレクトリ>/mvv-gate-design.json"; }
```

規則 15 の工程の出力の JSON ファイルも、同じく `mktemp` で作ったファイルに書いてから置き換える。

**設計承認ゲート（規則 17）:**

1. 上のコマンドで判定を打ち、作業ディレクトリの `mvv-gate-design.json` に保存する
2. 結果の `outputs.mvv_gate` を、設計の工程の出力の JSON ファイル（規則 15）の `outputs.mvv_gate` へそのまま載せる
3. 承認資料の「MVV 判定」の欄を、同じ値から組む（[approval-request.md の「MVV 判定の欄」](approval-request.md#mvv-判定の欄)）
4. 承認資料の根拠の行を `ndf records mvv cite --gate design` で確かめる（[approval-request.md の「承認資料を組んだら」](approval-request.md#承認資料を組んだら)）

**リリース承認ゲート（規則 18。プランを使わず、本番系へ届く操作の前で `結果: 承認ゲート` を返す手動の経路。フェーズの表の「仕上げ」など）:**

1. **承認する PR を先に決める。** このリリースで承認する人がマージを承認する PR で、承認資料の「対象を開くためのもの」に載せる PR である

   | 場合 | 承認する PR | 判定のコマンドに渡すもの |
   | --- | --- | --- |
   | このリリースで `ndf release-steps assemble` を打ち、`ok` の結果 JSON に `outputs.pr` がある（版上げの PR を組み立てた） | `outputs.pr` の PR | `--expect-pr <outputs.pr>` |
   | ブランチ戦略がリリース用の PR を作らない（`ndf release-steps assemble` を打たない。`trunk` の `production_pr` など） | スプリントの PR そのもの | 渡さない（判定する PR が承認する PR である） |
   | リリース用の PR を作る戦略なのに、`ndf release-steps assemble` の結果が `ok` でない・`outputs.pr` が無い（`not_applicable` を含む） | 決められない | 判定を打たず、承認も求めない。`結果: 止まった` で返し、`理由` に「承認するリリース用の PR を特定できない」と `ndf release-steps assemble` の結果 JSON のパスを書く |

   文脈のキー `release_pr` は使わない（承認ゲートの時点ではまだ無い）。`gh` でブランチ名から PR を探すこともしない（同じブランチの PR が複数あると決まらない）
2. 作業場所で `ndf records mvv gate --gate release --machine <ステートマシンの ID> [--expect-pr <承認する PR の番号>]` を打ち、上の書き方で
   作業ディレクトリの `mvv-gate-release.json` に保存する。`--expect-pr` を渡すと、判定のコマンドが判定に使う入力の PR と比べ、違えば
   判定せずに（LLM を呼ばず、PR にコメントを書かずに）`not_applicable` で止まる
3. 結果で承認資料の「MVV 判定」の欄を組む。`ok` なら「MVV 判定の欄」の手順で、`ok` でなければ同じセクションの「判定の結果 JSON が `ok` でないとき」の
   文で載せる。どの結果でも承認ゲートは返す。結果の `outputs.mvv_gate` は工程の出力へは載せない
4. 承認資料の根拠の行を `ndf records mvv cite --gate release` で確かめる

**判定の中身を、フェーズレポートの本文へ写さない。** `終えた工程` にはファイルのパスだけを書き、`outputs.mvv_gate` の中身（判定の理由・
レッドライン・`why`・`holds`）を `理由` などへ写さない。conductor はパスを `ndf progress finish --output` へ渡すだけで、中身を読んで人へ
転送しない。`mvv-gate-<区分>.json` は手元の記録で、呼び出し元へは返さない。

**`ndf plan next` / `queue` で回すフェーズの待ち方と `progress.jsonl` の読み方は、[waiting.md](waiting.md) の「`ndf plan` の進捗ログ」に従う。**

### supervisor → worker

| 引数 | 値 |
| --- | --- |
| `description` | `<作業種別>: <一言>`（例 `調査: 既存の規約の突き合わせ`） |
| `subagent_type` | **`ndf:worker`**（Skill と Agent のツールを外した定義。理由は [work-vessels.md](work-vessels.md) の「サブエージェントの Tool を定義で絞る」） |
| `model` | 省く（supervisor と同じ）。`調査` と `集計` は軽いモデルでよい（「モデルを選ぶ」） |
| `prompt` | 作業・入力・MVV・手順・読む Skill・返す形・保存先・作業の結果ファイルの 8 項目と、守る規則 8 個 |

| 項目 | 中身 |
| --- | --- |
| 作業 | 何を調べる・直す・実行する・数えるか。**1 つに絞る** |
| 入力 | 対象のパス・Pull Request 番号・指摘の場所など |
| MVV | supervisor が受け取った MVV の欄の 1 行をそのままコピーする。受け取っていなければ、supervisor が [project-mvv.md の「工程での読み方」](project-mvv.md#工程での読み方) のコマンドを打って書く |
| 手順 | 作業に要る手順の抜粋（呼び出し 1 行・結果の読み方・判断の基準）。**抜粋の元の Skill の `references/excerpt.md` をコピーする。** 抜粋が無い Skill の手順が要るときは、supervisor が要る段落だけをコピーする（抜粋の形は `plugins/ndf/skills/EXCERPTS.md`） |
| 読む Skill | 作業の前に読む規則の Skill の名前と `SKILL.md` の絶対パス。工程の名前は、起動指示の「フェーズ」に挙がった工程のうち、いま通している工程の名前である。**supervisor は下の「工程ごとに読む規則の Skill」の表から名前を取り、絶対パスは `ndf` の実体の位置から `"$(dirname "$(readlink -f "$(command -v ndf)")")/../skills/<名前>/SKILL.md"` で解いて並べる。** 工程に入る前の作業と、表に無い工程は「無し」と書く。1 つの作業が 2 つの工程にまたがるときは、工程ごとに作業を分けて渡す。パスのファイルが無ければ欄を空にせず、supervisor が `結果: 判断が要る` で返す。**欄は `prompt` の本文に置く** |
| 返す形 | `## 作業の報告` の 5 項目 |
| 保存先 | 長い出力と**報告コピー**を書くファイルの絶対パス（報告にはパスだけを載せる）。**worker は最後の応答の前に、長い出力の有無に依らず `## 作業の報告` のセクションを同じ中身で `ndf worker append --report "<保存先>" --done` で書く**（報告の末尾へ足し、続けて完了マーカー `<保存先>.done` を作る）。長い出力は報告の前に置き、できるだけ同じ 1 回の `--done` の本文にまとめる（分けて先に書くと `ndf` の起動が 1 回増える）。本文はどちらも `<<'NDF_REPORT'` のヒアドキュメントで渡す。`Write`・`Edit` の Tool とリダイレクト（`>`・`>>`・`: >`）で `保存先` と完了マーカーを書かない。supervisor は「無し」にせず、worker ごとに `ndf worker prepare --dir <自分の作業ディレクトリ> --name <worker の名前>` を 1 回打ち、結果 JSON の `metrics.paths.report` をそのままコピーして渡す。**`<worker の名前>` は `[A-Za-z0-9._-]` の 1〜64 文字で、同じ作業ディレクトリで稼働中の worker と重ならない名前にする**（`prepare` は同じ名前の報告・完了マーカー・結果ファイルを消して使い回す）。エージェントの名前（`worker` など）をそのまま使わず、`<作業種別の英字>-<Issue 番号>-<連番>`（例 `survey-550-2`）のように起動ごとに変える。起動の回数: 従来の `: >`・`Write`・`Read` の代わりに、worker 1 件につき、通常の完了通知（最後の応答で報告を受け取る）では `ndf` を `prepare` と `append --done` の 2 回起動する。中間通知を受けて `metrics.paths.done` を待ち、報告コピーを回収するときだけ `ndf worker collect` を足して 3 回になる（[waiting.md](waiting.md) の「中間通知を受けたとき」）。通常の完了通知で `collect` を打たない（Tool の呼び出しの回数は変わらない）。リンクをたどらずに読み書きするのに要る起動で、これより増やさない |
| 作業の結果ファイル | `作業の結果ファイル: <絶対パス>` の 1 行。supervisor は保存先と同じ 1 回の `ndf worker prepare` の結果 JSON の `metrics.paths.result` をそのままコピーする。**worker の作業の成否は、このファイルの `status` だけで決める**（下の「作業の結果ファイル」） |

工程ごとに読む規則の Skill（表に無い工程は「無し」）:

| 工程 | 読む Skill |
| --- | --- |
| 要求と受け入れ条件・設計・詳細設計・ドキュメント再構成・ドキュメントレビュー・計画・完了判定・Pull Request・確定仕様化・振り返り・棚卸し | `document-style` |
| 実装 | `logging-guidelines` |

worker が守る規則:

1. 人間へ問わない。**別のサブエージェントを起動しない**
2. 進行を記録しない（記録は supervisor が行う）
3. 収束の判定・設計の決定・受け入れ条件の書き換えを行わない。判断が要るときは `結果: 判断が要る` で返す
4. 最後の応答の前に作業の結果ファイルを書き（下の「作業の結果ファイル」）、末尾に `## 作業の報告` を置く
5. 待ち方は [waiting.md](waiting.md) に従う。バックグラウンドの処理を残したまま応答を終えない。`Monitor` で待つときも同じで（`Monitor` の通知で再開はされるが、supervisor には中間通知が届く）、長い出力が無くても、報告コピーと `<保存先>.done` を 1 回の `ndf worker append --report "<保存先>" --done` で書く（`保存先` は supervisor が必ず渡す）
6. **Skill を起動しない。工程 Skill の `SKILL.md` を読まない。** 手順は起動指示の「手順」に従う。手順が足りないときは `結果: 判断が要る` で返す。**起動指示が Skill の起動そのものを手順として渡したときだけ、その 1 つを起動してよい**。**起動指示の「読む Skill」に挙がった `SKILL.md` は作業の前に読み、その規則で作業する**（挙がっていない `SKILL.md` は読まない）
7. **手段（コマンド・手順の順序・Tool）は状況に合わせて変えてよい。** 作業を妨げる不具合が作業場所の中で直せ、[../SKILL.md](../SKILL.md) の「即時修正」の 4 条件を満たすなら、止まらずに直して続け、報告の「見つけたもの」に書く。作業場所の状態が想定と違っても（detached HEAD など）作業場所の中で完遂する。**指示された置く場所（作業場所・ブランチ・結果ファイルや出力のパス）と受け入れ条件・範囲は変えない。** 置く場所どうしが食い違ったら、どちらも選ばずに `結果: 判断が要る` で返す
8. **起動指示の MVV の欄にスナップショットのパスがあれば、本文と共通原則の全体を作業の前に読む。** 判断が MVV に反する疑いがあれば、進めずに `結果: 判断が要る` で返す（[project-mvv.md の「工程での読み方」](project-mvv.md#工程での読み方)）

**例外は今 `cross-review` の修正（`/ndf:fix` を渡す経路。`general-purpose` で起動する）だけで、#859 が抜粋へ置き換える。** 起動してよいかは起動指示を書く側が決める。

## 報告の形

### 作業の報告（worker → supervisor）

```markdown
## 作業の報告

- 作業: 調査
- 結果: 完了
- 見つけたもの: 3 件（`context-window.md:21` / `parallel-work.md:88` / `stage-notes.md:106`）
- 保存先: /tmp/claude-1000/<…>/scratchpad/設計-550/survey-550.report.md
- 次にすること: 無し
```

| 項目 | 値 | 空のとき |
| --- | --- | --- |
| 作業 | 作業種別の語彙のどれか | 空にしない |
| 結果 | `完了` / `判断が要る` / `できなかった` | 空にしない |
| 見つけたもの | 件数と、場所（ファイルと行・Pull Request のコメントの ID など） | `無し` |
| 保存先 | 長い出力と報告コピーのファイルの絶対パス。supervisor が渡したパスを、長い出力の有無に依らず書く | 空にしない（supervisor が必ず渡す） |
| 次にすること | supervisor が続けて行うことの候補を 1 行 | `無し` |

### 作業の結果ファイル（worker → supervisor）

worker は報告を終える前に、渡された保存先へ結果 JSON（[結果のスキーマ](../../../contracts/schemas/result.schema.json)の形。終了コードは [exit-codes.md](../../../docs/contracts/exit-codes.md)）を 1 行で書く。

```bash
ndf contracts emit --tool worker --status ok --summary "<1 行の要約>" --out "<作業の結果ファイル>"
ndf contracts emit --tool worker --status gate --summary "<判断が要る理由>" --route retry - --out "<作業の結果ファイル>"
ndf contracts emit --tool worker --status stopped --summary "<1 行の要約>" --cause work_stopped "<できなかった理由>" --out "<作業の結果ファイル>"
```

| 作業の報告の `結果` | `status` | 添えるもの |
| --- | --- | --- |
| `完了` | `ok` | 残した作業・確かめられなかった受け入れ条件があれば `ok` にしない |
| `判断が要る` | `gate` | `--summary` に判断が要る理由。`gate` は `--route` が要る（打ち直すなら `retry`） |
| `できなかった` | `stopped` | `--cause work_stopped` に理由 |

形が違えば `ndf contracts emit` が終了コード 2 で拒み、ファイルは書かれない（`gate` は 10、`stopped` は 1 で終わるが、ファイルは書かれる）。worker は直して打ち直す。**supervisor（`ndf plan` の
work のステップを含む）は、このファイルが `ok` のときだけ作業を成功と読む。** ファイルが無い・読めない・形が違うときは
失敗として扱い、`## 作業の報告` の文から成否を決めない。報告のセクションは人と conductor が経緯を読むために残す。

### フェーズレポート（supervisor → conductor）

supervisor の最後の応答の**末尾**に置く。見出しの後ろに他の見出しを置かない。

```markdown
## フェーズレポート

- フェーズ: 設計
- 課題: #550 #657
- 結果: 承認ゲート
- 承認ゲート: 設計 Pull Request のマージ
- 次のフェーズ: 実装
- Pull Request: https://github.com/<所有者>/<リポジトリ>/pull/<番号>
- 最後に記録した工程: ドキュメントレビュー
- 終えた工程: 設計=/tmp/claude-1000/<…>/scratchpad/設計-550/設計.output.json / ドキュメントレビュー=/tmp/claude-1000/<…>/scratchpad/設計-550/ドキュメントレビュー.output.json
- 使った worker: 調査 2 / 修正 1
- 承認資料: /tmp/claude-1000/<…>/scratchpad/approval-550-657.md
- 理由: 無し
```

| 項目 | 値 | 空のとき |
| --- | --- | --- |
| フェーズ | フェーズの語彙のどれか | 空にしない |
| 課題 | `#番号` を空白区切り | 空にしない |
| 結果 | `完了` / `承認ゲート` / `止まった` / `スイッチポイント`。`ndf` の結果 JSON（[結果のスキーマ](../../../contracts/schemas/result.schema.json)）の `status` は `ok` → `完了`・`gate` → `承認ゲート`（`presentation_path` を `承認資料` へ）・`stopped` → `止まった` とそのままコピーする | 空にしない |
| `承認ゲート` | `設計 Pull Request のマージ` / `本番系へ届く操作` | `無し` |
| 次のフェーズ | フェーズの語彙のどれか。`スイッチポイント` のときは同じフェーズで、次の行に `- 次の工程: <工程表の行名>` を足す（`スイッチポイント` のときだけ書く項目） | `無し`（最後のフェーズ、または止まったとき） |
| Pull Request | URL を空白区切り | `無し` |
| 最後に記録した工程 | 工程表の行名 | 空にしない |
| 終えた工程 | この supervisor が終えた工程だけを `<工程表の行名>=<出力の JSON の絶対パス>` で ` / ` 区切り。終えていない工程・途中の工程は載せない。conductor はこの行だけを `ndf progress finish` で終える | `無し`（1 つも終えていないとき） |
| 使った worker | 作業種別ごとの件数 | `無し` |
| `承認資料` | 絶対パス。`approval-request.md` の 2 層を持つ | `無し` |
| 理由 | 1 行 | `無し` |

**報告の中に次のフェーズの名前が入る。** そのため conductor は工程表を読まずに次の
supervisor を起動できる。

**worker の報告は conductor へ転送されない。** supervisor が畳むため、
**conductor が 1 つのフェーズについて読む報告は 1 件である**。worker を 5 つ使っても、
conductor が読む量は変わらない。

**プランで流したフェーズの結果は、キューの done の `status` で読む**（[waiting.md](waiting.md) の
「`ndf plan` の進捗ログ」）。`gate` なら承認資料を添えて承認を取り（`AskUserQuestion` に `ndf-gate:1` か `ndf-gate:2` を付ける）、承認の後に目録（`<out>/sprint.json`）の
次のステージの `command` を打つ。下の表は supervisor のフェーズレポートにだけ当たる。

**conductor が見るのは、見出しの有無と `結果` の 2 つである。**

| 見出しの有無 | `結果` | conductor の動き |
| --- | --- | --- |
| 無い | — | `SendMessage` で続けさせる（下の「報告が無いまま終わったとき」） |
| ある | `完了` | `次のフェーズ` を起動する。`無し` なら到達の報告 |
| ある | `承認ゲート` | `承認資料` を読み、`AskUserQuestion` で承認を求める（`metadata.source` は `設計 Pull Request のマージ` なら `ndf-gate:1`、`本番系へ届く操作` なら `ndf-gate:2`。[asking.md](asking.md)）。`設計 Pull Request のマージ` なら conductor がマージしてから `次のフェーズ` を起動する。`本番系へ届く操作` ならマージせずに `次のフェーズ` を起動する。**モードやフェーズの名前から分岐しない** |
| ある | `止まった` | `理由` を添えて利用者へ報告し、終える |
| ある | `スイッチポイント` | 同じフェーズを、`次の工程` から通す supervisor として起動し直す。`subagent_type` は起動の指示の `subagent_type` の欄で選び、起動指示の「フェーズ」の工程の一覧は `次の工程` からコピーする。「前のフェーズレポート」にスイッチポイントの報告を入れる。承認ゲートを問わない。**同じ `次の工程` の `スイッチポイント` が続けて 2 回返ったら、`止まった` と同じに扱う** |

**supervisor が worker の報告を見るときも同じ規則を使う。** `結果: 判断が要る` は supervisor が自分で判断する。

### 報告が無いまま終わったとき

待ちの Tool から戻った時点で応答を終えた相手は、上の層には「完了」の通知で届く。**報告の
見出しが無ければ完了として扱わない。**

**同じ相手へ続けさせるのは 3 回までである。**

| 回 | 上の層の動き |
| --- | --- |
| 1〜3 | `SendMessage` で「報告の形で終えるまで続ける」と送る |
| 4 | **4 回目は送らず**、相手の名前と最後の応答の 1 行を添えて上へ返す（conductor なら利用者へ報告して終える） |

**レートリミット中断からの再開は、この回数に数えない。**

## conductor の報告

conductor は到達したときと止まったときに、利用者への応答の末尾へ次の表を置く。
人のいない実行（`NDF_FACTORY_RUN`）では、表の後ろにセグメントの報告を置いてセグメントを終える（[asking.md](asking.md) の「人のいない実行」）。

```markdown
## フェーズの一覧

| フェーズ | 課題 | 結果 | 使った worker | 報告なしで続けさせた回数 | レートリミット中断から再開した回数 |
| --- | --- | --- | --- | ---: | ---: |
| 設計 | #550 #657 | 承認ゲート | 調査 2 / 修正 1 | 0 | 0 |
```

| 列 | 値 |
| --- | --- |
| フェーズ・課題・結果 | その supervisor の最後の `## フェーズレポート` の値。報告が無いまま止まったフェーズは `結果` を `報告なし` にする |
| 使った worker | フェーズレポートの同じ項目 |
| 報告なしで続けさせた回数 | 見出しが無いときに送った `SendMessage` の数（0〜3）。**記録からは見分けられないため、conductor が送るたびにフェーズごとに数えて持つ** |
| レートリミット中断から再開した回数 | 「中断の点検」の手順 2 で送った `SendMessage` の数 |

**同じフェーズを工程の頭から起動し直したときと、`スイッチポイント` の後に工程の途中から起動し直したときは、別の行にする。**

**止まるときは、この表を 1 回出す。** 出す時点は 3 つである。

1. `AskUserQuestion` を出す前
2. 失敗を報告する前
3. バックグラウンドの待ちを起動して応答を終える前

見回りは時間とともに間隔が伸び、やがて止まる。**現在地を出しておかないと、人が気づける
手がかりが残らない。**

## モデルを選ぶ

**既定は、層ごとに `model` を省くことである。** 省くと上の層と同じモデルで動く。

**軽いモデルへ落としてよいのは、次の 2 つを両方満たす相手である。**

1. 決定・受け入れ条件・収束の判定を書かない
2. 出力を、その外のチェック（CI・承認ラベルの判定・後のフェーズのレビュー・supervisor の
   読み直し）が受け止める

| 相手 | 2 つを満たすか |
| --- | --- |
| worker の `調査` と `集計` | **両方満たす。** 落としてよい |
| worker の `修正` と `検証` | 満たすかは対象による。落とすなら、その後のレビューで受け止める |
| supervisor | 満たさない（収束の判定と進捗記録を持つ） |
| conductor | 満たさない（承認ゲートの判断を持つ） |

**初期値は全層で既定のモデルとし、落とすかどうかは測定を見て振り返りで決める**
（`skill-stats --agents`）。

## 委譲の線

**委譲してよい対象と、しない対象は [context-window.md](context-window.md) の表が持つ。**
新しい判断基準をここで作らない。**どの実行方式（インライン実行・サブエージェント・CLI 実行・最小構成の
`claude -p`・スクリプト）へ渡すかと、小さな作業にサブエージェントを起動しない線引きは
[work-vessels.md](work-vessels.md) が持つ。**

| 作業種別 | 何をさせるか |
| --- | --- |
| `調査` | どのファイルにあるかの探索、全文の読解と要点の取り出し、範囲外の課題の下調べ |
| `修正` | レビューの指摘の修正とコミット。送る（push）のは起動した側 |
| `検証` | テストとチェックのコマンドの実行、失敗の要約 |
| `集計` | 差分・ログ・記録の集計 |

**委譲しない 5 つは worker へ出さない。**
モード判定・承認ゲートの判断・収束の判定・設計の決定と理由の記録・受け入れ条件の書き換えは、
**supervisor か conductor が持つ**。worker が返すのは項目と場所と根拠であって、判断ではない。

**`cross-review` の収束ループを回すのは supervisor である。** 修正はその supervisor が
起動する worker（作業種別 `修正`）で行う。

## 並行の本数

**並行の本数を数える単位は supervisor である。** **supervisor 1 つが 1 本で、1 つの worktree に
当たる。** worker はその 1 本の中で動くため、別に数えない。

**同時に動かす worker は、1 つの supervisor につき既定 1 つとする。** 増やすときは 1 本あたりの
見込みを測り直してから増やす。**本数を抑える必須ルールは [parallel-work.md](parallel-work.md)、
本数の測り方と実行計画は `issue-plan-strategy` の
[references/execution-plan.md](../../issue-plan-strategy/references/execution-plan.md) が持つ。**
この文書は数える単位だけを決める。

## 到達点を置き直す

**ゴール条件が Pull Request より後の工程を含むとき**（確定仕様化・クリーンアップ・リリース・リリース後
テスト・振り返り）、マージに他者の承認が要るリポジトリでは工程がそこで止まる。**他者の承認は
この会話の外にある。** ruleset の必須レビュー・CODEOWNERS・チームのレビュー担当が承認するまで、
会話の中でできることが無い。

**着手の時点で conductor が判定する。** Pull Request を出してから気づくと、そこまでの工程を
進めた後で待ち方を決めることになる。

```bash
gh api "repos/<所有者>/<リポジトリ>/rules/branches/<起点>" --jq '[.[] | select(.type == "pull_request")]'
gh api "repos/<所有者>/<リポジトリ>/branches/<起点>/protection" --jq '.required_pull_request_reviews'
```

| 結果 | 到達点 |
| --- | --- |
| 承認が要る | **Pull Request の提出とレビューの収束**へ置き直す |
| 要らない | ゴール条件が指す工程まで |
| 判定できない | ゴール条件が指す工程まで進み、マージが拒否された時点で置き直す |

**判定できないことを理由に待ち続けない。** 判定の手段が無いリポジトリでも、マージの拒否は
観測できる。

置き直したときは、収束まで進めた時点で**ゴールに到達したものとして報告する**。報告に
**停止理由**（マージに他者の承認が要る）と、**承認が付いた後に再開する手順**（残りの工程の
名前と、それを呼ぶコマンド）を書く。残りの工程は、承認が付いた後の別の起動で行う。

**待ち続けることと、conductor が自分でマージすることのどちらも採らない。** 前者は工程が
進まないまま時間と実行の費用を消費する。後者は他者の承認を経ない変更が起点ブランチへ入り、
必須レビューを置いた意味が失われる。
