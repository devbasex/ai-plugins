# 承認を求めるときに提示するもの

工程の途中で人間の承認を求める場面は 2 つある。**設計 Pull Request のマージ**の前と、
**本番系へ届く操作**の前である。**どちらも、この会話の中で利用者に判断を求める
形である**ため、提示するものを 1 箇所で定める。2 箇所へ同じ表を書くと、片方だけが更新される。

**要否の決まり方は 2 つで違う。** 設計 Pull Request のマージはマージ先のチャネルによらず
要り、本番系へ届く操作だけが**届く先が本番系かどうか**で決まる。要否そのものは
`SKILL.md` の「人手の承認を求める承認ゲート」が定める。この文書が扱うのは、求めるときに何を
出すかである。

**本番系へ届く操作は 2 つの形を取る。** リリース（`release`）と、運用モードの実行
（`operation` の実装）である。**性質が同じであるため、承認ゲートとしては 1 つ（リリース承認ゲート）に数える。**

## 承認資料は 2 層に分ける

**承認するのは中身であって、Pull Request の形ではない。** 対象の URL と変更量とレビューの
収束だけを示すと、承認する側は設計文書を最初から読むまで判断できない。1 の項目は対象を開く
手段であって、判断の材料ではない。

### 1. 対象を開くためのもの

| 項目 | 書き方 | 理由 |
| --- | --- | --- |
| Pull Request の URL | **生の URL のまま**書く | Markdown のリンクにすると利用者の画面では番号しか見えず、URL を取り出せない（`pr` の完了報告と同じ規約） |
| タイトル | そのまま | 何の変更かを示す |
| ベースと head | `<base> ← <head>` | どのブランチをどこへ入れるのかを示す |
| 変更量 | コミット数・ファイル数・行数 | 読む分量の見当が付く |

### 2. 承認の判断に使うもの

| 項目 | 何を書くか | 出所 | 出所が無いとき |
| --- | --- | --- | --- |
| 目的（設計 PR） | 目的の章を 3 行以内 | 要求仕様のコピー（`issues/issue-<番号>-requirements.md`）の「目的」 | 必ずある |
| 用語（設計 PR） | 新しく足した語と意味を変えた語（反映が「追加」「意味の変更」の行）と、その意味 | 設計文書の「用語」のセクションの、反映が「追加」「意味の変更」の行 | 当たるときだけのセクション。無ければ「無し（足した語・意味を変えた語が無い）」 |
| 適用範囲（設計 PR） | 働く範囲・当たるモードと、代表のリポジトリでの振る舞いの表をそのまま | 設計文書の「影響と危険」 | 必ずある |
| 目指す姿（設計 PR） | セクションをそのまま。要求仕様のコピーへのリンクも載せ、設計文書を基準にした相対リンクは、承認対象の Pull Request の head にあるファイルの絶対 URL（`https://github.com/<owner>/<repo>/blob/<head の sha>/<パス>`）へ書き換える（会話の中では相対リンクを開けない） | 設計文書の「解き方の全体像」と、要求仕様のコピーへのリンク | 必ずある |
| 目指す姿の根拠（設計 PR） | 根拠の行をそのまま | 設計文書の決定ごとの「根拠」の行 | 必ずある（決定の記録は必ず書くため） |
| 起票者の推定（設計 PR） | 各行の条件と「この要求での扱い」を要約せずに並べる。利用者がまだ決めていない条件として示し、承認で確かめる | 要求仕様のコピーの「起票者の推定」 | 当たるときだけのセクション。無ければ「無し」 |
| 決めたこと | 「決定の記録」の見出しをそのまま並べる | 設計文書の「決定の記録」の見出し | 必ずある |
| 作るもの | 新設するものと、変えるものを分けて挙げる（見分け方は参照元ごとに下の「作るものの見分け方」） | 設計文書の「構成要素」。無ければ「どこを変えるか」の表、詳細設計を別ファイルにしたときは詳細設計書の地図 | 3 つのどれか 1 つは必ずある（詳細設計を別ファイルにするか畳むかを必ず決めるため）。構成要素は当たるときだけ |
| 満たすこと | 受け入れ条件の件数 | 要求仕様のコピーの「受け入れ条件」（受け入れ条件は要求仕様だけが持つ） | 必ずある |
| 未確認のまま残ること | 件数と、そのうち実装で決めるもの | 設計文書の同名のセクション | 当たるときだけのセクション。無ければ「0 件」 |
| レビューの収束の状態 | 承認した担当と、未解決の指摘の件数 | `cross-review` の判定 | 今のまま |
| 本文との一致 | 本文の決めたことのセクションが設計文書と一致したか（一致 / 未確認） | 下の突き合わせの結果 | 今のまま |
| MVV 判定 | 判定（従う / 反する疑い / 判定できない）・理由・根拠の項目。機械のチェックで外れた・判定を読めないときは外れた理由。判定の記録が無ければ「MVV なし」 | 設計承認ゲートは設計 PR の MVV 判定のコメント、リリース承認ゲートは承認資料の末尾（`pace: normal` は助言の MVV 判定。[pace.md](pace.md) の「MVV 判定」） | 今のまま |

**作るものの見分け方は、拾った参照元ごとに変える。** 参照元ごとに新設と変更を持つ場所が違うためである。

| 参照元 | 新設と変更の見分け方 |
| --- | --- |
| 設計文書の「構成要素」 | 表は新設か変更かを列で持たない。要素を置くファイルを設計文書の「設計の結果」の触るファイルで引き、「（新設）」の表記があれば新設、無ければ変更に分ける。ファイルを引けない要素は、詳細設計書の地図（別ファイルのとき）か「どこを変えるか」の表（畳んだとき）の同じファイルの行で分ける |
| 設計文書の「どこを変えるか」の表 | 「ファイル」の列の「（新設）」の表記。表記が無ければ変更 |
| 詳細設計書の地図 | 「種類」の列の値。`新設` は新設、`変更` は変更に分け、`削除` は変えるものに「（削除）」と添えて挙げる |

**設計 PR の先頭の 4 行は、承認する人が問う項目である。** 欄の書き方は `design` の
[design-template.md の「承認する人が読む欄」](../../design/references/design-template.md#承認する人が読む欄) にある。
出所のセクションが無いか空なら、その行を「無し（<理由>）」と出して承認ゲートは止めない（変更を要求するかは承認する人が決める）。
対象を開くもののタイトルが題の付け方（`document-rebuild` の [format-markdown.md の「題と見出し」](../../document-rebuild/references/format-markdown.md#題と見出し)。`<対象>: <何ができるようになるか>` の短い 1 文と末尾の課題番号の括弧）でなければ、「題: 規約の形でない」と添える。

**出所を要求仕様と設計書の新しい並びに置くのは、目的と受け入れ条件を要求仕様だけが持ち、設計書は「どう解くか」と
「なぜその解き方か」だけを持つためである。** 設計書から目的を拾うと、2 つの文書が同じ事実を言い直す形に戻る。

**`legacy-refactor` の設計 PR は、上の表で出所を付け替えず、今の出所のままにする。** このモードは要求仕様を通らないので
「目的」の出所になる要求仕様のコピーが無く、設計書は「解き方の全体像」も書かない。設計書は
[design-template.md の「`legacy-refactor` の書き方」](../../design/references/design-template.md#legacy-refactor-の書き方) の欄
（H1・目的・適用範囲・目指す姿・目指す姿の根拠）を持ち、承認資料は次のとおり拾う。

| 承認資料の項目 | `legacy-refactor` の出所 |
| --- | --- |
| 目的・適用範囲・目指す姿の根拠 | 設計文書の同名の欄 |
| 目指す姿 | 設計文書の「目指す姿」（出所は「変更後の構造」）と、欄にある対象課題へのリンク（要求仕様のコピーへのリンクは無い） |
| 用語・決めたこと・作るもの・未確認のまま残ること | 上の表と同じ出所（無ければ上の表の出し方） |
| 起票者の推定・満たすこと | 「無し（`legacy-refactor` は要求仕様を通らない）」 |

**決定の見出しをそのまま並べるのは、要約で判断が変わるためである。** 承認する側が読むべき
なのは選んだ結論であり、その言い換えではない。件数だけを示す形も採らない（何を決めたのかが
分からない）。

**必須のセクションが埋まっていることを 1 行で示す。** モードごとに何を作るかは `design` の
「モードごとの成果物」の表が決める。承認を求める側は、その表に照らして欠けが無いことを言う。
**設計文書が揃っていることと、その中身が妥当であることは別である。** 前者は機械で確かめ
られ、後者を判断するのが承認する側である。

## 承認ゲートごとの違い

対象が Pull Request かバージョンかで、両方の層の項目が変わる。

### 設計 Pull Request のマージ

| 層 | 何を出すか |
| --- | --- |
| 対象を開くもの | Pull Request の URL / タイトル / ベースと head / 変更量 |
| 判断に使うもの | 目的・用語・適用範囲・目指す姿・目指す姿の根拠・起票者の推定・決めたこと・作るもの・満たすこと・未確認・収束の状態・本文との一致 |

**提示を組み立てる前に、本文と設計文書を突き合わせる。** 承認する人は Pull Request の本文を
読む。レビューやオーケストレーターの直接の修正で設計文書だけが変わっていると、古い決定を読んで承認する。
本文を直した経路が何であっても、ここが承認の前の最後の確かめになる。

```bash
gh pr view <番号> --json body --jq .body > <作業ディレクトリ>/pr-body.md
```

本文の決めたことのセクションの見出しを、設計文書の「決定の記録」の見出しと突き合わせる。

| 突き合わせの結果 | 提示の扱い |
| --- | --- |
| 一致する | 「本文との一致: 一致」と書いて提示する |
| 食い違う | 提示しない。本文のセクションを設計文書に合わせて直し（`gh pr edit <番号> --body-file <直した本文>`）、突き合わせ直す |
| 本文か設計文書を読めない | 「本文との一致: 未確認」と明記して提示する。一致と書かない |

#### 設計文書が 2 本以上の設計 Pull Request

**1 本の設計 Pull Request に設計文書が 2 本以上あるときは、設計文書ごとにまとまりを作る。** 上の表は設計文書 1 本ぶんの
出所で、頭の 1 本だけから拾うと、残りの課題の目的・決定・受け入れ条件を承認資料で確かめられないためである。

- **要求と設計の対応**: 設計文書のファイル名の課題番号で、同じ番号の要求仕様のコピーと組にする
  （`issue-<番号>-design.md` と `issue-<番号>-requirements.md`）。根本原因が共通で複数の課題を 1 本にまとめた設計文書
  （`issue-<番号1>-<番号2>-design.md`）は、名前に含む番号すべての要求仕様のコピーと組にする。要求仕様のコピーが無い番号は、
  その課題の行を「無し（要求仕様のコピーが無い）」と出す
- **並べる順**: 設計文書のファイル名の最初の課題番号の昇順に並べる。同じ Pull Request を何度組んでも同じ順にするためである。
  各まとまりは見出しに設計文書の H1 と課題番号を置き、上の表の項目（目的・用語・適用範囲・目指す姿・目指す姿の根拠・
  起票者の推定・決めたこと・作るもの・満たすこと・未確認のまま残ること）を、その組の設計文書と要求仕様のコピーから拾う。
  まとめた設計文書では、目的・起票者の推定・満たすことを課題番号ごとの行に分ける
- **Pull Request 全体で 1 回だけ出すもの**: 対象を開くためのもの（URL・タイトル・ベースと head・変更量）、レビューの収束の状態、
  本文との一致、MVV 判定は Pull Request の単位なので、まとまりの前に 1 回だけ出す。あわせて、設計文書の本数・満たすこと
  （受け入れ条件）の件数の合計・未確認のまま残ることの件数の合計を集計して出す

```text
（Pull Request 全体）URL / タイトル / ベースと head / 変更量 / 設計文書 2 本・受け入れ条件 9 件・未確認 3 件 / 収束 / 本文との一致 / MVV 判定
（1 つ目）#101 <issue-101-design.md の H1>: 目的 / 用語 / 適用範囲 / … / 未確認のまま残ること
（2 つ目）#102 #103 <issue-102-103-design.md の H1>: 目的（#102・#103 の行）/ … / 満たすこと（#102・#103 の行）/ …
```

**`documentation` ではこれが企画承認にあたる。** 判断に使うものは、その文書に合わせて
読み替える。

| 層 | `documentation` で出すもの |
| --- | --- |
| 対象を開くもの | 同じ（Pull Request の URL / タイトル / ベースと head / 変更量） |
| 判断に使うもの | 読み手 / 読み手に求める判断 / 章立て / 使う数値の出所 / 触れない範囲 / 版面と図表の種類 / 起票者の推定 |

### 本番系へ届く操作

**届くものがバージョンか外部の系の状態かで、両方の層の項目が変わる。**

#### リリース（`release`）

| 層 | 何を出すか |
| --- | --- |
| 対象を開くもの | バージョンの比較の URL（`compare/<前のバージョン>...<今のバージョン>`）/ 版数 / リリース対象の差分 / 承認したコミット（ベースブランチの HEAD の 40 桁。本番へ入れてよい中身の上限） |
| 判断に使うもの | リリースする中身・**取り消しの手段とその限界**・開発版のデプロイで確かめたこと・MVV 判定（承認資料の末尾。無ければ「MVV なし」） |

**リリースでは取り消しの手段を必ず示す。** 設計のマージは変更を要求できるが、リリースしたバージョンは利用者の側の
操作でしか戻せない。

#### 文書の提出（`documentation`）

| 層 | 何を出すか |
| --- | --- |
| 対象を開くもの | 提出先の名前と場所 / **本番か下書きかの区分** / 期待する公開範囲 |
| 判断に使うもの | **生成物を描画した画像** / **生成物と SSOT の内容検証の差分** / 受け入れ条件の充足 / 事実確認の記録 / 取り消しの手段とその限界 |

**文字だけでは体裁を承認できない。** スロットからの文字あふれ・図の重なり・改ページの位置は、
ソースを読んでも分からない。描画した画像を必ず含める。

**内容検証の差分も併せて出す。** 描画が見るのは版面だけであるため、非決定的な生成で数値が
変わったり本文が欠けたりしても、画像を見るだけでは表に出ない。

**取り消しの手段は共有の解除とバージョンの変更要求で、限界は「既に見た人には効かない」ことである。**
リリースしたバージョンが利用者の側の操作でしか戻せないのと違い、読まれた文書は戻せない。

**下書き先への提出は承認を求めない。** `production` が偽の提出先は、開発側の「開発版のデプロイ」
に当たる。設定の形は [document-destinations.md](document-destinations.md) にある。

#### 運用モードの実行（`operation`）

| 層 | 何を出すか |
| --- | --- |
| 対象を開くもの | 対象の系と、**本番か検証かの区分** / 使う権限（値は書かない） / 実行の単位の数 |
| 判断に使うもの | 単位ごとの変更前と変更後・**巻き添えで変わる依存する項目**・**単位ごとの取り消しの手段**・**取り消せない単位とその影響の範囲**・**踏めなかった分岐** |

**取り消せない単位は、承認を求める時点で示す。** 承認はその前提で行われる。実行してから
戻せなかったと報告する形にはしない。範囲と記録の決まりは
[operation-run.md](operation-run.md) が持つ。

## 対象が複数あるとき

**並行して走った Pull Request は、承認ゲートでまとめて 1 回の承認へ載せる。** 1 本ずつ求めると、
承認する側は同じ判断を回数分行うことになり、スプリント全体として何が入るのかが見えない。

**対象の Pull Request の URL をすべて明示する。** 生の URL のまま書き、Markdown のリンクに
しない（利用者の画面では番号しか見えず、URL を取り出せない）。

### 並べ方

**マージする順に並べる。** 依存の順序が無いときは番号の昇順にする。

| 列 | 何を書くか |
| --- | --- |
| 順 | 1 から始まる通し番号。**この順にマージする** |
| URL | 生の URL |
| タイトル | そのまま |
| モード | その Pull Request に対して判定したモード |
| 変更量 | ファイル数・行数 |

### 依存の順序があるとき

**マージの順序を示す。** どちらが先かを書かないと、承認した側から見て入る順が決まらない。
後から出た側の差分が、先に入る前提で書かれていることがある。

```text
1. https://github.com/<所有者>/<リポジトリ>/pull/425  共通の層の移設        standard
2. https://github.com/<所有者>/<リポジトリ>/pull/426  移設先を読む側の変更  standard   （1 の後）
```

**順序が無いときは、無いと書く。** 書かないと読む側が推測する。

**ベースブランチが「マージ前に最新をマージする」を求めるなら、2 本目以降にマージのステップを書く。**
先の 1 本をマージした時点で後続はすべて `BEHIND` になり、`gh pr merge` は
`the head branch is not up to date with the base branch` で拒む。`git merge-tree` でコンフリクトが
無くても、このステップは減らない。2 本目以降は「ベースブランチのマージ → push → CI の success → マージ」とし、
CI 1 回の所要 × (本数 − 1) を所要に足す。求めるかどうかは次の 2 つのどちらかが `true` を返すかで見る。

```bash
gh api repos/<所有者>/<リポジトリ>/branches/<起点>/protection --jq '.required_status_checks.strict'
gh api repos/<所有者>/<リポジトリ>/rules/branches/<起点> \
  --jq '[.[] | select(.type=="required_status_checks") | .parameters.strict_required_status_checks_policy] | any'
```

前者は branch protection、後者は ruleset である。保護が無いと前者は `Branch not protected`（HTTP 404）で終わる。

## 読み手役の確認

**承認や判断を求める質問は、読み手役が質問の文と文書を読んで確かめてから出す。** 誰が読ませるかは質問の種類で分かれる。MVV 判定で承認ゲートを通し、
人に尋ねないときは行わない。

| 質問 | 読ませる担当 | 質問を出す AI がすること |
| --- | --- | --- |
| 承認ゲート（`ndf-gate:1`・`ndf-gate:2`） | 工程のステップ（`ndf document-rebuild gate`。工程の外の承認は同じコマンドを打つ） | 記録と突き合わせて、記録した質問をそのまま出す。読み手役は起動しない。承認資料と質問の文も自分で書かない |
| 判断の質問（`ndf-ask:`） | 質問を出す AI | 質問の文と、その直前に示す材料を読ませて記録する |

### 承認ゲートの質問

承認資料と質問の文は、工程の承認ゲートの直前のステップ（`design-reading`・`release-reading`）が作り、読み手役に読ませて記録する。
流れは [document-rebuild の「承認の前の確認」](../../document-rebuild/SKILL.md#承認の前の確認) にある。設計承認の資料は、承認する
Pull Request のコメントにある（PR の題と本文は書き換えない）。会話のセッションのリリースと、状態を持たない単発の承認では、
`ndf document-rebuild gate --gate <design か release> [--pr <番号>] [--material <承認資料>] --state-dir <保存先> --out <結果のファイル>`
を打つ（`--material` はリリースだけで、直した資料は結果の `outputs.material` のパスにある）。

1. **記録と突き合わせる。** `ndf records reading check --gate <design か release> --pr <番号> --questions-out <ファイル>` を打つ（会話のセッションの
   リリースでは `present` に渡す資料を `--material <ファイル>` で足す）。PR を 1 回読み、決まった形の質問を作り直してファイルへ書き、記録と
   突き合わせる。別のセッションでも同じコマンドで質問を得る
2. **合わなければ確認をやり直す。** `stopped` の `precondition` の語が `no_record`・`head_moved`・`material_changed` なら、読み手役を自分で
   起動せず、承認の待ち方に合わせてやり直す。やり直した後は、前の質問・承認資料・回答のコマンドを使わず、手順 1 に戻る

   | 承認の待ち方 | やり直し方 |
   | --- | --- |
   | 工程の承認ゲートで待っている | `ndf progress reread <ステートマシンの ID>`。`ndf document-rebuild gate` は直接打たない。読み手役のステップを打ち直し、承認ゲートの待ちを新しい質問の id と今の対象で出し直す。結果の `metrics.gate` から head と回答のコマンドを読み直す |
   | 会話のセッションのリリース | `ndf document-rebuild gate --material <ファイル>` を打ち直し、`outputs.material` のファイルで `present` を打ち直す。資料か head が違えば提示し直される |

   `no_pr`（記録に無い Pull Request を承認しようとしている）は、その Pull Request を指定して `gate` を打つ。`unknown`（GitHub を読めない）なら、
   調べられなかったことを承認資料に添えて進む。`ndf document-rebuild gate` が `stopped`（`precondition`。PR の題か本文の直しが要る）を返したら、PR の題か本文を
   直してから、同じコマンドか工程を打ち直す
3. **質問を出す。** 出し方はランタイムで違う
   - **Claude Code**: 手順 1 が書いた `questions` を 1 字も変えずに `AskUserQuestion` へ渡す。`metadata.source` に区分（`ndf-gate:1` か
     `ndf-gate:2`）を足す（質問のキーは変わらない）。変えると、記録と合わずに hook が質問を止める（[asking.md](asking.md) の「質問の前に調べること」）
   - **ほかのランタイム**: 手順 1 が書いた質問の文と選択肢を変えずに、区分の名前を先頭に書いて出す（[asking.md](asking.md) の「ランタイムごとの扱い」）

### 判断の質問

読み手役・合格の条件・回数・直し方は [document-rebuild の「読み手役に読ませる」](../../document-rebuild/SKILL.md#読み手役に読ませる) にある。

1. **読ませる。** 読ませるものは、質問の文と、その直前に示す材料である。1 回目が不合格なら同じ範囲で 2 回目まで直す
   - **起動**: Claude Code では、新しい `ndf:worker` を起動する。ほかのランタイムでは、`external-ai` で別の CLI を呼ぶ。`prompt` は
     `ndf records reading prompt` が作った文だけにし、[agent-layers.md](agent-layers.md) の「supervisor → worker」の 7 項目を足さない
     （経緯を渡さないため）。`ndf:worker` の `description` は `検証: 読み手役（<文書>・<立場>）` とする。返った文をそのまま使う
     （報告コピーと作業の結果ファイルを求めない）
   - 質問の文と材料はどちらも同じ読み手の立場で読むので、1 つのファイルの並び（`files`）に入れて 1 回で読ませる。`reads` には
     `question` と `material` の 2 行を書く
2. **2 回目に挙がった「判断や作業を誤らせる文」と、直さなかった「読みにくいだけの文」を材料に書く。** 書き方は document-rebuild の表の
   「2 回目にも残った文」「読みにくいだけの文」のとおり
3. **記録して出す。** 出す質問と同じ `questions` を JSON ファイルに書き、`ndf records reading add --file <JSON>` を打つ。判断の質問は
   `prs` を空の配列にする。`result` は、合格なら `passed`、2 回目にも残ったなら `remained`

   ```json
   {
     "questions": [{"question": "<質問の文>", "header": "判断", "multiSelect": false, "options": [{"label": "進める", "description": "<説明>"}]}],
     "prs": [],
     "reads": [
       {"name": "question", "reader": "判断する人", "round": 1, "result": "passed"},
       {"name": "material", "reader": "判断する人", "round": 2, "result": "remained"}
     ]
   }
   ```

   Claude Code では記録した `questions` を 1 字も変えずに `AskUserQuestion` へ渡す

### 読み手役を起動できないとき

判断の質問だけに当てる。書いた担当が読み手の立場で読み直し、起動できなかった理由と読み直したものを材料に書く。「読み手役が確認した」とは
書かず、記録もしない。Claude Code では `check` を打たずに質問を出し、hook が止めたら同じ質問を出し直す（止めるのは 2 回までで、3 回目は
注意を付けて出せる）。承認ゲートの確認で読み手役を起動できないときは、`gate` と工程が `stopped` で止まる。原因を直して打ち直し、読まずに
承認を求めない。

## 止まる手段

**Claude Code では `AskUserQuestion` に限る。** `/goal` は停止の判定をターンの終わりに行うため、文中に
「承認を待つ」と書いてターンを終えると、判定が継続を促して承認のないまま先へ進む。
`AskUserQuestion` はツールの呼び出しでターンを終えないため、判定そのものが走らない。

ほかのランタイムでは [asking.md](asking.md) の「ランタイムごとの扱い」のとおりに質問を出し、利用者の回答が届くまで承認ゲートの先へ進まない。

**質問には承認ゲートの区分を付ける。** `AskUserQuestion` の入力に `"metadata": {"source": "ndf-gate:1"}`（設計 Pull Request のマージ）か
`"ndf-gate:2"`（本番系へ届く操作・制作物承認）を入れる。区分の無い質問は出さない。読み手役の記録が無い質問は hook が止める。区分の SSOT は [asking.md](asking.md) にある。

**承認ゲートに限らず、判断を求めるときは先に材料を示す**（何を決めるか・分かったこと・根拠の場所・
選択肢ごとに何が変わるか・推奨とその理由）。形は `decision-request` が定める。この文書の承認資料は、
その上に承認ゲートごとに足すものである。

承認資料は質問の**本文の外**（直前の応答）へ書いてよい。質問の選択肢の説明に URL を埋めると、
別の選択肢を選ぶつもりで読む人は対象を開かないまま承認することになる。

## 回答を記録する

**利用者が承認ゲートで回答したら、承認も変更要求もスプリントのステートマシンへ `ndf answer` で 1 行書く。** pace と MVV 判定の
有無を問わない。利用者へ新しい確認は求めない。書いた回答は `ndf answer list <ステートマシン>` で古い順に読める。

| 進め方 | 承認 | 変更要求 |
| --- | --- | --- |
| `reject` のステップを持つプランで止まった | `ndf answer <ステートマシン> --gate <質問の id> --result approved --reason <要約> --by human --key <冪等のキー>` | 直してから `ndf plan next <プラン> --from reject`（`reject` が変更要求を書いて再提示する） |
| スプリントのステートマシンがある（`reject` の無いプラン） | 同上 | `ndf answer <ステートマシン> --gate <質問の id> --result request_changes --reason <要約> --by human --key <冪等のキー> [--notes <指摘ファイル>]` |
| ステートマシンが無い（単発の変更など） | 記録しない。回答と要約を conductor の報告に書く | 同じ |

`--gate` は承認ゲートの結果の `metrics.gate.id`、`--result` はその結果の `routes` のキーから写す。`--key` は回答ごとに決め、
同じキーで打ち直しても 2 行にならない。終了コードが 0 以外（記録を書けない）なら、書けなかったことと `summary` を conductor の報告に出して先へ進む。
設計承認ゲートで起票者の推定が変更を要求されたときの仕様の直し方は `requirements-design` の手順 1a にある。
