# 承認を求めるときに提示するもの

工程の途中で人間の承認を求める場面は 2 つある。**設計 Pull Request のマージ**の前と、
**本番のチャネルへ届く操作**の前である。**どちらも、この会話の中で利用者に判断を求める
形である**ため、提示するものを 1 箇所で定める。2 箇所へ同じ表を書くと、片方だけが更新される。

**要否の決まり方は 2 つで違う。** 設計 Pull Request のマージはマージ先のチャネルによらず
要り、本番のチャネルへ届く操作だけがチャネルで決まる。要否そのものは `SKILL.md` の
「人手の承認を求める関門」が定める。この文書が扱うのは、求めるときに何を出すかである。

## 提示物は 2 層に分ける

**承認するのは中身であって、Pull Request の形ではない。** 対象の URL と変更量とレビューの
収束だけを示すと、承認する側は設計文書を最初から読むまで判断できない。1 の項目は対象を開く
手段であって、判断の材料ではない。

### 1. 対象を開くためのもの

| 項目 | 書き方 | 理由 |
| --- | --- | --- |
| Pull Request の URL | **生の URL のまま**書く | Markdown のリンクにすると利用者の画面では番号しか見えず、URL を取り出せない（`pr` の完了報告と同じ規約） |
| タイトル | そのまま | 何の変更かを示す |
| ベースと head | `<base> ← <head>` | どのブランチをどこへ入れるのかを示す |
| 変更量 | コミット数・ファイル数・行数 | 読む分量の見当が付く |

### 2. 承認の判断に使うもの

| 項目 | 何を書くか | 出所 |
| --- | --- | --- |
| 決めたこと | 「決定の記録」の見出しをそのまま並べる | 設計文書の決定の節 |
| 作るもの | 新設するものと、変えるものを分けて挙げる | 設計文書の「構成要素」 |
| 満たすこと | 受け入れ条件の件数 | 設計文書の受け入れ条件 |
| 未確認のまま残ること | 件数と、そのうち実装で決めるもの | 設計文書の同名の節 |
| レビューの収束の状態 | 承認した担当と、未解決の指摘の件数 | `cross-review` の判定 |

**決定の見出しをそのまま並べるのは、要約で判断が変わるためである。** 承認する側が読むべき
なのは選んだ結論であり、その言い換えではない。件数だけを示す形も採らない（何を決めたのかが
分からない）。

**必須の節が埋まっていることを 1 行で示す。** モードごとに何を作るかは `design` の
「モードごとの成果物」の表が決める。承認を求める側は、その表に照らして欠けが無いことを言う。
**設計文書が揃っていることと、その中身が妥当であることは別である。** 前者は機械で確かめ
られ、後者を判断するのが承認する側である。

## 関門ごとの違い

対象が Pull Request か版かで、両方の層の項目が変わる。

### 設計 Pull Request のマージ

| 層 | 何を出すか |
| --- | --- |
| 対象を開くもの | Pull Request の URL / タイトル / ベースと head / 変更量 |
| 判断に使うもの | 決めたこと・作るもの・満たすこと・未確認・収束の状態 |

### 本番のチャネルへ届く操作

| 層 | 何を出すか |
| --- | --- |
| 対象を開くもの | 版の比較の URL（`compare/<前の版>...<今の版>`）/ 版数 / 配布物の差分 |
| 判断に使うもの | 配る中身・**取り消しの手段とその限界**・検証への配布で確かめたこと |

**配布では取り消しの手段を必ず示す。** 設計のマージは差し戻せるが、配布した版は利用者の側の
操作でしか戻せない。

## 対象が複数あるとき

**並行して走った Pull Request は、関門でまとめて 1 回の承認へ載せる。** 1 本ずつ求めると、
承認する側は同じ判断を回数分行うことになり、まとまり全体として何が入るのかが見えない。

**対象の Pull Request の URL をすべて明示する。** 生の URL のまま書き、Markdown のリンクに
しない（利用者の画面では番号しか見えず、URL を取り出せない）。

### 並べ方

**マージする順に並べる。** 依存の順序が無いときは番号の昇順にする。

| 列 | 何を書くか |
| --- | --- |
| 順 | 1 から始まる通し番号。**この順にマージする** |
| URL | 生の URL |
| タイトル | そのまま |
| モード | その Pull Request に対して判定したモード |
| 変更量 | ファイル数・行数 |

### 依存の順序があるとき

**マージの順序を示す。** どちらが先かを書かないと、承認した側から見て入る順が決まらない。
後から出た側の差分が、先に入る前提で書かれていることがある。

```text
1. https://github.com/<所有者>/<リポジトリ>/pull/425  共通層の移設        standard
2. https://github.com/<所有者>/<リポジトリ>/pull/426  移設先を読む側の変更  standard   （1 の後）
```

**順序が無いときは、無いと書く。** 書かないと読む側が推測する。

## 止まる手段

**`AskUserQuestion` に限る。** `/goal` は停止の判定をターンの終わりに行うため、文中に
「承認を待つ」と書いてターンを終えると、判定が継続を促して承認のないまま先へ進む。
`AskUserQuestion` はツールの呼び出しでターンを終えないため、判定そのものが走らない。

提示物は質問の**本文の外**（直前の応答）へ書いてよい。質問の選択肢の説明に URL を埋めると、
別の選択肢を選ぶつもりで読む人は対象を開かないまま承認することになる。
