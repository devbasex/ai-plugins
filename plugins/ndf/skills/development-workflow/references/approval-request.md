# 承認を求めるときに提示するもの

工程の途中で人間の承認を求める場面は 2 つある。**設計 Pull Request のマージ**の前と、
**本番系へ届く操作**の前である。**どちらも、この会話の中で利用者に判断を求める
形である**ため、提示するものを 1 箇所で定める。2 箇所へ同じ表を書くと、片方だけが更新される。

**要否の決まり方は 2 つで違う。** 設計 Pull Request のマージはマージ先のチャネルによらず
要り、本番系へ届く操作だけが**届く先が本番系かどうか**で決まる。要否そのものは
`SKILL.md` の「人手の承認を求める承認ゲート」が定める。この文書が扱うのは、求めるときに何を
出すかである。

**本番系へ届く操作は 2 つの形を取る。** リリース（`release`）と、運用モードの実行
（`operation` の実装）である。**性質が同じであるため、承認ゲートとしては 1 つ（リリース承認ゲート）に数える。**

## 承認資料は 2 層に分ける

**承認するのは中身であって、Pull Request の形ではない。** 対象の URL と変更量とレビューの
収束だけを示すと、承認する側は設計文書を最初から読むまで判断できない。1 の項目は対象を開く
手段であって、判断の材料ではない。

### 1. 対象を開くためのもの

| 項目 | 書き方 | 理由 |
| --- | --- | --- |
| Pull Request の URL | **生の URL のまま**書く | Markdown のリンクにすると利用者の画面では番号しか見えず、URL を取り出せない（`pr` の完了報告と同じ規約） |
| タイトル | そのまま | 何の変更かを示す |
| ベースと head | `<base> ← <head>` | どのブランチをどこへ入れるのかを示す |
| 変更量 | コミット数・ファイル数・行数 | 読む分量の見当が付く |

### 2. 承認の判断に使うもの

| 項目 | 何を書くか | 出所 | 出所が無いとき |
| --- | --- | --- | --- |
| 目的（設計 PR） | 目的の章を 3 行以内 | 要求仕様のコピー（`issues/issue-<番号>-requirements.md`）の「目的」 | 必ずある |
| 用語（設計 PR） | 新しく足した語と意味を変えた語（反映が「追加」「意味の変更」の行）と、その意味 | 設計文書の「用語」のセクションの、反映が「追加」「意味の変更」の行 | 当たるときだけのセクション。無ければ「無し（足した語・意味を変えた語が無い）」 |
| 適用範囲（設計 PR） | 働く範囲・当たるモードと、代表のリポジトリでの振る舞いの表をそのまま | 設計文書の「影響と危険」 | 必ずある |
| 目指す姿（設計 PR） | セクションをそのまま。要求仕様のコピーへのリンクも載せ、設計文書を基準にした相対リンクは、承認対象の Pull Request の head にあるファイルの絶対 URL（`https://github.com/<owner>/<repo>/blob/<head の sha>/<パス>`）へ書き換える（会話の中では相対リンクを開けない） | 設計文書の「解き方の全体像」と、要求仕様のコピーへのリンク | 必ずある |
| 目指す姿の根拠（設計 PR） | 欄の見出しを深さ 2 まで（`## 目指す姿の根拠`）で置き、設計文書の決定の見出し（`### 決定 <数>: <題>`）をそのまま小見出しにして、その下へその決定の根拠の行をそのまま載せる（見出しの無い箇条書きへまとめない。形は下の「[承認資料を組んだら](#承認資料を組んだら)」） | 設計文書の決定ごとの「根拠」の行 | 必ずある（決定の記録は必ず書くため） |
| 起票者の推定（設計 PR） | 各行の条件と「この要求での扱い」を要約せずに並べる。利用者がまだ決めていない条件として示し、承認で確かめる | 要求仕様のコピーの「起票者の推定」 | 当たるときだけのセクション。無ければ「無し」 |
| 決めたこと | 「決定の記録」の見出しをそのまま並べる | 設計文書の「決定の記録」の見出し | 必ずある |
| 作るもの | 新設するものと、変えるものを分けて挙げる（見分け方は参照元ごとに下の「作るものの見分け方」） | 設計文書の「構成要素」。無ければ「どこを変えるか」の表、詳細設計を別ファイルにしたときは詳細設計書の地図 | 3 つのどれか 1 つは必ずある（詳細設計を別ファイルにするか畳むかを必ず決めるため）。構成要素は当たるときだけ |
| 満たすこと | 受け入れ条件の件数 | 要求仕様のコピーの「受け入れ条件」（受け入れ条件は要求仕様だけが持つ） | 必ずある |
| 未確認のまま残ること | 件数と、そのうち実装で決めるもの | 設計文書の同名のセクション | 当たるときだけのセクション。無ければ「0 件」 |
| レビューの収束の状態 | 承認した担当と、未解決の指摘の件数 | `cross-review` の判定 | 今のまま |
| 本文との一致 | 本文の決めたことのセクションが設計文書と一致したか（一致 / 未確認） | 下の突き合わせの結果 | 今のまま |
| MVV 判定 | 判定した PR と head・判定（従う / 従わない / 判定できない）・根拠の項目・レビューの保留・省かない理由・全文の参照先（載せ方と伏せる範囲は下の「[MVV 判定の欄](#mvv-判定の欄)」） | 進め方によらず、今回の判定の出力 `outputs.mvv_gate`（[pace.md](pace.md) の「MVV 判定」） | 「判定できない: <理由>」と「レビューの保留: 未確認」 |

**作るものの見分け方は、拾った参照元ごとに変える。** 参照元ごとに新設と変更を持つ場所が違うためである。

| 参照元 | 新設と変更の見分け方 |
| --- | --- |
| 設計文書の「構成要素」 | 表は新設か変更かを列で持たない。要素を置くファイルを設計文書の「設計の結果」の触るファイルで引き、「（新設）」の表記があれば新設、無ければ変更に分ける。ファイルを引けない要素は、詳細設計書の地図（別ファイルのとき）か「どこを変えるか」の表（畳んだとき）の同じファイルの行で分ける |
| 設計文書の「どこを変えるか」の表 | 「ファイル」の列の「（新設）」の表記。表記が無ければ変更 |
| 詳細設計書の地図 | 「種類」の列の値。`新設` は新設、`変更` は変更に分け、`削除` は変えるものに「（削除）」と添えて挙げる |

**設計 PR の先頭の 4 行は、承認する人が問う項目である。** 欄の書き方は `design` の
[design-template.md の「承認する人が読む欄」](../../design/references/design-template.md#承認する人が読む欄) にある。
出所のセクションが無いか空なら、その行を「無し（<理由>）」と出して承認ゲートは止めない（変更を要求するかは承認する人が決める）。
対象を開くもののタイトルが題の付け方（`document-rebuild` の [format-markdown.md の「題と見出し」](../../document-rebuild/references/format-markdown.md#題と見出し)。`<対象>: <何ができるようになるか>` の短い 1 文と末尾の課題番号の括弧）でなければ、「題: 規約の形でない」と添える。

**出所を要求仕様と設計書の新しい並びに置くのは、目的と受け入れ条件を要求仕様だけが持ち、設計書は「どう解くか」と
「なぜその解き方か」だけを持つためである。** 設計書から目的を拾うと、2 つの文書が同じ事実を言い直す形に戻る。

**`legacy-refactor` の設計 PR は、上の表で出所を付け替えず、今の出所のままにする。** このモードは要求仕様を通らないので
「目的」の出所になる要求仕様のコピーが無く、設計書は「解き方の全体像」も書かない。設計書は
[design-template.md の「`legacy-refactor` の書き方」](../../design/references/design-template.md#legacy-refactor-の書き方) の欄
（H1・目的・適用範囲・目指す姿・目指す姿の根拠）を持ち、承認資料は次のとおり拾う。

| 承認資料の項目 | `legacy-refactor` の出所 |
| --- | --- |
| 目的・適用範囲・目指す姿の根拠 | 設計文書の同名の欄 |
| 目指す姿 | 設計文書の「目指す姿」（出所は「変更後の構造」）と、欄にある対象課題へのリンク（要求仕様のコピーへのリンクは無い） |
| 用語・決めたこと・作るもの・未確認のまま残ること | 上の表と同じ出所（無ければ上の表の出し方） |
| 起票者の推定・満たすこと | 「無し（`legacy-refactor` は要求仕様を通らない）」 |

**決定の見出しをそのまま並べるのは、要約で判断が変わるためである。** 承認する側が読むべき
なのは選んだ結論であり、その言い換えではない。件数だけを示す形も採らない（何を決めたのかが
分からない）。

**必須のセクションが埋まっていることを 1 行で示す。** モードごとに何を作るかは `design` の
「モードごとの成果物」の表が決める。承認を求める側は、その表に照らして欠けが無いことを言う。
**設計文書が揃っていることと、その中身が妥当であることは別である。** 前者は機械で確かめ
られ、後者を判断するのが承認する側である。

## MVV 判定の欄

**欄の出所は、進め方によらず、今回の判定の出力 `outputs.mvv_gate` だけである。** PR のコメントからは拾わない。今回の判定が
コメントを書けなかったときも、PR には前回の判定のコメントが残っているためである。出力のキーの中身は [pace.md の「MVV 判定」](pace.md#mvv-判定) にある。

| 経路 | 欄を組む者 | 読む値 |
| --- | --- | --- |
| プランの経路（判定のステップ `design-mvv`・`release-mvv` を持つプラン） | NDF のコード（プランの承認資料） | 待っている工程の判定のステップの記録の `outputs.mvv_gate` |
| supervisor の経路（プランを使わずに supervisor が工程を進める） | supervisor（このセクションの手順） | 自分が打った `ndf records mvv gate --machine` の結果 JSON（作業ディレクトリの `mvv-gate-<区分>.json`）の `outputs.mvv_gate`。打ち方は [agent-layers.md](agent-layers.md) の supervisor が守る規則 17・18 |

このセクションの手順は supervisor の経路のものである。プランの経路の資料は NDF のコードが組み、次の 2 点だけをこの手順と共用する。

- 記録済みの判定の `pr`・`head` を、質問の PR と、質問の対象を取得したときの head（`q.target.head`）に照らす（下の「判定した PR と head を照らす」の表）
- 判定の全文があり、PR にコメントを書けなかった（`noted` が真でない）ときは、全文を読める場所が無いと伝え、承認せずに「変更を求める」の回答で判定のやり直しを求める文を載せる。`mvv-gate-<区分>.json` は supervisor の経路だけが作るファイルなので、プランの資料では案内しない

### 判定の結果 JSON が `ok` でないとき

| 結果 | 欄に載せる文 |
| --- | --- |
| `not_applicable`（`--expect-pr` の番号と判定する PR が違った。リリース承認ゲートだけ） | 「今回のリリースでマージする PR（<承認する PR の URL>）について、プロジェクトの判断基準に沿っているかの自動判定は行っていません。この PR の変更内容を確認して、リリースを承認するか判断してください。レビューで保留になった指摘は確認していません」だけ。判定した側の PR（文脈の `pr`）の URL と番号は載せない |
| ほかの `stopped`（`refused`・`input_missing`・`invalid` など） | 「判定できない: 判定の入力を組めない（<結果の `status`>・<`cause.kind`>）。結果の全文は、判定を打った実行環境の <`mvv-gate-<区分>.json` のパス> で読む」。`summary`・`cause.detail`・`warnings` は承認資料にもフェーズレポートにも写さない（入力の値やパスを含みうる） |

どちらのときも承認ゲートは返し、人へ問う。リリース承認ゲートでは、承認する PR を「対象を開くためのもの」に示す。

### 判定した PR と head を照らす

**head は、資料を確定するときに 1 回だけ取得し、資料の中のすべての用途で共用する。** プランの経路では、質問の対象を取得したときの
`q.target.head` を使い、PR を読み直さない。supervisor の経路では、承認ゲートを返す直前に、承認を求める PR の今の head を、PR の本文とレビューと一緒に 1 回で読む。

```bash
gh pr view <承認を求める PR の番号> --json headRefOid,body,reviews
```

**資料に使う PR の本文・設計文書・レビューは、すべてこの head に対応するものだけにする。** 別々に読むと、間に push されたとき、
表示した head と別のコミット向けの本文やレビューが資料に混ざるためである。

| 材料 | 読み方 |
| --- | --- |
| PR の本文 | 上のコマンドの `body`。head と同じ応答で読んだものだけを使い、PR の番号で読み直さない |
| 設計文書 | この head のコミットから読む（`git show <head>:<パス>`）。worktree やブランチ名から読まない |
| レビュー | 上のコマンドの `reviews` のうち、`commit.oid` がこの head のものだけ。cross-review の記録は、この head に対する行だけ |

承認資料の中で head を使う所（承認資料に示す head・設計文書へのリンク・判定と照らす値）は、すべてこの値にそろえる。
資料を組み始めたときの head がこの値と違えば、上の表の読み方で、この head の材料から決定と根拠を取り直し、根拠の行を確かめ直す
（下の「承認資料を組んだら」）。古い head から抜き出した内容は使わない。

**材料がこの head に対応すると確かめられなければ、資料を返さずに止まる。** この head のコミットを取得できない、レビューや
cross-review の記録がどの head に対するものか分からない、などの場合である。承認を求めず、`結果: 止まった` で呼び出し元へ返し、
`理由` に確かめられなかった材料を書く。欄には「この head と PR の今の head が違えば、承認せずに返す」を添える。

判定の `pr`・`head` を、承認を求める PR とこの head に照らす。

| 照らした結果 | 見分け方 | 欄に載せるもの |
| --- | --- | --- |
| 一致する | `pr`・`head` が承認を求める PR とこの head に等しい | 先頭に「判定した PR: #<pr>・head <head>」を置き、下の「判定を載せる」で組む |
| PR を特定する前に判定が止まった | `pr` も `head` も無く、`stopped_by` がある | 「対象の PR を特定できなかったため、MVV 判定は済んでいない。<`stopped_by.text`>」と「レビューの保留: 未確認」。PR と head を並べない |
| 判定が対象を確かめられない | `head` はあるが `pr` が無い（前のバージョンの NDF の判定）、または今の head を読めない | 「残っている判定が、承認を求める PR #<承認を求める PR> の今の変更に対するものかを確かめられません。この変更に対する判定はまだありません。承認せず、「変更を求める」の回答で判定のやり直しを求めてください」と「レビューの保留: 未確認」 |
| 同じ PR の古い head の判定がある | `pr` は承認を求める PR と同じで、`head` が違う | 「承認を求める PR #<承認を求める PR>・head <今の head> の判定はまだ無い。今ある判定は、判定の後に PR が更新される前の head <判定の head> に対するもの。この変更に対する判定はまだありません。承認せず、「変更を求める」の回答で判定のやり直しを求めてください」と「レビューの保留: 未確認」 |
| 別の PR の判定がある | `pr` があり、承認を求める PR と違う（`head` が同じでもこの行） | 「承認を求める PR #<承認を求める PR>・head <今の head> に対する判定はまだありません。承認せず、「変更を求める」の回答で判定のやり直しを求めてください」と「レビューの保留: 未確認」。判定した PR の番号と head は載せない（承認する人が見られない PR の存在とコミットを知らせないため） |

**判定の件数・`stopped_by.text`・コメントへの案内を載せるのは、PR の番号と head が両方一致したときだけである。** 例外は表の 2 行目
（PR を特定する前に判定が止まった）で、表のとおり定型の停止理由 `stopped_by.text` を載せる（PR の値を含まない文で、承認する人が何を直せば
判定をやり直せるかを知るために要る）。PR の番号は head と別に照らし、番号が違えば head が同じでも表の 5 行目にする（別の PR が同じコミットを指すことがあるため）。一致しないとき（表の 3〜5 行目）に
判定を打ち直して両方一致すれば、その結果で資料を組み直してよい。

**表の 3〜5 行目の資料に対して、承認する人が「変更を求める」で判定のやり直しを求めたら、supervisor は判定を打ち直し、PR と head が両方一致した
ときだけ、もう一度承認を求める。** 照らす相手は、前回の資料に載せた head ではない。判定をやり直した後、承認資料を確定するときに
承認を求める PR の最新の head を上の手順で読み、判定の結果の PR の番号と head を、承認を求める PR の番号とその最新の head に照らす。
一致した場合は、新しい結果で資料を組み直して承認を求める。一致しなければ、同じ未判定の資料で承認を
求め直さない。`結果: 止まった` で呼び出し元へ返し、`理由` に「打ち直した判定が承認を求める PR と head に一致しない」と、手元の
`mvv-gate-<区分>.json` のパスを書く。

この一致の条件は、ほかの理由の「変更を求める」には当てはめない。

- 変更の内容を直すよう求められた場合は、直した後に判定を打ち直し、上の表で照らした結果のまま資料を組んで承認を求める
- リリースの判定が `not_applicable` だった場合は、上の「判定の結果 JSON が `ok` でないとき」の文で承認を求める（PR と head の一致を確かめる手順には進まない）
- コメントを開けない・理由が伏せ字で読めないと返された場合は、下の「承認する人がこう返したときの続け方」の表に従う

**打ち直しは、初回と同じ指定で行う。** [pace.md の「supervisor の経路の打ち方」](pace.md#supervisor-の経路の打ち方) の初回と同じ作業場所で、同じ区分（`--gate`）・
同じステートマシンの ID（`--machine`）・リリースなら同じ承認する PR（`--expect-pr`）を渡し、同じ書き方で `mvv-gate-<区分>.json` に保存する。
保存した結果で、承認を求める PR と head をもう一度照らす。

### 判定を載せる

**supervisor の経路の資料には、PR から取った値を含みうる文の本文を載せず、件数だけを載せる。** 資料は呼び出し元を経て承認する人へ
転送され、受け手がその PR を GitHub で見られるかを確かめられないためである。本文を載せない文は、判定の理由・レッドライン・
レビューの保留の文・`why` である。

| 項目 | 載せ方 |
| --- | --- |
| 判定 | `verdict` があれば、判定（従う・従わない・判定できない）・根拠の項目の名前・理由とレッドラインの件数。`verdict` が `null` なら「判定できない。理由: <`stopped_by.text`>。今回の詳しい結果は <下の全文の参照先> で確かめる」（`stopped_by.text` は PR の値を含まない定型文なので、そのまま載せる） |
| 省かない理由 | 「省かない理由 <`why` の件数> 件（全文は下の参照先で読む）」と、省いたか（`skip`） |
| レビューの保留 | 下の表 |
| 全文の参照先 | 下の表。参照先は 1 つだけ添える |

| `holds` | 載せる文 |
| --- | --- |
| 空でない配列 | 「レビューの保留 <件数> 件（全文は下の参照先で読む）」 |
| `[]` | 「レビューの保留: 無し（レビューの記録に保留が無い。記録がまだ作られていない場合を含む）」。記録を読んで確かめたとは書かない |
| `null` かキーが無い | 「レビューの保留: 未確認（<理由>）」。理由は次の順で決める。リリース承認ゲートなら「リリースの保留は #4105 まで読まない（省かない）」、`verdict` が `null` なら「保留を読む前に判定が止まった」、`verdict` があれば「この判定は保留を読んでいない」 |

| `noted` | 全文の参照先と、欄に足す文 |
| --- | --- |
| 真 | 「理由と保留の全文は、今回の判定のコメント <`note_url`> で読む。コメントを開けない場合や、判断に必要な理由が伏せ字で読めない場合は、承認せずに『変更を求める』で返し、読めないことを伝える」 |
| 真でない（`false`・キーが無い） | PR の既存の判定のコメントを指さない（前回の判定を今回の理由として読ませない）。「理由と保留の全文は、判定を打った実行環境の <`mvv-gate-<区分>.json` のパス> にだけある。その環境を開けない場合は承認せず、『変更を求める』で返して判定の打ち直しを求める」 |

**`verdict` が `null` で、保留の本文も無い（`holds` が `null` か `[]`）ときは、`noted` の表の文を足さない。** 読めない本文が無く、
判定できない理由は `stopped_by.text` で分かるためである。承認するかどうかは承認する人が決める。承認済みの MVV が無いリポジトリでは
毎回この形になる。

承認する人がこう返したときの続け方:

| 返された内容 | supervisor がすること |
| --- | --- |
| コメントを開けない・理由が伏せ字で読めない（`noted` が真） | 承認を求め直さず、`結果: 止まった` で呼び出し元へ返す。`理由` に読めなかった内容と、全文がある手元の `mvv-gate-<区分>.json` のパスを書く（承認する人が読める場所は、その人の権限で決まり supervisor には選べない） |
| 判定の打ち直しを求めた（`noted` が真でない） | 上の「打ち直しは、初回と同じ指定で行う」のとおりに打ち直して PR と head を照らし直し、`noted` が真になった結果で資料を組み直す。打ち直しても PR に書けなければ、`結果: 止まった` で返す。`理由` には `why` の件数と `note_unwritten` の定型文（判定の記録を PR のコメントに書けない。GitHub への接続と書き込みの権限を確かめて判定を打ち直す）を書く |

## 承認ゲートごとの違い

対象が Pull Request かバージョンかで、両方の層の項目が変わる。

### 設計 Pull Request のマージ

| 層 | 何を出すか |
| --- | --- |
| 対象を開くもの | Pull Request の URL / タイトル / ベースと head / 変更量 |
| 判断に使うもの | 目的・用語・適用範囲・目指す姿・目指す姿の根拠・起票者の推定・決めたこと・作るもの・満たすこと・未確認・収束の状態・本文との一致 |

**提示を組み立てる前に、本文と設計文書を突き合わせる。** 承認する人は Pull Request の本文を
読む。レビューやオーケストレーターの直接の修正で設計文書だけが変わっていると、古い決定を読んで承認する。
本文を直した経路が何であっても、ここが承認の前の最後の確かめになる。

```bash
gh pr view <番号> --json body --jq .body > <作業ディレクトリ>/pr-body.md
```

本文の決めたことのセクションの見出しを、設計文書の「決定の記録」の見出しと突き合わせる。

| 突き合わせの結果 | 提示の扱い |
| --- | --- |
| 一致する | 「本文との一致: 一致」と書いて提示する |
| 食い違う | 提示しない。本文のセクションを設計文書に合わせて直し（`gh pr edit <番号> --body-file <直した本文>`）、突き合わせ直す |
| 本文か設計文書を読めない | 「本文との一致: 未確認」と明記して提示する。一致と書かない |

#### 設計文書が 2 本以上の設計 Pull Request

**1 本の設計 Pull Request に設計文書が 2 本以上あるときは、設計文書ごとにまとまりを作る。** 上の表は設計文書 1 本ぶんの
出所で、頭の 1 本だけから拾うと、残りの課題の目的・決定・受け入れ条件を承認資料で確かめられないためである。

- **要求と設計の対応**: 設計文書のファイル名の課題番号で、同じ番号の要求仕様のコピーと組にする
  （`issue-<番号>-design.md` と `issue-<番号>-requirements.md`）。根本原因が共通で複数の課題を 1 本にまとめた設計文書
  （`issue-<番号1>-<番号2>-design.md`）は、名前に含む番号すべての要求仕様のコピーと組にする。要求仕様のコピーが無い番号は、
  その課題の行を「無し（要求仕様のコピーが無い）」と出す
- **並べる順**: 設計文書のファイル名の最初の課題番号の昇順に並べる。同じ Pull Request を何度組んでも同じ順にするためである。
  各まとまりの見出しは深さ 1 の `# <設計文書の H1>（#<課題番号>）` の形にする（`ndf records mvv cite` がこの見出しで
  まとまりを見分ける）。まとまりには上の表の項目（目的・用語・適用範囲・目指す姿・目指す姿の根拠・起票者の推定・決めたこと・
  作るもの・満たすこと・未確認のまま残ること）を、その組の設計文書と要求仕様のコピーから拾う。
  まとめた設計文書では、目的・起票者の推定・満たすことを課題番号ごとの行に分ける
- **Pull Request 全体で 1 回だけ出すもの**: 対象を開くためのもの（URL・タイトル・ベースと head・変更量）、レビューの収束の状態、
  本文との一致、MVV 判定は Pull Request の単位なので、まとまりの前に 1 回だけ出す。あわせて、設計文書の本数・満たすこと
  （受け入れ条件）の件数の合計・未確認のまま残ることの件数の合計を集計して出す

```text
（Pull Request 全体）URL / タイトル / ベースと head / 変更量 / 設計文書 2 本・受け入れ条件 9 件・未確認 3 件 / 収束 / 本文との一致 / MVV 判定
（1 つ目）#101 <issue-101-design.md の H1>: 目的 / 用語 / 適用範囲 / … / 未確認のまま残ること
（2 つ目）#102 #103 <issue-102-103-design.md の H1>: 目的（#102・#103 の行）/ … / 満たすこと（#102・#103 の行）/ …
```

**`documentation` ではこれが企画承認にあたる。** 判断に使うものは、その文書に合わせて
読み替える。

| 層 | `documentation` で出すもの |
| --- | --- |
| 対象を開くもの | 同じ（Pull Request の URL / タイトル / ベースと head / 変更量） |
| 判断に使うもの | 読み手 / 読み手に求める判断 / 章立て / 使う数値の出所 / 触れない範囲 / 版面と図表の種類 / 起票者の推定 |

### 本番系へ届く操作

**届くものがバージョンか外部の系の状態かで、両方の層の項目が変わる。**

#### リリース（`release`）

| 層 | 何を出すか |
| --- | --- |
| 対象を開くもの | バージョンの比較の URL（`compare/<前のバージョン>...<今のバージョン>`）/ 版数 / リリース対象の差分 / 承認したコミット（ベースブランチの HEAD の 40 桁。本番へ入れてよい中身の上限） |
| 判断に使うもの | リリースする中身・**取り消しの手段とその限界**・開発版のデプロイで確かめたこと・MVV 判定（下の「[MVV 判定の欄](#mvv-判定の欄)」） |

**リリースでは取り消しの手段を必ず示す。** 設計のマージは変更を要求できるが、リリースしたバージョンは利用者の側の
操作でしか戻せない。

#### 文書の提出（`documentation`）

| 層 | 何を出すか |
| --- | --- |
| 対象を開くもの | 提出先の名前と場所 / **本番か下書きかの区分** / 期待する公開範囲 |
| 判断に使うもの | **生成物を描画した画像** / **生成物と SSOT の内容検証の差分** / 受け入れ条件の充足 / 事実確認の記録 / 取り消しの手段とその限界 |

**文字だけでは体裁を承認できない。** スロットからの文字あふれ・図の重なり・改ページの位置は、
ソースを読んでも分からない。描画した画像を必ず含める。

**内容検証の差分も併せて出す。** 描画が見るのは版面だけであるため、非決定的な生成で数値が
変わったり本文が欠けたりしても、画像を見るだけでは表に出ない。

**取り消しの手段は共有の解除とバージョンの変更要求で、限界は「既に見た人には効かない」ことである。**
リリースしたバージョンが利用者の側の操作でしか戻せないのと違い、読まれた文書は戻せない。

**下書き先への提出は承認を求めない。** `production` が偽の提出先は、開発側の「開発版のデプロイ」
に当たる。設定の形は [document-destinations.md](document-destinations.md) にある。

#### 運用モードの実行（`operation`）

| 層 | 何を出すか |
| --- | --- |
| 対象を開くもの | 対象の系と、**本番か検証かの区分** / 使う権限（値は書かない） / 実行の単位の数 |
| 判断に使うもの | 単位ごとの変更前と変更後・**巻き添えで変わる依存する項目**・**単位ごとの取り消しの手段**・**取り消せない単位とその影響の範囲**・**踏めなかった分岐** |

**取り消せない単位は、承認を求める時点で示す。** 承認はその前提で行われる。実行してから
戻せなかったと報告する形にはしない。範囲と記録の決まりは
[operation-run.md](operation-run.md) が持つ。

## 対象が複数あるとき

**並行して走った Pull Request は、承認ゲートでまとめて 1 回の承認へ載せる。** 1 本ずつ求めると、
承認する側は同じ判断を回数分行うことになり、スプリント全体として何が入るのかが見えない。

**対象の Pull Request の URL をすべて明示する。** 生の URL のまま書き、Markdown のリンクに
しない（利用者の画面では番号しか見えず、URL を取り出せない）。

### 並べ方

**マージする順に並べる。** 依存の順序が無いときは番号の昇順にする。

| 列 | 何を書くか |
| --- | --- |
| 順 | 1 から始まる通し番号。**この順にマージする** |
| URL | 生の URL |
| タイトル | そのまま |
| モード | その Pull Request に対して判定したモード |
| 変更量 | ファイル数・行数 |

### 依存の順序があるとき

**マージの順序を示す。** どちらが先かを書かないと、承認した側から見て入る順が決まらない。
後から出た側の差分が、先に入る前提で書かれていることがある。

```text
1. https://github.com/<所有者>/<リポジトリ>/pull/425  共通の層の移設        standard
2. https://github.com/<所有者>/<リポジトリ>/pull/426  移設先を読む側の変更  standard   （1 の後）
```

**順序が無いときは、無いと書く。** 書かないと読む側が推測する。

**ベースブランチが「マージ前に最新をマージする」を求めるなら、2 本目以降にマージのステップを書く。**
先の 1 本をマージした時点で後続はすべて `BEHIND` になり、`gh pr merge` は
`the head branch is not up to date with the base branch` で拒む。`git merge-tree` でコンフリクトが
無くても、このステップは減らない。2 本目以降は「ベースブランチのマージ → push → CI の success → マージ」とし、
CI 1 回の所要 × (本数 − 1) を所要に足す。求めるかどうかは次の 2 つのどちらかが `true` を返すかで見る。

```bash
gh api repos/<所有者>/<リポジトリ>/branches/<起点>/protection --jq '.required_status_checks.strict'
gh api repos/<所有者>/<リポジトリ>/rules/branches/<起点> \
  --jq '[.[] | select(.type=="required_status_checks") | .parameters.strict_required_status_checks_policy] | any'
```

前者は branch protection、後者は ruleset である。保護が無いと前者は `Branch not protected`（HTTP 404）で終わる。

## 承認資料を組んだら

**supervisor の経路で承認ゲートを返す前に、承認資料の根拠の行を、ベースブランチで承認された MVV と照らす。** 確かめていない
根拠の行を、確かめたものとして人へ渡さないためである。プランの経路の資料は設計文書の根拠の行を写さないので、打たない。

```bash
ndf records mvv cite --gate <design か release> --base <ベースブランチ> <承認資料のパス>
```

`--gate` は返す承認ゲートの区分である。`design` では、まとまりごとに「目指す姿の根拠」のセクションがあることと、セクションの中の決定の見出しごとに
根拠の行があることも確かめる。設計承認ゲートの資料の「目指す姿の根拠」は、次の形で書く。

```markdown
## 目指す姿の根拠

### 決定 1: <設計文書の決定の見出しの題>

- 根拠: Value 6 / P1（MVV バージョン {N}）

### 決定 2: <設計文書の決定の見出しの題>

- 根拠: 根拠なし（MVV バージョン {N}）
```

- 欄の見出しは深さ 2 まで（`#` か `##`）にする。深さ 3 以上は、中の決定の見出しでセクションが閉じるので、崩れた見出しとして扱われる
- 決定の見出しは設計文書の `### 決定 <数>: <題>` をそのまま置く。根拠の行は、その見出しの下に置く
- 根拠の行の書き方は [decisions.md の「根拠の行」](../../design/references/decisions.md#根拠の行) にある

| 結果 | すること |
| --- | --- |
| `ok` | 「MVV 判定」の欄の下に「根拠の行の確かめ: <`summary`>（<`metrics.commit`>）」の 1 行を載せてから資料を渡す。`metrics` に `commit` が無い（承認済みの MVV が無い）ときは括弧を付けずに「根拠の行の確かめ: <`summary`>」とし、バージョンやコミットを補わない |
| `stopped`・`refused` | 結果の `items` の `kind` で直す所を分けて直し（下の表）、打ち直す。`ok` になるまで資料を渡さない |
| `stopped`・`precondition`（ベースを取得できない・資料を読めない・ベースの本文が承認の記録と合わない） | 資料を利用者へ渡さず、`結果: 止まった`（`理由` は結果の `summary`）で呼び出し元へ返す |

| `kind` | 直し方 |
| --- | --- |
| `heading`（セクション「目指す姿の根拠」が無い・崩れている） | セクションの見出しを上の形（深さ 2 まで）で直す |
| `heading`（決定の見出しの外にある根拠の行を指す） | 設計文書の決定の見出し（`### 決定 <数>: <題>`）をそのまま置き、その行を見出しの下へ移す |
| `heading`（決定の見出しの行を指す。その見出しの下に根拠の行が無い） | 設計文書のその決定の根拠の行を、見出しの下へ書き足す。見出しには手を入れない（見出しを直しても消えない） |
| `format`・`version`・`unknown` | 資料の根拠の行を、設計文書と今のバージョンから書き直す |

## 読み手役の確認

**承認や判断を求める質問を出す前に、読み手役が質問の文と文書を読んで確かめる。** 読み手役・合格の条件・回数・直し方は
[document-rebuild の「読み手役に読ませる」](../../document-rebuild/SKILL.md#読み手役に読ませる) にある。MVV 判定で承認ゲートを通し、
人に尋ねないときは行わない。

1. **読ませるものを決める。** 質問の文と、その直前に示す材料（承認資料）は、必ず読ませる。`ndf-ask:` の質問は、この 2 つだけを読ませる。承認の質問では、承認する Pull Request の対象の文書も次の表のとおりに読ませる

   | 文書の状態 | 読ませるもの |
   | --- | --- |
   | 一度も読ませていない | 全体（新しい確認の 1 回目） |
   | 1 回目が不合格だった | 1 回目と同じ範囲（2 回目） |
   | 確認を終えた後に、レビューなどで直した（読み手役の指摘で直しただけのものは含めない） | 直した部分とその前後の段落だけを、別のファイルに作って（新しい確認の 1 回目）。指示と合格の条件は、document-rebuild の表の「一部だけ読ませるとき」のとおり |
   | 確認を終えた後に直していない | 読ませない |

2. **読み手役に読ませ、合格するか 2 回目が終わるまで直す。** レビューのラウンドごとには読ませず、レビューが終わった後に、直した部分をまとめて 1 つの確認で読ませる
   - **読ませる担当**: 質問を出す AI である。作業を自動実行（`ndf plan`）で流したときは conductor が読ませる。supervisor が設計を進めたときは、文書と承認資料は supervisor が、質問の文は conductor が読ませる。オーガナイザーがまとめて出す質問の文は、オーガナイザーが読ませる
   - **起動**: Claude Code では、新しい `ndf:worker` を起動する。ほかのランタイムでは、`external-ai` で別の CLI を呼ぶ。`prompt` は `ndf records reading prompt` が作った文だけにし、[agent-layers.md](agent-layers.md) の「supervisor → worker」の 7 項目を足さない（文書を書いた経緯を渡さないため）。`ndf:worker` の `description` は `検証: 読み手役（<文書>・<立場>）` とする。どちらの起動でも、返った文をそのまま使う（報告コピーと作業の結果ファイルを求めず、出力先のファイルも `prompt` に書かない）。起動できないときは、下の「読み手役を起動できないとき」に従う
   - **質問の文と、その直前に示す材料**: どちらも承認する人の立場で読むので、同じ担当が確かめるときは 1 つのファイルの並び（`files`）に入れ、1 つの読み手役に 1 回で読ませる。`reads` には `question` と `material` の 2 行を書く。文書と承認資料を supervisor が確かめ、質問の文を conductor が確かめるときは、別々に読ませる
3. **読み手役の指摘で直した差分を確かめる。** 承認を求める担当が、事実（数・日付・条件・決定など）が変わっていないことを差分で 1 回確かめ、確かめたコミットを承認資料に書く。確かめられれば、レビュー全体をやり直さない。レビューの上限に達した後の最後の直しがあるときは、最後の直しで変わった部分も読み手役に読ませ、2 つの直しを合わせた差分を 1 回で確かめる
4. **2 回目に挙がった「判断や作業を誤らせる文」と、直さなかった「読みにくいだけの文」を承認資料に書く。** 書き方は document-rebuild の表の「2 回目にも残った文」「読みにくいだけの文」のとおり
5. **記録する。** 出す質問と同じ `questions` を JSON ファイルに書き、`ndf records reading add --file <JSON>` を打つ。`reads` には、読ませたものと立場ごとに 1 行を書く。`result` は、合格なら `passed`、2 回目にも残ったなら `remained`。`head` は、確認を終えた時点（指摘で直したときは、その直しを含むコミット）の 40 桁の SHA。指摘で直したときは、push してから記録する。判断の質問と、Pull Request の無い承認では `prs` を空の配列にする

   ```json
   {
     "questions": [{"question": "<質問の文>", "header": "設計", "multiSelect": false, "options": [{"label": "承認する", "description": "<説明>"}]}],
     "prs": [{"number": 12, "branch": "design/12-x", "head": "<40 桁の SHA>"}],
     "reads": [
       {"name": "question", "reader": "承認する人", "round": 1, "result": "passed"},
       {"name": "material", "reader": "承認する人", "round": 2, "result": "remained"},
       {"name": "issues/issue-12-design.md", "reader": "エンジニア", "round": 1, "result": "passed"}
     ]
   }
   ```

6. **承認の質問では、質問を出す直前に調べる（どのランタイムでも打つ）。** `questions` と、承認する Pull Request の番号の配列 `prs` を書いた JSON で `ndf records reading check --file <JSON>` を打つ。`ok` なら質問を出す。`stopped` の `precondition` なら、足りないものの語に従って直す。`unknown`（GitHub を読めない）なら、調べられなかったことを承認資料に書いて進む

   | 足りないもの | すること |
   | --- | --- |
   | `no_record` | 出す質問と同じ文の記録が無い。質問の文を読ませて記録する |
   | `no_pr` | 記録に無い Pull Request を承認しようとしている。その文書を読ませ、記録し直す |
   | `head_moved` | 確認の後に Pull Request の head が変わった。手順 1 の対象の文書が変わっていれば、変わった部分だけを読ませる。変わっていなければ読ませない。どちらのときも、新しい head で記録し直す |

7. **質問を出す。** 出し方はランタイムで違う
   - **Claude Code**: 記録した `questions` を 1 字も変えずに `AskUserQuestion` へ渡す。変えると、記録と合わずに hook が質問を止める（[asking.md](asking.md) の「質問の前に調べること」）
   - **ほかのランタイム**: 記録した質問の文と選択肢を変えずに、[asking.md](asking.md) の「ランタイムごとの扱い」のとおりに出す。質問を止める hook は無い

### 読み手役を起動できないとき

書いた担当が、読み手の立場で読み直す。起動できなかった理由と、読み直したもの（Pull Request の文書なら、その URL と読み直したときの head）を
承認資料（判断の質問では材料）に書き、「読み手役が確認した」とは書かない。読み手役が読んでいないものは記録しない。

- **質問の文を読ませられなかったとき**: 記録せずに手順 7 へ進む。Claude Code では、手順 6 の `check` を打たずに質問を出し、hook が止めたら同じ質問を
  出し直す（止めるのは 2 回までで、3 回目は注意を付けて出せる）。ほかのランタイムの承認の質問では、`check` が返した足りないものを承認資料に書く
- **一部の Pull Request の文書だけを読ませられなかったとき**: その Pull Request を、手順 5 の記録と手順 6 の `check` の `prs` から外す。ほかの
  Pull Request は手順 6 のとおりに調べる

## 止まる手段

**Claude Code では `AskUserQuestion` に限る。** `/goal` は停止の判定をターンの終わりに行うため、文中に
「承認を待つ」と書いてターンを終えると、判定が継続を促して承認のないまま先へ進む。
`AskUserQuestion` はツールの呼び出しでターンを終えないため、判定そのものが走らない。

ほかのランタイムでは [asking.md](asking.md) の「ランタイムごとの扱い」のとおりに質問を出し、利用者の回答が届くまで承認ゲートの先へ進まない。

**質問には承認ゲートの区分を付ける。** `AskUserQuestion` の入力に `"metadata": {"source": "ndf-gate:1"}`（設計 Pull Request のマージ）か
`"ndf-gate:2"`（本番系へ届く操作・制作物承認）を入れる。区分の無い質問は出さない。読み手役の記録が無い質問は hook が止める。区分の SSOT は [asking.md](asking.md) にある。

**承認ゲートに限らず、判断を求めるときは先に材料を示す**（何を決めるか・分かったこと・根拠の場所・
選択肢ごとに何が変わるか・推奨とその理由）。形は `decision-request` が定める。この文書の承認資料は、
その上に承認ゲートごとに足すものである。

承認資料は質問の**本文の外**（直前の応答）へ書いてよい。質問の選択肢の説明に URL を埋めると、
別の選択肢を選ぶつもりで読む人は対象を開かないまま承認することになる。

## 回答を記録する

**利用者が承認ゲートで回答したら、承認も変更要求もスプリントのステートマシンへ `ndf answer` で 1 行書く。** pace と MVV 判定の
有無を問わない。利用者へ新しい確認は求めない。書いた回答は `ndf answer list <ステートマシン>` で古い順に読める。

| 進め方 | 承認 | 変更要求 |
| --- | --- | --- |
| `reject` のステップを持つプランで止まった | `ndf answer <ステートマシン> --gate <質問の id> --result approved --reason <要約> --by human --key <冪等のキー>` | 直してから `ndf plan next <プラン> --from reject`（`reject` が変更要求を書いて再提示する） |
| スプリントのステートマシンがある（`reject` の無いプラン） | 同上 | `ndf answer <ステートマシン> --gate <質問の id> --result request_changes --reason <要約> --by human --key <冪等のキー> [--notes <指摘ファイル>]` |
| ステートマシンが無い（単発の変更など） | 記録しない。回答と要約を conductor の報告に書く | 同じ |

`--gate` は承認ゲートの結果の `metrics.gate.id`、`--result` はその結果の `routes` のキーから写す。`--key` は回答ごとに決め、
同じキーで打ち直しても 2 行にならない。終了コードが 0 以外（記録を書けない）なら、書けなかったことと `summary` を conductor の報告に出して先へ進む。
設計承認ゲートで起票者の推定が変更を要求されたときの仕様の直し方は `requirements-design` の手順 1a にある。
