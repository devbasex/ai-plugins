# 別のリポジトリの改修が要るとき（並列の計画のレーン）

**作業の途中で、別のリポジトリ（上流の NDF など）の改修が先に要ると分かったら、並列の計画のレーンはこの手順で進める。**
既定は、相手のリポジトリのクローンを `repo` にしたレーン（相手のレーン）を計画へ足し、同じオーガナイザーの下で改修まで進める形である。
使えないときは代わりの手順（[out-of-scope](../../out-of-scope/SKILL.md) の手順 3〜5 の、別のリポジトリへの起票）へ戻る。

例: 利用側のリポジトリ `acme/app` のレーンが、課題 `acme/app#120` の設計で NDF の Skill の変更が先に要ると分かった。
`acme/app` と同じ親ディレクトリに NDF のクローン `/work/ai-plugins` がある。レーンは `devbasex/ai-plugins` へ課題を起票し（人の承認つき）、
2 つの課題を対に結び、`/work/ai-plugins` を `repo` にしたレーンを足す。NDF の改修はそのレーンが NDF の規約で進める。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| 依頼した側 | 作業の途中で、別のリポジトリの改修が先に要ると分かったレーンと、そのレーンが進めている課題 |
| 相手のリポジトリ | 依頼した側が改修を必要とする、依頼した側と違うリポジトリ |
| 相手のレーン | 依頼した側が計画へ足す、相手のリポジトリのクローンを `repo` にした別のリポジトリのレーン。相手の課題を最初の入力に持つ |
| 完全な形の参照 | `<所有者>/<リポジトリ>#<番号>` の形で課題を指す書き方。番号だけの `#<番号>` は相手のリポジトリでは別の課題を指すため使わない |
| 代わりの手順 | 既定の手順を使えないときに取る、`out-of-scope` の手順 3〜5 の別のリポジトリへの起票 |

## 手順

### 1. 判定する

次の 3 つがすべて成り立つときだけ既定の手順へ進む。どれかが成り立たなければ、代わりの手順へ戻る。

| 条件 | 確かめ方 | 成り立たないとき |
| --- | --- | --- |
| 並列の計画のレーンである | `NDF_RELAY_NAME` が動いている計画のレーンにある（引継ぎ文書が計画名とレーン名を持つ） | 並列の計画を使っていない。代わりの手順へ戻る |
| 相手のリポジトリのクローンが 1 つだけ見つかる | 依頼した側のメインディレクトリと同じ親ディレクトリの直下を探す。候補は、origin の URL から取った `<所有者>/<リポジトリ>` が相手と一致し、`git rev-parse --git-common-dir` がそのディレクトリの `.git` を返す（worktree でない）ものに限る | 0 件ならクローンが無い。2 件以上なら選ばない。どちらも代わりの手順へ戻る |
| `lane add` が検査の規則 `I20` で断らない | 手順 4 の `lane add` の結果で分かる | 手順 4 で代わりの手順の結果に切り替える |

マーケットプレイスの取得元（`~/.claude/plugins/marketplaces/`）は NDF のクローンでも候補にしない。ここはプラグインの導入元として Claude Code が管理する。
クローンの場所を利用者に問わない。代わりの手順でも課題は残る。

### 2. 相手の課題を用意する

`out-of-scope` の手順 4（`dup`）で既存の課題を探し、あればそれを使う。無ければ手順 5（`create`）で起票する。

- **どちらも別のリポジトリへの書き込みである（C5）。** 1 回目は承認資料を書いて 10 で止まる。承認資料を示して同意（`ndf-ask:redline:C5`）を取り、
  `--approved <metrics.digest>` を足して打ち直す。人に問えない起動では打ち直さず、承認資料を添えて人へ戻す
- **同意が無ければ起票せず、レーンも足さない。** 依頼した側の課題の由来の節に事実を残し、相手の改修に依らない作業だけを進める。
  相手の改修を前提にする段では、手順 6 の進む条件を満たさないので止まって人へ戻す
- **相手の課題の本文には、相手のリポジトリで直す内容だけを書く。** 依頼した側の規約・インフラの値・業務の情報を書かない

### 3. 対に結ぶ

両方の課題の由来の節へ、完全な形の参照で 1 行ずつ書く。書く場所は由来の節だけである。

| 課題 | 書く行 | 書き方 |
| --- | --- | --- |
| 相手の課題 | `依頼した側: <所有者>/<リポジトリ>#<番号>` | 起票するときは本文のファイルの由来の節へ書いておく（`create` は由来の節の既存の行を残す）。既存の課題なら `note` の 1 行で残す（手順 2 と同じく C5 の承認を通す） |
| 依頼した側の課題 | `相手の課題: <所有者>/<リポジトリ>#<番号>` | 自分のリポジトリの課題なので、`gh issue edit --body-file` で本文の由来の節を書き直す |

`create` が由来の節の先頭へ入れる番号だけの行（`issue #<番号>`）は、相手のリポジトリでは別の課題を指す。対の結びとしては完全な形の行を読む。

**2 つのリポジトリの公開の範囲が違う組では、公開の側の課題に非公開の側のリポジトリの名前と番号を書かない。**
公開の範囲は `gh repo view <所有者>/<リポジトリ> --json visibility` で両方について読む。

| 組 | 書き方 |
| --- | --- |
| 依頼した側が非公開・相手が公開 | 相手の課題の行を `依頼した側: 非公開のリポジトリの課題` にする。対の結びは依頼した側の課題の行から辿る |
| 依頼した側が公開・相手が非公開 | 依頼した側の課題の行を `相手の課題: 非公開のリポジトリの課題` にする。相手の完全な形の参照は依頼した側のレーンの引継ぎ文書へ書き、手順 5・6 はそこから読む |

### 4. 相手のレーンを足す

次の宣言を JSON のファイルに書き、[parallel.md](parallel.md) の「レーンを足す」の手順で `parallel.py lane p1 add --from <JSON>` を打つ。

```text
{"name": <名前>, "repo": <クローンの絶対パス>, "input": {"kind": "sprint", "issues": [<相手の番号>]}, "plans": 1, "touches": []}
```

| 結果 | 扱い |
| --- | --- |
| 0 | 耐久ワークフローが相手のレーンを起動の候補に入れる。手順 5 へ進む |
| 1（上限を超える） | レーン数の上限を変えずに、レーンを足さない。上限を変えるのは人の指示を受けたときだけである |
| 1（`I20` で断られた） | クローンでない場所を指した。代わりの手順の結果に切り替える |

1 で終わったときも起票した課題は残る。依頼した側の課題の由来の節に、レーンを足せなかった理由を 1 行足して終える。

### 5. 待つかを決める

依頼した側の受け入れ条件が相手の改修なしに満たせるなら、待たずに進む。満たせないなら待つ。

**`after` は始める条件である。** 並べたレーンがすべて止まってから起動し、起動に成功していないレーンだけに効く。
動いているレーンへ `lane set` で `after` を付けても待たないため、付けない。待つ形は依頼した側の課題が今どこにあるかで決まる。

| 依頼した側の課題の場所 | 待つ形 |
| --- | --- |
| まだどのレーンも起動していない（起動前のレーンの課題） | そのレーンに `parallel.py lane p1 set --lane <名> --from <JSON>` で `after: [<相手のレーン>]` を付ける |
| 開発ループのレーンで動いている | `sprint-state.py loop exclude <ループ> <番号> --reason "<相手の完全な形の参照> を待つ"` で外し、`{"kind": "sprint", "issues": [<番号>]}` と `after: [<相手のレーン>]` のレーンを `lane add` で足す。`I19` か上限で足せなければ外したままにし、引継ぎ文書の「次にやること」へ進む条件を書く |
| 1 スプリントのレーンで動いている | 待つ形を持たない。相手の改修に依らない作業を進め、相手の改修が要る段で手順 6 の進む条件を確かめる |

レーンを止めて `after` 付きで起こし直さない（`lane set` の `rule: relaunch` は `after` を見ずにすぐ起動する）。
答え待ちの停止で待たない（他のレーンの完了を待つことは問いの区分に当たらない）。

### 6. 進む条件を確かめる

`after` が解けて起動したレーンと、手順 5 で相手の改修が要る段に来たレーンが、続きの前に確かめる。
`after` は相手のレーンが失敗で止まっても解けるため、解けたことだけで進まない。

1. `gh issue view <番号> --repo <所有者>/<リポジトリ> --json state,stateReason` が `CLOSED`・`COMPLETED` を返す
2. リリース対象を通じて使う変更（NDF の Skill など）なら、依頼した側の環境に導入した版がその変更を含む

満たさなければ進まず、止まって人へ戻す。

## 相手のレーンの規約

**相手のレーンは、相手のリポジトリの規約で進む。** 設定（`.ndf/`）・課題・設計承認ゲート・リリース承認ゲート・漏れの検査は
相手のリポジトリのものが掛かる。承認ゲートの問いはオーガナイザーの依頼の一覧に届く（[parallel.md](parallel.md) の「別のリポジトリのレーン」）。

**依頼した側の規約と情報（インフラの値・業務の情報など）を、相手のレーンの引継ぎ文書と相手の課題へ持ち込まない。**
持ち込みは C5 の承認資料を見た人が差し戻し、残りは相手のリポジトリの漏れの検査が落とす。
