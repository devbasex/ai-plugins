# 並列開発のオーガナイザー（`--parallel <計画名>`）

並列の計画（[issue-plan-strategy の parallel-plan.md](../../issue-plan-strategy/references/parallel-plan.md) で作る）を、
1 行で始める。

```text
/goal /ndf:development-workflow --parallel p1 -- 終わり: [ndf-parallel] finished p1 の行を出したとき
```

このセッションの conductor が**オーガナイザー**になる。オーガナイザーは、設計の承認の答えで設計 PR をマージするほかは作業を持たない。レーンの起動・観測・リリースのまとめは
耐久ワークフロー（`parallel.py run`）が、リリースプランの実行は一時レーンが、答えの後の処理は持ち主のレーンが行う。
一時レーンの起動と、答えを受けた止まったレーンの再起動も耐久ワークフローが打ち、立ち上がりを確かめる。オーガナイザーが打つのは問いと答えだけで、
`wait` がオーガナイザーへ返るのは人へ問うもの・計画の終わり・耐久ワークフローが自分で解けない異常のときだけである。再開のコマンドも同じ 1 行である。

## 手順

1. `python3 "$NDF_SCRIPTS/parallel.py" start p1` を打つ。検査に誤りがあればレーンを 1 本も起動せずに 1 で終わる。
   ラッパーの外・tmux が無い・リレーハブが居ないときは 3 で終わり、`items` にレーンごとの手で起動する 1 行が並ぶ。
   その 1 行を示して終える
2. `metrics.next` の `parallel.py wait p1` を背景で打ち、完了の通知を待つ（[waiting.md](waiting.md) の形。前景の sleep で待たない）
3. 返った `metrics.action` ごとに次の 1 手を打ち、`wait p1 --after <metrics.seq>` を背景で打ち直す

| `wait` が返したもの | すること |
| --- | --- |
| `questions` | 届いている依頼（`items`）を下の「問い方」で問い、依頼ごとに答えを送る。答えを送った依頼だけが残る一覧では返らない。`metrics.batch` が `true` なら業務時間外に溜めた依頼のまとめで、`metrics.deferred` があれば業務時間外に今問う依頼だけが返っている（下の「業務時間外の依頼」） |
| `answer_hold` | `metrics.changes` の各行の `line` を利用者へそのまま 1 行ずつ出す（問いにしない）。出した最後の `n` を、以後の `wait` の `--changes-after` に渡す（下の「答え待ちの停止」） |
| `finished` / `stopped` | レーンごとの結果（リリースした版・止まった理由）を要約し、`metrics.prior_waits`（答えのまだの前のループの待ち）があれば並べ、`[ndf-parallel] finished p1` の行を出して終える |
| 終了コード 3 | 同じ `wait` を打ち直す（業務時間外に依頼を溜めただけのときも 3 で、`metrics.next` に打ち直す 1 行が載る） |
| 終了コード 1・`action: error` | 耐久ワークフローが失われた（下の「失われた計画」）。`metrics.next` の `parallel.py start p1` を 1 回打つ |

レーンの様子は `python3 "$NDF_SCRIPTS/parallel.py" status p1` で読む。レーンごとに 1 行（`state`・何回目のループか `lap`・今の課題 `issues`・
台帳でそのレーンが最後に送った時刻 `last_at`・ループの記録の費用 `cost_usd`）を返し、承認待ちのレーンと答えていない依頼を送ったレーンの行には
人が入る 1 行 `attach`（`relay.py attach <レーン>`）が載る。値の取れない欄は `null` で、一覧が読めなくても失敗しない。レーンの画面を見に行く前にこれを読む。

`wait` の `metrics` には、計画の台帳から読んだ次の項目が載ることがある。どれも計画を止めず、利用者へ 1 行で伝える。

| 項目 | 意味 |
| --- | --- |
| `versions` | レーンの NDF の版がオーガナイザーの版と違う（`organizer` と、レーンごとの `lanes`）。違うときだけ載る |
| `unknown`・`unknown_ids` | この版が知らない形の台帳の行の数と依頼の id。行は残り、読める版で作り直せば反映する |
| `broken` | 読めない台帳の行の数（途中で切れた行など）。外して続けている |
| `orphans` | レーンのループの記録が答えを待つのに、台帳に無い依頼の id。届いていない依頼なので、レーンに送り直させる |

### 問い方

並列の計画の下で区分つきの問いを出すのはオーガナイザーだけである。レーンと一時レーンの問いは依頼として `items` に届く。

1. 区分ごとに `AskUserQuestion` を呼ぶ（`metadata.source` は呼び出しごとに 1 つ）。順は `ndf-gate:1` → `ndf-ask:redline:*` →
   ほかの `ndf-ask:*` → `ndf-gate:2`。リリース承認ゲートを最後にするのは、答えの時点で `develop` の先頭を比べるためである
2. 依頼 1 件を問い 1 つにし、5 件以上の区分は届いた順に 4 件ずつ続けて呼ぶ。各問いにはレーン名・課題・設計 PR の URL か作業の場所を添える。
   依頼の行の `repo`（計画の宣言から導いたレーンのリポジトリ）が計画の置き場と違えば、そのリポジトリも添える
3. `ndf-ask:human-action` の依頼は `attach`（`relay.py attach <レーン>`）の 1 行を添えて「済んだ」「まだ」で問う。
   `merged` があれば、同じ原因でまとめた各レーンの元の文面を並べる（答えは全レーンへ届く）
4. 耐久ワークフローが自分で立てる問い（`kind` が `stall`・`helper`・`spawn`・`observe`・`build`）は `options` で問う。選んだ答え（「起こし直す」「続きから起こし直す」「止める」）は耐久ワークフローが当てる。`observe` の「ラッパーの環境を作り直す」だけは、答えを送った `answer` が `metrics.next` に `relay.py status` の 1 行を返すので、それを打つ
5. 答えを送り、下の「答えの後の整理」を通す

答えの種類ごとに読んで動く手順は [loop.md](loop.md) の「答えを読んで動く手順」にある。

| 依頼の `kind` | 問いの答え | 送るコマンド |
| --- | --- | --- |
| `gate1`（設計の承認） | 承認 / 直して出し直す（指摘を書く） / やらない | `parallel.py answer p1 <id> --approved` / `--revise --note <指摘ファイル>` / `--rejected`。`reasons` にマージできなかった理由があれば添えて問う（利用者へ戻した依頼） |
| `gate1` で `loop` を持つ（前のループの待ち） | 設計の承認と同じ。ループの名前を添えて問う | 設計の承認と同じ。答えは耐久ワークフローがそのループの `loop answer` で当てる |
| `gate2`（リリース承認ゲート） | 下の「リリース承認ゲート」 | `confirm` / `settle --rejected` |
| `unmatched`（当たらなかった答え） | `reason` を読んで答え直しの要否を確かめる。問いとして人へ問わず、人の判断が要れば答えた依頼を添えて伝える | `parallel.py answer p1 <id> --choice 確かめた` |
| `ask`・`stall`・`helper`・`spawn`・`observe`・`build` | 依頼の選択肢 | `parallel.py answer p1 <id> --choice <選んだ答え>` |

`gate1` の `--approved` では、`answer` が答えを送る前に設計 PR を宛先へマージしてみる（[loop.md](loop.md) の「承認した設計のマージ」）。
結果は `metrics.merge` に載り、答えにも載ってレーンへ届く。マージできなくても答えは送られ、終了コードは 0 である。`answer` はほかに、
答えのイベントを立てるだけで、ラベル・記録・直し・マージし直し・後片付けは持ち主のレーンがループの 1 回の境で行う。答えを待って止まった持ち主
（1 スプリントのレーン・記録が `waiting_only` で止まったループのレーン・問いを保留して止まった一時レーン）は、耐久ワークフローが `relay.py restart` で
再起動する。オーガナイザーは起こさない。持ち主の 1 スプリントのレーンが答え待ちの停止の範囲にあれば、再起動せず `metrics.held_owners` にレーン名が載り、
停止が解けたときに再開の印で起きる。持ち主がループのレーンなら範囲の中でも再起動する。起きたレーンは境で承認の要らない作業（承認した設計の実装など）を選び、無ければ止まり直す。

同じ行の新しい依頼は、古い依頼を一覧から外して置き換える（`replaced` に前の id と印が残る）。置き換えた id への答えは今の問いの持ち主へ流れ、
取り込みのコミットだけの違いなら当たる。当たらないと区分 `unmatched` の問いになる。前のループの待ちは、計画を始めるときとレーンのループの 1 回の境で
届く。同じ行は同じ id で 1 つにまとまり、計画を終えることを止めない。

### 答えの後の整理

出した `AskUserQuestion` は取り下げられず、答えを待つ間に届いた依頼は答えの後まで表に出ない。答えを受けたら、溜まった依頼を
整理してまとめて問い直す。

1. 依頼ごとに答えを送る（`parallel.py answer`）。`metrics.merge.result` が `merged`・`already_merged` 以外なら、理由（`reason`）を
   1 行で利用者へ伝える（問いにしない。ループの次の 1 回の境でレーンが結果に応じた手を打つ）。`production` なら、リリース承認ゲートで人が
   マージするまで実装に選ばれないことを添える
2. 最後の `answer` の `metrics.after`（答えの後に残る依頼）から、`drop` が付いた依頼を除く。`settled` は今送った答えと同じ設計 PR の依頼、
   `resend` は同じレーンの同じ設計 PR に、より新しい先端の依頼がある古い依頼である
3. `mvv.eligible` が `true` の依頼（設計の承認で、レーンの判定が「判定できない」「判定を読めない」で、レッドラインが空の依頼）ごとに、
   `mvv-gate.py check --sprint <依頼の sprint_state> --gate design --pr <依頼の pr>` を 1 回だけ打つ。「従う」（終了コード 0）なら
   `parallel.py answer p1 <id> --approved --by mvv` を送る（判定の記録は `mvv-gate.py` が書く）。ほかの結果なら、打ち直さずに残す。
   「従わない」・レッドライン・リリース承認ゲート・区分つきの問いは自分で答えない
4. 残りがあれば、上の「問い方」の区分の順と 4 件ずつで、まとめて `AskUserQuestion` を出す。残りが無ければ
   `wait p1 --after <metrics.seq>` を背景で打ち直す

リリース承認ゲートは、提示 1 なら「承認」「差し戻す」で問い、`parallel.py confirm p1 <連番>` か
`parallel.py settle p1 <連番> --rejected` を打つ。出し直しの提示（`represent: true`）なら加わった範囲を添えて
「新しい範囲で出す」「最初の範囲だけ出す」「差し戻す」で問い、`confirm --take new` / `--take first` / `settle --rejected` を打つ。

### セッションの切り替え

カットポイントでは、問いを出していなければ引継ぎ文書 `.ndf/handoff/parallel-p1.md` の「次に実行するコマンド」に起動と同じ 1 行を書き、
`ndf-next` を出して切る。新しいセッションの `start` は動いている `run` をそのまま使い、`wait --after 0` が答えていない問いを返す。
`start` と `run` は、どの経路でも打ったセッションへオーガナイザーの印を付け、同じ計画の前のセッションの印を外す（`metrics.organizer`）。

### 失われた計画

耐久ワークフローが ERROR になったか、耐久の記録（`~/.local/state/ndf/dbos` などの置き場の SQLite）が消えた計画を「失われた計画」と呼ぶ。
受けた依頼・問い・答え・リリースの連番・起動したレーンは、計画の置き場の計画の台帳（`ledger.jsonl` と `checkpoint.json`）に残っている。

- 戻すのは `python3 "$NDF_SCRIPTS/parallel.py" start p1` の 1 回だけである。`run` が耐久の記録を `<鍵>.sqlite.retired-<時刻>` へ退避し、
  同じ耐久ワークフローで新しく始めて台帳から状態を戻す。結果の `metrics.rebuilt` が true で、`metrics.restored` に戻す依頼と問いの数・外した行数が載る。
  台帳と耐久の記録を手で編集しない
- 作り直しの後の `wait --after <前の seq>` は、作り直しの後の知らせを取りこぼさない。起動済みのレーンは起動し直さない
- 失われた間もレーンの `request`・`request-ask`・`request-gate2` とオーガナイザーの `answer`・`confirm`・`settle` は受け付け、
  `metrics.queued` が true になる。作り直しの後に反映する
- 放棄する計画は `parallel.py stop p1` で閉じる。閉じた計画は `start` で作り直さない

### 答え待ちの停止

答えを待つ依頼が人の読める量を超えたら、耐久ワークフローがレーンに新しい作業を始めさせず、閾値以下へ戻ったら人の操作なしで再開する。
オーガナイザーが `AskUserQuestion` の答えを待つ間も、セッションが無い間も働く。閾値は止める引き金であり、依頼は捨てない。

たとえば答えていない依頼が 8 件の計画へ 9 件目が届くと、全レーンが区切りで止まる。2 件へ答えて 7 件になると、止まったレーンが起きて続きを流す。

| 範囲 | 閾値（既定） | 数えるもの | 止まる時点 |
| --- | --- | --- | --- |
| 計画全体 | `plan`（8） | 答えていない依頼の全件（`gate1`・`gate2`・`ask` と、耐久ワークフローが立てた問い）。MVV 判定で答えられる依頼も答えるまで数える | 超えたとき。計画の全レーンが止まり、まだ起動していないレーンを起動せず、新しいリリースを組まない |
| 1 つのレーン | `lane`（3） | そのレーンが送った答えていない `gate1` と `ask`。まとめた問いは送った各レーンへ 1 件ずつ数える | 超えたとき。そのレーンだけが止まる |

- 閾値は宣言 `.ndf/pace.json` の `{"parallel": {"answer_limit": {"plan": 8, "lane": 3}}}` で変える。正の整数でない値は既定へ戻り、`check`・`start` が警告を出す
- 同じ原因でまとめた問いと、同じレーンの同じ設計 PR の新旧の依頼は 1 件と数える。答えた設計 PR の古い依頼は一覧から外れる。リリースの依頼は数えない
- 止まるのは区切りである。ループのレーンはループの 1 回の境、1 スプリントのレーンはキューのプランの開始で止まる。動いているプランと流れているリリースは最後まで流す。`supervise.py run` の単発の開始は止めない
- ループのレーンは止まる前に承認の要らない作業を進める。答えの届いた保留したループの 1 回の残りを流し、承認とマージが済んだ設計の課題があれば選んで進む。設計を承認していない課題（新しい承認を生む作業）は選ばず、選べる課題が無いときだけ止まる（[loop.md](loop.md) の「答え待ちの停止の範囲の選定」）
- 止まったレーンは再開の印を置いて自分のラッパーを止める。耐久ワークフローが停止の範囲の外へ戻ったレーンを `relay.py restart` で起こす。再開を断られると起動の断りと同じに数えて問う
- 再開の印が残る間は計画を終えない。止めたままにするレーンは `parallel.py park p1 --lane <レーン> --clear` で印を消す

### 業務時間外の依頼

進め方の宣言 `.ndf/pace.json` に業務時間（[pace.md](pace.md) の「業務時間」）があれば、業務時間外の `wait` は設計の承認と問い
（`gate1`・`ask`）を返さずに溜める。業務時間に入った後の最初の `wait` が、答えていない依頼の全件を `metrics.batch: true` で 1 回に返す。
宣言が無いリポジトリの `wait` は今と同じに返す。

| 業務時間外に届いた依頼 | `wait` の扱い |
| --- | --- |
| `gate2`・`unmatched`・耐久ワークフローが立てた問い | 今と同じく返す（溜めると復旧が業務時間まで遅れる） |
| `mvv.eligible` の設計の承認 | 1 回だけ返す。「答えの後の整理」の手順 3 と同じく `mvv-gate.py check` を 1 回打ち、「従う」なら `--approved --by mvv` を送る。ほかの結果なら利用者へ問わず、同じ `wait` を打ち直す（答えの無い依頼は朝のまとめに入る） |
| ほかの `gate1`・`ask` | 返さずに溜める。今問う依頼が無ければ終了コード 3 で、`summary` に溜めた件数と業務時間の始まりが載る |
| 業務時間内に示した依頼 | 溜め直さず、返しもしない（答えが届くまで利用者の手元にある） |

- 業務時間外の `wait` の待ちの上限は、次の業務時間の始まりで切れる。終了コード 3 で打ち直すと、始まりの後の最初の `wait` がまとめを返す
- まとめは上の「問い方」で問う。設計の承認の行には課題の題（`title`）・設計 PR の URL（`url`）・レーンの判定（`verdict`）・MVV 判定の印（`mvv`）が付く。
  `gh` で引けなかった値は `null` で、件数が `metrics.annotate_errors` に載る
- 溜めた依頼の控えは `.ndf/parallel/p1/deferred.json` に置く。依頼そのものは依頼の一覧にあり、控えが読めなくても失わない（読めなければ溜めた依頼を作り直し、示した依頼も次のまとめでもう一度示す）
- 溜めても答え待ちの停止の数え方は変わらない。業務時間外に作る設計は閾値で止まる

## まとめたリリース

リリースの依頼が届いた時点で流れているリリースが無ければ、他のレーンを待たずに直ちにリリースを組む。リリースの中身は、
承認資料を作る時点の `origin/develop` のコミットまでの範囲で決まる。範囲に入ったレーンは、依頼していなくても結果を受ける。
承認の答えの時点で `develop` が進んでいれば、加わった範囲を添えて同じリリース承認ゲートを 1 回だけ出し直す。
流れているリリースは 1 本までで、範囲に入らない依頼は今のリリースが終わった直後の次のリリースになる。

依頼を受けるたびに、耐久ワークフローはリリースの組み方を `.ndf/supervise.json` の `release.form` と `.ndf/project.json` の `delivery` から読み直す。

| リポジトリの宣言 | リリースの組み方 | 依頼への答え |
| --- | --- | --- |
| `release.form` に雛形がある | 組む | リリースの結果（`released`・`rejected`・`failed`） |
| `delivery` の行がすべてマージで届くか、`delivery` が `[]` | 組まない | その場で `released`（`version` は `null`）。提示のプラン・本番のプラン・一時レーンは作らない |
| 手動の経路がある、宣言が無い・不明・読めない、雛形の無い `release.form` | 組めない | その場で `failed` と直す宣言を示す理由 |

組まないときの `released` は、オーガナイザーが組むリリースが要らないことを指す。本番系へ届いたことはリリース後テストが確かめる。

組むはずのリリースを組めないとき（出す版を読めない・連番の上限・組み立ての失敗）も同じく `failed` と理由を答える。
範囲が決まる前なら受けている依頼のすべてへ答え、提示の出し直しを組めないときは範囲の依頼だけへ答えて、残りは次のリリースへ回す。
リリースを組めないことでは計画は止まらない。止めるかは問い `kind: build`（下の「異常のとき」）への答えで決まる。

## 一時レーン（`--parallel-helper`）

持ち主のいない共有の作業は、耐久ワークフローが起動する一時レーン（`<計画名>-rel<連番>`、役割 `helper`）が行う。
耐久ワークフローはリリースを組んだとき（提示）・リリース承認ゲートの承認を受けたとき（確定）・保留したループの 1 回を流すときに一時レーンを起動し、
立ち上がりを確かめる（下の「起動と再起動」）。オーガナイザーは一時レーンを起動しない。
最初の入力は次のどちらかで、`development-workflow` は判定の手順へ進まずこの節の手順で進める。

```text
/goal /ndf:development-workflow --parallel-helper p1 <連番> <提示> -- 終わり: [ndf-parallel] helper-done p1 の行を出し、python3 <relay.py> stop p1-rel<連番> で自分のラッパーを止めたとき
/goal /ndf:development-workflow --parallel-helper p1 pending <ループ名> -- 終わり: [ndf-parallel] helper-done p1 の行を出し、python3 <relay.py> stop p1-rel<連番> で自分のラッパーを止めたとき
```

**リリース（`<連番> <提示>`）:**

1. `python3 "$NDF_SCRIPTS/parallel.py" helper p1 <連番> <提示>` を打つ。`metrics.phase` が流すものを決める
2. `metrics.pipeline` を流す（待ちは背景で打ち、完了の通知を待つ）
   - `phase: present`: 提示のプラン → 本番のプランの queue と待ち。提示のプランがリリース承認ゲートで止まったら（done の提示のプランの結果が承認ゲートで止まった値）、
     `metrics.gate2` の 1 行でリリース承認ゲートの依頼を送り、手順 4 へ進む。流れ切れば手順 3 へ進む
   - `phase: confirmed`: 答えの記録 → 提示のプランを `approve` から → 本番のプランの queue と待ち。`approve` が承認ゲート（終了コード 10）で
     終われば本番のプランを流さず、問いとして送って手順 4 へ進む
3. `metrics.settle` の 1 行（`parallel.py settle p1 <連番> --done <D>`）を打つ。結果は耐久ワークフローが範囲のレーンへ返す
4. `[ndf-parallel] helper-done p1` の行を出し、最後に最初の入力の「終わり」にある `relay.py stop <自分の名前>` の 1 行を打って
   自分のラッパーを止めて終える。止めないと対話の claude が入力待ちで残り、続きの一時レーンの起動が同じ名前か上限で断られる。
   答えの後は、耐久ワークフローが続きの一時レーンを起動する。リリース承認ゲートの依頼か `settle` を送ってから止まるのは手順どおりの停止で、
   「途中で止まった」の問いにならない

CI の失敗・衝突・版数の衝突は、リリースプランの直しの手順（judge・fix）で直す。直せない失敗は問いにする（区分つきの `AskUserQuestion` を
出すと、問いの hook がオーガナイザーへ送り、拒否の理由に保留の手順が返る）。保留したら手順 4 で終える。

**保留したループの 1 回（`pending <ループ名>`）:** `python3 "$NDF_SCRIPTS/sprint-state.py" loop pending <ループ名>` を打ち、`metrics.pipeline` を流す。
`metrics.status` が `none` になるまで繰り返し、手順 4 で終える。別のリポジトリのレーンのループなら、耐久ワークフローがそのリポジトリで
一時レーンを起動し、一時レーンはそのリポジトリで動く。

一時レーンは並列の計画の `lanes` に載らず、リリースの依頼を送らない。同時に 1 本までで、同時に動かせる数を 1 本だけ超えて通る。

### 起動と再起動

耐久ワークフローは、一時レーンの起動（提示・確定・保留したループの 1 回）と、答えを受けた止まったレーンの再起動を、耐久ステップ `parallel.launch` で打つ。

1. 打つ前にレーンの状態の一覧（`relay.py ls --json`）を読み、そのレーンが動いて（`running` か `awaiting_approval`）いれば打たずに立ち上がったと数える
2. `relay.py spawn`（一時レーン）か `relay.py restart`（止まったレーン）を打ち、一覧を 5 秒ごとに読んで立ち上がりを確かめる。上限は 120 秒
   （`NDF_PARALLEL_LAUNCH_SECONDS`）。動いて観えるか、止まっていても最後に動いた時刻が打った後なら立ち上がったと数える
3. 立ち上がらなければ 1 回だけ打ち直す。2 回目も立ち上がらなければ区分 `spawn` の問い（起こし直す / 止める）を立てる

起動の目的（リリースの連番と提示と段・保留したループ・再起動の回）ごとに結果を起動の記録へ残し、耐久ワークフローを作り直しても記録のある目的は打ち直さない。
問いの答えの「起こし直す」は新しい目的として流し、そこでも 1 回だけ打ち直す。

一時レーンの「途中で止まった」の問い（区分 `helper`）は、今の起動の立ち上がりを確かめた後に、その一時レーンが今の起動より後に止まった行を
2 回続けて観たときだけ立つ。リリース承認ゲートの依頼・`settle`・その一時レーンの答えていない問いのどれかがあれば立たない。前の起動の止まった行は数えない。

## レーンの側

並列の計画の下のレーン（`NDF_RELAY_NAME` が動いている計画のレーンにある）の本番のステージは、リリースの経路（`.ndf/supervise.json` の
`release.form` と `.ndf/project.json` の `delivery`）で決まる。`supervise.py new sprint` が経路ごとに組むため、conductor は組み上がった
プランを手で置き換えない（本番チャネルへ入れるリリースプランをリリースの依頼へ書き換えない）。リリースの Pull Request で届く経路では、レーンは本番チャネルへ入れるリリースプランをそのまま流す。

| リリースの経路 | 本番のステージ | レーンがすること |
| --- | --- | --- |
| テンプレートで出す | リリースの依頼のプラン（ステップ `parallel-request` の 1 つ。フェーズ「リリースの依頼」） | 依頼を送り、プランは承認ゲートとして終わる。自分の Pull Request がすでに `main` にあれば、送らずにリリース済みとして続きへ進む |
| リリースの Pull Request | 本番チャネルへ入れるリリースプラン 1 本 | そのまま流す。`pace: auto`・`fast` は MVV 判定が通ると本番チャネルへマージし、通らなければ止まる。`pace: normal` は `promote` がリリース承認ゲートで終わり、承認の後に `--from promote-approved` で続ける。本番チャネルへ入れるリリースプランはまとめを持たないため、1 スプリントのレーンは流れ切った後に `new close` のプランを流す |
| マージで届く | `pace: auto`・`fast` は導入の確認のプラン、`pace: normal` は置かない | そのまま流す。置かないときは `new close` のプランを流す |
| 手で届ける | 手で行うリリースのステージ | 手で行うリリースの手順に従う。オーガナイザーはこの経路のリリースを組めない（上の「まとめたリリース」） |

リリースの依頼の課題の一覧はプランの `課題` だけが持ち、コマンドの `--issues {plan_issues}` は流す時点の `課題` で埋まる。設計承認ゲートで
外した課題は、依頼にも本番チャネルへ入れるリリースプランにもまとめにも載らない。レーンで `supervise.py queue` の `--max` を省くと、並列の計画のそのレーンの
プランの本数で流す。

リリースの依頼を送ったレーンの続きは次のとおりである。

| レーン | 依頼の後 | 答えが届いたら |
| --- | --- | --- |
| 開発ループ | `loop lap` がループの 1 回を「リリース待ち」で締め、答えを待たずにループの次の 1 回へ進む（[loop.md](loop.md)） | ループの 1 回の境の `loop select` が答えを読み、まとめを流してループの 1 回を締め直す |
| 1 スプリント | `parallel.py await p1 --from <プランの状態ディレクトリ>/work/request.txt` を背景で打って待つ | `released` ならまとめのステージを流す。`rejected` は今のリリース承認ゲートの差し戻しと同じに扱う |

設計承認ゲート・リリース承認ゲート（リリースの Pull Request で届く経路の `pace: normal` を含む）・承認ゲートの外の問いは、1 台の中のレーンではオーガナイザーへ送られる（[asking.md](asking.md) の「並列の計画のレーン」）。

答え待ちの停止の範囲に入ったレーンは、区切りで止まる。

| レーン | 止まり方 |
| --- | --- |
| 開発ループ | `loop select` か `loop lap` が `answer_hold` で止まる（[loop.md](loop.md) の「止まる条件」） |
| 1 スプリント | `supervise.py queue` がプランを `流さなかった` として `status: gate` と `metrics.answer_hold` を返す（ほかのプランが止まっていれば `status: stopped`）。`metrics.park` の `parallel.py park p1 --lane <レーン> --done <D>` を打つ（`next` にも載る。承認ゲートと同居したら `next` は report.md の提示の後にこの 1 行を続ける）。止まる手順なら `metrics.next` の自分のラッパーを止める 1 行を最後に打って終える。`metrics.cleared` が `true` なら停止は解けているので、`metrics.next` の `supervise.py queue --resume <D>` で続ける |

## 別のリポジトリのレーン

計画の宣言のレーンに `repo`（レーンのリポジトリのメインディレクトリ）を書くと、計画の置き場と違うリポジトリのセッションもレーンになる
（同じマシンの同じ利用者に限る）。`parallel.py init`・`start`・`lane add` が計画の置き場を計画の所在の一覧へ書き、別のリポジトリの
セッションはその一覧から自分の計画を見つける。

| 場面 | 振る舞い |
| --- | --- |
| 起動 | 耐久ワークフローがレーンのリポジトリで `relay.py spawn` を打つ。引継ぎ文書はレーンのリポジトリの `.ndf/handoff/` にある |
| 承認ゲートと区分つきの問い | 同じリポジトリのレーンと同じく、オーガナイザーの依頼の一覧に届く（行の `repo` で区別する）。設計の承認の答えでは、オーガナイザーがレーンのリポジトリで設計 PR をマージする |
| 本番 | リリースの依頼を送らず、レーンのリポジトリの設定（`.ndf/supervise.json`）で本番のステージを組む。リリース承認ゲートの問いはオーガナイザーへ届く。まとめたリリースには入らない |
| 答え待ちの停止 | 同じリポジトリのレーンと同じく、レーン名で数える |

## レーンの動き方

並列の計画のレーンに共通の規定である。各規定の「起きた例」は、並行開発のモデルの文書（ai-plugins の `docs/ndf-parallel-model.md`）の
「レーンの動き方の規定で欠けているもの」の表の行を指す。

### 形によらない規定

| # | 規定 | 内容 | 起きた例 |
| --- | --- | --- | --- |
| R1 | 役割の変更 | 役割は計画の宣言の入力で変え、レーンの名前は変えない | レーンの役割を途中で変える手順 |
| R2 | ループの始め直し | 新しいループの名前を計画の宣言へ書いてから始める | ループを始め直すときの計画の更新 |
| R3 | 優先順位の指示 | 優先順位は引継ぎ文書の「次にやること」に書き、画面への入力では伝えない。除く課題は開発ループの除外で指す | 優先順位の指示の届け方 |
| R4 | レーンへの指示の手段 | 指示は引継ぎ文書と計画の宣言に書き、レーンはループの 1 回の境とセッションの切り替えで読む。画面への入力は「引継ぎ文書を読み直す」の 1 行だけにする | レーンへ指示を送る手段 |
| R5 | 止まったレーン | 止まったかはレーンの側の記録（ループの記録・引継ぎ文書）で決め、ラッパーの状態だけで決めない | ループが止まったレーンの扱い |
| R6 | 手で起動したレーン | 手で起動するときも、レーンの名前とレーンのリポジトリを計画の宣言と一致させる。一致しないセッションはレーンでなく計画の外のセッションとして止まる | 手で起動したレーンの扱い |
| R7 | 計画の外のセッション | 動いている計画があるとき、計画の外の開発ループとスプリントは止まる（基本不許可）。必要ならレーン数の上限を変えて計画へレーンを足す。急ぎの例外は理由を添えて起動する | 計画の外のセッションを止める仕組みとレーンの追加の手順 |

### 1 台だけの規定

| # | 手順 |
| --- | --- |
| R1 | `python3 "$NDF_SCRIPTS/parallel.py" lane p1 set --lane <名> --from <JSON>` で書き換える（書き換えられるキーは `input`・`plans`・`touches`・`after`・`handoff`。`plan.md` を書き直し、耐久ワークフローへ知らせる。在る引継ぎ文書は残し、ループの名前を変えて引継ぎ文書の名が変わったときだけ新しく書く）。`name` と `repo` は変えられない |
| R2 | `lane set` で `input.loop` を書き換え、結果の `items` の `rule: relaunch` の `next`（レーンを止めて新しい最初の入力で起動する 1 行）で起こし直す。`relay.py restart <名>` は前の入力を使い直すため使わない |
| R3 | 引継ぎ文書は `handoff.py` で書き、除く課題は `sprint-state.py loop exclude` で指す |
| R4 | 1 行の入力は `tmux send-keys` で行い、画面へ指示の本文を打たない |
| R5 | `relay.py ls` の `running` を止まっていない根拠にしない |
| R6 | レーンのリポジトリのメインディレクトリで `relay.py run --name <レーン名>` を打つ |
| R7 | 下の「レーンを足す」の手順で足す。例外は `sprint-state.py loop start --outside-plan <理由>` か `supervise.py new sprint --outside-plan <理由>` で起動する（理由は `<状態の根>/parallel/outside-plan.jsonl` に残る） |

計画の外のセッションの判定は、`sprint-state.py loop start` と `supervise.py new sprint` が何かを書く前に行う。動いている計画が
（計画の所在の一覧と自分のメインディレクトリに）あり、レーン・一時レーン・オーガナイザーのどれでもなく、`--outside-plan` も無ければ、
終了コード 3（`metrics.blocked: true`）で止まり、`items` にレーンの足し方の 2 行が、`next` に例外の起動の 1 行が出る。計画の状態を
読めないときは動いている計画として扱う。動いている計画が無いマシンと、Factory の実行ジョブ（`NDF_ORGANIZER_DIR` か `NDF_FACTORY_RUN`）
では判定せずに起動する。

#### レーンを足す

上限を変えるのは人の指示を受けたときだけである。オーガナイザーは上限の値を人へ問うてから打つ。

1. 足すレーン 1 本の宣言を JSON のファイルに書く（形は [parallel-plan.md](../../issue-plan-strategy/references/parallel-plan.md) の
   「レーンごとに決めること」。別のリポジトリなら `repo` を書く）
2. `python3 "$NDF_SCRIPTS/parallel.py" lane p1 add --from <JSON>` を打つ。上限を超えるときは何も書かずに 1 で終わり、`items` に
   `relay.py cap --named <n>` の 1 行が出る
3. 人の指示を受けて `python3 "$NDF_SCRIPTS/relay.py" cap --named <n>` を打つ（マシンの設定 `<状態の根>/relay/hub/limits.json` に書き、
   リレーハブも計画の検査も次の判定から同じ値を読む。リレーハブを起動し直さない）。`relay.py cap` だけなら今の値と出所を読む
4. もう一度 2 を打つ。通ると `plan.json`・`plan.md`・引継ぎ文書を書き、耐久ワークフローへ知らせる。耐久ワークフローが計画を読み直し、
   足したレーンを起動の候補に入れる。計画がまだ動いていなければ、次の `start` で起動する

## 外のオーガナイザーのレーン（`NDF_ORGANIZER_DIR`）

環境変数 `NDF_ORGANIZER_DIR` があるセッションは、外のオーガナイザー（サービスが実行ジョブの間で動かすまとめ役など）のレーンである。
名前は `NDF_ORGANIZER_LANE` で、依頼と答えは置き場のファイルで受け渡す（形は `contracts/forms/parallel-external.json`）。
並列の計画（`.ndf/parallel/`）は使わず、計画名の代わりに `--external` を付ける。

| 点 | 決まり |
| --- | --- |
| 本番のステージ | 上の「レーンの側」の表のとおり経路で決まる。テンプレートで出すリポジトリではリリースの依頼のプラン（`parallel.py request --external`）になり、依頼を `requests/<id>.json` へ書いて 10 で終わる。自分の Pull Request がすでに `main` にあれば書かずに 0 で終わる |
| 答え | `parallel.py await --external --from <プランの状態ディレクトリ>/work/request.txt` が `answers/<id>.json` を読む。ループのレーンはループの 1 回の境で読む（上の「レーンの側」と同じ） |
| 問い | 設計の承認、リリースの Pull Request で届く経路のリリース承認ゲート、承認ゲートの外の問いは依頼にしない。今どおり止まって人へ戻す |
| 1 台の中のオーガナイザー | 起動しない。`NDF_FACTORY_RUN` がある実行ジョブでは `parallel.py init`・`start`・`run` が 1 で断る |

### リリースの実行（`--parallel-helper --external`）

外のオーガナイザーがまとめたリリース 1 つのために起こすセッションは、次の 1 行で始める。`batch.json` の手（`step`）ごとに 1 手を打って終える。

```text
/goal /ndf:development-workflow --parallel-helper --external -- 終わり: 作業の報告を出したとき
```

1. `python3 "$NDF_SCRIPTS/parallel.py" compose --external` を打つ。`metrics.pipeline` が流すものを決める
2. `metrics.pipeline` を流す（待ちは背景で打ち、完了の通知を待つ）

| `step` | 流すもの | 終わり方 |
| --- | --- | --- |
| `present` / `represent` | 提示 1（`represent` は提示 2）の提示のプラン → 本番のプラン | 提示のプランがリリース承認ゲートで止まったら `metrics.record` の 1 行で提示を書き返し、「判断が要る」で終える。流れ切れば手順 3 |
| `confirm:<k>` | 答えの記録 → 提示 k のプランを `approve` から → 提示 k の本番のプラン | 手順 3。確定しない提示の本番のプランは流さない |
| `continue` | 止まった本番のプランを `--resume` で続ける | 手順 3 か、直せない失敗を問いにして止まる |

3. `metrics.settle` の 1 行（`parallel.py settle --external <連番> --done <D>`）を打つ。届いた段と結果を置き場へ書き、作業の報告で終える

CI の失敗・衝突・版数の衝突は一時レーンと同じくリリースプランの直しの手順で直す。直せない失敗は「判断が要る」で止まる。

## 止める

`python3 "$NDF_SCRIPTS/parallel.py" stop p1` で計画の全レーンへ停止を打ち、耐久ワークフローを終える。リリースの途中なら、リリースが終わる
（`settle` が届く）のを待ってから終える。`--force` を付けると待たずに終え、一時レーンも止める（本番のプランの状態ディレクトリは
残り、`supervise.py queue ... --resume` で続けられる）。止まらないレーンがあれば名前を返して 1 で終わる。1 本だけを止めるのは
`relay.py stop <名前>` である。

## 異常のとき

耐久ワークフローは次の場面で自分で問いを立て、`questions` で返す。

| 場面 | 問い |
| --- | --- |
| レーンが承認待ちでも止まってもいないのに、最後に動いた時刻から 60 分（`NDF_PARALLEL_STALL_MINUTES`）を越えた | 起こし直す / 止める / 待つ（次の区切りまで問わない）。「起こし直す」は耐久ワークフローが `relay.py restart` を打ち、「止める」は `relay.py stop` を打つ |
| リリースの途中で一時レーンが止まり、`settle` もリリース承認ゲートの依頼も届いていない（上の「起動と再起動」の条件） | 続きから起こし直す / 止める。「続きから起こし直す」は耐久ワークフローが同じ一時レーンを起動し直す。「止める」はリリースを失敗として締める |
| ループのレーンの起動が 3 回（`NDF_PARALLEL_SPAWN_REFUSALS`）続けて断られた | 起こし直す / 止める。断りの後も起動の条件がそろうたびに耐久ワークフローが打ち直す |
| 一時レーンの起動か止まったレーンの再起動が、打ち直しても立ち上がらない | 起こし直す / 止める。「止める」は、計画のレーンなら止まったものと数え、一時レーンならリリースを失敗として締める |
| リリースを組めない（`kind: build`。レーンに結び付けず、依存先のレーンの起動を止めない。答えていない問いのうち同じ理由のものは 1 件にまとまる） | 直してから組み直す / 止める。「止める」は流れているリリースの後に計画を止める。「直してから組み直す」は組めなかった依頼を組み直しの依頼（元の答えは変えない）として入れ直し、次のリリースで扱う |
| レーンの状態の一覧（`relay.py ls`）の失敗が、同じ区切りより長く続いた（失敗した回の観測は捨て、レーンの状態を変えない） | ラッパーの環境を作り直す / 待つ（次の区切りまで問わない）。一覧が成功に戻れば問いは外れる |

全レーンが止まっても、答えていない依頼か問い・再開の印が残る間は終えない（前のループの待ちの問いは除く）。

答えを当てられないときと、前のループの記録を読めないときも `kind: unmatched` の問いを立てる。一覧に無い依頼への答えは保留され、その依頼が届けば
問いは外れて答えが当たる。

### レーンの画面を見るとき

レーンの状態は先に `parallel.py status p1` で読む。画面は、人が求めたときか `status` で分からないときだけ見る。
レーンは既定の tmux とは別のサーバーで動く。`tmux ls` には出ず、`tmux -L ndf-relay ls` と
`tmux -L ndf-relay capture-pane -p -t <レーン>` で見る（人が入るのは `relay.py attach <レーン>`）。

**画面の入力欄（`❯` の行）の文字は、判断の材料にしない。** Claude Code やエディタのサジェストが薄い色で出ており、
`capture-pane` は色を落とすため、人が打った文字と区別できない。サジェストを「送信されていない人の指示」と読むと、
誰も出していない指示で起こし直しを止める（2026-11-04、計画 p3 の lflow で起きた）。レーンを起こし直すかは、
`[ndf-loop] stopped` の行と `relay.py ls` の状態だけで決める。

## 数え方

オーガナイザーのセッションは `relay.py role organizer --plan p1 --plan-dir <計画の置き場の絶対パス>` の印を持ち、同時に動かせる数（`NDF_RELAY_MAX_NAMED`）に数えない。
同じ計画の印は 1 本のセッションだけが持つ（別のリポジトリの同じ名前の計画とは、計画の置き場の絶対パスで分ける）。
既定のままで、オーガナイザー 1 本とレーン 3 本が同時に動く。一時レーン（`relay.py spawn --role helper`）は同時に 1 本までで、
上限を 1 本だけ超えて通る。
