# モード判定の境界事例

`SKILL.md` の条件表で決まらない場合の判断材料。ここも**判定基準の一部**であり、判定基準を
この Skill の外へ写さない原則はここにも及ぶ。

## 判定に使う問い

順に答える。1〜5 はすべて `architecture` の条件であり、**1 つでも「はい」なら
`architecture`** とする。

1. 公開インタフェース（API・イベント・コマンド）の約束が変わるか
2. 既存データの移行が要る形でデータ構造が変わるか（列の削除・改名・型変更など）
3. 誰が何をできるかが変わるか
4. 変更が複数のモジュール・サービスにまたがるか
5. 業務ルール（金額・期限・状態遷移・権限）の意味が変わるか

すべて「いいえ」なら、次の 3 つを上から見て**最初に該当した行**を採る。

| 変更の中身 | モード |
| --- | --- |
| 本番の振る舞いが変わる（機能追加・バグ修正・既定値の変更など） | `standard` |
| 本番の振る舞いは変えず本番コードの構造を変える（関数の抽出・分割・移動など） | テストが十分にあれば `standard`、テストがない・少なければ `legacy-refactor` |
| 本番の振る舞いも本番コードの構造も変えない局所変更（文言・書式・コメント・ドキュメント・静的な設定値、テストの追加、ログ出力の追加など） | `light` |

3 行目の括弧内は**例示であり限定列挙ではない**。基準は「本番の振る舞いも本番コードの構造も
変えない」ことであり、`SKILL.md` の条件表の `light` と同じ条件である。

構造変更のみの単独依頼も、テストがあるなら `standard` で扱う（`legacy-refactor` は
「振る舞い不変を示す手段がない」ことへの対処であり、テストが揃っていれば不要）。

## よくある境界事例

| 変更 | モード | 理由 |
| --- | --- | --- |
| ログ出力の追加 | `light` | 本番の振る舞いも処理の流れも変えない。ただし個人情報を含めないことを確認する |
| ログの内容を監視・課金の根拠に使っている場合の変更 | `standard` | 下流の利用者がいるため本番の振る舞いの変更として扱う。公開インタフェース自体は変わらないので `architecture` へは上げない |
| エラーメッセージの文言修正 | `light` | 文言のみ |
| エラーコード・状態コードの変更 | `architecture` | 呼び出し側が分岐に使う約束が変わる |
| 設定の既定値の変更 | `standard` | 既存利用者の本番の振る舞いが変わる |
| 設定項目の追加（既定値は現状維持） | `light` | 既存の本番の振る舞いは変わらない |
| 依存パッケージの版更新（互換範囲） | `light` | 本番コードを変えない。ただし影響範囲が広いため、`light` の検証の例外として既存テスト一式を実行する |
| 依存パッケージの入れ替え | `standard`（複数モジュールにまたがるなら `architecture`） | 本番の振る舞いの差異が出る |
| インデックスの追加 | `standard` | スキーマ定義は変わるが約束は変わらず、既存データの移行も不要。移行と性能を確認する |
| 列の追加（NULL 許容、既定値あり） | `standard` | 既存データの移行が不要な範囲 |
| 列の削除・改名・型変更 | `architecture` | 既存データの移行と後方互換の扱いが必要 |
| 内部関数の抽出（テストあり） | `standard` | 構造改善。テストがあるので `legacy-refactor` は不要。単独依頼でも `standard` で進める |
| 内部関数の抽出（テストなし） | `legacy-refactor` | 振る舞い不変を示す手段を先に作る |
| 生成物（ビルド出力・同期ファイル）の再生成 | `light` | 生成コマンドの再実行で確認する |
| 生成の仕組み自体の変更 | `standard`（生成結果が公開インタフェースに関わるなら `architecture`） | 生成結果が変わる |
| ドキュメントの更新 | `light` | リンクと手順の実行可能性を確認する |
| ドキュメントと実装が食い違っていた場合の実装修正 | `standard` | 本番の振る舞いが変わる |
| テストの追加のみ | `light` | 本番コードを触らないので本番の振る舞いは変わらない。追加分と関連する既存テストを合わせて実行する |
| テストの削除・書き換え | `standard` | 何を担保しなくなるかの判断が要る |

## モード別の詳細

### `light`

- 目的: 手を止めないこと。工程を増やさない
- **やること**: 成功条件（何をもって完了とするか）の確認、変更範囲の確定、変更箇所が
  読み込まれる経路の 1 度の実行、静的解析、`cross-review`
- **やらないこと**: 仕様の作成、テスト駆動の強制、全体テストの要求（依存パッケージの
  版更新のみ例外として既存テスト一式を実行する）
- 判断の根拠（本番の振る舞いに影響しないと言える理由）を報告に 1 行入れる
- **レビューは行う。** Pull Request を出す以上、その差分は誰かがレビューする。手段は
  他のモードと同じ `cross-review` で、差分の小ささはラウンド数が吸収する
- 要求と受け入れ条件も**行う**。モードを判定する単位が Pull Request であり、
  **判定の入力になる**ため、モードによらず通る
- 配布は**行う**。配布物の中の 1 行を直す変更は `light` になり得る。差分が無ければ
  `release` が飛ばす
- リリース後テストと振り返りは**行わない**。本番の振る舞いも本番コードの構造も変えない
  ため、配布した後の環境で新たに確かめることが無く、進め方を見直す材料も出ない
- 範囲外の課題は、見つかれば `out-of-scope` で起票する（工程ではないため `light` でも行う）

### `standard`

- 目的: 受け入れ条件を満たし、退行を出さないこと
- 受け入れ条件を先に作る。条件が作れない依頼は、質問して止まる
- 実装はテスト駆動で進める。**通したあとに構造改善の工程を通す**（手を付けない判断でもよいが、
  工程は飛ばさない）。手を入れる場合は差分を分ける
- 振る舞いを変えない構造変更のみの依頼は、受け入れ条件を「既存テストが通り続けること」とし、
  実装は `refactoring` の手順で進める
- レビューは `cross-review`（収束レビュー）を使う
- 完了判定は全体テストまで通す
- 配布は**行う**。まとまり単位でマージが終わった後、最後にマージした側が版を上げる
- リリース後テストは、`quality-gates` の完了報告に「未検証の項目」が残ったときに行う。
  残っていなければ省く
- 振り返りは**行う**。レビューの工程を通るため、起票の取りこぼしを確かめる

### `architecture`

- 目的: 約束（インタフェース・データ・権限）を壊さないこと
- 実装前に、代替案と採否の理由を残す
- 後方互換の扱いを決める。破る場合は移行手順と切り戻し手順を書く
- 移行は**前進と巻き戻しの両方**を実行して確認する
- レビューは `cross-review`（収束レビュー）を使う
- 配布を**行う**。約束を破る変更なら版は MAJOR になる。大小の根拠を配布の報告へ残す
- リリース後テストを**行う**。約束が壊れていないことは、配布された成果物の側でしか確かめられない
- 振り返りを**行う**

### `legacy-refactor`

- 目的: 振る舞いを変えないことを示せる状態を作ること
- 現状固定テストを先に置く。固定できない部分は範囲から外す
- 機能変更を混ぜない。混ぜたくなったら差分を分ける
- 固定テストで不具合を固定した場合は印を残す
- 配布を**行う**。振る舞いを変えないため、版は PATCH になるのが通常である
- リリース後テストを**行う**。振る舞いが変わっていないことを、実環境で確かめる
- 振り返りを**行う**

## 複数の変更が混ざっている依頼

1 つの依頼に複数モードの変更が含まれる場合、**モードを上げて全体を重くしない**。依頼を
分割し、それぞれのモードで進める。

```text
依頼: 「注文一覧に絞り込みを追加して、あと表記のゆれも直して」

分割:
- 絞り込みの追加   → standard（受け入れ条件・テスト駆動・全体検証）
- 表記のゆれの修正 → light（別の差分・別のコミット）
```

分割できない場合（同じ行を触るなど）は、上位のモードで進める。

## 構造改善の退避先

工程表は `architecture` と `legacy-refactor` の構造改善に `cross-refactoring` を置く。
**次のいずれかに当たるときは `refactoring` 単独で進める。**

| 条件 | 理由 |
| --- | --- |
| 振る舞い不変を示すテストが無い | `--baseline-test` が必須で、無ければ適用の検証が成り立たない |
| 参加する CLI のいずれかが未認証、または導入されていない | 起動の前の確認で中断する |
| 対象の範囲を絞れない | `--scope` が必須で、絞れないと提案が発散し Pull Request が肥大する |

**退避したことを完了報告へ残す。** 条件に当たったかどうかは、後から差分だけを見ても
分からない。

`standard` は既定が `refactoring` であるため、この判断が要らない。

## 判定を記録する場所

| 状況 | 記録先 |
| --- | --- |
| 計画ファイルを作る変更 | `implementation-plan` の計画ファイル冒頭 |
| 計画ファイルを作らない変更 | プルリクエスト本文（`light` は 1 行でよい） |

記録には**モードとその根拠**を書く。判定基準の表を写さない。
