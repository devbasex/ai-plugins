# モード判定の境界事例

`SKILL.md` の条件表で決まらない場合の判断材料。ここも**判定基準の一部**であり、判定基準を
この Skill の外へ写さない原則はここにも及ぶ。

## 判定に使う問い

**先に `operation` を見る。**

0. プロダクションコードも文書も変えず、**外部の系の状態だけ**を変えるか

「はい」なら `operation` である。**問い 1〜5 は見ない。** 権限の設定の変更は問い 3 に当たる
が、変えるのは外部の系の状態なので、テスト駆動は当たらない（設計は
触る領域に当たるときだけ通る。下の「`operation`」の節にある）。
重大さは実行前の承認で受ける（`SKILL.md` の「人手の承認を求める承認ゲート」）。
手順は [operation-run.md](operation-run.md) にある。

**次に `documentation` を見る。**

0.5. 読み手へ渡すビジネス文書を作る・改訂するか

「はい」なら `documentation` である。**問い 1〜5 は見ない。** 文書の中に公開インタフェースの
説明が含まれても、変えるのは説明であって約束ではない。**リポジトリの説明文書（`README.md` /
`docs/`）はこれに当たらない**（判定を分けるのは読み手である）。タイプの判定は
[document-types.md](document-types.md) にある。

「いいえ」なら順に答える。1〜5 はすべて `standard` の条件であり、**1 つでも「はい」なら
`standard`** とする。

1. 公開インタフェース（API・イベント・コマンド）の約束が変わるか
2. 既存データの移行が要る形でデータ構造が変わるか（列の削除・改名・型変更など）
3. 誰が何をできるかが変わるか
4. 変更が複数のモジュール・サービスにまたがるか
5. 業務ルール（金額・期限・状態遷移・権限）の意味が変わるか

すべて「いいえ」なら、次の 3 つを上から見て**最初に該当した行**を採る。**`standard` は
こちらにも現れる。** 問い 1〜5 に当たらなくても、本番の振る舞いが変われば `standard` である。

| 変更の中身 | モード |
| --- | --- |
| 本番の振る舞いが変わる（機能追加・バグ修正・既定値の変更など） | `standard` |
| 本番の振る舞いは変えずプロダクションコードの構造を変える（関数の抽出・分割・移動など） | テストが十分にあれば `standard`、テストがない・少なければ `legacy-refactor` |
| 本番の振る舞いもプロダクションコードの構造も変えない局所変更（文言・書式・コメント・ドキュメント・静的な設定値、テストの追加、ログ出力の追加など） | `light` |

3 行目の括弧内は**例示である**。基準は「本番の振る舞いもプロダクションコードの構造も
変えない」ことであり、`SKILL.md` の条件表の `light` と同じ条件である。

構造変更のみの単独依頼も、テストがあるなら `standard` で扱う（`legacy-refactor` は
「振る舞い不変を示す手段がない」ことへの対処であり、テストが揃っていれば不要）。

**実装の前に構造を整える判断は、モードとは別である。** `legacy-refactor` は変更全体に
掛かるモードで、そちらは**これから触る対象の構造**に対する判断である。書き分けは
[implementation-plan の pre-refactoring.md](../../implementation-plan/references/pre-refactoring.md)
にある。

## よくある境界事例

| 変更 | モード | 理由 |
| --- | --- | --- |
| ログ出力の追加 | `light` | 本番の振る舞いも処理の流れも変えない。ただし個人情報を含めないことを確認する |
| ログの内容を監視・課金の根拠に使っている場合の変更 | `standard` | 下流の利用者がいるため本番の振る舞いの変更として扱う |
| エラーメッセージの文言修正 | `light` | 文言のみ |
| エラーコード・状態コードの変更 | `standard` | 呼び出し側が分岐に使う約束が変わる |
| 設定の既定値の変更 | `standard` | 既存利用者の本番の振る舞いが変わる |
| 設定項目の追加（既定値は現状維持） | `light` | 既存の本番の振る舞いは変わらない |
| 依存パッケージの版更新（互換範囲） | `light` | プロダクションコードを変えない。ただし影響範囲が広いため、`light` の検証の例外として既存テスト一式を実行する |
| 依存パッケージの入れ替え | `standard` | 本番の振る舞いの差異が出る |
| インデックスの追加 | `standard` | スキーマ定義は変わるが約束は変わらず、既存データの移行も不要。移行と性能を確認する |
| 列の追加（NULL 許容、既定値あり） | `standard` | 既存データの移行が不要な範囲 |
| 列の削除・改名・型変更 | `standard` | 既存データの移行と後方互換の扱いが必要 |
| 内部関数の抽出（テストあり） | `standard` | リファクタリング。テストがあるので `legacy-refactor` は不要。単独依頼でも `standard` で進める |
| 内部関数の抽出（テストなし） | `legacy-refactor` | 振る舞い不変を示す手段を先に作る |
| 生成物（ビルド出力・同期ファイル）の再生成 | `light` | 生成コマンドの再実行で確認する |
| 生成の仕組み自体の変更 | `standard` | 生成結果が変わる |
| ドキュメントの更新 | `light` | リンクと手順の実行可能性を確認する |
| ドキュメントと実装が食い違っていた場合の実装修正 | `standard` | 本番の振る舞いが変わる |
| テストの追加のみ | `light` | プロダクションコードを触らないので本番の振る舞いは変わらない。追加分と関連する既存テストを合わせて実行する |
| テストの削除・書き換え | `standard` | 何を担保しなくなるかの判断が要る |
| 外部の系の権限・保護の規則の設定 | `operation` | プロダクションコードも文書も変えない。重大さは実行前の承認で受ける |
| 反映先の構成の変更（値の設定・機能の有効化） | `operation` | 同上。設定を書いたプロダクションコードを変えるなら `standard` |
| 本番のデータの投入・修正 | `operation` | 系の状態だけが変わる。**取り消せない単位を含むことが多い** |
| 外部サービスの操作（登録・停止・付け替え） | `operation` | 同上 |
| 設定を持つプロダクションコードの変更と、その反映 | `standard` | **プロダクションコードを変えるため `operation` の条件を外れる。** 反映はリリースの工程で扱う |
| 運用の手順書を書き直す | `light` | 外部の系を触らない。文書の変更である |
| 運用の手順を変え、実際に実行する | `operation` | 実行が伴うため。手順書の差分は実行の記録と同じ Pull Request に載る |

## モード別の詳細

### `light`

- 目的: 手を止めないこと。工程を増やさない
- **やること**: 成功条件（何をもって完了とするか）の確認、変更範囲の確定、変更箇所が
  読み込まれる経路の 1 度の実行、静的解析、`cross-review`
- **やらないこと**: 仕様の作成、テスト駆動の強制、全体テストの要求（依存パッケージの
  版更新のみ例外として既存テスト一式を実行する）
- 判断の根拠（本番の振る舞いに影響しないと言える理由）を報告に 1 行入れる
- **レビューは行う。** Pull Request を出す以上、その差分は誰かがレビューする。手段は
  他のモードと同じ `cross-review` で、差分の小ささはラウンド数が吸収する
- 要求と受け入れ条件も**行う**。モードを判定する単位が Pull Request であり、
  **判定の入力になる**ため、モードによらず通る
- 設計は**条件付き**である。触る領域が「すべての変更」以外に 1 つ以上当たるときだけ通る
  （記録の追加が運用・保守性の条件を持つ場合など）。**独立した設計文書は作らず、受け入れ
  条件を書いたファイルの節へ書く**。ドキュメント再構成とドキュメントレビューは通らない
- リリースは**行う**。配布物の中の 1 行を直す変更は `light` になり得る。差分が無ければ
  `release` が飛ばす
- リリース後テストと振り返りは**行わない**。本番の振る舞いもプロダクションコードの構造も変えない
  ため、リリースした後の環境で新たに確かめることが無く、進め方を見直す材料も出ない
- 範囲外の課題は、見つかれば `out-of-scope` で起票する（工程ではないため `light` でも行う）

### `standard`

- 目的: 約束（インタフェース・データ・権限）を壊さないこと
- 受け入れ条件を先に作る。条件が作れない依頼は、質問して止まる
- 実装前に、代替案と採否の理由を残す
- 振る舞いを変えない構造変更のみの依頼は、受け入れ条件を「既存テストが通り続けること」とし、
  実装は `refactoring` の手順で進める
- 後方互換の扱いを決める。破る場合は移行手順と切り戻し手順を書く
- 移行は**前進と巻き戻しの両方**を実行して確認する
- レビューは `cross-review`（収束レビュー）を使う
- リリースを**行う**。約束を破る変更なら版は MAJOR になる。大小の根拠をリリースの報告へ残す
- リリース後テストを**行う**。約束が壊れていないことは、リリースされた成果物の側でしか確かめられない
- 振り返りを**行う**

### `operation`

- 目的: 外部の系の状態を、記録の残る形で変えること
- **実行の範囲を先に文字にする。** 実行前の承認が読むのはその範囲であり、書かれていない
  ものは承認の対象にならない
- **単位ごとに取り消しの手段を書く。** 戻せない単位は、戻せないことと影響の範囲を実行の
  前に書く
- **実行の前に承認を得る**（対象が本番系のとき）。検証用の系への操作は提示して進めてよい
- **単位ごとにコマンド・出力・終了コードを残す。** 合否は終了コードで見る
- **失敗したらその時点で止める。** 部分適用の範囲を確定させる
- テスト駆動とリファクタリングは**行わない**。産物が外部の系の状態と実行の記録であり、
  データ構造も入出力の契約も持たない
- 設計は**条件付き**である。触る領域が「すべての変更」以外に 1 つ以上当たるときだけ通り、
  **独立した設計文書は作らず実行の記録と同じファイルの節へ書く**。非機能の実現方式が
  無条件の成果物になる（条件と成果物は `design` が持つ）
- リリースを**行う**。リリースするものが無ければ `release` が飛ばす
- 確定仕様化・リリース後テスト・振り返りは**条件付き**である（条件は
  [stage-notes.md](stage-notes.md)「`operation` の工程」）
- 手順は [operation-run.md](operation-run.md) にある

### `legacy-refactor`

- 目的: 振る舞いを変えないことを示せる状態を作ること
- 現状固定テストを先に置く。固定できない部分は範囲から外す
- 機能変更を混ぜない。混ぜたくなったら差分を分ける
- 固定テストで不具合を固定した場合はマーカーを残す
- リリースを**行う**。振る舞いを変えないため、版は PATCH になるのが通常である
- リリース後テストを**行う**。振る舞いが変わっていないことを、実環境で確かめる
- 振り返りを**行う**

### `documentation`

- 目的: 読み手へ渡すビジネス文書を、git の差分に載る形で作る
- **中間形式は Markdown である。** 版面・書体・色はソースへ埋めず、生成へ渡す入力として
  別に持つ。埋めると生成の経路が 1 つに固定される
- **6 つのタイプのどれかを 続けて選ぶ**（判定は [document-types.md](document-types.md)）
- **`構造改善` だけが対象外である。** 章立ての組み直しは `ドキュメント再構成` が担う
- `設計` は構成案と体裁設計の 2 つを作る。体裁設計は `design` の `layout-<出力の形>.md` が持つ
- `配布` は**生成と提出の 2 つの手順**である。生成は対になる下書き先へ行い、提出は本番の提出先へ
  承認した生成物を移す
- **企画承認は設計 Pull Request のマージ、制作物承認は本番の提出先への操作である。**
  どちらも既存の承認ゲートで、新しい承認ゲートを作らない
- リポジトリの説明文書（`README.md` / `docs/`）はこのモードに当たらない。判定を分けるのは
  読み手である

### `documentation` と他のモードが混ざるとき

**分ける。** コードと提案資料が同じ差分に入る場合は、文書の側を別の Pull Request へ出す。
混ぜたまま高い方のモードで進めると、文書にリファクタリングを、コードに体裁レビューを課すことになる。

**高さの大小はモードを上げる判断の根拠にしない。** `standard` から `documentation` への変更は
対象が変わったのであり、プロダクションコードを触ると分かった変更を文書のモードへ
移すのは誤りである。高さが使われるのは、1 つの Pull Request が閉じる課題のモードが食い違った
ときにどちらでチェックするかを決める場面だけである。

## 複数の変更が混ざっている依頼

1 つの依頼に複数モードの変更が含まれる場合、**モードを上げて全体を重くしない**。依頼を
分割し、それぞれのモードで進める。

```text
依頼: 「注文一覧に絞り込みを追加して、あと表記のゆれも直して」

分割:
- 絞り込みの追加   → standard（受け入れ条件・テスト駆動・全体検証）
- 表記のゆれの修正 → light（別の差分・別のコミット）
```

分割できない場合（同じ行を触るなど）は、上位のモードで進める。

## リファクタリングの退避先

工程表は `standard` と `legacy-refactor` のリファクタリング（`構造改善` の行）に `cross-refactoring` を置く。
`light` と `operation` は工程そのものが対象外である。**工程に入ったら、最初に
`refactor.py assess` で飛ばしてよいかを見る。** 飛ばす条件と、`refactoring` 単独へ退避する
条件は別である。

```bash
python3 "$RF/refactor.py" assess --base origin/develop; rc=$?; echo "exit=$rc"
```

`$RF` は `cross-refactoring` の `scripts/` の絶対パスである。

**飛ばす。** 次に当たるときは何も起動しない。

| 条件 | 理由 |
| --- | --- |
| `assess` が終了コード 3（プロダクションコードの差分が無い、または変更が 10 行以下） | 整える対象が無いか、提案の費用が見合わない |

`assess` が終了コード 2（引数の誤り・起点を解けない）を返したときは、値を直して打ち直す。
**判定できないことを、飛ばしてよいと読まない。**

飛ばしたときは次の 3 つを残す。**工程の記録は通した場合と同じ値にする。** 区別は Pull Request の
本文の 1 行が持つ。記録を打たずに進めると「記録なし」のまま残り、飛ばした場合と見分けられる。

| 記録先 | 何を残すか |
| --- | --- |
| 進捗記録 | 工程 `構造改善`（`projects-sync.sh <課題番号> stage "構造改善"`） |
| Pull Request の本文 | `構造改善: 飛ばした（<assess の理由の行>）` の 1 行 |
| フェーズレポート | 同じ 1 行を `理由` に含める |

**`refactoring` 単独へ退避する。** `assess` が終了コード 0 で、次のいずれかに当たるとき。

| 条件 | 理由 |
| --- | --- |
| 振る舞い不変を示すテストが無い | `--baseline-test` が必須で、無ければ適用の検証が成り立たない |
| 参加する CLI のいずれかが未認証、または導入されていない | 起動の前の確認で中断する |
| 対象の範囲を絞れない | `--scope` が必須で、絞れないと提案が発散し Pull Request が肥大する |

**退避したことを完了報告へ残す。** 条件に当たったかどうかは、後から差分だけを見ても
分からない。

## 途中でモードが変わったとき

判定はやり直してよい。ただし**上げる方向のみ**を既定とする。

| 状況 | 対応 |
| --- | --- |
| `light` のつもりが外部の系を触ると分かった | `operation` へ上げる |
| `operation` のつもりがプロダクションコードも触ると分かった | `standard` へ上げる。実行と差分を分ける |
| `light` のつもりが本番の振る舞いを変えると分かった | `standard` へ上げ、受け入れ条件を作り直す |
| `light` のつもりがプロダクションコードの構造を変えると分かった | テストの有無で `standard` か `legacy-refactor` へ上げる |
| `legacy-refactor` の途中で公開インタフェースが変わると分かった | `standard` へ上げる。ここまでの差分を分ける |
| `light` のつもりが読み手へ渡す文書だと分かった | `documentation` へ上げる |
| `documentation` の途中でプロダクションコードも触ると分かった | **分ける。** 文書とコードを別の Pull Request にする |
| 工程が重いのでモードを下げたい | 下げない。重い理由が条件に該当しているため |

**`documentation` と他のモードの間だけは上げ下げにしない。** 変わったのは対象である。
プロダクションコードを触ると分かった変更を文書のモードへ移すのは誤りである。

モードを下げたい場合は、**変更そのものを分割する**。本番の振る舞いもプロダクションコードの構造も
変えない部分を先に `light` として出し、残りを本来のモードで進める。

## 判定を記録する場所

| 状況 | 記録先 |
| --- | --- |
| 実装計画のファイルを作る変更 | `implementation-plan` の実装計画のファイル冒頭 |
| 実装計画のファイルを作らない変更 | プルリクエスト本文（`light` は 1 行でよい） |

記録には**モードとその根拠**を書く。判定基準の表を写さない。
