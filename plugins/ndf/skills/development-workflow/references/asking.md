# 人へ問うか、AI が決めるか（問い合わせの区分）

この文書が、`AskUserQuestion` で人へ問ってよい場面と、質問に付ける区分の SSOT である。承認資料の中身は `approval-request.md`、判断を求めるときの材料の示し方は `decision-request` の Skill が持つ。どちらも区分の表を写さずにここを指す。

## 例

設計の途中で「ライブラリ A と B のどちらを使うか」を問おうとした。これは下の「区分」のどれにも当たらない。問わずに、根拠を集めて推奨の案を選び、決めたことと理由をその工程の報告に 1 行で書いて進む。

```text
- 決めたこと: ライブラリ A と B のどちらを使うか → A（既存の依存に入っていて、B は保守が止まっている）
```

設計 Pull Request のマージの承認は設計承認ゲートである。`AskUserQuestion` の入力に `"metadata": {"source": "ndf-gate:1"}` を付けて問う。

## 原則: AI が自分で決める

人へ回すのは、AI が決めてよい範囲の外にある質問だけにする。**迷った・情報が足りない・好みが分かれるは、人へ回す理由にならない。** その場合は根拠を集めて推奨の案を選び、理由を記録して進む。

AI が決める例:

- 設計の選択・Tool とライブラリの選択・命名・ファイルの保存先
- テストの方針・範囲・順序、実装の順序、並列の数
- 範囲外の課題の扱い（`out-of-scope` で起票して進む）、課題を分ける・まとめる
- レビューの指摘を直すか退けるか（理由を記録する）
- 曖昧なリクエストの解釈（最も筋の通る解釈を選び、選んだ理由を記録する）

## 区分

`AskUserQuestion` の `metadata.source` に、質問の区分を 1 つ付ける。区分の無い質問は出さない。

| 区分（`metadata.source`） | 当たるもの | 設定で外せるか |
| --- | --- | --- |
| `ndf-gate:1` | 設計承認ゲート（設計 Pull Request のマージ。設計承認ゲートの委任の承認を含む） | 外せない |
| `ndf-gate:2` | リリース承認ゲート（本番系へ届く操作・制作物承認） | 外せない |
| `ndf-ask:redline:<番号>` | 共通原則の C1〜C8・プロジェクトの P・スプリントの R に当たる操作の承認。`<番号>` は `C4`・`P1`・`R2` の形 | 外せない |
| `ndf-ask:cost` | お金が出ていく: 有料の資源の起動・有料の外部 API・購入・プランの変更。`cost.threshold_usd` 以下は AI が決める | 外せる |
| `ndf-ask:irreversible` | 取り消せない操作のうちレッドラインに当たらないもの: 外部の人への送信（メール・チャット・Issue での言及）・外部の系のデータの削除・公開範囲を広げる操作 | 外せる |
| `ndf-ask:human-action` | 人にしかできない操作: 対話のログイン・二要素認証・権限の付与・秘密の発行と登録 | 外せる |
| `ndf-ask:legal` | 規約・コントラクト・ライセンス・個人情報の扱いへの同意 | 外せる |
| `ndf-ask:<名前>` | プロジェクトが `.ndf/ask.json` の `extra` に書いた区分 | — |

**レッドラインに当たる操作は、`irreversible`・`human-action` より先に `ndf-ask:redline:<番号>` を使う。** 例: 強制 push や `-D` の削除は `redline:C4`、秘密の登録は `redline:C1`、他のリポジトリへの起票は `redline:C5`、`.ndf/` の書き換えは `redline:C7`。

1 つの質問に複数の区分が当たるときは、表の上にあるものを付ける。どれに当たるかが中身で変わる手順では、区分ごとに場合を分け、どれにも当たらなければ AI が決める。

## 質問の前に調べること

`AskUserQuestion` の直前に、hook の guard `reading-check` が、読み手役が確認した記録（`ndf records reading add` の記録）を調べる。
文の良し悪しは判定しない。記録は、承認ゲートの質問では `ndf document-rebuild gate`（工程の読み手役のステップか、工程の外の承認では質問を出す AI が打つ）が、判断の質問では質問を出す AI が
作る（[approval-request.md の「読み手役の確認」](approval-request.md#読み手役の確認)）。承認ゲートの質問が止められたら、`ndf records reading check --gate` で
確かめ、合わなければ `ndf progress reread` か `ndf document-rebuild gate` を打ち直す。質問の文を直して出し直さない。

| 区分 | hook が調べること |
| --- | --- |
| `ndf-gate:` で始まる | 同じリポジトリに、同じ質問の文の記録がある。記録に Pull Request があれば、その head が、手元のリモート追跡ブランチの head と同じ |
| `ndf-ask:` で始まる | 同じリポジトリに、同じ質問の文の記録がある |
| 区分なし | 調べずに通す |

- 合わなければ質問を止め、足りないもの（`no_record`・`head_moved`）と、記録を残すコマンドを示す。止めるのは、利用者が次に入力するまでの間に、同じ区分・同じ理由で 2 回までで、その次は注意を付けて質問を出せる
- 止めないもの: 区分の無い質問、人に尋ねない自動の承認、人のいない実行（`NDF_FACTORY_RUN`）、記録のファイルを開けないとき、git が失敗したとき、hook の処理が失敗したとき
- 止めたくないときは、環境変数 `NDF_HOOK_OFF` に `reading-check` を足す

## 決めたことの記録

**11 系の NDF には、問わずに決めたことを記録するサブコマンドが無い。** hook の guard `ask-forward` は
`AskUserQuestion` を中継とオーガナイザーへコピーするだけである。区分に当たらない質問は出さずに自分で決め、決めたことと理由を
その工程の報告（フェーズレポートの `理由`・作業の報告の「見つけたもの」・conductor の報告）に上の例の形で 1 行ずつ書く。

## 並列の計画のレーン

並列の計画（[parallel.md](parallel.md)）の下で区分つきの質問を出すのはオーガナイザーだけである。レーン（`NDF_RELAY_NAME` が計画のレーンにある）
と一時レーン（作業ディレクトリの役割のファイルが `helper`）が、hook の通す質問（承認ゲート・レッドライン・許された区分）を出すと、
hook の guard `ask-forward` が質問を中継のシグナルファイルへ写し、中継のラッパーが `ndf lanes question` で計画へ質問のリクエストとして載せる。読み手役の記録が無く、guard `reading-check` が止めた質問は載せない。

送られたら、その作業を保留して別の作業へ進む。回答はオーガナイザーが送り、オーナーが読んで続ける。回答していないリクエストが閾値を超えると、
レーンは区切りで止まり、閾値以下へ戻ると起きる（[parallel.md](parallel.md) の「回答待ちの停止」）。リクエストそのものは止めない。

| 送り手 | 保留の仕方 | 回答が届いたとき |
| --- | --- | --- |
| 開発ループのレーン | リクエストの id・止まったプラン・続きのステップを引継ぎ文書の「次にやること」に書き、`ndf loop lap <ループ> --session <セッション>` でループの 1 回を締めて次の 1 回へ進む（[loop.md](loop.md)） | ループの 1 回の境で、止まったプランを続きのステップから流す |
| 1 スプリントのレーン・一時レーン | 引継ぎ文書の「次にやること」に続きのコマンドとリクエストの id を書き、`ndf-next` を出さずに、最後に `ndf relay stop "$NDF_RELAY_NAME"` で自分のラッパーを止めてセッションを終える（1 行は保留の手順が返す） | 耐久ワークフローが `ndf relay restart <レーン>` で再起動する（オーガナイザーは起動しない）。回答のイベントを読み、続きから進む |

設計の承認（設計承認ゲート）は、レーンがリクエストとして送るため問わない。ループのレーンは設計承認ゲートで課題を人の判断待ちへ移すときに
設計の承認のリクエストを送る。本番のリリースは、テンプレートで出すリポジトリではリリースのリクエストのプランがリクエストとして送るため問わない。
リリースの Pull Request で届く経路ではレーンが本番チャネルへ入れるリリースプランをそのまま流し、`pace: normal` のリリース承認ゲートは上の表の質問としてオーガナイザーへ送られる
（経路ごとの表は [parallel.md](parallel.md) の「レーンの側」）。

## 人のいない実行

Factory の実行ジョブ（環境変数 `NDF_FACTORY_RUN` が空でない `claude -p`）は人のいない実行である。`AskUserQuestion` は使えず、応答を人が読まない。conductor は人へ問わずに工程を進め、セグメントを終える最後の応答の末尾に**セグメントの報告**を置く。Factory のランナーは報告の結果の行の値でセグメントの結果を決める。

例: 標準のモードの課題 #12 を流し、設計 Pull Request を作ったところで設計承認ゲートに着いた。承認資料の中身を本文の「## 判断の材料」のセクションに書き、その後ろにセグメントの報告を置いて応答を終える。

```markdown
## セグメントの報告

- 結果: 判断が要る
- 課題: #12
- 区分: ndf-gate:1
- 承認ゲート: 設計 Pull Request のマージ
- 質問: 設計 Pull Request をマージしてよいか
- Pull Request: https://github.com/<所有者>/<リポジトリ>/pull/<番号>
- 材料: 本文
- 人に頼むこと: 無し
- 理由: 無し
```

報告の形（結果の値・項目・値ごとに要る項目・材料の書き方）の SSOT はコントラクトのファイル `contracts/hooks/unattended-report.json` である。結果の行の読み方は `ndf-next` のブロックの規則と同じで、応答の文の最後の `- 結果:` の行の値を読む。

区分ごとの扱い:

| 場面 | セグメント | 結果の値と添えるもの |
| --- | --- | --- |
| 区分の無い質問（`.ndf/` をコミットするか・次のコマンドを流してよいか など） | 終えない | 自分で決め、決めたことと理由を報告に書いて続ける |
| 承認ゲート（pace が MVV 判定で通さないとき） | 終える | `判断が要る`。区分 `ndf-gate:<番号>`・承認ゲート・材料。承認ゲートが `設計 Pull Request のマージ` なら Pull Request も（設計承認ゲートの委任の承認と `ndf-gate:2` は Pull Request が無ければ `無し`） |
| 承認を求める区分の質問（`redline`・`cost`・`irreversible`・`legal`・`extra` の区分） | 終える | `判断が要る`。区分・質問・材料 |
| 人の操作が要る質問（`ndf-ask:human-action`） | 終える | `できなかった`。区分・人に頼むこと・理由 |
| 工程を最後まで通した・カットポイント | 終える | `完了`。カットポイントでは `ndf-next` のブロックを添える |
| 続けられない（スクリプトの失敗・権限の不足） | 終える | `できなかった`。理由 |

- **判定結果（`mode:`〜`次のコマンド:`）を出したところでセグメントを終えない。** 判定結果は「呼び出し側へ返すもの」だが、人のいない実行の conductor は呼び出し側でもあり、出したら同じセグメントで `次のコマンド:` のコマンドを打って続ける。打った後に上の表の「終える」場面に着いたときだけセグメントを終える。打ったコマンドが失敗して `できなかった` で終えるときは、失敗を理由に書き、最後の応答に `次のコマンド:` の行を残さない。区分が `ndf-ask:human-action`（人の操作待ち）なら、再開用に `次のコマンド:` を残して終えてよい
- `.ndf/ask.json` の `allow` と `mode` は人のいない実行に当てない。外した区分を AI が決めると、人のいない所でレッドライン・費用・取り消せない操作・規約への同意を AI が承認し、人の操作を「決めて続ける」ことになるため、区分のある質問は `.ndf/ask.json` の設定を読まずにセグメントを終える
- 人の判断の材料は、ランナーのコンテナの外から読める形で渡す。中身は同じ応答の「## 判断の材料」のセクションに書き（材料の値は `本文`）、コンテナの中のファイルのパスは値にしない
- pace が MVV 判定で承認ゲートを通すときは今どおり通し、セグメントの報告は次の承認ゲートか終わりで書く
- セグメントの報告を書かずに応答を終えようとすると、Stop の hook（guard の表の `unattended`）が形の誤りの一覧を添えて変更を要求する。最後の応答の `次のコマンド:` にコマンド（空でも `無し` でもない値）が載ったまま、結果が `判断が要る` でも `完了` でもないときも同じく変更を要求する（区分が `ndf-ask:human-action` のときは変更を要求しない）。背景の作業か予定が残る Stop は変更を要求しない。変更要求の回数はほかの Stop の変更要求と合わせて、利用者の入力ごとに上限の設定 `hook.pushback` の回数までで、上限に達した後の Stop は変更を要求せずに通し、hook の計測に残す
- 変更要求の文と、セグメントの始めに UserPromptSubmit の hook が返す案内は、コントラクトのファイルから作った形の説明（結果の値とその意味・値ごとに要る項目と条件・材料の書き方・値ごとの例）を載せる。プラグインの導入先を Read できない権限でも、その説明に合わせてセグメントの報告を書く
- hook が働くのは、プロンプトの 1 行目が `/ndf:development-workflow`（前に `/goal ` を許す）のセッションだけである。UserPromptSubmit の hook がそのセッションにマーカーを付け、SessionEnd の hook が消す。worker やレビューの `claude -p` は対象にならない

## 問い合わせの設定 `.ndf/ask.json`

プロジェクトごとに hook の働き方と人へ回す区分を変える。NDF はこのファイルを読むだけで、書かない。

```json
{
  "version": 1,
  "mode": "enforce",
  "allow": ["cost", "irreversible", "human-action", "legal"],
  "cost": {"threshold_usd": 0},
  "extra": [
    {"name": "customer-contact", "description": "顧客の担当者へ連絡するかどうか"}
  ]
}
```

| 項目 | 無いとき | 意味 |
| --- | --- | --- |
| `version` | 読めない扱い | `1` |
| `mode` | `enforce` | `enforce`（止める）/ `advise`（止めずに案内だけ出す）/ `off`（hook を働かせない） |
| `allow` | 4 つすべて | 人へ回してよい組み込みの区分。空配列は「1 つも許さない」。承認ゲートとレッドラインは書かなくても通る。人のいない実行には当てない（「人のいない実行」） |
| `cost.threshold_usd` | `0` | これ以下の費用は AI が決める（hook は額を比べない） |
| `extra` | 無し | プロジェクトが足す区分。`name` は小文字・数字・`-` で、組み込みの名前と `redline` に重ねない |

- ファイルが無いリポジトリでも `enforce` で働く。止めたくないリポジトリは `"mode": "off"` を書く
- 1 か所でも形が誤っていれば設定全体を既定（`enforce`・4 区分・しきい値 `0`）で扱い、誤った箇所を止めた理由と案内に出す
- 保存先は、作業ディレクトリから親へ辿って `.git` を持つ最初のディレクトリの `.ndf/ask.json`（worktree では worktree の中）

## ランタイムごとの扱い

読み手役の記録を調べて質問を止める hook は Claude Code だけで働く。ほかのランタイムでは、承認の前に `ndf records reading check` を打って調べる（[approval-request.md の「読み手役の確認」](approval-request.md#読み手役の確認)）。区分に当たらない質問は、どのランタイムの hook も止めない。この文書の規則（区分に当たらない質問は出さず、決めて報告に書く）で守る。区分に当たる質問は本文か各ランタイムの問い合わせの Tool で出し、区分の名前を質問の先頭に書く。確かめた結果は `docs/ndf-plugin-reference.md` の hook のセクションにある。
