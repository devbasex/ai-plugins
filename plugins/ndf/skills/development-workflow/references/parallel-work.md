# 並行開発への対応と、任せるうえでの下限

**複数の課題をまとめて渡されることがある。** マイルストーンの単位で「この 22 件を進めて
ほしい」と渡されると、課題と Pull Request は 1 対 1 にならない。

**分割の粒度・束ね方・並行度は担当の判断に任せる。** 4 つの形すべてに手法の規約を書くと、
書いた規約の数だけ判断が増える。分割の粒度も束ね方も、触るファイルの重なり・依存の順序・
レビューの読みやすさで決まるもので、**その場で見えている情報のほうが多い**。

**任せることと、何をしてもよいことは別である。** 代わりに下限を定める。v10.5.0 で
`standard` の 3 件が `light` の進め方で通ったのは、束ね方が悪かったからではなく、
**束ねた後にモードを見直す下限が無かった**ためである。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| ミッション | 1 つの版として出す課題の束。マイルストーンの中から切り出す（マイルストーンは着手の順序の入れ物で、ミッションとは別） |
| 単位 | その工程が 1 回動く対象。課題・Pull Request・ミッションの 3 つがある |
| 下限 | 手法を任せたうえで、それでも守る規則 |

## ミッションの中の並列の 4 つの形

**工程はミッション単位で 1 回ずつ通し、中の設計と実装を並列にする。** ブランチはミッションのブランチ
（`mission/<名前>`）を develop から切り、課題ごとの作業ツリーはそのブランチから切る。課題の
Pull Request はミッションのブランチ宛てに出して集め、develop への Pull Request はミッションで 1 本にする。

| 形 | 例 | 並列の置き方 |
| --- | --- | --- |
| 1 : 1 | 課題 1 件のミッション | 設計・実装とも 1 本。ミッションのブランチを経ず、課題のブランチから develop 宛てに出してよい |
| 1 : N | 大きな課題の設計を 2 本に分ける | 設計 Pull Request を同時に開いて並列で回し、関門 1 で 1 回にまとめる |
| N : 1 | 触るファイルが重なる 3 件を 1 つの作業ツリーで直す | 3 件を 1 本の課題の Pull Request へ束ね、ミッションのブランチへ集める |
| N : M | ミッションの課題を設計 M 本・実装 N 本へ組み替える | 設計は M 本を同時に、実装は課題ごとに同時に回す（どちらも 3 本まで） |

**判定する単位はミッションの develop 宛て Pull Request である。** 単位の決め方そのものは
`SKILL.md` の「判定する単位」にある。

**ミッションの時間は、最も長い 1 本で決まる。** 見込みは「最も長い設計
（上限 3 ラウンド）+ 最も長い実装 + 検査 1 回 + 配布」で、設計や実装の本数を増やしても壁時計は
ほとんど伸びない。**設計を後から足さない。** 足すとその分ミッションが伸びる。

## 工程が動く単位

**工程表の行は、同じ単位では動かない。** 課題ごとに並列で動くものと、ミッションで 1 回のものがある。
`pace: fast`（SKILL.md の「進め方」）で単位が変わる行は、最後の列に書く。空欄は同じ単位である。

| 工程 | 単位 | 理由 | `fast` の単位 |
| --- | --- | --- | --- |
| 要求と受け入れ条件 | ミッション | 1 文書にまとめ、課題ごとの受け入れ条件はその節に置く | |
| 作業場所の用意 | 課題 | 課題ごとに 1 つの作業ツリーを、ミッションのブランチから切る | 課題（develop から切る） |
| 設計 | 設計 Pull Request（並列） | 主題ごとに 1 本。設計文書は 1,000 行以下で、超える主題は 2 本に分ける | |
| 素材の収集と出典の確定 | 設計 Pull Request（並列） | 使う数値と引用は、その Pull Request が載せる文書に対して集める | |
| ドキュメント再構成 | 設計 Pull Request（並列） | 組み直す対象がその Pull Request の設計文書である | |
| ドキュメントレビュー | 設計 Pull Request（並列）。関門 1 はミッションで 1 回 | 設計の `cross-review` は上限 3 ラウンドで関門 1 へ渡す | 設計 Pull Request（並列）。関門 1 は MVV 判定が返した Pull Request だけ |
| 計画 | 課題 | 分解の対象が課題の実装である | |
| 実装 | 課題（並列） | 課題の Pull Request はミッションのブランチ宛てで、実装レビューを通さない | 課題（並列。develop 宛て） |
| 構造改善 | ミッション | ミッションのブランチへ集めた差分に 1 回 | トリガーの範囲（前回の検査からの差分） |
| 実装レビュー | ミッション | `cross-review` はミッションの develop 宛て Pull Request で回る | トリガーの範囲（前回の検査からの差分） |
| 完了判定 | ミッション | 取り込み前の差分に対する証跡である | 課題 |
| Pull Request | 課題（ミッションのブランチ宛て）とミッション（develop 宛て） | develop への Pull Request は 1 本 | 課題（develop 宛て） |
| 確定仕様化 | ミッション | 仕様は課題の境界を越える | ミッションの終わりに 1 回 |
| 後片付け | ミッション | ミッションのマージの後に、課題とミッションのブランチと作業ツリーをまとめて消す | 本番の配布ごと |
| 配布 | ミッション | **課題ごとには版を上げない** | 実装の queue の後（開発版 → 本番） |
| 体裁レビュー | ミッション | 描画して見る対象は、配布（生成）が作った生成物である | |
| リリース後テスト | ミッション | 配布した版に対して行う | 配布ごと |
| 振り返り | ミッション | 進め方の見直しは 1 本では材料が足りない | ミッションの終わりに 1 回 |

## 守る下限

**6 つある。** いずれも v10.5.0 と v10.11.0 の事故か、その予防に当たる。

| # | 下限 | なぜ |
| --- | --- | --- |
| 1 | **モードの違う課題を 1 つのミッションへ混ぜない** | 混ざると、どちらの工程で進めるかが決まらない。混ざるなら高い方のモードで進めるか、ミッションを分ける |
| 2 | **ミッションごとにモードを判定して記録する** | 記録が無いまま実装へ進むと、後から通った工程を照合できない |
| 3 | **判定したモードの必須の工程を飛ばさない** | 飛ばすなら、飛ばした工程と理由を Pull Request の本文へ残す |
| 4 | **依存する工程が終わる前に、それを入力にする工程を始めない** | 依存は工程の対で決まる。B の設計が A の決定を読むなら A の設計の収束を、B の実装が A の実装を前提にするなら A の実装のマージを待つ。**実装の順序の依存は、B の設計を止めない** |
| 5 | **競合を解いた差分を、レビューを通さずにマージしない** | 触る箇所の重なりは「重なりの目安」の範囲で並行してよい。競合を解くとレビューした差分と入る差分が変わるため、**後からマージする側が解き、解いた後の head でレビューを収束させる** |
| 6 | **並行の本数は、測った本数と収束レビューが回る範囲の小さい方に抑える** | `cross-review` は 4 つの CLI を共有する。加えて、担当はそれぞれ CLI・テスト・コンテナを起動し、**ホストのメモリ**を使う。数えるのは作業ツリー 1 つ分の担当で、担当の中で動く補助の実行主体は 1 本に含める。21GiB のホストで 5〜6 本のとき OOM Killer が本体を 2 回落とし、3 本では落ちなかった（#621）。コンテナを起動する検査を持つ担当は同時に 1 本にする |

## 重なりの目安

**節（見出し）の単位で 3 つに分ける。** 行の単位は実装の後にしか分からず、ファイルの単位では
別の関数を触る組まで順になる。

| 区分 | 何が当たるか | 並行 | 待つもの |
| --- | --- | --- | --- |
| 別の節 | 別のファイル、または同じファイルの別の節（見出し）・別の関数 | してよい | なし |
| 足すだけ | 同じ節に行・項目・関数を足すだけで、既存の行を変えない | してよい | なし。競合は後からマージする側が両方を残して解く |
| 書き換え | 同じ節の既存の行を書き換える・移す・消す | **実装はしない** | 先の課題の Pull Request のミッションのブランチへのマージ |

**設計の工程どうしは、どの区分でも並行してよい。** 設計文書は束ごとに別のファイルへ書く。

**区分は設計の後に確定する。** 着手の時点の触る場所は見込みで、設計のレビューが収束した時点で
実行計画が確定の値に置き換える。

## 機械が見るものと、手順として書くもの

**振り分けを書かないと、手順の側にある下限が「機械が見ているはず」と読まれる。**

| # | 下限 | 誰が見るか | どこで |
| --- | --- | --- | --- |
| 1 | モードを混ぜない | **機械** | Pull Request の作成の時点で、閉じる課題の通過記録のモードが揃っているかを見る |
| 2 | モードを判定して記録する | **機械** | 同じ時点で、モードの記録が無いことを案内する |
| 3 | 必須の工程を飛ばさない | **機械** | 同じ時点で、記録の無い必須の工程を案内する |
| 4 | 依存する工程 | 手順 | 実行計画の依存の列。依存の有無は変更の中身が決める |
| 5 | 競合を解いた差分 | 手順 | 後からマージする側の実装レビュー。`cross-review` は head を読むため、解いた後のラウンドが差分を見る |
| 6 | 並行の本数 | **測定は機械、判断は手順** | `parallel-measure.py capacity` が起動してよい本数を出す。起動は拒否しない |

**機械が見るものも拒否はしない。** 案内だけを出す。記録が無いことは、その工程を通って
いないことと同じではない。

## `issue-plan-strategy` との境界

| 問い | 担当 |
| --- | --- |
| **工程の単位**（どの工程がどの単位で動くか、判定と記録の置き場所） | この Skill |
| **分割と並行の手順**（ミッションをどう割り、どの順で走らせ、どう束ね直すか） | `issue-plan-strategy` |
| **実行計画**（置き場所・形・見直す時点・本数の測り方の手順・閉じ方） | `issue-plan-strategy` |

**同じことを 2 箇所へ書かない。** 分割の手順をこちらへ写すと、片方だけが更新される。

## 複数のマイルストーンを渡されたとき

**原則として順次にする。** マイルストーンは配布の単位であり、並行させるとどの版に何が
入るかが確定しない。同時に進めたい理由があるときは、**配布の単位を先に決めてから**割る。

## 承認は関門でまとめる

**どう並行させても、人が見る点は 2 つに固定される。** 関門の定義は `SKILL.md` の
「人手の承認を求める関門」にあり、提示物は
[approval-request.md](approval-request.md) が定める。**並行して走った Pull Request は、
関門でまとめて 1 回の承認へ載せる。**
