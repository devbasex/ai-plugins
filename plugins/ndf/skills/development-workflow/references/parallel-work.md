# 並行開発への対応と、任せるうえでの下限

**複数の課題をまとめて渡されることがある。** マイルストーンの単位で「この 22 件を進めて
ほしい」と渡されると、課題と Pull Request は 1 対 1 にならない。

**分割の粒度・束ね方・並行度は担当の判断に任せる。** 4 つの形すべてに手法の規約を書くと、
書いた規約の数だけ判断が増える。分割の粒度も束ね方も、触るファイルの重なり・依存の順序・
レビューの読みやすさで決まるもので、**その場で見えている情報のほうが多い**。

**任せることと、何をしてもよいことは別である。** 代わりに下限を定める。v10.5.0 で
`standard` の 3 件が `light` の進め方で通ったのは、束ね方が悪かったからではなく、
**束ねた後にモードを見直す下限が無かった**ためである。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| まとまり | 1 回の配布で出す変更の集合。マイルストーンがこれに当たる |
| 単位 | その工程が 1 回動く対象。課題・Pull Request・まとまりの 3 つがある |
| 下限 | 手法を任せたうえで、それでも守る規則 |

## 課題と Pull Request の 4 つの形

| 形 | 例 | 判定と記録 |
| --- | --- | --- |
| 1 : 1 | 1 件の不具合を 1 本で直す | その課題の控えへモードを書く |
| 1 : N | 大きな課題を設計と実装で分ける | **Pull Request ごとに判定する。** 同じ課題の控えは後の判定で上書きされる |
| N : 1 | 触るファイルが重なる 3 件を束ねる | 3 件すべての控えへ同じモードを書く |
| N : M | まとまりを何本かへ組み替える | 上の 2 つの組み合わせ |

**判定する単位は Pull Request である。** 単位の決め方そのものは `SKILL.md` の
「判定する単位」にある。

## 工程が動く単位

**工程表の 15 行は、同じ単位では動かない。** 課題ごとに 1 回のもの、Pull Request ごとに
1 回のもの、まとまりで 1 回のものがある。

| 工程 | 単位 | 理由 |
| --- | --- | --- |
| 要求と受け入れ条件 | 課題 | 何を満たすかは課題が持つ |
| 作業場所の用意 | Pull Request | 1 本につき 1 つの作業ツリー |
| 設計 | Pull Request | 設計文書は Pull Request の中身に対して書く |
| ドキュメント再構成 | Pull Request | 組み直す対象がその Pull Request の設計文書である |
| ドキュメントレビュー | Pull Request | 設計だけを載せた Pull Request を先にマージする |
| 計画 | Pull Request | 分解の対象が Pull Request の中身である |
| 実装 | Pull Request | — |
| 構造改善 | Pull Request | — |
| 実装レビュー | Pull Request | `cross-review` は Pull Request 単位で回る |
| 完了判定 | Pull Request | 取り込み前の差分に対する証跡である |
| Pull Request | Pull Request | — |
| 確定仕様化 | まとまり | 仕様は Pull Request の境界を越える |
| 後片付け | Pull Request | ブランチと作業ツリーは 1 本ごとに残る |
| 配布 | まとまり | **Pull Request ごとには版を上げない** |
| リリース後テスト | まとまり | 配布した版に対して行う |
| 振り返り | まとまり | 進め方の見直しは 1 本では材料が足りない |

## 守る下限

**6 つある。** いずれも v10.5.0 の事故か、その予防に当たる。

| # | 下限 | なぜ |
| --- | --- | --- |
| 1 | **モードの違う課題を 1 本の Pull Request へ混ぜない** | 混ざると、どちらの工程で進めるかが決まらない。混ざるなら高い方のモードで進めるか、Pull Request を分ける |
| 2 | **Pull Request ごとにモードを判定して記録する** | 記録が無いまま実装へ進むと、後から通った工程を照合できない |
| 3 | **判定したモードの必須の工程を飛ばさない** | 飛ばすなら、飛ばした工程と理由を Pull Request の本文へ残す |
| 4 | **依存の順序があるものを並行させない** | 先に出た側の変更を前提にした差分が、レビューの時点で読めない |
| 5 | **同じファイルを触るものを並行させない** | 競合の解消がレビューの後に来ると、レビューした差分と入るものが変わる |
| 6 | **並行の本数は収束レビューが回る範囲に抑える** | `cross-review` は 4 つの CLI を共有する。同時に回すほど 1 本あたりのラウンドが遅くなる |

## 機械が見るものと、手順として書くもの

**振り分けを書かないと、手順の側にある下限が「機械が見ているはず」と読まれる。**

| # | 下限 | 誰が見るか | どこで |
| --- | --- | --- | --- |
| 1 | モードを混ぜない | **機械** | Pull Request の作成の時点で、閉じる課題の控えのモードが揃っているかを見る |
| 2 | モードを判定して記録する | **機械** | 同じ時点で、モードの記録が無いことを案内する |
| 3 | 必須の工程を飛ばさない | **機械** | 同じ時点で、記録の無い必須の工程を案内する |
| 4 | 依存の順序 | 手順 | 依存の有無は変更の中身が決める。差分からは読み取れない |
| 5 | 同じファイル | 手順 | 走らせる前に分かる。走った後では競合として現れる |
| 6 | 並行の本数 | 手順 | 回る範囲はそのときの CLI の状態で変わる |

**機械が見るものも拒否はしない。** 案内だけを出す。記録が無いことは、その工程を通って
いないことと同じではない。

## `issue-plan-strategy` との境界

| 問い | 担当 |
| --- | --- |
| **工程の単位**（どの工程がどの単位で動くか、判定と記録の置き場所） | この Skill |
| **分割と並行の手順**（まとまりをどう割り、どの順で走らせ、どう束ね直すか） | `issue-plan-strategy` |

**同じことを 2 箇所へ書かない。** 分割の手順をこちらへ写すと、片方だけが更新される。

## 複数のマイルストーンを渡されたとき

**原則として順次にする。** マイルストーンは配布の単位であり、並行させるとどの版に何が
入るかが確定しない。同時に進めたい理由があるときは、**配布の単位を先に決めてから**割る。

## 承認は関門でまとめる

**どう並行させても、人が見る点は 2 つに固定される。** 関門の定義は `SKILL.md` の
「人手の承認を求める関門」にあり、提示物は
[approval-request.md](approval-request.md) が定める。**並行して走った Pull Request は、
関門でまとめて 1 回の承認へ載せる。**
