# context window を単位として扱う

**工程の単位は 3 つある**（課題・Pull Request・まとまり）が、そこに **context window は
入っていない**。そのため 1 つの会話でまとまり全体を通せてしまう。長い context window では
判断の質が落ちるため、**工程の記録は残っているのに、後の工程の判断だけが悪くなる**状態が
起きる。

**この文書は切れ目と、委譲の線と、粒度の基準と、残量の見方を定める。** 工程の要否はモードが
決め、この文書はどのモードでも同じように掛かる。**誰が何を持つか**（conductor / supervisor /
worker の 3 層）は [agent-layers.md](agent-layers.md) が持つ。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| context window | 1 回の会話が保持する文脈の全体と、その量。捨てると前の内容は残らない |
| 切る | context window を捨てて新しい会話で続けること。要約して詰め直すこととは別である |
| 委譲 | 別の文脈（サブエージェント・別の CLI プロセス）へ作業を渡し、**結果だけ**を受け取ること |
| 残量 | context window の上限から、いま使っている分を引いたもの |
| 固定費 | 作業を始める前に既に埋まっている分（指示・規約・道具の定義）。**上の層が読む前から掛かる** |
| 実作業 | 最大充填から固定費を引いた分。その会話が実際に読み書きした量 |

## モデルに依る目安と、リポジトリに依る固定費

**2 つは別の量であり、別の理由で変わる。** 混ぜると、モデルを替えたときにリポジトリ側の
値まで書き換えることになる。

| 量 | 何で決まるか | どこに書くか |
| --- | --- | --- |
| **劣化が始まる長さの目安** | **モデルに依る。** 版が上がると変わる | この文書の「切れ目で切る」。`skill-stats --window-limit` の既定が同じ値を持つ |
| **固定費** | **リポジトリに依る。** 指示書・規約・導入した Skill と道具の数で変わる | **どこにも書かない。** 導入した先で測る（`skill-stats --agents`） |

**固定費の値を規約へ書かない。** 書くと、別のリポジトリで読んだ人がその値を自分の環境の
値だと読む。規約が持つのは**比**であって、量ではない。

## context window は工程の切れ目で切る

**目安は 1 工程あたり 10 万トークンで、遅くとも 20 万で切る。** モデルが持つ上限まで
詰めない。

**前提: この数値は公開された評価の設定と第三者のベンチマークからの推定であり、この
リポジトリでの実測ではない。** 実測が出た時点で書き換える。根拠は「出典」にある。

**要約して詰め直すより、切って入り直すほうを既定にする。** 要約は落ちた情報を残さない
ため、**落ちたことに気づけない**。工程の状態は会話の外にあり（課題の本文・盤面・通過工程の
控え・Pull Request の差分）、**捨てても復元できる**。復元の手順を持つのは各工程の
Skill であって、この文書ではない。

### 切ってよい点は 4 つある

| # | 切れ目 | なぜここか |
| --- | --- | --- |
| 1 | ドキュメントレビューのマージの後 | **すでに工程が切れている。** 設計のブランチと作業ツリーは消え、実装用に作り直す |
| 2 | 構造改善と実装レビューの前後 | 回すのは別の CLI プロセスで、**上の層は結果のファイルだけを読む**。載っているものが次の工程の入力にならない |
| 3 | Pull Request を出した後 | ここから先（確定仕様化・後片付け・配布）は単位が変わる。**材料は課題と Pull Request の側にある** |
| 4 | 配布の後 | リリース後テストと振り返りはまとまりの単位で、対象は配布した版である |

**この 4 点は上限ではなく初期値である。** 測った結果で束ねも割りもする（次の節）。
3 層で通すときは、この切れ目が supervisor の持ち場の境になる（[agent-layers.md](agent-layers.md)）。

### 切らない点

**1 つの context window で通す。** 前の工程の出力が、そのまま次の判断の入力になるためである。

| 通す範囲 | なぜ切らないか |
| --- | --- |
| 要求と受け入れ条件 → モード判定 → 作業場所の用意 | **判定の入力が同じ会話の中にある。** 切ると、何を触るかを読み直してから判定することになる |
| 1 本の Pull Request の実装 | 差分の連続性が要る。**途中で切ると、直前に何を直したかを差分から読み直す** |

**切れ目でないところで尽きたときは、尽きた側に合わせる。** 残量が足りないまま次の
工程へ入るより、進行を記録して切るほうが安い。

## 粒度は比で決める

**基準は値ではなく比である。** 固定費はリポジトリとモデルで変わるため、閾値を書くと
導入した先で意味を失う。

**基準を当てるのは supervisor の持ち場である。**

| 測った結果 | どうするか |
| --- | --- |
| その supervisor の**実作業が固定費を上回る** | 単独の持ち場のままにする |
| 実作業が固定費を下回る | **隣の持ち場と束ねる。** 固定費を 2 度払って読む量が増えていない |
| 最大充填がモデルに依る目安を超える | 持ち場を割る |

**判定は記録ごとの比で行う。** 別の会話の中央値どうしを比べない。固定費は設定で変わるため、
どの記録の比でもない値で判断することになる。

**worker にはこの基準を当てない。** worker は使い捨ての読解であり、返す量が小さいことが
目的であるから、実作業が固定費を下回ってよい。代わりに、**1 つの持ち場について
supervisor と配下の worker の固定費の合計が、その supervisor の実作業を上回ったら
「使いすぎ」と見る**。読む量に対して費用のほうが大きくなった状態である。

測り方は `/ndf:skill-stats --agents` が持つ。

## 委譲する対象と、しない対象

**委譲は context window を節約する唯一の手段ではないが、最も効く手段である。**
サブエージェントは別の文脈を持ち、別の CLI プロセスなら**上の層の context window を
1 トークンも消費しない**。

| 委譲してよい | 委譲しない |
| --- | --- |
| 探索（どのファイルにあるか） | **モード判定**（基準を持つ Skill は 1 つである） |
| 全文の読解と、そこからの要点の取り出し | **人手の承認を求める関門の判断**（取り消せない操作である） |
| テストの出力・ログ・差分の集計 | **収束の判定**（測れないことを 0 件として扱わないため） |
| 指摘の修正 | 設計の決定と、その理由の記録 |
| 範囲外の課題の下調べ | 受け入れ条件の書き換え |

**修正の委譲を必須と定めるのは実装レビューの側である。** 同じ規則をここへ写さない。

### 返させる形を決める

**自由文の要約を受け取らない。** 受け取ると、上の層は**要約の要約**を読むことになり、落ちた
情報が二重に落ちる。返させるのは、**項目と場所と根拠を持つ構造化された結果**である。
置き場所をファイルにすれば、context window に載せずに読み直せる。

### 数を増やすことは対策にならない

**4 本の委譲の報告を上の層が読めば、その context window は同じだけ埋まる。** 効くのは、
読んだ量に対して返す量が小さいときだけである。**読む量が変わらない委譲は、費用だけを
増やす。**

並行の本数の下限は [parallel-work.md](parallel-work.md) が持つ。**context window の観点でも
同じ下限が効く**（上の層が読む結果の本数が増える）。

## 残量は外から見る

**残量を自分で把握できるかは、モデルによって違う。** 把握できない側では、**使い切り
かけていることに気づけない**。気づけない前提で運用する。

- **工程の切れ目で残量を見る。** 切れ目でしか見ないのは、途中で見ても切れないためである
- **自動の要約が働く閾値を持つ実行環境では、既定より早める。** 既定は限界に近い側へ
  置かれていることがあり、そこまで待つと判断の質が落ちた後になる。**遅らせる方向には
  効かない設定もある**ため、変えられるのは早める側だと考えて扱う
- **推論の記録が履歴に残る実行環境では、それも量を食う。** 消す手段があるなら、長い工程で
  使う

## 出典

**外部の値を書くときは出典を添える。** 添えないと、次に読む人が現行の値か古い値かを
判定できない。

| 何を根拠にしたか | 出典 |
| --- | --- |
| トークン数が増えるほど精度と再現率が落ちること | モデル提供者の公式ドキュメントの「コンテキストウィンドウ」の節 |
| 100 万トークンに対し 20 万で要約を発火させた評価 | モデル提供者が公開したシステムカードの、web 探索の評価の節 |
| 要約より新しい文脈を選ぶ助言 | モデル提供者の公式ドキュメントの「プロンプトの実践」の節 |
| 残量の自己認識を持つモデルが限られること | 同上の「コンテキストの自己認識」の節 |
| 入力長に対する劣化が全モデルで単調であること | 第三者が 18 モデルを比べた公開の研究 |

**値そのものを写さない。** 版が変わると数字が変わり、写した側だけが古くなる。この文書が
持つのは**運用の目安**であって、モデルの性能値ではない。
