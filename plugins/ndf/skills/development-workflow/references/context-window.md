# context window を単位として扱う

**工程はスプリント単位で 1 回ずつ通し、中の設計と実装は課題ごとに並列に回す**が、その単位に
**context window は入っていない**。そのため 1 つの会話でスプリント全体を通せてしまう。長い context window では
判断の質が落ちるため、**工程の記録は残っているのに、後の工程の判断だけが悪くなる**状態が
起きる。

**この文書はカットポイントと、委譲の線と、粒度の基準と、残量の見方を定める。** 工程の要否はモードが
決め、この文書はどのモードでも同じように掛かる。**誰が何を持つか**（conductor / supervisor /
worker の 3 層）は [agent-layers.md](agent-layers.md) が持つ。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| context window | 1 回の会話が保持する文脈の全体と、その量。捨てると前の内容は残らない |
| 切る | context window を捨てて新しい会話で続けること。要約して詰め直すこととは別である |
| 委譲 | 別の文脈（サブエージェント・別の CLI プロセス）へ作業を渡し、**結果だけ**を受け取ること |
| 残量 | context window の上限から、いま使っている分を引いたもの |
| 固定費 | 作業を始める前に既に埋まっている分（指示・規約・Tool の定義）。**上の層が読む前から掛かる** |
| 実作業 | ピーク使用量から固定費を引いた分。その会話が実際に読み書きした量 |

## モデルに依る目安と、リポジトリに依る固定費

**2 つは別の量であり、別の理由で変わる。** 混ぜると、モデルを替えたときにリポジトリ側の
値まで書き換えることになる。

| 量 | 何で決まるか | どこに書くか |
| --- | --- | --- |
| **劣化が始まる長さの目安** | **モデルに依る。** バージョンが上がると変わる | この文書の「カットポイントで切る」と「再起動の方針」。`skill-stats` の「割る候補」は記録に残った方針の運用上限を使う |
| **固定費** | **リポジトリに依る。** 指示書・規約・導入した Skill と Tool の数で変わる | **どこにも書かない。** 導入した先で測る（`skill-stats --agents`） |

**固定費の値を規約へ書かない。** 書くと、別のリポジトリで読んだ人がその値を自分の環境の
値だと読む。規約が持つのは**比**であって、量ではない。

## context window はカットポイントで切る

**目安は 1 工程あたり 10 万トークンである。** モデルが持つ上限まで詰めない。切る点は 4 つのカットポイントで
（「再起動の方針」）、カットポイントの前に量だけで切らない。量で止めるのは運用上限を超えたときの hook である。

**目安は実測で守られていなかった**（#827。会話の記録から conductor のコンテキスト量を数えた。次の表の 20 万は
集計の基準であって、切る条件ではない）。

| 範囲 | conductor の文脈 | 20 万を超えた会話 | 工程の開始ごとに切ったときの再読込の削減見込み |
| --- | --- | --- | --- |
| 2026-09-20 以降の全プロジェクト | 最大 68 万 | 7 件中 4 件 | 58% |
| NDF のリポジトリの 30 日間 | 平均 41 万 | 45 件中 37 件 | 62% |

目安の値そのものは、公開された評価の設定と第三者のベンチマークからの推定である（「出典」）。
**書いた規定だけでは守られないため、上限を超えたら hook が止める**（次のセクション）。

**要約して詰め直すより、切って入り直すほうを既定にする。** 要約は落ちた情報を残さない
ため、**落ちたことに気づけない**。工程の状態は会話の外にあり（課題の本文・ボード・通過記録・
Pull Request の差分）、**捨てても復元できる**。新しい会話で戻す手順は、この文書の
「新しい会話で戻す」セクションが持つ。

### 切ってよい点は 4 つある

| # | カットポイント | なぜここか |
| --- | --- | --- |
| 1 | ドキュメントレビューのマージの後 | **すでに工程が切れている。** スプリントの設計 Pull Request を設計承認ゲートでまとめてマージし、設計のブランチと worktree は消え、実装用にスプリントブランチから作り直す |
| 2 | リファクタリングとコードレビューの前後（課題の実装がスプリントブランチへ集まった後） | 回すのは別の CLI プロセスで、**上の層は結果のファイルだけを読む**。載っているものが次の工程の入力にならない |
| 3 | スプリントの Pull Request を出した後 | ここから先（確定仕様化・クリーンアップ・リリース）はリリースするバージョンを扱う。**材料は課題と Pull Request の側にある** |
| 4 | マージのフェーズを終えた後（本番へのリリースの前。本番へのリリースが要らないリポジトリではリリースの後） | 再開後に扱うバージョンはリリースの形で 1 つに決まる。**開発版をリリースするリポジトリでは**、本番へのリリース・リリース後テスト・振り返りの対象は、マージのフェーズで出来上がったバージョンである。**正式版だけをリリースするリポジトリでは、切る時点で正式版のバージョンはまだ決まっていない。** マージのフェーズはスプリントの Pull Request のマージとクリーンアップで終わり、バージョンはその後のバージョンを上げる Pull Request で決まるためである。この場合の対象は、再開後の仕上げのリリース作業でバージョンを上げる Pull Request が決めたバージョンであり、リリース後テストと振り返りはそのバージョンを対象にする。**本番へのリリースが要らないリポジトリでは**、マージのフェーズでリリースまで済ませてから切るので、再開後のリリース後テストと振り返りの対象は、そのフェーズでリリースを済ませたバージョンである。移る条件は [agent-layers.md](agent-layers.md) のフェーズの表のマージの終わりの条件（正式版だけをリリースするリポジトリではクリーンアップまで） |

**この 4 点は初期値である。** 測った結果で合わせも割りもする（次のセクション）。
4 点で必ず切る（「再起動の方針」）。
3 層で通すときは、このカットポイントが supervisor のフェーズの境になる（[agent-layers.md](agent-layers.md)）。

### フェーズの中のスイッチポイント

**4 つのカットポイントのほかに、フェーズの中で supervisor を替える点（スイッチポイント）が 1 つある。** 収束ループ
（リファクタリング・コードレビュー・ドキュメントレビュー）の前である。フェーズの境にはならず、
フェーズの語彙も `description` も変わらない。

収束ループは待ちを必ず含み、`cross-review` は背景で起動した待ちの完了の通知を受けて呼び直す。
サブエージェントのキャッシュの寿命は既定で 5 分なので、寿命 5 分の supervisor が長い文脈のまま
待つと、待ちの後の呼び出しのたびに文脈の全体を書き込みの単価（入力の 1.25 倍）で書き直す。
スイッチポイントで替えると、寿命 1 時間の supervisor（`ndf:supervisor-waits`）が前提から始め、待ちの後は読み込み
（0.05 倍）で済む。

| 項目 | 値 |
| --- | --- |
| 替える相手 | 寿命 5 分の supervisor（`ndf:supervisor`）だけ。寿命 1 時間の supervisor は替えない（待ちの後が読み込みで済み、前提を書き直す分を取り返せない） |
| 替える条件 | 今の文脈 C が、その supervisor の最初の呼び出しの文脈 P の 1.5 倍以上 |
| 決める側 | hook（guard `context-limit`）。supervisor は自分から替えない（[agent-layers.md](agent-layers.md) の規則 12） |
| 比を変える | `NDF_SUPERVISOR_CUT_RATIO`（既定 1.5）。`NDF_SUPERVISOR_CUT_GUARD=0` で止めない |

**比は、続けた費用と替えた費用の損得から出す。** 待ち 1 回と後の k 回の呼び出しで比べると、
続けた費用は 1.25C + 0.05kC、替えた費用は 2P + R + 0.05(k + 1)P である（R は前の報告を読む量）。
k = 10 で C > 1.46P + 0.57R となり、R を P の約 1 割と見て 1.5 に丸めた。固定費の絶対値は
リポジトリとバージョンで変わるので、P との比で書く。

hook の無いランタイムにスイッチポイントは無い。Codex / Kiro / agy に 3 層の起動は無い。

### supervisor の定義を選ぶ

**このセクションは supervisor で回すフェーズにだけ当たる。** 設計・実装・検査・リリースはプランで流すのが既定で、
`subagent_type` を選ばない（[agent-layers.md](agent-layers.md) の「プランで流すか supervisor で回すか」）。

**`subagent_type` は、その supervisor が最初に通す工程で決める。** 2 つの定義は本文が同じで、
キャッシュの寿命だけが違う（`plugins/ndf/agents/supervisor.md` と `supervisor-waits.md`）。

| 最初に通す工程 | `subagent_type` | 当たる起動 |
| --- | --- | --- |
| リファクタリング・コードレビュー・ドキュメントレビュー（収束ループ） | `ndf:supervisor-waits`（寿命 1 時間） | 検査の起動、`結果: スイッチポイント` の後の設計・検査の起動 |
| それ以外 | `ndf:supervisor`（寿命 5 分） | プランのテンプレートが無い工程（要求と受け入れ条件・確定仕様化・振り返りなど）の起動 |

- モードで検査がリファクタリングを含まない（`documentation` / `light`）ときも、検査の最初の工程はコードレビューなので `ndf:supervisor-waits` にする
- 1 時間の寿命は、待ちの後の書き直しを読み込みに変えるぶんが、書き込みの割増し（5 分の 1.25 倍に対して 2 倍）を上回る supervisor にだけ使う。収束ループは待ちを必ず含むので上回る。待たない supervisor に使うと損になる
- **定義が使えないときは `subagent_type` を省く**（`general-purpose`）。起動の前に、自分の会話の「使えるエージェントの一覧」に `ndf:supervisor` があるかを見る。無ければ省いて起動する。一覧にあっても `Agent` が知らない `subagent_type` で失敗したら、同じ起動を `subagent_type` を省いて 1 度だけやり直す。省いて起動した supervisor は替えずに最後まで通す（hook は定義の名前が `ndf:supervisor` のときだけ判定する）

### 切らない点

**1 つの context window で通す。** 前の工程の出力が、そのまま次の判断の入力になるためである。

| 通す範囲 | なぜ切らないか |
| --- | --- |
| 要求と受け入れ条件 → モード判定 → 作業場所の用意 | **判定の入力が同じ会話の中にある。** 切ると、何を触るかを読み直してから判定することになる |
| 1 つの課題の実装 | 差分の連続性が要る。**途中で切ると、直前に何を直したかを差分から読み直す** |

**カットポイントでないところで尽きたときは、尽きた側に合わせる。** 残量が足りないまま次の
工程へ入るより、進行を記録して切るほうが安い。

## 上限を超えたら hook が止める

**Claude Code では、文脈が上限を超えたら hook が Tool の呼び出しを止める**（guard `context-limit`。
`contracts/hooks/guards.json` の `PreToolUse` で、Tool を問わない）。止めるのは文脈が運用上限（上限の設定
`contracts/limits.json` の `context.limit`。既定 **500,000** トークン）以上のときである。環境変数 `NDF_CONTEXT_LIMIT` で変えられる。

- **コンテキスト量は、会話の記録の最後の assistant 呼び出しの `usage` から読む**
  （`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`）。読めなければ止めない
- **工程の起動に限らず、すべての Tool を止める。** 通すのは `Read` / `Write` / `Edit` のうち、`file_path` の文字列が
  `.ndf/handoff/` を含む呼び出しだけである（Claude Code は、その会話でまだ読んでいない既存のファイルへの `Write` / `Edit` を
  拒むため、引継ぎ文書の `Read` も通す）。`Read` は、`..` とシンボリックリンクを解いた読み取り先がメインディレクトリの
  `.ndf/handoff/` の直下のときだけ通す。**`Write` / `Edit` は今は文字列を含むかだけを見て、実際の書き込み先を確かめない**
  （`..` やシンボリックリンクで引継ぎディレクトリの外を指すパスも通る）。`Write` / `Edit` を実際の書き込み先で照らす判定は、詳細設計で #3995 の
  後の単位に予定している（`issues/issue-3995-design-detail.md` の `_in_handoff`）。それまでは、引継ぎ文書をメインディレクトリの
  `.ndf/handoff/<名>.md` へ、`..` もリンクも含まないパスで書く。`Bash`・`TaskStop`・引継ぎ文書でない `Read` は止まる。同じ起動をやり直しても判定は変わらない
- **同じ拒否は利用者の入力ごとに 2 回まで返し、3 回目からは案内へ下がって通る**（上限の設定の `hook.deny-repeat`）。
  案内へ下がったのを続けてよい合図として扱わない
- **止められた後は、拒否される CLI を起動しない。** `ndf relay notice`・`ndf relay context record`（判定「再起動」もマーカー
  「引継ぎ開始」も）・`TaskStop` を打たない。カットポイントで自分で切るとき（次の「判定と再起動を記録する」と `SKILL.md` の
  「出す前に行うこと」）と違い、この再起動は記録に残らない
- **動いている supervisor とプランは止めない。** ブロックを出す前に、背景の作業が残っていないかを見る
  （ラッパーの Stop hook は背景の作業が残っていると切り替えない。次のセクション）
  - supervisor や `ndf plan queue` が動いていれば、Tool を呼ばずに応答を終え、その完了通知を受けてからブロックを出す
  - 止めてよい監視（`ndf lanes wait`・Monitor）が残っていても、`TaskStop` は止められるので打てない。上限時間のある監視は
    その完了通知を待ってからブロックを出す。上限時間が無いか待てないときは、自動では切り替わらない。応答で残っている
    task id を挙げ、利用者に止めてもらう（止まった後にブロックを出し直す）か、ラッパーの外と同じく人がブロックの中身を新しい会話へ
    貼り付けて続けると書く
- **ラッパーの内外とも、同じ順で終える。** 上の背景の作業の確かめの後、引継ぎ文書（「現在地」と「次にやること」と
  「次に実行するコマンド」）を `.ndf/handoff/` の下へ `Write` で書くか `Edit` で更新し、**保存してから**応答の最後に次のコマンドの
  ブロック（次のセクション）を書いて応答を終える。既存の文書をこの会話でまだ読んでいなければ、更新の前に `Read` で読む
  （`Read` を省くと `Write` / `Edit` が拒否される）。ブロックと文書の「次に実行するコマンド」には、保存した文書のパスを含む同じ
  再開コマンドを書く（次のセクションの「文書を保存したとき」）。ブロックが指す引継ぎ文書は、この保存で今の状態になる。ブロックを先に出すと、ラッパーが切り替えた先の
  会話は古い「次にやること」を読むか、指す文書を見つけられない。**この経路では `ndf records handoff check` を打たない**
  （`Bash` が拒否される）
  - **保存できなかったとき**（`Read` / `Write` / `Edit` が拒否された・失敗した・文書の名が決まらない）は、ブロックを出さない。
    応答で、引継ぎ文書を保存できなかったことと、拒否・失敗の理由（Tool の返した文面）を利用者に伝えて終える。ブロックを出すと、
    ラッパーの下では古い文書か文書なしで自動で再開してしまう（[handoff.md](handoff.md) の「文書を作れない・書けないとき」と同じ）
  - ラッパー（[relay.md](relay.md)）の下では、ラッパーが新しいセッションで続ける
  - ラッパーの外では、利用者が新しい会話へブロックの中身を貼り付けて続ける（アナウンスの書き方は次のセクション）
- サブエージェントの中の呼び出しを外す判定は、まだ入っていない（#3995 の後の単位で足す）

Codex / Kiro / agy には hook を置かない。4 つのカットポイントで 1 行を出す規約だけで守る
（[waiting.md](waiting.md) の「hook」セクションの表）。

## 再起動の方針

**方針は 1 つで、工程の切れ目（4 つのカットポイント）ごとに `ndf-next` を出して切る。** hook は文脈が運用上限
以上なら次の工程を止める（上の「上限を超えたら hook が止める」）。モデル名や窓の大きさで切り方が変わることは無い。

| 値 | 上限の設定の名前 | 既定 | 今の働き |
| --- | --- | --- | --- |
| 運用上限 | `context.limit` | 500,000 | 文脈がこれ以上なら hook が次の工程を止める。`NDF_CONTEXT_LIMIT`（正の整数）で替えられる |
| 判断開始の値 | `context.decide-from` | 250,000 | `ndf relay context resolve` と判定の記録に出る。運用上限を上回れば運用上限と同じ値へ下げる |

正の整数でない `NDF_CONTEXT_LIMIT` は無視して既定で動き、`resolve` の出所の `ignored` に変数名だけを出す。

**方針を選ぶ設定は廃止した（#3995）。** 試行方式（`trial`）と、それを選ぶ `.ndf/context.json`・環境変数
`NDF_CONTEXT_POLICY` は読まれず、置いても効かない。

**旧い設定からの移り方。** 旧い設定を消す前に、旧い解決器で実際に効いていた方針と運用上限を確かめてから値を移す。
ファイルに値があるだけでは、その値が効いていたとは限らない。

1. **更新する前に**、旧い版の `ndf relay context resolve` を打ち、結果の `policy`・`limit`・`sources` を控える。
   更新した後なら、プラグインのキャッシュに旧い版が残っていれば、その版の `bin/ndf` で同じリポジトリから
   `ndf relay context resolve` を打つのが確実である（`~/.claude/plugins/cache/<マーケットプレイス>/ndf/<更新前の版>/bin/ndf relay context resolve`）。
   残っていなくて手で読み直すときは、まず `.ndf/context.json` の全体を
   次の条件で検める。1 つでも外れれば旧い解決器はファイル全体を無効として捨てていた。
   - JSON のオブジェクトとして読める
   - `version` が無いか 1
   - `policy` が無いか `current` / `trial`
   - `trial` が無いかオブジェクトで、`trial.decide_from`（無ければ 200,000）と `trial.limit`（無ければ 400,000）が
     どちらも正の整数で、`trial.decide_from` が `trial.limit` 以下（例: `trial.limit` が 100000 で `trial.decide_from` を
     省くと、既定の 200,000 が上回るので無効）
   - `margin` が無いか 0 以上の整数

   方針は `NDF_CONTEXT_POLICY`（`current` か `trial` のとき）→ 有効なファイルの `policy` → `current` の順で最初に決まったもの。
   運用上限は、`NDF_CONTEXT_LIMIT` が正の整数ならその値、そうでなければ方針が `current` なら 200,000、`trial` なら有効な
   ファイルの `trial.limit`（無ければ 400,000）。**ファイルが無効なら、`NDF_CONTEXT_POLICY=trial` で `trial` が選ばれていても
   `trial.limit` の値は使われず、既定の 400,000 が効いていた。** **方針が `current` のときは `trial.limit` を使っていなかった**
2. `NDF_CONTEXT_LIMIT` が正の整数（1 の出所が `env`）なら、旧い版でもそれが効いていた。値を変えずに 3 へ進む
3. `NDF_CONTEXT_LIMIT` が正の整数でない（未設定・空文字・`0`・数字でない）ときは、旧い版でも新しい版でも無視される。
   1 で読んだ方針が `trial` なら、その運用上限を `NDF_CONTEXT_LIMIT` に入れる（無効な値はこの値で置き換える）。`current` なら、
   既定の 500,000 で動かすときは無効な値を外し、旧い 200,000 で止め続けたいときだけ 200,000 を入れる
4. `ndf relay context resolve` で、効いている 2 つの値と値ごとの出所（`default` か `env`）を確かめ、出所に `ignored` が無いことも見る
5. 確かめた後で `.ndf/context.json` を消し（コミットしていればその削除もコミットする）、環境変数 `NDF_CONTEXT_POLICY` を外す

**カットポイントの外でも conductor が自分で切ってよい理由は 2 つある。** 独立した視点が要るレビューを親の文脈ごと
新しくしたいとき（独立性）と、利用者が切ると決めたとき（手動）である。切るときは
`ndf relay context record --verdict 再起動 --reason 独立性 --work <作業の識別子>`（か `--reason 手動`）で記録し、引継ぎ文書の `ndf-next` のブロックを出す。

**切るときに守ること。** 承認ゲートの前に `ndf-next` を出さない。動いているプランと supervisor を
止めずに報告を待ってから引継ぎ文書を作る。新しいセッションは引継ぎ文書から状態を確かめ直す。承認待ちと
質問待ちは引継ぎ文書に保留として残す。supervisor のスイッチポイントと、サブエージェントの中で hook が
判定しないことも変わらない。

**再起動の理由は 7 つである。** 容量・運用上限・費用（hook が数える）、独立性・手動（conductor が決める）、
カットポイント、待ち（並列の計画のオーガナイザーが長い待ちの前に切り替える。
判定は `ndf lanes wait` が出す。[parallel.md](parallel.md) の「長い待ちの状況報告と切り替え」）。

### 判定と再起動を記録する

記録は状態ディレクトリ（`NDF_CONTEXT_DIR` → `${XDG_STATE_HOME}/ndf/context` → `~/.local/state/ndf/context`）の
`decisions/<owner>__<repo>.decisions.jsonl` へ追記する。作業の識別子は課題番号の昇順の並び（`#829 #830`）である。
**今の hook（guard `context-limit`）はこのファイルへ何も書かない**（判定の行も、下のマーカーも）。書くのは `ndf relay context record` だけである。
conductor は、カットポイント・独立性・手動で自分で切って `ndf-next` を出すたびに
`ndf relay context record --verdict 再起動 --reason <理由> --work <作業の識別子>` で判定「再起動」を書く。
**hook に止められて `ndf-next` を出すときは打たない**（`Bash` が拒否される。「上限を超えたら hook が止める」）。
`ndf relay context calibrate` は打たない（今の hook は費用の見込みを判定に使わない）。

**マーカー「引継ぎ開始」と「復元完了」は conductor が打つ。** hook は打たない。

| マーカー | conductor が打つ場面 | 打たない場面 |
| --- | --- | --- |
| 引継ぎ開始 | カットポイント・独立性・手動で自分で切るとき。引継ぎ文書を書き始める前に打つ（手順は [relay.md](relay.md) の「カットポイントの引継ぎ文書と ndf-next はスクリプトで作る」） | hook に止められた後（ラッパーの下でも外でも `Bash` が拒否される。その再起動の引継ぎの期間は記録に残らない） |
| 復元完了 | Codex で、再開して状態を確かめ終えた直後 | Claude Code（今は誰も打たないので、`report` の復元の期間と復元の量は「不明」と出る） |

マーカーを書けなくても判定と拒否の文面は変わらない。conductor が打つ形は次のとおりで、
Bash で打つので Codex でも同じに記録できる。`--work` に課題番号を含めば課題番号の昇順の並びに直して書き、含まなければ
同じセッションの前の行の作業の識別子で補う。

```bash
ndf relay context record --event 引継ぎ開始 --work "#829 #830"
ndf relay context record --event 復元完了 --work "#829 #830"   # Codex だけ
```

作業ごとの集計は `ndf relay context report --work "#829 #830"` で見る（結果 JSON の `items` を区分ごとに読む）。区分は conductor・
NDF が起動した分・引継ぎの期間・復元の期間で、同じ呼び出しを 2 つの区分へ数えない。マーカーが無いセグメントと取れない
品質の値は 0 でなく「不明」と出す。セッションごとの
復元の量（「復元完了」の直前の文脈の量）も出す。`--from` と `--until`（ISO 8601 の時刻）を渡すと、その間の呼び出し
（会話・サブエージェント・使用量の使用量ログ）と記録の行だけを数える。1 つのフェーズの費用を、作業の全体から切り出して見るときに使う。

**statusline の色と hook の止める値は意味が違う。** statusline は窓に対して危険な水準
（500K、窓 200K 以下は 150K）を赤で示す表示の警告で、hook の止める運用上限（`context.limit`）とは別の値である。

## 新しい会話で戻す

**conductor は、4 つのカットポイント（と、カットポイントの外で自分で切ると決めたとき）と hook に止められたときに、
次の工程を始めるコマンドを、情報文字列が `ndf-next` のコードブロック 1 つで出す。**

```ndf-next
/goal /ndf:development-workflow #829 #830
```

引継ぎ文書を保存したとき（カットポイントと hook に止められたときは保存してから出す）は、文書のパスを含める。
[handoff.md](handoff.md) の「読む」は、名指しが無いと入力の語と文書の名を照らすので、課題番号だけでは
`milestone-26.md` のような課題以外の名の文書が選ばれない。

```ndf-next
/goal /ndf:development-workflow #829 #830 .ndf/handoff/milestone-26.md の続きから
```

- **ブロックの中身がそのまま次のセッションの最初の入力になる。** 複数行でよい。最後の応答に
  **1 つだけ**置く。2 つ以上置くと、ラッパーは拾わない。説明のために引く例は 4 つのバッククォートの
  フェンスの中へ入れる（外側のフェンスの中は数えない）
- **中身は `development-workflow` を起動する 1 行である**（`/ndf:development-workflow #829 #830`）。
  **文書を保存したときは、そのパスを `.ndf/handoff/<名>.md の続きから` の形で同じ行に含め**、文書の「次に実行するコマンド」にも
  同じ中身を書く（[handoff.md](handoff.md) の「作る・更新する」の 3）。
  工程 Skill はモードと worktree を戻す手順を持たないため、エントリポイントから入り直す。Codex と Kiro では、
  それぞれの README が示す Skill の起動の書き方に読み替える
- **今のセッションを `/goal` で始めていたときだけ、中身の先頭を `/goal ` にする**。次のセッションは作業の最初に、
  条件の先頭の Skill（`/ndf:development-workflow`）を Skill ツールで読み込む（[relay.md](relay.md) の付則「`/goal` を付けた場合」）
- **3 層では、conductor がフェーズレポート（`## フェーズレポート`）を受け取った時点で出す**（supervisor は出さない）。
  フェーズの境がカットポイントに当たるためである。ただし報告が `結果: 承認ゲート` なら、承認ゲートの承認とマージ
  （設計 Pull Request のマージなど）が済んだ後に出す。**承認ゲートの承認より前には出さない。** 出すと、
  ラッパーが承認ゲートの前で会話を切る。カットポイント 1 はこの形で満たす
- **ラッパーがあってもなくても出す。** ラッパー（[relay.md](relay.md)）の下では、ラッパーがブロックを拾って
  次のセッションを自動で起動する。ラッパーが無ければ、人がブロックの中身を新しい会話へ貼り付ける
- **Claude Code では、ブロックの直前のアナウンスを `ndf relay notice` の結果の `summary` で書く**。`summary` を
  言い換えずにそのままコピーする。文面と秒数（アイドルの秒数）は `ndf relay notice` だけが持つ。呼び方は
  `development-workflow` の `SKILL.md` の、カットポイントのアナウンスの段落にある。hook に止められたときは
  `ndf relay notice` も止まるので打たない。拒否文がラッパーの下と告げていればアナウンスを書かずにブロックだけを出し、
  外と告げていればラッパーの外の書き方で書く。`ndf relay notice` を打てないか実行が失敗
  したときは、ラッパーの外として扱い、人がブロックの中身を新しい会話へ貼り付けると書く。Codex / Kiro /
  agy では、今までどおり中身を新しい会話へ貼り付けると書く。**ラッパーの下（`metrics.inside` が真）では、
  手で入力させる文（「次の 1 行を使って」「貼り付けて」）を書かない。** 例外は 2 行目そのものが
  貼り付けの手順を示すとき（`NDF_RELAY_QUIET=inf`）である。ラッパーの外の 2 行目は外である理由
  （ラッパーが無い・終わっている・fork したセッションなど直接の子でない）で変わる（[relay.md](relay.md) の
  「fork したセッションで進めたとき」）
- **バックグラウンドの作業が残っているとラッパーは切り替わらない。** ラッパーの Stop hook はシグナルファイルを書かず、Stop を 1 度だけ
  止めて動いている作業の id とコマンドの先頭を知らせる。監視のように止めてよい作業は `TaskStop <task id>`
  で止め、止まったかは完了通知（`failed` / `killed`）で確かめてからブロックを出し直す。supervisor や
  `ndf plan queue` は止めずに終わりを待ってから出し直す（[waiting.md](waiting.md) の「バックグラウンドの作業を止める」）。
  hook に止められた後は `TaskStop` も拒否されるので打たない。そのときの待ち方と、監視が残ったときの案内は
  「上限を超えたら hook が止める」にある
- **カットポイントの再起動は承認ゲートに数えない。** 引継ぎ文書を更新したら、承認・確認（`AskUserQuestion`
  を含む）を挟まずにアナウンスとブロックを出して応答を終える。状態は課題の本文と Pull Request に残り、
  取り消せるためである。ラッパーの外でも挟まない（確認の回答と貼り付けで入力が 2 度になる）。
  **`/goal` の文面が「承認を求める」と書いていても、指すのは `SKILL.md` の 2 つの承認ゲートだけである**
- **引継ぎ文書の「次に実行するコマンド」のセクションも、同じブロックで書く。** ブロックの形の定義はこのセクションだけに置く。
  引継ぎ文書の保存先・セクションの形・作る／更新する／消す規則は [handoff.md](handoff.md) にある

**新しい会話の `development-workflow` は、次の順で状態を戻す。**

| # | 読むもの | 戻すもの |
| --- | --- | --- |
| 0 | 引継ぎ文書（入力が名指ししたもの。無ければ入力の語に一致する 1 本。見つけ方と一致しないときの扱いは [handoff.md](handoff.md) の「読む」） | 次にやることの 1 つ目。状態は 1〜5 で確かめ、食い違えば 1〜5 を正とする |
| 1 | 課題の本文の `## 進行`（`gh issue view <番号> --json body`） | モード・worktree・計画ファイル・通った工程 |
| 2 | `ndf progress show <ステートマシンの ID>`（ID は `ndf progress new` の結果にある） | 通過記録。本文と食い違えば通過記録を正とする |
| 3 | 1 の worktree（`.worktrees/<ブランチ名>`）のブランチ名で `gh pr list --head <ブランチ名> --state all`。実装の Pull Request は `gh issue view <番号> --json closedByPullRequestsReferences` でも引く | 設計・実装の Pull Request と状態 |
| 4 | 引継ぎ文書の「今の会話の進み」が指す目録（`<out>/sprint.json`。無ければ改名の前の `<out>/mission.json`）の `ステージ` と、ステージごとのキューの done（`wait <done>` の結果）。プランの途中で止まっていれば、その `<プラン>-state/progress.jsonl` の最後のステップ | 終わったステージ・`gate` で止まったステージ・途中のプランとステップ |
| 5 | 1〜4 から、チェックの付いていない最初の必須の工程 | 次に打つコマンド。プランのあるフェーズは次のステージの `command`（途中のプランは `ndf plan next <プラン> --from <ステップの id>`）、テンプレートの無い工程は起動する supervisor |

**Pull Request は番号の全文検索で引かない。** 同じ番号に触れただけの別の Pull Request も返す
ためである。設計の Pull Request は GitHub の closing keywords（PR 本文に `Closes #123` のように書くと、マージ時にその課題を自動で閉じる機能）を持たないため、課題との結び付きでは引けず、
ブランチ名で引く。

## 粒度は比で決める

**基準は値ではなく比である。** 固定費はリポジトリとモデルで変わるため、閾値を書くと
導入した先で意味を失う。

**基準を当てるのは supervisor のフェーズである。**

| 測った結果 | どうするか |
| --- | --- |
| その supervisor の**実作業が固定費を上回る** | 単独のフェーズのままにする |
| 実作業が固定費を下回る | **隣のフェーズと 1 つにする。** 固定費を 2 度払って読む量が増えていない |
| ピーク使用量がモデルに依る目安を超える | フェーズを割る |

**判定は記録ごとの比で行う。** 別の会話の中央値どうしを比べない。固定費は設定で変わるため、
どの記録の比でもない値で判断することになる。

**worker にはこの基準を当てない。** worker は使い捨ての読解であり、返す量が小さいことが
目的であるから、実作業が固定費を下回ってよい。代わりに、**1 つのフェーズについて
supervisor と配下の worker の固定費の合計が、その supervisor の実作業を上回ったら
「使いすぎ」と見る**。読む量に対して費用のほうが大きくなった状態である。

測り方は `/ndf:skill-stats --agents` が持つ。

## 委譲する対象と、しない対象

**委譲は context window を節約する唯一の手段ではないが、最も効く手段である。**
サブエージェントは別の文脈を持ち、別の CLI プロセスなら**上の層の context window を
1 トークンも消費しない**。

| 委譲してよい | 委譲しない |
| --- | --- |
| 探索（どのファイルにあるか） | **モード判定**（基準を持つ Skill は 1 つである） |
| 全文の読解と、そこからの要点の取り出し | **承認ゲートの判断**（取り消せない操作である） |
| テストの出力・ログ・差分の集計 | **収束の判定**（測れないことを 0 件として扱わないため） |
| 指摘の修正 | 設計の決定と、その理由の記録 |
| 範囲外の課題の下調べ | 受け入れ条件の書き換え |

**修正の委譲を必須と定めるのはコードレビューの側である。** 同じ規則をここへコピーしない。

**どの実行方式へ渡すか（インライン実行・サブエージェント・CLI 実行・最小構成の `claude -p`・スクリプト）と、
小さな作業にサブエージェントを起動しない線引きと、新しい文脈で始めるか続けるかを決める費用の式は
[work-vessels.md](work-vessels.md) が持つ。**
ここへコピーしない。

### 返させる形を決める

**自由文の要約を受け取らない。** 受け取ると、上の層は**要約の要約**を読むことになり、落ちた
情報が二重に落ちる。返させるのは、**項目と場所と根拠を持つ構造化された結果**である。
置く場所をファイルにすれば、context window に載せずに読み直せる。

### 数を増やすことは対策にならない

**4 本の委譲の報告を上の層が読めば、その context window は同じだけ埋まる。** 効くのは、
読んだ量に対して返す量が小さいときだけである。**読む量が変わらない委譲は、費用だけを
増やす。**

並行の本数の必須ルールは [parallel-work.md](parallel-work.md) が持つ。**context window の観点でも
同じ必須ルールが効く**（上の層が読む結果の本数が増える）。

## 残量は外から見る

**残量を自分で把握できるかは、モデルによって違う。** 把握できない側では、**使い切り
かけていることに気づけない**。気づけない前提で運用する。

- **カットポイントで残量を見る。** カットポイントでしか見ないのは、途中で見ても切れないためである
- **自動の要約が働く閾値を持つ実行環境では、既定より早める。** 既定は限界に近い側へ
  置かれていることがあり、そこまで待つと判断の質が落ちた後になる。**遅らせる方向には
  効かない設定もある**ため、変えられるのは早める側だと考えて扱う
- **推論の記録が履歴に残る実行環境では、それも量を食う。** 消す手段があるなら、長い工程で
  使う

## 出典

**外部の値を書くときは出典を添える。** 添えないと、次に読む人が現行の値か古い値かを
判定できない。

| 何を根拠にしたか | 出典 |
| --- | --- |
| トークン数が増えるほど精度と再現率が落ちること | モデル提供者の公式ドキュメントの「コンテキストウィンドウ」のセクション |
| 100 万トークンに対し 20 万で要約を発火させた評価 | モデル提供者が公開したシステムカードの、web 探索の評価のセクション |
| 要約より新しい文脈を選ぶ助言 | モデル提供者の公式ドキュメントの「プロンプトの実践」のセクション |
| 残量の自己認識を持つモデルが限られること | 同上の「コンテキストの自己認識」のセクション |
| 入力長に対する劣化が全モデルで単調であること | 第三者が 18 モデルを比べた公開の研究 |
| conductor の最大文脈・20 万を超えた会話の数・再読込の削減見込み | #827（会話の記録からの実測） |

**値そのものをコピーしない。** バージョンが変わると数字が変わり、コピーした側だけが古くなる。この文書が
持つのは**運用の目安**であって、モデルの性能値ではない。
