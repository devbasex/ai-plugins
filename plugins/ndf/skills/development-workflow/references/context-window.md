# コンテキストの窓を単位として扱う

**工程の単位は 3 つある**（課題・Pull Request・まとまり）が、そこに**窓は入っていない**。
そのため 1 つの会話でまとまり全体を通せてしまう。長い窓では判断の質が落ちるため、
**工程の記録は残っているのに、後の工程の判断だけが悪くなる**状態が起きる。

**この文書は窓の切れ目と、委譲の線と、残量の見方を定める。** 工程の要否はモードが決め、
この文書はどのモードでも同じように掛かる。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| 窓 | 1 回の会話が保持する文脈の全体。切ると前の内容は残らない |
| 切る | 窓を捨てて新しい窓で続けること。要約して詰め直すこととは別である |
| 委譲 | 別の文脈（副エージェント・別の CLI プロセス）へ作業を渡し、**結果だけ**を受け取ること |
| 残量 | 窓の上限から、いま使っている分を引いたもの |

## 窓は工程の切れ目で切る

**目安は 1 工程あたり 10 万トークンで、遅くとも 20 万で切る。** モデルが持つ上限まで
詰めない。

**前提: この数値は公開された評価の設定と第三者のベンチマークからの推定であり、この
リポジトリでの実測ではない。** 実測が出た時点で書き換える。根拠は「出典」にある。

**要約して詰め直すより、切って入り直すほうを既定にする。** 要約は落ちた情報を残さない
ため、**落ちたことに気づけない**。工程の状態は会話の外にあり（課題の本文・盤面・通過工程の
控え・Pull Request の差分）、**窓を捨てても復元できる**。復元の手順を持つのは各工程の
Skill であって、この文書ではない。

### 切ってよい点は 4 つある

| # | 切れ目 | なぜここか |
| --- | --- | --- |
| 1 | ドキュメントレビューのマージの後 | **すでに工程が切れている。** 設計のブランチと作業ツリーは消え、実装用に作り直す |
| 2 | 構造改善と実装レビューの前後 | 回すのは別の CLI プロセスで、**親は結果のファイルだけを読む**。窓に載っているものが次の工程の入力にならない |
| 3 | Pull Request を出した後 | ここから先（確定仕様化・後片付け・配布）は単位が変わる。**材料は課題と Pull Request の側にある** |
| 4 | 配布の後 | リリース後テストと振り返りはまとまりの単位で、対象は配布した版である |

### 切らない点

**1 つの窓で通す。** 前の工程の出力が、そのまま次の判断の入力になるためである。

| 通す範囲 | なぜ切らないか |
| --- | --- |
| 要求と受け入れ条件 → モード判定 → 作業場所の用意 | **判定の入力が窓の中にある。** 切ると、何を触るかを読み直してから判定することになる |
| 1 本の Pull Request の実装 | 差分の連続性が要る。**途中で切ると、直前に何を直したかを差分から読み直す** |

**切れ目でないところで窓が尽きたときは、尽きた側に合わせる。** 残量が足りないまま次の
工程へ入るより、進行を記録して切るほうが安い。

## 委譲する対象と、しない対象

**委譲は窓を節約する唯一の手段ではないが、最も効く手段である。** 副エージェントの窓は
親と別であり、別の CLI プロセスなら**親の窓を 1 トークンも消費しない**。

| 委譲してよい | 委譲しない |
| --- | --- |
| 探索（どのファイルにあるか） | **モード判定**（基準を持つ Skill は 1 つである） |
| 全文の読解と、そこからの要点の取り出し | **人手の承認を求める関門の判断**（取り消せない操作である） |
| テストの出力・ログ・差分の集計 | **収束の判定**（測れないことを 0 件として扱わないため） |
| 指摘の修正 | 設計の決定と、その理由の記録 |
| 範囲外の課題の下調べ | 受け入れ条件の書き換え |

**修正の委譲を必須と定めるのは実装レビューの側である。** 同じ規則をここへ写さない。

### 返させる形を決める

**自由文の要約を受け取らない。** 受け取ると、親は**要約の要約**を読むことになり、落ちた
情報が二重に落ちる。返させるのは、**項目と場所と根拠を持つ構造化された結果**である。
置き場所をファイルにすれば、窓に載せずに読み直せる。

### 数を増やすことは対策にならない

**4 本の委譲の報告を親が読めば、親の窓は同じだけ埋まる。** 効くのは、読んだ量に対して
返す量が小さいときだけである。**読む量が変わらない委譲は、費用だけを増やす。**

並行の本数の下限は [parallel-work.md](parallel-work.md) が持つ。**窓の観点でも同じ下限が
効く**（親が読む結果の本数が増える）。

## 残量は外から見る

**残量を自分で把握できるかは、モデルによって違う。** 把握できない側では、**窓を使い切り
かけていることに気づけない**。気づけない前提で運用する。

- **工程の切れ目で残量を見る。** 切れ目でしか見ないのは、途中で見ても切れないためである
- **自動の要約が働く閾値を持つ実行環境では、既定より早める。** 既定は窓の限界に近い側へ
  置かれていることがあり、そこまで待つと判断の質が落ちた後になる。**遅らせる方向には
  効かない設定もある**ため、変えられるのは早める側だと考えて扱う
- **推論の記録が履歴に残る実行環境では、それも窓を食う。** 消す手段があるなら、長い工程で
  使う

## 出典

**外部の値を書くときは出典を添える。** 添えないと、次に読む人が現行の値か古い値かを
判定できない。

| 何を根拠にしたか | 出典 |
| --- | --- |
| トークン数が増えるほど精度と再現率が落ちること | モデル提供者の公式ドキュメントの「コンテキストウィンドウ」の節 |
| 100 万トークンの窓に対し 20 万で要約を発火させた評価 | モデル提供者が公開したシステムカードの、web 探索の評価の節 |
| 要約より新しい窓を選ぶ助言 | モデル提供者の公式ドキュメントの「プロンプトの実践」の節 |
| 残量の自己認識を持つモデルが限られること | 同上の「コンテキストの自己認識」の節 |
| 入力長に対する劣化が全モデルで単調であること | 第三者が 18 モデルを比べた公開の研究 |

**値そのものを写さない。** 版が変わると数字が変わり、写した側だけが古くなる。この文書が
持つのは**運用の目安**であって、モデルの性能値ではない。
