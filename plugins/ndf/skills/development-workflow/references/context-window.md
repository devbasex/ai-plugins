# context window を単位として扱う

**工程はミッション単位で 1 回ずつ通し、中の設計と実装は課題ごとに並列に回す**が、その単位に
**context window は入っていない**。そのため 1 つの会話でミッション全体を通せてしまう。長い context window では
判断の質が落ちるため、**工程の記録は残っているのに、後の工程の判断だけが悪くなる**状態が
起きる。

**この文書は切れ目と、委譲の線と、粒度の基準と、残量の見方を定める。** 工程の要否はモードが
決め、この文書はどのモードでも同じように掛かる。**誰が何を持つか**（conductor / supervisor /
worker の 3 層）は [agent-layers.md](agent-layers.md) が持つ。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| context window | 1 回の会話が保持する文脈の全体と、その量。捨てると前の内容は残らない |
| 切る | context window を捨てて新しい会話で続けること。要約して詰め直すこととは別である |
| 委譲 | 別の文脈（サブエージェント・別の CLI プロセス）へ作業を渡し、**結果だけ**を受け取ること |
| 残量 | context window の上限から、いま使っている分を引いたもの |
| 固定費 | 作業を始める前に既に埋まっている分（指示・規約・Tool の定義）。**上の層が読む前から掛かる** |
| 実作業 | 最大充填から固定費を引いた分。その会話が実際に読み書きした量 |

## モデルに依る目安と、リポジトリに依る固定費

**2 つは別の量であり、別の理由で変わる。** 混ぜると、モデルを替えたときにリポジトリ側の
値まで書き換えることになる。

| 量 | 何で決まるか | どこに書くか |
| --- | --- | --- |
| **劣化が始まる長さの目安** | **モデルに依る。** 版が上がると変わる | この文書の「切れ目で切る」。`skill-stats --window-limit` の既定が同じ値を持つ |
| **固定費** | **リポジトリに依る。** 指示書・規約・導入した Skill と Tool の数で変わる | **どこにも書かない。** 導入した先で測る（`skill-stats --agents`） |

**固定費の値を規約へ書かない。** 書くと、別のリポジトリで読んだ人がその値を自分の環境の
値だと読む。規約が持つのは**比**であって、量ではない。

## context window は工程の切れ目で切る

**目安は 1 工程あたり 10 万トークンで、遅くとも 20 万で切る。** モデルが持つ上限まで
詰めない。

**この上限は実測で守られていなかった**（#827。会話の記録から conductor の文脈量を数えた）。

| 範囲 | conductor の文脈 | 20 万を超えた会話 | 工程の開始ごとに切ったときの再読込の削減見込み |
| --- | --- | --- | --- |
| 2026-09-20 以降の全プロジェクト | 最大 68 万 | 7 件中 4 件 | 58% |
| ai-plugins の 30 日間 | 平均 41 万 | 45 件中 37 件 | 62% |

目安の値そのものは、公開された評価の設定と第三者のベンチマークからの推定である（「出典」）。
**書いた規定だけでは守られないため、上限を超えたら hook が止める**（次の節）。

**要約して詰め直すより、切って入り直すほうを既定にする。** 要約は落ちた情報を残さない
ため、**落ちたことに気づけない**。工程の状態は会話の外にあり（課題の本文・盤面・通過工程の
控え・Pull Request の差分）、**捨てても復元できる**。新しい会話で戻す手順は、この文書の
「新しい会話で戻す」節が持つ。

### 切ってよい点は 4 つある

| # | 切れ目 | なぜここか |
| --- | --- | --- |
| 1 | ドキュメントレビューのマージの後 | **すでに工程が切れている。** ミッションの設計 Pull Request を関門 1 でまとめてマージし、設計のブランチと作業ツリーは消え、実装用にミッションのブランチから作り直す |
| 2 | 構造改善と実装レビューの前後（課題の実装がミッションのブランチへ集まった後） | 回すのは別の CLI プロセスで、**上の層は結果のファイルだけを読む**。載っているものが次の工程の入力にならない |
| 3 | ミッションの Pull Request を出した後 | ここから先（確定仕様化・後片付け・配布）は配布する版を扱う。**材料は課題と Pull Request の側にある** |
| 4 | 配布の後 | リリース後テストと振り返りの対象は、ミッションを配布した版である |

**この 4 点は上限ではなく初期値である。** 測った結果で束ねも割りもする（次の節）。
3 層で通すときは、この切れ目が supervisor のフェーズの境になる（[agent-layers.md](agent-layers.md)）。

### フェーズの中の区切り

**4 つの切れ目のほかに、フェーズの中で supervisor を替える点が 1 つある。** 収束ループ
（構造改善・実装レビュー・ドキュメントレビュー）の前である。フェーズの境にはならず、
フェーズの語彙も `description` も変わらない。

収束ループは待ちを必ず含み、`cross-review` は `bg-wait.sh wait` を 1 回最長 540 秒で呼び直す。
サブエージェントのキャッシュの寿命は既定で 5 分なので、寿命 5 分の supervisor が長い文脈のまま
待つと、待ちの後の呼び出しのたびに文脈の全体を書き込みの単価（入力の 1.25 倍）で書き直す。
区切ると、寿命 1 時間の supervisor（`ndf:supervisor-waits`）が前提から始め、待ちの後は読み込み
（0.05 倍）で済む。

| 項目 | 値 |
| --- | --- |
| 区切る相手 | 寿命 5 分の supervisor（`ndf:supervisor`）だけ。寿命 1 時間の supervisor は区切らない（待ちの後が読み込みで済み、前提を書き直す分を取り返せない） |
| 区切る条件 | 今の文脈 C が、その supervisor の最初の呼び出しの文脈 P の 1.5 倍以上 |
| 決める側 | hook（`token-guard.sh`）。supervisor は自分から区切らない（[agent-layers.md](agent-layers.md) の規則 12） |
| 比を変える | `NDF_SUPERVISOR_CUT_RATIO`（既定 1.5）。`NDF_SUPERVISOR_CUT_GUARD=0` で止めない |

**比は、続けた費用と区切った費用の損得から出す。** 待ち 1 回と後の k 回の呼び出しで比べると、
続けた費用は 1.25C + 0.05kC、区切った費用は 2P + R + 0.05(k + 1)P である（R は前の報告を読む量）。
k = 10 で C > 1.46P + 0.57R となり、R を P の約 1 割と見て 1.5 に丸めた。固定費の絶対値は
リポジトリと版で変わるので、P との比で書く。

hook の無いランタイムでは区切らない。Codex / Kiro / agy に 3 層の起動は無い。

### supervisor の定義を選ぶ

**`subagent_type` は、その supervisor が最初に通す工程で決める。** 2 つの定義は本文が同じで、
キャッシュの寿命だけが違う（`plugins/ndf/agents/supervisor.md` と `supervisor-waits.md`）。

| 最初に通す工程 | `subagent_type` | 当たる起動 |
| --- | --- | --- |
| 構造改善・実装レビュー・ドキュメントレビュー（収束ループ） | `ndf:supervisor-waits`（寿命 1 時間） | 検査の起動、`結果: 区切り` の後の設計・検査の起動 |
| それ以外 | `ndf:supervisor`（寿命 5 分） | 設計・実装・取り込み・仕上げの起動 |

- モードで検査が構造改善を含まない（`documentation` / `light`）ときも、検査の最初の工程は実装レビューなので `ndf:supervisor-waits` にする
- 1 時間の寿命は、待ちの後の書き直しを読み込みに変えるぶんが、書き込みの割増し（5 分の 1.25 倍に対して 2 倍）を上回る区間にだけ使う。収束ループは待ちを必ず含むので上回る。待たない区間に使うと損になる
- **定義が使えないときは `subagent_type` を省く**（`general-purpose`）。起動の前に、自分の会話の「使えるエージェントの一覧」に `ndf:supervisor` があるかを見る。無ければ省いて起動する。一覧にあっても `Agent` が知らない `subagent_type` で失敗したら、同じ起動を `subagent_type` を省いて 1 度だけやり直す。省いて起動した supervisor は区切らずに最後まで通す（hook は定義の名前が `ndf:supervisor` のときだけ判定する）

### 切らない点

**1 つの context window で通す。** 前の工程の出力が、そのまま次の判断の入力になるためである。

| 通す範囲 | なぜ切らないか |
| --- | --- |
| 要求と受け入れ条件 → モード判定 → 作業場所の用意 | **判定の入力が同じ会話の中にある。** 切ると、何を触るかを読み直してから判定することになる |
| 1 つの課題の実装 | 差分の連続性が要る。**途中で切ると、直前に何を直したかを差分から読み直す** |

**切れ目でないところで尽きたときは、尽きた側に合わせる。** 残量が足りないまま次の
工程へ入るより、進行を記録して切るほうが安い。

## 上限を超えたら hook が止める

**Claude Code では、文脈が上限を超えた conductor が工程へ入る起動を hook が 1 度止める**
（`scripts/token-guard.sh`）。上限の既定は **200,000** トークンで、上の「遅くとも 20 万」と
同じ値である。環境変数 `NDF_CONTEXT_LIMIT` で変えられ、`NDF_CONTEXT_GUARD=0` で止められる。

| 経路 | 止める起動 |
| --- | --- |
| 対話 | 工程 Skill（上の 4 つの切れ目の直後に始まる工程と、入口の `development-workflow` / `issue-plan-strategy`。一覧は `scripts/lib/token-guard-stages.txt`） |
| 3 層 | `description` の先頭語がフェーズ（`設計` / `実装` / `検査` / `取り込み` / `仕上げ`）の Agent |

- **文脈量は、会話の記録の最後の assistant 呼び出しの `usage` から読む**
  （`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`）。読めなければ止めない
- **サブエージェントの中の起動は止めない。** 見るのは conductor だけである
- **止めるのは工程の切れ目ごとに 1 度である。** 止めた直後に、工程へ入る次の起動が同じもの
  （Skill なら名前と引数、Agent なら `description`）であれば 1 度だけ通す。**続けると決めたら、
  同じ起動をもう一度行う。** 別の起動なら、上限を超えている限り再び止める
- **ラッパー（[relay.md](relay.md)）の直接の子の conductor では、1 度の通しをしない。** 上限を
  超えている限り止め続ける。人が居ない前提で、上限を超えたまま進むことを機械で止めるためである。
  conductor は新しいフェーズを起動せず、動いている supervisor の報告を待ってから、引継ぎ文書を
  更新し、次のコマンドのブロック（次の節）を出して応答を終える
- 止めたときの理由の欄が、利用者へ示すコマンド（次の節）を持つ。conductor はそれを次の節の
  形で示して応答を終える

Codex / Kiro / agy には hook を置かない。4 つの切れ目で 1 行を出す規約だけで守る
（[waiting.md](waiting.md) の「hook」節の表）。

## 新しい会話で戻す

**conductor は、4 つの切れ目と hook に止められたときに、次の工程を始めるコマンドを、
情報文字列 `ndf-next` の囲みのコードブロック 1 つで出す。**

```ndf-next
/goal /ndf:development-workflow #829 #830
```

- **囲みの中身がそのまま次の区間の最初の入力になる。** 複数行でよい。最後の応答に
  **1 つだけ**置く。2 つ以上置くと、ラッパーは拾わない。説明のために引く例は 4 つのバッククォートの
  囲みの中へ入れる（外側の囲みの中は数えない）
- **中身は `development-workflow` を起動する 1 行である**（`/ndf:development-workflow #829 #830`）。
  工程 Skill はモードと作業ツリーを戻す手順を持たないため、入口から入り直す。Codex と Kiro では、
  それぞれの README が示す Skill の起動の書き方に読み替える
- **今の区間を `/goal` で始めていたときだけ、中身の先頭を `/goal ` にする**
- **3 層では、conductor が `## フェーズの報告` を受け取った時点で出す**（supervisor は出さない）。
  フェーズの境が切れ目に当たるためである。ただし報告が `結果: 関門` なら、関門の承認と取り込み
  （設計 Pull Request のマージなど）が済んだ後に出す。**関門の承認より前には出さない。** 出すと、
  ラッパーが関門の前で会話を切る。切れ目 1 はこの形で満たす
- **ラッパーの有無によらず出す。** ラッパー（[relay.md](relay.md)）の下では、ラッパーがブロックを拾って
  次の区間を自動で起動する。ラッパーが無ければ、人がブロックの中身を新しい会話へ貼り付ける
- **Claude Code では、ブロックの直前の告知を `relay.py notice` の 2 行目で書く**（#980）。2 行目を
  言い換えずにそのまま写す。文面と秒数（静まりの秒数）は `relay.py` だけが持つ。呼び方は
  `development-workflow` の `SKILL.md` の、区間の切れ目の告知の段落にある。hook に止められたときは、
  拒否文が同じ 1 文を含むので、実行し直さずに写してよい。`relay.py` を解決できないか実行が失敗
  したときは、ラッパーの外として扱い、人がブロックの中身を新しい会話へ貼り付けると書く。Codex / Kiro /
  agy では、今までどおり中身を新しい会話へ貼り付けると書く。**ラッパーの下（1 行目が `relay`）では、
  手で入力させる文（「次の 1 行を使って」「貼り付けて」）を書かない。** 例外は 2 行目そのものが
  貼り付けの手順を示すとき（`NDF_RELAY_QUIET=inf`）である。ラッパーの外の 2 行目は外である理由
  （ラッパーが無い・終わっている・fork したセッションなど直接の子でない）で変わる（[relay.md](relay.md) の
  「fork したセッションで進めたとき」）
- **背景の作業が残っているとラッパーは切り替わらない。** ラッパーの Stop hook は印を書かず、Stop を 1 度だけ
  止めて動いている作業の id とコマンドの先頭を知らせる。見張りのように止めてよい作業は `TaskStop <task id>`
  で止め、止まったかは完了通知（`failed` / `killed`）で確かめてからブロックを出し直す。supervisor や
  `supervise.py queue` は止めずに終わりを待ってから出し直す（[waiting.md](waiting.md) の「背景の作業を止める」）
- **区間の切れ目の再起動は関門ではない。** 引継ぎ文書を更新したら、承認・確認（`AskUserQuestion`
  を含む）を挟まずに告知とブロックを出して応答を終える。状態は課題の本文と Pull Request に残り、
  取り消せるためである。ラッパーの外でも挟まない（確認の答えと貼り付けで入力が 2 度になる）。
  **`/goal` の文面が「承認を求める」と書いていても、指すのは `SKILL.md` の関門 2 つだけである**
- **引継ぎ文書の「次に実行するコマンド」の節も、同じブロックで書く。** 形の定義はこの節だけに置く

**新しい会話の `development-workflow` は、次の順で状態を戻す。**

| # | 読むもの | 戻すもの |
| --- | --- | --- |
| 1 | 課題の本文の `## 進行`（`gh issue view <番号> --json body`） | モード・作業ツリー・計画ファイル・通った工程 |
| 2 | `bash <この Skill のディレクトリ>/scripts/stage-check.sh report <番号>`（プラグインの `scripts/` ではなく、`development-workflow` の `scripts/` にある） | 通過工程の控え。本文と食い違えば控えを正とする |
| 3 | 1 の作業ツリー（`.worktrees/<ブランチ名>`）のブランチ名で `gh pr list --head <ブランチ名> --state all`。実装の Pull Request は `gh issue view <番号> --json closedByPullRequestsReferences` でも引く | 設計・実装の Pull Request と状態 |
| 4 | 1〜3 から、チェックの付いていない最初の必須の工程 | 次に起動する工程 Skill |

**Pull Request は番号の全文検索で引かない。** 同じ番号に触れただけの別の Pull Request も返す
ためである。設計の Pull Request は閉じる語を持たないため、課題との結び付きでは引けず、
ブランチ名で引く。

## 粒度は比で決める

**基準は値ではなく比である。** 固定費はリポジトリとモデルで変わるため、閾値を書くと
導入した先で意味を失う。

**基準を当てるのは supervisor のフェーズである。**

| 測った結果 | どうするか |
| --- | --- |
| その supervisor の**実作業が固定費を上回る** | 単独のフェーズのままにする |
| 実作業が固定費を下回る | **隣のフェーズと束ねる。** 固定費を 2 度払って読む量が増えていない |
| 最大充填がモデルに依る目安を超える | フェーズを割る |

**判定は記録ごとの比で行う。** 別の会話の中央値どうしを比べない。固定費は設定で変わるため、
どの記録の比でもない値で判断することになる。

**worker にはこの基準を当てない。** worker は使い捨ての読解であり、返す量が小さいことが
目的であるから、実作業が固定費を下回ってよい。代わりに、**1 つのフェーズについて
supervisor と配下の worker の固定費の合計が、その supervisor の実作業を上回ったら
「使いすぎ」と見る**。読む量に対して費用のほうが大きくなった状態である。

測り方は `/ndf:skill-stats --agents` が持つ。

## 委譲する対象と、しない対象

**委譲は context window を節約する唯一の手段ではないが、最も効く手段である。**
サブエージェントは別の文脈を持ち、別の CLI プロセスなら**上の層の context window を
1 トークンも消費しない**。

| 委譲してよい | 委譲しない |
| --- | --- |
| 探索（どのファイルにあるか） | **モード判定**（基準を持つ Skill は 1 つである） |
| 全文の読解と、そこからの要点の取り出し | **人手の承認を求める関門の判断**（取り消せない操作である） |
| テストの出力・ログ・差分の集計 | **収束の判定**（測れないことを 0 件として扱わないため） |
| 指摘の修正 | 設計の決定と、その理由の記録 |
| 範囲外の課題の下調べ | 受け入れ条件の書き換え |

**修正の委譲を必須と定めるのは実装レビューの側である。** 同じ規則をここへ写さない。

**どの器へ渡すか（その場・サブエージェント・CLI 実行・最小構成の `claude -p`・スクリプト）と、
小さな作業にサブエージェントを起こさない線引きと、新しい文脈で始めるか続けるかを決める費用の式は
[work-vessels.md](work-vessels.md) が持つ。**
ここへ写さない。

### 返させる形を決める

**自由文の要約を受け取らない。** 受け取ると、上の層は**要約の要約**を読むことになり、落ちた
情報が二重に落ちる。返させるのは、**項目と場所と根拠を持つ構造化された結果**である。
置き場所をファイルにすれば、context window に載せずに読み直せる。

### 数を増やすことは対策にならない

**4 本の委譲の報告を上の層が読めば、その context window は同じだけ埋まる。** 効くのは、
読んだ量に対して返す量が小さいときだけである。**読む量が変わらない委譲は、費用だけを
増やす。**

並行の本数の下限は [parallel-work.md](parallel-work.md) が持つ。**context window の観点でも
同じ下限が効く**（上の層が読む結果の本数が増える）。

## 残量は外から見る

**残量を自分で把握できるかは、モデルによって違う。** 把握できない側では、**使い切り
かけていることに気づけない**。気づけない前提で運用する。

- **工程の切れ目で残量を見る。** 切れ目でしか見ないのは、途中で見ても切れないためである
- **自動の要約が働く閾値を持つ実行環境では、既定より早める。** 既定は限界に近い側へ
  置かれていることがあり、そこまで待つと判断の質が落ちた後になる。**遅らせる方向には
  効かない設定もある**ため、変えられるのは早める側だと考えて扱う
- **推論の記録が履歴に残る実行環境では、それも量を食う。** 消す手段があるなら、長い工程で
  使う

## 出典

**外部の値を書くときは出典を添える。** 添えないと、次に読む人が現行の値か古い値かを
判定できない。

| 何を根拠にしたか | 出典 |
| --- | --- |
| トークン数が増えるほど精度と再現率が落ちること | モデル提供者の公式ドキュメントの「コンテキストウィンドウ」の節 |
| 100 万トークンに対し 20 万で要約を発火させた評価 | モデル提供者が公開したシステムカードの、web 探索の評価の節 |
| 要約より新しい文脈を選ぶ助言 | モデル提供者の公式ドキュメントの「プロンプトの実践」の節 |
| 残量の自己認識を持つモデルが限られること | 同上の「コンテキストの自己認識」の節 |
| 入力長に対する劣化が全モデルで単調であること | 第三者が 18 モデルを比べた公開の研究 |
| conductor の最大文脈・20 万を超えた会話の数・再読込の削減見込み | #827（会話の記録からの実測） |

**値そのものを写さない。** 版が変わると数字が変わり、写した側だけが古くなる。この文書が
持つのは**運用の目安**であって、モデルの性能値ではない。
