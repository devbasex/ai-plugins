# テスト駆動のサイクル

**失敗するテスト → 通す最小実装 → 整理** を 1 単位として進める。NDF ではこの Skill を
テスト駆動の唯一の基準とし、他の Skill から重複した規則を持たせない。

## 同じリリースで追加する Skill（本文の `※` 印）

本文で `※` を付けた Skill 名は同じリリースで順次追加されるものであり、まだ配布物に
存在しないことがある。**見つからない場合は探し回らず、下表の代替でそのまま進める。**

| Skill | 参照している内容 | 未追加のあいだの代替 |
| --- | --- | --- |
| `requirements-design` | 受け入れ条件の作り方 | 受け入れ条件を「観測可能・一意・テスト可能」な 1 文へ自分で書き下す |
| `refactoring` | 構造改善と現状固定テスト | サイクル内の整理にとどめ、構造改善は別タスクへ切り出す |
| `quality-gates` | 全体テストの実行とカバレッジ閾値の判定 | 対象プロジェクトのカバレッジツール設定に従い、設定がなければ測定値の記録だけ行う |

## 適用しない対象

次の変更にテスト駆動を強制しない。テストを書けないのではなく、書いても振る舞いを
担保しないためである。

| 対象 | 代わりに行うこと |
| --- | --- |
| ドキュメント・コメント | リンクと手順の実行可能性を確認する |
| 静的な設定値・定数の変更 | 設定が読まれる経路を 1 度実行して確認する |
| 生成物（ビルド出力・lockfile・自動生成コード） | 生成コマンドを再実行して差分が一致することを確認する |
| 依存パッケージの版更新のみ | 既存テストを実行する |

判断に迷う場合は「この変更で壊れうる振る舞いがあるか」で決める。あるなら適用する。

## 事前調査（サイクルに入る前に 1 度だけ）

プロジェクト固有のテスト手段を先に確定させる。推測でコマンドを組み立てない。

```bash
# 例: どこにテストがあり、どう起動するか
ls tests/ test/ spec/ 2>/dev/null
grep -n '"test"' package.json 2>/dev/null
grep -n '\[tool.pytest' pyproject.toml 2>/dev/null
cat Makefile 2>/dev/null | grep -n '^test'
```

確定させる項目:

| 項目 | 例 |
| --- | --- |
| テスト実行コマンド | `pytest`、`npm test`、`go test ./...` |
| 単一テストの絞り込み方 | `pytest -k name`、`npm test -- -t name` |
| テストの置き場所と命名 | `tests/test_*.py`、`src/**/*.test.ts` |
| 既存のテストダブルの流儀 | fixture / factory / モックライブラリ |

既存テストがそもそも通らない場合は、**先にそれを報告する**。壊れた状態を基準にすると、
自分の変更が原因かどうかを切り分けられない。

## サイクル

### 1. 失敗するテストを書く

受け入れ条件 1 つに対してテスト 1 つを書く（条件の作り方は `requirements-design`※）。

### 2. 失敗を証跡として確認する

**テストを実行し、失敗を目で見る。** ここを飛ばすと、実は最初から通っていたテストや、
別の理由で失敗しているテストに気づけない。

記録する 3 点:

| 記録 | 目的 |
| --- | --- |
| 実行コマンド | 再現手段 |
| 失敗メッセージ | 何が起きたか |
| **失敗理由が期待どおりか** | 未実装による失敗か、構文エラーや設定ミスによる失敗かの区別 |

```text
$ pytest -k test_rejects_zero_quantity
E   assert 200 == 400        ← 期待どおり（検証が未実装のため通ってしまう）

$ pytest -k test_rejects_zero_quantity
E   ImportError: cannot import name 'validate'   ← 期待と違う。先にこれを直す
```

期待と違う理由で失敗しているときは、実装へ進まずテスト側を直す。

### 3. 通す最小実装を書く

そのテストを通すために必要な変更だけを書く。次のものは書かない。

- まだテストがない分岐・設定・拡張点
- 「あとで要るはず」の抽象化（差異が 1 つしかない時点で戦略や生成の仕組みを入れない）
- 依頼範囲外の整形・改名

対象の外で不具合や不整合に気づいたときは、その場で `/ndf:out-of-scope` を起動して
起票する。書かない判断だけをして先へ進むと、判断した理由が残らない。

### 4. 整理する

テストを**通ったまま**保って構造を整える。整理中にテストが落ちたら、整理をいったん戻す。
コードの兆候起点の本格的な構造改善は `refactoring`※ に委ねる。

### 5. 次の条件へ進む

1 サイクルで 1 条件。複数の条件をまとめて実装すると、どの条件が満たされていないのかが
失敗メッセージから読めなくなる。

## バグ修正は再現テストから

原因の調査より前に、**バグを再現する失敗テスト**を書く。再現できないまま修正すると、
直ったかどうかを判定できない。

```text
1. 不具合の入力・状態を突き止める
2. その入力で失敗するテストを追加する（この時点で失敗することを確認する）
3. 原因を直す
4. 同じテストが通ることを確認する
5. テストは残す（同じ退行を二度検出できる）
```

再現テストが書けないときは、まず再現条件が特定できていない。`problem-solving` で原因を
絞り込んでから戻る。

## テストの乏しい既存コードでは順序が変わる

変更対象にテストがほとんどない場合、いきなり新しいテストを足すより、**現状の振る舞いを
固定するテスト**を先に置く。手順は `refactoring`※ の現状固定テストに従う。

## テストダブルの優先順

| 優先 | 手段 | 使う条件 |
| --- | --- | --- |
| 1 | 本物 | 実行が速く、外部へ副作用が出ない |
| 2 | 疑似実装（インメモリ実装など） | 本物が遅い・環境依存だが、振る舞いを再現できる |
| 3 | スタブ（決まった値を返す） | 入力に対する応答だけが必要 |
| 4 | モック（呼び出しを検証する） | **呼び出し自体が仕様**のときに限る |

モックを既定にしない。実装の呼び出し手順に結合したテストは、振る舞いが同じでも実装を
変えた瞬間に落ちる（脆いテストの例は
[references/test-quality.md](references/test-quality.md)）。

## 報告の規則

- **実行していないテストを「通った」と書かない。** 実行したコマンドと結果だけを書く
- 一部だけ実行した場合は、絞り込み条件を明記する（全体実行は `quality-gates`※ の段階で行う）
- 失敗したまま完了扱いにしない。残す場合は失敗しているテスト名と理由を明記する
