# テストの階層と使い分け

同じ振る舞いを複数の階層で検証すると、実行時間が伸びるだけで検出力は上がらない。
**何をどの階層で担保するか**を決めてから書く。

## 4 つの階層

| 階層 | 検証対象 | 依存の扱い | 目安 |
| --- | --- | --- | --- |
| 単体 | 1 つの関数・クラスの振る舞い、分岐と境界値 | 外部依存は疑似実装かスタブ | 数ミリ秒。数が最も多い |
| 結合 | 複数の部品をつないだ経路（DB・キュー・ファイル） | 本物に近いものを使う（テスト用 DB 等） | 主要経路と失敗経路に絞る |
| 契約 | 呼び出す側と呼ばれる側で合意した入出力（API・イベント） | 相手側は契約定義に従う代替 | 契約 1 つにつき 1 組 |
| 端から端まで | 利用者の操作から結果までの通し | 本物の構成 | 代表シナリオのみ |

## 何をどこで担保するか

| 担保したいこと | 階層 |
| --- | --- |
| 入力の妥当性判定・計算・状態遷移の分岐 | 単体 |
| 境界値（0 件、上限、上限 + 1） | 単体 |
| 保存した内容が読み出せる、制約に違反した挿入が失敗する | 結合 |
| トランザクションの巻き戻し | 結合 |
| 公開 API の応答形式・状態コード・後方互換 | 契約 |
| イベントの項目名と型（発行側と購読側の合意） | 契約 |
| 画面から操作して結果が見える | 端から端まで |
| 認可（他人のデータが見えない） | 契約または結合。**単体だけで済ませない** |

## 上の階層へ持ち上げない

分岐の網羅を端から端までで行うと、実行時間が伸び、失敗時の原因特定も難しくなる。
**分岐は単体、つなぎ目は結合、通しは代表シナリオだけ**を原則にする。

```text
❌ 入力検証の 12 パターンを画面操作で確認する
✅ 12 パターンは単体、画面からは代表 1 つだけ通す
```

## 下の階層で済ませない

逆に、単体テストだけで「動く」と判断できないものがある。

- SQL・クエリビルダの実際の挙動（方言・NULL の扱い・型変換）
- スキーマ制約（一意制約・外部キー・NOT NULL）
- 権限・認可（実際の要求経路を通す必要がある）
- 直列化・文字コード・タイムゾーン

これらは疑似実装で通しても本番で失敗する。結合または契約の階層で 1 度は通す。

## 契約テストを置く場所

呼び出す側と呼ばれる側が別リポジトリ・別チームの場合、契約は**両側から検証する**。

| 立場 | 検証内容 |
| --- | --- |
| 呼ばれる側（提供者） | 契約どおりの応答を返す。項目を削っていない |
| 呼び出す側（利用者） | 契約どおりの応答を処理できる。未知の項目で壊れない |

片側だけの検証は、相手の変更を検出しない。

## 端から端までのテストで気をつけること

- シナリオを増やすほど不安定になる。**代表シナリオを決めて数を固定する**
- 落ちたときに原因が分かるよう、失敗時の証跡（画面記録・ログ・通信記録）を残す
- ブラウザ操作を伴う場合の作成手順と証跡は `playwright-kit` プラグインの
  `playwright-planning` / `playwright-authoring` を使う（導入していなければ対象プロジェクトの手順に従う）

## 実行時間の目安

| 階層 | いつ実行するか |
| --- | --- |
| 単体 | 変更のたび（サイクル内） |
| 結合 | 変更単位の区切り（コミット前） |
| 契約 | 継続的インテグレーション |
| 端から端まで | 継続的インテグレーション、またはリリース前 |

サイクル内で全階層を回すと手が止まる。段階の切り分けは同じリリースで追加される
`quality-gates` に従う。同 Skill がまだ配布物に無いあいだは、変更した振る舞いを覆う最小の
階層だけをサイクル内で回し、上位の階層は完了を宣言する前に 1 度実行する。
