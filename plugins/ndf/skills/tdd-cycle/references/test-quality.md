# 脆いテストと、その代替

テストが落ちる原因は 2 つしかない。**仕様が破れた**か、**テストが実装に結合している**か。
後者は退行を検出しないうえ、変更のたびに直す手間だけが増える。

## 判定の基準

> 振る舞いを変えずに実装を書き換えたとき、そのテストは落ちるか。

落ちるなら、そのテストは実装詳細に結合している。

## よくある例と代替

### 1. 内部メソッドの呼び出し回数を検証する

```python
# ❌ 実装の呼び出し手順に結合している
service.save(order)
assert repo.save.call_count == 1
```

```python
# ✅ 結果を検証する
service.save(order)
assert repo.find(order.id).status == "confirmed"
```

呼び出し回数の検証が正しいのは、**回数自体が仕様**のとき（外部への課金 API を二重に
呼ばない、通知を 1 回だけ送る）に限る。

### 2. private な関数を直接呼ぶ

公開されたエントリポイントから呼べない経路をテストすると、内部構造を変えるたびに落ちる。公開
インタフェース経由でその分岐に入る入力を探す。エントリポイントから到達できない分岐は、そもそも
不要な可能性がある。

### 3. 表示文字列に完全一致を要求する

```javascript
// ❌ 文言の微修正で落ちる
expect(msg).toBe("数量は 1 以上を入力してください。");
```

```javascript
// ✅ 判定に必要な部分だけを見る
expect(res.status).toBe(400);
expect(res.body.code).toBe("quantity_out_of_range");
```

文言そのものが仕様の場合（法的表記・利用者向け通知）は完全一致でよい。その場合は
文言の出典（仕様書・翻訳ファイル）をテストのそばに書く。

### 4. 現在時刻・乱数・実行順に依存する

| 依存 | 対処 |
| --- | --- |
| 現在時刻 | 時刻を引数または注入可能な依存にし、テストで固定する |
| 乱数・ID 生成 | 生成器を注入する。または生成値ではなく性質（一意である等）を検証する |
| 実行順・並び順 | 順序が仕様なら明示して検証する。仕様でないなら集合として比較する |
| 実行環境（時間帯・ロケール・OS） | テスト内で明示的に設定する |

これらは flaky（同じコードで通る／落ちるが変わる）テストの主要因である。1 度でも
再現性なく落ちたテストは、原因を特定してから残す。「たまに落ちるので再実行する」運用に
すると、本物の退行を見逃す。

### 5. 本物の時間を待つ

`sleep`・条件が満たされるまでのポーリング・timeout・錠の待ち・期限の経過を、本物の時間で確かめるテストを書かない。
**ポーリングに上限を付けても同じである。** 1 件で数秒かかり、合否が機械の負荷で変わる（測っているのはコードではなく
環境である）。競合や錠の正しさは、何回流しても証明できない。正しさは設計（実績のあるライブラリの錠・SQLite など）と
レビューで担保する。

待つコードは 2 つに分けて扱う。

| 部分 | 例 | 確かめ方 |
| --- | --- | --- |
| 判断 | 何秒で諦めるか・時間切れで何をするか・錠を取れなければ止めるか | 判断を純粋な関数へ寄せ、時計と結果を引数か注入した依存で渡して、待たずに確かめる |
| 待つ仕組み | `sleep`・`flock`・poll・子の終了の待ち | 確かめない。OS とライブラリの責任で、自分のコードの振る舞いではない |

```text
❌ sleep(2) してから結果を見る
❌ 条件が満たされるまでポーリングで待つ（上限つきでも）
❌ 期限（timeout）を超えるまで本当に待って、時間切れの処理を見る
✅ 時計を注入し、進めた時刻で判断の関数を呼ぶ
✅ 期限の秒は、設定の値を使っていることだけを見る（実際に N 秒待たない）
✅ 非同期処理を同期的に実行できるエントリポイントを用意する
```

時間や OS に触れる外側は薄く保ち、判断を持たせない（Humble Object。判断を純粋な核に、待ちと I/O を外側の殻に置く
Functional Core, Imperative Shell も同じ考え方）。外側が判断を持つと、判断を確かめるために本物の時間を待つことになる。
本物の時間と非同期の待ちは、flaky なテストの主な原因でもある（Martin Fowler「Eradicating Non-Determinism in Tests」）。

### 6. 1 つのテストで多くを検証する

失敗時にどの検証が落ちたのか読み取れない。テストは 1 つの振る舞いに絞り、名前で何を
検証しているかが分かるようにする。

```text
❌ test_order_flow
✅ test_confirm_sets_status_to_confirmed
✅ test_confirm_rejects_when_stock_is_insufficient
```

### 7. テストを通すためにプロダクションコードへ分岐を足す

```python
# ❌ テスト用の抜け道
if os.getenv("TESTING"):
    return True
```

テスト時だけ通る経路は、本番で検証されない経路を作る。依存を注入可能にするか、設定として
明示的に扱う。

### 8. `.md` の文言を検証する

`SKILL.md`・`references/`・`prompts/`・`docs/` などの文書を読み、言い回し・見出し・表の並び・
語の有無を `assert "..." in text` で検証するテストを書かない。**文書の振る舞いは文言そのもの
であり、同じ文面をプロンプトに渡しても同じ結果が返るわけではない。** 固定しても振る舞いは
保証されず、文書を整えるたびに期待値を書き換える手間と、リファクタリングが文書の整理を「振る舞いの
変更」として取り消す副作用だけが残る（#885）。

| 見たいもの | 代わりに使うもの |
| --- | --- |
| 文書が指すファイル・スクリプト・Skill の実在（参照切れ） | リンクと参照をチェックするスクリプト（対象リポジトリに無ければ、置くか、レビューで見る） |
| 文書の正しさ・言い回し | レビュー |
| 文書に埋め込んだ bash の振る舞い | そのブロックを取り出して実行するテスト |
| スクリプトが実行時に読む `.md`（プロンプト・表）の形式 | そのスクリプトを通すテスト（機械が読むコントラクト） |

### 9. 子のプロセスを起動して確かめる

CLI・スクリプト・ラッパーを子のプロセスで起動し、終了コードや出力を見るテストを書かない。起動だけで 1 本に数百ミリ秒から
数秒かかり、件数に比例して遅くなる。環境の変数・PATH・ロケールに合否が左右される。例 5 と合わせて、テストを
1 つのプロセス・1 つのスレッドで動く Small テスト（Google のテストのサイズ）に保つための決まりである。

| 見たいもの | 代わりに使うもの |
| --- | --- |
| CLI の振る舞い | エントリポイントの関数（`main(argv)` など）を同じプロセスで呼ぶ |
| 子へ渡す引数・環境 | 組み立てる関数の返りを直接見る |
| 子を起動する部品の判断 | 起動の手（`spawn` など）を偽物に差し替え、渡された引数と、偽物の返す結果への反応を見る |
| リリース対象として起動できること | 継続的インテグレーションのスモーク（代表の 1 本） |

## カバレッジの扱い

カバレッジは「テストが実行した行の割合」であって、正しさの指標ではない。数値を上げる
目的でテストを足さない。

閾値は Skill 側に持たず、対象プロジェクトのカバレッジツール設定に従う（判定手順は同じ
リリースで追加される `quality-gates` が扱う）。設定がないプロジェクト、および
`quality-gates` がまだリリース対象に無いあいだは、測定値を記録するだけにとどめる。

## 削除してよいテスト

- 仕様が変わり、検証対象の振る舞いがなくなった（削除して、削除理由を差分に残す）
- 同じ入力・同じ検証の重複
- 実装詳細に結合しており、振る舞いを検証していない（上記の例に該当するもの）
- `.md` の文言を検証している（上記の例 8。参照切れを見ていたものは、チェックスクリプトが同じ参照で失敗を返すことを確かめてから削る）
- 本物の時間を待つ・子のプロセスを起動して確かめている（上記の例 5・9。判断を純粋な関数で確かめるテストがあれば、それで足りる）

**落ちるから削除する**のは禁止。落ちた原因を先に説明する。
