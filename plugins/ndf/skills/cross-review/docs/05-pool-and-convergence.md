# 05: 参加者プールと終了基準

**誰がレビューし、いつ止めるか**を定める。手順そのものは
[01-state-and-review.md](01-state-and-review.md) にあり、この文書は Step 0（初期化）と
Step 1（ラウンドの開始）と Step 3（判定）が読む基準を持つ。

## 参加者プールと担当

**既定の参加者プールは claude / codex / kiro とホストである。** agy はテストをバックグラウンドで起動した
まま結果を残さずに終わることがあり、起動し直しても残らなければ収束が止まるため、既定から外した。
戻すときは `--include agy` を渡す。ホストは常に参加者プールに入る（#892。ホストが agy なら 4 者）。
レビュー担当は CLI プロセスとして起動するため、ホストと同じランタイムでもホストの会話の作業文脈は
持ち込まれない。外したい相手は `--exclude` で名指しする。既定の表とホストを足す関数
（`DEFAULT_RUNTIMES` / `default_pool`）は `cross-refactoring` と共通で、共通ライブラリの
`lib/assignment.py` にある。

| 決めるもの | どこで決まるか |
| --- | --- |
| ホスト | `--host` の明示指定、または環境変数からの推定（`detect_host`）。**推定できなければ `init` が失敗する** |
| 参加者プール | `review_pool(host)`（claude / codex / kiro とホスト） |
| 利用可能な参加者 | 参加者プール + `--include` で足した者 − `--exclude` で外した者 を確認へ通し、通った者（`resolve_participants`） |
| そのラウンドのスロット | 利用可能な参加者から 2 スロット（`review_seats`）。`init` が `participants` へ残す |

### 利用可能な参加者の決め方

**1 者が使えなくても始める。** 導入していない CLI や認証の切れた CLI が 1 者あるだけで
収束ループ全体を開始できないと、他の 2 者で回せる場面まで止まる。確認は「止めるゲート」では
なく「誰が使えるかを把握する手順」であり、通らなかった者は理由とともに状態ファイルの
`participants.unavailable` へ残して先へ進む。

**確認は認証だけでなく、モデルを 1 回引くところまで行う**（参加の確認。`lib/auth.py` の `probe_auth` が
参加者ごとに並行に走らせ、合否は `lib/assignment.py` の `admit` が決める）。認証の状態確認が通っても、
設定のモデルを引けない CLI や更新トークンが失効した CLI は結果を残さずに終わるためである。

| 種類 | 何をするか |
| --- | --- |
| 認証確認 | `claude auth status` / `codex login status` / `agy models` / `kiro-cli whoami`。通らなければ最小の呼び出しを走らせずに外す |
| 最小の呼び出し | 担当の起動と同じ CLI・同じプロジェクトのディレクトリ・同じ設定の上書き（claude の従量の接続の `--settings`）で、短い固定の問いを 1 回答えさせる（agy は持たない） |
| 既定のモデルでの引き直し | 最小の呼び出しがモデルを引けず、モデルを引数で明示していないときだけ、claude は `--model default`、codex は `--ignore-user-config` で引き直す。codex はこれで読めた既定のモデルを、担当の起動と同じ形（利用者の設定のまま `--model <名前>`）でもう 1 回引き、通ったときだけ通す（`--ignore-user-config` は提供元の設定も外すため）。通れば既定のモデルで担当に入り、`participants.default_models` に残る。利用者の設定ファイルは書き換えない |

1 者の持ち時間は 3 種類で共有して 120 秒。外した理由は `participants.unavailable` の値の先頭
（`model_unavailable: ERROR: ...` など）と `participants.checks[<名前>].result` に語で残る
（`unauthenticated` / `auth_expired` / `model_unavailable` / `timeout` / `missing_cli` / `probe_failed`）。
`init` は参加者ごとに次の形の 1 行を出す。

```text
✅ claude: 認証とモデル（4.9 秒）
↪ codex: 設定のモデル gpt-5.5 を引けないため、既定のモデル gpt-6.1-sol で担当に入れる（9.1 秒）
❌ kiro: auth_expired — ERROR: Your access token could not be refreshed ...（5.0 秒）
```

確認の後に同じ形（モデルを引けない・認証の失効）が起きたときは、監視が `err.log` の文言で理由を付けて止め、
同じ担当で起動し直さずに振り替える（`assignment.NO_RELAUNCH_REASONS`）。確認の結果は再開で使い回し、
参加者に関わる引数を渡した再開だけ確かめ直す。

| 引数 | 何をするか |
| --- | --- |
| `--exclude NAMES` | 参加者プールから外す。今は呼びたくない相手を、確認の前に落とす。**参加者プール（既定 + `--include`）に無い者の指定は止めずに無視する** |
| `--include NAMES` | 参加者プールに足す。agy を戻すときに使う。既に参加者プールにいる者を指定しても結果が変わらない（エラーにはしない） |
| `--require-all` | 全員の確認を必須にする。確認を通らない者が 1 者でもいれば `init` を失敗させる |

名前の矛盾（足す者と外す者の重なり、1 者指定と外す者の食い違い）は
`init` が状態ファイルを作る前に弾き、終了コード 1 で終わる。

**参加者プールに無い者の除外は矛盾として扱わない。** `--exclude agy` を書いた既存の手順が、既定から
agy を外した後もそのまま通るようにするためである。無視した名前は `participants.ignored_exclude`
へ残し（外した者の `excluded` とは分ける）、次の 1 行を出す。完了報告の「参加した者」にも
「--exclude で指定したが既定の参加者プールに無かった者」の行で出る。

```text
ℹ --exclude agy は既定の参加者プールに無いため無視しました（参加者プール: claude, codex, kiro）
```

`--exclude` を渡さない再開は、外した者と無視した除外の両方を記録から足し戻す。無視した名前を
`--include` か `--only` に渡したときだけ、その名前は足し戻さない（新しい指定を優先する）。確認そのものを飛ばしたい
ときは `NDF_SKIP_AUTH_CHECK=1` を使う（飛ばしたことは出力と状態ファイルへ残る）。

### スロットの埋め方

**毎ラウンド 2 スロットを確保する。** 1 スロットになると、指摘が 1 つの言語モデルの見方だけで決まり、
反証（`docs/06`）も成り立たない。**違うランタイムを先に使う。** 同じ言語モデルの 2 つの
文脈より、違う言語モデルの 2 つの文脈のほうが観点が分かれる。

| 利用可能な参加者の数 | スロット |
| ---: | --- |
| 3 以上 | 輪番で 2 スロット。外す 1 者をラウンドごとに回す |
| 2 | その 2 者 |
| 1 | その 1 者と、同じランタイムの 2 つ目のスロット |
| 0 | `init` が失敗する（終了コード 1、状態ファイルを作らない） |

**ホストを別に確かめてフォールバックに使わない。** ホストは既に参加者プールに入っており、利用可能な参加者に
居ないのは確認を通らなかったか `--exclude` で外したかのどちらかである。前者は確かめ直しても
通らず、後者でスロットへ戻すと利用者の指定に反する。そのため新しく作る状態の
`participants.fallback` は空になる。**この変更の前に作った状態**が持つ `fallback`（ホスト）は、
再開したときもそのままスロットのフォールバックに使う（担当を変えないため）。

同じランタイムの 2 つ目は、名前に `-2` を付けた**スロット名**（`claude-2`）で表す。結果
ファイルの名前と状態ファイルの鍵がこの名前になり、起動する CLI はハイフンの手前から選ぶ
（形は `04-contracts.md`）。保存された `fallback` を使う場合も、**フォールバックは利用可能な参加者に
含まれない相手だけを使う。** 含まれる相手を充てると、同じスロット名が 2 つ並ぶ。

**担当はラウンドを開くときに決めて状態へ残す。** 後から輪番を引き直すと、記録と実際に
起動した担当がずれる。`start-round` が `REVIEWERS` / `REVIEWERS_CSV` で返す。**シェル変数で
絞り直さない。** 返る一覧は 1 者指定とフォールバックを反映済みで、絞ると状態ファイルとずれた
ときに起動も監視も誰にも当たらない。

### 1 者だけで回す指定

**`--only` はそのラウンドの担当を 1 者へ絞り、スロットのフォールバックを行わない。** 利用者が 1 スロットと
決めた指定であるため、2 スロットへ戻さない。輪番が返す 2 者を担当のまま残すと、指定した 1 者が
含まれないラウンドで誰も起動されない。そのとき全員が「指定によるスキップ」として扱われ、
**レビューが行われていないのに収束する**。外した者を指定した場合は `init` が弾く。

**名指しした 1 者は、既定の参加者プールに無くても参加者にする**（`--only agy` は `--include agy` 無しで
agy 1 者で回る）。記録の `included` には書かない。再開で `--only none` を渡すと既定の参加者プールへ戻る。

**指定した 1 者が確認を通らなければ `init` が失敗する**（終了コード 1、状態ファイルを作らない）。
フォールバックを行わない以上、利用可能な参加者が 0 者のままスロットに入るのはその 1 者だけであり、起動しても
結果が残らないラウンドが積み重なる。利用可能な参加者が 0 者で `init` が失敗する点は、上の表の
「利用可能な参加者の数 0」と同じ扱いである。

### 参加者の記録を持たない状態ファイル

この変更の前に始めた実行の状態ファイルには `participants` が無い。そのときは `host` から
変更前と同じ輪番（`review_seats(round, 全ランタイム − ホスト, [])`）で 2 スロットを決める。
`default_pool(host)` はホストを含むため、この分岐だけは変更の前の参加者プールを式で持つ。`host` も
無ければ `codex` / `agy` の 2 者として読む。中断した実行を新しい版で再開したときに、担当が
入れ替わって前のラウンドの記録と突き合わせられなくなることを避ける。

**担当を保つのは、担当の引数を渡さない再開だけである。** 再開で `--only` / `--include` /
`--exclude` / `--require-all` を渡すと、参加者を今の参加者プール（claude / codex / kiro とホスト）から作り直す。
明示の作り直しであるため、#892 の前に始めた実行でも利用可能な参加者にホストが加わりうる。

## 終了基準

**3 つの層を、この順で見る。** いずれも同じ一致の判定（位置・近傍 3 行・本文）を使う。

| 順 | 層 | 見るもの | 結果 |
| --- | --- | --- | --- |
| 1 | 引継ぎ | 再開の時点で残っていた未解決の指摘 | 修正の工程を 1 度通すまで収束させない |
| 2 | 新規性 | そのラウンドの指摘のうち、前のラウンドと一致しないもの | **0 件なら収束** |
| 3 | 振動 | 前のラウンドとの重複率 | 0.5 以上で中断 |

**新規性を振動より先に見る。** 新規が 0 件のラウンドは重複率が 1.0 になるため、順序を
逆にすると収束すべきラウンドが中断として落ちる。

**測れないことを 0 件として扱わない。** 指摘の記録（payload）が残っていないラウンドでは
中身を読めない。これを 0 件と数えると、修正必須の指摘が出ているラウンドまで収束させて
しまう。測れないときは全員が pass かで判定し、出力の `NEW_FINDINGS` は `-` に
なる。

**担当が 1 者のラウンドと、起動し直した担当の指摘は、未反証（`unrefuted`）として新規性の層が
数える。** 担当が 1 者なら反証を返す相手がいない。起動し直した担当の指摘は、反証を取り込んだ
後に取り込まれるため反証を持たない。いずれも誰も誤りを示していない重大な指摘であり、数えない
と未解決のまま承認で収束する。1 者で回したラウンドの収束は、この新規性と、全員が通したかの
2 つで決まる。担当が承認か、重大な指摘の無いコメントを返せば、全員が通したとして収束する。
修正要求なら、未反証の重大な指摘が新規に数えられ、修正の工程へ進む。修正の後のラウンドで同じ
指摘が戻れば、前のラウンドと一致して新規 0 件になる。戻らなければ承認で収束する。

**全員 `APPROVE` は、最も止まらない参加者に律速される。** #156 が観測した 6 ラウンドでは、
一方が round 4 以降 3 ラウンド連続で承認を返す間、もう一方が round 6 まで指摘を出し続け、
round 5 の指摘は修正済みの箇所を指していた。再提出された指摘は Pull Request に残り、
最終スイープ（Step 7.5）が解消する。

## 範囲の照合

**担当が範囲を推測して一部だけを見た承認では、収束しない。** スプリント PR（複数課題の差分の末尾に
cross-refactoring のコミットが付く形）で、担当が末尾のコミットだけを見て承認し、そのラウンドが
「全員が通した」で収束した（#1702）。そのため範囲をプロンプトで渡し、担当が読んだファイル数を
範囲のファイル数と突き合わせる。

### レビュー範囲

`start-round` がラウンドを開くときに求め、`rounds[].review_scope` に書く。base の SHA は head を取る
REST の応答（`GET /repos/{repo}/pulls/{pr}`）の `base.sha` から読み、API の呼び出しを増やさない。

| 欄 | 意味 |
| --- | --- |
| `range` | `full`（PR の全差分）か `since_previous`（設計 PR の 2 ラウンド目以降。`classifications.diff_scope`） |
| `base_sha` | `full` は PR の `base.sha`。`since_previous` は同じ PR の 1 つ前のラウンドの `head_sha`（無いか今の head と同じなら `full` へ落とす） |
| `head_sha` | そのラウンドの `head_sha` |
| `files` | `git -C <worktree> diff --name-only <base_sha>...<head_sha>` の行数 |
| `unavailable` | 求められなかった理由。このとき上の 4 つは無い |

| `unavailable` | いつ |
| --- | --- |
| `no_head` | 作業ツリーの同期を飛ばし、head を記録していない |
| `no_base` | PR の応答に `base.sha` が無い |
| `base_missing` | base のコミットが作業ツリーに無く、`git fetch origin <base_sha>` でも取れない |
| `diff_failed` | `git diff --name-only` が非 0 で終わった |

範囲を求められなくてもラウンドは止めない。`launch-reviewer.sh` は `review_scope` に `unavailable` が
無く、`review_scope.head_sha` がそのラウンドの `head_sha` と一致するときだけ、プロンプトの「必須
コンテキスト」に節「このラウンドのレビュー範囲」（base・head・3 点の `git diff` のコマンド・ファイル数）を
載せ、結果ファイルに `read_files` を書くよう指示する。それ以外は節も指示も載せない。

### 読んだファイル数

担当は結果ファイルの `read_files` に、レビュー範囲のファイルのうち差分を読んだファイルの数を整数で書く
（自己申告）。`read-result` は席の記録へ写す。

| 席の記録 | 値 |
| --- | --- |
| `read_files` | 0 以上の整数。測れなければ `null`（0 件読んだことではない） |
| `read_files_reason` | `null` の理由。`missing`（鍵が無い）か `not_integer`（真偽値・文字列・小数・負の数） |

取り込みは `read_files` で止まらず、指摘も捨てない。

### 判定での照合

`judge` は結果なしの扱いを抜けた後、通した担当（`APPROVE` か重大な指摘の無い `COMMENT`）ごとに
`read_files` を照らす。通すのに要る数は `ceil(files × 0.5)`（`review_scope.READ_FILES_MIN_RATIO`）で、
16 ファイルなら 8 である。足りない（`too_few`）・測れない（`missing` / `not_integer`）担当を外れた担当とする。
通していない担当（`REQUEST_CHANGES`・重大な指摘のある `COMMENT`）は照らさない。

収束の式（終了基準の層）を今のまま評価し、成り立ったうえで外れた担当がいれば収束させない。
`verdict = scope_unmatched`・終了コード 2・`SCOPE_RETRY=1` を返し、`drive.py` は修正を挟まずに
次のラウンドを開く。次のラウンドは席の輪番で組み直され、別の担当が全範囲を見る。ラウンドの上限は
今のまま効く。収束の式が成り立たないラウンドは、照合の結果に関わらず修正へ回る。

照合しないラウンドは今と同じ判定になる。

| 照合しない理由（`SCOPE_CHECK=unchecked:<理由>`） | いつ |
| --- | --- |
| `review_scope.unavailable` の値 | 範囲を求められなかった |
| `legacy` | `review_scope` を持たない前の版のラウンド |
| `model_stage` | 設計 PR のモデルの段。指示どおりドメインモデルの節だけを読むため、照合すると誤って外す |

判定の出力と状態ファイル:

| 出力 | 形 |
| --- | --- |
| `SCOPE_CHECK` | `checked` か `unchecked:<理由>` |
| `SCOPE_UNMATCHED` | `checked` のとき。`'<席>=<読んだ数>/<差分の数> ...'`。測れないときは読んだ数の位置に理由（`'kiro=1/16 codex=missing/16'`） |
| `SCOPE_RETRY` | 出口が `scope_unmatched` のとき `1` |
| `rounds[].scope_check` | `{checked, reason?, files?, min_read?, unmatched: [{seat, read_files, reason}]}`。判定のたびに書き直す |
