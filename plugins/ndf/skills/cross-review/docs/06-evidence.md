# 06: 根拠と反証条件

指摘の採否を、票の数ではなく**別の担当が確かめられる根拠**で決めるための規約。
#156 の 2 本目で入った部分を持つ。**集約の判定は 3 本目が扱う。**

## なぜ根拠を求めるか

**重要度の自己申告と判定が対応しない。** PR #157 の round 6 で、担当が minor 2 件だけで
`REQUEST_CHANGES` を返した。判定の基準は「修正必須の指摘なし（minor 以下しか無い場合も
`APPROVE` で良い）」と定めてあり、基準どおりなら `APPROVE` になる。

**票の数でも決められない。** 同じ系列のモデルが同じ誤りをすると、それが「多数」に見える。
少数派だけが見つけた重大な指摘は、票では拾えない。

**確かめられる形を求める。** 根拠は「何がそう言えるか」、反証条件は「何が成り立てば
棄却できるか」である。どちらも別の担当が読んで確かめられる。

## 求める 3 項目

| 項目 | 何を書くか | 例 |
| --- | --- | --- |
| `evidence` | 根拠。対象のコードと到達経路 | `handle() が None を渡す経路が 1 本ある（api.py:88）` |
| `falsification` | 反証条件。これが成り立てば棄却できる | `test_null_input が通れば棄却できる` |
| `suggested_check` | 実行できる検証手順 | `pytest tests/test_foo.py::test_null_input` |

**自己申告の確信度は求めない。** 数値の尺度は担当ごとに違い、突き合わせられない。
根拠と反証条件は文章として読めるため、別の担当が確かめられる。

**確かめられない書き方は根拠にならない。** 「一般によくない」「読みにくい」は、読んだ側が
真偽を判定できない。**どのコードのどの経路がそう言わせるのか**を書く。

## `has_evidence` の決まり方

**`evidence` と `falsification` の両方が空でないときだけ真になる。** 取り込みのときに
`cmd_read_result` が付ける派生の項目で、担当が書く値ではない。

**片方だけでは足りない。** 根拠だけでは、どうなれば取り下げるのかが決まらない。反証条件
だけでは、なぜそう言えるのかが分からない。

空白だけの文字列は空として扱う。

## 4 項目を持たない指摘

**捨てない。** 捨てると、対応していない担当の指摘が記録から消える。`has_evidence` が
偽になり、集約でそのことが分かる形で残る。

## 総評だけへ書いた指摘

**`payload.json` の `comments[]` へ載せる。** インラインの有無と指摘の件数を切り離す。

差分の外を指す指摘は総評へ書く決まりで（インラインは差分に含まれる行にしか付かない）、
`HTTP 422` が返ったインラインも総評へ移す。この 2 つの経路を通った指摘は、投稿の写しを
`payload.json` にしていた頃は進行側から見えなかった。

`posted_to` が投稿先（`inline` / `body`）を持ち、`path` と `line` は総評へ書いたときも
埋める。

## 独立発見

**発見を終えるまで、参照してよい既存コメントは起動時のスナップショットに限る。**

担当は並列にバックグラウンドで起動し、互いの結果ファイルは読まない。一方、投稿の手順は
その時点の既存コメントを引くため、**同じラウンドで先に投稿した担当の指摘が後続の担当へ
入る**。並列に起動することだけでは塞げない。

| 参照してよいか | 対象 |
| --- | --- |
| よい | 起動時に渡された既存コメントのスナップショット（前のラウンドの指摘） |
| よくない | 同じラウンドの他の担当の投稿・結果ファイル・進捗ログ |

**スナップショットは渡し続ける。** これは前のラウンドの指摘であって、同じラウンドの他の
担当の結果ではない。渡さないと、同じ指摘が毎ラウンド出る。

**同じ指摘が 2 者から出たことに意味があるのは、互いを見ていない場合だけである。**

## 走らせる順序

**取り込み（`read-result`）と判定（`judge`）の間に置く。** 判定が読むのは区分であり、
区分は統合・実行検証・反証の結果から決まる。**どれか 1 つでも走らせないと、区分が
決まる前の値のまま収束する。**

| 順 | 呼ぶもの | 何をするか |
| --- | --- | --- |
| 1 | `state.py verify-findings` | 重複の統合（1 段目）と、`suggested_check` の実行 |
| 2 | `critique.sh <担当> <PR> <ラウンド>` | 提案者以外を起動し、賛否を書かせる |
| 3 | `state.py collect-critiques` | 賛否を指摘へ結び、申告の重複を束ねる（2 段目） |

**実行検証が反証より前にある。** 反証を返す担当は、実行の結果を読んだうえで賛否を
決める。そのため `critique.sh` は `verification` をプロンプトへ載せる。**射影から
落とすと、担当は結果を見ないまま賛否を返す。** **統合の 1 段目も反証より前である。**
後にすると、束ねられる 2 件へ別々に反証が付き、どちらの値を採るかという判断が増える。

**経路を通り切ったラウンドだけへ印を残す**（`evidence_rounds`）。収束の判定はこの印で
母集合を決める。`review_findings` の有無では、取り込みだけを済ませた旧いラウンドと
区別できない（[04-contracts.md](04-contracts.md)）。

**申告による統合（2 段目）は次のラウンドへ回さない。** 回すと、同じ主張を 2 者が別の
本文で出した組が、どちらも `origin_runtimes` 1 者・`support` 0 件のまま
`insufficient_evidence` へ落ち、統合される前に収束する。

## 反証

**提案者以外の担当が、各指摘へ 1 つの値を返す。** `critique.sh` が起動し、
`state.py collect-critiques` が `finding_id` で突き合わせて指摘へ結ぶ。

| 値 | いつ使うか |
| --- | --- |
| `support` | 根拠を**独立に確認できた**。同じ結論へ自分でも到達できる |
| `refute` | 反例・仕様・コードから**誤りを示せる** |
| `insufficient_evidence` | 可能性はあるが立証できない |
| `duplicate` | 別の指摘と同一。相手の `finding_id` を `duplicate_of` へ書く |
| `out_of_scope` | この Pull Request の範囲・目的から外れる |

**`refute` の代わりに `duplicate` や `out_of_scope` を使わせない。** どちらも「指摘が
誤っている」という主張ではない。範囲外の指摘は、この Pull Request で直さないだけで、
課題としては残る。

**自分の指摘へは返さない。** 自己支持を数に入れると、1 者が出した指摘が常に 1 票を持つ。
統合された指摘では `origin_runtimes` に載る担当すべてが提案者である。

**担当はファイル名から採る。** 本文の申告を採ると、別の担当を名乗った値をそのまま
数えることになる。

**結び先の無い値は捨てず `unmatched_critiques` へ残す。** 黙って捨てると、反証が 0 件の
ラウンドと、結び先を誤ったラウンドが同じに見える。

## 実行検証

**実行してよいのは、起動した側が `--verify-command` で渡したコマンドだけである。**
渡されなければ実行検証を行わない。

| 守ること | なぜ |
| --- | --- |
| 照合はトークン単位 | 前方一致では `pytest` の指定に `pytest-danger` が当たる |
| メタ文字の一覧は持たない | 列挙から漏れた文字がそのまま通る。区切りは `shlex.split` でトークンの一部になる |
| 後ろは `-` で始まらないものだけ | `-c` や `-p` は任意の設定とプラグインを読み込ませる |
| 位置指定は `realpath` で解決 | `abspath` は symlink をたどらず、外を指すリンクを見逃す |
| 位置指定が無い実行はしない | 指摘とは無関係な失敗を拾う |
| `shell=False` で実行 | `$(...)` や `` ` `` を展開させない |

**失敗が再現である。** 指摘は「壊れている」という主張であるため、テストが失敗することが
再現にあたる。**「0 でない」を再現としない**（pytest は対象が無いときに 4、収集 0 件で
5 を返し、バグの再現と指摘の書き誤りが別の値で分かれる）。

**`not_run` を `not_reproduced` と同じにしない。** 実行できなかったことと、再現しなかった
ことは別である。

**束ねた組の全員の `suggested_check` を対象にする。** 代表の値だけを読むと、代表が手順を
書いていない組は、束ねられた側が実行できる手順を書いていても `not_run` のまま
`insufficient_evidence` へ落ちる。**どちらが先に取り込まれたかで採否が変わる。** 代表が
持つのは組の集約で、`reproduced` > `not_reproduced` > `not_run` の順で最初に当たった
1 件を採り、出所を `verification.finding_id` へ残す。**同じコマンドは 1 度しか実行しない。**

## 区分

**上から順に見て、最初に当たった区分を採る。**

| 順 | 区分 | 条件 |
| --- | --- | --- |
| 1 | `verified_blocking` | 再現した、かつ `major` 以上 |
| 2 | `verified_non_blocking` | 再現した、かつ `minor` 以下 |
| 3 | `rejected` | 再現しなかった、または `refute` が 1 件以上 |
| 4 | `needs_human_judgment` | 根拠を持ち、`major` 以上で、`support` が 1 件以上または `origin_runtimes` が 2 者以上 |
| 5 | `insufficient_evidence` | 上のいずれにも当たらない |

**実行で再現した指摘を先に採るのは、順序そのもので「実行の結果を担当の支持より先に
見る」を表すためである。** 順 3 を先に置くと、機械が再現した事実を担当の再評価が覆す。

**収束の判定が数えるのは、`verified_blocking` と `needs_human_judgment` の 2 つだけ**
である。棄却した指摘を数えると、そのぶんラウンドが増える。

**`needs_human_judgment` を人へのエスカレーションにしない。** 決めるのは修正の担当で、
その判断は却下の記録（`rejected_findings`）へ残る。
