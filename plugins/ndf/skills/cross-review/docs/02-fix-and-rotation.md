# 02: 修正・PR の巻き直し・終わり方

`ndf cross-review run` がラウンドの中で行う修正と、終わったときの結果を持つ。ラウンドの進み方は
[01-state-and-review.md](01-state-and-review.md) にある。

**目次:** [修正](#修正) / [送る](#送る) / [終わり方](#終わり方) / [PR に残す記録](#pr-に残す記録) / [PR を巻き直す](#pr-を巻き直す) / [駆動の外で直したとき](#駆動の外で直したとき)

## 修正

**メインは修正コードを書かない。** 判定が修正を要すると、`run` が修正担当（claude）を作業の worktree で起動する。
修正担当へ渡す指示は、収束の妨げになる重さの未解決の指摘（`id`・本文・重要度・場所と、相手役が書いた起きることの 1 文）と、まだ決めていない足すべき内容
（`--findings`）の一覧と、相手役と同じ「指摘の基準」（[01](01-state-and-review.md) の「指摘の基準」）である。`minor`・`nit` の
指摘と、必ず人の承認が要る操作に当たる指摘（基準 5 の `P`・`C` の番号）は渡さない。担当は指摘ごとに基準に当たるかを確かめ直し、当たれば直し、当たらなければ対象のファイルを変えずに当たらない
理由を添えて見送る。この PR の目的の外の指摘は見送り、`/ndf:out-of-scope` の判断に従う。承認の要らない起票だけを行って番号を
見送りの理由に書き、起票しないと決めたらその理由を書く。別のリポジトリへの書き込みなど承認が要るときは GitHub へ書かず、
書き先・題・本文の案を見送りの理由に書いて呼び出し元へ返す（修正担当は人に問えない）。直したら
コミットする（push しない）。返信と resolve は `run` が行う（下の「PR に残す記録」）ので、担当は GitHub へ書かない。
終えたら修正の結果ファイル（`--state-dir` の `fix-pr<元の番号>-result.json`）へ次の形を書く。

```json
{"pr": 123, "commit": "<最後のコミット>", "findings": [{"id": "r1-1", "outcome": "fixed", "reason": null}, {"id": "r1-2", "outcome": "deferred", "reason": "<見送った理由>"}]}
```

`run` は結果ファイルを読んでジャーナルの指摘ごとの終わり方へ写し、状態ファイルのラウンドへ修正の記録（`commit`・`reported`・
`fixed`）を書いてから、結果ファイルを `-round<n>` の名前へ移す（次の起動が残りと読み違えない）。

| 起きたこと | 扱い |
| --- | --- |
| 修正担当が結果ファイルを書かなかった | `warnings` に載せ、そのラウンドを `errored` で終える。次の起動で修正担当をもう一度起動する |
| 結果ファイルの `pr` が元の番号とも今の番号とも合わない・読めない | 結果ファイルを `-mismatch-round<n>` へ退避し、`errored` で終える |
| 担当が DONE で終わらなかった（タイムアウトなど）が結果ファイルはある | 読み込む（直した・見送ったを失わない） |
| 続けようとした会話が見つからなかった（会話の記録が消えた・アカウントを切り替えた） | 同じラウンドで新しい会話の修正担当を 1 度だけ起動し直す（出力は `round<n>-fix-new.*`）。起動し直しも結果を書かなければ上の「結果ファイルを書かなかった」と同じ |

**修正担当の会話を続けるのは、実行者のメインディレクトリの `.ndf/review.json` に `"fixer_sessions": true` を書いたリポジトリだけである**
（[ndf-settings](../../../docs/contracts/ndf-settings.md) の `.ndf/review.json`）。書かない・偽なら、どのラウンドの修正担当も今のとおり
会話を残さずに起動する。真なら、同じ `run` の 2 ラウンド目からの修正担当は前のラウンドの修正担当の会話を続け、読んだファイルを
探し直さない。指示はラウンドごとに同じ形で渡す（前の指示を覚えていることを当てにしない）。会話の ID は `run` がその起動の中だけで
持ち、状態ファイルに書かない。次のどれかに当たると新しい会話で始める。

| 新しい会話にする条件 | `process` の修正担当の行の後ろ |
| --- | --- |
| その起動で修正担当を起動するのが初めて（1 ラウンド目・別の起動からの再開の最初のラウンド） | `（新しい会話: その起動で初めて）` |
| 前の修正担当が DONE で終わらなかった・結果をマージできなかった | `（新しい会話: 前の修正担当が正常に終わらなかった）`・`（新しい会話: 前の修正の結果をマージできなかった）` |
| 前の会話で自動の要約が起きた・文脈の大きさを読めない | `（新しい会話: 前の会話で自動の要約が起きた）`・`（新しい会話: 前の会話の文脈を読めない）` |
| 前の会話の最後の文脈 + その起動の 1 ラウンドの増分の最大 + 余白（`contracts/limits/cross-review.fixer.resume-margin.json`）がモデルの文脈の窓を超える | `（新しい会話: 前の会話の文脈が窓に収まらない）` |

続けたラウンドの行の後ろは `（会話を続けた）`、保存しない設定では `（新しい会話: 会話を保存しない設定）` である。真のときは claude の
設定の保存先に会話の記録が残る。値によらず、状態の保存先の `round<n>-fix.out` には修正担当が読んだファイルの中身と未公開の指摘が残る。

## 送る

修正のコミットは `run` が head ブランチへ送る。拒まれたら origin をマージして 1 回だけ送り直す。マージで衝突したら取り消して
止める。送れなかったときは、そのラウンドで直したとした指摘を未解決へ戻し（PR に届いていない）、`errored` で終える。
MVV の根拠の記述の誤りは PR に届いたコミットで確かめたものだけを指摘にし、送れなかった手元のコミットに誤りがあれば、中身を
PR に載せずに `mvv_unresolved` で止める。次の起動は、始めに送れなかったコミットを送り直してから進む。
送る範囲は `HEAD` までのすべてで、修正担当が結果を書かずに残したコミットも含む。最後のラウンドに修正の記録が無い（修正担当が結果を書かずに終わった）ときは、
始めの送り直しをせず、残ったコミットは次に修正を送るときに一緒に送る。送るだけを打つときは
`ndf cross-review push-fix <worktree> --branch <B> [--commit <C>]` を使う。

## 終わり方

`run` は終わると `--state-dir` へ要約（`summary.json`）を書き、終わり方から結果 JSON を出す。同じ判断を要約から出し直すときは
`ndf cross-review finish --summary <summary.json> [--findings <F>]` を打つ（読むだけ）。

| 終わり方（`final`） | 欠け（`gaps`） | 結果 |
| --- | --- | --- |
| `converged`・`max_rounds`・`oscillating`・`errored` | 0 件 | `status: ok`。上限・振動・誤りで終わったときは、そう決めた理由が `decisions` に載る |
| `converged`・`max_rounds`・`oscillating`・`errored` | 収束の妨げになる重さの未解決の指摘・扱わなかった足すべき内容・理由の無い見送りが 1 件以上 | `status: stopped`・`incomplete`（`gaps` つき）。プランは `incomplete` のルートへ進み、`gaps` は承認資料の「未確認の点」になる |
| `converged`・`max_rounds`・`oscillating`・`errored` | MVV に反する指摘か MVV の根拠の行の誤りの未解決・根拠の行を最後のコミットで確かめられない・PR に届いていない手元のコミットの根拠の行の誤り | `status: stopped`・`mvv_unresolved`。次の工程へ進まずに人へ戻す。欠けは最上位の `gaps` でなく `outputs.gaps` に載る |
| `incomplete_reviewers`（起動し直しても読めない相手役がいた） | どれでも | `status: stopped`・`work_stopped`。相手役ごとの理由は `warnings`。直して同じコマンドを打ち直せば次のラウンドから続く |
| `errored` で 1 ラウンドも終わらなかった | — | `status: stopped`・`work_stopped` |
| どれでも（承認ゲートの判定に要るレビューの記録の行 `redline`・`deferred` を書けなかった） | どれでも | `status: stopped`・`mvv_record_failed`。記録が無いと承認ゲートが PR を省けるため、ほかの行より優先する。本来の終わり方は `summary`、原因は状態ファイルの `mvv_record_error` に載る。記録の保存先を直して同じコマンドを打ち直す |

`minor`・`nit` の未解決の指摘は欠けにしない。`summary` に「軽い指摘 <件数>」と載る。必ず人の承認が要る操作に当たる指摘も欠けにせず、「人の承認を待つ <件数>」と載る。

結果 JSON の `items` は指摘ごとの `id` と `outcome`、`metrics` は `rounds`（終えたラウンドの数）と `findings`（指摘の数）、
`process` は起動ごとの過程（相手役ごとの指摘の数・修正担当・push）である。

マージ先のブランチに承認済みの MVV があれば、`outputs.mvv` に MVV の確かめの結果が載る。載るのは、今の MVV で判定した指摘だけである。

| キー | 中身 |
| --- | --- |
| `version`・`sha256`・`head` | 確かめた MVV のバージョンと本文の sha256、PR に届いた最後のコミット |
| `findings` | Mission・Vision・Value に反する指摘のうち、直したものと未解決のもの（`id`・`item`（反する項目）・`by`・`outcome`） |
| `disputed` | 反する指摘のうち、修正担当が反しないとして見送ったもの（`id`・`item`・`reason`） |
| `redlines` | 必ず人の承認が要る操作に当たる指摘（`id`・`item`・`text`） |
| `citations` | 根拠の行の誤り（`id`・`path`・`line`・`cited`・`unknown`・`outcome`） |

`reason`・`text`・`path`・`cited`・`unknown` は、記録のコメントと同じ方法で秘密や非公開の参照先を伏せた値である。参照先の公開範囲を
GitHub に問い合わせられなければ、固定の文「（参照先の公開範囲を確かめられず伏せた）」になり、`warnings` に載る。

指摘ごとの終わり方は MVV の記録（`mvv-validation.jsonl`）にも残る。`disputed` は MVV の改訂の兆候として数える
（[project-mvv.md](../../development-workflow/references/project-mvv.md#改訂の兆候)）。

## PR に残す記録

`run` は終わるときに、PR へ次を書く（#3939）。書けなければ終わり方は変えず `warnings` に残すので、
`ndf cross-review report --state-dir <D> --pr <N>` で書き足す。

- 収束の妨げになる重さの指摘をインラインのスレッドにする。相手役が返した `path`・`line` があればそこに付け、無ければ
  `section` のパスと本文の先頭の `<名前>:<行>` から付ける。`minor`・`nit` の指摘と、PR の差分に無いファイルの指摘はスレッドにしない
- 行の分かる指摘は、付けるコミット（指摘のラウンドの head）ごとに 1 つのレビューでまとめて書く（#4016）。レビューが行の
  位置で断られた組だけを 1 件ずつのスレッドに分け直す。行の分からない指摘はファイルに付ける
- この実行で直した・見送った指摘は、閉じた理由（修正のコミット・見送った理由）を最初のコメントへ入れて返信を省き、resolve する。
  前の実行のスレッドを持つ指摘が閉じたときだけ、そのスレッドへ理由を返信して resolve する。未解決の指摘のスレッドは開いたまま残す
  （次の実行が引き継ぐ。[01](01-state-and-review.md) の「残った指摘を引き継ぐ」）
- 最初のコメントと返信には指摘の発生の値（`<!-- ndf-occurrence: <値> -->`）を入れる。書く前に PR のスレッドを読み、自分が
  書いた同じ番号・同じ発生の値のスレッドがあれば書かずに状態ファイルへ戻す（打ち直しで二重に書かない。再発した指摘は
  新しい値を持つので、resolve 済みの古いスレッドへ結び付けない）。同じ PR への公開は 1 つずつ行う
- ラウンドと修正の記録・指摘ごとの重要度・場所・終わり方を 1 つのコメントに書く（次の起動は同じコメントを書き換える）。
  コメントの末尾には、未解決の重い指摘の一覧（スレッドの id と、MVV に反するという判定を含む）を HTML のコメント
  `<!-- ndf:cross-review-open [...] -->` で埋める（スレッドにならなかった指摘と、MVV の判定を次の実行が引き継ぐ）。必ず人の承認が要る
  操作に当たる指摘と、NDF が機械で確かめて作った指摘は、重さによらず載せる

書く操作が GitHub の二次レート制限（403・429 で `secondary rate limit`）に当たったら、GitHub が返した秒を待って打ち直す。
GitHub が秒を返さなければ、`contracts/limits/cross-review.secondary-rate-limit.json` の `interval` から `factor` 倍ずつ
延ばし（60・120・240 秒。`max_interval` で頭打ち）、回数の上限は同じ行の `attempts`。待ちの終わりはマシン全体の書き込みの
順番の記録へ知らせ、ほかのプロセスの書き込みも待たせる。書き込みどうしの間隔はマシン全体で `github.write-spacing`、
内容を作る書き込み（スレッド・レビュー・コメントの作成）は、マシン全体で 1 分と 1 時間のウィンドウの件数を数え、
上限（`github.content-window.minute`・`github.content-window.hour`）に達したときだけウィンドウが空くまで待つ。

## PR を巻き直す

`run` は PR を巻き直さない。上限まで回して収束しない PR を閉じて出し直すときは、メインが手で行う。

1. 新しい PR を作る（`gh pr create --base <マージ先> --head <ブランチ> --title <題> --body-file <本文>`）。title と body は
   cross-review の経緯でなく、今の差分と実装から書く
2. 旧い PR を閉じる（`gh pr close <旧い番号> --comment "<新しい PR の URL> へ出し直した"`）
3. 状態ファイルへ今の番号を記録する（`ndf cross-review state-file --state-dir <D> --pr <元の番号> --current <新しい番号>`）

状態ファイルと修正の結果ファイルは元の番号のまま残り、`--pr` に今の番号を渡しても元の状態ファイルを引く。
記録のコメントとスレッドは PR ごとに分かれる。次の `run`・`report` は旧い PR の記録を `report_earlier` へ移し、新しい PR へ
記録のコメントと未解決の指摘のスレッドを書き直す（旧い PR のコメントは書き換えない）。

## 駆動の外で直したとき

`run` が止まった後に残った修正の結果ファイルを読み込むときは、`ndf cross-review fix-gate --state-dir <D> --pr <N>` で要否を
確かめ、`next` に返った `ndf cross-review merge-fix --state-dir <D> --pr <N> --file <結果ファイル>` を打つ。`run` と同じ形で
ジャーナルへ写す。ホストが自分で直したときも、同じ形の結果ファイルを書いて `merge-fix` を通す（送るのは `push-fix`）。
