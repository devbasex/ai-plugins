# 判断を求める前に材料を示す

**利用者に判断を求めるときは、先に判断の材料を示す。** 選択肢だけを並べて聞くと、利用者は
何が起きたかを知らないまま選ぶことになるか、聞き返して材料を引き出すことになる。どちらも、
材料を持っている側が先に出せば起きない。

## 当たる場面

**判断・承認・選択を利用者に求めるすべての場面**に当たる。承認の関門に限らない。

| 場面 | 例 |
| --- | --- |
| 作業の途中で方針を決めてもらう | 試行の結果を受けて、ライブラリへ置き換えるかを決める |
| 下位の担当が「判断が要る」で止まった | 実装の担当が、設計に無い前提に当たって止まった |
| 承認の関門 | 設計のマージ・本番への配布の前 |
| 確認の質問 | 範囲・優先度・読み方が 2 通り以上ある |

**材料から 1 つに決まるなら聞かない。** 慣例の既定があるもの、コードや記録を読めば決まるものは、
決めて進み、決めたことを報告に書く。

## 示すもの

**質問の前の応答の本文に、次の 5 つを書く。**

| # | 項目 | 書くこと |
| ---: | --- | --- |
| 1 | 何を決めるか | 問いを 1 文で。決めないと何が止まっているか |
| 2 | 分かったこと | 調べた事実。数値・出力・再現の結果など、確かめたものだけ |
| 3 | 根拠の場所 | ファイルのパス・Pull Request や課題の URL・実行したコマンド。利用者が自分で開けるように生のまま書く |
| 4 | 選択肢ごとに何が変わるか | 得るもの・失うもの・後に残る作業・取り消せるか。選択肢どうしを同じ観点で並べる |
| 5 | 推奨とその理由 | どれを勧めるか、なぜか。勧めないなら勧めない理由。まだ確かめていないことと、それで推奨が変わりうるか |

**推奨は理由と一緒に書く。** 選択肢に「推奨」の印を付けるだけでは、利用者は印の根拠を確かめ
られない。

**下位の担当の報告は、そのまま渡さない。** 報告の要点を自分で確かめ、上の 5 つへ組み直す。
報告が複数あるときは、共通の原因と個別の問題を分けて書く。

## 置き場所

**材料は質問の本文の外、その直前の応答に書く。** 質問の選択肢の説明は、その選択肢を 1 行で
区別できる長さにとどめる。材料を選択肢の説明へ押し込むと、選ぶつもりの無い選択肢の説明は
読まれない。

**1 回の質問に載せる問いは、材料を示し終えたものだけにする。** 別の問いの材料がまだ揃って
いないなら、揃ってから聞く。

## しないこと

| しないこと | 起きること |
| --- | --- |
| 選択肢だけを並べて聞く | 利用者が「どれがよいのか分からない」と聞き返す |
| 根拠の場所を書かない | 利用者が確かめる手段を持たず、要約を信じるしかない |
| 聞き返されてから説明する | 材料を持つ側が出し惜しんだ分だけ、往復が増える |
| 推奨の印だけを付ける | 印の理由を確かめられず、承認が形だけになる |

## 例

**悪い形**（材料が無い）:

```text
（質問）ライブラリ X へ置き換えますか？
  - 置き換える（推奨）: 後で置き換える
  - 置き換えない: 今のまま残す
```

**良い形**（質問の前の応答）:

```text
何を決めるか: 今の呼び出しの包みを、ライブラリ X へ置き換えるか。決まるまで移行の計画を組めない。

分かったこと:
- X の既定のままだと費用が 2.77 倍（3 回の中央値）。原因は X が追加の呼び出しを 1 回足すこと
- 環境変数 Y を渡すと 1.01 倍に戻る。ただし Y は X の文書に無い
- 置き換えで消える自作は約 100 行。上限の扱いなどは残る

根拠: <測定の記録のパス> / <試行の Pull Request の URL>

選択肢:
- 置き換える: 自作が約 100 行減る。Y の名前が変わると費用が黙って 3 倍に戻るため、回帰テストで見張る必要がある
- 置き換えない: 今の文書化された契約のまま。自作の 100 行が残る

推奨: 置き換えない。減る自作が小さく、費用を守る手段が文書に無い値だけのため。
未確認: Y を公式に扱う予定があるか（あれば推奨が変わる）。
```
