# 決定の記録

設計で選んだ結論と、その理由を残す。**後から同じ検討を繰り返さないためである。** 理由が
残っていないと、次に読む人は採らなかった案を再び検討する。

## 書き方

決定 1 件を 1 つの小見出しにする。**見出しに目的と結論を置き、本文を 質問 → 選んだ案 → 理由 → 採らなかった案 → 代償 → 根拠 の順に書く。**
承認する人は見出しで何を決めたかをつかみ、本文で、何を決める必要があり、何を退け、何を引き受けたかを読む。見出しの形は
[design-writing.md の「承認する人が読む欄」](design-writing.md#承認する人が読む欄) の「決定の見出し」に従う。

```markdown
### 決定 1: {何のために}、{何を決めたか}

- 質問: {何を決める必要があったか。1〜2 文}
- 選んだ案: {何をどうするか}
- 理由: {なぜこの案を選んだか}
- 採らなかった案: {案}（{採らなかった理由}）
- 代償: {この案で引き受けること・悪くなること}
- 根拠: {MVV の項目}（MVV バージョン {N}）。{外部の調査の番号など}
```

| 行 | 書くこと |
| --- | --- |
| 質問 | 決める前に分かれていた選択。決定の見出しが回答になる質問を書く |
| 選んだ案 | 何をどうするか。変える前の形との違いが読める粒度で書く |
| 理由 | なぜ選んだ案にしたか。どの制約・事実が決め手かを書く。MVV の項目の番号は根拠の行に書き、ここは番号を知らない読み手にも分かる文にする。採らなかった案の行より前に置く |
| 採らなかった案 | 案 1 つにつき 1 行。行は `採らなかった案:` で始め、括弧に理由を添える（読み手役の言い直しと設計に出るテストの検査が、この書き出しで行を読む）。検査はこの行から次の見出しまでを採らなかった案として読み、中のテストの名前を拾わないので、作るテストの名前は選んだ案の行に書く。比べた案が 1 つしか無い決定は、決定として残さない（下の「何を決定として残すか」） |
| 代償 | 選んだ案で引き受けること。無いと言える決定は、比べた案の重さが釣り合っていないので、質問を見直す |
| 根拠 | 最後の行。形と、`{N}` に書くバージョンは下の「根拠の行」。外部の一次情報は外部の調査の表の番号（`STD1` など）で添える |

例:

```markdown
### 決定 5: 合わない対象へ同じ手法が選ばれないよう、時系列を保護する手法に既定を置かない

- 質問: 時系列を保護する手法（追記だけの表・履歴の表・イベントの記録）に既定を置くか
- 選んだ案: 既定を置かず、条件を課す。状態を上書きして過去を失う構造を選んだ場合は、失ってよい理由を残す
- 理由: どの手法が合うかは対象の性質で決まり、条件を課せば合う手法を選んだうえで過去を失う構造だけを止められる
- 採らなかった案: 追記だけの表を既定にする（どれを採るかは対象の性質で変わり、既定を置くと合わない対象へも同じ手法が選ばれる）
- 代償: 設計のたびに手法を選ぶ手間が残る
- 根拠: Value 5（MVV バージョン {N}）
```

## 作り方と比べた候補

**機能をどう得るかを選んだ決定には、代償の行と根拠の行の間に `作り方:` と `比べた候補:` の 2 行を置く。**
設計や手順の選び方の決定には書かない。

```markdown
### 決定 3: 認可の判定を設定で読めるよう、ポリシーの評価に既存のエンジンを使う

- 質問: {何を決める必要があったか}
- 選んだ案: {何をどうするか}
- 理由: {なぜこの案を選んだか}
- 採らなかった案: {案}（{採らなかった理由}）
- 代償: {この案で引き受けること}
- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB1 / LIB2 / STD1
- 根拠: Value 7（MVV バージョン {N}）
```

| 行 | 書くこと |
| --- | --- |
| `作り方:` | 「自前で作る」「ライブラリやサービスを使う」「標準に倣う」のどれか。組み合わせるときは `・` で並べる（標準を自前で実装する決定は `自前で作る・標準に倣う`） |
| `比べた候補:` | 外部の調査の表の番号（`STD<数>` / `PRD<数>` / `LIB<数>`）を `/` か `・` で並べる。採った候補と採らなかった候補の両方を含める |

**作り方に「自前で作る」を含む決定には、比べた候補を必ず 1 つ以上並べる。** 外部の調査を `省く:` で省いた
課題の決定は除く。番号は同じ課題の設計文書の外部の調査の表にあるものだけを使う。外部の調査の手順は
[external-survey.md](external-survey.md) にあり、`design` の手順 5 で書いた側が 2 行を確かめる。

## 人へ委ねない

**選択の分かれ目は設計者が決め、質問・選んだ案・理由・採らなかった案・代償・根拠で書く。** 決定の記録の標準（ADR・MADR）は結論を書く形だけを
持ち、決めないまま他者へ委ねる形を持たない。`設計承認ゲートで利用者が決める` の形で判断を残すと、MVV 判定が
判定できずに人を待つ。

| 場合 | 書く場所 |
| --- | --- |
| 選択肢があり、材料から選べる | 決定の記録（質問・選んだ案・理由・採らなかった案・代償・根拠） |
| 材料が無く、デプロイの前に確かめられない | 「未確認のまま残ること」へ事実として（何が分からず、いつ・何で分かるか）。選択肢を並べない |
| レッドライン（`C<番号>` / `P<番号>` / `R<番号>`）に当たる | 「人へ残す判断」の表へ、当たる番号となぜ当たるかの 1 行を添えて。番号を挙げられない判断はここへ置かず、設計者が決める |

**要求の「起票者の推定」は、扱い（受け入れ条件・前提・含まない・採らない）が書かれていれば、設計者が決めた判断として読む。**
推定であることだけを理由に人へ残さない。設計承認ゲートを MVV 判定が省いたときは、その判定の記録が推定を確かめた記録になる。

`design` の手順 5 で、「決定の記録」「未確認のまま残ること」「人へ残す判断」のセクションに、番号を名指さずに判断の主語を
人に置く行と、「人へ残す判断」の表で番号か「なぜ当たるか」を欠く行が無いことを確かめる。

## 根拠の行

決定 1 件ごとに、最後の行（`- 根拠:`）へ根拠にした MVV の項目を書く。形は「根拠: <項目>（MVV バージョン {N}）」である。

**`{N}` には、ベースブランチで承認された今のバージョンを書く。** 起動指示の MVV の欄のバージョンか、次のコマンドの結果の
`outputs.mvv.version` である。この文書の例や、前に書かれた設計文書の番号を写さない。引ける項目は同じ結果の `outputs.mvv.items` にある。

```bash
ndf records mvv current --base <マージ先のブランチ>
```

| 場合 | 根拠の行 |
| --- | --- |
| プロジェクト MVV の項目に当たる | `根拠: Value 6 / P1（MVV バージョン {N}）` |
| 項目の文を引く | `根拠: Value 7「<引用文>」・Value 11「<引用文>」（MVV バージョン {N}）`（項目は ` / ` か `・` で区切る。引用文は項目の番号の直後に `「` と `」` で囲む） |
| 外部の調査の番号も添える | `根拠: Value 6（MVV バージョン {N}）。STD1`（番号はバージョンの括弧の後ろに置く） |
| スプリント MVV もある | `根拠: Value 6 / スプリント Value 4（MVV バージョン {N}・スプリント MVV 3f9a1c2e）`（スプリント MVV の項目は頭に「スプリント」、括弧に sha256 の先頭 8 文字） |
| 当たる項目が無い | `根拠: 根拠なし（MVV バージョン {N}）` |
| 承認済みの MVV が無い | `（MVV なし）` |

**承認済みの MVV があるリポジトリでは、`ndf cross-review run` が Pull Request で足した根拠の行を確かめる。** 次の行は誤りとして
修正担当へ渡り、直るまで収束しない（見送れない）。

- 今のバージョンと違うバージョンを書いた行
- そのバージョンに無い項目を書いた行
- バージョンを読み取れない行。「MVV ver 11」のように形を変えた行、`（MVV なし）` と書いた行、`### 決定 N` の見出しの下でバージョンを
  書かなかった `根拠:` の行が当たる

コードブロックの中の行は確かめない。

MVV に反する疑いのある決定は記録に書かず、人へ戻す（[project-mvv.md の「工程での読み方」](../../development-workflow/references/project-mvv.md#工程での読み方)）。

## 置く場所

**設計文書の 1 セクションに置く。** 決定 1 件ごとに独立したファイルを作らない。設計と決定が別の
場所にあると、設計を読む人が理由へたどり着けない。

決定の数が増えて 1 ファイルが 500 行を超えた場合は、決定のセクションだけを別ファイルへ分ける
（`document-style` の分量の基準）。分けたファイルの形は次の 1 つにする。

| 書くこと | 形 |
| --- | --- |
| 分けたファイルの名前 | `issue-<番号>-design-decisions.md`（設計文書と同じ場所） |
| 分けたファイルの中身 | H1 は自由。`## 決定の記録` のセクションの下に、決定ごとに `### 決定 N: …` を置く |
| 設計文書に残すセクション | `## 決定の記録` のセクションに、分けたファイルの名前を示す 1 文だけを置く |

設計 PR の本文の「決めたこと」には、この形の `### 決定 N: …` の見出しを写す。分けたファイルに決定の見出しが無いと
写せないため、分けたときも見出しを必ず置く。

## 何を決定として残すか

| 残す | 残さない |
| --- | --- |
| 複数の選択肢があり、どれかを選んだこと | 選択肢が 1 つしかなかったこと |
| 一般的な作り方から外れた選び方 | 規約や既存の実装に従っただけのこと |
| 後から「なぜこうなっているのか」と問われる形 | 実装の詳細（コードを読めば分かること） |

**採らなかった案を比較のためだけに並べない。** 採否と理由として書く（`document-style` の
「検討過程の痕跡を残さない」）。

## 書かないこと

| 書かないもの | 理由 |
| --- | --- |
| 「案 A」「パターン 1」などの検討時のラベル | 会話の中でしか通じない |
| 「指摘を受けて変更した」などの経緯 | 変更の理由は Pull Request と履歴が持つ |
| 選択を否定する強い語 | 採否と理由で足りる（`document-style` のルール 5） |
