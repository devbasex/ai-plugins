# 決定の記録

設計で選んだ結論と、その理由を残す。**後から同じ検討を繰り返さないためである。** 理由が
残っていないと、次に読む人は採らなかった案を再び検討する。

## 書き方

決定 1 件を 1 つの小見出しにする。**結論を先頭に置き、検討の過程を後ろへ回す。** 急ぐ読み手が
先頭だけで判断できる。見出しの形は [design-template.md の「承認する人が読む欄」](design-template.md#承認する人が読む欄) の
「決定の見出し」に従う。

```markdown
### 決定 1: {何のために}、{何を決めたか}

{なぜその選択にしたか。2〜4 文}

{採らなかった案と、採らなかった理由。1〜2 文}

根拠: {MVV の項目}（MVV 版 {N}）
```

例:

```markdown
### 決定 5: 合わない対象へ同じ手法が選ばれないよう、時系列を保護する手法に既定を置かない

どれを採るかは対象の性質で変わる。既定を置くと、合わない対象へも同じ手法が選ばれる。
代わりに条件を課す。状態を上書きして過去を失う構造を選んだ場合は、失ってよい理由を残す。

根拠: Value 5（MVV 版 1）
```

## 根拠の行

決定 1 件ごとに、最後の行へ根拠にした MVV の項目を書く。形は見送りの返信と同じ「根拠: <項目>（MVV 版 N）」である。

| 場合 | 根拠の行 |
| --- | --- |
| プロジェクト MVV の項目に当たる | `根拠: Value 6 / P1（MVV 版 1）` |
| スプリント MVV もある | `根拠: Value 6 / スプリント Value 4（MVV 版 1・スプリント MVV 3f9a1c2e）`（スプリント MVV の項目は頭に「スプリント」、括弧に sha256 の先頭 8 文字） |
| 当たる項目が無い | `根拠: 根拠なし（MVV 版 1）` |
| 承認済みの MVV が無い | `（MVV なし）` |

MVV に反する疑いのある決定は記録に書かず、人へ戻す（`development-workflow` の `references/project-mvv.md` の「工程での読み方」）。

## 置き場所

**設計文書の 1 節に置く。** 決定 1 件ごとに独立したファイルを作らない。設計と決定が別の
場所にあると、設計を読む人が理由へたどり着けない。

決定の数が増えて 1 ファイルが 500 行を超えた場合は、決定の節だけを別ファイルへ分ける
（`markdown-writing` の分量の基準）。分けたファイルの形は次の 1 つにする。

| 書くこと | 形 |
| --- | --- |
| 分けたファイルの名前 | `issue-<番号>-design-decisions.md`（設計文書と同じ場所） |
| 分けたファイルの中身 | H1 は自由。`## 決定の記録` の節の下に、決定ごとに `### 決定 N: …` を置く |
| 設計文書に残す節 | `## 決定の記録` の節に、分けたファイルの名前を示す 1 文だけを置く |

`pr-body-decisions.sh` はこの形の `### 決定 N: …` を設計 PR の本文の「決めたこと」へ写す。分けたファイルに
決定の見出しが無いと、`check` と `sync` はそのファイルのパスを出して終了コード 1 で止まる。

## 何を決定として残すか

| 残す | 残さない |
| --- | --- |
| 複数の選択肢があり、どれかを選んだこと | 選択肢が 1 つしかなかったこと |
| 一般的な作り方から外れた選び方 | 規約や既存の実装に従っただけのこと |
| 後から「なぜこうなっているのか」と問われる形 | 実装の詳細（コードを読めば分かること） |

**採らなかった案を比較のためだけに並べない。** 採否と理由として書く（`markdown-writing` の
「検討過程の痕跡を残さない」）。

## 書かないこと

| 書かないもの | 理由 |
| --- | --- |
| 「案 A」「パターン 1」などの検討時のラベル | 会話の中でしか通じない |
| 「指摘を受けて変更した」などの経緯 | 変更の理由は Pull Request と履歴が持つ |
| 選択を否定する強い語 | 採否と理由で足りる（`markdown-writing` のルール 5） |
