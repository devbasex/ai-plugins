# 呼び出される約束

**API・イベント・コマンドの約束を追加・変更する変更でだけ読む。**

## 契約を先に書く

実装を始める前に仕様記述を完成させ、関係者が確認する。**実装しながら形が決まる状態にしない。**

```text
1. 仕様記述を書き、関係者が確認する
2. その記述から応答を返す仮の実装を立て、呼ぶ側と応じる側を並行して進める
3. 契約に対する試験を、実装より先に書く
```

3 の契約に対する試験は `tdd-cycle` が扱う。この Skill が担うのは 1 までである。

## 書式

**API は OpenAPI で書く。** 現行版は JSON Schema の系列と整合が取れており、条件付きの検証や
組み合わせの表現がそのまま書ける。

整形済みの説明文書ではなく**機械可読な記述を置く**。仕様記述があれば、経路・検証・型定義を
最初から正しく生成できる。無い場合は、経路や応答の形を推測することになる。

API 以外の呼び出される約束（イベント・コマンド）に定まった標準は無い。設計文書へ次の形で書く。

| 項目 | 書くこと |
| --- | --- |
| 名前 | 何を呼ぶか |
| 入力 | 受け取る値と、その型・必須かどうか |
| 出力 | 返す値。成功と失敗のそれぞれ |
| 失敗の形 | どういうときに何を返すか。終了コードや状態コード |
| 互換性 | 既存の呼び出し側が壊れるか。壊れる場合の移行 |

## 設計文書に書くこと

仕様記述そのものは別ファイルに置き、設計文書からは次を書く。

| 項目 | 内容 |
| --- | --- |
| 置き場所 | 仕様記述のファイルの場所 |
| 変わる約束 | 追加・変更・削除する経路と、その理由 |
| 互換性の扱い | 既存の呼び出し側への影響。段階的に移す場合はその順序 |
| 検査の手段 | 記述が規約を満たすことを、どのコマンドで確かめるか |

## 検査と生成

| 用途 | 道具 |
| --- | --- |
| 記述の検査 | Spectral（規則を設定して命名・記述漏れ・構造を検査する） |
| 仮の実装 | Prism / WireMock（記述から応答を返す） |
| 雛形の生成 | OpenAPI Generator（サーバ側と各言語の呼び出し側） |
| 閲覧 | Swagger UI / Redoc / Scalar |

**採用は各リポジトリの判断による。** 記述の標準と、その検査を担う 1 つの道具までを設計で
決め、それ以外は各リポジトリに委ねる。検査を入れたリポジトリでは、そのコマンドが
`quality-gates` の証跡になる。
