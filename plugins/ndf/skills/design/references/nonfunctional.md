# 非機能の実現方式

**仕様に非機能の条件があるときだけ読む。**

要求側（`requirements-design` の
`references/nonfunctional-requirements.md`）が決めた条件に対して、**どう実現するか**を書く。

**要求側に条件が無い項目は書かない。** 書く根拠が無く、実装の判断を先取りすることになる。

## 大項目ごとに決めること

| 大項目 | 設計で決めること |
| --- | --- |
| 可用性 | 冗長化の構成、停止を伴う作業の手順、復旧の経路 |
| 性能・拡張性 | 処理の分割、キャッシュ、索引、増加への備え |
| 運用・保守性 | 監視の対象と通知先、記録の形式と保存先、障害時の切り分けの手段 |
| 移行性 | 移行の順序、切り戻しの手段、旧版との並走 |
| セキュリティ | 認証認可の置き場所、通信と保存の保護、秘密情報の受け渡し |
| システム環境 | 動作環境、依存する実行基盤、資源の制約 |

## 非機能設計表の書き方

**要求の条件と、実現方式と、確かめ方を 1 行に並べる。** 3 つが揃ってはじめて、その条件を
満たしたと言えるかが判定できる。

```markdown
| 大項目 | 要求の条件 | 実現方式 | 確かめ方 |
| --- | --- | --- | --- |
| 性能・拡張性 | 1 万件で一覧の初期表示が 2 秒以内 | 一覧の取得を 50 件ずつに区切り、絞り込みの列へ索引を張る | 1 万件を投入して初期表示を測る |
| セキュリティ | 一般利用者は他人の下書きを取得できない | 取得の入口で所有者を照合し、一致しなければ 403 を返す | 他人の識別子で取得し、403 と応答本文を見る |
```

- **実現方式は、選んだものを書く。** 候補を並べるのは決定の記録の役目である
- **確かめ方は `quality-gates` の証跡になる。** 手段が書けない条件は、満たしたと言えない
- 要求の条件の文言は、仕様から写す。言い換えると対応が追えなくなる

## 実現方式が要求を満たさないとき

**条件を下げる判断は設計の側で行わない。** 要求へ戻し、条件を書き換えたうえで設計をやり直す。
書き換えた事実は仕様に残す（`requirements-design` の「変更の途中で要求が変わったとき」）。

**設計の時点で満たせないと分かることに意味がある。** 実装が終わってから分かるより安い。

## `operation` での扱い

**`operation` では非機能設計表が無条件の成果物である。** このモードは必ず外部の系の状態を
変えるため、可用性・セキュリティ・移行性・システム環境のいずれかに必ず当たる。

| 大項目 | `operation` で当たる例 |
| --- | --- |
| 可用性 | 反映の最中に止まる経路があるか。止まる時間 |
| セキュリティ | 誰の権限で実行するか。実行後に誰が何をできるようになるか |
| 移行性 | 戻す手段。戻せない単位 |
| システム環境 | 実行する場所と、そこから届く先 |

**戻す手段は `operation-run.md` が記録の形を持つ。** ここで書くのは、**その構成を選んだ理由**
である。**同じことを 2 か所へ書かない。**

## 設計文書に書くこと

| 項目 | 内容 |
| --- | --- |
| 非機能設計表 | 上の 4 列。要求側が書いた大項目の行だけを置く |
| 満たせない条件 | 要求へ戻した条件と、その理由（あれば） |

**要求側に条件が無い大項目の行は作らない。** 空の行は、書き忘れと意図的な省略を読み手が
区別できなくする。
