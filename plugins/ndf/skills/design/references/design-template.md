# 設計文書のテンプレート

セクションの並びは、文書の役割の表（`requirements-design` の [document-roles.md](../../requirements-design/references/document-roles.md) の「文書ごとの読み手と順序」の設計書の行）が決める。
承認する人が頭から読み、決定で立ち止まる順である。このテンプレートはその順に見出しを置き、書き方を添える。

**どのセクションも「必ず書く」か「当たるときだけ」のどちらかである。** 当たらないセクションは見出しごと消し、
「無し」「省く:」と書かない。空の見出しや「無し」の並びは、読み手に書くことの無いセクションを読ませるためである。
例外は「外部の調査」だけで、省くときも `省く: <理由>` の 1 行を残す（調べずに自前で作る決定を防ぐ `design` の手順 2 が、この 1 行を見るため）。

詳細設計を別のファイル（[detail-template.md](detail-template.md)）にするか、このテンプレートの「どこを変えるか」に畳むかは、下の「分量」が決める。

前の文書（要求仕様）にある事実は写さずにリンクで指す。識別子は普通の言葉の後ろに括弧で添える。

```markdown

（文書を省いたときだけ、`省いた文書: <文書>（<満たした条件の値>）` の行を 1 つずつ置く。条件は document-roles.md の「省いてよい文書と条件」）
```

## 承認する人が読む欄

設計承認ゲートで承認する人が問う項目（題・要約の段落・今の姿・解き方の全体像・決定の見出し・影響と危険）の書き方の SSOT はこのセクションである。
承認資料（`development-workflow` の `approval-request.md`）はこの欄を先頭に載せ、ほかの Skill はこのセクションを指す。
置く順は H1 → 要約の段落 → 今の姿 → 文脈と制約 → 解き方の全体像 → 決定の記録 → 影響と危険で、承認する人は最初の数行で課題と解き方をつかみ、
続けて変える前の姿と、何を選んで何を採らなかったかを読む。`legacy-refactor` の設計文書は、下の「`legacy-refactor` の書き方」の欄を書く。

| 欄 | 書くこと | 書けないとき |
| --- | --- | --- |
| 題（H1） | 題の付け方は `document-rebuild` の [format-markdown.md の「題と見出し」](../../document-rebuild/references/format-markdown.md#題と見出し) が決める（`<対象>: <何ができるようになるか>（#<課題番号>）` の短い 1 文）。今の状態は題に入れず「今の姿」に置く。1 行で、`# ` を除いて 256 コードポイントを超えない | 省けない |
| 要約の段落 | 題の直後、最初の `##` の前に、見出しを付けない段落を 1 つ置く。何が困ったかを 1 文、どう解くかを 1〜2 文、調査や採らなかった案がどこにあるかを 1 文で、合わせて 4 文以内。課題の事実は書かずに要求仕様へリンクする。見出しを付けないのは、承認資料の出所とコードが読む見出しを増やさず、「今の姿」から始まる見出しの順に割り込ませないためである | 省けない |
| 今の姿 | 要求仕様のコピーへのリンクと、変更の位置が分かる図。続けて設計に要る今の構造だけを書き、何が起きたかは要求仕様に任せる。リンク先は設計文書からの相対パスで書く（設計文書と同じ `issues/` にあるため `./issue-<番号>-requirements.md`。`issues/issue-…` と書くと `issues/issues/…` を指して開けない）。複数の課題を 1 本にまとめたときは、まとめた理由（共通の原因）をここに書く（`design` の SKILL.md の手順 3） | 省けない。要求仕様が無ければ先に要求を書く |
| 解き方の全体像 | 設計に沿った実装を終えた後に成り立つ姿を、図 1 枚と 3〜5 行で書く（設計 PR のマージだけで成り立つ姿ではない）。受け入れ条件の写しではなく、変更後の形（何がどこにあり、だれが何をできるか）を書く。その形が適切だと言える根拠は、決定ごとの「根拠」の行に置く | 省けない |
| 決定の見出し | `### 決定 N: <何のために>、<何を決めたか>`。例: `### 決定 1: 題の書き手を 1 つにするため、設計 PR の題を設計文書の H1 から作る`。本文の形は [decisions.md](decisions.md) | — |
| 影響と危険 | 働く範囲（このリポジトリだけか、利用先のリポジトリでも働くか）、プロジェクトごとに違うものを設定と引数のどちらで受けるか、当たるモード。続けて、書きかけの文書・同じファイルを触る別の変更・壊れうる箇所と、その扱い | 省けない |
| 代表のリポジトリでの振る舞い（影響と危険の小見出し。代表のリポジトリの設定があるとき） | 設定の `kinds` の種類ごとに 1 行。1 列目は種類の名前で始める（括弧で実物を添えてよい）。「直した後に起きること」は設計・設計の検査・cross-review・MVV 判定で何が起きるか。「この種類で扱えなくなること」は `無し` か、その種類で扱えなくなる運用・リリースの形・テストのツール・CI と、代わりの形が無い理由。判定の単位はリポジトリの種類で、値を改名・作り直しても同じ種類が別の形で扱えるなら `無し`。`無し` 以外の行があれば「人へ残す判断」に設定の `redline` の番号の行を足す | 設定の `paths` に当たらない設計では書かない。当たる設計では欄を必ず書き、`無し` 以外の行には番号の行を「人へ残す判断」に足す（`design` の手順 5 で確かめる） |
| このリポジトリだけの事情（影響と危険の小見出し。同上） | 設計を書くリポジトリの運用で決めた値（ブランチの運用・リリースの形など）と、作るものの既定や振る舞いへ入れずに置く設定の場所。見出しはリポジトリの名前で「<名前>だけの事情」と書いてよい | 無ければ `- 無し（<理由>）` と本文に書く（空の欄は `repo_scope_missing`） |
| 用語 | 「用語」のセクションに置く。新しく足した語は反映を「追加」、意味を変えた語は「意味の変更」にする。承認資料はこの 2 つの行を載せる | 足す語も意味を変える語も無ければセクションを消す。承認資料は「無し（<理由>）」と出す |

**設計 PR の題は H1 と同じ文にする。** スプリントの設計 PR は、pr のステップが頭のファイル
`issues/issue-<番号>-design.md`（分けたファイルは `issue-<番号>-design-<主題>.md`）の H1 から題を作り、
レビューの直しを送った後にも合わせ直す。H1 を読めないとき・256 コードポイントを超えるときは `設計: #<番号>` で出し、
承認資料に「題: 規約の形でない」と出る。単発の `/ndf:pr` では、呼ぶ者が H1 を題に渡す。

**欄が空でも承認ゲートは止まらない。** 承認資料は空の欄を「無し（<理由>）」で出し、変更を要求するかは承認する人が
決める。欄を埋めるのは設計の工程で、承認ゲートを返す前に埋められるものは埋める。用語を確定するために設計より前に
人へ問わず、足した語・意味を変えた語は承認と同じ 1 回に載せる。

題の実例（利用者が「今の問題 → 直した後」の形を読みづらいと指摘し、書き直した形で承認した設計 PR）:

- 書き直す前の #2086: `文書の組み直し: どの文書も「結論から」の 1 通りで組み直され、議論用の文書の提案が決定に読め、スライドや表計算には目安が無い → 文書形式と目的に合った構成と文章量で組み直し、文脈を持たない読み手が理解し納得できることを確かめてから渡せる（#2086 #2083 #2080 #469）`（現象と結果の 2 つを 1 行へ詰め、どちらも読みづらい）
- #2086: `document-rebuild: 文書形式と目的に合わせて組み直し、読み手が理解し納得できるかを確かめる`
- 仕組みの語だけの題も採らない: `Docs: 担当 1 回の起動の結果を共通の語彙で読む設計（#729 #619 #584）`（何ができるようになるかが読めない）

## 設計の結果の書き方

「設計の結果」のセクションは、スプリントの「設計の結果」のステージ（設計の結果のマージ（P1b #3092 が `ndf` のサブコマンドに足す。新しいプラグインだけではまだ打てない））が設計承認ゲートの後に
機械で読む。表の見出しは上の 4 列のまま変えない。セクションが無い・形が違う設計文書は「読めなかった」として扱われ、
実装のプランは書き換わらない（触るファイルなし・マージなし）。

| 列 | 書くこと |
| --- | --- |
| 課題 | `#<番号>`。表のすべての行の課題が、スプリント PR の `Closes` の行になる |
| 扱い | `実装する` / `マージする`（受け入れ内容を統合先の実装へ含め、自分の実装プランを流さない）/ `閉じる`（実装の PR を持たずにスプリント PR で閉じる） |
| 統合先 | `マージする` の行だけ `#<番号>`。それ以外は `—` |
| 触るファイル | `実装する` の行だけ。ファイルのパスをバッククォートで囲み、読点か `,` で区切る。同じステージで等しいファイルを持つ実装プランは 1 本ずつ流れる |

触るファイルのセルの決まり:

- ファイルを 1 つずつ書く。テストのディレクトリのように複数の課題が同時に触る保存先も、足す・変えるテストのファイルを 1 つずつ書く
- 索引のように複数の課題が行を書き足すファイルは、書き足すならそのファイル（例: `docs/index.md`）も書く。等しいファイルを書いた実装プランどうしが 1 本ずつ流れる
- ディレクトリ（末尾が `/` のパス、または作業場所に既にあるディレクトリ）を書くと、ステージは課題の番号とそのパスを標準エラーへ出し、末尾 `/` の形にそろえて進む。ディレクトリは重なりの判定に使わないため、そのプランは同じディレクトリのファイルを書いたプランとも、同じディレクトリを書いたプランとも同時に流れる
- 設計を複数のファイルに分割しても、先頭の表のセルへすべてのパスを直に列挙する。分割した文書の「触るファイル」の分も先頭の表へ写す
- リンクや語で別の文書へ委ねる（例: `` `a.py`。残りは [issue-1-design-loop.md](issue-1-design-loop.md) にある ``）と、ステージは課題の番号・文書のパス・読めなかった部分を出して止まる。パスを直に列挙して直した文書をマージし、打ち直す
- 注記は全角か半角の括弧で囲んで書ける（例: `` `a.py`（新設）、`b/` ``）。括弧の中は読まれず、括弧の中のパスも触るファイルに入らない。括弧の中のリンクは止まる
- 実装の worker へは、表を持つ文書と、それと番号でつながる同じ課題の設計文書（`issue-<番号>-design-<名前>.md`）がすべて渡る

## テスト設計に書く粒度

**テスト設計に書くのは、条件ごとの「どの振る舞いで縛るか」と「どう壊したら落ちるべきか」までである。**
フィクスチャ・起動の形・入力の打ち方・待ち方は書かず、実装（`tdd-cycle`）で走らせた結果として決める。
外部の振る舞い（シェル・端末・外部コマンド）に左右される細部は、走らせれば数秒で分かるのに、レビューでは
文面から推論するしかない。書くと、直すたびに次の細部が指摘され、実装で同じ細部をもう一度確かめ直す。

| 書く | 書かない |
| --- | --- |
| 例: `tmux` の中から打つと、今のセッションを除いた一覧が出る | 例: 偽の `tmux` を `PATH` の先頭に置いて組む |
| 例: 環境変数を読み捨てるように壊すと落ちる | 例: 端末へキーを打った直後の入力は捨てられるので待つ |

**細部を書くなら、実測のスクリプトで確かめた出力を添えた行に限る。** レビューは、添えた出力と文面が
合っているかを見る。出力を添えられない細部は書かない。

## 各節が実装計画のどこへつながるか

ここで「タスク」と書くのは、`implementation-plan` が並べる作業の単位である。

**タスクを機械的に導けるだけの情報を書く。** 導けない設計は、次の工程が成立しない。

各節に書く内容は [deliverables.md](deliverables.md) の「成果物ごとの中身」を唯一の定義として
読む。ここでは、各節を実装計画でどう使うかだけを定める。

| セクション | 実装計画での使われ方 |
| --- | --- |
| 今の姿・文脈と制約 | 制約は計画のリスクと、タスクが越えてはいけない線になる |
| 解き方の全体像 | タスクの並びの骨組みになる |
| 影響と危険 | 働く範囲と当たるモードは完了判定で照らす範囲、壊れうる箇所はリスクとして計画へ移す |
| ドメインモデル | 不変条件はテストのタスク（1 条件 1 テスト、`tdd-cycle`）、集約のオーナーは構成要素のタスクの境界になる |
| 外部の調査 | 採ったライブラリとサービスは依存を足すタスク、倣う標準はコントラクトテストの期待値の出所になる |
| 機能一覧 | タスクを機能の単位で割る根拠になる |
| 構成要素 | タスクの単位になる |
| 構造 | 変更の範囲を読む |
| データ構造 | 移行タスクと検査タスクになる |
| 入出力のコントラクト | コントラクトテストのタスクになる |
| 処理の流れ | 順序の依存を読む |
| 非機能の実現方式 | 検査タスクになる |
| 決定の記録 | 代替案の再検討を止める。決定ごとの根拠は採らなかった形へ戻さない根拠になる |
| 用語 | 計画とコードの名前の出所になる |
| 人へ残す判断 | 計画へ移さない。設計承認ゲートで人が決めた結論を決定の記録に足してから計画を書く |
| テスト設計 | テストのタスクになる |
| 未確認のまま残ること | リスクとして計画へ移す |
| どこを変えるか（詳細設計を畳んだとき） | 表の行が実装計画の「修正対象」になり、関数の行の入力・返り・異常系はタスクの変更内容になる |
| 詳細設計の文書（別のファイル） | 地図は修正対象、構成要素ごとの関数の仕様と異常系はタスクの変更内容、単体テストの観点はテストのタスクになる |

**参照を API と画面で 2 本に分けても、設計文書のセクションは「入出力のコントラクト」1 つである。** 参照を
分けるのは読ませる分量を絞るためで、成果物のセクションの粒度とは別の判断による。両方を触る変更では、
1 つのセクションに両方を書く。

## 図の水準

**4 つの階層すべてを成果物に持つ。** モードごとの要否は
[deliverables.md](deliverables.md) の要否表が決める。

| 階層 | 何を示すか | 書き方 |
| --- | --- | --- |
| システムの文脈（外部との関係） | 変更の影響が及ぶ外側 | system-architecture.md |
| 構成要素の関係 | 責務の分かれ目 | system-architecture.md |
| 配置（どこで動くか） | 実行の単位と境界 | system-architecture.md |
| クラス・コードの構造 | 変更が触る型と、その関係 | structure-behavior.md |

**クラス・コードの階層は、変更が触る型だけに絞る。** 載せる範囲・追随義務・同期の時点は
`structure-behavior.md` のクラス図規約を唯一の定義として読む。

記法・横幅の上限・使ってよい形式は `document-style` の図表ガイドが持つ。ここでは重ねて
定めない。

## 進む前に突き合わせる対

**実装または設計 Pull Request へ進む前に、次の 7 つの対を通す。4 モードすべてで行う**
（設計 Pull Request を出さないモードでも、文書の中で食い違ったまま実装へ進むことは同じように
起きる）。いずれも**同じ文書の中だけで確かめられる**もので、外部の情報を必要としない。
外部を要するものはレビューが拾う。

| 突き合わせる対 | 何を見るか |
| --- | --- |
| 構成要素の表 ↔ 処理の流れの図 | 表に挙げた要素が、すべて図に現れるか |
| 責務の記述 ↔ 失敗の形 | 「純粋な処理」としたものが、終了コードや出力を持っていないか |
| 導ける値の記述 ↔ その値を導いた表 | 本文に書いた行やセルの数・最大と最小・「すべて」が、表を数え直した値と一致するか。直下の表に限らない |
| 影響範囲の図 ↔ 呼び出し元の一覧 | 図の辺が、一覧に挙げた呼び出しと一致するか |
| 受け入れ条件 ↔ テスト設計 | 条件ごとに確かめ方が対応しているか |
| 決定の記録 ↔ 構成要素・処理の流れ | 決定で退けた案が、他のセクションに残っていないか |
| 不変条件 ↔ テスト設計 | 不変条件ごとにテスト設計の行があるか（ドメインモデルのセクションがあるときだけ） |

**確かめた結果は残さない。** 残らないことが結果である。チェックリストを成果物にすると、
埋めること自体が目的になり、埋めたかどうかのレビューが新しく増える。

**3 つ目の対は、書いたときの値ではなく数え直した値で照らす。** 「最も多い」「N 件」
「すべて」は表を数えれば決まるが、書いた側が数えていなければ自分では誤りに気づけない。
値を導いた表が別のセクションにあっても、分割した別のファイルにあっても対象にする。

**表を直したときは、その表から導いた記述を数え直す。** レビューの指摘を直すときも同じである。
表だけを直すと、本文の値が古いまま残る。

**図に含めない要素を明示している文書では、1 つ目の対はその一覧を差し引いて数える。**
参照を読む関係だけを描く図では、書き写す先や理由を残す先が図に現れない。

## `legacy-refactor` の書き方

このモードでは受け入れ条件が無い。次の 4 セクションだけを書く。

| セクション | 書く内容 |
| --- | --- |
| 現状の構造 | いま何がどこにあるか。手を付ける範囲 |
| 変更後の構造 | 何をどこへ移すか |
| 外部の調査 | 自前の実装を置き換えられる標準・ライブラリ・サービス。既存の形の延長なら `省く: <理由>` の 1 行 |
| 決定の記録 | なぜその形にするか。採らなかった案。作り方と比べた候補 |

**設計 Pull Request を出すときは、この 4 セクションの前に H1 と、次の承認する人が読む欄も書く。** 設計承認ゲートは
どのモードでも同じ承認資料を組むためである。このモードは要求仕様を通らないので、要約の段落・今の姿・解き方の全体像の
欄は書かず、承認資料はこの欄から拾う。

置く順は H1 → 目的 → 適用範囲 → 目指す姿（対象の課題へのリンクを含む）→ 目指す姿の根拠 → 管理上の注記（分けた文書への参照）→
ドメインモデルで、承認する人が最初に「何が壊れていて、設計どおりに実装すると何が成り立つか」を読む。

| 欄 | 書くこと | 書けないとき |
| --- | --- | --- |
| 題（H1） | 上の「承認する人が読む欄」の題の行と同じ。今の状態は題に入れず「目的」の「今どうなっているか」に置く | 省けない |
| 目的 | H1 の直後の章。今どうなっているか（不具合なら起きている現象、機能追加ならまだできないこと）・誰に効くか・変えると何が成り立つかを 5 行以内 | `- 無し（<理由>）` |
| 適用範囲 | 働く範囲（このリポジトリだけか、利用先のリポジトリでも働くか）、プロジェクトごとに違うものを設定と引数のどちらで受けるか、当たるモード | `- 無し（<理由>）` |
| 代表のリポジトリでの振る舞い・このリポジトリだけの事情（適用範囲の小見出し。代表のリポジトリの設定があるとき） | 上の「承認する人が読む欄」の同じ名前の行と同じ | 上の同じ名前の行と同じ |
| 目指す姿 | 設計に沿った実装を終えた後に成り立つ姿を 3〜5 行で書く（設計 PR のマージだけで成り立つ姿ではない）。根拠の表はこの姿を支えるものなので、読む人が何の根拠かを先に知れるよう根拠の直前に置く。出所は上の「変更後の構造」で、続けて対象の課題へのリンクを 1 文で書く（仕様のコピーは無い） | 省けない |
| 目指す姿の根拠 | 変更後の形が適切だと言える根拠を 1 行に 1 つ。種類は外部の一次情報・実測・利用者の指示の原文のどれか。外部の一次情報は、外部の調査の表の番号（`STD1` など）を指してよい。MVV の項目の番号（根拠の項目）とは別に書く | `- 無し（既存の形に揃える）` のように理由を添える |
| 用語・決定の見出し | 上の「承認する人が読む欄」の同じ名前の行と同じ | — |

```markdown
## 目的

- **今どうなっているか**:
- **誰に効くか**:
- **変えると何が成り立つか**:

## 適用範囲

- **働く範囲**:
- **プロジェクトごとに違うもの**:
- **当たるモード**:

## 目指す姿

- （設計に沿った実装を終えた後の姿を 3〜5 行で）

対象は {課題} にある。

## 目指す姿の根拠

| 根拠 | 種類 | 何を示すか |
| --- | --- | --- |
```

**振る舞いを変えないことが前提のため、入出力のコントラクトは変わらない。** コントラクトのセクションを作らない。

## 分量

1 ファイル 500 行を上限とし、超えたらセクションの単位で分割する（`document-style` の基準）。
分割したときは、先頭のファイルから他のファイルへの参照を張る。分割した文書は `issue-<番号>-design-<名前>.md` と名付け、
触るファイルは「設計の結果の書き方」のとおり先頭の表へ直に列挙する。

**詳細設計を別ファイル（`issue-<番号の並び>-design-detail.md`。番号の並びは設計書と同じ）にするのは、新設する関数が 2 つ以上あるか、既存の関数のシグネチャを変えるときだけである。**
判定はこの 2 つの数だけで決め、書き手の判断を挟まない。関数 1 つの仕様は表の 1 行に収まり、別ファイルにすると 1 つの関数のために別の文書を開かせるためである。
条件の SSOT は document-roles.md の「詳細設計を別ファイルにする条件」で、それ以外はこのテンプレートの「どこを変えるか」に畳む。

| 項目 | 畳んだときの書き方 |
| --- | --- |
| 頭の 1 行 | 畳んだことと理由（新設する関数の数・シグネチャを変える関数の数）。別ファイルにしたときは「どこを変えるか」を作らず、詳細設計書へのリンクを「設計の結果」の直前に 1 行置く（ファイルの一覧を見せたくて作るときは、頭の 1 行をそのリンクにする）。どちらも無い設計書は、工程「詳細設計」を終えていない |
| 表の列 | ファイル・変える中身・決定（満たす決定の番号） |
| ファイル | 「設計の結果」の触るファイルと一致させる。新設するファイルには「（新設）」を添える |
| 新設する関数が 1 つのとき | その関数の行に、関数の入力・返り・異常系を書く |
| 責務か失敗時の扱いだけを変える関数 | シグネチャを変えなければ畳み、その関数の行に変える前と後の振る舞い（どの入力で何を返すか・どの失敗をどう扱うか）を書く |
