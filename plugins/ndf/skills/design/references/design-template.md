# 設計文書の雛形

不要な節は削る。空の見出しを残さない。**触らない領域の節は作らない。**

```markdown
# {対象}: {今起きている問題（利用者が見る現象）} → {直した後に成り立つこと}（#{課題番号}）

## 目的

- **何が壊れているか**:
- **誰が困るか**:
- **直すと何が成り立つか**:

## 適用範囲

- **働く範囲**:
- **プロジェクトごとに違うもの**:
- **当たるモード**:

## あるべき姿の根拠

| 根拠 | 種類 | 何を示すか |
| --- | --- | --- |

（H1 からここまでの書き方は、この雛形の「承認する人が読む欄」の節）

要求と受け入れ条件は {課題} の本文にある（コピーは {仕様のコピーのファイル}）。この文書は「どう作るか」だけを扱う。

（承認する人が読む欄の次に書く。`standard` は必ず、ほかのモードは集約・不変条件・ドメインイベントを変えるとき。
　書き方は domain-model.md）

| コンテキスト | 何の語が 1 つの意味に決まるか |

### 不変条件

| --- | --- | --- | --- |

| # | イベント | 発生元 | 受け手 |
| --- | --- | --- | --- |
| E1 | （要求のドメインイベントの番号を引き継ぐ） | | |

### 用語

| 用語 | 意味 | 用語集への反映 |

| | | （追加 / 意味の変更 / 廃止。この表の 1 列目が用語チェックの対象になる） |

（永続データを持つ、またはスキーマを変える場合のみ。ER 図・テーブル定義・CRUD 図。

（処理の流れの図。状態を持つなら状態遷移図も。書き方は structure-behavior.md、
　記法と横幅の上限は markdown-writing の図表ガイド）

## 非機能の実現方式

（仕様に非機能の条件がある場合のみ。書き方は nonfunctional.md）

## 決定の記録
```

**節の要否はモードと領域が決める。** 一覧は [deliverables.md](deliverables.md) にある。
**触らない領域の節は作らない。**

## 承認する人が読む欄

承認ゲート 1 で承認する人が問う項目（題・目的・用語・適用範囲・あるべき姿の根拠）の書き方の正本はこの節である。
承認資料（`development-workflow` の `approval-request.md`）はこの欄を先頭に載せ、ほかの Skill はこの節を指す。
置く順は H1 → 目的 → 適用範囲 → あるべき姿の根拠 → 管理上の注記（要求の置き場・分けた文書への参照）→
ドメインモデルで、承認する人が最初に「何が壊れていて、マージすると何が成り立つか」を読む。

| 欄 | 書くこと | 書けないとき |
| --- | --- | --- |
| 題（H1） | `# [<対象>: ]<今起きている問題（利用者が見る現象）> → <直した後に成り立つこと>（#<課題番号>[ #<番号>...]）`。対象は Skill 名か領域で、省いてよい。仕組みの語（関数・ステップ・ファイルの名前）は本文へ回す。1 行で、`# ` を除いて 256 コードポイント以内 | 省けない |
| 目的 | H1 の直後の章。何が壊れているか・誰が困るか・直すと何が成り立つかを 5 行以内。出所は要求の「目的」 | `- 無し（<理由>）`。要求の「目的」が空なら先に要求を埋める |
| 適用範囲 | 働く範囲（このリポジトリだけか、配布先のリポジトリでも働くか）、プロジェクトごとに違うものを設定と引数のどちらで受けるか、当たるモード | `- 無し（<理由>）` |
| あるべき姿の根拠 | 変更後の形が適切だと言える根拠を 1 行に 1 つ。種類は外部の一次情報・実測・利用者の指示の原文のどれか。MVV の項目の番号（根拠の項目）とは別に書く | `- 無し（既存の形に揃える）` のように理由を添える |
| 用語 | ドメインモデルの「用語」の表に置く（場所は変えない）。新しく足した語は反映を「追加」、意味を変えた語は「意味の変更」にする。承認資料はこの 2 つの行を載せる | 該当の行が無ければ承認資料に「無し（<理由>）」 |
| 決定の見出し | `### 決定 N: <何のために>、<何を決めたか>`。例: `### 決定 1: 題の書き手を 1 つにするため、設計 PR の題を設計文書の H1 から作る` | — |

**設計 PR の題は H1 と同じ文にする。** スプリントの設計 PR は、pr のステップが頭のファイル
`issues/issue-<番号>-design.md`（分けたファイルは `issue-<番号>-design-<主題>.md`）の H1 から題を作り、
レビューの直しを送った後にも合わせ直す。H1 を読めないとき・256 コードポイントを超えるときは `設計: #<番号>` で出し、
承認資料に「題: 規約の形でない」と出る。単発の `/ndf:pr` では、呼ぶ者が H1 を題に渡す。

**欄が空でも承認ゲートは止まらない。** 承認資料は空の欄を「無し（<理由>）」で出し、差し戻すかは承認する人が
決める。欄を埋めるのは設計の工程で、承認ゲートを返す前に埋められるものは埋める。用語を確定するために設計より前に
人へ問わず、足した語・意味を変えた語は承認と同じ 1 回に載せる。

題の実例（利用者が「目的を明らかにして書き直し」と指示し、書き直した形で承認した設計 PR）:

- 書き直す前の #781: `Docs: 担当 1 回の起動の結末を共通の語彙で読む設計（#729 #619 #584）`（仕組みの語だけで、現象が読めない）
- #781: `cross-review: 利用上限で止まった担当が「結果ファイル無し」と報告されて空振りの起動し直しで待たされ、止めた担当が後から結果を書く → 上限を理由に報告して同じラウンドで起動し直さず、止めた後は書かせない（#729 #619 #584）`
- #782: `cross-review / cross-refactoring: 参加する CLI が 1 者でも使えないと収束ループを開始できず、再開で渡した引数が黙って無視される → 使える者だけで開始し、cross-review は毎ラウンド 2 席を確保し、再開で渡した引数は反映されるか反映しないと知らされる（#727 #687 #478 #664 #648）`
- #783: `cross-review: 誤りを示されていない重大な指摘が数えられずに承認で終わる → 数えない指摘を棄却と軽微な指摘に限る（#732 #624 #706）`

## 設計の結果の書き方

「設計の結果」の節は、スプリントの「設計の結果」のステージ（`supervise.py design-results`）が承認ゲート 1 の後に
機械で読む。表の見出しは上の 4 列のまま変えない。節が無い・形が違う設計文書は「読めなかった」として扱われ、
実装のプランは書き換わらない（触るファイルなし・取り込みなし）。

| 列 | 書くこと |
| --- | --- |
| 課題 | `#<番号>`。表のすべての行の課題が、スプリント PR の `Closes` の行になる |
| 扱い | `実装する` / `取り込む`（受け入れ内容を取り込み先の実装へ含め、自分の実装プランを流さない）/ `閉じる`（実装の PR を持たずにスプリント PR で閉じる） |
| 取り込み先 | `取り込む` の行だけ `#<番号>`。それ以外は `—` |
| 触るファイル | `実装する` の行だけ。パスかディレクトリをバッククォートで囲み、読点か `,` で区切る。同じステージで重なる実装プランは 1 本ずつ流れる |

## テスト設計に書く粒度

**テスト設計に書くのは、条件ごとの「どの振る舞いで縛るか」と「どう壊したら落ちるべきか」までである。**
フィクスチャ・起動の形・入力の打ち方・待ち方は書かず、実装（`tdd-cycle`）で走らせた結果として決める。
外部の振る舞い（シェル・端末・外部コマンド）に左右される細部は、走らせれば数秒で分かるのに、レビューでは
文面から推論するしかない。書くと、直すたびに次の細部が指摘され、実装で同じ細部をもう一度確かめ直す。

| 書く | 書かない |
| --- | --- |
| 例: `tmux` の中から打つと、今のセッションを除いた一覧が出る | 例: 偽の `tmux` を `PATH` の先頭に置いて組む |
| 例: 環境変数を読み捨てるように壊すと落ちる | 例: 端末へキーを打った直後の入力は捨てられるので待つ |

**細部を書くなら、実測のスクリプトで確かめた出力を添えた行に限る。** レビューは、添えた出力と文面が
合っているかを見る。出力を添えられない細部は書かない。

## 各節が実装計画のどこへつながるか

ここで「タスク」と書くのは、`implementation-plan` が並べる作業の単位である。

**タスクを機械的に導けるだけの情報を書く。** 導けない設計は、次の工程が成立しない。

各節に書く内容は [deliverables.md](deliverables.md) の「成果物ごとの中身」を唯一の定義として
読む。ここでは、各節を実装計画でどう使うかだけを定める。

| 節 | 実装計画での使われ方 |
| --- | --- |
| 承認する人が読む欄 | 目的と適用範囲は完了判定で照らす範囲、あるべき姿の根拠は採らなかった形へ戻さない根拠になる |
| ドメインモデル | 不変条件はテストのタスク（1 条件 1 テスト、`tdd-cycle`）、集約の持ち主は構成要素のタスクの境界になる |
| 機能一覧 | タスクを機能の単位で割る根拠になる |
| 構成要素 | タスクの単位になる |
| 構造 | 変更の範囲を読む |
| データ構造 | 移行タスクと検査タスクになる |
| 入出力の契約 | 契約テストのタスクになる |
| 処理の流れ | 順序の依存を読む |
| 非機能の実現方式 | 検査タスクになる |
| 決定の記録 | 代替案の再検討を止める |
| テスト設計 | テストのタスクになる |
| 未確認のまま残ること | リスクとして計画へ移す |

**参照を API と画面で 2 本に分けても、設計文書の節は「入出力の契約」1 つである。** 参照を
分けるのは読ませる分量を絞るためで、成果物の節の粒度とは別の判断による。両方を触る変更では、
1 つの節に両方を書く。

## 図の水準

**4 つの階層すべてを成果物に持つ。** モードごとの要否は
[deliverables.md](deliverables.md) の要否表が決める。

| 階層 | 何を示すか | 書き方 |
| --- | --- | --- |
| システムの文脈（外部との関係） | 変更の影響が及ぶ外側 | system-architecture.md |
| 構成要素の関係 | 責務の分かれ目 | system-architecture.md |
| 配置（どこで動くか） | 実行の単位と境界 | system-architecture.md |
| クラス・コードの構造 | 変更が触る型と、その関係 | structure-behavior.md |

**クラス・コードの階層は、変更が触る型だけに絞る。** 載せる範囲・追随義務・同期の時点は
`structure-behavior.md` のクラス図規約を唯一の定義として読む。

記法・横幅の上限・使ってよい形式は `markdown-writing` の図表ガイドが持つ。ここでは重ねて
定めない。

## 進む前に突き合わせる対

**実装または設計 Pull Request へ進む前に、次の 7 つの対を通す。4 モードすべてで行う**
（設計 Pull Request を出さないモードでも、文書の中で食い違ったまま実装へ進むことは同じように
起きる）。いずれも**同じ文書の中だけで確かめられる**もので、外部の情報を必要としない。
外部を要するものはレビューが拾う。

| 突き合わせる対 | 何を見るか |
| --- | --- |
| 構成要素の表 ↔ 処理の流れの図 | 表に挙げた要素が、すべて図に現れるか |
| 責務の記述 ↔ 失敗の形 | 「純粋な処理」としたものが、終了コードや出力を持っていないか |
| 導ける値の記述 ↔ その値を導いた表 | 本文に書いた行やセルの数・最大と最小・「すべて」が、表を数え直した値と一致するか。直下の表に限らない |
| 影響範囲の図 ↔ 呼び出し元の一覧 | 図の辺が、一覧に挙げた呼び出しと一致するか |
| 受け入れ条件 ↔ テスト設計 | 条件ごとに確かめ方が対応しているか |
| 決定の記録 ↔ 構成要素・処理の流れ | 決定で退けた案が、他の節に残っていないか |
| 不変条件 ↔ テスト設計 | 不変条件ごとにテスト設計の行があるか（ドメインモデルの節があるときだけ） |

**確かめた結果は残さない。** 残らないことが結果である。チェックリストを成果物にすると、
埋めること自体が目的になり、埋めたかどうかのレビューが新しく増える。

**3 つ目の対は、書いたときの値ではなく数え直した値で照らす。** 「最も多い」「N 件」
「すべて」は表を数えれば決まるが、書いた側が数えていなければ自分では誤りに気づけない。
値を導いた表が別の節にあっても、分割した別のファイルにあっても対象にする。

**表を直したときは、その表から導いた記述を数え直す。** レビューの指摘を直すときも同じである。
表だけを直すと、本文の値が古いまま残る。

**図に含めない要素を明示している文書では、1 つ目の対はその一覧を差し引いて数える。**
参照を読む関係だけを描く図では、書き写す先や理由を残す先が図に現れない。

## `legacy-refactor` の書き方

このモードでは受け入れ条件が無い。次の 3 節だけを書く。

| 節 | 書く内容 |
| --- | --- |
| 現状の構造 | いま何がどこにあるか。手を付ける範囲 |
| 変更後の構造 | 何をどこへ移すか |
| 決定の記録 | なぜその形にするか。採らなかった案 |

**設計 Pull Request を出すときは、この 3 節の前に H1 と承認する人が読む欄（上の節）も書く。** 承認ゲート 1 は
モードによらず同じ承認資料を組むためである。

**振る舞いを変えないことが前提のため、入出力の契約は変わらない。** 契約の節を作らない。

## 分量

1 ファイル 500 行を上限とし、超えたら節の単位で分割する（`markdown-writing` の基準）。
分割したときは、先頭のファイルから他のファイルへの参照を張る。
