# 設計文書の雛形

不要な節は削る。空の見出しを残さない。**触らない領域の節は作らない。**

```markdown
# {課題番号}: {何を作るか}

要求と受け入れ条件は {仕様のファイル} にある。この文書は「どう作るか」だけを扱う。

## 構成要素

| 要素 | 責務 |
| --- | --- |
| （作るもの・変えるもの） | （何を引き受けるか） |

## データ構造

（永続データを持つ、またはスキーマを変える場合のみ。書き方は data-structure.md）

## 入出力の契約

（呼び出される約束を変える、または画面を追加・変更する場合のみ。
　書き方は interface-api.md / interface-ui.md）

## 処理の流れ

（図 1 枚。記法と横幅の上限は markdown-writing の図表ガイド）

## 決定の記録

（結論・理由・採らなかった案。書き方は decisions.md）

## テスト設計

| 受け入れ条件 | 何で確かめるか |
| --- | --- |

## 未確認のまま残ること

| 項目 | 内容 |
| --- | --- |
```

## 各節が実装計画のどこへつながるか

ここで「タスク」と書くのは、`implementation-plan` が並べる作業の単位である。

**タスクを機械的に導けるだけの情報を書く。** 導けない設計は、次の工程が成立しない。

| 節 | 書く内容 | 実装計画での使われ方 |
| --- | --- | --- |
| 構成要素 | 何を作るか。それぞれの責務 | タスクの単位になる |
| データ構造 | 保存する形、時系列の扱い、検査の手段 | 移行タスクと検査タスクになる |
| 入出力の契約 | 呼び出される約束（経路・入出力）と画面（一覧・遷移・状態・入力規則） | 契約テストのタスクになる |
| 処理の流れ | 図 1 枚 | 順序の依存を読む |
| 決定の記録 | 結論・理由・採らなかった案 | 代替案の再検討を止める |
| テスト設計 | 受け入れ条件とテストの対応 | テストのタスクになる |
| 未確認のまま残ること | 確かめられなかったこと | リスクとして計画へ移す |

**参照を API と画面で 2 本に分けても、設計文書の節は「入出力の契約」1 つである。** 参照を
分けるのは読ませる分量を絞るためで、成果物の節の粒度とは別の判断による。両方を触る変更では、
1 つの節に両方を書く。

## 図の水準

| 階層 | 求めるか | 理由 |
| --- | --- | --- |
| システムの文脈（外部との関係） | `architecture` で求める | 変更の影響が及ぶ外側を示す |
| 構成要素の関係 | すべてのモードで求める | 責務の分かれ目を示す |
| クラス・コードの構造 | 求めない | コードが唯一の正であり、図は書いた時点で古くなる |

記法・横幅の上限・使ってよい形式は `markdown-writing` の図表ガイドが持つ。ここでは重ねて
定めない。

## `legacy-refactor` の書き方

このモードでは受け入れ条件が無い。次の 3 節だけを書く。

| 節 | 書く内容 |
| --- | --- |
| 現状の構造 | いま何がどこにあるか。手を付ける範囲 |
| 変更後の構造 | 何をどこへ移すか |
| 決定の記録 | なぜその形にするか。採らなかった案 |

**振る舞いを変えないことが前提のため、入出力の契約は変わらない。** 契約の節を作らない。

## 分量

1 ファイル 500 行を上限とし、超えたら節の単位で分割する（`markdown-writing` の基準）。
分割したときは、先頭のファイルから他のファイルへの参照を張る。
