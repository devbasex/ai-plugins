# 体裁設計: 共通

**読み手へ渡す文書を作るとき、出力の形にかかわらず先に読む。** 続けて、対象の形に当たる
`layout-<出力の形>.md` を 1 つだけ読む。

## 決める項目と渡し方を分ける

**決めるのは項目であって、渡し方ではない。** 決めた値を生成へどう渡すかは、`release` の
対象形態に対応する `form-<出力の形>.md` が持つ。

**版面・書体・色を正本の Markdown へ書かない。** 埋めると生成の経路が 1 つに固定される。
体裁設計の産物は**生成へ渡す入力**である。

| 生成の経路 | 渡し方 |
| --- | --- |
| 変換器を使う | その変換器の設定（前付け・テーマ・スタイル） |
| **AI エージェントが組む** | **指示として渡す**（版面・書体・色・1 枚あたりの情報量・図表の種類） |
| 既存のテンプレートへ流し込む | テンプレートの識別子 |

**渡し方が違っても、決める項目は同じである。** 項目は対象形態の参照が持つ。

## 主張と版面の分担

**主張がいくつあるかは中身の話**で `document-drafting` が持つ。
**収まるかは版面の話**で、体裁設計が持つ。

片方へ寄せると、版面を変えたときに主張の数まで書き直すことになる。

## 図表の種類は生成の経路が決める

**「本文へ埋める図」の規約とは根拠が違う。** `markdown-writing` の図表ガイドは
「GitHub がレンダリングするか」を根拠にする。ここでの根拠は**生成の経路が何を描画できるか**
である。

**描画できる形式を生成の側へ確かめる。** 経路を固定しないため、ここでは形式を列挙しない。

**一例として、Mermaid を直接描画しない変換器がある。** その経路では画像へ変換して参照する
ことになり、「本文へ ` ```mermaid ` で書く」は成り立たない。**どちらが正しいかではなく、
生成の経路で分岐する。**

## 決めた値の書き先

**設計文書の「入出力の契約」の節へ書く。** 生成へ渡す入力であるため、契約として扱う。

## 関連

- `layout-review` — 生成物を描画して版面を見る
- `markdown-writing` の図表ガイド — 本文へ埋める図の規約（**移していない。軸が違う**）
