# 外部の調査

`design` の手順 2 の正本。設計の判断の前に、触る領域の業界の事実上の標準・仕様、主要な製品の解き方、
使える既存のライブラリとマネージドサービスを一次情報で調べ、設計文書の `## 外部の調査` の節に残す。
節の形は [design-template.md](design-template.md) の `## 外部の調査` にある。

**プロジェクトの MVV に調査の項目があるかに依らず、`design` を通すすべてのモードで通すか省くかを決める。**

## 例

認可の仕組みを作り直す設計なら、次のように決める。

| 種類 | 調べるか | 理由 |
| --- | --- | --- |
| 標準・仕様 | 調べる | 利用者・ロール・ポリシーの形と、委任・短期のトークンに事実上の標準がある（例: IAM のポリシーの形・OAuth 2.1・RFC 8693） |
| 主要な製品 | 調べる | 同じ業務の主要な製品が、店舗と役職の権限をどう分けているかを比べる |
| ライブラリとサービス | 調べる | 認可のエンジン（例: Cedar・Amazon Verified Permissions）を使うか、自前で判定を書くかを決める |

例の標準・製品・ライブラリは読み手の理解のための例で、領域ごとに調べるべきものの一覧ではない。
調べる対象は、手順 1 で決めた触る領域から設計者が決める。

## 1. 通すか省くかを決める

次のどれかに当たる変更は省ける。

- 文言・書式・誤記の修正
- 既存の形の延長（同じ形の項目を 1 つ足す、既存の部品の使い方を変えずに呼ぶ場所を増やす）
- 外部の判断が要らない変更（プロジェクトの中の取り決めだけで形が決まる）

**省くときは、設計文書の `## 外部の調査` の節に `省く: <理由>` の 1 行だけを置く。** 設計の書き先は
[deliverables.md](deliverables.md) の「設計の書き先」が決める（`light` は受け入れ条件のファイルの設計の節）。
**省けるか決められないときは通す。**

## 2. 調べる対象を決める

3 種類のそれぞれについて、調べるかを決める。

| 種類 | 調べること |
| --- | --- |
| 標準・仕様 | 業界の事実上の標準・公開の仕様・規格（RFC・W3C・ISO・NIST など）。その領域で多くの実装が従っている形 |
| 主要な製品 | 同じ問題を世界の主要な製品・競合がどう解いているか |
| ライブラリとサービス | 自前で作る前に使える既存のライブラリ・フレームワーク・マネージドサービス。プロジェクトがすでに依存しているものを含む |

**調べない種類には、理由を 1 行残す。** 3 種類とも調べないなら、省ける条件に当たるかを見直す。

## 3. 一次情報を取得する

取得は、設計を書く担い手が手元の取得の手段（Web 検索・URL の取得・`gh` など）で行う。

- 出典は、公式の文書・仕様の原文・パッケージの登録簿（PyPI・npm など）・リポジトリの API を優先する。
  まとめ記事だけを出典にしない
- ライブラリは、版・ライセンス・最後のリリースの日付・終了のアナウンス（アーカイブ・非推奨のアナウンスを含む）・
  要件を満たすかを確かめる
- 棚卸しのシーズの調査の記録（`.ndf/backlog/research/`）に同じ対象があれば、その記録のパスと調べた日時を
  出典として引いてよい

## 4. 調べる量の上限

| 上限 | 値 |
| --- | --- |
| 種類ごとの候補 | 6 件 |
| 取得の試み（検索 1 回・URL の取得 1 回をそれぞれ 1 と数える） | 30 回 |

**どちらかの上限に当たったら調査を止め、残りの対象を「確かめられなかったこと」へ理由「上限」で書く。**
節の最後に `調べた量: 候補 <件数> 件・取得の試み <回数> 回。` の 1 行を残す。値の見直しはこの表の 1 か所を直す。

## 5. 結果を表に残す

標準・仕様は `STD<数>`、主要な製品は `PRD<数>`、ライブラリとサービスは `LIB<数>` の番号を表の 1 列目に振る。
決定の「比べた候補」はこの番号で指す。**どの行にも出典（URL・パス・コマンドのどれかと取得日）を付ける。**

## 6. 取得できなかった対象を書く

**取得できなかった対象・公開の資料が無い対象を、推定で埋めない。** 「確かめられなかったこと」の表へ、
対象・試した手段（URL か検索の語。試していなければ「試していない」）・結果と理由（取得の拒否・HTTP の状態・
ネットワークの誤り・上限）を書く。

「該当するライブラリは無い」「公開の資料は無い」のような否定の結論は、試した検索の語と結果を添えたときだけ
書く（`investigation-rules` の「否定的結論にはエビデンス必須」）。試していないなら「無い」と書かず、
確かめていないと書く。

## 7. 決定へつなぐ

調べた結果は、あるべき姿の根拠と決定の記録の材料にする。機能をどう得るかを選んだ決定には、作り方
（自前で作る / ライブラリやサービスを使う / 標準に倣う）と比べた候補の 2 行を書く。書き方は
[decisions.md](decisions.md) の「作り方と比べた候補」にある。

**自前で作る決定には、比べた候補を必ず並べる。** 候補が無いまま自前で作ると書いた設計は、`design` の
手順 5 の検査（`design-survey.py check`）が指摘する。
