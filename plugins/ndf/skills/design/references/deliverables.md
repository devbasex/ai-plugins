# 設計の成果物

**何を書くかはモードと領域の 2 つで決まる。** モードが水準を決め、領域が該当を決める。

## 水準は「必ず書く」と「当たるときだけ」の 2 つ

**どの成果物も、変更の中身が求めれば書く対象になる。** モードが決めるのは無条件に求めるか
どうかであって、書いてはいけない成果物を決めるものではない。

| 水準 | 対象があるとき | 対象が無いとき |
| --- | --- | --- |
| 必ず書く | そのモードで `design` を通すなら書く | `standard` の必ず書くセクションは、どの変更にも対象がある。ほかのモードで対象が無いとき（型を持たないリポジトリの `legacy-refactor` のクラス図など）は、**対象が無いことを下の「省いた理由の書き先」へ書く** |
| 当たるときだけ | 触る領域に当たれば書く | **見出しごと消す。** 「無し」と書かず、理由も要らない |

**当たらないセクションの見出しを残さない。** 空の見出しや「無し」の並びは、読み手に書くことの無いセクションを
読ませる。書き忘れと当たらないことは見出しの有無では見分けられないので、cross-review と設計承認ゲートが見る。
見分ける対象を減らすため、`standard` の必ず書くセクションは 8 つ（今の姿・文脈と制約・解き方の全体像・決定の記録・
影響と危険・テスト設計・設計の結果・外部の調査）に絞る。題の直後の要約の段落も必ず書くが、見出しを持たないので
8 つに数えない。

**「必ず書く」を「中身が無くても見出しを置く」と読まない。** 対象が存在しない変更がある。型を持たない
リポジトリで `legacy-refactor` の変更を行うと、クラス図の対象が 1 つも無い。無条件に求めると、
空の見出しか作り話が入る。

### 省いた理由の書き先

| モード | 書き先 |
| --- | --- |
| `light` / `operation` | 仕様の「対象範囲（含まない）」 |
| `legacy-refactor` | 設計文書の「決定の記録」 |

**`legacy-refactor` だけが違うのは、このモードが仕様を入力に取らないためである**
（`SKILL.md` の「受け取るもの」。工程表でも「要求と受け入れ条件」を通らない）。書き先を
仕様に限ると、書く先が存在しない。省略のためのセクションを新しく作ると、書くことが無いモードでも
空の見出しが残るため、既に必ず書くセクションである「決定の記録」を使う。

**`standard` の構成要素図・クラス図・処理の流れを「当たるときだけ」にするのは、変更の位置は「今の姿」の図が、
変更後の形は「解き方の全体像」の図が必ず示すためである。** 構成要素や型を足す・変える変更では、その図を当たる
セクションに描く。

**`operation` で非機能設計表を必ず書くのは、このモードが必ず外部の系の状態を変える
ためである。** 権限の設定・反映先の構成の変更・データの投入は、可用性・セキュリティ・
移行性・システム環境のいずれかに必ず当たる。実現方式を書かないまま実行すると、**戻せるか
どうかを実行の時点で初めて考えることになる。**

**`operation` と `legacy-refactor` でテスト設計を必ず書くにしないのは、そのモードで設計のセクションが
持てる範囲の外にあるためである。** `operation` の設計のセクションが足すのは、その構成を選んだ理由と
非機能の実現方式の 2 つだけである（下の「設計の書き先」と `operation-run.md`「設計を通る
場合の書き先」）。確かめ方は実行の記録が終了コードとして持つ。`legacy-refactor` は受け入れ
条件を入力に取らないため、「受け入れ条件と確かめ方の対応」の左側が存在しない。

**`legacy-refactor` で未確認のまま残ることを必ず書くにしないのも同じ理由である。** このモードの
設計文書は `design-writing.md`「`legacy-refactor` の書き方」が定める 4 セクション（現状の構造・
変更後の構造・外部の調査・決定の記録）でできており、必ず書く成果物はこの 4 セクションに収まるものに限る。要否表で
このモードが必ず書くとする構成要素図・クラス図は前の 2 セクションへ、外部の調査は 3 節目へ、
決定の記録は 4 節目へ入る。パッケージ構成と詳細設計は、設計文書とは別の詳細設計の文書に書く。
**セクションを増やす成果物を必ず書くにすると、要否表とテンプレートが食い違う。**

**外部の調査は、省くときもセクションを作り、省いた理由をそのセクションの `省く: <理由>` の 1 行に書く。** 上の「省いた理由の
書き先」へは書かない。通したか省いたかを、設計の書き先の 1 か所で読めるようにするためである。

**該当の判定は領域が持つ。** 永続データを持たない変更へ ER 図を求めず、画面を持たない変更へ
画面一覧を求めない。領域と参照の対応は `SKILL.md` の「触る領域を決める」にある。

## 成果物ごとの中身

**書き方の詳細は領域ごとの参照が持つ。** ここに書くのは、何を載せるかまでである。

| 成果物 | 何を載せるか | 書き方の詳細 |
| --- | --- | --- |
| 要約の段落 | 何が困ったか 1 文・どう解くか 1〜2 文・調査や採らなかった案の場所 1 文の、合わせて 4 文以内 | `design-writing.md` の「承認する人が読む欄」 |
| 今の姿・文脈と制約・解き方の全体像・影響と危険 | 要求仕様へのリンクと変更の位置の図、守る制約、実装を終えた後の姿、働く範囲と壊れうる箇所。承認する人が読む欄として設計文書の頭に置く | `design-writing.md` の「承認する人が読む欄」 |
| `legacy-refactor` の承認する人が読む欄 | 題・目的・適用範囲・目指す姿・目指す姿の根拠 | `design-writing.md` の「`legacy-refactor` の書き方」 |
| ドメインモデルのセクション | 変更が属するコンテキスト、変える集約とオーナー、不変条件、ドメインイベント。解き方の全体像の後、当たるときだけのセクションの先頭に置く | `domain-model.md` |
| 外部の調査 | 調べる対象の 3 種類ごとの採否と理由、出典つきの比較の表、確かめられなかったこと、調べた量。省くときは理由の 1 行だけ。省けるか決められないときは通す。設計文書の末尾に付録として置く | `external-survey.md` |
| 機能一覧表 | この変更が作る・変える機能を、利用者から見た単位で並べる。誰が使うかを添える | 下の「機能一覧表」 |
| 構成要素図 | 要素と、要素どうしの関係。責務の分かれ目を示す | `system-architecture.md` |
| システム構成図 | 外部の系との関係（文脈）と、どこで動くか（配置） | `system-architecture.md` |
| クラス図 | 変更が触る型と、その関係 | `structure-behavior.md` |
| オブジェクト図 | ある時点の実体の関係。型だけでは伝わらない場合に使う | `structure-behavior.md` |
| パッケージ・モジュール構成 | 置く場所。ツリーで書く。詳細設計の文書を書くときはそのモジュールマップに書き、設計文書に写さない | `system-architecture.md` |

| CRUD 図 | 機能がどのデータを作る・読む・更新する・消すか | `data-structure.md` |

| 状態遷移図 | 状態と、遷移の引き金 | `structure-behavior.md` |

| 用語 | 足した語・意味を変えた語・廃止した語と、用語集への反映 | `domain-model.md` の「用語」 |

| 設計の結果 | 課題・扱い・統合先・触るファイルの 4 列 | `design-writing.md` の「設計の結果の書き方」 |
| 人へ残す判断 | レッドライン（`C<番号>` / `P<番号>` / `R<番号>`）に当たる判断だけを、判断・当たる番号・なぜ当たるかの 1 行で並べる。番号を挙げられない判断は置かず、決定の記録で設計者が決める | `decisions.md` の「人へ委ねない」 |
| 未確認のまま残ること | デプロイの前に確かめられない事実（実測・外部の振る舞い）と、いつ・何で分かるか。利用者に選ばせる判断を置かない | `design-template.md` |

### 機能一覧表

**利用者から見た単位で並べる。** ファイルやクラスの単位で並べない。**実装の単位は構成要素の
表が持つ。**

```markdown
| # | 機能 | 誰が使うか |
| --- | --- | --- |
| F1 | 下書きを公開する | 記事の作成者 |
| F2 | 公開を取り消す | 記事の作成者と編集の担当 |
```

- 番号を付ける。テスト設計と受け入れ条件から、この番号で指せる
- **1 行が 1 つの受け入れ条件に対応するとは限らない。** 対応は「テスト設計」が持つ

## 設計の書き先

**独立した設計文書を必須とするのは `standard` だけである。**

| モード | 設計の書き先 | 設計 Pull Request |
| --- | --- | --- |
| `light` | 受け入れ条件を書いたファイルのセクション（`issues/` 配下） | 不要 |
| `operation` | 実行の記録と同じファイルのセクション（置く場所は `operation-run.md` が決める） | 不要 |
| `legacy-refactor` | 独立したファイル、または実装の Pull Request に載せる | 任意 |
| `standard` | 独立したファイル | 必須 |

独立したファイルの置く場所は、仕様のコピー（`requirements-design` の手順 7）と同じ `issues/` 配下とし、
完了後に `plan-to-spec` が `docs/` へ移す。仕様のコピーと同じ場所に置くのは、設計と要求を同じ差分で
レビューするためである。

独立したファイルにするのは、**設計として確定した内容と、実装の段階で入る計画の更新を、
別の差分として読めるようにする**ためである。**設計の分量が小さく、仕様と混ざっても区別
られるときだけ**、同じファイルの別のセクションでよい。判断は「**設計 Pull Request として単独で
読めるか**」で見る。

1 ファイルが 500 行を超えたらセクションの単位で分割する（`document-style` の分量の基準）。分割したときは、先頭のファイルから
他のファイルへの参照を張る。分割した文書は `issue-<番号>-design-<名前>.md` と名付け、触るファイルは
[design-writing.md の「設計の結果の書き方」](design-writing.md#設計の結果の書き方) のとおり先頭の表へ直に列挙する。

**`light` / `operation` に独立したファイルを求めない。** 1 セクションで足りる内容のために設計文書と
設計 Pull Request が生まれ、工程が中身に見合わなくなる。

**`operation` では、`operation-run.md` が既に求めているものを再掲しない。** 実行の範囲・
取り消しの手段・記録の置く場所はそちらが持つ。設計が足すのは、**その構成を選んだ理由と
非機能の実現方式**である。

## 図の記法

**記法・横幅の上限・使ってよい形式は `document-style` の図表ガイドが唯一の定義として持つ**。
この文書が決めるのは、
どの図を、いつ、どの粒度で描くかまでである。

### 図の水準

**4 つの階層すべてを成果物に持つ。** モードごとの要否は上の要否表が決める。

| 階層 | 何を示すか | 書き方 |
| --- | --- | --- |
| システムの文脈（外部との関係） | 変更の影響が及ぶ外側 | system-architecture.md |
| 構成要素の関係 | 責務の分かれ目 | system-architecture.md |
| 配置（どこで動くか） | 実行の単位と境界 | system-architecture.md |
| クラス・コードの構造 | 変更が触る型と、その関係 | structure-behavior.md |

**クラス・コードの階層は、変更が触る型だけに絞る。** 載せる範囲・追随義務・同期の時点は
`structure-behavior.md` のクラス図規約を唯一の定義として読む。
