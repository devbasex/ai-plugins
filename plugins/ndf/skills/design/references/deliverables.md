# 設計の成果物

**何を書くかはモードと領域の 2 つで決まる。** モードが水準を決め、領域が該当を決める。

## 水準は 2 つで、「不要」を置かない

**どの成果物も、変更の中身が求めれば書く対象になる。** モードが決めるのは無条件に求めるか
どうかであって、書いてはいけない成果物を決めるものではない。

| 水準 | 対象が存在するとき | 対象が存在しないとき |
| --- | --- | --- |
| 必須 | そのモードで `design` を通すなら書く | 書かない。**対象が無いことを、下の「省いた理由の書き先」へ書く** |
| 該当時 | 触る領域に当たれば書く | 書かない。理由も要らない |

**違いは、省いたときに理由が要るかである。** 値が 2 つとも「書きうる」を意味する以上、
区別できるのはここだけになる。

**「必須」を「無条件に書く」と読まない。** 対象が存在しない変更がある。型を持たない
リポジトリで `standard` の変更を行うと、クラス図の対象が 1 つも無い。無条件に求めると、
空の見出しか作り話が入る。

### 省いた理由の書き先

| モード | 書き先 |
| --- | --- |
| `light` / `operation` / `standard` | 仕様の「対象範囲（含まない）」 |
| `legacy-refactor` | 設計文書の「決定の記録」 |

**`legacy-refactor` だけが違うのは、このモードが仕様を入力に取らないためである**
（`SKILL.md` の「受け取るもの」。工程表でも「要求と受け入れ条件」を通らない）。書き先を
仕様に限ると、書く先が存在しない。省略のための節を新しく作ると、書くことが無いモードでも
空の見出しが残るため、既に必須の節である「決定の記録」を使う。

## モード × 成果物の要否

| 分類 | 成果物 | 形式 | `light` | `operation` | `legacy-refactor` | `standard` |
| --- | --- | --- | --- | --- | --- | --- |
| 全体 | 機能一覧表 | 表 | 該当時 | 該当時 | 該当時 | 必須 |
| 全体 | 構成要素図 | `graph` + `subgraph` | 該当時 | 該当時 | 必須（現状・変更後の 2 枚） | 必須 |
| 全体 | システム構成図（文脈・配置） | `graph` | 該当時 | 該当時 | 該当時 | 必須 |
| 構造 | クラス図 | `classDiagram` | 該当時 | 該当時 | 必須（現状・変更後の 2 枚） | 必須 |
| 構造 | オブジェクト図 | `graph` | 該当時 | 該当時 | 該当時 | 該当時 |
| 構造 | パッケージ・モジュール構成 | ツリー | 該当時 | 該当時 | 必須 | 必須 |
| データ | ER 図 | `erDiagram` | 該当時 | 該当時 | 該当時 | 該当時 |
| データ | テーブル定義 | 表 | 該当時 | 該当時 | 該当時 | 該当時 |
| データ | CRUD 図（機能 × データ） | 表 | 該当時 | 該当時 | 該当時 | 該当時 |
| 振る舞い | 処理の流れ | `sequenceDiagram` / `graph` | 該当時 | 該当時 | 該当時 | 必須 |
| 振る舞い | 状態遷移図 | `stateDiagram-v2` | 該当時 | 該当時 | 該当時 | 該当時 |
| 入出力 | 画面一覧・遷移図・項目定義 | 表 + `graph` | 該当時 | 該当時 | 該当時 | 該当時 |
| 入出力 | API 仕様記述 | OpenAPI（別ファイル） | 該当時 | 該当時 | 該当時 | 該当時 |
| 非機能 | 非機能設計表 | 表 | 該当時 | 必須 | 該当時 | 必須 |
| 全体 | 決定の記録 | 小見出し | 必須 | 必須 | 必須 | 必須 |
| 全体 | テスト設計 | 表 | 必須 | 該当時 | 該当時 | 必須 |
| 全体 | 未確認のまま残ること | 表 | 該当時 | 該当時 | 該当時 | 必須 |

**`operation` で非機能設計表だけを無条件にするのは、このモードが必ず外部の系の状態を変える
ためである。** 権限の設定・反映先の構成の変更・データの投入は、可用性・セキュリティ・
移行性・システム環境のいずれかに必ず当たる。実現方式を書かないまま実行すると、**戻せるか
どうかを実行の時点で初めて考えることになる。**

**`operation` と `legacy-refactor` でテスト設計を無条件にしないのは、そのモードで設計の節が
持てる範囲の外にあるためである。** `operation` の設計の節が足すのは、その構成を選んだ理由と
非機能の実現方式の 2 つだけである（下の「設計の書き先」と `operation-run.md`「設計を通る
場合の書き先」）。確かめ方は実行の記録が終了コードとして持つ。`legacy-refactor` は受け入れ
条件を入力に取らないため、「受け入れ条件と確かめ方の対応」の左側が存在しない。

**`legacy-refactor` で未確認のまま残ることを無条件にしないのも同じ理由である。** このモードの
設計文書は `design-template.md`「`legacy-refactor` の書き方」が定める 3 節（現状の構造・
変更後の構造・決定の記録）でできており、無条件の成果物はこの 3 節に収まるものに限る。要否表で
このモードが必須とする構成要素図・クラス図・パッケージ構成は前の 2 節へ、決定の記録は
3 節目へ入る。**節を増やす成果物を無条件にすると、要否表と雛形が食い違う。**

**該当の判定は領域が持つ。** 永続データを持たない変更へ ER 図を求めず、画面を持たない変更へ
画面一覧を求めない。領域と参照の対応は `SKILL.md` の「触る領域を決める」にある。

## 成果物ごとの中身

**書き方の詳細は領域ごとの参照が持つ。** ここに書くのは、何を載せるかまでである。

| 成果物 | 何を載せるか | 書き方の詳細 |
| --- | --- | --- |
| 機能一覧表 | この変更が作る・変える機能を、利用者から見た単位で並べる。誰が使うかを添える | 下の「機能一覧表」 |
| 構成要素図 | 要素と、要素どうしの関係。責務の分かれ目を示す | `system-architecture.md` |
| システム構成図 | 外部の系との関係（文脈）と、どこで動くか（配置） | `system-architecture.md` |
| クラス図 | 変更が触る型と、その関係 | `structure-behavior.md` |
| オブジェクト図 | ある時点の実体の関係。型だけでは伝わらない場合に使う | `structure-behavior.md` |
| パッケージ・モジュール構成 | 置き場所。ツリーで書く | `system-architecture.md` |
| ER 図 | 実体と関連。主キーと一意性の条件 | `data-structure.md` |
| テーブル定義 | 列の名前・型・空の値の扱い | `data-structure.md` |
| CRUD 図 | 機能がどのデータを作る・読む・更新する・消すか | `data-structure.md` |
| 処理の流れ | 呼び出しの順序と分岐 | `structure-behavior.md` |
| 状態遷移図 | 状態と、遷移の引き金 | `structure-behavior.md` |
| 画面一覧・遷移図・項目定義 | 画面の名前と役割、遷移、入力規則 | `interface-ui.md` |
| API 仕様記述 | 経路・入出力・失敗の形 | `interface-api.md` |
| 非機能設計表 | 要求側が書いた大項目ごとの実現方式 | `nonfunctional.md` |
| 決定の記録 | 結論・理由・採らなかった案 | `decisions.md` |
| テスト設計 | 受け入れ条件と確かめ方の対応 | `design-template.md` |
| 未確認のまま残ること | 確かめられなかったことと、いつ決まるか | `design-template.md` |

### 機能一覧表

**利用者から見た単位で並べる。** ファイルやクラスの単位で並べない。**実装の単位は構成要素の
表が持つ。**

```markdown
| # | 機能 | 誰が使うか |
| --- | --- | --- |
| F1 | 下書きを公開する | 記事の作成者 |
| F2 | 公開を取り消す | 記事の作成者と編集の担当 |
```

- 番号を付ける。テスト設計と受け入れ条件から、この番号で指せる
- **1 行が 1 つの受け入れ条件に対応するとは限らない。** 対応は「テスト設計」が持つ

## 設計の書き先

**独立した設計文書を作るのは `standard` だけである。**

| モード | 設計の書き先 | 設計 Pull Request |
| --- | --- | --- |
| `light` | 受け入れ条件を書いたファイルの節（`issues/` 配下） | 不要 |
| `operation` | 実行の記録と同じファイルの節（置き場所は `operation-run.md` が決める） | 不要 |
| `legacy-refactor` | 独立したファイル、または実装の Pull Request に載せる | 任意 |
| `standard` | 独立したファイル | 必須 |

**`light` / `operation` に独立したファイルを求めない。** 1 節で足りる内容のために設計文書と
設計 Pull Request が生まれ、工程が中身に見合わなくなる。

**`operation` では、`operation-run.md` が既に求めているものを再掲しない。** 実行の範囲・
取り消しの手段・記録の置き場所はそちらが持つ。設計が足すのは、**その構成を選んだ理由と
非機能の実現方式**である。

## 図の記法

**記法・横幅の上限・使ってよい形式は `markdown-writing` の図表ガイドが持つ。** ここでは
重ねて定めない。この文書が決めるのは、どの図を、いつ、どの粒度で描くかまでである。
