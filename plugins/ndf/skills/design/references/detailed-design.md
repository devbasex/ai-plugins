# 詳細設計

**詳細設計は、設計の後に置く工程と、その成果物である。** 設計文書の構成要素と構造を、ファイルと関数の粒度へ下ろし、
ファイル配置・関数ごとの責務と異常系の処理を実装の前に決める。設計 Pull Request に載せ、
`cross-review` と設計承認ゲートで責務の混在・重複・保存先の誤り・失敗の扱いの抜けを実装の前に止める。
読み手は実装する人とコードレビュー担当で、通読せずに要る構成要素を引いて読む。

| 項目 | 決まり |
| --- | --- |
| 通るモード | `standard`・`legacy-refactor`（工程の分類の「詳細設計」の行）。`light`・`operation`・`documentation` は通らない |
| 別ファイルにする条件 | `standard` では、**新設する関数が 2 つ以上あるか、既存の関数のシグネチャを変えるときだけ**別ファイルにする。それ以外は設計文書の「どこを変えるか」に畳む（下の「別ファイルにするか畳むか」）。`legacy-refactor` は今のとおり別ファイルに書く |
| 保存先 | `issues/issue-<番号の並び>-design-detail.md`。番号の並びは組になる設計文書と同じにする（`issue-7-8-design.md` なら `issue-7-8-design-detail.md`）。設計文書 1 本に 1 本置き、同じ設計 Pull Request に載せる |
| テンプレート | [detail-template.md](detail-template.md)。**セクションの見出しと表の列の唯一の保存先**で、ここでは並べ直さない |
| 長さ | 1 本 1,000 行以下。超える主題は設計を 2 本に分けると報告して止まる |
| 検査 | サブコマンドは無い。書いた側が、地図と構成要素ごとの小見出しがそろい、設計文書の構成要素がどれも詳細設計へ下りていることを読んで確かめる |
| 承認 | 承認ゲートを増やさない。設計と詳細設計をまとめて設計承認ゲートで 1 回見る |

## 別ファイルにするか畳むか

**判定は 2 つの数（新設する関数の数・シグネチャを変える既存の関数の数）だけで決め、書き手の判断を挟まない。**
関数 1 つの仕様は表の 1 行に収まり、別ファイルにすると 1 つの関数のために別の文書を開かせるためである。
条件の SSOT は `requirements-design` の [document-roles.md の「詳細設計を別ファイルにする条件」](../../requirements-design/references/document-roles.md#詳細設計を別ファイルにする条件) にある。

- 設計者が設計の工程で 2 つの数を数えて決め、設計文書の「どこを変えるか」の頭の 1 行（畳んだとき）か、詳細設計書へのリンク（別ファイルのとき）で示す。**どちらも無い設計文書は、工程「詳細設計」を終えていない**
- 畳んだときの書き方（頭の 1 行・表の列・新設する関数が 1 つのときの入力・返り・異常系・責務か失敗時の扱いだけを変える関数の変える前と後）は [design-template.md の「分量」](design-template.md#分量) にある
- 畳んだときの工程の出力は「設計書のセクションに畳んだ（<理由>）」の 1 行で、別ファイルは作らない。工程の完了は、設計文書に「どこを変えるか」があり、触るファイルが「設計の結果」の触るファイルと一致し、新設する関数が 1 つあるときはその行に入力・返り・異常系があること

## 書く範囲

**書く関数は、新設する関数と、シグネチャ・責務・失敗の扱いのいずれかを変える関数だけである。** 変えない関数は書かない。
呼ぶ引数を 1 つ足すだけの関数のように、上の 3 つを変えないものは地図の表に名前だけを置き、
「関数の仕様」には書かない。

**当たらないセクションは見出しごと消す。** 「無し」「省く:」と書かない。表の列も、当たらない列（境界値など）は
「無し」で埋めずに列ごと消してよい。調べた詳細設計で「事前条件」の列の半分近くが「無し」か「—」で、読み手に
書くことの無いセルを読ませていたためである。比べたいのは関数の仕様の 5 列（関数・保存先・種類・シグネチャ・責務）で、
この 5 列は消さない。

**ソースのコメントや型の定義で読める情報は、写さずに場所を指す。** 既にあるものを写すと、片方だけ直されて食い違う。

**クラスを持たない言語では、関数とモジュールで書く。** 地図の表の「クラスまたはモジュール」の列は、モジュールとその最上位の関数で埋める。

**詳細設計は実装の後に追随させない。** コードの粒度の図や一覧は IDE とコードが SSOT になる。詳細設計は、実装の前に
設計レビューで見るための文書である。実装が詳細設計から外れた箇所は、完了判定の設計との突き合わせ
（`quality-gates` の `references/design-match.md`）が並べる。

## 項目ごとの書き方と既存の参照との分担

**既存の参照が持つ事実を詳細設計で二重に書かない。** 下の表の「既存の参照」の列が持つものは、詳細設計からはそこを指す。
並びは地図 → 構成要素ごとの小見出しで、小見出しの中の項目はこの表の 2 行目からの順に置く。［当たるとき］の印の項目は、当たる構成要素だけに置く。

| セクション | 書くこと | 既存の参照 |
| --- | --- | --- |
| 地図 | パッケージ・モジュール構成のツリーと、依存の向き（一方向で循環が無いこと）を 1 段落。続けて、新設・変更・削除するファイルのパス・種類・役割 1 文・依存する先・クラスまたはモジュールと新設・変更するメソッドと最上位の関数の名前の表 | 構成要素の粒度は設計文書（`system-architecture.md`）。クラス図は設計文書の「構造」のセクション（`structure-behavior.md`）を指し、描き直さない。パッケージ・モジュール構成を設計文書に写さない |
| 満たす決定（構成要素の小見出しの最初の行） | `満たす決定: 決定 <番号>、受け入れ条件 <番号>`。実装する人が、作るものとそれが満たす約束を同じ場所で引くため | 決定の中身は設計文書の「決定の記録」、受け入れ条件の中身は要求仕様 |
| 関数の仕様 | 表は 関数・保存先・種類（`新設` か `変更`）・シグネチャ（引数と戻り値の型）・責務 1 文 の 5 列。事前条件（呼ぶ側が満たすこと）・事後条件（終わったときに成り立つこと。手順でなく設定の形）・副作用（ファイル・外部コマンド・ネットワーク）は、当たる関数だけ表の下に関数ごとの箇条で書く | 外から呼ばれる約束は `interface-api.md` が持つ。ここは内部の関数だけ |
| 異常系の処理 | 関数ごとの失敗・原因・検出する場所・扱い（呼び出し元へ返す / 再試行 / 既定値で続ける / 止める）・利用者に見える出力と終了コード・後始末と再実行の可否 | 境界の失敗の形は `interface-api.md`、要素をまたぐ失敗の経路は `structure-behavior.md`。ここは関数の粒度だけ |
| ［当たるとき］処理の手順 | 分岐の多い関数の判定表（条件の組み合わせと結果）。繰り返しの終わる条件と計算量の注意は表の後に箇条書き | 要素をまたぐ順序は設計文書の「処理の流れ」 |
| ［当たるとき］内部のデータと定数 | 関数の間で受け渡す内部の型・定数・閾値・設定値の保存先と既定値。**同じ事実を 2 か所の定数に持たない**（唯一の保存先を書く） | 永続データは `data-structure.md` |
| ［当たるとき］並行と排他 | 同時に走りうる処理（プロセス・レーン・hook）・共有する資源（ファイル・状態・ブランチ）・排他の取り方・冪等性と中断からの再開 | 無し（ここだけが持つ） |
| ［当たるとき］ログと記録の出力 | どの関数が何をどのレベルまたは書き先（ログ・結果 JSON・進捗記録）へ出すか、出さないもの（秘密） | 基準は `logging-guidelines` Skill。ここは適用先だけ |
| ［当たるとき］既存の部品の再利用 | 新設する関数ごとに、確かめた既存の関数・ライブラリ・確かめた手段（検索の語とコマンド）・結果（使う / 使えない理由） | ライブラリの比較は設計文書の「外部の調査」。ここは関数の粒度の確認だけ |
| 単体テストの観点 | 関数ごとの正常・境界値・異常（異常系の処理の行ごと） | 受け入れ条件の粒度は設計文書の「テスト設計」 |

## 検査が見ること

書いた側の確かめは詳細設計の文書の形を見る。中身の妥当さ（責務の分け方・再利用の見落とし）は `cross-review` の
設計 Pull Request の詳細レビューが見る。

- 地図があり、設計文書の構成要素（無ければ「どこを変えるか」の行）ごとに小見出しがあり、どの小見出しも最初の行に満たす決定を持つ
- 関数の仕様の表の 5 列がそろっている。副作用の箇条を持つ関数が、異常系の処理の表の 1 列目にある
- 関数の仕様の表で種類が `新設` の関数が、既存の部品の再利用の表の 1 列目にある
- 地図の表のパスが、設計文書の「設計の結果」の触るファイルに含まれる。`legacy-refactor` の書式（「設計の結果」が
  無く「現状の構造」「変更後の構造」がある）では検証せず、地図の表が触るファイルの SSOT になる
- `--require-detail` を付けたとき、詳細設計の文書がある

## 設計のプランでの位置

設計のプラン（`ndf route render design`）は、詳細設計を通るモードで次の順にステップを並べる。

1. `design`: 設計文書を書く（詳細設計は書かない）
2. `design-review`: 設計文書と要求のコピーだけを 1 つの AI がレビューし、作業ディレクトリの `design-review.md` へ書く
3. `design-review-check`: 指摘が無ければ詳細設計へ、あれば直しへ進む
4. `design-fix`: 指摘を直す。直せない指摘は `直さない: <理由>` を残し、設計 Pull Request の本文に載る
5. `detail-design`: 直した設計の上に詳細設計を書く（`/ndf:design #<番号> 詳細設計`。工程「詳細設計」）。畳む条件に当たれば別ファイルを作らず、「設計書のセクションに畳んだ（<理由>）」を出力にする

設計単体のレビューは `cross-review` にしない。直した設計は、詳細設計と合わせて後の設計 Pull Request の
`cross-review` がもう一度見る。畳んだときは、2 の設計単体のレビューが「どこを変えるか」を含む設計文書を見るので、
詳細設計のレビューを兼ねる。
