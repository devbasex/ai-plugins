# 詳細設計

**詳細設計は、設計の後に置く工程と、その成果物である。** 設計文書の構成要素と構造を、ファイルと関数の粒度へ下ろし、
ファイル配置・クラスと関数の構造・関数ごとの責務と異常系の処理を実装の前に決める。設計 Pull Request に載せ、
`cross-review` と設計承認ゲートで責務の混在・重複・置き場の誤り・失敗の扱いの抜けを実装の前に止める。

| 項目 | 決まり |
| --- | --- |
| 通るモード | `standard`・`legacy-refactor`（工程の分類の「詳細設計」の行）。`light`・`operation`・`documentation` は通らない |
| 置き場 | `issues/issue-<番号>-design-detail.md`。設計文書と同じ課題に 1 本置き、同じ設計 Pull Request に載せる |
| 雛形 | [detail-template.md](detail-template.md)。**節の見出しと表の列の唯一の置き場**で、ここでは並べ直さない |
| 長さ | 1 本 1,000 行以下。超える主題は設計を 2 本に分けると報告して止まる |
| 検査 | `design-survey.py check --file <設計文書> <詳細設計の文書> --require-detail`（規則は `design-survey.py` の冒頭） |
| 承認 | 承認ゲートを増やさない。設計と詳細設計をまとめて設計承認ゲートで 1 回見る |

## 書く範囲

**書く関数は、新設する関数と、シグネチャ・責務・失敗の扱いのいずれかを変える関数だけである。** 変えない関数は書かない。
呼ぶ引数を 1 つ足すだけの関数のように、上の 3 つを変えないものは「クラスと関数の構造」に名前だけを置き、
「関数の仕様」には書かない。

**当たらない節は見出しを残し、本文を `省く: <理由>` の 1 行にする。** 見出しを消すと、検査が「書き忘れ」と
「当たらない」を見分けられない。理由の空の `省く:` は検査が指摘する。

**クラスを持たない言語では、関数とモジュールで書く。** 「クラスと関数の構造」の列は、モジュールとその最上位の関数で埋める。

**詳細設計は実装の後に追随させない。** コードの粒度の図や一覧は IDE とコードが正本になる。詳細設計は、実装の前に
設計レビューで見るための文書である。実装が詳細設計から外れた箇所は、完了判定の設計との突き合わせ
（`quality-gates` の `references/design-match.md`）が並べる。

## 項目ごとの書き方と既存の参照との分担

**既存の参照が持つ事実を詳細設計で二重に書かない。** 下の表の「既存の参照」の列が持つものは、詳細設計からはそこを指す。

| 節 | 書くこと | 既存の参照 |
| --- | --- | --- |
| ファイル配置 | 新設・変更・削除するファイルのパス・役割 1 文・依存する先。表の前にパッケージ・モジュール構成のツリーを置き、依存の向き（一方向で循環が無いこと）を 1 段落で書く | 構成要素の粒度は設計文書（`system-architecture.md`）。このモードではパッケージ・モジュール構成を設計文書に写さない |
| クラスと関数の構造 | 置き場ごとのクラスまたはモジュールと、新設・変更するメソッドと最上位の関数の名前 | クラス図は設計文書の「構造」の節（`structure-behavior.md`）を指し、描き直さない |
| 関数の仕様 | シグネチャ（引数と戻り値の型）・責務 1 文・事前条件（呼ぶ側が満たすこと）・事後条件（終わったときに成り立つこと。手順でなく宣言の形）・副作用（ファイル・外部コマンド・ネットワーク。無ければ `無し`）。種類は `新設` か `変更` | 外から呼ばれる約束は `interface-api.md` が持つ。ここは内部の関数だけ |
| 異常系の処理 | 関数ごとの失敗・原因・検出する場所・扱い（呼び出し元へ返す / 再試行 / 既定値で続ける / 止める）・利用者に見える出力と終了コード・後始末と再実行の可否 | 境界の失敗の形は `interface-api.md`、要素をまたぐ失敗の経路は `structure-behavior.md`。ここは関数の粒度だけ |
| 処理の手順 | 分岐の多い関数の判定表（条件の組み合わせと結果）。繰り返しの終わる条件と計算量の注意は表の後に箇条書き | 要素をまたぐ順序は設計文書の「処理の流れ」 |
| 内部のデータと定数 | 関数の間で受け渡す内部の型・定数・閾値・設定値の置き場と既定値。**同じ事実を 2 か所の定数に持たない**（唯一の置き場を書く） | 永続データは `data-structure.md` |
| 並行と排他 | 同時に走りうる処理（プロセス・レーン・hook）・共有する資源（ファイル・状態・ブランチ）・排他の取り方・冪等性と中断からの再開 | 無し（ここだけが持つ） |
| ログと記録の出力 | どの関数が何をどのレベルまたは書き先（ログ・結果 JSON・進捗記録）へ出すか、出さないもの（秘密） | 基準は `logging-guidelines` Skill。ここは適用先だけ |
| 既存の部品の再利用 | 新設する関数ごとに、確かめた既存の関数・ライブラリ・確かめた手段（検索の語とコマンド）・結果（使う / 使えない理由） | ライブラリの比較は設計文書の「外部の調査」。ここは関数の粒度の確認だけ |
| 単体テストの観点 | 関数ごとの正常・境界値・異常（異常系の処理の行ごと） | 受け入れ条件の粒度は設計文書の「テスト設計」 |

## 検査が見ること

`design-survey.py check` は詳細設計の文書の形を見る。中身の妥当さ（責務の分け方・再利用の見落とし）は `cross-review` の
設計 Pull Request の詳細レビューが見る（観点は `cross-review` の `review_focus.py` の `DETAIL_REVIEW_TEMPLATE`）。

- 雛形の節がすべてあり、各節が表の行か `省く: <理由>` を持つ
- 関数の仕様の表で副作用が `無し` でない関数が、異常系の処理の表の 1 列目にある
- 関数の仕様の表で種類が `新設` の関数が、既存の部品の再利用の表の 1 列目にある
- ファイル配置の表のパスが、設計文書の「設計の結果」の触るファイルに含まれる。`legacy-refactor` の書式（「設計の結果」が
  無く「現状の構造」「変更後の構造」がある）では照合せず、ファイル配置の表が触るファイルの正本になる
- `--require-detail` を付けたとき、詳細設計の文書がある

## 工程の進行表での位置

詳細設計を通るモードの工程の定義（`plugins/ndf/contracts/workflow/modes/<モード>.json`）は、`設計` の工程の次に `詳細設計` の工程を置く。
`設計` は設計文書を書き（詳細設計は書かない）、`詳細設計` はその上に詳細設計を書く（`/ndf:design #<番号> 詳細設計`）。
設計と詳細設計は、後の `ドキュメントレビュー` の工程の `cross-review` が合わせて見る。
