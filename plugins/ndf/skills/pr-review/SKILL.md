# コードレビューコマンド

PR 差分、または `--branch` 指定時は現在のブランチの差分を、専門家としてレビューする。

## 引数

| 引数 | 意味 | 既定 |
|---|---|---|
| `[PR番号]` | レビュー対象の PR | 今のブランチの PR |
| `--branch` | PR ではなく **ローカルブランチの差分**をレビューする（PR 作成前のセルフレビュー） | OFF |
| `[AIエージェント]` | `codex` / `agy` に委譲。省略時は Claude 自身 | Claude |
| `--focus AREA` | 重点観点（`security` / `performance` / `tests` / 任意の文字列） | なし |

```
/ndf:pr-review                       # 今のブランチの PR をレビュー
/ndf:pr-review 9352                  # PR 番号を指定
/ndf:pr-review 9352 codex            # Codex CLI に委譲
/ndf:pr-review --branch              # ローカルブランチをセルフレビュー
/ndf:pr-review --branch security     # セキュリティに焦点を当ててセルフレビュー
```

## 2 つのモード

| 観点 | PR モード（既定） | `--branch` モード |
|---|---|---|
| 対象 | GitHub 上の PR 差分 | `git diff origin/<ベースブランチ>` の差分 |
| 出力先 | **PR 上にレビュー（総評と指摘）を投稿** | セッション上の報告のみ（投稿しない） |
| 判定 | `APPROVE` / `REQUEST_CHANGES` / `COMMENT` | 判定を出さず改善提案を返す |
| 用途 | PR 作成後のレビュー | PR 作成前のセルフレビュー |

**どちらのモードでもコード修正は行わない**（分析と指摘のみ。修正は `/ndf:fix`）。

## 観点

**第 1 ステップ（仕様適合）を先に通す。** コード品質だけを見ると、きれいに書かれた「仕様を
満たさない実装」を通してしまう。

### 第 1 ステップ: 仕様適合

| 確認 | 見るもの |
| --- | --- |
| 受け入れ条件を満たすか | プラン・PR 本文の受け入れ条件と、対応するテスト |
| ドメインの不変条件を破っていないか | 状態遷移・数量・期限・権限の扱い。上位層から迂回して不整合な状態を作れないか |
| 対象範囲外の変更がないか | リクエスト・プランの範囲と差分の一致。無関係な整形や改名の混入 |
| テストが仕様を表しているか | テスト名と検証内容が受け入れ条件に対応しているか。実装の複製になっていないか |

第 1 ステップで**満たさない項目があれば、その時点で `REQUEST_CHANGES` とする**。第 2 ステップの
指摘を積み上げても、仕様を満たさない実装は直しようがない。

受け入れ条件が PR 本文にもプランにも書かれていない場合は、その不在自体を指摘する
（条件がなければ第 1 ステップのレビューが成立しない）。

### 外部の調査の確認

設計 PR（`issues/issue-<番号>-design*.md` を変える PR）と実装 PR（コードを変える PR）で、触る領域の
業界の標準・仕様、主要な製品の解き方、既存のライブラリとサービスと比べたかを見る。比べる材料は、設計文書の
セクション `## 外部の調査`（調べた行の番号は `STD<数>` / `PRD<数>` / `LIB<数>`、取得できなかった対象は小見出し
「確かめられなかったこと」）と、決定ごとの `作り方:`（自前で作る / ライブラリやサービスを使う / 標準に倣う）と
`比べた候補:`（表の行の番号）の 2 行である。下の指摘の重要度は、どれも `major` とする。

| 区分 | 見ること | 指摘にする条件 |
| --- | --- | --- |
| 設計 PR | 外部の調査のセクション | セクションが無い。通したのに、3 種類（標準・仕様 / 主要な製品 / ライブラリとサービス）ごとの調べるかと、調べない理由が無い。省いたのに `省く: <理由>` の理由が無い |
| 設計 PR | 自前で作る決定 | 作り方に「自前で作る」を含む決定に、比べた候補が無い。機能をどう得るかを決めた決定に、作り方の行が無い。ただし、同じまとまりの設計文書（名前の番号を 1 つでも共有する `issue-<番号>-design*.md` と、それをたどってつながる文書のどれか。たとえば `issue-7-design.md` は `issue-7-8-design.md` を介して `issue-8-design.md` と同じまとまりになる）で外部の調査を理由つきの `省く:` で省いたときは、候補が無いことを指摘にしない |
| 設計 PR | 調べた行の出典 | 出典（URL・パス・コマンドのどれかと取得日）が無い。取得日が設計 PR を出した日より 90 日以上前 |
| 設計 PR | 確かめられなかったこと | 取得できなかった対象を、推定で表の行に埋めている |
| 実装 PR | 同じ課題の設計文書 | 設計で「ライブラリやサービスを使う」とした機能を自前で作った（仕様適合の指摘として扱う）。設計に作り方の行が無い自前の部品を足した。新しく足した依存（ライブラリ・サービス）が設計の比べた候補に無い |
| 両方 | 自分で調べた結果 | 表に無い標準・ライブラリ・主要な製品の形で、要求を満たすと出典で示せるもの（比べた候補の見落とし）。表の行のバージョンより新しいバージョンか、終了のアナウンスが取得日の後に出ている |

実装 PR では、PR の題・本文・ブランチ名にある課題の番号から、worktree の `issues/issue-<番号>-design*.md` を
探して読む。見つからないときは、設計が無いことを指摘にせず、見つからなかったことを総評に書く（設計を通さない
変更がある）。設計文書に作り方の行が 1 つも無い課題（この確認より前に書いた設計）では、作り方の行が無いこと
自体を指摘にしない。

外部を調べるときの規則:

- 調べてよいのは、自分のランタイムがすでに持つ取得の手段（Web 検索・URL の取得・`gh` など）だけである。手段の設定は変えない
- 調べる対象は、自前で作る決定・新しく足した依存・出典の古い行に絞る。設計の外部の調査を最初からやり直さない
- 取得の試み（検索 1 回・URL の取得 1 回をそれぞれ 1 と数える）は、1 ラウンドに 10 回までにする。上限に当たったら止め、残りを総評に書く
- 指摘には、取得した出典（URL と取得日）を添える。取得できなかったときは、推定で「より良いものがある」と指摘しない。試した URL か検索の語と、理由（拒否・HTTP の状態・ネットワークの誤り・上限）を総評に書く

### 第 2 ステップ: コード品質

| 確認 | 見るもの |
| --- | --- |
| 責務・凝集度・結合度 | 1 つの単位が複数の変更理由を持っていないか |
| 依存の向き | 業務ロジックが外部の仕組みへ直接依存していないか。循環がないか |
| 可読性・単純性 | 分岐の深さ、名前と実態の一致、不要な抽象化 |
| コードの兆候 | 重複、長すぎる単位、基本型への固執など（`refactoring` の一覧） |
| セキュリティ・性能 | 下の「具体的なチェックポイント」 |
| テストが実装詳細に結合していないか | 内部呼び出し回数の検証、private への直接依存（`tdd-cycle` の脆いテスト） |

### 具体的なチェックポイント（第 2 ステップの詳細）

- **その言語らしい記述方式**: イディオム・標準ライブラリ・言語機能の活用
- **メモリ効率・演算性能**
  - キャッシュ利用、不要なループ・コピーの排除
  - Python: numpy 利用、内包表記、ジェネレータ
  - PHP: switch 文の map（連想配列）化
  - N+1 クエリ、不要なデータベースアクセス、インデックスの活用
- **関数・メソッド・ファイル行数の適正化**
  - 目安: 関数/メソッド 50 行、ファイル 300 行。ただしプロジェクトの慣例に従う
  - 単一責任原則から外れていないか
- **重複・冗長コードの排除**
  - PR 範囲にこだわらず積極的にまとめるよう指摘
  - 逆に過剰な抽象化（YAGNI 違反）も指摘する
- **柔軟性を損なう定数化の排除**
  - 数字をそのまま定数にするような硬直化を避ける
  - 定数よりも DB の master テーブル、または json/yaml による外部化を検討
- **セキュリティ**
  - SQL インジェクション / XSS / CSRF 対策、入力値バリデーション
  - 認証・認可の適切性、機密情報（トークン、キー、個人情報）の取り扱い
- **エラーハンドリング**
  - 例外が適切に捕捉されているか、リトライ / タイムアウトの設計
  - ログ出力の妥当性（詳細は `/ndf:logging-guidelines`）

`--focus` が指定された場合は、該当する観点を優先し、他の観点は重大なもののみ指摘する。

### 重要度

| 重要度 | 定義 | 後工程（`/ndf:fix`）の扱い |
|---|---|---|
| `critical` | セキュリティ・データ破損・本番障害につながる | **必ず自動修正** |
| `major` | 保守性・性能・仕様逸脱の重要問題 | **必ず自動修正** |
| `minor` | 改善推奨（マージを止めない） | **直さず**、見送りの返信を付けて閉じる（`waived`）。中身が指摘の基準（`/ndf:fix` の「重要度の判定」）に当たれば `major` 以上として直す |
| `nit` | 好み・スタイル | **直さず**、見送りの返信を付けて閉じる（`waived`） |

過剰な nit 量産は避ける。critical / major で対応すべき真の問題に集中すること。

## 指摘の振り分け

| 指摘の種類 | レビューの本文での書き方 |
|---|---|
| 特定の行・ファイル単位（行を絞れなければ代表行） | 「指摘」の項目に `<path>:<line>`・重要度・中身を 1 件ずつ |
| 複数ファイルにまたがる設計指摘 | 代表箇所の `<path>:<line>` で 1 件にし、ほかの箇所を中身に並べる |
| 設計レベル・PR 全体の所見 | 総評（個別の指摘を繰り返さない） |
| 第 1 ステップで満たさない項目 | 総評の冒頭の「仕様適合」に載せる |
| この PR の範囲外 | `/ndf:out-of-scope` で起票し、番号を総評へ書く（起票先はその Skill が決める） |

## 手順

11 系に PR のレビューを受け持つサブコマンドは無い。対象と差分を `gh`・`git` で読み、AI が指摘をまとめて `gh pr review` で投稿する。

Claude 自身がレビューする（第二引数なし）:

1. **対象と差分を読む。** PR モードは `gh pr view <番号> --json number,title,body,baseRefName,headRefName,author,files` と
   `gh pr diff <番号>`、既存のレビューとコメントは `gh pr view <番号> --comments` で読む。`--branch` は
   `git diff origin/<ベースブランチ>...HEAD` を読む。受け入れ条件は PR の本文と、本文の課題の番号から `gh issue view` で読む
2. **「観点」で第 1 ステップ → 第 2 ステップの順に見る。** 第 1 ステップで満たさない項目が出たら、第 2 ステップは同じ箇所を
   直すときに一緒に直すものだけに絞る。未解決のスレッドと同じ趣旨の指摘は出さない。指摘は「指摘の振り分け」の形で
   重要度の高いものから並べ、良い点は列挙しない
3. **判定を決める。** `critical` / `major` か仕様適合の指摘があれば `REQUEST_CHANGES`、`minor` / `nit` だけなら `COMMENT`、
   0 件なら `APPROVE`
4. **投稿する（PR モードだけ）。** 総評と指摘を本文のファイルに書き、判定に合わせて 1 回投稿する

```bash
gh pr review <番号> --approve --body-file <本文のファイル>           # APPROVE
gh pr review <番号> --request-changes --body-file <本文のファイル>   # REQUEST_CHANGES
gh pr review <番号> --comment --body-file <本文のファイル>           # COMMENT
```

自分の PR は GitHub が approve と request changes を受け付けないため `--comment` で送り、本文の冒頭に本来の判定を書く。
`--branch` は投稿せず、同じ本文をセッション上に報告する。

外部 AI への委譲（第二引数 `codex` / `agy`）は `/ndf:external-ai` の手順でその CLI を起動する。プロンプトには「観点」・
「指摘の振り分け」・手順 1 で読んだ対象と差分（か、その読み方）を渡し、指摘と判定を本文の形で返させる。外部 AI には
投稿させず、返った本文を手順 4 で投稿する。上限越え・結果なし・読めない結果では投稿しない。**Claude 自身による追加判定は
行わず**、外部 AI の指摘と判定をそのまま採用する。

## 作業完了報告（必須）

利用エージェント（claude / codex / agy）・投稿したレビューの URL・判定（自分の PR なら本来の判定と送った形）・重要度ごとの
件数・総評の要約と PR URL を報告する。指摘の中身は PR 上にあるため繰り返さない。`--branch` では本文をセッション上に出す。
レビュー結果は提案であり、最終判断は開発者が行う。
