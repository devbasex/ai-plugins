# 実装計画ガイド

## 基本方針

実装の開始時およびPR作成時に、`issues/` 配下に実装計画のファイルが存在するか確認し、なければ作成する。プランを残すことで後任エンジニアや将来の自分が変更意図を追跡できる。

実装計画の読み手は、実装する人（worker）とコードレビュー担当である。読み手が下す判断は「どの順で、どのタスクに分けて作るか」で、タスクごとに引いて読む。実装計画が持つ事実はこれだけにし、何を満たすか（要求仕様）とどう解くか（設計書）は書かずにリンクと受け入れ条件の番号で指す。前の文書の要点を写すと、片方だけ直されて食い違うためである。文書ごとの読み手と順序は [文書の役割の表](../requirements-design/references/document-roles.md) が持つ。

## 実装計画を書くか

**書くか省くかは、`requirements-design` の [文書の役割の表の「省いてよい文書と条件」](../requirements-design/references/document-roles.md#省いてよい文書と条件) で、4 つの値を数えて決める。** 書き手の勘で決めない。

## ファイル配置・命名

- パス: `issues/`
- ファイル名に日本語は含めないこと（Git/CI/検索ツール互換性のため）
- 課題の番号がある場合: `issues/issue-<番号>-plan.md`。設計書を省いたときは必ずこの名前にする（実装の完了判定がこの名前で実装計画を探すため。`quality-gates` の [design-match.md](../quality-gates/references/design-match.md)）
- タスクIDがある場合: `issues/TASK-1234_concise-description.md`
- どちらも無い場合: `issues/{feature-name}.md`

## PR作成時の実装計画のファイル生成

PR作成時に `issues/` に実装計画のファイルが存在しない場合、以下の情報源から実装計画のファイルを生成する:

1. **会話履歴** - それまでのやりとりから要件・背景・方針を抽出
2. **git log** - コミット履歴からタスクの流れと変更概要を把握
3. **git diff** - 実際の変更内容から修正対象ファイルと変更内容を特定

これらを組み合わせて、「実装計画のフォーマット」に沿った実装計画のファイルを作成してからPRを作成する。

## 対象ファイルの出所

**「修正対象」と各タスクの「対象ファイル」は、前の文書の 1 か所から引き写す。** 対象ファイルの出所を 1 か所にし、設計レビューで見た保存先と実装の保存先をずらさないためである。引き写す先は、ある文書だけで 1 つに決まる。

| ある文書 | 引き写す先 |
| --- | --- |
| 詳細設計書（名前に含む番号のどれかが課題の番号と一致する `issues/issue-<番号の並び>-design-detail.md`。番号の並びは設計書と同じ） | その「モジュールマップ」と、構成要素ごとの関数の仕様 |
| 設計書だけ（詳細設計を畳んだ） | 設計書の「どこを変えるか」の表。そのセクションを持たないモードの設計文書では、「設計の結果」の触るファイルと構成要素 |
| 設計書も省いた | 引き写す先は無い。実装計画の「修正対象」に、ファイルと関数ごとの変える前と後を自分で書く（下の「設計書を省いたとき」） |

表に無いファイルを足すときは、そのタスクの「変更内容」に足す理由を書く。

## 前工程 Skill との関係

| 質問 | 担当 |
| --- | --- |
| どの工程が必要か（モード判定） | `development-workflow` |
| 何を満たすか（受け入れ条件・仕様） | `requirements-design` |
| どう作るか（データ構造・入出力のコントラクト・決定の理由） | `design` |
| **どう分解するか（この実装計画）** | この Skill |
| どう作るか（失敗するテスト → 実装） | `tdd-cycle` |
| 満たしたと言えるか（証跡） | `quality-gates` |

受け入れ条件が未確定のままタスクを並べない。分解の単位は受け入れ条件に紐づく。
設計文書がある場合は、そのセクション（構成要素・データ構造・入出力のコントラクト・テスト設計・どこを変えるか）からタスクを導く。
これらの Skill が導入されていない環境では、実装計画の中に受け入れ条件と検証手段を直接書く。

## 実装計画のフォーマット

テンプレートは [references/plan-template.md](references/plan-template.md)。**実装計画を書く前に読む。** 見出しの並びと各欄に何を書くかは
テンプレートが持ち、ここでは決め方を持つ。目的・前提・受け入れ条件・採らなかった案・用語・互換性は、要求仕様と設計書が持つので書かない。

**なぜその分け方と順番にするのかを書く。** タスクの分け方と順番の理由、レビューの単位の分け方の理由が無いと、設計レビューで
順番の妥当さを確かめられず、実装の途中で組み替えてよいかも判断できないためである。

### タスク分解の最初のタスク

**最初のタスクは変更の種類で決まる。** 新規作成は場面 1 つを通しで動かす、機能追加は今の振る舞いを縛る退行テスト、不具合は再現のテスト（今は落ちる）を最初に置く。変更の種類は要求仕様の「種類」にあり、種類ごとの中心は文書の役割の表の [変更の種類ごとの中心](../requirements-design/references/document-roles.md#変更の種類ごとの中心) にある。準備のリファクタリングで整えると決めたときは、それをさらに前に置く（下の「リファクタリングの時機」）。

### レイヤー単位で分けない

```text
❌ Task 1: モデル層をすべて作る / Task 2: サービス層 / Task 3: 画面
   → どのタスクが終わっても動く機能がなく、検証が最後にまとまる

✅ Task 1: 一覧を表示する（モデル〜画面まで通す）
   Task 2: 絞り込みを追加する
   → 各タスクの完了時点で受け入れ条件を 1 つ満たせる
```

### レビューの単位

**「タスク分解」の後ろに必ず書く。** レビュー担当が 1 回で読み切れる差分にするためである。表は単位ごとに 1 行で、列は 単位の名前・含むタスク・満たす受け入れ条件（番号）・見込みの差分の行数 とする。

決め方は次の順にする。

1. 1 つの課題を 1 つの単位にする
2. 見込みの差分が 1,000 行を超える課題は、タスクの依存の向きで分ける。どの単位も単独でテストが通り、終えた後も動くようにする（人やレイヤーで分けない。行数だけで機械的に切ると、依存の途中で切れて単位が単独で読めない）
3. 同じファイルを触り、片方の後でないともう片方を読めない小さな課題（合わせて 400 行以下）は、1 つの単位に束ねてよい

**大きさの目安は 1 単位 400 行以下で、1,000 行を超える単位は作らない。** 行数は追加と削除の和で、`git diff --shortstat` で数える。再生成で作るファイルとロックファイルは数えず、数えないパスは欄に書く（例: `git diff --shortstat <ベース>...HEAD -- . ':(exclude)uv.lock'`）。見込みは計画を書くときの見積もりで、実装の後に実際の行数を表の横の列に書き足す。見込みが外れたときは、実装の途中で単位を分け直す。

単位ごとに Pull Request を分けるか、どの工程でレビューを掛けるかは、工程表の側（`development-workflow`）が決める。実装計画は単位とその決め方だけを持ち、行がどこへ渡るかは下の「欄の行が渡る先」にある。

### リファクタリングの時機

**「レビューの単位」の後ろに必ず書く。** 局所の整理で終わらせず、単位をまたいでまとめて見る場所も持つためである。表は次の 3 行で、行ごとに対象（ファイルや処理）と理由を書く。

| 時機 | 何を整えるか | 計画に書くこと |
| --- | --- | --- |
| 実装の前（準備のリファクタリング） | これから積む先の構造が危うい箇所 | [references/pre-refactoring.md](references/pre-refactoring.md) の基準で整えると決めた対象と理由。整えるときは最初のタスクにする（進め方は同じ文書の「先に整えると決めたら」）。整えないときは「しない」と、測った値（触るファイルの行数・同じファイルを触るタスクの割合・テストの数） |
| 実装の中（TDD のリファクタリングのステップ） | タスクの中で書いたコードの重複と名前 | 「各タスクで行う」の 1 行だけ。どのタスクでも `tdd-cycle` のステップとして行う |
| スプリントの終わり（単位をまたぐ cross-refactoring） | 単位をまたぐ重複と構造 | 計画を書いた時点で見える候補（複数の単位が触る同じファイル・同じ形の処理）と理由。候補が無ければ「しない」と理由。候補は `cross-refactoring` の提案の入力になるだけで、採るかは `cross-refactoring` が予算の中で決める |

**準備とスプリントの終わりの行は、対象が無くても消さずに「しない」と書く。** 当たらないセクションを消す決まりの例外で、判断したことを残すための 1 行である（残っていないと、後から「判断した」のか「気づかなかった」のかを区別できない）。3 つの時機を工程表のどこに置くかは `development-workflow` が決める。

**「先に整える」を選択肢に入れていないと、書く手がかりが無いまま欄が空で残る。**
#436 の実装計画では、10 タスクのうち 9 つが 3706 行の 1 ファイルを触ると分かっていながら、
対処が「タスクごとにテストを通す」だけだった。

### 欄の行が渡る先

「レビューの単位」と「リファクタリングの時機」の行は、計画の後の工程がそのまま読む。書いた値を工程ごとに書き直さないためである。

| 欄の行 | 渡る先 |
| --- | --- |
| レビューの単位の 1 行 | 実行計画の実装の行 1 つと、実装のプラン 1 本になる。単位ごとに単位の PR をスプリントブランチへ出し、その PR で `cross-review` を収束まで回す（`issue-plan-strategy` の [execution-plan.md](../issue-plan-strategy/references/execution-plan.md)） |
| その行の満たす受け入れ条件 | 実装のプランの `acceptance`（`ndf loop acceptance check` の引数の並び）になる。課題を分けた単位は `--criteria <課題>:<条件>`、課題を束ねた単位は課題ごとの `--issue` になる（組むコマンドは `development-workflow` の [agent-layers.md の「実装のフェーズの単位」](../development-workflow/references/agent-layers.md#実装のフェーズの単位)） |
| リファクタリングの時機の実装の前 | 最初のタスクになり、そのタスクを含む単位が最初に流れる |
| リファクタリングの時機のスプリントの終わり | 工程「リファクタリング」のプランを組むときに集められ、`cross-refactoring` の提案へ `--candidates` で渡る |

満たす受け入れ条件は番号（`<課題>:<条件>` に直せる形）で書く。単位どうしで漏れた条件は、スプリントの完了判定がすべての課題の条件を照らして拾う。

### 設計書を省いたとき

省いてよい条件は文書の役割の表の [省いてよい文書と条件](../requirements-design/references/document-roles.md#省いてよい文書と条件) にある。

- 実装計画を `issues/issue-<番号>-plan.md` に置く
- 頭に `省いた文書: 設計書（<満たした条件の値>）` の行を書く。省いた他の文書（実行計画・並列の計画）も、同じ形で 1 行ずつ書く。承認する人と cross-review は、この値を要求仕様と差分の数と照らす
- 「修正対象」の頭に、直す場所と、不具合なら根本原因を 2 行で書く。表はファイルと関数ごとに、変える前と後の振る舞い（どの入力で何を返すか・どの失敗をどう扱うか）を書く
- 数え直して条件を外れたら、設計書を書いてから先へ進む

### 実装計画を省いたとき

レビューの単位はその課題 1 つ、リファクタリングの時機は TDD のステップだけになる。この 2 つを、設計書の「どこを変えるか」の頭の 1 行に書く。

## ワークフロー

1. 実装のリクエストを受けたら、まず実装計画を書くかを「実装計画を書くか」の条件で決める
2. 書く場合は `issues/` に実装計画のファイルを作成してから実装を開始する
3. PR作成時に実装計画のファイルが存在しない場合、必要であれば会話履歴・git log・git diffから実装計画のファイルを生成してからPRを作成する
4. 実装の後に、「レビューの単位」の実際の行数を書き足す

## 実装計画と PR Body の関係

- 実装計画のファイル = 「なぜ」「どう分解するか」を残す永続的な記録
- PR body = 「何をやったか」「どうテストするか」のレビュー用サマリ

同じ内容をコピーせず、PR bodyでは「詳細は `issues/xxx.md` 参照」と誘導してもよい。
