# 実装の前に構造を整えるか

**実装が触る対象の構造が危ういなら、その上へ積む前に整える。** 工程表では構造改善が実装の
後にあるが、それは「変更のついでに整理する」位置づけである。**既に危険な構造の上へ新しい
機能を積む場合は、順序が逆になる。**

## いつ判断するか

**計画を立てるときである。** 実装が触る先が見えた時点で決める。実装を始めてからでは、
構造が変わったときに積んだものが書き直しになる。

## 判断の基準

**測れるものと、やってみないと分からないものがある。**

| 測れる | 測り方 |
| --- | --- |
| 実装が触るファイルの規模 | 行数 |
| タスクの集中 | 同じファイルを触るタスクの割合 |
| テストの厚み | そのファイルを覆うテストの数 |

| 測れない | なぜ |
| --- | --- |
| 依存の循環 | **分割しないと分からない** |
| 責務の実際の分かれ目 | コメントは依存を反映しているとは限らない |

**測れない基準を「測ってから決める」形にしない。** 判断そのものが行われなくなる。

### 実測

**#436 の実装計画で、10 タスクのうち 9 つが 3706 行の 1 ファイルを触ると分かった。**
利用者の指摘で分割（#438）を先に行い、次のことが起きた。

| 起きたこと | 中身 |
| --- | --- |
| **循環が 1 つ見つかった** | 責務のコメントどおりに分けると `gitfacts → commands/report → gitfacts` になった。**分割して初めて分かった** |
| 分割のレビューは 1 ラウンドで収束 | 振る舞いを変えない変更は、変えないことが機械で確かめられる（テストの差分が 0 件） |
| 実装が入る場所が明確になった | 3706 行の中の 9 箇所ではなく、161 行と 657 行のモジュールになった |

**分割せずに実装していれば、循環の上に機能を積むことになっていた。**

### 比べるのは所要時間だけではない

**「分割は時間がかかる」の比較対象は「分割しない場合の実装時間」ではない。**
**「分割しない場合の実装時間 + 手戻りの期待値」である。**

| 手戻り | 中身 | #436 での実測 |
| --- | --- | --- |
| 順序を誤ったことによる作り直し | 構造が変わると、その上に積んだ実装は書き直しになる | **実際に起きた。** 分割前に 1 タスクを実装してコミットし、破棄した |
| 後で見つかる設計の誤り | 循環の上に実装を積むと、境界を引き直すときに実装も崩れる | 循環 1 件が分割で見つかった |
| レビューで差分が読めない | 3706 行の中の 9 箇所は、レビュワーが全体像を掴めない | 分割は 1 ラウンドで収束、設計は 6 ラウンドかかった |

## 先に整えると決めたら

**別の Pull Request へ分ける。**

| 進め方 | 採否 | 理由 |
| --- | --- | --- |
| 別の課題として起票し、先に通す | **採用** | 振る舞いを変えない変更として、機械で確かめられる |
| 同じ Pull Request の中で先に行う | 不採用 | Pull Request は増えないが、**レビューで差分を読み分けられない** |

**先に整える変更は、それ自体が独立したモード判定を持つ。** #438 は `standard` だった
（テストが十分にあり、振る舞いを変えない構造変更であるため）。

## `legacy-refactor` との違い

**掛かる対象が違う。**

| | `legacy-refactor`（モード） | 実装前の構造改善（この判断） |
| --- | --- | --- |
| 掛かる対象 | **変更全体** | **これから触る対象の構造** |
| 決まる時点 | モード判定（変更の性質で決まる） | 計画（実装が触る先が見えてから） |
| 振る舞い | 変えない | 変えない |
| テスト | **無いか少ない**（現状固定テストを先に置く） | 有無を問わない |
| その後 | そのモードのまま進む | **別の Pull Request として先に通し、本体は元のモードで進む** |

**同じ変更が両方に当たることはない。** `legacy-refactor` は「この変更は構造改善である」と
判定した状態で、こちらは「この変更は実装だが、その前に整える別の変更を挟む」判断である。

モードの定義は
[development-workflow の workflow-modes.md](../../development-workflow/references/workflow-modes.md)
が持つ。

## 整えないと決めたときも理由を残す

**残っていないと、後から指摘されたときに「判断した」のか「気づかなかった」のかを区別
できない。** 計画の「リスクと対処」へ 1 行書く。

```markdown
| `order.py` が 1200 行ある | 先に整えない。触るのは 1 タスクで、テストが 40 件ある |
```

**表の 1 行は折り返さない。** 折り返すと表として読まれない。

**3 択で決める。** `out-of-scope` の判断と同じ形である。

| 判断 | 残すもの |
| --- | --- |
| 先に整える | 別の課題として起票し、番号を計画へ書く |
| 実装の後の構造改善で足りる | **理由を 1 行** |
| 触る対象に構造の問題が無い | **理由を 1 行** |
