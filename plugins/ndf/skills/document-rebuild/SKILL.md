# 書き上げた文書を、文書形式と目的に合わせて組み直す

**この工程が作るのは、同じ内容を読み手が問う順に並べ直した文書と、前後の値の表である。**
内容を足すことも、書き方の規則を新しく持つこともしない。

| 作るもの | 中身 |
| --- | --- |
| 組み直した文書 | 文書の目的に合った構成へ章立てを並べ替え、文書形式に合った量へ整えたもの |
| 前後の値の表 | 測った指標を組み直しの前と後で並べたもの。目安を超えた項目は理由を添える |
| 確かめの記録 | キーワードの確認と、文脈を持たない読み手役の確かめの結果 |

## なぜ別の工程にするか

**最初に書き上がる文書は、書き手が調べた順に並んでいる。** 調査は「問題に気づく → 測る →
枠組みを当てる → 結論を出す」の順に進み、文書もその順で書かれる。読み手が最初に知りたいことは
文書の目的で決まり、調べた順とは食い違う。

**書いた本人はこの食い違いに気づけない。** 調べた順に読むと筋が通って見える。別の工程として
切り出さないかぎり、組み直す機会が来ない。

## いつ通すか

| 場面 | 扱い |
| --- | --- |
| 工程として | 文書を作る工程の後、その文書をレビューへ出す前（工程「ドキュメント再構成」と、`document-drafting` の手順 4） |
| 明示指示として | 書き上げた文書があるとき。文書形式と文書の目的を問わない（設計文書・Issue の本文・Pull Request の本文・スライド・表計算・ページ・ブログ・論文・小説など） |

**レビューの前に置く。** 後に置くと、レビュー担当が構成の指摘と内容の指摘を同時に出すことに
なり、どちらの指摘なのかが混ざる。構成を整えてから内容を見てもらう。

## 手順

**5 つの手順を順に通す。** 手順 1 と手順 4 は同じ指標を測る。

| 手順 | 行うこと | 出るもの |
| --- | --- | --- |
| 0. 決める | 文書形式・文書の目的・言語を決め、当たる参照を 1 つずつ読む | 読んだ参照 |
| 1. 測る | 組み直しの前の値を取る | 指標ごとの数 |
| 2. 組み直す | 章立てを目的別ガイドの構成へ並べ替える。**内容を足さない** | 並べ替えた文書 |
| 3. 整える | 共通ルールと他の Skill の規約で整え、キーワードを確かめ、読み手役に読ませる | 整えた文書と確かめの記録 |
| 4. 測り直す | 前後の値を並べ、目安を超えた項目に理由を添える | 前後の値の表 |

### 手順 0: 決める

**文書形式・文書の目的・言語の 3 つを、手がかりから決める。** 決めたら、それぞれに当たる参照を
`references/` から探して 1 つずつ読む。**この文書は形式・目的・言語の一覧を持たない**（1 つ足すときに
他のファイルを変えないため）。

| 決めるもの | 手がかり（上から順に見る） | 読む参照 |
| --- | --- | --- |
| 文書形式 | 呼び出し元の指定 → 拡張子と置き場（`.md` はリポジトリの Markdown、`slides/`・`.pptx` はスライド、`.xlsx`・Google スプレッドシートは表計算、Notion・Confluence はページ、`.docx`・Google ドキュメントは文書） → 設計文書の入出力の契約 | `references/format-<形式>.md` |
| 文書の目的 | 呼び出し元の指定 → 文書タイプ（`documentation` のとき。対応は [related-skills.md](references/related-skills.md#文書タイプと目的別ガイドの対応)） → 本文と Pull Request の語 → 各目的別ガイドの「見分ける手がかり」 | `references/purpose-<目的>.md` |
| 言語 | 本文の言語 | `references/lang-<言語>.md` |

**手がかりで決まらないときは推測しない。** 工程の中では呼び出し元へ、明示の呼び出しでは利用者へ確かめる。
**2 つ以上の参照が当たるときは、読む前に止めて決め直す。**

**当たる参照が無いときは、読まずに続ける。** その場で決めた構成・目安・区切りを手順 4 の報告に残し、
参照を足す候補として報告する。

あわせて、毎回 [common.md](references/common.md)（共通ルール）と
[related-skills.md](references/related-skills.md)（他の文書系 Skill との関係）を読む。
ソースが置き場（Notion・Confluence・Google Drive）にあるときは、手順 0 の前に `document-systems` で取得する。

### 手順 1: 測る

**形式別ガイドの「文章量の単位と目安」の指標と、指標「結論・成果物が定義される位置」を測る。**
形式別ガイドが「測らない指標」とした指標は測らず、報告に「この形式では測らない」と書く。

**測る手段は対象リポジトリから探して決める。** 候補の並びは優先の順を表さない。対象に実在する
ものを採る。

| 候補 |
| --- |
| そのリポジトリがすでに持つ文書のチェックの仕組み（設定ファイルや継続的統合の定義から探す） |
| そのリポジトリで動く処理系を使い、その場に書く短い集計 |
| エディタが備える文字数・行数の表示 |
| 手で数える（結論の位置・章の数・章あたりの行数・ページごとのメッセージの数） |

**どれも見つからないときは、手で数えられる指標だけを測る。** 測れなかった指標は
「測れなかった」と手順 4 の表へ残す。**測れないことを「目安に収まっている」と書かない。**

### 手順 2: 組み直す

**章立てを目的別ガイドの「構成」の順に並べ替える。** 段落と文はまだ触らない。

**別の Skill が固定した章は動かさない**（共通ルール K3）。設計文書の H1 と、H1 の直後の「目的」から
「あるべき姿の根拠」までの章は、`design` の
[design-template.md の「承認する人が読む欄」](../design/references/design-template.md#承認する人が読む欄) が決める。
要求のテンプレート・Pull Request の本文の形・`type-*.md` の必ず書く節・`document-sources` の出典の節も同じ扱いで、
目的別の構成は固定されていない章の中だけに当てる。

**構成に当てはまらない章は、並びの外へ置き、末尾へ集める。** 参照の一覧・用語表・付録がこれに当たる。

**内容を足さない。** 組み直しと書き足しを同時に行うと、どちらが読みやすさに効いたのかが
分からなくなる。目的に要る章が欠けているときも書き足さず、見つけたことを控えて報告に残す。

### 手順 3: 整える

**次の順で通す。** 規則の点検を手順 4 の測り直しの前に済ませるため、測り直しの後に文が変わらない。

**目的別ガイドが「行わない」「使わない」とした事柄は、どの順でも当てない。** 他の Skill の規約やセルフチェックが
求めても、目的別ガイドを先に効かせる（例: エッセイと小説では文長の目安で文を分けず、エッセイでは対比・列挙を表へ置き換えない）。

| 順 | 行うこと | 正本 |
| --- | --- | --- |
| 1 | 共通ルールを当てる。目的別ガイドが外した行は当てない | [common.md](references/common.md) |
| 2 | 当たる他の Skill の規約を当てる。長い文は形式別ガイドの目安で分け、対比・列挙の形は `document-style` のルール 8 に従う | [related-skills.md](references/related-skills.md) |
| 3 | `document-style` のセルフチェックを通す（ソースが Markdown のとき。多義語の候補もここで見る） | `document-style` の「書き終えたらセルフチェック」 |
| 4 | キーワードを確かめる。読み手が社外なら公式ドキュメントの語、社内なら用語集と流通している語と突き合わせる | [keyword-check.md](references/keyword-check.md) |
| 5 | 文脈を持たない読み手役に読ませる（下の節） | この節 |

**書き方の規則はこの文書が持たない。** 同じ規則を 2 か所に置くと、片方だけが更新される。

#### 読み手役に読ませる

**組み直した文書を読む人が、問い直さずに理解し納得できるかを確かめる。** 書き手と同じ文脈を持つ AI が
読み返しても、書き手の思い込み（内部の語・省いた前提）は見つからない。

| 項目 | 決まり |
| --- | --- |
| 渡すもの | 組み直した文書と、想定する読み手の説明（立場・前提知識）だけ。会話・設計の経緯・リポジトリの文脈は渡さない |
| 読み手役 | Claude Code ではサブエージェント、ほかのランタイムでは `external-ai` で別の CLI を呼ぶ |
| 返させるもの | 要点の言い直し（結論・求められていること）・分からなかった語と箇所・納得できなかった主張と理由・読み終えて次に何をするか |
| 合否の見方 | 言い直した要点が、目的別ガイドが冒頭に置く章と食い違わない。分からなかった語と箇所が 0 件か、残した理由がある |
| 返ってきたものの扱い | 語の置き換えと順の入れ替えで直せるものは、この手順の中で直す。前提や根拠が足りないものは直さず、「足すべき内容」として報告に控える |
| 回数 | 1 回。直した後に読み直させない |
| 立てられないとき | 理由を報告に残し、書き手が文脈を捨てて読む点検で代える。「確かめた」とは書かない |

### 手順 4: 測り直す

手順 1 と同じ手段で測り直し、前後の値を並べる。

**目安を超えても差し戻さない。** 目安を超えた項目を直すために手順 3 へ戻らない。
超えた項目ごとに、次の 3 つを表へ書いて終える。

| 書くもの | 例 |
| --- | --- |
| 測った値 | 最長文 138 字 |
| 超えた理由 | 分けると条件と結論の対応が読めなくなる 1 文である |
| 採らなかった直し方 | 2 文に分ける（主語が両方に要り、字数が増える） |

**固定の章が欠けた・説明できない増加があるときは、手順 2 からやり直す。** この戻りは目安を超えた
ときの扱いより先に効き、戻った後は手順 2〜4 を通し直す。

## 組み直しと書き足しを分ける

**内容が変わっていないことを直に確かめる手段は無い。** 章を並べ替えるついでに 1 文を足しても、
チェックには何も現れない。そのため**変えた量そのものを見る**。

| 見る値 | 組み直しだけのとき | 書き足しが混ざったとき |
| --- | --- | --- |
| 行数 | 表への置き換えと章の分割の分だけ増える | それを超えて増える |
| 章の数 | 分割した分だけ増える | 新しい主題の章が増える |
| 平均文長 | 減る | 減り方が鈍る（足した文が平均へ乗る） |

**行数の増加が説明できないときは、書き足しが混ざっている。** 増えた分が「どの表への置き換え」
「どの章の分割」に対応するかを手順 4 の表で言えるかどうかで見る。**言えない増加は手順 2 へ戻して
外し、別の作業として行う。**

**実測では行数が 1.4 倍から 4.7 倍になった。** 増えたのは表と章の分割で、減ったのは 1 文の
長さである。**読みやすさを短さで測らない。**

## 報告

手順 4 の表をそのまま報告に載せる。**前の値だけ、または後の値だけを載せない。**

```text
文書形式: リポジトリの Markdown（format-markdown.md）
文書の目的: 確定事項を伝える文書（purpose-decided.md）

| 指標 | 前 | 後 |
| --- | ---: | ---: |
| 結論が定義される位置 | 158 行目 | 1 行目 |
| 平均文長 | 46.1 字 | 33.4 字 |
| 最長文 | 186 字 | 105 字 |
| 章の数 | 7 | 10 |
| 行数 | 188 | 263 |

目安を超えた項目: 最長文 105 字（目安 100 字）。
  理由: 条件と結論の対応が 1 文で読める形を保った。
  採らなかった直し方: 2 文に分ける（主語が両方に要り、字数が増える）。

測れなかった指標: なし
キーワードの確認: （keyword-check.md の表）
読み手の確かめ: 要点の言い直し・分からなかった箇所・納得できなかった主張・直したもの
足すべき内容: （手順 2 と読み手役で控えたもの）
呼び出し先: （形式別ガイドの「呼び出し先」。形式への適用を渡す先）
```

- **測る手段が見つからず測れなかった指標は「測れなかった」と書く。** 空欄にしない
- **キーワードの確認と読み手の確かめを「無し」と書かない。** 行わなかったときは理由を書く
- **控えた「足すべき内容」は、別の作業として報告に残す。** 組み直しの中では行わない
- **形式への適用（生成・投稿・版面の点検）は、形式別ガイドの呼び出し先へ渡す。** この Skill では行わない

## `document-style` との境界

| Skill | 持つもの | いつ使うか |
| --- | --- | --- |
| `document-style` | 何が読みやすい文書かの規則（語・表現・図表・ファイルの長さ） | 書くときと、書いた後の点検 |
| この Skill | 書き上げた文書を組み直す手順・目的別の構成・形式別の文章量の目安 | 書き上げた後 |

**この Skill と `document-style` は規則と手順で分け、書く前後で分けない。** `document-style` のセルフチェックは
書いた後に走る。この Skill は手順 3 でその点検を呼ぶ。重なっていた規約の正本は
[related-skills.md](references/related-skills.md#document-style-と重なっていた規約) にある。

## 範囲外の課題を見つけたとき

組み直しの対象に含まれない課題（内容の誤り・別の文書の不整合・規約どうしの食い違い）を見つけたら、
**見つけたその場で `out-of-scope` が issue にする**。組み直しの中では直さない。

この工程に入ったら進捗記録 `bash "$SCRIPTS/projects-sync.sh" <issue番号> stage "ドキュメント再構成"` を 1 行打つ（issue の本文とボードの両方に残る。`$SCRIPTS` の決め方は `development-workflow` の `references/scripts-lookup.md`、3 層では起動指示の「進捗記録」を使う）。
