# 書き上げた文書を、文書形式と目的に合わせて組み直す

**この工程が作るのは、同じ内容を読み手が問う順に並べ直した文書と、前後の値の表である。**
内容を足すことも、書き方の規則を新しく持つこともしない。

| 作るもの | 中身 |
| --- | --- |
| 組み直した文書 | 文書の目的に合った構成へ章立てを並べ替え、文書形式に合った量へ整えたもの |
| 前後の値の表 | 測った指標を組み直しの前と後で並べたもの。目安を超えた項目は理由を添える |
| 確かめの記録 | キーワードの確認と、文脈を持たない読み手役の確かめの結果 |

## なぜ別の工程にするか

**最初に書き上がる文書は、書き手が調べた順に並んでいる。** 調査は「問題に気づく → 測る →
枠組みを当てる → 結論を出す」の順に進み、文書もその順で書かれる。読み手が最初に知りたいことは
文書の目的で決まり、調べた順とは食い違う。

**書いた本人はこの食い違いに気づけない。** 調べた順に読むと筋が通って見える。別の工程として
切り出さないかぎり、組み直す機会が来ない。

## いつ通すか

| 場面 | 扱い |
| --- | --- |
| 工程として | 文書を作る工程の後、その文書をレビューへ出す前（工程「ドキュメント再構成」と、`document-drafting` の手順 4） |
| 明示指示として | 書き上げた文書があるとき。文書形式と文書の目的を問わない（設計文書・Issue の本文・Pull Request の本文・スライド・表計算・ページ・ブログ・論文・小説など） |

**レビューの前に置く。** 後に置くと、レビュー担当が構成の指摘と内容の指摘を同時に出すことに
なり、どちらの指摘なのかが混ざる。構成を整えてから内容を見てもらう。

## 手順

**手順を順に通す。** 手順 1 と手順 4 は同じ指標を測る。

| 手順 | 行うこと | 出るもの |
| --- | --- | --- |
| 0. 決める | 文書形式・文書の目的・言語を決め、当たる参照を 1 つずつ読む | 読んだ参照 |
| 1. 測る | 組み直しの前の値を取る | 指標ごとの数 |
| 2. 組み直す | 章立てを目的別ガイドの構成へ並べ替える。**内容を足さない** | 並べ替えた文書 |
| 3. 整える | 共通ルールと他の Skill の規約で整え、キーワードを確かめ、読み手役に読ませる | 整えた文書と確かめの記録 |
| 4. 測り直す | 前後の値を並べ、目安を超えた項目に理由を添える | 前後の値の表 |

### 手順 0: 決める

**最初に `document-style` を読み込む。** 手順 3 の整えとセルフチェックはその規則で行うため、読まずに進めない。
Skill を呼べるランタイムでは `document-style` を Skill として起動し、呼べないとき（Skill のツールを外した worker など）は
`skills/document-style/SKILL.md` を読む。

**文書形式・文書の目的・言語の 3 つを、手がかりから決める。** 決めたら、それぞれに当たる参照を
`references/` から探して 1 つずつ読む。**この文書は形式・目的・言語の一覧を持たない**（1 つ足すときに
他のファイルを変えないため）。

| 決めるもの | 手がかり（上から順に見る） | 読む参照 |
| --- | --- | --- |
| 文書形式 | 呼び出し元の指定 → 拡張子と保存先（`.md` はリポジトリの Markdown、`slides/`・`.pptx` はスライド、`.xlsx`・Google スプレッドシートは表計算、Notion・Confluence はページ、`.docx`・Google ドキュメントは文書） → 設計文書の入出力のコントラクト | `references/format-<形式>.md` |
| 文書の目的 | 呼び出し元の指定 → 文書タイプ（`documentation` のとき。対応は [related-skills.md](references/related-skills.md#文書タイプと目的別ガイドの対応)） → 本文と Pull Request の語 → 各目的別ガイドの「見分ける手がかり」 | `references/purpose-<目的>.md` |
| 言語 | 本文の言語 | `references/lang-<言語>.md` |

**手がかりで決まらないときは推測しない。** 工程の中では呼び出し元へ、明示の呼び出しでは利用者へ確かめる。
**2 つ以上の参照が当たるときは、読む前に止めて決め直す。**

**当たる参照が無いときは、読まずに続ける。** その場で決めた構成・目安・区切りを手順 4 の報告に残し、
参照を足す候補として報告する。

あわせて、毎回 [common.md](references/common.md)（共通ルール）と
[related-skills.md](references/related-skills.md)（他の文書系 Skill との関係）を読む。
ソースが保存先（Notion・Confluence・Google Drive）にあるときは、手順 0 の前に `document-systems` で取得する。

### 手順 1: 測る

**形式別ガイドの「文章量の単位と目安」の指標と、指標「結論・成果物が定義される位置」を測る。**
形式別ガイドが「測らない指標」とした指標は測らず、報告に「この形式では測らない」と書く。

**測る手段は対象リポジトリから探して決める。** 候補の並びは優先の順を表さない。対象に実在する
ものを採る。

| 候補 |
| --- |
| そのリポジトリがすでに持つ文書のチェックの仕組み（設定ファイルやCIの定義から探す） |
| そのリポジトリで動く処理系を使い、その場に書く短い集計 |
| エディタが備える文字数・行数の表示 |
| 手で数える（結論の位置・章の数・章あたりの行数・ページごとのメッセージの数） |

**どれも見つからないときは、手で数えられる指標だけを測る。** 測れなかった指標は
「測れなかった」と手順 4 の表へ残す。**測れないことを「目安に収まっている」と書かない。**

### 手順 2: 組み直す

**章立てを目的別ガイドの「構成」の順に並べ替える。** 段落と文はまだ触らない。

**別の Skill が固定した章は動かさない**（共通ルール K3）。設計文書の承認する人が読む欄（H1・要約の段落・今の姿・
解き方の全体像・決定の見出し・影響と危険）は、`design` の
[design-template.md の「承認する人が読む欄」](../design/references/design-template.md#承認する人が読む欄) が決める。
`legacy-refactor`（既存コードを振る舞いを変えずに組み替えるモード）の設計文書では、H1 と、H1 の直後の「目的」から
「目指す姿の根拠」までの章を、同じファイルの
[「`legacy-refactor` の書き方」](../design/references/design-template.md#legacy-refactor-の書き方) が決める。
要求のテンプレート・Pull Request の本文の形・`type-*.md` の必ず書くセクション・`document-sources` の出典のセクションも同じ扱いで、
目的別の構成は固定されていない章の中だけに当てる。

**構成に当てはまらない章は、並びの外へ置き、末尾へ集める。** 参照の一覧・用語表・付録がこれに当たる。

**内容を足さない。** 組み直しと書き足しを同時に行うと、どちらが読みやすさに効いたのかが
分からなくなる。目的に要る章が欠けているときも書き足さず、見つけたことをメモして報告に残す。

### 手順 3: 整える

**次の順で通す。** 規則の点検を手順 4 の測り直しの前に済ませるため、測り直しの後に文が変わらない。

**目的別ガイドが「行わない」「使わない」とした事柄は、どの順でも当てない。** 他の Skill の規約やセルフチェックが
求めても、目的別ガイドを先に効かせる（例: エッセイと小説では文長の目安で文を分けず、エッセイでは対比・列挙を表へ置き換えない）。

| 順 | 行うこと | SSOT |
| --- | --- | --- |
| 1 | 共通ルールを当てる。目的別ガイドが外した行は当てない | [common.md](references/common.md) |
| 2 | 当たる他の Skill の規約を当てる。長い文は形式別ガイドの目安で分け、対比・列挙の形は `document-style` のルール 8 に従う | [related-skills.md](references/related-skills.md) |
| 3 | `document-style` のセルフチェックを通す（ソースが Markdown のとき。多義語の候補もここで見る） | `document-style` の「書き終えたらセルフチェック」 |
| 4 | キーワードを確かめる。読み手が社外なら公式ドキュメントの語、社内なら用語集と流通している語と突き合わせる | [keyword-check.md](references/keyword-check.md) |
| 5 | 文脈を持たない読み手役に読ませる（下のセクション） | このセクション |

**書き方の規則はこの文書が持たない。** 同じ規則を 2 か所に置くと、片方だけが更新される。

#### 読み手役に読ませる

**読み手役は、文書を書いた会話を引き継がずに、想定した読み手の立場で文書を読む AI である。** 読み手に通じない文を挙げ、
要点を言い直す。書き手と同じ文脈を持つ AI が読み返しても、書き手の思い込み（内部の呼び名・省いた前提）は見つからない。
読み手と、通じない文の見分け方は [文書の書き方・直し方の基準](../../contracts/data/writing-criteria.md) にある。

| 項目 | 決まり |
| --- | --- |
| 対象 | 要求仕様（Issue の本文から作ったコピー）、設計書と詳細設計書、リリース後の仕様書、ビジネス文書、変更履歴・README・利用者への案内、承認を求める文（質問の文）と承認資料。ほかの文書（Issue の本文、実装計画、PR の題と本文、コミットメッセージ、レビューの指摘と返信、AI への手順書）は、書いた担当が自分で読み直す |
| 時点 | 組み直した後に、文書の全体を読ませる。承認を求める前の確認（質問の文・承認資料・前に読ませた後で変わった文書の部分）は、承認ゲートの 1 つ前のステップが行う（下の「承認の前の確認」） |
| 起動 | Claude Code では新しい `ndf:worker`、ほかのランタイムでは `external-ai` で別の CLI を呼ぶ。指示は `ndf records reading prompt --file <JSON>` で作り、結果の `metrics.prompt` をそのまま渡す |
| 別の CLI の返答の受け取り | 出力先のファイルは指示に書かない。Codex CLI では、起動のコマンドに `-o <結果ファイル>` を足して最終応答を受け取り、ほかの CLI では標準出力から受け取る。本文の無かった起動も、「回数」の 2 回に数える |
| 立場 | 基準の表の読み手ごとに、別の読み手役を起動する。要求仕様は非エンジニア・PM・エンジニアの 3 つ、設計書と詳細設計書はエンジニアの 1 つ |
| 渡すもの | 文書、読み手の 3 点、4 つの型と 2 つの区分の見分け方、返す形だけ。設計書には、組になる要求仕様のコピーをすべて添える（`issue-<番号>-design.md` なら `issues/issue-<番号>-requirements.md`。名前に番号が複数あれば、その番号すべて）。文書を書いた経緯と、使わない言葉の一覧（用語集など）は渡さない |
| 補足の扱い | エンジニアでない立場の読み手役には、「エンジニア向けの補足」の見出しからそのセクションの終わりまでを外した文書を、別のファイルに作って渡す |
| 返させるもの | (1) 要点の言い直し。(2) 通じない文の一覧（引用・型・つまずく理由・書き直した案・2 つの区分のどちらか）。(3) 迷って (2) に入れなかった文を最大 3 つ。(3) は合否に関わらない |
| 合格の条件 | 起動した担当が、言い直しを文書と読み比べて決める。言い直しが文書の内容と合い、「判断や作業を誤らせる文」が 1 件も無ければ合格とする。要求仕様と設計書の言い直しは、[document-roles.md の「読み手役の言い直し」](../requirements-design/references/document-roles.md#読み手役の言い直し) の質問ごとに読み比べる。要点を言い直せたことだけでは合格にしない。不自然な文でも、AI は要点を言い直せるためである |
| 回数 | 1 回の確認につき、立場ごとに 2 回まで。1 回目が不合格なら書いた担当が直し、不合格だった立場の別の読み手役が文書の全体（一部だけを読ませたときはその部分）をもう一度読む。2 回目にも「判断や作業を誤らせる文」が残ったら、確認はそこで終える。レビューで直した後の読み直しは、新しい確認として数え直す。読み直しは、承認を求める前の 1 回にまとめ、レビューのラウンドごとには行わない |
| 一部だけ読ませるとき | 確認を終えた後に直した部分と、その前後の段落だけを読ませるときは、文書の種類によらず `questions_kind` を `none` にし、要求仕様のコピーを添えない。担当は、言い直しを読ませた部分の内容とだけ読み比べ、document-roles.md の質問では読み比べない。言い直しがその部分と合い、「判断や作業を誤らせる文」が 1 件も無ければ合格とする。ただし、文書のほかの部分に説明がある言葉を、説明が無いと挙げた指摘は数えない |
| 2 回目にも残った文 | 書いた担当が、引用して、直したか、直しきれなかった理由とともに書く。書く場所は、承認を求める文書なら承認の文、承認を求めず Pull Request で出す文書なら Pull Request の本文、どちらでもない文書なら文書を渡す相手への連絡 |
| 読みにくいだけの文 | 直すかどうかは書いた担当が決める。直さないときは、理由を上の行と同じ場所に書く。どちらのときも、確認をやり直さない |
| 直し方 | 単語を置き換えず、基準の「5. 直し方」のとおりに文や段落を書き直す。事実（数・日付・条件・決定など）を変えない。前提や根拠が足りないものは直さず、「足すべき内容」として報告に書く |
| 起動できないとき | 読ませずに先へ進まない。理由を報告に残して止める（`ndf document-rebuild run` と `gate` は `stopped`（precondition）で終える）。自分で読み直して代えない。supervisor が手順書に沿って組み直していて、起動した worker が読み手役を立てられないときは、`判断が要る` で conductor へ返し、conductor が `ndf document-rebuild run` を打つ（`ndf worker run` で起動した worker は読み手役を立ててよい）。読み手役を立てられる環境に直してから打ち直す |

`prompt` に渡す JSON の形:

```json
{
  "files": ["issues/issue-1-design.md", "issues/issue-1-requirements.md"],
  "reader": {
    "position": "エンジニア。この設計でよいかを判断し、実装し、保守する",
    "words": "日本のエンジニアが使っている言葉",
    "knowledge": "一般の技術を知っている。この機能の経緯と、開発チームの中だけの呼び名は知らない"
  },
  "questions_kind": "design"
}
```

`questions_kind` は、要求仕様なら `requirements`、設計書なら `design`、ほかの文書（詳細設計書など）と、文書の一部だけを読ませるときは `none` にする。

**報告には、文書・立場・読んだコミット・回・結果（合格か、2 回目にも残ったか）を 1 行ずつ残す。** 承認を求める担当が、
まだ読ませていない文書と、確認の後に直した部分を、この記録から見分ける。

### 手順 4: 測り直す

手順 1 と同じ手段で測り直し、前後の値を並べる。

**目安を超えても変更を要求しない。** 目安を超えた項目を直すために手順 3 へ戻らない。
超えた項目ごとに、次の 3 つを表へ書いて終える。

| 書くもの | 例 |
| --- | --- |
| 測った値 | 最長文 138 字 |
| 超えた理由 | 分けると条件と結論の対応が読めなくなる 1 文である |
| 採らなかった直し方 | 2 文に分ける（主語が両方に要り、字数が増える） |

**固定の章が欠けた・説明できない増加があるときは、手順 2 からやり直す。** この戻りは目安を超えた
ときの扱いより先に効き、戻った後は手順 2〜4 を通し直す。

## 承認の前の確認

**承認ゲートの 1 つ前のステップ（`design-reading`・`release-reading`）は、`ndf document-rebuild gate` を打ち、承認資料を書いて読み手役に読ませる。** 承認を問う側（レーンの conductor・オーガナイザー）は資料も質問の文も書かず、このステップが記録した質問をそのまま出す。`gate` が `ndf worker run` で起動した worker は、次の順に進める。記録（`reading-docs.jsonl`・`reading-checks.jsonl`）と、PR へのコメントの追記は `gate` が行い、worker は行わない。

1. **承認資料の判断の材料を書く。** 素材のファイル（`approval-facts.json`。PR の URL・題・ベースと head・変更量・直前の MVV 判定）と、承認資料の作業用のファイル（PR の本文のコピー、または `ndf release-steps materials` の出力）を読み、作業用のファイルに判断の材料を書き足す。載せる項目と出所は [approval-request.md の「承認資料は 2 層に分ける」](../development-workflow/references/approval-request.md#承認資料は-2-層に分ける) と「承認ゲートごとの違い」のとおりで、ここに写さない
2. **読み手役に読ませる。** 起動指示が挙げた対象（質問の文・承認資料・前に読ませた後で変わった文書の部分）を、上の「読み手役に読ませる」の決まりで読ませる。質問の文と承認資料は承認する人、文書はエンジニアの立場で読ませる。前に読ませた承認資料があるときは、変わった段落とその前後だけを読ませる
3. **直して 2 回目を読ませる。** 不合格なら、起動指示が「直してよいファイル」に挙げたものだけを直す。直した後は、事実（数・日付・条件・決定）が変わっていないことを差分で 1 回確かめる
4. **結果を書く。** 対象ごとに、読ませた時点の全体のハッシュ・立場・回・合否と、2 回目にも残った文の引用を、結果ファイルの `metrics.readers` に書く（形は起動指示の「確かめの記録」）

直すものごとの扱い:

| 直すもの | 扱い |
| --- | --- |
| 書き足した判断の材料 | 自由に直してよい。合格した最終版を `gate` が PR のコメントとして足す |
| PR の本文から写した行 | 直すと PR へは反映されない。`gate` は PR の題と本文を書き換えず、工程を止めて PR の直しを求める（変更要求）。直した後に工程を再開すると、新しい読み手役が変わった部分を読む |
| PR の題（質問の文が題のせいで通じないとき） | 題の案のファイルに 1 行で書く。PR の題は変わらず、上の行と同じく変更要求になる |
| 設計 PR の文書 | 直すと `gate` が push し、設計のレビューへ戻す（1 つの承認ゲートの前で 1 回まで） |

- 変更要求と設計のレビューへ戻すのは、どちらも 1 つの承認ゲートの前で 1 回までである。2 回目は起動指示がその対象を「直してよいファイル」から外すので、指摘は 2 回目にも残った文として返す。`gate` が承認資料の末尾の「読み手役が残した文」に書く
- 決まった形の質問の文そのものが通じないときは、ステップの中では直さない。2 回目にも残った文として返す

## 組み直しと書き足しを分ける

**内容が変わっていないことを直に確かめる手段は無い。** 章を並べ替えるついでに 1 文を足しても、
チェックには何も現れない。そのため**変えた量そのものを見る**。

| 見る値 | 組み直しだけのとき | 書き足しが混ざったとき |
| --- | --- | --- |
| 行数 | 表への置き換えと章の分割の分だけ増える | それを超えて増える |
| 章の数 | 分割した分だけ増える | 新しい主題の章が増える |
| 平均文長 | 減る | 減り方が鈍る（足した文が平均へ乗る） |

**行数の増加が説明できないときは、書き足しが混ざっている。** 増えた分が「どの表への置き換え」
「どの章の分割」に対応するかを手順 4 の表で言えるかどうかで見る。**言えない増加は手順 2 へ戻して
外し、別の作業として行う。**

**実測では行数が 1.4 倍から 4.7 倍になった。** 増えたのは表と章の分割で、減ったのは 1 文の
長さである。**読みやすさを短さで測らない。**

## 報告

手順 4 の表をそのまま報告に載せる。**前の値だけ、または後の値だけを載せない。**

```text
文書形式: リポジトリの Markdown（format-markdown.md）
文書の目的: 確定事項を伝える文書（purpose-decided.md）

| 指標 | 前 | 後 |
| --- | ---: | ---: |
| 結論が定義される位置 | 158 行目 | 1 行目 |
| 平均文長 | 46.1 字 | 33.4 字 |
| 最長文 | 186 字 | 105 字 |
| 章の数 | 7 | 10 |
| 行数 | 188 | 263 |

目安を超えた項目: 最長文 105 字（目安 100 字）。
  理由: 条件と結論の対応が 1 文で読める形を保った。
  採らなかった直し方: 2 文に分ける（主語が両方に要り、字数が増える）。

測れなかった指標: なし
キーワードの確認: （keyword-check.md の表）
読み手の確かめ: 要点の言い直し・分からなかった箇所・納得できなかった主張・直したもの
言い直しの合否: （要求仕様・設計書のとき。質問ごとの言い直し・合否・不合格の理由、渡せなかった要求仕様の番号）
足すべき内容: （手順 2 と読み手役でメモしたもの）
呼び出し先: （形式別ガイドの「呼び出し先」。形式への適用を渡す先）
```

- **測る手段が見つからず測れなかった指標は「測れなかった」と書く。** 空欄にしない
- **キーワードの確認と読み手の確かめを「無し」と書かない。** 行わなかったときは理由を書く
- **メモした「足すべき内容」は、別の作業として報告に残す。** 組み直しの中では行わない
- **形式への適用（生成・投稿・版面の点検）は、形式別ガイドの呼び出し先へ渡す。** この Skill では行わない

## `document-style` との境界

| Skill | 持つもの | いつ使うか |
| --- | --- | --- |
| `document-style` | 何が読みやすい文書かの規則（語・表現・図表・ファイルの長さ） | 書くときと、書いた後の点検 |
| この Skill | 書き上げた文書を組み直す手順・目的別の構成・形式別の文章量の目安 | 書き上げた後 |

**この Skill と `document-style` は規則と手順で分け、書く前後で分けない。** `document-style` のセルフチェックは
書いた後に走る。この Skill は手順 3 でその点検を呼ぶ。重なっていた規約の SSOT は
[related-skills.md](references/related-skills.md#document-style-と重なっていた規約) にある。

## 範囲外の課題を見つけたとき

組み直しの対象に含まれない課題（内容の誤り・別の文書の不整合・規約どうしの食い違い）を見つけたら、
**見つけたその場で `out-of-scope` が issue にする**。組み直しの中では直さない。
