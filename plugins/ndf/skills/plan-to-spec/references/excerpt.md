# plan-to-spec の抜粋

## 呼び出し

ndf records spec finalize --spec <仕様書>... --remove <元 plan・設計>... [--source-of <語>=<ファイル>]

- 仕様書を書き終え、`docs/specifications/README.md` があれば索引へ 1 行足した後に打つ。元の plan・設計を消し、用語集の SSOT を付け替える
- `-m` を渡さず、`items[]` の `path` と索引を `git add -A -- <パス>...` で入れ、`git commit -m "Docs: <名前> を確定仕様にする"` で 1 つのコミットにする

## 結果の読み方

状態と終了コードの意味は [終了コードと停止理由](../../../docs/contracts/exit-codes.md) にある。下の「意味」は、このコマンドでその終了コードになる場合である。

| 終了コード | 意味 | 次にすること |
| --- | --- | --- |
| 0 | 元の plan・設計を消し、コミットに入れるパスを `items[]` に出した | パスと索引をコミットし、SHA を報告に載せる |
| 1 | 用語集の文書を作り直せない（`check_failed`） | `summary` を読んで直し、打ち直す |
| 3 | 仕様書か設計が無い・語の SSOT を決められない（`precondition`） | `summary` と `items[]` の `term` を読んで直し（`--source-of`）、打ち直す |

## 判断の基準

- plan をそのまま移さず、現在のコードと一致する仕様として書き直す。開発の履歴・TODO・PR 分割・作業のチェックリスト・未採用案は落とす
- 保存先は同種の仕様書がある既存の docs の分類。無ければ `docs/specifications/`。ファイル名は英数字とハイフン
- 章立ては他の仕様書を先に見て揃える。既存 docs に明確な型があればそちらを優先し、無ければ標準の章立て: `# {仕様名}` → `概要` → `背景` → `対象範囲` → `仕様` → `データ・設定` → `外部連携` → `エラー処理` → `セキュリティ` → `運用` → `テスト観点` → `関連リンク`。該当しない章は削る
- plan と設計文書の次の項目は落とさず引き継ぐ（plan の項目 → 引継ぎ先の章）:
  - ドメイン用語 → `概要` の直後の `用語`（用語集の設定があればその文書を指し、定義を写さない）
  - コンテキスト → `概要` の直後
  - 集約 → `仕様` の冒頭
  - 不変条件 → `仕様` の中の「常に成り立つ条件」
  - ドメインイベント → `仕様` の該当箇所
  - 入出力のコントラクト → `仕様` / `データ・設定` / `外部連携`（現行のコントラクトだけ）
  - 設計判断の記録 → `背景`、または `仕様` の該当箇所に 1〜2 行（結論と理由だけ）
  - データ構造 → `データ・設定`（移行の手順は落とす）
  - 構成要素と責務 → `概要` の直後、または `仕様` の冒頭
  - 処理の流れ（図） → `仕様` の該当箇所（現行の図だけ）
  - 受け入れ条件 → `テスト観点`（観点へ言い換え、チェックボックスを外す）
- リンクは移した後の位置から有効に直す。確かめられないリンクは消すか確実な上位の文書へ差し替える
- 書いた後にコードと検証する。設計文書のクラス図はここで 1 度だけ実装に合わせる
- 対象の plan が決められないときは `結果: 判断が要る` で返す
