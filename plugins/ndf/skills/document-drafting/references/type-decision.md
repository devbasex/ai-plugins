# 決裁・稟議

**読み手に承認を求める。** 採否の議論は済んでおり、金額・期間・責任の所在が本体である。

**Markdown の実例は無い。** 実在の形は `.docx` / `.xlsx` / `.pdf` とシステムのページである。
**Markdown を正本にするのはこのワークフローの提案であり、生成の側が既存の形へ出せることが
前提になる**（`release` の `form-<出力の形>.md`）。

## 必ず書く節

| 節 | 何を書くか |
| --- | --- |
| 件名 | 何を承認するか。**金額と期間を含める** |
| 金額 | 総額と内訳。**税の扱いを明示する** |
| 期間 | いつからいつまで |
| 支払いの条件 | 一括か分割か。時期 |
| 起案の理由 | なぜ要るか。**やらなかったときに何が起きるか** |
| 責任の所在 | 起案・実行・検収の担当 |
| 承認の経路 | 誰の承認が要るか。**順序を持つなら順序も** |

## 書かない節

| 書かないもの | なぜ |
| --- | --- |
| 技術的な設計の詳細 | 承認者が判断するのは金額と責任である |
| 複数案の比較 | 案を選ぶのは提案・企画の工程。ここでは 1 案に絞る |
| 実施後の運用の詳細 | 別の文書が持つ |

## 読み手が最初に問うこと

**「いくらで、いつからで、誰が責任を持つか」。** 件名にこの 3 つが入っていれば、
一覧で見たときに判断の見当が付く。

続いて**「なぜ今か」**が来る。時期の必然性が無いと、次の期へ回される。

## よくある欠落

| 欠落 | 何が起きるか |
| --- | --- |
| 税の扱いが書かれていない | 決裁の区分（金額の閾値）が変わる |
| 内訳が無い | 削る判断も、比べる判断もできない |
| やらなかったときの影響が無い | 承認する理由が読み取れない |
| 承認の経路が分からない | 差し戻しの往復が増える |
| 継続の契約で前回との差が無い | 前回と同じか、増えたのかが分からない |
