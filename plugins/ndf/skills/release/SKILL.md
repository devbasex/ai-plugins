# 配布

**マージした変更を、利用者が取得できる状態にする。**

マージは取り込みであって配布ではない。配布物が変わったのに版が据え置きだと、利用者は
再インストールしても版数が同じに見えるため、更新に気づけない。

## 担い手と時期

| | 決まり |
| --- | --- |
| 担い手 | **まとまりの最後のマージを行った側**。単独の変更では実装した本人、複数の Pull Request を束ねたときは進行側 |
| 時期 | **まとまり単位でマージが終わった後** |

**まとまりとは、1 度にマージする Pull Request の集合である。** 単独の変更ではまとまりが
1 件になり、時期はマージ直後と一致する。

Pull Request ごとに版を上げない。3 件をまとめてマージして 3 つ版が進むと、利用者から見て
意味のない版が 2 つ増える。

マージの完了を知っているのは最後にマージした側だけである。実装担当に持たせると、自分の
Pull Request が最後かどうかを判断できない。

## 前後の工程との境界

| | 何を扱うか |
| --- | --- |
| `merged` | マージ後の後片付け。作業ツリーとブランチの削除 |
| **この Skill** | 版を上げて公開する。利用者が取得できる状態にする |
| `release-verification` | 配布された成果物を、利用者の環境で確かめる |

`release-verification` の開始条件はこの工程の完了である。順に通す。

## 開始条件

- まとまりのすべての Pull Request がマージされている
- 配布物に差分がある（後述の「配布物が変わったかを確かめる」）

配布物に差分が無ければ、この工程は飛ばしてよい。文書だけの変更で配布物が動かないことがある。

## 公開前の同意取得（必須）

版の公開は取り消しが難しい。**手順 4 の直前に、次を提示して同意を得る。**

- 上げる版と、その大小の根拠（MAJOR / MINOR / PATCH のどれで、なぜか）
- まとまりに含まれる Pull Request の一覧
- 配布物の差分（変更したファイル数）

同意が得られなければ、版の更新までで止め、公開しない。

## 手順

### 1. 配布物が変わったかを確かめる

```bash
git diff --stat <まとまりのマージ前>..HEAD -- <配布物のパス> | tail -1
```

差分が無ければ、この工程は飛ばす。飛ばしたことを完了報告へ残す。

### 2. 版の大小を決める

**新しい基準を作らない。** 判断は `docs/plugin-development-guide.md` の「バージョン管理」に従う。
破壊的変更は MAJOR、後方互換のある追加は MINOR、修正は PATCH である。

まとまりに複数の変更が入るときは、**最も大きいものが版の大小を決める**。修正 2 件と
機能追加 1 件なら MINOR になる。

### 3. 版と説明文書を更新する

手順は `docs/plugin-development-guide.md` の「バージョン更新時の手順」にある。機械で
確かめられない項目が 1 つあるため、そこだけ再掲する。

**更新案内の本文を、その版の変更内容へ書き直す。** 見出しの版数だけを置き換えて、本文を
前の版の説明のまま残さない。見出しの版数の遅れは検査が捕まえるが、本文が古いことは
機械では判定できない。

### 4. 公開する

同意を得てから実行する。公開の形は対象によって変わる（版のタグ、パッケージの公開、
既定ブランチへの反映）。

### 5. 取得の手順を示す

**配布は、利用者が取得して初めて届く。** 公開しただけでは、利用者の環境は前の版のままである。
完了報告に、利用者が実行する取得の手順を書く。

## 完了の判定

- 版が上がり、公開されている
- 説明文書の記載が新しい版と一致している（`python3 scripts/check-doc-staleness.py` が
  終了コード 0 で終わる。同等の検査があればそれを使う）
- 利用者が取得する手順が完了報告に書かれている

## 出力物

```markdown
## 配布

版: <前の版> → <新しい版>（<MAJOR / MINOR / PATCH> の根拠を 1 行）
まとまり: PR #<番号> / #<番号> / #<番号>
配布物の差分: <ファイル数> ファイル

利用者が取得する手順:

    <再インストールや再取得のコマンド>

次の工程: リリース後テスト（`/ndf:release-verification`）
```

配布物に差分が無くて飛ばしたときは、そのことと根拠のコマンドを残す。書かずに省くと、
配布し忘れたのか、配布が不要だったのかを後から区別できない。

## モードごとの要否

要否を決めるのは `development-workflow` である。この Skill は判定結果を受け取って実行する。
呼ばれた時点で、この工程が要ると判定されている。

範囲外の課題が見つかったときは `/ndf:out-of-scope` で起票する。

進行を盤面へ記録する場合は、[references/projects-tracking.md](../development-workflow/references/projects-tracking.md) の「`$SCRIPTS` を決める」でパスを解決してから
`bash "$SCRIPTS/projects-sync.sh" <issue番号> stage 配布` を実行する（`.ndf/projects.json` が無いリポジトリでは何も起きない）。

## 関連

- `/ndf:merged` — この工程の前に行うマージ後の後片付け
- `/ndf:release-verification` — この工程の後に行うリリース後テスト
- `/ndf:out-of-scope` — 配布で見つけた範囲外の課題の起票
