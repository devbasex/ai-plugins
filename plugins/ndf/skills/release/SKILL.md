# 配布

**マージした変更を、利用者が受け取れる状態にする。**

マージは取り込みであって配布ではない。取り込んだだけの変更は、利用者の環境では起きていない。

## 配布の形

**何をもって「受け取れる」かは対象で変わる。** 形を先に決める。手順の骨格は共通で、
形ごとに変わるのは**起点の決め方・公開の仕方・取得の手順・取り消し手段**の 4 つである。

| 形 | 例 | 利用者へ届く仕組み |
| --- | --- | --- |
| パッケージ・プラグイン | npm / PyPI / Claude Code のプラグイン | 利用者が取得する |
| サービス | Web アプリ / Web API / Web フロントエンド | 反映で届く。取得の動作は無い |
| デスクトップアプリ | Windows / macOS のアプリ | 利用者が導入する。署名が要る |
| モバイルアプリ | iOS / Android のアプリ | ストアの審査を経て公開される |
| 手順・設定 | 運用手順 / 設定の変更 | 利用者へ配る |

形ごとの詳細は [references/distribution-forms.md](references/distribution-forms.md) の索引から辿る。
**着手したら、対象の形のファイルだけを読んでから手順へ入る。** 探しに行くのは、読んだ
ファイルが別のファイルを名指しで指したときだけである（署名した配布物をストアへ出す場合など、
形が複合することがある）。当てはまる形が無ければ、最も近い形の考え方を借り、違うところを
完了報告へ書く。

**サービスは、反映を誰が起こすかでこの工程の形が変わる。** マージで反映が起きる仕組み
（継続的配布）があると、マージが配布そのものになり、同意を取る時点がマージの前へ移る。
参照先の「反映の起動によって工程の形が変わる」を必ず読む。

## 配布の段階

**配布は 1 度で終わらない。検証へ出す配布と、本番へ出す配布は別の配布である。**

| 段階 | 何をするか | この工程の扱い |
| --- | --- | --- |
| 検証への配布 | 検証環境へ反映する。または開発版と分かる形で公開する | 提示して進めてよい |
| 本番への配布 | 本番環境へ反映する。または正式版として公開する | **承認を得るまで進めない** |

**`development-workflow` が自動で進めてよいのは検証への配布までである。** 本番への配布は
工程の続きとして自動で通さない。承認を求めて止まる。反映した瞬間に全利用者へ届く形では、
取り消しても「壊れた状態を見た利用者」は戻らない。

検証への配布が何にあたるかは形で変わる。Web 系は検証環境（`staging` / `qa` / 開発環境）への
反映、パッケージやアプリは**開発版と分かる版数での公開**（`-dev` などの接尾辞、開発用に
充てた版数の帯）にあたる。詳細は [references/distribution-forms.md](references/distribution-forms.md)。

**検証環境が無い、または開発版として公開する手段が無い場合、最初の配布が本番への配布になる。**
その場合はこの工程の最初から承認が要る。「検証を挟めない」ことを同意の提示へ書く。

`release-verification` は段階ごとに行う。検証への配布の後は検証環境で、本番への配布の後は
本番で確かめる。**検証で確かめたことは本番で確かめたことにならない。**

## 担い手と時期

| | 決まり |
| --- | --- |
| 担い手 | **まとまりの最後のマージを行った側**。単独の変更では実装した本人、複数の Pull Request を束ねたときは進行側 |
| 時期 | **まとまり単位でマージが終わった後** |

**まとまりとは、1 度にマージする Pull Request の集合である。** 単独の変更ではまとまりが
1 件になり、時期はマージ直後と一致する。

Pull Request ごとに版を上げない。3 件をまとめてマージして 3 つ版が進むと、利用者から見て
意味のない版が 2 つ増える。

マージの完了を知っているのは最後にマージした側だけである。実装担当に持たせると、自分の
Pull Request が最後かどうかを判断できない。

**反映を仕組みが起こす場合、この決まりは当てはまらない。** マージが配布を引き起こすため、
時期は仕組みの起動に決まり、人がするのは起動の前の確認と起動後の記録になる。詳細は参照先。

## 前後の工程との境界

| | 何を扱うか |
| --- | --- |
| `merged` | マージ後の後片付け。作業ツリーとブランチの削除 |
| **この Skill** | 利用者が受け取れる状態にする |
| `release-verification` | 配布された成果物を、利用者の環境で確かめる |

`release-verification` の開始条件はこの工程の完了である。順に通す。

## 開始条件

- まとまりのすべての Pull Request がマージされている
- 配布物に差分がある（手順 1）
- そのまとまりが、配布そのものを目的とする変更ではない

配布物に差分が無ければ、この工程は飛ばしてよい。文書だけの変更で配布物が動かないことがある。

**配布そのものを目的とする変更は、この工程の対象外である。** 手順 3 が作る Pull Request が
これにあたり、差分は版数の記載と説明文書に限られる。利用者へ届く振る舞いは変わらないため、
配布を要する変更ではない。差分が無いときに飛ばすのと同じ判断になる。

対象外にしておかないと、この工程に終わりが来ない。既定ブランチを直接編集しない運用では版を
上げる作業も Pull Request を通り、それが単独の変更として次のまとまりになる。そのまとまりに
対してまた版を上げることになり、以降は同じことが繰り返される。

## 公開前の提示と承認

**公開の直前に、次を提示する。**

- **どの段階への配布か**（検証 / 本番）
- 上げる版と、その大小の根拠（MAJOR / MINOR / PATCH のどれで、なぜか）
- まとまりに含まれる Pull Request の一覧
- 配布物の差分（変更したファイル数）
- **取り消しの手段と、その限界**（形によって変わる。参照先を読んで書く）

| 段階 | 提示の後 |
| --- | --- |
| 検証への配布 | 提示して進めてよい。記録のために残す |
| 本番への配布 | **承認を得るまで進めない。** 得られなければ検証への配布までで止める |

**本番への配布の承認は、この工程の中で必ず求める。** 前の工程（レビュー・完了判定）を
通ったことは承認の代わりにならない。それらは取り込んでよいかの判断で、利用者へ出してよいかの
判断ではない。

**提示する時点は形で変わる。** マージが配布を引き起こす仕組みでは、公開の直前は
**マージの直前**にあたる。マージした後に承認を求めても、配布はもう起きている。

## 手順

### 1. 配布物が変わったかを確かめる

比較の起点は**前のまとまりを配布した時点**である。起点の取り方は形で変わる（タグ・版数を
書き込んだコミット・直前に反映したリビジョン）。参照先の形ごとのファイルに従う。

**起点を決められないときは推測せず、運用者に確認する。** 誤った起点で比べると、配布済みの
変更を未配布として数えるか、未配布の変更を見落とす。

差分が版数の記載と説明文書だけのときも飛ばす。判定は差分に残るパスで決まる。

差分が無いときと、差分が版数の記載と説明文書だけのときは、この工程を飛ばす。どちらも飛ばした
ことを完了報告へ残す。

### 2. 版の大小を決める

**新しい基準を作らない。** リポジトリに版の付け方の決まりがあればそれに従う。無ければ
セマンティックバージョニングを既定とし、破壊的変更は MAJOR、後方互換のある追加は MINOR、
修正は PATCH とする。

まとまりに複数の変更が入るときは、**最も大きいものが版の大小を決める**。修正 2 件と
機能追加 1 件なら MINOR になる。

**版数を持たない配布もある。** サービスでリビジョンだけで運用している場合がこれにあたる。
その場合は何が出ているかを一意に指せる値（リビジョン・ビルド番号）を記録の対象にする。

### 3. 版と説明文書を更新する

**ブランチを切って Pull Request を通す。** 版と説明文書の更新もほかの変更と同じ扱いで、
既定ブランチを直接編集しない。`merged` が作業ツリーを削除した直後であるため、この工程で
改めて用意する。この Pull Request は配布の工程の一部であり、マージしてもこの工程を
もう一度呼ばない（「開始条件」の対象外の規定にあたる）。

リポジトリに版を上げる手順があればそれに従う。機械で確かめられない項目が 1 つあるため、
そこだけ再掲する。

**更新案内の本文を、その版の変更内容へ書き直す。** 見出しの版数だけを置き換えて、本文を
前の版の説明のまま残さない。見出しの版数の遅れは検査が捕まえられるが、本文が古いことは
機械では判定できない。

### 4. 公開する

同意を得てから実行する。**公開の仕方は形で変わる**（レジストリへの公開・対象の系への反映・
署名した配布物の設置・ストアへの提出）。参照先の形ごとのファイルに従う。

**提出は公開ではない形がある。** ストアの審査を経るものは、審査を通って初めて利用者へ届く。
待っている間はこの工程が続いている状態で、`release-verification` はまだ始められない。

**段階的に公開する運用では、公開は 1 度で終わらない。** どこまで出したかと、次に広げる条件を
完了報告へ書く。

### 5. 届き方を示す

**公開しただけでは、利用者の環境は前の版のままである形がある。** 完了報告に次を書く。

| 形 | 書くこと |
| --- | --- |
| 利用者が取得するもの | 利用者が実行する取得の手順 |
| 反映で届くもの | いつから新しい版が出ているか。利用者が古い版を掴む経路（キャッシュ・接続の維持・再読み込み）があればそれも |
| 審査を経るもの | 公開された時点。段階的公開なら出している範囲 |

## 完了の判定

- **どの段階まで配布したかが定まっている。** 本番へ出していないなら、そこで止めた理由
  （承認待ち・承認が得られなかった）を残す
- 利用者が受け取れる状態になっている（形ごとの「公開」が完了している。審査を経るものは
  審査を通っていること、段階的公開なら出している範囲が定まっていること）
- 版または何が出ているかを一意に指せる値が記録されている
- 説明文書の記載が新しい版と一致している（検査があればそれを通す）
- 届き方が完了報告に書かれている

## 出力物

```markdown
## 配布

形: <パッケージ / サービス / デスクトップ / モバイル / 手順・設定>
段階: <検証 / 本番>（本番なら承認を得た時点、止めたなら理由）
版: <前の版> → <新しい版>（<MAJOR / MINOR / PATCH> の根拠を 1 行）
まとまり: PR #<番号> / #<番号> / #<番号>
配布物の差分: <ファイル数> ファイル
取り消しの手段: <前の版へ戻せるか。戻せないなら、その理由>

届き方:

    <取得の手順、または反映が済んだ時点と古い版を掴む経路>

次の工程: リリース後テスト（`/ndf:release-verification`）
```

配布物に差分が無くて飛ばしたときと、差分が版数の記載と説明文書だけで飛ばしたときは、
そのことと根拠のコマンドを残す。書かずに省くと、配布し忘れたのか、配布が不要だったのかを
後から区別できない。

## モードごとの要否

要否を決めるのは `development-workflow` である。この Skill は判定結果を受け取って実行する。
呼ばれた時点で、この工程が要ると判定されている。

範囲外の課題が見つかったときは `/ndf:out-of-scope` で起票する。

進行を盤面へ記録する場合は、[references/projects-tracking.md](../development-workflow/references/projects-tracking.md) の「`$SCRIPTS` を決める」でパスを解決してから
`bash "$SCRIPTS/projects-sync.sh" <issue番号> stage "配布"` を実行する（`.ndf/projects.json` が無いリポジトリでは何も起きない）。
