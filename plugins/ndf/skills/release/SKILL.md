# リリース

**マージした変更を、利用者が受け取れる状態にする。**

リリースは、マージでマージした変更を利用者の環境へ届けて終わる。マージしただけの変更は、利用者の環境では起きていない。

**環境へ届ける手順は CD（継続的デリバリー）が持つ。NDF の工程が受け持つのは、CD を起動するマージ・その前のリリース承認ゲート・CD の結果の確かめの 3 つである。**
CD はブランチへのマージを起点に環境へ反映する、NDF の工程の外の仕組みで、ブランチ戦略の設定の `release.deliveries` の `kind: auto` の行で定義する。

| `release.deliveries` の設定 | 工程の進み方 |
| --- | --- |
| CD がある（`kind: auto`） | 版上げ・タグ・公開の手順を NDF は打たない。リリースの Pull Request をリリース承認ゲートの後にマージし、CD の結果を読んでリリース記録へ残す |
| `release.form` でバージョンを上げて出す形 | 版上げと変更履歴は `release/v<バージョン>` の Pull Request で行う。行の `publishes_release` が真なら、タグと GitHub Release は CD が作る |
| CD が無い（設定が無い・不明、または理由の無い手動の行） | CD の案内を出し、今の経路のまま手で行うステージへ進む。案内は承認ゲートを増やさず、工程を止めない |
| あえて CD を置かない（手動の行に `manual_reason` がある） | 案内を出さず、`trigger` の手順で手で届ける |

`documentation` モードの提出とモバイルアプリのストアへの提出は CD に含めず、下の形ごとの手順で進める。

### リリースの場合

**リリース承認を取る場所・承認の証跡を書く者・マージする主体は、ブランチ戦略の設定（`.ndf/project.json` の `branch_strategy`）の
`approval` と `merge` で決まる。** 読むのは workflow の `ndf release-steps merge` で、会話のセッションは設定に合わせて承認を取るだけである。

| 設定 | リリース承認を取る場所 | 証跡を書く者 | マージする主体 |
| --- | --- | --- | --- |
| `approval.via: gate`・`merge.actor: ndf` | リリースの PR へ承認資料を `present` で置き、回答を `answer` で書く | `answer` | workflow の `merge`。証跡と HEAD の一致と必須のチェックの通過の後だけ |
| `approval.via: gate`・`merge.actor: human` | 同上 | `merge` が人のマージの記録を書く | 人 |
| `approval.via: review` | リリースの PR のレビューの承認。証跡は書かない | GitHub | workflow の `merge`。write 以上の人の最新の承認のレビューのコミットが HEAD と一致したときだけ |

**`merge.actor: ndf` では、会話のセッションはリリースの PR をマージしない（`ndf ci merge` を打たない）。** `answer` の証跡のコメントで
workflow の `merge` が起動し、必須のチェックを待ってから入れる。セッションが先にマージを打つと、workflow と取り合う。
`answer` の後は、PR がマージされ、タグと GitHub Release ができたことを確かめ（`gh release view <タグ>`）、
`ndf worktree merged <リリースの PR>` でクリーンアップする。マージの記録の名前は workflow が使う token（`NDF_RELEASE_TOKEN`）のオーナーになる。

承認の対象の PR は `approval.target` が決める（`release_pr` は版上げのリリースの PR、`production_pr` は本番の PR）。マージの方式は
`merge.method`（`merge-queue`・`strict`・`direct`）で、管理者の迂回は `merge.method: direct` で `merge.admin: true` のときだけ使う。
迂回でマージするときは利用者の証跡（`--by user`）だけを数え、MVV 判定はこの承認を代えない。

承認したコミットとリリースの PR の HEAD が違えば（承認の後のコミット・スプリントの組み直し）マージされず、承認を取り直す。
マージの後のタグと GitHub Release は workflow の `publish` が作り、会話の中でタグを打たない。

## リリースの形

**何をもって「受け取れる」かは対象で変わる。** 形を先に決める。手順の骨格は共通で、
形ごとに変わるのは**起点の決め方・公開の仕方・完了の確かめ方・取得の手順・取り消し手段**の
5 つである。

| 形 | 例 | 利用者へ届く仕組み |
| --- | --- | --- |
| パッケージ・プラグイン | npm / PyPI / Claude Code のプラグイン | 利用者が取得する |
| サービス | Web アプリ / Web API / Web フロントエンド | 反映で届く。取得の動作は無い |
| デスクトップアプリ | Windows / macOS のアプリ | 利用者が導入する。署名が要る |
| モバイルアプリ | iOS / Android のアプリ | ストアの審査を経て公開される |
| 手順・設定 | 運用手順 / 設定の変更 | 利用者へ配る |
| スライド | 提案資料 / 月次の報告 / 説明資料 | 提出先へ置き、読み手が開く |
| 文書 | 提案書 / 稟議書 / 報告書 | 同上 |
| 表計算 | 指標の管理表 / 稟議の内訳 | 同上 |
| ページ | 運用マニュアル / 稟議のページ | 同上 |

**下の 4 つ（スライド / 文書 / 表計算 / ページ）は `documentation` モードのリリースである。**
上の 5 つと違い、**リリースが生成と提出の 2 つの手順になる**。生成は対になる下書き先へ行い、その間に
生成物の内容検証と体裁レビューと制作物承認が入る。**投稿の手順は置き先のシステムが
持つ**（`document-systems` の `system-<名前>.md`）。

形ごとの詳細は [references/distribution-forms.md](references/distribution-forms.md) の索引から辿る。
**着手したら、対象の形のファイルだけを読んでから手順へ入る。** 探しに行くのは、読んだ
ファイルが別のファイルを名指しで指したときだけである（署名したアーティファクトをストアへ出す場合など、
形が複合することがある）。当てはまる形が無ければ、最も近い形の考え方を借り、違うところを
完了報告へ書く。

**サービスは、反映を誰が起動するかでこの工程の形が変わる。** CD があると、マージがリリースそのものになり、
同意を取る時点がマージの前へ移る。参照先の「反映の起動によって工程の形が変わる」を必ず読む。

## リリース種別

**リリースは 1 度で終わらない。検証へ出すリリースと、本番へ出すリリースは別のリリースである。**

| リリース種別 | 何をするか | この工程の扱い |
| --- | --- | --- |
| 開発版のデプロイ | 検証環境へ反映する。または開発版と分かる形で公開する | 提示して進めてよい |
| 本番リリース | 本番環境へ反映する。または正式版として公開する | **承認を得るまで進めない** |

**`development-workflow` が自動で進めてよいのは開発版のデプロイまでである。** 本番リリースは
工程の続きとして自動で通さない。承認を求めて止まる。反映した瞬間に全利用者へ届く形では、
取り消しても「壊れた状態を見た利用者」は戻らない。

開発版のデプロイが何にあたるかは形で変わる。Web 系は検証環境（`staging` / `qa` / 開発環境）への
反映、パッケージやアプリは**開発版と分かる版数での公開**（`-dev` などの接尾辞、開発用に
充てた版数の帯）にあたる。詳細は [references/distribution-forms.md](references/distribution-forms.md)。

**検証環境が無い、または開発版として公開する手段が無い場合、最初のリリースが本番リリースになる。**
その場合はこの工程の最初から承認が要る。「検証を挟めない」ことを同意の提示へ書く。

`release-verification` はリリース種別ごとに行う。開発版のデプロイの後は検証環境で、本番リリースの後は
本番で確かめる。**検証で確かめたことは本番で確かめたことにならない。**

## 担い手と時期

| | 決まり |
| --- | --- |
| 担い手 | **スプリントの最後のマージを行った側**。単独の変更では実装した本人、複数の Pull Request を 1 つのスプリントで出したときはオーケストレーター |
| 時期 | **スプリント単位でマージが終わった後** |

**スプリントとは、1 度にマージする Pull Request の集合である。** 単独の変更ではスプリントが
1 件になり、時期はマージ直後と一致する。

Pull Request ごとにバージョンを上げない。3 件をまとめてマージして 3 つバージョンが進むと、利用者から見て
意味のないバージョンが 2 つ増える。

マージの完了を知っているのは最後にマージした側だけである。実装担当に持たせると、自分の
Pull Request が最後かどうかを判断できない。

**CD が反映を起動する場合、この決まりは当てはまらない。** 時期はマージに決まり、工程がするのはマージの前の承認とマージの後の確かめになる。

## 前後の工程との境界

| | 何を扱うか |
| --- | --- |
| `merged` | マージ後のクリーンアップ。worktree とブランチの削除。その退避先は本番へ出した後にこの工程が回収の候補として挙げ、人の承認（`ndf-ask:redline:C4`）を得てから消す（[references/release-steps.md](references/release-steps.md)「退避先の回収」） |
| **この Skill** | 利用者が受け取れる状態にする |
| `release-verification` | リリースされた成果物を、利用者の環境で確かめる |

`release-verification` の開始条件はこの工程の完了である。順に通す。

## 開始条件

- **スプリントのすべての Pull Request がマージされている。** どこまでがスプリントかを確かめるのは
  この工程である（`merged` は判断できなくても待たない）。状態ファイル（スプリントの状態・目録）から AI が決め、決まらなければ止めて報告する
- リリース対象に差分がある（手順 1）
- そのスプリントが、リリースそのものを目的としない

リリース対象に差分が無ければ、この工程は飛ばしてよい。説明文書だけの変更でリリース対象が動かないことが
ある。**ただし `documentation` モードでは、提出する文書の SSOT がリリース対象そのものである**（手順 1）。

**リリースそのものを目的とする変更は、この工程の対象外である。** 手順 3 が作る Pull Request が
これにあたり、差分は版数の記載と説明文書に限られる。利用者へ届く振る舞いは変わらないため、
リリースを要さない変更として扱う。差分が無いときに飛ばすのと同じ判断になる。

対象外にしておかないと、この工程に終わりが来ない。既定ブランチを直接編集しない運用ではバージョンを
上げる作業も Pull Request を通り、それが単独の変更として次のスプリントになる。そのスプリントに
対してまたバージョンを上げることになり、以降は同じことが繰り返される。

## 公開前の提示と承認

**公開の直前に、次を提示する。**

- **どのリリース種別か**（検証 / 本番）
- 上げるバージョンと、その大小の根拠（MAJOR / MINOR / PATCH のどれで、なぜか）
- スプリントに含まれる Pull Request の一覧
- リリース対象の差分（変更したファイル数）
- **取り消しの手段と、その限界**（形によって変わる。参照先を読んで書く）

| リリース種別 | 提示の後 |
| --- | --- |
| 開発版のデプロイ | 提示して進めてよい。記録のために残す |
| 本番リリース | **承認を得るまで進めない。** 得られなければ開発版のデプロイまでで止める。`pace: fast` と `pace: auto` では MVV 判定の記録（「従う」でレッドラインなし）も承認として扱う（条件は `AGENTS.md` と [pace.md](../development-workflow/references/pace.md)） |

**承認を求めるときに提示するものは
[references/approval-request.md](../development-workflow/references/approval-request.md) が
定める。** 本番リリース・制作物承認・公開の同意の質問は `AskUserQuestion` の `metadata.source` に `ndf-gate:2` を付ける（区分の SSOT は [asking.md](../development-workflow/references/asking.md)）。ドキュメントレビューの承認と同じ定義を使い、リリースでは対象がバージョンになる分だけ項目が変わる
（バージョンの比較の URL・リリース対象の差分・**取り消しの手段とその限界**）。

**承認資料の機械で作れる部分は `ndf release-steps materials` が組む。** 打ち方と `status` の読み方は
[references/release-steps.md](references/release-steps.md) にある。判断の要る部分の書き足しと読み手役の確認は
`ndf document-rebuild gate --gate release --pr <リリースの PR> --material <承認資料> --state-dir <保存先> --out <結果のファイル>` が行う
（工程では読み手役のステップが打つ）。提示と質問には結果の `outputs.material` の資料を使い、会話のセッションは読み手役を起動しない
（[approval-request.md の「読み手役の確認」](../development-workflow/references/approval-request.md#読み手役の確認)）。

**承認の対象はリリースの PR の HEAD（40 桁）である。** 置き方は「リリースの場合」で変わる。

- 証跡で承認する設定（`approval.via: gate`）: `ndf release-steps present --pr <リリースの PR> --material <承認資料>` で資料を PR へ置き、
  承認を得たら `present` の routes の `answer`（提示した HEAD と資料の SHA-256 を固定する）に `--by user` を足して証跡を書く。
  承認の後に再開するときは、`present` の前に今の判定を読む（[release-steps.md](references/release-steps.md) の「承認を得たリリースを再開するとき」）。
  MVV 判定で通したときは `--by mvv` で書く（`--material-sha256` は渡さない）。誰がいつ承認したかは証跡のコメントの作成者と作成時刻で読む
- レビューで承認する設定（`approval.via: review`）: リリースの PR のレビューの承認がリリース承認である
変更の要求を受けたら、その場で変更要求の記録へ 1 行書く（[approval-request.md](../development-workflow/references/approval-request.md) の「回答を記録する」）。

**本番リリースの承認は、この工程の中で必ず求める。** 前の工程（コードレビュー・完了判定）を通ったことは
承認の代わりにならない。それらが決めるのはマージしてよいかで、利用者へ出してよいかは本番リリースの承認が決める。

**提示する時点は形で変わる。** マージがリリースの原因になる仕組みでは、公開の直前は
**マージの直前**にあたる。マージした後に承認を求めても、リリースはもう起きている。

## 手順

**手順の先頭でブランチ戦略の設定の `release.deliveries` を読む**（`documentation` モードでは読まない）。本番チャネルへのマージで届く
`kind: auto` の行が無く、手動の行に `manual_reason` も無ければ、CD の案内（[references/cd-setup.md](references/cd-setup.md)）を
完了報告へ載せて今の経路のまま続ける。設定を読めなければ止まり、理由を報告する。

### 1. リリース対象が変わったかを確かめる

比較の起点は**前のスプリントをリリースした時点**である。起点の取り方は形で変わる（タグ・版数を
書き込んだコミット・直前に反映したリビジョン）。参照先の形ごとのファイルに従う。

**起点を決められないときは推測せず、運用者に確認する。** 誤った起点で比べると、リリース済みの
変更を未リリースとして数えるか、未リリースの変更を見落とす。

差分が版数の記載と説明文書だけのときも飛ばす。判定は差分に残るパスで決まる。

**説明文書とは、リリース対象の使い方と変更点を説明する文書である**（`README` / 変更履歴 / `docs/`）。
**提出する文書の SSOT は、これに数えない。** `documentation` モードの 4 形（スライド / 文書 /
表計算 / ページ）では、SSOT の Markdown がリリース対象そのものであり、生成と提出を経てはじめて
読み手へ届く。SSOT の置く場所は `.ndf/document.json` の `source_root` が指定する。
**その配下に差分があれば、それだけでこの工程へ進む。**

数えると、文書を改訂しただけの通常の改訂で生成と提出が飛ばされる。**改訂した内容は SSOT に
あるだけで、提出先の読み手には前のバージョンが載ったままになる。**

差分が無いときと、差分が版数の記載と説明文書だけのときは、この工程を飛ばす。どちらも飛ばした
ことを完了報告へ残す。

### 2. バージョンの大小を決める

**新しい基準を作らない。** リポジトリにバージョンの付け方の決まりがあればそれに従う。無ければ
セマンティックバージョニングを既定とし、破壊的変更は MAJOR、後方互換のある追加は MINOR、
修正は PATCH とする。

スプリントに複数の変更が入るときは、**最も大きいものがバージョンの大小を決める**。修正 2 件と
機能追加 1 件なら MINOR になる。

**版数を持たないリリースもある。** サービスでリビジョンだけで運用している場合がこれにあたる。
その場合は何が出ているかを一意に指せる値（リビジョン・ビルド番号）を記録の対象にする。

### 3. バージョンと説明文書を更新する

**`release.form` でバージョンを上げて出す形でだけ行う。** CD の形はこの手順を飛ばし、リビジョンをバージョンの記録に使う（`release/v<バージョン>` の Pull Request を作らない）。

**ブランチ（`release/v<バージョン>`）を切って Pull Request を通す。** 既定ブランチを直接編集しない。
この Pull Request はリリースの工程の一部であり、マージしてもこの工程をもう一度呼ばない
（「開始条件」の対象外の規定にあたる）。**この Pull Request の本文へ `## リリース記録` のブロックを
置く**（下の「出力物」）。**workflow でリリースする形は除く。** その形では workflow の `record` が含めた PR の各々へ記録を書き、
リリースの PR は記録を持たない。

**版数と変更履歴の見出しは workflow の `ndf release-steps assemble` が上げる**（バージョンの保存先はブランチ戦略の設定の
`release.version_store`。打ち方は [references/release-steps.md](references/release-steps.md)）。設定が扱わない形では、
リポジトリにバージョンを上げる手順があればそれに従う。

**変更履歴（CHANGELOG.md のバージョンのセクション）の本文は、`assemble` が作ったリリースの PR のブランチで LLM が
各 PR の本文の `## 利用者向けの変化` と `## 移行の手順` から組み直す**（組み方は references の「CHANGELOG の本文」）。
plugin の README はデプロイで変えない。質は実装の PR の本文で決まる（`pr` の Skill）。

**LLM が確かめ、書くのは次の 2 つである。**

- **変更履歴のバージョンのセクション（移行の手順を含む）に載せたコマンドを、対象のランタイムごとに実行して確かめる。** 合否は終了コードで
  見て、確かめたコマンドと終了コードを完了報告へ残す

  | 確かめ方 | 対象 |
  | --- | --- |
  | そのまま実行する | 利用者の設定を書き換えないもの（一覧・検証・版数の表示） |
  | 設定ディレクトリを隔離して実行する | 取得元の登録と導入を伴うもの |
  | `--help` で副コマンドの存在を確かめる | 隔離しても実行できないもの |
- **組み直した変更履歴のセクションを読み、利用者に伝わらない箇条があれば直す。** 判断の理由はリポジトリの
  知識の側に置く

**バージョンごとの判断を開発の指示書へ書くリポジトリでは、リリース済みバージョンの段落を退避する。** リリースした時点で
その段落は過去の記録になる。指示書に残すと、**その内容を全セッションと全サブエージェントが
毎回読む**（読み込み量として毎回乗る）。退避先と参照の書き方はリポジトリの知識の側が定める。
**参照に@インポートの記法を使わない** ── 使うと退避しても読み込み量は減らない。**退避先が
扱うバージョンの範囲を書いているなら、その記載も同じ操作で直す** ── 段落だけを移すと範囲が古いまま
残り、移したバージョンが対象外に見える。版数どうしは一致したままなので、版数を突き合わせるチェックは拾えない。

**退避の直後に指示書を確かめる。** 移し忘れた段落と、退避先を毎回読ませている参照をここで拾う。
確かめる観点・指示書チェックの設定の書き方・観点の調べ直しは
[references/instruction-files.md](references/instruction-files.md) にある。

**リポジトリが設定したリリースの手順（`.ndf/release.json` の `steps`）は、`assemble` がバージョンと変更履歴を上げた後に走らせ**、
書いたファイルをリリースの Pull Request へ入れる。リリースの設定が無ければ何もしない。手順に `guide` があれば、
リリースの PR のブランチでその手引きに従って判断の要る部分だけを書き足す。**`assemble` が止まったら通ったとしない。**
リリースの設定の書き方と止まり方は [references/release-steps.md](references/release-steps.md) にある。

### 4. 公開する

同意（`ndf-gate:2`）を得てから実行する。**公開の仕方は形で変わる**（レジストリへの公開・対象の系への反映・
署名したアーティファクトの設置・ストアへの提出）。参照先の形ごとのファイルに従う。

**CD の形では、公開は CD が行う。** この手順は「マージの前に承認を取り、マージの後に CD の結果を読む」になる（下の「CD の結果を確かめる」）。

**ブランチ戦略の設定でリリースする形では、組み立てからタグまでを workflow が行う**（置き方は
[references/release-workflow.md](references/release-workflow.md)、打ち方は [references/release-steps.md](references/release-steps.md)）。
会話のセッションは workflow を起動し、承認を取り、結果を読む。`stopped` なら `summary` を報告して止まる。

1. 組み立て: `gh workflow run <workflow> -f step=assemble -f level=<patch|minor|major>`（開発版は `-f channel=dev`）
2. 承認: 「公開前の提示と承認」のとおり `present` で見せ、承認を得てから `answer` を打つ
3. マージ: 証跡のコメントで workflow の `approval-check` と `merge` が動く。承認の判定をコメント以外で打ち直したときは
   `gh workflow run <workflow> -f step=merge -f pr=<リリースの PR>` で起動する。承認と HEAD が一致しなければマージされず、承認を取り直す
4. 公開: 本番ブランチへの push で workflow の `publish` がタグと GitHub Release を作り、`record` がリリース記録を書く

**タグと GitHub Release は workflow の `publish` が作る。** 手元からタグを打たない。
リリースの手順は全体テストを流し直さない。テストは CI の必須チェックが受け持ち、マージはその通過を待つ。

**提出は公開ではない形がある。** ストアの審査を経るものは、審査を通って初めて利用者へ届く。
待っている間はこの工程が続いている状態で、`release-verification` はまだ始められない。

**段階的に公開する運用では、公開は 1 度で終わらない。** どこまで出したかと、次に広げる条件を
完了報告へ書く。

#### CD の結果を確かめる

本番チャネルへのマージの後に、CD の workflow の実行の結果を読み、リリース記録へ残す（読み方と値の意味は [references/release-steps.md](references/release-steps.md) の「デプロイの後にリリース記録を置く」）。
**失敗なら `段階: 反映失敗` を書いて止まり、この工程は完了にならない。未確定なら成功と書かず、リリース後テストが本番の状態を直接確かめる。**

#### 済んだことを確かめる

**公開操作が済んだことは、デプロイ先の状態から読み取る。** ログに出た語だけで済んだとしない。
実装の都合でログの語は変わるため、出ると見込んだ語が出ないだけで待ちが残る。

何を照会すれば済んだと言えるか（リリース完了の確認）は形で決まる。形ごとのファイル（`form-<形>.md`）の
「リリース完了の確認」に従う。workflow でリリースする形では、`merge` と `publish` の結果 JSON の `items[]`（マージした Pull Request・タグ・GitHub Release）と
`ndf release-steps records` が読んだリリース記録がその照会の結果である。公開物を CD が作る形では、CD の workflow の実行の結果がその照会の結果である。

**操作がその場で終わらないときは、待ち方の決まりを
[references/completion-check.md](references/completion-check.md) から読む。** 上限を決めずに
待たないことと、照会のループに待機を置くことがそこにある。

**どのリリースの形でも、リリースを実施した後に、実施後の値で `段階: 本番` のリリース記録を置く。** 形ごとの置き方は
[references/release-steps.md](references/release-steps.md) の「デプロイの後にリリース記録を置く」にある。

### 5. 届き方を示す

**公開しただけでは、利用者の環境は前のバージョンのままである形がある。** 完了報告に次を書く。

| 形 | 書くこと |
| --- | --- |
| 利用者が取得するもの | 利用者が実行する取得の手順 |
| 反映で届くもの | いつから新しいバージョンが出ているか。利用者が古いバージョンを掴む経路（キャッシュ・接続の維持・再読み込み）があればそれも |
| 審査を経るもの | 公開された時点。段階的公開なら出している範囲 |

## 完了の判定

- **どのリリース種別までリリースしたかが定まっている。** 本番へ出していないなら、そこで止めた理由
  （承認待ち・承認が得られなかった）を残す
- 利用者が受け取れる状態になっている（形ごとの「公開」が完了している。審査を経るものは
  審査を通っていること、段階的公開なら出している範囲が定まっていること）
- **リリース完了の確認を済ませている。** 公開操作が済んだことをデプロイ先の状態から読み取り、照会した
  対象と返ってきた値を残す。上限に達して未確定で止めたなら、そのことを残す
- バージョンまたは何が出ているかを一意に指せる値が記録されている
- 説明文書の記載が新しいバージョンと一致している（チェックがあればそれを通す）
- **設定されたリリースコマンドが 0 で終わり、`guide:` が指す手引きの判断を済ませている。** リリースの設定が
  無ければ当てはまらない
- **変更履歴のバージョンのセクションに載せたコマンドを対象のランタイムごとに実行し、終了コードが 0 である。** チェックが
  見るのは版数だけで、コマンドが動くかは見ていない。隔離しても実行できないものは `--help` で
  副コマンドの存在を確かめ、その旨を残す
- 届き方が完了報告に書かれている

## 出力物

```markdown
## リリース

形: <パッケージ / サービス / デスクトップ / モバイル / 手順・設定>
段階: <検証 / 本番>（本番なら承認を得た時点、止めたなら理由）
バージョン: <前のバージョン> → <新しいバージョン>（<MAJOR / MINOR / PATCH> の根拠を 1 行）
スプリント: PR #<番号> / #<番号> / #<番号>
リリース対象の差分: <ファイル数> ファイル
取り消しの手段: <前のバージョンへ戻せるか。戻せないなら、その理由>
完了の確認: <照会した対象> → <返ってきた値>（未確定で止めたなら、上限と止めた理由）

届き方:

    <取得の手順、または反映が済んだ時点と古いバージョンを掴む経路>

次の工程: リリース後テスト（`/ndf:release-verification`）
```

**このテンプレートは会話に出るだけで、別の実行からは読めない。** そのため `段階:`・`バージョン:`・`スプリント:` の
3 行を、見出し `## リリース記録` の直後にそのままの形で並べたブロックを**手順 3 のリリースの
Pull Request の本文へ置く。workflow でリリースする形は除く**（Pull Request を作らない形では、スプリントの最後にマージした
Pull Request へコメントで投稿する）。**workflow でリリースする形では、本番ブランチへのマージの後に workflow の `record` が
含めた PR の各々へ記録を書くため、手で置かない**（[references/release-steps.md](references/release-steps.md) の「デプロイの後にリリース記録を置く」）。

```markdown
## リリース記録

段階: 本番（2026-09-18 10:00 に承認）
バージョン: 10.14.0 → 10.15.0（MINOR: 機能追加）
スプリント: PR #717 / #718 / #720
CD の結果: 成功（リビジョン 5d6e7f8… https://github.com/<所有者>/<リポジトリ>/actions/runs/1）
```

CD の形のバージョンは `main 1a2b3c4 → main 5d6e7f8` のようにリビジョンで書く。`CD の結果:` の行は CD を読んだときだけ置く。

リリース対象に差分が無くて飛ばしたときと、差分が版数の記載と説明文書だけで飛ばしたときは、
そのことと根拠のコマンドを残す。書かずに省くと、リリースし忘れたのか、リリースが不要だったのかを
後から区別できない。**飛ばしたときも同じブロックを残す。** `段階: デプロイなし（<飛ばした理由>）` と
`スプリント:` の 2 行だけを書き（`バージョン:` は書かない）、置く場所は Pull Request を作らない形と同じにする。
**この記録が無いと、スプリント課題が閉じられない**（閉じる条件と読み方は `progress-tracking` の
「スプリントを閉じる」が持つ）。

## モードごとの要否

要否を決めるのは `development-workflow` である。この Skill は判定結果を受け取って実行する。
呼ばれた時点で、この工程が要ると判定されている。

範囲外の課題が見つかったときは `/ndf:out-of-scope` で起票する。

## スプリントを閉じる

**後にリリース後テストも振り返りも続かない変更（`light`、どちらも通らない `operation`）では、
この工程がその実行の最終工程である。** デプロイを終えた後に、
`progress-tracking` の「スプリントを閉じる」を `--final-stage デプロイ` で行う。**手順と、閉じた後の順序（棚卸しへ進む）はそこが SSOT で、ここにはコピーしない。**
続く工程があるなら呼ばない（`release-verification` か `retrospective` が行う）。
**開発版のデプロイで止めた実行でも呼ぶ。** 課題は閉じる条件に当たらず `開いたまま` になり、
閉じるのは後で本番リリースを行った実行の最終工程である。
