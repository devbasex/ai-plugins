# 配布

**マージした変更を、利用者が受け取れる状態にする。**

マージは取り込みであって配布ではない。取り込んだだけの変更は、利用者の環境では起きていない。

## 配布の形

**何をもって「受け取れる」かは対象で変わる。** 形を先に決める。手順の骨格は共通で、
形ごとに変わるのは**起点の決め方・公開の仕方・完了の確かめ方・取得の手順・取り消し手段**の
5 つである。

| 形 | 例 | 利用者へ届く仕組み |
| --- | --- | --- |
| パッケージ・プラグイン | npm / PyPI / Claude Code のプラグイン | 利用者が取得する |
| サービス | Web アプリ / Web API / Web フロントエンド | 反映で届く。取得の動作は無い |
| デスクトップアプリ | Windows / macOS のアプリ | 利用者が導入する。署名が要る |
| モバイルアプリ | iOS / Android のアプリ | ストアの審査を経て公開される |
| 手順・設定 | 運用手順 / 設定の変更 | 利用者へ配る |
| スライド | 提案資料 / 月次の報告 / 説明資料 | 提出先へ置き、読み手が開く |
| 文書 | 提案書 / 稟議書 / 報告書 | 同上 |
| 表計算 | 指標の管理表 / 稟議の内訳 | 同上 |
| ページ | 運用マニュアル / 稟議のページ | 同上 |

**下の 4 つ（スライド / 文書 / 表計算 / ページ）は `documentation` モードの配布である。**
上の 5 つと違い、**配布が生成と提出の 2 段になる**。生成は対になる下書き先へ行い、その間に
生成物の内容照合と体裁レビューと制作物承認が入る。**投稿の手順は形ではなく置き先のシステムが
持つ**（`document-systems` の `system-<名前>.md`）。

形ごとの詳細は [references/distribution-forms.md](references/distribution-forms.md) の索引から辿る。
**着手したら、対象の形のファイルだけを読んでから手順へ入る。** 探しに行くのは、読んだ
ファイルが別のファイルを名指しで指したときだけである（署名した配布物をストアへ出す場合など、
形が複合することがある）。当てはまる形が無ければ、最も近い形の考え方を借り、違うところを
完了報告へ書く。

**サービスは、反映を誰が起こすかでこの工程の形が変わる。** マージで反映が起きる仕組み
（継続的配布）があると、マージが配布そのものになり、同意を取る時点がマージの前へ移る。
参照先の「反映の起動によって工程の形が変わる」を必ず読む。

## 配布の段階

**配布は 1 度で終わらない。検証へ出す配布と、本番へ出す配布は別の配布である。**

| 段階 | 何をするか | この工程の扱い |
| --- | --- | --- |
| 検証への配布 | 検証環境へ反映する。または開発版と分かる形で公開する | 提示して進めてよい |
| 本番への配布 | 本番環境へ反映する。または正式版として公開する | **承認を得るまで進めない** |

**`development-workflow` が自動で進めてよいのは検証への配布までである。** 本番への配布は
工程の続きとして自動で通さない。承認を求めて止まる。反映した瞬間に全利用者へ届く形では、
取り消しても「壊れた状態を見た利用者」は戻らない。

検証への配布が何にあたるかは形で変わる。Web 系は検証環境（`staging` / `qa` / 開発環境）への
反映、パッケージやアプリは**開発版と分かる版数での公開**（`-dev` などの接尾辞、開発用に
充てた版数の帯）にあたる。詳細は [references/distribution-forms.md](references/distribution-forms.md)。

**検証環境が無い、または開発版として公開する手段が無い場合、最初の配布が本番への配布になる。**
その場合はこの工程の最初から承認が要る。「検証を挟めない」ことを同意の提示へ書く。

`release-verification` は段階ごとに行う。検証への配布の後は検証環境で、本番への配布の後は
本番で確かめる。**検証で確かめたことは本番で確かめたことにならない。**

## 担い手と時期

| | 決まり |
| --- | --- |
| 担い手 | **ミッションの最後のマージを行った側**。単独の変更では実装した本人、複数の Pull Request を束ねたときは進行側 |
| 時期 | **ミッション単位でマージが終わった後** |

**ミッションとは、1 度にマージする Pull Request の集合である。** 単独の変更ではミッションが
1 件になり、時期はマージ直後と一致する。

Pull Request ごとに版を上げない。3 件をまとめてマージして 3 つ版が進むと、利用者から見て
意味のない版が 2 つ増える。

マージの完了を知っているのは最後にマージした側だけである。実装担当に持たせると、自分の
Pull Request が最後かどうかを判断できない。

**反映を仕組みが起こす場合、この決まりは当てはまらない。** マージが配布を引き起こすため、
時期は仕組みの起動に決まり、人がするのは起動の前の確認と起動後の記録になる。詳細は参照先。

## 前後の工程との境界

| | 何を扱うか |
| --- | --- |
| `merged` | マージ後の後片付け。作業ツリーとブランチの削除 |
| **この Skill** | 利用者が受け取れる状態にする |
| `release-verification` | 配布された成果物を、利用者の環境で確かめる |

`release-verification` の開始条件はこの工程の完了である。順に通す。

## 開始条件

- **ミッションのすべての Pull Request がマージされている。** どこまでがミッションかを確かめるのは
  この工程である（`merged` は判断できなくても待たない）。分からなければ運用者に聞く
- 配布物に差分がある（手順 1）
- そのミッションが、配布そのものを目的としない

配布物に差分が無ければ、この工程は飛ばしてよい。説明文書だけの変更で配布物が動かないことが
ある。**ただし `documentation` モードでは、提出する文書の正本が配布物そのものである**（手順 1）。

**配布そのものを目的とする変更は、この工程の対象外である。** 手順 3 が作る Pull Request が
これにあたり、差分は版数の記載と説明文書に限られる。利用者へ届く振る舞いは変わらないため、
配布を要する変更ではない。差分が無いときに飛ばすのと同じ判断になる。

対象外にしておかないと、この工程に終わりが来ない。既定ブランチを直接編集しない運用では版を
上げる作業も Pull Request を通り、それが単独の変更として次のミッションになる。そのミッションに
対してまた版を上げることになり、以降は同じことが繰り返される。

## 公開前の提示と承認

**公開の直前に、次を提示する。**

- **どの段階への配布か**（検証 / 本番）
- 上げる版と、その大小の根拠（MAJOR / MINOR / PATCH のどれで、なぜか）
- ミッションに含まれる Pull Request の一覧
- 配布物の差分（変更したファイル数）
- **取り消しの手段と、その限界**（形によって変わる。参照先を読んで書く）

| 段階 | 提示の後 |
| --- | --- |
| 検証への配布 | 提示して進めてよい。記録のために残す |
| 本番への配布 | **承認を得るまで進めない。** 得られなければ検証への配布までで止める |

**承認を求めるときに提示するものは
[references/approval-request.md](../development-workflow/references/approval-request.md) が
定める。** ドキュメントレビューの承認と同じ定義を使い、配布では対象が版になる分だけ項目が変わる
（版の比較の URL・配布物の差分・**取り消しの手段とその限界**）。

**Claude Code のプラグインの形では、提示物の機械で作れる部分を `release-steps.py approval-facts` が
書き出す。** 打ち方と `status` の読み方は [references/release-steps.md](references/release-steps.md) にある。

**本番への配布の承認は、この工程の中で必ず求める。** 前の工程（実装レビュー・完了判定）を
通ったことは承認の代わりにならない。それらは取り込んでよいかの判断で、利用者へ出してよいかの
判断ではない。

**提示する時点は形で変わる。** マージが配布を引き起こす仕組みでは、公開の直前は
**マージの直前**にあたる。マージした後に承認を求めても、配布はもう起きている。

## 手順

### 1. 配布物が変わったかを確かめる

比較の起点は**前のミッションを配布した時点**である。起点の取り方は形で変わる（タグ・版数を
書き込んだコミット・直前に反映したリビジョン）。参照先の形ごとのファイルに従う。

**起点を決められないときは推測せず、運用者に確認する。** 誤った起点で比べると、配布済みの
変更を未配布として数えるか、未配布の変更を見落とす。

差分が版数の記載と説明文書だけのときも飛ばす。判定は差分に残るパスで決まる。

**説明文書とは、配布物の使い方と変更点を説明する文書である**（`README` / 変更履歴 / `docs/`）。
**提出する文書の正本は、これに数えない。** `documentation` モードの 4 形（スライド / 文書 /
表計算 / ページ）では、正本の Markdown が配布物そのものであり、生成と提出を経てはじめて
読み手へ届く。正本の置き場所は `.ndf/document.json` の `source_root` が宣言する。
**その配下に差分があれば、それだけでこの工程へ進む。**

数えると、文書を改訂しただけの通常の改訂で生成と提出が飛ばされる。**改訂した内容は正本に
あるだけで、提出先の読み手には前の版が載ったままになる。**

差分が無いときと、差分が版数の記載と説明文書だけのときは、この工程を飛ばす。どちらも飛ばした
ことを完了報告へ残す。

### 2. 版の大小を決める

**新しい基準を作らない。** リポジトリに版の付け方の決まりがあればそれに従う。無ければ
セマンティックバージョニングを既定とし、破壊的変更は MAJOR、後方互換のある追加は MINOR、
修正は PATCH とする。

ミッションに複数の変更が入るときは、**最も大きいものが版の大小を決める**。修正 2 件と
機能追加 1 件なら MINOR になる。

**版数を持たない配布もある。** サービスでリビジョンだけで運用している場合がこれにあたる。
その場合は何が出ているかを一意に指せる値（リビジョン・ビルド番号）を記録の対象にする。

### 3. 版と説明文書を更新する

**ブランチ（`release/v<版>`）を切って Pull Request を通す。** 既定ブランチを直接編集しない。
この Pull Request は配布の工程の一部であり、マージしてもこの工程をもう一度呼ばない
（「開始条件」の対象外の規定にあたる）。**この Pull Request の本文へ「配布の記録」のブロックを
置く**（下の「出力物」）。

**Claude Code のプラグインの形では、版数と変更履歴を `release-steps.py bump` / `changelog` が
上げる**（打ち方は [references/release-steps.md](references/release-steps.md)）。ほかの形では、
リポジトリに版を上げる手順があればそれに従う。

**更新案内と変更履歴の本文は `release-steps.py notes` が各 PR の本文の `## 利用者向けの変化` から組む。**
`changelog` は見出しと PR のタイトルを並べるだけで、`notes` がそれを利用者向けの説明へ差し替える。
説明の良し悪しは実装の Pull Request の本文で決まる（書き方は `pr` の Skill）。

**LLM が確かめ、書くのは次の 2 つである。**

- **更新案内に載せたコマンドを、対象のランタイムごとに実行して確かめる。** 合否は終了コードで
  見て、確かめたコマンドと終了コードを完了報告へ残す

  | 確かめ方 | 対象 |
  | --- | --- |
  | そのまま実行する | 利用者の設定を書き換えないもの（一覧・検証・版数の表示） |
  | 設定ディレクトリを隔離して実行する | 取得元の登録と導入を伴うもの |
  | `--help` で副コマンドの存在を確かめる | 隔離しても実行できないもの |
- **`notes` が組んだ変更履歴の節を読み、利用者に伝わらない箇条があれば直す。** 判断の理由はリポジトリの
  知識の側に置く

**版ごとの判断を開発の指示書へ書くリポジトリでは、出た版の段落を退避する。** 配布した時点で
その段落は過去の記録になる。指示書に残すと、**その内容を全セッションと全サブエージェントが
毎回読む**（読み込みの量として毎回乗る）。退避先と参照の書き方はリポジトリの知識の側が定める。
**参照に即時読み込みの記法を使わない** ── 使うと退避しても読み込みの量は減らない。**退避先が
扱う版の範囲を書いているなら、その記載も同じ操作で直す** ── 段落だけを移すと範囲が古いまま
残り、移した版が対象外に見える。版数どうしの一致ではないため、版数を突き合わせる検査は拾えない。

**退避の直後に指示書の検査を実行する**（`python3 "$SCRIPTS/instructions-check.py" --root .`）。
移し忘れた段落と、退避先を毎回読ませている参照がここで落ちる。`$SCRIPTS` の解決・終了コードを
潰さない 4 行・宣言の書き方・観点の調べ直しは
[references/instruction-files.md](references/instruction-files.md) にある。

**版と説明文書を上げた後、配布の Pull Request を作る前に、リポジトリが宣言した配布の段を走らせる**
（`python3 "$SCRIPTS/release-steps.py" run --root . --stage <production|verification> --version <版>`）。
宣言（`.ndf/release.json`）が無ければ何も出さずに 0 で終わる。段が書いたファイルは配布の
Pull Request に入れる。`guide:` の行が出たら、その手引きに従って判断の要る部分だけを書き足す。
**0 以外を通ったとしない。** 宣言の書き方と終了コードは
[references/release-steps.md](references/release-steps.md) にある。

### 4. 公開する

同意を得てから実行する。**公開の仕方は形で変わる**（レジストリへの公開・対象の系への反映・
署名した配布物の設置・ストアへの提出）。参照先の形ごとのファイルに従う。

**Claude Code のプラグインの形では、公開を `release-steps.py release --channel dev|prod` が行う**
（打ち方は [references/release-steps.md](references/release-steps.md)）。**`--channel prod` は
「公開前の提示と承認」で承認を得るまで打たない。** `stopped` なら `summary` を報告して止まる。

**提出は公開ではない形がある。** ストアの審査を経るものは、審査を通って初めて利用者へ届く。
待っている間はこの工程が続いている状態で、`release-verification` はまだ始められない。

**段階的に公開する運用では、公開は 1 度で終わらない。** どこまで出したかと、次に広げる条件を
完了報告へ書く。

#### 済んだことを確かめる

**公開の操作が済んだことは、配布先の状態から読み取る。** ログに出た語だけで済んだとしない。
実装の都合でログの語は変わるため、出ると見込んだ語が出ないだけで待ちが残る。

何を照会すれば済んだと言えるか（完了の事実）は形で決まる。形ごとのファイル（`form-<形>.md`）の
「完了の事実」に従う。Claude Code のプラグインの形では、`release` の結果 JSON の `items[]`
（マージした Pull Request・タグ・GitHub Release）がその照会の結果であり、LLM が照会を回さない。

**操作がその場で終わらないときは、待ち方の決まりを
[references/completion-check.md](references/completion-check.md) から読む。** 上限を決めずに
待たないことと、照会のループに待機を置くことがそこにある。

### 5. 届き方を示す

**公開しただけでは、利用者の環境は前の版のままである形がある。** 完了報告に次を書く。

| 形 | 書くこと |
| --- | --- |
| 利用者が取得するもの | 利用者が実行する取得の手順 |
| 反映で届くもの | いつから新しい版が出ているか。利用者が古い版を掴む経路（キャッシュ・接続の維持・再読み込み）があればそれも |
| 審査を経るもの | 公開された時点。段階的公開なら出している範囲 |

## 完了の判定

- **どの段階まで配布したかが定まっている。** 本番へ出していないなら、そこで止めた理由
  （承認待ち・承認が得られなかった）を残す
- 利用者が受け取れる状態になっている（形ごとの「公開」が完了している。審査を経るものは
  審査を通っていること、段階的公開なら出している範囲が定まっていること）
- **完了の事実を確かめている。** 公開の操作が済んだことを配布先の状態から読み取り、照会した
  対象と返ってきた値を残す。上限に達して未確定で止めたなら、そのことを残す
- 版または何が出ているかを一意に指せる値が記録されている
- 説明文書の記載が新しい版と一致している（検査があればそれを通す）
- **宣言された配布の段が 0 で終わり、`guide:` が指す手引きの判断を済ませている。** 宣言が
  無ければ当てはまらない
- **更新案内に載せたコマンドを対象のランタイムごとに実行し、終了コードが 0 である。** 検査が
  見るのは版数だけで、コマンドが動くかは見ていない。隔離しても実行できないものは `--help` で
  副コマンドの存在を確かめ、その旨を残す
- 届き方が完了報告に書かれている

## 出力物

```markdown
## 配布

形: <パッケージ / サービス / デスクトップ / モバイル / 手順・設定>
段階: <検証 / 本番>（本番なら承認を得た時点、止めたなら理由）
版: <前の版> → <新しい版>（<MAJOR / MINOR / PATCH> の根拠を 1 行）
ミッション: PR #<番号> / #<番号> / #<番号>
配布物の差分: <ファイル数> ファイル
取り消しの手段: <前の版へ戻せるか。戻せないなら、その理由>
完了の確認: <照会した対象> → <返ってきた値>（未確定で止めたなら、上限と止めた理由）

届き方:

    <取得の手順、または反映が済んだ時点と古い版を掴む経路>

次の工程: リリース後テスト（`/ndf:release-verification`）
```

**この雛形は会話に出るだけで、別の実行からは読めない。** そのため `段階:`・`版:`・`ミッション:` の
3 行を、見出し `## 配布の記録` の直後にそのままの形で並べたブロックを**手順 3 の配布の
Pull Request の本文へ置く**（Pull Request を作らない形では、ミッションの最後にマージした
Pull Request へコメントで投稿する）。

```markdown
## 配布の記録

段階: 本番（2026-09-18 10:00 に承認）
版: 10.14.0 → 10.15.0（MINOR: 機能追加）
ミッション: PR #717 / #718 / #720
```

配布物に差分が無くて飛ばしたときと、差分が版数の記載と説明文書だけで飛ばしたときは、
そのことと根拠のコマンドを残す。書かずに省くと、配布し忘れたのか、配布が不要だったのかを
後から区別できない。**飛ばしたときも同じブロックを残す。** `段階: 配布なし（<飛ばした理由>）` と
`ミッション:` の 2 行だけを書き（`版:` は書かない）、置き場所は Pull Request を作らない形と同じにする。
**この記録が無いと、ミッションの課題が閉じられない**（閉じる条件は「本番への配布まで済んだ、または
配布を飛ばした」。読み方は `progress-tracking` の「ミッションを閉じる」が持つ）。

## モードごとの要否

要否を決めるのは `development-workflow` である。この Skill は判定結果を受け取って実行する。
呼ばれた時点で、この工程が要ると判定されている。

範囲外の課題が見つかったときは `/ndf:out-of-scope` で起票する。

この工程に入ったら記録のコマンド `bash "$SCRIPTS/projects-sync.sh" <issue番号> stage "配布"` を 1 行打つ（issue の本文と盤面の両方に残る。`$SCRIPTS` の決め方は `development-workflow` の `references/scripts-lookup.md`、3 層では起動指示の「記録のコマンド」を使う）。

## ミッションを閉じる

**後にリリース後テストも振り返りも続かない変更（`light`、どちらも通らない `operation`）では、
この工程がその実行の終わりの工程である。** 次の「蓄積した課題を手入れする」の前に、
`progress-tracking` の「ミッションを閉じる」を行う。**手順はそこが正本で、ここには写さない。**
続く工程があるなら呼ばない（`release-verification` か `retrospective` が行う）。
**検証への配布で止めた実行でも呼ぶ。** 課題は閉じる条件に当たらず `開いたまま` になり、
閉じるのは後で本番への配布を行った実行の終わりの工程である。

## 蓄積した課題を手入れする

**後にリリース後テストも振り返りも続かない変更では、「ミッションを閉じる」の後に
`/ndf:issue-upkeep` を呼ぶ。** 続く工程があるなら、そちらの最後で呼ばれるため呼ばない。

対象が 0 件ならその Skill 自身が飛ばす。
