# 配布

**マージした変更を、利用者が取得できる状態にする。**

マージは取り込みであって配布ではない。配布物が変わったのに版が据え置きだと、利用者は
再インストールしても版数が同じに見えるため、更新に気づけない。

## 担い手と時期

| | 決まり |
| --- | --- |
| 担い手 | **まとまりの最後のマージを行った側**。単独の変更では実装した本人、複数の Pull Request を束ねたときは進行側 |
| 時期 | **まとまり単位でマージが終わった後** |

**まとまりとは、1 度にマージする Pull Request の集合である。** 単独の変更ではまとまりが
1 件になり、時期はマージ直後と一致する。

Pull Request ごとに版を上げない。3 件をまとめてマージして 3 つ版が進むと、利用者から見て
意味のない版が 2 つ増える。

マージの完了を知っているのは最後にマージした側だけである。実装担当に持たせると、自分の
Pull Request が最後かどうかを判断できない。

## 前後の工程との境界

| | 何を扱うか |
| --- | --- |
| `merged` | マージ後の後片付け。作業ツリーとブランチの削除 |
| **この Skill** | 版を上げて公開する。利用者が取得できる状態にする |
| `release-verification` | 配布された成果物を、利用者の環境で確かめる |

`release-verification` の開始条件はこの工程の完了である。順に通す。

## 開始条件

- まとまりのすべての Pull Request がマージされている
- 配布物に差分がある（後述の「配布物が変わったかを確かめる」）
- そのまとまりが、配布そのものを目的とする変更ではない

配布物に差分が無ければ、この工程は飛ばしてよい。文書だけの変更で配布物が動かないことがある。

**配布そのものを目的とする変更は、この工程の対象外である。** 手順 3 が作る Pull Request が
これにあたり、差分は版数の記載と説明文書に限られる。利用者へ届く振る舞いは変わらないため、
配布を要する変更ではない。差分が無いときに飛ばすのと同じ判断になる。

対象外にしておかないと、この工程に終わりが来ない。既定ブランチを直接編集しない運用では版を
上げる作業も Pull Request を通り、それが単独の変更として次のまとまりになる。そのまとまりに
対してまた版を上げることになり、以降は同じことが繰り返される。

## 公開前の同意取得（必須）

版の公開は取り消しが難しい。**手順 4 の直前に、次を提示して同意を得る。**

- 上げる版と、その大小の根拠（MAJOR / MINOR / PATCH のどれで、なぜか）
- まとまりに含まれる Pull Request の一覧
- 配布物の差分（変更したファイル数）

同意が得られなければ、版の更新までで止め、公開しない。

## 手順

### 1. 配布物が変わったかを確かめる

比較の起点は**前のまとまりを配布した時点**である。次の順で決める。

```bash
# 版のタグを打つ運用なら、直前のタグが起点になる。--match には対象の版のタグだけに
# 当たる形を渡す（1 つのリポジトリで複数のプラグインへ別々にタグを打つ運用があるため）
BASE=$(git describe --tags --abbrev=0 --match 'ndf-v*' 2>/dev/null)

# タグが無いなら、いま入っている版数を書き込んだコミットが起点になる
CURRENT=$(python3 -c "import json;print(json.load(open('plugins/ndf/.claude-plugin/plugin.json'))['version'])")
[ -n "$BASE" ] || BASE=$(git log -1 --format=%H -S"\"version\": \"$CURRENT\"" -- plugins/ndf/.claude-plugin/plugin.json)

# どちらでも決まらなければ、比較へ進まずここで止める
[ -n "$BASE" ] || { echo "起点を決められない。運用者に確認する" >&2; exit 1; }

# 比較の対象は、いま版を上げるプラグインの配布物のパスに絞る
git diff --stat "$BASE"..HEAD -- plugins/ndf/ | tail -1
```

版数を持つファイルと配布物の置き場所、タグの付け方はリポジトリごとに違う。上の
`plugins/ndf/.claude-plugin/plugin.json`（版数）と `plugins/ndf/`（配布物）と `ndf-v*`
（タグ）は、対象のリポジトリのものへ読み替える。

**配布物のパスは、いま版を上げるプラグインのものを指定する。** 1 つのリポジトリで複数の
プラグインを配布していると、それらをまとめて置く上位のディレクトリ（この例では `plugins/`）
には対象外のプラグインの変更も入る。それを数えると、対象の配布物が動いていないのに版を
上げることになる。`--match` でタグを絞るのと同じ理由である。

**まとまりで複数のプラグインの版を上げるときは、プラグインごとに確かめる。** 版はプラグイン
ごとに独立しているため、起点も大小の判断もプラグインごとに分かれる。次は 2 つの配布物を
1 度に数える書き方で、起点が同じときだけ使える。

```bash
git diff --stat "$BASE"..HEAD -- plugins/ndf/ plugins/playwright-kit/ | tail -1
```

**`--match` を省いて直前のタグを採らない。** 1 つのリポジトリで複数のプラグインへ別々に
タグを打つ運用では、対象外のプラグインのタグが直前になることがある。そのタグを起点にすると、
それより前にある対象の差分が比較から消え、配布が要るのに不要と判定する。

**`BASE` が空のままなら、起点を推測せず運用者に確認する。** 版数を書き込んだコミットが
見つからない場合と、まとまりの範囲が履歴から読み取れない場合がこれにあたる。誤った起点で
比べると、配布済みの変更を未配布として数える。

空の `BASE` を止めるのは、`git diff` が失敗しないためである。空の起点は `HEAD..HEAD` として
受け取られ、終了コード 0 と空の出力が返る。差分が無いときと見分けがつかないため、配布物が
変わっていてもこの工程を飛ばすことになる。

**差分が版数の記載と説明文書だけのときも飛ばす。** 判定は差分に残るパスで決まる。版数を持つ
ファイルとプラグインの説明文書を除いて何も残らなければ、配布そのものを目的とする変更である。

```bash
REST=$(git diff --name-only "$BASE"..HEAD -- plugins/ndf/ \
  | grep -vxE 'plugins/ndf/(\.claude-plugin|\.codex-plugin)/plugin\.json|plugins/ndf/README\.md')
if [ -z "$REST" ]; then
  echo "版数の記載と説明文書だけ。この工程を飛ばす"
else
  echo "$REST"
fi
```

除外するパスは、対象のリポジトリで版数を持つファイルと、そのプラグインの説明文書へ読み替える。
配布物の中にある説明文書（`plugins/ndf/skills/README.md` など）は除外しない。それらは利用者へ
届く配布物の一部である。

結果は変数で受けて中身を見る。`grep` は一致が無いと終了コード 1 を返すため、`&&` や `||` で
つなぐと、対象外と判定できた場合を失敗として扱うことになる。

差分が無いときと、差分が版数の記載と説明文書だけのときは、この工程を飛ばす。どちらも飛ばした
ことを完了報告へ残す。

### 2. 版の大小を決める

**新しい基準を作らない。** 判断は `docs/plugin-development-guide.md` の「バージョン管理」に従う。
破壊的変更は MAJOR、後方互換のある追加は MINOR、修正は PATCH である。

まとまりに複数の変更が入るときは、**最も大きいものが版の大小を決める**。修正 2 件と
機能追加 1 件なら MINOR になる。

### 3. 版と説明文書を更新する

**ブランチを切って Pull Request を通す。** 版と説明文書の更新もほかの変更と同じ扱いで、
既定ブランチを直接編集しない。`merged` が作業ツリーを削除した直後であるため、この工程で
改めて用意する。この Pull Request は配布の工程の一部であり、マージしてもこの工程を
もう一度呼ばない（「開始条件」の対象外の規定にあたる）。

手順は `docs/plugin-development-guide.md` の「バージョン更新時の手順」にある。機械で
確かめられない項目が 1 つあるため、そこだけ再掲する。

**更新案内の本文を、その版の変更内容へ書き直す。** 見出しの版数だけを置き換えて、本文を
前の版の説明のまま残さない。見出しの版数の遅れは検査が捕まえるが、本文が古いことは
機械では判定できない。

### 4. 公開する

同意を得てから実行する。**既定ブランチへの反映は、手順 3 の Pull Request をマージして
行う。** 版のタグやパッケージの公開は、そのマージの後に進める。

### 5. 取得の手順を示す

**配布は、利用者が取得して初めて届く。** 公開しただけでは、利用者の環境は前の版のままである。
完了報告に、利用者が実行する取得の手順を書く。

## 完了の判定

- 版を上げた Pull Request がマージされ、公開されている
- 説明文書の記載が新しい版と一致している（`python3 scripts/check-doc-staleness.py` が
  終了コード 0 で終わる。同等の検査があればそれを使う）
- 利用者が取得する手順が完了報告に書かれている

## 出力物

```markdown
## 配布

版: <前の版> → <新しい版>（<MAJOR / MINOR / PATCH> の根拠を 1 行）
まとまり: PR #<番号> / #<番号> / #<番号>
配布物の差分: <ファイル数> ファイル

利用者が取得する手順:

    <再インストールや再取得のコマンド>

次の工程: リリース後テスト（`/ndf:release-verification`）
```

配布物に差分が無くて飛ばしたときと、差分が版数の記載と説明文書だけで飛ばしたときは、
そのことと根拠のコマンドを残す。書かずに省くと、配布し忘れたのか、配布が不要だったのかを
後から区別できない。

## モードごとの要否

要否を決めるのは `development-workflow` である。この Skill は判定結果を受け取って実行する。
呼ばれた時点で、この工程が要ると判定されている。

範囲外の課題が見つかったときは `/ndf:out-of-scope` で起票する。

## 関連

- `/ndf:merged` — この工程の前に行うマージ後の後片付け
- `/ndf:release-verification` — この工程の後に行うリリース後テスト
- `/ndf:out-of-scope` — 配布で見つけた範囲外の課題の起票
