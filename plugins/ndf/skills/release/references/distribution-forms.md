# 配布の形ごとの手順

`release` の手順は形に依らない。**形ごとに変わるのは、起点の決め方・公開の仕方・取得の
手順・取り消し手段の 4 つ**である。ここではそれを形ごとに書く。

対象がどの形にあたるかは `SKILL.md` の「配布の形」で決める。当てはまるものが無ければ、
最も近い形の考え方を借り、違うところを完了報告へ書く。

## 形ごとの一覧

| 形 | 起点 | 検証への配布 | 本番への配布 | 取得 | 取り消し |
| --- | --- | --- | --- | --- | --- |
| パッケージ・プラグイン | 直前の版のタグ、または版数を書き込んだコミット | 開発版と分かる版数で公開 | 正式版としてレジストリへ公開 | 利用者が取得する | 新しい版を出す |
| サービス | 直前に反映したリビジョン | 検証環境へ反映 | 本番環境へ反映 | **無い**（反映で届く） | 前のリビジョンへ戻す |
| デスクトップアプリ | 直前の版のタグ | 開発版のチャネルへ置く | 正式版として署名して置く | 利用者が導入する | 新しい版を出す |
| モバイルアプリ | 直前の版のタグ | 内部テスト・クローズドテストへ配る | ストアへ提出し、審査を経て公開 | 利用者が更新する | 段階的公開を止める |
| 手順・設定 | 直前に配った版 | 一部の利用者へ先に配る | 全員へ配る | 利用者が読む | 前の版を配り直す |

**本番への配布は、どの形でも承認を得てから行う**（`SKILL.md` の「配布の段階」）。この表の
「検証への配布」までが、工程の続きとして進めてよい範囲である。

## 開発版と分かる形で公開する

パッケージ・プラグイン・デスクトップ・モバイルは、**検証のための配布も利用者から見える場所へ
出ることがある**。正式版と取り違えられないよう、版数で開発用だと分かるようにする。

| やり方 | 例 | 向く場面 |
| --- | --- | --- |
| 接尾辞を付ける | `1.4.0-dev.3` / `1.4.0-rc.1` / `1.4.0-beta` | レジストリが事前公開の版を区別できる場合。多くのレジストリは既定の取得先から外す |
| 版数の帯を開発用に充てる | `1.5.x` を開発用、`1.6.x` を正式版（奇数を開発用にする慣習） | 接尾辞を扱えない配布先。番号だけで区別が付く |
| 配布の経路を分ける | 開発版のチャネル / 内部テストの配布先 | ストアや自動更新の仕組みが経路を持つ場合 |

**どれを採るかは配布先が決める。** レジストリが事前公開の版を既定の取得先から外すなら接尾辞が
素直で、そうでなければ帯か経路を分ける。**選んだやり方を完了報告へ書く。** 書かないと、次に
配布する人が別のやり方を採り、利用者から見て規則が無くなる。

**開発版の版数を正式版へ流用しない。** `1.4.0-rc.1` を確かめた後に出す正式版は `1.4.0` で
あって、`-rc` を外しただけの同じ中身とは限らない。確かめた対象と出す対象が違うなら、
`release-verification` は正式版に対してやり直す。

## パッケージ・プラグイン

npm / PyPI / Claude Code のプラグインなど、レジストリを経て利用者が取得するもの。

- **起点**: 直前の版のタグ。タグを打たない運用では、いま入っている版数を書き込んだコミット
- **公開**: レジストリへ公開する。既定ブランチへの反映を伴う運用ではそれも含む
- **取得**: 利用者が実行する。完了報告に取得のコマンドを書く
- **取り消し**: **取り下げには制限がある。** npm は公開から 72 時間を過ぎると不可、PyPI は
  同じ版数を再利用できない。取り消しではなく新しい版で直す前提で公開する

**1 つのリポジトリで複数のパッケージを配布している場合**、比較の対象を対象のパッケージの
配布物のパスへ絞る。まとめて置く上位のディレクトリを数えると、対象が動いていないのに版を
上げることになる。タグも同じ理由で、対象の版のタグだけに当たる形で絞る。

版はパッケージごとに独立するため、まとまりで複数の版を上げるときは、起点も大小の判断も
パッケージごとに分ける。

### このリポジトリでの例

```bash
# 版のタグを打つ運用なら、直前のタグが起点になる。--match には対象の版のタグだけに
# 当たる形を渡す（1 つのリポジトリで複数のプラグインへ別々にタグを打つ運用があるため）
BASE=$(git describe --tags --abbrev=0 --match 'ndf-v*' 2>/dev/null)

# タグが無いなら、いま入っている版数を書き込んだコミットが起点になる
CURRENT=$(python3 -c "import json;print(json.load(open('plugins/ndf/.claude-plugin/plugin.json'))['version'])")
[ -n "$BASE" ] || BASE=$(git log -1 --format=%H -S"\"version\": \"$CURRENT\"" -- plugins/ndf/.claude-plugin/plugin.json)

# どちらでも決まらなければ、比較へ進まずここで止める
[ -n "$BASE" ] || { echo "起点を決められない。運用者に確認する" >&2; exit 1; }

# 比較の対象は、いま版を上げるプラグインの配布物のパスに絞る
git diff --stat "$BASE"..HEAD -- plugins/ndf/ | tail -1
```

起点が同じなら、複数の配布物を 1 度に数えてよい。

```bash
git diff --stat "$BASE"..HEAD -- plugins/ndf/ plugins/playwright-kit/ | tail -1
```

**空の `BASE` で先へ進まない。** 空の起点は `HEAD..HEAD` として受け取られ、終了コード 0 と
空の出力が返る。差分が無いときと見分けがつかず、配布物が変わっていてもこの工程を飛ばす。

配布そのものを目的とする変更かは、差分に残るパスで決まる。

```bash
REST=$(git diff --name-only "$BASE"..HEAD -- plugins/ndf/ \
  | grep -vxE 'plugins/ndf/(\.claude-plugin|\.codex-plugin)/plugin\.json|plugins/ndf/README\.md')
if [ -z "$REST" ]; then
  echo "版数の記載と説明文書だけ。この工程を飛ばす"
else
  echo "$REST"
fi
```

結果は変数で受けて中身を見る。`grep` は一致が無いと終了コード 1 を返すため、`&&` や `||` で
つなぐと、対象外と判定できた場合を失敗として扱うことになる。

除外するのは版数を持つファイルとパッケージの説明文書だけである。**配布物の中にある説明文書
（`plugins/ndf/skills/README.md` など）は除外しない。** それらは利用者へ届く配布物の一部である。

## サービス（Web アプリ・Web API・Web フロントエンド）

利用者が取得するのではなく、**反映した瞬間に全利用者が新しい版になる**もの。

**この形は検証環境があることを前提にする。** 反映した瞬間に全利用者へ届くため、本番へ出す
前に確かめる場が要る。このリポジトリの運用では環境ブランチ（`qa/*` / `staging/*` /
`release/*`）がそれにあたり、反映の手順は `/ndf:deploy` と `/ndf:cherry-pick-pr` が扱う。

**検証環境が無い場合、最初の反映が本番への配布になる。** その場合はこの工程の最初から承認が
要る。検証環境を用意していないことを同意の提示へ書く。

- **起点**: 直前に反映したリビジョン。配布の記録（デプロイの履歴）から取る。版数ではなく
  リビジョンで決まるため、タグを打たない運用でも起点は残っている。**環境ごとに別の起点を
  持つ。** 検証環境の起点で本番の差分を数えない
- **公開**: 対象の系へ反映する。**環境が複数ある運用では、環境ごとに別の配布である**
  （検証環境への反映は本番の配布ではない）
- **取得**: **無い。** 手順 5 の「取得の手順」の代わりに、**いつから新しい版が出ているか**と
  **利用者が古い版を掴んでいる可能性**（キャッシュ・接続の維持・アプリの再読み込み）を書く
- **取り消し**: 前のリビジョンへ戻す。**戻せることを公開前に確かめる。** データの移行を伴う
  変更は戻せないことがあり、その場合は前進でしか直せない旨を同意の提示へ含める

### 反映の起動によって工程の形が変わる

**サービスは、反映を誰が起こすかで担い手・時期・同意の取り方が変わる。** 3 つに分かれる。

| 起動 | 反映が起きる時点 | 担い手 | 同意 |
| --- | --- | --- | --- |
| 継続的配布（マージで反映） | **マージした瞬間** | 仕組み。人は結果を確かめる | **マージの前**に取る |
| 起動が手動（承認・タグ・手元からの実行） | 人が起こした時点 | 起こす人 | 起動の前に取る |
| 仕組みが無い | 人が手で反映した時点 | 反映する人 | 反映の前に取る |

#### 継続的配布（マージで反映）が設定されている場合

**マージが配布そのものになる。** `merged` の後に配布を置く並びは、この形では成り立たない。
工程の順序ではなく、実際に起きる順序に合わせる。

- **同意はマージの前に取る。** 手順 4 の直前に同意を取る決まりは、この形ではマージの直前へ
  移る。マージした後に同意を求めても、配布はもう起きている
- **まとまり単位の配布にならない。** 3 件をまとめたければ、マージ自体をまとめるか、反映の
  対象を既定ブランチから外す（タグや別のブランチで起こす）。**版数だけを揃えても配布は
  分かれる**
- **担い手は結果を確かめる側になる。** 反映は仕組みが行うため、人がするのは「反映が成功
  したか」「どのリビジョンが出ているか」の確認と、版の記録である
- **手順 4 は「反映を待って結果を確かめる」になる。** 失敗したときに何が出ているか
  （前の版のままか、途中で止まっているか）を確かめる
- **取り消しも仕組みに乗る。** 打ち消しのコミットをマージして再び反映させる形が多い。
  その経路が働くこと（所要時間を含む）を公開の前に確かめておく

この形では、**この工程の実体はマージの前の確認とマージ後の記録**である。飛ばしてよい工程では
なく、置き場所が変わる。

**本番への反映まで自動で起こす設定は、承認の決まりと両立しない。** 反映の対象が本番なら、
マージの前に承認を得る（マージが承認の実行になる）。検証環境までを自動、本番を手動の起動に
分けている運用なら、検証への配布は自動で進み、本番への配布で改めて承認を得る形になる。

#### 起動が手動（承認・タグ・手元からの実行）の場合

マージと配布が分かれるため、`SKILL.md` の並び（まとまり単位でマージが終わった後）がそのまま
当てはまる。担い手はまとまりの最後のマージを行った側で、その人が起動する。

**承認の仕組みがある場合、その承認は同意の提示の代わりにならない。** 承認は誰が押したかを
記録するもので、上げる版と根拠を示す手続きではない。手順どおり提示してから起動する。

#### 仕組みが無い場合

手で反映する。**手順を書いた通りに実行して確かめる**（配布は取り消しが難しいため、手元で
試せる環境があるなら先に通す）。反映の途中で失敗したときに、どこまで出ているかを確かめる
手段を用意してから始める。

**段階的に公開する運用では、公開は 1 度で終わらない。** 一部へ出して様子を見る形を取るなら、
どこまで出したかと、次に広げる条件を完了報告へ書く。`release-verification` はその時点で
出ている範囲を対象にする。

**API は利用者が他の実装である。** 契約を変える配布は、利用者側の変更と順序が付く。互換性を
壊す変更を出す場合は、いつ古い契約を止めるかを同意の提示へ含める。

## デスクトップアプリ（Windows・macOS など）

配布物を利用者が導入するもの。パッケージに近いが、署名と配布チャネルが加わる。

- **起点**: 直前の版のタグ
- **公開**: 配布物へ署名して置く。**署名が無いと利用者の環境が導入を拒む**ため、署名は公開の
  一部であって後回しにできない。ストアを経る場合はモバイルアプリの項も読む
- **取得**: 利用者が導入する。自動更新の仕組みがあるなら、それが配る時期も書く
- **取り消し**: 新しい版を出す。**導入済みの環境は戻らない。** 自動更新で下げられるかは
  仕組みによる。戻せない前提で公開の同意を取る

## モバイルアプリ（iOS・Android）

ストアの審査を経て公開されるもの。**公開が即時に完了しない**点が他と違う。

- **起点**: 直前の版のタグ
- **検証への配布**: 内部テスト・クローズドテストの配布先へ出す。審査が軽いか不要な経路が
  用意されていることが多い。ここまでが工程の続きとして進めてよい範囲である
- **公開**: ストアへ提出する。**提出は公開ではない。** 審査を通って初めて利用者へ届く。
  審査で落ちることがあり、その場合は直して出し直す
- **取得**: 利用者が更新する。自動更新の設定に依るため、古い版が長く残る
- **取り消し**: 段階的公開の途中なら止められる。公開済みの版は新しい版で直す

**この工程は提出までで終わらない。** 完了の判定は「審査を通って公開された」ことに置く。
審査待ちの間は工程が続いている状態で、`release-verification` はまだ始められない。
待ちが長い場合は、待っていることと次に確かめる時期を完了報告へ残す。

## 手順・設定の変更

運用手順や設定など、利用者へ配って読んでもらうもの。

- **起点**: 直前に配った版
- **公開**: 利用者へ配る（周知の手段は運用による）
- **取得**: 利用者が読む。読まれたかは確かめられないため、**いつ誰へ配ったか**を残す
- **取り消し**: 前の版を配り直す。配った先へ訂正が届くまで、古い手順で動く人が残る
