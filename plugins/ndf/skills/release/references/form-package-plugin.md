# 配布の形: パッケージ・プラグイン


利用者が取得の操作をして受け取るもの。**取得先の作りで 2 つに分かれる。**

| 種別 | 例 | 取得先 | 版を選ぶ手段 |
| --- | --- | --- | --- |
| レジストリ型 | npm / PyPI / RubyGems | レジストリ | **版数**（`install <名前>@<版>`） |
| エージェントプラグイン型 | Claude Code / Codex / Kiro のプラグイン | **git リポジトリ**（マーケットプレイス） | **git の ref**。版数では選べない |

**この違いは起点・公開・取り消しのすべてに効く。** 以下はレジストリ型の要約で、
エージェントプラグイン型は末尾の節に別に書く。

- **起点**: 直前の版のタグ。タグを打たない運用では、いま入っている版数を書き込んだコミット
- **公開**: レジストリへ公開する。既定ブランチへの反映を伴う運用ではそれも含む
- **取得**: 利用者が実行する。完了報告に取得のコマンドを書く
- **取り消し**: **取り下げには制限がある。** npm は公開から 72 時間を過ぎると不可、PyPI は
  同じ版数を再利用できない。取り消しではなく新しい版で直す前提で公開する

起点の決め方（次節）は両方に当てはまる。

**1 つのリポジトリで複数のパッケージを配布している場合**、比較の対象を対象のパッケージの
配布物のパスへ絞る。まとめて置く上位のディレクトリを数えると、対象が動いていないのに版を
上げることになる。タグも同じ理由で、対象の版のタグだけに当たる形で絞る。

版はパッケージごとに独立するため、まとまりで複数の版を上げるときは、起点も大小の判断も
パッケージごとに分ける。

## このリポジトリでの例

```bash
# 版のタグを打つ運用なら、直前のタグが起点になる。--match には対象の版のタグだけに
# 当たる形を渡す（1 つのリポジトリで複数のプラグインへ別々にタグを打つ運用があるため）。
# `claude plugin tag` が作るのは {プラグイン名}--v{版} で、ハイフンは 2 つである
BASE=$(git describe --tags --abbrev=0 --match 'ndf--v*' 2>/dev/null)

# タグが無いなら、いま入っている版数を書き込んだコミットが起点になる
CURRENT=$(python3 -c "import json;print(json.load(open('plugins/ndf/.claude-plugin/plugin.json'))['version'])")
[ -n "$BASE" ] || BASE=$(git log -1 --format=%H -S"\"version\": \"$CURRENT\"" -- plugins/ndf/.claude-plugin/plugin.json)

# どちらでも決まらなければ、比較へ進まずここで止める
[ -n "$BASE" ] || { echo "起点を決められない。運用者に確認する" >&2; exit 1; }

# 比較の対象は、いま版を上げるプラグインの配布物のパスに絞る
git diff --stat "$BASE"..HEAD -- plugins/ndf/ | tail -1
```

起点が同じなら、複数の配布物を 1 度に数えてよい。

```bash
git diff --stat "$BASE"..HEAD -- plugins/ndf/ plugins/playwright-kit/ | tail -1
```

**空の `BASE` で先へ進まない。** 空の起点は `HEAD..HEAD` として受け取られ、終了コード 0 と
空の出力が返る。差分が無いときと見分けがつかず、配布物が変わっていてもこの工程を飛ばす。

配布そのものを目的とする変更かは、差分に残るパスで決まる。

```bash
REST=$(git diff --name-only "$BASE"..HEAD -- plugins/ndf/ \
  | grep -vxE 'plugins/ndf/(\.claude-plugin|\.codex-plugin)/plugin\.json|plugins/ndf/README\.md')
if [ -z "$REST" ]; then
  echo "版数の記載と説明文書だけ。この工程を飛ばす"
else
  echo "$REST"
fi
```

結果は変数で受けて中身を見る。`grep` は一致が無いと終了コード 1 を返すため、`&&` や `||` で
つなぐと、対象外と判定できた場合を失敗として扱うことになる。

除外するのは版数を持つファイルとパッケージの説明文書だけである。**配布物の中にある説明文書
（`plugins/ndf/skills/README.md` など）は除外しない。** それらは利用者へ届く配布物の一部である。


## エージェントプラグイン（Claude Code / Codex / Kiro）

レジストリではなく **git リポジトリをマーケットプレイスとして配る**形。npm や PyPI と違い、
取得する版を決めるのは版数ではなく **git の ref** である。

### 版数は「どのコードを取るか」を決めない

**`plugin.json` の `version` は更新の判定に使う識別子である。** 取得する実体は、利用者が
登録した取得元の ref が決める。インストールのコマンドに版を指定する手段は無い。

```bash
claude plugin install <名前>@<マーケットプレイス名>   # @ の右はマーケットプレイス名。版ではない
```

このため、**版数を書き戻しても過去のコードには戻らない。** 戻す手段は「取り消し」にある。

### 版数が複数箇所にある

配布物とマーケットプレイス定義の両方に版数を書く運用では、**上げ忘れた箇所が検査を落とす**。
上げる前に、版数を書いている箇所を数え上げておく。

- **版を持つのは配布物の `plugin.json` だけにする。** マーケットプレイス定義に `version`
  フィールドを置くと、`plugin.json` が無警告で優先され、食い違いに気づけない
- 説明文書に書いた版数（`(vX.Y.Z)` など）は読み手向けの記載で、取得する版を決める値ではない
- 生成物を持つ構成では、版を上げた後に**同期を回してから**コミットする

### チャネルは ref で分ける

**開発版と正式版を分けるなら、版数の接尾辞ではなく ref を分ける。** 接尾辞は人が読むための
印であって、取得の経路を変えない。

```bash
claude plugin marketplace add <owner>/<repo>@<ref>          # GitHub の短い形
claude plugin marketplace add <git-url>#<ref>               # URL の形
codex plugin marketplace add <owner>/<repo> --ref <ref>
```

- **ref を指定しない登録は、登録した時点の既定ブランチに固定される。** 既定ブランチを別の
  名前へ移しても、すでに登録した利用者は追随しない。**正式版を既定ブランチへ置く**と、
  利用者の取得手順を変えずに済む
- **2 つのチャネルが同じ版数へ解決されると、更新が飛ばされる。** 開発版の版数へ接尾辞を
  付けておけば必ず異なる
- **取得元は名前ごとに 1 つしか登録できない。** 同じ名前で別の取得元を追加すると、利用者の
  登録が**置き換わる**。ローカルのディレクトリを同じ名前で追加してはならない
- 名前を変えれば併存できるが、**同名のプラグインが両方とも有効になる**ため、どちらが使われる
  かが定まらない。手元での確認は取得元を書き換えない手段（`claude --plugin-dir` や installer）
  で行う

### リリースタグを打つ

```bash
claude plugin tag <配布物のディレクトリ> --dry-run   # 打つ内容を確認する
claude plugin tag <配布物のディレクトリ> --push      # {名前}--v{版} を作って送る
```

**`plugin.json` の版とマーケットプレイスの項目が食い違っていないかを、打つ前に検査する。**
タグは起点の決定（この文書の前半）と、利用者が過去の版へ戻るときの目印を兼ねる。

### 取り消しは利用者の側の操作になる

**配布した側から前の版へ戻す手段は無い。** 利用者が取得元の ref を変える。完了報告へ書く
「取り消しの手段」は、次の 2 つとその限界を指す。

| 手段 | 内容 | 限界 |
| --- | --- | --- |
| 取得元ごとタグへ固定 | `marketplace add <owner>/<repo>@<名前>--v<版>` | **同じ取得元の他のプラグインも過去の状態になる** |
| 対象だけを固定 | 別名のマーケットプレイスを 1 つ作り、`git-subdir` で対象のパスと `ref` / `sha` を直接指す | 利用者が定義ファイルを持つ必要がある |

```json
{"name": "<別名>", "owner": {"name": "<所有者>"},
 "plugins": [{"name": "<プラグイン名>",
   "source": {"source": "git-subdir", "url": "<git-url>",
              "path": "<配布物のパス>", "ref": "<タグ>"}}]}
```

`ref` はブランチまたはタグ、`sha` は 40 文字のコミット。両方あるときは `sha` が効く。

**固定した版と最新版を同時に有効にしない。** どちらのスキルが使われるかが定まらない。

### 届き方

**サードパーティのマーケットプレイスは自動更新が既定で無効である。** 公開した版が即座に全
利用者へ届くわけではなく、利用者が更新を実行した時点で届く。完了報告の「届き方」には、
利用者が実行する更新のコマンドを書く。
