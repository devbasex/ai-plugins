# 蓄積した課題を手入れする

**変更をまたいで溜まった課題そのものを見直す。** 起票はその場で行い、その変更から出た
取りこぼしは振り返りが拾うが、**一覧の全体を現状に合わせる手順**はどちらも持たない。

2026-09-04 に open 43 件を 1 件ずつ実物と突き合わせたところ、**24 件（56%）の本文が現状と
食い違っていた**。食い違いの原因は 3 つの版をまたいだ変更に集約された。

**直さないと、すでに直っている課題を拾って作業する。** 前提の違う課題を、書かれたとおりに
直す。着手のまとまりが決まらないまま溜まる。

## いつ呼ぶか

**変更が終わった時点で呼ぶ。** 振り返りがあればその後、無ければ配布の後である。

**着手の直前は判断が歪む場所である。** 実装を担う側には締め切りがあり、そこで「この課題は
成り立たない」と気づいても、止める判断は自分の作業を遅らせる。判断を下す人が、その判断で
損をする立場にある。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| まとまり | 1 度にマージする Pull Request の集合。配布が版を上げる単位 |
| 手入れ | 既存の課題の本文・マイルストーン・ラベルを現状に合わせること |
| 判定 | 課題ごとに決める 7 つの区分 |
| やらない | 課題そのものは成り立つが、抱える費用が直す費用を下回ると決めること |
| 再燃の条件 | 「やらない」で閉じた課題を、再び考える条件 |

**「手入れ」は起票を含まない**（新しい課題を作るのは `out-of-scope` の役目である）。

## 扱う 3 つ

| # | 扱うこと | 決めること |
| --- | --- | --- |
| 1 | 誤りの訂正 | 本文が現状と食い違っている課題を、実物に合わせて直す |
| 2 | マイルストーンの設定 | どのまとまりで着手するかを決める。無ければ新しく作る |
| 3 | やらないの判断 | 成り立つ課題でも、費用に見合わないものを再燃の条件付きで閉じる |

2 の決め方は [references/milestones.md](references/milestones.md)、3 の必要条件は
[references/no-work.md](references/no-work.md) にある。**段 1 と段 2A では読まない**
（対象を選んで調べる段では、どちらの判断も起きない）。

## 手順

**4 段に分け、判定と反映の間に切れ目を置く。**

| 段 | 何をするか | 分担 | 書き込み |
| --- | --- | --- | --- |
| 1 | 対象を選ぶ | しない | なし |
| 2A | 課題ごとに調べる | **件数で割る** | **なし（読み取りだけ）** |
| 2B | 全体で突き合わせて判定を確定する | **しない** | なし |
| 3 | 反映する | 依存の無いものだけ割る | あり |

**段 1 で対象が 0 件なら、そこで飛ばす。** 飛ばしたことを報告へ残す。

**判定を 2A と 2B に分けるのは、課題どうしが独立しないためである。** 重複の判定・正本の
決定・関連する課題の状態・マイルストーンの完了・同じ前提の変化を受けた課題群の書き換えは、
いずれも課題をまたいで決まる。件数で割ると、担当 A が「#10 は #20 の重複」、担当 B が
「#20 は #10 の重複」と判定しうる。

### 段 1: 対象を選ぶ

3 つの経路で集め、重複を除く。**対象は open の課題だけである。**

| 経路 | 取り方 | 拾えるもの |
| --- | --- | --- |
| 機械の候補 | 前の配布から今までの差分のファイルのパスと、削除された行に現れる識別子を検索語にする | 消えたパス・改名された識別子を指す課題 |
| 担当が足す | 差分に現れない前提の変化（運用の開始、外部の状態、版が上がった外部コマンド） | 実在するようになったブランチのような、差分に出ないもの |
| そのまとまり自身 | このまとまりで閉じた課題が属するマイルストーンと、**この期間に起票された課題**（起票した主体を問わない） | 完了したマイルストーン、マイルストーンの付いていない新しい課題 |

**機械の候補だけでは足りない。** 上の 3 原因のうち、`develop` の実在は差分に現れないため
取りこぼす（3 件）。担当が足す経路がこれを拾う。**候補は広めに出して落とす**
（`out-of-scope` が「迷ったら起票する側へ倒す」としたのと同じ考え方である）。

**起票した主体で絞らない。** 3 つ目の経路が拾うのは「この期間に起票され、まだどのまとまりへも
割り当てられていない課題」であり、**自分が起票したものに限らない**。人が起票したもの、別の
担当が起票したもの、自動で起票されたものが同じように入る。

主体で絞ると、**未設定のまま溜まる課題を誰も見ないことになる。** 起票した側は一覧の全体を
見る立場に無く（`out-of-scope` は見つけたその場で起票する）、棚卸をする側が「自分の分だけ」を
見ると、残りは次の棚卸でも同じ理由で外れる。

```bash
# 未設定のまま残っている課題（投稿者で絞らない）
gh issue list --state open --json number,title,labels,milestone \
  --jq '.[] | select(.milestone == null) | "#\(.number) \(.title)"'
```

**全体に影響する変更では、触った領域では足りない。** 次のいずれかに当たるときは対象を
open の全件へ広げる（`--all`）。

| 全体に影響する変更 | 例 |
| --- | --- |
| ディレクトリの移動・統合 | 配布物の置き場所を変える |
| 対応する実行環境の増減 | 配る先のランタイムを足す |
| ブランチ戦略の変更 | 配布のチャネルを分ける |
| 識別子の一括改名 | 委譲先の CLI を置き換える |

**着手の前に対象の件数を示す。** 選んだ結果が少ないとき、担当は全件へ広げる判断をできる。
件数の閾値は決めない（リポジトリによって open の規模が違うため）。

### 段 2A: 課題ごとに調べる

**この段では何も書き込まない。** 課題ごとに独立するため、件数で割って同時に進めてよい。

確かめるのは 5 点である。**本文が指す対象が現在も存在するか / すでに直っているか（再現手順を
実行して確かめる）/ 前提が現状と食い違っていないか / 他の課題と重複していないか / 抱える
費用が直す費用を下回るか。**

| 判定 | 選ぶ条件 | 段 3 での対応 |
| --- | --- | --- |
| そのまま | 本文と現状が一致している | 何もしない |
| 追記が要る | 本文は有効だが、数値・パス・関連する課題の状態が古い | 該当箇所だけを直す |
| 書き直しが要る | 本文の前提が現状と食い違う | 主旨を変えずに前提を書き直す |
| 閉じてよい | すでに直っている | 実行結果を添えて閉じる |
| **やらない** | **課題は成り立つが、抱える費用が直す費用を下回る**（[references/no-work.md](references/no-work.md)） | **`wontfix` を付け、理由と再燃の条件を添えて閉じる** |
| 重複 | 他の課題と同じもの | 段 2B で正本を決める |
| **要判断** | **自動で決められない** | **人へ返す。反映しない** |

**「閉じてよい」と「書き直しが要る」には実行結果を添える**（`investigation-rules`）。読んだ
だけで直っていると判断しない。

段 2A は課題ごとに、**番号・`updated_at`・本文の要約値・判定と根拠（実行したコマンドと
出力）・反映で行う変更・依存する課題の番号**を控える。`updated_at` と要約値は段 3 の照合に、
依存の番号は段 2B と反映の順序に使う。

### 段 2B: 全体で突き合わせて判定を確定する

**この段は分担しない。** 課題をまたいで決まるものを、ここでまとめて確定する。

| 突き合わせるもの | 何を決めるか |
| --- | --- |
| 重複と判定された組 | どちらを正本にするか。片方を閉じたときに残らないものが無いか |
| 関連する課題の状態 | 一方を閉じると、他方の本文が指す前提が変わらないか |
| マイルストーン | 未完了が 0 件になったものはあるか。設定されていない課題をどこへ入れるか |
| ラベルの体系 | 新しく起票された課題に付いているか。基準はそのリポジトリのラベルの説明が持つ |
| 同じ前提の変化を受けた課題群 | 同じ書き換えを、同じ言い回しで行うか |

**重複の判定では、起点が同じことと同じ課題であることを分ける。** 同じ誤りから出た 2 件でも、
片方が 1 行を直すもの、もう片方が手順に確認の項目を足すものであれば、片方を閉じるともう
片方が残らない。

**「やらない」の候補は、この段の後に一括で提示して承認を得る。** 件ごとに聞かない。提示する
項目は [references/no-work.md](references/no-work.md) にある。

### 段 3: 反映する

判定がすべて揃ってから始める。

- **本文は全文を書き直す。** コメントの追記ではなく本体を直す
- **変更の経緯を本文に残さない**（`markdown-writing` のルール 4）。書くのは確定した現在の情報だけ
- **反映する側も 1 度は実物と突き合わせる。** 段 2A の値が現物と合わないことがある

**段 2A と段 3 の間に、別の担当や人が課題を書き換えることがある。** そのまま反映すると相手の
変更を消すため、段 3 は反映の直前に照合する。**`updated_at` が変わっていれば本文の要約値を
見る。** 要約値も変わっていればその課題だけを段 2A へ戻し、同じならそのまま反映する。

**反映は同じ操作を 2 度行っても結果が変わらない形にする。** 済んだ課題を控えへ記録して
やり直しのときは飛ばし、変える内容が無いときは書き込みを行わない。

## 自動で反映してよい変更と、返す変更

| 変更 | 自動で反映してよいか |
| --- | --- |
| パス・行番号・版数の更新 | よい |
| 再現手順を実行して直っていることを確かめて閉じる | よい |
| 明らかな重複を正本へ寄せる | よい |
| 課題をマイルストーンへ入れる。無ければ末尾に新しく作る | よい |
| 依存の記述と食い違うマイルストーンの順序を直す | よい |
| ラベルの説明に照らして重要度を付け替える | よい |
| 前提が反転した課題の問いを立て直す | よい |
| **やらないと判断して閉じる** | **一括で提示し、承認を得てから行う** |
| **起票の意図が現在も要るかを判断できない** | **返す** |
| **正しい読み方が複数ある** | **返す** |

**分かれ目は、判断の材料が本文の外にあるかどうかである。** ラベルの説明・依存の記述・実物の
状態に照らして 1 つに決まるものは反映し、決まらないものだけを返す。

### 重要度と問いの形を変えるときの基準

**新しい基準を作らない。** 判断の材料はリポジトリの側にある。

| 変えるもの | 基準 | 材料の在り処 |
| --- | --- | --- |
| 重要度 | 実害の観測が変わったか | **ラベルの説明**（`gh label list --json name,description`） |
| 問いの形 | 前提が反転したか | 本文が指す実物の状態 |

**重要度は、ラベルの説明が持つ区分へ当てはめる。** 実害の観測が本文へ追記された課題は上げ、
実害が起きない経路だと分かった課題は下げる。**説明の無いラベルへは付け替えない。**

**問いを立て直すのは、前提が反転したときに限る。** **立て直すのは問いの形であって、主旨では
ない。** 何が困るかは変えない。**主旨まで変わるなら、それは別の課題である。** 元の課題を
閉じて新しく起票する判断になるため、返す。

## 外部への書き込みの制限

課題の作成と本文の更新を続けると、GitHub がコンテンツの作成を拒む。実測では 60 秒の間隔で
13 回待った例がある。**待つ長さは応答から取る。** 固定の間隔で待たない。

| 状況 | 待ち方 |
| --- | --- |
| 応答が `Retry-After` を返す | その秒数だけ待つ |
| 上限の回復時刻を返す | その時刻まで待つ |
| どちらも無い（作成の二次的な制限） | 間隔を倍にしながら待つ |
| 一定の回数を超えた | 部分的に終わった状態として止め、何が済んだかを報告へ残す |

## 他のリポジトリで動くこと

前提にしてよいのは `gh` が使えることと、課題管理に issue を使っていることだけである。

| 無いもの | 振る舞い |
| --- | --- |
| マイルストーン | 段 1 の 3 つ目の経路と、扱うこと 2 を飛ばす |
| 重要度ラベル | `gh label list` が返す説明を基準にする。説明が無ければ付け替えない |
| `wontfix` にあたるラベル | ラベルを付けずに閉じる。理由と再燃の条件は本文に残るため検索で拾える |

## 既存の Skill との境界

| Skill | 扱うもの |
| --- | --- |
| `out-of-scope` | 範囲外の課題を、**見つけたその場で**起票する |
| `retrospective` | **その変更の進め方**を見直し、起票の取りこぼしを拾う |
| `issue-upkeep` | **蓄積した既存の課題**を手入れする |

**価値の判断（やらない）を持つのはこの Skill だけである。** `out-of-scope` の「起票しない」は
発見の瞬間の 3 択で、蓄積した課題には及ばない。**発見の瞬間には、指摘の周辺しか見えて
いない。** 同じ原因の課題がほかにあるか、抱える費用が直す費用を下回るかは、一覧を見る棚卸で
しか分からない。

## 完了報告

| 項目 | 何を書くか |
| --- | --- |
| 対象 | 段 1 で選んだ件数と、選んだ経路。0 件なら飛ばしたことと理由 |
| 判定の内訳 | 7 つの判定ごとの件数 |
| 反映 | 直した件数・閉じた件数・返した件数 |
| 未設定のまま残った課題 | 件数と理由（主題が合わず重要度も低い / 1 件しか残らない / 複数に当てはまる） |
| 待った回数 | 外部への書き込みの制限に当たった回数と、待った長さ |

**未設定の件数を報告へ残す。** 残った件数と理由が、次の棚卸の材料になる。

この工程に入ったら `/ndf:progress-tracking <issue番号> "振り返り"` を呼ぶ（この Skill は
工程表に載らないため、直前の工程の値をそのまま使う）。

## 関連

- `/ndf:out-of-scope` — 範囲外の課題を、見つけたその場で起票する
- `/ndf:retrospective` — その変更の進め方を見直す
- `/ndf:investigation-rules` — 「無い」と言うときに示す検索
