# マイルストーンを決める

**マイルストーンは「いつ着手するか」を表す。** 決める軸は 2 つある。

| 軸 | 何を決めるか | 材料の在り処 |
| --- | --- | --- |
| **重要度** | **どのくらい先のマイルストーンか** | ラベルの説明 |
| 主題 | どの課題と一緒に直すか | マイルストーンの説明 |

**重要度が先に効く。** 主題だけで決めると、実害のある課題が「合うマイルストーンが無い」という
理由で後回しになる。主題は、重要度が決めた範囲の中でどれと一緒に直すかを決める。

**重要度は先に見直す。** 起票の時点の値のまま振り分けると、着手の時期が古い値で決まる
（見直しの基準は `SKILL.md` の「重要度と問いの形を変えるときの基準」）。

**マイルストーンを使っていないリポジトリでは、この文書ごと飛ばす。**

## 設定されていない課題を割り当てる

**起票の直後は設定されていなくてよい。** `out-of-scope` は見つけたその場で起票するため、
一覧の全体を見る立場に無い。どのマイルストーンで直すかは、他の課題と並べて初めて決まる。

| 重要度 | 入れる先 | 主題の合うものが無いとき |
| --- | --- | --- |
| **高い**（実害・安全機構の欠落） | 直近のマイルストーンのうち主題の合うもの | **直近のマイルストーンへ、主題によらず入れる** |
| 中くらい（保守性・設計一貫性） | 主題の合うもの | 末尾に新しく作る（下記） |
| 低い（余力があれば） | 主題の合うもの | 未設定のまま残す |

**直近のマイルストーンは、open のうち名前の先頭の連番が最も小さいものである。** open の
マイルストーンは版数を持たず、名前は `<2 桁の連番> <主題>` で着手の順序を表す。**説明が連番と
別の着手の順序を書いているときは、説明を採る**（例: 「次に着手する（05 より先）」）。主題の外から
入れたときは、そのマイルストーンの説明へ課題の番号を足す。主題が複数に当てはまるときは
**要判断**へ倒す。

## 親 issue を割り当てる

**親 issue の重要度は、クラスタの中で最も高いものを採る**（[grouping.md](grouping.md)）。
そのうえで、上の表を先に効かせる。

- **重要度が「高い」ときは、上の表のとおり直近のマイルストーンへ入れる。** 主題によらない
- **主題で決まるときだけ、子 issue が既に属するマイルストーンのうち最も早いものを採る。**
  原因を直すまでクラスタのどの課題も直らないため、遅い側に合わせると早いマイルストーンの
  課題が待つ。クラスタは 1 つの原因で括られており、主題が複数に当てはまっても**要判断**へ
  倒さない
- どの子 issue もマイルストーンを持たないときは、上の表で決まる

**子 issue のマイルストーンは動かさない。** 振り直しは重要度と位置の食い違いで決まり、
次の「既に設定されているものを振り直す」がその判断を持つ。クラスタへ属したことは重要度を
変えないため、振り直しの理由にならない。

## 既に設定されているものを振り直す

**重要度とマイルストーンの位置が食い違っていれば振り直す。** 重要度は棚卸のたびに見直される
ため、設定した時点と現在で食い違う。

| 状況 | 対応 |
| --- | --- |
| 重要度が高いのに、直近でないマイルストーンにある | **直近へ移す** |
| 重要度が低いのに、直近のマイルストーンにある | **要判断。** 後ろへ移すと着手が遅れる |
| 重要度と位置が合っている | 何もしない |

**早める方向だけを自動で反映する。** 早める判断は実害の記述が根拠になる。遅らせる判断は
「今やらなくてよい」という価値の判断であり、それは「やらない」の 2 つの必要条件で決める
（[no-work.md](no-work.md)）。後ろへ動かして着手を先送りする形は、判断の根拠を残さない。

## 新しく作るとき

**末尾に置く。** 既存のマイルストーンの順序を動かさないため、連番は現在の最大の次にする。
既存の間へ差し込むことは、他の課題の着手の順序を早めるか遅らせるかの判断にあたるため、
**要判断**へ倒す。

| 決めること | 決め方 |
| --- | --- |
| 名前 | `<2 桁の連番> <主題>`。連番はこれまでに付けた最大の次（`14` があれば `15`）で、再利用しない。閉じたマイルストーンは版数へ改名されるため、名前ではなく説明の「着手の順序: N 番目」から読む |
| 説明 | **残った課題から導く。** 既存の説明と同じ形にし、主題と対象の課題番号を書く |
| 入れる課題 | その主題を持つものだけ。残りは未設定のまま残す |

**1 件しか残らないときは作らない。** マイルストーンは複数の課題の着手の時期を揃えるもので、
1 件のために作ると、その意味を持たない。未設定のまま残し、次の棚卸で他の課題と合わさるのを
待つ。

## 並列の組を説明へ書く

**課題をマイルストーンへ入れるときに、その課題の組を説明へ書く。** 組は、触る場所の見込みと
依存でまとめた課題の集まりで、実行計画（`issue-plan-strategy`）が**束の初期値**として読む。
書かないと、複数の課題を渡された進行側が、何本を並列にできるかを本文から読み直すことになる。

**組の間は並列にできる見込み、組の中は同じ Pull Request へ束ねるか順に進める見込みである。**
触る場所が違えば作業ツリーを分けて同時に進められ、同じなら競合の解消がレビューの後に来る。

**見込みであり、確定は設計の後に実行計画が持つ。** どのファイルのどの節を触るかは設計が
出た後にしか決まらない。確定した値を説明へ**書き戻さない**。書き戻すと 2 か所が同じ事実を持つ。

### 置き場所

**説明の末尾に、見出し行と表を置く。** 説明はマークダウンとして描画されるため、見出しは
`### 並列の組（見込み）` にする。**既存の説明の文は変えない。**

```markdown
### 並列の組（見込み）

| 組 | 課題 | 触る場所の見込み | 依存 |
| --- | --- | --- | --- |
| 1 | #561 #623 | `merged` / `release` | なし |
| 2 | #540 #541 #621 | `development-workflow/references/parallel-work.md` / `issue-plan-strategy` | なし |
| 3 | #550 #657 | `development-workflow`（工程の窓） / `skill-stats` | 1（#561 の後） |
```

### 列の値

**段 2A が既に控えているものから写す。新しく調べる項目を増やさない。**

| 列 | 値 | 写す元 |
| --- | --- | --- |
| 組 | 1 から始まる連番。説明の中で一意 | — |
| 課題 | 同じ修正レイヤーを持つ課題の番号 | 段 2A の「修正レイヤー」 |
| 触る場所の見込み | 修正レイヤーの名前。Skill の名前・スクリプトのパス・文書のパスのいずれか | 同上 |
| 依存 | `なし`、または組の番号（括弧で課題の番号） | 段 2A の「依存する課題の番号」 |

**同じ修正レイヤーの課題は同じ組、違えば別の組にする。**

### 書く時点

| 時点 | 行うこと |
| --- | --- |
| 課題をマイルストーンへ入れる（新しく作る・既存へ足す・直近へ移す） | その課題の修正レイヤーが既存の組と同じなら、その組の「課題」へ番号を足す。違えば組を 1 つ足す。**表が無ければ見出しと表を作る** |
| 課題を別のマイルストーンへ移す | 元の説明の表から番号を消す。課題が 0 件になった組は行を消し、**組の番号は詰めない** |
| 課題が閉じた | 何もしない。実行計画が状態を持つ |

**組の表が無い既存のマイルストーンを、一括で書き直さない。** 課題を足す時点で、その課題の
行だけを持つ表を作る。段 2A が控えるのは棚卸の対象の課題だけで、マイルストーンの残りの課題の
修正レイヤーは控えに無い。表に無い課題は、実行計画を作る進行側が本文から読む。

**組はマイルストーンの中の単位である。** 組のために**既存のマイルストーンを分けたり
束ね直したりしない**。名前・連番・着手の順序の規則（上の節）は変わらない。

## 順序を直すとき

**依存の記述が連番の順序と食い違うときだけ直す。** 説明が「A の後に着手する」と書いているのに
A が後の連番にあるなら、どちらかが古い。**依存の記述が無いものの順序は変えない。** 早く出したい
という判断が入るため、返す。

## 報告へ残す

**未設定の件数と理由を残す。** 残った件数と理由（主題が合わず重要度も低い / 1 件しか残らない /
複数に当てはまる）が、次の棚卸の材料になる。
