# コードスメル

スメルは「直すべき欠陥」ではなく **調べる価値がある兆候** である。見つけても、変更の
理由（機能追加・不具合修正・読みにくさ）が伴っていなければ手を付けない。

行数などの数値規則は使わない。判断は凝集度・結合度・変更理由・認知負荷・テスト容易性で行う。

## 一覧

| スメル | 兆候 | 何が問題か | 主な手法 |
| --- | --- | --- | --- |
| 長すぎるメソッド | 1 つの関数が複数の段階（取得・判定・整形・保存）を通しで行う | 部分だけをテストできない。名前が実態を表せない | メソッドの抽出 |
| 肥大したクラス | 1 つのクラスが無関係な関心を複数持つ | 変更理由が複数あり、片方の修正が他方を壊す | クラスの分割、責務の移動 |
| 重複 | 同じ判断・計算が複数箇所にある | 片方だけ直され、挙動が食い違う | 共通化。ただし**偶然の一致は共通化しない** |
| 長い引数リスト | 引数が多く、呼び出し側で順序を間違える | 呼び出しの意味が読めない。追加のたびに全呼び出しを直す | 引数オブジェクトの導入 |
| 他クラスへの過度な関心 | 他のオブジェクトの内部を取り出して判断する | 相手の内部構造に結合する | 処理を持ち主側へ移す |
| 基本型への固執 | ID・金額・単位を文字列や数値のまま扱う | 取り違えを型で防げない。検証が散る | 値オブジェクトの導入 |
| マジックナンバー・文字列 | 意味のある値が直接書かれている | 意味が読めない。変更漏れが起きる | 名前付き定数、列挙 |
| 深いネスト | 条件の入れ子が続き、正常系が末尾に埋もれる | 読む負荷が高く、分岐の抜けに気づけない | 早期リターン、条件の反転 |
| デッドコード | 呼ばれない関数、到達しない分岐、使われない設定 | 読み手が現役だと誤解する | 削除（履歴に残る） |
| 過度な相互依存 | 双方向に参照し合う、循環する依存 | 部分だけを取り出せない。初期化順に依存する | 依存の向きを一方向に整える |
| 一貫しない命名 | 同じ概念に複数の呼び名がある | 検索できない。別物だと誤解する | 用語を 1 つに統一して改名 |
| 例外の飲み込み | 捕まえて何もしない、ログだけ出して続行する | 失敗が沈黙し、原因が追えない | 呼び出し元へ伝える、または明示的に扱う |
| 条件分岐の連鎖 | 型・状態ごとの分岐が複数箇所で繰り返される | 種類を増やすたびに全箇所を直す | 多態による置き換え |
| 設定の散在 | 同じ設定値が複数の場所で定義される | どちらが効くか分からない | 定義を 1 箇所へ寄せる |

## 共通化してよい重複の見分け方

重複を見つけても、**同じ理由で変わるか**を確認する。

| 状況 | 判断 |
| --- | --- |
| 同じ業務ルールに由来し、変わるときは必ず一緒に変わる | 共通化する |
| 今は同じ形だが、変更理由が別（別の画面・別の業務） | 共通化しない。別々に置く |
| 3 箇所目が出てきた時点でまだ同型 | 共通化を検討する |

早すぎる共通化は、後から片方だけ変えたいときに分岐（フラグ引数）を生む。フラグ引数が
増えたら、共通化が誤りだった兆候である。

## 抽象化を足す前の確認

差異が 1 つしかない時点で、戦略の切り出し・生成の仕組み・拡張点を導入しない。

```text
確認する問い
- いま解決したい具体的な問題は何か
- 差異は実際に何種類あるか（1 種類なら分岐で足りる）
- 抽象化しない単純案と比べて何が良くなるか
- 増える間接参照を将来の読み手が追えるか
- 不要になったとき、どうやって外すか
```

答えが出ないものは入れない。判断の記録が必要な場合の書式は `object-design`（Release 2）で
扱う。

## スメルに手を付けない場合

- 変更予定のない領域（読みにくいだけで、今回の変更に関係しない）
- 生成物・外部から取り込んだコード（上流で直す）
- 削除予定の領域

手を付けないと決めた場合、指摘だけを残すよりも**何もしない**方がよい。残す価値がある
指摘は、後続の作業として記録する。
