# 脆いテストと、その代替

テストが落ちる原因は 2 つしかない。**仕様が破れた**か、**テストが実装に結合している**か。
後者は退行を検出しないうえ、変更のたびに直す手間だけが増える。

## 判定の基準

> 振る舞いを変えずに実装を書き換えたとき、そのテストは落ちるか。

落ちるなら、そのテストは実装詳細に結合している。

## よくある例と代替

### 1. 内部メソッドの呼び出し回数を検証する

```python
# ❌ 実装の呼び出し手順に結合している
service.save(order)
assert repo.save.call_count == 1
```

```python
# ✅ 結果を検証する
service.save(order)
assert repo.find(order.id).status == "confirmed"
```

呼び出し回数の検証が正しいのは、**回数自体が仕様**のとき（外部への課金 API を二重に
呼ばない、通知を 1 回だけ送る）に限る。

### 2. private な関数を直接呼ぶ

公開された入口から呼べない経路をテストすると、内部構造を変えるたびに落ちる。公開
インタフェース経由でその分岐に入る入力を探す。入口から到達できない分岐は、そもそも
不要な可能性がある。

### 3. 表示文字列に完全一致を要求する

```javascript
// ❌ 文言の微修正で落ちる
expect(msg).toBe("数量は 1 以上を入力してください。");
```

```javascript
// ✅ 判定に必要な部分だけを見る
expect(res.status).toBe(400);
expect(res.body.code).toBe("quantity_out_of_range");
```

文言そのものが仕様の場合（法的表記・利用者向け通知）は完全一致でよい。その場合は
文言の出典（仕様書・翻訳ファイル）をテストのそばに書く。

### 4. 現在時刻・乱数・実行順に依存する

| 依存 | 対処 |
| --- | --- |
| 現在時刻 | 時刻を引数または注入可能な依存にし、テストで固定する |
| 乱数・ID 生成 | 生成器を注入する。または生成値ではなく性質（一意である等）を検証する |
| 実行順・並び順 | 順序が仕様なら明示して検証する。仕様でないなら集合として比較する |
| 実行環境（時間帯・ロケール・OS） | テスト内で明示的に設定する |

これらは flaky（同じコードで通る／落ちるが変わる）テストの主要因である。1 度でも
再現性なく落ちたテストは、原因を特定してから残す。「たまに落ちるので再実行する」運用に
すると、本物の退行を見逃す。

### 5. スリープで待つ

```text
❌ sleep(2) してから結果を見る   → 遅く、環境が変わると落ちる
✅ 条件が満たされるまで待つ（明示的な待機・ポーリング上限つき）
✅ 非同期処理を同期的に実行できる入口を用意する
```

### 6. 1 つのテストで多くを検証する

失敗時にどの検証が落ちたのか読み取れない。テストは 1 つの振る舞いに絞り、名前で何を
検証しているかが分かるようにする。

```text
❌ test_order_flow
✅ test_confirm_sets_status_to_confirmed
✅ test_confirm_rejects_when_stock_is_insufficient
```

### 7. テストを通すために本番コードへ分岐を足す

```python
# ❌ テスト用の抜け道
if os.getenv("TESTING"):
    return True
```

テスト時だけ通る経路は、本番で検証されない経路を作る。依存を注入可能にするか、設定として
明示的に扱う。

## カバレッジの扱い

カバレッジは「テストが実行した行の割合」であって、正しさの指標ではない。数値を上げる
目的でテストを足さない。

閾値は Skill 側に持たず、対象プロジェクトのカバレッジツール設定に従う（判定手順は
`quality-gates`）。設定がないプロジェクトでは、測定値を記録するだけにとどめる。

## 削除してよいテスト

- 仕様が変わり、検証対象の振る舞いがなくなった（削除して、削除理由を差分に残す）
- 同じ入力・同じ検証の重複
- 実装詳細に結合しており、振る舞いを検証していない（上記の例に該当するもの）

**落ちるから削除する**のは禁止。落ちた原因を先に説明する。
