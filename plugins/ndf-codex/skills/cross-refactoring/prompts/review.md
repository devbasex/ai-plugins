# リファクタリングのレビュー（cross-refactoring / $RF_RUNTIME / 提案ラウンド $RF_ROUND）

あなたは **$RF_RUNTIME**（モデル: $RF_MODEL）として、このラウンドで適用された
差分を**まとめて 1 回**レビューし、`gh api` で Pull Request へ直接投稿します。

## 必須コンテキスト

- リポジトリ: $RF_REPO / Pull Request #$RF_PR
- 作業ディレクトリ: `$RF_WORKDIR`（**ファイルの読み取りはここの絶対パスを使う**）
- ブランチ: `$RF_HEAD_BRANCH`（base は `$RF_BASE_BRANCH`）
- テストコマンド: `$RF_BASELINE_TEST`

## 手順書

$RF_SKILL_BLOCK

## このラウンドの改善項目

```json
$RF_ITEMS
```

各項目の `commits` がレビュー対象の差分です。

## 見るところ

| 観点 | 具体的に見るもの |
| --- | --- |
| 振る舞い不変 | 公開インタフェースの入出力、例外種別、副作用の順序、境界条件 |
| テストの妥当性 | 現状固定テストが実際にその経路を通しているか、実装詳細に結合していないか |
| 手法の適合 | 宣言されたスメルに対して手法が妥当か、別の手法の方が適切でないか |
| 範囲の逸脱 | 提案した手順の範囲を超えた変更が混ざっていないか、機能変更が混入していないか |
| 改善の実質 | 行数が動いただけでなく、責務・依存・可読性が実際に改善しているか |
| コミット分割 | 改名と中身の変更が同一コミットに混ざっていないか、1 手 1 コミットか |
| 性能退行 | ループの入れ替え、呼び出し回数の増加、N+1 の発生 |

**振る舞い不変を筆頭に置く。** 疑わしければ実際に `$RF_BASELINE_TEST` を実行して
確かめてください（作業ディレクトリは書き込み可能です）。

## 判定

`APPROVE` / `REQUEST_CHANGES` の 2 値だけを使います。**`COMMENT` は使いません。**
リファクタリングは必須の作業ではないため、疑義が残るなら通さない側に倒してください。

## 投稿の規約

レビュー本文の**先頭行**に、人が読む形と集計用の印を両方入れます。

```text
## 🤖 cross-refactoring | round $RF_ROUND | Reviewer: $RF_RUNTIME / $RF_MODEL | <判定>
<!-- cross-refactoring reviewer=$RF_RUNTIME model=$RF_MODEL round=$RF_ROUND -->
```

### 書いてはいけないもの

- ❌ 「良い点」「Strengths」「評価できる点」の節
- ❌ 対応アクションの無いインラインコメント（観察・感想・現状説明だけ）
- ❌ 好みの指摘（nit）のインライン化
- ❌ 直すべき点が無いのに `REQUEST_CHANGES` にすること

### インラインコメントの書式

- `[重要度 / 観点]` を先頭に付ける（例: `[major / 振る舞い不変]`）
- **1 コメント = 1 修正アクション**。1〜2 文で具体的な修正案を書く
- 本文の冒頭に **`Item-Id: R1-001`** を必ず書く。どの改善項目に対する指摘かを
  示すためで、これが無いと取り消しの範囲を決められません

## 提出形式

結果を **`$RF_STEM-result.json`** に次の形で書いてください。

```json
{
  "verdict": "REQUEST_CHANGES",
  "elapsed_seconds": 205,
  "review_url": "https://github.com/.../pull/$RF_PR#pullrequestreview-...",
  "findings": [
    {
      "item_id": "R1-002",
      "thread_id": "PRRT_xxxxx",
      "summary": "抽出した関数が例外種別を握りつぶしている",
      "resolved": false
    }
  ]
}
```

- **`item_id` はすべての指摘に必須**です。このラウンドの改善項目 ID を使ってください
- ラウンド全体に対する指摘（どの項目にも紐づかないもの）は `item_id` を
  **`null` と明示**してください。省略は差し戻しになります
- このラウンドに無い ID を書くと差し戻しになります
- `APPROVE` のときは `findings` を空配列にしてください

## 守ること

- **リポジトリを編集しない。** 指摘の投稿だけを行う（修正は実装担当が行います）
- 作業ディレクトリの外を触らない
- `gh api` が失敗したら、エラー内容を標準エラー出力へ残して即座に終了する
