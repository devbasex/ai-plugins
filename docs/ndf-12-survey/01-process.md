## 0. 結論

1. **設計が無かったのではなく、設計が速すぎて薄く、決定の大半が実装の後に来た。** 作り直しの設計（PR #3280）は書き始めから承認まで約 50 分、PR を開いてから 17 分でマージされ、その 20 分後に実装が始まった。全 129 の決定のうち 49（38%）は最初の子 4 本が閉じた後に足され、実装後の設計レビューで 24 Issue・182 項目が出た。仮説 1 は「半分当たり」。
2. **ai-plugins の事情と製品 NDF の区別は、作り直しの前（11-12）から指摘され、決まりも作ったのに、11-15・11-16 に 2 回再発した。** リリースの設計 #3572 は 11 時間で設計 PR を 4 本出し、最新もまだ開いている。仮説 2 は当たり。
3. **外部の参照は「部品の選定」には十分あり、「進め方・全体の形」にはほとんど無い。** ライブラリの比較表は 29 行あり pypi で版まで確かめているが、AI 開発の方法論・競合ツールとの比較は #1142 の文書に 0 件。Spec Kit や arc42 を調べたのは作り直しの後の #3600（11-15）が最初。仮説 3 は「全体の形については当たり」。
4. **仮説に無い大きな問題が 3 つある。** (a) 直す対象が直している間に 3 倍に育った（Python 37,575 行 → 約 12 万行）。(b)「作り直しの間はほかの開発を止める」と決めたのに、止まらなかった（作り直しの開始後に `plugins/ndf/` へのマージ 42 本・本番リリース 10 回）。(c) 端から端まで通す確かめ（機能の対応表の試走）が最後に来て、1 回目は 204 行中 7 行しか通らなかった。
5. **範囲が何度も広がった。** 起点は「スクリプトの分割と重複の整理」で Skill 本文は範囲外だったが、AI の分岐をスクリプトへ（11-12）、AI が陥りやすい作りの撲滅・定数からデータへ・0 から作り直し・テストの作り直し（11-13）が足され、ラベル `rebuild-1142` の Issue は 377 本（開いている 85 本）になった。

## 6. 12.0 での変え方の案（推測を含む提案）

1. **要求の段階で「価値の判断」を先に問う。** 後方互換・同等の定義・ほかの開発を止めるか・ブランチ運用・テストの扱いは、今回すべて実装中に覆った。要求のテンプレートにこれらを必ず問う欄を置き、答えが無ければ設計へ進まない。
2. **全体の設計（アーキテクチャ設計書）を先に作り、実装前に承認する。** 入出力の規約・状態の置き場・エントリポイント・用語・宣言のスキーマ・同等性の物差しを先に固める（#3600 の形を 12.0 の最初のスプリントにする）。設計の承認に最低の滞在時間か人の読みの時間を置く。
3. **製品と ai-plugins を最初から分けて書く。** 要求と設計に「代表のリポジトリの種類ごとの振る舞い」の表を必須にし（#3618）、ai-plugins 以外の試す場（Web・モバイル・文書だけのサンプルリポジトリ）を最初に用意して CI で回す。ai-plugins の運用は `.ndf/` の値としてだけ書く。
4. **外部の比較を設計の最初に置く。** 部品だけでなく、全体の形（Spec Kit・SWE-agent 系・既存のワークフローエンジン、Strangler Fig と一括の入れ替えの比較）を要求か設計の冒頭で比べ、採らない理由を残す。
5. **Walking Skeleton を最初に作る。** 機能の対応表の試走を最後でなく最初のスプリントに置き、全行を「赤」から始めて毎スプリント通る数を測る。
6. **凍結を仕組みで守る。** 「ほかの開発を止める」と決めたら、`plugins/ndf/**` への PR を CI で止める（例外は緊急の不具合の直しだけで、行き先の Issue を必須に）。決めないなら、対象の成長を見込んだ計画にする。
7. **規模と収束の上限を工程に置く。** PR の大きさの上限、進まないループ（修正 0 が続く）の自動停止、傘の Issue の子の上限。
8. **振り返りを区切りごとに必ず残す。** 第 3 期のような短期の大きな作業ほど振り返りが落ちた。
