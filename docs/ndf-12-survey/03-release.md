# NDF のリリースと並列の運用: 記録の集計と 12.0 の作り方の材料

作成: 2026-11-16（JST）。読むだけで、編集・起票はしていない。時刻はすべて JST。
各節は **事実**（記録から数えたもの）と **推測**（数字からの解釈）に分けた。

中間データ（提示 1 回ごとの表・Release の PR 540 件・Issue 1,490 件・bug の分類）は調査の作業ファイルで、リポジトリには置かない。

## 0. 結論

1. **正式版 1 回のリリースに、提示が平均 1.7 回、Release の PR が約 3.8 本、人の答えが 1 回以上要る。** p4〜p6 では提示を 49 回組んで、正式版のタグは 28 本だった（ほかに 1 本が承認待ち）。
2. **承認した後にも 40% が詰まる。** p6 で承認したリリースは 15 回で、そのうち 6 回は承認の後に止まった。原因は、2 つ目の承認（main の PR のレビュー）・版数の衝突（`bump` exit 3）・リリースブランチの消失。うち 1 回（#3661）では、承認を取り直さないまま main へマージされた。
3. **不具合の主な原因は、同じ事実（版数・承認・依頼・問い）を複数の場所で持つことである。** 版数は develop・リリースブランチ・dev の接尾辞・定義ファイル 5 箇所・文書 5 箇所に分かれている。承認と問いは台帳・answer.json・answers-sent.json・DBOS・PR コメントに分かれている。食い違いの直しを 4 回以上繰り返した系統がある（§2）。
4. **運用の仕組みは大きい。** parallel・relay・release・supervise・merged のスクリプトだけで約 37,000 行・副命令 144 個ある。題の語で分けると、リリース・並列・リレー・承認・待ちの不具合は 167 件（bug ラベル 340 件の 49%）。そのうち 103 件が 11 月に起票された。
5. **12.0 では、リリースを「main への 1 本の Release PR のマージ」1 つにする。** 版数・CHANGELOG・タグ・承認の証跡・同時マージの順序は、CI・release-please 型の bot・GitHub の environment 承認・merge queue へ任せる。NDF の本体として残すのは、MVV 判定と承認資料の中身・Issue と版の対応・リリース後テストだけにする。

## 4. 外部の一般的なやり方との比較

| NDF が自前で持つもの | 一般的なやり方 | 任せられるか |
| --- | --- | --- |
| 版数を上げる（`bump`）・版の衝突の検査 | release-please / changesets / semantic-release が main の上で版を決める | **任せられる。** 版をブランチの上で決めない（マージの時点で 1 回だけ決める）と、#3551・#3598・exit 3 の系統が起きない |
| CHANGELOG と注記（`changelog`・`notes`） | release-please（Conventional Commits）か changesets（PR ごとの変更ファイル） | 任せられる。#1834（手で直した行を消す）・#1867 の系統が起きない |
| まとめたリリース（organizer が複数レーンを 1 本に） | release-please の Release PR はマージされた変更を自動で積み上げる | **任せられる。** 一時レーン 23 本・提示の組み直しが要らない |
| タグと GitHub Release | すでに CD（`release-cd.yml`）が作っている | 済み |
| 承認の証跡・承認ゲート 2・`--admin` | PR のレビュー必須、または GitHub の environment の required reviewers | 任せられる。承認を 1 箇所（GitHub）にすれば 2 つ目の承認が生まれない |
| 同時に承認したスプリントの組み合わせの確認 | merge queue | 任せられる（2026-11-16 の利用者の決定と一致） |
| 開発版（`-dev.N` の PR を develop へ） | trunk の HEAD を開発版のチャネルにする（2 つ目のマーケットプレイスの ref か prerelease タグ） | 任せられる。開発版の PR 72 本が要らない |
| CI の待ち・判定（merge-when-green） | `gh pr merge --auto` と必須チェック | 大部分は任せられる。#1645・#3656・#3594 の系統は GitHub の判定へ寄せると消える |

## 5. 12.0 のリリースと運用の作り方（最小の形の案）

**原則:** 状態は GitHub に 1 つだけ持つ。NDF は判定と提示を担い、版数・順序・証跡を自前で持たない。

1. **リリースは「Release PR を main へマージすること」の 1 つにする。** Release PR は release-please 型の bot（既製品か、200 行程度の同じ役割の CI ジョブ）が main の変更から積み上げる。版数・CHANGELOG・plugin.json の書き換えはこの PR の中で CI が行う。人の承認はこの PR のレビュー（または environment の承認）1 回だけ。承認ゲート 2 は「この PR の承認」と同じものになる。
2. **版数は 1 箇所に置く。** plugin.json の `version` だけを正本にし、description・marketplace.json・README の版数は生成するか書かない。版はマージの時点で決まるので、レーンもブランチも版数を持たない。
3. **開発版は trunk の HEAD にする。** 開発版のための PR とブランチを作らない。チャネルは ref（main の HEAD と、リリースタグ）の違いだけで表す。
4. **ブランチ運用は宣言の 2 行だけにする。** trunk（GitHub flow）と develop→main の 2 つ。どちらも「Release PR の宛先」と「開発版の ref」の 2 つの値で表す。ai-plugins は trunk を選ぶ（リポジトリの宣言の値であり、NDF の既定ではない）。
5. **同時マージは merge queue に任せる。** スプリントの PR は auto-merge＋merge queue で入れる。organizer は「まとめる」をやめ、問いに答えるだけにする。
6. **リリースの一時レーンと DBOS の再開を外す。** リリースは CI のジョブで、再実行は Actions の「Re-run」で足りる。手元の状態は GitHub から再構成できるキャッシュに限る（台帳・answers-sent・requests を作らない）。
7. **MVV 判定と承認資料は CI の check として Release PR に載せる。** 「検査の結果」は GitHub の checks API から直接読む（#2655 系の 4 回の再発の元は、写しを作ること）。
8. **問いと答えも GitHub に置く**（PR のレビューかコメント）。台帳を持たないので、ID の衝突（#3118・#3405）と送り直し（#3608）が起きない。

**推測（効果の見込み）:** 1 回のリリースは、提示 1 回・PR 1 本・人の操作 1 回（レビューの承認）になる。§2 の A・B・D 系統（約 100 件）の多くは、状態の写しをやめることで原因ごと消える。残る自前のコードは、MVV 判定・承認資料・Issue との対応・リリース後テストで、数千行の規模と見込む。

**12.0 で決めることが要る点:**

- 設計承認ゲート（49 件。人の答えの最大の源）をどうするか。この分析の範囲外
- 正式版と開発版の 2 チャネルを、ref の違いだけで足りるとするか

- `release` の Skill の本文（`plugins/ndf/skills/release/SKILL.md`）は読んでいない。worker の規則で、起動指示の「読む Skill」に挙がっていない `SKILL.md` は読まないため。行数だけ測った。
- 提示の時刻は `presented.json` の更新時刻、承認の時刻は `answer.json` の最後の `at` を使った。p6-17 では答えがタグより後に記録されており、`at` の意味（書いた時刻か答えた時刻か）は確かめていない。
- タグの時刻は `creatordate` を使った。p6-11（stop）と p6-22（stop）の後にタグが付いた経路は、#3661 以外は追っていない。
- Issue の分類は題の語による。誤分類がある（例: #392・#1661 はリリースの不具合ではない）。同じ原因の再発は題と本文の「再発」「移し」から拾った分だけで、網羅していない。
- p4 の台帳は 3 行で、それより前の一時レーンの数は数えられない。
- merge queue と environment の承認が devbasex の契約の範囲で使えるかは確かめていない。
- ndf-next（rebuild-1142、Issue 374 件）の `domains/release` が既に何を持つかは見ていない。
- 一時レーン 1 本あたりの token と費用は測っていない（`present.log` の LLM の使用量はどれも $0 で、Claude のセッション側の消費は記録に無い）。
