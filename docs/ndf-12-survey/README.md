## 結論

1. **11.0 の一番の問題は「見切りで始めた」より「速すぎて中身が薄く、途中で前提が覆り続けた」ことである。** 作り直しの設計 PR #3280 は作成から 17 分でマージされ、その 20 分後に実装が始まった。決定 129 件のうち 38% は、最初の子 4 本が閉じた後に足された
2. **ai-plugins と製品 NDF の混同は、決まりを作った後も 2 回再発した。** 文書の決まりでは止まらない。ai-plugins 以外のリポジトリで CI を回さない限り再発する
3. **運用の仕組みが本体より重くなった。** リリース・並列・リレー・承認は約 41,500 行・副命令 144 個で、bug 全体の 49% がここから出た。主な原因は、同じ事実を複数の場所に持つことである
4. **コードは、検査に載せた規約だけが揃った。** 層・純度・大きさは違反 0 件。検査の外の横断の部品は 2〜5 通りに割れた
5. **一番欠けているのは、工程の効き目を測る評価の仕組みである。** これが無いので、どの工程を残すかも、自作するかどうかも、感覚で決まってきた

## 仮説に無かった課題

- 工程の効き目を測る仕組みが無い（04 §4）
- 作り直しの間も対象が動き続けた。「ほかの開発を止める」と決めた後にも、マージ 42 本・本番リリース 10 回があった（01 §5.1・§5.2）
- 端から端までの確かめが最後に来た。機能の対応表の試走の 1 回目は 204 行中 7 行だけが通った（01 §5.5）
- 同じ事実を複数の場所に持つ。版数・承認・依頼・問い、定数とスキーマ、宣言だけの依存（02 §5・§6、03 §2.A）
- 承認が 1 回で済まない。承認の後に 40% が詰まった（03 §1.2）
- 大きすぎる PR と、空回りするループを止めない（01 §5.3・§5.4）
- 記録が当てにならない。傘の Issue が意図せず閉じ、作り直しの期間の振り返りが無い（01 §5.8・§5.9）

## 12.0 で加える観点

観点 V1〜V13 の一覧と、各観点の 12.0 での案は Issue #3668 にある。作り直す順は次のとおり。

1. **コードより前に作るもの:** 工程の効き目の評価の仕組み、最小の骨組み（Walking Skeleton）、製品の試し用リポジトリ（ai-plugins 以外）の CI
2. **要求:** 価値の判断（後方互換・同等の定義・開発の停止・ブランチ運用・テストの扱い）を必須の問いにする。全体の形を外部と比べる
3. **設計:** 外部の標準の形（arc42＋C4・MADR・Diátaxis・EARS）で書く。代表的なリポジトリの種類ごとの振る舞いの表を必須にする
4. **コードの規約:** 文書 1 本に書き、規則ごとに検査を対応させる
5. **進め方:** trunk-based を既定にし、PR の大きさと空回りのループに上限を置き、区切りごとに振り返る
6. **リリース:** Release PR 1 本・版数 1 か所・承認 1 回・merge queue。ほぼ既製品に任せる
7. **自作は強みだけ:** モードの判定・承認の代行・複数 AI の収束レビュー・並列・耐久実行。評価で効き目が示せたものに限る
