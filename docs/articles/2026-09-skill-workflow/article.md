# 人間がやってた開発フローを全部Skill化した

こんにちは。ナイルの大浜です。

いきなり結論です。

**要件定義から設計、実装、レビュー、リリース、振り返りまで、人間がやっていた開発フローを全部 Skill にしました。**

Claude Code で `/goal /ndf:development-workflow` と打つと、AI がその流れを最後まで通します。人間が中身を見るのは、ほぼ「企画承認」の 1 か所だけです。

今回はこの仕組みの紹介と、1 か月ほど回してみて気づいたことを書きます。

## 前回のおさらい

前回の記事「[AIエージェントは何行に1つ、バグを生むのか？](https://note.com/nyle_engineer/n/nbc43fa926104)」で、社内で作っている Claude Code 向けプラグイン集 ai-plugins と、複数の AI にレビューを回させる cross-review を紹介しました。

ざっくり言うと「AI が書いたコードを、別の AI たちに指摘が出なくなるまでレビューさせる」仕組みです。

今回はその外側、**開発フロー全体**の話です。

## /goal /ndf:development-workflow って何？

コマンドは 2 つの部品でできています。

- `/goal` は Claude Code のコマンドです。「この条件を満たすまで止まらないで」と頼めます
- `/ndf:development-workflow` は ai-plugins の NDF プラグインに入っている Skill です。変更の中身を見て、どの工程を通すかを決めます

NDF の Skill は全部で 45 個あります。development-workflow はそれらを工程の順に並べる、いわば進行役です。

変更の種類は 5 つのモードに分けています。全部の変更にフルコースを課すと、誤字の修正にも設計書が要ることになるからです。

| モード | どんな変更か | ざっくりした流れ |
| --- | --- | --- |
| operation | コードは触らず、外部サービスの設定やデータだけを変える | 本番に届く操作は、実行の前に人間が承認 |
| documentation | 人に渡す文書を書く | この記事がこれ |
| standard | 機能の追加やバグ修正 | フルコース |
| legacy-refactor | テストの無いコードの構造を直す | 先に今の動きを固定するテスト |
| light | 文言・コメント・テストの追加など | レビューだけは必ず通す |

判定も AI がやります。実際に触るファイルを見て、上から順に当てはまるモードを選びます。

## いつもの開発フローを、そのまま Skill にした

standard モードの流れはこうです。

```text
要求と受け入れ条件   requirements-design
  ↓
設計               design
  ↓
設計レビュー         pr → cross-review → 【企画承認】→ マージ
  ↓
実装計画            implementation-plan
  ↓
テストを先に書く実装  tdd-cycle
  ↓
構造改善            cross-refactoring
  ↓
実装レビュー         cross-review
  ↓
完了判定 → PR → マージ  quality-gates / pr / merged
  ↓
リリース            release（本番は【承認】）
  ↓
リリース後テスト      release-verification
  ↓
振り返り            retrospective
```

見てのとおり、特別なことは何もしていません。チームで普通にやっている流れを、工程ごとに Skill にしただけです。

ポイントは、**どの工程にも担当の Skill がいる**ことです。AI は「次に何をするか」を毎回考えなくていいし、人間も「あの手順、今回は飛ばしてない？」と心配しなくていい。

いくつか補足します。

- 構造改善の `cross-refactoring` は、複数の AI に「ここ直したほうがいい」を提案させ、別の AI が適用し、残りがレビューします。新しい提案が出なくなるまで回します
- 実装レビューの `cross-review` は前回の記事で紹介したものです
- 人間の承認で止まるのは「設計 PR のマージ」と「本番へのリリース」の **2 か所だけ**です

工程の外で動いている Skill も 3 つあります。

- `out-of-scope`：作業中に見つけた「今回の範囲外の問題」を、その場で issue にする
- `retrospective`：リリースした後に、進め方そのものを見直す
- `issue-upkeep`：溜まった issue を棚卸しして、ずれを直したり「やらない」と決めて閉じたりする

この 3 つが、後で書く「気づいたこと」に効いてきます。

## ドキュメントも同じ流れで書ける

documentation モードは、提案資料や報告書、マニュアルなど、人に渡す文書を作るモードです。

骨格は standard とほぼ同じです。違うのは次のところです。

- 設計のあとに「数字や引用の出どころを押さえる」工程が入る
- テストを先に書く実装の代わりに、執筆の工程が入る
- 構造改善は通らない
- リリースのあとに「実際に描画して、見た目を確かめる」工程が入る

企画承認にあたるのは、構成案を載せた設計 PR のマージです。

で、実はこの記事もこのモードで書いています。

AI が構成案を作って設計 PR を出し、2 つの AI が 3 ラウンドほどレビューしました。「周辺 Skill として紹介すると言っていた cross-refactoring が、構成案のどこにも出てこない」なんて指摘もちゃんと出ています。

そのうえで私のところに企画承認が回ってきて、「構成がちょっと堅い。もう少しライトに」と差し戻しました。今読んでいるのは、その 2 回目の構成案から書かれた版です。

## ai-plugins 自体もこのやり方で育てている

ai-plugins の開発そのものも、`/goal /ndf:development-workflow` で回しています。

development-workflow を入れたのが 8 月中旬。そこから約 1 か月でマージした PR は 273 本、NDF の版は 6.1.0 から 10.12.0 まで進みました。

面白いのは、**Skill の不具合が Skill を使っている最中に見つかる**ことです。

レビューの手順に穴があれば、レビューを回している最中に AI が気づいて issue にする。その issue も同じ工程で直す。直した Skill で次の開発を回す。自分の尻尾を食べながら太っていく感じです。

## やってみて気づいたこと

1 か月ほど回してみて、気づいたことが 4 つあります。

### AIに任せるなら、結局ウォーターフォール + TDD が安心

意外だったのがこれです。

人間同士の開発なら、作りながら決めていくアジャイルな進め方のほうが合う場面は多いと思います。

でも AI に任せると、**決めていないことを AI が勝手に決めてきます**。しかも、それっぽく。

先に受け入れ条件と設計を固めて、テストを先に書かせる。そうすると AI の出力は「条件を満たしたか」「テストが通ったか」だけで判定できます。手戻りがあっても、どこで食い違ったかがすぐ分かる。

古き良きウォーターフォールと TDD の組み合わせが、AI 相手だと一番安心感がありました。

### 人間が見るのは、ほぼ企画承認だけ

承認の関門は、あえて 2 つだけにしています。

関門を増やすと、人間はだんだん読まずに通すようになります。承認のボタンを押す回数が増えるほど、1 回あたりの重みが減るんですよね。

2 つのうち、中身をしっかり読むのは設計 PR のマージ、つまり企画承認です。この記事の前までに承認した設計 PR は 28 本ありました。

ここさえ押さえておけば、あとは AI 同士のレビューとテストがかなり拾ってくれます。逆に、ここで方向を間違えると、その後の工程が全部きれいに間違った方向へ進みます。

この記事の差し戻しも、まさにその関門で起きました。

### 振り返りと issue の棚卸しが効く

フローを回し続けると、2 種類のずれが溜まっていきます。

- 進め方のずれ：同じところで毎回つまずいている
- issue のずれ：issue に書かれた内容が、もう現状と合っていない

前者を直すのが振り返り（retrospective）、後者を直すのが棚卸し（issue-upkeep）です。

棚卸しの Skill を作ったとき、open だった issue 43 件を 1 件ずつ実物と突き合わせてみたら、**24 件の本文が現状とずれていました**。半分以上です。

ずれた issue を AI に渡すと、AI はずれたまま真面目に作業します。人間なら「これ、もう直ってない？」と気づくところです。

### out-of-scope で issue が増えまくるので、刈り込む

out-of-scope は「迷ったら起票する」ルールにしています。後で閉じるほうが、拾い直すより安いからです。

その結果どうなったか。8 月末からの 2 週間ちょっとで起票された issue 264 件のうち、**127 件が範囲外の起票**でした。約半分です。

AI は真面目なので、見つけたものは全部 issue にします。入口を広くした分、出口が要ります。

そこで、棚卸しの Skill に「やらない」と決めて閉じる判断を持たせました。直す価値より抱えておくコストのほうが高いものは、「こうなったらまた考える」という条件を付けて閉じます。

**人間の仕事は、作ることから刈り込むことへ寄ってきた**実感があります。

## まとめ

人間がやっていた開発フローを全部 Skill にして、`/goal /ndf:development-workflow` の 1 行で AI に通させています。

やってみて分かったのは、AI に任せるほど「先に決める」ことと「後で刈り込む」ことが大事になる、ということでした。

- 先に決める：受け入れ条件と設計を固め、企画承認で方向を確かめる
- 後で刈り込む：振り返りで進め方を直し、棚卸しで issue を減らす

全部 Skill 化しても、人間が要らなくなるわけではありません。人間の仕事が「作る」から「決める・刈り込む」へ移っただけです。
