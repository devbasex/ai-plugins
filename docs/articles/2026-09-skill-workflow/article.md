# 人間がやってた開発フローを全部Skill化した

こんにちは。ナイルの大浜です。

AI エージェントを使った開発にも、そろそろ疲れが見えてきた頃ではないでしょうか。

先日、Anthropic の CEO が AI の能力向上のペースを落とすべきだと業界に呼びかけました。同社の研究者が AI 開発への懸念から抗議の退社をしたことも報じられています。

このテックブログでも「[AIを使っているか、AIに使われているか](https://note.com/nyle_engineer/n/ncb7b1a08fb55)」という記事が出ました。10 分で終わるはずの修正が、AI のレビュー指摘に応え続けるうちに 1 時間を超えてしまった、という話が出てきます。

身に覚えのある方も多いのではないかと思います。

とはいえ、技術というものは、一度世に出てしまえば、それを使わなかった世界には戻れません。

表計算ソフトが普及した後、経理の現場が手作業の検算へ戻らなかったのと同じです。

AI エージェントも「使うかどうか」ではなく「どう付き合うか」に移っていくはずです。

## では、まさにどう付き合えばよいのか

開発プロセスとは、突き詰めれば「間違える実行者のために、人間が積み上げてきた工夫の集まり」です。

要件定義書を書くのは、口頭の合意がすぐに忘れられるからです。コードレビューをするのは、書いた本人が自分の誤りに気づけないからです。テストを先に書くのは、「動いたつもり」を信用しないためです。どの工程も、実行する人間が間違えるという前提の上に立っています。

では、AI エージェントはどうでしょうか。

[以前の記事](https://note.com/nyle_engineer/n/nee2f820d54fd)でも書いたとおり、AI はよく指示を忘れます。加えて、決めていないことをそれらしく決めてしまうこともあります。しかも人間よりはるかに速く、大量に。

つまり AI もまた、間違える実行者です。

だとすれば、AI に開発を任せるときに必要なのは新しい魔法ではなく、人間が長い時間をかけて作ってきた、あの地味で退屈な手順のほうではないか。

そう考えて、要件定義から設計、実装、レビュー、リリース、振り返りまで、人間がやっていた開発フローを全部 Skill にしました。Claude Code で `/goal /ndf:development-workflow` と打つと、AI がその流れを最後まで通します。人間が中身を見るのは、ほぼ「企画承認」の 1 か所だけです。

この稿では、その仕組みと、1 か月ほど運用してみて気づいたことを書いてみます。

## /goal /ndf:development-workflow とは

このコマンドは 2 つの部品でできています。

- `/goal` は Claude Code のコマンドで、「この条件を満たすまで作業を止めない」ことを指示できます
- `/ndf:development-workflow` は ai-plugins（社内で開発している Claude Code 向けのプラグイン集）の NDF プラグインに含まれる Skill で、変更の中身を見て、どの工程を通すかを決めます

NDF には全部で 45 個の Skill があり、development-workflow はそれらを工程の順に呼び出す進行役にあたります。

変更の種類は 5 つのモードに分けています。すべての変更にフルコースの工程を課すと、誤字を 1 つ直すためにも設計書が必要になってしまうからです。

| モード | どんな変更か | 流れの特徴 |
| --- | --- | --- |
| operation | コードは触らず、外部サービスの設定やデータだけを変える | 本番に届く操作は、実行の前に人間が承認する |
| documentation | 人に渡す文書を書く | 本稿もこのモードで書いている |
| standard | 機能の追加やバグ修正 | すべての工程を通す |
| legacy-refactor | テストの無いコードの構造を直す | 先に現在の動きを固定するテストを書く |
| light | 文言・コメント・テストの追加など | レビューだけは必ず通す |

どのモードに当たるかも AI が判定します。実際に触るファイルを見て、上から順に当てはまるものを選ぶ仕組みです。

## いつもの開発フローを、そのまま Skill にした

standard モードの流れは次のとおりです。

```text
要求と受け入れ条件   requirements-design
  ↓
設計               design
  ↓
設計レビュー         pr → cross-review → 【企画承認】→ マージ
  ↓
実装計画            implementation-plan
  ↓
テストを先に書く実装  tdd-cycle
  ↓
構造改善            cross-refactoring
  ↓
実装レビュー         cross-review
  ↓
完了判定 → PR → マージ  quality-gates / pr / merged
  ↓
リリース            release（本番は【承認】）
  ↓
リリース後テスト      release-verification
  ↓
振り返り            retrospective
```

見てのとおり、目新しいことは何もしていません。チームで当たり前に行ってきた流れを、工程ごとに Skill として書き起こしただけです。

重要なのは、**どの工程にも担当の Skill がいる**ことです。AI は次に何をすべきかをその都度考える必要がなく、人間の側も「今回はあの確認を飛ばしていないか」と心配する必要がなくなります。

いくつか補足しておきます。

- 構造改善の `cross-refactoring` は、複数の AI に改善案を出させ、別の AI が適用し、残りの AI がレビューします。新しい提案が出なくなるまでこれを繰り返します
- 実装レビューの `cross-review` は、AI が書いたコードを別の AI たちに指摘が出なくなるまでレビューさせる仕組みで、[前回の記事](https://note.com/nyle_engineer/n/nbc43fa926104)で紹介しました
- 人間の承認で止まるのは、「設計 PR のマージ」と「本番へのリリース」の **2 か所だけ**です

流れの最後にある振り返り（`retrospective`）は、リリースの後に進め方そのものを見直す工程です。

これとは別に、工程の外で動いている Skill が 2 つあります。

- `out-of-scope`：作業中に見つけた「今回の範囲外の問題」を、その場で issue にする
- `issue-upkeep`：溜まった issue を棚卸しし、現状とのずれを直したり、「やらない」と決めて閉じたりする

振り返りとこの 2 つが、後で述べる気づきに深く関わってきます。

## ドキュメントも同じ流れで書ける

documentation モードは、提案資料や報告書、マニュアルといった、人に渡す文書を作るためのモードです。

骨格は standard とほぼ同じで、違いは次のとおりです。

- 設計の後に、数字や引用の出どころを確定させる工程が入る
- テストを先に書く実装の代わりに、執筆の工程が入る
- 構造改善の工程は通らない
- リリースの後に、実際に描画して見た目を確かめる工程が入る

ここでの企画承認は、構成案を載せた設計 PR のマージにあたります。

実のところ、本稿もこのモードで書いています。

AI が構成案を作って設計 PR を出し、2 つの AI が 3 ラウンドにわたってレビューしました。「周辺の Skill として紹介すると書いた cross-refactoring が、構成案のどこにも出てこない」といった指摘も、この段階で出ています。

そのうえで企画承認に回ってきた構成案は、堅すぎたため差し戻されました。いまお読みいただいているのは、その後に作り直した構成案から書かれたものです。

## ai-plugins 自体もこのやり方で育てている

ai-plugins の開発そのものも、`/goal /ndf:development-workflow` で回しています。

development-workflow を導入したのが 8 月中旬で、そこから約 1 か月の間にマージした PR は 273 本、NDF の版は 6.1.0 から 10.12.0 まで進みました。

興味深いのは、**Skill の不具合が、その Skill を使っている最中に見つかる**ことです。

レビューの手順に穴があれば、レビューを回している最中に AI がそれに気づき、issue として起票します。その issue も同じ工程で直され、直った Skill で次の開発が回ります。道具が、自分自身を使って自分を改良していく構図になっています。

## やってみて気づいたこと

1 か月ほど運用してみて、気づいたことが 5 つあります。

### AIに任せるなら、ウォーターフォール + TDD が一番安心できる

人間同士の開発であれば、作りながら決めていくアジャイルな進め方のほうが合う場面は多いと思います。

ところが AI に任せると、**決めていないことを AI が勝手に、それらしく決めてしまいます**。

先に受け入れ条件と設計を固め、テストを先に書かせる。そうすれば AI の出力は、「条件を満たしたか」「テストが通ったか」だけで判定できます。手戻りが起きても、どこで食い違ったのかがすぐに分かります。

古くからあるウォーターフォールと TDD の組み合わせが、AI を相手にしたときに最も安心感のある進め方でした。冒頭の「間違える実行者のための工夫」という話は、ここに行き着きます。

### 人間が見るのは、ほぼ企画承認だけ

承認の関門は、あえて 2 つに絞っています。

関門を増やすと、人間は次第に中身を読まずに通すようになります。承認の回数が増えるほど、1 回ごとの重みが薄れていくためです。

2 つのうち、中身をしっかり読むのは設計 PR のマージ、つまり企画承認です。

ここさえ押さえておけば、その先は AI 同士のレビューとテストがかなりの部分を拾ってくれます。逆に、ここで方向を誤ると、その後の工程はすべて、きれいに誤った方向へ進んでいきます。

### worktree とマイルストーンで、並列開発が回る

効果が大きかったのが、並列開発です。

開発の変更は、`worktree` Skill が用意する作業ツリー（`.worktrees/<ブランチ名>`）の中で行います。作業ディレクトリが PR ごとに分かれているので、複数の AI が同時に別の課題を進めても、互いの変更が混ざりません。

そのうえで、マイルストーン単位で「このまとまりを進めて」と `/goal /ndf:development-workflow` に渡すと、課題の分け方や束ね方、どれを並べて進めるかは AI が判断します。並行して走った設計 PR の企画承認も、1 本ずつではなく、まとめて 1 回で済みます。

たとえば v10.11.0 では、前の版を出してから約 1 日の間に 16 件の課題を閉じ、33 本の PR をマージしました。同時に開いていた PR は、多いときで 9 本あります。

ただし、並列にするほど速くなるわけではありません。サブエージェントを 5〜6 本同時に走らせたときは、レビュー用の CLI やテスト用のコンテナも合わせてメモリを使い切り、全員がまとめて止まりました。いまは同時に 3 本までに抑えています。人間のチームと同じく、並列度にも適正値があるようです。

### 振り返りと issue の棚卸しが効く

フローを回し続けていると、2 種類のずれが溜まっていきます。

- 進め方のずれ：同じところで何度もつまずいている
- issue のずれ：issue に書かれた内容が、すでに現状と合っていない

前者を直すのが振り返り（retrospective）、後者を直すのが棚卸し（issue-upkeep）です。

棚卸しの Skill を作ったとき、open だった issue 43 件を 1 件ずつ実物と突き合わせたところ、**24 件の本文が現状とずれていました**。半数を超えています。

ずれた issue を渡されても、AI はずれたまま真面目に作業を進めます。人間であれば「これはもう直っているのでは」と気づくところです。

### out-of-scope で issue は増え続ける。だから「やらない」を定義する。

out-of-scope は「迷ったら起票する」というルールで運用しています。後から閉じるほうが、見落としたものを拾い直すよりも安く済むからです。

その結果、8 月末からの 2 週間余りで起票された issue 264 件のうち、**127 件が範囲外の起票**でした。およそ半分にあたります。

AI は律儀なので、見つけたものはすべて issue にします。入口を広くした以上、出口も用意しなければなりません。

そこで、棚卸しの Skill に「やらない」と決めて閉じる判断を持たせました。直す価値よりも抱えておくコストのほうが大きいものは、「こうなったら再び検討する」という条件を付けて閉じます。

**人間の仕事は「作る」ことから「やること・やらないことを定義する」へ移りつつある**。

## まとめ

人間がやっていた開発フローを全部 Skill にし、`/goal /ndf:development-workflow` の 1 行で AI に通させるようにしました。

AI もまた間違える実行者である以上、人間のために作られてきた開発プロセスは、そのまま AI のためのプロセスとして機能します。運用してみて分かったのは、AI に任せる範囲が広がるほど、「先に決める」ことと「やらないことを定義する」ことの重みが増す、ということでした。

- 先に決める：受け入れ条件と設計を固め、企画承認で方向を確かめる
- やらないことを定義する：振り返りでやめる進め方を決め、棚卸しで「やらない」と決めた issue を閉じる

開発フローを全部 Skill にしても、人間が不要になるわけではありません。人間の役割が「作る」から「決める」へ移っていく、ということなのだと思います。
