# NDF の版ごとの決定と理由（v10.12.0〜v10.17.4）

`CLAUDE.md` から移した、出た版の記録である。**その版で何を決め、なぜそう決めたか**を残す。
変更点の列挙は `CHANGELOG.md` にあり、こちらは判断の理由を持つ。**`CLAUDE.md` へ書くのは
現行版で決めたことだけで、版を配布した時点でこちらへ移す。** そのため `CLAUDE.md` に版の段落が
1 つも無いことがある（配布の直後がその状態で、現行版で新しく決めたときに書き足される）。

**v10.6.0 から v10.11.0 の判断はここにも `CLAUDE.md` にも無い。** この 8 版は退避の手順を決める
より前、または `CLAUDE.md` へ段落を書かないまま配布された。変更点は `CHANGELOG.md` にある。
退避が働いたのは v10.12.0 の配布からで、**この文書の最初の段落が v10.12.0 なのはそのためである。**

**v6.1.0 から v10.5.1 までの記録は [ndf-version-decisions-v6-v10.5.md](ndf-version-decisions-v6-v10.5.md) に
ある。** v10.15.0 の配布でこの文書が分割の基準（500 行）を超えたため、古い側を分けた。

v10.12.0 で作業ツリー運用の残課題 6 件を塞いだ（マイルストーン「04 worktree 運用の残課題」、
#312 #315 #313 #573 #610 #495）。

**追従を既定で止め、`follow_branch` で有効にする**（#610）。セッション開始時の hook が主
ディレクトリの HEAD を動かすのは、**並列に動くエージェントの前提と噛み合わない。** どの担当が
セッションを開始・再開しても、他の担当が読んでいる主ディレクトリの内容が入れ替わる。**追従を
消すのではなく既定を裏返したのは、1 人が 1 つの作業ツリーで作業し、主ディレクトリを開いた
エディタでその内容を見る使い方が成立するためである。** 真偽値以外（`"true"` / `1` / `null`）は
`false` と同じに倒す。**宣言の項目を増やす側に置いたことで、追従の断りの文言も条件付きになる**
── 追従しないリポジトリで「追従しません」と出すと、有効にできることが伝わらないまま断りだけが
残る。`base_branch` の説明は「作業ツリーの起点」と「追従先」に分かれ、後者だけが条件付きに
なった。AGENTS.md・KIRO.md・スキーマ・`development-workflow` の 4 箇所も同じ操作で直した。

**宣言を共有と個人に分ける**（#495）。ポートの帯・持ち込み物・追従の有無は機械ごとに違う。
共有の宣言に書くと**各自の値が差分に載る**ため、`.ndf/worktree.local.json` を追跡しないファイル
として置く。**反映する項目を 3 つ（`localenv` / `testenv`（`expose` を除く）/ `follow_branch`）に
限ったのは、個人の宣言がレビューを通らないためである。** `base_branch` / `production_branch` /
`guard` を個人が変えられると、手元の動作と継続的統合の判定が食い違う。`testenv.expose` を外した
のは、**追跡されないファイルから外部への公開を有効にできる状態を作らない**ためである。
**配列は併合せず置き換える** ── 継ぎ足す形にすると、共有の要素を個人が外せない。**`null` は
反映しない** ── 消せると、仕組みが手元でだけ黙って止まる。**空になった `testenv` は節ごと
反映しない** ── 空の節を重ねると、`testenv` を宣言していないリポジトリで試験環境の仕組みが
有効に変わる。読めないときは共有の宣言だけで動き、hook もコマンドも止めない（気づく手がかりは
`status` の行が持つ）。**`status` は個人の宣言が無いときに何も出さない** ── 使わない利用者の
出力を変えると、既存の出力に依存する手順とテストが壊れる。

**読めない宣言を `init` が失敗として報告する**（#573）。それまでは読めない宣言でも「既に
あります」と報告して終了コード 0 で終わっていた。**壊れた宣言のまま手順が先へ進むと、仕組みが
動いていないことに気づく手がかりが無い。** 状態の行と案内を標準エラーへ出して 1 で終わり、
`worktree` の手順 0 はそこで止まる。**エージェントは宣言を書き換えない。** 直す・消す・
`init --force` で作り直すのは利用者が決める（宣言はリポジトリの運用であり、壊れた内容にも
書き手の意図が入っている）。

**保持の判定を陳腐化の規則へ揃える**（#312）。`ndf_lock_is_held` は `pid` を読んで生存を見て
おり、**`pid` を書く前に落ちたプロセスのロックを「握られている」と読んでいた。** 取得の側
（`ndf_lock_acquire`）が捨ててよいと読むロックを保持と読むため、その割り当ては時間が経っても
`reap` の対象へ戻らない。**「握られている」を「陳腐化していない」と同じ意味に定め**、判定の
規則は `_ndf_lock_is_stale` の 1 か所へ置いて、保持の判定はその否定だけを返す。作った直後の
`pid` の無いロックが 0 になるのは受け入れる（取得の途中にも `pid` の無い時間があり、落ちた
持ち主のものと区別できない）。5 分（`NDF_LOCK_STALE_MINUTES`）を過ぎたものだけが 1 へ変わる。

**台帳の更新の失敗を呼び出し元が受け取る**（#315）。`env` / `up` / `down` / `expose` /
`unexpose` は台帳の書き込みが失敗しても続けていた。**割り当ての記録が無い状態は、次の採番が
同じポートを渡す状態である。** 失敗を終了コードと案内で返す。**ただし時刻の記録だけは警告に
留める** ── 最後に使った時刻は `reap` の対象を選ぶ値で、欠けても割り当てそのものは壊れない。
止める失敗と警告に留める失敗を分けたのは、**すべてを止めると、取り戻せる失敗で作業が止まる**
ためである。

**書き込み先の走査をリダイレクトで終えない**（#313）。走査はリダイレクトの印を命令の区切りと
読んでおり、`sed -i 's/a/b/' x.md >log y.md` の `y.md` を出していなかった。**区切りの定義は
`cd` の枝や `||` の右辺の判定など多くの箇所が共有するため、定義は変えず、被演算子を走査する枝の
先頭で読み飛ばす。** 影響は 3 つの枝に閉じる。**読み飛ばしはオプションの引数を取る判定より前に
置く** ── bash はリダイレクトを引数の並びから除いてから命令へ渡すため、後に置くと
`cp -t >log dir a b` が `dir` を出さない（実測）。**プロセス置換 `<(` はリダイレクトとして
扱わない** ── `/dev/fd/N` へ展開される被演算子であり、読み飛ばすと最後の被演算子が消える。
**出力の順序は契約に含めない** ── 読み飛ばしで走査の順序が変わるため、テストは集合として比べる。

v10.13.0 で収束ループの上限を 1 つの表へ集めた（#598 #537 #662、マイルストーン 21 の P1 と P2）。

**上限を 1 か所へ集めたのは、3 つの上限が互いを知らずに置かれていたためである。** 監視の上限・
CLI の上限・無進捗の許容は別々の場所に既定値を持ち、**順序が崩れても失敗としては現れなかった**。
CLI が監視より先に打ち切ると、監視の記録には理由が残らず「無言で終わった」ようにしか見えない。
表を 1 つにして、全 28 組で「許容 < 監視 < CLI」をテストで固定する。

**上限を工程ごとに変えたのは、レビューと適用で所要が一桁違うためである。** 1 つの値に揃えると、
短い工程に合わせれば適用が打ち切られ、長い工程に合わせれば止まった担当を待ち続ける。実際に
cross-refactoring の修正と最終ゲートの修正は 420 秒で打ち切られていた。

**CLI の上限は監視の上限から導く。** 固定値にすると、利用者が監視の上限を上書きしたときだけ
順序が崩れる。崩れ方が利用者の設定に依存するため、こちらの既定値をいくつにしても塞げない。

**600 秒を超える監視は、区切って待つ以外に手が無い。** Claude Code の Bash の 1 回の上限が
600 秒であり、待ちを 1 回の呼び出しへ書けない。`bg-wait.sh` は背景で起動して終了コードを
ファイルへ残し、540 秒ずつ区切って待つ。**待ちの繰り返しを 1 回の Bash 呼び出しへ書かない**
（レビューで指摘され、#683 の round 2 で直した）。

**実行の要約は利用者の状態ディレクトリへ置く。** レビュー用の作業ツリーは実行のたびに作られて
消えるため、中に置いた記録は消える。**上限を変える前（P1）に測る側を入れたのは、変えた後の値
しか残らないと、変更が効いたかを比べられないためである。**

v10.14.0 で棚卸に、課題を根本原因の場所で直す判定「ルートコーズ」を足した（#712 #713）。

**判定を足したのは、原因を残したまま個別に直すと、同じ形が別の場所で出るためである。** v10.13.0
で打ち切りの上限（#598 / #537）を直したが、打ち切りの後に部分的な結果が失われる機構（#548 / #583 /
#584 / #619）は残った。上限は引き金であって原因ではなく、原因の側を指す記録が無かった。

**課題への判断を価値（やるか）と構造（どこを直すか）に分け、溜まった課題の構造の判断を
`issue-upkeep` に持たせた。** この升だけ、どの Skill も自分の役目と書いていなかった。判断と
見る対象の表の正本は `issue-upkeep` に置き、`out-of-scope` / `problem-solving` / `retrospective` は
写さずに指す。

**条件は「修正レイヤーが現象レイヤーと違う」の 1 つで、件数も大きさも条件にしない。** 目的は
原因を直すことで、まとめるのは手段である。件数が決めるのは記録の持ち方だけで、分け方は着手の
時点が決める。**既存の判定へ統合しない** ── 閉じてよいものと閉じられないものが同じ判定になり、
検索で区別できない。**分岐を「要判断」へ倒さない** ── 人へ返しても、人が見る材料は同じである。

**子 issue を閉じず、親 issue は子の中身を写さない。** 原因を直した後も各所への適用が残り、
写すと同じ再現手順の片方だけが古くなる。閉じた親の子は別のマイルストーンにいることがあるため、
段 1 に拾う経路を足した。**段 2A はクラスタを決めず（分担した担当には他の控えが見えない）、
段 2B は重複を先に突き合わせる**（逆にすると行き先が突き合わせを待ち、判定が循環する）。

**起票の例外は親 issue の 1 つだけにした。** 親 issue は既存の課題から導かれる。発見の瞬間の
3 択と `retrospective` はクラスタを判定する材料を持たないため、クラスタの発見を担わない。

**判定の値を足すと、それまでの値だけを想定した規則が外れる。** `no-work.md` の条件 2 を
「重複」固定のままにすると、同じ修正レイヤーを指す別の課題が重複として閉じられる。
`milestones.md` の直近を連番で決めるのは open のマイルストーンが版数を持たないため、語を
「マイルストーン」へ揃えたのは「まとまり」が配布の単位を指すためである。

v10.15.0 で無人の運転と工程の測定を入れた（マイルストーン 18「10 無人運転と工程の測定」、#540 #541 #550
#554 #561 #621 #623 #657）。**8 件の課題は設計の時点で 4 束に分けた** ── G1 後片付けと課題を閉じる時点
（#561 #623）、G2 3 層の運転と中断の再開（#550 #657）、G3 実行計画と本数の測定と組（#540 #541 #621）、
G4 指示書の検査（#554）。束ごとに 1 本の設計 Pull Request（#739〜#742）を通し、実装は束の中で
Pull Request を分けた（G2 は測定 / 運転 / 再開の 3 本、G3 は本数 / 組 / 実行計画の 3 本）。
**触るファイルが重ならない束を並行させ、同じ節を書き換える束だけを順にした**（G1 と G2 が
`development-workflow/SKILL.md` を触るため、G2 は関門の節に触れない取り決めで並行した）。

**層の語は conductor / supervisor / worker の 3 つに固定し、「窓」と「親」を規約から無くした**（#550）。
conductor はまとまり、supervisor は持ち場（連続する工程の束）、worker は 1 つの作業を持つ。単位を工程
1 つではなく持ち場にしたのは、工程表の 18 行ごとに supervisor を立てると固定費が 18 回掛かるためである。
worker を葉にするのは深さ 3 を実測していないため、3 層へ出すのを `/goal` だけにするのは対話では人が
工程ごとに指示を変えられるためである。**worker の報告を conductor へ転送しない** ── 層を増やしても
conductor の読む量が変わらず、押し上がるのは固定費の合計だけで、それは測定が見せる。識別子は層の側を
揃え（`agent-layers.md` / `transcript_agents.py` / `--agents`）、量を指す名前は `window` のまま残した
（`context-window.md` / `--window-limit`）。

**上限の中断は通知ではなく記録で見分け、再開は直下だけを見る**（#657）。通知の本文は書式を約束して
いないが、記録からは同じ一覧が得られる。conductor が孫の worker を直接再開すると、再開した supervisor と
worker が同じ書き込みを重ねる。解除を待つ手段は 3 段（自動の継続 / `wait-reset` の通知 / 人の 1 通）で、
人の 1 通は承認ではなく関門に数えない。`StopFailure` フックは出力も終了コードも無視されるため使わない。

**測定はコマンドが行い、起動の拒否はしない**（#621）。担当はサブエージェントとして本体のプロセスの中で
動くため、フックで本数を数える手がかりが無い。数えられないものを拒否の条件にすると、止める必要の無い
起動を止めるか、止めないまま「機械が見ている」と読まれる。本数は
`min(上限, 動いている本数 + ⌊(空き − 予備) ÷ 1 本の見込み⌋)` で出し、初期値（予備 2048 MiB / 1 本
2048 MiB / 上限 3 / スワップ 25%）は `parallel-measure.py` の定数だけが持つ。文書に写すと写した側だけが
古くなる。**OOM Killer の回数が増えた見直しを除き 1 を下回らない** ── 0 本では進行が止まり、逐次で
進めた過去 11 版で本体は落ちていない。

**実行計画は主ディレクトリの `issues/` に置き、開いている間はコミットしない**（#540）。見直しのたびに
Pull Request を通すと、計画の更新がマージを待って進み具合に遅れる。`parallel-batch-<連番>/` の規約は、
全体指示書を主ディレクトリへコミットする運用が `develop` への直接コミットの禁止と両立しないため
置き換えた。依存は「B のどの工程が A のどの時点（`収束` / `マージ`）を入力にするか」で書き、重なりは
節の単位で 3 つ（別の節 / 足すだけ / 書き換え）に分けて、書き換えの重なりだけ実装を順にする。
**競合は後からマージする側が解く。** 先にマージした側は解く時点で既に閉じている。**マイルストーンの型を
宣言せず、束ね直さず、説明に組を書く**（#541）── 型を宣言しても組み替えは起きず、束ね直すと連番が表す
着手の順序が動く。組は見込みで、確定の値は実行計画が持ち、説明へ書き戻さない。

**実行前確認の要否は 3 つの問いで決め、止める合図は git の拒否だけにした**（#561）。「実際に取り消せるか」
の 1 問では `pr` の push と `out-of-scope` の起票も取り消せるため確認が外れる。問い 2（他者が読む新しい
内容を外へ出すか）は関門 2 と同じ「見た人は戻らない」性質、問い 3（判断を問うか）は判断そのものへの
同意である。`headRefOid` の一致で `-D` の代わりになる判定を NDF の側に作ると、二重の確認が形を変えて残る。
**起点・本番のチャネル・現在のブランチは同意を求めずに対象から外す** ── 消してよいかを尋ねる場面が
作られること自体が誤りで、1 回の誤答で開発の本流が消える。無視されたファイルは止める条件にすると
`__pycache__` を持つほぼすべての作業ツリーで止まるため、退避してから消す。

**まとまりの課題は終わりの工程を通った時点で閉じ、`merged` では閉じない**（#623）。開いている課題が
「利用者へ届いて確かめるまでが終わっていない」を表し、配布・リリース後テスト・振り返りの記録を開いた
課題へ書ける。閉じる条件は本番への配布とリリース後テストの合格で、検証への配布は利用者が常用する版に
まだ届いていない。閉じる手順は `progress-tracking` の 1 か所に置いた ── 終わりの工程はモードで 3 つに
分かれ、どれかへ置くと残りへ写しが要る。盤面を Done にする前に状態を読んで控えるのは、`Auto-close issue`
で閉じた課題を `既に閉じていた` ではなく `閉じた` と数えるためである。**コミットメッセージに閉じる語を
書かない** ── `main` へのマージは終わりの工程より前に来ることがあり、全件が早く閉じる。

**指示書の検査は、判定の強さをリポジトリ側の宣言（`.ndf/instructions.json`）で決め、宣言が無ければ既定の
判定だけを動かす**（#554）。利用者は NDF を入れた任意のリポジトリで、版も変更履歴も持たないことがある。
全部に同じ判定を掛けると入れた瞬間に落ちる。閾値を配布物に持たないのは、4 つのランタイムが別々の値を
助言しており、どれを既定にしても他の 3 つでは誤りになるためである。出た版は変更履歴の最大値との大小で
見る（節の一覧との一致では、節を持たない版の段落を取りこぼす）。版の段落は段落の先頭と見出しの
書き出しだけで拾う（行の途中まで見ると現行の規約の文が指摘される）。即時読み込みの一致範囲は
Claude Code 2.1.274 の実測 8 通りのうち読み込まれた 2 通り（行頭・空白の直後、強調の中）に合わせた。
観点は根拠を出典として残して値そのものは持たず、調べ直しは自動で書き換えない（外部の記述の読み違いが
そのまま検査の基準になる）。**この配布が、退避の検査を配布の工程で通した最初の版である。**

v10.16.0 で収束ループを、担当が揃わない・上限で止まる・結果を残さないときにも止まらず終わる形にした
（マイルストーン 13「agy の打ち切りと止まらない収束ループ」、#478 #553 #583 #584 #592 #619 #624 #647
#648 #664 #678 #687 #706 #727 #728 #729 #730 #732 #736）。**19 件の課題を、根本原因の場所 5 つ
（#727 #728 #729 #730 #732）へ寄せてから設計した。** 現れ方ごとに直すと、同じ判断が cross-review と

**結果なしの判断と起動し直しの可否は、結末の共通層の 1 つの真偽値が持つ**（#729）。偽にするのは
利用上限だけにした ── 利用上限は起動し直しても解けず、起動のたびに待ちと相手の枠を使う。他の理由は

**認証の確認を関門から外し、使える者だけで始める**（#478 #727）。確認と中断が 1 つの関数にあると、

運用を残した。**席は 2 つとし、使える者 → ホスト → 同じランタイムの 2 つ目の順で埋める**（#687）──

**起動した後に分かる使えなさで担当を自動で外す仕組みは作らない** ── 一時的な打ち切りでも、以後の
ラウンドから恒久的に外れる。

**cross-refactoring の既定の参加者を codex / kiro とホストにした**（#664）。起動 199 回のうち失敗は

レビュー担当の役は消した ── 残すと読み手が「この 2 者がレビューした」と読む。

**再開で渡した引数は、反映するか知らせるかのどちらかの表に必ず載せる**（#648）。引数の既定を未指定に

である。担当に関わる引数を渡した再開でだけ参加者を作り直す ── 途中で担当が入れ替わると、前の
ラウンドの記録と突き合わせられなくなる。

**収束の判定で数えないのは、棄却と `minor` 以下だけにした**（#732 #624 #706）。反証する相手がいない
構成（`--only` の 1 者）で、誤りを示されていない `major` が立証不足の区分へ落ち、未解決のまま承認で
終わっていた。立証不足の区分の名前は変えず軽微な指摘の残余だけに当てた ── 改名すると旧い状態
ファイルの値・測定の読み方・語彙を同時に付け替えることになり、変更の前後を測定で比べられなくなる。

**GitHub と git へ書くのは、レビューを回す側だけにした**（#730 #583）。担当が投稿してから結果ファイルを
書く形では、その間で止まると投稿は残り記録は残らず、起動し直した担当が同じ論点を重ねて投稿した
（PR #578）。担当の投稿の後に実物と照合して記録を補う形は採らない ── 照合の問い合わせが上限で
失敗すると同じ食い違いが残る。修正は現在の頭を指定して送り、送った後に照合する ── ブランチ名だけの
送信は、切り離された頭で何も送らずに終了コード 0 で終わる。単独の `/ndf:fix` の口は新しい入口の
スクリプトにせず共通層の部分命令にした ── 手順に書く行が 1 本で済み、実装が 1 つになる。

**同じ適用ラウンドを開き直すのは 2 回までの固定値とし、引数を足さない**（#728 #647 #592）。2 回目は
別の担当が試すため、2 回とも残らなければ担当ではなく適用ラウンドの側を疑える。上限を引数にして 2 つ
置くと、どちらで止まったかを読み解く必要が出る。**進行側は取り込みでコミットを書き換えない**（#553）
── 識別子が変わり申告と実体の対応が切れるため、必須の記名は末尾の段落から前へ git の判定に掛けて読む。

**テストの実行中は `MONITOR_` で始まる環境変数を、根の `conftest.py` の 1 か所で外す**（#678）。
名前を並べずに接頭辞で一致させるのは、上限の種類が増えるたびに一覧へ足し忘れる形を作らないためで、
収集より前に外すのは、テストの本体を読み込む時点で上限を決める実装があるためである。

**照合の表へ足す文言は、実物に出所を持つものだけにする**（#811）。記録（CLI の会話と収束ループの
標準エラー）か、導入済みの実行ファイルに埋め込まれた文字列に当たるものだけを足した。出所の無い行は
合っているかをテストで確かめられず、**書いた側の思い込みがテストの期待値にも入って通ってしまう**。
claude の旧い形は記録にも実行ファイルにも 0 件のため足していない。**足す文言は行頭で始まる形に
固定する** ── 担当は作業中のコマンドの出力（差分・ファイルの中身）も標準エラーへ書くため、文言を
含む文書やテストを読み上げた行に一致させない。見逃しは 1 度起動し直すだけで済むが、誤検知は結果を
書ける担当を止める。**期間や種類は 1 行の照合で覆う** ── 形ごとに行を足すと、CLI が種類を増やす
たびに照合が遅れる。再試行の上限は最後の状態が 429 のときだけ利用上限と読む ── 同じ文言は 503
などの一時的な誤りでも出て、そちらは起動し直せば解けうる。

**確認コマンドを起動できないときは、例外の種類を問わず「通らない」として返す**（#813）。権限の

ときも、理由は「実行できない」として出す** ── Python の起動は「見つからない」と「実行権が無い」を
同じ例外で返し、見分けるには検索のパスを自分で辿り直すことになって、確認を 1 つ走らせる関数の範囲を
超える。理由に権限の拒否が出れば、利用者は検索のパスとファイルの権限を見ればよい。
