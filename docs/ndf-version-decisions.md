変更点の列挙は `CHANGELOG.md` にあり、こちらは判断の理由を持つ。**`CLAUDE.md` へ書くのは
現行版で決めたことだけで、版を配布した時点でこちらへ移す。** そのため `CLAUDE.md` に版の段落が
1 つも無いことがある（配布の直後がその状態で、現行版で新しく決めたときに書き足される）。

退避が働いたのは v10.12.0 の配布からで、**記録の最初の段落が v10.12.0 なのはそのためである。**

v10.17.41 で工程の単位の呼び名を「ミッション」から「スプリント」へ改めた（#1407）。語は ミッション →
スプリント、ミッション状態ファイル → スプリント状態ファイル、ミッションブランチ → スプリントブランチ、
ミッション課題 → スプリント課題、ミッション MVV → スプリント MVV で、コードの名前は `mission` → `sprint`
（`supervise.py new sprint`・`--sprint`・`sprint/<名前>`・`sprint.json`・`sprint-state.py`・`sprint-close.py`）である。

**改名するのは工程の単位の側である** ── 工程の単位（1 つの版として出す課題と Pull Request のセット）と
MVV の Mission（使命）が同じ語で、「ミッション MVV」のように並ぶと 1 語 1 意味が崩れる。MVV は変えられない。
**スプリントは期間ではなく、1 つの版として出す中身で切る** ── 候補のうちバンドル・バッチ・ウェーブは用語集か
本文の語と重なり、スプリントだけが重ならなかった。意味の文に切り方を書いて、期間の意味で読まれるのを防ぐ。
**過去の記録（`CHANGELOG.md`・この文書・`issues/` の既存の文書・既存の課題と Pull Request の本文）は
書き換えない** ── 書いた時点の記録である。

**旧名（`new mission`・`--mission`・`mission/<名前>` のブランチ・`mission.json`・旧名のスクリプト）は
しばらく受け付け、新しい名前を 1 行で案内する** ── 改名の前に始めた実行はプランの JSON にスクリプトの
絶対パスを埋めており、受け付けないと再開できない。**受け付けは `plugins/ndf/scripts/lib/legacy_names.py` の
表 1 つに集める** ── 各所に分岐を持つと、やめるときに消し残しが出る。前例の `bundle-close.py` は、やめる版を
決めずに残した結果、呼ぶ Skill が無くなった後も残っている。**`mission.json` はその場で書き換えず読むだけにする**
── 書き換えると、旧版の NDF へ戻したときに読めなくなる。

**旧名の受け付けは、改名を載せた正式版の次の正式版でやめる。改名を載せた正式版は 10.17.41 なので、
10.17.41 の次の正式版でやめる**（#1427）── 版数はリリースまで決まらないため、設計では「改名を載せた
正式版 + 1 つ」の規則で決め、版数はリリースで書き足した。やめる版では表を断る側へ切り替え、旧名で呼ぶと新しい
名前を示して終了コード 2 で止める。黙って消さない ── 改名の前に覚えた人やプランが、何が変わったか分からない
まま失敗する。表と旧名の入口のスクリプトを消すのは、断る振る舞いを 1 つの正式版として出した後で、時期は #1427 が決める。

v10.17.42 で配布の工程を、プラグインの版数を持たないプロジェクトでも回せるようにし、マージが本番へのデプロイに
なるリポジトリでは承認ゲート 2 をそのマージに掛けるようにした（#1336）。設計は `issues/issue-1336-design.md`、
選んだ結論と理由の全体は `issues/issue-1336-design-decisions.md` にある。

**止める場所はプランや hook ではなく `merge-when-green` に置く** ── プランのマージはすべてこのスクリプトを通るため、
4 ランタイムのどれから流しても同じに止まる。hook だけでは、スクリプトが子のプロセスで呼ぶ `gh` が見えない。
**プランでは判定のステップをマージの前に分ける（`merge-gate` → `merge` → `merge-approved`）** ── 後片付けの同意も
同じ終了コード 10 を返すため、マージのステップで終えると、承認ゲート 2 のつもりで記録とまとめのステップまで流れなくなる。

**本番へ出るマージかは、本番チャネル（`production_branch` → 既定ブランチ）と `delivery` の `kind: auto` の行の
`branch` の一致で決め、宣言の形は拡げない** ── 行へ系（本番 / 検証）のキーを足すと、本番を表す値が 2 か所に分かれて
食い違ったときの正が要る。解析（#1333）もそのキーを埋めない。**決められないとき（宣言が読めない・本番チャネルが
決まらない・本番チャネル宛てで `delivery` が無いか不明）は止める** ── 通す側へ倒すと、承認の無いまま本番へ届く経路が
残る。宣言の無いリポジトリは、本番へ出るかが最も分からないリポジトリでもある。止まるのは本番チャネル宛てに限られる。

**承認は `--gate-approved user|mvv` の 1 か所で受け、誰が承認したかとマージした先頭のコミットを結果に残す** ──
後から監査で辿るためである。先頭のコミットへ承認を縛る案は、プランを書く時点でコミットが決まらないため採らない。
**hook は自動反映の本番チャネル宛ての直接の `gh pr merge` を拒み、`merge-when-green` へ案内する** ── hook で承認を
受けると承認を示す場所が 2 つになる。人の手によるマージは hook を通らず、止めない。

**リリースの経路は `delivery` から導き、`release.form` に値を足さない。`release.form` があればそちらを優先する** ──
配布の仕方の正本は `delivery` で、`release.form` に値を足すと同じ事実を 2 か所に書く。ai-plugins は
`package-plugin` が先に効くため、今の雛形のまま動く。**手で反映する経路（`manual`）では NDF はコマンドを実行せず、
`/ndf:release` の手で行うステージを置く** ── `trigger` は解析が書く文で実行してよい形をしておらず、反映は認証情報を
使い、成否を見届ける仕組みも無い。**`package-plugin` から宣言へ移すのはブランチ・タグの接頭辞・題・リポジトリ名に
限る** ── どれも既存の宣言か `origin` から決まる。CHANGELOG・配置・版の形は、この形を選ぶのが ai-plugins だけで
値の出所を決める材料が無いため、形の約束として残す。

**ベースブランチと本番チャネルが同じリポジトリでは、承認ゲート 2 はスプリントで 1 回（検査の Pull Request の
マージ）になる** ── 実装の Pull Request はスプリントブランチへ入るため本番へ出ない。スプリントを通さない
`new impl` / `new fix` は 1 本のマージが 1 回の反映なので Pull Request ごとに止まる。**設計 Pull Request のマージが
本番へ出るときは、承認ゲート 1 の問いに本番への反映を載せて 1 回の承認で進める** ── 同じ 1 回のマージに 2 回の
承認を求めない。**昇格の Pull Request は head がベースブランチなので、マージの後に後片付けをしない** ── 後片付けを
通すとベースブランチを消す。

v10.17.43 で課題の棚卸しに優先順位の組み替えを足し、Skill を `issue-upkeep` から `backlog-refinement` へ改名した
（#1429）。設計は `issues/issue-1429-design.md`、選んだ結論と理由の全体は `issues/issue-1429-design-decisions.md` にある。

**マイルストーンの間をプロダクトバックログ、マイルストーンの中の順位をスプリントバックログの候補と読む**（決定 0）
── #1407 の「スプリントはマイルストーンから切り出す」を変えずに済み、1 本から何十ものスプリントを出す
マイルストーンでも成り立つ。**スクラムの語は、NDF に同じものがあって名前が無いときだけ採る**（決定 19）──
役割・イベント・ベロシティは、利用者が 1 人で担い手が AI の 3 層のため当てはまるものが無く、名前だけの儀式が残る。

**Skill の名前は `backlog-refinement` にし、`sprint-planning` にしない**（決定 20。承認ゲート 1 で利用者が決定）──
棚卸し（本文の訂正・やらない・ルートコーズ）と順位付けの両方が名前に入る。スプリントの中身の確定は今どおり
`issue-plan-strategy` と `supervise.py new sprint` が持ち、この Skill は切り出しの境界を示すまでにする。旧名は
#1407 と同じく `lib/legacy_names.py` の表で受け付け、改名は実装の最初のコミットに分けて順位付けと混ぜない。

**層をまたいだ逆転は、遅延コスト（CoD）で比べる前倒しの規則で防ぐ**（決定 0b）── WSJF で比べると大きい課題が
割り算で沈み、永久に前へ出ない。比べる相手は直近のマイルストーンの切り出しの境界で、尺度の 1 段階の余白を置く
（LLM の見積の順位相関は 0.4 程度で、1 段階の差は揺れの範囲である）。語は「昇格」でなく「前倒し」にする ──
用語集の「昇格の Pull Request」と 1 語 2 意味になる。**自動で反映するのは実害の観測がある前倒しと、マイルストーンの
中の順位だけにする**（決定 4）── マイルストーンの順序と後ろ倒しは人が決める。

**大きい課題を優先する**（決定 21。利用者の決定）── 実施するのは AI エージェントで、人より基盤の課題と大きい課題を
抱える許容度がはるかに高い。#1142・#760・#889 がいまだに解けていないことが経緯である。順位の値は
「遅延コスト ÷ 大きさ^α」（既定 α=0.3）、容量の半分を大きい課題の 1 切れへ先に当て、被依存の数の加点を強めた。
**費用は AI の実行の費用（所要時間・LLM の費用・差分の行数）で見積る**（決定 22）── 単位が担い手と違うと、人に
重く AI には軽い基盤の課題が沈む。人の判断待ちは費用に数えず、印を付けて判断を先に求める材料にする。
**実害の段階は影響範囲の帯（全体 13〜20 / 機能 5〜8 / 表示 2〜3）で先に決める**（決定 23）── 相対だけで付けると、
全体の停止（#889）が表示の誤り（#1422）より後ろに来る逆転が起きた。退避策は、止まるのを防いだ記録があるときだけ
段階を下げる根拠にする。

**宣言は `.ndf/backlog.json` に置き、`project.json` に節を足さない**（決定 9）── `project.json` は解析が書き直す
宣言で、人が決める容量・閾値・アンカーを混ぜると解析のたびに人の値と機械の値が 1 つのファイルで競う。
**承認済みの移動は `rank --approved` で表に入れてから `apply` する**（決定 14）── `approved: true` だけで反映すると
説明の表が移動の前の並びのまま書かれ、`apply` の中で算出し直すと算出が 2 か所に分かれる。

**`rank --approved` が承認した時の移動と照合しない不足（cross-review の major 1 件）は、保留のまま本番へ出した**
（承認ゲート 2 で利用者が決定。行き先は #1462）── 直すには承認済みの設計（決定 14・AC9）の引数の形を変える
必要があり、仕様の判断になる。承認の後に境界・移動先・依存が変わると、承認した時と違う移動が実行されうる。

v10.17.44 で relay のアカウント選びを残りの量で行うようにし（#1453）、手動反映の本番系で `pace: auto` / `fast` を
使えるようにした（#1454）。設計はそれぞれ `issues/issue-1453-design.md` と `issues/issue-1454-design.md`（決定の記録は
`issues/issue-1454-design-decisions.md`）にある。

**アカウントは残りの量 = 枠の大きさ ×（1 − 使用率）の、枠ごとの最小で選ぶ**（#1453）── 使用率だけで選ぶと、
Max 20x に余りがあっても使用率の少し低い Max 5x へ切り替わる。5 時間の枠と週の枠は大きさの比が違うため、使用率の
大きい方が止める側とは限らない。単位は API 料金の換算額（USD）にそろえた。**対応表はモジュールの定数に置き、
アカウントごとの値の違いは `account.json` の `capacity` の宣言が受ける**（決定 1・2）── 表を変えたい理由は「自分の
アカウントの値が違う」ことで、設定ファイルに表を置くと同じ問いに答える場所が 2 つになる。宣言は利用者が手で書かず
`relay.py account capacity` で書く ── `account.json` は排他の中で読み書きされ、手で書いた内容が並行の書き込みで消えうる。
Max 5x の週の枠（640）は非公式の比による仮の値で、見かけの精度を持たせずに丸めた。

**`Choice.score` は使用率のまま残し、残りの量は `remaining` として足す**（決定 3）── 切り替えの閾値は使用率で比べて
おり、`score` を USD に変えると閾値との比較がすべて誤る。残りの量の順だけで並べると、閾値を超えた大きいアカウントが
先に返って従量の接続から戻れなくなるため、閾値未満の候補を先に試す。**残りの量の分からない候補は、分かる候補の後ろへ
今の使用率の順で並べる**（決定 4）── 未知の tier に推定の値を当てると、根拠の無い値で順序が決まる。

**支出上限の到達は `spend.percent` ≥ 100 か severity critical でも判定し、一覧の `spend_limit_reached` をその合成の
判定にする**（決定 5）── `spend_limit_reached` が偽のまま上限に達した応答を実測した。別のキーを足すと同じ問いに答える
キーが 2 つになり、既存の読み手が誤った方を読み続ける。生の値は `spend` に残す。**`limits[]` からは `weekly_scoped`
だけを読む**（決定 7）── 残りは `five_hour`・`seven_day` と同じ値の別の表し方で、両方を読むと食い違ったときの規則が要る。

**「本番系へ届く」は配布の宣言の行の真偽値 `production` で表し、書いていない行は決めない**（#1454 決定 1）── 判定に
要るのは 2 値だけで、環境の区分を列挙すると使わない値の意味を決める必要が出る。書いていない行を偽へ倒すと、既存の宣言の
本番の行を検証の環境と読み、承認ゲート 2 を落とす。語に `channel` を使わないのは、用語集の「本番チャネル」がブランチを
指すためである。**`production: true` の行がすべて手動で 1 つ以上あるときだけ、起点と本番チャネルが同じでも開発版の
チャネルがあると数える**（決定 4）── 本番系の行が無い宣言は、本番へ手で届くのかを NDF が知らないため今どおり断る。

**手で届ける経路は「開発版」「承認ゲート 2」「本番」の 3 ステージに分け、承認ゲート 2 だけを MVV 判定のプランにする**
（決定 5）── 手で行うステージはプランを持たず、MVV 判定と `verify` を置く場所が無い。`production` を書いていない手動の
行は「本番」へ入れる ── 承認の後に届けても失うのは待ち時間だけだが、本番系を承認の前に届けると取り消せない。**承認資料に
ベースブランチの先頭のコミットを載せ、「本番」はそのコミットを届ける**（決定 6）── 承認の後にベースブランチへ入った変更を
承認なしに届けない。**判定は `lib/delivery.py` の 1 か所に置き、起点と本番チャネルが違うリポジトリでは `delivery` を
読まない**（決定 2・9）── 判定の食い違いを防ぎ、ai-plugins 自身のように今 `auto` が通っているリポジトリの振る舞いを変えない。

**実物での確認を残したまま本番へ出した**（承認ゲート 2 で利用者が決定）── #1453 の実アカウントでの残りの量の照合（AC10）と
#1454 の手動反映の本番系を持つ実物のリポジトリでの確認は、どちらもリリース後テストで行う。テストは偽の応答と一時リポジトリ
だけで見ており、表の値が実物と違っても切り替えそのものは止まらない。範囲外の欠陥として見つけた merge / promote の経路で
`verify` が走らない件は #1457 へ回した。

v10.17.45 で relay の Bedrock の登録をスクリプトにし、`account` の副命令をすべて引数でも打てるようにした（#1468）。
設計は `issues/issue-1468-design.md`、選んだ結論と理由の全体は `issues/issue-1468-design-decisions.md` にある。

**副命令は `add-bedrock`・`check metered`・`remove metered` にする**（決定 1）── `add <名前>` の名前には `bedrock` も
使えるため、`add bedrock` は同じ形に別の意味を持ち込む。`metered` は従量の接続の予約の名前として既にあり、一覧の行の
名前もそれになる。`add-metered --provider bedrock` にしないのは、提供元ごとに要る引数が違うためである。**宣言は
`provider`・`env`・`details` の 3 つに分ける**（決定 11）── 子へ足す値と一覧に出す値を提供元を知らずに扱え、Vertex を
足すときに変えるのは副命令と確かめる手段だけになる。

**呼べるかの確認は `aws sts get-caller-identity` と、保存するのと同じプロファイル・地域・モデルでの `aws bedrock-runtime
converse`（最大 1 トークン）で行う**（決定 4）── `aws` はエラーの種類の名前を返すので、理由を「認証切れ・権限・地域・
モデル」の 4 区分へ振り分けて元の名前も出せる。`claude -p` で 1 回呼ぶ案は、種類の名前が残らず、システムの指示の分の
