# Neural Development Factory: 画面の地図

Neural Development Factory の Web の画面の全体を 1 つの表にまとめる。どの経路にどの画面があり、どの役割が使い、確定仕様のどの機能がどの画面に載るかを示す。画面を足す課題は、この表に 1 行を足し、`factory/web/src/screens.ts` に同じ行を足し、翻訳のファイルにキーを足し、[画面の部品](ndf-factory-ui-components.md)で画面を組む。予定の行に作る課題として書かれた課題は、行を足さずにその行の状態を「あり」へ変え、経路を書き、作る課題の括弧を確定仕様の節へ置き換える（節が無ければ括弧を消す）。予定の行は、どれも作る課題を `（作る課題: #<番号> <題>）` の形で「載る機能」の列の末尾に 1 つ持つ。作る課題は、書く時点で GitHub で open のものに限る。作る課題がその画面を作らないと決めたときは、同じ変更で行ごと消す。別の課題がその行を作ると決めたときは、その課題の変更で作る課題を自分の番号と題へ書き換える。

## 概要

- **経路の定義は `factory/web/src/screens.ts` の 1 か所にある。** アプリの経路（`App.tsx`）とナビゲーション（`NavMenu`）はそこから作り、経路を別に書かない。この文書の表の「状態が あり」の行の経路の集合と `screens.ts` の `available` の経路の集合は、テスト（`factory/web/src/docs.test.ts`）が一致を確かめる
- **ログインの後の画面は枠（`AppShell`）で包む。** 枠は見出しの帯・ナビゲーション・つながりの状態を持つ。ログインの画面・ログインの戻り・地図に無い経路の転送は枠で包まない
- **地図に無い経路を開くと `/account` へ移る。**
- **ナビゲーションの行き先には、スマートフォンの幅（360 px）でもメニューのボタンと行き先の 2 手で届く。**

## 用語

定義は [用語集](../glossary.md) が正である（文脈 `ndf-factory`）。この文書で使う語は「画面の地図」「見本の画面」「つながりの状態」である。

## 役割

| 役割 | `screens.ts` の値 | 決め方 |
| --- | --- | --- |
| 個人 | `personal` | 今の経路のアカウント（無ければ個人のアカウント）が `kind: "personal"` |
| Team の管理者 | `team_owner` | 今の経路のアカウントが Team で、`role: "owner"` |
| 席 | `team_seat` | 今の経路のアカウントが Team で、`role: "member"` |

枠は `api.me()` を token ごとに 1 度だけ呼んで役割を決める。経路のアカウントが `Me.accounts` に無いとき（チームを作った直後など）だけ、そのアカウントにつき 1 度呼び直す。役割が決まるまでと失敗したときは、役割の要る行き先（キーの持ち込み）を出さない。画面の判定は表示のためだけで、認可は API が行う。

## 画面の地図

| 経路 | 画面 | 役割 | 状態 | 載る機能（確定仕様の節） |
| --- | --- | --- | --- | --- |
| `/login` | ログイン | ログイン前 | あり | Google・GitHub でログイン（[accounts-and-plans](ndf-factory-accounts-and-plans.md)「ログインの流れ」） |
| `/callback` | ログインの戻り | ログイン前 | あり | code を token に換える（accounts-and-plans「ログインの流れ」） |
| `/account` | 自分のアカウント | 個人・管理者・席 | あり | 利用者の ID・個人の料金プランと実行の形態・使える量・チームの一覧・ログアウト（accounts-and-plans） |
| `/teams/new` | チームを作る | 個人 | あり | Team を作る（accounts-and-plans） |
| `/accounts/:accountId` | チームのアカウント | 管理者・席 | あり | 席の追加・種類の変更・削除（管理者）・実行の形態（管理者）・使える量（accounts-and-plans） |
| `/accounts/:accountId/repositories` | リポジトリ | 個人・管理者・席 | あり | 導入の案内・登録と外す（個人・管理者）・同時の実行の数の宣言（個人・管理者）・実行の状態（[runs-and-runner](ndf-factory-runs-and-runner.md)「画面」） |
| `/accounts/:accountId/model-credential` | キーの持ち込み | 個人・管理者 | あり | キーの保存と消去・外部 ID（runs-and-runner） |
| `/accounts/:accountId/repositories/:repositoryId/sprints/new` | スプリントを始める | 個人・管理者・席 | あり | 課題の候補・選び直し・開始（runs-and-runner） |
| `/accounts/:accountId/sprints` | スプリントの一覧 | 個人・管理者・席 | あり | 今のフェーズ（5 つの棒）と今の工程・状態・状態の絞り込み・最後の動き（[contracts-and-progress](ndf-factory-contracts-and-progress.md#スプリントの一覧と詳細の読み出し)） |
| `/accounts/:accountId/sprints/:sprintRunId` | スプリントの詳細 | 個人・管理者・席 | あり | フェーズの欄（仕上げに振り返りと棚卸し）・課題ごとの工程の記録・工程の詳細パネル・Pull Request と CI・承認ゲート・注意（取り込みで解けない衝突など、記録された順）・使用量（contracts-and-progress「スプリントの一覧と詳細の読み出し」）・起票の依頼（[issue-requests](ndf-factory-issue-requests.md)） |
| `/accounts/:accountId/approvals` | 承認待ちの一覧 | 個人・管理者・席 | あり | アカウントの答えの無い承認の依頼（設計承認ゲート・リリース承認ゲート・判断）を、種類・ループの名前・周回の番号・リポジトリ・課題・待ち始めた日時とともに古い順に読む（読むだけ）・行からスプリントの詳細へ移る |
| `/accounts/:accountId/repositories/:repositoryId/loops` | ループ | 個人・管理者・席 | あり | 開発ループの一覧（名前・選定の対象・状態・周回の数・費用・予算の残り・最後に動いた時刻・止まった理由）・始める |
| `/accounts/:accountId/loops/:loopId` | ループの詳細 | 個人・管理者・席 | あり | 周回・周回の実行と区間の数・利用上限の再開の時刻・人の判断待ちと答え・予算の変更・止める・次の周回を始める |
| `/accounts/:accountId/repositories/:repositoryId/backlog` | バックログ | 個人・管理者・席 | あり | 順位の表と棚卸しの記録（読むだけ） |
| `/delegations` | エージェントへの委任 | 個人・管理者・席 | あり | 委任の資格情報の発行（値は発行の直後に 1 度だけ出す）・一覧（範囲・期限・状態）・取り消し。オフラインの間は発行と取り消しをしない。自分のアカウントからたどる |
| 未定 | 請求と使用量 | 個人・管理者 | 予定 | 料金プランの料金・使用量の台帳・決済（作る課題: #2174 サブスクリプションと Bedrock の token 課金） |
| 未定 | 手元のマシン | 個人・管理者 | 予定 | 手元のマシンの登録・心拍（作る課題: #2189 手元のマシン（利用者の環境で、利用者の claude ログインで実行する）） |

## ナビゲーション

ナビゲーションに出す行き先は、自分のアカウント・スプリントの一覧・承認待ちの一覧・リポジトリ・キーの持ち込み（個人と管理者だけ）の 5 つである。`:accountId` は今開いている経路のアカウントで埋め、無ければ個人のアカウントで埋める。幅 1024 px 以上は見出しの帯に横に並べ、未満はメニューのボタンで開く。

## 役割ごとの主な動線

| 役割 | 主な動線 |
| --- | --- |
| 個人 | ログイン → 自分のアカウント → リポジトリ → スプリントを始める → スプリントの一覧 → スプリントの詳細 |
| エージェントに任せる人（個人・管理者・席） | 自分のアカウント → エージェントへの委任（発行して値を MCP のクライアントへ写す・取り消す） |
| 開発ループを回す人（個人・管理者・席） | リポジトリ → ループ（始める）→ ループの詳細（人の判断待ちに答える・次の周回を始める）→ スプリントの詳細 |
| 承認を待つものを確かめる人（個人・管理者・席） | 承認待ちの一覧（どのループの何周目の、どの種類の承認の依頼か）→ スプリントの詳細 |
| Team の管理者 | ログイン → 自分のアカウント → チームのアカウント（席の管理・実行の形態）→ キーの持ち込み・リポジトリ |
| 席 | ログイン → 自分のアカウント → チームのアカウント → リポジトリ → スプリントを始める → スプリントの一覧 |

## 見本の画面

スプリントの一覧と詳細とバックログと承認待ちの一覧は、部品だけで組み、ダミーデータでも動く。スプリントの一覧と詳細と承認待ちの一覧は開いている間、画面の設定の間隔（環境変数 `FACTORY_POLL_INTERVAL_MS`、既定 30 秒）で読み直し、読み直しが失敗しても前の表示を残して失敗の時刻を出す。

| 状態 | 一覧 | 詳細 | 承認待ちの一覧 |
| --- | --- | --- | --- |
| 読み込み中 | `LoadingState` | 同じ | 同じ |
| 0 件 | `EmptyState`「スプリントの実行はまだありません」 | 工程が 0 件なら `EmptyState`「工程の記録はまだありません」。注意が 0 件なら注意の欄に「ありません」 | `EmptyState`「承認を待っているものはありません」 |
| 失敗（5xx など） | `ErrorState` と「もう一度読む」 | 同じ | 同じ |
| 401 | token を消してログインへ | 同じ | 同じ |
| 403（無い実行も同じ） | 「このアカウントを見る権限がありません」 | 同じ | 同じ |
| 読み直しの失敗 | 前の表示を残し、上に「読み直せませんでした（<時刻>）」 | 同じ | 同じ |
| オフライン | 枠の `ConnectionStatus` が出し、画面は最後の表示を残す | 同じ | 同じ |

詳細の注意の欄は、理由が `base_conflict` なら「取り込みで解けない衝突」と出し、ほかの理由は値そのものを出す。承認待ちの一覧の行は、ループでない実行のループの名前と周回の番号を「—」で出す。

詳細は `Api` の `sprintRunDetails`、工程の中身は `stepDetails`、バックログは `backlogs` で読む（どれも ID の配列を受け、要素の配列を返す）。承認待ちの一覧は `approvalRequests` で、アカウントの行の配列を 1 回で読む。本物の実装は経路を 1 件ずつ読む。

## ダミーで起動する

`factory/` で `npm run dev:dummy -w web` を打つと、API を呼ばずにダミーの `Auth`・`Api`・つながりで画面が動く。切り替えは `factory/web/src/main.tsx` の 1 か所で、本番のビルドにはダミーが入らない（`npm run check:bundle -w web` が確かめる）。

| 検索の値 | 値 | 何が出るか |
| --- | --- | --- |
| `scenario` | `normal`（既定）・`empty`・`error` | 決まったデータ・一覧が 0 件・読み込みがすべて失敗 |
| `connection` | `online`（既定）・`offline`・`pending` | オンライン・最後に受け取った時刻つきのオフライン・つながってから確定する操作が 2 件 |

例: `http://localhost:5173/accounts/00000000-0000-4000-8000-000000000001/sprints?scenario=empty&connection=offline`
