# 文書の書き方の基準と読み手役の確認: 想定した読み手に通じない文を、承認を求める前に見つけて直す

## 概要

NDF は、AI が書いた文書（要求仕様書・設計書など）と質問の文が、それを読む人に通じるかを、次の 3 つで確かめる。

1. 文書の種類ごとの読み手と、読み手に通じない文の見分け方を 1 つのファイルにまとめた（以下「基準」）。文書を書く AI・レビューする AI・指摘を受けて直す AI への指示に、プログラムがこの本文を入れる
2. 文書を書いた会話を知らない AI（**読み手役**）が、想定した読み手の立場で文書と質問の文を読み、通じない文を引用して挙げる
3. 読み手役が確認したことを記録し、承認や判断の質問を出す直前に、その記録があるかを hook（Claude Code が Tool を使う直前に動かすプログラム）が調べる。無ければ質問を止める

例: 設計書の Pull Request（PR）の承認を人に求めるとき、次の順に進む。

| 順 | 誰が | 何をするか |
| ---: | --- | --- |
| 1 | 設計書を書いた AI が起動した読み手役 | 設計書を読み、「判断や作業を誤らせる文」を 2 件挙げる。1 件でもあるので不合格である |
| 2 | 設計書を書いた AI | 2 件の文を書き直す |
| 3 | 別の読み手役 | 設計書の全体をもう一度読む。誤らせる文が無く、要点の言い直しも合っているので合格である |
| 4 | 質問を出す AI | 質問の文と承認資料も読み手役に読ませ、`ndf records reading add` で記録する。`ndf records reading check` で、記録が今の PR に合うことを確かめる |
| 5 | hook の `reading-check` | 同じ質問の文の記録があり、PR の head（ブランチの先頭のコミット）も記録と同じなので、質問を通す |

手順と基準の本文は、次のファイルが正である。この文書には書き写さない。この文書が扱うのは、複数のファイルにまたがる振る舞い、そう決めた理由、既知の限界である。

| 何を | 正 |
| --- | --- |
| 文書の種類ごとの読み手、言葉の選び方、通じない文の 4 つの型と 2 つの区分、書き方・直し方・レビューの仕方 | [writing-criteria.md](../../plugins/ndf/contracts/data/writing-criteria.md) |
| 読み手役の対象・渡すもの・返させるもの・合否・回数・直し方 | [document-rebuild の「読み手役に読ませる」](../../plugins/ndf/skills/document-rebuild/SKILL.md#読み手役に読ませる) |
| 承認や判断を求める前の手順、読み手役を起動できないときの進み方 | [approval-request.md の「読み手役の確認」](../../plugins/ndf/skills/development-workflow/references/approval-request.md#読み手役の確認) |
| cross-review（複数の AI で PR をレビューし、指摘が無くなるまで直す仕組み）の指摘の基準 | [review-criteria.json](../../plugins/ndf/contracts/data/review-criteria.json)。基準 6 は `document` の項目 |
| 質問の区分ごとに hook が調べること | [asking.md の「質問の前に調べること」](../../plugins/ndf/skills/development-workflow/references/asking.md#質問の前に調べること) |
| 記録の 1 行の形 | [reading-check.schema.json](../../plugins/ndf/contracts/schemas/internal/reading-check.schema.json) |

「読み手役」の定義は、用語集（[docs/glossary.md](../glossary.md)）にある。

## 背景

2026 年 11 月 23 日から 24 日にかけて、意味が分からないという理由で、利用者が承認を 8 回以上見送った（ https://github.com/devbasex/ai-plugins/issues/4285 ）。基準が無かったのではない。7 か所に少しずつ違う形で書かれ、次の場面で守られなかった。

- レビューの指摘を受けて直す AI は、書き方の基準を受け取っていなかった
- レビューする AI は、言い回しを指摘しないと決められていた
- 読み手役は、要点を言い直せれば合格としていた。AI は不自然な文でも要点を言い直せる
- 承認の直前には、使わない言葉を検索して数えるだけで、文を読んでいなかった

## 仕様

### 基準を指示に入れる

基準を読むのは `ndf.contracts.writing` だけで、ほかのコードはこのモジュールから受け取る。

| 指示を受ける AI | 入るもの | 入る条件 | 組み立てるコード |
| --- | --- | --- | --- |
| 文書を書く worker（作業を 1 つ受け持つ AI） | 基準の全文 | 作業の種類の定義（[kinds.json](../../plugins/ndf/contracts/worker/kinds.json)）で、`document-style` を読むと決まっている。`ndf worker run` が起動するプロセスに限る | `core/worker.py` の `system_prompt` |
| cross-review でレビューする AI | 指摘の基準 6、指摘の書き方、基準の全文 | PR の全体の差分に、拡張子が `.md` のファイルがある | `criteria_decide.document_block` |
| cross-review で直す AI | 指摘の基準 6、文や段落を書き直して前後と一緒に読み直すという指示、基準の全文 | 同上 | 同上 |
| 読み手役 | 4 つの型と 2 つの区分の節だけ | 必ず | `records/reading.py` の `prompt` |

- 基準を読めなければ、指示を作る前に止める。worker は起動せず、cross-review はどの AI も起動せずに終わる
- `.md` を含まない PR の指示は、指摘しないものの一覧の 1 項目を除いて変わらない。その 1 項目は、「字句や言い回し」を「読み手に通じる文の、好みの言い換え」に狭めたものである
- NDF の共通原則（[ndf-common-principles.md](../../plugins/ndf/contracts/data/ndf-common-principles.md)）には、「文書は、想定した読み手に通じる言葉で書く。」の 1 文がある

### cross-review の基準 6

基準 6 は「文書の想定した読み手に通じない文」である。重要度は、「判断や作業を誤らせる文」なら major、「読みにくいだけの文」なら minor とする。major だけがレビューの終了を妨げ、直す AI に渡る。起きることの 1 文（`impact`）の無い major を minor に下げる規則（[cross-review-impact-severity.md](cross-review-impact-severity.md)）も、ほかの基準と同じように働く。

**2 ラウンド目以降は、基準 6 を major にしてよい文を 2 つに限る。** 前のラウンドまでに全体が読まれていないセクションの文と、比較元のラウンドの後に書き換わった文である。比較元のラウンドは、レビューする AI の全員が読めたラウンドのうち、最後のものである。そのラウンドが次の 3 つをすべて満たすときだけ使い、満たさなければ、さらに前のラウンドには戻らない。

- 今回レビューする AI の全員が、そのラウンドを読んでいる
- 比較基点（base との merge-base の SHA）とレビューの重点が、今回と同じである
- そのラウンドの head が、今回の head の祖先である

比較元が無いラウンドには、この制限を入れず、PR の全差分を読ませる。比較元があれば、その head からの差分のファイルをラウンドごとに 1 回だけ作り、全員に渡す。設計の PR では、比較元があっても、全体が読まれていないセクションが残る間は全差分を読ませるが、制限は入れる。ラウンドの差分の範囲と、この制限の両方を、`round_scope.previous_head` が返す 1 つの head から決めている。別々に決めると、全差分を初めて読む AI に「前に読んだ文」の制限がかかるためである。

### 読み手役の合否と回数

- 読み手役は合否を決めない。起動した担当が決める。「判断や作業を誤らせる文」が 1 件も無く、要点の言い直しが文書の内容と合えば合格である。「読みにくいだけの文」は合否に関わらない
- 1 回の確認で、読み手の立場ごとに 2 回まで読ませる。2 回目にも残った文は、直したか、直しきれなかった理由とともに引用する。引用する場所は、承認を求める文書なら承認の文、承認を求めずに PR で出す文書なら PR の本文である。そのまま進めるかは、承認する人か PR をマージする側が決める
- 承認を求める前に読ませるのは、まだ読ませていない文書、1 回目が不合格だった文書、確認の後にレビューなどで直した部分である。直した部分は、前後の段落と一緒に、新しい確認の 1 回目として読ませる。レビューのラウンドごとには読ませない
- 質問の文と承認資料は、どの承認でも読ませる。MVV（プロジェクトの判断基準）に照らした自動の承認で、人に尋ねないときは読ませない
- 読み手役の指摘で直した後は、質問を出す担当が差分を 1 回読み、事実（数・日付・条件・決定など）が変わっていないことを確かめる。レビューはやり直さない

### 記録と 3 つのコマンド

`ndf records reading` の 3 つのコマンドは、どれも `--file` で JSON のファイルを 1 つ受け取る。複数行の文を引数に載せないためである。

| コマンド | 入力のキー | すること | 終わり方 |
| --- | --- | --- | --- |
| `prompt` | `files`・`reader`・`questions_kind` | 読み手役への指示を作る。文書は加工しない | `ok`。指示は結果の `metrics.prompt` |
| `add` | `questions`・`prs`・`reads` | 記録を 1 行追記する。GitHub は読まない | `ok`。形が違えば `stopped`（`invalid`）で、追記しない |
| `check` | `questions`・`prs`（承認する PR の番号） | 承認の質問の前に、記録と今の PR を比べる | `ok`。足りないものがあれば `stopped`（`precondition`）で、`items` に語を返す。GitHub を読めないか、head を得られない PR があれば `stopped`（`unknown`） |

`check` は、使う記録に書かれた PR のブランチを先に `git fetch` で取り込む。後で動く hook が、手元のリモート追跡ブランチ（`refs/remotes/`）を読むためである。記録だけで足りないと決まれば、fetch も GitHub の読み取りもしない。

| 足りないものの語 | 条件 | 出るところ |
| --- | --- | --- |
| `no_record` | 同じリポジトリで、同じ質問の記録が無い | hook と `check` |
| `no_pr` | 承認する PR が、使う記録に書かれていない | `check` だけ |
| `head_moved` | 使う記録に書かれた PR の head が、今の head と違う | hook と `check` |

記録は `reading-checks.jsonl` に 1 行ずつ追記し、消さない。保存先はリポジトリの外で、環境変数 `NDF_MVV_STATE_DIR` があればそこ、無ければ NDF の状態の保存先（既定は `~/.local/state/ndf`）である。

- 1 行は `version`・`at`・`repo`・`question_key`・`prs`・`reads` を持つ。文書の本文、質問の文、残った文の引用は書かない
- `question_key` は、質問ごとの「質問の文・複数選択か・選択肢の名前と説明」から作った SHA-256 である。見出しと区分は含めず、文字列の前後の空白は除く。選択肢の説明を 1 文字変えても別の質問になる
- `repo` と `question_key` が同じ行が複数あれば、最後の行を使う。期限は無い
- `reads` には、質問の文を読ませた行（`name` が `question`）が 1 つ以上要る。結果は `passed`（合格）か `remained`（2 回目にも残った）で、`remained` は 2 回目にだけ書ける。どちらの結果でも質問を出せる
- 壊れた行は無いものとして読む。`prs[].branch` に `*` などのパターンを含む値は、`add` が拒み、書かれていても壊れた行として扱う。取り込むブランチの指定に使うので、複数のブランチに当たる値を受けない

### 質問の直前に調べる hook

guard（hook の中で、1 つの条件を調べて止めるか通すかを決める部品）の `reading-check` は、Claude Code の `AskUserQuestion` の直前に動く。文の良し悪しは判定しない。質問の区分は、`metadata.source` の先頭の `ndf-gate:`（承認を求める質問）か `ndf-ask:`（判断を求める質問）である。上から順に調べ、最初に当てはまった行に従う。

| 順 | 条件 | 結果 |
| ---: | --- | --- |
| 1 | 区分が無い | 通す |
| 2 | 人のいない実行（環境変数 `NDF_FACTORY_RUN` がある） | 通す |
| 3 | 記録のファイルを開けない、今の NDF より新しいバージョンの行がある、リポジトリの名前が決まらない | 通す。hook の計測の記録に `reading: unreadable` を残す |
| 4 | `no_record` か `head_moved` に当たる | 止める |
| 5 | どれでもない | 通す。head を読めない PR があれば、計測の記録に `reading: no_head` を残す |

- 記録のファイルがまだ無いときは、記録が 0 件として順 4 で止める。git の失敗と、リモート追跡ブランチが手元に無いときは、止めずに順 5 で通す。guard の処理そのものが失敗したときも通す（`fail_closed` は偽）
- head を比べるのは、`ndf-gate:` の質問で、使う記録に PR があるときだけである。git を 1 回だけ起動する。使える時間は、`hook.git-rev-parse` の 0.4 秒と、hook の締め切りから余白を引いた残りの、小さいほうである。質問を転送する次の guard（`ask-forward`）の時間を残すためである。残りが無ければ git を起動しない
- **同じ区分・同じ理由で止めるのは、利用者が次に入力するまでに 2 回までである。** 3 回目からは、記録が足りないという注意を添えて通す。同じ理由の拒否を数える仕組み（`hook.deny-repeat`）の働きなので、止める理由の文は区分と足りないものの語だけで決め、質問の文を入れない
- 止めた質問は人に出ない。`ask-forward` も、止まった質問を中継とオーガナイザー（並行する作業の質問をまとめて出す AI）の質問のファイルに書かない
- 環境変数 `NDF_HOOK_OFF` に `reading-check` を入れると（複数ならコンマ区切り）、この guard は働かない
- Codex には `AskUserQuestion` が無いので、この guard は動かない。承認の質問の前に手順の中で打つ `ndf records reading check` だけが確かめる

### 常に成り立つ条件

| # | 条件 | 破れたときの扱い |
| --- | --- | --- |
| I1 | 基準の本文は `writing-criteria.md` だけにある。手順書はリンクし、プログラムは読み込んで指示に入れる | レビューで指摘し、書き写した側をリンクに直す |
| I2 | 読み手役に、文書を書いた経緯と、使わない言葉の一覧を渡さない | `prompt` は、`files`・`reader`・`questions_kind` のほかのキーを受けない |
| I3 | 記録に、文書の本文・質問の文・引用を書かない | スキーマに無いキーは `add` が拒む |
| I4 | 記録を調べられないことを理由に、質問を止めない | hook は通し、計測の記録に残す |
| I5 | hook が使うコード（`reading_decide`）は、標準ライブラリだけで書く | `ndf check` が、hook から import してよいモジュールの表（`contracts/hooks/imports.json`）と比べて落とす |

## 決定と理由

| 決定 | 理由と、採らなかった案 |
| --- | --- |
| 共通原則の 1 文、指示に入れる基準の本文、確認の記録の 3 つに分けて置く | 原則だけでは、文書を書く AI の指示に入らない。指示だけでは、従わなかったことに誰も気づかない |
| hook で文の良し悪しを判定しない | 言葉の有無では、通じるかを判定できない。hook から AI を起動すると、hook の時間の上限に収まらない |
| 基準を 1 つの Markdown ファイルに置き、場所ではなく本文を指示に入れる | 場所を渡すだけでは、読んだかを確かめられない。レビューする AI は、作業ディレクトリの外のファイルを読めるとは限らない。`document-style` の本文に置くと、ほかの規則の分までレビューのたびに費用がかかる |
| 言葉の選び方を、「開発に関わる文書かビジネス文書か」ではなく読み手の表で決める | 要求仕様書は非エンジニアと PM も読む。要求仕様書だけを別の分類に移す案では、承認資料などにエンジニアの言葉が残る |
| 基準 6 を major と minor に分ける | すべて major にすると、好みに近い指摘が出続けてレビューが終わらない。すべて minor にすると、判断を誤らせる文も直されない |
| 2 ラウンド目以降の major を限る指示を、コードで強制しない | 指摘された行が差分にあるかをコードで調べるには、どの基準の指摘かを返させる項目が要る。行番号の無い指摘は調べられない |
| 要点の言い直しだけで合格にしない。通じない文が 0 件になるまで続けることもしない | 差し戻された文書でも、要点は言い直せた。挙がる件数は読み手役ごとに変わるので、0 件を条件にすると終わらない |
| 読ませるのを、組み直しの後と承認の前の 2 つにする | 組み直しの後だけでは、レビューで直した文と質問の文が読まれない。CI で行うには、AI の認証情報と費用を CI に持たせることになる |
| 2 回目にも残った文があっても質問を出せる | 合格だけを認めると、残った文があるときに、承認する人に尋ねられなくなる |
| hook は GitHub に問い合わせず、リモート追跡ブランチの head と比べる | hook の時間の上限に収まらないことがある。GitHub の head とは、承認の手順の `check` が比べる |
| 止めるのは 2 回までとし、区分と理由で数える | 記録ができるまで止めると、読み手役を起動できない環境で、人に尋ねる手段が無くなる。質問の文ごとに数えると、文を直すたびに数え直しになる |
| 記録の使える範囲を、作業の識別子や期限で絞らない | 同じ質問の文で同じ head なら、同じ記録を使ってよい。絞るには、文書のコピーの保管と削除の仕組みが要る |
| 使わない言葉を機械で探す検査を作らない | 登録した言葉しか見つからない。利用者が差し戻した文には当たらなかった |

## 運用

### 既知の限界

| 項目 | 内容 |
| --- | --- |
| 記録が事実かは確かめられない | 読み手役に本当に読ませたかは、記録からは分からない。PR を記録に書き忘れても hook では分からず、承認の手順の `check` で `no_pr` になる |
| 2 回止めた後 | 同じ区分・同じ理由の別の質問も、記録が無いまま通る。そのたびに、注意が会話に残る |
| 指示に基準が入らない起動 | `ndf worker run` を通さずに起動した worker（サブエージェントの `ndf:worker` など）の指示には、本文が自動では入らない。起動する側が読ませる手順書 `document-style` からのリンクで基準を読ませる |
| PR の題と本文 | 読み手役の対象ではない。head が同じまま書き換えても、記録は有効なままである |
| 指示に従わない AI | 2 ラウンド目以降の制限は指示だけなので、外れた major の指摘はそのまま残る。ラウンドの上限（既定 3 回）で終わる |

### 費用と揺れの実測（2026-11-24）

| 項目 | 実測 |
| --- | --- |
| 指示の長さ | 基準の本文の分だけ、1 回あたり約 110 行（約 5,200 文字）長くなる。トークンの増加は、Codex（gpt-6.2-sol）で 4,225、Claude（claude-opus-5-5）で 4,853 だった |
| cross-review | 基準 6 が働いたレビュー 1 回は 3 ラウンド（上限）回った。基準 6 の指摘は major 3 件・minor 6 件で、上限に達したときに残った major は 0 件だった。major はすべて Codex が挙げた |
| 読み手役 | 同じ設計書を 3 回読ませると、「判断や作業を誤らせる文」は 7・5・5 件で、3 回とも挙がったのは 2 か所だった。1 回の費用は 0.33〜0.40 ドル、時間は 72〜99 秒だった |

ほかの PR でのラウンド数と費用、Codex と Kiro CLI の重さの違いが続くかは、まだ分からない。

## テスト観点

テストは `plugins/ndf/tests/` にある。手順書と基準の文言を照合するテストは書かない。

| 観点 | テスト |
| --- | --- |
| 文書を含む PR の 2 つの指示にだけ基準が入り、含まない PR の指示は変わらない。文書があるかは PR の全体の差分で決める。基準を読めなければ起動しない | `domains/crossreview/test_crossreview_documents.py` |
| major を限る文が、比較元のあるラウンドにだけ入る。レビューする AI を加えたときと、head が巻き戻ったときは入らない。差分のファイルはラウンドに 1 つである | 同上 |
| `document-style` を読む作業の worker にだけ基準が入り、読めなければ起動しない | `worker/test_rules.py` |
| 読み手役への指示に、読み手と 4 つの型が入り、経緯を受け取らない。記録の形の違いを拒み、文を残さない。`check` が GitHub の head と比べ、読めなければ `unknown` になる | `domains/records/test_reading.py` |
| hook が、区分の無い質問・人のいない実行・開けない記録・git の失敗で通し、記録が無いときと head が違うときに止める。3 回目は注意を付けて通す。止めた質問を転送しない | `domains/hooks/test_reading_check.py` |
