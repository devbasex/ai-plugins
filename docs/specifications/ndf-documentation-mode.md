# ビジネス文書のワークフロー（`documentation` モード）

提案資料・稟議書・定例報告・指標の定義・運用マニュアル・説明資料を作る工程を、開発の工程表へ
5 番目のモードとして足した決定を残す。

**手順と表は各 Skill が正である。** ここに書き写さない。この文書が扱うのは、そこに書かない
決定の理由である。

## 概要

**中間形式を Markdown にしてリポジトリへ格納する。** そこから slide / ページ / 文書 / 表計算へ
生成する。この 1 点が工程の持ち方をすべて決める。

| これで成り立つもの | なぜ |
| --- | --- |
| 工程が git に載る | 執筆の産物がファイルになる。`worktree` `pr` `merged` がそのまま効く |
| レビューが差分でできる | `cross-review` が Pull Request の差分を外部 AI へ渡す経路に乗る |
| 企画承認が既存の工程になる | 構成案を載せた Pull Request を執筆より先にマージする |
| 生成先を後から選べる | ソースが体裁を持たないため、同じソースから複数の形へ出せる |

**軸は 3 つで、別々に変わる。** 1 つへ潰すと値の数が 6 × 4 × 5 に膨らむ。

| 軸 | 値 | 持つ場所 |
| --- | --- | --- |
| 文書タイプ | 6 | 判定は `development-workflow`、中身は `document-drafting` |
| 出力の形 | スライド / 文書 / 表計算 / ページ | 決めるのは `design`、生成するのは `release` |
| ドキュメンテーションシステム | Google Drive / Notion / Confluence / SharePoint / リポジトリ自身 | `document-systems` |

**承認の関門は 2 つのままである。** 新しい関門を作らない。

## 用語

| 用語 | 意味 |
| --- | --- |
| 正本 | リポジトリに置く Markdown。生成の入力になる |
| 企画承認 | 構成案と体裁設計を載せた設計 Pull Request のマージ |
| 制作物承認 | `production` が真の提出先への操作 |
| 下書き先 | `production` が偽の提出先。承認の前に書き込んでよい唯一の場所 |
| 決定的な経路 | 変換器を使う生成。同じ入力から同じ生成物が出る |
| 非決定的な経路 | AI エージェントが組む生成。同じ入力から同じ生成物が出ない |
| 実績 / 見込み / 概算 | 数値に付ける区別の語。実績にだけ出所を必須にする |

## 背景

**ビジネス文書は、担当した AI ごとに成果物が変わっていた。** 何という文書に何を書くかの規約が
無く、出所の無い数値がそのまま提出されていた（実在の提案資料では出所を書く列の 20 行以上が
空だった）。

**実在の文書はすべて外部のシステムにある。** 新規の文書にしか適用できないなら、既存の改訂が
対象外になる。

## 決定と理由

### 工程表を分けない

18 行 × 5 列のうち、`documentation` 列の対象外は 1 セル（構造改善）だけである。分けると
`worktree` `cross-review` `pr` `merged` と同じ規約が 2 箇所へ書かれる。

### 工程の行を 2 つ増やす

「工程表の行は増やさない」の例外にした。**どちらも判定の手段が既存の行と違う。** 素材の収集は
文書の外（数値の出所）を見て、体裁レビューは描画した画像を見る。既存の行へ畳むと、文字を
読む判定と描画を見る判定が同じ行に同居する。

**行を増やすかどうかは、工程が増えるかではなく判定の手段が既存の行に収まるかで決める。**
収まるものは既存の行の中の段にした（事実確認が `完了判定` の段になったのがその例である）。

### `documentation` の高さを 5 にする

**根拠は工程の数ではない。** 工程表で必須を数えると `standard` が 16 個、`documentation` は
14 個で、最多ではない。

根拠は**混在が分割し損ねた状態であること**にある。`documentation` の列にしかない必須の工程は
2 つあり、`standard` の側で検査すると一度も求められない。**文書が混ざっていること自体が表に
出ない。**

**高さはモードを上げる判断の根拠にしない。** `standard` から `documentation` への変更は、
重くなったのではなく対象が変わったのである。

### リポジトリの説明文書は対象外である

**判定を分けるのは読み手である。** `README.md` と `docs/` はリポジトリを読む人へ向けたもので、
`light` として扱う。ファイルの形式では分けない（どちらも Markdown である）。

### 承認の前に書き込んでよいのは下書き先だけである

**本番の提出先ごとに、対になる下書き先が要る。** 対の下書き先は `system` が同じでなければ
ならない。系が違うと、承認した生成物をそのまま移せず作り直しになり、**承認したものと届くもの
が別になる**。

**「偽の提出先がどこかに 1 つある」では足りない。** 解決できないときは提出の工程で止める。

### 生成物の内容は、描画とは別に照合する

体裁レビューが見るのは版面だけであるため、非決定的な生成で数値が変わったり本文が欠けたりしても
描画では表に出ない。**生成した後・制作物承認の前に生成物を取り込み、正本と差分で突き合わせる。**

**不一致のときは正本を直さず、生成をやり直す。** 正本が誤っていたと分かったときだけ執筆へ戻る。

### 生成の経路に既定を置かない

変換器と AI エージェントのどちらが良いかは、出力の形と求める見栄えで変わる。**選んだ経路が
「生成物を保存するか」の答えを決める**（非決定的な経路では、ソースから復元できないため保存する）。

### 出所は本文の節へ置き、無い値を拒否しない

frontmatter は生成の経路で落ち、別ファイルは生成物に含まれない。**読み手が確かめられなければ、
出所を書いた意味が無い。**

出所を必須にすると見込みと概算を書けなくなる。代わりに 3 語で区別し、**実績にだけ出所を必須に
する**。

### 事実確認は書いた本人だけでは完了しない

書いた側が確かめると、同じ思い込みで通る。**`cross-review` のレビュワーが、出典の節と本文の値を
突き合わせる。** 新しい仕組みは作らず、レビューの観点として渡す。

### 描画できない・画像を読めないときは止める

体裁レビューは制作物承認（取り消せない）の手前にある。**判定できないまま通すと、版面を一度も
見ないまま提出へ進む。** 止めたうえで、人が描画結果を見て承認する経路を残す。

**配布の可否と、判定できないときの倒し方は別である。** `layout-review` は 4 ランタイムすべてへ
配る。配らないと、そのランタイムでは工程が存在しないことになり、止まったことにも気づけない。

### 取得の手段を作らない

`google-drive` が Drive の取得を持ち、システムごとの手順は `document-systems` が持つ。
`document-sources` が決めるのは**出所の残し方だけ**である。取得の手段を持つと、システムが
増えるたびに太る。

### 既存の実装を移植せず、知識として書き起こす

Confluence と SharePoint の実装は別のリポジトリにあり、自リポジトリ前提を含む。
`system-<名前>.md` が持つのは手順と落とし穴だけで、スクリプトは持ち込まない。

## 仕様

### 工程表

18 行 × 5 列。`documentation` 列の対象外は `構造改善` の 1 セルだけである。増やした 2 行は
`素材の収集と出典の確定`（`設計` の後）と `体裁レビュー`（`配布` の後）である。

**工程名の並びは 5 箇所で一致する。** `SKILL.md` の工程表 / `WF_STAGE_MATRIX` / `PJ_STAGES` /
`projects-tracking.md` の対応表 / `parallel-work.md` の「工程が動く単位」。

### 判定の順序

`operation` → **`documentation`** → `standard` → `legacy-refactor` → `light`。
最初に該当したモードを採る。`documentation` を `standard` より前に置くのは、文書の中に公開
インタフェースの説明が含まれても `standard` にしないためである。

### 文書タイプ（2 段目の判定）

提案・企画 / 決裁・稟議 / 定例報告 / 指標定義 / 運用マニュアル / 説明・研修。
**境界は「読み手に何を求めるか」で切る。** 同じ内容でも、採否を求めれば提案、承認を求めれば
決裁である。

### 承認の 2 つの関門

| 関門 | 文書での意味 | 引き金 |
| --- | --- | --- |
| 設計 Pull Request のマージ | 企画承認 | head のブランチ名 `design/` + ラベル `design-approved` |
| 本番の系へ届く操作 | 制作物承認 | 提出先の `production` が真 |

**制作物承認の提示物には、生成物を描画した画像と、生成物と正本の内容照合の差分を含める。**
文字だけでは体裁を承認できない。

**取り消しの手段は共有の解除と版の差し戻しで、限界は「既に見た人には効かない」ことである。**

### 配布は生成と提出の 2 段である

```text
生成（下書き先へ） → 内容照合 → 体裁レビュー → 制作物承認 → 提出（本番の提出先へ）
```

提出は「置くこと」ではなく「読み手が辿れること」で完了する（索引への登録を含む）。
**公開範囲は設定した後に取得し直して突き合わせる。**

## データ・設定

### `.ndf/document.json`

**無ければ何も起きない。** 提出の工程が「提出先が宣言されていない」と伝えて止まる。

| キー | 何を書くか |
| --- | --- |
| `source_root` | 正本を置く根。リポジトリの根からの相対パス |
| `destinations[].system` | `gdrive` / `notion` / `confluence` / `sharepoint` / `repo` |
| `destinations[].production` | 真なら本番の系。届く操作が制作物承認の関門になる |
| `destinations[].draft` | 本番の提出先が指す、対になる下書き先の `name` |
| `destinations[].visibility` | 期待する公開範囲。提出の後にこの値と突き合わせる |
| `destinations[].auth` | 認証の**出所**（環境変数の名前や秘密情報の管理系の識別子）。**値は書かない** |
| `index` | 索引への登録先。無ければ登録を飛ばす |

形と書き方は
[`document-destinations.md`](../../plugins/ndf/skills/development-workflow/references/document-destinations.md)
が正である。

### 出典の 4 項目

場所 / 位置 / 時点 / 手段。**URL だけでは同じ値へ戻れない**（スプレッドシートは値が後から
変わり、画面は絞り込みの条件で表示が変わる）。

### 配布 Skill

新設は 4 個（`document-systems` / `document-sources` / `document-drafting` /
`layout-review`）で、**4 つの manifest すべてに載る**。

## 運用

### 未確認のまま残ること

| 項目 | 状態 |
| --- | --- |
| 往復（外部 → Markdown → 生成 → 外部） | **未実測。** 生成の手段がまだ無い。実測できるまで、既存文書の取り込みは 1 件で止める |
| Confluence / SharePoint | **このリポジトリで実行していない。** 別のリポジトリの実装の知識から書いた |
| ページを描画して見る手段 | Notion / Confluence / SharePoint は**未確認**。無いときは `layout-review` が止める |
| 画像を読めるランタイム | **未実測。** 4 つとも配り、読めないときは止める側へ倒した |
| コメントの取り込み | **未確認。** 取り込まないを既定にした |

### リポジトリの外に残る作業

**盤面（GitHub Projects）の単一選択へ、新しい 2 工程と `documentation` の値を足す必要がある。**
リポジトリの変更では完結せず、足りない値は書き込み時に弾かれる。
