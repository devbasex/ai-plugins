# 承認待ちの間の作業と業務時間: 答え待ちの停止でも承認の要らない作業を進め、業務時間外の承認の依頼を朝にまとめて示す

## 概要

**並列の計画のループのレーンは、答え待ちの停止の範囲に入っても、承認の要らない作業があればそれを進める。** 止めるのは新しい承認を生む作業だけである。
**業務時間を進め方の宣言（`.ndf/pace.json` の `business_hours`）に書くと、業務時間外は設計を作り溜め、届いた承認の依頼を溜めて、業務時間の始めに 1 回でまとめて示す。**

例: 業務時間を平日 09:00〜18:00（`Asia/Tokyo`）と宣言した並列の計画で、夜にレーン l1 が設計 PR の承認の依頼を、レーン l2 が問いを送る。

| 時刻 | 起きること |
| --- | --- |
| 22:00 | オーガナイザーの `parallel.py wait` は 2 件の依頼を返さず、`.ndf/parallel/<計画名>/deferred.json` に溜める。今問う依頼が無いため終了コード 3 で返り、待ちの上限は翌朝 09:00 で切れる |
| 23:00 | l1 は答え待ちの停止の範囲に入っているが、承認した設計の課題が残っているため、その実装をループの 1 回として始める。設計を承認していない課題は選定で外す |
| 翌 09:00 | 業務時間に入った後の最初の `wait` が、答えていない依頼の全件を `metrics.batch: true` で返す。設計の承認には課題の題・設計 PR の URL・MVV 判定の結果が付く |

開発ループの選定と止まる条件の全体は [ndf-workflow-development-loop.md](ndf-workflow-development-loop.md) が、オーガナイザーの待ちと答えの全体は [ndf-parallel-organizer.md](ndf-parallel-organizer.md) が持つ。
答え待ちの停止の閾値（`parallel.answer_limit`）は [ndf-development-loop-limits.md](ndf-development-loop-limits.md) にある。この文書は、業務時間の判定・答え待ちの停止の範囲での選定・依頼の溜め方の決まりと理由を持つ。

## 用語

語の定義は用語集（ [docs/glossary.md](../glossary.md) ）が正である。この文書で使う主な語は次のとおり。

| 用語 | この文書での使い方 |
| --- | --- |
| 業務時間 | 進め方の宣言の `business_hours` が表す時間帯。宣言が無い・不正なら常に業務時間内として扱う |
| 新しい承認を生む作業 | ループの 1 回のプランに設計のステップ（設計承認ゲート）を含む作業。開発ループでは、設計を承認していない課題すべてがこれに当たる |
| 承認の要らない作業 | 新しい承認を生む作業以外。開発ループでは、承認した設計の実装と、答えの届いた保留したループの 1 回の残り |
| 溜めた依頼 | 業務時間外に `parallel.py wait` がオーガナイザーへ返さずに控えへ書いた、レーンが送った設計の承認（`gate1`）と問い（`ask`）の依頼 |

## 背景

| 決めたこと | 理由 |
| --- | --- |
| 「設計を要る課題」を、ループの 1 回が設計のステップを置く規則と同じ関数（`design_issues`）で決め、選定の分類にも使う | ループの 1 回は、設計を承認していない課題にモードに依らず設計のステップを置く。モードは選定の後に決まるが、設計のステップの有無は選定の時点で決まる。分類と組み立てを 1 つの規則にすれば食い違わない |
| 業務時間は IANA の時刻帯・曜日・始まり・終わりの 4 項目で書き、時刻帯を必須にする | 判定を実行するマシンの時刻帯に依らせないため。営業時間（schema.org の `OpeningHoursSpecification`）や通知の時間帯（PagerDuty の Support Hours）と同じ組で、利用者が別の製品で書く形と揃う |
| 日をまたぐ宣言と UTC のオフセットは受けない | 夜勤の時間帯の需要は確かめていない。オフセットは夏時間で変わる |
| 祝日と休暇は宣言に入れない | 国と地域の選び方・休暇の書き方が加わり、宣言と検査が大きくなる。祝日に止めたいときは `days` を書き換えて済む |
| 不正な宣言は、一部の項目を既定へ戻さず、宣言全体を無いものとする | 一部だけ既定へ戻すと、利用者が書いていない時間帯で判定が動く。閾値（`parallel.answer_limit`）には安全な既定があるが、業務時間には無い |
| 依頼を溜める判定は `parallel.py wait` に置き、耐久ワークフローは変えない | 依頼の一覧とイベントの再生は耐久ワークフローが持つ。`wait` はオーガナイザーへ返す内容を決める最後の場所で、返さない依頼を控えに書けば済む。業務時間の始まりの契機は、待ちの上限をその時刻で切って作る（耐久ワークフローに時計の役を持たせない） |
| 答え待ちの停止は、保留したループの 1 回の残りを流した後に判定する | 答えの届いた残りは承認の要らない作業で、先に止まると流れない。新しい承認を生む作業は選定で外れるため、止める範囲は広がらない |
| 答えを受けたループのレーンは、答え待ちの停止の範囲の中でも起こす | 設計の承認の答えは、承認した設計の実装（承認の要らない作業）を生む。起こしたレーンは境で選び直し、承認の要らない候補が無ければ同じ条件で止まり直す。1 スプリントのレーンは承認の要らない作業の選び方を持たないため、今のまま起こさない |
| 溜めるのは `gate1`・`ask` だけにする | 答え待ちの停止のレーンの閾値が数えるものと一致する。リリース承認ゲートと、耐久ワークフローが立てた運用の問い（起動の失敗など）は、溜めると復旧が業務時間まで遅れる |
| 承認前の設計での試作は行わない | token の費用と引き換えになるため |

## 仕様

### 業務時間の判定

- 判定は `plugins/ndf/scripts/lib/pace.py` の `hours_state(宣言, 時刻)` が、宣言の時刻帯だけで行う。地方時（`datetime.now()`）を読まない
- 業務時間内は「`days` に入る曜日で、`start` ≦ 時刻 < `end`」である。業務時間外のときは、次の業務時間の始まり（`next_start`。UTC の ISO 8601）も返す
- 宣言が無い・不正なら `declared: false`・`inside: true` を返し、時間外の振る舞いへ入らない
- 夏時間の切り替わりで存在しない時刻を `start` にした宣言は、切り替え前のオフセットで読む（`zoneinfo` の振る舞い。日本の時刻帯では起きない）
- 判定はループの 1 回の境（選定の前）と `parallel.py wait`・`answer` でだけ行う。動いているプランと流れているリリースは、業務時間の境や閾値をまたいでも止めない

### 答え待ちの停止の範囲での選定

ループの 1 回の境の順と止まる条件の表は [ndf-workflow-development-loop.md](ndf-workflow-development-loop.md) にある。この変更が足した決まりは次のとおり。

- 答えのまだ無い待ち（人の判断待ち）の課題は、候補の枠を使わない。承認待ちの課題があっても、別の候補を選んでループの 1 回が始まる
- 答え待ちの停止は、すぐ止まる条件（`user_stop`・`mvv_changed`）に入れない。届いた答えと保留したループの 1 回の残りを流した後に、範囲に入っているかを読む
- 範囲に入っていれば、設計を要る課題を理由「答え待ちの停止の範囲（新しい承認を生む作業）」で外して選ぶ。選べたループの 1 回は `hold_only: true` を持つ
- 選べる課題が無ければ、今と同じく `answer_hold` で止まり、ループの 1 回を開かない
- `hold_only` のループの 1 回で、設計を承認していない課題を含めて `loop sprint` を打つと、組まずに終了コード 2 で断る。`loop exclude` で選び直しても `hold_only` を引き継ぐ
- `answer_hold` で止まったループは、範囲に残っていても再開で解く。承認の要らない候補があるかは次の境の選定が決める

### 業務時間外の選定の順

業務時間外は、枠を「承認した設計 → 設計を要る課題 → 設計の要らない課題」の順に割り当てる。同じ組の中は順位の順である。
業務時間内は今の順（承認した設計と直しの先頭 → 品質の枠 → 順位）のまま。

開発ループの中では設計を承認していない課題すべてに設計のステップが置かれるため、「設計の要らない課題」の組は、ループの 1 回の組み方が変わるまで空になる。

### 依頼の溜め方（`parallel.py wait`・`answer`）

| 場合 | `wait` の終了コード | 返すもの |
| --- | --- | --- |
| 業務時間内で、控えの `ids` が空でない | 0（待つ前に返す） | `action: questions`。`items` は答えていない依頼の全件、`metrics.batch: true`。`gate1` の行に `title`（課題の題）・`url`（設計 PR）・`verdict`・`mvv` が付く |
| 業務時間外に依頼が届き、今問う依頼がある | 0 | `items` は今問う依頼だけ。`metrics.deferred: {count, until}` |
| 業務時間外に依頼が届き、今問う依頼が無い | 3 | `summary` に溜めた件数と業務時間の始まり。`next` は同じ `wait --after <seq>` |
| 業務時間外の待ちが業務時間の始まりに達した | 0 | 1 行目と同じ（待ちの上限を次の業務時間の始まりで切る） |
| 宣言が無い・不正 | 今と同じ | 今と同じ。控えを読み書きしない |

業務時間外に「今問う依頼」は、`gate1`・`ask` 以外の依頼と、まだ返していない MVV 判定を試せる設計の承認（`mvv.eligible`）の 2 つである。
後者は 1 回だけ返し、オーガナイザーが MVV 判定で再判定する。承認以外なら利用者へ問わずに同じ `wait` を打ち直し、その依頼は業務時間の始めのまとめに入る。
`title`・`url` を `gh` で引けなければ `null` にし、`metrics.annotate_errors` に件数を載せる。

`parallel.py answer` の `metrics.after`（答えの後に残る依頼）にも同じ振り分けを通す。業務時間外は溜めた依頼を `after` に出さず、`metrics.deferred` に件数を載せる。

答えた依頼の持ち主がループのレーンなら、答え待ちの停止の範囲でも `metrics.next` に `relay.py restart <レーン>` の 1 行を返す。1 スプリントのレーンは今と同じく起こさず `metrics.held_owners` に載せる。

### 業務時間の宣言の警告

宣言が不正なら、`loop start`・`parallel.py check`・`parallel.py start` が `items` に次の 1 行を足す。`loop start` は警告を出しても始める。

```json
{"level": "warning", "rule": "business-hours", "at": "business_hours", "message": "<理由>"}
```

### 常に成り立つ条件

| 条件 | 破れたときの扱い |
| --- | --- |
| 答え待ちの停止の範囲で始めたループの 1 回は、設計のステップを持たない | `loop sprint` が組まずに終了コード 2 で断る |
| 選定で承認の要らない作業とした課題は、組んだスプリントで設計のステップ（`--design`）に入らない | 分類と組み立てが同じ `design_issues` を読む |
| 宣言が無い・不正なときの判定は業務時間内で、時間外の振る舞いへ入らない | 警告を出し、宣言なしとして進む |
| 業務時間の判定は、宣言の時刻帯と判定する時刻だけで決まる | 判定の関数は地方時を読まない |
| 溜めた依頼は捨てない。業務時間内に入った後の最初の `wait` が、答えていない依頼の全件を 1 回で返す | 控えは依頼の一覧を id で参照するだけで、依頼そのものは一覧に残る。オーガナイザーが問わずに終わっても `wait --after 0` が返す |
| 業務時間外に `mvv.eligible` の依頼を返すのは 1 回だけ | 控えの `offered` が持つ。返した依頼は `ids` にも入れ、答えが届くまで外さない |
| 一度示した `gate1`・`ask` は、答えないまま業務時間外へ入っても溜め直さず、問いもしない | 控えの `shown` が持つ。示し済みは id で判定し、`wait --after` の seq は使わない（seq は依頼ごとの番号ではない） |

## データ・設定

### 業務時間の宣言（`.ndf/pace.json`）

```json
{
  "version": 1,
  "business_hours": {"timezone": "Asia/Tokyo", "days": ["mon", "tue", "wed", "thu", "fri"], "start": "09:00", "end": "18:00"}
}
```

| 項目 | 規則 |
| --- | --- |
| `business_hours` | 任意。無ければ宣言なし。オブジェクトでなければ不正 |
| `timezone` | 必須。IANA の名前で、`zoneinfo.ZoneInfo` で読めなければ不正 |
| `days` | 必須。`mon`〜`sun` の 1 個以上の配列。知らない語・重複は不正 |
| `start` / `end` | 必須。`HH:MM`（00:00〜23:59）。`start` が `end` 以降なら不正 |

契約は `plugins/ndf/contracts/settings/pace.json.json` にある。値は利用者が書き、AI は書かない。

### ループの記録（`.ndf/loop/<名>/loop.json`）に足す項目

| 置き場 | 項目 | 中身 |
| --- | --- | --- |
| ループの 1 回 | `hours` | `{declared, inside, timezone, at}`。選定のときの判定 |
| ループの 1 回 | `hold_only` | 答え待ちの停止の範囲で始めたなら `true` |
| ループの 1 回 | `answer_hold` | 範囲のとき、止める指示の値（`{plan, scope, count, limit}`） |
| 選定の行（`decision: dropped`） | `reason` | 範囲で外した課題は `答え待ちの停止の範囲（新しい承認を生む作業）` |

`loop select` の結果の `metrics` にも `hours` と、範囲なら `answer_hold` を載せる。項目の無い古い記録は `hours` 無し・`hold_only: false` と読む。

### 溜めた依頼の控え（`.ndf/parallel/<計画名>/deferred.json`）

```json
{"version": 1, "ids": ["l1-g2950-ab12cd34ef56"], "offered": [], "shown": ["l1-g2948-0f1e2d3c4b5a"], "since": "2026-11-10T13:05:00Z", "until": "2026-11-11T00:00:00Z"}
```

| 項目 | 中身 |
| --- | --- |
| `ids` | 溜めた依頼の id。業務時間外に 1 回返した `mvv.eligible` の依頼も入る |
| `offered` | 業務時間外に 1 回だけ返した `mvv.eligible` の依頼の id |
| `shown` | 業務時間内の `wait`・`answer` が利用者へ示した `gate1`・`ask` の id |
| `since` / `until` | 溜め始めた時刻と、次の業務時間の始まり（UTC）。`ids` が空なら `null` |

- 書くのは `parallel.py wait`・`answer` だけで、業務時間の宣言があるときだけ書く。コミットしない
- 業務時間内の `wait`・`answer` は、`ids`・`offered` を空にし、示した `gate1`・`ask` の id を `shown` へ足す
- 書くたびに、依頼の一覧に無い（答えた）id を `ids`・`offered`・`shown` から外す
- 読めなければ空と読み、依頼の一覧から作り直す。示し済みの依頼も溜めた依頼に入り、次のまとめでもう一度示す（時間外に問う方へは倒さない）

## テスト観点

- 承認待ち（人の判断待ち・保留したループの 1 回）の課題があり、選べる候補が別にあるとき、`loop select` がその候補を選び、ループの 1 回が始まること
- 答え待ちの停止の範囲で承認した設計があれば `selected` を返し、承認していない課題が範囲の理由で外れ、結果に `answer_hold` が載ること
- 答え待ちの停止の範囲で、答えの届いた保留したループの 1 回の残りが流れること（停止を残りの処理より先に判定すると落ちる）
- 範囲で承認した設計が無ければ `answer_hold` で止まり、再開の印が置かれ、ループの 1 回が開かれないこと
- 時刻帯が無い・読めない名前・`25:00`・始まり ≥ 終わり・知らない曜日の宣言で、`check`・`start`・`loop start` が `business-hours` の警告を出し、判定が宣言なしと同じになること
- 宣言の無いリポジトリで、既存の選定・`wait`・答え待ちの停止のテストが通り、控えが書かれないこと
- 時刻を固定した業務時間外の選定で、承認した設計 → 設計を要る課題 → 設計の要らない課題の順に枠が割り当たり、業務時間内は今の順であること
- 業務時間外に届いた `gate1` が `wait` から返らずに控えへ入り、業務時間に入った後の最初の `wait` が全件を `batch: true` で返し、各行に `title`・`url`・`verdict`・`mvv` が付くこと
- 業務時間外の `wait` の待ちが、次の業務時間の始まりで切れること
- 同じ UTC の時刻に対し、環境変数 `TZ` を変えても `hours_state` の結果が同じであること
- 動いているループの 1 回があるとき、答え待ちの停止と業務時間の境をまたいでも止まらないこと
- `hold_only` のループの 1 回で、承認していない課題を含めて `loop sprint` を打つと終了コード 2 で断ること
- 選定が承認の要らない作業とした課題が、`new_sprint_argv` の `--design` に入らないこと
- 控えを書いた後にオーガナイザーが問わずに終わっても、`wait --after 0` が依頼を返すこと
- まとめて示した依頼に答えないまま業務時間外へ入ると、その依頼は溜め直されず `wait` からも返らず、後から届いた `gate1` は溜まること
- 控えが読めないとき、業務時間外の `wait` が答えていない `gate1`・`ask` を溜め、業務時間のまとめに入れること
- `mvv.eligible` の依頼が業務時間外に 1 回だけ返り、答えないまま業務時間に入ると最初の `wait` のまとめに入ること
- 業務時間外の `answer` の `metrics.after` に溜めた依頼が出ず、業務時間内の `answer` が示した依頼を次の `wait` がまとめて返し直さないこと
- 答え待ちの停止の範囲にあるループのレーンへ答えると `metrics.next` に起こす 1 行が返り、1 スプリントのレーンでは返らないこと
- リリース後の確かめ方: 業務時間を宣言した並列の計画で、時間外に設計の承認の依頼を 2 件以上溜め、業務時間の始めの `wait` が 1 回でまとめて示すことを見る

テストは `plugins/ndf/scripts/tests/` の `test_pace_hours.py`・`test_sprint_loop_hold_select.py`・`test_parallel_defer.py`・`test_parallel_hold_lanes.py` にある。
