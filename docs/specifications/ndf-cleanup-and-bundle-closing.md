# 後片付けを止めずに通し、まとまりの課題を終わりの工程で閉じる

マージ後の後片付け（`merged`）が、戻せる操作のために利用者を止めないようにした。あわせて、
正式版と開発版のチャネルを分けたリポジトリで、まとまりの課題を閉じる時点を **終わりの工程を
出るとき** の 1 つに決め、その手順を `progress-tracking` の 1 か所に置いた。この文書は、決めた
ことの理由と、書く側と読む側が共有する記録の形を残す。

**手順は各 Skill の `SKILL.md` が正である。** 止まる条件の一覧・退避のコード・閉じる手順の
コード例をここへ書き写さない。

| 何を読むか | 正本 |
| --- | --- |
| 実行前確認の要否を決める 3 つの問い、守り方 3 つ、適用表 | `plugins/ndf/skills/AUTHORING.md` の「実行前確認の要否を決める 3 つの問い」 |
| 後片付けの手順、止まる条件、無視されたファイルの退避、作業完了報告の項目 | `plugins/ndf/skills/merged/SKILL.md` |
| 工程の単位と記録する課題、まとまりを閉じる手順と結果の 4 値、配布の記録の読み方 | `plugins/ndf/skills/progress-tracking/SKILL.md` の「工程の単位と記録する課題」「まとまりを閉じる」 |
| 配布の記録を書く形と置き場所 | `plugins/ndf/skills/release/SKILL.md` の「出力物」 |
| リリース後テストの記録の形（`課題` の列） | `plugins/ndf/skills/release-verification/SKILL.md` の「出力物」 |
| 関門の外で実行前確認を足さない原則 | `plugins/ndf/skills/development-workflow/SKILL.md` の「人手の承認を求める関門」 |

## 概要

**実行前確認を置くかどうかは、3 つの問いで決める。** 失うと戻せないものを git やサービスが
拒まずに消すか、他者が読む新しい内容を外へ出すか、操作そのものが判断を問うか。どれか 1 つでも
「はい」なら置き、すべて「いいえ」なら置かずに事後に対象と戻し方を報告する。

**後片付けが止まるのは git が拒んだときだけである。** 作業ツリー・ローカルブランチ・Pull
Request の head のリモートブランチは、同意を求めずに消す。拒まれた対象は最後に 1 回だけ
一覧で示す。無視されたファイルは消さずに退避し、退避が 1 件でも失敗した作業ツリーは同意の
有無にかかわらず消さない。

**まとまりの課題は、終わりの工程を出るときに閉じる。** 閉じる条件は「本番への配布まで済んで
いる、または配布を飛ばした」と「リリース後テストを通る経路では受け入れ条件がすべて `合格`」の
2 つで、課題ごとに見る。`merged` は課題を閉じない。

**配布の記録は Pull Request に置く。** `release` の出力物は会話に出るだけで別の実行からは
読めないため、書く側の形を 1 つに決め、読む側はその形だけを読む。

## 用語

| 用語 | 意味 |
| --- | --- |
| 実行前確認 | Skill の手順の途中で、操作の対象を示して利用者の同意を得ること。関門（承認）とは別枠 |
| 関門 | `development-workflow` の「人手の承認を求める関門」の 2 つ（設計 Pull Request のマージ / 本番の系へ届く操作） |
| 取り消せる操作 | 失う状態を git 自身が拒むか、事後の手段（ハッシュからの復元・Restore branch・reopen）で元へ戻せる操作 |
| まとまり | 1 回の配布で出す変更の集合（`parallel-work.md` の定義。マイルストーンがこれに当たる）。単独の変更は 1 件のまとまり |
| まとまりの課題 | まとまりに含まれる Pull Request の本文が、閉じる語で指す課題 |
| 終わりの工程 | その実行で最後に通る工程。振り返りを通るなら `retrospective`、通らずリリース後テストを通るなら `release-verification`、どちらも通らなければ `release` |
| 進行側 | まとまりの最後のマージを行う側（`release` の「担い手」） |
| チャネルを分けたリポジトリ | 開発の起点（`base_branch`）と本番のチャネル（`production_branch`、無ければ既定ブランチ）が別のブランチであるリポジトリ |
| 配布の記録 | `release` が Pull Request へ残す `## 配布の記録` のブロック。段階・版・まとまりの Pull Request を持つ |
| 未完了 | 無視されたファイルの退避が 1 件でも失敗した作業ツリーの結果。止まる対象とは別で、同意の対象に含めない |

## 背景

**後片付けで止まる回数が多すぎた（#561）。** `merged` は削除の対象を一覧で示して同意を取って
から消していたが、worktree の削除・`git branch -d`・マージ済み Pull Request の head の削除は
どれも戻せる。戻せる操作のために止まると、無人で進める運転（`/goal`）が後片付けで毎回止まる。

**まとまりの課題を閉じる時点が 4 つに割れていた（#623）。** 手順の記載（起点へのマージで
閉じる）・v10.11.0 の運用（振り返りの記録の後）・GitHub の自動クローズ（既定ブランチへの
マージ）・盤面の自動化（Status を Done にすると閉じる）が別々の時点を指した。v10.11.0 では
コミットメッセージに `Closes` を持つ 2 件だけが `main` へのマージで閉じ、まとまりが 2 件と
12 件に割れた。

git 2.53.0 の実測が境界を決めた。upstream があり squash でマージしたブランチは、リモートの
ブランチが消えた後の `git branch -d` で `not fully merged` と拒まれる（終了コード 1）。
未追跡ファイルを持つ worktree の `git worktree remove` は終了コード 128 で拒まれるが、
**無視されたファイルだけを持つ worktree は終了コード 0 で、無視されたファイルは確認なしに消える。**

## 決定と理由

**実行前確認の要否は 3 つの問いで決める。** #561 の提案は「実際に取り消せるか」の 1 つだった
が、それだけでは `pr` の push と `out-of-scope` の起票も取り消せる（閉じる・消す）ため確認が
外れる。問い 2（他者が読む新しい内容を外へ出すか）は関門 2 と同じ「見た人は戻らない」性質、
問い 3（判断を問うか）は判断そのものへの同意である。1 問に例外の一覧を添える形は、例外の理由が
書き手ごとに増えるため採らなかった。**課題を閉じることは問い 3 に当たらない。** 閉じる判断は
まとまりの工程を通ったことで済んでいる。

**止める合図は git の拒否だけにし、`-D` の代わりになる判定を NDF の側に作らない。** 先端が
Pull Request の `headRefOid` と一致すれば `refs/pull/<番号>/head` から戻せるため `-D` で自動に
消す案もあったが、NDF の判定を安全の網にすると二重の確認が形を変えて残る。止まった一覧に
一致の有無と戻し方を並べ、判断の材料を揃える。

**起点・本番のチャネル・現在のブランチは、同意を求めずに対象から外す。** 起点から本番へ出す
Pull Request では `merged` の対象が起点ブランチそのものになる。消してよいかを尋ねる場面が
作られること自体が誤りで、1 回の誤答で開発の本流が消える。

**同意なしに消すリモートブランチは、同じリポジトリにあるマージ済み Pull Request の head で、
先端が `headRefOid` と一致するものに限る。** マージの後に積まれたコミットは Restore branch で
戻らない。先端が違う・対応する Pull Request が無いときは、同意を得ても戻せないため消さずに
対象外として報告する。

**無視されたファイルは消さずに退避してから作業ツリーを消す。** 止める条件にすると
`__pycache__` を持つほぼすべての作業ツリーで止まる。退避は `git status --ignored --porcelain=v1 -z`
の `!! ` の値を NUL 区切りで読み、同じ相対パスで
`<共通の git ディレクトリ>/ndf/worktree-trash/<ブランチ名の / を __ に置換>-<YYYYmmddHHMMSS>` の
下へ移す。改行区切りでは空白・引用符・改行・非 ASCII を含むパスが引用されて `mv` が実在しない
パスを指す。**1 件でも失敗したら残りを移さず、作業ツリーを消さない。** 止まる側へ積むと最後の
一括の同意で `--force` へ進めてしまい、退避しきれなかったファイルが消える。退避先は自動では
消さず、容量を報告に載せて利用者が消す。

**後片付けは、まとまりの最後か判断できなくても待たない。** 判断が要るのは配布を始める時点で
あり、確認は `release` の開始条件（まとまりのすべての Pull Request がマージされている）が持つ。

**まとまりの課題は、まとまりの終わりの工程を通った時点で閉じ、`merged` では閉じない。**
開いている課題が「利用者へ届いて確かめるまでが終わっていない」を表し、配布・リリース後テスト・
振り返りの記録を開いた課題へ書ける。「マージで閉じ、記録を続ける」は盤面の `Item closed` で
起点へのマージ時に Done になり、配布で問題が出ても課題の一覧に出ない。「盤面の自動クローズを
正とする」は盤面の設定しだいで時点が変わる。**本番への配布とリリース後テストの合格を閉じる
条件にする。** 検証への配布は「提示して進めてよい」段階で、利用者が常用する版にまだ届いて
いない。不合格・保留の課題を閉じると、確かめていないことが終わったように見える。

**閉じる手順は `progress-tracking` の 1 か所に置き、盤面を Done にしてから OPEN のものだけを
閉じる。** 終わりの工程はモードで 3 つに分かれ、どれかへ置くと残りへ写しが要る。盤面を先に
書くのは `Auto-close issue` の有無によらず終わりの状態を揃えるためで、その前に状態を読んで
控えるのは、Done で閉じた課題を `既に閉じていた` ではなく `閉じた` と数えるためである。
**終わりの工程で Done を書くのはこの手順だけである。** 工程の入口の進行の記録で Done を
書くと `Auto-close issue` が先に閉じ、reopen の手段が報告から落ちる。**閉じられなければ
止まる。** 進行の記録は失敗しても工程を止めないが、閉じる操作は #623 の目的そのもので、
黙って通すと OPEN が残ったまま終わりに見える。

**コミットメッセージに閉じる語を書かない。** `main` へのマージは終わりの工程より前に来ること
があり、全件が早く閉じる。Pull Request の本文の閉じる語は残す（作成の時点の案内が本文を入力に
している）。

**記録は工程を行った側が、工程の単位に含まれる課題すべてへ書く。** v10.11.0 では担当が記録
した工程で止まり、進行側が行った工程が 14 件とも空欄だった。まとまりの課題は本文の閉じる語
から集める。マイルストーンから引く案は、このまとまりで直さない課題も割り当てられ得るため
採らなかった。**別の配布の記録とは版で対応づけ、版の無い `配布なし` の記録とは投稿の順で
対応づける。**

**関門の節には原則を 1 文で足し、`development-workflow/SKILL.md` の行数を増やさない。**
基準の中身は `AUTHORING.md` が持つ。

## 仕様

### 常に成り立つ条件

- 関門は 2 つで、増えない（`development-workflow/SKILL.md` の関門の表が 2 行）
- `plugins/ndf/skills/*/SKILL.md` のうち `gh issue close` と `status "Done"` を書くのは
  `progress-tracking` だけである
- `merged` は課題を閉じない。閉じる語が指す課題のうち OPEN のものを報告に載せるだけである
- 起点・本番のチャネル・現在のブランチは、同意の有無にかかわらず削除の対象に入らない
- 退避が 1 件でも失敗した作業ツリーは、同意の有無にかかわらず消さない（`--force` も使わない）
- 止まらずに行った削除は、すべて完了報告に戻し方つきで載る

### 実行前確認の守り方

| 守り方 | 選ぶ条件 | 実装 |
| --- | --- | --- |
| 明示指示専用 | 問いのどれかが「はい」で、明示起動が定着している | 実行前確認を持つ |
| 自動発動 + 実行前確認 | 問いのどれかが「はい」で、自然文で依頼される | 実行前確認を持つ |
| 自動発動 + 事後の報告 | 3 つとも「いいえ」 | 実行前確認を置かず、止まる条件（git やサービスの拒否）だけを本文に書き、消した対象と戻し方を完了報告の必須項目にする |

`merged` は「自動発動 + 事後の報告」で、`pr` / `release` / `out-of-scope` / `issue-upkeep` /
`official-skills-autoloader` は「自動発動 + 実行前確認」のままである。どの問いに当たるかは
`AUTHORING.md` の適用表が持つ。

### 後片付けの止まる条件

| 対象 | 止めずに行う | 止まる | 触らない（対象外） |
| --- | --- | --- | --- |
| 作業ツリー | `status --porcelain` が空で、無視されたファイルを退避した後の `git worktree remove` が 0 で終わる | `status --porcelain` が空でない、または `git worktree remove` が 0 以外 | — |
| ローカルブランチ | `git branch -d` が 0 で終わる | 同じコマンドが 0 以外 | 起点・本番のチャネル・現在のブランチ |
| リモートブランチ | マージ済み Pull Request の head で、同じリポジトリにあり、先端が `headRefOid` と一致する | — | 起点・本番のチャネル・fork の head・先端が違う・対応する Pull Request が無い |
| 課題 | 閉じない | — | — |

止まる対象は最後に 1 回だけ示す。見つけるたびに止まると、止まる回数が拒否の件数だけ戻る。
未完了は同意の対象に含めず、完了報告の「未完了」へ載せる。

### まとまりを閉じる

**終わりの工程を出るときに 1 度だけ行う。** 工程に入った時点で呼ぶ進行の記録とは契機が違う。
検証への配布で止めた実行も同じ流れを通り、課題は閉じる条件に当たらず `開いたまま` になる。

| 呼ぶ Skill | 呼ぶ時点 | 呼ぶ条件 |
| --- | --- | --- |
| `retrospective` | 記録を投稿した後 | 振り返りを通る変更 |
| `release-verification` | 検証結果を記録した後 | 後に振り返りが続かない変更 |
| `release` | 「蓄積した課題を手入れする」の前 | 後にリリース後テストも振り返りも続かない変更 |

いずれも「まとまりを閉じる → `issue-upkeep`」の順で呼ぶ。

| # | 閉じる条件 | 満たさないとき |
| --- | --- | --- |
| 1 | 本番への配布まで済んでいる、または配布を飛ばした（配布の記録の `段階:` が `本番` または `配布なし` で始まる） | まとまりの課題すべてを OPEN のまま残す。`段階:` の行が無ければ `開いたまま（配布の記録が読めない）` |
| 2 | リリース後テストを通る経路では、その課題の受け入れ条件がすべて `合格` | `不合格`・`保留` の条件を持つ課題を OPEN のまま残す |

まとまりの課題は、まとまりの Pull Request ごとに本文の閉じる語から集める（`closing-issues.sh`）。
**一覧が空なら推測せずに止まる（終了コード 1）。** 番号を省いた `gh pr view` は現在のブランチの
Pull Request を選ぶため、別のまとまりの課題を閉じうる。

課題ごとの手順は、盤面を書く前に状態を読んで控える → 記録のリポジトリの課題なら盤面を Done に
する → 状態を読み直して OPEN のときだけ `gh issue close` → もう一度読み直して CLOSED を確かめる、
の 4 段である。**最初の読みに失敗した課題は `失敗（before を読めない）` にし、盤面を触らずに次の
課題へ進む。** **結果は最後の読み直しで決め、`gh issue close` の終了コードでは決めない。** 盤面の
自動化は非同期で、OPEN と読んだ直後に自動化が閉じると close が 0 以外を返しうる。

| 結果 | 条件 |
| --- | --- |
| `閉じた` | 最初の読みが OPEN で、最後の読みが CLOSED（盤面の自動化が閉じた場合と、close が 0 以外で終わった場合を含む） |
| `既に閉じていた` | 最初の読みが CLOSED（既定ブランチへのマージで GitHub が先に閉じた場合を含む） |
| `失敗（理由）` | 最後の読みが CLOSED でない、または読み取りが 0 以外で終わった |
| `開いたまま（理由）` | 閉じる条件に当たらない |

**`失敗` が 1 件でもあれば、終わりの工程を完了と報告せず、`issue-upkeep` を呼ばずに止まる。**
`開いたまま` は失敗ではなく、`issue-upkeep` へ進んでよい。

**他のリポジトリの課題には盤面を書かない。** `projects-sync.sh` は `--repo` を取らず、実行した
リポジトリの盤面で番号を引くため、他のリポジトリの番号を渡すと同じ番号の別の課題を更新する。

### 工程の単位と記録する課題

| 工程の単位 | 記録する側 | 記録する課題 |
| --- | --- | --- |
| 課題 | その課題を扱う担当 | その課題 |
| Pull Request（後片付けを含む） | その工程を行った側。後片付けはマージした側 | その Pull Request の本文の閉じる語が指す課題すべて |
| まとまり（確定仕様化・配布・体裁レビュー・リリース後テスト・振り返り） | その工程を行った側。配布以降は進行側 | まとまりの課題すべて |

通過工程の控えを読む検査は Pull Request の作成の時点と後片付けの報告までしか読まないため、
配布以降の記録は 1 回の実行で課題を並べてよい。後片付けまでの記録は課題ごとに 1 回の実行にする。

## データ・設定

### 配布の記録

| 記録 | 形 | 置く側 | 置き場所 |
| --- | --- | --- | --- |
| 配布の記録 | 見出し `## 配布の記録` の直後に `段階: <検証 / 本番 / 配布なし>（…）`・`版: <前の版> → <新しい版>（<根拠>）`・`まとまり: PR #<番号> / #<番号>` の行が続くブロック。`配布なし` のときは `版:` を書かない。終わりは次の `## ` 見出しか入力の終わり | `release` | 配布の Pull Request の本文。Pull Request を作らない配布の形と配布を飛ばしたときは、まとまりの最後にマージした Pull Request へコメントで投稿する |
| リリース後テスト | `## リリース後テスト` から `合否:` までのブロック。`対象の版: <配布した版>（<配布した時刻>）` の行と、列が `課題` / 受け入れ条件 / 実行したこと / 実行時刻 / 結果 の表を持つ | `release-verification` | 配布の記録を置いた Pull Request へコメントで投稿する |

読む側は、本文とコメントを 1 つの出力として時刻順に読み、**最後の `## 配布の記録` ブロック 1 つ
だけ**を使う。`段階:` が `本番` で始まるときは `版:` の `→` の後を本番の版として取り、`対象の版:` の
`（` の前が**完全一致**する最後のリリース後テストのブロックを読む（前方一致にすると
`10.15.0-dev.1` も当たる）。`配布なし` のときは、その記録より後に投稿された最後のブロックを読む。
表の `課題` の列が無い、または空欄の行があるときは、まとまりの課題すべてを
`開いたまま（条件と課題の対応が読めない）` にする。

### 盤面の自動化

このリポジトリの盤面では `Item closed`（閉じると Done）と `Auto-close issue`（Done で閉じる）の
両方が有効である（`gh api graphql` の `projectV2.workflows`）。他のリポジトリでは片方だけ、
または両方無効のことがあり、閉じる手順はどの組み合わせでも終わりの状態が同じになる。

## 運用

**人が書いたコミットメッセージの閉じる語は防げない。** `pr` を通るコミットだけに効く。
手で書いたコミットに閉じる語があると、既定ブランチへのマージで早く閉じる。

**Codex / Kiro / agy は自分の承認設定で `git push --delete` などを止めることがある。** NDF の
手順が止めなくても、ランタイムの設定で止まる回数は変わらない。

**退避先の容量は増え続ける。** いつ消すかは利用者が決める。レビュー用の作業ツリーはシステムの
一時ディレクトリにあり、共通の git ディレクトリと別のファイルシステムのことがあるため、`mv` が
複製になる。

**チャネルを分けないリポジトリでは、既定ブランチへのマージで GitHub が先に閉じる。** 「まとまりを
閉じる」は `既に閉じていた` を数えるだけで、二重に閉じようとしても結果は変わらない。
