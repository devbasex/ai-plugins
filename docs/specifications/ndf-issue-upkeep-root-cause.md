# 課題を根本原因の場所で直す区分（ルートコーズ）

溜まった課題の棚卸（`issue-upkeep`）に、課題を現れている場所ではなく根本原因の場所で直すと
決める区分「ルートコーズ」を置いた。あわせて、どこを直すかという構造の判断の担い手を、4 つの
Skill の境界に書いた。この文書は、決めたことの理由と、実測で確かめた事実を残す。

**手順は各 Skill の `SKILL.md` と `references/` が正である。** 区分の並び・条件・書き方を
ここへ書き写さない。

| 何を読むか | 正本 |
| --- | --- |
| 8 つの区分の並び、用語、手順 1 / 2A / 2B / 3、判断と見る対象の表 | `plugins/ndf/skills/issue-upkeep/SKILL.md` |
| ルートコーズの条件、手順 3 での対応、修正レイヤーの決め方、採る手、親 issue と子 issue | `plugins/ndf/skills/issue-upkeep/references/grouping.md` |
| 「やらない」の条件 2 の行き先 | `plugins/ndf/skills/issue-upkeep/references/no-work.md` |
| 直近のマイルストーン、親 issue の割り当て | `plugins/ndf/skills/issue-upkeep/references/milestones.md` |

## 概要

**目的は根本原因を直すことで、同じ原因を持つ課題をまとめるのはその手段である。** 区分の
条件は「修正レイヤーが現象レイヤーと違う」の 1 つに置き、件数を条件にしない。件数が決めるのは
記録の持ち方だけで、同じ修正レイヤーを指す課題が 2 件以上あり、直しても個別の作業が残るときに
親 issue を 1 件つくる。

実例は 2026-09-16 の棚卸である。未解決の 62 件から、同じ修正レイヤーを指すクラスタが 4 つ
見つかった。

| クラスタ | 修正レイヤー / 採る手 | 子 issue | 親 issue |
| --- | --- | --- | --- |
| 失敗・欠落を黙って捨てる | 失敗・欠落の扱いを決める共通の層 / 新設 | #671 #577 #459 #684 #642 #653 | #716 |
| 配布済みの版と開発中の版が食い違う | 実行する版を解決する層 / 統合 | #459 #590 #658 #534 | #715 |
| 打ち切りの後に部分的な結果が失われる | 担当の結果を保持する層 / 新設 | #548 #583 #584 #619 | 未処理 |
| 待ち方と起動の形が Skill ごとに決まっている | 起動と待ちの規則を持つ層 / 統合 | #560 #656 #680 | 未処理 |

## 用語

| 用語 | 意味 |
| --- | --- |
| 現象レイヤー | 課題が実際に現れている場所。ファイル・クラス・層のいずれかで書く |
| 修正レイヤー | 原因を直すべき場所。その責務を持つべき場所までさかのぼる |
| ルートコーズ | 修正レイヤーが現象レイヤーと違う課題に付ける区分 |
| クラスタ | 同じ修正レイヤーを指す課題の集まり |
| 親 issue | クラスタの修正レイヤーを直すために新しくつくる課題 |
| 子 issue | クラスタに属する既存の課題。親 issue をつくった後も閉じない |
| 採る手 | 修正レイヤーへの直し方。移動 / 統合 / 新設 / 向きの修正 / 分離 の 5 つ |

**用語は外来語由来のものを採る。** 一般語（束ねる・群・かたまり・グループ）は読み手ごとに
指す対象が変わる。**区分の名前（ルートコーズ）と作る課題の名前（親 issue）を分ける。**
1 つの語が 2 つの対象を指さないためである。親 issue と子 issue は GitHub 自身の語彙で、
機能もそのまま使う。

## 背景

**原因を残したまま個別に直すと、直した後に同じ形が別の場所で出る。** v10.13.0 ではレビューの
打ち切りの上限（#598 / #537）を直したが、打ち切りの後に部分的な結果が失われる機構
（#548 / #583 / #584 / #619）は直っていなかった。上限は引き金であって原因ではなく、原因の側を
指す記録が無かった。

**課題への判断は、価値（やるか）と構造（どこを直すか）の 2 種類ある。** 発見の瞬間の判断は
`out-of-scope` と `problem-solving` が持ち、溜まった課題の価値の判断は `issue-upkeep` の
「やらない」が持っていた。溜まった課題の構造の判断を、どの Skill も自分の役目と書いていな
かった。この升を「ルートコーズ」で埋め、判断と見る対象の表の正本を `issue-upkeep` に置いた。

## 仕様

### 区分の並び

**「ルートコーズ」は「重複」の次、「要判断」の前に置く。** どちらも課題をまたいで決まり、
手順 2B で確定する。「要判断」は自動で決められないものの受け皿で、末尾に置く。既存の区分へ
統合しないのは、閉じてよいものと閉じられないものが同じ区分になり、後から検索で区別できない
ためである。

### 常に成り立つ条件

- **ルートコーズの分岐は「要判断」へ倒さない。** 行き先は手順 2A の記録だけで決まる。区分は
  2 つ（ルートコーズ / 既存の区分のまま）、手順 3 での対応は 3 つ（その課題の本文へ書く /
  親 issue をつくる / 重複として正本へ寄せる）である。層を名指しできない・層がまたがる・手が
  1 つに決まらないときも同じで、人へ返しても人が見る材料は同じである
- **子 issue を閉じない。** 各課題の固有の再現手順が残り、原因を直した後も各所への適用が残る。
  原因が直った後の棚卸が、既存の「閉じてよい」で再現手順を実行して閉じる
- **親 issue は子 issue の中身を写さない。** 写すと同じ再現手順が 2 か所に残り、片方だけが
  古くなる
- **大きさの歯止めを区分の条件に置かない。** 層がまたがっても直さなければならないことは変わらない。
  分け方は着手の時点（マイルストーンの割り当てと実装計画）が決める

### 手順の分け方

**手順 2A はクラスタを決めない。** 複数人で分担し、他の課題の記録が見えないためである。控えるのは
現象レイヤーと修正レイヤーで、課題が書いている直し方をそのまま採らない見直しも同じ時点で行う
（起票は現象を見て書かれ、棚卸は一覧の全体を見る）。

**手順 2B は重複の突き合わせを先に行う。** 手順 3 での対応は「同じ課題ではない」ことを前提にする。
順序を逆にすると、条件が欠けたときの行き先が突き合わせの結果を待ち、区分の決定が循環する。

**手順 1 は閉じた親 issue の子 issue を拾う。** 子 issue は親と別のマイルストーンにいることがあり、
ほかの 3 経路（機械の候補・担当が足す・マイルストーン）では拾えない。

### 起票の例外

**「手入れ」は起票を含まず、例外は親 issue の起票 1 つだけである。** 親 issue は新しい発見では
なく、既存の課題から導かれる。発見の瞬間の判断を 3 択から増やさないのは、その時点では指摘の
周辺しか見えず、クラスタを判定する材料が無いためである。`retrospective` もクラスタの発見を
担わない。振り返りは 1 回の変更を見る。

### 既存の規則を直したところ

**区分の集合へ値を足すと、それまでの値だけを想定した規則が新しい値に当てはまらない。**

| 箇所 | 現行 | 理由 |
| --- | --- | --- |
| `no-work.md` の条件 2 の行き先 | 重複 / ルートコーズ / 寄せ先なし の 3 つ | 「重複」固定のままだと、同じ修正レイヤーを指す別の課題が重複として閉じられる |
| `no-work.md` の「要判断」へ倒す文 | 見積りである条件 1 だけに掛かる | 条件 2 は突き合わせの結果で、3 つの行き先で終わる |
| `milestones.md` の直近 | open のうち名前の先頭の連番が最も小さいもの。説明が別の着手の順序を書いていれば説明 | open のマイルストーンは版数を持たない（`AGENTS.md` の「版と配布の方針」） |
| `milestones.md` の着手の時期の語 | 「マイルストーン」 | 「ミッション」は `SKILL.md` で配布の単位（1 度にマージする Pull Request の集合）を指す |

### 親 issue の割り当て

**親 issue の重要度はクラスタの最高値を採り、重要度の規則を先に効かせる。** 高いものは直近の
マイルストーンへ入る。主題で決まるときだけ、子 issue が属するマイルストーンのうち最も早いものを
採る。原因を直すまでクラスタのどの課題も直らないためである。子 issue のマイルストーンは動かさない。
クラスタへ属したことは重要度を変えない。

## データ・設定

### 親子の結び付き

**既定は GitHub のサブイシュー関係である。** 多数のケースは 1 対多で、関係を張れば画面と API から
親子をたどれる。**2 つ目以降のクラスタと、サブイシューの API を持たないリポジトリだけ、子 issue の
本文へ親 issue を指す 1 行を足す。** 子 1 件が持てる親は 1 件だけである。

実測で確かめた形（2026-09-16、`devbasex/ai-plugins`）。

| 操作 | 形 |
| --- | --- |
| 親から子を引く | REST `GET repos/<所有者>/<リポジトリ>/issues/<親>/sub_issues` の配列 |
| 子から親を引く | GraphQL `issue(number:<子>){parent{number}}`。単数で、親が無ければ `null` |
| 結び付ける | REST `POST .../issues/<親>/sub_issues` に `sub_issue_id`。**渡すのは issue の番号ではなく、`GET .../issues/<子>` の `.id`（データベースの ID）** |
| 空の本文で結び付ける | 422 `Invalid input: data cannot be null.` |

**やり直しで 2 度行わない見分けは親 issue の側から引く。** 起票の要否はこの修正レイヤーを指す
親 issue の有無で、結び付けの要否はその親の子の一覧で決める。本文の 1 行だけでは決めない。
複数のクラスタへ属する課題では、1 行が別の親 issue を指していることがある。

### マイルストーンの名前

open は `<2 桁の連番> <主題>`、closed は `v<版数>` へ改名される。閉じたマイルストーンの連番は
名前に残らず、説明の「着手の順序: N 番目」に残る。2026-09-16 の closed 13 件のうち、連番の
名前で作られた 5 件（v10.7.0 / v10.8.0 / v10.10.0 / v10.11.0 / v10.12.0）が説明にこの行を持ち、
それより前に版数の名前で作られた 8 件は持たない。
open の `13` は説明に「次に着手する（05 より先）」と書き、連番と別の着手の順序を持っていた。

## 運用

**課題の本文と PR の本文を用語へ揃える。** 区分の名前で検索したときに起点の課題が漏れないため、
#712 / #713 の本文とタイトルも「ルートコーズ」「クラスタ」「親 issue」へ揃えた。

**直近の判定は、主題の違う長期のマイルストーンを選ぶことがある。** 2026-09-16 の open では直近が
`03 研究基盤`（研究の 2 件だけを持つ）になり、#715 / #716 は利用者の判断で `05` へ入れた。規則の
見直しは #718 が扱う。

## テスト観点

`plugins/ndf/skills/issue-upkeep/tests/test_issue_upkeep_layout.py` が、`SKILL.md` と参照の文字列を
直接照合する。

| 観点 | 満たすこと |
| --- | --- |
| 区分の並び | 区分の表が 8 行で、`ルートコーズ` を含む順序であること。その行から `references/grouping.md` へたどれること |
| 手順 | 手順 1 が 4 経路を持つこと。手順 2A が 6 点を確かめ、現象レイヤーと修正レイヤーを控え、クラスタを決めないこと。手順 2B が同じ原因を持つクラスタを突き合わせ、注記が重複と親 issue へ分岐すること |
| 条件と対応 | 条件が 1 つで件数が条件でないこと。手順 3 での対応が 3 つで、3 行目が重複との境目であること。`grouping.md` に「要判断」が無いこと |
| 親 issue と子 issue | 子 issue を閉じないこと、結び付けがサブイシュー関係を既定にすること、1 件が複数のクラスタへ属してよいこと、親 issue に書く 4 つ |
| 修正レイヤーと採る手 | 現象レイヤーと修正レイヤーの対応の例、さかのぼる層の数を決めないこと、5 つの手の呼び名が `refactoring/references/vocabulary.md` に実在すること |
| 承認 | 親 issue の起票と子 issue への書き込みが、一括で提示して承認を得る側にあること |
| 境界 | 判断と見る対象の表が価値と構造の担い手を示し、`out-of-scope` / `problem-solving` / `retrospective` / `release` がこの Skill を指すこと |
| 用語 | 4 語が用語の表にあり、置き換えた語が残っていないこと。`milestones.md` に「ミッション」「版数が最も小さい」「版数の順序」が無いこと |
| 既存の規則 | `no-work.md` の条件 2 が 3 つの行き先を持ち、「要判断」の文が条件 1 だけに掛かること |

GitHub 上の状態（親 issue の起票と結び付け）は自動テストにしない。リポジトリの外にあるためで、
`gh api .../sub_issues` と子 issue の本文の検索で確かめる。
