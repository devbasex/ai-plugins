# モードを判定する単位と、承認ゲート

開発ループでモードを判定する単位を Pull Request と定め、人手の承認を 2 つの承認ゲートへ集約し、
判定したモードに対する実行証跡を機械で見るようにした経緯と決定を残す。起動時の worktree の
設定の確認と、設計 Pull Request の本文の決めたことの突き合わせもここで扱う。

**手順と表は
[`development-workflow` の SKILL.md](../../plugins/ndf/skills/development-workflow/SKILL.md)
が正である。** ここに書き写さない。この文書が扱うのは、そこに書かない決定の理由である。

## 概要

**モードを判定する単位は Pull Request である。** 1 つの Pull Request に対しモードは 1 つで、
その Pull Request が閉じる課題すべての通過記録へ同じ値を書く。判定の入力になるため、工程の順序は
**要求と受け入れ条件 → モード判定 → 作業場所の用意**である。

**コードレビューは全モードで通る。** Pull Request を出す以上、その差分は誰かがレビューする。

**人手の承認を求める承認ゲートは 2 つで、増やさない。** 設計 Pull Request のマージと、**本番系へ
届く操作**である。後者はリリースと、運用モード（`operation`）の実行の両方を含む。

**判定したモードに対する実行証跡は、Pull Request を作る時点で機械が見る。** 記録の無い必須の
工程を案内するが、**拒否はしない**。

**`development-workflow` を起動したら、判定の手順 1 より先に worktree の設定を確かめる。**
設定が無ければ作ってから進み、状態を判定結果の出力へ残す。

**設計 Pull Request の本文は、設計文書の決定の見出しだけを写し、機械で突き合わせる。**

## 用語

| 用語 | 意味 |
| --- | --- |
| 通過記録 | 通過工程とモードを課題ごとに残すファイル。リポジトリの外に置く |
| 承認ゲート | 人手の承認を求めて工程を止める場所 |
| 本番チャネル | リリースした版が常用する利用者へ届くブランチ |
| 本番系 | 利用者が現に使っている配布のチャネル・環境・外部サービス。**チャネルは系の一種である** |
| ミッション | 1 つの版として出す課題と Pull Request のセット。マイルストーンの中から切り出す（マイルストーンは着手の順序を決める単位で、ミッションとは別） |
| 必須ルール | 分割と並行の手法を担当へ任せたうえで、それでも守る規則 |

## 背景

v10.5.0 は 22 件を 5 本の Pull Request へ束ねて通した。束の中の `standard` 3 件が束全体の
進め方に引きずられ、`cross-review` を通さないままリリースまで進んだ。リリースの後にレビューを行うと、
2 つの外部 AI がどちらも変更要求を返し、8 件の指摘が出た。

**進捗記録を一度も書かなかったため、工程の飛ばしを見る仕組みが一度も走らなかった。**
その仕組みはリリース記録を引き金にしており、記録が無ければ引き金も引かれない。

**束ねたときにどのモードを採るかは、規約では解けない。** 「最も高いモードを採る」という
規約を置く案は、規約を読む人が束の中身を数え直すことを前提にする。

## 決定と理由

| 決定 | 理由 |
| --- | --- |
| モードを判定する単位を Pull Request にする | 数える対象が 1 つになる。束ね方を変えても同じ判断が要らない |
| `light` のコードレビューを `cross-review` にする | レビューの深さをモードで変える根拠が無い。差分の小ささはラウンド数が吸収する |
| `light` にも要求と受け入れ条件を課す | 判定の入力になる。入力が無いまま判定する状態のほうが高くつく |
| 「モード判定」を工程表の行にしない | ボードへ記録する工程の値が増える。順序は本文で書ける |
| モードの高さを列の位置から導かない | 読みやすさのための並びが、高さの根拠として読まれる |
| 通過記録の鍵を課題番号のままにする | 判定の時点で Pull Request の番号はまだ無い。「1 つの Pull Request に 1 つのモード」は値の一致で表せる |
| 閉じる語の読み取りをライブラリへ移し、コピーを持たない | 同じ規則を 2 箇所に持つと、GitHub が構文を変えたときに直し忘れた側が残る |
| 実行証跡の欠落は案内にとどめ、拒否しない | 記録が無いことは、その工程を通っていないことと同じではない。記録の側が遅れているだけの状態で作成が止まると、正当な操作が止まる |
| チェックの終点を工程表の並びで決める | 記録済みの最も先の工程に置くと、Pull Request を作る時点では常にその手前であるため、欠落が 1 件も出ない |
| `実装レビュー` の工程だけは作成の時点で求めない | `cross-review` は Pull Request が無いと回せない。求めれば毎回欠落として出て、案内が読まれなくなる |
| `light` をチェックの対象から外さない | 必須の工程が少ないモードほど、通していないことが見えにくい。外すと `light` と申告するだけで回避できる |
| 承認ゲートを 2 つに集約し、増やさない | 増やすほど「承認したこと」の意味が薄れる。通過の回数が増えると、内容を読まずに通す動きが入る |
| 設計 Pull Request のマージはチャネルに依存させない | 承認するのは、この設計で実装へ進んでよいかである。この費用はマージ先で変わらない |
| 実装 Pull Request のマージを承認ゲートにしない | 要否を決めるのはマージ先のチャネルである。一律で止めると検証への反映まで止まる |
| ゲート 2 を「本番系へ届く操作」へ広げる | 運用モードの実行はリリースと同じ性質を持つ。反映した瞬間に効き、取り消しても「その状態を見た人」は戻らない。性質が同じものを別の承認ゲートとして数えると、数だけが増える |
| ゲート 2 の要否を「届く先が本番系かどうか」で決める | 運用モードの実行はマージ経路を持たないため、マージ先のチャネルでは判定できない。リリースの工程では両者の判定は一致する |
| 本番チャネルへ `production_branch` を新設し、`base_branch` を流用しない | `base_branch` は開発の起点である。流用すると、開発版のチャネルへのマージが本番の扱いになる |
| 分割・束ね方・並行度を担当の判断に任せる | 課題と Pull Request は 4 つの形を取る。すべてに手法の規約を書くと、書いた規約の数だけ判断が増える |
| 代わりに必須ルールを 6 つ定める | 任せることと、何をしてもよいことは別である。v10.5.0 の事故は束ね方ではなく、束ねた後にモードを見直す必須ルールが無かったことによる |
| 複数のマイルストーンは原則として順次にする | マイルストーンはリリースの単位であり、並行させるとどの版に何が入るかが確定しない |
| 設定の確認は `development-workflow` の本文の「判定の手順」の先頭（手順 0）に置く | `light` / `operation` は作業場所の用意を飛ばしうるため、`worktree` の工程に置くと確認が通らない。`guard.allow_paths` の例外の判定もモード判定の後にあり、その前でなければ既定値のまま進む |
| 設定が無くても拒否せず、状態を判定結果の出力の `宣言:` の行へ載せる | 機械で止める手段は tool 実行前の hook だけで、起動の時点に引き金が無い。案内だけで済ませると v10.5.0 のように飛ばしが表に出ないため、出力に行を残して呼び出し側が読めるようにする |
| 読めない設定のときだけは先へ進まない（承認は求めない） | 上書きすると書き加えた内容が消え、進めると運用が無効のまま進む。どちらも取り返しにくい |
| 判定できない（git・jq が無い、`$SCRIPTS` を決められない）ときは止めない | 止めても直す手段が本文の中に無い。測れなかったことを「あり」とも「なし」とも書かない |
| 設定の状態を分ける処理は `wt_declaration_state` の 1 関数だけに置く | `status` の分岐を残して `check` を足すと、基準が 2 か所になる。本文に `[ -f .ndf/worktree.json ]` を書くと、壊れた JSON と未対応の版を「あり」と読む |
| 設定の確認を `workflow-guard.sh` と frontmatter の `hooks` に置かない | Claude Code でしか働かず、起動の時点に引き金も無い |
| 設定を作る手は `worktree` の手順 0（`init`）のまま、`check` は読むだけにする | 作成の入口が 2 つになると、上書きしない扱いと `--force` を 2 か所で揃え続けることになる |
| 設定を作る前に承認を求めない | 承認ゲートは 2 つで増やさない。メインディレクトリの 1 ファイルで、コミットするまでは消せば戻る。`development-workflow` を起動したこと自体を運用を使う意思表示とする |
| `base_branch` / `production_branch` は推測で書かない | 正しい値はリポジトリの運用が決める。`check` の 2・3 行目と出力の `宣言: 作成した（…）` が既定ブランチへ落ちていることを示す |
| 設計 Pull Request の本文は決定の中身を持たず、決定の見出しだけを写す | 同じ決定を 2 か所が別の文で持つと片方だけが直る（PR #539 では決定の見出しが変わったのに本文が古いまま残った）。見出しは結論を 1 文で表すため、並べれば本文だけでも結論を追える。本文から決定を消すと、承認の提示と同じ一覧に届かない |
| 写した見出しはスクリプトで突き合わせ、ずれていれば節だけを書き直す | 変わったかの判定を担当に委ねると、手順を通らない直接の修正を拾えない。節の単位に限れば、人が書いた Summary と Test plan を壊さない |
| 突き合わせは承認の提示の直前を最後のゲートとし、`pr` と `fix` の後、継続的統合でも走らせる | 設計 Pull Request のマージはどの経路で直されても承認の提示を通る。前段で走らせるのは、承認の直前に初めて書き直すことを減らすためである。hook で止める形は agy がプラグインの `hooks.json` を読まず、4 ランタイムで同じに効かない |
| 対象の判定（head が `design/` で始まるか）はスクリプトが持つ | 呼び出し元 4 か所に同じ条件を書かない。実装の Pull Request は承認を通らず、確定仕様へ移す設計文書を含むことがある |
| 設計文書はファイル名ではなく `## 決定の記録` の節を持つかで見分ける | `design` はファイル名を決めていない。本文にパスを書かせると、突き合わせる対象を入力に使うことになる |
| 読めなかったときは一致と扱わず 2 を返す | 承認の提示で「一致した」と「確かめていない」を区別できなくなる |
| `cross-review` の手順は変えない | 修正と最終スイープは `fix` を呼び、最終スイープはどの終了経路でも走るため、ローテーションで作り直した本文もそこで `sync` を通る |
| 継続的統合の突き合わせは必須のチェックにしない | 必須にするのは ruleset の変更で、利用者の承認が要る。落ちたチェックは Pull Request の画面に出る |
| 進捗記録の取りこぼしは語の分割で直し、hook の登録には触れない | hook は発火していた。値に密着した `;` を値の一部として読み、工程名に無いとして黙って捨てていた（`"要求と受け入れ条件"; echo "exit=$?"` の形の 5 件がすべて積まれず、空白を挟んだ `2>&1` の形はすべて積まれていた） |
| 区切りは空の語で表す | 分割はそれまで空の語を出さないため、実在の語と衝突せず、読み手の受け方（`read -r -d ''`）も変わらない。演算子を語として出すと引用符で囲んだ `";"` と区別できない |
| 読み手は最初に見つけたコマンドの終わりで読むのを止め、2 つ目以降を読まない | 2 つ目以降を読むのは別の判断（進捗記録は #487、マージの判定は #581）である |
| リダイレクトの `&` は区切りにしない | `2>&1` は記録に残ったコマンドで最も多い書き方である。直前が `>` `<` か直後が `>` のときだけ語の一部として残す |
| 捨てた値を案内に出す変更は入れない | 工程名として読めない値を黙って捨てる出口は #459 と同じで、文言と条件を 2 か所で決めると食い違う |

## 仕様

### 判定の単位と工程の順序

工程の順序と、モードごとの要否は
[SKILL.md の「モードごとに起動する Skill」](../../plugins/ndf/skills/development-workflow/SKILL.md)
が持つ。**この表は 4 か所（工程表・対応表の 2 つの列・ボードの値の一覧）で並びまで一致する。**

**常に成り立つ条件**は 2 つである。

- **1 つの Pull Request に対しモードは 1 つである。** 鍵ではなく値の一致で表す
- **工程の並びは 4 か所で一致する。** 集合ではなく並びまで一致する

### 起動時の worktree の設定の確認

`development-workflow` の本文は、「判定の手順」の手順 1 より前に
`worktree-setup.sh check` を実行し、終了コードだけで分岐する。

| 終了コード | 状態 | 本文の指示 | 判定結果の出力 |
| --- | --- | --- | --- |
| 0 | あり | 手順 1 へ進む | `宣言: あり` |
| 2 | なし | `worktree` の手順 0（`init`）を通し、`check` が 0 を返してから進む | `宣言: 作成した（起点 <名前> / 本番 <名前>。未宣言なら既定ブランチ）` |
| 3 | 読めない | 進まない。`init --force` を実行せず、`check` の出力を示す | 出さない |
| 1、または `$SCRIPTS` を決められない | 判定できない | 止めずに手順 1 へ進む | `宣言: 判定できない（<理由>）` |

**`init` の後にもう一度 `check` を通す。** `init` の終了コード 0 は「作った」と「読める設定が既にある」の
両方を含み、判定結果の出力に載せる起点と本番の名前は `check` の 2・3 行目から取るためである（読めない
設定では `init` が 1 で終わる。#573）。

`check` は読み取り専用で、ファイルを作らず通信もしない。標準出力は人が読む 3 行（`宣言ファイル:` /
`開発の起点:` / `本番のチャネル:`）で、1 行目は `status` の同じ行と一字一句同じにする。2・3 行目は
設定に書かれた名前の実在を確かめない（確かめる関数は origin へ問い合わせうる）。

**起動していない会話の振る舞いは変えない。** 設定の無いリポジトリで `worktree-guard.sh` と
`worktree-session.sh` は何も出さずに終わる。他のリポジトリを巻き込まないための `worktree` の性質である。

### 承認ゲート

| 承認ゲート | いつ | 要否の決まり方 |
| --- | --- | --- |
| 設計 Pull Request のマージ | ドキュメントレビューの工程 | マージ先のチャネルによらず要る |
| 本番系へ届く操作 | リリースの工程、および `operation` の実装の工程 | 届く先が本番系かどうかで決まる |

**要否の決まり方が違うため、承認ゲートごとに節を分けて書く。** 並べて書くと、片方に掛かる規則が
両方に掛かって読める。本番リリースの要否の規則そのものは `release` が持ち、運用モードの
実行の規則は
[operation-run.md](../../plugins/ndf/skills/development-workflow/references/operation-run.md)
が持つ。

**ゲート 2 は 2 つの形を取る。** マージ先が本番チャネルであるリリースと、操作する先が本番系で
ある運用モードの実行である。**リリースの工程では、旧い基準（マージ先のチャネル）と新しい基準
（届く先が本番系か）の判定は一致する。** チャネルは系の一種であるため、既存の判定は
変わらない。

### 設計 Pull Request の本文の決めたこと

`plugins/ndf/scripts/pr-body-decisions.sh` が、本文の `## 決めたこと` の節と、設計文書の決定の
見出しを突き合わせる。

```text
pr-body-decisions.sh check <PR番号> [--repo <所有者>/<リポジトリ>]
pr-body-decisions.sh sync  <PR番号> [--repo <所有者>/<リポジトリ>]
```

| 終了コード | `check` | `sync` |
| --- | --- | --- |
| 0 | 一致した。または対象外（head が `design/` で始まらない） | 一致した（書き込まない）、または書き込んだ後の突き合わせで一致した。対象外も 0 |
| 1 | 食い違った。差分を標準出力へ出す | 書き込んだ後も食い違った |
| 2 | 読めなかった（`gh` が無い・Pull Request が無い・API の失敗） | 読めなかった、または書き込みに失敗した |
| 3 | 呼び出しの誤り。GitHub を読まない | 同左 |

| 規則 | 内容 |
| --- | --- |
| 設計文書 | Pull Request の変更したファイルのうち `removed` でない `.md` をパスの昇順に並べ、head のコミットから読む。コードフェンスの外の `## 決定の記録` から次の `# ` / `## ` の手前までにある `### ` の見出しを持つもの |
| 本文 | Pull Request の `body` から読む。手元の worktree にも、継続的統合のマージの試行のコミットにも左右されない |
| 節の範囲 | コードフェンスの外の行全体が `## 決めたこと` の行から、次の `# ` / `## ` の手前（無ければ末尾）まで |
| 節の形 | 設計文書ごとにパスの行と、`### ` の後ろをそのまま置いた `- ` の行。先頭に「手で書き換えない」のコメントを置く |
| 比べ方 | 行末の空白と節の前後の空行を除いた完全一致。`\r\n` は `\n` と同じに扱う |
| 書き直し | 節があれば範囲だけを置き換える（設計文書が無ければ取り除く）。無ければ `## Test plan` の直前、それも無ければ末尾へ足す。節の外は 1 バイトも変えない。REST の `PATCH pulls/<番号>` へ本文だけを送る |

| 呼び出し元 | 時点 | 副コマンド |
| --- | --- | --- |
| `pr` | 作成した直後 / 本文を更新した直後 | `sync` |
| `fix` | 返信と Resolve の後。コミットの有無によらない | `sync` |
| 承認の提示（[approval-request.md](../../plugins/ndf/skills/development-workflow/references/approval-request.md)） | 設計 Pull Request の提示を組み立てる前 | `check`、1 なら `sync`。2 なら「本文との一致: 未確認」と書く |
| 継続的統合（`.github/workflows/pr-body-decisions.yml`） | `pull_request` の `opened` / `synchronize` / `edited` / `reopened` | `check`。権限は `contents: read` / `pull-requests: read` だけ |

本文の節の書き方は [`pr` の SKILL.md](../../plugins/ndf/skills/pr/SKILL.md) が持ち、`design` の
SKILL.md はそこへ渡す。本文の自由文が決定を言い換えているかは機械では判定せず、レビューが拾う。

### 実行証跡の gate

`gh pr create` を tool 実行前の判定が観測し、本文の閉じる語が指す課題の通過記録を読む。

| 見るもの | 出すもの |
| --- | --- |
| モードの記録が無い | その旨 |
| 通過記録の行が 0 件 | その旨 |
| 工程表で `Pull Request` より前にある必須の工程に記録が無い（`実装レビュー` を除く） | 工程名の一覧 |
| 閉じる課題どうしでモードが食い違う | 最も高いモードと、食い違っていること |

**判定できないときは何も出さずに通す。** 本文を読み取れる形と読み取れない形は
[stage-completeness.md](../../plugins/ndf/skills/development-workflow/references/stage-completeness.md)
にある。**案内が出ないことは、工程を通っていることの裏付けにはならない。**

**tool 実行前の判定がコマンドの本文を読む読み手は 3 つで、読み方は共通である。** 進捗記録（通過記録を積む）・マージの判定（設計 Pull Request のマージを承認ラベルに縛る）・Pull Request の作成（この gate）である。
`wf_split`（`development-workflow/scripts/lib/workflow-common.sh`）が引用符を解いて語に割り、
引用の外の制御演算子を空の語（区切り）として出す。

| 本文の中の文字（引用の外） | 出力 |
| --- | --- |
| 空白・タブ | 語の終わり |
| `;` `\|` `(` `)` | 語の終わり + 区切り |
| `&` | 語の終わり + 区切り。ただし直前が `>` か `<`、または直後が `>` のときは語の一部（`2>&1` / `>&2` / `&>`） |
| 途中の改行 | 語の終わり。区切りは 2 行目以降の行頭で出す。最後の改行では出さない |
| 行末の `\` と改行 | 継続。区切りを出さない |
| 引用の中の上記すべて | 語の一部 |

| 読み手 | 対象を見つける前の区切り | 見つけた後の区切り |
| --- | --- | --- |
| `wf_parse_sync`（進捗記録） | 読み飛ばす | 読むのを止める。3 語そろっていなければ積まない |
| `wf_merge_target`（マージの判定） | 探索をやり直す | 読むのを止める。番号が無ければブランチから引き当てる |
| `_wf_pr_create_body`（Pull Request の作成） | 探索をやり直す | 読むのを止める |

分割は awk の 1 回の起動で行い、hook の制限時間に対して十分に短く保つ。

### 並行開発の必須ルール

**6 つある。** 内容と、機械が見るものと手順として書くものの振り分けは
[parallel-work.md](../../plugins/ndf/skills/development-workflow/references/parallel-work.md)
にある。**振り分けを書かないと、手順の側にある必須ルールが「機械が見ているはず」と読まれる。**

## データ・設定

**通過記録はリポジトリの中に置かない**（変更として Pull Request に載るため）。置き場所と JSON の
形は
[stage-completeness.md](../../plugins/ndf/skills/development-workflow/references/stage-completeness.md)
にある。**この版で形は変えていない**（`.repo` / `.issue` / `.mode` / `.stages`）。

**設定の状態は `wt_declaration_state <主ディレクトリ>`（`plugins/ndf/scripts/lib/worktree-common.sh`）が
分ける。** `wt_declaration` が読めれば `present`、読めずファイルが存在しなければ（`[ -e ]` が偽。壊れた
symlink を含む）`absent`、存在すれば（ディレクトリを含む）`unreadable` を 1 語で出す。`jq` が無いと
読める設定も `unreadable` になるため、呼び出し側が先に `jq` を確かめる。

**本番チャネルは `.ndf/worktree.json` の `production_branch` に書く。** 読み取りの順序は
設定 → 既定ブランチの 2 段階で、**`base_branch` は読まない**。設定が無いリポジトリは既定
ブランチを本番チャネルとして扱う。指定された名前が origin にもローカルにも無いときは、
既定へ落とさず解決に失敗する。

## 運用

**ボード（GitHub Projects）の単一選択の並びは、リポジトリ側の操作で揃える。**

**v10.5.1 では工程の値の集合は変わらず、並びだけが変わった**（`要求と受け入れ条件` が
`作業場所の用意` より前へ移った）。集合が同じであるため記録そのものは通った。

**v10.5.2 では集合が変わる。** `ドキュメント再構成` を足し、`設計レビュー` を
`ドキュメントレビュー` へ、`レビュー` を `実装レビュー` へ改名した。**後方互換の仕組みは
持たず、記録済みの値は移行で 1 度だけ書き換える。** ボードへ新しい値を足すのは、ボードを持つ
リポジトリ側の操作である（値が無くても `projects-sync.sh` は終了コード 0 で終わり、
工程は止まらない）。

**`light` の費用は上がる。** `cross-review` を全 Pull Request へ課したときの実行時間と費用は
まだ測っていない。次のミッションで実測する。
