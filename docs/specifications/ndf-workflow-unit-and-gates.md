# モードを判定する単位と、承認の関門

開発ループでモードを判定する単位を Pull Request と定め、人手の承認を 2 つの関門へ集約し、
判定したモードに対する実行証跡を機械で見るようにした経緯と決定を残す。

**手順と表は
[`development-workflow` の SKILL.md](../../plugins/ndf/skills/development-workflow/SKILL.md)
が正である。** ここに書き写さない。この文書が扱うのは、そこに書かない決定の理由である。

## 概要

**モードを判定する単位は Pull Request である。** 1 つの Pull Request に対しモードは 1 つで、
その Pull Request が閉じる課題すべての控えへ同じ値を書く。判定の入力になるため、工程の順序は
**要求と受け入れ条件 → モード判定 → 作業場所の用意**である。

**レビューは全モードで通る。** Pull Request を出す以上、その差分は誰かがレビューする。

**人手の承認を求める関門は 2 つで、増やさない。** 設計 Pull Request のマージと、**本番の系へ
届く操作**である。後者は配布と、運用モード（`operation`）の実行の両方を含む。

**判定したモードに対する実行証跡は、Pull Request を作る時点で機械が見る。** 記録の無い必須の
工程を案内するが、**拒否はしない**。

## 用語

| 用語 | 意味 |
| --- | --- |
| 控え | 通過工程とモードを課題ごとに残すファイル。リポジトリの外に置く |
| 関門 | 人手の承認を求めて工程を止める場所 |
| 本番のチャネル | 配布した版が常用する利用者へ届くブランチ |
| 本番の系 | 利用者が現に使っている配布のチャネル・環境・外部サービス。**チャネルは系の一種である** |
| まとまり | 1 回の配布で出す変更の集合。マイルストーンがこれに当たる |
| 下限 | 分割と並行の手法を担当へ任せたうえで、それでも守る規則 |

## 背景

v10.5.0 は 22 件を 5 本の Pull Request へ束ねて通した。束の中の `standard` 3 件が束全体の
進め方に引きずられ、`cross-review` を通さないまま配布まで進んだ。配布の後にレビューを行うと、
2 つの外部 AI がどちらも変更要求を返し、8 件の指摘が出た。

**進行の記録を一度も書かなかったため、工程の飛ばしを見る仕組みが一度も走らなかった。**
その仕組みは配布の記録を引き金にしており、記録が無ければ引き金も引かれない。

**束ねたときにどのモードを採るかは、規約では解けない。** 「最も高いモードを採る」という
規約を置く案は、規約を読む人が束の中身を数え直すことを前提にする。

## 決定と理由

| 決定 | 理由 |
| --- | --- |
| モードを判定する単位を Pull Request にする | 数える対象が 1 つになる。束ね方を変えても同じ判断が要らない |
| `light` のレビューを `cross-review` にする | レビューの深さをモードで変える根拠が無い。差分の小ささはラウンド数が吸収する |
| `light` にも要求と受け入れ条件を課す | 判定の入力になる。入力が無いまま判定する状態のほうが高くつく |
| 「モード判定」を工程表の行にしない | 盤面へ記録する工程の値が増える。順序は本文で書ける |
| モードの高さを列の位置から導かない | 読みやすさのための並びが、高さの根拠として読まれる |
| 控えの鍵を課題番号のままにする | 判定の時点で Pull Request の番号はまだ無い。「1 つの Pull Request に 1 つのモード」は値の一致で表せる |
| 閉じる語の読み取りを共通層へ移し、写しを持たない | 同じ規則を 2 箇所に持つと、GitHub が構文を変えたときに直し忘れた側が残る |
| 実行証跡の欠落は案内にとどめ、拒否しない | 記録が無いことは、その工程を通っていないことと同じではない。記録の側が遅れているだけの状態で作成が止まると、正当な操作が止まる |
| 検査の終点を工程表の並びで決める | 記録済みの最も先の工程に置くと、Pull Request を作る時点では常にその手前であるため、欠落が 1 件も出ない |
| 「レビュー」だけは作成の時点で求めない | `cross-review` は Pull Request が無いと回せない。求めれば毎回欠落として出て、案内が読まれなくなる |
| `light` を検査の対象から外さない | 必須の工程が少ないモードほど、通していないことが見えにくい。外すと `light` と申告するだけで回避できる |
| 承認の関門を 2 つに集約し、増やさない | 増やすほど「承認したこと」の意味が薄れる。通過の回数が増えると、内容を読まずに通す動きが入る |
| 設計 Pull Request のマージはチャネルに依存させない | 承認するのは配布の可否ではなく、この設計で実装へ進んでよいかである。この費用はマージ先で変わらない |
| 実装 Pull Request のマージを関門にしない | 要否を決めるのはマージ先のチャネルである。一律で止めると検証への反映まで止まる |
| 関門 2 を「本番の系へ届く操作」へ広げる | 運用モードの実行は配布と同じ性質を持つ。反映した瞬間に効き、取り消しても「その状態を見た人」は戻らない。性質が同じものを別の関門として数えると、数だけが増える |
| 関門 2 の要否を「届く先が本番の系かどうか」で決める | 運用モードの実行はマージ経路を持たないため、マージ先のチャネルでは判定できない。配布の工程では両者の判定は一致する |
| 本番のチャネルへ `production_branch` を新設し、`base_branch` を流用しない | `base_branch` は開発の起点である。流用すると、開発版のチャネルへのマージが本番の扱いになる |
| 分割・束ね方・並行度を担当の判断に任せる | 課題と Pull Request は 4 つの形を取る。すべてに手法の規約を書くと、書いた規約の数だけ判断が増える |
| 代わりに下限を 6 つ定める | 任せることと、何をしてもよいことは別である。v10.5.0 の事故は束ね方ではなく、束ねた後にモードを見直す下限が無かったことによる |
| 複数のマイルストーンは原則として順次にする | マイルストーンは配布の単位であり、並行させるとどの版に何が入るかが確定しない |

## 仕様

### 判定の単位と工程の順序

工程の順序と、モードごとの要否は
[SKILL.md の「モードごとに起動する Skill」](../../plugins/ndf/skills/development-workflow/SKILL.md)
が持つ。**この表は 4 か所（工程表・対応表の 2 つの列・盤面の値の一覧）で並びまで一致する。**

**常に成り立つ条件**は 2 つである。

- **1 つの Pull Request に対しモードは 1 つである。** 鍵ではなく値の一致で表す
- **工程の並びは 4 か所で一致する。** 集合ではなく並びまで一致する

### 承認の関門

| 関門 | いつ | 要否の決まり方 |
| --- | --- | --- |
| 設計 Pull Request のマージ | 設計レビューの工程 | マージ先のチャネルによらず要る |
| 本番の系へ届く操作 | 配布の工程、および `operation` の実装の工程 | 届く先が本番の系かどうかで決まる |

**要否の決まり方が違うため、関門ごとに節を分けて書く。** 並べて書くと、片方に掛かる規則が
両方に掛かって読める。本番への配布の要否の規則そのものは `release` が持ち、運用モードの
実行の規則は
[operation-run.md](../../plugins/ndf/skills/development-workflow/references/operation-run.md)
が持つ。

**関門 2 は 2 つの形を取る。** マージ先が本番のチャネルである配布と、操作する先が本番の系で
ある運用モードの実行である。**配布の工程では、旧い基準（マージ先のチャネル）と新しい基準
（届く先が本番の系か）の判定は一致する。** チャネルは系の一種であるため、既存の判定は
変わらない。

### 実行証跡の gate

`gh pr create` を tool 実行前の判定が観測し、本文の閉じる語が指す課題の控えを読む。

| 見るもの | 出すもの |
| --- | --- |
| モードの記録が無い | その旨 |
| 控えの記録が 0 件 | その旨 |
| 工程表で `Pull Request` より前にある必須の工程に記録が無い（「レビュー」を除く） | 工程名の一覧 |
| 閉じる課題どうしでモードが食い違う | 最も高いモードと、食い違っていること |

**判定できないときは何も出さずに通す。** 本文を読み取れる形と読み取れない形は
[stage-completeness.md](../../plugins/ndf/skills/development-workflow/references/stage-completeness.md)
にある。**案内が出ないことは、工程を通っていることの裏付けにはならない。**

### 並行開発の下限

**6 つある。** 内容と、機械が見るものと手順として書くものの振り分けは
[parallel-work.md](../../plugins/ndf/skills/development-workflow/references/parallel-work.md)
にある。**振り分けを書かないと、手順の側にある下限が「機械が見ているはず」と読まれる。**

## データ・設定

**控えはリポジトリの中に置かない**（変更として Pull Request に載るため）。置き場所と JSON の
形は
[stage-completeness.md](../../plugins/ndf/skills/development-workflow/references/stage-completeness.md)
にある。**この版で形は変えていない**（`.repo` / `.issue` / `.mode` / `.stages`）。

**本番のチャネルは `.ndf/worktree.json` の `production_branch` が宣言する。** 読み取りの順序は
宣言 → 既定ブランチの 2 段で、**`base_branch` は読まない**。宣言が無いリポジトリは既定
ブランチを本番のチャネルとして扱う。指定された名前が origin にもローカルにも無いときは、
既定へ落とさず解決に失敗する。

## 運用

**盤面（GitHub Projects）の単一選択の並びは、リポジトリ側の操作で揃える。** この版で工程の
値の集合は変わらず、並びだけが変わった（`要求と受け入れ条件` が `作業場所の用意` より前へ
移った）。集合が同じであるため記録そのものは通る。

**`light` の費用は上がる。** `cross-review` を全 Pull Request へ課したときの実行時間と費用は
まだ測っていない。次のまとまりで実測する。
