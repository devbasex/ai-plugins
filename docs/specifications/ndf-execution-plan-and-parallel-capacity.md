# 並列の実行計画と、メモリで見る本数

進行側が、まとまりを渡されたら最初の担当を起動する前に**実行計画**を書き、工程の終わりごとに
読み直して着手できる行を起動する形にした。起動してよい本数はホストのメモリから測り、触る箇所の
重なりは 3 つの区分で判定して並行するか順にするかを決める。マイルストーンへ課題を入れる時点では
**組**（触る場所の見込みと依存）を説明へ書き、実行計画がそれを束の初期値として読む。この文書は、
決めたことの理由と、実行計画・組・測定のコマンドの契約を残す。

**手順は各 Skill の `references/` が正である。** 実行計画の雛形・見直しの手順の文言・下限の文言を
ここへ書き写さない。

| 何を読むか | 正本 |
| --- | --- |
| 実行計画の置き場所・形・作る手順・見直す時点と手順・閉じる手順、組の読み方 | `plugins/ndf/skills/issue-plan-strategy/references/execution-plan.md` |
| 実行計画の入口 | `plugins/ndf/skills/issue-plan-strategy/SKILL.md` |
| 守る下限 6 つ、重なりの目安、機械が見るものと手順として書くもの | `plugins/ndf/skills/development-workflow/references/parallel-work.md` |
| マイルストーンの説明へ組を書く手順 | `plugins/ndf/skills/issue-upkeep/references/milestones.md` の「並列の組（見込み）」 |
| 測定のコマンドの引数と出力 | この文書と `plugins/ndf/scripts/parallel-measure.py` |

## 概要

**依存は工程の対で書き、実装の順序の依存は次の設計を止めない。** B の設計が A の決定を読むなら
`A-設計:収束`、B の実装が A の実装を前提にするなら `A-実装:マージ` を B の実装の行に書く。

**競合は後からマージする側が解き、解いた後の head でレビューを収束させる。** 下限 5 は「同じ
ファイルを触るものを並行させない」から「競合を解いた差分を、レビューを通さずにマージしない」へ
変わった。触る箇所の重なりは「別の節」「足すだけ」「書き換え」の 3 区分で、前の 2 つは並行し、
書き換えだけ実装を順にする。

**本数は空きメモリから導き、スワップと OOM Killer で下げ、上限で抑える。** 測定はコマンドが行い、
起動の拒否はしない。初期値はコマンドの定数だけが持ち、文書は引数の名前だけを書く。

**実行計画は主ディレクトリの `issues/` に 1 ファイルで持ち、開いている間はコミットしない。** 閉じる
ときに全文をまとまりで最後にマージした Pull Request へコメントとして投稿し、ファイルを消す。

## 用語

| 用語 | 意味 |
| --- | --- |
| 進行側 | 課題を束ね、担当を起動し、承認を仲介する実行主体。3 層では conductor |
| 担当 | 進行側が起動し、作業ツリー 1 つで 1 本の Pull Request を進める実行主体。3 層では supervisor 1 つに当たり、その中の worker は 1 本に含める |
| 本数 | 同時に動いている担当の数。CLI・テスト・コンテナのどれかを起動しうる担当を数え、worker は別に数えない |
| 実行計画 | まとまりの課題を、束・工程ごとの依存・触る箇所・着手できる時点で並べた表。進行側が持つ |
| 束 | 1 本の設計 Pull Request で決める課題の集まり |
| 組 | マイルストーンの説明に書く、触る場所の見込みと依存でまとめた課題の集まり。実行計画の束の初期値 |
| 重なり | 2 つの Pull Request が同じファイルを触ること。節（見出し）・関数の単位で程度を分ける |
| 並行度 | 対象の Pull Request のうち、2 本以上が同時に開いていた時間の割合 |
| 予備 | 進行側の本体と同じ VM に常駐する他のプロセスの揺れのために空けておくメモリ |
| 1 本の見込み | 担当 1 本が使うメモリの見込み。CLI・テスト・コンテナの山を含む |

## 背景

**並行度は指示があると上がり、無いと 0 に戻った。** v10.11.0 の後半 3 回は、設計の依存と実装の
依存を区別しなかったために設計が実装のマージを待った。**並べた本数で本体が落ちた。** 21GiB の
ホストで 5〜6 本を並行したとき、OOM Killer が claude 本体を 2 回落として全担当が止まり、3 本では
落ちなかった（#621）。落ちた後に初めてメモリを見たため、値の読み方（`MemAvailable` と cgroup の
違い、スワップ）を毎回人が判断していた。2 回目の落ち方では後片付けの漏れで残ったコンテナが 238 個
あった。**重なりを見分けたのは設計の後だった。** マイルストーン 04 では #643 → #646 を逐次にしたが、
どのファイルを触るかは設計が出た後にしか確定しなかった（#541）。

## 決定と理由

**依存は「B のどの工程が、A のどの時点を入力にするか」で書く。** 時点は `収束`（レビューが収束した）
と `マージ` の 2 つだけである。設計の依存に `マージ` ではなく `収束` を採るのは、承認の関門をまとめて
通すためで、承認で A の設計が変わったら承認を待っている B の設計の行を `待ち` に戻す。「長い待ちに
入ったら次の設計に着手する」を下限に足す形は採らない。工程を supervisor へ出す運転では supervisor の
中の待ちは進行側から見えず、依存と本数だけで着手を決めれば待ちを知らなくても次の設計が起動される。

**競合は後からマージする側が解く。** 先にマージした側は解く時点で既に閉じている。`cross-review` は
Pull Request の head を読むため、新しい手順は要らない。並行する組ごとにレビューの観点で分担を決める
形は、分担を決めても同じ節を書き換えれば競合が起きるため採らない。

**重なりは節の単位で 3 つに分け、書き換えの重なりだけ実装を順にする。** 節は設計の時点で分かる最も
細かい単位である。行の単位は実装の後にしか分からず、ファイルの単位では別の関数を触る組まで順になる。
「足すだけ」を並行へ入れるのは、git の競合が起きても解き方が両方を残すことに決まっているためである。
設計文書は束ごとに別のファイルへ書くため、設計の工程どうしはどの区分でも並行する。

**実行計画は主ディレクトリの `issues/` に置き、開いている間はコミットしない。** 見直しのたびに
Pull Request を通すと、計画の更新がマージを待ち、進み具合に遅れる。マイルストーンの説明（節だけを
差し替える仕組みが要る）・追跡用の issue（`issue-upkeep` が拾う）・`.git/ndf/`（人がたどり着かない）
は採らなかった。`parallel-batch-<連番>/` の規約は、全体指示書を主ディレクトリへコミットする運用が
`develop` への直接のコミットの禁止と両立しないため置き換えた。

**実行計画の行は Pull Request の単位にし、設計が収束したら実装の行を足す。** 実装を何本に分けるかは
設計文書の決定が持つため、着手の時点では書けない。本数に数えるのは `動いている` だけで、承認待ちの
担当は報告を返して終わっており CLI もテストも動かしていない。

**本数は `min(上限, 動いている本数 + ⌊(空きメモリ − 予備) ÷ 1 本の見込み⌋)` で出す。** 空きは動いて
いる担当の使用量を引いた後の値なので、割った値は追加できる本数であり、動いている本数を足して総本数に
する。空きメモリは VM 全体の空き（`MemAvailable`）と cgroup の残り（`memory.max − memory.current`）の
小さい方を使う。**OOM Killer の回数が増えた見直しを除き、1 を下回らない。** 0 本では進行が止まり、
逐次で進めた過去 11 版で本体は落ちていない。増えた見直しは 0 を許し、起点をその見直しで今の値へ
更新するため、次の見直しで 1 以上に戻る。

| 値 | 初期値 | 根拠 |
| --- | ---: | --- |
| 予備 | 2048 MiB | 進行側の claude 本体（約 470MiB）と、同じ VM に常駐する他のプロセスの揺れ |
| 1 本の見込み | 2048 MiB | 5〜6 本で落ちた後の `memory.peak` 7.4GiB。1 本あたり約 1.2GiB に、テストとコンテナの山を足した |
| 上限 | 3 | 5〜6 本で 2 回落ち、3 本では落ちなかった。収束レビューが共有する CLI も同じ上限で抑える |
| スワップの閾値 | 25% | 2026-09-17 の値（空き 9.5GiB・スワップの空き 15%）で 2 本になり、進行側が実際に選んだ本数と一致する |

**初期値はコマンドの定数だけが持ち、引数で上書きできる。** 文書は値を写さず、実行計画の「測った値」の
表が起動のたびの値と結果を残して初期値を直す根拠になる。

**測定はコマンドが行い、起動の拒否はしない。** 担当は Agent ツールで起動され、サブエージェントは本体の
プロセスの中で動くため、フックで本数を数える手がかりが無い。数えられないものを拒否の条件にすると、
止める必要の無い起動を止めるか、止めないまま「機械が見ている」と読まれる。

**コンテナを起動する検査を持つ担当は同時に 1 本にする。** コンテナは担当の cgroup の外で動くため、
担当の使用量として測れず、1 本の見込みの外側で空きを食う。後片付けの漏れは `trap EXIT` で直してあり
（#597）、再び起きても空きメモリの低下として測定に現れる。

**マイルストーンの型を宣言せず、束ね直さず、説明に組を書く。** 型を宣言しても組み替えは起きず、
束ね直すと連番が表す着手の順序と既存の説明の意味が動く。組の触る場所は段 2A が既に控える修正
レイヤーから写し、依存は「依存する課題の番号」から写す。新しく調べる項目を増やさない。**組は見込み
である。** 確定の値は実行計画が持ち、マイルストーンの説明へ書き戻さない。**組の表が無い既存の
マイルストーンは一括で書き直さず、課題を足すときに足した課題だけを載せる。**

## 仕様

### 常に成り立つ条件

- 本数の初期値（予備・1 本の見込み・上限・スワップの閾値）を持つのは `parallel-measure.py` の定数だけで、
  `parallel-work.md` と `execution-plan.md` に数値が現れない
- 測定のコマンドは読み取りだけを行い、GitHub へ書き込まない。出力は数値と時刻だけである
- 実行計画を書くのは進行側だけで、担当は絶対パスで読むだけである
- 組はマイルストーンの中の単位で、マイルストーンの名前・連番・着手の順序の規則を変えない
- 下限 1〜3 と関門の節、`development-workflow/SKILL.md` は変わっていない

### 実行計画

| 項目 | 値 |
| --- | --- |
| 場所と名前 | 主ディレクトリの `issues/execution-plan-<キー>.md`。キーはマイルストーンの名前の先頭の 2 桁の連番、無ければ `issue-<束ねた課題の最小の番号>` |
| 節 | `## 行` / `## 重なり` / `## 測った値` / `## 見直し` / `## 閉じたときの測定`。冒頭に状態・開始・`oom_kill の起点` |
| 行の列 | 行 / 束 / 種類 / 課題 / モード / 触るファイルと節 / 確度 / 設計の依存 / 実装の依存 / 状態 / Pull Request |
| 確度 | `見込み` / `確定`。設計のレビューが収束した見直しで、その束の行を `確定` にする |
| 状態 | `待ち` / `着手できる` / `動いている` / `承認待ち` / `止まった` / `マージ済み` |
| 作らないとき | 課題が 1 件で、Pull Request も 1 本のとき |

**見直しの契機は 5 つである。** 担当の報告を受け取った / Pull Request がマージされた / 担当が止まった /
測定で `oom_kill` が増えていた / 進行側が再起動して実行計画を読み直した。見直しでは、状態の更新と
実装の行の追加 → `確定` の行どうしの重なりの突き合わせ → 依存が済んだ行を `着手できる` に →
`capacity` の実行と測った値の記録 → 空きの数だけ `着手できる` の行を上から起動 → 束・順序・依存を
変えたら見直しの表へ 1 行、の順で行う。`capacity` が終了コード 3（測れない）なら本数を 1 として扱う。
`oom_kill_increased=yes` の見直しでは起動せず、起点を今の値へ更新して見直しの表へ 1 行足す。減らす分は
動いている担当を止めずに終わるのを待つ。

すべての行が `マージ済み` になったら、`concurrency` を実行して閉じたときの測定へ写し、状態を `閉じた`
にし、全文をまとまりで最後にマージした Pull Request へ `gh pr comment --body-file` で投稿し、投稿の
URL を確かめてからファイルを消す。GitHub のコメントの上限は 65,536 文字で、1 行 150 文字として 400 行を
超えるまで届かないため、`<details>` で畳まない。

### 重なりの目安

| 区分 | 何が当たるか | 並行 | 待つもの |
| --- | --- | --- | --- |
| 別の節 | 別のファイル、または同じファイルの別の節（見出し）・別の関数 | してよい | なし |
| 足すだけ | 同じ節に行・項目・関数を足すだけで、既存の行を変えない | してよい | なし。競合は後からマージする側が両方を残して解く |
| 書き換え | 同じ節の既存の行を書き換える・移す・消す | 実装はしない | 先の Pull Request のマージ |

区分は設計の後に確定する。書き換えなら、後の行の実装の依存へ先の行の `:マージ` を足す。

### マイルストーンの組

マイルストーンの説明の末尾に見出し `### 並列の組（見込み）` と、列が 組 / 課題 / 触る場所の見込み / 依存
の表を置く。組は 1 から始まる連番で、課題は同じ修正レイヤーを持つ課題の番号、触る場所の見込みは修正
レイヤーの名前（Skill の名前・スクリプトのパス・文書のパス）、依存は `なし` または組の番号である。

| 時点 | 行うこと |
| --- | --- |
| 課題をマイルストーンへ入れる | 修正レイヤーが既存の組と同じならその組へ番号を足す。違えば組を 1 つ足す。表が無ければ見出しと表を作る |
| 課題を別のマイルストーンへ移す | 元の表から番号を消す。0 件になった組は行を消し、番号は詰めない |
| 課題が閉じた | 何もしない。実行計画が状態を持つ |

実行計画は表の組を束の初期値として読む。表に無い課題は本文を読んで束を決め、どの組にも足さない。

## データ・設定

### `parallel-measure.py capacity`

| 引数 | 意味 |
| --- | --- |
| `--running N` | いま動いている担当の数（既定 0） |
| `--oom-baseline N` | 実行計画に控えた `oom_kill` の起点。渡さなければ増えたかを判定しない |
| `--reserve-mib N` / `--per-lane-mib N` / `--max N` / `--swap-free-min-pct N` | 予備 / 1 本の見込み / 上限 / スワップの空きの閾値（%）。既定はスクリプトの定数。`--per-lane-mib 0` は引数の誤り |
| `--meminfo PATH` | 空きとスワップを読む元（既定 `/proc/meminfo`） |
| `--cgroup-dir DIR` | `memory.events`・`memory.max`・`memory.current` を読む元。既定は `/sys/fs/cgroup`、そこに `memory.events` が無ければ `/proc/self/cgroup` の `0::<path>` から導いた先、それも読めなければ根へ戻す |

出力は標準出力に `キー=値` を `mem_available_mib` / `swap_total_mib` / `swap_free_mib` /
`cgroup_available_mib` / `oom_kill` / `oom_kill_increased` / `running` / `by_memory` / `allowed` /
`limited_by` の順で出す。`cgroup_available_mib` は `memory.max` が数値なら残り（負なら 0）、`max` なら
`max`、読めなければ `unknown`。`oom_kill` は読めなければ `unknown`。

```text
by_memory = running + max(0, ⌊(min(mem_available, cgroup_available) − reserve) ÷ per_lane⌋)
allowed   = min(max, by_memory)
swap_total > 0 かつ swap_free × 100 < swap_total × swap_free_min_pct なら allowed −= 1
oom_kill_increased = yes なら allowed = max(0, min(allowed, running − 1))
それ以外なら allowed = max(allowed, 1)
```

`limited_by` には `memory`（`by_memory ≤ max`）/ `max`（`max ≤ by_memory`）/ `swap_low` / `oom_kill_increased`
（値が下がった）/ `floor`（1 へ上げた）のうち当たったものをこの順で `,` で並べる。終了コードは 0 = 測れた
（`unknown` を含む）、2 = 引数の誤り、3 = `--meminfo` を読めない、または `MemAvailable` が無い（標準出力に
何も出さず、標準エラーに理由を 1 行）。

### `parallel-measure.py concurrency`

`<PR番号>...`（`--input PATH` のときは不要）と `--repo OWNER/REPO` / `--input PATH`（`gh` を呼ばず
`[{"number", "createdAt", "mergedAt", "closedAt"}]` の JSON を読む）/ `--now ISO8601` を受け取る。
区間は `createdAt` から `mergedAt`・`closedAt`・`--now` のうち最初に値のあるものまでで、同じ時刻に
閉じる区間と開く区間は重ならない。出力は `prs` / `start` / `end` / `span_minutes` / `overlap_minutes` /
`concurrency_pct`（秒どうしの比を小数 1 桁へ四捨五入、`span` が 0 秒なら `0.0`）/ `max_open` である。
終了コードは 0 / 1（`gh pr view` が失敗、または `gh` を起動できない）/ 2（引数の誤り、`--input` の
中身が形に合わない）。**`gh` へ渡すのは `pr view <番号> --json number,createdAt,mergedAt,closedAt`
（と `--repo`）だけである。**

### 測った値の写し方

実行計画の「測った値」の表には `capacity` の出力のうち `mem_available_mib` / `cgroup_available_mib` /
`swap_free_mib` / `oom_kill` / `running` / `allowed` / `limited_by` を写す。`swap_total_mib` /
`oom_kill_increased` / `by_memory` は写さない（起動のたびに変わらないか、他の列から導ける）。測れなかった
行は空きの列に `測れない` と書く。閉じたときの測定は `concurrency` の出力と、`oom_kill` の最後の値 −
最初の行の `oom_kill` である。

## テスト観点

| 観点 | 確かめ方 |
| --- | --- |
| `capacity` が空き・cgroup の残り・スワップ・`oom_kill`・本数を出し、`--running` を総本数に足し、引数で上書きでき、cgroup の残りが小さければそちらで決まる | `plugins/ndf/scripts/tests/test_parallel_measure.py` |
| 測れない環境で本数を出さず終了コード 3。`memory.events` が無ければ `oom_kill=unknown` で 0 | 同上 |

## 運用

**1 本の見込み 2048MiB が CLI を起動した担当の実際に合うかは、実行計画の「測った値」の表から直す。**
5〜6 本のときの cgroup の最大使用量からの推定で、CLI ごとの常駐の値は測っていない。

**メモリを測る手段は Linux の `/proc/meminfo` と cgroup v2 である。** 無い環境（macOS など）では
終了コード 3 になり、実行計画に「測れない」と書いて 1 本で進める。
