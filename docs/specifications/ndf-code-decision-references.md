# plugins/ndf のコメントが作り直しの決定を指す形: 確定仕様のファイルと決定の番号

`plugins/ndf` のコメント・docstring・README・JSON の説明は、#1142 の作り直しの決定を `docs/specifications/ndf-rebuild-<主題>.md の決定 N` の形で指す。例えば `plugins/ndf/bin/ndf-claude` の 2 行目は「`#3409・docs/specifications/ndf-rebuild.md の決定 74`」と書き、読み手はファイルを開いて見出し「決定 74」を 1 回検索すれば根拠に着く。この文書は、その形・作り直しの決定とほかの設計の決定の見分け方・書き換えずに残した参照・確かめを検査にしない理由を持つ。

## 概要

- 指す先は作り直しの確定仕様 6 本（索引 [ndf-rebuild.md](ndf-rebuild.md) と、その索引が挙げる 5 本）の決定とセクションである。`issues/` の設計文書は指さない
- 作り直しの決定かどうかは番号ではなく中身で決める。番号が同じ別の設計の決定（例 `progress/gate/answering.py` の「#3097 の決定 99」）は書き換えない
- 子の表の値と、規則 `review-items` が読む 2 つの表の置き場は、ほかの文書が持つ（下の「子の表と規則の入力の置き場」）
- 参照の実在と表の一致を見る規則は `ndf check` に無い。書き方はレビューが見る

## 背景

作り直しの設計文書（`issues/` の 36 本）は確定仕様化で消す材料である。コメントがその文書のパスか番号だけで決定を指していると、文書を消した後は根拠に行き着けず、番号の振り直し（[ndf-rebuild.md の「番号の対応表」](ndf-rebuild.md#番号の対応表)）も読み手が自分で当てることになる。#3960 で、作り直しの決定を指すコメントを確定仕様のファイルと番号の形へ書き換えた。

## 仕様

### 参照の形

| 指す先 | 書き方 | 例 |
| --- | --- | --- |
| 決定 | `docs/specifications/ndf-rebuild-<主題>.md の決定 N` | `docs/specifications/ndf-rebuild.md の決定 88` |
| 同じ文書の複数の決定 | パスを 1 回書き、番号を `・` で並べる。範囲（`81〜86`）は使わない | `docs/specifications/ndf-rebuild.md の決定 81・82・83・84・85・86` |
| セクション（決定でないもの） | パスの後ろに「」でセクションの名前を書く | `docs/specifications/ndf-rebuild.md の「常に成り立つ条件」`・`docs/specifications/ndf-rebuild-scripted-flow.md の「洗い出しの一覧」` |
| 振り直しで決定でなくなった番号 | 「番号の対応表」の替わった先を、決定の番号かセクションの名前で指す | 決定 102 → `docs/specifications/ndf-rebuild.md の「番号の対応表」` |

- パスと番号は 1 行に置き、改行で分けない。番号の並びの直後に `、` などを挟んで別の数を続けない（`決定 83、14 日` と書かない）
- 不変条件の番号（`I1`・`IH2` など）は、決定の番号の後ろに並べて残す
- `# noqa` の理由の中の決定は、抑制コメントの形を保ったまま同じ形で書く
- パスは NDF のリポジトリの中のパスである。`docs/specifications/` は利用者へ配らないが、Skill の本文が確定仕様を指すのと同じ扱いにする
- `contracts/` の JSON の説明を変えたときは、`ndf check --write-spec` で生成物を作り直す

### 作り直しの決定の見分け方

番号だけで系統を決めると、番号が同じ別の決定を取り違える。参照ごとに次の順で系統を決め、決定の本文がコメントの文を裏付けるときだけ指す。

| 行の書き方 | 読み方 |
| --- | --- |
| `#1142`・`#3347`・`#3388`・`#3395` の決定か、作り直しの設計文書のパスを添えた行 | 作り直しの決定。「番号の対応表」で今の番号にしてから引く |
| `#3344` の決定 81〜86、`#3345` の決定 88〜96 | `ndf-rebuild.md` の同じ番号の決定 |
| ほかの課題の番号を添えた行（例 `#3394` の決定 60） | 番号と中身の両方が作り直しの決定と合うときだけ作り直しの系統とする（例 `llm.py` の打ち直しの回数は `ndf-rebuild-scripted-flow.md` の決定 60） |
| 番号だけの行 | 前後 10 行のコメントと、同じファイルのほかの参照の系統で決める |
| 番号が同じ別の系統の行（例 `fixes` の決定 75 と `next` の決定 75） | コメントの文を両方の決定の本文と突き合わせて決める |

「番号の対応表」で番号が替わり、替わった先の本文がコメントの文を裏付けないときは、6 本の全部の決定から探す。参照の付いた文を裏付ける決定が 1 つならそれを指す。無ければ、同じコメント（1 つの docstring・連続する `#` の行・JSON の 1 つの説明文）のほかの文を裏付け、かつそのモジュールを名指しする決定が 1 つだけで、元の位置とその文の間にほかの決定への参照が無いとき、参照をその文の後ろへ移して指す。移せる文が複数あるときは、コメントの中で最初の文を選ぶ。この条件を満たす文が無いときは「決められない」（下の「書き換えずに残す参照」）として、元の位置の参照を残す。例えば `domains/worktree/write_target.py` は、書き込み先の推定を裏付ける決定が無いので 1 行目に参照を置かず、「構文木は tree-sitter-bash で作る」の文の後ろで `docs/specifications/ndf-rebuild-libraries.md の決定 14` を指す。

### 書き換えずに残す参照

| 分類 | 扱い | 今ある行 |
| --- | --- | --- |
| 別の設計の決定 | 書き換えない | 中継・承認ゲート・レーンなどの設計の決定（例 `answering.py` の「#3097 の決定 99」）。Skill とエージェントの本文やテストの見本にある書き方の例の「決定 N」も含む |
| 決められない | 番号と文を変えない。作り直しの設計文書へのパスを伴うときは、パスだけを `docs/specifications/ndf-rebuild.md の「番号の対応表」` に替える | `domains/hooks/guards/turn.py`・`domains/relay/__init__.py`・`domains/relay/markers.py`・`domains/relay/signals.py` の「決定 111」。`ndf-rebuild-review-scope.md` の決定 111（受け入れ条件が 25 行を超える子を分ける）は中継のマーカーと依存の向きの文を裏付けず、番号は対応表で替わっていない |
| 移設対象外（「番号の対応表」が「移さない」とした決定） | 元の系統の名前と番号を残し、パスだけを「番号の対応表」に替える（例 `fixes の決定 70（docs/specifications/ndf-rebuild.md の「番号の対応表」）`） | 無し |
| コードの値 | 文字列の値の中の参照は書き換えない。書き換えるとコードの構文木が変わる | `identity.py` の `OldPlace` の `reason` の「決定 85」 |
| 不変条件の番号だけの参照（「決定 N」もパスも無い） | 対象にしない | — |

### 子の表と規則の入力の置き場

決定を指すコメントの書き換えとあわせて、子の表と規則 `review-items` の入力を `issues/` の外へ出した。値と手順はそれぞれの文書だけが持つ。

| もの | SSOT | 置き場の理由 |
| --- | --- | --- |
| 子の表（子ごとのサブパッケージ・先に要る子・順番・レーン・閉じたか、共有の表の書き込み元） | `plugins/ndf/src/ndf/checks/children.json`。変え方は `plugins/ndf/src/ndf/checks/README.md` の「子の表の規則」 | 値を 1 か所にするため、検査が読む JSON を正にした。[ndf-rebuild.md の「子の記号」](ndf-rebuild.md#子の記号) は読み手のために記号・Issue・中身だけを持つので、子の記号か Issue を足す・変える・消すときは、同じ Pull Request で 2 か所を揃えて直す。`children.json` は中身を持たないので、中身の説明だけを変えるときは「子の記号」の表だけを直す |
| 設計レビューの項目 182 件の表 | [ndf-review-items.md](ndf-review-items.md)（`checks/rules.json` の `spec.review_items_source` が指す） | 設計文書を消しても規則が入力を読めるようにするため。名前を `ndf-rebuild` で始めないのは、決定の番号を持つ 6 本の数え方を変えないためである。`plugins/ndf` の中に置かないのは、利用者へ配る量を増やさないためである |
| 11.x へ回した 72 行の行き先の表 | [ndf-review-items-11x.md](ndf-review-items-11x.md) | 11.x の行のリンクが表そのものに着くよう、182 件の表と別の文書にした |

### 確かめを検査にしない

参照の実在・子の表の一致・移した表の一致・構文木の一致は、書き換えたときに一度だけコマンドで数え、結果を Pull Request に載せた。`ndf check` に参照の実在を見る規則は足していない。検査を足すのは振る舞いの変更であり、一度きりの確かめのために常設の規則を持つと重複と冗長が増えるためである。代わりに、後から書き足された参照が壊れても機械は知らせない。参照の書き方はレビューが見る。

## テスト観点

- 作り直しの決定を指す参照が、上の「参照の形」のどれかで書かれ、指す決定かセクションの見出しが確定仕様にあること
- `git grep` で、`plugins/ndf` から作り直しの設計文書（#1142・#3347・#3388・#3395 の設計文書）へのパスが 0 件であること
- 別の設計の決定を指す行（例 `answering.py` の「決定 99」）が、作り直しの確定仕様を指していないこと
- 規則 `review-items` が [ndf-review-items.md](ndf-review-items.md) の 182 件を読み、`ndf check --write-spec` の後に `children.json` の差分が出ないこと
