# 別のリポジトリの改修が要るとき: 相手のクローンで動くレーンを計画へ足す

並列の計画のレーンが、作業の途中で別のリポジトリ（上流の NDF など）の改修が先に要ると分かったときの既定の扱いである。
依頼した側のレーンは、相手のリポジトリへ課題を用意し（人の承認つき）、2 つの課題を対に結び、相手のリポジトリのクローンを
`repo` にしたレーンを計画へ足す。相手の改修は同じオーガナイザーの下で、相手のリポジトリの規約のまま進む。

この文書は設計判断の結論と理由・常に成り立つ条件・テスト観点を残す。**手順は Skill の文書が正である。ここへは写さない。**

| 何を読むか | 正本 |
| --- | --- |
| 既定の手順（判定・課題の用意・対の結び・レーンの追加・待つ形・進む条件・相手のレーンの規約） | `plugins/ndf/skills/development-workflow/references/parallel-cross-repo.md` |
| 別のリポジトリのレーンの起動・問いの往復・本番 | `plugins/ndf/skills/development-workflow/references/parallel.md` の「別のリポジトリのレーン」と [ndf-parallel-other-repo-lanes-and-outside-plan.md](ndf-parallel-other-repo-lanes-and-outside-plan.md) |
| 代わりの手順（別のリポジトリへの起票） | `plugins/ndf/skills/out-of-scope/SKILL.md` の手順 3〜5 と [out-of-scope-issue-file.md](out-of-scope-issue-file.md) |
| 計画の宣言のレーンの `repo`・`after` | `plugins/ndf/skills/issue-plan-strategy/references/parallel-plan.md` |

## 概要

**例:** 利用側のリポジトリ `acme/app` のレーンが、課題 `acme/app#120` の設計で NDF の Skill の変更が先に要ると分かった。
`acme/app` と同じ親ディレクトリに NDF のクローン `/work/ai-plugins` がある。

| 順 | 誰が | 何をする |
| ---: | --- | --- |
| 1 | 依頼した側のレーン | 3 つの判定（並列の計画のレーンである・クローンが 1 つだけ見つかる・`lane add` が断らない）を確かめる |
| 2 | 依頼した側のレーン | `devbasex/ai-plugins` で既存の課題を探し、無ければ起票する。どちらも承認資料を示して人の同意を取ってから打つ |
| 3 | 依頼した側のレーン | 2 つの課題に、完全な形の参照で 1 行ずつ相手を書く |
| 4 | 依頼した側のレーン | 計画の置き場で `parallel.py lane p1 add` を打ち、`/work/ai-plugins` を `repo` にしたレーンを足す |
| 5 | 相手のレーン | NDF の設定・課題・承認ゲートで改修を進める。承認ゲートの問いはオーガナイザーへ届く |
| 6 | 依頼した側 | 相手の改修が要る段に来たら、相手の課題が完了で閉じ、導入した版がその変更を含むことを確かめてから続ける |

並列の計画を使っていないセッションは、範囲外の課題の起票（`out-of-scope` の手順 3〜5）のまま変わらない。

## 用語

語の定義は [docs/glossary.md](../glossary.md)（正本は `docs/glossary/glossary.json`）にある。この文書で使う語は、
依頼した側・相手のリポジトリ・相手のレーン・完全な形の参照・代わりの手順である。

## 背景

範囲外の課題が別のリポジトリへ当たったときの扱いは、相手のリポジトリへ起票して終わっていた。誰がいつ直すかが決まらず、
依頼した側は相手の進みを追えず、設計は「相手の側の変更が先に要る」と書いたまま止まる。並列の計画には、計画の置き場と違う
リポジトリでレーンを動かす仕組み（レーンの `repo` と検査の規則 `I20`）がすでにあるため、スクリプトを変えずに手順だけで既定にした。

## 対象範囲

- 働く範囲: NDF を使うすべてのリポジトリの、並列の計画の下のレーン。どのモードでも、`out-of-scope` を呼ぶ工程で起票先が別のリポジトリになったとき
- 新しい設定と引数は足さない。スクリプト（`parallel.py` など）の振る舞いは変えない
- 含まない: 計画の宣言の作り替え・スプリントをまたぐ閉じる条件・重なりの判定の変更・相手のリポジトリへの漏れの検査の追加

## 決定と理由

| 決定 | 理由 |
| --- | --- |
| 手順の正本を新しい参照の文書 `parallel-cross-repo.md` に置き、`parallel.md`・`out-of-scope` の `SKILL.md` と `issue-target.md`・`parallel-plan.md` はリンクの 1 行だけを持つ | `parallel.md` は行数の上限（500 行）に近く、手順を足すと超える。同じ `references/` に置けば並列開発の文書からたどれる |
| 相手の課題は依頼した側が用意する | 相手のレーンの最初の入力（`{"kind": "sprint", "issues": [...]}`）は課題の番号を要る。依頼した側が `out-of-scope` の `dup`・`create` を使えば、他のリポジトリへの書き込みの承認（C5）が今の仕組みのまま働く |
| 対の結びは両方の課題の由来の節に置き、既存の相手の課題だけは `issue-file.py note` のコメントで残す | `issue-file.py create --counterpart` の既存の形にそろえる。由来の節は `retrospective` が課題を辿るときに読む場所でもある。GitHub の課題の依存（blocked by）は、リポジトリをまたぐ関係と非公開の課題の見え方が確かめられておらず、書き込みが 1 回増えるため採らない |
| 参照は `<所有者>/<リポジトリ>#<番号>` の完全な形で書く | GitHub がリポジトリをまたぐ課題の参照として扱う標準の形である。番号だけの形は相手のリポジトリでは別の課題を指す |
| `after` は起動前のレーンにだけ付ける。動いている開発ループのレーンと 1 スプリントのレーンは待つ形を持たず、相手の改修が要る段で進む条件を確かめる | `after` は起動に成功していないレーンだけに効く（`parallel_plan.py` の `ready_lanes`）。`loop exclude` は選定の後・`loop sprint` の前にしか打てず、外すのはループの 1 回だけなので、途中の課題を別のレーンへ移せない。`lane set` の `rule: relaunch` は `after` を見ずにすぐ起動し、他のレーンの完了を待つことは問いの区分に当たらない |
| 続きの前に、相手の課題が `CLOSED`・`COMPLETED` であることと、リリース対象を通じて使う変更なら導入した版がその変更を含むことを確かめる | `after` は相手のレーンが失敗で止まっても解け、改修が出たかを見ない。課題が閉じても、リリース対象の変更は依頼した側の環境へ届くまで使えない |
| クローンは依頼した側のメインディレクトリと同じ親ディレクトリの直下から、origin の一致と worktree でないことで探し、1 つに絞れなければ代わりの手順へ戻る。利用者に場所を問わない | マーケットプレイスの取得元（`~/.claude/plugins/marketplaces/`）は Claude Code が管理する導入元で、作業場所ではない。選び違えて別の作業場所でレーンを動かすより、戻すほうが安い。代わりの手順でも課題は残る |
| `lane add`・`lane set` は計画の置き場で打つ | `parallel.py` は打った場所のメインディレクトリの `.ndf/parallel/` だけを読む。依頼した側が別のリポジトリのレーンなら、自分のリポジトリで打つと計画が無いとして断られる |
| 公開の範囲が違う組では、公開の側の課題に非公開の側のリポジトリの名前と番号を書かない。依頼した側が非公開・相手が公開の組は起票しない | 非公開の側の名前と番号そのものが公開の側へ出る情報になる。`create` は `--origin`（`issue #<番号>`）が必須で由来の節の先頭へ必ず入れ、`note` の固定文は依頼した側の完全な形の参照を必ず含むため、どちらも伏せた行を渡せない |

## 仕様

### 常に成り立つ条件

| # | 条件 | 破れたときの扱い |
| --- | --- | --- |
| 1 | 手順の本文は `parallel-cross-repo.md` の 1 か所だけにあり、ほかの文書はリンクだけを持つ | レビューで複製を消し、リンクへ置き換える |
| 2 | 相手のリポジトリへの起票と書き込みは、`issue-file.py` の承認資料（終了コード 10）と `ndf-ask:redline:C5` の同意を通してからだけ行う。人に問えない起動では打ち直さず人へ戻す | 同意が無ければ起票せず、レーンも足さない。依頼した側の課題に事実を残し、相手の改修に依らない作業だけを進める |
| 3 | 相手のレーンは `parallel.py lane add` だけで足す。レーン数の上限は人の指示なしに変えない | `lane add` が 1 で終われば、レーンを足さずに代わりの手順の結果（起票した課題）で終える |
| 4 | 公開の範囲が違う組では、公開の側の課題に非公開の側の名前と番号を書かない | 依頼した側が公開なら、相手の完全な形の参照は依頼した側のレーンの引継ぎ文書へ書く |
| 5 | 相手の課題の本文には相手のリポジトリで直す内容だけを書き、依頼した側の規約・インフラの値・業務の情報を書かない | C5 の承認資料を見た人が差し戻す。相手のリポジトリの漏れの検査が落とす |
| 6 | `after` は起動前のレーンにだけ付ける | 待てないレーンは待たずに進み、相手の改修が要る段で止まって人へ戻す |
| 7 | 相手の改修を前提にする作業へ進む前に、進む条件を確かめる | 満たさなければ進まず、止まって人へ戻す |
| 8 | 並列の計画を使っていないセッションの手順（`out-of-scope` の手順 3〜5）は変わらない | 退行としてレビューで差し戻す |

### `lane add` の結果ごとの扱い

| 結果 | 扱い |
| --- | --- |
| 0 | 耐久ワークフローが相手のレーンを起動の候補に入れる |
| 1（上限を超える） | 上限を変えずにレーンを足さない |
| 1（`I20`: クローンでない場所を指した） | 代わりの手順の結果に切り替える |
| 1（`I19`: 相手のリポジトリのスプリントのレーンが同じ課題を持つ） | レーンを足さず、そのレーンを相手のレーンとして扱う |
| 1（`I19`: 相手のリポジトリに `--milestones` の無いループのレーンがある） | ループがこの課題を選ぶとは限らないため、代わりの手順の結果に切り替える |
| 1（在る引継ぎ文書を上書きしない） | 別の作業がその課題を進めている文書かもしれないので消さず、代わりの手順の結果に切り替える |

同じ課題を持つレーンへ任せたときを除き、1 で終わったら依頼した側の課題の由来の節に、レーンを足せなかった理由を 1 行足す。

## セキュリティ

相手のリポジトリへの書き込みはすべて C5（他のリポジトリへ公開する）として人の承認を通す。書く内容は直す内容だけに限り、
公開の範囲が違う組では非公開の側の名前と番号を公開の側へ出さない。残りは相手のリポジトリの漏れの検査が守る。

## 運用

相手のレーンは、相手のリポジトリの設定（`.ndf/`）・課題・設計承認ゲート・リリース承認ゲート・漏れの検査で進む。
依頼した側の規約と情報を、相手のレーンの引継ぎ文書と相手の課題へ持ち込まない。

## テスト観点

文書の手順の変更であり、`.md` の文言を照合するテストは置かない。確かめ方はチェックスクリプトとレビューで読む項目である。

- 手順の本文が `parallel-cross-repo.md` だけにあり、ほかの 4 文書はリンクの行だけを持つこと
- 判定の 3 つの条件と、代わりの手順へ戻る場面（クローンが無い・1 つに絞れない・計画を使っていない・`lane add` が断る）が書かれていること
- 対に結ぶ行の形と書く場所が、相手の課題（起票する・既存）と依頼した側の課題のそれぞれで 1 つに決まっていること
- 相手のリポジトリへの書き込みがすべて承認資料と `ndf-ask:redline:C5` を通ること
- `after` を起動前のレーンにだけ付け、上限を変える段を持たないこと
- 続きの前に課題の状態と版を確かめること
- `python3 scripts/check-skill-frontmatter.py`・`python3 scripts/check-markdown-links.py`・`python3 scripts/check-doc-line-limit.py`・`python3 plugins/ndf/scripts/instructions-check.py --root .` が 0 で終わること

未確認のまま残ること: 手順を読んだレーンが実際に相手のレーンを足すか代わりの手順を選ぶかは、別のリポジトリの改修が要る場面に
当たったレーンで、リリース後テストとして確かめる。
