# 工程「実装」をレビューの単位ごとに流す: 決定の記録・受け入れた代償・見送った指摘

[ndf-implement-stage-review-units.md](ndf-implement-stage-review-units.md) の振る舞いを決めた理由を持つ。決定の番号は
コードのコメント（`#4369 の決定 N`）と同じである。根拠の「Value N」は承認済みのプロジェクト MVV（`.ndf/mvv.md`、
バージョン 11）の Value の項目、「C N」・「P N」は必ず人の承認が要る操作の表の行を指す。

## 範囲を縮めた経緯

2026-11-26 の設計承認ゲートで、利用者が範囲を縮めた。設計の cross-review の指摘が、単位の完了を記録する専用の仕組み
（マージコミットの本文の記録と打ち消しの判定）・指摘の持ち越し・自動の後片付けに集まり、指摘の出ない状態にならなかった
ためである。目的は自動の経路でも単位ごとに PR とレビューを通すことで、安全さは今の supervisor の手順と同じにする。
決定 6・11・14・15 はこの判断から来ている。

## 決定

### 決定 1: #3702 の実装を待たずに、単位を順に流す部分を先に入れる

単位の大きな変更を流すたびに起きる事象で、直すのに要るのは「読んで順に流す」部分だけである。#3702 の残り（9 タスク・
見込み約 3,550 行）を待つと同じ事象が続く。単位を読む処理と流す処理は分け、流す処理のファイル（`progress/units_invoke.py`）・
差し込み（`unit_file`）・工程のメタデータ（`per_unit`）の名前は #3702 の詳細設計に合わせた。#3702 の実装は読み手を単位の
ファイルへ差し替え、流す処理に並列実行と入力の承認の確認を足す。代償は、表の読み手が #3702 で置き換わり、流す処理にも書き
直す部分が出ることである（Value 5・11）。

### 決定 2: 表だけの実装計画は表の順に流し、#3702 の実装の後は止める

利用者が求めたのは実装計画に書いた分け方のとおりに流れることで、表があるのに 1 本にすると分けた意図が黙って捨てられる。

| 時期 | 単位の表があり、単位のファイルが無い実装計画 |
| --- | --- |
| #3702 の実装が入るまで | 表の単位を流す |
| #3702 の実装が入った後 | 単位の見出しがあるのに単位のファイルが無ければ止まる。表は読まず、1 単位にもまとめない |

#3702 の設計は、単位のファイルも区間の印も無い実装計画がスプリントの起点にあれば課題 1 つの 1 単位（`single`）にする。
#3702 の実装はこの判定を、起点にあったかより先に「レビューの単位」の見出しを調べ、見出しがあれば止まる順に改める。表の読み手を
残して 2 通りを読む案は、同じ事実の読み手が 2 つになるので採らない。代償は、#3702 の実装が入った時点で終わっていないスプリント
が、単位のファイルを書き足すまで工程「実装」で止まることである。書き足した後の再開点とマージ済みの単位の引き継ぎは決まって
おらず、#3702 の実装で決める（PR 4567 のドキュメントレビュー r3-3 で見送った）（Value 3・8・11）。

### 決定 3: #3905 をこの課題へ統合する

#3905 の受け入れ条件（単位ごとに実行しマージの後に記録する・未マージなら記録せずに止まる・欄が無ければこれまでどおり）は、
この課題の条件 1〜5 に含まれる。別に残すと同じ処理を 2 回設計して確かめることになる。#3905 は #4369 の確かめで閉じる（Value 11）。

### 決定 4: 工程の定義のステップは変えず、プランを呼ぶ層で単位の経路へ分ける

単位があるかは実装計画を読むまで分からない。分けるのをプランの呼び出し（`invoke.py`）に置けば、今ある打ち直しと差し込みの
確かめをそのまま使え、単位の無いスプリントの流れは変わらない。ステップを単位を流すスクリプトに置き換える案は単位の無い
スプリントにも作り直しを強い、単位の数だけ工程の行を足す案は、工程の行をモードの定義が決め、単位の数が実装計画の後にしか
分からないので採らない。代償は、繰り返しがあることが定義の上では `per_unit` の 1 語でしか分からないことと、実装計画から見出しを
すべて消して打ち直すとこれまでの経路で流れることである（Value 3・9）。

### 決定 5: 単位は並列にせず 1 つずつ流す

単位が触るファイルは実装計画の表に無く、重なりを前もって確かめられない。順に流せば後の単位は前の単位の変更の上で作られる。
並列は触るファイルと承認を持つ #3702 が足す。代償は、単位が多いスプリントで supervisor が並列に回すより遅いことである（Value 3・9）。

### 決定 6: 単位の完了は、スプリントブランチ宛ての単位の PR がマージ済みかで見分ける

マージ済みの PR はこの課題の目的（単位ごとの PR とレビュー）の結果そのもので、GitHub が持っている。単位のブランチ名は
スプリントブランチ・代表の課題・単位の名前から決まるので、別のマシンの打ち直しでも同じ名前になる。単位のブランチ名は公開の
情報から決まり、フォークが同じ名前で PR を出せるため、完了の判定（`github_pulls.merged_pulls`）・`pr` の `probe`・
`ndf ci merge --pr` の 3 か所は、head・宛先・フォークでないことを同じ条件にする。今の `pulls_by_head` は head だけで直近 5 件を
読むので使わない。単位の経路では `impl` の `done-check` を外す。残すと照会が単位ごとに繰り返され、head だけで探す今の
`done-check` が別の宛先のマージ済み PR を完了と読むことがある。マージコミットに記録を持つ案（専用のマージ・打ち消しの読み方・
履歴の照合が要る）と、手元のファイルにだけ記録する案（別のマシンで確かめられない）は採らない。

工程の外（GitHub の画面など）でのマージも完了と読む。工程が根拠にするのはマージ済みの PR があることだけで、レビューの収束・
レビューした HEAD・人の判断を待つ指摘が残っていないかは確かめず、残っていた指摘を解消とも承認とも扱わない。飛ばした単位は
状態を `already_merged` にして PR の番号を示し、指摘の中身は単位の PR の cross-review の記録に残る（Value 3・11）。

### 決定 7: 表は決めた形だけを読み、読めなければ始めずに止まる

読み違えた単位は、実装もレビューもされないまま `gathered` の後ろへ進む。始める前に止まれば、直すのは実装計画の 1 行で済む。
2026-11-01 以降の実装計画で単位の見出しがある 22 本・129 行のうち、形に合わないのは 1 本の 2 行（`5a`・`5b`）だけだった。
`<課題>:<番号>` だけを受ける案は範囲や番号の省略を使う計画の多くを止め、読めない行を飛ばす案は落ちた単位に気づけない。
代償は、`5a` のような番号で条件を指す実装計画が、番号を直すまで止まることである（Value 3・13）。

### 決定 8: 単位の指示のファイルを実装・修正・レビューのすべてに渡す

単位の PR を読み切れる大きさに保つには、後からコミットする修正担当にも同じ範囲が要る。初回の `impl` にだけ渡すと、テストや
CI が落ちたときに修正担当が後の単位のタスクまで実装できる。受け入れ条件の指定だけで絞る案は、1 つの条件が複数の単位にまたがる
表と、条件を持たないプレリファクタリングの単位があり使えない。課題の本文のコピーへ範囲の指示を足す案は、そのファイルが PR の
本文になり課題の本文と食い違う。範囲を理由に危険な指摘が後回しにならないよう、秘密・認証認可・利用者のデータ・戻せない操作の
指摘は例外にした（Value 7）。単位の外を変えてよい条件は設計の承認の後に狭めた（今の単位の変更が原因のときだけ）。代償は、
設定でレビューや worker の起動を差し替えたリポジトリは `unit_file` と `NDF_UNIT_FILE` を読む側も合わせる必要があり、範囲を
守るのは指示で、差分を機械では確かめないことである（Value 3・9）。

### 決定 9: 条件を持たない単位は `--no-criteria` で突き合わせないことを明示する

プレリファクタリングの単位は突き合わせる受け入れ条件を持たない。`--issue` だけを渡すと課題のすべての条件を突き合わせて必ず
止まり、条件の無い単位を読めない表にすると実在する計画が止まる。条件の渡し忘れと区別するため、引数で書く。代償は、条件の漏れが
その単位では見つからないことで、工程「完了判定」がすべての条件を確かめる（Value 11・13）。

### 決定 10: すべてのマージの後に工程「実装」がスプリントの PR を開く

単位の経路ではスプリントの PR を誰も作らず、後の工程「リファクタリング」「コードレビュー」はそれを読む。最後のマージを知るのは
工程「実装」である。後の工程の側で作る案は、作る場所が 2 つ以上になる。テンプレート `pr` から `push`・`fix-push` を外すのは、
単位のレビューを経ないコミットを最後の処理で作らないためである。

スプリントの PR の前に、リモートの履歴がレビューを経た単位のマージ結果だけでできているかを照合する案は採らない。マージの方式
（merge・squash・rebase）ごとにマージ結果を再現する照合が要り、実装のレビューで抜け道の指摘が続いた。代わりに、単位のマージで
`ndf ci merge --reviewed` がレビューした HEAD を確かめ、スプリントの PR の前にリモートの先端が作業場所の HEAD と同じかを
確かめる。代償は工程「実装」の仕事が 1 つ増えることと、下の「受け入れた代償」の 5 である（Value 3・11）。

### 決定 11: `ndf ci merge --reviewed` でマージし、宛先と PR の番号の確認だけを足す

supervisor が使っているマージで足りる。条件 4 が求める宛先の確認は今のコマンドに無いので `--base` を足した（利用者の決定、
2026-11-26）。`--pr` は、レビューと CI の確認をした PR だけをマージするために足した。同じブランチ・宛先・HEAD で作り直された PR
をレビューしないままマージしないためである。工程が merge commit を作って直接 push する案は、保護の読み取り・完了の記録・PR の
後処理まで要る。工程の中で PR を読んで宛先を確かめコマンドを変えない案は、読む PR とマージする PR を 2 か所で選ぶ。送る直前の
照合は既にある `MergeExpect` を使う（設計の時点の `GitHub.merge` への `expect_base` の追加は、main が同じ照合を先に入れたので
足していない）。サーバー側で拒否する条件（ブランチの保護など）を自動のマージの前提にはしない（Value 3・11）。

### 決定 12: 単位が 1 つでも単位の PR とスプリントの PR の 2 本にする

条件 1・4 は、表があれば単位の数に関わらず、単位のブランチ・スプリントブランチ宛ての PR・単位の `--criteria`・レビューした
HEAD だけのマージを求める。これまでの経路は単位の範囲の指示も単位の条件も渡さない。代償は、1 単位のスプリントで PR の作成と
マージが 1 回ずつ増え、両方の PR で CI が走る設定では CI も 1 回増えることである（Value 3）。

### 決定 13: 単位の PR で待つチェックを `workflow.unit_required_checks` で選べるようにする

CI の起動の条件はリポジトリごとに違い、スプリントブランチ宛ての PR で起動しないチェックを待つと最初の単位から進めない。
`ci.required_checks` をそのまま使う案はベースブランチ宛てでだけ CI が起動するリポジトリを止め、`ci` の下にキーを足す案は、`ci`
がプロジェクトの解析が書く値で利用者が選ぶ値は `workflow` に置くので採らない。CI の定義を読んで起動を判定する案は、書き方が
提供元ごとに違う。空の並びで `ci` を外すのは、`ndf ci watch` がチェックの名前が 1 つも無いと起動できないためである。代償は、
空の並びや少ない並びを宣言するとその分の検査がスプリントの PR まで行われないことである（Value 4）。

### 決定 14: 人の判断を待つ指摘が残る単位は、分類を問わずマージせずに止める

利用者の承認は設計と本番の 2 回のままになり、分類で通すものと止めるものを分けないので分類の漏れでマージされることが無い。
前の回の指摘をファイルに残して解けるまで止める案は持ち越しと解く条件の仕組みが要り（範囲を縮めた経緯）、単位ごとに利用者の
承認を受ける案は承認の回数が単位の数だけ増え、指摘を残したままマージする案は条件 4 に反し、人が判断していない変更の上に後の
単位が積まれる。指示書の書き換えのように必ず人の承認が要る操作を含む単位は、相手役がそれを指摘するかぎり自動の経路では
通らない（Value 1・9）。

### 決定 15: 単位の作業場所とブランチは自動で消さない

後片付けは目的に要らない。工程が作ったものだけを消すには作った記録と照合が要り（範囲を縮めた経緯）、作った記録を持って一致する
ものを消す案も、同じ名前で作り直されたものを区別できない場合が残る（Value 11）。

### 決定 16: 単位の見出しが無いスプリントでも、実装の開始時にブランチを取得する

別の作業場所で足された単位の表は、実装を始める時点のリモートの先端を読まないと分からず、見落とすと分けるはずの変更が 1 本に
なる。取得 1 回は worker とレビューの起動に比べて費用が小さい。工程「計画」が記録したコミットを渡す案は記録の後に足された単位が
分からず、手元の `refs/remotes/` を読む案はいつの取得か分からず、先に `git ls-remote` で調べる案は照会が減らず違うときは 2 回に
なる。実装の開始の直前に同じブランチを取得する処理がほかにできたら、その結果を使い回して追加の取得をやめる。代償は、単位を
使わないスプリントも開始のたびに取得の時間がかかり、リモートへ届かないときは実装を始めずに止まることである（Value 2・3）。

### 決定 17: PR の番号の取り方は、テンプレートの展開の時点で共有のステップへ組み込む

共有のステップ `ci` と `impl` の `ci` は番号の取り方だけが違う。番号の取り方はテンプレートごとに決まるので、展開の時点で
`pr_source` の `command` を `@pr_command`、`arg` を `@pr_arg` へ差し込めば、監視の起動と結果の保存は `parts/steps.json` の
1 か所に残り、シェルの起動も増えない。`arg` は位置引数で渡すのでシェルのコードとして解釈されない。`impl` が `run` を丸ごと上書き
する案は手順が 2 か所になり、実行時に `sh -c` で打つ案はステップのたびにシェルの起動が 1 回増える。代償は、差し込みの形が
もう 1 つ増え、`parts/steps.json` の `ci` の `run` が展開しないと実行できないことである（Value 2・11）。

## 受け入れた代償

利用者は次の 5 つを受け入れた（1〜4 は 2026-11-26 の設計承認ゲート、5 は実装の中の判断。一覧はスプリントの PR
https://github.com/devbasex/ai-plugins/pull/4567 の本文の「利用者が受け入れた代償」）。この仕様の中では塞がない。

| # | 代償 | 決定 | 塞がない理由 |
| --- | --- | --- | --- |
| 1 | マージ先を最後に確認してからマージの要求が届くまでの間に PR の宛先が書き換えられても気づけない | 11 | PR をマージする GitHub の API は宛先を条件にできない |
| 2 | マージした単位の変更を後で打ち消しても気づかず、完了した単位として飛ばす。マージ済みの単位のタスクや条件を後で直しても飛ばし、工程の外でのマージも完了と読む | 6 | 完了の専用の記録を持たない（範囲を縮めた経緯） |
| 3 | 単位の作業場所とブランチは自動で消さず、単位の数だけ残る | 15 | 後片付けは目的に要らない |
| 4 | 打ち直したレビューが前回と同じ指摘を挙げなければ、直していなくてもマージされる。直さなくてよいと利用者が判断しても、承認するだけで単位を進める手段は無い | 14 | 指摘の持ち越しを作らない |
| 5 | 人や別の作業場所がスプリントブランチへ直接足したコミットは、コードレビューの対象に入らない | 10 | 履歴の照合を採らない |

代償 5 の中身: 単位のマージの合間に別の作業場所から push されたコードは次の単位のマージ結果に含まれ、作業場所の先端は一致して
スプリントの PR が開く。工程「コードレビュー」は `gathered` より後にコードの差分が無ければ省かれるので、そのコードはどのレビュー
も通らずに取り込みへ進む。最後の単位のマージの後に push されたコードも、利用者が「スプリントの PR」の手順で作業場所を進めて
打ち直せば `gathered` に含まれる。利用者が PR に含めてよいと確かめても、コードレビューを受けたことにはならない。

## 実装で見送った指摘（決定 10 に関するもの）

単位の実行と有効化の単位の PR（https://github.com/devbasex/ai-plugins/pull/4593 ）の cross-review で、次の指摘を承認済みの
設計の範囲として見送った（記録は https://github.com/devbasex/ai-plugins/pull/4593#issuecomment-7206374251 ）。

| 指摘 | 中身 | 見送った理由 |
| --- | --- | --- |
| r7-1 | 単位のマージの合間に別の作業場所から push されたコードが、先端の一致で `gathered` に入り、レビューを経ない。確かめられない差分があればスプリントのコードレビューを必須にすべき | 受け入れた代償 5 そのもの |
| r8-1 | 最後の単位のマージの後に push されたコードも、案内どおり進めて打ち直すと `gathered` に入りレビューを経ない | 同上 |
| r8-2 | 利用者が確かめた後も、作業場所の fast-forward と打ち直しを利用者に求める。確かめた SHA を回答に記録し NDF が同期すべき | 承認済みの決定 10 の形（先端が違えば止まり、利用者が確かめてから打ち直す） |
| r8-3 | 確かめた SHA まで進められるかの検査と fast-forward を復旧の手順として NDF が持つべき | 同上 |

あわせて推された「`gathered` を最後の単位のマージコミットにし、リモートだけが進んでいれば NDF が fast-forward して止まらずに
PR を開く（後から入ったコミットは `gathered` より後の差分になり、工程「コードレビュー」が必ずレビューする）」形は、決定 10 と
`gathered` の意味を変える設計の変更になるので、この課題では採っていない。r7-1 の最後の単位より前に入ったコミットには、各単位の
マージコミットの第 1 親を確かめる案・確かめられない差分でスプリントのコードレビューを必須にする案・代償として受け入れる案が
挙がり、代償として受け入れた。
