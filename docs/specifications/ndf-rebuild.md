# NDF の作り直し: 別のディレクトリで 0 から作り、`ndf` と入れ替えた 11.0.0

#1142 は、NDF のスクリプト全体をモデルとクラスの設計から作り直した。今の `plugins/ndf/` は、別のディレクトリ（開発の間は `plugins/ndf-next/`）で 0 から作ったものを、S2 #3304 の 1 本の PR で `git mv` して入れ替えた 11.0.0 の系列である。この文書は作り直しの索引で、目的・構造・入れ替えの結果・子の記号・番号の対応表と、配置と入れ替えと hook の基盤と依存の版の決定を持つ。部品ごとの決定は下の索引の 5 本が持つ。

## 概要

**例: 10 系から 11.0.0 へ上げた利用者の手元。** 取得元 `./plugins/ndf` とプラグイン名 `ndf` は変わらないため、登録し直さずに `plugin update` で 11.0.0 が届く（決定 73）。最初の起動で、新しい NDF は 10 系の状態のホーム `~/.local/state/ndf` とチェックアウトの置き場 `<git の共通ディレクトリ>/ndf/state` を `<元の名前>.v10-<YYYYMMDD>` へ名前を変えて退避し、新しい形の置き場を作る（決定 79・85）。以後のプランの実行は鍵ごとの `state/dbos/<鍵>.sqlite` に、進行表は `state/progress.sqlite` に書く（決定 81）。

## 背景

10 系の NDF のスクリプトは Issue ごとの継ぎ足しで育ち、500 行を超えるファイルと、同じ名前で本体の違う関数が多く残った。#1142 はまず今のコードを子 Issue 72 本・22 の順番で段階的に直す計画を立てた（PR #3250）。しかし進行表 #3092 の実装 PR #3247 は 246 ファイルを書き換えて major の指摘 25 件と CI の失敗 70 件が残り、4 ラウンドの cross-review でも直らずに閉じた。動いている仕組みをその場で置き換えると、旧い経路との互換・移行・旧いテストの書き換えが変更の大半を占める。

そこで利用者は 2026-11-13 に、同じリポジトリの別のディレクトリで 0 から作り、できたら `ndf` と入れ替えると決めた。同時に、後方互換を置かない・テストを 1 から作り直す・実装の間はほかの開発を止める、と決めた。作り直しの目的は次のとおりである。

- スクリプトの変更 1 回で読む量を減らし、触るファイルが重ならない単位でスプリントを並べられるようにする
- 同じ概念の実装を 1 つにし、汎用の処理は既存のライブラリを使う
- 工程・文書の種類・モード・閾値などの事実を、コードの定数ではなく 1 か所のデータに持つ
- 分岐と例外の行き先をスクリプトが決め、AI は実装・レビューの中身・文書を書く補助として呼ばれるだけにする
- 改善の効果を、入れ替えの前後で同じ物差しで測る
- ほかのプロジェクトでも同じように使える形を保つ（プロジェクトごとに違うものは `.ndf/` の宣言か引数で受ける）

**要求の受け入れ条件のオーナー。** #1142 の本文の受け入れ条件は、次の本が仕様として持つ（11.x の行は #3388 の子が持つ）。11.0.0 の 7 つの条件（同等・機能の対応表・試走・退行させない・リリースの workflow）は `ndf-rebuild-review-scope.md`、計測と振り返りは `ndf-rebuild-measure.md`、設計（モデル・責務・エントリポイントの一覧）はこの文書の「仕様」、構造（行数の上限・同じ概念の実装を 1 つ）と外部パッケージ（不足 h）は [ndf-rebuild-libraries.md](ndf-rebuild-libraries.md) とこの文書の I22、AI が陥りやすい作り・定数からデータへは [ndf-rebuild-data-and-smells.md](ndf-rebuild-data-and-smells.md)、AI の判断からスクリプトへは `ndf-rebuild-scripted-flow.md`、退行しないことはこの文書の「テスト観点」が持つ。

## 対象範囲

- **含む**: `plugins/ndf/` の全体（スクリプト・契約・hook・Skill 本文・エージェント定義・テスト）、`bin/ndf` の副命令、CI の NDF の検査、中継の複製 `~/.claude/ndf/relay.py`、利用者の手元の旧い状態の置き場の退避
- **含まない**: playwright-kit と mcp-* のスクリプト、NDF を呼ぶ Web サービス（別のリポジトリ）、11.x へ回した項目（#3388 の子）。Skill とエージェントの本文は、パスとコマンドを直した範囲だけを含む
- **プロジェクトごとに違うもの**: 足さない。利用先のリポジトリには 11.0.0 以降の版として届く

## 仕様

### 構造

**コンテキストは 3 つで、契約の形は上流が決める。**

| 上流 | 下流 | 契約 |
| --- | --- | --- |
| 配布（プラグイン・取得元・版） | 進行・プランの実行 | `plugin.json` のプラグイン名と版。状態の置き場の名前もここから求める（決定 75） |
| プランの実行（プラン・ステップ・止まった理由・行き先） | 進行（工程・進行表・行・承認ゲート・レーン） | 進行表の行が工程から作業を呼ぶ層を通してプランを呼び、結果 JSON の `cause`・`outputs` を読む。プランの実行は進行表を読まず書かない |

**集約ごとに書き手は 1 つである。**

| 集約 | 書き手 | 根 |
| --- | --- | --- |
| プラグインの定義 | 版上げの PR | `.claude-plugin/plugin.json`・`.codex-plugin/plugin.json` |
| 止まった理由の表 | 結果 JSON の契約を変える PR（下流の読み手とそのテストも同じ PR で直す） | `contracts/causes.json` |
| 進行表 | `progress` の書き手 | 進行表の DB |
| 耐久の記録 | DBOS の殻（ほかは殻の関数を通してだけ読み書きする） | 実行の鍵の記録（SQLite は鍵ごとのファイル、URL は鍵ごとの `application_name`） |
| チェックアウトの置き場 | DBOS の殻が形の番号を確かめて用意する | `<git の共通ディレクトリ>/<プラグイン名>/state/` |
| 子の表のコピー | 設計 PR（表を変える設計を先に通す） | `src/ndf/checks/children.json` |

**層の向きは `contracts` → `adapters` → `core` → `progress` → `domains` の 1 方向で、`ndf check` の規則 `structure` が逆向きの import を落とす。** 名前が `_decide` で終わるモジュールは判断だけを持ち、入出力のモジュールを import しない。

### 入れ替え（S2 #3304）の結果

- `plugins/ndf/` を消してから `git mv plugins/ndf-next plugins/ndf` を打ち、版上げの PR で 11.0.0 を出した。プラグイン名は `ndf`、取得元は `./plugins/ndf` のまま（決定 73）。新しいディレクトリの中で書き換えたのは `plugin.json` 2 本と、名前から作る生成物（hook の登録・Codex の定義）だけである（決定 75）
- 外から `plugins/ndf/` の中を名指す参照は、R0 #3757 が入れ替えより先に検査と書き換えの表を入れ、入れ替えの PR が表を当てた。CI の `scripts/check-plugin-refs.py` が参照先の実在を確かめる
- 開発の間のジョブ（`plugins/ndf-next/**` だけを見るもの）は消し、`ndf check` は `script-structure.yml` が打つ
- 旧い状態の置き場の退避と、中継の複製の版の記録は R1 #3758 が入れた（決定 79）
- 子の表のコピー `children.json` と規則 `child-deps` は残り、閉じていない子の import の向き・順番・レーンを照らす

### エントリポイント

**利用者・Skill・hook・CI が呼ぶのは次だけで、スクリプトのパスを直に呼ばない。** 10 系の 45 本のエントリポイント（`supervise.py`・`relay.py`・各 Skill の `scripts/` など）は、互換の経路を置かずに `bin/ndf` の副命令へ置き換えた（決定 76）。

| エントリポイント | 呼び手 | 形 |
| --- | --- | --- |
| `bin/ndf <副命令>` | Skill の手順・プランの雛形・CI・利用者 | 副命令は `cli.COMMANDS`（`answer`・`check`・`ci`・`contracts`・`cross-review`・`gws`・`hooks`・`issues`・`lanes`・`launch-args`・`loop`・`manifests`・`materials`・`notify`・`plan`・`progress`・`project`・`records`・`refactor`・`relay`・`release-steps`・`route`・`settings`・`statusline`・`test-slot`・`training`・`worker`・`worktree`）。結果 JSON を 1 つ出し、終了コードは止まった理由の表から引く |
| `hooks/entry.py`・`hooks/boot.py` | Claude Code・Codex の hook の登録（事象ごとに 1 行） | `argv[1]` がランタイム、`argv[2]` が事象（決定 89） |
| `bin/ndf-claude` | このプラグインを試す起動 | 入っている同じ名前のプラグインを外して `--plugin-dir` で読む |
| `~/.claude/ndf/relay.py`・`~/.local/bin/ndf-relay` | 利用者の端末 | `ndf relay install` が置く標準ライブラリだけの複製。隣の `relay.root` が指すプラグインの `bin/ndf relay` を呼ぶ |

### 常に成り立つ条件

| # | 対象 | 条件 | 破れたときの扱い |
| --- | --- | --- | --- |
| I1 | プラグイン | `src/` の `.py`・`bin/`・`hooks/` のスクリプトは、自分のプラグイン名・ディレクトリ名・状態の置き場の名前を文字で持たない。照合する名前は今の名前と入れ替えの後の名前 `ndf`（`identity.FINAL_NAME`）の両方で、固定の語は `identity.FIXED_WORDS` の定義の行だけが通る（決定 75・101） | `ndf check` が CI で落とす |
| I2 | プラグイン | 入れ替えの前は、子の PR が旧いプラグインを変えない（即時修正を除く） | 入れ替えで旧いプラグインが無くなり、検査から外した（`checks/invariants.py`） |
| I3 | プラグイン | import は自分のパッケージ・標準ライブラリ・`pyproject.toml` に定義した依存だけ | `ndf check` が落とす |
| I4 | 進行表 | 進行表のほかに、工程の遷移を決めるものを置かない | 工程の定義の登録が断る |
| I5 | 耐久の記録 | ある鍵の耐久ワークフローを取り出して流すのは、同じ鍵で起動したプロセスだけ（決定 81） | 2 つのプロセスが鍵違いで開くテストで、相手のキューを流したら落ちる |
| I6 | 耐久の記録 | 1 つの鍵の記録を開くプロセスは同時に 1 つで、`executor_id` と `application_name` は鍵から求めた同じ値 | 2 つ目は鍵のロック（SQLite は `run_lock`、URL は DB 側の鍵のロック）で待つ。片付けは待たずに試し、取れた鍵だけを移す・消す |
| I7 | 耐久の記録 | アプリの版は形の番号と鍵の名前だけで決まり（`format-<FORMAT>-<鍵の名前>`）、NDF の版とワークフローのソースでは変わらない（決定 84） | `plugin.json` の版だけを上げて起動し直すテストで、途中の実行が回復しなければ落ちる |
| I8 | 耐久の記録 | SQLite では退避の単位は鍵のファイル全体で、鍵の耐久ワークフローがすべて終わった（`SUCCESS`・`ERROR`・`CANCELLED`）ときだけファイルごと `dbos/retired/` へ移す。同じ鍵に待ちを抱えた実行（`PENDING`・`ENQUEUED`・`DELAYED`）がある間は、終わったステップや実行の記録もファイルに残り、実行の単位で記録を取り除かない。待ちを抱えた実行は日数で消さない。URL では鍵の実行の 1 つでも待ちを抱えるか、終わってから `KEEP_DAYS` を過ぎていなければ 1 つも消さない（決定 83） | 退避と消去のテストで待ちの記録が消えたら落ちる |
| I9 | チェックアウトの置き場 | 進行表の DB は DBOS の表を持たない。SQLite の進行表の DB は、`quick_check` が `ok` を返した目印（`state/progress.checked`）が 24 時間以内に無ければ、`ok` を返すまで書かない。書き込みが `SQLITE_CORRUPT` を受けたら目印を消す（決定 82） | 目印の無い壊したファイルを開くテストで、書き込みが起きたら落ちる |
| I10 | チェックアウトの置き場 | 形の番号が自分と違う置き場へは書かない。古ければ置き場ごと退避し、新しければ止まる（決定 85） | 番号を上げた・下げた置き場を開くテスト |
| I11 | チェックアウトの置き場 | 置き場を使うプロセスは `state.lock` を共有で持つ。置き場ごとの退避と進行表の DB の `restore` は、`state.lock` を排他で取れ、退避では旧い置き場の鍵のロックもすべて、`restore` では `<実ファイル>.lock` も取れたときだけ行う。進行表の DB を開くプロセスは、接続の前に `<実ファイル>.lock` を共有で取り、全接続を閉じるまで持つ（決定 82・85） | 共有で持つプロセスがいる間に退避・`restore` を打つテストで、名前の変更か控えの配置が起きたら落ちる |
| I12 | 耐久の記録 | URL の片付けが消すのは、台帳 `ndf_runs` に `durable.launch` が書いた鍵の実行だけ（決定 83） | 台帳に無い `run-` で始まる終わった実行が消えたら落ちる |
| I13 | 耐久の記録 | URL では、同じ鍵の起動と片付けは DB 側の同じ鍵のロックの下で直列に起きる（決定 83） | 鍵のロックを別の接続が持つ間に片付けを打つテストで、その鍵の実行か台帳の行が消えたら落ちる |
| IH1 | hook の登録 | 事象 1 つにつき登録は 1 行・プロセスは 1 本。payload・シェルの構文木・会話の記録の末尾・最後の応答の分類は 1 回の事象で 1 度だけ作る（決定 88） | 登録の検査と、解析の呼び出し回数を数えるテストが落とす |
| IH2 | hook の入口 | 入口から import でたどれるのは標準ライブラリと `contracts/hooks/imports.json` で許した依存だけで、`bin/ndf` を通らず、依存を入れ直す処理を呼ばない。環境が無いときはシステムの `python3` で `boot.py` を動かし、`strict` の guard と SessionStart の環境の用意の起動だけを行い、ほかは出力なし・終了コード 0。`python3` も無ければ 0 で終わる（決定 89） | import の閉包を構文木でたどるテストと、環境を消した状態で全事象を起動するテストが落とす |
| IH3 | 予算 | 事象ごとに「部品の上限 ≤ 締め切り − 余白」「締め切り ≤ 登録の timeout」が成り立ち、すべての登録に timeout がある（決定 90） | `check_budget` が SessionStart で案内を出し、CI で落ちる |

## 決定と理由

### 決定 73: 入れ替えは `git mv` で行い、プラグイン名と取得元を変えない

導入の鍵は取得元の名前とプラグイン名で、リポジトリの中のディレクトリを含まない。名前 `ndf` と取得元 `./plugins/ndf` を保てば、利用者は登録し直さずに `plugin update` で 11.0.0 を受け取る。外からの参照は、書き換えの表と検査を R0 #3757 が先に `main` へ入れ、入れ替えの PR が当てた。

- 採らなかった案: `plugins/ndf-next/` を残してマーケットプレイスの `source` だけを差し替える。外からの参照を向け直す漏れが、空のディレクトリを見て 0 件で通る検査を生む
- 代償: 入れ替えの PR は大きく、戻すと版上げごと戻る

### 決定 74: 開発の間は新しいプラグインをマーケットプレイスへ載せない

載せると開発版の利用者の手元で hook が二重に走り、状態の置き場も混ざる。試す起動は `bin/ndf-claude` で、入っている同じ名前のプラグインを `--settings` の `enabledPlugins` で外し、`--plugin-dir` でこのプラグインを読む。外す設定と読む引数は `ndf launch-args`（`adapters/claude.py` の `plugin_args`）の 1 か所から読み、自分の `plugin.json` の名前の行は外さない。利用者の設定ファイルは書き換えない。

### 決定 75: プラグインの中では自分の名前を文字で持たない

ディレクトリは `CLAUDE_PLUGIN_ROOT` か `__file__` から、プラグイン名と Skill の前置きは `plugin.json` の `name` から、状態の置き場の名前はプラグイン名から求める。名前を変えるときに書き換えるのは `plugin.json` 2 本と、`ndf hooks render`・`ndf manifests render` で作り直す生成物だけになる。Python のパッケージ名 `ndf` はプラグイン名から切り離した固定の名前である。

### 決定 76: 10 系との互換と動いているスプリントの取り込みを作らない

副命令名・引数・`plan.json` の形を 10 系の `supervise.py`・`parallel.py` に合わせず、動いているスプリントの取り込み（`adopt`）も作らない。入れ替えの前に 10 系で動いていたスプリントを終わらせたため、取り込むものが無い。

- 代償: 入れ替えの時点で動いているスプリントは、10 系のまま終わらせてから移る

### 決定 77: #1142 と #3092 の設計の食い違いは #3092 の側にそろえる

承認ゲートは #3092 の決定 7 のとおり `recv` で待ってプロセスを抜け、`answer` の後の `next` で続ける。終了コードは止まった理由の種類から引き、「工程の失敗は 1」は採らない。`jsonschema` の依存は `pyproject.toml` の 1 つの一覧に置く（グループに分けない）。0 から作るなら、続きを手で組み立てる経路を持つ理由が無い。アプリの版と DBOS の記録の置き場は決定 84・81 が持つ。

- 採らなかった案: 承認ゲートで結果を関門にしてプランを終え、`--from` で続ける（前の企画の形）。0 から作ると `--from` を手で組み立てる経路だけが残る

### 決定 78: プラグインは自分の依存の宣言と lock を持つ

`plugins/ndf/pyproject.toml` と `uv.lock` を置き、テストは `uv run --frozen --project plugins/ndf` で走らせる。リポジトリの根の `pyproject.toml` は根の `scripts/` のためのもので、プラグインはそこから読まない。

### 決定 79: 旧い状態のホームとチェックアウトの置き場だけを、置き場ごとの条件と時点で退避する

10 系が状態を書く置き場 14 種のうち、新しい NDF が同じパスへ書き、状態を持つ 2 つ（`~/.local/state/ndf` と `<git の共通ディレクトリ>/ndf/state`）だけを退避する。どちらも名前の変更だけで `<元の名前>.v<旧い形の版>-<YYYYMMDD>` へ移し、消さない。退避の条件と時点は置き場ごとに違う。

| 置き場 | 退避する条件 | 時点 | 持ち主 |
| --- | --- | --- | --- |
| 状態のホーム | `format.json` が無く、書き途中の一時ファイル（`.format.json.<pid>.tmp`）のほかにファイルがある（`identity._is_old`）。`format.json` があれば番号を比べず、退避しない | `bin/ndf` の副命令の前と、状態のホームへ書く部品が `identity.prepare_state_dir` を呼んだとき | `identity.py` |
| チェックアウトの置き場 | 書き途中の一時ファイルのほかにファイルがあり、`format.json` から番号を取れないか、番号が `STORE_FORMAT` より小さい（番号の読み方は決定 85）。ファイルの無い置き場は退避せずに作る | DBOS の殻が置き場を使う前（`durable.prepare_store`） | `core/durable.py` |

状態のホームの退避先の版は 10（`LEGACY_FORM`）、チェックアウトの置き場の退避先の版は読んだ番号である。ただしデータのあるチェックアウトの置き場で `format.json` から番号を取れないときは、状態のホームと同じ 10（`LEGACY_FORM`）を使う（`durable._read_format` は内部の値 0 を返し、`_retire_store` が `None` に変えて `identity.retired_name` へ渡す。退避名を `.v0-…` にせず、番号が取れないことで止めもしない）。状態のホームは、退避する候補があるときに限り、呼び出し元のプラグインの根が実行中のプラグインの根と違えば、何も変えずに止まる（`identity._refuse_unsafe_retire` の `IdentityError`。別のプラグインの根から起動されたプロセスに利用者の旧い状態を動かさせない）。`bin/ndf` は呼び出し元の `CLAUDE_PLUGIN_ROOT` を `NDF_CALLER_PLUGIN_ROOT` へ写してから `CLAUDE_PLUGIN_ROOT` を自分の根で上書きするので、呼び出し元の根は `NDF_CALLER_PLUGIN_ROOT` が設定されていれば（空でも）その値、設定されていなければ `CLAUDE_PLUGIN_ROOT` の値とする（`identity._foreign_root`）。その値が空か未設定なら比べずに退避する。退避先が既にあれば止まり（`retire_target_exists`）、旧い置き場の錠を待たずに取れなければ止まる（`legacy_running`）。退避する置き場が退避しない置き場（表 `OLD_STATE_LOCATIONS` の `KEEP` の行。アカウントの設定・旧い NDF のジャーナル・動いているプロセスの排他など）を中に持てば、名前を変える前に何も変えずに止まる（`identity.refuse_holding_kept`。両方の置き場が呼ぶ）。重ならない置き場は退避しない。中継の複製を置き換えるときは `relay.version` へ自分の版を書き、10 系の起動に戻されないようにする（`domains/relay/install.py`）。

- 採らなかった案: 状態のホームも番号を比べて退避する。移行を済ませた利用者の状態のホームまで、形の番号を上げるたびに動く
- 代償: 利用者の手元の 10 系の記録と進行中のプランは読まれない（名前を戻せば 10 系で続けられる）

### 決定 80: 旧い子 Issue は閉じずに新しい子へ結び、入れ替えまでに閉じる

前の企画の子 72 本は消さず、取り込んだ新しい子の本文に番号を書き、その子の PR の closing keywords で閉じた。要らなくなった子は入れ替えの PR で理由を添えて閉じた。ラベルの件数を進み具合の目印にしていたため、先に閉じると件数が実態とずれる。

### 決定 81: 別のレーンがよそのキューを流さないよう、DBOS の記録を実行の鍵ごとに分け、1 つの DB には進行表だけを置く

SQLite では DBOS の記録を `state/dbos/<鍵の名前>.sqlite` に、進行表と進行の事象を `state/progress.sqlite` に置く。URL（PostgreSQL）では両方を 1 つの DB に置き、DBOS の記録を `application_name` で鍵ごとに分ける。DBOS のキューの取り出しは `executor_id` で絞らず、`application_name` が一致するか `NULL` の行を取り出すため、1 つの DB を開いたプロセスどうしは互いのキューを流す。鍵ごとに分けると相手の行が見えず、`BEGIN IMMEDIATE` の待ち・見回り・壊れたとき・消す単位も 1 つの実行に閉じる。

- 採らなかった案: 1 回の起動を 1 つのプロセスと 1 つの SQLite で動かす形を、進行表との同居（#3092 の決定 2）へ一度寄せた。取り出しの混ざりが起きるため、鍵ごとの記録へ戻した（前の企画の決定 26 の形）
- 採らなかった案: 1 つの DB のまま起動ごとに `application_name` を分ける。34 本のプロセスが同じファイルへ `BEGIN IMMEDIATE` を掛け、1 つの破損がすべてのレーンに効く
- 代償: キューの同時の本数は 1 つの実行の中でだけ数え、レーンをまたぐ枠は持たない

### 決定 82: 進行表の DB が壊れても気づいて戻せるよう、その日の最初に開くときに `quick_check` を打ち、backup API で控えを取る

SQLite の進行表の DB は WAL・`busy_timeout` 30 秒で開き、目印 `state/progress.checked` が 24 時間より古いか無ければ、`maint.lock` を排他で取って期限を読み直してから `PRAGMA quick_check` を打つ。`ok` でなければ書かずに止まり（`store_broken`）、最新の控えと戻す副命令（`ndf progress restore --from`）を返す。控えは Online Backup API で取り、新しい 7 本を残す（`progress/backup.py` の `KEEP_BACKUPS`）。鍵ごとのファイルも鍵ごとの目印で同じ検査を受け、壊れていれば `dbos/broken/` へ移す。`ndf` は呼ぶたびに新しいプロセスで動くため、検査を「プロセスで最初に開いたとき」にすると回数が呼び出しに比例する。URL ではどれも打たず、DB の運用に任せる。

- 代償: 開いた後に壊れた分は、書き込みの失敗（`SQLITE_CORRUPT`）として呼び手に返る。壊れた DB を控えで自動では置き換えない

### 決定 83: 置き場が膨らみ続けないよう、終わった実行の鍵ごとのファイルを退避し、退避から 14 日で消す

終わった鍵のファイルは本体と `-wal`・`-shm`・`-journal` をそろえて `dbos/retired/` へ移し、鍵の `.checked` と `.lock` を消す。鍵に終わっていない耐久ワークフローが 1 つでもあれば移さない（I8）。目印 `dbos/.swept` が 24 時間より古ければ、`retired/`・`broken/` と、表の移行の前に取る鍵のファイルの控え `backup/` の 14 日（`durable_sweep.KEEP_DAYS`）より古いファイルを消す（`durable_sweep._sweep_kept`）。走査はどれも `maint.lock` を待たずに取れたときだけ流し（取れなければ飛ばす）、操作ごとの排他と時刻の基準は次のとおりである。

| 操作 | 排他 | 時刻の基準 |
| --- | --- | --- |
| ライブの鍵のファイルを `retired/` へ移す（`_retire_finished`） | `maint.lock` に加え、その鍵の `.lock` を待たずに取れたときだけ（取れない鍵は開いているプロセスがいるので触らない） | 時刻は見ない。鍵の耐久ワークフローがすべて終わっていること。移す前に更新時刻を移した時刻に付け直す |
| `retired/`・`broken/`・`backup/` の古いファイルを消す（`_sweep_kept`） | `maint.lock` だけ。鍵のロックは取らない。作る側と移す側は鍵のロックを持つ: `backup/` の控えは鍵のロック（`run_lock`）を持つ起動（`durable.launch`）が表の移行の前に作り、`broken/` へは同じ起動が鍵のロックの下で移し、`retired/` へは `_retire_finished` が `maint.lock` と鍵の `.lock` の下で移す。`retired/` への移動は同じ `maint.lock` の下で行うので掃除と直列になる。`broken/` への移動と `backup/` の新規作成は `maint.lock` を取らず、掃除と並行して起こりうるので、移す側は移す前に更新時刻を移した時刻に付け直し（`_move_out`。`retired/` への移動も同じ関数を通る）、作ったばかり・移したばかりのファイルが元の古い時刻で消されないようにする | ファイルの更新時刻が 14 日より古いこと |
| URL の鍵の記録と台帳の行を消す（`_sweep_url_run`） | `maint.lock` に加え、その鍵の advisory lock を待たずに取れたときだけ（起動と直列になる） | 鍵の実行がすべて終わり、どれも最後の更新から 14 日を過ぎたこと（実行が無ければ台帳の開始時刻） |

URL では台帳 `ndf_runs` に載った鍵だけを消す。DBOS の `delete_children` には頼らない（待ちの子まで消す）。

- 採らなかった案: DBOS に日数で消させる。保持期限で消す設定と公開の関数が無い
- 代償: 消した記録は戻せない。失敗の調べ物は 14 日の中で済ませる

### 決定 84: 開発版が出ても途中の実行を回復できるよう、アプリの版を NDF の版から切り離した形の番号にする

`durable.launch` は `application_version` に `format-<FORMAT>-<鍵の名前>`（`durable.app_version`）を渡す。版名は DB 全体で一意のため鍵の名前を入れる。`FORMAT` を上げるのは耐久ワークフローの中の DBOS の呼び出しの順を変えたときだけで、上げ忘れは `@durable.workflow` の関数のソースの hash を `FORMAT_SOURCE_HASH` と比べるテストが落とす。

DBOS が回復で流すのは、`application_version` が今の `app_version` と同じ実行だけで、NDF は版の違う実行を照合して書き換えない。`FORMAT` の違う実行は回復されず、待ちの状態のまま記録に残る。`ndf plan pending` が一覧に出し、レーンの起動は形の番号の違いで止まる（決定 86）。自動では取り消さず、行も失敗にしない。`durable.cancel_before_launch` は、DBOS を起動せずに指定した 1 つの実行とその子を取り消す関数だけを提供し、本番コードの呼び手は無い（取り消すかは人が決めて呼ぶ）。

- 採らなかった案: 更新で再開できなかった待ちの実行を自動で取り消す。取り消しは戻せず、形の番号を戻した版なら続けられた実行まで失う
- 採らなかった案: 形式の版を NDF の版から切り離した定数にする前の企画の形を、NDF の版で回復できない実行を取り消す形（#3092 の決定 21）へ一度寄せた。開発版が出るたびに途中の実行が取り消されるため、定数の形へ戻した
- 採らなかった案: `DBOS.patch` で旧い実行と新しい実行を同じ版で流す。分かれ目がコードに残り続ける

### 決定 85: 形の違う置き場を読み違えないよう、チェックアウトの置き場の `format.json` に形の番号を持たせ、合わなければ書かない

DBOS の殻は置き場を使う前に `format.json` の番号を `STORE_FORMAT` と比べる。無い・空（書き途中の一時ファイルだけ）なら作り、データがあって `format.json` から番号を取れない（ファイルが無い・読めない・壊れた JSON・`format` キーが無い・値を `int()` で整数にできない）か番号が小さければ置き場ごと退避して作り直し（番号を取れないときの退避先の版は 10。決定 79）、同じならそのまま使い、大きければ書かずに止まる（`format_newer`）。`durable._read_format` は値を `int(...)` で読むため、`"2"`・`2.5`・`true` も `int()` の結果（2・2・1）を番号として比べる。JSON の整数だけを受け取る直しは #3978 が持つ。退避は `state/` の外の `state.lock` を排他で取り、番号を読み直し、旧い置き場の鍵のロックと `progress.sqlite.lock` をすべて取れたときだけ行う（取れなければ `store_in_use`）。ロックは標準の `fcntl.flock` で取る（`core/durable_locks.py`）。ほかのファイルの排他に使うライブラリの選択は `ndf-rebuild-review-scope.md` の決定 119 が持つ。

- 採らなかった案: 置き場の中のファイルだけを移して `state/` を残す。開いたままの DB とロックが移した先を指し続ける

### 決定 86: 版の混ざりで止まらないよう、レーンの起動では形の番号がそろっているかを確かめ、NDF の版の違いは記録だけにする

レーンの起動は、計画が記録した形の番号（`STORE_FORMAT`・`durable.FORMAT`・進行表の表の版）を自分のものと比べ、違えば止まる（`format_mismatch`）。NDF の版だけが違えば止まらずに `warnings` に残す。プラグインを更新する前の待ちの一覧は `ndf plan pending` が出し、中継は再起動の前にそれを結果に載せる。

- 採らなかった案: 計画の中の NDF の版がすべて同じでなければ起動しない。決定 84 の後は版の違いで壊れるものが無い

### 決定 87: DBOS は 3.4.0 で出し、殻の直しを C2 の前の 1 本の PR にした

DBOS 3.5.0 は公開から 7 日を待つ決まりに当たったため、C1+ は 3.4.0 で出した。3.4.0 でもキューの取り出しは `executor_id` で絞らず、`application_versions.version_name` は DB 全体で一意で、決定 81・84 の前提が成り立つ。殻の直しは C1 #3285 の追補として 1 本の PR にし、殻の直しだけを revert できるようにした。3.5.0 への引き上げは X2 #3370 の依存の更新に含む。

### 決定 88: hook が増えても所要と解析が増えないよう、事象 1 つにつき登録 1 行・プロセス 1 本にし、guard を表で並べて入力を 1 回だけ解析する

登録の command が起動する入口は、guard の表 `contracts/hooks/guards.json` を `order` の順に呼ぶ。表は guard ごとに事象と Tool・順序・`strict`・`fail_closed`・`suggests`・`deny_key` を持つ。解析は入口が作る `HookContext` が 1 度だけ行い、会話の記録は末尾の決まった大きさ（`hook.transcript-tail`）だけを読む。10 系で別のプロセスが受け持った AskUserQuestion と Stop の判定は、同じプロセスの中の関数にした。

- 採らなかった案: 事象ごとに 1〜3 行の登録のまま解析の結果をファイルで渡す。Claude Code は同じ事象の登録を並列に起動し、順序が決まらない
- 採らなかった案: guard の振り分けに pluggy を使う。表の当たり・順序・締め切りは自前で書くことになり、import に 18.5 ms かかる

### 決定 89: 環境が無くても Tool の呼び出しを止めないよう、hook は `bin/ndf` を通らない軽い入口から始める

登録の command は用意済みの環境の python で `hooks/entry.py` を直に起動し、環境が無ければシステムの `python3` で `hooks/boot.py` を、それも無ければ 0 で終わる（`sh -c '[ -x "$0" ] && exec "$0" "$@"; command -v python3 …'`）。依存の環境は `<キャッシュ>/<プラグイン名>/venv/<uv.lock の hash>` に作る。`boot.py` は `strict` の guard の判定と、SessionStart のときの `python3 -m ndf.domains.hooks.env prepare` の切り離した起動だけを行う。用意は排他を取って一時の置き場に `uv sync --frozen` で作って名前を変え、根の目印から指されず `hook.venv-keep`（7 日）使われていない環境を消す。`uv run` も依存の入れ直しも挟まずに決まった環境の python を直に起動する方針と lock の hash ごとの環境は、hook の経路だけに当てる（前の企画の hook の依存の決定から引き継いだ）。

CLI の起動形は別で、hook の経路に合わせない。

| 経路 | 起動形 | 依存の環境 |
| --- | --- | --- |
| hook（`hooks/entry.py`・`hooks/boot.py`） | 用意済みの環境の python を直に起動する。`uv run` を挟まない | `<キャッシュ>/<プラグイン名>/venv/<uv.lock の hash>` |
| CLI（`bin/ndf`） | `uv run --frozen --no-dev --project <根> python -P bin/start.py`。uv が無ければ版を固定した uv を入れてから続け、`start.py` が依存の欠けを確かめてから `python -m ndf` と同じに呼ぶ | `<キャッシュ>/<プラグイン名>/venv/<NDF の版>`（`UV_PROJECT_ENVIRONMENT`） |

- 採らなかった案: hook も `bin/ndf` から起動する。依存の確かめと起動し直しが毎回の所要に入る
- 採らなかった案: 古い環境の片付けを `uv cache prune` に任せる。NDF が lock の hash ごとに置いた環境は対象に入らない

### 決定 90: 遅い hook と長い注入を CI で見つけるよう、事象ごとの予算を `limits.json` に置き、上限の順序を検査し、すべての登録に timeout を付ける

| 事象 | p95 の目標 | 締め切り | 余白 | timeout | 注入の上限 |
| --- | ---: | ---: | ---: | ---: | ---: |
| PreToolUse・PermissionRequest・PostToolUse | 100 ms | 1 秒 | 0.5 秒 | 3 秒 | 600 字 |
| UserPromptSubmit | 100 ms | 1 秒 | 0.5 秒 | 3 秒 | 2,000 字 |
| Stop | 300 ms | 3.5 秒 | 1.5 秒 | 6 秒 | 2,000 字 |
| SubagentStop | 300 ms | 3.5 秒 | 1.5 秒 | 6 秒 | 800 字 |
| SessionStart | 300 ms | 3.5 秒 | 1.5 秒 | 6 秒 | 1,500 字 |
| SessionEnd・Notification・StopFailure | 300 ms | 3.5 秒 | 1.5 秒 | 6 秒 | 0 字 |
| SessionEnd（Codex） | 300 ms | 2 秒 | 0.5 秒 | 3 秒 | 0 字 |

値は `limits.json` の `hook.budget.<事象>`（ランタイムで違えば `.<ランタイム>`）にある。UserPromptSubmit と Stop の注入の上限は、人のいない実行の案内が収まる字数である。部品の上限は `締め切り − 余白` 以下にする。鍵をまたぐ順序は JSON Schema で書けないため `check_budget` が確かめ、SessionStart では 1 行の案内を出して続ける。注入の上限は Claude Code が会話へ入れる上限 10,000 字より小さい。

### 決定 91: hook の不具合で作業が止まらないよう、失敗は通す側に倒し、止める側に倒すのは宣言した guard だけにする

`strict` の guard（本番チャネルへのマージを見る `merge-production`）は標準ライブラリだけで書き（`domains/hooks/strict.py`）、入口が依存の import より先に呼ぶ。環境が無いときも `boot.py` から同じものを呼ぶ。問い合わせの転送（`ask-forward`）は `fail_closed` で、締め切りを過ぎても呼び、guard の外へ出た例外を拒否にする（#3814）。拒否にする範囲は、中継の下でロックの中に今の起動（`NDF_RELAY_LAUNCH` と `launch.json`）の質問として記録できなかったときだけである。中継へ記録できた後の失敗は、通常の例外と締め切りで経路が分かれる。

| 起きたこと | 捕まえる所 | 振る舞い |
| --- | --- | --- |
| オーガナイザーの質問の保存先への書き込みや待ちの知らせが例外を投げた | `ask.check` が転送ごとに捕まえる | 質問を通し、例外の種類を計測の `forward_errors` に残す |
| 入口の締め切りの割り込みが来た（オーガナイザーのロックの待ちなど） | guard の外。`main._deadline_out` が `ask.on_deadline` を呼ぶ | 中継の外（中継の置き場が無い）なら `None` を返し、質問を通す。中継の下でこの実行の記録が終わっていれば `None` を返し、質問を通す（記録は消さない）。終わっていなければ拒否する。拒否の前に、hook の `tool_use_id` が空でない文字列なら `signals.drop_question` を待ち 0 秒で呼び、ロックの中で読み直した質問の `tool_use_id` が同じなら消す。`NDF_RELAY_LAUNCH` があれば中継の `launch.json` と同じときだけ進み、空か未設定なら起動の ID を比べずに進む。質問の JSON が壊れていれば照合せずに消し、読み直せない・ロックが取れない・消せないときは残す（ロックの `OSError` も拒否を返す）。残った質問は `ask-closed` か、子が終わった後の中継が消す。起動の ID と `tool_use_id` の両方を確かめたときだけ消す直しは #3978 が持つ。`forward_errors` は作らず、計測の `error` は `deadline` |

記録済みの質問は、どちらの経路でも入口で拒否しない。通知の不調で質問を止めない（`guards/ask.py`）。登録に `onFailure: "block"` は付けない（1 行の全 guard が止まる）。

- 採らなかった案: 環境が無い経路にだけ `strict` の判定を別に書く。同じ guard の実装が 2 つになる

### 決定 92: 止められ続けて進まない状態を作らないよう、差し戻しと拒否をセッション共通の数え手で数え、利用者の入力ごとの上限を超えたら案内へ下げる

数え手はセッションごとの状態のファイル 1 つで、利用者の入力（UserPromptSubmit）で数え直し、中継が送った入力では数え直さない。Stop の差し戻しは理由をまたいで `hook.pushback`（2 回）まで、同じ拒否は `hook.deny-repeat`（2 回）の後は通して理由を追加の文脈に入れる。`strict` と `fail_closed` の guard の拒否は数えず、上限を超えても下げない（`dispatch.py`）。中継に質問を記録できない状態が続いても、`ask-forward` は質問を通さない。数え手の排他は標準の `fcntl` で `hook.counter-lock`（0.2 秒）まで待ち、取れなければ数えずに通す（`domains/hooks/counter.py`）。hook の経路の import の所要を予算に収めるためで、hook の外のファイルの排他に使うライブラリの選択は決定 119（`ndf-rebuild-review-scope.md`）が持つ。

- 採らなかった案: 理由ごとに上限を持つ。10 系は 3 か所で別々に数え、合計 6 回続く差し戻しが起きた

### 決定 93: hook の所要を通信の具合に左右させないよう、同期の経路では通信せず、外部コマンドは git のローカルの副命令だけにする

通知は送信待ちのファイル（1 件 1 ファイル。一時名で書いて名前を変える）へ書き、NDF 自身の送り手を切り離して起動する。SessionStart の `git fetch` と学習の設定の読み書きは hook から外し、AskUserQuestion の転送は中継へのシグナルファイルを書いて返る。

- 採らなかった案: 送信待ちに persist-queue を使う。import に 47 ms かかり、書くのは 1 回の起動で 1 件までである

### 決定 94: 予算を守れているかを後から測れるよう、hook の起動ごとに所要・判定・注入の字数を 1 行で記録する

入口は状態の置き場の `hooks/<日付>.jsonl` へ `json` と `O_APPEND` で 1 行を足す（`domains/hooks/metrics.py`）。`hook.metrics-keep`（14 日）より古いファイルは SessionStart の入口だけが消す。`ndf hooks stats` は事象・guard ごとの p50・p95・拒否と差し戻しの数・注入の最大を返す。CI の退行の検査は所要時間で合否を決めず、入口が起動する子のプロセス・読み込むモジュール・ディレクトリの走査を数えて決めた値と比べる（`tests/domains/hooks/test_process.py`。所要は機械の具合で決まる。#3436）。

- 採らなかった案: structlog か python-json-logger を使う。import が 53 ms・25 ms かかり、書くのは 1 行だけである

### 決定 95: ランタイムの仕様の変化で hook が壊れたことに気づけるよう、入出力の契約表と本体の版ごとの入力の見本で CI を回す

契約表 `contracts/hooks/runtimes.json` は、ランタイムごとに事象・読む入力の鍵・判定ごとの出力の形・timeout の上限を持つ。Codex の Stop は `hookSpecificOutput` を許さないため、出力の形をランタイムごとに分ける。見本は `tests/domains/hooks/samples/<ランタイム>/<版>/`（Claude Code 2.1.325・Codex 0.167.0）で、新しい版は `ndf hooks capture` で加工してから足す。形は jsonschema で確かめ、hook の経路では import しない。

`ndf hooks capture` の加工（`domains/hooks/cli.py` の `redact`）は次の範囲だけで、すべての秘密を伏せる保証は無い（扱いは #3391 が持つ）。トップレベルの `hook_event_name`・`tool_name`・`source`・`reason`・`permission_mode`・`model`・`matcher` の文字列はそのまま残し、`session_id`・`turn_id`・`tool_use_id`・`prompt_id` は 16 進の文字を `0` に、`cwd`・`transcript_path` は `<cwd>`・`<transcript>` に置き換える。ほかの文字列（入れ子の中も含む）は `<text>` に置き換え、辞書のキー・数・真偽値・`null` はそのまま残す。

辞書のキー（パスや利用者の語を鍵にした入力など）と残したメタデータには、利用者のデータや秘密が残り得る。見本をコミットする前に、出力したファイルを読み、残ったキーと値に認証情報・利用者のパス・社名や人名などの利用者のデータが無いかを確かめ、あれば手で伏せるか、作った入力で採り直す。実際の作業の payload は使わず、試しのセッションで採る。

### 決定 96: guard の止め方を 1 つで覚えられるよう、止める環境変数を `NDF_HOOK_OFF` の 1 つにする

止める guard の名前をカンマでつなぐか `all` を渡す。閾値は `limits.json` に置き、環境変数で受けない。10 系の変数名（`NDF_SLEEP_GUARD` など）は読まない。

### 決定 97: 子が依存を迷わないため、先に要るものを「import する部品の持ち主」から引き、表に無い import を検査で落とす

子 A の先に要るものは、A のサブパッケージが import する部品の持ち主の子と、A の作業が出力を読む子である。表を `children.json` へ写し、規則 `child-deps` が `ndf check` の構文木から import の向きを読み、推移の閉包に無い向きを落とす。

- 採らなかった案: 推移を見ずに直の依存だけを許す。当たり前の向きまで表に並べることになる

### 決定 98: P1 を 1 本の PR に収まる大きさにするため、進行表の型と保存（P1a）と `next`・`answer`・工程から作業を呼ぶ層（P1b）に分ける

P1 #3092 が抱えた P3・P4・S1 の受け入れ条件を持ち主へ返し、残りを P1a #3369 と P1b #3092 に分けた。P1a はプランの実行を呼ばないため C2 を待たない。#3092 は工程の進行表の全体の要求で、`next` が動いたときに閉じるのが自然なため P1b に残した。

### 決定 99: クリティカルパスを 1 レーンの直列にしないため、P3 を P2 の前へ、P4 を lrebuild へ移す

P3 の先に要るものを P1a にし、外した課題を順番表の次の行へ入れる操作は P3 が作り P2 が呼ぶ形に分けた。P4 を lrebuild へ移し、lrebuild の空きに X1+・X2 と設計レビューの差分を置いた。1 つのレーンが続けて持つ段は 3 つまでになる。

- 採らなかった案: レーンを 7 本へ増やす。上限は利用者の決めた 6 本である

### 決定 100: 中継のブロックの語と衝突させないため、開発の間のプラグイン名を `ndf11` にし、ディレクトリ名は変えない

開発の間の名前 `ndf-next` は、中継が切り替えの指示として拾うブロックの語と同じで、I1 が中継のコードを落とした。名前を `ndf11` に替え、動いている子の PR との衝突を避けるためディレクトリ `plugins/ndf-next/` は入れ替えまで動かさなかった。入れ替えで名前は `ndf` になった。

### 決定 101: I1 が入れ替えの前後で同じ箇所を当てるよう、照合する名前に入れ替えの後の名前を足す

I1 の完全一致の照合は `plugin.json` の `name` と入れ替えの後の名前 `ndf` を、パスとプレフィックスの照合はそれにディレクトリ名を足した集合を当てる。固定の語は `identity.FIXED_WORDS`（`.ndf`・`bin/ndf` のファイル名・工程の定義の名前空間）の定義の行だけが通り、Python のパッケージ名 `ndf` の形は照合から外す。開発の間は名前を `ndf` にした一時コピーで検査とテストを打った。

- 採らなかった案: 入れ替えの後の名前だけを照合する。開発の間の名前を文字で書いても落ちない

### 決定 103: 捨てた決定と置き換えた材料を読み違えないため、置き換えの印を材料の側に置く

設計の材料の中身は変えず、置き換えた先を指す引用の 1 段落を材料の側に足す。確定仕様では、置き換えた決定を独立した見出しで残さず、置き換え先の決定の `採らなかった案:` の行へ理由とともに畳む（#3412 の決定 4）。

### 決定 104: 根拠の原文をリポジトリから辿れるよう、git の外の引継ぎ文書を写す

利用者の決定の原文を持つ引継ぎ文書（`.ndf/handoff/` の下で git の外）は、レーンの作業で書き換わる。2026-11-14 時点で止めた写しを設計の材料に置いた。確定仕様化の後は、番号の対応表の頭の固定リンクの下に残る。

### 決定 105: 要求と設計の食い違いを 1 か所で解くため、#1142 と #3092 の本文に取り消し線を引き、置き換えの文を添える

#1142 の前提 1（エントリポイント・プランの JSON・状態ファイルを変えない）を「後方互換を意識しない」へ改めた後も、受け入れ条件・影響・ドメインイベント・非機能の条件に古い文が残った。古い文に取り消し線を引き、置き換えの文を添える。正は Issue の本文である。

### 決定 106: 依存を最新に保つため、宣言の版は「最新の安定版。安定版が 365 日より古く、より新しいプレリリースがあれば最新」とし、入れられないものは固定する

| 場合 | 上げる先 |
| --- | --- |
| 最新の安定版が 365 日以内にリリースされた | 最新の安定版 |
| 最新の安定版が 365 日より前で、より新しいプレリリースがある | 最新（プレリリースを含む） |
| 最新の安定版が 365 日より前で、新しいプレリリースが無い | 最新の安定版 |
| 安定版が無い | 最新 |
| 上の版で `uv lock` が解決できない | 解決できる最も新しい版で固定する |

「安定版」は PEP 440 の pre-release でも developmental release でもない版で、候補は公開から 7 日たった版に限る（供給網の守り）。今の宣言では httpx が 0.28.1 で固定される（githubkit 0.17.1 が `httpx<1.0.0` を求める）。規則を表す設定と固定の理由の置き場は `ndf-rebuild-review-scope.md` の決定 118 が持つ。

- 採らなかった案: プレリリースを常に採る。安定版が新しい依存まで不安定な版になる

### 決定 108: 動いている子の PR との衝突を減らすため、依存の更新は 1 本の PR で行い、`uv.lock` の衝突は `uv lock` で作り直す

依存の版の一度の引き上げは X2 #3370 の 1 本の PR が持つ。ほかの PR は既存の行の版を変えず、足すときは 1 行と lock だけを持つ。2 本の PR が `uv.lock` で衝突したら、後の PR は手で解かずに取り込んだ `pyproject.toml` から `uv lock` で作り直す。上げた版で落ちる箇所が動いている子の PR の触るファイルに当たるときは、その PR のマージの後に取り込み直してから入れる。

## テスト観点

- I1〜I13・IH1〜IH10・IG1〜IG5・I22・I23 は、表の「破れたときの扱い」のテストか検査で縛る。所要時間を合格の条件にしない
- `ndf check` と `uv lock --check --project plugins/ndf` が CI で通る
- 入れ替えの後、利用者が登録し直さずに `plugin update` で版を受け取り、最初の起動で旧い置き場が 1 度だけ退避される
- 新しいテストは詳細設計の単体テストの観点から書き、10 系のテストを安全網にしない。利用者から見た振る舞い（Skill の手順・hook・プランの流れ）は、新しいテストと入れ替えの前の試走（T2 #3411）で確かめた
- `bash scripts/build-runtime-plugins.sh --check` と `claude plugin validate .` が通り、Codex の導入先に新しいモジュールが入る
- 中継の複製 `~/.claude/ndf/relay.py` が、プラグインを更新しても 1 回の導入で動き続ける
- 番号の一意: `grep -hoE '^#{2,4} 決定 [0-9]+' docs/specifications/ndf-rebuild*.md | grep -oE '[0-9]+$' | sort -n | uniq -d` が 0 行
