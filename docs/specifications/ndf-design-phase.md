# 設計工程の規約

開発ループに設計工程を置き、その成果物を規約化した経緯と決定を残す。

**手順と表は [`design` の SKILL.md](../../plugins/ndf/skills/design/SKILL.md) が正である。**
ここに書き写さない。この文書が扱うのは、そこに書かない決定の理由と、工程表での位置である。

## 概要

設計工程は `design` Skill が担う。**成果物の水準はモードが、該当は変更が触る領域が決める。**
読ませる参照も領域が決め、当たらない領域の参照は読まない。`standard` では設計を実装より先に
組み直してからレビューへ通し、設計だけを載せた Pull Request をマージしてから実装へ進む。

**非機能は要求側と対にして扱う。** 要求側（`requirements-design`）が 6 大項目のどれに条件を
書いたかが、設計側で実現方式を求める範囲になる。

## 用語

| 用語 | 意味 |
| --- | --- |
| 設計文書 | `design` が作る成果物。`issues/` 配下に置く Markdown |
| 設計 Pull Request | 要求仕様と設計文書だけを載せ、実装を含まない Pull Request |
| 記述標準 | 機械が読める形式で契約を書く外部の取り決め（OpenAPI・Open Data Contract Standard・Design Tokens Format Module） |

## 背景

設計工程には、何という文書を作り何を書くかの規約が無かった。そのため成果物の構成が担当した
AI ごとに変わり、文書の分割単位・記載項目・粒度をその場で決めることになっていた。

仕様駆動開発の主要なツールは、要求・設計・タスクの 3 段構成を採る。NDF は要求
（`requirements-design`）とタスク（`implementation-plan`）を持ち、その間が空いていた。

## 決定と理由

| 決定 | 理由 |
| --- | --- |
| 設計の Skill を 1 個にする | 過去の計画にあった 3 分割（設計レビュー・ドメインモデリング・クラス設計）は、起動の時点でどれを使うかの判断が要る。設計の観点の切れ目がモードや領域と一致しない |
| 触る領域ごとに参照を分け、入出力は API と画面で 2 本にする | 読ませる分量を、実際に触る領域まで絞る。片方だけを触る変更が多い |
| 記述標準は対象がある場合にだけ必須にする | モードで一律に必須とすると、画面を持たないリポジトリでも画面の節を求めることになる |
| 成果物は `issues/` 配下へ置く | 仕様と同じ場所に置き、完了後に `plan-to-spec` が `docs/` へ移す既存の流れに乗せる |
| 時系列を保護する手法に既定を置かない | どれを採るかは対象の性質で変わる。既定を置くと合わない対象へも同じ手法が選ばれる。代わりに、過去を失う構造を選んだときは理由を残すことを求める |
| 画面は策定中の標準を待たず、当面の書き方を定める | 画面要素の構造を記述する標準は策定の途中にある。確定を待つとその間の設計に規約が無い |
| 決定の記録を設計文書の 1 節に置く | 決定を別ファイルにすると、設計を読む人が理由へたどり着けない |
| 図は 4 つの階層すべてを求める | 文脈・構成要素・配置・クラスの 4 つ。クラスの階層は**変更が触る型だけ**に絞り、実装後の追随義務を負わせない。絞れば設計の差分と実装の差分が同じ範囲を指す。同期の時点は `plan-to-spec` が `docs/` へ移すときの 1 回である |
| 設計 Pull Request で課題を閉じない | 実装が終わっていない段階でマージするため、閉じると残りの工程が追えなくなる |
| ドキュメントレビューに新しい Skill を作らない | `pr` → `cross-review` → `merged` と手順が同じであり、作ると同じ内容が 2 箇所に増える |
| 成果物の水準を「必須」と「該当時」の 2 つにし、「不要」を置かない | どの成果物も、変更の中身が求めれば書く対象になる。モードが決めるのは無条件に求めるかどうかであって、書いてはいけない成果物を決めるものではない |
| 水準の違いを「省いたときに理由が要るか」に置く | 値が 2 つとも「書きうる」を意味する以上、区別できるのはここだけになる。「必須は無条件に書く」と定めると、対象が存在しない変更で空の見出しか作り話が入る |
| 省いた理由の書き先を `legacy-refactor` だけ変える | このモードは仕様を入力に取らない。書き先を仕様に限ると、書く先が存在しない。既に必須の節である「決定の記録」を使う |
| `light` / `operation` でも、領域が該当すれば `design` を通す | 成果物の要否表で 2 列を「該当時」にする以上、該当したときに起動する経路が要る。条件は触る領域が決め、「すべての変更」の行は数に入れない（入れると常に該当する） |
| `light` / `operation` は独立した設計文書を作らない | 1 節で足りる内容のために設計文書と設計 Pull Request が生まれ、工程が中身に見合わなくなる。ドキュメント再構成とドキュメントレビューも通らない |
| 工程の分類を `C`（条件付き）にし、`R` にしない | 記録が無いときの並び先が違う。`C` は「条件付き」の行に、`R` は「記録なし」の行に並ぶ。**`R` にすると、領域に当たらない変更でも必須の工程を通していないことと同じ扱いになる。** どちらも案内そのものは出る（`workflow-guard.sh` は「記録なし」と「条件付き」のどちらでも案内を出す）。拒否はしない |
| `operation` では非機能設計表だけを無条件にする | このモードは必ず外部の系の状態を変え、可用性・セキュリティ・移行性・システム環境のいずれかに当たる。実現方式を書かないまま実行すると、戻せるかどうかを実行の時点で初めて考えることになる |
| 非機能の要求を IPA 非機能要求グレードの 6 大項目にする | 要求側に項目が無いと、設計側で実現方式を決める根拠も無い。現行 4 種（性能・容量・権限・記録）は書き方と例を残し、親だけを付け替える |
| 設計 Pull Request を出す前に、文書の内部整合を突き合わせる | 設計レビューの指摘の 6 割が、同じ文書の中で突き合わせれば拾えるものだった（`takemi-ohama/with-bi` のマイルストーン 10、8 ラウンド 10 件の実測）。指摘 1 件につきレビュー 2 回と修正 1 回の往復が生じる |
| 突き合わせた結果は残さない | 残らないことが結果である。チェックリストを成果物にすると、埋めること自体が目的になり、埋めたかどうかのレビューが新しく増える |
| 表から導ける値を扱う対は、行数に限らず「導ける値の記述 ↔ その値を導いた表」とする | 行やセルの数・最大と最小・「すべて」はどれも表を数えれば決まる。「最も多い」「9 セル」の誤りは行数ではなく、値を導いた表も直下ではなく別の節（分割した別のファイル）にあった（PR #516）。行数の対と別に 7 つ目を足すと、どちらで見るかを読み手が決めることになる |
| 表を直したときは、その表から導いた記述を数え直すことを対の節に書く | 突き合わせの手順は「進む前」に 1 度通すもので、レビューの往復で表を直す場面を含まない。手順全体を通し直す形は、表に関係しない対まで繰り返す |
| 値の集合へ値を足す設計では、その集合を前提にした既存の規則を集めて判定し、当てはまらない規則を構成要素の表へ載せる | 同じ誤りの、文書の外にある形である。`documentation` の 4 形を足したとき、それまでの値だけを想定した規則 3 つが当てはまらないまま残った（PR #519）。判定の結果が構成要素の表へ入れば、図との突き合わせの対にも掛かる |
| 既存の規則は名前の検索と、新しい値が通る手順を読むことの 2 つで集める | PR #519 の 3 件は、どれも集合の名前も値の名前も含まない、すべての値へ同じように当たる規則だった。名前では集まらない |
| 既存の規則の判定は突き合わせの対に入れず、設計文書を書く手順に置く | 対は同じ文書の中だけで確かめられるものに限り、外部を要するものはレビューが拾う、という境界がある。検索を要する判定を対へ混ぜると境界が崩れる |
| 突き合わせを機械で確かめる検査は作らない | `design` は配布する Skill で、設計文書は利用者のリポジトリで書かれる。導ける値の記述は形が決まらず、どの表のどの列から導いたかは本文の意味を読まないと決まらない |

## 工程表での位置

| 工程 | `light` | `operation` | `legacy-refactor` | `standard` |
| --- | --- | --- | --- | --- |
| 設計 | `design`（該当時） | `design`（該当時） | `design` | `design` |
| ドキュメント再構成 | — | — | 設計 Pull Request を分けた場合 | `document-restructuring` |
| ドキュメントレビュー | — | — | 設計 Pull Request を分けた場合 | `pr` → `cross-review` → `merged` |

**`light` と `operation` の条件は触る領域が決める。** 「すべての変更」以外の領域が 1 つ以上
該当するときだけ通る。工程の分類（`WF_STAGE_MATRIX`）では `C` にあたる。

**記録が無いときは「条件付き」の行に並ぶ。** 「記録なし」（必須の工程の欠落）とは別の行で、
どちらの場合も拒否はしない。振る舞いは
`development-workflow/tests/test_workflow_guard.py::test_a_conditional_stage_without_a_record_is_not_a_gap`
が固定する。

`legacy-refactor` でこの 2 つを条件付きにしたのは、このモードが要求と受け入れ条件を通らず、
レビューの軸が現状固定テストの通過に寄るためである。**2 つは同じ条件で同時に発動する。**

設計 Pull Request をマージした後は、`worktree` を実装用のブランチ名で呼び直す。`merged` が
設計のブランチと作業ツリーを消すため、そのまま実装を続けられない。

前後の Skill との受け渡し:

| 相手 | 受け渡すもの |
| --- | --- |
| `requirements-design` | 受け入れ条件と対象範囲を受け取る（`legacy-refactor` を除く） |
| `implementation-plan` | 設計文書の節からタスクを導く |
| `plan-to-spec` | 設計文書を確定仕様へ取り込む。**クラス図を実装と突き合わせるのはこの 1 回だけである** |

## 要求側の非機能との対応

**非機能の軸は 6 大項目である。** IPA「非機能要求グレード」の大項目に対応する。要求側が条件を
書いた項目だけが、設計側で実現方式を求められる。

| 大項目 | 要求側が決めること | 設計側が決めること |
| --- | --- | --- |
| 可用性 | 運転時間、復旧の時間、停止の許容、冗長化 | 冗長化の構成、停止を伴う作業の手順、復旧の経路 |
| 性能・拡張性 | 応答時間、容量、処理量、増加への備え | 処理の分割、キャッシュ、索引、増加への備え |
| 運用・保守性 | 記録、監視、保存、障害時の切り分け | 監視の対象と通知先、記録の形式と保存先、切り分けの手段 |
| 移行性 | 移す対象、順序、切り戻し、並走 | 移行の順序、切り戻しの手段、旧版との並走 |
| セキュリティ | 権限、認証、通信と保存の保護、秘密情報 | 認証認可の置き場所、通信と保存の保護、秘密情報の受け渡し |
| システム環境 | 動作環境、依存する実行基盤、資源の制約 | 動作環境、依存する実行基盤、資源の制約 |

**該当しない項目は要求側でも設計側でも書かない。** 触らない項目へ条件を求めると、空欄か
「特になし」で埋まり、書き忘れと意図的な省略を読み手が区別できなくなる。

**現行 4 種（性能・容量・権限・記録）は、書き方と例を残して親だけを付け替えた。** 性能と容量は
性能・拡張性、権限はセキュリティ、記録は運用・保守性の下に入る。既にある仕様文書を書き直す
必要はない。

**`operation` では非機能設計表が無条件の成果物である。** このモードは必ず外部の系の状態を
変えるため、可用性・セキュリティ・移行性・システム環境のいずれかに必ず当たる。

## データ・設定

`design` は永続データを持たない。**この Skill が記録する値は `設計` と
`ドキュメントレビュー` の 2 つ**で、`.ndf/projects.json` を持つリポジトリでだけ働く。

**ボードの単一選択へ足す値は、この 2 つに限らない。** 設計の工程の前後には
`ドキュメント再構成`（`document-restructuring` が記録する）も入る。**ボードへ足すのは
工程表の行すべてであり、その操作はボードを持つリポジトリ側が行う。**

## テスト観点

| 観点 | 確かめ方 |
| --- | --- |
| frontmatter が執筆規約を満たす | `python3 scripts/check-skill-frontmatter.py` |
| 4 ランタイムのマニフェストと配布物が一致する | `bash scripts/build-runtime-plugins.sh --check` / `bash scripts/validate-runtime-plugins.sh` |
| 説明文書の Skill 数が実体と一致する | `python3 scripts/check-doc-staleness.py` |
| 参照のリンクが解決できる | `python3 scripts/check-markdown-links.py` |
| 4 ランタイムで Skill が読み込める | `bash scripts/runtime-smoke-test.sh` |
| 工程表の「設計」の行と `WF_STAGE_MATRIX` が一致する | 文書を読んで確かめる（照合していたテストは #885 で削除） |
| 条件付きの工程は、記録が無くても欠落として並ばない | `test_workflow_guard.py::test_a_conditional_stage_without_a_record_is_not_a_gap` |
