# cross-review: 1 ラウンド目で指摘を出し切らず、次のラウンドの担当が前のラウンドの指摘を知らず、担当が背景の処理を残して結果なしで終わっていた → 出し切りを求め、スナップショットをラウンドごとに取り直し、担当にテストと背景の処理を起動させない

## 目的

**3 ラウンド以上に進む実行を減らす。** ラウンドを増やす原因は 2 つある。1 ラウンド目で指摘を
出し切っていないことと、前の修正が作った穴を次のラウンドが後追いで見つけることである（#542）。
この仕様は判定を変えず、**担当が受け取るもの**でその穴を早く出させる。

- **どのラウンドの担当も「見つけた指摘はこのラウンドですべて出す」指示を受ける**
- **2 ラウンド目以降の担当は、同じ実行の前のラウンドの指摘と「対応しました」の返信を含む
  既存コメントのスナップショットを受ける。** スナップショットはラウンドの開始ごとに取り直す
- **設計 Pull Request の担当は、設計の文書に特有の穴を見る観点を受ける**
- **レビューの担当はテストも背景の処理も起動しない。** cross-refactoring の適用担当はテストを
  前景で終わるまで待つ（#786）

例: 設計 Pull Request の 2 ラウンド目。1 ラウンド目で major 3 件・minor 2 件が出て、修正が
2 コミット入った後である。

| 担当が受け取るもの | 変更の前 | 今 |
| --- | --- | --- |
| 既存コメントのスナップショット | `init` の時点のもの。1 ラウンド目の 5 件もその返信も入らない | `start-round` が取り直したもの。1 ラウンド目の 5 件と各件への返信が入る |
| 観点テンプレート | `common` / `docs_only` | `common` / `docs_only` / `design` |
| 指示 | 結果ファイルへ全件を書く指示だけ | 加えて、出し切り・テストを実行しない・背景で処理を起動しない |

**2 ラウンド目以降に「前のラウンドからの変更」（2 つの head と変わったファイルの一覧）を渡す案は
#934 へ移した。** 出し切りとスナップショットの取り直しの効果を測ってから入れるかを決める。

**既定の担当の母集合（claude / codex / kiro とホスト。agy は `--include agy`）と、母集合に無い者の
除外の扱いは [参加者と席の確定仕様](cross-review-participants-and-seats.md)が持つ。**

**手順と引数の表は
[`cross-review` の SKILL.md](../../plugins/ndf/skills/cross-review/SKILL.md)と
[`docs/04-contracts.md`](../../plugins/ndf/skills/cross-review/docs/04-contracts.md)が正である。**
ここに書き写さない。この文書が扱うのは、そこに書かない決定の理由と、進行の内部の契約である。

## 用語

| 用語 | 識別子 | 意味 |
| --- | --- | --- |
| 既存コメントのスナップショット | `cross-review-pr<STATE_PR>-existing-comments.txt` | PR の既存のインラインコメント・レビュー本文・PR コメントを 1 行 1 件で並べたファイル。プロンプトへそのまま入る |
| 取得元 | — | スナップショットを作る 3 つの API（インラインコメント・レビュー本文・PR コメント） |
| 取り直し | `_fetch_existing_comments(strict=True)` | ラウンドの開始でスナップショットを作り直すこと |
| 通しのラウンド | `len(rounds) + 1` | 状態ファイル全体で数えたラウンドの番号。PR ごとの番号（`round_in_pr`）ではない |
| 新しい指摘 | `_new_finding_count` | 直前のラウンドの指摘と一致しない、そのラウンドの指摘。証拠集約を通ったラウンドでは数える 3 区分（`verified_blocking` / `needs_human_judgment` / `unrefuted`）だけ |
| 設計 Pull Request | `design` | 変更ファイルに `issues/` 配下の `*-requirements.md` / `*-design.md` / `*-design-decisions.md` を含む Pull Request |

## 対象範囲

| 扱う | 扱わない |
| --- | --- |
| レビューのプロンプトの出し切りと、起動しない処理の指示 | 収束の判定・振動の検知・`max_rounds`・起動し直しの規則（変えない。決定と理由） |
| ラウンドの開始でのスナップショットの取り直しと、`fetch-pr-comments.sh --strict` | スナップショットの圧縮 |
| 設計 Pull Request の分類と観点テンプレート | `design` の成果物へ「状態を書き換える経路の一覧」を足すこと |
| cross-refactoring の適用のプロンプトの、テストを前景で待つ指示 | 結果を残さなかった担当を別のランタイムへ振り替えること（#919） |
| | 前のラウンドからの変更の節（#934） |

## 背景

**ラウンドの多い実行が所要の大半を使っていた。** 2026-09-01〜09-15 の 88 件では、1 ラウンドが
42%（中央値 8.1 分）、2 ラウンドが 28%（16.2 分）、3 ラウンド以上が 30%（50.2 分）で、3 ラウンド以上が
時間の 70% を使った（#542、集計の方法は #662）。PR #539 の 10 巡の指摘は 15 → 6 → 2 → 2 → 5 → 2 →
0 → 2 → 3 → 0 で、3 巡目以降に分類した指摘はすべて前の修正が作った穴だった。

**スナップショットが `init` の 1 回しか取られていなかった。** #908 の実行 3 の round 5 のプロンプトには、同じ
実行の round 1〜4 の指摘が入っていない（プロンプト 61,962 バイトのうちスナップショット 54,957 バイト）。直った
指摘の近くを別の言い方で再び指摘すると振動の検知に当たり、#908 の実行 2 と #911 は振動で
打ち切られた。

**担当が背景でテストを起動し、結果を残さずに終わることがあった**（#786）。devbase v3.6.0 で agy が
8 回（cross-review 5・cross-refactoring 3）結果を残さなかった。

## 決定と理由

| 決定 | 理由 |
| --- | --- |
| 1 ラウンド目から「見つけた指摘はすべて出す」を求める。出す対象は今のまま修正アクションのある指摘に限る | 1 ラウンド目で出し切らない指摘は、修正の後のラウンドで新しい指摘として数えられ、ラウンドを 1 つ増やす。nit や良い点まで網羅させても、nit は収束を止めないためラウンドは減らない。出力が増えて無進捗の打ち切りに当たる懸念は、既定の母集合から agy が外れたため既定では当たらない |
| 既存コメントのスナップショットをラウンドの開始ごとに取り直し、失敗しても止めない | 次のラウンドの担当が前のラウンドの指摘と返信を知らないと、同じ場所を再び指摘して振動の検知に当たる。前のスナップショットでも今と同じ条件でレビューできるため、取り直しの失敗で止める理由が無い |
| 取り直しは 3 つの取得元の 1 つでも失敗したら前のスナップショットを残す（`--strict`） | 一部だけのスナップショットで上書きすると、前のラウンドの指摘が重複の検出から消える |
| `init` の取得の失敗は今どおり止める（3 つとも失敗したときだけ） | スナップショットが無いと重複の検出が働かない |
| 取り直しは round エントリを状態ファイルへ保存する前に行う | 保存の後に取ると、取得の途中で割り込まれたときに結果の無い round だけが残り、再実行が前のラウンドの後始末のチェックで止まる（PR #930 のレビューで前へ移した） |
| スナップショットは圧縮しない | 取り直しで増えるのは同じ実行の前のラウンドの行だけで、まず大きさを見る |
| 設計 Pull Request 向けの観点テンプレートを足し、設計の成果物は増やさない | 設計の文書に特有の穴は、3 文書の食い違い・状態の書き手の衝突・外部ツールの挙動の事実誤認の 3 つで、今の観点に無い（devbase PR #163 では事実誤認 1 件が 2 ラウンドを生んだ）。成果物へ経路の一覧を足すと、対象になる設計を見分ける基準が要り、すべての設計の手間が増える。レビューの観点なら、状態を持たない設計では当たらずに済む |
| 設計 Pull Request はファイル名の規約で見分ける。ブランチ名（`design/`）では見分けない | 観点を組む入力は PR の変更ファイルであり、ブランチ名は分類の入力に無い |
| レビュー担当にはテストも背景の処理も起動させない | 実行の確かめはオーケストレーターの `verify-findings` が行い、担当が走らせたテストは判定に使われない。背景で起動すると結果を書かずに終わる経路になる |
| cross-refactoring の適用担当にはテストの実行を禁じず、前景で終わるまで待たせる | 適用担当はラウンドごとに 1 回テストを実行する設計である（`apply.md` の「適用ラウンドの単位で 1 回」） |
| 収束の判定は変えない。新しい指摘が minor だけのラウンドは今も収束する | 証拠集約は minor を `insufficient_evidence` か `verified_non_blocking` へ分け、新しい指摘として数えない。ラウンドを延ばしているのは前の修正が作った major の穴である。`_is_pass` を REQUEST_CHANGES へ広げても、収束するラウンドは増えない |
| 母集合の全員が見るまで収束しない条件（#631）は採らない | ラウンドを増やす方向で、1 ラウンドで収束した 37 件のうち 29 件にもう 1 ラウンドずつ（約 4 時間）掛かる。根拠にした取りこぼし（devbase#171・#191）は round 1 が agy + kiro の形で、既定の母集合から agy を外した後は、ホストが agy 以外なら round 1 は必ず codex + kiro になる |
| 振動の検知（閾値 0.5・近傍 3 行）・`max_rounds`（12）・起動し直し（同じ席で 1 度）は変えない | スナップショットの取り直しが振動の原因の 1 つを減らす。閾値を同時に変えると、どちらが効いたかを分けられない。`max_rounds` を下げるのは、振動を減らさずに打ち切るだけになる |
| 結果を残さなかった担当を別のランタイムへ振り替えることは含めない（#919） | 既定から agy を外した後に残る結果なしは、手元の記録で codex の利用上限の 2 件だけである。利用上限は振り替えても同じ実行の中で再び当たり得るため、振り替えの規則（いつ・誰へ・何回）は別に決める |
| 前のラウンドからの変更の節は #934 へ移した | 出し切りとスナップショットの取り直しだけで後のラウンドの指摘が減るかを先に測り、その結果で入れるかを決める |

## 仕様

### 常に成り立つ条件

| 条件 | 破れたときの扱い |
| --- | --- |
| スナップショットのファイルは、3 つの取得元をすべて取れた中身か、前の中身のどちらかである | 取り直しは一時の名前へ書き、成功したときだけ改名する |
| 取り直しの失敗でラウンドは止まらない | 起動できない（`OSError`）ときも失敗の理由として返し、`⚠` の 1 行を出して続ける |
| 通しの 1 ラウンド目は取り直さない | `init` が取った直後である |
| スナップショットの形（1 行 1 件、`[PR-COMMENT]` などの接頭辞）と置き場所の名前は変わらない | `launch-reviewer.sh` が読む名前は 1 つである |
| 設計 Pull Request の分類は `common` / `docs_only` を消さない | `design` は足す分類で、`docs_only` の判定は変えない |
| 収束の判定は、母集合の各担当がレビューしたかを見ない | #631 を採らない |

### 既存コメントのスナップショットの取得

`state.py` の内部関数が 1 本で取る。

```python
def _fetch_existing_comments(repo: str, pr: int, path: pathlib.Path, *, strict: bool) -> str | None:
    """fetch-pr-comments.sh を呼び、成功なら path へ書いて None、失敗なら理由の文（先頭 200 字）を返す。"""
```

| 呼ぶ場所 | `strict` | 失敗したとき |
| --- | --- | --- |
| `init` の新規開始 | 偽 | 3 つとも失敗したときだけ終了コード 1（`既存コメント取得失敗 (重複検出無効のため中断)`）。状態ファイルは作らない。1〜2 つの失敗はスナップショットを書いて続ける |
| `start-round`（通しのラウンドが 2 以上、round エントリの保存の前） | 真 | 前のスナップショットを残し、`⚠ 既存コメントのスナップショットを取り直せませんでした（<理由>）。前のスナップショットのまま進めます` を標準エラーへ出して続ける |

| 項目 | 値 |
| --- | --- |
| 取得する PR | 状態ファイルの `current_pr`。PR の巻き直しの後の最初のラウンドは新しい PR の既存コメントに置き換わる |
| 書く先 | `$TMP_DIR/cross-review-pr<STATE_PR>-existing-comments.txt`（`STATE_PR` は状態ファイルの鍵） |
| 増える行 | 前の取得の後に投稿された行（同じ実行の前のラウンドの指摘と返信）だけ |

### `fetch-pr-comments.sh` の終了コード

`fix` の共有スクリプトである。使い方は `fetch-pr-comments.sh [--strict] <owner/repo> <pr_number>`。
出力（3 つの取得元をタグ付きの 1 行 1 件で標準出力へ）は変わらない。

| 失敗した取得元の数 | `--strict` 無し | `--strict` 付き |
| ---: | ---: | ---: |
| 0 | 0 | 0 |
| 1〜2 | 0（取得元ごとに `WARNING` の行） | 1 |
| 3 | 1 | 1 |
| 引数が足りない | 1（`gh` を呼ぶ前） | 1 |

### レビューのプロンプトに入る指示

`launch-reviewer.sh` が組むプロンプトに次を置く。文言はスクリプトが正である。

| 置く節 | 指示 |
| --- | --- |
| `## 出し切り`（追加レビュー観点の後、`## 指摘に含めてはいけないもの` の前） | 見つけた指摘はこのラウンドですべて出す。次のラウンドへ回さない。重要度が minor のものも書く。出すのは修正アクションのある指摘だけで、含めてはいけないもの（良い点・対応アクションが無い指摘）は変わらない |
| `## 守るべきこと` | テストを実行しない。実行して確かめる手順は `suggested_check` に書く（オーケストレーターの `verify-findings` が実行する） |
| 同上 | 背景で処理を起動しない。起動した処理の終わりを待たずに結果のファイルを書かないまま終わると、結果が無い担当として扱われる |

cross-refactoring の適用のプロンプト（`prompts/apply.md`）の禁止事項には、「テストは前景で実行し、
終わるまで待つ。背景で起動した処理を残したまま終えない」を置く。

### 設計 Pull Request の分類と観点

分類の述語は、パスが `issues/` で始まり、ファイル名が `-requirements.md` / `-design.md` /
`-design-decisions.md` のどれかで終わるときに真を返す（`_is_design_doc_path`）。分類の表
（`PATH_CATEGORY_RULES`）の先頭に `design` を、観点の表（`CATEGORY_TEMPLATES`）に
`DESIGN_REVIEW_TEMPLATE` を置く。2 つの表は対で直す。

観点テンプレートが求めることは次の 3 つである。

- 要求・設計・決定の記録の 3 文書で、受け入れ条件ごとに設計の要素とテスト設計の行があるか。決定で
  退けた案が他の節に残っていないか
- 状態（ファイル・環境変数・状態ファイルの項目・引数）ごとに書き手と読み手を並べ、同じ状態を 2 つの
  経路が書く・読む側が書く側より先に動く・失敗した書き手の後に読む、の矛盾が無いか
- 外部コマンド・外部ツールの挙動（優先順位・終了コード・一致の範囲）を断定する記述に、実測の根拠
  （コマンドと出力）があるか

`issues/notes.md` や `docs/x-design.md` のように規約の名前と置き場所から外れた文書は `design` に
分類されない。

## データ・設定

状態ファイルの項目は増えない。worktree の `.cross_review/` に置くファイルも増えない（スナップショットは
同じ名前のファイルを置き換える）。取り直しの一時ファイルはスナップショットの名前に `.tmp` を付けた名前で、
成功するとスナップショットへ改名される。

## 運用

**効果はリリースの後の設計 Pull Request のラウンド数で見る。** 比べる手段は #893 が作る。手元では
退避された状態ファイル（`.git/ndf/worktree-trash/*/.cross_review/`）の `rounds` を数えて比べられる。
#934（前のラウンドからの変更の節）を入れるかは、この結果で決める。

**出し切りの指示で 1 ラウンド目の出力が増えると、担当の所要が延びる。** 既定の担当の無進捗の
許容は codex 180 秒・kiro 480 秒・claude 900 秒である。

**スナップショットの大きさは圧縮していない。** #908 の実行 3 でスナップショットは 54,957 バイトだった。取り直しで同じ実行の
指摘と返信の行が増える。

## テスト観点

`.md` の文言は固定しない（#885）。プロンプトは節の有無と条件の分岐を見る。

| 観点 | 確かめ方 |
| --- | --- |
| 2 ラウンド目の `start-round` がスナップショットを取り直して新しい中身にし、1 ラウンド目では取り直さないこと | `plugins/ndf/skills/cross-review/tests/test_state_round_refetch.py` |
| PR の巻き直しの後の `start-round` が新しい PR の番号で取ること | 同上 |
| 取り直しが 1 つの取得元の失敗で前のスナップショットを残し、終了コード 0 で `⚠` の行を出すこと。起動できないときも同じこと | 同上 |
| 取り直しの途中で割り込まれても、結果の無い round が残らないこと | 同上 |
| `init` の取得が `--strict` を付けず、1 つの失敗ではスナップショットを書いて続け、3 つとも失敗すると状態ファイルを作らず終了コード 1 になること | 同上 |
| `fetch-pr-comments.sh` が `--strict` の有無で表の終了コードを返し、出力の形が変わらないこと | 同 `test_fetch_pr_comments_strict.py` |
| 設計の文書を含む変更が `common` / `docs_only` / `design` に分類され、`issues/notes.md` と `docs/x-design.md` だけの変更が `design` を含まないこと | 同 `test_state_auto_review_templates.py` |
| プロンプトの組み立てが通ること（出し切り・起動しない処理・観点の文言は読んで確かめる） | 同 `test_launch_reviewer_prompt_context.py` |
| 新しい指摘が minor だけのラウンドが収束すること（判定を変えていないこと） | 同 `test_classify_findings.py` と judge のテストが変更なしで通る |
| 振動の検知と結果が無い担当の起動し直しが変わらないこと | 同 `test_state_check_oscillation.py` / `test_judge_no_result_reason.py` が変更なしで通る |
| 全体のテストが通ること | `uv run --project plugins/playwright-kit/skills/playwright-kit-ops --with pytest pytest . -q -n 4` |
