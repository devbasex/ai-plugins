# 証拠ベースのレビューと効果の測定

`cross-review` が指摘の採否を、票の数ではなく**別の担当が確かめられる根拠**で決めるように
した経緯と決定を残す。あわせて、その効果を同じ記録から測る枠組みを定める。

**手順と表は
[`cross-review` の SKILL.md](../../plugins/ndf/skills/cross-review/SKILL.md)と
[`docs/`](../../plugins/ndf/skills/cross-review/docs/06-evidence.md)が正である。**
ここに書き写さない。この文書が扱うのは、そこに書かない決定の理由と、状態ファイルの契約
である。

## 概要

**指摘は自由文だけでなく、根拠・反証条件・実行できる検証手順を持つ。** 担当は発見を
終えるまで、同じラウンドの他の担当が出したものを参照しない。

**進行側は、担当の再評価より先に検証手順を実行する。** 機械が再現した事実は、担当の支持
より確かである。

**指摘は 5 つの区分へ分かれ、収束の判定は担当の判定（`event`）ではなく区分を見る。**
数えるのは `verified_blocking` と `needs_human_judgment` の 2 つだけである。

**却下した指摘は、位置・重要度・理由とともにラウンドをまたいで残る。** 次のラウンドの
レビュープロンプトへ渡り、同じ論点が戻ることを止める。

**効果は回し直さずに測る。** 収束ループが残した記録を読み、4 つの方式の結果を同じデータ
から計算する。

## 用語

| 用語 | 意味 |
| --- | --- |
| 担当 | そのラウンドでレビューする CLI。「全ランタイム − ホスト」の 3 者から輪番で選んだ 2 者 |
| 母集合 | 判定や測定が数える対象の集合。レビュワーを選ぶ 3 者の集合とは別である |
| 指摘 | 担当が出した 1 件の主張。`review_findings[]` の 1 要素にあたる |
| 根拠 | 何がそう言えるか。対象のコードと到達経路（`evidence`） |
| 反証条件 | 何が成り立てば棄却できるか（`falsification`） |
| 検証手順 | 実行できる形で書いた確かめ方（`suggested_check`） |
| 反証 | 提案者以外の担当が、各指摘へ返す 1 つの値 |
| 区分 | 1 件の指摘を分ける 5 つの分類（`classification`） |
| 方式 | 効果の測定で指摘を採る規則。`single` / `majority` / `proposed` / `oracle` の 4 つ |
| 代表 | 統合した組で、判定が読む 1 件。束ねられた側は `merged_into` を持つ |
| 印 | そのラウンドが統合・実行検証・反証を通ったこと（`evidence_rounds`） |
| 却下の記録 | 修正の担当が直さないと決めた指摘の per-item の控え（`rejected_findings`） |
| 上限の方式 | 実際に修正された指摘の集合（`oracle`）。どの方式もこれを超えられない |
| 再現率 | その方式が上限の方式の何割を拾えたか（`of_oracle`） |

## 背景

**重要度の自己申告と判定が対応しない。** PR #157 の round 6 で、担当が `minor` 2 件だけで
`REQUEST_CHANGES` を返した。判定の基準は「修正必須の指摘なし（`minor` 以下しか無い場合も
`APPROVE` で良い）」であり、基準どおりなら `APPROVE` になる。

**却下した論点が次のラウンドへ渡らず、同じ指摘が戻る。** #69 で同じ論点が round 1 から 5 の
5 回、#70 で 3 回現れた。却下の記録は件数の整数へ潰れており、位置も理由も残っていなかった。

**票の数でも決められない。** 同じ系列のモデルが同じ誤りをすると、それが「多数」に見える。
少数派だけが見つけた重大な指摘は、票では拾えない。

**総評だけへ書いた指摘が進行側から見えなかった。** 差分の外を指す指摘と、`HTTP 422` が
返ったインラインは総評へ移る。`payload.json` が投稿したインラインの写しであった頃は、
この 2 つの経路を通った指摘が記録へ届かなかった（PR #157 の round 4）。

## 決定と理由

| 決定 | 理由 |
| --- | --- |
| 自己申告の確信度（`confidence`）は求めない | 数値の尺度は担当ごとに違い、突き合わせられない。根拠と反証条件は文章として読めるため、別の担当が確かめられる |
| `has_evidence` は根拠と反証条件の**両方**が空でないときだけ真にする | 根拠だけでは、どうなれば取り下げるのかが決まらない。反証条件だけでは、なぜそう言えるのかが分からない |
| 4 項目を持たない指摘も捨てない | 捨てると、対応していない担当の指摘が記録から消える |
| 却下の記録は件数と per-item の両方を持つ | 件数はラウンドごとの報告が読む。per-item は、件数だけが返る劣化表現（修正の担当が整数を返す経路）では作れない |
| 独立発見はプロンプトの規約とテストで固定し、新しい仕組みを作らない | 結果ファイルを共有しない性質は実装の副産物で、壊れても失敗として現れない。投稿の手順がその時点の既存コメントを引くため、並列に起動することだけでは塞げない |
| `pr-review` の手順そのものは変えない | 単独で使うときは、その場の既存コメントを見るのが正しい。制約が要るのは `cross-review` から呼ぶ経路だけである |
| 実行してよいコマンドは起動の引数（`--verify-command`）で受け取る | `suggested_check` は担当が書いた文字列で、そのまま実行すると誤りや誘導がそのまま実行になる |
| 宣言ファイル（`.ndf/cross-review.json`）は新設しない | `cross-refactoring` は同じ性質の値を `--baseline-test` の引数で受け取る。同じものを 2 つの Skill が別の方法で受け取る形にしない。宣言ファイルには置き場所のほかに「作る手段」と「作る時期」が要る |
| 照合はトークン単位で行い、メタ文字の一覧を持たない | 前方一致では `pytest` の指定に `pytest-danger` が当たる。弾く文字を列挙する方式は、列挙から漏れた文字がそのまま通る |
| 位置指定は `realpath` で作業ツリーの配下へ解決する | `abspath` は symlink をたどらず、作業ツリーの中から外を指すリンクを見逃す |
| 位置指定を 1 つも持たない値は実行しない | 対象を絞らない実行は、指摘と無関係な失敗を拾う |
| 「0 でない」を再現としない | pytest は対象が無いときに 4、収集 0 件で 5 を返す。バグの再現と、検証手順の書き誤りが別の値で分かれる |
| 実行の結果を担当の支持より先に見る | 機械が再現した事実は、担当の再評価より確かである。**この向きは区分の順序そのもので表す**（条件の中で優先順位を書き分けない） |
| 統合の条件を振動の検知と同じにしない | 振動は近傍・本文の**いずれか**で結ぶ。統合は近傍**かつ**本文を求める。過剰な統合は指摘を失うが、統合し損ねても失われるものは無い。誤りの代償が非対称であるため、厳しい側へ倒す |
| 反証は新しいラウンドを足さず、同じラウンドの中で回す | ラウンド数が 2 倍になり、収束の上限（12）の意味が変わる |
| 申告による統合（2 段目）は次のラウンドへ回さない | 回すと、同じ主張を 2 者が別の本文で出した組が、統合される前に `insufficient_evidence` へ落ちて収束する |
| 反証の値は担当ごとに置き換え、積み増さない | 取り直したときに古い値が残る。`refute` を `support` へ訂正しても両方が並び、区分の順で `refute` が先に当たって指摘が `rejected` のままになる |
| 収束の判定が数えるのは 2 区分だけである | 棄却した指摘と `minor` の指摘を数えると、そのぶんラウンドが増える（#69 の 5 ラウンド） |
| 測れたかどうかは、区分で絞る**前**に決める | 絞った後の集合へ「空なら測れない」を適用すると、全件を棄却したラウンドが「測れなかった」ことになり、元の判定のままループが終わらない |
| 印（`evidence_rounds`）で母集合を決め、`review_findings` の有無では判定しない | 取り込みはこの変更より前から要素を積む。存在で判定すると、区分も検証結果も持たない旧いラウンドが絞り込みに掛かり、修正必須の `major` が落ちて収束する |
| 印を付けるのは経路の最後で、対象ごとに有効な反証が揃ったときだけである | 途中で付けると反証を結ぶ前の値で数える。結果ファイルの欠落でも付けると、未検証のまま収束する |
| `needs_human_judgment` を人へのエスカレーションにしない | 収束のループはこの工程の中で回っており、止めて人を待つと自動で進まなくなる。決めるのは修正の担当で、その判断は却下の記録へ残る |
| 振動の検知（一致の判定・閾値 0.5）は変えない | 母集合は指摘の構造化で既に広がっている。判定式まで同時に変えると、ラウンド数が動いたときにどちらが原因かを切り分けられない |
| 測定は独立したスクリプトにし、記録の項目だけを `state.py` へ足す | 収束ループの中に置くと、測定の失敗が進行を止める。読むだけのスクリプトなら、いつでも後から計算し直せる |
| 解決したスレッドの位置を GitHub API で引かない | 外部依存を足すと、測定が GitHub の状態と認証に左右される。Pull Request が消えた後は引けず、後片付けの後に測る運用と合わない |
| 1 回の実行が測るのは 1 つの状態ファイルである | 集計の単位は測る目的で変わる（変更の前後・担当ごと・リポジトリごと）。0 か 1 の値で出しておけば、どの単位でも測る側が足し合わせられる |
| 測る単位はローテーション全体である | ローテーションは同じ変更に対するレビューの続きで、終わり方も上限の判定も状態ファイル全体で 1 つである。`current_pr` の分だけを測ると、それ以前のラウンドがまるごと落ちる |
| 精度（誤った指摘の割合）は測らない | 修正されなかった指摘が誤りだったかは記録から決まらない。範囲外として却下したもの、判断が割れて `deferred` にしたもの、単に対応しなかったものが混ざる。**測れない値を数字にすると、比較の根拠として使われる** |
| 1 者だけの方式は担当ごとに出す | 1 つの数字にまとめると、誰を選ぶかが結果に混ざる |
| 状態ファイルを残す仕組みは作らない | 状態ファイルには Pull Request の中身が入り、置き場所と保持の期間を決める必要がある。測定のためだけに決めるには重い。測る側が測る前に控える |

## 仕様

### 常に成り立つ条件

- **`has_evidence` は `evidence` と `falsification` の両方が空でないときだけ真である。**
  取り込みのときに進行側が付ける派生の項目で、担当は書かない。空白だけの文字列は空として
  扱う
- **束ねられた側は消さない。** `merged_into` を書いて残す。消すと、反証の結果がその指摘を
  指したときに結び先を失う。判定・区分・測定はいずれも代表だけを数える
- **実行できなかったこと（`not_run`）と、再現しなかったこと（`not_reproduced`）を同じに
  しない。** 前者は区分の順 3 の前半に当たらず、区分は反証と根拠で決まる
- **`ran_at` は実行した記録にだけ入る。** 実行しなかった記録では `exit_code` とともに
  `null` である。時刻が残ると、実行済みと見分けられない
- **1 つの（ラウンド, 指摘, 担当）が持つ反証は 1 つである**
- **自分が提案した指摘へは反証を返さない。** 統合された指摘では `origin_runtimes` に載る
  担当すべてが提案者である
- **項目が欠けた記録も落とさない。** 却下の記録も、解決したスレッドの位置も、記録に残せない
  ことと、それが何件あったかを失うことは別である
- **測定の出力はキーを常に置き、決まらない値を `null` にする。** `reason` は値が `null` の
  ときだけ置く
- **再現率は 1.0 を超えない。** 分子は採用集合と上限の方式の積集合であり、`found` では
  ない。採用集合には修正されなかった指摘も却下された指摘も入る

### 指摘の構造化と独立発見

担当が書き出す `payload.json` の `comments[]` は、**その担当が出した指摘の全件**である。
投稿したインラインの写しではない。総評だけへ書いた指摘も載り、`path` と `line` はそのときも
埋める。投稿先は `posted_to`（`inline` / `body`）が持つ。

**インラインの件数（`result.json` の `comments_count`）は変えない。** 進行側が GitHub 側の
実数と突き合わせる値であり、指摘の全件を入れると照合が常に食い違う。

**発見を終えるまで、参照してよい既存コメントは起動時のスナップショットに限る。** 同じ
ラウンドの他の担当の投稿・結果ファイル・進捗ログは参照しない。スナップショットは前の
ラウンドの指摘であるため、渡し続ける（渡さないと、同じ指摘が毎ラウンド出る）。

**母集合が広がることを受け入れる。** 総評だけの指摘に位置を埋めると、新規性の判定と振動の
検知が数える対象が増える。新規性はラウンドが増える方向へ、振動は上下どちらへも動きうる。
見えていない指摘を 0 件として収束するほうが害が大きい。

### 走らせる順序

取り込みと判定の間に 3 つを置く。**どれか 1 つでも走らせないと、区分が決まる前の値のまま
収束する。**

| 順 | 何をするか |
| --- | --- |
| 1 | 重複の統合（1 段目）と、検証手順の実行 |
| 2 | 提案者以外の担当を起動し、賛否を書かせる |
| 3 | 賛否を指摘へ結び、申告の重複を束ねる（2 段目） |

**実行検証が反証より前にある。** 反証を返す担当は、実行の結果を読んだうえで賛否を決める。
**統合の 1 段目も反証より前である。** 後にすると、束ねられる 2 件へ別々に反証が付き、
どちらの値を採るかという判断が増える。

**有効な反証が揃わないときは印を付けず、同じラウンドで 1 度だけ取り直す。** 2 度目も
揃わなければ印を付けないまま進み、そのラウンドは全件を数える。

**監視へ渡すのは、実際に起動した担当だけである。** 反証の対象が無い担当（自分の指摘だけ、
または指摘 0 件）は起動せず、pid ファイルを作らない。全員を渡すと、両者とも指摘 0 件で
収束するラウンドでも毎回 30 秒止まる。

### 重複の統合

**1 段目は機械の判定である。** 同じファイル・行差 3 以内・正規化した本文の一致を求める。
同じ担当どうしは比較しない。近傍で当たっただけで本文が違う組は統合せず、両方の識別子を
`duplicate_candidates` へ残す。

**2 段目は担当の申告である。** 反証で相互に `duplicate` が付いた組を、区分の前に束ねる。
片側だけの申告では束ねない。

**代表は先に取り込まれた側だが、値は組の集約を採る。** 取り込みの順序で採否が変わらない
ようにするためである。

| 項目 | 集約の仕方 |
| --- | --- |
| 重要度 | 組の中で最も高いもの |
| 実行の結果 | `reproduced` > `not_reproduced` > `not_run` の順で最初に当たった 1 件。出所を残す |
| 根拠 | 組のいずれかが `has_evidence` を持てば代表も持つ。**対は同じ要素から採り、本文ごと写す** |

**根拠を片方ずつ継ぎ合わせない。** 根拠だけを書いた要素と反証条件だけを書いた要素はどちらも
`has_evidence` が偽であり、両者を継ぎ合わせると、誰も書いていない組を根拠として作り出す。

**真偽だけを引き継がない。** 本文を写さないと、修正の担当と次のラウンドの担当が読む代表に、
根拠の本文が無いまま「根拠あり」の印だけが付く。

**2 段目では実行し直さない。** その時点で組の全員が実行の結果を持っており、記録済みの値を
上の順で選び直すだけである。実行し直すと、反証を返した担当が読んだ結果と、区分を決めるとき
の結果が食い違いうる。

### 実行検証

**実行してよいのは、起動した側が渡したコマンドだけである。** 渡されなければ実行検証を
行わず、区分は根拠と反証で決まる。**新しい実行系は導入しない。**

| 守ること | なぜ |
| --- | --- |
| 渡されたコマンドのトークン列が、検証手順のトークン列の先頭と全要素で一致すること | 前方一致では別のコマンドが当たる |
| 後ろのトークンは `-` で始まらないものだけ | `-c` や `-p` は任意の設定とプラグインを読み込ませる |
| 後ろのトークンがすべて作業ツリーの配下へ解決されること | 外を指すと、リポジトリの外の任意のコードを実行できる |
| 後ろのトークンが 1 つ以上あること | 対象を絞らない実行は無関係な失敗を拾う |
| `shell=False` で実行すること | コマンド置換と逆引用符を展開させない |

**束ねた組の全員の検証手順を対象にする。** 代表の値だけを読むと、代表が手順を書いていない
組は、束ねられた側が実行できる手順を書いていても実行されない。**同じコマンドは 1 度しか
実行しない。**

**失敗が再現である。** 指摘は「壊れている」という主張であるため、テストが失敗することが
再現にあたる。打ち切りと起動の失敗も再現としない（終了コードを読む前に例外で分かれる）。

### 反証

提案者以外の担当が、各指摘へ次の 5 つのいずれか 1 つを返す。

| 値 | いつ使うか |
| --- | --- |
| `support` | 根拠を独立に確認できた |
| `refute` | 反例・仕様・コードから誤りを示せる |
| `insufficient_evidence` | 可能性はあるが立証できない |
| `duplicate` | 別の指摘と同一。相手の識別子を `duplicate_of` へ書く |
| `out_of_scope` | この Pull Request の範囲・目的から外れる |

**区分の条件に現れるのは `support` と `refute` の 2 つだけである。** `duplicate` は 2 段目の
統合の入力になり、`out_of_scope` は区分を変えずに、範囲外の課題を起票する材料として残る。
**`refute` の代わりに後ろの 2 つを使わせない。** どちらも「指摘が誤っている」という主張では
ない。

**担当はファイル名から採る。** 本文の申告を採ると、別の担当を名乗った値をそのまま数える
ことになる。**結び先の無い値は捨てず `unmatched_critiques` へ残す**（捨てると、反証が 0 件の
ラウンドと、結び先を誤ったラウンドが同じに見える）。

### 区分

**上から順に見て、最初に当たった区分を採る。**

| 順 | 区分 | 条件 |
| --- | --- | --- |
| 1 | `verified_blocking` | 再現した、かつ `major` 以上 |
| 2 | `verified_non_blocking` | 再現した、かつ `minor` 以下 |
| 3 | `rejected` | 再現しなかった、または `refute` が 1 件以上 |
| 4 | `needs_human_judgment` | 根拠を持ち、`major` 以上で、`support` が 1 件以上**または** `origin_runtimes` が 2 者以上 |
| 5 | `insufficient_evidence` | 上のいずれにも当たらない |

**順 3 を順 1・2 より先に置かない。** 置くと、機械が再現した事実を担当の再評価が覆す。

**独立に到達した担当の数を、支持と並べて数える。** 担当は 2 者であるため、2 者が同じ指摘を
独立に出すと提案者以外が 1 人も残らず、支持は必ず 0 件になる。支持の数だけを見ると、最も
強い一致である全員一致が `insufficient_evidence` へ落ちて収束する。

**順 4 の分岐は、ラウンドの担当が 2 者であることに支えられている。** 担当を 3 者以上へ
広げると、単一の `refute` が順 3 で全員一致を覆す。広げるときに順 3 と順 4 の順序を決め直す。

**棄却には理由を残す**（実行の結果か、`refute` の理由）。

### 区分ごとの行き先

| 区分 | 当ラウンドの修正の工程 | 行き先 |
| --- | --- | --- |
| `verified_blocking` | 渡す | 直す。機械が再現しているため判断の余地は無い |
| `needs_human_judgment` | 渡す | **修正の担当が読んで決める。** 直す・却下の理由を返す・範囲外として起票する |
| `verified_non_blocking` | 渡さない | 最終スイープ。再現した事実は記録に残る |
| `insufficient_evidence` | 渡さない | 同上 |
| `rejected` | 渡さない | 棄却の理由が残り、次のラウンドのレビュープロンプトへ渡る |

**数えないことと、扱わないことは別である。** 最終スイープはループのどの終了経路でも走り、
残った未解決のスレッドを直すか `deferred` として記録して、未解決 0 件で終える。

### 収束の判定

**3 層の順序（引き継ぎ → 新規性 → 振動）は変えない。** 変えるのは 2 層目が数える対象である。

| 状態 | 返る値 |
| --- | --- |
| 指摘の記録を読めない | `(0, 測れない)`。従来の判定（全員が pass か）へ落ちる |
| 記録はあるが、数える 2 区分が 0 件 | **`(0, 測れた)`。収束させる** |
| 記録があり、数える 2 区分に一致しない指摘がある | `(件数, 測れた)` |

**記録が読めることと、数える対象があることは別である。** 全件を棄却したラウンドは「新しい
修正必須の指摘が 0 件」であって、測れなかったラウンドではない。

**新規性の層は却下の記録を読まない。** 一致の判定を持つのは 1 か所であり、区分はその判定が
数える母集合を絞るだけである。同じ抑止を 2 つの仕組みが持たない。

### 効果の測定

**同じ記録を、方式ごとに違う規則で読む。** 母集合は代表だけで、4 つとも `merged_into` を
持つ要素を数えない。

| 方式 | 採る指摘 |
| --- | --- |
| `single` | 1 者だけの結果。担当ごとに 1 通り出す |
| `majority` | `origin_runtimes` が 2 者以上の指摘 |
| `proposed` | 区分が `verified_blocking` または `needs_human_judgment` の指摘 |
| `oracle` | いずれかの担当が出した指摘のうち、**修正された**もの |

**`origin_runtimes` を持たない指摘は、取り込み時の担当 1 者として読む。** この値は統合の
ときに初めて付くため、統合まで届かずに終わったラウンドの指摘と、この変更より前に取った記録は
持たない。0 者として読むと、比較対象の過去の記録の `single` が全件 0 になり、変更の前後を
比べるという目的そのものが立たない。補った値は 1 者であるため `majority` には入らない。

**`majority` は統合の結果を読み、位置の一致を数え直さない。** 同じ判定を 2 か所に持つと
片方だけが古くなる。

**`proposed` が読むのは印のあるラウンドだけで、分母も同じ範囲に限る。** 分子だけを絞ると、
印の混ざった記録で再現率が過小に出る。分母が他の 3 つと違うことは `oracle_scope` と
`oracle_base` の 2 つのキーで常に出す。

**`oracle` は、解決したスレッドの位置と指摘の位置を `(path, line)` で結んで決める。**
絞り込みは 2 つある。

| 絞り込み | なぜ |
| --- | --- |
| 同じ Pull Request の指摘に限る | 指摘のラウンド番号は状態ファイル全体の通し番号で、ラウンドだけで絞るとローテーション前の Pull Request の指摘へ結ばれる |
| 解決を記録したラウンド以下の指摘に限る | それより後の指摘は、解決した時点でまだ存在しない |

絞り込んだ後になお複数が一致するときは、**ラウンドが最も新しいものを採る**（行番号は修正で
動くため、古い側へ結ぶと別の指摘を数える）。その中に 2 件以上あるときはどれとも結ばずに
`ambiguous` へ、どの指摘とも一致しないものは `unmatched` へ数える。**どちらも `found` には
数えない**（落としたことが出力から見えないと、再現率が実際より高く出ていることに気づけない）。

**`oracle` はインラインへ投稿された指摘の上限である。** 総評だけへ書いた指摘はスレッドを
持たないため、修正されても解決済みスレッドとして現れない。

## データ・設定

### 状態ファイルが持つキー

形式そのものは
[04-contracts.md](../../plugins/ndf/skills/cross-review/docs/04-contracts.md)が正である。
この変更で増えたキーと、その約束を示す。

| キー | 何を持つか |
| --- | --- |
| `rejected_findings` | 却下した指摘の per-item の蓄積。`comment_id` / `path` / `line` / `severity` / `summary` / `reason_for_rejection` に `pr` / `round` を添える |
| `review_findings` | 取り込んだ指摘の per-item の蓄積。同じ（Pull Request, ラウンド, 担当）の記録は追記ではなく**入れ替える** |
| `unmatched_critiques` | 結び先の無い反証 |
| `evidence_rounds` | 統合・実行検証・反証を通ったラウンドの番号 |
| `rounds[].fix.resolved_thread_positions` | 解決したと申告したスレッドの位置。**読むのは測定だけで、収束ループは見ない** |
| `rounds[].critique_relaunched` | 反証を取り直した担当。同じラウンドで 1 度だけ取り直すための控え |
| `verify_commands` / `verify_exit_codes` | 実行を許すコマンドと、再現とみなす終了コード |

`review_findings[]` の 1 要素が持つ項目は次のとおりである。

| 項目 | 誰が書くか |
| --- | --- |
| `path` / `line` / `severity` / `body` | 担当（`payload.json`） |
| `evidence` / `falsification` / `suggested_check` / `posted_to` | 同上。**持たなくてよい**（既定は空文字と `inline`） |
| `finding_id` / `pr` / `round` / `agent` / `has_evidence` | 取り込みのときに進行側が付ける |
| `origin_runtimes` / `merged_from` / `merged_into` / `evidence_from` / `duplicate_candidates` | 統合 |
| `verification` | 実行検証。`command` / `exit_code` / `result` / `finding_id` / `ran_at` |
| `critiques` | 反証。要素は `agent` / `verdict` / `reason`（`duplicate` のときは `duplicate_of`） |
| `classification` / `rejection_reason` | 区分 |

**識別子は取り込みの時点で採番する。** 形は `<担当>-r<ラウンド>-<索引>` で、索引はその担当の
`payload.json` の並びである。同じ組の取り込みは入れ替えであるため、再実行しても同じ指摘へ
同じ値が付く。

### 起動時に渡す値

| 引数 | 意味 | 既定 |
| --- | --- | --- |
| `--verify-command CMD` | 実行を許すコマンド。**繰り返し指定でき、トークン列として読む** | なし（実行検証を行わない） |
| `--verify-exit-code N` | 再現とみなす終了コード | `1` |

実行の上限時間は 300 秒である。**超えた実行は実行できなかった扱いであり、再現ではない。**

### 測定の呼び出しと出力

```
measure.py <状態ファイルのパス> [--output <パス>]
```

状態ファイルは 1 つだけ受け取る。省略すると標準出力へ出す。出力は 1 件の JSON で、
`pr`（状態ファイルの鍵）・`prs`（ローテーションで扱った全件）・`rounds`・`methods`・
`cost`・`convergence` を持つ。

| キー | 何の件数か |
| --- | --- |
| `found` | その方式が採る指摘の件数。修正されたかどうかを問わない |
| `matched` | 採用集合と、その方式の分母に使う `oracle` 集合の積集合 |
| `of_oracle` | `matched` を分母の件数で割った再現率。小数第 2 位で丸める |

**`matched` を出力へ出す。** `of_oracle` は `found` からは計算し直せず、添えないと読む側が
`found` を分子として検算して食い違う。

| 決まらない場面 | 出る値 |
| --- | --- |
| 印を持つラウンドが無い | `proposed` が全て `null` で、`reason` は `no_evidence_rounds` |
| 位置の記録を持つラウンドが無い | `oracle` が全て `null` で、`reason` は `no_resolved_thread_positions`。`matched` と `of_oracle` は全方式で `null` |
| 分母が 0 件 | `of_oracle` だけが `null`。`reason` は置かない |
| その方式が 0 件 | `found` と `matched` は `0`、`of_oracle` は `0.0` |

**比べる相手がいないことと、拾えなかったことは別である。** 前者は `null`、後者は `0.0` で
出る。

費用（ラウンド数・担当の起動回数・実時間）と収束の様子（終わり方・振動・上限の到達）は、
**ローテーション全体の合計**である。終わり方は状態ファイル全体で 1 つであるため、振動と
上限の到達は 0 か 1 の値で出す。**合計そのものは作らない**（複数を比べるときに測る側が
足し合わせる）。

## 運用

**実行検証を使うかは、起動する側が決める。** 引数を渡さないリポジトリでは実行検証が走らず、
区分は根拠と反証で決まる。既定の一覧は持たない（リポジトリによってテストの起動が違う）。

**印を持たない記録では `proposed` を計算できず、位置の記録を持たない記録では `oracle` と
再現率を計算できない。** この変更より前に回した Pull Request が該当する。変更の前後を
再現率で比べるには、両方の期間の記録が位置を持っている必要がある。

**比較には変更の前後の状態ファイルが要る。** 状態ファイルは作業ツリーの中にあり、後片付けの
工程が作業ツリーごと消す。**測る前に控える。**

**`majority` の値は、統合の判定の厳しさを含んだ数字である。** 統合は過剰を避けて厳しい側へ
倒しており、取りこぼしは `duplicate_candidates` に残る。統合し損ねた組をこの方式へ数え直すか
どうかは、統合の実測が出てから決める。

**振動の閾値（0.5）は、母集合が広がった後の実測で見直す。** この変更では触れていない。

**担当を 3 者以上へ広げるときは、区分の順 3 と順 4 の順序を決め直す。**
