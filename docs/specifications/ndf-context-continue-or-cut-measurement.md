# conductor の文脈: 続けるか切るかの計測と、その結果で決める閾値

## 概要

conductor（オーガナイザー・レーン・単独の `/goal` の会話）の文脈を、そのまま続けるか、引継ぎ文書を書いて新しい会話で
続けるかを、同じ物差しで比べて決める仕組みである。比べた結果から、切る閾値・待ちの前に切る規則の要否・復元の量の上限を
数値の根拠つきで決める。

仕組みは 2 つの部分からなる。

| 部分 | 中身 | 状態 |
| --- | --- | --- |
| 比べる材料 | hook が「引継ぎ開始」と「復元完了」の印を打つ・記録の CLI が作業の識別子を課題番号の並びへ揃える・集計を時間で区切る・計測の回ごとに 1 行を作る実験版の補助 | ndf v10.27.53 で入っている |
| 値の決め方 | 計測の手順・計測の記録の形・値を導く式・待ちの前に切る規則を入れるときの形 | 計測の後に当てる。今の hook の既定値（現行方式の運用上限 200,000）と規約は変わっていない |

**hook の判定・印の書き方・集計の CLI の形の正本は [ndf-context-restart-policy.md](ndf-context-restart-policy.md) である。**
この文書は、その上に足した印と区切りが守る条件と、計測でそれらをどう使い、値をどう決めるかを持つ。

## 用語

語の定義は用語集（ [docs/glossary.md](../glossary.md) ）が正である。この文書で使う主な語は次のとおり。

| 用語 | この文書での使い方 |
| --- | --- |
| 復元の量 | 切った後の新しいセッションが「復元完了」の印を書いた時点の文脈の量。費用の式の Q |
| 計測の条件 | 比べる 2 つの設定（「続ける」と「閾値で切る」）。どちらも試行方式の設定で作る |
| 計測の回 | 計測の条件 1 つで、スプリントの設計のフェーズを起動してから、設計承認ゲートの答えを受けた最初の呼び出しまで |
| 待ちの前に切る規則 | 承認ゲートか人の判断の問いを出す直前に、文脈が決めた量を超えていれば会話を切り、新しいセッションで問いを出し直す規則。計測の結果で入れるかを決める |

## 背景

conductor の費用の大半は、文脈が 20 万 token を超える呼び出しにある（ https://github.com/devbasex/ai-plugins/pull/2905 ）。
キャッシュの寿命は最長 1 時間で、人の答えの待ちはその寿命を超えることがある。続けるか切るかの損得は、
新しいセッションが状態を戻すのに読む量（復元の量）と、その区間の呼び出し数で決まるが、手で打つ手順のままでは
「復元完了」の印が 1 行も残らず、引継ぎの印も課題番号で引けない識別子で書かれていた。

| 決めたこと | 理由 |
| --- | --- |
| 印の自動化と計測の補助を先に入れ、値の反映は計測の後に行う | 比べる材料が揃うまで値を決められない。規則を先に入れると、要らないと分かったときに hook とテストを変えないという条件を満たせない |
| 「復元完了」と「引継ぎ開始」は hook が打つ | 手順で打たせると打ち忘れが残る。hook はすべての工程の起動を見ているため、状態を戻し終えた時点と、切ることが決まった時点の両方を見分けられる |
| 引継ぎ文書で始まったかは、会話の記録の先頭（最初の利用者の発言まで）を 1 セッションに 1 回だけ読んで決める | 判定の重さ（末尾の `usage` だけを読む）を変えないため。UserPromptSubmit が起動の引数の最初の入力に発火するかは公式の文書から確かめられず、頼らない |
| ラッパーの外で止めたときは「引継ぎ開始」を書かない | 利用者が続けると決めれば同じ起動が通るため、切るとは限らない |
| 比べるフェーズはスプリントの設計のフェーズにする | conductor の起動 1 回で始まり設計承認ゲートの問いで終わるため、起動の時点の文脈と、待ちの後の書き直しの費用を同じ回で測れる。実装のフェーズは 1 つのキューの続きで流れ、conductor の起動の単位にならない |
| 2 つの計測の条件をどちらも試行方式で作り、判断開始の値と運用上限を同じ値にする | 現行方式はカットポイントで文脈の量に依らず切るため、切った理由に閾値以外が混ざる。同じ値にすると費用の判断帯を通らず、違いが運用上限だけになる |
| 条件の切り替えは既存の `.ndf/context.json` で行う | 新しい切り替えの仕組みを作らない。環境変数はラッパーの起動で決まり、スプリントごとに替えられない |
| 測るためだけのフェーズを流さず、実際のスプリントで計測する | 測るためだけに流すと NDF が起動した分の費用を回ごとに払う。実際のスプリントなら増えるのは 2 つの条件の会話の側の差だけである |
| 回ごとの区切りは集計の CLI（`report --from --until`）に足し、1 行を作る部分は実験版に置く | 区分の数え方を 1 か所に保つ。1 行を作る部分は計測のときだけ呼ぶ |
| 記録の CLI へ渡した作業の識別子は、拒まずに課題番号の並びへ揃える | 拒むと印を打つ手順が止まり、記録が欠ける |
| 決める閾値は 200,000 を上回らない | 品質が落ちる文脈の長さを測っていないため、上回る値が費用で有利でも品質の側の根拠が無い |

## 仕様

### 常に成り立つ条件

| # | 条件 |
| --- | --- |
| I1 | 引継ぎ文書（`.ndf/handoff/`）で始まったセッションには「復元完了」が 1 行だけ付く。付く時点は、エントリポイントの Skill（`development-workflow`・`issue-plan-strategy`）を除く最初の工程の起動である |
| I2 | 引継ぎ文書で始まっていないセッションには「復元完了」を書かない |
| I3 | ラッパーの直接の子の conductor を hook が止めたとき、そのセッションに「引継ぎ開始」が 1 行付く。2 回目以降の拒否では書かない。ラッパーの外の拒否では書かない |
| I4 | 印や状態のファイルを書けなくても、hook の判定（継続・拒否）と拒否の文面は変わらない |
| I5 | サブエージェントの中の起動では判定も印も書かない |
| I6 | 記録の CLI へ渡した作業の識別子は、課題番号を含めば昇順の `#<番号>` の並びに直して書く。含まずセッションの識別子があれば空で書き、読むときに同じセッションの前の行の値で補う |
| I7 | 集計に時間の区切りを渡すと、区切りの中の呼び出し（会話・サブエージェント・使用量の帳簿）と記録の行だけを数える。渡さなければ区切らないときと同じ値を返す |
| I8 | 計測から決める閾値は 200,000 以下である |
| I9 | 待ちの前に切る規則を入れるなら、復元の量の上限 < 待ちの前に切る量 ≤ 閾値 である（新しいセッションがすぐ同じ規則で止まらないため） |
| I10 | 計測の記録に会話の ID・会話の本文・生の記録を置かない |

### セッションの復元の状態

hook はセッションごとに復元の状態を持つ。置き場と形は [ndf-context-restart-policy.md](ndf-context-restart-policy.md) の「状態ディレクトリ」にある。

| 今の状態 | 起動 | 次の状態 | 印 |
| --- | --- | --- | --- |
| 未判定 | 先頭が読めない・利用者の発言がまだ無い | 未判定のまま（次の起動で読み直す） | 書かない |
| 未判定 | 先頭の利用者の発言が引継ぎ文書を指さない | 対象外 | 書かない |
| 未判定 | 先頭が引継ぎ文書を指し、エントリポイントの Skill の起動 | 待ち | 書かない |
| 未判定・待ち | 先頭が引継ぎ文書を指し、エントリポイントの Skill 以外の起動 | 済み | 「復元完了」 |
| 待ち | エントリポイントの Skill の起動 | 待ち | 書かない |
| 済み・対象外 | どの起動でも | 変わらない | 書かない |

「済み」と書けなかったときは「復元完了」も書かない（2 行目を避けるため）。印を書く処理は
[context_marks.py](../../plugins/ndf/scripts/hook_lib/context_marks.py) にあり、token の guard がセッションの排他を取ってから呼ぶ。

### 計測の回の区切り

計測の回の始めと終わりは、実験版の補助が会話の記録から見つける。

| 端 | 既定 | 見つからないとき |
| --- | --- | --- |
| 始め | 渡した会話の記録で、最初に `supervise.py queue` を起動した Bash の時刻（設計のキューの起動） | 止まり、`--from` を渡すよう求める |
| 終わり | 始めの後で最初に答えを受けた `AskUserQuestion`（設計承認ゲートの問い）の後の、最初の呼び出しの時刻 | 止まり、`--until` を渡すよう求める |

会話の記録は、渡したものと、判定の記録で同じ作業の行を持つほかのセッションのものを合わせて読む（切った回は 2 つ以上の会話にまたがる）。

### 値を導く式

計測が揃った後、次の式で値を導く。単価は 100 万 token あたり読込 r = 0.2・書込 1 時間 w = 8・出力 o = 20 USD（Opus 5.5）で、
記号は試行方式の費用の式（ [work-vessels.md](../../plugins/ndf/skills/development-workflow/references/work-vessels.md) の「会話を替えて続けるか」）と同じである。値はすべて計測の回の中央値を使う。

| 記号 | 意味 | どの条件の回から取るか |
| --- | --- | --- |
| k | conductor の呼び出し数 | 続ける |
| m | キャッシュの切れの数 | 続ける |
| Q | 復元の量 | 閾値で切る |
| q | 復元の区間の呼び出し数 | 閾値で切る |
| h | 引継ぎの区間の呼び出し数 | 閾値で切る |
| H | 引継ぎの区間の出力 token | 閾値で切る |

| 決める値 | 式 | 決め方 |
| --- | --- | --- |
| 閾値 T | C\* = (o·H + w·Q + q·r·Q + k·r·Q + m·w·Q) ÷ (k·r + m·w − h·r) | 「閾値で切る」の会話の側の費用の中央値が「続ける」より小さければ T = min(200,000, C\* を 10,000 単位に切り上げた値)。大きいか同じ、または分母が 0 以下なら T = 200,000 のままにし、上げない理由を記録に書く |
| 待ちの前に切る量 W | P を計測の期間の設計承認ゲートの待ちのうち 3,600 秒を超えた割合として、W\* = (o·H + w·Q + q·r·Q + P·w·Q) ÷ (P·w − h·r) | P·w − h·r ≤ 0 か W\* > T なら規則は入れず、hook とテストを変えずに理由を記録に書く。それ以外は W\* を 10,000 単位に切り上げた値で規則を入れる |
| 復元の量の上限 R | (k·r·T + m·w·T − h·r·T − o·H) ÷ (w + q·r + k·r + m·w) | 10,000 単位に切り下げる。I9 を満たさなければ W − 10,000 まで下げる。「閾値で切る」の回の Q が R を超えたら、その回と理由（引継ぎ文書の行数・読み直した文書）を記録に書く |

閾値の値の正本は方針の部品の定数 `CURRENT_LIMIT`（ [context_policy.py](../../plugins/ndf/scripts/lib/context_policy.py) ）1 か所で、規約は値を書く箇所で定数の名前を添える。

### 待ちの前に切る規則を入れるときの形

W の式で規則が要ると決まったときだけ入れる。今の hook には無い。

- 判定は、問い合わせの guard（ [ask_guard.py](../../plugins/ndf/scripts/hook_lib/ask_guard.py) ）が問いを人へ届けると決めた後（区分が許され、オーガナイザーへ送らないとき）に呼ぶ。区分の無い問いは問い合わせの guard が先に止め、レーンの問いはオーガナイザーへ送られて人を直接待たないためである
- 対象はラッパーの直接の子の conductor だけで、ラッパーの外では止めない（人が新しい会話へ貼り付ける操作が増えるため）
- 判定の記録の理由の語に「待ち」を足し、運用上限の拒否と分けて集計する
- 規約「承認ゲートの承認より前に `ndf-next` を出さない」を「問いを出した後、答えを得るまでは `ndf-next` を出さない」に改める。止められた conductor は問いを引継ぎ文書の「次にやること」に保留として残し、新しいセッションが状態を戻した後に出し直す
- 出し直すセッションは工程を起動せずに問いを出すため、待ちの判定を通した時点でも復元の状態を判定し、引継ぎ文書で始まっていれば「復元完了」を書く。最初の工程の起動まで待つと、人の待ちと承認の後の処理が復元の区間に入り、Q と回の費用が大きく出る

## データ・設定

### 計測の条件の設定

メインディレクトリの `.ndf/context.json` に書く（形は [ndf-context-restart-policy.md](ndf-context-restart-policy.md) の「`.ndf/context.json`」）。

| 条件 | 設定 |
| --- | --- |
| 続ける | `{"version": 1, "policy": "trial", "trial": {"decide_from": 950000, "limit": 950000}, "margin": 50000}`（窓 1,000,000 − 容量の余白 50,000） |
| 閾値で切る | `{"version": 1, "policy": "trial", "trial": {"decide_from": 200000, "limit": 200000}, "margin": 50000}` |

### 回ごとの行の補助

[context-trial.py](../../plugins/ndf/scripts/experimental/context-trial.py) は実験版で、台帳は [docs/ndf-experiments.md](../ndf-experiments.md) にある。読むだけで書き込まない。

```bash
python3 plugins/ndf/scripts/experimental/context-trial.py row --work "#2908" --condition 閾値で切る \
  --transcript <conductor の会話の記録> [--from <ISO 8601>] [--until <ISO 8601>] [--input-usd 4.0]
```

| 引数 | 意味 | 既定 |
| --- | --- | --- |
| `--work` | 作業の識別子（I6 と同じ形に揃えてから引く） | 必須 |
| `--condition` | `続ける` / `閾値で切る` | 必須 |
| `--transcript` | 起動した側の conductor の会話の記録 | 必須 |
| `--from` / `--until` | 回の区切り（両端を含む） | 「計測の回の区切り」の既定 |
| `--input-usd` | 入力 100 万 token あたりの USD。入力の単価に換算した費用に掛ける | 4.0（Opus 5.5） |

Markdown の表の 1 行と、統一 JSON の 1 行を出す。終了コードは 0 / 1 区切りが見つからない / 2 `--from`・`--until` が時刻でない。
1 行の列は次のとおりで、会話の ID は持たない。

| 列 | 中身 |
| --- | --- |
| 計測の条件・方針と値 | 区切りの中の最初の判定の行の方針・判断開始の値・運用上限・余白 |
| 起動の時点の文脈 | 同じ判定の行の文脈の量 |
| 会話の側の費用 | conductor・引継ぎの区間・復元の区間の USD とその和 |
| token の内訳 | 会話の側の入力・出力・読込・書込 5 分・書込 1 時間 |
| NDF が起動した分 | supervisor・worker・相手役の USD（判定には使わない） |
| 所要 | 区切りの秒から人の待ちの秒を引いた値 |
| 人の待ち | 待ちの回数と各回の秒 |
| 切った回数・復元の量 | 区切りの中の「引継ぎ開始」の数と、セッションごとの復元の量 |
| 対象外 | 起動の時点の文脈が 200,000 以下か不明なら理由を入れる（2 つの条件が同じに動くため） |

## 運用

計測は、実際のスプリントの設計のフェーズで行う。

1. 起動の前にメインディレクトリの `.ndf/context.json` へ計測の条件を書き、`python3 plugins/ndf/scripts/context-policy.py resolve` の出力の要約を記録の列へ写す。設定はコミットせず、計測を終えたら消す
2. スプリントごとに「続ける」「閾値で切る」を交互に置く（時期による偏りを両方へ散らす）
3. 設計承認ゲートの答えを受けた後に `context-trial.py row` で 1 行を作り、記録へ足す。対象外の回と報告が無い回も、理由を添えて残す
4. 条件ごとに標本が 3 回以上揃ったら、中央値と判定を出し、「値を導く式」で値を決める。3 回に満たないまま 10 スプリントを過ぎたら、その件数で記録を書き、閾値をその条件の結果に依らずに決めた理由を添える
5. 記録は `docs/metrics/` の規約（ [docs/metrics/README.md](../metrics/README.md) ）に従ってその下へ置き、一覧に 1 行足す
6. 決めた値を方針の部品の既定値と `context-window.md` へ反映し、待ちの前に切る規則を入れるなら hook とテストを足す

費用の判定は会話の側（conductor・引継ぎの区間・復元の区間の和）の中央値で行う。サブエージェントは新しい文脈で始まり、
conductor の文脈の量に依らないためである。所要には引継ぎと復元の時間を含め、人の待ちは含めない。

計測が揃う時期は決まっていない。標本に入るのは起動の時点の文脈が 200,000 を超える回だけで、進め方 `fast`・`auto` の
スプリントでは MVV 判定が承認ゲートを通して人の待ちが生じず、P が 0 に寄る。「続ける」は窓 1,000,000 を前提にしており、
statusline が窓を書かなければ運用上限 950,000 だけで判定される。

## テスト観点

- 引継ぎ文書で始まった会話で、エントリポイントの Skill の後に工程を起動すると「復元完了」が 1 行だけ増え、その文脈の量が起動の直前の量であること
- 引継ぎ文書で始まっていない会話では、何度起動しても「復元完了」が書かれないこと
- ラッパーの直接の子で止めると「引継ぎ開始」が 1 行増え、続けて止めても増えず、ラッパーの外で止めると増えないこと
- 状態のファイルの置き場を書けなくしても、判定と拒否の文面が印の無いときと同じであること
- サブエージェントの中の起動で判定の行も印も増えず、既存の `test_token_guard.py`・`test_token_guard_supervisor_cut.py`・`test_context_policy_hook.py` が通ること
- 課題番号を含む識別子が昇順の番号の並びで書かれ、含まない識別子が同じセッションの前の行の値で集計されること
- 区切りを渡すと区切りの外の呼び出しが会話・サブエージェント・使用量の帳簿のどれでも数えられず、渡さなければ区切らない出力と一致すること
- 印が両方そろった会話の組を集計すると、引継ぎの区間と復元の区間が「不明」でなく、復元の量がセッションごとに出ること
- 回ごとの 1 行に会話の ID が現れないこと。キューの起動か答えのある問いが見つからなければ止まり、キューの起動より前の問いは区切りに使わないこと
- 計測の後に値を反映したとき: 既定値で解決した運用上限が決めた値で、文脈がその値を 1 超えると止まり、同じ値では止まらないこと。待ちの前に切る規則を入れたときは、超えていれば止まり、超えていなければ止まらず、区分の無い問いは問い合わせの guard の拒否が出ること
- 計測そのもの（標本・中央値・判定・復元の量が上限以下か）はテストにせず、計測の記録の表と、表から再計算した中央値で確かめる。リリースの後は、ラッパーの下で conductor を 1 回動かし、決めた閾値で hook が止め、新しいセッションが「復元完了」を記録することを見る
