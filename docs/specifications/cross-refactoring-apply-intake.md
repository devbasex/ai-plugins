# cross-refactoring: 担当が結果を残さないと同じ適用ラウンドが上限なしに開き直され、未検証のコミットが残り、帰属トレーラーで必須トレーラーが読めなかった → マージ処理は git から項目を読み、結果ファイルの欠けを値で受けて進行を止めず、最終ゲート修正の結果なしは取り消して記録し、必須トレーラーは帰属トレーラーの後ろから読む

**#933 で改めた。** 適用ラウンド・群・輪番が無くなり、適用ラウンドの開き直しの判定・試行の上限
2 回・担当の交代・項目の無い適用ラウンドの扱いは過去の仕様になった。テストの追加・実装・修正の
マージ処理は結果ファイルを読まずに git だけで決める（[検証と最終ゲートの確定仕様](cross-refactoring-verify-and-final-gate.md)）。
この文書に残るのは、結果ファイルの欠けを値で受ける読み取り・最終ゲート修正の結果なしの
マージ処理・必須トレーラーの読み方である。

## 目的

**担当の CLI が作業結果を残さずに終わっても、進行は止まらずに終わる。** 下位の読み取りが
進行を打ち切ることはない。結果ファイルの欠けをどう扱うかは、読んだ側が値として受けて決める。

**検証を受けていないコミットは Pull Request に残らない。** 最終ゲート修正を行った実装担当が結果を
残さなかったときは、作られたコミットを取り消し、起動結果を記録し、次の最終ゲートは取り消した後の
地点でテストする。

**起動し直しても解けない起動結果（利用上限）では、最終ゲート修正を起動し直さない。**

**実行環境が帰属トレーラーを後ろへ足したコミットでも、必須トレーラーが読める。** オーケストレーターはマージ処理で
コミットを書き換えない。

**手順と引数の表は
[`cross-refactoring` の SKILL.md](../../plugins/ndf/skills/cross-refactoring/SKILL.md)と
[`docs/`](../../plugins/ndf/skills/cross-refactoring/docs/02-plan-and-implement.md)が正である。**
ここに書き写さない。この文書が扱うのは、そこに書かない決定の理由と、進行の内部の契約である。

## 用語

本文は左の業務用語で書く。識別子は表・コードブロック・業務用語の初出の括弧書きにだけ置く。

| 業務用語 | 識別子 | 何を指すか |
| --- | --- | --- |
| マージ処理 | `merge-proposals` / `merge-plan` / `merge-tests` / `merge-implement` / `merge-fix` / `merge-final-fix` | 担当の結果やコミットをオーケストレーターが受け入れるコマンド |
| 最終ゲート | `final-gate` | 全体テストか継続的統合で合否を判定する |
| 最終ゲート修正 | `final-fix` / `merge-final-fix` | 最終ゲートの失敗を直す起動と、そのマージ処理 |
| 起動結果 | `LaunchOutcome` | 担当 1 回の起動の終わり方。使える結果か、結果なしの理由かを持つ |
| 結果なし | `payload` が `None` | 結果ファイルが無い、または JSON オブジェクトとして読めない |
| リトライ可否 | `relaunch_same_agent` | 同じ担当を同じ条件で起動し直せば解ける起動結果か |
| 起動結果の読み取り | `gitfacts.read_result` | 状態・担当・手順から結果ファイルの名前の幹を組み、起動結果を値で返す包み |
| 起動結果のライブラリ | `lib/monitor_outcome.py` の `read_launch_outcome` | 理由の語彙と可否を持つ、2 つの Skill 共通の読み取り |
| マージ処理の共通手順 | `refactor_lib/intake.py` | 範囲の確定・取り消し・起動結果の記録。今は最終ゲート修正のマージ処理だけが通る |
| マージ処理の範囲の値 | `IntakeScope` | マージ処理 1 つ分の「どこを見て、どこへ書くか」 |
| 起点 | `final_gate.fix_base_sha` | 範囲の始まり。最終ゲートが落ちた時点の HEAD |
| 起動結果の記録 | `final_gate.failed_attempts[]` | 結果を残さなかった起動の記録 |
| 打ち切りのフラグ | `final_gate.no_relaunch` | 起動し直しても解けない起動結果だったことのフラグ |
| 必須トレーラー | `Item-Id` / `Impl-Runtime` / `Impl-Model` | コミットメッセージのトレーラーとして担当が書く 3 つ（最終ゲート修正は `Item-Id` を除く 2 つ） |
| 帰属トレーラー | `Co-Authored-By:` / `Claude-Session:` | 実行環境がコミットメッセージの末尾へ足す段落 |

## 対象範囲

| 扱う | 扱わない |
| --- | --- |
| 起動結果を値で受け取る読み取りの包み、マージ処理ごとの結果ファイルの扱い | 起動結果のライブラリそのもの（[起動結果](cross-review-launch-outcome.md)） |
| 最終ゲート修正の結果なし・マージ処理の共通手順・起動結果の記録の形 | テストの追加・実装・修正のマージ処理のチェック（[検証と最終ゲートの確定仕様](cross-refactoring-verify-and-final-gate.md)） |
| 必須トレーラーの読み方、オーケストレーターがコミットを書き換えないこと | 手順の監視の上限と無音の打ち切り（[想定最大時間の確定仕様](cross-refactoring-time-budget.md#手順の監視の上限)） |

## 背景

**結果ファイルの読み取りが、そのまま進行の終了コードを決めていた。** 結果ファイルが無い・
読めないときは下位の読み取りがプロセスを終わらせるため、その先にある範囲のチェック・未検証の
コミットの取り消し・状態の記録へ一度も進めなかった（#728）。

**同じ適用ラウンドが上限なしに開き直されていた。** 結果を残さない担当に当たり続け、同じ
適用ラウンドを 29 回開き直した実行（PR #757）と、空振りの起動し直しが 3729 回に達した実行
（#647）があった。採用が 0 件でも項目の無い適用ラウンドに担当を 187 回起動した（#592）。
これらは #728 で開き直しの判定と試行の上限 2 回を置いて止め、#933 で適用ラウンドそのものを
無くした。

**未検証のコミットが Pull Request に残りうる状態だった。** 最終ゲート修正のマージ処理が結果
なしで止まると、担当の作ったコミットは範囲のチェックも取り消しも受けず、以後どの範囲にも入らな
かった（#674）。

**必須トレーラーが、実行環境の足す帰属トレーラーのために読めなかった。** git の標準の読み方は
メッセージの最後の段落しか読まない。帰属トレーラーが後ろに付くと必須トレーラーが欠落と判定された（#553）。

## 決定と理由

| 決定 | 理由 |
| --- | --- |
| 起動結果の読み取りは名前を残した包みとし、結果ファイルの名前の幹をそこで 1 度だけ組んで起動結果を値で返す | 監視へ渡した名前の雛形と食い違う幹で読むと、監視結果ファイルを引けない。幹の組み立てを 1 か所に置く |
| テストの追加・実装・修正のマージ処理は結果ファイルを読まず、`Item-Id` とコミットの時刻だけで決める（#933） | 申告は JSON を書き換えるだけで通る。コミットが無ければ `not_done` か「直っていない」になり、結果なしという別の経路が要らない |
| リファクタリング計画の結果が無くても止めない | 止めると提案に使った時間が丸ごと無駄になる。グレードは既定、テストは足さず、範囲テストはラウンドテストをそのまま使う |
| 「範囲の確定 → 未検証のコミットの取り消し → 起動結果の記録」を共通の層に置き、差は範囲の値で渡す | 取り消しの本体を 1 か所に保つ。共通の層はコマンドの層にも、git の事実の読み取りにも置かない（取り消しは進行の手順である） |
| 最終ゲート修正の結果なしは取り消して判定へ戻し、修正の回数はそこで進めない | 取り消せば、次の最終ゲートは修正前の地点でテストする。回数を進めるのは最終ゲートの側である |
| 起動し直せない起動結果では打ち切りのフラグを立てる | 利用上限の担当を空振りで起動し直さない。1 回目の前には立っていないため、1 回目の直しは妨げない |
| 必須トレーラーは、末尾の段落から前へ 1 段落ずつ git の判定に掛け、判定しなかった段落で止める。1 段落目（題名）は掛けない | トレーラーの形の署名なら、誰が何行足しても同じに読める。題名を掛けるとトレーラーの形の題名を必須トレーラーとして読む |
| オーケストレーターはマージ処理でコミットを書き換えない | コミットの識別子が変わり、申告と実体の対応が切れる。実際に使ったモデル名は担当しか知らない |
| 雛形のコミットの規約にも、必須トレーラーを最後の段落に置くことを書く | 人が git の標準の読み方で集計できる。従わなくてもオーケストレーターの検証は通る |

## 仕様

### 常に成り立つ条件

| 条件 | 破れたときの扱い |
| --- | --- |
| 起動結果の読み取りは中断せず、標準出力と標準エラーにも書かない | 結果を読めなかったときに何をするかは、読んだ側が終了コードとして決める |
| 検証を受けていないコミットを、公開したまま次の工程へ渡さない | 最終ゲート修正の結果なしは範囲を取り消し、取り消した後の先端を次の起点にする |
| 取り消しへ着手する前に、公開の保留のフラグを立てて保存する | 取り消しは済んだのに公開できずに終わると、未検証の変更が Pull Request に残る |
| 取り消した後の起点は、その場で保存する | 保存せずに落ちると、次の実行が古い起点から範囲を取り直し、取り消しのコミット自体を未申告と判定する |
| 同じ工程・同じ試行番号の起動結果は、記録に 1 件しか入らない | 記録済みなら結果ファイルを読まずに終了コード 2 を返す |
| 範囲の「1 件もコミットされていない」と「確定できなかった」を区別する | 混同すると、確定できないときにチェックが素通りする |
| 起動結果の記録は追記だけで、上書きしない | どの担当がどの試行で失敗したかが記録から読める |

### マージ処理ごとの結果ファイルの扱い

| マージ処理 | 結果ファイル | 無い・読めないとき |
| --- | --- | --- |
| 提案（`merge-proposals`） | 参加者ごとの提案を読む | その者の提案を 0 件として続ける。全員が 0 件なら改善候補 0 件で最終ゲートへ |
| リファクタリング計画（`merge-plan`） | 実装担当のリファクタリング計画を読む | 止めない。グレードは既定、テストは足さず、範囲テストはラウンドテストをそのまま使う |
| テストの追加・実装・修正 | **読まない**。モデルの観測（`record_observed_model`）と監視が止めたかの確認（`note_stopped`）だけに標準出力の記録と監視結果ファイルを使う | 関係しない。コミットが無ければ `not_done` か、項目が落ちたまま次の `verify` が締め切りで判定する |
| 最終ゲート修正（`merge-final-fix`） | 読む | 下の「最終ゲート修正の結果なし」 |

**理由の語彙 9 語とリトライ可否は、起動結果のライブラリが 1 か所で持つ。** この文書では定義せず、
[起動結果の仕様](cross-review-launch-outcome.md)を参照する。

### 起動結果を読む

| 項目 | 内容 |
| --- | --- |
| 入力 | 状態ファイルの辞書（一時ディレクトリと実行の識別子を読む）、担当、手順 |
| 名前の幹 | `<担当>-<手順>-rf<ID>`。最終ゲート修正だけ `<担当>-final-fix`（`paths.stem_for`。監視の `--stem-template` と揃える） |
| 出力 | 起動結果。使える結果、または結果なしの理由とリトライ可否 |
| 失敗の形 | **失敗しない。** 中断せず、画面にも出力しない |

### マージ処理 1 回の共通手順

| 手順 | 契約 |
| --- | --- |
| 範囲の確定 | 起点から先端までのコミットを新しい順で返す。確定できなければ「確定できなかった」を返す |
| 取り消し | 公開の保留のフラグを立てて保存 → 新しい順に取り消す → 起点を先端にして保存。取り消した件数を返す |
| 叩き直しの判定 | 同じ工程・同じ試行番号の記録があれば真 |
| 結果なしの一連 | 範囲の確定 → 取り消し → 起動結果の記録へ 1 件を足して保存。取り消したときだけ公開する。範囲を確定できなければ、取り消しも記録も行わずに「確定できなかった」を返す |

### 最終ゲート修正の結果なし

`merge-final-fix` は、未コミットの変更を捨て、公開の保留があれば先に公開し、叩き直しの判定を
見てから起動結果を読む。結果なしのときは次のとおりである。

| 場面 | 扱い | 終了コード |
| --- | --- | ---: |
| 範囲を確定できない | 取り消しも記録もしない | 2 |
| 範囲を確定でき、リトライできる | 範囲を取り消し、記録へ 1 件（工程 `final-fix`）を足す。修正の回数は進めない | 2 |
| 範囲を確定でき、リトライできない（利用上限） | 同上に加えて打ち切りのフラグ `no_relaunch` を立てる。次の最終ゲートは落ちれば取り消さずに報告して終わる（終了コード 1） | 2 |
| 同じ試行を記録済み | 結果ファイルを読まない | 2 |
| 修正担当が未記録（`final-gate` を先に通していない） | 中断する | 4 |

**最終ゲート修正を取り消すと、次の最終ゲートは修正前の地点でテストする。** 取り消した
コミットは修正のコミットの一覧に入らない。押し出し済みの地点で、採用した改善項目は取り消さない
という規則を変えない。

### 必須トレーラーの読み方

コミットメッセージを空行で段落に分け、末尾の段落から前へ 1 段落ずつ git の判定
（`git interpret-trailers --parse`）に掛ける。判定がトレーラーの段落と認めなかった段落で止める。
同じ鍵が 2 つの段落にあれば、末尾に近い段落の値を採る。**1 段落目（題名）は判定に掛けない。**

| 読む側 | 読み方 | どこまで読むか |
| --- | --- | --- |
| オーケストレーターの検証（`gitfacts.commit_trailers`） | 末尾から続くトレーラーの段落 | 帰属トレーラーを越えて必須トレーラーまで届く |
| 人の集計 | git の標準の読み方 | 最後の段落だけ |

**判定そのものは git に委ねる。** 段落だけを渡すと git は何も返さないため、題名の行を補って渡す。
求める必須トレーラーは `vocabulary.REQUIRED_TRAILERS`（`Item-Id` / `Impl-Runtime` / `Impl-Model`）で、
#933 でラウンドの番号（`Round`）を外した。最終ゲート修正は `Item-Id` を求めない。

雛形のコミットの規約は、必須トレーラーをメッセージの最後の段落に置き、実行環境が帰属行を足すときは
空行を挟まず同じ段落に続けることを求める。**従わなくてもオーケストレーターの検証は通る。**

## データ・設定

### 起動結果の記録の 1 件（`final_gate.failed_attempts[]`）

| 列 | 型 | 空を許すか | 意味 |
| --- | --- | --- | --- |
| `phase` | 文字列 | 許さない | `final-fix` |
| `attempt` | 整数 | 許さない | 最終ゲート修正の回数（`final_gate.fix_rounds`）。叩き直しの判定の鍵 |
| `impl` | 文字列 | 許さない | 起動した担当（実装担当） |
| `reason` | 文字列 | 許さない | 起動結果の理由。語彙は起動結果のライブラリが持つ |
| `detail` | 文字列 | 許す（空文字） | 監視の詳細 |
| `at` | 文字列 | 許さない | 記録した時刻 |
| `reverted` | 整数 | 許さない | その起動の範囲から取り消したコミットの数。0 = コミットなし |

### マージ処理の範囲の値

| マージ処理 | 起点を持つ記録 | 起点の鍵 | 記録先 | 工程 |
| --- | --- | --- | --- | --- |
| 最終ゲート修正 | `final_gate` | `fix_base_sha` | `final_gate` | `final-fix` |

**消した値**（#933）: 適用ラウンドの `attempt` / `failed_attempts` / `drop_reason`、試行の上限
`MAX_APPLY_ATTEMPTS`、無進捗の許容 `IMPL_STALL_TIMEOUT` / `IMPL_STALL_MARGIN`、輪番から担当を
引く `impl_for_seq`、開き直しの判定 `group_reopening`。無進捗の打ち切りは手順の監視の上限と同じ値に
なった（[想定最大時間の確定仕様](cross-refactoring-time-budget.md#手順の監視の上限)）。

## テスト観点

| 観点 | 確かめ方 |
| --- | --- |
| 起動結果の読み取りが中断も出力もせず、結果なしと理由を値で返し、名前の幹が監視の雛形と一致すること | `plugins/ndf/skills/cross-refactoring/tests/test_intake.py` |
| 範囲が 1 件・0 件・確定できない場合の取り消しと記録。叩き直しで記録が増えないこと | 同 `tests/test_intake.py` |
| 最終ゲート修正の結果なしで取り消し、起点を進め、次の最終ゲートが取り消し後の地点でテストすること。範囲を確定できなければ試行を開いたままにすること | 同 `tests/test_final_fix.py` |
| 利用上限で打ち切りのフラグが立ち、その後の最終ゲートが取り消さずに報告すること | 同 `tests/test_final_fix.py` |
| リファクタリング計画の結果が無くても止まらないこと | 同 `tests/test_merge_plan.py` |
| 提案の結果が壊れていてもその者を 0 件として続けること | 同 `tests/test_merge_proposals.py` |
| 帰属トレーラーが後ろに付いたコミットから必須トレーラーを読み、散文の中のトレーラーの形の行と題名を読まないこと | 同 `tests/test_commit_trailers_git.py`（一時リポジトリで git を実行する） |
| 文書の分量が分割の基準を超えないこと・参照のリンクが解決できること | `python3 scripts/check-doc-line-limit.py` / `python3 scripts/check-markdown-links.py` |
