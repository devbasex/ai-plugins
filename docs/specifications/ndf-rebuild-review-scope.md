# NDF の作り直しの範囲: 設計レビューの全項目に行き先と版を付け、11.0.0 を今の NDF と同等で切る

#1142 の作り直しの設計レビュー 4 巡で見つかった 182 項目に、行き先の子と版（11.0.0 か 11.x）を付けた決まりと、11.0.0 を出せる時点の条件・11.x へ回したものの受け皿・解消する Issue を閉じる操作と証拠・テストと CI の予算・依存の更新の扱いを持つ確定仕様である。決定の番号は `ndf-rebuild` で始まる 6 本の確定仕様を通して一意で、索引と番号の対応表は [ndf-rebuild.md](ndf-rebuild.md) にある。

## 概要

**例: 11.0.0 を出した時点の判定。** 2026-11-17、利用者は 11.0.0 を早めるため、試走で機能の対応表の全行が通ること・今の機能の不具合を直す Issue を閉じることの 2 つを 11.x へ移した（#1142 と S2 #3304 の本文に取り消し線と理由がある）。入れ替えの PR は、残った条件で判定した。機能の対応表 `scripts/ndf-next-parity/parity/features.json` は 216 行で、200 行が行き先の子（`to`）を、16 行が作らない理由（`not_built`）を持つ。退行させないもの 5 つ（承認ゲート 2 つ・hook の守り・秘密の検査・Codex 向けのリリース・Factory の契約）は `kind` が `non-regression` の行として載り、承認前の試用（S2 #3304 の S2-10）で主な Skill を 1 回ずつ起動して確かめた。リリースは `release-cd.yml` の workflow が組み立て・承認の証跡の確かめ・マージキュー・タグ `ndf--v11.0.0` と GitHub Release まで行った。

**例: 解消する Issue を証拠つきで閉じる。** 棚卸しの子 M6 #3301 が作った `ndf issues settle --file <JSON>` は、入力の行ごとに証拠を GitHub で確かめ、通った行だけを、証拠をコメントに書いてから閉じる。1 行でも確かめられなければ、その行を閉じずに理由を返し、結果を `stopped`（止まった理由 `refused`）にする。

| 構成要素 | 責務 |
| --- | --- |
| 振り分け表（#3395 の設計の材料） | 182 項目の行き先の子・順番・要求の行・版。結果は各子の Issue の本文が持ち、確定仕様へ移さない |
| 機能の対応表（`scripts/ndf-next-parity/parity/`） | 10 系の機能 1 つを 1 行にし、行き先の子か作らない理由と試走の結果を持つ。形はスキーマ `schema.json` と `table.shape_errors` が縛る |
| #3388 | 11.x へ回した項目の受け皿。11.x の行の行き先は #3388 の対応表が持つ |
| `ndf issues settle`（`plugins/ndf/src/ndf/domains/backlog/settle.py`・`settle_decide.py`） | 解消する Issue を、閉じる証拠を確かめてから閉じる唯一の操作 |
| `release-cd.yml`・`ndf-release-reusable.yml` と `ndf release-steps` | リリースの組み立て・承認の証跡の確かめ・マージ・タグと GitHub Release・リリース記録 |
| X2 #3370 | 依存の遅れの知らせと版の引き上げ（11.x） |

| 語 | 意味 |

## 背景

#1142 の作り直しの設計レビューは 4 巡で 182 項目を見つけたが、子の表に席があるのは 2 分類だけで、閉じた子へ足す項目が 61 件、要求の受け入れ条件に持ち主の無い行が残った。利用者は新しい子の着手を止め、全項目の行き先と範囲を先に決めるよう求めた（2026-11-14、#3395）。同じ日に、今の機能とほぼ同等の実装ができたら一度 NDF を差し替え（11.0.0）、上げた版で残りの機能を作ると指示した。受け入れ条件が「ラベル `rebuild-1142` の Issue がすべて閉じる」のままでは、11.0.0 の時期が改善の量で決まる（開いていたラベルの Issue は 291 件）。

#3395 は全項目を振り分け表へ割り当て、版の基準で 11.0.0 の 125 件と 11.x の 57 件に分け、11.0.0 の受け入れ条件を置き換えた。

### 閉じる操作と証拠

**解消する Issue は閉じる証拠を 1 つ持ち、`ndf issues settle` が証拠を確かめてから閉じる**（決定 117）。子の PR の closing keywords では閉じない。

| 証拠の種類 | 当てる場合 | 確かめ方（`settle.py`。基底のブランチは `--base`、省けば既定のブランチ） |
| --- | --- | --- |
| `improved`（改善の証拠） | 原因の機能を作り直した | PR がマージ済みでマージ先が基底のブランチ、PR の変更ファイル（REST の `pulls/<N>/files`）にテストのファイルがあり、その差分がテストの関数の定義を足し、基底のブランチのそのファイルに関数がある |
| `removed`（消えたコードのパス） | 原因の機能の後継を作らない | コミットが基底のブランチの祖先で、パスがコミットの親にあってコミットで消え、基底のブランチに無い |
| `not_reproduced`（再現しない記録） | 原因が CI・GitHub・時間の外部の振る舞いで、単体のテストで再現できない | 終了コードが 0、記録のファイルが基底のブランチにあり、`after_pr` がマージ済みで、日時がそのマージより後で今より前 |

入力は `{"settle": [{"issue": <N>, "child": "<子の記号>", "evidence": {"kind": "<種類>", ...}}]}` で、種類ごとの必須のキーは `improved` が `pr`・`test`（テストのノード ID）、`removed` が `path`・`commit`、`not_reproduced` が `command`・`exit`・`record`・`at`・`after_pr` である。行ごとの結果は `closed`・`verified`（`--dry-run`）・`unverified`（理由つき）・`already_closed` で、既に閉じた Issue にはコメントを書かない。

- **依存の遅れの知らせと版の引き上げは、既存のツールに任せる**（決定 118）。ツールの選択と設定は X2 #3370 の設計（Renovate を GitHub Actions の上で動かす）が持ち、X2 は 11.x である

- `plugins/ndf/pyproject.toml` に宣言があって `src`・`tests` からの import が 0 件の依存は 4 本ある（2026-11-21。mdit-py-plugins・pydantic・slack-sdk・tabulate）。数えたコマンドは次のとおりで、`plugins/ndf` で打つ

```bash
for m in mdit_py_plugins pydantic slack_sdk tabulate; do
  echo "$m $(grep -rEn "^\s*(import|from) $m(\.| |$)" src tests | wc -l)"
done
```

**新しく書くファイルの排他は filelock、打ち直しは tenacity を使う**（決定 119）。filelock は `ndf.slot_pool`・`ndf.adapters.launch_slot`・`ndf.domains.worktree`・`ndf.domains.loop` など 17 ファイルが、tenacity は `ndf.adapters.notify` が import する。標準の `fcntl` で取る箇所は次のとおりである。

### リリースの workflow とリリース記録

- **リリースは GitHub Actions の workflow が行う**（決定 128）。`release-cd.yml` は `main` への push でタグと GitHub Release を作り、リリースの PR の承認の証跡を確かめて commit status `ndf/release-approval` を付け、証跡の後にマージキューへ入れ、`workflow_dispatch` の `step=assemble` で版上げのブランチと PR を組み立てる。処理はすべて `plugins/ndf/bin/ndf release-steps` が持ち、会話のセッションは承認資料の提示（`present`）と答えの証跡（`answer`）だけを持つ
- **リリース記録は含めた PR の各々へ書く**（決定 129）。副命令は次の 3 つで、記録の印は `<!-- ndf:release-record -->` と `<!-- ndf:release-verification -->` である

| 副命令 | 打つもの | すること |
| --- | --- | --- |
| `record --pr <リリースの PR> --production <本番ブランチ> --production-sha <SHA>` | workflow（マージの後） | 本番ブランチへ入ったリリースの PR に含めた PR の各々へ、リリース記録（`version`・`release`・`included`）を書く。同じ版の記録が既にある PR には書かない |
| `verification-record --pr <N> --record <JSON>` | 会話のセッション | リリース後テストの記録（スキーマ `release-verification`）を、同じ版のリリース記録を持つ PR へだけ書く。リリースの PR を渡すと、記録を持つ PR を示して止まる |
| `records --pr <N>` | 課題を閉じる側 | 信用する書き手のリリース記録とリリース後テストの記録を読む |

含めた PR は、組み立てがリリースのコミットへ書いた承認資料の「含む PR」の行から読み、行が無ければリリースの PR のコミットを先端から first-parent で辿った件名から、承認資料と同じ規則（`included_decide`）で決める。コミットはマージの第 1 親からリリースの先端までの compare をページ送りで読む。読む側と、既に書いたかの判定は、write 以上の権限を持つ書き手の記録だけを見る。書く前に書く token の書き手が信用されるかを確かめ、信用されなければ 1 件も書かずに止まる。

## 決定と理由

### 決定 109: 子の着手を表の上で再開するため、全 182 項目を 1 つの振り分け表へ割り当て、行き先を子の本文へ写す

項目ごとに行き先の子・順番・新設か追補か・要求の行・版を 1 行で持ち、抜き出しのコマンドの出力（182 件）と表の 1 列目を突き合わせて漏れを 0 件にした。行き先は各子の Issue の本文の受け入れ条件へ写し、11.x の行は #3388 へ移した。

- 採らなかった案: 項目を分類ごとの Issue の本文に残し、子の本文から指す。項目と子の対応が 2 か所に分かれ、どちらが正か決まらない
- 採らなかった案: 子の表のコピー `children.json` に項目を生成して置き、規則 `review-items` で表と本文を突き合わせる（#3395 の初めの形）。11.x へ回し（決定 123）、今のコピーは項目を持たない

### 決定 110: 閉じた子の範囲を閉じたまま追えるよう、閉じた子への作業は追補の単位にする

形は「子の分け方」にある。動いている子には足さず、その範囲の新しい項目は後続の子へ送る。

- 採らなかった案: 閉じた子を開き直す。閉じた PR と受け入れ条件の済みの記録が混ざり、何が残りかが読めなくなる

### 決定 111: 1 本の PR に収まる大きさに揃えるため、受け入れ条件が 25 行を超える子を分ける

基準は、1 本の PR に収まらないと判断して P1a #3369 と P1b #3092 に分けた子の、分ける前の 38 行と分けた後の P1a の 19 行の間に置いた。

- 採らなかった案: 基準を検査で縛る。受け入れ条件は Issue の本文にあり、数え方（追補の節・取り消し線）を持ち込むと規則の方が大きくなる

### 決定 112: 持ち主の無い機能に席を作るため、X3・M8・T2・S3 を新設する

対応表は順番 2 で要り、後の子に置くと後続の子が対応表なしで進む。worktree はほかの子のどの領域にも属さない。

- 採らなかった案: 既存の子へ足す。席の順番と領域が合わない

### 決定 113: 範囲を 1 回で決められるよう、要求の行が無い 34 件と範囲が膨らんだ 7 点に推奨を付け、振り分け表をその推奨で書く

推奨は版の列と同じ値で、基準は決定 123 の版の基準である。11 件を 11.0.0 へ広げ、23 件を 11.x へ回した。範囲が膨らんだ 7 点（全 lock・`docs/` の整理・英語・GitHub Enterprise・macOS・LLM の予算・Skill 本文）は、`docs/` の整理のうち入れ替えに要る分を除いて 11.x である。

- 採らなかった案: 推奨を付けずに並べる。判断の材料が利用者に偏り、承認の場で同じ検討を繰り返す

### 決定 115: 要求と実装の食い違いを実装の決定に沿って解くため、行数の上限と Python の下限は要求を書き換える

ファイルの行数の上限は `checks/rules.json` の `structure.max_lines` の 1,000 で（[ndf-rebuild.md](ndf-rebuild.md) の I22）、Python の下限は `plugins/ndf/pyproject.toml` の `requires-python = ">=3.11"` である。Python 3.10 は 2026-10-01 に保守を終えた（PEP 619）。AI が陥りやすい作りの種類 6（コピーで生まれた重複）は検査で落とさない（[ndf-rebuild-data-and-smells.md](ndf-rebuild-data-and-smells.md) の決定 44）。

- 採らなかった案: Python の下限を 3.10 へ戻す。保守の終わった版のために、filelock の脆弱性の 14 件（#3380）を抱えることになる
- 採らなかった案: 種類 6 の規則を `rules.json` に足す（#3395 の初めの形）。11.x の範囲で、今の `smells` は種類 2・3・4・5・7 の 14 規則を持つ

### 決定 116: 要求の全行を作り直しの設計と矛盾させないため、食い違う 13 か所と構造の条件 3 か所を #1142 の本文で書き換える

書き換えは [ndf-rebuild.md](ndf-rebuild.md) の決定 105 と同じ形（取り消し線と置き換えの文）で行い、正は Issue の本文である。作らない 4 行には取り消し線だけを引いた。

### 決定 117: 解消する Issue を改善を確かめてから閉じるため、閉じる証拠を 3 種類に決め、`ndf issues settle` が確かめて閉じる

形は「閉じる操作と証拠」にある。M6 #3301 は Issue の一覧を GitHub のアダプター越しに読む棚卸しの子で、閉じる操作も同じ境界に置ける。

- 採らなかった案: 子の PR の closing keywords で閉じる。テストが無いまま閉じても止める手段が無い

### 決定 118: 依存の更新を自前で保たないため、遅れの知らせと版の引き上げを既存のツールに任せる

ツールは X2 #3370 の設計が Renovate に決めた（GitHub Actions の上で動かし、7 日待つ・固定と理由・1 件の Issue での知らせを設定で持つ）。GitHub Actions の版は今の Dependabot が見る。

- 採らなかった案: `scripts/plugin-deps.py` と週 1 回の CI で遅れを Issue へ知らせる自作（#3347 の決定 107）。知らせ・上げる操作・推移的な依存をスクリプトとテストとワークフローで保守し続ける
- 採らなかった案: Dependabot で `plugins/ndf` の uv を見る（#3395 の推奨）。固定の理由を書く項目を持たず、知らせが PR の単位で、1 件の Issue にまとめる設定が無い（X2 #3370 の設計の比較）

### 決定 119: 同じ概念を 2 つ持たないため、新しく書く排他と打ち直しは lock にある filelock と tenacity を使う

置き場は「ロックと打ち直しの部品」にある。`fcntl` を残す箇所は、共有のロック・hook の予算・10 系の旧い錠と互いに待つ、のどれかの理由を持つ。

- 採らなかった案: 自作のロックと打ち直しをすべて置き換える（#3395 の初めの形）。11.x の範囲（項目 3395-9）で、`identity.py`・`adapters/run_log.py`・`adapters/llm.py` は今も自前で持つ
- 採らなかった案: 使う予定の依存も今すべて消す。使う子が足し直すたびに宣言と lock の変更が子の PR どうしで衝突する（`uv.lock` の衝突は [ndf-rebuild.md](ndf-rebuild.md) の決定 108）

### 決定 120: テストと CI を作り直しで増やさないため、10 系の NDF の半分を予算にする

値は「テストと CI の予算」にある。半分にするのは、テストを削る方針（2026-10-31 の利用者の方針）に沿うためである。

- 採らなかった案: 予算を超える PR を検査（X1+ #3283）とテスト基盤（T1+ #3286）で落とす（#3395 の初めの形）。11.x の範囲（項目 3395-10）で、今は数えて比べるだけである
- 採らなかった案: 子ごとに配分する。子の大きさの差が大きく、配分の値の根拠が無い

### 決定 122: 作り直しの子が前の子の成果の上に切られるため、子の起点と宛先をブランチ戦略の宣言から読む

ai-plugins の宣言は `branch_strategy` の `release_strategy: trunk` で、`branches` の `base` と `production` はどちらも `main` である。子の worktree は `main` から切り、PR は `main` へ出す。

- 採らなかった案: 子の起点と宛先を `develop` にし、入れ替え（S2 #3304）まで `main` へ出さない（作り直しの間の形。#3378）。11.0.0 の後に開発版のチャネルをやめ（#3672）、`develop` は無い

### 決定 123: 11.0.0 を早く出すため、11.0.0 を今の NDF と同等で切り、振り分け表の全行に版を付ける

基準は「版の基準」にある。182 件は 11.0.0 の 125 件と 11.x の 57 件に分かれた（決定 127 で 11 件を 11.0.0 へ戻した後の数）。

- 採らなかった案: 行き先の子の列を #3388 へ書き換える。11.x で作るときの持ち主が表から消え、#3388 の中で同じ割り当てをやり直すことになる

### 決定 124: 11.0.0 を出せる時点を判定できるよう、受け入れ条件を「ラベルの Issue がすべて閉じる」から対応表の行の条件へ置き換える

条件と扱いは「11.0.0 の受け入れ条件」にある。11.0.0 で判定したのは、対応表の全行の行き先・退行させないもの・対応表の行で判定すること・リリースの workflow の 4 つである。試走で全行が通ることは、2026-11-17 の利用者の判断で 11.x へ移した。

- 採らなかった案: ラベルの件数で見る。開いていたラベルの Issue は 291 件（2026-11-14）で、多くは今の NDF に無い改善である
- 採らなかった案: 試走で対応表の全行が通ることを 11.0.0 の条件にする（#3395 の形）。11.0.0 を早めるため、承認前の試用と 11.0 で開発を回すことで代えた

### 決定 125: 振り分けの案を版の基準で行ごとに確かめ、基準に合わない 13 件を 11.0.0 へ直す

分類ごとの案を行ごとに当て直し、今の NDF が持つ振る舞いを外す 13 件を 11.0.0 にした（待ちの Slack 通知・宣言の無いリポジトリで既定ブランチのまま動くこと・やめる判断の時点・README・Factory の契約の 5 行・学習に使わない設定の確かめ・宣言 7 種・suite の runner・件数の黙った切り捨て）。11.0.0 の子でも、今の NDF に無い機能を足す行は 11.x にした。

### 決定 126: S1 を短くするため、Skill 本文とエージェント定義は今のまま移し、直すのはスクリプトのパスとコマンドだけにする

S1a #3303 は本文を移し、スクリプトのパスとコマンドを `bin/ndf` の副命令へ書き換えた。役割の書き換えと本文の書き直しは 11.x である。

- 採らなかった案: 本文を書き直してから入れ替える。書き直した本文の振る舞いの違いが入れ替えの差分に混ざる

### 決定 127: 不具合を引き継がないため、「同等」を意図した振る舞いと同じことと定め、今の機能の不具合を直す Issue を閉じる確かめを 11.x に置く

不具合（誤った振る舞い・止まる・誤報）を直す項目は版の基準で 11.0.0 に置き、振り分け表の 11.x の行から 11 行を戻した。新しい機能・改善・汎用化は 11.x のままである。不具合の Issue を閉じる確かめは、閉じる証拠（決定 117）で行う。

- 採らなかった案: 今の NDF を不具合ごと同じ形で移す。不具合を引き継ぐのは同等と言えない（利用者の決定、2026-11-14）
- 採らなかった案: 不具合の Issue がすべて閉じることを 11.0.0 の条件にする（#3395 の形）。11.0.0 を早めるため、2026-11-17 の利用者の判断で 11.x へ移した
- 採らなかった案: ラベルの Issue をすべて閉じる形へ戻す。多くは改善で、時期が改善の量で決まる

### 決定 128: 会話のセッションを承認資料の提示と答えだけにするため、リリースを GitHub Actions の workflow で行う

形は「リリースの workflow とリリース記録」にある。承認の正本を PR の証跡に一本化し、承認の答えが記録へ届く前に止まると同じ承認ゲートで止まり続ける不具合を持ち越さない。

- 採らなかった案: 会話のセッションがリリースの手順のスクリプトを打つ形を移す。会話が切れる・止まると承認の後のリリースが進まない（#3175 の約 6 時間の停止）

### 決定 129: まとめて出した正式版でも各スプリントの課題を閉じられるよう、含めた PR の各々へリリース記録を書き、リリース後テストの記録も同じ PR へ書く

元の事象は #2783（まとめて出した版で、スプリントの PR にリリース記録が無く課題が閉じなかった）と #3128（リリース後テストの記録が本番ブランチ宛てのリリースの PR に置かれ、閉じる側が読めなかった）である。形は「リリースの workflow とリリース記録」にある。

- 採らなかった案: リリースの PR に 1 件だけ記録を書き、各スプリントの PR から探す。閉じる側が自分の PR から記録を読めない
- 採らなかった案: 含めた PR の範囲を手元の git で読む。マージのジョブは既定ブランチを浅く取り出し、認証情報を残さないため、非公開のリポジトリで範囲の履歴を取り込めない
- 採らなかった案: `pulls/<番号>/commits` で範囲を読む。250 件で切れ、大きなリリースの PR を読み切れない

## テスト観点

- IY5: `plugins/ndf/tests/domains/backlog/test_settle.py` が、証拠の種類ごとに通る行と通らない行（PR が未マージ・マージ先が違う・差分がテストの関数を足していない・パスが残る・終了コードが 0 でない・日時がマージより前）を確かめ、1 行でも通らなければ閉じずに `stopped` になることを縛る
- 機能の対応表: `scripts/ndf-next-parity/tests/test_table.py` が、`to` と `not_built` のどちらも無い行・`locations` に無い行き先・重なる `id` を誤りにし、`non-regression` の 5 行があることを確かめる
- リリース記録: 同じ版の記録がある PR に書き直さないこと・信用しない書き手の印のあるコメントを読み飛ばすこと・リリースの PR へリリース後テストの記録を書かないことを、`plugins/ndf/tests/domains/release/test_release_record.py` が縛る
- 決定の番号の一意: `grep -hoE '^#{2,4} 決定 [0-9]+' docs/specifications/ndf-rebuild*.md | grep -oE '[0-9]+$' | sort -n | uniq -d` が 0 行
- テストの数: 「テストと CI の予算」のコマンドで数えた値が予算以下であることを、確定仕様化の測り直しで見る（検査は無い）
