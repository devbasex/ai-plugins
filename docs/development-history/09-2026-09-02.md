## 用語

| 語 | この文書での意味 |
| --- | --- |
| 担当 | 1 件の課題を最後まで進める実行主体。1 担当 = 1 作業ツリー = 1 Pull Request |
| 検査 | `scripts/` 配下のスクリプトが行う機械的な突き合わせ |
| 接尾辞 | 開発版の版数に付ける `-dev.1` などの部分 |

## 何が起きたか

### 設計レビューを 1 本にまとめた

`standard` の 3 件は設計 Pull Request が必須である。3 件を別々に出すとレビューは設計 3 回と
実装 3 回の計 6 回になる。**設計文書はいずれも `issues/parallel-batch-03/` の別々のファイルにあり、
同じ行を書き換えない**ため、1 本にまとめて 4 回に減らした。

まとめた設計 Pull Request（#230）は 6 ラウンドで収束した。指摘は 6 件で、内訳は次のとおりである。

| ラウンド | 指摘 | 何を直したか |
| --- | --- | --- |
| 1 | 1 | 終了コードの割り当ての食い違い（進行側の置換漏れ） |
| 2 | 3 | 版数の比較を整数の組へ、フォーク元の Pull Request での同期の基準 |
| 3 | 2 | 全体指示書の境界表と詳細設計の食い違い |
| 4 | 1 | `strict=True` のときのフォールバックの記述 |
| 5 | 1 | 結果なしのとき判定へ到達しない経路 |
| 6 | 0 | 収束 |

**6 件のうち 4 件は、実装に入っていれば書き直しが 2 か所（設計文書とコード）になっていた。**
特にラウンド 5 の「取り込みの終了コードで判定の手前に止まる」は、設計どおりに実装しても
起動し直しの経路が動かない性質のもので、実装後に気づくとテストも書き直しになる。

### 担当どうしが同じ終了コードを選んだ

担当 B（#196）と担当 C（#217）は、どちらも `state.py` の終了コードを 1 つ新設する設計を書いた。
1〜6 は使用済みで、**両者とも独立に 7 を選んでいた**。

境界の表には「触る関数」を書いていたが、**終了コードのような資源の割り当ては書いていなかった**。
関数が離れていても、同じ番号を使えば後からマージする側が先の値を上書きする。設計をまとめて
読んだ時点で気づき、マージの順序（B → C）に合わせて 7 と 8 に分けた。

### 接尾辞付きの版数で検査が 2 か所落ちた

`develop` チャネルを作り、開発版の版数に接尾辞を付ける運用にした。**版を上げる直前に、接尾辞を
読めない検査が 2 つ見つかった。**

| 番号 | どこ | 何が起きるか |
| --- | --- | --- |
| #248 | `check-doc-staleness.py` の `UPGRADE_HEADING` | `## v9.7.0-dev.1 へ更新するとき` を見出しとして読めない |
| #254 | `validate-runtime-plugins.sh` の `VERSION_IN_DESCRIPTION` | `description` の `(v9.7.0-dev.1)` に一致しない |

**2 件が別々に見つかったのは、版数の書式が 2 つのファイルで別々に定義されているためである**
（#258 として起票）。#248 を直した Pull Request のレビューで、gemini がこの重複そのものを指摘した。

どちらも接尾辞を落とすと「版数が古い」で落ちるため、**片方だけでは接尾辞付きの版を出せない**。
配布の前に両方を直した。

### `cross-review` が実機で #196 の不具合を踏んだ

PR #250 のラウンド 3 で、gemini が結果を残さずに終わった。

```console
$ "$SCRIPTS/state.py" judge 250
✅ 両方 APPROVE。収束。
CODEX_INTENT=APPROVE
GEMINI_INTENT=SKIP
```

**この時点で使っていたのは修正前の版である。** #196 が直した経路がそのまま出た。収束を採らず
gemini を起動し直したところ、結果は `APPROVE` で結論は変わらなかった。**結論が変わらなくても、
結果なしを承認として数えた事実は残る。**

同じ実行の中で、別の形の投稿の失敗も観測した。PR #255 のラウンド 2 で、gemini が
`REQUEST_CHANGES` を返しながら投稿に失敗し、`review_url` が空で重要度別の件数もすべて 0 になった。
**修正の担当が読むべき指摘が Pull Request に 1 件も無いまま、修正の工程が起動する。** #196 が
扱ったのは「結果を残さなかった」場合で、これは対象外である（#261 として起票）。

### `develop` 宛の Pull Request では issue が閉じない

GitHub の自動クローズは既定ブランチへマージしたときにだけ働く。**このリポジトリは既定ブランチが
`main`（正式版）で、開発の変更は `develop` へマージする。** 配布は
`git push origin develop:main` の fast-forward で行うため Pull Request を経由せず、自動クローズは
一度も働かない。

#248 / #254 / #252 の 3 件が OPEN のまま残り、レビュー担当の指摘で気づいて手で閉じた（#259）。

## 次に変えること

| 変えること | 落とし先 | 状態 |
| --- | --- | --- |
| 並行開発の境界に、終了コードなど**資源の割り当て**を書く | 並行開発の指示書の書き方 | この文書で記録。次のバッチで試す |
| `merged` が、閉じ忘れた issue を拾って閉じる | `merged` の手順 | [#259](https://github.com/devbasex/ai-plugins/issues/259) として起票 |
| 版数の書式を 1 か所で持つ | `scripts/` の構成 | [#258](https://github.com/devbasex/ai-plugins/issues/258) として起票 |
| 投稿に失敗したレビューを、結果なしと同じ経路へ乗せる | `cross-review` の判定 | [#261](https://github.com/devbasex/ai-plugins/issues/261) として起票 |
| `develop` 宛の Pull Request で必ず走る検査を持つ | 継続的統合の設定 | [#237](https://github.com/devbasex/ai-plugins/issues/237) の範囲に含む |
| 盤面の値の一覧を工程表と揃える | `projects-common.sh` | [#231](https://github.com/devbasex/ai-plugins/issues/231) として起票 |

**設計レビューを 1 本にまとめる判断は、次も同じ条件で採る。** 条件は「設計文書が別々のファイルに
あり、同じ行を書き換えないこと」である。今回は 6 件の指摘のうち 2 件が担当をまたぐ整合性の指摘
（境界表と詳細設計の食い違い、終了コードの割り当て）で、**分けていれば別々のレビューに出て、
突き合わせる機会が無かった**。

**リリース後テストで確かめる対象に、配布の手続きそのものを含める。** 今回は接尾辞付きの版数で
検査が落ちる不具合が 2 件見つかったが、いずれも**版を上げようとした時点**で表に出た。マージ前の
検証では踏めない。
