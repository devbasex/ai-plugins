# 開発履歴と知見 (2026-08-31)

**期間**: 2026-08-30 〜 2026-08-31
**対象**: [issue #175](https://github.com/devbasex/ai-plugins/issues/175) / [PR #177](https://github.com/devbasex/ai-plugins/pull/177)

`development-workflow` の工程は、どのモードでもマージ後の後片付けで終わっていた。配布した
ものが実環境で動くかを確かめる場と、進め方を見直す場を工程として足し、範囲外の課題を
その場で issue にする横断的な手順を加えて NDF を v9.3.0 へ上げた。

Skill の挙動そのものは各 `SKILL.md` を正とする。本書には、そこに書かない**設計判断の理由**と
**この変更の進め方から出た事実**を残す。

## 何が起きたか

### 工程と横断的な手順を分けた

追加した 3 個のうち、`release-verification` と `retrospective` は順序を持つ工程で、
モードごとに要否が決まる。`out-of-scope` は順序を持たず、実装・構造改善・レビュー・
完了判定のどこからでも呼ばれる。

この違いは表への載せ方に出る。工程表に横断的な手順の行を作ると、モードごとの要否を
決める列ができてしまう。範囲外の課題は見つかるか見つからないかであって、変更の重さが
決めるものではない。工程表には載せず、別の節と図を持たせた。

### 案内を 2 か所へ置いた

横断的な手順は、呼び出し元の各 `SKILL.md` と `development-workflow` の両方へ書いた。

| 置き場所 | 何のために要るか |
| --- | --- |
| 呼び出し元の `SKILL.md`（6 個） | 工程の実行中は手元の `SKILL.md` しか読まない |
| `development-workflow` の節 | 工程との関係と、3 択の判断が一覧で見える |

片方だけにすると、全体像が無いか、実行中に呼ばれないかのどちらかになる。

### レビューは 3 ラウンドで収束した

| ラウンド | codex | gemini | 直した件数 |
| --- | --- | --- | ---: |
| 1 | REQUEST_CHANGES (2) | REQUEST_CHANGES (3) | 6 |
| 2 | REQUEST_CHANGES (1) | REQUEST_CHANGES (3) | 4 |
| 3 | APPROVE | APPROVE | — |

ラウンド 2 の 4 件のうち 3 件は同じ原因だった。起票した課題の由来を `PR #<番号>` と
決め打っていたため、**Pull Request を作る前に見つけた課題**が検索から漏れる。起票・
重複の確認・検索の 3 か所に同じ決め打ちが写っていたので、指摘も 3 件に分かれた。

同じ値を複数箇所へ書くと、直すときも指摘されるときも箇所の数だけ増える。この変更自体が
「判定基準を持つのは `development-workflow` だけ」という原則を扱っているのに、
書いている側で同じ形の重複を作っていた。

## 次に変えること

| 変えること | 落とし先 | 状態 |
| --- | --- | --- |
| 版を上げるときに古くなる記載を検査の対象へ広げる | `scripts/validate-runtime-plugins.sh` | [#178](https://github.com/devbasex/ai-plugins/issues/178) として起票 |
| 版数の一括置換の後に、その版の説明文を読み直す | 同上 | 同じ issue に含めた |

版数を `sed` で一括置換したところ、`plugins/ndf/README.md` の「`v<版>` へ更新するとき」の
本文が前の版（#173 の作業ツリー運用の修正）の説明のまま残った。数字は新しく、説明は古い
状態になり、レビューで指摘された。配布先の表に至っては、1 つ前の版から実測と食い違った
ままだった。

数の記載は `plugin.json` / `marketplace.json` / manifest の 3 つが既に突き合わされている。
`README.md` の 2 か所が検査の外に残っていたため、そこだけが古くなった。

## 途中で起票した課題

| 番号 | 何を見つけたか | 見つけた場面 |
| --- | --- | --- |
| [#176](https://github.com/devbasex/ai-plugins/issues/176) | 並行開発で進行状況を横断して見る場所が無い（GitHub Projects の活用） | 作業中の依頼 |
| [#178](https://github.com/devbasex/ai-plugins/issues/178) | 版を上げるときに古くなる記載が検査の外にある | 振り返り |

実装・構造改善・レビューの各工程では、範囲外の課題は出なかった。#178 は振り返りで拾った
もので、`out-of-scope` が想定する「その場で起票する」経路には乗っていない。発見の時点
（レビューでの指摘とその修正）で起票していれば、振り返りを待たずに残せた。

## リリース後テストで分かったこと

3 ランタイムとも、利用者と同じ導入経路で v9.3.0 を取得でき、追加した 3 個の Skill が
配布物に含まれることを確認した。Kiro CLI だけ Skill 数が manifest より 1 少ない（30 に対して
29）が、これは `ndf-policies` が `.kiro/steering/` へ置き換わる設計どおりである。

Claude Code はセッションの再起動まで新しい Skill を読み込まないため、実際に発動するかの
確認は次のセッションへ持ち越した。配布物の実体・版・内容はいずれも一致している。
