## 何が起きたか

### 設計 Pull Request が 4 ラウンドで収束し、指摘 4 件はすべて設計の内側だった

`standard` の 4 担当（B / C / D / E）の設計を 1 本の Pull Request にまとめた。バッチ 03 と
同じ形である。

| ラウンド | 指摘 | 何を直したか |
| --- | --- | --- |
| 1 | 1 | 担当 D / E の対象範囲が、全体指示書の境界表と食い違っていた |
| 2 | 2 | 担当 D の `scripts/tests/` の扱いが境界表に無い / 振動検知の本文の正規化 |
| 3 | 1 | 閉じる語の読み取りが GitHub の構文と違う |
| 4 | 0 | 収束 |

**4 件のうち 3 件は、実装に入っていれば書き直しが 2 か所（設計文書とコード）になっていた。**
特にラウンド 3 の「`Fixes #12, #13` は 12 だけを閉じる」は、実装してテストまで書いた後に
気づくと、テストの期待値も一緒に書き直すことになる。

ラウンド 1 と 2 の指摘は、いずれも**同じ Pull Request の中の食い違い**である。全体指示書の
境界表を設計と同じ Pull Request で更新したため、片方だけを直した状態が差分に残った。

**設計を通した後の実装で出た指摘は 3 件で、いずれも設計の内容ではなく実装の細部だった。**

どの束にどのコマンドが要るかは実装で調べる項目だった。

### GitHub の GraphQL の上限に当たって 11 分止まった

設計 Pull Request を作る直前に、`gh pr list` が上限で失敗した。

```console
$ gh api graphql -f query='{rateLimit{limit remaining resetAt}}'
{"data":{"rateLimit":{"limit":5000,"remaining":0,"resetAt":"2026-09-02T05:42:54Z"}}}
```

**REST は残っていた。** `gh pr create` と `gh pr list` は GraphQL を使うため止まるが、
`POST /repos/{owner}/{repo}/pulls` と `PUT .../merge` は REST で通る。以降の Pull Request の
作成とマージはすべて REST で行った。

同じ時間帯に別のセッションが [#270](https://github.com/devbasex/ai-plugins/issues/270) と
[#271](https://github.com/devbasex/ai-plugins/issues/271) を起票している。上限の引き上げと、
呼び出し回数の削減がそちらで扱われる。

### テストの実行環境への依存を、実測で確かめてから直した

担当 D の 3 件は、いずれも「テストが実行されないのに、実行されたように見える」経路である。
設計の前に実測を取った。

| 何を測ったか | 結果 |
| --- | --- |
| 全体設定の身元を空にして実行する | `12 failed, 1461 passed`。落ちる範囲は 3 ファイル |
| 根の `conftest.py` へ宣言を移して根から実行する | `1652 passed`（当時） |
| 直した後、根から 1 回で実行する | `1748 passed` |

**実測を先に取ったことで、設計の「候補 2 つのどちらを採るか」が 1 つに決まった。** #235 の
候補には「呼び出し側が既定の身元を与える」もあったが、落ちる 12 件が 3 ファイルに収まると
分かった時点で、テストの側で用意する形の作業量が見えた。

### 配布のたびに読み直す箇所が、この版でも 1 つあった

版数を持つ箇所は 13 あり、すべて検査が突き合わせる。**`plugins/ndf/README.md` の更新案内の
本文だけは機械では判定できない。** 見出しの版数は検査が捕まえるが、本文がその版の変更を
説明しているかは判定できないため、手で書き直した。

`AGENTS.md` の「版の付け方と開発版の配布」の節も、例に並ぶ版数の基底が現行版より小さいと
落ちる。`9.7.0` の例を `9.8.0` へ書き換えた。

## 次に変えること

| 変えること | 落とし先 | 状態 |
| --- | --- | --- |
| 設計と全体指示書の境界表を同じ Pull Request で更新するときは、片方を直したらもう片方も同じ差分で直す | 次の並行開発バッチの全体指示書 | 次のバッチで試す |
| GitHub の呼び出しが上限に当たったとき、REST で代替できる操作を先に試す | `pr` の手順 | [#271](https://github.com/devbasex/ai-plugins/issues/271) で扱う |
| 開発版チャネルの取得手順を、利用者の登録を壊さずに確かめる | 新しい issue | [#277](https://github.com/devbasex/ai-plugins/issues/277) として起票 |
| Skill のスクリプトの位置の決め方を、進行記録の参照から独立させる | `worktree` / `merged` の参照 | [#193](https://github.com/devbasex/ai-plugins/issues/193) へ由来を追記 |

**「設計を 1 本にまとめる」は変えない。** 4 担当の設計をまとめて 1 本にしたことで、レビューは
設計 1 回と実装 5 回の計 6 回になった。分ければ設計 4 回と実装 5 回で 9 回である。まとめた
Pull Request で出た指摘 4 件のうち 2 件は、**担当をまたいで読んだから見つかったもの**
（境界表との食い違い）だった。
