# 開発履歴と知見 (2026-09-01)

**期間**: 2026-09-01
**対象**: [#202](https://github.com/devbasex/ai-plugins/issues/202)（開発の起点ブランチの宣言）と、
その配布（v9.6.0）

配布のチャネルを `main`（正式版）と `develop`（開発版）へ分ける前に、「開発の起点 = 既定
ブランチ」を前提にしていた箇所を揃えた。起点は `.ndf/worktree.json` の `base_branch` で
宣言し、書かなければ既定ブランチのまま動く。あわせて、既定ブランチ宛の Pull Request の
分岐元を継続的統合で検査するようにした。

## 用語

| 語 | この文書での意味 |
| --- | --- |
| 既定ブランチ | リポジトリの HEAD が指すブランチ。clone 直後に checkout される |
| 起点ブランチ | 開発の変更が分岐し、Pull Request の宛先になるブランチ |
| 検査 | 継続的統合（GitHub Actions）で走る自動判定 |

## 何が起きたか

### 課題が挙げた箇所が、前提を持つ箇所の全部ではなかった

issue #202 は前提を持つ箇所を表で 5 つ挙げていた（`worktree` の 2 箇所、`ndf-policies`、
`cherry-pick-pr`、`deploy`）。実装に入って `plugins/ndf/skills/` を grep したところ、同じ
前提が 4 つの Skill に残っていた。

| | 課題の一覧 | 実際に前提を持っていた Skill |
| --- | --- | --- |
| 数 | 4 | 8 |
| 差 | — | `merged` / `pr` / `pr-review` / `problem-solving` |

`merged` は `git checkout main` → `git pull` と `git branch --merged main` を持ち、`develop`
運用では正式版を pull してマージ済み判定も正式版に対して行う。`pr-review` の `--branch`
モードは `git diff main` を比較元にしており、起点が別なら違う差分をレビューする。**課題の
一覧だけを直していれば、移行の後にこの 2 つを踏んでいた。**

範囲を広げるかは運用者へ確認して決めた。4 Skill を含めた結果、変更は 23 ファイルになった。

### 外部コマンドの挙動を確かめずに書いた 3 件が、レビューで修正必須になった

いずれも「1 つのコマンドを 1 回実行すれば分かる」性質のものである。実測はすべて
git 2.53.0 による。

| 書いた前提 | 実際の挙動 |
| --- | --- |
| `git ls-remote --heads origin develop` はそのブランチの有無を返す | パターンは参照名の**末尾**に一致する。`refs/heads/feature/develop` があると成功する。完全な参照名 `refs/heads/develop` を渡しても `refs/heads/x/refs/heads/develop` に一致して終了コード 0 になる |
| `git rev-parse <名前>` はローカルに無ければ追跡参照で解決する | 解決の順序に `refs/remotes/origin/<名前>` は含まれない。失敗時は**渡した名前を標準出力へそのまま書く**ため、出力の有無では失敗を判定できない |
| 既定ブランチの解決は `main` へ落とせば足りる | 共通ライブラリは `origin/HEAD → main → master` の順で探す。`master` だけのリポジトリで、手順側の `${dev_base:-main}` と結果が食い違う |

**テストは 3 件とも通っていた。** 書き手が思い込みを持ったまま期待値を書くと、テストは
その思い込みごと固定する。外れていることは、コマンドを実行するか、外部のレビューが
入るまで分からない。

`AGENTS.md` は「手順・指示書・README に書くコマンドは、書く前に実行して結果を確かめる」と
定めているが、対象が文書に書くコマンドに限られており、コードが呼ぶ外部コマンドは
入っていない（#224）。

### 収束レビューの後半ほど、深いところの指摘が出た

`cross-review`（codex + gemini）を 5 ラウンド回し、13 件を修正した。

| round | codex | gemini | 修正 | 内容の性質 |
| --- | --- | --- | --- | --- |
| 1 | 変更要求 (1) | 変更要求 (3) | 4 件 | 突き合わせテストの穴、参照先の不足 |
| 2 | 変更要求 (1) | 変更要求 (1) | 2 件 | 同上 |
| 3 | 変更要求 (1) | 承認 | 3 件 | `ls-remote` の末尾一致 |
| 4 | 変更要求 (2) | 承認 | 2 件 | `rev-parse` の解決順序、スニペットの照合漏れ |
| 5 | 承認 | 承認 | — | — |

**round 3 以降の 5 件は、いずれも実測しないと分からない外部コマンドの挙動だった。** 前半で
構成の穴が埋まった後に、実装の内側へ指摘が移っている。片側 1 回のレビューで止めていれば、
round 3 以降の 5 件は残っていた。

### 収束レビューの外部 AI が 2 度タイムアウトした

round 1 と round 3 の gemini である。round 1 は結果ファイルが書かれた直後に監視の期限へ
達したもので、結果は拾えた。round 3 は結果が残らず、同じ round で gemini だけを再実行した
（2 度目は 285 秒で承認）。既存の [#196](https://github.com/devbasex/ai-plugins/issues/196) へ
記録した。

修正を担当したサブエージェントが 1 度、利用の上限で途中終了した。成果物（コミット・返信・
Resolve・戻り値ファイル）はすべて揃っており、報告を書く直前で止まっていた。**戻り値ファイルを
報告より先に書く**指示を後続のラウンドから入れている。

## 設計の判断

**起点の解決を 1 箇所に集めつつ、Skill の手順には同じ内容を重複して置いた。** 判定の実体は
`worktree-common.sh` の `wt_base_branch` にあるが、`cherry-pick-pr` / `deploy` / `merged` /
`pr-review` は作業ツリーの仕組みを前提にしない Skill で、共通ライブラリを読み込む前提を
持たせられない。手順には共通ライブラリ無しで動く数行を置き、**両者の解決結果が一致することを
テストで突き合わせる**形にした（`scripts/tests/test_base_branch_consistency.py`）。片方だけを
直すとテストが落ちる。

**起点を入れる変数は `dev_base` にした。** `cherry-pick-pr` は環境ブランチを「ベースブランチ」と
呼んでおり、`base` では 1 つの語が 2 つの対象を指す。

**宣言した起点が実在しないとき、既定ブランチへ落とさない。** 落とすと、開発版のつもりの変更が
正式版から分岐したまま進む。これは直そうとしている事象そのものである。

**宛先の検査は `develop` の有無で自分を有効にする。** 課題は「入れる時期は `develop` を作るのと
同時である」と書いていたが、時期を人が合わせる代わりに、宣言に起点が書かれていてそのブランチが
origin にあるときだけ判定する形にした。作る前に出す Pull Request はそのまま通る。この
Pull Request 自身の検査が実機で通ったことで、その経路は確認できている。

## 残っていること

`develop` ブランチはまだ作っていない。宛先の検査のうち、`develop` が存在する 2 経路は
実機で踏めていない（判定を切り出したスクリプトのテストでは確認済み）。**実機での確認は
`develop` を作るときに行う。** 作るときの手順は `AGENTS.md`「Git運用ルール」にある。
