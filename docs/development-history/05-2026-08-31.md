## 何が起きたか

### 並行して進めた 3 件は互いを妨げなかった

境界の設計は、書き換えてよいパスを担当ごとに分けることと、**3 担当に共通の禁止事項を 1 つ
置くこと**で行った。禁止したのは配布 Skill の数を変えることである。数が動くと、担当 A が
入れた検査が突き合わせる値そのものが変わり、3 者の Pull Request が互いの検査を落とす。

結果として、同じ行を書き換えた箇所は無く、マージの順序による衝突も起きなかった。統合後の
main で検査とテストを実行し、いずれも通っている。

```console
$ bash scripts/validate-runtime-plugins.sh; echo "exit=$?"
runtime plugin validation passed
exit=0

$ uv run --with pytest pytest scripts/tests plugins/ndf -q
1000 passed in 40.59s
```

この制約から、配布 Skill の数を動かす 3 件（[#116](https://github.com/devbasex/ai-plugins/issues/116) /
[#144](https://github.com/devbasex/ai-plugins/issues/144) /
[#161](https://github.com/devbasex/ai-plugins/issues/161)）は次のまとまりへ回した。3 件とも
数を動かすため、そのまとまりの中では直列になる。

### 完了条件を満たした実装に、レビューが 8 件の欠陥を見つけた

3 件とも、指示書に書いた完了条件をすべて満たした状態でレビューへ入った。それでも 2 件で
指摘が出た。

| Pull Request | ラウンド | 指摘 | 内容 |
| --- | --- | --- | --- |
| #184 | 1 | 0 件 | — |
| #183 | 3 | 1 件 | 置換の対象を拾う処理が、テストの失敗メッセージに現れるファイル位置まで書き換えていた |
| #185 | 3 | 7 件 | 収束のループが終わらない経路 1 件、検査を素通りする経路 3 件、ほか 3 件 |

#183 の指摘は、置換の件数が本来の 2 件ではなく 4 件になることを再現して確かめている。
完了条件は「一覧に無い文字列は書き換わらない」までを求めており、**一覧に載っている位置と
同じ文字列が別の文脈に現れる場合**を条件に書いていなかった。

#185 の 7 件は、いずれもこの Pull Request が新しく入れた仕組み自身の穴である。とくに
`eval "$(スクリプト)"` がコマンド置換の終了コードを飲む件は、新設した停止条件が働かない
ことを意味しており、条件を足しただけでは止まらない状態だった。

**この 2 件は、完了条件を書いた側（進行側）が想定できなかった範囲にある。** 完了条件は
「何ができていれば終わりか」を定めるものであり、実装が持ち込む副作用までは書けない。
レビューの工程がその差を埋めた。

### 版を上げる工程が、どの担当にも属していなかった

3 件をマージした時点で、配布物は変わったのに版は据え置きだった。`release-verification` の
開始条件は版の配布が終わっていることであり、この状態では工程を進められない。

版を上げる作業は、指示書にも、いずれかの担当の受け入れ条件にも入っていなかった。進行側が
気づいて別の Pull Request（#187）として出している。

### 指示書に書いた検証コマンドが動かなかった

指示書は 3 担当に `uv run pytest <パス> -q` を渡したが、リポジトリの根には対象のプロジェクトが
無く、この形では実行できない。

```console
$ uv run pytest plugins/ndf/skills/cross-review/tests -q
error: Failed to spawn: `pytest`
  Caused by: Permission denied (os error 13)

$ uv run --with pytest pytest plugins/ndf/skills/cross-review/tests -q
148 passed in 0.38s
```

担当 C が実行して報告し、進行側が残る 2 担当へ訂正を送った。あわせて「既存のテスト 15 本」と
書いた件数がテストファイルの数であり、実際の件数（148 件 / 176 件）ではなかったことも分かった。

**どちらも、指示書を書くときにコマンドを実行していれば防げた。** 記載した時点では、実行せずに
リポジトリの慣習から書いている。

## 次に変えること

| 変えること | 落とし先 | 状態 |
| --- | --- | --- |
| 版を上げる担い手と時期を工程へ明記する | `development-workflow` / `release-verification` の手順 | #188 として起票 |
| 手順の文書に書くコマンドは、書く前に実行して結果を確かめる | `AGENTS.md` の取り決め | この変更で反映 |

版を上げる工程は、`merged` と `release-verification` の間に置き場所が無い。単独の変更では
担当が版も上げるため表面化しなかったが、複数の Pull Request をまとめてマージすると、誰の
担当でもないまま残る。

コマンドの確認は、`markdown-writing` のルール 6（否定的な結論にエビデンスを添える）が
扱う範囲の外にある。実行できることは肯定的な主張であり、エビデンスを求める対象になって
いなかった。
